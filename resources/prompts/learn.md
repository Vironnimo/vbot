Author a reusable skill for yourself from the request below. A skill is a SKILL.md playbook that teaches you how to handle a specific task or domain.

The request may mix two kinds of content, in any order: sources to learn from (a folder, a URL, pasted text, "what we just did") and requirements that shape the skill (focus, scope, what to leave out, the angle to take). Every part is load-bearing — prose after a path or link is the user telling you what they want from that source. Gather every source named and honor every requirement; never fetch the first source and ignore the rest.

Use `skill_manage` to publish exactly one well-formed private vBot Skill package. Every call takes exactly one top-level operation object; begin with `{"begin":{"name":"short-hyphenated-name","mode":"create"}}`, copy the returned `draft_id`, and use calls such as `{"put_file":{"draft_id":"<returned id>","path":"SKILL.md","content":"..."}}`. Never send flat `operation`, `name`, or `draft_id` fields. Put the Skill's `SKILL.md` into the draft, add every required support file, validate the complete draft, then commit it. Abort instead of committing when validation or source review exposes a problem. A vBot Skill package contains exactly `SKILL.md` plus optional files under `scripts/`, `references/`, and `assets/`; do not invent another top-level path.

The `SKILL.md` needs YAML front matter with `name` (matching the Skill's directory) and a `description` of one or two sentences stating when to load the Skill — name the concrete trigger situations, do not repeat the Skill name, no filler words. A future Session decides from the description alone whether this Skill applies, so make the trigger obvious.

Structure the body with clear sections in this order, omitting a section only when it genuinely has no content: Overview (what it is for and what it does not do), When to use (concrete trigger phrases), Prerequisites (required Tools, credentials, setup), Steps (the numbered procedure, with commands exactly as they appear in the source), Pitfalls (edge cases, gotchas, things that look broken but are not), Verification (one check that proves the procedure worked). Keep it tight and scannable — around 100 lines for a simple Skill, 200 for a complex one; do not re-paste the source.

Frame any Tool usage in terms of vBot's actual Tools — `read`, `write`, `edit`, `glob`, `grep`, `bash`, `web_fetch`, `web_search`, `process`, `status` — and do not invent Tools, commands, flags, paths, or facts that are not in the source. If a source is a folder or URL, read it first with your file/web Tools; if it is the recent conversation or pasted text, work from that. Capture only what is genuinely there. A non-trivial script belongs under `scripts/` and is referenced from `SKILL.md` by relative path, not inlined; longer reference material goes under `references/`; starter files and output resources go under `assets/`. Use `put_file` with text `content`, or with `source_path` when a source file must be copied byte-for-byte.

After creating the skill, tell the user in one or two sentences what skill you created and when it will help. Do not paste the full SKILL.md back.
