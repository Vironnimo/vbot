# Tool Review Workflow

The procedure for reviewing, repairing or redesigning an Agent-facing Tool or Tool family, and for adding a new one. The design rules it applies live in `.vorch/domain-maps/tools/designing-agent-tools.md`; per-Tool contracts live in the sibling maps under `.vorch/domain-maps/tools/`. Work one family at a time and finish it (tests, docs, commit) before the next.

## Instruments

All three run from the checkout root and never touch a real installation.

- `python -m scripts.tool_lab definitions [--agent ID] [--all] [--show NAME]` - the System Prompt blocks and Tool definitions a fresh Agent of a fresh Runtime receives, with token estimates. `--show` prints one block, or one Tool in readable form and as sent. `--all` adds Tools outside the default allowlist.
- `python -m scripts.tool_lab probe <cases.json> [--case TEXT] [--visible] [--max N]` - dispatches calls through the production executor with the Agent's compiled input contracts (argument repair, validation, handler, envelope), each case in a fresh copy of the seeded Workspace. It prints each call, the Model-visible result (the text Provider wires send, not the persisted envelope) with its token estimate, and the files a case names; carriage returns always print as `\r`, and `--visible` also shows tabs as `\t`. Case format: the `scripts/tool_lab/probe.py` docstring. Family case files live in `scripts/tool_lab/cases/<family>.json`; their expectations state the target behavior, so a `FAIL` line is an open gap and the pass count tracks the review.
- `python -m scripts.tool_lab sessions <sessions.db or data dir> [--work DIR] [--tool NAME] [--by-arg KEY] [--since DATE] [--model TEXT] [--agent ID] [--export FILE]` - measures real calls in a copy made with SQLite's online backup API, so a running server keeps working. A pre-Generation-1 copy is converted in the copy with the persistence converter. The overview shows calls, failures, codes and result sizes per Tool; `--tool` adds argument keys (marking keys the current schema lacks), failure shapes with an example, what followed each failure in the same Run, identical repeats and failure rates per Model; `--by-arg command` groups shell calls by their first word.
- Black-box task evaluations: `scripts/probe_provider_tool_call.py --scenario tool_first_use` owns first-use task evaluations (currently search and delegation, `--first-use-tool`); add a family's task cases there. The other scenarios of that script prescribe calls and are conformance probes. For Luna, select `--provider openai --connection openai:subscription` explicitly; never run Luna through OpenCode Go or inherit the script's default Provider.

Session data is the user's private data. Keep database copies outside the repository and delete them when the review ends. Case files use synthetic content; findings in docs, commits and case files carry counts and short anonymized shapes, never raw private messages, paths or secrets.

## Procedure per family

1. **Scope.** List the family members, their System Prompt guidance blocks, completion notifications and reminders, and every consumer of the public contract: `ToolDisplay`, WebUI rendering of historical calls, E2E fake-provider calls, generated Tool catalogs, persisted Tool Access Policy names and converter rename rules, Skills or prompts that teach the call shape. Before changing a public contract, inventory every accepted shape, default, permission rule and persisted or UI consumer.
2. **Agent view.** Read the definitions and blocks with `definitions --show`. Could a fresh Agent write a correct first call from them alone? Do names, parameter names and formats match the dominant trained habit? Note the token cost.
3. **Session evidence.** Start from what was actually delivered: definitions, arguments, results and the Agent's next decision. Use `sessions --tool` for each member and `sessions --tool <shell> --by-arg command` for shell bypasses of the family's job (searching, reading, editing through the shell). Investigate successful but empty, noisy or truncated results as well as errors, and check an `ok` result's effect where the evidence allows it. Verify suspected false positives and false negatives against independent evidence; separate proven defects from uncertain task outcomes and historical file state. Generation 1 stores each call once (forks share history); deduplicate copies in any other source.
4. **Probe baseline.** Extend the family case file with canonical calls, the other common dialects (Claude Code, Codex, opencode, Hermes), copy mistakes seen in Sessions, placeholder fields, and genuinely ambiguous requests. Every case asserts the resulting state (file content, result text), not only `ok`. Run it before changing anything.
5. **Diagnose** against the principles of the design guide: wrong effect under `ok`, rejected clear intent, error that does not name the next call, noisy or escaped result, misleading or missing guidance, missing capability. Recurring errors may call for a redesign rather than another sentence; current names, shapes and splits into Tools are revisable choices.
6. **Propose.** Target definitions, guidance blocks, result and error texts, with token counts before and after. For consequential open decisions, give options and a recommendation. Present Agent-facing text changes verbatim to the user (`AGENTS.md` -> Communication with the user -> Present Agent-facing text changes).
7. **Implement** with deterministic tests through production dispatch (rules below), then make the probe expectations pass. Keep each change reviewable around its workflow; verify a coordinated change of competing Tools (for example search and shell guidance) together; keep unrelated Tool behavior intact and the repository releasable after every step.
8. **Recheck** after the change: Provider rendering and the non-strict invariant, schema fingerprints, descriptions, `ToolDisplay`, prompts and guidance blocks, E2E fake-provider calls, generated Tool catalogs, and the consumers from step 1. Rerun the family case file and the affected Session views' failure shapes as probes.
9. **Evaluate** with black-box tasks (rules below) when the change affects Tool choice or first use. A live installation round trip is not required.
10. **Document** in the owning Tool map; update the design guide only when a rule changed.
11. **Commit** each verified Tool or coordinated family change as one cohesive releasable unit, with the quality gates of `AGENTS.md` -> Git. Tool work adds no separate gate schedule.

## Evidence rules

Three evidence layers stay separate; transport conformance never substitutes for usability.

- **Deterministic production-dispatch tests** cover every action and mode, consequential defaults, explicit values, recoverable representations and ambiguous or unsupported requests. Pair each repair with nearby different and conflicting inputs. Assert independently specified receiving targets, payloads, scope and effects. Do not ask a Model to reproduce malformed JSON as a substitute for these tests.
- **Provider conformance probes** may prescribe arguments to isolate serialization, streaming or schema transport. Label them transport or conformance evidence; they cannot establish Tool choice, first-use understanding or task success.
- **Black-box Model evaluations** supply only a natural user goal, the production definitions and prompts, realistic state, and the competing Tools normally available. Keep expected Tool names, actions, argument shapes, grading criteria and the suspected fix out of Model context. Never force a Tool, demand one call, teach the answer in a test-only reminder, or hide the shell to make a selection pass. Exercise common tasks, defaults, recovery, continuation, and cases where another Tool is the right choice. Use genuine results through completion and judge the requested outcome, including final claims; equivalent valid call sequences pass. Include weaker Models.

Spend effort where uncertainty is: deterministic tests cover known argument and runtime variants; Model trials resolve open questions about choice and use. Batch independent checks, reuse relevant evidence, expand trials around observed failures, and do not rerun unchanged passing checks or use exhaustive exact-JSON Model matrices as a usability gate.

## Reporting

- Repeat fresh trials with fixed settings, compare unchanged cases before and after where possible, and keep evaluation variants out of tuning.
- Preserve every attempt and diagnostic response, including no-call replies, timeouts, wrong selections and retries. Report first-attempt success separately from recovery and final outcome, always with denominators. Reruns or changed thinking effort never erase failures. State fixture limitations and unresolved failures.
- Token counts follow the design guide (Token Cost). Count repeated history exposure separately from a payload counted once, never attribute whole-Run Provider usage to one Tool, never present unrelated live workloads as proof of savings, and name measurements that were unavailable. Present absolute counts and deltas next to outcome quality.
