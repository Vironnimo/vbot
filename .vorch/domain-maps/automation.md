# Automation

Programmatic Run triggering, time- and startup-based scheduling, and background self-improvement reviews in `core/automation/`.

## Overview

`TriggerService` is the kernel bridge for non-WebUI producers starting normal chat Runs: cron jobs, Bootstrap jobs, channels, maintenance work, coalesced background-completion delivery. It owns no second execution path - it calls Chat and uses the same `ChatRunManager` guard and FIFO as browser sends. `CronService` owns persisted time-based jobs under `<data_dir>/cron/jobs.json`; `BootstrapService` owns startup-triggered jobs under `<data_dir>/bootstrap/jobs.json`, activated by the server only after the lifespan reaches application-ready. Server RPCs and the CLI are thin clients; scheduling behavior lives in this domain. Bootstrap deliberately has no Agent Tool or WebUI surface. `ReflectionService` owns background self-improvement reviews (shared fork-review orchestration plus the automatic cadence).

## Interfaces

- `TriggerService` is DI-wired with the command ChatLoop and the streaming trigger ChatLoop; programmatic Runs stream through the same SSE path as normal sends.
- Calendar actions reuse `TriggerService` with visible `RunKind.CALENDAR` Runs. Calendar owns their relative schedule, expiry, claims, and recovery (`calendar.md`); they are not Cron jobs and have no Cron Tool operations.
- `trigger_run(...)` starts or queues through the trigger loop, forwarding reply surface, static Tool ceiling, live denial resolver, persistence hook, Run origin/kind, activity policy, and the narrow restart-recovery flag through every admission path. No `session_id` creates a Session only after target/model/provider preflight passes, so a rejected trigger never leaves an empty Session. Channels supply `RunKind.CHANNEL`, Cron `RunKind.CRON`, Bootstrap internal `RunKind.SYSTEM` with activity disabled; `internal=True` persists a note instead of a visible turn. Attention opt-out is explicit - neither `internal` nor run kind alone implies exclusion. Only Bootstrap may pass `resume_process_restart`.
- **Completion coordinator:** producers submit uniquely identified Bash/Sub-Agent terminal results (`submit_completion`) whose Future resolves only when durably persisted into a combined completion note; terminal exceptions mean no durable target exists. Chat's request-boundary seam (`deliver_background_completions`) persists ready results as one note before pending notes drain, under the Session write lock; `cancel_completion` withdraws a notice when an equivalent manual Result reached history first. When an idle Session needs a follow-up Run, the coordinator recovers its latest persisted `ReplySurface` through Sessions' newest-prefixed-Note read rather than loading history; Runtime injects the Channel relay so a Channel-surface result is delivered through the ordinary adapter instead of remaining transcript-only.
- `has_active_run(...)` is a synchronous predicate delegate letting producers refuse conflicting actions without depending on the run manager directly.
- Manual Compaction runs through `start_compaction_run` as an observable Run (same lifecycle events as automatic); `compact_session` remains the synchronous compatibility wrapper mapping outcomes to legacy reply strings.
- `CronService`/`BootstrapService`: lazy job loading returned as clones, atomic persistence, one invalid entry logged/skipped/preserved while valid siblings schedule; malformed whole-file storage disables scheduling/activation without failing Runtime startup and blocks mutations so unreadable state cannot be overwritten. Both job files are Generation 1 documents `{"format_version": 1, "jobs": [...]}` (contract in `settings.md`): unknown fields survive saves, and only the document root guards writes.
- Cron's internal `_cron_jobs.py` owns records, JSON diagnostics and field normalization; `_cron_schedule.py` owns pure parsing, schedule normalization and projections with explicit timezone/time inputs. `_cron_claims.py` owns once-job fire claim files and `_cron_timing.py` owns interruptible wall-clock waits and retry timing. `CronService` retains the job catalog, reference/capacity checks, tasks and Run admission; its public schedule methods supply the current application timezone and clock.
- Cron lifecycle: idempotent start/stop; start reconciles all jobs before any task; an escaping scheduler-task exception flows through the failure-health path; completion from a stale replaced task never restarts its replacement.
- **Bootstrap lifecycle:** Every Runtime start has a UUID `startup_id`; creating/updating/enabling arms a job with it so it cannot fire in the arming process. `once` completes/fails only after an admitted Run terminates (an `interrupted` Run counts as unsuccessful -> retry policy); `always` stays active at most once per startup. Activation groups fixed-Session jobs per owner for sequential execution within four global slots; session-less jobs create fresh Sessions; crash reconciliation asks Sessions for the claimed Run's exact persisted terminal summary instead of loading its complete transcript before deciding whether to retry.

New Cron and Bootstrap job ids use `cron_` and `boot_` plus 12 lowercase base32 characters. Synchronous creation checks the loaded job catalog and retries collisions before publication; persisted ids remain stable on load/update (`cron.py`, `bootstrap.py`, owning tests).

## Conventions

- Validation: both stores export strict validators consumed by diagnostics; whole-file failures raise `CronStorageError` on mutation, bad data raises `CronJobValidationError`. Bootstrap modes `once|always`, statuses `active|paused|completed|failed`; completed one-shots are immutable history, failed ones rearm. Rearming clears the old Run/Session reconciliation references so the previous terminal result cannot undo the new activation.
- Schedules: `schedule_type` is `cron` / `interval` / `once` with kind-owned fields cleared on change; `remaining_runs` patches preserve on omission, replace on integer, `null` unlimited only for recurring. Statuses: `completed`/`missed` are immutable terminal history; `failed` re-enables after cause fix (resetting its failure counter); only `active` holds a scheduler task. Timestamps persist UTC with explicit offsets; naive once `run_at` interprets in the application timezone from `server.timezone`; creating a once job, changing its `run_at`/schedule type, or activating it (enable, failed rearm) with an elapsed `run_at` raises `CronJobInPastError` (user decision) instead of firing immediately - only jobs that became past during downtime reconcile to `missed`; a stored per-job `timezone` is an unknown field: ignored, kept on save, and reported by `doctor config`.
- Names: human-readable, need not be unique (id is identity), derived once from the first useful prompt line when omitted at creation (capped 80 chars); a stored job requires `name`. The Generation 1 converter backfilled legacy nameless records with the same derivation and dropped the retired per-job `timezone`.
- Cron grammar is exactly five fields (minimum cadence one minute); parsing, mutations, and job loading also require a reachable next fire within croniter's search horizon, so impossible dates are rejected before persistence or skipped and preserved on load. Calendar projections use half-open UTC windows, including exact start ticks (`tests/core/automation/test_cron.py`, `test_cron_projection.py`). Cron is evaluated with `croniter` in the application IANA timezone including future DST; intervals use their persisted anchor and skip missed ticks rather than approximating into cron. Runtime injects the effective Settings zone and `set_timezone` wakes cron sleepers so a live setting change reprojects before firing; intervals and once jobs remain absolute UTC instants. Accessors must not duplicate interval/croniter/timezone logic - the service owns parse/format/projection.
- Execution health (`last_*`, `consecutive_failures`) persists per job: a fire takes one of four global Cron Run slots as `RunKind.CRON` with activity disabled, consumes one finite `remaining_runs` slot after admission, waits terminally; one job never overlaps itself, slow Runs skip intervening instants, five consecutive recurring failures stop the job as `failed`, success clears the counter. Capacity bounds: 512 stored / 64 active jobs; terminal history blocks no deletions, live references do.
- Changing schedule/count/status restarts an active sleeper; during queued admission or an admitted Run it defers the restart until that execution settles, retaining its global slot and preventing overlap. Name/prompt/agent/session updates do not restart it (the task reloads before firing).
- References: target validation is core-owned (RPC/Tool edges only parse `agent@projekt` spelling). Cron create/update resolves the target and raises a `CronTargetError` (a `CronJobValidationError`) on failure: a missing Agent or Project raises `CronTargetAgentNotFoundError` / `CronTargetProjectNotFoundError` ("Cron target does not exist"), which are also the resolver's not-found errors so RPC reports `agent_not_found` / `project_not_found`; a target that exists but cannot run (for example, no usable Model) raises `CronTargetUnavailableError` with the resolver's reason ("Cron target <target> cannot run: ...") and stays `domain_error`. Bootstrap surfaces the resolver error unwrapped. A cron job may target a Project agent via stored separate fields; firing creates a fresh Project-anchor Session unless pinning an owned existing one. Project removal blocks only on non-terminal qualified jobs; Identity deletion blocks only on non-terminal identity jobs; rename retargets only non-terminal identity jobs. Non-completed Bootstrap jobs join the same coordination and share the server reference lock.
- Active once jobs write durable fire claims before triggering: pre-admission failure removes and retries with bounded backoff then abandons; an admitted Run consumes the fire even if it later fails; persistence failures retry saves with a bounded attempt cap, then log and continue on in-memory state without refiring. Pre-admission trigger failures never advance a job's execution-failure counter - only an admitted Run's failure can push a recurring job to the five-strike stop. At-most-once beats duplicate execution across restarts: a persisted claim reconciles to completed with an unknown outcome and a restart diagnostic, even if the crash preceded admission. Cron never replays that uncertain fire; Bootstrap uses the separate terminal-summary recovery described above. A claim file that exists but cannot be read at start holds only that once job for the process (WARNING; not scheduled, not reconciled as missed, file kept for the next start). Claims (`cron/once-fire-claims/<sha256 of job id>.json`: `job_id`, `claimed_at`, `run_at`) are transient runtime state outside the JSON document contract (`settings.md`): one exists only from before admission until the job's resulting state is saved or reconciled at the next start, is never edited or converted, is not a data-snapshot member, and fails safe when unreadable. A failed save of startup reconciliation keeps the reconciled state in memory and its claims on disk; only an unreadable or invalid `jobs.json` degrades Cron storage. Every `jobs.json` and claim write runs on the `cron` `OrderedWorker` (`runtime.md`) in submission order, from a snapshot taken on the Event Loop: job tasks await their writes off the loop, while job edits, deletion and the startup reconciliation block on the same writer, so an edit's save lands after an in-flight fire save. A fire re-reads its job after the first save and does not trigger when an edit meanwhile removed or deactivated it. A crashed job task's failure accounting (a done callback) saves with the blocking variant.
- Background completions key exactly `(project_id, agent_id, session_id)` and capture their active Run: ready results inject at Model-request boundaries without extra requests or split Tool cycles; unconsumed notices deliver in one internal follow-up Run, recovering and persisting the latest `ReplySurface`, or persist as a System Reminder when that cannot start (the append runs on the Sessions worker pool; failures retry capped at 30s). A configured relay consumes the follow-up Run events for accessor delivery while the coordinator still owns durable note acknowledgement. Every completion message opens by stating it is not a new request and the Agent must re-evaluate the original goal; user-cancelled origins append notes instead of starting Runs - no cancellation-triggered cascades.

Extension-owned completion notices additionally retain their exact execution owner.
Submission checks that owner through the injected owned-completion validator
(Runtime wires the temporary-group Run admission check) and rejects a closed epoch,
replaced generation, or retired registration before any state is kept; without a
validator, owned notices are rejected. The Session-write fallback for a
user-cancelled origin checks the owner again, because that write bypasses Run
admission. Admitted notices join only a matching owned Run's request boundary or use
the injected owned continuation starter; admission failure never falls back to an
arbitrary Session write. Group closure withdraws only matching pending notices and
keeps no per-group state: late submissions fail validation, which matters because a
Terminal's stale activity owner can submit long after the group closed. Unrelated
notices retain normal delivery behavior (`automation.py`,
`tests/core/automation/test_automation_completion.py`,
`tests/core/runtime/test_runtime_extension_host.py`).

## Reflection (background self-improvement reviews)

`ReflectionService` exposes `run_review(...)` and the cadence trigger:

The bundled review briefs classify candidates before authoring: durable facts go
to Memory, supported reusable procedures to Skills, and already captured or
low-value material needs no write. A missing write capability never changes the
candidate's destination. Candidates are checked against current Tool reads rather
than inherited prompt snapshots; Skill maintenance replaces obsolete guidance in
the affected passage. These are Model instructions, not semantic runtime guards.
`tests/core/automation/test_reflection.py` checks brief delivery and dispatch scope;
`scripts/probe_provider_tool_call.py --scenario reflection_workflow` evaluates
decisions against `tests/fixtures/reflection/cases.json` with production guidance,
definitions, and disposable Memory/Skill handlers. Expected outcomes stay outside
the Model context; the probe checks stored effects and read-before-write behavior.

- **Shared review orchestration:** requires an Identity Agent with active `memory` Tool; reads only the source title (`metadata_value_async`) off the Event Loop, then forks same-Agent (always-strip keys applied, pinned Skill catalog kept) with the Agent-display-name title and the scope-specific Run kind committed in the fork's one write transaction, and starts an internal Run in the fork whose admission carries the source Session id. Scope selects brief + dispatch boundary: `memory` -> reflect-memory brief with only `memory`; `skill` -> skill brief with `skill`+`skill_manage`; `combined` -> combined brief with all three. No Run-local Tool grant - fork keeps source definitions and prompt unchanged; each brief states all other Tools are disabled. The review is a real Run (admission, cancellation, viewing, history, traces) but produces no attention status; the source Session is untouched; `/reflect` rejects before forking when Memory is inactive.
- **Cadence trigger** fires non-blocking at every Run end, and its Settings read and counter write run on the bounded `reflection` worker pool, never on the Event Loop: internal Runs, empty workspaces, inactive memory Tools, and Sub-Agent Sessions never count. Each completed visible Run (and each user-cancelled one with >=1 completed Model step) increments counters in canonical Session metadata; a dispatched memory call resets the Memory counter even if the Run later fails; iteration counting uses Chat's canonical count, never derived from messages. Settings read live per boundary; at interval one scoped review fires (both due -> combined). Counts consume only on successful completion - failed reviews stay due; one review at a time per Agent; due Sessions during a review keep counters for next end. The review being internal never re-triggers accounting; forks strip counters and restart at zero.
- `reset_counters` zeroes and advances generation (manual `/reflect` covers both dimensions). Cadence resets from `memory` or `skill_manage` also advance that generation, so an older in-flight review cannot consume activity counted after a reset. `aclose()` rejects later notifications and clears per-Agent guards.
- Attribution: the server event bridge stamps the review Run's `source_session_id` onto its payloads (`server/events-and-reconnect.md`); background forks appear in the drawer on next load; manual reviews report via the command change observer projected to `resource_changed(sessions)`. Automation and Chat never import the server event bus.

## Constraints & Gotchas

- Runtime startup without asyncio loop wires Cron but never starts scheduler tasks.
- Bootstrap activates only via the server's post-ready hook - never inside `Runtime.start()`.
- Busy-session queueing shares `ChatRunManager`'s 32-item system ceiling; queued triggered work dies on restart. Removing one queued item surfaces `RunCancelledError` to its producer rather than cancelling the producer task; recurring Cron jobs retain scheduling, while a removed one-shot settles as failed and releases its fire claim. Actual producer-task cancellation still propagates as cancellation.
- `TriggerService` owns each supplied Waiting-Work Admission through admission: Queue transfer consumes it, while immediate starts (including fresh Sessions), failures, and cancellation release it. Callers must not depend on an unrelated later cleanup to return shared capacity (`test_automation.py`).
- Completion buckets, dedup, retries, and remembered cancelled origins are process-local; delivery waits at Run boundaries rather than queuing one Run per producer. Once the fallback note persists, the reminder itself is durable across restarts.
- Missed once jobs log warn and become `missed` (no fabricated timestamps); missed ticks never replay - the next fire computes from current time. Fired once jobs retain as `completed`.
- Cron ticks always advance in UTC: repeated-hour wall times use only their first occurrence, and elapsed first occurrences are skipped. Spring-gap fires shift forward by the gap; projection resumes from that resolved wall time to match live scheduling without duplicate instants (`test_cron.py`, `test_cron_projection.py`).
