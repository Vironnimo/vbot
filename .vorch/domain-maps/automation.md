# Automation

Programmatic Run triggering, time- and startup-based scheduling, background self-improvement reviews, and the Librarian's Skill curation in `core/automation/`.

## Overview

`TriggerService` is the kernel bridge for non-WebUI producers starting normal chat Runs: cron jobs, Bootstrap jobs, channels, maintenance work, coalesced background-completion delivery. It owns no second execution path - it calls Chat and uses the same `ChatRunManager` guard and FIFO as browser sends. `CronService` owns persisted time-based and calendar-event-based jobs under `<data_dir>/cron/jobs.json`; `BootstrapService` owns startup-triggered jobs under `<data_dir>/bootstrap/jobs.json`, activated by the server only after the lifespan reaches application-ready. Server RPCs and the CLI are thin clients; scheduling behavior lives in this domain. Bootstrap deliberately has no Agent Tool or WebUI surface. `ReflectionService` owns background self-improvement reviews (shared fork-review orchestration plus the automatic cadence). `LearningChanges` (`core/automation/learning.py`) reads and undoes the Memory and Skill changes of one Run. `LibrarianService` (`core/automation/librarian.py`) curates each Identity Agent's own Skills on a schedule (-> Librarian). `GoalService` (`core/automation/goals.py`) owns Session Goals: `/goal` and the automatic Runs that pursue one (-> References).

## Terms

### Session Goal

An objective the user sets for one Session with `/goal`. While it is active, the end of each completed Run starts the next automatic Run until the Agent marks it complete, blocked or paused with `update_goal` or the kernel pauses it. Not a Cron job or Bootstrap job: it has no schedule and lives in Session metadata.

## Interfaces

- `TriggerService` is DI-wired with the Runtime's one ChatLoop; programmatic Runs stream through the same SSE path as normal sends.
- Calendar events drive Cron jobs of schedule type `event` (Conventions -> Event jobs); the calendar keeps events only and runs nothing (`calendar.md`). `CronService` reads it through the narrow `EventCalendar` protocol (`_cron_events.py`: `get_event`, `iter_occurrences`, `system_timezone_name`, `add_changed_callback`) and serves the calendar's `EventJobs` protocol (`core/calendar/event_jobs.py`: `check_event_change`, `event_deleted`). Runtime builds the calendar first, passes it as `CronService(calendar=)` and binds the service back with `CalendarService.bind_event_jobs`; the calendar never imports automation.
- `trigger_run(...)` starts or queues through the trigger loop, forwarding reply surface, static Tool ceiling, live denial resolver, per-Run Tool-iteration limit, persistence hook, Run origin/kind, and activity policy through every admission path. No `session_id` creates a Session only after target/model/provider preflight passes, so a rejected trigger never leaves an empty Session. That path also accepts the new Session's `working_project_id` and creation `actor`, passing both to Chat's owning admission method. Channels supply `RunKind.CHANNEL`, Cron `RunKind.CRON`, Bootstrap internal `RunKind.SYSTEM` with activity disabled; `internal=True` persists a note instead of a visible turn. Attention opt-out is explicit - neither `internal` nor run kind alone implies exclusion.
- **Completion coordinator:** producers submit uniquely identified Bash/Terminal/Sub-Agent results (`submit_completion`), keyed exactly `(project_id, agent_id, session_id)`, whose Future resolves only when durably persisted into a combined completion note; terminal exceptions mean no durable target exists. Ready results join an active Run at its next Model-request boundary (Chat's `deliver_background_completions` seam) without extra requests; otherwise one internal follow-up Run delivers them, or a System Reminder note when that cannot start. `cancel_completion` withdraws a notice only until a delivery claims it; after that the result is delivered once, as submitted. User-cancelled origins append notes instead of starting Runs - no cancellation-triggered cascades. Extension-owned notices keep their exact execution owner and never fall back to an arbitrary Session write. Delivery detail -> `automation/completion-delivery.md`.
- `has_active_run(...)` is a synchronous predicate delegate letting producers refuse conflicting actions without depending on the run manager directly.
- Manual Compaction runs through `start_compaction_run` as an observable Run (same lifecycle events as automatic); `compact_session` remains the synchronous compatibility wrapper mapping outcomes to legacy reply strings.
- `CronService`/`BootstrapService`: lazy job loading returned as clones, atomic persistence, one invalid entry logged/skipped/preserved while valid siblings schedule; malformed whole-file storage disables scheduling/activation without failing Runtime startup and blocks mutations so unreadable state cannot be overwritten; a job file that cannot be checked counts as unreadable (Cron seeds only a missing `cron/jobs.json` empty). Both job files are Generation 1 documents `{"format_version": 1, "jobs": [...]}` (contract in `json-documents.md`): unknown fields survive saves, and only the document root guards writes.
- **Automation references:** `AutomationReferences` (`references.py`; Runtime builds it over the Bootstrap and Cron services as `Runtime.automation_references`) owns which automations still count as live references, and the reference lock; it lives here because Automation owns both pin kinds and their Run admission. Live are non-completed Bootstrap jobs and Cron jobs that can still fire (`CronService.can_fire`): non-terminal (paused and failed count) and, for an event job, with an owed or later occurrence of an existing event (true while the calendar cannot be read). `agent_triggered_skill_names(agent_id)` returns the Skill names those automations of the Identity Agent trigger (`/name` at the start or any `$name` in a job's prompt; the grammar is `core.skills.triggered_skill_names`, shared with Chat), which the Librarian's aging keeps (`automation/librarian.md`). `agent_references(agent_id)` returns those targeting the Identity Agent (a target without a Project; `builder@vbot` names that Project's Agent even when the ids match), `project_references(project_id)` those targeting any Agent of the Project, and `session_references(address)` those that start their Runs in exactly that Session; each as `kind`, `id` and `name` (the job name), sorted by `kind:id` (`tests/core/automation/test_references.py`). Agent delete (through `Runtime.agent_references`, which adds Channels) and Project removal refuse on the first two (`agent.md`, `projects.md`). An Agent rename moves the identity jobs itself, event jobs that cannot fire now included (`runtime/agent-rename.md`); Sessions keep their ids, so pins stay valid. Its `lock` is the server's Agent reference lock (`server.md`): RPC reference checks, the Agent Takeover, every Cron and Bootstrap job create and update (RPC, the cron Tool's `create`/`update` in `tools/cron.md`, and the Bootstrap job of `application.update_continuation`) and the calendar changes that can revive an event job (RPC `calendar.update` and occurrence `calendar.delete`, the calendar Tool's `update` and `delete`, `tools/calendar.md`) serialize on it, from the check through the change (`tests/server/rpc/test_automation_methods.py`). `session.delete` refuses a selected Session (`session_in_use`, `server/session-agent-rpcs.md`) and an Agent Takeover (`/agent`) refuses to move one (`chat/commands.md`).

## Conventions

Mechanics -> `automation/cron.md`; jobs bound to calendar events -> `automation/event-jobs.md`.

- `CronService` owns schedule parsing, formatting and projection in the application timezone (`server.timezone`, injected by Runtime); accessors must not duplicate interval/croniter/timezone logic.
- A fire is a normal Run through `TriggerService`: Cron `RunKind.CRON`, Bootstrap internal `RunKind.SYSTEM`, both with activity disabled and within four global Run slots per service.
- **Catch-up** (user decision 2026-10-08): a fire that came due while vBot did not run the job (server off, computer asleep, a stalled scheduler) starts once, late, for the most recent missed due time; earlier missed due times are counted, never replayed. The late Run gets a `context_note`, read as a System Reminder, so it can adapt or decline; no limit bounds how late it starts (the former per-job `max_delay_seconds` is an ignored unknown field).
- **Event jobs** (user decision 2026-10-08, replacing the Calendar actions): a Cron job of schedule type `event` binds to every occurrence of one calendar event through an event time such as `start - 30m`, runs once per occurrence while that occurrence's window is open, never completes, and is deleted with its event.
- At-most-once beats duplicate execution across restarts: an active once job writes a durable fire claim before triggering, and a claim left by a crash reconciles to completed with an unknown outcome; Cron never replays that fire.
- Target validation is core-owned: RPC/Tool edges only parse the `agent@project` spelling, and a missing target Agent or Project raises the resolver's not-found errors (RPC `agent_not_found` / `project_not_found`).
- Cron and Bootstrap log each effective job mutation once, at the service, with `actor=` (policy: `logging.md`).

## Reflection

`ReflectionService` owns background self-improvement reviews: a review forks the source Session same-Agent and starts one internal Run in the fork whose brief and dispatch boundary follow the reviewed scope (`memory`, `skill` or `combined`); a dimension exists only while the effective Agent can call all of its Tools. The briefs are Model instructions, not runtime guards, assembled by `core/prompts/briefs.py` (`prompts/learning-briefs.md`). The cadence trigger counts completed visible Runs through Chat's Run completion observer and reviews on the Settings interval. Detail -> `automation/reflection.md`.

- The review is a real Run (admission, cancellation, viewing, history, traces) without attention status and without a limit of its own: like every Run of the Agent it runs under Chat's `MAX_TOOL_ITERATIONS` (user decision 2026-10-03). Its fork stays a Recall-hidden review fork that follows its source (`sessions.md` -> Terms -> Review fork).
- Reviews and Librarian passes of one Agent exclude each other: the Skill dimension is not due while a pass runs, and a pass does not start while an automatic review or a manual Skill review of the Agent is starting or running (`ReflectionService.reviewing`, `LibrarianService.running`).
- Automation and Chat never import the server event bus; the server event bridge stamps the review Run's `source_session_id` onto its payloads (`server/events-and-reconnect.md`).
- **Outcome and undo (user requirement: background learning stays quiet, and every change is traceable and reversible in one step):** `LearningChanges` (Runtime `learning_changes`, `core/automation/learning.py`) reads and undoes, all or none, the Memory and Skill changes of any Run of an Identity Agent (reviews and Librarian consolidation Runs) by `(agent_id, run_id)`, derived from both histories without storing anything new. It is the one place both stores meet; Memory and Skills never know each other (-> `automation/learning-changes.md`).

## Librarian (scheduled Skill curation)

`LibrarianService` (Runtime `librarian`) keeps each Identity Agent's private Skill library small and current. The passes run as the built-in Librarian Agent (`agent.md` -> Built-in Agents, GLOSSARY -> Librarian), a hidden Identity Agent with its own Model and Model settings and only the Tools `skill` and `skill_manage`. Its passes change only that Agent's own unpinned Skills: the brief lists them as the candidates and calls every other Skill read-only, and `skill_manage` never writes global, Project, bundled or Extension Skills. A pass ages out unused unpinned Skills without a Model, then runs one internal consolidation Run of kind `librarian` in a kept Session of the Librarian bound to the Agent (`skill_agent_id`); passes run one at a time over all Agents.

- **Invariants:** every Librarian write is a Skill History revision with actor `librarian` (aging directly through `SkillAuthoringService`, consolidation through `skill_manage` in a Librarian Session, also while the user talks with it there), so the Background Writer guards (`skills.md`) apply (no pinned Skill; `automation/librarian.md` -> A pass). A pass is reversible as a whole through `skill.revert` over the revisions its status lists. `RunKind.LIBRARIAN` is in `UNATTENDED_RUN_KINDS` (its Sessions are not Skill use, its Runs have the Statistics origin `reflection` and count as the Librarian's activity), and a Session carrying it is hidden from Recall and listed only in the Librarian's own scope (`runs.md`, `sessions.md`, `statistics.md`).

## Constraints & Gotchas

- Runtime startup without asyncio loop wires Cron but never starts scheduler tasks.
- Bootstrap activates only via the server's post-ready hook - never inside `Runtime.start()`.
- Busy-session queueing shares `ChatRunManager`'s 32-item system ceiling; queued triggered work dies on restart. Removing one queued item surfaces `RunCancelledError` to its producer rather than cancelling the producer task; recurring Cron jobs retain scheduling, while a removed one-shot settles as failed and releases its fire claim. Actual producer-task cancellation still propagates as cancellation.
- `TriggerService` owns each supplied Waiting-Work Admission through admission: Queue transfer consumes it, while immediate starts (including fresh Sessions), failures, and cancellation release it. Callers must not depend on an unrelated later cleanup to return shared capacity (`test_automation.py`).
- Completion delivery state is process-local; closing it (`TriggerService.aclose`) persists pending notices without an owner as a System Reminder, so Runtime closes it before canonical Sessions (`automation/completion-delivery.md`).
