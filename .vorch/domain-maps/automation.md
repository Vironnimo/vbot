# Automation

Programmatic Run triggering, time- and startup-based scheduling, background self-improvement reviews, and the Librarian's Skill curation in `core/automation/`.

## Overview

`TriggerService` is the kernel bridge for non-WebUI producers starting normal chat Runs: cron jobs, Bootstrap jobs, channels, maintenance work, coalesced background-completion delivery. It owns no second execution path - it calls Chat and uses the same `ChatRunManager` guard and FIFO as browser sends. `CronService` owns persisted time-based jobs under `<data_dir>/cron/jobs.json`; `BootstrapService` owns startup-triggered jobs under `<data_dir>/bootstrap/jobs.json`, activated by the server only after the lifespan reaches application-ready. Server RPCs and the CLI are thin clients; scheduling behavior lives in this domain. Bootstrap deliberately has no Agent Tool or WebUI surface. `ReflectionService` owns background self-improvement reviews (shared fork-review orchestration plus the automatic cadence). `LearningChanges` (`core/automation/learning.py`) reads and undoes the Memory and Skill changes of one Run. `LibrarianService` (`core/automation/librarian.py`) curates each Identity Agent's own Skills on a schedule (-> Librarian).

## Interfaces

- `TriggerService` is DI-wired with the command ChatLoop and the streaming trigger ChatLoop; programmatic Runs stream through the same SSE path as normal sends.
- Calendar actions reuse `TriggerService` with visible `RunKind.CALENDAR` Runs. Calendar owns their relative schedule, expiry, claims, and recovery (`calendar.md`); they are not Cron jobs and have no Cron Tool operations.
- `trigger_run(...)` starts or queues through the trigger loop, forwarding reply surface, static Tool ceiling, live denial resolver, per-Run Tool-iteration limit, persistence hook, Run origin/kind, activity policy, and the narrow restart-recovery flag through every admission path. No `session_id` creates a Session only after target/model/provider preflight passes, so a rejected trigger never leaves an empty Session. Channels supply `RunKind.CHANNEL`, Cron `RunKind.CRON`, Bootstrap internal `RunKind.SYSTEM` with activity disabled; `internal=True` persists a note instead of a visible turn. Attention opt-out is explicit - neither `internal` nor run kind alone implies exclusion. Only Bootstrap may pass `resume_process_restart`.
- **Completion coordinator:** producers submit uniquely identified Bash/Sub-Agent terminal results (`submit_completion`) whose Future resolves only when durably persisted into a combined completion note; terminal exceptions mean no durable target exists. Chat's request-boundary seam (`deliver_background_completions`) persists ready results as one note before pending notes drain, under the Session write lock; `cancel_completion` withdraws a notice when an equivalent manual Result reached history first. When an idle Session needs a follow-up Run, the coordinator recovers its latest persisted `ReplySurface` through Sessions' newest-prefixed-Note read rather than loading history; Runtime injects the Channel relay so a Channel-surface result is delivered through the ordinary adapter instead of remaining transcript-only.
- `has_active_run(...)` is a synchronous predicate delegate letting producers refuse conflicting actions without depending on the run manager directly.
- Manual Compaction runs through `start_compaction_run` as an observable Run (same lifecycle events as automatic); `compact_session` remains the synchronous compatibility wrapper mapping outcomes to legacy reply strings.
- `CronService`/`BootstrapService`: lazy job loading returned as clones, atomic persistence, one invalid entry logged/skipped/preserved while valid siblings schedule; malformed whole-file storage disables scheduling/activation without failing Runtime startup and blocks mutations so unreadable state cannot be overwritten; a job file that cannot be checked counts as unreadable (Cron seeds only a missing `cron/jobs.json` empty). Both job files are Generation 1 documents `{"format_version": 1, "jobs": [...]}` (contract in `settings.md`): unknown fields survive saves, and only the document root guards writes.
- Cron's internal `_cron_jobs.py` owns records, JSON diagnostics and field normalization; `_cron_schedule.py` owns pure parsing, schedule normalization and projections with explicit timezone/time inputs. `_cron_claims.py` owns once-job fire claim files and `_cron_timing.py` owns interruptible wall-clock waits and retry timing. `CronService` retains the job catalog, reference/capacity checks, tasks and Run admission; its public schedule methods supply the current application timezone and clock.
- Cron lifecycle: idempotent start/stop; start reconciles all jobs before any task; an escaping scheduler-task exception flows through the failure-health path; completion from a stale replaced task never restarts its replacement.
- **Bootstrap lifecycle:** Every Runtime start has a UUID `startup_id`; creating/updating/enabling arms a job with it so it cannot fire in the arming process. An Agent rename is not such an edit: it retargets through `retarget_agent`, which changes only the Agent id and keeps status, arming and the Run/Session references, so a paused or failed job stays paused or failed (`tests/core/automation/test_bootstrap.py`, `tests/core/runtime/test_runtime_agent_rename.py`). `once` completes/fails only after an admitted Run terminates (an `interrupted` Run counts as unsuccessful -> retry policy); `always` stays active at most once per startup. Activation groups fixed-Session jobs per owner for sequential execution within four global slots; session-less jobs create fresh Sessions; crash reconciliation asks Sessions for the claimed Run's exact persisted terminal summary instead of loading its complete transcript before deciding whether to retry.

New Cron and Bootstrap job ids use `cron_` and `boot_` plus 12 lowercase base32 characters. Synchronous creation checks the loaded job catalog and retries collisions before publication; persisted ids remain stable on load/update (`cron.py`, `bootstrap.py`, owning tests).

## Conventions

- Validation: both stores export strict validators consumed by diagnostics; whole-file failures raise `CronStorageError` on mutation, bad data raises `CronJobValidationError`. Bootstrap modes `once|always`, statuses `active|paused|completed|failed`; completed one-shots are immutable history, failed ones rearm. Rearming clears the old Run/Session reconciliation references so the previous terminal result cannot undo the new activation.
- Schedules: `schedule_type` is `cron` / `interval` / `once` with kind-owned fields cleared on change; `remaining_runs` patches preserve on omission, replace on integer, `null` unlimited only for recurring. Statuses: `completed`/`missed` are immutable terminal history; `failed` re-enables after cause fix (resetting its failure counter); only `active` holds a scheduler task. Timestamps persist UTC with explicit offsets; naive once `run_at` interprets in the application timezone from `server.timezone`; creating a once job, changing its `run_at`/schedule type, or activating it (enable, failed rearm) with an elapsed `run_at` raises `CronJobInPastError` (user decision) instead of firing immediately - only jobs that became past during downtime reconcile to `missed`; a stored per-job `timezone` is an unknown field: ignored, kept on save, and reported by `doctor config`.
- Names: human-readable, need not be unique (id is identity), derived once from the first useful prompt line when omitted at creation (capped 80 chars); a stored job requires `name`.
- Cron grammar is exactly five fields (minimum cadence one minute); parsing, mutations, and job loading also require a reachable next fire within croniter's search horizon, so impossible dates are rejected before persistence or skipped and preserved on load. Calendar projections use half-open UTC windows, including exact start ticks (`tests/core/automation/test_cron.py`, `test_cron_projection.py`). Cron is evaluated with `croniter` in the application IANA timezone including future DST; intervals use their persisted anchor and skip missed ticks rather than approximating into cron. Runtime injects the effective Settings zone and `set_timezone` wakes cron sleepers so a live setting change reprojects before firing; intervals and once jobs remain absolute UTC instants. Accessors must not duplicate interval/croniter/timezone logic - the service owns parse/format/projection.
- Execution health (`last_*`, `consecutive_failures`) persists per job: a fire takes one of four global Cron Run slots as `RunKind.CRON` with activity disabled, consumes one finite `remaining_runs` slot after admission, waits terminally; one job never overlaps itself, slow Runs skip intervening instants, five consecutive recurring failures stop the job as `failed`, success clears the counter. Capacity bounds: 512 stored / 64 active jobs; terminal history blocks no deletions, live references do.
- Logging (policy: `logging.md`): Cron and Bootstrap log each effective job mutation once at the service at INFO with changed field names and `actor=` (`rpc` from the RPCs, `tool` from the `cron` Tool, `application` for the update-continuation Bootstrap job, `internal` by default); no-ops are silent. The Agent-rename steps `retarget_agent` and `retarget_agent_async` log at DEBUG because the rename logs one summary line. A recurring job stopped after consecutive failures, a fire that could not start its Run because its pinned Session or target is unavailable (`Cron job could not start its Run`, no traceback), an exhausted job that ends `failed`, a once job whose Run was cancelled before admission, and a Bootstrap Run that finishes failed log WARNING (`test_cron.py`, `test_cron_execution.py`).
- Changing schedule/count/status restarts an active sleeper; during queued admission or an admitted Run it defers the restart until that execution settles, retaining its global slot and preventing overlap. Schedule/count/status edits while waiting for a Run slot or the initial fire save withdraw that unadmitted fire, so its replacement waits for the new schedule. Name/prompt/agent/session updates do not restart it (the task reloads before firing).
- References: target validation is core-owned (RPC/Tool edges only parse `agent@projekt` spelling). Cron create/update resolves the target and raises a `CronTargetError` (a `CronJobValidationError`) on failure: a missing Agent or Project raises `CronTargetAgentNotFoundError` / `CronTargetProjectNotFoundError` ("Cron target does not exist"), which are also the resolver's not-found errors so RPC reports `agent_not_found` / `project_not_found`; a target that exists but cannot run (for example, no usable Model) raises `CronTargetUnavailableError` with the resolver's reason ("Cron target <target> cannot run: ...") and stays `domain_error`. Bootstrap surfaces the resolver error unwrapped. A cron job may target a Project agent via stored separate fields; firing creates a fresh Project-anchor Session unless pinning an owned existing one. `AutomationReferences` (`references.py`; Runtime builds it over the Bootstrap, Cron and Calendar services as `Runtime.automation_references`) owns which automations still count as live references, and the reference lock. Live are non-completed Bootstrap jobs, non-terminal Cron jobs (paused and failed count) and Calendar actions that can still fire (`CalendarActions.can_fire`, `calendar.md`). `agent_triggered_skill_names(agent_id)` returns the Skill names those automations of the Identity Agent trigger (`/name` at the start or any `$name` in a job's prompt, or in a Calendar action's prompt, event title and notes; the grammar is `core.skills.triggered_skill_names`, shared with Chat), which the Librarian's aging keeps and a background `skill_manage` delete refuses (`skills.md` -> skill_manage). `agent_references(agent_id)` returns those targeting the Identity Agent (a target without a Project; `builder@vbot` names that Project's Agent even when the ids match), `project_references(project_id)` those targeting any Agent of the Project, and `session_references(address)` those that start their Runs in exactly that Session; each as `kind`, `id` and `name` (job name, or the action's event title), sorted by `kind:id` (`tests/core/automation/test_references.py`). Agent delete (through `Runtime.agent_references`, which adds Channels) and Project removal refuse on the first two (`agent.md`, `projects.md`). Agent rename selects what it moves itself (`_agent_rename.py`, `runtime.md`): the same non-terminal identity Cron and Bootstrap jobs, but every Calendar action of the id; Sessions keep their ids, so pins stay valid. It lives here because Automation owns two of the three pin kinds and the Run admission all three share; Calendar is read through its public service. Its `lock` is the server's Agent reference lock (`server.md`): RPC reference checks, the Agent Takeover, every Cron and Bootstrap job create and update (RPC, the cron Tool's `create`/`update` in `tools/cron.md`, and the Bootstrap job of `application.update_continuation`) and the calendar Tool's `add_action`/`update_action`/`update` (`tools/calendar.md`) serialize on it, from the check through the change (`tests/server/rpc/test_automation_methods.py`). `session.delete` refuses a selected Session (`session_in_use`, `server.md`) and an Agent Takeover (`/agent`) refuses to move one (`chat/commands.md`).
- Active once jobs write durable fire claims before triggering: pre-admission failure removes and retries with bounded backoff then abandons; an admitted Run consumes the fire even if it later fails; persistence failures retry saves with a bounded attempt cap, then log and continue on in-memory state without refiring. Pre-admission trigger failures (full Queue, shutdown) never advance a job's execution-failure counter - only an admitted Run's failure can push a recurring job to the five-strike stop. The exceptions are a pinned Session that no longer exists (`SessionNotFoundError` before admission, for example after a data restore) and a target Agent or Project that no longer exists (`ResolutionAgentNotFoundError` / `ResolutionProjectNotFoundError`): each lasts until the job is edited, so the fire counts toward the stop rule without consuming a finite run and sets `last_error` to the same text that create/update/enable validation raises ("Session does not exist for cron target <target>: <session>", "Cron target does not exist: <target>"); enabling the stopped job therefore fails until it is edited. A target that exists but cannot run (for example, no usable Model) sets "Cron target <target> cannot run: ..." without counting, because it can recover without an edit (`test_pre_admission_trigger_failures_neither_stop_nor_consume_a_recurring_job`). A single transient miss (a fire racing an Agent rename's Session retarget) is cleared by the next success (`test_recurring_job_stops_after_consecutive_failures`). At-most-once beats duplicate execution across restarts: a persisted claim reconciles to completed with an unknown outcome and a restart diagnostic, even if the crash preceded admission. Cron never replays that uncertain fire; Bootstrap uses the separate terminal-summary recovery described above. A claim file that exists but cannot be read at start holds only that once job for the process (WARNING; not scheduled, not reconciled as missed, file kept for the next start). Claims (`cron/once-fire-claims/<sha256 of job id>.json`: `job_id`, `claimed_at`, `run_at`) are transient runtime state outside the JSON document contract (`settings.md`): one exists only from before admission until the job's resulting state is saved or reconciled at the next start, is never edited or converted, is not a data-snapshot member, and fails safe when unreadable. A failed save of startup reconciliation keeps the reconciled state in memory and its claims on disk; only an unreadable or invalid `jobs.json` degrades Cron storage. Every `jobs.json` and claim write runs on the `cron` `OrderedWorker` (`runtime.md`) in submission order, from a snapshot taken on the Event Loop. Job tasks and job edits (`create_job`, `update_job`, `enable_job`, `disable_job`, `delete_job`, all `async`; the RPC handlers and the cron Tool await them) await their writes off the loop, so an edit's save lands after an in-flight fire save and a data snapshot holding `jobs.json` never blocks the loop. An edit first checks its target Agent and selected Session on the Session database's pool (`ChatSessionManager.run_async`), never on the Event Loop, then stages again against the job as a fire may have left it meanwhile (`test_edits_validate_target_and_owned_session_off_the_loop`, `test_a_fire_while_an_edit_checks_its_references_is_kept`). It applies to memory and the job tasks at once (a fire in flight sees it, as before), then saves; a failed save undoes both. Edits run one at a time and finish even when their caller is cancelled (`settle_before_cancelling`, `runtime.md`). An Agent rename moves the jobs of a started service with `retarget_agent_async`, an edit like the others, on the Event Loop, where the rename runs; the blocking `retarget_agent` serves only a rename that completes at startup, before the service starts, and refuses once it runs. Only that and the startup reconciliation block on the writer. A fire re-reads its job after the first save and does not trigger when an edit meanwhile removed or deactivated it. A crashed job task's failure accounting (a done callback) saves in a tracked task that `aclose` awaits.
- Background completions key exactly `(project_id, agent_id, session_id)` and capture their active Run: ready results inject at Model-request boundaries without extra requests or split Tool cycles; unconsumed notices deliver in one internal follow-up Run, recovering and persisting the latest `ReplySurface`, or persist as a System Reminder when that cannot start (the append runs on the Sessions worker pool; failures retry capped at 30s). Blocked admission (a Run Admission Guard) is not a start failure: it does not announce its end, so the notices join a still-active Run of the Session or retry the start with the same 0.25s->30s backoff, logged per attempt at DEBUG (`test_blocked_completion_admission_backs_off_until_admission_reopens`). A configured relay consumes the follow-up Run events for accessor delivery while the coordinator still owns durable note acknowledgement. Every completion message opens by stating it is not a new request and the Agent must re-evaluate the original goal; user-cancelled origins append notes instead of starting Runs - no cancellation-triggered cascades.

Extension-owned completion notices additionally retain their exact execution owner.
Submission checks that owner through the injected owned-completion validator
(Runtime wires the temporary-group Run admission check) and rejects a closed epoch,
replaced generation, or retired registration before any state is kept; without a
validator, owned notices are rejected. The Session-write fallback for a
user-cancelled origin checks the owner again, because that write bypasses Run
admission. Admitted notices join only a matching owned Run's request boundary or use
the injected owned continuation starter; admission failure never falls back to an
arbitrary Session write. A blocked admission re-checks the owner: a stale owner (closed
group, retired Extension) fails its notices terminally like the fallback instead of
retrying. Producers treat that `RunAdmissionBlockedError` as the expected end of the
owner's lifecycle: the Sub-Agent tracker and Terminal attention delivery leave the
result undelivered and log it at DEBUG without a traceback, while any other terminal
failure logs ERROR (`tests/core/subagents/test_tracker.py`,
`tests/core/tools/test_terminal_manager_attention.py`). Group closure withdraws only matching pending notices and
keeps no per-group state: late submissions fail validation, which matters because a
Terminal's stale activity owner can submit long after the group closed. Unrelated
notices retain normal delivery behavior (`automation.py`,
`tests/core/automation/test_automation_completion.py`,
`tests/core/runtime/test_runtime_extension_host.py`).

Once-Cron claim writes join the in-flight execution guard: edits wait for the
write to settle, then withdraw its unadmitted claim before the replacement task
starts. Cancellation during the claim write also removes that known-unadmitted
claim after the ordered writer settles, so a clean restart cannot consume a
rescheduled future fire (`tests/core/automation/test_cron_execution.py`).

## Reflection (background self-improvement reviews)

`ReflectionService` exposes `run_review(...)` and the cadence trigger:

The bundled review briefs classify candidates before authoring: durable facts go
to Memory, supported reusable procedures to Skills, and already captured or
low-value material needs no write. A missing write capability never changes the
candidate's destination. Candidates are checked against current Tool reads rather
than inherited prompt snapshots; Skill maintenance replaces obsolete guidance in
the affected passage. These are Model instructions, not semantic runtime guards.
The briefs are assembled per scope from shared fragments by `core/prompts/briefs.py`
(`reflection_brief`; see `prompts.md`), so shared guidance exists once.
`tests/core/automation/test_reflection.py` checks brief delivery, dispatch scope,
and that each production brief names exactly its scope's Tools.

- **Tool gating:** a review dimension exists only while the effective Agent (Project ceilings and Tool Access Policy denials applied, via `resolve_tool_access`) can call all of its Tools: Memory needs `memory`, Skills need `skill` and `skill_manage`. `available_review_scope(agent, requested)` narrows a requested scope to the callable dimensions (`combined` -> `memory` or `skill`) or returns `None`; it resolves in memory, so `/reflect` calls it on the Event Loop as its pre-check.
- **Shared review orchestration:** requires an Identity Agent and a callable requested scope - otherwise `ReflectionUnavailableError` before forking; `ReflectionResult.scope` names the scope actually reviewed. Assembles the scope's brief (user focus appended) and reads only the source title (`metadata_value_async`) off the Event Loop, then forks same-Agent (always-strip keys applied, pinned Skill catalog kept) with the Agent-display-name title and the scope-specific Run kind committed in the fork's one write transaction, and starts an internal Run in the fork whose admission carries the source Session id. Scope selects brief + dispatch boundary: `memory` -> memory brief with only `memory`; `skill` -> skill brief with `skill`+`skill_manage`; `combined` -> combined brief with all three (briefs: `core/prompts/briefs.py`, wording rows in `prompts.md`). No Run-local Tool grant - fork keeps source definitions and prompt unchanged; each brief names the only Tools that work and the call limit, and the Run's denial resolver answers any other call with `REVIEW_TOOL_DENIAL_MESSAGE` (denied Tool and the scope's Tools by Model name, "Do not retry this call."). The Run passes `max_tool_iterations=REFLECTION_TOOL_ITERATION_LIMIT` (16, `REVIEW_TOOL_CALL_LIMIT` in `briefs.py`, which the brief states) - Chat's per-Run iteration limit (`chat/run-execution.md`). The review is a real Run (admission, cancellation, viewing, history, traces) but produces no attention status; the source Session is untouched.
- **Cadence trigger** fires non-blocking at every Run end, and its Settings read and counter write run on the bounded `reflection` worker pool, never on the Event Loop: internal Runs, empty workspaces, Agents with no callable dimension, and Sub-Agent Sessions never count; an uncallable dimension is neither counted nor reset nor reviewed (its counter stays frozen). Each completed visible Run (and each user-cancelled one with >=1 completed Model step) increments counters in canonical Session metadata; a dispatched memory call resets the Memory counter even if the Run later fails; iteration counting uses Chat's canonical count, never derived from messages. Settings read live per boundary; at interval one scoped review fires (both due -> combined). Counts consume only on successful completion - failed reviews stay due; one review at a time per Agent; due Sessions during a review keep counters for next end. While a Librarian pass of the Agent runs (`librarian_running`, wired to `LibrarianService.running`), the Skill dimension is not due: a due Memory dimension is reviewed alone, and the Skill counts stay due for the first Run end after the pass, because both would change the same Skills from texts each read earlier. In turn a pass does not start while an automatic review of the Agent is starting or running (`ReflectionService.reviewing`, from the trigger's per-Agent guard; the review Run itself also counts as Agent activity). A manual `/reflect` is not deferred; during a pass the Librarian's concurrent-change refusal (`skills.md` -> `skill_manage`) keeps the pass from overwriting the review's changes. The review being internal never re-triggers accounting; forks strip counters and restart at zero. A review that narrowed when it started (Tool access changed after the Run end) consumes only the dimensions it reviewed; one refused with `ReflectionUnavailableError` logs a DEBUG skip and keeps the counts due. A background review logs one INFO outcome line (Agent, source Session, fork, scope, reviewed turns and iterations) or a WARNING on failure; its closing summary is Model output and never enters the log (`test_reflection.py`).
- `reset_counters(..., review_scope)` zeroes the reviewed dimensions' counters and advances generation (manual `/reflect` passes `ReflectionResult.scope`). Cadence resets from `memory` or `skill_manage` also advance that generation, so an older in-flight review cannot consume activity counted after a reset. `aclose()` rejects later notifications and clears per-Agent guards.
- Attribution: the server event bridge stamps the review Run's `source_session_id` onto its payloads (`server/events-and-reconnect.md`); background forks appear in the drawer on next load; manual reviews report via the command change observer projected to `resource_changed(sessions)`. Automation and Chat never import the server event bus.
- **Outcome and undo (user requirement: background learning stays quiet, and every change is traceable and reversible in one step):** `LearningChanges` (Runtime `learning_changes`) is Run-generic - it serves any Run of an Identity Agent (reviews and Librarian consolidation Runs), keyed by `(agent_id, run_id)`. It is the one place both stores meet; Memory and Skills never know each other, and `ReflectionService` stays review-specific. Nothing new is stored: the outcome is derived from the Memory and Skill histories by the Run id that their revisions record, and the review rows already keep that id durably (`chat.reflections`), so it survives reloads and restarts.
  - `of_run(agent_id, run_id)` -> `RunLearningChanges`: one Memory item per entry the Run's `edit` revisions changed for good - its net effect, matched by entry text (`added`/`replaced`/`removed`, `scope`, the resulting or removed entry `text` cut to 160 characters, the Run's `revisions` behind it); an entry the Run added and removed again, or changed back, is no item, so a review that only did that reads `Nothing saved`; one Skill item per Skill name over the Run's non-`revert` revisions (`archived` when the last one moved it out of the home, with `absorbed_into`; else `created`, `changed` when `SKILL.md` changed, `file_written`, `file_removed`), with the changed `files`. Each item names its `revisions` and whether it is `undone`: a revision is undone when a `revert` that is not itself undone names it. `summary` counts the items (`memory`, `skills`) and is `undone` once every item is. `summaries(agent_id, run_ids)` returns the summaries of many Runs from one read of both histories.
  - `undo(agent_id, run_id, workspace=, actor=)` takes back every change of the Run not undone yet, all or none, and records ordinary `revert` revisions (Memory with the caller's `actor`, `rpc` from the RPC; Skills as `human`). It reverts the revisions behind the listed items, so Memory revisions that cancel out within the Run are left alone and never block. A Run that is still running is refused first (`LearningRunActiveError`, "Nothing was undone: the Run is still running. ..."; the Runtime passes `ChatRunManager.is_running`). Both stores are checked before either is written: Memory `check_revert(strict=True, related=)` (which first records outside edits of the files) refuses any later Memory revision in the same scope that added, removed or replaced the change's resulting text (or the removed text), because the Memory history's own revert rule tolerates an effect that is already gone; then Skills `check_revert`, whose rule refuses any later revision that touched the same part. The Memory revert repeats the strict check under its scope locks, so a write that slips in after the check is still a conflict. A refusal raises `LearningUndoConflictError` ("Nothing was undone: ...", naming the entry or Skill and the later revision; `to_dict()` gives `store`, `revision`, `later {revision, at, actor, run_kind?}` and `scope`/`text` or `skill`). The Run's lineage - its revisions plus every revert chain that started from one of them - never blocks, so an undo can be repeated after a partial manual revert or a restored failure. Skills are written first, then Memory; when the Memory revert fails or is refused, the recorded Skill reverts are reverted again - a refusal then surfaces as the conflict, a failure as `LearningUndoFailedError` saying whether nothing was changed or which store stopped part-way (`Undo again to finish`). A Memory revert that stops part-way keeps the written scope recorded as reverted, so the next undo takes back only the rest. A Skill revert that cannot take its own steps back (`SkillRevertIncompleteError`) is a failure, not a refusal. A Skill step the history could not record stays undone and cannot be put back; the result still reports the Skills as changed once the revert returned, so views refresh. An undo with nothing left is a no-op. One in-process lock serializes undos. Each undo logs one INFO line (Agent, Run, revision counts, actor) without entry text (`tests/core/automation/test_learning.py`).
  - Surfaces: `learning.changes` / `learning.undo` and the `outcome` of finished `reflection_runs` rows (`server.md`); the Activity panel (`webui/chat.md`). No CLI.

The learning evaluation (`scripts/probe_provider_tool_call.py --scenario
reflection_workflow`, cases in `tests/fixtures/reflection/cases.json`) runs reviews,
`/learn` and Librarian consolidation against a real Model in a disposable vBot
through production prompt rendering and dispatch, repeats every attempt, scores stored effects and Tool use in
code, and swaps learning texts through text packs. Briefs come from production
`reflection_brief`/`learn_brief`/`librarian_brief` over the run's fragment texts, and
review and Librarian dispatch use production's restrictions, denial answers and
iteration limits, so brief and Run changes reach evaluations through their owners;
a pack holds every fragment in `BRIEF_FRAGMENT_NAMES`.

```
# export the current texts as a pack (edit a copy for a candidate arm)
python -m scripts.provider_probe.learning_eval export-pack ~/.cache/vbot-evals/learning/packs/<name>
# run one arm; omit --text-pack for the checkout's texts
python scripts/probe_provider_tool_call.py --scenario reflection_workflow --repetitions 3 \
  --text-pack <pack> --reflection-report ~/.cache/vbot-evals/learning/reports/<arm>.json
# compare two arms with equal attempt counts per (case, scope)
python -m scripts.provider_probe.learning_eval compare <a>.json <b>.json
```

`--reflection-case` and `--reflection-scope` narrow the matrix; every attempt is a
Provider request loop.

## Librarian (scheduled Skill curation)

`LibrarianService` (Runtime `librarian`) keeps each Identity Agent's private Skill library small and current. It never touches shared-in, global, Project, bundled or Extension Skills. A pass has two parts: aging archives (reason `inactive`, no Model) unpinned Skills that a background Run created and that went unused and unchanged by attended writers for `librarian.archive_after_days`, except Skills a live automation of the Agent triggers and Skills the Agent shares with other Agents; consolidation, which never lists a shared Skill, then runs one internal Run of kind `librarian` in a new hidden Session, restricted to `skill` and `skill_manage`, which merges overlapping Skills into umbrellas (`delete` with `absorbed_into`) and fixes hard-to-use ones. An hourly check starts a pass once `librarian.interval_days` passed since the Agent's last pass, also one that failed or was interrupted (the first one an interval after a check first saw the Agent), only while the Agent has no active or queued Run without a Project and no automatic review is starting (Project Runs execute Config Agents, which never load or change an Identity Agent's own Skills); `librarian.run` / `vbot librarian run` / the Skill manager start one at once. `librarian.enabled` switches scheduled passes off for every Agent; the Agent's own `librarian_enabled` (`agent.md`) excludes it from both scheduled and manual passes. The consolidation Run uses the Agent's Model unless `librarian.model` binds one, stored as overrides of the pass's hidden Session only, so the Agent's other Sessions and their prompt cache are untouched. `librarian.status` names why an Agent gets no scheduled pass (`unscheduled_reason`).

- **Invariants:** every Librarian write is a Skill History revision with actor `librarian` (aging directly through `SkillAuthoringService`, consolidation through `skill_manage` under Run kind `librarian`), so the Background Writer guards (`skills.md`) apply: no pinned, human-origin, shared or unknown-origin Skill, no revert, no delete of a Skill a live automation of the Agent triggers by name or that the Agent shares with other Agents, and no delete without `absorbed_into`; a consolidation Run's first change to a Skill that something else changed after the Run started is refused once, so it merges from the current text. Background reviews and passes of one Agent exclude each other (-> Reflection). A pass is reversible as a whole through `skill.revert` over the revisions its status lists. `RunKind.LIBRARIAN` is in `UNATTENDED_RUN_KINDS` (its Sessions are not Skill use, its Runs have the Statistics origin `reflection`), and a Session carrying it is never listed and hidden from Recall (`runs.md`, `sessions.md`, `statistics.md`).
- **Consolidation default (design decision):** Hermes makes consolidation opt-in; vBot defaults it on because every Librarian write is recorded, reversible and limited to Skills the Agent itself created. Hermes' incidents came from missing guards (user-authored Skills merged, clusters archived without a target, shell moves outside the ledger); the Skill History, pins, origin guards and `absorbed_into` prevent each, the consolidation Run runs only after the candidates changed since the last one, and every change is reported in the Skill manager. Revisit this default only together with those guards.
- **State:** the durable document `agents/<id>/librarian.json` (kind `librarian_state`); an unreadable one stops that Agent's passes until fixed. The report of a pass is derived from the Skill History, nothing else is stored.
- Details (schedule, aging rule, candidates and fingerprint, Run setup, state fields, status, RPC/CLI, shutdown, Agent-facing texts, known gaps) -> `automation/librarian.md`.

## Constraints & Gotchas

- Runtime startup without asyncio loop wires Cron but never starts scheduler tasks.
- Bootstrap activates only via the server's post-ready hook - never inside `Runtime.start()`.
- Busy-session queueing shares `ChatRunManager`'s 32-item system ceiling; queued triggered work dies on restart. Removing one queued item surfaces `RunCancelledError` to its producer rather than cancelling the producer task; recurring Cron jobs retain scheduling, while a removed one-shot settles as failed and releases its fire claim. Actual producer-task cancellation still propagates as cancellation.
- `TriggerService` owns each supplied Waiting-Work Admission through admission: Queue transfer consumes it, while immediate starts (including fresh Sessions), failures, and cancellation release it. Callers must not depend on an unrelated later cleanup to return shared capacity (`test_automation.py`).
- Completion buckets, dedup, retries, and remembered cancelled origins are process-local; delivery waits at Run boundaries rather than queuing one Run per producer. Once the fallback note persists, the reminder itself is durable across restarts.
- Closing completion delivery (`TriggerService.aclose`) persists every still-pending notice without an owner as that System Reminder in one attempt (failure logs ERROR and drops them) and withdraws owned ones, so a result still waiting when the server stops, for an update too, survives the restart. Runtime therefore closes it before canonical Sessions. A worker cancelled mid-append settles that append first, so close never writes it twice (`test_completion_delivery_aclose_persists_pending_results_and_rejects_later_ones`, `test_closing_during_a_reminder_write_persists_it_once`). A follow-up Run admitted just before close that had not yet persisted its input may still persist it: at-least-once, not exactly-once.
- Missed once jobs log warn and become `missed` (no fabricated timestamps); missed ticks never replay - the next fire computes from current time. Fired once jobs retain as `completed`.
- Cron ticks always advance in UTC: repeated-hour wall times use only their first occurrence, and elapsed first occurrences are skipped. Spring-gap fires shift forward by the gap; projection resumes from that resolved wall time to match live scheduling without duplicate instants (`test_cron.py`, `test_cron_projection.py`).
