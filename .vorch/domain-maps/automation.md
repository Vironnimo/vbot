# Automation

Programmatic Run triggering, time- and startup-based scheduling, and background self-improvement reviews in `core/automation/`.

## Overview

`TriggerService` is the kernel bridge for non-WebUI producers starting normal chat Runs: cron jobs, Bootstrap jobs, channels, maintenance work, coalesced background-completion delivery. It owns no second execution path - it calls Chat and uses the same `ChatRunManager` guard and FIFO as browser sends. `CronService` owns persisted time-based jobs under `<data_dir>/cron/jobs.json`; `BootstrapService` owns startup-triggered jobs under `<data_dir>/bootstrap/jobs.json`, activated by the server only after the lifespan reaches application-ready. Server RPCs and the CLI are thin clients; scheduling behavior lives in this domain. Bootstrap deliberately has no Agent Tool or WebUI surface. `ReflectionService` owns background self-improvement reviews (shared fork-review orchestration plus the automatic cadence).

## Interfaces

- `TriggerService` is DI-wired with the command ChatLoop and the streaming trigger ChatLoop; programmatic Runs stream through the same SSE path as normal sends.
- `trigger_run(...)` starts or queues through the trigger loop, forwarding reply surface, static Tool ceiling, live denial resolver, persistence hook, Run origin/kind, activity policy, and the narrow restart-recovery flag through every admission path. No `session_id` creates a Session only after target/model/provider preflight passes, so a rejected trigger never leaves an empty Session. Channels supply `RunKind.CHANNEL`, Cron `RunKind.CRON`, Bootstrap internal `RunKind.SYSTEM` with activity disabled; `internal=True` persists a note instead of a visible turn. Attention opt-out is explicit - neither `internal` nor run kind alone implies exclusion. Only Bootstrap may pass `resume_process_restart`.
- **Completion coordinator:** producers submit uniquely identified Bash/Sub-Agent terminal results (`submit_completion`) whose Future resolves only when durably persisted into a combined completion note; terminal exceptions mean no durable target exists. Chat's request-boundary seam (`deliver_background_completions`) persists ready results as one note before pending notes drain, under the Session write lock; `cancel_completion` withdraws a notice when an equivalent manual Result reached history first. When an idle Session needs a follow-up Run, the coordinator recovers its latest persisted `ReplySurface`; Runtime injects the Channel relay so a Channel-surface result is delivered through the ordinary adapter instead of remaining transcript-only.
- `has_active_run(...)` is a synchronous predicate delegate letting producers refuse conflicting actions without depending on the run manager directly.
- Manual Compaction runs through `start_compaction_run` as an observable Run (same lifecycle events as automatic); `compact_session` remains the synchronous compatibility wrapper mapping outcomes to legacy reply strings.
- `CronService`/`BootstrapService`: lazy job loading returned as clones, atomic persistence, one invalid entry logged/skipped/preserved while valid siblings schedule; malformed whole-file storage disables scheduling/activation without failing Runtime startup and blocks mutations so unreadable state cannot be overwritten.
- Cron lifecycle: idempotent start/stop; start reconciles all jobs before any task; an escaping scheduler-task exception flows through the failure-health path; completion from a stale replaced task never restarts its replacement.
- Every Runtime start has a UUID `startup_id`; creating/updating/enabling arms a job with it so it cannot fire in the arming process. `once` completes/fails only after an admitted Run terminates (an `interrupted` Run counts as unsuccessful -> retry policy); `always` stays active at most once per startup. Activation groups fixed-Session jobs per owner for sequential execution within four global slots; session-less jobs create fresh Sessions; a persisted terminal summary reconciles before retrying after crashes.

## Conventions

- Validation: both stores export strict validators consumed by diagnostics; whole-file failures raise `CronStorageError` on mutation, bad data raises `CronJobValidationError`. Bootstrap modes `once|always`, statuses `active|paused|completed|failed`; completed one-shots are immutable history, failed ones rearm.
- Schedules: `schedule_type` is `cron` / `interval` / `once` with kind-owned fields cleared on change; `remaining_runs` patches preserve on omission, replace on integer, `null` unlimited only for recurring. Statuses: `completed`/`missed` are immutable terminal history; `failed` re-enables after cause fix (resetting its failure counter); only `active` holds a scheduler task. Timestamps persist UTC with explicit offsets; naive once `run_at` interprets in the server timezone; legacy `timezone` fields ignore-and-drop on next save.
- Names: human-readable, need not be unique (id is identity), derived once from the first useful prompt line when omitted (capped 80 chars) and backfilled identically for legacy nameless records.
- Cron grammar is exactly five fields (minimum cadence one minute), evaluated with `croniter` in the server IANA timezone including future DST; intervals use their persisted anchor and skip missed ticks rather than approximating into cron. Accessors must not duplicate interval/croniter/timezone logic - the service owns parse/format/projection.
- Execution health (`last_*`, `consecutive_failures`) persists per job: a fire takes one of four global Cron Run slots as `RunKind.CRON` with activity disabled, consumes one finite `remaining_runs` slot after admission, waits terminally; one job never overlaps itself, slow Runs skip intervening instants, five consecutive recurring failures stop the job as `failed`, success clears the counter. Capacity bounds: 512 stored / 64 active jobs; terminal history blocks no deletions, live references do.
- Changing schedule/count/status restarts an active sleeper; name/prompt/agent/session updates do not (the task reloads before firing).
- References: target validation is core-owned (RPC/Tool edges only parse `agent@projekt` spelling). A cron job may target a Project agent via stored separate fields; firing creates a fresh Project-anchor Session unless pinning an owned existing one. Project removal blocks only on non-terminal qualified jobs; Identity deletion blocks only on non-terminal identity jobs; rename retargets only non-terminal identity jobs. Non-completed Bootstrap jobs join the same coordination and share the server reference lock.
- Active once jobs write durable fire claims before triggering: pre-admission failure removes and retries with bounded backoff then abandons; an admitted Run consumes the fire even if it later fails; persistence failures retry saves with a bounded attempt cap, then log and continue on in-memory state without refiring. Pre-admission trigger failures never advance a job's execution-failure counter - only an admitted Run's failure can push a recurring job to the five-strike stop. At-most-once beats duplicate execution across restarts.
- Background completions key exactly `(project_id, agent_id, session_id)` and capture their active Run: ready results inject at Model-request boundaries without extra requests or split Tool cycles; unconsumed notices deliver in one internal follow-up Run, recovering and persisting the latest `ReplySurface`, or persist as a System Reminder when that cannot start (append failures retry capped at 30s). A configured relay consumes the follow-up Run events for accessor delivery while the coordinator still owns durable note acknowledgement. Every completion message opens by stating it is not a new request and the Agent must re-evaluate the original goal; user-cancelled origins append notes instead of starting Runs - no cancellation-triggered cascades.

## Reflection (background self-improvement reviews)

`ReflectionService` exposes `run_review(...)` and the cadence trigger:

- **Shared review orchestration:** requires an Identity Agent with active `memory` Tool; forks same-Agent (always-strip keys applied, pinned Skill catalog kept), titles the fork from the Agent display name, records the scope-specific Run kind, and starts an internal Run in the fork. Scope selects brief + dispatch boundary: `memory` -> reflect-memory brief with only `memory`; `skill` -> skill brief with `skill`+`skill_manage`; `combined` -> combined brief with all three. No Run-local Tool grant - fork keeps source definitions and prompt unchanged; each brief states all other Tools are disabled. The review is a real Run (admission, cancellation, viewing, history, traces) but produces no attention status; the source Session is untouched; `/reflect` rejects before forking when Memory is inactive.
- **Cadence trigger** fires non-blocking at every Run end: internal Runs, empty workspaces, inactive memory Tools, and Sub-Agent Sessions never count. Each completed visible Run (and each user-cancelled one with >=1 completed Model step) increments sidecar counters; a dispatched memory call resets the Memory counter even if the Run later fails; iteration counting uses Chat's canonical count, never derived from messages. Settings read live per boundary; at interval one scoped review fires (both due -> combined). Counts consume only on successful completion - failed reviews stay due; one review at a time per Agent; due Sessions during a review keep counters for next end. The review being internal never re-triggers accounting; forks strip counters and restart at zero.
- `reset_counters` zeroes and advances generation (manual `/reflect` covers both dimensions; generation prevents overlapping background consumption). `aclose()` rejects later notifications and clears per-Agent guards.
- Attribution: the server event bridge stamps `source_session_id` onto reflection-kind payloads (`server/events-and-reconnect.md`); background forks appear in the drawer on next load; manual reviews report via the command change observer projected to `resource_changed(sessions)`. Automation and Chat never import the server event bus.

## Constraints & Gotchas

- Runtime startup without asyncio loop wires Cron but never starts scheduler tasks.
- Bootstrap activates only via the server's post-ready hook - never inside `Runtime.start()`.
- Busy-session queueing shares `ChatRunManager`'s 32-item system ceiling; queued triggered work dies on restart.
- Completion buckets, dedup, retries, and remembered cancelled origins are process-local; delivery waits at Run boundaries rather than queuing one Run per producer. Once the fallback note persists, the reminder itself is durable across restarts.
- Missed once jobs log warn and become `missed` (no fabricated timestamps); missed ticks never replay - the next fire computes from current time. Fired once jobs retain as `completed`.
