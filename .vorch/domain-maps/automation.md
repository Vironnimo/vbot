# Automation

Programmatic Run triggering, time-based scheduling, and background self-improvement reviews in `core/automation/`.

## Overview

`TriggerService` is the kernel bridge for non-WebUI producers that need to start normal chat Runs: cron jobs, channels, sub-agent batch completion, and background tools. It does not own a second execution path; it calls the Chat domain and uses the same `ChatRunManager` active-Run guard and FIFO queue as browser sends. `CronService` owns persisted time-based jobs under `<data_dir>/cron/jobs.json`, creates one asyncio task per active job while the Runtime is started inside an event loop, and fires due jobs through `TriggerService.trigger_run(...)`. Server cron RPCs (`server/rpc/automation_methods.py`) and the `cron` tool are thin clients; scheduling behavior belongs in `core/automation/cron.py`.

`ReflectionService` (`core/automation/reflection.py`) owns background self-improvement reviews: the shared fork-review orchestration used by both the `/reflect` command and the automatic cadence trigger, plus the cadence policy itself. See the Reflection section below.

## Interfaces

- `TriggerService(chat_loop, chat_run_manager, runtime, trigger_chat_loop=None)` - constructed through DI. Runtime passes the non-streaming ChatLoop for command/compaction helpers and the streaming ChatLoop as `trigger_chat_loop`, so programmatic Runs stream through the same SSE path as normal sends.
- `await trigger_run(agent_id: str, message: str | list[ContentBlock], session_id: str | None = None, *, internal: bool = False, sender: MessageSender | None = None, reply_surface: ReplySurface | None = None, project_id: str | None = None, input_persisted_hook: Callable[[], None] | None = None, contributes_to_agent_activity: bool = True) -> Run` - starts or queues through the trigger ChatLoop and forwards the optional immutable surface, persistence hook, and generic Agent-activity policy through every admission path. With no `session_id`, it calls `ChatLoop.start_run_in_new_session(...)`, whose target/model/provider preflight precedes Session creation so a rejected automation trigger cannot leave an empty Session. Channels supply a reply surface for interactive inbound/internal Runs; cron, sub-agent, background, and maintenance producers leave it `None`. `internal=True` persists a string note instead of a visible user turn; `sender` is forwarded only for non-internal messages. The hook runs only after Chat durably persists the initiating message and is currently used by Subagent batch delivery to record an exact Child read receipt. Producers opt out of attention status explicitly; `internal` alone does not imply exclusion.
- `has_active_run(agent_id: str, session_id: str, *, project_id: str | None = None) -> bool` - synchronous active-run query, a thin delegate to `ChatRunManager.active_run(agent_id=..., session_id=..., project_id=...) is not None`. Lets command producers refuse run-conflicting actions (channels' `/new` refusal) without taking their own dependency on the run manager; `project_id` defaults to the identity scope. Not a coroutine — callers use it as a plain predicate.
- `await compact_session(agent_id: str, session_id: str) -> str` - command accessor helper that returns user-facing reply text. It delegates to `ChatLoop.compact_session(...)` on the non-streaming command ChatLoop; all compaction behavior (active-run refusal, settings load, summary-adapter resolution, checkpoint append, adapter close, `"Compaction failed: ..."` replies) lives in the chat domain.
- `CronService(trigger_service, data_root, *, agent_resolver=None, sessions=None)` - DI service rooted at the Runtime data directory. The Runtime supplies the resolver and Session manager so target existence and fixed-Session ownership are core invariants rather than RPC-only checks. Jobs load lazily on CRUD calls or at `start()`, are returned as clones, create the cron directory/file on demand, and are persisted with atomic JSON replace. One invalid entry is logged, skipped, and preserved verbatim across later valid mutations; valid siblings still schedule.
- `CronService.create_job(...)`, `list_jobs()`, `get_job(job_id)`, `update_job(job_id, **fields)`, `delete_job(job_id)`, `enable_job(job_id)`, `disable_job(job_id)` - persisted job CRUD/status controls. Every returned job has a non-empty human-readable `name`; names need not be unique because `id` remains identity. Creation may omit the name, which is derived once from the first useful prompt line and remains stable across later prompt updates. `list_jobs()` returns all jobs in stable created order, including completed finite jobs.
- `CronService.parse_schedule(schedule)` owns the Agent-facing grammar (ISO timestamp, `in <duration>`, `every <duration>`, or five-field cron); `format_schedule(job)`, `system_timezone_name()`, and `next_fire_at(job)` are the canonical projections used by RPC, the Tool, CLI/WebUI, and scheduler. Accessors must not duplicate interval, `croniter`, or host-timezone logic. Cron create/update/enable/disable RPCs return the same complete job projection used by list. `add_changed_callback(callback)` reports every successfully persisted user or scheduler mutation; the server bridges it to `resource_changed(kind="cron")`.
- `CronService.start()`, `stop()`, and `aclose()` - lifecycle methods for scheduler tasks. `start()` and `stop()` are idempotent; `start()` loads jobs and starts active-job tasks, `stop()` cancels tracked tasks without awaiting their cancellation, and `aclose()` stops then awaits cancellation. Malformed JSON or a non-array root disables Cron scheduling and logs the storage error without failing Runtime startup; reads degrade to an empty list, while mutations remain blocked so the unreadable file cannot be overwritten.

## Conventions

- `core.automation` exports `validate_cron_jobs_data`, `validate_cron_jobs_file`, and the strict `load_validated_cron_jobs_json` used by diagnostics/direct consumers. `CronService` validates entries independently before constructing `CronJob` objects, then applies semantic validation in `core/automation/cron.py`. Whole-file storage failures surface as `CronStorageError` on mutation; bad job data or unsupported update fields raise `CronJobValidationError`.
- `schedule_type` is `cron`, `interval`, or `once`. Cron jobs require `cron_expression`; interval jobs require minute-aligned `interval_seconds` plus a persisted UTC `interval_anchor_at`; once jobs require `run_at`. Validation clears fields owned by other schedule kinds. `remaining_runs` is `null` for unlimited recurring jobs or a non-negative persisted count; Once jobs normalize a missing count to one when created or loaded. Updates are patches: omitting `remaining_runs` preserves it even when the schedule kind changes, an explicit integer replaces it, and explicit `null` makes only a recurring job unlimited. Once updates reject explicit `null`; changing to Once with an omitted incompatible count requires one.
- `status` is optional in persisted data and defaults to `active`; explicit values are `active`, `paused`, `completed`, `failed`, or `missed`. `completed` and `missed` are terminal history and cannot be re-enabled or paused; `failed` means execution stopped after the retry/failure ceiling and can be re-enabled after the cause is fixed (re-enable resets its consecutive-failure counter). Only `active` owns a scheduler task.
- `created_at` is optional in persisted data and defaults to the current UTC timestamp. `created_at`, `run_at`, `last_attempt_at`, `last_fired_at`, and `last_completed_at` are stored as UTC timestamps with explicit offsets when written. A naive once `run_at` is interpreted in the server's IANA system timezone and normalized to UTC before persistence; an explicit offset denotes an absolute instant. Legacy persisted `timezone` fields are accepted and ignored while loading, omitted from the in-memory model, and removed the next time the valid job is saved.
- Persisted jobs without `name` remain loadable: Cron uses the same stable create fallback from the first useful prompt line after stripping a Markdown prefix and collapsing whitespace, capped at 80 characters with `Scheduled Run` as the empty fallback, and persists that name on the next valid save.
- Cron expressions contain exactly five fields (minute, hour, day-of-month, month, day-of-week), so seconds-level schedules are rejected and minimum cadence is one minute. They are evaluated with `croniter` in the server's IANA system timezone from `tzlocal`, including future DST rules. Native intervals use their persisted anchor, compute the next future boundary, and skip missed ticks rather than translating approximate intervals into cron.
- `last_attempt_at`, `last_fired_at`, `last_completed_at`, `last_run_id`, `last_outcome`, `last_error`, and `consecutive_failures` are persisted execution-health projection. A fire acquires one of four global Cron Run slots, starts (or queues) through TriggerService, consumes one finite `remaining_runs` slot immediately after admission, then waits for the Run's terminal result; an admitted failed Run counts, while a pre-admission trigger failure does not. One job never overlaps itself and a slow recurring Run skips intervening schedule instants. Five consecutive recurring failures stop the job as `failed`; success clears the counter.
- Capacity is bounded at 512 stored jobs and 64 active jobs. Terminal history remains listable/deletable and does not block Identity Agent or Project deletion; active, paused, and recoverable failed references still do.
- Changing a schedule field, `remaining_runs`, or `status` restarts an active scheduler task. Name, prompt, agent, and session updates do not restart a sleeper; the task reloads the latest job before firing.
- `CronService` validates target syntax/existence and, when `session_id` is set, that the Session exists under the same Agent/Project owner. Server/Tool edges only parse the outside `agent@projekt` spelling into the structured `agent_id` + `project_id`; they do not reimplement reference validation.
- A `CronJob` may target a **project agent**: it carries an optional `project_id` (default `None` = identity/global agent, unchanged). The server RPC and Cron Tool parse an explicit target through `core.projects.parse_agent_address`, store the fields separately, and list/display via `format_agent_address`. Firing a Project job creates a fresh Session under the Project anchor unless the job pins an existing owned Session. The reference lock is qualified and ignores terminal history: Project removal is blocked only by a non-terminal job whose `project_id` equals that Project; Identity Agent deletion is blocked only by a non-terminal job with `project_id is None`.
- Coordinated Identity Agent rename retargets only non-terminal jobs whose `project_id is None`; qualified Project jobs and terminal `completed`/`missed` records retain their original id as independent routing or immutable history. Agent-id-only updates do not restart the scheduler sleeper, which reloads the latest job before firing.
- Active once jobs write a durable fire claim under `<data_dir>/cron/once-fire-claims/` before calling `trigger_run(...)`. A pre-admission trigger failure removes the claim and retries with bounded exponential backoff, then abandons the job after `_ONCE_MAX_FIRE_ATTEMPTS`; an admitted Run consumes the one fire even if that Run later fails. If admitted-state or completed-state persistence fails, the scheduler retries the save without firing again.

## Reflection (background self-improvement reviews)

`ReflectionService(runtime: RuntimeServices)` — wired by the Runtime before the chat loops; exposed as `runtime.reflection`. Two halves:

- **Shared review orchestration** — `await run_review(agent_id, session_id, *, project_id=None, extra_instruction=None, on_fork_created=None, reply_surface=None) -> ReflectionResult(session_id, summary)`: forks the Session same-Agent (prompt-cache-warm, pinned Skill catalog kept, `SESSION_FORK_ALWAYS_STRIP_META_KEYS` from `core.sessions` applied), titles the fork recognizably (`"Reflection"` or `"Reflection: <source title>"` via `set_title`), then starts an internal Run in the fork on the streaming Chat loop with the dispatch-only `REFLECTION_TOOL_RESTRICTION = ("memory", "skill", "skill_manage")`, the `reflect.md` brief, optional `extra_instruction`, the initiating reply surface, and `contributes_to_agent_activity=False`. The System Prompt and Provider Tool definitions remain byte-identical to the source for prompt-cache reuse; the tail brief explicitly says every other Tool is disabled and must not be attempted. The review remains a real Run for admission, cancellation, live viewing, persisted Session history, and debug traces, but it never produces Agent running/unread attention status. Returns the fork id and the Run's closing summary; the source Session is never touched. `on_fork_created(fork_id)` fires before the review Run starts so Chat `/reflect` can report a neutral Sessions change immediately for an accessor to project. Used by `CommandDispatcher` and the cadence trigger.
- **Cadence trigger** — `notify_run_end(run, agent, *, internal, outcome)`: called by the chat loop at the end of every run (see `chat.md`); non-blocking, schedules an asyncio task. Inline gates: internal runs, non-`success` outcomes, and empty-`workspace` (config) agents never count. In the task: reads `settings.reflection` live via `storage.load_reflection_settings()` (disabled → no-op, so the toggle applies without restart), skips sub-agent sessions (`is_subagent_session` metadata), then increments the per-session counters in the metadata sidecar (`reflection_counters`: `turns_since_memory_review` +1 per run, `tool_calls_since_skill_review` += `run.tool_call_count`). When a counter reaches its interval (`memory_turn_interval` / `skill_tool_call_interval`), one review run fires in the background with a cadence note naming the due dimension (both due → bare brief). The counts covered by a successful review are consumed only after it completes; a failed review leaves them due so the next eligible visible Run retries, while activity recorded during the review remains counted for a later cycle. One review at a time per agent (in-memory guard); a due session during an active review keeps its counters and re-checks on its next run end. Trigger and outcome (summary excerpt) are logged at info on `vbot.automation.reflection`.
- `reset_counters(agent_id, session_id, project_id=None)` zeroes both counters and advances their generation; Chat's `/reflect` execution calls it after a successful manual review because that review covers both dimensions. The generation prevents an overlapping background review from consuming activity recorded after the manual reset.
- The review run is itself internal, so it never re-triggers accounting (no recursion). Counters are stripped from forks (`reflection_counters` is in the always-strip set), so a fork restarts at zero.
- Background review forks appear in the Session drawer on its next load. Manual `/reflect` reports its fork through `CommandExecutionContext.on_change`; RPC projects that neutral fact to `resource_changed(sessions)` while Channels use a no-op observer. Automation and Chat never import the server event bus.

## Constraints & Gotchas

- Runtime startup without a running asyncio loop wires `CronService` but does not start scheduler tasks; `Runtime._start_cron_service()` only calls `start()` when `asyncio.get_running_loop()` succeeds.
- Busy-session queueing is in-memory and shares `ChatRunManager`'s system-wide waiting-work ceiling of 32 queued Runs and ingress reservations; queued triggered work is lost on process restart.
- Missed once jobs are not caught up on startup; they are logged at warn level and retained with `status="missed"`, `last_outcome="missed"`, and no fabricated `last_fired_at`. Missed cron occurrences and interval ticks are not replayed; the next future fire is computed from current time and the stored schedule.
- Once jobs are retained after firing with `status = "completed"` and `last_fired_at` set.
- Once-job fire claims intentionally prefer at-most-once behavior across restarts: a crash after claim creation but before `trigger_run(...)` may skip that once job on restart instead of risking duplicate execution.
- Trigger and Run-terminal failures are logged and persisted in the job health fields. Recurring jobs continue until the consecutive-failure ceiling, then stop as `failed`; once jobs retry a failed fire (claim write, trigger, or Run failure) with bounded exponential backoff and are abandoned as `failed` after `_ONCE_MAX_FIRE_ATTEMPTS`. The completed-state save after a successful once Run still retries until it persists.
