# Sessions

Canonical Session history, metadata, completion activity, continuation state, and SQLite persistence.

FTS queries preserve Unicode spelling for SQLite's tokenizer (for example `Straße`); Python case folding belongs only to the canonical fallback matcher, not the FTS expression (`test_session_fts.py`).

## Overview

`core/sessions/` owns the system-managed Session domain and the single canonical database `<data-dir>/sessions.db`. Chat, Agents, Projects, Channels, Recall, Statistics, and server orchestration address Sessions only through `ChatSessionManager`; no caller constructs storage paths or queries the database directly.

## Internal source routing

The public `core.sessions` package routes stable imports to the Session service in `sessions.py`, the buffered Session handle in `session.py`, immutable records in `_types.py`, and semantic history helpers in `history.py`. Metadata validation/cursors and bounded I/O/write leases live in `_metadata.py` and `_io.py`.

`store.py` retains Runtime connection lifecycle, read/write admission, FTS error recovery. Private `_store_*` functions receive its connection: `codec` owns normalized entity writes, `runs` owns admission/completion/restart recovery, `continuation` folds recoverable work, `history` builds bounded Message projections, `timeline` resolves Run attribution and append-cursor validity within that same read transaction, `queries` reads the catalog, `mutations` updates canonical history/metadata, and `owned` commits temporary bindings, receipts and Run attribution. `values` supplies shared relational projections, `fts` owns disposable index lifecycle, `search` executes bounded search, `schema` reconciles and validates an opening database. Do not open independent runtime connections or commit within a mutation helper; metadata, Message relations, revisions, receipts and FTS effects must share the caller's transaction. Read helpers that reconstruct Messages select rows inside the read transaction and return a decoder; `store.py` (`_read_decoded`) runs it after the transaction ends, because a rollback-journal store serves reads on the serialized writer.

`snapshots.py` owns capture, verified inventory and shared file/lock primitives. `recovery.py` owns quarantine, restore and durable incident acknowledgement, using the same operation lock.

## Terms

Core terms (Session, Agent, Run, Project) live in `.vorch/GLOSSARY.md`.

### Session generation
**Definition:** One immutable incarnation of a public `(project_id, agent_id, session_id)` address, identified internally by a unique generation id and surrogate key. Archiving ends the live generation; recreating the same public address starts a new generation without colliding with or inheriting derived state from the archived one.
**Not:** The public Session id or its append revision.

### Continuation state
**Definition:** Current recoverable work state materialized in `continuations`, `continuation_requests`, `continuation_steps`, and `continuation_operations`. Chat owns event semantics; Sessions folds each event transactionally into replaceable state and returns it as one typed read model, `SessionContinuationState` (`ChatSession.load_continuation`). A step is identified by Run id plus a positive Run-local step number (Chat numbers a Run's first Model step 1); the store rejects any other step and rolls back the whole append. Stream deltas append to their step in SQL without reading it back, but each flush still rewrites the step's whole stored text (`_store_continuation.py`).
**Not:** An append-only event journal, canonical Message history, or Run events.

### Prompt-cache affinity id
**Definition:** An opaque per-Session lineage value Chat passes separately from Session identity; Provider adapters decide whether their wire can use it. It lives in residual metadata; `prompt_cache_affinity_id` reads only that value (`json_extract`) and derives a deterministic default when none is stored.
**Not:** A Session id or generation id. Compaction rotates it to break prior prompt prefixes.

## Extension-owned execution

Temporary Session bindings, delivery receipts, Run ownership and Run starts live in
normalized relations outside open metadata and copied Messages. Exact address plus
Session generation and registered owner establish authority; forked history does
not copy these capabilities. Carrier Messages and delivery receipts commit together.
Explicit Message Run membership restricts owned usage even when ordinary Runs reuse the Session. Deletion of a drained temporary group uses `delete_temporary_group`: one
transaction removes only Session generations bound to the exact owner/group;
normal Session deletion still rejects owner-managed history. Schema and ownership tests cover these relations (`test_schema_reconcile.py`, `test_run_ownership.py`). The owner-bound creation/admission facade is
`core/agents/temporary.py`; domain state belongs to the Extension.

`temporary_group_titles` holds one optional display title per owner/group
(single line, stripped, <= 120 characters); it describes and never authorizes,
survives a disabled owner, and is removed by `delete_temporary_group`.
`list_owned_session_summaries(owner_name?, group_id?, metadata_keys)` is the one
set-oriented read of live owner-managed Sessions for derived consumers
(Statistics, title candidates): normalized summaries plus owner, group, group
title, participant id and the binding config's display `name`/`model`, never
other binding config. Ordinary Agent/Project discovery must not report the
synthetic `tmp_...` participant Agents: `list_addresses(exclude_owner_managed=True)`
backs `ProjectStore.session_owning_agents`.

## Storage Contract

Generated Session ids use `ses_` plus 12 lowercase base32 characters. Creation and forking allocate inside the SQLite write transaction, checking live and archived addresses in the destination scope; caller-chosen ids remain exact opaque values. The public facade returns the committed address (`store.py`, `tests/core/sessions/test_sessions_concurrency.py`).

- `sessions` stores one row per generation. A partial unique index permits exactly one live row per public address while retaining any number of archived generations; `sessions_archived_address` serves archived-address lookups (id allocation, restore). `messages` and the normalized Continuation tables reference the immutable surrogate key, so Agent renames and Session moves update one row rather than every record.
- Missing live-address reads raise the typed `SessionNotFoundError` (a `ChatSessionError` subtype), allowing disposable consumers to distinguish a concurrent delete/archive race from storage failure.
- `runs` owns each execution, its status, timing, work id and completion facts. `messages.run_id` and checkpoint Run ids reference that exact Run within the Session. `tool_calls` holds one invocation per assistant/call identity, including arguments, execution status, timing, result and display; completing a Tool updates that row. There are no physical Tool-result or Run-summary Messages. `history_records` is a read-only SQL projection for Provider history, Timeline and search. Its dense `seq` orders actual Messages, completed Tool results, Run footers, checkpoints and edit audit records. JSON is reserved for nested content, arguments, Provider extras and display payloads.
- Normal appends are transactional and update message count, last Message projections, indexed `active_sort`, history revision, and state revision in the same commit. Open-ended metadata remains a JSON object, but Session-list fields (titles, Channel identity, Sub-Agent/Fork provenance, Run kinds, the Session Compaction Policy, and the derived visibility mask) live in dedicated `sessions` columns and are reconstructed into the metadata facade; list filtering never parses open-ended JSON, ordered pages use declared keyset indexes, and exact per-scope counts use a narrow covering index. Existing baseline-generation databases receive one versioned transactional projection backfill identified in `store_meta`; the backfill reads and rewrites metadata under the same write transaction so concurrent committed edits survive, and also repairs `active_sort` from the last Message or creation instant for zero-valued metadata-only rows, and normal creation/metadata writes keep the columns synchronized. Completion activity remains JSON-backed with generated columns for indexed unread reads.
- SQLite opens with foreign keys, `synchronous=FULL`, a bounded busy timeout (1s SQLite, 20s/60s/0.5s application jittered budgets for BUSY/LOCKED), application id, schema version, lightweight identity/schema/table probes, one serialized writer with `BEGIN IMMEDIATE` and time-based retry, and a bounded LIFO read pool (8 permits, 60s backoff). Whole-database `quick_check`, foreign-key, hash, and FTS integrity scans are snapshot/recovery work and never block normal Runtime readiness. `required_journal_mode()` selects WAL only on SQLite builds without the WAL-reset corruption bug; affected builds use rollback-journal mode and an existing WAL database is never live-downgraded. Packaged Windows runtimes pin a fixed SQLite and therefore use WAL (`cli/windows-application.md`); source checkouts use the SQLite bundled with their Python. Reader connections are query-only and open only after the writer has reconciled schema; close drains the pool and releases permits. Page caches are bounded per connection (`sqlite_runtime.py`): the writer, which also serves every read in rollback-journal mode, keeps up to 64 MiB and each pooled reader up to 16 MiB. The ceiling is 64 MiB + 8 x 16 MiB = 192 MiB per Session store in WAL mode and 64 MiB in rollback-journal mode, reached only when each connection has read that many distinct pages. Measured on a 24 MB store with one 4,000-record Session (2026-09-24, noisy shared machine): a 100-Message `chat.history` snapshot fell from about 125 ms to 70 ms through the writer and from about 105 ms to 60-75 ms through a reader, versus the 2 MB compiled default; 400-record Sessions showed no measurable change. Operational failures (busy/locked/permission/disk-full/transient I/O) surface as `SessionStoreUnavailableError` and never trigger quarantine; only classified corruption (malformed/not-a-db/integrity/FK/schema mismatch) may enter recovery. Quarantine moves `sessions.db` plus `-wal/-shm/-journal` as one bundle under `<data-dir>/session-quarantine/<timestamp>-quarantine/` with all-or-rollback semantics; if rollback itself fails, remaining quarantine members are retained and their path is reported; version-protocol failures still fail closed without quarantine. `SQLiteRuntime` measures each write attempt (`sqlite.write`), its connection-lock wait (`sqlite.write_wait`) and each read context (`sqlite.read`) on the `sqlite` performance Track (`performance.md`).
- Verified snapshots for update, manual, recovery, and maintenance operations live in `<data-dir>/session-snapshots/<snapshot-id>/` via `core/sessions/snapshots.py`; each holds a standalone `sessions.db` plus `manifest.json` with SHA-256, file size, sqlite version/source, schema/application identity, counts, integrity results, revision watermarks, and completeness. Normal Runtime startup, writes, and shutdown never create or schedule snapshots. Online explicit captures run through `ChatSessionManager.create_snapshot`. Online and stopped-store captures copy through `sqlite_runtime.copy_database`: one `VACUUM INTO` read transaction, cancellable through a progress handler, never a stepped `Connection.backup` (which restarts whenever another connection commits, so it could not finish beside a streaming Run). The snapshot database is therefore a compact standalone rollback-journal file with the source's rowids, application id and schema version, no freelist and no WAL sidecars. With WAL the online copy reads beside running writers; in rollback-journal mode it holds the Runtime connection lock, so writes and reads queue in Python for the copy's duration (a few seconds per GB) instead of exhausting their busy budgets. Captures stage as `.<id>.<pid>.partial/` and publish only after hash/integrity/FK verification and fsync. One OS-backed operation lock serializes snapshot, recovery, and incident acknowledgement work; it is held open for the whole operation and never broken solely because its metadata is old. Retention uses strict manifest/stat inventory, protects the newly published snapshot, keeps within `SNAPSHOT_KEEP_COUNT` and `SNAPSHOT_KEEP_BYTES`, and never deletes the last verified snapshot; it does not rehash retained snapshots, while explicit verification and recovery candidates still receive full checks. Snapshot creation returns the newly published summary directly instead of immediately re-inventorying the directory. Snapshot attempts publish non-content health in `<data-dir>/session-snapshot-health.json`. Deep verification checks manifest identity, counts and revision watermarks against the database; selection and retention compare timestamp instants. Recovery validates table compatibility and stages verified bytes before publishing a pending incident or quarantining canonical data. Operational verification, copy, quarantine, or publication failures stop candidate fallback. Retries retain the original quarantine reference and failure time; pending incidents finalize only when the canonical image matches the intended snapshot. Canonical recovery probes also check table compatibility. Malformed incident evidence fails as corruption on read/open/acknowledgement, access failures fail as unavailability, and the durable possible-loss interval remains until exact incident acknowledgement.
- Integrated FTS follows the Hermes storage shape: `messages_fts` is a standard-tokenizer external-content index over searchable normalized Message relations, while `messages_fts_trigram` is an external-content trigram index over the same source excluding Tool-role rows. There is no mirrored `message_search` table. Canonical writes explicitly project completed Messages and explicitly remove disappearing rows before canonical state hides them: Session delete, temporary-group delete and history-edit tail deactivation each issue one set-wise external-content delete per index for the affected Session (`_store_fts._delete_fts_session`), never one statement per Message; on FTS write corruption the writer detaches both indexes, sets a stale breadcrumb, and retries the canonical write so derived-index failure never blocks canonical persistence. Runtime repair selects bounded record identities before loading content; FTS writes for individual Messages or forked Sessions constrain source reads before joining relational projections. Repair is chunked and resumable with generation, target/completed high-water marks, transactional progress, and explicit base/trigram coverage checks. Ordinary Search availability trusts the lifecycle/version/stale/high-water markers and never runs canonical coverage anti-joins; startup repair, snapshot verification, and explicit operator health checks own deep coverage validation. Interruption reports rebuilding/degraded state and never healthy incompleteness. Search picks one index up front: requests whose roles exclude Tool use trigram when every term (or the phrase) has >=3 characters, all others use standard whole-token FTS; a standard miss never retries trigram. One full `MATCH` scan ranks every eligible hit so bm25 statistics stay whole-index; only the best `limit` ranks and their ties leave SQLite. Healthy no-match queries that exclude Tool rows never load canonical histories. Tool-inclusive misses or unavailable-index requests use the SQL canonical fallback: it orders eligible record keys newest-first in SQL, decodes and matches at most 10,000 of them in keyed batches, stops once `limit` records match, and marks typed Recall results degraded/partial if that budget cannot prove complete coverage. FTS results are explicitly bounded, Recall eligibility filters apply in SQL before the limit, and `messages_by_session_instant` serves `julianday(timestamp)` filters without changing equivalent-offset or fractional timestamp semantics.
- `SCHEMA_SQL` defines the canonical schema (version 1). Runtime validates the database shape and marker before opening readers. Additive reconciliation rechecks its plan under write admission and rolls back every applied statement on failure; an already current schema requires no write transaction.
- Startup authorizes `sessions.db` only via the current-format marker `<data-dir>/session-store.json` (`bootstrap`/`ready` with `database_id`/`schema_version`, strict closed schema, atomic write+fsync, `validate_session_store_paths` enforces `sessions.db` parent == `data_dir`). A fresh directory is bootstrapped only when `initialize_data_directory` creates the root (the call whose `mkdir` succeeded); an existing directory without a marker is a hard `SessionStorageFormatError` without any JSONL inspection. A process that loses a concurrent root-creation race and opens the store before the winner publishes its marker therefore fails with that error; there is no cross-process wait. `<data-dir>/session-store-maintenance.json` blocks Runtime startup while an offline source-mutating operation is incomplete. When the store is `ready` but `sessions.db` is missing or fails classified corruption, startup attempts auto-restore of the newest verified snapshot (quarantining the failed DB as a bundle) before surfacing an error; busy/locked/permission/disk-full never quarantines.
- Run completion commits the terminal row, unfinished Tool states, Session revisions/activity and successful Continuation removal together. Only then does Run management publish a persistence acknowledgement. Startup settles abandoned running rows as interrupted without replaying Model or Tool work.

## Interfaces

- `ChatSession` is a path-free handle: `append`/`append_many`, `load`, `load_active`, continuation operations, notes, Skill activation state, and `load_since(cursor)`. `append_many` and owned receipt appends optionally fold Continuation records and return the `load_since` delta for a given cursor within their write transaction; a rejected record rolls back the whole append. Frequent partial consumers use dedicated read models instead: one atomic Chat History snapshot, the status aggregate, targeted Run summary/result lookup, and checkpoint-bounded History record batches. Async counterparts execute through bounded worker pools at their owning boundary.
- `SessionReadCursor` carries generation id, append revision, next sequence, count, and the prior Message id anchor. A cursor from the same generation returns only appended records after its prefix; a generation change, invalid sequence, or mismatched anchor returns `None` so disposable consumers rebuild. A current cursor returns an empty delta from the Session row alone; otherwise one indexed read from the anchor sequence validates the anchor and returns the appended records.
- `ChatSessionManager` owns create/get/get-or-create/exists/list/archive/restore/delete/move/fork and identity/project lifecycle operations. `get_or_create` is one database transaction. Archive is asynchronous at the public boundary, runs off the Event Loop, and holds the Session write lock.
- `write_lock(address)` is context-reentrant for a holder and child tasks. It protects ordered Chat boundaries and whole move/fork/archive operations; Provider latency and other unbounded work stay outside it. Locks are manager-owned and released with manager lifetime.
- `mutate_metadata` and `mutate_metadata_with_previous` perform one transactional read-modify-write. Domain code must use them for partial updates; `set_metadata` is reserved for complete replacement and exact compensation snapshots. Completion activity uses the equivalent atomic mutation path. A metadata or activity mutation whose persisted form is unchanged issues no `UPDATE`, so it neither fsyncs nor bumps `state_revision`; that column only feeds the snapshot manifest's `latest_state_revision` watermark and is not a per-change signal (`test_sessions_listing.py`).
- Identity-rename reference compensation restores only the exact `subagent_parent` link it retargeted, conditionally on that link remaining unchanged; concurrent titles, other metadata, and later parent links survive (`test_sessions_identity_references.py`).
- `list_summaries_page` is the bounded accessor read model: one SQLite transaction globally orders one or many Agent scopes, applies execution-category and Channel inclusion filters, returns a keyset cursor and total count, and may add one explicitly required selected Session without letting it alter cursor progression. Channel filtering uses the existing platform plus conversation-id metadata, applies before counts/pagination, and defaults to inclusion at the service/RPC edge; the WebUI explicitly opts out. `list_summaries` returns only normalized list/completion columns plus explicitly allowlisted residual fields such as Statistics-owned `seen_skills`. The Agent-facing Search Tool has no listing mode. `list_with_metadata` is the exceptional full-metadata surface, not a candidate-list API. `list_completion_activity` selects only completion columns. `bookend_timestamps`, `session_ids_with_messages`, bounded active User Message counts, and newest prefixed Note lookup use direct SQL reads rather than loading complete histories. `descriptor_source(address)` obtains normalized descriptor metadata, cached Message count, only the first User Message, and the Session's Recall visibility without reconstructing history; multi-Session callers must use `descriptor_sources(addresses)` so descriptor lists remain set-oriented. `recall_context(address, message_id)` reads only the active enclosing User question and final Assistant answer, with text bounded in SQL and no full-history hydration. `history_version(address)` returns generation plus revision for derived projections; comparing revision alone is insufficient. `list_history_versions(addresses)` resolves generation plus revision for many addresses in one query per scope - derived projections must use it instead of per-Session `history_version` loops when refreshing freshness stamps. `list_history_revisions(agent_id, project_id)` returns every live Session's generation, revision and Recall visibility for one scope in one query.
- Recall visibility (`SessionRecallVisibility`) is classified in SQL from the visibility mask column, so callers never classify metadata in Python: reflection Run kinds make a Session `hidden`; otherwise a Sub-Agent flag or Run kind makes it `subagent`; otherwise a Session without recognized Run kinds or with a user-facing Run kind (`user`, `channel`, `cron`, `calendar`) is `conversation`; anything else (system-only, memory, Skill) is `hidden`. `recall_visibilities(include_subagents=...)` names the admitted values. Message search (`fts_search`) applies it inside the scope subquery before any candidate limit.
- `read_chat_history_snapshot` returns a consistent page or bounded append batch with Usage, editability, record sequence, stored Run membership and explicit Run completeness. `after` is a generation/next-sequence cursor; hidden rows advance it. An edit/takeover watermark or generation mismatch forces a replacement snapshot. `before` independently pages older history. Page expansion uses native Run starts. A page selects narrow sequence/key rows first and reads full records by key; its Run descriptions are ordered by Run start sequence. `load_run_result` and `load_run_messages_async` query exact Run membership; consumers must not infer ownership from preceding footers or Message coverage.
- `fork` copies entities and FTS set-wise into a new generation. Inherited Runs retain origin-generation provenance and never gain execution ownership, Continuation or completion activity. Running source Runs and unfinished Tools become interrupted snapshots in the fork; they cannot be resumed or readmitted. `move` retargets one live generation. Both use the latest metadata in the same write transaction.
- Archive and restore are generation-aware. A new live generation may reuse an archived address; restore fails while that address already has a live generation and otherwise restores the newest archived generation.
- `status_projection()` returns one typed top-level state: `healthy`, `snapshot_degraded`, `search_degraded`, `recovered_with_incident`, or `unrecoverable` (the last is produced by stopped-store diagnostics when normal open fails). Snapshot, FTS, marker, and incident details contain no Session content.

## Cross-Domain Rules

- `ChatSession.reflection_runs()` selects the first non-inherited terminal Run in each live, same-owner reflection fork. It uses explicit Run provenance and rejects stale source generations; copied Runs cannot masquerade as review results.

- Chat owns `ChatMessage`, request assembly, Run execution, Compaction behavior, and continuation record meaning. Sessions owns canonical persistence, ordering, metadata transactionality, validation, and storage lifecycle.
- Agents and Projects must share the Runtime Session manager when started by Runtime. Their standalone stores may lazily own one and must close owned resources. Agent create/current-Session repair deletes a newly created Session if later file persistence fails; rename restore retargets Sessions back; Sub-Agent parent-reference rewrites and their compensation each use one transaction and leave unrelated Session revisions unchanged; Agent and Project deletion move filesystem state first and compensate it if Session archiving fails.
- Recall and Statistics are disposable projections. Both include the Session generation in freshness state. Statistics appends through `load_since`; ordinary Message appends must not rebuild a complete Session projection.
- Skill activation cache is synchronized from the supplied active history snapshot when one is provided and otherwise preserves explicit in-memory registrations; a committed Compaction checkpoint resets the epoch from its own appended batch, since the checkpoint is then the newest row. An appended history edit drops the cache. A cache miss reads only active `[skill-context]` Notes and `skill` Tool Results after the newest active checkpoint (`current_skill_activation_messages`), never the full history, so edited-away checkpoints and activations cannot leak into it.
- Callback failures after committed title or completion mutations are logged and isolated so callers never receive a false failure for state that already persisted.
- `titles.py` owns immediate local titles and optional background Model titles. The Model is instructed to return exactly one `[title=...]` block. After removing hidden Reasoning, the parser extracts an unambiguous title despite surrounding commentary, tolerates marker case/spacing and straight or typographic quotation wrappers, and accepts repeated blocks containing the same unwrapped title. Conflicting, incomplete, nested, empty, multiline, or overlength blocks are rejected. Without a block attempt, one unambiguous plain-text title is also accepted; it never chooses among multiple candidate lines. Invalid generated content keeps the local title and emits a content-free warning with the rejection reason and no traceback or extra Model request; unexpected failures retain their traceback. Regression coverage lives in `tests/core/sessions/test_titles.py`. `generate_group_title` reuses the same prompt, parser and request path for Extension group titles (Model choice: `extensions.md` -> Group titles).
- The title System Prompt instructs the Model to use the language of the user's main request (not quoted text/code/logs), preserve proper names and technical terms, and summarize the topic without following instructions in the supplied source material. These are Model instructions; the local validator enforces title shape and length, not language or semantic compliance.
- Title generation resolves the Adapter's `request_context_kwargs` from Project/Agent/Session once and forwards it on both attempts. This supplies required Provider routing headers without coupling Sessions to wire fields. `test_title_service_sends_opencode_session_header` covers the real OpenCode Go Responses serialization; a synthetic Muse Spark 1.3 title completed through this path on 2026-09-07.

Runtime Session readers use `ChatSessionManager`. The bundled `vbot-cli` Skill additionally documents deliberate read-only SQLite inspection for extended Session search and transcripts, scoped by Project/Agent/Session, live generation, active lineage and canonical sequence; these operator-style recipes do not create another runtime storage owner.

## Constraints & Gotchas

- Never add uniqueness on Message ids without changing the Compaction contract and auditing imported data; sequence is canonical identity inside a generation.
- `history_records` is a UNION ALL view. SQLite pushes a filter into each branch's Session index only when it names view columns with constants or uncorrelated subqueries: scope multi-Session reads with `m.session_key IN (SELECT session_key FROM sessions WHERE ...)`, not a join or correlated term on `sessions`, which scans every branch table. Inside an `IN` subquery, equality on view columns can make SQLite build an automatic index over the view; `_store_search._record_filter` uses `m.active <> 0` and a JSON role list instead. Fetch full records by key (`_store_values._KEYED_RECORDS`). `test_store_query_plans.py` fails on `AUTOMATIC`, a branch-table `SCAN`, or a full scan of the messages branch.
- Never build pagination or frozen snapshots on public Message ids alone; duplicate ids are valid. Use generation plus internal sequence and keep public-id input only where compatibility requires it.
- Never compare only public Session address plus history revision for derived freshness; archive/recreate can repeat the same revision.
- Never implement metadata as `get_metadata` followed by `set_metadata` for a partial change; concurrent fields will be lost.
- SQLite serializes database writes, not a read-modify-write split across transactions. Domain mutation callbacks must remain deterministic, side-effect free, and JSON-serializable.
- Never force WAL directly. Canonical and disposable Session-derived databases share `required_journal_mode()` so a vulnerable SQLite build cannot reintroduce the WAL-reset race.
- Stored Run membership is authoritative. A settled or inherited Run rejects new output and cannot be admitted again; duplicate completion is rejected.
