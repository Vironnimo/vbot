# Sessions

Persisted chat containers, session metadata, and current JSONL-backed storage.

## Overview

`core/sessions/` owns the system-managed Session domain. A Session belongs to exactly one Agent and stores canonical `ChatMessage` history under `<data_dir>/agents/<agent-id>/sessions/`. The current implementation uses append-only UTF-8 JSONL for canonical messages, a JSON metadata sidecar, a dedicated completion-activity sidecar, and an internal append-only continuation journal sidecar while visible work is active or interrupted.

The Sessions domain owns persistence and file-format details. Chat code may append and load messages through the session API, but other domains must not construct `.jsonl` paths directly. Accessors and server delegates should use the runtime's `chat_sessions` service. `session_search` uses `core/recall/` backends for discovery, while `session_read` uses `ChatSessionManager` directly for canonical records.

## Interfaces

`ChatSessionManager` keeps synchronous storage methods for synchronous callers and exposes matching async facades for create/existence/get-or-create/get, metadata read/write, manual title updates, terminal-read acknowledgement, and Session listing/activity projections. All Session async I/O, including `ChatSession` append/load primitives and manager `move`, `fork`, and `archive`, runs through the dedicated eight-worker Session pool; source write locks still cover the entire move/fork/archive worker operation, and cancellation is reported only after an already-started filesystem mutation settles.

- `ChatSession(path)` — handle for one current JSONL session file. The constructor validates the current `.jsonl` path shape.
- `ChatSession.create(sessions_dir, session_id=None)` — creates an empty session file in the supplied sessions directory. Custom IDs are validated before path construction.
- `ChatSession.id` — session identifier derived from the current filename stem.
- `ChatSession.sidecar_path` — current metadata sidecar path `<session-id>.meta.json`.
- `ChatSession.activity_path` — durable terminal-Run/read-receipt sidecar path `<session-id>.activity.json`; this state is isolated from general metadata so unrelated metadata rewrites cannot lose a completion notification.
- `ChatSession.continuation_path` — internal continuation journal path `<session-id>.continuation.jsonl`; Chat owns the record semantics, while Sessions alone owns this path and its file lifecycle.
- `ChatSession.append(message)` appends one compact UTF-8 JSON object plus newline; `append_many(messages)` appends an ordered Message batch through one durable write and one `fsync`. Their `append_async` / `append_many_async` counterparts run that storage work outside the Event Loop and do not release cancellation until an already-started worker write has settled.
- `ChatSession.load()` returns validated `ChatMessage` objects in append order; `load_async()` provides the Event-Loop-safe boundary used by Chat. An incomplete final line is always omitted, but only a caller whose current async context holds that Session's `write_lock` may truncate it; unlocked readers leave the bytes untouched because they may belong to an in-progress append.
- `ChatSession.load_since(cursor=None) -> SessionReadBatch | None` — validates only complete Messages after an opaque `SessionReadCursor{byte_offset, message_count, last_message_id}`; `None` starts at byte zero, while a supplied cursor whose prior complete line no longer ends with the recorded Message id returns `None` so disposable consumers rebuild. The returned cursor lands after the last complete observed line and uses the same lock-aware incomplete-tail handling as `load()`; `load_since_async()` is the corresponding off-Event-Loop boundary.
- `ChatSession.append_continuation_record(record)` / `append_continuation_records(records)` — append one record or one fsynced batch to the journal without rewriting its accumulated contents. `load_continuation_records()` returns ordered JSON objects and repairs only an incomplete trailing line; `clear_continuation()` removes the disposable journal. Chat uses the async append/load/clear counterparts so Continuation durability never blocks the Event Loop.
- `ChatSession.add_note(content)` — persists a kernel-internal `role: "note"` message and queues it for the next provider request.
- `ChatSession.begin_defer_notes()` / `take_deferred_notes()` / `flush_deferred_notes()` — bracket Tool dispatch so notes created during a Tool-use turn can join the ordered Tool Result batch after its Results; async flush persists any remaining notes off the Event Loop.
- `ChatSession.drain_pending_notes()` — returns queued note messages and clears only the in-memory pending-note buffer.
- `ChatSession.activate_skill_context(name, data)` — the **user-trigger** activation carrier: accepts the loader's internal `activation_content`, persists it as a `[skill-context] ` note at the activation point (right after the triggering user message), and returns `False` only when the same name already has identical activation context. The chat loop renders the note **in place** as a `<skill_content>` user message at request build.
- `ChatSession.register_skill_activation(name, content) -> bool` — the **Tool-path** dedup seam: records an activation without persisting anything (the `skill` Tool Result is the durable carrier). It returns `False` only for identical name+content within the current Compaction epoch and replaces the in-memory content for a changed package.
- `ChatSession.activated_skill_contents(messages=None) -> dict[str, str]` — newest activated Skill content by name after the latest committed checkpoint, scanned from **both carriers** (trigger notes + successful loading `skill` Tool Results); later carriers replace earlier content without changing the name's original insertion order. Callers that already hold the Session's loaded messages pass them to avoid a second full Session read. A successful checkpoint append resets the same-handle cache only after its durable write, so failed/stale Compaction attempts cannot revoke activations.
- `skill_context_note_payload(message)` / `skill_tool_activation(message)` / `skill_tool_activation_name(message)` / `skill_activation_names(messages)` / `skill_activation_contents(messages)` — module-level carrier parsers: the single prefix/JSON and envelope parse shared by request building, statistics, and Compaction reconstruction. For a Tool carrier, Sessions reconstructs the internal activation context from raw `content` plus optional structured `resource_files` / `environment_access`; `current_skill_activation_contents(messages)` applies that latest-wins projection only to canonical carriers after the newest checkpoint. The `skill` Tool's message name and `"loaded"` status remain literals to avoid importing the Tool domain.
- `project_tool_context_id(message)` / `latest_project_tool_context_id(messages)` — parse the successful `project` Tool Result that durably selects the latest explicit Project Skill activation context for an Identity Session. Failures and malformed envelopes are ignored; Chat owns how the recovered id changes Run-local Skill routing.
- `ChatSession.bookend_timestamps()` — returns `(first, last)` message timestamps by reading only the first and last complete JSONL lines (backward chunked tail read). Returns `None` when the fast path cannot answer (empty file, partial trailing write, unparseable bookend line); callers must then fall back to `load()`, which owns partial-write recovery.
- `ChatSession.delete()` — hard-deletes the session file, metadata sidecar, activity sidecar, and continuation journal (all `missing_ok`). Low-level primitive: the session-deletion feature does **not** call it — it archives via `ChatSessionManager.archive(...)` so a removed Session stays recoverable. Kept as the genuine "remove the files" capability (tests, staleness).
- `ChatSessionManager(data_dir)` — the path-free entry point for sessions: `create` / `get` / `get_or_create` / `exists` / `list` / `delete(agent_id, session_id)` / `archive(agent_id, session_id)` resolve agent session roots so callers never construct `.jsonl` paths; all validate the session ID first.
- `async ChatSessionManager.archive(agent_id, session_id, project_id=None) -> Path` — the deletion feature's storage step: moves a Session's transcript, metadata sidecar, activity sidecar, and continuation journal under `<data_dir>/archive/sessions/` instead of hard-deleting, so a removed Session is recoverable by hand (there is no in-app restore). Layout mirrors the live tree beneath a dedicated archive root — `archive/sessions/agents/<agent-id>/` (identity) or `archive/sessions/projects/<project-id>/agents/<agent-id>/` (project) — so it never collides with the agent (`archive/agents/<agent-id>/`) or project (`archive/projects/<project-id>/`) archives. Crash-safe like `move`: holds the source `write_lock`, `os.replace`s the transcript first; an existing archive for the same id, including its sidecars and journal, is replaced. The `session.delete` orchestrator holds `ChatRunManager.session_admission_guard` across the awaited archive, landing selection, and recall removal; that atomic Run boundary, not the storage lock alone, prevents a new writer from recreating the file mid-archive.
- **Project scoping:** every manager method (`sessions_dir`, `create`, `get`, `get_or_create`, `exists`, `list`, `list_with_metadata`, `list_completion_activity`, `get_metadata`, `set_metadata`, `write_lock`, `delete`) takes a trailing optional `project_id=None`. `None` → the global root `agents/<agent-id>/sessions/` (unchanged behavior, every existing caller stays on this). A set `project_id` → the project anchor `projects/<project-id>/agents/<agent-id>/sessions/`. The anchor path comes from the single layout source `core.projects.project_sessions_dir(...)` (also used by `ProjectStore.sessions_dir`) — sessions imports that helper, not a `ProjectStore` instance, so there is no cycle. `write_lock` keys on the resolved transcript path, so a global and a project-scoped session sharing one id get distinct locks. The project binding is *carried in* by the caller (it lives in the Session meta, so an opener must already know `project_id` before it can find the file).
- A Rooted Identity Agent still passes `project_id=None`; its internal working Project never changes Session paths, metadata addressing, archive layout, current-session ownership, or public lookup keys.
- `ChatSessionManager.get_metadata(agent_id, session_id)` / `set_metadata(...)` — read/write arbitrary JSON-object metadata through the current sidecar file using atomic replace.
- `ChatSessionManager.record_run_kind(agent_id, session_id, run_kind, project_id=None)` idempotently appends a validated `RunKind` value to the Session's `run_kinds` metadata list. The accumulated list describes which producer categories have actually executed in the Session; an absent list means unclassified legacy or empty Session, not background-only work.
- `ChatSessionManager.prompt_cache_affinity_id(agent_id, session_id, project_id=None)` resolves the opaque, provider-neutral cache lineage for a Session without creating a sidecar when the initial deterministic address-derived value is sufficient; `rotate_prompt_cache_affinity_id(...)` persists a fresh epoch under `prompt_cache_affinity_id`. Chat passes this value separately from Session identity, and Provider adapters alone decide whether their wire can use it.
- `retarget_identity_agent_references(old_agent_id, new_agent_id)` changes only functional, unqualified `subagent_parent.agent_id` links across live Identity and Project Session sidecars and returns exact snapshots for `restore_identity_agent_references(...)`. Historical `fork_source` and transcript content never change during an Identity Agent rename.
- Session metadata may carry a complete `compaction_policy` override. Absence means the Session dynamically inherits the effective Agent/Project/global Policy; changing an inherited Policy does not rewrite the sidecar or trigger compaction.
- A Rooted Identity Agent Session may carry `pinned_working_project_context: {text}`. Chat writes it once from the selected Project's identity/cwd and readable auto-load files before the first provider request, then reuses that text verbatim for the automatic Working Project block; Sessions owns only the metadata persistence, not rendering or selection policy.
- `ChatSessionManager.set_title(agent_id, session_id, title, project_id=None) -> str | None` stores the manual display title under the `title` sidecar key. The title is collapsed to one trimmed line and capped at `SESSION_TITLE_MAX_LENGTH` (200, a safety bound — the UI ellipsizes); a blank result clears only the manual key and reveals `auto_title`. Manual title writes never overwrite automatic title state.
- `ChatSessionManager.set_auto_title(...)` stores the local or Model-generated display title under `auto_title` and marks automatic initialization complete; `mark_auto_title_initialized(...)` records a no-backfill decision without inventing a title. Display precedence is `title` → `auto_title` → legacy fallback. Both title setters publish through the manager's process-local title-change callback seam so the server can invalidate Session lists; they touch only the atomic metadata sidecar, never the transcript or its `write_lock`.
- `SessionTitleService` immediately derives a bounded local title from the first visible user message, then may replace it through one background Model call. The call receives only a bounded projection of that message plus Attachment metadata, requests `thinking_effort="none"` without imposing a title-specific output-token limit, and never receives Session history. Only one final content line of at most 60 characters can replace the local fallback: normalized Reasoning fields and typed reasoning blocks are ignored, hidden reasoning tags are removed even when unclosed, and multiline or meta-descriptive output is rejected. Sub-Agent Sessions bypass this generic service because `SubAgentCoordinator` initializes their stable `auto_title` from the parent delegation before the Child Run starts.
- `ChatSessionManager.record_terminal_run(...)` records the latest terminal Run as unread; `mark_terminal_run_read(...)` acknowledges only the supplied Run id and cannot clear a newer completion. A successful acknowledgement notifies callbacks registered through `add_completion_read_callback(...)` after releasing the activity lock, so internal result delivery and Accessor reads share one server-invalidation seam; stale acknowledgements emit nothing. The activity update has its own process-wide read-modify-write lock and atomic replace. Absence of the activity sidecar means no unread completion, so pre-feature Sessions start clean without migration or backlog. Chat calls the recorder only for Runs whose Runs-domain Agent-activity policy contributes to attention status; Sessions does not infer that policy from `internal` messages or Run type.
- `ChatSessionManager.list_with_metadata(agent_id)` — returns session summaries with `id`, `created_at`, `last_active_at`, general metadata fields (including accumulated `run_kinds` when present), and the public completion projection (`has_unread_completion`, `latest_completion_run_id`, `unread_run_id`, `unread_run_status`, `unread_run_at`). `latest_completion_run_id` remains present after acknowledgement so Accessors can reconcile an exact retained/replayed terminal event without clearing or resurrecting a different Run.
- `ChatSessionManager.list_completion_activity(agent_id, project_id=None)` — returns only each live Session id plus its normalized public completion projection. It enumerates transcript filenames to establish Session existence but deliberately does not read transcript bookends, full History, or general metadata; use it for Agent-wide attention badges, not for the Session drawer or landing decisions that require timestamps, titles, bindings, origins, or compaction policy.
- `ChatSessionManager.write_lock(agent_id, session_id)` — returns the process-wide, context-reentrant async append lock for one session's transcript. Shared across manager instances (keyed by the resolved file path), so every writer reaches the same lock regardless of which manager it holds. Reentrancy is tracked through a live lease carried by a `contextvars.ContextVar`, not the running task, so it extends to the holder **and child tasks that enter while that lease still owns the lock**: a Run holds it across its tool cycle, and the tool executor runs each tool in its own `asyncio.create_task`, so a tool (e.g. `channel_send`) targeting its own session re-enters from that child task instead of self-deadlocking. Keying on `current_task()` would deadlock there (the tool runs in a different task than the acquirer). A child that outlives the original holder retains only an inactive copied lease and must acquire normally, exactly like an unrelated context chain (observe worker, RPC handler, other-accessor Run); neither can bypass a later owner. The lock protects only short append/snapshot/conditional-commit boundaries; Provider or other unbounded I/O must run after releasing it.
- `async ChatSessionManager.fork(source_agent_id, session_id, *, target_agent_id=None, source_project_id=None, target_project_id=None, strip_meta_keys=frozenset())` — copies a session into a **fresh** id (a v4 UUID, generated exactly like `ChatSession.create`) and returns the new `ChatSession`. A general capability (used by the `session.fork` RPC and the `/reflect` command). Copy-not-move: the source is left completely untouched (no `os.replace`, no sidecar delete) — a pure read of the source transcript plus two writes at the destination. The source continuation journal and completion-activity sidecar are deliberately omitted, so a fork never auto-attaches interrupted work or inherits an unread notification from its parent. A same-Agent, same-Project fork inherits the source's resolved `prompt_cache_affinity_id`, including through nested forks, while keeping its fresh Session id; a fork re-homed across either boundary starts a new affinity because its prompt envelope is no longer guaranteed identical. `target_agent_id=None` forks within the source's own agent. Holds the **source** `write_lock` across the whole copy, so the snapshot lands on a message boundary (a Run holds that lock across its tool cycle, so the copy blocks until an open cycle completes — the fork needs no separate run-quiescence precondition). The fork's metadata sidecar starts from the source sidecar (empty when absent), drops caller-owned `strip_meta_keys` (same import-free reasoning as `move`), and **always** gains the cache-affinity key plus the `fork_source` provenance key `{agent_id, session_id, project_id, forked_at (UTC ISO), message_count (int, count of copied `\n`-terminated lines)}` — so a fork is self-describing even when the source carried no sidecar. Any failure after the destination transcript is created removes that destination and all of its sidecars before the error is re-raised, so failed forks never become visible through `list()` and a retry starts cleanly. `FORK_SOURCE_META_KEY` is exported for the RPC layer. Forking a nonexistent source raises `ChatSessionError`. Copied checkpoints make the fresh Session History-capable, but the new Session id deliberately invalidates every source History cursor.
- `async ChatSessionManager.move(source_agent_id, session_id, target_agent_id, *, source_project_id=None, target_project_id=None, strip_meta_keys=frozenset())` — relocates a session's transcript, metadata sidecar, activity sidecar, and continuation journal from one (agent, project) home to another and returns the destination `ChatSession`. Storage-only: it resets **no** "current" pointer and touches **no** derived recall index — the caller owns those (the `/agent` move orchestrator in `core/chat/commands.py`). `strip_meta_keys` is a parameter so callers can drop metadata owned by another domain without Sessions importing that domain's constants. Crash-safe ordering: holds the source `write_lock`; fails cleanly (no partial move) if the destination transcript already exists; under the activity state lock, `os.replace` moves the transcript first (it alone defines the session to `list()`) and then its activity sidecar, after which the key-stripped metadata is written and the continuation journal is moved when present. A completion read acknowledgement therefore either lands before the move and travels with it or observes the missing source transcript and fails without recreating an orphan sidecar. A crash between steps never loses the conversation — worst case is an orphan source sidecar, invisible to `list()`. The write lock only guarantees append-contiguity; Agent Takeover additionally holds one `ChatRunManager.session_admission_guard` over both source and destination keys through the move, takeover divider/note, identity-pointer updates, and transfer of any Session-scoped Terminal Sessions, preventing new Runs from writing either side mid-transition. Because the transcript and Session id are preserved, checkpoint-backed History availability, cursors, unread completion state, and live Terminal Sessions survive a move/takeover.

- **Fork/move strip policy constants** live beside the primitives and are exported from `core.sessions`: `SESSION_FORK_ALWAYS_STRIP_META_KEYS` (Channel binding keys, Sub-Agent linkage keys, reflection cadence counters, and accumulated Run kinds — a fork is a plain, unbound Session that restarts its counters and origin history), `SESSION_FORK_CROSS_AGENT_STRIP_META_KEYS` (pinned Skill catalog + seen-Skills + prompt-cache affinity; stripped when a fork re-homes to a different Agent, after which the fork primitive stamps a fresh affinity), and `SESSION_MOVE_STRIP_META_KEYS` (the same cross-Agent set for `/agent` moves, so the moved Session derives a fresh affinity at its new address). The manager methods still take `strip_meta_keys` as a parameter; these constants are the callers' shared policy values (Session RPC, Chat Built-in Commands, and ReflectionService).

## Current Storage Contract

- Session files use `.jsonl` and are append-only during normal chat operation.
- Session appends write one UTF-8 encoded line through an append-only file descriptor and fsync before returning. If a read observes an invalid final line without a trailing newline, it returns the preceding valid Messages and a cursor before that line. It truncates and logs recovery only while the caller holds the Session `write_lock`; an unlocked read must leave the tail untouched because an append may still be completing. Complete invalid JSON/message lines remain hard errors.
- Session history may include `role: "tool"` messages with optional `timing`, interrupted Assistant messages with `interrupted: true` plus a normalized `interruption_cause`, and `role: "run_summary"` annotations with `run_id`, terminal `status` (`completed`, `failed`, `cancelled`, or `interrupted`), `timing`, and the Run-owned `iteration_count`. Run summaries are append-only records that annotate the preceding Assistant Run for reload/UI display; interruption annotations and Run summaries are not ordinary provider-visible chat fields. A summary without `iteration_count` carries unknown Iteration history and remains loadable for imported/pre-field transcripts, but consumers must not reconstruct a replacement from Assistant or Tool records; every summary created by the current Chat loop includes the field.
- Metadata sidecars use `<session-id>.meta.json` beside the session file. Metadata and completion-activity rewrites use the shared durable atomic-write helper: the temporary file is flushed and `fsync`ed before `os.replace`, and POSIX directory entries are `fsync`ed afterward.
- A successful manual or automatic Compaction rotates `prompt_cache_affinity_id` after appending its checkpoint; the active auto-Compaction Run immediately uses the new value for subsequent Model steps. The transcript projection may break every prior prompt prefix at this boundary by design.
- Completion activity sidecars use `<session-id>.activity.json` with the latest terminal Run and exact `read_run_id`; they are public only through normalized Session projections, never by exposing the persisted object directly.
- Continuation journals use `<session-id>.continuation.jsonl` beside the session file. Each batch is appended through one append-only descriptor and fsynced; a torn final record is truncated on load, while malformed complete records fail loudly. Chat clears a resolved/discarded journal instead of rewriting snapshots during a Run.
- Session IDs must be 1-128 ASCII letters, digits, hyphen, or underscore and must not start with punctuation.
- Public/server-facing session identifiers are UUID strings. Internal helpers may accept custom IDs, but must validate them before any path construction.
- `list_with_metadata()` derives `created_at` and `last_active_at` from first and last persisted messages; empty sessions fall back to the session file mtime. It uses `bookend_timestamps()` so listing does not load full session files; the full unlocked `load()` path runs only when the fast path returns `None` and never repairs an incomplete tail while a writer may be active.
- Unknown future fields in persisted message JSON may appear; session storage validates through `ChatMessage.from_dict()` and should not depend on provider-specific metadata shape.

## Cross-Domain Rules

- `core/chat/` owns `ChatMessage`, provider-request assembly, Run execution, note embedding, and compaction behavior.
- `core/sessions/` owns session persistence, metadata persistence, ID validation, existence checks, and storage path details.
- `core/agents/` may create and validate current sessions only through `ChatSessionManager`.
- Channel adapters must use `ChatSessionManager.exists()` / `get_or_create()` / metadata methods instead of deriving `.jsonl` paths.
- Server RPC delegates should expose session operations through the runtime service and keep storage details out of the public contract.
- Session deletion remains the Sessions archive workflow, but its admission-guarded server orchestrator first asks `TerminalManager` to terminate every Terminal Session with the exact same `(project_id, agent_id, session_id)` owner. A Chat Session archive must not leave its interactive children reachable without an owner.
- `core/recall/` and `core/statistics/` may maintain derived indexes, but JSONL remains canonical. Their indexes must be disposable and rebuildable through `ChatSessionManager`; Statistics uses the Sessions-owned append cursor instead of parsing or constructing JSONL paths itself.
- **Cross-accessor append ordering:** a Run's tool cycle must stay contiguous in the transcript. Runs on one Session are serialized by `ChatRunManager`, while out-of-band note writers such as Channel observations and `channel_send` acquire `ChatSessionManager.write_lock(...)` around their append. The Chat executor takes its initial canonical snapshot under that lock so a crash-torn tail is repaired before the Run can append; it also uses the lock to append any speech note, tagged reply-surface note, and initiating visible/internal message as one ordered boundary. Automatic Compaction snapshots and conditionally commits under this lock but performs its Model call outside it, so an out-of-band writer is never delayed by Provider latency and a stale checkpoint cannot hide the concurrent append. `session.link_channel` writes metadata only and no longer appends a note.

## Constraints & Gotchas

- Skill contexts are not a separate store: they are persisted as ordinary `role: "note"` messages prefixed `[skill-context] ` and lazily rebuilt from the current post-checkpoint epoch on first access (cached in-memory thereafter). Use the exported `is_skill_context_note()` predicate to recognize them, and the exported `skill_context_note_name(message) -> str | None` to read the activated skill's name (malformed/nameless payload → `None`; the statistics skills section consumes this) — never treat these notes as normal user-visible or provider-injected notes, and never re-implement the prefix/JSON parse outside this domain. Original pre-checkpoint carriers remain append-only History even though they no longer confer active instructions or environment grants.
- Other kernel-internal `role: "note"` types follow the same prefix/predicate pattern: `[channel-message] `, `[skill-available] `, and Chat-owned `[reply-surface] `. The reply-surface tag encodes only WebUI or platform + Channel identity/rendering facts; Chat scans full append order against `compaction_checkpoint` entries and strips the tag when rendering the exact model reminder. Passive Channel observations remain separate untrusted context. Interrupted readable Thinking belongs only to the continuation journal, never a note.

## SQLite Migration Notes

- This domain boundary exists so a later SQLite implementation can replace JSONL without changing ChatLoop, server RPC, channel routing, or WebUI contracts.
- A SQLite implementation should preserve `ChatMessage.to_dict()` payload JSON as the canonical message shape, with indexed columns only for lookup/listing.
- Format changes must use explicit converter scripts under `scripts/converters/`; do not add silent startup migrations to app code.
