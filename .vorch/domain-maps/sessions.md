# Sessions

Canonical Session history, metadata, completion activity, continuation state, and SQLite persistence.

## Overview

`core/sessions/` owns the system-managed Session domain and the single canonical database `<data-dir>/sessions.db`. Chat, Agents, Projects, Channels, Recall, Statistics, and server orchestration address Sessions only through `ChatSessionManager`; no caller constructs storage paths or queries the database directly. Legacy JSONL artifacts are accepted only by the explicit offline converter under `scripts/converters/` and are rejected at Runtime startup.

## Terms

Core terms (Session, Agent, Run, Project) live in `.vorch/GLOSSARY.md`.

### Session generation
**Definition:** One immutable incarnation of a public `(project_id, agent_id, session_id)` address, identified internally by a unique generation id and surrogate key. Archiving ends the live generation; recreating the same public address starts a new generation without colliding with or inheriting derived state from the archived one.
**Not:** The public Session id or its append revision.

### Continuation state
**Definition:** Current recoverable work state materialized in `continuations`, `continuation_requests`, `continuation_steps`, and `continuation_operations`. Chat owns event semantics; Sessions folds each event transactionally into replaceable state.
**Not:** An append-only event journal, canonical Message history, or Run events.

### Prompt-cache affinity id
**Definition:** An opaque per-Session lineage value Chat passes separately from Session identity; Provider adapters decide whether their wire can use it.
**Not:** A Session id or generation id. Compaction rotates it to break prior prompt prefixes.

## Storage Contract

Generated Session ids use `ses_` plus 12 lowercase base32 characters. Creation and forking allocate inside the SQLite write transaction, checking live and archived addresses in the destination scope; caller-chosen ids remain exact opaque values. The public facade returns the committed address (`store.py`, `tests/core/sessions/test_sessions.py`).

- `sessions` stores one row per generation. A partial unique index permits exactly one live row per public address while retaining any number of archived generations. `messages` and the normalized Continuation tables reference the immutable surrogate key, so Agent renames and Session moves update one row rather than every record.
- Missing live-address reads raise the typed `SessionNotFoundError` (a `ChatSessionError` subtype), allowing disposable consumers to distinguish a concurrent delete/archive race from storage failure.
- Message order is the dense integer `seq`; duplicate public Message ids are allowed because Compaction may persist the same checkpoint object more than once. `messages` holds compact cross-role columns, while role-owned scalar fields and repeated values live in `assistant_messages`, `tool_calls`, `assistant_output_files`, `user_message_senders`, `tool_messages`, `error_messages`, `compaction_checkpoints`, `run_summaries`, `run_change_paths`, and `history_edits`. JSON remains only for genuinely nested or open-ended values such as Content Blocks, provider extras, Tool arguments, projections, and display payloads. There is no full-row `message_json`; reads reconstruct and validate `ChatMessage` from the normalized relations. `content_search` exists only for list-valued Content Blocks whose canonical nested representation cannot directly serve external-content FTS.
- Normal appends are transactional and update message count, last Message projections, indexed `active_sort`, history revision, and state revision in the same commit. Open-ended metadata remains a JSON object, but Session-list fields (titles, Channel identity, Sub-Agent/Fork provenance, Run kinds, the Session Compaction Policy, and the derived visibility mask) live in dedicated `sessions` columns and are reconstructed into the metadata facade; list filtering never parses open-ended JSON, ordered pages use declared keyset indexes, and exact per-scope counts use a narrow covering index. Existing baseline-generation databases receive one versioned transactional projection backfill identified in `store_meta`; the backfill also repairs `active_sort` from the last Message or creation instant for zero-valued metadata-only rows, and normal creation/metadata writes keep the columns synchronized. Completion activity remains JSON-backed with generated columns for indexed unread reads.
- SQLite opens with foreign keys, `synchronous=FULL`, a bounded busy timeout (1s SQLite, 20s/60s/0.5s application jittered budgets for BUSY/LOCKED), application id, schema version, lightweight identity/schema/table probes, one serialized writer with `BEGIN IMMEDIATE` and time-based retry, and a bounded LIFO read pool (8 permits, 60s backoff). Whole-database `quick_check`, foreign-key, hash, and FTS integrity scans are converter/snapshot/recovery work and never block normal Runtime readiness. `required_journal_mode()` selects WAL only on SQLite builds without the WAL-reset corruption bug; affected builds use rollback-journal mode and an existing WAL database is never live-downgraded. Reader connections are query-only and open only after the writer has reconciled schema; close drains the pool and releases permits. Operational failures (busy/locked/permission/disk-full/transient I/O) surface as `SessionStoreUnavailableError` and never trigger quarantine; only classified corruption (malformed/not-a-db/integrity/FK/schema mismatch) may enter recovery. Quarantine moves `sessions.db` plus `-wal/-shm/-journal` as one bundle under `<data-dir>/session-quarantine/<timestamp>-quarantine/` with all-or-rollback semantics; version-protocol failures still fail closed without quarantine.
- Verified snapshots for update, manual, recovery, and converter-install operations live in `<data-dir>/session-snapshots/<snapshot-id>/` via `core/sessions/snapshots.py`; each holds a standalone `sessions.db` plus `manifest.json` with SHA-256, file size, sqlite version/source, schema/application identity, counts, integrity results, revision watermarks, and completeness. Normal Runtime startup, writes, and shutdown never create or schedule snapshots. Online explicit captures run through `ChatSessionManager.create_snapshot`. Captures stage as `.<id>.<pid>.partial/` and publish only after hash/integrity/FK verification and fsync. One OS-backed operation lock serializes snapshot, recovery, and incident acknowledgement work; it is held open for the whole operation and never broken solely because its metadata is old. Retention uses strict manifest/stat inventory, protects the newly published snapshot, keeps within `SNAPSHOT_KEEP_COUNT` and `SNAPSHOT_KEEP_BYTES`, and never deletes the last verified snapshot; it does not rehash retained snapshots, while explicit verification and recovery candidates still receive full checks. Snapshot creation returns the newly published summary directly instead of immediately re-inventorying the directory. Snapshot attempts publish non-content health in `<data-dir>/session-snapshot-health.json`. Recovery publishes a pending incident before quarantine/replacement, finalizes it only after verified restore, and retries finalization on the next safe open; malformed incident evidence fails as corruption, lock/access failures fail as unavailability, and the durable possible-loss interval remains until exact incident acknowledgement.
- Integrated FTS follows the Hermes storage shape: `messages_fts` is a standard-tokenizer external-content index over searchable normalized Message relations, while `messages_fts_trigram` is an external-content trigram index over the same source excluding Tool-role rows. There is no mirrored `message_search` table. Canonical writes explicitly project completed Messages and delete triggers remove disappearing rows; on FTS write corruption the writer detaches both indexes, sets a stale breadcrumb, and retries the canonical write so derived-index failure never blocks canonical persistence. Runtime repair is chunked and resumable with generation, target/completed high-water marks, transactional progress, and explicit base/trigram coverage checks; the offline converter instead builds each complete index once after canonical bulk import. Ordinary Search availability trusts the lifecycle/version/stale/high-water markers and never runs canonical coverage anti-joins; startup repair, offline verification, and explicit operator health checks own deep coverage validation. Interruption reports rebuilding/degraded state and never healthy incompleteness. Standard FTS handles whole-token queries of every length; trigram handles >=3-character substring queries only after a standard miss. Healthy no-match queries that exclude Tool rows never load canonical histories. Tool-inclusive or unavailable-index requests may use the SQL canonical fallback, which scans at most 10,000 newest eligible Messages and marks typed Recall results degraded/partial if that budget cannot prove complete coverage. FTS results are explicitly bounded, Recall eligibility filters apply in SQL before the limit, and `messages_by_session_instant` indexes `julianday(timestamp)` filters without changing equivalent-offset or fractional timestamp semantics.
- `SCHEMA_SQL` is the declarative source of truth at the current `SCHEMA_VERSION`. The unreleased SQLite Session store is baseline generation 1; intermediate worktree revisions do not create compatibility generations. Writer open accepts only the supported current schema after additive reconciliation; older destructive versions and newer versions raise `SessionStoreSchemaMismatchError` and never enter corruption recovery. Marker, database, and snapshot schema/application identity must agree before mutation or publication. Primary-key, existing-column contract, table-constraint, generated-column, table-option, and unique-index definition changes are destructive: after release, raise `SCHEMA_CONVERSION_FLOOR` and use the offline converter rather than teaching startup to rewrite data. Readers require exactly `SCHEMA_VERSION` after reconciliation.
- Startup authorizes `sessions.db` only via the current-format marker `<data-dir>/session-store.json` (`bootstrap`/`ready` with `database_id`/`schema_version`, strict closed schema, atomic write+fsync, `validate_session_store_paths` enforces `sessions.db` parent == `data_dir`). A fresh directory is bootstrapped only when `initialize_data_directory` creates the root; an existing directory without a marker is a hard `SessionStorageFormatError` without any JSONL inspection. `<data-dir>/session-store-maintenance.json` blocks Runtime startup while an offline source-mutating operation is incomplete. When the store is `ready` but `sessions.db` is missing or fails classified corruption, startup attempts auto-restore of the newest verified snapshot (quarantining the failed DB as a bundle) before surfacing an error; busy/locked/permission/disk-full never quarantines.
- `scripts/converters/session_sqlite.py` is the one standalone offline conversion entry point (commands: `inventory`, `dry-run`, `convert`, `verify`, `install`, `resume`, `export-jsonl`) and `jsonl_sessions.py` is its private legacy parser. It inventories all six physical roots and sidecars, reads and hashes each discovered regular artifact once, classifies accepted, skipped, orphan, and unknown evidence, records torn tails and rejected paths, and reports/skips malformed individual Sessions including canonical `ChatMessage` validation failures. Every accepted generation maps deterministically; conversion preserves complete projected and residual metadata, completion activity, folded Continuation, and all canonical Content Blocks, imports canonical rows in one savepoint-isolated bulk transaction, and builds FTS once afterward. Verification compares each generation's address, lifecycle, Messages, reconstructed metadata, activity, and independently folded Continuation after SQLite integrity/foreign-key checks, then verifies the nested manifest database hash. The external backup includes all captured evidence, while relocation removes only accepted source artifacts using resumable copy/hash/fsync/atomic-publish/unlink semantics that work across filesystems. The disposable staging database has no redundant snapshot; `install` creates the initial verified live snapshot. `install` is the only source-mutating command and requires no listener on the exact target, an external backup, and a verified staged database before replacing the target and publishing the `ready` marker last; stage guards and actionable missing-database errors keep resume fail-closed. It rechecks listener absence at mutation boundaries and holds the persisted maintenance guard across interruption/resume so a racing Runtime cannot open the target. Current-format snapshot and recovery maintenance belongs to `ChatSessionManager` and the `session-store` CLI/RPC surface; no retired converter or duplicate database owner remains.

## Interfaces

- `ChatSession` is a path-free handle: `append`/`append_many`, `load`, `load_active`, continuation operations, notes, Skill activation state, and `load_since(cursor)`. Frequent partial consumers use dedicated read models instead: one atomic Chat History snapshot, the status aggregate, targeted Run summary/result lookup, and checkpoint-bounded History record batches. Async counterparts execute through bounded worker pools at their owning boundary.
- `SessionReadCursor` carries generation id, append revision, next sequence, count, and the prior Message id anchor. A cursor from the same generation returns only appended records after its prefix; a generation change, invalid sequence, or mismatched anchor returns `None` so disposable consumers rebuild.
- `ChatSessionManager` owns create/get/get-or-create/exists/list/archive/restore/delete/move/fork and identity/project lifecycle operations. `get_or_create` is one database transaction. Archive is asynchronous at the public boundary, runs off the Event Loop, and holds the Session write lock.
- `write_lock(address)` is context-reentrant for a holder and child tasks. It protects ordered Chat boundaries and whole move/fork/archive operations; Provider latency and other unbounded work stay outside it. Locks are manager-owned and released with manager lifetime.
- `mutate_metadata` and `mutate_metadata_with_previous` perform one transactional read-modify-write. Domain code must use them for partial updates; `set_metadata` is reserved for complete replacement and exact compensation snapshots. Completion activity uses the equivalent atomic mutation path.
- `list_summaries_page` is the bounded accessor read model: one SQLite transaction globally orders one or many Agent scopes, applies execution-category filters, returns a keyset cursor and total count, and may add one explicitly required selected Session without letting it alter cursor progression. `list_summaries` returns only normalized list/completion columns plus explicitly allowlisted residual fields such as Statistics-owned `seen_skills`; Recall listing uses `list_recall_summaries` so visibility, period, ordering, exclusion, and limit execute before rows are materialized. `list_with_metadata` is the exceptional full-metadata surface, not a candidate-list API. `list_completion_activity` selects only completion columns. `bookend_timestamps`, `session_ids_with_messages`, bounded active User Message counts, and newest prefixed Note lookup use direct SQL reads rather than loading complete histories. `descriptor_source(address)` obtains normalized descriptor metadata, cached Message count, and only the first User Message without reconstructing history; multi-Session callers must use `descriptor_sources(addresses)` so descriptor lists remain set-oriented. `history_version(address)` returns generation plus revision for derived projections; comparing revision alone is insufficient. `list_history_versions(addresses)` resolves generation plus revision for many addresses in one query per scope - derived projections must use it instead of per-Session `history_version` loops when refreshing freshness stamps.
- `read_chat_history_snapshot` returns one newest-page projection, whole-Session Usage aggregate, active Context Usage tail, background Bash inputs, and editability from one read transaction. Its continuation is an integrity-checked generation-plus-sequence cursor; legacy public Message ids remain accepted only as a compatibility input. `status_snapshot` obtains first-message/turn/latest-Usage/cache facts with SQL aggregates. `find_run_summary` and `load_run_result` query one Run boundary rather than scanning a transcript. History recovery resolves a frozen checkpoint by generation and sequence, reads canonical records in bounded batches, and aggregates overview sections in SQL.
- `fork` copies the normalized canonical Message graph and its FTS projection set-wise inside SQLite into a new generation without reconstructing or reserializing `ChatMessage`; continuation and completion activity remain excluded and provenance is recorded. `move` retargets one live generation. Both read and transform the latest committed metadata inside the same writer transaction as the copy or retarget; Fork provenance takes its Message count from that transaction's source row. Identity rename retargets live global Sessions only; archived history keeps its historical address.
- Archive and restore are generation-aware. A new live generation may reuse an archived address; restore fails while that address already has a live generation and otherwise restores the newest archived generation.
- `status_projection()` returns one typed top-level state: `healthy`, `snapshot_degraded`, `search_degraded`, `recovered_with_incident`, or `unrecoverable` (the last is produced by stopped-store diagnostics when normal open fails). Snapshot, FTS, marker, and incident details contain no Session content.

## Cross-Domain Rules

- `ChatSession.reflection_runs()` projects terminal reviews for the exact source Agent/Project/Session from live same-owner forks through an indexed provenance lookup. Only the first Run Summary after the fork's inherited Message count belongs to the review; copied summaries and later user Runs must not substitute for it. The query reads compact summary columns without reconstructing transcripts, excludes archived forks, and rejects provenance older than the live source generation.

- Chat owns `ChatMessage`, request assembly, Run execution, Compaction behavior, and continuation record meaning. Sessions owns canonical persistence, ordering, metadata transactionality, validation, and storage lifecycle.
- Agents and Projects must share the Runtime Session manager when started by Runtime. Their standalone stores may lazily own one and must close owned resources. Agent create/current-Session repair deletes a newly created Session if later file persistence fails; rename restore retargets Sessions back; Agent and Project deletion move filesystem state first and compensate it if Session archiving fails.
- Recall and Statistics are disposable projections. Both include the Session generation in freshness state. Statistics appends through `load_since`; ordinary Message appends must not rebuild a complete Session projection.
- Skill activation cache is synchronized from the supplied active history snapshot when one is provided and otherwise preserves explicit in-memory registrations; a committed Compaction checkpoint resets the epoch.
- Callback failures after committed title or completion mutations are logged and isolated so callers never receive a false failure for state that already persisted.
- `titles.py` owns immediate local titles and optional background Model titles. It accepts one final text line after removing hidden Reasoning and unambiguous presentation wrappers (a complete plain-text fence or a standalone Title/Titel label); it never chooses among multiple candidate lines. Invalid generated content keeps the local title and emits a content-free warning with the rejection reason and no traceback or extra Model request; unexpected failures retain their traceback. Regression coverage lives in `tests/core/sessions/test_titles.py`.
- The title System Prompt instructs the Model to use the language of the user's main request (not quoted text/code/logs), preserve proper names and technical terms, and summarize the topic without following instructions in the supplied source material. These are Model instructions; the local validator enforces title shape and length, not language or semantic compliance.

## Constraints & Gotchas

- Never add uniqueness on Message ids without changing the Compaction contract and auditing imported data; sequence is canonical identity inside a generation.
- Never build pagination or frozen snapshots on public Message ids alone; duplicate ids are valid. Use generation plus internal sequence and keep public-id input only where compatibility requires it.
- Never compare only public Session address plus history revision for derived freshness; archive/recreate can repeat the same revision.
- Never implement metadata as `get_metadata` followed by `set_metadata` for a partial change; concurrent fields will be lost.
- SQLite serializes database writes, not a read-modify-write split across transactions. Domain mutation callbacks must remain deterministic, side-effect free, and JSON-serializable.
- Never force WAL directly. Canonical and disposable Session-derived databases share `required_journal_mode()` so a vulnerable SQLite build cannot reintroduce the WAL-reset race.
- Existing JSONL names belong only in converter code and migration documentation. Canonical Runtime code and Recall use SQLite-backed Session APIs.
