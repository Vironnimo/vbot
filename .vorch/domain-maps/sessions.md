# Sessions

Canonical Session history, metadata, prompt state, completion activity, Continuation state, and SQLite persistence.

## Overview

`core/sessions/` owns the system-managed Session domain and the single canonical database `<data-dir>/sessions.db`. Chat, Agents, Projects, Channels, Recall, Statistics, and server orchestration address Sessions only through `ChatSessionManager`; no caller constructs storage paths or queries the database directly.

History is stored once. A fork reads its source's entries through lineage instead of copying them, and a history edit supersedes the replaced tail in place instead of deleting it. Every history read therefore names one view: the current view (what the Session shows and sends to the Model) or the own audit (what the Session itself wrote). See Terms.

## Internal source routing

The public `core.sessions` package routes stable imports to the Session service in `sessions.py`, the buffered Session handle in `session.py`, immutable records in `_types.py`, and semantic history helpers in `history.py`. Metadata validation/cursors and bounded I/O/write leases live in `_metadata.py` and `_io.py`. Canonical timestamps come from `core/utils/timestamps.py`.

`store.py` opens the Session database through the shared kernel (`database.md`) and keeps read/write admission, the Session write budgets and FTS error recovery. Private `_store_*` modules receive its connection:
- `codec` - per-role entry rows and side tables, set-wise decoding, Tool-result linking, materialized copies.
- `lineage` - the lineage visibility predicate (`admits`, the one fragment every view read, the search candidates and the FTS membership views are built from), view ranges, fork lineage and edit truncation; every current-view read goes through `view_ranges` plus `ordered_rows` (one index range scan per range) or `view_query` (one set-wise query over a `VALUES` CTE of the ranges). It imports no other store module, so `schema.py` builds on it.
- `history` - bounded reads over one explicit view (current view, own audit, own spend), cursors and deltas, Run lookups, History Tool batches.
- `usage` - paged accounting-only own-audit export across live and archived generations, through `ChatSessionManager.usage_history`; includes entry and Message identities plus Assistant interruption state, without inherited prefixes or content decoding. The independent canonical recorder imports this evidence and repairs incomplete records after restore (`usage.md`).
- `timeline` - the WebUI Chat History snapshot and edit eligibility (`_editable`, `latest_takeover`).
- `operations` - compound transactions: the Compaction commit and the history edit.
- `prompts` - prompt pins, seen Skills and the prompt-cache affinity id.
- `runs` - admission, completion, restart recovery and completion activity.
- `continuation` - folds Continuation records into current state.
- `mutations` - lifecycle (create, archive, move, fork, restore, delete with delete-time detachment), metadata writes and plain appends.
- `queries` - catalog, Session-list summaries, descriptors and revisions.
- `owned` - temporary bindings, delivery receipts and owned Runs.
- `values` - Session row columns, the metadata facade, scope and value validation.
- `fts` - disposable index lifecycle; `search` - bounded search.
- `schema` - the kernel spec (`session_database_spec`: the DDL from `schema.py`, the FTS readiness hook, snapshot facts and status health).

Do not open independent runtime connections or commit within a helper; entries, metadata, revisions, prompt state, Continuation, receipts and FTS effects must share the caller's transaction. Helpers return typed records or summary dicts rather than raw rows, so `ChatSessionManager` does not decode storage columns. Read helpers that reconstruct Messages or decode JSON columns (summaries, temporary bindings) select rows inside the read transaction and return a decoder; `store.py` (`_read_decoded`) runs it after the transaction ends, because a rollback-journal store serves reads on the serialized writer.

Data snapshots, quarantine, restore, recovery incidents and the data-store marker belong to the kernel (`database.md`); the Session store contributes only its spec hooks.

Session and group title generation records each exposed Adapter request through
the injected `UsageRecorder`, including the explicit effort retry, before title
validation or persistence. Invalid titles and later Session/group deletion keep
their known consumption; accounting stores no generated title response content.

## Terms

Core terms (Session, Agent, Run, Project) live in `.vorch/GLOSSARY.md`.

### Session generation
**Definition:** One immutable incarnation of a public `(project_id, agent_id, session_id)` address, identified internally by a unique generation id and surrogate `session_key`. Archiving ends the live generation; recreating the same public address starts a new generation without colliding with or inheriting derived state from the archived one.
**Not:** The public Session id or its history revision.

### Entry
**Definition:** One stored history item: an `entries` row with a dense per-Session `seq`, a role and a public Message id (`entry_id`, not unique), with role-specific values in 1:1 side tables. Every role is a physical entry, including Tool results, Run summaries (`run_summary`) and history-edit markers (`history_edit`). Reads decode entries into `ChatMessage`s.

### Current view
**Definition:** What a Session shows and sends to the Model: its own non-superseded entries plus the entries it inherits through lineage, as sorted disjoint seq ranges (`_store_lineage.view_ranges`). `load_active`, Provider history, the History Tool, Recall context, Search, counts, Notes, the Skill cache and the Chat History snapshot read it.
**Not:** The own audit.

### Own audit
**Definition:** Every entry the Session wrote itself from its fork point on, superseded ones included (`ChatSession.load`, `SessionReadBatch.messages`). Statistics consumes it, and the Session's own spend (`session_usage`) sums its Assistant usage.
**Not:** The current view. Inherited entries and materialized copies precede the fork point and are not the Session's own.

### Lineage and fork point
**Definition:** A fork's `session_lineage` rows name, per inherited seq range, the ancestor Session that stores those entries and the ancestor's `next_seq` at fork time (`as_of_seq`). Lineage is flat: a fork of a fork references the storing Session directly, so no read follows lineage recursively. The fork point (`sessions.fork_point_seq`) is the seq where the fork's own entries start.
**Not:** `fork_parent_key`, which only names the direct source for `fork_source` and reflection lookups.

### Superseded entry
**Definition:** An entry a history edit replaced; `superseded_at_seq` records the edit's seq. It leaves its owner's current view but stays stored for the own audit and for forks whose lineage was frozen before the edit (`superseded_at_seq >= as_of_seq`). A `history_edit` marker is superseded at its own seq, so no current view contains it.

### Materialized copy
**Definition:** When a Session with descendants is deleted, each descendant first receives its own copy of every entry it inherited from it: same `seq` and id, a new `entry_key`, side rows, Tool calls with payloads, and the referenced Runs. Copied Runs are `inherited` (never admitted again, no activity contribution); unfinished copied Runs and calls end `interrupted`.
**Not:** The descendant's own history; copies precede its fork point.

### Continuation state
**Definition:** Current recoverable work state materialized in `continuations`, `continuation_requests`, `continuation_steps`, `continuation_step_chunks` and `continuation_operations`. Chat owns event semantics; Sessions folds each record transactionally into replaceable state and returns it as one typed read model, `SessionContinuationState` (`ChatSession.load_continuation`). A step is identified by Run id plus a positive Run-local step number (Chat numbers a Run's first Model step 1); a record naming a Run must name a Run of this Session, and an invalid record rolls back the whole append. Each stream delta inserts one chunk row, so a flush never rewrites a step's accumulated text; the Assistant boundary folds the step's chunks into one (`_store_continuation.py`). Records other than `run_started` are ignored while the Session has no Continuation.
**Not:** An append-only event journal, canonical Message history, or Run events.

### Prompt state
**Definition:** Per-Session prompt inputs kept outside metadata (`_store_prompts.py`): prompt pins (named `pinned_*` slots, each referencing one content-addressed `prompt_blobs` row that forks share), the seen-Skill set (`session_seen_skills`; `None` until first recorded) and the prompt-cache affinity id. They have dedicated APIs; the metadata facade rejects their keys.

### Prompt-cache affinity id
**Definition:** An opaque per-Session cache-lineage value Chat passes separately from Session identity; Provider adapters decide whether their wire can use it. It is the `prompt_cache_affinity_id` column; while that is NULL, `prompt_cache_affinity_id(address)` derives a deterministic default from the address. A Compaction commit and a history edit rotate it to a new random value; a same-scope fork or move keeps the effective value, a cross-scope one starts a new one.
**Not:** A Session id or generation id.

## Extension-owned execution

Temporary Session bindings, delivery receipts, Run execution owners and group titles live in dedicated relations outside open metadata; `core/agents/temporary.py` is the owner-bound creation/admission facade and domain state belongs to the Extension. Exact address plus Session generation and registered owner establish authority; no fork or materialized copy carries a binding. Owner-managed Sessions reject ordinary archive, move and delete, and a fork unless the caller names a target Agent and the fork lands in another scope; `delete_temporary_group` removes a drained group. Ordinary Agent/Project discovery must not report the synthetic `tmp_...` participant Agents: `list_agent_ids(exclude_owner_managed=True)` backs `ProjectStore.session_owning_agents`. Relations, reads and receipts: `sessions/owned-execution.md`.

## Storage Contract

Generated Session ids use `ses_` plus 12 lowercase base32 characters. Creation and forking allocate inside the SQLite write transaction, checking live and archived addresses in the destination scope; caller-chosen ids remain exact opaque values. The public facade returns the committed address (`store.py`, `tests/core/sessions/test_sessions_concurrency.py`).

- All tables are `STRICT`. `sessions` stores one row per generation. The partial unique index `sessions_one_live_address` permits exactly one live row per public address while retaining any number of archived generations; `sessions_archived_address` serves archived-address lookups (id allocation, restore). Entries, Runs, lineage, prompt state, Continuation and owned relations reference the immutable surrogate `session_key`, so Agent renames and Session moves update one row. `store_meta` holds the FTS lifecycle markers.
- Missing live-address reads raise the typed `SessionNotFoundError` (a `ChatSessionError` subtype), allowing disposable consumers to distinguish a concurrent delete/archive race from storage failure.
- `entries` holds every history item (Terms -> Entry) with `UNIQUE(session_key, seq)`; large or role-specific values live in 1:1 side tables (`entry_text`, `assistant_entries`, `assistant_reasoning`, `assistant_output_files`, `user_entry_senders`, `error_entries`, `history_edit_entries`, `checkpoint_entries`, `checkpoint_projections`). Reads select entry rows first and then only the side tables their roles need, set-wise by `entry_key`. `assistant_entries` stores the Usage field-provenance flags but not the whole-turn `estimated` summary, which the codec derives on read; `assistant_output_files` requires every reference's marker span (`start_index`, `end_index` NOT NULL). `entry_key` is `AUTOINCREMENT` because it is the FTS rowid and the rebuild high-water mark. JSON is reserved for open payloads (content blocks, arguments, Provider extras, display payloads).
- `runs` owns each execution: status, timing, work id, `start_seq` (the Session's `next_seq` at admission), `inherited`, `contributes_to_activity`, completion facts, and its `run_summary` entry (`end_entry_key`); `(status = 'running') = (completed_at IS NULL)` is a CHECK. Entries reference their exact Run by `run_key`. `tool_calls` holds one invocation per Assistant entry and ordinal with status, timing and the linked result entry (`result_entry_key`, unique); arguments and display live in `tool_call_payloads`. A call stays `pending` without timing while its Tool executes; the Tool-result append links exactly one stored call of the same Session (and Run, when given) and sets its terminal status (`ToolResultFacts`: `completed`, `failed` or `cancelled`; no facts means `completed`), timing and outcome in the same transaction; Run finish or restart recovery settles unfinished calls as `cancelled` or `interrupted`. A Tool that is currently running is visible only through Run events, never as stored state. `tool_result_payloads` holds Extension-attached result payloads per Tool call (`payload_id`, `owner_name`, JSON text): the Tool-result append inserts `ToolResultFacts.payloads` (`ToolResultPayload`) in the transaction that links the result, refusing the whole append for unsafe or duplicate ids, an empty owner or non-text JSON, and materialized copies copy them.
- The `sessions` row carries history state (`next_seq`, `history_revision`, `state_revision`, `cursor_floor_seq`, `last_activity_at`, `last_entry_id`), fork columns (`fork_parent_key` with `ON DELETE SET NULL`, `forked_at`, `fork_point_seq`), prompt state columns, the latest-completion columns (Run references by `run_key`, see Interfaces), and the Session-list fields (titles, Channel identity, Sub-Agent parent link, the Session Compaction Policy, the derived visibility mask). Run kinds live in `session_run_kinds`. List filtering never parses open-ended JSON (`metadata_json` holds only residual metadata); ordered pages use declared keyset indexes, and exact per-scope counts use a narrow covering index. There is no projection backfill.
- Channel metadata keys are listed in `channels.md`. Channel conversation pointers, conversation kinds and group participants are Channel state in `channels.db`, not Session metadata.
- Appends are transactional: `append_messages` writes the entries at `next_seq`, then updates `next_seq`, `last_activity_at` (the last Message's canonical timestamp), `last_entry_id`, both revisions and the FTS rows in the same commit. Plain appends accept `system`, `user`, `assistant`, `tool`, `note`, `error`, `compaction_checkpoint` and `agent_takeover`; other roles are written by their Session operation. A Compaction checkpoint without a projection is rejected. An `agent_takeover` raises `cursor_floor_seq` past itself.
- Every stored timestamp is canonical UTC text `YYYY-MM-DDTHH:MM:SS.ffffffZ` (`core/utils/timestamps.py`), so text order is time order; writes normalize other ISO 8601 forms and reject values without an offset.
- `sessions.db` is a canonical kernel database: connection and journal policy, the serialized `BEGIN IMMEDIATE` writer with jittered busy retry, the bounded LIFO read pool, page caches (64 MiB writer, 16 MiB per pooled reader), error classification, quarantine and metrics are kernel behavior (`database.md`). Session write budgets are 20s by default, 60s for transcript writes (appends, receipt appends, `finish_run`, `commit_compaction` and `apply_edit`) and 0.5s for the advisory completion-read write `mark_terminal_run_read` (`store.py`). Whole-database `quick_check`, foreign-key, hash, and FTS coverage scans never block normal Runtime readiness. Operational failures (busy/locked/permission/disk-full/transient I/O) surface as `DatabaseUnavailableError` and never trigger quarantine; only classified corruption may enter recovery, which moves the bundle to `<data-dir>/quarantine/sessions/<YYYYmmddTHHMMSS>-<uuid8>/`. Stored rows that cannot be trusted raise `SessionStoreCorruptError` (a `DatabaseCorruptError`). Metrics are `sqlite.sessions.write`, `.write_wait` and `.read` (`performance.md`).
- `sessions.db` is a member of every data snapshot (`database.md`); the Session spec adds the snapshot facts `session_count`, `entry_count`, `latest_history_revision` and `latest_state_revision`, recomputed when the copy is verified. Normal Runtime startup, writes, and shutdown never create or schedule snapshots. Online captures (`data_store.snapshot_create`) copy through the open kernel handle, so streaming Runs keep committing in WAL mode; in rollback-journal mode the copy holds the connection lock and writes and reads queue for its duration (a few seconds per GB).
- Search uses two disposable external-content FTS5 indexes over the entries some current view contains: the standard `entries_fts` and the trigram `entries_fts_trigram` (User, Assistant and Compaction-checkpoint text only). A derived-index failure never blocks a canonical write. Index shape, upkeep, rebuild and query behavior: `sessions/search.md`.
- `SCHEMA_SQL` (`schema.py`) declares format generation 1 of the Session database. The kernel checks identity and generation, applies the additive reconcile and probes every table before readers open; an already current schema requires no write transaction.
- A pre-Generation-1 `sessions.db` (application id 0, `VBOT` or the interim `VBSS` with the old `messages` shape) is converted offline by `scripts/converters/persistence_generation_1/sessions.py`: every Session is rewritten through the Generation 1 codec, legacy edits become superseded entries, legacy boundary checkpoints get the projection the old reader derived (and old projections lose the retired Tail-guidance note), a fork whose copied prefix still matches its source shares it through `session_lineage` (otherwise it keeps its copies below its fork point), Continuations are dropped, the retired Channel routing keys (`active_session_id`, `conversation_kind`, `participants`) leave metadata, other retired values are renamed or dropped (Reflection counters and `visited_projects` in metadata, the `fork_snapshot` completion reason of Runs, `_reasoning_key` in Assistant `reasoning_meta`: `database/generation-1-conversion.md` -> Retired fields and values), and three old Assistant Message shapes get their current form in history and stored checkpoint projections: a line-only output-file reference gets the span of its whole line (the old server replaced that whole line with the link), or is dropped when its line is missing, empty or shared with another reference; a Usage whose only provenance was the whole-turn `estimated` gets both field flags (the old reader applied it to both primary counters); and a Usage without a `context_usage` snapshot gets the input-plus-output projection the old reader derived (`chat/usage.md`), or keeps none, reported, when it has no input count. Every drop or approximation is reported; coverage: `tests/scripts/converters/persistence_generation_1/test_sessions*.py`. The later `mcp.py` area attaches saved MCP results to the staged database as Tool result payloads (`extensions/mcp.md`).
- Startup authorizes `sessions.db` only through the kernel marker `<data-dir>/data-store.json` (`database.md`). A fresh directory is bootstrapped only when `initialize_data_directory` creates the root (the call whose `mkdir` succeeded) and writes a marker listing no databases; the first open then creates and registers `sessions.db`. An existing directory without a marker is a hard `DatabaseFormatError` without any JSONL inspection. A process that loses a concurrent root-creation race and opens the store before the winner publishes its marker therefore fails with that error; there is no cross-process wait. `<data-dir>/data-maintenance.json` blocks Runtime startup while an offline restore or conversion is incomplete. A registered `sessions.db` that is missing, fails classified corruption or has another identity is auto-restored from the newest verified data snapshot member (quarantining the failed bundle) before an error surfaces; busy/locked/permission/disk-full never quarantines.
- Run admission (`admit_run`, via `ChatSessionManager.start_run(run)`) commits in one transaction: it creates a missing live Session, inserts the running row at the current `next_seq`, records the Run kind in `session_run_kinds`, and inserts the execution owner (`run_execution_owners`) when the Run has one. Re-admitting a running Run with the same owner and input is a no-op; a settled or inherited Run is rejected. `fork(..., run_kind=...)` records the fork's Run kind in its creating write, so a fork is classified before its Run starts. Admission and that fork label are the only ways a Session gains a Run kind. `finish_run` commits the `run_summary` entry, the terminal Run columns and change paths, unfinished Tool calls (`cancelled` for a cancelled Run, else `interrupted`), removal of the Continuation a completed Run continued, the latest-completion columns (only for an activity-contributing Run), revisions and FTS together, and returns the committed Chat History cursor. Only then does Run management publish a persistence acknowledgement. Startup (`recover_interrupted_runs`) settles running non-inherited Runs of live Sessions as `interrupted` with `completion_reason` `process_restart`, without replaying Model or Tool work.

## Interfaces

- `ChatSession` is a path-free handle: `append`/`append_many`, `load` (own audit), `load_active` (current view), `commit_compaction`, `apply_edit`, Continuation operations, Notes, Skill activation state, and `load_since(cursor)`. `append_many(messages, *, tool_results, seen_skills, continuation_records, since)` and owned receipt appends optionally fold Continuation records and return the `load_since` delta for a given cursor within their write transaction; a rejected record rolls back the whole append. Frequent partial consumers use dedicated read models instead: one atomic Chat History snapshot, the status aggregate, targeted Run summary/result lookup (`load_run_result`/`load_run_result_async`), the manager's `tool_result_persisted_async` probe (an Assistant Tool call stored in the live Session and its durable result, via `tool_calls_by_call_id`; calls a fork inherits through lineage do not count), and checkpoint-bounded History record batches over the current view. Async counterparts execute through bounded worker pools at their owning boundary. `ChatSessionManager.run_async(function, ...)` runs any blocking work that reads or writes Sessions on the Session database's own worker pool (`database.md`); callers outside the domain (Recall, temporary participants and bindings, Sub-Agents, Session/Agent/Chat RPCs, Identity Agent resolution, Channel routing and outbound delivery, `channel_send`, title generation) use it instead of `asyncio.to_thread` or a private pool, keeping only non-database work on their own pools.
- `ChatSessionManager.tool_result_payload_async(address, payload_id, *, owner_name)` returns the decoded payload only when one with that id and owner belongs to a Tool call whose result entry is in the address's current view (own, inherited or materialized), else `None` (also for an unknown Session). It is one statement driven by `tool_result_payloads_by_id` (`test_store_query_plans.py`); its caller is the Extension host (`extensions.md`); coverage `tests/core/sessions/test_tool_result_payloads.py`.
- `commit_compaction(checkpoint, *, since, epoch: PromptEpoch)` appends a `compaction_checkpoint` only while `since` still names the newest entry (same generation, at or above the cursor floor, same `next_seq` and last entry id); otherwise it writes nothing and returns `None`. In the same transaction it replaces the named prompt pins (`epoch.pins`; `None` removes a slot), replaces the seen Skills when `epoch.seen_skills` is given, and rotates the prompt-cache affinity id; it returns the delta after `since` with the new affinity id.
- `apply_edit(target_message_id, messages, *, seen_skills, continuation_records)` replaces history from one current, editable User entry on, in one transaction, and returns `SessionEditResult(batch, prompt_cache_affinity_id)`: the complete own audit and current view after the edit plus the rotated affinity id. It rejects a target that is not a current User entry with plain text and no named sender after the latest Agent takeover (`Only a current User message with plain text, sent after the latest Agent takeover, can be edited`) and a replacement without a User Message. Step order and FTS handling: `sessions/lineage.md`.
- `SessionReadCursor` carries generation id, history revision, next sequence and the prior entry id anchor. `load_since` returns `None` so disposable consumers rebuild when the generation differs, `next_seq` is out of range or below `cursor_floor_seq` (after an edit or Agent takeover), or the entry at `next_seq - 1` has another id; the revision is not checked. A current cursor returns an empty delta from the Session row alone; otherwise one read returns `SessionReadBatch(messages, cursor, active_messages, inherited_count)`: `messages` are the own-audit entries after the cursor, `active_messages` the current view after it, and a fork's own conversation is `active_messages[inherited_count:]`.
- `ChatSessionManager` owns create/get/get-or-create/exists/list/archive/restore/delete/move/fork and identity/project lifecycle operations. `existing_addresses(addresses)` answers existence for many addresses in one indexed statement per 300 addresses; callers must use it instead of per-address `exists` loops. `get_or_create` reads first and creates a missing Session in one write transaction. `ensure_metadata(address, mutation, create_missing=...)` applies an idempotent mutation against a read snapshot and enters the writer only for a real change or creation (reapplying the mutation to the latest row), so re-asserted routing state costs no write; its mutation may run twice and must be deterministic. Archive is asynchronous at the public boundary, runs off the Event Loop, and holds the Session write lock.
- `write_lock(address)` is context-reentrant for a holder and child tasks. It protects ordered Chat boundaries and whole move/fork/archive operations; Provider latency and other unbounded work stay outside it. Locks are manager-owned and released with manager lifetime.
- `mutate_metadata` and `mutate_metadata_with_previous` perform one transactional read-modify-write. Domain code must use them for partial updates; `set_metadata` is reserved for complete replacement and exact compensation snapshots. A metadata mutation whose persisted form is unchanged issues no `UPDATE`, so it neither fsyncs nor bumps `state_revision`; that column only feeds the snapshot manifest's `latest_state_revision` watermark and is not a per-change signal (`test_sessions_listing.py`). The facade includes two derived values a write may repeat but not change (`Session metadata <key> is managed by Sessions`): `run_kinds` from `session_run_kinds`, and `fork_source` = `{agent_id, session_id, project_id, forked_at}`, read through the direct parent's current row, so it follows the parent's renames and moves and disappears when the parent is deleted. Prompt-state keys (`seen_skills`, `prompt_cache_affinity_id`, `pinned_*`) are rejected (`Session prompt state has dedicated APIs, not metadata`).
- Prompt state APIs: `prompt_pin(address, slot)`, `ensure_prompt_pin(address, slot, value, accept)` (keeps an acceptable pin, else pins `value`; check and write share one transaction), `seen_skills(address)` (`None` before the first record), `record_seen_skills(address, SeenSkillsUpdate(baseline, added))` (seeds from `baseline` on first use, then adds `added`; an addition that changes nothing writes nothing) and `prompt_cache_affinity_id(address)`. Unreferenced prompt blobs are deleted in the transaction that drops their last reference.
- Completion activity is the latest-completion columns: `finish_run` sets them for activity-contributing Runs, and `mark_terminal_run_read` writes (and fires completion-read callbacks) only when it marks the latest completion read. The latest completion and its read mark name `runs` rows of the same Session by integer key (`latest_completion_run_key`, `read_completion_run_key`); reads map them to the public Run id at the store boundary (`_store_values._COMPLETION_ACTIVITY_COLUMNS`), so RPC and WebUI keep the `latest_completion_run_id` key. A Run is deleted only with its Session, so the keys never dangle; they carry no SQL foreign key, which would scan `sessions` for every deleted Run. A fork starts without a completion and never names an inherited Run: marking an inherited Run's id read in a fork is a no-op. Ancestor-delete materialization copies Runs under new keys and leaves the descendant's completion columns untouched. The Generation 1 converter keeps a legacy latest completion or read mark only when it names a Run stored in that Session and reports the rest.
- Identity-rename reference compensation restores only the exact `subagent_parent` link it retargeted, conditionally on that link remaining unchanged; concurrent titles, other metadata, and later parent links survive (`test_sessions_identity_references.py`).
- `list_summaries_page` is the bounded accessor read model: one SQLite transaction globally orders one or many Agent scopes, applies execution-category and Channel inclusion filters, returns a keyset cursor and total count, and may add one explicitly required selected Session without letting it alter cursor progression. Channel filtering uses the existing platform plus conversation-id metadata, applies before counts/pagination, and defaults to inclusion at the service/RPC edge; the WebUI explicitly opts out. `list_summaries` returns only normalized list/completion columns plus explicitly requested `metadata_keys`, of which only `seen_skills` exists (derived from the seen-Skill relation, name-ordered, present only once recorded). The Agent-facing Search Tool has no listing mode. There is no full-metadata listing. `newest_session_id(agent_id, project_id)` is the landing read after a Session leaves its scope: `list_summaries_page(limit=1)` with every run kind included and Extension-owned Sessions excluded. `list_addresses(project_id, agent_id=...)` lists bare addresses of one scope or one Agent. `metadata_value(address, key)` (async: `metadata_value_async`) returns one facade value from the Session row (`None` when absent; prompt state is not in the facade). `list_completion_activity(scopes)` reads many `(project_id, agent_id)` scopes in one statement per bounded chunk (a scope `VALUES` join on the live address index) and maps each scope to its live Sessions that have a latest completion, selecting only completion columns; Sessions without a completion are omitted. `summary(address)` point-reads one live Session's list row (`None` when absent). Bounded current User entry counts (`active_user_message_count`) and newest prefixed Note lookup (`latest_note`) are direct SQL reads over the current view. `descriptor_sources(addresses)` returns, in set-oriented reads, each live Session's metadata facade and Recall visibility (`SessionDescriptorSource`). `recall_context(address, message_id)` reads only the enclosing current User question and final Assistant answer, with text bounded in SQL and no full-history hydration. `list_history_versions(addresses)` resolves generation plus revision for many addresses in one query per scope; Statistics refreshes its freshness stamps with it, because comparing revision alone is insufficient. `list_history_revisions(agent_id, project_id)` returns every live Session's generation, revision, Recall visibility and creation order (its `session_key`, larger is newer) for one scope in one query; Recall uses the creation order to attribute inherited Passages to the newest Session that shows them, the same rule as store search.
- Recall visibility (`SessionRecallVisibility`) is classified in SQL from the visibility mask column, so callers never classify metadata in Python: reflection Run kinds make a Session `hidden`; otherwise a Sub-Agent flag or Run kind makes it `subagent`; otherwise a Session without recognized Run kinds or with a user-facing Run kind (`user`, `channel`, `cron`, `calendar`) is `conversation`; anything else (system-only, memory, Skill) is `hidden`. `recall_visibilities(include_subagents=...)` names the admitted values. Message search (`search_messages`) applies it to the eligible Sessions before any candidate is checked.
- `read_chat_history_snapshot` returns a consistent page or bounded append batch over the current view with Usage, editability, record sequence, stored Run membership and explicit Run completeness. `after` is a generation/next-sequence cursor; hidden rows advance it. An edit/takeover floor or generation mismatch forces a replacement snapshot. An incremental read covers at most `limit` (500 without one) sequences after the cursor. With `skip_unchanged`, an `after` cursor already at the Session's end returns an `unchanged` snapshot from the Session row alone: an empty page and no Usage, Context messages or background records. Callers request background-status candidates by Tool names plus a Note content marker; the snapshot then carries only narrow `SessionBackgroundRecord(role, name, content)` rows for matching current Tool Results and Notes, limited to the appended range for an incremental read. `before` independently pages older history. Page expansion uses native Run starts (`runs.start_seq`). A page selects narrow sequence/key rows first and reads full records by key; its Run descriptions are ordered by Run start sequence. `load_run_result` and `load_run_messages_async` query exact Run membership; consumers must not infer ownership from preceding footers or Message coverage.
- `status_snapshot` reports the current view's first entry time, User count and latest Assistant Usage, plus the Session's own spend.
- `fork(source, *, target_agent_id, target_project_id, title, run_kind)` creates a new generation under a fresh id in one write; it copies no entries. The fork inherits the source's current view up to the fork point: the start of the source's earliest running non-inherited Run, else its end. Channel, Sub-Agent and reflection bindings (`SESSION_FORK_ALWAYS_STRIP_META_KEYS`) and the Run kinds stay behind; a given `title` replaces the source's (an empty one clears it) and fires title-changed callbacks after commit, and `run_kind` classifies the fork. `target_project_id=None` places the fork outside any Project. `move` retargets one live generation; its history, forks and relations stay attached. Both apply the prompt-state scope rule: within one scope (same Project and Agent) pins, seen Skills and the effective affinity id carry over; into another scope the Agent-bound pins (`AGENT_BOUND_PROMPT_PIN_SLOTS`: `pinned_skill_catalog`, `pinned_soul_context`, `pinned_memory_files`) and seen Skills stay behind and a new affinity id starts, so the destination Agent renders its own Skill catalog, SOUL and memory; the Project-qualified Working Project Context pin carries over and re-renders on its own qualifier (`tests/core/sessions/test_sessions_lifecycle.py`). Fork-point, lineage and deletion rules: `sessions/lineage.md`.
- `delete` removes one live generation and everything it owns after giving every descendant materialized copies of what it inherited (`delete_session`); it rejects owner-managed Sessions. Archive and restore are generation-aware: archiving keeps the generation's entries readable by its descendants; a new live generation may reuse an archived address; restore fails while that address already has a live generation and otherwise restores the newest archived generation.
- Operator status is the kernel's `data_store_status` (`database.md`). The Session member reports `degraded` with a `Session search: ...` reason and `fts` details when the search index is not healthy; details contain no Session content.

## Cross-Domain Rules

- `ChatSession.reflection_runs()` selects, for each live direct fork of this generation (`fork_parent_key`) in the same Project and Agent that carries a reflection Run kind, its first settled own Run by start sequence. Inherited (copied) Runs never count, so they cannot masquerade as review results.
- Chat owns `ChatMessage`, request assembly, Run execution, Compaction behavior, and Continuation record meaning. Sessions owns canonical persistence, ordering, views, metadata and prompt-state transactionality, validation, and storage lifecycle.
- Agents and Projects must share the Runtime Session manager when started by Runtime. Their standalone stores may lazily own one and must close owned resources. Agent create/current-Session repair deletes a newly created Session if later file persistence fails; rename restore retargets Sessions back; Sub-Agent parent-reference rewrites and their compensation each use one transaction and leave unrelated Session revisions unchanged; Agent and Project deletion move filesystem state first and compensate it if Session archiving fails.
- Recall and Statistics are disposable projections. Both include the Session generation in freshness state. Recall reads the current view; Statistics appends each Session's own audit through `load_since`, and ordinary appends must not rebuild a complete Session projection.
- The Skill activation cache is synchronized from the supplied current history snapshot when one is provided and otherwise preserves explicit in-memory registrations; a committed Compaction checkpoint resets the epoch from its own appended batch, since the checkpoint is then the newest entry. `apply_edit` drops the cache. A cache miss reads only current `[skill-context]` Notes and `skill` Tool Results after the newest current checkpoint (`current_skill_activation_messages`), never the full history, so edited-away checkpoints and activations cannot leak into it.
- A history edit that replaces the first current User entry clears the generated title (`auto_title`, `auto_title_initialized`) in the edit transaction; it fires no title-changed callback.
- Title-change callbacks receive the Session address; completion-read callbacks receive the address plus the acknowledged Run id. Callback failures after committed title or completion mutations are logged and isolated so callers never receive a false failure for state that already persisted.
- `titles.py` owns immediate local titles and optional background Model titles. The Model is instructed to return exactly one `[title=...]` block. After removing hidden Reasoning, the parser extracts an unambiguous title despite surrounding commentary, tolerates marker case/spacing and straight or typographic quotation wrappers, and accepts repeated blocks containing the same unwrapped title. Conflicting, incomplete, nested, empty, multiline, or overlength blocks are rejected. Without a block attempt, one unambiguous plain-text title is also accepted; it never chooses among multiple candidate lines. Invalid generated content keeps the local title and emits a content-free warning with the rejection reason and no traceback or extra Model request; unexpected failures retain their traceback. Regression coverage lives in `tests/core/sessions/test_titles.py`. `generate_group_title` reuses the same prompt, parser and request path for Extension group titles (Model choice: `extensions.md` -> Group titles).
- The title System Prompt instructs the Model to use the language of the user's main request (not quoted text/code/logs), preserve proper names and technical terms, and summarize the topic without following instructions in the supplied source material. These are Model instructions; the local validator enforces title shape and length, not language or semantic compliance.
- Title generation resolves the Adapter's `request_context_kwargs` from Project/Agent/Session once and forwards it on both attempts. This supplies required Provider routing headers without coupling Sessions to wire fields. `test_title_service_sends_opencode_session_header` covers the real OpenCode Go Responses serialization; a synthetic Muse Spark 1.3 title completed through this path on 2026-09-07.

Runtime Session readers use `ChatSessionManager`. The bundled `vbot-cli` Skill additionally documents deliberate read-only SQLite inspection for extended Session search and transcripts, scoped by Project/Agent/Session, live generation, current view and canonical sequence; these operator-style recipes do not create another runtime storage owner.

## Constraints & Gotchas

- Never add uniqueness on Message ids without changing the Compaction contract and auditing imported data; `seq` is canonical identity inside a generation, and forks and materialized copies share ids across Sessions.
- Read history only through a view: `_store_lineage.view_ranges` plus `ordered_rows` or `view_query`, or the `_store_history` helpers built on them. Filtering `entries` by `session_key` alone misses inherited entries and includes superseded ones. `test_store_query_plans.py` records the statements of every Session read over a fork and fails on a plan that scans a canonical table or builds an `AUTOMATIC` index; `test_lineage_model.py` checks every Session's current view, own audit, narrow reads, own spend and search coverage against a reference model under random appends, forks, edits and deletes.
- Delete a Session only through `_store_mutations.delete_session` (`delete`, `delete_temporary_group`). `session_lineage.ancestor_key` is `ON DELETE RESTRICT`, so a direct row delete fails while descendants inherit from it; `delete_session` materializes their copies first.
- Search membership changes need the FTS rule: forget the affected entries (`fts_forget`/`fts_forget_keys`) before the change that can end their membership, and re-index the same candidates (`fts_index_keys`) after it. See `sessions/search.md`.
- SQL names its columns: no `SELECT *`, no `alias.*` and no `INSERT` without a column list (`database.md` -> Evolution contract item 5, enforced by `tests/core/database/test_named_columns.py`).
- Store timestamps only as canonical text (`core/utils/timestamps.py`); the store compares and orders them as text.
- Never write prompt state through metadata. The facade rejects `seen_skills`, `prompt_cache_affinity_id` and `pinned_*` keys; `metadata_value(address, "seen_skills")` reads `None`, so use `seen_skills(address)`.
- Never build pagination or frozen snapshots on public Message ids alone; duplicate ids are valid. Use generation plus internal sequence and keep public-id input only where compatibility requires it.
- Never compare only public Session address plus history revision for derived freshness; archive/recreate can repeat the same revision.
- Never implement metadata as `get_metadata` followed by `set_metadata` for a partial change; concurrent fields will be lost.
- SQLite serializes database writes, not a read-modify-write split across transactions. Domain mutation callbacks must remain deterministic, side-effect free, and JSON-serializable.
- Never force WAL directly. Canonical and disposable Session-derived databases share `core.database.required_journal_mode()` so a vulnerable SQLite build cannot reintroduce the WAL-reset race.
- Stored Run membership is authoritative. Messages of a Run require that Run admitted, running and not inherited in this Session; a settled or inherited Run rejects new output and cannot be admitted again; duplicate completion is rejected.
