# Tools

Tool metadata registry, Tool Access Policy resolution, provider definitions, context-aware execution, stable result envelopes, display metadata, and async dispatch.

## Overview

`core/tools/` owns the canonical contracts, registry, declarative family/activation/constraint metadata, and Tool Access Policy resolver for callable Tools available to the agentic loop. Registration compiles immutable JSON Schemas before exposure; a Tool may additionally select a configuration-bound Definition Profile for one Agent. Dispatch uses the exact model-facing input schema from that Provider cycle to normalize a copied argument object for common unambiguous Model encodings, validates the normalized value before the handler, and validates successful result data afterward. The registry exposes provider/prompt definitions, filters Tools by the resolver's exact effective names, schedules sibling calls concurrently by default within bounded limits while preserving explicit ordering barriers, and turns expected failures into stable result envelopes. Chat may apply an additional route-specific visibility filter after registry definitions are built; this currently gates `analyze_image` from the effective Model route's image capability and `ImageService`'s live binding-plus-Adapter-wire availability, without changing Tool registration or permissions. Concrete built-in Tool behavior lives in child maps under `.vorch/domain-maps/tools/`.

## Terms

Domain-specific vocabulary for tools. The core Tool term lives in `.vorch/GLOSSARY.md`.

### Readiness
**Definition:** A per-tool, cheap, I/O-free predicate (`Tool.ready`, a zero-arg `Callable[[], bool] | None`) evaluated at every prompt/tool-definition build; filter order is registered → policy-allowed → ready. A not-ready Tool vanishes from the System Prompt and provider Tool definitions but remains visible with its explanation in configuration surfaces so persisted policy survives; a direct dispatch returns a clean `tool_not_ready` envelope instead of running the handler. A predicate that raises counts as not-ready.
**Not:** A permission — Tool Access Policy answers "may this Agent use it", readiness answers "can it run right now" (e.g. is the Extension's token set). Not a stored Extension state either: the Extensions tab's waiting status is a derived `ready_state`, not a third switch.

### Session Grant
**Definition:** A capability Chat derives while building one Session's request state and carries through provider definitions and dispatch. `history` appears only after persisted Compaction state makes it meaningful.
**Not:** A Run-local input, Agent or Project configuration, a catalog choice, or permission to address another Session.

### Definition Profile
**Definition:** A model-facing Tool description and input schema selected from stable persisted configuration for an Agent. Its key identifies one immutable profile; unchanged configuration must reproduce byte-identical Provider definitions, while transient Run, Session, Adapter-liveness, and execution state must never select a different profile.
**Not:** The canonical Tool contract, a per-Run schema, readiness, or an execution-time fallback.

## Data Model

- `Tool`: `name`, `description`, canonical input `parameters`, `handler`, optional success-data `result_schema`, compiled `contract`, `parallel_safe` (default `True`), `internal`, `session_scoped`, optional presentation `family` plus `family_label`, declarative `activation` (`configurable`, `follows`, `memory_mode`, or `session_grant`), optional `activation_source`, `constraints`, `display`, `ready` (an optional zero-arg readiness predicate, `Callable[[], bool] | None`; `None` = always ready), `readiness_hint` (`str | None`, default `None` — English text explaining the readiness precondition, surfaced by `tool.list`; server-delivered content like the description, never frontend i18n), `extension` (`str | None`, default `None` — the name of the owning Extension, set at Extension-Tool apply time; `None` for a built-in), and optional `definition_profile_resolver`. `ToolContract` owns deep-copied Draft 2020-12 validators, schema-guided argument normalization, and the deterministic SHA-256 fingerprint of the Tool name, input schema, result schema, and concurrency policy. `ToolRegistry` owns `ToolFamily` definitions and copies their label onto registered members. Families are optional comprehension/bulk-action metadata and never imply activation; an ungrouped Tool remains fully configurable. A Session-granted Tool is hidden from Model-facing surfaces unless its current Session grant survives policy.
- `ToolDisplay`: presentation-only per-invocation metadata. Built-ins explicitly choose ordered argument candidates, computed semantic parts, or no summary; each primary part declares its kind (`path`, `description`, `query`, `command`, `url`, `identifier`, or text), truncation direction, tooltip/full-value policy, optional quoting/copyability, and the shared 64-character budget. Facts are typed UI data rather than formatted strings: result counts (`matches` or `results`), requested line ranges, and added/removed line counts. Argument-derived fact builders may run before a Result exists; Result-derived builders must return no fact until a successful Result supplies their source. The resulting versioned payload is `{version, summary, hidden_argument_keys, primary, facts}` and never enters Provider definitions or Tool result envelopes.
- `ToolContext`: `agent_id`, `session_id`, `run_id`, `tool_call_id`, `tool_name`, `tool_call_index`, `iteration_number`, `workspace`, `cwd`, `project_id`, `vbot_root`, `data_root`, `nesting_depth`, `allowed_skills`, Chat-derived `session_tool_grants`, the optional exact Provider-cycle `input_contract`, presentation-only `presentation_facts`, plus emit/cancel/note/skill hooks, per-call cancel hooks (`cancel_registration_hook`, `cancel_check_hook`), and the optional post-persistence hook used by `after_result_persisted(callback)`. `add_display_count()` and `add_display_line_changes()` record validated UI facts without changing the Tool's Agent-visible result.
  - `cwd` (`Path | None`) is the working directory relative file/shell Tools use: the selected working Project repository for a Rooted Identity Agent or Project Config Agent, otherwise Workspace. `ToolContext.effective_cwd` falls back to Workspace; Memory deliberately ignores cwd.
  - `project_id` (`str | None`) remains Session/address ownership, not working context. It stays `None` for a Rooted Identity Agent so bare Subagent targets remain Identity targets; `skill_project_id` separately carries the Project whose registry currently serves Skill activation — normally the working Project, or the latest Project Context loaded explicitly in an Identity Session.
  - `iteration_number` is the completed Agentic Loop Iteration whose Assistant response requested the Tool Call (`0` only for direct callers outside Chat). Provider-backed Tools use it for trace correlation; executing the Tool does not increment the Run's Iteration count.
- Result envelope: `{ ok, error, data, artifacts }`. Success uses `error: null`; failure uses `data: null` and `error.code`/`error.message`. The top-level key set is exactly `{ok, error, data, artifacts}` — `is_tool_result_envelope()` checks it exactly, so retry-signalling fields go *inside* `error`, never as new top-level keys.
- Failure retry signal (optional, inside `error`): `tool_failure(code, message, *, retryable=None, attempts_made=None)` may add `error.retryable: bool` and `error.attempts_made: int` (non-negative). They tell the model whether the failure is transient and how many attempts the tool already made, so it does not pointlessly re-invoke a tool that already exhausted its own retries. Convention: a tool that gives up after exhausting its own retries on a retryable status / transport error sets `retryable=True` with the real `attempts_made`; validation/fatal failures set `retryable=False`. Both keys are optional — when omitted (e.g. non-network tools) the model gets no signal. `is_tool_result_envelope()` accepts only these two optional error keys. `retry_async()` records its current loop's one-based attempt count on every rethrown `VBotError`; `analyze_image` preserves that count and retryability through its typed Image error. The network tools (`web_fetch`, `web_search`, and the bundled Home Assistant extension's tools — see `.vorch/domain-maps/extensions/homeassistant.md`) populate the same envelope fields via the shared retry policy in `core/utils/http_status.py` (`is_retryable_status`, `HttpRequestFailure`, `parse_retry_after` — the `Retry-After` header parser shared with the provider adapters); backoff delay math (exponential + jitter, `Retry-After` honored as a capped floor) is shared via `core/utils/retry.compute_retry_delay`.
- Rich-media result artifact: `read_media_artifact(attachment_id, filename, media_type)` (in `core/tools/tools.py`) builds the one cross-Tool artifact `{ kind: "read_media", attachment_id, filename, media_type }`. `read` (local image files) and `web_fetch` (image URLs) emit it so Chat can resolve the Attachment as Run-local content on the correlated Tool Result. The persisted Result keeps only this compact reference; base64 stays request-local, and no synthetic user message is written. Consumed by `core/chat/tool_dispatch.py` via `READ_MEDIA_ARTIFACT_KIND`; a new Tool returning an image should reuse the builder rather than hand-roll the shape.
- Tool timing is not part of the result envelope. Completed tool calls expose a sibling `timing` object on `tool_call_result` Run events and on persisted `role: "tool"` ChatMessages: `{ started_at, completed_at, duration_ms }`. Durations are non-negative milliseconds measured with a monotonic clock.
- `ToolCall`: one requested tool invocation with stable id, name, and arguments; execution index is assigned when scheduling a sibling batch.

## Interfaces

`run_tool_worker(function, *arguments, **keyword_arguments)` uses the dedicated eight-worker Tool pool, applies admission backpressure before executor submission, and waits for an already-started mutation to settle before propagating cancellation. Built-ins opt in at their blocking boundary: `edit`, `history`, `project`, `glob`, `grep`, `memory`, `session_search`, and `write` use the pool wholly or around their filesystem/parser core; `skill`, `read`, `channel_send`, and `web_fetch` split blocking work from loop-owned Runtime mutation or async Provider/network work. Ordinary synchronous built-in handlers keep the historical Event-Loop dispatch contract because some intentionally call loop-owned APIs; synchronous Extension Tool handlers are identified by their owning `Tool.extension` and automatically use the Tool pool.

- `ToolRegistry.register_family(family_id, label, *, extension=None) -> ToolFamily` owns family metadata; the constructor pre-registers the six Built-in families. `register(...)` accepts only a registered family id and copies its label into the immutable Tool. `unregister_family(...)` removes only matching Extension-owned metadata after no live member remains, protecting Built-in families during reload and live disable.
- `ToolRegistry.register(name, description, parameters, handler, *, internal=False, session_scoped=False, family=None, activation="configurable", activation_source=None, constraints=(), display=None, ready=None, readiness_hint=None, extension=None, result_schema=None, parallel_safe=True, open_input_schema=False, definition_profile_resolver=None) -> Tool` (all optional arguments keyword-only; callable fields are validated). Registration compiles the canonical contract and rejects invalid schemas, unknown families, or incoherent activation metadata before publishing the Tool. Names match `^[A-Za-z][A-Za-z0-9_]{0,63}$`; fixed-shape objects are closed by default, while migrated model-facing schemas opt into `open_input_schema=True` and leave unknown-field rejection to the handler; schema references must resolve locally. A profile resolver receives only `ToolDefinitionProfileContext(agent_id)` and returns a keyed immutable description/schema profile or `None` to hide the Tool for that Agent; the registry compiles and caches profiles by Tool name plus profile key. Family, family label, activation, constraints, `readiness_hint`, and `extension` are metadata surfaced by `tool.list`; Extension-Tool registration passes `extension=<record.name>` and every declared contract field through `_apply_one_tool`.
- `ToolRegistry.get(name) -> Tool`
- `ToolRegistry.display_for_call(name, arguments, *, context=None, result=None) -> dict` resolves the versioned UI payload for one invocation. Passing the call's `ToolContext` resolves full file paths and carries handler-recorded facts; passing the terminal Result enables result-derived facts. Unknown or Extension Tools without an explicit profile safely return an empty primary/fact projection rather than exposing arbitrary arguments.
- `result_count_fact_builder(data_field, *, when_arguments=None, at_least_field=None, unit="results")` declaratively derives a presentation-only count from either a successful Result array or non-negative integer. It emits nothing for failures, missing/invalid fields, or non-matching argument conditions; a true `at_least_field` marks paginated counts as a lower bound. Use this for existing structured Result data, while handlers such as `glob`/`grep` use `ToolContext.add_display_count()` when the count must stay outside the Agent-visible envelope.
- `ToolRegistry.unregister(name) -> None`
- `ToolRegistry.list_tools(allowed_tools=None, *, include_internal=False, include_session_scoped=True, ready_only=False) -> list[Tool]` — filter order **registered → allowed → ready**. Callers choose whether automatic Session-granted Tools belong on their surface; `tool.list` includes them so the policy editor can explain them, while Model-facing definitions still require a surviving grant. `ready_only` applies the readiness filter *after* the other filters and defaults **off**.
- `ToolRegistry.provider_definitions(..., *, session_grants=(), ready_only=True, profile_context=None) -> list[dict]` returns provider-visible `name`, `description`, and JSON Schema only. With a profile context it resolves the Agent's stable Definition Profile and omits a Tool whose resolver returns `None`; without one it returns the canonical definition for compatibility. Ungranted Session-scoped Tools are hidden; a matching grant overrides the ordinary Agent allowlist. `ready_only` defaults **on** (model-facing surface).
- `ToolRegistry.prompt_definitions(..., *, session_grants=(), ready_only=True, profile_context=None) -> list[dict]` applies the same profile, grant, allowlist, and readiness contract and returns prompt-visible name/description pairs.
- `ToolRegistry.contracts_for_provider_definitions(definitions) -> dict[str, ToolContract]` compiles the exact final Provider-cycle input schemas after every profile and Chat route projection. Chat stores this mapping in request state and passes it through `ToolExecutionConfig` to each `ToolContext`.
- `ToolRegistry.dispatch(context, arguments, allowed_tools=None) -> dict` authorizes and readiness-checks a Tool, normalizes a deep copy of the arguments with `context.input_contract` when supplied or the canonical input schema otherwise, validates that normalized value, executes the handler with it, validates the fixed result envelope, validates successful `data` against the canonical `result_schema` when declared, and verifies that the complete result is finite JSON-serializable. Normalization accepts numeric strings for integer/number fields, case-insensitive `true`/`false`, the string `null` for nullable fields, JSON-encoded arrays/objects, and a single non-null value for an array; it recurses through container items/properties and matching unions while preserving a string already accepted by the schema. Missing fields, unknown fields on closed Tools, invalid ranges, ambiguous values, and other remaining violations still raise `ToolContractError` before handler side effects; `open_input_schema=True` Tools deliberately delegate unknown-field rejection to their handler. An invalid or non-serializable result raises `InvalidToolResultError`. It rejects an ungranted Session-scoped Tool with `<tool>_unavailable` before the ordinary allowlist check; a matching grant overrides that allowlist. **Dispatch is not list-filtered by readiness**, but it re-evaluates readiness live and, when not ready, returns a `tool_not_ready` failure envelope (`retryable=False`) without running the handler — the safety net for a prompt built moments before the credential vanished.
- `run_tool_worker(function, *arguments)` is the blocking-work boundary for Tool implementations: it uses a worker thread, shields the worker from task cancellation, and waits for an already-started mutation to settle before propagating cancellation. `offload_tool_handler(handler)` adapts a wholly synchronous handler to that boundary. Use selective offloading rather than moving all sync handlers automatically: `edit`, `history`, and `project` are wholly offloaded; `skill`, `read`, and `web_fetch` split blocking filesystem/parsing work from loop-owned Runtime mutation or async Provider/network work.
- `ToolRegistry.schema_fingerprint(name) -> str` returns the canonical contract fingerprint; `validate_result(name, result) -> dict` is the shared envelope and success-data validation seam used by normal dispatch and Extension replacements.
- `compile_tool_contract(name, input_schema, success_data_schema=None, *, require_closed_input=True) -> ToolContract` compiles the canonical Runtime validator. Registered migrated Tools set `open_input_schema=True`, so their model-facing object omits `additionalProperties` while the handler owns unknown-field and conditional validation; closed input remains available only for backward-compatible external Extension contracts.
- `tool_is_ready(tool) -> bool` (module-level) — the readiness predicate contract: `ready is None` → ready; a predicate that raises is logged once at `warning` and counts as **not ready** (a broken predicate never takes a build down or makes a tool spuriously available). Cheap, I/O-free (a string-nonempty check, never a network ping) — it runs on every prompt/tool-definition build.
- `ToolContext.add_display_count(...)` and `add_display_line_changes(added=..., removed=...)` record validated presentation-only facts without changing the Agent-visible Result. `ToolContext.on_cancel(callback)` registers a per-tool-call cancel callback (no-op when no registration hook is wired); `ToolContext.was_cancelled_by_user() -> bool` reports whether the current call was user-cancelled (False when no check hook is wired). These hooks are wired by the chat dispatcher through `ToolExecutionConfig` so a Tool can plug into `Run.register_tool_cancel` / `Run.tool_call_cancelled` without importing the Run domain. A targeted per-call cancel invokes only that callback and leaves the Run alive; a full `Run.request_cancel` cascades every still-active callback in registration order before forcefully cancelling the executor, and late registration after the Run signal fires immediately.
- `ToolContext.change_tracker` (wired through `ToolExecutionConfig.change_tracker`) is the session-scoped file-content tracker for git-style change statistics. `write`/`edit` record before/after content per `(session, path)`, diffing every mutation against the file's actual on-disk content immediately before the mutation; the chat loop streams live totals after each dispatched Tool round via `ChangeTracker.peek_run_stats(session_id)` (non-consuming) as the transient `run_change_stats` event and consumes the run's deltas at run end via `ChangeTracker.take_run_stats(session_id)`, persisting them on the run summary (`change_stats`) and terminal payload. Best-effort: untracked files (non-UTF-8, oversized, bash-driven) simply fall back to the client-side per-tool-call counts. See `tools/change_tracker.md`.
- `ToolContext.after_result_persisted(callback)` registers a per-call delivery callback. The dispatcher keys it by `tool_call_id`, and Chat invokes it only after the corresponding ordered Tool Result append returns; absence of the hook is a no-op so Tools remain reusable outside Chat execution.
- Result-envelope validation failures raise `InvalidToolResultError` (a `ValueError` subclass), distinct from plain `ValueError` argument failures. The chat loop maps the former to an `invalid_tool_result` failure envelope and the latter to `invalid_arguments`, without inspecting error message text.
- `ToolExecutor.execute_many(tool_calls, config) -> list[dict]` executes sibling calls concurrently by default within the bounded Run/global limits and preserves original result order. Recovery metadata never changes scheduling: native, recovered, rejected, and unknown sibling calls enter the same parallel-by-default path. Only a registered Tool with `parallel_safe=False` is an explicit ordering barrier before and after itself; an unknown Tool cannot invoke a handler and therefore does not create a barrier. Chat serializes Extension `tool_call` and `tool_result` hook callbacks through a batch-local lock so hook transformations stay deterministic without serializing parallel-safe Tool handlers. Chat may also supply a live per-name denial resolver; it runs before Extension hooks and the Tool handler for every sibling, and a denial returns `tool_not_allowed` without side effects.
- `core.tools.availability.normalize_tool_access(...)` validates the strict persisted policy, and `resolve_tool_access(...)` is the single policy resolver consumed by prompt/provider definitions and dispatch. It selects configurable Tools by mode, applies identity/route constraints and automatic activation (`session_read` follows `session_search`, Memory mode activates `memory`, current Session Grants activate their Tools), then applies `denied` as an absolute veto and removes orphaned followers. Mode `none` suppresses every activation path.
- Extensions register their own Tools through `api.register_tool(..., family=None)` and may first declare presentation groups through `api.register_tool_family(family_id, label)` (`.vorch/domain-maps/extensions.md`). The Extension registry namespaces local family ids by Extension identity before routing both declarations into `ToolRegistry` during Runtime bootstrap — applied after the last built-in Tool, right before `SystemPromptManager` consumes the registry. Extension Tools are **normal Tools** afterward: same compiled contracts, provider/prompt definitions, allowlist filtering, and dispatch. A name colliding with a built-in or another Extension's Tool is skipped (the existing Tool wins) and diagnosed on the Extension record; an invalid Tool declaration is likewise isolated and diagnosed without preventing other capabilities from applying. An invalid or missing family declaration only drops grouping from the affected Tool.
- `ToolPromptBlockRegistry` is the **tool-side System Prompt block-declaration seam**: a tool that wants prompt content declares a block here (`register(tool_name, *, default_text=None, render=None)`, exactly one of text/render, first-wins-with-warning on a duplicate tool name), and the runtime gathers `block_definitions()` and merges them with the extension blocks before handing the list to the prompt manager. A declared block is id `tool:<name>` and owner `tool:<name>`, so gate 2 renders it only when `<name>` is on the agent's effective allowlist; static or dynamic, the same split as a core or extension block. **The prompt domain imports no tool classes** — it only ever consumes a list of `core.prompts.BlockDefinition` (the `core.prompts` import in `block_definitions()` is lazy so the tools domain has no import-time dependency on prompts either). The built-in `project` and `subagent` Tools use dynamic blocks for their current catalogs and guidance. See `tools/project.md`, `.vorch/domain-maps/prompts.md` (block model), `.vorch/domain-maps/subagents.md` (Sub-Agent catalog semantics), and `.vorch/domain-maps/extensions.md` (the parallel extension-block path).
- `core.tools.arguments` is the shared strict semantic-parsing home for `optional_string`/`required_string`, `optional_int`/`required_int`, and `optional_number`. These helpers do not coerce numeric strings, integral floats, boolean spellings, aliases, or blank values around the canonical contract. They raise `ToolArgumentError` (a `ValueError`) for semantic handler checks. The module also hosts `logical_line_count` for Edit/Write display parity plus `looks_like_line_numbered_content` and the shared `LINE_NUMBER_GUTTER_SEPARATOR`: a content-shape guard that `write`/`edit` use to reject text echoing `read`'s `N|` line-number gutter back into a file (see `tools/read.md`).

## Conventions

- When vBot authors a filesystem path for Model consumption in Tool output, it renders only the separator syntax with forward slashes (`C:/...`, `//server/share/...`). Resolution, persistence, input handling, and OS calls retain native `Path` semantics; never normalize arbitrary Tool text globally.

- **Repair representation mistakes before rejecting a Tool Call.** `ToolRegistry.dispatch()` normalizes only schema-guided, unambiguous representation mistakes on a deep copy, then applies the normal input validator and handler semantic checks. It never renames fields, treats whitespace-only values as omitted, accepts Boolean aliases such as `yes`/`1`, or mutates the original Assistant Tool Call. An exact empty string in an optional object property is omitted before validation; required properties and array items remain present and are still validated. Missing requirements, invalid unions/ranges, and unknown properties on closed contracts still fail before handler side effects; migrated model-facing Tools use open schemas and must reject unknown and inapplicable fields in the handler. Handlers retain semantic validation for authorization, existence, state transitions, and constraints the schema cannot decide.
- **Definition Profiles are configuration-bound, never request-bound.** Use one only when stable configured capabilities change which arguments are meaningful. Derive it from persisted Agent/Channel/Model configuration, sort set-like inputs, use a deterministic profile key, and keep transient Adapter liveness, Provider request, Session, Run, and tool-call data out of both key and schema. A real configuration change may legitimately change the Provider prefix once; an unchanged configuration must keep the same bytes. The exact post-projection contract shown to the Model remains the dispatch validator for that cycle, while the handler and downstream service retain semantic and liveness checks.
- **Agent-facing definitions follow the repository-root `TOOLS.md` rules and migrate one verified Tool at a time.** `process`, `memory`, `subagent`, `cron`, `skill_manage`, and `history` are migrated Action Tools: one flat object advertises required `action` plus the shared optional-property superset, parameter descriptions state action-dependent requirements and omission behavior, and the handler remains the authority for rejecting inapplicable or missing fields; `memory.scope` and `skill_manage.name` are additionally required because every action needs them. `web_fetch`, `web_search`, `skill`, `write`, `read`, `glob`, `grep`, `edit`, `text_to_speech`, `project`, `analyze_image`, `image_generation`, `generate_video`, `generate_music`, `status`, `session_read`, `session_search`, `channel_send`, and `bash` are migrated Tools whose model-facing schemas omit `additionalProperties`; the four bundled Home Assistant Extension Tools and the `word_count` Extension example follow the same contract through `open_input_schema=True`. Omitted defaults remain handler-owned and are stated in parameter descriptions where needed. `web_search.page`, `session_search.limit`, and Bash's profile-dependent `background_after_seconds` retain stable numeric schema defaults; configurable defaults stay handler-only. `grep`, `status`, `session_read`, and `session_search` replace duplicated mode/target branches with one flat property set and handler validation; `skill` uses omission of both optional fields for its catalog mode; `channel_send` replaces platform branches with one configuration-derived flat profile and handler enforcement; `bash` replaces mode branches with one flat property set and a depth-projected mode enum. Do not add nested `request.operation`, operation-key objects, redundant single-value actions, or action inference from unrelated optional-field combinations. Historical persisted calls may retain retired shapes for presentation only. See `tools/designing-agent-tools.md`.
- **Readiness is a separate axis from Tool Access Policy and Session Grants.** A not-ready Tool stays *registered* (persisted permissions survive) but is filtered out of the **model-facing** surfaces and returns a `tool_not_ready` envelope on a direct dispatch. Two surfaces apply the readiness filter: `provider_definitions` and `prompt_definitions` (both default `ready_only=True`, so the prompt Tool list, the provider Tool definitions, and — through the prompt definitions — gate 2 of a `tool:<name>`-owned prompt block all drop a not-ready Tool). The `tool.list` RPC intentionally includes automatic and Session-granted public Tools and returns each Tool's `family`, `family_label`, `activation`, `activation_source`, `constraints`, `ready`, `readiness_hint`, `extension`, and Projects-owned configurability projection, so policy editors keep every state visible and explain why it is automatic or currently unavailable. Consumers that keep seeing not-ready Tools with no styling deliberately leave `ready_only` off: Extension collision detection, dispatch policy computation, and the Runtime startup inventory count. A `tool:<name>`-owned prompt block still drops when its Tool is not ready, because gate 2 reads the readiness-filtered prompt definitions.
- At the generic ToolRegistry boundary, `allowed_tools=None` and `["*"]` mean all registered normal tools, while `allowed_tools=[]` means no normal tools. The Project Tool Whitelist is intentionally stricter: it is an explicit security ceiling and rejects `"*"` in raw `project.json`, entity construction, and `project.set`.
- Tool families are optional registry metadata for comprehension and current-member bulk actions only. Built-ins use `files`, `execution`, `web`, `sessions`, `skills`, and `media`; Extensions may declare their own namespaced families and labels. A family with fewer than two members in the current catalog/ceiling is presented under Individual Tools rather than receiving a fake family card; filtering the UI does not dissolve an otherwise real family. Membership never changes activation semantics.
- Agent Tool permission is the explicit `tool_access` policy; automatic Tools are declared in registry metadata rather than persisted as independently enabled names. A denial remains valid for an automatic Tool and wins after its activation source.
- For a **config (project) Agent**, the Project Tool Whitelist (`project.allowed_tools`) is the outer ceiling. Without `overrides.<agent_id>.tool_access`, scanned repository denials narrow that ceiling; a present vBot policy override fully replaces the scanned Tool policy and may re-enable a repo-denied Tool, but `selected.allowed` must remain inside the ceiling and `all` means the complete ceiling. `project.set` permits only registered Project-configurable Tools; a previously persisted unavailable name may only be retained or removed. The scan preview reports unavailable entries without dropping them, so a temporarily disabled Extension keeps its permission (see `projects/resolution.md` → Effective Capabilities).
- Internal tools bypass normal `allowed_tools` filtering and must enforce their own domain rules.
- Provider-visible definitions must not expose handlers, runtime context, internal flags, or display metadata.
- Display labels are not tool parameters. Do not add generic arguments such as `description` only to affect UI chrome; use `ToolDisplay`.
- Every built-in Tool registration must pass an explicit `ToolDisplay`, including `ToolDisplay()` for an intentional no-summary row. The frontend renders semantic parts generically; normal Built-in growth belongs in the Tool-owned profile, not a new Tool-name branch in Svelte. `bash`, `grep`, and `web_search` already prefer a future nonblank `description` candidate without adding that field to their current Agent-facing schemas.
- Tool Call failures are per-call data, not Run failures: unknown/disallowed Tools, invalid arguments, handler exceptions, and invalid/non-serializable results must become correlated failure envelopes. Run cancellation and failures in Provider, process, or persistence infrastructure remain outside this Tool boundary.
- Same-turn sibling Tool Calls execute concurrently by default within the shared limits, including multiple calls to the same Tool. A Tool with `parallel_safe=False` is an explicit barrier. Active Tool hooks serialize only the hook callbacks; parallel-safe Tool handlers may still overlap.
- Tool timing metadata must never be forwarded to provider adapters; provider tool messages contain only the tool role, call correlation, name, and content.

## Constraints & Gotchas

- Tool results must be finite JSON-serializable objects matching the stable envelope; non-envelope results, non-serializable values, non-finite numbers, and successful data that violate the declared result schema are rejected as `invalid_tool_result` without aborting the Run.
- Disallowed normal tools fail at dispatch even if a provider asks for them.
- An ungranted Session-scoped Tool fails with its stable `<tool>_unavailable` code. Chat alone derives grants during request building: persisted Compaction state adds `history` at the permitted prompt-epoch break. A static Run restriction and live per-call denial remain dispatch-only intersections and can return `tool_not_allowed` even while the Provider was correctly told the Tool exists. Restrictions and denials must never filter Provider Tool definitions or mutate System Prompt assembly.
- Result persistence must preserve the Assistant's original Tool Call order even when a parallel-safe group finishes out of order.
- Relative filesystem paths resolve from `ToolContext.effective_cwd` (the project repo for a project Session, else `workspace`); absolute paths bypass it unless a specific tool forbids them. The file tools (`read`/`write`/`edit`/`grep`/`glob`/`search`) and `bash` resolve against `effective_cwd`; `memory` deliberately stays on `workspace` (it is the identity/memory home, not project-relative).
