# Tools

Tool metadata registry, allowlist filtering, provider definitions, context-aware execution, stable result envelopes, display metadata, and async dispatch.

## Overview

`core/tools/` owns the canonical contracts and registry of callable Tools available to the agentic loop. Registration compiles immutable JSON Schemas before exposure; a Tool may additionally select a configuration-bound Definition Profile for one Agent, and dispatch validates the exact model-facing contract from that Provider cycle before the handler plus successful result data afterward. The registry exposes provider/prompt definitions, filters Tools by Agent allowlists, schedules sibling calls concurrently by default within bounded limits while preserving explicit ordering barriers, and turns expected failures into stable result envelopes. Chat may apply an additional route-specific visibility filter after registry definitions are built; this currently gates `analyze_image` from the effective Model modalities, Adapter wire support, and live task-model binding usability, without changing Tool registration or permissions. Concrete built-in Tool behavior lives in child maps under `.vorch/domain-maps/tools/`.

## Terms

Domain-specific vocabulary for tools. The core Tool term lives in `.vorch/GLOSSARY.md`.

### Readiness
**Definition:** A per-tool, cheap, I/O-free predicate (`Tool.ready`, a zero-arg `Callable[[], bool] | None`) evaluated at every prompt/tool-definition build; filter order is registered → allowed → ready. A not-ready tool vanishes from the System Prompt, the provider tool definitions, and the pickers but stays registered (its persisted permissions survive); a direct dispatch returns a clean `tool_not_ready` envelope instead of running the handler. A predicate that raises counts as not-ready.
**Not:** A permission — an allowlist answers "may this agent use it", readiness answers "can it run right now" (e.g. is the extension's token set). Not a stored extension state either: the Extensions tab's waiting status is a derived `ready_state`, not a third switch.

### Session Grant
**Definition:** An ephemeral capability derived from persisted Session state or explicitly supplied to one admitted Run, then carried through request building and dispatch. A grant makes its matching Session-scoped Tool model-visible and may override the ordinary Agent allowlist; Run-supplied grants survive fallback and automatic Compaction within that Run but are never persisted.
**Not:** Agent or Project configuration, a catalog choice, or permission to address another Session.

### Definition Profile
**Definition:** A model-facing Tool description and input schema selected from stable persisted configuration for an Agent. Its key identifies one immutable profile; unchanged configuration must reproduce byte-identical Provider definitions, while transient Run, Session, Adapter-liveness, and execution state must never select a different profile.
**Not:** The canonical Tool contract, a per-Run schema, readiness, or an execution-time fallback.

## Data Model

- `Tool`: `name`, `description`, canonical input `parameters`, `handler`, optional success-data `result_schema`, compiled `contract`, `parallel_safe` (default `True`), `internal`, `session_scoped`, `display`, `ready` (an optional zero-arg readiness predicate, `Callable[[], bool] | None`; `None` = always ready), `readiness_hint` (`str | None`, default `None` — English text explaining the readiness precondition, surfaced by `tool.list`; server-delivered content like the description, never frontend i18n), `extension` (`str | None`, default `None` — the name of the owning Extension, set at Extension-Tool apply time; `None` for a built-in), and optional `definition_profile_resolver`. `ToolContract` owns deep-copied Draft 2020-12 validators plus the deterministic SHA-256 fingerprint of the Tool name, input schema, result schema, and concurrency policy. A Session-scoped Tool is hidden unless its name is present in the current Session grants.
- `ToolDisplay`: per-invocation presentation metadata. It builds `{ summary, hidden_argument_keys }` for `tool_call_started` events without adding provider-visible parameters.
- `ToolContext`: `agent_id`, `session_id`, `run_id`, `tool_call_id`, `tool_name`, `tool_call_index`, `workspace`, `cwd`, `project_id`, `vbot_root`, `data_root`, `nesting_depth`, `allowed_skills`, `session_tool_grants` (the merged persisted-state and Run-local grants), the optional exact Provider-cycle `input_contract`, plus emit/cancel/note/skill hooks, per-call cancel hooks (`cancel_registration_hook`, `cancel_check_hook`), and the optional post-persistence hook used by `after_result_persisted(callback)`.
  - `cwd` (`Path | None`) is the working directory relative file/shell Tools use: the selected working Project repository for a Rooted Identity Agent or Project Config Agent, otherwise Workspace. `ToolContext.effective_cwd` falls back to Workspace; Memory deliberately ignores cwd.
  - `project_id` (`str | None`) remains Session/address ownership, not working context. It stays `None` for a Rooted Identity Agent so bare Subagent targets remain Identity targets; `skill_project_id` separately carries the Project whose registry currently serves Skill activation — normally the working Project, or the latest Project Context loaded explicitly in an Identity Session.
- Result envelope: `{ ok, error, data, artifacts }`. Success uses `error: null`; failure uses `data: null` and `error.code`/`error.message`. The top-level key set is exactly `{ok, error, data, artifacts}` — `is_tool_result_envelope()` checks it exactly, so retry-signalling fields go *inside* `error`, never as new top-level keys.
- Failure retry signal (optional, inside `error`): `tool_failure(code, message, *, retryable=None, attempts_made=None)` may add `error.retryable: bool` and `error.attempts_made: int` (non-negative). They tell the model whether the failure is transient and how many attempts the tool already made, so it does not pointlessly re-invoke a tool that already exhausted its own retries. Convention: a tool that gives up after exhausting its own retries on a retryable status / transport error sets `retryable=True` with the real `attempts_made`; validation/fatal failures set `retryable=False`. Both keys are optional — when omitted (e.g. non-network tools) the model gets no signal. `is_tool_result_envelope()` accepts only these two optional error keys. The network tools (`web_fetch`, `web_search`, and the bundled Home Assistant extension's tools — see `.vorch/domain-maps/extensions/homeassistant.md`) populate them via the shared retry policy in `core/utils/http_status.py` (`is_retryable_status`, `HttpRequestFailure`, `parse_retry_after` — the `Retry-After` header parser shared with the provider adapters); backoff delay math (exponential + jitter, `Retry-After` honored as a capped floor) is shared via `core/utils/retry.compute_retry_delay`.
- Rich-media result artifact: `read_media_artifact(attachment_id, filename, media_type)` (in `core/tools/tools.py`) builds the one cross-Tool artifact `{ kind: "read_media", attachment_id, filename, media_type }`. `read` (local image files) and `web_fetch` (image URLs) emit it so Chat can resolve the Attachment as Run-local content on the correlated Tool Result. The persisted Result keeps only this compact reference; base64 stays request-local, and no synthetic user message is written. Consumed by `core/chat/tool_dispatch.py` via `READ_MEDIA_ARTIFACT_KIND`; a new Tool returning an image should reuse the builder rather than hand-roll the shape.
- Tool timing is not part of the result envelope. Completed tool calls expose a sibling `timing` object on `tool_call_result` Run events and on persisted `role: "tool"` ChatMessages: `{ started_at, completed_at, duration_ms }`. Durations are non-negative milliseconds measured with a monotonic clock.
- `ToolCall`: one requested tool invocation with stable id, name, and arguments; execution index is assigned when scheduling a sibling batch.

## Interfaces

- `ToolRegistry.register(name, description, parameters, handler, *, internal=False, session_scoped=False, display=None, ready=None, readiness_hint=None, extension=None, result_schema=None, parallel_safe=True, open_input_schema=False, definition_profile_resolver=None) -> Tool` (all optional arguments keyword-only; callable fields are validated). Registration compiles the canonical contract and rejects invalid schemas before publishing the Tool. Names match `^[A-Za-z][A-Za-z0-9_]{0,63}$`; fixed-shape objects are closed by default, while migrated model-facing schemas opt into `open_input_schema=True` and leave unknown-field rejection to the handler; schema references must resolve locally. A profile resolver receives only `ToolDefinitionProfileContext(agent_id)` and returns a keyed immutable description/schema profile or `None` to hide the Tool for that Agent; the registry compiles and caches profiles by Tool name plus profile key. `readiness_hint`/`extension` are metadata surfaced by `tool.list`; Extension-Tool registration passes `extension=<record.name>` and every declared contract field through `_apply_one_tool`.
- `ToolRegistry.get(name) -> Tool`
- `ToolRegistry.display_for_call(name, arguments) -> dict` returns `{ summary, hidden_argument_keys }` for one invocation.
- `ToolRegistry.unregister(name) -> None`
- `ToolRegistry.list_tools(allowed_tools=None, *, include_internal=False, include_session_scoped=True, ready_only=False) -> list[Tool]` — filter order **registered → allowed → ready**; catalogs pass `include_session_scoped=False`, while runtime consumers can retain them for grant evaluation. `ready_only` applies the readiness filter *after* the other filters and defaults **off**.
- `ToolRegistry.provider_definitions(..., *, session_grants=(), ready_only=True, profile_context=None) -> list[dict]` returns provider-visible `name`, `description`, and JSON Schema only. With a profile context it resolves the Agent's stable Definition Profile and omits a Tool whose resolver returns `None`; without one it returns the canonical definition for compatibility. Ungranted Session-scoped Tools are hidden; a matching grant overrides the ordinary Agent allowlist. `ready_only` defaults **on** (model-facing surface).
- `ToolRegistry.prompt_definitions(..., *, session_grants=(), ready_only=True, profile_context=None) -> list[dict]` applies the same profile, grant, allowlist, and readiness contract and returns prompt-visible name/description pairs.
- `ToolRegistry.contracts_for_provider_definitions(definitions) -> dict[str, ToolContract]` compiles the exact final Provider-cycle input schemas after every profile and Chat route projection. Chat stores this mapping in request state and passes it through `ToolExecutionConfig` to each `ToolContext`.
- `ToolRegistry.dispatch(context, arguments, allowed_tools=None) -> dict` authorizes and readiness-checks a Tool, validates arguments against `context.input_contract` when supplied or the canonical input schema otherwise, executes the handler, validates the fixed result envelope, and validates successful `data` against the canonical `result_schema` when declared. Schema types, required fields, arrays, and other declared constraints fail with `ToolContractError` before handler side effects; unknown fields do likewise for closed Tools, while `open_input_schema=True` Tools deliberately delegate them to their handler. An invalid successful result raises `InvalidToolResultError`. It rejects an ungranted Session-scoped Tool with `<tool>_unavailable` before the ordinary allowlist check; a matching grant overrides that allowlist. **Dispatch is not list-filtered by readiness**, but it re-evaluates readiness live and, when not ready, returns a `tool_not_ready` failure envelope (`retryable=False`) without running the handler — the safety net for a prompt built moments before the credential vanished.
- `ToolRegistry.schema_fingerprint(name) -> str` returns the canonical contract fingerprint; `validate_result(name, result) -> dict` is the shared envelope and success-data validation seam used by normal dispatch and Extension replacements.
- `discriminated_union_schema(discriminator, variants, *, description, discriminator_description) -> dict` builds a canonical flat union of closed `oneOf` branches. Each branch requires its single-value discriminator beside only that variant's fields and structurally required inputs. `action_schema(...)` is the `action`-specific wrapper used by multi-action Tools. Runtime handlers retain semantic checks and defense-in-depth field rejection, but Provider-visible correctness does not depend on them.
- `tool_is_ready(tool) -> bool` (module-level) — the readiness predicate contract: `ready is None` → ready; a predicate that raises is logged once at `warning` and counts as **not ready** (a broken predicate never takes a build down or makes a tool spuriously available). Cheap, I/O-free (a string-nonempty check, never a network ping) — it runs on every prompt/tool-definition build.
- `ToolContext.on_cancel(callback)` registers a per-tool-call cancel callback (no-op when no registration hook is wired); `ToolContext.was_cancelled_by_user() -> bool` reports whether the current call was user-cancelled (False when no check hook is wired). These hooks are wired by the chat dispatcher through `ToolExecutionConfig` so a Tool can plug into `Run.register_tool_cancel` / `Run.tool_call_cancelled` without importing the Run domain. A targeted per-call cancel invokes only that callback and leaves the Run alive; a full `Run.request_cancel` cascades every still-active callback in registration order before forcefully cancelling the executor, and late registration after the Run signal fires immediately.
- `ToolContext.after_result_persisted(callback)` registers a per-call delivery callback. The dispatcher keys it by `tool_call_id`, and Chat invokes it only after the corresponding ordered Tool Result append returns; absence of the hook is a no-op so Tools remain reusable outside Chat execution.
- Result-envelope validation failures raise `InvalidToolResultError` (a `ValueError` subclass), distinct from plain `ValueError` argument failures. The chat loop maps the former to an `invalid_tool_result` failure envelope and the latter to `invalid_arguments`, without inspecting error message text.
- `ToolExecutor.execute_many(tool_calls, config) -> list[dict]` executes sibling calls concurrently by default within the bounded Run/global limits and preserves original result order. A Tool registered with `parallel_safe=False` is an explicit ordering barrier before and after itself. Chat serializes Extension `tool_call` and `tool_result` hook callbacks through a batch-local lock so hook transformations stay deterministic without serializing parallel-safe Tool handlers. Chat may also supply a live per-name denial resolver; it runs before Extension hooks and the Tool handler for every sibling, and a denial returns `tool_not_allowed` without side effects.
- `core.tools.availability.effective_agent_allowed_tools(...)` applies Agent-level derived availability before runtime dispatch and merges current Session grants. The `memory` Tool is added when `memory_prompt_mode` is not `off`; `session_read` is derived whenever configurable `session_search` is allowed; a Session grant independently adds its matching Session-scoped Tool. Runtime-derived Tools are removed from persisted Agent allowlists.
- Extensions register their own Tools through `api.register_tool(name, description, parameters, handler, *, internal=False, display=None, ready=None, readiness_hint=None, result_schema=None, parallel_safe=True)` (`.vorch/domain-maps/extensions.md`), which routes into this same `ToolRegistry.register` during Runtime bootstrap — applied after the last built-in Tool, right before `SystemPromptManager` consumes the registry. Extension Tools are **normal Tools** afterward: same compiled contracts, provider/prompt definitions, allowlist filtering, and dispatch. A name colliding with a built-in or another Extension's Tool is skipped (the existing Tool wins) and diagnosed on the Extension record; an invalid Tool declaration is likewise isolated and diagnosed without preventing other capabilities from applying.
- `ToolPromptBlockRegistry` is the **tool-side System Prompt block-declaration seam**: a tool that wants prompt content declares a block here (`register(tool_name, *, default_text=None, render=None)`, exactly one of text/render, first-wins-with-warning on a duplicate tool name), and the runtime gathers `block_definitions()` and merges them with the extension blocks before handing the list to the prompt manager. A declared block is id `tool:<name>` and owner `tool:<name>`, so gate 2 renders it only when `<name>` is on the agent's effective allowlist; static or dynamic, the same split as a core or extension block. **The prompt domain imports no tool classes** — it only ever consumes a list of `core.prompts.BlockDefinition` (the `core.prompts` import in `block_definitions()` is lazy so the tools domain has no import-time dependency on prompts either). The built-in `project` and `subagent` Tools use dynamic blocks for their current catalogs and guidance. See `tools/project.md`, `.vorch/domain-maps/prompts.md` (block model), `.vorch/domain-maps/subagents.md` (Sub-Agent catalog semantics), and `.vorch/domain-maps/extensions.md` (the parallel extension-block path).
- `core.tools.arguments` is the shared strict semantic-parsing home for `optional_string`/`required_string`, `optional_int`/`required_int`, and `optional_number`. These helpers do not coerce numeric strings, integral floats, boolean spellings, aliases, or blank values around the canonical contract. They raise `ToolArgumentError` (a `ValueError`) for semantic handler checks. The module also hosts `looks_like_line_numbered_content` and the shared `LINE_NUMBER_GUTTER_SEPARATOR`: a content-shape guard that `write`/`edit` use to reject text echoing `read`'s `N|` line-number gutter back into a file (see `tools/read.md`).

## Conventions

- **The canonical contract is executable.** `ToolRegistry.dispatch()` rejects wrong types, missing requirements, invalid unions, invalid ranges, and empty values constrained by the schema before the handler executes. Closed contracts also reject unknown properties there; migrated model-facing Tools use open schemas and must reject unknown and inapplicable fields in the handler. Public Tool inputs are not coerced: callers must send the advertised field names and JSON types. Handlers retain semantic validation for authorization, existence, state transitions, and constraints the schema cannot decide.
- **Definition Profiles are configuration-bound, never request-bound.** Use one only when stable configured capabilities change which arguments are meaningful. Derive it from persisted Agent/Channel/Model configuration, sort set-like inputs, use a deterministic profile key, and keep transient Adapter liveness, Provider request, Session, Run, and tool-call data out of both key and schema. A real configuration change may legitimately change the Provider prefix once; an unchanged configuration must keep the same bytes. The exact post-projection contract shown to the Model remains the dispatch validator for that cycle, while the handler and downstream service retain semantic and liveness checks.
- **Agent-facing definitions follow the repository-root `TOOLS.md` rules and migrate one verified Tool at a time.** `process`, `memory`, and `subagent` are migrated Action Tools: one flat object advertises required `action` plus the shared optional-property superset, parameter descriptions state action-dependent requirements and omission behavior, and the handler remains the authority for rejecting inapplicable or missing fields; `memory.scope` is additionally required because every action needs it. `web_fetch`, `web_search`, `skill`, the Reflection-only empty `skill_list`, `write`, `read`, `glob`, `grep`, `edit`, `text_to_speech`, `project`, `analyze_image`, `image_generation`, `status`, `session_read`, `session_search`, `channel_send`, and `bash` are migrated Tools whose model-facing schemas omit `additionalProperties`; omitted defaults remain handler-owned and are stated in parameter descriptions where needed. `web_search.page`, `session_search.limit`, and Bash's profile-dependent `yield_after` retain stable numeric schema defaults; configurable defaults stay handler-only. `grep`, `status`, `session_read`, and `session_search` replace duplicated mode/target branches with one flat property set and handler validation; `channel_send` replaces platform branches with one configuration-derived flat profile and handler enforcement; `bash` replaces mode branches with one flat property set and a depth-projected mode enum. The not-yet-migrated Action Tools (`cron`, `history`, and `skill_manage`) still use `action_schema` closed branches until each completes its own local and Luna verification matrix. Do not add nested `request.operation`, operation-key objects, redundant single-value actions, or action inference from unrelated optional-field combinations. Historical persisted calls may retain retired shapes for presentation only. See `tools/designing-agent-tools.md`.
- **Readiness is a separate axis from the allowlist and Session grants.** A not-ready tool stays *registered* (persisted permissions survive) but is filtered out of the **model-facing** surfaces and returns a `tool_not_ready` envelope on a direct dispatch. Two surfaces apply the readiness filter: `provider_definitions` and `prompt_definitions` (both default `ready_only=True`, so the prompt tool list, the provider tool definitions, and — through the prompt definitions — gate 2 of a `tool:<name>`-owned prompt block all drop a not-ready tool). The `tool.list` RPC calls `list_tools(include_session_scoped=False)` without the readiness filter — it returns every registered normal Tool, each carrying `ready` (bool, via `tool_is_ready`, a raising predicate counting as false), `readiness_hint` (or null), `extension` (owning extension or null), and the Projects-owned `project_configurable` plus `project_configurability_reason` projection — so the Agent Tool picker and Project Tool Whitelist editor see a not-ready Tool but never expose a Session-scoped capability or duplicate Project policy. Consumers that keep seeing not-ready tools with no styling deliberately leave `ready_only` at its default: extension collision detection, dispatch allowlist computation, and the runtime startup inventory count. A `tool:<name>`-owned prompt block still drops when its Tool is not ready, because gate 2 reads the readiness-filtered prompt definitions.
- At the generic ToolRegistry boundary, `allowed_tools=None` and `["*"]` mean all registered normal tools, while `allowed_tools=[]` means no normal tools. The Project Tool Whitelist is intentionally stricter: it is an explicit security ceiling and rejects `"*"` in raw `project.json`, entity construction, and `project.set`.
- Agent `allowed_tools` is the configurable allowlist for normal tools except runtime-derived `memory` and `session_read`; Memory mode owns `memory`, while `session_search` availability owns its exact-read companion.
- For a **config (project) agent**, `allowed_tools` is not stored on the agent: the resolver computes it as the Project Tool Whitelist (`project.allowed_tools`, the ceiling) minus the Agent's scanned denials — the Agent can only narrow the ceiling, never widen it. `project.set` permits only registered normal non-Session-scoped Project tools, excluding `memory`, `project`, and `skill_manage`; a previously persisted unavailable name may only be retained or removed. The scan preview reports unavailable entries without dropping them, so a temporarily disabled Extension keeps its permission. The whitelist filtering here receives an explicit computed list, never `["*"]` (see `projects/resolution.md` → Effective Capabilities).
- Internal tools bypass normal `allowed_tools` filtering and must enforce their own domain rules.
- Provider-visible definitions must not expose handlers, runtime context, internal flags, or display metadata.
- Display labels are not tool parameters. Do not add generic arguments such as `description` only to affect UI chrome; use `ToolDisplay`.
- Tool result failures should be returned as failure envelopes where possible instead of raising through the Run.
- Same-turn sibling Tool Calls execute concurrently by default within the shared limits, including multiple calls to the same Tool. A Tool with `parallel_safe=False` is an explicit barrier. Active Tool hooks serialize only the hook callbacks; parallel-safe Tool handlers may still overlap.
- Tool timing metadata must never be forwarded to provider adapters; provider tool messages contain only the tool role, call correlation, name, and content.

## Constraints & Gotchas

- Tool results must be JSON objects matching the stable envelope; non-envelope results and successful data that violate the declared result schema are rejected.
- Disallowed normal tools fail at dispatch even if a provider asks for them.
- An ungranted Session-scoped Tool fails with its stable `<tool>_unavailable` code. A matching persisted-state or Run-local grant intentionally adds that Tool to Provider definitions; a static Run restriction and live per-call denial remain dispatch-only intersections and can return `tool_not_allowed` even while the Provider was correctly told the Tool exists. Restrictions and denials must never filter Provider Tool definitions or mutate System Prompt assembly.
- Result persistence must preserve the Assistant's original Tool Call order even when a parallel-safe group finishes out of order.
- Relative filesystem paths resolve from `ToolContext.effective_cwd` (the project repo for a project Session, else `workspace`); absolute paths bypass it unless a specific tool forbids them. The file tools (`read`/`write`/`edit`/`grep`/`glob`/`search`) and `bash` resolve against `effective_cwd`; `memory` deliberately stays on `workspace` (it is the identity/memory home, not project-relative).
