# Tools

Tool metadata registry, Tool Access Policy resolution, provider definitions, context-aware execution, stable result envelopes, display metadata, and async dispatch.

## Overview

`core/tools/` owns canonical contracts, registry, declarative family/activation/constraint metadata, and the Tool Access Policy resolver. Registration compiles immutable JSON Schemas before exposure; a Tool may additionally select a configuration-bound Definition Profile per Agent. Dispatch uses the exact model-facing input schema from that Provider cycle to normalize a copied argument object for common unambiguous Model encodings, normally validates before the handler, and validates successful result data afterward. A deliberately batched Tool may set `handler_validates_arguments=True` when whole-call schema rejection would violate item independence; its handler must then validate the complete root plus every item before that item's side effects. Sibling calls schedule concurrently by default within bounded limits while preserving explicit ordering barriers; expected failures become stable result envelopes. Chat may apply an additional route-specific visibility filter after definitions are built (currently gating `analyze_image` on route image capability or an explicit Agent grant, plus live binding/wire availability; see `tools/image.md`) without touching registration or permissions. Concrete built-in Tool behavior lives in child maps under `.vorch/domain-maps/tools/`.

The public `tools.py` entry point retains Tool registration, dispatch, scheduling, and prompt-block collection. Internal units own immutable definitions (`_tool_definitions.py`), per-call context (`_tool_context.py`), presentation metadata (`_tool_display.py`), and result-envelope validation (`_tool_results.py`). These are internal parts of the existing Tools owner; public imports remain stable.

## Terms

Domain vocabulary. The core Tool term lives in `.vorch/GLOSSARY.md`.

### Readiness
**Definition:** A per-tool, cheap, I/O-free predicate (`Tool.ready`) evaluated at every prompt/tool-definition build; filter order is registered -> policy-allowed -> ready. A not-ready Tool vanishes from System Prompt and provider definitions but stays visible with its explanation in configuration surfaces so persisted policy survives; direct dispatch returns a clean `tool_not_ready` envelope instead of running. A raising predicate counts as not-ready (logged once at warning).
**Not:** A permission - policy answers "may this Agent use it", readiness answers "can it run right now". Also not stored Extension state: the Extensions tab's waiting status is a derived display value.

### Session Grant
**Definition:** A capability Chat derives while building one Session's request state and carries through provider definitions and dispatch. Example: `history` appears only after persisted Compaction state makes it meaningful.
**Not:** A Run-local input, Agent/Project configuration, catalog choice, or permission to address another Session.

### Definition Profile
**Definition:** A model-facing description + input schema selected from stable persisted configuration for an Agent, keyed by an immutable profile key; unchanged configuration must reproduce byte-identical provider definitions, transient state must never select a different profile.
**Not:** The canonical contract, a per-Run schema, readiness, or an execution-time fallback.

## Contracts

- **Agent-facing purpose, clarity and cost:** Design around the intended user task, not preservation of the current interface. Definitions must teach a complete action and observable result; first-use guidance cannot be replaced by expected error recovery. Minimize unnecessary context and round trips across the whole workflow, including redesign and testing. Deterministic contract tests and Provider conformance are distinct from black-box task evaluations. Audits verify useful outcomes beyond `ok` and report before/after token costs; detailed design rules live in `tools/designing-agent-tools.md`, the review procedure, evidence rules and instruments (`scripts/tool_lab`) in `.vorch/workflows/tool-review-workflow.md`.
- **Agent error tolerance:** Execute a call whose intended effect a competent reader would identify without asking - operation, target, values, scope and explicit constraints are clear - even when its expression does not match the schema: aliases, other Tool dialects, representation differences, copy artifacts, fields the selected action does not use. A round trip spent correcting such a call is a defect. Purely representational differences execute silently; an interpretation that involved judgment executes and is stated in the result (a timeout read as milliseconds, an invalid regex searched literally, replacement indentation mapped to the file's style). Tolerance must produce the correct effect, not merely an accepted call. Never write to a guessed target, substitute an unavailable explicit target, rewrite valid application data, discard a requested effect, or resolve conflicting instructions by choosing one; a unique similar name, an existing alternative target, or fewer schema errors does not establish intent for a mutation or an explicit target. Plausible readings with different effects, or a missing decision, fail before side effects with the corrected call. General representation repair belongs to the shared contract; aliases, call wrappers, vocabulary formatting, inapplicable fields and empty-selection defaults require the owning Tool's explicit interpretation. Apply authorization and execution checks to the interpreted operation. Verify equivalent calls and plausible different calls against independently specified receiving arguments and effects, not an expectation derived from the same repair code.
- **Result envelope:** `{ ok, error, data, artifacts }` - success uses `error: null`, failure `data: null` plus `error.code`/`error.message`. The top-level key set is exact (`is_tool_result_envelope()`); retry-signalling fields go *inside* `error`: optional `retryable: bool` and `attempts_made: int` tell the Model whether a failure is transient and how many attempts were already made (a tool exhausting its own retries sets `retryable=True` with the real count; validation/fatal failures omit or set false). Network tools share the retry policy in `core/utils/http_status.py` (`is_retryable_status`, `parse_retry_after`) and backoff math via `core/utils/retry.compute_retry_delay`.
- **Timing** is never inside the envelope: completed calls expose a sibling `timing {started_at, completed_at, duration_ms}` (monotonic, non-negative) on Run events and persisted Tool messages - never forwarded to adapters.
- **Rich-media artifact:** `read_media_artifact(...)` builds the one cross-Tool artifact `{kind: "read_media", attachment_id, filename, media_type}` used by `web_fetch` and other stored remote media; Chat resolves it as Run-local content on the correlated Result. Local `read` images instead transfer pixels via the request-only `ToolContext.result_media` list, never through the persisted envelope or public events.
- **Display metadata** (`ToolDisplay`) is presentation-only per-invocation data: typed facts (counts, line ranges, +/- changes) recorded via `ToolContext.add_display_count()`/`add_display_line_changes()` plus optional original-image paths in `presentation_images` (persisted as internal `image_files`, projected by the server into signed URLs), assembled into a versioned payload that never enters provider definitions or result envelopes. Every built-in registers an explicit display (an intentional no-summary row included); new growth belongs in the Tool-owned profile, not per-name branches in Svelte.
- **ToolContext** carries identity/addressing (`agent_id`, session/run/tool-call ids, nesting depth, iteration number), `workspace`, `cwd`/`effective_cwd` (the working Project repo for Rooted Identity or Project Agents, else Workspace; Memory deliberately ignores it), `project_id` (Session/address ownership, stays `None` for Rooted Identity Agents so bare Sub-Agent targets remain Identity targets; `skill_project_id` separately carries the Project serving Skill activation), cancel hooks wired by the chat dispatcher, the change tracker, `after_result_persisted(callback)` invoked only after ordered persistence, and `attach_result_payload(payload)` (Extension Tools in a Session only; `result_payloads_available` says whether it works; contract in `extensions.md`).
- **Concurrency:** same-turn sibling Calls execute concurrently by default within bounded Run/global limits, preserving original order in results and persistence. Only a registered Tool with `parallel_safe=False` is an explicit ordering barrier before and after itself; unknown Tools invoke no handler and create no barrier. Extension hooks serialize their callbacks batch-locally without serializing parallel-safe handlers. If cancellation or another `BaseException` escapes a parallel group, the executor cancels and drains its remaining child Tasks before propagating the original abort; ordinary `Exception` failures remain per-call envelopes. Interrupted batch recovery belongs to Chat (see `chat/run-execution.md`; coverage: `tests/core/tools/test_tools_execution.py`).
- **Blocking work:** handlers offload blocking sections through the dedicated worker pool (`run_tool_worker` / `offload_tool_handler`) with admission backpressure and cancellation shielding; built-ins choose selectively (wholly offloaded: apply_patch/history/project/search_files/memory/session_search/skill_manage; split: skill/read/channel_send/web_fetch). Ordinary sync built-ins keep loop-dispatch because some intentionally call loop-owned APIs; sync Extension handlers auto-offload.
- A retired Tool name (such as `grep`, `glob`, `write`, `edit`, `terminal_beta`) left in a persisted policy is an ordinary unknown Tool name; the Generation 1 converter replaces retired names with their successors without widening access (`database/generation-1-conversion.md` -> Retired Tool names), and Project scanners map external grep/glob denials to `search_files` (see `tools/search_files.md`). Direct dispatch of a not-ready Tool includes its specific `readiness_hint` when supplied.
- **Policy resolution:** `normalize_tool_access` validates strict persisted policy; `resolve_tool_access` is the single resolver behind prompt/provider definitions and dispatch - mode selection, automatic activation (declared followers, Memory mode activates `memory`, grants activate theirs), constraints, `denied` as absolute veto, orphaned followers removed, mode `none` suppresses every activation path.
- **Prompt-block seam:** `ToolPromptBlockRegistry` lets a Tool declare a System Prompt block (`id`/owner `tool:<name>`, rendered only when the Tool is effectively allowlisted); the prompt domain imports no tool classes. Built-in `project` and `subagent` use dynamic blocks for current catalogs.

Configurable Tools may declare `requires_opt_in=True`. They require an explicit name in `tool_access.granted` in addition to ordinary policy permission; All mode and materialized Project ceilings never grant opt-in. None and denials still win, and companions cannot follow an ungranted parent. Missing Tools retain stored grants. `tool.list` exposes the flag for the shared editor; raw wildcard/unfiltered definition and dispatch paths do not authorize opt-in Tools. Coverage: `tests/core/tools/test_availability.py`, `tests/core/extensions/test_capabilities.py`.

## Registration and dispatch rules

- Names match `^[A-Za-z][A-Za-z0-9_]{0,63}$`. Registration compiles the canonical Draft 2020-12 contract up front and rejects invalid schemas, unknown families, or incoherent activation metadata before publishing; fixed-shape objects close by default while model-facing schemas set `open_input_schema=True` and omit `additionalProperties`. Either way a Tool's root `properties` are its complete parameter list: the contract treats an omitted root `additionalProperties` like `false`, and only an explicit schema/`true` or `patternProperties` accepts undeclared arguments (Extension and MCP schemas included). Families are comprehension/bulk-action metadata only - membership never implies activation.
- Contract compilation is memoized by the exact JSON content of its inputs, so the per-Provider-cycle contracts reuse one immutable compiled contract per unchanged definition and any content change compiles afresh. Inputs holding non-JSON values (for example tuples) always compile uncached, so the cache never changes whether a schema is accepted.
- Dispatch authorizes and readiness-checks, normalizes a deep copy of arguments against the cycle's exact input contract, validates unless the registered handler explicitly owns complete argument validation, executes, validates the envelope plus declared result schema, and verifies finite JSON-serializability. Shared normalization follows the repair rules below and always leaves meaningful operation validation in place; it drops an undeclared root argument whose value is null, `""`, `[]` or `{}` (it requests nothing), while any other undeclared argument fails. A validation failure reports every problem at once in Agent-readable sentences (`<tool> was not run: ...`): the field, the expectation, the received value, the first sentence of a missing parameter's description, a suggested parameter for an unknown name (never applied), and the parameter list whenever a name was missing or unknown. Handlers do not repeat unknown-argument checks; they own conditional rules such as fields one action requires. A Tool may register `unadvertised_parameters` (name -> schema): root parameters its handler accepts without offering them, such as options copied from older conversation history (`web_fetch`) or a Participant's own identity echoed from reminders (Swarm). Dispatch validates them like advertised parameters, but they never appear in Provider definitions or argument errors. Aliases that an owner normalizer translates into advertised parameters need no declaration. Handler-deferred validation currently supports independently executed batches whose item errors must not reject valid siblings; complete validation remains the owner's responsibility. An invalid/non-serializable result raises `InvalidToolResultError`, distinct from argument errors, mapped to `invalid_tool_result`.
- An ungranted Session-scoped Tool fails `<tool>_unavailable` before allowlist checks; a matching grant overrides the allowlist. Dispatch is not list-filtered by readiness but re-evaluates live -> `tool_not_ready` envelope (retryable=False) instead of running.
- `deferred=True` keeps a Tool registered for policy, metadata, and dispatch while excluding it from Provider definitions and System Prompt Tool lists. Discovery owners deliver selected schemas through ordinary results; catalog changes must not promote deferred Tools implicitly.
- `catalog_visible=False` hides a Tool only from public catalog projections, including Extension capability lists and Project selection. Internal enumeration retains it for policy, collision detection, replacement, fingerprints and teardown; this flag alone neither grants access nor establishes Session scope. Public projections explicitly use `include_catalog_hidden=False`; the default preserves internal enumeration. Coverage: `tests/server/rpc/test_catalog_methods.py`, `tests/core/extensions/test_operations.py`.
- Provider-visible definitions expose only name/description/schema - never handlers, context, internal flags, or display metadata; Definition Profiles resolve per Agent from stable config (deterministic key, sorted set inputs, transient liveness excluded) and a `None` profile hides the Tool.
- `list_tools` filters registered -> allowed -> ready (readiness last, default off); `provider_definitions`/`prompt_definitions` default `ready_only=True`; `tool.list` intentionally includes not-ready/granted public Tools with full metadata so policy editors can explain states. At this boundary `allowed_tools=None`/`["*"]` mean all normal Tools, `[]` means none - the Project Tool Whitelist is deliberately stricter and rejects `"*"` (see `projects/resolution.md`).
- For a **config (Project) Agent**, the Project Tool Whitelist is the outer ceiling: scanned repository denials narrow it, a vBot override fully replaces the scanned policy but must stay inside the ceiling; `project.set` accepts only registered configurable Tools and keeps previously persisted unavailable names retain-or-remove.
- Internal tools bypass allowlist filtering and enforce their own domain rules. Same-turn failures are per-call envelopes, never Run failures; Run/provider/process/persistence failures stay outside this boundary. Result persistence preserves the Assistant's original call order even when a parallel group finishes out of order.
- Extensions register Tools via `api.register_tool(...)` after declaring families if desired; applied last during bootstrap, then ordinary Tools in every respect. Name collisions skip with diagnosis; invalid declarations isolate without blocking other capabilities.

## Conventions

- Public and private Session Tools use dispatch normalization. The production Swarm probe checks independently prescribed calls, real registry results, and durable receipts.

- When vBot authors a filesystem path for Model consumption in Tool output, render separators as forward slashes (`C:/...`); resolution, persistence, input handling, and OS calls keep native `Path` semantics - never global text normalization.
- A Tool may register a pure `argument_normalizer` for domain-specific repairs that must precede required-field validation. Dispatch invokes it on a deep copy after access/readiness checks, then applies the cycle's exact canonical contract normally. It changes no Provider schema or authorization policy.
- **Shared argument repair:** `contracts.py` normalizes copied schema-guided value encodings: numeric counts without rounding, boolean aliases, JSON containers, and scalar arrays. Accepted text and arbitrary object keys remain unchanged. Generic repair does not rename fields, rewrite enums, unwrap business objects, or omit explicit empty/null values. Conflicting duplicate encoded JSON keys and multiple valid conversion meanings fail rather than selecting a value by branch order.
- **Owner-selected call repair:** `_argument_repair.py::normalize_call_arguments` is an internal part of the Tools owner, used by existing `argument_normalizer` hooks and item-validating handlers. It repairs one declared call object's field formatting, explicit field aliases, and known wrappers; enum formatting and empty-as-omission require explicit field selection. Optional per-field normalizers run on canonical field names before shared schema conversion and alias conflict checks (search_files uses this for encoded argument lists). It never applies edit-distance matching and never recursively treats nested payloads as call syntax. Conflicts are checked before omission. Batch owners invoke it separately per item to preserve independent execution. Target ids are not vocabulary enums.

Live Extension catalogs publish atomically through `ExtensionOperations.replace_tools`; ToolRegistry revision changes refresh the next Provider cycle's definitions and contracts. Removing a catalog retires its authority. Definition-profile context includes the exact Agent/Project identity. See `extensions/mcp.md` for connection opt-ins and remote schema changes.

## Constraints & Gotchas

Tool execution normally consumes the shared 500-slot semaphore (also the default per-batch limit). The registered `subagent` coordinator opts out via `execution_slot_required=False`: waiting for a child Run must not hold a slot that its Tools need. Per-batch concurrency and Sub-Agent admission limits still apply. Chat's emitting registry delegates this execution policy.

- Non-envelope, non-serializable, or schema-violating successful results reject as `invalid_tool_result` without aborting the Run.
- Disallowed normal Tools fail at dispatch even if a provider asks for them.
- Chat alone derives Session Grants during request building; static restrictions and live denials stay dispatch-only and must never filter provider definitions or mutate prompt assembly.
- Relative paths resolve from `effective_cwd` (Project repo else Workspace); absolute bypass unless a specific Tool forbids. File tools and `bash` use it; `memory` deliberately stays on Workspace (identity home, not project-relative).
- A live per-name denial resolver runs before hooks and handler for every sibling; the dispatcher also carries that resolver and the Run Tool restriction through ToolContext for delegated calls. Denial returns `tool_not_allowed` without side effects.

- `ToolContext.resolve_path` follows host path grammar without filesystem-dependent fallback. Windows double quotes may wrap a path because they cannot be literal filename characters; single quotes remain literal. POSIX quotes and backslashes remain literal even when a different unquoted/slash-separated file exists. Path objects remain literal. Scope, read-state, and mutation checks still use the resolved target. `follow_final_link=False` resolves only the parent, for operations on a link entry itself (apply_patch Delete/Move); `is_link_entry` in `_tool_context.py` is the shared symlink-or-junction test (`Path.is_symlink` misses junctions).
