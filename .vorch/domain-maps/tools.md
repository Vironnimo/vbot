# Tools

Tool metadata registry, Tool Access Policy resolution, provider definitions, context-aware execution, stable result envelopes, display metadata, and async dispatch.

## Overview

`core/tools/` owns canonical contracts, registry, declarative family/activation/constraint metadata, and the Tool Access Policy resolver. Registration compiles immutable JSON Schemas before exposure; a Tool may additionally select a configuration-bound Definition Profile per Agent. Dispatch uses the exact model-facing input schema from that Provider cycle to normalize a copied argument object for common unambiguous Model encodings, normally validates before the handler, and validates successful result data afterward. A deliberately batched Tool may set `handler_validates_arguments=True` when whole-call schema rejection would violate item independence; its handler must then validate the complete root plus every item before that item's side effects. Sibling calls schedule concurrently by default within bounded limits while preserving explicit ordering barriers; expected failures become stable result envelopes. Chat may apply an additional route-specific visibility filter after definitions are built (currently gating `analyze_image` on route image capability or an explicit Agent grant, plus live binding/wire availability, see `tools/image.md`; and offering one dialect of the file edit Tools by Model family, `apply_patch` or `edit` plus `write`, see `tools/edit.md`) without touching registration or permissions. Concrete built-in Tool behavior lives in child maps under `.vorch/domain-maps/tools/`.

The public `tools.py` entry point retains Tool registration, dispatch, scheduling, and prompt-block collection. Internal units own immutable definitions (`_tool_definitions.py`), per-call context (`_tool_context.py`), presentation metadata (`_tool_display.py`), and result-envelope validation (`_tool_results.py`). These are internal parts of the existing Tools owner; public imports remain stable.

## Terms

Domain vocabulary. The core Tool term lives in `.vorch/GLOSSARY.md`.

### Readiness
**Definition:** A per-tool, cheap, I/O-free predicate (`Tool.ready`) evaluated at every prompt/tool-definition build; filter order is registered -> policy-allowed -> ready. A Tool not ready when a prompt epoch pins its Tool list stays out of that pin and the System Prompt and is announced once it becomes ready; readiness never removes a Tool the Model already knows in the epoch (`chat/request-building.md` -> Tool catalog per prompt epoch). Configuration surfaces keep a not-ready Tool visible with its explanation so persisted policy survives; direct dispatch returns a clean `tool_not_ready` envelope instead of running, with the Tool's `readiness_hint` and `retryable` from `Tool.readiness_retryable` (a `register` keyword, so also of live Extension Tool declarations; default false, true only when the hint names a retry that can succeed, such as an MCP remote Tool whose connection reconnects). A raising predicate counts as not-ready (logged once at warning).
**Not:** A permission - policy answers "may this Agent use it", readiness answers "can it run right now". Also not stored Extension state: the Extensions tab's waiting status is a derived display value.

### Session Grant
**Definition:** A capability Chat derives while building one Session's request state and carries through provider definitions and dispatch. Example: an Extension's private Tools appear only in a Session its temporary binding grants them to (`extensions.md`).
**Not:** A Run-local input, Agent/Project configuration, catalog choice, or permission to address another Session.

### Definition Profile
**Definition:** A model-facing description + input schema selected from stable persisted configuration for an Agent, keyed by an immutable profile key; unchanged configuration must reproduce byte-identical provider definitions, transient state must never select a different profile.
**Not:** The canonical contract, a per-Run schema, readiness, or an execution-time fallback.

### On-demand Tool
**Definition:** A Tool an Agent may use whose definition its Tool list leaves out while the Agent's `tool_loading` switch is on (`agent.md` -> Data Model): the System Prompt lists it by name and summary, and the Agent loads its definition with `load_tools` before the first call (`tools/load_tools.md`). `core/tools/on_demand.py::on_demand_tools` is the one classification Chat, `prompt.preview` and `scripts/tool_lab` share: every Tool except `load_tools`, the Session's granted Tools and the always-loaded Tools (the default set, or `always_loaded`; the file edit Tools count as one). Built-in Agents, fixed Tool sets, Tool access `none` and temporary Agents have none.
**Not:** A permission or a deferred Tool (`deferred=True`): an On-demand Tool is allowed and callable, only its definition is not shown until loaded.

### Failure modes F1-F6
**Definition:** The codes that rows under `## Agent-facing text` cite for the failure a sentence prevents: F1 wrong choice (another Tool or the shell, or this Tool for the wrong job), F2 malformed call (wrong names or types, placeholders, missing fields), F3 wrong effect (wrong target, misread default or unit), F4 misread result (believes it is done, misses a truncation, polls, rereads to verify), F5 error loop (the error does not say how to fix the call), F6 context waste (long definitions, large or repeated results, extra round trips).
**Not:** The failure codes of Tool results, such as `invalid_arguments`.

## Contracts

- **Agent-facing purpose, clarity and cost:** Design around the intended user task, not preservation of the current interface. Definitions must teach a complete action and observable result; first-use guidance cannot be replaced by expected error recovery. How to write and review what an Agent sees of a Tool: the `vbot-agent-tools` Skill; evaluating it with real Models: the `vbot-agent-eval` Skill. The instruments are `python -m scripts.tool_lab` (`definitions`, `probe`, `sessions`, `replay`; `--help`).
- **Agent error tolerance:** Execute a call whose intended effect a competent reader would identify without asking - operation, target, values, scope and explicit constraints are clear - even when its expression does not match the schema: aliases, other Tool dialects, representation differences, copy artifacts, fields the selected action does not use. A round trip spent correcting such a call is a defect. Purely representational differences execute silently; an interpretation that involved judgment executes and is stated in the result (a timeout read as milliseconds, an invalid regex searched literally, replacement indentation mapped to the file's style). Tolerance must produce the correct effect, not merely an accepted call. Never write to a guessed target, substitute an unavailable explicit target, rewrite valid application data, discard a requested effect, or resolve conflicting instructions by choosing one; a unique similar name, an existing alternative target, or fewer schema errors does not establish intent for a mutation or an explicit target. Plausible readings with different effects, or a missing decision, fail before side effects with the corrected call. General representation repair belongs to the shared contract; aliases, call wrappers, vocabulary formatting, inapplicable fields and empty-selection defaults require the owning Tool's explicit interpretation. Apply authorization and execution checks to the interpreted operation. Verify equivalent calls and plausible different calls against independently specified receiving arguments and effects, not an expectation derived from the same repair code.
- **Result envelope:** `{ ok, error, data, artifacts }` - success uses `error: null`, failure `data: null` plus `error.code`/`error.message`. The top-level key set is exact (`is_tool_result_envelope()`); retry-signalling fields go *inside* `error`: optional `retryable: bool` and `attempts_made: int` tell the Model whether a failure is transient and how many attempts were already made (a tool exhausting its own retries sets `retryable=True` with the real count; validation/fatal failures omit or set false). Sessions persist the envelope as compact JSON; the Model reads a plain-text rendering of it that Provider wires produce (`providers/request-policy.md`), so `content`/`output` strings reach it verbatim (except neutralized look-alike `<system-reminder>` tags) and data field names are its only labels. Network tools share the retry policy in `core/utils/http_status.py` (`is_retryable_status`, `parse_retry_after`) and backoff math via `core/utils/retry.compute_retry_delay`.
- **Model Tool names:** the registry name identifies a Tool everywhere inside vBot: policy, Session history, dispatch, Run events, Extension hooks and UI. `core/tools/model_names.py` may give a Tool a different name for the Model on this host; today only the shell Tool `bash` is offered as `powershell` on Windows, because a Tool called `bash` makes Models write bash syntax. Chat renames at the Provider boundary in both directions (`chat.md` -> `wire_shaping.py`). Model-facing text that names a Tool uses `model_tool_name`/`SHELL_MODEL_NAME`: Tool descriptions, guidance blocks, the opt-in `core:tools_list` block, `Tool not allowed`, argument errors and the repeated-failure reminder. Registration rejects a name that is another Tool's Model name (`DuplicateToolError`). Provider-native replay data (Responses output items, Gemini parts) keeps the names the Model emitted. Coverage: `test_model_names.py`, `test_tools_registry.py`, `test_tools_execution.py`, `test_chat_loop_tool_definitions.py`, `test_streaming.py`.
- **Called Tool names:** Models also call Tools by names from other harnesses or with a namespace prefix. Before Chat persists an Assistant turn, `called_tool_name` (`model_names.py`) maps each Call whose name is neither offered in that request (listed, or available in the prompt epoch without being listed: an announced addition or an On-demand Tool the Model knows by name only, so `KillShell` reaches `background_tasks` before it is loaded) nor registered (a Tool announced as removed counts as registered) to the offered Tool it clearly means. Tool-call markup leaked after the name (`<` or `</` followed by `|`, a full-width bar or a letter, such as DeepSeek's `board_placeholder</...DSML... parameter>`) is cut off first; the rest is resolved like any called name and, unresolved, is the name the Call keeps (Swarm Sessions, 2026-10-12). Then namespace prefixes (`functions.`, `default_api:`, ...), case and separators are ignored (`Read`, `WebFetch`), and a fixed table maps other harnesses' names for the same capability to the first offered of its targets (`Edit`/`MultiEdit`/`str_replace` -> `edit`, else `apply_patch`; `Write`/`create_file` -> `write`, else `apply_patch`; `patch`/`apply_diff` -> `apply_patch`; `Grep`/`Glob`/`ls` -> `search_files`, `Task` -> `subagent`, `shell`/`run_shell_command` -> the shell Tool, ...). A name outside that table maps to the one offered Tool whose registry or Model spelling (at least 5 characters without separators) it misses by one inserted, removed, replaced or swapped character (`powerhell` -> the shell Tool on Windows); two such Tools leave it unresolved. The Tool name selects the operation, not a target, so this does not relax the rule against guessed targets. The target's own argument handling then decides whether the Call runs. History, Run events and dispatch all carry the resolved name, so the next request replays the Call under the name the Model should use. A spelling shared by two offered Tools stays unresolved even when the fixed harness-name table has a target; a target not offered also stays unresolved. An unresolved name fails `tool_not_found` with `Unknown Tool: <name>. Call one of the available Tools instead: <names>.`, listing the ready, non-deferred Tools the caller may use under their Model names. When the Call's arguments fit exactly one of those Tools (every field one of its parameters, its required ones present, the value of a parameter with fixed values such as `action` one of them; `_arguments_fit` in `tools.py`), the message names that Tool instead of the list: `Unknown Tool: pash. These arguments fit powershell; call powershell with them.` It never runs that Tool, because the name did not say which Tool was meant (Swarm Sessions, 2026-10-12: 4 of 9 unknown-Tool Calls, such as `pash` with a `command` and `swagger_placeholder` with a Wiki read, fit exactly one offered Tool). Otherwise a Call that shows damage from a Provider's parser splitting the Model's tool-call markup wrongly is asked for again complete instead of being sent to the list: one that arrived with no arguments at all (`Unknown Tool: <name>. Nothing was run: the call arrived with no arguments at all. If you sent some, the call was garbled on the way: send the complete call again.`; the conditional, because a Call to an unknown Tool can also be meant without arguments), or with `<`, `>`, `=` or `"` in its name or an argument name (`... the call arrived with tool-call markup in the argument name "parameter=command", so it was garbled on the way. Send the complete call again.`). It ends with `The closest available Tool is <name>.` when one Model name clearly resembles the called one (difflib ratio of the separator-free spellings at least 0.5 and 0.1 ahead of the next; markup and what follows it in the name are ignored; `_closest_tool_name`), else `Available Tools: <names>.`; that Tool is never run either. Evidence: Swarm run 2026-10-13, one Model's Provider turned its shell calls into `powerhellsparameter` 15 times, 10 of them with `{}`, plus `powerthrough` with an argument named `parameter=command`; the list answer told it to pick another Tool, while what it needed was to resend the same call. Coverage: `test_model_names.py`, `test_tools_execution.py`, `test_chat_loop_tool_definitions.py` (`test_tool_called_by_another_harness_name_runs_and_is_stored_under_its_name`, listed and On-demand).
- **Timing** is never inside the envelope: completed calls expose a sibling `timing {started_at, completed_at, duration_ms}` (monotonic, non-negative) on Run events and persisted Tool messages - never forwarded to adapters.
- **Rich-media artifact:** `read_media_artifact(...)` builds the one cross-Tool artifact `{kind: "read_media", attachment_id, filename, media_type}` used by `web_fetch` and other stored remote media; Chat resolves it as request-only content on the correlated Result in every request until Compaction. Tools that load pixels in memory (`read`, computer use) instead hand them over via `ToolContext.result_media`, delivered with successful and failed Results alike, never through the persisted envelope or public events; Chat stores them as Attachments referenced by the Tool message's internal `tool_media` (`chat/request-building.md`).
- **Display metadata** (`ToolDisplay`) is presentation-only per-invocation data: typed facts (counts, line ranges, +/- changes) recorded via `ToolContext.add_display_count()`/`add_display_line_changes()` plus the images, videos and audio the user sees in the call's details - files it read, looked at or produced, and with `source=True` files it started from such as a generation's reference images - recorded via `ToolContext.add_display_media(path, media_type, filename=None, source=False)` (`media_type` a media type or only its kind `image`/`video`/`audio`, other kinds ignored; `filename` for a file whose path does not name it, such as a download; persisted as internal `media_files` of absolute `path`, `kind`, `filename` and optional `role: source`, projected by the server into signed `media` URLs; every Tool uses this one path, so the WebUI shows all Tool media alike), plus, for a display declaring `details=True` or a `detail_builder`, ordered user-facing detail blocks (payload `details`, present even when empty) that the WebUI shows in place of the raw arguments and result - first the blocks the builder derives from the call's arguments and result (`display_notice()`, `display_text()`, `display_results()`; the builder runs again for every projection, so it sees the final result), then those the handler recorded, in recording order: a `text` block (`label` `command`/`content`/`input`/`output`/`page`/`query`/`response`/`results`/`screen`/`scrollback`/`task`, either its own `text` of at most 16384 characters or a `source` naming `from` `arguments`/`result` and a key `path` to a string there, so a large value such as command output is not copied into the display; recorded via `ToolContext.add_display_text()`), a `results` block (`items` of what the call found, each with a `title` and optional `url` (absolute http(s), at most 2048 characters, otherwise dropped), `meta`, ISO `time` and `text` cut at 600 characters; at most 20 items, untitled ones dropped; recorded via `ToolContext.add_display_results()`), a `memory_changes` block (`scope` `agent`/`user`, non-empty `changes` of `op` `added`/`removed` with `text` or `replaced` with `previous` and `text`, optional positive `revision` of the Memory history) recorded via `ToolContext.add_display_memory_changes()`, a `notice` block (`level` `info`/`warning`/`error`, `text`, optional `subject`) recorded via `ToolContext.add_display_notice()` - a failed call without a recorded error notice, such as one rejected before its handler, gets one from its result's error message - and one `file_changes` block at the place of the first changed file, whose `files` are diffs recorded via `ToolContext.add_display_file_change()` (`core/tools/_display_diff.py`, over the minimal line diff `core/tools/_line_diff.py` that Run change statistics share, so both count alike; per file `path`, `change` (`created`/`updated`/`replaced`/`deleted`/`moved`), optional `destination`, `added`/`removed` over every changed line, `hunks` of `old_start`/`new_start` and `+`/`-`/space-prefixed `lines` with 3 context lines, `omitted_lines` beyond one 2000-line budget shared by the call, `binary` for non-text files), assembled into a versioned payload that never enters provider definitions or result envelopes. A primary part may carry `detail` (with `detail_kind`), the complete value a shorter part stands for (the command behind a Bash description), which the WebUI shows and copies in the part's value card. Every built-in registers an explicit display (an intentional no-summary row included); new growth belongs in the Tool-owned profile, not per-name branches in Svelte.
- **ToolContext** carries identity/addressing (`agent_id`, session/run/tool-call ids, nesting depth, iteration number), `workspace`, `cwd`/`effective_cwd` (the repo of the Run's Working Project, else Workspace; Memory deliberately ignores it), `project_id` (Session/address ownership, stays `None` for Identity Sessions working in a Project so bare Sub-Agent targets remain Identity targets; `skill_project_id` separately carries the Project serving Skill activation, and `working_project_id` the Run's Working Project, which a Sub-Agent with an Identity target inherits), `run_kind` (the dispatching Run's `RunKind`, `None` outside Runs; `core.runs.is_unattended_run_kind` names the background learning kinds, one shared definition `UNATTENDED_RUN_KINDS` in `core/runs/run.py`), cancel hooks wired by the chat dispatcher (an awaitable an `on_cancel` callback returns is awaited within the Run's cancellation cleanup budget, `runs.md` -> `Run.request_cancel`), the change tracker scoped by complete Session address and Run id, `after_result_persisted(callback)` invoked only after ordered persistence, `can_call(tool_name)` (whether the allowlist dispatch checked this call against and the Run's denial resolver let the Agent call a Tool, by registry name; a result names another Tool only when it is true), `offers(tool_name)` (`can_call` and listed in the Model request's Tools, `offered_tools`, which the executor fills from the request's input contracts; `None` outside a Model request counts every callable Tool as listed; text that points to one of several Tools for the same purpose, such as the file edit Tools, uses it), and `attach_result_payload(payload)` (Extension Tools in a Session only; `result_payloads_available` says whether it works; contract in `extensions.md`).
- **Concurrency:** same-turn sibling Calls execute concurrently by default within bounded Run/global limits, preserving original order in results and persistence. `ToolExecutor.start_batch()` returns a `ToolBatch` that starts each Call the moment it is added (Chat adds Calls while the Model still streams); `execute_many` is the same batch with all Calls known up front. A batch may run its Calls in a given `contextvars` context (Chat passes the one from before its Model request). Only a registered Tool with `parallel_safe=False` is an explicit ordering barrier before and after itself; unknown Tools invoke no handler and create no barrier. Extension hooks serialize their callbacks batch-locally without serializing parallel-safe handlers. If cancellation or another `BaseException` escapes a parallel group, the executor cancels and drains its remaining child Tasks before propagating the original abort; ordinary `Exception` failures remain per-call envelopes. Interrupted batch recovery belongs to Chat (see `chat/run-execution.md`; coverage: `tests/core/tools/test_tools_execution.py`).
- **Blocking work:** handlers offload blocking sections through the dedicated worker pool (`run_tool_worker` / `offload_tool_handler`) with admission backpressure and cancellation shielding; built-ins choose selectively (wholly offloaded: apply_patch/edit/write/project/search_files/memory/session_search/skill_manage; split: skill/read/channel_send/web_fetch). Ordinary sync built-ins keep loop-dispatch because some intentionally call loop-owned APIs; sync Extension handlers auto-offload.
- A retired Tool name (such as `grep`, `glob`, `terminal_beta`) left in a persisted policy is an ordinary unknown Tool name, and Project adapters map external grep/glob denials to `search_files` (see `tools/search_files.md`). Direct dispatch of a not-ready Tool includes its specific `readiness_hint` when supplied. `edit` and `write` are registered again as followers of `apply_patch` (`tools/edit.md`): a persisted `denied` entry vetoes one, and an `allowed` entry grants nothing without `apply_patch`.
- **Policy resolution:** `normalize_tool_access` validates strict persisted policy; `resolve_tool_access` is the single resolver behind prompt/provider definitions and dispatch - mode selection, automatic activation (a declared follower is active while any of its sources is, `activation_sources(tool)`; Memory mode activates `memory`; grants activate theirs), constraints, `denied` as absolute veto, orphaned followers removed, mode `none` suppresses every activation path. `ToolAccess.fixed` (absent from public policy JSON; the Agent store sets it for the built-in Agents, `agent.md`, and an owner may set it for a temporary Agent) makes a `selected` list the whole Tool set: memory-mode and Session-grant Tools activate only when it names them, and nothing configurable outside it is added. Followers still follow the Tools it names, because each belongs to its sources' capability (the edit dialect of `apply_patch`, `background_tasks` beside the shell Tool and `subagent`, an MCP connection's remote Tools), and a denial still vetoes one (`test_availability.py`). Fixed sets therefore never list followers. Constraint `live_call` (`TOOL_CONSTRAINT_LIVE_CALL`) resolves a Tool only for a policy with `ToolAccess.live_call` set, which is runtime-only like `fixed` and set by the Agent store only for the two built-in Agents of a Live call; the Live Tools (family `live`, `core/tools/live.py`, opt-in) carry it, so no other Agent can get them, whatever its policy names (`model_tasks/live-operator.md` -> Live Tools).
- **Prompt-block seam:** `ToolPromptBlockRegistry` lets a Tool declare a System Prompt block (`id`/owner `tool:<name>`, rendered only when the Tool is effectively allowlisted; `requires_generated` makes static text render nothing while the named Producer renders nothing, `prompts.md` -> Data Model); the prompt domain imports no tool classes. Built-in `project` and `subagent` use dynamic blocks for current catalogs; a renderer may return a `RenderedBlock` whose `BlockCatalog` lets Chat announce a mid-epoch change entry by entry, because Chat pins every dynamic block's text per prompt epoch (`chat/request-building.md` -> Dynamic prompt blocks per prompt epoch).

Configurable Tools may declare `requires_opt_in=True`. They require an explicit name in `tool_access.granted` in addition to ordinary policy permission; All mode and materialized Project ceilings never grant opt-in. None and denials still win, and companions cannot follow an ungranted parent. Missing Tools retain stored grants. `tool.list` exposes the flag for the shared editor; raw wildcard/unfiltered definition and dispatch paths do not authorize opt-in Tools. Coverage: `tests/core/tools/test_availability.py`, `tests/core/tools/test_tools_registry.py` (registration rules), `tests/core/extensions/test_capabilities.py`.

## Registration and dispatch rules

- Names match `^[A-Za-z][A-Za-z0-9_]{0,63}$`. Registration compiles the canonical Draft 2020-12 contract up front and rejects invalid schemas, unknown families, or incoherent activation metadata before publishing (a followed Tool names one `activation_source` or a sequence of distinct ones, and is active while any of them is; `tool.list` reports several as a list); fixed-shape objects close by default while model-facing schemas set `open_input_schema=True` and omit `additionalProperties`. Either way a Tool's root `properties` are its complete parameter list: the contract treats an omitted root `additionalProperties` like `false`, and only an explicit schema/`true` or `patternProperties` accepts undeclared arguments (Extension and MCP schemas included). Families are comprehension/bulk-action metadata only - membership never implies activation.
- Contract compilation is memoized by the exact JSON content of its inputs, so the per-Provider-cycle contracts reuse one immutable compiled contract per unchanged definition and any content change compiles afresh. Inputs holding non-JSON values (for example tuples) always compile uncached, so the cache never changes whether a schema is accepted.
- Dispatch authorizes and readiness-checks, normalizes a deep copy of arguments against the cycle's exact input contract, validates unless the registered handler explicitly owns complete argument validation, executes, validates the envelope plus the executing Tool's retained result contract, and verifies finite JSON-serializability. Canonical dispatch records that selected result contract and the allowlist it checked the call against (for `can_call`) on the per-call ToolContext; Chat validation and Extension result hooks reuse it without resolving the live catalog again. Live catalog removal or replacement cannot change an already-started call's result validation. Shared normalization follows the repair rules below and always leaves meaningful operation validation in place; it drops an undeclared root argument whose value is null, `""`, `[]` or `{}` (it requests nothing); dispatch then runs a call without unknown fields it can run without and refuses the rest (Conventions -> Unknown fields). A validation failure reports every problem at once in Agent-readable sentences (`<tool> was not run: ...`): the field, the expectation, the received value, for a missing parameter its valid values when it has an `enum` (a first sentence that describes the values one by one ends mid-list; eval 2026-10-12, `terminal` `action`), else the first sentence of its description, a suggested parameter for an unknown name (never applied), and the parameter list whenever a name was missing or unknown. A call that arrived as exactly `{}` and is refused, by the owner's repair or by validation, lost its arguments on the way (mostly Tool-call markup a Provider could not read: 10 `powershell` calls in the 2026-10-11 review), so it gets `ToolContract.no_arguments_message()` instead: `<tool> was not run: the call arrived with no arguments at all. Send the complete call again.` plus the parameter list. A call the owner's repair emptied did send arguments and keeps the ordinary message. Coverage: `test_contracts.py::test_a_call_that_arrived_without_arguments_is_asked_for_again_complete`. Handlers do not repeat unknown-argument checks; they own conditional rules such as fields one action requires. A Tool may register `unadvertised_parameters` (name -> schema): root parameters its handler accepts without offering them, such as options copied from older conversation history (`web_fetch`) or a Participant's own identity echoed from reminders (Swarm). Dispatch validates them like advertised parameters, but they never appear in Provider definitions or argument errors. Aliases that an owner normalizer translates into advertised parameters need no declaration. Handler-deferred validation currently supports independently executed batches whose item errors must not reject valid siblings; complete validation remains the owner's responsibility. An invalid/non-serializable result raises `InvalidToolResultError`, distinct from argument errors, mapped to `invalid_tool_result`.
- **Failure codes follow the phase, not the exception type.** Whatever argument repair (`argument_normalizer`, shared normalization) and validation raise refuses the call as `ToolContractError` before the handler runs: `invalid_arguments` with the raised message unchanged (a bare `ValueError` from a normalizer needs no migration; a non-`ValueError` there is a defect, logged, and reads `<tool> was not run: <cause>`). `ToolContractError` (`contracts.py`) is the one refusal type: a handler raises it only before the call has any effect, and the `core/tools/arguments.py` helpers raise it too. Every other exception escaping a handler, `ValueError`, `JSONDecodeError` and `UnicodeDecodeError` included, is `tool_execution_error`, logged with its traceback: `<tool> failed while running: <cause> It is unknown how much of the call took effect. Check the current state before you call <tool> again.` (`<cause>` is the message, or the exception type name when the message is empty). One mapping, `tool_failure_for_exception` (`_tool_results.py`), serves ToolExecutor and Chat and never raises; an exception without a message gets one complete sentence per code (for example `Tool not allowed: <tool>.`). A handler that catches exceptions itself keeps the same rule: only its argument refusals become `invalid_arguments`; an operation failure after an effect may have started is not an argument error (terminal, process and channel_send catch `ToolContractError`, never `ValueError`). Test helpers that stand in for the executor map exceptions with `tool_failure_for_exception` (`tests/core/tools/tools_test_support.py::dispatch_as_executor`), so a test sees the code the Model reads. Coverage: `test_tools_execution.py::test_failure_code_follows_the_phase_that_raised`, `test_chat_loop_tool_failures.py`.
- An ungranted Session-scoped Tool fails `<tool>_unavailable` before allowlist checks; a matching grant still requires dispatch allowlist permission. Dispatch is not list-filtered by readiness but re-evaluates live -> `tool_not_ready` envelope (`retryable` from `Tool.readiness_retryable`, default false) instead of running.
- `deferred=True` keeps a Tool registered for policy, metadata, and dispatch while excluding it from Provider definitions and System Prompt Tool lists. Discovery owners deliver selected schemas through ordinary results; catalog changes must not promote deferred Tools implicitly.
- `catalog_visible=False` hides a Tool only from public catalog projections, including Extension capability lists and Project selection. Internal enumeration retains it for policy, collision detection, replacement, fingerprints and teardown; this flag alone neither grants access nor establishes Session scope. Public projections explicitly use `include_catalog_hidden=False`; the default preserves internal enumeration. Coverage: `tests/server/rpc/test_catalog_methods.py`, `tests/core/extensions/test_operations.py`.
- Provider-visible definitions expose only name/description/schema - never handlers, context, internal flags, or display metadata; Definition Profiles resolve per Agent from stable config (deterministic key, sorted set inputs, transient liveness excluded) and a `None` profile hides the Tool.
- `list_tools` filters registered -> allowed -> ready (readiness last, default off); `provider_definitions`/`prompt_definitions` default `ready_only=True`; `tool.list` intentionally includes not-ready/granted public Tools with full metadata so policy editors can explain states. At this boundary `allowed_tools=None`/`["*"]` mean all normal Tools, `[]` means none - the Project Tool Whitelist is deliberately stricter and rejects `"*"` (see `projects/resolution.md`).
- For a **config (Project) Agent**, the Project Tool Whitelist is the outer ceiling: scanned repository denials narrow it, a vBot override fully replaces the scanned policy but must stay inside the ceiling; `project.set` accepts only registered configurable Tools and keeps previously persisted unavailable names retain-or-remove.
- Internal tools bypass allowlist filtering and enforce their own domain rules. Same-turn failures are per-call envelopes, never Run failures; Run/provider/process/persistence failures stay outside this boundary. Result persistence preserves the Assistant's original call order even when a parallel group finishes out of order.
- Extensions register Tools via `api.register_tool(...)` after declaring families if desired; applied last during bootstrap, then ordinary Tools in every respect. Name collisions skip with diagnosis; invalid declarations isolate without blocking other capabilities.

## Conventions

- **Tool families** hand data to each other and change together with their guidance blocks and notifications: `read` -> `apply_patch` or `edit`/`write`; `search_files` -> `read`; `bash` -> `background_tasks` (a command that outlives its call continues in the background, delivers its result as a new message, and is listed, checked and stopped there) and `terminal` for programs that need input or a terminal; `subagent` -> `background_tasks` (list, status and stop of Sub-Agents); `subagent` with its block and completion delivery, and `status`; `web_search` -> `web_fetch`; `memory`, `skill`/`skill_manage` with the Skills prompt section, and `session_search`.
- Public and private Session Tools use dispatch normalization. The production Swarm probe checks independently prescribed calls, real registry results, and durable receipts.

- When vBot authors a filesystem path for Model consumption in Tool output, render separators as forward slashes (`C:/...`); resolution, persistence, input handling, and OS calls keep native `Path` semantics - never global text normalization.
- **Tool changes in a Session:** Chat keeps a Session's Tool list pinned per prompt epoch (`chat/request-building.md` -> Tool catalog per prompt epoch) and itself announces only which Tools exist: added, removed and On-demand Tools. A changed definition of a Tool the Session already knows is announced only for the parts the Tool names in `announce_changes` (a `register` keyword, also of `api.register_tool` and live Extension catalog declarations): `description`, `parameters` (any change of the parameter schema), or `parameters.<name>` (that parameter's schema or whether it is required); `definition_change_announced` compares them between the definition the Model knows and the current one. Without a declaration nothing is announced: the Session keeps its known definition, dispatch validates calls against it, and the handler answers what the current state no longer allows; the next prompt epoch pins the current definition. The owning Tool decides per part, since only it knows which changes the Agent needs before its next call. Declared today: `channel_send` (`parameters`: a Channel on a new platform brings that platform's fields) and the MCP connection Tools (`parameters.target`, which lists the remote Tool names). Coverage: `test_tool_epoch.py::test_a_tool_change_is_announced_only_for_the_parts_the_tool_names`, `test_chat_loop_tool_definitions.py::test_an_announced_tool_change_reaches_the_session_and_validates_calls`.
- A Tool may register a one-sentence, Model-facing `summary` (`register(..., summary=...)`, also `api.register_tool` and live catalog declarations; at most 200 characters, whitespace collapsed). It lists the Tool where its full definition is not shown: the On-demand Tool list of the System Prompt and the `on_demand` Tool-change note (`tools/load_tools.md`). `tool_summary(tool, description=None)` returns it, else the first sentence of the description (the Definition Profile's when given): cut at the first `. ` or line break, whitespace collapsed, capped at 200 characters with an ellipsis. Every Tool an Agent can load on demand declares one: a few words naming what the Tool is for, such as `Manage the user's calendar.`, not a list of what it can do; the list is paid on every request, and the full definition arrives with `load_tools`. The first-sentence fallback serves only Tools whose opening sentence is already that short (`apply_patch`, `edit`, `write`), Live Tools (never on demand) and third-party Extension Tools without one. The MCP connection Tool's summary is its description heading (`MCP connection <id>: <about>.`), which a catalog change leaves alone. A summary naming another Tool uses its Model name. Coverage: `test_tools_registry.py::test_summary_lists_a_tool_by_its_declared_text_or_first_sentence`; `test_runtime_wiring.py::test_loadable_tools_declare_a_summary_unless_their_first_sentence_serves` keeps the fallback list exact.
- A Tool may register a pure `argument_normalizer` for domain-specific repairs that must precede required-field validation. Dispatch invokes it on a deep copy after access/readiness checks, then applies the cycle's exact canonical contract normally. It changes no Provider schema or authorization policy.
- **Shared argument repair:** `ToolContract.normalize_arguments` (`contracts.py`, implemented in `_argument_repair.py`) normalizes copied schema-guided value encodings: numeric counts without rounding, boolean aliases, JSON containers, and scalar arrays. Accepted text and arbitrary object keys remain unchanged. Generic repair does not rename fields, rewrite enums, unwrap business objects, or omit explicit empty/null values. Conflicting duplicate encoded JSON keys and multiple valid conversion meanings fail rather than selecting a value by branch order. One call shape is read before the owner's `argument_normalizer`, for every Tool with `coerce_arguments`: a call sent as one name/value pair is the parameter it names (`ToolContract.read_name_value_pair`, called by `_checked_arguments`), so `{"name": "command", "value": "ls"}` reaches the owner as `{"command": "ls"}` and the owner's repairs apply to the value. It applies only when neither `name` nor `value` is a parameter of the Tool (advertised or unadvertised), `name` is exactly a parameter the Model request offered, and every other field is another parameter or repeats this one with the same value; anything else stays as sent and is refused for its unknown fields. Silent, as a representation repair. Evidence, the 2026-10-12 Swarm run: one `powershell` command arrived as such a pair and ran in the regular field right after; no other call in the Session database had the shape. Coverage: `test_contracts.py::test_a_call_sent_as_one_name_value_pair_runs_as_that_parameter`.
- **Unknown fields:** a root field that is not a parameter (nor an `unadvertised_parameters` entry) of a Tool with a closed parameter list either runs without effect or refuses the call, by one rule for every Tool and action; vBot has no per-call read-only marker, and action Tools mix reads and changes. `commentary` (a label some Models attach to the channel of their output) is dropped silently. Any other unknown field is dropped before the handler (`ToolContract.drop_inert_fields`, called by `_checked_arguments` in `tools.py`), and the result says so, unless ignoring it could give an effect the Agent did not ask for. It stays, and validation refuses the call before any effect, when its name is close to a parameter (contains one or is a typo of one: the "Did you mean" suggestion), when it is a parameter of the Tool that this Model request's definition left out (`withheld`), when a word of its name reads as a mode, condition or safety switch (`dryRun`, `mode`, `force`, `if_exists`), as a target (`thread_id`, `path`, `to`) or as content (`message`, `body`, `patch`) (`_DECISIVE_WORDS`), or when its value is content or call fields rather than a label: an object, or text with a line break or longer than 80 characters. A refused call names every unknown field, the dropped ones included. The dropped names reach the Agent as `ignored_fields_note`: `"transition" had no effect: swarm_board has no such parameter.` A success carries it first in `data.note` (`with_call_note` in `_tool_results.py`, before an existing string note), a failure envelope and a handler's `ToolContractError` end their message with it. `note` is therefore a reserved data field: every Tool that sets one keeps it a string, and `validate_success_data` checks a result against a schema that does not declare `note` without it, so closed result schemas (`load_tools`, `analyze_image`) admit it. Extension Tools get the note through the same dispatch, rendered as a `note:` line of the result. Evidence, the 2026-10-12 Swarm run: 21 calls were refused for unknown fields, among them complete swarm_board posts with `transition: "support wiring"` (x3) and `commentary: "analysis"`, which now run; the rule keeps refusing a post whose text came as multi-line `retext`, `action` on apply_patch, `path` on swarm_wiki and the `*_id` references. Coverage: `test_contracts.py::test_dispatch_rejects_invalid_arguments_before_handler`, `::test_an_unknown_field_without_effect_is_left_out_and_the_result_says_so`, `::test_a_parameter_the_model_request_left_out_is_never_ignored`; Extension Tools in `test_capabilities.py` and `test_examples.py`.
- **Quote repair of JSON text:** an array or object argument sent as JSON text that does not decode is read once more (`_argument_repair.py::_repaired_json_text`; some Providers pass an argument they could not decode on as text): a raw line break, tab or other control character inside a string stands for itself, and the stray `"` inside the text of the schema's declared fields are escaped (`core/utils/json_text.py::escape_inner_quotes`). A text that writes line breaks inside its strings both raw and as `\n`/`\r` escapes gets no reading: a raw one there can be a slip of the output (Swarm 2026-10-12: one raw break inside a word among 27 escaped ones). Inside such a field's string, a `"` ends the text only where `}` or `]` follows, a `:` before a value (`"`, `{`, `[`, a number, `true`, `false`, `null`), a comma before a string, object or array, a comma before a declared field name that lost its opening quote, or the end of the text; every other `"` belongs to the text, since read as structure it would leave text where JSON needs a value (`got "x": not a number`). Closing brackets (`]`, `}`) after the end of a complete value close nothing it opened and are left out (Swarm 2026-10-13: an `edits` array followed by one `}`); any other text there, such as `, {...}`, keeps the text refused, since it can be a value meant to run. The text is read with and without its quotes escaped; the value counts only when exactly one distinct reading is valid for the field's schema and every object in it uses only declared fields (an object schema with `properties` and no `additionalProperties`/`patternProperties` counts as closed); a repeated field or an ambiguous conversion also discards it. Otherwise the original text goes on to validation unchanged; `decode_json_argument` then raises the first break past the raw control characters (a cut-off text reports its end, not an earlier raw line break), else the strict decoding error. Schemas without declared field names (string arrays such as `search_files` `patterns`) are never repaired. Silent, as a representation repair. Owner field normalizers reach the same reading through `decode_json_argument(text, schema)` (edit's `edits`, `tools/edit.md`). Replay 2026-10-11 over all 249 live calls with JSON-looking text in a field: 5 decoded differently than before, all `edits`, each identical to the reviewed manual reading; the rest unchanged. Replay 2026-10-12 over the 18 live `edit` calls with JSON-looking `edits` text, for the raw control characters and the `:` rule: 1 more decoded (raw line breaks and a `"` before `:` and text; 3 edits, checked against the reviewed reading), the rest unchanged; no other live array or object argument failed strict decoding where these rules apply. Coverage: `test_contracts.py::test_slips_in_json_text_are_read_only_into_a_value_the_schema_accepts`.
- **Owner-selected call repair:** `call_syntax.py` is the public call-syntax toolkit for every Tool owner outside the registry as well (Extensions, the Live Tools, Subagent interpretation): `spelling`, `SpellingAliases`, `PLACEHOLDER_WORDS`/`is_placeholder`, and `normalize_call_arguments`. `normalize_call_arguments` is used by `argument_normalizer` hooks and item-validating handlers. It repairs one declared call object's field formatting, explicit field aliases, and known wrappers; enum formatting and empty-as-omission require explicit field selection, and so does `wrapping_fields`: a selected field whose value is an object of the call's own fields (or JSON text of one) wraps those fields, so owners select only fields whose real values can never be such an object (apply_patch's `patch`). Optional per-field normalizers run on canonical field names before shared schema conversion and alias conflict checks (search_files uses this for encoded argument lists and output synonyms). It never applies edit-distance matching and never recursively treats nested payloads as call syntax. Conflicts are checked before omission. Batch owners invoke it separately per item to preserve independent execution. Target ids are not vocabulary enums.

The registry is read from worker threads (prompt assembly) while the loop registers and removes Tools, so every ToolRegistry mutation publishes a new Tool and family dict instead of changing the current one; keep that copy-on-write rule when adding a mutation, or a listing in progress fails with "dictionary changed size during iteration". Live Extension catalogs publish atomically through `ExtensionOperations.replace_tools`; a ToolRegistry revision change makes a running Run compare the live catalog with its prompt epoch's Tool pin at the next request boundary and announce the difference as System Reminders, while the Tool list itself stays pinned until Compaction (`chat/request-building.md` -> Tool catalog per prompt epoch). Producers never announce Tool changes themselves. Removing a catalog retires its authority. Definition-profile context includes the exact Agent/Project identity. See `extensions/mcp.md` for connection opt-ins and remote schema changes.

## Constraints & Gotchas

Tool execution normally consumes the shared 500-slot semaphore (also the default per-batch limit). The registered `subagent` coordinator opts out via `execution_slot_required=False`: waiting for a child Run must not hold a slot that its Tools need. Per-batch concurrency and Sub-Agent admission limits still apply. Chat's emitting registry delegates this execution policy.

- Non-envelope, non-serializable, or schema-violating successful results reject as `invalid_tool_result` without aborting the Run.
- Disallowed normal Tools fail at dispatch even if a provider asks for them.
- Chat alone derives Session Grants during request building; static restrictions and live denials stay dispatch-only and must never filter provider definitions or mutate prompt assembly.
- Relative paths resolve from `effective_cwd` (Project repo else Workspace); absolute bypass unless a specific Tool forbids. File tools and `bash` use it; `memory` deliberately stays on Workspace (identity home, not project-relative).
- A live per-name denial resolver runs before hooks and handler for every sibling; the dispatcher also carries that resolver and the Run Tool restriction through ToolContext for delegated calls. Denial returns `tool_not_allowed` without side effects.
- A Tool announced to the Model as removed in the current prompt epoch (`ToolDispatchContext.removed_tool_names`, `chat/request-building.md`) fails first, after only a Provider-rejected call and before the denial resolver, hooks, handler and registry lookup, with `tool_removed` (retryable false): `Nothing was run: the Tool <name> was removed from your Tools in this Session. Use your other Tools, or tell the user if the task needs <name>.` An unregistered removed Tool therefore reports its removal instead of `tool_not_found`, and name resolution treats removed names as registered so a call to one is never remapped to another Tool.

- `ToolContext.resolve_path` follows host path grammar without filesystem-dependent fallback. Windows double quotes may wrap a path because they cannot be literal filename characters; single quotes remain literal. POSIX quotes and backslashes remain literal even when a different unquoted/slash-separated file exists. Path objects remain literal. A path containing NUL raises `ToolContractError` (`<tool> was not run: the path ... contains a NUL character ...`) before any filesystem access, whether or not the host's `Path.resolve` would raise; every caller resolves before its effect, and callers that catch `ValueError` or `ToolContractError` pass the message through (`test_read.py::test_read_refuses_invalid_arguments_before_reading`). Scope, read-state, and mutation checks still use the resolved target. `follow_final_link=False` resolves only the parent, for operations on a link entry itself (apply_patch Delete/Move); `is_link_entry` (a path) and `is_link_status` (unfollowed metadata, such as search traversal's `DirEntry` stat) in `_tool_context.py` are the shared symlink-or-junction test (`Path.is_symlink` misses junctions; reparse tags exist only on Windows, so elsewhere only symlinks count).

- Renaming a Tool or one of its parameters reaches beyond the definition: `ToolDisplay` summaries and hidden arguments, WebUI rendering of historical calls, E2E fake-provider calls, generated Tool catalogs, persisted Tool Access Policy names, and Skills or prompts that teach the call shape. Inventory them before the change; recognizable older call shapes stay interpreted. Example: the shell's `mode` became `run_in_background` (2026-10-11), which reached `scripts/fake-provider.mjs`, `scripts/tool_lab/cases/shell.json` and the playwright-cli Skill (`resources/skills/playwright-cli/SKILL.md`); `mode` stays an accepted alias (`tools/shell.md`). Core names two Extension Tools: the file Tools' errors for a Swarm Wiki page number or Board post sent to them name `swarm_wiki` and `swarm_board` calls (`core/tools/_swarm_references.py`, `tools/read.md`), so renaming those Tools or their `action`, `page_id` or `message_id` parameters updates that module.
