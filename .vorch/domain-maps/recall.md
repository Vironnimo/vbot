# Recall

Backend-selected read model for discovering content in persisted chat Sessions. Canonical Session storage stays owned by `core/sessions/`; curated durable facts stay owned by `core/memory/`.

## Overview

One Agent-facing Tool: `session_search` requires a query and returns backend-ranked excerpts with bounded canonical conversation context. Optional Session scope supports focused follow-up searches. Session listing, full transcripts, and exact Tool Results are taught by the bundled `vbot-cli` Skill through CLI and read-only SQLite recipes; there is no `session_read` Tool.

`core/tools/session_search.py` owns Tool definitions, validation, execution and the final visibility recheck of hit Sessions; `_session_recall_results.py` holds internal bounded result projection, conversation context and descriptors under the same owner.

The selected backend fixes at Tool registration. The selectable first-party backends are `sqlite_fts`, `vector`, and `hybrid`; `sqlite_fts` is the Built-in default. `Runtime.reload_recall_backend()` rebuilds the registry from `settings.recall.backend` and re-registers the Search Tool with the resolved name; an unknown name or non-default backend construction failure falls back to `sqlite_fts` (recording the resolved name so description and behavior align). Failing to construct `sqlite_fts` itself is fatal; search inside a constructed SQLite backend may still degrade to the Session store's substring scan when the derived index is unavailable.

## Terms

Session and Tool terms live in `.vorch/GLOSSARY.md`.

### Semantic Recall
**Definition:** Meaning-based search using vector embeddings instead of keywords - a session about "vehicles" matches "cars". Enabled via `recall.backend: vector` plus a configured `text_embedding` model.
**Not:** Keyword search (that's `canonical_scan`/`sqlite_fts`), curated memory, or session browsing.

### Passage
**Definition:** A source-derived overlapping span of eligible canonical Message text - the retrieval and fusion unit of semantic and Hybrid search - carrying stable Message boundaries and offsets so results point back exactly.
**Not:** A Message, a Session summary, or an independently persisted source of truth.

## Search Contract

- `RecallSearchCapabilities` declares the active backend's result unit, Agent-facing texts, literal-match support, ordering, and role-filter meaningfulness; one capability value drives both Tool texts and declared defaults while its five public fields stay stable across backends.
- `RecallSearchRequest` normalizes scope (agent/project, Recall visibility via `include_subagents`, excluded Sessions), query, time range, roles, literal mode, order, and pagination into the shared backend contract. Every backend admits only Sessions whose Session-store Recall visibility (see `sessions.md`) the request allows: `conversation` always, `subagent` only with `include_subagents`, `hidden` never. Explicit exclusions name individual Sessions only; the Agent-facing Tool always requests ten results and excludes just the current conversation. Filtered/paginated variants stay lower-layer capabilities, never public Tool controls.
- Hits are backend-ranked Messages or Passages with canonical source identifiers; raw scores never leave Recall. Pages carry deterministic ranking slices, continuation state, candidate counts, and optional explicit degradation. Continuation snapshots bind the backend, query, scope, filters, ordering and canonical history; offset and page size may vary within that selection. Every request scopes by `ToolContext.project_id`, never a model-supplied argument - derived indexes key scope separately so equal Session UUIDs cannot collide.
- All built-in and Extension backends implement `RecallBackend.search_capabilities` and `search_page`; registry construction rejects missing methods or invalid capability values. Synchronous search methods run off the event loop. Session listing and exact reads are outside the Search Tool; the old browse/overview/search/scroll API and payload adapters are removed.

## Passage Policy

Eligible input comes only from default conversation roles (`user`, `assistant`, `compaction_checkpoint`) - Tool Results, reasoning, Tool arguments, errors, notes, Skill contexts, and persisted Recall results are excluded. Only canonical content text contributes; Compaction summaries are built as separate Passages so they can be labeled reliably. Text is used verbatim (no whitespace rewriting); Passages are 1,500-char windows with 200-char overlap, so long Messages become multiple Passages instead of truncating. Each records exact text, policy-derived stable id, boundary Message ids/timestamps/roles, and in-message offsets; fusion keys id together with `session_id` because forks share Message ids. Search excerpts are presentation-only (capped at 1,800 characters within a 50 KiB result budget); canonical identifiers and partial User/Assistant context support focused follow-up searches or Skill-guided inspection. `PASSAGE_POLICY_VERSION` feeds both Recall projection versions, so a policy change rebuilds both derived indexes (Passage Catalog).

## Passage Catalog

`core/recall/_passage_catalog.py` owns the catalog both derived Passage indexes hold (Passage FTS and vector), each in its own kernel disposable database (`database.md`) opened through `DisposableDatabase` and used only through the async `read`/`write` variants, so no SQLite work runs on the Event Loop. Blocking Session reads (refresh planning, scope reads, `canonical_scan` and Passage FTS pages) run on the Session database's worker pool through `ChatSessionManager.run_async`, not `asyncio.to_thread`. Time filters (`time_bounds`) compare the Passages' boundary timestamps, the Session's canonical stored text, directly with the canonical form of the bound. Tables: `indexed_sessions` (one freshness stamp `(generation_id, history_revision)` per Session, recorded even for Sessions without Passages), `passages` (stored once per Recall scope under `passage_key`, a hash of Passage id, text hash, boundary Message ids, timestamps and roles - the id alone is insufficient because a growing tail window keeps its id) and `passage_views(session_ref, passage_ref, owned)`. Passages are built over each Session's complete current view, so a fork and its origin build identical Passages over shared history and share the rows; `owned` marks a Passage whose last Message is one of the Session's own entries (position >= `SessionReadBatch.inherited_count`).

- Refresh (once per search and arm): one stamp read prunes Sessions that left the complete live scope and finds the request's candidates whose stamp changed; only those are reread on the Session database's worker pool (`load_since(None)` returns history and version atomically) and diffed by `passage_key`. One write transaction applies it: compare-and-set on each stamp (a stamp that moved since planning is skipped), new Passages and views, changed `owned` flags, and deletion of Passages no Session shows. An excluded Session catches up when a later search includes it. Deleting an origin materializes its entries into descendants and bumps their history revision, so they are reindexed and then own that history.
- Attribution: a Passage matches only when a candidate Session shows it, and its hit is reported for exactly one candidate, the highest `(owned, creation_order, session_id)`: the owner when it is eligible and still shows it, else the newest eligible Session that shows it (`RecallScope.creation_orders` from `list_history_revisions`). This mirrors store search (`sessions/search.md`), so a fork and its origin never both return shared history. Limits: attribution works per Passage window, so a window straddling the fork point, or a tail window of an origin that grew after the fork, differs by key and can surface once per side as a near-duplicate; history materialized into several descendants is reported once, for the newest.
- Recovery: `PassageCatalog.recovering` discards a damaged database (`projection_failure` is `rebuild`) and runs the operation once more; busy or unavailable never discards (writes wait 5 s, then fail as busy); canonical read failures propagate unchanged. `projection_version(layout) = layout + PASSAGE_POLICY_VERSION - 1`: both counters started at 1 with Generation 1 and only grow.

## Backends

### Internal `canonical_scan` backend

Not registered or selectable in Settings; `CanonicalSessionRecallBackend` is also the base whose Message page shaping `sqlite_fts` reuses. It calls `ChatSessionManager.search_messages(use_fts=False)`: the Session store orders eligible current entries globally by their canonical `created_at` text in SQL (the requested order, newest first by default; ties by entry key), checks each candidate's conversation text with case-insensitive substring matching (`telegram` matches inside longer words; the Tool uses `all_terms`), and stops at one hit beyond the page, so `has_more` is exact. Scope, visibility, role and time filters apply in SQL before the budget; at most 10,000 candidates are checked, and a page that budget cut short is degraded/partial. No Session history is loaded or decoded. Continuations bind to a generation-aware selection digest so changed arguments, recreated Sessions, or changed history fail rather than mix content.

### `sqlite_fts`
Lexical search over Sessions-owned external-content FTS inside `<data_dir>/sessions.db`: `entries_fts` indexes searchable current entries with the standard tokenizer, and `entries_fts_trigram` provides substring matching over User, Assistant and Compaction-checkpoint text only, so bulk Tool output is not indexed twice. There is no mirrored searchable-text table. Each stored entry is indexed and checked once however many forks show it; a hit is reported for the Session that stores it when that Session is eligible and still shows it, else for the newest eligible Session that inherits it (`sessions/search.md`). Conversation searches use trigram whenever every term has at least three characters; otherwise standard FTS applies whole-token matching to the query. The FTS indexes hold only content and extracted Content Block text, and the column filter restricts matching to them before the candidate limit. Each ordinary Search availability check reads only lifecycle/version/stale/high-water markers; canonical coverage anti-joins belong to startup repair and explicit operator verification, not the Search path. The backend asks `ChatSessionManager.search_messages` for one hit more than the page needs. FTS only enumerates candidates in the requested order (bm25 rank, or Message time for newest/oldest); every candidate's conversation text is checked with the literal case-insensitive matcher before it counts, so pages are full and `has_more` is exact even when standard FTS over-matches (a `C#` query searches the token `c`). At most 10,000 candidates are checked; typed Search pages explicitly report degraded/partial results when that budget cannot prove complete coverage instead of presenting a false complete empty result. A healthy zero-result public Tool search that excludes Tool rows returns empty without scanning; lower-level requests that include Tool rows retry a zero-hit FTS search as a substring scan because the trigram index deliberately omits Tool rows. A stale, unavailable, or unsupported integrated index degrades to the store's SQL substring scan (newest first for relevance, otherwise the requested order; the degradation reason names the order used), and FTS corruption detaches the derived indexes without blocking canonical writes. Scope, Recall visibility, Session, exclusion, role, and time filters execute in SQL before the bounded candidate limit; time filters are canonicalized and compared with the stored canonical UTC text, so `Z`, `+00:00`, equivalent offsets, and fractional precision remain equivalent. Hits carry the matched conversation text from a narrow keyed projection without decoding Messages, and result shaping reads only targeted Session descriptors and bounded conversation context, never complete histories. Skill-context notes are never searchable; persisted Recall results are never indexed, and the literal check reads them as empty text, so Tool-inclusive searches cannot match them. A separate Passage FTS at `<data_dir>/recall/session_index.sqlite` (kernel disposable projection `recall_index`, `sqlite_fts.recall_index_database_spec`) remains only for Hybrid's literal Passage arm until integrated Passage FTS lands; it is never authoritative. It holds the Passage Catalog; `passages` feeds two external-content FTS tables kept in step by triggers: `passages_fts` (trigram) serves queries whose every term (or phrase) has at least three characters, `passages_fts_tokens` (unicode61) serves all others with whole-token candidates. The kernel cannot declare virtual tables, so the spec's `after_open` creates missing FTS tables and triggers and fills a new FTS table from `passages`. Ranked FTS candidates are restricted to Passages the request's candidates show, checked with the literal matcher before they count, and attributed to one Session, so Passage pages are full and `has_more` is exact. A damaged index is discarded and rebuilt once within the search; one that still fails, or a busy index, fails the literal arm; there is no history-scan fallback.

### `vector`
One sqlite-vec cosine index at `<data_dir>/recall/session_passage_vectors.sqlite` (kernel disposable projection `recall_vectors`, `vector_store.recall_vectors_database_spec`; its `connection_setup` loads sqlite-vec on every connection). Besides the Passage Catalog it holds a vec0 table `passage_vectors` (rowid = `passage_ref`, partitioned by Recall scope, start/end timestamps as microseconds; a Passage timestamp that is not canonical is damage (`DatabaseCorruptError`), so the store is discarded and rebuilt instead of guessing an instant), a singleton `store_header` pinning provider/model/actual-model/embedding-space fingerprint/index policy/dimension, and `pending_vectors`, the queue of Passages without a vector (an insert trigger on `passages` fills it). Vectors from different actual models never mix: the first space is pinned when vec0 is created, and another space (`use_space`) drops vec0, replaces the header and requeues every stored Passage while keeping the catalog. A header without its vec0 table is damage. Typed search returns pure semantic top-K Passages by cosine distance without literal revalidation, per-session collapsing, universal cutoffs, or keyword fallback; missing embedding config or store failure yields stable `semantic_unavailable`. The scope partition, the candidate filter (`rowid IN` the Passages the request's candidates show) and time filters execute inside the vec0 KNN before top-K, so ineligible Passages cannot starve eligible ones; each hit is then attributed to one Session (Passage Catalog).

Search flow: the shared scope read (`CanonicalSessionRecallBackend._read_scope`: one `list_history_revisions` query on the Session database's worker pool) yields every live Session version and Recall visibility of the scope, the request's candidates with their creation order, and the continuation snapshot; with a pinned header a stale continuation fails before any embedding. The query embeds first and pins the live dimension and actual model every document vector of the search must match. The catalog then refreshes; a newly stored Passage reuses any stored vector with the same text (another Session's included), so only new texts wait in the queue. A search embeds at most one bounded batch (`_EMBED_BATCH_SIZE` = 64 distinct pending texts of its candidates and period, newest first, skipping texts the background task is embedding); a failed batch is logged and the search answers from what is indexed. While eligible Passages still wait, the page is `degraded` with `SEMANTIC_PARTIAL_REASON` (partial coverage, like a fallback page) and the backend starts one background task that drains the queue of every scope in batches of 64 (one provider call, then one short write) until it is empty, the space changes or a failure stops it; the next search with waiting Passages restarts it. An embedding-space change is backfilled the same way. There are no asyncio locks: the kernel serializes writes, and no search waits for the backfill. Document vs query embedding purposes are distinct (OpenRouter maps them explicitly); context overflow splits multi-input batches recursively, never rewriting stored text. One normalized Usage summary emits per search (`typed_search`) and per background run (`recall_backfill`). A damaged store is discarded and rebuilt once while a search prepares; damage found by KNN or the background task discards it for the next search.

### `hybrid`
Reads the scope once and prepares Passage FTS and Vector concurrently over it once per search - the literal arm reconciles its Passage index, the semantic arm reconciles freshness and embeds the query - then fuses ranks via Reciprocal Rank Fusion (`k=60`) - never raw score mixing. Candidate depth grows until every selected hit's arm contributions are resolved and the requested prefix cannot be displaced under the unseen-score bound, preserving exact ordering and source labels as well as membership; each deeper pass reruns only the two ranked queries. An arm that fails to prepare or rank stays out for the rest of the search with explicit degradation; both failing returns `hybrid_unavailable`. A semantic arm that answered before its background indexing finished also degrades the fused page (`hybrid._degradation_reason`: keyword matches complete, or, when the literal arm failed, results incomplete). Cursors snapshot both arms - source or backend changes invalidate continuation rather than mixing rankings.

## Lifecycle & Removal

Canonical Messages always come from `ChatSessionManager`; Recall modules construct no Session paths and index/read only each Session's current view (`load_since(None).active_messages`, `recall_context`), so entries superseded by a history edit cannot be rediscovered. Candidate and freshness enumeration uses version rows (`list_history_revisions`, which carry each Session's Recall visibility) rather than Session summaries or open-ended metadata; complete active histories are loaded only when a stale Session must be re-projected for a derived index. Vector and Hybrid hits carry canonical Passage boundaries and do not hydrate a complete Session per hit. Freshness comparisons use `(generation_id, history_revision)`, never revision alone, so archive/recreate cannot reuse stale rows. FTS/vector files under `<data_dir>/recall/` are kernel disposable projections - rebuilt on a projection version change or damage, never migrated. Backends holding them implement `SupportsClose` (`aclose()` stops background indexing and waits; `close()` cancels it): `RecallIntegration` closes a backend replaced by `reload_recall_backend()` and the active one on Runtime shutdown. Deleted Sessions evict immediately from fts/vector/hybrid (`canonical_scan` needs nothing because it scans current canonical state). A Session that vanishes between listing, freshness lookup, and Vector hydration is skipped; a stale derived hit never fails the whole search and is removed by a later search's complete-scope pruning.

Vector regressions in `tests/core/recall/test_vector*.py` separate typed search, index lifecycle (including incremental refresh), embedding batching, Passage projection and scope isolation. `vector_helpers.py` owns shared fake embedding engines (counting document and query inputs), stored-Passage row and pending-queue readers, canonical Session setup, `forbid_event_loop_calls` (fails synchronous Session store calls made on the Event Loop) and `forbid_database_calls_on_loop` (fails blocking kernel `Database.read`/`write` calls on the Event Loop or on any thread other than that database's own worker pool). Tests that start a search with waiting Passages await `backend._backfill_task` so no background task outlives them.

## Constraints & Gotchas

- Never expose backend tuning just to make payloads look alike: capabilities describe real behavior while the public Tool keeps one compact field set with declared defaults.
- Search returns selected excerpts and explicitly partial context, not a transcript. The Skill owns guidance for extended read-only SQLite inspection; runtime Recall callers continue to use `ChatSessionManager`.
- Do not deduplicate Passages by Session - multiplicity is Vector/Hybrid semantics. Do report each shared Passage once: attribution, not per-viewer rows, decides the Session. Do not move structural filters after KNN - post-filtering global top-K produces false empty pages. Do not fuse raw FTS scores with vector distances.
