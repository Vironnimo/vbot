# Recall

Backend-selected read model for discovering content in persisted chat Sessions. Canonical Session storage stays owned by `core/sessions/`; curated durable facts stay owned by `core/memory/`.

## Overview

One Agent-facing Tool: `session_search` requires a query and returns backend-ranked excerpts with bounded canonical conversation context. Optional Session scope supports focused follow-up searches. Session listing, full transcripts, and exact Tool Results are taught by the bundled `vbot-cli` Skill through CLI and read-only SQLite recipes; there is no `session_read` Tool.

`core/tools/session_search.py` owns Tool definitions, validation, execution and the final visibility recheck of hit Sessions; `_session_recall_results.py` holds internal bounded result projection, conversation context and descriptors under the same owner.

The selected backend fixes at Tool registration. The selectable first-party backends are `sqlite_fts`, `vector`, and `hybrid`; `sqlite_fts` is the Built-in default. `Runtime.reload_recall_backend()` rebuilds the registry from `settings.recall.backend` and re-registers the Search Tool with the resolved name; an unknown name or non-default backend construction failure falls back to `sqlite_fts` (recording the resolved name so description and behavior align); an unknown name warns once per configured value, not on every reload. Failing to construct `sqlite_fts` itself is fatal; search inside a constructed SQLite backend may still degrade to the Session store's substring scan when the derived index is unavailable.

`core/runtime/_recall.py::RecallIntegration` owns the one Passage index (`core/recall/passage_index.py`) and the one `SemanticIndexer` (`core/recall/semantic_indexer.py`) per Runtime; both outlive backend reloads. `RecallBackendRegistry.with_builtins(passage_index=..., on_waiting=...)` hands that index to `vector` and `hybrid`; a backend built without one (scripts, tests) opens and owns its own. Extension backends keep receiving only `RecallBackendContext`.

## Terms

Session and Tool terms live in `.vorch/GLOSSARY.md`.

### Semantic Recall
**Definition:** Meaning-based search using vector embeddings instead of keywords - a session about "vehicles" matches "cars". Enabled via `recall.backend: vector` or `hybrid` plus a configured `text_embedding` model.
**Not:** Keyword search (that's `canonical_scan`/`sqlite_fts`), curated memory, or session browsing.

### Passage
**Definition:** A source-derived overlapping span of eligible canonical Message text - the retrieval and fusion unit of semantic and Hybrid search - carrying stable Message boundaries and offsets so results point back exactly.
**Not:** A Message, a Session summary, or an independently persisted source of truth.

### Embedding space
**Definition:** The provider, configured model, binding fingerprint (`EmbeddingSpaceIdentity`), index policy and dimension the Passage index pins in `store_header`. Vectors of two spaces never mix; leaving a space drops every vector. The model name the provider reports serving is recorded but is not part of the space: a router such as OpenRouter answers one configured model from several hosts that report different names (seen live with `baai/bge-m3`), and treating each name as a new space wiped the index on every alternation.

## Search Contract

- `RecallSearchCapabilities` declares the active backend's result unit, Agent-facing texts, literal-match support, ordering, and role-filter meaningfulness; one capability value drives both Tool texts and declared defaults while its five public fields stay stable across backends.
- `RecallSearchRequest` normalizes scope (agent/project, Recall visibility via `include_subagents`, excluded Sessions), query, time range, roles, literal mode, order, and pagination into the shared backend contract. Every backend admits only Sessions whose Session-store Recall visibility (see `sessions.md`) the request allows: `conversation` always, `subagent` only with `include_subagents`, `hidden` never. Explicit exclusions name individual Sessions only; the Agent-facing Tool always requests ten results and excludes just the current conversation. Filtered/paginated variants stay lower-layer capabilities, never public Tool controls.
- Hits are backend-ranked Messages or Passages with canonical source identifiers; raw scores never leave Recall. Pages carry deterministic ranking slices, continuation state, candidate counts, and optional explicit degradation. Continuation snapshots bind the backend, query, scope, filters, ordering and canonical history; offset and page size may vary within that selection. Every request scopes by `ToolContext.project_id`, never a model-supplied argument - derived indexes key scope separately so equal Session UUIDs cannot collide.
- All built-in and Extension backends implement `RecallBackend.search_capabilities` and `search_page`; registry construction rejects missing methods or invalid capability values. Synchronous search methods run off the event loop. Session listing and exact reads are outside the Search Tool; the old browse/overview/search/scroll API and payload adapters are removed.

## Passage Policy

Eligible input comes only from default conversation roles (`user`, `assistant`, `compaction_checkpoint`) - Tool Results, reasoning, Tool arguments, errors, notes, Skill contexts, and persisted Recall results are excluded. Only canonical content text contributes; Compaction summaries are built as separate Passages so they can be labeled reliably. Text is used verbatim (no whitespace rewriting); Passages are 1,500-char windows with 200-char overlap, so long Messages become multiple Passages instead of truncating. Each records exact text, policy-derived stable id, boundary Message ids/timestamps/roles, and in-message offsets; fusion keys id together with `session_id` because forks share Message ids. Search excerpts are presentation-only (capped at 1,800 characters within a 50 KiB result budget); canonical identifiers and partial User/Assistant context support focused follow-up searches or Skill-guided inspection. `PASSAGE_POLICY_VERSION` feeds the Passage index's projection version, so a policy change rebuilds it (Passage Catalog).

## Passage Catalog

`core/recall/_passage_catalog.py` owns the catalog the Passage index holds. The index is one kernel disposable database (`database.md`) opened through `DisposableDatabase` and used only through the async `read`/`write` variants, so no SQLite work runs on the Event Loop. Blocking Session reads (refresh planning, scope reads, `canonical_scan` and Passage FTS pages) run on the Session database's worker pool through `ChatSessionManager.run_async`, not `asyncio.to_thread`. Time filters (`time_bounds`) compare the Passages' boundary timestamps, the Session's canonical stored text, directly with the canonical form of the bound. Tables: `indexed_sessions` (one freshness stamp `(generation_id, history_revision)` per Session, recorded even for Sessions without Passages), `passages` (stored once per Recall scope under `passage_key`, a hash of Passage id, text hash, boundary Message ids, timestamps and roles - the id alone is insufficient because a growing tail window keeps its id) and `passage_views(session_ref, passage_ref, owned)`. Passages are built over each Session's complete current view, so a fork and its origin build identical Passages over shared history and share the rows; `owned` marks a Passage whose last Message is one of the Session's own entries (position >= `SessionReadBatch.inherited_count`).

- Refresh: one stamp read prunes Sessions that left the given live set and finds the candidates whose stamp changed; only those are reread on the Session database's worker pool (`load_since(None)` returns history and version atomically) and diffed by `passage_key`. One write transaction applies it: compare-and-set on each stamp (a stamp that moved since planning is skipped), new Passages and views, changed `owned` flags, and deletion of Passages no Session shows. A search refreshes once for its own candidates and prunes by the complete live scope; an indexing pass refreshes every Recall-visible Session of every live scope, so hidden Sessions are pruned there (Semantic Indexing). Deleting an origin materializes its entries into descendants and bumps their history revision, so they are reindexed and then own that history.
- Attribution: a Passage matches only when a candidate Session shows it, and its hit is reported for exactly one candidate, the highest `(owned, creation_order, session_id)`: the owner when it is eligible and still shows it, else the newest eligible Session that shows it (`RecallScope.creation_orders` from `list_history_revisions`). This mirrors store search (`sessions/search.md`), so a fork and its origin never both return shared history. Limits: attribution works per Passage window, so a window straddling the fork point, or a tail window of an origin that grew after the fork, differs by key and can surface once per side as a near-duplicate; history materialized into several descendants is reported once, for the newest.
- Recovery: `PassageCatalog.recovering` discards a damaged database (`projection_failure` is `rebuild`) and runs the operation once more; busy or unavailable never discards (writes wait 5 s, then fail as busy); canonical read failures propagate unchanged. `projection_version(layout) = layout + PASSAGE_POLICY_VERSION - 1`: both counters started at 1 with Generation 1 and only grow.

## Passage Index

`<data_dir>/recall/passage_index.sqlite` (kernel disposable projection `recall_index`, `passage_index.passage_index_database_spec`; `connection_setup` loads sqlite-vec on every connection). It is never authoritative and holds:

- the Passage Catalog;
- literal FTS over `passages`: two external-content FTS tables kept in step by triggers, `passages_fts` (trigram) for queries whose every term (or phrase) has at least three characters and `passages_fts_tokens` (unicode61) for all others with whole-token candidates. The kernel cannot declare virtual tables, so the spec's `after_open` creates missing FTS tables and triggers and fills a new FTS table from `passages`;
- vectors: a singleton `store_header` pinning the Embedding space, the vec0 table `passage_vectors` (rowid = `passage_ref`, partitioned by Recall scope, start/end timestamps as microseconds; a Passage timestamp that is not canonical is damage (`DatabaseCorruptError`) instead of a guessed instant), and `pending_vectors`, the queue of Passages without a vector (an insert trigger on `passages` fills it; a new Passage whose text already has a vector in the pinned space copies it at once);
- `skipped_texts` (text hashes the provider permanently rejected, with a reason code) and `indexer_state` (document embedding usage spent in the pinned space and the last completed pass).

The first space is pinned when vec0 is created; another space (`use_space`) drops vec0, skipped texts and spent usage, replaces the header and requeues every stored Passage while keeping the catalog. `reset_vectors` (rebuild) does the same without a new header. A header without its vec0 table is damage. `knn_search` asks vec0 for `k = min(limit, KNN_MAX_K)` (4096, the sqlite-vec limit) and reports `truncated` when the limit cut the ranking; a KNN query sqlite-vec rejects as a parameter error raises `PassageIndexError`, which is not damage, so the index is never discarded for it.

## Semantic Indexing

`SemanticIndexer` is the only owner of document embedding; searches embed only their query. It runs while the selected backend is in `SEMANTIC_RECALL_BACKENDS` (`vector`, `hybrid`; `RecallIntegration` calls `set_enabled` at construction and on every reload) and a `text_embedding` binding is set. Runtime starts its loop task (`recall-semantic-indexer`) through `start_event_loop_service`, so only inside a serving Event Loop and never in safe-startup mode, and closes it before the index.

- Triggers: start (`START_DELAY_S` 5 s), every terminal Run (`RecallIntegration.observe_runs` adds a completion observer to each started Run; coalesced within `RUN_DEBOUNCE_S` 20 s), a periodic sweep (`SWEEP_INTERVAL_S` 600 s) that also catches edits, imports and Channel traffic, a `text_embedding` binding change (`Runtime.apply_settings_change` -> `embedding_binding_changed`), `rebuild`, enabling, and a search that finds waiting Passages (`on_waiting`). Settings changes, rebuild and enabling clear a pending backoff; the others respect it.
- A pass refreshes the catalog for every scope with live Sessions (`ChatSessionManager.list_live_scopes`), over conversation and Sub-Agent Sessions only, evicts indexed scopes without live Sessions, then drains `pending_texts` newest first in batches of `BATCH_SIZE` (64 distinct texts, or the smaller `EmbeddingService.document_batch_size()` of a local Model, 8), one embedding call at a time, each followed by one short write. Usage of each stored batch adds to `indexer_state`.
- Failures: transient (network, timeout, retryable status, 429) back off 30 s doubling to 30 min and honor `Retry-After` (state `retrying`); a permanent rejection (another 400/413/422, a context overflow, or a local Model's `EmbeddingInputTooLongError`) bisects the batch, stores the accepted halves and records each single text that still fails in `skipped_texts` until the space changes or a rebuild; if every text of a multi-text batch fails alone, the provider rejects the request shape, so the pass stops as `error` without skipping. Configuration failures (unusable binding, 401/403, 404 model, unusable response) stop as `error` with the same backoff. A local Model (`EmbeddingSpaceIdentity.local`) has no provider to retry: not installed or not ready stops as `local_model_missing`, any other engine failure as `local_engine_failed`; a finished local installation re-triggers the indexer (`add_local_ready_listener`). An index failure discards a damaged index (`discard_if_damaged`) and backs off as `index_unavailable`.
- Space: a pass whose binding names another space than the pinned header drops every vector first (`reset_vectors`, logged with `reason=binding`), so a binding change re-embeds everything even when nothing was waiting; a dimension that differs from the pinned header re-pins (`use_space`), which requeues everything; a pass that moves space more than `_MAX_SPACE_MOVES` (3) times stops as `space_unstable`. A response from a binding other than the one the pass started with restarts the pass.
- Status: `IndexStatus` (`semantic_enabled`, `state` in `disabled|unconfigured|idle|indexing|retrying|error`, provider/model, `indexed`/`waiting`/`skipped` Passage counts, `last_error {code, message}`, `next_attempt_at`, `last_completed_at`, `spent` usage, `estimate` of the waiting texts at `CHARS_PER_TOKEN` 4 with the Model DB input price, 0 for a local Model, and while `indexing` the pass's `rate` in texts embedded or skipped per second and `eta_seconds` for the waiting texts at that rate; both stay `null` until the pass finished a batch and ran `RATE_MIN_SECONDS` 5 s, and outside a pass). `status()` and `rebuild()` never create the index file. Listeners get a status on every state change and at most every 2 s while indexing; the server bridges them to the `recall_index_status` event and serves `recall.status`/`recall.rebuild_index` (`server/rpc/recall_methods.py`).
- Logs: INFO for pass start/finish (counts, duration, usage), space pinning and rebuild; WARNING once per failure condition (`Paused Recall indexing (code=...)`), INFO on recovery; batches at DEBUG. Never text content.

## Backends

### Internal `canonical_scan` backend

Not registered or selectable in Settings; `CanonicalSessionRecallBackend` is also the base whose Message page shaping `sqlite_fts` reuses. It calls `ChatSessionManager.search_messages(use_fts=False)`: the Session store orders eligible current entries globally by their canonical `created_at` text in SQL (the requested order, newest first by default; ties by entry key), checks each candidate's conversation text with case-insensitive substring matching (`telegram` matches inside longer words; the Tool uses `all_terms`), and stops at one hit beyond the page, so `has_more` is exact. Scope, visibility, role and time filters apply in SQL before the budget; at most 10,000 candidates are checked, and a page that budget cut short is degraded/partial. No Session history is loaded or decoded. Continuations bind to a generation-aware selection digest so changed arguments, recreated Sessions, or changed history fail rather than mix content.

### `sqlite_fts`
Lexical search over Sessions-owned external-content FTS inside `<data_dir>/sessions.db`; the backend keeps no derived index of its own. `entries_fts` indexes searchable current entries with the standard tokenizer, and `entries_fts_trigram` provides substring matching over User, Assistant and Compaction-checkpoint text only, so bulk Tool output is not indexed twice. There is no mirrored searchable-text table. Each stored entry is indexed and checked once however many forks show it; a hit is reported for the Session that stores it when that Session is eligible and still shows it, else for the newest eligible Session that inherits it (`sessions/search.md`). Conversation searches use trigram whenever every term has at least three characters; otherwise standard FTS applies whole-token matching to the query. The FTS indexes hold only content and extracted Content Block text, and the column filter restricts matching to them before the candidate limit. Each ordinary Search availability check reads only lifecycle/version/stale/high-water markers; canonical coverage anti-joins belong to startup repair and explicit operator verification, not the Search path. The backend asks `ChatSessionManager.search_messages` for one hit more than the page needs. FTS only enumerates candidates in the requested order (bm25 rank, or Message time for newest/oldest); every candidate's conversation text is checked with the literal case-insensitive matcher before it counts, so pages are full and `has_more` is exact even when standard FTS over-matches (a `C#` query searches the token `c`). At most 10,000 candidates are checked; typed Search pages explicitly report degraded/partial results when that budget cannot prove complete coverage instead of presenting a false complete empty result. A healthy zero-result public Tool search that excludes Tool rows returns empty without scanning; lower-level requests that include Tool rows retry a zero-hit FTS search as a substring scan because the trigram index deliberately omits Tool rows. A stale, unavailable, or unsupported integrated index degrades to the store's SQL substring scan (newest first for relevance, otherwise the requested order; the degradation reason names the order used), and FTS corruption detaches the derived indexes without blocking canonical writes. Scope, Recall visibility, Session, exclusion, role, and time filters execute in SQL before the bounded candidate limit; time filters are canonicalized and compared with the stored canonical UTC text, so `Z`, `+00:00`, equivalent offsets, and fractional precision remain equivalent. Hits carry the matched conversation text from a narrow keyed projection without decoding Messages, and result shaping reads only targeted Session descriptors and bounded conversation context, never complete histories. Skill-context notes are never searchable; persisted Recall results are never indexed, and the literal check reads them as empty text, so Tool-inclusive searches cannot match them.

### `vector`
Pure semantic top-K Passages by cosine distance over the Passage index, without literal revalidation, per-session collapsing, universal cutoffs, or keyword fallback; missing embedding config or an index/provider failure yields stable `semantic_unavailable`. The scope partition, the candidate filter (`rowid IN` the Passages the request's candidates show) and time filters execute inside the vec0 KNN before top-K, so ineligible Passages cannot starve eligible ones; each hit is then attributed to one Session (Passage Catalog). A ranking cut at `KNN_MAX_K` still reports `has_more` on a page that reaches its end.

Search flow: the shared scope read (`CanonicalSessionRecallBackend._read_scope`: one `list_history_revisions` query on the Session database's worker pool) yields every live Session version and Recall visibility of the scope, the request's candidates with their creation order, and the continuation snapshot; with a pinned header of the binding's space a stale continuation fails before any embedding. The query embeds (purpose `query`) and fixes the dimension; the snapshot binds the space, so any space change invalidates continuations. A different space is pinned at once (dropping every vector). The catalog then refreshes for the candidates; the search embeds no documents. While some of the candidates' Passages in the period still wait (skipped texts do not count), the page is `degraded` with `SEMANTIC_PARTIAL_REASON` and the search nudges the indexer. One normalized Usage summary logs at DEBUG per search (`typed_search`). A damaged index is discarded and rebuilt once while a search prepares; damage found by KNN discards it for the next search.

### `hybrid`
Reads the scope once, refreshes the catalog for its candidates once, and prepares the literal arm (Passage FTS) and the semantic arm (query embedding) over the same Passage index, then fuses ranks via Reciprocal Rank Fusion (`k=60`) - never raw score mixing. Candidate depth grows until every selected hit's arm contributions are resolved and the requested prefix cannot be displaced under the unseen-score bound, preserving exact ordering and source labels as well as membership; each deeper pass reruns only the two ranked queries. Depth stops at `_RRF_MAX_DEPTH` (2048, below `KNN_MAX_K`), where the fused prefix is accepted as it stands and a page reaching the end of the fused ranking still reports `has_more` while an arm has more. An arm that fails to prepare or rank stays out for the rest of the search with explicit degradation; both failing returns `hybrid_unavailable`. A semantic arm that answered before indexing finished also degrades the fused page (`hybrid._degradation_reason`: keyword matches complete, or, when the literal arm failed, results incomplete). Cursors snapshot both arms - source or backend changes invalidate continuation rather than mixing rankings.

## Lifecycle & Removal

Canonical Messages always come from `ChatSessionManager`; Recall modules construct no Session paths and index/read only each Session's current view (`load_since(None).active_messages`, `recall_context`), so entries superseded by a history edit cannot be rediscovered. Candidate and freshness enumeration uses version rows (`list_history_revisions`, which carry each Session's Recall visibility) rather than Session summaries or open-ended metadata; complete active histories are loaded only when a stale Session must be re-projected. Vector and Hybrid hits carry canonical Passage boundaries and do not hydrate a complete Session per hit. Freshness comparisons use `(generation_id, history_revision)`, never revision alone, so archive/recreate cannot reuse stale rows.

- `<data_dir>/recall/` belongs to `RecallIntegration` alone: at construction it deletes every file there except `passage_index.sqlite` and its `-wal`/`-shm`/`-journal` sidecars (earlier layouts such as `session_index.sqlite` and `session_passage_vectors.sqlite`), skipping files a database handle of this process holds open; subdirectories stay.
- The Passage index is a kernel disposable projection - rebuilt on a projection version change or damage, never migrated.
- Backends implement `SupportsClose`: `vector`/`hybrid` close only an index they own. `RecallIntegration` closes a backend replaced by `reload_recall_backend()` and the active one on shutdown, after stopping the indexer; it closes the shared index last.
- Deletion is best-effort and independent of the selected backend: when the archive service archives a Session (`session.delete`, `archive.md`), `Runtime.remove_session_from_recall` evicts it from the Passage index whenever its file exists, and from an Extension backend implementing `SupportsSessionRemoval`; when it archives an Agent (`agent.delete`), `RecallIntegration.remove_agent_from_recall` evicts the Agent's whole scope. Index errors are logged, never fail the delete. A restore needs no call, because its Sessions are live again and the next semantic indexing pass catalogs them again; a purge deletes only archived Sessions, which Recall already left. A Session that vanishes between listing, freshness lookup, and Vector hydration is skipped; a stale derived hit never fails the whole search and is removed by a later refresh's pruning.

Contracts every backend shares (continuation binding, project-scope isolation) live in `tests/core/recall/test_backend_contract.py`. `test_passage_index.py` covers the index (projection identity, space/queue/skipped/spent bookkeeping, catalog refresh and scope eviction, KNN limit, literal search, damage), `test_semantic_indexer.py` the indexer (order, status, visibility, bisection, backoff, configuration errors, space thrash, scheduling with injected clocks and zero delays), and `test_vector*.py`/`test_hybrid.py` the search paths. `recall_test_support.py` owns the shared request builder, the fake embedding service (recording document and query inputs), `embed_documents` (one indexing pass), stored-Passage row readers, `forbid_event_loop_calls` (fails synchronous Session store calls made on the Event Loop) and `forbid_database_calls_on_loop` (fails blocking kernel `Database.read`/`write` calls on the Event Loop or on any thread other than that database's own worker pool). The directory's `conftest.py` provides a `sessions` fixture over a cloned current-format store and the `vector_backend`/`hybrid_backend` factory fixtures (typed by `VectorBackendFactory`/`HybridBackendFactory` in `recall_test_support.py`), which close every backend they open, and with it its own Passage index, when the test ends. Runtime wiring (stale files, deletion under any backend, Run nudge) is in `tests/core/runtime/test_runtime_recall.py`.

## Agent-facing text

| Text | Reason |
|---|---|
| `SEMANTIC_PARTIAL_REASON`: `Semantic search has not finished indexing the eligible Sessions and continues in the background.` | Agents read a page with missing vectors as complete; the sentence says coverage is partial and still improving. |
| `Results are incomplete: repeat the search later for complete results.` | Names the one action that helps. Searches embed no documents, so narrowing `period` or `session_id` does not speed indexing. |
| `An empty result does not establish that no related conversation exists.` | Prevents an empty partial page from being reported as proof of absence. |

## Constraints & Gotchas

- Never expose backend tuning just to make payloads look alike: capabilities describe real behavior while the public Tool keeps one compact field set with declared defaults.
- Search returns selected excerpts and explicitly partial context, not a transcript. The Skill owns guidance for extended read-only SQLite inspection; runtime Recall callers continue to use `ChatSessionManager`.
- Do not deduplicate Passages by Session - multiplicity is Vector/Hybrid semantics. Do report each shared Passage once: attribution, not per-viewer rows, decides the Session. Do not move structural filters after KNN - post-filtering global top-K produces false empty pages. Do not fuse raw FTS scores with vector distances.
- Never embed documents on the search path, and never ask vec0 for `k > KNN_MAX_K`: sqlite-vec rejects it, and before the cap the kernel classified that rejection as damage and discarded every vector.
- Skipped texts never count as waiting, so a page can be complete while a skipped Passage stays unsearchable by meaning; only a space change or `recall.rebuild_index` retries them.
