# Model DB Refresh

Read this reference when you change Model DB roots, the manifest, per-file root selection, refresh staging or publication, `model.refresh_db`, carry-forward enrichment, refresh-time reasoning derivation, the refresh of per-Connection Context windows, or registry reload concurrency. The Refresh/Load split, the layers and the typed Model stay in `models.md`; the Provider-facing fetch and normalization side is `providers/catalog-discovery.md`.

## Refresh pipeline

Refresh (`discovery.py` + `models_dev.py`) fetches provider `/models`, the public models.dev `catalog.json`, and any adapter-declared task-capability catalog, projecting results to disk per file. Where a `/models` endpoint omits facts, refresh fills them from that provider's own models.dev section ("fill, don't overwrite"). When the models.dev catalog is unavailable (outage, or the local sweep that never fetches it), or its exact Provider/Model entry is absent, a wire id the current catalog already holds keeps what earlier enrichment gave it - canonical pointer, pricing, limits, family, widened modalities, `metadata.<provider>.npm`/`interleaved_field`, and the reasoning control description as one unit - under the same fill-don't-overwrite rules (`_carry_forward_enrichment`), so an outage never strips the protocol hint that routes and admits a gateway Model. Refresh writes only Models the wire profile admits on the refreshed Connection (restricted and retired ones are skipped); a Runtime passes its own wire data, so a Custom Provider's Settings `wire` block decides admission too; advertised-but-unusable ids drop via `ProviderConfig.catalog_exclusions`. Per-model enrichment (`enrich_discovered_models`, e.g. Ollama `POST /api/show`) and task-capability catalogs (e.g. OpenRouter image/video APIs) are adapter-declared hooks merging typed facts after normalization; failures degrade per model/catalog, never failing the refresh.

## Roots, manifest and selection

System root is the tracked `resources/models/`; runtime root is `<data_dir>/artifacts/models/`. The system root is complete: every generated catalog it ships, all bundled Overrides, and `manifest.json`. The runtime root holds only the generated catalogs this installation fetched, plus its `manifest.json`; Overrides always come from the system root. A manifest (`schema_version`, UTC `refreshed_at`, `source` `runtime`|`system`, `catalogs`) records in `catalogs` each generated file name (`models.json`, `<provider>.json`) with the timezone-aware time a refresh of that root last fetched it. A manifest with another schema version, without `catalogs`, or with a record that is not a generated catalog file name or lacks a timezone is incompatible.

Load (`select_model_database_files`, `core/models/database.py`) selects every catalog file on its own: the runtime copy when the runtime manifest is compatible, records that file, the file exists, and either the system root does not ship it or the runtime record is later than the system record (an unrecorded system file such as the `nous.json` seed counts as oldest); otherwise the system copy, which also wins ties. An unrecorded runtime file is never read. So a vBot update's newer bundled catalogs win over older runtime copies, while catalogs only this installation produces (Custom Providers, local servers) keep coming from the runtime root. Staging leaves out the legacy `*.raw.json` dumps older refreshes wrote; Load ignores any that remain.

## Staging and publication

Manual and automatic refreshes in one Runtime share ProviderRuntime admission from staging through publication and reload (see `providers/catalog-discovery.md`). Both refresh targets stage and validate before atomic directory replacement - a failed fetch/publish leaves the previous root intact. Staged validation (`ModelRegistry.validate`) collects what Load would ignore without logging it; the live reload after publication logs each ignored entry once, and `model.refresh_db` reports their number as `invalid_entry_count` (result only when non-zero, always in its completion log line).

A runtime refresh (`begin_runtime_model_database_refresh`) stages what Load currently sees: each selected catalog from its root plus the current bundled Overrides. Its commit (`ModelDatabaseRefresh.commit(providers=..., canonical=...)`) records the catalogs it fetched with the commit time, keeps the records of the catalogs it took from the runtime root, and drops every other staged file before publishing, so a system-sourced catalog is never re-stamped as newer than the bundled one. Consequence: a canonical refresh's repricing of a system-sourced Provider catalog is not kept; the next bundled snapshot carries current prices. What each refresh records: a full refresh every Provider at least one Connection refreshed, plus `models.json` when the models.dev catalog was fetched; a single-Provider refresh that Provider (plus `models.json` likewise); a local sweep only its refreshed local Providers (`providers/catalog-discovery.md`). A system refresh copies the complete system root, records what it fetched, and carries the other records forward.

`model.refresh_db` with `target: system` writes the shipped root, so it skips Custom Providers (they exist only in this installation's Settings) and refuses one named as `provider_id`; a runtime refresh covers them. A runtime refresh also drops each staged generated `<provider>.json` whose Provider no longer exists (neither in the Provider registry nor among the Settings Custom Providers), such as a deleted Custom Provider's catalog; a catalog file the system root ships is always kept (`begin_runtime_model_database_refresh(provider_ids=...)`).

The manual refresh stages, validates, publishes and discards its copy on the `model-db-refresh` worker, then reloads the live registry with `reload_async`. Cancellation during staging still discards the created copy; once publication starts, publication and live reload settle together before cancellation releases refresh admission. Model RPC credential and Settings snapshots run on `model-access`; wire observations and response assembly remain on the Event Loop. Directory publication and rollback use the shared bounded Windows sharing-violation retry (`core.utils.atomic.replace_path`).

A single-Provider refresh that refreshes no Connection reports why: the first discovery error, else the disabled catalog Connections by id, else missing credentials. The manual refresh RPC reads the configured bundled root from `runtime.storage.resources_dir`, the same StorageManager initialized at Runtime startup. Do not probe Runtime-private path resolvers; regression coverage exercises both refresh targets against a started Runtime with a custom resources path (`tests/server/rpc/test_model_methods_refresh.py`).

`ModelsDevCatalog.model(models_dev_id, wire_id)` binds an exact Provider Model once. Its `ModelsDevModel` view owns canonical pointers, reasoning, limits, modalities, family, protocol hints and pricing; missing entries and absent facts retain their existing `None` semantics.

## Typed reasoning derivation

`capabilities.reasoning` is derived at refresh from models.dev `reasoning_options` - effort option wins over budget over toggle; the canonical ladder lifts from the lab provider only, never unioned across providers; a deviating provider gets its ladder stamped on its provider file while a conforming one inherits canonically. At a canonical join without deviation, refresh keeps an Adapter-reported control description (one with a `control`, e.g. Anthropic's live capability tree) and allows a bare true/unknown support flag to inherit the fuller control description. An explicit false or an endpoint-reported control remains authoritative, including during carry-forward; absent optional reasoning booleans stay unknown. When the endpoint support is unknown, an exact Provider support flag beats a contradictory canonical flag. During a complete public-feed outage, the surviving canonical file is read only to decide whether dropping a fresh support flag for inheritance is safe; no canonical or override values are copied into the generated Provider record. Adapter facts outside the control description (`mandatory`, from OpenRouter's `reasoning.mandatory`) survive in every case.

## Per-Connection Context windows

Connection-aware refresh preserves each surviving Connection's effective window before replacing the current Connection, removes departed memberships' exceptions, and stores in `connection_context_windows` (a frozen positive-int map on `Model`) only values differing from the Model-wide fallback. The generated fallback is the smallest known Connection limit, or null if a serving Connection has no known limit; no private limit is copied from another Connection to that new membership.

## Reload concurrency

`ModelRegistry.reload` and `reload_async` share one generation guard: once a newer reload begins, an older in-flight assembly cannot publish its catalog or cache entry. Readers retain the last published state until the newest reload succeeds. Both return whether the swap changed the assembled catalog (`False` for an identical or superseded reload); the local catalog sweep signals Model changes only on `True` (`providers/catalog-discovery.md`).

`model.list` and `model.get` share the Settings mutation lock while selecting Models, resolving credential snapshots on workers and projecting their live wire facts. A concurrent Provider deletion or credential edit cannot replace the registries midway through a response. The local catalog refresh wait occurs before acquiring that lock.
