# Provider Connections and Accounts

Read this reference only for Provider/Connection configuration, Accounts, credentials, enabled state, OAuth/device flow, token storage/refresh, Connection RPCs, or local reachability. The root Provider boundary lives in `providers.md`.

## Configuration model

`ProviderConfig` owns id/name, Adapter selector, base URL, `connections`, request `defaults`, extra headers, optional Provider-level discovery endpoint/models.dev id, and an optional read-side `context_window` default. `ConnectionConfig` owns local id/label/type, auth metadata, optional OAuth metadata, optional `base_url`, `mode`, `models_endpoint`, and `auto_refresh`.

Provider-level `catalog_scope` controls whether a generated catalog may ship with vBot: `shared` (default) or `instance`. Local Ollama and LM Studio declare `instance`; Custom Providers always parse as `instance`. This is independent of Connection credentials, reachability, and `auto_refresh`. System refresh skips instance inventories and strips their old generated files; runtime refresh still covers them (`models/refresh.md` -> Staging and publication).

`ProviderRegistry` assembles these records from bundled JSON plus the current data directory's normalized Custom Provider overlay. Its direct load/reload API is strict by default; Runtime opts into tolerant assembly so an invalid/unreadable bundled or Custom Provider is logged and omitted without blocking valid siblings or startup, and an unreadable Provider directory yields the valid Custom Provider overlay. Tolerant registries never populate the bundled-only strict cache. Custom registries are never shared through that cache: two Runtimes using the same resources but different data directories must remain isolated.

Settings-owned Custom Providers use the same types with one implicit `default` Connection. `auth: "api_key"` maps to standard `Authorization: Bearer` auth and deterministic `VBOT_CUSTOM_<ID>_API_KEY` storage; `auth: "none"` maps to a keyless Connection. Custom Provider CRUD owns generated default/named Account keys among the data-directory credentials (Secret Store, `secrets.md`), while the persisted Provider record remains secret-free.

A Custom Provider record lives under raw `providers.custom` in `settings.json`. Its optional `wire` block (an additive field without its own `format_version`) is stored as any JSON value; its meaning belongs to Providers (`providers.md` -> Conventions and gotchas). Raw-file validation (`_warn_custom_provider_wire` in `core/settings/validation.py`) reports the entries the Runtime would ignore as warnings, which never omit the `providers` section, while `provider.custom_save` refuses them. `provider.custom_list` items carry a `revision` (`custom_provider_revision()`, a fingerprint of the stored record); `provider.custom_save` with `expected_revision` refuses a save based on an outdated record with `settings_conflict` (`StorageManager.save_custom_provider_settings(..., expected_revision=)`), which the WebUI modal, `vbot provider custom-save` and `scripts/verify_wire_profile.py --write` send. `StorageManager.update_custom_provider_settings(id, update)` transforms one stored record inside the Settings transaction (`verify_wire_profile.py --write` without a running server).

Supported Connection types are `api_key`, `oauth`, and `none`. Keyed Connections default enabled and are gated by credentials. A `none` Connection is keyless: auth may be empty, it resolves credential `""`, exposes one implicit usable default Account, and is disabled by default so vBot never probes a local endpoint without explicit opt-in.

Connection addition is distinct from credentials, enablement, and usability. `ProviderCredentialResolver.is_connection_added()` treats a keyed Connection as added when it has credentials; for a keyless Connection, presence of its persisted `providers.connections` override is the enrollment marker regardless of whether that override is `true` or `false`. This lets fresh local Providers stay in Add Provider while an added-but-disabled Provider remains in the configured list.

Connection-level base URL and models endpoint override Provider-level values. `mode` is an Adapter-interpreted wire selector. `auto_refresh` is a boolean for local catalogs whose installed Model set changes independently of vBot; it changes refresh behavior, not credential semantics.

## Identity and Accounts

Public Connection ids use `provider:connection[:account]`. Account ids match `^[a-z0-9][a-z0-9_]{0,31}$`; `default` is the unnamed slot. Account selection is deterministic: default first, then remaining ids sorted.

API-key Accounts map to environment keys through `derive_credential_key()`: default uses the base key; a named Account uses `BASE__<ACCOUNT>`. `BASE__DEFAULT` is rejected as a second spelling. Discovery and credential lookup share one Account selection: suffix casing is normalized, process environment wins over the data-directory credential even for an empty value, and within one source the canonical uppercase suffix wins over case aliases (remaining aliases are ordered lexically). Account projections keep the canonical derived key.

Bundled Connections can intentionally share a base credential key: OpenCode Go and Zen both use `OPENCODE_API_KEY`. Their same-named API-key Accounts therefore share edits/removal, while enablement remains Connection-level. Enrollment details and the retired `OPENCODE_GO_API_KEY` names: `opencode-zen.md`.

OAuth Accounts are stored per Account in `TokenStore(storage.secrets)`, the `oauth_tokens` section of the Secret Store (`secrets.md`): token id `<provider>-<connection>` for default and `<provider>-<connection>--<account>` for named slots. Id validation keeps ids to safe names. An expired OAuth token remains usable only when it has a refresh path. Each entry holds the token document text, still the Generation 1 OAuth token format of `token_store.py` (`format_version` 1, unknown fields kept); `validate_oauth_token_data` also checks plaintext token files during their conversion. A token that fails to load (damaged entry, unversioned or newer document, or the whole store unavailable) makes `load` raise `OAuthTokenFileError` and `has_valid_token` report false (logged once per condition), and `save` refuses to overwrite it with a hint to disconnect or reset the store; `provider.disconnect` checks existence (`TokenStore.exists`, which lists names without decrypting) instead of loading, so it still removes a damaged entry. Every write of an unavailable store fails with `OAuthTokenFileError`; the plaintext `oauth/*.json` files of earlier versions are never read except by the conversion.

Accounts are credential choices only. Model catalogs, discovery, Connection enablement, and task-target expansion stay Connection-level; Account suffixes are not a catalog or target cross-product.

## Enablement, credentials, and usability

`ProviderCredentialResolver` is the single decision owner:

- `has_credentials()` asks whether credentials exist and is used by management surfaces.
- `is_connection_added()` asks whether the user has enrolled the Connection and is used only by management surfaces.
- `is_connection_enabled()` reads the live `providers.connections` override, else the type default; an Account suffix is ignored.
- `is_usable()` requires enabled and credentialed on the same Connection and is used for behavior gating.
- `list_accounts()` returns deterministic `ProviderAccount` projections with source and usable state.
- `resolve_account_id()` validates an explicit Account or chooses the first usable one.

Model listing, task targets, catalog auto-refresh, usage probes, Chat's unpinned-Connection selection, and Project model probes use `is_usable()`. A disabled Connection fails `Runtime.get_adapter()` with the disabled reason before credential resolution.

## Credential and OAuth lifecycle

API keys resolve from process environment first and the data-directory credentials (Secret Store) second. Key set/unset RPCs can mutate only the data-dir value, so removing it can still leave the Account configured through process environment. Set writes the canonical key and removes that Account's data-dir case aliases; unset removes all of that Account's data-dir spellings. They reload the fallback snapshot into the existing `ProviderCredentialResolver`; its stable identity ensures every already-injected consumer sees the new credential state on its next check. `none` Connections reject key mutation.

`StaticTokenGetter` wraps fixed API-key/keyless values. `OAuthTokenGetter` reads the Account token, refreshes near expiry, stores refreshed values under the same Account, and can force refresh a Provider-rejected access token even when its stored expiry is still in the future. Token reads, refresh compare-and-publish and device-flow writes use the `provider-tokens` worker pool through `TokenStore` async methods, which settle a started write before cancellation. Synchronous methods remain available to off-loop readers. Refresh locks live on `TokenStore` per Provider Connection Account, so separate getters in one Runtime coalesce the same refresh; a waiter reuses a token another getter already replaced. Publication and terminal-failure cleanup use `TokenStore.replace_if_current` against the exact Account credentials read before the network wait; comparison and publication share one Secret Store transaction, including its inter-process lock. These newer Account changes supersede the delayed result. A successful stale refresh reuses a newer non-expiring token or fails without restoring removed credentials. Adapters and task/usage clients ask the getter inside each request attempt rather than retaining raw access tokens. MiniMax refresh accepts either TTL seconds or absolute Unix milliseconds and quarantines terminally rejected refresh state by deleting the dead Account token; retryable failures keep it. `ROTATING_REFRESH_DEVICE_FLOWS` (MiniMax, Nous, OpenCode, xAI) is the single source for both rotating-token rules: their refresh POST is sent once and never replayed after an ambiguous failure (a replay would present the retired token, and its auth rejection would delete the valid login), and only a definite rejection quarantines the stored token: a 4xx reply carrying the RFC 6749 `invalid_grant` code, Nous's reuse signal, or a reply that cannot yield a token (MiniMax's in-band failure status, non-object JSON, a missing access token, a Nous scope or MiniMax expiry failure). Every other failure keeps the login: server-side statuses (5xx including CDN 52x pages, 408) and 4xx replies without `invalid_grant` (a WAF page, a bare 401, `invalid_client`, `invalid_request`, a non-JSON body), because a wrong delete costs a full device re-login while a wrong keep costs a retry (`test_rotating_refresh_is_never_replayed_and_preserves_token`, `test_rotating_refresh_rejection_quarantines_the_login`).

`DeviceFlowEngine` owns Account lifecycle, OAuth device sessions, polling cadence, replacement/cancellation and token persistence; `_auth_wire.py` owns authorization/token requests, response decoding and Provider-specific exchanges. `DeviceFlowSession` and `DeviceFlowTerminalError` remain available from `auth_flow.py`. `connect()` owns the initial authorization request as well as subsequent polling. Caller cancellation also retires authorization verifiers when the response is ready but polling has not started. Replacement and cancellation retire either stage per Account; `is_flow_active()` includes pending authorization. `cancel_flow_and_wait()` and replacement `connect()` serialize each Account transition and drain any admitted token save before disconnect deletes its token or a replacement starts. This prevents an old save from restoring a disconnected Account. `aclose()` permanently closes the engine and drains cancelled/replaced authorization and poll tasks, so a late authorization cannot restart polling after disconnect or shutdown. Connection RPCs use this managed lifecycle against declared OAuth metadata; UI/CLI code must not reproduce flow policy. `device_flow` selects the standard OAuth2 shape, OpenAI Codex's two-step device authorization, or MiniMax's PKCE/user-code variant; provider-specific secrets remain engine-internal.

A 2xx token-endpoint reply (refresh or Copilot exchange) that is not JSON raises a non-retryable plain `ProviderError`, not `ProviderAuthError`, so it is neither replayed nor treated as a terminal rejection that quarantines the stored token; valid JSON that is not an object stays an auth failure (`test_malformed_token_endpoint_json_is_fatal_provider_error_and_keeps_token`).

A successful token refresh and a device-flow start log only at DEBUG (routine, per expiry); a failed refresh logs WARNING and a connected device flow INFO, each with Provider and Connection id, never the Account id. Token-endpoint error bodies (refresh or Copilot exchange) may echo credentials or account details, so failure messages and refresh-failure logs never carry them. They keep only the HTTP status and the OAuth `error` code: the RFC 6749 string `error`, or a nested `error.code`, accepted only when it matches `[a-z0-9_.:-]{1,64}`. `error_description` and other body text are dropped. HTTP 429 raises `ProviderRateLimitError` ("OAuth token refresh rate limited (HTTP 429, slow_down)"), retryable 502/503/504 raise a retryable `ProviderError` ("OAuth token endpoint unavailable (HTTP 503)"), and any other server-side status (other 5xx, 408) raises a non-retryable plain `ProviderError` ("OAuth token endpoint failed (HTTP 500)"): not an authentication failure, no reconnect prompt, and not replayed because the POST is non-idempotent. Every remaining 4xx is a `ProviderAuthError` "OAuth token refresh failed (HTTP 400, invalid_grant) - please reconnect"; only one carrying `invalid_grant` is a definite rejection, the others are a private `ProviderAuthError` subclass (`_InconclusiveRejectionError`) that callers see as the same error but that rotating flows do not quarantine on. Nous reuse detection still reads the body only to classify it. Coverage: `test_terminal_refresh_failure_reports_status_and_oauth_error_code`, `test_refresh_failure_keeps_only_a_valid_oauth_error_code`, `test_retryable_refresh_failure_is_sanitized_and_keeps_token`, `test_server_side_refresh_failure_is_not_an_authentication_failure`.

Generic OAuth refresh and Copilot exchange expiry parsing use the existing fallback lifetime when optional expiry metadata exceeds numeric or UTC datetime limits. Unusable expiry metadata must not prevent publishing an otherwise valid refreshed token, especially a rotated refresh token. MiniMax retains its separate expiry contract.

`OAuthRequestRecovery` in `token_getter.py` owns rejected-access-token recovery for HTTP consumers. Each logical request records its actual HTTP status and sent auth headers before Provider classification, then asks `refresh_after_rejection` once only when classification produces `ProviderAuthError` and the getter has that capability. The getter owns rejection semantics together with its OAuth flow: 401 permits renewal; xAI additionally recognizes only HTTP 403 with top-level JSON `code: unauthenticated:bad-credentials`. Other 403 bodies return no recovery without reading or changing token state. Refresh runs outside the request's transient retry loop; the next request rebuilds all token-derived headers. Static credentials, ordinary permission 403, non-auth 401 errors, getter/parser failures without an actual rejected request, and failures after stream establishment never enter recovery. Catalog subrequests each own their recovery state; separate getters still share the Account's refresh lock. Chat Completions, Responses, Messages, Zen Gemini, task GET/POST, catalog GET/POST, and OpenAI Usage use this same owner; new OAuth HTTP consumers must use it rather than add Provider-name allowlists or their own refresh loops.

Local regressions cover all six bundled OAuth flows, each Chat wire with and without streaming, rotation and four concurrent rejected requests coalescing into one exchange per Account. They do not establish live entitlement for an unconfigured Provider. Protocol basis: RFC 6750 section 3.1 permits obtaining a new access token and retrying `invalid_token`/401 while distinguishing insufficient scope (https://www.rfc-editor.org/rfc/rfc6750, read 2026-09-09). Provider-specific classification remains authoritative, including OpenCode's entitlement errors disguised as 401.

## RPC and runtime projections

- `connection.list` combines static Provider/Connection config with Account/added/configured/enabled/usable state and optional local reachability. The Provider projection inside `settings.get` preserves the same Connection-level distinctions so management surfaces and behavior gates do not infer one state from another.
- `connection.set_enabled` persists the explicit Connection override. Enabling an auto-refresh Connection forces an immediate local catalog attempt; enabled-but-unreachable remains a valid persisted state.
- `provider.set_key`/`unset_key` address API-key Accounts through derived keys and never return secret values.
- Provider connect/status/disconnect operate on OAuth Accounts and token-store state. A completed login and a disconnect also close the Connection's kept-open Provider transports (`Runtime.close_connection_transports`: Codex WebSockets opened with the previous token, `providers/openai.md`).

Local endpoint reachability is Runtime probe state, not credential state. `Runtime.connection_reachability()` is `True`, `False`, or `None` (not probed) for auto-refresh Connections and is surfaced separately from enabled/usable.
