# Provider Request Policy

Read this reference only for Adapter request/response/SSE translation, shared HTTP behavior, reasoning, CoT replay, media support, output/context limits, or Provider-backed task HTTP clients.

## Adapter ownership

`ProviderAdapter` defines `send()`, `stream()`, `normalize_response()`, `aclose()`, and the per-request policy hooks. `stream()` yields normalized delta types for content, reasoning, Tool calls, opaque reasoning metadata, usage, finish, and transport-only heartbeat; raw Provider frames stay private. Every production response and finish normalizes Provider stop state to `stop`, `tool_calls`, `output_truncated`, `content_filtered`, `error`, or `unknown`.

`OpenAICompatibleAdapter` deeply owns generic Chat Completions mechanics. `AnthropicCompatibleAdapter` deeply owns Messages-compatible requests, content blocks, SSE, usage/cache normalization, and retry. Concrete Provider Adapters extend or compose those mechanics only for verified Provider differences. A Provider-owned router may inspect its injected Model lookup and Connection mode, but Runtime never selects an inner wire per Model.

The compatible bases retain transport lifecycle and overridable policy methods. Their private `_chat_completions_*` and `_messages_*` modules contain the existing wire conversion, stream decoding, constants and catalog parsing implementations. These are internal file boundaries, not additional Adapter types or new transport policy. `_tool_calls.py` implements the shared canonical Call/Result and target-id operations exported by `adapter.py`.

`normalize_response(response, *, model_id=None)` produces canonical assistant fields. The optional Model id supports data-driven wire selectors; shape inference is compatibility fallback only. Every Adapter routes recognizable Tool attempts through `normalize_tool_call_candidates()`: object or encoded-object arguments become canonical JSON objects, malformed names/arguments retain an addressable id and safe placeholder fields plus persisted rejection metadata, and sibling order is never collapsed by dropping a bad call. A string consisting entirely of multiple consecutive top-level JSON values expands into independently validated same-name canonical calls; the first keeps the Provider id, later calls receive deterministic synthetic ids, and internal index/length metadata preserves their authored sequence. A syntactically unsegmentable string remains one rejected attempt rather than executing a guessed prefix. Interpreter limits on integer conversion or JSON nesting also produce correlated rejection instead of escaping as parsing exceptions. Opaque `reasoning_meta` crosses only the Adapter/Chat boundary and is preserved, not interpreted.

## Tool-call terminal safety and correlation

Only the canonical `tool_calls` terminal outcome authorizes dispatch. When a Provider ends with `output_truncated`, Chat persists the partial Assistant turn and emits ordered, correlated `tool_call_truncated` Results without invoking Tool handlers or Extensions, then lets the Model recover. `content_filtered`, `error`, `unknown`, and inconsistent outcome/call combinations likewise produce correlated `tool_call_rejected` Results without dispatch before failing the Model step. Missing outcomes remain inferable only for source compatibility with legacy third-party/test Adapters; an explicit unrecognized outcome becomes `unknown` and fails closed.

OpenAI-compatible streamed Tool fragments carry a stable slot independently of the Provider id. Some Ollama-compatible servers reuse one raw wire index for every parallel Tool Call, distinguishing calls only by `id`; stream normalization keeps an id-to-slot mapping per raw index so returning ids resume their original calls. New native or virtual slots cannot collide with occupied slots, and id-less continuation fragments keep their raw index's active slot. The accumulator groups by that slot, adopts a real id whenever a later fragment supplies it, and synthesizes a deterministic fallback only when finalization has no Provider id. Recognizable empty or id-less Tool attempts retain a slot and become addressable rejected Calls. Finalization preserves malformed/incomplete argument JSON as a rejected canonical Call; parsing failure is never a streaming exception once the Provider has completed the Tool Call.

Canonical Session Tool-call ids are Provider-origin evidence and remain immutable. `normalize_tool_call_ids()` returns a copy-on-write request view (a new list that copies only the messages, Tool Calls, and Responses output items whose ids change and shares the rest with the caller), preserves already-valid unused ids, and deterministically allocates collision-free target-wire ids while rewriting each Assistant Tool Call together with the matching Results in its immediately following Tool batch. The explicit profiles are Anthropic Messages (`[A-Za-z0-9_-]`, at most 64 characters), Mistral (exactly 9 alphanumeric characters), and Responses (`[A-Za-z0-9_-]`, at most 64 characters, no trailing underscore). The shared Chat Completions codec applies the profile its wire profile names in `request.tool_call_ids` (Mistral: `resources/wire/mistral.json`) before the output-limit estimate; ordinary OpenAI Chat requests name none and do not use this transform. Responses replay also rewrites matching `reasoning_meta.response_output` function-call `call_id` values and removes a Provider-owned item `id` only when the call identity changed, preventing a foreign item from falsely pairing with opaque reasoning.

## Reasoning and CoT

### Reasoning intent

`ReasoningWire.plan()` (`core/providers/wire_profile.py`) is the decision layer for every wire-profile codec (Chat Completions, Messages, native Ollama, OpenCode Zen's Gemini wire, and the shared Responses codec, which renders reasoning only through the caller's wire-profile renderer): from the profile's reasoning wire (support, control, ladder, effort map, off/unset spelling, budget rule) plus Agent effort and output allowance it returns `default`, `off`, `effort`, `budget`, or `on`, and the profile's dialect in `core/providers/reasoning_dialects.py` spells that intent onto the wire. `resolve_reasoning_intent()` (`reasoning.py`) remains the Provider-neutral decision behind the declared-control description; no bundled Adapter spells reasoning in Adapter code any more. Both own snapping, `none`->off, effort-to-budget math, minimum/clamp behavior, and skip rules; each Adapter only renders the result onto its wire.

Adapters must not reimplement this decision policy. Provider-specific maps document each render (for example OpenRouter object fields, Anthropic adaptive/native budget, or binary thinking toggles).

Every request render is also *described*: `describe_profile_reasoning(profile, effort)` (`core/providers/reasoning_dialects.py`) is the single description of what a request with the selected effort would actually carry - the profile's `ReasoningWire.plan()` passed through the dialect's describe function, so it snaps against the same effective ladder the render uses. A known Model whose profile marks reasoning unsupported describes `off`; a Model whose off sends nothing describes `default`, not `off`; a budget or plain `on` render reports no effort level. Two entry points use it: the Adapter instance method `describe_reasoning_render(model_id, effort)` on its bound Connection's profile, and `ProviderRuntime.describe_reasoning_render(provider_id, connection_id, model_id, effort)` on the Runtime's profiles; both include learned observations and, for a Custom Provider, its Settings `wire` block. `/status` asks the Runtime through `Runtime.describe_agent_reasoning_render(agent)`, which resolves the Agent's own Connection as Chat does (a pinned `::connection`, else the first usable one) without constructing an Adapter, so no credentials or HTTP are involved; it falls back to the declared-control rendering (`resolve_reasoning_intent()`) only when the Agent's Model cannot resolve to a Connection. Profile descriptions follow the dialect: an OpenRouter on/off Model describes `on` because `openrouter_reasoning` sends `reasoning: {enabled: true}` instead of an effort, and MiniMax M2.x/M3 never send an effort level. `tests/core/providers/test_reasoning_describe.py` pins descriptions against renders that the request tests pin on the wire, and the Provider request tests (`test_ollama_cloud.py`, `test_openai_requests.py`, `test_opencode_go_reasoning.py`, `test_opencode_zen.py`, `test_openrouter_reasoning.py`) check the description against the sent body; extend them when a wire profile changes a render.

### Chain of Thought

The governing rule is **replay minimality** (see `.vorch/PROJECT.md` -> Context): return exactly the reasoning state the target Model needs to work optimally - opaque meta when the wire makes it contract state, readable text only when the Model demonstrably benefits from it on that wire. Replay decisions are per-Provider/per-Wire facts documented in each Provider map; an undocumented default-on replay is a gap to verify and fix, never a safe baseline.

CoT contains two different classes of state: readable Reasoning text and opaque signatures/encrypted/provider metadata required for native round-trip continuity. `reasoning_replay_policy(model_id)` returns the wire profile's `replay.scope`: the system default `full_history` unless `resources/wire/<provider>.json` narrows it in `defaults` or a rule (`none`, `current_run`, `tool_turns`, or `full_history`; an invalid value is reported and the layer ignored like any other wire-file issue). A narrower scope is a compatibility escape hatch for a demonstrated wire limitation, not a required opt-in for full replay. `tool_turns` is the one cost scope: it keeps Tool Call turns' reasoning across the whole history and drops answer turns' reasoning, for a gateway that bills historical answer-turn reasoning the Model's vendor does not require (OpenCode Go Qwen). Choosing a scope, in order: valid for the wire's protocol, faithful to the vendor's intended history, stable per message (only `current_run` is not, see `chat/request-building.md`), then cheapest.

Serialization carries exactly **one** reasoning class per Assistant turn. Which class is an explicit adapter-owned wire fact: `ProviderAdapter.reasoning_replay_fidelity(model_id)` returns the wire profile's `replay.fidelity`: `meta_preferred` (opaque meta when the turn captured it, otherwise readable text), `meta_only`, or `readable_only`. The default `meta_preferred` matches OpenRouter's documented contract that `reasoning_details` supersede duplicated plaintext; raw-string-only wires keep readable continuity. Deviations come from protocol defaults (Messages, Responses, Gemini: `meta_only`; native Ollama: `readable_only`), wire files (`resources/wire/ollama-cloud.json` and `resources/wire/kimi.json`: `readable_only`; `resources/wire/mistral.json`: `meta_only`; `resources/wire/minimax.json` keeps the Chat Completions declaration on its Messages subscription wire, see `providers/minimax.md`, and `resources/wire/github-copilot.json` does the same on Copilot's Messages wire; `resources/wire/opencode-go.json`: `readable_only` on Chat Completions); no bundled Adapter overrides fidelity. Fidelity is never encoded in Override files or provider metadata - it is a wire fact like `wire_media_support`.

Keep three facts separate. Replay scope says which canonical Assistant turns vBot may return; wire fidelity says whether it must return exact original blocks/items instead of reconstructing them; Provider render scope says which returned historical reasoning the remote Model actually makes available to the next sample. A `full_history` replay policy does not by itself prove all historical reasoning is rendered.

Chat owns history shaping. `full_history` native replay survives only when the persisted `reasoning_scope` exactly matches the resolved Provider/Model/Connection/Account identity; an interrupted Assistant turn, Model switch, Connection or Account switch, and run-local fallback are hard native-state boundaries. Textual vBot Compaction is not: the summarized Head leaves the request, while retained Tail turns keep their native reasoning under the same scope rule. On a route mismatch Chat always removes native `reasoning` and `reasoning_meta`; only non-empty readable Reasoning from a completed reasoning-only or Tool-associated turn may be escaped into a provider-neutral request-only reminder after its Tool batch. Ordinary answer reasoning is not duplicated, and opaque/meta-only, redacted, scope, and interrupted state are never projected. Interruption preserves native Reasoning only as canonical evidence and replays readable work solely through the separate provider-neutral Continuation reminder, never through `reasoning` or `reasoning_meta`. `phase` is semantic assistant history, not opaque reasoning state, so it survives ordinary request shaping and Compaction. Adapters serialize whatever native reasoning survives shaping and must not apply a second history-wide strip except for a documented wire incompatibility such as explicitly disabled thinking.

Responses-shaped adapters persist and replay every original response output item in order; that preserves encrypted reasoning, message `phase`, function/program items, ids, and future item kinds without lossy reconstruction. When one raw function item was canonically rejected, replay preserves all other opaque items/order but replaces that item with its safe canonical function call so malformed raw arguments cannot poison the recovery request. When one raw function item expanded from a consecutive argument sequence, replay replaces that item in place with every recovered canonical function call so each following Result remains correlated. The ABC and hook-less compatibility default is `full_history`. Within Tool loops, dropping Provider-required signatures or opaque blocks can break continuity even though vBot never reads them.

On OpenAI-compatible Chat wires, readable Reasoning normalization selects the first non-empty configured/provider alias across `reasoning_content`, `reasoning`, `reasoning_text`, and `thinking`; duplicate aliases therefore never duplicate readable Reasoning. The base serializer emits readable text only under its declared fidelity - never alongside opaque meta (`meta_preferred` sends meta when captured). Streamed `reasoning_details` remain message-level opaque metadata, but the Adapter accumulates the complete ordered list before it crosses into Chat: entries with a stable embedded `id` update their original slot, id-less entries retain arrival order, and each delta carries the cumulative list so Chat's intentionally shallow opaque-metadata merge cannot discard sibling Tool-associated details.

Reasoning rejection/ignored-effort warnings are diagnostic only. They may warn conservatively on a relevant HTTP 400, or (non-streaming Chat Completions `send()` only) on a swallowed effort: the request's rendered intent from the Adapter's `describe_reasoning_render` asks for reasoning (`effort`/`budget`/`on`; a catalog non-reasoning strip, `off`, and `default` never qualify), usage reports exactly zero reasoning tokens, and the response returned no readable Reasoning or non-empty reasoning meta - a zero counter alongside returned Reasoning is an observed Provider report (`providers/openrouter.md`). They do not reclassify status/retry behavior and never log token values.

## Request limits and context

`ProviderAdapter.image_size_limit(model_id)` exposes a known positive encoded-file byte ceiling for one image, excluding base64 overhead; `None` means unknown. Chat and isolated image understanding use it during shared image preparation. Copilot supplies existing catalog `vision.max_prompt_image_size` metadata. This hook is independent of image-count and whole-request limits; it introduces no inferred limits or new Model-format claims.

`ProviderAdapter.request_body_limit(model_id)` declares a verified whole-request byte ceiling, or `None` when unknown. After wire shaping and streaming options, the OpenAI-compatible wire prepares httpx's actual UTF-8 JSON bytes off the Event Loop in the bounded `provider-request-body` worker pool. It checks any declared ceiling against those same bytes and reuses them for sending and ordinary/OAuth retries; only a payload rebuilt by rejection learning is encoded again. Headers still rebuild per attempt, preserving explicit case-insensitive Content-Type values. Overflow raises non-retryable `ProviderRequestTooLargeError` with actual/allowed bytes before network I/O; ordinary HTTP retries and Model fallback do not hide it. The Anthropic-compatible wire checks the same ceiling through `_http_shared.enforce_request_body_limit`, and the OpenCode Zen Gemini route raises it for its 20 MB inline limit. `classify_http_status` maps any HTTP 413 to the same error without sizes, so an undocumented Provider limit (for example the ChatGPT Codex backend) takes the same recovery. Chat retires already delivered images and rebuilds the request locally until it fits or no eligible images remain (`chat/request-building.md`). This byte ceiling is independent of token Context. Wire files declare it as `media.request_max_bytes`: Ollama Cloud 16 MiB, Anthropic 32 MB, MiniMax 64 MB (both wires), Kimi 100,000,000 bytes (Platform) / 80 MiB (Coding Plan), OpenCode Zen Gemini protocol 20,000,000 bytes; no universal Provider ceiling is inferred.

`ProviderAdapter.request_image_limit(model_id)` declares a documented maximum number of images per request, earlier turns and Tool Results included, or `None` when unknown. Chat keeps every request within it by retiring the oldest delivered images (`chat/request-building.md`). Wire files declare it as `media.request_max_images` (evidence gathered 2026-10-04 from Provider docs): Anthropic 600, which `AnthropicAdapter` caps at 100 for Models with a context window <= 200k; StepFun 60; Mistral 8 (vision FAQ; another Mistral page says it depends on the Model); OpenCode Zen Gemini protocol 3,600. GitHub Copilot overrides the hook with the catalog's per-Model `vision.max_prompt_images` (VS Code's own Copilot client ignores these values, so they may be stricter than the service). OpenAI Platform (1,500 images / 512 MB) is not declared: Context Compaction comes first, and `OpenAIAdapter` also serves xAI, OpenCode Zen and the Codex backend. Evidence: `adapter.py`, `wire_profile.py`, `openai_compatible.py`, `_http_shared.py`, `errors.py`, `tests/core/providers/test_openai_compatible_request_body.py`, `tests/core/providers/test_anthropic_requests.py::test_documented_limits_bound_requests_and_oversized_bodies_fail_before_io`, `tests/core/providers/test_ollama_cloud.py::test_request_body_limit_counts_exact_wire_bytes_before_io`, and the mixed-image Run tests in `tests/core/chat/test_chat_integration_images.py`.

None-valued caller kwargs mean unspecified and are removed before Provider defaults; falsy real values such as `temperature=0.0` remain explicit overrides. Bundled Provider configs carry no sampling defaults (only `max_tokens` where one is needed): an unset Agent value leaves `temperature` and `top_p` to the Provider's own default. A Custom Provider's configured `defaults` still apply.

Compatible Adapters resolve a positive output allowance in this order: explicit caller limit, Model catalog `max_output_tokens`, then flat Provider default. Before every request, `resolve_request_output_limit()` clamps that allowance so the input budget for its actual wire request including Tool definitions and media, an uncertainty reserve (`max(25% of estimated input, 1% of the effective context window, 256)`), and output fit inside the effective context window. `ProviderAdapter.estimate_request_input_tokens()` is the common seam: its fallback uses the shared message estimator, while Chat Completions, Messages, and Responses implementations count their rendered messages/items, instructions, and Tool definitions rather than redundant canonical history. The shared estimator (`core/utils/tokens.py`) also replaces oversized opaque reasoning-continuity blobs (`encrypted_content`/`signature`/`redacted_thinking`, and any non-text string inside `reasoning_details`) with fixed reservations instead of counting their encoded size as prose - providers bill those blobs by decoded content, and replayed details otherwise inflate the local estimate far beyond real prompt tokens (live evidence 2026-08-25: ~1.04M estimated vs ~220k real). It likewise compacts legacy per-delta `reasoning.text` fragments before counting. A catalog output ceiling equal to the entire context therefore cannot produce an invalid request. The uncertainty reserve only shrinks the output allowance. Exhausted input fails locally as a non-retryable `ProviderError` only when estimated input overflows the window even after removing its own uncertainty reserve - an estimate inside that margin goes out unclamped, because an inflated estimate must not kill a request whose measured Context still fits. The window check runs regardless of whether an output allowance exists: Models without any known ceiling send no `max_tokens` (their Provider default applies) but still fail locally on overflow instead of receiving a remote Provider rejection mid-Run. Independently, Chat runs a pre-send guard on every request: when the current Run carries a compatible measured request anchor, it checks measured input plus the estimated change to the actual next request. The same projection reaches output clamps through the task-local `request_input_budget` scope. A changed Adapter/Model, prompt epoch, System Prompt, or Tool catalog starts a full estimate; measured input already includes System Prompt and Tool definitions. Safety reserves never inflate the Context display or Compaction trigger. The request estimator in `core/utils/tokens.py` is separate from persisted Usage estimation and never counts native transport payloads as prose.

The output-limit and Copilot prompt-limit paths resolve `request_input_budget` before evaluating their local estimator. Fallback estimates, including explicit Responses-wire estimates, stay callable until needed: ordinary Chat has already prepared the projection off the Event Loop, so rebuilding and hashing the request again would discard the result. A missing or different-Model scope still runs the selected-wire estimator; the projected value, output reserve, prompt limit, and outgoing fields are unchanged. Regression coverage: `test_adapter.py`.

`resolve_context_window()` owns the read-side chain: positive Model fact, then positive Provider-config default, then `GLOBAL_CONTEXT_WINDOW_FLOOR`. `resolve_effective_context_window()` adds local-Model policy: positive user setting, else the chain capped by `LOCAL_CONTEXT_DEFAULT_CAP`. These helpers inform budgeting/status/payloads; only verified local Adapters enforce the effective value on the wire.

## Wire media and request context

`wire_media_support(model_id)` declares exact MIME types the concrete wire can carry (the wire profile's `media.types` unless an Adapter still overrides it). Chat intersects this with Model input modalities and degrades unsupported content; the ABC default is empty so a missing declaration degrades rather than crashes. PDF support is declared only in verified wire files (`resources/wire/anthropic.json`; `resources/wire/openai.json` for Chat Completions and Platform Responses), never in protocol defaults.


The shared estimator uses tiktoken's known Model mapping to select `cl100k_base` or `o200k_base`, with `o200k_base` as the fallback for unknown/private tokenizers. Each encoding is loaded lazily once per process through tiktoken's synchronized registry, shared by all Agents/Sessions. Bounded digest-only caches retain token counts (4096 entries) and image dimensions (256 entries), never text, base64, or decoded pixels. Top-level request arrays count items separately so appending a message reuses unchanged item counts; JSON framing is still approximate. `estimate_structured_tokens` counts an item's compact JSON directly unless it contains a structural string start that media or opaque-reasoning normalization acts on (`data`, `base64`, image contexts, `reasoning_details`, the opaque blob keys); only those items take the copying normalization walks, with identical counts either way (`tests/core/utils/test_tokens.py`). No estimation path calls a Provider.

Known image profiles in `core/utils/tokens.py` apply OpenAI tile/patch rules, Claude 28px patch rules, or DeepSeek V4.1/Flash preprocessing to local Pillow header dimensions and the rendered image `detail` (omitted means `auto`). Inspection decodes at most 256 KiB of header and never loads pixels or fetches URLs. Unknown Models, unavailable/oversized headers, unsupported detail modes, audio and documents retain the 4096-token media reserve; fixed OpenAI low-detail costs do not need dimensions. Opaque Reasoning reservations remain approximate and independent of image counting. Formula sources are linked in the implementation (checked 2026-09-11); golden image examples, cache bounds, mutation safety and wire forwarding are covered by `tests/core/utils/test_tokens.py` and the Chat/Messages/Responses request tests. These are local estimation rules, not evidence of gateway preprocessing or private tokenizer equivalence.

Every Provider wire sends a Tool Result's content to the Model as text, never as the persisted JSON envelope. `tool_result_text()` (`core/providers/_tool_result_text.py`) renders a failure as `Error (<code>): <message>` plus any further error fields, and a success as `name: value` lines for its data fields (null values omitted; nested values as compact JSON; multi-line strings indented) followed by a blank line and the first non-empty `content` or `output` string verbatim. Empty success data reads `ok`, and envelope artifacts become an `artifacts:` line. Content that is not an envelope (legacy text, compacted digests) passes through unchanged. The rendered text, and every string and key of a function-response object, then has its look-alike `<system-reminder>` tags neutralized to `&lt;system-reminder>` by `neutralize_system_reminder_tags`, the rule Chat's `model_facing_request` applies to the other request text (`chat/request-building.md`); neutralizing after JSON decoding means escaped forms such as `<` cannot reintroduce a tag. Rendering happens exactly once at the final wire boundary: a literal body may itself be envelope-shaped JSON, so the projection is not idempotent. The rendering is deterministic, so replayed history keeps its prompt-cache prefix, and Chat requests, Compaction requests on the active target and Adapter token estimates see the same text. Wires that require an object (Gemini `functionResponse.response`) classify the canonical envelope before rendering and receive `{"output": text}` or, for a failure, `{"error": text}`; Anthropic-compatible and GitHub Copilot Messages wires add `is_error: true` for failures. Canonical Session history, Run events and Extension hooks keep the JSON envelope. Coverage: `tests/core/providers/test_adapter_tools.py` and the actual Adapter payload tests in `test_openai_compatible_requests.py` and `test_opencode_zen_gemini.py`.

Run-local rich Tool Results retain their persisted JSON-string envelope and carry resolved media/path blocks in the request-only `tool_result_content` field. Anthropic-compatible and GitHub Copilot Messages adapters render it as nested Tool Result content; Responses-shaped adapters render it as the `function_call_output.output` content array. OpenAI Chat Completions, native Ollama and Zen Gemini use `project_tool_result_content_fallbacks()` to move all media into one request-only user message after the complete consecutive Result batch. The projection preserves each canonical envelope and keeps its supplemental text blocks in `tool_result_content`; the final wire renderer appends that text to the rendered Result, retaining Gemini's success/failure classification. This fallback never mutates canonical Session history and must preserve sibling Result order.

`request_context_kwargs(agent_id, session_id, project_id=None)` lets an Adapter derive Provider routing/cache hints from stable conversation identity. The default adds nothing. Chat supplies the Run's Project anchor and merges returned kwargs without knowing their Provider meaning. OpenAI Codex uses Agent + Session for its conversation headers; OpenRouter hashes Project + Agent + Session into its top-level sticky-routing `session_id`.

### Wire request extras

The wire profile's free-form request rules `request.body_defaults`, `request.extra_body`, and `request.extra_headers` mean the same on every chat request path, in `send()` and `stream()` alike: Chat Completions (`OpenAICompatibleAdapter` and its subclasses, GitHub Copilot's Chat route included), Messages (`AnthropicCompatibleAdapter`, including the MiniMax and OpenCode Go/Zen inner Messages Adapters), the Platform `/responses` of `OpenAIAdapter` (OpenAI `api-key`, xAI, OpenCode Zen's Responses route), the Codex wire over SSE and WebSocket, the OpenRouter, GitHub Copilot, and OpenCode Go Responses routes, GitHub Copilot Messages, OpenCode Zen Gemini, and native Ollama `/api/chat` (local and locally proxied Cloud Models; direct Ollama Cloud is a Chat Completions subclass).

- Body: each request builder calls `RequestRules.apply_body()` (`core/providers/wire_profile.py`) once the body is built. `body_defaults` fill keys the body has no value for; `extra_body` replaces whatever the body holds. Values are deep-copied (`thaw_json`), so a request never mutates the profile. Keys are always top-level request-body keys: on Gemini they sit beside `contents`, not inside `generationConfig`; on native Ollama an `options` value fills or replaces the whole `options` object.
- Order: the body rules run after the Adapter's own fields, so `extra_body` can override the Responses `store: false`, OpenRouter's `session_id`, the Messages `max_tokens` pin, and even the rendered `messages`, `instructions`, or `system`. Parameter shaping runs afterwards and treats an `extra_body` key like a caller's kwarg (`RequestRules.shape_parameters()` stops protecting it), so allowlists, drops, and caps still apply. Later steps stay last: Messages prompt caching (an `extra_body` `system` string still gets its cache breakpoint), OpenRouter's prompt caching and `provider` routing preferences, and the transport `stream` flag on Chat Completions, Messages, Copilot Messages, and native Ollama. The request path alone decides streaming: the wire file parser refuses a `stream` key in `body_defaults` or `extra_body` (reported, ignored), so no body rule can turn a stream into a plain request or back on any path. Native Ollama applies the body rules after its `options` shaping and local `num_ctx` enforcement, so a replaced `options` object carries neither.
- Headers: `ProviderAdapter._stable_request_headers(model_id, request_kwargs)` returns the request-context headers (`_request_headers_from_kwargs`, such as OpenCode Go's `x-opencode-session`) plus `extra_headers`. Every attempt adds them over the Adapter's rebuilt headers, so a profile header replaces an Adapter header of the same name, auth included. On Codex, Provider-level `extra_headers` never apply (`providers/openai.md`), but a profile's `request.extra_headers` does, on SSE requests and on the WebSocket handshake.

Coverage: `tests/core/providers/test_wire_request_rules.py` binds all three rules on each path (send and stream where they differ) through the shared request paths in `wire_paths_test_support.py`, which `test_wire_learning.py` uses too.

## HTTP, retry, and streaming

Streamed `tool_call_delta` values are true deltas: each Adapter reconciles its own wire snapshots at the boundary, and Chat appends every emitted name and argument delta verbatim without prefix heuristics. Responses Tool argument events append each delta exactly after reconciling the first event with any initial item snapshot and later `output_item.done`/terminal snapshots; repeated bytes and overlapping prefixes in later deltas are meaningful. Chat Completions arguments are true deltas; its decoder only drops a repeated whole Tool name that a compatible server resends on later fragments of the same slot. Messages, Gemini, and native Ollama emit each Call's name once or as one complete Call with its own identity (`test_repeated_name_is_deduplicated_but_argument_bytes_are_kept`, `test_argument_deltas_preserve_repeated_or_prefix_overlapping_fragments`, `tests/core/chat/test_streaming.py`). OpenAI, GitHub Copilot, OpenRouter, and LM Studio stream forwarding closes its nested generators before outer closure returns. This releases partial HTTP responses and the Codex WebSocket route lock deterministically.

- Chat Adapters construct HTTP clients through `_http_shared.build_async_client()` so timeouts and optional debug capture are consistent. Task clients use it too, through `ProviderTaskClient.http_client()`; they get a recorder only when `from_runtime(..., debug_context=...)` names a Run (`debug.md`).
- Stream and JSON request establishment goes through `_http_shared.connect_streaming_with_retry()` / `post_json_with_retry()`: the shared module owns the retry loop, per-attempt header rebuild, reading/closing error bodies before classification, and the fallback raise; adapters inject only their header builder, an error-status handler (detail formatting plus status classification), and optionally a transport-error wrapper. Rejected streaming responses close even when reading their error body fails or is cancelled; transport failures during that read use the same error wrapper as connection failures. The OpenRouter and OpenCode Go Responses streams use this connector with their own status classifier rather than private copies (`test_responses_error_body_read_failure_is_a_retryable_network_error_and_closes`). Rejection learning (`_wire_learning.py`) wraps around these calls, never inside them.
- Every streamed SSE/NDJSON body, including the Responses framers and Ollama's NDJSON, reads lines through `_http_shared.iter_stream_lines()` (complete bodies: `split_stream_lines()`), never `httpx.Response.aiter_lines()` or `str.splitlines()`. It decodes UTF-8 incrementally and ends lines only at CR, LF, or CRLF, including a CRLF split across chunks; U+2028/U+2029/NEL and other Unicode separators are legal unescaped inside JSON strings and stay in their data line (`test_http_shared.py`, `test_responses_stream_joins_split_crlf_and_keeps_raw_line_separators`).
- Chat wraps each Model attempt in the task-local `caller_owns_retries()` scope: `retry_async()` then makes one operation attempt, allowing Chat's shared budget to cover establishment, open-stream recovery, continuations, and Model fallback without multiplication. Other callers retain their normal retry policy; auto-refresh catalog discovery is the other caller-owned scope (`providers/catalog-discovery.md`). A caller-owned single attempt that fails logs nothing in `retry_async` - its caller logs what it catches; retry and exhaustion warnings otherwise count against the same total (`attempt n/<max_retries + 1>`). Bounded OAuth and rejection-learning repairs remain Adapter-owned; Chat's attempt count measures Model operation attempts, not every underlying protocol exchange. The recovery deadline begins at the first failure and also bounds subsequent streams on local routes; initial healthy local inference remains exempt from streaming stall windows.
- Non-streaming Adapter requests use the shared client's bounded connect/write/pool timeouts plus a 180-second read-inactivity timeout; this includes `ImageService.analyze()` because it uses `Adapter.send()`. Chat HTTP streaming calls build requests through `_http_shared.build_streaming_request()`, which alone disables the HTTP read timeout so Chat can own open-stream stalls with separate transport and Model-progress clocks. OpenAI Codex `send()` is semantically non-streaming but consumes an SSE/WebSocket exchange internally, so it applies the same 180-second inactivity bound between normalized events and maps expiry to `ProviderTimeoutError`. Remote Chat streams allow 180 seconds without a normalized delta or transport heartbeat and 900 seconds without a normalized Model delta. The shared SSE framer exposes comments separately; the OpenAI-compatible Adapter normalizes comments as transport-only heartbeats because OpenCode Go was verified to buffer a 40,560-character GLM-5.2 `write` Tool Call for 18 heartbeat intervals before releasing it as one Tool delta. Heartbeats keep the connection alive and feed the transient Run status but never count as Assistant, Reasoning, Tool, Usage, or finish progress. Incomplete SSE events and arbitrary raw bytes reset neither clock. Local/loopback Providers disable both streaming windows.
- The shared default classifies HTTP 401/403 as fatal auth errors, 429 and 502/503/504 as retryable, HTTP 500 as retryable only for explicitly declared idempotent requests, and Provider POST 500 as fatal; `classify_http_status()` requires every caller to declare idempotency so read-only GETs and non-idempotent POSTs cannot silently share the wrong branch. OAuth HTTP consumers wrap request/stream establishment with the shared `OAuthRequestRecovery` from `token_getter.py` (contract in `providers/connections.md`): an actual HTTP 401 classified as auth may refresh once, rebuild token-derived headers, and retry; the xAI OAuth flow additionally recognizes its exact token-rejection code on HTTP 403. Provider-specific entitlement classification runs first; static keys, ordinary permission 403, and failures after stream establishment do not enter recovery. All bundled OAuth Chat wires and task GET/POST share this mechanism; refresh failures stay outside the operation retry loop. Concrete Adapters or task clients can add verified codes through their explicit extra-status policy (Anthropic and embedding task requests opt into 529). Billed non-idempotent task generation applies the stricter `TaskRequestRetryPolicy` described below instead of blindly inheriting gateway retries. Retryable errors can carry parsed `Retry-After`, used as a capped floor over backoff with the attempt's bounded jitter added afterward so equal server hints do not synchronize clients.
- The shared default maps every `httpx.TimeoutException` to retryable `ProviderTimeoutError` and other transport failures to retryable `NetworkError`. Billed non-idempotent task generation overrides ambiguous read/write/remote-protocol failures as `ProviderOutcomeUnknownError`; malformed 2xx task results receive the same classification because the Provider may already have completed the operation. Chat malformed 2xx JSON and malformed SSE JSON remain non-retryable `ProviderError` with the decode error chained.
- Responses-shaped streams classify exact structured in-band error facts into the same auth, rate-limit, timeout, transient, or fatal exception taxonomy as establishment failures: the typed `error_type` (top-level, nested, or under `metadata`), a string or numeric `code`, the HTTP `status` (or `status_code`) that a wrapped WebSocket error frame carries, and `availability` router hints. Unknown codes stay fatal unless the stream state opts into leniency (OpenRouter; OpenAI, see `providers/openai.md`). OpenAI also sets `rejected_requests_fatal`, so an unknown code whose frame carries a client-error `status` other than 408 or 429 stays fatal; a router leaves it off because another upstream may accept the identical request. The raised message embeds compact error facts as trailing JSON - the error object plus the envelope's type, status, code, message, param, error type, metadata and availability, never a failed response's instructions, output or Usage, or a frame's headers - so code and status survive into persisted Run failures (`_classify_responses_stream_error` in `_responses_stream.py`; `test_responses_codec_decoding.py`, `test_openrouter_errors.py`, `test_openai_websocket.py`). A retryable error before visible Model output enters Chat's existing bounded restart/fallback policy; after visible output Chat preserves the partial turn and never replays the request. `response.incomplete` is a normal terminal event mapped to `output_truncated`, `content_filtered`, or `unknown`, and it can never authorize Tool dispatch.
- Generic OpenAI-compatible streams classify in-band `error` chunks through the shared `classify_in_band_provider_error()` (`core/providers/errors.py`), reading the typed `error_type` (top-level or under `metadata`), a string/numeric `code`, and an `availability.retryable`/`retry_after` router hint instead of treating every chunk as fatal. Classification is strict by default (unknown errors stay non-retryable); a concrete Adapter opts into lenient unknowns when its Provider can serve the identical request through another upstream, or when the Provider's own client retries unknown codes (OpenAI Responses). Every classified Mapping payload is embedded into the raised error's message as trailing JSON (`<summary>: {body}`, bare `{body}` when the payload has no message) so the Provider's structured detail - upstream message, code, router metadata such as OpenRouter's `metadata.raw` and `provider_name` - survives into persisted run failures, where the WebUI's existing trailing-JSON parser renders it in the collapsible details block and shows a summary message its prefix already starts with only once (`chatTimelinePresentation/messages.js::errorMessagePresentation`). Non-Mapping payloads stay plain text. The code sets are single-sourced there and reused, through `classify_in_band_error_type()`, by the Responses-shaped classifier above and by the shared Messages decoder (`_messages_stream.py`, inherited by Anthropic, MiniMax, OpenCode Zen/Go Messages routes and Copilot Messages). A Messages `error` event after HTTP 200 is classified by its documented `error.type`: `overloaded_error` and `api_error` are retryable, `rate_limit_error`/`timeout_error` map to the rate-limit/timeout errors, `authentication_error` is a fatal auth error, and request, permission, billing, not-found, size, conflict, and unknown types stay fatal while each decoder keeps its own message wording (`test_in_band_error_event_is_classified_by_its_documented_type`, `test_in_band_error_maps_to_the_shared_taxonomy_and_keeps_the_raw_body`).
- A Chat Completions `finish_reason=stop` is not trusted when `native_finish_reason` is `network_error` or `server_error`. Those chunks raise retryable `NetworkError` / `ProviderError` instead of a completed `stop`, so Chat's pre-visible stream restart can replay the request. A bare `finish_reason=network_error` still maps to terminal `error` (existing contract). Observed 2026-08-24 on OpenRouter `stealth/ox-alpha`: HTTP 200 SSE with empty `delta.content`, `finish_reason=stop`, and `native_finish_reason=network_error` - accepting that as `stop` made Chat persist an empty Assistant turn and die on `ChatMessageValidationError` with no retry.
- Outside caller-owned retry scopes, Adapter retry covers request/stream establishment. Mid-stream failures always propagate to the caller; Chat owns partial preservation and bounded recovery, including shared backoff for in-band errors carrying `Retry-After`. Only `ProviderStreamingUnsupportedError` triggers the nonstreaming fallback.
- Every Adapter `send()` and `stream()` path except the native Ollama wire runs establishment through the shared rejection learning in `_wire_learning.py`, which also owns the detection markers. `execute_learning_from_rejections` wraps a request, established when its reply arrives; `stream_learning_from_rejections` wraps a stream, established at its first delta, so an HTTP rejection or an in-band error event before that delta (the Codex WebSocket reports a rejected request as an error frame) is learned the same way, and every error after it propagates unchanged. Covered paths: Chat Completions (`OpenAICompatibleAdapter` and its subclasses), Messages (`AnthropicCompatibleAdapter`, including the MiniMax and OpenCode Go/Zen inner Messages Adapters, which share the outer Adapter's binding), the Platform `/responses` of `OpenAIAdapter` (OpenAI `api-key`, xAI, OpenCode Zen's Responses route), the Codex wire over SSE and WebSocket, the OpenRouter, GitHub Copilot and OpenCode Go Responses routes, GitHub Copilot Messages, and OpenCode Zen Gemini. Only a fatal, non-auth `ProviderError` whose detail blames something this request carried teaches, at most two lessons per request: (1) a sampling parameter (`temperature`/`top_p`/`top_k`) present at its protocol location (Gemini: `generationConfig.temperature`/`topP`/`topK`) and named next to a rejection marker (`unsupported parameter`, `not supported`, `does not support`, `unknown parameter`, `unrecognized ...`, `invalid parameter`) is recorded as a rejected parameter, which later requests drop; two or more such parameters the request carried, named next to a combination marker (`cannot both be specified`, `cannot both be set`, `cannot be specified together`, `cannot be used together`, `mutually exclusive`, `only one of`), are recorded as an exclusive group (`ObservedFacts.exclusive_parameters`, `+`-joined in `temperature`/`top_p`/`top_k` order), which later requests shape like a configured `request.exclusive_parameters` group, joined to the configured groups; (2) the effort value the request sent, named together with its carrier field (a generic `reasoning_effort`/`reasoning.effort` spelling, the dialect's dotted effort path, or a compound leaf such as `thinking_level`), is recorded as a rejected effort, which narrows the ladder; (3) the dialect's explicit off switch `thinking: {type: "disabled"}` (`thinking_toggle`, `thinking_toggle_with_effort`, `minimax_thinking`, `anthropic_thinking`), named with its value next to a rejection marker (here also `unsupported value`, `not allowed`, `cannot be disabled`), is recorded as rejected effort `none`. The resolver turns a learned `none` into `reasoning.off: "omit"` when the dialect has an off switch or `none` is no ladder rung, so Agent effort `none` then sends no reasoning field and leaves reasoning to the Provider; where `none` is a rung (`reasoning_effort`, `responses_reasoning`, OpenRouter's `effort: "none"`) it narrows the ladder like any other effort. After recording, the payload is rebuilt from the updated profile, every parameter rejected during this request, and every exclusive group member after the first, stays removed for its retry even when provider-config `defaults` or an explicit Model entry would refill it, and the request runs again; a rebuild that changes nothing re-raises. Auth and retryable errors (including OpenRouter's lenient structured HTTP 400s), a rejection of something the payload does not carry, a detail without a rejection marker, and an effort or off value the detail does not name propagate unchanged and teach nothing. Runtime-bound Adapters persist learned facts; a directly constructed Adapter keeps them in memory for its lifetime. Learned facts are layer 7: they outrank catalog values and rules, never a Model entry, so a configured profile keeps its shape for later requests (`providers.md` -> wire profile layers). This reactive net backs up the proactive wire-profile parameter rules (the Messages `drop_while_thinking` sampling drop, Anthropic's `supports_temperature` rule and `temperature`/`top_p` exclusive group, Kimi's sampling drop) and Responses allowlists for backends that accept a parameter for one model and reject it for another. Deliberately not learned: the native local Ollama wire (a local server accepts sampling in `options`) and OpenRouter's `reasoning: {enabled: false}` off, which carries no effort value. Tests: `tests/core/providers/test_wire_learning.py` (one case per path and lesson, the negative contracts), `test_openai_websocket.py::test_a_rejection_event_before_the_first_delta_is_learned_on_a_fresh_socket`, and the resolver case `test_wire_profiles.py::test_a_learned_none_rejection_omits_an_off_switch_or_narrows_the_ladder`.
- Every path also records what replies show (`WireBinding.observe_*`, `wire_observations.py`). The Chat Completions and native Ollama decoders record the readable field a Model's reasoning arrived in, because their carrier varies per Model; every path records that a Model returned reasoning: a non-streaming reply by its wire's content (Chat reasoning text or non-empty reasoning meta such as `reasoning_details`, a Messages `thinking`/`redacted_thinking` block, a Responses `reasoning` output item, Gemini thought text), a stream at the first `reasoning_delta` with text or `reasoning_meta` carrying reasoning details, encrypted content, reasoning items or content blocks - response ids, the raw Responses output and Gemini parts are no proof. A Model the catalog does not know that returned reasoning resolves `reasoning.supported: true`, and `/status` lists every learned wire fact (there, a rejected effort `none` is either a rejected explicit off or a rejected `none` rung).
- `retry_async()` stamps every caught `VBotError` with this retry loop's one-based `attempts_made` count before either retrying or rethrowing it. Provider-backed Tools may preserve that metadata in their failure envelope; a nested retry boundary reports its own operation-attempt count rather than an aggregate of lower-level HTTP attempts.
- Authorization headers are rebuilt inside every retry attempt so OAuth refresh remains effective.

The shared Responses SSE framer uses Provider-neutral error wording and includes the malformed/non-object data frame in the exception message so persisted failures retain the evidence (`test_stream_bad_frames_keep_evidence_without_naming_a_provider`).

## Provider-backed task clients

`ProviderTaskClient` is the shared HTTP base for speech, image, and embedding Provider clients. Its local structural Runtime/target Protocols avoid importing Runtime or `core/model_tasks/`. `from_runtime()` resolves the Connection and refresh-capable token getter. Task endpoints are OpenAI-compatible paths (`/embeddings`, `/images/...`, `/audio/...`) below the base that `ProviderAdapter.openai_compatible_base_url()` derives from the effective Connection or Provider base URL, looked up by the Provider's `adapter` selector in `adapter_types.py` without importing Runtime: most Adapters keep the configured base, while Ollama (local and Cloud) and LM Studio, whose configured base addresses their native API, append `/v1`. An unknown selector keeps the configured base. `post_and_parse()` puts request, status classification, and parsing inside `retry_async`, rebuilding headers per attempt. Keyed Connections contribute their configured auth header; a keyless `none` Connection contributes no auth header while still preserving Provider `extra_headers`.

`TaskRequestRetryPolicy` separates replay-safe calls from billed non-idempotent generation. The default preserves the historical retry behavior used by embeddings and STT. Image generation/editing and TTS use a non-idempotent policy: connect/connect-timeout/pool-timeout failures and HTTP 429 remain retryable because the operation was not accepted, while read/write/remote-protocol failures, unverified 5xx responses, and unusable 2xx results stop after one attempt with non-retryable `ProviderOutcomeUnknownError`. OpenRouter image generation explicitly verifies HTTP 503 as safe to retry; 502 and 504 remain ambiguous. Every call has one operation key; current image/TTS wires expose it only through the error and do not send an unverified idempotency header, while a future endpoint policy may name a verified header and `post_and_parse()` will reuse the same key on every attempt.

A refusal is a known outcome, not an ambiguous one. Before status classification, a 4xx JSON error body whose `error.code` is `moderation_blocked`/`content_policy_violation` or whose `error.message` contains "rejected by the safety system", "content policy" or "was flagged" raises non-retryable `ProviderContentRefusedError` (code `generation_refused`, `reason` = the provider message), also for HTTP 403, which would otherwise read as an auth failure. A task parser may raise the same error for a 2xx body that reports a refusal; `post_and_parse()` passes it through instead of converting it into `ProviderOutcomeUnknownError`. OpenAI sends `moderation_blocked`; OpenRouter forwards the upstream text under a numeric code (live-verified 2026-10-04). Coverage: `tests/core/providers/test_task_client.py::test_post_retries_only_what_its_policy_proves_safe`.

An optional structural `TaskRequestObserver` records each POST attempt after header preparation and before send, then receives raw Usage evidence plus any parsed result and its terminal status. Collection precedes response validation so rejected results retain measured consumption. GETs may enrich the latest create call without creating another Model call. Task-owned code projects telemetry into the canonical `UsageRecorder`; the Provider base never imports the accounting owner or persists payloads. This observation changes no request, replay, authentication or classification policy. Music's existing stream client uses the same lifecycle directly; image subscription handling keeps independently reported carrier Usage separate.

Task-specific payload/response semantics remain in `model_tasks.md` and its task references. `extra_options` is the common JSON escape hatch: empty placeholders are omitted while `0`, `0.0`, and `False` remain meaningful. Non-empty entries may add provider-specific fields but cannot replace any field already authored by the task wire; a collision rejects locally as a non-retryable `ProviderError` before the payload mutates or sends. Embeddings additionally reject their reserved identity/input/encoding/dimension fields during settings validation even when an optional field would otherwise be absent from a particular request.

## Usage normalization

Across Adapters, `input_tokens` means total prompt tokens including cached tokens. Optional `cache_read_tokens` and `cache_write_tokens` preserve Provider counters, while optional `reasoning_tokens` preserves a reported subset of output and never changes `output_tokens`. OpenAI Chat reads prompt/completion detail blocks, Responses-shaped wires read input/output detail blocks, and Anthropic Messages reads cache fields from input Usage plus `output_tokens_details.thinking_tokens` from final output Usage. OpenAI-compatible, Messages, Responses, and Gemini input and output counters are preserved independently: if either primary counter is absent or malformed, that field remains absent rather than becoming a measured zero. Boolean and negative counters are invalid; Messages cache counters contribute to total input only when both the primary input counter and each added cache counter are valid. Adapters omit unsupported or malformed optional counters rather than inventing zero; canonical Session aggregation and display semantics live in `chat/usage.md`.
