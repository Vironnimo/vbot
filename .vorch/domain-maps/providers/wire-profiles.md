# Wire Profiles

Read this reference when you change a wire profile file (`resources/wire/<provider>.json`) or a Custom Provider's Settings `wire` block, protocol or layer resolution, family defaults, rules and admission, learned wire facts, or wire status reads. The rule that per-Provider, per-Connection and per-Model request rules live in wire profiles rather than Adapter branches stays in `providers.md` -> Boundaries and invariants.

## What a profile holds

Request rules that differ per Provider, Connection, or Model - the protocol of an Adapter that speaks several, reasoning dialect, ladder and off/unset spelling, sampling and other parameter rules (drop, bounds, refusal, `exclusive_parameters` groups of which only the first carried parameter is sent), output-limit field/cap/alias collapse, Tool-call ids, replay scope, fidelity and carriers, media types, byte limits and the per-request image count (`media.request_max_images`), prompt caching, listing announced Tools in `tools[]` (`request.list_announced_tools`), whether the route serves On-demand Tools (`request.on_demand_tools`, default true), Model admission - belong in the Provider's wire profile file `resources/wire/<provider>.json` (for a Custom Provider, its Settings `wire` block) over the protocol defaults in `core/providers/_wire_protocol_defaults.py`. The shared Chat Completions and Messages codecs, the Responses routes (OpenAI, xAI, OpenCode Go, OpenCode Zen, OpenRouter, GitHub Copilot), OpenCode Zen's Gemini wire, GitHub Copilot's Messages builder, and the native Ollama wire apply them. The free-form `request.body_defaults`, `request.extra_body`, and `request.extra_headers` apply on every chat request path with one meaning (`providers/request-policy.md` -> Wire request extras).

Two rules are not applied by the shared Chat Completions codec: `allowed_parameters` (honored by the Responses routes and every GitHub Copilot wire) and `prompt_cache` (applied on Chat Completions by OpenRouter only). Per-conversation cache routing stays in Adapter code: `request_context_kwargs()` derives `prompt_cache_key` (Kimi, xAI) or the Codex cache-scope headers from the Session identity, which no static wire profile value can express; `request.prompt_cache` selects only the caching strategy of the wire.

## Protocol selection and admission

A profile-routed Adapter (GitHub Copilot, MiniMax, OpenAI, OpenCode Go, OpenCode Zen, OpenRouter, xAI) reads only its resolved wire profile's `protocol`, chosen among the Adapter's `WIRE_PROTOCOLS` (the first one is the default) in this order: the Model entry's Connection block, the Model entry, the last matching explicit rule, the catalog protocol hint, the last matching family default, the file's Connection block, the file defaults (`core/providers/wire_profiles.py::_Resolution._protocol`).

The catalog protocol hint is the Model's own AI SDK package from its Provider's models.dev section (`metadata.<provider>.npm`, projected at refresh from the per-Model `provider.npm` only, never the section default): `@ai-sdk/anthropic` -> `messages`, `@ai-sdk/openai` -> `responses`, `@ai-sdk/google` -> `gemini`, `@ai-sdk/openai-compatible` -> `chat_completions`; it applies only when the Adapter speaks that protocol, any other package is ignored, and its provenance is `catalog_hint`. A hint is a catalog fact: a hint-routed profile is `inferred`, not `configured`. Of the bundled Providers' models.dev sections, only OpenCode Go's and Zen's carry per-Model packages (2026-10-02); a section-wide `npm` is never projected, so single-protocol Providers and OpenAI keep their routing. Refresh carries the hint forward through a models.dev outage (`models/refresh.md` -> Refresh pipeline). A rule may match catalog facts such as GitHub Copilot's reported vendor and supported endpoints under `metadata.github_copilot` or the hint itself (`when.npm`).

A rule's `admission` (`available`, `restricted`, or `retired`, with a message) refuses a Model before network I/O, and discovery writes only Models whose profile admits them on the refreshed Connection (`providers/catalog-discovery.md`). New listed chat Models are available by default (`providers.md` -> Defaults and concrete exceptions).

## Profile layers

A profile resolves per `(provider, connection, model)` from ten layers, later ones winning: 1 the resolved protocol's code defaults, 2 the file's `defaults`, 3 its `protocols[<protocol>]`, 4 its `connections[<connection>]`, 5 matching `family_defaults`, 6 catalog-derived values (reasoning capability and control; on Chat Completions the models.dev `interleaved` field `metadata.<provider>.interleaved_field` as preferred response field and `replay.history_field`, unless it names a structured carrier such as `reasoning_details`), 7 matching explicit `rules` in file order, 8 observations learned from live traffic (learnable fields only), 9 the Model entry's `set`, 10 the Model entry's `connections[<connection>]`; the protocol is decided first (module docstring of `core/providers/wire_profile.py`). After layer 10, an output maximum a Provider rejection stated (`ObservedFacts.max_output_tokens`) bounds `request.output_limit_cap`: a cap only lowers the allowance, so the stricter of a configured cap and the stated maximum holds, with provenance `observed` when the stated one wins. Model facts enter a profile only through layer 6; a manual Custom Model's Reasoning switch is such a fact: off makes that layer set `reasoning.supported: false` (`models.md` -> Wire selectors and context windows).

## Family defaults

A family entry's `set.protocol` proposes its fallback route and scopes its other values to that protocol. A different exact catalog route therefore cannot inherit the old route's dialect or request fields. Use `reasoning.floor` for a fallback ladder; `reasoning.levels` is rejected in family defaults because it is an explicit override. Defaults never copy sibling prices, limits or modalities. Family inference does not create a verification record. Concrete known restrictions remain exact and Connection-scoped where needed; neither unknown compatibility nor an id suffix such as `-free` establishes a restriction.

## Wire reads and learned facts

Wire profile reads for accessors go through `core/providers/runtime.py::ProviderRuntime`: `wire_profile(provider, local_connection, model)` returns the resolved profile requests use (learned facts included), `wire_status(...)` its `(status, verification)` without resolving the profile (`WireProfiles.status`: the Model entry and matching rules only, so `model.list` can ask for every catalog Model), and `learned_wire_facts(...)` the `ObservedFacts` live traffic recorded.

Learned facts live in `<data-dir>/artifacts/wire-observations.json` (`WireObservations`, a disposable cache: format version 2, an unreadable or older file starts empty). Each rejected parameter or effort, and each stated limit (`max_output_tokens`, `context_window`, stored as `{value, learned_at}`), carries the time it was learned and expires after `REJECTION_TTL` (30 days), so a one-off or misattributed rejection heals by itself; reasoning carrier facts do not expire. A newer stated limit replaces the older one. `WireBinding.learned_context_window` reads the stated window for the Adapter (`providers/request-policy.md` -> Request limits and context). A learned `effort_updates_rejected` expires the same way (`providers/request-policy.md` -> Effort updates). How rejections and replies teach these facts: `providers/request-policy.md` -> HTTP, retry, and streaming. `forget_wire_facts(provider, connection=None, model=None)` drops facts on request - RPC `model.forget_wire_facts` (`model`: `<provider>` or `<provider>/<model-id>`, optional `connection`), CLI `vbot model forget-wire-facts`. `reload_custom_wire_profiles(custom_providers)` swaps the Custom Provider `wire` blocks into the shared `WireProfiles` (`Runtime.reload_custom_providers()` calls it), and `describe_reasoning_render(...)` describes a Custom Provider from that runtime profile (`providers/request-policy.md` -> Reasoning intent).

`model.list` and `model.get` (`server/rpc/model_methods.py`, mappers in `payloads.py`) add `wire_profiles`, keyed by local Connection id over the Model's usable allowed Connections: `{wire_status: verified|configured|inferred, verified_at: <date>|null}`: `verified` when the Model entry in the wire profile file carries a `verified` record for that Connection, `configured` when a Model entry or an `ids` rule names the Model, otherwise `inferred` (only defaults, catalog values, `prefix`/`metadata`/`family` rules and learned facts apply; `WireProfiles._status()`). `model.list` reads the cheap `Runtime.wire_status` (about 2 ms added for the ~875 Model x Connection targets of the bundled catalog); `model.get` resolves `Runtime.wire_profile` and adds `protocol`, `reasoning_dialect`, `reasoning_ladder`, `replay_fidelity` and `learned` (`reasoning_field`, `rejected_parameters`, `exclusive_parameters` (groups of which only the first is sent), `rejected_efforts`, `reasoning_returned`, `max_output_tokens`, `context_window` from `Runtime.learned_wire_facts`) - facts about fields and values, never request or response content. The WebUI's "verified" picker marker reads the `model.list` statuses (`webui/source-map.md` -> Shared dropdowns).

## Custom Provider wire block

A Custom Provider's optional Settings `wire` block is that Provider's wire profile file; it never uses a bundled one. It has the body of `resources/wire/<provider>.json` (`defaults`, `protocols`, `connections`, `family_defaults`, `rules`, `models`) without `format_version`, and `custom_provider_wire_file()` (`core/providers/wire_profiles.py`) parses it with the bundled-file parser (`parse_wire_profile_block()` in `_wire_profile_files.py`), limited to the `default` Connection and the Adapter's `WIRE_PROTOCOLS` (`chat_completions`); issue paths are dotted (`wire.defaults.reasoning.dialect`). `wire_profile_files(custom_providers)` merges the blocks over the bundled files for the Runtime and `scripts/verify_wire_profile.py`. The Runtime logs and omits invalid entries, and a block that is not an object counts as absent. `provider.custom_save` is strict: it refuses a block with any entry vBot would ignore (`invalid_request`, `data.wire_issues` lists them) and saves nothing; raw-file validation reports them as warnings (`providers/connections.md` -> Configuration model). A save applies live: `Runtime.reload_custom_providers()` -> `ProviderRuntime.reload_custom_wire_profiles()` -> `WireProfiles.replace_files()`, so already built Adapters, `/status`, and `model.get` use the new block from their next request (`test_custom_provider_wire_block_shapes_requests_live`).

Gotcha: a manual Model whose Reasoning switch is off yields `reasoning.supported: false` at the catalog layer, which beats the block's `defaults`, `protocols`, and `connections`; only a rule or Model entry can set `supported: true` again. A discovered Model whose listing carries no reasoning signal leaves support unknown (`null`), so the block's `defaults` decide for it.
