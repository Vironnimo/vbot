# Ollama Provider

Two Providers share Ollama-native catalog discovery but use different Chat transports: `ollama` owns the keyless local service at `http://localhost:11434`, including signed-in locally proxied `:cloud` Models, and speaks native `/api/chat` through `OllamaAdapter`; `ollama-cloud` owns the direct API at `https://ollama.com` with `OLLAMA_API_KEY` and speaks `/v1/chat/completions` through `OllamaCloudAdapter`. Both still discover through `/api/tags` plus `/api/show`. Keeping the Provider identities separate prevents identical wire Model ids in the local and direct catalogs from colliding in Model selection. Local wire facts were verified against Ollama 0.24.0 on 2026-07-07; direct Cloud discovery, authenticated inference, reasoning, Tool Calls, streaming, token Usage, and Account usage were verified live through 2026-09-02.

**The `local` Connection is disabled by default** (keyless Connections need an explicit opt-in - `providers.md` -> Terms -> Usable and `providers/connections.md`). Until the user enables it (Settings -> Providers toggle, `vbot provider enable ollama --connection ollama:local`, or the `connection.set_enabled` RPC), vBot never probes localhost, lists no Ollama Models, and refuses Adapter creation with a clear "connection is disabled" error. Enabling an auto-refresh Connection forces an immediate catalog probe so the caller gets live reachability feedback; "enabled but not running" is a valid state - the enable sticks and the Models appear on the next successful probe.

## Wire protocol

- Local non-streaming: `POST /api/chat` with `"stream": false` -> one JSON object: `message` (`content`, optional `thinking`, optional `tool_calls`), `done_reason`, usage counters `prompt_eval_count` (input) / `eval_count` (output).
- Local streaming: `"stream": true` -> **NDJSON lines** (one JSON object per line, no SSE framing); the final line has `"done": true` and may carry the usage counters. The adapter maps chunks to normalized deltas; a stream ending without a done chunk is a `NetworkError`; an in-band `{"error": ...}` line is a fatal `ProviderError`.
- Direct Cloud non-streaming: `POST /v1/chat/completions` with `"stream": false` -> OpenAI-compatible `choices[].message`, including optional `reasoning` and Tool Calls, plus `usage`.
- Direct Cloud streaming: the same endpoint with `"stream": true` and `stream_options.include_usage: true` -> SSE reasoning/content/tool deltas followed by a Usage chunk.
- Local Tool Call `function.arguments` is a JSON object; Direct Cloud uses the OpenAI-compatible JSON string. vBot's canonical arguments remain a dict and each adapter owns the conversion. Missing response ids get positional fallbacks.
- Local Tool results replay with native Ollama identity fields and Assistant reasoning via `thinking`; Direct Cloud replays the OpenAI-compatible Assistant/Tool shapes and uses the shared full-history policy unless an explicit Provider/Model override narrows it.
- Local sampling/runtime parameters ride under `options`: `temperature`, `max_tokens` -> `num_predict`, `top_p` - and the enforced `num_ctx` (see below). Direct Cloud uses the generic OpenAI-compatible top-level parameters. The direct Cloud Provider config pins `defaults.max_tokens: 65536` because the Cloud compat layer otherwise truncates at an internal `num_predict` of ~128; the catalog ceiling or an explicit caller limit still wins.
- Images are the only advertised media type on both transports. Local sends per-message `images` arrays of bare base64 strings; Direct Cloud uses OpenAI-compatible image blocks. Non-image media is rejected or degraded upstream via the wire-media intersection.
- Local errors use Ollama's `{"error": "..."}` shape; Direct Cloud uses the OpenAI-compatible error handling and SSE framing.

## Reasoning

Ollama thinking controls and replay are Model/template-specific. `/api/show` `capabilities` containing `"thinking"` marks support; unknown support sends no reasoning control because Ollama rejects controls on non-reasoning Models. Local Chat renders the capability metadata as native `think`: an active level intent sends the snapped level string, while off sends `think: false` except for GPT-OSS Models, which reject boolean false and therefore omit `think`. Direct Cloud renders confirmed support as `reasoning_effort`; its accepted vocabulary is `none`, `low`, `medium`, `high`, `max`, and vBot's `xhigh` normalizes to `max`. Responses and historical input on the compatible Cloud wire use `message.reasoning`, not the upstream Model template's internal `reasoning_content` name.

Discovery no longer stamps replay scope into Model metadata. The system default is `full_history`; `ollama-cloud.overrides.json` pins that Provider policy explicitly and narrows individual Models only when live transport evidence requires it. The Cloud chat wire declares `readable_only` fidelity, so readable Reasoning replays under the profiled carrier field and never alongside opaque meta. An unprofiled Direct Cloud Model uses the run-local response scan to select `reasoning_content` or `reasoning`; a verified Model profile wins over that scan.

The selected 13-Model Cloud audit was repeated on 2026-09-02 with streaming `/v1/chat/completions`, explicit `reasoning_effort`, `stream_options.include_usage`, real Tool shapes, with/without-carrier comparisons, and visible-content accounting controls. Every selected Model emitted Reasoning as `delta.reasoning`. Effective replay policy is: `full_history` for DeepSeek V4 Flash/Pro, GLM-5.2, GLM-5.3, GLM-5.3-Flash, and Kimi K3; `current_run` for Kimi K2.7 Code; `none` for MiniMax M2.7/M3, Nemotron 3 Nano/Super/Ultra, and Qwen 3.5 397B. The other six catalog Models were explicitly outside this audit and retain their existing profiles.

DeepSeek V4 is the request-shape trap that invalidated the earlier `current_run` verdict. A Tool-free cross-Run request ignores old Reasoning, but the Model's official contract says every prior Reasoning value must be sent when the current request carries Tools. Live cross-Run comparisons with Tools billed the `reasoning` carrier (+110 Flash, +102 Pro), and the corrected exact vBot Adapter/history path produced +20 for both Models with the carrier and zero without it. Both therefore inherit `full_history`; vBot keeps sending the history, and DeepSeek decides to ignore it only for Tool-free requests. Both expose the verified `low`, `high`, `max` ladder. The upstream Models document 384K output, but Ollama Cloud rejects `max_tokens: 384000` for both ids and reports a Provider maximum of 65,536, so their Provider profiles pin 65,536.

GLM-5.2, GLM-5.3, GLM-5.3-Flash, and Kimi K3 accept cross-Run `reasoning` with input-token deltas matching their visible controls. Kimi K2.7 Code accepts it only in-run; adding Moonshot's `thinking: {"type":"enabled","keep":"all"}` does not change Ollama Cloud's cross-Run zero delta, so it remains `current_run`. MiniMax M2.7/M3, all three selected Nemotron Models, and Qwen 3.5 strip readable Reasoning in both scopes. MiniMax additionally continues emitting Reasoning for `reasoning_effort: "none"` and for `thinking: {"type":"disabled"}`, so vBot marks Reasoning supported but advertises no false control for those two Models. Nemotron and Qwen stop Reasoning at `none`, so their on/off controls remain valid.

The native `/api/chat` and Anthropic-compatible `/v1/messages` probes produced no wider replay scope for the selected Models than `/v1/chat/completions`; the native probe must send explicit `think` or its result is invalid. `/v1/responses` is documented as non-stateful, lacks `previous_response_id` and `conversation`, and lists reasoning summaries rather than a historical Reasoning carrier or request effort control. It returns reasoning output items, but manually replaying those items for Kimi K2.7 Code and MiniMax M2.7/M3 changed Provider input tokens by zero with and without Tools while visible controls added 47 to 125 tokens. Direct Cloud therefore stays on `/v1/chat/completions`: it has the verified common Reasoning control, response/history carrier, streaming Usage, Tool, and image contract vBot needs. This is a Provider-wire decision, not a claim that the same endpoint is best for local Ollama.

## Catalog discovery

- `GET /api/tags` lists available Models. On the local service, an entry with `remote_host` is a proxied Cloud Model (`metadata.ollama.remote: true`; the `:cloud` name suffix is convention, `remote_host` is the fact), otherwise normalization stamps `metadata.ollama.local: true`. The direct `ollama-cloud` Connection is authoritative remote scope: its post-normalization finalizer removes any baseline local marker and stamps `metadata.ollama.remote: true` even though direct entries have no `remote_host`.
- `enrich_discovered_models` (the discovery POST hook) calls `POST /api/show` per model (bounded concurrency 8): `capabilities` list -> tools/vision/thinking; context window from `model_info["<architecture>.context_length"]` where `<architecture>` = `model_info["general.architecture"]` - **only that exact key**; a suffix scan would wrongly match `*.rope.scaling.original_context_length`. Absent architecture/key -> window stays honestly unknown.
- The `local` connection auto-refreshes **only while enabled** (startup + `model.list`, 30s throttle - `models.md` -> "Local catalogs auto-refresh"); Ollama down keeps the last known catalog. Each probe outcome is recorded (`Runtime.connection_reachability`) and surfaces as a "not reachable" marker on the connection payloads and as `reachable: false` on the affected `model.list` entries - the models stay listed and selectable.
- Direct Cloud catalog endpoints are public: explicit/system refresh can fetch `/api/tags` and enrich through `/api/show` without an API key because the Connection declares `catalog_requires_credentials: false`. Chat still requires a usable Account, so discovered Cloud Models are not selectable for inference until `OLLAMA_API_KEY` is configured.
- A refused/failed TCP connect is wrapped into a `NetworkError` that names the base URL and asks "is the Ollama service running?" (still retryable, unchanged classification) - so a chat against a stopped Ollama fails with the real cause instead of a bare socket error.

## Provider Usage

The usable `ollama-cloud:api-key` Connection participates in Provider Usage through authenticated `GET https://ollama.com/api/usage`. This endpoint was discovered and live-verified on 2026-08-09 but is not in Ollama's public API documentation, so its parser is strict and any HTTP or shape change must degrade to an unavailable snapshot without affecting Chat or Statistics.

The response's `limits.session.usage` and `limits.weekly.usage` are ratios; vBot multiplies them by 100 and projects the documented 5-hour and 7-day durations. Ollama returns no exact reset timestamps, window start, plan name, or extra quota headers, so vBot leaves those absent rather than inventing precision. Each window's `models[].request_count` values are summed only as observed requests: they are not total or remaining quota units because Ollama weights usage separately. The unrelated four-week `activity.cost` field is not a subscription-credit balance and is intentionally ignored.

## Effective context window / num_ctx enforcement

Ollama reports a local Model's *theoretical* max (262144 for an 8B model) and **silently truncates** the prompt when the loaded context is smaller. vBot therefore budgets flagged-local Models against the effective window (user knob or `min(32768, max)` - `resolve_effective_context_window`) **and enforces exactly that window on the wire**: the runtime injects `local_context_resolver` (keyword-only constructor arg, DI like `model_lookup`) into the adapter, which sets `options.num_ctx` on every send/stream for flagged-local Models. Direct `ollama-cloud`, locally proxied `:cloud`, and unknown Models are remote/non-local and receive no local cap or `num_ctx`. Settings are read live per call; verified via `GET /api/ps` -> `context_length` of the loaded local Model. Assumption == reality.

## Constraints & Gotchas

- **Read Ollama's official docs thoroughly before judging wire behavior** (see the hard prerequisite and evidence rule in `providers.md` -> Conventions and gotchas). Ollama exposes four wires on ollama.com: native `/api/chat`, OpenAI-compatible `/v1/chat/completions`, non-stateful `/v1/responses`, and Anthropic-compatible `/v1/messages`. A result on one endpoint or one Tools shape says nothing about another; use the exact Provider/Model profile and request shape under test.
- Direct Cloud Chat uses `/v1/chat/completions`; discovery and Account usage remain native `/api/tags`, `/api/show`, and `/api/usage` concerns. Do not infer that native `/api/chat` is broken from a probe that omitted its explicit `think` control.
- Direct Cloud MiniMax M3 may report `prompt_tokens: 0` for non-empty short and Tool requests and a positive value for longer requests. `OllamaCloudAdapter` treats only that impossible zero input count as absent, preserves measured output/reasoning/cache subsets, and lets Chat estimate the missing input field with field-level provenance. Positive prompt counts are preserved. `total_tokens` is never used to fabricate missing subsets.
- OpenAI-compatible Usage normalization accepts canonical nested `prompt_tokens_details.cached_tokens` / cache-write details plus observed gateway fallbacks `cache_read_input_tokens`, `cache_creation_input_tokens`, and `prompt_cache_hit_tokens`. Missing fields remain unknown; two repeated live MiniMax M3 requests exposed no cache counters, so vBot cannot claim a cache hit when Ollama reports none.
- Transport errors are mode-aware: local failures suggest checking the local service, while direct Cloud failures name Ollama Cloud and never suggest starting a daemon.
- The same wire Model id may legitimately exist in both catalogs. Preserve the distinct Provider ids `ollama/<model>` and `ollama-cloud/<model>`; do not fold direct Cloud back into an `ollama` Connection.
- `/api/ps` (loaded models + actual context) and `/api/version` are live-testing aids only - vBot does not consume them.
- Changing `num_ctx` between requests makes Ollama reload the model with the new window (slow first call after a knob change; expected).
