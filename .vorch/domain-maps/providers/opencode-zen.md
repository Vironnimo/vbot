# OpenCode Zen Provider

OpenCode Zen is a hosted gateway whose one Model namespace spans OpenAI Responses, Anthropic Messages, OpenAI Chat Completions, and native Gemini `generateContent`; the models.dev catalog protocol hint and its wire profile `resources/wire/opencode-zen.json` decide the exact per-Model routing and admission, and `OpenCodeZenAdapter` dispatches on the resolved profile.

## Interfaces

- Provider config: `resources/providers/opencode-zen.json`
- Adapter selector and owner: `opencode_zen` / `core/providers/opencode_zen.py::OpenCodeZenAdapter`
- Wire profile: `resources/wire/opencode-zen.json` (per-Model protocol and admission, reasoning, optional parameters, media, prompt cache)
- Connections: `opencode-zen:api-key` and `opencode-zen:account`
- Discovery: public `GET https://opencode.ai/inference/v1/models`, normalized by `OpenCodeZenAdapter` and enriched from the models.dev `opencode` section, including the protocol hint `metadata.opencode_zen.npm`
- Shared native Gemini transport/codec: `core/providers/gemini_compatible.py` and `_gemini_wire.py` (also used by Go)
- Generated projection: `resources/models/opencode-zen.json`

## Connections and Authentication

- `api-key` reads the shared OpenCode credential `OPENCODE_API_KEY` (also used by Go, including named Account suffixes); it never infers Connection type from credential text. The default request auth is `Authorization: Bearer`, while the Adapter replaces it with the exact header required by Messages (`x-api-key`) or Gemini (`x-goog-api-key`).
- `account` uses OpenCode's current JSON Device Flow at `https://opencode.ai/console/auth/device/code` and `https://opencode.ai/console/auth/device/token` with client id `opencode-cli`, as the official client uses since the console moved from `console.opencode.ai` (which now redirects there). The authorization answer carries a relative `verification_uri_complete` (`/console/device?user_code=...`); like the official client, vBot appends it to the server URL, giving `https://opencode.ai/console/console/device?...`. Observed and confirmed against the official client on 2026-10-08; a full login through the new host is not yet live-verified. Polling accepts the standard `authorization_pending` response, and refresh POSTs JSON and persists the rotated access/refresh pair. A definite refresh rejection (`invalid_grant`) quarantines the rotating token chain; server errors, other auth failures and ambiguous transport failures keep it and are not replayed automatically (`providers/connections.md`).
- Both Connections expose the same public Zen catalog and base URL. Both declare `catalog_requires_credentials: false`, so a refresh reconciles their projections even without an OAuth token; inference still requires credentials and enablement. Account identity changes only the credential slot and never the Model id, endpoint family, or catalog policy. Requests identify this client with `User-Agent: vBot`.

## Exact Model Routing

- Protocol and admission are resolved by the shared wire-profile owner. Exact catalog hints select Messages, Responses, Gemini or Chat; below those facts, `family_defaults` route GPT/Grok/Muse to Responses, Claude/Qwen to Messages, and Gemini to Gemini, with Chat as the Provider default. Qwen Max infers the latest Chat/toggle wire; exact `qwen3.7-max` retains its older Messages route. Other Qwen variants infer Messages. New GPT versions infer the latest verified Zen GPT floor (`low/medium/high/xhigh/max`) and map off to the lowest catalog-supported effort; exact older GPT exceptions retain their prior off behavior, and catalog ladders win. GPT-6.1 Sol's replay exclusion remains exact. Chat families inherit their latest Zen contracts: DeepSeek/GLM `low/high/max`, Kimi `max`, and Mistral Large `none/high` with captured-chunk replay (`meta_only`). Claude uses the current 5.5 floor, Gemini the current Argon floor, and Muse `minimal/low/medium/high/xhigh`; older differences remain exact corrections. These family patterns are inferred from the official Model table and existing local evidence (read 2026-10-15), not a verification claim for future ids. `send`, `stream`, response normalization, media support and request limits all read the same profile. Unknown ids and new free ids are available by default; exact known restrictions/retirements still fail before network I/O and are omitted by discovery. Literal wire ids never alias or silently fall back to another Model.
- Responses Models use `POST /responses` through the deep `OpenAIAdapter`; the Provider override hook classifies Zen errors on both non-streaming and streaming Responses paths.
- Messages Models use `POST /messages` through a borrowed `AnthropicCompatibleAdapter`, `x-api-key`, `anthropic-version: 2023-06-01`, non-strict Tool schemas, PDF/images, prompt-caching breakpoints (the Messages protocol's `request.prompt_cache`), only `temperature` when a request carries `temperature` and `top_p` (the Messages protocol's `request.exclusive_parameters`; Claude Haiku 4.5 rejected both, live 2026-10-03), and the outer connection-scoped HTTP client/token getter and wire-profile binding (`bind_wire_profiles` forwards it, so facts learned on the inner wire resolve into the same Connection profile).
- Chat Models use `POST /chat/completions` through `OpenAICompatibleAdapter` with bearer auth and the shared Tool, usage, terminal-outcome, and SSE contracts.
- Gemini Models use `POST /models/{model}:generateContent` and `POST /models/{model}:streamGenerateContent?alt=sse`. The shared `GeminiCompatibleAdapter` and `_gemini_wire.py` own native `systemInstruction`, `contents`, `generationConfig`, Function declarations/calls/responses, inline media, usage, finish reasons, and opaque thought-signature replay. Gemini's JSON omits zero counters: `thoughtsTokenCount` counts separately from `candidatesTokenCount`, so either one makes the output (a turn that only thought reports no candidates), and with a reported `promptTokenCount` a missing `cachedContentTokenCount` is a measured cache miss (`cache_read_tokens: 0`).

OpenCode's gateway may fail over between upstream suppliers serving the same requested Model. That is same-Model infrastructure routing, not a vBot alias or cheaper-Model fallback, and vBot must continue sending the exact selected id.

## Reasoning, Replay, and Prompt Caching

- Responses, Messages, Chat, and Gemini inherit the shared `full_history` replay default unless a wire-file rule narrows it; GPT-6.1 Sol pins `none` after the accounting checks above. `space-bunny-free` on Chat maps an Agent `none` selection to its verified lowest `low` effort; `qwen3.8-max` instead uses its verified binary `thinking.type` control. Both preserve readable `reasoning_content` in history. Gemini renders through the `gemini_thinking` dialect: the Model's exact models.dev effort ladder (else the current Gemini family floor `low/medium/high`), the closest supported level as `thinkingLevel`, Agent `none` as the lowest level (`off: "lowest"`), and visible thoughts (`includeThoughts`) because Google requires opaque `thoughtSignature` parts to accompany later turns and Function responses. Replay scope is never Model data; a legacy `reasoning_replay` key in an older generated snapshot or override is an unknown field that load ignores.
- Gemini normalization persists the complete native parts in `reasoning_meta.gemini_parts`; replay retains signed parts unchanged. After a stream break, unstarted trailing Function Calls are omitted to match the canonical executed prefix (`providers/request-policy.md` -> Chain of Thought); unsigned text has look-alike System Reminder tags neutralized (`chat/request-building.md`). Streaming (`_gemini_wire.py::GeminiStreamDecoder`) sends the cumulative `gemini_parts` snapshot after a part that carries more than text (a `thoughtSignature`, a Function Call), once the stream finished (before the terminal outcome), and before a stream error the Adapter raises, never per text chunk: Chat keeps only the newest snapshot, and one per chunk copied the growing list on both sides of the boundary (about 19 s of CPU for a 4000-chunk answer, 2026-10-22). A stream Chat itself cancels keeps the parts up to the last snapshot as interrupted evidence, which is never replayed (`test_gemini_stream_hands_over_every_part_without_a_snapshot_per_text_chunk`). Id-less Function Calls use the response-wide native-part position for fallback identity, so separate chunks cannot collapse parallel Calls; explicit Provider ids and retained replay parts remain unchanged. A prompt-feedback block without candidates is a terminal `content_filtered` outcome in both response modes. A stream without either a Gemini `finishReason` or a prompt block is an unknown transport outcome and fails rather than inventing success. Encoded Function arguments retain their original string through streaming accumulation so completed and streamed responses apply the same canonical validation and recovery; arguments inside retained native replay parts remain unchanged.
- The Messages protocol enables explicit compatible cache breakpoints (`request.prompt_cache: anthropic_breakpoints`). Responses and Chat retain their shared automatic-cache accounting. Gemini preserves `promptTokenCount` as total `input_tokens`, including the cached subset, and reports `cachedContentTokenCount` as `cache_read_tokens`; vBot does not invent a `cachedContent` resource or claim cache creation when Zen returned none. Missing or invalid Gemini primary counters remain absent so Chat can estimate them independently; explicit zero cache/Reasoning counters remain reported. Live cache effectiveness remains Provider/upstream-dependent. Cache-total, partial-counter, and cross-chunk id-less Call normalization are regression-tested in `test_opencode_zen_gemini.py`; the frequency of id-less Gemini chunks on live Zen remains unverified.

## Limits, Sampling, Tools, and Media

- Local Context estimation dispatches on the same resolved protocol as send and stream: Messages delegates to the inner codec, Responses/Chat use their inherited codecs, and Gemini counts native `contents`, `systemInstruction` and Function declarations. `_gemini_wire.py::gemini_input_payload` renders Gemini input for both estimation and sending, including media validation and Tool Result fallbacks. The shared token estimator reserves inline media and opaque thought signatures instead of counting encoded transport bytes as prose. Audio (WAV/OGG), video (MP4), and whole-request byte rejection are covered in both request modes by `test_opencode_zen_gemini.py`; these local regressions establish no new live gateway capability claim.
- Request output is clamped to the selected Model's catalog ceiling and remaining context. Gemini accepts exactly one effective output field and emits native `maxOutputTokens`; duplicate aliases collapse to the smallest valid value.
- Gemini validates `temperature` 0-2, `top_p` 0-1, positive integer `top_k`, penalties -2-2, integer seed, stop strings, supported JSON response formats, and Tool choice locally. Unknown request fields fail locally instead of leaking OpenAI-only parameters onto the Google wire. `parallel_tool_calls` is intentionally omitted because native Gemini controls parallel Function Calls without that OpenAI flag.
- Gemini supports inline PNG/JPEG/WEBP/HEIC/HEIF images, documented audio/video types, and PDF. Google's 20 MB inline request limit is the Gemini protocol's `media.request_max_bytes` (20,000,000), enforced before network I/O through `request_body_limit`; the Adapter enforces the 3,600-image maximum. The protocols' `media.types` declare the wire ceilings: Responses/Chat only their established image types, Messages images and PDF. Catalog modalities still intersect these wire ceilings at Chat ingress.
- All four wires preserve canonical non-strict Tool schemas and normalize Tool Calls, usage, and one terminal outcome. Gemini maps STOP, MAX_TOKENS, safety/content blocks, malformed/unexpected Tool Calls, and unknown reasons without treating every transport completion as successful generation. A malformed non-string `finishReason` becomes canonical `unknown` while preserving correlated Tool attempts for rejection.
- The shared Gemini codec sends canonical Tool schemas through `FunctionDeclaration.parametersJsonSchema`, never the restricted OpenAPI `parameters` field; schema keywords and optional fields remain unchanged. Google's [FunctionDeclaration contract](https://ai.google.dev/api/generate-content#FunctionDeclaration) defines these mutually exclusive fields (read 2026-10-28). Raw API-key probes of `gemini-4-argon` on both Go and Zen at their configured `/inference/go/v1` and `/inference/v1` `generateContent` endpoints reproduced HTTP 400 for `uniqueItems` under `parameters`; changing only the wrapper to `parametersJsonSchema` returned HTTP 200 and a Function Call. The production Adapter checks cover send, stream and streamed Tool continuation with that schema. This establishes the schema transport fix, not enforcement of every JSON Schema keyword or a full Model compatibility audit; account authentication and other Models were not live-tested. Regression coverage: `test_gemini_request_preserves_native_tools_media_thinking_and_replay` and Go's `test_no_wire_enables_strict_tool_schemas`.

## Errors, Regions, and Privacy

- Zen `AuthError` is reconnectable authentication failure. `CreditsError`, `MonthlyLimitError`, `UserLimitError`, and `ModelError` are fatal account/entitlement/Model-access failures even though Zen returns HTTP 401 for them. `RegionError` and `FreeTierError` are fatal HTTP 403 access failures. The latter preserves the status and explains that a replacement key cannot enable another client.
- All four account-authenticated wires use the shared OAuth recovery in `providers/connections.md`. The Messages error-detail hook preserves the complete error body so an error `name` or `type` survives even without a human-readable message; otherwise an entitlement 401 could incorrectly trigger token renewal. `test_opencode_zen.py` verifies the entitlement codes across all four wires and both request modes.
- After the Zen-specific checks, the Messages route keeps its Anthropic-compatible HTTP 529 `overloaded_error` retry; the other three wires use the shared status policy without 529 (`test_zen_error_policy_separates_auth_region_allowance_and_retryable_failures`).
- Gemini in-band errors with an HTTP-like `code` use the owning Provider's HTTP status policy, including transient 503 and rate-limit 429 recovery; errors without a recognized numeric status remain fatal. This applies after HTTP 200 has opened the stream and after a candidate finish; a prior `STOP` cannot hide a later explicit error. The shared Gemini transport preserves the structured error detail. Google's [retry guide](https://ai.google.dev/gemini-api/docs/troubleshooting) identifies 429/503 as retryable (read 2026-10-29); local Adapter regressions establish the classification here, not live gateway compatibility.
- Gemini stream establishment uses the shared connector in `http.py`; an error-body read failure or cancellation closes the rejected response before propagating, with the shared transport-error classification.
- All four wires, send and stream, run through the shared rejection learning (`providers/request-policy.md` -> HTTP, retry, and streaming). On Gemini a sampling rejection is attributed under `generationConfig` (`temperature`/`topP`/`topK`) and an effort rejection by the `thinkingLevel` field name (also spelled `thinking_level`); the request applies the profile's parameter rules, configured or learned, before the sampling parameters move into `generationConfig`.
- Stable allowance exhaustion markers such as `FreeUsageLimitError`, `GoUsageLimitError`, `BlackUsageLimitError`, monthly/weekly usage limits, and quota exhaustion make HTTP 429 fatal. A genuine burst `RateLimitError` remains retryable and honors `Retry-After` through the shared bounded retry policy.
- OpenCode documents Zen hosting in the United States. Standard paid requests are described as zero-retention except that OpenAI- and Anthropic-routed requests may be retained for 30 days; free Models permit data collection. Treat these as product/privacy constraints, not Adapter behavior, and re-check them before making deployment or compliance promises.

## Constraints & Gotchas

- Do not replace this composite Adapter with a generic OpenAI-compatible JSON entry: header selection, protocol dispatch, Gemini translation/signature replay, terminal outcomes, and Zen error semantics are genuine Adapter code. Per-Model routing, admission, reasoning controls, parameters, media, and caching belong in `resources/wire/opencode-zen.json` (routing also in the projected catalog protocol hint), not in Adapter tables or hand-written Model metadata.
- Do not inherit OpenAI Codex discovery query parameters or ChatGPT account headers merely because the outer Adapter extends `OpenAIAdapter`; the inherited hooks apply them only to a `codex_responses` Connection, and Zen overrides `accepts_discovered_model` to keep every entry instead of inheriting OpenAI Platform's task-family exclusions.
- The public catalog proves presence, not entitlement, regional availability, Tool correctness, caching, or successful inference. Regression tests use mocked provider responses; the dated live checks above establish only their stated Model/Connection/request shapes and limitations.
