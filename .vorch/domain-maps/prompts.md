# Prompts

System Prompt assembly as a block model: every contribution to the prompt is a declared block, ordered by a per-scope layout, gated, and joined deterministically.

## Overview

`core/prompts/` owns the product-facing System Prompt domain. The System Prompt is assembled from **blocks**: each piece of the prompt (shared Runtime, Identity Environment, Working Project context, tools/channels/skills text, SOUL, a config agent's body, pinned memory, and any tool/extension/user contribution) is one block with a stable id, an owner, and a content kind. A per-scope **layout** decides their order and on/off state; three **gates** decide which blocks render; the survivors are trimmed and joined. The domain also expands prompt variables, renders the tool/skill/channel/memory lists, validates the public block edit/layout requests, and filters provider tool schemas through prompt-time Agent policy.

It does not own raw file I/O, workspace memory, HTTP/RPC transport, or tool execution. `core/storage/` persists the layout and per-block text overrides (`PromptBlockStore`) and the bundled fragment resources; `core/memory/` declares the memory block and renders its files; `core/tools/`, `core/skills/`, `core/channels/` provide catalogs; `core/extensions/` declares extension blocks; `core/chat/` sends the assembled system message whole (nothing is appended at runtime); `server/rpc/operations_methods.py` maps `prompt.*` to this domain.

The module is split into the pure assembly engine (`blocks.py`) and the manager facade (`prompts.py`). The engine takes everything **injected** — the definition list, the layout, an override resolver, the producers, and the owner-active inputs — so it is fully unit-testable with no storage, RPC, or runtime wiring.

## Terms

Domain-specific vocabulary for System Prompt assembly. These are all prompt-domain internals; no core prompt term lives in the glossary.

### Prompt Block
**Definition:** The unit the System Prompt is assembled from — an ordered, gated contribution that is either an editable **text** block (its text may carry `{include:…}` and `{generated:…}` markers) or a non-editable **data** block (SOUL, Working Project context, the config-agent body, an auto-list, or a dynamic render function). Every contributor (core, a tool, an extension, the user) hands the prompt domain a block *definition*; the System Prompt is the layout-ordered, three-gate-filtered, normalized concatenation of the surviving blocks.
**Not:** A prompt fragment. The old closed set of five editable fragment files (`system.md`/`runtime.md`/`tools.md`/`channels.md`/`skills.md`) is gone — a block is fragment-sized but reorderable, toggleable, gated, and contributable from any source.

### Block Layout
**Definition:** The persisted, per-scope ordered list of `{id, enabled, source}` that owns a scope's block order and on/off state, stored as `layout.json` under the scope (default scope in `<data_dir>/prompts/`, agent scope under the agent dir). A block absent from the layout is inserted at its definition's `default_rank` with its definition's `default_enabled` state (ranks never come from this file; an opt-in block like the tool list defaults in off); a layout entry whose definition is gone is inert — skipped at build, pruned on the next write.
**Not:** The block definitions or their text. The layout owns order + enabled only; a block's text/owner/kind/source live in its definition and per-scope text override, never in `layout.json`.

### Block Owner (three-gate filter)
**Definition:** A block renders only when **all three** gates hold: user-enabled (its layout entry is on) ∧ owner-active ∧ non-empty (rendered text non-empty after marker/include expansion). The **owner** — `always` / `identity` / `memory` / `tool:<name>` / `channel` / `extension:<name>` — is gate 2: `identity` means the Agent has an Identity/Memory Workspace, a `channel`-owned block drops entirely when the agent has no active channel, and the memory block renders whenever the memory tool is on, even with empty memory files.
**Not:** The Source prefix. Owner is the per-agent/run activation condition (gate 2); the source prefix is provenance. They reuse the words `tool:`/`extension:` but are distinct fields on the block.

### Source prefix
**Definition:** The namespace before the first colon in a block id — `core:` / `tool:` / `extension:` / `user:` / `memory:` — naming where the block came from and mapping to its on-disk override folder `blocks/<namespace>/<slug>.md` (the colon itself never reaches the path; Windows-safe). A separate field from the owner.
**Not:** The Block Owner. Source is provenance (and the disk path); owner is the gate-2 activation condition — even though both can read `tool:`/`extension:`.

### Producer
**Definition:** A function registered under a marker name that renders a `{generated:NAME}` placeholder inside a block at build time — the auto-lists `tool_list` / `skill_list` / `channel_list` and `memory_files`. An unknown marker renders to empty with a warning (fail-soft); an empty producer result leaves no residue after normalization.
**Not:** A dynamic block. A producer fills one marker inside an otherwise-static editable block; a dynamic block's entire body is a render function (a deliberate cache break).

## Data Model

A **block** (`BlockDefinition`) is the immutable unit a contributor hands to the prompt domain:

- `id` — fully-qualified `<source>:<slug>` (e.g. `core:runtime`, `memory:guidance`, `extension:my_block`, `user:notes`). The **source** is the namespace prefix before the first `:`; it is an open string, not a closed enum — a contributor may use any non-empty prefix, and an id with no `:` is a contract error. `BlockSource` names the common sources (`core`/`tool`/`extension`/`user`/`memory`) for typed comparison without a string literal.
- `owner` — drives gate 2 (is the owner active for this agent/run). Owners: `always` (always active), `identity` (the Agent has a non-empty Identity/Memory Workspace), `memory` (the memory tool is enabled), `channel` (at least one active+enabled+running channel for the agent), `tool:<name>` (the tool is on the agent's effective allowlist), `extension:<name>` (the extension is in the loaded-extension set). The source says *who shipped* the block; the owner says *when it renders* — they reuse `tool:`/`extension:` but are distinct.
- `kind` — `text` or `data`. A **text** block flows through the override cascade and may carry `{generated:…}` / `{include:…}` markers and runtime placeholders. A **data** block is not user-editable (SOUL, Working Project context, a config-agent body, and any dynamic render block); its `default_text` is inserted **verbatim** (its `{…}` is never interpreted) and a data block that needs expansion uses a `render` function instead.
- Exactly one of `default_text` (static block) / `render` (dynamic build-time function) is set — enforced at construction. `editable` (a convenience for the metadata surface) is true only for a static text block with a default.
- `default_rank` — where a block sorts when it is absent from the layout (a newly added contributor defaults in at its rank, ties broken by id).
- `default_enabled` — the enabled state a block defaults in with when absent from the layout (default `True`). `False` ships an opt-in block that stays off even under an older persisted layout; an explicit layout entry always wins.

The **core/data block ids** (constants in `prompts.py`): `core:runtime`, `core:identity_runtime`, `core:tools`, `core:tools_list`, `core:channels`, `core:skills`, `core:skill_maintenance` (text, built from prompt resources), `core:soul`, `core:working_project`, `core:agent_body` (data, per-run content), and `memory:guidance` (text, declared by the memory domain). `core:identity_runtime` has owner `identity`; `core:skill_maintenance` has owner `tool:skill_manage`/`BLOCK_OWNER_SKILL_MANAGE`, so each renders only for an Identity Agent satisfying its gate. `core:tools_list` is the full name/description Tool list and ships **disabled** (`default_enabled=False` + `enabled: false` in the bundled layout): Providers already receive every Tool's description in the native Tool definitions, so the prompt copy is an opt-in booster for Models that attend poorly to Tool schemas. A **custom user block** is `user:<slug>`, owner `always`, a static text block whose override file *is* its content (no default text).

A **layout** is an ordered list of `LayoutEntry` (`id`, `enabled` default true, optional `source`). The `source` is persisted per entry so an entry whose definition is momentarily gone (a contributor removed between writes) can still be ranked by its namespace. The **scope key** is `default` or `agent:<id>`; an agent scope is owned only by an Agent with `custom_system_prompt_enabled: true`.

The **bundled default layout** lives in `resources/prompts/layout.json` (data, not code) and ships this order: `core:soul`, `memory:guidance`, `core:runtime`, `core:identity_runtime`, `core:tools`, `tool:project`, `tool:subagent`, `core:tools_list` (disabled), `core:channels`, `core:skills`, `core:skill_maintenance`, `core:agent_body`, `core:working_project`. A missing/malformed file reads as an empty layout (every block then defaults in at its rank — a broken layout never takes a build down).

The seven core text blocks read their **default text** from the editable fragment resources `runtime.md`, `identity_runtime.md`, `tools.md`, `tools_list.md`, `channels.md`, `skills.md`, and `skill_maintenance.md` (the bundled resource for the default scope, the agent copy for an agent scope). The non-editable dynamic `core:working_project` block renders through the separate bundled template `working_project.md`; model-facing framing remains in that file rather than Python. `tools.md` carries only the cross-tool call-style guidance; the `{generated:tool_list}` marker lives in `tools_list.md`. `system.md` is no longer a prompt block — the old root fragment is gone; the block layout replaced it. Backend-only fragments are storage-readable but never prompt blocks. There is no fragment-edit facade anymore — the old `PromptFragmentManager` / `prompt.update_fragment` surface has been removed; the only prompt-edit surface is `SystemPromptManager`'s block facade below.

## Assembly Pipeline

`assemble_system_prompt(definitions, layout, context, *, owner_activity, override_resolver, producers, replacements)` is the deterministic entry point — same inputs always produce the same output (the prompt cache depends on this):

1. **Dedupe** definitions by id, first-collected wins, logging both sources on a collision (mirrors the extension tool-collision policy). The core/data/memory blocks are collected first, then contributed blocks, then custom blocks — so a contributor or custom block can never shadow a core id.
2. **Resolve layout** into the effective ordered `(definition, enabled)` list: a layout entry with a matching definition keeps its order + `enabled`; an entry with **no** matching definition is inert (skipped, never an error — pruned on the next write); a definition **absent** from the layout is appended after the laid-out ones at its `default_rank`. The user's chosen order is never disturbed by a new block.
3. **Resolve each block's text**. Dynamic block: call `render(context)` in isolation — any exception logs a warning and drops **only that block**, never the run. Static text block: take the override cascade result (else `default_text`), expand `{generated:…}` (producers) then `{include:…}` (workspace files) — both fail-soft — then apply the build-time `replacements`. Static data block: `default_text` verbatim, no expansion.
4. **Three gates** (`passes_gates`) — a block renders only when **all three** hold: (1) user-enabled (its layout entry is on; a defaulted-in block follows its definition's `default_enabled`), (2) owner-active (delegated to the injected `OwnerActivity` — never hardcoded), (3) non-empty after trim.
5. **Normalize** — trim each surviving block, drop empties, join with exactly one blank line (`\n\n`). No leading/trailing blank line, no double blank between blocks, an empty block/marker leaves no trace. This is the contract that replaces the old blank-line padding trick — the prompt is content-equal but not byte-identical to the pre-block format (the old format deliberately abandoned).

### Producers (`{generated:NAME}`)

A producer turns build-time inputs into the text a `{generated:NAME}` marker expands to. The manager builds them as closures over the registries it already holds: `tool_list`, `channel_list`, `skill_list` feed the core tools/channels/skills text blocks, and `memory_files` renders the pinned-memory entries (each scope under its heading label with its `- ` bullets) for the `memory:guidance` block (the file reading lives in `core/memory/read_memory_files`). An **unknown** marker renders to `""` with a warning — fail-soft, like a missing `{include:…}`, never a `PromptError`. `BlockRenderContext` carries **no conversation messages** — message-dependent content belongs to the `context` extension hook, not the System Prompt.

### Runtime variables (replacements)

`{server_hostname}`, `{vbot_version}`, `{os}`, `{model}`, `{identity_workspace}`, `{vbot_root}`, `{data_root}`, `{thinking_effort}`, and `{current_date}` are the only plain-text replacements applied to text blocks at build (`apply_replacements`, per-key `str.replace`, never a format engine — an unrelated `{…}` is left untouched). The retired `{host}`, `{app_version}`, `{agent_workspace}`, and `{app_dir}` names have no compatibility aliases and remain literal in persisted custom prompts. `runtime.md` is owner `always` and carries only OS, Model, thinking level, date, and the current-time Tool hint. `identity_runtime.md` is owner `identity`, presents itself model-facing as `## Identity Environment`, and carries the server hostname, vBot version, Identity/Memory Workspace, vBot root, and data root; Project Config Agents therefore never receive those identity/server paths. `{current_date}` is the UTC ISO date only.

### Override cascade

A static block's effective text resolves **agent override ← default-scope override ← owner default** (`definition.default_text`). The agent layer applies only on an agent scope. A dynamic block has no override path; it always renders from its `render`. The cascade is composed by the manager from the `BlockStore`'s two reads, not by the store.

### Data blocks

- `core:soul` renders the workspace `SOUL.md` through the single `{include:…}` expansion path (so fail-soft never drifts from a normal include), then prepends the `SOUL_FRAMING` identity line so the model reads SOUL as its core operating contract, not as neutral file content. The framing stays out of the shared `wrap_include_file` (so it never leaks onto MEMORY/USER/project includes) and out of the render's empty case: when the file is missing or the workspace is `""` (a config agent) the render returns `""` before any framing, so the whole block gates out clean.
- `core:working_project` renders the file-backed `working_project.md` template from `ProjectPromptContext` (`project_id`, display name, Project Workspace path, ordered auto-load list). A Project Config Agent always receives this block for its addressed Project, including when no auto-load file is readable; a Rooted Identity Agent receives Chat's already-rendered, Session-pinned `working_project_context`, which wins without another file read; an Unrooted Identity Agent has no Project context and the block gates out. The template labels the Identity/Memory Workspace and Project Workspace independently when both blocks render. `render_project_files` remains the unframed live file renderer for the explicit `project` Tool result. Auto-load paths are taken **verbatim with no location restriction** — relative resolves against the Project Workspace at any depth, absolute is read as-is. File reads are lazy and fail-soft; missing/unreadable files are skipped and never abort the run.
- `core:agent_body` carries a config agent's verbatim prompt body as `data` default text (substituted as-is, its `{…}` never re-interpreted — like an include). Empty for identity agents → gates out.

## Interfaces

- `SystemPromptManager.build_system_prompt(agent, scope=None, *, agent_body="", project_context=None, working_project_context=None, skill_registry=None, skill_catalog=None, effective_tool_names=None, session_tool_grants=(), read_paths=None) -> str` collects the full block-definition list for this agent/run and routes it through `assemble_system_prompt`. `working_project_context`, when present, is emitted verbatim by `core:working_project` and prevents that block from reading `project_context`; it pins only the Rooted Identity Agent's Working Project block, not the rest of the System Prompt. `read_paths` is a pure side channel for files actually read during this build; a pinned Working Project block reports its files only when Chat originally renders the snapshot, never on reuse. With no explicit scope the manager uses the agent scope only when `custom_system_prompt_enabled`; otherwise default. `agent_body`, the normal `project_context`, and Skill/Tool inputs retain their existing behavior.
- For a Rooted Identity Agent, SOUL and pinned Memory still render from Workspace while `project_context` comes from the admitted explicit working Project. Live Run, compaction rebuild, and preview share that resolver and fail closed when the selected Project cannot be resolved.
- The `core:skills` catalog is **origin-grouped**: `_format_skill_list` groups the filtered skills into `<skill_group label="...">` elements by `SkillMetadata.origin` (ordered bundled → global → project '<name>' → agent), path-free. `SkillPromptMetadata` carries `name`/`description`/`origin`; the labels are English prompt strings owned here, the origin vocabulary comes from `core.skills` (`skill_origin_sort_key`, `SKILL_ORIGIN_*`). `render_skill_catalog(agent, skill_registry=None) -> PinnedSkillCatalog` renders the snapshot (the grouped catalog text) the chat loop pins.
- `ProjectPromptContext.from_project(project_id, project_name, cwd, auto_load)` captures the presentation fields needed by `core:working_project`; `cwd` is exposed to the Agent as its Project Workspace, not as an Identity Workspace.
- `SystemPromptManager.render_working_project_context(project_context, *, on_read=None) -> str` renders the exact file-backed Working Project frame and readable auto-load files; Chat owns its Session persistence for Rooted Identity Agents. `render_project_files(project_context, *, on_read=None) -> str` remains the unframed live renderer for the explicit `project` Tool. `render_project_skills(project_name, skills) -> str` remains the Tool result's path-bearing Project Skill list.
- `SystemPromptManager.provider_tool_definitions(agent, *, session_tool_grants=()) -> list[dict]` returns provider-ready tool schemas filtered by the agent's effective Tool availability. It applies the memory and identity-only derived-visibility passes, then lets an ephemeral Session grant add its matching Session-scoped Tool independently of the Agent allowlist. It takes no skill-registry/catalog params — Tool presence is never derived from the pinned Skill catalog.
- `SystemPromptManager.update_block_definitions(block_definitions, loaded_extensions)` is called by the runtime on every extension/skill reload so the contributed-block list and gate-2's `extension:<name>` membership refresh without a restart. `update_skill_registry(skill_registry)` refreshes the skills catalog the same way.
- `SystemPromptManager.vbot_root` (read-only) exposes the vBot installation or source root the manager was built with.

**Block-edit facade** (the `prompt.*` RPC surface; lives on the manager beside assembly so listing, override, layout, and create/remove all share one definition collection and scope resolution):

- `list_scopes()` → `default` plus every Agent with `custom_system_prompt_enabled`. Each agent-scope entry carries `has_customizations` (bool): true when that scope owns a saved layout and/or at least one editable-block text override (read straight off the `BlockStore`; a `user:` custom block is caught by the saved-layout check). The default-scope entry carries no such key. The editor uses it to confirm before disabling an agent's custom prompt.
- `list_blocks(scope=None)` → per-block static metadata in layout order: `id`, `owner`, `kind`, `editable`, `enabled` (the scope's on/off), `rank`, `source`; editable text blocks also carry their effective `text` (cascade result) and `is_modified`; an agent scope adds the `inheritance` layer per block (`agent_override` / `default_override` / `owner_default`). Non-editable blocks carry only read-only metadata. "Owner currently active?" is deliberately **not** here — that is the preview's job.
- `update_block(id, content, scope=None)` writes a text override (autosave) — only an **editable** block accepts one; updating a data/dynamic block is a `PromptError`. `reset_block(id, scope=None)` drops the scope's override → the inherited/default text; a `user:` block has no default to reset (delete it instead).
- `set_layout(layout, scope=None)` persists order + on/off, **tolerating** a contributor-gone id (the store prunes any entry with no live definition on this write, so a reorder never errors on a vanished contributor). `reset_layout(scope=None)` overwrites the scope's `layout.json` with the bundled default (text overrides untouched).
- `create_block(slug, content=None, scope=None, *, position=None)` creates a custom `user:<slug>` block (override file + layout entry; slug validated with the canonical agent-id rule; must not collide with an existing `user:` block). `remove_block(id, scope=None)` deletes a `user:` block (override file + layout entry) — only a `user:` block is removable; a core/tool/extension block is toggled off, never deleted.

RPC: `prompt.list`, `prompt.update`, `prompt.reset`, `prompt.set_layout`, `prompt.create_block`, `prompt.remove_block`, `prompt.reset_layout`, `prompt.preview` (see `server.md`). `prompt.preview` returns rendered `text`, `tokens`, `tool_tokens`/`tool_count` (the provider tool-definition array's estimated footprint), and `estimated`; for an explicit agent scope the server infers `agent_id` from the scope, otherwise the `agent_id` param is an `agent@projekt` address.

## Conventions

- Prompt-domain code depends on Protocols for the Agent, Tool, Skill, Channel, and Storage shapes; it imports no concrete AgentStore/ChannelService/StorageManager/ConfigAgent/tool classes. The contributed-block list arrives as plain `BlockDefinition` objects (tools and extensions hand their definitions in via the runtime — see `tools.md`/`extensions.md`), so the domain never imports a tool or extension class.
- The bundled block default texts are **English Markdown in resources** (`resources/prompts/*.md` + `memory:guidance`'s prose in `core/memory/`), a deliberate, signed-off i18n exception: the System Prompt is the model-facing English contract, not a localized UI string.
- `{include:filename}` accepts only a safe flat filename, resolves under the agent workspace, wraps as `<file name="…">…</file>`, and drops missing **or unreadable** files with a warning (a prompt file never aborts the run); an **unsafe** include path raises `PromptError` (a malformed directive, not a readability issue). An **empty workspace** (`workspace == ""`) drops every `{include:…}` with no read — it must never resolve against `Path("")` (= `Path(".")`), which would read SOUL.md/USER.md from the server's CWD.
- The `core:channels` block is owner `channel`, so with no active channel it gates out entirely — **no more `- None`** fallback line. Its producer is only ever invoked when at least one channel is active. A single allowed chat id shows `default target available`; multiple/zero require an explicit target.
- Skill prompt metadata is XML-escaped before insertion. Escaping stays in `core/prompts/`; Skills owns discovery/availability, not prompt serialization.
- Provider Tool permissions/schemas come from ordinary effective Agent availability plus ephemeral Session grants; the `core:tools` (call style) and `core:tools_list` (opt-in description list) blocks control only prompt-visible text, not Tool access. The dynamic `tool:project` block lists registered Projects with id, display name, absolute cwd, reachability, and the Rooted Identity Agent's current Project marker; its owner gate makes it appear only when the effective `project` Tool is available. The optional root `tools.subagent.allowed_agents` setting contains additional targets only: an explicit list narrows the Sub-Agent schemas to the calling Agent plus those values, an empty list is self-only, and a missing setting or wildcard retains free optional addressing. The Tool descriptions stay target-agnostic; the dynamic `tool:subagent` block lists the currently resolvable additional Agents by id, name, and description, explains implicit self-delegation, and is rendered exactly when the effective `subagent` Tool is available. A live Run passes the exact provider Tool names and the Agent's addressing Project into prompt assembly so both blocks agree with provider visibility and Identity-versus-Project routing; prompt preview supplies the same addressing scope.
- `memory_prompt_mode` controls both the `memory:guidance` block (gate 2, owner `memory`) and the derived provider visibility of the `memory` tool. `agent`/`agent_user` make `memory` available even with an empty `allowed_tools`; `off` removes it from prompt and provider definitions.

## Constraints & Gotchas

- Prompt RPC error behavior is split: block list/update/reset/layout/create/remove and preview scope validation map `PromptError` → `invalid_request`; assembly/storage/runtime failures during preview go through the normal domain-error path.
- User block-text overrides and the per-scope `layout.json` in the data dir must be preserved unless reset explicitly. Agent-scope blocks/layout are owned only when the Agent's `custom_system_prompt_enabled` is true; the store ignores an agent scope's files while that flag is false.
- Prompt preview uses the runtime's live `SystemPromptManager`, so it reflects the current Skill registry, normal Tool registry, Channel state, loaded extensions, layout, and overrides. For a Rooted Identity Agent it renders the Working Project frame as a prospective new-Session snapshot but does not persist one. It has no Session snapshot and therefore supplies no Session grants; Session-scoped Tools such as `history` are absent. No `scope` parameter shows the Agent's effective baseline prompt; `scope: {type: "default"}` previews the default scope.
- Chat builds the system prompt for every request and omits the provider system message entirely when the assembled prompt is empty or whitespace-only.
- Do not move block behavior into Agent or WebUI code. Agents own only the `custom_system_prompt_enabled` flag and workspace path; WebUI owns editing UX; this domain owns assembly semantics and the block contract.
