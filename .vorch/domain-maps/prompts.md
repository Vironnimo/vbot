# Prompts

System Prompt assembly as a block model: every contribution to the prompt is a declared block, ordered by a per-scope layout, gated, and joined deterministically.

## Overview

`core/prompts/` owns the product-facing System Prompt domain. The prompt is assembled from **blocks**: each piece (shared Runtime, vBot Environment, Working Project context, tools/channels/skills text, SOUL, a config agent's body, pinned memory, and tool/extension/user contributions) is one block with a stable id, an owner, and a content kind. A per-scope **layout** decides order and on/off state; three **gates** decide which blocks render; survivors are trimmed and joined. The domain also expands prompt variables, renders the tool/skill/channel/memory lists, validates public block edit/layout requests, and filters provider tool schemas through prompt-time Agent policy.

It does not own raw file I/O, workspace memory, HTTP/RPC transport, or tool execution. Storage persists layout and text overrides (`PromptBlockStore`) plus bundled fragments; memory declares its block and renders files; tools/skills/channels provide catalogs; extensions declare blocks; Chat sends the assembled system message whole. `blocks.py` is the pure assembly engine; `prompts.py` coordinates prompt-epoch rendering and Tool policy. Internal `_catalog.py` owns scope validation, editable block definitions, layouts and the shared override cascade used by both editing and assembly. `_types.py` holds contributor contracts and block identifiers; `_formatting.py` renders the Tool/Channel/Skill catalogs. `briefs.py` composes the one-shot learning-Run briefs (Interfaces), which are a Run's input, not System Prompt blocks. Existing public manager methods remain the RPC and Chat boundary.

## Terms

Domain-specific vocabulary for System Prompt assembly. These are all prompt-domain internals; no core prompt term lives in the glossary.

### Prompt Block
**Definition:** The unit the System Prompt is assembled from - an ordered, gated contribution that is either an editable **text** block (text may carry `{include:...}` and `{generated:...}` markers) or a non-editable **data** block (SOUL, Working Project context, config-agent body, auto-list, or dynamic render). Every contributor hands over a block *definition*; the prompt is the layout-ordered, three-gate-filtered, normalized concatenation of survivors.
**Not:** A prompt fragment - the old closed set of five fragment files is gone. A block is fragment-sized but reorderable, toggleable, gated, and contributable from any source.

### Block Layout
**Definition:** The persisted per-scope ordered list of `{id, enabled, source}` owning order and on/off state (`layout.json` per scope, `{"format_version": 1, "entries": [...]}`). A saved layout that fails to load reads as no layout and refuses edits; only `reset_layout` (`prompt.reset_layout`) replaces it. A block absent from the layout inserts at its definition's `default_rank` with `default_enabled`; an entry whose definition is gone is inert - skipped at build, pruned on next write.
**Not:** Definitions or text - the layout owns order + enabled only.

### Block Owner (three-gate filter)
**Definition:** A block renders only when all three gates hold: user-enabled (layout on) + owner-active + non-empty after expansion. The **owner** - `always` / `identity` / `memory` / `tool:<name>` / `channel` / `subagent_session` / `extension:<name>` - is gate 2: `identity` requires an Identity/Memory Workspace, `channel` drops entirely without an enabled Channel config for that Agent, `subagent_session` requires a prompt built for a Session linked to a Parent Agent, `memory` requires an Identity/Memory Workspace and renders whenever `memory_prompt_mode` is on regardless of Tool permission.
**Not:** The Source prefix - owner is the activation condition, source is provenance; both may read `tool:`/`extension:` but are distinct fields.

### Source prefix
**Definition:** The namespace before the first colon in a block id - `core:` / `tool:` / `extension:` / `user:` / `memory:` - mapping to its override folder `blocks/<namespace>/<slug>.md` (the colon never reaches the path).
**Not:** The Block Owner (see above).

### Producer
**Definition:** A function registered under a marker name rendering a `{generated:NAME}` placeholder at build time - the auto-lists `tool_list` / `skill_catalog` / `channel_list` and `memory_files`. Unknown markers (warned once per process per marker) and raising Producers render empty with a warning; empty results leave no residue, and one Producer cannot fail the System Prompt or Run.
**Not:** A dynamic block - a producer fills one marker inside an editable block; a dynamic block's entire body is a render function, whose text Chat pins per prompt epoch (Interfaces -> `render_dynamic_blocks`).

## Data Model

A **block** (`BlockDefinition`) carries: fully-qualified `id` `<source>:<slug>` (source is an open string, no-colon ids are contract errors); `owner` driving gate 2 (`always`, `identity`, `memory`, `channel`, `subagent_session`, `tool:<name>` = Tool among the request's Tool definitions when the caller passes them, else in exact effective policy + current provider definitions; a trailing `*` (`tool:mcp_*`) matches any such Tool with that name prefix, used by Tool-gated Extension blocks (`extensions/capabilities.md`); `extension:<name>` = in loaded set); `kind` `text` (override cascade + markers) or `data` (not user-editable, `default_text` inserted verbatim, `{...}` never interpreted); exactly one of `default_text`/`render`; `default_rank`; `default_enabled` (`False` ships an opt-in block staying off even under older layouts).

Core/data ids: `core:runtime`, `core:identity_runtime` (owner `identity`), `core:tools`, `core:system_reminders` (the static anchor telling the Model that `<system-reminder>` messages come from vBot and that Tool changes arrive that way; Models distrust those messages without it, `model-communication.md`), `core:subagent_role` (owner `subagent_session`; tells a Sub-Agent who delegated its work and where its answers go, `subagents.md`; every scope reads the bundled `subagent_role.md` like `core:system_reminders`), `core:tools_list` (**ships disabled** - providers already receive Tool descriptions natively, so the prompt copy is an opt-in booster for models attending poorly to schemas), `core:channels`, `core:skills`, `core:skill_maintenance` (owner `tool:skill_manage`, Identity Agents only), `core:soul`, `core:working_project`, `core:agent_body` (data, per-run), `memory:guidance`. Custom user blocks are `user:<slug>`, owner `always`.

The bundled default layout lives in `resources/prompts/layout.json` shipping soul -> memory -> runtime -> identity_runtime -> tools -> system_reminders -> project/subagent dynamic blocks -> tools_list (off) -> channels -> skills -> skill_maintenance -> agent_body -> working_project. A missing, explicitly empty, or broken persisted layout uses the bundled defaults; a broken file logs a warning and remains untouched. Empty means no custom order or enablement, not no blocks: disabling all blocks requires explicit `enabled: false` entries. Storage validates the entire persisted layout before use; a malformed entry discards that layout rather than partially applying it (`test_prompt_blocks.py`, `test_prompts_edit_facade.py`). The eight core text blocks read defaults from their fragment resources; an Agent scope reads its Agent copies, except `core:system_reminders`, which renders the bundled `system_reminders.md` in every scope because custom-prompt Agent copies predate it (block overrides and layout enablement still apply). `working_project.md` backs the non-editable dynamic block. There is no fragment-edit facade anymore - the only prompt-edit surface is the manager's block facade below.

## Assembly Pipeline

`assemble_system_prompt(definitions, layout, context, *, owner_activity, override_resolver, producers, replacements)` is deterministic - same inputs, same output (prompt cache depends on it):

1. **Dedupe** definitions by id, first-collected wins (core/data/memory first, then contributed, then custom - nothing shadows a core id); collisions log both sources.
2. **Resolve layout:** matching entries keep order/enabled; entries without definitions are inert (pruned later); absent definitions append at `default_rank` - the user's chosen order is never disturbed by new blocks.
3. **Resolve text:** skip disabled or inactive blocks before rendering; dynamic blocks call `render(context)` in isolation (exception drops only that block), except that a contributed block whose id is in `build_system_prompt(pinned_blocks=...)` shows that pinned text instead (`blocks.py::with_pinned_texts`); static text takes the override cascade, then `expand_block_template` tokenizes that author-controlled template once and substitutes `{generated:...}` and `{include:...}` (fail-soft) plus build-time replacements in the same pass. Producer output, included file content, and replacement values are inserted verbatim and never scanned again, so a Memory entry or Skill description containing `{include:...}` or `{model}` stays literal and cannot read files or fail the build (`test_blocks.py`, `test_prompts_assembly.py`); data stays verbatim. Explicit inspection via `block_details` also renders disabled active blocks to show their content, without including them in the combined prompt.
4. **Three gates:** user-enabled + owner-active (delegated to injected `OwnerActivity`, never hardcoded) + non-empty.
5. **Normalize:** trim, drop empties, join with exactly one blank line - no padding traces anywhere.

**Producers:** closures over manager-held registries; `memory_files` emits Chat's pinned epoch rendering verbatim instead of re-reading. `BlockRenderContext` carries `subagent_session` (the prompt is built for a Session linked to a Parent Agent) for role-dependent block prose, `tool_available` (which Tools the receiving Agent can call, by registry name: membership in `effective_tool_definitions` when given, else the Agent's live policy resolved once on first use) and deliberately **no conversation messages** - message-dependent content belongs to the `context` extension hook.

**Prompt files:** `render_prompt_file` (`core/prompts/blocks.py`) is the single reader for every file vBot puts into a Model's Context on its own: workspace `{include:...}` files (SOUL included) and Project auto-load files (Working Project block and `project` Tool result). A file enters whole up to `INLINE_FILE_MAX_BYTES` (128 KiB, the same cap as `@`-mention snapshots): these blocks ride on every request of the Session, so the cap only stops a runaway file (generated dump, wrong path) from flooding the Context; real instruction files stay far below it. A larger file keeps its `<file>` frame but holds `FILE_TOO_LARGE_NOTICE` (size and limit) instead of its content; `FILE_READ_HINT` (the file's absolute path and `read`) is appended only when the receiving Agent can call `read`. At most cap+1 bytes are read, the file is not stamped read, and missing (includes only), unreadable and oversized files each log once per condition through `LoggedConditions` without content, with an INFO line when the file loads whole again; there is no aggregate budget across files (`test_blocks.py`, `test_project_files_render_readable_files_after_memory_and_report_them`). Memory is not a file here: its scopes are cut to their Memory budgets by the Memory domain (`memory.md` -> Prompt block).

**Runtime variables:** `{server_hostname}`, `{vbot_version}`, `{operating_system}`, `{model}`, `{agent_id}`, `{agent_name}` (the display name, the id when it is empty), `{identity_workspace}`, `{vbot_root}`, `{data_root}`, `{thinking_effort}`, `{current_local_date}`, `{timezone}` substitute exactly, one pass, non-recursively; unrelated `{...}` stays literal; vBot-authored path values use the forward-slash Model presentation; retired names have no aliases and remain literal. `runtime.md` (owner `always`) carries OS/model/thinking effort plus the current date in the configured IANA timezone and the timezone name - unset effort renders "provider default", never blank. The runtime block deliberately exposes no clock time: its date changes at most once per configured-zone day, preserving the stable prompt prefix and provider prompt-cache reuse. `identity_runtime.md` (owner `identity`) carries hostname/version/workspace/roots, so Config Agents receive none of those.

**Override cascade:** agent override <- default-scope override <- owner default; composed by the manager from two store reads, never by the store. Dynamic and data blocks have no override path. Request-local data namespaces therefore never reach the persistent override store (`blocks.py`, `test_prompts_layouts_overrides.py`).

**Data blocks:** `core:soul` renders workspace SOUL.md through the single include-expansion path plus a framing prefix (kept out of shared wrapping so it never leaks onto other includes; missing/empty workspace returns "" before framing so the block gates out clean), pinned per prompt epoch. `core:working_project` renders the file-backed template from `ProjectPromptContext` (only `{project_name}/{project_id}/{project_workspace}/{project_files}`; retired `$project_*` unresolved); metadata renders once in Markdown while `<project_context>` wraps auto-load files verbatim; auto-load paths are taken verbatim with no location restriction, reads lazy and fail-soft (a missing file is skipped silently), each file through `render_prompt_file` above. Identity Sessions working in a Project and Config Agents receive Chat's pinned prompt-epoch snapshot instead of re-reading; a Session working in its Agent's Workspace gates the block out. `core:agent_body` carries a Config Agent's body verbatim (empty for Identity Agents -> gates out); Chat pins the body of every Workspace-less Agent (Project Config Agent, temporary participant) per prompt epoch as `pinned_agent_body` (`pinned_context.py::pinned_agent_body`), so an edited Agent file reaches the System Prompt only at the next Compaction, with no announcement.

## Interfaces

`build_system_prompt_async`, `provider_tool_definitions_async`, and `render_working_project_context_async` are Event-Loop-safe entry points running reads/expansion/schema generation through the dedicated four-worker pool with backpressure.

- `render_soul(agent)`, `render_memory_files(agent)` and `render_working_project_context(agent, project_context)` render Chat's epoch snapshots before a request exists, so a notice in them names a Tool by the Agent's live Tool policy; `render_project_files(project_context, *, tool_available)` takes the caller's answer (the `project` Tool passes `ToolContext.can_call`).
- `SystemPromptManager.build_system_prompt(...)` collects the full definition list for Agent/Run and routes through assembly. Key inputs: Chat's prompt-epoch snapshots (`working_project_context`, `soul_context`, `memory_files_context`) emit verbatim and prevent the corresponding file reads - Working Project pinning covers only its own block; `subagent_session` activates the `subagent_session` block owner (the `core:subagent_role` block) and is otherwise build context only; `read_paths` is a pure side channel reporting files actually read (only when rendering/refreshing a snapshot, never on reuse); `pinned_blocks` (block id -> text) replaces the render of those contributed dynamic blocks, which still pass gates 1-3. Without explicit scope, the Agent scope applies only under `custom_system_prompt_enabled`.
- `render_dynamic_blocks(agent, *, block_ids=None, skip=(), <build_system_prompt render inputs>)` renders the contributed (Tool and Extension) `render` blocks that pass gates 1 and 2, keyed by id, for Chat's per-epoch pin and change check (`chat/request-building.md` -> Dynamic prompt blocks per prompt epoch). An empty render is kept (it pins as empty); a failing render is left out. A renderer returns `str` or `RenderedBlock(text, catalog)`: a `BlockCatalog(title, entries, frame)` names the block's keyed entries (`(key, line)` pairs) and the rest of its content (`frame`), so a change can be told per entry. Built-in catalogs: `tool:project` (one entry per Project id, frame = header) and `tool:subagent` (one entry per target id, frame = execution guidance).
- For an Identity Session working in a Project, SOUL/memory still render from Workspace while Project context comes from the admitted Working Project; live Runs, compaction rebuilds, and preview share one resolver failing closed.
- The `core:skills` catalog is origin-grouped and path-free (`SkillPromptMetadata`: name/description/origin); `_formatting.py` wraps `core.skills.skills.format_skill_catalog_entries` (which owns the English origin labels) in `<available_skills>`. `render_skill_catalog(...)` produces the `PinnedSkillCatalog` Chat pins per epoch.
- `core/prompts/pinned_context.py` owns the Chat-side pinned-snapshot assembly persisted as Session prompt pins between Compactions, plus `stamp_prompt_files_read` for read-before-write state. Initial SOUL/Memory/Project renders stamp their reported files; snapshot reuse never updates stamps. Memory snapshots carry their rendering mode and refresh when that mode changes, while unchanged-mode file edits stay pinned. The Working Project Context and Skill catalog pins carry the `working_project_id` they were rendered for (the catalog: its Skill-scope Project), because Chat resolves the Working Project per Run admission and a Session's can still change: a move or fork into another scope, or a Project restored under a new id (`sessions.md` -> Terms -> Working Project), re-renders both at the next Run instead of showing the old Project until Compaction; a Run in the Workspace ignores a stale Working Project pin. A pin missing a qualifier re-renders (`tests/core/chat/test_chat_prompt.py`). `prompt_epoch_pins` returns the same qualified shapes for the Compaction commit's `PromptEpoch`. Called directly by ChatLoop/Compaction via a narrow dependency slice, no chat-owned copy. The module also names the `pinned_tool_definitions` and `pinned_dynamic_blocks` slots, but Chat resolves and commits those pins itself (`chat/request-building.md` -> Tool catalog per prompt epoch, Dynamic prompt blocks per prompt epoch).
- `provider_tool_definitions(...)` filters schemas by the single Tools-domain `resolve_tool_access` result (`ready_only=False` also returns allowed Tools that are not ready, which Chat uses to tell a removed Tool from a not-ready one), passing stable Definition Profile context so profile-based visibility cannot drift between native schemas, `core:tools_list`, and owner gates. Takes no Skill registry/catalog params - Tool presence is never derived from the pinned catalog.
- `update_block_definitions(...)` / `update_skill_registry(...)` refresh contributed blocks and gate-2 membership on every extension/skill reload without restart.
- `core/prompts/briefs.py` owns the learning-Run briefs: `reflection_brief(fragments, scope, *, focus=None)` for the Reflection scopes `memory`/`skill`/`combined`, `learn_brief(fragments, request)` for `/learn` and `librarian_brief(fragments, candidates, *, agent_id, agent_name)` for a Librarian consolidation Run, one public function per brief kind, used by Reflection and the Librarian (`automation.md`), `/learn` (`chat/commands.md`) and the provider probe. The Librarian brief is the one fragment `librarian.md`: `{generated:agent}` takes the curated Agent (`<name> (id <id>)`, or the id when the name equals it; an override without the marker gets it named in a first paragraph), `{max_chars}` `LIBRARIAN_SKILL_MD_MAX_CHARS`, and `{generated:candidates}` the rendered `LibrarianCandidate` list (appended as a last paragraph when an override lacks the marker); it states no call limit, because the Run has Chat's normal limit; its wording rows are in `automation/librarian.md` -> Agent-facing text. A brief is a fixed recipe of shared fragments: fragments of one group continue a paragraph (joined by one space), groups are paragraphs (joined by one blank line), so guidance shared between briefs lives in exactly one fragment. `fragments` is any `read_prompt_fragment` reader (Storage in production), so each fragment resolves and overrides on its own; every name is in `BRIEF_FRAGMENT_NAMES`, which Storage must allowlist (`storage.md`). Assembly reads files: callers run it on a worker, never on the Event Loop. Fragments name Tools literally; `test_reflection.py` checks that each production review brief names exactly its scope's Tools. Coverage: `tests/core/prompts/test_briefs.py`.

**Block-edit facade** (the `prompt.*` RPC surface): `list_scopes()` reports each custom-prompt Agent scope with `has_customizations` (saved layout or any override) so the editor can confirm before disabling custom prompts. `list_blocks(scope)` gives static metadata in layout order including effective text, `is_modified`, and inheritance layer for editable blocks - owner-active status deliberately excluded (preview's job). `update_block` accepts overrides on editable blocks only (data/dynamic reject); `reset_block` drops to inherited/default (a `user:` block has no default - delete instead). `set_layout` tolerates contributor-gone ids (store prunes them on write); `reset_layout` restores the bundled default leaving text overrides untouched. `create_block`/`remove_block` manage `user:<slug>` blocks only - core/tool/extension blocks toggle off, never delete. `create_block` rejects a slug that matches an existing `user:` block case-insensitively on every platform (`PromptError`), because the override file is named after the slug and a case-insensitive filesystem would give both spellings one file; for the same reason it rejects a slug Windows reserves for a device (`con`, `nul`, ...); a layout that already holds case variants keeps every entry (never pruned or rewritten), see `storage.md` for how their files behave. `prompt.preview` returns rendered `text`, token counts including the Tool-definition footprint (corrected by the Agent's Model input estimate factor, `chat/usage.md` -> One Context rule), and `estimated`. Optional boolean `include_tools` adds the same effective Provider definitions with individual token estimates for inspection; it does not mutate definitions or Prompt context. Deferred Tools remain excluded, and omission keeps the compact response. Every `prompt.*` handler does its catalog, scope, Agent, and Skill work on the `prompt-rpc` worker pool, never on the Event Loop; that includes `prompt.preview`'s scope validation, which reads the Agent for an Agent scope. Coverage: `tests/server/rpc/test_operations_methods.py`.

## Conventions

A temporary Agent's optional `prompt_blocks` selection overrides block enablement
exhaustively while retaining layout order: `None` inherits the ordinary layout,
an explicit list includes only selected active non-empty blocks, and newly
registered blocks remain off. `build_system_prompt(block_details=...)` optionally
collects rendered content, enabled/active state and actual inclusion for previews.
Normal rendering does not read disabled block files or invoke their renderers.
Source/tests: `prompts.py`, `blocks.py`, `test_prompts_layouts_overrides.py`.

- Prompt code consumes Protocols for Agent/Tool/Skill/Channel/Storage shapes; contributions arrive as plain `BlockDefinition` objects handed in via Runtime. The manager uses the Memory domain's default renderer when no custom memory provider is injected.
- Bundled default texts are **English Markdown in resources** - a deliberate signed-off i18n exception: the System Prompt is the model-facing English contract, not localized UI string.
- `{include:filename}` accepts safe flat filenames under the agent workspace and renders through `render_prompt_file` (Assembly Pipeline -> Prompt files): wrapped as `<file name="...">`, an oversized file as its notice, missing/unreadable files dropped with a warning (never aborting a run) - logged once per path and state rather than on every build, with an INFO line once the file loads whole again; unsafe paths in the template raise `PromptError`. Includes do not nest: markers and runtime variables inside an included file stay literal. An **empty workspace** drops every include without reading - it must never resolve against `Path("")` (= CWD), which would read server-side files.
- The `core:channels` block gates out entirely without enabled Channels - no `- None` fallback. Its producer lists persisted enabled Channels independent of adapter liveness, keeping the prompt prefix stable through transient failures; a single allowed chat id shows "default target available".
- `resources/prompts/channels.md` carries the static group-authorization contract (member attribution format, admin/member authorization split, authority-by-message rule); per-group identities and live roles never enter blocks or producers, so access changes never break the cache.
- Provider Tool permissions come from resolved policy plus Chat-derived grants - admitted Runs cannot inject any; the `core:tools`/`core:tools_list` blocks control only prompt-visible text, not permission. Chat passes the prompt epoch's pinned Tool definitions as `effective_tool_definitions`: gate 2 for `tool:<name>` is then plain membership (no readiness or registry check) and `core:tools_list` renders exactly those names and route-projected descriptions, so a pinned Tool that stops being ready or registered keeps its block and line, and a Tool announced mid-epoch gets neither until the next epoch. Without them (previews) both follow the live policy, grants and readiness. Coverage: `test_system_prompt_describes_the_pinned_tools_for_the_whole_epoch` in `tests/core/chat/test_chat_prompt.py`. The dynamic `tool:project` and `tool:subagent` blocks render exactly when their Tool is effectively available and agree with provider visibility and addressing routing; preview supplies the same scope. In Chat their texts are pinned per prompt epoch like every contributed dynamic block; previews render live.
- The dynamic `tool:bash` block renders only with permanent `tools.bash.allowed_env` grants and lists credential names plus the `env_keys` contract; Skill-derived grants never enter the System Prompt (their payload carries its own notice at load time).
- `memory_prompt_mode` alone controls the memory block and independently gates the `memory` Tool: `agent`/`agent_user` keep prompt Memory visible even when the Tool is denied (intentional read-only Memory); `off` removes both; `tool_access.mode: none` removes the Tool but not prompt Memory.

## Constraints & Gotchas

- RPC error split: block edit/layout/preview validation maps `PromptError` -> `invalid_request`; assembly/storage/runtime failures during preview use the normal domain-error path.
- User overrides and per-scope layouts persist until explicitly reset; agent scopes are owned only while `custom_system_prompt_enabled` is true - the store ignores their files otherwise.
- Preview uses the live manager (current registries, extensions, layout, overrides), renders the Working Project frame prospectively without persisting a snapshot, uses no Session pins and therefore no Session-scoped Tools: an optional `session_id` applies only that Session's Agent overrides and Working Project, and `working_project_id` (without `session_id`) names the Project a new Session would work in (omitted: the Agent's default Project; `null`: the Workspace); no scope shows the Agent's baseline, `scope: {type: "default"}` previews the default scope.
- Chat builds the prompt per request and omits the provider system message entirely when the result is empty/whitespace-only.
- Bound temporary Sessions supply request-local data block definitions through `build_system_prompt`; the normal assembly engine owns ordering and joining. Chat gates and revalidates their exact Extension registration and complete Session Tool grant set. These definitions never enter editable/global block catalogs or unbound previews (`tests/core/chat/test_chat_loop_extension_tools.py`).
- Do not move block behavior into Agent or WebUI code: Agents own only the flag and Workspace path, WebUI owns editing UX, this domain owns assembly semantics and the block contract.
- Adding a keyword parameter to `build_system_prompt` breaks every duplicated prompt-manager test double that spells out the full signature - grep `def build_system_prompt` under `tests/` and `scripts/` (three today: `tests/core/chat/chat_loop_support.py`, `tests/server/rpc_test_support_runtime.py`, `scripts/probe_background_completion.py`). The failure appears at runtime as `TypeError: ... unexpected keyword argument` inside server/integration tests, not at import time; update every double in the same change. Chat also calls `render_dynamic_blocks`, so each double implements it (returning `{}` contributes no dynamic block).

## Agent-facing text

| Text | Reason |
|---|---|
| `[Not included: this file has {size} bytes, more than the {limit}-byte limit for automatically loaded files.` (`FILE_TOO_LARGE_NOTICE`) | Marks the cut: without it the Agent reads the empty frame as an empty file, or never learns that the instructions (SOUL, an include, a Project file) exist. |
| `The following is your SOUL: your role, how you work, your voice and your boundaries.` (`SOUL_FRAMING`, `core/prompts/_types.py`) | Labels the block as the Agent's own role and conduct, not reference data, and names the four parts a SOUL holds. Where the file lives, what belongs in it and when to change it live only in the `vbot-docs` Skill (`references/soul.md`), so an Agent that wants to change its SOUL loads that guide (user decision 2026-10-07). Earlier framings said "who you are", which invited any identity request such as a new name into SOUL.md, and carried change rules that did not stop it. Eval 2026-10-07 with this framing: GLM 5.3 Flash still edits SOUL.md directly through its Workspace path without loading the Skill (rename 2 of 3, requested change 2 of 2, unrequested change after feedback 1 of 2); DeepSeek V4.1 Flash loads the Skill and renames correctly in 4 of 6 runs, otherwise only offers it. |
| `## vBot Environment` (`identity_runtime.md` heading; formerly `Identity Environment` with `You are an Identity Agent in this vBot server environment.`) | Names the place the Agent works in with a word it can act on: the bundled `vbot-docs` Skill is the guide to vBot. The sentence went with the rename; `Identity Agent` is vBot vocabulary a fresh Agent cannot use. A sentence `You work inside vBot, which holds your settings, your Skills and your Sessions.` showed no effect on renames in the eval of 2026-10-07 and was not kept (user decision 2026-10-07). |
| ``- Your display name: `{agent_name}`; your Agent id: `{agent_id}` `` (`identity_runtime.md`) | Without it no prompt text tells the Agent its own name or id: it cannot answer to its name, and commands about itself (`vbot agent update <agent-id>`) need a lookup. The identity block is not pinned per prompt epoch, so a rename reaches later Runs without a Compaction. |
| ``When your work needs its content, read `{path}` with the `read` Tool, which returns large files in pages.`` (`FILE_READ_HINT`) | Gives the way to the rest. Only when the receiving Agent can call `read`: otherwise it points at a Tool the Agent cannot call. The absolute path because the Agent's relative paths can resolve against another directory than the file's (the Working Project's files, `project` Tool files); naming paging keeps Agents from dumping the whole file through the shell. |
| `... This is a background review: the user does not see your replies, and the user can see and undo every change you make. From now on only ... work; do not continue the task under review.` (`review-intro-*.md`) | The fork carries the whole task: without this the review answers the user or resumes the task. Reversibility counters the timidity of "no change is fine" texts. |
| `Act when the conversation shows one of these signals:` + per-scope lists (`review-signals-*.md`) | Hermes' signal list: concrete, observable triggers make weak Models act on corrections and not on long routine tasks. |
| `Without such a signal, reply "Nothing to save." and stop; ...
