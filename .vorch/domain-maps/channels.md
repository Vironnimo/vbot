# Channels

Messaging-platform accessors for vBot. Owns channel configuration, adapter lifecycle, outbound delivery, and routing platform inbound messages into normal agent Sessions.

## Overview

`core/channels/` bridges external messaging platforms into the existing agentic loop. A Channel is an accessor-side transport abstraction, not a model provider: it receives inbound platform messages, resolves them into an Agent and Session, triggers normal Runs, and routes assistant replies back through the platform adapter. `ChannelService` owns the channel configs and Channel state (Data Model), starts and stops adapter tasks for enabled channels, and exposes outbound message and file support for the `channel_send` tool. Channels reuse normal Sessions, `TriggerService`, `CommandDispatcher`, attachment storage, and prompt/tool registration; they do not own a separate conversation store.

Platform-neutral conversation behavior lives in `core/channels/engine.py` (`ChannelConversationEngine`), shared by all adapters. `ChannelService` owns one engine per started Channel (`_engines`): it outlives the Channel's supervised adapter restarts and ends only with the Channel (`stop_channel`: disable, delete, a config change, `restart_channel`, shutdown), after its adapter stopped. Adapters receive the engine in their constructor, delegate to it, and attach their `ConversationTransport` in `start()`; the adapter is reduced to platform I/O. `ChatRunManager` remains the single authority for active and waiting-work capacity. The engine never imports a platform library: raw platform messages flow through it as opaque values and are converted to canonical content blocks by the adapter-supplied `ConversationTransport`.

Modules: `config.py` (configuration values, schema diagnostics), `storage.py` (`channel.json`), `state.py` (`ChannelStateStore` for `channels.db`; DDL and kernel declaration in `_state_schema.py`), `channels.py` (adapter lifecycle, public Service API), `_delivery.py` (outbound normalization, durable Run-button binding, completion relay); `engine.py` (admission, FIFO workers, Command projection, Run relay) with `_conversation_routing.py` (Session anchors, navigation, metadata through the injected `ConversationPointerStore`), `_conversation_access.py` (response eligibility, group sender authority), `_conversation_content.py` (neutral notes and results) and `_conversation_work.py` (transport and admitted work payloads). Helpers receive the specific dependencies they need, never the engine.

## Terms

### Conversation anchor and pointer ("Wegweiser")
A platform conversation's derived Session id is its stable anchor; its pointer in `channel_conversations` names the Session it currently routes to, and without a pointer the anchor itself is that Session. The pointer is Channel state, never Session metadata (`channels/conversation-routing.md`).

## Data Model

- `ChannelConfig` lives at `<data_dir>/channels/<channel-id>/channel.json`, a Generation 1 JSON document (`format_version` 1, unknown fields kept on save, never overwritten after a failed load; contract in `settings.md`). The retired `owner_user_ids` is an ordinary unknown field; group admins live in access settings. Reads never migrate configuration or permissions. Raw-file validation, config construction and saving share the same schema checks and accepted-value normalization; `core.channels` exports the validators RPC and CLI consume.
- `allowed_chat_ids` (strings: platform conversation ids, or literal `self` for WhatsApp) gates inbound only: empty or missing means deny-all inbound, not "allow everyone". Outbound is deliberately unrestricted within the adapter's supported targets: `channel_send` with an explicit target may message any reachable chat; WhatsApp supports only `self` in either direction. Do not add outbound allowlist filtering to other adapters.
- `token_env_var` is the adapter-facing credential indirection (`channels/config-lifecycle.md`). Slack uses a separate `app_token_env_var`; Mattermost requires `server_url`; WhatsApp uses linked-device pairing and accepts no token fields. Tokens cross RPC only as write-only inputs, stored via `StorageManager.set_data_dir_credential`, never part of `ChannelConfig` or `channel.json`, returned, or logged.
- Channel state lives in the canonical kernel database `<data_dir>/channels.db` (`channel_database_spec`; `database.md`). All tables are STRICT and WITHOUT ROWID; conversation kinds are validated in code, not by CHECK constraints; timestamps are canonical UTC text (`core/utils/timestamps.py`), so text order is time order. Tables: the registry `channels(channel_id, platform, self_user_id)`, group access and the observation inbox (`channels/groups.md`), conversation pointers (`channels/conversation-routing.md`), Run-button bindings (`channels/interactive-messages.md`), owed replies (`channels/reply-delivery.md`), socket receipts (`channels/network-platforms.md`) and the Telegram polling watermark (`channels/telegram.md`).
- Routing/access/reply tables reference the registry with `ON DELETE CASCADE`; the observation inbox is independent so accepted context survives deleting the transport. State writes for an unregistered Channel raise `ChannelNotFoundError`, so a late save of a stopping adapter cannot recreate state after a delete.
- A committed platform change resets the Channel's platform-id state in one transaction (`ChannelStateStore.bind_platform`); a rotated token or another bot keeps it (`channels/config-lifecycle.md`). A new state table must decide whether its rows name platform ids and belong in the `bind_platform` reset (`tests/core/channels/test_channels_platform_change.py`).
- Channel Session metadata (ChatSessionManager-owned Session store) has the Channel-owned keys `source_channel_id`, `platform`, `platform_conv_id`, and `last_reply_target {channel_id, platform_target, thread_id?}` (per-Session delivery state for completion relays and the fallback for `channel_send` outside an admitted Channel reply). WebUI Session browsing and retroactive linking (`session.link_channel`, which writes the same keys and appends no reply-surface note) depend on them: keep them stable when changing routing. Conversation pointers, conversation kinds and group participants are Channel state in `channels.db`, never Session metadata; the pre-Generation-1 keys `active_session_id`, `conversation_kind` and `participants` are retired.
- `FileData` (`filename`, `media_type`, raw bytes) is the generic outbound file payload handed from tools/service code to adapters.

## Interfaces

- No Session or config persistence I/O runs on the Event Loop. Engine ingress takes one hop per database: conversation pointers and Run-button claims/restores on the `channels.db` pool (the `ConversationPointerStore`/`RunButtonBindingRegistry` seams of `ChannelStateStore`), route metadata, Session existence checks and notes on the Session database's pool (`ChatSessionManager.run_async`). Outbound work splits the same way. A closed database on either side fails with `DatabaseUnavailableError` before anything is sent, bound or created. Session write locks still protect note ordering against open Tool cycles.
- `ChannelService` is the domain facade: config reads and CRUD, lifecycle, health checks, `send(...)`, and async `ensure_outbound_session(...)`, which reads the conversation pointer on the `channels.db` pool and creates a missing Session with its metadata on the Session pool. Async config reads and writes touch `channel.json` only on the `channels.db` pool; sync reads (prompt/Tool checks, enabled-state checks, adapter construction) use `ChannelStorage`'s immutable published snapshot (`channels/config-lifecycle.md`). Runtime injects `credential_resolver`, so adapters never read `os.environ` themselves.
- The engine's ingress entry points are `handle_inbound_text`, `handle_inbound_media`, `trigger_internal_reply`, `trigger_interaction_reply` and `ensure_channel_session` (`channels/conversation-routing.md`). `should_respond(conversation, gating_texts)` is the public gating decision: direct always responds; groups respond in `"all"` mode, or in `"mention"` mode when mentioned/replying-to-bot or a wake-word regex matches (`channels/groups.md`).
- `ConversationTransport` is the typing.Protocol keeping the engine platform-free: display name, text send (reply/thread targeting, buttons where supported), activity indicator, media blocks, quoted messages, captions. Adapters classify the conversation (`direct`/`group`), supply display name, message id, addressing facts (`mentioned_bot`, `is_reply_to_bot`) and thread ids, and convert payloads into canonical content blocks; the engine owns every gating and routing *decision*.
- Every relayed Channel Run supplies `RunKind.CHANNEL` and a Chat-owned `ReplySurface` (platform, display name, Channel id, direct/group); ingress adds the reply plan's target and thread as runtime-only fields, so `channel_send` follows the Run's own destination (`channels/reply-delivery.md`).
- Session-id derivation is a stable contract (WebUI browsing, `session.link_channel`): `group` -> `ch-<channel-id>-<chat-id>`; `direct` follows `dm_scope` - `per_conversation` (default) -> `ch-<channel-id>-<chat-id>`, `main` -> `ch-<channel-id>-main`, `per_peer` -> `ch-<channel-id>-u<user-id>`, `per_account_channel_peer` -> `ch-<channel-id>-<chat-id>-u<user-id>`. The derived id does not show where the channel id ends, and Sessions are per Agent (routing and the anchor-collision rule: `channels/conversation-routing.md`).
- A failed adapter send raises `ChannelError` with `possibly_delivered` set unless nothing of the message can be visible, and marks it `retryable` only when the platform cannot have posted it; `channel_send` and the Run-button binding read it (`channels/reply-delivery.md`).
- `ChannelConfig.agent_id` is a live reference that the Identity Agent rename retargets through `retarget_agent_async` (`channels/config-lifecycle.md`).

## Interactive messages

Channels carry the neutral interaction contract of `core/extensions/interactions.py`; Extension-handled taps bypass the engine entirely (`extensions/capabilities.md`). Two prefixes are runtime-reserved: `run:<payload>` wakes the Agent through a durable one-shot origin binding, and `chk` checklist items toggle in the adapter without a Run (`channels/interactive-messages.md`).

## Conventions

- Channels are accessors. Do not put provider behavior, model fallback, or alternate chat-loop semantics in this domain.
- Where new channel code goes: platform-neutral conversation behavior (queueing, command handling, run trigger/relay, session routing/metadata) belongs in `engine.py`; platform I/O (library lifecycle, inbound parsing, media download, outbound send, activity indicator) belongs in the adapter module. New cross-platform features land in the engine once, not per adapter.
- Outbound text splitting is shared: `split_message` in `_message_chunks.py` cuts at paragraph, then line, then whitespace boundaries (hard cuts only inside a single overlong token, between grapheme clusters where possible). For Markdown-rendering platforms it closes a code fence open at a cut and reopens it with the same opener line in the next chunk, counting added markers toward the limit. Adapters supply only their limit and length measure (values in the platform maps); never slice outbound text by fixed offsets.
- Inbound attachment classification is shared: `content_blocks_for_attachment(record)` in `adapter.py` is the single rule mapping sniffed media type to content blocks (image/audio/video -> `MediaBlock`, everything else including text -> `FileBlock`). Adapters extend their block lists with the result, so platforms cannot drift; classification is by sniffed type, never by delivery channel (a Telegram MP3 sent as document is media).
- The engine serializes all work of one conversation through one FIFO; every queued candidate first reserves waiting-work capacity in `ChatRunManager` (at most 8 per chat, within the process-wide limit, `runs.md`), while immediate Commands consume none (`channels/conversation-routing.md`). Chat owns every Command workflow.
- Session history remains the single source of truth: Channels add routing metadata and contextual notes but keep no parallel transcript or separate mutable surface store. Only Assistant text from a completed Run or preserved partial text from an interrupted Run reaches the platform; Tool Results, Reasoning, and intermediate events stay in canonical Session history/SSE.
- Final assistant text for inbound platform turns is automatic; every file delivery goes through `channel_send` (`tools/channel_send.md`). Its registration and the System Prompt's Channel list follow persisted enabled configs, never adapter liveness, so transient downtime cannot churn Provider Tool definitions or the prompt cache; a send through an unavailable Channel is an ordinary Tool failure.
- Channel logs (service, engine, adapters, and the `channel.identity.set` / `channel.admin.*` RPC lines) name only the Channel id, conversation kinds, and counts: external chat/user/thread/message ids, group scopes, platform display names, and derived Session ids stay out at every level; routine routing stays silent. Other owners log Session ids as usual; the log pipeline pseudonymizes a derived one (`logging.md`).

## Constraints & Gotchas

- Channel ids are bare slugs (`^[A-Za-z0-9][A-Za-z0-9_-]*$`), enforced at the `_normalize_channel_id` choke point every storage/service call funnels through - the id is a path segment and `delete_channel` rmtree's its directory, so a separator or `..` must never reach the filesystem layer. Tighten id handling here, never just at config validation. Reserved device names: `.vorch/PROJECT.md` -> Object IDs.
- A bound `agent_id` must match the full agent-id slug pattern - it flows into session paths on every inbound message; the file-load slug check is the defense-in-depth backstop for hand-edited configs.

## Agent-facing text

This domain owns the Run note of a Run-button tap or checklist submission (`_format_interaction_note` in `_conversation_content.py`). Before you change, add or delete a sentence of them, read `channels/agent-facing-text.md`: it records why each sentence exists. Update its row for every sentence you change and add one for every sentence you add.
