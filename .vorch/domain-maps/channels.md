# Channels

Messaging-platform accessors for vBot. Owns channel configuration, adapter lifecycle, outbound delivery, and routing platform inbound messages into normal agent Sessions.

## Overview

`core/channels/` bridges external messaging platforms into the existing agentic loop. A Channel is an accessor-side transport abstraction, not a model provider: it receives inbound platform messages, resolves them into an Agent and Session, triggers normal Runs, and routes assistant replies back through the platform adapter. `ChannelService` owns persisted channel configs under `<data_dir>/channels/`, starts and stops adapter tasks for enabled channels, and exposes outbound message and file support for the `channel_send` tool. Channels reuse normal Sessions, `TriggerService`, `CommandDispatcher`, attachment storage, and prompt/tool registration; they do not own a separate conversation store.

Platform-neutral conversation behavior lives in `core/channels/engine.py` (`ChannelConversationEngine`), shared by all adapters. Each `ChannelAdapter` composes one engine in its `__init__` and delegates to it; the adapter is reduced to platform I/O. The engine owns per-conversation ingress ordering and worker serialization, slash-command dispatch handling, run trigger/relay, and session routing/metadata/derivation; `ChatRunManager` remains the single authority for active and waiting-work capacity. It never imports a platform library: raw platform messages flow through it as opaque values and are converted to canonical content blocks by the adapter-supplied `ConversationTransport`.

## Data Model

- `ChannelConfig`: `id`, `platform`, `agent_id`, `dm_scope`, `allowed_chat_ids`, `token_env_var`, `enabled`, `response_mode`, `mention_patterns`, `observe_unaddressed`. Supported platforms are `telegram` and `discord`. The parser still accepts legacy `owner_user_ids` only so `ChannelStorage` can migrate it; serialized config and public create/update surfaces omit it.
- `token_env_var` remains the adapter-facing credential indirection. A caller that supplies a managed token to `channel.create` gets a deterministic collision-free key from `managed_channel_token_env_var(channel_id)` (`VBOT_CHANNEL_TOKEN__` plus the exact Channel id's uppercase UTF-8 hex); externally managed deployments can instead supply their own key. The raw token is never part of `ChannelConfig` or `channel.json`.
- `allowed_chat_ids` is normalized to strings in memory and serialized output (integer RPC/config input is accepted and normalized). Telegram uses chat ids; Discord uses channel ids. Empty means deny-all inbound.
- Group response gating fields: `response_mode` is `"mention"` (default — groups only respond when addressed) or `"all"` (respond to every allowed group message; pre-gating behavior). `mention_patterns` is a list of wake-word regexes (validated to compile; matched case-insensitively with `re.search` against message text and media captions). `observe_unaddressed` is a boolean (default `false`) that persists otherwise-unaddressed group messages as internal context notes in `"mention"` mode. DMs always respond regardless of `response_mode`; `"all"` mode has no unaddressed messages to observe.
- Channel config files live at `<data_dir>/channels/<channel-id>/channel.json`.
- Group access state lives separately at `<data_dir>/channels/<channel-id>/access.json`: one optional Channel-own `self_user_id`, plus groups keyed by stable adapter-supplied access scope, each with additional admin user ids and durable seen participants (`display_name`, `last_seen_at`). `admin` and `member` are the only roles. The own identity is effectively admin in every group and cannot be demoted; additional admins are scoped per group. Access mutations are atomic and never rewrite `channel.json`, restart an adapter, rebuild the System Prompt, or alter provider Tool definitions. A legacy `owner_user_ids` list migrates idempotently into every configured allowed group and is then removed from `channel.json`.
- Origin bindings for `channel_send`-authored `run:*` buttons live at `<data_dir>/channels/<channel-id>/run-button-bindings.json`. `ChannelStorage` writes the versioned file atomically and retains consumed entries so a duplicate or post-restart tap cannot start a second Run; this is routing/idempotency state, not conversation state.
- `core.channels` exports `validate_channel_data`, `validate_channel_file`, and `load_validated_channel_json`; config reads pass through this Channels-owned schema before `ChannelConfig.from_dict()`. Schema errors raise `ChannelConfigError` with file/path diagnostics; runtime-only dependency failures such as missing credentials do not mutate the persisted config. The same module owns and exports the platform, DM-scope, and response-mode sets consumed by Channel RPC/CLI validation.
- Channel session metadata lives in `<data_dir>/agents/<agent-id>/sessions/<session-id>.meta.json` beside the JSONL transcript and is owned by `ChatSessionManager`. Channel-owned keys are `source_channel_id`, `platform`, `platform_conv_id`, `last_reply_target: { channel_id, platform_target, thread_id? }` (the optional `thread_id` is present only while the conversation lives in a platform thread/topic; a later non-topic message rewrites the dict without it), and — for group conversations only — `participants: { <user_id>: { display_name, last_seen_at } }` (engine-maintained for messages that trigger a Run or are passively observed; unaddressed messages with observation disabled and unauthorized group commands touch nothing; `last_seen_at` is UTC ISO 8601; existing entries are preserved and merged; outbound sends refresh the base keys but never write `participants`, since a proactive target has no real sender). A conversation **anchor** session additionally carries `active_session_id`, the `/new` pointer to the chat's currently active session (see "Wegweiser" routing under Interfaces); it lives only on the anchor sidecar, never on the sessions it points at.
- Adapter fact dataclasses in `core/channels/adapter.py`: `ConversationFacts` for inbound platform origin, including `access_scope_id` and the immutable ingress `sender_role`; `RouteFacts` for resolved `agent_id`/`session_id`; `ReplyPlanFacts` for outbound targets; `MessageFacts` for model-visible inbound content; `QuotedMessageFacts` for an on-demand resolved replied-to attachment plus its original sender; and `RunButtonBinding`/`RunButtonClaim` for the persisted origin and one-shot claim of a bound Run button. `ChannelAccessRegistry` is the adapter/engine seam for atomically recording a participant plus its role and resolving the current live role.
- Denied-chat visibility in `core/channels/adapter.py`: `DeniedChatLog` is a bounded in-memory record (most recent `DENIED_CHAT_LOG_LIMIT` = 20 chats, dict insertion order = recency) of inbound chats rejected by the allowlist; entries are `DeniedChatFacts` (`chat_id`, `kind`, `display_name`, `last_seen_at`, `count`). Purely observational — recording never changes gating — and it lives on the adapter instance, so allowing a chat (which restarts the adapter) or any channel restart clears it. This is the chat-id discovery surface: message the bot once, read the id from channel status, allow it.
- `ConversationFacts.kind` is `"direct"` (default) or `"group"`: the adapter classifies the conversation, the engine derives the session id from it. A `group` conversation routes to a shared session keyed by the adapter-supplied `chat_id` and ignores `dm_scope`. Discord supplies a thread id as `chat_id`, so each thread owns its own Session; Telegram forum topics keep the parent chat id for session routing (all topics share the group Session), while delivery follows the topic via `thread_id` (see below).
- `ConversationFacts.user_display_name` is the optional human-readable sender name supplied by the adapter (Telegram: `full_name` → `username` → `None`). The engine falls back to `user_id` where a display name is needed.
- `ConversationFacts` also carries per-message addressing facts supplied by the adapter: `message_id` (platform message id, used for group reply threading), `mentioned_bot` (platform-derived direct addressing, including Telegram @username and visible-name matches), and `is_reply_to_bot` (message replies to one of the bot's messages). The gating *decision* is engine-owned; adapters only supply facts.
- `ReplyPlanFacts.reply_to_message_id` is the platform message id engine replies should reference; the engine sets it from `ConversationFacts.message_id` for group conversations only, so DM replies stay plain. `ReplyPlanFacts.thread_id` is the platform thread/topic replies should land in, set from `ConversationFacts.thread_id`: it flows into every engine reply, the activity indicator, and the `last_reply_target` metadata, so multi-chunk replies and typing stay in the topic the message came from. Adapters whose threads are their own platform targets (Discord) accept and ignore it.
- `MessageFacts.content` may be plain text or canonical chat `ContentBlock` values; platform adapters own conversion from platform payloads into those blocks.
- `FileData` is the generic outbound file payload passed from tools/service code to adapters: `filename`, `media_type`, and raw `data` bytes.

## Interfaces

- `ChannelService(trigger_service, chat_sessions, *, agent_store, data_root, credential_resolver, attachment_store=None, command_dispatcher, interaction_dispatcher=None)` — constructor injection only, no runtime handle. `credential_resolver` is a `Callable[[str], str]`; Runtime wires `resolve_environment_credential`, which already prefers process environment over the data-dir `.env` fallback, so adapters never read `os.environ` themselves. `interaction_dispatcher` is the button-tap dispatcher threaded into interactive-capable adapters (see Interactive messages). The service's `ChannelStorage` also implements `ChannelAccessRegistry` and is injected into every adapter.
- `ChannelService` is the domain facade for config CRUD, lifecycle (`start`, `stop`, per-channel start/stop/restart), active/failed health checks, `send(channel_id, message, platform_target, files=..., thread_id=..., buttons=..., run_origin=None)`, and `ensure_outbound_session(channel_id, platform_target)` (delegates to the active adapter; raises `ChannelNotFoundError` when the channel is not active). `restart_channel(channel_id) -> bool` preflights and rebuilds only that enabled Channel from its current config and live credential, preserving server and sibling-Channel uptime; disabled Channels retain the new credential for their next enable and return `False`. `send` normalizes/validates `buttons` centrally (`_normalize_outbound_buttons`: rows of `InteractionButton`, each `data` a non-empty str ≤64 UTF-8 bytes, else `ChannelConfigError`) before delegating, so a bad payload fails uniformly across adapters. When `run_origin` is supplied, the Channel must belong to that Identity Agent and its origin Session must already exist; `send` persists one binding before platform delivery, replaces only `run:*` callback data with opaque private values, and removes the binding if delivery fails. Other buttons are byte-for-byte unchanged.
- `ChannelAdapter` exposes `platform`, `start()`, `stop()`, `send(message, platform_target, files=None, thread_id=None, buttons=None)`, `ensure_outbound_session(platform_target) -> RouteFacts` (resolves and ensures the Session mirroring an outbound target chat, creating it with channel context when missing), and `denied_chats() -> list[DeniedChatFacts]` (base implementation returns empty; Telegram and Discord override it with their `DeniedChatLog` entries). Only interactive-capable adapters honor `buttons`; Discord rejects a non-`None` `buttons` with `ChannelError` (interactive support is out of scope there). Platform-specific receiving, command dispatch, routing, and file-send details belong in child maps.
- `ChannelService.denied_chats(channel_id)` returns the running adapter's denied chats, or empty when the channel is not active. The `channel.status` RPC serializes them as `denied_chats` (list of `DeniedChatFacts.to_dict()`), consumed by the CLI status output and the WebUI channels panel (which offers a per-entry Allow action that appends the chat id via `channel.update`). Access reads and mutations are separate service calls over durable storage, so they work independently of adapter liveness.
- `ChannelConversationEngine(config, trigger_service, chat_sessions, transport, *, command_dispatcher, run_button_binding_registry=None)` is composed by adapters. Inbound entry points: `handle_inbound_text(conversation, text, *, raw_message=None)` (authorize/prepare a Command or gate/enqueue normal text; the optional opaque platform trigger lets the worker resolve a replied-to attachment after admission), `is_command(text)` (side-effect-free Chat-owned live Command recognition for adapter ingress decisions), `handle_inbound_media(conversation, raw_messages, *, companion_text=None)` (gate via the optional transport-reunited companion text plus captions, then enqueue one message or buffered album; the companion becomes the leading `TextBlock`), `observe_inbound_text(conversation, text)` (enqueue platform-acquired context without a Run; used by Discord backfill), `trigger_internal_reply(conversation, prompt) -> bool` (asynchronously enqueue an internal note-driven Run whose reply is relayed like any Channel answer), `trigger_interaction_reply(conversation, event) -> InteractionTriggerStatus` (`enqueued`, `denied`, `busy`, `already_handled`, or `unavailable` for a reserved Run tap), `prepare_inbound_route(conversation) -> (RouteFacts, ReplyPlanFacts)`, and `ensure_channel_session(conversation) -> RouteFacts` (the proactive `channel_send` entry; also writes the base Channel sidecar metadata — `source_channel_id`/`platform`/`platform_conv_id`/`last_reply_target` — without participant tracking). It owns the per-conversation ingress FIFO, immediate-versus-serialized scheduling from `PreparedCommand`, generic `CommandOutcome` projection, Run relay, Channel navigation/metadata, and platform-aware Command-unavailability text; Chat owns every Command workflow. `stop()` cancels workers and releases still-held ingress admissions.
- `should_respond(conversation, gating_texts=()) -> bool` is the engine's public gating decision (also consulted by adapters for adapter-local replies such as Telegram's unsupported-message-type reply): direct conversations always respond; groups respond when `response_mode` is `"all"`, or in `"mention"` mode when `mentioned_bot`/`is_reply_to_bot` is set or a `mention_patterns` regex matches one of the supplied texts.
- Group slash commands and reserved Run buttons use the same immutable ingress role as ordinary messages: only `admin` is authorized. The engine calls `CommandDispatcher.prepare(text)` without side effects, checks the role and Chat-owned surface availability before Queue admission or `execute`, and silently drops unauthorized group commands with an info log. DM commands remain authorized because the chat allowlist already identifies the sender and DM commands act on that sender's own Session.
- Non-triggering (unaddressed) group messages are dropped before any session work when `observe_unaddressed` is `false`. When it is `true`, the engine enqueues observation work in the conversation FIFO; the worker ensures the shared group Session, refreshes metadata/participants, and appends an internal note without triggering a Run or sending a reply.
- Sender identity is engine-derived and group-only: at the first Channel ingress boundary the engine atomically records the stable platform user id/display name and snapshots `admin` or `member` from `ChannelAccessRegistry`. It builds `MessageSender(id, display_name, role)` and carries that immutable value through the Channel FIFO and `TriggerService`, so queued work and historical attribution never change after a grant/revoke. Group user content renders `[display_name|platform_user_id|role]`; observed notes and interaction notes carry the same attribution. DM turns carry no sender.
- Every Channel Run whose Agent output is relayed to the initiating chat supplies a Chat-owned `ReplySurface` built from the configured platform, transport display name, Channel id, and `direct`/`group` conversation kind. This covers visible text/media, `/start`, and reserved `run:` button taps; repeated Runs on the same surface do not repeat the reminder. Chat/topic/thread ids are absent because `ReplyPlanFacts` and `last_reply_target` continue to own exact delivery.
- Group Tool access is dispatch-only and role-aware. A `member` Run receives an immutable admission ceiling of `web_search` and `web_fetch`; an `admin` Run receives no additional ceiling. Both receive a live pre-dispatch resolver: non-web Tools require both an admitted `admin` snapshot and a current `admin` role. Therefore a later grant cannot upgrade queued/running member work, while a revoke limits an active or waiting admin Run before its next Tool handler or Extension hook. The Agent's own allowlist remains an independent intersection, provider-visible definitions stay unchanged, and a denial returns `tool_not_allowed` with the stable member denial text.
- `ConversationTransport` is the `typing.Protocol` the adapter implements so the engine stays platform-free: `platform_display_name` (used to render reply/reminder text), `send_text(platform_target, text, *, reply_to_message_id=None, thread_id=None)`, `activity_indicator(platform_target, thread_id=None)` (async context manager), `build_media_blocks(raw_message) -> list[ContentBlock]`, `build_quoted_message(raw_message) -> QuotedMessageFacts | None` (adapter-owned reply-reference resolution and attachment ingestion), and `caption_text(raw_message) -> str | None` (caption extraction for gating checks).
- Session-id derivation is engine-owned. `group` kind → `ch-<channel-id>-<chat-id>` (ignores `dm_scope`). `direct` kind follows `dm_scope`: `per_conversation` (default) → `ch-<channel-id>-<chat-id>`, `main` → `ch-<channel-id>-main`, `per_peer` → `ch-<channel-id>-u<user-id>`, `per_account_channel_peer` → `ch-<channel-id>-<chat-id>-u<user-id>`. Session-id strings are a stable contract (WebUI session browsing, `session.link_channel`).
- **"Wegweiser" routing (anchor vs. active session).** The derived id is a stable **conversation anchor**, not necessarily the live session. `_route_facts` resolves the anchor through `_resolve_active_session_id` before routing: it reads the anchor sidecar's `active_session_id` pointer and routes there, falling back to the anchor itself when no pointer is set — so all inbound text/media, observed messages, and proactive `channel_send` follow the pointer (they all go through `_ensure_channel_session` → `_route_facts`). With no pointer the anchor *is* the session, so a chat that never ran `/new` routes byte-for-byte as before (no migration, no legacy branch — "no pointer" is the normal default). A successfully claimed origin-bound Run tap deliberately repoints this same anchor at the invoking Identity Agent Session before entering the conversation FIFO, so the tap and later Telegram messages continue there; `/new` uses the existing command flow to repoint it to a fresh Channel Session and therefore detaches Telegram again. The agent-wide `current_session_id` (WebUI/Desktop) is per-agent, not per-chat, and is deliberately **not** consulted for channel routing.
- **Slash Commands through Channels.** Telegram and Discord execute the shared live Chat-owned Built-in and Extension Command set through `prepare`/`execute`; neither transport has a command-name switch. Chat creates `/new` and returns `continue_in_session`; the engine then writes Channel metadata and repoints the anchor's `active_session_id`. `/handoff` and Extension follow-up Runs are relayed through the same generic outcome path without changing `ChannelConfig.agent_id` or the source anchor used by later messages. Every `/agent` form is refused before execution with `The /agent command is not available through <Platform>.`; the wording is permanent and must not imply future implementation.
- **Platform chat-id migration.** `ChannelConversationEngine.migrate_group_conversation(old_chat_id, new_chat_id)` bridges a group conversation whose platform chat id changed in place (Telegram group→supergroup upgrade): the new chat id's anchor gets an `active_session_id` pointer at the old conversation's active session (single hop), that session's channel sidecar moves to the new chat id (`platform_conv_id`/`last_reply_target`, so proactive `channel_send` targeting follows), and a session note tells the model; returns False (no-op) when the old conversation has no session to bridge. `ChannelService.record_chat_id_migration(channel_id, old, new)` persists the allowlist swap into `channel.json` and merges/moves the old access group (admins plus newest participant records) into the new scope **without restarting the adapter**. It is idempotent when the old id is already gone. The Telegram adapter receives this as the injected `chat_migration_persister` callback.
- Server RPCs live in `server/rpc/channel_methods.py`: config/lifecycle methods plus `channel.access.get`, `channel.identity.set`, `channel.admin.grant`, and `channel.admin.revoke`. Access mutations return the complete saved access projection, publish `resource_changed(kind: "channels")`, and deliberately do not call `runtime.reload_channel_tool()`; config/lifecycle mutations retain their existing reload behavior. The WebUI uses the access projection for durable participant rows, own-identity selection, and immediate role toggles. The CLI mirrors it with `channel identity`, `channel access`, and idempotent additive `channel grant-admin` / `channel revoke-admin` commands.
- `ChannelConfig.agent_id` is a live Identity Agent reference. The coordinated `agent.rename` server operation retargets every matching Channel through `ChannelService.update_channel`, preserving its normal validation, persistence, adapter stop/restart, and per-channel rollback behavior; Channels do not interpret Agent rename themselves.
- Retroactive Channel linking lives in `session.link_channel` in `server/rpc/agent_methods.py`. It verifies the Channel belongs to the Agent and writes the same Session metadata keys used by adapters. Linking does not append a reply-surface note; a later interactive Run establishes the current surface.
- `register_channel_send_tool(registry, channel_service, chat_sessions)` registers `channel_send` when at least one valid Agent owns an enabled persisted Channel config. Adapter liveness is deliberately not part of this contract.

## Interactive messages (buttons + taps)

A message can carry an inline **keyboard** (rows of buttons); tapping one produces a **tap event** the runtime normally routes to an in-process **extension** handler, so extension-owned taps are handled deterministically with no Run. The reserved `run` prefix is the deliberate agent-waking exception. Channels carry the neutral interaction contract (`InteractionButton`/`InteractionEvent`/`InteractionResponder`, defined in `core/extensions/interactions.py` — channels imports these; extension tap-handling logic lives in an extension, see `extensions/capabilities.md` → Channel interaction handlers).

- **Outbound buttons.** `ChannelService.send(..., buttons=...)` takes `list[list[InteractionButton]]`, validates centrally, and passes it to the adapter. `channel_send` exposes this as its `buttons` parameter (see `tools/channel_send.md`). Only interactive-capable adapters render it (Telegram today); Discord rejects it.
- **Extension-handled taps are adapter-owned and do NOT produce a Run** (the reserved `run` prefix is the exception — see the next bullet). Such a tap bypasses the `ChannelConversationEngine` entirely — no `should_respond`, no `TriggerService`, no per-conversation FIFO (queuing taps behind runs would add latency). The callback path is a separate adapter handler. The tap reuses only the inbound *identity + allowlist* plumbing (`_conversation_facts`, `_is_chat_allowed`, `_record_denied_inbound`): a denied tap is recorded and silently acknowledged but never dispatched.
- **One reserved prefix wakes the agent.** Agent/Skill authors emit only the public form `run:<payload>` (`RUN_TRIGGER_PREFIX` in `core/extensions/interactions.py`); no extension can claim it. For an Identity Agent `channel_send`, the tool supplies its calling Session as `run_origin`, and `ChannelService` replaces the wire callback with an opaque versioned binding envelope while preserving the original public values in durable storage. On a tap, `trigger_interaction_reply` verifies the exact Channel/target/thread, claims the whole message binding once, restores the public keyboard state for the model-facing note, verifies the origin Session still exists without recreating it, repoints the conversation anchor, and queues an `internal=True` Run in that origin Session. The Run reply still relays to the tapped Telegram chat, and an immediately following Telegram message enters the same FIFO behind the tap and resolves to the newly pointed Session. A duplicate tap is terminal and starts no Run, including after restart; an invalid/missing binding or deleted origin returns `unavailable` without falling back to or recreating another Session. Queue rejection is retryable: the engine restores both the previous anchor metadata and the pending claim before sending the normal busy reply. Project-session `channel_send` calls retain the legacy raw callback and therefore wake the Channel's current active Identity Session rather than failing or crossing the project/identity storage boundary. Legacy raw `run:<payload>` buttons from direct service/adapter callers also retain current-active-Session routing.
- **Run-button UI completion follows the engine outcome.** Telegram closes the keyboard only for `enqueued`, `already_handled`, or `unavailable`; `already_handled` receives an explanatory toast and `unavailable` an alert. `busy` and unauthorized group taps keep the keyboard so a legitimate retry remains possible. Accepted taps are silently acknowledged. The model-facing note always contains the tapped button and every current button's restored public label/data in row order, so checklist state remains message-carried rather than server-owned.
- **The dispatcher is injected live-reading.** Runtime injects `Runtime._dispatch_channel_interaction` (which reads the current `self._extensions`) as `interaction_dispatcher=` into `ChannelService`, which threads it into the adapter. Because it reads the registry live, an extension reload/disable needs **no** channel re-wiring — the next tap uses the current registry.
- **Guaranteed single acknowledge.** The adapter's concrete `InteractionResponder` tracks an `answered` flag; after extension dispatch the adapter sends a fallback ack if the handler did not (or no handler matched, or the handler raised), so the tapper's client-side spinner always stops. `answer()` acknowledges; `edit()` rewrites the tapped message's text and/or keyboard. Extension-owned tap state has no core persistence — the platform delivers the current message + keyboard with every tap. The only persisted interaction state is the reserved Run-button origin/idempotency binding above; checklist selection state still comes from the Telegram keyboard snapshot.

## Specific Specs

- `channels/discord.md` - Discord Gateway adapter: message-content intent, history backfill, thread routing, attachments, typing, replies, and send limits.
- `channels/telegram.md` - Telegram platform-I/O adapter: long polling, update parsing, media ingestion, typing indicator, and Telegram send behavior.

## Conventions

- Channels are accessors. Do not put provider behavior, model fallback, or alternate chat-loop semantics in this domain.
- Where new channel code goes: platform-neutral conversation behavior (queueing, command handling, run trigger/relay, session routing/metadata) belongs in `engine.py`; platform I/O (library lifecycle, inbound parsing, media download, outbound send, the activity indicator) belongs in the adapter module. New cross-platform features land in the engine once, not per adapter.
- Inbound attachment classification is shared: `content_blocks_for_attachment(record)` in `adapter.py` is the single rule mapping a stored attachment's sniffed media type to one or more content blocks (image/audio/video → `MediaBlock`; every other type, including text, → `FileBlock`). Adapters `extend` their block list with the result, so the platforms cannot drift, regardless of how the platform delivered the file (e.g. a Telegram MP3 sent as a "document" is media, not a generic file). Classification is by sniffed type, never by the platform's delivery channel; the chat resolver gives a text `FileBlock` the exact same bounded, line-numbered initial read as the `read` tool, plus its `Path:` handle.
- The engine serializes inbound messages, reserved Run taps, serialized `PreparedCommand` values, and media work per conversation through one FIFO queue and worker keyed by platform target. Every queued candidate first reserves capacity in `ChatRunManager`: a chat may have at most 8 waiting messages or deferred operations, and all Channels together at most 32 waiting tasks; the active operation does not count. The reservation transfers into the normal Run FIFO when a Session is busy and is otherwise released when work starts. Ordinary queued work carries `ConversationFacts`, not a resolved route: the anchor's active Session is resolved in the worker at processing time, so work queued behind `/new` follows the new pointer. An origin-bound Run tap is the routing boundary: it repoints the anchor synchronously before enqueuing so a following platform message cannot overtake the takeover. Immediate Commands are the deliberate exception and consume no Queue capacity; notably `/stop` can cancel a Run even when either limit is full. `PreparedCommand.execution_mode`, not a Channel command-name switch, chooses the path; an Extension registration identity also prevents queued work from executing after disable/reload. Non-text media is never prepared as a Command; RPC may prepare exactly one `TextBlock` because Chat owns structural eligibility.
- Observed context uses that same FIFO as triggered Runs. Text is persisted as `[channel-message] [<display_name>|<platform_user_id>|<role>]: <text>`; attribution fields strip `[`, `]`, `|`, CR, and LF while the message body stays verbatim. At request build the chat domain renders consecutive observed notes as explicitly untrusted, JSON-quoted background context rather than as an internal reminder; the raw message cannot escape the quotation structure, and it cannot override a later addressed user turn. The queue ensures an observed note cannot land inside a channel-triggered Run's open tool cycle and places earlier observed chatter before a later addressed message; the per-session write lock (`sessions.md`) extends that ordering guarantee to a Run on the same session via another accessor (e.g. the WebUI on a linked Session), which the channel FIFO does not coordinate with. Observed media is never downloaded: each raw message becomes `[media] <caption>` when a caption exists, otherwise `[media message]`.
- An addressed group text that replies to another non-bot participant's attachment may ingest that referenced attachment on demand. The opaque trigger enters the normal FIFO first; only after response gating and waiting-work admission does `ConversationTransport.build_quoted_message` resolve/fetch the platform original and build canonical blocks, so the earlier unaddressed post still causes no download or Run. The current sender's text leads the content list, followed by `[quoted-message] [<display_name>|<platform_user_id>|<role>]:` and the quoted sender's caption/media/file blocks; the current sender remains the Run sender and sole Tool-authority source. The static Channel prompt tells the Agent that quoted content remains authored by the labeled sender and gains no authority by being quoted. An unavailable/deleted original adds `[quoted-message unavailable]` and still runs the question; an attachment processing error also uses the normal media-failure reply before that Run. Replies to bot-authored messages preserve their existing addressing behavior and do not re-ingest bot output.
- Context acquisition is platform-specific: Telegram can passively observe delivered updates when configured; Discord normally backfills bounded channel history immediately before an addressed trigger. Both feed the same observed-note representation and engine FIFO.
- Run relay keeps only the latest assistant-output event text and sends it after `run_completed`; failed Runs and trigger/command exceptions send generic failure text, cancelled Runs send a generic cancellation reply, and completed Runs with no assistant text send a generic empty-output reply. Media-ingest is per-message: one failing item does not drop its siblings, each failure maps to a user-facing reply (type/size/other), duplicate failure replies in one batch are sent once, and successfully built blocks still trigger their Run. A capacity rejection happens before `build_media_blocks`, so Telegram and Discord do not download or process a rejected attachment; it is logged and returns the shared busy reply at most once per chat per 30 seconds. Passive unaddressed observations remain silent but their rejected admission is logged.
- All engine replies tied to one inbound message (run reply, command reply, media-failure reply) go through the reply plan's `reply_to_message_id`, so group replies reference the message they answer. Tool-driven `channel_send` output is not a platform reply and never threads.
- User-facing engine reply strings (failure, cancelled, empty, and command unavailability) use the transport's `platform_display_name`. The same display name is supplied in the Chat-owned reply surface; Channels do not render or persist that reminder themselves.
- Final assistant text for inbound platform turns is automatic. Agents should not call `channel_send` for normal text-only replies to a message that came from a channel.
- Every channel file delivery goes through `channel_send`, including files sent while replying to a channel-originated turn; the normal reply relay forwards text only. `channel_send` may send text only, files only, or both; at least one payload is required.
- `channel_send` target resolution order is explicit `platform_target`, then matching `last_reply_target` session metadata, then a single configured `allowed_chat_ids` value. Metadata for a different `channel_id` is ignored. An optional `thread_id` argument addresses a thread/topic inside the target (Telegram forum topics); an explicit `thread_id` always wins, the metadata thread rides along only with the metadata target (an explicitly targeted send never inherits another conversation's topic), and `ChannelService.send(..., thread_id=...)` passes it to the adapter.
- `channel_send` is registered only while at least one valid Agent owns an enabled Channel config. Persisted create/delete/enable/disable transitions re-evaluate registration; adapter start, stop, failure, and restart do not, so transient liveness cannot churn Provider Tool definitions or the prompt cache.
- Public create/update/enable paths reject unknown Agent IDs before persisting or enabling a channel. Runtime startup degrades per channel and never fails as a whole: a corrupt or schema-invalid `channel.json` is skipped with a logged warning when configs are loaded (`ChannelStorage.load_all`), so one bad file neither blocks server startup nor hides the other channels (strict single-channel access via `get` still raises); and an enabled channel with invalid runtime dependencies is marked failed with a diagnostic reason without preventing the server from starting.
- Missing or empty `allowed_chat_ids` means deny-all for inbound allowlisted platforms. It is not "allow everyone".
- Channel token values cross the RPC boundary only as write-only inputs. They are stored through `StorageManager.set_data_dir_credential`, never persisted in Channel JSON, returned, or logged; log records may name the Channel, credential key, and effective source only.
- **`allowed_chat_ids` gates inbound only — outbound is deliberately unrestricted.** `channel_send` with an explicit `platform_target` may message any chat the bot can reach; the platform itself bounds this (a Telegram bot can only message groups it was invited to or users who contacted it first). This is a conscious max-agency decision, not an oversight — do not "fix" it by filtering outbound targets through the allowlist.
- Session history remains the single source of truth. Channels add routing metadata and contextual notes, but reply-surface state is the Chat-owned tagged Session chronology; Channels do not keep a parallel transcript or mutable surface sidecar.
- `channel_send` records sent content as a contextual System Reminder in the target chat's Session via `ensure_outbound_session`, so inbound replies keep context. The append acquires the Session write lock and re-enters safely when a Run sends to its own Session. This proactive path writes base Channel sidecar metadata but no reply-surface note, because sending proactively is not an interactive reply Run.

## Constraints & Gotchas

- Only final assistant text from a completed Run is forwarded to the platform by current adapters. Tool results, reasoning, and intermediate Run events stay in the JSONL/SSE flow.
- Adapter failures use bounded restart with exponential backoff (`1s`, `2s`, `4s`, max 3 retries). Exhausted retries mark the channel failed in runtime-local health state; `channel.json` remains the source of truth for configuration.
- Create/update paths preflight adapter construction when possible and roll back persisted config if starting the enabled adapter fails.
- `channel_send` reports success only after `ChannelService.send()` and the adapter send call complete. It is not fire-and-forget.
- Prompt rendering lists enabled persisted Channels for the current Agent regardless of adapter liveness. A channel with exactly one `allowed_chat_ids` value is shown as having a default target; otherwise agents must provide an explicit target. A send through an enabled but currently unavailable Channel reaches the ordinary execution boundary and returns a Tool failure instead of changing the prompt prefix.
- WebUI session browsing and retroactive channel linking depend on the sidecar metadata contract. Keep `source_channel_id`, `platform`, `platform_conv_id`, and `last_reply_target` stable when changing channel routing.
- Channel ids are bare slugs (`^[A-Za-z0-9][A-Za-z0-9_-]*$`), enforced at the `_normalize_channel_id` choke point every storage/service call funnels through — not only by `ChannelConfig.validate`. The id is a path segment under `<data_dir>/channels/` and `delete_channel` recursively removes that directory, so a separator or `..`/absolute id must never reach the filesystem layer (it would otherwise let an operation escape storage and rmtree an arbitrary directory). Tighten id handling here, never just at config validation.
- A channel's bound `agent_id` is validated as a full agent-id slug (`AGENT_ID_PATTERN`) by `validate_channel_data`, not merely as a non-empty string — it flows into `ChatSessionManager` session paths on every inbound message, so a non-slug value must never load. `channel.create`/`channel.update` additionally require the agent to exist (`_validate_channel_agent_exists`); the file-load slug check is the defense-in-depth backstop for a hand-edited `channel.json`.
