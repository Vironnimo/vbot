# Channels

Messaging-platform accessors for vBot. Owns channel configuration, adapter lifecycle, outbound delivery, and routing platform inbound messages into normal agent Sessions.

## Overview

`core/channels/` bridges external messaging platforms into the existing agentic loop. A Channel is an accessor-side transport abstraction, not a model provider: it receives inbound platform messages, resolves them into an Agent and Session, triggers normal Runs, and routes assistant replies back through the platform adapter. `ChannelService` owns persisted channel configs under `<data_dir>/channels/` and Channel state in the canonical `<data_dir>/channels.db`, starts and stops adapter tasks for enabled channels, and exposes outbound message and file support for the `channel_send` tool. Channels reuse normal Sessions, `TriggerService`, `CommandDispatcher`, attachment storage, and prompt/tool registration; they do not own a separate conversation store.

`config.py` owns configuration values and schema diagnostics; `storage.py` owns the persisted `channel.json` configuration; `state.py` (`ChannelStateStore`, DDL and kernel declaration in `_state_schema.py`) owns `channels.db`. `channels.py` coordinates adapter lifecycle and the public Service API; `_delivery.py` implements outbound normalization, durable Run-button binding and completion relay within that owner.

Platform-neutral conversation behavior lives in `core/channels/engine.py` (`ChannelConversationEngine`), shared by all adapters. Each `ChannelAdapter` composes one engine in its `__init__` and delegates to it; the adapter is reduced to platform I/O. The engine owns per-conversation ingress ordering and worker serialization, slash-command dispatch handling, run trigger/relay, and session routing/metadata/derivation; `ChatRunManager` remains the single authority for active and waiting-work capacity. It never imports a platform library: raw platform messages flow through it as opaque values and are converted to canonical content blocks by the adapter-supplied `ConversationTransport`.

## Data Model

- `ChannelConfig`: `id`, `platform` (`telegram` | `discord` | `slack` | `mattermost` | `whatsapp`), `agent_id`, `dm_scope`, `allowed_chat_ids`, `token_env_var`, `app_token_env_var`, `server_url`, `enabled`, `response_mode`, `mention_patterns`, `observe_unaddressed`. Config files live at `<data_dir>/channels/<channel-id>/channel.json`, a Generation 1 JSON document (`format_version` 1, unknown fields kept on save, never overwritten after a failed load; contract in `settings.md`). The retired `owner_user_ids` is an ordinary unknown field; group admins live in access settings. Reads never migrate configuration or permissions. Raw-file validation, config construction and saving share the same schema checks and accepted-value normalization.
- Group response gating: `response_mode` is `"mention"` (default - groups respond only when addressed) or `"all"` (respond to every allowed group message). `mention_patterns` are wake-word regexes (must compile, matched case-insensitively against text and captions). `observe_unaddressed: true` persists otherwise-unaddressed group messages as internal context notes in `"mention"` mode. DMs always respond regardless of `response_mode`. `allowed_chat_ids` is normalized to strings - platform conversation ids, or literal `self` for WhatsApp - and empty means deny-all inbound.
- `token_env_var` is the adapter-facing credential indirection: managed tokens get a deterministic collision-free key (`VBOT_CHANNEL_TOKEN__` plus the Channel id's uppercase hex); externally managed deployments may supply their own key. Slack uses a separate `app_token_env_var`; Mattermost requires `server_url`. WhatsApp uses linked-device pairing and accepts no token fields. The raw token is never part of `ChannelConfig` or `channel.json`.
- Channel state lives in the canonical database `<data_dir>/channels.db` (`channel_database_spec`, `APPLICATION_IDS["channels"]`; opening, corruption handling, snapshots and recovery follow the kernel's canonical profile, `database.md`). `ChannelService` opens `ChannelStateStore` at construction, adopts every Channel id with a `channel.json` into the registry together with the platform that config names (keeping existing rows unless they belong to another platform, see Platform, token and bot changes), and closes it with the service. All tables are STRICT and WITHOUT ROWID; conversation kinds are validated in code, not by CHECK constraints; timestamps are canonical UTC text `YYYY-MM-DDTHH:MM:SS.ffffffZ` (`core/utils/timestamps.py`), so text order is time order.
- `channels(channel_id, platform, self_user_id)` is the registry of configured Channels with the platform whose ids the state holds and the optional channel-own platform identity. Every other table references it with `ON DELETE CASCADE`. State writes for an unregistered Channel raise `ChannelNotFoundError`, so a late save of a stopping adapter cannot recreate state after a delete. Create resets any rows left under a reused id; delete removes `channel.json`, then unregisters the Channel, removing all its rows in one transaction. Both registry writes run together with their `channel.json` write as one unit on the `channels.db` worker pool (`Database.run_async`), never on the Event Loop: create writes `channel.json` first and removes both again when the registration, the adapter start, or a cancellation after the unit fails; delete stops the adapter on the loop first. Update, enable and disable read and write `channel.json` on the same pool (`_change_config`): the write lands before a running adapter is disturbed, so a failed write leaves config and connection untouched; the adapter then stops and starts on the loop, and a failed adapter start or a cancellation after the write restores the previous config and the adapter it ran (enabling a Channel whose start fails therefore leaves it disabled). A platform change also waits for the old adapter's stop and rebinds the state before the new adapter starts (below). Restart reads its config there too. While any of these config changes is in flight, every other change of that Channel id (create, update, enable, disable, restart, delete, WhatsApp setup/pairing) is refused with `ChannelError` (`_pending_config_changes`, `tests/core/channels/test_channels_service.py`, `test_channels_recovery.py`).
- Group access: `channel_admins(channel_id, access_scope_id, user_id)` and `channel_participants(channel_id, access_scope_id, user_id, display_name, last_seen_at)`, keyed by the stable adapter-supplied access scope. Roles are only `admin`/`member`; the own identity is effectively admin everywhere and cannot be demoted; additional admins are scoped per group. Ingress records the participant and reads its role in one write transaction (`snapshot_participant_role`); the per-Tool-dispatch `role_for` reads an in-memory index that every committed access mutation refreshes, never storage. Access mutations are transactional and never rewrite `channel.json`, restart an adapter, rebuild the System Prompt, or alter provider Tool definitions; the access projection lists only groups with admins or participants.
- `channel_conversations(channel_id, conversation_id, conversation_kind, active_session_id, updated_at)` holds the "Wegweiser" pointer per derived anchor id (see Interfaces). A row exists once a conversation was first pointed; a NULL `active_session_id` means the anchor itself is active.
- `channel_run_buttons(channel_id, binding_id, platform_target, thread_id, origin_session_id, button_data_json, created_at, consumed_at)` holds origin bindings for `channel_send`-authored `run:*` buttons - routing/idempotency state, not conversation state. A claim is one conditional update of a NULL `consumed_at` inside a write transaction, so of racing taps exactly one claims; consumed rows are retained (no retention limit yet) so a duplicate or post-restart tap cannot start a second Run.
- `channel_received(channel_id, message_ref, received_at)` is the socket platforms' inbound receipt window (`channels/network-platforms.md`): each recorded receipt prunes the Channel to its newest `RECEIVED_MESSAGE_WINDOW` (4096) entries, the only reader of the index `channel_received_by_time`.
- `channel_polling(channel_id, bot_id, last_update_id, updated_at)` is the Telegram long-polling watermark of the bot `bot_id` (the `get_me()` id at adapter start). Update ids count per bot, so another bot's watermark (or one naming no bot) reads as 0 and yields to that bot's first save: a token for another bot would otherwise drop every update at or below the old bot's mark for up to 48 hours, while a rotated token of the same bot keeps its mark. A save is one conditional upsert that only raises a fresh watermark of the same bot, so out-of-order worker saves cannot regress it; a watermark whose `updated_at` is older than 48 hours reads as 0 and yields to any new id. Live adapters also expire theirs after 48 hours without a claimed update using a monotonic clock. This covers Telegram's 24-hour replay window while accepting randomized lower ids after a week idle. A restart skips updates at or below a fresh watermark so unconfirmed recent updates do not replay as duplicate Runs (`tests/core/channels/test_telegram_failures.py`).
- **Platform, token and bot changes.** User, chat, group and message ids of one platform mean nothing on another. A committed platform change (`channel.update` from RPC, CLI or the WebUI edit form, through `_change_config`) therefore resets that Channel's state in one transaction (`ChannelStateStore.bind_platform`): own identity, group access, conversation pointers, Run-button bindings, receipts and watermark. The reset runs after the old adapter finished stopping, so its last writes cannot land afterwards, and before the new adapter starts; a failed change binds back to the previous platform, whose state then stays empty too. Only the pointer of the `dm_scope` `main` anchor (`main_conversation_id`), which names no platform id, survives: dropping it would revive the anchor Session instead of the Session `/new` or a Run tap moved to. A NULL `channels.platform` (no readable config yet) takes the first platform without a reset. At construction, `adopt` resets state recorded for another platform than `channel.json` names (a hand edit, or a change interrupted between `channel.json` and `channels.db`) and logs `Channel state reset for a new platform`. Everything else deliberately stays: a rotated token or another Telegram or Discord bot (`channel.set_token`, `token_env_var`, `.env`) keeps access and pointers because user and chat ids are global on both platforms; only the watermark is per bot (above), and an old bot's Run buttons can never reach the new bot because Telegram delivers a tap to the bot that sent the message. A Slack workspace or Mattermost server change cannot be told apart from a token rotation or URL change of the same one; ids of another workspace or server are opaque and practically never match, so leftover rows stay inert (their groups remain visible in the access settings). WhatsApp re-pairing keeps its state (`channels/network-platforms.md`). Session metadata stays too: a completion relay refuses a reply surface of another platform, and a `channel_send` to a previous-platform `last_reply_target` fails as an ordinary Tool failure. A new state table must decide whether its rows name platform ids and belong in the `bind_platform` reset (`tests/core/channels/test_channels_platform_change.py`).
- Pre-Generation-1 state files beside `channel.json` (`access.json`, `run-button-bindings.json`, `polling.json`, `received.json`) and the anchor-Session `active_session_id` pointers in `sessions.db` are converted offline by `scripts/converters/persistence_generation_1/channels.py`: every directory with a `channel.json` is registered with the platform its config names (NULL when unreadable), pointers are kept only for the Channel's current Agent, invalid entries are skipped and reported, and every state file is retired. The old polling watermark names no bot, so it is dropped and reported; the first start after the conversion may see Telegram redeliver updates it never confirmed. vBot itself never reads the old files.
- Config reads pass through the Channels-owned schema (`core.channels` exports the validators consumed by RPC/CLI); schema errors raise `ChannelConfigError` with file/path diagnostics, while runtime-only failures such as missing credentials do not mutate persisted config.
- Channel Session metadata lives in the ChatSessionManager-owned canonical Session store. Channel-owned keys: `source_channel_id`, `platform`, `platform_conv_id`, and `last_reply_target {channel_id, platform_target, thread_id?}` (per-Session delivery state for completion relays and `channel_send`). Conversation pointers, conversation kinds and group participants are Channel state in `channels.db`, never Session metadata; the pre-Generation-1 keys `active_session_id`, `conversation_kind` and `participants` are retired. Routing re-asserts this context through `ChatSessionManager.ensure_metadata`: a known conversation with unchanged context costs only reads, and a first message creates the Session with its context in one write. An observed message on a known conversation therefore writes only its note, and a repeated `channel_send` target only its outbound note (`test_engine_groups.py`).
- Telegram adapter internals separate lifecycle/update dispatch (`telegram.py`), delivery and media conversion (`_telegram_transport.py`), inbound coalescing (`_telegram_inbound.py`), message values (`_telegram_messages.py`), and SDK operations (`_telegram_api.py`), keeping the public Channel adapter lifecycle unchanged.
- The conversation engine keeps admission, FIFO workers, Command projection and Run relay in `engine.py`; `_conversation_routing.py` owns Session anchors/navigation/metadata through the injected `ConversationPointerStore`, `_conversation_access.py` owns response eligibility and group sender authority, `_conversation_content.py` projects neutral notes and results, and `_conversation_work.py` defines the transport and admitted work payloads. Helpers receive the specific config/Session/access dependencies they need, never the engine.
- Adapter/engine facts: adapters classify the conversation (`direct`/`group`), supply display name, message id, addressing facts (`mentioned_bot`, `is_reply_to_bot`), and thread ids, and convert payloads into canonical content blocks; the engine owns every gating and routing *decision*. Discord threads route as their own chats; Telegram forum topics share the parent group Session while delivery follows the topic via `thread_id`.
- Conversation-engine and Telegram logs omit external conversation/user/thread ids and derived Session ids; routine routing stays silent. Allowlist-rejected chats land in a bounded recency log on the adapter, surfaced through channel status - that log is the discovery workflow: message the bot once, read the id from status, allow it. Recording never changes gating; restarts clear the log.
- `FileData` (`filename`, `media_type`, raw bytes) is the generic outbound file payload handed from tools/service code to adapters.

## Interfaces

Async Channel ingress and outbound delivery never perform Session or config persistence I/O directly on the Event Loop. Engine ingress takes one hop per database: conversation pointers and Run-button claims/restores run on the `channels.db` pool (`run_async` of the `ConversationPointerStore`/`RunButtonBindingRegistry` seams, implemented by `ChannelStateStore`), route metadata, Session existence checks and notes on the Session database's pool (`ChatSessionManager.run_async`). Outbound work splits the same way. A Run-button send checks its origin Session on the Session pool, then reads the Channel config, checks ownership and saves the binding in one `channels.db` hop, like other `channel.json` reads that belong to Channel state work. The async `ensure_outbound_session` reads the conversation pointer on the `channels.db` pool and creates the Session with its metadata on the Session pool. A closed database on either side fails with `DatabaseUnavailableError` before anything is sent, bound or created (`tests/core/channels/test_channels.py`, `test_engine_routing.py`). An unadmitted bound tap, including one failing on a closed database, restores its pointer and binding before the error propagates (`tests/core/channels/test_engine_interactions_replies.py`). Session write locks still protect note ordering against open Tool cycles.

- `ChannelService` is the domain facade: config CRUD (`create_channel`, `update_channel`, `enable_channel`, `disable_channel`, `delete_channel` and `restart_channel` are async and keep `channel.json` I/O off the loop; `list_channels`/`has_enabled_channels`, adapter recovery and the WhatsApp status/setup paths still read configs synchronously on the loop), lifecycle (`start`/`stop`/per-channel start/stop/restart), health checks, `send(...)`, and async `ensure_outbound_session(...)`. Runtime injects `credential_resolver` so adapters never read `os.environ` themselves (process environment wins over the data-dir `.env` fallback). `restart_channel(channel_id)` preflights and rebuilds only that enabled Channel from current config and live credential, preserving server and sibling uptime; disabled channels retain the new credential for their next enable.
- Outbound `send` validates `buttons` centrally (rows of `InteractionButton`, non-empty data <=64 UTF-8 bytes) before delegating, so a bad payload fails uniformly across adapters. With `run_origin`, the Channel must belong to that Identity Agent and its origin Session must exist; see Interactive messages for the binding contract.
- Cancellation during outbound Run-button preparation keeps a binding the `channels.db` worker already saved and removes it before returning, because its message was never sent. Repeated cancellation still waits for that cleanup on the `channels.db` pool.
- Only interactive-capable adapters honor `buttons`; Discord, Slack, Mattermost and WhatsApp reject them (`ChannelError`). Platform-specific receiving, command dispatch, routing, and send details live in the child maps.
- `denied_chats(channel_id)` exposes the running adapter's rejected-chat log (empty when inactive) to the `channel.status` RPC, CLI status output, and the WebUI panel's per-entry Allow action; access reads/mutations work independently of adapter liveness.
- The engine's ingress surface: `handle_inbound_text` (authorize a Command or gate/enqueue text), `handle_inbound_media` (gate then enqueue one message or buffered album), `trigger_internal_reply` (note-driven Run whose reply relays like any answer), `trigger_interaction_reply` (reserved Run taps -> `enqueued`/`denied`/`busy`/`already_handled`/`unavailable`), `prepare_inbound_route`/`ensure_channel_session` (routing plus the proactive `channel_send` entry). Text/media ingress reports admission and accepts bounded `observed_context` carried under the triggering turn's one waiting-work reservation. The engine snapshots context sender roles at ingress and persists the notes before triggering the Run; rejected turns do not consume their context. It owns the per-conversation FIFO, immediate-vs-serialized Command scheduling, generic `CommandOutcome` projection, Run relay, navigation/metadata, and platform-aware unavailability text; Chat owns every Command workflow.
- `should_respond(conversation, gating_texts)` is the public gating decision: direct always responds; groups respond in `"all"` mode, or in `"mention"` mode when mentioned/replying-to-bot or a wake-word regex matches.
- Group slash commands and reserved Run buttons use the immutable ingress role: only `admin` is authorized; unauthorized group commands drop silently with an info log. DM commands stay authorized because the allowlist identifies the sender acting on their own Session.
- Observed (unaddressed, `observe_unaddressed: true`) group messages enqueue in the conversation FIFO: the worker ensures the shared group Session, refreshes its Channel metadata, and appends an internal note - no Run, no reply. The sender is recorded as a participant at ingress like any group sender.
- Sender identity is engine-derived and group-only: at first ingress the engine atomically records stable user id/display name and snapshots `admin`/`member`; the immutable value rides the FIFO and `TriggerService`, so queued work and historical attribution never change after a grant/revoke. Group user content renders `[display_name|platform_user_id|role]`; DM turns carry no sender.
- Every Channel Run whose output is relayed supplies `RunKind.CHANNEL` and a Chat-owned `ReplySurface` (platform, display name, Channel id, direct/group). Chat/topic/thread ids stay absent because `last_reply_target` owns delivery; repeated Runs on the same surface do not repeat the surface reminder.
- Group Tool access is dispatch-only and role-aware. A `member` Run receives an immutable admission ceiling of `web_search` and `web_fetch`; an `admin` Run receives none. Both get a live pre-dispatch resolver: non-web Tools require both an admitted `admin` snapshot and a current `admin` role - a later grant cannot upgrade queued/running member work, while a revoke limits an active or waiting admin Run. The Agent's own allowlist intersects independently, provider-visible definitions stay unchanged, denial returns `tool_not_allowed`.
- `ConversationTransport` is the typing.Protocol keeping the engine platform-free: display name, text send (reply/thread targeting), activity indicator, media-block building, quoted-message resolution, caption extraction.
- Session-id derivation is a stable contract (WebUI browsing, `session.link_channel`): `group` -> `ch-<channel-id>-<chat-id>`; `direct` follows `dm_scope` - `per_conversation` (default) -> `ch-<channel-id>-<chat-id>`, `main` -> `ch-<channel-id>-main`, `per_peer` -> `ch-<channel-id>-u<user-id>`, `per_account_channel_peer` -> `ch-<channel-id>-<chat-id>-u<user-id>`.
- **"Wegweiser" routing (anchor vs active session).** The derived id is a stable conversation anchor; routing resolves the conversation's `channel_conversations` pointer first and falls back to the anchor itself. The pointer is Channel state: deleting or archiving the anchor Session does not reset it. All inbound text/media, observed messages, and proactive `channel_send` follow the pointer; without one the anchor *is* the session ("no pointer" is the default - no migration branch). A claimed origin-bound Run tap repoints the anchor at the invoking Identity Agent Session before entering the FIFO, so following platform messages continue there; `/new` repoints it to a fresh Channel Session and detaches the platform again. The agent-wide `current_session_id` is deliberately not consulted for channel routing.
- **Slash Commands** execute the shared live Chat-owned set through `prepare`/`execute` - neither transport has a command-name switch. `/new` uses the Session store's compact `ses_` allocation rather than appending a UUID to the conversation anchor, and returns `continue_in_session`; the engine writes the new Session's Channel metadata and repoints the conversation. `/handoff` and Extension follow-up Runs relay generically without changing `ChannelConfig.agent_id` or the source anchor. Every `/agent` form is refused before execution with `The /agent command is not available through <Platform>.` - permanent wording, never implying future implementation.
- **Platform chat-id migration** (Telegram group->supergroup upgrades): the new chat id's conversation gets a one-hop pointer at the old active Session (no Session is created for the new anchor), that Session's Channel metadata moves to the new id, a session note informs the model, and the allowlist swap plus the merge of the group's admins and participants into the new access scope persist without restarting the adapter; idempotent when the old id is gone.
- Access reads and mutations are async `ChannelService` methods (the `channels.db` I/O runs on the database worker pool); mutations return the complete saved access projection and publish `resource_changed(kind: "channels")`, deliberately without calling `runtime.reload_channel_tool()`; config/lifecycle mutations keep their existing reload behavior.
- `ChannelConfig.agent_id` is a live reference: coordinated `agent.rename` retargets matching Channels through the service with normal validation and per-channel rollback; its worker thread hands each `update_channel` to the Event Loop that owns the adapters (`server/rpc/agent_refs.py::_retarget_channel`). Retroactive linking (`session.link_channel`) writes the same Session metadata keys and appends no reply-surface note. `channel_send` registers only while at least one valid Agent owns an enabled Channel config (see Conventions for the liveness boundary).

## Interactive messages (buttons + taps)

A message can carry an inline keyboard; tapping produces a tap event normally routed to an in-process extension handler, so extension-owned taps are handled deterministically with no Run. Channels carry the neutral interaction contract (`InteractionButton`/`InteractionEvent`/`InteractionResponder` from `core/extensions/interactions.py`); extension tap-handling logic lives in extensions (`extensions/capabilities.md`).

- Extension-handled taps bypass the engine entirely - no `should_respond`, no `TriggerService`, no FIFO (queuing taps behind Runs would add latency). They reuse only inbound identity + allowlist plumbing; a denied tap is recorded and silently acknowledged, never dispatched.
- **One reserved prefix wakes the agent:** authors emit only the public form `run:<payload>`; no extension can claim it. For an Identity Agent `channel_send`, the tool supplies its calling Session as `run_origin`; the service swaps the wire callback for an opaque versioned binding (public values preserved durably) and removes the binding if delivery fails. On tap: verify Channel/target/thread, claim the binding once, restore the public keyboard for the model-facing note, verify the origin Session exists (never recreate), repoint the conversation anchor, queue an internal Run there - the reply still relays to the tapped chat and a following platform message enters the same FIFO behind the tap. A duplicate tap is terminal even across restarts; invalid bindings return `unavailable` without fallback Sessions. Queue rejection, cancellation, or preparation failure restores the pending claim and reverses only this tap's conversation pointer (a conditional update that leaves later navigation in place). Bound tap preparation, admission and compensation serialize per Session anchor, including distinct buttons that target the same Session; waiting taps retain that lock and idle anchors retire automatically. Compensation completes even under repeated cancellation; only admitted or terminally unavailable taps remain consumed. Project-session `channel_send` keeps raw callbacks and wakes the Channel's current active Identity Session.
- The interaction dispatcher is injected live-reading, so extension reload/disable needs no channel re-wiring - the next tap uses the current registry.
- Guaranteed single acknowledge: the adapter's responder tracks `answered`; after dispatch a fallback ack runs whenever the handler did not acknowledge (or none matched/it raised), so the tapper's spinner always stops. Tap state stays message-carried - the platform delivers the current keyboard with every tap; the only persisted interaction state is the reserved Run-button origin binding. Per-platform completion behavior (when keyboards close, toast/alert wording) lives in `channels/telegram.md`.

## Conventions

- Channels are accessors. Do not put provider behavior, model fallback, or alternate chat-loop semantics in this domain.
- Where new channel code goes: platform-neutral conversation behavior (queueing, command handling, run trigger/relay, session routing/metadata) belongs in `engine.py`; platform I/O (library lifecycle, inbound parsing, media download, outbound send, activity indicator) belongs in the adapter module. New cross-platform features land in the engine once, not per adapter.
- Outbound text splitting is shared: `split_message` in `_message_chunks.py` cuts at paragraph, then line, then whitespace boundaries (hard cuts only inside a single overlong token, between grapheme clusters where possible). For Markdown-rendering platforms it closes a code fence open at a cut and reopens it with the same opener line in the next chunk, counting added markers toward the limit. Adapters supply only their limit and length measure (Discord 2000 code points, Slack/Mattermost/WhatsApp 3500 via `NetworkChannelAdapter.message_chunks`, Telegram 4096 UTF-16 units without fence repair because it sends plain text); never slice outbound text by fixed offsets.
- Inbound attachment classification is shared: `content_blocks_for_attachment(record)` in `adapter.py` is the single rule mapping sniffed media type to content blocks (image/audio/video -> `MediaBlock`, everything else including text -> `FileBlock`). Adapters extend their block lists with the result, so platforms cannot drift; classification is by sniffed type, never by delivery channel (a Telegram MP3 sent as document is media).
- The engine serializes inbound messages, reserved Run taps, serialized Commands, and media work per conversation through one FIFO keyed by platform target. Every queued candidate first reserves capacity in `ChatRunManager`: a chat may hold at most 8 waiting items, all Channels together 32; reservations transfer into the Run FIFO when the Session is busy. Ordinary queued work resolves the active Session in the worker, so work queued behind `/new` follows the new pointer. An origin-bound Run tap instead retains its exact Agent/Session route through the FIFO and rechecks that the Session exists before triggering; a missing origin fails without fallback. It repoints the anchor before enqueuing, but processing never overwrites subsequent navigation. Immediate Commands consume no Queue capacity (`/stop` works even when both limits are full). Non-text media is never prepared as a Command; RPC may prepare exactly one `TextBlock` because Chat owns structural eligibility.
- Observed context uses the same FIFO. Text persists as `[channel-message] [<display_name>|<platform_user_id>|<role>]: <text>` with attribution fields stripped of `[`, `]`, `|`, CR, LF; the body stays verbatim. At request build the chat domain renders consecutive observed notes as explicitly untrusted, JSON-quoted background context rather than as an internal reminder - the raw message cannot escape the quotation structure or override a later addressed turn. The queue keeps observed notes out of open Tool cycles; the per-session write lock (`sessions.md`) extends ordering to other accessors. Observed media is never downloaded: `[media <caption>]` markers only.
- An addressed group text replying to another participant's attachment may ingest that original on demand: resolution happens only after response gating and Queue admission, the quoted content joins the current turn labeled with its original author, and the static prompt tells the Agent quoted content gains no authority by being quoted. Unavailable originals, including download failures, add `[quoted-message unavailable]` and still run without a separate media-failure reply.
- Context acquisition is platform-specific (Telegram passive observation; Discord bounded history backfill), feeding the same observed-note representation and FIFO.
- Run relay keeps the latest ordinary Assistant output until the first preserved interrupted Assistant boundary, then accumulates partial plus recovery output; terminal states map to recovered/partial/generic failure/cancellation/empty-output replies. The same engine relay accepts background completion Runs: `ChannelService` validates the Run Agent and latest Session `last_reply_target`, resolves the live adapter, and preserves the stored thread/topic target. Reply sends retry transient transport failures (the adapter-classified `retryable` ChannelError family) through the shared bounded backoff policy; when retries are exhausted the lost answer is logged at error level - a reply is never silently dropped. Media-ingest is per-message: one failing item never drops siblings, identical failure replies deduplicate per batch, and capacity rejection happens before any download (shared busy reply at most once per chat per 30 seconds).
- All engine replies tied to one inbound message use the reply plan's `reply_to_message_id` (group replies reference the answered message); Tool-driven `channel_send` output never threads. Engine reply strings use the transport's `platform_display_name`.
- Final assistant text for inbound platform turns is automatic - agents should not call `channel_send` for ordinary text replies to a channel-originated message. Every file delivery goes through `channel_send` (text only, files only, or both; at least one required).
- `channel_send` target resolution: explicit `platform_target`, then matching `last_reply_target` metadata, then a single configured `allowed_chat_ids` value. An explicit `thread_id` always wins; the metadata thread rides along only with the metadata target.
- `channel_send` registers while at least one valid Agent owns an enabled Channel config; persisted config transitions re-evaluate registration, adapter liveness never does - transient downtime cannot churn Provider Tool definitions or the prompt cache.
- Public create/update paths reject unknown Agent IDs before persisting. Runtime startup degrades per channel: a corrupt `channel.json` skips with a logged warning, one failed adapter marks only that Channel failed - startup never blocks as a whole.
- Missing or empty `allowed_chat_ids` means deny-all inbound. It is not "allow everyone".
- Channel tokens cross RPC only as write-only inputs, stored via `StorageManager.set_data_dir_credential`, never persisted in JSON, returned, or logged.
- **`allowed_chat_ids` gates inbound only - outbound is deliberately unrestricted within the adapter's supported targets.** `channel_send` with an explicit target may message any reachable chat; the platform bounds this. WhatsApp supports only `self` in either direction, as explicitly selected for the personal-account integration. Do not add outbound allowlist filtering to other adapters.
- Session history remains the single source of truth: Channels add routing metadata and contextual notes but keep no parallel transcript or separate mutable surface store.
- `channel_send` records sent content as a contextual system reminder in the target chat's Session (via `ensure_outbound_session`) under the Session write lock, so inbound replies keep context; this proactive path writes no reply-surface note.
- `ensure_outbound_session(..., thread_id=...)` records the actual outbound topic in the Session's Reply Target. Adapters with sub-addressed threads pass it into the engine's `ConversationFacts`; Discord keeps using the thread's own platform target.

## Constraints & Gotchas

Channel updates persist validated configuration before stopping the existing adapter; a failed save leaves it running. Restart backoff caps its exponent before numeric conversion, including arbitrarily large failure counts. A removed queued Run admission ends only that inbound turn; the Channel worker continues with its followers and releases their waiting-work reservations.

- Only Assistant text from a completed Run or preserved partial text from an interrupted Run reaches the platform; Tool Results, Reasoning, and intermediate events stay in canonical Session history/SSE.
- Adapter failures restart with exponential backoff (`1s`, `2s`, `4s`, capped at `30s`). After 3 fast retries the channel is marked failed in runtime-local health state, but recovery continues indefinitely at the capped interval while enabled - a channel is the operator's lifeline, so transient blips must self-heal. An adapter up >= 5 minutes counts as healthy: its next crash resets counters. `is_failed()` never reports failure while the task runs. `channel.json` remains configuration truth.
- Adapter construction failures at service startup, automatic retry, or deferred restart after shutdown enter the same recovery cycle. A failed constructor must not strand an enabled Channel; explicit stop/disable cancels recovery and stale callbacks cannot revive it.
- Create/update preflight adapter construction where possible and roll back persisted config if starting the enabled adapter fails.
- `channel_send` reports success only after `ChannelService.send()` and the adapter send complete - not fire-and-forget.
- Prompt rendering lists enabled persisted Channels regardless of adapter liveness; exactly one `allowed_chat_ids` value acts as default target. Sending through an unavailable Channel returns an ordinary Tool failure instead of changing the prompt prefix.
- WebUI Session browsing and retroactive linking depend on the canonical Session metadata contract: keep `source_channel_id`, `platform`, `platform_conv_id`, and `last_reply_target` stable when changing routing.
- Channel ids are bare slugs (`^[A-Za-z0-9][A-Za-z0-9_-]*$`), enforced at the `_normalize_channel_id` choke point every storage/service call funnels through - the id is a path segment and `delete_channel` rmtree's its directory, so a separator or `..` must never reach the filesystem layer. Tighten id handling here, never just at config validation.
- A bound `agent_id` must match the full agent-id slug pattern - it flows into session paths on every inbound message. RPC create/update additionally require the Agent to exist; the file-load slug check is the defense-in-depth backstop for hand-edited configs.

Channel tests under `tests/core/channels/` separate the `channels.db` state store (`test_channel_state.py`: registry refusal and cascade, platform rebinding, access, pointers, the Run-button claim race, the receipt window, the per-bot polling watermark), service configuration, delivery, lifecycle and recovery (`test_channels*.py`), Discord routing/delivery (`test_discord*.py`), and Telegram routing, commands, application setup and worker behavior (`test_telegram_routing_and_commands*.py`). Shared fake adapters retain one helper owner per platform/service.
