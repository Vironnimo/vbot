# Channels

Messaging-platform accessors for vBot. Owns channel configuration, adapter lifecycle, outbound delivery, and routing platform inbound messages into normal agent Sessions.

## Overview

`core/channels/` bridges external messaging platforms into the existing agentic loop. A Channel is an accessor-side transport abstraction, not a model provider: it receives inbound platform messages, resolves them into an Agent and Session, triggers normal Runs, and routes assistant replies back through the platform adapter. `ChannelService` owns persisted channel configs under `<data_dir>/channels/`, starts and stops adapter tasks for enabled channels, and exposes outbound message and file support for the `channel_send` tool. Channels reuse normal Sessions, `TriggerService`, `CommandDispatcher`, attachment storage, and prompt/tool registration; they do not own a separate conversation store.

Platform-neutral conversation behavior lives in `core/channels/engine.py` (`ChannelConversationEngine`), shared by all adapters. Each `ChannelAdapter` composes one engine in its `__init__` and delegates to it; the adapter is reduced to platform I/O. The engine owns per-conversation ingress ordering and worker serialization, slash-command dispatch handling, run trigger/relay, and session routing/metadata/derivation; `ChatRunManager` remains the single authority for active and waiting-work capacity. It never imports a platform library: raw platform messages flow through it as opaque values and are converted to canonical content blocks by the adapter-supplied `ConversationTransport`.

## Data Model

- `ChannelConfig`: `id`, `platform` (`telegram` | `discord`), `agent_id`, `dm_scope`, `allowed_chat_ids`, `token_env_var`, `enabled`, `response_mode`, `mention_patterns`, `observe_unaddressed`. Config files live at `<data_dir>/channels/<channel-id>/channel.json`; a legacy `owner_user_ids` list is accepted on load only so storage can migrate it and is never serialized.
- Group response gating: `response_mode` is `"mention"` (default - groups respond only when addressed) or `"all"` (respond to every allowed group message). `mention_patterns` are wake-word regexes (must compile, matched case-insensitively against text and captions). `observe_unaddressed: true` persists otherwise-unaddressed group messages as internal context notes in `"mention"` mode. DMs always respond regardless of `response_mode`. `allowed_chat_ids` is normalized to strings - Telegram chat ids, Discord channel ids - and empty means deny-all inbound.
- `token_env_var` is the adapter-facing credential indirection: managed tokens get a deterministic collision-free key (`VBOT_CHANNEL_TOKEN__` plus the Channel id's uppercase hex); externally managed deployments may supply their own key. The raw token is never part of `ChannelConfig` or `channel.json`.
- Group access state lives separately at `<data_dir>/channels/<id>/access.json`: an optional channel-own `self_user_id`, plus groups keyed by stable adapter-supplied access scope with additional admin ids and durable seen participants. Roles are only `admin`/`member`; the own identity is effectively admin everywhere and cannot be demoted; additional admins are scoped per group. Access mutations are atomic and never rewrite `channel.json`, restart an adapter, rebuild the System Prompt, or alter provider Tool definitions.
- Origin bindings for `channel_send`-authored `run:*` buttons live at `run-button-bindings.json`: versioned, written atomically, consumed entries retained so a duplicate or post-restart tap cannot start a second Run - routing/idempotency state, not conversation state.
- Telegram long-polling dedup state lives at `<data_dir>/channels/<id>/polling.json`: the persisted highest processed update id (versioned, written atomically off-loop). After an adapter restart the adapter skips updates at or below this watermark - Telegram redelivers unconfirmed updates, and without it every restart replayed recent messages as duplicate Runs.
- Config reads pass through the Channels-owned schema (`core.channels` exports the validators consumed by RPC/CLI); schema errors raise `ChannelConfigError` with file/path diagnostics, while runtime-only failures such as missing credentials do not mutate persisted config.
- Channel session metadata lives in the ChatSessionManager-owned sidecar beside each transcript. Channel-owned keys: `source_channel_id`, `platform`, `platform_conv_id`, `last_reply_target {channel_id, platform_target, thread_id?}`, group-only `participants`, and the anchor-only `active_session_id` `/new` pointer (see "Wegweiser" below).
- Adapter/engine facts: adapters classify the conversation (`direct`/`group`), supply display name, message id, addressing facts (`mentioned_bot`, `is_reply_to_bot`), and thread ids, and convert payloads into canonical content blocks; the engine owns every gating and routing *decision*. Discord threads route as their own chats; Telegram forum topics share the parent group Session while delivery follows the topic via `thread_id`.
- Allowlist-rejected chats land in a bounded recency log on the adapter, surfaced through channel status - that log is the discovery workflow: message the bot once, read the id from status, allow it. Recording never changes gating; restarts clear the log.
- `FileData` (`filename`, `media_type`, raw bytes) is the generic outbound file payload handed from tools/service code to adapters.

## Interfaces

Async Channel ingress and outbound delivery never perform Session/config sidecar filesystem I/O directly on the Event Loop - route preparation, metadata, notes, durable Run-button claims, and binding preparation use dedicated bounded pools; Session write locks still protect note ordering against open Tool cycles.

- `ChannelService` is the domain facade: config CRUD, lifecycle (`start`/`stop`/per-channel start/stop/restart), health checks, `send(...)`, and `ensure_outbound_session(...)`. Runtime injects `credential_resolver` so adapters never read `os.environ` themselves (process environment wins over the data-dir `.env` fallback). `restart_channel(channel_id)` preflights and rebuilds only that enabled Channel from current config and live credential, preserving server and sibling uptime; disabled channels retain the new credential for their next enable.
- Outbound `send` validates `buttons` centrally (rows of `InteractionButton`, non-empty data <=64 UTF-8 bytes) before delegating, so a bad payload fails uniformly across adapters. With `run_origin`, the Channel must belong to that Identity Agent and its origin Session must exist; see Interactive messages for the binding contract.
- Only interactive-capable adapters honor `buttons`; Discord rejects them (`ChannelError`). Platform-specific receiving, command dispatch, routing, and send details live in the child maps.
- `denied_chats(channel_id)` exposes the running adapter's rejected-chat log (empty when inactive) to the `channel.status` RPC, CLI status output, and the WebUI panel's per-entry Allow action; access reads/mutations work independently of adapter liveness.
- The engine's ingress surface: `handle_inbound_text` (authorize a Command or gate/enqueue text), `handle_inbound_media` (gate then enqueue one message or buffered album), `observe_inbound_text` (context without a Run, e.g. Discord backfill), `trigger_internal_reply` (note-driven Run whose reply relays like any answer), `trigger_interaction_reply` (reserved Run taps -> `enqueued`/`denied`/`busy`/`already_handled`/`unavailable`), `prepare_inbound_route`/`ensure_channel_session` (routing plus the proactive `channel_send` entry). It owns the per-conversation FIFO, immediate-vs-serialized Command scheduling, generic `CommandOutcome` projection, Run relay, navigation/metadata, and platform-aware unavailability text; Chat owns every Command workflow.
- `should_respond(conversation, gating_texts)` is the public gating decision: direct always responds; groups respond in `"all"` mode, or in `"mention"` mode when mentioned/replying-to-bot or a wake-word regex matches.
- Group slash commands and reserved Run buttons use the immutable ingress role: only `admin` is authorized; unauthorized group commands drop silently with an info log. DM commands stay authorized because the allowlist identifies the sender acting on their own Session.
- Observed (unaddressed, `observe_unaddressed: true`) group messages enqueue in the conversation FIFO: the worker ensures the shared group Session, refreshes metadata/participants, and appends an internal note - no Run, no reply.
- Sender identity is engine-derived and group-only: at first ingress the engine atomically records stable user id/display name and snapshots `admin`/`member`; the immutable value rides the FIFO and `TriggerService`, so queued work and historical attribution never change after a grant/revoke. Group user content renders `[display_name|platform_user_id|role]`; DM turns carry no sender.
- Every Channel Run whose output is relayed supplies `RunKind.CHANNEL` and a Chat-owned `ReplySurface` (platform, display name, Channel id, direct/group). Chat/topic/thread ids stay absent because `last_reply_target` owns delivery; repeated Runs on the same surface do not repeat the surface reminder.
- Group Tool access is dispatch-only and role-aware. A `member` Run receives an immutable admission ceiling of `web_search` and `web_fetch`; an `admin` Run receives none. Both get a live pre-dispatch resolver: non-web Tools require both an admitted `admin` snapshot and a current `admin` role - a later grant cannot upgrade queued/running member work, while a revoke limits an active or waiting admin Run. The Agent's own allowlist intersects independently, provider-visible definitions stay unchanged, denial returns `tool_not_allowed`.
- `ConversationTransport` is the typing.Protocol keeping the engine platform-free: display name, text send (reply/thread targeting), activity indicator, media-block building, quoted-message resolution, caption extraction.
- Session-id derivation is a stable contract (WebUI browsing, `session.link_channel`): `group` -> `ch-<channel-id>-<chat-id>`; `direct` follows `dm_scope` - `per_conversation` (default) -> `ch-<channel-id>-<chat-id>`, `main` -> `ch-<channel-id>-main`, `per_peer` -> `ch-<channel-id>-u<user-id>`, `per_account_channel_peer` -> `ch-<channel-id>-<chat-id>-u<user-id>`.
- **"Wegweiser" routing (anchor vs active session).** The derived id is a stable conversation anchor; routing resolves the anchor sidecar's `active_session_id` pointer first and falls back to the anchor itself. All inbound text/media, observed messages, and proactive `channel_send` follow the pointer; without one the anchor *is* the session ("no pointer" is the default - no migration branch). A claimed origin-bound Run tap repoints the anchor at the invoking Identity Agent Session before entering the FIFO, so following platform messages continue there; `/new` repoints it to a fresh Channel Session and detaches the platform again. The agent-wide `current_session_id` is deliberately not consulted for channel routing.
- **Slash Commands** execute the shared live Chat-owned set through `prepare`/`execute` - neither transport has a command-name switch. `/new` returns `continue_in_session`; the engine writes Channel metadata and repoints the anchor. `/handoff` and Extension follow-up Runs relay generically without changing `ChannelConfig.agent_id` or the source anchor. Every `/agent` form is refused before execution with `The /agent command is not available through <Platform>.` - permanent wording, never implying future implementation.
- **Platform chat-id migration** (Telegram group->supergroup upgrades): the new chat id's anchor gets a one-hop `active_session_id` pointer at the old active session, the sidecar moves to the new id, a session note informs the model, and the allowlist/access-group swap persists without restarting the adapter; idempotent when the old id is gone.
- Access mutations return the complete saved access projection and publish `resource_changed(kind: "channels")`, deliberately without calling `runtime.reload_channel_tool()`; config/lifecycle mutations keep their existing reload behavior.
- `ChannelConfig.agent_id` is a live reference: coordinated `agent.rename` retargets matching Channels through the service with normal validation and per-channel rollback. Retroactive linking (`session.link_channel`) writes the same sidecar keys and appends no reply-surface note. `channel_send` registers only while at least one valid Agent owns an enabled Channel config (see Conventions for the liveness boundary).

## Interactive messages (buttons + taps)

A message can carry an inline keyboard; tapping produces a tap event normally routed to an in-process extension handler, so extension-owned taps are handled deterministically with no Run. Channels carry the neutral interaction contract (`InteractionButton`/`InteractionEvent`/`InteractionResponder` from `core/extensions/interactions.py`); extension tap-handling logic lives in extensions (`extensions/capabilities.md`).

- Extension-handled taps bypass the engine entirely - no `should_respond`, no `TriggerService`, no FIFO (queuing taps behind Runs would add latency). They reuse only inbound identity + allowlist plumbing; a denied tap is recorded and silently acknowledged, never dispatched.
- **One reserved prefix wakes the agent:** authors emit only the public form `run:<payload>`; no extension can claim it. For an Identity Agent `channel_send`, the tool supplies its calling Session as `run_origin`; the service swaps the wire callback for an opaque versioned binding (public values preserved durably) and removes the binding if delivery fails. On tap: verify Channel/target/thread, claim the binding once, restore the public keyboard for the model-facing note, verify the origin Session exists (never recreate), repoint the conversation anchor, queue an internal Run there - the reply still relays to the tapped chat and a following platform message enters the same FIFO behind the tap. A duplicate tap is terminal even across restarts; invalid bindings return `unavailable` without fallback Sessions. Queue rejection restores prior anchor metadata and the pending claim before the busy reply. Project-session `channel_send` keeps raw callbacks and wakes the Channel's current active Identity Session.
- The interaction dispatcher is injected live-reading, so extension reload/disable needs no channel re-wiring - the next tap uses the current registry.
- Guaranteed single acknowledge: the adapter's responder tracks `answered`; after dispatch a fallback ack runs whenever the handler did not acknowledge (or none matched/it raised), so the tapper's spinner always stops. Tap state stays message-carried - the platform delivers the current keyboard with every tap; the only persisted interaction state is the reserved Run-button origin binding. Per-platform completion behavior (when keyboards close, toast/alert wording) lives in `channels/telegram.md`.

## Conventions

- Channels are accessors. Do not put provider behavior, model fallback, or alternate chat-loop semantics in this domain.
- Where new channel code goes: platform-neutral conversation behavior (queueing, command handling, run trigger/relay, session routing/metadata) belongs in `engine.py`; platform I/O (library lifecycle, inbound parsing, media download, outbound send, activity indicator) belongs in the adapter module. New cross-platform features land in the engine once, not per adapter.
- Inbound attachment classification is shared: `content_blocks_for_attachment(record)` in `adapter.py` is the single rule mapping sniffed media type to content blocks (image/audio/video -> `MediaBlock`, everything else including text -> `FileBlock`). Adapters extend their block lists with the result, so platforms cannot drift; classification is by sniffed type, never by delivery channel (a Telegram MP3 sent as document is media).
- The engine serializes inbound messages, reserved Run taps, serialized Commands, and media work per conversation through one FIFO keyed by platform target. Every queued candidate first reserves capacity in `ChatRunManager`: a chat may hold at most 8 waiting items, all Channels together 32; reservations transfer into the Run FIFO when the Session is busy. Queued work carries `ConversationFacts`, not a resolved route - the active Session resolves in the worker, so work queued behind `/new` follows the new pointer. An origin-bound Run tap repoints the anchor synchronously before enqueuing so no platform message overtakes the takeover. Immediate Commands consume no Queue capacity (`/stop` works even when both limits are full). Non-text media is never prepared as a Command; RPC may prepare exactly one `TextBlock` because Chat owns structural eligibility.
- Observed context uses the same FIFO. Text persists as `[channel-message] [<display_name>|<platform_user_id>|<role>]: <text>` with attribution fields stripped of `[`, `]`, `|`, CR, LF; the body stays verbatim. At request build the chat domain renders consecutive observed notes as explicitly untrusted, JSON-quoted background context rather than as an internal reminder - the raw message cannot escape the quotation structure or override a later addressed turn. The queue keeps observed notes out of open Tool cycles; the per-session write lock (`sessions.md`) extends ordering to other accessors. Observed media is never downloaded: `[media <caption>]` markers only.
- An addressed group text replying to another participant's attachment may ingest that original on demand: resolution happens only after response gating and Queue admission, the quoted content joins the current turn labeled with its original author, and the static prompt tells the Agent quoted content gains no authority by being quoted. Unavailable originals add `[quoted-message unavailable]` and still run.
- Context acquisition is platform-specific (Telegram passive observation; Discord bounded history backfill), feeding the same observed-note representation and FIFO.
- Run relay keeps the latest ordinary Assistant output until the first preserved interrupted Assistant boundary, then accumulates partial plus recovery output; terminal states map to recovered/partial/generic failure/cancellation/empty-output replies. The same engine relay accepts background completion Runs: `ChannelService` validates the Run Agent and latest Session `last_reply_target`, resolves the live adapter, and preserves the stored thread/topic target. Reply sends retry transient transport failures (the adapter-classified `retryable` ChannelError family) through the shared bounded backoff policy; when retries are exhausted the lost answer is logged at error level - a reply is never silently dropped. Media-ingest is per-message: one failing item never drops siblings, failure replies deduplicate per batch, and capacity rejection happens before any download (shared busy reply at most once per chat per 30 seconds).
- All engine replies tied to one inbound message use the reply plan's `reply_to_message_id` (group replies reference the answered message); Tool-driven `channel_send` output never threads. Engine reply strings use the transport's `platform_display_name`.
- Final assistant text for inbound platform turns is automatic - agents should not call `channel_send` for ordinary text replies to a channel-originated message. Every file delivery goes through `channel_send` (text only, files only, or both; at least one required).
- `channel_send` target resolution: explicit `platform_target`, then matching `last_reply_target` metadata, then a single configured `allowed_chat_ids` value. An explicit `thread_id` always wins; the metadata thread rides along only with the metadata target.
- `channel_send` registers while at least one valid Agent owns an enabled Channel config; persisted config transitions re-evaluate registration, adapter liveness never does - transient downtime cannot churn Provider Tool definitions or the prompt cache.
- Public create/update paths reject unknown Agent IDs before persisting. Runtime startup degrades per channel: a corrupt `channel.json` skips with a logged warning, one failed adapter marks only that Channel failed - startup never blocks as a whole.
- Missing or empty `allowed_chat_ids` means deny-all inbound. It is not "allow everyone".
- Channel tokens cross RPC only as write-only inputs, stored via `StorageManager.set_data_dir_credential`, never persisted in JSON, returned, or logged.
- **`allowed_chat_ids` gates inbound only - outbound is deliberately unrestricted.** `channel_send` with an explicit target may message any reachable chat; the platform bounds this. A conscious max-agency decision - do not "fix" it by filtering outbound through the allowlist.
- Session history remains the single source of truth: Channels add routing metadata and contextual notes but keep no parallel transcript or mutable surface sidecar.
- `channel_send` records sent content as a contextual system reminder in the target chat's Session (via `ensure_outbound_session`) under the Session write lock, so inbound replies keep context; this proactive path writes no reply-surface note.

## Constraints & Gotchas

- Only Assistant text from a completed Run or preserved partial text from an interrupted Run reaches the platform; Tool results, Reasoning, and intermediate events stay in JSONL/SSE.
- Adapter failures restart with exponential backoff (`1s`, `2s`, `4s`, capped at `30s`). After 3 fast retries the channel is marked failed in runtime-local health state, but recovery continues indefinitely at the capped interval while enabled - a channel is the operator's lifeline, so transient blips must self-heal. An adapter up >= 5 minutes counts as healthy: its next crash resets counters. `is_failed()` never reports failure while the task runs. `channel.json` remains configuration truth.
- Create/update preflight adapter construction where possible and roll back persisted config if starting the enabled adapter fails.
- `channel_send` reports success only after `ChannelService.send()` and the adapter send complete - not fire-and-forget.
- Prompt rendering lists enabled persisted Channels regardless of adapter liveness; exactly one `allowed_chat_ids` value acts as default target. Sending through an unavailable Channel returns an ordinary Tool failure instead of changing the prompt prefix.
- WebUI session browsing and retroactive linking depend on the sidecar contract: keep `source_channel_id`, `platform`, `platform_conv_id`, and `last_reply_target` stable when changing routing.
- Channel ids are bare slugs (`^[A-Za-z0-9][A-Za-z0-9_-]*$`), enforced at the `_normalize_channel_id` choke point every storage/service call funnels through - the id is a path segment and `delete_channel` rmtree's its directory, so a separator or `..` must never reach the filesystem layer. Tighten id handling here, never just at config validation.
- A bound `agent_id` must match the full agent-id slug pattern - it flows into session paths on every inbound message. RPC create/update additionally require the Agent to exist; the file-load slug check is the defense-in-depth backstop for hand-edited configs.
