# Chat Command

Supplementary to `cli.md`. Covers `vbot chat`, which sends one message to an Agent Session and follows the Run it starts: Session choice, Run following over SSE, output and exit codes.

## Command

- `chat [<prompt>] [--agent <agent|agent@project>] [-c | --session <id> | --project <project-id> | --workspace] [--model] [--thinking-effort] [--temperature] [--top-p] [--json]` (`cli/chat_management.py`, translated by `_dispatch_agents.dispatch_chat_command`) sends one message and follows the Run it starts to its end. The message is the positional, or piped UTF-8 stdin when it is `-` or omitted; an omitted message with a terminal (or absent) stdin is a parse-time usage error (exit 2, no RPC). `--agent` defaults to `main`.
- Session choice: no selector -> a new Session, sent as `chat.stream` `new_session {agent_overrides?, working_project_id?}` so the server creates it only for a message it accepts; `--project <project-id>` sends that `working_project_id` and `--workspace` sends `null`, so the new Session works there instead of in the Agent's default Project (`sessions.md` -> Terms -> Working Project; a Team address refuses either) (`server/chat-rpcs.md` -> Chat submission target); `-c` -> `session.list` with `limit: 1` and every `include_*` filter false, i.e. the most recently active user conversation (Sub-Agent, reflection, Cron and Channel Sessions are skipped), and a new Session when there is none; `--session` is used as given. `agent_overrides` carries only the given override flags. On an existing Session, given flags are saved first with `session.set_agent_overrides`; without flags nothing is sent, because Session Agent overrides persist for the Session's later Runs (`projects/resolution.md`; RPC shapes in `server/chat-rpcs.md` and `server/session-agent-rpcs.md`). `chat.stream` makes the chosen or created Session the Identity Agent's current one; the Session id of a new one comes from the result's `session_id`.

## Run following

- `chat.stream {agent_id, session_id | new_session, content}`. A `queued` result exits 1 with the queue item id and does not wait; a `command_handled` result prints its `reply` on stdout and exits 0 with no Run (a command for a new Session may run without creating it: the outcome line then says `handled without a Session` and `session_id` is null). Otherwise the result's `events` are applied first, then `stream_run_events` follows `sse_url` from the last applied `sequence`; each event applies once by sequence. An early close reconnects with that `after_sequence`; three reconnects in a row without a new event, or HTTP 404, end in a "lost the event stream" failure that says the Run may still be running. SSE reading runs on a daemon thread while the command thread polls a queue, so Ctrl-C lands during quiet Tool calls on Windows; Ctrl-C sends `chat.cancel {run_id, reason: "user"}`, prints a stderr note and exits 130.
- `stream_run_events` (`cli/rpc_client.py`) follows one Run's SSE stream (`GET <sse_url>?after_sequence=<n>`, the path a `chat.stream` result names), skips `heartbeat` frames and comments, uses a 60 s read timeout against the server's 10 s heartbeat, and raises `RunEventStreamError` (with the HTTP status when the server answered) on open, transport or malformed-JSON failure. It builds its requests from `cli/server_client.py`, so they carry the target's credential.

## Output

- stdout carries only the answer (the last `assistant_output` text; when stdout is a terminal and neither `--json` nor plain output is selected, every Model step's `assistant_output_delta` text streams instead and is never printed again) or, with `--json`, one object: `agent_id`, `session_id`, `run_id`, `status`, `model`, `message`, `tool_calls` (`id`, `name`, `arguments`, `is_error`, `error`, `result_preview`), `usage` (summed `model_step_usage`), `duration_ms`, `error`, `agent_overrides` (stored overrides when this call saved some, else null), `queue_item`, `command`. Progress lines (Tool call name plus the Tool display summary or visible arguments, Tool errors, Provider retries, Model fallback, Compaction start) go to stderr when stderr is a terminal or `--output human`.
- `chat` is exempt from the elapsed-time tracker and the generic completion line, because its streamed answer shares the terminal: `print_chat_command_result` prints its outcome on stderr instead (a success trailer with Session, Agent, Model, saved overrides and a `Continue:` command, omitted in plain output; failures in every mode).
- Exit codes: 0 completed Run or handled command; 1 failed, cancelled or interrupted Run, queued message, lost stream, or RPC failure; 2 usage error; 130 Ctrl-C. Tests: `tests/cli/test_chat_command.py`.
