# Chat Command

Supplementary to `cli.md`. Covers `vbot chat`, which sends one message to an Agent Session and follows the Run it starts: Session choice, attachments, Run following over SSE, output and exit codes.

## Command

- `chat [<prompt> | --file <path>] [--agent <agent|agent@project>] [-c | --session <id> | --project <project-id> | --workspace] [--ephemeral] [--attach <path>]... [--model] [--thinking-effort] [--temperature] [--top-p] [--json]` (`cli/chat_management.py`, translated by `_dispatch_agents.dispatch_chat_command`) sends one message and follows the Run it starts to its end. The message is the positional, a local `--file` (encodings: `cli/system-commands.md` -> Content files), or piped UTF-8 stdin when the positional is `-` or both text sources are omitted; an omitted message with a terminal (or absent) stdin is a parse-time usage error (exit 2, no RPC), except: with only `--agent`, `-c`, `--session` or `--project` and a terminal stdout too, `cli/parser._check_chat_arguments` sets `open_tui` and the command opens `vbot tui` on that Agent and Session instead (`_dispatch_tui.open_tui_for_chat`; `-c` resolves through `chat_management.latest_conversation`); with `--attach`, the files alone are the message. `--agent` defaults to `main`. Hidden aliases: `--temporary`/`--temp` for `--ephemeral`, `--resume` for `--session`.
- Attachments: each `--attach` file is uploaded first with `rpc_client.upload_attachment` (multipart `POST /api/upload`, the WebUI composer's route; `server/_upload_routes.py`), so an unreadable file or a refused upload sends nothing. The message becomes content blocks: a text block when there is text, then one block per file, `media` for `image/`, `audio/` and `video/` types and `file` otherwise, as the WebUI composer builds them.
- Session choice: no selector -> a new Session, sent as `chat.stream` `new_session {agent_overrides?, working_project_id?}` so the server creates it only for a message it accepts; `--ephemeral` adds `ephemeral: true` (GLOSSARY -> Ephemeral Session), and with `-c` it is a parse-time usage error; `--project <project-id>` sends that `working_project_id` and `--workspace` sends `null`, so the new Session works there instead of in the Agent's default Project (GLOSSARY -> Working Project; a Team address refuses either) (`server/chat-rpcs.md` -> Chat submission target); `-c` -> `session.list` with `limit: 1` and every `include_*` filter false, i.e. the most recently active user conversation (Sub-Agent, reflection, Cron and Channel Sessions are skipped), and a new Session when there is none; `--session` is used as given. `agent_overrides` carries only the given override flags. On an existing Session, given flags are saved first with `session.set_agent_overrides`; without flags nothing is sent, because Session Agent overrides persist for the Session's later Runs (`projects/resolution.md`; RPC shapes in `server/chat-rpcs.md` and `server/session-agent-rpcs.md`). `chat.stream` makes the chosen or created Session the Identity Agent's current one unless it is an Ephemeral Session; the Session id of a new one comes from the result's `session_id`.

## Run following

- `chat.stream {agent_id, session_id | new_session, content}`. A `queued` result exits 1 with the queue item id and does not wait; a `command_handled` result prints its `reply` on stdout and exits 0 with no Run (a command for a new Session may run without creating it: the outcome line then says `handled without a Session` and `session_id` is null). Otherwise the result's `events` are applied first, then `stream_run_events` follows `sse_url` from the last applied `sequence`; each event applies once by sequence. An early close reconnects with that `after_sequence`; three reconnects in a row without a new event, or HTTP 404, end in a "lost the event stream" failure that says the Run may still be running. SSE reading runs on a daemon thread while the command thread polls a queue, so Ctrl-C lands during quiet Tool calls on Windows; Ctrl-C sends `chat.cancel {run_id, reason: "user"}`, prints a stderr note and exits 130.
- Ordinary messages carry one client-minted `input_id`; an unknown submission outcome retries that exact prepared request once. Slash-prefixed input retains Command execution and is never automatically retried. A duplicate historical receipt confirms acceptance without inventing a live Run status: the CLI reads current history and Queue and, with a Run id, its exact `chat.run_result` excerpt. It reports `status: accepted`, `input_state` and the same `input_id`; a truncated excerpt is disclosed, and a reconciliation-read failure keeps acceptance confirmed but exits 1. A separate CLI invocation is a new input, not a retry of the previous invocation.
- `stream_run_events` (`cli/rpc_client.py`) follows one Run's SSE stream (`GET <sse_url>?after_sequence=<n>`, the path a `chat.stream` result names), skips `heartbeat` frames and comments, uses a 60 s read timeout against the server's 10 s heartbeat, and raises `RunEventStreamError` (with the HTTP status when the server answered) on open, transport, malformed-JSON or non-object event failure. It builds its requests from `cli/server_client.py`, so they carry the target's credential.

## Output

- stdout carries only the answer (the last `assistant_output` text; when stdout is a terminal and neither `--json` nor plain output is selected, every Model step's `assistant_output_delta` text streams instead and is never printed again) or, with `--json`, one object: `agent_id`, `session_id`, `ephemeral` (the Run response's flag; null for a queued message or a handled command), `attachments` (the upload records), `run_id`, `status`, `model`, `message`, `tool_calls` (`id`, `name`, `arguments`, `is_error`, `error`, `result_preview`), `usage` (summed `model_step_usage`), `duration_ms`, `error`, `agent_overrides` (stored overrides when this call saved some, else null), `queue_item`, `command`. Progress lines (Tool call name plus the Tool display summary or visible arguments, Tool errors, Provider retries, Model fallback, Compaction start) go to stderr when stderr is a terminal or `--output human`.
- `chat` is exempt from the elapsed-time tracker and the generic completion line, because its streamed answer shares the terminal: `print_chat_command_result` prints its outcome on stderr instead (a success trailer with Session, Agent, Model, saved overrides and a `Continue:` command; for an Ephemeral Session the outcome names it so and adds its 24-hour lifetime, and `--ephemeral` on an existing normal Session adds a `Note:` that it applied only to a new Session; omitted in plain output; failures in every mode).
- Both `Continue:` (including handled commands) and the lost-stream `/status` command preserve the resolved server target and local data directory through `_recovery.target_options` and its shell formatter. Copying the command therefore keeps the same server and local credential source even when the original target came from environment or installation defaults.
- Exit codes: 0 completed Run or handled command; 1 failed, cancelled or interrupted Run, queued message, lost stream, or RPC failure; 2 usage error; 130 Ctrl-C. Tests: `tests/cli/test_chat_command.py`.
- A historical acceptance whose reconciliation reads succeeded also exits 0; this confirms input admission, not successful completion of its Run. Every JSON report includes its `input_id` when one is available.
- Silent answers (`runs/events.md`) produce no answer text, including in JSON reports. Terminal streaming holds marker prefixes until they differ from `[SILENT]`; a later silent ending also clears any earlier step from the final report.
- Historical receipts use the returned canonical `agent_id` for reconciliation. `session_available: false` confirms prior acceptance without reading or recreating the retired Session; this accepted outcome also exits 0.
