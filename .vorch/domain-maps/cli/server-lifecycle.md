# Server Lifecycle Commands

Supplementary to `cli.md`. Covers `vbot server start|stop|restart|status` of a server without an installation, health classification, process termination, lifecycle logging, and the local `home` and `desktop` commands. The packaged installation's lifecycle path is `cli/application.md`.

## Commands

- `server_management.py` retains process lifecycle of a server without an installation and the scheduled restart helper, and re-exports the public target primitives of `cli/_server_target.py` (target resolution, result records, HTTP health classification, local listener matching).
- `server start [--host] [--port] [--data-dir]` resolves the target instance and starts `python -m server.main` in the background when no vBot server is already reachable there and no local listener holds the target without answering (Health outcomes below); it succeeds only after the exact vBot `/health` contract responds. On Windows the child uses a new process group and `CREATE_NO_WINDOW`, with Job-aware detachment through `core.utils.processes` (see `tools/os-processes.md`). Ordinary terminal exit does not stop the server. A caller inside another application's Windows Job that forbids breakaway (a coding agent's shell) starts the server outside it through WMI (`start_outside_foreign_job`); a packaged installation with a running tray hands the command to that tray instead (`cli/application.md` -> Update operation, server requests). When WMI fails too, the server starts inside the Job and the result carries an `attention` note (`CommandResult.attention`, printed as a `warning:` line with a warning status) naming the application and pid, saying the server ends when that application closes, the WMI error, and the remedy (dev: start it from a terminal outside that application; packaged: start vBot from the Start menu and use Restart server in its tray menu). Never refused for a missing tray; other platforms and unconfined callers are unchanged. The child gets only `--host/--port/--data-dir`, so it serves the Access Mode its data directory records (`access/server.json`, `access.md` -> Interfaces). The start therefore targets the recorded bind host (`_recorded_target`): silently for the default host, otherwise with an `attention` note that the server binds the recorded address and how to change it (`python -m server.main --access <mode> --host <address> ...`). An unreadable record fails the start with the server's reason.
- `server stop [--host] [--port] [--data-dir]` requires a local target and refuses non-vBot listeners. The target owner verifies resolved addresses against loopback and assigned local interfaces before local listener lookup or control-record fallback; remote or mixed local/remote DNS answers cannot authorize local process control. Every vBot answers `/health`, so a confirmed vBot listener is stopped only when the target data directory's current control record identifies its exact process (PID plus process creation time); otherwise stop fails with `port occupied by a vBot server of another data directory` and leaves it running, so a wrong `--data-dir` or a missing `--port` never stops another installation. Stop posts the per-process secret to the private shutdown route and waits for FastAPI/Runtime teardown; a rejected or failed request falls back to platform termination. The request names its initiator for the server's stop line (`stop_server(initiator=...)`, `cli` by default; the Windows application passes `tray_stop`, `tray_restart`, `tray_quit` or `update`, the scheduled restart helper `scheduled_restart`; `server.md`). If the listener has already closed while teardown is still running, the PID plus process creation time in the control record identifies that exact process so stop waits for completion instead of reporting `not running`; a bounded kill fallback applies if it remains stuck.
- `server restart [--host] [--port] [--data-dir]` stops the resolved target if present and re-resolves host/port/data-dir before starting - if stop fails, restart does not start. In a packaged installation all server lifecycle commands go through `cli/application/processes.py` (`start_or_restart` for these two), which delegates to the Linux systemd user unit when the installation owns one (`cli/application.md` -> Autostart and server supervision). The development path passes the restart's start `attention` through. A restart, also one the server schedules itself, keeps the recorded Access Mode.
- `server status [--host] [--port] [--data-dir]` reports running/not running, resolved URL, WebUI availability, data dir, and log path. Status verifies a vBot listener against the target data directory's live control record before reporting it as running. A server of another data directory prints `port occupied by a vBot server of another data directory`, reports the target as not running and omits its log path. Either this or a non-vBot listener prints a conflict note but still exits 0 for `status`; the same conflict fails `start`, `stop`, and `restart`. A listener that never answers `/health` fails `status` with `port occupied by unresponsive process` (`status` cannot tell whether vBot runs); `stop` and `restart` end it only when the control record identifies its process. `start` spawns only for a target `classify_server` finds `absent` (Health outcomes): a live recorded server that does not answer (busy, starting, stopping) fails it with `the server process is running but does not answer its health check`, an unidentified silent listener with `port occupied by unresponsive process`, and another data directory's vBot with `port occupied by a vBot server of another data directory`.
- Every lifecycle invocation flushes an action-and-target sentence before work and ends with a complete outcome sentence; no-op states, conflicts, forced termination, and failures are stated explicitly. Lifecycle and update results keep explicit outcome text in every output mode.
- If a vBot server already runs at the target, `start` reports `already running` and spawns nothing. A reachable non-vBot occupant conflicts: `start`/`stop`/`restart` fail and must not terminate that process, while `status` reports it and exits 0.
- Built WebUI assets are optional: missing `webui/dist` leaves `/health` healthy while `/` may be unavailable; lifecycle output reports `webui: unavailable` instead of treating startup as failed.

## Health outcomes and process control

- Process termination is allowed only for a verified local target whose current control record's PID plus process creation time identifies the exact server process: the listener `/health` confirms as vBot, or the server process after its listener has closed. Local listener lookup matches the resolved host/address and port, not port alone; wildcard listeners cover locally assigned addresses of their family, never arbitrary remote addresses (`test_server_management_target.py`, `test_server_management.py`).
- Stop is best effort: terminate first, kill after the bounded timeout, report `forced: true` when the kill fallback ran. If the bounded post-kill wait also times out, `stop_server` returns a failed `CommandResult` rather than raising or claiming success. On Windows this can still interrupt in-flight Runs abruptly. A stop that bypasses the server's own shutdown (terminate after a failed request, kill after the timeout) writes a WARN line to the target's daily log, ERROR when the kill also times out; a missing data directory is never created for it. `log_bypassed_stop` writes these lines; the Windows tray reuses it for a server end it observed (`cli/application/tray.md`).
- Live reachability and `/health` classification are the authority for listeners. The target-specific control record is the only post-listener lifecycle identity; PID alone is never trusted because the OS can reuse it.
- **Probes.** `start`, `stop` and `status` decide through `probe_health_patiently` (`_server_target.py`): answered as vBot, answered as non-vBot, absent, or `unresponsive`. The 0.5 s quick probe that polling loops and the remaining consumers (`data-store status` and `unregister`, which only choose between the RPC and a local read or a claim-guarded local change) use cannot separate absent from busy: a stalled Event Loop (heavy Run load, large replay) misses it, and on Windows a refused connection to a closed port also surfaces as a connect timeout, so a timeout alone never proves a listener. Every quick probe contacts the target, because the host socket table can omit a listener in another network namespace. Local probes connect within `LOCAL_CONNECT_TIMEOUT_SECONDS` (0.2 s), bounding Windows' delay on a refused connection while a busy server's handshake completes in the kernel. A timeout with a local listener on the target (`has_local_listener`, one system-wide socket-table read) earns one `PATIENT_PROBE_TIMEOUT_SECONDS` (5 s) probe; a listener that still times out is `unresponsive`. Without a local listener, or for a remote target, the quick result stands.
- **Start and stop decisions.** `start` spawns nothing for a target that answers or is `unresponsive` (a duplicate child would fail to claim the target and the next probe would report `started` for the old server); it spawns only when `classify_server` finds the target `absent`. `stop` acts only on the control record's exact process, asks it for cooperative shutdown first (request timeout equals the patient budget; a refused or timed-out request falls back to terminate, then kill), and kills a process that has not exited `DEFAULT_SHUTDOWN_TIMEOUT_SECONDS` (30 s) after the request, comfortably beyond the Runtime's own bounded teardown (`runtime.md` -> Shutdown), so a busy server finishes cancelling its Runs instead of being killed mid-teardown and, with no such record, fails without touching the listener. `classify_server` (`server_management.py`) is the lifecycle decision on top of the patient probe: identity and liveness from the control record's exact process, health from the probe; its four states are in `cli.md` -> Health outcomes, where `foreign` also covers a recorded process the caller's `is_expected` rejects. `start` and `data-store snapshot restore` decide through it; the packaged application narrows it to the exact installed version and startup mode for its start, update, uninstall and data reset (`processes.server_state`, `cli/application.md` -> Update operation). Regression coverage: `tests/cli/test_server_management.py`, `test_server_management_target.py`.
- Startup waits for health readiness (`DEFAULT_STARTUP_TIMEOUT_SECONDS`, 60 s like the other start paths) and cleans up the just-spawned child on readiness timeout, early child exit, or a non-vBot responder appearing during startup; the timeout ERROR log names the child pid and the elapsed seconds. A successful start writes one INFO outcome line with the child pid, URL and readiness seconds; the spawn steps and `already running` are DEBUG.
- Lifecycle logs belong under `<data_dir>/logs/` through the managed `LogManager`; background server startup must not bypass that logger or rely on raw child streams. Before that logger writes into a missing data root, `_create_cli_log_manager` initializes the root through `initialize_data_directory`, so a fresh `--data-dir` carries the data-store bootstrap marker (`data-store.json` listing no databases) instead of becoming an unauthorized existing root; the CLI never initializes an existing root.

## Local accessor actions

- `home [--data-dir]` is local and read-only (no server needed) and prints exactly two deterministic fields: `vbot_root` is the checkout/install root containing the running vBot code, `data_dir` follows the explicit argument -> `VBOT_DATA_DIR` -> applicable `.vbot-worktree` -> `~/.vbot` chain (`Config` owns selection). Neither field is the caller's arbitrary shell cwd or a Project cwd.
- `desktop [--host] [--port]` opens the pywebview Desktop window pointed at a local or remote server. It is neither an RPC command nor server lifecycle: it branches before the shared resolver, lazily imports `desktop.main` (the default CLI path needs no pywebview), forwards only the target flags actually supplied - bare `vbot desktop` reaches the launcher's last-used auto-connect path instead of a silent localhost target - plus `--server-data-dir` with the data directory every `vbot` command uses by default (`Config().data_dir`), so the Desktop signs in to that server on this computer with its local access token as the CLI does; it takes no `--data-dir` (Desktop has its own per-user config dir; see `desktop.md`), and blocks until the window closes, then prints `desktop window closed`.
- The installed Windows Desktop shortcut runs the stable GUI bootstrap `vBot.GUI.exe desktop` without a console (`cli/application.md`); the CLI `desktop` remains the console launch surface.
- `home` only reports locally resolved paths; the `desktop` launch is a local GUI action. Neither uses RPC or constructs a `ServerInstance`.
