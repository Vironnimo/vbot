# Server Targets, Credentials and Devices

Supplementary to `cli.md`. Covers port resolution safeguards, how the CLI reads a `--url` target, what `cli/server_client.py` attaches to every connection, the Device sign-in store, and `vbot devices` including pairing and logout. Which credential the server admits from where is owned by `access.md`.

## Targets and ports

- Port resolution (order: `cli.md` -> Conventions) uses the shared resolver in `core/utils/config.py`. `DEFAULT_PORT` is the one Python home of the default port, which also sets the development ports (`scripts/README-worktree.md`); the Desktop, the WebUI and the installers cannot import it and repeat it, and `tests/core/utils/test_config.py` keeps those copies equal. A malformed Settings document or an invalid port refuses target inference before any request, so a damaged development configuration cannot redirect commands to the installed default instance. An explicit port still selects its intended target, and invalid unrelated Settings keys leave a valid port usable. Ambient `PORT`/`SERVER_PORT` process variables are ignored - those names matter only as settings keys inside `settings.json`.
- `parse_server_url` (`_server_target.py`) reads the address: `http`/`https` only, no user info, host required, IDN to punycode, the default port dropped from the origin; a missing scheme becomes `https` (`http` for a loopback name) and a path, query or fragment is dropped, each with a `Note:` line on stderr. `ServerInstance.url` is then the origin, and `is_url_target` (its scheme is not `http` or its port is not the instance port) tells a target only `--url` can name: recovery commands repeat `--url` for it, and an `auth_required` from a non-loopback target puts `vbot devices pair <origin>` first.
- `--url` together with `--host` or `--port` is a usage error. Server lifecycle and autostart take no `--url` (`_add_command_parser(..., remote=False)`).
- `ServerInstance.url` is the single connectable HTTP base URL; wildcard binds map to the matching loopback address and IPv6 literals are bracketed before probes or RPC paths are appended (`_probe_url` uses `build_server_base_url` except for a `--url` target).
- An Agent's shell runs `vbot` on the server's computer with `VBOT_DATA_DIR`/`VBOT_SERVER_PORT` and so signs in with the local access token; it must never follow a user-level `VBOT_SERVER_URL` to another server, hence the Run check in `selected_server_url`. Any shell outside a Run still follows it.

## Credentials (`cli/server_client.py`)

- `cli/server_client.py` is the one owner of what every connection to a server target needs; the RPC client, the TUI transport, the tray monitor and the facade's login ticket, and `devices pair|logout` build on it, and nothing else attaches credentials. `http_options(instance)` gives `trust_env=False`, `verify=ssl_context_for(url)` and `ServerAuth`; `websocket_target(instance, path)` the `ws(s)://` URL with the credential header, `ssl` for `wss` and no proxy; `access_refusal(instance, code)` the explanation of `auth_required`/`access_denied`/`devices_unavailable` for that target (CLI recovery, TUI); `WEBSOCKET_REFUSALS` maps the close codes 4401/4403/4503 to those codes.
- Credential rules: a loopback target (`is_loopback_target`) sends the local access token of its port from the target's `--data-dir` (`Authorization: Bearer`) only where the token file admits it (`LocalAccess.admits`; which addresses qualify: `access.md` -> Invariants; `build_server_base_url` turns `0.0.0.0`/`::` into `127.0.0.1`/`::1`), looked up at the first request and read again after a 401, repeating the request once when the token changed (a restarted server); an `https://` target sends the stored Device sign-in of the exact origin, likewise looked up again after a 401; any other target (plain `http://` elsewhere, a host name, a tunnel) and a request to another origin carry neither. For a loopback target the token file does not admit, `access_refusal` names the `--url` that gets the token.
- `credential_for`, `http_options` and `websocket_target` take `device_sign_in`, another source of Device tokens by origin (`cli_sign_in` is the default); the tray of a Desktop Client passes the Desktop's (`cli/application/tray.md`). A 503 `devices_unavailable` (WebSocket 4503) changes no credential; nothing in the CLI removes a sign-in for it. In `local`/`lan` the server ignores the credential (`access.md`). Tokens are never printed or logged. Tests: `tests/cli/test_server_client.py`.

## Device sign-ins

Device sign-ins (`cli/sign_ins.py`, `SignInStore`): one file per OS user on the CLI's computer, not in a data directory: `%LOCALAPPDATA%\vbot\sign-ins.json` on Windows (not roaming: a Device is one computer), `$XDG_CONFIG_HOME/vbot/sign-ins.json` (default `~/.config/vbot/`) elsewhere. Keyed by origin, it holds the Device token with its id and name, and a pairing that waits for approval (request id, code, expiry, poll secret). On Windows every secret is DPAPI-wrapped for the current user with the origin as entropy (`core/utils/dpapi.py`, shared with the Secret Store key); elsewhere the secrets are plain. Owner-only file (`core/utils/owner_only.py`), every change a locked atomic rewrite; an unreadable or foreign file is reported with its path and never overwritten; a token this account cannot open counts as no sign-in. `tests/cli/conftest.py` points it into the test's home because the shared isolation leaves `LOCALAPPDATA` alone. Tests: `tests/cli/test_sign_ins.py`.

## `vbot devices`

- `devices list|approve <code> [--yes]|deny <code>|rename <device-id> <name>|revoke <device-id>` (`cli/device_management.py`) manage the paired Devices of a server in the Access Mode `authenticated` (`access.md`) through the `devices.*` RPCs. `approve` first shows what is waiting (`devices.pending`: name, kind, requesting address, time, code, and that approving gives full control, so only a pairing the user started from that address) and asks `[y/N]` on a terminal; without a terminal it needs `--yes`. Inside an Agent's Run (`VBOT_RUN_AGENT_ID` set) `approve` refuses before any RPC, so text an Agent reads cannot make it hand out access. `run_refusal(action, instead)` in `cli/device_management.py` is the one Run guard for actions that hand out access; who uses it and why the server has no counterpart: `access.md` -> Invariants. On the server's computer the CLI acts as the host through the local access token, so the host can always approve a Device, even when none is left. Recovery guidance covers `auth_required`, `access_denied`, `auth_disabled`, `rate_limited` and `devices_unavailable` (`_recovery.py`). Server text (names, addresses, codes) reaches the terminal only through `inline_text`. Tests: `tests/cli/test_cli_devices.py`.
- `devices pair [<url>]` and `devices logout [<url>]` (`cli/device_pairing.py`) sign this computer's CLI in to and out of a server; the address is their whole target (`--url`, which names the same server, and the other target options are accepted but hidden from their help; without an address `VBOT_SERVER_URL` is used, else a usage error). `pair` refuses a plain `http://` address of another computer before sending anything, then asks `GET /api/auth/status` with the current credential: an accepted Device, a mode without login, or the host's local token end it with nothing changed. Otherwise it continues a stored, unexpired pairing of that origin or starts one (`kind` `cli`, name `CLI on <computer name>`, `device_name`), stores the started request at once, prints the code and where alone to approve it (in vBot at the paired origin: WebUI Settings > Access & devices > Add device, or `vbot devices approve <code>` on that server's computer; never for another address, since whoever gets it approved signs in as this CLI), and polls per `poll_interval`, honoring `Retry-After`, retrying transport errors, and stopping on a coded 4xx refusal. In a terminal (stdin and stdout) it waits until the code is decided or expires; otherwise it returns after `PAIR_WAIT_SECONDS` (50) with exit 0, an attention line and `Not finished: ...`, and the same command continues with the same code. Approved stores the token (then prints the `--url` to use and the logout command); denied or expired drop the pairing (exit 1); Ctrl-C keeps it. The pairing endpoints get no credential (`http_options(sign_in=False)`), because a stale token would count as a failed sign-in. A start answer whose code is not `XXXX-XXXX` (`_PAIRING_CODE`) ends the command as a foreign answer, and a stored pairing with such a code is not resumed; server text is shown through `inline_text`. `logout` calls `devices.logout` with the stored token and deletes the sign-in also when the server cannot be reached or no longer accepts it (the Device then stays listed until revoked or 90 days unused). Recovery adds no inspection command to either. Tests: `tests/cli/test_device_pairing.py`.
- Pairing, sign-in and logout output never contains the Device token or the poll secret; `SignIn`, `PendingPairing` and `Credential` reprs hide them. Server-supplied names are printed without control characters (`device_pairing._shown`).
