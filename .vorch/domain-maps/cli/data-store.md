# Data Store Commands

Supplementary to `cli.md`. The complete data-store grammar belongs to `cli/_parser_data_store.py`; `cli/parser.py` composes it with the other areas. Covers `vbot data-store` (`cli/data_store_management.py`), the operator surface of the database kernel (`database.md`): `status`, `snapshot`, `incident`, `unregister`, `config-backup` and `secrets`, including when they work on the local data directory instead of through the server.

## Status

`status` prefers the live `data_store.status` projection and falls back to an explicitly labeled local projection (`source: "local"`, kernel `data_store_status` with this vBot's specs from `core/runtime/databases.canonical_database_specs`) only for an unreachable loopback target; `maintenance` and `unavailable` exit non-zero. Ordinary status reads Session search lifecycle markers plus the latest process-local coverage check when known. `status --verify-search` requests a current full coverage check through `data_store.status {verify_search: true}` with unbounded read timeout; the local fallback requests the same read-only coverage mode from `canonical_database_specs(data_dir, verify_search=True)`, without constructing an owner spec or database path itself.

## Snapshots and incidents

- `snapshot list|verify` are local read-only checks against the marker's registered identities; local commands reject remote hosts before file access; `snapshot create` uses the running Runtime.
- `snapshot restore <id> --yes [--database <name>]... [--documents] | --all` checks the snapshot first, classifies the target with `classify_server` (`cli.md` -> Health outcomes; `foreign` refuses), stops and verifies the exact vBot target through its lifecycle owner (the packaged installation's `processes.stop`/`start` when `processes.owning_installation` finds one for the target, otherwise `stop_server`/`start_server`) even after its listener has closed or while it is busy (it must classify `absent` afterwards), and restores through the kernel's incident/restore state machine: no selector restores every database; `--database` only the named ones; `--documents` adds the JSON document set (alone it restores no database); `--all` restores every database and the document set and quarantines databases registered after the snapshot, and combines with no other selector. It then opens each restored database this vBot declares and verifies its read/write path, and restores the prior running state only after success; a busy `unresponsive` server counts as running and is started again. The packaged path takes the installation's operation lock without waiting; when another application operation holds it (or the installation refuses otherwise), the stop fails before any change, and a refused start after the restore fails the command with `<done>, but restoring the prior server state failed: ...`, the same result as a failed start, never a bare error (`_lifecycle`, shared by every command that changes the data directory while stopped).
- `incident acknowledge` clears only the warning state and preserves snapshots and quarantine evidence.
- `unregister <name> --yes` releases the registered database of a removed Extension (`ext.<extension>.<name>`; core databases are refused): it goes through `data_store.unregister` on a reachable server, which refuses while the Extension has the database open, and changes the local data directory directly (`source: "local"`) only for an unreachable loopback target with no server claim on the data directory (`live_server_ports`); a reachable server's refusal and a remote failure never fall back. A restore that installs such a released member registers it again and names it (`registered again: ...`).

## Configuration backups

- `config-backup list|show <id>` are local read-only views of the configuration backups (`database.md` -> Configuration backup; `list` adds the files each backup changed against the next older one, `show` compares each file with the current one).
- `config-backup restore <id> --yes` needs exactly one of `--file <path>`... (as `show` names it; backslashes accepted) or `--all` (which, like a snapshot's document-set restore, keeps the current `secrets.json`; only `--file secrets.json` restores it, `database.md`); it runs a check-only pass first, which refuses an unknown, damaged or folder-less named file before the server is touched, returns without stopping the server when every selected file already matches and no interrupted restore of that backup is pending (`plan.interrupted`; a pending one is finished like a restore), and otherwise stops, restores and restarts the target like `snapshot restore` (shared `_change_while_stopped`, same refusal and failure texts with the noun `configuration backup`). The report names the restored files, the left-alone files with their reason, the files created after the backup (kept), and the `before restore` backup that takes the restore back.

## Secrets

- `secrets list|set <NAME>|unset <NAME>` manage named data-directory credentials through the `secrets.*` RPCs (`secrets.md` -> Credential RPCs); `set` reads the value from a hidden prompt (`_input._read_secret`, `getpass` on a TTY) or from piped UTF-8 stdin, never from argv, and the prompt and output name only the credential. Like `unregister`, they read and write the Secret Store directly (`"local": true`) only for an unreachable loopback target with no `live_server_ports` claim (`_stopped_server_health`); a local `list` reports `source` as `data_dir` or `null` only, since the server's environment is unknown.
- `secrets status|convert --yes|reset --yes` manage the Secret Store of a loopback target's data directory directly (`secrets.md`): `status` prints the health projection (state, counts, damaged entries, key locations, ignored plaintext files, quarantined copies and stores; never a value) and exits non-zero while the store is unavailable; `convert` imports `.env` and `oauth/*.json` without removing store entries (`remove_missing=False`) and deletes what the store verifiably holds, checking first (nothing to convert, unavailable store) and then stopping and restarting the target through `_change_while_stopped`; `reset` refuses unless this process cannot open the store and, while a server runs on the data directory, unless that server's `data_store.status` reports it `unavailable` too with the same `new_key_location` (an unreachable target with a `live_server_ports` claim refuses), then moves it to quarantine and starts an empty one the same way; refusals name where the CLI and the server search for the key and would create a new one.
- These run in the CLI process, so its account, `HOME` and `VBOT_SECRET_KEY_FILE` decide where it looks for or creates a key.
