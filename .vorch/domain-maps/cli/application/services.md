# Managed optional services

`cli/application/services.py` owns SearXNG installation and lifecycle because its container, configuration and recovery outlive the vBot server process. `server/rpc/managed_service_methods.py` adapts that owner for the shared setup and service CLI, and coordinates ordinary Settings mutations after a verified search. A development checkout or a server not owned by the discovered packaged installation reports the feature unavailable; configuring an existing SearXNG URL remains ordinary Settings behavior.

## Ownership and persistence

- One SearXNG container belongs to the exact installation path through its name and both ownership labels. Every inspect, start, stop, replacement and removal verifies that ownership. Foreign containers, images and shared Docker/Podman installations are never removed. Runtime discovery admits local Unix sockets, Windows named pipes in the explicit local `\\.\pipe\` namespace, and local Podman-machine connections only; remote SMB pipe names are rejected before runtime probing. Ambient remote-target environment variables are not passed to container commands.
- `<install>/services/searxng/service.json` stores the application-owned schema-1 operation record, chosen runtime/target, port, desired running state and prior search selection. Writes preserve unknown fields, refuse invalid records and use the application's atomic writer; it is installation state outside the data-directory JSON/snapshot contract. `settings.yml` beside it retains the generated SearXNG configuration across container replacement/removal. Installation paths reject links and junctions.
- Each operation holds the existing application operation lock, excluding updates/removal. The server keeps its asynchronous operation task until admitted work settles; command and system-installer waits are bounded. After process interruption, a persisted running operation reports `action_required`; an explicit repeat reconciles the owned container instead of blindly creating another. A previously installed service left enabled starts in the background with vBot; startup never installs missing prerequisites.

## Installation and updates

- Install/update require the currently displayed plan identity. Preparing missing or stopped prerequisites additionally requires `allow_prerequisites`; a changed plan refuses before mutation. This consent is distinct from OS authorization.
- Windows reuses local Docker Desktop or Podman. A stopped Docker Desktop uses its bounded `desktop start`; otherwise a missing runtime installs `Podman.CLI` through Winget. Podman setup can request WSL through Windows elevation, then reports a resumable restart step. An owned Podman machine uses an explicit connection and `--update-connection=false`, preserving the user's default connection.
- Linux installs Podman from apt, dnf, zypper or pacman. A graphical host can use Polkit authorization. On a terminal host, the CLI/TUI's local prerequisite helper uses the fixed sudo command only after proving the selected server is this installation and obtaining the user's explicit prerequisite choice. Passwords stay in the local terminal, never RPC. Remote accessors get the exact host-terminal command and can resume after it completes. Unsupported/missing package managers require an existing Docker/Podman installation.
- SearXNG pulls the official fully qualified image, resolves it to an immutable image identity, and publishes its HTTP port only on `127.0.0.1`. The generated configuration enables JSON search and disables the limiter for this private service. A real JSON search must answer before vBot changes `web_search` through the existing Settings mutation owner.
- The previous search selection is recorded before installation. A concurrent search-setting change is preserved and leaves selection awaiting an explicit resume. Removal restores the prior selection only while the current selection still points to the owned service.
- A managed-service action called from an active Settings publication callback is refused with `mutation_in_progress` before operation-lock acquisition or installation admission. The shared RPC mutation guard prevents a callback from waiting on its own publisher or starting external work before that refusal; after publication settles, normal admission remains available.
- An update retains the old owned container until the new image passes the search check. Verification failure restores the old container; restart reconciliation restores a replacement interrupted between rename/create/verification. Removal deletes owned current/previous containers, retains configuration, and removes neither shared runtime nor downloaded images.
- Both CLI application removal and direct Windows Inno removal remove the owned service and restore its prior search selection in retained data before the application's records disappear. Offline restoration uses the Settings transaction and rechecks ownership there, preserving later user selections and unknown fields. An unavailable runtime refuses removal rather than abandoning an unverifiable container; early attempts with no stored port and `installed=false` cannot have created a container and do not require a runtime. Completed removal can retry Settings restoration without a runtime. Data-only reset preserves the installation-owned service.

## Verification

`tests/cli/application/test_services.py` covers ownership, local publication, consent/plan admission, replacement rollback/recovery and removal. `test_service_prerequisites.py` covers local-runtime selection and preserving the default Podman connection. `tests/server/rpc/test_managed_service_methods.py` covers Settings selection/restoration, concurrent changes, failed verification and unavailable development installations. Existing integration/removal tests cover both application uninstall entrypoints.

Runtime installation and real Docker/Podman execution are not part of unit tests; tests use deterministic command stand-ins and never install system packages.
