# Windows Tray Host

Supplementary to `cli/application.md`. Read when changing the `vBot.exe` tray: its state, menu, status window, activity history, toasts, its server connection, or its restart into a newly activated version.

## Owners

- `host.py` `ApplicationFacade`: the tray's view of one installation (`state()`, lifecycle actions, `open_session`, `restart`, update milestones, status rows). `watch(sink)` creates the monitor and notifier; `main()` keeps the startup order (recover operations, then the tray, whose first action is the optional initial server start).
- `tray.py` `TrayController`: projects `TrayState` into `TrayPresentation` (icon state, tooltip, menu, status window). Facade actions run one at a time on an action thread; state refreshes run on their own thread, so the view keeps changing while an action such as a server start takes its time. Toolkit-free; tests drive it with fake views.
- `activity.py` `ActivityJournal` and `ActivityRecorder`: the persisted activity history and the rules that turn server observations and tray actions into its entries (Activity history below).
- `monitor.py` `ServerMonitor`: one asyncio thread holding the `/ws` connection, the `/health` classification and an `httpx.AsyncClient` for RPC.
- `notifications.py` `Notifier` and `run_toast_kind`: which events deserve a toast and what it says.
- `windows_tray.py` `WindowsTray`: hidden host window, notification icon, owner-drawn popup menu, toasts, icon badges, `interacting()`. `windows_status.py` `StatusWindow`: the status window. `windows_native.py`: private `WinDLL` instances with full prototypes, theme palette and drawing helpers. All Win32 calls run on the tray's main thread; other threads enqueue work and post one wake message.
- `integration.py` `register_notification_identity` / `remove_notification_identity`: the toast identity in the registry.

## Idle cost contract

The tray does no periodic server I/O. Server state comes from the event stream; `/health` is probed only after a failed connect, and only a refused connect or an unanswered `/health` request adds the local control-record and process check below (no further probe). The controller's 1 s poll only calls `facade.state()`, which must stay cheap (about 0.15 ms; about 0.08 ms with a full activity history): `operations.OperationObserver` rereads only operation records whose mtime/size changed, the release version and server URL are cached, and the activity lines are rendered again only after a new entry or a change of the local date. Do not add network, process or full-directory work to `state()`. Measured idle cost: about 0.02 % of one core (previously 0.5-3 % from a per-second health probe with a fresh HTTP client plus reloading every operation record).

## Server connection

- URL `ws://<target>/ws?connection_id=<stable hex>&accessor=tray`, plus `epoch` and `after_sequence` when reconnecting within 60 s of a loss. Heartbeat frames are ignored; protocol pings (20 s) are the only idle traffic. The hello's `server` object (version, process start time) becomes `MonitorStatus.server_version`/`started_at`; a `server_stopping` event names who stops the server. Protocol details: `server/events-and-reconnect.md`.
- Target: the owned server (`processes.target`) for server shapes; a Desktop Client follows the Desktop's last used server and re-checks it every 30 s while connected.
- Retry backoff 1-5 s for a local target, up to 30 s for a remote one. `start_server`/`restart_server` skip the current delay.
- Busy server: when the stream and then `/health` go unanswered (not refused), a server shape classifies its target with `classify_server`, passing that unanswered request as the health observation, on the monitor thread. A live recorded server process makes the status `unresponsive`; anything else stays `unreachable`. A Desktop Client never classifies.
- Starting or stopping server: a refused connect is classified the same way, from the refused observation. A live recorded process of the target makes it `not_listening`: uvicorn binds its socket only after the Runtime started, and closes it before the Runtime shuts down, so this covers both the whole startup and the shutdown teardown, whoever started or stopped the server (tray, CLI, updater). Anything else stays `refused`, so the server-stopped toast keeps its meaning. Without a control record the check is one failed file open.
- State mapping in the facade: connected -> running; not_listening -> stopping after the stream ended since the last connect (`ActivityRecorder.phase`), else starting; unresponsive -> unresponsive; refused or unreachable -> stopped; rejected by a listener whose `/health` is exactly vBot -> running (safe mode); rejected by anything else -> conflict; before the first attempt -> unknown.
- Close codes 1000, 1001 and 1012 are cooperative. Any other loss (a killed process shows 1006) arms the server-stopped toast, which fires only if the next connect is refused.

## Toasts

- Kinds and switches: Settings `notifications.run_completed`, `run_failed`, `automation_failed`, `update_result`, `server_stopped` (all default on), read through `settings.values` on each connect and before each Run toast.
- Run toasts: only `user` and `system` Runs whose event does not carry `contributes_to_agent_activity: false`; Cron and Calendar Runs only on failure; `run_interrupted` counts as failed; cancelled never. Title names the Agent (`agent.get` name for Identity Agents, the id for Project Agents); the body is the Session title (`session.get`) plus the first error line.
- "Already looking at it": Run toasts wait 1.5 s. A `resource_changed` `sessions` event carrying `read_run_id` for that Run cancels the pending toast or dismisses the shown one. The WebUI acknowledges only while its page is visible and focused (`webui/chat.md`).
- Server stopped: only server-owning shapes, never after a tray-requested stop or restart (`expect_server_stop`) or while an update runs; dismissed when the stream reconnects.
- Update result: fired once when the facade observes an operation's terminal state, together with the matching status-window lines. The newest operation is history, without lines or toast, when it is already terminal at the tray's first observation.
- Mechanics: legacy `NIF_INFO` balloons, which Windows 10/11 shows as toasts. The process sets AppUserModelID `vBot.Tray`; `HKCU\Software\Classes\AppUserModelId\vBot.Tray` (DisplayName, IconUri) names them "vBot". The tray writes it at every start (last started installation wins); `begin_removal` deletes it only while its IconUri points into the removed installation.
- Click opens the Session through `facade.open_session`: the `server` shape opens the browser at `<url>/?open_agent=...&open_session=...`; Desktop shapes launch Desktop with explicit `--host/--port` and `--open-session AGENT SESSION` (contract in `desktop.md`). Toasts without a Session open the status window.
- While a toast shows, a foreground WinEvent hook (skipping the tray's own process) dismisses it when a `vBot.Desktop.exe` window becomes foreground.

## Menu, icon and status window

- Left click (`NIN_SELECT`/`NIN_KEYSELECT`) runs the default item: Open Desktop for Desktop shapes, Open in browser for a running `server` shape, otherwise Status. Right click (`WM_CONTEXTMENU`) builds the owner-drawn popup at open time.
- A queued or running tray lifecycle action (Start, Stop, Restart server, Quit) shows as its transition (starting, stopping, restarting) and withholds every lifecycle item until it finished, so a click never queues a second start behind a running one. A server starting elsewhere offers only Stop server, so a start that never finishes can still be ended; a server stopping elsewhere offers no lifecycle item.
- The menu follows the Windows light/dark app theme and DPI. Lifecycle items and Quit are disabled while an update runs. Application logs and Server logs open their respective owners. External tray shutdown ends an open popup before destroying the window.
- Busy-cursor gotcha: the host window class carries the arrow cursor and the tray calls `SetCursor` before `TrackPopupMenuEx`; without both, Windows shows the busy cursor while hovering the menu.
- Icon states normal, stopped, busy (an update or a server transition runs) and error are badges rendered with Pillow over the release icon; conflict, unresponsive and a failed action or update show error. The tooltip is at most 127 characters.
- The status line always says how the server stands (or Updating...); a failed action, a failed update or a prepared one adds a note after it (`action failed`) instead of replacing it.
- An unresponsive server reads "Server not responding" and offers Restart server and Stop server, never Start server (its process lives, so a start is refused) or Open in browser.
- The status window shows version, a headline with the server state (`Server running since 14:58` from the hello's start time, or the running update's current message), rows (Last error, Server, Data or the Desktop Client's server, Updates from, Last update, Installed in), the activity history and up to three action buttons.

## Activity history

What happened to the server and to updates, shown in the status window and kept across tray restarts, including the restart into a newly activated version.

- Journal: `<install>/logs/tray-activity.jsonl`, one JSON object per line: `at` (canonical UTC), `kind`, `text` (finished English), `level` (`info`, `warning`, `error`), optional `ref`. Readers show `text`, so a tray of another version shows kinds it does not know. Disposable history outside the durable JSON document contract: unreadable lines are skipped, a write failure keeps the entry in memory only. Bounded: the tray keeps 200 entries and rewrites the file (temporary file plus replace) once it holds 400 lines; it reads at most the last 512 KiB.
- Single writer: only the tray host writes, under its host lock; a restarting tray releases the lock before its successor writes.
- `ref` makes an entry happen once, across trays: `server:<started_at>` for a server process, `<operation id>` for an update result, `<operation id>:started`/`:target` for update milestones. A successor that finds the server or the finished update already recorded adds nothing; a tray that starts after an update ran without a tray records its result at the operation's own time.
- Server entries come from observations, not from action results (`ActivityRecorder`): a stop when the stream ends, named by the server's `server_stopping` announcement or, for an older server, by the tray's own request (`server_stopped`, `server_restarting` for `tray_restart`/`scheduled_restart`); a vanished stream (no announcement, non-cooperative close) counts as `server_crashed` only once a connect is refused, and a reconnect to the same process records nothing. A start when the stream of a new process opens (`server_started`, with the startup duration from the process start time and "from the tray" after a tray start), or `server_running` at the tray's first observation of an already running server. Also `server_unresponsive`/`server_responding`, `port_occupied`, and for a Desktop Client `connected`/`disconnected`.
- Tray entries: `tray_started` or `tray_restarted` (successor) from `main()`; `action_failed` for a failed start, stop, restart or update request (the facade's `_recording`).
- Update entries from the facade's update observation: `update_started`, `update_target` (`Updating vBot: <from> -> <to>`), then `update_finished` or `update_failed` (summary from `operations.result_summary`, plus message and reason on failure). Per-phase progress messages are not recorded; the headline shows the current one.

## Restart after activation

A tray host keeps running the code it started with, so after any change of `<install>/active-version` (an update or `update activate` operation, or an installer run) it hands itself over to a successor on the active version. The Desktop has its own restart handoff (`desktop/update-restart.md`).

- Detection: the facade's `running_version` is the version whose payload holds its loaded module (`state.loaded_version_id`); `None` (a development checkout) disables restarts. `TrayState.restart_pending` is true when the active id cached by `_version()` differs from it and the newest operation is terminal or absent; an unreadable operation record counts as busy. It reuses the `active-version` mtime/size signature, so polling costs no extra file or process work.
- Safe point: `TrayController` starts the restart only while no update is active or requested, no tray action is queued or running and `TrayView.interacting()` is false. `WindowsTray.interacting()` is true while the popup menu is open, a toast is shown or the status window is open and not minimized. It reads flags only, without Win32 calls off the UI thread. A toast counts as shown from `show_toast` (before the UI thread shows it) until balloon hide, timeout or click, but at most 300 s, so a close event Windows never sends cannot block restarts.
- Handoff: `facade.restart()` spawns `<install>/vBot.exe` without arguments (the stable bootstrap resolves `active-version` itself) with cwd the install root, `child_environment` plus `VBOT_HOST_SUCCESSOR=1`, standard streams on DEVNULL and windowless creation flags with a new process group and Job breakaway. A child that exits within 2 s raises `ApplicationError` and this tray keeps running. Otherwise the facade logs one INFO line `Tray restarting into the active version (from=<id> to=<id>)` on `vbot.application.host` and the controller stops the view without `facade.quit()`: the server keeps running. `main()` returns and releases the host lock.
- Successor: with `VBOT_HOST_SUCCESSOR=1`, `main()` waits up to 30 s for the host lock (otherwise 0 s) and runs `recover_operations`, but never the initial server start, so a server the user stopped or an update left stopped stays stopped. It sees the finished update as history, without a second toast or activity entry. `operations.child_environment` drops the marker so servers, Desktop and update workers never inherit it.
- Retry: attempts run on the controller's action thread, one at a time. A failure becomes the tray's last error and is retried no sooner than 10 minutes later (injectable clock); after a successful handoff the controller never tries again.
- Gotcha: a successor from a version without this protocol ignores the marker and exits while the predecessor still holds the host lock. The 2 s check catches that only when it exits within 2 s (then the tray reports the failure every 10 minutes); a slower exit leaves no tray until the next start.
