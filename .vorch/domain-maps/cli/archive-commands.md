# Archive Commands and Delete Output

Supplementary to `cli.md`. Covers the `vbot archive` area and what the deleting commands (`agent delete`, `project rm`, `session delete`, with or without `--permanent`) print, refuse and exit with. Archive semantics are owned by `archive.md`.

## Deleting commands

Every deleting command's output names the entry id and the `vbot archive restore <entry-id>` that reverses it. Concrete restore, purge and next-page commands preserve the resolved server target and local credential directory through `target_options`; copying a hint must not fall back to another installation.

- `agent delete <id>` archives the Agent and prints `archived agent <id> as archive entry arc_... (N sessions); restore with: vbot archive restore arc_...`, plus `external Workspace left in place: <absolute-path>` when its Workspace lay outside the Agent's own directory. `--permanent` deletes it now instead and requires `--yes`; without it the command refuses before any RPC and names the corrected call.
- `project rm` archives the Project and its Sessions as an archive entry and prints its id, Session count and restore command (`removed project <id> (archived as archive entry arc_..., N sessions); restore with: vbot archive restore arc_...`) with the Agents whose default Project it cleared (`default_project_cleared_for:`); `--permanent --yes` deletes them now instead (`removed project <id> permanently (N sessions); the repo is untouched`); `--copy-rooted-agent-files` also copies their identity files and reports the copied and backed-up files.
- `session delete` immediately archives the Session (`archived as archive entry arc_...`, with its restore command); only `--permanent` requires `--yes` to delete it now. Both print the landing `next_session_id`.
- A permanent delete (`agent delete`, `project remove`, `session delete` with `--permanent`) whose purge did not finish prints the archived form plus `but deleting it permanently did not finish`, exits 1 and names, beside the automatic retry, the `vbot archive purge <entry-id> --yes` re-run. When another operation took the new entry first, it says so instead: deleted or restored meanwhile (exit 0), or held (`busy`, exit 1, naming `vbot archive show`); a purge that failed before it began leaves the entry archived and names the re-run (exit 1). All four archive error codes select `vbot archive list` as the recovery inspection, with explanations for conflict, not-restorable and busy entries (`_recovery.py`). Tests: `tests/cli/test_cli_archive.py`.

## `vbot archive`

- `archive list|show|restore|purge` (`cli/archive_management.py`, translated by `_dispatch_agents.dispatch_archive_command`; alias `archives`) map to the `archive.*` RPCs (`archive/rpcs.md`, semantics in `archive.md`).
- `list [--kind ...] [--agent <agent|agent@project>] [--project <id>]` pages like `session list` (`--limit`, default 50, JSON `--cursor`, `--all` with repeated-cursor protection). The header names the retention period (`archive entries (automatic deletion after N days):`, `automatic deletion off`, or `automatic deletion paused: the retention period cannot be read` with an attention line naming `vbot doctor settings`, exit 0); each row carries id, kind, subject, scope, label, Session count, `archived_at`, `origin=recovered` for an entry found without its record, `purge_at`, `user_folders=yes` for an entry that may hold the user's folders, and `restorable` with its reason. A further page ends the output with the complete `next page: vbot archive list ... --cursor '<json>'` command; an empty archive prints `no archive entries` (`no matching archive entries` with filters).
- `show <entry-id>` prints the entry, up to 100 member Sessions, the payload trees (a tree that may be the user's own folder is marked so, with what a restore and a purge do to it: a legacy moved Workspace comes back with a restore, and a purge deletes either), the recorded details and `restore: possible|blocked` with every blocker and warning; a conflict blocker names the `--as` retry.
- `restore <entry-id> [--as <new-id>]` prints what came back under which id (`restored agent coder as coder-2 from archive entry arc_... (N sessions; delegation grants: ...)`); restore warnings print as `warning: ...` lines and make the result WARN. A refused restore names its reasons: `archive_restore_conflict` with the corrected `vbot archive restore <entry-id> --as <new-agent-id>` call (the placeholder follows the entry's kind from the error `data`), `archive_not_restorable` with one line per blocker; its guidance says to resolve them and offers `vbot archive purge <entry-id> --yes` only when a blocker no action resolves (`kind_not_restorable`, `older_format`, `payload_missing`), and its `Next:` command is `vbot archive show <entry-id>`. `archive_entry_busy` prints the server's reason; the recovery guidance reads the error `data` (`RpcFailure.data`) and says what to do by state: for an interrupted restore that cannot finish (`problem`), resolve it or move the folder, then restart the server; for `purging`, that the entry will not become restorable and `vbot archive purge <entry-id> --yes` finishes it now; otherwise, retry after the other operation finished. Its `Next:` command is `vbot archive show <entry-id>` with the entry's id. Every concrete recovery command keeps the resolved server and local credential directory, including purge commands in prose; missing or unsafe entry ids never produce runnable placeholders. Restart advice names the server's own computer.
- `purge (<entry-id>... | --all [--kind] [--agent] [--project]) --yes` deletes entries permanently. The parser rejects ids together with `--all`, neither of them, and filters without `--all` (exit 2); its errors name `vbot archive list` with the given filters and the delete-by-id call, never an `--all` call, so deleting a whole selection stays an explicit choice; without `--yes` the command refuses before any RPC (exit 1). Output: `purged N archive entries (M sessions)` (`purged no archive entries` when only unfinished ones remain) plus one row per entry, or `no archive entries matched; nothing was purged`. Entries `--all` keeps because they may hold the user's folders are listed `kept reason=files|user_folders`, with WARN attention naming the `vbot archive purge <entry-id>... --yes` call that deletes them (exit 0). An entry another operation deleted or restored first is listed `gone` and counts as done (exit 0); one it holds is listed `skipped reason=busy state=<state>` with WARN attention naming `vbot archive show <entry-id>`, without promising a retry (exit 1). The purge runs synchronously without a response deadline (`archive.purge` is long-running and announces the phase `Deleting archived Sessions and files`), so a large `--all` finishes in one call. An entry that did not finish is listed `pending reason=...`, the command exits 1 with WARN attention saying that vBot retries it automatically and naming the re-run that continues it at once; an interrupted purge leaves its entries `purging`, which the retention sweep or the same re-run continues.
