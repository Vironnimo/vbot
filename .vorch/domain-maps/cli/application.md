# Packaged Application

Read for native distribution, installers, tray/lifecycle integration, transactional updates, Autostart and managed Extension dependencies. Every vBot installation is a packaged application: per-user Windows installations in three shapes and Linux server installations, both updating from the signed packages of their channel. `cli/application/` extends CLI lifecycle ownership because its state and update worker must remain available when Runtime is stopped. It does not own business configuration or Sessions. A source checkout is a development checkout only: `application`, `update`, `uninstall` and `autostart` refuse there with a pointer to git (`command._INSTALLATION_AREAS`, `tests/cli/test_cli_main.py`).

## Terms

### Update channel
Where an installation installs and updates from: `release` (published releases) or `main` (the rolling `main-build` prerelease of green main commits). Recorded as `release_url` in `application.json`. Not a messaging Channel (see `channels.md`).

### Development checkout
A Git checkout running vBot from source for development and tests (`pip install -e ".[dev]"`, Worktrees included). It is not an installation: it has no `application.json`, is updated with git, and refuses the installation commands.

## Layout and native boundary

- Windows: `<install>/vBot.GUI.exe` is the stable Windows GUI companion used by the Desktop shortcut with `desktop`. It resolves `active-version` on each launch and shares CLI/Desktop dispatch without allocating a console. The console `vBot.exe` keeps terminal output and wait semantics. Both remain protocol-1 bootstraps: the Inno installer places them at the root (`install_payload` copies a missing one from the first version's `runtime/`, as for a direct `application install`), and updates never replace them.
- The exact `vBot.GUI.exe desktop` shortcut enters `cli/main.py` without loading the console parser or server services. `cli/application/desktop.py` owns the shared launch used by this entry and the tray facade, retaining installation discovery, active-version resolution, recorded/explicit target handling and the removal-admission lock. It passes the Desktop its relaunch contract (`VBOT_DESKTOP_RELAUNCH`: `active-version` path, running version id, stable bootstrap command) so an open Desktop can restart into a newly activated version (`desktop/update-restart.md`). Other arguments use the complete CLI parser/output path. This is a payload-only optimization; existing protocol-1 GUI bootstraps need no replacement. Fresh-process import and failure coverage: `tests/cli/test_startup.py`; launch/lock/target coverage: `tests/cli/application/test_host.py`.
- `<install>/vBot.exe` is the stable native bootstrap. No arguments starts the per-user tray host; arguments dispatch CLI commands. Native role hosts run CPython in-process: `vBot.Server.exe`, `vBot.Desktop.exe`, `vBot.Update.exe`, and `vBot.Python.exe`. Desktop is optional and independent of server lifetime.
- Linux: `<install>/vbot` (default `~/.local/share/vbot`) is the stable protocol-1 shell bootstrap (`scripts/linux/vbot`), copied from the first version's `runtime/vbot` at install and never replaced by updates. It reads `active-version`, exports `VBOT_INSTALL_ROOT` and runs `runtime/bin/python3 -I -B -X utf8 -m cli.main`; `vbot --server ...` instead runs `server.main` from the version's `app/`, which is how the systemd unit starts it. A missing or invalid version exits 111 (`autostart.BOOTSTRAP_FAILED_EXIT_CODE`). The runtime is python-build-standalone CPython pinned in `scripts/linux/python.lock.json`, with wheel-only locked dependencies per architecture (`linux-aarch64`, `linux-x86_64`); `Installation.interpreter` resolves every role to `runtime/bin/python3`. There is no tray, Desktop or GUI companion on Linux. `~/.local/bin/vbot` is a symlink to the bootstrap. On Linux, psutil's process creation time follows wall-clock changes, so process identity compares `core.utils.server_control.process_started` (boot-relative) values instead.
- `vBot.Server.exe` uses the console subsystem. Managed starts in `processes.py` use `CREATE_NO_WINDOW`, providing an attached, windowless console. Do not build the Server as a GUI executable: Windows ignores `CREATE_NO_WINDOW` for it, so pywinpty's ConPTY setup can allocate a visible console before hiding it. Native-host coverage in `tests/scripts/test_build_windows.py` checks the windowless console across real PTY start/close cycles. Desktop and the GUI bootstrap keep the Windows subsystem.
- Both native manifests declare PerMonitorV2 and Windows 10/11 compatibility. Desktop retains its separate manifest and WinForms opt-in (see `desktop.md`).
- The tray host (`host.py` facade, toolkit-free `tray.py` controller, Win32 view in `windows_tray.py`/`windows_status.py`) follows its server through one `/ws` connection as accessor `tray` (`monitor.py`) and raises toasts (`notifications.py`); it has no third-party UI toolkit. Invariant: an idle tray does no periodic server I/O and its 1 s `facade.state()` poll stays cheap, so never add network, process or full-directory work there. Tray status uses a cached human release version and a separate short state line, never an entire operation message. Details -> References.
- Packaged server start/stop/restart/status use the shared CLI progress, result renderer and exit-code policy. Native startup results carry health and WebUI facts so successful startup never renders as stopped. Packaged `server status` uses the shared CLI status renderer and exit-code policy, including structured running, URL, WebUI, data-directory and log-path fields and a successful exit for a reported non-vBot listener conflict.
- The running server reports its build from these records (`runtime.md` -> `build`): `core/utils/version.py` reads the version's `release.json` `revision` and `channel`; a `main` package reports branch `main`, any other package an official release. `scripts/package_build.py` writes both fields. Keep their meaning when changing either side.
- `application.json` records schema, shape, exact server target, `release_url` and `release_public_key`; `active-version` atomically selects `versions/<safe-id>`. Each version contains `app/` readable runtime sources/resources/built WebUI and `runtime/` private CPython 3.14 (PROJECT.md -> Development -> Python version)/dependencies, plus a complete `release.json` inventory. Standard payload collection excludes checkout metadata, tests and build tooling. The version id is `v<version>_<12-hex revision>` (`package_build.version_id`), so two main builds of one version differ.
- Bootstrap protocol 1 is immutable across ordinary updates. An incompatible release fails validation before activation and needs a new installer. Native paths are isolated from ambient Python environments; application code does not write bytecode into releases. Native hosts explicitly enable Python UTF-8 mode so redirected CLI output and Agent Tool results preserve Unicode independently of the Windows code page.
- Server payload collection includes the private, digest-locked ripgrep/PCRE2 executable and third-party notices. `payload.copy_application` reuses a verified executable from the checkout it builds from or provisions the locked archive of the package's platform (`search_target`: Windows x64, Linux aarch64 or x86_64) before inventory generation. Desktop-client excludes native search assets. See `tools/search_files.md`.
- Every prepared runtime replaces `runtime/DLLs/sqlite3.dll` with the official sqlite.org build pinned in `scripts/windows/sqlite.lock.json` (archive SHA3-256 plus library SHA256), so the database kernel's journal policy selects WAL for every packaged database (`database.md` -> Conventions). `runtime_sqlite.py` owns this stdlib-only step for the Windows release builder (`copy_runtime`), before inventory generation. A library already matching the pin is kept; otherwise the archive is downloaded without ambient proxies and verified before an atomic replace. The lock is mandatory: a missing or malformed lock fails the build. `smoke.py` asserts the pinned version. Coverage: `tests/cli/application/test_runtime_sqlite.py`, `tests/scripts/test_build_windows.py`. Linux packages keep the SQLite of python-build-standalone; `build_linux.py` refuses a runtime whose SQLite is not WAL-safe.
- Source: `state.py`, `packages.py`, `payload.py`, `retention.py`, `scripts/package_build.py` (shared packaging, signing, `vbot-release.json`), `scripts/build_windows.py`, `scripts/windows/native_hosts.py`, `scripts/windows/launcher.c`, `scripts/windows/vbot.iss`, `scripts/build_linux.py`, `scripts/linux/`. Windows ships the three shapes server, server-desktop and desktop-client; Linux ships only server. A client never probes, snapshots or stops a default local server.
- `install.py` `main` is the only installation command line: the stable Windows bootstrap routes `vBot.exe application install ...` to it with the payload's own runtime, and `install.sh` runs it as a module; the `vbot` parser has no install command. It rejects equal or nested application/payload roots in either direction after resolving paths, before any filesystem mutation, and refuses a non-empty destination or one that already holds an installation. Coverage: `tests/cli/application/test_install.py`.

## Update operation

- Update channels: `release` follows the latest published release and `main` the rolling `main-build` prerelease that `.github/workflows/main-build.yml` republishes for every main commit whose push CI passed. `application.json` stores the channel as `release_url`, which must be one of the two GitHub API URLs of `state.CHANNEL_URLS` (`releases/latest`, `releases/tags/main-build`), and `Installation.channel` names it. These URLs are only the stored channel identity: installed applications validate them, so they never change, and nothing requests them. `Installation.download_base` (`state.CHANNEL_DOWNLOADS`) maps the channel to its release download base, `https://github.com/Vironnimo/vbot/releases/latest/download` or `.../releases/download/main-build`. The updater never queries `api.github.com`: its anonymous limit (60 requests per hour and IP) fails users and CI runners behind shared IPs, while release downloads have no such limit. `load_installation` rejects a record without both `release_url` and `release_public_key` (empty for an unsigned development package). Installers record the channel (`install.py --channel`); `vbot application channel main|release` switches it under the dispatch and operation locks, refuses while an update is pending, and takes effect with the next `vbot update`. `application status` shows it. Both channels use the same signed packages, worker and rollback; there is no local build path.
- `packages.download_release` reads `<download base>/vbot-release.json`, the release identity (`version_id`, `version`, `revision`, `channel`, and `assets`, the SHA-256 digest of every other asset; published last so it never names a version whose packages are missing; at most `packages.MAX_IDENTITY_BYTES`, 4096, which every installed updater enforces). When the identity names the active version the update skips the download and, after checking Extension dependency compatibility, completes as already up to date without snapshot, maintenance admission, Agent continuation or restart, including with `--no-restart`. Otherwise it downloads `vbot-<platform>-<shape>.zip` and its `.sig` (`packages.package_name`) from the same base; the Ed25519 signature, not the identity digest, authenticates the package. A release without an identity (404) fails the update before any download; a missing package or signature fails it with `No matching signed application package`. A selected `--package` whose version id equals the active one completes the same way.

- Human CLI, tray and Agent CLI call `operations.request_update`. Atomic records under `operations/` contain phases, identities, result and exact worker PID/create-time. Only equivalent pending requests coalesce. The short dispatch lock protects worker handoff; the OS-owned operation lock covers the entire mutation, also excluding manual lifecycle changes. Every CLI command dispatched on an installation (`command.dispatch`) holds a `LogManager` on `<install root>/logs/` for its duration, like the host and worker, so its lines are kept (`tests/cli/application/test_command.py`). `Operation.transition` logs each phase change once on `vbot.application.update` (`<install root>/logs/`) with the operation id, kind (`package` or `online`), from/to phase and version ids: INFO, `failed`/`rolled_back` WARN and `needs_attention` ERROR carrying the saved error; progress within a phase is DEBUG. The worker adds the data-rollback outcome (restored or not restored at WARN, not needed at INFO); a version cleanup that keeps every version or defers a tree is WARN (`tests/cli/application/test_worker.py`).
- `_output.py` owns readable update outcomes using `_progress.py` status markers and elapsed-time heartbeats. Native updates opt into one transient progress line on capable terminals; captures remain append-only and a new phase resets its heartbeat deadline. The source and target release versions include short Git revisions and the target is announced as soon as resolved. Worker messages distinguish downloading, unpacking and verifying, dependencies, verification starts and data snapshots. Display labels are stored under `operations/details/`, outside the protocol-1 transaction record so still-running prior-version consumers can read it. Native default output has no raw phase prefixes or trailing JSON; a terminal result states its total duration from request to saved outcome (`created_at`/`updated_at`). Explicit `--output plain` retains one structured operation result, and `update status` remains a read-only structured inspection. Prepared/detached/handoff outcomes retain the exact status or activation command and never imply completed activation. The PowerShell installer preserves these shared status labels while retaining full diagnostics in its log.
- All background dependency and Autostart subprocesses use the shared windowless creation flags. Native CLI/Server/Update startup failures write stderr and exit instead of waiting on a modal dialog; tray/Desktop GUI launches may display a dialog. Early child errors are captured under application logs: the packaged server start (`processes.start`) runs the child with console logging off (`VBOT_LOG_STDIO=0`), so `<install>/logs/server-startup.log` receives only output that bypasses logging, such as a crash before logging starts; at the next start a file over `STARTUP_LOG_ROTATE_BYTES` (1 MiB) moves to `server-startup.log.1`.
- A human `vbot update` normally waits for terminal state and returns nonzero on failure. `--detach` returns acceptance. `--no-restart` produces terminal `prepared`, leaves the pointer unchanged, and requires `update activate <id>` later. A dead caller cannot cancel the worker. The waiting CLI, an equivalent repeated update request, or tray startup can recover an orphan by reconciling its saved phase; `update status` only reads saved state.
- Official archive signatures are Ed25519 over the raw SHA256 digest, verified against the install's public key. Deliberately supplied `--package` artifacts can be local/unsigned. Extraction rejects unsafe paths, special files, case collisions, invalid shape/platform/protocol and inventory mismatches before activation. Payload verification scans entries without following links/reparse points, checks the exact inventory and hashes every file; it does not repeatedly resolve each file's ancestors. Payload files are hashed and copied by `packages.FILE_WORKERS` concurrent readers: Windows scans every newly written file on its first open, which made sequential hashing of a fresh candidate the slowest update step. A digest mismatch names the first differing file in inventory order. An inventory mismatch names up to three unexpected and three missing paths.
- Stray bytecode: running a version's `runtime/python.exe` directly (also through a venv based on it) writes `__pycache__/*.pyc` into the verified version. Native hosts pass `-B`, which stops writes but not loads, so such caches are deleted, never ignored. Call sites that verify an already installed version (active/base, candidates, removal-reset, re-staged identity, archive export) pass `validate_release(..., remove_bytecode_caches=True)`: uninventoried files named `*.pyc` or `*.pyc.<digits>` (interrupted cache writes) directly inside a `__pycache__` directory are removed with a warning on `vbot.application.packages` before the exact check. Any other difference still fails, an undeletable cache fails with an actionable error, and inventoried bytecode is hashed like any file. Fresh builds and extractions stay strict. Because candidate preparation runs the active version's code, only updates started from a version containing this removal benefit; an older active version fails such an update with "Release file inventory does not match its payload". A runtime-level write block is not viable: the `encodings` imports precede `site`, and `._pth` has no bytecode switch.
- `worker.py` prepares a version and carries the Extension dependency recipe forward before stopping anything. It then classifies the server once with `processes.server_state` for the previous version (states below). Only `running` obtains server-owned maintenance admission, drains accepted work and stops the exact server. `absent` stops nothing; the snapshot's claim check proves that no server started since. `unresponsive` ends `failed` before any drain, stop, snapshot or activation: the server keeps running, the previous version stays active and the message asks to retry once the server responds; `foreign` also fails there, through the generic error path. `server_was_running` records liveness (`running` or `unresponsive`), so an update never leaves a server stopped that ran before it. The worker runs the previous version's code, so this classification protects the updates started from a version that contains it. After the stop it takes the update snapshot (`database.md` -> Update snapshot) offline and keeps it in memory; the Operation record gains no field. The worker runs the previous version's code, so it passes `canonical_database_specs(data_dir)` to the snapshot and the rollback: core owner facts are recorded and verified (Extension databases by identity and integrity only). Before the snapshot and again before the candidate starts, no server may still claim the data directory (`live_server_ports`, re-checked for up to `_CLAIM_SETTLE_SECONDS` because Windows can release an exited process's lock late; a failed check counts as a claim), and the data must still match the snapshot's stamp. A snapshot or fence failure restarts the previous version if it was running and ends `failed` without activation. Then it probes the candidate with `--verification-only`, changes the pointer and verifies required normal startup. Candidate failure can retain previous code only after previous startup verification. Recovering an interrupted `stopping`/`activating` operation whose previous version is still active stops an answering candidate verification server, releases a living previous server (`running` or `unresponsive`) from this operation's maintenance, and starts the previous server only when it is `absent`, so a busy server is never duplicated; an `unresponsive` verification server, or a `foreign` occupant where the previous server has to return, makes the operation `needs_attention`. Coverage: `tests/cli/application/test_worker.py`.
- Version retention (`retention.py`): after a `completed` operation, still under the operation lock, `retire_unneeded` renames every complete version (one with `release.json`) outside the needed set to `staging/retired-*`, together with every download directory whose operation is not unfinished. `worker.run` deletes these trees with `remove_retired` only after releasing the lock. A tree that cannot be renamed or fully deleted is retried by the next cleanup. The needed set contains:
  - the active version;
  - the versions named by every operation newer than the last one that changed the active version, that operation's own previous and candidate versions (the known-good fallback), and every unfinished operation;
  - the `home` version of each managed speech or embedding environment (`speech-engines/*`, `embedding-engines/*`), because such a venv breaks when its base runtime disappears;
  - every version a running process of this installation uses: its executable, or, for a root bootstrap, a loaded module. The tray host keeps running from its start-time version until its restart handoff, which the user's interaction with the tray can defer.

  A vBot-named process that cannot be inspected, or an unreadable record, keeps every version. Cleanup never changes an operation's outcome. The worker runs the previous version's code, so cleanup begins with the update after the one that installs it. Coverage: `tests/cli/application/test_retention.py`, `test_worker.py`.
- Long-lived clients switch to a newly activated version by restarting at a safe point: the tray hands over to a successor started through the stable bootstrap while the server keeps running (`cli/application/tray.md` -> Restart after activation); the Desktop has its own restart handoff (`desktop/update-restart.md`). Completion texts for a Desktop Client (`worker.py`, `operations.result_summary`) say that an open Desktop switches by restarting.
- Data rollback (`roll_back_data`) runs only after a failed candidate verification start and before the previous version is probed: with no server claim left and the data changed since the stamp, it calls `restore_update_snapshot`. A refusal restores nothing and the `rolled_back` message says so and why; unchanged data needs no restore; a restore that started but failed raises, so the operation becomes `needs_attention` naming `vbot data-store snapshot restore <id> --all --yes`, and the maintenance guard keeps every version off the half-restored data. After the candidate verified, the snapshot is stale and never restored automatically, including when normal startup after the pointer change fails. Recovery of a lost worker never restores; an incomplete maintenance guard in `stopping`/`activating` becomes `needs_attention` (with the repeat command when this operation's snapshot exists). Residual risk: a foreign writer that exits while the candidate runs is indistinguishable from the candidate. Ambiguous recovery becomes `needs_attention`. Coverage: `tests/cli/application/test_worker.py`.
- `processes.server_state(install, version_id=, verification=)` is the one classification of the installation's server for an exact version and startup mode: `classify_server` (`cli.md` -> Health outcomes) with the recorded process narrowed to that version's native executable and `--verification-only` or normal mode. Identity and liveness come from the control record (PID plus creation time), health from `probe_health_patiently`, never from one 0.5 s probe. `running`: that exact process answers `/health`. `unresponsive`: it lives but does not answer (busy Event Loop, still starting, already stopping; the control record exists before the listener). `foreign`: anything else holds or answers the target (another version or mode, a live process that cannot be inspected, another data directory's vBot, an unidentified listener). `absent`: no live recorded process and no listener. `processes.start` spawns only on `absent`; `unresponsive` fails with `the server process is running but does not answer its health check`, the others keep `already running` or the occupied conflict. Its readiness loop uses the quick probe. The data-only reset and removal admission (Verification and operation entrypoints) decide through it as well. Coverage: `tests/cli/application/test_processes.py`. Dispatch detaches the updater from vBot's lifetime Job once; the updater owns no Job and starts its verification/recovery/normal servers without requesting another breakaway from ambient Windows Jobs. Direct lifecycle starts and dispatch use the shared immediate-Job policy in `core.utils.processes` (see `tools/process.md`), preserving a restrictive external ancestor while escaping vBot's own Job. `core.utils.server_control.server_control_claim` prevents competing starts from replacing live shutdown authority. Its per-data-directory/port OS lock spans control publication through final cleanup.

## Installers and published packages

- `scripts/install.ps1` (Windows) and `scripts/install.sh` (Linux) are the only installation entrypoints, and each installs one signed package: release (default), `-Version`/`--version <tag>`, or the newest main build (`-Main`/`--main`, recorded as channel `main`; cannot be combined with a version). Neither builds anything locally. An existing installation is never overwritten: `install.ps1` refuses an existing directory, `install.sh` reports an existing `application.json` and points to `vbot update`.
- `install.ps1` matches exactly one `vBot-<version>-windows-x86_64-<shape>.exe`, requires its GitHub SHA-256 digest, an HTTPS `github.com` URL and a valid or absent Authenticode signature, then runs Inno silently with `/TASKS=startup` unless `-NoAutostart` or `-DesktopClient`. With Autostart it then starts the tray (`vBot.exe`, which starts the server; the logon task alone would start it only at the next sign-in) and waits for `/health` (`Get-ServerHealthUrl` mirrors the CLI's server URL for wildcard and IPv6 hosts). It refuses an elevated PowerShell (`-AllowElevatedInstall` is for disposable automation), logs to an OS-temporary file that a failure preserves, and rethrows instead of `exit` when run without a script file (`irm | iex`, script block) so the caller's window stays open. Coverage: `tests/scripts/test_install_scripts.py`.
- `install.sh` needs only `curl` and `python3`: it picks `vbot-linux-aarch64-server.zip` or `-x86_64-` from `uname -m` (a 32-bit Raspberry Pi OS is refused with a hint), checks the published digest, unpacks with the system Python and installs with the package's own runtime (`python3 -m cli.application.install --channel ...` plus the release public key). It links `~/.local/bin/vbot`, and unless `--no-autostart` runs `vbot autostart enable`, asks `sudo loginctl enable-linger` when lingering is off (a refusal is a warning) and starts the server. Default root `~/.local/share/vbot` (`$VBOT_DIR`), data `~/.vbot`. Coverage: `tests/scripts/test_install_sh.py` (Linux only).
- Packages are built only by CI: `windows-package.yml` and `linux-package.yml` (reusable; `release_mode`, `channel`, `ref`) build, sign and smoke them; `main-build.yml` publishes them to `main-build` after a green CI push run, and `release.yml` to a tagged release. `scripts/release_assets.py` is the complete asset contract both publishers validate: for every Windows shape and Linux platform the zip, `.sig` and runtime inventory, the Windows installers, and `vbot-release.json` naming the expected version, revision and channel. Once the set passes, `--record-digests` writes the lowercase SHA-256 digest of every other file into the identity's `assets` map as compact JSON, and refuses an identity larger than `packages.MAX_IDENTITY_BYTES` (4096 bytes; the current 18 other assets need about 2150) (`tests/scripts/test_release_assets.py`). Local `scripts/build_windows.py` / `scripts/build_linux.py` runs serve development and smoke tests only; a Linux package must be built on its own architecture.

## Autostart and server supervision

- `autostart.py` owns `autostart enable|disable|status` for one installation root; another root's registration is never changed, and a same-named registration of another root makes `status` and `enable` fail. Windows registers a passwordless per-user Task Scheduler logon task that runs `vBot.exe` without arguments (the tray). The task script sets priority 4: the default 7 starts the whole process tree below normal with low I/O and memory priority, so Windows trims the idle server's working set and pages it back in at low I/O priority, producing multi-second Event Loop stalls with no CPU use. The tray never restarts a stopped server.
- Linux writes the systemd user unit `vbot.service` (`$XDG_CONFIG_HOME/systemd/user`, default `~/.config/systemd/user`): `ExecStart=<root>/vbot --server --host --port --data-dir`, `VBOT_LOG_STDIO=0` (the daily log is the log; the journal keeps only output that bypasses logging), `Restart=on-failure` after 5 s except for `RestartPreventExitStatus` 3 (`STARTUP_FAILED_EXIT_CODE`), 70 (`SHUTDOWN_FAILED_EXIT_CODE`, both `core/utils/server_control.py`, `server.md`) and 111 (bootstrap without a valid version), `KillMode=mixed` with `TimeoutStopSec=60` so the server shuts down its Runtime and leftover descendants are removed. A unit belongs to this installation when its single `ExecStart` runs this bootstrap (`owned_unit`). `enable` rewrites the unit only when its content differs, rolls back on a failed `daemon-reload`/`enable`, and requests `loginctl enable-linger`; a refusal leaves the registration with `attention` (the server then starts only at login). `enable` registers without starting the server.
- While `owned_unit` holds, `processes.start` (normal mode on the active version) runs `systemctl --user start vbot.service` and waits for health, and `processes.stop` runs `systemctl --user stop`, so lifecycle commands never fight the unit's restart policy. Verification starts of a candidate or previous version spawn the server directly.
- Everything left in a service's cgroup dies with the service. A process that must outlive the server it was started from (the update worker from `operations.spawn_worker`, the scheduled restart helper of `cli/server_management.schedule_server_restart`) starts through `core.utils.processes.outside_service_unit`, which prefixes `systemd-run --user --scope --quiet --collect --` when the caller runs inside a service of the user's systemd manager (`user@<uid>.service/…/<unit>.service`), the counterpart of the Windows Job breakaway. A system service such as cron or a CI runner is not one: `systemd-run --user` cannot leave it, so the process starts directly.
- A server restart the server schedules itself (`server_management._run_scheduled_restart`) and `data-store snapshot restore` route through the owning installation when `processes.owning_installation` finds one for the exact target (same port and resolved data directory): `processes.stop`/`start` under the operation lock, so a packaged server restarts through its unit or native host. Without an installation (development checkout) they use `stop_server`/`start_server`. Coverage: `tests/cli/test_server_management.py`, `tests/cli/test_data_store.py`.
- A successful registration change logs `Application Autostart enabled` / `disabled` with `mode=task_scheduler` or `mode=systemd` on `vbot.application.integration` (enable logs only when it changed the registration). The lines reach the installation's `logs/` because every dispatched command holds a `LogManager` there.

## Agent handoff

`core/tools/_bash_update_handoff.py` gives each Bash call with a persistence boundary an opaque in-memory token in `VBOT_UPDATE_HANDOFF`; the call itself writes no file. The token is claimable only while a process of that call may still run: Bash releases it when the command exits or its spawn fails, and a server restart forgets every token. A `vbot update` on a server-owning installation claims the token before dispatch through `application.update_handoff_mint` on its own server (`processes.target`). Only then does the server write the durable opaque ticket under `<data_dir>/runtime/update-handoffs/`, once per token, logging one INFO line with the Agent, Session and Run (never the token, ticket id or path), and the operation record stores its absolute path; the CLI still validates that path and content against the exact data directory. An unknown or released token or an unreachable server raises an `ApplicationError` and starts no update. The callback after the complete Tool batch enters Session history acknowledges the call, whether its ticket is claimed before or after that point. The worker waits for that acknowledgement and durably registers an idempotent once-Bootstrap before maintenance begins. The private application RPC validates the saved call and Session, closes new admission, then cancels and awaits only the exact origin Run; its cleanup and already accepted Queue work remain part of the drain. The Bootstrap resumes in that Session on the next startup and inspects the saved operation without repeating prior actions. Human/tray updates create no Agent or Bootstrap. Tickets and `runtime/update-continuations/` receipts serve one operation: Runtime start deletes those older than `UPDATE_HANDOFF_FILE_RETENTION` (7 days) and logs one DEBUG count summary that never names ticket ids or tokens. Coverage: `tests/core/tools/test_bash_update_handoff.py`, `tests/server/rpc/test_application_methods.py`.

## Optional dependencies

- User Extension sources stay in data/configured roots. `application dependencies install --requirements` replaces the complete managed dependency recipe. Resolution uses a fresh data-directory site constrained by the immutable runtime inventory. ## Verification and operation entrypoints

`uninstall [--app-only | --data-only | --all] [--yes]` (`command.py`): a terminal without a mode gets a menu (application only, data only, both, cancel; a Desktop Client offers only the application) and must confirm with `YES` (application only) or `DELETE` (data); anything else prints `uninstall: cancelled; no changes made`. Non-interactive callers must pass one mode and `--yes`. `integration.uninstall` refuses while an update is pending or when the caller's cwd lies inside the installation, stops the exact owned server before removing anything, and guards the data directory (no filesystem root, home, installation root, or a path containing the installation or cwd). Linux removes the systemd unit, the `~/.local/bin/vbot` link when it points to this bootstrap (a foreign file stays) and the installation directory directly; Windows hands application removal to the registered Inno uninstaller as follows.

Windows native uninstall creates `removal-pending.json` under dispatch/operation locks before deleting application files. Admission verifies Inno's copied second-phase process, its exact registered-uninstaller target and its first-phase parent; only those two verified processes and the current command are exempt from the owned-process scan. The scan checks only absolute executable paths because Windows process enumeration can return non-path pseudo-process names. The second-phase PID/create-time owns the marker through actual deletion. It refuses pending updates, a server that `processes.server_state` does not find `absent` (a busy `unresponsive` one included; admission never stops it, Inno ran `server stop` before), or other remaining owned processes. The durable marker blocks update dispatch, recovery, tray start and ordinary operation mutations throughout Inno deletion; explicit stop remains available. Desktop launch holds the short dispatch lock across its guard and process creation so it cannot race this reservation. Normal Inno completion/cancel removes it. Inno's `[UninstallDelete]` removes the whole application folder, logs and locks included: installation accepts only an empty folder and keeps server data outside it, so a later install into the same folder succeeds. After an uninstaller crash, `application removal-reset` requires a dead/different PID creation identity and a verified complete active release before clearing the marker.

A packaged data-only reset (`uninstall --data-only`, `integration.uninstall`) classifies the server first: `running` is stopped, its data removed and the server restarted; `absent` removes the data and leaves the server stopped; `unresponsive` or `foreign` refuse before stopping or deleting anything, so data is never deleted under a live server.
