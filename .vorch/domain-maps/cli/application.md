# Packaged Application

Read for native distribution, installers, tray/lifecycle integration, transactional updates, Autostart and managed Extension dependencies. Every vBot installation is a packaged application: per-user Windows installations in three shapes and Linux server installations, both updating from the signed packages of their channel. `cli/application/` extends CLI lifecycle ownership because its state and update worker must remain available when Runtime is stopped. It does not own business configuration or Sessions. A source checkout is a development checkout only: `application`, `update`, `rollback`, `uninstall` and `autostart` refuse there with a pointer to git (`command._INSTALLATION_AREAS`, `tests/cli/test_cli_main.py`).

## Layout and native boundary

- `cli.main.run` dispatches the installation commands before the console command surface. Package discovery (`state.discover`) follows loaded payload/native executable provenance; ordinary source Python ignores an inherited `VBOT_INSTALL_ROOT`, including in Worktrees and nested development checkouts (only a native host of a temporary install payload without a recorded ancestor uses it), so the CLI of a development checkout that a packaged server's shell started never adopts that installation. Loaded `versions/<id>/app` provenance is authoritative even when `application.json` is missing or unavailable: discovery refuses instead of treating it as source code; native-host record checks also propagate metadata failures.
- Windows: `<install>/vBot.GUI.exe` is the stable Windows GUI companion used by the Desktop shortcut with `desktop`. It resolves `active-version` on each launch and shares CLI/Desktop dispatch without allocating a console. The console `vBot.exe` keeps terminal output and wait semantics. Both remain protocol-1 bootstraps: the Inno installer places them at the root (`install_payload` copies a missing one from the first version's `runtime/`, as for a direct `application install`), and updates never replace them.
- The exact `vBot.GUI.exe desktop` shortcut enters `cli/main.py` without loading the console parser or server services. `cli/application/desktop.py` owns the shared launch used by this entry and the tray facade, retaining installation discovery, active-version resolution, recorded/explicit target handling and the removal-admission lock. It passes the Desktop its relaunch contract (`VBOT_DESKTOP_RELAUNCH`: `active-version` path, running version id, stable bootstrap command) so an open Desktop can restart into a newly activated version (`desktop/update-restart.md`). Without an explicit host or port, an installation with its own server opens that server: over the loopback address of the wildcard's family when the recorded host is a wildcard (`0.0.0.0`, `*`, empty -> `127.0.0.1`; `::` -> `::1`; the address the server records for its local access token), and with `--server-data-dir <server data dir>`, so the Desktop signs in to it with the local access token instead of pairing (`desktop/sign-in.md`); an explicit target gets neither. Other arguments use the complete CLI parser/output path. This is a payload-only optimization; existing protocol-1 GUI bootstraps need no replacement. Fresh-process import and failure coverage: `tests/cli/test_startup.py`; launch/lock/target coverage: `tests/cli/application/test_host.py`.
- `<install>/vBot.exe` is the stable native bootstrap. No arguments starts the per-user tray host; arguments dispatch CLI commands. Native role hosts run CPython in-process: `vBot.Server.exe`, `vBot.Desktop.exe`, `vBot.Update.exe`, and `vBot.Python.exe`. Desktop is optional and independent of server lifetime.
- `payload.py` includes the shared native Computer Use target and wire modules in a Desktop Client, alongside its Desktop, core utility and CLI sources; the server-side Extension, Skills, server and WebUI assets stay in server shapes. Desktop declares its Terminal/Computer Use dependencies directly in the `desktop` extra even when the base package also needs them. These capabilities run inside the Desktop app's lifetime (`desktop.md`).
- Linux: `<install>/vbot` (default `~/.local/share/vbot`) is the stable protocol-1 shell bootstrap (`scripts/linux/vbot`), copied from the first version's `runtime/vbot` at install and never replaced by updates. It reads `active-version`, exports `VBOT_INSTALL_ROOT` and runs `runtime/bin/python3 -I -B -X utf8 -m cli.main`; `vbot --server ...` instead runs `server.main` from the version's `app/`, which is how the systemd unit starts it. A missing or invalid version exits 111 (`autostart.BOOTSTRAP_FAILED_EXIT_CODE`). The runtime is python-build-standalone CPython pinned in `scripts/linux/python.lock.json`, with wheel-only locked dependencies per architecture (`linux-aarch64`, `linux-x86_64`); `Installation.interpreter` resolves every role to `runtime/bin/python3`. There is no tray, Desktop or GUI companion on Linux. `~/.local/bin/vbot` is a symlink to the bootstrap. On Linux, psutil's process creation time follows wall-clock changes, so process identity compares `core.utils.server_control.process_started` (boot-relative) values instead.
- `vBot.Server.exe` and `vBot.Desktop.exe` use the console subsystem. Managed starts in `processes.py` and `desktop.py` use `CREATE_NO_WINDOW`, providing an attached, windowless console for their PTYs. Do not build these hosts as GUI executables: Windows ignores `CREATE_NO_WINDOW` for those, so pywinpty's ConPTY setup can allocate a visible console before hiding it. Native-host coverage in `tests/scripts/test_build_windows.py` checks both hosts' windowless consoles across real PTY start/close cycles. The stable GUI bootstrap keeps the Windows subsystem.
- Both native manifests declare PerMonitorV2 and Windows 10/11 compatibility. Desktop retains its separate manifest and WinForms opt-in (see `desktop/window.md` -> Windows monitor scaling).
- The tray host (`host.py` facade, toolkit-free `tray.py` controller, Win32 view in `windows_tray.py`/`windows_status.py`) follows its server through one `/ws` connection as accessor `tray` (`monitor.py`) raises toasts (`notifications.py`) and keeps a persisted activity history of server and update events (`activity.py`); it has no third-party UI toolkit. Its connections carry the target's credential (`cli/server_client.py`; for its own server the local access token), and in the Access Mode `authenticated` it opens the browser through a login ticket. Invariant: an idle tray does no periodic server I/O and its 1 s `facade.state()` poll stays cheap, so never add network, process or full-directory work there. Tray status uses a cached human release version and a separate short state line, never an entire operation message. Details -> References.
- Packaged server start/stop/restart/status use the shared CLI progress, result renderer and exit-code policy. Native startup results carry health and WebUI facts so successful startup never renders as stopped. Packaged `server status` uses the shared CLI status renderer and exit-code policy, including structured running, URL, WebUI, data-directory and log-path fields and a successful exit for a reported non-vBot listener conflict.
- The running server reports its build from these records (`runtime.md` -> `build`): `core/utils/version.py` reads the version's `release.json` `revision` and `channel`; a `main` package reports branch `main`, any other package an official release. `scripts/package_build.py` writes both fields. Keep their meaning when changing either side.
- `application.json` records schema, shape, exact server target, `release_url`, `release_public_key` and, for a server shape, `server_access` (the server's Access Mode with its options, `AccessConfig.to_record`, `access.md`; a record without it, written before Access Modes, infers `local` for a loopback `server_host` and `lan` otherwise, `Installation.access`). `load_installation` refuses an invalid `server_access` or one whose mode the recorded host contradicts; `Installation.save()` keeps record fields it does not know (versions before Access Modes drop them, `server_access` included, which turns the mode back into the inferred one); `active-version` atomically selects `versions/<safe-id>`. Each version contains `app/` readable runtime sources/resources/built WebUI and `runtime/` private CPython 3.14 (PROJECT.md -> Development -> Python version)/dependencies, plus a complete `release.json` inventory. Standard payload collection excludes checkout metadata, tests and build tooling. The version id is `v<version>_<12-hex revision>` (`package_build.version_id`), so two main builds of one version differ.
- Bootstrap protocol 1 is immutable across ordinary updates. An incompatible release fails validation before activation and needs a new installer. Native paths are isolated from ambient Python environments; application code does not write bytecode into releases. Before writing the release inventory, both builders use the packaged CPython to compile application modules, bundled Extensions and runtime libraries into unchecked hash caches (`scripts/package_build.compile_bytecode`). Those caches are deterministic (version-relative code filenames, no source timestamps) and inventoried and hashed like sources; the immutable, verified payload lets Python load them without rereading sources after extraction. Inherited caches are removed first; Skill scripts and test fixtures are not compiled. Native hosts keep `-B` and explicitly enable Python UTF-8 mode so redirected CLI output and Agent Tool results preserve Unicode independently of the Windows code page. Coverage: `tests/scripts/test_package_build.py`, `test_build_windows.py`, `tests/cli/application/test_packages.py`.
- Server payload collection includes the private, digest-locked ripgrep/PCRE2 executable and third-party notices. `payload.copy_application` reuses a verified executable from the checkout it builds from or provisions the locked archive of the package's platform (`search_target`: Windows x64, Linux aarch64 or x86_64) before inventory generation. Desktop-client excludes native search assets. See `tools/search_files.md`.
- Every prepared runtime replaces `runtime/DLLs/sqlite3.dll` with the official sqlite.org build pinned in `scripts/windows/sqlite.lock.json` (archive SHA3-256 plus library SHA256), so the database kernel's journal policy selects WAL for every packaged database (`database/connections.md` -> Journal policy). `runtime_sqlite.py` owns this stdlib-only step for the Windows release builder (`copy_runtime`), before inventory generation. A library already matching the pin is kept; otherwise the archive is downloaded without ambient proxies and verified before an atomic replace. The lock is mandatory: a missing or malformed lock fails the build. `smoke.py` asserts the pinned version. Coverage: `tests/cli/application/test_runtime_sqlite.py`, `tests/scripts/test_build_windows.py`. Linux packages keep the SQLite of python-build-standalone; `build_linux.py` refuses a runtime whose SQLite is not WAL-safe.
- Windows runtime dependencies are hash-locked per shape. Desktop's source-only `proxy-tools` builds in a temporary environment provisioned from the wheel-only `scripts/windows/requirements-build.lock`; automatic build isolation and reuse of cached source-built wheels are disabled, so build dependencies cannot escape hash verification. The backend stays outside the payload, its lock participates in the prepared-runtime cache key, and server dependencies remain wheel-only (`scripts/windows/requirements.md`).
- Source: `state.py`, `packages.py`, `payload.py`, `retention.py`, `scripts/package_build.py` (shared packaging, signing, `vbot-release.json`), `scripts/build_windows.py`, `scripts/windows/native_hosts.py`, `scripts/windows/launcher.c`, `scripts/windows/vbot.iss`, `scripts/build_linux.py`, `scripts/linux/`. Windows ships the three shapes server, server-desktop and desktop-client; Linux ships only server. A client never probes, snapshots or stops a default local server.
- `install.py` `main` is the only installation command line: the stable Windows bootstrap routes `vBot.exe application install ...` to it with the payload's own runtime, and `install.sh` runs it as a module; the `vbot` parser has no install command. It resolves application, payload and server data paths before mutation, rejects equal or nested application/payload roots and overlapping application/data roots in either direction (including `..` and directory links), and refuses a non-empty destination or one that already holds an installation. It repeats destination admission under the operation lock, so a concurrent completed install or newly added file stays untouched. A server shape records its Access Mode from `--access local|lan|authenticated` (default `local`) with `--allow-network`, `--allow-host`, `--public-url`, `--trusted-proxy`, `--tls-cert` and `--tls-key` (`add_access_arguments`, shared with `application access set`); `--host` defaults to the mode's bind address. A configuration the server could not start with (a non-loopback host for `local`, missing HTTPS or public URL for `authenticated`, unreadable TLS files) is refused before anything is created. Coverage: `tests/cli/application/test_install.py`.
- `vbot application access show` prints the recorded Access Mode, bind address and options; `access set <mode> [options] [--host]` refuses inside an Agent's Run (`VBOT_RUN_AGENT_ID`, `run_refusal` in `cli/device_management.py`), validates and records a new configuration under the dispatch and operation locks (refused while an update is pending), logs `Server access mode changed (from=... to=... host=...)` on `vbot.application.integration`, rewrites an owned systemd unit (`autostart.refresh_unit`) and applies at the next server start. Options not given are cleared; without `--host` the address stays while the mode and its transport stay, else it becomes the new mode's default. The installed server reads the record itself at start: for its own port and data directory the recorded mode and host win over launcher flags, explicit contradicting access flags refuse the start, and an unreadable record refuses it. It mirrors the configuration into the data directory's `access/server.json`, so a server started on that data directory another way (another port, a development checkout) keeps the mode (`access/server-setup.md` -> Start precedence). A running tray keeps the server target it cached at its start until it restarts; only its browser opening reads the record again (`cli/application/tray.md` -> Browser sign-in). Coverage: `tests/cli/application/test_command.py`, `test_state.py`, `tests/server/test_main.py`.

Saving `application.json` creates a record only when it is absent; an unreadable or malformed existing record refuses the change and keeps its bytes, including fields this version does not know.

## Update operation

- A new package for an installation in `authenticated` Access Mode must declare `server_access_protocol: 1` in its verified `release.json`. The staged source declares this contract in `pyproject.toml` (`tool.vbot.package.server-access-protocol`) and the builders emit it, so a newer builder cannot mark older source as compatible; the package owner checks it before staging publishes a version, before installer mutations, before a candidate verification start and again before `Installation.activate` changes the pointer. Prepared updates are checked against the current mode. Missing, mistyped or unsupported values refuse admission without selecting an older mode. A candidate failure retains the original pointer and may restart only the operation's recorded previous baseline even if that baseline predates the marker; arbitrary old candidates receive no exemption. The first upgrade is run by the previous updater, so its existing rollback remains usable. A pre-marker updater or manually invoked old executable does not enforce this gate.
- Update channels: `release` follows the latest published release and `main` the rolling `main-build` prerelease that `.github/workflows/main-build.yml` republishes for every main commit whose CI and package builds passed. `application.json` stores the channel as `release_url`, which must be one of the two GitHub API URLs of `state.CHANNEL_URLS` (`releases/latest`, `releases/tags/main-build`), and `Installation.channel` names it. These URLs are only the stored channel identity: installed applications validate them, so they never change, and nothing requests them. `Installation.download_base` (`state.CHANNEL_DOWNLOADS`) maps the channel to where its identity downloads from, `https://github.com/Vironnimo/vbot/releases/latest/download` or `.../releases/download/main-build`; `Installation.asset_base(version)` names where the assets of that identity download from: the main channel keeps `main-build`, the release channel pins `.../releases/download/v<version>` after checking the version is strict `X.Y.Z`, because `releases/latest` can move to a newer release between the identity and the package download and would mix two releases. The updater and both Installers never query `api.github.com`: its anonymous limit (60 requests per hour and IP) fails users and CI runners behind shared IPs, while release downloads have no such limit. `load_installation` rejects a record without both `release_url` and `release_public_key` (empty for an unsigned development package). Installers record the channel (`install.py --channel`); `vbot application channel main|release` switches it under the dispatch and operation locks, refuses while an update is pending, and takes effect with the next `vbot update`. `application status` shows it. Both channels use the same signed packages, worker and rollback; a deliberately selected local package (`update --package`) uses the same worker without the signature check.
- `packages.download_release` reads `<download base>/vbot-release.json`, the release identity (`version_id`, `version`, `revision`, `channel`, and `assets`, the SHA-256 digest of every other asset; published last so it never names a version whose packages are missing; at most `packages.MAX_IDENTITY_BYTES`, 4096, enforced while reading the response so oversized identities never buffer in full). When the identity names the active version the update skips the download and, after checking Extension dependency compatibility, completes as already up to date without server stop, snapshot, Agent continuation or restart, including with `--no-restart`. An identity that is not newer than the active version fails the update with `OlderReleaseError` before any download, stop or snapshot (phase `failed`, WARN; the reason names the switch back `vbot application channel <channel of the active version>` and the deliberate path `vbot update <offered release version>`), so switching from `main` to `release` never installs older code and never repeats a failing downgrade on every update (`packages._not_newer`): versions order by their numeric release part, and for an equal version a `release` identity is older than an active `main` build, because a version's main builds start with its release bump commit (an identical build shares the version id); unparseable versions are not ordered (`test_packages.py::test_download_refuses_a_channel_version_not_newer_than_the_active_one`). The check runs in the active version's worker, so it protects updates started from a version that contains it. Otherwise it downloads `vbot-<platform>-<shape>.zip` and its `.sig` (`packages.package_name`) from `asset_base` (a release identity without a strict version fails before any download); the Ed25519 signature, not the identity digest, authenticates the package. Both the downloaded identity and the signed package must name the selected update channel; explicit local packages remain independent of it. A release without an identity (404) fails the update before any download; a missing package or signature fails it with `No matching signed application package`. A selected `--package` whose version id equals the active one completes the same way.

- Human CLI, tray and Agent CLI call `operations.request_update`. Atomic records under `operations/` contain phases, identities, result and exact worker PID/create-time. Only equivalent pending requests coalesce. A recorded worker that cannot be inspected is treated as still live, so recovery never duplicates an unproven orphan. After acquiring the operation lock, a worker reloads the saved record and proceeds only while it still owns the unfinished operation; unreadable or superseded records stay untouched. The short dispatch lock protects worker handoff; the OS-owned operation lock covers the entire mutation, also excluding manual lifecycle changes. `state.exclusive` owns lock lifetime, timeout and removal admission; OS acquire/release uses the stdlib-only `core/utils/file_lock.py`, available in every package shape. Every CLI command dispatched on an installation (`command.dispatch`) holds a `LogManager` on `<install root>/logs/` for its duration, like the host and worker, so its lines are kept (`tests/cli/application/test_command.py`). `Operation.transition` logs each phase change once on `vbot.application.update` (`<install root>/logs/`) with the operation id, kind (`package` or `online`), from/to phase and version ids: INFO, `failed`/`rolled_back` WARN and `needs_attention` ERROR carrying the saved error; progress within a phase is DEBUG. The worker adds the data-rollback outcome (restored or not restored at WARN, not needed at INFO); a version cleanup that keeps every version or defers a tree is WARN (`tests/cli/application/test_worker.py`).
- Worker dispatch (`operations._dispatch`): the worker, and every server it starts, must not belong to the requester's lifetime. A requester inside another application's Windows Job (a coding agent's shell running `vbot update` or `scripts/deploy_local.py`) cannot give it that, since whatever it starts stays in the Job and ends when that application closes (`tools/os-processes.md`). So on Windows only the tray host starts workers: `request_update(..., host=True)` and `recover_operations(..., host=True)` are its calls and spawn directly. Any other requester, when a tray of this installation runs (`operations.host_running`: `host.json` pid and creation time), writes `host-dispatch-request.json` (`{"schema_version": 1, "operation": id}`, clearing a dead worker's identity) under the dispatch lock and waits up to `HOST_DISPATCH_SECONDS` (30 s) for the tray to start the worker (`dispatch_requested`, `cli/application/tray.md` -> Update dispatch). Without a running tray, a requester whose `foreign_job()` confines its children (`confining_job()`) starts the tray outside its Job through WMI (`core.utils.outside_job.start_outside_job`, no Job, the user's session and default environment; `tools/os-processes.md`) and hands over the same way; the new tray's startup recovery already starts the worker. Otherwise (Linux, no Job, a Job that allows breakaway) the requester spawns the worker as before. A handoff no tray takes is settled by the requester: outside a foreign Job it starts the worker itself with a WARN (a tray of an older version ignores the request); inside one it refuses with `ApplicationError` naming the Job's owner (a `queued` operation becomes `failed`, so no tray runs it later by surprise), as it does when WMI cannot start the tray (for example under Defender's rule blocking process creation from WMI). A tray started this way logs one INFO line (`operation`, `job_owner`, `job_owner_pid`). `deploy_local.py` runs the installed version's CLI, so an installed version without this handoff still runs the worker inside the caller's Job; the script prints a warning when its own Job would confine the update. Coverage: `tests/cli/application/test_operations.py`.
- Server requests (`vbot server start`/`restart` from a confined caller, `processes.start_or_restart`): when `confining_job()` finds a Job and a tray of this installation runs, `operations.request_server` hands the command over through the same `host-dispatch-request.json` (`{"schema_version": 1, "server": "start"|"restart", "request": <32 hex>}`, written only when no request is pending). The tray consumes it under the dispatch lock, writes `host-server-result-<request>.json` with `state: accepted` and runs the command as its own tray action; it then writes `state: done` with `ok`, `message` and `process_id` (`answer_server_request`), and the requester reports that result like a local start. The requester waits up to `HOST_DISPATCH_SECONDS` for acceptance; a request no tray accepted (none answers, or a tray of an older version drops the unknown record) is withdrawn under the lock and the command runs locally. An accepted request without a result within `HOST_SERVER_SECONDS` (300 s) fails with `the vBot tray accepted the server <command> but reported no result within 300 seconds; check the server with vbot server status`. The requester removes the result file. Without a tray, or unconfined, `start_or_restart` runs stop/start itself under the operation lock; `processes.start(breakaway=True)` then leaves a confining Job through WMI (`start_outside_foreign_job`) and, if that fails, starts inside it and returns the confinement warning in `CommandResult.attention` (`cli/server-lifecycle.md` -> Commands). A server started through WMI writes nothing to `server-startup.log`. No tray is ever started for a server command. Coverage: `test_operations.py`, `test_processes.py`, `test_host.py`, `test_tray.py`.
- `_output.py` owns readable update outcomes using `_progress.py` status markers and elapsed-time heartbeats. Native updates opt into one transient progress line on capable terminals; captures remain append-only and a new phase resets its heartbeat deadline. The source and target release versions include short Git revisions and the target is announced as soon as resolved. Worker messages distinguish downloading, unpacking and verifying, dependencies, verification starts and data snapshots. Display labels are stored under `operations/details/`, outside the protocol-1 transaction record so still-running prior-version consumers can read it. Native default output has no raw phase prefixes or trailing JSON; a terminal result states its total duration from request to saved outcome (`created_at`/`updated_at`). Explicit `--output plain` retains one structured operation result, and `update status` remains a read-only structured inspection. Prepared/detached/handoff outcomes retain the exact status or activation command and never imply completed activation. The PowerShell installer preserves these shared status labels while retaining full diagnostics in its log.
- All background dependency and Autostart subprocesses use the shared windowless creation flags. Native CLI/Server/Update startup failures write stderr and exit instead of waiting on a modal dialog; tray/Desktop GUI launches may display a dialog. Early child errors are captured under application logs: the packaged server start (`processes.start`) runs the child with console logging off (`VBOT_LOG_STDIO=0`), so `<install>/logs/server-startup.log` receives only output that bypasses logging, such as a crash before logging starts; at the next start a file over `STARTUP_LOG_ROTATE_BYTES` (1 MiB) moves to `server-startup.log.1`.
- A human `vbot update` normally waits for terminal state and returns nonzero on failure. `--detach` returns acceptance. `--no-restart` produces terminal `prepared`, leaves the pointer unchanged, and requires `update activate <id>` later. `update activate` writes no package: it requests the prepared, already installed version (`request_update(prepared_version=)`), whose directory becomes the operation's `package` (`local_package`), and `stage_package` verifies that directory in place like a package of it, so a repeated `update activate` joins the running operation. A dead caller cannot cancel the worker. The waiting CLI, an equivalent repeated update request, or tray startup can recover an orphan by reconciling its saved phase; `update status` only reads saved state.
- Official archive signatures are Ed25519 over the raw SHA256 digest, verified against the install's public key. Deliberately supplied `--package` artifacts can be local/unsigned. Extraction rejects unsafe paths (any name `core.utils.ids.is_reserved_name` reports, on every platform, so a Linux package stays portable: `ntpath.isreserved` plus `COM0`/`LPT0`), special files, case collisions, invalid shape/platform/protocol and inventory mismatches before activation. Payload verification scans entries without following links, rejects symbolic links and junctions (`is_link_status`; other reparse points such as cloud-file placeholders are ordinary files), checks the exact inventory and hashes every file; it does not repeatedly resolve each file's ancestors. Payload files are hashed by `packages.FILE_WORKERS` concurrent readers: Windows scans every newly written file on its first open, which made sequential hashing of a fresh candidate the slowest update step. A digest mismatch names the first differing file in inventory order. An inventory mismatch names up to three unexpected and three missing paths.
- Stray bytecode: running a version's `runtime/python.exe` directly (also through a venv based on it) writes `__pycache__/*.pyc` into the verified version. Native hosts pass `-B`, which stops writes but not loads, so such caches are deleted, never ignored. Call sites that verify an already installed version (active/base, candidates, removal-reset, re-staged identity, archive export) pass `validate_release(..., remove_bytecode_caches=True)`: uninventoried files named `*.pyc` or `*.pyc.<digits>` (interrupted cache writes) directly inside a `__pycache__` directory are removed with a warning on `vbot.application.packages` before the exact check. Any other difference still fails, an undeletable cache fails with an actionable error, and inventoried bytecode is hashed like any file. Fresh builds and extractions stay strict. Because candidate preparation runs the active version's code, only updates started from a version containing this removal benefit; an older active version fails such an update with "Release file inventory does not match its payload". A runtime-level write block is not viable: the `encodings` imports precede `site`, and `._pth` has no bytecode switch.
- `worker.py` prepares a version and carries the Extension dependency recipe forward before stopping anything. It then classifies the server once with `processes.server_state` for the previous version (states below). Only `running` is stopped, at once and exactly like `vbot server stop` (`processes.stop`, initiator `update`): the update does not wait for accepted work. Runtime shutdown (`runtime.md` -> Shutdown) rejects new work, cancels queued items and waiting-work reservations (the in-memory Queue is lost, as with any stop) and cancels active Runs, waiting only for their bounded cancellation cleanup; cancelled Runs keep their persisted partial history. As with any stop, a server that has not exited after the 30 s stop timeout is ended by force (`cli.md` -> Health outcomes). `absent` stops nothing; the snapshot's claim check proves that no server started since. `unresponsive` ends `failed` before any stop, snapshot or activation: the server keeps running, the previous version stays active and the message asks to retry once the server responds; `foreign` also fails there, through the generic error path. `server_was_running` records liveness (`running` or `unresponsive`), so an update never leaves a server stopped that ran before it. The worker runs the previous version's code, so this classification protects the updates started from a version that contains it. After the stop it takes the update snapshot (`database.md` -> Update snapshot) offline and keeps it in memory; the Operation record gains no field. The worker runs the previous version's code, so it passes `canonical_database_specs(data_dir)` to the snapshot and the rollback: core owner facts are recorded and verified (Extension databases by identity and integrity only). Before the snapshot and again before the candidate starts, no server may still claim the data directory (`live_server_ports`, re-checked for up to `_CLAIM_SETTLE_SECONDS` because Windows can release an exited process's lock late; a failed check counts as a claim), and the data must still match the snapshot's stamp. A snapshot or fence failure restarts the previous version if it was running and ends `failed` without activation. Then it probes the candidate with `--verification-only`, changes the pointer and verifies required normal startup. Candidate failure can retain previous code only after previous startup verification. Recovering an interrupted `stopping`/`activating` operation whose previous version is still active stops an answering candidate verification server, leaves a living previous server (`running` or `unresponsive`) running, and starts the previous server only when it is `absent`, so a busy server is never duplicated; an `unresponsive` verification server, or a `foreign` occupant where the previous server has to return, makes the operation `needs_attention`. Phase `waiting_for_idle`, which earlier versions stored while the server drained, stays a valid stored phase (`state.PHASES`) that the worker never writes; like `queued` and `preparing` it is outside the recovery phases, so a recovered operation in it runs again from the start. An older version's worker, which runs against its own older server, still drains through that server's maintenance RPCs. Coverage: `tests/cli/application/test_worker.py`.
- Version retention (`retention.py`): after a `completed` operation, still under the operation lock, `retire_unneeded` renames every complete version (one with `release.json`) outside the needed set to `staging/retired-*`, together with every download directory whose operation is not unfinished and every `staging/<version id>.zip` that earlier versions' `update activate` left behind, unless an unfinished operation names it as its package. `worker.run` deletes these trees with `remove_retired` only after releasing the lock. A tree that cannot be renamed or fully deleted is retried by the next cleanup. The needed set contains:
  - the active version;
  - the versions named by every operation newer than the last one that changed the active version, that operation's own previous and candidate versions (the known-good fallback), and every unfinished operation;
  - the `home` version of each managed speech or embedding environment (`speech-engines/*`, `embedding-engines/*`), because such a venv breaks when its base runtime disappears;
  - every version a running process of this installation uses: its executable, or, for a root bootstrap, a loaded module. The tray host keeps running from its start-time version until its restart handoff, which the user's interaction with the tray can defer.

  A vBot-named process that cannot be inspected, an unreadable record or operation-directory listing, or an incomplete speech/embedding environment inventory (directory listing, child status, or configuration read failure) keeps every version in its original location. An unavailable operation inventory also refuses update and removal admission; only a missing directory means no operations. Cleanup never changes an operation's outcome. The worker runs the previous version's code, so cleanup begins with the update after the one that installs it. Coverage: `tests/cli/application/test_retention.py`, `test_worker.py`.
- Long-lived clients switch to a newly activated version by restarting at a safe point: the tray hands over to a successor started through the stable bootstrap while the server keeps running (`cli/application/tray.md` -> Restart after activation); the Desktop has its own restart handoff (`desktop/update-restart.md`). Completion texts for a Desktop Client (`worker.py`, `operations.result_summary`) say that an open Desktop switches by restarting.
- Data rollback (`roll_back_data`) runs only after a failed candidate verification start and before the previous version is probed: with no server claim left and the data changed since the stamp, it calls `restore_update_snapshot`. A refusal restores nothing and the `rolled_back` message says so and why; unchanged data needs no restore; a restore that started but failed raises, so the operation becomes `needs_attention` naming `vbot data-store snapshot restore <id> --all --yes`, and the maintenance guard keeps every version off the half-restored data. After the candidate verified, the snapshot is stale and never restored automatically, including when normal startup after the pointer change fails. Recovery of a lost worker never restores; an incomplete maintenance guard in `stopping`/`activating` becomes `needs_attention` (with the repeat command when this operation's snapshot exists). Residual risk: a foreign writer that exits while the candidate runs is indistinguishable from the candidate. Ambiguous recovery becomes `needs_attention`. Coverage: `tests/cli/application/test_worker.py`.
- Credential conversion rides on this transaction (`secrets/plaintext-conversion.md` -> Settle per start mode): the candidate's verification start imports `.env` and `oauth/*.json` into `secrets.json` without touching them and fails verification when the import fails; on an update from a version before the Secret Store, the worker's rollback (previous version's code) neither knows `secrets.json` nor finds the plaintext files touched, so the previous version keeps its credentials. Only the first normal start after activation deletes the plaintext files and purges their copies from configuration backups and data snapshots.
- Document format conversion rides on this transaction too: the candidate's verification start converts JSON documents of an older format version (`json-documents.md` -> Document rules) under the update snapshot, and a failure fails the verification and rolls back.
- `processes.server_state(install, version_id=, verification=)` is the one classification of the installation's server for an exact version and startup mode: `classify_server` (`cli.md` -> Health outcomes) with the recorded process narrowed to that version's native executable and `--verification-only` or normal mode. Identity and liveness come from the control record (PID plus creation time), health from `probe_health_patiently`, never from one 0.5 s probe. `running`: that exact process answers `/health`. `unresponsive`: it lives but does not answer (busy Event Loop, still starting, already stopping; the control record exists before the listener). `foreign`: anything else holds or answers the target (another version or mode, a live process that cannot be inspected, another data directory's vBot, an unidentified listener). `absent`: no live recorded process and no listener. `processes.start` spawns only on `absent`; `unresponsive` fails with `the server process is running but does not answer its health check`, the others keep `already running` or the occupied conflict. Its readiness loop uses the quick probe. The data-only reset and removal admission (Verification and operation entrypoints) decide through it as well. Coverage: `tests/cli/application/test_processes.py`. Dispatch detaches the updater from vBot's lifetime Job once (and from foreign Jobs through the tray, Worker dispatch above); the updater owns no Job and starts its verification/recovery/normal servers without requesting another breakaway from ambient Windows Jobs. Direct lifecycle starts and dispatch use the shared immediate-Job policy in `core.utils.processes` (see `tools/os-processes.md`), escaping vBot's own Job; a breakaway start from a confining foreign Job goes through WMI (Server requests above), while the worker's `breakaway=False` starts never do. `core.utils.server_control.server_control_claim` prevents competing starts from replacing live shutdown authority. Its per-data-directory/port OS lock spans control publication through final cleanup.

## Supported version switching and operator rollback

The first release whose source declares `tool.vbot.package.version-switch-protocol = 1` is the earliest supported target. `scripts/package_build.py` copies it into the signed `release.json` and release identity as `version_switch_protocol`; rebuilding older source never grants it support. The current protocol covers candidate admission, operation records and tray handoff. Once the active payload declares the protocol, every different candidate, including local and prepared packages, must declare this same supported protocol. No earlier-target adapters are provided.

`vbot update <version>` accepts exact `X.Y.Z` and `vX.Y.Z`, resolves the signed release independently of the installation's update channel, binds its identity/version/channel/revision to the verified package before publication, and retains the configured channel. It bypasses only the ordinary channel's newer-only rule. Existing candidate verification and data rollback remain the compatibility boundary: failed vBot startup/data checks prevent activation. Extension code does not run in verification mode, so Extension database compatibility remains checked on its normal open (`extensions/databases.md`); failed Extension startup stays isolated and is not proof that the entire application failed verification. A prepared exact selection keeps its version constraint when activated.

`cli/application/rollback.py` identifies the last activated switch from operation records, skipping no-op updates. A `needs_attention` operation whose candidate is active is eligible too, so failed normal startup does not strand the previous version. `vbot rollback` binds its request to that operation and its verified previous payload; worker admission rechecks that binding. The normal path uses current data. Only `rollback --restore-data <snapshot-id> --yes` selects the checkpoint's exact retained snapshot; the CLI refuses this form inside a Run because it can remove its history and continuation. The worker saves current data first and verifies the chosen snapshot. Under the restore owner's maintenance guard and operation lock, it rechecks live server claims and data changes before recording restore intent and modifying data. New canonical opens are refused while that guard is held. It restores every snapshot member and retires newer registrations through the database owner's restore API, respecting its document exclusions. A failed target verification restores the safety snapshot, including newer database registrations, before checking the original version. This restore also checks live claims and a fresh post-candidate data stamp under its maintenance guard; a competing writer leaves the data untouched and requires inspection. The precise approved-reset command remains in the error even when the current version also fails to restart. Loss of the worker after restore intent requires inspection and never automatically repeats the restore.

The rollback worker can stop an unresponsive owned server through the shared lifecycle path. A stopped server remains stopped, except that rollback from a failed normal start restores that operation's recorded running intent. Desktop Clients do no data or server work. Server data remains outside the installation.

Operation request and recovery metadata live in `operations/details/<id>.json`: selected release, rollback source, requested restore snapshot, captured safety snapshot and whether restoration started, alongside display labels. Exact switches and rollbacks use operation schema 2 and require every sidecar field. Ordinary updates keep schema 1 for the first forward-upgrade record; after `queued`, a schema-1 operation whose retained source payload declares switching support also requires complete details. Only a genuinely missing historical optional sidecar is ignored; unreadable or malformed ones refuse. A new tray advertises `operation_protocol: 2` in `host.json`; every new request and orphan dispatch refuses until a still-running predecessor tray restarts. The worker repeats admission before any server or data mutation, covering requests from the predecessor tray itself. All eligible return targets understand it. Structured output calls the restore `requested_restore_snapshot` and exposes `data_restore_started`, never claiming that a started restore completed.

Update snapshots are retained under their operation id at creation (`database/snapshots-and-recovery.md` -> Snapshot creation and retention). Cleanup keeps the last completed switch and unresolved operations' claims, releases only this installation's obsolete operation claims, and does not change the operation outcome if cleanup fails. Existing version retention keeps the associated payloads. A successful rollback becomes the next return point, with the data captured immediately before that rollback. A `needs_attention` checkpoint remains retained for inspection.

## Installers and published packages

- `scripts/install.ps1` (Windows) and `scripts/install.sh` (Linux) are the only installation entrypoints, and each installs one signed package: release (default), `-Version`/`--version <version>` (exact `X.Y.Z` or `vX.Y.Z`), or the newest main build (`-Main`/`--main`, recorded as channel `main`; cannot be combined with a version). Neither builds anything locally. An existing installation is never overwritten: `install.ps1` refuses an existing directory, `install.sh` reports an existing `application.json` and points to `vbot update`.
- Both pass the server's Access Mode only when given, leaving the defaults to `install.py`: `install.ps1 -HostName -Access -AllowNetwork -AllowHost -PublicUrl -TrustedProxy -TlsCert -TlsKey` become the Inno parameters `/VBOTHOST`, `/VBOTACCESS`, `/VBOTALLOWNETWORK`, `/VBOTALLOWHOST`, `/VBOTPUBLICURL`, `/VBOTTRUSTEDPROXY`, `/VBOTTLSCERT`, `/VBOTTLSKEY` (lists comma-joined; `vbot.iss` repeats the option per item; TLS paths made absolute; values with quotes or line breaks, and list items with commas, are refused), and `install.sh --host --access --allow-network --allow-host --public-url --trusted-proxy --tls-cert --tls-key` pass straight through (`scripts/windows/README.md`).
- Both Installers download from the release download base of their selection (`releases/latest/download`, `releases/download/<tag>` or `releases/download/main-build` under `https://github.com/Vironnimo/vbot`): first `vbot-release.json`, then the asset whose SHA-256 digest its `assets` map records. For the latest release they download the asset from the tag the identity names (`releases/download/v<version>`, version strictly `X.Y.Z`), like the updater. A chosen version is normalized to the `vX.Y.Z` tag; both Installers refuse an identity whose version or channel differs from the selection. A digest mismatch asks to run the Installer again, since a main build replaces its assets in place.
- `install.ps1` takes the version from the identity, downloads `vBot-<version>-windows-x86_64-<shape>.exe`, refuses it without a valid recorded digest, accepts only HTTPS `github.com` URLs (`Save-ReleaseDownload`) and requires a valid or absent Authenticode signature, then runs Inno silently with `/TASKS=startup` unless `-NoAutostart` or `-DesktopClient`. `-DesktopClient` installs the `desktop-client` shape and `-Desktop` the `server-desktop` shape; the two are mutually exclusive, and without either it installs `server`. With Autostart it then starts the tray (`vBot.exe`, which starts the server; the logon task alone would start it only at the next sign-in) and waits for `/health` (`Get-ServerHealthUrl` mirrors the CLI's server URL for wildcard and IPv6 hosts). It refuses an elevated PowerShell (`-AllowElevatedInstall` is for disposable automation), logs to an OS-temporary file that a failure preserves, and rethrows instead of `exit` when run without a script file (`irm | iex`, script block) so the caller's window stays open. Coverage: `tests/scripts/test_install_scripts.py`.
- `install.sh` needs only `curl` and `python3`: it picks `vbot-linux-aarch64-server.zip` or `-x86_64-` from `uname -m` (a 32-bit Raspberry Pi OS is refused with a hint), refuses an identity without a valid package digest before downloading the package, checks that digest, unpacks with the system Python and installs with the package's own runtime (`python3 -m cli.application.install --channel ...` plus the release public key). It links `~/.local/bin/vbot`, and unless `--no-autostart` runs `vbot autostart enable`, asks `sudo loginctl enable-linger` when lingering is off (a refusal is a warning) and starts the server. Default root `~/.local/share/vbot` (`$VBOT_DIR`), data `~/.vbot`. Coverage: `tests/scripts/test_install_sh.py` (Linux only).
- Packages are built only by CI: `windows-package.yml` and `linux-package.yml` (reusable; `release_mode`, `channel`, `ref`) build, sign and smoke them; `main-build.yml` runs on every push to `main` (except pushes that change only development documentation), calls the complete CI alongside the package builds and publishes to `main-build` only once all passed; a newer push cancels the CI and package jobs of an older run, never a publish that has started. Main packages skip the release-only Windows smokes (`release_smoke: false`: managed speech provisioning, compiled installer); `release.yml` runs every smoke and publishes a tagged release. `scripts/release_assets.py` is the complete asset contract both publishers validate: for every Windows shape and Linux platform the zip, `.sig` and runtime inventory, the Windows installers, and `vbot-release.json` naming the expected version, revision and channel. Once the set passes, `--record-digests` writes the lowercase SHA-256 digest of every other file into the identity's `assets` map as compact JSON, and refuses an identity larger than `packages.MAX_IDENTITY_BYTES` (4096 bytes; the current 18 other assets need about 2150) (`tests/scripts/test_release_assets.py`). Local `scripts/build_windows.py` / `scripts/build_linux.py` runs serve development and smoke tests; a Linux package must be built on its own architecture. `scripts/deploy_local.py` (Windows only) puts unpushed commits into a local installation for live testing: it refuses uncommitted changes to tracked files, exports HEAD with `git archive` into `~/.cache/vbot-deploy` (so ignored and untracked checkout files never ship; the checkout's verified `resources/native` is reused), builds the WebUI and the installation's shape with the dev interpreter's base CPython as runtime and channel `main`, reusing the prepared runtime of an earlier run (`build_windows.py --runtime-cache`, kept in `~/.cache/vbot-deploy/runtime-cache`: one per shape, keyed by the input runtime's files, the shape's dependency lock, the SQLite lock and the builder code; CI never uses it), and runs `<install>/vBot.exe update --package` (unsigned, otherwise the normal update with snapshot, verification start and rollback). The version id is that of the CI build of the same commit, so a later main-channel `vbot update` finds it already installed; a HEAD that is already active stops before building.
- The native Windows package smoke (`scripts/windows/smoke.py`) runs through the built `vBot.Python.exe` in its own vBot Job. That Job permits updater breakaway while the outer CI runner keeps ownership of all disposable processes; otherwise the runner's restrictive Job routes ordinary update/tray checks through WMI, which can be unavailable there. The detached-update scenario still creates and ends a separate inner Job to verify requester-independent updates (`scripts/windows/README.md`).

CI package construction and smokes run without the release private key. Each package workflow then downloads the tested files onto a fresh signing runner with only `scripts/sign_packages.py`, the installer's public identity and the signing dependency; the key is scoped to that isolated Python invocation. The signer treats archives as opaque bytes, checks the complete platform archive set and refuses a key that differs from `scripts/install.sh`'s published public key. Windows installers embed that same public key before signing. The final `vbot-*` artifacts contain the original tested files and their detached signatures; intermediate `unsigned-*` artifacts are never selected by publishers.

## Autostart and server supervision

- `autostart.py` owns `autostart enable|disable|status` for one installation root; another root's registration is never changed, and a same-named registration of another root makes `status` and `enable` fail. Windows registers a passwordless per-user Task Scheduler logon task that runs `vBot.exe` without arguments (the tray). The task script sets priority 4: the default 7 starts the whole process tree below normal with low I/O and memory priority, so Windows trims the idle server's working set and pages it back in at low I/O priority, producing multi-second Event Loop stalls with no CPU use. Every Task Scheduler call runs `powershell.exe` with a 30 s budget; the read-only ownership query (`inspect`) that `status`, `enable` and `disable` start with is asked once more after a timeout, because a cold PowerShell start occasionally hangs past it (seen in the installer uninstall smoke on CI runners), while a second timeout and every failed change refuse. The tray never restarts a stopped server.
- Linux writes the systemd user unit `vbot.service` (`$XDG_CONFIG_HOME/systemd/user`, default `~/.config/systemd/user`): `ExecStart=<root>/vbot --server --host --port --data-dir` (every argument quoted, with `%` and `$` doubled so systemd expands no specifier or variable in a path), `VBOT_LOG_STDIO=0` (the daily log is the log; the journal keeps only output that bypasses logging), `Restart=on-failure` after 5 s except for `RestartPreventExitStatus` 3 (`STARTUP_FAILED_EXIT_CODE`), 70 (`SHUTDOWN_FAILED_EXIT_CODE`, both `core/utils/server_control.py`, `server.md`) and 111 (bootstrap without a valid version), `KillMode=mixed` with `TimeoutStopSec=60` so the server shuts down its Runtime and leftover descendants are removed. A unit belongs to this installation when its single `ExecStart` runs this bootstrap (`owned_unit`). `enable` rewrites the unit only when its content differs, rolls back on a failed `daemon-reload`/`enable`, and requests `loginctl enable-linger`; a refusal leaves the registration with `attention` (the server then starts only at login). `enable` registers without starting the server. `refresh_unit` rewrites an owned unit whose content changed (for example a new bind host from `application access set`) and reloads systemd without enabling or starting anything. If reloading fails, it restores the previous unit file and reports failure; the access settings remain saved, and repeating the same access command retries the refresh.
- While `owned_unit` holds, `processes.start` (normal mode on the active version) runs `systemctl --user start vbot.service` and waits for health, and `processes.stop` runs `systemctl --user stop`, so lifecycle commands never fight the unit's restart policy. Verification starts of a candidate or previous version spawn the server directly.
- Everything left in a service's cgroup dies with the service. A process that must outlive the server it was started from (the update worker from `operations.spawn_worker`, the scheduled restart helper of `cli/server_management.schedule_server_restart`) starts through `core.utils.processes.outside_service_unit`, which prefixes `systemd-run --user --scope --quiet --collect --` when the caller runs inside a service of the user's systemd manager (`user@<uid>.service/…/<unit>.service`), the counterpart of the Windows Job breakaway. A system service such as cron or a CI runner is not one: `systemd-run --user` cannot leave it, so the process starts directly.
- A server restart the server schedules itself (`server_management._run_scheduled_restart`) and `data-store snapshot restore` route through the owning installation when `processes.owning_installation` finds one for the exact target (same port and resolved data directory): `processes.stop`/`start` under the operation lock, so a packaged server restarts through its unit or native host. Without an installation (development checkout) they use `stop_server`/`start_server`. Coverage: `tests/cli/test_server_management.py`, `tests/cli/test_data_store.py`.
- A successful registration change logs `Application Autostart enabled` / `disabled` with `mode=task_scheduler` or `mode=systemd` on `vbot.application.integration` (enable logs only when it changed the registration). The lines reach the installation's `logs/` because every dispatched command holds a `LogManager` there.

## Agent handoff

`core/tools/update_handoff.py` gives each shell Tool call with a persistence boundary an opaque in-memory token in `VBOT_UPDATE_HANDOFF`; the call itself writes no file. The token is claimable only while a process of that call may still run: the shell Tool releases it when the command's whole process tree has ended or its start fails, and a server restart forgets every token. A `vbot update` on a server-owning installation claims the token before dispatch through `application.update_handoff_mint` on its own server (`processes.target`). Only then does the server write the durable opaque ticket under `<data_dir>/runtime/update-handoffs/`, once per token, logging one INFO line with the Agent, Session and Run (never the token, ticket id or path), and the operation record stores its absolute path; the CLI still validates that path and content against the exact data directory. An unknown or released token or an unreachable server raises an `ApplicationError` and starts no update. The callback after the complete Tool batch enters Session history acknowledges the call, whether its ticket is claimed before or after that point. The worker waits for that acknowledgement (preparing phase, at most 300 s) and, through the private `application.update_continuation` RPC, which validates the saved call and Session, durably registers an idempotent once-Bootstrap before it stops the server. The stop cancels the origin Run like every other active Run (`cancel_reason` `shutdown`). The Bootstrap resumes in that Session on the next normal startup (verification starts suppress Bootstrap) and inspects the saved operation without repeating prior actions. Human/tray updates create no Agent or Bootstrap. Tickets and `runtime/update-continuations/` receipts serve one operation: Runtime start deletes those older than `UPDATE_HANDOFF_FILE_RETENTION` (7 days) and logs one DEBUG count summary that never names ticket ids or tokens. Coverage: `tests/core/tools/test_update_handoff.py`, `tests/core/tools/test_shell.py` (token lifetime), `tests/server/rpc/test_application_methods.py`.

## Optional dependencies

- User Extension sources stay in data/configured roots. `application dependencies install --requirements` replaces the complete managed dependency recipe. Resolution uses a fresh data-directory site constrained by the immutable runtime inventory. Compatible distributions are appended only at normal server startup, without executing `.pth` files; base packages cannot be replaced. Recipe changes require restart. Updates prepare the recipe for the candidate's runtime/Python-DLL fingerprint before stopping the current server. `core/extensions/dependencies.py` owns runtime activation; `cli/application/dependencies.py` owns provisioning.
- Packaged STT/TTS and local embeddings use managed user-data environments and child workers; no setup pip call mutates a released runtime. See `model_tasks/speech.md`. Extension dependency generations are not removed. Application versions referenced by a private environment or a live process survive version retention (Update operation).

## Verification and operation entrypoints

`uninstall [--app-only | --data-only | --all] [--yes]` (`command.py`): a terminal without a mode gets a menu (application only, data only, both, cancel; a Desktop Client offers only the application) and must confirm with `YES` (application only) or `DELETE` (data); anything else prints `uninstall: cancelled; no changes made`. Non-interactive callers must pass one mode and `--yes`. `integration.uninstall(mode=RemovalMode.APPLICATION|DATA|ALL)` selects one removal operation and refuses while an update is pending or when the caller's cwd lies inside the installation, resolves application and data paths and refuses overlap before any process or filesystem change, stops the exact owned server before removing anything, and guards data deletion (no filesystem root, home, or a path containing cwd). Immediately before deleting data it checks every lifetime claim through `live_server_ports`; a remaining claim on any port or an unreadable claim directory refuses deletion. Linux removes the systemd unit, the `~/.local/bin/vbot` link when it points to this bootstrap (a foreign file stays) and the installation directory directly; Windows hands application removal to the registered Inno uninstaller as follows.

Windows native uninstall also checks normalized application/data separation at `begin_removal`, then creates `removal-pending.json` under dispatch/operation locks before deleting application files. Admission verifies Inno's copied second-phase process, its exact registered-uninstaller target and its first-phase parent; only those two verified processes and the current command are exempt from the owned-process scan. The scan checks only absolute executable paths because Windows process enumeration can return non-path pseudo-process names. The second-phase PID/create-time owns the marker through actual deletion. It refuses pending updates, a server that `processes.server_state` does not find `absent` (a busy `unresponsive` one included; admission never stops it, Inno ran `server stop` before), or other remaining owned processes. The durable marker blocks update dispatch, recovery, tray start and ordinary operation mutations throughout Inno deletion; explicit stop remains available. Desktop launch holds the short dispatch lock across its guard and process creation so it cannot race this reservation. Normal Inno completion/cancel removes it. Inno's `[UninstallDelete]` removes the whole application folder, logs and locks included: installation accepts only an empty folder and keeps server data outside it, so a later install into the same folder succeeds. After an uninstaller crash, `application removal-reset` requires a dead/different PID creation identity and a verified complete active release before clearing the marker.

A packaged data-only reset (`uninstall --data-only`, `integration.uninstall`) classifies the server first: `running` is stopped, its data removed and the server restarted; `absent` removes the data and leaves the server stopped; `unresponsive` or `foreign` refuse before stopping or deleting anything, so data is never deleted under a live server. Coverage: `tests/cli/application/test_integration.py`, `test_removal.py`.

`tests/cli/application/` covers state, archives, worker recovery, CLI/tray behavior, Autostart, removal and dependencies. Server/Run/Tool tests cover authorization, durable acknowledgement, continuation and startup suppression. `tests/scripts/test_build_windows.py` covers payload/build contracts. Native/package smoke uses disposable paths and ports, with no production credentials, Autostart registrations or user installation changes. Building is not publishing; release signing credentials and external publication remain explicit release operations.
