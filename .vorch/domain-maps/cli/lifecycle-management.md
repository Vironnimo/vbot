# CLI Lifecycle Management

Task-gated reference for the local installer, self-updater, uninstaller/data-reset, and OS-autostart manager. Read this when changing those flows, their persisted `.vbot-install.json` state, or their platform plumbing - the root map carries only their contracts.

## Install (`scripts/install.sh` / `scripts/install.ps1`)

- `scripts/install.sh` and `scripts/install.ps1` are the only public installation entrypoints: they select a release or current checkout, establish an isolated checkout-local `.venv`, obtain or build the WebUI, then call the internal `scripts/setup.*` helper for package/data/autostart configuration. Fresh installer-owned clones carry `.vbot-install-root` and are deleted wholesale on uninstall; installs in an existing checkout carry `.vbot-install-venv` and remove only the managed environment and launcher. `cli/install_state.py` owns the versioned, checkout-local `.vbot-install.json` manifest used by setup, updater, and uninstallers: it atomically persists the install shape (`server`, `server-desktop`, or `desktop-client`), exact dependency groups, the absolute Python entry point, source track, applied revision, dependency/WebUI digests, and the complete host/port/data-dir target - install-management state, not runtime configuration (no credentials, git-ignored).
- The Windows installer exposes `vbot` through an installer-owned `bin/vbot.cmd` invoking the Python module entrypoint rather than pip's replaceable `vbot.exe`, so the launcher cannot lock itself during an update; the Desktop shortcut is created only for Desktop shapes and points at the windowless GUI launcher. Both uninstallers remove per-user Desktop artifacts only for Desktop-bearing installs, judged from the recorded shape.
- The public installers refuse an elevated process so checkout, environment, data, and server stay user-owned (`-AllowElevatedInstall` is for disposable automation), show only high-level phases while capturing internal output in an OS-temporary log that failures preserve, and for server shapes independently verify actual vBot health plus Autostart before printing `vBot is ready`.
- Uninstallers still recognize retired pre-manifest markers so an older installed release remains removable after updating - removal tooling is the one sanctioned legacy-tolerance surface.

## Update (`update`)

- `update [--host] [--port] [--data-dir] [--discard | --stash] [--no-restart] [--service-name]` is a local self-updater (`cli/update_management.py`) for git-based installs. It preserves the recorded install shape, dependency groups, Python executable, and server target from `.vbot-install.json`; each explicit target flag overrides only its matching recorded field.
- Branch installs use `git pull --ff-only` and `npm ci`; detached release installs preflight the latest tag's WebUI bundle before changing the checkout. Dependency and WebUI steps carry persisted digest/revision markers so either step can retry after a partial failure even if Git already advanced.
- Tracked changes require `--discard` or `--stash`; `--stash` snapshots to a unique temporary Git ref that is kept on conflict, so a concurrent ordinary stash cannot change which snapshot is applied.
- On Windows the updater refuses mutation while the environment-local `vbot.exe`/`vbot-desktop.exe` launchers are running (with a source-based resume command), migrates the installer-owned shortcut/launcher after success, and fails the update when a required Desktop launcher or shortcut write is missing.
- WebUI assets swap as a wholesale staged `dist` replacement with the previous dist restored on failure; Desktop Client installs skip WebUI work and server restart. Only after all managed steps succeed does it record the applied revision and restart a server installation through the shared systemd-aware path.
- In a Bash-injected vBot Run context the public invocation stays exactly `vbot update`: a detached helper outside the old server's process containment strips all `VBOT_RUN_*` environment, waits for the outer launcher, performs one normal restart, and exits. It never touches the data dir; external git/pip/npm/PowerShell calls have bounded timeouts and disable interactive credential prompts.

## Uninstall (`uninstall`)

- `uninstall [--app-only | --data-only | --all] [--yes] [--host] [--port] [--data-dir] [--task-name] [--service-name]` owns the local removal/reset orchestration in `cli/uninstall_management.py`. A TTY caller with no mode gets a four-choice menu; non-interactive callers must provide one mutually exclusive mode and `--yes`.
- Target resolution: the recorded server target in `.vbot-install.json`, then normal Config resolution, with explicit flags winning; a Desktop Client without an explicit target removes only the accessor installation, while data-only requires `--host`, `--port`, and `--data-dir` together.
- Data-removing modes show the exact resolved path and require `DELETE` unless `--yes`; guards refuse filesystem roots, the user home, a path containing the installation, and a path containing the caller's cwd (application removal also refuses when cwd is inside the installation).
- Data-only stops the target, deletes its directory, and restores the prior running state (systemd-aware). Server-owning application-removing modes synchronously stop the exact selected server before cleanup and abort without handing files to a remover when that stop fails.
- Linux replaces the CLI process with `scripts/uninstall.sh`; Windows launches an elevated helper after UAC and explicitly distinguishes successful helper launch from completed removal.

## Autostart (`autostart`)

- `autostart enable | disable | status [--host] [--port] [--data-dir] [--task-name] [--service-name]` is a local OS-autostart manager (`cli/autostart_management.py`), OS-branched: Windows Task Scheduler logon task, Linux systemd **user** unit + login lingering.
- Registration is passwordless per-user without elevation and distinguishes a genuinely absent task from Scheduler failures. The task invokes the environment's `vbot-autostart` GUI-script launcher (delegating to `server start` with suppressed console output; the Windows launcher allows longer cold-start readiness with bounded launch retries).
- Linux unit paths are constructed only after the restrictive shared service-name validation, and an enable failure rolls the prior unit back. Generated units use `KillMode=mixed` so systemd signals the main process for normal Runtime teardown and removes remaining descendants after `TimeoutStopSec`, including after a crash.
- Failures are never masked as success: disable checks `systemctl`/reload failures instead of deleting the unit and claiming success, status reports unknown states as failures, and a failed linger request is a warning that boot-before-login is not guaranteed. `enable` registers autostart and requests a start now; `disable` leaves an already-running server alone. The installers call `vbot autostart enable` by default (`--no-autostart` opts out).
