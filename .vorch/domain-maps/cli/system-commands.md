# Provider, Model, Channel, Extension and System Commands

Supplementary to `cli.md`. Covers the command shapes and output of the `provider`, `model`, `task-model`, `channel`, `extensions` (including Extension management operations), `prompt`, `log`, `config`, `doctor`, `tool`, `debug`, `performance` and `statistics` areas.

## Provider area

- `provider list/status` read `connection.list` and group readable Connection states under Provider headings, retaining exact ids and Account names in the overview; `list --details` and `status` include type, enabled/usable/reachable and Account source sub-lines. Configured is enabled plus credentialed, not a live upstream access check. `provider usage` prints live subscription plans; `provider history list [--since] [--until]` and `provider history clear --yes` (aliases of `usage-history` / `usage-history-clear`) read or delete the Provider-owned durable observations - separate from Session statistics.
- Provider commands that also take `--connection` accept a Connection id as `provider list` prints it (`provider enable ollama:local`) as their positional target (`cli/_dispatch_connections.py::_accept_connection_target`).
- `custom-save` replaces the Custom Provider record's endpoint, auth, discovery path and Model list; it first reads `provider.custom_list` and carries over what its options cannot express - `defaults`, the stored record of every Model id still listed, and the `wire` block unless `--wire-file <path>` (a JSON object) replaces or `--clear-wire` removes it; repeated `--model` values create conservative manual chat Models, and the optional key is write-only - output never echoes it.
- `enable|disable` is the connection switch: keyless local providers start disabled, multi-connection providers require `--connection` (candidates listed on failure), enable probes local auto-refresh reachability and points to connection status/authentication when no credential exists.
- `set-key <id> (<api-key> | --stdin) [--connection] [--account] [--refresh-models]` writes the resolved account's derived credential to the data-directory credentials (Secret Store, `secrets.md`), reloads runtime credentials live, rejects OAuth connections, and never returns or prints the secret (why it accepts a direct value: `cli.md` -> Constraints & Gotchas); `--refresh-models` chains a provider-scoped Model DB refresh after success. Discovery errors make the overall command fail while retaining the successful credential-write result; retry guidance does not resend the key. `custom-save --api-key-stdin` offers the same UTF-8 secret input route. `unset-key` reports when an account is still configured via the process environment.
- `connect`, `connect-status`, and `disconnect` allow omitted `--connection` only when `connection.list` identifies exactly one OAuth Connection on that Provider; ambiguity lists candidates before any mutation. `connect` starts the OAuth device flow, printing `user_code`, `verification_uri`, expiry, and the follow-up `connect-status` command; the server polls in the background, so the CLI stays non-interactive. All credential commands accept `[--account <account-id>]` and render the resolved account - semantics in `providers/connections.md`.

## Model and task-model areas

- `model list` exposes Provider/capability/task/modality/minimum-context filters; the server includes only Models with at least one usable Connection. `model list --task chat` is the primary recovery/discovery command for an Agent without an effective Model. `model show` prints the complete loaded projection as deterministic JSON.
- `model forget-wire-facts <provider>[/<model-id>] [--connection <id>]` calls `model.forget_wire_facts` and reports how many (Connection, Model) targets lost what live traffic taught (`providers.md`).
- `model refresh [<provider-id>]` stages a copy of the effective Model DB, refreshes requested Provider projections, atomically publishes the fetched catalogs under `<data_dir>/artifacts/models/`, and never writes the bundled `resources/models/` root. `scripts/refresh_model_db.py` is the maintainer-only client for the tracked `resources/models/` root; the RPC rejects cross-checkout targets. Snapshot mechanics live in `models.md`.
- `task-model` validates `<task-type>` locally against `SUPPORTED_TASK_TYPES`; `options` prints the schema plus configured/effective values; `set --option` and `set-option` read each value as its field's declared type from `task_model.options` (select/text keep the text, so a duration choice `8` stays `"8"`; boolean words `true/false/yes/no/on/off/1/0`; other fields JSON with a text fallback); `set-option --stdin` carries JSON values without shell-quoting loss; every successful mutation prints the saved binding; `clear` sends an empty target.

## Channel area

- `--platform` accepts `telegram`, `discord`, `slack`, `mattermost`, or `whatsapp`; `--response-mode`/`--observe-unaddressed` expose the Channels-owned group-gating policy. `channel identity/access/grant-admin/revoke-admin` manage the Channel account identity and saved group roles (additive, idempotent mutations). `channel status` prints enabled/running/failed plus failure reason and denied inbound chats with an allowlist suggestion. Group-policy semantics live in `channels.md`.
- Except WhatsApp, add requires exactly one bot-token source: recommended `--token-stdin` sends the UTF-8 value as a write-only managed token; `--token-env` references an externally managed variable name, never a token. `set-token <id> --stdin` rotates the credential and prints non-secret source/applied state, targeted-adapter restart decision, immediate health, and a verification command. Managed setup and rotation read token values only from stdin and send them only to `channel.create`/`channel.set_token`.
- Slack adds `--app-token-env` and `channel token set --slot app --stdin`; Mattermost adds `--server-url`. `channel add --disabled` saves credentials/configuration before starting a connection. WhatsApp add always starts disabled without a token; `channel whatsapp setup|status|pair <id>` uses service-owned asynchronous setup and pairing. The private QR is visible only in Settings > Channels, never CLI output. Setup failure or revoked pairing is an attention result. Platform setup instructions: `USAGE.md` -> Channels and bundled `vbot-docs/references/channels.md`.

## Extensions

- Action-first routing: static actions (`list`, `reload`, `enable`, `disable`, `show`, `set`, `operations`, `run`) are discoverable subparsers. `run <name> <operation>` preserves opaque operation arguments after the operation; vBot target/output options precede it. Legacy name-first calls remain accepted and normalize to the same `selector` + `rest` dispatch contract; follow-up commands vBot prints (the waiting-for-configuration line, the operation catalog's `next`, the secret-path settings refusal from `server/rpc/settings_methods.py`) name the action-first forms (`extensions show <name>`, `extensions set <name> <field> ...`, `extensions run <name> <operation> --help`; tests: `test_extensions_list_marks_tools_waiting_for_configuration`, `test_catalog_is_bounded_and_operation_help_keeps_the_complete_schema`). `reload` performs the full restart-equivalent rebuild and prints count summary plus per-failure lines and a follow-up pointer when anything failed.
- `enable|disable <name>` read the persisted `extensions` section from `settings.values` and write the complete section back through `settings.update` with what they read as `base`; on `settings_conflict` they read again and retry, at most three writes, then fail with the conflict and its recovery guidance. Both apply live without restart. Enabling re-lists and fails if the freshly rebuilt extension did not load or verification failed, preserving the saved switch result. Reload likewise fails when any extension failed.
- `show <name>` shows one extension's settings: each schema field with type, description, options/constraints, and current value, secrets only as `set`/`not set` (schema-less falls back to raw config). `set <name> <field> <value>` routes by declared schema type: a `secret` field calls `extensions.set_secret` (caller names the schema field key; server maps it to the declared `env_key` credential), anything else is coerced to its declared type and written as that one field through `settings.patch` (`extensions.config["<name>"]["<field>"]`), so concurrent changes to other settings stay. `--stdin` reads the value out of shell history; an empty value clears a secret. Unknown extension/field get candidate + did-you-mean output.
- Extension operation arguments remain opaque to the static parser and receive schema-based diagnostics in `extensions_management.py`. Leading options never enter an Extension operation payload.

## Extension management operations

`extensions operations <name>` and `extensions run <name> <operation> --help` (name-first `extensions <name> operations` and `extensions <name> <operation> --help` remain accepted) discover management operations introduced in API v4 through `extensions.operation`. Catalog output contains names, descriptions, secret-input markers, and a pointer to per-operation help; only that help prints the complete argument schema. Dynamic operation flags are forwarded in order while `--host`, `--port`, and `--data-dir` remain accessor-owned. The first bare argument fills `id`, `request_id` or `job_id`, else the first document property. A document property (a string with `contentMediaType`, such as MCP `import`'s `source`) takes a file path, or `-` for standard input (not together with `--stdin`), and sends the file's UTF-8 text, so setup text that may hold secrets never enters shell arguments; an unreadable file fails without repeating the given text (`test_document_argument_is_read_from_a_file_or_standard_input`, `test_unreadable_document_argument_is_not_echoed`). Secret operations require UTF-8 JSON on stdin; the generic parser does not echo their values. Long operations return job ids with explicit terminal states and a cancellation operation. Existing Extension settings commands keep their original grammar. Source: `cli/parser.py`, `cli/extensions_management.py`; tests: `tests/cli/test_extensions_operations.py`.

The MCP `explore` management operation offers the search/describe/call actions of its stable connection Tool through asynchronous jobs. It runs outside a Session, so its job result holds the complete payload inline and it has no `read`; the CLI and Agent Tool share access checks. Exact protocol `invoke` remains available and also returns inline. Feature contracts and regression pointers: `extensions/mcp.md`.

## Prompt, log, config, doctor and tool

- `prompt` commands accept `--scope default|agent:<id>`; the default object is omitted toward the RPC because the server defines it. `show <block-id>` prints one complete block with scope and metadata before replacement. Layout is locally shape-checked JSON; preview prints text plus Tool-definition token metadata.
- `log list|read` map to their RPCs - the CLI must never read `<data_dir>/logs/` directly. `log read <daily-log-name>` filters exact `--level` and prints the last `--limit` entries (100 default, 0 all) with counts; `log.read` returns one page, so the CLI filters each page locally and reads older pages (`before` = `next_before`) until `--limit` entries match or the file start (`N+` counts when it stopped early).
- `config` is the public Settings-path catalog: `describe/get/set/unset/patch` map to `settings.catalog/get_path/patch`. Patch operations form one atomic mutation (invalid/overlapping persist nothing); values are JSON-decoded before string fallback; dynamic keys are bracketed JSON strings. Mutation output reports active value, pending restart value, application lifecycle, and aggregate `restart_required`. `config effective` prints `settings.values`; `config raw` is the diagnostic-only internal document. `config set --stdin` accepts exact UTF-8 JSON and rejects malformed JSON before RPC. Secrets stay on their dedicated commands.
- `doctor settings|config [--data-dir]` run locally without a reachable server: strict `settings.json` validation, respectively whole-bundle discovery delegating each file to its owning domain. Missing files report OK when defaults apply; diagnostics render as severity, JSON path, message. An Agent of the user that holds the id `librarian` gets a warning at `$.id` saying the built-in Librarian is unavailable and how to rename it (`agent.md` -> Built-in Librarian). Doctor commands accept only `--data-dir` because they are local file validators.
- `tool list` prints registered public Tools.

## Diagnostics areas

- `debug trace <trace-id>` prints the full sanitized trace as sorted JSON; `probe` prints status/duration/trace id plus model preview and never dumps raw responses (points at `trace`). Listing/probing fail server-side while Debug Mode is disabled; `status`/`clear` always work.
- `performance status` summarizes `performance.snapshot`: recording state, key gauges, the top 10 metrics by p99 and by total time, the 10 largest counters, and the 5 newest stalls (duration, `gc_ms`, loop CPU over the CPU window, sample count) with the top frames of their most frequent stack and of the Tasks awaiting the Task the loop ran (`awaited by`), plus up to two busy other threads with their CPU and top frames. `performance record start [--label <text>] [--max-seconds <n>]` (default 300) and `record stop` control the single Recording; stop prints the trace path and a `https://ui.perfetto.dev` hint. `recordings [--limit <n>]` lists stored Recordings newest first. `history [--hours <n>] [--metric <name>]... [--at <time>]` reads `performance.history`: by default one health line per window of the last 24 hours (maximum RSS, CPU and active Runs, `event_loop.lag` p99, `gc.gen2` count and maximum, stall count), with `--metric` those metrics, counters or gauges per window, and with `--at` the full windows containing that time (top metrics, counters, stalls). Times print in the CLI host's local time like log lines; an `--at` time without an offset is read as local time. A `server started` line marks each new server process. `heap [--top <n>]` (default 20) prints a Heap Census: tracked objects per generation, frozen count, the largest types and modules and, from the second census of a server process on, the largest growth since the previous one. RPC contract and metric catalog: `performance.md`.
- `statistics <section>` (`overview`, `usage`, `runs`, `compactions`, `errors`, `tools`, `skills`) makes one `statistics.report` call that requests only the report section it renders (`compactions` reads `diagnostics.compactions`, `errors` reads `runs.errors`) and prints deterministic compact text with explicit empty states and `-` for unknown values; ranked lists are capped (20 rows, 10 Runs). `--since/--until` pass through verbatim (the server validates ISO-8601 and window order, floors `since` and ceils `until` to the hour, and the output echoes the effective window); the CLI sends no `timezone`, so day buckets use the Settings time zone; it prints no series. Section fields: `statistics.md` -> Report sections. Tests: `tests/cli/test_cli_statistics.py`.
