# Packaged Windows Application

Read for native distribution, tray/lifecycle integration, transactional updates, and managed local code or Extension dependencies. `cli/application/` extends CLI lifecycle ownership because its state and update worker must remain available when Runtime is stopped. It does not own business configuration or Sessions.

## Layout and native boundary

- `<install>/vBot.GUI.exe` is the stable Windows GUI companion used by the Desktop shortcut with `desktop`. It resolves `active-version` on each launch and shares CLI/Desktop dispatch without allocating a console. The console `vBot.exe` keeps terminal output and wait semantics. Both remain protocol-1 bootstraps; installer/update integration adds a missing GUI companion and updates only the standard shortcut pointing to this installation with exactly `desktop`, preserving foreign/customized links and existing bootstraps.
- The exact `vBot.GUI.exe desktop` shortcut enters `cli/main.py` without loading the console parser or server services. `cli/application/desktop.py` owns the shared launch used by this entry and the tray facade, retaining installation discovery, active-version resolution, recorded/explicit target handling and the removal-admission lock. It passes the Desktop its relaunch contract (`VBOT_DESKTOP_RELAUNCH`: `active-version` path, running version id, stable bootstrap command) so an open Desktop can restart into a newly activated version (`desktop/update-restart.md`). Other arguments use the complete CLI parser/output path. This is a payload-only optimization; existing protocol-1 GUI bootstraps need no replacement. Fresh-process import and failure coverage: `tests/cli/test_startup.py`; launch/lock/target coverage: `tests/cli/application/test_host.py`.
- `<install>/vBot.exe` is the stable native bootstrap. No arguments starts the per-user tray host; arguments dispatch CLI commands. Native role hosts run CPython in-process: `vBot.Server.exe`, `vBot.Desktop.exe`, `vBot.Update.exe`, and `vBot.Python.exe`. Desktop is optional and independent of server lifetime.
- `vBot.Server.exe` uses the console subsystem. Managed starts in `processes.py` use `CREATE_NO_WINDOW`, providing an attached, windowless console; foreground customization tests inherit the caller's console. Do not build the Server as a GUI executable: Windows ignores `CREATE_NO_WINDOW` for it, so pywinpty's ConPTY setup can allocate a visible console before hiding it. Native-host coverage in `tests/scripts/test_build_windows.py` checks the windowless console across real PTY start/close cycles. Desktop and the GUI bootstrap keep the Windows subsystem.
- Both native manifests declare PerMonitorV2 and Windows 10/11 compatibility. Desktop retains its separate manifest and WinForms opt-in (see `desktop.md`).
- The tray host (`host.py` facade, toolkit-free `tray.py` controller, Win32 view in `windows_tray.py`/`windows_status.py`) follows its server through one `/ws` connection as accessor `tray` (`monitor.py`) and raises toasts (`notifications.py`); it has no third-party UI toolkit. Invariant: an idle tray does no periodic server I/O and its 1 s `facade.state()` poll stays cheap, so never add network, process or full-directory work there. Tray status uses a cached human release version and a separate short state line, never an entire operation message. Details -> References.
- Packaged server start/stop/restart/status use the shared CLI progress, result renderer and exit-code policy. Native startup results carry health and WebUI facts so successful startup never renders as stopped. Packaged `server status` uses the shared CLI status renderer and exit-code policy, including structured running, URL, WebUI, data-directory and log-path fields and a successful exit for a reported non-vBot listener conflict.
- The running server reports its build from these records (`runtime.md` -> `build`): `core/utils/version.py` reads the version's `release.json` `revision` and treats a manifest without `official_base` as an official release, otherwise naming the `branch` of `source-update.json`. Keep those fields' meaning when changing either record.
- `application.json` records schema, shape, exact server target and release trust; `active-version` atomically selects `versions/<safe-id>`. Each version contains `app/` readable runtime sources/resources/built WebUI and `runtime/` private CPython 3.13/dependencies, plus a complete `release.json` inventory. Standard payload collection excludes checkout metadata, tests and build tooling. Main installs retain a separate `<install>/source` Git checkout; explicit customization uses `development/source`.
- Bootstrap protocol 1 is immutable across ordinary updates. An incompatible release fails validation before activation and needs a new installer. Native paths are isolated from ambient Python environments; application code does not write bytecode into releases. Native hosts explicitly enable Python UTF-8 mode so redirected CLI output and Agent Tool results preserve Unicode independently of the Windows code page.
- Server payload collection includes the private, digest-locked ripgrep/PCRE2 executable and third-party notices. `payload.py` reuses verified source/base assets or provisions the locked Windows x64 archive before inventory generation. Desktop-client excludes native search assets. See `tools/search_files.md`.
- Every prepared runtime replaces `runtime/DLLs/sqlite3.dll` with the official sqlite.org build pinned in `scripts/windows/sqlite.lock.json` (archive SHA3-256 plus library SHA256), so the database kernel's journal policy selects WAL for every packaged database (`database.md` -> Conventions). `runtime_sqlite.py` owns this stdlib-only step for both the release builder (`copy_runtime`) and local candidates (`customize._candidate`), before inventory generation. A library already matching the pin is kept; otherwise the archive is downloaded without ambient proxies and verified before an atomic replace. A source without the lock leaves the runtime unchanged. The step runs for every candidate, independent of the dependency fingerprint. Candidate preparation executes the active version's code, so the update that introduced this step still produced a CPython-bundled library; later pin changes apply on their first update because the lock is read from the new source. `smoke.py` asserts the pinned version. Coverage: `tests/cli/application/test_runtime_sqlite.py`, `test_customize.py`, `tests/scripts/test_build_windows.py`.
- Source: `state.py`, `packages.py`, `payload.py`, `retention.py`, `scripts/build_windows.py`, `scripts/windows/native_hosts.py`, `scripts/windows/launcher.c`, `scripts/windows/vbot.iss`. The three shapes are server, server-desktop and desktop-client. A client never probes, snapshots or stops a default local server.
- `install.py` rejects equal or nested application/payload roots in either direction after resolving paths, before source-transition shutdown or filesystem mutation. Coverage: `tests/cli/application/test_install.py`.

## Update operation

- Windows release and main installations use the same native hosts, tray and durable updater. `install.ps1 -Dev` installs a verified release base without startup, selects main with `application source main`, runs the normal update, then enables requested Autostart. Failure leaves the complete base installation and failed operation available for retry. `-SourceCheckout` and current-checkout setup remain source-only modes.
- `source_updates.py` owns `source-update.json`, recording an exact Git root, remote and branch. `application source main [--from-checkout]` selects it without activation; `application source release` removes only the binding and preserves source files. Selection refuses pending updates. `application status` exposes the selected update source. A transitioned branch installation retains its recorded branch instead of silently becoming a release installation.
- Bound updates fetch their recorded upstream, fast-forward when possible and retain clean local-ahead commits. Dirty work, branch changes and divergence stop preparation without discarding source or stopping the running version. Main preparation uses the shape's hashed Windows dependency lock without running repository checks or committing source; exact HEAD and cleanliness are checked again before accepting the candidate. `build_inputs` in the candidate manifest records the runtime recipe and tracked WebUI/Extension page inputs. Unchanged runtime dependencies are copied concurrently, never hard-linked; unchanged generated assets come from the verified base, including complete Extension page trees. A WebUI rebuild runs `npm ci` only when `webui/package-lock.json`, `webui/package.json` or the Node.js version differ from the last successful install, recorded in `webui/node_modules/.vbot-npm-ci` (which `npm ci` itself deletes first); a build that fails with reused packages is retried once after a clean `npm ci`. `cli/webui_build.py` owns this policy for both source-update paths (`tests/cli/test_webui_build.py`); `customize._build_web_assets` supplies npm and the Node.js version. Missing provenance requires one fresh build. Changes to the runtime provisioning recipe must invalidate its fingerprint. Native-host compilation runs in the private build environment with only the Python standard library and the external compiler/SDK; importing its build helpers must not load application dependencies or search provisioning. Native input fingerprints avoid recompiling unchanged hosts; changed native inputs require LLVM (`clang-cl`, `llvm-rc` on PATH) and the Visual Studio C++ build tools with the Windows SDK. A source update compiles changed hosts first, before the WebUI and dependency work, into a temporary directory that `customize._candidate` copies over the base runtime's hosts; a failure (`customize._build_native_hosts`) names that toolchain and the log, leaving the running version unchanged. `install.ps1 -Dev` only warns when `clang-cl` or `llvm-rc` is missing (`Confirm-NativeBuildTools`), because unchanged hosts need no compiler. `payload.NATIVE_SOURCE_FILES` names those inputs: the launcher sources, manifests, icon and `scripts/windows/native_hosts.py`, which owns the complete compile recipe (host roles, stable bootstraps, compiler and linker flags), so edits elsewhere in the release builder never recompile hosts. Keep every output-affecting compile detail in that module. `scripts/build_windows.py` re-exports `HOSTS` and `compile_host` because updaters of earlier versions import them from there against the new source. The stable root bootstrap remains protocol-bound and installer-owned.
- An unchanged Main revision, build inputs and native inputs without managed customization state returns the verified active version. It checks Extension dependency compatibility and completes without a snapshot, maintenance admission, Agent continuation or restart, including with `--no-restart`. Managed customization reconciliation remains on its existing validation path.

- Human CLI, tray and Agent CLI call `operations.request_update`. Atomic records under `operations/` contain phases, identities, result and exact worker PID/create-time. Only equivalent pending requests coalesce. The short dispatch lock protects worker handoff; the OS-owned operation lock covers the entire mutation, also excluding manual lifecycle and customization changes. Every CLI command dispatched on an installation (`command.dispatch`) holds a `LogManager` on `<install root>/logs/` for its duration, like the host and worker, so its lines are kept (`tests/cli/application/test_command.py`). `Operation.transition` logs each phase change once on `vbot.application.update` (`<install root>/logs/`) with the operation id, kind (`package` or `online`), from/to phase and version ids: INFO, `failed`/`rolled_back` WARN and `needs_attention` ERROR carrying the saved error; progress within a phase is DEBUG. The worker adds the data-rollback outcome (restored or not restored at WARN, not needed at INFO); a version cleanup that keeps every version or defers a tree is WARN (`tests/cli/application/test_worker.py`).
- `_output.py` owns readable native update outcomes alongside source-update rendering; both use `_progress.py` status markers and elapsed-time heartbeats. Native updates opt into one transient progress line on capable terminals; captures remain append-only and a new phase resets its heartbeat deadline. The source and target release versions include short Git revisions and the target is announced as soon as resolved. Worker messages distinguish fetching, building, dependencies, verification and data snapshots. Display labels are stored under `operations/details/`, outside the protocol-1 transaction record so still-running prior-version consumers can read it. Native default output has no raw phase prefixes or trailing JSON; a terminal result states its total duration from request to saved outcome (`created_at`/`updated_at`). Explicit `--output plain` retains one structured operation result, and `update status` remains a read-only structured inspection. Prepared/detached/handoff outcomes retain the exact status or activation command and never imply completed activation. The PowerShell installer preserves these shared status labels while retaining full diagnostics in its log.
- All background Git, dependency, build and Autostart subprocesses use the shared windowless creation flags, including compiler descendants. Foreground customization test instances retain their terminal. Native CLI/Server/Update startup failures write stderr and exit instead of waiting on a modal dialog; tray/Desktop GUI launches may display a dialog. Early child errors are captured under application logs: the packaged server start (`processes.start`) runs the child with console logging off (`VBOT_LOG_STDIO=0`), so `<install>/logs/server-startup.log` receives only output that bypasses logging, such as a crash before logging starts; at the next start a file over `STARTUP_LOG_ROTATE_BYTES` (1 MiB) moves to `server-startup.log.1`.
- A human `vbot update` normally waits for terminal state and returns nonzero on failure. `--detach` returns acceptance. `--no-restart` produces terminal `prepared`, leaves the pointer unchanged, and requires `update activate <id>` later. A dead caller cannot cancel the worker. The waiting CLI, an equivalent repeated update request, or tray startup can recover an orphan by reconciling its saved phase; `update status` only reads saved state.
- Official archive signatures are Ed25519 over the raw SHA256 digest, verified against the install's public key. Deliberately supplied `--package` artifacts can be local/unsigned. Extraction rejects unsafe paths, special files, case collisions, invalid shape/platform/protocol and inventory mismatches before activation. Payload verification scans entries without following links/reparse points, checks the exact inventory and hashes every file; it does not repeatedly resolve each file's ancestors. Payload files are hashed and copied by `packages.FILE_WORKERS` concurrent readers: Windows scans every newly written file on its first open, which made sequential hashing of a fresh candidate the slowest update step. A digest mismatch names the first differing file in inventory order. An inventory mismatch names up to three unexpected and three missing paths.
- Stray bytecode: running a version's `runtime/python.exe` directly (also through a venv based on it) writes `__pycache__/*.pyc` into the verified version. Native hosts pass `-B`, which stops writes but not loads, so such caches are deleted, never ignored. Call sites that verify an already installed version (active/base, candidates, removal-reset, re-staged identity, archive export) pass `validate_release(..., remove_bytecode_caches=True)`: uninventoried files named `*.pyc` or `*.pyc.<digits>` (interrupted cache writes) directly inside a `__pycache__` directory are removed with a warning on `vbot.application.packages` before the exact check. Any other difference still fails, an undeletable cache fails with an actionable error, and inventoried bytecode is hashed like any file. Fresh builds and extractions stay strict. Because candidate preparation runs the active version's code, only updates started from a version containing this removal benefit; an older active version fails such an update with "Release file inventory does not match its payload". A runtime-level write block is not viable: the `encodings` imports precede `site`, and `._pth` has no bytecode switch.
- `worker.py` prepares a version and carries local commits/dependency recipes forward before stopping anything. It then classifies the server once with `processes.server_state` for the previous version (states below). Only `running` obtains server-owned maintenance admission, drains accepted work and stops the exact server. `absent` stops nothing; the snapshot's claim check proves that no server started since. `unresponsive` ends `failed` before any drain, stop, snapshot or activation: the server keeps running, the previous version stays active and the message asks to retry once the server responds; `foreign` also fails there, through the generic error path. `server_was_running` records liveness (`running` or `unresponsive`), so an update never leaves a server stopped that ran before it. The worker runs the previous version's code, so this classification protects the updates started from a version that contains it. After the stop it takes the update snapshot (`database.md` -> Update snapshot) offline and keeps it in memory; the Operation record gains no field. The worker runs the previous version's code, so it passes `canonical_database_specs(data_dir)` to the snapshot and the rollback: core owner facts are recorded and verified (Extension databases by identity and integrity only). Before the snapshot and again before the candidate starts, no server may still claim the data directory (`live_server_ports`, re-checked for up to `_CLAIM_SETTLE_SECONDS` because Windows can release an exited process's lock late; a failed check counts as a claim), and the data must still match the snapshot's stamp. A snapshot or fence failure restarts the previous version if it was running and ends `failed` without activation. Then it probes the candidate with `--verification-only`, changes the pointer and verifies required normal startup. Candidate failure can retain previous code only after previous startup verification. Recovering an interrupted `stopping`/`activating` operation whose previous version is still active stops an answering candidate verification server, releases a living previous server (`running` or `unresponsive`) from this operation's maintenance, and starts the previous server only when it is `absent`, so a busy server is never duplicated; an `unresponsive` verification server, or a `foreign` occupant where the previous server has to return, makes the operation `needs_attention`. Coverage: `tests/cli/application/test_worker.py`.
- Version retention (`retention.py`): after a `completed` operation, still under the operation lock, `retire_unneeded` renames every complete version (one with `release.json`) outside the needed set to `staging/retired-*`, together with every download directory whose operation is not unfinished. `worker.run` deletes these trees with `remove_retired` only after releasing the lock. A tree that cannot be renamed or fully deleted is retried by the next cleanup. The needed set contains:
  - the active version;
  - the versions named by every operation newer than the last one that changed the active version, that operation's own previous and candidate versions (the known-good fallback), and every unfinished operation;
  - the `*_version` fields of the customization state, including `pending_rebase`;
  - the `home` version of each `development/*/pyvenv.cfg` and of each managed speech environment, because such a venv breaks when its base runtime disappears;
  - every version a running process of this installation uses: its executable, or, for a root bootstrap, a loaded module. The tray host keeps running from its start-time version until its restart handoff, which the user's interaction with the tray can defer.

  A vBot-named process that cannot be inspected, or an unreadable record, keeps every version. Cleanup never changes an operation's outcome. The worker runs the previous version's code, so cleanup begins with the update after the one that installs it. Coverage: `tests/cli/application/test_retention.py`, `test_worker.py`.
- Long-lived clients switch to a newly activated version by restarting at a safe point: the tray hands over to a successor started through the stable bootstrap while the server keeps running (`cli/windows-application/tray.md` -> Restart after activation); the Desktop has its own restart handoff (`desktop/update-restart.md`). Completion texts for a Desktop Client (`worker.py`, `operations.result_summary`) say that an open Desktop switches by restarting.
- Data rollback (`roll_back_data`) runs only after a failed candidate verification start and before the previous version is probed: with no server claim left and the data changed since the stamp, it calls `restore_update_snapshot`. A refusal restores nothing and the `rolled_back` message says so and why; unchanged data needs no restore; a restore that started but failed raises, so the operation becomes `needs_attention` naming `vbot data-store snapshot restore <id> --all --yes`, and the maintenance guard keeps every version off the half-restored data. After the candidate verified, the snapshot is stale and never restored automatically, including when normal startup after the pointer change fails. Recovery of a lost worker never restores; an incomplete maintenance guard in `stopping`/`activating` becomes `needs_attention` (with the repeat command when this operation's snapshot exists). Residual risk: a foreign writer that exits while the candidate runs is indistinguishable from the candidate. Ambiguous recovery becomes `needs_attention`. Coverage: `tests/cli/application/test_worker.py`.
- `processes.server_state(install, version_id=, verification=)` is the one classification of the installation's server for an exact version and startup mode: `classify_server` (`cli.md` -> Health outcomes) with the recorded process narrowed to that version's native executable and `--verification-only` or normal mode. Identity and liveness come from the control record (PID plus creation time), health from `probe_health_patiently`, never from one 0.5 s probe. `running`: that exact process answers `/health`. `unresponsive`: it lives but does not answer (busy Event Loop, still starting, already stopping; the control record exists before the listener). `foreign`: anything else holds or answers the target (another version or mode, a live process that cannot be inspected, another data directory's vBot, an unidentified listener). `absent`: no live recorded process and no listener. `processes.start` spawns only on `absent`; `unresponsive` fails with `the server process is running but does not answer its health check`, the others keep `already running` or the occupied conflict. Its readiness loop uses the quick probe. The data-only reset and removal admission (Verification and operation entrypoints) decide through it as well. Coverage: `tests/cli/application/test_processes.py`. Dispatch detaches the updater from vBot's lifetime Job once; the updater owns no Job and starts its verification/recovery/normal servers without requesting another breakaway from ambient Windows Jobs. Direct lifecycle starts and dispatch use the shared immediate-Job policy in `core.utils.processes` (see `tools/process.md`), preserving a restrictive external ancestor while escaping vBot's own Job. `core.utils.server_control.server_control_claim` prevents competing starts from replacing live shutdown authority. Its per-data-directory/port OS lock spans control publication through final cleanup.

## Agent handoff

`core/tools/_bash_update_handoff.py` gives each Bash call with a persistence boundary an opaque in-memory token in `VBOT_UPDATE_HANDOFF`; the call itself writes no file. The token is claimable only while a process of that call may still run: Bash releases it when the command exits or its spawn fails, and a server restart forgets every token. A packaged `vbot update` or `vbot customize activate` on a server-owning installation claims the token before dispatch through `application.update_handoff_mint` on its own server (`processes.target`). Only then does the server write the durable opaque ticket under `<data_dir>/runtime/update-handoffs/`, once per token, logging one INFO line with the Agent, Session and Run (never the token, ticket id or path), and the operation record stores its absolute path; the CLI still validates that path and content against the exact data directory. An unknown or released token or an unreachable server raises an `ApplicationError` and starts no update. The callback after the complete Tool batch enters Session history acknowledges the call, whether its ticket is claimed before or after that point. The worker waits for that acknowledgement and durably registers an idempotent once-Bootstrap before maintenance begins. The private application RPC validates the saved call and Session, closes new admission, then cancels and awaits only the exact origin Run; its cleanup and already accepted Queue work remain part of the drain. The Bootstrap resumes in that Session on the next startup and inspects the saved operation without repeating prior actions. Human/tray updates create no Agent or Bootstrap. Source-checkout Agent updates retain their separately documented manual Bootstrap workflow. Tickets and `runtime/update-continuations/` receipts serve one operation: Runtime start deletes those older than `UPDATE_HANDOFF_FILE_RETENTION` (7 days) and logs one DEBUG count summary that never names ticket ids or tokens. Coverage: `tests/core/tools/test_bash_update_handoff.py`, `tests/server/rpc/test_application_methods.py`.

## Customization and optional dependencies

- `customize.prepare` creates an exact-revision development Git checkout, separately from active sources. `check --intent` applies Ruff/Prettier/ESLint fixes, runs mypy, the complete pytest and Vitest suites and the WebUI build, records exact HEAD plus tree digest, and builds a candidate with fresh dependencies. Activation and foreground test reject subsequent unvalidated changes, including clean manual commits. Testing uses fresh data (the test server initializes its not-yet-created data root), a separate port and explicit `--test-instance` suppression of Extensions/automatic producers.
- Official updates rebase local commits into a separate retained worktree. Conflict state points to the preserved source for manual resolution; `customize rebase --intent` checks it and creates an activatable candidate. Successful activation alone promotes the new source/base metadata. No patches are silently discarded. Git and Node.js/npm are development prerequisites; normal updates require neither unless carrying local code changes.
- User Extension sources stay in data/configured roots. `application dependencies install --requirements` replaces the complete managed dependency recipe. Resolution uses a fresh data-directory site constrained by the immutable runtime inventory. Compatible distributions are appended only at normal server startup, without executing `.pth` files; base packages cannot be replaced. Recipe changes require restart. Updates prepare the recipe for the candidate's runtime/Python-DLL fingerprint before stopping the current server. `core/extensions/dependencies.py` owns runtime activation; `cli/application/dependencies.py` owns provisioning.
- Packaged STT/TTS use managed user-data environments and child workers; no setup pip call mutates a released runtime. See `model_tasks/speech.md`. Extension dependency generations are not removed. Application versions referenced by customization state, a private environment or a live process survive version retention (Update operation).

## Verification and operation entrypoints

Interactive native uninstall reuses the source CLI selection and confirmation wording, including cancellation by default; non-interactive removal still needs an explicit scope and confirmation. Native uninstall creates `removal-pending.json` under dispatch/operation locks before deleting application files. Admission verifies Inno's copied second-phase process, its exact registered-uninstaller target and its first-phase parent; only those two verified processes and the current command are exempt from the owned-process scan. The scan checks only absolute executable paths because Windows process enumeration can return non-path pseudo-process names. The second-phase PID/create-time owns the marker through actual deletion. It refuses pending updates, a server that `processes.server_state` does not find `absent` (a busy `unresponsive` one included; admission never stops it, Inno ran `server stop` before), or other remaining owned processes. The durable marker blocks update dispatch, recovery, tray start and ordinary operation mutations throughout Inno deletion; explicit stop remains available. Desktop launch holds the short dispatch lock across its guard and process creation so it cannot race this reservation. Normal Inno completion/cancel removes it. After an uninstaller crash, `application removal-reset` requires a dead/different PID creation identity and a verified complete active release before clearing the marker.

A packaged data-only reset (`uninstall --data-only`, `integration.uninstall`) classifies the server first: `running` is stopped, its data removed and the server restarted; `absent` removes the data and leaves the server stopped; `unresponsive` or `foreign` refuse before stopping or deleting anything, so data is never deleted under a live server. Coverage: `tests/cli/application/test_integration.py`, `test_removal.py`.

`tests/cli/application/` covers state, archives, worker recovery, CLI/tray behavior, customization and dependencies. Server/Run/Tool tests cover authorization, durable acknowledgement, drain and startup suppression. `tests/scripts/test_build_windows.py` covers payload/build contracts. Native/package smoke uses disposable paths and ports, with no production credentials, Autostart registrations or user installation changes. Building is not publishing; release signing credentials and external publication remain explicit release operations.
