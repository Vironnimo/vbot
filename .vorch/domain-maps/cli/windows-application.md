# Packaged Windows Application

Read for native distribution, tray/lifecycle integration, transactional updates, and managed local code or Extension dependencies. `cli/application/` extends CLI lifecycle ownership because its state and update worker must remain available when Runtime is stopped. It does not own business configuration or Sessions.

## Layout and native boundary

- `<install>/vBot.GUI.exe` is the stable Windows GUI companion used by the Desktop shortcut with `desktop`. It resolves `active-version` on each launch and shares CLI/Desktop dispatch without allocating a console. The console `vBot.exe` keeps terminal output and wait semantics. Both remain protocol-1 bootstraps; installer/update integration adds a missing GUI companion and updates only the standard shortcut pointing to this installation with exactly `desktop`, preserving foreign/customized links and existing bootstraps.
- `<install>/vBot.exe` is the stable native bootstrap. No arguments starts the per-user tray host; arguments dispatch CLI commands. Native role hosts run CPython in-process: `vBot.Server.exe`, `vBot.Desktop.exe`, `vBot.Update.exe`, and `vBot.Python.exe`. Desktop is optional and independent of server lifetime.
- Both native manifests declare PerMonitorV2 and Windows 10/11 compatibility. Desktop retains its separate manifest and WinForms opt-in (see `desktop.md`). `windows_tray.py` owns explicit light/dark menu drawing and DPI-scaled text while Windows retains popup input. Menu replacement is serialized onto its UI thread and deferred while the popup is open; unchanged status polls do not rebuild it. Tray status uses a cached human release version and a separate short state line, never an entire operation message. Grouped actions use themed separators and inset hover backgrounds; Update details exposes the saved result without widening the menu. Application logs and Server logs open their respective owners. External tray shutdown dismisses an open popup before ending the message loop.
- Packaged server start/stop/restart/status use the shared CLI progress, result renderer and exit-code policy. Native startup results carry health and WebUI facts so successful startup never renders as stopped. Packaged `server status` uses the shared CLI status renderer and exit-code policy, including structured running, URL, WebUI, data-directory and log-path fields and a successful exit for a reported non-vBot listener conflict.
- `application.json` records schema, shape, exact server target and release trust; `active-version` atomically selects `versions/<safe-id>`. Each version contains `app/` readable runtime sources/resources/built WebUI and `runtime/` private CPython 3.13/dependencies, plus a complete `release.json` inventory. Standard payload collection excludes checkout metadata, tests and build tooling. Main installs retain a separate `<install>/source` Git checkout; explicit customization uses `development/source`.
- Bootstrap protocol 1 is immutable across ordinary updates. An incompatible release fails validation before activation and needs a new installer. Native paths are isolated from ambient Python environments; application code does not write bytecode into releases. Native hosts explicitly enable Python UTF-8 mode so redirected CLI output and Agent Tool results preserve Unicode independently of the Windows code page.
- Server payload collection includes the private, digest-locked ripgrep/PCRE2 executable and third-party notices. `payload.py` reuses verified source/base assets or provisions the locked Windows x64 archive before inventory generation. Desktop-client excludes native search assets. See `tools/search_files.md`.
- Source: `state.py`, `packages.py`, `payload.py`, `scripts/build_windows.py`, `scripts/windows/launcher.c`, `scripts/windows/vbot.iss`. The three shapes are server, server-desktop and desktop-client. A client never probes, snapshots or stops a default local server.

## Update operation

- Windows release and main installations use the same native hosts, tray and durable updater. `install.ps1 -Dev` installs a verified release base without startup, selects main with `application source main`, runs the normal update, then enables requested Autostart. Failure leaves the complete base installation and failed operation available for retry. `-SourceCheckout` and current-checkout setup remain source-only modes.
- `source_updates.py` owns `source-update.json`, recording an exact Git root, remote and branch. `application source main [--from-checkout]` selects it without activation; `application source release` removes only the binding and preserves source files. Selection refuses pending updates. `application status` exposes the selected update source. A transitioned branch installation retains its recorded branch instead of silently becoming a release installation.
- Bound updates fetch their recorded upstream, fast-forward when possible and retain clean local-ahead commits. Dirty work, branch changes and divergence stop preparation without discarding source or stopping the running version. Main preparation uses the shape's hashed Windows dependency lock without running quality gates or committing source; exact HEAD and cleanliness are checked again before accepting the candidate. `build_inputs` in the candidate manifest records the runtime recipe and tracked WebUI/Extension page inputs. Unchanged runtime dependencies are copied, never hard-linked; unchanged generated assets come from the verified base, including complete Extension page trees. Missing provenance requires one fresh build. Changes to the runtime provisioning recipe must invalidate its fingerprint. Native input fingerprints avoid recompiling unchanged hosts; changed native inputs require LLVM and the Windows SDK. The stable root bootstrap remains protocol-bound and installer-owned.
- An unchanged Main revision, build inputs and native inputs without managed customization state returns the verified active version. It checks Extension dependency compatibility and completes without a snapshot, maintenance admission, Agent continuation or restart, including with `--no-restart`. Managed customization reconciliation remains on its existing validation path.

- Human CLI, tray and Agent CLI call `operations.request_update`. Atomic records under `operations/` contain phases, identities, result and exact worker PID/create-time. Only equivalent pending requests coalesce. The short dispatch lock protects worker handoff; the OS-owned operation lock covers the entire mutation, also excluding manual lifecycle and customization changes.
- `_output.py` owns readable native update outcomes alongside source-update rendering; both use `_progress.py` status markers and elapsed-time heartbeats. Native updates opt into one transient progress line on capable terminals; captures remain append-only and a new phase resets its heartbeat deadline. The source and target release versions include short Git revisions and the target is announced as soon as resolved. Worker messages distinguish fetching, building, dependencies, verification and Session snapshots. Display labels are stored under `operations/details/`, outside the protocol-1 transaction record so still-running prior-version consumers can read it. Native default output has no raw phase prefixes or trailing JSON. Explicit `--output plain` retains one structured operation result, and `update status` remains a read-only structured inspection. Prepared/detached/handoff outcomes retain the exact status or activation command and never imply completed activation. The PowerShell installer preserves these shared status labels while retaining full diagnostics in its log.
- All background Git, dependency, build and Autostart subprocesses use the shared windowless creation flags, including compiler descendants. Foreground customization test instances retain their terminal. Native CLI/Server/Update startup failures write stderr and exit instead of waiting on a modal dialog; tray/Desktop GUI launches may display a dialog. Early child errors are captured under application logs.
- A human `vbot update` normally waits for terminal state and returns nonzero on failure. `--detach` returns acceptance. `--no-restart` produces terminal `prepared`, leaves the pointer unchanged, and requires `update activate <id>` later. A dead caller cannot cancel the worker. The waiting CLI, an equivalent repeated update request, or tray startup can recover an orphan by reconciling its saved phase; `update status` only reads saved state.
- Official archive signatures are Ed25519 over the raw SHA256 digest, verified against the install's public key. Deliberately supplied `--package` artifacts can be local/unsigned. Extraction rejects unsafe paths, special files, case collisions, invalid shape/platform/protocol and inventory mismatches before activation. Payload verification scans entries without following links/reparse points, checks the exact inventory and hashes every file; it does not repeatedly resolve each file's ancestors.
- `worker.py` prepares a version and carries local commits/dependency recipes forward before stopping anything. It obtains server-owned maintenance admission, drains accepted work, asks Sessions for a verified snapshot, stops the exact server, probes the candidate with `--verification-only`, then changes the pointer and verifies required normal startup. Candidate failure can retain previous code only after previous startup verification. It never restores a data snapshot. Ambiguous recovery becomes `needs_attention`.
- `processes.py` verifies health plus control PID/create-time, exact native executable and startup mode. Dispatch detaches the updater from vBot's lifetime Job once; the updater owns no Job and starts its verification/recovery/normal servers without requesting another breakaway from ambient Windows Jobs. Direct lifecycle starts and dispatch use the shared immediate-Job policy in `core.utils.processes` (see `tools/process.md`), preserving a restrictive external ancestor while escaping vBot's own Job. `core.utils.server_control.server_control_claim` prevents competing starts from replacing live shutdown authority. Its per-data-directory/port OS lock spans control publication through final cleanup.

## Agent handoff

`core/tools/_bash_update_handoff.py` gives each durable Bash invocation an opaque scoped ticket. Only the callback after the complete Tool batch enters Session history acknowledges it. The worker waits for that acknowledgement and durably registers an idempotent once-Bootstrap before maintenance begins. The private application RPC validates the saved call and Session, closes new admission, then cancels and awaits only the exact origin Run; its cleanup and already accepted Queue work remain part of the drain. The Bootstrap resumes in that Session on the next startup and inspects the saved operation without repeating prior actions. Human/tray updates create no Agent or Bootstrap. Source-checkout Agent updates retain their separately documented manual Bootstrap workflow.

## Customization and optional dependencies

- `customize.prepare` creates an exact-revision development Git checkout, separately from active sources. `check --intent` runs quality gates/build, records exact HEAD plus tree digest, and builds a candidate with fresh dependencies. Activation and foreground test reject subsequent unvalidated changes, including clean manual commits. Testing uses fresh data, a separate port and explicit `--test-instance` suppression of Extensions/automatic producers.
- Official updates rebase local commits into a separate retained worktree. Conflict state points to the preserved source for manual resolution; `customize rebase --intent` checks it and creates an activatable candidate. Successful activation alone promotes the new source/base metadata. No patches are silently discarded. Git and Node.js/npm are development prerequisites; normal updates require neither unless carrying local code changes.
- User Extension sources stay in data/configured roots. `application dependencies install --requirements` replaces the complete managed dependency recipe. Resolution uses a fresh data-directory site constrained by the immutable runtime inventory. Compatible distributions are appended only at normal server startup, without executing `.pth` files; base packages cannot be replaced. Recipe changes require restart. Updates prepare the recipe for the candidate's runtime/Python-DLL fingerprint before stopping the current server. `core/extensions/dependencies.py` owns runtime activation; `cli/application/dependencies.py` owns provisioning.
- Packaged STT/TTS use managed user-data environments and child workers; no setup pip call mutates a released runtime. See `model_tasks/speech.md`. Version and dependency generations are retained for recovery rather than deleted while referenced by code changes or live processes.

## Verification and operation entrypoints

Interactive native uninstall reuses the source CLI selection and confirmation wording, including cancellation by default; non-interactive removal still needs an explicit scope and confirmation. Native uninstall creates `removal-pending.json` under dispatch/operation locks before deleting application files. Admission verifies Inno's copied second-phase process, its exact registered-uninstaller target and its first-phase parent; only those two verified processes and the current command are exempt from the owned-process scan. The scan checks only absolute executable paths because Windows process enumeration can return non-path pseudo-process names. The second-phase PID/create-time owns the marker through actual deletion. It refuses pending updates, a reachable server, or other remaining owned processes. The durable marker blocks update dispatch, recovery, tray start and ordinary operation mutations throughout Inno deletion; explicit stop remains available. Desktop launch holds the short dispatch lock across its guard and process creation so it cannot race this reservation. Normal Inno completion/cancel removes it. After an uninstaller crash, `application removal-reset` requires a dead/different PID creation identity and a verified complete active release before clearing the marker.

`tests/cli/application/` covers state, archives, worker recovery, CLI/tray behavior, customization and dependencies. Server/Run/Tool tests cover authorization, durable acknowledgement, drain and startup suppression. `tests/scripts/test_build_windows.py` covers payload/build contracts. Native/package smoke uses disposable paths and ports, with no production credentials, Autostart registrations or user installation changes. Building is not publishing; release signing credentials and external publication remain explicit release operations.
