# Command-line analysis

`core/permissions/commands/` turns one shell command line into a `CommandPlan`: the simple commands it runs, the paths it reads, writes or changes into, the URLs and host names it reaches, and what it could not resolve. It runs nothing and never touches the filesystem (no realpath, no existence checks); deciding about a plan, link resolution included, belongs to the Permission Boundary. Public interface: `core/permissions/commands/commands.py`; everything else in the folder is private.

## Interface

- `CommandAnalyzer(*, powershell_executable: Path | None, limits=None, helper_launcher=None)`, one per server. `async analyze(command_line, *, shell, cwd, env, home) -> CommandPlan`; `async analyze_argv(argv, *, cwd, env, home) -> CommandPlan` for a program started directly (a terminal's program: literal words, the program dispatched like a command, a shell with a command analyzed as a nested shell); `async aclose()`. The Runtime's `CommandChecker` owns the one instance and creates it on first use (`permissions.md` -> Command checks). `shell` is a `ShellKind`: `"powershell"`, `"bash"` (also zsh and other POSIX shells) or `"cmd"`; the terminal uses the same type. `env` is the environment the command would run with; `home` the user's home folder.
- The analysis itself is synchronous and runs on a `BoundedWorkerPool` (`command-analysis`, 2 workers), never on the Event Loop: a 163 KB bash script blocks the loop at most about 45 ms (it was about 290 ms on the loop). A PowerShell parse goes from the worker to the helper on the loop (`run_coroutine_threadsafe`) and waits for its answer.
- `powershell_executable` comes from `core.tools.shell.powershell_executable(search_path)`, the lookup the Shell Tool uses; None makes PowerShell analysis unavailable. `helper_launcher` replaces the helper process (tests); `limits` is a `PowerShellHelperLimits`.
- `CommandAnalysisUnavailable` (a `VBotError`): the PowerShell helper could not answer (no executable, start failure, timeout, crash, unknown answer). Callers fail closed. bash and cmd never raise it.
- `shell_kind(program) -> ShellKind | None`: the analysis language of a shell program (`pwsh.exe` -> `powershell`), for the terminal: a line typed at such a prompt is analyzed with `analyze`, the terminal's shell and its reported working directory.
- `normalize_command_pattern(pattern)`, `command_pattern_matches(pattern, command, *, case_insensitive)`, `command_pattern_may_match(...)`: see Patterns.
- `MAX_COMMAND_LINE_CHARS` (1,000,000) and `MAX_NESTING_DEPTH` (8).

## CommandPlan contract

- `commands: tuple[SimpleCommand, ...]` in source order, from every depth: pipelines, `$( )`, `@( )`, script blocks, backticks, subshells, control-flow bodies, nested shells. `SimpleCommand(name, words, source, shell)`: `name` is canonical (PowerShell alias resolved to its cmdlet; program without folder and `.exe`/`.com`/`.cmd`/`.bat`; transparent wrappers removed), `words` the arguments as `CommandWord(text, static)` without a program's global options (Lowering), `source` the original text (at most 500 characters), `shell` the language the command was written in. A static word's `text` is its value after expansion; a dynamic word's `text` is its source.
- `paths: tuple[PlannedPathAccess, ...]`: `PlannedPathAccess(kind, path, source, subtree, glob, pruned, work_tree)`; `work_tree`: `path` is the folder a git command works in and the access counts from its repository's top (Paths -> git). `kind` is `read`, `write` or `start_dir` (every folder a `cd` changes into). `path` is absolute and lexically normalized. `glob`: a wildcard access reaches the entries below `path` this relative pattern in rule syntax matches (`src/*.py` -> `path` `src`, `glob` `*.py`). `subtree` True: it also reaches everything below `path`, or below the entries `glob` matches (recursive operations, `Remove-Item`, pipeline-fed writes, archive extraction, output folders), so a rule below applies too. `pruned`: folder names a recursive search leaves out at every depth (Paths). `check_path` takes all three (`permissions.md` -> Interfaces).
- `unresolved: tuple[UnresolvedElement, ...]`: `UnresolvedElement(kind, source, reason)` with `kind` `path_read`, `path_write` (a read or write whose path is unknown), `cwd` (a change into an unknown folder), `url` (a web address computed when it runs) or `command` (something the analysis cannot see into). `reason` is a lower-case clause for refusals and logs.
- `urls: tuple[str, ...]`: http(s) URLs found in any word; a scheme-less target of curl, wget or `Invoke-WebRequest`/`Invoke-RestMethod` (`e.example/x`, `localhost:8765`) becomes an `http://` URL.
- `hosts: tuple[str, ...]`: host names a command reaches without a URL, lower-cased: ssh and scp targets, rsync and scp remotes, `git@host:path`. The checker decides them like a URL's host.
- Entries are deduplicated in first-seen order. A plan is conservative: when a directory change may fail, later paths resolve against both folders.

What becomes an unresolved `command`: a command line above the limit or that does not parse; nesting deeper than 8; a computed command name (`& $x`, `. $profile`, `$cmd args`) or method name; `Invoke-Expression`/`iex`, `eval`, `pwsh -Command`, `bash -c` or `cmd /c` of a computed string; `--%` (the rest of the line goes to the program unparsed); a name the line redefines with `Set-Alias`/`New-Alias`; a shell that reads commands from its input (`curl ... | sh`, `pwsh -`); `wsl`; fish scripts; `env -S`.

## Lowering

- PowerShell: PowerShell's own parser in the helper (Helper below), with `StaticParameterBinder` for cmdlets and functions; aliases resolve against the session's default commands. bash: tree-sitter-bash in process (imported on first use, about 4 us per parse). cmd: a small tokenizer in `_cmd.py` (`&`, `&&`, `||`, `|`, blocks, `^`, redirects, `if`/`for ... do`/`else`); a built-in's name ends at the first of `. \ / : = ; , + (` as cmd ends it (`cd..` is `cd ..`, `cd\x` is `cd \x`).
- Nested shells unwrap recursively: `pwsh`/`powershell` `-Command`/`-c`, `-EncodedCommand`/`-e` (UTF-16LE base64), `-File`/`-f` and a script operand are reads, `-WorkingDirectory` a `start_dir`; `bash`/`sh`/`zsh`/... `-c`; `cmd /c` and `/k` (`/v:on` turns on delayed expansion); `iex`, `eval`, `watch`, `trap` with literal strings; `find -exec`; `Start-Process` (its program and `ArgumentList` become a command, `WorkingDirectory` a `start_dir`, redirect parameters accesses).
- Wrappers: `timeout`, `time`, `nice`, `nohup`, `stdbuf`, `command`, `builtin`, `exec`, `ionice`, `env` (its assignments make those variables dynamic for nested shells; `-C` changes folder), `xargs` (the inner command's targets come from the pipeline) and cmd's `call` are removed. `sudo` and `doas` stay and the inner command is added too.
- Runners (`RUNNERS`: `uv run`, `uvx`, `pipx run`, `poetry run`, `pdm run`, `hatch run`, `pixi run`, `rye run`, `conda`/`mamba`/`micromamba run`) stay and the command they run is added too, so `uv run vbot ...` is vBot's CLI; their folder options (`uv --directory`) change folder.
- Global options (`GLOBAL_OPTIONS`: git, docker, kubectl, npm, cargo, dotnet) are dropped from the words before patterns match, so `git -C x --no-pager push` matches `Shell(git push *)`. `git -C dir` changes into `dir` for that command only; `npm --prefix dir` and similar folder options write below `dir`; git writes there only with a writing subcommand.
- PowerShell expression statements: .NET method calls are accesses by type and method (`_dotnet.py`): static `System.IO.File`/`Directory`/`ZipFile` methods (`[IO.File]::WriteAllText` writes, `ReadAllText` reads, `Directory.Delete` writes the subtree, `AllDirectories` enumeration reads it), file objects from `New-Object`/`[T]::new` (`StreamWriter 'f'` writes `f`), web clients (`WebClient.DownloadFile` names a URL and writes its file), and methods of items a listing cmdlet produced, also through `%`, `Where-Object` and `& { }` script blocks (`gci *.log | % { $_.Delete() }` writes them). A file method on an object the analysis cannot follow is an unresolved `path_write`. A string constant in an expression that looks like a path is a tier B read; a computed `-Uri` is an unresolved `url`.
- Variables: PowerShell `$env:NAME` (case-insensitive on Windows), `$HOME`, `$PWD`, `~`; bash `$HOME`, `$PWD`, `$OLDPWD`, `~` and exact environment names; cmd `%NAME%` and `%CD%`. A variable the script assigns anywhere (assignments, `for`, `read`, `Set-Variable`, `env:` item writes, `set X=`), a missing one, and every other expansion are dynamic. `[Environment]::SetEnvironmentVariable` makes all PowerShell variables dynamic.

## Paths

- Tier A, known commands, by bound parameter or per-program spec (`_specs.py`): the PowerShell item, content, archive, ACL and web cmdlets in `CMDLETS`, plus any `<write verb>-<noun>` cmdlet with a generic path parameter (`Path`, `LiteralPath`, `FilePath`, `Destination`, `OutFile`, ...); `Import-Module` of a path, `. script` and `& script` read it; POSIX file programs in `PROGRAMS` (rm, mv, cp, ln, mkdir, touch, chmod, sed, cat, grep, rg, ls, tee, rsync, scp, zip, ...), with option parsing (bundles, `--x=v`, `--`) and the last operand as destination; special handlers (`_handlers.py`) for find, tar, dd, unzip, curl, wget, icacls, attrib, git (`clone` writes its target folder; work tree and index below) and python (the script is read; `-m venv`/`virtualenv` writes its folder); cmd built-ins in `CMD_BUILTINS` (del, rd, md, copy, move, ren, type, dir, mklink). Redirects are accesses (`$null`, `NUL`, `/dev/null` are none). A tier A path that is dynamic or cannot be placed is unresolved.
- Programs without a spec: their `OUTPUT_OPTIONS` (`pip --target`, `dotnet -o`, `cargo --target-dir`, `gcc -o`, ...) write below the value; every other word is tier B. Tier B: only words that are clearly paths count, as reads: absolute, drive-letter, UNC, `~` or home-variable paths, and relative paths that climb out with `..`, also as the value of `--opt=value` or `key=value`; `file://` URLs give their path. URLs, git refs and other words are ignored; dynamic tier B words are not unresolved. Trade-off: an unknown program's positional paths stay reads, so `mytool in out` is not seen writing `out`; counting them as writes would refuse most unknown programs under read-only rules.
- git (`_git_files.py`; pathspecs and `-C` count from the folder git works in): pathspec operands of `checkout -- <paths>` (without `--` every operand and the whole work tree), `restore`, `rm`, `mv`, `clean` (pathless: its folder), `stash push`, `worktree remove|move` and `checkout-index` are subtree writes, a wildcard of its whole literal folder (a git `*` crosses folders); `apply` writes its folder's subtree (from inside a repository it changes nothing outside it). `reset --hard|--merge|--keep`, `stash` push/pop/apply/branch, `pull`, `merge`, `rebase`, `switch`, `checkout <branch>`, `cherry-pick`, `revert`, `am`, `bisect`, `submodule`, `sparse-checkout`, `read-tree`, `filter-branch` are `work_tree` writes: the checker finds the repository's top (the nearest folder at or above with `.git`, looking only where the Agent may read; where it may not, that folder counts as the top; without one, the git folder) and checks a subtree write there, where the repository's own rule files may change (the honest limit in `permissions.md`). Operands of `add`, `commit`, `diff`, `difftool`, `blame`, `annotate`, `grep` (pathless: its folder), `ls-files`, `status` and `hash-object` are subtree reads; an index path `:path` (`:0:path`) in any subcommand is a `work_tree` read of that path below the top; `rev:path` reads history and is not checked; other pathspec magic is unresolved. Everything else writing (`commit`, `fetch`, `reset` without those flags, `restore --staged`, `rm --cached`) writes only its folder, not below. `submodule foreach`, `bisect run`, `rebase -x` and `filter-branch` filters run commands and are unresolved, as are `--pathspec-from-file`, `--prefix` and `--unsafe-paths`.
- Globs: a wildcard path is an access on its literal folder with the rest as `glob` (`src/*.py`); `..` after a wildcard is unresolved. PowerShell treats wildcards per parameter (`-LiteralPath` none). The Boundary matches deny patterns against the glob's segments, so `Get-ChildItem *.md` passes a deny of `secrets/**`.
- Recursive operations reach the subtree: `Get-ChildItem -Recurse` or `-Depth`, `ls -R`, `grep -r`, `rg`, `find`, `Copy-Item -Recurse`, `Compress-Archive` of a folder. Exact exclusions are `pruned` names: `rg -g/--glob '!name'` only where file names are case-sensitive (on Windows it would still read `Name`), `rg --iglob '!name'` (folded), `grep --exclude-dir=name` (case-sensitive likewise).
- Pipelines: a cmdlet or `xargs` command that takes its targets from the pipeline gets accesses on what the listing command before it names (Get-ChildItem, Get-Item, Resolve-Path, Select-String; ls, find, fd, grep, rg, dir), with its glob, through filters (Where-Object, Select-Object, Sort-Object, ...); writes reach the subtree. With any other producer, or a listing cmdlet that itself takes piped input, the targets are unresolved.
- Windows forms: drive-relative `C:foo` resolves against the cwd only on the same drive, else against the folder the line last used on that drive or the `=C:` environment entry, else unresolved; root-relative `\x` against the cwd's drive; UNC stays as-is; `\\?\` and `\\?\UNC\` are stripped, other device paths kept; `FileSystem::` is stripped; non-file PowerShell drives (`HKCU:`, `env:`, `variable:`, ...) are no paths; other PowerShell drives are unresolved. bash on Windows (Git Bash) maps `/c/x` to `C:\x`; other POSIX absolute paths are unresolved there. A relative path in a .NET call resolves against the PowerShell locations and the process folder (`[Environment]::CurrentDirectory`, the start folder).

## Working directory tracking

- Handled: `cd`, `chdir`, `Set-Location`/`sl`, `pushd`/`Push-Location`, `popd`/`Pop-Location`, `cd -`, `cd..`, `cd\`, `cd~`, `X:` drive switches, cmd `cd /d`, `env -C`, `pwsh -WorkingDirectory`, `git -C`, runner folder options, `[IO.Directory]::SetCurrentDirectory`.
- Every change may fail, so the old folder stays a candidate; at most 16 candidates, beyond that the folder is unknown. A dynamic or unplaceable target makes later relative paths unresolved. Every folder changed into is a `start_dir` access.
- bash scopes changes to subshells, command substitutions, pipeline elements and background commands; PowerShell and cmd have no such scopes.
- `cd -` without a known previous folder is unresolved (bash falls back to `$OLDPWD`); a bare `cd`/`Set-Location` goes home.

## Patterns

`Shell(...)` patterns follow Claude Code: the command is its canonical name and static words joined by single spaces; `*` matches any text; a trailing ` *` also matches the bare command; a dynamic word matches only `*`. `normalize_command_pattern` collapses spaces, reads the legacy `prefix:*` as `prefix *`, reduces a first word with a folder or extension to the program name, and raises `ValueError(reason)` for an empty pattern or control characters. PowerShell commands always compare case-insensitively, and the pattern's first word resolves through PowerShell's default aliases (`rm *` matches `Remove-Item x`; on Linux and macOS only the aliases that are no programs there). `command_pattern_may_match` is for deny rules: it matches when some value of the dynamic words could make the pattern match (`rm <$X>` may match `rm -rf /`).

## PowerShell helper

- One long-lived `pwsh` per analyzer, started lazily: `-NoLogo -NoProfile -NonInteractive -Command <bootstrap>`; the bootstrap reads the base64 helper script `powershell_analysis.ps1` (a resource beside the module, shipped with `core`) from the first stdin line and runs it, so no execution policy applies. Module autoloading is off; the helper imports the built-in Management, Utility, Security and Archive modules from `$PSHOME`, builds its command table and runs one warm-up analysis before it reports ready.
- JSON lines over stdin/stdout: ready line `{"ready": true, "version": ...}`, request `{id, script: base64}`, answer `{id, ok, result | error}`. The result lists commands, .NET member calls (`calls`) and expression strings (`strings`), each with its offset; lowering orders them by offset. Requests are serialized.
- One helper, not a pool: it takes about 115 MB and a typical line a few milliseconds, so a second one costs memory without gain. A request that waited 1 s or more for the helper is logged at WARNING.
- Limits (`PowerShellHelperLimits`): start 20 s, request 5 s, restart after 2000 requests or above 512 MiB RSS, stop after 600 s idle. A failed request is retried once with a fresh helper; after a failed start, requests fail at once for 15 s. Every failure raises `CommandAnalysisUnavailable`.
- Started like every server child (`core/utils/processes.py`): windowless in a new process group with System32 as cwd inside the server's kill-on-close Job on Windows; under the process guardian with its own session on POSIX. `aclose` kills the process tree.
- Measured on Windows with pwsh 7.6 over 50 varied lines: about 0.55 s from start to ready (warm-up included), then 4 ms median and 8 ms at the 90th percentile per line, nested shells included. Long scripts cost about 50 ms per KB in the helper, so one above about 100 KB exceeds the request limit and is refused as unavailable.

## Command checks

`CommandChecker` (`_command_check.py`, `permissions.md` -> Interfaces) decides a plan in this order; the first refusal wins: the analysis (`CommandAnalysisUnavailable` refuses), the start directory (`start_dir`), every simple command against deny rules of every layer (`command_pattern_may_match`), every `commands: listed` layer's allow rules (`command_pattern_matches`), vBot's own CLI (`vbot` as a program or `.ps1`, a Python running `<vbot>/cli/...` or `server/main.py`, `python -m cli...`/`server...` in a folder inside the checkout), the vBot server (a `host:port` word, or an own-host word plus a word that is the port), every URL (`check_url`) and host (`check_host`), every path access (`check_path` with its `subtree`, `glob` and `pruned`; a `work_tree` access at the repository's top with `work_tree=True`; a read refused for a denied part `below` gets the hint to use `search_files`), and last every unresolved element. The platform for case folding comes from the boundary's context, vBot's checkout from `core.utils.config.VBOT_ROOT`.

## Limits and false-refusal risks

- Command-line analysis is lexical: links, junctions and mounts are not resolved, so a path that reaches elsewhere through a link looks local.
- Scripts a line runs (`./x.sh`, `. .\setup.ps1`, `source f`, `python s.py`) are reads; their contents are not analyzed, nor is a script fed on stdin (`python - <<EOF`).
- Unknown programs contribute only tier B reads; a program that writes where its arguments do not say (or through a config file) is not seen. git commands that read history (`git show HEAD:secrets/key`, `git log -p`) can read tracked files below a denied folder unseen, and a pathless `git diff`, `git status` or `git ls-files` shows names and changes of tracked files there (refusing them whenever a Read deny lies in the repository would refuse nearly every `git diff`).
- git: a work-tree change (`git pull`, `git switch`) is refused in a repository with a deny rule or a protected location below its top, and `git restore .`, `git clean`, `git apply` or `git add .` where a rule file or a Read deny lies below that folder; a revision operand of a reading subcommand is read as a path (harmless unless a deny names it), a dynamic one is unresolved.
- Likely false refusals: any `cd` keeps the old folder, so relative paths after it also resolve in the starting folder; dynamic tier A paths (loop variables, `$_` outside a listing pipeline) are unresolved; PowerShell parameter binding errors on a tier A cmdlet (`rm -rf x`) are unresolved; POSIX absolute paths under Git Bash; `cd -` first on a line; a recursive search over a folder with a denied folder below (`rg foo`, `Get-ChildItem -Recurse`) unless it excludes that folder exactly.
- PowerShell analysis needs `pwsh`; the Shell Tool runs PowerShell only on Windows, and the tests of the PowerShell table run only there.
