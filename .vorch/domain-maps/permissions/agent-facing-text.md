# Permission Rules Agent-facing text

Why each sentence of the permission texts exists: the `permission_denied` refusal (`PermissionRefusal.message`, `core/permissions/_refusal.py`) that every Tool returns, the Cron watch refusal (`PermissionRefusal.watch_message`), the command-check reasons and hints (`core/permissions/_command_check.py`), the `core:permissions` System Prompt block and the permission Run failures (`core/chat/_run_permissions.py`, `core/settings/agent_defaults.py`). Texts of single Tools stay with their Tool: the terminal's attach and prompt refusals (`tools/terminal.md`), the listing, search and similar-entry notes that name what the rules leave out (`core/tools/_refused_notes.py`; reasons in `tools/read.md`, `tools/search_files.md`), the `web_search` count (`tools/web_search.md`). Rules for this file: `.vorch/workflows/domain-map-workflow.md` -> Agent-facing text; failure modes F1-F6: `tools/agent-facing-text.md` -> Failure modes.

Every text addresses the Agent as `you` (`vbot-agent-tools` Skill -> Wording), except the watch refusal, which the user also reads.

## Refusal (`permission_denied`)

| Text | Reason |
|---|---|
| `<tool> was not run: the permission rules refuse <reading / changing / working in / running "<command>" / fetching / connecting to> <target>, because <reason>.` | Names the refused access, its normalized target and what refused it, so the Agent knows nothing ran and why (F4, F5). The `was not run` prefix matches the other refusals before any effect. `connecting to` is a host a network program reaches (ssh, scp, `git@host:`), which `fetching` misnamed (review 2026-10-21). |
| `The page was not fetched: the permission rules refuse ...` (`message(outcome=...)`) | `web_fetch` leads like every other refusal where `web_fetch was not run` would be false: after a redirect (a request was sent) and for one page beside others it fetched; an address refused before any request of a one-page call reads `web_fetch was not run: ...`. Its refusal began `The permission rules refuse ...` until 2026-10-22, the only refusal without an outcome first (acceptance check). |
| `The permission rules refuse ...` without a Tool name (`message()`) | Image downloads (`_image_downloads.py`) join every refused address, each after its argument index, into the one failure the calling Tool reports, so no single outcome fits. |
| `..., which leads to <resolved>, ...` | When a link or junction on the path leads elsewhere, the refusal of a path that looks inside the allowed folders would otherwise read as a contradiction and invite retries (F5). |
| Reasons: `the rule <rule> denies it`; `it is outside the folders you can read` / `can change` / `can work in`; `only commands that match an allow rule can run`; `only hosts that match an allow rule can be fetched` / `can be reached`; `it is in vBot's data folder`; `it is part of vBot's installation`; `it is the vBot server itself`; `it is vBot's own command line`; `it is a <network path / device path / drive-relative path> that no allow rule names` / `an alternate data stream`; `it would also read <below> / change <below>, which the rule <rule> denies` | The exact rule or base tells the Agent which other targets will work and lets it tell the user precisely what to change (F5). The `below` form names the denied part of a recursive or wildcard access (`rg foo`, `rm -r .`), whose own target is permitted, so the refusal does not read as a contradiction. Protected locations are named as vBot's own, so the Agent does not take them for an ordinary folder outside its area. |
| `what is written there decides your permission rules` (`agent_config`) | Covers every protected rule source: an Identity Agent's `agent.json`, a Team member's repository profile and settings files, and the definition folders where a definition would replace the member's (2026-10-22). `your own configuration` was wrong for the repository files and hid why the file is protected; the former `it is a file your permission rules come from` was false for a folder or a definition not yet written. |
| `, inherited from the Session that started you,` / `that scheduled this job` / `set by the Extension that runs you` | A ceiling refuses what the Agent's own rules allow; without the source the Agent and the user look for the rule in the wrong place (F5). |
| `vBot's Tools and commands refuse the same access, and the limits also apply to scripts and programs that vBot does not check.` | Without it Agents retry the same access through the shell or another Tool, which the same boundary refuses (F1, F5), or move it into a script or interpreter, which vBot does not inspect. It claims no enforcement vBot lacks and names no source, since protected locations are vBot's and ceilings are inherited (review 2026-10-21: the former `The user set these rules for this Agent; every Tool and command refuses ...` claimed both). Left out when the refusal has a `hint`, which names another way that works. |
| `You can read in: <folders>.` / `You can change files in:` / `You can work in:` / `You can run only:` / `You can fetch only from:` / `You can connect only to:` (or `You cannot ... any ...`) | Names what is allowed, so the next call can succeed inside the boundary instead of probing (F5, F6). Left out when the base allows everything. Reading, changing and working also name the Workspace, which every rule set lets the Agent read and change; working names the literal folder of a rule (`docs`, not `docs/**`), since a process starts in a folder. |
| `If the task needs this access, tell the user.` | The only way forward when the task needs the refused access; the user, not the Agent, changes the rules (F5). Left out when the refusal has a `hint`, which names the way forward. |
| `fetching "", because the address names no host` | An empty host name (`ssh ""`) is refused as unanalyzable; the quotes keep the empty target visible (it rendered as `fetching , because`). |
| `fetching "exa\u200dmple.com", because it is not a host name every program reads the same way` | A host IDNA rejects or with a character some programs decode (`%`) names no one host (`rule-language.md` -> Bases, kinds and placeholders); the reason says why an address that looks ordinary was refused, and characters that do not print appear escaped, so the Agent sees the difference (2026-10-22). |

## Command-check reasons and hints

| Text | Reason |
|---|---|
| `<what the analysis could not resolve, such as the path is computed when it runs> (<the part of the command>), so the check cannot tell what it reads` / `what it changes` / `which folder it works in` / `which address it reaches` / `what it runs`; other clauses: `the address is computed when it runs`, `it calls <method> on an object this analysis cannot follow`, `the method it calls is computed`, `the new name is computed when it runs` (cmd `ren`), `forfiles fills in its /c command for each file it finds when it runs`, `it changes into a folder a wildcard picks when it runs` (`cd sec*`), `the bash command parser could not be loaded` (inside `vBot could not analyze it to check it (...)`) | A command the analysis cannot see into is refused although it may be harmless; naming the part and why it cannot be checked tells the Agent that rewriting it, not another Tool, gets it to run (F5). The wildcard clause names the cause the Agent can remove: the computed-folder clause would leave it looking for a variable in `cd sec*` (2026-10-22). The `same access` sentence is left out for these refusals: a rewritten command can pass, so it would be false. |
| Hints: `Write each path literally in the command.` / `Change into folders by their literal path, or pass the folder as workdir.` / `Write each address literally in the command.` / `Write each command and its arguments literally.` | The concrete rewrite that makes the command analyzable; `workdir` is the shell parameter that replaces a computed `cd` (F5, F6). The terminal and Cron watch commands have no `workdir`, so their hint ends after `literal path.` (review 2026-10-21: the suggestion named a parameter the Tool lacks). |
| `Use search_files, which leaves denied folders out, or name only the folders the command needs.` | A recursive search or listing over a folder with a denied folder below is refused although every file the Agent wants may be allowed; `search_files` searches the same tree and skips refused folders, and naming the needed folders lets the command pass (F5, F6). |
| `vBot could not analyze it to check it (<error>)` with `Run it again; if this repeats, tell the user.` | The analysis failed (helper timeout or crash, fail closed); the command itself may be fine, and the helper restarts, so one retry is the right next step before involving the user (F5). The only refusal with `retryable` true, since every other refusal repeats for the same call. |
| `this vBot cannot analyze commands to check them` | A Tool registry without a command checker cannot run a restricted Session's commands; the Agent learns that no rewrite helps (F5). |

## Cron watch refusal (`watch_message`)

`The check did not run: the permission rules refuse <access> <target>, because <reason>. Change the watch to a command these rules allow` (or `an address`), stored as `last_check_error` without a final period (`automation/cron-watch.md`). The user reads it in failure alerts and the Agent in the `cron` Tool's job.

| Text | Reason |
|---|---|
| Lower-case `the permission rules refuse ...` after `The check did not run:` | The joined text read `The check did not run: The permission rules ...` (review 2026-10-21). |
| Reasons in a neutral voice: `it is outside the folders these rules allow reading` / `changing` / `working in`; `what is written there decides the Agent's permission rules`; every ceiling source as `inherited from the Session that scheduled this job` | A check runs no Agent and the user reads the alert, so `you` would address the wrong reader; every layer of a job's ceiling comes from the Session that scheduled the job. |
| `Change the watch to a command these rules allow.` / `Change the watch to an address these rules allow.` | The way forward for both readers: the job keeps the ceiling it was created with, so changing the Agent's rules does not help; `tell the user` and the same-everywhere sentence would be wrong in an alert. An unanalyzable command keeps its rewrite hint instead; a failed analysis ends after its reason, since the next check retries. |

## `core:permissions` block

| Text | Reason |
|---|---|
| `## Permission rules` (heading, rendered only for a restricted Run) | Names the section in `[prompt-block-change]` notes; without the block a restricted Agent learns its limits only from refusals, one failed call each. |
| `The user set permission rules for you.` / `..., including those of the Session that started you` / `the Session that scheduled this job` / `the Extension that runs you` | Says the limits are deliberate, so the Agent neither works around a refusal nor treats it as a fault; an inherited ceiling names its source, as the refusals do. |
| `vBot's Tools and commands refuse access outside these limits, and the limits also apply to scripts and programs that vBot does not check.` | Tells the Agent that every vBot Tool and command enforces the limits and that it must keep to them itself where vBot does not check (scripts, interpreters, MCP servers, Extensions); the former `every Tool and command refuses access` claimed enforcement that does not exist (review 2026-10-21). |
| `- You can read files only in: {items}, plus your Skills and the files vBot's Tool results point you to.` / `- You can read only your Skills and the files vBot's Tool results point you to.` (only when `read` is limited) | Lets the Agent plan reads inside the readable folders instead of discovering the limit by refusal; the list includes the Workspace, and the tail names what stays readable without being listed (Skill folders; command logs, fetched pages and media vBot hands the Session), so the Agent does not avoid them. Folders in `/` form. |
| `- You can change files only in: {items}.` / `- You cannot change any files.` (only when `write` is limited) | Lets the Agent put new files and changes where it may, for example in its Scratch Area or Workspace, instead of failing a write first. |
| `- You can run only these commands: {items}.` / `- You cannot run any commands.` (only under `commands: listed`) | Lets the Agent choose an allowed command instead of a refused one. |
| `- You can fetch only from: {items}.` / `- You cannot fetch from any host.` (only under `web: listed`) | Lets the Agent pick an allowed source instead of a refused fetch. |
| `- Always refused, even inside these folders: {items}.` / `- Always refused: {items}.` (deny rules of every layer, deduplicated; the short form when no folder line is shown) | Deny rules win over every allowed folder; without them the Agent reads the allowed folders as fully open. The former `These rules refuse access everywhere` read as if the rules refused all access. |

## Run failures

| Text | Reason |
|---|---|
| `This Session's inherited permission rules cannot be read, so it does not run. Continue the work in a new Session.` (`_INVALID_CEILING`) | A Session whose stored ceiling (a Parent's or a Cron job's) is unreadable must not run unrestricted; a new Session, a new Sub-Agent Session for a Parent, gets a ceiling that reads. The former `Ask the user to check the Session.` named nothing the user can check. |
| ``defaults.agent.permission_rules in settings.json is invalid, so Agents that inherit it do not run until it is fixed; `vbot doctor config` names the problem`` (`InvalidPermissionRulesDefaultError`, resolution failure) | An invalid default must not grant full access; the text names the setting and the command that shows the problem, for the user or a Parent Agent that relays it. |
