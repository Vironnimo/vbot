# Chat

Canonical backend chat messages and chat-loop execution exposed through the server layer.

## Overview

`core/chat/` owns the provider-agnostic conversation representation used between the chat layer and provider adapters, plus the chat loop that executes provider and tool turns. Run lifecycle and queue coordination live in `core/runs/`; Session persistence lives in `core/sessions/`; compaction/context management lives in `core/compaction/`; chat should interact with those domains through their public APIs rather than knowing storage paths or lifecycle internals. Provider-specific wire details stay in `core/providers/`; chat should assemble canonical history and request options only. A Session is the persisted chat container; a Run is one active execution inside that session.

## Terms

Core terms Agent, Session, Run, Tool, Provider, and Cancel live in `.vorch/GLOSSARY.md`.

### Continue

**Definition:** Start a new visible Run from a Session's unresolved Continuation Checkpoint without appending or replaying a user message. A normal next visible user turn also consumes the checkpoint context automatically, while Discard abandons it explicitly.

**Not:** Retrying a Provider request or resuming the same coroutine; Continue always creates a new Run and never re-executes an unknown Tool Call automatically.

## Data Model

- `ToolCall` — assistant-requested tool invocation: `id`, `name`, `arguments`. Tool-call index is derived from the assistant message order for runtime lifecycle events.
- `ChatMessage` — persisted canonical message; every message carries `id`, `timestamp`, `role`, then role-specific fields:
  - `system`: `model`, `content`
  - `user`: `content` (`str` or `list[ContentBlock]`), optional `sender` (`MessageSender` `{id, display_name}`, both non-empty strings; rejected on every other role)
  - `assistant`: `model`, nullable `content`, nullable `reasoning`, nullable `reasoning_meta`, nullable `usage`, nullable `tool_calls`, optional `interrupted` (bool, default false; only valid on `assistant`, rejected on every other role). `interrupted` marks a turn whose provider stream broke *after* visible output was emitted: the accumulated answer is preserved but the turn did not finish, so the next request continues it. It is a vBot-internal annotation — `to_dict` emits it only when true, and `_message_to_request_dict`/`_assistant_continuation_dict` strip it before any provider request.
  - `tool`: `tool_call_id`, `name`, `content`, optional `timing`
  - `note`: `content`; kernel-internal background note persisted in the Session, not shown as a normal chat message
  - `compaction_checkpoint`: `content` (summary text), canonical `projection`, `compaction_policy`, `compaction_strategy`, and optional `usage.compacted_token_count`; self-contained persisted Context used to rebuild future requests. New checkpoints include an ordinal, model-facing reminder that the Session-scoped `history` Tool can retrieve canonical messages hidden by Compaction.
  - `error`: `content`, `error_kind`; persisted run-time failure visible in normal history
  - `run_summary`: `run_id`, `status`, `timing`; append-only run annotation persisted after a Run reaches `completed`, `failed`, or `cancelled`
  - `agent_takeover`: `content` only — a compact JSON string `{"from": "<address>", "to": "<address>"}` of the source/target `agent@projekt` addresses (raw, not i18n; the WebUI composes the localized label). Persisted takeover divider written when `/agent` moves a session to another agent; visible in normal history, never sent to providers
- `reasoning` is readable thinking text. `reasoning_meta` is opaque provider data and must not be interpreted by chat.
- `timing` is a canonical timing object `{ started_at, completed_at, duration_ms }`. Durations are non-negative milliseconds measured with a monotonic clock; timestamps are UTC ISO 8601 values used only for persistence and display. `timing` is not token usage and must not be stored under `usage`.
- A **user-triggered** skill activation is persisted as a special internal `note` whose content begins with `[skill-context] `, appended right after the triggering user message. These notes are not converted to `<system-reminder>` blocks; the request build renders each one **in place** as its own `<skill_content>` user message at its chronological position (`_notes_to_request_messages` in `core/chat/messages.py`). A skill loaded by the agent via the `skill` tool has **no note at all** — the tool result itself carries the full content and replays like any other tool result (see `tools/skill.md`).
- Passively observed channel context is persisted as an ordinary internal `note` whose content begins with `[channel-message] `. At request-build time the chat layer coalesces a consecutive run into one separate synthetic user message headed as untrusted group context, never a `<system-reminder>`. Each stored value becomes one JSON-quoted record; control characters are JSON-escaped and `<` / `>` are Unicode-escaped, so a group member cannot imitate or break the surrounding context structure. The header says the records are background only, not instructions or requests, and separately addressed user messages remain normal user turns. Acquisition and the stored per-message format are owned by `core/channels/`.
- An interactive Run may carry an immutable `ReplySurface`: WebUI (which also covers Desktop) or one configured Channel identified by platform plus Channel id. At executor start, Chat scans the full append-only Session chronology for `[reply-surface] ` notes and appends a fresh tagged note only when none exists, the identity changed, or a newer `compaction_checkpoint` exists. The tag is stripped when rendered; the model sees an exact turn-bounded `<system-reminder>` immediately before the visible user message or internal prompt, or at the live tail before explicit Continue. Runs without a supplied surface are unchanged, old untagged Channel notes are ignored as state, and no mutable metadata sidecar duplicates this chronology.
- Every admitted visible Run owns a provider-neutral Continuation Checkpoint journal. It records the original visible requests, readable Thinking and partial output, stable assistant boundaries, Tool Call references/status, Compaction boundaries, and the terminal interruption cause without copying opaque `reasoning_meta` or full Tool Results. Structured `ContentBlock` requests are converted through their canonical JSON-compatible representation before the initial journal append, so attachment-backed visible Runs follow the same continuation contract as plain text. Streaming deltas are coalesced to at most one periodic append per dirty Run every two seconds; completed Model/Tool boundaries and controlled termination append immediately. The canonical Session transcript remains authoritative for Tool Calls and Results.
- An interrupted checkpoint is attached exactly once to the next visible Run at executor start: immediately before a newly persisted user turn, or as the final synthetic instruction for explicit Continue. This timing lets a message queued during Cancel receive the finalized checkpoint. A complete non-interrupted assistant result resolves and removes it; another interruption extends the same chain. Internal Runs neither consume nor resolve a visible checkpoint, and Compaction rebuilds re-inject the reminder until resolution. Missing or unknown `write`, `edit`, or `bash` Results require the Agent to inspect actual filesystem/process state before repeating the work; no Tool effect classification or automatic Tool replay exists.

## Interfaces

- `ChatMessage.system(content, model)` / `.user(content)` / `.assistant(...)` / `.tool(...)` / `.note(content)` / `.compaction_checkpoint(summary, projection, compacted_token_count, policy, strategy)` / `.error(error_kind, content)` / `.run_summary(run_id, status, timing)` / `.agent_takeover(from_address, to_address)` — constructors for role-specific messages.
- `ChatMessage.to_dict()` / `ChatMessage.from_dict(data)` — canonical JSON-compatible conversion.
- `error_kind_llm_visible(kind)` — returns whether a persisted error should be embedded into the next provider request.
- Session persistence interfaces live in `.vorch/domain-maps/sessions.md` and are exported from `core.sessions`.
- Run lifecycle types (`Run`, `RunEvent`, `ChatRunManager`, queue items, and Run errors) live in `.vorch/domain-maps/runs.md` and are exported from `core.runs`. Chat depends on one invariant from that domain: at most one active Run per `(project_id, agent_id, session_id)` (the project anchor is part of the key — caller-chosen session ids may repeat across anchors), other Sessions run in parallel, and busy-session follow-ups enqueue into an in-memory FIFO that drains automatically when the active Run clears.
- Extension hooks live in `.vorch/domain-maps/extensions.md`. Chat owns only the fire-points and payload meaning: it constructs `HookContext` (with `run_id` and `add_note` wired to `session.add_note`), decides when each event fires, and applies the dispatcher's results (the `context` shallow per-message copy then its returned list as the request messages, the tool-result-envelope `validator` injected into `tool_call`/`tool_result` in `core/chat/tool_dispatch.py`). The System Prompt is assembled **whole** by `SystemPromptManager.build_system_prompt(...)` and nothing is appended to it at runtime — there is no prompt-append hook and no `messages[0]` append; an extension that wants standing prompt content declares a prompt block instead (see `prompts.md`/`extensions.md`). For `tool_call`, chat consumes the `ToolCallDecision`: a deny builds a `tool_call_denied` failure envelope (logged at `warning`), a replace uses the envelope as the result, and a modify executes the tool with the modified input; the `tool_call_started` event is emitted after the hook phase so it shows effective arguments. Iteration, async/await, exception isolation, and composition semantics belong to the `ExtensionRegistry.dispatch_*` methods — chat never touches `_handlers`.
- `RunEvent` — provider-agnostic visible timeline event for one Run. Payloads must not expose opaque provider fields such as `reasoning_meta`.
- `compaction_completed` is a visible Run event carrying `{ message, checkpoint, checkpoint_id, history_available }` after auto-compaction appends a `compaction_checkpoint` during a Run. `message` remains the compatibility copy of the checkpoint payload.
- `model_fallback_activated` is a visible Run event with payload `{ from_model, to_model }` emitted when the chat loop switches from the agent's primary model to its configured fallback model within the current Run.
- `CommandDispatcher` — shared pre-run slash-command router for pure-text messages. `dispatch(agent_id, session_id, message_text, project_id=None)` carries the session's project (`None` = identity session) through to the handlers; accessors that have a project session must pass it (the server chat path does), channels pass nothing (identity only). Recognized built-ins either return a `CommandHandled` result (optional reply text/data plus an `output` channel) or a `CommandAction` for accessor-level execution; unknown slash text falls through so normal chat behavior, including skill activation, stays intact. Each built-in is a `CommandSpec(name, description, argument, output)` in `BUILT_IN_COMMANDS`, and trigger/presentation behavior is derived from those two attributes instead of per-command special cases:
  - **`argument`** (`none` / `optional` / `required`): `_match_command` matches a `none` command only when nothing trails the token (text after a no-arg command falls through as a normal message); `optional`/`required` take the entire remainder after the first token as the argument. `required` is unused today but kept in the enum for future commands. There is no longer a `/handoff`-specific parse branch — `dispatch` and `recognizes` share the one `_match_command` path.
  - **`output`** (`toast` / `transient` / `action`): advisory channel for accessors that render command replies (WebUI), carried on `CommandHandled.output` and surfaced through the server envelope (see `server.md`). `toast` = a transient confirmation, `transient` = a non-persisted chat card, `action` = a state change (session switch / re-run).
  - Current built-ins (each a `CommandSpec(argument, output)`): `/agent` (optional, action), `/compact` (optional, toast), `/continue` (none, action), `/handoff` (optional, action), `/help` (none, transient), `/learn` (optional, action), `/model` (optional, action), `/new` (none, action), `/reflect` (optional, action), `/rename` (optional, action), `/status` (none, transient), `/stop` (none, toast). Recognition and argument parsing live in `core/chat/commands.py`; the `action` commands' orchestration lives in `server/rpc/chat_methods.py`. Per-command behavior (what each writes, its data payload, its orchestration) is task-gated → `chat/commands.md`.
- Streaming Run events: `assistant_output_delta`, `reasoning_delta`, `tool_call_delta`, `tool_call_stdout`, and `tool_call_stderr` are transient visible Run events used for SSE streaming only. They receive normal monotonically increasing Run sequence numbers, are not persisted to JSONL session files, and must not contain opaque `reasoning_meta`.
- Tool lifecycle Run events: `tool_call_started` has payload `{ tool_call: { id, index, name, arguments }, display: { summary, hidden_argument_keys } }`; `tool_call_result` has payload `{ tool_call: { id, index, name }, result, timing }`, where `result` is the stable tool result envelope and `timing` is the completed tool-call timing object. Tool failures use `tool_call_result` with `result.ok = false`; there is no public `tool_call_failed` event.
- Error persistence Run event: `error_message_persisted` has the same message payload shape as other output-message events and indicates that a `role: "error"` message was appended to the Session.
- `ChatLoop(runtime, max_tool_iterations=1000, streaming=False, attachment_resolver=None, compaction_service=None, reflection_service=None, session_title_service=None)` — agentic loop with non-streaming and streaming modes over the same Run/session/tool dispatch infrastructure. `runtime` is typed as the `RuntimeServices` protocol from `core/runtime/interfaces.py` (imported under `TYPE_CHECKING` only); the loop accesses runtime services directly, without `getattr` probes. The optional compaction service comes from `core.compaction`. `reflection_service` is typed as the loop-owned `ReflectionNotifier` protocol (one method, `notify_run_end(run, agent, *, internal, outcome)`): in `_execute_run`'s finally — after the extension `run_end` dispatch — the loop reports every finished run to it, exception-guarded so a notifier failure never masks the run outcome. `session_title_service` is the loop-owned notifier seam: after a visible user message is durably appended, the loop reports it synchronously, while the service owns immediate local metadata and any non-blocking Model request. The loop only reports; title selection, projection, cost policy, and persistence remain in Sessions. Runtime wires the real shared services into both canonical loops.
  - `child_loop(*, nesting_depth) -> ChatLoop` — builds a sub-agent child loop sharing this loop's runtime, streaming flag, attachment resolver, compaction service, reflection service, and Session-title notifier; only the nesting depth differs. Sub-agent Sessions carry metadata that makes the notifier skip title work, so internal fan-out never adds a title Model request. Used by `core/subagents/`.
  - `run_executor(content) -> RunExecutor` — returns a run-manager executor that runs `content` through this loop; the public way for other domains to hand `ChatRunManager` an executor without touching loop internals. The executor takes no project_id — the project is read from `run.project_id` inside `_execute_run` (the manager set it from the `start`/`enqueue` call), so a child/project Run executes project-scoped (used by `core/subagents/`).
  - **Session ownership versus working Project.** `project_id` remains the public Session/address scope and run/queue key; it is `None` for every Identity Agent. At admission the loop separately captures `working_project_id` from the addressed Config Agent's Project or the Identity Agent's explicit `root_project_id`. Queued work retains that stable id, resolves its current cwd when it starts, and fails before persisting new user content if the Project or repository is unavailable; Workspace is never a fallback.
  - **Working behavior.** `run.working_project_id` supplies Tool cwd, Project Files, Project Skills, prompt preview parity, compaction rebuilds, file mentions, and suppression of duplicate Visiting injection. `run.project_id` still supplies Session storage and Tool addressing context, so Rooted Identity Agents keep their own Sessions, permissions, Memory-backed Workspace, private Skills, and bare Subagent routing. Visiting still uses `find_by_cwd` only when an Identity Agent reaches another registered Project by absolute path. The Visiting reminder names the Project and its absolute cwd, scopes the auto-loaded instructions to work affecting that Project for the duration of the visit in the Session, and explicitly leaves the visitor's home Workspace and cwd unchanged; its existing trigger timing and once-per-Project-per-Session lifecycle are unchanged.
  - `send(agent_id, content, session_id=None, input_origin=None) -> ChatMessage` — loads the agent, validates model and connection, appends the user message, sends canonical history through the adapter, dispatches allowed tools, and returns the final assistant message.
  - `start_run(agent_id, content, session_id=..., internal=False, input_origin=None, sender=None, reply_surface=None, project_id=None, tool_restriction=None) -> Run` — server-facing entry point that requires an existing Session and starts the same execution model in the run manager. Internal Runs persist `content` as a note rather than a visible user message. `sender` is attached to non-internal user messages; `reply_surface` opts an interactive Run into the direct destination reminder above. `tool_restriction` remains dispatch-only and does not change provider definitions or the System Prompt.
  - `queue_run(agent_id, content, *, session_id, internal=False, input_origin=None, sender=None, reply_surface=None, project_id=None) -> QueuedRunItem` — validates the same prerequisites and enqueues through `ChatRunManager`. The immutable surface rides in the executor and is compared only when that item actually starts, so cross-accessor arrival order cannot produce a stale switch decision.
  - `continue_run(agent_id, session_id, project_id=None, *, reply_surface=None) -> Run` — starts a new visible Run from a non-user unresolved checkpoint without appending a user message. An optional surface note is appended as the newest persisted note before the synthetic Continue instruction.
  - `build_queue_update(agent_id, session_id, content, input_origin=None, reply_surface=None, project_id=None) -> tuple[str, RunExecutor, str]` — returns replacement queue data without mutating queue state; the replacement executor retains the supplied surface. Project-scoped callers must still pass the address's `project_id`.
  - `compact_session(agent_id, session_id, instruction=None) -> str` — manual `/compact` implementation; returns a user-facing reply string. The optional `instruction` is the free-text `/compact <instruction>` argument, threaded into the summarization prompt (see `compaction.md`). Refuses while a Run is active for the session, loads persisted compaction settings, resolves the summary adapter through the same `_resolve_summary_adapter` path as auto-compaction, appends one checkpoint with History guidance on success, closes opened adapters, and converts compaction failures into `"Compaction failed: ..."` replies instead of raising. `TriggerService.compact_session` is a thin delegate to this method.
- `core/chat/content_blocks.py` owns `TextBlock`, `MediaBlock`, `FileBlock`, and `FileMentionBlock`, plus dict round-trip helpers for persisted JSONL content lists. `FileMentionBlock` (`{path, status, text, size_bytes}`, `status` ∈ `inlined`/`too_large`/`not_text`/`missing`) is a send-time snapshot of a file the user `@`-mentioned in the composer; `text` is present exactly when `status == "inlined"` (validated on parse).
- `core/chat/file_mentions.py` owns `@`-mention support end-to-end: `resolve_mention_root` (project cwd for a project address, else agent workspace — mirrors `ToolContext.effective_cwd`), `list_mention_files` (gitignore-aware cwd listing for the picker, capped at `MENTION_FILE_LIST_LIMIT` with a truncation flag, reusing the `core/tools/search.py` walker with a context-less `SearchBudget`), `expand_file_mentions` (snapshots each mentioned file into a `FileMentionBlock` — inline text up to `MENTION_INLINE_MAX_BYTES` (128 KiB), degraded reference otherwise — and stamps an inlined snapshot as a read in `runtime.file_read_state` so a later edit needs no read call), and `file_mention_request_text` (the provider-text render used by the block resolver). Expansion runs at the RPC edge (`chat.send`/`chat.stream`/`chat.queue_update` accept an optional `file_mentions: [str]` param) **before** Run start and before busy-session enqueue, so a queued message carries the files as the user saw them at send time; a file changed after the snapshot correctly trips the stale-guard on a later edit.
- `core/chat/block_resolver.py` owns last-mile attachment resolution from persisted content blocks to provider-ready dicts just before adapter calls. A `file_mention` block always resolves to the same plain-text render regardless of turn (a durable snapshot — replayed history stays byte-identical, prompt-cache friendly). A text attachment remains a sole `FileBlock` in the Session and is rendered from its blob through `core.tools.read.render_text_file`, so direct attachment input has the `read` tool's exact 50 KiB / 2,000-line / continuation behavior without persisting its full body in history.
- **Auto-injected files count as read.** `ChatLoop._stamp_prompt_files_read(session_id, paths)` registers files vBot auto-shows the model as read-before-write for the session (via `runtime.file_read_state`, see `file_state.md`), so the agent can `write`/`edit` one without a redundant `read` call. Two feeders: `_build_request_messages` passes a fresh `read_paths` list into `build_system_prompt` (collecting SOUL, the on-disk pinned-memory files, the project auto-load files, workspace `{include:…}` — see `prompts.md`) and stamps the result every request, so the stamp always reflects what the model currently sees and a later on-disk change still trips the stale guard; `inject_visiting_project_files` stamps the visited project's files via `render_project_files(on_read=…)`. Only files actually inlined are reported (a missing/unreadable/not-yet-created one is not).

## Conventions

- Timestamps are UTC ISO 8601 with an explicit offset.
- UTC timestamps using either `+00:00` or `Z` are accepted when reading persisted messages.
- Public/server-facing session identifiers are UUID strings. Storage-level ID validation and path construction rules are owned by `core/sessions/`.
- Current code can still create a session implicitly when `ChatLoop.send()` is called without an existing `session_id`, or create the named session if it does not yet exist. This describes current implementation behavior and should not be mistaken for the intended public/server product contract.
- Only user messages may persist `list[ContentBlock]` content. System, assistant, tool, note, and error messages remain string-or-null content only.
- Replay of persisted assistant `reasoning`/`reasoning_meta` into provider requests is governed by the adapter's `ReasoningReplayPolicy` (`none` / `current_run` / `full_history`, declared in adapter code — see `providers.md`). The chat layer resolves the policy from the live adapter per request build (`_resolve_reasoning_replay_policy`, tolerant of adapters without the hook → `current_run`) and owns all history shaping; the fallback path resolves from the fallback adapter. `current_run` — the universal default — keeps reasoning only on the active run's assistant turns; `none` strips it everywhere, including the live tool-continuation turn; `full_history` keeps reasoning on assistant entries whose persisted `model` passes the **same-model gate**: bare-model comparison against the agent's current model with the optional `::<connection>[:<account>]` suffix stripped on both sides (`parse_bare_model`). Under `full_history`, same-model reasoning-only assistant turns stay in the request history instead of being skipped as empty; gate-failing entries are stripped/skipped as under `current_run`.
- Current-turn `reasoning` and `reasoning_meta` must be preserved unchanged during tool-use loops when the same assistant turn continues after tool results (except under the `none` policy). Mid-run rebuilds restore `reasoning`/`reasoning_meta` for **every** assistant entry of the live request list, matched by message id (`_restore_in_run_assistant_reasoning`), so `current_run` means the same thing on the incremental and the rebuild path.
- Notes are kernel-internal background events. They remain in JSONL history as `role: "note"`; ordinary notes become synthetic user messages containing one or more `<system-reminder>...</system-reminder>` blocks, while passive `[channel-message] ` notes become their own untrusted quoted-context message and skill-context notes become their own `<skill_content>` user message. Provider adapters must never receive `role: "note"`.
- Run summaries are kernel/UI annotations. They remain in JSONL history as `role: "run_summary"`, are returned by normal history RPCs, and are never embedded into provider requests or rendered as normal chat bubbles.
- `role: "agent_takeover"` stays in JSONL history and is returned by normal history RPCs, but is never embedded into a provider request — `_assemble_request_history` skips it with a plain `continue`, exactly like `run_summary`. It is **not** a `note`, so `_is_visible_history_message` passes it through; the WebUI renders it as a timeline divider, composing the localized label from the `{"from","to"}` address JSON in `content`. It is not counted in token/turn counting (only `role == "user"`/assistant usage is). Written by the `/agent` move (below).
- `role: "compaction_checkpoint"` stays in Session JSONL but is never sent directly to providers. A new checkpoint owns a self-contained canonical Projection beginning with its `[compaction-summary]` note; request assembly uses that Projection plus messages appended after the checkpoint and never recovers hidden pre-checkpoint history. An existing old checkpoint is accepted unchanged and materialized in memory from its summary plus surviving `tail_boundary_id` slice, so the next new checkpoint can compact it cumulatively without rewriting the old record. **Activated skills stay loaded across compaction:** activations whose carrier is absent from the effective Projection are re-injected ahead of the summary in activation order, while surviving carriers retain their chronological position and are not duplicated. See `compaction.md` for Strategy and Policy resolution rules.
- Each provider request is assembled from one loaded canonical Session snapshot. Chat derives Session Tool grants from that snapshot, builds provider Tool definitions first, passes their exact names into System Prompt owner gates, and then builds effective Context and dispatch configuration from the same snapshot; this prevents the model-visible Tool set and executable Tool set from drifting at a Compaction boundary.
- If the latest checkpoint Projection omitted the newest complete, unconsumed Assistant Tool-call batch, effective Context overlays that canonical batch until a later Assistant message consumes it. This preserves Provider Tool-cycle continuity without recovering any older hidden history.
- Notes generated during a tool-use turn must not appear between an assistant message with `tool_calls` and that turn's tool-result messages, either in JSONL persistence or in the provider request history. Such notes are deferred until after the last tool result for that assistant turn. That deferral only covers notes added through the Run's own session handle; an out-of-band Channel observation or `channel_send` append is serialized instead by `ChatSessionManager.write_lock(...)`, which the Run holds across its whole tool cycle (see `sessions.md`).
- Reply-surface placement and the initiating visible/internal message append share the Session write lock at executor start. Speech-transcription notes are appended first, then the surface reminder, then the unchanged user message; an internal interactive prompt follows the surface note directly. This ordering does not alter the System Prompt, prompt fragments, public message schema, or existing history bytes.
- Normal visible user turns may carry `input_origin="speech_transcription"`. The chat loop persists a kernel-internal note immediately before the visible user message so provider requests see a `<system-reminder>` that the following user message came from speech-to-text and may contain transcription errors. The visible `role: "user"` message remains unchanged.
- User messages may carry `sender: {id, display_name}` (platform identity of the human who sent them; `from_dict()` rejects the field on every other role). Attribution is rendered only at provider-request build time in `_message_to_request_dict`: string content gets a `[<display_name>|<id>]: ` prefix, block content gets a leading text block with the tag, and `[ ] | \r \n` are stripped from both tag parts (a part that sanitizes to empty becomes `unknown`). The `sender` key itself is never sent to providers, and persisted content never contains the tag — the tag is derived from platform metadata, not message text, so a participant cannot forge another participant's tag by typing a look-alike prefix. Which messages carry a sender is a channels-domain decision (group conversations only in v1; see `channels.md`). WebUI/CLI sends and `ChatLoop.send()`/`build_queue_update()` have no platform sender and never set the field.
- Auto-compaction is evaluated only at safe completed Model boundaries. Summary+Tail may run after a complete Tool-result cycle or a final assistant response; Continuation waits for a final assistant response so the Engine receives the exact completed active request prefix. Any rebuilt request preserves `reasoning` and `reasoning_meta` for all current-run assistant turns surviving in the Projection (matched by message id), not just the latest Tool continuation; the rebuild flows through the same policy-aware shaping helpers as fresh history.
- Failed Runs may append `role: "error"` messages to JSONL history. `error_kind` must be non-empty when writing; unknown future `error_kind` values are accepted on read. LLM-visible error kinds are embedded into later provider requests as `<system-reminder>` blocks; non-visible error kinds stay in history/UI only.
- Skill-context notes are kernel-internal persistence records. They remain in JSONL history as `role: "note"`, are filtered from normal history, and are rendered into provider requests as standalone `<skill_content>` user messages **at their chronological position** (never folded into a `<system-reminder>` block, never hoisted to the request front). They follow the same tool-cycle deferral discipline as other notes, so a skill message can never split an assistant↔tool-result adjacency. Because activation appends at the conversation tail, loading a skill never shifts the request prefix — the provider prompt cache stays warm.
- User messages can trigger deterministic skill activation before provider requests with `/skill-name` at the start of the message or `$skill-name` anywhere in the message. The original user message is preserved unchanged.
- `$skill-name` is always interpreted as a skill activation hint, never as a built-in command route. If it matches an allowed loadable and currently available skill, the chat loop persists that skill's `<skill_content>` context directly after the original user message (rendered in place in the request); if it does not match or has unmet required vBot requirements, the original message remains unchanged and an internal system reminder explains why activation did not happen.
- **Agent-aware, Rooted-aware Skill resolution.** `runtime.skills_for(skill_project_id, identity_agent_id)` receives the admitted working Project plus the Identity Agent id for Rooted Identity work, while Config-Agent work passes its Project and no identity id. Prompt, activation, autocomplete, Tool context, and compaction therefore share one pool without applying Project Config-Agent ceilings to the Identity Agent or exposing a same-named private Skill home to a Config Agent.
- **Session-pinned skill catalog (prompt-cache invariant).** `_pinned_skill_catalog(agent_id, session_id, agent, registry, project_id)` snapshots the rendered catalog **text** into session metadata (`PINNED_SKILL_CATALOG_META_KEY`) on a session's **first** build and reuses it for the session's lifetime, including the compaction rebuild — so a skill written mid-session never changes that session's `<available_skills>`, and the provider prompt cache holds. `build_system_prompt` takes this snapshot as `skill_catalog`; `provider_tool_definitions` no longer needs it — `skill` and `skill_manage` are ordinary allow-list tools offered per the agent's `allowed_tools` (`skill_manage` identity-only), so **tool presence is derived from policy, not pinned** (and, like any tool, stable across a session unless the agent's config changes). Skill **activation** (the `skill` tool, incl. its list mode) and `/`–`$` triggers stay **live** against the current registry, so a newly authored skill is loadable at once; a new session pins a fresh snapshot. The agent's `skill_manage` tool (and `/learn`) author into the agent's own home and call `invalidate_agent_skills` so the live registry updates immediately.
- **Mid-session skill availability announcement.** Because the catalog text is pinned, a skill that becomes available+allowed to the agent *after* the session's first build never appears in the prompt. At run setup `_announce_newly_available_skills(...)` diffs the agent's current available+allowed skills against a per-session `seen_skills` set in session metadata: the first build seeds the set silently, and any later addition is announced **once** via a tail `<system-reminder>` note (`SKILL_AVAILABLE_NOTE_PREFIX`, stripped at render) listing the new skills' name + description. Additions only — a skill going away is not announced. Source-agnostic: authored (`skill_manage`), opted-in (bundled/global), globally added, or freshly scanned all surface identically. The diff reuses the registry already resolved for the run (a small in-memory set comparison), and writes metadata only when the set actually grows. See `skills.md` → Terms → Skill Availability Announcement.
- Recognized built-in slash commands (`/agent`, `/compact`, `/continue`, `/handoff`, `/help`, `/learn`, `/model`, `/new`, `/reflect`, `/rename`, `/status`, and `/stop`) are not part of that skill-activation path. They are handled earlier by the shared command dispatcher; unrecognized slash text still reaches the existing skill-trigger logic unchanged.
- Command action results mean the dispatcher recognizes the command while the accessor executes behavior that needs runtime services: `/compact` compacts the current Session in the chat's own scope — a project chat compacts its project session and resolves a project agent, an identity chat its identity session — by threading the chat's `project_id` from the RPC handler through `TriggerService.compact_session` into `ChatLoop.compact_session` (passing any free-text argument through as a compaction instruction), `/continue` starts the checkpoint-backed no-new-message Run, `/new` creates/switches the current Session where the accessor can honor that, and `/rename [name]` sets or clears the Session's display title (no argument clears it; the accessor routes it through the same `session.rename` handler as the WebUI, so the title write and the session-list refresh stay in one place).
- `CommandDispatcher.recognizes(text)` reports whether `dispatch()` would handle the text as a command, without running handler side effects (`dispatch("/stop")` cancels a Run). Accessors that gate command authorization (channel engine: group owner check) must call it before `dispatch()`; both share one internal command-resolution path, so recognition cannot drift between them.
- Built-in slash commands are intercepted before `ChatLoop.start_run()` only for pure-text messages. Attachment-bearing or multi-block messages bypass command dispatch and continue through the normal Run path.
- Normal server history responses and the standard WebUI timeline must filter out notes; only debug-specific surfaces may expose them intentionally.
- Consecutive notes in loaded history are grouped into one synthetic user message. Notes added while a Run is active are drained before each model request, including follow-up requests after tool results, but note embedding must still preserve immediate assistant-tool adjacency within a tool-call sequence.
- If a Session later continues with a different provider, stale `reasoning_meta` from the old provider must never be sent to the new provider. History rebuilds for new Runs strip these via `_message_to_request_dict` (under `full_history` the same-model gate strips model-mismatched entries); the in-run model-fallback switch additionally strips `reasoning`/`reasoning_meta` from the assistant entries of the reused request-messages list before the first fallback request — this unconditional fallback strip stays regardless of policy.
- `agent.model` must be in `<provider>/<model-id>` form and may optionally carry `::<connection-local-id>[:<account-id>]` at the end. An empty model or missing provider raises `ChatError` before an adapter request.
- Runtime target resolution parses `agent.model` with `rpartition("::")`. When a suffix is present, the chat loop reconstructs the full connection ID as `<provider>:<suffix>` verbatim (the suffix may pin a credential account; resolution happens in the credential resolver — see `providers.md` → Accounts). Without a suffix, the chat loop picks the first usable connection for the model provider in provider-config order, **filtered by the model's `connections` allowlist** (`_first_usable_connection_id` in `model_resolution.py`): a connection-bound model (e.g. a subscription-only model) never silently resolves onto a forbidden connection just because that connection is configured and listed first. An empty allowlist (or an unknown/custom model id) means no restriction; when the allowlist is non-empty and none of its connections is usable, resolution raises `ChatError` instead of falling onto a wrong connection. This runtime enforcement is the counterpart to the save-time guard `_ensure_model_connection_supported`, which only checks explicitly pinned suffixes.
- Queued display previews are derived from plain-string content or the concatenated text of `TextBlock` items and fall back to `[attachment]` when a queued payload has no text blocks.
- If a retryable `ProviderError` escapes adapter retries and the Agent has a resolvable `fallback_model`, the chat loop may switch to that fallback for the rest of the current Run. The switch emits `model_fallback_activated` and persists a note so the next provider request sees the change as a `<system-reminder>`. The Agent config itself is not mutated, so the next turn starts from the primary model again.
- `fallback_model` follows the same optional `::<connection-local-id>[:<account-id>]` convention as `model`; fallback resolution uses that suffix when present and otherwise auto-resolves the first usable connection for the fallback provider under the same `connections`-allowlist filter. When no allowed connection is usable, the fallback is skipped (treated as no fallback) rather than misrouted.
- Run-local model fallback is part of the shared ChatLoop execution path and therefore applies equally to direct and internal Runs that execute through that path.
- The chat loop does not prevalidate model existence in static model resources; unknown model IDs are left for the provider API to reject.
- Surfaces that need the catalog model key rather than the pinned connection form, such as context-window lookup or display helpers, must strip the optional `::<connection-local-id>[:<account-id>]` suffix first.
- Attachment resolution happens in the chat layer, not inside provider adapters, and is a **provider-agnostic intersection** of model capability and adapter wire capability. The resolver receives both the agent model's `input_modalities` (via `_model_input_modalities`, empty set for unknown models) **and** the adapter's `wire_media_types` (via `_resolve_wire_media_support(adapter, model_id)`, which mirrors `_resolve_reasoning_replay_policy` and tolerates test doubles without the hook → `frozenset()`). Both are resolved at the call sites that already resolve `replay_policy` and threaded through `_build_request_messages` and the tool-loaded `_inject_read_media` path. An attachment goes native only on the current turn when the model advertises the modality **and** the wire carries the concrete media type; otherwise it degrades (audio→STT, else path note). Resolution is **one block in, one or more out**: current-turn image/native-audio `MediaBlock`s and a current-turn PDF `FileBlock` become their native dicts, each **followed by a `Path:` note** so the agent also holds a file handle; everything else (unsupported wire, non-capable model, historical media, video) becomes a text path note. A `text/*` `FileBlock` becomes that path note plus the exact bounded text rendering the `read` tool would return; a following full-text duplicate from an already-persisted message is omitted. A plain `TextBlock` stays embedded text. No provider format constant lives in the chat layer. Details and the per-modality table live in `.vorch/domain-maps/attachments.md`.
- Capability checks also happen in the chat layer, and none of them abort the run: whenever an attachment cannot be delivered as native content — a current-turn image to a non-vision model, or audio that can be neither sent natively nor transcribed (no service, STT failure, or empty result) — it degrades to a path note that states why and carries the file path, so the agent can still route the file (e.g. hand the path to a capable sub-agent). Only a genuine stored-blob I/O fault still raises `ChatError` (via `AttachmentResolveError`).
- `_build_request_messages` is async because attachment resolution may call the speech-to-text provider.
- **Tool-media injection.** A tool may emit a `read_media` artifact (`{kind: "read_media", attachment_id, filename, media_type}`) to ask the loop to show the model a media file it loaded — currently `read` on an image (see `tools/read.md`). `_dispatch_tool_calls` returns `(tool_messages, media_injections)`; the loop appends a synthetic current-turn `role: "user"` message holding one `MediaBlock` **after** all tool results, preserving the tool-cycle invariant (results before any non-tool message). Only that small `MediaBlock` reference is persisted to the Session, so a later run degrades it to a path note through the normal once-at-start resolver and context stays small. Because the resolver runs once *before* the tool loop and never again inside it, the injected message is resolved **inline at injection** (`ContentBlockResolver.resolve_messages` with the message id marked as the current turn — the native media dict now trailed by its path note) and only the resolved dicts are appended to the in-flight request list — never to the persisted Session. A non-vision model (no `image` modality) or an absent resolver degrades to a plain text note instead of raising, so the run never aborts.
- In streaming mode, provider adapters yield normalized deltas that the chat loop accumulates into the final canonical assistant message; the final message is persisted at the same turn boundary as non-streaming and remains authoritative over transient deltas.
- Tool calls from the same assistant turn execute concurrently; the next model request waits until every sibling tool call reaches a terminal result.
- Tool result messages are persisted in the assistant's original tool-call order, even when lifecycle result events complete and stream in a different order.
- Tool calls are dispatched only through the runtime tool registry and agent allowlist. Normal tool execution failures, including disallowed or unknown tools, are appended as failed result envelopes so the assistant can recover.
- Adapters returned by runtime are closed after each `ChatLoop.send()` turn when they expose `aclose()`.
- **Tool-cycle invariant for provider requests:** every assistant turn with `tool_calls` must be followed in the request history by exactly one tool-result entry per `tool_call_id`, in the assistant's original tool-call order, before the next non-tool message. This invariant holds for both the live history path and the compaction-tail rebuild path; both run through `_embed_notes_into_request` and the same dangling-tool-call repair.
- **Dangling-tool-call repair:** when an assistant turn's tool results are missing from the loaded Session history (because the previous Run was cancelled, crashed, or interrupted before persisting them, or because the JSONL file was left in an inconsistent state), the request-build path synthesizes a request-only tool message for every missing `tool_call_id`. The synthesized entry uses the stable tool-failure envelope (`tool_failure(...)` from `core.tools`) with `code == "result_unavailable"` and a message stating the tool run was interrupted before a result was recorded, carries the original tool call's `name`, and uses the original `tool_call_id`. Synthesized entries are never written to the Session JSONL — they exist only in the provider-request payload — so existing broken sessions recover on their next request without any session migration.
- **Cancel-during-tool-dispatch persistence:** the chat loop's tool-dispatch path never discards computed tool results because the run is cancelled. `_dispatch_tool_calls` does not raise between `executor.execute_many` returning and its result list being built, and `_send_until_final`'s persist loop records every sibling tool message before honoring `run.raise_if_cancelled()`. The Run still ends as `cancelled` (the cancel is honored at the end of the persist block, not in the middle), and per-tool `cancelled_by_user` envelopes from well-behaved handlers keep the persisted history truthful.

## Token Usage

- Provider adapters extract token usage from responses: OpenAI maps `prompt_tokens`/`completion_tokens` to canonical `input_tokens`/`output_tokens`; Anthropic maps directly from `usage.input_tokens`/`usage.output_tokens`. If a provider doesn't supply usage (e.g., local providers without usage reporting), the backend falls back to a 4-chars-per-token estimation via the structured message estimator in `core/utils/tokens.py` and marks the result with `"estimated": true`. The fallback counts provider-relevant fields such as text, content blocks, tool calls, and active reasoning fields, but ignores storage metadata such as ids, timestamps, timing, and usage.
- `ChatMessage.assistant()` accepts an optional `usage: JsonObject | None` field (canonical keys: `input_tokens`, `output_tokens`; optional `cache_read_tokens`, `cache_write_tokens`, and `estimated` boolean). Usage is only valid on assistant messages and is rejected on other roles by `from_dict()`.
- Canonical `input_tokens` is the **total prompt including cached tokens**. Adapters whose wire reports cache tokens separately from input (Anthropic-style `cache_read_input_tokens`/`cache_creation_input_tokens`) must add them onto `input_tokens` during normalization; OpenAI-style wires (`prompt_tokens_details.cached_tokens`, Responses `input_tokens_details.cached_tokens`) already include cached tokens in the prompt count. `cache_read_tokens`/`cache_write_tokens` are present only when the provider reported them. This total-input semantic is what the auto-compaction threshold check and the WebUI token badge rely on.
- `_message_to_request_dict()` always strips `usage` from assistant history before it is sent to provider APIs; `reasoning`/`reasoning_meta` are stripped or kept according to the resolved `ReasoningReplayPolicy` and same-model gate (see Conventions). Readable `reasoning` still round-trips for reasoning-aware adapters on the active tool-continuation path, except under the `none` policy.
- The live tool-continuation request for the current turn appends the assistant message via a helper that strips `usage` while preserving `reasoning`/`reasoning_meta`, so per-turn token accounting is never echoed back to the provider even mid-loop.
- After each assistant turn is finalized and persisted, the chat loop emits `model_step_usage` with `{usage, session_usage}`. `usage` is the exact persisted provider-reported or estimated turn payload; `session_usage` is the canonical whole-Session total after that turn. This is a non-visual Run update for live consumers, including tool-only steps where no assistant text exists. The `run_completed` payload still includes `usage` from the final assistant message when available; failed or cancelled terminal events do not add per-turn `usage`.
- **Whole-session usage totals.** `core/chat/usage.py` `aggregate_session_usage(messages)` sums provider-reported usage across a session's assistant turns into the canonical `session_usage` payload `{measured_turns, estimated_turns, cache_turns, input_tokens, output_tokens, cache_read_tokens, cache_write_tokens}` — token totals cover measured turns only (estimated turns are counted, never summed), and `cache_turns` counts cache-field *presence* so consumers can tell "provider reported zero cache" from "provider does not report caching". At the first model step the chat loop seeds this total once from the persisted Session, advances it with the same usage accumulator after each assistant append, and carries it on every `model_step_usage` event and in `Run.terminal_payload_extras`. The end-of-Run `finally` recomputes the persisted total after the run-summary append as a diagnostic-safe final authority (failure logged and swallowed), so every terminal outcome carries it. `chat.history` returns the same full-transcript payload even when its message page is a slice. The WebUI reads these persisted-server projections rather than calculating Session totals itself (see `webui.md`).
- In streaming mode, usage arrives as a `{"type": "usage", ...}` delta. OpenAI sends it only in the final streaming chunk (with `stream_options.include_usage`). Anthropic splits it across `message_start` (input tokens and cache token counts) and `message_delta` (output_tokens). The `StreamingAccumulator` collects these deltas and passes the optional integer `cache_read_tokens`/`cache_write_tokens` fields through (non-integer values are dropped); `finalize_assistant_fields()` includes usage in the finalized assistant fields.
- Provider wire specifics (e.g. GitHub Copilot's `/responses` and `/v1/messages` usage shapes) are normalized to the same canonical fields inside the adapters; raw provider SSE events and opaque reasoning metadata stay inside adapters and must never appear in Run event payloads. Per-provider details live in the provider maps.

## Constraints & Gotchas

- Unknown future fields in session JSON may appear; avoid making chat depend on provider-specific metadata shape.
- Model IDs in messages use user-facing `<provider>/<model-id>` form for traceability, while adapters receive the provider-specific `model_id` part.
- The loop stores user, assistant, tool, and note messages in session files. The system prompt is assembled for each request rather than appended as normal chat history. If the assembled system prompt is empty or whitespace-only, the provider request omits the system message entirely.
- **Stream-break recovery has one provider-agnostic owner: `decide_stream_recovery` in `core/chat/streaming.py`.** It reads only normalized vBot errors plus the attempt state — `emitted_visible_delta`, `can_restart` (restart budget remaining), `has_partial_content`, `finish_received` — and returns a `StreamRecoveryAction` (`ACCEPT_COMPLETE` / `RESTART` / `FALLBACK` / `PRESERVE_PARTIAL` / `FAIL`). The three recovery predicates (`_is_streaming_fallback_error`, `_is_stream_restartable_error`, `_is_model_fallback_trigger`) live in `streaming.py` too; `events.py` keeps only event projection and error persistence. The decision lives in `streaming.py`; executing each action (the side effects) stays in `_consume_stream_attempt` in `chat.py`. Recovery is never decided by inspecting error message text. The recovery matrix:
  - **After a normalized finish delta:** any later normalized provider/transport error → `ACCEPT_COMPLETE`. The finish delta is the logical response boundary, so a missing transport terminator cannot retroactively mark completed text as interrupted or discard a completed tool-only turn. Deltas received between the finish and the transport failure (notably usage) remain accumulated normally.
  - **Before any visible delta** (clean replay still possible): `ProviderStreamingUnsupportedError` → `FALLBACK` (one non-streaming retry); a retryable transient (`NetworkError`, `ProviderTimeoutError`, retryable `ProviderError`, or a `StreamingChunkTimeoutError` chunk stall) → `RESTART` while restarts remain (full fresh stream, up to `MAX_STREAM_RESTARTS` = 2 replays beyond the first attempt, via `_StreamRestartNeeded`); otherwise `FAIL`. A restart-exhausted retryable `ProviderError` then propagates and can still trigger model fallback; a `NetworkError` fails the Run; a chunk stall fails with a `timeout` error kind. `StreamingChunkTimeoutError` is a `StreamingError(VBotError)` (no `retryable` attribute), matched by type. Discarded restart attempts write no checkpoint delta because nothing readable was emitted.
  - **After a visible delta** (replay would duplicate, so the stream is never replayed): accumulated visible **content** → `PRESERVE_PARTIAL` — the partial answer is finalized into an `interrupted` assistant turn (no finish reason, any in-flight tool call dropped because it was never executed = side-effect-free), the Run ends as a normal turn-less assistant turn, and the Continuation Checkpoint preserves it for the next visible Run. This *replaces* the old "propagate + maybe model-fallback" path after visible output (re-running would duplicate). A **reasoning-only** interruption (no content) propagates the error while the checkpoint retains the readable Thinking. This whole decision sits *inside* the model-fallback wrapper, so before any visible delta a same-model restart is tried before switching models.
  - User cancel is **not** a recovery case — `CancelledError` is `BaseException`-side and never reaches `decide_stream_recovery` (the typed `except` catches only `ProviderError`/`NetworkError`/`StreamingChunkTimeoutError`) — but it **shares the preserve-partial finalize**: `_consume_stream_attempt` catches `asyncio.CancelledError`, and when `run.cancel_requested` is set and the accumulator holds visible **content**, it returns the same `_finalize_interrupted_partial` result as `PRESERVE_PARTIAL` (interrupted assistant turn, in-flight tool calls dropped) so output the user already saw never vanishes (GLOSSARY → Cancel). `_send_until_final` then skips its post-request `raise_if_cancelled`, persists the interrupted message, skips auto-compaction, and returns normally — the run manager sees `cancel_requested` and marks the Run **cancelled** anyway, so a cancel is never reclassified as transient or completed. The settled `assistant_output` event passes the cancel suppression via `Run.emit(..., allow_after_cancel=True)` (it re-publishes already-seen text, not a late result — see `runs.md`). A cancel with **no** visible content persists no assistant turn, but the checkpoint retains any readable Thinking and the cancelled `run_summary` remains the timeline anchor.
- Local/loopback providers are exempt from the per-chunk stall guard: `_resolve_chunk_timeout` resolves the connection's effective base URL and, when `is_local_provider_base_url` matches (loopback, `localhost`/`*.local`/`*.localhost`, RFC1918 private, or link-local), passes `timeout_seconds=None` to `iter_with_chunk_timeout` so a long-silent local prefill (Ollama/llama.cpp/vLLM) is not aborted. Remote providers keep `STREAM_CHUNK_TIMEOUT_SECONDS`. Detection lives once in `is_local_provider_base_url`.
- Cancellation is best effort: once requested, late non-terminal output is not forwarded (the one exception being the preserved-partial `assistant_output` above, which finalizes already-shown text), new tool dispatch is blocked or suppressed, and the Run ends as `cancelled`. Run cancellation also calls the runtime `ProcessManager.cancel_scope(run.id)` hook so active host processes started by tools in that Run are killed.
