# Chat

Provider-agnostic conversation representation and Agentic Loop execution in `core/chat/`.

## Overview

Chat owns canonical messages, provider-request shaping, Skill/Tool turn orchestration, and the loop that advances one admitted Run through Model and Tool steps. Run lifecycle, cancellation state, and Queue coordination live in `core/runs/`; Session persistence lives in `core/sessions/`; Compaction policy, checkpoint construction, and Compaction-run coordination live in `core/compaction/`; Provider wire translation lives in `core/providers/`. Chat uses those public APIs and must not absorb their storage or lifecycle internals.

Chat is the execution seam between Sessions and Runs: it loads canonical Session history, resolves the Agent/Model/Tools, builds provider-ready context, persists canonical results, and emits provider-agnostic Run events.

## Data Model

- `ToolCall` (`core/chat/messages.py`) is the canonical Assistant-requested invocation: `id`, `name`, JSON-object `arguments`, and an optional persisted `rejection` (`code`, Model-visible `message`, stable raw-attempt `fingerprint`). A rejection preserves an addressable malformed Provider attempt while marking it ineligible for dispatch.
- `ChatMessage` is the canonical conversation/read projection; Tool results and Run footers are reconstructed from their owning SQLite entities. Every role carries `id`, UTC-offset `timestamp`, and `role`; constructors and `from_dict` enforce role-specific fields.
- Provider-visible conversation roles are `system`, `user`, `assistant`, and `tool`. Only `user` may carry `list[ContentBlock]`; Assistant messages may carry readable `reasoning`, opaque `reasoning_meta`, semantic `phase`, Usage and Tool Calls. Presentation-only and internal fields (`tool_display`, `output_files`, `reasoning_summary`, `reasoning_timing`, `reasoning_scope`, `interrupted`, the Sub-Agent reply target) persist for History but never reach a Provider request (`chat/request-building.md` -> Canonical message fields).
- Kernel/history roles are `note`, `compaction_checkpoint`, `error`, `run_summary`, `agent_takeover`, and `history_edit`. Their Provider/public visibility differs intentionally: notes and edit controls are internal, checkpoints contribute through their Projection, errors are conditionally Model-visible, takeover annotations never enter Provider requests, and a run summary enters only as the interruption notice of a Run that stopped unfinished.
- `MessageSender` (user messages only) identifies a human or peer Session; its source fields and framing belong to `chat/request-building.md`. `ReplySurface` identifies the submitting accessor: WebUI/Desktop, terminal TUI, or one configured Channel (`direct` or `group`); only a delivered Steer changes the active Run's reply context. Channel ingress can include runtime-only target/thread facts, passed unchanged to Tool dispatch and never persisted or shown to the Model.

## Interfaces and source ownership

- `core/chat/messages.py` owns `ChatMessage`, `ToolCall`, `MessageSender`, `ReplySurface`, constructors and JSON round-trip; `_message_records.py` holds the validated Message value records and constants, `_message_validation.py` (role/payload checks) and `_message_history.py` (effective Compaction history, checkpoint projections, note chronology) are private parts of the same owner. Public record imports route directly to `messages.py` without loading the Agentic Loop. Compaction and Automation use history/projection operations through `core.chat`, never private modules.
- `core/chat/wire_shaping.py` owns the canonical-to-provider projection (history assembly, note embedding, reasoning replay shaping, Tool-call repair, fallback request dicts) and provider-response ingestion (`chat/request-building.md`). It also owns the host-specific Tool-name projection (`tools.md` -> Model Tool names): `model_facing_request` renames Tool definitions, Assistant Tool Calls and Tool messages and neutralizes look-alike `<system-reminder>` tags as the last step before the adapter, and response ingestion maps returned Call names back to registry names. Public `note_request_messages` and `system_reminder_request_message` expose the deliberate Note projection to other domains, and `core.chat.EffortState` exposes prompt-epoch effort state.
- `core/chat/chat.py::ChatLoop` owns admission; `_accessor_inputs.py` captures and restores durable Accessor input through Sessions and the shared Run Queue. Execution contracts: `chat/run-execution.md`.
- `core/chat/commands.py::CommandDispatcher` (protocol records/parsing in `_command_types.py`, Extension catalog/outcome checks in `_extension_commands.py`) owns Built-in and Extension Commands end to end; RPC and Channels supply addressing and `ReplySurface` and project outcomes generically, and command-specific behavior must not return to a transport (`chat/commands.md`).
- `core/chat/model_resolution.py` owns Model-string parsing, exact Connection selection, per-Model Connection allowlists, and Run-local fallback resolution. Its public `resolve_model_target` resolves a Model binding for both Chat and Session titles.
- An interrupted Run leaves only canonical history (its persisted work plus the `run_summary`'s `completion_reason`, from which `wire_shaping.py` renders an interruption notice); `_stream_draft.py` keeps unpersisted streamed output crash-safe in the Sessions Stream draft (`chat/run-execution.md` -> Interruption). `core/chat/streaming.py` owns normalized delta accumulation, chunk timeout, provider-agnostic stream-recovery decisions, Tool Call completion during the stream (`chat/run-execution.md` -> Tool Calls during the stream), and `stream_model_response`, the streaming request helper for every Model request outside Chat (`chat/run-execution.md` -> Streaming requests outside Chat).
- `core/chat/recovery.py` owns the Run-local budget shared by Model retries, partial continuations, and configured Model fallback (`chat/run-execution.md` -> Streaming recovery).
- `core/chat/tool_dispatch.py` owns effective Tool dispatch, live pre-dispatch denials (before handlers and Extension Tool hooks), Extension Tool hooks, Tool lifecycle emission, Skill activation (`_skill_activation.py`), `read_media` extraction, and Extension Tool result payload staging. Every dispatched call emits exactly one `tool_call_started` and one `tool_call_result`: an exception from Extension hook dispatch or the bookkeeping around the handler becomes that call's `tool_execution_error` result (`test_tool_dispatch_extensions.py`). `_tool_context.py` owns Run-local Tool authority, staged payloads and acknowledgement state; `_tool_registry.py` owns registry/hook execution and emission, and `_tool_result_projection.py` owns Result envelopes and media/display projection. Registry/result-envelope contracts: `tools.md`; Extension dispatch semantics: `extensions.md`.
- `core/chat/content_blocks.py`, `file_mentions.py`, and `block_resolver.py` own canonical content blocks, verified `@`-file snapshots, and last-mile media resolution; `output_files.py` resolves explicit `file:` markers in Assistant text (`chat/request-building.md` -> Content Blocks, mentions, and media). Blob storage and extraction live in `attachments.md`.
- `core/chat/usage.py` owns canonical whole-Session Usage aggregation. Provider adapters own wire normalization; the WebUI consumes the server projection rather than recalculating it.
- `core/chat/events.py` projects visible message/Tool/error events and strips opaque Provider data. Run sequencing and terminal lifecycle remain owned by `runs.md`.

## Invariants and conventions

- A successful Tool may request graceful turn completion through `ToolContext.request_turn_end`. Ordinary Chat Runs stop after every sibling Tool result has persisted, without another Model request; failed results cannot request completion. Extension-owned Runs keep their owner reconciliation decision.
- Tool Result facts persist `cancelled_by_user` as `cancelled`, alongside the legacy cancellation codes, so a user's stopped call never becomes a failed call in History.
- Chat remains Provider-agnostic. It may inspect declared adapter capabilities/policies but never Provider-specific wire payloads or raw SSE events.
- Chat starts or enqueues only through `ChatRunManager` and keeps no second Queue; one active Run per Session and busy-Session FIFO are Runs-domain invariants (`runs.md`).
- No caller can inject a Run-local Tool grant. The static Tool restriction and the live Tool-denial resolver are dispatch-only and never change System Prompt text or Provider Tool definitions (`chat/run-execution.md` -> Agentic progression and events).
- Each request is built from one active-lineage Session snapshot; the System Prompt is assembled per request and never persisted as history. Prompt-only inputs, the Provider Tool list, dynamic prompt blocks and the thinking effort are pinned per prompt epoch for prefix stability; changes within an epoch reach requests only as change notes, and every successful Compaction starts a new epoch (`chat/request-building.md` -> Skills and prompt-cache stability, Tool catalog per prompt epoch, Dynamic prompt blocks per prompt epoch, Thinking effort per prompt epoch).
- Every Assistant Tool-call batch is followed by exactly one Tool Result per `tool_call_id`, in declared order, before any non-Tool request message. This includes malformed/rejected Calls, unknown Tools, invalid arguments, handler crashes, and invalid results; concurrent execution must not change persistence/request order. Results missing after an aborted batch are repaired from durable Session evidence in the next Provider request, never from uncommitted handler results (`chat/request-building.md` -> Tool-cycle invariant and repair).
- `reasoning_meta` is opaque. Chat may preserve or strip it according to adapter policy and the exact persisted `reasoning_scope` but never interprets or exposes either field in Provider requests or public Run payloads.
- Notes are kernel-internal and excluded from ordinary history/UI. Any Model-visible rendering is an explicit Chat request-building rule; Provider adapters must never receive `role: "note"`. A note may also carry a display-only record (`messages.py`), valid only on notes: `model_fallback` (Model fallback switch), `goal_event` (`automation/goals.md` -> Goal rows), `subagent_messages` (`subagents/forwarding.md` -> message_parent). Only the note text reaches the Model, and an empty note never does.
- A Session of a Live Agent (`agent/builtin-agents.md` -> Live Agents) records a Live call: `start_run` and `start_run_in_new_session` refuse typed input to a Live Agent with `This Session records a Live voice call; it takes no typed messages.` unless the Run kind is `live`, as the Live backend's requests are.
- Session ownership (`run.project_id`) and its Working Project (`run.working_project_id`) are distinct. The Working Project supplies cwd, instructions, Skills and shared Memory in the existing Memory block; it does not move Identity Sessions, their Workspace or personal Memory, permissions, or Sub-Agent addressing.
- Chat never infers or injects foreign Project Context from filesystem paths a Tool used. An Identity Agent loads it explicitly through the `project` Tool, whose latest successful Result also routes Skill activation for that Session while the prompt-epoch Skill catalog keeps the admitted scope (`tools/project.md`).
- Visible output, canonical Assistant/Tool messages, and Run annotations persist at stable boundaries; transient streaming deltas are never Session records.
- Chat masks known Agent Secret values in Tool results and displays, user input and every Model request; persisted history is never rewritten (`secrets/agent-secrets.md` -> Masking).

## Constraints & Gotchas

- Model-response finalization owns the Reasoning/content boundary exactly once (`streaming.py`), and `_assistant_message_from_response` never parses again. Native readable Reasoning is authoritative; only replies without it use the shared inline fallback `core/providers/reasoning.py::split_inline_reasoning`, and literal tags in code examples stay text. Chat, Compaction and Session titles share this boundary (`chat/run-execution.md` -> Reasoning/content normalization).
- Public history hides notes and opaque reasoning metadata while retaining visible errors, Compaction separators, run summaries, Agent-takeover dividers and the display records of notes (record shapes and paging: `server/chat-rpcs.md` -> History, edit and timeline).
- The public `model` field persisted in messages uses user-facing `<provider>/<model-id>` form and names the route that actually answered: the Agent's Model string, or the active fallback binding, so Statistics attribute Usage and cost to that Model; adapters receive only their Provider-specific Model id.
- Unknown future JSON fields and `error_kind` values may appear. Do not make Chat depend on Provider-specific metadata shapes or a closed error-kind vocabulary.
- The per-step Model request shares the live request-state message dicts instead of copying them, and Tool lifecycle events share the canonical Tool Call's argument object and display snapshot; Context hooks get shallow copies (`extensions/capabilities.md`), image limiting copies on write and always returns a new list, and Provider Adapters treat request messages as read-only (`providers.md`). Code that must change a shared message, argument object, or nested value copies it first; Chat edits only its own live request state in place (live-view image limiting, fallback reasoning stripping).
- Adapters opened for a Chat turn are closed when they expose `aclose`; OAuth token refresh and HTTP error translation remain Provider-owned.

## Agent-facing text

This domain owns the context-command note, the Compaction checkpoint guidance, the steering reminder and interruption texts of Run execution, the reply-surface reminders and the Command texts; permission texts: `permissions/agent-facing-text.md`. Before you change, add or delete a sentence of them, read `chat/agent-facing-text.md`: it records why each sentence exists or names the supplement that does. Update its row for every sentence you change and add one for every sentence you add.
