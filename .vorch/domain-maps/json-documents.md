# JSON Documents

The cross-cutting Generation 1 contract (versioning, unknown-field preservation, write guard, snapshot freeze) of every durable JSON document in the data directory, whichever domain owns it.

## Overview

`core/json_documents.py` owns the contract mechanics (tests `tests/core/test_json_documents.py`); `core/config_validation.py` owns the shared transport-neutral reports and the JSON file loader. Each document's schema, records and normalizers stay with its owning domain. `DURABLE_DOCUMENTS` in `core/json_documents.py` is the single list of documents under the contract (kind -> data-dir relative pattern, `*` within one segment); read it there. A new durable JSON file joins it, with a `doctor config` validator, unless it falls under Outside the contract below.

## Document rules

- A document is a JSON object with a required top-level `format_version` (1 for most documents; 2 for `calendar/events.json` and `project.json`). Collections are named arrays (`jobs`, `events`, `actions`, `entries`, `groups`, `connections`), never bare arrays. `validate_format_version` refuses a missing version (the message ends with the database kernel's `older_format_hint`, `database.md` -> Evolution contract, item 6), an older one, and a newer one; a file written by a newer vBot is never overwritten.
- Each owner declares the object levels it models as a `JsonShape`: `json_document`/`json_object` (declared fields plus nested shapes), `json_map` (data-keyed objects; `drop_empty=True` for maps whose entries must hold a field: an entry holding only unknown fields loads as `{}` and keeps them, and the writer leaves out an entry still empty after the merge - Project overrides), `json_list(items, key=...)` (entries identified by a key field), `OPAQUE`. Loaders validate, then `strip_unknown_fields`, so records and normalizers see only modeled fields; unknown fields are warnings (`warn_unknown_fields`), never errors. Exception: an unknown part of a stored `permission_rules` set is an error, because it may restrict (`OPAQUE` shape, `permissions.md`).
- Tolerance applies only to documents read from disk: RPC and management input normalizers still reject unknown keys.
- An object shape can explicitly mark an already-retired field with `retired`; loaders omit it and writes remove it instead of preserving it as an unknown field. This implements the existing retirement of `librarian.model`, including section and path writes, without discarding unknown siblings. It does not replace the version-bump rule for future schema changes. Coverage: `test_settings_writes_remove_only_the_retired_librarian_model`.
- Version-bump rule: an optional field with a default is additive and needs no bump. Removing, renaming, or changing a field's type or meaning requires bumping that document's `format_version` together with an explicit offline converter (`database.md` -> Evolution contract); the application keeps no old-field branches. A new default that changes what existing documents mean is such a meaning change.
- Converters run in an update's verification start (`--verification-only`, under the update snapshot, so a failure rolls the update back) and through `vbot data-store convert --yes` for data directories the updater does not update (a checkout's); normal startup never converts and refuses the older document, whose diagnostic names that command (`validate_format_version(..., older_hint=...)`). A converter is idempotent: it changes only documents of the version it converts from. Today: `project.json` 1 -> 2 (`projects/configuration.md` -> Format version 2 conversion).

## Writing

- Owners persist through `write_json_document(path, body, JsonDocumentFormat)`: it re-reads the file on disk, refuses with `JsonDocumentWriteError` when `format.validate` reports an error, merges the file's unknown fields back into `body` at every modeled level (list entries match by `key`; duplicate keys and entries the owner dropped are not merged; a field the owner writes wins), puts `format_version` first, and replaces atomically. `reset=True` skips guard and merge for an explicit user reset (prompt layout reset).
- `documents_written()` counts the `document_change` scopes the process has left; a reader that caches a view of documents compares it to notice that one may have changed, without I/O (the Permission Boundary refresh, `chat/run-execution.md`).
- A file that exists but cannot be checked or read is a failed load (`Cannot read file`), never a missing one: the shared loader checks presence with `exists_strict` (PROJECT.md -> Conventions -> Filesystem checks), so the guard refuses instead of replacing it unread. Decoder limits, including excessive nesting, produce validation diagnostics. `load_validated_json_file` keeps an underlying `OSError` as the cause of `JsonConfigValidationError`, so callers tell storage failure from invalid content.
- Guard choice: single-record documents pass their full validator; collections that keep invalid entries verbatim (Cron, Bootstrap, Calendar events, both Terminal documents, MCP connections) guard only the document root (`validate_collection_root` or an owner root check); they skip invalid entries in their effective view, write them back verbatim, and `doctor config` reports them. The Device store is a collection with the full validator: an entry it cannot read makes the whole store unavailable, so no Device signs in until it is repaired (`access.md`).
- Every change of a snapshot document passes the data snapshot freeze (`database.md` -> Snapshot consistency): `write_json_document` enters `document_change(path)` itself, and an owner that removes or moves a snapshot document, or a directory holding one, outside a compound mutation wraps that step in `document_change` (Channel delete, OAuth token delete, the cleanup of a failed Project create). While a snapshot copies the data directory the change waits, off the Event Loop; on the Event Loop it enters at once and the overlapping capture is taken again instead. A waiting change keeps its thread's locks, so an owner whose lock Event Loop code takes enters `document_change` before that lock, and a change under the lock without that entry passes `wait=False` and handles `MemberFrozenError` by leaving the lock and entering again with waiting (`database.md` -> Freeze admission).

## Snapshots and doctor

- Data snapshots and configuration backups capture `SNAPSHOT_DOCUMENTS`: every kind except those in `DOCUMENTS_OUTSIDE_SNAPSHOTS` (set, restore and backup rules: `database.md` -> JSON document set, Configuration backup); `snapshot_document_paths`/`is_snapshot_document_path` enumerate and recognize that set, over the generic matchers `matching_data_paths`/`path_matches_patterns`. When a new kind joins, decide whether a restore of an older copy would be wrong: blob sidecars stay out because a snapshot holds no blobs and a set restore would delete every sidecar created after it while its blob stays; the Device store and the access record stay out because a restore would revive revoked Devices or a weaker Access Mode (`access.md`).
- `validate_data_dir_config()` (`core/settings/validation.py`, `vbot doctor config`) maps every core `DURABLE_DOCUMENTS` kind to its owner's `validate_*_file` and raises when a kind has no validator; documents under `extension-data/` are validated through the Extension manifest's `config_documents` (`core/extensions/config_validation.py`), and one without a declared validator is reported as an error. `settings.json` is always reported, every other document only when present. The CLI (`cli/doctor_management.py`) folds a directory of five or more valid documents (attachment sidecars) into one `<dir>/: N documents valid` line; documents with diagnostics are always listed.

## Outside the contract

State that is not a JSON document (the SQLite databases, which follow `database.md`: canonical ones such as `channels.db` and `provider-usage.db`, disposable indexes), the refreshed Model DB catalog under `artifacts/models/`, which carries its own `manifest.json` and falls back to the bundled root (`models.md`), the kernel files of `core/database/` (`data-store.json`, the maintenance guard, snapshot manifests and health, recovery incidents; `database.md`), append-only JSON Lines histories (the Skill History `skill-history.jsonl` beside each writable Skill home, `skills.md`; Memory's `agents/<id>/memory-history.jsonl`, `memory.md`) and archived Skill packages under `skill-archive/`, install receipts and markers (Skill install receipts, the `verified.json` receipts of local speech and embedding environments and Models), diagnostics under `artifacts/debug/` and `artifacts/performance/`, transient runtime state that exists only while an operation is in flight and fails safe when unreadable (Cron once-fire claims, `automation.md`), disposable runtime state that is recorded anew when missing or unreadable (Cron watch baselines, `automation/cron-watch.md`), the requests a Cron webhook job holds for its next Run (`cron/webhook-events/`, held without replacement when unreadable; `automation/cron-webhooks.md`), and archive payloads under `archive/`, which no data snapshot holds (`archive.md` -> Payload layout and data snapshots). A new JSON file of one of these categories is added to this list.
