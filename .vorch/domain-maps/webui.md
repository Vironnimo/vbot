# WebUI

Svelte accessor that talks only to the vBot server through HTTP RPC, Server-Sent Events, and WebSocket.

## Overview

`webui/` owns the browser interface. It imports no Python/core code, does not talk to providers directly, and treats the server as the source of truth for agents, sessions, runs, queues, settings, logs, channels, prompts, and debug data. The UI is an Agent-first app shell with Chat, Agents, Projects, Cron, System Prompt, Settings, Statistics, Logs, and a Debug tab gated by `debug.enabled`; Voice controls are visible only inside the Desktop accessor when the pywebview bridge reports wakeword support. Built assets are emitted to `webui/dist`, which FastAPI serves when present.

The per-file breakdown of what each view/helper/primitive owns, and the deep per-feature runtime behavior, are task-gated — see References. This map keeps only the orientation, transport contracts, conventions, and invariants an agent needs before touching *anything* here.

## Transport & app state

- **One transport seam.** `webui/src/lib/api.js` is the boundary: RPC envelopes to `/api/rpc`, per-Run output over SSE, app-wide lifecycle over `/ws`, logs over `/ws/logs`, and attachments/speech over dedicated HTTP endpoints (`/api/upload`, `/api/attachments/{id}`, `/api/speech/*`). Binary payloads stay out of the RPC envelope by design.
- **`/ws` is server-push only** — clients send commands through `POST /api/rpc`, never the socket. On connect the server sends a `connection_ready` hello (bus `epoch`, `last_sequence`, `active_runs` snapshot); reconnect passes `epoch` + `after_sequence` for replay-or-live. The snapshot — not a buffer replay — is the source of truth for in-flight Run state on a fresh connect/reload.
- **SSE is the primary per-Run output stream.** `/ws` lifecycle summaries deliberately omit SSE-only deltas, so any catch-up logic must not assume `/ws` saw every Run sequence. All three reconnect loops (app WS, per-Run SSE, log stream) share one jittered exponential-backoff helper (`lib/backoff.js`).
- **Reload-on-change.** The generic `resource_changed` event drives per-kind refresh tokens (`lib/resourceInvalidation.js`); the `queue` kind is scope-routed (carries an `{agentId, sessionId}` scope), not a token. A surface fetches the fresh data in the background but defers the *visible* swap while its picker/form is busy, so an open selection or in-flight edit is never yanked.
- **Queue is a server-backed projection** keyed by (Agent, Session). The accessor may optimistically add/remove/update items, but `chat.queue_*` remains the source of truth — the WebUI must never implement a second send queue.
- **Interrupted work is a server-backed projection.** `chat.history.continuation` and terminal Run payloads are the only authoritative state; `chatState` stores the summary per Session and clears it optimistically when a visible turn or continuation action starts. ChatView renders the shared footer `Banner` titled “Interrupted work retained”: non-user interruptions offer Continue and Discard, while user Cancel offers Discard only because the composer is the correction/continuation path. Continue and Discard have disabled/in-flight states; resolution, discard, or a new Session removes the banner. The old timeline-derived retry action does not exist.
- **`@`-file-mentions are client-verified, server-expanded.** The composer's `@` trigger (alongside `/` and `$`) opens `FileAutocomplete.svelte`, fetching the session cwd's file list via `files.list` **once per picker open** (ChatView's `onListFiles`) and fuzzy-filtering locally per keystroke (`lib/fileMentions.js` — filename-substring hits rank above path hits above subsequence matches). At submit, boundary-anchored `@`-tokens are matched against the file list (fetching it once if the draft never opened the picker) and only verified files ride as the `file_mentions` RPC param on `chat.stream`/`chat.queue_update`; the server snapshots them into the message (see `chat.md`). The mention text stays verbatim in the message; the timeline renders the persisted `file_mention` blocks as chips with a status hint for degraded snapshots.
- **Override-first chat display.** An active session override (drawer pick or sub-agent link) wins over both the identity-current and the project-agent branches. Overrides are accessor-local, must offer a return path, and must never mutate the Agent's persisted current Session.
- **Project-agent addressing.** The identity path stays bare-id. A project agent is addressed `agent@projekt` for `chat.stream`/`chat.history`/`session.*`, and by **bare** id for the queue RPCs; `chat.cancel` keys on `run_id` only (see `webui/state-flows.md` → two-bar chat).
- **First-run onboarding.** When no provider has usable credentials (`isOperational(settings)` in `lib/onboarding.js`, derived from `settings.get` → `providers.items[]`), `OnboardingView` takes over the content area (the nav/AppShell stays reachable) and walks choose-service → connect (reusing `ProviderConnectModal`, incl. the OAuth device flow) → choose-model, assigning the chosen model to the bootstrap `main` agent via the Agents save path (`agentForm.js` + `agent.update`). Activation is a **one-shot** decision on the first successful `settings.get` — a late response never pops the wizard over a view the user opened; once shown it is **sticky** through the connect flip (operational → true) so the model step survives, and clears only on complete/dismiss. Dismissing or navigating away while not operational sets an accessor-local flag (`localStorage vbot.onboardingDismissed`, cleared once operational) and leaves a slim "Finish setup" re-entry (shown only while not operational). Independent of that state, an **always-available "Setup guide" re-entry row** lives in Settings → Server info (`SettingsGeneralPanel`, keys `settings.general.setupGuide*`): its button calls `App.reopenOnboarding` (threaded down as `onOpenSetupGuide`), which sets `onboardingActive = true` — the same activation the "Finish setup" banner uses, so the wizard takes over the content area even on an operational install. Reopened while operational, step 1 renders its `{#if operational}` "Choose a model" footer (hero/subscription/more all hide when every provider is already connected), so it never dead-ends. The live trigger is re-derived on `modelsRefreshToken`, so connecting anywhere (including the Settings → Providers panel) retires the wizard/banner. A model-less selected agent surfaces an actionable "no model" notice in Chat (`agentNeedsModel`, identity current path only) instead of failing the send at the provider.
- **Desktop Voice projection.** `lib/desktopBridge.js` is the only pywebview seam. App polls the status plus its bounded sequence-numbered event history, updates the Chat status control, and plays best-effort Web Audio cues without replaying events from before mount. `WakewordVoiceSettings` keeps editable fields separate from runtime fields, saves Agent/session/microphone changes immediately through a serialized promise chain (sensitivity saves when the slider change commits), shows compatible/unsupported microphone options, stable error explanations and Retry, and no redundant Save action. The configured target is explicitly a server-scoped Personal Agent; Project Agent routing is not implied by the current Chat view.

## Conventions

- Svelte code uses JavaScript, not TypeScript.
- Use Svelte 5 callback props for new component communication; do not add event dispatchers for new code.
- All visible strings go through `t(...)` in `webui/src/lib/i18n.js`. Add or update i18n tests when introducing new copy.
- Dates and times follow the app language, not the browser/OS locale: pass `activeLocaleTag()` from `i18n.js` to `Intl.DateTimeFormat`/`toLocaleString`, never the implicit `undefined` locale. Fractional numeric fields (temperature, compaction threshold) are `type="text"` + `inputmode="decimal"` inputs so the displayed separator stays the dot; their parsers accept a typed comma (`normalizeTemperature`, `normalizeAgentDefaultsTemperature`, `normalizeCompactionSettings`).
- Browser resources (`EventSource`, `WebSocket`, `MediaRecorder`, object URLs, timers, and polling intervals) need explicit cleanup on component destroy or state change.
- App-wide transient success/error feedback should use the app-level `ToastStack`; avoid new local toast systems inside individual views.
- Hover hints never use the native `title` attribute (guard-enforced). Short labels go through the shared quick tooltip (`use:tooltip` from `lib/tooltip.js`, or the `tooltip` prop on `Button`/`CopyButton`); concept explanations go through the `ui/InfoHint.svelte` "?" dot; permanently visible inline text is reserved for must-see state and warnings. Details in `webui/source-map.md` → Hint system.
- Keep business-ish normalization in `webui/src/lib/*` helpers where it can be unit-tested, and keep Svelte components focused on display, input, and orchestration.
- Frontend tests use Vitest/jsdom and live near the source under `webui/src/**/__tests__/`. For frontend-only changes, use `python scripts/quality-frontend.py [paths...]` when a real code path changes; doc-only domain-map edits do not need Vitest.

## Constraints & Gotchas

- The Toasted `Components` showcase is a design/reference artifact only. It must not ship as a live WebUI tab or appear in normal navigation.
- `Debug` navigation is hidden unless `debug.enabled` is true; `DebugView` should not become the normal place to inspect chat/session internals.
- Full reload recovery for in-flight Runs is out of scope. The accessor restores the last selected Agent (and, inside a project, the last active project agent — see the two-bar chat note in `webui/state-flows.md`) through `localStorage`, the active tab through the URL hash, and a session override from the adopted top-of-stack history entry (see the browser-history note in `webui/state-flows.md`); on reload, old chat content comes from Session history plus the `connection_ready` snapshot (which is the new source of truth for in-flight Run state — the historical WS buffer-replay path is gone).
- `New Session` is blocked while the selected Agent/current Session has an active Run. Switching to another Agent while a Run is active is allowed.
- In Chat, only the message timeline should scroll. The Agent bar, notices, queued-message region, and composer stay visible inside the bounded view.
- `System Prompt`, `Settings`, and `Logs` are functional product views, not placeholders. Do not replace them with links to files or backend-only instructions.
- **Agent editor inherit state.** The editor's four inheritable run fields (model, fallback_model, temperature, thinking_effort) bind to the agent's **raw** own values (`agent.config`), never the baked top-level fields — an empty/null raw value is the explicit "inherit" state. The empty select option / temperature-empty hint describes what is inherited using that field's `agent.effective[field]` (`{value, source}`): source `"global_default"` → "Inherited: {value} (global default)"; source `null` → model "Inherit (not configured)", thinking-effort "Inherit (provider default)", temperature the provider-default hint. The create modal has no persisted agent, so it labels those same options from the live global defaults (`settings.get` → `defaults.agent`, fetched by AgentsView when the modal opens; absent-case labels on fetch failure). The reasoning-gating helpers (`reasoningForModelValue`, `effortOptionsForReasoning`) live in `lib/agentForm.js` and are shared by the editor and the create modal — do not re-fork them.
- **Soft model-suitability filter in the agent-model pickers.** `lib/modelSelection.js` annotates every catalog option with `suitable`/`suitabilityReasons` (`noTools` when `capabilities.tools !== true`; `contextUnknown` when `effective_context_window ?? context_window` is null; `belowMinContext` when it is under the view constant `SUITABLE_MIN_CONTEXT = 32768`) and a badge `secondaryLabel` on unsuitable options. Five picker surfaces (Agent editor model + fallback, create modal, Projects default + per-member overrides, Settings Defaults model + fallback, Onboarding) filter unsuitable options out by default via `filterModelSelectOptions` and expose a per-picker "Show all models (N hidden)" reveal through `SearchableDropdown`'s optional footer action (`footerActionLabel`/`onFooterAction`, click keeps the panel open); the currently selected value always stays visible even when unsuitable. The **compaction summary-model picker is deliberately unfiltered** (summarization needs no tools). Everything stays selectable — the backend never hard-filters. A `model.list` entry with `reachable: false` (local endpoint down, e.g. Ollama not running) additionally gets a "service not running" `secondaryLabel` badge without affecting `suitable` — the option stays selectable so agents can be configured before the service is started.
- **Connection enable/disable toggle.** Every connection row in Settings → Providers carries an Enable/Disable button driving the `connection.set_enabled` RPC (`isConnectionEnabled` / `connectionReachability` in `lib/settingsView.js`). A disabled connection shows a "Disabled" chip, a disabled-state description, and hides its account rows/actions; keyless local connections (Ollama) start disabled by design. Each provider is one collapsed row (name, description, summary chip, ▸ — `expandedProviders` in `SettingsProvidersPanel`, sub stays in the DOM with the `hidden` attribute); the entire connection list, account rows, Add account/Add connection, and the local-context editor live in the sub. The head summary chip is the best state across connections: any connected → "Connected", else any enabled-but-unreachable → "Not reachable", else any enabled-without-usable-account → "Not usable", else "Disabled". Enabling reports the probe outcome as a toast ("enabled — endpoint reachable" success / "enabled, but the endpoint is not reachable" warn — the enable sticks); an enabled auto-refresh connection whose last probe failed shows a "Not reachable" chip instead of "Connected". Disabled connections' models vanish from all model pickers server-side (`model.list` gate).
- **Local model context editor.** Settings → Providers renders a keyless (`type: "none"`) connection with a "No key required" description, a Connected chip, and no key/account actions (`isKeylessConnection` in `lib/settingsView.js`). A provider card whose models include flagged-local entries (`model.list` → `local: true`; fetched only when some provider has a keyless connection) gets a "Local model context" block inside the provider's ▸ sub: per model a number input (placeholder = current effective window, hint = model max) writing a sparse `settings.update` `local_models.context_windows` update on change (empty input → `null` → unset).
- **Settings is one scrolling document, not a panel switcher.** All settings sections are always mounted and rendered as stacked cards in group order (Connect / Models / Behavior / System); the left column is a table of contents (click scrolls, scrollspy highlights) plus a live search. The search hides non-matching rows/sections via the DOM `hidden` attribute only — it never unmounts panels, so their component state (extension schema forms, secret inputs, in-flight edits) survives filtering. Dense detail collapses behind ▸ disclosure rows (whole provider cards, Specialized Models per-target options, extension config forms; per-panel `SvelteSet` state, collapsed by default) whose sub-block also stays in the DOM while hidden — so search matches text inside collapsed subs, and jsdom tests can interact with collapsed controls without expanding first. Consequences: every section's mount-time RPC load fires when Settings opens, and same-labeled per-section controls (each section's Save) exist many times per document — tests scope queries to a `[data-settings-section]` subtree (see the `openSettingsSection` helpers in the SettingsView test suites).
- **Cross-view navigation from the editor.** "Edit global defaults" / the not-ready "Open Extensions" link deep-link to a Settings section via `App.navigateToSettingsPanel(panelId)` (panel ids `'defaults'` / `'extensions'` / `'voice'`), threaded as `onNavigateToSettingsPanel` into AgentsView/ProjectsView; SettingsView answers the request by scrolling to that section and highlighting its index entry (sections are never mounted/unmounted by navigation). "Edit this agent's prompt" deep-links to the System Prompt view with an agent scope preselected via `App.navigateToAgentPromptScope(agentId)` → SystemPromptView's `targetScopeAgentId`/`targetScopeRequestId` (mirrors the settings-panel request-id mechanism; falls back to the default scope when the target scope is absent).
- **Tool/skill allow-lists are one shared chip component.** All four allow-list surfaces — the Agent editor's Allowed-tools and Allowed-skills lists, and the ProjectsView Tool-Whitelist and Skill-Whitelist (its three origin groups) editors — render through `ui/ToggleChipList.svelte`: each item is a toggle *chip* (the chip itself is the on/off control, accent-filled = allowed) in a wrapping cloud, above an always-present toolbar (live name search, `on / total` tally, `all on` / `all off`; callers inject extras like Projects' "Reset to defaults" via a `headerActions` snippet). A chip's description, not-ready hint, and skill warnings show on plain hover, not inline — so the lists stay compact and scale past 100 items. Change the layout here, once, not per surface. The pure filter/count helpers live in `lib/accessChips.js`; the chip is a bespoke `role="switch"` `<button class="access-chip">` (NOT the `Toggle` primitive — the guard bans `chip`/`toggle` classes, so the class is `access-chip`).
- **Not-ready tools are shown, not hidden.** `tool.list` returns every registered tool with `ready`/`readiness_hint`/`extension`; a not-ready tool's chip is attention-marked (dashed + amber dot) but stays a functional allow-list toggle (the whitelist is independent of readiness), and its hover card carries the shared `ui/ToolReadinessNotice.svelte` (badge + verbatim server hint — NOT run through i18n — + optional Extensions link). The `memory` tool is a display-only **locked** chip (an `access-chip--locked` div with an `auto` tag — never a toggle; its on/off tint and hover note follow `memory_prompt_mode`) rendered **first** in the Agent editor's tools cloud, and stays excluded from the `on / total` tally, `all on` / `all off`, and all allow-list math. A `ToggleChipList` item is a locked chip when it carries `locked: true` (+ optional `lockedNote`).
- **Projects skill chips carry descriptions too.** The project scan's skill pool (`project.show`/`add` → `scan.skills`) is `{project, bundled, global}`, each a list of `{name, description}` objects (not bare names), so the Skill-Whitelist chips show a hover description like the tool chips. `lib/projectsView.js` (`normalizeScanSkills` → `buildSkillToggleSections`) threads the description through; the pool is produced server-side by `server/rpc/project_methods.py::_project_skill_pool` (names stay authoritative from `project_skill_names`, descriptions are best-effort from `project_own_skills` + the skills registry).
- **Disabling a custom prompt with customizations confirms first.** When the custom-prompt toggle is switched OFF and the agent's prompt scope reports `has_customizations` (fetched via `prompt.list` at that moment), the editor opens a non-danger `ConfirmDialog` before applying the form change; cancel keeps it on. No customizations or a failed fetch → the toggle flips with no dialog.
- Attachments, speech audio, and generated speech artifacts intentionally stay outside the RPC envelope; do not force binary payloads through `rpc(...)`.
- WebSocket lifecycle summaries intentionally omit SSE-only delta events. Any reconnect or catch-up logic that assumes `/ws` saw every Run sequence will skip streamed content.
- `/ws` run lifecycle/output payloads and the `connection_ready` snapshot carry a bare `agent_id` plus the Run's `project_id` (`null` for identity). `chatRunStream` rebuilds the outside `agent@projekt` address with `formatAgentAddress(agent_id, project_id)` at its two ingestion seams — `runEventFromServerEvent` (per-event) and `applyConnectionSnapshot` (handshake snapshot) — so the `/ws` re-attach/catch-up path matches a project-agent session **state** keyed by its full address. The **sub-agent status projection is the deliberate exception:** its session-scoped keys (`session:`/`sessionTool:`/`sessionDuration:`) are written with the **bare** child agent id (`bareAgentIdForStatusKey` strips the `@projekt` suffix), because their readers are persisted spawn descriptors that only carry bare ids — a display projection scoped to the rows of one displayed parent session, not a run-key surface. The RPC side of those rows goes the other way: ChatView qualifies a descriptor's bare child id with the **displayed session's** project (`qualifiedChildAgentAddress`) for the spawn-row navigation link, the dot-verification `chat.history`, the queue lookups (`chat.queue_list`/`chat.queue_remove` — the run/queue key is project-scoped), and the result fetch, so a project run's children are addressed `child@projekt` while identity children pass through unchanged. An identity run has no `project_id`, so the rebuild yields the bare id and the identity path stays byte-identical.
- Public chat/history/Run rendering must not expose opaque provider metadata such as `reasoning_meta`; backend payload stripping is required, but UI code should not add debug escapes in normal views.
- The selected log file remains user-controlled. A newer file appearing in the catalog must not automatically move the active Logs view away from the user's current file.
- The production server serves `webui/dist` only when the built `index.html` exists; missing built assets must not break server startup.
