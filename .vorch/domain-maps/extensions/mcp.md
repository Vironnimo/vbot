# MCP Extension

The bundled `resources/extensions/mcp/` package is a vBot MCP host/client. Its package entry point exports registration; API v4 supplies management, host capabilities, and live Tool publication. It runs external MCP processes on the vBot server machine; accessors do not launch helpers on their own machines.

## Ownership and invariants

`_definitions.py` holds the fixed connection Tool description/schema, its messages, and operation constants; `_arguments.py` normalizes the connection Tool's own call shapes; `_views.py` renders payloads as the Model's view; `extension.py` keeps the existing live service and registration. This internal split preserves the registered definitions and remote Tool naming.

`extension.py` owns connection CRUD, live Tool declarations, and asynchronous management jobs. `config.py` validates and atomically persists `connections.json` in the Extension's owner-bound `host.state_dir` (`<data-dir>/extension-data/mcp/`; startup fails without one) as `{"format_version": 1, "connections": [...]}` (JSON Document Contract in `settings.md`; `validate_connections_file` serves `vbot doctor config`). Persisted connections load independently: unknown fields of a connection or of the document produce structured warnings and are excluded from runtime configuration; invalid records and duplicate ids are skipped without suppressing healthy connections. `list.configuration_issues` and startup logs identify the affected record and reason without configuration values. Management input remains strict. Saves preserve unknown fields and rejected records belonging to other connections; an explicit replacement can repair a rejected id. A document whose root fails to load (invalid JSON, not an object, missing or other `format_version`, `connections` not an array) cannot be loaded or overwritten through normal management. Credential references are configuration; values use the host credential store. Transport changes close and replace the connection.

The connection Tool is `mcp_<id>`, with fixed search/describe/call/read arguments. Remote Tools remain registered with `deferred=True` for authorization and dispatch, but never enter Provider definitions or System Prompt Tool lists. Search returns one bounded `target: description` line per match; describe returns only the selected definition and arguments schema as an ordinary Tool result. A fingerprint of an earlier definition is never substituted for a call (Agent discovery below). The parent is published before connection startup and its readiness depends on saved enablement, not transient connectivity. Catalog growth, discovery, and reconnects therefore leave the existing Tool-definition prefix unchanged; explicit connection/Tool-policy changes can still alter it. Remote Tools receive deterministic bounded names and follow that parent Tool's activation. The parent declares `requires_opt_in=True`: its ordinary Tool switch adds an explicit `tool_access.granted` entry. All mode and Project ceilings never opt in; selected mode also requires the parent in `allowed`. There is no connection-level Agent list or grant/revoke operation. Explicit Tool denials, selected Tool policies, and Project ceilings still apply. Direct CLI invocation and the `explore` management operation resolve that Agent's effective policy and use ToolRegistry dispatch. Chat propagates Run restrictions and the live denial resolver through ToolContext so calls delegated by the parent cannot bypass them. Remote schema changes fail stale calls rather than applying old arguments to a new definition.

`client.py` uses the pinned official MCP SDK for stdio, Streamable HTTP, and legacy SSE. One task owns each connection's SDK context; invocations serialize per connection, while different connections run independently. Cancellation is not a promise to undo a remote mutation, and mutations are never automatically replayed. Transient failures of read operations retry at most three times with exponential backoff and jitter; authorization and validation failures do not retry. Connection-owner cancellation exits an active request and releases its pending inputs. Discovery preserves all catalog pages and their standard metadata. Catalog notifications trigger republishing; Resource subscriptions acknowledge before success and expose changes through bounded sequenced events, with explicit gap counts. Stderr is drained and configured credentials are redacted before diagnostic retention. Closing a connection cancels its task and waits at most `CONNECTION_CLOSE_TIMEOUT_SECONDS` (15s); a task that has not stopped by then is abandoned with a warning, and disable/remove still retire that connection's Tools (an abandoned runner can no longer publish). Coverage: `test_stopping_a_connection_that_ignores_cancellation_still_removes_its_tools` in `tests/resources/extensions/test_mcp.py`.

Sampling uses the invoking Agent's configured Model and only the server's explicitly supplied context. It does not copy Session history or other connections into the request. Sampling requests, the selection policy, and usage are available in connection events; these auxiliary requests do not currently contribute to the parent Run's main response usage counters. Roots use the invoking work directory. Elicitation and OAuth are resumable pending inputs available to the CLI and global WebUI request dialog; OAuth tokens use host credentials. Legacy callback and current `input_required` flows are exercised through real SDK connections.

`content.py` preserves standard structured content, annotations, `_meta`, and Resource/Prompt content. Binary extraction visits only protocol content positions, never media-shaped application JSON, schemas, or metadata. Binary blocks go to the Attachment store (`path`, `attachment_id`, `size_bytes` replace the bytes); image/audio attachment artifacts use normal Chat media routing. If the Attachment store rejects a binary (too large or type not allowed), vBot keeps no copy: the block keeps `size_bytes` and gets the omission marker `content_omitted: true` with `media_delivery_error`. Input requests and management jobs use `req_`/`job_` with catalog collision checks; external MCP and correlation ids stay unchanged. In a Session the Model sees a view (`_views.payload_view`): SDK default fields (`isError: false`, `resultType`, `ttlMs`, `cacheScope`) and a `structuredContent` that only repeats the text blocks are dropped, and `content`/`contents`/`messages` become one `content` text (text verbatim; other blocks as one-line descriptors such as `[image] {...}`; Resource contents and Prompt messages behind a short header). A view within the 6000-character limit returns as is. A larger result is attached to its Tool Result as a Tool result payload `{connection, source, payload}` (`extensions.md` -> Tool result payloads): a text body shows its first 3000 characters with `result_id`, the small fields, and a `note` naming the exact `read` (pointer and offset) that continues it; a payload without a text body returns the outline receipt `{result_id, complete: false, preview, read}`. Search attaches its payload only when server guidance is longer than its shown part. An `isError` result returns `mcp_tool_error` with the server's own error text and advice; a report over about 3200 characters keeps its first 1000 and last 2000 characters and names the `read` for the rest. Views and receipts carry no file path: `read` is the only way in. It loads the payload through `host.load_result_payload`, so only a Session whose current view holds that Tool Result (forks included) can read it, then requires the same connection (`RESULT_DENIED`) and rechecks effective access to the parent and the source remote Tool. The reader supports JSON Pointer, offsets, limits, and field projection; a string page returns `{result_id, pointer, offset, total, next?, content}` with the text verbatim and shrinks until it fits, and a selection that still does not fit returns `complete: false` with `READ_TOO_LARGE` guidance to narrow it. Expansion actions for projected array rows retain the requested fields. No preview is a complete-result claim. A payload lives as long as its Tool Result in Session history; no loaded-schema Session state or history rewriting is involved. Outside a Session (management `explore`/`invoke`, CLI) nothing is saved: the complete payload returns inline, and `explore` offers no `read`. The complete protocol catalog remains explicitly callable, but does not automatically include every operation schema.

Pre-Generation-1 data kept every result as `mcp/content/results/<result_id>.json` and rejected binaries as files under `mcp/content/`. `scripts/converters/persistence_generation_1/mcp.py` runs after the sessions area and attaches each saved result to the Tool call whose Tool Result returned its receipt (the one whose `read` names it; later read pages do not count) in the staged `sessions.db`, keeping the id as `payload_id` with owner `mcp`; a fork's self-contained copy of that same Tool Result gets its own copy. A result no Tool Result returned, one several different Tool Results name, and an unreadable file are dropped and reported; rejected binaries inside kept payloads get the omission marker; every file under `mcp/content/` retires. Without a staged `sessions.db` the files stay and are reported. Coverage: `tests/scripts/converters/persistence_generation_1/test_mcp.py`.

## Agent discovery and operator inspection

Remote Tools use `catalog_visible=False`: general Tool selectors and Extension capability summaries expose only `mcp_<id>`, including the catalog consumed by Swarms. The MCP `inspect` projection still lists the original remote Tool names without generated dispatch-name suffixes. Hidden catalog entries remain registered for discovery, policy resolution, and dispatch. Coverage: `tests/resources/extensions/test_mcp_discovery.py`.

Search ranks partial word matches and places application Tools before protocol operations on an unfiltered page. The view gives policy-filtered capability counts (`available`), a `matches` range, and an executable `next`. Only the unfiltered first page (no query, kind, or offset) shows external server guidance (first 1200 characters; long guidance has an explicit incomplete marker and, in a Session, a `guidance_read` for its remainder) and up to three unlisted Prompts; other pages point back to it. Empty searches offer a Tool browse without asserting that the task is unsupported. After connection startup republishes Tools, discovery resolves access again before filtering the new catalog. Describe returns the target, its arguments schema, and the call shape.

Describe and call accept a full target, or a name with or without its kind (`tool:name`, a Resource URI; case and separators ignored) when it names exactly one policy-visible item. A name of several items returns `mcp_unknown_target` listing them and is never chosen; an unknown name returns `mcp_unknown_target` with close candidates or a search call. A fingerprint of an earlier definition fails a call with `mcp_target_changed` naming the current target; describe returns the current definition with a note. A connection that cannot be reached, and a call that provably never reached the server (`client.InvocationNotSentError`: closing, not ready, shut down, refused at dequeue), return `mcp_request_failed` with `retryable: true` (a dequeue refusal returns `mcp_access_denied`). A Tool invocation that fails without a result reports `mcp_call_unconfirmed`; for read operations (`client.READ_OPERATIONS`) it is retryable and says so, otherwise it warns that the call may have changed the application. It never claims that remote effects were undone.

The connection Tool's own arguments pass through `_arguments.browse_normalizer` (its registered `argument_normalizer`) before schema validation: owner-defined aliases (such as `tool`/`name` -> target, `args`/`input`/`parameters` -> arguments, `q` -> query, `path` -> pointer), action synonyms (such as `run`/`invoke` -> call, `browse`/`list` -> search), kind plurals, JSON-text arguments, and an action inferred from the fields present. It never guesses between effects: a bare target without an action, non-empty fields of another action, target arguments placed beside `arguments`, and unparsable argument text are refused before any remote request with the corrected call, and invalid argument text is never echoed. Coverage: `tests/resources/extensions/test_mcp_call_shapes.py`.

The same failure boundary covers calls to protocol operations. Discovered target arguments first receive shared schema-guided repair against that target's exact schema, including protocol operations; arbitrary application data and external field names/enum identifiers stay intact. Remote schemas alone do not establish typo aliases or call wrappers for target arguments; the connection Tool's aliases above belong to its own fixed schema. Only the locally owned `logging/setLevel` protocol vocabulary explicitly accepts field/level formatting. Ambiguous encodings and genuinely invalid target arguments return `mcp_invalid_arguments` before invocation, naming the JSON Pointer and problem without echoing values, a summary of the target's arguments, and its describe call. Expected storage/media preparation failures after a received result return `mcp_result_unavailable`, independently from an unconfirmed call; neither path replays the operation. Event diagnostics redact decoded string values and keys before retention so JSON escaping cannot hide a credential or corrupt an event. Coverage: `tests/resources/extensions/test_mcp_execution.py` and `test_mcp_oauth_and_cancellation.py`.

The read-only `inspect` management operation returns the cached, paged Tool catalog, server guidance, and Prompts. It does not connect or execute an application Tool. Access is configured through the shared Agent or Swarm Tool editor; connection management does not maintain a second roster. The Settings inspector uses this projection without duplicating policy resolution and discards stale or closed inspection requests.

`scripts/probe_provider_tool_call.py --scenario mcp_workflow` runs an actual Model against the production MCP entry point and an inert application served through the official SDK. Cases cover indirect render intent, recovery from an empty search, and selective reading of a large result. Argument refusals reach the Model as Chat's `invalid_arguments` envelope with the refusal text. The fixture never evaluates generated Python or renders a real Blender scene. Structural call-shape coverage remains in the existing `mcp` scenario; deterministic host and probe tests protect the evaluation machinery.

`ExtensionHost.resolve_tool_agent(context)` resolves the actual calling Session through Runtime, including exact temporary bindings and their execution-owner generation. MCP uses it for fresh policy checks, including queued calls; ordinary management still uses addressed Identity/Project resolution. Sampling uses the same Session-aware resolver. Regression coverage: `test_mcp_access.py` and `tests/core/runtime/test_runtime_mcp_access.py`.

Obsolete per-connection Agent lists have no runtime meaning and grant no access; startup never rewrites configuration or interprets them. The offline grant converter was removed with Generation 1; an Agent that relied on such a list enables the connection in its Tool editor.

## Compatibility boundary

The SDK is pinned to `mcp==2.1.1`. The 2026-07-28 protocol removes ping; connection testing reports catalog verification instead when that revision is negotiated. Historical task-augmented Tools require the SDK dispatcher's raw request seam because the high-level SDK wrongly validates task handles as ordinary Tool results. That seam stays inside `ConnectionRunner._task_send`, reuses the existing connection stamping/cancellation/progress machinery, validates task handles, and returns the complete original task payload. Do not replace it with the empty `GetTaskPayloadResult` model or an unparameterized generic Request: those drop payload or argument fields. The real stdio task test protects both cases.

Protocol extensions that the selected SDK cannot interpret must fail explicitly; never advertise a capability that the host does not implement or silently discard unsupported content. External protocol-version compatibility is distinct from prohibited legacy vBot configuration migrations.
