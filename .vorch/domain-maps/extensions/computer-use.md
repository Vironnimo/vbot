# Computer Use Extension

Read this reference for the bundled `computer_use` Extension: its three opt-in Tools (`computer`, `computer_batch`, `computer_apps`), the access mode and per-Session approvals, screenshots and coordinates, desktop input, and operator stop.

## Overview

The Extension lets an Agent operate a selected interactive Windows desktop, on the server or a connected Desktop app, with the user's real mouse and keyboard (foreground input only). Actions follow Anthropic's computer vocabulary; coordinates use the pixels of the latest screenshot, or of an earlier screenshot named by `screenshot_id`; zoom images are for looking only. Screenshots initially show the foreground window; display view remains available. The first generation (one `computer` Tool with background delivery, element refs and the external Cua Driver) is archived in `archive/computer-use.zip` (`archive/README.md`); the current implementation does not use it.

Windows is the only native platform today. The Tools stay registered and are ready when the server has an interactive desktop or a connected Desktop app shares Computer Use. A Linux or headless server can therefore route these Tools to a Windows Desktop; a call still checks the exact selected computer's readiness, without falling back to another computer.

Decided direction for later work (2026-10, user decision): further targets (VM, second session, Linux Xvfb container) implement the same `DesktopTarget` protocol; a Provider capability may later declare the native Anthropic toolset and map it 1:1 to `computer`. Neither exists yet.

## Terms

### Access mode
Whether Agents allowed to use the Computer Use Tools operate every app or only the apps the user approved for the Session; set by the user, off by default (Contracts -> Access mode).

### Approval
In ask mode, the user's permission for one application in one Session, given through an access request (Contracts -> Access requests). Not the Tool opt-in, which must also allow each Tool.

### Desktop control
The period in which Agents hold the desktop, shown by the activity sign and stoppable by the user (Contracts -> Desktop control). Not a vBot Session.

### Frame
One published image's pixel space mapped to its physical desktop rectangle, together with the apps it shows at each point (Contracts -> Frames).

## Ownership and source routing

`resources/extensions/computer_use/`:
- `extension.py` - `ComputerUseService`: readiness, opt-in check per Tool, Session state lookup, call serialization, desktop control and stop, hotkey arming, `run_end`/shutdown release, the three Tool handlers. `_registration.py` owns the declarations and display summaries, re-exported as `extension.register`. `_presentation.py` owns app-list text and result/error presentation without controlling the desktop.
- `_tools.py` - descriptions, schemas, argument normalizers (other harnesses' spellings; Agent error tolerance per `tools.md`).
- `_actions.py` - parses one `computer` action into an `Action` (points, seconds, notes).
- `_desktop.py` - `Desktop`: one call's view of the desktop under its `Access`: frame resolution, display selection, screenshot/zoom/cursor, access checks before input, dispatch to the target.
- `_access.py` - `Access` (the call's mode and what it may operate), Session state (approvals, capture choice, bounded image references), expiry, app name resolution, access requests as pending inputs.
- `_screens.py` - platform-neutral imaging: frames, coordinate mapping, display choice, masking, PNG publishing.
- `_color_filter.py` - platform-neutral proof and removal of a composition colour filter from references (Contracts -> Screen colour filter).
- `_keys.py` - chord parsing to canonical key names (xdotool/Anthropic spellings accepted).
- `target.py` - `DesktopTarget` protocol and value types (`Display`, `AppInfo`, `WindowInfo`, `TargetError`, `InputInterrupted`). The only boundary to the operating system.
- `_routing.py` and `_remote_target.py` - exact computer selection through `ExtensionHost.computers`, one service per remote native instance, and the remote implementation of `DesktopTarget`. `_remote_wire.py` owns native wire values and bounded PNG transfer, with no kernel imports.
- `windows_target.py` with `_win32.py` (bindings, displays, capture, window enumeration), `_win_input.py` (`SendInput`), `_win_apps.py` (app identity, shell surfaces, Start-menu discovery, launching), `_win_overlay.py` (`ActivityOverlay`, the activity sign) - the Windows target.
- `hotkey.py` - `EmergencyHotkey` (double Esc).
- `skills/computer-use/SKILL.md` - the workflow Skill, discovered like any loaded-Extension Skill; it grants nothing.

The Desktop-side owner is `desktop/computer_execution.py`: one lazy native target and worker, its stop event and emergency hotkey, explicit operation dispatch and connection-generation fencing. `computer_use/__init__.py` loads the Extension registration lazily so Desktop-only packages can import these native modules without loading core or the Extension service.

Tests: `tests/resources/extensions/computer_use/` (`computer_use_test_support.py` holds `FakeTarget`, `FakeHotkey`, the dispatch `Harness`; `test_computer_use_tools.py`, `_access.py`, `_batch.py`, `_dialects.py`, `_remote.py` for broker/native routing, `test_hotkey.py`, `test_windows_target.py` for pure Windows helpers, `test_windows_target_input.py` for native input cleanup with a fake `SendInput`, `test_windows_target_overlay.py` for the sign's lifecycle and z-order with an in-memory native message queue, `test_color_filter.py` for filter proof and removal), `tests/desktop/test_computer_execution.py` (native stop and connection fencing) and `tests/core/runtime/test_runtime_computer_access.py` (opt-in through runtime dispatch, temporary Agents). No test sends real input or captures the real screen.

## Contracts

- **Connected computers:** `computer_id` on each Tool chooses the exact computer id or name; omission uses `ToolContext.execution`'s Session default. The shared computer registry enforces allowed computers, availability and the advertised `computer_use` capability. The batch chooses one computer for all its actions. Remote results identify the computer by name, and approval requests identify its desktop. App grants, capture choices and screenshot references belong to that computer's service and Session; a screenshot from another computer is refused. The server still owns Tool policy, app approvals, masking, images and action guards; the Desktop executes the native target methods. Native input and metadata travel over the dedicated authenticated computer connection, never through the WebUI's JavaScript bridge.
- **Remote lifecycle:** disconnect stops active Computer Use Runs, clears their image/app-grant state, cancels pending app requests and releases input on the Desktop without waiting for the server. A Run whose desktop control was interrupted stays refused after reconnection; a later Run uses fresh screenshots. A restarted instance gets a fresh service. Native double Esc immediately refuses the stopped control id locally and forwards its exact id to the server. Stop requests bypass ordinary serialized native work so typing or held keys can be interrupted. Requests whose result is lost are never replayed. The Desktop process owns its native target and closes it on exit. Removing an offline Computer closes its retained server-side service and worker; queued control requests are fenced before that id can register again.
- **Remote control status:** hotkey availability comes from the native control response, starts false and becomes false on disconnect. A change publishes the existing control resource, so the WebUI never infers a working emergency hotkey merely from an online connection.

- **Access mode:** the Extension setting `ask_per_app` (toggle "Ask before each app", default off, read live per call). Off: an Agent whose Tool Access Policy allows a Computer Use Tool operates every app. On: it operates only apps the user approved for the Session (`SessionState.grants`). User decision 2026-10: no app is treated specially - browsers, terminals, IDEs and vBot itself are ordinary apps; asking is opt-in because remote use (for example over Telegram) cannot answer a WebUI prompt.
- **Permission.** Each Tool is `requires_opt_in`; the handler re-checks the calling Agent's Tool Access Policy (`resolve_tool_access`, `host.resolve_tool_agent`) and refuses with `tool_not_allowed`. Desktop admission repeats this check after lock and hotkey-startup waits, reads the current app-approval mode and rejects Session state invalidated by disconnect or expiry. A pending app approval repeats authorization before adding grants. In ask mode, approvals come on top. A call outside a Session is refused (`computer_use_unavailable`): display choice and approvals are per Session.
- **Check before input** (`Desktop._check_access`): every input action requires a window under each target point (every drag point; the pointer position when no coordinate is given), and that window and the foreground window must not be elevated (`target_elevated`; UIPI would drop the input). In ask mode their apps must also be approved (`access_required`, naming the app and the exact `computer_apps request` call). The taskbar and desktop belong to "File Explorer". With no foreground window, only pointer actions proceed.
- **Masking (ask mode only):** screenshots and zooms paint windows bottom to top of z-order; an approved app's window reveals its frame, every other window and uncovered pixels are a solid neutral fill. Results name the hidden apps (names, never titles). Without ask mode nothing is masked.
- **Coordinates:** image-local pixels, with the top-left at `[0, 0]`. `screenshot_id` selects a screenshot returned in the same Session; omission selects the latest screenshot (`SessionState.latest_image`). Coordinate/region actions and `cursor_position` need a prior observation. The Session keeps at most 64 image mappings, without image bytes; eviction, Session expiry or restart makes a reference unavailable. Unknown or other-Session references never fall back to a different image. Changes to display layout or the captured foreground window's geometry refuse before input; each batch step rechecks its mapping before acting. Another app now lying at a point refuses through the Screen-change guard. Bounds use the actual image size. `zoom` captures its region of the selected screenshot fresh, at screen resolution or reduced to the image limits like a screenshot, never enlarged; its bottom-right corner is exclusive. A zoom gets no `screenshot_id` and no mapping, so no coordinate can refer to it. Why one coordinate system (user decision 2026-10-19, modelled on Claude Code's computer use, whose zoom is read-only and whose results never mention scaling): zooms that took clicks and enlarged 2-4x, plus a reduction note on every screenshot, made Agents convert between images by hand. In a Paint Session an Agent zoomed 28 times, never clicked in a zoom, recomputed zoom positions as screenshot coordinates in 17 reasoning steps (misclicks: circle for rectangle, eraser for bucket, Share for Undo) and calibrated canvas pixels against the screenshot, and its Reflection Skill recorded that calibration as a rule (Session 2063).
- **Frames** (`_screens.Frame`): a Frame is one published image's pixel space and its physical desktop rectangle, plus the app that was in front when it was taken (`front`) and the windows over its area, topmost first (`stack`), which tell what app the image shows at each point (`Frame.owner`). Images fit a long edge <= 1568 and area <= 1,150,000 pixels (Anthropic's vision limit; a full 2560x1440 monitor therefore arrives at about 0.56 scale). There is no Agent-chosen `scale`: Agents mixed screenshots at 0.6-1.0 scale and converted between their coordinate systems (Session 1681, 2026-10); the normalizer silently drops a sent `scale`. It also silently drops per-action summaries (`action_summary`, `summary`, `action_description`): the user decided 2026-10 that Agents label no actions, and the UI summary of a call lists its action names. Each axis maps from the actual returned pixel size, including rounding, to the recorded rectangle. Image pixel `x` covers physical `[x*W/w, (x+1)*W/w)` and input goes to the physical pixel at its centre, `floor((x + 0.5) * W / w)`; `cursor_position` maps back with the same cells. Rounding to the cell's left/top edge instead biased scaled clicks by about -0.4 physical pixels and left visible gaps at Paint canvas edges (2026-10). Agents do not undo scaling, crop offsets or monitor origins.
- **Durations** (`_actions._seconds`) are seconds, 0-100. `wait` caps a larger value at 100 s with a result note: Agents sent 110 and 120 to wait for a long-running script, which the former milliseconds reading turned into 0.11-0.12 s, so they acted before the script finished (GIMP Session, 2026-10). `hold_key` and `left_click_drag` read 100 < value <= 100000 as milliseconds with a note.
- **Drag** (`left_click_drag`): `start_coordinate` (default: the pointer) and `coordinate`, or `path` with 2-200 points (`MAX_PATH_POINTS`) in one image. With `path`, redundant start/end coordinates are accepted only when they match its corresponding endpoints; conflicts fail before input. Bounds failures name `path point N`. `duration` (Durations) defaults to 1 s per 1000 image pixels along the given points, within 0.25-5 s (`_actions.DRAG_PIXELS_PER_SECOND`). `WindowsInput.drag` presses at the first point and moves straight from point to point at constant speed, about every 10 ms, passing every point exactly (`_win_input.drag_steps`): straight segments keep the Agent's corners (lasso, polygon), and more points give rounder curves. OpenAI's `drag` with a `path` of `{x, y}` points maps directly. Added for drawing and lasso selection after an Agent tried `path` and stepped a curve with 58 `mouse_move` actions in one batch (2026-10).
- **Screen-change guard** (`Desktop._check_owner`, `_check_front`): input goes only where the Agent's image says it goes, in window and display view alike. It checks every input action of a call, ahead of Check before input, so a refusal names the changed screen rather than, say, an unapproved app. Pointer: each point of every pointer action (clicks, every drag point, scroll, `mouse_move`, `left_mouse_down`/`up`, the pointer position when no coordinate is given) refuses with `screen_changed` when the topmost window there now belongs to another app than the image's `stack` shows there (the named image, else the latest screenshot; a pointer position outside that image is not checked). Both sides read a window stack the same way, so a fresh screenshot always resolves a refusal; `window_at`, which also hit-tests invisible resize borders, still decides access and elevation. A new window of the same app (menu, dialog) passes. Keys go to the foreground window, so `type`, `key` and `hold_key` refuse with `focus_changed` when the foreground app differs from the app the call's last mouse button press went into (`_actions.PRESSES`: clicks, drag start, `left_mouse_down`), or before any press from the `front` app of the image (`screenshot_id` if given, else the latest screenshot). Keys that follow other keys of the call since its last press are not checked, because those keys can bring up another app themselves (`win` opens the Start menu, `ctrl+o` a dialog) and the foreground changes asynchronously; a window switch between a click and the following keys is still refused. Without a recorded or current app a check is skipped. Seen: the user clicked into vBot between the Agent's look and its typing (Session 1679, 2026-10); in a GIMP Session the vBot window came to the front several times while batches `click -> type -> key enter` aimed at GIMP's Python console, and their clicks landed in vBot, because the former guard checked only calls whose first input was a key and only window view refused clicks into a covering app (2026-10). On `screenshot` and `wait`, `screenshot_id` is ignored with a result note.
- **Screen colour filter** (user decision 2026-10: Agents need the colours applications drew, and a capture with normal colours must never change): colour-temperature tools such as f.lux can tint the composed desktop instead of the display output; then GDI, DXGI duplication and other screen captures all carry the tint (verified 2026-10 with f.lux 4.141 on Windows 11 25H2: neutral gray 32 arrived as (32,23,14); Claude Code's own screenshots showed the same). Such a filter is one 3x3 matrix on 8-bit sRGB values (fitted to within rounding). `WindowsTarget.capture` therefore renders references before composition with `PrintWindow(PW_RENDERFULLCONTENT)` - the foreground window (not the desktop, `Progman`/`WorkerW`, whose rendering already shows the composed, filtered screen) and each display's taskbar - and `_color_filter.measure` compares them with the capture at the same place. One reference the capture shows unchanged (>= 30% of its informative pixels) vetoes any correction. Otherwise a matrix must explain >= 60% of every voting reference, be fitted from >= 24 distinct explained colours spanning the colour space (or be the display's previously proven matrix, confirmed now), invert, keep positive diagonals and only dim (white response 0.1-1.02 per channel); then the capture is multiplied by its inverse. Anything less returns the capture unchanged. Removal restores 99.75% of a window's pixels to within one level (live 2026-10); saturated colours keep the levels the filter itself clipped or compressed. `PrintWindow` blocks while the window's thread is busy (5.6 s measured), so each reference renders on its own thread for at most 0.25 s (`_REFERENCE_WAIT`); a late or hung window does not vote. A capture with references costs about 40-100 ms more.
- **Capture choice** is per Session. Initial `view` is `window`: capture the visible desktop rectangle of the foreground window and its visible owned popups, across displays when needed. With no usable approved foreground window, capture the chosen display instead, still applying masking. `view: display` captures a whole monitor. Setting `display` (name, 1-based number, `auto`) also selects display view; `auto` follows the visible foreground window's monitor, else the primary display. `view: window` restores window capture and automatic monitor choice; combining it with an explicit `display` refuses. Input and wait screenshots retain the capture choice.
- **Results:** text `content` plus images in `context.result_media` and `add_display_media`. A screenshot's text names what it shows and its `screenshot_id` (the generated PNG basename, without its suffix); a zoom's text names its region and screenshot and that coordinates still refer to the latest screenshot. No text states an image size, a ratio or that an image is reduced: Agents used a stated ratio as a conversion factor (Session 1681) and the reduction note as a reason to calibrate (Session 2063). Input actions in `computer` (except `left_mouse_down`, `cursor_position`) settle 0.5 s and attach a screenshot; `wait` attaches one after its pause. `computer_batch` runs 1-60 actions in order with 0.2 s between input steps, resolves every explicit/default image reference and validates all items before running any, stops at the first failure (reporting completed steps), and attaches a final screenshot after input unless the last item was one. A `computer` or `computer_batch` call that fails after it sent input settles 0.5 s and attaches a fresh screenshot, named in the failure text as "The screen now: ..." (not after a stop). Failed Results carry their images to the Model like successful ones (Tool dispatch delivers `result_media` regardless of outcome), so every image that becomes `latest_image` is one the Model received. Images returned inside the batch never change a later step's coordinate basis. `computer_apps open` brings an open window of the app to the front or, when the app has none, starts it (`DesktopTarget.open` returns whether it started the app); it waits 1.5 s, attaches a screenshot, and its text says which of the two happened.
- **Screenshot encoding** (user decision 2026-10-19: fewer upload bytes, exactly the same pixels): `publish_image` encodes every screenshot and zoom as lossless 8-bit RGB PNG at zlib level 4 (`_screens._PNG_COMPRESS_LEVEL`). Chat persists these bytes as an Attachment and sends them unchanged in every later request of the Session, so each byte is uploaded again per request while encoding happens once. Measured 2026-10-19 on eight 1.1 MP window captures (Pillow 12.3 with zlib-ng): level 4 is 18% smaller than the former level 1 (15-29% per capture) for about 6 ms more (median 25 ms, at most 30 ms); levels 5-6 save another 1% for up to 48 ms, level 9 and `optimize` take 65-220 ms. Lossless WebP (method 0, quality 0) would save about 31% in a similar time, but not every route carries WebP: xAI documents only JPEG and PNG (`resources/wire/xai.json`; docs.x.ai image-understanding guide, checked 2026-10-19), and LM Studio's OpenAI-compatible endpoint has open reports of refused WebP data URLs (lmstudio-bug-tracker #1752, #1839). On such a route Chat would convert each WebP screenshot on every request and add a conversion note to what the Model reads (`attachments/image-conversion.md`). A new encoding applies to new screenshots only; never re-encode stored Attachments, whose bytes the prompt cache depends on.
- **Access requests (ask mode):** `computer_apps request` resolves names (case-insensitive exact, then unique contains, else suggestions), skips apps already approved, and raises one pending input (`kind` `computer_access`, `payload.message`, `session_id`) through `api.operations.pending_inputs`; operation `respond` takes `{request_id, response: {action: accept|decline|cancel}}`. Each add/remove publishes a `pending_inputs` change. Unanswered after 300 s it counts as declined; Run cancellation withdraws it. Approvals, capture choice and image references expire 30 minutes after the Session's last Computer Use call and are in memory only (reload/restart clears them). One INFO line per decision with counts, never app names. Without ask mode, `request` returns at once that no approval is needed, and `list`/`open` cover every app.
- **Desktop control:** it begins with the first call that takes the desktop (`computer`, `computer_batch`, `computer_apps open`) and ends when every Run in it has released (`computer_apps release`) or ended (`run_end`), after `CONTROL_IDLE_SECONDS` (120 s) without a call, at shutdown, or on a user stop. Identified by `control_id`.
- **Activity sign** (user decision 2026-10: subtle but visible, like Claude Code and Codex): while an Agent controls the desktop, every display shows an accent glow along its edges and the primary display a pill "vBot is using this computer - Esc Esc to stop" (`DesktopTarget.set_activity`). It is shown exactly while desktop control lasts (Desktop control), including between calls. On Windows its windows are layered, click-through, never activate, stay out of `windows()`/`window_at`, and use `WDA_EXCLUDEFROMCAPTURE`, so screenshots never contain it.
- **Activity sign lifetime and z-order:** while visible, the overlay thread watches native foreground, show/hide, move/resize and desktop z-order events. It coalesces events and raises the existing windows only if another visible, uncloaked window precedes them; it does not poll, repaint, take focus or react to its own raises. Other vBot frames are ignored to avoid competing instances raising each other. Windows reports a top-level z-order change as `EVENT_OBJECT_REORDER` on the desktop's `OBJID_CLIENT`, not necessarily on the moved window. A completed hide removes the hooks, destroys the windows and unregisters their instance-owned class, keeping native callbacks alive until removal; close also ends the thread, including when requested during startup. Extension Reload cannot reuse a class pointing into an unloaded module. Verified on Windows with two displays (2026-10-26): ordinary maximize, a covering topmost fullscreen window, repeated reordering and twelve show/hide cycles, with no remaining windows/hooks/classes or growth in GDI/USER resources. This does not establish the cause of the user's intermittent flicker after Computer Use, which was not reproduced.
- **Stop** (user decision 2026-10: the user must be able to stop at any moment the sign shows, not only during a call): operation `control` returns `{available, active, stopping, hotkey_available, control_id?}`, where `active` means desktop control; `stop` with the current `control_id` and double Esc end desktop control as the user. That interrupts a running call, hides the sign, disarms the hotkey, and marks every Run in control as stopped: their later calls that take the desktop are refused (`computer_use_interrupted`, "Nothing was done") until the Run ends, so the user's next message may take control again. Run cancellation and shutdown interrupt only the running call. A stop also queues release of held input on the desktop worker, including between calls and during a wait when no target input remains to observe the stop event; idle expiry releases held input as well. An interrupt sets the target's stop event; the target releases keys and buttons it pressed and raises `InputInterrupted`, reported as `computer_use_interrupted` with whether input may have been sent and the completed batch steps. Every control change publishes a `control` change. The hotkey's keyboard hook starts with the first call that takes the desktop and is armed with the `control_id` for the whole desktop control.
- **Release:** `computer_apps release` ends the calling Run's part in desktop control and releases a left button it still holds; the sign goes when no other Run is in control. A later call in the same Run takes control again. Without control it reports that there was nothing to release.

## Conventions and gotchas

- All target calls run on one dedicated worker thread (`ThreadPoolExecutor(1)`), which is per-monitor DPI aware; an `asyncio.Lock` serializes whole calls, so a batch is atomic across Sessions. Task cancellation removes queued worker work; input already running receives the cooperative stop, settles and releases held native input before the call releases its lock and active stop owner. This also covers input completed before its async result bookkeeping. `computer_apps list`/`request` do not take the lock, so a waiting access request never blocks Stop.
- `run_end` ends the Run's desktop control, clears its stopped mark, and releases a left button its `left_mouse_down` left held; shutdown releases all input and stops the worker.
- Hotkey startup runs on the owned desktop worker and settles before cancellation can release the call lock. Cancelled, failed or shutdown-overlapped startup closes the new hotkey before discarding it; it never leaves an unowned global hook. The native Desktop handler applies the same rule to disconnects, keeps startup outside its state lock so disconnect never waits on the native hook, and rechecks its connection generation before arming (`tests/desktop/test_computer_execution.py`). A failed stop callback is logged without killing the dispatch thread, so subsequent desktop control can still receive double Esc (`test_computer_use_batch.py`, `test_hotkey.py`).
- Temporary key and mouse-button releases are part of input success. A refused release retries cleanup and reports `computer_use_unavailable`; still-held input remains tracked for later cleanup, and cleanup during interruption preserves the interruption. Normal key operations retain an intentionally held mouse button. The F24 activation tap uses the same tracked press/release path: a partially accepted native batch must not leave an untracked key down (`test_windows_target_input.py`).
- Windows app identity: keys are the lowercased executable path, `exe:<basename>` and `pkg:<package family>`; generic hosts (python, java, node, explorer, mmc, rundll32, ...) get no `exe:` key. UWP frames resolve to their CoreWindow process. Apps with the same display name merge into one app, so an approval by name covers all of its windows. A process belongs to a Start app by path or package key first; else to the Start app whose shortcut's executable lies in the process's own folder (not a subfolder), when that folder holds the executable of exactly one Start app, lies outside the Windows directory, and both executables have the same version-resource ProductName; else by a unique `exe:` key (`StartIndex.lookup`). Reason: a shortcut can start a launcher that runs the app beside it (`blender-launcher.exe` -> `blender.exe`); without the folder match `list` showed the installed and the running app as two apps and `open` started a second instance (Session 2026-10-21). The product check keeps unrelated tools that share a folder apart. Known limit (observed, not fixed): installations whose executables share a name, such as two Blender versions, still cross-match through their `exe:` keys, so one running marks both entries running and `open` of the other brings its window to the front. Start-menu discovery (one hidden PowerShell call, cached 60 s, refreshed in the background) can delay the first window lookup up to 20 s. Start names are localized.
- Own windows: the current process and any `vBot*.exe` map to app "vBot" (key `vbot:self`) so they are named like the Start entry; they get no special access treatment. A development Desktop shell running under `python.exe` in another process is named after its executable.
- Every key, chord and typed character is held 20 ms and followed by a 20 ms gap (`_win_input._KEY_HOLD`, `_KEY_GAP`): Windows 11 Notepad and other WinUI text boxes drop or repeat keys whose down and up events arrive together (verified live 2026-10). Typing therefore runs at about 25 characters per second.
- Bringing a window to the front (`WindowsTarget._activate`, used by `computer_apps open`) tries `SetForegroundWindow`, then `AttachThreadInput`; when Windows' foreground lock refuses both, it taps F24 (`_tap_unbound_key`), which makes vBot the source of the latest input, and retries. Never Alt: an Alt tap put the activated window into menu mode, and Paint then swallowed the next click while showing its key tips, so ribbon clicks and drag starts did nothing and Agents fell back to UI Automation scripts (Session 2061, 2026-10; F24 activation verified live 2026-10-19).
- Typing presses, for each character the foreground window's keyboard layout types with one key, that key with its scan code, holding Shift or Ctrl+Alt (AltGr) for it alone, like a real keyboard: apps that read raw keys, such as Blender's Python console, ignore `KEYEVENTF_UNICODE` input (Session 2026-10-21: typed text did not arrive, Enter did). The key comes from `VkKeyScanExW` and must type exactly the character per `ToUnicodeEx` with the current CapsLock state; with CapsLock the other Shift state is tried. Control characters (their keys are shortcuts), dead-key characters (German `^`, backtick, acute: a dead key would accent the next character), characters without a key, and all text while an input method is open (`IMC_GETOPENSTATUS` of the foreground window's IME window) go as `KEYEVENTF_UNICODE`. The plan is the pure `_win_input.text_units` over a `KeyboardLayout`. Single-character keys map through the same layout and refuse characters needing dead keys. `cmd`/`meta` are refused with a pointer to `ctrl` or `win`.
- Screenshots are written to `<data_root>/artifacts/temp/computer_use/shot_*.png` (`IMAGE_CATEGORY`), a Storage temporary-file category with 72-hour retention by modification time (`storage.md`). The Model receives the pixels with the Result; Chat keeps its own Attachment copy for later requests (`chat/request-building.md`). Only the displayed Tool media reads the temporary file, so older Session history shows such images as unavailable. Installs before 2026-10 left images in `<data_root>/tmp/computer-use/`, which nothing removes.

## Agent-facing text

One row per sentence of the Tool descriptions, the changed parameter descriptions and the Skill's coordinate guidance. Evidence: Paint Runs and Sessions 1679 and 1681 (2026-10), where Agents converted coordinates between images of different scales, analysed screenshot files with PowerShell, missed canvas edges by a pixel and did not know they could reuse screenshot ids.

Extension Tools have one static description for every Agent: Extensions get no per-Agent definition hook, so mentions of companion Tools stay conditional ("If you have computer_batch ..."), unlike core Tools, which name only Tools the Agent has.

| Text | Reason |
| --- | --- |
| `Operate the selected computer's desktop (Windows)...` and the Skill's `selected Windows computer` / `selected computer's desktop` | Tool choice: names the selected execution target and native OS, so Agents do not mistake a remote Desktop for the server or use macOS keys. |
| `Computer id or exact name. Omit to use this Session's default computer; choose another only when the user's task calls for it.` | Target selection: a call can stay on its Session default without guessing an id; mentioning another computer is deliberate. The registry refuses a computer outside the Session's allowed set. |

An explicit unavailable screenshot reference is refused for keyboard actions as well as coordinate actions; only an omitted reference may fall back to the latest observation or no observation. Batch validation refuses it before any earlier input runs. Reference failures (`invalid_arguments`) state the unavailable/changed image, that no input was sent for the action, and the recovery: take a new screenshot and use its reference. Bounds failures name the selected image and its pixel size. `focus_changed` names the app in the image or the app the last click went into, the app now in front, that the action was not sent, and the fix: click into the intended window or take a screenshot. `screen_changed` names the image, the app it shows at the point, the app there now, that the action was not sent, and the fix: take a screenshot, and bring the app to the front first to continue in it. The `wait` cap note names the cap and says to wait again for the rest, so the Agent waits the remainder instead of acting early. Conflicting window/display selection refuses before execution.
