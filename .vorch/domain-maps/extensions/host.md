# Extension Owner-bound Host

The capabilities an Extension reaches through its owner-bound host and owned execution: temporary execution groups and private Session Tools, prompt inspection, group titles, owner-managed Session lifetime, deferred Tool outcomes, Tool result payloads, OAuth browser redirects and Computer routing. Source: the `ExtensionHost` fields in `core/extensions/operations.py`, bound per owner by `core/runtime/_extension_host.py::ExtensionHostFactory`; Extension databases have their own file (`extensions/databases.md`); owned-Session storage and authority belong to `sessions/owned-execution.md`, temporary Agents to `agent.md`.

## Temporary execution groups

API 6 adds owner-bound temporary execution groups, hidden Session Tools and prompt blocks, receipt-bearing request callbacks, and isolated page declarations. `core/agents/temporary_execution.py` owns creation/admission/drain and exact receipt/history/usage reads; it never creates Identity workspaces. Every private Tool declaration must retain its exact current registration; a missing or collided declaration blocks the Session capability. The binding's `tool_access.denied` may then remove individual private Tools from its grant set. Private denials are excluded from ordinary Tool/Project validation, while ordinary selections cannot grant private Tools. Prompt inspection and execution use the same selected grants. Their input types use the shared Tool representation normalization and validation contract; owner-specific call repairs use their argument normalizer, and public catalogs exclude them while collision detection and teardown retain them. Quiesce drains owned work before declarations are removed; a drain past its deadline is logged and left running uncancelled while removal proceeds, and the retired registration fails closed. Evidence: `tests/core/agents/test_temporary.py`, `tests/core/extensions/test_deactivate.py`, and `tests/core/chat/test_chat_loop_extension_tools.py`.

Temporary-profile preflight validates ordinary names/settings separately from owner-issued private grants. A broad repository Tool policy snapshots only ordinary catalog names; private selections cannot grant capabilities. Unready ordinary integrations follow normal request-time visibility instead of blocking an unrelated participant's startup; the owner's private handoff Tools still require readiness (`test_runtime_extension_host.py`).

API 27 adds optional `register_session_runtime(before_tool_call=...)`. Chat invokes it after Tool authorization and before hooks or handlers, including programmatic calls and owned Sub-Agents. It receives `SessionRequestContext`, `tool_name` and `tool_call_id`; return `None` to admit or a non-empty reason to refuse with `execution_paused` and request turn end. Already admitted sibling calls settle normally. Exceptions and retired registration fail closed; this is a required admission check, not a fail-open Hook.

The optional API 27 `before_model_request(context)` admission callback runs after automatic Compaction and retry waiting, immediately before every physical Chat Model attempt, including the non-streaming fallback. Descendant Runs also call it before request preparation and automatic Compaction because they have no private input-delivery boundary; owners admit an unseen Run once by id. It returns `None`; an exception prevents that attempt. The registry revalidates the exact registration after the callback. It does not deliver Notes: `before_request` retains its receipt-backed input boundary before Compaction and runs once for the logical request, not again for physical retries. Chat resolves descendants' admission binding from their execution owner without granting private Session Tools or invoking parent delivery callbacks. This separation lets owners enforce settled consumption without duplicating input or acknowledging a delivery that was never appended.

`await host.execution_usage(group_id, run_ids=None)` reads settled canonical Model consumption at recorded prices for this owner and group. Omit Run ids for the whole group, including group-level requests; an empty list selects none. It returns calls, input/output tokens, USD cost, and unreported/unpriced call counts. Running requests enter the next read after settlement, including failures and cancellations. Missing usage is explicit; estimates remain included. Both sides of the await check registration. Budgets use this read rather than the disposable Statistics projection (`usage.md`).

## Native Decisions

`host.review_context(context)` returns bounded canonical human requests, separate delegated evidence and a Permission summary for a prepared-shell review. It uses Session sender provenance and stamped Sub-Agent reply targets, includes live ancestors' human requests and masks known Agent Secrets. Full bounds and truncation behavior: `extensions/shell-review.md` -> Execution integration.

API 23 exposes `await host.decide(context, request)` for one native judgment through the configured Decision Model. The request contains `state`, `questions` in the DecisionService vocabulary and optional shared `context`; it never selects another Model or simulates Chat JSON. The result is the canonical native answer map, Model and Usage. Item failures raise `DecisionError`. `context` is the calling ToolContext, or `None` for management previews. Runtime attributes Usage to the declaring Extension plus the available Run/Session/Agent/Project/group and checks the exact registration both before admission and after the request. A retired host cannot return a late authorization. Source/tests: `_extension_host.py`, `tests/core/runtime/test_runtime_extension_host.py`; executor: `model_tasks/decisions.md`.

## Prompt inspection

The optional host `inspect_prompt(config, project_id)` capability previews a temporary configuration with the owner's private Tools, the selected Project's context and Model-specific Tool routing. It returns combined text, rendered block details and Tool definitions without creating a Session or Run; API 24 also returns the resolved prospective Agent's `model` binding and `thinking_effort`, so an editor can check selected roles without resolving every catalog profile. `catalog()` includes public System Prompt block metadata and, since API 25, the roster `agents` (`id`, `name`, `description`, `placement`; built-in Agents excluded) that `identity_profile` can name. Its `models` list each Model with the usable Connections it allows, in Provider order, and `context_window`: the raw window of the first of them, the Connection a bare Model binding resolves to (`Model.context_window_for`; `null` stays unknown). The bundled Swarm uses these capabilities for explicit prompt composition; see `extensions/swarm.md` and `tests/core/runtime/test_runtime_extension_host.py`.

## Transient attention

API 24 adds `await host.notify(title, body, *, page_id, route="", key=None)` and synchronous `host.set_page_badge(page_id, count)`. Both authorize the current registration and one of its declared pages before publication; stale hosts fail. Notifications contain plain text (title <=200, body <=2000 characters), a local optional key <=128 characters, a canonical UTC `at`, and the owner/page/local route, never an arbitrary URL. A route is empty or `/segment/...` with no empty or dot segment, URL escaping, query, fragment, backslash or control character (<=1024 characters). The key replaces that owner's same visible notification in each accessor; it does not suppress repeated publications or create an inbox. The server's bounded event replay is the only retention. WebUI presentation: `webui/app-shell.md`; native presentation and its switch: `cli/application/tray.md`.

Badges are registry-local integers from 0 to 2^31-1 (not booleans); zero clears, an unchanged value publishes nothing. Their revisioned `page_badges` invalidation and descriptor projection are in `extensions/capabilities.md` -> Page declarations. Owners reconstruct their counts at startup rather than relying on a durable core store. Sources/tests: `core/extensions/notifications.py`, `_extension_host.py`, `tests/core/runtime/test_runtime_extension_host_attention.py`.

## Current authority and pending approvals

API 24 `await host.input_authority(context)` classifies only the latest canonical input of the current Run as `user`, `authorized_task` or `none`, using `_shell_review_context.py`; Assistant output, old human inputs and delegated/ancestor content cannot manufacture authority. The helper returns no conversation text and never authorizes another effect by itself (`runtime/extension-host.md`).

`await host.pending_approvals(group_id, run_ids)` accepts at most 1000 exact Run ids and returns `{revision, requests}` from the existing Run manager, filtered through canonical owned-Run records for this owner and group. Each request exposes only `run_id`, `project_id`, `agent_id`, `session_id`, never prepared arguments or a decision capability. The registration is checked again after the owned read. Pages open the original Session through `client.openSession(address)` and use its existing approval UI; no Extension-specific approval store or automatic resolution is introduced (`webui/extension-pages.md`).

## Group titles

`temporary_agents.title_group(group_id, source_text)` stores a local title immediately (the request's first paragraph without a Markdown heading marker, bounded like a Session's local title, so a brief's heading does not run into its body), then lets the Runtime's shared Session title generator replace it (configured Title Model, else the approximately cheapest group participant Model by catalog input+output rate, else the first participant; one attempt, failures keep the local title). It awaits the Model call, so owners run it in the background. `group_titles(group_ids)` reads stored titles within the caller's owner namespace. Titles are canonical Session data (see `sessions.md`), so Statistics keeps showing them after the Extension is disabled. Evidence: `test_titles.py`, `test_runtime_extension_host.py`.

## Owner-managed Session lifetime

While its Extension is installed - loaded, failed, disabled or overridden - only the owner can remove its Sessions; ordinary archive, move, delete and Project removal refuse them (`sessions/owned-execution.md`). API 10 lets an owner reconcile: `temporary_agents.groups(after="", limit=100)` pages its group ids that still have live participant Sessions, and `archive_group(group_id)` (closed groups only, else `ValueError("group_not_closed")`) archives them under a no-Run guard as one `owner_group` archive entry (`archive.md`; listed and purgeable, not restorable, purged by the retention sweep once the user's retention period ends), keeping history, bindings and usage attribution; `delete_group` still removes an archived group (`agent.md`). Both close each live participant's Terminal Sessions and shell commands first, like an ordinary Session removal (`release_temporary_group`), then remove the Scratch Areas of the removed root Sessions after the archive/delete succeeds. A participant that is only a Sub-Agent retains its live Parent's area.

Once an Extension is removed from every root, nothing could manage its Sessions any more, so `ExtensionRuntime` archives the live ones of every owner name without a registry record (entry reason `extension_removed`) before startup handlers run, at initial startup and after each reload (`ExtensionHostFactory.archive_uninstalled_owner_groups`, logged at WARNING per owner). It skips this when a scan root was missing or unreadable (`ExtensionRegistry.installed_names()` is `None`), since absence then proves nothing, and leaves a group with active or queued work live until the next load. Failures are logged and never block the Extension layer. An archived participant cannot be re-created, so a returning owner deletes such groups. Evidence: `test_runtime_extension_host.py`, `test_runtime_extension_reload.py`.

## Deferred Tool outcomes

API 15: owner-bound hosts expose `capture_tool_call(context)` for an opaque receipt tied to this Extension's exact canonical invocation; `restore_tool_call(receipt)` resolves only its original live Session generation, following moves and Agent renames, never a fork or reused address. It returns `None` once the ordinary Tool Result exists or the original invocation is no longer live. `deliver_tool_outcome(receipt, content)` commits one persisted note with an atomic receipt; repeating identical delivery is a no-op, conflicting content is refused. The producer quotes external content and does not add reminder tags. Recovery never restarts the Run or repeats a mutation. Domain task state belongs in the Extension's database. Canonical receipts and exact source validation belong to Sessions (`sessions.md`); Runtime rechecks the current registration and resolves Agent, working Project, paths and the Session's Permission Boundary (its stored ceiling included) off the Event Loop, so a restored context reaches no more than the original call. API 18: `resolve_permissions(project_id, agent_id)` returns the boundary of a new Session of that Agent, for a call an Extension makes as it outside any Session (MCP management `invoke`). `resolve_tool_agent_async(context)` is the async host capability for ordinary policy and sampling resolution; the synchronous capability remains for compatibility. Evidence: `test_runtime_extension_host.py`, `test_runtime_mcp_access.py`.

API 26 adds `defer_tool_call(context)`: it captures the same invocation or upgrades its existing receipt, which remains resolvable after the initial pending Tool Result. The Extension waits for `after_result_persisted` before delivering a live completion. `deliver_tool_outcome` binds the exact final content, then uses the existing completion coordinator: a running Session reads it at a request boundary, an idle Session gets a continuation, and a user-stopped origin gets only a Note. The host retains the origin independently of bounded Run-manager retention, including cancellation and continuation settings. After restart, delivery persists only the Note and never revives an execution epoch. The canonical receipt pins the Session generation; the completion coordinator follows moves and rejects replacement generations. A stored outcome and the canonical Note marker close the history-commit/acknowledgement crash window; conflicting content is refused. Ordinary `capture_tool_call` keeps API 15 semantics.

Agent-facing delivery prefix: `Background Tool result <receipt>:` identifies the completed invocation in a coalesced Note and supplies its durable delivery marker; the Extension provides the attributed, quoted outcome below it. It adds no polling or replay instruction.

## Tool result payloads

API 8: an Extension Tool running in a Session keeps JSON data beside its Tool Result with `context.attach_result_payload(payload) -> payload_id` (`res_` plus 16 base32 characters; readers accept any safe opaque id, `is_safe_id`). `context.result_payloads_available` is false outside a Session (management, CLI, direct calls), where attaching raises `RuntimeError`; the Extension then returns the data inline. Chat stages the payload and stores it with the Tool Result in one transaction (`chat/run-execution.md`, `sessions/runs.md` -> Tool result payloads): a handler that raises, returns an invalid result or is cancelled leaves none, a returned failure keeps them. The owner is the attaching Tool's Extension; a built-in Tool's payload belongs to `builtin_payload_owner(name)` (`tool:<name>`, never an Extension name, which has no `:`), as for `show_widget` (`tools/show_widget.md`). The owner-bound `await host.load_result_payload(context, payload_id)` returns the decoded payload, or `None` unless it belongs to this Extension and its Tool Result is in the calling Session's current view (own, fork-inherited, or materialized after an ancestor's deletion); it raises `ValueError` once the registration is no longer current. The Extension adds its own policy check (MCP: `extensions/mcp.md`). Evidence: `tests/core/runtime/test_runtime_extension_host.py`, `tests/core/chat/test_tool_result_payloads.py`, `tests/core/sessions/test_tool_result_payloads.py`.

## OAuth browser redirects

API 11: `host.oauth_redirects` is the Runtime's `OAuthRedirects` (`core/extensions/oauth_redirects.py`), or `None` without a Runtime. An Extension that sends the user's browser to an authorization server uses `callback_url` as its redirect URI when it is not `None`, awaits `expect(state)` for the redirect query and calls `discard(state)` when it stops waiting. The server binds `callback_url` at startup and passes `GET /api/oauth/callback` queries to `deliver` (`server/browser-capabilities.md` -> OAuth callback); only a pending, unexpired `state` (`DEFAULT_TTL_SECONDS`, 600 s) matches, each one once, so a stray or replayed request completes nothing and cancels nothing. `callback_url` is `None` when the server listens only on an address that is not this machine's loopback or wildcard address; the Extension then needs another way back, such as the user pasting the redirected address (MCP: `extensions/mcp.md`). Evidence: `tests/core/extensions/test_oauth_redirects.py`, `tests/server/test_app_http.py`.

## Computer routing

API 21: `host.computers` is the Runtime's shared `ComputerRegistry`, or `None` without that service. Extensions resolve a Tool context's selected Computer with `resolve(context, requested_id, capability)` before execution. Local `server` execution stays with the capability owner; remote operations use `call`, or `call_sync` from a native worker, with instance fencing for retained process or desktop state. The host supplies no additional Computer grant: exact Session policy, durable identity, availability and no mutation replay remain the registry's contract (`computers.md`). The bundled Computer Use Extension consumes this service without importing Runtime or transport code (`extensions/computer-use.md`).
