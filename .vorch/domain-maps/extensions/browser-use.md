# Browser Use Extension

Read this reference when changing the bundled `browser_use` Extension or `browser` Tool. Setup and deployment limits are documented in `docs/browser-use.md` (repository-relative).

## Ownership and permission

`resources/extensions/browser_use/extension.py` owns registration, configuration, validation, native transport, browser lifecycle, tab/ref ownership, and media. The existing Extension API, Tool Access Policy, and `ToolContext` media seams supply the integration; this capability has no browser add-on or executable Skill. The API v5 manifest and `requires_opt_in=True` require an explicit Agent grant. Mode `all` and Project whitelist membership alone do not grant it. The handler resolves live Agent and Run restrictions before every backend command, including each form field and observations.

`runtime.py` owns dependency preparation: an authorized opening operation downloads the pinned native `agent-browser 0.36.0` into `<data-dir>/artifacts/browser-use`, verifies the release SHA-256 and version, and prepares the managed browser. No Node/npm or PATH client is required. Readiness stays available before preparation; registration and service startup do not download. General host Bash access remains outside this Tool permission boundary.

The Extension's `skills/browser-use/SKILL.md` supplies workflow instructions through the existing loaded-Extension Skill discovery path. It contains no executable helpers and uses the granted Tool. Disabling the Extension removes its Tool and Skill from runtime discovery; ordinary Skill visibility policies remain in effect.

## Lifecycle and input invariants

- Runtime preparation uses thread and cross-process installation locks; the shared `~/.agent-browser/browsers` cache has its own cross-process lock. Successful installations survive reloads; per-service failure caching allows two attempts per mode. Cancellation, shutdown, and permission checks run during setup and before connection creation. Setup subprocesses have deadlines, bounded output, isolated environment variables, and no shell. Attached modes prepare only the client.
- Managed Windows/macOS uses the native client's Chrome for Testing installer and its standard cache. Linux prefers system Chromium/Chrome; apt hosts can install missing Chromium with root or noninteractive sudo. The public Debian/Raspberry Pi OS server Installer prepares Chromium and shared libraries, excluding desktop-only clients. Linux ARM64 needs system Chromium. Browser binaries are passed explicitly to the owned native client; the Agent cannot choose an executable.
- Backend identities are generated internally and keyed by exact Project/Agent/Session identity. A browser stays connected across Runs in that Session; refs do not. Explicit close, idle cleanup, and Extension shutdown close only that owned backend connection. Native close shuts down a managed browser but only detaches from an external browser. Failed cleanup stays tracked for retry.
- The three live connection settings are managed launch, local existing Chrome auto-connect, or a configured remote CDP URL. Managed visibility defaults to `runtime.desktop_available()`; an explicit saved setting wins. Windows checks the process window station, macOS the console owner, and Linux the display environment. The window belongs to the server host, with no Desktop Client bridge. Configuration changes retire the old connection before another browser operation; the next call reconnects. Endpoint credentials are resolved through the existing Extension secret setting mechanism.
- `status` reads configuration and tracked connection state without setup, version probing, connection creation, or retirement. It reports mode, managed visibility, and browser host; pending configuration appears as `next_connection`. This is tracked ownership, not a liveness probe. Opening results also identify the connection configuration without exposing its endpoint.
- Per-session locks serialize managed browsers; a shared lock serializes external browser operations. Cancellation, policy, and config are rechecked after lock admission and before subsequent commands. Already dispatched commands can finish. The Extension never replays input; the pinned native client's transport can resend commands after EOF/reset errors (upstream `cli/src/connection.rs::send_command`), so an end-to-end exactly-once guarantee is unavailable.
- External connections use native `--pin-tab`. Public tab ids are stable CDP target ids, never list indexes. Before page operations, verify the bound target still exists and is selected; restoring a drifted selection clears refs. A missing target fails rather than falling back to another tab. Another tracked Session's selected external tab cannot be selected or closed.
- Snapshots default to 4000 characters of compact interactive content; `limit` allows expansion to 16000 and `selector` scopes a section. Both options also apply to requested action observations, and fail validation when that action will not observe. Only refs on complete returned lines become opaque snapshot-scoped public refs. Short numeric ids are leased from the Extension-owned `artifacts/browser-use/refs.db` counter through SQLite transactions; unused ids are not reclaimed, so concurrent services and reloads sharing a data directory cannot reuse them. The counter is not authorization: only the current Session/Run ref map permits input. Every snapshot clears old refs before dispatch, including empty/failed observations. Input clears refs; a new Run cannot reuse them. Resolve the entire fill target list before applying its first field.
- Snapshot/read observations use a temporary document observer and bounded read-only navigation retries. A still-changing snapshot withholds refs; origin mismatches cannot publish a snapshot, and observation-invalidated targeted reads cannot reuse native refs. Returned page metadata includes an actual HTTP status only when available, never inferred from the URL. The settling interval does not prove application completion. `wait` supports visible text, exact URL, or neither; it observes by default and returns the current page with `condition_met=false` when its five-second condition deadline expires.
- `open` reconciles a lost reply, timeout, or navigation-context error by checking the owned target and observing it, without another navigation. A readable page returns a successful observation with `navigation_confirmed=false` and the classified `navigation_error`, never a fabricated completed count. URL matching and redirect spelling cannot establish command completion. `observe=false` returns metadata only; requested snapshot scope/limit still apply. Failed reconciliation retains the original error; cancellation, permission/config changes, and a missing owned tab remain explicit failures. Other uncertain input errors direct the Agent to inspect rather than repeat.
- `fill` applies text and selection fields in order without repeated snapshots. Each field's optional `kind` selects native fill or select; omission means text fill. Validate every item's shape, kind, and ref before any input; recheck permissions and cancellation before each command. A later failure reports completed fields and stops. Argument errors name schema paths and a correction without returning input values. Failed observation after successful input preserves the successful action and reports an observation error. Failed close-tab replies are reconciled by reading tabs, never by replaying close.
- Native commands are argv arrays sent through one-command batch JSON on stdin, preventing form values from becoming global CLI options. Use the native Windows executable directly, no shell. Seekable temporary files avoid daemon-inherited pipe EOF hangs. Transport has a 45-second timeout and bounded output; ambient browser configuration and credentials are not forwarded. Known native diagnostics map to navigation, timeout, lost-response, connection, or unavailable-element recovery codes without echoing raw backend text or inferring website detection causes. Navigation reconciliation logs only its classified error code, never URL or page contents.
- Screenshots and managed downloads live below the calling data directory's `tmp/browser-use` tree. Screenshot paths use `shot_` plus 12 lowercase base32 characters, reserved exclusively before native capture. Screenshots are bounded PNG files delivered directly through `result_media` and `presentation_images`. Downloads lists only completed, nonsymlink files from the managed browser's download directory. Attached-browser downloads and upload paths belong to the browser host, which can differ from the server.

## Verification routing

`tests/resources/extensions/test_browser_use.py` covers grants, validation, preparation admission, cancellation/revocation between fields and observation retries, Session/Run isolation, stale refs, selected-tab drift, side-effect-free status, bounded observations, wait conditions, cleanup, transport, media, and the complete action matrix. `test_browser_runtime.py` covers desktop detection, cold setup, integrity, caching, concurrency, supported asset selection, package preparation, and cancellation. `tests/scripts/test_install_scripts.py` exercises the server browser prerequisite. Bundled discovery and Extension Skill lifecycle expectations live in `tests/core/runtime/test_runtime.py` and `test_runtime_providers.py`. Generic opt-in policy and registration tests live in `tests/core/tools/test_availability.py` and `tests/core/extensions/test_capabilities.py`.

`scripts/probe_provider_tool_call.py --scenario browser --browser-case ...` uses the production Tool definition for structural Model-call probes without executing browser input. Run the module with `--scenario browser_workflow` for a real Model/Skill/browser workflow against a delayed local form, unrelated page navigation, and download fixture, including automatic native-client preparation. The fixture validates website submissions and file bytes independently of the final reply and reports observation sizes/states. Operator documentation records measurements and their limits.
