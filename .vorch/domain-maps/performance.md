# Performance

Always-on, low-overhead measurement of the server process, History Windows that keep it across restarts, on-demand Recordings that produce Perfetto-compatible timelines, and on-demand Heap Censuses.

## Overview

`core/performance/` owns process-wide duration histograms, gauges and counters, the Event Loop monitor and stall watchdog, History Windows, Recordings and their files, and Heap Censuses. Instrumented code in any domain records through module-level functions into one process-wide sink, the same way it logs. The Runtime-owned `PerformanceService` runs the monitor, watchdog and History Windows and owns Recording start/stop, trace writing, retention and listing. Exposure is `performance.*` RPC (`server/rpc/performance_methods.py`) and the `vbot performance` CLI area (`cli/performance_management.py`, alias `perf`); there is no WebUI view. The WebUI measures itself (`webui/src/lib/clientMetrics.js`) and reports into the same sink through `performance.client_report`, under `webui.*` names.

The domain measures; it never changes behavior. It does not own what is measured: each owner decides its own measurement points (catalog below). Provider wire capture is a separate subsystem (`debug.md`); a performance trace never contains request or response content.

Module split: `performance.py` (public API, sink, service), `_metrics.py` (log-scale histograms, gauges, counters, name cap), `_monitor.py` (lag task, samplers, watchdog thread, stack rendering), `_thread_cpu.py` (per-thread CPU time on Windows and Linux), `_gc.py` (cyclic garbage collection pause observer), `_recording.py` (event buffer, lanes, trace/summary files, retention), `_heap.py` (Heap Census), `_history.py` (History Window lines, day files, retention).

## Terms

Shared terms (Run, Session, Tool) live in `.vorch/GLOSSARY.md`.

### Recording
One bounded, explicitly started capture window. At most one is active per process. While active, measurements with a track also become trace spans, counted occurrences with a track become instant events, gauges become counter samples, and stalls become instant events; the Recording keeps its own window histograms, gauge maxima, counters and stalls. It stops on request or at `max_seconds`, then writes a trace and a summary file. Not a Debug trace (`debug.md`).

### Track
The trace group a measurement belongs to, rendered as one Perfetto process: a Session address (`session_track()`: `<agent>@<project>/<session>` or `<agent>/<session>`), `rpc`, `sqlite`, `events` (server-pushed invalidations), `webui` (WebUI client reports), `runtime` (Event Loop lag, stalls, process gauges) or `worker pool <name>`. Tracks exist only inside a Recording; histograms ignore them.

### Lane
A trace thread inside one Track. A span takes the lowest lane that is free at its start, so concurrent spans of one Track never overlap on a lane. Lane numbers carry no identity (lane 0 is not a particular Run).

### History Window
A fixed stretch of server time (10 minutes, `HISTORY_INTERVAL_SECONDS`) whose measurement changes are appended as one JSON line to disk when it ends, and at shutdown. Windows start when the service starts; each holds what the process-lifetime histograms and counters gained during it, the gauges' last and highest values, and its stalls. They survive restarts, unlike the snapshot, and need no preparation, unlike a Recording.

### Heap Census
An on-demand count of the objects the cyclic garbage collector tracks, per generation and by module-qualified type name (`module.qualname`), aggregated by module (first two package segments). Changes are relative to the same service's previous census. Objects frozen at startup (`server.md`) are only counted as `frozen`, so the generations show what serving created. Not a memory size: it counts container objects, whose number drives full-collection pauses.

### Stall
An Event Loop tick overdue by more than the stall threshold (250 ms). The watchdog thread samples the loop thread's Python stack every 50 ms during the stall and aggregates identical stacks; frames are `path:line qualname` only. On Windows and Linux it also reads every Python thread's CPU time on each sample and samples the stacks of the other threads that ran since the previous one; the stall names the other threads that used at least 10% of the measured CPU window, with their stacks. The loop's own CPU in that window tells the cases apart: close to the window means the loop computed itself; near zero means it waited, on I/O, a lock, or the GIL held by a named busy thread. Few samples over a long stall mean the watchdog could not get the GIL either: a long GIL-holding call, most often a cyclic garbage collection, which `gc_ms` then shows.

## Interfaces

**Module API** (`core.performance`, usable from any thread):
- `measure(metric, *, track=None, name=None, args=None)` -> `Measurement` context manager, valid across awaits. The histogram always records; with a track and an active Recording the block also becomes a span named `name` (default: metric). `Measurement.annotate(**args)` adds span args; `Measurement.discard()` drops both the observation and the span.
- `record_span(metric, started, *, ended=None, track=None, name=None, args=None, min_span_ms=0.0)` records a duration that began at a `time.perf_counter()` value. A span is emitted only when the active Recording began before `started` and the duration reaches `min_span_ms`.
- `record_duration(metric, ms)` and `set_gauge(name, value, *, track=None)`; `session_track(agent_id, session_id, project_id=None)`.
- `count(metric, amount=1, *, track=None, args=None)` adds occurrences to a counter; with a track and an active Recording each call also becomes an instant event named `metric` with `args`. Use it for events, not durations.
- `merge_histogram(metric, histogram)` adds durations measured outside the process, already sorted into this module's buckets: `ExternalHistogram(count, total_ms, min_ms, max_ms, buckets)` maps a bucket index (`bucket_index`: 10% log steps from 0.01 ms to one hour, 0 for underflow, 208 for overflow) to its count and raises `ValueError` when the data cannot come from such observations. It has no track and no span.
- `PerformanceService(recordings_dir, *, samplers=..., history_interval_s=600)`: `start()`/`stop()`/`aclose()`, `snapshot()`, `start_recording(label=, max_seconds=)`, `stop_recording()`, `recording_status()`, `list_recordings(limit=)`, `heap_census(top=)`, `history(since=, until=, limit=, names=)`. `start()` opens the first History Window; `stop()`/`aclose()` append the last one (`reason` `shutdown`). `history_interval_s=None` disables History Windows. File and snapshot work runs on its own `performance` worker pool. Errors: `RecordingActiveError`, `RecordingInactiveError` (both `PerformanceError`); an invalid label or `max_seconds` raises `ValueError`.

**RPC contract** (field names are a contract; an external load-test harness consumes them):
- `performance.snapshot` `{}` -> `{started_at, uptime_seconds, metrics, gauges, counters, stalls, recording}`. `metrics` maps name -> `{count, sum_ms, min_ms, max_ms, p50_ms, p90_ms, p99_ms}`; `gauges` maps name -> latest value; `counters` maps name -> total occurrences; `stalls` is the retained list (max 50, oldest first) of `{started_at, duration_ms, gc_ms, cpu_window_ms, loop_cpu_ms, samples: [{count, stack: [frame]}], threads: [{name, cpu_ms, samples}]}` with samples ordered most frequent first; `gc_ms` is the cyclic garbage collection pause time of all threads between the stall's last on-time monitor tick and its end, capped at `duration_ms` (its window opens up to one 100 ms tick early); `cpu_window_ms` is the stretch from the stall's first sample until the watchdog saw the loop resume, over which `loop_cpu_ms` and each thread's `cpu_ms` were measured (Windows counts CPU in 15.6 ms ticks); `threads` lists at most 5 other threads by CPU, each with at most 5 distinct stacks; the three CPU fields are `null`/empty on platforms without per-thread CPU time; `recording` is the status below or `null`. Values are process-lifetime, not windowed.
- `performance.recording_start` `{label?, max_seconds?}` -> status `{recording_id, label, started_at, elapsed_seconds, max_seconds, event_count, truncated}`. `label` is non-blank, <= 200 characters; `max_seconds` is an integer 1..3600, default 300.
- `performance.recording_stop` `{}` -> `{recording_id, label, started_at, duration_seconds, event_count, truncated, stopped_reason, trace_path, summary: {metrics, gauges_max, counters, stalls}}`. `summary` covers only the Recording window.
- `performance.recording_list` `{limit?}` (1..100, default 20) -> `{recordings: [...]}` newest first, each the stop result without `summary`.
- `performance.heap` `{top?}` (1..100, default 20) -> `{taken_at, duration_ms, previous_taken_at, tracked, generations: [{objects, collections, collected, uncollectable}], frozen, types, modules, growth}`. `types` and `modules` are the `top` largest rows `{name, count, change}` (`change` is `null` on the first census of the service); `growth` holds the `top` rows with the largest positive `change` (empty on the first census). Censuses run one at a time on the `performance` worker pool.
- `performance.history` `{since?, until?, limit?, names?}` -> `{interval_seconds, retention_days, windows}`: the newest `limit` (1..2016, default 144 = one day) stored History Windows with `ended_at >= since` and `started_at <= until`, oldest first. `since`/`until` are ISO 8601 timestamps with an offset; `names` (at most 50) keeps only those metrics, counters and gauges in each window. A window is `{started_at, ended_at, reason, process_started_at, metrics, counters, gauges, gauges_max, stalls, stalls_dropped}`: `reason` is `interval` or `shutdown`; `process_started_at` changes when the server restarted; `metrics` holds summaries (snapshot shape) of the observations made in the window only; `counters` the occurrences added in it; `gauges` the last values and `gauges_max` the highest value set in the window, at least the value at its start; `stalls` at most 20 (`stalls_dropped` counts the rest), each with its 3 most frequent samples and each named thread with its most frequent one. Window extremes the window did not move are bucket estimates (about 10%).
- `performance.client_report` `{histograms?, counters?}` -> `{accepted, skipped}`: one WebUI client's measurements since its previous report. `histograms` maps a name to `{count, sum_ms, min_ms, max_ms, buckets}` (`buckets` maps a bucket index, as a string, to its count; see `merge_histogram`); `counters` maps a name to an integer 1..1,000,000; at most 200 names per report. A malformed value rejects the whole report with `invalid_request` before anything is recorded. Only the `webui.*` names of the Metric Catalog are merged; other names are listed in `skipped` (sorted, at most 20) so an older or newer WebUI still reports the rest. Across all clients, at most 60 reports per sliding minute are accepted; a report beyond that returns `{accepted: 0, skipped: [], rate_limited: true}` and counts `webui.reports_dropped`.
- Errors: `performance_recording_active` (start while recording), `performance_recording_inactive` (stop while idle), `invalid_request` (unknown params, bad label/limits, malformed client reports).
- `stopped_reason` is `requested` or `max_seconds`. `trace_path` is an absolute path with `/` separators.

**Files:** `<data_dir>/artifacts/performance/<recording_id>.trace.json` (Chrome Trace Event JSON object format: `{"traceEvents": [...], "displayTimeUnit": "ms"}`, `ts`/`dur` in microseconds from the Recording start) and `<recording_id>.summary.json` (list fields plus `stopped_at` and `summary`). Recording ids use the `perf_` prefix (`core/utils/ids.py`). Both files are atomic; the summary is written last and marks a complete Recording, so listing reads summaries only. The newest 20 Recordings are retained; older pairs are pruned after each write. History Windows are appended to `<data_dir>/artifacts/performance/history/<YYYY-MM-DD>.jsonl`, one compact JSON line per window in the file of its UTC end date; a line torn by a crash is skipped on read and the next line starts fresh. After each append, day files older than 14 days or beyond 64 MB in total (oldest first, never the current day) are deleted. A heavily used server writes roughly 3-6 MB per day (about 25-40 KB per window with 200-300 active metrics); idle windows are small. Like Recordings they are diagnostics outside the JSON document contract (`settings.md`). Placement is owned by Storage (`storage.md`).

**Trace events:** each Track emits a `process_name` metadata event and each Lane a `thread_name` (`lane <n>`); spans are `X` events with `cat` = first metric segment; gauges and `event_loop.lag` are `C` counters; stalls are process-scoped `i` events named `event_loop.stall` with `duration_ms`, `gc_ms`, `cpu_window_ms`, `loop_cpu_ms`, `samples` and `threads` args; counted occurrences with a track are process-scoped `i` events named after their counter (an accepted client report is a `webui.reports` event on the `webui` Track with `rpcs`, `long_tasks`, `long_task_max_ms` and `invalidations` args); garbage collections of at least 1 ms are `gc gen<n>` spans on the `runtime` Track.

## Metric Catalog

Durations are milliseconds; counters are occurrence totals. Names are dotted lowercase words with low cardinality.

- `rpc.<method>` - every registered RPC method in `server/rpc/dispatcher.py::dispatch_method`, track `rpc`. Unknown method names return before measurement.
- Per kernel database `<name>` (`sessions`, ...): `sqlite.<name>.write_wait` (lock wait; spans only >= 1 ms), `sqlite.<name>.write` (each `BEGIN IMMEDIATE`..`COMMIT`/`ROLLBACK` attempt, so a busy retry counts twice) and `sqlite.<name>.read` (the whole read context including the caller's work, plus the writer-lock wait when no WAL reader is available) - `core/database/_runtime.py`, track `sqlite` (`database.md`). The load suite reads the `sqlite.sessions.*` series.
- `worker_pool.<pool>.wait` (admission; spans only >= 1 ms) and `.run` (span named after the callable), gauges `.active`/`.waiting` - every `BoundedWorkerPool` (`core/utils/workers.py`), track `worker pool <pool>`; an `OrderedWorker` records only `.run`.
- On the Session Track, with `run_id` args: `chat.run` (whole Run, `run_kind` arg; `_run_execution.py`), `chat.request_build` (first step: from request-state build to send, or from the loop top when a pre-request Compaction ran; later steps: loop top to send), `provider.response` (each send attempt incl. the too-large retry, `iteration` arg), `provider.first_token` (streaming: first non-heartbeat delta; non-streaming: the whole `adapter.send`), `chat.persist` (spans `persist assistant` / `persist tool results`), `chat.tool_round` (`tool_calls` arg) and `tool.<name>` (one Tool dispatch; discarded for unknown Tool names). Sources: `core/chat/_agentic_progression.py`, `request_runner.py`, `tool_dispatch.py`.
- `chat.compaction` - whole automatic attempt or manual Compaction Run (`trigger` arg `auto`/`manual`), `core/compaction/run_coordination.py`.
- Counters `events.<type>` - each `/ws` server event published by `ServerEventBus` (`server/events.py`), per contract event type; `events.resource_changed.<kind>` - each invalidation per contract kind, also an instant event on the `events` Track with a `subscribers` arg (connected `/ws` clients), so the RPCs clients send in reply appear right after their cause; `events.sse` - each Run event sent over an SSE stream (`server/_streams.py`), all streams together, heartbeats excluded.
- WebUI client measurements, reported by each open WebUI about once a minute (`webui/src/lib/clientMetrics.js`) and merged by `performance.client_report`: `webui.rpc` (each RPC from call to settled result in the browser, including its wait for a connection; the report itself is not measured), counter `webui.rpc_errors` (RPCs that failed), `webui.long_task` and `webui.long_animation_frame` (browser main-thread Long Tasks and Long Animation Frames of at least 50 ms, where the browser reports them; Long Animation Frames only in Chromium), counters `webui.invalidations.<kind>` (each `resource_changed` event a WebUI received, per contract kind), `webui.invalidation_rpcs.<kind>.<method>` (RPCs a WebUI started within 250 ms after a `<kind>` invalidation: the wave that invalidation caused, by registered method) and `webui.extension_page.invalidations.<reason>` (the Extension host told an open Extension page to refresh: `change`, `reload`, `descriptor_changed`, `disposed` or `run_stream_recovered`; `extensions.md`). Counter `webui.reports` counts accepted reports.
- `event_loop.lag` - how late each 100 ms monitor tick woke.
- `gc.gen<n>` - each cyclic garbage collection's pause, in any thread, recorded at the next monitor tick (spans only >= 1 ms, track `runtime`). `n` is CPython's generation: the packaged 3.13 runtime collects generations 0/1/2, where gen 2 is the full stop-the-world traversal of every tracked object; 3.14 reports its incremental collections as gen 1. Collections are counted only while the monitor runs; beyond 4096 unrecorded ones (a very long stall) the oldest are dropped.
- Gauges sampled about once per second: `event_loop.utilization` (loop-thread CPU / wall time), `process.cpu_percent`, `process.rss_mb`, `process.python_threads` (Python threads only: the OS thread count needs a system-wide process scan on Windows, milliseconds of GIL time per sample), `asyncio.tasks`, and the Runtime-injected `runs.active` / `runs.queued`. `performance.dropped_metrics` counts observations dropped by the name cap.

## Conventions

- The sink is the documented exception to constructor injection (`.vorch/PROJECT.md` -> Conventions): it holds only measurements, never state other code reads to decide behavior. The service, monitor and files stay Runtime-owned.
- Metric names, span names and args never carry content: no prompts, messages, Tool arguments, paths from requests or credentials. Ids and counts are allowed as span args only, never in metric names. Only code-defined or registry-validated names may become metric names (for example registered RPC methods, dispatched Tool names).
- More than 1000 distinct histogram, gauge or counter names (each kind separately) are rejected: the observation is dropped, `performance.dropped_metrics` counts it, and one WARNING is logged.
- Recording start/stop and a shutdown discard log one INFO event; a stall >= 1 s logs a WARNING with `gc_ms`, `loop_cpu_ms` (as `<cpu>/<window>`), its five innermost frames, its three innermost vBot frames (files in the vBot source tree, bundled Extensions included) and the busiest other thread with its CPU and innermost vBot frames (or innermost frames), at most once per 30 s (suppressed count reported). Sampler failures warn once per gauge.
- Client-reported names are fixed server-side sets or derived from contract registries (`resource_changed` kinds, registered RPC methods, fixed page reasons), so a client cannot grow the metric set.
- Measure at the owner's boundary with `measure` or `record_span`; use `min_span_ms` for high-frequency short waits so they stay histogram-only in traces.

## Constraints & Gotchas

- The monitor and watchdog start with the Runtime whenever a running Event Loop exists, in every `safe_startup_mode`; a synchronous start without a loop does not monitor. Shutdown discards an active Recording without writing it.
- Windows timer granularity (about 15.6 ms) gives `event_loop.lag` a baseline of 0-16 ms; judge lag by p99 and stalls, not p50.
- A system suspend or debugger pause can show up as one long stall whose samples do not explain it.
- A worker thread that computes in Python holds the GIL until the Event Loop asks for it, and the loop waits one switch interval before asking, again after every I/O operation. Windows rounds such a wait of 1 ms or more up to its 15.6 ms timer tick: with the default 5 ms, one busy thread cut a loop from about 22,000 to 11 local I/O round trips per second (Python 3.12 and 3.14). The server therefore sets 0.5 ms once ready (`server.md`); the loop then asks at once, and at realistic loop load the computing thread lost no measurable time. Such stalls name the busy thread (`busiest other thread`) while the loop samples sit in I/O calls such as `SSLObject.read`.
- Stalls whose loop samples sit in `IocpProactor._poll` with `loop_cpu_ms` near zero, `gc_ms` 0 and no busy thread, while `process.rss_mb` is far below the process's private bytes, are page faults of a trimmed working set: the loop thread waits for its memory to be paged back in. Check the server's priority class, I/O and memory priority first; a Task Scheduler start at the default task priority lowers all three (`cli/application.md` -> Autostart and server supervision).
- A Recording buffers at most 500,000 events (roughly 75-175 MB in memory) and sets `truncated` when full; histograms continue. Trace JSON is written off the Event Loop in 1000-event chunks.
- A span appears only if it began inside the Recording; `measure` blocks open when the Recording stops are dropped from the trace but still counted in histograms.
- Stack sampling uses `sys._current_frames()`; frames are rendered relative to the vBot root or the Python library root. During a stall the watchdog keeps stacks as raw (file, line, name) tuples and renders them once the stall ends: rendering resolves paths through file system calls, each of which releases the GIL and, while another thread holds it, costs a 5 ms switch interval (15.6 ms on Windows) to get it back. Per-thread CPU reads keep the GIL for the same reason (`PyDLL` calls on Windows, the kernel's per-thread CPU clock on Linux; psutil's thread listing scans the whole system on Windows, about 34 ms).
- Outside stalls the watchdog costs nothing beyond its 50 ms wakeup. With 43 Python threads, a stall sample takes about 0.16 ms of GIL time (0.33 ms for the first, which also samples every thread once), and ending the stall about 0.4 ms (Python 3.14, Windows).
- The garbage collection callback runs inside the collector on whatever thread allocated, possibly while that thread holds a lock such as the metric registry's. It must stay lock-free (timestamps, a float total and a bounded deque); histograms and spans are recorded later on the Event Loop.
- The server process freezes its startup heap once the app is ready (`server.md`), so full collections skip modules, classes and Runtime services; `gc.gen2` then reflects the objects created while serving.
- A `gc.gen2` pause grows with the number of tracked objects created since the freeze, and full collections come more often the more container objects survive into the old generation. Long-retained dict/list graphs therefore drive the pauses: finished Runs keep only their settled ending (`runs.md`), finished processes drop their asyncio internals (`tools/process.md`), and Model requests share the live request view instead of copying it per step (`chat.md`). Keep new per-Run or per-step data out of long-lived containers, or bound it.
- A Heap Census lists each generation with one interpreter call that holds the GIL, then counts in 20,000-object slices: 5 million tracked objects took 355 ms with at most 107 ms of continuous Event Loop blocking (Python 3.14, Windows). It also holds references to every listed object until counted. Automatic collection pauses while the generations are listed: a collection between two listings, started by any thread's allocations, would move objects to a generation listed next and count them twice (on Python 3.14 whole old-generation lists at once) or miss them (`test_heap_census_counts_types_by_generation_and_reports_growth`).
- Ending a History Window copies every histogram once and runs on the `performance` worker pool: about 10 ms for 300 active metrics. Tracking gauge peaks for windows adds about 30 ns to `set_gauge`.
- The process sink is shared by every `PerformanceService` of the process; only one should run History Windows, because ending a window resets the gauge peaks.
- A client report lands at once: its histograms enter the snapshot, the current History Window and an active Recording when it arrives, even though they were measured over the minute before. Browser durations use the browser's clock and include its connection queue, so `webui.rpc` minus `rpc.<method>` approximates network and queueing time. The wave attribution is a time heuristic: an RPC the user started within 250 ms of an invalidation counts too, and overlapping invalidations credit only the latest one.
- The WebUI side costs about 0.1-0.3 us per RPC (two clock reads and a map update, Node 24), native PerformanceObservers and one report per minute; an idle tab with nothing measured sends none. Handling a report with 45 names takes about 130 us on the Event Loop (Python 3.14, Windows).
- `measure()` costs about 0.7 us per call without a Recording and about 2.4 us with a track while recording (Python 3.14, Windows); keep it out of per-token or per-byte loops.
