# Compaction

Policy-driven Context transformation and checkpoint creation for chat Sessions.

## Overview

`core/compaction/` owns the provider-neutral Engine: evaluates Triggers, asks one Strategy for a Plan, performs zero or one Model call, validates the resulting Projection, returns one self-contained `compaction_checkpoint` - never rewriting or deleting prior canonical Session records. The Model call always consumes the adapter's canonical stream through Chat's shared accumulator, without passing normalized content back through a raw Provider response parser: some providers (observed on OpenRouter's stealth tier) reject large non-streaming completions outright while streaming the same payload fine. Summary+Tail keeps the already-built request byte-for-byte through the chosen Tail boundary when the Summary target is the active target, removes the native Tail from the Compaction request, and appends one canonical System Reminder containing only the Compaction instruction. `run_coordination.py` owns Compaction Policy decisions, checkpoint persistence, and manual/automatic Run lifecycle. Chat owns request materialization and recovery through `core/chat/compaction_host.py::ChatCompactionHost`, the implementation of `CompactionRunHost`; the coordinator never imports private Chat symbols or reconstructs Chat request state. Pinned prompt-epoch assembly lives in `core/prompts/pinned_context.py` behind that host; Policy configuration belongs to Settings/Agent/Project/Session layers.

## Data Model & Checkpoint contract

- A resolved Policy is `{enabled, trigger, strategy}`; built-in triggers are `context_ratio{threshold, tokens?}` and `input_tokens{tokens}`. For `context_ratio`, the optional absolute `tokens` cap combines with the ratio and whichever limit is reached first triggers Compaction. Built-in strategies are `summary_tail{tail_tokens, summary_model}` and `continuation`. `CompactionSettings` is the typed runtime view - not a second settings source.
- A `CompactionPlan` is the Strategy/Engine boundary permitting zero or one Model call; the Engine never loops or follows up. The Strategy receives the current effective canonical Context and the corresponding already-built provider request.
- A new checkpoint stores the reference-framed summary in `content`, canonical message `projection`, cumulative compacted-token count (both strategies add only newly compacted messages, never the previous checkpoint notes), before/after context tokens, and Policy/Strategy provenance. The after count builds and estimates the exact projected request under Chat's one Context rule (`chat/usage.md` -> One Context rule), records the factor it used, (refreshed System Prompt, request-only Context, retained Summary+Tail, same-Run Reasoning/Tool restoration, complete Tool definitions) - explicitly approximate in the UI, never derived by subtracting reclaim from a differently scoped estimate. The Projection constructor guarantees it starts with the matching `[compaction-summary]` note. Retained Tail Assistant turns keep their reasoning fields, meta and scope unchanged, so the next Run resends the Tail exactly as the compacting Run sent it after the checkpoint and the Provider prompt cache keeps that prefix; request shaping applies the ordinary replay policy and scope rules to them (`test_next_run_continues_the_compacting_runs_request_byte_for_byte`). The summary is framed as historical reference and ends with an explicit boundary marker; standalone outer System Reminder delimiter lines and checkpoint framing copied by the Model are discarded first, for both strategies, and a response with no text left after that is rejected. The native Tail follows without an extra serialized copy or Tail-guidance note. Its framing describes the state at the cutoff and directs unfinished work to continue from the summary plus later chronological messages without reissuing historical requests. Chat appends an ordinal guidance sentence (`COMPACTION_CHECKPOINT_GUIDANCE`, `_message_history.finalize_checkpoint_guidance`) stating that earlier original messages left active Context and stay stored unchanged; Compaction changes no Tool list (the retired `history` Tool: `tools/history.md`). Latest checkpoint Projection + later messages = effective Context; hidden history never re-reads into later compaction. Every checkpoint carries a Projection; `ChatMessage` validation rejects one without it.
- Every completed checkpoint also ends one Skill activation epoch: Skill names derive only from post-checkpoint carriers, `[skill-context]` carriers drop from the Projection, retained loading Tool Results become instruction-free digests preserving complete cycles, and one `[compaction-skills]` names-only reminder (replacing any previous) says instructions and environment access are inactive with reload guidance.
- Every completed checkpoint also ends a Tool epoch: `[tool-change]` notes drop from the Projection, and the next epoch's Tool pin lists every Tool the Run's primary route offers when the projected request is built, also on a fallback target, so announced Tools become listed and removed ones disappear; of the On-demand Tools, those the current Agent called in the ending epoch and that ran (not refused at dispatch or never started) stay listed and the others, loaded or not, return to the System Prompt's list (`chat/request-building.md` -> Tool catalog per prompt epoch). In the same way `[prompt-block-change]` notes drop, and the next epoch's dynamic block pin holds the Tool and Extension block texts as they render for the projected request (`chat/request-building.md` -> Dynamic prompt blocks per prompt epoch).

The Engine records successful Model-backed work as `usage.model_call = {model, usage}` on the checkpoint, including canonical token counters, the cost snapshot and the stable `usage_call_id` from `core/usage` (`usage.md`). Runtime injects the shared Model registry lookup and Usage recorder; the coordinator passes both full Model references and Run/Extension-group identity so summary-target and active-target accounting cannot be confused. The private `_model_request.py` stream boundary records every exposed Adapter invocation, including partial Usage on failure/cancellation, before checkpoint validation or commit. Rejected summaries, insufficient reclaim and stale results therefore retain their reported consumption independently of checkpoint persistence. Duration and direct before/after Context estimates remain separate checkpoint fields. Zero-call Strategies have no invented Model usage. Coverage: `tests/core/compaction/test_compaction_model_request.py`.

## Strategies

- `SummarizationStrategy` slices the already-built provider request immediately before the Tail boundary and calls the resolved Summary Model once after appending one System Reminder through Chat's canonical note renderer. The Reminder contains only the shared automatic/manual Compaction instruction; the Tail is absent from the request and follows the returned summary natively in the Projection. Older steps move wholly into the summarized prefix; no message is a mandatory Tail anchor, and ordinary retained Tool payloads are not shortened. When Summary and active targets match, the native prefix including Provider Reasoning remains unchanged for cache reuse; a different target strips Provider-owned Reasoning from the prefix because that state cannot cross targets.
- `ContinuationStrategy` requires the completed active provider request, appends one canonical System Reminder asking for checkpoint Context, calls the active Model once with the same Tool definitions, and uses the response directly as Projection - the cache-preserving append-only shape. Automatic Continuation runs only where the same Run will continue: before its first Model request or after a complete Tool batch. Manual Continuation uses its separate no-active-Run prompt. Neither path changes Context between an Assistant Tool Call and its correlated Tool Results.
- `find_tail_boundary` selects a chronological suffix of whole steps. A step starts at a User or Assistant message and includes the notes directly before it (for example delivered Board messages), so an input stays with the response that reacted to it; against a live request the notes join the step only when they render as exactly the request messages before it, otherwise the step starts at its User/Assistant message and the notes are summarized. The configurable `tail_tokens` is the request-side size the Tail should reach: the first whole-step start at or above it wins while the Tail stays within 150% of it; otherwise the largest start down to 70%; without one, the first start past 150% (for example one oversized step). Only a history shorter than the target yields a smaller Tail. Every step start is an equally valid cut: tool calls and their results always stay together, so the provider-visible sequence stays valid wherever the Tail begins. Runtime planning and the automatic new-context check count slices of the already-built request with the active Adapter's wire estimator, including replayed Reasoning and request-only Tool media, corrected by the active Model's input estimate factor (`estimate_factor`, from Chat's Context accounting) like every Context number; so are the new-context and reclaim checks. No second compaction Model call is made to repair the size. Opaque Reasoning remains approximate under the existing shared blob reservation; encoded length is not a measured context cost (`core/compaction/compaction.py`, `tests/core/compaction/test_compaction_tail_selection.py`).

## Policy Resolution

Resolved per compaction decision: Session override -> Agent effective (incl. Project member override) -> global settings. For a temporary Agent the Agent level is the `compaction_policy` of its admitted immutable configuration (for example a Swarm profile's override); without one it inherits global settings (`agent.md`, `test_temporary.py`). Absence inherits dynamically - global changes affect existing Sessions without rewrites; a Policy change triggers nothing itself and never reprocesses hidden history. `compaction.py::effective_compaction_policy()` is the single implementation of this chain, used by Run coordination, `session.list` (`compaction_policy_effective`), `session.set_compaction_policy` (`effective`), the Agent payload (`effective_compaction_policy`, no Session override) and `chat.history`, which returns the Session's normalized effective Policy as `compaction_policy` on current (non-`before`) reads so accessors can relate Current Context Usage to the automatic trigger (`tests/server/rpc/test_chat_methods_history.py`). Every reported effective Policy is normalized and complete.

## Cross-Domain Contracts

- Runtime constructs one registry-backed service shared by both chat loops. Automatic Compaction runs inside the current Agentic Run; manual `/compact` starts a dedicated Session Run so admission prevents concurrent work and accessors subscribe immediately. Both emit the shared started/completed/aborted lifecycle. Manual Runs use the same native admission, completion transaction and History Run-completeness projection as Agentic Runs. Checkpoints retain their Run identity; no checkpoint-specific terminal proof is needed.
- Both paths supply the exact Session address and current prompt-cache affinity to the Engine. After selecting the Strategy's active or Summary target, the Engine obtains request-context kwargs from that target Adapter; never copy another Adapter's wire-specific context or omit it for internal Model calls. The affinity is the Session's and a committed checkpoint keeps it, so the new epoch's unchanged System Prompt and Tool prefix stays on its Provider cache route. On the active target the Model call sends the Agent's `thinking_effort`, exactly as the Run's requests do, because a different reasoning setting renders a different prompt and loses the Run's cache; it sends no sampling parameters, and another target gets the Provider default. A `summary_model` that names the active Provider and Model, without a different Connection, is the active target and reuses the active Adapter (`compaction.py`, `run_coordination.py`, `_request_builder.py::resolve_summary_adapter`; `test_chat_loop_compaction_requests.py`).
- Auto-compaction evaluates before the first Model request (and again before a fallback target's first request), after each complete Tool batch, and for Summary+Tail after a final Assistant response. Continuation skips the final-response check because no work remains in that Run. Every decision uses the actual request target's Context Window and the shared Run-local projection: measured Provider input plus selected-wire request changes while the measurement scope matches, otherwise the target Adapter's complete request estimate. A checkpoint resets that measurement scope; manual Compaction always estimates its rebuilt request; raw records removed by a `history_edit` never re-enter a later checkpoint. Summary+Tail defers an otherwise eligible automatic attempt when this Run's newest unconsumed Tool batch contains a freshly loaded Skill (the next Model step must receive that Result first), re-evaluating after the consuming Assistant boundary. A batch written by an earlier Run never defers: that Run ended before a Model step consumed it, so waiting could keep an oversized Context forever (`test_summary_tail_waits_until_this_runs_loaded_skill_result_is_consumed`, `test_a_failed_runs_loaded_skill_result_never_blocks_the_next_runs_compaction`).
- Chat's `CompactionRunHost` materializes the exact request snapshot and adapters, prepares refreshed prompt-only inputs (full Skill rescan, catalog + seen-Skill set replacement, Working Project rebuild, Config Agent body refresh - while Model target, Connection, Tool policy, Agent identity, working Project identity, and cwd stay Run-stable), closes adapters, builds and counts the projected request (with a fresh Tool pin), commits the checkpoint with its epoch, and rebuilds after stale results. Compaction coordinates the Strategy call, stamps and conditionally persists the checkpoint, and emits lifecycle completion.
- Manual attempts load one complete snapshot and its cursor under the Session write lock. Automatic attempts never reload complete history: they bring the Run snapshot current with a delta read under that lock and compact its active lineage (`test_automatic_compaction_boundaries_never_reload_complete_history`, `test_edit_run_compacts_only_its_edited_lineage`). Both plan and call Models outside the lock, then re-acquire it briefly for `ChatSession.commit_compaction` (`commit_compaction_async`): one write transaction verifies that the cursor is still current (same generation, history floor, next sequence and newest entry id), appends the checkpoint, writes its `PromptEpoch` (the refreshed prompt pins and seen-Skill set), and returns the delta the automatic Run snapshot advances by. Notes that other writers append during an automatic attempt's Model call are not in its summary: before committing, the attempt absorbs them into the Run snapshot under the lock and `carry_notes_into_checkpoint` keeps them verbatim after the checkpoint's Tail, exactly like the Tail messages, so they stay in the live Context. A writer landing while the request projection runs fails that commit and the next attempt absorbs it too, at most `AUTO_COMPACTION_COMMIT_ATTEMPTS` attempts per Model call. Any other appended entry (a message, Tool result, checkpoint, or a Skill-context or Tool-change note of the ending prompt epoch), a cursor discontinuity (edit or takeover), or exhausting the attempts makes the result stale: it writes nothing and aborts without a checkpoint or prompt-epoch change, and automatic attempts rebuild request state. Manual Runs never carry notes and fail with retry guidance on any change. Concurrent notes remain available. A note can also reach the Session without reaching the live request the summary is written from, for example when another writer appends it after the request was built but before the attempt brings its snapshot current. The summary cannot cover such a note, so both strategies keep it verbatim after the summary and before the Tail: Chat's `wire_shaping.notes_missing_from_request` compares each note group with the request messages that replay would put before the next sent message, and a group that does not match is kept whole, so an unverifiable note is duplicated rather than lost (`test_checkpoint_keeps_notes_its_summarized_request_never_showed`). Projected-request failure likewise aborts (`test_final_answer_compaction_meets_a_concurrent_entry`, `test_mid_tool_compaction_meets_a_concurrent_entry_and_rebuilds_the_request`, `test_automatic_compaction_absorbs_notes_landing_during_projection_up_to_a_bound`, `test_checkpoint_carries_only_plain_notes_appended_after_its_snapshot`).
- Automatic checkpoints must reclaim >=4,096 estimated tokens; no per-Run limit - every later safe boundary re-evaluates trigger and usefulness rules. The new-context check runs before any Model call: Summary+Tail needs a non-summary Head; Continuation needs non-checkpoint content added since the latest checkpoint whose estimate reaches that floor (the new summary is assumed no smaller than the one it replaces), so fixed overhead above the trigger never causes a paid Continuation call per boundary (`test_continuation_skips_model_call_without_reclaimable_new_context`). A checkpoint before the first Model request or after a Tool batch is inserted before the next Model step and the Agentic Run continues from it; a Summary+Tail checkpoint after the final Assistant response affects only the next Run, and Stop during that attempt aborts only the Compaction (`chat/run-execution.md` -> Cancellation). Manual `/compact` performs no follow-up Agent Model call.
- Each automatic attempt and each manual Compaction Run is measured as `chat.compaction` on the Session's performance Track with a `trigger` arg (`performance.md`).
- Sessions persists checkpoints plus the optional `compaction_policy` metadata override (each evaluation reads only that value through `metadata_value`); Settings/Agents/Projects validate the same shape as nullable inheritance overrides; server exposes both override and effective values in listings, WebUI edits all scopes.

## Invariants & Gotchas

- Manual `/compact` runs the selected Strategy as the primary active Run and refuses while another Run is active.
- The Chat context-card action requests Compaction inside the exact active Run. It bypasses automatic enablement, token thresholds and the fresh-Skill deferral; the configured Strategy, complete Tool-cycle boundaries, new-context check, minimum reclaim, and cursor validation remain unchanged. A checkpoint right after a Skill load ends that activation like any other, so the Skill-loading Result becomes a digest and the `[compaction-skills]` reminder asks for a reload. Requests coalesce while pending/running; a terminal Run cannot carry a request into its successor. Started/completed/aborted events identify user-requested attempts, including a request that cannot run before completion (`core/compaction/run_coordination.py`, `tests/core/chat/test_chat_loop_compaction.py`).
- Automatic Summary+Tail never re-summarizes only its own previous Summary; it advances within long turns once older cycles move to Head, always governed by threshold/usefulness/reclaim floor.
- If the latest User is before the Tail cutoff, the checkpoint carries its exact canonical JSON in a historical-quote note adjacent to the summary. Angle brackets are escaped at that boundary, preserving decoded content, attribution, and timestamp without allowing quoted reminder delimiters. The summary explains the User's reference and agreed work from the preceding context. Later compactions carry this one quote from the effective checkpoint until a newer User replaces it; a User already in the native Tail needs no duplicate quote. Quote-only history does not count as new compactable work; hidden canonical history is never reopened to reconstruct the quote (`test_user_quote_is_escaped_carried_forward_and_replaced_by_a_newer_user`).
- Model-backed Compaction requires an explicit successful `stop`, summary text that stays non-empty once copied reminder delimiters and checkpoint framing are removed, and no Tool attempts. Truncated, filtered, unsuccessful, unknown, or missing stream finishes abort without a checkpoint; both strategies use this same acceptance boundary (`test_compaction_accepts_only_a_completed_text_summary`). A retryable Provider failure, such as a stream cut short by a dropped connection, gets one in-place retry after the shared `compute_retry_delay` backoff (`_model_request.py`, whose `_sleep` seam tests patch); acceptance failures, non-retryable errors, stalls and cancellation never retry. Each attempt records its own Usage row (`test_compaction_attempts_retain_usage_and_retry_a_transient_failure_once`).
- Compaction streams use the shared 180-second transport and 900-second Model-progress guards, including local routes. Heartbeats reset only the transport clock. A stalled attempt closes its iterator and cannot produce a checkpoint. A failed automatic attempt or post-compaction request projection never defers the next evaluation: retrying is the only path out of an oversized Context, so every eligible boundary (before a request, after each complete Tool batch) evaluates trigger and usefulness again from scratch. Chat can continue with its existing request state meanwhile. Coverage: `test_compaction_stalled_stream_is_bounded_and_closed` and `test_failed_auto_compaction_retries_at_the_next_boundary`.
- Failed automatic Compaction settles its started row as a visible warning and leaves the Agentic Run untouched; stale-context and insufficient-reclaim skips remove their placeholder. An expected failure (a `CompactionError` raised by Compaction itself or wrapping a vBot error such as a Provider or network failure) logs one WARNING without traceback naming run, Session, trigger, Model (`CompactionError.model`, set when a Model call failed) and cause; any other exception logs ERROR with its traceback (`test_failed_compaction_logs_and_keeps_the_request`). Failure warnings are transient Run events, not persisted checkpoints; failed/cancelled manual Compaction terminates its dedicated Run accordingly - neither path appends a checkpoint. A Stop that arrives while the manual checkpoint commits cannot undo the write (the Session database's worker finishes it), so `ChatCompactionHost.commit_checkpoint` waits for the outcome like Chat's visible boundaries: a stored checkpoint emits `compaction_completed` (published after the cancel) and logs `Compaction completed`, and only the Run itself ends cancelled, its terminal payload carrying the stored `checkpoint_id` (as every completed manual Compaction Run's does), so `ChatLoop.compact_session` still replies `Context compacted.`; a commit refused as stale ends it cancelled without a checkpoint (`test_stop_during_the_checkpoint_commit_reports_the_stored_checkpoint`).
- A committed Compaction logs one INFO `Compaction completed` line (`vbot.compaction.coordination`) with run, Agent, Session, `trigger` (`auto` when a configured threshold fired, `manual` for the context-card request and manual Compaction Runs), `reason` (`context_ratio` or `input_tokens`; `requested` for the context card; `command` for a manual Compaction Run), input tokens, `tokens_after`, `carried_notes` (automatic attempts only) and duration. The triggered, skipped, discarded and requested lines and each in-place Model retry log at DEBUG (`test_automatic_compaction_commits_a_checkpoint_and_rebuilds_the_request`, `test_user_compaction_waits_for_tool_result_and_continues_run`).
- Skill activation state changes only on successful checkpoint append - failed/stale/insufficient attempts retain dedup state and environment grants exactly.
- Temporary Agents refresh from their admitted immutable configuration, never the Identity/Team resolver, and rescan Skills without a private Identity scope. Their Working Project Context pins and refreshes like ordinary Sessions, including temporary self-delegation. Applying a committed refresh replaces SOUL and Memory in the active Run as well as the persisted prompt pins (`core/chat/compaction_host.py`, `tests/core/chat/test_chat_loop_compaction_prompt_epoch.py`).
- Prompt-refresh inputs prepare before persistence (stored after-count covers the request actually used). Their pins and seen-Skill set commit in the checkpoint's transaction, so no checkpoint exists without its epoch pins; a failed refresh preparation still commits the checkpoint with the previous pins and seen Skills, except the Tool pin: it always comes from the projected request, because the checkpoint drops the notes the old pin relied on.
- App code knows only projected checkpoints: there is no `tail_boundary_id` field, boundary-based reader, or retired Tail-guidance note. The removed flat Policy shape has no compatibility parser.

Some earlier original messages are no longer directly present in active Context; the Session still stores them unchanged.` (`core/chat/messages.py::COMPACTION_CHECKPOINT_GUIDANCE`, appended once to each new checkpoint's summary note) | Tells the Agent that the summary is lossy and that the originals still exist, so it neither treats the summary as the complete record nor assumes earlier wording is lost.
