# Compaction

Policy-driven Context transformation and checkpoint creation for chat Sessions.

## Overview

`core/compaction/` owns the provider-neutral Engine that evaluates Triggers, asks one Strategy for a Plan, performs zero or one Model call, validates the resulting Projection, and returns one self-contained `compaction_checkpoint`. It never rewrites or deletes prior Session JSONL records. The chat loop owns safe execution points and runtime resolution; settings, Agent, Project, and Session layers own persisted Policy configuration.

Core cross-cutting terms (Session, Agent, Model, Tool) live in `.vorch/GLOSSARY.md`.

## Data Model

- A resolved Compaction Policy is `{enabled, trigger, strategy}`. Built-in Triggers are `{type: "context_ratio", threshold}` and `{type: "input_tokens", tokens}`. Built-in Strategies are `{type: "summary_tail", tail_tokens, summary_model}` and `{type: "continuation"}`.
- `CompactionSettings` is the typed runtime view of one resolved Policy. It is not the persisted schema and must not become a second settings source.
- `CompactionPlan` is the Strategy/Engine boundary: optional Model messages and target (`active` or `summary`), ordered messages before/after the returned text, optional zero-call text, and cumulative compacted-token count. The Strategy receives the current effective canonical Context and the corresponding already-built provider request; a previous Summary, when present, is an ordinary leading message in both rather than a separate input. A Plan permits zero or one Model call; the Engine never loops or performs follow-up calls.
- A new `compaction_checkpoint` stores its plain summary in `content`, a canonical message `projection`, cumulative `usage.compacted_token_count`, the triggering request's `usage.context_tokens_before` / projected `usage.context_tokens_after`, and Policy/Strategy provenance. The before count is Chat's canonical current Context projection: measured Provider input plus its output and only any newer estimated request messages, or a complete request estimate when no measured anchor exists. Because no Provider measurement exists for the unsent post-Compaction request, Chat obtains the after count by building the exact projected request before checkpoint persistence and structurally estimating its refreshed System Prompt, request-only Context, retained Summary+Tail, applicable same-Run Reasoning/Tool Result restoration, and complete effective Tool-definition array. It remains explicitly approximate in the UI, but it is never derived by subtracting a canonical-history reclaim from a differently scoped before estimate. The constructor guarantees the Projection starts with the matching `[compaction-summary]` note and removes Assistant `reasoning`, `reasoning_meta`, and internal `reasoning_scope`: vBot Compaction is textual Summary+Tail state, not a Provider-native opaque reasoning token. Assistant `phase` remains semantic history. Summary+Tail inserts a separate model-facing reminder immediately before the retained Tail that identifies those following messages as the most recent verbatim Session activity and places them chronologically after the Summary; a later Summary+Tail pass ignores the reminder as new Head content for automatic Strategy usefulness and cumulative Head-token accounting while normal Context-size estimates still include it. Before persistence, Chat adds an ordinal model-facing reminder that the Session-scoped `history` Tool can retrieve hidden canonical messages and original Tool payloads replaced by deterministic Tail digests. The latest checkpoint's Projection plus messages appended after that checkpoint is the effective Context; hidden pre-checkpoint JSONL history is never re-read into later compaction. Existing boundary-based checkpoints remain valid read-only input: their stored summary plus the surviving slice from `tail_boundary_id` is materialized in memory as the effective Projection, then any later compaction writes only the new format.

## Interfaces

`CompactionService.compact` keeps Provider `adapter.send` on the Event Loop but runs synchronous Strategy planning, prompt-fragment reads, canonical/model-message projection, Provider response normalization, projection validation, and token/reclaim estimation through a dedicated four-worker Compaction pool. The boundary preserves the single-Model-call contract and keeps cancellation/order behavior at the async orchestration layer.

- `CompactionService.should_auto_compact(...)` selects the configured Trigger from the registry and evaluates it against current input tokens and the resolved Context window.
- `CompactionService.has_new_compactable_context(...)` preflights automatic Strategy usefulness. Summary+Tail returns true when the selected Head contains canonical content beyond the previous Summary and separately pinned active User, or when deterministic compaction of already-consumed Tool payloads alone reclaims at least the automatic 4,096-token floor; manual Compaction bypasses this preflight.
- `CompactionStrategy.plan(context, settings) -> CompactionPlan` is the extension seam for programmed Strategies. A Strategy receives the current effective canonical messages, an optional exact provider-request snapshot, previous cumulative count, manual instruction, and prompt-fragment storage; it performs no Model I/O itself.
- `CompactionService.compact(...) -> ChatMessage` selects the Strategy, executes at most one planned Model request, assembles the Projection, validates complete Tool cycles, optionally enforces a caller-provided minimum estimated reclaim, and returns an unstamped checkpoint. Chat alone owns the complete Provider-request rebuild and stamps both Context token counts before persistence.
- `SummarizationStrategy` selects a token-budgeted, provider-safe working Tail, slices the already-built provider request immediately before the canonical Tail boundary, appends one Compaction instruction, and calls the resolved Summary Model once. The request prefix is not rendered, digested, or otherwise rewritten: it includes the System Prompt, any previous Summary message, User/Assistant messages, Tool Calls, Tool Results, and request-only Context exactly as the active request contained them. The returned text becomes the new Summary; the Projection then retains the latest active User exactly once plus the selected chronological Assistant/Tool trajectory, with only Provider-owned Reasoning removal and pressure-triggered deterministic compaction of consumed Tool payloads.
- `ContinuationStrategy` requires the exact active provider request, appends one internal `<system-reminder>` asking for checkpoint Context, calls the active Model once with the same Tool definitions, and uses the one text response directly as the Projection. This append-only request shape is the cache-preserving strategy; any provider cache hit still depends on the provider's exact-prefix rules.
- `find_tail_boundary(messages, tail_tokens)` returns the canonical Summary-prefix boundary chosen by the working-Tail planner. The planner walks backward across provider-visible User or Assistant boundaries, treats `tail_tokens` as a target, admits ordinary complete groups only through a 115% soft ceiling, and continues before the active User when post-User work does not fill the target. The active User may therefore be pinned separately ahead of a newer suffix. Assistant Tool Call carriers and all matching Tool Results are atomic, so a boundary never starts inside or ends before completion of a Tool cycle.

## Policy Resolution

The chat loop resolves a Policy at every compaction decision, in this order: Session metadata override → Agent effective Policy (including a Project member override) → global settings. Absence means inheritance, so later global or Agent changes affect existing Sessions immediately without rewriting metadata. A Policy change never triggers compaction by itself and never reprocesses hidden history; the next normal or manual compaction consumes the existing checkpoint Projection under the newly resolved Policy.

## Cross-Domain Contracts

- `core/runtime/` constructs one registry-backed `CompactionService` shared by the canonical ChatLoops.
- `core/chat/` executes every Compaction on a Run timeline. Automatic Compaction uses its current Agentic Run; manual `/compact` starts a dedicated Session Run before request preparation, so Run admission prevents concurrent Session work and accessors can subscribe immediately. Both paths emit the shared `compaction_started` → `compaction_completed` / `compaction_aborted` lifecycle and the same completed payload after checkpoint persistence. Chat evaluates auto-compaction only at safe completed Model boundaries against the same current Context projection exposed through Run events, History, and the WebUI: measured Provider input plus output and only newer estimated Tool messages, with a complete request estimate solely as the fallback when no measured input exists. It resolves effective Policy and adapters, supplies the exact request snapshot actually sent plus any completed Assistant/Tool continuation to both built-in Strategies, finalizes History guidance, prepares refreshed prompt-only inputs, builds and counts the complete projected Provider request plus effective Tool set, stamps the checkpoint, persists it, commits the prepared prompt epoch, and emits completion. Automatic Compaction captures its complete append cursor under the Session write lock, performs all planning and Model I/O after releasing that lock, then briefly re-acquires it to append the checkpoint only when no message has appeared since the snapshot. A stale automatic result emits `compaction_aborted`, persists no checkpoint, and rebuilds current same-Run request state so the concurrent note remains available at the next Model boundary. A projected-request failure likewise aborts without a checkpoint. The prompt refresh rescans every Skill source, replaces the prompt-epoch Skill catalog and `seen_skills`, rebuilds the Working Project input from the admitted cwd plus the Project's current display name/auto-load list, refreshes a Config Agent's prompt body without replacing the admitted runtime Agent, and reruns normal System Prompt assembly; Model target, Connection, Tool policy, Agent identity, working Project identity, and cwd remain Run-stable. Automatic checkpoints must reclaim at least 4,096 estimated tokens; there is no per-Run Compaction limit, so every later safe boundary evaluates the normal Trigger and Strategy usefulness rules again. A checkpoint after a Tool batch can therefore affect the next Model request in the same Run and counts restored request-local Provider state; a checkpoint after the final Assistant response affects the next Run and counts only its durable provider-neutral Projection.
- `core/sessions/` persists checkpoints and the optional Session Policy override under metadata key `compaction_policy`.
- `core/settings/`, `core/agents/`, and `core/projects/` validate the same complete Policy shape. Agent and Project-member values are nullable inheritance overrides.
- `server/` exposes Session override mutation and returns both `compaction_policy_override` and `compaction_policy_effective` in Session listings. The WebUI edits the same Policy shape globally and at Agent, Project-member, and Session scopes.

## Invariants & Gotchas

- Automatic compaction is enabled/disabled by Policy. Manual `/compact` still executes the selected Strategy, but does so as the Session's primary active Run and therefore refuses while another Run is active.
- Automatic Summary+Tail never re-summarizes only its previous Summary. It can advance within one long User turn once an older completed Assistant or Assistant/Tool cycle moves into the Head; threshold evaluation, Strategy usefulness, and the reclaim floor govern every attempt without a per-Run count or cap.
- The latest User message is the active request anchor: it is retained with the same canonical id and content across every later Summary+Tail checkpoint until a newer User message supersedes it. If the chosen chronological suffix starts later, the anchor is inserted immediately before that suffix; if recent work is short, selection crosses the anchor and fills backward from earlier work. Checkpoints created before this invariant that already hid their User message are not rehydrated from hidden history.
- A Strategy cannot split or orphan an Assistant Tool-call cycle in its retained Projection. Summary+Tail boundaries begin only on provider-visible User or Assistant messages whose complete suffix validates, and the append-only Session JSONL remains untouched.
- Summary+Tail keeps selected messages exact first. A completed Tool batch is considered consumed only after a later Assistant step; if admitting that batch verbatim would exceed the 115% soft ceiling, its structured arguments and Results may be replaced in the checkpoint Projection by bounded deterministic previews carrying the original Result message id. The Summary Model still receives the exact active request prefix, the append-only Session retains the original payload for `history`, and the newest complete Tool batch with no later Assistant remains exact even when it alone exceeds the soft ceiling. Other indivisible newest working groups and an oversized active User anchor are the same explicit exceptional-oversize case.
- With no configured `summary_model`, Summary+Tail resolves to the active adapter and Model and preserves the prior request as an exact prefix before appending its instruction, enabling provider prefix-cache reuse. A configured Summary Model intentionally starts a fresh cache and receives the same message/Tool structure, but Assistant `reasoning`, `reasoning_meta`, and `reasoning_scope` are stripped because Provider-owned reasoning state cannot cross a Model target.
- Continuation runs only when the chat loop can provide a completed active request snapshot. At a mid-tool safe point it waits until the final assistant boundary rather than synthesizing a different prefix.
- Compaction is a hard boundary for cross-Run Provider reasoning. A mid-Run rebuild may restore the live Tail's opaque state by message id, but that restoration is request-local and is not written back into the checkpoint Projection. Existing checkpoints containing legacy Tool-ageing digests remain readable, and request-only rich Tool Result media is deliberately not restored onto such a digest.
- The previous Summary has no parallel lifecycle: the latest checkpoint Projection exposes it as one ordinary Context message, so a later compaction sees that message exactly once in its request Head and replaces it together with the rest of the Head.
- Failed automatic compaction logs, emits `compaction_aborted` to settle its preceding `compaction_started` activity row, and leaves the active Agentic Run untouched. A failed or cancelled manual Compaction emits `compaction_aborted` and then terminates its dedicated Run as failed or cancelled, so every accessor removes the same in-progress row without a local pending-state workaround. Neither failure path appends a checkpoint or activates `history`.
- A concurrent out-of-band Session append makes an in-flight automatic result stale rather than blocking the writer or allowing the later checkpoint to hide that new message. Staleness is a normal aborted attempt: final-answer Compaction leaves the note for the next Run, while mid-Run Compaction rebuilds the uncompacted request from current persisted history before continuing.
- Prompt-refresh inputs are prepared before checkpoint persistence so the stored after count covers the request Chat will actually use; Session prompt metadata is committed only after the stamped checkpoint persists. Preparation failure logs and projects the previous prompt snapshots instead. Metadata-commit failure logs without invalidating the checkpoint or an already prepared same-Run request.
- Summary Model resolution and fallback remain chat-loop responsibilities because only that layer knows the active Provider/Connection. Both Summary+Tail and Continuation receive the active Tool definitions; Continuation always targets the active Model/Connection.
- Do not write new `tail_boundary_id` checkpoints or rewrite old ones. The old checkpoint reader exists solely to preserve already persisted Session history under the explicit cumulative-compaction contract. The removed flat `{auto, threshold, tail_tokens, summary_model}` Policy has no compatibility parser.
