# Storage

Data-directory bootstrap, temporary-file lifecycle, atomic settings and credential persistence, and raw prompt-fragment file access.

## Overview

`core/storage/` owns the process-local filesystem services and the canonical placement contract for the runtime data root. It resolves the data directory (an explicit value, else the `Config` chain: `VBOT_DATA_DIR` -> a `.vbot-worktree` marker in the current directory -> the checkout's own marker -> `~/.vbot`; a marker with `cwd_only` applies only from the current directory, letting a development checkout carry a dev data dir without redirecting installed CLIs; `core/utils/config.py`), initializes the complete canonical structure, manages categorized temporary files, and reads/writes `settings.json`, the data-directory credentials (through its Secret Store, `secrets.md`), prompt fragments, and System Prompt block persistence. Storage owns placement but not schemas (`core/settings/`), prompt assembly rules (`core/prompts/`), or domain records stored in those directories; generated images are caller-owned Workspace/Project files outside the layout.

## Canonical layout

`DataDirectoryLayout` is the immutable path contract: `artifacts/{attachments,speech,models,debug,performance,temp/{atomic,commands,scratch,subagents,terminals,web_fetch}}`, `statistics/` (the Statistics-owned disposable SQLite), `recall/` (owned by Recall: only its disposable Passage index `passage_index.sqlite` with SQLite sidecars; Runtime start deletes every other file there, `recall.md` -> Lifecycle & Removal), and independent roots `agents`, `archive` (archive entry payloads, owned by `archive.md`), `bootstrap`, `calendar`, `channels`, `cron`, `extensions`, `logs`, `processes`, `projects`, `prompts`, `skills`, `terminals`. Canonical databases belong to their owning domains, as do the global Skill home's history `<data-dir>/skill-history.jsonl` and archive `<data-dir>/skill-archive/` (Skills, created on first need, `skills.md`); the kernel's files and roots (`database.md` -> Data Model; the marker path is `DataDirectoryLayout.data_store_marker_path`) belong to the database kernel, which creates them on demand.

Initialization creates the full set non-destructively - empty settings only when missing, and no credential file (the Secret Store's first write creates `secrets.json`, `secrets.md`); creation failures in the canonical directory are fatal. A new root is published atomically together with its bootstrap marker, and an existing directory without a marker is never adopted; `initialize_data_directory(require_new=True)` refuses any existing root (`storage/initialization.md`).

Directory creation does not transfer ownership: Agents own their trees, Channels theirs, Cron/Bootstrap their job stores, Attachments/Speech their artifacts, Performance its Recordings and History Windows (`performance.md`), Live voice its call records (`model_tasks/live-operator.md`), Models the Model DB, Statistics its read model, Terminal Manager launch history, the logging pipeline its daily log files and their retention (`logging.md`), local speech and local embeddings their engine roots `speech-engines/` and `embedding-engines/` (durable installation data, created only by explicit setup; `model_tasks/speech.md`, `model_tasks/embeddings.md`). Layout changes belong in `layout.py`; format/retention changes stay with owning domains. Caches outside the data directory, such as the PowerShell host cache, are their owners' (`tools/shell.md`).

Current code reads only the canonical paths; there is no dual-read of an older layout, and an existing data directory without `data-store.json` is refused (`database.md` -> Evolution contract, item 6). A data directory converted from vBot 0.4.4 or earlier can still hold `pre-generation-1/`: the old files the conversion replaced, old credential copies included; vBot never reads it.

Runtime creates `<data-dir>/extension-data/<owner>/` for a loaded Extension's persistent host state. It is separate from `extensions/`, which contains executable overrides, and is not temporary-file cleanup data. Databases an Extension opens through `host.open_database` live there as canonical kernel databases `<name>.db` (`database.md`, `extensions/databases.md`). The Extension owns its format; canonical temporary Session bindings, delivery receipts and Run ownership remain in `sessions.db` (`extensions/host.md`, `sessions.md`).

## Temporary files

Conversation Scratch Areas (`artifacts/temp/scratch/`) and their bookkeeping (`artifacts/temp/scratch-state/`) belong to the Tools owner and are not `TemporaryFileManager` categories (`tools/scratch.md`).

`TemporaryFileManager` owns only retained categories under `artifacts/temp/`: `commands` (shell command logs, owned by `CommandManager`, `tools/shell.md`), `computer_use`, `subagents`, `terminals`, `web_fetch`. Web Fetch snapshots and Computer Use screenshots retain for 72 hours; Computer Use writes its files directly, without leases, so retention runs from each file's modification time (`extensions/computer-use.md`); their Session/Agent ownership and saved-view format belong to the Tools owner. Leases protect active files; idempotent completion starts retention (72 h commands/terminals, 24 h subagents); cleanup runs at start and every 60 s, off the Event Loop, removing only expired inactive regular files (filenames and sweep: `storage/temporary-files.md`). The `atomic` child is short-lived staging removed by producers, not a retention category; `browser/` holds the web_fetch browser's throwaway profile, which its owner removes when the browser stops and at its next start (`tools/web_fetch.md` -> Local browser). This lifecycle is internal - Extensions get no temporary-file API.

## Settings & credentials

- `<data_dir>/settings.json`: raw I/O, validation-gated loading, normalized persistence helpers and locked transactions remain in `StorageManager`. Internal `_settings_updates.py` applies pure merges to the transaction-owned mapping; schemas and the shared Subagent defaults stay in `core/settings/`. `load_settings` serves an unchanged file version from memory: the stat stamp `(mtime_ns, size, inode)` is taken before reading, a file modified within the last 3 s is always re-read (writes inside one timestamp tick), `save_settings` invalidates, and every call returns an independent parsed copy. A file that exists but cannot be read (another program holding it, an unresponsive share) is no file version: the last loaded Settings stay in use (defaults before the first load), nothing is cached, and the next call reads again; invalid content still degrades to defaults. `save_settings` writes through `write_json_document`: unknown keys survive, and a file that fails to load is never overwritten (`json-documents.md`). External edits therefore stay live without restarting.
- `patch_settings` owns the strict raw snapshot, known-field candidate and optional runtime validation within the existing Settings lock. The path owner uses that snapshot only to preserve unknown fields when deciding whether an emptied ancestor can be pruned; runtime validation still runs on known Settings before the single write. Section updates continue through `update_settings_sections`.
- Data-directory credentials live in the `credentials` section of the Secret Store, `StorageManager.secrets` (`secrets.md`), the one store instance per data directory and process; `TokenStore` shares it. `load_data_dir_credentials()` (also `load_environment()`) returns every entry that decrypts, an empty snapshot while the store is unavailable; process environment keeps higher precedence when callers merge. On Windows the snapshot holds one spelling per credential (`fold_credential_names`, `secrets.md` -> Interfaces).
- `set_data_dir_credential` validates shell-style keys and rejects empty or multiline values before one store write and returns whether the stored value changed; on Windows that write also removes every other case spelling of the name. `remove_data_dir_credential` removes every spelling, reports whether one existed, and never creates a store. Both raise `StorageError` (`SecretStoreError`) without writing while the store is unavailable or the write fails, so other credentials are never dropped (`test_storage_credentials.py`). Removal touches only the store, so process-env credentials can outlive removal. Values never copy into `os.environ` and never log.
- Storage never reads `<data_dir>/.env`: a plaintext credential file is converted once and otherwise ignored with a warning (`secrets/plaintext-conversion.md`).

## Prompt files

Storage reads prompt fragments (bundled `resources/prompts/`, overridden per name by a hand-created data-dir copy) and persists System Prompt block layouts and overrides per scope; the prompts domain composes them (`prompts.md`). `PromptBlockStore` is the single block id-to-path writer and raises on unsafe ids rather than sanitizing; fragment names must be in `PROMPT_FRAGMENT_NAMES` and Agent ids valid before any path is built, so traversal and absolute fragment paths are invalid storage data, never sanitized inputs (`storage/prompt-files.md`).

## Conventions

- Settings writes are UTF-8 sorted indented JSON with trailing newline. Atomic writes go through shared helpers staging under `artifacts/temp/atomic/` with fsync + `os.replace` (+ POSIX directory fsync). On Windows, a replace that fails with a sharing-type error (WinError 5, 32, 33: an antivirus scanner or indexer briefly holding the target or temp file open) is retried within a fixed ~0.4 s budget before the original error surfaces; a read-only or directory target is never retried, and the waits go through the module-local `_sleep` seam (`core/utils/atomic.py`, `test_atomic.py`). For a file that must never replace another, `write_new_bytes` creates the target exclusively (`FileExistsError`, existing entry untouched) and writes it in place with the same fsyncs, removing its own file on failure; the caller publishes it through a later step, as the attachment and task-artifact sidecars do (`attachments.md`, `model_tasks.md`).
- `core.utils.atomic.preserve_windows_file_metadata` serves file edit Tools that stage beside an existing user file (`tools/apply_patch.md`); ordinary Settings writes keep their existing policy.
- Runtime Settings/credential read-modify-write serializes per-process only - not cross-process locks. The installer is a separate boundary: its explicit-port update of an existing `settings.json` uses a cross-process sidecar lock plus same-directory atomic replace so parallel setup processes cannot lose unrelated changes or expose partial JSON.
- New code routing: section validation/normalization -> settings domain; fragment/block file access -> the two stores; categorized temp leases -> `TemporaryFileManager`; atomic staging -> `core/utils/atomic.py`. `StorageManager` composes and orchestrates - no new normalization or path logic there.

## Constraints & Gotchas

- Durable artifacts (attachments/speech/models/debug/performance) are not temporary-file cleanup candidates; caller-owned generated images sit outside both.
- User-editable JSON validates before runtime consumption: Storage gates settings.json while other domains use validated loaders from the same module.
