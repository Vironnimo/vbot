# Legacy archive adoption

Task-gated detail for `archive.md`: how archives written before archive entries existed become entries. Read it when changing the migration `sessions.0001_archive_entries`, the startup adoption of archived Sessions without an entry, or when reasoning about `backfill` entries.

## Adoption

The Session spec's named migration `sessions.0001_archive_entries` (`core/sessions/_store_schema.py`, applying `_store_archive_backfill.py::adopt_legacy_archives`; not `breaks_older`) turns archives written before entries existed into `backfill` entries. Legacy containers under `archive/agents/<id>/`, `archive/projects/<id>/` and flat `archive/<name>/` with an `agent/` child become `agent`/`project` entries (a moved Workspace beside the Agent becomes a `workspace` tree; other content of the container becomes a separate `files` entry for the container, because a restore of the Agent leaves it behind); any other directory under `archive/` except `entries/` becomes a `files` entry. Trees are adopted oldest modification time first; each claims archived Sessions of its id that no entry holds yet (an Agent tree: its global Sessions; a Project tree: every Agent's Sessions in the Project) and records `backfill.match` (`timestamp` or `none`). An Agent tree claims those archived at the one instant closest to its modification time within `[mtime - 2 s, mtime + 10 min]`: the old Agent delete created the container and moved the trees into it right before it archived the Sessions, so the container's time is the archive time. A Project tree claims the latest instant at or after `mtime - 2 s`, with no upper bound: the old Project removal only renamed the directory, which keeps the directory's own modification time (verified on NTFS), so the time is the Project's last edit, a lower bound of the archive time. Remaining archived Sessions are batched by scope (or owner group) and archive instant into `session`/`owner_group` entries. Adopted payloads without a valid `format_version` record `payload_format: "older"`: listed and purgeable, never restorable, because app code reads only the current format. Trees that may be folders the user owns rather than copies vBot made - every `files` tree and a moved Workspace whose folder lay outside the data directory - are named in the entry's `user_folders` fact, which the retention purge reads (`archive.md`). A directory that cannot be read is skipped with a WARNING and stays outside any entry; the migration never fails because of it, and since it runs once, a later start does not adopt it. Every step skips what an entry already records, so the adoption is idempotent. A fresh `sessions.db` records the migration without running it: a new data directory has no legacy archives.

## Startup adoption

Startup recovery (`archive.md` -> Recovery) runs only the Session half, `adopt_unrecorded_archived_rows`: archived Sessions an older vBot wrote after a downgrade get `session`/`owner_group` entries with the same batching. It never adopts legacy trees; those exist only from before the migration ran.

Tests: `tests/core/sessions/test_archive_backfill.py`.
