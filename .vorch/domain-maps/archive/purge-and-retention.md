# Archive purge and retention

Task-gated detail for `archive.md`: permanent deletes, the purge operation, its outcomes and order, and the retention setting, due computation and sweep, which also expires Ephemeral Sessions. Source: `core/archive/_purge.py`, `_retention.py`, `server/rpc/archive_methods.py` (`purge_permanently`). Tests: `tests/core/archive/test_archive_service.py`, `test_archive_retention.py` (the sweep, with the timer `_retention._wait` replaced and a fixed clock), `tests/core/utils/test_tree_move.py`, `tests/server/rpc/test_archive_methods.py` (permanent deletes), `tests/core/sessions/test_store_query_plans.py` (the `archive_entries_due` index).

## Permanent delete

A delete with `permanent: true` archives the same way, then purges exactly the entry it created (`purge([entry_id], reason="permanent")`, `server/rpc/archive_methods.py::purge_permanently`), after the archive released the reference lock. One transactional path therefore removes the Agent, Project or Session; there is no separate erase path. The archive has succeeded by then, so the purge never fails the delete: the result always names the entry (`archive_entry_id`) and says whether it was purged. When that purge does not finish, the entry stays `purging`, the delete result reports `purge_pending` with its reason, and the retention sweep continues it. When another operation took the entry first, `purge_reason` is `busy` (held, for example by a restore; nothing deleted) or `gone` (no longer in the archive); a failed usage import (`usage_import_failed`) or claim leaves it `archived`, still restorable, and names the reason. A restore of the new entry between the archive and the purge makes the purge skip it (`busy`) or find it gone.

## Purge outcomes

`purge(entry_ids, all_matching=, reason=, actor=)` returns `PurgeOutcome(purged, pending, skipped, gone, kept)`. An unknown id refuses the whole call with `ArchiveEntryNotFoundError` and a non-`archived`/`purging` entry with `ArchiveEntryBusyError` (with the same `reason` and `details` as the restore check, `_restore.busy_error`), before anything is deleted. `all_matching` skips entries in other states and keeps every `archived` entry that may hold the user's folders (`_retention.may_hold_user_folders`: kind `files`, or a `user_folders` fact), reported in `kept` (`KeptEntry`, reason `files` or `user_folders`); only naming such an entry deletes it. A `purging` one is continued. A pending entry (`PendingPurge.reason`: `usage_import_failed` for an entry already `purging`, `stopped` or the failure's exception class) began its deletion and stays `purging`, and the call wakes the retention sweep. An entry another operation took between that check and the claim is `skipped` (`SkippedPurge`, reason `busy` with the state it holds; nothing deleted, never retried) or `gone` (its id: another operation deleted or restored it, which callers count as done); a failed usage import (`usage_import_failed`) or a claim that failed otherwise skips an `archived` entry unchanged with that reason.

## Purge order

- `purge_entries` (`_purge.py`): bring the usage ledger up to date (a failed import, or a missing usage ledger, changes nothing: an `archived` entry is skipped `usage_import_failed` and stays restorable, one already `purging` is pending `usage_import_failed`); claim every entry (`begin_purge`; an entry another operation took meanwhile is skipped `busy` or `gone`, logged at DEBUG); then per entry finish an `agent` entry's cleanup that did not complete (`cleanup_pending`: `cleanup_agent`, which with a live Agent of the same id only clears the flag; while it fails, the entry is pending with the failure and nothing of it is deleted), delete the members newest key first, one `delete_session` transaction each, so a fork inside the entry, such as a `session` entry's review fork, goes before its source and descendants elsewhere, archived ones included, receive materialized copies (`sessions/lineage.md` -> Delete); remove the recorded trees; for an `agent` entry whose id no live Agent and no other entry holds, drop the Agent Secret grants that waited for its restore (`release_agent_secrets`); `finish_purge` deletes the row (and an `owner_group` title once no Session of the group remains).
- Tree removal: after `remove_tree(path, within=archive/)` deleted a recorded tree, the purge removes empty parents up to, not including, `archive/`; a tree that is already gone counts as removed. Trees named in `user_folders` are deleted like any other.
- The service's stop event is checked before each Session and before each file or folder a tree removal deletes (`remove_tree(..., stop=)`); a stopped entry is pending `stopped`. A failed entry stays `purging` and is reported pending; the retention sweep or a later purge continues it.
- Usage totals stay; previously referenced attachment blobs become eligible for quiescent lifecycle collection only after all live, archived, fork and retained-snapshot references disappear (`attachments.md`).
- Logging: the owner line `Archive entry purged` carries `reason` (`manual`, `permanent`, `retention` or `resumed`) and `actor` (`rpc` or `retention`). A purge failure is WARNING once per entry and failure kind, a failing usage import once per data directory, each with an INFO once it no longer fails (`LoggedConditions`).

## Retention setting

- Setting `archive.retention_days` (`settings/sections.md`): integer 1-3650 or `null`, default 30, applies live. The Runtime's `ArchiveServices.retention_days` reads `StorageManager.load_archive_settings(strict=True)` on every call, and `Runtime.apply_settings_change` calls `retention_changed()` when the raw `archive` section changed. `ArchiveServices.clock` (UTC now) is the time due entries are compared with; tests replace both.
- Unknown period: that strict read, unlike every other Settings read, never falls back to the default when `settings.json` is degraded (invalid JSON, another `format_version`, an invalid `archive` section), because a default period could delete entries the user meant to keep longer; it raises `StorageError`, and `retention_days` raises `ArchiveRetentionUnknownError`. A sweep then still continues `purging` entries but purges nothing for retention, logging one WARNING (`Archive retention period cannot be read; ...`) and one INFO once it reads again (`LoggedConditions`); an entry whose period became unreadable after its page was read is left alone. `list` reports `retention_unknown` and no `purge_at`.

## Due entries

`purge_at` (`_retention.purge_at`) is `retention_start` plus the period, computed on read, so a changed period applies to existing entries at once and a lowered one makes older entries due at the next sweep. It is `None` with a `null` period, for entries not `archived`, for `recovered` entries (only a purge deletes them), for `files`-kind entries and for entries whose facts name `user_folders` (folders the user may own, not copies vBot made; `may_hold_user_folders` on the listing): only a purge that names them deletes those, never retention or a purge of every matching entry, and `show` names such folders. A `backfill` entry's clock starts at its adoption.

## Sweep

- `_retention.py::RetentionSweeper`, inside the service: the Runtime starts it after startup through `_start_archive_retention`, never in a safe startup mode and never outside a serving Event Loop. The first sweep runs 60 s after start, then hourly (`FIRST_SWEEP_DELAY_SECONDS`, `SWEEP_INTERVAL_SECONDS`); `retention_changed()` and a manual purge that left an entry pending wake it at once. A sweep first continues `purging` entries (also with a `null` period), then walks `ledger.due` oldest retention start first (index `archive_entries_due`, pages of 100 behind an `after` entry). Each entry is one `archive` worker call that re-reads it and purges only when it is still `purging` (reason `resumed`) or still due under the current period and clock (reason `retention`), actor `retention`. Manual purges and permanent deletes therefore interleave between entries, and a restore or a raised period in between wins. Nothing runs on the Event Loop.
- Ephemeral Session expiry: each sweep first calls `ArchiveService.expire_ephemeral_sessions()`, whatever the retention period. It reads up to 100 live Ephemeral Sessions idle longer than `EPHEMERAL_SESSION_LIFETIME` (`sessions/lists-and-metadata.md` -> Ephemeral Sessions) and deletes each like a permanent Session delete: `archive_session(actor="ephemeral", ephemeral_expiry=True)` under the automation reference lock, then `purge([entry_id], reason="ephemeral", actor="ephemeral")`, so terminals, Scratch Areas, Recall entries and review forks go the same way. The archive transaction records the `ephemeral_expiry` fact before follow-up cleanup or the purge can be interrupted. `ledger.pending_purges` supplies those still `archived` entries alongside `purging` entries; each later sweep retries them independently of the retention period, including `null` or unreadable settings. Retry targets are read before new expiries, so a skipped purge is attempted at most once per sweep. A Session with an active or queued Run, one a live automation pins, or one already gone stays for a later sweep (DEBUG); an unexpected failure of the archive or the purge is a WARNING for that Session only. A skipped purge keeps the entry `archived` and its expiry fact for the next sweep. The sweep logs `Deleted <n> expired Ephemeral Sessions` at INFO when it deleted any.
- Stop: `stop()`/`aclose()` (shutdown step `archive_retention`, after `bootstrap`) set the service's stop event, which every purge checks before each Session and each file or folder of a payload tree, manual ones included. The entry stays `purging` and the next start's sweep continues it, so shutdown never waits for a large entry; `aclose()` waits only for the worker call in progress.
- Logging: one owner line per purged entry and no summary of retention purges; sweep start and pass at DEBUG; a `null` period logs nothing more. An unexpected sweep failure is ERROR with traceback once per data directory, INFO when sweeps work again; the next sweep retries.
