# WebUI Chat

Read this reference only for WebUI Chat selection, Session, history, Run, Queue, timeline, composer, attachment, command, or speech-input work. Backend Chat contracts live in `chat.md` and its task-gated references. As everywhere: these are working notes - the components and their tests remain the truth for rendered behavior.

## Ownership and addressing

Chat admission responses preserve early events from the accepted edited Run and cannot replace a successor already observed live. A queued send or Queue edit response triggers a fresh authoritative Queue read: its item may already have been consumed or edited again, even after the matching live events or a newer snapshot were reconciled. An edit acknowledgement never writes its submitted text over the current projection. Authoritative reconnect Queue snapshots invalidate older pending Queue reads. `chat.timeline` checks active-Run identity around its durable read and freezes the live descriptor before asynchronous projection, preventing an earlier page from being paired with a later idle state. Regression coverage lives in `chatState.send-and-queue.test.js` and `tests/server/rpc/test_chat_methods_history.py`.

`ChatView.svelte` composes presentation and applies navigation consequences; `createChatController()` in `chatState.js` owns the reactive client projection plus roster/history/activity/command loading, send and Queue workflows, cancellation, and durable-state reconciliation. Presentation components consume projections and forward intents - they never sequence Chat RPCs or rebuild Run state independently. Private View implementations under `components/chat/view/` retain target/Project selection and eligibility for a new Session in the shown Project (`target.svelte.js`), Session navigation and parent provenance (`navigation.svelte.js`), action-result presentation (`actions.svelte.js`), layout/focus/loading feedback (`layout.svelte.js`), and the composer footer's Session settings (`sessionSettings.svelte.js`); the View still constructs the existing Chat controller and forwards server events. Supporting owners: `chatRunStream.js` (one active semantic Run stream and reconnect), `chatTimeline.js` (renderable timeline items), `ChatActivityPanel.svelte` (presentation-only Session-info panel over timeline/Sub-Agent/background-command projections and the displayed Session's row, Sub-Agent tree, usage and changes; opened and closed from the Chat header's toggle, which `ChatView.svelte` wires to it (`ChatHeader.svelte` `infoPanel*` props), it lies inside the chat surface at its right side, left of the timeline's scrollbar, which stays at the window edge (user decision 2026-10-18); where the surface (container `chat-surface`) is at least 740px wide, the timeline content and the composer keep its width free through `--chat-activity-reserve` (chatView.css) and center in the rest, otherwise it overlays the Chat). For a displayed derived Session, `ChatView.svelte` resolves the immediate Parent Session from `subagent_parent` first or `fork_source` otherwise, loads its exact list row through the required-Session contract, and gives the panel its display name plus the normal Session-navigation target; unresolved provenance renders no link. `App.svelte` keeps this owner mounted across ordinary main-view navigation (one `serverRecoveryGeneration`); onboarding and confirmed server recovery are the intentional remount boundaries. An Agent address may be global or Project-scoped (`chatState.js::resolveAgentAddressing()` selects the scope; `agentAddress.js::formatAgentAddress()` formats the address); Chat's selected Project context changes active addressing, not the Project managed in `ProjectsView`.

Reflection rows retain their review Session owner (`agent_id`/`project_id`) independently of the displayed source Session. Opening, loading changes and undo use that owner, including after the source moves to another Agent or Project; live legacy rows without one use the source owner. Agent renames update retained review owners too.

Reflection reviews appear in the Activity panel's Running and Finished sections alongside Sub-Agents and commands. `chat.timeline` reads without a cursor restore the source Session's `reflection_runs` (incremental reads carry none and leave an in-flight `chat.reflections` read in place); reconnects refresh the displayed Session through `chat.reflections` without reloading its transcript. `chatState.js` reconciles these snapshots by request generation and preserves newer live events. Server-marked reflection payloads carry `source_session_id`; `chatRunStream.js` delegates its private child/Reflection activity projection to `chatRunStream/activity.js` and WebSocket event normalization to `chatRunStream/serverEvents.js`, maintaining entries from those events, while the durable refresh recovers reviews completed during a disconnect. Rows show scope as their title (`Memory reflection`, `Skill reflection`, `Memory & skill reflection`; user-facing text says Reflection, never review - user requirement) and status plus coarse elapsed time or outcome on their second line, and navigate to the fork Session through ordinary session selection - no sub-agent banner, no cancel control, no unread contribution. A shown Reflection Session (a fork whose `run_kinds` hold a reflection kind) gets its own compact footer banner, "Viewing a reflection session", whose "Return to main session" opens the source Session as a history step (`ChatView.sessions.test.js`).

A finished review row with an `outcome` adds one quiet line (user requirement: background learning stays quiet - no toasts - and every change is traceable and reversible in one step): `2 Memory entries, 1 Skill changed`, `Nothing saved`, or `Reflection undone`. A review that changed something opens from that line (`aria-expanded`) to its change list (`learning.changes`, read again on every opening): per change what happened, the Memory scope or Skill name, and the entry text or files; undone changes are struck through. `Undo reflection` asks inline (`Undo every change of this reflection?`, Undo/Keep) and then calls `learning.undo`; the result updates the row's outcome and list, and a refusal stays inline under the list, worded from `error.data` (which entry or Skill, who changed it later and when); other failures show the server message and read the review again; reopening the list drops an earlier refusal. Live, `chatRunStream/activity.js` reports a review's first terminal event (`onReflectionFinished`), and ChatView rereads that source Session's reviews through `chat.reflections`, displayed or not, so the row gains its outcome. The controller's internal `lib/chatState/reflections.js` owns the row restore, the outcome, the change list and the undo; lists and undo state live in `reflectionDetails` beside `reflectionTasks`, so a row refresh keeps an open list. `lib/chatTimelinePresentation/reflections.js` words rows, outcomes, changes and refusals. Coverage: `ChatActivityPanel.test.js`, `chatState.child-work.test.js`, `chatRunStream.child-activity.test.js`, `chatTimelinePresentation.activity.test.js`.

`chatState.js` preserves the public state/controller interface; internal `lib/chatState/` modules own controller orchestration, Session/activity/Queue state, timeline paging, lifecycle events and Project addressing. `childTasks.js` is the controller's internal child-work lifecycle: the bounded Sub-Agent status cache, exact-work inspection, Sub-Agent cancellation, the live background command states by Session (`chatState.commandStatuses`: App's forwarded `command_status_changed` map joined with what its own stop and output reads learned), stopping a background command (`chat.stop_command`) and reading its newest output (`chat.command_output`). It receives the same state and operations; cleanup stays with the controller.

`chatTimeline.js` applies authoritative server items and keyed patches. The server owns semantic ordering, History/live overlap, Tool finalization and Compaction; see `chat/timeline.md`. The former `lib/chatTimeline/` semantic reducers and `streamingEvents.js` have been removed. `chatTimelinePresentation.js` keeps its public formatting surface; internal `lib/chatTimelinePresentation/` modules own messages/attachments, Tool rows, child-Run status projections, activity, change statistics and shared time formatting. Both dependency graphs are acyclic; callers continue through the existing public modules.

`SessionListDrawer.svelte` keeps Session-list presentation, filters and menus; its private `components/sessions/list.svelte.js` owns list snapshots, selection, live-activity overlay, source-key/request-generation guards, coalesced invalidation refreshes, and pagination for both list modes. Its header names the listed scope (the selected Agent's name, All agents, or Projects) beside a Group by Project toggle, a direct All agents toggle (hidden while grouped by Project) and the category filter. Opened from the Agent bar's Session-list toggle, it docks left of the Chat surface and pushes it aside; in a Chat area narrower than 720px (container `chat-area` on `.chat-view__content-shell`) it overlays the Chat instead. It stays open until the toggle closes it. A row's status marker sits before its title: a pulsing amber dot while its Session works, an amber ring while it waits (its tooltip names what it waits for and the work span), otherwise a blue dot for an unread result (see Session activity below). Channel Sessions are hidden by default through the persisted `channels` filter and server-side `include_channels`; the required selected Session remains visible. All agents is independent of the category count. Its internal `components/sessions/actions.svelte.js` owns rename, deletion (with the delete dialog's Archive option, `webui/archive.md` -> Delete dialogs) and Compaction Policy edit lifecycles; a rename starts from the name the row shows (empty for a Session without any name yet), and saving that name unchanged sends nothing, so an untouched automatic title stays automatic; `menus.svelte.js` owns the row/filter popovers; `presentation.js` holds row labels and timestamps; `kindIcons.js` holds each Session kind's icon as data, drawn by the row marker (`SessionKindIcon.svelte`) and the details card's legend alike. Mutations and their parent callbacks retain the original Session target, but completion refreshes the drawer's current Agent/filter scope, including after navigation while a mutation was pending (`SessionListDrawer.actions.test.js`). The shared Session-list API and parent navigation callbacks are unchanged. The list reloads, coalesced, on the full `reloadToken` or when an entry of App's `sessionInvalidations` window names an Agent it lists (read acknowledgements excepted, because the live Chat overlay already shows unread state).

## Selection and Sessions

- `ChatWorkspace.svelte` composes at most two independent Chat/Preview areas. Each retained `ChatView` has its own controller, selected Agent/Project/Session, composer, history viewport, and Run subscription. Closing an area or selecting Preview hides its Chat without cancelling the Run or discarding the draft. The first area's shown Session is Chat's place in App navigation; the second keeps its selection and child-Session navigation local and out of history. Both areas accept the same child-link target object (`{agentId, sessionId}`), open the child at the live tail, and retain its Parent return. Hidden Chat owners reconcile events but do not acknowledge unread completions or request composer focus.
- Area actions are direct icon buttons at the right end of Chat's Agent bar (`ChatHeader` `actions` snippet, class `chat-header__action`) and in Preview's file toolbar: each area carries the split toggle (Split view when single, Close area when split) and, only once a file was opened in that area, the chat/preview content toggle. `ChatWorkspace` owns focus restoration (closing an area focuses the remaining one) and the portaled file-actions menu; it adds no persistent toolbar, content tabs, duplicate title or focus stripe. Tests cover focus after closing an area and manual content switching with a retained draft.
- **Open in split view:** context menus (right click, ContextMenu key or Shift+F10, shared `ContextMenu`) offer to show a target in the workspace's other area: Session list rows (first item of the row menu), Agent bar tabs, Sub-Agent rows of the Activity panel, Sub-Agent session links in the Timeline, and the Agents view's row menu. The item reads Open in split view while one area shows and Open in other area once both do; it opens the split view when it is closed, and a request from the Agents view opens beside the area shown now (or in the second area when both show). `ChatWorkspace::openInOtherArea` hands the target (`{agentAddress, sessionId?, subAgent?}`) to the other area's `ChatView` as `openRequest`, which applies it once that area is active and has its roster, exactly like a choice in its own Session list (`handleSessionSelected`, including the Sub-Agent banner) or Agent bar (`handleSelectPickerAgent`); so in the first area it is a history step, in the second it stays local. A second area created for an Identity Agent starts on that Agent instead of copying the first area's selection. App drops an Agents-view request whose switch to Chat did not happen before another view was shown (`ChatWorkspace.test.js`, `AgentsView.test.js`).
- Both retained Chat areas enable `preserveSessionSelection` for roster adoption, the first area also while it is alone: shared Agent refreshes update configuration without moving a locally held Session to the backend's last-written pointer. This also keeps an area's draft: `sessionState.js::setAgents` with `preserveSessionSelection` keeps an empty local Identity pointer. Explicit New Session and a draft's created Session still update the initiating area's selection. Deletion matching uses the full Agent/Project address plus Session id, so another owner's identically named Session never navigates away. Deleting a Session releases every area's retained pointer to it: the deleting area re-aims its identity current pointer (or its Project Agent's held Session) to the server's `next_session_id` landing before navigating there (a null landing empties the pointer, and the owning Agent shows its draft), and `ChatWorkspace` forwards the deletion to the other area, which releases and follows passively (no composer focus). The server's `sessions` deletion event reaches every window: `appController` maps its scope to an App-owned `sessionDeletion` (`agent@projekt` address, deleted id, landing id) and `ChatWorkspace` forwards each new one to every mounted Chat area through the same passive sibling path; a deletion already present when the workspace mounts is ignored. In the deleting window the event and the delete response arrive in either order: when the event came first, the drawer's deletion completes the deliberate part (composer focus) without reloading the landing; in every area the deleted Session's history entry is corrected to its landing, never a new step (`ChatWorkspace.test.js`, `ChatView.projects.test.js`, `appController.test.js`). `ChatWorkspace.test.js` mounts both real Chat owners and verifies addressing, retained drafts, resizing, and preview switching; Chat title ids are instance-specific and composer selectors must be scoped to their area.
- Selecting a Session keeps its area's Session list open. `ChatWorkspace.svelte` restores Session filters from origin-local `localStorage` independently per area through `sessionListView.js`, surviving page reloads and Desktop restarts with the shell's persistent browser profile. A newly mounted second Chat starts with its list closed and uses its saved filters, or copies the first area's latest filters when none were saved, including when first opened from Preview. Changes save immediately and remain area-local across list/area close and reopen; invalid values normalize to defaults and unavailable storage leaves in-memory interaction usable (`ChatWorkspace.test.js`, `sessionListView.test.js`).
- **Identity Agent rename:** App's `onAgentIdChanged` first moves composer memory (`composerMemory.js::renameComposerAgent`: drafts and attachments keyed `<old>::...`, including unsaved draft keys, and the send history; every tab applies it and the next merge persists it), then `selection.remapIdentityAgentId` calls every `subscribeAgentRenames` listener synchronously before it remaps the shared selection, then App remaps navigation (`webui/app-shell.md` -> Navigation). `ChatWorkspace` remaps the second area's Agent and both areas' displayed Sessions; each `ChatView` re-keys its own state (`renameAgent`): controller Sessions and roster entry (`sessionState.js::renameAgentInState`), Session settings drafts, transient cards and the viewed Sub-Agent address, and it reads the shown Session's History again under the new id. History, Queue and reflection reads still in flight for the old key are superseded (`supersedeRenamedSessionKey`), so they cannot land on the renamed Session; its Run stream closes, since a rename admits no active Run. The second area's pending child-Session navigation is not remapped, because it was already handled (`ChatView.sessions.test.js`, `ChatWorkspace.test.js`, `chatState.history-loading.test.js`, `composerMemory.test.js`, `selection.test.js`).
- Two areas showing the same addressed Session share one composer owner so Session-scoped draft storage cannot race. The visible first Chat owns input unless only the second Chat is visible; closing/switching areas transfers the composer through the existing draft store. New Session in the duplicate view shows that area's own draft even when the shared Session is empty. A second Chat owner is mounted only when its Chat content is opened, never merely to open an HTML preview.
- HTML file links in Assistant Markdown open the opposite area's Preview; modifier clicks retain browser navigation. `MarkdownContent.svelte` adds a neutral external-browser arrow beside delivered HTML links only; their file actions open on right-click or the keyboard context-menu shortcut, with no additional menu button; `ChatWorkspace.svelte` owns menu navigation, preview opening, and Desktop external-browser dispatch. Download requests the original with `?download=true`; ordinary web links are unchanged. The file link is the user entry point: there is no manual path form or menu entry into an empty Preview; the Show preview button only restores an already opened file. `HtmlPreview.svelte` opens through `file.preview_open`, polls the bounded folder revision serially every 1.5 seconds only while visible with Live enabled, and cleans up requests/timers on replacement or teardown. The iframe has `sandbox="allow-scripts allow-downloads"` without same-origin permission. Only source-checked opaque-frame messages with a URL inside the current capability prefix may update its reload destination; this preserves subpages and allows a deleted/recreated page to recover. Reload replaces the iframe document even when the URL includes a fragment; Retry and explicitly reopening the same file navigate to the entry again. Retired-frame messages cannot redirect the new document (coverage: `HtmlPreview.test.js`). Preview serving/isolation is owned by `server/file_delivery.py` (see `server/browser-capabilities.md`).

- Display state is override-first: a temporary UI choice leads while a mutation is pending, but Agent/Project/Session state must reconcile to server responses.
- **History places** (`webui/app-shell.md` -> Navigation): the first area's place names the Session it shows, `[agentAddress, sessionId]` with `extra` `{selection, subAgent}`, or only `[agentAddress]` for a draft (reported with an empty `sessionId`). `chat/view/navigation.svelte.js` reports every change of the shown Session (the viewed override, else the active Agent's own current Session or draft) to App through `onSessionNavigation(session, {replace})`. Changes made inside a user action wrapped in `asStep` - choosing an Agent, Project, Project Agent or Session, New Session, the parent link, Return to current - become a history step; every other change (a restore, a load resolving the Session, a deletion landing, a Session moved by `/agent`, a draft's created Session, the passive follow of the shared Agent selection) corrects the current entry. App restores a place without a Session as `{agentId, draft: true}`: it shows the draft again when that Agent is the area's active own Agent, otherwise it returns to the current view like `returnToCurrent`. While Chat is hidden a report corrects the place Chat returns to. App-driven Locations (Back/Forward, deep links, the main navigation, sub-agent links) arrive as `pendingSessionNavigation` and are never reported back as a step; `returnToCurrent` re-reports the shown Session so the entry names it.
- A copied Chat place without `extra.selection` establishes the linked selectable Identity Agent or listed Project Team member as the normal target, including for its draft and later New Session. Explicit history selection remains authoritative; hidden owners and child-Session links keep the existing selection and use a Session override. App waits for its initial Project catalog attempt before inferring Team membership; a failed attempt still permits an explicit Session override.
- Session restoration from history retires an older navigation after asynchronous Project loading. Project team responses, errors, and loading indicators belong to the latest team request across picker switches and history restoration, including revisiting the same Project.
- Session state keys on (Agent address, Session id); switching Agents or Project context never merges histories, Queue items, usage, or active Runs.
- Session activity (server-owned, user decisions 2026-10-21): `lib/sessionActivity.js` owns App's store of every `working` or `waiting` Session (a Session absent from it is `idle`), keyed like Chat's Session state (`<agent address>::<session id>`, the address qualified from the event's bare `agent_id` and `project_id`). Each `connection_ready.session_activity` replaces the store (null before the first hello), each `session_activity_changed` replaces one entry and `idle` removes it, and an Identity Agent rename moves its entries (`appController.js`). `ChatView` forwards it to `chatState.sessionActivity` and to the Session list. The WebUI never rebuilds this state from Run or command events: Agent status, Session-row markers and Stop all read it, and an unread result counts (Agent bar, Session row, Main menu) only while its Session is idle. While the displayed Session is `waiting`, its latest Run's footer keeps that Run's own duration followed by `(Waiting)` (`runFooterParts`; user decision 2026-10-21: no second elapsed-time display, no work-span duration in the footer). `finished_work` is not read. Coverage: `appController.test.js`, `chatState.agent-activity.test.js`, `sessionListView.test.js`, `SessionListDrawer.test.js`, `ChatView.activity.test.js`.
- Agent navigation projects status with strict priority `running` (one of the Agent's Sessions works and counts toward Agent activity) -> `waiting` (one waits for work that will wake it) -> unread (an idle Session holds an unread result) -> idle (`sessionState.js::agentActivityStatus`); selection is a separate accent state. Tooltips (`chat/agentActivityTooltip.js`, shared by `ChatHeader` and `ChatView`) title the Agent's name, then an `Activity` row in words (`Running` or what the Agent waits for, both in amber with the span since its earliest working or waiting Session left idle, built at each hover, e.g. `Waiting for 2 Sub-Agents, 1 command · 4m 12s`; unread result count; `Idle`), the effective Model as a `Model` row in canonical `provider/model` form (no `::connection[:account]` suffix), a `Thinking effort` row (the effective effort, or `Provider default` when none is set), and the id as a mono `Agent ID` row when it is more than the name in other letter case - Identity Agents from `agent.list`, Team members from the Project scan (`project.list` cached scan, `project.show` for the open Project). Every Agent bar tab and every All agents option shows the same tooltip.
- `ChatHeader.svelte` is each Chat area's Agent bar: the Session-list toggle and New session, then the first five Identity Agents in roster order (the Agents tab's order; no pinning, user decision) as tabs, then `...` for All agents, and the area actions at the right. The selected tab is a neutral `--surface-3` tab. A tab shows a status dot before its name only while the Agent is running (amber, pulsing), waiting (amber ring, user decision 2026-10-21) or has unread results (blue); idle Agents show no dot (user decision). Tabs that do not fit the bar wrap onto a clipped second line and are reached through All agents (`measureFittingAgents`, re-measured through a ResizeObserver on the row and on every tab); on a bar narrower than 560px (container `agent-bar`) unselected tabs show the name's first two letters through a `data-initials` pseudo-element, so their text content stays the name. A displayed Agent outside the shown tabs (a later Identity Agent, a Team member named `Builder · vBot`, or an override stand-in through `displayedAgentName`) gets one temporary tab after them. `...` appears whenever an Agent is not shown as a tab and carries the combined status dot of the Agents reachable only there. It opens the All agents list (`SearchableDropdown`): every Identity Agent first, without a heading, then each Project that has Team members as a collapsible group headed only by its name (tree mode); a Project without Team members is left out (user decision). The filter field appears whenever a Project group exists or above 6 Agents, and also matches Project names. Options order running, then waiting, then unread (newest result first), then roster order within Identity Agents and within each group, and name their status (`Beta: Running`, `Gamma: 2 unread results`). A closed group shows its Agents' combined status dot (running over waiting over unread) and unread count; an amber warning icon marks a Project whose scan report is not clean. A group opens for the selected Agent's Project on every list open, otherwise by this browser's remembered toggle (`vbot.chat.agentPicker.expandedProjects`), otherwise when any of its Agents is not idle. Team members come from `project.list` with `include_scan` (the server's cached scans, loaded by App's `selection.svelte.js`); the open Project's Team starts from the live `project.show` result, and a newer listed scan replaces its Team/report in place and retires an older pending Team read without resetting held Sessions (`target.svelte.js`, `ChatView.projects.test.js`). Choosing a Team member opens its Project (`target.svelte.js::handleSelectProjectAgent` -> `openProjectTeam`, which shows the listed Team at once and replaces it with the `project.show` result); choosing an Identity Agent leaves the Project (`leaveProject`), so App persists `''` for both the Project and the Project Agent. The scan banner shows while a Project Agent is active. The unread count is the number of the Agent's idle Sessions with an unread result (`hasUnreadCompletion` plus `unreadRunId`, excluding the displayed Session) from `sessionState.js::agentUnreadResults`; Chat reads activity for every Agent address on the bar and in the list. The first Chat area also reports the number of unread results across those addresses to the Main menu's Chat entry (`onNavigationIndicator`, tone `unread`, `webui/app-shell.md` -> Main menu indicators); while that area is shown, its displayed Session does not count, like on the Agent bar, and while Chat is hidden it does, because a hidden Chat sends no read acknowledgement (`ChatView.activity.test.js`). Tabs and list options both call `ChatView.svelte::handleSelectPickerAgent`, which routes by Agent address. The drawer's All agents roster stays the Identity Agents plus the open Project's Team, keeping `session.list` within its address bound. Coverage: `ChatHeader.test.js` -> Project Teams, `ChatView.projects.test.js`. A shown Session whose Identity Agent is not in the roster (the hidden Librarian's, opened from Settings or the Skills manager, or a deleted Agent's) is an override view with a stand-in Agent (`target.svelte.js` `overrideAgentDisplayStandIn`, named "Librarian" for the Librarian through `lib/librarian.js`, and "Live voice" / "Live backend" for the Live Agents through `lib/liveAgents.js`); a Live Agent's Session shows the notice "This Session records a Live voice call. Only the call writes to it." in place of the composer (the stand-in's `__liveCall`), matching the server's refusal of other Runs for these Agents (`ChatView.sessions.test.js`); the bar shows that name as the temporary tab (`displayedAgentName`), and the composer sends to that Agent and Session (`ChatView.sessions.test.js` -> Librarian Session). Coverage: `components/chat/__tests__/ChatHeader.test.js`, `ChatView.activity.test.js`. `connection_ready.active_runs` supplies post-reconnect Run state; batched `session.activity_list` supplies durable completion state; `session.list` stays authoritative for the selected Agent's drawer and Project-Agent landings. List rows carry the server's `activity_state`, `work_started_at` and `waiting_for`; the WebUI ignores their `has_active_run` (Live voice reads it). While the drawer remains open, it overlays Chat's held per-Session unread state and, once App holds it, the Session activity store onto those authoritative list rows by complete Agent address plus Session id (`sessionListView.js::overlayLiveSessionActivity`), so working, waiting and unread markers react without another list request. Clicking an unread Agent opens its newest unread Session. Runs with `contributes_to_agent_activity: false` stay out of Subagent status maps, and a working Session reporting it stays out of Agent-level activity, while its concrete Session row still shows it working.
- A completion counts as read only once its exact `run_id` appears in the displayed history (as a finished Run of the loaded page, `historyRuns`, since windowed `chat.timeline` messages carry no Run summaries) or terminal events and the user can see it: ChatView's acknowledgement effect is the only `session.mark_read` trigger (a History load does not acknowledge), and it sends only from an active Chat area while the page is visible and focused (`document.visibilityState === 'visible' && document.hasFocus()`, read live). Regaining window focus or visibility re-checks the displayed Session. Do not loosen this gate: other clients treat the resulting `read_run_id` as "the user has seen this result" (the vBot tray skips or dismisses its toast, see `server/events-and-reconnect.md`) (`ChatView.activity.test.js`). The displayed Session leaves unread presentation immediately while its acknowledgement pends or waits for attention, and returns on failure. Retained `latest_completion_run_id` is the reconciliation key - arrival order of replayed terminal events must not flip read state, and an older completion must never clear a newer local result. A terminal event with `completion_read: true` (a Sub-Agent Run that answered its Parent, `sessions/runs.md` -> Completion activity) becomes the latest completion without unread state (`chatRunStream.test.js`). Completion activity reads (`lib/chatState/activity.js`) are coalesced: at most one `session.activity_list` runs, one pending pass collects the addresses requested meanwhile, and a burst of invalidations waits 100 ms to become one read. Newly displayed Agent addresses are read once successfully; failed reads release their addresses for another read and retry while displayed, after 1 second with backoff up to 30 seconds. ChatView shows the activity error until recovery; disposal cancels retries. The full `sessionsRefreshToken` or a new connection snapshot re-reads all. From App's `sessionInvalidations` window, a terminal `run_id` whose terminal event App's Run event feed still holds (applied as it arrived, or first by a hidden owner), a `read_run_id` matching the held completion (cleared locally), a deletion (marker dropped) and other Session changes such as create or rename need no read; a terminal `run_id` no longer retained or an unmatched `read_run_id` re-reads that displayed Agent, and an unscoped entry or a window overflow re-reads every displayed Agent. The response omits Sessions without a completion, so an omitted Session is cleared only while its local completion is still the one seen when the read started.
- Loading flags are responsibility-specific (`loadingAgents` only `agent.list`, etc.); background activity loading never resurrects the roster loading surface. Only the newest displayed History request owns the loading state; a pending request for a departed Session releases its loading state immediately on navigation, including to a draft; its eventual completion cannot clear a newer displayed request. An older request for the same Session cannot keep the composer disabled after the displayed load finishes. History loading disables the composer and New Session; a draft has no History to load, so its composer is usable at once. Initial History feedback waits 300ms and is keyed to the currently displayed Session, so a fast Agent/Session change stays quiet and a stale destination cannot flash feedback over the new Session.
- Only the latest roster read can publish Agents, selection callbacks or errors. A silent refresh that supersedes initial loading inherits its pending loading/initial History responsibility; ordinary background refreshes keep Chat mounted and skip initial History. A Chat mounted hidden adopts App's shared Agent selection silently on its first display (no navigation report, so a restored override survives), and the controller still loads that Agent's current History unless the pending initial roster load reads it (`loadAdoptedSelectionHistory`). Disposal invalidates pending roster reads (`chatState.agent-activity.test.js`).
- History loads newest-first and prepends older pages without moving the reading position. Windowed `chat.timeline` reads keep raw User records only; `last_usage` supplies the latest Assistant usage before child windowing. An omitted field preserves the held value, null clears it on replacement, older pages never replace it, and newer live usage supersedes a pending read. The controller stores `next_before` from each response and sends that opaque cursor for the next older page; falling back to the first public Message id exists only for compatibility with older servers. An older-page response belongs to the loaded History snapshot: a successful full refresh, Run reconciliation, or accepted edit invalidates its result and errors while preserving the replacement cursor for the next request; failed refreshes and other Sessions do not invalidate it. Subsequent History reads use `next_after`; bounded append batches are collected before application (their messages, Run records and background statuses fold together, a later record winning) and preserve loaded older pages. History Edit, Agent Takeover or generation replacement resets the snapshot. Record sequence identifies occurrences even when public Message ids repeat. A matching canonical Run Summary proves completion; matching stable output ids never prove complete Run coverage. Without terminal persistence, the live terminal projection remains visible.
- A History response mutates only its addressed Session; full refreshes and recovery requests for the same Session share a generation guard and reject snapshots superseded by an accepted edit; a full refresh overtaken by a newer Run rereads History before applying an obsolete active-Run snapshot, and only the newest response for the still-displayed Session may touch global loading/error state or attach the Run stream. These guards belong to the controller, not the View.
- Background-only Sessions: a non-Channel Session whose `run_kinds` are entirely cron/reflection kinds classifies as hidden-by-default, as does every Sub-Agent Session. One with a `latest_completion_run_id` (a Cron Run that reported to vBot) is still listed, as the server lists it (`sessionListView.js` `visibleSessionsForSelection`), but never chosen as a Project Agent's landing Session. A Librarian Session (`run_kinds` `librarian`) is an ordinary row: the server lists it only in the hidden Librarian's own scope (`sessions.md`), which the drawer addresses while one of its Sessions is shown. `SessionListDrawer` sends those category filters to `session.list`, loads 35 globally ordered rows initially and 20 per scroll page, and keeps the selected Session visible through the required-Session contract even when it is old or classified. The **All agents** toggle sends the deduplicated roster in one bounded request; returned rows carry their owning Agent address and the UI routes selection/rename/delete/policy actions through it, using a composite Agent-address-plus-Session-id row identity. A refused delete shows inline: `session_in_use` names the pinning Cron jobs (Agent jobs of Calendar events included) and Bootstrap jobs from `error.data.references` through catalog text (`sessions/presentation.js` `sessionDeleteErrorText`), `session_busy` (an active or queued Run) shows the catalog text `sessions.delete_busy`, other refusals keep the server message (`SessionListDrawer.actions.test.js`). The browser never downloads hidden pages or open-ended Session metadata merely to calculate the list or its remaining count. Project Agents have no server current-session pointer: their initial landing requests the newest ordinary Session only, else shows a draft; Parent/Sub-Agent navigation requests its exact Session through the same required-Session contract.
- **Drafts (lazy Session creation):** a Session exists only once it is used. Until then the area shows an unsaved draft: an Identity Agent whose area-local `current_session_id` is empty, or a Project Agent whose `projectAgentSessions` entry is `''` (an absent entry means not resolved yet). New Session, `/new` (the server returns `command: "new"` without a Session id and has cleared the Identity pointer; an Identity Agent becomes the selected one), an Identity Agent without a current Session, a Project Agent without a Session and a deletion without landing all show a draft; none of them calls the server. `target.svelte.js::activeDraft()` names the shown draft; its composer key is `<agentAddress>::~draft-<area index>` (`~` never occurs in a Session id), so each area keeps its own draft text, attachments and Session settings (Composer and inputs -> Session settings) across navigation. A draft has no Session state, unread state, activity or list entry.
- `New Session` is an idempotent intent and requests nothing: a draft, or an empty displayed Session whose composer this area owns (no visible history/events/Queue/command card and no composer text), only gets focus; otherwise the area shows the Agent's draft. A shown draft clears the drawer's row selection without reloading the list (`SessionListDrawer.test.js`). History loading disables the action. The server's Identity pointer is untouched until the draft's first send. New Session stays available during an active Run - leaving closes only the local SSE subscription while the server Run continues, and returning reconciles/reattaches it.
- **By Project:** the drawer's Group by Project toggle (persisted filter `byProject`, collapsed groups in `collapsedProjects`) is an additional view beside the per-Agent list, not a replacement (user decision). It reads `session.project_groups` (`server/session-agent-rpcs.md`): one group per registered Project with its newest 5 Sessions of every Agent, then "Other chats" for Sessions in the Workspace or an unregistered Project. The Project groups show in the order of App's `projects` (the user's Project order, the same as the Projects tab) and move by their header through the shared `SortableList` (the Sessions below are `data-sortable-ignore`); a move stores the new order through `selection.svelte.js::saveProjectOrder` (optimistic, `project.reorder` against App's `order_revision`, a refusal restores, reloads and toasts), "Other chats" stays last; "Show more" continues a group by 10 through `session.list` `working_project_id` and the group's cursor. A row names its Agent only in its details card, not on the row (user decision; roster names, Team names from `target.projectGroups`); the shown Session is the active row. The view reloads, coalesced, on every Session invalidation except read acknowledgements. A group's `+` starts a draft in that Project (`onNewSessionInProject` -> `navigation.handleNewSessionWith`, which makes the Agent the active one and shows its draft): with the displayed Agent when it can work there (an Identity Agent in every group, a Team member only in its own Project), else from a menu of the Identity Agents and that Project's Team. For an Identity Agent `sessionSettings.startDraftIn` sets the draft's `working_project_id` without changing the Agent's Default Project. While the view is shown, New Session continues the shown Session's Project with the displayed Agent (an empty shown Session only gets focus); with a draft shown, an unknown Project or a stand-in Agent it stays the plain New Session (`SessionListDrawer.test.js` -> by Project, `ChatView.sessions.test.js`).

It reads the returned Session id (top level, else a command response's `data.session_id`, else a queued `item.session_id`), creates the (address, id) Session state and calls `onSessionCreated` before the Run stream attaches; ChatView then adopts it through `navigation.adoptCreatedSession` (only while that Agent's pointer or held Session is still empty; an Identity adoption is reported through `onAgentsChanged`) and refreshes the Session list. While the draft is still shown, the created Session replaces it and corrects the history entry; after the area moved on, a later return to the Agent opens it. A command answered without a Session (`/status`, `/help`) keeps the draft. `actions.sendDraft` resolves `{draftKey}` for the created Session, and `ChatComposer` treats that as sent and moves text and attachments added during the send to the created Session's key; an upload still running when they move completes or fails where its attachment now is. ## Runs, streaming, and recovery

- `ChatReasoning.svelte` owns the shared Reasoning disclosure for live and saved Timeline entries. Structured summaries show a fixed Reasoning summary label, the latest section's optional Markdown heading, and a section count; expansion renders and copies all readable sections. No heading is invented from prose. Summary headers do not display a thinking-duration estimate or completed-step checks. Ordinary commentary and Tool rows retain their own presentation. Unstructured Reasoning, including mixed summary/raw text, uses the existing complete-text fallback. The server supplies ordered summary sections and final text; presentation never merges raw reasoning deltas.

- `createChatRunStream()` owns one EventSource for the displayed Run's `/timeline` stream, a heartbeat watchdog, reconnect and terminal cleanup. Every connection begins with an authoritative `timeline_snapshot`; `timeline_update` carries keyed edits and text suffixes with an exact `base_sequence`. A mismatched base reopens the stream for a snapshot. Clients never reconstruct missing semantic content from sparse raw events.
- Snapshot/patch application preserves unchanged row and child object identities. Local drafts, disclosure state, scroll anchors, selection and media playback remain client-owned. Paging prepends complete Run groups and stable ids preserve mounted state when live work becomes durable history.
- `/ws` continues to supply lifecycle, Queue, activity and invalidation facts. It does not feed transcript content. A terminal event refreshes the addressed Session; a late predecessor cannot stop its successor, and a deferred start cannot revive a Run whose timeline already proves completion.
- Run server events reach a Chat owner through App's Run event feed (`webui/app-shell.md` -> Server connection and events): the controller keeps a feed cursor and hands each event to `chatRunStream.js::handleServerEvent` once, in feed order, so no owner keeps a key index of server events. A shown ChatView applies new events as they arrive. A hidden one (Chat behind another main view, or its area showing a preview or not shown) reacts only to Run starts: it applies those of the Session it displays at once, so that Session streams as when shown, and leaves the rest - typically the Runs of Swarm participants and other background Sessions - in the feed. It applies them in order when shown again, and earlier where a result must follow them: before a Session activity read, before a deletion or read acknowledgement from `sessionInvalidations`, before a finished Run of a displayed Agent, before a connection snapshot and before an Agent rename (`chatState.test.js`, `chatState.agent-activity.test.js`, `ChatView.test.js`). If the feed dropped events the owner never applied, it starts again from current state as after a reconnect: App's `activeRuns`, a re-read of every displayed Agent's activity, the Queue reads of a Run end and the displayed Sessions' Reflections. A mirrored event of a displayed Run whose History is already complete  is dropped, so a late deferred `run_started` cannot restart a finished Run (`chatRunStream.test.js`).
- `connection_ready.active_runs` replaces locally projected active Run/Subagent status; excluded Runs still reattach SSE when displayed. A Chat owner mounted after the app connected applies App's live `activeRuns` list instead of the retained snapshot's list and starts reading App's Run event feed at its end (`chatController.startFromServerState`; see `webui/app-shell.md`). If the displayed local Run is absent from reality, reconcile via `chat.timeline` before clearing (missed terminal -> durable final answer); once History confirms no active Run, discard all retained replay before rendering so sparse fragments cannot reappear behind it.
- Active snapshots preserve server timestamps (`currentRun.startedAt`; Child inspection keeps separate run/session start keys). One visibility-aware adaptive clock feeds elapsed times downward; Unstructured Reasoning headers tick from first delta until the next stable boundary freezes the estimate (`reasoning_timing` replaces it once available).
- Terminal timeline frames settle and close their matching stream. Raw lifecycle completion and cancellation trigger an authoritative timeline read. The server finalizes unfinished Tools and preserves partial text; `run_interrupted` remains amber and no control starts another Run implicitly. A failed refresh leaves the visible content available for recovery.
- The Iteration badge projects only reported numbers: seeded from `active_run`, advanced by each completed Model response regardless of sibling Tool count, settled terminally, restored from `run_summary`; a summary without the field means unknown - omitted, never estimated.
- `subagent_status_changed` is the explicit Parent-cancellation projection: spawn rows settle to cancelled even when the event belongs to a later/non-contributing Parent Run.
- Cancelling a Run and cancelling a cancellable tool call are distinct operations - preserve that in labels, availability, and error handling.
- Pending Run cancellation is keyed by Session and exact Run id. Switching Sessions or starting a successor leaves its Stop control usable; duplicate cancellation requests for the same Run coalesce, and late failures do not overwrite a successor's action state.
- `sendMessage()`, `sendToNewSession()` and `editMessage()` resolve semantic outcomes after reconciling Session/Run/Queue state; the View snapshots display key and UI generation before awaiting either, then applies navigation/toasts/transient cards and scroll updates only while that generation is current. Edit admission calls `chat.edit`; only after success does the controller remove the targeted User message and later active suffix locally, attach the new Run stream, and clear Current Context Usage until the server refreshes it. Failure preserves the visible lineage unchanged.

`ChatComposer.svelte` keeps draft/History navigation, submission admission and input/keyboard coordination. Internal `components/composer/media.svelte.js` owns per-draft attachments, upload/recording lifetimes and transient feedback; `picker.svelte.js` owns Skill/file/Model triggers, catalogs and picker selection. Both consume current values through local getters; the component retains its public props and the existing admission snapshot semantics. `composer.css` contains the namespaced presentation rules.

A short step advances latency while keeping the preceding measurable rate. Neither projection is reconstructed from paged raw Messages. The footer marks stream-derived rates with an approximation sign, distinguishes answer-only, streamed output and Provider decode rates in the tooltip, and shows TTFT even without a rate; separate keyboard-focusable tooltips identify each measurement's Model. History resets and edits clear replaced measurements, and a newer live step wins over an in-flight History read. Explicit choices are remembered as the addressed Agent's start values for future Sessions; opening an existing Session only reads its stored choices and never changes those start values. A draft's Project picker writes an Identity Agent's `root_project_id`; existing Sessions keep their Working Project, and a Team Agent always works in its Team Project. A pending Project scan cannot complete the move after newer navigation or Chat teardown; the source draft stays in place. Changing Model maps effort through `effortForReasoning`, saving an adjusted effort together with the Model. Draft choices save through `agent.update` or `project.set_override`; existing Session choices use `session.set_agent_overrides` with `remember: true`. An Autosave participant per Session or draft key serializes its writes, keeps newer choices over an older reply, and retains failed changes for retry. Sending flushes only the captured destination key; a failed or running save for another conversation cannot block it. The footer's SaveStatus shows only the displayed key's pending/saving state and retries that key. All participants still join app-level navigation protection and follow Agent renames. A submission captures Model, effort (including explicit Provider default) and Working Project before asynchronous file-mention lookup, so later draft edits belong to the next Session. New drafts start from remembered values. Session rows refresh on display change, changed Agent start values (which also capture legacy Sessions), scoped invalidation, `/model`, and settled writes; reads overlapping a write are discarded, then retried. `/model` refreshes the Agent's defaults and rereads the Session's captured Model. The Model catalog loads when the footer first shows and whenever the Model picker opens. ## Usage and errors

Speech Tool artifacts in `ChatAssistantRun.svelte` and `ChatTimelineEntry.svelte`
use `components/ui/AudioPlayer.svelte`, also used by the Settings preview. It
owns media state, seeking, speed, volume, download, playback errors and resource
cleanup. A successful `generate_speech` result shows the player whether its Tool
result envelope is a live event object or the persisted Tool message's JSON text
from Session history (`chatTimelinePresentation/messages.js`). Only a live Run
projection (`item.source === 'live'`) requests one automatic start per source;
a player first mounted for a Run rebuilt from Session history stays paused. The
player latches that request when a source is attached and ignores re-renders
with an equal source, so a player that survives the live-to-History handoff
keeps playing (or still starts) without reloading. Later `canplay` events must
not undo Pause. Starting another shared player pauses the previous one.
`speech_playback` Run events attach a transient server PCM stream to the
running Tool row before its result arrives. `api/media.js` validates the framed
transport and requires an explicit success terminal; `speechPlayback.js`
schedules at most about two seconds in WebAudio plus one bounded frame, with
backpressure during Pause. `AudioPlayer` owns this resource and keeps it through
the final artifact and History handoff without replaying audio. Seeking and speed
become available after streaming ends, download when the artifact arrives;
manual replay uses that artifact from the beginning unless the user selected a
position, which survives an artifact or metadata that arrives later. Transient
failure never auto-replays a partial answer. Tool/Run
cancellation and component teardown stop playback and abort its request. The
Settings preview uses the same player from its NDJSON `playback` notification.
Mounted coverage: `components/__tests__/AudioPlayer.test.js`.

- The context ring is a button that opens the shared interactive hover card (hover intent, press, keyboard focus, touch; Tab reaches its action, Escape returns to the ring) with Context usage and one `Compact now` action. Ring and card are `components/chat/ContextUsageRing.svelte`, shared with Swarm Activity: the composer places it and wires the Compaction action; Swarm passes `showFigures`, which adds the compact figures (`formatTokens`, `51.2K / 1M · 5%`) beside the ring and to its accessible name (`Context window usage: …`), while the card keeps exact counts (`formatTokensExact`) (`ContextUsageRing.test.js`). During an active Run the action forwards `compact` through `chatState.js` `controlRun`, which the Run applies at its next safe step; without an active Run it submits the server-owned `/compact` command through the ordinary send path, starting a manual Compaction Run. `contextCompactionState` derives availability from server state only: `idle` without an active Run, the running Run's advertised `controls.compaction`, `running` during a manual Compaction Run. Pending requests, in-flight submissions, and running Compaction disable repeat submission and show the requested/compacting labels; the shared card returns keyboard focus to the ring when the action disables itself. Ring/card warning levels come from `tokenUsageTooltip.js::contextLimitWarning` and the displayed Session's effective Compaction Policy (`chat.timeline.compaction_policy`, held as `sessionState.compactionPolicy`; a Policy saved in the Session drawer applies at once through `applySessionCompactionPolicy`, another window's Session invalidation refreshes it through the displayed Session settings row, without re-reading History; an older in-flight History response cannot overwrite that accepted policy). Amber starts 10 percentage points before the automatic trigger (the earlier of `context_ratio` threshold and token cap, or `input_tokens` over the window) and says the threshold is reached at or past it; with automatic Compaction disabled, unknown, or unreachable within the window it warns about the context limit from 70% instead; red from 90%. The numerator is Current Context Usage `tokens`, the same Run-local projection the server trigger evaluates; the denominator is the projection's `context_window`, the window of the route the projected request goes to, which the server trigger uses too. Tool rows receive server-advertised background eligibility and forward `Move to background` through the same controller; no Session-depth policy is inferred in Svelte. Run-control events and sequenced reconnect/RPC snapshots restore these actions, rejecting stale projections (`ChatComposer.test.js`, `ChatAssistantRun.test.js`, `chatState.run-events.test.js`, `chatState.send-and-queue.test.js`). Background Bash terminal-event ingestion is untracked by the View effect so writing the process projection cannot retrigger the same ingestion (`ChatView.runs.test.js`).

Chat shows three distinct server-owned projections: last-step Provider Usage, cumulative Session Usage, and Current Context Usage (restored from History, updated from live/terminal events; badge and card use `tokens` and `context_window`). The card shows no provenance (`estimated`, `~`, Provider anchor or delta): the reported/estimated distinction is rarely of interest and stays reachable in Statistics diagnostics. The frontend formats but never sums, recalculates cost, or infers missing values; cache counts are input subsets and reasoning an output subset. The card counts an unreported counter as zero: the Session hit rate is cache read over total input, and Last turn always lists cache read, cache write and uncached input; Reasoning rows appear when non-zero.

Chat has no top error strip. Run failures appear once in the timeline with full Provider payloads in the existing Details disclosure; terminal failures without an error Message use a timeline fallback until the canonical error event or Run Summary arrives. History, admission/action, command-catalog and stream errors remain visible beside the composer until their owning state clears them.

Errors normalize at the transport boundary, then attach to their Session/Run/Queue operation/toast; command-catalog errors use latest-request-wins. Admission failures never become Run failures, and rendering a failure discards no recoverable history nor leaves a finished Run marked active.
