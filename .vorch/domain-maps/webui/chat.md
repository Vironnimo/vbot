# WebUI Chat

Read this reference only for WebUI Chat selection, Session, history, Run, Queue, timeline, composer, attachment, command, or speech-input work. Backend Chat contracts live in `chat.md` and its task-gated references. As everywhere: these are working notes - the components and their tests remain the truth for rendered behavior.

## Ownership and addressing

Chat admission responses preserve early events from the accepted edited Run and cannot replace a successor already observed live. Authoritative reconnect Queue snapshots invalidate older pending Queue reads. `chat.history` checks active-Run identity around its durable read and freezes the live descriptor before asynchronous projection, preventing an earlier page from being paired with a later idle state. Regression coverage lives in the controller tests and `tests/server/test_rpc_chat_history.py`.

`ChatView.svelte` composes presentation and applies navigation consequences; `createChatController()` in `chatState.js` owns the reactive client projection plus roster/history/activity/command loading, send and Queue workflows, cancellation, and durable-state reconciliation. Presentation components consume projections and forward intents - they never sequence Chat RPCs or rebuild Run state independently. Private View implementations under `components/chat/view/` retain target/Project selection (`target.svelte.js`), Session navigation and parent provenance (`navigation.svelte.js`), action-result presentation (`actions.svelte.js`), and layout/focus/loading feedback (`layout.svelte.js`); the View still constructs the existing Chat controller and forwards server events. Supporting owners: `chatRunStream.js` (one active Run stream), `chatTimeline.js` (renderable timeline items), `ChatActivityPanel.svelte` (presentation-only floating Session-info panel over timeline/Sub-Agent/background-Bash projections). For a displayed derived Session, `ChatView.svelte` resolves the immediate Parent Session from `subagent_parent` first or `fork_source` otherwise, loads its exact list row through the required-Session contract, and gives the panel its display name plus the normal Session-navigation target; unresolved provenance renders no link. `App.svelte` keeps this owner mounted across ordinary main-view navigation (one `serverRecoveryGeneration`); onboarding and confirmed server recovery are the intentional remount boundaries. An Agent address may be global or Project-scoped (`chatState.js::resolveAgentAddressing()` selects the scope; `agentAddress.js::formatAgentAddress()` formats the address); Chat's selected Project context changes active addressing, not the Project managed in `ProjectsView`.

Reflection reviews surface as a dedicated "Reflections" section between Subagent Runs and Bash in the Activity panel, with running reviews first. `chat.history` reads without a cursor restore the source Session's `reflection_runs` (incremental reads carry none and leave an in-flight `chat.reflections` read in place); reconnects refresh the displayed Session through `chat.reflections` without reloading its transcript. `chatState.js` reconciles these snapshots by request generation and preserves newer live events. Server-marked reflection payloads carry `source_session_id`; `chatRunStream.js` delegates its private child/Reflection activity projection to `chatRunStream/activity.js` and WebSocket event normalization to `chatRunStream/serverEvents.js`, maintaining entries from those events, while the durable refresh recovers reviews completed during a disconnect. Rows show scope/status/coarse elapsed time and navigate to the fork Session through ordinary session selection - no sub-agent banner, no cancel control, no unread contribution.

`chatState.js` preserves the public state/controller interface; internal `lib/chatState/` modules own controller orchestration, Session/activity/Queue state, History reconciliation, Run events, streaming compression and Project addressing. `childTasks.js` is the controller's internal child-work lifecycle: bounded status/result caches, exact-work inspection, cancellation races and background-process notifications. It receives the same state and operations; cleanup stays with the controller.

`chatTimeline.js` keeps the public projection interface while internal `lib/chatTimeline/` files own persisted History, live events, ordered child construction and History/live reconciliation. `chatTimelinePresentation.js` keeps its public formatting surface; internal `lib/chatTimelinePresentation/` modules own messages/attachments, Tool rows, child-Run status/result projections, activity and shared time formatting. Both dependency graphs are acyclic; callers continue through the existing public modules.

`SessionListDrawer.svelte` keeps list loading/pagination, filters and selection. Its compact header renders ChatView's shared Session/New/Split controls once, with a direct All agents toggle beside the category filter. Channel Sessions are hidden by default through the persisted `channels` filter and server-side `include_channels`; the required selected Session remains visible. All agents is independent of the category count. Its internal `components/sessions/actions.svelte.js` owns rename, deletion and Compaction Policy edit lifecycles; `menus.svelte.js` owns the row/filter popovers; `presentation.js` holds row labels and timestamps. The shared Session-list API and parent navigation callbacks are unchanged. The list reloads, coalesced, on the full `reloadToken` or when an entry of App's `sessionInvalidations` window names an Agent it lists (read acknowledgements excepted, because the live Chat overlay already shows unread state).

## Selection and Sessions

- `ChatWorkspace.svelte` composes at most two independent Chat/Preview areas. Each retained `ChatView` has its own controller, selected Agent/Project/Session, composer, history viewport, and Run subscription. Closing an area or selecting Preview hides its Chat without cancelling the Run or discarding the draft. The first area retains App/browser-history navigation; the second keeps its selection and child-Session navigation local. Hidden Chat owners reconcile events but do not acknowledge unread completions or request composer focus.
- Area actions are direct icon buttons in Chat's existing floating Session controls and Preview's file toolbar: each area carries the split toggle (Split view when single, Close area when split) and, only once a file was opened in that area, the chat/preview content toggle. `ChatWorkspace` owns focus restoration (closing an area focuses the remaining one) and the portaled file-actions menu; it adds no persistent toolbar, content tabs, duplicate title or focus stripe. Tests cover focus after closing an area and manual content switching with a retained draft.
- Both retained Chat areas enable `preserveSessionSelection` for roster adoption, the first area also while it is alone: shared Agent refreshes update configuration without moving a locally held Session to the backend's last-written pointer. Explicit New Session still updates the initiating area's selection. Deleting a Session releases every area's retained pointer to it: the deleting area re-aims its identity current pointer (or its Project Agent's held Session) to the server's `next_session_id` landing before navigating there, and `ChatWorkspace` forwards the deletion to the other area, which releases and follows passively (no browser-history entry or composer focus). The server's `sessions` deletion event reaches every window: `appController` maps its scope to an App-owned `sessionDeletion` (`agent@projekt` address, deleted id, landing id) and `ChatWorkspace` forwards each new one to every mounted Chat area through the same passive sibling path; a deletion already present when the workspace mounts is ignored. In the deleting window the event and the delete response arrive in either order: when the event came first, the drawer's deletion completes the deliberate parts (browser-history report, composer focus) without reloading the landing (`ChatWorkspace.test.js`, `ChatView.test.project-sessions.test.js`, `appController.test.js`). `ChatWorkspace.test.js` mounts both real Chat owners and verifies addressing, retained drafts, resizing, and preview switching; Chat title ids are instance-specific and composer selectors must be scoped to their area.
- Selecting a Session keeps its area's Session list open. `ChatWorkspace.svelte` restores Session filters from origin-local `localStorage` independently per area through `sessionListView.js`, surviving page reloads and Desktop restarts with the shell's persistent browser profile. A newly mounted second Chat starts with its list closed and uses its saved filters, or copies the first area's latest filters when none were saved, including when first opened from Preview. Changes save immediately and remain area-local across list/area close and reopen; invalid values normalize to defaults and unavailable storage leaves in-memory interaction usable (`ChatWorkspace.test.js`, `sessionListView.test.js`).
- Two areas showing the same addressed Session share one composer owner so Session-scoped draft storage cannot race. The visible first Chat owns input unless only the second Chat is visible; closing/switching areas transfers the composer through the existing draft store. New Session in the duplicate view explicitly creates an independent Session even when the shared Session is empty. A second Chat owner is mounted only when its Chat content is opened, never merely to open an HTML preview.
- HTML file links in Assistant Markdown open the opposite area's Preview; modifier clicks retain browser navigation. `MarkdownContent.svelte` adds a neutral external-browser arrow beside delivered HTML links only; their file actions open on right-click or the keyboard context-menu shortcut, with no additional menu button; `ChatWorkspace.svelte` owns menu navigation, preview opening, and Desktop external-browser dispatch. Download requests the original with `?download=true`; ordinary web links are unchanged. The file link is the user entry point: there is no manual path form or menu entry into an empty Preview; the Show preview button only restores an already opened file. `HtmlPreview.svelte` opens through `file.preview_open`, polls the bounded folder revision serially every 1.5 seconds only while visible with Live enabled, and cleans up requests/timers on replacement or teardown. The iframe has `sandbox="allow-scripts allow-downloads"` without same-origin permission. Only source-checked opaque-frame messages with a URL inside the current capability prefix may update its reload destination; this preserves subpages and allows a deleted/recreated page to recover. Reload replaces the iframe document even when the URL includes a fragment; Retry and explicitly reopening the same file navigate to the entry again. Retired-frame messages cannot redirect the new document (coverage: `HtmlPreview.test.js`). Preview serving/isolation is owned by `server/file_delivery.py` (see `server.md`).

- Display state is override-first: a temporary UI choice leads while a mutation is pending, but Agent/Project/Session state must reconcile to server responses.
- Browser-history Session restoration retires an older navigation after asynchronous Project loading. Project team responses, errors, and loading indicators belong to the latest team request across dropdown switches and history restoration, including revisiting the same Project.
- Session state keys on (Agent address, Session id); switching Agents or Project context never merges histories, Queue items, usage, or active Runs.
- Agent navigation projects status across held Sessions with strict priority `running` -> unread -> idle; selection is a separate accent state. Tooltips add the effective Model as canonical `provider/model` (no `::connection[:account]` suffix) - Identity Agents from `agent.list`, Team members from `project.show`.
- `ChatHeader.svelte` selects personal (Identity) Agents through one picker built on the shared `Dropdown` (`SearchableDropdown` with a filter field above 6 Agents): the trigger shows the selected Agent's name and status dot, options order running, then unread (newest result first), then roster order, and name their status (`Beta: Running`, `Gamma: 2 unread results`). The unread count is the number of the Agent's Sessions with an unread result (`hasUnreadCompletion` plus `unreadRunId`, excluding the displayed Session) from `sessionState.js::agentUnreadResults`. `chat/AgentActivityChips.svelte` adds one chip per other running/unread personal Agent (unread first, then running); it measures chip widths, shows the chips that fit plus a `+N` chip that opens the picker, and collapses to dot-only chips at <=640px. Picker options and chips both call `handleSelectAgent`. The Project Team bar keeps its tabs (`ChatView.svelte`). Coverage: `components/chat/__tests__/ChatHeader.test.js`, `ChatView.test.display-and-commands.test.js`. `connection_ready.active_runs` supplies post-reconnect activity; batched `session.activity_list` supplies durable completion state; `session.list` stays authoritative for the selected Agent's drawer and Project-Agent landings. While the drawer remains open, it overlays Chat's held per-Session Run/activity projection onto those authoritative list rows by complete Agent address plus Session id, so running and unread markers react without another list request. Clicking an unread Agent opens its newest unread Session. Runs with `contributes_to_agent_activity: false` stay out of Agent-level activity and Subagent status maps while their concrete Session row still shows an active Run.
- A completion counts as read only once its exact `run_id` appears in the displayed history or terminal events; the displayed Session leaves unread presentation immediately while its acknowledgement pends, and returns on failure. Retained `latest_completion_run_id` is the reconciliation key - arrival order of replayed terminal events must not flip read state, and an older completion must never clear a newer local result. Completion activity reads (`lib/chatState/activity.js`) are coalesced: at most one `session.activity_list` runs, one pending pass collects the addresses requested meanwhile, and a burst of invalidations waits 100 ms to become one read. Newly displayed Agent addresses are read once; the full `sessionsRefreshToken` or a new connection snapshot re-reads all. From App's `sessionInvalidations` window, a terminal `run_id` whose Run event App still retains (already applied), a `read_run_id` matching the held completion (cleared locally), a deletion (marker dropped) and other Session changes such as create or rename need no read; a terminal `run_id` no longer retained or an unmatched `read_run_id` re-reads that displayed Agent, and an unscoped entry or a window overflow re-reads every displayed Agent. The response omits Sessions without a completion, so an omitted Session is cleared only while its local completion is still the one seen when the read started.
- Loading flags are responsibility-specific (`loadingAgents` only `agent.list`, etc.); background activity loading never resurrects the roster loading surface. Only the newest displayed History request owns the loading state; a pending request for a departed Session or an older request for the same Session cannot keep the composer disabled after the displayed load finishes. New session also keeps the composer disabled until the created Session is displayed, so a message sent during the switch cannot land in the Session being left. Initial History feedback waits 300ms and is keyed to the currently displayed Session, so a fast Agent/Session change stays quiet and a stale destination cannot flash feedback over the new Session.
- Only the latest roster read can publish Agents, selection callbacks or errors. A silent refresh that supersedes initial loading inherits its pending loading/initial History responsibility; ordinary background refreshes keep Chat mounted and skip initial History. A Chat mounted hidden adopts App's shared Agent selection silently on its first display (no navigation report, so a restored override survives), and the controller still loads that Agent's current History unless the pending initial roster load reads it (`loadAdoptedSelectionHistory`). Disposal invalidates pending roster reads (`chatState.test.controller.agent-activity.test.js`).
- History loads newest-first and prepends older pages without moving the reading position. The controller stores `next_before` from each response and sends that opaque cursor for the next older page; falling back to the first public Message id exists only for compatibility with older servers. An older-page response belongs to the loaded History snapshot: a successful full refresh, Run reconciliation, or accepted edit invalidates its result and errors while preserving the replacement cursor for the next request; failed refreshes and other Sessions do not invalidate it. Subsequent History reads use `next_after`; bounded append batches are collected before application and preserve loaded older pages. History Edit, Agent Takeover or generation replacement resets the snapshot. Record sequence identifies occurrences even when public Message ids repeat. A matching canonical Run Summary proves completion; matching stable output ids never prove complete Run coverage. Without terminal persistence, the live terminal projection remains visible.
- A History response mutates only its addressed Session; full refreshes and recovery requests for the same Session share a generation guard and reject snapshots superseded by an accepted edit; a full refresh overtaken by a newer Run rereads History before applying an obsolete active-Run snapshot, and only the newest response for the still-displayed Session may touch global loading/error state or attach the Run stream. These guards belong to the controller, not the View.
- Background-only Sessions: a non-Channel Session whose `run_kinds` are entirely cron/reflection kinds classifies as hidden-by-default, as does every Sub-Agent Session. `SessionListDrawer` sends those category filters to `session.list`, loads 35 globally ordered rows initially and 20 per scroll page, and keeps the selected Session visible through the required-Session contract even when it is old or classified. The **All agents** toggle sends the deduplicated roster in one bounded request; returned rows carry their owning Agent address and the UI routes selection/rename/delete/policy actions through it, using a composite Agent-address-plus-Session-id row identity. The browser never downloads hidden pages or open-ended Session metadata merely to calculate the list or its remaining count. Project Agents have no server current-session pointer: their initial landing requests the newest ordinary Session only, else creates a fresh one; Parent/Sub-Agent navigation requests its exact Session through the same required-Session contract.
- `New Session` is an idempotent intent: an empty displayed Session (no visible history/events/Queue/draft/command card) gets focus instead of a create call; a pending draft makes it non-empty. History loading and in-flight create disable the action. It stays available during an active Run - leaving closes only the local SSE subscription while the server Run continues, and returning reconciles/reattaches it.
- Selecting another same-Agent Session is ordinary navigation; the backend `current_session_id` is a default landing pointer only - no "past" labels, return warnings, or competing Current badges. Cross-owner Sub-Agent navigation highlights the owning Agent and keeps a contextual return banner targeting the immediate Parent.

## Runs, streaming, and recovery

- `ChatReasoning.svelte` owns the shared Reasoning disclosure for live and saved Timeline entries. Structured summaries show a fixed Reasoning summary label, the latest section's optional Markdown heading, and a section count; expansion renders and copies all readable sections. No heading is invented from prose. Summary headers do not display a thinking-duration estimate or completed-step checks. Ordinary commentary and Tool rows retain their own presentation. Unstructured Reasoning, including mixed summary/raw text, uses the existing complete-text fallback. Live compression merges summary fragments only within the same `summary_index`; stable output replaces the draft with persisted sections.

- `createChatRunStream()` owns the EventSource lifecycle, expected sequence, reconnect cursor, heartbeat watchdog, and terminal cleanup for one Run; replacing or leaving the Run tears down everything pending.
- Terminal events settle and close only their matching current Run; late completion from a predecessor remains in its event history without stopping the successor. A delayed start response enriches the same Run without resetting live drafts, controls, or terminal status. Reconnect snapshots cannot downgrade a terminal Run to running (`chatRunStream.test.js`, `chatState.test.controller.test.js`).
- Ordered reducer with a two-second sequence-gap watchdog: an unresolved gap closes SSE and replays from the highest contiguous cursor; a replay head beyond retained history rebases the reducer. Recovery diagnostics log only reason/ids/cursor/attempts/error type - never payloads. A terminal event buffered behind a gap for one second triggers reconciliation from canonical History, so completion never needs a manual reload.
- Streaming deltas are compressed before retention and all ride the ~33 ms flush: text deltas merge per phase, tool argument deltas per (run, tool call, phase), and tool stdout/stderr chunks per (run, tool call, stream). Per-chunk retention made the per-render active-run projection replay quadratic in streamed output size - a multi-MiB bash output froze the whole UI (fixed 2026-08-30). The replay cursor stays correct because every raw delta sequence also lands in `seenStreamingEventKeys`; terminal runs keep streamed stdout/stderr drafts visible until History confirms (same retention set as text drafts).
- The first delivered event of each new subscription is the transport-proven replay head: starting beyond the requested cursor rebases (the prefix left the bounded replay window); later gaps buffer until filled. Duplicates never duplicate timeline items. `provider_heartbeat` stores only its latest seconds-since-delta measurement (rendered as connection metadata, never progress). `stream_attempt_restarted` clears the failed phase's transient deltas, advances the phase, and stays sequence-accounted. A delta's phase follows its sequence position, not arrival order: boundaries (`tool_call_started`, `tool_call_result`, restart) already applied at later sequences - mirrored over the WebSocket while the Session was hidden, before the SSE replay on return - place replayed deltas in their own earlier phase, and a delta whose next applied boundary is a restart is dropped (`streamingEvents.js`; `chatState.test.streaming.test.js`, `chatRunStream.test.reconnect-and-queue.test.js`).
- Displayed Sessions reduce SSE plus mirrored WebSocket events in one contiguous-sequence reducer (either transport fills gaps, duplicates harmless, terminal buffers until complete). Non-displayed Sessions hold no SSE; their sparse stable WebSocket events reduce directly, and opening the Session reloads durable history. When a Run of a Session that the Chat owner neither displays nor holds History for finishes, `chatRunStream.js` releases that Run's retained events (`releaseFinishedRunEvents`) while keeping Run status, unread completion, usage and Queue projections; a bounded per-Session list of released Run ids stops a late `run_started` from reviving it and re-releases late events, so a long-lived tab does not keep every background Run's stable events (`chatRunStream.test.js`). Stable events deduplicate by Run id plus sequence through a key index tied to the current `runEvents` array, rebuilt after any owner replaces that array. Session entries themselves are not evicted: the activity list sync recreates listed Sessions on every refresh, and entries carry client-only reconciliation keys (read completion, History cursors, stream closures). SSE is the only high-volume-delta source; WebSocket stable output is backstop, not competing projection.
- `connection_ready.active_runs` replaces locally projected active Run/Subagent status; excluded Runs still reattach SSE when displayed. A Chat owner mounted after the app connected applies App's live `activeRuns` list instead of the retained snapshot's list and skips App's retained event window (`chatController.startFromServerState`; see `webui/app-shell.md`). If the displayed local Run is absent from reality, reconcile via `chat.history` before clearing (missed terminal -> durable final answer); once History confirms no active Run, discard all retained replay before rendering so sparse fragments cannot reappear behind it.
- Active snapshots preserve server timestamps (`currentRun.startedAt`; Child inspection keeps separate run/session start keys). One visibility-aware adaptive clock feeds elapsed times downward; Unstructured Reasoning headers tick from first delta until the next stable boundary freezes the estimate (`reasoning_timing` replaces it once available).
- Terminal events settle the projection, close the stream and synchronize canonical History for displayed or already-loaded Sessions; failed reads retry through the existing recovery owner. An explicit cancel merges the authoritative `chat.cancel` response events (only while that exact Run is current), promotes undispatched sibling Tool previews to settled-cancelled, and immediately reconciles durable History. When terminal live events overlap not-yet-loaded history, keep the richer history content and overlay live terminal status instead of reverting to a provisional completed state. `run_interrupted` is amber: preserved partial text stays visible, output-less interruptions still get a bare summary row, and no UI control starts another Run.
- The Iteration badge projects only reported numbers: seeded from `active_run`, advanced by each completed Model response regardless of sibling Tool count, settled terminally, restored from `run_summary`; a summary without the field means unknown - omitted, never estimated.
- `subagent_status_changed` is the explicit Parent-cancellation projection: spawn rows settle to cancelled even when the event belongs to a later/non-contributing Parent Run.
- Cancelling a Run and cancelling a cancellable tool call are distinct operations - preserve that in labels, availability, and error handling.
- Pending Run cancellation is keyed by Session and exact Run id. Switching Sessions or starting a successor leaves its Stop control usable; duplicate cancellation requests for the same Run coalesce, and late failures do not overwrite a successor's action state.
- `sendMessage()` and `editMessage()` resolve semantic outcomes after reconciling Session/Run/Queue state; the View snapshots display key and UI generation before awaiting either, then applies navigation/toasts/transient cards and scroll updates only while that generation is current. Edit admission calls `chat.edit`; only after success does the controller remove the targeted User message and later active suffix locally, attach the new Run stream, and clear Current Context Usage until the server refreshes it. Failure preserves the visible lineage unchanged.

`ChatComposer.svelte` keeps draft/History navigation, submission admission and input/keyboard coordination. Internal `components/composer/media.svelte.js` owns per-draft attachments, upload/recording lifetimes and transient feedback; `picker.svelte.js` owns Skill/file/Model triggers, catalogs and picker selection. Both consume current values through local getters; the component retains its public props and the existing admission snapshot semantics. `composer.css` contains the namespaced presentation rules.

## Timeline and Queue

- `visibleTimelineItemsForRender()` is the render boundary; item components display derived items and never reconstruct ordering from raw arrays.
- `appearance.chat_working_mode` is presentation-only: `compact` groups contiguous spans of >=2 visible Reasoning/Tool children into a closed Working disclosure (single children stay inline; Assistant output ends a span). The borderless summary says `working...` only while its group is a running Run's latest activity (latest Tool name allowed, never Reasoning), otherwise `done working`; opening preserves nested details.
- History supplies explicit `history_run_id` attribution. Reconciliation overlays each live Run onto precisely its persisted segment, retaining canonical prefixes absent from bounded replay; User content and neighboring Message roles never determine ownership. Stored Run identities also separate adjacent History groups when a prior terminal summary is missing. Stable Message/Tool-call identity joins individual children, while the server's explicit complete Run descriptor retires its live projection. The History rebuild of a retired Run takes over the timeline ids that view last showed live for that Run and for children matched by Message or Tool-call identity (`chatTimeline/reconciliation.js::keepLiveRunIdentities`, first rebuilt group only), so keyed rendering updates it in place: expanded rows and playing speech survive the handoff. Tool row ids come from the Tool-call key and its occurrence in the Run, not from the event that created the row, so a Run end that drops streamed Tool previews keeps them; History rows merged into an active Run use their own id namespace (`chatTimeline/runChildren.js`, `mergeRun`). Manual Compaction follows the same completion contract. Starting a successor preserves unfinished terminal drafts until this reconciliation. A standalone Compaction Run (only compaction events) dissolves at the render boundary into its bare separator - no run header or footer - so both triggers render the checkpoint identically; failed or cancelled runs keep their (empty) block so the failure status stays visible, and an in-run auto Compaction never dissolves because its Run carries output/tool children. During an active Run, `compaction_started` inserts one amber in-progress divider; completion swaps in the completed label, abort/terminal removes the placeholder. The completed label carries the Compaction duration ("Context compacted in 45s") - both triggers stamp the observed wall-clock time as `compaction_duration_ms` into the checkpoint Usage at completion - and abbreviates token counts (254224 -> "254k", no unit word). Manual `/compact` is a server-owned Run entering the same path - the WebUI synthesizes no local Compaction state; its terminal event uses the same incremental History synchronization as other Runs. Completed checkpoints render their exact string content in a whitespace-preserving disclosure (no trimming, Markdown, or HTML interpretation) and store tokens in Usage so History reconstructs identically. History reconstruction preserves terminal semantics from summaries: cancelled settles open Tools/Sub-Agents as cancelled; interrupted drops preparing previews once stable interrupted output proves the call was discarded. Only the latest visible streaming child of a running Run may carry the working caret.
- A Run without a visible User anchor reconciles its persisted Assistant/Tool/checkpoint segment with live children by Message and Tool-call identity, preserving the prefix absent from bounded replay and retaining new text, Reasoning, Tool activity, and stdout/stderr. Fresh text phases never overwrite finalized answers. Retained older Run groups absent from the loaded page are inserted chronologically before the tracked turn rather than appended behind it; persisted History order and live User/Assistant pairing remain intact. Error-message overlap is deduplicated against the final selected timeline, so an error stays visible once whether its History row or live row supplies it. Regression coverage lives in `chatState.test.history-reconciliation.test.js`, `chatState.test.controller.test.js`, and the mounted `ChatTimeline.test.live-runs.test.js` suite.
- Transient command cards (`/status`, `/help`) are non-persisted and anchor to the timeline item they followed at creation. A history reload can replace its anchor's live id with a history id (a retired Run this view showed live keeps its id, its User message item does not), so the card then re-anchors by creation time - after the last item whose timestamp predates the command - instead of sinking below newer messages; cards created on an empty timeline stay at the top, and cards without a creation time keep the end-of-timeline fallback (`groupTransientCards` in `chatTimelinePresentation.js`).
- Expanded Tool details render `read` and `analyze_image` thumbnails from server-projected original-file URLs in display image references; stored remote media such as `web_fetch` uses `read_media` result artifacts. `chatToolDetails.js` accepts bounded opaque Attachment basenames (including current `att_` ids) or signed `/api/files/` URLs, never raw local paths or external URLs. Both ordinary Run rows and standalone Tool events share this selection; thumbnails open the existing Timeline lightbox by pointer or keyboard, retain modifier-click navigation, and reconstruct from History. Original-file URLs include server-observed revisions (see `server.md`); thumbnails key by the entire URL so a refreshed revision replaces both decoded images and prior failed-image state. Missing/unloadable images show a visible icon and localized unavailable label in thumbnails and the lightbox. Coverage: `ChatTimeline.test.tool-summaries.test.js`. Older `analyze_image` calls without original-path preview references have no thumbnails.
- `search_files` rows consume Tool-owned argument-vector display parts and preserve result warnings/continuation in details. Fallback labels support current `args` arrays and historical pattern/root arguments; historical grep/glob rows remain readable.
- Preparing Tool rows derive safe preview arguments from completed top-level string fields only; stable arguments replace them at `tool_call_started`. Expanded details decode an outer payload once and render Args/Stdout/Stderr/Result as ordered sections preserving types (objects -> key/value fields, arrays unwrapped per line, explicit empties shown, CR/LF visible, escape sequences literal); Copy uses the exact sanitized representation.
- Tool rows consume the structured display snapshot before the narrow historical fallback: single-line order dot/name, primary values, typed facts, status/duration, actions; the 64-character semantic budget governs paths/prose/URL ends; quick tooltips cover non-copyable full values while copyable ones use the shared card (hover dwell 500 ms, focus/touch immediate, Tab enters its Copy action) rendered by `chat/ToolPrimaryLine.svelte`. A successful envelope with `data.status: "partial"` renders as a settled amber partial state, distinct from both green success and red failure. Unknown Tools never leak raw arguments into the collapsed row.
- The special Sub-Agent row belongs only to `subagent` action `run` (navigation/progress/cancel); other actions render as ordinary rows. Results expose the stable public id only; internal handles arrive solely via live `subagent_session_started` events for accessor use, and `chatState.js` resolves public ids through `subagent.inspect` with bounded caches - Timeline components render supplied state and start no recovery requests. Legacy transcripts without work ids fall back conservatively through exact-Run history matching. Row addressing accepts current results whose `agent_id` is already `agent@project`, historical results with a bare `agent_id` beside `project_id`, and bare live start events: `agentAddress.js::qualifyAgentAddress` yields one address without double qualification (`chatTimelinePresentation.test.subagent-work.test.js`). Session-scoped status keys (`session:`/`sessionStarted:`/`sessionDuration:`/`sessionTool:`), which rows without a resolvable run id read, use that same address as their only form - `agent@project` for a Project child, bare for an Identity child. Every writer produces it: Run events (addressed at ingestion for both WebSocket and SSE, `chatState/runEvents.js::normalizeRunEvent`), connection snapshots, explicit `subagent_status_changed` data, and inspection (`chatRunStream.test.child-activity.test.js`, `chatState.test.controller.child-work.test.js`).
- Cancellable background Bash/Sub-Agent rows use shared icon buttons with immediate pending state; a finished Sub-Agent keeps its neutral navigation control. A handed-off Bash row tracks its process, not the ~instant delegation call: the dot shows running and the time label ticks from the Tool call's internal start timestamp until a terminal status arrives (`bash_process_status_changed` live event or the durable `background_bash_statuses` fold), then the dot settles and the label becomes the process's real runtime measured by the terminal notification; without known times the label stays empty rather than showing the ~0s delegation duration, and the expanded Result section swaps the handoff envelope for the actual completion result on the same terminal data. Live terminal data is a bounded in-memory projection keyed by process id, so after a full page reload terminal rows settle from History without a runtime.
- The floating Activity panel lists automatic-delivery Sub-Agent spawns and handed-off Bash processes from the loaded Session only; foreground/synchronous work stays Timeline-only. Background process rows deduplicate by process id while retained live Runs overlap History, keeping the latest projection so opening the panel cannot fail on duplicate keyed rows (`ChatActivityPanel.test.js`). Rows group by Subagent Runs, Reflections, and Bash, with running work first within each category. Subagent rows include task previews and keep Session navigation after completion; active Subagent and Bash rows additionally carry cancel controls delegating through the controller (Bash via `chat.cancel_process`, an explicit user cancellation). Bash starts collapsed when Subagent or Reflection work exists, with its running count visible in the disclosure; Bash rows carry the same tick/runtime time label as their Timeline row, and the panel's clock runs only while it is open and something is actually running (the clock effect depends on a value-stable flag, never on the ticking task lists - otherwise Svelte reports `effect_update_depth_exceeded`). `chat.history.background_bash_statuses` folds durable results by Process Session id so rows survive reload; switching Agent/Session swaps projections immediately; terminal `bash_process_status_changed` events merge into a global bounded projection keyed by process id that wins over the durable string statuses.
- Copy actions preserve semantic boundaries rather than copying rendered DOM: Assistant copies join that Run's Markdown sections, user copy reconstructs mentions minus binaries, reasoning/output copy independently, Tool copy uses the sanitized displayed value. `MarkdownContent.svelte` is the safe-Markdown owner (shared CopyButton in fenced-code headers, withheld while streaming incomplete); complete HTTP(S) URLs become safe new-tab links in Assistant Markdown and escaped user plaintext, everything else inert. The Reasoning-only normalizer strips Provider HTML-comment separators and splits adjacent bold blocks without touching canonical content.
- Public History marks only server-approved plain-text WebUI User messages as `editable`; structured/Channel messages and messages before the latest Agent Takeover never expose the action. `ChatTimelineEntry` swaps the message body for an inline editor with explicit cancel and `Save & restart`; edit is disabled while History loads, a Run is active, or the Queue is non-empty. The hint describes removal from the active conversation, not deletion from storage.
- Assistant file delivery arrives pre-projected as relative `/api/files/` URLs (images inline/lightbox, others as links). Non-image links carry the canonical server path in an escaped Markdown title; `MarkdownContent.svelte` replaces that native title with the shared hover/focus tooltip and marks delivered links for `ChatWorkspace`'s context menu. All delivered file links offer browser opening/download and, when a path is supplied, Copy file path; only HTML links offer Preview. Copy uses the Desktop clipboard bridge or browser clipboard and reports success/failure through the shared toast. The WebUI displays/copies the supplied path without resolving it or decoding capabilities, and never sees `output_files` metadata. Coverage: `MarkdownContent.test.js`, `ChatWorkspace.test.js`.
- The server owns Queue order, contents, and `editable`. Optimistic continuity is allowed, but `syncQueueFromServer()` is authoritative and applies only the newest outstanding response per Session. Accepted Queue edits, removals, and queued admissions retire earlier pending Queue reads so stale snapshots cannot undo the mutation. Complete raw-text items expose the editor; structured/attached inputs remain non-editable. `QueuedMessages.svelte` renders compact single-line rows with Steer and icon actions. A shared floating hover card shows the entire text on pointer hover or keyboard focus and scrolls long content. Opening an editor (preview click or pencil) focuses its textarea; while another item's editor holds a modified draft, the request keeps that editor open and focused with a save-or-cancel notice instead of discarding the draft (edits save only through explicit Save; `QueuedMessages.test.js`). Queue updates report semantic success and close only then; failures preserve input.
- `connection_ready.queues` authoritatively replaces every held Session's Queue projection (including clearing scopes missing from the snapshot); on `epoch_changed`, locally known ids absent from the new process trigger a restart-loss notice, while same-process gaps reconcile silently.
- Steer targets the exact active Run through the existing controller/API owner and reconciles the authoritative Queue afterward. Pending items show "Steering..." until persistence; `user_message_persisted.queue_item_id` retires them and suppresses older Queue snapshots. Timeline projections retain additional User messages as ordered children of the same Assistant Run, live, after partial History reconciliation, and after reload (`chatTimeline.test.steering.test.js`). They render through the shared `ChatTimelineEntry`; role styles in `app/chat-content.css` target each Message's own header/body so an enclosing Assistant Run cannot override User padding, line height, or colors. Nested User entries cancel the Run-content indent and duplicate horizontal padding to retain ordinary User alignment (`ChatTimeline.test.live-runs.test.js`).
- Queue invalidation addresses exactly its Agent/Session - switching Sessions never shows another's queued items.
- The timeline is the only scrolling surface, coordinated by `createChatScrollController()`: per-Session pinned flag plus reading anchor (item id + offset), one writer recording expected positions (its echo never reclassifies ownership), user motion classified from live position, upward input releasing the pin before the browser scrolls. Bottom growth never moves reading position; growth above the anchor corrects once through it. Navigation restores saved viewports, explicit Sub-Agent links open pinned at bottom, sending pins to the bottom so the incoming response is always visible, and Jump-to-latest appears only away from the live tail.
- The composer floats as an absolutely positioned overlay over the full-height timeline: its measured height reaches the timeline via `--chat-overlay-height`, the overlay ends before the scrollbar column (`--chat-scrollbar-width`), and reserved space is a trailing in-flow block (Chromium drops bottom padding/margin from scroll extent) - autosizing therefore never changes content geometry.

## Composer and inputs

`ComputerUseControl.svelte` owns contextual Computer Use stop/resume buttons inserted through ChatComposer's existing action slot by ChatView. It discovers the loaded Extension and polls its management operation; availability alone renders nothing. Ongoing control remains visible between Tool calls, and a latched stop exposes explicit recovery. Mutation generations reject stale status/resume responses, resume forwards the current stop token, and Stop remains reachable during resume. Mutation errors use Chat's existing toast. Native double-Esc and the persisted interlock belong to the Extension (see `extensions/computer-use.md`), not browser key listeners.

- `ChatComposer.svelte` owns draft entry and delegates parsing/media to established helpers; every submission variant uses the same resolved address.
- Submission serializes from an initial snapshot (text, origin, attachments, callbacks) through file-mention resolution and admission; only a confirmed successful outcome clears draft and attachments - failures and mid-flight additions stay editable. No-argument immediate Commands enter the same guarded path.
- Setup guidance is prerequisite-ordered: missing Provider routes to Settings -> Providers before model-less-Agent guidance routes to Agents; readiness is never inferred from the Model catalog, and neither prompt shows while Settings are unresolved.
- Slash Commands and Skills come from the server catalog submitted through the command contract - no competing frontend roster or backend-semantics interpretation. Catalog loading guards on Agent address plus the App-owned refresh token, so Extension lifecycle changes refresh autocomplete without disturbing selection or draft.
- File mentions constrain to the server-provided list for the active address. `fileMentions.js` owns the mention grammar: bare `@path` tokens accept letters/digits in any script plus `_ . / \ -`; every other listed path is written as `@"path"` (`\"`/`\\` escapes). The picker and user-message copy write tokens through `formatMentionToken`, so every listed path round-trips into `file_mentions`; a mid-word `@` (e-mail) is never a mention. Attachment ids stay opaque with safe server URLs for preview/download. Image cards render their persisted Session reference (for example, `Image 1`) as the normal label and retain the original upload filename only as hover detail, matching the Model-facing reference.
- The `/model ` autocomplete opens on demand (catalog fetched only when triggered), reuses the Agent-dropdown suitability filter and show-all toggle, auto-submits the selection through the guarded path, and shares one keyboard contract with the skill/file popups. Enter/Tab selects only the visibly active row; if a list change leaves the active index out of range, selection returns false instead of falling back to an unmarked first row. While an open `@` or `/model` picker is still loading and has no row to select, Enter is consumed instead of sending the partial token (`ChatComposer.test.js`).
- Speech input releases every media resource (tracks, recorder, timers, object URLs) on completion, cancellation, replacement, teardown, and failure - cleanup best effort across failing tracks. Changing the displayed Session or tearing down the composer cancels capture, aborts pending transcription, and rejects late audio, progress, transcript and error results so speech cannot enter another Session's draft. A pending browser microphone permission request cannot be aborted, so cancellation invalidates it and a late recorder result must release its tracks without starting capture. The native recorder container uploads as-is; `SpeechService` converts to the server-wide Voice -> Transcription profile, so Chat and wakeword capture share one Provider-facing audio policy.
- Drafts and completed pending Attachments are interaction state keyed by the full displayed Session address; refresh or selection transitions never silently submit or cross-address either. A pending Attachment becomes Model-visible only when that Session's send is admitted. `composerMemory.js` shares drafts, pending Attachments and per-Agent send history across browser tabs through origin `localStorage`: a tab persists only the keys it changed (history per sent message), merged into the currently stored maps with the same caps, and adopts other tabs' writes from the `storage` event, so tabs neither erase nor resurrect each other's entries (`composerMemory.test.js`).
- Chat microphone uploads opt into the speech endpoint's NDJSON progress stream.
  `api.js` delivers phase snapshots before the terminal transcript and rejects an
  interrupted stream or missing heartbeats without automatically resubmitting
  audio. `ChatComposer` shows the server phase and elapsed time beside a spinner
  above the composer; its microphone tooltip uses a wrapper so it remains
  accessible while the button is disabled. Completion and errors clear busy
  state; teardown invalidates late progress/results. Coverage: composer/API tests.
- Composer focus follows deliberate navigation only (New Session always; user-driven selections after destination history settles, desktop only; mobile stays in reading mode with `preventScroll`) - passive changes (reconnects, invalidations, mount restoration) never steal focus.

Request status is footer metadata on a running Assistant Run: retry causes and available attempt counts appear immediately; ordinary request waits and Provider heartbeats stay quiet until 60 seconds without Model output. Request waits use the shared live clock, while heartbeats use the server-reported idle measurement. Actual Provider progress replaces the notice; terminal Runs hide it. This projection is shared by Chat and embedded Swarm Activity. Failed Compaction attempts keep a visible warning separator without marking an otherwise continuing Agentic Run failed; harmless stale/insufficient-reclaim attempts remove their placeholder. These diagnostics remain live-event projections, not persisted checkpoints (`chatTimeline/live.js`, `chatTimelinePresentation/activity.js`, `ChatTimeline.test.layout-history-attachments.test.js`).

## Usage and errors

Speech Tool artifacts in `ChatAssistantRun.svelte` and `ChatTimelineEntry.svelte`
use `components/ui/AudioPlayer.svelte`, also used by the Settings preview. It
owns media state, seeking, speed, volume, download, playback errors and resource
cleanup. A successful `text_to_speech` result shows the player whether its Tool
result envelope is a live event object or the persisted Tool message's JSON text
from Session history (`chatTimelinePresentation/messages.js`). Only a live Run
projection (`item.source === 'live'`) requests one automatic start per source;
a player first mounted for a Run rebuilt from Session history stays paused. The
player latches that request when a source is attached and ignores re-renders
with an equal source, so a player that survives the live-to-History handoff
keeps playing (or still starts) without reloading. Later `canplay` events must
not undo Pause. Starting another shared player pauses the previous one.
Mounted coverage: `components/__tests__/AudioPlayer.test.js`.

- The context ring is a button that opens the shared interactive hover card (hover intent, press, keyboard focus, touch; Tab reaches its action, Escape returns to the ring) with Context usage and one `Compact now` action. During an active Run the action forwards `compact` through `chatState.js` `controlRun`, which the Run applies at its next safe step; without an active Run it submits the server-owned `/compact` command through the ordinary send path, starting a manual Compaction Run. `contextCompactionState` derives availability from server state only: `idle` without an active Run, the running Run's advertised `controls.compaction`, `running` during a manual Compaction Run. Pending requests, in-flight submissions, and running Compaction disable repeat submission and show the requested/compacting labels; the shared card returns keyboard focus to the ring when the action disables itself. Ring/card warning levels come from `tokenUsageTooltip.js::contextLimitWarning` and the displayed Session's effective Compaction Policy (`chat.history.compaction_policy`, held as `sessionState.compactionPolicy`; a Policy saved in the Session drawer applies at once through `applySessionCompactionPolicy`, other Policy changes arrive with the next History read). Amber starts 10 percentage points before the automatic trigger (the earlier of `context_ratio` threshold and token cap, or `input_tokens` over the window) and says the threshold is reached at or past it; with automatic Compaction disabled, unknown, or unreachable within the window it warns about the context limit from 70% instead; red from 90%. The numerator is Current Context Usage `tokens`, the same Run-local projection the server trigger evaluates; the denominator is the Agent payload's resolved window for its primary Model, so a fallback target's different window can shift the server's actual trigger point. Tool rows receive server-advertised background eligibility and forward `Move to background` through the same controller; no Session-depth policy is inferred in Svelte. Run-control events and sequenced reconnect/RPC snapshots restore these actions, rejecting stale projections (`ChatComposer.test.js`, `ChatAssistantRun.test.js`, `chatState.test.controller.test.js`). Background Bash terminal-event ingestion is untracked by the View effect so writing the process projection cannot retrigger the same ingestion (`ChatView.test.streaming-and-history.test.js`).

Chat shows three distinct server-owned projections: last-step Provider Usage, cumulative Session Usage, and Current Context Usage (restored from History, updated from live/terminal events; badge uses `{tokens, estimated}`, tooltip exposes provenance). The frontend formats but never sums, recalculates cost, or infers missing values; cache counts are input subsets, provider-reported reasoning an output subset, absent counters stay absent, and `reasoning_turns` distinguishes no-reporting from zero.

Chat has no top error strip. Run failures appear once in the timeline with full Provider payloads in the existing Details disclosure; terminal failures without an error Message use a timeline fallback until the canonical error event or Run Summary arrives. History, admission/action, command-catalog and stream errors remain visible beside the composer until their owning state clears them.

Errors normalize at the transport boundary, then attach to their Session/Run/Queue operation/toast; command-catalog errors use latest-request-wins. Admission failures never become Run failures, and rendering a failure discards no recoverable history nor leaves a finished Run marked active.
