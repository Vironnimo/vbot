# WebUI Chat

Read this reference only for WebUI Chat selection, Session, history, Run, Queue, timeline, composer, attachment, command, or speech-input work. Backend Chat contracts live in `chat.md` and its task-gated references. As everywhere: these are working notes - the components and their tests remain the truth for rendered behavior.

## Ownership and addressing

Chat admission responses preserve early events from the accepted edited Run and cannot replace a successor already observed live. Authoritative reconnect Queue snapshots invalidate older pending Queue reads. `chat.history` checks active-Run identity around its durable read and freezes the live descriptor before asynchronous projection, preventing an earlier page from being paired with a later idle state. Regression coverage lives in `chatState.send-and-queue.test.js` and `tests/server/rpc/test_chat_methods_history.py`.

`ChatView.svelte` composes presentation and applies navigation consequences; `createChatController()` in `chatState.js` owns the reactive client projection plus roster/history/activity/command loading, send and Queue workflows, cancellation, and durable-state reconciliation. Presentation components consume projections and forward intents - they never sequence Chat RPCs or rebuild Run state independently. Private View implementations under `components/chat/view/` retain target/Project selection (`target.svelte.js`), Session navigation and parent provenance (`navigation.svelte.js`), action-result presentation (`actions.svelte.js`), layout/focus/loading feedback (`layout.svelte.js`), and the composer footer's Session settings (`sessionSettings.svelte.js`); the View still constructs the existing Chat controller and forwards server events. Supporting owners: `chatRunStream.js` (one active Run stream plus predecessor completion reconciliation), `chatTimeline.js` (renderable timeline items), `ChatActivityPanel.svelte` (presentation-only floating Session-info panel over timeline/Sub-Agent/background-command projections). For a displayed derived Session, `ChatView.svelte` resolves the immediate Parent Session from `subagent_parent` first or `fork_source` otherwise, loads its exact list row through the required-Session contract, and gives the panel its display name plus the normal Session-navigation target; unresolved provenance renders no link. `App.svelte` keeps this owner mounted across ordinary main-view navigation (one `serverRecoveryGeneration`); onboarding and confirmed server recovery are the intentional remount boundaries. An Agent address may be global or Project-scoped (`chatState.js::resolveAgentAddressing()` selects the scope; `agentAddress.js::formatAgentAddress()` formats the address); Chat's selected Project context changes active addressing, not the Project managed in `ProjectsView`.

Reflection reviews appear in the Activity panel's Running and Finished sections alongside Sub-Agents and commands. `chat.history` reads without a cursor restore the source Session's `reflection_runs` (incremental reads carry none and leave an in-flight `chat.reflections` read in place); reconnects refresh the displayed Session through `chat.reflections` without reloading its transcript. `chatState.js` reconciles these snapshots by request generation and preserves newer live events. Server-marked reflection payloads carry `source_session_id`; `chatRunStream.js` delegates its private child/Reflection activity projection to `chatRunStream/activity.js` and WebSocket event normalization to `chatRunStream/serverEvents.js`, maintaining entries from those events, while the durable refresh recovers reviews completed during a disconnect. Rows show scope as their title (`Memory reflection`, `Skill reflection`, `Memory & skill reflection`; user-facing text says Reflection, never review - user requirement) and status plus coarse elapsed time or outcome on their second line, and navigate to the fork Session through ordinary session selection - no sub-agent banner, no cancel control, no unread contribution.

A finished review row with an `outcome` adds one quiet line (user requirement: background learning stays quiet - no toasts - and every change is traceable and reversible in one step): `2 Memory entries, 1 Skill changed`, `Nothing saved`, or `Reflection undone`. A review that changed something opens from that line (`aria-expanded`) to its change list (`learning.changes`, read again on every opening): per change what happened, the Memory scope or Skill name, and the entry text or files; undone changes are struck through. `Undo reflection` asks inline (`Undo every change of this reflection?`, Undo/Keep) and then calls `learning.undo`; the result updates the row's outcome and list, and a refusal stays inline under the list, worded from `error.data` (which entry or Skill, who changed it later and when); other failures show the server message and read the review again; reopening the list drops an earlier refusal. Live, `chatRunStream/activity.js` reports a review's first terminal event (`onReflectionFinished`), and ChatView rereads that source Session's reviews through `chat.reflections`, displayed or not, so the row gains its outcome. The controller's internal `lib/chatState/reflections.js` owns the row restore, the outcome, the change list and the undo; lists and undo state live in `reflectionDetails` beside `reflectionTasks`, so a row refresh keeps an open list. `lib/chatTimelinePresentation/reflections.js` words rows, outcomes, changes and refusals. Coverage: `ChatActivityPanel.test.js`, `chatState.child-work.test.js`, `chatRunStream.child-activity.test.js`, `chatTimelinePresentation.activity.test.js`.

`chatState.js` preserves the public state/controller interface; internal `lib/chatState/` modules own controller orchestration, Session/activity/Queue state, History reconciliation, Run events, streaming compression and Project addressing. `childTasks.js` is the controller's internal child-work lifecycle: the bounded Sub-Agent status cache, exact-work inspection, Sub-Agent cancellation, live handed-off command statuses and stopping a handed-off command. It receives the same state and operations; cleanup stays with the controller.

`chatTimeline.js` keeps the public projection interface while internal `lib/chatTimeline/` files own persisted History, live events, ordered child construction and History/live reconciliation. `chatTimelinePresentation.js` keeps its public formatting surface; internal `lib/chatTimelinePresentation/` modules own messages/attachments, Tool rows, child-Run status projections, activity, change statistics and shared time formatting. Both dependency graphs are acyclic; callers continue through the existing public modules.

`SessionListDrawer.svelte` keeps list loading/pagination, filters and selection. Its header names the listed scope (the selected Agent's name, or All agents) beside a direct All agents toggle and the category filter. Opened from the Agent bar's Session-list toggle, it docks left of the Chat surface and pushes it aside; in a Chat area narrower than 720px (container `chat-area` on `.chat-view__content-shell`) it overlays the Chat instead. It stays open until the toggle closes it. A row's running or unread dot sits before its title. Channel Sessions are hidden by default through the persisted `channels` filter and server-side `include_channels`; the required selected Session remains visible. All agents is independent of the category count. Its internal `components/sessions/actions.svelte.js` owns rename, deletion (with the delete dialog's Archive option, `webui/archive.md` -> Delete dialogs) and Compaction Policy edit lifecycles; `menus.svelte.js` owns the row/filter popovers; `presentation.js` holds row labels and timestamps. Mutations and their parent callbacks retain the original Session target, but completion refreshes the drawer's current Agent/filter scope, including after navigation while a mutation was pending (`SessionListDrawer.actions.test.js`). The shared Session-list API and parent navigation callbacks are unchanged. The list reloads, coalesced, on the full `reloadToken` or when an entry of App's `sessionInvalidations` window names an Agent it lists (read acknowledgements excepted, because the live Chat overlay already shows unread state).

## Selection and Sessions

- `ChatWorkspace.svelte` composes at most two independent Chat/Preview areas. Each retained `ChatView` has its own controller, selected Agent/Project/Session, composer, history viewport, and Run subscription. Closing an area or selecting Preview hides its Chat without cancelling the Run or discarding the draft. The first area's shown Session is Chat's place in App navigation; the second keeps its selection and child-Session navigation local and out of history. Both areas accept the same child-link target object (`{agentId, sessionId}`), open the child at the live tail, and retain its Parent return. Hidden Chat owners reconcile events but do not acknowledge unread completions or request composer focus.
- Area actions are direct icon buttons at the right end of Chat's Agent bar (`ChatHeader` `actions` snippet, class `chat-header__action`) and in Preview's file toolbar: each area carries the split toggle (Split view when single, Close area when split) and, only once a file was opened in that area, the chat/preview content toggle. `ChatWorkspace` owns focus restoration (closing an area focuses the remaining one) and the portaled file-actions menu; it adds no persistent toolbar, content tabs, duplicate title or focus stripe. Tests cover focus after closing an area and manual content switching with a retained draft.
- **Open in split view:** context menus (right click, ContextMenu key or Shift+F10, shared `ContextMenu`) offer to show a target in the workspace's other area: Session list rows (first item of the row menu), Agent bar tabs, Sub-Agent rows of the Activity panel, Sub-Agent session links in the Timeline, and the Agents view's row menu. The item reads Open in split view while one area shows and Open in other area once both do; it opens the split view when it is closed, and a request from the Agents view opens beside the area shown now (or in the second area when both show). `ChatWorkspace::openInOtherArea` hands the target (`{agentAddress, sessionId?, subAgent?}`) to the other area's `ChatView` as `openRequest`, which applies it once that area is active and has its roster, exactly like a choice in its own Session list (`handleSessionSelected`, including the Sub-Agent banner) or Agent bar (`handleSelectPickerAgent`); so in the first area it is a history step, in the second it stays local. A second area created for an Identity Agent starts on that Agent instead of copying the first area's selection. App drops an Agents-view request whose switch to Chat did not happen before another view was shown (`ChatWorkspace.test.js`, `AgentsView.test.js`).
- Both retained Chat areas enable `preserveSessionSelection` for roster adoption, the first area also while it is alone: shared Agent refreshes update configuration without moving a locally held Session to the backend's last-written pointer. This also keeps an area's draft: `sessionState.js::setAgents` with `preserveSessionSelection` keeps an empty local Identity pointer. Explicit New Session and a draft's created Session still update the initiating area's selection. Deleting a Session releases every area's retained pointer to it: the deleting area re-aims its identity current pointer (or its Project Agent's held Session) to the server's `next_session_id` landing before navigating there (a null landing empties the pointer, and the owning Agent shows its draft), and `ChatWorkspace` forwards the deletion to the other area, which releases and follows passively (no composer focus). The server's `sessions` deletion event reaches every window: `appController` maps its scope to an App-owned `sessionDeletion` (`agent@projekt` address, deleted id, landing id) and `ChatWorkspace` forwards each new one to every mounted Chat area through the same passive sibling path; a deletion already present when the workspace mounts is ignored. In the deleting window the event and the delete response arrive in either order: when the event came first, the drawer's deletion completes the deliberate part (composer focus) without reloading the landing; in every area the deleted Session's history entry is corrected to its landing, never a new step (`ChatWorkspace.test.js`, `ChatView.projects.test.js`, `appController.test.js`). `ChatWorkspace.test.js` mounts both real Chat owners and verifies addressing, retained drafts, resizing, and preview switching; Chat title ids are instance-specific and composer selectors must be scoped to their area.
- Selecting a Session keeps its area's Session list open. `ChatWorkspace.svelte` restores Session filters from origin-local `localStorage` independently per area through `sessionListView.js`, surviving page reloads and Desktop restarts with the shell's persistent browser profile. A newly mounted second Chat starts with its list closed and uses its saved filters, or copies the first area's latest filters when none were saved, including when first opened from Preview. Changes save immediately and remain area-local across list/area close and reopen; invalid values normalize to defaults and unavailable storage leaves in-memory interaction usable (`ChatWorkspace.test.js`, `sessionListView.test.js`).
- **Identity Agent rename:** App's `onAgentIdChanged` first moves composer memory (`composerMemory.js::renameComposerAgent`: drafts and attachments keyed `<old>::...`, including unsaved draft keys, and the send history; every tab applies it and the next merge persists it), then `selection.remapIdentityAgentId` calls every `subscribeAgentRenames` listener synchronously before it remaps the shared selection, then App remaps navigation (`webui/app-shell.md` -> Navigation). `ChatWorkspace` remaps the second area's Agent and both areas' displayed Sessions; each `ChatView` re-keys its own state (`renameAgent`): controller Sessions and roster entry (`sessionState.js::renameAgentInState`), Session settings drafts, transient cards and the viewed Sub-Agent address, and it reads the shown Session's History again under the new id. History, Queue and reflection reads still in flight for the old key are superseded (`supersedeRenamedSessionKey`), so they cannot land on the renamed Session; its Run stream closes, since a rename admits no active Run. The second area's pending child-Session navigation is not remapped, because it was already handled (`ChatView.sessions.test.js`, `ChatWorkspace.test.js`, `chatState.history-loading.test.js`, `composerMemory.test.js`, `selection.test.js`).
- Two areas showing the same addressed Session share one composer owner so Session-scoped draft storage cannot race. The visible first Chat owns input unless only the second Chat is visible; closing/switching areas transfers the composer through the existing draft store. New Session in the duplicate view shows that area's own draft even when the shared Session is empty. A second Chat owner is mounted only when its Chat content is opened, never merely to open an HTML preview.
- HTML file links in Assistant Markdown open the opposite area's Preview; modifier clicks retain browser navigation. `MarkdownContent.svelte` adds a neutral external-browser arrow beside delivered HTML links only; their file actions open on right-click or the keyboard context-menu shortcut, with no additional menu button; `ChatWorkspace.svelte` owns menu navigation, preview opening, and Desktop external-browser dispatch. Download requests the original with `?download=true`; ordinary web links are unchanged. The file link is the user entry point: there is no manual path form or menu entry into an empty Preview; the Show preview button only restores an already opened file. `HtmlPreview.svelte` opens through `file.preview_open`, polls the bounded folder revision serially every 1.5 seconds only while visible with Live enabled, and cleans up requests/timers on replacement or teardown. The iframe has `sandbox="allow-scripts allow-downloads"` without same-origin permission. Only source-checked opaque-frame messages with a URL inside the current capability prefix may update its reload destination; this preserves subpages and allows a deleted/recreated page to recover. Reload replaces the iframe document even when the URL includes a fragment; Retry and explicitly reopening the same file navigate to the entry again. Retired-frame messages cannot redirect the new document (coverage: `HtmlPreview.test.js`). Preview serving/isolation is owned by `server/file_delivery.py` (see `server.md`).

- Display state is override-first: a temporary UI choice leads while a mutation is pending, but Agent/Project/Session state must reconcile to server responses.
- **History places** (`webui/app-shell.md` -> Navigation): the first area's place names the Session it shows, `[agentAddress, sessionId]` with `extra` `{selection, subAgent}`, or only `[agentAddress]` for a draft (reported with an empty `sessionId`). `chat/view/navigation.svelte.js` reports every change of the shown Session (the viewed override, else the active Agent's own current Session or draft) to App through `onSessionNavigation(session, {replace})`. Changes made inside a user action wrapped in `asStep` - choosing an Agent, Project, Project Agent or Session, New Session, the parent link, Return to current - become a history step; every other change (a restore, a load resolving the Session, a deletion landing, a Session moved by `/agent`, a draft's created Session, the passive follow of the shared Agent selection) corrects the current entry. App restores a place without a Session as `{agentId, draft: true}`: it shows the draft again when that Agent is the area's active own Agent, otherwise it returns to the current view like `returnToCurrent`. While Chat is hidden a report corrects the place Chat returns to. App-driven Locations (Back/Forward, deep links, the main navigation, sub-agent links) arrive as `pendingSessionNavigation` and are never reported back as a step; `returnToCurrent` re-reports the shown Session so the entry names it.
- A copied Chat place without `extra.selection` establishes the linked selectable Identity Agent or listed Project Team member as the normal target, including for its draft and later New Session. Explicit history selection remains authoritative; hidden owners and child-Session links keep the existing selection and use a Session override. App waits for its initial Project catalog attempt before inferring Team membership; a failed attempt still permits an explicit Session override.
- Session restoration from history retires an older navigation after asynchronous Project loading. Project team responses, errors, and loading indicators belong to the latest team request across picker switches and history restoration, including revisiting the same Project.
- Session state keys on (Agent address, Session id); switching Agents or Project context never merges histories, Queue items, usage, or active Runs.
- Agent navigation projects status across held Sessions with strict priority `running` -> unread -> idle; selection is a separate accent state. Tooltips (`chat/agentActivityTooltip.js`, shared by `ChatHeader` and `ChatView`) title the Agent's name, then an `Activity` row in words (`Running` in amber, unread result count, `Idle`), the effective Model as a `Model` row in canonical `provider/model` form (no `::connection[:account]` suffix), a `Thinking effort` row (the effective effort, or `Provider default` when none is set), and the id as a mono `Agent ID` row when it is more than the name in other letter case - Identity Agents from `agent.list`, Team members from the Project scan (`project.list` cached scan, `project.show` for the open Project). Every Agent bar tab and every All agents option shows the same tooltip.
- `ChatHeader.svelte` is each Chat area's Agent bar: the Session-list toggle and New session, then the first five Identity Agents in roster order (the Agents tab's order; no pinning, user decision) as tabs, then `...` for All agents, and the area actions at the right. The selected tab is a neutral `--surface-3` tab. A tab shows a status dot before its name only while the Agent is running (amber) or has unread results (blue); idle Agents show no dot (user decision). Tabs that do not fit the bar wrap onto a clipped second line and are reached through All agents (`measureFittingAgents`, re-measured through a ResizeObserver on the row and on every tab); on a bar narrower than 560px (container `agent-bar`) unselected tabs show the name's first two letters through a `data-initials` pseudo-element, so their text content stays the name. A displayed Agent outside the shown tabs (a later Identity Agent, a Team member named `Builder · vBot`, or an override stand-in through `displayedAgentName`) gets one temporary tab after them. `...` appears whenever an Agent is not shown as a tab and carries the combined status dot of the Agents reachable only there. It opens the All agents list (`SearchableDropdown`): every Identity Agent first, without a heading, then each Project that has Team members as a collapsible group headed only by its name (tree mode); a Project without Team members is left out (user decision). The filter field appears whenever a Project group exists or above 6 Agents, and also matches Project names. Options order running, then unread (newest result first), then roster order within Identity Agents and within each group, and name their status (`Beta: Running`, `Gamma: 2 unread results`). A closed group shows its Agents' combined status dot (running over unread) and unread count; an amber warning icon marks a Project whose scan report is not clean. A group opens for the selected Agent's Project on every list open, otherwise by this browser's remembered toggle (`vbot.chat.agentPicker.expandedProjects`), otherwise when any of its Agents is running or has unread results. Team members come from `project.list` with `include_scan` (the server's cached scans, loaded by App's `selection.svelte.js`); the open Project's Team starts from the live `project.show` result, and a newer listed scan replaces its Team/report in place and retires an older pending Team read without resetting held Sessions (`target.svelte.js`, `ChatView.projects.test.js`). Choosing a Team member opens its Project (`target.svelte.js::handleSelectProjectAgent` -> `openProjectTeam`, which shows the listed Team at once and replaces it with the `project.show` result); choosing an Identity Agent leaves the Project (`leaveProject`), so App persists `''` for both the Project and the Project Agent. The scan banner shows while a Project Agent is active. The unread count is the number of the Agent's Sessions with an unread result (`hasUnreadCompletion` plus `unreadRunId`, excluding the displayed Session) from `sessionState.js::agentUnreadResults`; Chat reads activity for every Agent address on the bar and in the list. The first Chat area also reports the number of unread results across those addresses to the Main menu's Chat entry (`onNavigationIndicator`, tone `unread`, `webui/app-shell.md` -> Main menu indicators); while that area is shown, its displayed Session does not count, like on the Agent bar, and while Chat is hidden it does, because a hidden Chat sends no read acknowledgement (`ChatView.activity.test.js`). Tabs and list options both call `ChatView.svelte::handleSelectPickerAgent`, which routes by Agent address. The drawer's All agents roster stays the Identity Agents plus the open Project's Team, keeping `session.list` within its address bound. Coverage: `ChatHeader.test.js` -> Project Teams, `ChatView.projects.test.js`. A shown Session whose Identity Agent is not in the roster (the hidden Librarian's, opened from Settings or the Skills manager, or a deleted Agent's) is an override view with a stand-in Agent (`target.svelte.js` `overrideAgentDisplayStandIn`, named "Librarian" for the Librarian through `lib/librarian.js`, and "Live voice" / "Live backend" for the Live Agents through `lib/liveAgents.js`); a Live Agent's Session shows the notice "This Session records a Live voice call. Only the call writes to it." in place of the composer (the stand-in's `__liveCall`), matching the server's refusal of other Runs for these Agents (`ChatView.sessions.test.js`); the bar shows that name as the temporary tab (`displayedAgentName`), and the composer sends to that Agent and Session (`ChatView.sessions.test.js` -> Librarian Session). Coverage: `components/chat/__tests__/ChatHeader.test.js`, `ChatView.activity.test.js`. `connection_ready.active_runs` supplies post-reconnect activity; batched `session.activity_list` supplies durable completion state; `session.list` stays authoritative for the selected Agent's drawer and Project-Agent landings. While the drawer remains open, it overlays Chat's held per-Session Run/activity projection onto those authoritative list rows by complete Agent address plus Session id, so running and unread markers react without another list request. Clicking an unread Agent opens its newest unread Session. Runs with `contributes_to_agent_activity: false` stay out of Agent-level activity and Subagent status maps while their concrete Session row still shows an active Run.
- A completion counts as read only once its exact `run_id` appears in the displayed history or terminal events and the user can see it: ChatView's acknowledgement effect is the only `session.mark_read` trigger (a History load does not acknowledge), and it sends only from an active Chat area while the page is visible and focused (`document.visibilityState === 'visible' && document.hasFocus()`, read live). Regaining window focus or visibility re-checks the displayed Session. Do not loosen this gate: other clients treat the resulting `read_run_id` as "the user has seen this result" (the vBot tray skips or dismisses its toast, see `server/events-and-reconnect.md`) (`ChatView.activity.test.js`). The displayed Session leaves unread presentation immediately while its acknowledgement pends or waits for attention, and returns on failure. Retained `latest_completion_run_id` is the reconciliation key - arrival order of replayed terminal events must not flip read state, and an older completion must never clear a newer local result. Completion activity reads (`lib/chatState/activity.js`) are coalesced: at most one `session.activity_list` runs, one pending pass collects the addresses requested meanwhile, and a burst of invalidations waits 100 ms to become one read. Newly displayed Agent addresses are read once; the full `sessionsRefreshToken` or a new connection snapshot re-reads all. From App's `sessionInvalidations` window, a terminal `run_id` whose Run event App still retains (already applied), a `read_run_id` matching the held completion (cleared locally), a deletion (marker dropped) and other Session changes such as create or rename need no read; a terminal `run_id` no longer retained or an unmatched `read_run_id` re-reads that displayed Agent, and an unscoped entry or a window overflow re-reads every displayed Agent. The response omits Sessions without a completion, so an omitted Session is cleared only while its local completion is still the one seen when the read started.
- Loading flags are responsibility-specific (`loadingAgents` only `agent.list`, etc.); background activity loading never resurrects the roster loading surface. Only the newest displayed History request owns the loading state; a pending request for a departed Session or an older request for the same Session cannot keep the composer disabled after the displayed load finishes. History loading disables the composer and New Session; a draft has no History to load, so its composer is usable at once. Initial History feedback waits 300ms and is keyed to the currently displayed Session, so a fast Agent/Session change stays quiet and a stale destination cannot flash feedback over the new Session.
- Only the latest roster read can publish Agents, selection callbacks or errors. A silent refresh that supersedes initial loading inherits its pending loading/initial History responsibility; ordinary background refreshes keep Chat mounted and skip initial History. A Chat mounted hidden adopts App's shared Agent selection silently on its first display (no navigation report, so a restored override survives), and the controller still loads that Agent's current History unless the pending initial roster load reads it (`loadAdoptedSelectionHistory`). Disposal invalidates pending roster reads (`chatState.agent-activity.test.js`).
- History loads newest-first and prepends older pages without moving the reading position. The controller stores `next_before` from each response and sends that opaque cursor for the next older page; falling back to the first public Message id exists only for compatibility with older servers. An older-page response belongs to the loaded History snapshot: a successful full refresh, Run reconciliation, or accepted edit invalidates its result and errors while preserving the replacement cursor for the next request; failed refreshes and other Sessions do not invalidate it. Subsequent History reads use `next_after`; bounded append batches are collected before application (their messages, Run records and background statuses fold together, a later record winning) and preserve loaded older pages. History Edit, Agent Takeover or generation replacement resets the snapshot. Record sequence identifies occurrences even when public Message ids repeat. A matching canonical Run Summary proves completion; matching stable output ids never prove complete Run coverage. Without terminal persistence, the live terminal projection remains visible.
- A History response mutates only its addressed Session; full refreshes and recovery requests for the same Session share a generation guard and reject snapshots superseded by an accepted edit; a full refresh overtaken by a newer Run rereads History before applying an obsolete active-Run snapshot, and only the newest response for the still-displayed Session may touch global loading/error state or attach the Run stream. These guards belong to the controller, not the View.
- Background-only Sessions: a non-Channel Session whose `run_kinds` are entirely cron/reflection kinds classifies as hidden-by-default, as does every Sub-Agent Session. A Librarian Session (`run_kinds` `librarian`) is an ordinary row: the server lists it only in the hidden Librarian's own scope (`sessions.md`), which the drawer addresses while one of its Sessions is shown. `SessionListDrawer` sends those category filters to `session.list`, loads 35 globally ordered rows initially and 20 per scroll page, and keeps the selected Session visible through the required-Session contract even when it is old or classified. The **All agents** toggle sends the deduplicated roster in one bounded request; returned rows carry their owning Agent address and the UI routes selection/rename/delete/policy actions through it, using a composite Agent-address-plus-Session-id row identity. A refused delete shows inline: `session_in_use` names the pinning Cron jobs (Agent jobs of Calendar events included) and Bootstrap jobs from `error.data.references` through catalog text (`sessions/presentation.js` `sessionDeleteErrorText`), `session_busy` (an active or queued Run) shows the catalog text `sessions.delete_busy`, other refusals keep the server message (`SessionListDrawer.actions.test.js`). The browser never downloads hidden pages or open-ended Session metadata merely to calculate the list or its remaining count. Project Agents have no server current-session pointer: their initial landing requests the newest ordinary Session only, else shows a draft; Parent/Sub-Agent navigation requests its exact Session through the same required-Session contract.
- **Drafts (lazy Session creation):** a Session exists only once it is used. Until then the area shows an unsaved draft: an Identity Agent whose area-local `current_session_id` is empty, or a Project Agent whose `projectAgentSessions` entry is `''` (an absent entry means not resolved yet). New Session, `/new` (the server returns `command: "new"` without a Session id and has cleared the Identity pointer; an Identity Agent becomes the selected one), an Identity Agent without a current Session, a Project Agent without a Session and a deletion without landing all show a draft; none of them calls the server. `target.svelte.js::activeDraft()` names the shown draft; its composer key is `<agentAddress>::~draft-<area index>` (`~` never occurs in a Session id), so each area keeps its own draft text, attachments and Session settings (Composer and inputs -> Session settings) across navigation. A draft has no Session state, unread state, activity or list entry.
- `New Session` is an idempotent intent and requests nothing: a draft, or an empty displayed Session whose composer this area owns (no visible history/events/Queue/command card and no composer text), only gets focus; otherwise the area shows the Agent's draft. A shown draft clears the drawer's row selection without reloading the list (`SessionListDrawer.test.js`). History loading disables the action. The server's Identity pointer is untouched until the draft's first send. New Session stays available during an active Run - leaving closes only the local SSE subscription while the server Run continues, and returning reconciles/reattaches it.
- The first send from a draft goes through `chatController.sendToNewSession()`, the one place that builds `chat.stream` with `new_session` instead of `session_id`: `{}` for a draft on its defaults, else the draft's `working_project_id` and non-empty `agent_overrides` (`sessionSettings.draftWithSettings` adds them at send time). It reads the returned Session id (top level, else a command response's `data.session_id`, else a queued `item.session_id`), creates the (address, id) Session state and calls `onSessionCreated` before the Run stream attaches; ChatView then adopts it through `navigation.adoptCreatedSession` (only while that Agent's pointer or held Session is still empty; an Identity adoption is reported through `onAgentsChanged`) and refreshes the Session list. While the draft is still shown, the created Session replaces it and corrects the history entry; after the area moved on, a later return to the Agent opens it. A command answered without a Session (`/status`, `/help`) keeps the draft. `actions.sendDraft` resolves `{draftKey}` for the created Session, and `ChatComposer` treats that as sent and moves text and attachments added during the send to the created Session's key; an upload still running when they move completes or fails where its attachment now is. Coverage: `ChatView.sessions.test.js` -> New session, `ChatView.commands.test.js`, `ChatView.projects.test.js`, `ChatWorkspace.test.js`, `chatState.send-and-queue.test.js`, `ChatComposer.test.js`.
- Selecting another same-Agent Session is ordinary navigation; the backend `current_session_id` is a default landing pointer only - no "past" labels, return warnings, or competing Current badges. Cross-owner Sub-Agent navigation highlights the owning Agent and keeps a contextual return banner targeting the immediate Parent.

## Runs, streaming, and recovery

- `ChatReasoning.svelte` owns the shared Reasoning disclosure for live and saved Timeline entries. Structured summaries show a fixed Reasoning summary label, the latest section's optional Markdown heading, and a section count; expansion renders and copies all readable sections. No heading is invented from prose. Summary headers do not display a thinking-duration estimate or completed-step checks. Ordinary commentary and Tool rows retain their own presentation. Unstructured Reasoning, including mixed summary/raw text, uses the existing complete-text fallback. Live compression merges summary fragments only within the same `summary_index`; stable output replaces the draft with persisted sections.

- `createChatRunStream()` owns the EventSource lifecycle, expected sequence, reconnect cursor, heartbeat watchdog, and terminal cleanup for one Run; ordered event buffers, gap/terminal watchdogs and History retries are keyed by Session plus Run. A successor replaces only the active SSE subscription; its predecessor's buffered output and terminal reconciliation continue independently. Leaving the Session tears down its transport state.
- Terminal events settle and close only their matching current Run; late completion from a predecessor remains in its event history without stopping the successor. A delayed start response enriches the same Run without resetting live drafts, controls, or terminal status. Reconnect snapshots cannot downgrade a terminal Run to running (`chatRunStream.test.js`, `chatState.send-and-queue.test.js`).
- Ordered reducer with a two-second sequence-gap watchdog: an unresolved gap closes SSE and replays from the highest contiguous cursor; a replay head beyond retained history rebases the reducer. Recovery diagnostics log only reason/ids/cursor/attempts/error type - never payloads. A terminal event buffered behind a gap for one second triggers reconciliation from canonical History, so completion never needs a manual reload.
- Streaming deltas are compressed before retention and all ride the ~33 ms flush: text deltas merge per phase, tool argument deltas per (run, tool call, phase), and a Tool's `tool_call_output` screens keep only the latest per (run, tool call): each screen replaces the previous one, and a replayed older screen never replaces a newer one. Per-chunk retention made the per-render active-run projection replay quadratic in streamed output size - a multi-MiB bash output froze the whole UI (fixed 2026-08-30). The replay cursor stays correct because every raw delta sequence also lands in `seenStreamingEventKeys`; terminal runs keep the live Tool output visible until History confirms (same retention set as text drafts).
- The first delivered event of each new subscription is the transport-proven replay head: starting beyond the requested cursor rebases (the prefix left the bounded replay window); later gaps buffer until filled. Duplicates never duplicate timeline items. `provider_heartbeat` stores only its latest seconds-since-delta measurement (rendered as connection metadata, never progress). `stream_attempt_restarted` clears the failed phase's transient deltas, advances the phase, and stays sequence-accounted. A delta's phase follows its sequence position, not arrival order: boundaries (`tool_call_started`, `tool_call_result`, restart) already applied at later sequences - mirrored over the WebSocket while the Session was hidden, before the SSE replay on return - place replayed deltas in their own earlier phase, and a delta whose next applied boundary is a restart is dropped (`streamingEvents.js`; `chatState.streaming.test.js`, `chatRunStream.test.js`, `chatRunStream.reconnect.test.js`).
- Displayed Sessions reduce SSE plus mirrored WebSocket events in one contiguous-sequence reducer (either transport fills gaps, duplicates harmless, terminal buffers until complete). Non-displayed Sessions hold no SSE; their sparse stable WebSocket events reduce directly, and opening the Session reloads durable history. When a Run of a Session that the Chat owner neither displays nor holds History for finishes, `chatRunStream.js` releases that Run's retained events (`releaseFinishedRunEvents`) while keeping Run status, unread completion, usage and Queue projections; a bounded per-Session list of released Run ids stops a late `run_started` from reviving it and re-releases late events, so a long-lived tab does not keep every background Run's stable events (`chatRunStream.test.js`). Stable events deduplicate by Run id plus sequence through a key index tied to the current `runEvents` array, rebuilt after any owner replaces that array. Session entries themselves are not evicted: the activity list sync recreates listed Sessions on every refresh, and entries carry client-only reconciliation keys (read completion, History cursors, stream closures). SSE is the only high-volume-delta source; WebSocket stable output is backstop, not competing projection.
- `connection_ready.active_runs` replaces locally projected active Run/Subagent status; excluded Runs still reattach SSE when displayed. A Chat owner mounted after the app connected applies App's live `activeRuns` list instead of the retained snapshot's list and skips App's retained event window (`chatController.startFromServerState`; see `webui/app-shell.md`). If the displayed local Run is absent from reality, reconcile via `chat.history` before clearing (missed terminal -> durable final answer); once History confirms no active Run, discard all retained replay before rendering so sparse fragments cannot reappear behind it.
- Active snapshots preserve server timestamps (`currentRun.startedAt`; Child inspection keeps separate run/session start keys). One visibility-aware adaptive clock feeds elapsed times downward; Unstructured Reasoning headers tick from first delta until the next stable boundary freezes the estimate (`reasoning_timing` replaces it once available).
- Terminal events settle the projection, close the stream and synchronize canonical History for displayed or already-loaded Sessions; failed reads retry through the existing recovery owner. An explicit cancel merges the authoritative `chat.cancel` response events (only while that exact Run is current; a finished Run returns only its settled ending, `runs.md`), promotes undispatched sibling Tool previews to settled-cancelled, and immediately reconciles durable History. When terminal live events overlap not-yet-loaded history, keep the richer history content and overlay live terminal status instead of reverting to a provisional completed state. `run_interrupted` is amber: preserved partial text stays visible, output-less interruptions still get a bare summary row, and no UI control starts another Run.
- The Iteration badge projects only reported numbers: seeded from `active_run`, advanced by each completed Model response regardless of sibling Tool count, settled terminally, restored from `run_summary`; a summary without the field means unknown - omitted, never estimated.
- `subagent_status_changed` is the explicit Parent-cancellation projection: spawn rows settle to cancelled even when the event belongs to a later/non-contributing Parent Run.
- Cancelling a Run and cancelling a cancellable tool call are distinct operations - preserve that in labels, availability, and error handling.
- Pending Run cancellation is keyed by Session and exact Run id. Switching Sessions or starting a successor leaves its Stop control usable; duplicate cancellation requests for the same Run coalesce, and late failures do not overwrite a successor's action state.
- `sendMessage()`, `sendToNewSession()` and `editMessage()` resolve semantic outcomes after reconciling Session/Run/Queue state; the View snapshots display key and UI generation before awaiting either, then applies navigation/toasts/transient cards and scroll updates only while that generation is current. Edit admission calls `chat.edit`; only after success does the controller remove the targeted User message and later active suffix locally, attach the new Run stream, and clear Current Context Usage until the server refreshes it. Failure preserves the visible lineage unchanged.

`ChatComposer.svelte` keeps draft/History navigation, submission admission and input/keyboard coordination. Internal `components/composer/media.svelte.js` owns per-draft attachments, upload/recording lifetimes and transient feedback; `picker.svelte.js` owns Skill/file/Model triggers, catalogs and picker selection. Both consume current values through local getters; the component retains its public props and the existing admission snapshot semantics. `composer.css` contains the namespaced presentation rules.

- Queue invalidation addresses exactly its Agent/Session - switching Sessions never shows another's queued items.
- The timeline is the only scrolling surface, coordinated by `createChatScrollController()`: per-Session pinned flag plus a row anchor for windowing and a reading point within that row (`lib/chatScroll/readingAnchor.js`), one writer recording expected positions (its echo never reclassifies ownership), user motion classified from live position, upward input releasing the pin before the browser scrolls. Ineffective upward input at the top of a short timeline keeps following; at the top of overflowing History it establishes a reading position and can retry paging without a scroll event. Older-page requests are independent per Session, deduplicated while pending, and ignore completion after teardown. Bottom growth never moves reading position; growth above the reading point corrects once through it. Within a long Run, the point follows a visible text character (or a non-text block), so image loads and width reflow preserve the displayed line. Assistant Markdown scopes use the stable child id; block paths and block-local text offsets rebind after Markdown replaces its HTML or a Session remounts, with the row position as fallback when the point disappears. Independently scrolling Tool output and table boxes anchor by their outer bounds, so scrolling their contents never counter-scrolls the timeline. Navigation restores saved viewports, explicit Sub-Agent links open pinned at bottom, sending pins to the bottom so the incoming response is always visible, and Jump-to-latest appears only away from the live tail.
- Window: the controller also owns which rows are mounted. Once the content column has layout, only the rows in and around the viewport (about one viewport of overscan each way, with hysteresis) plus held rows are mounted; `aria-hidden` spacers (`[data-timeline-spacer]`, never carrying `data-timeline-item-id`, so anchors always name real rows) stand in for the rest. Spacer heights come from a per-Session layout model (`lib/chatScroll/layoutModel.js`): measured ResizeObserver border-box heights of rows that were mounted, per-kind running-average estimates for the others, prefix sums. Estimates adopt new averages only when the window moves, so measuring a streaming row never resizes spacers above the reader. `lib/chatScroll/timelineWindow.js` keeps the window as row ids, so appends and prepends do not shift it; a pinned view windows the tail with an open end. `ChatTimeline` renders `controller.renderPlan(items, sessionKey)` and calls `controller.rendered()` after every update: new rows are measured, a changed window or spacer corrects the position once through the anchor before the browser paints, and a viewport the window does not cover extends it synchronously (bounded per frame). Restoring a Session is two steps: the window is aimed at the saved anchor through the model, then the final position comes from the mounted anchor. Older History enters as spacer above the mounted anchor, and that same correction keeps the reading position. Without layout (jsdom; a timeline created hidden until it shows) every row is mounted; once active, losing layout keeps the last window.
- Held rows stay mounted outside the window until their interaction ends: the row containing focus and the mounted rows the text selection touches (`lib/chatScroll/interactionHolds.js`), a message in inline edit and a playing `AudioPlayer` (through `lib/mountHold.js`, a no-op outside a virtualizing host), and the displayed Session's running Run, so its fresh speech starts regardless of the scroll position.
- Row UI state that must survive an unmount lives in the timeline's per-Session store `components/chat/timelineViewState.svelte.js`, keyed by stable ids: open Reasoning, Working groups, Tool/Sub-Agent/error/Compaction disclosures, pending row actions, and the speech sources that already started automatically (a remounted player does not start again). Components rendered outside a timeline (the Swarm page's `ChatAssistantRun`) get a private store with the former component-local behavior.
- Consequence of the window (user decision 2026-09-28): browser find-in-page (Ctrl+F) finds text only in mounted rows.
- Screen readers: the scroller is not a live region, because the window mounts old rows while the user scrolls. A visually hidden polite status region (`components/chat/timelineAnnouncer.js`) announces only content appended at the end of the displayed Session once it is final: a Run's answer as plain text when the Run finishes (not its streaming deltas), Assistant and error messages, and new command output cards; each Run at most once. History loads, older-History prepends, and Session switches announce nothing.
- The composer floats as an absolutely positioned overlay over the full-height timeline: its measured height reaches the timeline via `--chat-overlay-height`, the overlay ends before the scrollbar column (`--chat-scrollbar-width`), and reserved space is a trailing in-flow block (Chromium drops bottom padding/margin from scroll extent) - autosizing therefore never changes content geometry.

## Composer and inputs

`ComputerUseControl.svelte` owns the contextual Computer Use Stop button inserted through ChatComposer's existing action slot by ChatView. It does not poll: it reads the `control` status on mount, on each `computer_use` change App's Extension invalidations deliver (Computer Use publishes one whenever desktop control or a call starts, starts stopping, or ends), and on owner-less invalidations (reconnect, Extension reload, enable or disable), which also re-check that the Extension is loaded (`webui/app-shell.md`). One read runs at a time and a change arriving meanwhile triggers exactly one more. Availability alone renders nothing; Stop shows for the whole desktop control (`active`, also between calls) and is disabled while an interrupted call drains. Stop addresses the status's `control_id`; a mutation revision rejects status responses that started before it, and changes published while the stop request was in flight are read after it settles. Mutation errors use Chat's existing toast. Native double-Esc belongs to the Extension (see `extensions/computer-use.md`), not browser key listeners. Tests: `ComputerUseControl.test.js`.

- `ChatComposer.svelte` owns draft entry and delegates parsing/media to established helpers; every submission variant uses the same resolved address.
- Sent-message recall uses plain ArrowUp only at a collapsed caret at the start of the input; ArrowDown returns toward the draft only at its end. Interior positions, including soft-wrapped text, selections, modified arrows and IME composition retain native editing behavior. Recalled-message working copies and the original draft survive navigation (`ChatComposer.test.js`).
- Disabled Send and Stop say why through `Button` `disabledReason` (sending, uploading, recording or transcribing, empty draft; cancelling).
- Every composer submission path stays blocked while microphone permission, recording or transcription is active. The microphone's Stop action remains available during capture; submission never cancels recording (`ChatComposer.speech.test.js`).
- Stop all: while a Run is active the composer shows Stop (cancels only that Run) joined with a menu button (shared `ContextMenu`) offering Cancel run and Stop all; without an active Run a standalone Stop all shows while the loaded Timeline holds a running Sub-Agent `run` row or a running handed-off command (ChatView derives `backgroundWorkRunning` from `backgroundTasks`). Stop all calls `chat.stop_all {agent_id, session_id}` -> `{ok, stopped}` through `chatController.stopAll` (guarded by `sessionState.stoppingAll`); the server stops the Run, background commands, terminals and every Sub-Agent below while the Session's own Queue stays. The outcome shows in the chat toast while the Session is still displayed ("Nothing is running in this Session." for 0); a failure goes to the Session action error. Terminals started through the `terminal` Tool and work outside the loaded History page do not make Stop all visible (`ChatView.runs.test.js`, `ChatComposer.test.js`).
- Submission serializes from an initial snapshot (text, origin, attachments, callbacks, and a draft's Project/Model/thinking-effort choices) through file-mention resolution and admission; changing the draft settings or navigating during lookup cannot redirect that submission. The created Session's footer starts from the submitted choices, while later choices remain with the next draft. Only confirmed admission consumes unchanged draft choices; only a confirmed successful outcome clears draft and attachments - failures and mid-flight additions stay editable. No-argument immediate Commands enter the same guarded path.
- Setup guidance is prerequisite-ordered: missing Provider routes to Settings -> Providers before model-less-Agent guidance routes to Agents; readiness is never inferred from the Model catalog, and neither prompt shows while Settings are unresolved.
- Slash Commands and Skills come from the server catalog submitted through the command contract - no competing frontend roster or backend-semantics interpretation. Catalog loading guards on Agent address, the read scope (`sessionSettings.readScope()`: the displayed Session's id, sent as `session_id`, or a draft's explicitly chosen Project, sent as `working_project_id`) plus the App-owned refresh token, so Extension lifecycle changes refresh autocomplete without disturbing selection or draft.
- File mentions constrain to the server-provided list for the active address: `files.list` with the active Session's id lists the tree of its Working Project, and a draft lists the Project it chose (`working_project_id`, `null` for the Workspace) or else the Agent's default Project's (`server.md`). A new `onListFiles` (another draft Project) drops the composer's cached file list. Each `@` picker open asks twice: once for the index (`files` plus `directories`, the folders that hold non-ignored files) and once with `directory` for the direct entries of the typed folder (`''` is the listing root), which include ignored entries; a folder typed later is listed after a 120 ms pause, a chosen folder at once, each at most once per open (`picker.svelte.js`). A typed path that would leave the listing root (absolute, such as `/x` or `C:/x`, or with a `..` segment) lists no folder, so only index matches show; `resolveMentionFiles` never lists such a folder either. Rows (`fileMentions.js::mentionCandidates`, at most 50) list the typed folder's entries whose names start with the typed name first, folders first, then the fuzzy matches over the index (`createMentionIndex`: built once per listing; while the query grows it searches only the previous matches, and it scores subsequence matches only while substring matches leave room, so the server's 20000-file cap stays smooth); ignored entries render dimmed with an "ignored" label, and a list that opens on ignored entries highlights its first non-ignored row until the arrow keys or the pointer move the highlight. Choosing a folder inserts `@dir/` (or the open quoted form `@"my dir/`) and keeps the picker open; an unclosed `@"...` also opens it. At send, `resolveMentionFiles` confirms each token against the index, then against the entries of its folder (the picker's listings from this open, else up to 20 folder listings), so files reached by browsing, ignored ones included, become `file_mentions`; Queue edits run the same check (`ChatComposer.suggestions.test.js`, `fileMentions.test.js`). `fileMentions.js` owns the mention grammar: bare `@path` tokens accept letters/digits in any script plus `_ . / \ -`; every other listed path is written as `@"path"` (`\"`/`\\` escapes). The picker and user-message copy write tokens through `formatMentionToken`, so every listed path round-trips into `file_mentions`; a mid-word `@` (e-mail) is never a mention. Attachment ids stay opaque with safe server URLs for preview/download. Image cards render their persisted Session reference (for example, `Image 1`) as the normal label and retain the original upload filename only as hover detail, matching the Model-facing reference.
- The `/model ` autocomplete opens on demand (catalog fetched when triggered, through the Session settings' shared catalog), reuses the Agent-dropdown suitability filter and show-all toggle, auto-submits the selection through the guarded path, and shares one keyboard contract with the skill/file popups. Enter/Tab selects only the visibly active row; if a list change leaves the active index out of range, selection returns false instead of falling back to an unmarked first row. While an open `@` or `/model` picker is still loading and has no row to select, Enter is consumed instead of sending the partial token (`ChatComposer.test.js`).
- **Session settings:** `chat/ComposerSessionSettings.svelte`, rendered through ChatComposer's `footer` snippet, is a quiet row under the input box: Project picker left, Model and thinking-effort pickers right (accessible names "Project", "Model", "Thinking effort"); `chat/view/sessionSettings.svelte.js` owns its state. Project: in a draft of an Identity Agent a Dropdown of Workspace plus the registered Projects, defaulting to the Agent's `root_project_id` (else Workspace); for an existing Session (the `session.get` row's `working_project_id`) and for a Project team Agent it is a read-only name, and a Project no longer registered shows its id in amber once the Project list has loaded (before that, an unlisted Project shows its id without a warning). Model: an "Agent default" entry naming the Agent's Model (`agent.list` row `model`; a Team member's `effective.model.value` from `project.show`) plus the usable catalog Models as canonical `provider/model` (`buildModelSelectOptions` `modelOnly`). Thinking effort: the Agent's effort (else "Provider default") plus the levels `effortOptionsForReasoning` allows for the effective Model's `capabilities.reasoning`; hidden while the effective Model or the catalog answer is unknown and for a Model with `reasoning.supported: false`. Choosing a Model that does not offer the chosen effort clears the effort with it. Choices are Session-only and never write the Agent: a draft holds them per draft key until its Session is created (the next draft starts from defaults unless the user changed the choices while the previous submission was pending); an existing Session writes each change through `session.set_agent_overrides` (`null` clears), shows it at once and settles to the response's `agent_overrides`. The Session row is re-read on display change, `sessionsRefreshToken`, an invalidation naming the Session (Run-completion and read scopes excepted) and after `/model`; a read that overlaps an override write to that same addressed Session is dropped; writes finishing for another Session never invalidate its read. `/model <value|reset>` (controller outcome `modelChanged`) clears a draft's held Model or re-reads the Session (the server clears its Model override), then refreshes the Agent's defaults (silent `agent.list`, or `target.refreshProjectTeam()`). The Model catalog (`model.list` + `connection.list`) loads when the footer first shows and whenever the Model picker opens (`ChatView.sessionSettings.test.js`).
- Speech input releases every media resource (tracks, recorder, timers, object URLs) on completion, cancellation, replacement, teardown, and failure - cleanup best effort across failing tracks. Changing the displayed Session or tearing down the composer cancels capture, aborts pending transcription, and rejects late audio, progress, transcript and error results so speech cannot enter another Session's draft. A pending browser microphone permission request cannot be aborted, so cancellation invalidates it and a late recorder result must release its tracks without starting capture. The native recorder container uploads as-is; `SpeechService` converts to the server-wide Voice -> Transcription profile, so Chat and wakeword capture share one Provider-facing audio policy.
- Drafts and completed pending Attachments are interaction state keyed by the full displayed Session address (for an unsaved draft, its per-area draft key; Selection and Sessions -> Drafts); refresh or selection transitions never silently submit or cross-address either. A pending Attachment becomes Model-visible only when that Session's send is admitted. `composerMemory.js` shares them and per-Agent send history across browser tabs through origin `localStorage`: drafts merge per changed Session key, history per sent message, and Attachments per added or explicitly removed attachment id. Attachment deltas merge into the newest stored projection, so a completed local upload cannot resurrect an unchanged file another tab removed or sent. Mounted composers subscribe to the shared projection, reconcile active and cached scopes without writing it back, and retain local uploads plus unchanged preview identities; scope mutations reconcile synchronously before reading their attachment list (`composerMemory.test.js`, `ChatComposer.test.js`).
- Once browser recording has started, the composer sends `prepareSpeechTranscription()` without awaiting it and ignores its failure, so the server can load a local speech model while the user speaks (`model_tasks/speech.md`).
- Chat microphone uploads opt into the speech endpoint's NDJSON progress stream.
  `api.js` delivers phase snapshots before the terminal transcript and rejects an
  interrupted stream or missing heartbeats without automatically resubmitting
  audio. `ChatComposer` shows the server phase and elapsed time beside a spinner
  above the composer; its microphone tooltip uses a wrapper so it remains
  accessible while the button is disabled. Completion and errors clear busy
  state; teardown invalidates late progress/results. Coverage: composer/API tests.
- Composer focus follows deliberate navigation only (New Session, mobile included; user-driven selections after destination history settles, desktop only; mobile stays in reading mode with `preventScroll`). Async completion keeps a one-use focus intent in `layout.svelte.js`: newer navigation, later pointer/keyboard input or focus, and loss of active/input ownership retire it, including an away-and-back visit to the same Session. Sends and confirmed deletions capture before their RPC as well as any later History load; the matching deletion event preserves the initiating intent without granting other areas focus. Passive changes (reconnects, invalidations, mount restoration) never steal focus.

Request status is footer metadata on a running Assistant Run: retry causes and available attempt counts appear immediately; ordinary request waits and Provider heartbeats stay quiet until 60 seconds without Model output. Request waits use the shared live clock, while heartbeats use the server-reported idle measurement. Actual Provider progress replaces the notice; terminal Runs hide it. Failed Compaction attempts keep a visible warning separator without marking an otherwise continuing Agentic Run failed; harmless stale/insufficient-reclaim attempts remove their placeholder. ## Usage and errors

Speech Tool artifacts in `ChatAssistantRun.svelte` and `ChatTimelineEntry.svelte`
use `components/ui/AudioPlayer.svelte`, also used by the Settings preview. It
owns media state, seeking, speed, volume, download, playback errors and resource
cleanup. A successful `generate_speech` result shows the player whether its Tool
result envelope is a live event object or the persisted Tool message's JSON text
from Session history (`chatTimelinePresentation/messages.js`). Only a live Run
projection (`item.source === 'live'`) requests one automatic start per source;
a player first mounted for a Run rebuilt from Session history stays paused. The
player latches that request when a source is attached and ignores re-renders
with an equal source, so a player that survives the live-to-History handoff
keeps playing (or still starts) without reloading. Later `canplay` events must
not undo Pause. Starting another shared player pauses the previous one.
`speech_playback` Run events attach a transient server PCM stream to the
running Tool row before its result arrives. `api/media.js` validates the framed
transport and requires an explicit success terminal; `speechPlayback.js`
schedules at most about two seconds in WebAudio plus one bounded frame, with
backpressure during Pause. `AudioPlayer` owns this resource and keeps it through
the final artifact and History handoff without replaying audio. Seeking and speed
become available after streaming ends, download when the artifact arrives;
manual replay uses that artifact. Transient failure never auto-replays a partial answer. Tool/Run
cancellation and component teardown stop playback and abort its request. The
Settings preview uses the same player from its NDJSON `playback` notification.
Mounted coverage: `components/__tests__/AudioPlayer.test.js`.

- The context ring is a button that opens the shared interactive hover card (hover intent, press, keyboard focus, touch; Tab reaches its action, Escape returns to the ring) with Context usage and one `Compact now` action. During an active Run the action forwards `compact` through `chatState.js` `controlRun`, which the Run applies at its next safe step; without an active Run it submits the server-owned `/compact` command through the ordinary send path, starting a manual Compaction Run. `contextCompactionState` derives availability from server state only: `idle` without an active Run, the running Run's advertised `controls.compaction`, `running` during a manual Compaction Run. Pending requests, in-flight submissions, and running Compaction disable repeat submission and show the requested/compacting labels; the shared card returns keyboard focus to the ring when the action disables itself. Ring/card warning levels come from `tokenUsageTooltip.js::contextLimitWarning` and the displayed Session's effective Compaction Policy (`chat.history.compaction_policy`, held as `sessionState.compactionPolicy`; a Policy saved in the Session drawer applies at once through `applySessionCompactionPolicy`, other Policy changes arrive with the next History read). Amber starts 10 percentage points before the automatic trigger (the earlier of `context_ratio` threshold and token cap, or `input_tokens` over the window) and says the threshold is reached at or past it; with automatic Compaction disabled, unknown, or unreachable within the window it warns about the context limit from 70% instead; red from 90%. The numerator is Current Context Usage `tokens`, the same Run-local projection the server trigger evaluates; the denominator is the Agent payload's resolved window for its primary Model, so a fallback target's different window can shift the server's actual trigger point. Tool rows receive server-advertised background eligibility and forward `Move to background` through the same controller; no Session-depth policy is inferred in Svelte. Run-control events and sequenced reconnect/RPC snapshots restore these actions, rejecting stale projections (`ChatComposer.test.js`, `ChatAssistantRun.test.js`, `chatState.run-events.test.js`, `chatState.send-and-queue.test.js`). Background Bash terminal-event ingestion is untracked by the View effect so writing the process projection cannot retrigger the same ingestion (`ChatView.runs.test.js`).

Chat shows three distinct server-owned projections: last-step Provider Usage, cumulative Session Usage, and Current Context Usage (restored from History, updated from live/terminal events; badge and card use `tokens` and `context_window`). The card shows no provenance (`estimated`, `~`, Provider anchor or delta): the reported/estimated distinction is rarely of interest and stays reachable in Statistics diagnostics. The frontend formats but never sums, recalculates cost, or infers missing values; cache counts are input subsets and reasoning an output subset. The card counts an unreported counter as zero: the Session hit rate is cache read over total input, and Last turn always lists cache read, cache write and uncached input; Reasoning rows appear when non-zero.

Chat has no top error strip. Run failures appear once in the timeline with full Provider payloads in the existing Details disclosure; terminal failures without an error Message use a timeline fallback until the canonical error event or Run Summary arrives. History, admission/action, command-catalog and stream errors remain visible beside the composer until their owning state clears them.

Errors normalize at the transport boundary, then attach to their Session/Run/Queue operation/toast; command-catalog errors use latest-request-wins. Admission failures never become Run failures, and rendering a failure discards no recoverable history nor leaves a finished Run marked active.
