# WebUI Chat

Read this reference only for WebUI Chat selection, Session, history, Run, Queue, timeline, composer, attachment, command, or speech-input work. Backend Chat contracts live in `chat.md` and its task-gated references.

## Ownership and addressing

`ChatView.svelte` composes Chat presentation and applies navigation consequences, while `createChatController()` in `chatState.js` owns the reactive client projection plus roster/history/activity/command loading, send and Queue workflows, cancellation, and durable-state reconciliation. `App.svelte` keeps this owner and its presentation DOM mounted for one `serverRecoveryGeneration` and only hides it during ordinary main-view navigation; onboarding and confirmed server recovery remain intentional remount boundaries. `chatRunStream.js` owns one active Run stream, and `chatTimeline.js` derives renderable timeline items. `ChatActivityPanel.svelte` is the presentation-only floating right-edge rail/panel over those same timeline, Sub-Agent status, and durable Background Bash status projections. Presentation components consume those projections and forward user intents; they do not sequence Chat RPCs or rebuild Run state independently.

An Agent address can be global or Project-scoped. `resolveAgentAddressing()` and `formatAgentAddress()` are the canonical client helpers for that distinction. Chat's selected Project context changes which Agent address and Session collection are active; it does not change the Project selected for management in `ProjectsView`.

## Selection and Sessions

- Display state is override-first: a temporary UI choice can lead while a server mutation is pending, but the resulting Agent, Project, and Session state must reconcile to server responses.
- Session state is keyed by Agent address and Session id so switching Agents or Project context does not merge histories, Queue items, usage, or active Runs.
- Agent navigation projects status across all held Sessions with strict priority `running` → `unread` → `idle`: running is amber/orange, a durable unread terminal result is blue, and idle is neutral. Selection remains a separate accent-text/underline state. `connection_ready.active_runs` supplies activity after reconnect, while one batched `session.activity_list` call supplies durable completion-only state for requested Identity and Project Agent addresses without transcript bookends or general Session metadata; `session.list` remains authoritative for the selected Agent's full Session drawer and Project-Agent landing decisions. Clicking a blue Agent opens its newest unread Session. A Run carrying `contributes_to_agent_activity: false` is excluded from this projection and from active Subagent status maps even though its Session-local state remains running/terminal for direct viewing.
- A completion is marked read only after the exact `run_id` appears in the displayed Session's history or terminal Run events. The displayed Session is excluded immediately from Agent and Session-drawer unread presentation while its Run-specific `session.mark_read` acknowledgement is pending; other Sessions remain eligible, and a failed acknowledgement becomes visible again after leaving the Session. Successful acknowledgements performed internally after a Sub-Agent result reaches its Parent arrive through the same Sessions invalidation and activity/listing refresh as Accessor reads. The normalized `latest_completion_run_id` is retained after a read and is the exact reconciliation key for retained/replayed terminal App-shell events: either arrival order must stay read, while a clean projection for an older completion must not clear a newer local result. A newer activity refresh or exact acknowledgement invalidates an older in-flight activity batch; a failed batch retains the last known projection.
- Loading states are responsibility-specific: `loadingAgents` covers only `agent.list`, `loadingHistory` covers the displayed History request, and background `loadingAgentActivity` never keeps or reintroduces the “Loading agents…” surface after the roster has arrived.
- History initially loads the newest page and prepends older pages without changing the user's visible reading position. Persisted history and live Run events are reconciled by identity/sequence rather than appended blindly.
- A History response may update only its addressed Session state, and overlapping requests for the same Session are generation-guarded so only the newest response may replace that state; only a newest response for the still-displayed Session may change global loading/error state or attach the Run stream. These stale-request and stale-display guards belong to `createChatController()`, not the View.
- Creating, renaming, deleting, moving, or selecting a Session uses backend responses as the final identity and routing decision. `sessionListView.js` classifies only a non-Channel Session with a non-empty `run_kinds` list consisting entirely of `cron` and/or `reflection` as background-only; unclassified legacy/empty Sessions, Channel-bound Sessions, and Sessions with any other or mixed origin remain important. `SessionListDrawer.svelte` hides background-only Sessions by default, preserves the currently selected Session even when it is background-only, exposes `Show all` to restore the complete list, and labels Cron/Reflection origins in that complete view. Project-Agent addressing and move targets are normalized by the helpers in `chatState.js`; because a Project Agent has no server `current_session_id`, its initial Agent-bar landing selects the newest non-Sub-Agent, non-background-only Session and creates a fresh Session when only execution-owned Sub-Agent or background-only Sessions exist.
- `New Session` is an idempotent Accessor intent once the displayed Session history is loaded: if that Session has no visible history, Run/Run events, Queue, local text draft, or transient command card, `ChatView` keeps it and focuses the Composer instead of calling `session.create`. A pending draft makes the current Session non-empty for this action so creating another Session preserves the draft under its existing Session key. History loading and an in-flight create disable/reject the action, closing both the unknown-state and rapid-repeat duplicate paths; the backend `session.create` contract remains unchanged.
- Selecting another same-Agent Session is ordinary browser navigation: the selected row and loaded history identify what the browser is using. The identity Agent's backend `current_session_id` remains a default landing pointer, not an age or usability classification, so the WebUI does not label another selected Session "past," show a return warning, or expose that pointer as a competing "Current" badge. Cross-owner Sub-Agent navigation highlights the Agent that owns the displayed Session while retaining the original selection as its root return context; its contextual return banner targets the immediate Parent Session and remains available through every nested Parent that is itself a Sub-Agent Session.
- New-Session availability is constrained by active local Run state; a stale local Run can be reset only through the explicit reconciliation path.

## Runs, streaming, and recovery

- `createChatRunStream()` owns the Run EventSource lifecycle, expected sequence, reconnect cursor, heartbeat watchdog, and terminal cleanup for one Run. Replacing or leaving that Run closes the old stream and all pending reconnect/recovery timers.
- `chatState.js` accepts ordered Run events and tracks the highest contiguous sequence. The first Run event delivered by each new SSE subscription is the transport-proven replay head: when it starts beyond the requested cursor, `chatRunStream.js` rebases to that sequence because the missing prefix has already left the bounded server replay window; later gaps on the same connection remain buffered until their missing events arrive. Duplicates and already-persisted events must not produce duplicate timeline items. `provider_heartbeat` remains a transient event on the active Assistant Run: `chatTimeline.js` stores only its latest seconds-since-Model-delta measurement, and presentation renders that measurement as Provider connection/wait metadata rather than Reasoning, text, or Tool progress. `stream_attempt_restarted` removes the failed current phase's compressed Reasoning, answer, and Tool preview deltas for the same Run, advances the streaming phase, and remains accounted for in event sequencing without removing stable output from earlier phases.
- For the displayed Session, SSE and mirrored WebSocket Run events enter one per-Run contiguous-sequence reducer. Either transport may fill a missing stable event, duplicates are harmless, and a terminal event remains buffered until every preceding sequence arrives. Non-displayed Sessions intentionally have no SSE subscription, so their sparse stable WebSocket events are reduced directly in WebSocket order; opening the Session later reloads durable History. SSE remains the only source for high-volume deltas while WebSocket stable output is a backstop rather than a competing projection.
- The `connection_ready.active_runs` snapshot replaces locally projected active Run and Subagent status. Every active Run creates/refreshes its addressed Session state, but only contributing Runs project running Agent/Subagent status; excluded Runs still reattach SSE when their Session is displayed so direct inspection remains live. If the displayed local Run is absent, the client reconciles through `chat.history` before clearing it so a missed terminal event reveals the durable final answer; an active durable Run is reattached, and transient History failures retry without executing the Run again. Once History confirms that no Run remains active, Chat discards all retained stable and streaming replay before rendering because persisted History is then the sole timeline source; sparse replay must never reappear behind it as duplicate User messages or empty Assistant runs. Active `run:` and `session:` Subagent entries absent from the snapshot are removed, while terminal status, duration, tool, and Queue-to-Run metadata remain.
- Terminal events complete, fail, cancel, or interrupt the local Run projection and close its stream. A successful explicit Run cancel also merges the terminal events returned by `chat.cancel`, so the cancel response is an authoritative backstop when SSE/WebSocket delivery is delayed or missed; it applies only while that exact Run remains current. When terminal live events overlap persisted Assistant/Tool history whose matching Run Summary has not been loaded yet, the timeline keeps the richer history content but overlays the live terminal status, timing, and pending-Tool settlement instead of reverting to History's provisional completed state. `run_interrupted` is an amber terminal outcome: preserved partial Assistant text remains visible, an interrupted Run without readable output still gets a bare Run Summary row, and no UI recovery control starts another Run. Continuation checkpoints remain internal Chat state and are available to a later eligible visible Run only after same-Run recovery has exhausted.
- The Iteration badge never reconstructs execution from rendered rows. `active_run.iteration_count` seeds/reconciles current state, each non-visual `model_step_usage.iteration_count` advances it after a completed Model response, terminal events settle it, and `run_summary.iteration_count` restores it from History; these are projections of `Run.iteration_count`. One response with any number of sibling Tool Calls counts once, and a Reasoning-only response counts once. A historical Run Summary without the field means unknown, so the badge is omitted instead of estimating from Assistant outputs, Tool rows, or messages.
- `subagent_status_changed` is the explicit Parent-Agent cancellation projection. Run transport writes its child `run:` status and exact queued `queue:` status (plus the queue-to-Run mapping when both handles are present), so the original spawn row settles to cancelled even though the event belongs to a later or non-contributing Parent Run; session-scoped status remains a fallback only.
- Cancelling a Run and cancelling a cancellable tool call are distinct operations. The UI must preserve that distinction in labels, availability, and error handling.
- `sendMessage()` returns a semantic outcome (`move`, `switch`, `transient`, `toast`, `queued`, `started`, or failure) after it has reconciled Session/Run/Queue state. `ChatView` snapshots the displayed Session key and UI generation before awaiting that outcome, then applies navigation, transient cards, toasts, and submitted-turn scroll updates only while the same generation is still current.

## Timeline and Queue

- `visibleTimelineItemsForRender()` is the render boundary. `ChatTimeline.svelte` and its item components display derived items; they do not reconstruct event ordering from raw arrays.
- Persisted messages prune matching transient Run events, and a persisted Run Summary authoritatively removes every inactive live group for that Run even when the bounded App replay retained only sparse lifecycle/User events; those fragments must never be appended behind History while another Run streams. Assistant output, reasoning, tool activity, child-Agent progress, compaction checkpoints, usage, and errors retain their distinct timeline semantics. During an active Run, `compaction_started` immediately inserts one amber in-progress divider between the surrounding Assistant/Tool children; `compaction_completed` replaces that same projected item with the localized before→after token summary, while `compaction_aborted` or a terminal Run removes an unfinished placeholder. Manual `/compact` is itself a server-owned Run and enters this exact projection path; the WebUI must not synthesize local Compaction state or reload History after a successful command response. The completed divider is a native disclosure in both the live Run and reconstructed History: opening it shows the checkpoint's exact string `message.content` in an escaped whitespace-preserving `<pre>` plus a shared `CopyButton`, with no trimming, Markdown rendering, or HTML interpretation; an unfinished divider and a legacy checkpoint without string content remain non-interactive. The completed checkpoint stores the token pair in Usage, so History reconstructs the same summary without appending the live event to the History array or moving multiple checkpoints ahead of their Run position. History reconstruction must preserve terminal semantics supplied by a Run Summary: a cancelled Run settles every still-open Tool and Sub-Agent row as cancelled while leaving already completed/failed rows unchanged, matching the live `run_cancelled` projection; an interrupted Run removes any transient preparing Tool preview once stable interrupted Assistant output proves that incomplete Tool Call was discarded. A text/reasoning child may remain a transient draft for later stable-event reconciliation, but only the latest visible streaming child of a running Run may display the working caret; a later Tool or text child proves earlier content is no longer the current activity.
- A preparing Tool row derives safe preview arguments only from completed top-level string fields in the streamed argument fragments. Its compact header and expanded Args detail use that same preview immediately; final parsed arguments replace it when `tool_call_started` arrives. Persisted rows rebuild their compact label from canonical flat arguments when event display metadata is unavailable; the `process` Tool uses `action` plus `session_id`, while a nested `request.operation` discriminator remains a presentation-only fallback for historical calls without exposing sibling request fields. Expanded Tool details decode an outer serialized payload once, preserve field types inside the parsed object, and quote nested strings so `"false"` cannot look like the JSON boolean `false`; top-level prose content remains unquoted.
- The special Sub-Agent timeline row belongs only to `subagent` with `action: "run"` because that action owns Child Session navigation, progress, and cancellation. `status` and `cancel` actions render as ordinary Tool Call rows and do not create another View Session link or Child Run cancel action. New Agent-facing results carry a stable public id and hide internal Run/Queue handles; live `subagent_session_started` events still carry those internal handles for accessor navigation, exact cancellation, duration, and status projection. `chatState.js` owns bounded status/result caches and resolves the stable public id through `subagent.inspect`; `ChatView` supplies displayed-scope context, while Timeline components render supplied state and never start recovery requests. A conservative exact-Run History fallback remains only for legacy Child transcripts whose Run Summary predates persisted public work ids.
- The floating Chat Activity panel lists automatic-delivery Sub-Agent spawns and handed-off Bash processes from the currently loaded Session timeline; inline/foreground Sub-Agents and synchronously completed Bash calls remain Timeline-only. It partitions both task kinds into a first `Active` group for `running` and a `Finished` group for completed, failed, and cancelled states, omitting either group when empty. A Sub-Agent row remains one whole-row Child Session link containing only the Agent address and accessible semantic status symbol. A Bash row is non-interactive information containing a `$` marker, compact command, and the same status symbol; it has no Session link, hover/focus action, separate View Session control, or cancellation action. `chat.history.background_bash_statuses` folds automatic completion notes and durable Process Tool Results by Process Session id so a handed-off row survives reload with its terminal state while internal notes stay hidden. Switching Agent or Session changes the supplied projections immediately; the panel remains open but correctly shows the destination Session's own tasks or empty state.
- Chat copy actions preserve semantic boundaries rather than copying rendered DOM: one Assistant action joins only that Run's ordered `assistant_output` Markdown sections, user copy reconstructs text plus `@` file mentions while omitting binary attachments, reasoning and command output copy independently, and Tool detail actions copy the same sanitized compact value the row displays. `MarkdownContent.svelte` is the shared safe-Markdown presentation owner; it mounts the shared `CopyButton` into renderer-owned fenced-code headers and withholds code copy for an incomplete streaming fence. The Reasoning-only Markdown source normalizer strips Provider HTML-comment separators and inserts a line break between adjacent bold blocks (`**First****Second**` → `**First**\n**Second**`) for both live streams and persisted History without changing canonical Session content or ordinary Assistant Markdown.
- The server owns Queue order, contents, and the public `editable` capability. The client may show optimistic continuity for edit/remove operations, but `syncQueueFromServer()` is the authoritative reconciliation path. Only items whose complete content is represented losslessly as editable text expose the editor; structured content, attachments, and truncated text remain removable but cannot be converted into preview text. Queue update callbacks return a semantic success status, and the editor closes only after confirmed success while preserving failed or subsequently changed input.
- `connection_ready.queues` authoritatively replaces every held Session's public Queue projection, including clearing scopes omitted from the complete snapshot. On `epoch_changed`, locally shown item ids absent from the new process trigger a transient restart-loss notice; a same-process replay gap reconciles silently because missing items may have started normally while disconnected.
- Queue invalidation applies only to the addressed Agent and Session. Switching Session must not display another Session's queued items.
- The timeline is Chat's only scrolling surface; the page and Composer do not become competing scroll containers. `ChatTimeline.svelte` owns one per-Session viewport record with `follow`, `reading`, or `restoring` mode, an item anchor plus offset, and a generation guard. Real content growth is observed with `ResizeObserver` and coalesced through one animation frame: follow mode assigns the bottom immediately, upward wheel/touch/key intent enters reading mode before a pending content resize can reclaim the viewport, returning to the bottom, activating the floating Jump to latest button, or sending resumes follow, and History prepend/Session restoration cannot apply or let a stale callback displace the current Session's pending sync. Normal navigation restores that per-Session viewport, while every explicit Sub-Agent timeline link opens its target at the bottom in follow mode and leaves passive browser-History restoration unchanged. The centered Jump to latest button appears over the timeline only while the displayed Session is above its live tail; native scroll anchoring remains disabled on the managed container.

## Composer and inputs

- `ChatComposer.svelte` owns draft entry and delegates stateful parsing or media behavior to the established helpers. Sending plain text, a slash command, attachments, file mentions, or speech-derived text must use the same resolved Agent/Project/Session address.
- Composer submission is serialized from its initial snapshot through file-mention resolution and server admission. The snapshot owns the text, input origin, attachments, file-list/send callbacks, and address-bound callback closure for that attempt; only a confirmed successful semantic send outcome clears the submitted draft and attachments, while failures and edits or attachments added during the request remain available.
- Current-session setup guidance is prerequisite-ordered: `App.svelte` passes Chat the tri-state, Settings-backed usable-Provider state; an explicitly missing Provider routes to Settings → Providers and takes priority over Model assignment, while a connected Provider plus a model-less Identity Agent routes to Agents. Chat must not infer Provider readiness from the Model catalog, and it shows neither prompt while Settings are unresolved.
- Slash Commands and Skills are discovered from the server and submitted through the Chat command contract; the frontend must not maintain a competing command roster or interpret backend-only command semantics. `ChatView` guards loading by Agent address plus the App-owned Command refresh token, so Extension lifecycle invalidation refreshes autocomplete without changing the selected Agent, Session, or draft.
- File mentions are constrained to the server-provided file list for the active address. Attachment ids are opaque public identifiers; previews and downloads use safe server URLs rather than filesystem paths.
- Speech input owns browser media resources only for its capture lifetime and releases streams, recorders, timers, and object URLs on completion, cancellation, replacement, or teardown. The browser may upload its native MediaRecorder container (normally WebM/Opus); `SpeechService` converts it to the server-wide Voice → Transcription audio profile before the STT Model sees it, so Chat and post-Wakeword command capture do not maintain separate Provider-facing audio policies.
- Drafts and picker state are interaction state, not Session history. A refresh or selection transition must not silently submit or cross-address a draft.
- `ChatView` issues explicit Composer-focus requests only after deliberate Chat navigation. New Session focuses on every viewport (including the empty-Session no-op); user-selected Agent, Project Agent, Project, Session, and parent/current returns focus after destination history settles on desktop but remain in reading mode on mobile. `ChatComposer` waits out its disabled state and focuses with `preventScroll`; mount restoration, browser-history requests, reconnects, invalidations, and other passive state changes issue no request and cannot steal focus.

## Usage and errors

Usage displayed in Chat consists of three server-owned projections with distinct meanings: last-step Provider Usage, cumulative Session Usage, and Current Context Usage. `chatState.js` restores Current Context Usage from History and accepts updates from live Run and terminal events; the header badge uses only its `{tokens, estimated}` value, while the tooltip exposes its Provider-anchor/estimated-delta provenance alongside the other two projections. The frontend formats these values but never sums last-step input/output into Context, recalculates Provider cost, or infers missing Usage from rendered text. Cache counts remain input subsets and provider-reported Reasoning remains an output subset; an absent optional counter stays absent, while `reasoning_turns` lets Session display distinguish no reporting from a reported zero.

Errors are normalized at the transport boundary, then attached to the relevant Session, Run, Queue operation, or transient toast. Session action errors and Run-stream recovery warnings live on their addressed Session; command-catalog errors use a separate latest-request-wins projection. History/send admission failures must not be promoted into Run failures. Rendering a failure must not discard recoverable history or leave a finished Run marked active.
