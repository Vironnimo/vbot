# WebUI Chat

Read this reference only for WebUI Chat selection, Session, history, Run, Queue, timeline, composer, attachment, command, or speech-input work. Backend Chat contracts live in `chat.md` and its task-gated references. As everywhere: these are working notes - the components and their tests remain the truth for rendered behavior.

## Ownership and addressing

`ChatView.svelte` composes presentation and applies navigation consequences; `createChatController()` in `chatState.js` owns the reactive client projection plus roster/history/activity/command loading, send and Queue workflows, cancellation, and durable-state reconciliation. Presentation components consume projections and forward intents - they never sequence Chat RPCs or rebuild Run state independently. Supporting owners: `chatRunStream.js` (one active Run stream), `chatTimeline.js` (renderable timeline items), `ChatActivityPanel.svelte` (presentation-only floating Session-info rail over timeline/Sub-Agent/background-Bash projections). For a displayed derived Session, `ChatView.svelte` resolves the immediate Parent Session from `subagent_parent` first or `fork_source` otherwise, loads its exact list row through the required-Session contract, and gives the panel its display name plus the normal Session-navigation target; unresolved provenance renders no link. `App.svelte` keeps this owner mounted across ordinary main-view navigation (one `serverRecoveryGeneration`); onboarding and confirmed server recovery are the intentional remount boundaries. An Agent address may be global or Project-scoped (`resolveAgentAddressing()`/`formatAgentAddress()` are the canonical helpers); Chat's selected Project context changes active addressing, not the Project managed in `ProjectsView`.

Reflection reviews surface as a "Reflections" subsection inside both Activity-panel groups. Server-marked reflection payloads carry `source_session_id`; `chatRunStream.js` maintains per-fork tracking entries from those events (run events create/update running entries, terminal events settle them in place, snapshot rebuilds drop absent running entries while keeping finished ones). Rows show scope/status/coarse elapsed time and navigate to the fork Session through ordinary session selection - no sub-agent banner, no cancel control, no unread contribution.

## Selection and Sessions

- Display state is override-first: a temporary UI choice leads while a mutation is pending, but Agent/Project/Session state must reconcile to server responses.
- Session state keys on (Agent address, Session id); switching Agents or Project context never merges histories, Queue items, usage, or active Runs.
- Agent navigation projects status across held Sessions with strict priority `running` -> unread -> idle; selection is a separate accent state. Tooltips add the effective Model as canonical `provider/model` (no `::connection[:account]` suffix) - Identity Agents from `agent.list`, Team members from `project.show`. `connection_ready.active_runs` supplies post-reconnect activity; batched `session.activity_list` supplies durable completion state; `session.list` stays authoritative for the selected Agent's drawer and Project-Agent landings. While the drawer remains open, it overlays Chat's held per-Session Run/activity projection onto those authoritative list rows by complete Agent address plus Session id, so running and unread markers react without another list request. Clicking an unread Agent opens its newest unread Session. Runs with `contributes_to_agent_activity: false` stay out of Agent-level activity and Subagent status maps while their concrete Session row still shows an active Run.
- A completion counts as read only once its exact `run_id` appears in the displayed history or terminal events; the displayed Session leaves unread presentation immediately while its acknowledgement pends, and returns on failure. Retained `latest_completion_run_id` is the reconciliation key - arrival order of replayed terminal events must not flip read state, and an older completion must never clear a newer local result. A newer activity refresh invalidates older in-flight batches.
- Loading flags are responsibility-specific (`loadingAgents` only `agent.list`, etc.); background activity loading never resurrects the roster loading surface. Only the newest displayed History request owns the loading state; a pending request for a departed Session or an older request for the same Session cannot keep the composer disabled after the displayed load finishes. Initial History feedback waits 300ms and is keyed to the currently displayed Session, so a fast Agent/Session change stays quiet and a stale destination cannot flash feedback over the new Session.
- History loads newest-first and prepends older pages without moving the reading position. The controller stores `next_before` from each response and sends that opaque cursor for the next older page; falling back to the first public Message id exists only for compatibility with older servers. An older-page response belongs to the loaded History snapshot: a successful full refresh, Run reconciliation, or accepted edit invalidates its result and errors while preserving the replacement cursor for the next request; failed refreshes and other Sessions do not invalidate it. Live Run events and persisted history reconcile by identity/sequence, never blind append: an arriving snapshot retires a terminal live projection only after a matching Run Summary or complete stable-id coverage proves inclusion; otherwise the live terminal view persists until later reconciliation.
- A History response mutates only its addressed Session; full refreshes and recovery requests for the same Session share a generation guard and reject snapshots superseded by an accepted edit; a full refresh overtaken by a newer Run rereads History before applying an obsolete active-Run snapshot, and only the newest response for the still-displayed Session may touch global loading/error state or attach the Run stream. These guards belong to the controller, not the View.
- Background-only Sessions: a non-Channel Session whose `run_kinds` are entirely cron/reflection kinds classifies as hidden-by-default, as does every Sub-Agent Session. `SessionListDrawer` sends those category filters to `session.list`, loads 35 globally ordered rows initially and 20 per scroll page, and keeps the selected Session visible through the required-Session contract even when it is old or classified. The **All agents** toggle sends the deduplicated roster in one bounded request; returned rows carry their owning Agent address and the UI routes selection/rename/delete/policy actions through it, using a composite Agent-address-plus-Session-id row identity. The browser never downloads hidden pages or open-ended Session metadata merely to calculate the list or its remaining count. Project Agents have no server current-session pointer: their initial landing requests the newest ordinary Session only, else creates a fresh one; Parent/Sub-Agent navigation requests its exact Session through the same required-Session contract.
- `New Session` is an idempotent intent: an empty displayed Session (no visible history/events/Queue/draft/command card) gets focus instead of a create call; a pending draft makes it non-empty. History loading and in-flight create disable the action. It stays available during an active Run - leaving closes only the local SSE subscription while the server Run continues, and returning reconciles/reattaches it.
- Selecting another same-Agent Session is ordinary navigation; the backend `current_session_id` is a default landing pointer only - no "past" labels, return warnings, or competing Current badges. Cross-owner Sub-Agent navigation highlights the owning Agent and keeps a contextual return banner targeting the immediate Parent.

## Runs, streaming, and recovery

- `createChatRunStream()` owns the EventSource lifecycle, expected sequence, reconnect cursor, heartbeat watchdog, and terminal cleanup for one Run; replacing or leaving the Run tears down everything pending.
- Ordered reducer with a two-second sequence-gap watchdog: an unresolved gap closes SSE and replays from the highest contiguous cursor; a replay head beyond retained history rebases the reducer. Recovery diagnostics log only reason/ids/cursor/attempts/error type - never payloads. A terminal event buffered behind a gap for one second triggers reconciliation from canonical History, so completion never needs a manual reload.
- Streaming deltas are compressed before retention and all ride the ~33 ms flush: text deltas merge per phase, tool argument deltas per (run, tool call, phase), and tool stdout/stderr chunks per (run, tool call, stream). Per-chunk retention made the per-render active-run projection replay quadratic in streamed output size - a multi-MiB bash output froze the whole UI (fixed 2026-08-30). The replay cursor stays correct because every raw delta sequence also lands in `seenStreamingEventKeys`; terminal runs keep streamed stdout/stderr drafts visible until History confirms (same retention set as text drafts).
- The first delivered event of each new subscription is the transport-proven replay head: starting beyond the requested cursor rebases (the prefix left the bounded replay window); later gaps buffer until filled. Duplicates never duplicate timeline items. `provider_heartbeat` stores only its latest seconds-since-delta measurement (rendered as connection metadata, never progress). `stream_attempt_restarted` clears the failed phase's transient deltas, advances the phase, and stays sequence-accounted.
- Displayed Sessions reduce SSE plus mirrored WebSocket events in one contiguous-sequence reducer (either transport fills gaps, duplicates harmless, terminal buffers until complete). Non-displayed Sessions hold no SSE; their sparse stable WebSocket events reduce directly, and opening the Session reloads durable history. SSE is the only high-volume-delta source; WebSocket stable output is backstop, not competing projection.
- `connection_ready.active_runs` replaces locally projected active Run/Subagent status; excluded Runs still reattach SSE when displayed. If the displayed local Run is absent from reality, reconcile via `chat.history` before clearing (missed terminal -> durable final answer); once History confirms no active Run, discard all retained replay before rendering so sparse fragments cannot reappear behind it.
- Active snapshots preserve server timestamps (`currentRun.startedAt`; Child inspection keeps separate run/session start keys). One visibility-aware adaptive clock feeds elapsed times downward; Reasoning headers tick from first delta until the next stable boundary freezes the estimate (`reasoning_timing` replaces it once available).
- Terminal events settle the projection and close the stream. An explicit cancel merges the authoritative `chat.cancel` response events (only while that exact Run is current), promotes undispatched sibling Tool previews to settled-cancelled, and immediately reconciles durable History. When terminal live events overlap not-yet-loaded history, keep the richer history content and overlay live terminal status instead of reverting to a provisional completed state. `run_interrupted` is amber: preserved partial text stays visible, output-less interruptions still get a bare summary row, and no UI control starts another Run.
- The Iteration badge projects only reported numbers: seeded from `active_run`, advanced by each completed Model response regardless of sibling Tool count, settled terminally, restored from `run_summary`; a summary without the field means unknown - omitted, never estimated.
- `subagent_status_changed` is the explicit Parent-cancellation projection: spawn rows settle to cancelled even when the event belongs to a later/non-contributing Parent Run.
- Cancelling a Run and cancelling a cancellable tool call are distinct operations - preserve that in labels, availability, and error handling.
- `sendMessage()` and `editMessage()` resolve semantic outcomes after reconciling Session/Run/Queue state; the View snapshots display key and UI generation before awaiting either, then applies navigation/toasts/transient cards and scroll updates only while that generation is current. Edit admission calls `chat.edit`; only after success does the controller remove the targeted User message and later active suffix locally, attach the new Run stream, and clear Current Context Usage until the server refreshes it. Failure preserves the visible lineage unchanged.

## Timeline and Queue

- `visibleTimelineItemsForRender()` is the render boundary; item components display derived items and never reconstruct ordering from raw arrays.
- `appearance.chat_working_mode` is presentation-only: `compact` groups contiguous spans of >=2 visible Reasoning/Tool children into a closed Working disclosure (single children stay inline; Assistant output ends a span). The borderless summary says `working...` only while its group is a running Run's latest activity (latest Tool name allowed, never Reasoning), otherwise `done working`; opening preserves nested details.
- Persisted messages prune matching transient events, and a persisted Run Summary authoritatively removes inactive live fragments for that Run - never appended behind streaming history. A manual Compaction Run gets no Run Summary (it bypasses the chat loop's run-end path), so its persisted checkpoint plays that role: once History contains the `compaction_completed` checkpoint message, the Run's live block is retired like any other finalized Run. This dedup is what keeps the checkpoint separator from rendering twice - once from History and once as a live block appended behind the active Run - after the history reload a user message triggers via the agents refresh. A standalone Compaction Run (only compaction events) dissolves at the render boundary into its bare separator - no run header or footer - so both triggers render the checkpoint identically; failed or cancelled runs keep their (empty) block so the failure status stays visible, and an in-run auto Compaction never dissolves because its Run carries output/tool children. During an active Run, `compaction_started` inserts one amber in-progress divider; completion swaps in the completed label, abort/terminal removes the placeholder. The completed label carries the Compaction duration ("Context compacted in 45s") - both triggers stamp the observed wall-clock time as `compaction_duration_ms` into the checkpoint Usage at completion - and abbreviates token counts (254224 -> "254k", no unit word). Manual `/compact` is a server-owned Run entering the same path - the WebUI synthesizes no local Compaction state and does not reload History after the command succeeds. Completed checkpoints render their exact string content in a whitespace-preserving disclosure (no trimming, Markdown, or HTML interpretation) and store tokens in Usage so History reconstructs identically. History reconstruction preserves terminal semantics from summaries: cancelled settles open Tools/Sub-Agents as cancelled; interrupted drops preparing previews once stable interrupted output proves the call was discarded. Only the latest visible streaming child of a running Run may carry the working caret.
- A Run without a visible User anchor reconciles its persisted Assistant/Tool/checkpoint segment with live children by Message and Tool-call identity, preserving the prefix absent from bounded replay and retaining new text, Reasoning, Tool activity, and stdout/stderr. Fresh text phases never overwrite finalized answers. Retained older Run groups absent from the loaded page are inserted chronologically before the tracked turn rather than appended behind it; persisted History order and live User/Assistant pairing remain intact. Error-message overlap is deduplicated against the final selected timeline, so an error stays visible once whether its History row or live row supplies it. Regression coverage lives in `chatState.test.history-reconciliation.test.js`, `chatState.test.controller.test.js`, and the mounted `ChatTimeline.test.live-runs.test.js` suite.
- Transient command cards (`/status`, `/help`) are non-persisted and anchor to the timeline item they followed at creation. A history reload replaces live Run ids with history ids, so the card re-anchors by creation time - after the last item whose timestamp predates the command - instead of sinking below newer messages; cards created on an empty timeline stay at the top, and cards without a creation time keep the end-of-timeline fallback (`groupTransientCards` in `chatTimelinePresentation.js`).
- Expanded Tool details render image thumbnails from `read_media` result artifacts and presentation-only display image references. `chatToolDetails.js` accepts only image MIME types with valid Attachment identities, never local paths or external URLs. Both ordinary Run rows and standalone Tool events share this selection; thumbnails open the existing Timeline lightbox by pointer or keyboard, retain modifier-click navigation, and reconstruct from History. Older `analyze_image` calls without saved preview references have no thumbnails.
- Preparing Tool rows derive safe preview arguments from completed top-level string fields only; stable arguments replace them at `tool_call_started`. Expanded details decode an outer payload once and render Args/Stdout/Stderr/Result as ordered sections preserving types (objects -> key/value fields, arrays unwrapped per line, explicit empties shown, CR/LF visible, escape sequences literal); Copy uses the exact sanitized representation.
- Tool rows consume the structured display snapshot before the narrow historical fallback: single-line order dot/name, primary values, typed facts, status/duration, actions; the 64-character semantic budget governs paths/prose/URL ends; quick tooltips cover non-copyable full values while copyable ones use the shared card (hover dwell 500 ms, focus/touch immediate). A successful envelope with `data.status: "partial"` renders as a settled amber partial state, distinct from both green success and red failure. Unknown Tools never leak raw arguments into the collapsed row.
- The special Sub-Agent row belongs only to `subagent` action `run` (navigation/progress/cancel); other actions render as ordinary rows. Results expose the stable public id only; internal handles arrive solely via live `subagent_session_started` events for accessor use, and `chatState.js` resolves public ids through `subagent.inspect` with bounded caches - Timeline components render supplied state and start no recovery requests. Legacy transcripts without work ids fall back conservatively through exact-Run history matching.
- Cancellable background Bash/Sub-Agent rows use shared icon buttons with immediate pending state; a finished Sub-Agent keeps its neutral navigation control. A handed-off Bash row tracks its process, not the ~instant delegation call: the dot shows running and the time label ticks from the Tool call's internal start timestamp until a terminal status arrives (`bash_process_status_changed` live event or the durable `background_bash_statuses` fold), then the dot settles and the label becomes the process's real runtime measured by the terminal notification; without known times the label stays empty rather than showing the ~0s delegation duration, and the expanded Result section swaps the handoff envelope for the actual completion result on the same terminal data. Live terminal data is a bounded in-memory projection keyed by process id, so after a full page reload terminal rows settle from History without a runtime.
- The floating Activity panel lists automatic-delivery Sub-Agent spawns and handed-off Bash processes from the loaded Session only; foreground/synchronous work stays Timeline-only. Rows partition into Active/Finished; active rows carry navigation plus cancel delegating through the controller (Bash via `chat.cancel_process`, an explicit user cancellation), finished rows none; Bash rows carry the same tick/runtime time label as their Timeline row, and the panel's clock runs only while it is open and something is actually running (the clock effect depends on a value-stable flag, never on the ticking task lists - otherwise Svelte reports `effect_update_depth_exceeded`). `chat.history.background_bash_statuses` folds durable results by Process Session id so rows survive reload; switching Agent/Session swaps projections immediately; terminal `bash_process_status_changed` events merge into a global bounded projection keyed by process id that wins over the durable string statuses.
- Copy actions preserve semantic boundaries rather than copying rendered DOM: Assistant copies join that Run's Markdown sections, user copy reconstructs mentions minus binaries, reasoning/output copy independently, Tool copy uses the sanitized displayed value. `MarkdownContent.svelte` is the safe-Markdown owner (shared CopyButton in fenced-code headers, withheld while streaming incomplete); complete HTTP(S) URLs become safe new-tab links in Assistant Markdown and escaped user plaintext, everything else inert. The Reasoning-only normalizer strips Provider HTML-comment separators and splits adjacent bold blocks without touching canonical content.
- Public History marks only server-approved plain-text WebUI User messages as `editable`; structured/Channel messages and messages before the latest Agent Takeover never expose the action. `ChatTimelineEntry` swaps the message body for an inline editor with explicit cancel and `Save & restart`; edit is disabled while History loads, a Run is active, or the Queue is non-empty. The hint describes removal from the active conversation, not deletion from storage.
- Assistant file delivery arrives pre-projected as relative `/api/files/` URLs (images inline/lightbox, others as links); the WebUI never sees `output_files` metadata or resolves server paths.
- The server owns Queue order, contents, and `editable`. Optimistic continuity is allowed, but `syncQueueFromServer()` is authoritative and applies only the newest outstanding response per Session. Only losslessly textual items expose the editor; structured/attached/truncated items stay removable only. Queue updates report semantic success and close only then; failures preserve input.
- `connection_ready.queues` authoritatively replaces every held Session's Queue projection (including clearing scopes missing from the snapshot); on `epoch_changed`, locally known ids absent from the new process trigger a restart-loss notice, while same-process gaps reconcile silently.
- Queue invalidation addresses exactly its Agent/Session - switching Sessions never shows another's queued items.
- The timeline is the only scrolling surface, coordinated by `createChatScrollController()`: per-Session pinned flag plus reading anchor (item id + offset), one writer recording expected positions (its echo never reclassifies ownership), user motion classified from live position, upward input releasing the pin before the browser scrolls. Bottom growth never moves reading position; growth above the anchor corrects once through it. Navigation restores saved viewports, explicit Sub-Agent links open pinned at bottom, sending pins to the bottom so the incoming response is always visible, and Jump-to-latest appears only away from the live tail.
- The composer floats as an absolutely positioned overlay over the full-height timeline: its measured height reaches the timeline via `--chat-overlay-height`, the overlay ends before the scrollbar column (`--chat-scrollbar-width`), and reserved space is a trailing in-flow block (Chromium drops bottom padding/margin from scroll extent) - autosizing therefore never changes content geometry.

## Composer and inputs

- `ChatComposer.svelte` owns draft entry and delegates parsing/media to established helpers; every submission variant uses the same resolved address.
- Submission serializes from an initial snapshot (text, origin, attachments, callbacks) through file-mention resolution and admission; only a confirmed successful outcome clears draft and attachments - failures and mid-flight additions stay editable. No-argument immediate Commands enter the same guarded path.
- Setup guidance is prerequisite-ordered: missing Provider routes to Settings -> Providers before model-less-Agent guidance routes to Agents; readiness is never inferred from the Model catalog, and neither prompt shows while Settings are unresolved.
- Slash Commands and Skills come from the server catalog submitted through the command contract - no competing frontend roster or backend-semantics interpretation. Catalog loading guards on Agent address plus the App-owned refresh token, so Extension lifecycle changes refresh autocomplete without disturbing selection or draft.
- File mentions constrain to the server-provided list for the active address; attachment ids stay opaque with safe server URLs for preview/download. Image cards render their persisted Session reference (for example, `Image 1`) as the normal label and retain the original upload filename only as hover detail, matching the Model-facing reference.
- The `/model ` autocomplete opens on demand (catalog fetched only when triggered), reuses the Agent-dropdown suitability filter and show-all toggle, auto-submits the selection through the guarded path, and shares one keyboard contract with the skill/file popups. Enter/Tab selects only the visibly active row; if a list change leaves the active index out of range, selection returns false instead of falling back to an unmarked first row.
- Speech input releases every media resource (tracks, recorder, timers, object URLs) on completion, cancellation, replacement, teardown, and failure - cleanup best effort across failing tracks. A pending browser microphone permission request cannot be aborted, so teardown invalidates it and a late recorder result must release its tracks without starting capture. The native recorder container uploads as-is; `SpeechService` converts to the server-wide Voice -> Transcription profile, so Chat and wakeword capture share one Provider-facing audio policy.
- Drafts and completed pending Attachments are interaction state keyed by the full displayed Session address; refresh or selection transitions never silently submit or cross-address either. A pending Attachment becomes Model-visible only when that Session's send is admitted.
- Composer focus follows deliberate navigation only (New Session always; user-driven selections after destination history settles, desktop only; mobile stays in reading mode with `preventScroll`) - passive changes (reconnects, invalidations, mount restoration) never steal focus.

## Usage and errors

Chat shows three distinct server-owned projections: last-step Provider Usage, cumulative Session Usage, and Current Context Usage (restored from History, updated from live/terminal events; badge uses `{tokens, estimated}`, tooltip exposes provenance). The frontend formats but never sums, recalculates cost, or infers missing values; cache counts are input subsets, provider-reported reasoning an output subset, absent counters stay absent, and `reasoning_turns` distinguishes no-reporting from zero.

Errors normalize at the transport boundary, then attach to their Session/Run/Queue operation/toast; command-catalog errors use latest-request-wins. Admission failures never become Run failures, and rendering a failure discards no recoverable history nor leaves a finished Run marked active.
