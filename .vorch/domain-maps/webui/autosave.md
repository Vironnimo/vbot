# WebUI Autosave

Read before adding or changing editable configuration, an existing-record editor, save controls, or navigation that can replace an editor, including Extension-owned pages. This is the shared UI persistence contract; backend validation and storage remain with the owning domain. Source and test paths below are repository-relative; map pointers resolve under `.vorch/domain-maps/`.

## Scope and ownership

- Use the shared autosave mechanism for editable settings and existing configuration records. Extend the existing editor/controller for payload validation and reconciliation; timing, serialization, pending-state tracking, and transition flushing belong to `webui/src/lib/autosave.js`.
- Creation, credentials, destructive actions, and operational commands retain their explicit submission semantics. A text field alone does not imply autosave: sending a Chat message or starting a Run is an action, not configuration persistence.
- Show the editor's save state after the fields, right-aligned inside the content scrollport, with `components/ui/SaveStatus.svelte`; it needs no sticky or permanently reserved footer. At rest it shows nothing. While `participant.hasChanges()` reports an unsaved draft it offers a small tertiary Save action that runs the same tracked save operation, which is also the retry after a failed save. While the editor's reactive `saving` flag is set it reads "Saving..."; when a write ends with nothing pending it shows a green check and "Saved" for about two seconds before fading. The text is a `role="status"` live region, and keyboard focus on the Save action moves to it when the action disappears. Pass `pending={participant.hasChanges()}`, not `hasPending()`: the in-flight part of `hasPending()` is plain JS state that Svelte cannot observe. Success is inferred from `saving` turning false while `pending` is false, so the editor must reconcile its baseline before clearing `saving`. The save state is the whole confirmation: an unchanged editor offers no Save, and saves raise neither success nor "Already saved" toasts; errors stay inline or in an error toast.

## Integrating an editor

- Prefer `createDebouncedAutosave({ getSnapshot, hasChanges, save })`. Schedule from the reactive draft effect with `scheduleRun()` and cancel through `cancelPendingTimer()` on cleanup. The helper reads the full snapshot in that effect so every edit restarts the timer; observing only a dirty boolean misses later keystrokes.
- Collection editors or immediate discrete controls can use `createAutosaveParticipant`; collection timers use the shared `scheduleAutosave`. Do not introduce a separate timeout, save queue, or navigation-flush implementation per tab. Checkboxes and pickers use the same tracked operation without waiting for text completion.
- Snapshots must include all edited values and the target identity when an editor can switch records. `hasChanges` compares the draft with its persisted baseline. `save(reason)` validates and submits a captured draft, returning `true` only on success and `false` on validation or persistence failure.
- Register the participant with `useAutosaveContext().register(...)`, unregister on destruction, and route editor-replacing selection/navigation through `requestTransition(...)`. Manual Save uses the same participant through `runSave('manual')`, which cancels the pending timer and also retries a snapshot whose automatic save failed. `force: true` runs the save even when `hasChanges` reports nothing, for writes the draft comparison does not cover (a creation, or Agent Workspace/Project changes that automatic saves skip).
- Extension pages register with `extensionPageClient.registerAutosave(participant)` and publish changed pending state with `notifyAutosave()`. The host joins the App coordinator; the Extension still owns its domain draft and payload. See `resources/extensions/swarm/ui/ProfileEditor.svelte` for this integration.

## Input continuity and failure behavior

- The common idle interval is 800 ms from the latest edit. Focused number/decimal controls wait for blur; IME composition waits for completion and the idle interval. Explicit Save and transition flushes do not wait for the timer. Shared `TextField` and `TextArea` report composition through `autosaveInput`; custom native editing controls need equivalent integration.
- Keep controls mounted and editable during automatic saves. Reconcile the response into the persisted baseline without replacing newer draft values, stealing focus, or remounting the editor through a loading state. Normalize numbers at the payload boundary, preserving incomplete input while it is edited.
- The participant serializes writes. Transition flushing waits for in-flight work and saves remaining newer snapshots before leaving. Failed unchanged snapshots do not retry in a background loop; retain the draft and visible error. App-level navigation failure, the still-saving prompt and Retry / Discard behavior belong to `webui/app-shell.md`.
- RPC calls have no deadline, so a write can hang. When the user leaves while writes run, App calls the coordinator's `releaseRunningSaves()`: each participant's `release()` stops holding transitions for the write running now. That write finishes in the background; `hasPending()` and `flush()` ignore it while the draft is clean or equals the snapshot it writes. An edit made after it started still waits for it, because writes stay serialized, and is then saved from the current draft. The Extension page host forwards `release` to its frame (`vbot.extension.autosave.release`) and stops sharing the running flush, so the next transition asks the frame again; the frame's participant answers it at once unless edits were made after its running write started, and reports its pending state again. A participant without `release` (a custom Extension page participant, or a page built before the message existed) keeps holding transitions until its flush settles; the host's flush gives up after 35 s. Coverage: `autosave.test.js` (released save), `ExtensionPage.test.js`, `extensionPageClient.test.js`.
- The helper does not replace the editor's reconciliation or backend validation. A successful response for an older draft must not mark a newer draft saved. Pending-state and save decisions follow the current persisted baseline through `hasChanges`, never a cached formerly successful draft: an external refresh can make an unedited draft differ from the baseline, and its save is then refused and rebased instead of reverting the refresh (Concurrent writers). Successful saves must reconcile that baseline before resolving. `hasChanges`, the scheduling guard, and the save's no-op check must use one comparison: when the payload normalizes a value (a cleared number becomes its default), compare normalized draft and baseline; `createSettingsDraft` carries the saved values into the fields not edited during the request. A raw comparison against a normalized payload stays pending after every successful write, so the transition flush repeats identical saves until it fails (Sub-Agent and Web Search regressions: `SettingsView.autosave.test.js`; Agent Defaults regression: `SettingsDefaultsPanel.test.js`; all mounted through `AutosaveContextHost.support.svelte`).

## Concurrent writers

- Settings editors write through `createSettingsDraft` (`webui/src/lib/settingsSave.js`): `fromSettings` projects Settings to draft values, `toPayload` builds the update sections, `read`/`write` access the editor's reactive draft, and `save({ onCommit, onError, setSaving })` runs the save lifecycle. It keeps the origin (the saved values the draft derives from) and sends `toPayload(origin)` as `base` (`settings.md` -> Public surface), so a write that would replace a value changed meanwhile - by another window, an Agent, or a released save that finished after the user left - is refused with `settings_conflict` instead of reverting it. A later editor seeded before a released save landed is the common case. The write is `toPayload(draft, origin)`, so a payload may name only what changed; `submit` replaces `settings.update` for another based writer and resolves to the saved Settings.
- On a conflict the helper re-reads Settings (`getSettings`), commits them, and rebases the draft per leaf (`rebaseDraft`): values the draft left alone take the saved ones, values only the draft changed stay, and a value changed on both sides takes the saved one (first committed wins) and shows the `settings.saveConflict` notice. It then retries the remaining edits, at most three writes in all. After a successful write, values edited during the request stay and the others take the returned values. `leafDepth` makes every value that many keys deep one leaf, for values whose parts are only valid together.
- Specialized Models (`SettingsSpecializedModelsPanel.svelte`) uses the helper with `task_model.update` as `submit`: it writes only the bindings of its placement that the draft changed, with all of them as `base`, and merges each binding as a whole (`leafDepth: 1`), because a binding's options belong to its target. Its `write` reloads the option controls of a task whose target a rebase changed; autosave stays armed only by user edits and disarms after a save that no newer edit followed.
- Editors that replace a whole object outside the helper apply the same rule with `rebaseDraft` and `isSettingsConflict`: OpenRouter routing (`OpenRouterRoutingSettings.svelte`) and the Extensions panel's configuration autosave and enable toggle (`SettingsExtensionsPanel.svelte`, which writes the full-replace `extensions` section). The panel builds each write from the saved section `extensions.list` returns (`buildExtensionsUpdate`), changing only the toggled or edited Extensions and sending that section as `base`; built from the records instead, a saved `disabled` order other than load order (`vbot extensions disable` appends) or an entry of an Extension that no longer loads would change leaves the `base` never matches, so every save would be refused.
- Editors that send only the leaf the user changed send no base, because a stale baseline cannot revert other values there and the same leaf stays last-writer-wins: the timezone and keep-awake switches (`SettingsGeneralPanel.svelte`, which also rebases unedited values on refresh), local Model context windows (per key), and DebugView's `debug.trace_limit`.
- Coverage: `settingsSave.test.js`, `SettingsView.autosave.test.js` (rebase onto a value saved elsewhere), `SettingsSpecializedModelsPanel.test.js` (bindings changed elsewhere), `OpenRouterRoutingSettings.test.js`, `SettingsExtensionsPanel.test.js`.
