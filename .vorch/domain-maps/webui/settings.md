# WebUI Settings

Read this reference only for WebUI Settings, Provider, Extension, Skill, Agent, onboarding, appearance, channel, logs, or Desktop Voice work. Backend policy and persistence remain in the corresponding domain maps.

## Settings shell

`SettingsView.svelte` opens General and exposes five category destinations: General, Sessions & Memory, Tools & Media, Connections, and System. A category shows its related feature cards together; expanded editors stay mounted to preserve drafts and Provider authentication state. The General page exposes Appearance and Region/setup directly. Feature headings open compact editors; deep links select the owning category and expand the exact feature. Search indexes hidden rendered text, normalizes punctuation/spacing/diacritics, and points to the canonical editor. Shared Model/Thinking/fallback defaults and Compaction live in Agents; a Settings search result routes there without mounting duplicate editors. `SettingsGeneralPanel` still owns the Region/setup and System projections, each rendered once.

The Compaction Policy editor keeps the pure absolute Trigger and also exposes an optional maximum-input-token cap alongside the Context ratio. Its shared normalizer omits an empty cap and preserves a positive cap in every scope payload, so `0.8` plus `200000` means whichever boundary is reached first.

The App shell retains the selected Settings feature, expanded cards, and scroll offset while another main view is active. `SettingsView` restores that offset while independently loaded content settles; deliberate deep links replace the remembered page. There is no scrollspy or document-tail spacer. The compact five-category picker replaces the second navigation column through tablet widths.

`settingsView.js` owns normalization and payload builders shared by the panels. Each panel loads and submits through `api.js`, keeps editable values local until save, and adopts server responses after mutation. Decimal settings remain strings during editing and are normalized only when building the payload.

Settings-style panels register their pending local draft and save lifecycle with the App autosave coordinator via `createDebouncedAutosave({ getSnapshot, hasChanges, save })` (`webui/src/lib/autosave.js`, `DEFAULT_AUTOSAVE_DEBOUNCE_MS` = 800 ms, `scheduleRun()`/`cancelPendingTimer()` + `participant`). The `$effect` in each panel only calls `scheduleRun()`/`cancelPendingTimer`; the helper owns the timer handle, the single participant, and the cancelPending wiring. The coordinator-shared 800 ms debounce and explicit Save action use the same tracked operation, so leaving Settings waits for an in-flight request and persists a newer snapshot when the user edits during that request. Failed unchanged snapshots are not retried in a background loop; an internal context transition remains blocked until the App-level Retry succeeds or the user explicitly discards the draft. Cross-cutting value coercion for JSON-derived data lives in `webui/src/lib/values.js` (`isPlainObject` strict `[object Object]`, `asText`, `asOptionalText`).

## Providers and models

- Provider rows distinguish added Connections, configured credentials, usable Accounts, reachability, and enabled state. Those values come from backend contracts; the UI must not infer connectivity from the presence of a masked credential or a Model result.
- Connect and disconnect payloads preserve Provider id, connection id, and account id. OAuth, device-flow, API-key, environment, local, and keyless connections have different affordances and must not be collapsed into a single credential form.
- Adding a Provider means exposing a backend-advertised Connection candidate. Keyless local Connections use the same Add Provider flow: adding persists enablement and triggers discovery but never loads a Model. The frontend does not maintain its own Provider registry.
- Adding a Custom Provider is a separate full entity flow owned by `SettingsProvidersPanel` plus `CustomProviderModal`: the form edits the Settings-backed name, stable id, allowlisted Adapter, endpoint, auth mode, optional write-only API key, discovery path, and zero or more manual Models with task/capability facts. Create/edit/delete use `provider.custom_*`, refresh the server-owned Provider/Model projections, and never rehydrate a secret. Delete confirmation states that existing Model references remain but become unavailable.
- Model pickers share server suitability/filtering results. `createModelCatalogLoader()` is the common versioned reload boundary used by Agent and default-Model views: only the newest request may publish a catalog or error, and invalidation prevents a response from updating an unmounted owner. A new refresh clears any deferred catalog snapshot from an older autosave boundary, saves the canonical Model id, and reconciles to returned Settings.
- `SettingsSpecializedModelsPanel` renders backend-discovered task targets from the generic `TASK_MODEL_ROWS` contract. Its schema requests are versioned per task and bound to the selected Provider/Model target, so a delayed response cannot populate or save options for a newer selection. Its image rows are distinct: `image_understanding` configures the route-gated `analyze_image` Tool for Main Model routes that cannot carry images, while `image_generation` configures output creation/editing. The UI stores bindings only; Chat and `TaskModelService.binding_is_usable` own whether `analyze_image` is actually Model-visible.
- The expanded OpenRouter row owns a routing editor with a global scope and optional full per-Model overrides. `automatic` leaves OpenRouter-managed Sticky Routing eligible while permitting blocks, `allowed` restricts candidates without imposing order, and `ordered` exposes priority controls plus an explicit cache-affinity warning because OpenRouter ignores Sticky Routing when `provider.order` is present. Global blocks remain effective inside Model overrides. An always-visible info banner states that Sticky Routing is best effort and identifies one exact allowed endpoint with fallbacks off as the no-switch configuration.
- Routing Provider choices are backend-advertised through `provider.routing_options`: base slugs globally and exact endpoint tags for the selected Model. The editor remains operable with a validated custom slug when a catalog omits an endpoint, but it only auto-loads catalogs while OpenRouter has a usable Connection. Saves send the complete `providers.openrouter.routing` object and reconcile through a Settings reload.

## Extensions, Skills, Agents, and channels

- The dedicated Skills management surface moved out of Settings into the Configure -> Skills view (`webui/src/components/skills/`, see the WebUI map's Interfaces); Settings keeps no Skill section. Agent editors still use Skill *selectors* (below) for per-Agent allowlists and authoring entry points.
- Extension management renders the backend-provided capability, status, schema, waiting, and configuration projections, including declared Slash Commands and whether each is currently registered. Commands are code-owned capabilities summarized in the existing row, not editable Settings. Only an Extension with a non-empty Settings Schema receives a configuration disclosure; schema-less Extensions expose no generic editor. The loaded MCP Extension embeds its dedicated connection manager independently of Settings Schema. Schema forms preserve unknown/non-secret config through the backend contract; secrets use the dedicated secret operation and are never rehydrated into normal form state.
- A transition flush batches all changed non-secret Extension schema forms into one complete `settings.update` projection so independently edited rows cannot overwrite each other. Invalid schema drafts fail the transition in place. Secret values remain outside autosave and retain their explicit per-secret operation.
- Reload, enable/disable, and configuration changes are separate operations. Live capability ownership remains in the Extensions domain even when the panel displays its result.
- Skill selectors retain the shared catalog/chip behavior and explicit scope. Identity Agent Tool policy uses `ToolAccessEditor`: a compact All / Choose / None mode control, search, a responsive grid of real registry-family cards plus one `Individual Tools` card, one bulk switch per real family, and wrapping name-only binary Tool chips. Known Built-in family ids retain i18n labels; Extension families render the server-projected `family_label`, and a family with fewer than two members in the current catalog/ceiling folds into Individual Tools without changing identity merely because search hides siblings. The UI translates each binary click into canonical `allowed`/`denied` semantics instead of exposing separate Off and Block controls; automatic Tools use a neutral dashed treatment and keep activation/readiness details in hover/focus content. Gated, unavailable, and stored-but-unregistered Tools stay visible and editable. Changes autosave through the Agent editor's normal reconciliation boundary. Creating or editing Skill content uses the Skill API; selecting a Skill or changing Tool Access only changes that owner's policy.
- Agent detail uses the shared `TabList` for Overview, Behavior, Tools & Skills, and Details. Topic switches retain the editor and use the App autosave coordinator; save remains outside the scrolling content. Overview leads with Model/Thinking and then name/Project; Behavior owns Compaction/System Prompt/Memory, and Details owns identity/Workspace/metadata/deletion. Agent editors preserve inheritance versus explicit override. System Prompt block editing, preview, reset, and layout changes use their dedicated backend contracts rather than treating the composed prompt as one editable blob; a scope load may update scope, blocks, preview, error, and loading state only while it remains the newest request for the still-selected scope.
- `AgentsView` owns a separate Shared defaults destination alongside the real Agent roster. Ordinary entry opens the selected Agent; opening Shared defaults retains that selection and the mounted editor. It loads Settings before mounting the existing Defaults/Compaction panels, routes transitions through autosave, and refreshes the authoritative Agent roster after successful saves so inherited values update without converting explicit overrides. The App routes defaults/Compaction links from Projects into this destination and consumes the target so ordinary returns still open the individual Agent.
- Channel forms keep platform, DM scope, allowed chat ids, enabled state, and runtime status distinct. A saved channel is not necessarily enabled or currently running. Each Channel card also loads the independent durable access projection: groups show stable scope ids and seen participant name/id/role rows; `This is me` selects the Channel-own identity, and role actions call additive grant/revoke RPCs then reload saved state. The own identity is visibly `Me`, remains admin, and cannot be demoted from the UI.

## Onboarding and appearance

- `onboarding.js` derives operational readiness and the recommended next action from server-backed Settings, Provider Connections, and the target Agent's Model state. Operational readiness requires at least one Connection whose server-projected `usable` value is true; a fresh keyless Connection remains an Add Provider candidate, while an added-but-disabled keyless Connection remains visible in Provider management without becoming operational. The frontend does not persist a second readiness flag or reconstruct usability from credentials, Account state, enablement, or reachability.
- Automatic onboarding is a one-shot entry into the Settings surface; users can later reopen the flow explicitly. Completing one step refreshes the underlying resources before deciding the next step.
- Provider recommendations and model-search prefills are presentation guidance. Availability and connectability still come from current backend data.
- Appearance saves language, Chat width, and the `normal` / `compact` Working presentation through Settings. `appearancePrefs.svelte.js` projects both Chat display preferences app-wide so a successful save reflows the open Chat without a reload; changing the active language updates i18n immediately while persisted state still reconciles to the save result.

## Desktop app settings and browser boundaries

- `desktopBridge.js` is the only browser-side seam for the native desktop bridge. Web-only accessors must remain functional when no bridge exists.
- Desktop capability discovery independently gates `serverSelection` and `wakeword`. Desktop accessor startup keeps retrying while the asynchronously injected bridge is absent or rejects the capability call; only a successful response is authoritative. When server selection is available, Settings inserts a Desktop app group between Behavior and System for Connection. Voice is always a server-owned Behavior section; only its Wakeword rows are capability-gated.
- `DesktopConnectionSettings.svelte` manages the Desktop-local remembered-server list through `desktopBridge.js`: `listServers` marks the active target, add/remove mutate only the OS per-user Desktop config, and a switch probes through `selectServer` before JavaScript applies the returned URL. The component is reused inside the AppShell outage modal, where it remains interactive outside the otherwise inert server-backed content.
- `wakewordSettings.js` separates saved Voice settings from runtime wakeword status. Payload builders submit the ordered one-to-two `active_model_ids`, keyed `model_sensitivities`, stable `{index,name,host_api}` microphone identity, and routing configuration; structured values are compared, cloned, and snapshotted by value so status subscriptions cannot overwrite in-progress edits. Transient guided-calibration phase, scores, noise levels, repetition counts, target model, and recommendations are runtime-only and never enter config payloads or dirty-state comparison.
- The Voice panel saves one server-wide `speech.transcription_audio` projection for the Chat microphone and post-Wakeword command recording. It exposes the `compatibility` (WAV/16 kHz), `high_quality` (FLAC/48 kHz), and `custom` profiles; custom keeps mono PCM16 fixed while allowing WAV or FLAC and 16, 24, or 48 kHz. These controls remain available in browser accessors. When Desktop Wakeword capability exists, the same panel also obtains the authoritative model catalog through `listWakewordModels()`, distinguishes curated Built-ins from imported TFLite models, presents one or two simultaneous active phrases with independent sensitivity sliders, imports finished custom models through `importWakewordModel()`, and gates permanent removal of inactive imported models with the shared `ConfirmDialog`; custom training is not a WebUI responsibility. Guided calibration presents the Bridge-owned ambient-noise, per-phrase repetition, and review phases; identifies which model to say; visualizes score, session peak, noise, and the proposed threshold; and disables manual sensitivity editing until complete. Discard restores the session baseline, Restart discards measurements and returns to the noise phase, and Apply copies the complete recommendation set into the saved per-model sensitivities.
- Imported-model paths are Desktop-private. The browser receives only the descriptor fields required for selection and management, rejects files over 20 MiB before FileReader/base64 expansion, and transfers accepted file content as base64 only for the explicit import call.
- Real Wakeword activation consumes the bridge's explicit `{ enabled, error_code }` result. A rejected STT readiness check keeps the toggle off and renders the actionable reason in the Voice panel; the app-level sequence-numbered event consumer independently raises global Toasts for sent commands, no-speech, transcription failure, and fatal errors so the active main view does not hide Voice feedback. Runtime microphone loss is distinct: `microphone_disconnected` - whether the microphone was lost while listening or was already missing at startup - renders as an amber warning in the Voice panel and an auto-dismissing warning Toast, never as a sticky error.
- Bridge discovery, event subscriptions, polling, and media/runtime listeners require explicit retry, timeout, and cleanup behavior. The Voice panel reacts when the Desktop capability becomes available after mount, retries a failed initial status/model/microphone load without accepting false defaults, and may not start polling after unmount. UI state must not claim the wakeword runtime is active merely because the saved setting is enabled, and a disabled activation that failed must retain its red error indicator until the next state transition. Enable/disable and model actions disable conflicting controls while in flight; the Bridge lifecycle remains authoritative for serialization.
- Log listing and file reads use RPC; live tailing uses the dedicated log WebSocket. Log content is display data and must not be interpreted as HTML.

## Extension input outside Settings

`ExtensionRequests.svelte` is mounted in the App content area and polls the shared Extension request projection with owned cleanup. A pending request shows a review banner; the shared Modal displays the external message, schema-derived controls, or a safe HTTP(S) login link and redirected-address field. Accept/decline/cancel use the Extension's declared response operation. Form validity remains server-owned. Polling does not reset an open draft, and a resolved or cancelled request dismisses its dialog. Tests: `ExtensionRequests.test.js` and `extensionInputs.test.js`.


## MCP connection management

`SettingsMcpPanel.svelte` renders local/HTTP/SSE connection forms, exact argument rows, Agent grants through the shared Identity/Project target catalog, advanced connection fields, write-only credentials, enable/disable, removal confirmation, and asynchronous connection tests. It is embedded in the loaded MCP Extension row. `lib/mcpSettings.js` owns management RPC workflows, current-state reconciliation, and disposable polling; form drafts stay in the modal and status updates never replace them. Saving is explicit because it starts or replaces an external connection. A preflight read rejects a duplicate create or an edit whose saved record changed; this is UI conflict detection, not an atomic backend compare-and-swap. Existing Tool denials and Project ceilings remain authoritative.

Credential values go only to the dedicated operation and are never added to connection records or retained controller state. Test jobs remain cancellable and use the existing global Extension input dialog for authentication/questions; test output shows verification results rather than dumping the catalog. Test failure stops automatic polling until Retry. Regression coverage: `SettingsMcpPanel.test.js` and `lib/__tests__/mcpSettings.test.js`.


## System Prompt inspection

`SystemPromptView.svelte` owns the persistent Agent selection and Prompt / Tools / Edit blocks navigation above the scrolling content. Prompt opens as a readable Markdown document with a separate verbatim Original text representation; Copy always uses the original text. The view describes current Agent configuration rather than claiming to reproduce a running Session. Agent changes pass through the autosave boundary, select an available custom scope or Default, and invalidate old preview responses; refresh clears stale content and failures expose Retry. Edit blocks remain mounted across tabs, retain drafts and expansion state, and distinguish disabled/inherited state without reducing content contrast. Scope deep links open the editor.

`ToolDefinitionsPanel.svelte` owns the read-only search and selected-definition display, using `prompt.preview(include_tools=true)` rather than reconstructing Tool policy from the management catalog. It preserves full descriptions and parameter schemas and offers the complete definition as JSON and clipboard content. Token estimates remain separate from the definitions. Regression coverage is in `components/__tests__/SystemPromptView.test.js`; shared contrast/surface invariants are in `lib/__tests__/uiPrimitives.guard.test.js`.
