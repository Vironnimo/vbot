# WebUI Settings

Read this reference only for WebUI Settings, Provider, Extension, Skill, Agent, onboarding, appearance, channel, logs, or Desktop Voice work. Backend policy and persistence remain in the corresponding domain maps.

`settingsView.js` retains the public pure-helper interface. Internal `lib/settingsView/` modules own appearance/audio, Agent defaults, retrieval, Channels, Extensions and Provider/account projections; forms keep their existing payload and normalization contracts.

## Settings shell

SettingsView.svelte opens General and organizes settings into seven pages by user task: General (display, Session titles, region/setup), Providers, Voice (speech Models and voice controls), Memory (Recall, embeddings and Reflection), Tools (web search/reading, media Models, evaluation and Sub-Agent limits), Integrations (Channels and Extensions/MCP), and System (server, optional Desktop connection and Debug). Sections are visible together within a page; editor component boundaries do not define navigation entries. Providers links to Agents' Shared defaults, the sole editor of shared Model/Thinking/fallback defaults and Compaction.

Hidden pages and their sections stay mounted to preserve drafts and Provider authentication state. Search indexes rendered section text and page labels, normalizes punctuation/spacing/diacritics, and returns sections with their owning page. Selecting a result or a section deep link opens the page, scrolls to the section and focuses its heading. A section destination stays anchored while asynchronous content above it settles, until user interaction releases restoration. Ordinary page changes focus the page heading and reset its scroll. Both use the autosave transition boundary, as does the Shared defaults shortcut. SettingsGeneralPanel still owns regional preferences and server information, each rendered once.

The shared `CompactionPolicyEditor.svelte` leads with the Classic (`continuation`) / With tail (`summary_tail`) radio group, then conditional tail fields, then automatic enablement and Trigger settings; mode selection does not change enablement. Component coverage lives in `SettingsView.test.behavior.test.js`. It keeps the pure absolute Trigger and also exposes an optional maximum-input-token cap alongside the Context ratio. Its shared normalizer omits an empty cap and preserves a positive cap in every scope payload, so `0.8` plus `200000` means whichever boundary is reached first.

The App shell retains the selected Settings page and scroll offset while another main view is active. `SettingsView` restores that offset while independently loaded content settles; deliberate deep links replace the remembered page. There is no scrollspy or document-tail spacer. The compact page picker replaces the second navigation column through tablet widths.

`settingsView.js` owns normalization and payload builders shared by the panels. Each panel loads and submits through `api.js`, keeps editable values local until save, and adopts server responses after mutation. Decimal settings remain strings during editing and are normalized only when building the payload.

`appearancePrefs.svelte.js` owns applying canonical appearance snapshots (language, Chat width, and Work details) for both App setup and SettingsView loads/commits. The Appearance panel submits its draft and forwards the response; it never publishes draft values into global preferences after an awaited save. A newer draft remains editable, and a failed follow-up save leaves the last confirmed appearance active (`SettingsView.test.appearance.test.js`).

Provider operations and Model/Provider invalidations call `SettingsView.refreshProviderSettings` through `onRefreshProviderSettings`. This refresh replaces only the `providers` and `local_models` projections, preserving mounted editors, unrelated baselines, drafts, and in-flight saves. Provider projection commits use the separate `onCommitProviderSettings` boundary; unrelated Settings commits preserve the current Provider projection before publishing to App. Initial Settings loading owns the blocking loading/error surface; refresh failures report through the caller and retain the current editors. Newer refreshes and teardown invalidate older replies; a Provider-owned commit restarts a pending refresh so a Model-refresh result cannot discard another Provider invalidation (`SettingsView.test.provider-refresh.test.js`).

Before adding or changing panel fields or saving behavior, read `webui/autosave.md` for the shared integration and input-continuity contract. Settings panels keep domain-specific normalization and payloads here; save timing, serialization, and transition flushing use that common mechanism.

Cross-cutting value coercion for JSON-derived data lives in `webui/src/lib/values.js` (`isPlainObject` strict `[object Object]`, `asText`, `asOptionalText`).

`WakewordVoiceSettings.svelte` edits the Desktop Voice configuration against the app-level Voice owner it receives as `desktopVoice` (`app/desktop.svelte.js`: current status snapshot, `adopt(snapshot)`, `refresh()`), saves it, and manages wakeword models. Internal `voice/TranscriptionAudioSettings.svelte` owns the independent audio draft/autosave participant; `voice/VoicePhraseCard.svelte` renders one catalog phrase (activation, sensitivity, action with optional Agent/Session override, problem and overlap notices, Calibrate); `voice/VoiceUnavailablePhraseCard.svelte` renders an active phrase missing from the catalog ("Not installed", the model-unavailable message, and a deactivate button that sends only `active_model_ids` and is disabled for the last active phrase; stored sensitivity and actions stay); `voice/WakewordCalibration.svelte` renders the running calibration of one phrase. `voice/voiceLabels.js` (status labels, error texts, the sidebar indicator presentation `voiceIndicator`) and the namespaced `voice.css` hold presentation details. The Voice page also shows the "Live voice" section (`live_voice_model`), which edits the `live_voice` Task Model binding through `SettingsSpecializedModelsPanel`; committed Settings reach App, whose sidebar control appears once a target is bound. See `model_tasks/live.md` for the sidebar control and call lifecycle. With the Desktop `liveHotkey` capability, the "Live voice shortcut" section (`live_voice_shortcut`, `settings/DesktopLiveVoiceShortcut.svelte`) follows it; it applies each change immediately through the bridge rather than autosave, and the Desktop answer stays authoritative (`desktop/live-voice.md`).

`SettingsMcpPanel.svelte` keeps MCP configuration and inspector composition; its uniquely named presentation rules live in adjacent `mcp.css`.

## Web Fetch settings

`SettingsWebFetchPanel.svelte` is a section on Tools alongside Web Search. It uses shared autosave and preserves newer drafts during saves. The backend advertises extraction services; the panel edits only `web_fetch.provider` and `web_fetch.mode`. Direct fetching is the default. Opting into a service reveals fallback/preferred routing, the URL-sharing and billing explanation, credential presence/setup, and the official pricing link. Credential values never enter this form. Pure payload helpers live in `settingsView/retrieval.js`; coverage is in `SettingsWebFetchPanel.test.js`.

## Providers and models

- Task Model options render directly below the selected target without a per-target disclosure. Structured JSON fields have their own initially closed disclosure; ordinary options remain immediately editable. Local speech setup and the visibly labeled TTS preview follow those fields. `SettingsSpecializedModelsPanel.test.js` covers initial Qwen/Chatterbox visibility, field order, edits and target changes; `LocalSpeechSupport.test.js` covers the preview label and generation lifecycle.
- `SettingsProvidersPanel.svelte` delegates local Model loading and editable Context-window values to private `settings/providers/localModels.svelte.js`; credentials, Provider refresh and connection workflows remain in the panel.
- Provider rows distinguish added Connections, configured credentials, usable Accounts, reachability, and enabled state. Those values come from backend contracts; the UI must not infer connectivity from the presence of a masked credential or a Model result.
- OpenCode Go/Zen descriptions distinguish subscription allowance from Zen credits and explain that upstream Free Models are restricted to OpenCode. Their shared API-key form explains that replacement/removal affects both Providers, and the removal action is labeled "Remove shared key". Backend Account/credential ownership remains in `providers/connections.md`.
- Connect and disconnect payloads preserve Provider id, connection id, and account id. OAuth, device-flow, API-key, environment, local, and keyless connections have different affordances and must not be collapsed into a single credential form.
- Adding a Provider means exposing a backend-advertised Connection candidate. Keyless local Connections use the same Add Provider flow: adding persists enablement and triggers discovery but never loads a Model. The frontend does not maintain its own Provider registry.
- Adding a Custom Provider is a separate full entity flow owned by `SettingsProvidersPanel` plus `CustomProviderModal`: the form edits the Settings-backed name, stable id, allowlisted Adapter, endpoint, auth mode, optional write-only API key, discovery path, and zero or more manual Models with task/capability facts. Create/edit/delete use `provider.custom_*`, refresh the server-owned Provider/Model projections, and never rehydrate a secret. Delete confirmation states that existing Model references remain but become unavailable.
- Model pickers share server suitability/filtering results. `createModelCatalogLoader()` is the common versioned reload boundary used by Agent and default-Model views: only the newest request may publish a catalog or error, and invalidation prevents a response from updating an unmounted owner. A new refresh clears any deferred catalog snapshot from an older autosave boundary, saves the canonical Model id, and reconciles to returned Settings.
- `SettingsSpecializedModelsPanel` renders backend-discovered task targets from the generic `TASK_MODEL_ROWS` contract. The shell places scoped instances under Voice, Memory, and Tools instead of a separate Specialized Models page. Each instance loads, compares, and saves only its declared task types; commits from another instance cannot cause stale unrelated bindings to be resubmitted. Only the speech instance polls local speech memory. Mounted coverage includes cross-page Settings updates with a pending draft. Its schema requests are versioned per task and bound to the selected Provider/Model target, so a delayed response cannot populate or save options for a newer selection. Local targets carry a searchable `(local)` label; engine option fields still use the generic renderer. Local STT setup offers Install, server-owned phase status and retry, followed by an explicit Restart server after verification. Polling survives navigation through the backend job, resumes after remount, and rechecks target usability after restart without overwriting option drafts. An uncertain restart response is checked, never automatically replayed. The ready state explains the first model download and offline use. Its image rows are distinct: `image_understanding` configures `analyze_image` for Main Model routes that cannot carry images, or for Agents explicitly granted availability with vision (see `tools/image.md`), while `image_generation` configures output creation/editing. Chat and `TaskModelService.binding_is_usable` own whether `analyze_image` is actually Model-visible. Coverage: `SettingsSpecializedModelsPanel.test.js`; setup ownership is documented in `model_tasks/speech.md`.
- The expanded OpenRouter row owns a routing editor with a global scope and optional full per-Model overrides. `automatic` leaves OpenRouter-managed Sticky Routing eligible while permitting blocks, `allowed` restricts candidates without imposing order, and `ordered` exposes priority controls plus an explicit cache-affinity warning because OpenRouter ignores Sticky Routing when `provider.order` is present. Global blocks remain effective inside Model overrides. An always-visible info banner states that Sticky Routing is best effort and identifies one exact allowed endpoint with fallbacks off as the no-switch configuration.
- Routing Provider choices are backend-advertised through `provider.routing_options`: base slugs globally and exact endpoint tags for the selected Model. The editor remains operable with a validated custom slug when a catalog omits an endpoint, but it only auto-loads catalogs while OpenRouter has a usable Connection. Routing drafts autosave through the shared participant, send the complete `providers.openrouter.routing` object, and preserve edits made during the Settings reload. The manual Save routing action also works on an unchanged editor.

## Extensions, Skills, Agents, and channels

- `components/settings/mcp.css` scopes paragraph and heading typography to the MCP panel and its portaled dialogs. Bare element selectors would override Chat prose globally; `SettingsMcpPanel.test.js` covers this boundary.

- MCP connection rows show discovered capability counts and backend-reported Agent policy blocks. Their Capabilities & access dialog reads the Extension's cached `inspect` projection, supports Tool search and paging, and exposes server guidance and Prompts. Grant, effective Tool policy, and connection health remain separate facts; inspecting never calls an application Tool. The controller versions searches independently from connection refresh and invalidates pending inspection responses on close/disposal.

- The dedicated Skills management surface moved out of Settings into the Configure -> Skills view (`webui/src/components/skills/`, see the WebUI map's Interfaces); Settings keeps no Skill section. Agent editors still use Skill *selectors* (below) for per-Agent allowlists and authoring entry points.
- Extension management renders the backend-provided capability, status, schema, waiting, and configuration projections, including declared Slash Commands and whether each is currently registered. Commands are code-owned capabilities summarized in the existing row, not editable Settings. Only an Extension with a non-empty Settings Schema receives a configuration disclosure; schema-less Extensions expose no generic editor. While the MCP Extension is loaded, its dedicated connection manager renders after the Extension list as its own sub-topic, independently of Settings Schema. Schema forms preserve unknown/non-secret config through the backend contract; secrets use the dedicated secret operation and are never rehydrated into normal form state.
- A transition flush batches all changed non-secret Extension schema forms into one complete `settings.update` projection so independently edited rows cannot overwrite each other. Successful config writes update the persisted baseline without reloading/unmounting the form or replacing newer drafts. Invalid schema drafts fail the transition in place. Secret values remain outside autosave and retain their explicit per-secret operation.
- Reload, enable/disable, and configuration changes are separate operations. Live capability ownership remains in the Extensions domain even when the panel displays its result.
- Agent Skill selection uses one Checkbox group: an All Skills Checkbox (mixed when partly selected; selecting all stores the `['*']` wildcard, including future Skills) with a count, then one Checkbox row per Skill with its description; unavailable saved Skills stay editable in their own group. Project Skill ceilings use one such group per source. `ToolAccessEditor` owns Identity/Team Agent policy projection and Select all / Deselect all actions; individual Tool checkboxes remain editable after clearing the selection. `ToolCatalogEditor` owns presentation shared with the Project Tool Whitelist: search by name, description or family, one panel per family in balanced columns, a Checkbox row per Tool (accessible name = the caller's `toggleLabel`, default the Tool name; a visible state is linked through `aria-describedby`), and a family Checkbox (`All {family} Tools`, mixed when partly allowed) affecting the filtered members. Built-in families retain i18n labels; Extension families use server `family_label`. Families with fewer than two catalog/ceiling members fold into Individual Tools before search. Descriptions and full activation/readiness guidance appear on hover/focus; automatic, unavailable and opt-in states also have visible labels. Catalog selection is permission, not a claim of runtime availability.
- Policy changes preserve canonical `allowed`/`denied`/`granted` semantics. `requires_opt_in` remains off under the default policy until explicitly selected, individually or by a bulk selection. Select all selects every catalog Tool inside the ceiling; Deselect all clears access and grants. Enabling one Tool from no access leaves unrelated automatic Tools denied. The separate image-analysis vision grant is not created by bulk selection. Automatic Tools remain explicitly deniable; gated and stored-but-unregistered Tools remain editable. The Project Whitelist adapter changes only its fixed ceiling list, never Agent policy. Creating/editing Skill content still uses the Skill API.
- `AgentEditor.svelte` owns one continuous page and the shared form draft, validation, save/rename/delete lifecycle and autosave registration. Its mounted `AgentOverviewPanel`, `AgentBehaviorPanel`, `AgentAccessPanel` and `AgentDetailsPanel` are private presentation splits, not navigation entries. Identity (name/Project) precedes Model/Thinking; temperature and fallbacks have a local disclosure. Context & Memory combines custom Prompt and Memory rows with a separate Compaction group; `CompactionPolicyEditor` `layout="rows"` renders the custom policy as rows of that group (the default layout still serves Projects and the Session dialog); the Behavior panel owns Memory request generations, editing and refresh deferral. Tools, Skills and Sub-Agent targets follow. Workspace, ID, metadata and deletion are in a final advanced disclosure that opens for its validation errors. The title scrolls with all fields, followed by a tertiary Save action. App autosave still guards Agent selection, Shared defaults and main navigation, and inheritance remains distinct from explicit overrides.
- `SystemPromptView.svelte` composes two private implementations: `prompt/scope.svelte.js` owns scope/preview requests and their generations; `prompt/editor.svelte.js` owns block drafts, autosave, confirmations and layout editing. The view retains deep-link/tab coordination and cleanup. Block editing, preview, reset and layout use their dedicated backend contracts, not one editable composed prompt; only the newest request for the still-selected scope may publish scope/blocks/preview/error/loading.
- `AgentEditor.svelte` separates Sub-Agent targets into Identity and collapsible Project groups under one filter (`AgentSelectionGroup.svelte`). Each group Checkbox is mixed when partly selected; a click on a mixed or empty group selects its filtered members, a second click clears them. Group changes materialize the current selection without promoting complete explicit selections to the cross-group wildcard; an unchanged wildcard remains intact. Unavailable saved targets stay editable in their address-based group. Coverage: `AgentsView.test.identity-and-access.test.js`.
- `AgentsView` owns a separate Shared defaults destination above the real Agent roster. The page title, section jump links, and the Model & Thinking and always-open Compaction sections (rows with their save state on the heading line) share one scrollport; deep links scroll to their target section (`AgentsView.test.creation-and-layout.test.js`). Ordinary entry opens the selected Agent; opening Shared defaults retains that selection and the mounted editor. It loads Settings before mounting the existing Defaults/Compaction panels, routes transitions through autosave, and refreshes the authoritative Agent roster after successful saves so inherited values update without converting explicit overrides. The App routes defaults/Compaction links from Projects into this destination and consumes the target so ordinary returns still open the individual Agent.
- Existing Channel forms autosave through the shared participant and remain open after saving (a reload keeps the Channel rows and the open edit form mounted); switching or closing them flushes pending edits. Creating a Channel remains explicit. Channel forms keep platform, DM scope, allowed chat ids, enabled state, and runtime status distinct. A saved channel is not necessarily enabled or currently running. Each Channel row also loads the independent durable access projection: groups show stable scope ids and seen participant name/id/role rows; `This is me` selects the Channel-own identity, and role actions call additive grant/revoke RPCs then reload saved state. The own identity is visibly `Me`, remains admin, and cannot be demoted from the UI.

## Onboarding and appearance

- `onboarding.js` projects operational readiness and setup choices from server-backed Settings. Readiness requires a Connection whose server-projected `usable` value is true; the frontend never reconstructs it from credentials or reachability. The searchable setup catalog renders each Provider once with its available method types and server-confirmed connection state. `OnboardingProviders.svelte` owns the responsive preview and explicit Show all/Show fewer control; search always covers the full catalog, matching Provider ids/names and Connection labels, including subscription names. Other addable methods remain reachable on an already configured Provider; disabled, already-added Connections remain manageable in Settings.
- `app/setup.svelte.js` owns automatic one-shot entry and dismissal; `OnboardingView.svelte` is a separate two-step guide, also reopened from Settings. It always starts with Providers, including when reopened with existing connections. Selecting a Provider opens its shared connection dialog, with a method choice only when multiple methods are addable. Successful connections update the list and connected summary, clear the search, and stay on this step so users can add more Providers. Only explicit continuation opens Model selection. A Provider picker scopes the shared Connection-aware Model picker when several Providers are usable; changing Provider clears the prior selection. Free Models use a visible opt-in filter, not a hidden search prefill. Unavailable selections cannot complete setup.
- Settings and Model reads reject stale or post-unmount replies; Model reads reuse `createModelCatalogLoader`. Loading, failure and empty states retain Back/dismiss actions and retry where appropriate. Completion explicitly saves only the selected target Agent's Model through the existing form normalizer. Shared ProviderConnectModal's setup variant uses the default Account and omits optional Account/storage fields; Provider management retains its full form. Coverage: `OnboardingView.test.js`, `onboarding.test.js`, and `App.test.onboarding.test.js`.
- Appearance saves language, Chat width, and the `normal` / `compact` Working presentation through Settings. `appearancePrefs.svelte.js` projects both Chat display preferences app-wide so a successful save reflows the open Chat without a reload; changing the active language updates i18n immediately while persisted state still reconciles to the save result.

## Desktop app settings and browser boundaries

- `desktopBridge.js` is the only browser-side seam for the native desktop bridge. Web-only accessors must remain functional when no bridge exists.
- Desktop capability discovery independently gates `serverSelection`, Desktop Voice, and `liveHotkey` (Live voice shortcut section). Desktop Voice needs `wakeword` plus the Voice bridge version `voiceApi === 2` (`supportsDesktopVoice`); a Desktop that reports `wakeword` with another version gets the notice "Update the vBot Desktop app to use Voice with this server." instead of the Voice rows and sidebar indicator. Desktop accessor startup keeps retrying while the asynchronously injected bridge is absent or rejects the capability call; only a successful response is authoritative. When server selection is available, Settings includes Connection under System. Voice is always a server-owned page; only its Wakeword rows are capability-gated.
- `DesktopConnectionSettings.svelte` manages the Desktop-local remembered-server list through `desktopBridge.js`: `listServers` marks the active target, add/remove mutate only the OS per-user Desktop config, and a switch probes through `selectServer` before JavaScript applies the returned URL. The component is reused inside the AppShell outage modal, where it remains interactive outside the otherwise inert server-backed content.
- Voice configuration and transcription preferences use shared autosave participants for serialization and retry; calibration Apply remains explicit. The Voice controls section shows one heading-line save state for both participants; `TranscriptionAudioSettings` reports its status to `WakewordVoiceSettings` through `onSaveStatusChange`. `wakewordSettings.js` projects the editable configuration out of a status snapshot (`voiceConfigFromStatus`), carries unsaved edits onto newer snapshots per value and per phrase (`rebaseVoiceConfig`), and builds partial `updateVoiceConfig` changes holding only what differs (`buildVoiceConfigChanges`): ordered `active_model_ids`, per-phrase `model_sensitivities` and `phrase_actions` (the Desktop merges both; `null` restores the default command, a command sends only its non-null `agent_id`/`session_behavior` overrides, Live voice sends `{type: 'live_voice', mode: 'start'|'toggle'}`), stable `{index,name,host_api}` microphone identity, `echo_cancellation`, `default_agent_id`, and `default_session_behavior`. The snapshot `updateVoiceConfig` returns is authoritative and adopted by the app-level owner. Calibration, recording, commands, and limits are status-only and never enter change payloads or dirty-state comparison.
- The Voice panel saves one server-wide `speech.transcription_audio` projection for the Chat microphone and post-Wakeword command recording. It exposes the `compatibility` (WAV/16 kHz), `high_quality` (FLAC/48 kHz), and `custom` profiles; custom keeps mono PCM16 fixed while allowing WAV or FLAC and 16, 24, or 48 kHz. These controls remain available in browser accessors. When Desktop Voice is available, the same panel also obtains the authoritative model catalog through `listWakewordModels()` (each descriptor carries `overlaps`: models that can fire on the same words), distinguishes curated Built-ins from imported TFLite models, activates between one and `status.limits.max_active_phrases` phrases with sensitivity sliders bounded by `limits.min_sensitivity`/`max_sensitivity` (controls whose limit the status lacks stay disabled; nothing is hard-coded), warns on both cards when overlapping active phrases do different things, imports finished custom models through `importWakewordModel()`, and gates permanent removal of inactive imported models with the shared `ConfirmDialog`; custom training is not a WebUI responsibility. Calibrate is offered per saved active phrase and enabled while Voice is enabled, listening, and in real mode; commands pause while it runs. The panel presents the Bridge-owned room-noise, repetition, and review phases; visualizes score, peak, noise, and the proposed threshold; and disables capture edits until calibration ends. Discard stops it without saving, Restart returns to the noise phase, and Apply stops calibration first, then saves the recommended sensitivity of that phrase. Leaving the panel stops a running calibration.
- Imported-model paths are Desktop-private. The browser receives only the descriptor fields required for selection and management, rejects files over 20 MiB before FileReader/base64 expansion, and transfers accepted file content as base64 only for the explicit import call.
- Real Wakeword activation consumes `setVoiceEnabled`'s `{ enabled, error_code }` result. The current Desktop always returns `error_code: null` and reports problems through the status snapshot; a returned code would keep the toggle off and render the reason in the Voice panel until the next toggle or until Voice is enabled. A rejected Voice bridge call shows an error Toast whose message is `bridgeErrorMessage(error)` (`voiceLabels.js`): the localized text for a known code (`desktopErrorCode`), empty for an unknown code, else the error message. The app-level Voice owner (`app/desktop.svelte.js`) independently plays cues and raises global Toasts for pushed events that happened after its first snapshot, so the active main view does not hide Voice feedback: `sent` (success), `no_speech` (warning), `transcription_failed` and `command_failed` (errors; `command_failed` explains its `error_code`), `error` (sticky error), and `microphone_disconnected` (auto-dismissing warning). An `error` state already present in the first snapshot raises one sticky Toast; older events raise nothing. `microphone_disconnected` renders as an amber warning in the Voice panel and sidebar indicator, never as a sticky error. Voice has no `paused` state: a running Live voice call is held instead while a command records (`lib/liveVoice.js` `hold`/`release`, driven by `status.recording` in `LiveVoice.svelte`).
- Bridge discovery, push subscriptions, and media/runtime listeners require explicit retry, timeout, and cleanup behavior. The app-level Voice owner starts once the capabilities offer Desktop Voice: it reads the snapshot (retrying a failed first read every second), then applies pushed snapshots (`vbot-desktop-voice`, validated in `desktopBridge.js`) unless a newer sequence was already seen, and runs each pushed event once in sequence order. An event that skips a sequence number triggers one snapshot re-read; missed events are not replayed. `recording_started`/`recording_ended` patch `recording` at once for the sidebar indicator and the Live hold. The Voice panel retries a failed model/microphone load without accepting false defaults and clears its timers on unmount. UI state must not claim the wakeword runtime is active merely because the saved setting is enabled. Enable/disable, calibration, and model actions disable conflicting controls while in flight; the Bridge lifecycle remains authoritative for serialization.
- Log listing and file reads use RPC; live tailing uses the dedicated log WebSocket. Log content is display data and must not be interpreted as HTML.

## Extension input outside Settings

`ExtensionRequests.svelte` is mounted in the App content area and polls the shared Extension request projection with owned cleanup. A pending request shows a review banner; the shared Modal displays the external message, schema-derived controls, or a safe HTTP(S) login link and redirected-address field. Accept/decline/cancel use the Extension's declared response operation. Form validity remains server-owned. Polling does not reset an open draft, and a resolved or cancelled request dismisses its dialog. Tests: `ExtensionRequests.test.js` and `extensionInputs.test.js`.


## MCP connection management

`SettingsMcpPanel.svelte` renders local/HTTP/SSE connection forms, exact argument rows, advanced connection fields, write-only credentials, enable/disable, removal confirmation, and asynchronous connection tests. It renders after the Extension list, only while the MCP Extension is loaded. `lib/mcpSettings.js` owns management RPC workflows, current-state reconciliation, and disposable polling; form drafts stay in the modal and status updates never replace them. Saving is explicit because it starts or replaces an external connection. A preflight read rejects a duplicate create or an edit whose saved record changed; this is UI conflict detection, not an atomic backend compare-and-swap. Connection access uses the shared Agent/Swarm Tool editor with explicit opt-in; no separate Agent roster is loaded or saved. Existing Tool denials and Project ceilings remain authoritative.

Credential values go only to the dedicated operation and are never added to connection records or retained controller state. Test jobs remain cancellable and use the existing global Extension input dialog for authentication/questions; test output shows verification results rather than dumping the catalog. Test failure stops automatic polling until Retry. Regression coverage: `SettingsMcpPanel.test.js` and `lib/__tests__/mcpSettings.test.js`.


## System Prompt inspection

`SystemPromptView.svelte` owns the persistent Agent selection and Prompt / Tools / Edit blocks navigation above the scrolling content. Prompt opens as a readable Markdown document with a separate verbatim Original text representation; Copy always uses the original text. The view describes current Agent configuration rather than claiming to reproduce a running Session. Agent changes pass through the autosave boundary, select an available custom scope or Default, and invalidate old preview responses; refresh clears stale content and failures expose Retry. Edit blocks remain mounted across tabs, retain drafts and expansion state, and distinguish disabled/inherited state without reducing content contrast. Scope deep links open the editor.

`ToolDefinitionsPanel.svelte` owns the read-only search and selected-definition display, using `prompt.preview(include_tools=true)` rather than reconstructing Tool policy from the management catalog. It preserves full descriptions and parameter schemas and offers the complete definition as JSON and clipboard content. Token estimates remain separate from the definitions. Regression coverage is in `components/__tests__/SystemPromptView.test.js`; shared contrast/surface invariants are in `lib/__tests__/uiPrimitives.guard.test.js`.


## Skill manager

`components/skills/SkillsView.svelte` and `skillsView.js` present a collection index (all, shared, Identity Agent owners, global/bundled, and Projects), word search over names/descriptions/owners, status filtering, and 50-row pages. An Agent collection means owned packages, including shared originals; it is not a reconstruction of that Agent's effective runtime catalog. One selected package exposes readable instructions and exact original text, access context, diagnostics, and explicit mutations. Server-projected inventory ids distinguish same-name packages; `editable_scope` alone enables human editing/deletion. The inspection request is versioned independently of inventory refresh, and stale responses cannot replace a newer selection. Open drafts survive resource refreshes. Creation separates name, description, and instructions and serializes quoted YAML metadata; original-text editing preserves the full authored document. The sharing dialog may save an empty receiver selection to stop sharing. Skill locations remains mounted after first visit so its autosave participant survives collection changes. Mounted regression coverage lives in `components/skills/__tests__/skillsView.test.js`.

Local STT/TTS setup and TTS previews are owned by `LocalSpeechSupport.svelte`,
keyed by the selected target in the Voice speech Model editor. Setup polling survives
navigation through server-owned jobs; TTS installs only its selected engine and
refreshes availability immediately. The preview waits for saved options, streams

The task Model editor on Voice also owns per-engine speech memory controls. It polls the
metadata-only memory RPC without reloading option drafts; each model has its own
loaded/busy state and targeted unload button. Unloading STT leaves TTS usable,
including when TTS is busy. Stale polls cannot overwrite unload results, failed
unloads permit retry, and unmount clears polling. Coverage:
`SettingsSpecializedModelsPanel.test.js` and `lib/__tests__/api.test.js`.

The task Model editor displays schema defaults without inserting them into stored option drafts and submits only changed bindings. Each configured row with stored options offers Reset options, including when those options are absent from the live schema; it clears the options while preserving the target. Coverage: `SettingsSpecializedModelsPanel.test.js` exercises unrelated stale bindings, displayed defaults, and reset after schema drift.

Select choices with an empty value (for example "Provider default" or "Model default") are real, selectable choices. A select carrying `options_by` shows only the choices its referenced field's current value allows, is not rendered at all when that value's entry is an empty list (the stored value stays in the binding), and changing that field moves a now-hidden value as the contract in `model_tasks.md` -> Conventions requires; the renderer knows no field names. Pure helpers `visibleFieldOptions` / `isOptionFieldHidden` / `reconcileDependentOptions` live in `taskModelSettings.js` (`taskModelSettings.test.js`); mounted coverage in `SettingsSpecializedModelsPanel.test.js`.


## Channel connection setup

`SettingsChannelsPanel.svelte` supports Telegram, Discord, Slack, Mattermost and WhatsApp. The existing Channel autosave owner also persists Slack app-token variable names and Mattermost server URLs. IDs stay strings, preserving opaque IDs and integers beyond JavaScript's safe range. Create saves WhatsApp disabled with the literal `self` allowlist by default.

`WhatsAppSetup.svelte` owns explicit install/connect/re-pair actions and disposable three-second status polling. Only `channel.whatsapp.status` and the dedicated setup/pair responses expose the transient QR; the component clears it after connection and ignores stale responses after unmount. Server-owned installation continues across navigation. Normal Channel status additionally exposes actual `connected` state for the new transports. Coverage: `WhatsAppSetup.test.js`, `SettingsView.test.channels.test.js`, and `channelSettings.test.js`.
