# WebUI Settings

Read this reference only for WebUI Settings, Provider, Extension, Skill, Agent, onboarding, appearance, channel, logs, or Desktop Voice work. Backend policy and persistence remain in the corresponding domain maps.

`settingsView.js` retains the public pure-helper interface. Internal `lib/settingsView/` modules own appearance/audio, Agent defaults, Recall (`recall.js`), web search/fetch (`retrieval.js`), Channels, Extensions and Provider/account projections; forms keep their existing payload and normalization contracts.

## Settings shell

SettingsView.svelte opens General and organizes settings into eight pages by user task: General (display, Session titles, desktop notifications, then region/setup; running background work above them), Providers, Voice (speech Models, Live voice and its optional shortcut, Wakeword, then Transcription audio), Memory (Reflection, Skill maintenance, then Conversation search, which includes the embedding Model), Tools (web search, web page reading, media Models, evaluation and Sub-Agent limits), Integrations (Channels and Extensions/MCP), Archive (retention, then the archived items, whose entries open as sub-pages; `webui/archive.md`), and System (server, optional Desktop connection and Debug). Each page lists its sections by priority in the `pages` array; row presentation follows `design.md` -> Settings, Agents, Projects, and Schedules (short visible text, explanations behind the "?"). Sections are visible together within a page; editor component boundaries do not define navigation entries. Providers links inline to Agents' Shared defaults, the sole editor of shared Model/Thinking/fallback defaults and Compaction.

Hidden pages and their sections stay mounted to preserve drafts and Provider authentication state. Settings rows hide settings that have no effect in the current state (the Title model while automatic titles are off, the trace limit while Debug is off, Reflection intervals while Reflection is off, the Librarian interval while scheduled Skill maintenance is off, the embedding Model rows while the search method does not search by meaning, transcription Format/Sample rate outside the Custom profile) with `hidden`, not `{#if}`: the row stays mounted so search still finds it, and the value stays saved. Search finds individual settings. `lib/settingsSearch.js` indexes the mounted DOM through the configuration page grammar: one entry per page, one per section of a page with several sections, and one per label element inside a section (`.s-row-label`, `.s-subhead__title`, FormField labels, `[data-search-label]`). A label in an entity head (`.s-entity__head`) stands for the whole entity including its collapsed details; any other label stands for its row (the parent of its `.s-row-info`), its FormField or its parent. An entry's own text is its label, description (`.s-row-desc`, `.s-subhead__desc`, FormField help), the `data-help-text` of its `InfoHint`s (so explanations behind a closed "?" match) and its rendered content. Matching ignores case, punctuation, spacing and diacritics; every query term must occur in the entry's own text or in its page and section labels, and at least one in its own text; a row containing another matching row is left out. Per term a label scores 3 (4 at a word start), a description 2, help or content 1; results sort by score, then page before section before row, then document order, capped at 40. A result shows its label and its location: a page result the page description, a section result its page, a setting "Page › Section" (only the page on a single-section page). Enter in the search field opens the first result. The index is rebuilt after mutations inside the editors, at most once per animation frame while a query is active. **`[data-search-label]` contract:** a panel that renders a setting only on demand declares it with a hidden element in its section carrying the translated label and optional extra words in `data-search-terms`; a declaration yields to a rendered row with the same label in the same section. SettingsChannelsPanel declares the Channel edit-form fields at the end of its Channel list, so they are found only while a Channel exists. Selecting a page or section result or a section deep link opens the page, scrolls to the section and focuses its heading. Selecting a setting result opens its place, then reveals the setting without another step: it opens closed `<details>` ancestors, clicks the `[aria-controls]` control reporting `aria-expanded="false"` for a hidden ancestor with an id, and opens an entity's details when the match lies only there; it keeps the row in view (for a row hidden while the setting it depends on is off, the visible row before it, such as the Debug switch for the trace limit), anchored like a section destination on the section heading while the row fits below it and on the row itself otherwise, focuses its first enabled control (else the section heading), and tints it briefly (`settings-search-hit` in `pages.css`, static under reduced motion). A section destination stays anchored while asynchronous content above it settles, until user interaction releases restoration. Ordinary page changes focus the page heading and reset its scroll. The view's place (`webui/app-shell.md` -> Navigation) is `[pageId]`, or `[pageId, sectionId]` for a search result on a page with more than one section. A page with sub-pages (`subPages` names the section whose panel shows them; only the Archive) also takes `[pageId, subPageId]`: a shown sub-page hides the page heading, the other sections and its section's heading, opens at the top without heading focus (the panel focuses its content), and returning to the page resumes the scroll position it was opened from; the panel moves through a handle whose place is the part below the page. Choosing a page (buttons or the compact picker) or a search result is a history step and passes the navigator's autosave gate, as does the Shared defaults shortcut; choosing the page or result already shown only scrolls back to it (a setting result reveals its setting again), and search input and scrolling are no steps. An empty or unknown place corrects to `['general']`, a bare section id (an App deep link such as `['decision_model']`) to `[pageId, sectionId]`, and a section outside the named page to `[pageId]`. SettingsGeneralPanel still owns regional preferences and server information, each rendered once. The server information starts with Version: the running build from `settings.get` `general.build` as version, Release or branch, and short commit; its Copy button copies the full commit for bug reports (`formatBuildIdentity` in `settingsView/appearance.js`). SettingsActivityPanel shows the server's background activity (`server.md` -> Background activity) at the top of General, below the page heading, only while the `backgroundActivity` list App keeps current (`webui/app-shell.md`) has entries. It is no section: it has no heading, no navigation or search entry and no empty state. `describeBackgroundActivity` (`settingsView/activity.js`) titles each row with what happens ("Downloading <Model>" while bytes are counted, else "Installing <Model>" with the phase below; "Installing WhatsApp support for <Channel>"; "Indexing conversations for search" with passages and time left; failure, restart and finished titles name the Model or Channel) and adds the problem or phase as a second line only when the title needs it. Actions: Open shows the managing section (`speech_models`, `recall`, `channels`) through `openDestination`, Cancel calls `task_model.local_setup_cancel` for a running local Model installation, and Dismiss calls `activity.dismiss` for finished, failed and restart entries. It never polls; the next push shows each action's result. SettingsNotificationsPanel autosaves the `notifications` switches the Windows tray app reads and shows every switch on when the payload lacks the section.

The shared `CompactionPolicyEditor.svelte` leads with the Classic (`continuation`) / With tail (`summary_tail`) radio group, then conditional tail fields, then automatic enablement and Trigger settings; mode selection does not change enablement. Component coverage lives in `SettingsCompactionPanel.test.js`. It keeps the pure absolute Trigger and also exposes an optional maximum-input-token cap alongside the Context ratio. Its shared normalizer omits an empty cap and preserves a positive cap in every scope payload, so `0.8` plus `200000` means whichever boundary is reached first.

The shared `sampling/SamplingSettings.svelte` is the only editor of Temperature and Top P (explicit user requirement: both are secondary "advanced settings", collapsed, with a visible recommendation to keep the Provider defaults). The Agent editor and the Librarian's Model settings (both through `AgentModelSettings`), Shared defaults, Project Agent defaults and each Team member's overrides render it as the last items of their Model group: a disclosure row "Advanced sampling", closed by default, whose head summarizes the explicit values while closed ("Temperature 0.1 · Top P 0.9"), and a body with the note "We recommend the Provider defaults. Change these only to fix a problem or when you know what the Model needs." above the two decimal rows. Props: `idPrefix` (control ids `<idPrefix>-temperature`, `<idPrefix>-top-p`, toggle `<idPrefix>-sampling-toggle`), `fields` (`{temperature, top_p}`, each `{value, hint?, error?, recommended?, explicit?, clearLabel?}`), `onChange(field, value)` and optional `onClear(field)`, which adds a clear action to fields with an explicit value. A field error opens the block. Values stay text; callers normalize them. A finite `recommended` (from `model.list` `recommended_temperature`/`recommended_top_p` via `samplingRecommendationsForModelValue` in `agentForm.js`) shows "Model recommends {value}" and a tertiary "Use {value}" action, hidden while the field already holds it; the action is the only way a recommendation enters a draft. Coverage: `SamplingSettings.test.js`.

The App shell keeps Settings' reading position `{top, pageId, place}` (captured by the navigation gate while Settings still owns its DOM) while another main view is active. `SettingsView` restores it while independently loaded content settles, but only on the page it belongs to and, for an entry with a section target, only for the entry it was kept for; a section deep link scrolls to its section instead. There is no scrollspy or document-tail spacer. The compact page picker replaces the second navigation column through tablet widths.

`settingsView.js` owns normalization and payload builders shared by the panels. Each panel loads and submits through `api.js`, keeps editable values local until save, and adopts server responses after mutation. Decimal settings remain strings during editing and are normalized only when building the payload.

`appearancePrefs.svelte.js` owns applying canonical appearance snapshots (language, Chat width, and Work details) for both App setup and SettingsView loads/commits. The Appearance panel submits its draft and forwards the response; it never publishes draft values into global preferences after an awaited save. A newer draft remains editable, and a failed follow-up save leaves the last confirmed appearance active (`SettingsView.test.js`).

Provider operations and Model/Provider invalidations call `SettingsView.refreshProviderSettings` through `onRefreshProviderSettings`. This refresh replaces only the `providers` and `local_models` projections, preserving mounted editors, unrelated baselines, drafts, and in-flight saves. Provider projection commits use the separate `onCommitProviderSettings` boundary; unrelated Settings commits preserve the current Provider projection before publishing to App. Initial Settings loading owns the blocking loading/error surface; refresh failures report through the caller and retain the current editors. Newer refreshes and teardown invalidate older replies; a Provider-owned commit restarts a pending refresh so a Model-refresh result cannot discard another Provider invalidation (`SettingsView.providers.test.js`).

Before adding or changing panel fields or saving behavior, read `webui/autosave.md` for the shared integration and input-continuity contract. Settings panels keep domain-specific normalization and payloads here; save timing, serialization, and transition flushing use that common mechanism.

Cross-cutting value coercion for JSON-derived data lives in `webui/src/lib/values.js` (`isPlainObject` strict `[object Object]`, `asText`, `asOptionalText`).

`WakewordVoiceSettings.svelte` edits the Desktop Voice configuration against the app-level Voice owner it receives as `desktopVoice` (`app/desktop.svelte.js`: current status snapshot, `adopt(snapshot)`, `refresh()`), saves it, and manages wakeword models; it renders the Wakeword section (`voice_controls`). `voice/TranscriptionAudioSettings.svelte` is the separate Transcription audio section (`transcription_audio`), rendered by SettingsView with its own draft, autosave participant and save footer, in every accessor; `voice/VoicePhraseCard.svelte` renders one catalog phrase (activation, sensitivity, action with optional Agent/Session override, problem and overlap notices, Calibrate); `voice/VoiceUnavailablePhraseCard.svelte` renders an active phrase missing from the catalog ("Not installed", the model-unavailable message, and a deactivate button that sends only `active_model_ids` and is disabled for the last active phrase; stored sensitivity and actions stay); `voice/WakewordCalibration.svelte` renders the running calibration of one phrase. `voice/voiceLabels.js` (status labels, error texts, the sidebar indicator presentation `voiceIndicator`) and the namespaced `voice.css` hold presentation details. The Voice page also shows the "Live voice" section (`live_voice_model`), which edits the `live_voice` Task Model binding through `SettingsSpecializedModelsPanel`; committed Settings reach App, whose sidebar control appears once a target is bound. See `model_tasks/live.md` for the sidebar control and call lifecycle. In the Desktop app the Voice page shows, in this order after it: "Microphone" (`microphone`, `settings/DesktopMicrophoneSettings.svelte`, with the `microphone` capability: the shared Desktop microphone and echo cancellation for Voice and dictation; the device list is read again whenever the dropdown opens; a stored device that is not listed stays selected as "Not connected" with a warning; locked while a wake phrase calibration runs), "Live voice shortcut" (`live_voice_shortcut`, `settings/DesktopLiveVoiceShortcut.svelte`, with `liveHotkey`), and "Dictation" (`desktop_dictation`, `settings/DesktopDictationSettings.svelte`, with `dictation`: enable, key combination, toggle or hold mode, and the latest failure with its time; it reads the status again every second until the dictation is idle). The section order is `speech_models`, `live_voice_model`, `microphone`, `live_voice_shortcut`, `desktop_dictation`, `voice_controls`, `transcription_audio`. These three Desktop sections apply each change immediately through the bridge rather than autosave, and the Desktop answer stays authoritative (`desktop/voice.md` -> Capture and microphones, `desktop/live-voice.md`, `desktop/dictation.md`). Both shortcut sections use one key capture row, `settings/ShortcutCombination.svelte` with `lib/globalShortcut.js` (capture, layout-aware labels, shortcut error texts). The Wakeword section shows the microphone in use and the echo cancellation state read-only.

`SettingsMcpPanel.svelte` keeps MCP configuration and inspector composition; its uniquely named presentation rules live in adjacent `mcp.css`.

## Web Search and Web Fetch settings

`SettingsWebSearchPanel.svelte` is the "Web search" section at the top of Tools. A keyed selected provider gets the API key row below the provider row; SearXNG and DuckDuckGo get none. Keyed Dropdown options carry "API key set"/"API key missing" as secondary text (`webServiceKeyHint` in `settingsView/retrieval.js`, used by both panels). Coverage is in `SettingsWebSearchPanel.test.js`.

`SettingsWebFetchPanel.svelte` is the "Web page reading" section on Tools, right after Web Search. It uses shared autosave and preserves newer drafts during saves. The backend advertises extraction services; the panel edits only `web_fetch.provider` and `web_fetch.mode`. Direct fetching is the default. Opting into a service reveals a short cost line with the official pricing link, the service's API key row, and the fallback/preferred mode row; the URL-sharing and billing explanation sits behind the service row's "?". Pure payload helpers live in `settingsView/retrieval.js`; coverage is in `SettingsWebFetchPanel.test.js`.

`settings/ServiceApiKey.svelte` is the API key row both panels render for a keyed selected service. Key facts come from the server (`settings.<section>.services` entries `{id, api_key_env, configured, source}`, normalized with a `shared` flag by `getWebServiceKeys(settings, section)` in `settingsView/retrieval.js`), are read from the current `settings` prop, and never enter a panel's autosave draft or dirty comparison. The row is write-only like the Extension secret fields: a status chip ("Set"/"Missing"; `data-api-key` = `set`/`missing`, `data-api-key-source` = `process_environment`/`data_dir`/`none`) and a password field whose typed value lives only in the row, is never rehydrated, and belongs to one variable, so choosing another service starts empty. A missing key shows the amber chip, the field and Save (disabled while blank). A key in the data directory offers Replace (an empty field with Save and Cancel) and Remove (saves an empty value; no confirmation, like Provider key removal). A key from the server environment offers no action; a blank environment variable shows "Missing" without a field, because it would shadow a saved key. Save and Remove call `settings.set_service_key` (`tools/web_search.md` -> External Dependencies) and pass the full settings response to the panel's `onCommit`; success clears the field and toasts, failure keeps the typed value and reports through `onError`. The row's "?" names the data directory's `.env` file, that the server environment takes precedence, that hand edits need a server restart, and, for keys both sections use (Tavily, Exa, Firecrawl), that one key serves both. Coverage is in `ServiceApiKey.test.js`.

## Conversation search settings

`SettingsRecallPanel.svelte` is the "Conversation search" section on Memory and the only editor of the `text_embedding` binding; there is no separate embedding section. It holds two drafts with one save state: the Recall backend (`settings.update`, `recall.backend`) and the `text_embedding` binding (`taskModelEditor.svelte.js`, below).

The panel reads top to bottom: search method, embedding Model (with its options), index status.

- "Search method" is the first row, a Dropdown over the advertised backends (`buildRecallMethodOptions`): Keywords (`sqlite_fts`), Keywords and meaning (`hybrid`, marked Recommended), Meaning only (`vector`), then Extension backends under their id. The line under the label describes the chosen method (`describeRecallMethod`, `settings.recall.backendDescriptions.<backend>`, Extension fallback).
- While the method searches by meaning (`vector`/`hybrid`), the "Embedding model" row shows the searchable Model picker (`#settings-specialized-text_embedding`, `buildEmbeddingModelOptions`) over every `text_embedding` target, grouped "On this computer" (`kind` local or `facts.local`) and "Cloud", each best `facts.recommended_rank` first, then by label. Beside each option: "Not installed · <size>" for a vBot-run target that is not usable (it stays selectable), "Unavailable" (disabled) for any other unusable target, else "Free" or the price per 1M input tokens, plus "English only" when `facts.multilingual` is false; the profile note is the option's tooltip. A saved target the server no longer lists stays as the selection under "No longer offered". The line under the label (`describeEmbeddingModel`) says where conversation text goes and the price, or, in amber, asks for a Model and names the best recommended one, says a saved Model is no longer offered, or that a chosen Model is not installed yet.
- Choosing a vBot-run target that is not usable opens `settings/LocalModelInstallDialog.svelte` instead of selecting it: the Model's note, its download size and license from the target's `metadata` (`download_bytes`, `license`), and Install. The dialog presents the target's installation job (`settings/localSetupJob.svelte.js`, below) through `describeLocalModelSetup` (`settingsView/localModels.js`): while installing the translated phase (`settings.localModel.phase.<phase>`), during the download its bytes "X of Y" with the shared `components/ui/ProgressBar.svelte` (`role="progressbar"`); a failure translates `status.error` (`settings.localModel.error.<code>`, `install_failed` fallback) with Try again; an unreachable server offers Check again. A `ready` status (also one already reported when the dialog opens) refreshes the targets, closes the dialog and selects the Model. Closing the dialog leaves the server-owned installation running; choosing the Model again reopens it with the current state.
- A selected target with option fields adds a closed "Model options" disclosure row (`TaskModelOptions.svelte`); it starts open when the binding has non-default options. Option fields render a backend `placeholder` (the local Models' CPU threads show "Automatic (N)" while empty).
- The "Search index" row shows `describeRecallIndexStatus`: coverage (indexing, indexed of total, complete, empty), while `indexing` the time left from the server's `eta_seconds` ("about N min left", "less than a minute left", hours from 90 min; nothing while it is `null`), the waiting token estimate and its cost, skipped and spent (a zero cost, as for a local Model, is not named); while `retrying` or `error` a second line translates `last_error.code` (`settings.recall.indexError.<code>`, generic fallback) and names the next attempt relative to now, re-rendered every 15 s. The row is hidden while the method does not search by meaning, while no Model is chosen, and for the `disabled` and `unconfigured` states. The panel reads `recall.status` on mount, after each of its saves and when `modelsRefreshToken` changes (which also covers replay gaps), and applies every pushed `recall_index_status` payload App forwards as `recallIndexStatus`; a version counter keeps a slower read from replacing a newer push. A tertiary Rebuild action appears only once something is indexed or skipped; it confirms that every conversation is indexed again, that a Model change does not need it, and the renewed Provider cost, before `recall.rebuild_index`, whose returned status it shows.
- Coverage: `settingsView.recall.test.js` (method options, Model picker options and line, status line with time left), `settingsView.localModels.test.js` (installation states, download facts) and the Memory tests in `SettingsView.test.js` (method then Model choice, combined save, pushed status, options disclosure, installation dialog until selected, stored meaning-only method, rebuild).

## Providers and models

- Task Model options render directly below the selected target without a per-target disclosure. Each field's schema description sits behind a "?" on its label. Ordinary options come first and remain immediately editable; structured JSON fields follow, each in its own initially closed disclosure, sharing a line with the tertiary Reset options action. Local speech setup and the visibly labeled TTS preview follow those fields. `SettingsSpecializedModelsPanel.test.js` covers initial Qwen/Chatterbox visibility, field order, edits and target changes; `LocalSpeechSupport.test.js` covers the preview label and generation lifecycle.
- `SettingsProvidersPanel.svelte` delegates local Model loading and editable Context-window values to private `settings/providers/localModels.svelte.js`; credentials, Provider refresh and connection workflows remain in the panel.
- Provider rows distinguish added Connections, configured credentials, usable Accounts, reachability, and enabled state. Those values come from backend contracts; the UI must not infer connectivity from the presence of a masked credential or a Model result.
- A collapsed Provider row shows its name, the Model count and one status chip (plus a short hint while unreachable); the head toggles the details. Status chips explain their state in a tooltip, an account's "Not usable" chip says why (empty variable or invalid sign-in), and its source names the credential variable. The details hold the Connections (a Connection's chip only when it differs from the row's), Add connection, OpenRouter routing and local context windows (each a closed `providers/ProviderDetailDisclosure.svelte` that stays mounted), and last the endpoint with custom-Provider Edit/Delete. The Model database refresh is a separate row at the end of the page.
- OpenCode Go/Zen billing help, behind a "?" on the Provider name, distinguishes subscription allowance from Zen credits and explain that upstream Free Models are restricted to OpenCode. Their shared API-key form explains that replacement/removal affects both Providers, and the removal action is labeled "Remove shared key". Backend Account/credential ownership remains in `providers/connections.md`.
- Connect and disconnect payloads preserve Provider id, connection id, and account id. OAuth, device-flow, API-key, environment, local, and keyless connections have different affordances and must not be collapsed into a single credential form. Removing an API key or disconnecting an OAuth Account first passes `requestTransition`, because the Provider projection refresh that follows can disconnect the Provider and remove its row with the OpenRouter routing editor (`SettingsProvidersPanel.test.js`).
- Adding a Provider means exposing a backend-advertised Connection candidate. Keyless local Connections use the same Add Provider flow: adding persists enablement and triggers discovery but never loads a Model. The frontend does not maintain its own Provider registry.
- Adding a Custom Provider is a separate full entity flow owned by `SettingsProvidersPanel` plus `CustomProviderModal`: the form edits the Settings-backed name, stable id, allowlisted Adapter, endpoint, auth mode, optional write-only API key, discovery path, and zero or more manual Models with task/capability facts. Create/edit/delete use `provider.custom_*`, refresh the server-owned Provider/Model projections, and never rehydrate a secret. Delete confirmation states that existing Model references remain but become unavailable. An "Advanced: wire profile" disclosure (open when the record has a `wire` block) edits that block as JSON in a code textarea, with help for the common fields (dialect, levels, off/unset, response fields, replay, request fields, and the Reasoning-switch gotcha). Invalid JSON or a non-object blocks Save with an inline error, an empty field removes the block, and the entries the server refuses (`provider.custom_save` `data.wire_issues`) are listed under the field. An edit sends the record's `revision` as `expected_revision`; when the record changed elsewhere after the modal opened (`settings_conflict`), the modal keeps the draft and asks to close and reopen it. Coverage: `CustomProviderModal.test.js`.
- Model pickers share server suitability/filtering results. `createModelCatalogLoader()` is the common versioned reload boundary used by Agent and default-Model views: only the newest request may publish a catalog or error, and invalidation prevents a response from updating an unmounted owner. A new refresh clears any deferred catalog snapshot from an older autosave boundary, saves the canonical Model id, and reconciles to returned Settings.
- `SettingsSpecializedModelsPanel` renders backend-discovered task targets from the generic `TASK_MODEL_ROWS` contract. The shell places scoped instances under Voice and Tools instead of a separate Specialized Models page; the `text_embedding` row is presented by Conversation search instead. The binding editing (scoped draft and autosave, target lists, versioned option schemas, option edits) lives in the private controller `settings/taskModelEditor.svelte.js`, created during component initialization by both panels; `settings/TaskModelOptions.svelte` renders a selected target's option fields for either placement. Each instance loads, compares, and saves only its declared task types; commits from another instance cannot cause stale unrelated bindings to be resubmitted. Saves go through the shared Settings draft with a `task_model.update` base, rebasing binding by binding when another writer changed them (`webui/autosave.md` -> Concurrent writers). Only the speech instance polls local speech memory. Mounted coverage includes cross-page Settings updates with a pending draft. Its schema requests are versioned per task and bound to the selected Provider/Model target, so a delayed response cannot populate or save options for a newer selection. Local targets carry a searchable `(local)` label; engine option fields still use the generic renderer. Local speech setup (per target, `LocalSpeechSupport.svelte` below) offers Install, server-owned phase status with download progress, and retry; only a development checkout's STT install is followed by an explicit Restart server. Polling survives navigation through the backend job, resumes after remount, and rechecks target usability after restart without overwriting option drafts. An uncertain restart response is checked, never automatically replayed. The ready state says the Model is installed and works offline; the first use only loads it. Its image rows are distinct: `image_understanding` configures `analyze_image` for Main Model routes that cannot carry images, or for Agents explicitly granted availability with vision (see `tools/image.md`), while `image_generation` configures output creation/editing. Chat and `TaskModelService.binding_is_usable` own whether `analyze_image` is actually Model-visible. Coverage: `SettingsSpecializedModelsPanel.test.js`, with speech memory and local setup in `SettingsSpecializedModelsPanel.local-speech.test.js`; setup ownership is documented in `model_tasks/speech.md`.
- The expanded OpenRouter row owns a routing editor with a global scope and optional full per-Model overrides. `automatic` leaves OpenRouter-managed Sticky Routing eligible while permitting blocks, `allowed` restricts candidates without imposing order, and `ordered` exposes priority controls plus an explicit cache-affinity warning because OpenRouter ignores Sticky Routing when `provider.order` is present. Global blocks remain effective inside Model overrides. The editor sits in an initially closed "Routing" disclosure whose head summarizes the current policy; its "?" states that Sticky Routing is best effort and identifies one exact allowed endpoint with fallbacks off as the no-switch configuration. Save errors render outside the disclosure.
- Routing Provider choices are backend-advertised through `provider.routing_options`: base slugs globally and exact endpoint tags for the selected Model. The editor remains operable with a validated custom slug when a catalog omits an endpoint, but it only auto-loads catalogs while OpenRouter has a usable Connection. Routing drafts autosave through the shared participant, send the complete `providers.openrouter.routing` object, and preserve edits made during the Settings reload.

## Extensions, Skills, Agents, and channels

- `components/settings/mcp.css` scopes paragraph and heading typography to the MCP panel and its portaled dialogs. Bare element selectors would override Chat prose globally; `SettingsMcpPanel.test.js` covers this boundary.

- A collapsed MCP connection row shows the name, the optional description, an error (the diagnosed problem's advice when known), a status chip and the enabled switch; a connection with `missing_credentials`, enabled or not, shows the Extensions panel's waiting state instead (`mcpSetupNeeded`: the "Needs setup" warn chip and a "Waiting for: <names>" line, `settings.extensions.waiting`/`waitingFor`), and its `credential_missing` problem line is left out; the head toggles details with the endpoint, an OAuth connection's sign-in state and redirect URL (from `list`'s `oauth`), diagnostics (MCP connection management below), discovered capability counts and the Capabilities, Edit, Test, Reconnect, Credentials, Sign in again (OAuth connections; the `reauthorize` operation) and Remove actions. Their Capabilities & access dialog reads the Extension's cached `inspect` projection, supports Tool search and paging, and exposes server guidance and Prompts. Grant, effective Tool policy, and connection health remain separate facts; inspecting never calls an application Tool. The controller versions searches independently from connection refresh and invalidates pending inspection responses on close/disposal.

- The dedicated Skills management surface moved out of Settings into the Configure -> Skills view (`webui/src/components/skills/`, see the WebUI map's Interfaces); Settings keeps no Skill section. The Agent editor still edits its Agent's Skill selection (below).
- Extension management renders the backend-provided capability, status, schema, waiting, and configuration projections, including declared Slash Commands. A collapsed row shows the name, one description line, attention lines (error, missing setup, capability warnings), a status chip only for states needing attention (`extensionStatusChip`: failed, overridden, waiting, unknown) and the enabled switch. A row with a version, capabilities, an override path or a Settings Schema toggles details from its head; they list the facts (commands are code-owned capabilities, not editable Settings) and, only for a non-empty Settings Schema, the configuration form; schema-less Extensions expose no generic editor. While the MCP Extension is loaded, its dedicated connection manager renders after the Extension list as its own sub-topic, independently of Settings Schema. Schema forms preserve unknown/non-secret config through the backend contract; secrets use the dedicated secret operation and are never rehydrated into normal form state.
- A transition flush batches all changed non-secret Extension schema forms into one complete `settings.update` projection so independently edited rows cannot overwrite each other. Successful config writes update the persisted baseline without reloading/unmounting the form or replacing newer drafts. Invalid schema drafts fail the transition in place. Secret values remain outside autosave and retain their explicit per-secret operation.
- Reload, enable/disable, and configuration changes are separate operations. ## Extension input outside Settings

`ExtensionRequests.svelte` is mounted in the App content area and reads the shared Extension request projection (`extensions.requests`) without polling: on mount, on each `pending_inputs` change from any Extension (`extensions/management.md`), and on owner-less Extension invalidations (reconnect, Extension reload, enable or disable); other Extension changes are ignored (`webui/app-shell.md`). A `date-time` is entered and shown in the app time zone (`dateTimePrefs`, named under the field) and sent as RFC 3339 with that zone's offset (`zonedDateTime`).

Requested addresses (`RequestedUrl.svelte`, `lib/requestedUrl.js`) serve MCP URL-mode elicitations and OAuth sign-ins: the full address as text with its registrable domain highlighted and named ("Opens on"), warnings for plain http, punycode (`xn--`) labels, user information in the address and IP-address hosts, and one open action (`target="_blank"`, `rel="noopener noreferrer"`, no referrer; the Desktop accessor opens the system browser through its bridge). A URL-mode elicitation names the requesting server, has no form or send action, and accepts only when the user opens the page; Decline and Cancel answer without opening it. It shows the one reason an Agent gets no scheduled pass from `unscheduled_reason`: "Off in Settings; Run now still works" as the schedule, or, when no pass can run (`available` false), a note that the Agent's Librarian switch is off, that it has no Skills of its own, or that the Librarian cannot run with the fix for its `librarian_problem` (`lib/librarian.js`), without schedule and next pass. Otherwise it shows the schedule, the next pass ("Due; starts once the Agent is idle" once due), a running pass, and the last pass (when and how it started, a Result row when it stopped early by an error or because vBot stopped, how many Skills it retired, what the merge step did, and a Session row whose Open session calls `onOpenSession('librarian', session_id)`, wired by App to `navigateToSession`), or "No pass has run yet." Its changes list the pass's revisions; a Skill name opens that Skill's History tab, or the Archived collection searched for the name when the Skill is archived now, and stays plain text when it is gone. Revert together (`actions.requestRevertPass`) sends one `skill.revert` over all revisions of the pass after confirmation; a later conflicting revision is offered for inclusion like a single revert. Run now (`librarian.run`) is disabled with the reason while no pass can run for the Agent or a pass runs; an `invalid_request` refusal toasts the same reason; `agent_busy` shows a warning toast. It also works while scheduled maintenance is off.
- **Package page** (drill-in): replaces the collection page in the content column. Back, the breadcrumb, choosing the current collection again, or Escape (not when another layer consumed it or focus is in a text field) return to the collection page, which stays mounted hidden, restoring its scroll position, filters and focused row. The view's places (`webui/app-shell.md` -> Navigation) are `[collection]`, `[collection, skillId]` for a package page and `['directories']` for Skill folders; choosing another collection, opening a package or the folders is a history step, and leaving a package or the folders goes up to the collection (Back when the previous entry is that collection). An empty or unknown collection corrects to `['all']`, an unknown package to its collection. The page shows the source line (with a "Pinned" badge while pinned), description, the provenance and use facts (`skillPageFacts`: "Created by" and "Last changed" for editable packages from `created_by`/`changed_at`/`changed_by`, "Last used" from `last_used_at`/`uses` when the inventory carries them), same-name notes (which copy wins where), header "Turn this skill off" (turns this one package off for every Agent and Project, `skill.set_disabled` with the inventory id), the Pin toggle (editable packages, `aria-pressed`, `skill.set_pinned`) and Delete (disabled with the reason for a read-only package, like Edit), an off banner with Turn on, the Access section, requirement notes, and Instructions/Original text tabs with Edit plus, for an editable package, a History tab. History (`SkillHistory.svelte`) reads `skill.history` (scope `editable_scope`, the package name, limit 50) whenever the package changes, so every inventory reload refreshes it; each revision shows number, what it did, when and who, and its changed files, and every revision but a baseline has Revert. Revert asks first; when the server refuses because a later revision changed the same part of the Skill (`domain_error` with `data.later`), the dialog offers to revert both together and repeats until the server accepts or refuses otherwise. Delete asks first, says who loses the Skill and that it moves to Archived. Access has one row per Identity Agent and one per Project that can activate the package. Agent rows toggle that Agent's access, the owner's row included (through its exclusions); Project grants and names that resolve to another copy or are not visible are locked with a reason. For a private package the other Agents' rows are sharing rows (`skill.share` with the full receiver list; none stops sharing), and a receiver blocked by its own selection gets an Allow action and does not count as receiving it (group count and the library summary's blocked note). A disabled package replaces Access with the off banner; selections and sharing stay stored.

`skillAccess.js` owns the rules: with `*`, unticking adds the name to `excluded_skills` and ticking removes it; with a fixed list, ticking adds it to `allowed_skills` (and releases an exclusion) and unticking removes it; an own Skill follows the `*` rule in both modes (its owner has it unless excluded, see `../skills.md`); only changed fields are sent. The library summary of a private package reads "Off for <owner>" while its owner excludes it. `skillMenus.js` builds the row context menus (Library, Agent, Project perspectives; items in `design.md` -> Skills) and SkillsView supplies their actions (the Agent editor supplies its own for Agent rows, see Extensions, Skills, Agents, and channels above); Edit instructions reads the package's SKILL.md through `skill.inspect` unless the caller already shows it; Copy name writes through `lib/clipboard.js` and confirms with a toast. Row menus (`skillMenus.js`) give every row that resolves to a package the same package items: Open, Edit instructions, Copy name | Turn this skill off/on | Delete... Edit and Delete act on the package wherever it is listed (user requirement 2026-10-05: a Skill is managed where it is seen), also a global or shared one from an Agent row; a package without `editable_scope` keeps both disabled with a short reason from its `source_kind` (`skillReadOnlyHint`: ships with vBot, comes with an Extension, from a skill folder, in the Project repository, cannot be loaded). The Skill page shows Edit and Delete the same way, disabled with the full reason (`skillReadOnlyReason`). The delete confirmation says who loses the Skill (`skillDeleteConfirmText`: every Agent and Project for a global package; the owner, and its share receivers, for a private one). `SkillSelectionPanel` gives every row a "⋯" button for its menu whenever the caller offers one. A Project change writes exactly one list for the package's pool (`skills_project_disabled` inverted, `skills_bundled_enabled`, `skills_global_enabled`). Writes run one at a time and reload the inventory; failures are toasts.

Server-projected inventory ids distinguish same-name packages; `editable_scope` alone enables human editing/deletion. The inspection request is versioned independently of inventory refresh, and stale responses cannot replace a newer selection. The view reloads on Skills, Agents and Projects refresh tokens; open drafts survive those refreshes. The add menu offers "Install from link or file...", "Create skill..." (defaulting to the selected Agent's private home, else global) and "Manage skill folders...", a page with Back whose folder editor stays mounted after first visit so its autosave participant survives collection changes. Creation separates name, description, and instructions and serializes quoted YAML metadata; original-text editing preserves the full authored document. Local STT/TTS setup and TTS previews are owned by `LocalSpeechSupport.svelte`,
keyed by the selected target in the Voice speech Model editor, which also passes the
target's `metadata`. Its setup runs on
`settings/localSetupJob.svelte.js`, the installation job controller shared with the

for one target, 1.5 s polling while installing or restarting, a request-id guard, and

does not reconnect within 90 s reports `restart_timeout`). While the target is missing
or failed it shows the download size and license (`describeLocalModelDownload`);
while it installs, the translated phase (`settings.localSpeech.phase.<phase>`), and
during the Model download `settings.localSpeech.downloadingModel` with the shared
`components/ui/ProgressBar.svelte` ("X of Y", `describeDownloadProgress` in
`settingsView/localModels.js`); errors translate `settings.localSpeech.error.<code>`
(`install_failed` fallback). Setup polling survives

refreshes availability immediately. The preview waits for saved options, streams
phases/elapsed time, offers cancellation and displays the server-owned artifact
in the shared `components/ui/AudioPlayer.svelte` without autoplay (media ownership
and coverage: `webui/chat.md`). Unmount aborts its request and timers; failed generation

The task Model editor on Voice also owns per-engine speech memory controls. It polls the
metadata-only memory RPC without reloading option drafts; each model has its own
loaded/busy state and targeted unload button. Unloading STT leaves TTS usable,
including when TTS is busy. Stale polls cannot overwrite unload results, failed
unloads permit retry, and unmount clears polling. Coverage:
`SettingsSpecializedModelsPanel.test.js` and `lib/__tests__/api.test.js`.

The task Model editor displays schema defaults without inserting them into stored option drafts and submits only changed bindings. A boolean field without a boolean default (for example video `generate_audio`) renders as a select of Provider default/On/Off, where Provider default removes the stored value; a boolean with a default stays a toggle. Emptying a JSON field removes its stored value while the textarea keeps the typed text; an empty object or array default shows the field's `placeholder`. Choosing another target keeps the previous options the new schema accepts unchanged (`compatibleOptions`: same name, an offered choice, a number in range, a switch, text or JSON; a carried select hidden by the carried options is dropped) unless an option was already edited for the new target. Each configured row with stored options offers Reset options (tertiary, on the JSON line), including when those options are absent from the live schema; it clears the options while preserving the target. Coverage: `SettingsSpecializedModelsPanel.test.js` exercises unrelated stale bindings, displayed defaults, and reset after schema drift.

Select choices with an empty value (for example "Provider default" or "Model default") are real, selectable choices. A select carrying `options_by` shows only the choices its referenced field's current value allows, is not rendered at all when that value's entry is an empty list (the stored value stays in the binding), and changing that field moves a now-hidden value as the contract in `model_tasks.md` -> Conventions requires; the renderer knows no field names. Pure helpers `visibleFieldOptions` / `isOptionFieldHidden` / `reconcileDependentOptions` live in `taskModelSettings.js` (`taskModelSettings.test.js`); mounted coverage in `SettingsSpecializedModelsPanel.test.js`.


## Channel connection setup

`SettingsChannelsPanel.svelte` supports Telegram, Discord, Slack, Mattermost and WhatsApp. The existing Channel autosave owner also persists Slack app-token variable names and Mattermost server URLs. IDs stay strings, preserving opaque IDs and integers beyond JavaScript's safe range. Create saves WhatsApp disabled with the literal `self` allowlist by default.

`WhatsAppSetup.svelte` owns explicit install/connect/re-pair actions and disposable three-second status polling. Only `channel.whatsapp.status` and the dedicated setup/pair responses expose the transient QR; the component clears it after connection and ignores stale responses after unmount. With `hideWhenConnected` (a collapsed Channel row) a connected setup renders nothing; errors and unfinished steps always show. Server-owned installation continues across navigation. Normal Channel status additionally exposes actual `connected` state for the new transports. Coverage: `WhatsAppSetup.test.js`, `SettingsView.channels.test.js`, and `settingsView.test.js` (channel payloads).
