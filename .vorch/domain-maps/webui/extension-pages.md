# WebUI Extension page host

Read when changing the WebUI host of Extension pages or the page client: the frame bridge, page routes and history forwarding, layers, invalidations, Run streams and their recovery, Tool Call cancel, server folder listing, autosave participants, clipboard permission, message caps and page styles. The invariants every WebUI task needs are in `webui.md` -> Ownership; the Extension side of pages (declarations, API versions, page build) is `extensions.md`.

## SDK transport boundary

The SDK source closure excludes `lib/api.js` and the application API directory; `webui/scripts/extension-sdk.mjs` rejects either during packaging, including transitive imports. Shared Chat controllers require `operations`; Settings drafts require `submit` and conflict `reload`. Pure Run event classifications, media addresses and error values are shared without importing network clients. The App supplies permission approval, Portal, path listing and speech playback capabilities through callbacks/context; an isolated page acquires only its declared bridge capabilities.

## Host and bridge

Extension pages use generic shell routes and `ExtensionPage.svelte`; the opaque frame bridge binds source window, nonce and registration epoch. `extensionPageClient.js` exposes owner operations, declared public domain services, route/toast/context, explicit local UI commands, selected Run/file capabilities and server folder listing. Reload/disposal rejects stale replies and closes subscriptions; reconnect refreshes snapshots without replaying mutations. Domain UI stays under its Extension's `ui/`, built by `scripts/build-extension-pages.mjs` with the shared Vite/Svelte dependencies. Page-owned text lives in the Extension's `ui/i18n.js` catalog under its own key namespace, registered from its `ui/main.js` before mounting; shared core keys stay in the core catalog. Tests: `ExtensionPage.test.js`, `extensionPageClient.test.js` and the independently built fixtures.

A bridge addition that is optional on either side keeps `BRIDGE_VERSION` and the Extension `API_VERSION` unchanged; a method a page relies on raises the Extension API version (`extensions.md`).

App applies the Page catalog as soon as it arrives, so a pending Contribution read cannot delay resolving a Page link.

## Contribution surfaces

`lib/contributions.js` owns deterministic composition: core snippets use `core:` IDs and Extensions use owner-qualified IDs. Additions follow declared order then ID; saved order takes precedence. Replacements render only after an explicit user choice and only while available and matching the surface's scalar context. Missing, disabled or hidden replacements restore the core contribution. Server Settings own shared preferences at `appearance.ui_layout`; Settings Appearance edits them through shared sortable/toggle controls. Unknown surfaces, uninstalled IDs and future layout fields survive read-modify-write updates. An uncustomizable recovery button opens the same editor whenever a layout is customized, so hiding navigation or Settings cannot strand the user. The registry participates in the App autosave coordinator; failed writes keep the visible draft and offer Save retry. A cold read failure has an explicit reload action.

`contributions.svelte.js` loads shared Settings and refreshes them on public Settings invalidation or reconnect. `null` means no server decision; an object (including `{}`) always wins over browser storage. A legacy `vbot.ui-layout.v1` customization is previewed but requires an explicit import/default choice before editing; its original copy is only removed after a successful server write. The shared Settings draft owner sends compare-and-set bases, rebases unrelated edits, keeps newer local input during in-flight writes, and reports competing saved edits.

`contributionPresentation.js` holds native metadata even before a view mounts; mounted registrations refine its labels. Preferences therefore work on a cold Settings link without visiting Chat first. The shared icon renderer supports the declared named icons as well as bounded path geometry. Local composer commands edit drafts but never submit through the human Send path; programmatic admissions use declared domain services and retain SYSTEM provenance.

The surface catalog in `contributions.js` covers shell status/navigation, Chat header/composer/context/footer, timeline, individual Messages, Message actions, Session list controls/rows, Tool results, Agent/Project editor sections, and Settings sections. Existing controls are core snippets in those same surfaces. The shell navigation, timeline and each Settings panel are replaceable as whole regions; composer, footer, header actions and status controls have individual IDs. `settings.sections` receives the current `settings_section`; settings-only pages declare `navigation: false`. The surface passes only whitelisted scalar context and explicitly supplied bounded JSON data, never Svelte state or DOM handles. Composer commands remain local to each Chat area. Message views receive a bounded text projection without attachments or Provider payloads; their `message.copy` command copies only the current Message. Session row `session.open` opens only that row. Editor `editor.focus` accepts only explicitly offered field names; domain saves remain with the editor autosave owner. Rich Tool-result views receive the shown arguments/result and may request the existing lazy read through `tool.read`.

`contributions.svelte.js` owns native source reads through `contributionSources.js`: equal owner/id/epoch/operation/parameter inputs share one live read and retained result, and unique inputs travel through read-only `extensions.contribution_sources` batches of at most 32 with at most two batches in flight. One registry subscription filters invalidations; each running input keeps at most one trailing read and superseded replies are discarded. A batch has a 60-second transport deadline; reconnect/lifecycle refresh aborts old batches, and releasing their final consumer aborts them immediately. Slots are released independently of an unresponsive transport promise, and aborted late replies are fenced. Released consumers drop queued work and receive no late result; cache entries exist only while subscribed. A failed input retains usable data and supports explicit retry, independently of other batch results. Actions still use the single-call `extensions.contribution_operation` path and are never batched or replayed. `ContributionControl.svelte` subscribes Message, Message-action and Session-row sources only within 200px of the viewport using one registry-owned IntersectionObserver; leaving the viewport releases the subscription, and re-entry reads current data. Browsers without IntersectionObserver retain bounded scheduling for all mounted rows. Hidden documents pause queued source batches and refresh live subscriptions once visible. Source subscription visibility is independent of any parent list windowing. The declaration's operation allowlist governs dynamic actions. Context/registration changes and disposal discard stale replies. Native items render bounded plain text and validated icon geometry; rich views reuse the isolated page host, autosave and navigation layers. API 30 pages receive `ui` context plus available command names; `client.command` dispatches only explicit local/global callbacks. Conditions preserve flat scalar equality and support bounded `all`/`any`/`not`, explicit existence, membership and numeric comparisons; missing values never satisfy comparisons and invalid expressions fail closed. Changing the canonical Session/Run/Tool/Message/editor scope renews the nonce before another command can affect the new scope. Coverage: `contributions.test.js`, `contributionSources.test.js`, `ContributionSurface.test.js`, `ChatComposer.test.js` and `AppShell.test.js`.

Isolated Settings views publish only non-secret, plain searchable metadata through `client.setSearchIndex([{id,label,terms}])` and handle `client.onSearch(id)`. The host indexes hidden declared markers through the existing Settings search owner and forwards reveal/focus into the frame. Entries are bounded to 200 with unique IDs (128 characters), labels (256), terms (4096) and the ordinary bridge request byte cap. Page reload clears the index. Embedded pages reporting an open navigation layer temporarily expand the same frame to the viewport, preserving their editor and dialog state.

## Routes, layers and history

- The page route is the view's navigation place: `ExtensionPage` sends `'/' + place.join('/')` (or `''` at the page's start) in init and context; `route.push` becomes `navigation.navigate(place)`, a Back/Forward step, and `route.replace` becomes `navigation.replace(place)`. Both reply `{}`, and the page receives the new route with the next context update.
- Open dialogs and menus inside a page are layers of the App navigation: the client's `registerLayer({close})` keeps a local stack and sends the one-way `vbot.extension.layers.state {open}` when the stack becomes non-empty or empty, and again after init; while the page reports layers, `ExtensionPage` holds one navigator layer whose close posts `vbot.extension.layers.close`, and the client closes its topmost layer. The host releases that layer on `open: false`, reload, registration change and unmount. A Svelte page calls `provideNavigation({ registerLayer: client.registerLayer })` in its root, so the shared Modal and ContextMenu register themselves.
- Back/Forward input inside a page reaches the App in the Desktop app: when the navigator handles that input itself (`handlesInput`), `init` carries `forwardHistoryInput: true`; the client then cancels Alt+Left/Right, BrowserBack/BrowserForward and side buttons 3/4 pressed inside the page, by the navigator's rules, and sends the one-way `vbot.extension.history.move {direction}`, which the host accepts only after Ready from the current frame (and only when it asked for forwarding) and turns into the navigator's `back()`/`forward()`. In a browser the page keeps its native handling.
- These additions are optional on either side, so `BRIDGE_VERSION` and the Extension `API_VERSION` stay unchanged (`ExtensionPage.test.js`, `extensionPageClient.test.js`).

## Invalidations

Extension page invalidations arrive as `vbot.extension.invalidate`. An owner-scoped `extensions` change (from `ExtensionHost.publish_change`) reaches only that Extension's open page and carries the optional field `change: {resource, ids, revision}`; descriptor reloads, frame-context replacement and Run-stream recovery invalidate without it. `extensionPageClient.onInvalidation` listeners receive `{reason, change}`, where `change: null` means anything can have changed; a malformed `change` is dropped to `null`. The field is additive, so pages built without it still refresh everything and neither `BRIDGE_VERSION` nor the Extension `API_VERSION` changed (`ExtensionPage.test.js`, `extensionPageClient.test.js`).

The reserved `page_badges` resource refreshes only shell descriptors, not page data. A newer authoritative permission snapshot instead sends every open page a `permissions_approvals` invalidation with no request ids or contents; the page can refresh its own owner-filtered read through its Extension operation (`extensions/host.md` -> Current authority and pending approvals). Reconnect still refreshes normal snapshots; no decision mutation is replayed (`appController.test.js`).

Custom Service Resources use `extension_resource_changed`, independently of `extensions` lifecycle changes. The App preserves canonical Resource identity and revision without fetching Page or Contribution catalogs. A Page receives the existing `change` shape with that canonical name and empty `ids` only when its declared Services intersect the event's affected Services. A Contribution source must name the canonical Resource, or its local name when the source and publisher share an owner. Both filter registration epochs before refreshing or holding hidden-page changes. Arbitrary Python observer scope is never forwarded. Global lifecycle/reconnect invalidations still refresh every retained consumer, including after a failed catalog read; this recovers missed publications without replaying mutations. Tests: `App.test.js`, `ExtensionPage.test.js`, `ContributionSurface.test.js`.

While the browser tab is hidden (`document.hidden`), the host holds these App invalidations for the current frame instead of posting them, so a page does not refresh what nobody sees; on `visibilitychange` to visible it posts one invalidation in the same shape: `change` with the union of the held ids (newest `revision`) when every held change named the same resource, otherwise no `change` (a full refresh). A reload drops what was held, as the new frame reads everything. Descriptor, reload and Run-stream recovery invalidations are not held (`ExtensionPage.test.js`).

## Capabilities

- Extension pages can cancel an active Tool Call through `extensionPageClient.cancelToolCall(groupId, runId, toolCallId)`. The host routes the fixed capability to the Extensions RPC edge, which checks current page registration and canonical owned-Run access before calling the existing Run cancellation API. No arbitrary Chat RPC access is granted (`ExtensionPage.test.js`, `test_extensions_methods.py`).
- API 24's optional `client.openSession({agent_id, project_id?, session_id})` sends fixed bridge method `session.open`; the host accepts only those canonical address fields and uses the App's existing Session navigation, including hidden temporary owners. URLs and arbitrary RPC methods are not accepted. This opens the original Chat approval UI rather than cloning decisions into the Extension. Current frame/nonce/epoch checks remain unchanged, and `BRIDGE_VERSION` stays 1 (`ExtensionPage.test.js`, `extensionPageClient.test.js`).
- Extension pages read and change the user's favorite Models through `extensionPageClient.readModelFavorites()` and `setModelFavorite(model, favorite)` (bridge methods `favorite_models.list`, `favorite_models.set`). A page that bundles `modelSelection.js` shows stars after it calls `configureModelFavorites`; a page does not hear of a change in another window until it reads them again.
- Every failed bridge call retains an API error's `code` in `vbot.extension.error`; the page client restores it for domain recovery, including management revision conflicts and deleted records. Declared service failures preserve their structured `details.data`; directory listings retain their specific recovery reason (`ExtensionPage.test.js`).
- API 30's `client.services.describe/query/execute` uses the public host service catalog, canonical domain payloads and each page's declared service allowlist, with registration epoch validation at the server edge. Public resource changes reach `onInvalidation` without private state. `client.openExternalUrl` opens explicit HTTP(S) links with no embedded credentials; it does not grant arbitrary protocols or RPC access.
- `client.context.api` exposes the host catalog's `{version, features}` for optional capability negotiation; an unavailable catalog has `version: null` and no features. Both standalone and embedded pages receive it in init and subsequent context updates. External links use the Desktop browser handoff when running in the Desktop accessor.
- Extension pages list the server's folders through `extensionPageClient.listDirectory(params)` (bridge method `directory.list`), which takes and returns the `filesystem.list` params and result, so a page passes it to the shared `PathField` as `listDirectory`. `ExtensionPage` checks the params' types and relays them through `api.listServerDirectory`; the reply is bound to the frame like every call, so reload and unmount drop it. A failed listing additionally projects its listing `reason` as `details.data.reason` for the shared `PathField`'s translated recovery. A page relies on this method, so it is Extension API v12 (`extensions/management.md` -> API versions); `BRIDGE_VERSION` stays 1, since the envelope is unchanged and a page built before never sends the method (`ExtensionPage.test.js`, `extensionPageClient.test.js`).
- The isolated Extension iframe permits clipboard writes so shared Copy actions work. Its opaque origin requires `clipboard-write *`; clipboard reads and same-origin access remain ungranted (`ExtensionPage.svelte`, `ExtensionPage.test.js`).
- Extension pages can register one autosave participant through `extensionPageClient.js`; the host joins the App navigation coordinator and accepts save state/results only from the current frame registration. Reload rejects every pending flush; stale client completions are ignored. Leaving a transition while the frame saves sends the one-way `vbot.extension.autosave.release`, which the client passes to its participant's `release()` before it reports its pending state (`webui/autosave.md`); the message is additive, so `BRIDGE_VERSION` stays unchanged. Tests: `ExtensionPage.test.js` and `extensionPageClient.test.js`.

## Run streams and history

- Extension Run subscriptions relay the verified Run replay watermark (`replay_through_sequence`) with their subscription id. A page can buffer initial replay until that sequence before replacing its displayed History (`ExtensionPage.test.js`, `test_extensions_methods.py`).
- The Extension host's `extensionRunStream.js` refreshes owned Run capabilities after stream errors or 25 seconds without transport activity, with bounded backoff and the last delivered sequence. Successful recovery or an unavailable replay stream invalidates the page's snapshots through the existing bridge; it never replays mutations. Heartbeats reset liveness without becoming page events, terminal events stop recovery, and teardown rejects late callbacks (`ExtensionPage.test.js`).
- Extension page History and timeline Run streams take the Chat's step window (`chat/timeline.md` -> Transport): `history.read` with `query.child_limit` and `run.subscribe` with `child_limit` (1-200, timeline only, kept when the stream recovers) deliver each Run's latest steps behind a `history_gap`, and `history.children` (`extensionPageClient.readRunChildren`, RPC `extensions.page_timeline_children`) reads the steps before a gap of a Run the participant owns. A step page's verified `file_urls` join the selected participant's grants like a History page. Tool rows carry previews of their call (`chat/timeline.md` -> Semantic contract); `history.tool_call` (`extensionPageClient.readToolCall`, RPC `extensions.page_tool_call`) reads the whole arguments and result of one row of a Run the participant owns, granting its `file_urls` the same way (API v19). Without the window a Run arrives whole, and a long one exceeds the bridge's 8 MB reply cap (Message caps). A page relies on these, so they are Extension API v16; `BRIDGE_VERSION` stays 1 (`ExtensionPage.test.js`, `test_extensions_methods.py`).
- Extension page history includes canonical Current Context Usage from the full Session context tail, independently of the visible page. Swarm Activity uses that projection and live Run usage events with the shared Chat usage formatter (`test_extensions_methods.py`, `SwarmPage.activity.test.js`).
- The Extension host unwraps the API subscriber envelope before forwarding canonical Run events (`type`, `run_id`, `sequence`, `payload`). Server-verified `file_urls` from History and Run streams remain available for the selected participant; stream ownership comes from `extensions.page_run.participant_id`. Switching participant/group clears that scope and ignores late prior-scope replies and stream file grants (`ExtensionPage.test.js`).

## Message caps and styles

- Extension bridge commands are capped separately from larger host replies. An oversized operation reply must return an error, never silently disappear; client requests time out without automatic replay. Shared typography loads the bundled Geist Sans/Mono variable `woff2` assets from `styles/fonts/` through `styles/app.css`, so isolated pages need no external font allowance (`build-extension-pages.test.js`).
- An Extension page's bundle holds only `styles/app.css` and the stylesheets its imported components import themselves. Rules a core component takes from a stylesheet its parent view imports (such as the Skills view's `skills.css`) are missing there, so a core component that Extension pages reuse keeps its rules in its own `<style>` block or in a stylesheet `app.css` imports. Through `app.css` a page also declares the dark `color-scheme`, while the host keeps the frame element in the light scheme (`webui/design.md` -> Tokens and assets).
- An isolated page importing the app styles owns a bounded scrollport, because the shared body/app shell intentionally hides document overflow.
