# WebUI Extension page host

Read when changing the WebUI host of Extension pages or the page client: the frame bridge, page routes and history forwarding, layers, invalidations, Run streams and their recovery, Tool Call cancel, server folder listing, autosave participants, clipboard permission, message caps and page styles. The invariants every WebUI task needs are in `webui.md` -> Ownership; the Extension side of pages (declarations, API versions, page build) is `extensions.md`.

## Host and bridge

Extension pages use generic shell routes and `ExtensionPage.svelte`; the opaque frame bridge binds source window, nonce and registration epoch. `extensionPageClient.js` exposes only owner operations, route/toast/context, selected Run/file capabilities and server folder listing. Reload/disposal rejects stale replies and closes subscriptions; reconnect refreshes snapshots without replaying mutations. Domain UI stays under its Extension's `ui/`, built by `scripts/build-extension-pages.mjs` with the shared Vite/Svelte dependencies. Page-owned text lives in the Extension's `ui/i18n.js` catalog under its own key namespace, registered from its `ui/main.js` before mounting; shared core keys stay in the core catalog. Tests: `ExtensionPage.test.js`, `extensionPageClient.test.js` and the two independently built fixtures.

## Routes, layers and history

- The page route is the view's navigation place: `ExtensionPage` sends `'/' + place.join('/')` (or `''` at the page's start) in init and context; `route.push` becomes `navigation.navigate(place)`, a Back/Forward step, and `route.replace` becomes `navigation.replace(place)`. Both reply `{}`, and the page receives the new route with the next context update.
- Open dialogs and menus inside a page are layers of the App navigation: the client's `registerLayer({close})` keeps a local stack and sends the one-way `vbot.extension.layers.state {open}` when the stack becomes non-empty or empty, and again after init; while the page reports layers, `ExtensionPage` holds one navigator layer whose close posts `vbot.extension.layers.close`, and the client closes its topmost layer. The host releases that layer on `open: false`, reload, registration change and unmount. A Svelte page calls `provideNavigation({ registerLayer: client.registerLayer })` in its root, so the shared Modal and ContextMenu register themselves.
- Back/Forward input inside a page reaches the App in the Desktop app: when the navigator handles that input itself (`handlesInput`), `init` carries `forwardHistoryInput: true`; the client then cancels Alt+Left/Right, BrowserBack/BrowserForward and side buttons 3/4 pressed inside the page, by the navigator's rules, and sends the one-way `vbot.extension.history.move {direction}`, which the host accepts only after Ready from the current frame (and only when it asked for forwarding) and turns into the navigator's `back()`/`forward()`. In a browser the page keeps its native handling.
- These additions are optional on either side, so `BRIDGE_VERSION` and the Extension `API_VERSION` stay unchanged (`ExtensionPage.test.js`, `extensionPageClient.test.js`).

## Invalidations

Extension page invalidations arrive as `vbot.extension.invalidate`. An owner-scoped `extensions` change (from `ExtensionHost.publish_change`) reaches only that Extension's open page and carries the optional field `change: {resource, ids, revision}`; descriptor reloads, frame-context replacement and Run-stream recovery invalidate without it. `extensionPageClient.onInvalidation` listeners receive `{reason, change}`, where `change: null` means anything can have changed; a malformed `change` is dropped to `null`. The field is additive, so pages built without it still refresh everything and neither `BRIDGE_VERSION` nor the Extension `API_VERSION` changed (`ExtensionPage.test.js`, `extensionPageClient.test.js`).

## Capabilities

- Extension pages can cancel an active Tool Call through `extensionPageClient.cancelToolCall(groupId, runId, toolCallId)`. The host routes the fixed capability to the Extensions RPC edge, which checks current page registration and canonical owned-Run access before calling the existing Run cancellation API. No arbitrary Chat RPC access is granted (`ExtensionPage.test.js`, `test_extensions_methods.py`).
- Extension pages list the server's folders through `extensionPageClient.listDirectory(params)` (bridge method `directory.list`), which takes and returns the `filesystem.list` params and result, so a page passes it to the shared `PathField` as `listDirectory`. `ExtensionPage` checks the params' types and relays them through `api.listServerDirectory`; the reply is bound to the frame like every call, so reload and unmount drop it. A failed listing's `vbot.extension.error` also carries the API error `code` and the listing `reason`, which the client restores as `code` and `details.data.reason`, so the page's field shows the app's translated failures. A page relies on this method, so it is Extension API v12 (`extensions/management.md` -> API versions); `BRIDGE_VERSION` stays 1, since the envelope is unchanged and a page built before never sends the method (`ExtensionPage.test.js`, `extensionPageClient.test.js`).
- The isolated Extension iframe permits clipboard writes so shared Copy actions work. Its opaque origin requires `clipboard-write *`; clipboard reads and same-origin access remain ungranted (`ExtensionPage.svelte`, `ExtensionPage.test.js`).
- Extension pages can register one autosave participant through `extensionPageClient.js`; the host joins the App navigation coordinator and accepts save state/results only from the current frame registration. Reload rejects every pending flush; stale client completions are ignored. Leaving a transition while the frame saves sends the one-way `vbot.extension.autosave.release`, which the client passes to its participant's `release()` before it reports its pending state (`webui/autosave.md`); the message is additive, so `BRIDGE_VERSION` stays unchanged. Tests: `ExtensionPage.test.js` and `extensionPageClient.test.js`.

## Run streams and history

- Extension Run subscriptions relay the verified Run replay watermark (`replay_through_sequence`) with their subscription id. A page can buffer initial replay until that sequence before replacing its displayed History (`ExtensionPage.test.js`, `test_extensions_methods.py`).
- The Extension host's `extensionRunStream.js` refreshes owned Run capabilities after stream errors or 25 seconds without transport activity, with bounded backoff and the last delivered sequence. Successful recovery or an unavailable replay stream invalidates the page's snapshots through the existing bridge; it never replays mutations. Heartbeats reset liveness without becoming page events, terminal events stop recovery, and teardown rejects late callbacks (`ExtensionPage.test.js`).
- Extension page history includes canonical Current Context Usage from the full Session context tail, independently of the visible page. Swarm Activity uses that projection and live Run usage events with the shared Chat usage formatter (`test_extensions_methods.py`, `SwarmPage.activity.test.js`).
- The Extension host unwraps the API subscriber envelope before forwarding canonical Run events (`type`, `run_id`, `sequence`, `payload`). Server-verified `file_urls` from History and Run streams remain available for the selected participant; stream ownership comes from `extensions.page_run.participant_id`. Switching participant/group clears that scope and ignores late prior-scope replies and stream file grants (`ExtensionPage.test.js`).

## Message caps and styles

- Extension bridge commands are capped separately from larger host replies. An oversized operation reply must return an error, never silently disappear; client requests time out without automatic replay. Shared typography loads the bundled Geist Sans/Mono variable `woff2` assets from `styles/fonts/` through `styles/app.css`, so isolated pages need no external font allowance (`build-extension-pages.test.js`).
- An Extension page's bundle holds only `styles/app.css` and the stylesheets its imported components import themselves. Rules a core component takes from a stylesheet its parent view imports (such as the Skills view's `skills.css`) are missing there, so a core component that Extension pages reuse keeps its rules in its own `<style>` block or in a stylesheet `app.css` imports. Through `app.css` a page also declares the dark `color-scheme`, while the host keeps the frame element in the light scheme (`webui/design.md` -> Tokens and assets).
- An isolated page importing the app styles owns a bounded scrollport, because the shared body/app shell intentionally hides document overflow.
