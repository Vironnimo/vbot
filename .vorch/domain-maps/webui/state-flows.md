# WebUI State Flows

Deep per-feature runtime behavior of `webui/` — chat timeline projection, sub-agent rows, streaming, queue, history-load discipline, navigation history, and the Settings/Projects/Providers/Logs/Cron panels. Read the relevant part only when working on that surface; the cross-cutting transport contracts and invariants live in `webui.md`.

- `api.js` normalizes transport errors into `ApiClientError` with stable codes. Add new server methods as thin wrappers only when the helper improves validation or caller ergonomics; otherwise call `rpc(...)` directly from the view.
- `/ws` is server-push only. Clients send commands through `POST /api/rpc`. On connect the server sends a `connection_ready` hello frame with the bus `epoch`, `last_sequence`, and `active_runs` snapshot. Clients pass `epoch` and `after_sequence` on reconnect: when the epoch matches and `after_sequence > 0` the bus replays retained events above that sequence (resume); otherwise the client receives only live events (the snapshot covers state). `connectionState.js` starts in `reconnecting`, moves to `connected` on open and `disconnected` on close/disconnect, schedules jittered exponential-backoff reconnects after unexpected closes, and tracks the bus `epoch` to detect server restarts.
- SSE is the primary per-Run output stream. `subscribeRunEvents(...)` subscribes to whole Run events plus transient streaming deltas and may add `after_sequence`; native reconnect also uses server SSE event IDs / `Last-Event-ID`. On stream errors `chatRunStream` resubscribes itself with jittered exponential backoff (500ms base, doubling per attempt, max 3 attempts); the attempt budget counts *consecutive* failures only — it resets as soon as an event arrives, so transient drops spread across a long run never exhaust it.
- All three reconnect loops — app WebSocket (`connectionState.js`), per-Run SSE (`chatRunStream.js`), and the log stream (`LogsView.svelte`) — share one jittered exponential-backoff helper, `lib/backoff.js` `reconnectBackoffDelay(attempt, { initialDelayMs, maxDelayMs })`. Each call site keeps its own timer, attempt counter, and attempt cap; only the delay math (exponential doubling clamped to `maxDelayMs`, then ±`jitterFactor` jitter, default 25%) is shared. A new reconnect path reuses the helper rather than re-deriving the formula, so no two clients reconnect in lockstep after a server blip.
- Logs do not use the shared app WebSocket. `LogsView` reads one file with `log.read`, then opens `/ws/logs` with the returned `cursor` so lines appended between read and subscribe are not lost.
- Tab switches and chat Session overrides are browser-history entries, so Back/Forward navigate inside the SPA (e.g. from a Sub-Agent session back to the parent) instead of leaving the app; this works identically in the Desktop accessor because pywebview hosts a full browser engine (WebView2/WebKit) where mouse back buttons map to `history.back()`. App.svelte owns the wiring: it seeds `history.replaceState` on mount, pushes on tab switches (URL hash `#<view>`, which also restores the active tab on reload) and on override changes, and applies `popstate` entries. State format and comparisons live in `lib/navigationHistory.js`. Each entry captures the whole chat context that was on screen: the session override (`session`) **and** the selection (`selection: { agentId, projectId, projectAgentId }` — selected identity agent plus project context, tri-state `projectAgentId` like App's persisted mirror), so Back/Forward restore chips, project bar, and displayed session together. A restore fires `pendingSessionNavigation` whenever the session override **or** the selection differs from App's mirrors; ChatView applies the selection itself (`applyNavigationSelection` — pre-syncing `lastSharedSelectedAgentId`/`lastLoadedProjectId` so the round-tripped props cannot re-run the restore as a fresh user action) and reports it up only through the non-pushing callbacks (`onAgentSelected`/`onProjectSelected`/`onProjectAgentSelected`). The echo discipline matters: user-initiated session navigation in ChatView (drawer selection, return banner, override cleared by an agent switch in either bar) reports upward via `onSessionNavigation` and becomes a push; App-driven navigation (sub-agent link via `navigateToSubAgent`, history restores) flows down through the `pendingSessionNavigation` prop (`{ agentId, sessionId, subAgent, requestId, selection? }` or `{ returnToCurrent: true, requestId, selection? }`) and is never reported back, so a restore cannot re-push and truncate forward history. The mount path keeps the same discipline: ChatView's first `sharedSelectedAgentId` prop sync after mount is a **silent** reconciliation (no override clear, no report) — routing it through the user-action handler used to push a phantom `chat(null)` entry over a just-restored one when ChatView remounted during a restore. App also clears its override mirror and any pending navigation when ChatView unmounts (tab switch away from Chat), because the override state dies with the component. On a full reload, App **adopts** an own history entry that carries a session override for the initial view (mirror + pending navigation) instead of replace-seeding it away — the override survives the reload and Back/Forward keep working from it; the selection half comes from the localStorage mirrors, which the same state persisted. The project restore on that mount path runs `openProjectAgent(..., { keepOverride: true })`, so re-opening the remembered team member never clears the adopted override.
- Chat normally displays the selected Agent's `current_session_id` (or, with a project agent active, that agent's locally chosen session). **Display resolution is override-first:** an active session override (drawer pick or sub-agent link) wins over both the project branch and the identity-current branch in `activeAddressing`/`getActiveAgent`/`getActiveSessionState`/`displayedSessionKey`, so session navigation works identically in the identity and the project world. The override's owner is stored in `viewingSessionAgentId` as its outside spelling (bare identity id or full `agent@projekt`; `''` = the active agent's own past session), the session drawer lists and loads through the displayed agent's full address, and an override whose owner is not in the identity roster (project agent's session, deleted agent) renders through a minimal stand-in agent object so the banner and return button stay usable instead of dead-ending. Session drawer selections and Sub-Agent session links create accessor-local overrides only; they must not mutate the Agent's persisted current Session and must offer a return path. Every active override shows the footer banner; the copy differs (`chat.subagentSessionNotice` vs `chat.pastSessionNotice`). **The sub-agent banner's button returns to the PARENT session**: on entering a sub-agent view ChatView resolves the child's `subagent_parent` metadata via `session.list` (parent addressed `agent@projekt` when it carries a `project_id`); with a resolvable parent the button reads "Return to parent session" (`chat.returnToParentSession`, hint `chat.subagentSessionParentHint`) and navigates there as a normal user-initiated session navigation (history push — Back returns to the child; a parent that is not the owning agent's current session lands as a normal past-session view). Without usable parent metadata (old child sessions, vanished identity parent) the button keeps the return-to-current copy and behavior; the past-session banner's button stays return-to-current. The drawer marks the Agent's persisted current Session with a green "Current" badge, distinct from the accent highlight of the currently *viewed* session. Each row carries a "…" actions menu (the first per-row action surface; built to hold more, e.g. a later delete) whose one entry, Rename, swaps the row name for an inline input (Enter saves, Escape cancels) and calls the `renameSession` wrapper → `session.rename`; on success the drawer re-fetches so the row shows the server-normalized title, and other windows refresh through the same `sessions` token. A user title wins over the channel-derived `platform/conv_id` label and the raw id in `sessionDisplayName`; clearing it (blank) falls back to those. Repeated clicks on the same Sub-Agent session link are distinct navigation requests via App/ChatView request IDs, so returning to the parent and opening the same child Session again reloads it. `ChatTimeline` keeps a per-session scroll memory (keyed by `sessionState.key`, intentionally non-reactive, LRU-capped): switching the displayed session saves the outgoing session's scroll position and restores the incoming one's after render — a session the user left mid-history resumes there, a session left at the bottom (or viewed for the first time) starts at the newest content. A mid-history restore is additionally *pinned*: post-switch content turbulence (history reload after navigation, late-rendering content, browser re-clamps, run events) re-asserts the restored position instead of letting the stick-to-bottom autoscroll steal it from a transient near-bottom scroll offset; only real user scroll input (wheel/touchstart/pointerdown/keydown on the container) or a newly submitted turn releases the pin. The session-switch path, the pin re-assert, and the same-session stick-to-bottom autoscroll live in one pre-effect so they cannot fight; this works both during and outside an active Run.
- A non-blocking Sub-Agent spawn returns only a "running" descriptor as its tool result, so the child's final output never lands in `tool.result` (a blocking spawn carries it as `data.result`). When the child run's dot reaches `success` and no inline result exists, `ChatAssistantRun` requests the child's response through `ChatView.requestSubAgentResult`, which fetches the child Session's last assistant message via `chat.history` (small limit, distinct from the `limit: 100` navigation load) and caches it in `subAgentResults` under the row's cache key from `subAgentResultKey`: run-scoped (`agent::session::run_id`) when the child run id is known, session-scoped only otherwise — so repeated spawns into the same child session each fetch their own result. A failed fetch is cached as a retryable error entry (`error`/`failedAt`, 15s cooldown via `subAgentResultEntryAllowsFetch`) instead of a permanent empty result. The cached text is rebuilt into the same `tool_success` envelope a blocking spawn produces, so it renders in the tool block's Result row identically. Failed/cancelled children are not fetched. The tool row's time label shows the *child* Run's real runtime, not the spawn tool call's own duration (which is ~0s for a non-blocking spawn that returns the moment the child starts): `chatRunStream` records each tracked Run's terminal `timing.duration_ms` into the `subAgentRunStatuses` projection under `runDuration:<run_id>` / `sessionDuration:<agent>::<session>` keys (alongside the `run:` / `session:` status keys), and `subAgentToolStatusLabel` resolves it strictly by run id when one is known, by session only for run-id-less rows. When no child runtime was tracked (e.g. the WS lifecycle buffer rolled over before refresh), a non-blocking spawn shows no time rather than the misleading ~0s call duration; a blocking spawn (inline `data.result`) and `subagent_result` lookups fall back to their own tool-call duration.
- Sub-agent status/result/duration lookups are run-scoped whenever a run id is resolvable: a child session can be reused by later spawns, so `session:`-keyed entries may describe a different run and apply only to rows with no resolvable run id. A queued spawn's frozen descriptor never learns its run id; `chatRunStream` records a `queueRun:<queue_item_id>` → run_id mapping from the `run_started` payload, and `subAgentEffectiveRunId` resolves the row through it.
- Sub-agent spawn rows show live child activity: `trackSubAgentRunStatus` also records each run's most recent `tool_call_started` tool name into the status projection under `runTool:<run_id>` / `sessionTool:<agent>::<session>` keys (the session key is reset to empty on `run_started`, so a reused child session never shows the previous run's tool on run-id-less rows), and `ChatAssistantRun` swaps the spawn row's prompt preview for `subAgentLastToolName` while the row's dot is `running`. The lookup follows the same run-scoping discipline — strictly run-scoped when a run id resolves, session-scoped only for run-id-less rows — and only `subagent` spawn rows render it (`subagent_result` rows keep their session-id preview). The names arrive through the existing `/ws` `run_output` bridging of child runs (no new transport or backend contract); after a reconnect or reload the prompt preview shows until the child's next tool call. `verifySubAgentStatus` follows the same discipline: with a run id it writes only `run:`/`runDuration:` keys (and falls through to the run_summary scan when a *different* run is active in the child session); session-level keys are written only for run-id-less verifications.
- Sub-agent dot self-heal: when a sub-agent row has a "running" dot that comes only from the frozen persisted descriptor (for a row with a resolvable run id: no `run:<run_id>` entry exists; for a run-id-less row: no `session:<agent>::<session>` entry either), `ChatAssistantRun` triggers a verification via `ChatView.verifySubAgentStatus` (passing the row's run id and, for queued spawns, its `queue_item_id`). This calls `chat.history` (limit 20) with a once-per-key guard: if `active_run` is present and matches the verified run id (or no run id was given) → records `'running'`; otherwise finds the last `role: "run_summary"` message (matching the run id when given) and maps its `status`/`timing.duration_ms` into the status projection. When no summary exists, a run-id-less verification with a `queue_item_id` consults `chat.queue_list` (the child address, qualified with the displayed project via `qualifiedChildAgentAddress`): item still pending → `'running'`; item gone without a run ever starting → `'cancelled'` (a never-started spawn must not read as success); any other no-trace case falls back to `'completed'`. On error the guard is released so later attempts can retry. Settling the dot to `success` causes the existing `subAgentShouldFetchResult` effect to fire, filling the Result row without further changes.
- Per-row cancel controls: bash tool rows and sub-agent rows show a small cancel button while they are running. The button is hidden when the row is not running and uses a pure-CSS ~0.5s fade-in (no per-call JS timers) so fast bash calls never flash a button; during the reveal delay it is `visibility: hidden`, never an invisible click target. The "is this row cancellable" rule lives in `chatTimelinePresentation.js` (`isRowCancellable(row)`) as the single source of truth. The bash button calls `chat.cancel_tool_call` with the row's `run_id` and `tool_call_id`; a bash call cancelled this way returns the `cancelled_by_user` failure envelope, which `chatTimeline.js` renders as the `cancelled` row state (amber, like a run-level cancel), not as a red failure — and it never marks the run itself failed. The sub-agent button routes through `resolveSubAgentCancelPlan(tool, statuses)` (`chatTimelinePresentation.js`): a resolvable child run id — frozen descriptor or the `queueRun:<item>` mapping — goes to `chat.cancel` with `reason: "user"`; a queued spawn without one goes to `chat.queue_remove` (the child address, qualified with the displayed project), which on success also settles the row's session key to `cancelled` (nothing else will ever report a never-started child). When the queue item is already consumed and no mapping survived (page reload), ChatView looks up the child session's `active_run` via `chat.history` and cancels that run, or — child already terminal — forces a fresh verification so the stale dot settles. Cancelling one row does not cancel the parent Run.
- Run-level cancel lives in the composer, not the header: while the displayed session's run is active, an icon-only stop button (danger variant, 32px square, red at rest) renders left of the Send button and calls `chat.cancel` via ChatView's `handleCancelRun`. Send stays Send during a run (Enter/click queues; only the tooltip changes to "Queue message") — cancel and queue are two coexisting, equally visible actions, never one morphing button. The stop button ignores the composer `disabled` state (a run must stay cancellable while the input is locked) and disables itself only while the cancel RPC is in flight. There is no keyboard shortcut for cancel by explicit user decision (2026-07-02), and no run-cancel control in the chat header anymore.
- Initial Chat history loads the newest 100 visible messages; older pagination requests 50 at a time. When history returns an `active_run`, ChatView merges retained events before deciding whether to resubscribe so SSE-only deltas are not skipped after navigation.
- **History-load discipline (stale responses and background refreshes):** `loadHistoryForSession` is the one initial-load path for identity and project sessions (both worlds address `chat.history` by the session's stored agent spelling). After every await, per-session state may always be written, but global UI state (`loadingHistory`, `historyError`) and the SSE `attachRunStream` belong to the **displayed** session only — a response for a session the user has already left must not re-open a subscription the newer navigation closed, unlock the composer early, or banner-error the healthy view. A load whose target is not displayed at start never sets the loading flag or closes other subscriptions. `loadAgents` (the roster refresh on `resource_changed(kind:"agents")`) reloads current-session history only while the display actually follows the identity current pointer (no override, no active project agent) — a roster refresh must never steal the displayed override session's stream or composer — and prefers the live in-component selection over its captured `preferredAgentId` so a concurrent restore is not undone.
- `chat.stream` can return a Run/SSE payload, `{ command_handled: true, reply, output, data? }`, or `{ queued: true, item }`. Handled commands render inline and do not subscribe to SSE. ChatView routes purely on the response: a `data.command` of `new`/`handoff` is the **action** path (`/new` switches the selected Agent to the new current Session locally; `/handoff` switches to the new session under the response's `agent_id`, cross-agent capable). A `data.command` of `agent` is the **move** action (`/agent`): the current session was relocated server-side (**same** session id) to the response's `agent_id`, and ChatView opens it there. It is handled *before and independently of* the `new`/`handoff` switch, because a move can target **and originate from** either world (identity or project) whereas that switch is identity-only. `resolveMoveActionFromResponse`/`resolveMoveTarget` (`chatState.js`) decode the target world from the address (`@` present → project) via the shared `parseAgentAddress` seam; `moveSessionToAgent` (`ChatView.svelte`) routes an identity target through `switchToCurrentSession` and a project target through the project-bar path. Otherwise the `output` channel decides — `transient` appends a non-persisted card to the stream (`appendTransientCard`), `toast` (the default) shows a chat-local bottom toast (`showCommandToast`, 5s auto-dismiss via `COMMAND_TOAST_TIMEOUT_MS`); `/compact` is a toast that additionally reloads history so the new compaction separator appears immediately, and `/retry` follows the normal Run/SSE path when it returns a Run payload. There is no longer a top `actionInfo` notice for command output — only the bottom toast and transient cards; error notices stay in the top stack. Queued sends are displayed from server queue items and refreshed through `chat.queue_list`.
- Transient command cards (`output: "transient"`, e.g. `/status`, `/help`) are a client-only display concern: they live in a ChatView `transientCards` array (not in `sessionState`), are passed to `ChatTimeline`, and render as bordered monospace `.transient-card`s. They are never persisted and never sent to the model. Each card is **anchored in place**: `appendTransientCard` records the id of the last visible timeline item at creation time (`anchorId`, `null` for an empty timeline), and `ChatTimeline.groupTransientCards` interleaves each card immediately after its anchor item — so a later message renders below the card instead of pushing it to the bottom. Cards created on an empty timeline render `leading` (top); cards whose anchor item is gone after a history reload render `trailing` (end) rather than being dropped; multiple cards sharing an anchor keep creation order, so successive snapshots taken at the same point still **stack** for visual comparison. The array survives history reloads and run events for the displayed session and is cleared only when the displayed session key changes (or on page reload). The timeline's stick-to-bottom autoscroll keys on the cards too (they are part of `timelineSignature`).
- Queue state is a server-backed projection scoped by Agent plus Session. The accessor may optimistically add/remove/update items, but `chat.queue_*` remains the source of truth; the WebUI must not implement a second send queue. When a `run_started` event carries `queue_item_id`, the client removes that item from the local queue projection immediately; the terminal-event `syncSessionQueue` remains the consistency backstop.
- High-frequency SSE deltas may be batched in ChatView. Stable lifecycle events such as run start, tool start/result, Sub-Agent session links, assistant output, errors, and terminal events flush immediately so short-lived states remain visible in order.
- Long-lived-tab bookkeeping is bounded through `webui/src/lib/clientCaches.js`: the WS run-event dedup keys in `chatRunStream` live in a capped insertion-ordered set (the cap only has to exceed App.svelte's bounded `runServerEvents` window of 500), and ChatView's `subAgentRunStatuses` / `subAgentResults` projections are LRU-capped — evicting a `run:`/`session:` status key also releases its status-verification guard so a still-rendered row re-verifies instead of freezing on a frozen `running` descriptor. `loadHistory` additionally prunes retained `runEvents` of non-active Runs whose output the freshly loaded history fully persists (the event-level counterpart of `dropPersistedInactiveLiveRuns`, so nothing visible changes). For render cost, `chatTimeline` memoizes the projected `assistant_run` item of terminal Runs per session and run (terminal Runs' non-delta events are append-only and never mutate; in-place-mutating compressed streaming deltas exist only for the active Run), so the ≤33 ms streaming flush rebuilds only the active Run's projection instead of re-walking the whole session. `runEvents` of the currently viewed session still grows with genuinely viewed scrollback between history loads — that is retained content, not leaked bookkeeping.
- `App.svelte` passes Run lifecycle summaries from `/ws` to ChatView as a bounded list, and ChatView deduplicates them by Run id, Run-event sequence, and server event type. Do not reduce this to a single event prop; rapid internal follow-up Runs can otherwise overwrite each other before Svelte renders.
- SSE replay uses the highest contiguous sequence for the active Run, not the maximum sequence seen, because WebSocket summaries omit SSE-only deltas.
- Timeline selectors exported through `chatState.js` aggregate visible Run history into one `assistant_run` item per Run; their projection implementation lives in `chatTimeline.js`. Tool starts/results/stdout/stderr, timing, `subagent_session_started`, `model_fallback_activated`, and terminal Run data merge into that Run block rather than becoming separate chat messages.
- On refresh during a running Run, history (persisted messages) and the snapshot's `active_run` events both describe the same turn, so `selectTrackedRunTimelineSource` deduplicates by anchoring the live Run to its `user_message_persisted` message in history and dropping the persisted copy of that turn. Internal/automation Runs emit no `user_message_persisted` (notably the follow-up Run a non-blocking Sub-Agent completion spawns, triggered by a hidden `note`, and assistant/tool messages carry no `run_id`), so they cannot be anchored: when every `assistant_output`/`tool_call_result` message id the live Run produced is already persisted in history, the live Run is dropped in favor of history; otherwise (output not yet persisted) the live Run is kept. Skipping this dedup renders such a turn twice after refresh. A complementary safety net in `chatTimeline.js` (`dropPersistedInactiveLiveRuns`) drops live items of any non-active run whose output is fully persisted in history — needed when a run completes while the tab is open and its events stay in `runEvents` until the next `loadHistory` (the snapshot eliminates the original WS-replay trigger, but this natural-flow case can still surface).
- The `/ws` `connection_ready` snapshot replaces the historical buffer-replay-from-0 behavior. Instead of replaying every retained event (including stale `run_started` for long-completed Runs), the client applies the snapshot directly: active runs for the displayed session get SSE-attached; active runs in other sessions update sub-agent status projections; completed prior Runs no longer re-enter `runEvents` on a fresh connect. This eliminates replay-churn and ensures a fresh connect never re-injects stale lifecycle events. The snapshot is applied once per distinct reference by ChatView; reconnects that deliver the same hello frame are no-ops via the existing `attachRunStream` dedup.
- The ChatHeader token badge shows `input+output / context_window` from the session's last known usage (last assistant message with `usage`, or the `run_completed` payload). Hovering shows a native-`title` breakdown composed by the pure `lib/tokenUsageTooltip.js` (`formatTokenUsageTooltip(usage, sessionUsage)`): a **Last turn** block (input with middot-indented "read from cache (N%)" / "newly written to cache" / "uncached" share lines — only when the provider reported cache fields — then output and the estimation note) plus a **Session** block (measured-turn count, total input with cache share + hit %, total output, average cache read per cache-reporting turn, and an "N estimated turns excluded" line). Canonical `input_tokens` already includes cached tokens — the cache lines are shares of the input, never added on top; the session cache lines are hidden when `cache_turns` is 0 so a non-cache-reporting provider never reads as a 0% hit rate. `sessionState.sessionUsage` holds the whole-session totals: seeded/replaced by `chat.history`'s `session_usage` field on every history load (`loadHistory` option) and refreshed by every terminal run event's `session_usage` payload (`finishRun`) — replace-only, the client never accumulates turns itself.
- Persisted `role: "error"` messages and live `error_message_persisted` events render as standalone error items. Error text of the shape `"<prefix>: <status> <json-body>"` is split by `errorMessagePresentation` (`chatTimelinePresentation.js`): the embedded provider message (`error.message`, falling back to top-level `message`) becomes the visible summary, the pretty-printed raw body goes into a collapsed Details block; text without parseable embedded JSON renders unchanged. Persisted `role: "compaction_checkpoint"` messages and live `compaction_completed` events render as timeline separators. Persisted `role: "agent_takeover"` messages render as a **takeover separator** (`takeover_separator` item from `chatTimeline.js`, which closes the active assistant run at the divider like the compaction separator; `takeoverSeparatorLabel` in `chatTimelinePresentation.js` composes the localized "Taken over by {from} → {to}" from the `{from,to}` address JSON in `content`, addresses kept raw; rendered as accent-colored `.takeover-sep`, distinct from the muted compaction separator). `agent_takeover` is in `isVisibleHistoryMessage` so it survives normal history filtering. Kernel-internal notes/system reminders must be filtered from normal Chat history if they ever arrive.
- Live reasoning, assistant text, and tool-call deltas are compressed into `streamingRunEvents` (one retained event per run/type/streaming phase) and projected into the active Run's `assistant_run` block by `visibleTimelineItemsForRender` — the only render selector. There is no separate `streaming` timeline item type; `chatState.js` tracks only `streamingPhase` (incremented on each `tool_call_started`/`tool_call_result`) so deltas before and after a tool call stay in distinct phases. The final `assistant_output` event replaces the streamed draft in place and becomes the authoritative rendered assistant message.
- An assistant turn whose provider stream broke after visible output carries `interrupted: true` on the `assistant_output` message payload (and on the persisted history message). `chatTimeline.js` threads that flag onto the projected `assistant_output` child, and `ChatAssistantRun.svelte` renders an `.interrupted-notice` marker (i18n `chat.interrupted`) under the settled (non-streaming) content. No new event type — the flag rides the existing assistant-output payload.
- **Cancelled runs render the preserved partial plus a "Cancelled" label.** A user cancel after visible streamed output finalizes the partial backend-side (see `chat.md`): the settled `assistant_output` event arrives before `run_cancelled` and replaces the streamed draft in place through the normal merge machinery, so the text never vanishes; after reload the interrupted assistant message renders from history. The run header's meta (`runMetaParts`) always names the user action for a cancelled run — "Cancelled" (`chat.runStatus.cancelled`) followed by the runtime — instead of the duration-or-status fallback, and `ChatAssistantRun` suppresses the involuntary `.interrupted-notice` when the run's status is `cancelled` (the header label is the cancel marker). A run cancelled with zero visible output persists no assistant message; its `run_summary(status: "cancelled")` is the only trace, and `chatTimeline.js` renders an anchorless **cancelled** summary as a bare run row (header with status + timing, no children) instead of leaving a hole — anchorless non-cancelled summaries (page-slice orphans) still render nothing.
- `tool_call_delta` events are compressed into one retained streaming event per (run, tool call, streaming phase) in `streamingRunEvents` (`appendCompressedToolCallDeltaEvent`, merged by `tool_call_id` because sibling calls may interleave), so the live Run projection renders a `preparing` tool row — name plus running dot — from the first delta, the moment the model starts writing the call. While arguments stream, `chatState.js` feeds each fragment to an incremental partial-JSON scanner (`lib/toolArgumentPreview.js`, scanner state in a WeakMap keyed by the compressed event) that extracts *completed top-level string fields* and publishes them as `preview_arguments` on the compressed event; the projection carries them as `previewArguments` on the preparing row, and `toolArgumentSummary` uses them as stand-in arguments so the row is labeled (e.g. a write's path) long before the full arguments finish streaming. The scanner ignores nested keys and key-shaped text inside string values, skips non-string values, and caps captured values at 200 chars with an ellipsis. `tool_call_started` merges into the same row by tool-call id, clears `partialArgumentsText` and `previewArguments`, and supplies settled arguments/display; settled tool details must come from complete `tool_call_started`, `tool_call_result`, or persisted tool messages. Do not render partial argument JSON as final normal UI data, and preparing rows must not offer a cancel control (`isRowCancellable` excludes `streaming` rows — there is no dispatched call to cancel yet).
- Assistant output Markdown rendering is accessor-side only through `renderMarkdown(...)` and `renderMarkdownStreaming(...)` with raw HTML disabled and `breaks: true` (single newlines are intentional line breaks in chat output, not soft wraps). User text, reasoning bodies, tool details, and error text stay plain/pre-wrapped; user text must also wrap long unbroken tokens.
- Chat images open in `ImageLightbox` on click — both Markdown images in assistant output (`.msg-markdown`) and user attachment thumbnails (`.inline-attachment`). Because the Markdown is injected via `{@html}`, `ChatTimeline` attaches one delegated click listener to the messages container rather than per-image handlers; it opens the lightbox for plain left clicks on either image kind and ignores everything else. Modifier clicks (Ctrl/Cmd/Shift/Alt) fall through so the attachment `<a>` can still open the raw image in a new tab. - The composer remembers unsent input across navigation through `webui/src/lib/composerMemory.js` (localStorage-backed, an in-memory live copy plus a debounced persist, flushed on composer unmount and `beforeunload`; capped + reset helper for tests). Two scopes, both keyed by what ChatView derives from `displayedSessionKey()`: a **per-session draft** keyed by the full `<agent>::<session>` key (passed as `draftKey`) — loaded on mount/session-switch and persisted on every edit, so leaving a session (drawer peek, tab switch, reload) and returning keeps the half-typed text without it bleeding into another session; and a **per-agent send history** keyed by the agent part alone (`historyKey`, bare id or `agent@projekt`) so messages recall from any of that agent's sessions. Arrow-key recall is readline-style: Up enters history only when the caret is on the first logical line and the skill/command popup is closed, Down walks back toward and finally into the live draft. The live draft is the bottom slot; a per-slot working-copy buffer (`navWorkingCopies`) preserves edits to recalled entries for the duration of one navigation session, so an accidental Up never loses in-progress text (Down restores it). Sending records the typed text (trimmed, deduped, newest-first, capped) and clears that session's draft; attachments are not part of draft memory.

- The two-bar chat keeps the identity path byte-identical and only diverges once a **project agent** is the chat target. A project agent is not in `chatState.agents` (that holds identity agents only) — it is a scanned team member, so ChatView holds a parallel project path (selected team member + a local session map). Two contract traps drive every project-agent RPC. **Trap 1 — no server current session:** `session.create` sets make-current only for identity (`project_id is None`), so a project agent has no `current_session_id`; the accessor chooses the session locally — newest from `session.list` (`pickProjectAgentSessionId`), else `session.create` (no `make_current`) — held in a local `address → session_id` map, never on `chatState.agents`. **Trap 2 — bare id vs. full address for the same agent:** the full `agent@projekt` address goes to `chat.stream`/`chat.history`/`session.create`/`session.list`/`chat.retry_last_turn`; the **bare** id (`bareIdFromSessionAgentId`, strips `@projekt`) goes to `chat.queue_list`/`queue_remove`/`queue_update`/`cancel_tool_call`; `chat.cancel` keys on `run_id` only. A project-agent session state is keyed by the full address (`agent@projekt::<session>`); an identity session stays bare-keyed, so identity keys and payloads are unchanged. An empty team renders an empty second bar (not an error); `/new`/`/handoff` action-switches stay identity-only. The `/agent` **move** is the exception that crosses both worlds in every direction: it opens the **same** session id under the target, and for a project target pre-seeds that id into the local `projectAgentSessions[address]` map so `ensureProjectAgentSession` reuses it (instead of picking/creating), setting `lastLoadedProjectId`/`selectedProjectAgentId`/`initialProjectRestoreDone` up front so the dropdown-driven project effect cannot clobber the moved agent/session before the round-tripped `selectedProjectId` prop flushes. The active project agent is persisted (App's `selectedProjectAgentId`, a localStorage tri-state: `null` = nothing remembered, `''` = an identity agent was active alongside the project, or a team-member id) and **restored on reload** — only the **first** project-effect run after mount honors it (a team member is reopened, `''` keeps the identity bar in control, `null`/a vanished member falls through to the project default); every later run is a genuine dropdown switch and always jumps to the project default. ChatView reports each settled change up through `onProjectAgentSelected` so the mirror stays current.
