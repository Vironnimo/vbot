# WebUI Source Map

Per-file / per-component reference for `webui/`: what each Svelte view, `lib/` helper, and UI primitive owns. Read the entry for a component only when you are about to touch it — the always-needed orientation, transport contracts, conventions, and invariants live in `webui.md`.

- `webui/src/lib/api.js` is the transport boundary: RPC envelopes go to `/api/rpc`, attachments go through `/api/upload` and `/api/attachments/{id}`, speech audio uses `/api/speech/*`, Run output uses SSE, app-wide lifecycle uses `/ws`, and logs use `/ws/logs`. `subscribeServerEvents` also stamps the `/ws` connect with this window's presence identity — a per-tab `connection_id` plus `accessor` query param (defaults resolved from `lib/clientIdentity.js`, overridable for tests) — so the server can register it in the client roster.
- `webui/src/lib/clientIdentity.js` owns the per-window presence identity: `resolveClientConnectionId()` mints a per-tab id (sessionStorage-backed with a module-cache fallback — **never** localStorage, which is shared across a browser's tabs and would collapse N tabs into one row) and `resolveAccessorType()` returns `browser`/`desktop`. The General settings panel matches the same `connection_id` to mark "this window".
- `webui/src/App.svelte` owns the Toasted two-pane shell, navigation, browser-history integration (with pure state helpers in `lib/navigationHistory.js`), selected-Agent state, the chat project context (the `project.list` list + persisted `selectedProjectId` **and** `selectedProjectAgentId`, both mirrored to `localStorage` like the selected agent; empty `selectedProjectId` = Personal/identity path), app-level WebSocket subscription, bounded Run server-event queueing, Debug-tab gating, app toasts, provider-auth completion forwarding, Desktop capability loading, and a one-time `settings.get` appearance bootstrap on mount that seeds the `appearancePrefs` store (chat width) and i18n language and passes `chatWidth` down to ChatView. `handleServerEvent` is the single `/ws` funnel; alongside the `app_error`/`provider_auth_completed`/`connection_ready`/run-lifecycle branches it routes the generic `resource_changed` event (the reload-on-change channel) through `lib/resourceInvalidation.js`. There is **no** separate agent-CRUD branch — agent CRUD arrives as `resource_changed(kind:"agents")` and triggers the same `agent.list` re-fetch + `refreshAgents` the old `agent.created/updated/deleted` branch did. App holds per-kind refresh tokens it bumps and passes down: `modelsRefreshToken` (bumped by `kind` `models` **and** `providers`, since both change which models are selectable) → AgentsView, ProjectsView, SettingsView; `sessionsRefreshToken` (bumped by `kind` `sessions`) → ChatView → SessionListDrawer; `clientsRefreshToken` (bumped by `kind` `clients`) → SettingsView → SettingsGeneralPanel; `channelsRefreshToken` (bumped by `kind` `channels`) → SettingsChannelsPanel; and `debugTracesRefreshToken` (bumped by `kind` `debug_traces`) → DebugView. The `queue` kind is **scope-routed**, not a token: App forwards the affected session's scope (a fresh `{agentId, sessionId}` object) as `queueInvalidation` to ChatView, which re-syncs that one held session's queue live instead of waiting for the next terminal event.
- **Projects-tab selection seam.** `App.svelte` persists a `managedProjectId` separately from Chat's `selectedProjectId`: a non-empty Chat project seeds/updates the management mirror, while ProjectsView reports its own list choices back without changing Chat. On each ProjectsView mount/list load, a still-valid preferred id opens first; otherwise the first listed Project opens, and an empty list clears the mirror. This state belongs in App because tab navigation unmounts ProjectsView.
- `webui/src/lib/appearancePrefs.svelte.js` is a tiny app-wide reactive singleton (`appearancePrefs.chatWidth`, default `comfortable`, with a coercing `setChatWidth`) for pure display preferences from the appearance section. Chat width has no runtime reload hook — it only drives the `data-chat-width` attribute — so the store is the bridge between App (seeds + passes the prop) and the Appearance panel (updates it on save so the open chat reflows live).
- `webui/src/lib/connectionState.js` owns persistent app WebSocket state: `connected` / `reconnecting` / `disconnected`, reconnect backoff, and `lastSequence` replay handoff.
- `webui/src/lib/resourceInvalidation.js` is the pure, framework-free half of the reload-on-change channel: `tokenKeysForKind(kind)` maps a `resource_changed` kind to the refresh-token group(s) it invalidates (`models`/`providers` → `models`, plus dedicated `agents`, `sessions`, `clients`, `channels`, and `debug_traces` groups; `queue` has **no** token group — it carries a session scope the watcher must match, so App routes it directly), and `shouldApplyReloadNow(surface, signals)` / `isSurfaceBusy(signals)` decide whether a reload may swap visible data now (`SURFACE_DISPLAY` always; `SURFACE_FORM` only when not `dropdownOpen`/`focused`/`savePending`). App holds the reactive tokens; each consuming view holds its own editing signals and does the fetch — a model surface fetches the fresh catalog in the background on every token bump but **defers the visible option swap** while its picker is open (or, for the Specialized/Providers forms, while a save/credential edit is in flight), applying the held swap once idle so an open selection or in-progress edit is never yanked.
- `ChatView.svelte`, `chatState.js`, `chatTimeline.js`, `ChatTimeline.svelte`, `ChatComposer.svelte`, `QueuedMessages.svelte`, and `SessionListDrawer.svelte` own the Chat surface, timeline aggregation, composer input, server-backed queue projection, and local Session overrides. The Session drawer loads on Agent change, reloads through `resource_changed(kind=sessions)` and successful local mutations, and has no permanent Refresh action; a failed list load exposes a contextual Retry. The composer's three trigger popups are `SkillAutocomplete.svelte` (`/` commands+skills, `$` skills) and `FileAutocomplete.svelte` (`@` file mentions — fed per picker open by ChatView's `files.list` callback, fuzzy-ranked by `lib/fileMentions.js`, which also owns the submit-time token extraction/verification that produces the `file_mentions` send param). `chatState.js` is the public helper surface and owns Session/Run mutation; pure history/live timeline projection belongs in `chatTimeline.js`. The two-bar project chat also lives here: an identity-agent bar (always) plus, when a project is chosen in the dropdown, a second team bar projected from `project.show`'s scan; `chatState.js` owns the project-address helpers (`formatAgentAddress`/`resolveAgentAddressing`/`pickProjectAgentSessionId`) and `components/chat/ProjectScanBanner.svelte` is the non-blocking unclean-scan banner.
- `AgentsView.svelte`, `agentForm.js`, and `modelSelection.js` own Agent CRUD form state, sparse edit payloads, backend-backed model/connection selection, tool/skill access controls, custom prompt toggle, workspace editing, and memory-mode handling. The thinking-effort dropdown in `AgentEditor.svelte` is gated by the selected model's reasoning facts from the `model.list` payload: it is **disabled** when `capabilities.reasoning.supported === false` (with an explanatory hint), and its options are narrowed to the model's published ladder — when `reasoning.levels` is non-empty the dropdown shows only the default, `none`, and those levels. A model with no ladder (unknown/custom, or a reasoning model whose ladder is not projected) keeps the full effort list because the adapter applies a provider-specific floor the UI cannot see. The `model.list` payload carries `capabilities.reasoning.{supported,control,levels}` for this gating.
- `SettingsView.svelte`, `settingsView.js`, `channelSettings.js`, `taskModelSettings.js`, `desktopBridge.js`, and `wakewordSettings.js` own the Settings surface, settings update payloads, provider OAuth UI state, channel forms, specialized model bindings, Desktop bridge calls, and Voice panel state. `SettingsView` renders **one scrolling document**: every section panel is always mounted, wrapped in a `[data-settings-section]` card with its own header, stacked under mono-caps group labels (Connect / Models / Behavior / System). The left column is the index — a live search input (DOM-based filter: rows/sections get the `hidden` attribute, match count shown, non-matching index entries dim; a `MutationObserver` re-applies an active filter after panel re-renders) above a grouped table of contents (click scrolls via `scrollIntoView`, a rAF-throttled scrollspy highlights the current section, bottom-of-scroll counts as the last section). Deep links (`targetPanelId`/`targetPanelRequestId`) scroll to the section instead of switching panels. Channels and Extensions both load when their always-mounted panels initialize and reload after their own mutations; neither has a permanent generic Refresh action, while a failed list load exposes a contextual Retry. Channel mutations also reload other windows through `resource_changed(kind:"channels")`; SettingsChannelsPanel defers that external reload while its form or an action is active. The **Reflection** panel (`SettingsReflectionPanel.svelte`, section id `reflection`, ordered after Sub-Agents) edits the `settings.reflection` section (enable toggle + the two cadence intervals) with the Debug panel's pattern: seeded once from the settings prop, 800ms debounced auto-save plus manual Save, partial-merge `settings.update` writes; changes apply live (no restart — the backend reads the section at run end, see `automation.md`). The **Extensions** panel (`SettingsExtensionsPanel.svelte`) keeps **Reload extensions** as a distinct explicit operation that rebuilds the extension layer from disk, then re-lists it. It renders a schema-driven **form** for an extension whose `extensions.list` entry carries a `settings_schema` (text/number/toggle inputs saved together as one `settings.update` config write via `buildExtensionsUpdatePayload`; write-only secret inputs saved/cleared per-field via `extensions.set_secret` then a `loadExtensions()` refresh — never mixed into `settings.update`), and keeps the raw-JSON `config` editor as the fallback for schema-less extensions. The pure form helpers (`normalizeSchemaFields`, `buildSchemaFormState`, `buildSchemaConfigFromForm` — number parsing, empty-omission, toggle-explicitness, secret exclusion — and `hasSettingsSchema`) live in `settingsView.js` and are Vitest-covered. This panel is the **single** place the derived **waiting state** appears (design decision — the tool pickers just omit a not-ready tool): when an extension's `extensions.list` `ready_state === 'waiting'` it shows "On, waiting for configuration" and, via `describeExtensionWaiting(extension, t)`, names the unset secret fields ("Waiting for: <labels>", the schema secret fields where `set === false`). `applyExtensionsPanelList` carries `readyState` and normalizes `capabilities.tools` from the `{name, ready}` shape; `summarizeExtensionCapabilities` still lists tool names only.
- `StatisticsView.svelte` + the pure `statisticsView.js` own the Statistics tab's six sub-views (Overview / Usage / Runs & errors / Tools / Skills / **Limits**). Overview..Skills render the single `statistics.report` loaded on mount; project agents arrive in the report keyed as `agent@projekt`, so every agent cell renders through `agentDisplay` (parses the address) as the bare name plus a small project badge — identity agents (no `@`) render unchanged, no badge. This is read-only display only (no project filter/grouping in v1). The Usage sub-view renders the report's cache aggregation (see `statistics.md`): a "Cache hit rate" card and per-provider/per-model "Cache hit" columns via `cacheHitRate(record)` (`cache_read_tokens / cache_input_tokens`, `null` → "—" for records without cache data), a green cache-hit-% polyline in the "Tokens per period" sparkline (absolute 0–100% scale via `sparklinePoints(..., { max: 1 })`, with a legend), a "Sessions with lowest cache hit rate" table, and a "Suspected cache breaks (derived)" block (summary line + incident table) labelled as a best-effort heuristic. The **Skills** sub-view renders `report.skills` (see `statistics.md`): summary cards (total / used / never used), the per-skill table (name, origin chips via `parseOrigin` + localized labels, offered/activated sessions, `formatUsageRate` — whole-percent, em dash for `null` — first/last activated) with a highlight + "Never activated" badge on zero-activation rows, and a panel-wide per-agent activations breakdown via `rollupSkillActivationsByAgent` through the shared `agentCountTable` pattern. The **Limits** sub-view is independent — it lazily calls `provider.usage` on first open (own loading/error state, manual refresh) and renders one card per provider snapshot with each window as a severity-colored progress bar (`clampUsagePercent`/`usageSeverity`) and a `formatResetAt` relative+absolute reset time. Error/empty snapshots show a clean "unavailable" row; no connections → an empty-state message. It is live provider state, not part of the read-only statistics aggregation (see `statistics.md`, `providers.md` → Provider Usage Probe).
- `SystemPromptView.svelte` owns the System Prompt **block list** and prompt-scope UX; backend prompt semantics live in `.vorch/domain-maps/prompts.md`. Blocks come from `prompt.list` in layout order and are keyed by their stable `id` (never an array index, so autosave timers and DnD/keyboard-reorder identity survive a reorder). The list is **sortable** — native HTML5 drag-and-drop on a per-row handle **and** keyboard reorder (ArrowUp/ArrowDown on the focused handle, with an aria-live announcement and focus that follows the moving row) — and every reorder/toggle persists immediately via `prompt.set_layout`. Editable text blocks render a textarea with 800ms debounced autosave (`prompt.update`) plus a Reset button (`prompt.reset`); **data blocks** (`kind === 'data'`) are read-only with an expandable preview of their current text. Each row shows an **owner hint** — a plain sentence stating the render condition (owner = gate 2 of the prompt filter), e.g. "Always included.", "Included only while the {name} tool is active.", "Included only while the memory tool is on." (`ownerHint()` maps the internal owner token to `systemPrompt.blockList.ownerHint.*`) — `custom`/`auto` badges, and in an agent scope an `inherited`/`modified` **inheritance badge** (an inherited block shows greyed default text; editing it creates the override). Custom `user:` blocks can be **created** (slug prompt, client-side slug pre-check mirroring the backend agent-id rule) and **removed**; a "Reset order & visibility" button calls `prompt.reset_layout`. Both pickers in this view are the shared `Dropdown` primitive (no raw `<select>`): the header **scope** picker (Default + enabled identity Agent scopes) and the **preview agent** picker. The preview agent picker combines identity agents (`agent.list`, bare-id values) with project agents (lazily scanned via `project.list` → `project.show` on mount, cached) addressed as `agent@projekt`, built by the shared `lib/agentTargetOptions.js` helper; the selected option value is passed straight to `prompt.preview` as `agent_id` (the backend resolves a project-qualified address). Project agents appear only in the Default-scope preview — an Agent prompt scope is identity-only. The preview pane has Copy but no manual Refresh: it loads on mount/preview-target change and refreshes after successful block text, layout, reset, create, or remove mutations through a short debounce with stale-response protection. Its token chip renders `~{prompt} prompt + ~{tools} tools = ~{total} tokens` when tool definitions are present (from `prompt.preview`'s `tokens`/`tool_tokens`; tooltip explains `tool_count`), or the plain `~{count} tokens` for a tool-less agent.
- `LogsView.svelte` and `logsView.js` own read-only log file selection, local level/search/sort state, and dedicated log-stream reconnect behavior. The catalog and selected file load on mount; append/reset events update entries, catalog events update the file dropdown without switching a still-valid selected file, and reconnect first reloads the catalog before re-reading/subscribing. The header has no generic Refresh action; catalog/read failures expose contextual Retry actions. Backend parsing and socket contracts live in `.vorch/domain-maps/logs.md`.
- `CronView.svelte`, `cronView.js`, and `styles/cron.css` own the Cron tab as a **master-detail** view mirroring AgentsView/ProjectsView (list pane left + fluid detail, no modal — `CronView` uses `Modal` nowhere). The **list pane** shows every visible job (friendly agent label + mono `schedule_description` + `StatusChip`) with the shared plus-icon + “Add” action in its header; the first job auto-selects. “Add” switches the detail to a blank create form (Save + Cancel; Cancel returns to the prior selection). The **detail pane** is the directly-editable job form (Agent `Dropdown`, prompt textarea, Cron/Once radio, cron expression OR run-at, timezone, session id) with the enable/disable `Toggle` + Delete danger button in its header, read-only Status/Last-fired/Next-fire info rows, an inline validation/save error, and a sticky-footer Save; **explicit-save only** (entity edit form, never autosaves). A **schedule-preset** `Dropdown` (`buildCronPresetOptions`/`cronPresetExpression`/`cronPresetForExpression` in `cronView.js`, keys under `cron.presets.*`) sits above the cron expression field for the Cron type: picking a preset fills its expression (field stays editable, live `describeCronExpression` preview keeps working), hand-editing re-derives the selection (drift → Custom), and opening a job derives the preset by exact expression match. Success/status and load-error feedback go to the **app-level toast** (`onToast` prop threaded from App, error toasts sticky by default); only form validation/save errors stay inline. The agent dropdown (built via the shared `lib/agentTargetOptions.js` helper, also used by System Prompt) combines identity agents (`agent.list`, bare-id values) with project agents (lazily scanned from `project.list` → `project.show` when the detail form first renders, cached) whose option value is the full `agent@projekt` address — so saving sends that address straight through as the `cron.create`/`cron.update` `agent_id` param. An existing job pre-fills from the server-formatted `target` field of `cron.list` (not the bare `agent_id`), so a project job re-saves its address. Scheduler behavior lives in `.vorch/domain-maps/automation.md`.
- `webui/src/lib/agentAddress.js` is the one client-side `agent@projekt` parse/format seam (`formatAgentAddress`/`parseAgentAddress`), mirroring `core/projects/address.py`; Cron, Statistics, and the `agentTargetOptions.js` builder consume it. (`chatState.js` keeps its own Phase-2 `formatAgentAddress` deliberately, in lockstep via the shared `@` separator.)
- `webui/src/lib/agentTargetOptions.js` is the one builder for "agent target" dropdowns — it turns `agent.list` plus lazily-scanned project teams (`project.list` → `project.show` → `projectTeamEntry`/`projectIdsFromList`) into a flat option list mixing identity agents (bare-id values) with project agents (`agent@projekt` values), and `buildAgentTargetDropdownOptions` adds disabled "Identity agents"/"Project agents" group headers only when project agents exist (identity-only stays header-free). Cron and System Prompt both feed it into a `Dropdown`; cron re-exports it under its historical `buildCronAgent*` names for back-compat.
- `ProjectsView.svelte` (flat), the pure `projectsView.js`, and `styles/projects.css` own the Projects tab as a **master-detail** view mirroring AgentsView (see `webui/state-flows.md` → Projects tab / Team rows for the runtime contract). The **list pane** shows every project (display name + cwd, selected state) with the shared plus-icon + “Add” action in its header; the selected Project's detail header has the single explicit “Rescan repository” action, which reruns `project.show` once and refreshes the shared Team/report/Skills scan projection. Add opens a modal collecting cwd + optional display name (blank → backend derives the name) plus the **source-format** choice: on a debounced cwd blur it probes `project.detect` (`detectProject`) and, via the pure `normalizeDetectResult`/`presentFormats`/`shouldSuggestClaudeMd` helpers, renders one of three states — both formats present → a radio choice (pick-list cards with per-format `{agents} agents · {skills} skills`, default `opencode`), exactly one present → a quiet "Detected: <format>" line, none → nothing (the server auto-detects). Only an actual radio pick is sent as `source_format` in the `buildAddProjectPayload` payload; otherwise the field is omitted and the server auto-detects. When the repo has a `CLAUDE.md` but no `AGENTS.md`, a `Toggle` offers loading `CLAUDE.md` as a project file (accepted → `auto_load: ['CLAUDE.md']`, backend seeds `AGENTS.md` in front). The **detail pane** for the selected project (`project.show` scan loaded on select) is five ordered sections: **Project settings** (display name `TextField`; **source format** `Dropdown` — GLOSSARY → Source Format; switching flows through the same `buildManageProjectPayload`/`project.set` path and the backend re-derives team + skills; **default agent** `Dropdown` via `buildDefaultAgentOptions`; **default model** `SearchableDropdown` + `modelSelection.js`; **default temperature** + **default thinking effort** — the three defaults carry the shared `inherit.*` inherit-state labels seeded from the global `defaults.agent` fetched once via `settings.get`, absent-case labels on failure; explicit-save with an 800ms debounced auto-save via `buildManageProjectPayload`'s sparse `project.set` diff plus a Save button, App must pass `onToast`), **Auto-load files** (editable list + add), **Team** (see below; the `ProjectScanBanner`-style report renders at the top when unclean), **Tools** (the `Toggle` whitelist of `tool.list` minus `memory`/`skill_manage`, readiness via the shared `ToolReadinessNotice`, reset-to-`default_project_tools` button), **Skills** (three `Toggle` sections — project auto-on/off-exception, bundled + global opt-in; a shadowed same-name bundled/global skill is dropped). **Team rows** are expandable: each scanned member (`projectTeam` carries `agent_id`/`display_name`/`description`/`denied_tools`/`source_*`/`overrides`/`effective`) shows effective `model`/`temperature`/`thinking_effort` with a provenance badge (`override`/`agent file (repo)`/`project default`/`global default`; null → "not configured"/"provider default", no badge), an **override control per field** (model select, comma-tolerant temperature input, effort select gated by the member's effective model via `agentForm.js` helpers), the denied-tools lines, and the source line. Overrides are **immediate actions**: Set → `setOverride`/`project.set_override`, Clear (only when overridden) → `clearOverride`/`project.clear_override`, each refreshing team/report from the returned scan with success/sticky-error toasts (model override also settable command-only via `/model`). `projectsView.js` holds the add/manage/default-agent-option builders, the source-format vocabulary (`PROJECT_SOURCE_FORMATS`) and detect-result helpers (`normalizeDetectResult`/`presentFormats`/`shouldSuggestClaudeMd`), the tool/skill toggle-list builders, `projectTeam` (with `normalizeOverrides`/`normalizeEffective`, `memberFieldIsOverridden`, `seedTeamOverrideDraft`, `normalizeOverrideTemperature`), `normalizeScanSkills`, the scan-report normalization (clean/empty = normal bare-project case), and the re-point payload. The thin `project.*` wrappers (`addProject`/`listProjects`/`showProject`/`setProject`/`removeProject`/`setOverride`/`clearOverride`/`detectProject`) live in `api.js`; backend behavior is in `.vorch/domain-maps/projects.md`. `ChatView` also imports `projectTeam` (uses only `agent_id`/`display_name`) — do not drop those fields.
- `markdown.js`, `toastState.js`, `audioRecorder.js`, `sessionListView.js`, `clientCaches.js`, and the other small `lib/` helpers should stay pure where practical and are covered by focused Vitest tests under matching `__tests__/` directories.
- **UI primitives (`components/ui/`)** group the shared design-system controls, distinct from the feature components in `chat/`, `agents/`, `settings/`, `debug/`. Each primitive owns the single canonical CSS class per variant (styling source stays the global classes in `styles/app.css`; the component consumes them and hides the markup) and follows the `Dropdown.svelte` convention (that exemplar and `SearchableDropdown.svelte` live flat in `components/`, **not** in `ui/` — see the shared-dropdowns bullet below) — Svelte 5 `$props()`, callback props (`onClick`/`onChange`/…), no event dispatchers, already-translated content in via `children`/props. `Button.svelte` covers `variant` (`primary`/`secondary`/`tertiary`/`danger`) + `icon` footprint, replacing the ~80 hand-built `btn-*` call sites and collapsing the duplicate class names (`btn-new`/`btn-outline`/`modal-btn-*`/`send-btn`/`icon-btn`/`tl-btn`/`pane-action`) to one per variant. `Modal.svelte` owns the dialog chrome (overlay, overlay-click/Escape close, `role="dialog"`/`aria-modal`, header with title + close button, focus-on-open) behind `title`/`labelledById`/`onClose`/`closeDisabled` props plus `body` + optional shell-wrapped `footer` snippets; the duplicate modals (`AgentCreateModal`, `ProviderConnectModal`, the Projects add/re-point modals) supply only their body/footer. `Toggle.svelte` renders the `role="switch"` button + knob in two sizes (`lg`/`sm`) behind `checked`/`onChange`/`size`/`disabled`/`ariaLabel`, replacing the hand-built `.toggle`/`.tl-toggle` switches — including the Desktop Voice panel's former `voice-toggle` checkbox-slider (the raw-checkbox guard now has no allowlist); only the `stats-toggle` segmented period selector remains a distinct control. `StatusChip.svelte` renders the semantic pill (`variant`: `success`/`warn`/`info`/`error`/`neutral` + `children`), collapsing the `chip-green`/`-amber`/`-orange`/`-red` color aliases into the `chip <variant>` semantic names; the chip-classifying helpers (`channelEnabledChipVariant`, `channelRunningChipVariant`, `extensionStatusChipVariant`, and CronView's `statusChipVariant`) now return variant names. `Badge.svelte` is the metadata-tag counterpart to `StatusChip` — a small pill (`variant`: `neutral`/`info`/`success`/`warn`/`error` + `children`, default `neutral`; canonical `badge badge--<variant>` classes) folding the former bespoke pills (`sp-badge`, `session-row__badge`, `stats-badge`/`stats-skill-badge`/`stats-origin`, `logs-view__stream-chip`, `debug-view__status-chip`, `s-ext-version`) into one primitive; an inline icon rides the `children` snippet (SVGs keep explicit `width`/`height`) and a `use:tooltip` hint rides a wrapping `tooltip-anchor` span since Svelte actions can't apply to a component. `Banner.svelte` owns persistent in-flow feedback (`variant`: `neutral`/`info`/`success`/`warn`/`error` + already-translated `children`; canonical `banner banner--<variant>` classes), including loading feedback, form and RPC errors, warnings, and non-blocking notices; feature classes may adapt placement but never recreate the semantic variants, while known content absence belongs to `EmptyState` and transient app-wide feedback stays in `ToastStack`. `EmptyState.svelte` owns known content absence (`title`/`description`, optional `icon`/`actions`, `density`: `default`/`compact`, optional `fill`; canonical `empty-state*` classes) across Chat, Agents, Projects, Cron, Sessions, Logs, Debug, Statistics, Settings, System Prompt, and Onboarding; it must not represent loading, failure, or warning states. `TabList.svelte` owns local content-view switching across Statistics and Debug: already-translated `{ id, label }` items, caller-owned `value`/`onChange`, canonical `tab-list*` classes, generated tab/panel ids, complete ARIA tab semantics, and automatic Arrow Left/Right/Home/End activation; `appearance` selects `underline` or `segmented`, and `density="compact"` selects the smaller Mono footprint. Period/filter selectors and Chat agent navigation are deliberately outside this primitive. `FormField.svelte` owns ordinary labeled-control anatomy across Agents, Projects, provider connection, Channels, Extensions, and Specialized Models: translated label, required marker, help/error placement, full-grid span, and generated label/help/error ids exposed to the caller-rendered control through its snippet contract; value and validation state remain caller-owned, and optional field actions render after feedback. `TextField.svelte` covers the editable input (`variant` default/modal → `s-input`/`modal-input`), the `invalid` state (`s-input--invalid` red border, replacing the agents-only `agents-view__invalid`), and the read-only `s-value-box` (`readonly`); it uses the `value`/`onInput(next, event)` callback pattern (no `bind:`), so the migrated call sites pass a setter callback instead of two-way binding. `TextArea.svelte` owns ordinary multi-line form fields across Cron, System Prompt, Extensions, Skills, and Specialized Models with the same `value`/`onInput(next, event)` contract; `variant` selects bordered `default` or embedded `inset`, while `code` and `invalid` own JSON whitespace/height and validation styling. Chat Composer and queued-message editing are the only raw-textarea exceptions because they own specialized resize/send/inline-edit behavior. `ConfirmDialog.svelte` builds on `Modal` + `Button` for destructive/irreversible confirmations (`title`/`body`/`confirmLabel`/`cancelLabel`/`danger`/`onConfirm`/`onCancel`; danger confirm by default, overlay/Escape/× route to cancel), replacing every native `window.confirm` across the WebUI — callers own the open state and conditionally render it. `InfoHint.svelte` is the explanatory tier of the two-tier hint system (see the hint-system bullet below): a small "?" dot whose portaled `info-popover` opens on hover/focus, pins on click/tap (touch), and closes on Escape/outside-click; callers pass already-translated `text` (blank lines split paragraphs) and optionally `ariaLabel` (defaults to `common.moreInfo`). A growing Vitest guard (`lib/__tests__/uiPrimitives.guard.test.js`) scans all `*.svelte` and fails if a raw element reintroduces a primitive's class outside its `ui/` owner (including `badge`/`badge--*`, `banner`/`banner--*`, `empty-state*`, `tab-list*`, `text-area*`, and `form-field*` outside their owners, plus retired-alias scans banning the former bespoke pill, feedback, empty-state, content-tab, multi-line field, and form-shell class names so they cannot return), if a native `confirm(` call reappears in any component (use `ConfirmDialog` instead), **and** if a raw lowercase element carries a native `title=` attribute (use the shared tooltip action or `InfoHint` — component `title` props like Modal's are unaffected).
- **Hint system (`lib/tooltip.js` + `components/ui/InfoHint.svelte`)** — two tiers, one rule: native `title` attributes are banned (guard-enforced). Tier 1, the **quick tooltip**, is the Svelte action `use:tooltip={text}` from `lib/tooltip.js` (also exposed as the `tooltip` prop on `Button`/`CopyButton`): a single shared `#app-tooltip` element portaled to `<body>`, styled per DESIGN.md's tooltip token, multi-line via `pre-line` (the chat-header token badge renders `tokenUsageTooltip.js`'s line-structured text through it), shown after `TOOLTIP_SHOW_DELAY_MS` (150ms) on hover/focus, hidden on leave/blur/pointerdown/Escape/scroll, size-capped so oversized content clips. Empty text disables it, so conditional hints pass `''`. It is presentational only — icon-only controls keep their own `aria-label`; while visible it links to the anchor via `aria-describedby`. Browsers fire no pointer events on disabled controls, so a "why is this disabled" hint goes on a wrapping `<span class="tooltip-anchor" use:tooltip={…}>` (ChatHeader's blocked New-session, AgentEditor's last-agent Delete, the Providers env-locked Remove). Tier 2, **`InfoHint`**, is the "?" dot for concept explanations that would otherwise clutter the UI as permanent grey text; permanently visible inline hints remain only for must-see state (inherit values, "model does not support reasoning") and wizard-flow instructions (ProviderConnectModal). `positionFloating` in `lib/tooltip.js` is the shared anchored-positioning helper for both tiers. (**not** in `components/ui/` — this trips agents up repeatedly): `Dropdown.svelte` is the **simple** picker (absolute list, no filter — short option sets) and `SearchableDropdown.svelte` is the **searchable** one (fixed/portaled panel with a filter-input header — long lists like models). Both share the callback-prop contract (`value` in, `onValueChange(value, option)` out; `options` as strings or `{ value, label, disabled, secondaryLabel[, searchText] }`, plus `id`/`placeholder`/`disabled`/`ariaLabel`/`triggerClass`) and position through `lib/dropdownPanel.js` (`computePanelPosition` + `portal`). A model picker is `SearchableDropdown` fed by `modelSelection.js` (`buildModelSelectOptions`/`selectModelValue`), reused 1:1 by Agents, Cron, and Projects — don't hand-roll one. Design tokens for both live in `.vorch/DESIGN.md` → Dropdowns.
