# WebUI Source Map

Per-file / per-component reference for `webui/`: what each Svelte view, `lib/` helper, and UI primitive owns. Read the entry for a component only when you are about to touch it — the always-needed orientation, transport contracts, conventions, and invariants live in `webui.md`.

- `webui/src/lib/api.js` is the transport boundary: RPC envelopes go to `/api/rpc`, attachments go through `/api/upload` and `/api/attachments/{id}`, speech audio uses `/api/speech/*`, Run output uses SSE, app-wide lifecycle uses `/ws`, and logs use `/ws/logs`. `subscribeServerEvents` also stamps the `/ws` connect with this window's presence identity — a per-tab `connection_id` plus `accessor` query param (defaults resolved from `lib/clientIdentity.js`, overridable for tests) — so the server can register it in the client roster.
- `webui/src/lib/clientIdentity.js` owns the per-window presence identity: `resolveClientConnectionId()` mints a per-tab id (sessionStorage-backed with a module-cache fallback — **never** localStorage, which is shared across a browser's tabs and would collapse N tabs into one row) and `resolveAccessorType()` returns `browser`/`desktop`. The General settings panel matches the same `connection_id` to mark "this window".
- `webui/src/App.svelte` owns the Toasted two-pane shell, navigation, browser-history integration (with pure state helpers in `lib/navigationHistory.js`), selected-Agent state, the chat project context (the `project.list` list + persisted `selectedProjectId` **and** `selectedProjectAgentId`, both mirrored to `localStorage` like the selected agent; empty `selectedProjectId` = Personal/identity path), app-level WebSocket subscription, bounded Run server-event queueing, Debug-tab gating, app toasts, provider-auth completion forwarding, Desktop capability loading, and a one-time `settings.get` appearance bootstrap on mount that seeds the `appearancePrefs` store (chat width) and i18n language and passes `chatWidth` down to ChatView. `handleServerEvent` is the single `/ws` funnel; alongside the `app_error`/`provider_auth_completed`/`connection_ready`/run-lifecycle branches it routes the generic `resource_changed` event (the reload-on-change channel) through `lib/resourceInvalidation.js`. There is **no** separate agent-CRUD branch — agent CRUD arrives as `resource_changed(kind:"agents")` and triggers the same `agent.list` re-fetch + `refreshAgents` the old `agent.created/updated/deleted` branch did. App holds per-kind refresh tokens it bumps and passes down: `modelsRefreshToken` (bumped by `kind` `models` **and** `providers`, since both change which models are selectable) → AgentsView, ProjectsView, SettingsView; `sessionsRefreshToken` (bumped by `kind` `sessions`) → ChatView → SessionListDrawer (the session list refreshes; the viewed conversation never switches — "stay put"); `clientsRefreshToken` (bumped by `kind` `clients`) → SettingsView → SettingsGeneralPanel (the "Connected clients" presence roster reloads when a window connects/disconnects). The `queue` kind is **scope-routed**, not a token: App forwards the affected session's scope (a fresh `{agentId, sessionId}` object) as `queueInvalidation` to ChatView, which re-syncs that one held session's queue live instead of waiting for the next terminal event.
- `webui/src/lib/appearancePrefs.svelte.js` is a tiny app-wide reactive singleton (`appearancePrefs.chatWidth`, default `comfortable`, with a coercing `setChatWidth`) for pure display preferences from the appearance section. Chat width has no runtime reload hook — it only drives the `data-chat-width` attribute — so the store is the bridge between App (seeds + passes the prop) and the Appearance panel (updates it on save so the open chat reflows live).
- `webui/src/lib/connectionState.js` owns persistent app WebSocket state: `connected` / `reconnecting` / `disconnected`, reconnect backoff, and `lastSequence` replay handoff.
- `webui/src/lib/resourceInvalidation.js` is the pure, framework-free half of the reload-on-change channel: `tokenKeysForKind(kind)` maps a `resource_changed` kind to the refresh-token group(s) it invalidates (`models`/`providers` → the `models` group, `agents` → the `agents` group, `sessions` → the `sessions` group, `clients` → the `clients` group; `queue` has **no** token group — it carries a session scope the watcher must match, so App routes it directly), and `shouldApplyReloadNow(surface, signals)` / `isSurfaceBusy(signals)` decide whether a reload may swap visible data now (`SURFACE_DISPLAY` always; `SURFACE_FORM` only when not `dropdownOpen`/`focused`/`savePending`). App holds the reactive tokens; each consuming view holds its own editing signals and does the fetch — a model surface fetches the fresh catalog in the background on every token bump but **defers the visible option swap** while its picker is open (or, for the Specialized/Providers forms, while a save/credential edit is in flight), applying the held swap once idle so an open selection or in-progress edit is never yanked.
- `ChatView.svelte`, `chatState.js`, `chatTimeline.js`, `ChatTimeline.svelte`, `ChatComposer.svelte`, `QueuedMessages.svelte`, and `SessionListDrawer.svelte` own the Chat surface, timeline aggregation, composer input, server-backed queue projection, and local Session overrides. `chatState.js` is the public helper surface and owns Session/Run mutation; pure history/live timeline projection belongs in `chatTimeline.js`. The two-bar project chat also lives here: an identity-agent bar (always) plus, when a project is chosen in the dropdown, a second team bar projected from `project.show`'s scan; `chatState.js` owns the project-address helpers (`formatAgentAddress`/`resolveAgentAddressing`/`pickProjectAgentSessionId`) and `components/chat/ProjectScanBanner.svelte` is the non-blocking unclean-scan banner.
- `AgentsView.svelte`, `agentForm.js`, and `modelSelection.js` own Agent CRUD form state, sparse edit payloads, backend-backed model/connection selection, tool/skill access controls, custom prompt toggle, workspace editing, and memory-mode handling. The thinking-effort dropdown in `AgentEditor.svelte` is gated by the selected model's reasoning facts from the `model.list` payload: it is **disabled** when `capabilities.reasoning.supported === false` (with an explanatory hint), and its options are narrowed to the model's published ladder — when `reasoning.levels` is non-empty the dropdown shows only the default, `none`, and those levels. A model with no ladder (unknown/custom, or a reasoning model whose ladder is not projected) keeps the full effort list because the adapter applies a provider-specific floor the UI cannot see. The `model.list` payload carries `capabilities.reasoning.{supported,control,levels}` for this gating.
- `SettingsView.svelte`, `settingsView.js`, `channelSettings.js`, `taskModelSettings.js`, `desktopBridge.js`, and `wakewordSettings.js` own Settings panel state, settings update payloads, provider OAuth UI state, channel forms, specialized model bindings, Desktop bridge calls, and Voice panel state. The **Extensions** panel (`SettingsExtensionsPanel.svelte`) renders a schema-driven **form** for an extension whose `extensions.list` entry carries a `settings_schema` (text/number/toggle inputs saved together as one `settings.update` config write via `buildExtensionsUpdatePayload`; write-only secret inputs saved/cleared per-field via `extensions.set_secret` then a `loadExtensions()` refresh — never mixed into `settings.update`), and keeps the raw-JSON `config` editor as the fallback for schema-less extensions. The pure form helpers (`normalizeSchemaFields`, `buildSchemaFormState`, `buildSchemaConfigFromForm` — number parsing, empty-omission, toggle-explicitness, secret exclusion — and `hasSettingsSchema`) live in `settingsView.js` and are Vitest-covered. This panel is the **single** place the derived **waiting state** appears (design decision — the tool pickers just omit a not-ready tool): when an extension's `extensions.list` `ready_state === 'waiting'` it shows "On, waiting for configuration" and, via `describeExtensionWaiting(extension, t)`, names the unset secret fields ("Waiting for: <labels>", the schema secret fields where `set === false`). `applyExtensionsPanelList` carries `readyState` and normalizes `capabilities.tools` from the `{name, ready}` shape; `summarizeExtensionCapabilities` still lists tool names only.
- `StatisticsView.svelte` + the pure `statisticsView.js` own the Statistics tab's five sub-views (Overview / Usage / Runs & errors / Tools / **Limits**). Overview..Tools render the single `statistics.report` loaded on mount; project agents arrive in the report keyed as `agent@projekt`, so every agent cell renders through `agentDisplay` (parses the address) as the bare name plus a small project badge — identity agents (no `@`) render unchanged, no badge. This is read-only display only (no project filter/grouping in v1). The Usage sub-view renders the report's cache aggregation (see `statistics.md`): a "Cache hit rate" card and per-provider/per-model "Cache hit" columns via `cacheHitRate(record)` (`cache_read_tokens / cache_input_tokens`, `null` → "—" for records without cache data), a green cache-hit-% polyline in the "Tokens per period" sparkline (absolute 0–100% scale via `sparklinePoints(..., { max: 1 })`, with a legend), a "Sessions with lowest cache hit rate" table, and a "Suspected cache breaks (derived)" block (summary line + incident table) labelled as a best-effort heuristic. The **Limits** sub-view is independent — it lazily calls `provider.usage` on first open (own loading/error state, manual refresh) and renders one card per provider snapshot with each window as a severity-colored progress bar (`clampUsagePercent`/`usageSeverity`) and a `formatResetAt` relative+absolute reset time. Error/empty snapshots show a clean "unavailable" row; no connections → an empty-state message. It is live provider state, not part of the read-only statistics aggregation (see `statistics.md`, `providers.md` → Provider Usage Probe).
- `SystemPromptView.svelte` owns the System Prompt **block list** and prompt-scope UX; backend prompt semantics live in `.vorch/domain-maps/prompts.md`. Blocks come from `prompt.list` in layout order and are keyed by their stable `id` (never an array index, so autosave timers and DnD/keyboard-reorder identity survive a reorder). The list is **sortable** — native HTML5 drag-and-drop on a per-row handle **and** keyboard reorder (ArrowUp/ArrowDown on the focused handle, with an aria-live announcement and focus that follows the moving row) — and every reorder/toggle persists immediately via `prompt.set_layout`. Editable text blocks render a textarea with 800ms debounced autosave (`prompt.update`) plus a Reset button (`prompt.reset`); **data blocks** (`kind === 'data'`) are read-only with an expandable preview of their current text. Each row shows an **owner label** ("appears when: …"), `custom`/`auto` badges, and in an agent scope an `inherited`/`modified` **inheritance badge** (an inherited block shows greyed default text; editing it creates the override). Custom `user:` blocks can be **created** (slug prompt, client-side slug pre-check mirroring the backend agent-id rule) and **removed**; a "Reset order & visibility" button calls `prompt.reset_layout`. Both pickers in this view are the shared `Dropdown` primitive (no raw `<select>`): the header **scope** picker (Default + enabled identity Agent scopes) and the **preview agent** picker. The preview agent picker combines identity agents (`agent.list`, bare-id values) with project agents (lazily scanned via `project.list` → `project.show` on mount, cached) addressed as `agent@projekt`, built by the shared `lib/agentTargetOptions.js` helper; the selected option value is passed straight to `prompt.preview` as `agent_id` (the backend resolves a project-qualified address). Project agents appear only in the Default-scope preview — an Agent prompt scope is identity-only. The preview pane (Refresh + Copy) shows a token chip: with tool definitions present it renders the breakdown `~{prompt} prompt + ~{tools} tools = ~{total} tokens` (from `prompt.preview`'s `tokens`/`tool_tokens`, tooltip explains the tool-definition array with `tool_count`); a tool-less agent falls back to the plain `~{count} tokens`.
- `LogsView.svelte` and `logsView.js` own read-only log file selection, local level/search/sort state, and dedicated log-stream reconnect behavior; backend parsing and socket contracts live in `.vorch/domain-maps/logs.md`.
- `CronView.svelte` and `cronView.js` own the Cron tab view state and create/update payload construction; scheduler behavior lives in `.vorch/domain-maps/automation.md`. The agent dropdown (built via the shared `lib/agentTargetOptions.js` helper, also used by System Prompt) combines identity agents (`agent.list`, bare-id values) with project agents (lazily scanned from `project.list` → `project.show` on first modal open, cached) whose option value is the full `agent@projekt` address — so saving sends that address straight through as the `cron.create`/`cron.update` `agent_id` param. An existing job pre-fills from the server-formatted `target` field of `cron.list` (not the bare `agent_id`), so a project job re-saves its address.
- `webui/src/lib/agentAddress.js` is the one client-side `agent@projekt` parse/format seam (`formatAgentAddress`/`parseAgentAddress`), mirroring `core/projects/address.py`; Cron, Statistics, and the `agentTargetOptions.js` builder consume it. (`chatState.js` keeps its own Phase-2 `formatAgentAddress` deliberately, in lockstep via the shared `@` separator.)
- `webui/src/lib/agentTargetOptions.js` is the one builder for "agent target" dropdowns — it turns `agent.list` plus lazily-scanned project teams (`project.list` → `project.show` → `projectTeamEntry`/`projectIdsFromList`) into a flat option list mixing identity agents (bare-id values) with project agents (`agent@projekt` values), and `buildAgentTargetDropdownOptions` adds disabled "Identity agents"/"Project agents" group headers only when project agents exist (identity-only stays header-free). Cron and System Prompt both feed it into a `Dropdown`; cron re-exports it under its historical `buildCronAgent*` names for back-compat.
- `ProjectsView.svelte` (flat), the pure `projectsView.js`, and `styles/projects.css` own the Projects tab as a **master-detail** view mirroring AgentsView (see `webui/state-flows.md` → Projects tab / Team rows for the runtime contract). The **list pane** shows every project (display name + cwd, selected state) with Refresh + "Add project" in its header; Add is a modal collecting only cwd + optional display name (blank → backend derives the name). The **detail pane** for the selected project (`project.show` scan loaded on select) is five ordered sections: **Project settings** (display name `TextField`; **default agent** `Dropdown` via `buildDefaultAgentOptions`; **default model** `SearchableDropdown` + `modelSelection.js`; **default temperature** + **default thinking effort** — the three defaults carry the shared `inherit.*` inherit-state labels seeded from the global `defaults.agent` fetched once via `settings.get`, absent-case labels on failure; explicit-save with an 800ms debounced auto-save via `buildManageProjectPayload`'s sparse `project.set` diff plus a Save button, App must pass `onToast`), **Auto-load files** (editable list + add), **Team** (see below; the `ProjectScanBanner`-style report renders at the top when unclean), **Tools** (the `Toggle` whitelist of `tool.list` minus `memory`/`skill_manage`, readiness via the shared `ToolReadinessNotice`, reset-to-`default_project_tools` button), **Skills** (three `Toggle` sections — project auto-on/off-exception, bundled + global opt-in; a shadowed same-name bundled/global skill is dropped). **Team rows** are expandable: each scanned member (`projectTeam` carries `agent_id`/`display_name`/`description`/`denied_tools`/`source_*`/`pins`/`effective`) shows effective `model`/`temperature`/`thinking_effort` with a provenance badge (`pin`/`agent file (repo)`/`project default`/`global default`; null → "not configured"/"provider default", no badge), a **pin control per field** (model select, comma-tolerant temperature input, effort select gated by the member's effective model via `agentForm.js` helpers), the denied-tools lines, and the source line. Pins are **immediate actions**: Set → `setPin`/`project.set_pin`, Clear (only when pinned) → `clearPin`/`project.clear_pin`, each refreshing team/report from the returned scan with success/sticky-error toasts (model pin also settable command-only via `/model`). `projectsView.js` holds the add/manage/default-agent-option builders, the tool/skill toggle-list builders, `projectTeam` (with `normalizePins`/`normalizeEffective`, `memberFieldIsPinned`, `seedTeamPinDraft`, `normalizePinTemperature`), `normalizeScanSkills`, the scan-report normalization (clean/empty = normal bare-project case), and the re-point payload. The thin `project.*` wrappers (`addProject`/`listProjects`/`showProject`/`setProject`/`removeProject`/`setPin`/`clearPin`) live in `api.js`; backend behavior is in `.vorch/domain-maps/projects.md`. `ChatView` also imports `projectTeam` (uses only `agent_id`/`display_name`) — do not drop those fields.
- `markdown.js`, `toastState.js`, `audioRecorder.js`, `sessionListView.js`, `clientCaches.js`, and the other small `lib/` helpers should stay pure where practical and are covered by focused Vitest tests under matching `__tests__/` directories.
- **UI primitives (`components/ui/`)** group the shared design-system controls, distinct from the feature components in `chat/`, `agents/`, `settings/`, `debug/`. Each primitive owns the single canonical CSS class per variant (styling source stays the global classes in `styles/app.css`; the component consumes them and hides the markup) and follows the `Dropdown.svelte` convention (that exemplar and `SearchableDropdown.svelte` live flat in `components/`, **not** in `ui/` — see the shared-dropdowns bullet below) — Svelte 5 `$props()`, callback props (`onClick`/`onChange`/…), no event dispatchers, already-translated content in via `children`/props. `Button.svelte` covers `variant` (`primary`/`secondary`/`tertiary`/`danger`) + `icon` footprint, replacing the ~80 hand-built `btn-*` call sites and collapsing the duplicate class names (`btn-new`/`btn-outline`/`modal-btn-*`/`send-btn`/`icon-btn`/`tl-btn`/`pane-action`) to one per variant. `Modal.svelte` owns the dialog chrome (overlay, overlay-click/Escape close, `role="dialog"`/`aria-modal`, header with title + close button, focus-on-open) behind `title`/`labelledById`/`onClose`/`closeDisabled` props plus `body` + optional shell-wrapped `footer` snippets; the three duplicate modals (`AgentCreateModal`, the `CronView` job modal, `ProviderConnectModal`) supply only their body/footer. `Toggle.svelte` renders the `role="switch"` button + knob in two sizes (`lg`/`sm`) behind `checked`/`onChange`/`size`/`disabled`/`ariaLabel`, replacing the hand-built `.toggle`/`.tl-toggle` switches (the Desktop `voice-toggle` checkbox-slider and the `stats-toggle` segmented control are distinct controls, left as-is). `StatusChip.svelte` renders the semantic pill (`variant`: `success`/`warn`/`info`/`error`/`neutral` + `children`), collapsing the `chip-green`/`-amber`/`-orange`/`-red` color aliases into the `chip <variant>` semantic names; the chip-classifying helpers (`channelEnabledChipVariant`, `channelRunningChipVariant`, `extensionStatusChipVariant`, and CronView's `statusChipVariant`) now return variant names. `TextField.svelte` covers the editable input (`variant` default/modal → `s-input`/`modal-input`), the `invalid` state (`s-input--invalid` red border, replacing the agents-only `agents-view__invalid`), and the read-only `s-value-box` (`readonly`); it uses the `value`/`onInput(next, event)` callback pattern (no `bind:`), so the migrated call sites pass a setter callback instead of two-way binding. Multi-line textareas keep their own `<textarea class="s-input">` markup (out of scope), so the input guard is scoped to `<input>`. `ConfirmDialog.svelte` builds on `Modal` + `Button` for destructive/irreversible confirmations (`title`/`body`/`confirmLabel`/`cancelLabel`/`danger`/`onConfirm`/`onCancel`; danger confirm by default, overlay/Escape/× route to cancel), replacing every native `window.confirm` across the WebUI — callers own the open state and conditionally render it. A growing Vitest guard (`lib/__tests__/uiPrimitives.guard.test.js`) scans all `*.svelte` and fails if a raw element reintroduces a primitive's class outside its `ui/` owner, **and** if a native `confirm(` call reappears in any component (use `ConfirmDialog` instead).
- **Shared dropdowns** are two flat components in `components/` (**not** in `components/ui/` — this trips agents up repeatedly): `Dropdown.svelte` is the **simple** picker (absolute list, no filter — short option sets) and `SearchableDropdown.svelte` is the **searchable** one (fixed/portaled panel with a filter-input header — long lists like models). Both share the callback-prop contract (`value` in, `onValueChange(value, option)` out; `options` as strings or `{ value, label, disabled, secondaryLabel[, searchText] }`, plus `id`/`placeholder`/`disabled`/`ariaLabel`/`triggerClass`) and position through `lib/dropdownPanel.js` (`computePanelPosition` + `portal`). A model picker is `SearchableDropdown` fed by `modelSelection.js` (`buildModelSelectOptions`/`selectModelValue`), reused 1:1 by Agents, Cron, and Projects — don't hand-roll one. Design tokens for both live in `.vorch/DESIGN.md` → Dropdowns.
