# WebUI App Shell

Read this reference only for WebUI application-shell, navigation, connectivity, server-event, or global invalidation work. The root boundary and domain-wide frontend invariants live in `webui.md`; file-level ownership lives in `webui/source-map.md`.

Before changing editor-replacing navigation or pending-save handling, read `webui/autosave.md` for participant integration. This file owns the App-level transition and failure presentation below.

## Ownership

`App.svelte` composes the major views and creates the long-lived application controller and the navigator. `appController.js` owns global loading, server-event dispatch, and refresh coordination; `lib/navigation.svelte.js` owns the displayed Location and browser history (Navigation below). `AppShell.svelte` owns global viewport/focus presentation, including the capability-gated Desktop context menu. Its private `components/shell/menu.svelte.js` owns action derivation, selection snapshots and editing/native actions; rendering, positioning, keyboard and dismissal come from the shared `components/ui/ContextMenu.svelte` (`design.md` -> Shared controls). The shell keeps navigation and mounting. `api.js` owns the actual HTTP, WebSocket, and SSE transport adapters; `connectionState.js`, `navigation.svelte.js`, and `resourceInvalidation.js` keep their respective state machines out of the root component.

Domain controllers still own their data. The app shell may request a refresh or route a lifecycle event, but it must not duplicate Chat, Provider, Extension, Project, or Settings rules.


AppShell's optional `sidebarFooter` snippet precedes the existing microphone and connection rows. App mounts the Live voice control there, shown while a `model_tasks.live_voice` binding exists; its lifecycle lives in `model_tasks/live.md`.

## Main menu responsiveness

- `AppShell.svelte` watches the phone (`<=640px`) and tablet (`641-960px`) ranges through one `matchMedia` helper whose listeners are removed on unmount. The saved compact preference (`vbot.sidebar.collapsed.v1` in localStorage) applies only from desktop width (`>=961px`); tablet behavior never reads it for layout and never writes it.
- At tablet width the Main menu always renders the compact rail. Its toggle (`aria-expanded`, not `aria-pressed`) opens the full menu as an overlay (`data-tablet-menu-open`) above a light scrim; the shell reserves the rail width while it is open, so the content - including fitted Terminals - never resizes. Focus moves to the current destination and the content is `inert`.
- The overlay closes on any navigation (including history and deep links), a backdrop click, the toggle, leaving the tablet range, or an Escape no floating layer consumed (`defaultPrevented`); Escape returns focus to the toggle. The phone More sheet follows the same Escape rule. Coverage: `components/__tests__/AppShell.test.js`.

## Main menu indicators

- A view can show an indicator on its Main menu entry: App keeps `navigationIndicators` by view id and passes it to `AppShell.svelte` as `indicators`. Each entry is `{count, tone, label}` or null: tone `unread` (blue) or `running` (amber), and a label saying in words what the count means. The view that owns the meaning reports it; the shell only renders it. Chat is the first reporter (`webui/chat.md` -> Selection and Sessions); another view adds its own entry the same way.
- The count (capped at `99+`, `aria-hidden`) sits at the row's end in the full menu and in the phone More sheet, and as a solid count at the icon's corner in the compact rail and the phone bottom bar. The entry's accessible name becomes `<label>, <indicator label>` (`navigation.itemIndicator`); the tooltip shows the indicator label, in the compact rail together with the entry name (`AppShell.test.js`).

## Desktop context menu

- `App.svelte` enables the custom menu only after the live Desktop bridge advertises `contextMenu`; an ordinary browser never has its native `contextmenu` event cancelled by AppShell. Only a component that opens its own menu cancels it there.
- The handler ignores `contextmenu` events that are already `defaultPrevented`: a component menu (for example on a skill row) handles the event first and calls `preventDefault()`, so the component menu and the Desktop menu never both open.
- `AppShell.svelte` derives actions from the event's composed DOM path: safe absolute HTTP(S) links expose Copy link address and Open in browser, selected non-sensitive text exposes Copy, and writable text controls additionally expose Cut and Paste. Password controls expose Paste without copying/cutting their selected value. It snapshots the selection before moving focus into the menu so editing actions still target the original control.
- The menu renders through the shared `ContextMenu.svelte`, with the action icons passed as its `icon` snippet; measuring, clamping, keyboard handling, dismissal and focus return are the primitive's contract. Focus returns to the original text control (or the previously focused element) before the action runs.
- Native operations go through `lib/desktopBridge.js`; AppShell never depends on `navigator.clipboard`, and the Desktop Python boundary repeats URL validation. Failures produce one warning Toast through App's existing `onToast` callback.

## Startup and availability

- Startup loads the server-backed resources required to decide which views are available, then mounts view state through `createAppController`. Project-catalog loads are generation-guarded so only the newest outstanding response updates the shell, and a transient failure retains the last valid catalog. Failure to load one optional surface must not turn the whole accessor into a second source of truth.
- View availability is derived from current capabilities and server state. If the active view becomes unavailable, navigation resolves to a valid view instead of leaving an unreachable route selected.
- User-initiated context changes that would replace an autosave editor-main-view navigation, Agent or Project selection, System Prompt scope selection, and editor deep links-go through the coordinator in `autosave.js`. Registered editors cancel their debounce, wait for any in-flight save, and keep saving newer snapshots until stable; the latest requested transition runs only after every pending participant succeeds, including when the user selects another destination during the flush. A waiting navigation never locks the app, because RPC calls have no deadline. When a save still runs after `AUTOSAVE_STILL_SAVING_MS` (12 s), App opens a "Still saving" modal: Keep waiting closes it and the navigation still runs once the save finishes (a further navigation request reopens it); Leave anyway runs the latest navigation now and lets the running writes finish in the background (`releaseRunningSaves()`, `webui/autosave.md`). A failure leaves the editor mounted and opens the App-owned Retry / Discard and continue modal. Discard and continue stays enabled while a Retry runs; closing the modal (Escape, its close button, Back) drops the navigation and keeps the unsaved edits. A flush of a transition the user left or closed cannot navigate or reopen a prompt when it settles. Coverage: `App.navigation.test.js`. A browser beforeunload guard warns while registered changes or writes remain pending. Browser tab visibility is outside this contract, and explicit confirmation or special-operation flows do not become autosave operations.
- Every change of the shown place, Back/Forward and deep links included, goes through the navigator (Navigation below).
- Within one `serverRecoveryGeneration`, `App.svelte` keeps `ChatWorkspace` and its retained Chat/Preview areas mounted even while another main view is active; ordinary navigation changes `active` visibility instead of replacing owners. This preserves area-local selection, drafts, timeline viewport/disclosures, transient state, and Run-stream ownership, and prevents roster/History/activity initialization from repeating when the user returns. App selection/history callbacks address the first Chat; the second Chat keeps independent navigation inside the workspace.
- App setup owns automatic onboarding entry and dismissal; the dedicated `OnboardingView` can also be reopened from Settings. Its detailed policy belongs in `webui/settings.md`.
- **Desktop restart into a new version** (Desktop capability `restart`; bridge `getDesktopUpdate`, `restartDesktop`, `onDesktopUpdate`, `onDesktopRestartRequest` in `lib/desktopBridge.js`): `app/desktop.svelte.js` reads the update state `{pending, restarting, failed}` once the capability is true, then follows the `vbot-desktop-update` push (a push drops an older read still in flight). While `pending` or `restarting`, App shows one info Banner with a Restart button instead of the WebUI reload banner, because the new Desktop also loads the new WebUI; `restarting` (set optimistically once `restartDesktop()` is accepted) disables the button with progress, `failed` says the restart did not complete and the button retries. Browsers and Desktops without the capability keep the reload banner.
- One function in `App.svelte` (`restartDesktopApp`) prepares every restart. The Restart button asks with a `ConfirmDialog` before discarding an unsaved new Cron job (`cronNewJobDraft`), saves pending edits through the autosave transition gate (with its Retry / Discard and continue modal), then calls `flushComposerMemory()` and `restartDesktop()`; a refusal becomes an error Toast. In the Desktop app the page acknowledges every `vbot-desktop-restart` push (`preventDefault()`) and never declines it, because the request follows an update the user started: it saves pending edits for at most `AUTOSAVE_STILL_SAVING_MS` (12 s, the time a navigation waits before it offers to leave; a slower save keeps running), then calls `flushComposerMemory()` and `restartDesktop()` without any UI, discarding an unsaved new Cron job and ending a Live voice call. A refusal stays silent; the Desktop restarts on its own 15 s after the request anyway (`desktop/update-restart.md` -> Restart triggers). While `restarting`, the beforeunload guard no longer asks about the Cron job; pending edits still ask. Coverage: `__tests__/App.desktop-restart.test.js`, `lib/__tests__/desktopBridge.test.js`.

## Navigation

`lib/navigation.svelte.js` is the one owner of Back/Forward. App creates its navigator (`createNavigator`) and provides it through Svelte context (`provideNavigation`, `useNavigation`); views never touch `window.history`. Coverage: `lib/__tests__/navigation.test.js`, `__tests__/App.navigation.test.js`.

- **Location:** `{view, place, extra}`: the main view, a view-owned `place` (string segments naming the shown record or sub-page) and, for Chat only, structured `extra`. The URL hash spells view and place (`#skills/all/<skill>`; segments URL-encoded except `:` and `@`), so a copied URL or a reload opens the same place. Each entry's history state is `{marker: 'vbot.location', index, view, place, extra}`; the entry stack is mirrored in sessionStorage (`vbot.navigation.stack`, the last 200 entries) so a reload keeps what Back and Forward lead to and the place each view was last shown at (a new document starts a new stack). A typed or linked hash becomes a new entry after the current one.
- **Step rule (user requirement):** one history entry per change of the main content: another main view, another selected record (Agent, Project, Cron job, Session, log file, trace), a sub-page (Skill page, shared Agent defaults) or a page-level tab (Settings page, Statistics section, System Prompt tab, Swarm tab). Filters, search, sort, scroll, disclosures, scroll targets inside one page and representation tabs (Instructions/Original, request/response) are not steps. Automatic corrections - a default selection, a vanished record, a load that resolved the real id - replace the current entry. In-view back arrows and breadcrumbs go "up": `up(parent)` goes Back when the previous entry is exactly that parent (Forward then returns to the child), otherwise it adds a step.
- **View handle:** `navigator.view(id)` gives a view `{active, place, extra, origin, revision, navigate, replace, up}`. A view applies its place to its state once its data is ready, shows its default for an empty or unknown place and corrects the place with `replace`; it reports state changes it made itself (a default, a deletion, a saved new record) with `replace`; user actions call `navigate` and let the place drive the state. `origin` tells who set the displayed Location: `history` (startup, Back/Forward), `app` (the shell or another view) or `view` (the view's own handle). `replace` is ignored while a Back/Forward still waits in the autosave gate. `createStandaloneNavigation(place)` offers the same interface without history; views default their `navigation` prop to it, so they work in component tests and isolated trees. Only Chat stays mounted while hidden; its `replace` then corrects the place Chat returns to.
- **Main navigation:** choosing a view returns to the place last shown there; choosing the view already shown goes to its start (its empty place), which the view corrects to its concrete default. `navigator.forget(view)` drops a remembered place: when another view selects a different Agent, App forgets Chat's so Chat follows the shared selection.
- **Layers:** an open dialog (`Modal`), context menu (`ContextMenu`), the menus that still render their own `role="menu"` (Chat file-link actions, Session row and filter menus, Terminal group actions, the Skills add menu), image lightbox, the phone More sheet or tablet menu overlay (AppShell), a maximized Terminal, dialogs and menus inside an Extension page (one layer for the page, `webui.md` -> Ownership) and the onboarding wizard register with `useNavigation()?.registerLayer({close})` and release when they close. Back and Forward first close the topmost layer and stay at the current place (a browser popstate is sent back to the current entry); only then do they navigate. Onboarding's layer returns from the Model step to the service step and from the service step sets the wizard aside.
- **Autosave gate:** every navigation runs through App's `navigationGate` (`requestAutosaveTransition`, Startup and availability above). A popstate records the new entry index at once and displays its Location when pending edits are saved; a failed save keeps the editor and opens the Retry / Discard and continue modal. When the gate drops that move (the failure modal closed), `navigator.cancelPendingMove()` sends the browser back to the entry of the displayed Location; a bounce requested while another one is under way (the modal's own layer bounce) continues from where the first lands. The gate also captures the Settings reading position while Settings still owns its DOM.
- **Availability and identity:** a Location whose view is unknown or unavailable shows the default view instead (Debug while Debug Mode is off shows Settings) and its entry is rewritten. An Identity Agent rename rewrites, once, the places remembered at that moment: each view's last place, the entry stack and the shown place (`remapAll(remap)` with App's `renameAgentInLocation`). Back/Forward reads an entry from that mirror, not from the browser's history state, which only the current entry can rewrite. Later navigation is never remapped, so an id reused by a new or another renamed Agent opens that Agent.
- **Desktop app** (`?accessor=desktop`; `guardExit` and `handleInput`): a floor entry below the first app entry sends the WebView forward again, so Back never leaves the app (at the floor it still closes an open layer). The navigator handles Alt+Left/Right, the BrowserBack/BrowserForward keys and the mouse side buttons itself, cancelling their default so each press moves once (an Extension page forwards the same input from its frame). The app shows no Back/Forward buttons of its own (user decision 2026-09-29); browsers keep their toolbar.
- **Startup Extension page link:** Extension page routes become known views only after `extensions.pages` loads. When the startup Location names an unknown `extension:` view, the navigator shows the default view but keeps that entry and URL; after the first successful catalog load (`app/extensions.svelte.js` `onPagesLoaded`) `resolvePendingStart()` opens the page in place of the entry, or rewrites the entry to the shown view when the page does not exist. Any user navigation first forgets the pending link.
- **Session links from outside the page:** a page loaded with `open_agent` (Agent address, `agent` or `agent@project`) and `open_session` (Session id) opens that Session. `navigator.takeSessionLink()` removes exactly those two parameters with `history.replaceState` (other parameters and the hash keep their spelling), so no entry or reload repeats the link; App then navigates to the Session as a step, the path of Live UI's `open` action, and Back returns to the previous place. A link with only one non-empty parameter is removed without navigating. In the Desktop app App handles the `vbot-desktop-open-session` push (`onDesktopOpenSession` in `lib/desktopBridge.js`, `detail` `{agent, session}`, acknowledged with `preventDefault()`) the same way. An unknown Session shows Chat's History error in place. The Desktop app's `--open-session` produces both (`desktop.md` -> Interfaces).
- **Chat:** the place is `[agentAddress, sessionId]` with `extra` `{selection, subAgent}`, or `[agentAddress]` for the Agent's unsaved draft (`#chat/<agent>`), which a restore shows as a draft again. Chat's first area reports every Session or draft it shows; App turns Chat Locations it did not set itself (Back/Forward, links, the main navigation) into a restore request once the Agent roster has loaded, skipped when Chat already shows that Session; Chat's start place (`#chat`) is corrected to the shown Session, also when Chat resolved it while hidden. The second Chat area stays out of history. Details: `webui/chat.md` -> Selection and Sessions.

## Server connection and events

- `subscribeServerEvents()` opens the app-wide WebSocket. A `connection_ready` payload establishes the server epoch, replay position, and replay completeness; reconnect logic distinguishes a fresh connection, complete resume, replay gap, and server restart.
- Reconnect uses bounded backoff and exposes connection state to the shell. A short interruption is tolerated before the offline notice is shown so transient browser/network churn does not flash disruptive UI.
- The global offline notice replaces connection-state symptoms but does not dismiss unrelated sticky error toasts; those remain until the user acknowledges them. New error toasts are suppressed while the connection is already known to be offline so dependent failures do not flood the UI.
- The offline notice keeps Retry as the normal browser recovery. When Desktop capability discovery reports `serverSelection`, it also offers Switch server; that action hides the notice and opens the shared Desktop remembered-server picker in a modal rendered outside AppShell's inert main content. Browser accessors never see this action, and launch-time Desktop failures remain with the native Connection screen because the WebUI is not available yet.
- `connection_ready.replay_status` is `fresh`, `resumed`, `gap`, or `epoch_changed`. A complete resume keeps the client's acknowledged cursor until replayed events arrive; a gap or epoch change adopts the hello high-water mark and invalidates every resource-backed projection through its existing owner. The authoritative `active_runs` and public `queues` snapshots are forwarded to Chat for immediate Run and Queue reconciliation.
- Replay-gap and epoch-change invalidations are published before awaiting read owners. Data-store status, Extension-page descriptors, Projects and Agents refresh independently, so a slow or failed optional projection cannot delay unrelated recovery (`appController.test.js`).
- Recovery after a confirmed offline notice increments `serverRecoveryGeneration`, remounting the keyed main-view generation-including the retained Chat owner-so normal load paths refresh server-backed state. A reconnect that completes inside the notice grace period does not force that remount.
- Every `connection_ready` also checks the WebUI build (`lib/webuiBuild.js`): each production build carries one id, derived from its hashed output file names by `scripts/webui-build-identity.mjs`, in a `vbot-webui-build` meta tag of `index.html` (the build the page runs) and in `build.json` (the build the server serves now, read with `getServedWebuiBuild` past the browser cache). When they differ, typically after an update restarted the server under an open page, App shows a sticky info Banner whose Reload button reloads the page (the Desktop restart Banner replaces it while a Desktop restart is offered, Startup and availability above); the autosave `beforeunload` guard still warns about pending changes. A page without the meta tag (Vite dev server, tests) or a served build without an id counts as current, and a failed read keeps the last answer (`webuiBuild.test.js`, `App.test.js`).
- App keeps the background activity list as `backgroundActivity`: `activity.list` loads it on every `connection_ready` (a refresh owner, so a server restart cannot leave a stale list), and each `activity_status` push replaces it; SettingsView shows it at the top of General while it has entries (`webui/settings.md`).
- App keeps the latest `recall_index_status` payload as `recallIndexStatus` and forwards it through SettingsView to the Conversation search panel, which reads `recall.status` itself when it mounts (`webui/settings.md` -> Conversation search settings).
- Data-store status loads on `connection_ready` and on `resource_changed(kind="data_store")`; the App-owned sticky Banner keeps an unacknowledged recovery incident visible through transient refresh failures, and acknowledgement adopts only the returned status projection.
- App retains the latest `connection_ready` and a bounded window of the last 500 Run events for mounted Chat owners, plus a live `activeRuns` list: the snapshot's `active_runs` advanced by later `run_started` and terminal events. A Chat owner created after the app connected (the lazily mounted second area, leaving onboarding, a recovery remount) starts from that snapshot with `activeRuns` and marks the retained window handled instead of replaying it, because the window may no longer hold the terminal event of a Run the snapshot listed (`appController.test.js`, `ChatWorkspace.test.js`). The window is append-only - new events join at its end, the oldest drop off - and each Chat owner resumes after the last event it visited instead of re-keying all 500 on every event; a window without that event is visited in full (`chatRunStream.js::handleServerEvents`, `chatRunStream.test.js`).
- WebSocket Run events are lifecycle summaries used for global awareness and recovery. Per-Run output, reasoning, tool-call, and log deltas arrive through the Run SSE subscription owned by Chat.
- Presence is server-owned. `clients.list` supplies the Settings projection; the WebSocket only signals when that projection should refresh.

## Resource invalidation

- `resource_changed` events carry a resource family and optional scope. `resourceInvalidation.js` converts them into refresh tokens or targeted callbacks rather than copying RPC-specific branching into every component.
- `commands` invalidation bumps the App-owned Command refresh token forwarded to Chat. Replay gaps and epoch changes bump it with the other server-backed projections so the active autocomplete catalog is re-fetched after uncertain continuity.
- Queue invalidation is scoped to the addressed Agent and Session. Every `sessions` event appends `{id, scope}` to App's bounded `sessionInvalidations` window (last 200, `lib/sessionInvalidation.js`) instead of bumping a token: Chat activity, the Session drawer and the Parent Session link each keep a cursor into it, adopt the retained window when they mount, refresh only what a scope can affect, and refresh everything they show when the window dropped entries they never saw. `sessionsRefreshToken` bumps only on a replay gap or epoch change. A `sessions` event whose scope names a `deleted_session_id` additionally sets the App-owned `sessionDeletion` (a fresh object per event) that Chat turns into Session release and landing follow; see `webui/chat.md`. Other resource families refresh the controller that owns their displayed projection.
- `archive` invalidation bumps the App-owned `archiveRefreshToken`, and so does every replay gap or epoch change; SettingsView forwards it to the Archive page, which reloads its list and the shown entry (`webui/archive.md`).
- `terminals` invalidation bumps the App-owned terminal refresh token. The mounted Terminals controller re-fetches the active catalog without replacing a still-valid selection; PTY output is not an invalidation and remains on the selected terminal's dedicated stream.
- `data_store` invalidation refreshes the App-owned health and incident projection without touching Chat selection or Session content.
- An `extensions` invalidation whose scope names an `owner` (`{owner, resource, ids, revision}` from `ExtensionHost.publish_change`) goes to `app/extensions.svelte.js` `publishChange`, which hands `{owner, change}` to every subscriber of `subscribeInvalidations`; page descriptors are not fetched again. An unscoped `extensions` event (explicit Extension reload, Settings reload/enable/disable) and every connection-ready snapshot reload `extensions.pages`; after each successful load every subscriber is invalidated with `{owner: null, change: null}`. Each subscriber filters for itself: an open Extension page refreshes on its owner's changes, the Settings `ExtensionRequests` panel on `pending_inputs` changes from any owner (`webui/settings.md`), the MCP connections panel on `connections` and `jobs` changes of owner `mcp` (`webui/settings.md` -> MCP connection management), and the composer's Computer Use control on `computer_use` changes (`webui/chat.md`); all of them refresh fully on an owner-less invalidation, so reconnect gaps and epoch changes cannot leave them stale (`appController.test.js`, `ExtensionPage.test.js`, `App.test.js`).
- Refresh completion does not automatically replace an active editing surface. A controller can retain the visible snapshot while a modal, picker, or draft is busy, then adopt the newest server result at the safe boundary.
- Event handlers must be idempotent because reconnect replay and explicit refreshes can describe state the browser already knows.

## Transport contracts

- RPC requests go through the wrappers in `api.js`; validation, network, HTTP, malformed-envelope, malformed-SSE, and malformed-WebSocket failures are normalized before reaching views.
- `subscribeLogEvents()` owns the per-file log WebSocket. Log browsing behavior lives with the Settings/log surfaces; it does not share Run SSE semantics.
- `subscribeTerminalEvents()` owns the per-Terminal server-push WebSocket. It carries an authoritative snapshot plus sequenced live output/state only; terminal input, resize, and stop remain RPC wrappers, and the view/controller owns reconnect and cleanup.
- Attachment downloads use server URLs returned by `getAttachmentUrl()` and remain outside JSON-RPC.
- Debug wrappers remain guarded by the frontend development gate and the server's debug policy.
- `lib/clientMetrics.js` measures the browser side for the performance domain (`performance.md` -> Metric Catalog, `webui.*`). `App.svelte` starts it on mount and stops it on teardown; `rpc()` in `lib/api/transport.js` times every RPC except those sent with `untracked` (the report itself), `appController.js` notes each `resource_changed` kind before routing it, and `ExtensionPage.svelte` notes host-requested page invalidations. It reports through `reportClientMetrics` about once a minute, drops a batch whose report fails, and records nothing before it starts, so tests and views need no setup.

Private App view implementations live in `webui/src/app/`: `selection.svelte.js` owns persisted Agent/Project selection and roster loading, `setup.svelte.js` owns Settings-backed operational state and onboarding, `desktop.svelte.js` owns Desktop capability/Voice feedback, the Desktop update state with the restart request, and toast lifetimes, and `extensions.svelte.js` owns Extension-page descriptors, theme synchronization, and the Extension invalidation fan-out. `App.svelte` retains application-controller construction, autosave transitions, navigation, and composition; the public `NAVIGATION_ITEMS` export remains unchanged.

Agent roster reads are ordered within the App owner and invalidated on disposal. If a child publishes a roster while the latest App read is pending, App re-reads before publishing and invalidating consumers; the pending resource refresh is not lost and its older snapshot cannot revert the published selection (`app/__tests__/selection.test.js`).
