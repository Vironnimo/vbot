# WebUI Visual State

Task-specific companion to `../webui.md`: the implemented appearance and interaction patterns, with pointers to their owners.

## How to use this description

This is a description of the current implementation, not a design specification, quality endorsement, or template for new work. Existing colors, typography, dimensions, layouts, action placement, and information hierarchy are all open to revision within the user's requested scope. Changing them does not require an exception to this document. A previous implementation becoming documented does not make it an approved design constraint.

Read the relevant sections when the task needs visual context, such as changing shared styling, understanding an existing layout, or assessing a redesign. This companion is not an additional prerequisite for every WebUI task. Source code remains the authority for implemented behavior. Screenshots and browser checks establish what the current interface actually looks like; a passing component test does not establish design quality.

The parent map separately records engineering contracts such as server-owned state, accessibility, draft preservation, and shared-component integration. Those contracts do not prescribe a layout. Explicit user requirements remain distinguishable from implementation observations; record a new visual constraint only when the user establishes it as one. Update the affected observations after a change without turning the new arrangement into a requirement for other views.

Paths beginning `webui/`, `desktop/`, or `resources/` are repository-relative. Other map links are relative to this file. Short component/lib names identify their owners under `webui/src/`; `source-map.md` supplies the detailed source routing. The source and test references below are starting points, not a claim that every current screen has been visually approved.

## Shared appearance

### Tokens and assets

`webui/src/styles/app.css` is the ordered stylesheet entrypoint; its private `app/foundation.css` owns the implemented CSS tokens and bundled font declarations, while adjacent `app/` files own primitive styles and app-shell geometry. There is no separate machine-consumed token catalog in this map. `webui/src/styles/settings.css`, `projects.css`, and `cron.css`, plus component-local styles, specialize those foundations.

The current palette is a warm, low-chroma graphite with a single orange accent. Hierarchy reads from clearly separated surface tones rather than from border lines. The main surface roles are:

| Role | Current implementation |
|---|---|
| Page background | `--bg`, `#15130F` |
| Main menu and Secondary panes | `--secondary-surface`, `#1A1814` |
| Surface steps | `--surface`, `--surface-2`, `--surface-3`: `#1E1B17`, `#26231E`, `#302C26` |
| Structural and control borders | `--border`, `--border-2`: `#2E2A25`, `#423C35` |
| Text levels | `--text-hi`, `--text-med`, `--text-lo`: `#F1EDE6`, `#B3AA9E`, `#9D9387` (all WCAG AA on bg and every surface step, including `--surface-3`); `--text-body` `#E3DED6` is a barely dimmer step for long-form Chat Markdown prose, whose headings, bold text and table headers stay `--text-hi`; `--text-faint` `#6B635A` only for decoration, separators, and disabled glyphs |
| Interaction accent | `--accent`, `#E8870A`, with `color-mix` opacity steps and `--on-accent` for text on a solid accent fill |
| Status colors | Green for success, amber (`#E5B53E`, deliberately yellower than the accent) for running/warning/recording, red for failure/destructive actions, blue for info notices/badges/toasts, unread Chat results and neutral data series; each has a `-dim` tint token |

The accent is reserved for the current selection where it has an icon or underline to carry it (tab underlines, the Main menu's active icon), primary actions, focus, and genuine links. Keyboard focus on controls is a solid accent ring (`--focus-ring`); text-entry fields, which also match focus on click, use an accent border with the softer `--field-focus-ring` halo, and the Chat composer an accent border only. Elements without their own focus style (plain `<summary>` disclosures, scroll regions) fall back to a zero-specificity accent outline in `foundation.css`. Info notices, badges and chips are blue, running/recording states amber, and Calendar's "today" marker a neutral light circle; none of them use the accent. Selected rows and segments use `--selected-surface` (currently `--surface-3`) with `--text-hi` and no edge rail; list rows are marked by the surface alone and keep their text neutral, so no secondary detail outshines the name (user decision 2026-10-07). An accent stays possible where a selected item has an element meant to carry it, such as the Main menu's icon. Hover on quiet controls uses a neutral surface. Status tints use tokens or `color-mix`, never raw literals.

Semantic aliases allow controls to be restyled independently: `--field-surface` currently uses `surface-2`; `--composer-surface`, `--prompt-content-surface`, and `--preview-surface` use `surface`; `--prompt-header-surface` uses `surface-2`; `--terminal-surface` is `#0E0D0B`. Changing a semantic role has a narrower effect than changing the underlying shared surface token. Startup background continuity across the HTML entrypoint, CSS, and Desktop is an engineering concern recorded in the parent map.

The root declares `color-scheme: dark`, so native control parts the styles do not paint (number spinners, date and time picker icons, radios and checkboxes, autofill) render dark; Extension pages declare it through `app.css` too. The search fields' clear control, which the browser draws in its own colors, is filtered to a muted gray. `iframe` elements stay in the light scheme that an embedded page without its own `color-scheme` has: in a dark frame the browser would paint an opaque white canvas behind such a page instead of leaving it transparent over the frame's own background.

The metallic `V_` assets live under `webui/public/brand/`. `vbot-mark-transparent.png` is used with the app name; `vbot-icon.png` supplies the square treatment. Browser derivatives live in `webui/public/`, and Desktop icons in `desktop/`. `AppShell.svelte` owns the in-app presentation: beside the mark, the app name is a wordmark of spaced capitals in `--brand-copper` led by a `--brand-steel` initial, the mark's two metals lifted for text on the Main menu surface (user decision 2026-10-07). These are existing assets rather than instructions to redraw the mark from text.

### Typography, spacing, and depth

The bundled typefaces are Geist Sans (`--font-ui`) and Geist Mono (`--font-mono`) as local variable `woff2` files. Sans carries all interface text: labels, headings, tabs, buttons, status pills, badges, counts, dates, table headers, and names, including the names of Models, Agents, Skills, Tools, Extensions and MCP connections (user decision 2026-10-06). Mono is limited to values a user reads or copies as code: paths, URLs, commands, Tool-call arguments, code/JSON, log lines, cron expressions, error codes, and opaque ids such as Session, trace and Agent ids. A Model id is a name, not code: it renders in Sans with its provider path (`openrouter/nvidia/`) in `--text-lo`, so the Model's own name stands out. `ui/ModelId.svelte` renders this for displays and table cells (`modelIdParts` in `lib/modelSelection.js` splits the id); `SearchableDropdown` options carry the provider path as `labelLead`, which the list and the trigger show muted (every Model option from `buildModelSelectOptions` sets it). Text fields holding code values use `TextField`'s `code` variant. Labels next to code values (for example "Hooks:" on Extension rows) stay Sans. Numbers in tables and stat tiles use Sans with tabular figures. Small headings use sentence case and weight rather than uppercase letter-spaced labels. The current `--fs-*` scale runs from 12px (`mono-xs`) to 24px (`display`); body roles are 13px, 14px (the base), and 15px (Chat prose and composer). No readable text is set below 12px. Full values are in `styles/app/foundation.css`, rather than duplicated as a second token schema here.

The base `.form-field__label` is readable sentence-case Sans in `--text-hi`; `FormField.svelte` owns the associated label/help/error structure. Some feature styles still scope their own label treatments, so inspect the complete CSS cascade before changing one of these surfaces.

Named spacing anchors are 4/8/14/20/28px; component styles also use intermediate values. Rectangular corner tokens are 3/6/10px. Toggle knobs and some status/metadata markers use circular or pill treatments. Tonal surface steps and warm borders provide most depth; floating controls use elevation and explicit stacking layers. Floating panels are portaled above dialogs so a picker inside a dialog stays usable.

### Geometry and responsive behavior

The Main menu is currently 210px wide, with a 64px compact rail: optional on desktop, always used at tablet widths. Secondary panes use the shared 216px token. `AppShell.svelte`, `.secondary-pane*`, and `.secondary-list*` in `styles/app/view-surfaces.css` own the common geometry; feature components own their row contents and responsive alternatives. Every Secondary pane (Agents, Projects, Schedules, Skills, Settings, Swarm) has one anatomy (user decision 2026-10-06): the header row (`.secondary-pane__header`), then an optional pinned area for a destination or control that is not a list item (`.secondary-pane__pinned`: Agents' Shared defaults, Swarm's New Run, Settings' search), then a `--border` divider that is always present, then the scrolling list (`.secondary-pane__scroll`, which draws the divider). Group headings inside a list are `.secondary-list__group`: small `--text-lo` Sans with a trailing hairline.

Pages come in three types with one shared inset (user decision 2026-10-06; tokens in `styles/app/foundation.css`): configuration pages - every view with a Secondary pane, plus System Prompt - center their content at `--content-max-narrow` (860px); overview pages (Statistics, Logs) center at `--content-max-wide` (1180px); work areas (Terminals, Calendar, Debug) start at the page edge and use the full width. `--page-inset-top`/`-x`/`-bottom` (28/32/32px, 24/24/28 at <=960px, 16/16/24 at <=640px) pad `.view-frame` and every page scrollport, so page titles sit at the same height across tabs. A configuration page scrolls in `.page-scroll`, a centered scrollport with a stable gutter on both edges whose children are capped by `--page-measure`, which the view sets. Chat has its own user-selectable comfortable/wide/full measure (780px, 1100px, uncapped).

Common breakpoints are mobile at <=640px, tablet through 960px, desktop from 961px, and wide at 1280px. Some components respond to their own available width instead: split Chat areas stack below 760px of workspace width, and the AudioPlayer rearranges its controls at narrower component widths. Actual media/container queries and scroll owners live with the component. Mobile controls commonly grow to 40px touch targets.

Tooltip content earns its place by telling the reader something the anchor does not show. These rules apply to every quick tooltip, hover card, and InfoHint:

1. **Add information.** Repeat visible text only in full while it is truncated (`whenTruncated`).
2. **Complete values, not previews.** The tooltip receives the full value; layout does the shortening. Text shortened by characters and text clipped by layout both count as truncated.
3. **Names lead.** Ids follow as a secondary Mono row, never in place of a name.
4. **Moments are absolute and relative** (`lib/timeText.js` `formatMoment`: `Sep 29, 2026, 3:04 PM · 12 minutes ago`); states add their duration.
5. **Numbers carry their basis.** A share names numerator and denominator ("4 of 125 Runs"), a total its breakdown, a rounded value its exact figure. Labels keep an absent value apart from zero and mark a derived heuristic as such.
6. **Color-only signals are explained in words.** Every status dot, chip, or bar states what it means, since when, and why when a reason exists.
7. **Mono only for code-like values** (paths, commands, opaque ids, URLs); names, Model ids included, and prose stay Sans. Long or multi-line values a user copies go into a hover card with Copy.
8. **Definitions once, facts at the value.** What a metric means is an InfoHint on its label or column header; facts about one value go into that value's tooltip.
9. **Disabled controls say why** (`Button` `disabledReason`).
10. **Master-list rows share one details card:** the item's name as title, an optional legend (icon plus meaning, for icons the row shows) or lead line, then label/value rows; placed beside the row in a navigation pane, at the cursor in a content list (placement below).

Quick tooltips expose short labels, full truncated values, or compact details. They appear after 300ms of hover, instantly and without the entry motion while another tooltip is visible or was hidden less than 400ms ago, and instantly on keyboard focus; Escape dismisses them, and none opens while a pointer button is held. They support without obstructing: the pointer passes through them and they close shortly after it leaves the anchor, so sweeping across a list never gets caught on a bubble. Only tooltips whose text a user plausibly copies (file paths, commands, working directories) are `selectable`; they take the pointer and stay open while it travels straight toward them or while text in them is selected. Placement (user decision 2026-10-05): a control's tooltip sits at the control, above it by default. Rows in a view's content area (Checkbox selection groups such as Skills and Sub-Agent targets, Skill library and archived rows) stick it to the cursor: below the pointer, following it across the row, above it near the bottom edge, and below the row's name on keyboard focus (`placement: 'pointer'`). A bubble beside its anchor is the exception, kept only where it was asked for: master lists in navigation panes (Sessions, Projects, Agents, Schedules, Swarm Runs, Debug traces, Skills collections) and the compact Main menu rail place tooltips to the right, and the Chat Activity panel at the right edge, including its Session information, places them to the left. Do not extend the side placement to content lists. Tooltips that only repeat a row's own text show only while that text is truncated. Session rows show a details card (name; last activity and creation as absolute and relative moments; source channel; the parent or fork source by name and Agent, or by Agent and Session id when it is not listed); the unread marker adds the unread Run's result and finish time, and the filter trigger names the categories it currently reveals. Schedule rows show the same kind of card (last error as lead text, status with its tone and failure streak, cadence and expression, next Run, last result, target Agent and Session). Agent activity tooltips lead with the name, then the activity in words, the Model and thinking effort, and a differing id. Hover cards hold richer or interactive content (Copy, Open Extensions, full queued text, image previews, changed-file lists), may open only while their anchor clips its text (`whenTruncated`), open after 300ms (500ms for Chat Tool values), stay open while the pointer travels toward them, close at once when it heads elsewhere, and let Tab move from the anchor into their controls. The InfoHint popover previews on hover or focus and pins on click or tap. The changed-files card (`ChangeStats.svelte`, shared by the Run footer and, listed in place as its `list` mode with the shared directory on one line, the Session information Changes card) heads with the file count and colored totals, names the shared directory once in quiet Mono, and groups the files by folder: each folder row (icon, relative folder that loses its start when too long, file count, quiet line sums) heads its indented files, and files directly in the shared directory come first without a folder row. File rows use aligned Mono columns: full name (a clipped name shows its path on hover), per-file `+X` and `-Y` (blank for Runs recorded before per-file counts; a column no file has is left out), and a row Copy action for the full path that appears on row hover or focus and stays visible without hover. Zero counts are dimmed; the card grows up to 680px wide and 75% of the viewport high, and the list scrolls under a fixed header. Chat's copyable-value card (`chat/CopyableValueCard.svelte`: Tool values, Sub-Agent tasks, Activity panel task names and commands) shows an optional quiet title, the complete value (Mono only for code-like values) and a Copy action. Only one of these layers is open at a time, except that a pinned InfoHint stays while quick tooltips and hover cards come and go. Presentation-only labels do not replace accessible names. Behavior, integration, and cleanup details are in `source-map.md`.

Autosaved configuration editors, Extension pages included, end with a quiet save state (`SaveStatus.svelte`): nothing at rest, a small Save action only while a draft is unsaved, "Saving..." during a write, and a green check with "Saved" that fades after a successful one; the rules are in `autosave.md`. Agents derive "pending" from the full form draft, so a Workspace change that autosave deliberately skips still offers Save. Entity creation, destructive confirmations, and write-only secrets use explicit operations. Draft preservation and navigation flushing are behavioral contracts: their owner and failure handling are in `settings.md` and `app-shell.md`.

## Current view patterns

### First-run setup

`OnboardingView.svelte`, `OnboardingProviders.svelte` and `styles/onboarding.css` use a compact header, horizontal two-step progress and a single working panel. One searchable, alphabetically ordered catalog contains API-key, account-sign-in and local Providers. It initially shows ten complete entries (three in a narrow catalog) with an explicit Show all/Show fewer control; search always includes the entire catalog. Expanding focuses the first newly revealed available Provider. The list grows in the view's scroll area instead of clipping entries inside a nested scrollport; search stays visible while scrolling through the catalog. Provider selection precedes method selection. Connected status stays visible in the list and a separate summary; adding a connection does not advance the guide. Model selection offers a Provider picker, readable Model names with exact ids as secondary text, an explicit free filter and a selection summary before completion. Narrow containers use one Provider column and full-width continuation. The view owns scrolling, keyboard step focus and reduced-motion styling. Setup uses a simplified variant of the shared Provider dialog. Behavioral ownership and tests: `settings.md`.

### Navigation and action placement

The Main menu groups destinations by subject (user decision 2026-10-07): Chat, Terminals and Extension pages first without a heading, then Agents (Agents, Skills, System Prompt, Projects), Planning (Schedules, Calendar) and System (Statistics, Logs, Debug) under small sentence-case Sans headings, and Settings after System behind a hairline instead of a heading (a `divided` group); the active item uses a raised surface, bright text, and an accent icon. The compact mode hides text and separates later groups with small hairlines; its toggle sits at the end of the brand row. At tablet widths the rail is always shown and its toggle unfolds the full menu as an elevated overlay above a light scrim, leaving the content size unchanged. On mobile a bottom tab bar shows Chat, Terminals, Agents, and Calendar plus More, which opens every destination as a bottom sheet. The optional Live voice control sits above the connection/microphone indicators. The connection row's card (in both rail modes) names the state, the server host and since when the state holds (the first state counts from page load); the microphone's card adds what a click does. `AppShell.svelte`, `LiveVoice.svelte`, and `app.css` own these surfaces; lifecycle details are in `app-shell.md` and `../model_tasks/live.md`.

Standalone views share one page-header pattern: a display-size title and an optional one-line description, without an eyebrow above it (`.view-frame`, `.view-header__title`, `.view-header__subtitle`). Secondary panes share one header: a 50px row (the height of the Chat and Terminals top bars) with a 14px `--text-hi` Sans title at the start and a compact icon action (usually a plus with an accessible name and tooltip) at the end; the pane title matches the Main menu label (for example "Schedules"). Settings' index uses the same header row. `.view-toolbar*` groups tabs and filters without a boxed frame. Existing shared action-group styles align controls right, and `.view-toolbar--split` separates groups with space-between. Settings list heads likewise currently place counts and actions at opposite ends. These styles explain the existing appearance; they are not prescriptions for a new or redesigned view.

The user's expressed direction is to avoid page-level action clusters at the top right and unnecessary permanently labelled buttons. The Skills manager applies that direction with one plus menu next to search, list rows without actions, and no Refresh button. Other existing placements have not thereby been approved or scheduled for an automatic redesign. A Refresh control's presence elsewhere is not evidence that a new view needs one; inspect its actual loading and invalidation behavior.

### Skills

`components/skills/SkillsView.svelte` pairs a collection sidebar (headed "Skills"; Library: All skills / Global / Bundled / Shared skills / Archived; then Agents and Projects, each entry with the number of Skills active there; an entry's tooltip names what its count counts) with a toolbar and the content. Section headings are the shared `.secondary-list__group` headings with a trailing hairline; there is no sidebar action footer. At <=960px one Dropdown replaces the sidebar, its options grouped under the same section labels with counts. The main header uses the shared page-header classes and has no actions except Back on the Skill folders page. The toolbar starts with one plus menu ("Install from link or file...", "Create skill...", "Manage skill folders...") before search; the Library adds a status filter. Install offers link/upload tabs and a global/private destination; source checking previews one package or offers a candidate picker, and replacing different files requires an explicit switch. Manage skill folders focuses the existing new-directory draft.

The Library list is one bordered group with a quiet result count above it and at most 50 rows per page. Each row is a single line (about 40px, 44px on phones): a name part that is the button opening the package, with the name, at most one status marker (a status chip, or a "Requirement notes" badge) and, at its end, muted, a source label ("Private", "Project", "Bundled", "<name> extension", a humanized folder name, or "Global") and an access summary ("2 of 3 Agents", "Main + 1 shared", "Off for Main", "Active in Repo", "Off everywhere"); then the row's own controls, always visible (user requirement 2026-10-05: actions must not hide behind a right click): a small on/off Toggle, a tertiary Edit (pencil) icon and a tertiary Delete (trash) icon whose glyph turns `--red` on hover. A read-only package keeps Edit and Delete in place but disabled, with the reason as their tooltip, so every row's controls line up. Archived rows end in a tertiary Restore and the Delete permanently icon instead. Phones drop the source label so rows stay single-line. A disabled Skill keeps its row with a receding name. Event and Agent job dialogs use the shared `Dropdown`, not native selects. Calendar behavior is in `../calendar.md`.

The event form (`lib/calendarEventForm.js`) shows a timed event's start and end on the server zone's wall clock, converted from the event's `tz_name`, and sends them as naive server-local times, so a save without edits keeps the wall clock; an all-day event's last day is sent as the exclusive end. The WebUI reads an event's Agent jobs from `cron.list` (schedule type `event`) and leaves `calendar.window` Cron rows with an `event_id` out of the Schedules layer, so an Agent job shows only on its event. The view's place (`app-shell.md` -> Navigation) is `[mode, 'YYYY-MM-DD']` (mode `month`, `week`, `day` or `agenda`); Prev, Next, Today and each mode tab are history steps, layer toggles are not. Before the first response establishes the zone, the view may make a provisional UTC-window request; an empty place is corrected to today in the server zone only once that zone is known, and an explicit day in the place is never moved. Agenda navigation always derives its window from the displayed anchor.

### Statistics, Logs, and server feedback

Statistics is the overview page, centered at `--content-max-wide`. It shows its header, content tabs (Overview, Costs & tokens, Runs, Tools & skills, Limits, Extensions, Diagnostics) and range toolbar (24 hours, 7 days, 30 days, 90 days, All time; default 30 days, remembered across visits) from first paint; Limits hides the range toolbar. Each tab loads only its own report sections, so a revisited tab or range shows its last numbers at once while they revalidate behind a quiet pulse on the toolbar; a tab's first load shows a layout-shaped skeleton, and a failure shows an error Banner with Retry above any stale numbers instead of blanking them. The Extensions tab appears only when the range's report lists Extension activity. Content leads with cost: Overview has KPI tiles (Cost with its reported/estimated split and an amber marker beside the label when calls without cache data may overstate the estimate, Tokens, Cache hit rate, Runs, Typical Run, Cost per Run) with the change against the previous period (arrow plus % or percentage points, neutral except the judged failure rate), a trend chart with Cost/Tokens/Runs and Day/Week/Month switches (pressed-button groups, `.stats-toggle`, styled like the segmented `TabList`, as is the range toolbar) (a range of up to two days counts by the hour, labelled in the Settings time zone, without the period switch), whose tooltip and data table list the Runs started per period beside Cost and Tokens (also on Costs & tokens), a row of Cost by origin, Top Agents and Top Models with "All" links that open Costs & tokens on that dimension, and "Worth a look" lines linking to the tab that explains them. Costs & tokens puts one breakdown table behind a dimension switch; it is the only tab that explains pricing coverage (unpriced, retrospective and unreported calls, uncached value); the Runs tiles (Runs, Completed, Failed, Cancelled, Your Runs) carry the same previous-period changes, with only the Failed tile's failure rate judged; Runs, Tools & skills and Diagnostics follow tiles with tables; long or rare lists (expensive Runs and Sessions, recent calls, pricing coverage, rejection codes, everything in Diagnostics) sit in collapsed disclosures that use the app-wide summary chevron. Every table is the shared `DataTable` (sortable, filter and Show all where long): text columns start-aligned, numbers end-aligned with tabular figures, Mono only for codes (rejection codes); names, Model ids (provider path muted) and table dates stay on one line, names and ids shortened with the full value on hover, dates as "Sep 30, 9:30 AM" in the Settings time zone (with the year outside the current year) and the full moment on hover. Overview's top lists use a fixed-layout compact table so their cost column stays in view, Run tables shorten Run and Model names sooner so their ten columns fit a desktop-wide view, and Diagnostics' Data quality table wraps its column labels to fit one and keeps its Model column in place while it scrolls sideways on a narrower view. Numbers: compact tokens (1.2M) with the exact count on hover or focus, estimated parts included and unmarked (whether a Provider reported or vBot estimated token counts is rarely of interest, so it stays in Diagnostics' Data quality table and the per-call cost tooltip); costs with two decimals, `<$0.01` for tiny non-zero amounts, `$0.00` for zero and a dash for unknown, with the exact amount or cost basis in tooltips and exact amounts in per-call rows; percentages with one decimal. Origins have translated labels (You, Sub-agents, Extensions, Automation, Channels, Reflection, System, Background); recorded Run error kinds have translated names (Rate limit, Authentication failed, ...; a kind without a label reads as its id in words) with the recorded kind as a Mono row on hover. Agent cells lead with the name and keep their Project or Extension badge whole; where the column width is set (compact tables, bar lists) the badge shortens faster than the name; calls made outside any Session (an empty Agent key) read "Outside a Session". A failed hour lists its first three Models and Agents with their counts and the rest behind a "+N" with a details card. Bar lists align their bars across rows; Cost by origin lists the largest cost first, and its InfoHint says it covers every Model request including background work outside Runs, while the Runs tab's cost columns read "Run cost" with an InfoHint that they cover only requests made inside Runs. Charts label columns at one regular stride that ends at the latest column, as many as their width leaves room for, and count axes (Runs, durations, errors by hour) keep whole-number ticks. Chart columns and Limit-history snapshots are focusable and open a details card; each Limit-history trace keeps one Tab stop that arrow keys move between snapshots. Limits shows at most 10 overlapping Runs with a Show all toggle and keeps Delete history as a quiet action at the end of the history. Layout steps follow the view's own width (container queries), not the window, so the sidebar cannot squeeze three-abreast rows; tiles and rows stack on narrow views, wide tables and switches scroll inside their block, and the page never scrolls sideways. Owners: `StatisticsView.svelte` (shell state), one component per tab under `components/statistics/` with private `statistics/report/` components for shared tiles, names, cells and bar lists and `report.css`, `lib/statisticsView.js`, `lib/statisticsReports.svelte.js`, and their tests.

Logs is an overview page centered at the wide measure like Statistics. It uses compact Mono rows with timestamp, level, logger, and the entry's header message; a multi-line entry (a traceback) adds a quiet `+N lines` count. A click anywhere on a row (not a drag that selects text) or its leading disclosure chevron expands the whole entry below the summary as a selectable, wrapped, preformatted block inset like a code block (`--bg`, `--border`, `--r-md`). The list sits in one framed panel (`--surface`, `--border`, `--r-lg`) and rows show a `--surface-2` hover background, and on phone widths the expanded block replaces the already wrapped summary message. The chevron stays visible on multi-line and expanded rows and otherwise appears with Copy on hover or keyboard focus (always on phone widths). Log rows carry no quick tooltip except the full logger name while it is truncated. On phone widths search stays inline beside a Filters disclosure that shows how many of file/level/order differ from their defaults; those three controls open below it. Levels carry their color in the level column (WARN amber, ERROR/CRITICAL red) with a thin left marker; only error rows get a subtle red tint, so routine warnings do not color the whole list. Row-local disclosure and Copy button sizing overrides the shared minimum height so the controls do not stretch desktop rows. File/level/order/search controls sit above the list. A centered secondary "Load older entries" button follows the oldest row (below the list newest-first, above it oldest-first, and as the empty state's action when no loaded entry matches); once the view holds its maximum a quiet note replaces it. It loads and follows data automatically and exposes Retry on failure, without a generic header Refresh control; the header's live-update chip explains its state (live, connecting, reconnecting with catch-up, failed, idle) in a tooltip. `LogsView.svelte`, `logs/LogsEntry.svelte`, `logsView.js`, and `../logs.md` own this surface; live-log behavior is separate from ordinary app invalidation.

The AppShell server-availability popup is a global floating surface with connection state, details, and Retry; Desktop can also offer Switch server. Navigation stays available while server-dependent content is inert. A short grace period avoids transient flashes, and recovery briefly displays success. Timing, suppression of duplicate errors, reconnect, and Desktop capability behavior belong to `app-shell.md` and `settings.md`.

### Swarms

The bundled Swarm page pairs a Secondary pane with the work area. The pane header "Swarms" ends in a plus icon button (tooltip "New Swarm") that opens a new Swarm's editor; "New Run" is the pinned row under it, styled like Agents' Shared defaults and marked current while the start form shows. The pane lists the Swarms, then the Runs under the small group headings "Active Runs" (preparing, running, stopping, idle and needs-attention Runs, so a Run that waits for messages or for the user stays in view) and "Inactive Runs", each with a compact EmptyState when it is empty. Rows have two lines: a Swarm's name over its size and Model (`6 participants · perf-model`), a Run's state dot and title over its state and start (`Interrupted · 15 hours ago`); their tooltips are details cards, and their context menus only repeat actions reachable elsewhere. At <=640px of iframe width one bar above the work area replaces the pane, as a picker replaces the sidebar in Skills and Settings: a searchable picker filling the row, then the New Swarm plus button. The picker lists New Run, then the Swarms, Active Runs and Inactive Runs as labelled groups, shows each row's second line under its name and loads more Swarms and Runs from its footer; its value is what the work area shows. The start form ("Give the group a goal") and the Run view are centred at the configuration measure and use the shared page header without an eyebrow. The form asks for the Swarm, the working directory (the shared `PathField`) and the goal; Start Run stays enabled while only fields are missing, and a click shows each missing value's error under its field and focuses the first, so the page's error Banner is left to failed requests. The Run view's header names the Run by its title as plain text, then `Research · started 2 hours ago · 6 participants` with the absolute moment in the time's tooltip, then one row with the state chip, at most one lifecycle button (Stop while anything works, otherwise Resume, primary when the Run needs attention or was interrupted) and a `⋯` menu (`Communication settings…` for open Runs, Run details, `Delete…`). A warning notice below the header names failed or interrupted participants as links to their Activity and carries Resume while others still work. The tab row (Board, Wiki, Activity, Usage) sticks at the top of the view on the page background while a panel scrolls; sticky bars inside the panels stick below it. Run details is a dialog with label/value facts (Swarm, start, state, participants, settings revision, a copyable Run id), the participants and a closed "Swarm snapshot" disclosure with Copy. Deleting a Run or a Swarm goes through the shared `ConfirmDialog` naming its target, and a failed deletion stays in the dialog for another try; a Run's `Delete…` is disabled with "Stop the Run first" while anything works. The Board tab starts with one toolbar row: a searchable discussion picker (titles with a muted `dN`; the server's "Main" reads "Main discussion"; "Load more discussions" is its footer action) and a secondary Write post button. Below it the goal is a framed, collapsible "Goal" card whose closed summary shows the goal's first line; the working directory is one Mono line elided in the middle, with the full path in its tooltip and a Copy action. The discussion's participants follow as outlined chip buttons: an unframed initials avatar in the participant's identity colour, the name, and a state dot unless the participant is idle. A post header shows the avatar (a person icon and "You" for the user's posts), the name, a muted `#N`, the short time (the time for today, otherwise the date) with absolute and relative moment in its tooltip, and a Reply icon that appears on hover or focus and always on touch screens.
