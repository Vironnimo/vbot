# WebUI Visual State

Task-specific companion to `../webui.md`: the implemented appearance and interaction patterns, with pointers to their owners.

## How to use this description

This is a description of the current implementation, not a design specification, quality endorsement, or template for new work. Existing colors, typography, dimensions, layouts, action placement, and information hierarchy are all open to revision within the user's requested scope. Changing them does not require an exception to this document. A previous implementation becoming documented does not make it an approved design constraint.

Read the relevant sections when the task needs visual context, such as changing shared styling, understanding an existing layout, or assessing a redesign. This companion is not an additional prerequisite for every WebUI task. Source code remains the authority for implemented behavior. Screenshots and browser checks establish what the current interface actually looks like; a passing component test does not establish design quality.

The parent map separately records engineering contracts such as server-owned state, accessibility, draft preservation, and shared-component integration. Those contracts do not prescribe a layout. Explicit user requirements remain distinguishable from implementation observations; record a new visual constraint only when the user establishes it as one. Update the affected observations after a change without turning the new arrangement into a requirement for other views.

Paths beginning `webui/`, `desktop/`, or `resources/` are repository-relative. Other map links are relative to this file. Short component/lib names identify their owners under `webui/src/`; `source-map.md` supplies the detailed source routing. The source and test references below are starting points, not a claim that every current screen has been visually approved.

## Shared appearance

### Tokens and assets

`webui/src/styles/app.css` is the ordered stylesheet entrypoint; its private `app/foundation.css` owns the implemented CSS tokens and bundled font declarations, while adjacent `app/` files own primitive styles and app-shell geometry. There is no separate machine-consumed token catalog in this map. `webui/src/styles/settings.css`, `projects.css`, and `cron.css`, plus component-local styles, specialize those foundations.

The current palette is a warm, low-chroma graphite with a single orange accent. Hierarchy reads from clearly separated surface tones rather than from border lines. The main surface roles are:

| Role | Current implementation |
|---|---|
| Page background | `--bg`, `#15130F` |
| Main menu and Secondary panes | `--secondary-surface`, `#1A1814` |
| Surface steps | `--surface`, `--surface-2`, `--surface-3`: `#1E1B17`, `#26231E`, `#302C26` |
| Structural and control borders | `--border`, `--border-2`: `#2E2A25`, `#423C35` |
| Text levels | `--text-hi`, `--text-med`, `--text-lo`: `#F1EDE6`, `#B3AA9E`, `#9D9387` (all WCAG AA on bg and every surface step, including `--surface-3`); `--text-faint` `#6B635A` only for decoration, separators, and disabled glyphs |
| Interaction accent | `--accent`, `#E8870A`, with `color-mix` opacity steps and `--on-accent` for text on a solid accent fill |
| Status colors | Green for success, amber (`#E5B53E`, deliberately yellower than the accent) for running/warning/recording, red for failure/destructive actions, blue for info notices/badges/toasts, unread Chat results and neutral data series; each has a `-dim` tint token |

The accent is reserved for the current selection (a 2-3px rail or underline, or the active icon), primary actions, focus, and genuine links. Keyboard focus on controls is a solid accent ring (`--focus-ring`); text-entry fields, which also match focus on click, use an accent border with the softer `--field-focus-ring` halo, and the Chat composer an accent border only. Elements without their own focus style (plain `<summary>` disclosures, scroll regions) fall back to a zero-specificity accent outline in `foundation.css`. Info notices, badges and chips are blue, running/recording states amber, and Calendar's "today" marker a neutral light circle; none of them use the accent. Selected rows and segments use `--surface-3` with `--text-hi`; hover on quiet controls uses a neutral surface. Status tints use tokens or `color-mix`, never raw literals.

Semantic aliases allow controls to be restyled independently: `--field-surface` currently uses `surface-2`; `--composer-surface`, `--prompt-content-surface`, and `--preview-surface` use `surface`; `--prompt-header-surface` uses `surface-2`; `--terminal-surface` is `#0E0D0B`. Changing a semantic role has a narrower effect than changing the underlying shared surface token. Startup background continuity across the HTML entrypoint, CSS, and Desktop is an engineering concern recorded in the parent map.

The metallic `V_` assets live under `webui/public/brand/`. `vbot-mark-transparent.png` is used with the app name; `vbot-icon.png` supplies the square treatment. Browser derivatives live in `webui/public/`, and Desktop icons in `desktop/`. `AppShell.svelte` owns the in-app presentation. These are existing assets rather than instructions to redraw the mark from text.

### Typography, spacing, and depth

The bundled typefaces are Geist Sans (`--font-ui`) and Geist Mono (`--font-mono`) as local variable `woff2` files. Sans carries all interface text: labels, headings, tabs, buttons, status pills, badges, counts, dates, and table headers. Mono is limited to code-like values: ids, paths, URLs, Model ids, commands, code/JSON, Tool calls, log lines, and cron expressions. Text fields holding such values use `TextField`'s `code` variant; `SearchableDropdown` renders options flagged `code: true` (every Model option from `buildModelSelectOptions`) and their trigger label in Mono, while placeholder options such as "Inherit global default" stay Sans. Labels next to code values (for example "Hooks:" on Extension rows) stay Sans. Numbers in tables and stat tiles use Sans with tabular figures. Small headings use sentence case and weight rather than uppercase letter-spaced labels. The current `--fs-*` scale runs from 12px (`mono-xs`) to 24px (`display`); body roles are 13px, 14px (the base), and 15px (Chat prose and composer). No readable text is set below 12px. Full values are in `styles/app/foundation.css`, rather than duplicated as a second token schema here.

The base `.form-field__label` is readable sentence-case Sans in `--text-hi`; `FormField.svelte` owns the associated label/help/error structure. Some feature styles still scope their own label treatments, so inspect the complete CSS cascade before changing one of these surfaces.

Named spacing anchors are 4/8/14/20/28px; component styles also use intermediate values. Rectangular corner tokens are 3/6/10px. Toggle knobs and some status/metadata markers use circular or pill treatments. Tonal surface steps and warm borders provide most depth; floating controls use elevation and explicit stacking layers. Floating panels are portaled above dialogs so a picker inside a dialog stays usable.

### Geometry and responsive behavior

The Main menu is currently 210px wide, with a 64px compact rail: optional on desktop, always used at tablet widths. Secondary panes use the shared 216px token. `AppShell.svelte`, `.secondary-pane`, and `.secondary-list*` own the common geometry; feature components own their row contents and responsive alternatives.

Many editors use centered inner measures: `--content-max-narrow` is 920px and `--content-max-wide` is 1180px. Chat has a user-selectable comfortable/wide/full measure; the first two use 780px and 1100px. These are existing choices, not a ban on full-width work areas: Terminals and wide data surfaces have different needs and layouts.

Common breakpoints are mobile at <=640px, tablet through 960px, desktop from 961px, and wide at 1280px. Some components respond to their own available width instead: split Chat areas stack below 760px of workspace width, and the AudioPlayer rearranges its controls at narrower component widths. Actual media/container queries and scroll owners live with the component. Mobile controls commonly grow to 40px touch targets.

| Checkboxes | `Checkbox.svelte` renders a `role="checkbox"` button with a 16px box that fills with `--accent` and a check when selected. `indeterminate` shows a dash for a partly selected group (`aria-checked="mixed"`); choosing it selects every member. Use it for actions on the one item under the pointer or keyboard focus; choosing a value stays a picker. Caller pattern: the row's `oncontextmenu` calls `event.preventDefault()` and sets `menu = { ...contextMenuAnchor(event), label, items }`; its keydown does the same when `isContextMenuKey(event)` (ContextMenu key, Shift+F10); `onClose` clears `menu`. | Tabs | `TabList.svelte` has underline and segmented treatments, with a compact density option. Period filters and Chat Agent navigation (picker and Project Team bar) are separate controls. |
| Tables | `DataTable.svelte` renders data tables in a keyboard-scrollable region: text columns start-aligned, numbers end-aligned in Sans with tabular figures, Mono only for code-like columns; small `--text-lo` header labels above a hairline, hairline-separated rows with a `--surface-2` hover band. A sortable header is a button whose hit area covers the header cell; a small chevron shows the active direction and, on the other columns, previews on hover or focus the direction a click chooses; numeric columns lead with it so the label ends flush with its numbers. The header cell carries `aria-sort`, and a column can add an InfoHint. An optional search field above the table shows "N of M" while filtering; a limited table ends with a quiet tertiary "Show all N" / "Show fewer" toggle; activatable rows get a pointer and an inset accent focus ring; a totals footer row is semibold above a stronger hairline; a height-bounded table keeps its header row sticky. | State and metadata | `StatusChip.svelte` represents status; `Badge.svelte` represents kind/origin/version/scope. Most are text pills; Session drawer metadata uses compact accessible icon badges. |
| Inline feedback | `Banner.svelte` displays loading, errors, warnings, and notices using a surface with a 3px semantic left stripe. Its compact appearance shares the quiet composer surface and tertiary action sizing between Queue rows and Chat context notices. `EmptyState.svelte` displays known absence with a quiet dashed frame when inline or compact; its `fill` variant for a whole work area is frameless centered copy, usually with an action. |

| Tooltips and hints | Three layers on one floating infrastructure (`lib/tooltip.js`): Quick tooltips (compact `.floating-tooltip` bubble: `--surface-3`, `--border-2`, `--r-md`, 12.5px Sans, max 320px, wraps and scrolls), Hover cards and the `InfoHint.svelte` question-mark popover (`.floating-card`: `--surface-2`, `--border-2`, `--r-lg`, 12px padding, 13px Sans). No native browser title bubbles. A details tooltip (`.app-tooltip--rich`, max 360px, `--r-lg`) adds a 13px semibold title and a two-column grid of `--text-lo` labels and tabular values; lead text after the title is `--text-med`, and a hairline separates lead text from the rows. Code-like values (paths, commands, ids, Models) use the mono face. A long non-selectable label is clipped with a bottom fade instead of scrolling. |
| Disclosures | One marker everywhere: a small chevron pointing right when closed and down when open. Plain `<summary>` elements get it from `controls.css`; custom disclosure buttons render `<span class="disclosure-chevron">` (`--open` modifier); Settings entity rows use the borderless `.s-disclosure-btn` chevron button (28px, 40px on phones). Dialog and toast close buttons use the same SVG X icon. |
| Audio | `AudioPlayer.svelte` provides a bounded playback surface with Play/Pause, progress/time, speed, mute, volume, and download. Secondary controls wrap as the component narrows; inline failure leaves playback retry reachable. |

Tooltip content earns its place by telling the reader something the anchor does not show. These rules apply to every quick tooltip, hover card, and InfoHint:

1. **Add information.** Repeat visible text only in full while it is truncated (`whenTruncated`).
2. **Complete values, not previews.** The tooltip receives the full value; layout does the shortening. Text shortened by characters and text clipped by layout both count as truncated.
3. **Names lead.** Ids follow as a secondary Mono row, never in place of a name.
4. **Moments are absolute and relative** (`lib/timeText.js` `formatMoment`: "Sep 29, 2026, 3:04 PM · 12 minutes ago"); states add their duration.
5. **Numbers carry their basis.** A share names numerator and denominator ("4 of 125 Runs"), a total its breakdown, a rounded value its exact figure.
6. **Color-only signals are explained in words.** Every status dot, chip, or bar states what it means, since when, and why when a reason exists.
7. **Mono only for code-like values** (paths, commands, ids, URLs, Model ids); prose stays Sans. Long or multi-line values a user copies go into a hover card with Copy.
8. **Definitions once, facts at the value.** What a metric means is an InfoHint on its label or column header; facts about one value go into that value's tooltip.
9. **Disabled controls say why** (`Button` `disabledReason`).
10. **Master-list rows share one details card:** the item's name as title, an optional lead line, then label/value rows, placed beside the row.

Quick tooltips expose short labels, full truncated values, or compact details. They appear after 300ms of hover, instantly and without the entry motion while another tooltip is visible or was hidden less than 400ms ago, and instantly on keyboard focus; Escape dismisses them, and none opens while a pointer button is held. They support without obstructing: the pointer passes through them and they close shortly after it leaves the anchor, so sweeping across a list never gets caught on a bubble. Only tooltips whose text a user plausibly copies (file paths, commands, working directories) are `selectable`; they take the pointer and stay open while it travels straight toward them or while text in them is selected. Rows of vertically swept lists (Sessions, Schedules, Projects, Skills collections and Skill rows, Swarm runs, Debug traces) and the compact Main menu rail place tooltips to the right; Chat Activity panel controls at the right edge place them to the left. Tooltips that only repeat a row's own text show only while that text is truncated. Session rows show a details card (name; last activity and creation as absolute and relative moments; source channel; the parent or fork source by name and Agent, or by Agent and Session id when it is not listed); the unread marker adds the unread Run's result and finish time, and the filter trigger names the categories it currently reveals. Schedule rows show the same kind of card (last error as lead text, status with its tone and failure streak, cadence and expression, next Run, last result, target Agent and Session). Agent activity tooltips lead with the name, then the activity in words, the Model and thinking effort, and a differing id. Hover cards hold richer or interactive content (Copy, Open Extensions, full queued text, image previews, changed-file lists), may open only while their anchor clips its text (`whenTruncated`), open after 300ms (500ms for Chat Tool values), stay open while the pointer travels toward them, close at once when it heads elsewhere, and let Tab move from the anchor into their controls. The InfoHint popover previews on hover or focus and pins on click or tap. The changed-files card (`ChangeStats.svelte`, shared by the Run footer and the Session information stats) heads with the file count and colored totals, names the shared directory once in quiet Mono, and groups the files by folder: each folder row (icon, relative folder that loses its start when too long, file count, quiet line sums) heads its indented files, and files directly in the shared directory come first without a folder row. File rows use aligned Mono columns: full name (a clipped name shows its path on hover), per-file `+X` and `-Y` (blank for Runs recorded before per-file counts; a column no file has is left out), and a row Copy action for the full path that appears on row hover or focus and stays visible without hover. Zero counts are dimmed; the card grows up to 680px wide and 75% of the viewport high, and the list scrolls under a fixed header. Chat's copyable-value card (`chat/CopyableValueCard.svelte`: Tool values, Sub-Agent tasks, Activity panel task names and commands) shows an optional quiet title, the complete value (Mono only for code-like values) and a Copy action. Only one of these layers is open at a time, except that a pinned InfoHint stays while quick tooltips and hover cards come and go. Presentation-only labels do not replace accessible names. Behavior, integration, and cleanup details are in `source-map.md`.

Autosaved configuration editors, Extension pages included, end with a quiet save state (`SaveStatus.svelte`): nothing at rest, a small Save action only while a draft is unsaved, "Saving..." during a write, and a green check with "Saved" that fades after a successful one; the rules are in `autosave.md`. Agents derive "pending" from the full form draft, so a Workspace change that autosave deliberately skips still offers Save. Entity creation, destructive confirmations, and write-only secrets use explicit operations. Draft preservation and navigation flushing are behavioral contracts: their owner and failure handling are in `settings.md` and `app-shell.md`.

## Current view patterns

### First-run setup

`OnboardingView.svelte`, `OnboardingProviders.svelte` and `styles/onboarding.css` use a compact header, horizontal two-step progress and a single working panel. One searchable, alphabetically ordered catalog contains API-key, account-sign-in and local Providers. It initially shows ten complete entries (three in a narrow catalog) with an explicit Show all/Show fewer control; search always includes the entire catalog. Expanding focuses the first newly revealed available Provider. The list grows in the view's scroll area instead of clipping entries inside a nested scrollport; search stays visible while scrolling through the catalog. Provider selection precedes method selection. Connected status stays visible in the list and a separate summary; adding a connection does not advance the guide. Model selection offers a Provider picker, readable Model names with exact ids as secondary text, an explicit free filter and a selection summary before completion. Narrow containers use one Provider column and full-width continuation. The view owns scrolling, keyboard step focus and reduced-motion styling. Setup uses a simplified variant of the shared Provider dialog. Behavioral ownership and tests: `settings.md`.

### Navigation and action placement

The Main menu groups Work, Configure, and Insights under small sentence-case Sans headings; the active item uses a raised surface, bright text, and an accent icon. The compact mode hides text and separates later groups with small hairlines; its toggle sits at the end of the brand row. At tablet widths the rail is always shown and its toggle unfolds the full menu as an elevated overlay above a light scrim, leaving the content size unchanged. On mobile a bottom tab bar shows Chat, Terminals, Agents, and Calendar plus More, which opens every destination as a bottom sheet. The optional Live voice control sits above the connection/microphone indicators. The connection row's card (in both rail modes) names the state, the server host and since when the state holds (the first state counts from page load); the microphone's card adds what a click does. `AppShell.svelte`, `LiveVoice.svelte`, and `app.css` own these surfaces; lifecycle details are in `app-shell.md` and `../model_tasks/live.md`.

Standalone views share one page-header pattern: a display-size title and an optional one-line description, without an eyebrow above it (`.view-frame`, `.view-header__title`, `.view-header__subtitle`). Secondary panes share one header: a 52px row with a 14px `--text-hi` Sans title at the start and a compact icon action (usually a plus with an accessible name and tooltip) at the end; the pane title matches the Main menu label (for example "Schedules"). Settings' index uses the same header row. `.view-toolbar*` groups tabs and filters without a boxed frame. Existing shared action-group styles align controls right, and `.view-toolbar--split` separates groups with space-between. Settings list heads likewise currently place counts and actions at opposite ends. These styles explain the existing appearance; they are not prescriptions for a new or redesigned view.

The user's expressed direction is to avoid page-level action clusters at the top right and unnecessary permanently labelled buttons. The Skills manager applies that direction with one plus menu next to search, list rows without actions, and no Refresh button. Other existing placements have not thereby been approved or scheduled for an automatic redesign. A Refresh control's presence elsewhere is not evidence that a new view needs one; inspect its actual loading and invalidation behavior.

### Skills

`components/skills/SkillsView.svelte` pairs a collection sidebar (Library: All skills / Global / Bundled / Shared skills / Archived; then Agents and Projects, each entry with the number of Skills active there; an entry's tooltip names what its count counts) with a toolbar and the content. Section headings are emphasized with an adjacent separator; there is no sidebar action footer. At <=960px one Dropdown replaces the sidebar, its options grouped under the same section labels with counts. The main header uses the shared page-header classes and has no actions except Back on the Skill folders page. The toolbar starts with one plus menu ("Install from link or file...", "Create skill...", "Manage skill folders...") before search; the Library adds a status filter. Install offers link/upload tabs and a global/private destination; source checking previews one package or offers a candidate picker, and replacing different files requires an explicit switch. Manage skill folders focuses the existing new-directory draft.

The Library list is one bordered group with a quiet result count above it and at most 50 rows per page. Each row is a single-line button (about 40px, 44px on phones): the Mono name with at most one status marker (a status chip, or a "Requirement notes" badge), then at the end, muted, a source label ("Private", "Project", "Bundled", a humanized folder or Extension name, or "Global") and an access summary ("2 of 3 Agents", "Main + 1 shared", "Off for Main", "Active in Repo", "Off everywhere"); phones drop the source label so rows stay single-line. A disabled Skill keeps its row with a receding name. Rows sit inset in their group: hover is one rounded `--surface-2` band over the whole row (checkbox included in Checkbox rows) without layout shift, keyboard focus is the same band with an inset `--accent` ring, and the package opened last keeps an `--accent-08` band after returning to the list. Agent and Project collections show the Checkbox group panel described under Agents below, in one column, with the "Add new skills automatically" switch and InfoHint in the Agent panel's count line; a locked row (a Project grant) explains in its tooltip why it is fixed and where to change it.

**Descriptions only in tooltips (explicit user requirement, 2026-09-29).** No Skill list shows a Skill description inline: not the Library, not the Agent or Project collections, not the Skill panels of the Agents and Projects editors, not the Access rows of a Skill page. The description appears only in the row's quick tooltip on hover and keyboard focus, placed to the right beside the name (`alignTo`, see `source-map.md`); a Library row's tooltip is a details card led by the description, adding the full source, who gets the package and its requirement notes, and a Checkbox row's tooltip heads with the complete name and lists every missing requirement when there are several. Search and filters still match descriptions. The Skill page is the one place that shows the description as body text. Do not re-add inline description lines or second lines to Skill rows.

Opening a Skill drills in: its page replaces the collection page in the same content column at every width, so the view never exceeds three columns including the app navigation. The page starts with an icon Back button (tooltip "Back (Esc)") and a breadcrumb "<collection> › <skill>"; Back, the breadcrumb's collection link, choosing the current collection again, or Escape (unless a dialog, menu or picker consumed it, or focus is in a text field) return to the collection page with its scroll position, filters and focused row restored. The open Skill page is its own history place (`[collection, skillId]`), so Back from it returns to the collection and Forward reopens it; Back, the breadcrumb and Escape go up to the collection the same way. The header holds the Mono name, then the source line with the status chip and a Read only badge whose tooltip says why the package cannot be edited, and the actions Edit instructions (editable packages), Turn off everywhere (secondary, with an explanatory tooltip) or Turn on, a Pin icon toggle (editable packages; its pin fills in the accent color while pressed, the tooltip says what a pin does) and a danger Delete icon; a pinned package shows a "Pinned" badge in the source line. Below it the description is body text, then one quiet line of label/value facts (Created by, Last changed, Last used), then same-name notes. While the Skill is off everywhere a warn Banner replaces Access; otherwise Access follows as a sub-heading with Agents and Projects Checkbox groups, side by side when there is room (no group Checkbox, Sans names, locked rows with a short state and their reason in the tooltip, an inline tertiary Allow action for a blocked receiver), then requirement notes and the Instructions/Original text tabs, plus History for an editable package: a list of revisions, newest first, each a head line (Mono number, what it did, muted date and actor, a tertiary Revert at the end) with its changed files in Mono below, rows divided by hairlines. Creation and editing use explicit dialogs; folder setup remains mounted after first visit. The view has automatic inventory reconciliation and no manual Refresh control.

Skill rows have context menus (right click, ContextMenu key or Shift+F10) through the shared `ContextMenu.svelte`: a Library row offers Open, Edit instructions (editable packages), Copy name | Turn off everywhere or Turn on everywhere | Delete... (danger, editable packages); an Agent collection row offers Turn on/off for <Agent> (disabled with the hint "Managed in project <name>" for a Project grant), Open skill, Copy name | Turn off/on everywhere; a Project collection row offers Activate/Deactivate in <Project>, Open skill, Copy name; an Archived row (whose click opens the same menu, since an archived package has no page) offers Restore, Copy name | Delete permanently... (danger). Copy name confirms with a toast.

Behavior, ownership, and source-package policy are in `settings.md` -> Skill manager and `../skills.md`. Rendered coverage: `components/skills/__tests__/skillsView.test.js`.

### Settings, Agents, Projects, and Schedules

Settings currently opens General and offers eight pages: General, Providers, Voice, Memory, Tools, Integrations, Archive, and System. The sidebar contains pages, while related settings appear together under section headings in one scrollport. An archived item opens as a sub-page of Archive in place of the page heading and its other sections, with a breadcrumb back to the list. Session titles sit with display preferences; speech Model choices sit with Voice, the embedding Model inside Conversation search, and web search/reading with the other Tool settings. Providers has an inline Shared defaults link in the line under its page header. Pages follow the configuration page grammar in `styles/settings/sections.css`, shared with Agents, Projects and Schedules: titled sections separated by whitespace, never by a line, each holding one bordered group (`.s-group`) per topic whose items are divided by hairlines. Hairlines exist only inside groups, so a line always means the next item of the same topic. Setting rows put label and description on the left and the control in one 300px column, so controls align across a page; switches, buttons and numbers sit at the row end, and number fields share one width. More of the same topic opens inside its group through a disclosure row (`.s-disclosure` on a native details element, `.s-disclosure-row` on a button, with nested setting rows in `.s-group__rows`), never as a nested card. Selection lists use Checkbox groups (`.s-check-group`): a head with the group Checkbox, title and count, then full-width Checkbox rows. Settings content follows an explicit user requirement (2026-09-29): pages stay calm and scannable, ordered by priority. A row shows at most one short visible description, only when a user cannot choose correctly without it or when it states a non-obvious consequence; it never restates the label.
