# Subagents

Sub-Agent Sessions: the durable Parent-to-Sub-Agent tree, forwarding of Sub-Agent answers to the Parent, tree control, and the Sub-Agent's side of the conversation.

## Overview

`core/subagents/` owns the runtime behavior behind the `subagent` and `message_parent` Tools and the Sub-Agent branch of `background_tasks`; their definitions, schema, call-syntax normalization and display live in `core/tools/subagent.py` (`tools/subagent.md`) and `core/tools/background_tasks.py`. `SubAgentCoordinator` (`subagents.py`) handles the `subagent` actions `run` and `send`, `message_parent`, what `background_tasks` lists, checks and stops (`subagents`, `running_work`, `stop_subagent`), the user's "Stop all" (`stop_tree`) and the WebUI projections (`inspect`; `subagents` also answers `subagent.tree {agent_id, session_id}`, the Session's Sub-Agents at every depth breadth first with `id`, `title`, qualified `agent_id`, `session_id`, `parent_id` (null for a direct Sub-Agent) and `status` `working|queued|idle`, for the Session information panel). Internal parts: `links.py` answers every tree question from durable Session metadata; `forwarding.py` follows Runs in Sub-Agent Sessions, forwards their answers and owns the activity files; `activity.py` writes one activity file; `catalog.py` projects prompt targets; `_interpretation.py` settles what a call addresses and names valid choices; `_constants.py` holds policy defaults, event names and the domain's Agent-facing results, refusals and sections.

Not owned here: coalescing and waking for deliveries (the automation completion coordinator, `automation.md`); selecting the reply target for incoming messages (Chat persistence, see Conventions); the Stop commands themselves (`/stop` in `core/chat/commands.py`, the `chat.cancel` / `chat.stop_all` RPCs in `server/rpc/chat_methods.py`); System Prompt block mechanics (`prompts.md`).

## Terms

Core terms (Agent, Session, Run, Queue, System Reminder) live in `.vorch/GLOSSARY.md`.

### Sub-Agent
A Session linked to the Parent Session that started it with `run`, together with the Agent working in it. It keeps one public id (`sub_` plus 16 lowercase base32 characters, `new_id("sub")`) for its whole life; every `send` and every `background_tasks` call on it uses that id.

### Parent Session / Parent Agent
The Session (and its Agent) whose `run` created a Sub-Agent. A Sub-Agent can itself be a Parent.

### Agent tree
A root Session that is not a Sub-Agent plus every Sub-Agent below it. Stop all and `background_tasks` stop act on complete subtrees, regardless of who receives their answers; the active limits count per Session and app-wide, not per tree.

### Forwarding
Delivering the final answer of a Sub-Agent's turn to its Parent Session as a completion section, which wakes an idle Parent.

### Reply target
The recipient of a Sub-Agent's final answers: Parent or user. User input selects the user; Parent input or an accepted `message_parent` call selects the Parent again. This never changes the Parent link, messaging, visibility, limits or stop controls (user decision 2026-10-14, replacing the former takeover boundary). Automatic continuations retain the selected recipient.

## Data Model

- **The Parent link is the only tree state.** `_open_subagent_session` creates the Session, sets its `auto_title`, writes `is_subagent_session: true` and `subagent_parent` `{id, agent_id, session_id, project_id, run_id, tool_call_id, tool_call_index}` (the Parent address plus the creating call) and stores Session Agent overrides, as one blocking unit on the Session database's pool, so a cancelled Parent never leaves an unlinked Session. A first Run that cannot start removes the Session again, so no Sub-Agent exists without one. The Session store projects the link into `subagent_parent_*` columns; two partial indexes back `ChatSessionManager.subagent_children(parent)` (live children, oldest first) and `subagent_session(id)` (the live Session with that public id). Forks strip the Sub-Agent marker, Parent link, reply target and historical takeover timestamp.
- `links.py` answers children, descendants (breadth first), ancestors (at most 64) and id lookup from durable links; callers use `sessions.run_async`. Descendant walks visit each Session once, so cycles cannot repeat work, and always cover the complete subtree regardless of reply target or historical size. `background_tasks` list shows at most 1000 Sub-Agent rows. The tree survives restarts without an in-memory registry; a deleted Session and its descendants become unreachable from the root.
- `read_link` and `ancestors` accept `strict=True`: a missing Session still ends the chain, but any other metadata-read failure propagates. Scratch Areas use this mode for placement and retention, so unavailable ancestry cannot turn a busy shared area into a deletion candidate (`tools/scratch.md`; `test_runtime_wiring.py`). The default remains tolerant for existing tree readers.
- `subagent_reply_target` is `parent` (the default for linked Sessions) or `user`. Chat commits a changed target with the input through `append_many` / `apply_edit`; an accepted `message_parent` changes it under the Session write lock. Sessions stamp the current target on each new entry and the terminal Run summary (`entries.subagent_reply_target`), so later input cannot redirect earlier answers or a completed Run. The field never enters Provider requests or public Message payloads. The one-time migration `sessions.0003_subagent_reply_targets` selects `user` for linked Sessions with historical `subagent_taken_over_at` and no explicit target; the old timestamp no longer affects control.
- Title: the whitespace-normalized `description`, at most 48 characters, set at creation and never changed by the coordinator; automatic title generation skips Sub-Agent Sessions (`core/sessions/titles.py`).
- Process-local state only: one coordinator-wide admission lock (`_admission_lock`, held through limit checks and Run admission, and through a stopped tree's lookup and cancellation signals), the followed Runs and silenced Run ids in `SubAgentForwarding`, and the activity file per Session in `SubAgentActivities`.
- **Activity file:** one Markdown file per Sub-Agent Session under `<data_dir>/artifacts/temp/subagents/`, created on first use (by `run`, `send`, or the first followed Run in this process) and recording every followed Run in start order. It holds visible Assistant output (deltas live, finalized output as fallback) and one line per Tool call with name, display summary and state; user and Parent messages, Reasoning, Tool arguments and results never enter it. The lease is held while a Run is followed or a Parent delivery is pending; the next Run or delivery reopens it (`TemporaryFileManager.reopen`, recreating a removed file), so the 24 h retention counts from the last Run or delivery to finish. Delivery entries carry the delivery id, Run id, Parent address and answer Message ids: pending on submission, delivered only after the coordinator confirms persistence in the Parent Session, failed or cancelled otherwise. Delivered is not a Model read receipt. These status writes remain available after the Run watcher closes and never use the droppable Assistant-output buffer. All file I/O runs on the process-wide `subagent-activity` `OrderedWorker`: text is handed off at most every 250 ms and at once when a Run ends; beyond 256 pending chunks a chunk of only Assistant text is dropped and a missing-activity note marks the gap (headings, Tool and status lines are always written); a watcher its Run evicts for lagging still writes the Run's outcome. `drain_activity()` waits until the text so far is on disk; Runtime shutdown awaits it after the Run manager closed. Failures affect only observability. Coverage: `tests/core/subagents/test_activity.py`.

## Interfaces

- `SubAgentCoordinator(runtime, trigger_service)`; `install(run_manager)` registers forwarding as a Run-started callback. Bootstrap (`core/runtime/_bootstrap.py`) passes `runtime._chat_run_manager` because the started-service accessors raise before the Runtime has started.
- `spawn(context, arguments)` handles `subagent` `run` and `send` (the Tool runs its former `list` and `cancel` words as `background_tasks`, `tools/subagent.md`); `message_parent(context, arguments)` is the `message_parent` handler.
- `background_tasks` reads the tree through `subagents(caller)` (all descendants, breadth first, as frozen `SubAgentState`: `id`, `title`, `agent_id`, Session, `parent_id` (`None` for a direct child), `status` `working` | `queued` | `idle`, `last_tool`, `activity_file`, and independent `reply_target`), `running_work(subagent)` (commands, terminals and working children, as `kind id (label)`) and `stop_subagent(context, subagent) -> SubAgentStopOutcome` (`stopped` or `idle`). These form `SubAgentTree`, implemented by `SubAgentCoordinator`; `background_tasks` and `terminal` receive it from Runtime and import it for annotations only. The Tools own ids, texts and row layout.
- `stop_tree(address) -> int` is "Stop all" (`/stop all`, `chat.stop_all`, WebUI); returns how many Runs, queued items, commands and terminals it stopped across the complete subtree.
- `work_snapshot(address, include_entries=False)` is the live control projection served by `chat.work`: `run_active` for the root and `background_work_running` for stoppable commands, Terminal ownership/attachments and descendant Runs/Queues. It reads durable links on the Sessions worker independently of loaded History, includes pending resource launches, and excludes the root Queue that Stop all retains. Tree reads for this projection and stopping are strict: an unavailable descendant cannot be mistaken for an idle or complete subtree.
- `subagent_reply_to_user(address, message_id)` is Chat's hook for a switch to user replies (`ChatLoopDependencies.subagent_reply_to_user`).
- `chat.work` requests `include_entries=True` to add a neutral `running` list from the same strict descendant snapshot, independent of loaded conversation History. Each Sub-Agent, command and Terminal entry carries its exact Agent/Project/Session address and identity; Sub-Agents include parent/reply-target/active-Run facts, commands include `still_running`. Existing boolean-only callers keep the cheaper default projection.

- `inspect(agent_id, session_id, subagent_id, project_id=None)` returns the WebUI projection of one Sub-Agent Session (active Run, queued, or its latest persisted Run result) plus `running`, what it still runs besides its own Run, from `running_entries`: `{kind, id, label}` with kind `subagent` (working; label its title), `command` or `terminal` (label its name or command line); `chat_methods.py` serves it.
- `references_identity_agent(agent_id)` guards Identity rename while a followed Run in that Identity's Session is still forwarding.
- `prompt_targets(agent, project_id)` feeds the `tool:subagent` block: each target with its Tool-call id, display name and description (an Identity Agent's user-written `description`, `agent.md`; a Team member's repository description), empty when none; `drain_activity()` is for shutdown.
- Events (WebUI, through `ToolContext.emit`): `subagent_session_started` on `run` and `send` (`id`, bare `agent_id`, `session_id`, `project_id` when set, `status` `running`/`queued`, `delivery: "automatic"`, `activity_file`, `run_id` for `run`), `subagent_status_changed` (status `cancelled`) when `stop_subagent` stopped something. Events and metadata keep bare ids; Agent-facing results use the qualified address.
- Sub-Agent Runs are admitted with `RunKind.SUBAGENT`, `work_id` = public id, `owner` = the caller's execution owner, and count toward Agent activity only without an owner. The executor is `chat_loop.run_executor(content, parent_agent_input=True, temporary_parent_binding=...)`, which is steerable.
- Deliveries go through `TriggerService.submit_completion`: forwarded answers use notice id `subagent:<run_id>` and the Run's execution owner. `on_persisted` marks the terminal Run read only if its terminal reply target was Parent, leaving a later user-directed answer unread. Explicit Parent messages use fresh notice ids. The reply-target notice `subagent-user-reply:<message_id>` has `wake=False`: persisted without starting a Run; an active Parent reads it at its next boundary.

## Conventions

- A new Sub-Agent captures its Model and thinking effort in Session metadata. Self-delegation inherits the running Parent's actual Model/effort, including a fallback route and explicit Provider default; later Parent/default changes cannot alter the child. An explicitly supplied child setting wins. Another Agent uses its own resolved settings (a Project profile with `model: inherit` still takes the caller's actual Model). Tool dispatch carries the Run settings in `ToolContext.agent_model` / `agent_thinking_effort`; callers without that context resolve the Parent Session. Working Project inheritance remains the existing Session-bound rule. Coverage: `test_new_subagent_captures_the_running_parent_or_its_other_agent` and `test_model_and_thinking_effort_belong_to_the_subagent_session`.


- **`run`** always starts a new Sub-Agent in the background and returns at once with `id`, `agent_id` (the address the Tool accepts back: `agent@project` when the Session has a Project), `session_id`, `project_id`, `status: "running"`, a `note` and an `activity_note`. Checks, all before any Session work, in this order: id/`session_id` interpretation, `description` present, target allowed, target resolvable and runnable, depth, active limit. `run` with an `id` or `session_id` naming one of the caller's own Sub-Agents is treated as `send`; an unknown `sub_`-shaped id fails `subagent_not_found`; another id is an ignored label (note); a `session_id` that is not the caller's Sub-Agent starts a new one when it reads as a stand-in (note) and is refused otherwise. `background: false` is ignored with a note. Each start logs one INFO `Sub-agent started` line (`vbot.subagents`) with ids, Sessions, target and Run.
- **`send`** reaches only a direct child (`subagent_not_direct` names the intermediate Sub-Agent); the caller cannot message grandchildren, and Sub-Agents cannot message siblings. It captures the child's generation before asynchronous preflight, rechecks that generation and Parent link under the Session write lock, and carries the generation expectation into native Run admission: a stale send refuses instead of recreating an archived Session or messaging its replacement. It enqueues through `ChatRunManager.enqueue`: an idle Session starts a turn (`started`); otherwise the item is steered into the running turn (`steered`) unless it carries an execution owner or a temporary binding, which stay `queued`. `model`/`thinking_effort` replace stored overrides only after enqueue accepts the input; any admission rejection leaves them unchanged. An executor gate keeps accepted input out of Chat until preparation commits, and queued input regains its native Chat executor before steering becomes eligible. Preparation failure removes queued work or fails an already-admitted Run without executing its content. The Session lock protects validation through settings preparation; no Run-manager lock spans metadata I/O. A stored Model that cannot run, unreadable stored overrides, or a Working Project that no longer exists (`project_not_found`, `retryable: false`, `SUBAGENT_SESSION_PROJECT_MISSING_MESSAGE_TEMPLATE`) refuse before enqueueing. Regression coverage: `test_subagents_admission.py` and the real Chat steering cases in `test_answer_delivery.py`.
- **`background_tasks` list and status:** list shows every Sub-Agent in tree order, then commands of the caller and every descendant; a descendant's command names it in `subagent`. It never repeats answers. A note against polling appears for the caller's running commands or direct working/queued children whose reply target is Parent. Status adds `project_id`, non-empty `running` and actionable `next` text. A user-directed child keeps its ordinary status and adds `reply_to: "user"`; its next text names sending a message to restore Parent replies (only for a direct child with `subagent` available), and stopping it. A `ses_` id identifying exactly one descendant is read as that Sub-Agent with a note. Coverage: `test_background_tasks_lists_and_checks_the_whole_tree`, `test_user_input_keeps_the_complete_subagent_tree_controllable`, and `tests/core/tools/test_background_tasks.py`.
- **`background_tasks` stop** (`stop_subagent`) stops any descendant with its whole subtree: queued items removed (including input being steered), active Runs cancelled with reason `parent_agent` and initiator `parent_run:<run_id>`, terminals and background commands closed. A direct child's outcome is silenced because the Tool reports it; a deeper child's cancellation can forward to its own Parent if addressed there. Descendants of the stopped target are silenced. The result is success with `status: "stopped"` or `"idle"` when nothing needed stopping. Sessions and history remain; the result names continuing with `send` while the caller can call `subagent`, or names the intermediate Parent for a deeper child. User input changes none of this.
- **Forwarding** follows `subagent`, `system`, `user` and `channel` Runs in linked Sessions. When a Run ends, it selects complete text answers addressed to Parent under that exact Run id, in persistence order, each headed by its Message id. A failed, interrupted or cancelled Run also includes its latest partial text if Parent-directed. A returned answer is a fallback only when not persisted. The terminal Run summary snapshots the final target: an outcome without Parent answers is forwarded only if the terminal target is Parent. The section carries the Sub-Agent id/title, Run id, outcome and selected answers, without repeating the Agent/Session address already returned at start, in one `subagent:<run_id>` notice. A cancelled Run counts as completed only if its last User/Assistant/Tool/error entry is a complete answer; Notes and post-answer Compaction do not invalidate completion. Facts name its unfinished commands, terminals and working children, plus other direct children whose Parent-directed answers are pending. Silenced Runs and missing Parent Sessions are dropped. Target changes after persistence cannot redirect earlier answers; mixed-recipient answers in one steered Run are filtered individually.
- **Parent framing:** Parent input reaches the Sub-Agent with `PARENT_AGENT_INPUT_SYSTEM_REMINDER` at a turn start or `PARENT_AGENT_STEERING_SYSTEM_REMINDER` when steered (`core/chat/messages.py`). The `core:subagent_role` System Prompt block (owner `subagent_session`, text `resources/prompts/subagent_role.md`) and the session-scoped `message_parent` grant (`SUBAGENT_SESSION_TOOL_NAMES`) apply exactly when the Session has a Parent link; Chat reads that flag per Run context and at Compaction, regardless of the reply target.
- **Recipient changes:** on Run start and steering, Chat selects `parent` for Parent input and `user` for other external input (`subagent_input_reply_target`); internal or already-persisted input keeps the current target. The Session write lock orders the switch with input persistence. A transition to user replies adds `SUBAGENT_REPLY_TO_USER_SYSTEM_REMINDER` before the message and invokes `report_subagent_user_input` after commit. Its non-waking Parent notice is best effort and skipped if Parent replies have already resumed. Repeated user input needs no additional notice until the target changed back to Parent. Parent reminders announce that final answers now go to Parent. The Parent link and all controls remain intact.
- **`message_parent`** submits a section to Parent (waking it) without ending the turn. Accepted submission restores Parent replies under the Session write lock before the call succeeds, even if the calling Run is cancelled during that write. Success returns `status: "queued"`, a `delivery_id` shared with the Parent section and activity log, and a note announcing the target. Acceptance is distinct from confirmed persistence. Refusals: `not_a_subagent`, `parent_not_found`, and `delivery_unavailable` for immediate rejection; rejection leaves the target unchanged.
- **Stop (every Session and Channel):** Run cancellation stops only the current Run and the shell commands still inside its calls (`CommandManager.cancel_run`, `tools/shell.md`); background commands, terminals and Sub-Agents keep working and deliver later, waking the Session. `stop_tree` stops the Session's Run (its own Queue stays, its answer is not silenced) and, for every Sub-Agent below it, clears the Queue, cancels and silences the Run; it closes the terminals and background commands of the Session and of every Session below it (`commands.close_scope`, without delivery; `test_a_tree_stop_stops_its_background_commands_without_delivery`); reason `user`, initiator `user_stop_all`. Terminal cleanup closes the captured address set in one batch, so an admitted launch without a published Terminal row is drained and a Terminal attached within the same tree is counted only once. The entire captured subtree cleanup settles before propagating caller cancellation; a resource failure is reported only after the other resources and Runs were given their cleanup (`test_stop_all_drains_terminals_of_the_complete_tree`).
- **Tree cancellation admission:** both `stop_tree` and `stop_subagent` take the admission lock while reading the complete subtree and signalling every affected Run, so an in-flight child start is included and every affected Run receives cancellation before cleanup is awaited. They release the lock before awaiting terminal and command shutdown or Run completion. `run` and `send` recheck the calling Run's cancellation under that lock before starting or enqueueing work; a cancelled `send` changes no stored overrides. Past that check the call completes and returns its result even when the calling Run is cancelled meanwhile (`finish_despite_cancel`), so the Parent keeps the Tool result of a Sub-Agent that started or a message that was sent and never repeats the work (`test_a_call_cancelled_once_its_work_began_still_returns_its_result`).
- **Limits** (Sub-Agent settings, `settings.md`): `max_subagent_depth` (default 2) refuses a `run` when the caller already has that many ancestors. Two active limits refuse a `run`, and a `send` to an idle Sub-Agent (it would start a Run); a refused `send` stores no Model overrides. Working means an active Run or queued input (`is_working`); all working Sub-Agents count regardless of reply target.
  - `max_active_subagents` (default 8, `subagent_limit_exceeded`) counts the caller's own working Sub-Agents only: not the caller itself, not their Sub-Agents. Its refusal says that one stops counting once it answered or was stopped, and offers waiting, `background_tasks` stop (only while the Agent can call `background_tasks`) or doing the task itself.
  - `max_active_subagents_total` (default 50, `subagent_app_limit_exceeded`) counts the working Sub-Agent Sessions of the whole process, found among the Run manager's active Runs and queues. Its refusal offers doing the task itself or waiting for one of the caller's own working Sub-Agents, because the caller cannot free other Agents' places.
  - A `send` to a working Sub-Agent bypasses the Sub-Agent active limits because it starts no further Run, but Run-manager waiting-work capacity and lifecycle admission still apply. All `run` and these `send` checks are serialized under one coordinator-wide admission lock, so parallel starts cannot pass on a stale count.
- **Targets:** a bare `agent_id` inherits the caller's scope; `agent@project` selects that Project. The Sub-Agent Session lives in the target scope, its link records the Parent address, and the Parent Session never moves. It works in a Working Project fixed at its start (`sessions.md` -> Terms): an Identity target, a copy of the caller included, works where the caller's Run works (`ToolContext.working_project_id`; the Workspace when none), whatever the target's default Project; a Team target works in its Team's Project. `tools.subagent.allowed_agents` (snapshotted in the caller's Tool settings) lists additional targets only: missing or `['*']` allows every resolvable target, `[]` is self-only, omitting `agent_id` always selects the caller. A Project caller can reach only its own Project, whatever the policy. A generic worker name (`general-purpose`, `default`, `self`, ...) that is no allowed Agent id selects the caller with a note. The built-in Librarian is never a target. `agent_not_found`/`project_not_found` list the valid choices; a target that cannot run fails `agent_unavailable` (`retryable: false`) with the resolver's reason; an unusable `model` fails `invalid_arguments`. Explicit Identity grants carry the Agent-owned incarnation binding captured for the Run (`agent.md`); before opening a child Session, the coordinator checks it offloop while holding the shared Agent lifecycle/reference mutex through Run admission. A replaced target is refused without a Session or Run. Catalogs and Provider schema choices apply the same binding check; wildcard, self, Project-qualified and unbound legacy entries retain their existing scope. The coordinator is the security boundary; Provider-schema narrowing and the prompt block are guidance.
- **Execution ownership** (temporary Agents, extension groups): Sub-Agent Runs and queued sends carry the caller's owner, forwarded sections carry the Run's owner, and a copy of a temporary caller runs under its temporary parent binding without the private Session grants. A closed owner drops its deliveries silently (`RunAdmissionBlockedError`, DEBUG). `tests/core/agents/test_temporary.py` covers actual Chat execution.

## Constraints & Gotchas

- Forwarding and activity state are process-local: a Run is followed only when it starts in this process (Runs do not survive restarts either), and an activity file allocated before a restart is not reused.
- After a plain Stop, a Session's Sub-Agents and background work continue, and their later answers wake it. That is intended; Stop all is the control that ends them.
- The domain's Agent-facing texts live in `_constants.py` (results, refusals, forwarded sections), `resources/prompts/subagent_role.md` (role block) and `core/chat/messages.py` (reminders). A new prompt fragment must also be listed in `PROMPT_FRAGMENT_NAMES` (`core/storage/prompt_fragments.py`), or Runtime start fails.
- Tests: `tests/core/subagents/subagents_test_support.py` dispatches through the registered Tools (`subagent`, `message_parent`, `background_tasks` over a `CommandManager`) over real Sessions and a real `ChatRunManager`; only the Agent resolver, the completion coordinator and the Chat loop are doubles. Coverage: `tests/core/subagents/test_subagents.py`, `tests/core/tools/test_subagent.py`, `tests/core/tools/test_background_tasks.py` (Sub-Agent rows, status and stop texts against a fake tree).

## Agent-facing text

Review labels such as "Review B12" name the reviews of 2026-10-12: `tools/shell/agent-facing-text.md`.

| Text | Reason |
|---|---|
| Role block: `You are a Sub-Agent: another Agent, your Parent Agent, delegated work to you ...` | Without it a Sub-Agent takes the brief as the user's request and addresses the user. |
| Role block: `vBot sends your final answers to your Parent Agent unless the user writes in this Session. ...` | Parent-directed final answers are forwarded; a Sub-Agent that ends a turn while work still runs must say so instead of presenting a result. |
| Role block: `When you find that the task cannot be done as briefed, ... do not switch to a different task on your own. ...` | A Sub-Agent that silently substitutes another approach or scope hands the Parent a result it integrates unknowingly. A question via `message_parent` cannot be awaited within the turn, so a Sub-Agent blocked on the decision ends its turn with the finding instead; one that can continue asks and continues. |
| Role block: `vBot starts a new turn for you when background work you started delivers ...` | Sub-Agents otherwise poll or wait on background work they can leave running. |
| Role block: `If the user writes in this Session, your final answers go to the user. ... You remain connected throughout.` | User input selects the audience without severing the relationship; messaging in either direction restores Parent replies. User decision 2026-10-14. |
| `PARENT_AGENT_INPUT_SYSTEM_REMINDER` | Identifies Parent input and announces that final answers now go to Parent. |
| `PARENT_AGENT_STEERING_SYSTEM_REMINDER` | A steered Parent message must change the running task, and a question in it needs `message_parent` because the final answer comes later. |
| `SUBAGENT_REPLY_TO_USER_SYSTEM_REMINDER` | Announces user replies and how either side restores Parent replies; avoids interpreting user input as permanent disconnection. |
| Forwarded section header (Sub-Agent id/title), Run id, `Answer <message_id>` / `Partial answer <message_id>`, and facts line | The Parent must tell which Sub-Agent answered, how its turn ended, and what is still running before it treats the answer as final. The repeated Agent/Session address was removed on 2026-10-14; the initial result keeps it for Session lookup. Stable Message ids distinguish a main report from a steered addendum in the same Run (observed 2026-10-13); later answers must not displace earlier ones. |
| `FACTS_SIBLINGS_PENDING_TEMPLATE` / `FACTS_NO_SIBLINGS_PENDING_TEXT` | After one of several Sub-Agents answered, a Parent called `subagent` `list` to learn whether the others still ran (black-box runs, 2026-10). |
| `REPLY_TO_USER_NOTICE_TEMPLATE` | The Parent learns the current recipient, its unchanged messaging/status/stop controls, and how to restore automatic replies. |
| `PARENT_MESSAGE_SECTION_TEMPLATE`: `Delivery {delivery_id}.` | Correlates the received message with the Tool result and its activity receipt. |
| Activity receipt: `Pending: submitted for delivery to the Parent Session.` | Submission alone is not confirmed persistence; a disputed delivery needs a visible intermediate state. |
| Activity receipt: `Delivered: stored in the Parent Session.` | Marks the completion coordinator's persistence acknowledgement, without claiming the Model has read it. |
| Activity receipts: `Delivery failed: {error}` / `Cancelled before delivery was confirmed.` | A failed or rejected delivery must not look like a confirmed one; the reason stays with its id. |
| `PARENT_MESSAGE_SECTION_TEMPLATE` closing sentence | A message is not the Sub-Agent's result; the Parent must keep waiting for the answer. |
| Per-Session limit refusals (`SUBAGENT_ACTIVE_LIMIT_MESSAGE_TEMPLATE`, `SUBAGENT_SEND_LIMIT_MESSAGE_TEMPLATE`): `You already have 8 Sub-Agents working, the most you can have at the same time. ...
