# Subagents

Sub-agent orchestration, in-memory batch tracking, parent-child run linkage, and child result lookup.

## Overview

`core/subagents/` owns the runtime behavior behind the single public `subagent` Tool. The Tool module is only the registration/schema boundary; `SubAgentCoordinator` (`subagents.py`) performs run/status/cancel orchestration and owns the process-local `SubAgentBatchTracker` (`tracker.py`) - batch state-machine logic belongs there. `subagents.py` keeps admission, target resolution and child Run construction; `_completion.py` keeps completion watchers, persisted-result lookup and Parent cancellation linkage; `_status.py` owns public status/cancel/inspection projections; `_interpretation.py` settles what a `run` call addresses (work ids, Session owners, generic worker names) and names valid choices in refusals. These are internal parts of the same coordinator; `_constants.py` centralizes their unchanged policy defaults, event names and Agent-facing result wording.

## Data Model & Tracking

- Every admitted work item receives one stable public id (`sub_` plus 12 lowercase base32 characters); entries hold child addressing, optional activity file, completion/fetched flags, captured result, and internal live run or queue handles that never appear in Agent-facing parameters/results. Status/cancel resolve only the public id within the caller's Parent Session and Project; an untracked id (foreign, unknown, pruned after delivery, lost at restart) fails `subagent_not_found` without distinguishing these causes. Batch tracking does not survive restarts; the per-turn slot reserves before async spawn work so siblings cannot bypass `max_subagents_per_turn`. The tracker reserves the public id before spawn yields, retries collisions across retained batches, and releases allocation state when its batch is pruned (`tests/core/subagents/test_tracker.py`).
- Each spawn allocates a temporary Markdown activity file under `<data_dir>/artifacts/temp/subagents/`: visible Assistant deltas stream live with finalized events as fallback; Tool entries carry only name/display-summary/state - User messages, Reasoning, arguments/result bodies, stdout/stderr stay out. Retention (24 h) starts at terminal; failures affect observability only.
- Spawning writes durable parent->child links into child Session metadata (`is_subagent_session`, `subagent_parent` record) plus an `auto_title` derived from the parent-authored description (fallback content start), collapsed to one line <=48 chars - before the start event, preserved across continuations. Creating or loading the child Session, its title, and the Parent link are one unit of Session work on the Session database's pool (`_open_subagent_session`), off the Event Loop; a cancelled Parent never leaves a created child without its link. Metadata survives restarts for navigation/display; active status/cancel ownership does not.
- **Parent and target scope stay separate:** a qualified `agent@project` target explicitly selects that Project regardless of parent scope; a bare target inherits the caller's scope. Child Session, Run/Queue key, metadata location, and navigation use the target project; durable linkage, tracker, and completion trigger keep the parent scope - the parent Session never moves. Status/cancel need no address because ownership recovers from the public id.
- **Target authorization** enforces the caller's snapshotted `tools.subagent.allowed_agents` before any lookup/mutation/reservation: the setting holds additional targets only (omitting agent_id selects self whenever the Tool is active; self never repeats in the list; empty list = self-only, not disabled; missing/`['*']` allows every resolvable target). Project targets always constrain to the caller's current Team - a qualified cross-Project id cannot escape even under wildcard policy.
- Optional two-field Run overrides (`model`, `thinking_effort`) validate together with target resolution before Session creation/slot reservation and ride the immutable executor - changing only that Child Run's resolved view, writing no configuration.
- `references_identity_agent(agent_id)` gates Identity rename: batches can outlive the visible parent Run, so retargeting waits until the tracker clears.
- `prompt_targets(...)` projects additional callable Agents for the Tool-owned prompt block (deterministic call-id order, excluding the caller; Identity callers receive qualified addresses for Project Agents).

## Behavior contracts

- Continuing an existing Session uses its exact `session_id` in the owning Agent's scope (ids are Agent-scoped). Without `agent_id`, `_interpretation.py` takes the owner from the tracked child of that Session, else the caller itself; an unknown Session fails before effects unless the id reads as a stand-in (then a new Session starts, with a note). `subagent(content)` defaults an omitted action to `run`; an id without a task cannot infer status/cancel and refuses naming both calls. The Tool boundary owns flat schema and call-syntax normalization, including other harnesses' dialects and placeholder values (`tools/subagent.md`); orchestration ignores fields an action does not use, refuses unknown fields before effects, and never replaces an explicit unknown Agent with another target (only a generic worker name such as `general-purpose` that is not an allowed Agent id selects the caller, stated in the result). Empty model/effort selections inherit the target Agent; `"none"` explicitly disables Reasoning.
- Child Runs execute through the streaming loop's public `child_loop(nesting_depth=...)` + `run_executor(content)` seam - inheriting attachment resolution, media handling, and auto-compaction like live Runs; only nesting depth differs. A runtime without `streaming_chat_loop` is a wiring bug, never a silent fallback.
- Delivery mode derives solely from `ToolContext.nesting_depth`: depth 0 = background with automatic delivery, >=1 = foreground inline waiting up to `subagent_timeout_minutes` then cancelling with a timeout failure. The foreground bound covers queued waiting plus execution; expiry while queued removes the item. Removing a queued foreground child from the Queue returns the `subagent_removed` Tool failure to the Parent (the Parent Run continues), while cancelling the Parent itself still propagates and cascades. No public mode switch: a requested `background`/`blocking` that differs is ignored and stated in the result note. The Tool-owned prompt block tells the Agent which rule applies before calling, including the configured timeout for nested callers (`foreground_timeout_minutes()`).
- Top-level execution returns immediately with public id, child address, running/queued state, delivery mode, activity path, and a state-dependent behavioral `note` (queued names the busy Session; running states the background contract); internal handles are never returned. Foreground results deliver `delivery: "inline"` acknowledged only after Chat durably persists the Parent Tool Result; successful runs carry a contextual activity-note (forward-slash path) telling the Agent when reading progress is relevant.
- `status` snapshots one public id or all retained work in the calling Parent Session and Project without fetching entries (return shapes: `tools/subagent.md`); persisted terminal lookup asks Sessions for the exact Run summary, last non-empty Assistant result, and latest Tool name within that Run boundary through the async Session boundary (`ChatSession.load_run_result_async`), never on the Event Loop, instead of loading the child transcript. Interrupted children report their preserved partial result or explicit interruption note with Continuation coordinates. Only proven terminals mark fetched. `inspect(...)` (async; its persisted Session read uses the same boundary) resolves one exact child across queued/running/persisted states without trusting newest-Run selection; legacy summaries without work ids fall back conservatively in the WebUI only.
- `cancel` waits for the exact running child to reach cancelled or synchronously removes the queued item; success reports without internal handles and emits the status-changed event. Cancelling started work adds a resume note to the Tool result only (not the event); removed Queue work never ran and gets none.
- **Agent-facing `agent_id` is the value the Tool accepts back:** a bare id resolves in the caller's scope, so every Agent-facing result (run descriptors, inline results, status snapshots, cancel results) renders `agent_id` as `agent@project` whenever the child Session has a Project, bare for Identity children, with `project_id` kept as its own field; `_completion.py::_public_subagent_result` is the single projection. Completion notices name the same address. Events (`subagent_session_started`, `subagent_status_changed`), Session metadata and `inspect(...)` keep bare ids plus `project_id`; WebUI readers of persisted results also accept historical bare `agent_id` beside `project_id` (`webui/chat.md`).
- **Continuation notes name exact call values:** interrupted (partial or no output), cancelled-running, and non-user cancelled-without-output results tell the Agent to call `subagent` with the same `agent_id` value the result field carries plus `session_id`. User-cancelled results get no resume suggestion. The queued-to-running cancellation race resolves the manager's exact public work id, independently of completion-watcher scheduling. Cancelling an automatic-delivery child from inside its own Session still reaches its watcher and delivers like any cancellation.
- Busy targeted existing Sessions enqueue follow-ups; freshly created busy Sessions fail `session_busy`. Queued work registers its tracker, completion watcher and applicable Parent cancellation before emitting its queued notification; foreground notification failure also cancels a child that started during that notification. Background queued work that never starts without the coordinator removing it (a user Queue removal, or admission failing at drain) completes as `cancelled`/`failed` with an explanatory note, submits the ordinary automatic completion notice, and stays answerable through `status` until the Parent durably received it; Agent-initiated `cancel` still removes the entry directly.
- Every started child gets an independent completion watcher accepting each entry once - keeping handles and automatic delivery alive if the Parent cancels before Result persistence. Foreground Parent cancellation removes never-started queued children and cancels started ones without discarding handles; background children deliberately skip the cascade (single flip-back constant `CASCADE_BACKGROUND_CHILDREN`). Parent-cancel with reason `user` cascades the same reason; children cancelled by the user report `cancelled_by_user` with distinct wording everywhere.
- Terminal unfetched results submit immediately to the shared automation completion coordinator per child (not batch-wide); combined automatic notes carry complete untruncated output plus activity paths and open with "not a new request" guidance. Fetch/read marks only after durable Parent persistence; a missing Parent Session drops only the tracker entry leaving the child unread. A terminal `status` reaching history first cancels the pending notice; stable notice ids prevent duplicate deliveries.
- Overrides are not ambient nesting state: nested calls omitting them resolve the target's configured values, and continuing a Session requires them again per Run.
- Extension execution ownership follows child Runs, Queue items, completion notices and managed resources, including work in an existing target Session. Group Stop cancels those exact descendants rather than every Run in that Session. Self-delegation from a temporary Agent preserves its protected configuration in an ordinary child Session without private Session grants or orientation. The group lifetime overrides ordinary background-child survival; `tests/core/agents/test_temporary.py` covers actual Chat execution.

## Constraints & Gotchas

Per-Run spawn admission counts remain attached weakly to the live parent Run after fetched/completed batches are pruned. Releasing an unregistered reservation refunds it; fetching a successful child result does not reset the parent's admission budget.

- The caller cannot target its own active Session.
- Limits from Sub-Agent settings: depth 4, per-turn 8, timeout 60 minutes defaults (schema in `settings.md`).
- Parent-Run and Parent-Agent cancellation are separate controls: a top-level background child survives Run cancellation while a later Run can cancel it via public id; ownership relies on the process-local tracker, sufficient because Runs/queue do not survive restarts either.
- Batches drop only when every remaining entry is complete *and* fetched; empty batches drop too. Removing a queued entry never gates ready sibling delivery.
- The `tool:subagent` System Prompt block owns delegation guidance and catalog, contributed by the Tool, gating out with it; native descriptions stay short schema guidance.
