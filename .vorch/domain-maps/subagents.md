# Subagents

Sub-agent orchestration, in-memory batch tracking, parent-child run linkage, and child result lookup.

## Overview

`core/subagents/` owns the runtime behavior behind the single public `subagent` Tool. The Tool module is only the registration/schema boundary; `SubAgentCoordinator` (in `subagents.py`) performs run/status/cancel orchestration and owns the in-memory `SubAgentBatchTracker` (in `tracker.py`) for one Runtime instance. Batch-tracking state machine logic belongs in `tracker.py`, lifecycle orchestration in `subagents.py`; callers import from the `core.subagents` package.

## Data Model

- `SubAgentCoordinator`: runtime-facing service with one `spawn(context, arguments)` handler for every public action plus `prompt_targets(agent, project_id)` for the Tool-owned System Prompt block.
- `SubAgentPromptTarget`: prompt-only projection of one additional callable Agent with its exact Tool-call id, display name, and optional description. `catalog.py` builds this projection from the caller's snapshotted Tool settings plus the live Identity/Project catalogs and deliberately excludes the calling Agent.
- `SubAgentBatchTracker`: process-local tracker keyed by parent `(agent_id, session_id, run_id)`.
- Every admitted work item receives one stable public `id` (`sub_<uuid>`). Batch entries are keyed by that id and hold the child `agent_id`/`project_id`/`session_id`, optional `activity_file`, completion/fetched flags and captured result, plus either an internal live `run_id` or — while still queued — an internal `queue_item_id`; attaching a started Run never changes the public id.
- Status and cancellation resolve only the stable public id within the caller's Parent Agent Session and Project. Internal Run/Queue handles remain available to lifecycle and accessor code but never appear in Agent-facing Tool parameters or results.
- Every admitted spawn allocates a unique temporary Markdown activity file through Storage under `<data_dir>/artifacts/temp/subagents/`, including each new Run that reuses an existing child Session. `activity.py` projects replayable child Run events into this supplemental file: visible Assistant deltas are flushed live; finalized Assistant events provide a non-streaming fallback without duplicating streamed text; Tool entries contain only the Tool name, existing `ToolDisplay.summary`, and completed/failed state; User messages, Reasoning, raw/full Tool arguments, Tool result bodies, stdout, and stderr are excluded. The activity lease remains active while queued/running, starts Storage's 24-hour retention when the Run reaches a terminal event (or a queued item is removed), and failures affect only observability, never child execution or canonical Session history.
- Spawning also writes the durable parent→child link into the child Session's metadata: `is_subagent_session: true` plus a `subagent_parent` record (public `id` and parent `agent_id`, `session_id`, `run_id`, `tool_call_id`, `tool_call_index`, `project_id`). The batch tracker is only the in-memory ownership side; metadata survives a restart for navigation, but active public-id status/cancel ownership does not (constants `SUBAGENT_SESSION_METADATA_FLAG` / `SUBAGENT_PARENT_METADATA_KEY`).
- `SubAgentBatchTracker.references_identity_agent(agent_id)` reports whether any unpruned batch still addresses that Identity Agent as an unqualified parent or child. Identity Agent rename uses this as a busy gate because a child batch can outlive the visible parent Run and its later completion callback still addresses the parent id; durable unqualified `subagent_parent` links are retargeted only after the tracker is clear.
- **Parent and target scope stay separate:** `action: "run"` parses its optional public `agent_id` through the canonical `parse_agent_address` seam. A qualified `agent@project` explicitly selects that target Project regardless of the parent's scope; a bare target preserves the existing rule by inheriting `context.project_id` (`None` means an Identity Agent, a set value means that Project's Team). The child Session, Run/Queue key, metadata location, result fallback, and navigation event all use the target `project_id`. The durable `subagent_parent.project_id`, tracker batch `project_id`, and automatic completion trigger keep the parent `context.project_id`, so the parent Session never moves or changes ownership. Status/cancel need no target address because ownership and target are recovered from the public id. The child executor (`run_executor(content)`) takes no project id because the target scope rides `Run.project_id`.
- **Target authorization is a separate axis:** after address parsing and before any target lookup, Session mutation, quota reservation, or queueing, both coordinator operations enforce the caller's Run-snapshotted Sub-Agent Tool setting from root `tools.subagent.allowed_agents`. The setting contains additional targets only: omitting `agent_id` always selects the calling Agent in the same Identity/Project scope whenever the `subagent` Tool itself is active, and the calling Agent is never repeated in `allowed_agents` or the prompt catalog. An empty list is therefore self-only, not Tool-disabled. A missing setting or Identity-Agent `['*']` allows every resolvable additional Identity and Project Agent; explicit Identity entries are bare ids or qualified `agent@project` ids. Project-Agent targets are always constrained to the caller's own current Team, so a qualified cross-Project id cannot escape the Project boundary even if repository policy materialized as a wildcard.
- A spawn may carry the two-field `AgentRunOverrides` value (`model`, `thinking_effort`). The coordinator validates it together with target resolution before Child Session creation or batch-slot reservation, then captures it in the immutable Chat executor for immediate or queued execution. It changes only the resolved runtime view for that Child Run; no Agent, Project, or Session configuration is written.
- Batch tracking does not persist across restarts.
- The tracker reserves a per-turn slot before async spawn work begins, so sibling tool calls cannot bypass `max_subagents_per_turn` while they are waiting on session or queue state.

## Interfaces

- `SubAgentCoordinator(runtime, trigger_service, *, batch_tracker=None)` — `runtime` is typed as the `RuntimeServices` protocol (imported under `TYPE_CHECKING`); services are accessed directly, without `getattr` probes.
- `SubAgentCoordinator.spawn(context, arguments) -> JsonObject`
- `SubAgentCoordinator.batch_tracker -> SubAgentBatchTracker`
- `SubAgentCoordinator.prompt_targets(agent, project_id) -> list[SubAgentPromptTarget]` returns only additional Agents in deterministic Tool-call-id order. Project callers receive bare Team ids; Identity callers receive bare Identity ids and qualified `agent@project` ids for Project Agents.
- `SUBAGENT_SESSION_STARTED_EVENT` is exported for transport layers that need to bridge the live child-Session navigation event.
- `SUBAGENT_STATUS_CHANGED_EVENT` is exported for transport layers to project an explicit Parent-Agent cancellation back onto the previously returned child Run/Queue handles.

## Conventions

- Continuing an existing Session requires both its exact `session_id` and owning `agent_id`; Session ids are Agent-scoped, so an omitted/blank `agent_id` with a non-blank `session_id` fails `invalid_arguments` instead of silently targeting the caller. Without `session_id`, spawning creates a new persisted Session and an omitted `agent_id` selects the calling Agent.
- Canonical Sub-Agent calls use one open flat object with required `action: "run" | "status" | "cancel"` plus optional siblings `content`, `agent_id`, `session_id`, `model`, `thinking_effort`, and `id`. The handler requires non-blank `content` for `run`, requires the exact `agent_id` when `session_id` is supplied, requires the non-blank public `id` for `status` and `cancel`, and rejects action-irrelevant, unknown, and legacy `request`, `operation`, `background`, `run_id`, or `queue_item_id` fields.
- A blank optional `model` means omitted, matching the shared lenient optional-string policy. `thinking_effort` deliberately uses presence-sensitive parsing because `""` is the canonical explicit Provider-default value; omission inherits the target Agent, while `null`, a non-string, or an unknown effort fails `invalid_arguments`.
- Child Runs execute through a streaming `ChatLoop`, matching normal live Runs and allowing long provider generations to make progress through stream deltas instead of waiting for one complete non-streaming response. `_make_subagent_executor(runtime, content, context)` builds the child via the public `runtime.streaming_chat_loop.child_loop(nesting_depth=...)` + `run_executor(content)` API, so child Runs inherit the attachment resolver and compaction service and resolve persisted media blocks / auto-compact like live Runs; only the nesting depth differs. A runtime without `streaming_chat_loop` is a wiring bug — there is no silent fallback loop.
- Every started Child Run has an independent completion watcher, regardless of inline or automatic delivery. The foreground handler may observe the same terminal transition while preparing its Tool Result, but `SubAgentBatchTracker.on_sub_agent_complete(...)` accepts the exact entry only once; this keeps the public handle and automatic-delivery fallback alive if the Parent is cancelled before that Tool Result persists.
- An explicitly targeted existing Session that is busy enqueues a follow-up Run through `ChatRunManager`; a freshly created Session that is already busy instead fails with `session_busy` (a new Session should never be busy).
- Nested foreground execution waits for completion and returns the result payload with `delivery: "inline"`. The exact Child Run is acknowledged as read only after Chat durably appends that payload as the Parent Tool Result; producing the Child result or returning it from the handler is not delivery. Every successful `run` result whose activity file was allocated also carries a contextual `activity_note` with the concrete path and the instruction to read it if progress becomes relevant.
- The Tool emits `subagent_session_started` Run events as soon as a child Session is known, then again when internal Run/Queue details are known. The event payload includes the parent Tool Call id/index plus public `id`, child `agent_id`, `session_id`, optional target `project_id`, internal optional `run_id` or `queue_item_id`, `status`, `delivery`, and stable `activity_file: string | null`; accessors use the internal fields for live navigation/status while the Agent-facing contract stays id-only.
- A successful `cancel` waits until the exact running child reaches `cancelled`, or synchronously removes the exact queued item. If a queue item started before cancellation, its retained tracker origin resolves the public id to that exact Run. Success returns the public id, child address, and `status: "cancelled"` without internal handles and emits `subagent_status_changed`; missing, terminal, or another Parent Session's work fails without cancelling the target.
- Top-level execution always runs in the background and returns immediately with the public id, child address, `status: "running" | "queued"`, `delivery: "automatic"`, and `activity_file`; the result explains that vBot monitors it, that the Agent may continue independent work or finish the current Run, and that `status` is only for a next action that genuinely depends on the result. Internal Run/Queue handles are not returned.
- `status` is a non-blocking snapshot by public id. It returns queued/running state immediately without fetching the batch entry; terminal lookup accepts only the exact internal Run or a matching terminal Run Summary plus the last non-empty Assistant message in that Run segment. A preserved partial Assistant remains terminal but carries `interrupted: true`, optional normalized `interruption_cause`, and a continuation note. Only a proven terminal result is marked fetched and acknowledged after Parent persistence.
- Every admitted or queued Child Run carries its public work id in manager state, and Chat persists that id on the terminal `run_summary`. `SubAgentCoordinator.inspect(...)` and the read-only `subagent.inspect` RPC resolve one exact child address/work id across queued, running, and persisted terminal states without depending on the process-local tracker or selecting the newest Run in a reused Child Session; the projection may include the exact Run id, status, result, Usage, timing, and latest Tool name. Legacy summaries without a work id remain readable through the WebUI's conservative History fallback but are not retroactively inferred as exact durable associations.
- Running and queued snapshots leave tracked entries unfetched so normal automatic completion delivery still fires; a terminal lookup marks only the exact resolved Run fetched.

## Constraints & Gotchas

- The caller cannot target its own active Session.
- Limits come from `runtime.storage.load_subagent_settings()` (re-normalized in-domain as a fallback): `max_subagent_depth` (default 4), `max_subagents_per_turn` (default 8), `subagent_timeout_minutes` (default 60). Full schema in `settings.md`.
- Foreground spawns wait at most `subagent_timeout_minutes` (default 60); on timeout the child Run is cancelled and the Tool returns a `subagent_timeout` failure. The tracker records the terminal failure immediately but marks it fetched only after that Tool Result or its automatic fallback note persists.
- Foreground Parent cancellation removes queued child Runs that never started and cancels already-started children; it does not discard a started entry's public handle. The independent completion watcher captures the terminal result so a result that missed inline Parent persistence remains eligible for automatic delivery or a later `status` lookup. Background children deliberately do not register this cascade.
- Execution mode is derived solely from `ToolContext.nesting_depth`: depth 0 is background with automatic delivery; depth ≥ 1 is foreground with inline delivery. There is no public mode switch. `ChatLoop` passes nesting depth into System Prompt assembly, so the Tool-owned prompt tells the current Agent which rule applies before it calls the Tool; successful results and start events repeat the selected delivery mode.
- Parent-cancel cascade is **foreground-only by default**: only foreground spawns (and queued-then-started foreground waits) register the parent-cancel cascade callback; background spawns survive a parent cancel and keep running. The policy is gated by a single constant `CASCADE_BACKGROUND_CHILDREN` in `core/subagents/subagents.py` — set it to `True` to restore the legacy "cascade to all children" behaviour. This is the single flip-back point.
- Parent-Run cancellation and Parent-Agent cancellation are separate controls. A top-level background child survives cancellation of the Run that spawned it, while a later Run in the same Parent Agent Session can invoke `action: "cancel"` with the stable public id. A result from a user-cancelled origin is persisted to the Parent Session without starting an automatic follow-up Run. This ownership depends on the process-local batch tracker, which is sufficient because active Runs and queued work also do not survive a Runtime restart.
- Run overrides are not ambient nesting state. A nested `subagent` call that omits them resolves its own target's configured values even when the calling Child Run itself uses overrides; continuing the same Child Session also requires the fields again on each Run that should use them.
- When the parent is cancelled with reason `user`, the cascaded child Run is cancelled with the same reason (`request_cancel(reason="user")`). A child cancelled with reason `user` is reported to the parent as a `cancelled_by_user: True` entry: inline results, status snapshots, and the batch-completion note all use the "Cancelled by the user" wording. Non-user cancellations keep the generic "Cancelled" wording.
- A batch is dropped from the tracker only once *every remaining* entry is both complete and fetched; an empty batch is dropped too. Removing a queued entry only removes/prunes tracking and never gates already-ready sibling delivery.
- Each unfetched Child result is submitted to `TriggerService.submit_completion(...)` as soon as that Child becomes terminal; the tracker no longer waits for every sibling. The shared automation coordinator combines this result with every Bash or Sub-Agent result already ready at the Parent Session's current Run boundary. Siblings still running at that boundary remain tracked and are submitted for later delivery when they finish.
- Each Sub-Agent section names its public id and carries the complete final output (untruncated), Run status, and activity-file path when available. The combined automatic note begins with explicit guidance that it is not a new user request. The exact Child Run becomes fetched/read only after Chat durably persists the Parent note; a failed delivery leaves it unread, and Run-specific acknowledgement cannot clear a newer Child completion.
- A terminal `status` result that reaches Parent history first cancels that entry's still-pending automatic notice. Notice ids are stable per Parent Run and public work id, so duplicate terminal callbacks reuse one delivery instead of starting duplicate Runs.
- The `tool:subagent` System Prompt block owns delegation workflow guidance, the additional-Agent catalog, and context-specific execution guidance. It is contributed by the `subagent` Tool, enabled in the bundled layout, and gates out with that Tool. Native Tool/parameter descriptions remain short schema guidance; concrete success results own delivery and activity-file guidance.
- `SubAgentCoordinator` starts child Runs through the public `ChatLoop.child_loop` / `run_executor` surface; keep this boundary narrow until Runs exposes a dedicated child-run API.
