# Subagents

Sub-agent orchestration, in-memory batch tracking, parent-child run linkage, and child result lookup.

## Overview

`core/subagents/` owns the runtime behavior behind the public `subagent` and `subagent_result` tools. The tool module is only the registration/schema boundary; `SubAgentCoordinator` (in `subagents.py`) performs spawn/result orchestration and owns the in-memory `SubAgentBatchTracker` (in `tracker.py`) for one Runtime instance. Batch-tracking state machine logic belongs in `tracker.py`, spawn/result orchestration in `subagents.py`; callers import from the `core.subagents` package.

## Data Model

- `SubAgentCoordinator`: runtime-facing service with `spawn(context, arguments)` and `result(context, arguments)` handlers plus `prompt_targets(agent, project_id)` for the Tool-owned System Prompt block.
- `SubAgentPromptTarget`: prompt-only projection of one additional callable Agent with its exact Tool-call id, display name, and optional description. `catalog.py` builds this projection from the caller's snapshotted Tool settings plus the live Identity/Project catalogs and deliberately excludes the calling Agent.
- `SubAgentBatchTracker`: process-local tracker keyed by parent `(agent_id, session_id, run_id)`.
- Batch entries hold the child `agent_id`/`project_id`/`session_id`, its optional `activity_file`, completion/fetched flags and captured result, and either a live `run_id` or — while still queued — a `queue_item_id`.
- Every admitted spawn allocates a unique temporary Markdown activity file through Storage under `<data_dir>/artifacts/temp/subagents/`, including each new Run that reuses an existing child Session. `activity.py` projects replayable child Run events into this supplemental file: visible Assistant deltas are flushed live; finalized Assistant events provide a non-streaming fallback without duplicating streamed text; Tool entries contain only the Tool name, existing `ToolDisplay.summary`, and completed/failed state; User messages, Reasoning, raw/full Tool arguments, Tool result bodies, stdout, and stderr are excluded. The activity lease remains active while queued/running, starts Storage's 24-hour retention when the Run reaches a terminal event (or a queued item is removed), and failures affect only observability, never child execution or canonical Session history.
- Spawning also writes the durable parent→child link into the child Session's metadata: `is_subagent_session: true` plus a `subagent_parent` record (parent `agent_id`, `session_id`, `run_id`, `tool_call_id`, `tool_call_index`, `project_id`). The batch tracker is only the in-memory side; this metadata is what survives a restart (constants `SUBAGENT_SESSION_METADATA_FLAG` / `SUBAGENT_PARENT_METADATA_KEY`).
- `SubAgentBatchTracker.references_identity_agent(agent_id)` reports whether any unpruned batch still addresses that Identity Agent as an unqualified parent or child. Identity Agent rename uses this as a busy gate because a child batch can outlive the visible parent Run and its later completion callback still addresses the parent id; durable unqualified `subagent_parent` links are retargeted only after the tracker is clear.
- **Parent and target scope stay separate:** `subagent` and `subagent_result` parse their public `agent_id` through the canonical `parse_agent_address` seam. A qualified `agent@project` explicitly selects that target Project regardless of the parent's scope; a bare target preserves the existing rule by inheriting `context.project_id` (`None` means an Identity Agent, a set value means that Project's Team). The child Session, Run/queue key, metadata location, cancellation, result fallback, and navigation event all use the target `project_id`. The durable `subagent_parent.project_id`, tracker batch `project_id`, and automatic completion trigger keep the parent `context.project_id`, so the parent Session never moves or changes ownership. The child executor (`run_executor(content)`) takes no project id because the target scope rides `Run.project_id`.
- **Target authorization is a separate axis:** after address parsing and before any target lookup, Session mutation, quota reservation, or queueing, both coordinator operations enforce the caller's Run-snapshotted Sub-Agent Tool setting from root `tools.subagent.allowed_agents`. The setting contains additional targets only: omitting `agent_id` always selects the calling Agent in the same Identity/Project scope whenever the `subagent` Tool itself is active, and the calling Agent is never repeated in `allowed_agents` or the prompt catalog. An empty list is therefore self-only, not Tool-disabled. A missing setting or Identity-Agent `['*']` allows every resolvable additional Identity and Project Agent; explicit Identity entries are bare ids or qualified `agent@project` ids. Project-Agent targets are always constrained to the caller's own current Team, so a qualified cross-Project id cannot escape the Project boundary even if repository policy materialized as a wildcard.
- A spawn may carry the two-field `AgentRunOverrides` value (`model`, `thinking_effort`). The coordinator validates it together with target resolution before Child Session creation or batch-slot reservation, then captures it in the immutable Chat executor for immediate or queued execution. It changes only the resolved runtime view for that Child Run; no Agent, Project, or Session configuration is written.
- Batch tracking does not persist across restarts.
- The tracker reserves a per-turn slot before async spawn work begins, so sibling tool calls cannot bypass `max_subagents_per_turn` while they are waiting on session or queue state.

## Interfaces

- `SubAgentCoordinator(runtime, trigger_service, *, batch_tracker=None)` — `runtime` is typed as the `RuntimeServices` protocol (imported under `TYPE_CHECKING`); services are accessed directly, without `getattr` probes.
- `SubAgentCoordinator.spawn(context, arguments) -> JsonObject`
- `SubAgentCoordinator.result(context, arguments) -> JsonObject`
- `SubAgentCoordinator.batch_tracker -> SubAgentBatchTracker`
- `SubAgentCoordinator.prompt_targets(agent, project_id) -> list[SubAgentPromptTarget]` returns only additional Agents in deterministic Tool-call-id order. Project callers receive bare Team ids; Identity callers receive bare Identity ids and qualified `agent@project` ids for Project Agents.
- `SUBAGENT_SESSION_STARTED_EVENT` is exported for transport layers that need to bridge the live child-Session navigation event.

## Conventions

- With `session_id`, spawning routes into an existing Session; otherwise it creates a new persisted Session for the target Agent.
- Optional spawn arguments are coerced through the shared lenient policy in `core.tools.arguments` (see `tools.md`): a blank `session_id`/`agent_id` means omitted (creates a new Session / falls back to the calling agent), and `background` accepts string/0-1 booleans. A present-but-non-string value still fails `invalid_arguments`. `content` (spawn) and `session_id` (`subagent_result`) stay strictly required.
- A blank optional `model` means omitted, matching the shared lenient optional-string policy. `thinking_effort` deliberately uses presence-sensitive parsing because `""` is the canonical explicit Provider-default value; omission inherits the target Agent, while `null`, a non-string, or an unknown effort fails `invalid_arguments`.
- Child Runs execute through a streaming `ChatLoop`, matching normal live Runs and allowing long provider generations to make progress through stream deltas instead of waiting for one complete non-streaming response. `_make_subagent_executor(runtime, content, context)` builds the child via the public `runtime.streaming_chat_loop.child_loop(nesting_depth=...)` + `run_executor(content)` API, so child Runs inherit the attachment resolver and compaction service and resolve persisted media blocks / auto-compact like live Runs; only the nesting depth differs. A runtime without `streaming_chat_loop` is a wiring bug — there is no silent fallback loop.
- An explicitly targeted existing Session that is busy enqueues a follow-up Run through `ChatRunManager`; a freshly created Session that is already busy instead fails with `session_busy` (a new Session should never be busy).
- Foreground mode waits for completion and returns the result payload. The exact Child Run is acknowledged as read only after Chat durably appends that payload as the Parent Tool Result; producing the Child result or returning it from the handler is not delivery. Every successful `subagent` spawn result whose activity file was allocated also carries a contextual `activity_note` with the concrete path and the instruction to read it if the Sub-Agent's status or progress becomes relevant; this guidance is result data, not part of either Tool description.
- The `subagent` tool emits `subagent_session_started` Run events as soon as a child Session is known, then again when run/queue details are known. The event payload includes the parent tool-call id/index plus child `agent_id`, `session_id`, optional target `project_id`, optional `run_id` or `queue_item_id`, `status`, and stable `activity_file: string | null` so accessors can build the qualified navigation address before the final tool result exists.
- Background mode (top level only — forced to the foreground at nesting depth ≥ 1, see Constraints) returns a running descriptor when a Run has started. If the target Session is still busy and the child Run is only queued, it returns a queued descriptor containing `agent_id`, optional target `project_id`, `session_id`, `queue_item_id`, `status: "queued"`, and `activity_file` instead of waiting for the child Run to start. The queued path exists immediately and follows the eventual Run.
- Spawn/result payloads carry `activity_file: string | null`. `subagent_result` keeps that structured path but does not repeat the contextual `activity_note`. Result lookup is a non-blocking snapshot: it first resolves the caller's tracked Run/Queue entry, then the target Session's manager-owned active Run or Queue across later Parent Runs, and returns `running`/`queued` immediately without fetching the batch entry. Durable fallback accepts only a matching terminal Run Summary and the last non-empty Assistant message inside that exact Run segment; Assistant output without a following terminal summary is never a final result, an omitted `run_id` does not fall back past newer unfinished Session output, and the summary supplies the returned exact Run id and status. Only a proven terminal result is marked fetched and acknowledged after Parent persistence. `subagent_result` accepts the same bare/qualified address contract as `subagent`; a fallback with no surviving tracker association returns `activity_file: null`.
- Running and queued snapshots leave tracked entries unfetched so normal automatic completion delivery still fires; a terminal lookup marks only the exact resolved Run fetched.

## Constraints & Gotchas

- The caller cannot target its own active Session.
- Limits come from `runtime.storage.load_subagent_settings()` (re-normalized in-domain as a fallback): `max_subagent_depth` (default 4), `max_subagents_per_turn` (default 8), `subagent_timeout_minutes` (default 60). Full schema in `settings.md`.
- Foreground spawns wait at most `subagent_timeout_minutes` (default 60); on timeout the child Run is cancelled and the tool returns a `subagent_timeout` failure (the entry is still marked complete + fetched).
- Parent cancellation removes queued child Runs when possible and cancels already-started child Runs.
- **Forced foreground at nesting depth ≥ 1.** A sub-agent's Session is ephemeral — nobody reads it once it returns its single result — so a sub-agent cannot park work for a later run the way the top level can; a background spawn at depth would strand the child's result one level down (the batch-completion hand-off reaches only one level up). A spawn at `nesting_depth >= 1` is therefore forced to run in the foreground regardless of the requested `background` flag, gated by the single constant `BLOCK_BACKGROUND_AT_DEPTH` in `core/subagents/subagents.py` (set it to `False` to allow background spawns at depth — the single flip-back point). The top level (depth 0) is unchanged. When an explicit background request is overridden this way, the success result carries a `spawn_note` explaining why it ran in the foreground and that sibling spawns issued in one turn run concurrently (expendable guidance — the result payload is complete without it). Consequence: a forced-foreground child registers the parent-cancel cascade like any foreground spawn, so it dies with its parent.
- Parent-cancel cascade is **foreground-only by default**: only foreground spawns (and queued-then-started foreground waits) register the parent-cancel cascade callback; background spawns survive a parent cancel and keep running. The policy is gated by a single constant `CASCADE_BACKGROUND_CHILDREN` in `core/subagents/subagents.py` — set it to `True` to restore the legacy "cascade to all children" behaviour. This is the single flip-back point.
- Run overrides are not ambient nesting state. A nested `subagent` call that omits them resolves its own target's configured values even when the calling Child Run itself uses overrides; continuing the same Child Session also requires the fields again on each Run that should use them.
- When the parent is cancelled with reason `user`, the cascaded child Run is cancelled with the same reason (`request_cancel(reason="user")`). A child cancelled with reason `user` is reported to the parent as a `cancelled_by_user: True` entry: the foreground `subagent` tool result, the `subagent_result` lookup result, and the batch-completion note all use the "Cancelled by the user" wording. Non-user cancellations keep the generic "Cancelled" wording.
- A batch is dropped from the tracker only once *every* entry is both complete and fetched; an empty batch (no entries, no reserved slots) is dropped too.
- Every event that can turn "some entries open" into "all complete" re-runs the one completion check (`_notify_or_prune_if_complete` in `tracker.py`): a child finishing (`on_sub_agent_complete`) **and** a queued child's entry being removed (`remove_queued` — e.g. the user removes the queue item via `chat.queue_remove` and the cancelled item future propagates into the tracker). Without the removal-side check, a batch whose last open entry was a removed queued child would never fire the promised completion note and would leak with every sibling's full result text.
- When all unfetched sub-agent Runs in a batch finish, the tracker sends one internal automation trigger to continue the parent Agent via a system-reminder note. The trigger passes the batch's `project_id`, so a project parent continues under its project instead of failing identity resolution. The note carries each sub-agent's complete final output (untruncated), run status, and activity-file path when available, so the parent does not need a `subagent_result` fetch to read batch results. Each exact Child Run is acknowledged as read only after Chat durably appends that note to the Parent Session; a failed trigger or persistence leaves it unread, and the Run-specific acknowledgement cannot clear a newer Child completion. Runtime automation triggers use the streaming Chat loop, so this follow-up Run emits the same SSE delta timeline as a normal streamed chat turn.
- Entries embedded in the completion note are marked fetched immediately after the trigger is scheduled, so the batch is dropped right away. Without this the standard background flow leaks one batch (including each child's full final output string) per parent run for the server-process lifetime, because the tool contract forbids fetching noted results via `subagent_result`.
- The `tool:subagent` System Prompt block owns delegation workflow guidance and the additional-Agent catalog; it is contributed by the `subagent` Tool, enabled in the bundled layout, and gates out with that Tool. The short native Tool/parameter descriptions describe only their operations and fields and never receive a dynamic `Allowed agent targets` suffix. The concrete successful spawn result separately owns contextual activity-file guidance; `subagent_result` remains the explicit lookup surface and does not repeat that instruction.
- `SubAgentCoordinator` starts child Runs through the public `ChatLoop.child_loop` / `run_executor` surface; keep this boundary narrow until Runs exposes a dedicated child-run API.
