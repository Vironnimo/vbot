# Compaction Run Coordination

How `core/compaction/run_coordination.py` runs Compaction inside Runs: preparation, when automatic Compaction evaluates, the context-card request, commit and staleness, the Compaction Run events, limits, failures, logging and the prompt refresh through Chat's host. The host boundary, the reclaim floor and the invariants are in `compaction.md`.

## Preparation

Manual Compaction resolves Project paths, Settings, Model routes and Adapters on the Chat preparation worker. Automatic Compaction uses the same worker boundary for its Context window and summary Adapter. The coordinator retains every acquired Adapter before a worker returns, so cancellation waits for preparation and closes new Adapters even when the awaited result is discarded; the active Run's Adapter remains owned by that Run.

## Evaluation

- Automatic Compaction evaluates once immediately before each needed Model request, for both Strategies and fallback targets, after delivering selected steering input, joining pending Notes, applying request hooks and limiting media. A final Assistant answer triggers no automatic Compaction; a later Run evaluates its own prepared request. Withdrawn steering that leaves no work ends the Run without another check (user decision 2026-10-15). A checkpoint or stale-result rebuild re-renders the changed request's context hooks and media without repeating input delivery or Compaction at that boundary.
- Every decision uses the actual request target's Context Window and the shared Run-local projection: measured Provider input plus selected-wire request changes while the measurement scope matches, otherwise the target Adapter's complete request estimate. A checkpoint resets that measurement scope; manual Compaction always estimates its rebuilt request; raw records removed by a `history_edit` never re-enter a later checkpoint.
- Summary+Tail defers an otherwise eligible automatic attempt when this Run's newest unconsumed Tool batch contains a freshly loaded Skill (the next Model step must receive that Result first), re-evaluating before the next needed Model request after consumption. A batch written by an earlier Run never defers: that Run ended before a Model step consumed it, so waiting could keep an oversized Context forever (`test_summary_tail_waits_until_this_runs_loaded_skill_result_is_consumed`, `test_a_failed_runs_loaded_skill_result_never_blocks_the_next_runs_compaction`).
- The new-context check runs before any Model call: Summary+Tail needs a non-summary Head; Continuation needs non-checkpoint content added since the latest checkpoint whose estimate reaches the reclaim floor (the new summary is assumed no smaller than the one it replaces), so fixed overhead above the trigger never causes a paid Continuation call per boundary (`test_continuation_skips_model_call_without_reclaimable_new_context`). An automatic checkpoint is inserted before the needed Model step and the Agentic Run continues from it. Manual `/compact` performs no follow-up Agent Model call.

## Context-card requests

The Chat context-card action requests Compaction inside the exact active Run. It bypasses automatic enablement, token thresholds and the fresh-Skill deferral; the configured Strategy, complete Tool-cycle boundaries, new-context check, minimum reclaim, and cursor validation remain unchanged. A checkpoint right after a Skill load ends that activation like any other, so the Skill-loading Result becomes a digest and the `[compaction-skills]` reminder asks for a reload. Requests coalesce while pending/running; a terminal Run cannot carry a request into its successor. Only such a pending request can run Summary+Tail after a final Assistant response; that checkpoint affects the next Run, and Stop during that requested attempt aborts only the Compaction (`chat/run-execution.md` -> Cancellation). Started/completed/aborted events identify user-requested attempts, including a request that cannot run before completion (`core/compaction/run_coordination.py`, `tests/core/chat/test_chat_loop_compaction.py`).

## Commit and staleness

Manual attempts load one complete snapshot and its cursor under the Session write lock. Automatic attempts never reload complete history: they bring the Run snapshot current with a delta read under that lock and compact its active lineage (`test_automatic_compaction_boundaries_never_reload_complete_history`, `test_edit_run_compacts_only_its_edited_lineage`). Both plan and call Models outside the lock, then re-acquire it briefly for `ChatSession.commit_compaction` (`commit_compaction_async`; the cursor check, `PromptEpoch` write and returned delta: `sessions/history-api.md`).

- Notes that other writers append during an automatic attempt's Model call are not in its summary: before committing, the attempt absorbs them into the Run snapshot under the lock and `carry_notes_into_checkpoint` keeps them verbatim after the checkpoint's Tail, exactly like the Tail messages, so they stay in the live Context. A writer landing while the request projection runs fails that commit and the next attempt absorbs it too, at most `AUTO_COMPACTION_COMMIT_ATTEMPTS` attempts per Model call.
- Any other appended entry (a message, Tool result, checkpoint, or a Skill-context or Tool-change note of the ending prompt epoch), a cursor discontinuity (edit or takeover), or exhausting the attempts makes the result stale: it writes nothing and aborts without a checkpoint or prompt-epoch change, and automatic attempts rebuild request state. Manual Runs never carry notes and fail with retry guidance on any change. Concurrent notes remain available.
- A note can also reach the Session without reaching the live request the summary is written from, for example when another writer appends it after the request was built but before the attempt brings its snapshot current. The summary cannot cover such a note, so both strategies keep it verbatim after the summary and before the Tail: Chat's `wire_shaping.notes_missing_from_request` compares each note group with the request messages that replay would put before the next sent message, and a group that does not match is kept whole, so an unverifiable note is duplicated rather than lost (`test_checkpoint_keeps_notes_its_summarized_request_never_showed`). Projected-request failure likewise aborts (`test_mid_tool_compaction_meets_a_concurrent_entry_and_rebuilds_the_request`, `test_automatic_compaction_absorbs_notes_landing_during_projection_up_to_a_bound`, `test_checkpoint_carries_only_plain_notes_appended_after_its_snapshot`).

## Run events

The coordinator emits the shared lifecycle on the Run (constants in `core.runs`, `runs/events.md`); none is transient.

- `compaction_started`: an automatic attempt emits `{context_tokens_before, context_usage}` once its summary Adapter is acquired; a manual Compaction Run emits `{context_usage}` (or `{}` without one) after loading its snapshot.
- `compaction_aborted`: `{reason}`, non-sensitive, when no checkpoint will follow: `cancelled`, `failed`, `run_finished`, `context_window_unavailable`, `no_compactable_context`, `insufficient_reclaim` or `stale_context`.
- `compaction_completed`: `{message, checkpoint, checkpoint_id, context_tokens_before, context_tokens_after, context_usage?, duration_ms}` after persistence, where `checkpoint` is the ordinal and `message` the checkpoint record, whose Usage carries the same token pair so History reloads keep the completed presentation. It is emitted with `allow_after_cancel` because the checkpoint is already stored.
- While a context-card request is pending, the Run adds `requested_by_user: true` to all three (`core/runs/run.py::Run.emit`).

## Limits and failures

- Compaction Model work has one absolute 420-second budget across its attempts and retry backoff, including local routes; fresh text, Reasoning and heartbeats never extend it. The shared 180-second transport and 900-second Model-progress guards still apply within that budget. Summary text is limited to 100,000 streamed characters (user decisions 2026-10-14), checked before accumulation; Reasoning is bounded by time, not by that text limit. A limit failure closes the request iterator, records reported Usage as failed, never retries in place and cannot produce a checkpoint, even when the Provider suppresses cancellation and reports success afterward. Graceful transport cleanup and durable Usage writes can settle after the deadline. Chat can continue with its existing request state after a failed attempt. Coverage: `test_compaction_stalled_stream_is_bounded_and_closed`, `test_compaction_deadline_covers_active_output_and_recovery`, `test_compaction_summary_limit_rejects_without_retry_and_closes` and `test_failed_auto_compaction_retries_at_the_next_boundary`.
- Failed automatic Compaction settles its started row as a visible warning and leaves the Agentic Run untouched; stale-context and insufficient-reclaim skips remove their placeholder. Failure warnings exist only as Run events, never as persisted checkpoints; failed/cancelled manual Compaction terminates its dedicated Run accordingly - neither path appends a checkpoint.
- A Stop that arrives while the manual checkpoint commits cannot undo the write (the Session database's worker finishes it), so `ChatCompactionHost.commit_checkpoint` waits for the outcome like Chat's visible boundaries: a stored checkpoint emits `compaction_completed` (published after the cancel) and logs `Compaction completed`, and only the Run itself ends cancelled, its terminal payload carrying the stored `checkpoint_id` (as every completed manual Compaction Run's does), so `ChatLoop.compact_session` still replies `Context compacted.`; a commit refused as stale ends it cancelled without a checkpoint (`test_stop_during_the_checkpoint_commit_reports_the_stored_checkpoint`).

## Logging

- An expected failure (a `CompactionError` raised by Compaction itself or wrapping a vBot error such as a Provider or network failure) logs one WARNING without traceback naming run, Session, trigger, Model (`CompactionError.model`, set when a Model call failed) and cause; any other exception logs ERROR with its traceback (`test_failed_compaction_logs_and_keeps_the_request`).
- A committed Compaction logs one INFO `Compaction completed` line (`vbot.compaction.coordination`) with run, Agent, Session, `trigger` (`auto` when a configured threshold fired, `manual` for the context-card request and manual Compaction Runs), `reason` (`context_ratio`, `input_tokens`, or `output_reservation`; `requested` for the context card; `command` for a manual Compaction Run), input tokens, `tokens_after`, `carried_notes` (automatic attempts only) and duration. The triggered, skipped, discarded and requested lines and each in-place Model retry log at DEBUG (`test_automatic_compaction_commits_a_checkpoint_and_rebuilds_the_request`, `test_user_compaction_waits_for_tool_result_and_continues_run`).

## Prompt refresh

Temporary Agents refresh from their admitted immutable configuration, never the Identity/Team resolver, and rescan Skills without a private Identity scope. Their Working Project Context pins and refreshes like ordinary Sessions, including temporary self-delegation. Applying a committed refresh replaces SOUL and Memory in the active Run as well as the persisted prompt pins (`core/chat/compaction_host.py`, `tests/core/chat/test_chat_loop_compaction_prompt_epoch.py`).
