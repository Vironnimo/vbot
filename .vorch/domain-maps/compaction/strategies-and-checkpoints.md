# Compaction Strategies and Checkpoints

How the Compaction Engine (`core/compaction/compaction.py`, `_tail.py`, `_model_request.py`) builds one checkpoint: the Model call and its target, both Strategies, Tail selection, checkpoint content, the User quote, summary acceptance and Usage recording. The checkpoint contract, the epoch endings and Policy resolution are in `compaction.md`.

## Model call

- The Model call always consumes the adapter's canonical stream through Chat's shared accumulator, without passing normalized content back through a raw Provider response parser: some providers (observed on OpenRouter's stealth tier) reject large non-streaming completions outright while streaming the same payload fine.
- Both paths supply the exact Session address and current prompt-cache affinity to the Engine. After selecting the Strategy's active or Summary target, the Engine obtains request-context kwargs from that target Adapter; never copy another Adapter's wire-specific context or omit it for internal Model calls. The affinity is the Session's and a committed checkpoint keeps it, so the new epoch's unchanged System Prompt and Tool prefix stays on its Provider cache route. On the active target the Model call sends the Agent's `thinking_effort`, exactly as the Run's requests do (effort updates included), because a different reasoning setting renders a different prompt and loses the Run's cache; it sends no sampling parameters, and another target gets the Provider default. A `summary_model` that names the active Provider and Model, without a different Connection, is the active target and reuses the active Adapter (`compaction.py`, `run_coordination.py`, `_request_builder.py::resolve_summary_adapter`; `test_chat_loop_compaction_requests.py`).
- The Model call scopes an Adapter input budget (`request_input_budget`) like a Chat request, so the output limit and prompt-limit checks use a corrected count: the selected wire's estimate of exactly the sent messages and Tools, times the target Model's input estimate factor (`estimate_factor` on the active target, the Usage recorder's factor for another Summary Model). A request that appends to the complete active request, as Continuation does, builds instead on Chat's Context of that request when the caller passes it (`active_context_tokens`: measurement plus corrected change) and adds the appended reminder's corrected estimate; Run coordination does not pass it yet. Compaction Model calls do not teach the calibration (`_estimates.py::_model_request_input_budget`; `test_compaction_request_carries_its_corrected_input_budget`).

## Strategies

- `SummarizationStrategy` slices the already-built provider request immediately before the Tail boundary and calls the resolved Summary Model once after appending one System Reminder through Chat's canonical note renderer. The Reminder contains only the shared automatic/manual Compaction instruction; the Tail is absent from the request and follows the returned summary natively in the Projection. Older steps move wholly into the summarized prefix; no message is a mandatory Tail anchor, and ordinary retained Tool payloads are not shortened. When Summary and active targets match, the native prefix including Provider Reasoning remains unchanged for cache reuse; a different target strips Provider-owned Reasoning from the prefix because that state cannot cross targets.
- `ContinuationStrategy` requires the completed active provider request, appends one canonical System Reminder asking for checkpoint Context, calls the active Model once with the same Tool definitions, and uses the response directly as Projection - the cache-preserving append-only shape. Automatic Continuation runs at the shared pre-request boundary only when the same Run will continue. Manual Continuation uses its separate no-active-Run prompt. Neither path changes Context between an Assistant Tool Call and its correlated Tool Results.
- Automatic Summary+Tail never re-summarizes only its own previous Summary; it advances within long turns once older cycles move to Head, always governed by threshold/usefulness/reclaim floor.

## Tail selection

- `find_tail_boundary` selects a chronological suffix of whole steps. A step starts at a User or Assistant message and includes the notes directly before it (for example delivered Board messages), so an input stays with the response that reacted to it; against a live request the notes join the step only when they render as exactly the request messages before it, otherwise the step starts at its User/Assistant message and the notes are summarized. The configurable `tail_tokens` is the request-side size the Tail should reach: the first whole-step start at or above it wins while the Tail stays within 150% of it; otherwise the largest start down to 70%; without one, the first start past 150% (for example one oversized step). Only a history shorter than the target yields a smaller Tail. Every step start is an equally valid cut: tool calls and their results always stay together, so the provider-visible sequence stays valid wherever the Tail begins. No second compaction Model call is made to repair the size (`core/compaction/_tail.py`, `tests/core/compaction/test_compaction_tail_selection.py`).
- **Counts.** Every Compaction count is in the Session's Context unit: the active Adapter's wire estimate, in which replayed Reasoning costs its reported tokens, times the active Model's input estimate factor (`estimate_factor`, from Chat's Context accounting; `_estimates.py`). Tail planning counts slices of the already-built request, including replayed Reasoning, resolved media and request-only Tool media. The Continuation new-context check, the reclaim floor and `compacted_token_count` count canonical history as that request sends it (`wire_shaping.history_request_messages`): a message the live request sends counts as sent there; any other message, a message the Projection rewrites (a digested Skill Result) and every note count as a request without replay renders them. Reasoning without a reported count stays approximate under the shared opaque-blob reservation (`test_continuation_counts_new_content_as_the_active_request_sends_it`).
- Tail boundary safety uses one reverse pass through messages and Tool Calls. Its accepted suffixes match the Projection validator even for malformed history, duplicate Call IDs, and ignored timeline metadata; an invalid older prefix cannot exclude a valid newer suffix. Checkpoint Projections are still validated independently (`_safe_tail_boundary_indices`, `_validate_projection`, `test_find_tail_boundary_keeps_only_provider_safe_suffixes_of_historical_sequences`).

## Checkpoint content

- The after count builds and estimates the exact projected request under Chat's one Context rule (`chat/usage.md` -> One Context rule) and records the factor it used (refreshed System Prompt, request-only Context, retained Summary+Tail, same-Run Reasoning/Tool restoration, complete Tool definitions) - explicitly approximate in the UI, never derived by subtracting reclaim from a differently scoped estimate.
- The Projection constructor guarantees it starts with the matching `[compaction-summary]` note. Retained Tail Assistant turns keep their reasoning fields, meta and scope unchanged, so the next Run resends the Tail exactly as the compacting Run sent it after the checkpoint and the Provider prompt cache keeps that prefix; request shaping applies the ordinary replay policy and scope rules to them (`test_next_run_continues_the_compacting_runs_request_byte_for_byte`).
- The summary is framed as historical reference and ends with an explicit boundary marker; standalone outer System Reminder delimiter lines and checkpoint framing copied by the Model are discarded first, for both strategies, and a response with no text left after that is rejected. The native Tail follows without an extra serialized copy or Tail-guidance note. Its framing describes the state at the cutoff and directs unfinished work to continue from the summary plus later chronological messages without reissuing historical requests. Chat appends an ordinal guidance sentence (`COMPACTION_CHECKPOINT_GUIDANCE`, `_message_history.finalize_checkpoint_guidance`, reasons in `chat/agent-facing-text.md`) stating that earlier original messages left active Context and stay stored unchanged; Compaction changes no Tool list (the retired `history` Tool: `tools/history.md`).
- **User quote.** If the latest User is before the Tail cutoff, the checkpoint carries its exact canonical JSON in a historical-quote note adjacent to the summary. Angle brackets are escaped at that boundary, preserving decoded content, attribution, and timestamp without allowing quoted reminder delimiters. The summary explains the User's reference and agreed work from the preceding context. Later compactions carry this one quote from the effective checkpoint until a newer User replaces it; a User already in the native Tail needs no duplicate quote. Quote-only history does not count as new compactable work; hidden canonical history is never reopened to reconstruct the quote (`test_user_quote_is_escaped_carried_forward_and_replaced_by_a_newer_user`).

## Summary acceptance

Model-backed Compaction requires an explicit successful `stop`, summary text that stays non-empty once copied reminder delimiters and checkpoint framing are removed, and no Tool attempts. Truncated, filtered, unsuccessful, unknown, or missing stream finishes abort without a checkpoint; both strategies use this same acceptance boundary (`test_compaction_accepts_only_a_completed_text_summary`). A retryable Provider failure, such as a stream cut short by a dropped connection, gets one in-place retry after the shared `compute_retry_delay` backoff (`_model_request.py`, whose `_sleep` seam tests patch); acceptance failures, non-retryable errors, stalls and cancellation never retry. Each attempt records its own Usage row (`test_compaction_attempts_retain_usage_and_retry_a_transient_failure_once`).

## Usage

The Engine records successful Model-backed work as `usage.model_call = {model, usage}` on the checkpoint, including canonical token counters, the cost snapshot and the stable `usage_call_id` from `core/usage` (`usage.md`). Runtime injects the shared Model registry lookup and Usage recorder; the coordinator passes both full Model references and Run/Extension-group identity so summary-target and active-target accounting cannot be confused. The private `_model_request.py` stream boundary records every exposed Adapter invocation, including partial Usage on failure/cancellation, before checkpoint validation or commit. Rejected summaries, insufficient reclaim and stale results therefore retain their reported consumption independently of checkpoint persistence. Duration and direct before/after Context estimates remain separate checkpoint fields. Zero-call Strategies have no invented Model usage. Coverage: `tests/core/compaction/test_compaction_model_request.py`.
