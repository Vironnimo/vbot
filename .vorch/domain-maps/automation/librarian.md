# Librarian

Read when changing or debugging Librarian passes: the schedule, aging, the consolidation Run, the state document, the `librarian.*` RPCs and CLI, or the Librarian's Agent-facing texts. The boundary and the invariants are in `../automation.md` -> Librarian; the built-in Librarian Agent itself (creation, fixed Tools, hidden surfaces, Skill subject) in `../agent.md` -> Built-in Librarian; the WebUI surfaces in `../webui/settings.md`; the learning evaluation of passes in `learning-evaluation.md`.

## Owner and entry points

- `core/automation/librarian.py` (`LibrarianService`, Runtime `librarian`). Runtime builds it in `_bootstrap.py::_librarian_service` over the Skill authoring service, `agent_skills_dir`, a `StatisticsService` for Skill use (`skill_usage_async`), `AutomationReferences.agent_triggered_skill_names`, `Runtime.shared_skill_names` (the Skills the Agent shares, read on the worker), `ReflectionService.reviewing` and the Skills change notification. `ReflectionService` in turn reads `LibrarianService.running` (`../automation.md` -> Reflection).
- Blocking state, history and package work runs on the `librarian` `BoundedWorkerPool` (2 workers); Skill writes and the history reads of aging and fingerprints hold `AgentStore.lifecycle_guard`. `status` and the pass counts read only the recorded history (`SkillAuthoringService.recorded_revisions`, no outside-change observation) without the guard; a home that is gone or unreadable has no revisions there.
- Tests: `tests/core/automation/test_librarian.py` (aging, consolidation and its Session, state and pass history, status and overview, refusals, schedule), `tests/server/rpc/test_librarian_methods.py`, `tests/cli/test_cli_librarian.py`, `tests/core/prompts/test_briefs.py` (brief and candidate format), `tests/core/automation/test_references.py` (triggered names), `tests/core/sessions/test_sessions_listing.py` (pass Sessions listed in the Librarian's scope).

## Schedule

- `start()` (normal startup only, after the archive retention sweep; `runtime.md`) runs a check `FIRST_CHECK_DELAY_SECONDS` (300) after start, then every `CHECK_INTERVAL_SECONDS` (3600). `_wait` is the test seam. A failed check logs WARNING and the next one retries.
- A check reads `librarian.*` live and does nothing while `enabled` is false or the Librarian Agent is unavailable (`AgentStore.librarian_problem()`, `../agent.md`). For each Identity Agent of the roster (`agents.list()`, which never holds the Librarian), one at a time (`_check_agent`; one that raises logs WARNING and the check goes on with the next Agent): skip all while a pass runs; skip an unreadable state document (WARNING); an Agent with neither `last_pass` nor `first_seen_at` (after a running record became the last pass, see State document) only gets `first_seen_at` = now and is due one interval later (design decision: a new or upgraded installation gets a full interval before its first pass); otherwise skip until `interval_days` after `last_pass.finished_at`, else after `first_seen_at`. A failed or interrupted pass counts like a completed one, so it is not retried before the next interval (design decision: a pass that keeps failing costs at most one consolidation Run per interval). A due Agent runs only when it resolves, is eligible, has no active or queued Run (`ChatRunManager.has_activity_for_agent` with `project_id=None`) and no automatic review starting or running (`reviewing`, which covers the moments before and after the review's Run), and the Librarian has no active or queued Run either (its pass Run, or the user chatting with it); this is checked again after the last await so nothing starts in between.
- **Passes run one at a time, over all Agents** (user requirement): the schedule awaits each pass before the next Agent, and `run` refuses while any pass runs. A pass is the Librarian's Run, and the Librarian is one Agent with one FIFO per Session; one pass at a time keeps its Runs and the passes' Skill-use reads apart.
- Project Runs and Project automations are not considered, by design: a Project Run executes a Config Agent, which has no private home, never loads an Identity Agent's own Skills (`SkillRuntime.skills_for` gets no identity for it, `resolve_skill_scope`) and cannot call `skill_manage`, even when its slug equals an Identity Agent id. An Identity Agent's own Runs, rooted ones included, carry no Project id, and the automations that trigger its Skills are those targeting it without a Project (`AutomationReferences.agent_triggered_skill_names`, `tests/core/automation/test_references.py`).
- A check reads Skill use (`skill_usage`, every Agent's) once, at its first due, idle and eligible Agent, and passes it to the following passes; after a pass that ran a consolidation Run it reads it again, because other Agents can use Skills during the minutes the Run takes. A manual pass reads its own. Use is keyed by the Session's owner, so the Librarian loading an Agent's Skill in its own Session never counts as that Agent's use.
- Eligible (`_blocked` returns no reason): the Librarian is available, and the Agent is an Identity Agent of the user (not the Librarian) whose own `librarian_enabled` switch is on (`../agent.md`; a missing or `null` value in `agent.json` reads as on) and whose private Skill home holds at least one Skill (`_has_own_skills`). The switch is the user's per-Agent opt-out (user requirement); `librarian.enabled` stays the master switch of scheduled passes. Neither is read outside this service, so neither touches any Agent's System Prompt, Tool definitions or ordinary Sessions. The Agent's own Tool access does not matter: the Librarian, not the Agent, calls the Tools.
- `run(agent_id)` starts a manual pass at once, regardless of `interval_days` and `enabled`, as a task, and returns `status`. Refusals, checked in this order before anything changes: shutting down -> `LibrarianBusyError`; not an Identity Agent -> `AgentNotFoundError`; the Librarian itself -> `LibrarianUnavailableError` (`The Librarian maintains the Skills of other Agents and gets no pass itself.`); unreadable state -> `LibrarianStateError`; not eligible -> `LibrarianUnavailableError` (the Librarian unavailable: `librarian_problem_message`, see Surfaces; the switch off: `The Librarian is off for Agent <id> (librarian_enabled is false), so it does not curate its Skills.`; no Skills: `Agent <id> has no Skills of its own, so the Librarian has nothing to curate.`); a pass of the Agent running, another Agent's pass running (`A Librarian pass of Agent <other> is running; passes run one at a time, so start this one when it has finished.`), an active or queued Run of the Agent or an automatic review starting, or an active or queued Run of the Librarian (`The Librarian has an active or queued Run; start the pass when it is idle.`) -> `LibrarianBusyError`.
- Passes start and end announce through `status_changed` (Runtime publishes `resource_changed(skills)`, `server/events-and-reconnect.md`).

## A pass

1. **Aging** (no Model, `_age_library`): archives with `SkillAuthoringService.delete(..., reason="inactive")` as writer `SkillWriter(actor="librarian", run_kind="librarian")` (no Session or Run id) every Skill of the Agent's private home that is unpinned, has origin `reflection` or `librarian` (`AGED_ORIGINS`), is not triggered by a live automation of the Agent, is not shared with other Agents (design decision: sharing is the user's choice, and a receiver's use does not count as the owner's use, so aging would retire a Skill another Agent depends on), and whose newest activity is older than `archive_after_days`. Activity is creation, the newest file change by an attended writer (`human`, `agent` or `external`; changes by `reflection` and `librarian` writers do not keep a Skill) and the Agent's last use (`SkillUse.last_activated`, Statistics; background Sessions are not use). A time that cannot be parsed never ages a Skill. One Skill that cannot move logs WARNING and the rest continue. Archiving anything invalidates the Agent's Skill caches and publishes `skills` (`skills_changed`) and logs one INFO line with the count.
2. **Consolidation** (`_consolidate`), only when `consolidate` is on (else outcome `disabled`), at least two candidates exist after aging (else `too_few`) and their fingerprint differs from `consolidation_fingerprint` (else `unchanged`). Candidates (`librarian_candidates`): every loadable, unpinned Skill of the home, whoever created it, each with description, origin, created and last-changed dates, last use and use count, SKILL.md length and support files. The fingerprint is a SHA-256 over the sorted (name, latest revision id) pairs of the candidates.
   - The brief (`librarian_brief(..., agent_id=, agent_name=)`, `core/prompts/briefs.py`) is rendered on the worker. Then a new Session of the Librarian is created (`ChatSessionService.create_async("librarian", run_kind=RunKind.LIBRARIAN, metadata=...)`), whose creating write already holds the Run kind, `skill_agent_id` = the Agent (`SKILL_AGENT_ID_KEY`, `../agent.md` -> Built-in Librarian -> Skill subject) and the title `Skills of <Agent name> · <YYYY-MM-DD>` (the server's local date) as `auto_title` with `auto_title_initialized` set, so no title is generated and the user can rename it (`sessions.md`). One internal Run starts on the streaming loop: `start_run("librarian", brief, session_id=, internal=True, run_kind=RunKind.LIBRARIAN)`, nothing else. It runs with the Librarian's own Model and Model settings (`agent.update` / `vbot agent update librarian`; a new Librarian resolves `defaults.agent.model`), its fixed Tools `skill` and `skill_manage`, and Chat's normal Tool iteration limit (`MAX_TOOL_ITERATIONS`). In this bound Session the resolver gives the Librarian the Agent's Skill pool (`projects/resolution.md` -> Librarian Skill subject), so its System Prompt lists the Agent's current Skill catalog and both Tools work on the Agent's Skills. The Run counts as the Librarian's activity (Statistics, Agent activity), not the Agent's.
   - Inside the Run, `skill_manage` writes as actor `librarian` with the Session, Run id and Run kind (`skills.md` -> Background Writer): it never changes a pinned Skill and deletes only with `absorbed_into`, and a delete with `absorbed_into` moves the deleted Skill's shares and the automations that trigger it to the absorbing Skill (`tools/skill.md`). A change to an existing Skill that another Run or a person changed after the consolidation Run started is refused once with `skill_changed` (`skills.md` -> `skill_manage`), so the Run reads that Skill again before it merges over the change. A Skill absorbed into an umbrella that a later pass absorbs again still loads the newest umbrella (`skills/history.md` -> holder).
   - A Run that cannot start deletes the new, empty Session and ends as `failed` with the error; a Run that fails ends as `failed` with its Session and Run ids. Only `ran` records a new fingerprint (computed from the candidates as the Run left them); `failed` keeps the old one, so the next pass retries.
3. The pass counts the consolidation Run's revisions (`created` = Skills with a `create`, `merged` = Skills archived with reason `absorbed`, `changed` = the other Skills it wrote), writes the state with outcome `completed` and logs one INFO line (Agent, trigger, counts, outcome).
- While it runs, a pass keeps its record in `running_pass` (see State document): written when it starts, after aging archived anything, and once the consolidation Run started, before the pass awaits the Run, so a crash or shutdown leaves the Session, Run and aging revisions on record.
- A pass that raises logs WARNING and writes its record as `last_pass` with outcome `failed` and the `error`, with what it did so far (the counts of a started Run included); a pass whose state document could not be read writes nothing.
- **Pass Sessions are kept** (user requirement): vBot never deletes the Session of a pass whose Run started. It is an ordinary listed Session of the Librarian (`sessions.md`; hidden from Recall like every Session with a `librarian` Run): the user opens it from Settings or the Agent's Skills page, reads what the Run did and can go on talking with the Librarian there about the Agent's Skills; those user Runs write as `librarian` too (`skills.md`). Revisions, `skill.revert` and `learning.changes` / `learning.undo` (with the curated Agent's id and the Run id) work from the Skill history and do not need the Session; the Run's Model usage stays in the Usage ledger (`statistics.md`).

## State document

`agents/<id>/librarian.json` of the curated Agent, durable kind `librarian_state` (`settings.md` -> JSON documents; validated by `doctor config`, in data snapshots), format version 1, `LIBRARIAN_STATE_FORMAT`:

- `first_seen_at` (when a scheduled check first saw the Agent), `last_pass`, `earlier_passes`, `running_pass`, `consolidation_fingerprint`; unknown fields warn.
- `last_pass`: `started_at`, `finished_at` (timestamps), `trigger` `schedule`|`manual`, `outcome` `completed`|`failed`|`interrupted` (missing reads as `completed`), `archived`, `candidates`, `created`, `changed`, `merged` (non-negative integers), `archived_revisions` (the aging revision ids), `consolidation` `ran`|`unchanged`|`too_few`|`disabled`|`failed` (`failed` also when the pass stopped before the step), optional `session_id`, `run_id` (the Librarian's Session and Run), `error` (why the pass or its consolidation Run failed).
- `earlier_passes` (optional list, newest first, added within format 1 because a missing list reads as empty): the passes before `last_pass` in the same form, so the state keeps at most `LIBRARIAN_PASS_HISTORY` (10) passes; a pass's final record moves the previous last pass in front of the list and drops the oldest (`LibrarianState.recorded`).
- `running_pass`: the same form, the record of the pass in progress as of its `finished_at`, with outcome `interrupted`. Whenever no pass of the Agent runs in this process, a `running_pass` is read as the last pass (`LibrarianState.settled`): vBot stopped during that pass. The next pass's writes replace it.
- A missing document is an empty state. An invalid one raises `LibrarianStateError`: `status` and `run` refuse, the schedule and the overview skip the Agent; nothing overwrites it until it is fixed. Writes happen only while the Agent exists (under the lifecycle guard), so a removed Agent keeps none; the file lives in the Agent tree `agents/<id>/`, which an Agent rename and an Agent archive move as a whole.

## Status, overview, report and undo

- `status(agent_id)` -> `{agent_id, settings, available, unscheduled_reason, librarian_problem, running, running_since, last_pass, passes, next_due_at, changes}`. While no pass of the Agent runs, a `running_pass` is the last pass. `available` is false when no pass can run at all (`run` refuses). `unscheduled_reason` (`UnscheduledReason`) names the one reason the Agent gets no scheduled pass, in this order: `librarian_unavailable` (`librarian_problem` says why: `agent_id_taken`, `invalid_config` or `missing`), `agent_disabled`, `no_skills`, then `schedule_disabled` (`librarian.enabled` is off; a manual pass still runs); `null` while it gets them. `next_due_at` is set only while `unscheduled_reason` is `null`; for an Agent no check has seen yet it estimates one interval from now. `passes` are the Agent's recent passes, newest first (`last_pass` first). `changes` are the home's revisions of the last pass, newest first: the ids in `archived_revisions` plus the `librarian` revisions with the pass's `run_id` (`SkillRevision.to_dict`, `skills/history.md`). An interrupted pass never counted its Run's revisions, so `status` counts them from `changes`. The Librarian's own id refuses with `LibrarianUnavailableError`.
- `overview()` -> `{agent_id: "librarian", available, problem, settings, running, passes}`: whether the Librarian is available and why not, the Agent whose pass runs (or `null`), and the recent passes of all roster Agents, newest first, at most `LIBRARIAN_OVERVIEW_PASSES` (20), each a pass record plus `agent_id` and `agent_name`. It feeds the Settings panel and `vbot librarian status` without an Agent.
- The whole pass is taken back with `skill.revert` over those revision ids (all or none; the CLI prints the command, the WebUI's Revert together sends it). `learning.changes` / `learning.undo` (`../automation.md` -> Reflection) also serve the consolidation Run by the curated Agent's id and the `run_id`, but not the aging archives, which carry no Run id.

## Surfaces

- RPC `server/rpc/librarian_methods.py`: `librarian.status {agent_id}` -> the status; `librarian.run {agent_id}` -> the status after the start; `librarian.overview {}` -> the overview. `LibrarianBusyError` -> `agent_busy`, `LibrarianUnavailableError` -> `invalid_request`, others through `_map_expected_error` (`agent_not_found`, `domain_error`). `settings.get` carries the `librarian` section; `settings.update` accepts partial `librarian` updates.
- The Librarian's unavailability (`librarian_problem_message`, `core/agents/_types.py`): `The Librarian is unavailable: one of your Agents uses its id librarian. Rename that Agent (vbot agent rename librarian <new-id>) and restart vBot to create the Librarian.` / `... agents/librarian/agent.json cannot be loaded. Fix that file (vbot doctor names the problem) and restart vBot.` / `... it does not exist yet. Restart vBot to create it.`
- Its Model and Model settings: `agent.update librarian {model, fallback_models, temperature, thinking_effort}`, `vbot agent update librarian --model ... --thinking-effort ...` (`../agent.md`). An earlier vBot's `librarian.model` setting is ignored when settings load and dropped by the next `librarian` write; `doctor config` warns about it with the command above (`settings.md`).
- CLI `cli/librarian_management.py` (`../cli.md`): `vbot librarian status` without an Agent prints the overview: availability (`unavailable: ...` with the fix), the schedule, a running pass, the recent passes over all Agents with their Sessions and hints to the per-Agent status, to a pass Session and to the Librarian's Model. `vbot librarian status <agent-id>` prints the reason line of `unscheduled_reason` (`not scheduled: ...`), the schedule settings, a running pass, the next scheduled pass, the last pass (whether it stopped early, counts, consolidation outcome, Session and Run), the earlier passes, the last pass's revisions with the `vbot skill revert ... --scope agent:<id>` command and how to open a pass Session (WebUI, or `vbot chat --agent librarian --session <session-id> "<message>"`); `vbot librarian run <agent-id>`. `vbot doctor config` warns at an Agent of the user that holds the id `librarian`.
- The per-Agent switch: `agent.update {librarian_enabled}`, `vbot agent update <id> --librarian true|false` (`cli.md`) and the Agent editor's Librarian row (`../webui.md` / `../webui/settings.md`).
- WebUI: Settings -> Memory -> Skill maintenance (`SettingsLibrarianPanel`: the schedule settings, the Librarian's Model settings saved with `agent.update`, and the recent passes of `librarian.overview`, each opening its Session in Chat) and the Librarian section of an Agent's Skills page (`LibrarianSection`, which shows the `unscheduled_reason` and opens the last pass's Session), both in `../webui/settings.md` and `../webui/source-map.md`; Chat shows a Librarian Session as an override view named "Librarian" and continues it (`../webui/chat.md`). Agents learn the commands from the bundled `vbot-cli` Skill (`references/skills.md`, `../skills.md` -> Agent-facing text).

## Shutdown

`_shutdown.py` step `librarian` after Reflection and before the Runs: `stop()` stops checking and cancels passes in progress; `aclose()` also waits for them. A cancelled pass writes nothing more: its `running_pass` reports it as interrupted, and the next scheduled pass comes one interval after that record. Its consolidation Run ends when `ChatRunManager` closes; its Session stays.

## Known gaps

- A merge moves the deleted Skill's shares and the triggers of the Agent's live automations to the umbrella at delete time (`core/runtime/_skill_merge.py`). A reference that could not move keeps the old name, and a `/name` or `$name` trigger is looked up in the registry only, so it no longer finds the Skill; the `skill_manage` result names such references, and undoing the merge moves nothing back.
- `absorbed_into` is unadvertised in the `skill_manage` schema; the brief names it, and the refusal explains it when a Model omits it.
- Aging changes the candidate set, so a pass after aging archived a candidate runs consolidation even when nothing else changed.
- The evaluation covers consolidation only; aging is checked by unit tests.
