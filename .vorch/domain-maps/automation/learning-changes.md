# Learning Changes

Read when changing how the outcome of a learning Run (a Reflection review, a Librarian consolidation Run) is read or undone: `LearningChanges.of_run`, `summaries` and `undo`, its conflicts and failures, and its surfaces. The user requirement it serves is in `../automation.md` -> Reflection.

`LearningChanges` (Runtime `learning_changes`) is Run-generic - it serves any Run of an Identity Agent (reviews and Librarian consolidation Runs), keyed by `(agent_id, run_id)`. It is the one place both stores meet; Memory and Skills never know each other, and `ReflectionService` stays review-specific. Nothing new is stored: the outcome is derived from the Memory and Skill histories by the Run id that their revisions record, and the review rows already keep that id durably (`chat.reflections`), so it survives reloads and restarts.

Registered Projects' shared Memory histories join the Agent's personal history through the injected Project catalog. A Project change carries its `project_id` because revision numbers belong to one history, and it belongs to a Run only when both its Run id and writer Agent id match. Reads and undo hold the Project configuration guard, preventing archive from moving an anchor between discovery and file work; disabled Memory remains visible to this user-facing history operation. A summaries request reads each history once. Reflection admission and cadence remain Identity-Agent-only.

Registered Agents' Skill histories join the caller's home through the injected Skill-home catalog, regardless of current sharing. A Run can change a shared package at its owner's home; each home's revision numbers and same-named packages stay separate. Foreign Skill changes and conflicts carry `skill_owner_id`, and the user-facing list names that owner. Renaming an owner changes that current id without losing the Run attribution in its moved history. Reads and undo hold the Agent lifecycle guard before the Project configuration guard, so homes and anchors cannot move during discovery or writes.

New Tool writes persist the maintained Agent's immutable creation identity in each Skill revision (`subject_created_at`, `skills/history.md`), including shared-home writes and Librarian work. Runtime captures this identity at Tool admission, stamping an old Agent configuration once; history reads never create it. The Skill-home catalog includes built-in Identity Agents. Learning compares recorded stamps to the current subject before reporting or undoing a Run: another Agent or a replacement under the same id is refused, while an Agent rename keeps its identity. Session moves, forks and archives do not determine this attribution.

Own-home legacy Skill revisions retain their previous behavior. Unstamped foreign revisions need a matching stamped revision of the same globally unique Run, a personal Memory edit recorded by that Run, or the Librarian's internally validated exact pass. Without such evidence, the entire read or undo refuses before changing anything; the user can inspect and revert those old changes in each owner's Skill history. A mismatching recorded stamp always refuses, including when an internal pass is validated. No identity is inferred from the Session's current Agent.

Undo preflights every participating Memory and Skill history before writing; the Skill authoring lock spans those checks and the complete undo. A later change by another Agent to a shared entry or package refuses the whole undo, including personal Memory and Skills. Skills are reverted per home before Memory. A failure in a later Skill home compensates earlier homes; if a later Project write fails after earlier Memory owners were reverted, their recorded reverts are reverted again before every completed Skill home's compensation runs. Failure to restore any owner is reported as a partial undo that can be inspected and retried. Successful RPC undo invalidates each changed Skill owner's dependent registries; failed undo invalidates all Agent Skill registries because its effects can span homes.

The internal `undo(..., skill_revisions=)` keyword adds explicit Skill revision ids grouped by owner to the same operation (Librarian aging archives have no Run id). It includes their revert lineage for conflict checks and skips already undone ids on retry; an unavailable named owner refuses before any write. These extras do not become changes attributed to the Run. The internal `validate` callback rechecks the Librarian's exact pass and subject incarnation under the lifecycle guards before reading histories. The learning RPC accepts only the Run identity, never a caller-supplied revision set or validation callback.

- `of_run(agent_id, run_id)` -> `RunLearningChanges`: one Memory item per entry the Run's `edit` revisions changed for good - its net effect, matched by entry text (`added`/`replaced`/`removed`, `scope`, the resulting or removed entry `text` cut to 160 characters, the Run's `revisions` behind it); an entry the Run added and removed again, or changed back, is no item, so a review that only did that reads `Nothing saved`; one Skill item per Skill name over the Run's non-`revert` revisions (`archived` when the last one moved it out of the home, with `absorbed_into`; else `created`, `changed` when `SKILL.md` changed, `file_written`, `file_removed`), with the changed `files`. Each item names its `revisions` and whether it is `undone`: a revision is undone when a `revert` that is not itself undone names it. `summary` counts the items (`memory`, `skills`) and is `undone` once every item is. `summaries(agent_id, run_ids)` returns the summaries of many Runs from one read of both histories.
- `undo(agent_id, run_id, workspace=, actor=)` takes back every change of the Run not undone yet, all or none, and records ordinary `revert` revisions (Memory with the caller's `actor`, `rpc` from the RPC; Skills as `human`). It reverts the revisions behind the listed items, so Memory revisions that cancel out within the Run are left alone and never block. A Run that is still running is refused first (`LearningRunActiveError`, "Nothing was undone: the Run is still running. ..."; the Runtime passes `ChatRunManager.is_running`). Both stores are checked before either is written: Memory `check_revert(strict=True, related=)` (which first records outside edits of the files) refuses any later Memory revision in the same scope that added, removed or replaced the change's resulting text (or the removed text), because the Memory history's own revert rule tolerates an effect that is already gone; then Skills `check_revert`, whose rule refuses any later revision that touched the same part. The Memory revert repeats the strict check under its scope locks, so a write that slips in after the check is still a conflict. A refusal raises `LearningUndoConflictError` ("Nothing was undone: ...", naming the entry or Skill and the later revision; `to_dict()` gives `store`, `revision`, `later {revision, at, actor, run_kind?}` and `scope`/`text` or `skill`). The Run's lineage - its revisions plus every revert chain that started from one of them - never blocks, so an undo can be repeated after a partial manual revert or a restored failure. Skills are written first, then Memory; when the Memory revert fails or is refused, the recorded Skill reverts are reverted again - a refusal then surfaces as the conflict, a failure as `LearningUndoFailedError` saying whether nothing was changed or which store stopped part-way (`Undo again to finish`). A Memory revert that stops part-way keeps the written scope recorded as reverted, so the next undo takes back only the rest. A Skill revert that cannot take its own steps back (`SkillRevertIncompleteError`) is a failure, not a refusal. A Skill step the history could not record stays undone and cannot be put back; the result still reports the Skills as changed once the revert returned, so views refresh. An undo with nothing left is a no-op. One in-process lock serializes undos. Each undo logs one INFO line (Agent, Run, revision counts, actor) without entry text (`tests/core/automation/test_learning.py`).
- Surfaces: `learning.changes` / `learning.undo` and the `outcome` of finished `reflection_runs` rows (`server/session-agent-rpcs.md` -> Learning RPCs); the Activity panel (`webui/chat.md`). No CLI.
