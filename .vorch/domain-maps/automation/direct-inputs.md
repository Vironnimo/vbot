# Direct Task inputs

User decisions 2026-10-29: distinguish caller-supplied tasks from event webhooks, bind each input to one Agent, allow Model and Reasoning defaults on the input and overrides in each request, create a fresh Session unless continuing an input's own Session, acknowledge asynchronously with optional waiting. Both use the existing Chat/Run execution kernel. Event webhook jobs retain their configured prompts and labeled request data (`cron-webhooks.md`).

## Ownership and persistence

`core/automation/inputs.py::DirectInputService` owns Task input configuration, secrets, request scoping and the merge of execution overrides. Runtime constructs it as `direct_inputs` before automation reference checks and pending Agent-rename recovery. It creates no scheduler or execution queue: `ChatLoop.submit_accessor_input` owns durable acceptance and the shared Run Queue. Its accepted inputs recover with every other ordinary Accessor input.

`automation/inputs.json` is a Generation 1 document registered in `DURABLE_DOCUMENTS` and the Settings doctor's validator catalog, so it participates in configuration backups and data snapshots. Unknown fields survive writes. Invalid or unreadable configuration disables inputs and refuses changes instead of replacing it; repair the file and restart. Configuration and Secret Store I/O run on the named `direct-inputs` worker pool. Mutations settle persistence before honoring caller cancellation. Only effective configuration changes log at INFO; prompts, results and secrets never do.

Paused inputs still count as Agent and Project references, because they can be enabled again. `AutomationReferences` includes them with kind `input`. Runtime's recoverable Agent rename retargets them in both directions, during live renames and startup recovery. Operator configuration changes and HTTP admission hold the shared automation reference lock; never hold it while waiting for execution to finish.

The encrypted Secret Store's `webhook_secrets` section keeps a Task input's secret under its input id. No secret is stored in the input document or returned by list/create/update. Reveal and rotation are separate operator operations. Deleting an input revokes its URL and credential; accepted tasks and Sessions remain. Disabling it rejects new submissions while authenticated status reads remain available. Secret rotation rejects subsequent admissions using the old credential, including requests waiting for the reference lock.

## Requests and Sessions

`server/_direct_inputs.py` mounts secret-authenticated submission and status routes. Their exact shapes are exempt from Device authentication, while the ordinary access guard still enforces Access Mode, peer, transport and Host rules, and the origin guard still applies. Exactly one Bearer authorization header must prove the selected input's secret; unknown inputs, disabled submission targets and wrong/missing credentials return 404. These routes share webhook ingress rate limits and refusal accounting, and the shared bounded JSON reader (1 MiB). Configuration RPCs remain protected operator operations.

An authenticated request supplies a concrete nonempty `prompt`, not arbitrary event data to interpret. The input fixes the Agent and the Working Project/Workspace of new Sessions; continued Sessions retain their own immutable Working Project. The caller cannot select another Agent, Project or execution Computer. Only Model/Reasoning Run overrides are accepted. The request's supplied settings override the input's supplied settings, with omitted values inheriting ordinary Session/Agent settings. Explicit Provider-default Reasoning replaces an explicit effort, and vice versa. Overrides are persisted with the accepted input for restart recovery, but ordinary Session defaults are captured without them and remain unchanged.

No Session id creates a fresh Session after Agent/Model/Provider preflight. The Session's creating write records `input_source_id`; continuation accepts only an existing Session of the input's fixed Agent that records that same input id. The generation read during this check is retained through Chat admission, so an archive/recreate race cannot substitute another conversation. Forks strip the provenance marker rather than granting the input access to another conversation.

Requests use the canonical Sessions Accessor-input receipts; no second request database exists. The internal input identity namespaces the request id by the configured input id, so another input's secret cannot read or retry that receipt. A request without an Idempotency-Key gets an opaque request id. A supplied nonempty key of at most 128 characters is hashed to a stable request id within that namespace; reuse of the key with different original input returns 409. Waiting options do not change the request identity, and retries resolve the original receipt before consulting changed input defaults or creating a Session. Receipt lookup follows the existing Session-generation and archive contracts.

## Acceptance, completion and UI

The immediate response is HTTP 202 with a durable request identity, Session id, status URL and Run id when available. A queued request does not yet need a Run id. Status reads authenticate against the same input and report its exact receipt and Run, including after another Run has continued the Session or the process has restarted. Terminal reads include the full final textual answer, with the silent-answer marker hidden; a no-longer-live Session reports unavailable.

Optional waiting observes the same admitted work, by its live Run or Queue future. The default wait is 30 seconds, with a positive caller-selected limit of at most 60. A deadline returns the accepted task as HTTP 202; it does not cancel or resubmit it. Completed, failed, interrupted and cancelled executions are terminal response data (HTTP 200), not transport failures that invite another execution. Disconnecting or cancelling an HTTP waiter does not cancel the Run. Clients use the returned status URL for later reads with the same Bearer credential.

`server/rpc/input_methods.py` registers operator configuration with the existing RPC dispatcher and publishes `resource_changed` kind `inputs`. The frontend maps that to the Automations refresh token. `cron/DirectInputsView.svelte` owns the Task inputs tab, reuses execution selectors and Model/Reasoning catalogs, autosaves existing inputs with the shared participant, and retains new drafts through App's existing Automation-draft state. It presents URL/reach, reveal/rotate controls and copyable submission, polling and continuation examples. Event webhooks stay a separate tab. Input drafts and saved selections follow the App's Agent-rename notifications.
