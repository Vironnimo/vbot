# Cron and Bootstrap

Read when changing Cron or Bootstrap jobs: modules and lifecycle, validation and schedules, DST, execution health and the failure stop, where a Run's answer goes (delivery, `[SILENT]`, the previous answer, failure alerts), catch-up, once claims, edit and fire ordering, target errors and logging. The boundary and the rules every automation change keeps are in `../automation.md` -> Conventions; jobs bound to calendar events in `event-jobs.md`; jobs that watch a command or URL in `cron-watch.md`; jobs run by webhook requests in `cron-webhooks.md`; jobs run by incoming mail in `cron-email.md`.

## Modules and lifecycle

- Cron's internal `_cron_jobs.py` owns records, JSON diagnostics and field normalization; `_cron_schedule.py` owns pure parsing, schedule normalization and the per-job occurrence ticks with explicit timezone/time inputs; `_cron_projection.py` owns `CronProjection`, the detached, read-only copy of jobs, bound events, timezone and clock that `CronService.projection()` captures in one loop turn and whose `project_occurrences(window_start, window_end)` the calendar window RPC expands off the loop (read-only; respects `remaining_runs`, capped per job; an event job's rows name the occurrence). `_cron_events.py` owns event times (`start - 30m`), the owed and next occurrences of event jobs with their catch-up windows, and the event context note. `_cron_claims.py` owns once-job fire claim files and `_cron_timing.py` owns interruptible wall-clock waits and retry timing. `CronService` retains the job catalog, persistence and reference/capacity checks; its internal `_cron_scheduler.py` owns task lifecycle, due-fire/claim/restart coordination, `_cron_execution.py` owns Run admission/outcomes and post-fire persistence, `_cron_context.py` the context note of every fire path (with the late notice), `_cron_watch.py` and `_cron_watcher.py` the checks of watching jobs (`cron-watch.md`), `_cron_webhooks.py` and `_cron_webhook_events.py` the requests and secrets of webhook jobs (`cron-webhooks.md`), `_cron_email.py` the mails of email jobs (`cron-email.md`), `_cron_inbox.py` the waiting arrivals both share, and `_cron_binding.py` owns Calendar binding changes; its public schedule methods supply the current application timezone and clock.
- Cron lifecycle: idempotent start/stop; start reconciles all jobs before any task; an escaping scheduler-task exception flows through the failure-health path; completion from a stale replaced task never restarts its replacement.
- **Bootstrap lifecycle:** Every Runtime start has a UUID `startup_id`; creating/updating/enabling arms a job with it so it cannot fire in the arming process. An Agent rename is not such an edit: it retargets through `retarget_agent`, which changes only the Agent id and keeps status, arming and the Run/Session references, so a paused or failed job stays paused or failed (`tests/core/automation/test_bootstrap.py`, `tests/core/runtime/test_runtime_agent_rename.py`). `once` completes/fails only after an admitted Run terminates (an `interrupted` Run counts as unsuccessful -> retry policy); `always` stays active at most once per startup. Activation groups fixed-Session jobs per owner for sequential execution within four global slots; session-less jobs create fresh Sessions; crash reconciliation asks Sessions for the claimed Run's exact persisted terminal summary instead of loading its complete transcript before deciding whether to retry.

New Cron and Bootstrap job ids use the prefixes `cron_` and `boot_` (format: PROJECT.md -> Object IDs). Synchronous creation checks the loaded job catalog and retries collisions before publication; persisted ids remain stable on load/update (`cron.py`, `bootstrap.py`, owning tests).

## Validation and schedules

- Validation: both stores export strict validators consumed by diagnostics; whole-file failures raise `CronStorageError` on mutation, bad data raises `CronJobValidationError`. Bootstrap modes `once|always`, statuses `active|paused|completed|failed`; completed one-shots are immutable history, failed ones rearm. Rearming clears the old Run/Session reconciliation references so the previous terminal result cannot undo the new activation.
- Schedules: `schedule_type` is `cron` / `interval` / `once` / `event` / `webhook` / `email` with kind-owned fields cleared on change (a webhook job has none: its secret lives in the Secret Store, `cron-webhooks.md`; an email job keeps `email`, `cron-email.md`); an event id or event time given for another schedule is refused. `remaining_runs` patches preserve on omission, replace on integer, `null` unlimited only for recurring; an event job refuses it (its event's occurrences drive the repetition), and a switch to `event` drops it. Statuses: `completed`/`missed` are immutable terminal history; `failed` re-enables after cause fix (resetting its failure counter); only `active` holds a scheduler task. Timestamps persist UTC with explicit offsets; naive once `run_at` interprets in the application timezone from `server.timezone`; creating a once job, changing its `run_at`/schedule type, or activating it (enable, failed rearm) with an elapsed `run_at` raises `CronJobInPastError` (user decision) instead of firing immediately - a once job whose `run_at` passed while vBot did not run it fires late under the catch-up rule below; a stored per-job `timezone` is an unknown field: ignored, kept on save, and reported by `doctor config`.
- Permission ceiling: a job created through the `cron` Tool by a restricted Run stores `permission_ceiling` (`to_ceiling_dict(source="cron")`); an update by a restricted Run adds the layers of its own boundary that the stored ceiling lacks (`join_ceilings`; every layer limits the job, so no update widens it), a full-access update keeps it. A watch the resulting ceiling refuses is refused with `permission_denied` before the job changes (`CronService.watch_refusal` -> `WatchChecks.permission_refusal`; `cron-watch.md`). RPC, CLI and WebUI jobs store none and cannot set it. Every fire passes `CronJob.ceiling()` to `trigger_run(permission_ceiling=...)`; Chat joins it into the fired Session's stored ceiling, so its follow-up Runs keep it (`chat/run-execution.md` -> Permission Boundary). A stored ceiling that does not read makes the job invalid. Because that joined ceiling stays with the Session, a restricted Run pins a job only to its own Session or a Session below it in its Sub-Agent tree (user decision 2026-10-21): a create or update whose job would run in any other Session fails `permission_denied` before the job changes (`cron.py::_check_pinned_session`, Parent links read through `register_cron_tool(session_ancestors=...)`, `subagents/links.py::ancestors`); the user lifts a ceiling a Session already holds with `permissions.clear_session_ceiling`. Coverage: `tests/core/tools/test_cron.py::test_a_restricted_session_bounds_the_jobs_it_creates_or_changes`, `test_a_restricted_session_pins_jobs_only_to_its_own_session_tree`, `test_cron_execution.py`.
- Names: human-readable, need not be unique (id is identity), derived once from the first useful prompt line when omitted at creation (capped 80 chars); a stored job requires `name`.
- Cron grammar is exactly five fields (minimum cadence one minute) in croniter's syntax, without its random `R` and hashed `H` tokens, which pick other times at every parse so live scheduling, catch-up and projection would disagree (`_cron_is_schedulable`; `L`, `W`, `#` and `?` stay accepted); parsing, mutations, and job loading also require a reachable next fire within croniter's search horizon, so impossible dates are rejected before persistence or skipped and preserved on load. Calendar projections use half-open UTC windows, including exact start ticks; cron-expression ticks are bounded below by the job's `created_at`, so a new job never projects earlier ticks (`tests/core/automation/test_cron.py`, `test_cron_projection.py`). Cron is evaluated with `croniter` in the application IANA timezone including future DST; intervals use their persisted anchor rather than approximating into cron. Runtime injects the effective Settings zone and `set_timezone` wakes cron sleepers so a live setting change reprojects before firing; intervals and once jobs remain absolute UTC instants. Accessors must not duplicate interval/croniter/timezone logic - the service owns parse/format/projection.

## Execution health

- Execution health (`last_*`, `consecutive_failures`) persists per job: a fire takes one of four global Cron Run slots as `RunKind.CRON`, admitted with activity disabled (-> Delivery decides it at completion), consumes one finite `remaining_runs` slot after admission, waits terminally; one job never overlaps itself, slow Runs skip intervening instants, five consecutive recurring failures stop the job as `failed`, success clears the counter. Capacity bounds: 512 stored / 64 active jobs; terminal history blocks no deletions, live references do.

## Delivery

User decision 2026-10-20 (`.vorch/plans/cron-proactive-automation.md`, phase 1): a job says where each Run's final answer goes. `_cron_delivery.py` owns the rules (silence, alert timing, texts, the chat check); `_cron_execution.py` records the outcome and stages messages; `_cron_notifications.py` owns their durable send/retry lifecycle in the existing job file; `_cron_context.run_context` builds the context note.

- **Persisted fields** (optional, written only when set, additive to Generation 1): `delivery` `{kind: app}` or `{kind: chat, channel_id, platform_target, thread_id?, platform?}`; kind `none` is stored as no field (`CronDelivery.stored()`). `last_result` `{text, at, run_id?}`: the latest answer that was not silent, cut to 2,000 characters ending in an ellipsis (`CronResult.excerpt`). `last_run_silent`: the latest Run succeeded with a silent answer; every other outcome clears it, and `last_outcome` keeps its values. A Project job refuses `chat` (Channels belong to Identity Agents). The cron RPCs return `delivery` (kind `none` when unset), `last_run_silent` and `last_result`.
- **Kinds:** `none` delivers nothing and leaves the Run a background Run, as before; RPC and CLI callers that omit `delivery` get it. `app`: the Run is admitted as non-activity, and its `completion_activity` (`../runs/queue-and-admission.md`) marks it as activity when it completed with an answer that is not silent, or failed or was interrupted; such a Run appears under its Schedule with independent unread state and source-policy-filtered notifications (`../sessions/lists-and-metadata.md`, tray: `../cli/application/tray.md`). `chat`: the complete masked answer and destination snapshot are saved with the successful outcome in `notifications`, then sent through `ChatDelivery.send`; only confirmed delivery removes that message and sets `last_delivered_at`. `record_outbound_note` records the sent message in the chat's Session, skipped when the Run ran in that Session. The `cron` Tool defaults to the calling chat or vBot, the WebUI to `app` (`../tools/cron.md`).
- **`ChatDelivery`** (`get_channel`, `send`, `record_outbound_note`) is the narrow protocol Cron uses; Runtime binds the Channel service with `CronService.set_chat_delivery` (`core/runtime/_bootstrap.py`), so Cron imports only the public `ChannelError` delivery classification, not Channel internals. `check_chat_delivery` runs on create and on edits that change `delivery` or `agent_id`: the Channel must exist and belong to the job's Agent, so an unrelated edit works while the Channel is gone.
- **`[SILENT]`:** every Cron Run's context note says where its answer goes and that answering exactly `[SILENT]` delivers nothing; a `none` job's note claims no delivery (wording and reasons: `../tools/cron.md` -> Agent-facing text). `is_silent` reads the answer before masking (a Secret value matching the marker cannot turn a silent completion into a notification): the trimmed answer equals `[SILENT]` in any case, its first or last non-empty line is exactly `[SILENT]`, or it is empty. A silent success delivers nothing and leaves no unread mark or notification. `SILENT_ANSWER` comes from `core.runs`; an answer that is exactly the marker is also hidden from the job's Session transcript (`../runs/events.md` -> Silent answer).
- **Previous answer:** a success that is not silent replaces `last_result`, and the next Run's context note carries it as a JSON record with its local time (`previous_result_note`, `<` and `>` escaped), labeled as earlier output. A silent Run keeps the previous one. Logs never carry answer content.
- **Failure alerts** (fixed English text, no Model call): at the second failure of a streak and when a failure stops the job (a once job failed for good, the five-failure stop, a finite job whose last Run failed). A watching job's failed checks count in the same streak and alert alike (`cron-watch.md` -> Check failures). `chat`: the same persistent notification queue as answers, then an outbound note after a confirmed send. `app`: every failed or interrupted Run is eligible for unread activity; the policy filters attention. `none`: nothing. A failure no Run reports (a failed check, an unavailable target or pinned Session, a once fire cancelled or abandoned before admission, a crashed job task) alerts a chat the same way; for `app` the service stores it on the job as `unread_alert` and raises a `CronFailureAlert` (`job_id`, `name`, `agent_id`, `project_id` and the alert text as `message`) to its `add_failure_alert_callback` subscribers, which the server publishes as `cron_failure_alert` (`../server/events-and-reconnect.md`) and the tray shows as a toast (`../cli/application/tray.md` -> Toasts). A failed Run reports itself instead (`_alert_failure(run_reports=True)`). The crash and abandon paths alert through `_save_and_alert`.
- **Unread alert** (user decision 2026-10-22, plan decision 5 "A failing check never stays silent"): optional `unread_alert` `{message, at, kind}` keeps an alert without a Run durable, because a toast or event reaches only the accessors connected at that moment and such failures often have no Session to mark unread. `CronService._record_alert` writes it (text cut to 2,000 characters, Cron clock) and then raises the callback, so every alert the callback carries is also stored. Kind `failure` (alerts above) clears on the next successful Run, on a successful check that ends the streak, and when a failed job is enabled again; kind `delivery` (an uncertain send, or messages given up for a deleted Channel) clears on `cron.retry_delivery`. Either clears on `cron.acknowledge_alert` (`acknowledge_alert`, undoable). The cron RPCs return `unread_alert`; the WebUI marks the job in the Schedules list and shows the alert with a "Mark as read" action, and `vbot cron list` prints it as `alert=`. The `cron` Tool does not show it.
- **Durable chat notifications:** optional `notifications` records hold id, original Agent and Channel/chat/thread, masked text and outbound note, source Session, state (`pending`, `sending`, `uncertain`), masked error and `retry_after_at`, the canonical UTC timestamp (Cron clock) before which a known-unsent message waits; none means send now. Earlier builds stored epoch seconds as `retry_at`; that field is no longer read and survives saves as an unknown field. A successful Run saves these in the same jobs snapshot as its outcome; no second Channel outbox takes ownership. Before each send, the original Channel owner is checked and a `sending` marker must persist. `send(expected_agent_id=...)` also checks the selected active engine after that write, so a Channel reassignment cannot redirect the notification while its claim saves. Known-unsent failures retry every 30 seconds (honoring longer rate-limit hints), independently of the job's active/paused/terminal state and without another Model Run. The notification worker waits for transport outside Cron Run slots; a slow send cannot occupy scheduling capacity. A stopped Channel, or one that now belongs to another Agent, keeps the notification waiting; a retry that changes only `retry_after_at` by at most 30 seconds stays in memory and does not rewrite the job file. Messages to one conversation (Channel, chat and thread) go out in order: one still waiting holds back only later messages to that conversation, never the job's messages to other chats. Each startup resumes pending messages; edits never redirect older messages. An Agent rename is not such an edit: `retarget_notifications`/`retarget_notifications_async` move the notifications of the old Agent id on every job, terminal jobs included, whose Channel the rename moved, and a send's later state update never reverts that (`../runtime/agent-rename.md`, `test_an_agent_rename_takes_the_waiting_notifications_along`). Deleting the job also discards its retained notifications, including when deletion finishes while a send claim is saving; after that wait the sender checks that the job still exists before contacting the Channel (`test_a_destination_changed_while_its_notification_claim_saves_prevents_the_send`).
- **Bounds** (user decision 2026-10-22): a staged message keeps at most 8,000 characters, the rest replaced by a marker that points to the job's Session (`chat_message_text`); the outbound note records the cut text. A job keeps at most 20 waiting messages (`MAX_RETAINED_NOTIFICATIONS`): staging another drops the oldest that is not `sending`, counts it in the job's `dropped_notifications`, and the next confirmed send opens with one line naming the count (`dropped_messages_line`), after which the count drops by what it announced. A Channel that no longer exists (`ChannelNotFoundError`) sets `channel_missing_since` on the waiting message; 24 hours later (`CHANNEL_GONE_HOURS`, Cron clock) every message for that Channel that is not `sending` is dropped and a `delivery` unread alert names the count (`channel_gone_alert`). Finding the Channel again clears the mark. A notification discarded while its Channel lookup awaits cannot acquire a send claim and never reaches the transport.
- **Uncertain sends:** a platform failure marked `possibly_delivered`, an unclassified send exception, or a persisted `sending` record after interruption becomes `uncertain`, triggers an in-app alert, and is never blindly repeated. Other notifications can proceed. `cron.retry_delivery` explicitly resets retained messages for retry after the user checked the chat; the WebUI shows the uncertainty and offers that action. Confirmed sends are not repeated when writing the chat's mirror note fails. A crash after send but before recording confirmation remains uncertain, rather than claiming delivery or duplicating it.
- **Visibility:** RPC `delivery_progress` reports waiting/uncertain counts, latest retained error, `last_delivered_at` and `dropped` (the RPC adds it; `CronJob.delivery_progress()` and so the Tool omit it); the Tool includes the progress while messages remain. WebUI shows retained delivery independently from Run success, including for completed jobs. The watch baseline advances once a successful Run has durably recorded its notification; a disconnected Channel does not rerun the Agent for the same change.
- Coverage: `test_cron_notifications.py` (restart, offline and known-unsent retry, uncertain/interrupted sends and their alert, failed durable claims, failure alerts after stop, destination snapshots, rename, the backlog cap, the deleted-Channel deadline), `test_cron_execution.py` (delivery, silence, previous answer, activity decisions, alerts in a chat and for vBot, the unread alert and its acknowledgement), `test_cron.py` (round trip, chat check), `test_cron_validation.py`, `tests/server/test_app_events.py` (the `cron_failure_alert` bridge), `tests/cli/application/test_notifications.py` (the toast).

User requirement 2026-10-29: chat destinations and retained notifications bind to their original platform. `delivery.platform` and each notification's `platform` are optional Generation 1 additions; creating a destination or explicitly selecting it on update captures the checked Channel platform. A supplied platform is an expectation and a mismatch refuses the selection. Unrelated edits and startup never infer missing bindings from today's Channel. Missing or changed platforms block delivery, including after restart; the send and mirror-note boundaries check both the original Agent and platform against the captured active adapter. Pending messages report `delivery_progress.platform_blocked`; the conversation-order key includes platform so an old blocked destination does not hold a newly selected one.

`cron.retry_delivery` without `delivery` retains its explicit uncertain-send retry contract and never changes a destination. With an explicit chat `delivery`, it rebinds only pending messages whose original platform is unknown or whose original Channel now has another platform, for the job's Agent. Healthy original destinations and uncertain sends stay unchanged; missing Channels with a known binding retain their existing deletion deadline. This repair also works for completed jobs and does not edit the job's future destination. The result adds `rebound_notifications`; zero eligible messages refuses without mutation. The WebUI offers a chat-target selection dialog for `platform_blocked`, limited to the job's Agent's Channels and submitting the selected current platform as an expectation. Ordinary WebUI edits omit an unchanged delivery, including legacy records with no platform; deliberate delivery edits submit the selected Channel's current platform as an expectation, and selecting a changed platform clears the old chat/thread so the user must enter a fresh target. The CLI exposes the same operation as `cron retry-delivery` (`../cli/agent-commands.md`). Retry waits for the edit and delivery locks before its cancellation-protected mutation begins; cancelling a waiter changes nothing. A failed retry save restores only its own still-retained changes, preserving notifications staged or evicted meanwhile. Coverage: `test_cron_notifications.py`, `test_channels_delivery.py`, RPC and CLI Cron tests.

## Catch-up

The catch-up rule (`../automation.md` -> Catch-up) follows anacron, systemd `Persistent=` and Quartz fire-once misfire handling. `_cron_schedule.owed_fire` decides for the three time-based schedule types: due times after `covered_until(job)`, the latest of `created_at`, the persisted `covered_until`, `last_attempt_at`, `last_completed_at` and a watching job's `last_checked_at`, are owed, so instants that passed during the job's own Run (overlap skip), while it was paused, or under an earlier schedule are not. Activating a job or changing a schedule field of an active job sets `covered_until` to now (`_stage_update`). The recurring loop fires only what `owed_fire` returns, also after waking at a due time: a due time a Run already covers waits for the next one, so a wall clock stepped back after a fire never repeats it (`test_cron_recurring.py`). A fire more than 60 s after its due time (`_cron_context.ON_TIME_SECONDS`), or one with earlier missed due times, passes `context_note` through `TriggerService.trigger_run` to Chat, which stores it as a note before the prompt, read as a System Reminder: due time, actual start, the count (capped at 100, then "At least") and first of the earlier missed due times, all server-local ISO with offset, an instruction to adapt time-dependent parts of the prompt, and one to say so instead of carrying out an instruction that no longer makes sense this late. An on-time fire passes no late notice, and a watching job's Run never gets one (`cron-watch.md`). No limit bounds how late a missed fire starts (user decision 2026-10-08: the late Run is told and can adapt or decline, which beats a limit set in advance; the former per-job `max_delay_seconds` was removed). A `max_delay_seconds` stored by earlier versions is an unknown field: ignored, kept on save, reported by `doctor config` (`test_a_stored_max_delay_no_longer_skips_a_missed_fire`). Legacy jobs without `covered_until` fall back to the other timestamps (`tests/core/automation/test_cron_catch_up.py`). Event jobs bound late starts by their event instead and run once per missed occurrence (`event-jobs.md`); they share the 60 s on-time tolerance and the late notice.

- A missed fire runs once, never once per missed instant (an event job runs once per missed occurrence whose window is open); after it, the next fire computes from current time. Fired once jobs retain as `completed`. Nothing sets status or `last_outcome` `missed` any more; both stay valid (`missed` remains terminal) for jobs that earlier versions skipped by `max_delay_seconds`.
- Lateness is classified immediately before `trigger_run`, after Run-slot and claim-persistence waits. Keep the owed due time even when a fire looks on time before those waits; once-job retries retain that due time but refresh the actual start (`test_cron_catch_up.py`).
- Cron ticks always advance in UTC: repeated-hour wall times use only their first occurrence. Forward scheduling skips elapsed first occurrences; catch-up still finds them during the second occurrence even when their wall-clock time looks later than now. Spring-gap fires shift forward by the gap and remain eligible when scheduling starts after the clock jump but before their shifted instant; forward scheduling also compares the first valid tick after a gap against a shifted gap tick, since their UTC order can differ from their local order. Projection resumes from the resolved wall time to match live scheduling without duplicate instants. Catch-up compares resolved UTC instants even when a non-hour forward jump reverses the order of local ticks (`test_cron.py`, `test_cron_projection.py`, `test_cron_catch_up.py`).

## Once claims, failures and edits

Terminal jobs accept notification-policy changes but refuse effective edits to execution fields, including the schedule, count and delivery, before reference checks or persistence; identical values are a no-op. Deletion and the separate retained-notification retry/acknowledgement operations remain available. Internal Agent retargeting keeps its rename-specific path. Coverage: `test_terminal_jobs_cannot_be_changed_through_update`, `test_finished_job_cannot_resume_or_change`, `test_cron_notifications.py`.

- Changing schedule/count/status restarts an active sleeper; during queued admission or an admitted Run it defers the restart until that execution settles, retaining its global slot and preventing overlap. Schedule/count/status edits while waiting for a Run slot or the initial fire save withdraw that unadmitted fire, so its replacement waits for the new schedule. Name/prompt/agent/session updates do not restart it (the task reloads before firing).
- Rescheduling a non-terminal once job to a different time rearms its one fire unless the edit explicitly supplies a count. The previous queued/admitted execution records its own outcome without spending or completing the replacement fire; a failed edit restores the consumed budget if it rolls back to an admitted once fire (`test_cron_rescheduling.py`).
- Active once jobs write durable fire claims before triggering: pre-admission failure removes and retries with bounded backoff then abandons; an admitted Run consumes the fire even if it later fails; persistence failures retry saves with a bounded attempt cap, then log and continue on in-memory state without refiring. The execution outcome distinguishes admitted Runs from rejected triggers, and a once fire's claim stays until a post-admission save succeeds, so an unsaved outcome cannot refire after restart. Claim lookup matches the stored `run_at`; a saved explicit reschedule arms a new fire instead of consuming the previous fire's retained claim. Pre-admission trigger failures (full Queue, shutdown) never advance a job's execution-failure counter - only an admitted Run's failure can push a recurring job to the five-strike stop. The exceptions are a pinned Session that no longer exists (`SessionNotFoundError` before admission, for example after a data restore) and a target Agent or Project that no longer exists (`ResolutionAgentNotFoundError` / `ResolutionProjectNotFoundError`): each lasts until the job is edited, so the fire counts toward the stop rule without consuming a finite run and sets `last_error` to the same text that create/update/enable validation raises ("Session does not exist for cron target <target>: <session>", "Cron target does not exist: <target>"); enabling the stopped job therefore fails until it is edited. A target that exists but cannot run (for example, no usable Model) sets "Cron target <target> cannot run: ..." without counting, because it can recover without an edit (`test_pre_admission_trigger_failures_neither_stop_nor_consume_a_recurring_job`). A single transient miss (a fire racing an Agent rename's Session retarget) is cleared by the next success (`test_recurring_job_stops_after_consecutive_failures`). At-most-once beats duplicate execution across restarts: a persisted claim reconciles to completed with an unknown outcome and a restart diagnostic, even if the crash preceded admission. Cron never replays that uncertain fire; Bootstrap uses the separate terminal-summary recovery described above. A claim file that exists but cannot be read at start holds only that once job for the process (WARNING; not scheduled, not reconciled as missed, file kept for the next start). Claims (`cron/once-fire-claims/<sha256 of job id>.json`: `job_id`, `claimed_at`, `run_at`) are transient runtime state outside the JSON document contract (`json-documents.md`): one exists only from before admission until the job's resulting state is saved or reconciled at the next start, is never edited or converted, is not a data-snapshot member, and fails safe when unreadable. A failed save of startup reconciliation keeps the reconciled state in memory and its claims on disk; only an unreadable or invalid `jobs.json` degrades Cron storage. Every `jobs.json` and claim write runs on the `cron` `OrderedWorker` (`runtime/workers.md`) in submission order, from a snapshot taken on the Event Loop. Job tasks and job edits (`create_job`, `update_job`, `enable_job`, `disable_job`, `delete_job`, all `async`; the RPC handlers and the cron Tool await them) await their writes off the loop, so an edit's save lands after an in-flight fire save and a data snapshot holding `jobs.json` never blocks the loop. An edit first checks its target Agent and selected Session on the Session database's pool (`ChatSessionManager.run_async`), never on the Event Loop, then stages again against the job as a fire may have left it meanwhile (`test_edits_validate_target_and_owned_session_off_the_loop`, `test_a_fire_while_an_edit_checks_its_references_is_kept`). It applies to memory and the job tasks at once (a fire in flight sees it, as before), then saves; a failed save undoes both, taking back only the fields the edit changed so a fire recorded during the save stays (runs it spent from the edited budget are spent from the restored one; `test_a_failed_edit_save_keeps_a_fire_recorded_meanwhile`). Edits run one at a time and finish even when their caller is cancelled (`settle_before_cancelling`, `runtime/workers.md`). An Agent rename moves the jobs of a started service with `retarget_agent_async`, an edit like the others, on the Event Loop, where the rename runs; the blocking `retarget_agent` serves only a rename that completes at startup, before the service starts, and refuses once it runs. Only that and the startup reconciliation block on the writer. A fire re-reads its job after the first save and does not trigger when an edit meanwhile removed or deactivated it. A crashed job task's failure accounting (a done callback) saves in a tracked task that `aclose` awaits.

Once-Cron claim writes join the in-flight execution guard: edits wait for the
write to settle, then withdraw its unadmitted claim before the replacement task
starts. Cancellation during the claim write also removes that known-unadmitted
claim after the ordered writer settles, so a clean restart cannot consume a
rescheduled future fire (`tests/core/automation/test_cron_rescheduling.py`).

## Targets

Cron create/update resolves the target and raises a `CronTargetError` (a `CronJobValidationError`) on failure: a missing Agent or Project raises `CronTargetAgentNotFoundError` / `CronTargetProjectNotFoundError` ("Cron target does not exist"), which are also the resolver's not-found errors so RPC reports `agent_not_found` / `project_not_found`; a target that exists but cannot run (for example, no usable Model) raises `CronTargetUnavailableError` with the resolver's reason ("Cron target <target> cannot run: ...") and stays `domain_error`. Bootstrap surfaces the resolver error unwrapped. A cron job may target a Project agent via stored separate fields; firing creates a fresh Project-anchor Session unless pinning an owned existing one.

User decision 2026-10-27: WebUI Automations exposes schedules and webhooks with the same execution choices. A fresh Identity Session has an explicit Working Project or Workspace (`working_project_id: null`), independent of later changes to the Agent's Default Project. Callers omitting that choice when creating a job capture the current default once; the same applies when changing the target to a fresh Identity Session (unpinning or changing the Agent). The WebUI requires a deliberate choice. Existing stored jobs without the optional field keep their previous default-following behavior until configured, and unrelated edits preserve the omission. A Project Agent works in its address Project, and a pinned Session keeps its own immutable Working Project. Switching to either derived target without an explicit Project choice clears the old fresh-Session choice; a conflicting explicit choice is refused.

Optional `run_overrides` holds Model and Reasoning choices for this job's Runs only (`AgentOverrides`, `chat/run-execution.md`). Missing settings inherit the selected Session or Agent; a Model override is validated by the same resolver as Chat. Neither a pinned Session's defaults nor the ordinary defaults captured for a fresh Session change. `cron.update` patches only supplied override leaves: null removes one override, whole-object null clears all known overrides, and choosing an explicit effort or the Provider default replaces the other. Unknown future override fields survive unrelated edits and clearing supported settings, even when no known setting remains. Core callers may also pass an `AgentOverrides` value as a full replacement. Known fields are optional additions to Generation 1; nested future fields survive saves. Validation, round trip and patch contracts: `test_cron.py`, `test_automation_methods.py`; all fire paths use `_cron_execution`'s shared forwarding.

Live jobs bind a Project through their Project Agent, explicit Working Project, or pinned Identity Session. `CronService.references_project` reads the latter's stored binding; `AutomationReferences.project_references` therefore runs on the Session pool. Project archive refuses those live references; event revival rechecks a Working Project that could disappear while the event job was history. Legacy fresh-Session jobs with no explicit binding have no stable Working Project reference. Tests: `test_references.py`, `test_cron.py`, `test_cron_events.py`.

## Logging

- Logging (policy: `logging.md`): Cron and Bootstrap log each effective job mutation once at the service at INFO with changed field names and `actor=` (`rpc` from the RPCs, `tool` from the `cron` Tool, `application` for the update-continuation Bootstrap job, `internal` by default); no-ops are silent. The Agent-rename steps `retarget_agent` and `retarget_agent_async` log at DEBUG because the rename logs one summary line. A recurring job stopped after consecutive failures, a fire that could not start its Run because its pinned Session or target is unavailable (`Cron job could not start its Run`, no traceback), an exhausted job that ends `failed`, a once job whose Run was cancelled before admission, and a Bootstrap Run that finishes failed log WARNING (`test_cron.py`, `test_cron_execution.py`). A late fire appends `late_by=<s>s earlier_missed=<n>` to its INFO `Cron job fired` line (a webhook Run `webhook_requests=<n> webhook_dropped=<n>`, `cron-webhooks.md`; an email Run `email_mails=<n> email_dropped=<n>`, `cron-email.md`). A failure-alert subscriber that raises logs ERROR `Cron failure alert callback failed`; the other subscribers still get the alert. An answer, failure alert or outbound note that cannot reach its chat logs WARNING with the job, Channel and error, never the answer (`Cron job answer not delivered`, `Cron job failure alert not sent`, `Cron job message not noted in its chat's Session`).

## App notifications and Run history

User decision 2026-10-24: `notification_policy` is `all` (default), `errors` (failed/interrupted Runs and job alerts), or `muted`. It controls vBot badges and desktop toasts independently of delivery. Changing it does not read any result and works on terminal jobs or after execution references disappear; a policy-only Tool edit adds no execution permission ceiling. Muted jobs retain their unread alerts without publishing toast events.

Each admitted Run carries the Schedule id into Sessions. A continuation created solely for that Schedule's background results keeps its captured source and policy callback (`completion-delivery.md`). Manual Runs in a reused Session remain Chat results. Pure scheduled results no longer force their Session into Chat's default list; the Automations view opens that Session at the selected Run. Older installations only retain the last Run id per Schedule: catalog load adopts that exact known link and preserves its existing read state, without guessing older history.

`cron.activity {}` returns per-job activity plus the total notification count; busy Sessions are excluded from visible counters and dots using SessionActivity. `cron.runs {id, before?, limit?}` returns newest-first Run rows with Agent/Project/Session targets, status, times, unread state and `next_before` (default five, maximum 50). Expanding or paging never marks read. `cron.mark_read {id, through?, alert_at?}` acknowledges completed Runs through the supplied Run key and clears an alert only when its timestamp still matches, so a newer result or alert survives. At least one boundary is required. These reads do not load transcripts.
