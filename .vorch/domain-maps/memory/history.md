# Memory History

The per-owner Memory revision log and revert (`core/memory/_history.py`, the history methods of `MemoryService`) and the `memory.history`, `memory.show`, `memory.diff` and `memory.revert` RPCs. Storage rules of the Memory files themselves: `memory.md` -> Storage contract.

## Log and revert

`core/memory/_history.py` keeps one append-only JSON Lines file per owner. Identity Agent histories live at `<data_dir>/agents/<id>/memory-history.jsonl`, beside the Workspace, and move with rename/archive (`agent.md`). Project histories live at `<data_dir>/projects/<id>/memory-history.jsonl` and move with the Project Anchor's archive. Runtime passes `history_root=layout.agents` and `project_history_root=layout.projects`; an omitted root disables that kind's history. An id that is not path-safe or has no owner directory has no history, and its mutations still work.

- Each line is one revision of one scope with a sequential id: `v`, `id`, `at` (UTC), `scope`, `kind`, `actor`, `state` (hash of the resulting entries), `changes` (`added`/`removed`/`replaced` with `text`, `index` and `previous`), optional `session_id`/`run_id`/`run_kind` (the Run kind of a Tool change, such as `user` or `memory_reflection`; additive, absent on older lines), `reverts`. Shared Project revisions additionally carry optional `agent_id` identifying the actual writing Agent; the Project owner comes from the containing Anchor. Revision numbering and scope state are independent between personal and Project histories. Kinds: `edit` (a service mutation), `revert`, `baseline` (entries found when a scope's history starts) and `external` (the file changed outside the service). `baseline` and `external` also carry the complete `entries`; replay applies `changes` in between. Unreadable lines (not UTF-8, not JSON, a missing or mistyped field, a torn last line) are skipped with a warning. An append after a last line without its newline writes a newline first, so a torn fragment stays its own skipped line and the new revision keeps its id and writer after a restart.
- Change positions use the pre-revision list for removals and replacements and the post-revision list for additions. Replay applies removals/replacements from the end before inserting additions; revert translates replacement positions and undoes additions/replacements before restoring removals. Revert reconstructs transient occurrence identities from revision states and the existing `reverts` links, including earlier recorded reverts, and restores removals beside surviving original neighbors. Unrelated insertions/removals cannot select a different duplicate or displace restored entries; an already restored occurrence is not duplicated when later edits changed its text. An unreadable/incomplete history or an older incorrect revert keeps its recorded state whenever reconstructing its intended undo would disagree with that state. This preserves entry order and duplicate occurrences, including moves represented as removal plus addition, without changing the version 1 log format.
- Every backend mutation whose writer names its owner first compares the file with the last recorded state and records a difference as `external`, dated by the file's modification time, then records its own change. Personal mutations select `MemoryWriter.agent_id`; Project mutations select `MemoryWriter.project_id` and retain the writer's `agent_id` as attribution. Lock order: scope file lock, then history lock; multi-scope personal operations take user then agent file locks, while Project operations hold only the project file lock. A history failure never fails the mutation: a `MemoryError` logs a warning, any other exception an error with traceback, and the unrecorded change is noticed as `external` later.
- Mutation results name the revision that recorded them (`MemoryEntry.revision`, `MemoryTextChange.revision`; `None` without a history, for a listed entry or an unchanged result), which the `memory` Tool shows the user (`tools/memory.md`).
- `history`, `entries_at` and `compare` sync every scope of their owner first, so they include edits made since the last Memory operation. `revert(revision_ids)` takes back the named revisions newest first against the current entries, all or none: a removed entry returns at its old position, a replaced entry gets its previous text even when another entry already holds that text, an added entry is removed, and an effect that is already gone needs nothing. It returns a `MemoryRevertResult`: the scopes it `changed` and the `revert` `revisions` that recorded them, fewer when the history could not record one. When a later revision changed the same entry again it raises `MemoryRevertError` naming that revision and writes nothing. The budget applies to growing reverts; the `baseline` revision cannot be reverted; a revert is itself a revertible revision. `strict=True` with `related=` also refuses when any later revision of the scope outside the named and related ones added, removed or replaced an entry text a named change made or removed, even though the change could still be taken back (`MemoryRevertConflict.missing` false; used by the undo of a Run's changes). `check_revert` runs the same checks under the same locks and writes no entry (it does record outside edits first, like every history read), returning the scopes a revert would change; `recorded_revisions(agent_id)` returns the recorded revisions oldest first without that sync. Both serve the undo of a Run's changes (`automation/learning-changes.md`) (`tests/core/memory/test_memory_history.py`).
- A revert writes every changed scope before it records any. When a write fails, the scopes already written get their earlier file content back (a file that did not exist is removed) and the failure is raised; when that restore fails too, `MemoryRevertIncompleteError` names the scopes left reverted (`changed`) and the write `failure`, and those scopes are recorded as `revert` revisions (`revisions`) before it is raised, so reverting the same revisions again takes back only the rest. There is no durable journal: a process crash between two scope writes can still leave one scope reverted without a record.

## RPCs

`memory.history` (newest first, optional `scope` and `limit`, plus `total`), `memory.show` (entries after a `revision`), `memory.diff` (`from`, optional `to`, else current) and `memory.revert` (`revisions`, returning the projections and the recorded revisions) expose the history. Each requires exactly one `agent_id` or `project_id`, returns that owner field, and reads only that owner's scopes. The service history/read methods retain their positional Agent owner and add keyword `project_id`; revert/check_revert select the owner from `MemoryWriter`. Revert is a guarded mutation and publishes whenever it changed a file: also when the history recorded nothing, and before re-raising a `MemoryRevertIncompleteError` that left scopes reverted (`test_memory_revert_announces_changed_files_without_a_recorded_revision`). Reference and Project lifecycle locks match the other `memory.*` RPCs (`memory.md` -> Interfaces).
