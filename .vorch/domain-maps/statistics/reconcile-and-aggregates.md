# Reconcile and Aggregates

How `StatisticsIndex` ingests its two canonical sources into fact tables and maintains the `agg_*` aggregate tier: scope discovery, origin flags, the fact and aggregate tables, incremental maintenance, origin classification and Run request totals. The invariants (incremental equals rebuild, projection version, failure policy) are in `statistics.md`.

## Fact tables and scope discovery

The index stores per-Session cursors plus typed fact tables keyed `(session_key, seq)` (`stat_records`, `stat_calls`, `stat_tools`, `stat_errors`, `stat_checkpoints`, `stat_runs`, `stat_skills`), canonical Run records in `stat_run_records` keyed `(session_key, run_id)`, all holding only aggregation-consumed fields. Both call tables (`stat_calls` for saved Session usage, `stat_usage_calls` for the ledger) also keep each call's output speed from `usage.speed` (`_measurements._speed_facts`): `speed_tokens` and `speed_window_ms` only when both are positive whole numbers, `speed_estimated`, `first_token_ms`, and `speed_basis` (missing or unrecognized bases stay `unknown`). `stat_usage_records` also keeps the ledger outcome columns `duration_ms`, `failure_class` and `http_status` (`usage.md` -> Failures). `_accounting.py` maintains the typed durable-call projection that feeds `agg_usage`, `agg_runs` and `agg_run_models`; group usage and Run activity read Run totals from those aggregates. Changed calls go through the per-call path (unit lookup, prior contribution, upsert); a ledger rebuild (new index, ledger restore, revision rewind) instead fills the emptied usage tables a page at a time (`_LedgerRebuild`), keeping units and call sequences in memory and inserting each page in batches. A call that changed while the pages were read comes back on a later page and replaces its rows under its sequence, like the per-call path; both must write the same rows (`test_paged_revisions_and_new_run_origins_equal_a_full_rebuild`).

Scope discovery reads normalized Session summaries plus only the `seen_skills` summary value (`metadata_keys=("seen_skills",)`), never complete open-ended metadata. Reconciliation consumes each Session's own audit, superseded entries included, so a Message edit preserves historical Usage, Runs, Compactions, errors, and Tool activity while adding one `history_edit` record. Session summary values (title, `created_at`, `seen_skills`) come from the current listing on every read and are never stored, so metadata-only changes need no history read or index write. Only the origin flags are stored on `stat_sessions`: `is_subagent` (the `is_subagent_session` summary value) and `owner_name` (the listing Extension scope's owner; it sticks when another scope lists the same Session). A flag change rewrites the flags without a history read and recomputes that Session's aggregates. Reconciliation ingests ordinary growth from the generation-aware cursor, rebuilds only a new generation or an invalid cursor (a history edit or Agent takeover invalidates it), and deletes missing scopes. A Session that is deleted or archived between scope listing, version lookup, and detail loading is skipped and its old derived rows are pruned. Reports and Run activity share one surviving-Session read boundary.

## Aggregate tables

`_rollups.py` maintains derived aggregates over the fact tables in the reconcile write transaction, after Session reconcile, usage reconcile and repricing (table definitions in `_rollup_schema.py`).

- **Tables:** `agg_runs` (one row per Run, key `(session_key, run_id)`: status and timing, Model steps, visible and user messages, `first_visible_ms`, Tool calls and time, Compactions, errors, request totals, Models, request kinds, change stats), `agg_usage` (hourly ledger cube, key `(hour, unit_key, origin, model_key, kind, status, failure_class, http_status)`, the last two `''`/`0` when the call has none, with `hour = instant // 3_600_000_000` and `unit_key = stat_usage_units.session_key`), `agg_tools` (hourly, key `(hour, session_key, origin, name)`), `agg_tool_latency` (the same key plus `bucket = floor(4 * log2(duration_ms + 1))`, stored on `stat_tools.latency_bucket`), `agg_records` (hourly records and visible Assistant steps per Session and role), `agg_cache` (hourly saved Chat turns with Usage per Session: input, cache read/write, evaluated and suspected turns, last instant) `agg_cache_breaks` (each suspected cache break with its predecessor's input) and `agg_run_models` (per Run and Model, key `(session_key, run_id, model_key)`: the `Totals` measures of that Run's requests, for group usage). The measures of `agg_usage` and `agg_run_models` (`_rollups.USAGE_MEASURES`) are additive sums, output speed included (measured calls, estimated ones, window tokens and time, first-token calls and time, plus separate counts/tokens/time for each known speed basis, and the request duration as `duration_calls`/`duration_ms`), so ledger deltas and rebuilds stay exact; rates and averages are divided only when a report builds `Totals`. A new measure joins `USAGE_MEASURES`, `_MEASURE_SQL` and both tables in `_rollup_schema.py`, with a projection version bump.
- **First-token distribution:** `agg_first_token` uses the usage cube's key plus the exact observed `first_token_ms`, with a frequency `calls`. It shares the request before-images and whole-unit rebuild boundary with `agg_usage`, including origin changes, moves and repeated revisions; zero-frequency rows are deleted. Reports sum frequencies across their requested dimension and select nearest ranks in SQL, never transfer individual requests or the complete histogram to Python. Historical observations are rebuilt unchanged from canonical Usage; adding a histogram does not reinterpret old samples.
- **Maintenance contract:** reconcile records changed units in `RollupChanges`. Validated Session tails add only their new Tool, record and cache contributions; cache judgment includes the last preceding Assistant/checkpoint/takeover, even when it has no Usage or lies in another hour, without counting that predecessor twice. Changed ledger calls retain their first pre-mutation contribution in a temporary table, including before Run-origin changes and repricing; maintenance subtracts it and adds the final contribution using the same per-call integer rounding as a full rebuild. This covers repeated revisions and moves between hours, units, origins, Models, kinds and statuses, removing empty cube rows. A new Run ordinarily adds no historical work: only its already indexed requests need origin deltas, and existing Tool contributions whose Run origin changes require Session cube recomputation. Replaced/deleted Sessions, flag changes and affected Runs are recomputed; a whole ledger-unit recomputation overrides its deltas. A changed catalog fingerprint keeps whole-unit repricing, avoiding per-call before-images for bulk changes. A new index, ledger restore or revision rewind rebuilds all aggregates. The equality contract is tested in `test_statistics_rollups.py`, including the transient in-memory path; the test also fails when the incremental index falls back to a rebuild, because a failing maintenance step otherwise rebuilds and still matches. Gotcha: SQLite resolves a GROUP BY name to a source column before a result alias, so a query whose source includes a before-image table (columns named like the cube keys) groups by the key expressions, not their aliases; grouping by `failure_class` there failed every incremental usage step from 2026-10-20 to 2026-10-21 and rebuilt the whole index instead. Gotcha: `stat_sessions_generation` is a partial index (`WHERE generation_id <> ''`), and SQLite uses it only when a term on `stat_sessions` itself implies that condition, so every request-to-Session join (usage cubes, Run marking, recent calls) names `s.generation_id <> ''`. The same term on the request side scanned every Session per request: a full usage recompute took 18.8 s instead of 1.8 s on real data. Planner guard: `test_requests_find_their_session_through_the_generation_index`.

## Origin

Every Run, Tool call and request gets one origin, first match wins: `extension` (the Session's `owner_name`, or the request's), `subagent` (Run kind `subagent` or `is_subagent`), `automation` (`cron`, `calendar`), `channel`, `reflection` (background learning: `UNATTENDED_RUN_KINDS`, the three reflection kinds and `librarian`), `system`, `user` (user Runs and unknown kinds). A request of an indexed Run (Session generation plus `run_id`) takes the Run's origin; any other request in an Extension or Sub-Agent Session, and a chat or Compaction request anywhere, takes the Session origin (`extension`, `subagent`, else `user`); everything else is `background`. A Tool call takes its Run's origin, else its Session's.

## Run requests

A Run's request totals come from ledger requests for its Session generation and Run id, failed attempts included; a Run without any uses the usage saved in its own records. `primary_model` has the most input tokens (ties by name); `models` is a JSON array ordered by first use. `first_visible_ms` runs from the Run start (record timing, else admission) to its first visible assistant text.

## Report reads

`ReportContext` loads the listed Sessions and ledger units once per report (`temp.report_sessions`, `temp.report_units`) with their actor, Project and a Session address id shared by a Session and its ledger units. Group usage joins its owned Runs (`temp.group_runs`) to `agg_runs` and `agg_run_models` by primary key; `run_activity` is a SQL `ORDER BY ... LIMIT 200` plus a count over `agg_runs`. Report sections read the aggregate tier plus small indexed fact queries (errors, Tool error codes, Skill activations, Extension groups, recent calls, Run lists); only diagnostics Compactions still walk checkpoint rows (`_compactions.CHECKPOINT_SQL` folded by `CompactionAccumulator`).
