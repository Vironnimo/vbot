# Skills

Local skill metadata loading, validation diagnostics, and prompt allowlist filtering.

## Overview

`core/skills/` scans bundled skills under `resources/skills/`, user (global) skills under `<data_dir>/skills/`, per-agent private skills under `<data_dir>/agents/<id>/skills/`, project skills under the project's declared source format's directory (`PROJECT_SKILLS_SUBPATHS`: `opencode → <cwd>/.opencode/skills/`, `claude → <cwd>/.claude/skills/` — GLOSSARY → Source Format), configured extra skill directories, and the `skills/` folder of every **loaded extension** (see Extension-bundled skills). A directory is considered a skill only when it contains `SKILL.md` (a scan root whose own path contains `SKILL.md` contributes exactly that one package — see package roots below); the authored vBot package shape is exactly that file plus optional regular files under `scripts/`, `references/`, and `assets/`. The package is **read and write**: alongside the registry/loader, `core/skills/authoring.py` is the one validated write core (see Authoring & Write Scope) shared by every surface that creates or edits a skill.

**Skill Policy (`core/skills/policy.py`).** The domain owns one validated, versioned control-plane file at `<data_dir>/skills/policy.json` (the scanner only considers subdirectories containing `SKILL.md`, so the file never pollutes the pool). Schema version 1: `{"version": 1, "disabled": ["<name>"], "shared": {"<owner-agent-id>": ["<name>"]}}`. `SkillPolicyService` (constructor-injected storage) loads it — missing file means an empty policy; a malformed file yields diagnostics plus an empty effective policy instead of breaking startup — validates through the shared `core/config_validation.py` helpers, and mutates via `set_disabled(name, disabled)` / `set_shared(owner_id, name, shared)` under one process-local lock with one atomic replace per write. Names failing the trigger-safe charset produce warnings and are dropped from the effective sets; unknown owner ids and names matching no scanned Skill are kept in the file but ignored at resolution time (surfaced as stale entries by the manager inventory). There is no legacy compatibility or auto-migration. See Terms for Disabled/Shared semantics.

**Extension-bundled skills.** An extension in package/directory form may ship skills under `<extension>/skills/` (`<data_dir>/extensions/<name>/skills/` or a bundled `resources/extensions/<name>/skills/`), with no code — just the folder. The runtime folds every **loaded** extension's `skills/` dir into the global scan-root list (`Runtime._extension_skill_dirs`, appended by `_skill_scan_roots`), so extension skills present as **global** skills (origin `global`) with no inherent allowlist bypass; an Identity Agent may allow one personally, or a Project may opt into it through `skills_global_enabled`, in which case active Project Context grants that effective name. They are scanned **after** the user's own `<data_dir>/skills`, so a hand-authored global skill wins a name collision. Only `loaded` extensions contribute (disabled/failed/overridden add nothing); a single-file `.py` extension has no folder for a `skills/` child. The pool is refreshed live on every extension enable/disable/reload (`reload_extensions` and `apply_extension_disabled_change` both call `reload_skills`). They are **read-only** in the skill editor: `skill.read`/`skill.*` writes target only the `global`/`agent:<id>` scope directories (never an extension folder), so an extension skill never appears in the editor's editable list and no write can reach it — to customize one, copy it into `<data_dir>/skills` (your copy then shadows it by the precedence above).

**Project- and agent-scoped pool.** `runtime.skills_for(project_id, identity_agent_id=None)` merges selected Project, global/bundled, and optional Identity-private layers. A Rooted Identity Agent or an Identity Session with explicit Project Context passes the effective Project id plus its own id, yielding agent > project > global > bundled; the scoped registry always allows the Agent's private Skills and the exact effective Project Skill set while the Agent's configured `allowed_skills` continues to govern other shared Skills. A Config Agent passes its Session Project plus no identity id and receives the same Project-derived effective names through its resolved allowlist. Live Runs, compaction, preview, activation, and autocomplete share this policy. Agent-aware registries additionally insert the **shared layer** (see Terms → Shared Skill) between the Project root and the global scan roots: each owner's individually resolved shared package directories — never an owner's whole skills home — in deterministic sorted-owner/sorted-name order, so first-found-wins collision handling gives own > project > shared > global > bundled. Shared Skills are tagged with the receiver-facing Agent origin (`SKILL_ORIGIN_AGENT`), are NOT added to the receiver's `always_allowed`, and pass through `filter_allowed` like global Skills.

Skills are playbooks, not normal user-managed tools. A bundled Skill may package a script-backed capability without registering more Tools: its required binary gates catalog visibility, activation supplies the script path and operating contract, and the Agent invokes the script through `bash`. The registry exposes prompt metadata and internal activation metadata; actual activation is handled by the chat/tool pipeline. The ordinary `skill` Tool has three flat optional-field modes against the same live scoped registry: no arguments return available Skills grouped by origin; `name` activates that Skill's `SKILL.md`; `name` plus `file_path` returns one UTF-8 package file by relative path without activating it or exposing an absolute path in the file result. A named miss rescans disk once so a hand-dropped Skill can activate or serve a file without a restart. User messages can also activate Skills deterministically through `/skill-name` at the start of the message or `$skill-name` anywhere before the Provider request is sent.

## Terms

Domain-specific vocabulary for skills. The core Skill term lives in `.vorch/GLOSSARY.md`.

### Per-Agent Skill
**Definition:** A Skill that lives in one agent's **private** home `<data_dir>/agents/<id>/skills/` (archived with the agent on delete, like its Workspace). It is visible and loadable **only** to that agent — layered on top of the project/global/bundled pool at the highest precedence (agent > project > global > bundled) — and is **always-allowed for its owner**, bypassing the agent's `allowed_skills` filter. An active Project Context independently always-allows that Project's effective Skill set in the same scoped registry; it never exposes another Agent's private home. An agent authors its own per-agent skills with the `skill_manage` tool (and via `/learn`); the user can curate any agent's per-agent skills via the WebUI/RPC (`agent:<id>` scope).
**Not:** A global skill (`<data_dir>/skills/`, shared across the user's identity agents, user-curated), a project/team skill (the project's Source Format skill directory, e.g. `<cwd>/.opencode/skills/` or `<cwd>/.claude/skills/`, repo-owned), or a bundled skill (`resources/skills/`, read-only). Shared-pool Skills normally stay subject to the Agent's allowlist; the separate Project Context grant bypasses it only for names in that Project's effective Skill set.

### Disabled Skill
**Definition:** A Skill whose name is listed in the Skill Policy (`<data_dir>/skills/policy.json`). Disable is name-based across all origins (a master switch): if a bundled and a private Skill share a name, disabling hides both. It is completely invisible to every runtime consumer — absent from prompt catalogs, `/`–`$` triggers, the `skill` Tool list/activation, `$` autocomplete, config-Agent resolver name sets, explicit Project Context listings, and availability answers — including the owning Agent's own always-allowed copy. Mechanically, `SkillRegistry.load(excluded_names=...)` moves matching Skills to a separate excluded bucket absent from `get`/`list_all`/`filter_allowed`/availability; only editor-scope loads (manager/RPC) omit the exclusion so a disabled Skill stays visible and editable there. A trigger attempt against it yields the standard unknown/unavailable system reminder.
**Not:** A Project-level disable (`skills_project_disabled`, which removes a name from one Project's opt-in set) or an Agent allowlist omission. The policy switch outranks both.

### Shared Skill
**Definition:** An Identity Agent's private Skill that the Skill Policy marks shared under its owner id. It appears to every **other** Identity Agent as an extra pool layer (own-private > Project > shared > global > bundled), subject to the receiver's `allowed_skills` and to disable; in the receiver's prompt catalog it renders indistinguishably among "Your own skills" — no new group, no provenance hint — because it is tagged with the same Agent origin. The owner keeps it as an always-allowed private Skill unchanged. Config/Project Team Agents never see shared Skills (the private-home boundary stays identity-only). Receiving Agents may update a shared package through `skill_manage`'s `edit`/`patch`/`write_file`/`remove_file` actions (co-maintenance); `create` stays own-home-only and `delete` stays owner/human-only. Stale entries (owner id no longer an existing Identity Agent, or the package directory vanished) are ignored at load with a warning diagnostic and surfaced in the manager listing.
**Not:** A copy or move — the package stays at the owner's home and edits land there; not a new origin group; and not visible to the owner as anything different from before.

### Prompt-Epoch Catalog
**Definition:** The System Prompt Skill catalog **text** (`<available_skills>`) snapshotted on a Session's first build and reused until successful Compaction (stored in Session metadata as a `PinnedSkillCatalog`). Compaction rescans every Skill source and replaces the snapshot, so the next prompt epoch advertises current additions, removals, descriptions, and requirement availability while unchanged content remains byte-identical.
**Not:** A freeze on using Skills or on Skill activation. The `skill` Tool and `/`–`$` triggers resolve the live registry, while only the advertised catalog text is pinned between Compactions; activated Skill content is canonical conversation Context and is outside this System Prompt snapshot.

### Skill Availability Announcement
**Definition:** A one-time `<system-reminder>` note appended at the conversation tail when a Skill becomes available+allowed during a prompt epoch and had not already been shown — whether newly authored (`skill_manage`), opted into a Project (bundled/global), added to the global pool, or freshly scanned from a repo. Run setup diffs the current available+allowed Skills against Session metadata `seen_skills`; the first build and every successful Compaction seed that set from the freshly rendered catalog without announcing.
**Not:** A removal notice (additions only), a replacement for the Prompt-Epoch Catalog, or the live catalog returned by `skill({})`. Successful Compaction folds current Skills into the refreshed catalog; announcements cover additions between those boundaries.

## Authoring & Write Scope

`core/skills/authoring.py` (`SkillAuthoringService`) is the single validated write core shared by the Agent Tool, RPC, WebUI, CLI, and `/learn`. It operates on an already-resolved target root and exposes direct `create` / `edit` / `patch` / `delete` / `write_file` / `remove_file` methods; each successful call changes the published Skill immediately. `create`, `edit`, and `SKILL.md` patches reuse the loader's shared lenient document split, front-matter parse, metadata normalization, and `parse_vbot_requirements`: a missing name is filled from the trigger-safe directory name, an explicit different name is rejected, and accepted documents are canonicalized to complete YAML frontmatter before the service stamps `author` plus optional `source` under `metadata.vbot` and writes atomically. Support-file writes accept UTF-8 text only and remain confined to `scripts/`, `references/`, or `assets/`; patches default to `SKILL.md`, may target one support file, require a unique match unless `replace_all=true`, and write atomically. The service confines every path under the target root and refuses a target at/under a protected bundled root. Failures raise `SkillAuthoringError` with surface-neutral diagnostics.

**Write-scope boundary (v1 is data-dir only — vBot never writes the repo as runtime state):**
- **Agent Tool `skill_manage`** (`core/tools/skill_manage.py`, a directly configurable Tool, always registered, not gated on already having a Skill): the public contract is one open flat object requiring `action` and `name`, with only three optional siblings: `content`, `file_path`, and `match`. Actions are `create`, `edit`, `patch`, `write_file`, `remove_file`, and `delete`; the handler requires and accepts only each action's applicable fields. `content` carries complete `SKILL.md` for create/edit, replacement text for patch, and complete UTF-8 support-file text for write_file; `file_path` selects a support file and patch defaults to `SKILL.md`; `match` is the unique exact patch target. Agent authoring is deliberately private-only: every mutation targets the calling Identity Agent's Skill home, invalidates that Agent's registry, and emits one content-free control-plane event. **Shared-target resolution is the single exception** (see Terms → Shared Skill): when a name is not one of the caller's own Skills but resolves to a shared instance (own home first; otherwise the effective first-found shared package via the runtime-injected resolver), the update actions `edit`/`patch`/`write_file`/`remove_file` operate on that owner's package directory and invalidate all agent-aware registries; `create` and `delete` still refuse non-own targets. The Tool Result reports `scope: "own"` identically for own and shared targets and the Tool description stays untouched by design — a receiving Agent discovers editability through normal use, never through provenance wording. Global authoring remains available to the human RPC/WebUI/CLI surfaces; Project/repo and bundled Skills are never Agent Tool targets. The model-facing schema emits neither branch/closure keywords nor string/Boolean defaults. `skill_manage` carries the declarative `identity_agent` constraint at policy resolution, prompt visibility, and dispatch; it is configurable for Identity Agents and excluded from the Project Tool Whitelist by Projects-owned metadata derived from that constraint.
- **`/learn`**: a user-triggered internal run seeded with an authoring brief that uses `skill_manage` to author into the current agent's home (see `chat.md`).
- **RPC + user Accessors** (`server/rpc/skill_methods.py`, WebUI, CLI): `skill.read` (scope's own Skills with content), `skill.create` / `skill.update` / `skill.delete` / `skill.write_file` / `skill.remove_file`, each scoped `global` (`<data_dir>/skills`) or `agent:<id>`, `author="human"`; a Project/repo scope is rejected; global writes `reload_skills`, Agent writes `invalidate_agent_skills`. The manager RPCs (`skill.inventory`, `skill.set_disabled`, `skill.share`) are described under Interfaces. The Agent-scope id is validated traversal-safe before any path is built, and must name an **existing Identity Agent** — an unknown id (e.g. a Project Team slug) is rejected with `invalid_request` instead of silently creating an unowned `agents/<id>/skills` home.
- **Project skills** (the chosen format's skill directory, e.g. `<cwd>/.opencode/skills/` or `<cwd>/.claude/skills/`) stay repo-owned: authored with the ordinary `write`/`edit` file tools, validated at scan/load. The skill write core/tool/RPCs never write the repo in v1.
- **Bundled** (`resources/skills/`) is read-only — the write core refuses it.

## Data Model

- `SkillMetadata`: normalized `name` and `description`, internal `path`, optional `license`, `compatibility`, `metadata`, `allowed_tools`, and parsed vBot requirements from frontmatter when available. `SkillRegistry.always_allowed` is scoped metadata: an Identity registry contains its private Skill names plus the active Project's effective Skill names, while registries without Identity Project Context need no such Project grant.
- `SkillDiagnostic`: `name`, `path`, `valid`, `warnings`, and `loadable` for both loadable skills with warnings and rejected skill directories.
- Skill availability has three runtime states: `invalid` for malformed/non-loadable skills, `unavailable` for loadable skills with unmet required vBot requirements, and `available` when required requirements are satisfied. Optional requirements never make a skill unavailable.
- Complete YAML frontmatter is preferred and parsed with PyYAML. The shared parser strips one leading UTF-8 BOM, then degrades in stages: it first re-quotes unquoted scalar values that contain a colon-space (`key: a: b`), then extracts top-level simple `key: value` lines as untyped strings if YAML still fails. A document without complete frontmatter uses its entire content as the Skill body. A missing or empty `name` is filled from the directory name; a missing or empty `description` uses the first non-heading body text line, or an empty string when none exists. Every fallback is a loadable diagnostic rather than a loadability gate. Name/directory mismatch, names longer than 64 characters, and names using characters outside letters/digits/`-`/`_` (or not starting with a letter or digit) are also warnings only — such a name still loads but can never be triggered with `/name` or `$name` (only via the `skill` Tool's explicit `name` argument).
- vBot-specific machine-checkable requirements live under `metadata.vbot.requirements`, not `compatibility`. Supported required/optional primitives are `env`, `binary`, and `skill`, composed with nested `all` and `any` groups. Provider requirements are intentionally not supported; model/provider-specific prerequisites should be expressed as concrete env vars or skill instructions.
- Resource paths are not stored in `SkillMetadata`; the resource directories (`RESOURCE_DIRECTORIES`: `scripts/`, `references/`, `assets/`) are scanned at activation time.
- Bundled `resources/skills/` contains both instruction-only Skills and script-backed capabilities. `browser-use` requires `agent-browser`; `computer-use` requires `cua-driver`. Their Python wrappers normalize one backend action per invocation to JSON and retain backend state through an explicit named session rather than a resident vBot Tool object. Warning and broken skill diagnostics are covered by tests with local fixtures rather than shipped as bundled resources.
- A fresh Tool activation returns the SKILL.md instruction body alone in `content`; optional additional package files live in sibling `resource_files: {guidance, files}`, with `scripts/` paths absolute for direct `bash` execution and `references/` / `assets/` paths relative for `skill(name, file_path)` reads. Optional Bash credential guidance lives separately in `environment_access`. The activation path also derives one internal `<skill_content name="...">` context from those structured fields for deterministic triggers, current-epoch dedup, and Compaction carrier recognition; that wrapper never appears inside the Tool Result's `content`. An OpenClaw-compatible `{baseDir}` marker in the body is replaced with the absolute Skill directory at activation time. A `file_path` call, including one for a relative `scripts/...` path when script source is needed, returns `{name, status: "file_loaded", file_path, content}` with no absolute path and does not touch activation dedup. User-trigger activation persists an internal note; Tool activation uses its Tool Result as the durable carrier. Identical activation context for a name deduplicates within one Compaction epoch, but a directly changed package may activate again before the boundary and a committed checkpoint permits a fresh load; the newest carrier wins until that boundary.

## Prompt Catalog

Prompt-facing skill metadata is XML and follows the vBot agentskills.io-compatible catalog shape:

```xml
<available_skills>
  <skill_group label="Bundled skills">
    <skill>
      <name>teach</name>
      <description>Teach the user a topic so they actually understand it.</description>
    </skill>
  </skill_group>
  <skill_group label="Your own skills">
    <skill>
      <name>deploy</name>
      <description>Ship the app to the Pi.</description>
    </skill>
  </skill_group>
</available_skills>
```

- `available_skills` is the root; skills are grouped into `<skill_group label="...">` elements by **origin** (in order: Bundled / Your global skills / Skills from project '<name>' / Your own skills). The origin is a tag set at load from each skill's scan root (`SKILL_ORIGIN_*`; a project tag carries the project display name); `_format_skill_catalog` maps it to the English header. A registry loaded without origins renders one untitled group.
- Each `skill` element contains only `name` and `description` — the catalog stays **path-free**. This is a **presentation preference for prompt economy, not a hard routing rule** (vBot does not truncate the catalog). The explicit `project` Tool returns the loaded Project's own Skills in its ordinary Tool Result; after that result is persisted, the `skill` Tool resolves activation against that Project-aware registry while the current Prompt-Epoch Catalog stays unchanged (see `tools/project.md`).
- The catalog text is prompt-epoch-pinned: the first Session build snapshots it, ordinary Runs reuse it, and every successful manual or automatic Compaction forces a full Skill rescan and replaces it before the next request build. The refreshed catalog therefore reflects additions, removals, description changes, and requirement/environment availability from bundled, global, loaded-extension, Project, and private roots; `seen_skills` is synchronized to the same filtered catalog so those Skills are not redundantly announced. Between Compactions, newly available+allowed Skills are announced once via a tail `<system-reminder>` without changing the prefix. Tool presence and Skill activation remain independent and live.
- The prompt catalog includes only available Skills allowed by the Agent, filtered against the same explicit working-Project/private-layer registry as live activation. `chat.commands` and `prompt.preview` resolve a bare Identity Agent's current `root_project_id`; a qualified Project Config Agent receives no private layer. Lookup failure preserves the saved Project reference and fails closed.
- Skill values inserted into the XML block must be XML-escaped.
- The bundled Skills prompt must explain that `/skill-name` and `$skill-name` user tokens are activation hints once matching `<skill_content>` has been injected, so the Model follows the loaded Skill instructions without echoing the marker as requested output. Listed script paths are absolute and can be passed directly to `bash`; listed reference and asset paths are relative and are read on demand through `skill(name, file_path)`. Script source remains readable through the same Tool with its relative `scripts/...` path.

## Interfaces

- `core/skills/__init__.py` exports `SkillMetadata`, `SkillRegistry`, `SkillAvailability`, `SkillRequirements`, the allowlist/frontmatter constants (`WILDCARD_ALLOWLIST`, `FRONT_MATTER_DELIMITER`), the origin vocabulary (`SKILL_ORIGIN_AGENT`/`GLOBAL`/`BUNDLED`/`PROJECT_PREFIX`, `project_skill_origin`, `skill_origin_sort_key`), the scan helpers (`scan_skill_names`, `scan_project_skill_names`, `project_skills_dir`, `load_project_skill_registry`), and the authoring write core (`SkillAuthoringService`, `SkillWriteResult`, `SkillAuthoringError`, `SkillAuthor`).
- `SkillRegistry.load(skills_dir, extra_dirs=None, environment=None, always_allowed=None, origins=None, excluded_names=None) -> SkillRegistry` — missing roots mean an empty contribution; failure to enumerate one root becomes an invalid diagnostic plus warning and does not block the remaining roots or Runtime startup. A scan root whose own path contains `SKILL.md` is a **package root** and contributes exactly that one package (this is how shared packages are inserted without scanning an owner's whole home). `environment` snapshots the env used for requirement checks (see Constraints & Gotchas); when omitted it defaults to `os.environ`. `always_allowed` names bypass the `allowed_skills` filter for this registry only (the runtime passes an agent's own private skills). `origins` is a per-scan-root tag list whose value lands on each loaded skill's `SkillMetadata.origin` for catalog grouping. `excluded_names` (the policy disable switch) removes matching names from the effective pool into a separate bucket readable via `excluded_skills()`; runtime consumers pass the disabled set, editor-scope loads omit it.
- `Runtime.refresh_skills_for(project_id, identity_agent_id=None) -> SkillRegistry` is the explicit Compaction refresh seam: it reloads the global/bundled/loaded-extension pool, invalidates every cached Project/Agent registry, and then returns the freshly resolved scope. Normal consumers use cached `skills_for(...)`; they must not imitate the full rescan independently.
- `load_project_skill_registry(project_cwd, source_format, bundled_scan_roots, environment=None) -> SkillRegistry` — the project-first merge (the format's own skill dir then the bundled roots). `scan_project_skill_names(project_cwd, source_format, environment=None) -> frozenset[str]` — only the project's own skill names (the set the resolver subtracts `skills_project_disabled` from); `scan_skill_names(skills_dir, environment=None) -> frozenset[str]` is the general one-directory scan it (and the agent-private-home scan) builds on. `find_skill_package_dir(skills_dir, name, environment=None) -> Path | None` resolves a Skill *name* to its exact package directory inside one home (normalized front-matter name; `None` = stale entry) — the shared-layer insertion and shared-target authoring both build on it. `project_skills_dir(cwd, source_format)` maps the format to its directory via `PROJECT_SKILLS_SUBPATHS` — the format is a **required** argument (no default; every caller states which format it means), and a test asserts the dict's keys equal `core.settings.PROJECT_SOURCE_FORMATS` so the vocabularies cannot drift. `SkillRegistry.load(..., always_allowed=None)` marks names that bypass the `allowed_skills` filter for that registry only. The runtime owns the caches and exposes `agent_skills_dir(agent_id)` (= `<data_dir>/agents/<id>/skills`), `skills_for(project_id, identity_agent_id=None)`, `project_skill_names(project_id)`, `invalidate_project_skills(project_id=None)` (also drops matching agent-aware entries), and `invalidate_agent_skills(agent_id=None)`.
- Manager surface (Skills-owned): `SkillPolicyService` (`policy_path`, `load`, `validation_diagnostics`, `set_disabled`, `set_shared`) persists `<data_dir>/skills/policy.json`; Runtime exposes it as `runtime.skill_policy` and adds `skill_inventory()` — one exclusion-free pass over every source annotating each package with origin, owner, share/disable state, availability, and warnings, plus `stale_shared` entries and policy diagnostics — and `agent_owns_private_skill(agent_id, name)`. RPC: `skill.inventory` `{}`, `skill.set_disabled` `{name, disabled}` (validates the name exists somewhere → `invalid_request`; then reloads skills), and `skill.share` `{agent_id, name, shared}` (agent must exist and own that private Skill). Both mutations publish `resource_changed(kind="skills")`. Disable change invalidates via `reload_skills()`; share change via `invalidate_agent_skills(None)` (shared Skills never enter the global pool).
- Registry read surface (return types live on the `core/skills/` dataclasses): `get(name)`, `list_all()`, `filter_allowed(allowed_skills)`, `availability_for(name, allowed_skills=None)`, `is_allowed(name, allowed_skills)`, `diagnostics()`, `invalid_diagnostics()`, `warnings_for(name)`.
- Activation helper behavior (`load_skill_content`): read the Skill body after YAML frontmatter, substitute `{baseDir}`, scan resource directories while excluding generated `__pycache__` trees, present executable scripts as absolute paths and readable references/assets as relative paths, and return the raw body plus structured `resource_files`, optional `environment_access`, and an internal activation context. A `skill` Tool load projects only the public structured fields into its durable Result; a user trigger persists the internal context as a `[skill-context]` note under the triggering message (see `tools/skill.md` and `chat.md`).

## Conventions

- `allowed_skills=['*']`, or a missing/`None` allowlist, exposes all loaded skills — this is real `_allowed_names` behavior, not just a test default.
- `allowed_skills=[]` exposes none.
- Explicit allowlists match exact skill names.
- Unknown allowlist entries are ignored because skills are not hard execution gates.
- Skill dependency requirements (`skill: other-skill`) must not bypass agent allowlists. If the dependency skill is not allowed for the current agent, the dependent skill is unavailable for that agent.
- Duplicate skill names are resolved by first-found-wins scan order and recorded as diagnostics for rejected duplicates. In a project's merged registry the project skill dir is scanned first, so a project skill **wins** a name collision with a bundled skill of the same name (one slot, the project's own playbook wins); the WebUI editor drops the shadowed bundled name from the opt-in list.
- `skill` and `skill_manage` are ordinary configurable Tools controlled by Tool Access Policy and listed in `tool.list`; neither is gated on the Agent already having a Skill (a Skill can be authored or activated mid-Session). `skill` is seeded default-on in the Project Tool Whitelist. `skill_manage` carries the declarative `identity_agent` constraint, so the common resolver withholds it from a config/Project Agent (empty Workspace) at Provider/prompt visibility and dispatch, and Projects-owned configurability metadata excludes it from the Project Tool Whitelist.
- Full Skill instructions have a single provider-visible source per activation: the carrier at the point of activation (the `skill` Tool Result, or the trigger note under the user message). `ChatSession.register_skill_activation` deduplicates identical content only until the next successfully committed Compaction checkpoint. That checkpoint removes full activation carriers from active Context, revokes Skill-derived environment grants, and retains only a names reminder for the immediately completed activation epoch; reloading after the boundary creates a fresh carrier with the current package content (see `chat/request-building.md`).
- `/skill-name` and `$skill-name` triggers preserve the original user message. Unknown, non-loadable, or unavailable triggers become internal system reminders rather than activations.
- `$skill-name` is a Skill-only mention convention. Surfaces that provide `$` autocomplete must list only currently available Skills and must not include Slash Commands. Slash autocomplete may list active Built-in and Extension Commands plus available Skills because `/` is the shared user-entry affordance; backend Command dispatch handles every recognized Command before the normal Skill-trigger path. A same-named Skill therefore remains explicitly reachable through `$skill-name`.

## vBot Requirements Metadata

Example:

```yaml
metadata:
  vbot:
    requirements:
      all:
        - binary: git
        - any:
            - binary: gcc
            - binary: clang
        - any:
            - env: OPENAI_API_KEY
            - env: ANTHROPIC_API_KEY
        - skill: vbot-cli
      optional:
        - binary: jq
```

- `all` requires every child node.
- `any` requires at least one child node.
- `optional` is a list of nodes whose missing checks are reported but do not change `available` status.
- `env` checks for a non-empty value in the snapshot skill environment: process environment first, then data-dir `.env` fallback (see Constraints & Gotchas).
- Every declared `env` leaf is also an activation-time Bash grant. A Tool activation returns the notice as the sibling `environment_access` field, while the internal trigger/Compaction context wraps the same guidance in `<environment_access>` before the instructions; both list those names and explain per-call `bash.env_keys`. The current Run derives Skill grants from the Session's active Skill names and effective Skill registry. Permanent Agent Bash grants are a separate `tools.bash.allowed_env` source (see `tools/bash.md`).
- `binary` looks up the snapshot environment's `PATH` with `shutil.which` — safe path lookup, not shell execution.
- `skill` checks that the dependency skill is loadable, available, and allowed for the current agent.
- `skill` dependency chains are walked with a cycle guard: a circular `skill:` requirement resolves to `unavailable` with a `skill dependency cycle: a -> b -> a` reason instead of recursing.
- Malformed `metadata.vbot.requirements` makes the skill invalid/non-loadable.

## External Dependencies

- `pyyaml` is a direct core dependency for `SKILL.md` YAML frontmatter parsing.
- Script-backed bundled Skills may declare their own non-core binary dependency. `browser-use` wraps `agent-browser`; `computer-use` wraps `cua-driver`. Neither wrapper installs or upgrades its backend, and an absent binary keeps only that Skill unavailable.

## Constraints & Gotchas

- Requirement `env`/`binary` checks run against an environment snapshot captured when the registry is loaded/reloaded (`.env` fallback overlaid by `os.environ`, process env winning), not live `os.environ` at activation time. A newly exported key or freshly installed `PATH` binary does not flip a skill's availability until the registry reloads.
- Bundled Skill scripts execute on the machine running the vBot server through that Run's `bash` environment. In a Pi-server plus Windows Desktop Client deployment, `browser-use` and `computer-use` therefore control the Pi host, not the user's Windows browser or desktop. Their screenshots are file artifacts and become Model-visible only after the Agent loads the returned path through `read`.
- The prompt catalog and `skill({})` result keep paths out as a presentation preference (prompt economy, clean UI), not a hard routing rule. The explicit `project` Tool result may carry Project Skill paths as structured context metadata, but Agents activate those Skills normally by name. A fresh activation exposes absolute executable-script paths and relative readable-reference/asset paths under `resource_files`; trackable `skill(name, file_path)` reads still accept only relative package paths and return only that relative path. Provenance (`metadata.vbot.author`/`source`) is internal too — it never appears in the catalog (only name/description/origin do).
- Non-loadable skill directories should be retained as diagnostics so the UI can explain I/O failures, malformed vBot requirements, or duplicate names. Plain YAML errors and missing ordinary metadata use loadable fallbacks instead.
- Skill metadata diagnostics are logged at `DEBUG` (`vbot.skills`) **once per process**, keyed by `(resolved SKILL.md path, warning text)`, and the message carries that path so the file is locatable when debug logging is enabled. Registries reload on every project run/reload, so without this guard a repaired/mismatched skill floods debug logs; a server restart starts a fresh process and logs the current diagnostics once again. Only the log is deduplicated — the diagnostics returned to callers (`warnings_for`, `diagnostics`, `skill.list`/UI) still carry every warning on every load.
- The project forbids in-app legacy compatibility. Do not add automatic migrations for older `allowed_skills` formats; use explicit converter scripts if needed.
