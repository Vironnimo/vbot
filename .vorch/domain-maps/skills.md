# Skills

Skill package installation, metadata loading, validation diagnostics, and prompt allowlist filtering.

## Overview

`core/skills/` scans bundled skills under `resources/skills/`, user (global) skills under `<data_dir>/skills/`, per-agent private skills under `<data_dir>/agents/<id>/skills/`, project skills under the project's declared source format's directory (`projects.md` -> Source Format), configured extra directories, and the `skills/` folder of every **loaded extension**. A directory counts as a skill only when it contains `SKILL.md`; imported packages may also contain arbitrary regular support files, including binary assets. `scripts/`, `references/`, and `assets/` are conventional directories, not the read boundary. The domain is **read and write**: `core/skills/authoring.py` is the one validated write core shared by every surface that installs, creates or edits a skill (see Authoring & Write Scope). Each writable home records every write in its Skill History, and deleting a Skill moves it into the home's Skill Archive (Terms).

**Skill Policy (`core/skills/policy.py`).** One validated, versioned control-plane file at `<data_dir>/skills/policy.json`: `{"format_version": 1, "disabled": ["<name>"], "shared": {"<owner-agent-id>": {"<skill-name>": ["<receiver-agent-id>"]}}}` (Generation 1 contract in `settings.md`; unknown top-level fields survive mutations). Missing file means empty policy; a malformed file yields diagnostics plus an empty effective policy instead of breaking startup. Mutations run under one process-local lock with one atomic replace per write. Trigger-unsafe names and receivers that are not Identity Agent ids produce warnings (in the manager diagnostics and `doctor config`) and drop from the effective policy only: mutations rewrite the stored lists unchanged apart from the one entry they change. Unknown owner ids and names matching no scanned skill are kept in the file but ignored at resolution (surfaced as stale entries). No legacy compatibility or auto-migration. Disabled/Shared semantics live in Terms below.

Policy mutations strictly load the existing document and reject malformed files (including a missing or other `format_version`) without replacing them with the tolerant read fallback; the RPC edge reports that refusal as a `domain_error` carrying the file diagnostics, not as an unexpected failure. A pre-Generation-1 `version` 2 document has no `format_version` and is refused like any other. Writes validate trigger-safe Skill names and canonical Agent ids before persistence; sharing requires at least one receiver other than the owner.

**Extension-bundled skills.** An extension may ship skills under `<extension>/skills/` - folders only, no code. Every **loaded** extension's folder joins the global scan roots, so extension skills present as **global** skills without inherent allowlist bypass (an Identity Agent may allow one personally, or a Project opts in via `skills_global_enabled`). They are scanned **after** the user's own global directory and the configured `skill_directories`, so a hand-authored or explicitly configured skill wins name collisions, and **before** bundled Skills, so an Extension Skill overrides a same-named bundled one. Only loaded extensions contribute; disabled/failed/overridden add nothing, and the pool refreshes live on extension enable/disable/reload. They are **read-only**: editor writes target only `global`/`agent:<id>` scopes, so customizing one means copying it into `<data_dir>/skills`.

**Project- and agent-scoped pool.** `runtime.skills_for(project_id, identity_agent_id=None)` merges the layers with first-found-wins precedence **own > project > shared > global > bundled**: private Skills are always allowed for their owner unless its Agent Skill Exclusions (Terms) name them, the effective Project set is always allowed inside active Project Context, shared Skills insert between Project and global layers (each owner's individually resolved packages, never a whole home, in sorted order), while the Agent's `allowed_skills` minus its Agent Skill Exclusions (Terms) governs everything else. An Identity Agent with exclusions always resolves such a scoped registry; the per-(Project, Agent) cache entry is reused only while it carries the Agent's current `excluded_skills`, so `agent.update` or a hand edit of `agent.json` needs no explicit invalidation (`test_runtime_skills.py`). Config Agents receive the Project-derived set through their resolved allowlist. Live Runs, compaction, preview, activation, and autocomplete share this policy. Shared Skills carry the receiver-facing Agent origin, never enter the receiver's always-allowed set, and pass through `filter_allowed` like globals.

Skills are playbooks, not normal user-managed tools: a bundled Skill may package a script-backed capability without registering Tools - its required binary gates visibility, activation supplies script path plus operating contract, and the Agent invokes it through `bash`. The ordinary `skill` Tool has three flat modes against the live scoped registry: no arguments lists available Skills by origin; `name` activates `SKILL.md`; `name` + `file_path` returns one UTF-8 package file without activating or exposing absolute paths. A named miss rescans disk once so hand-dropped Skills work without restart. User messages activate deterministically via `/skill-name` at message start or `$skill-name` anywhere before the request.

## Terms

Domain-specific vocabulary for skills. The core Skill term lives in `.vorch/GLOSSARY.md`.

### Per-Agent Skill
**Definition:** A Skill living in one agent's private home `<data_dir>/agents/<id>/skills/` (archived with the agent like its Workspace, together with the home's Skill History and Skill Archive beside it). Visible/loadable only to that agent, highest precedence, and **always-allowed for its owner**, bypassing `allowed_skills`. Active Project Context independently always-allows that Project's effective set - it never exposes another Agent's private home. Agents author their own via `skill_manage` (and `/learn`); users curate any agent's via WebUI/RPC (`agent:<id>` scope).
**Not:** A global, project/repo-owned, or bundled skill. Shared-pool Skills normally stay subject to the receiver's allowlist; the Project Context grant bypasses it only for that Project's effective names.

### Disabled Skill
**Definition:** A Skill whose name sits in the Skill Policy. Disable is name-based across all origins (a master switch: a bundled and a private same-named skill hide together). It vanishes from every runtime consumer - catalogs, triggers, Tool list/activation, resolver sets, availability answers - including the owner's own always-allowed copy; only editor-scope loads still show it. A trigger attempt yields the standard unknown/unavailable reminder.
**Not:** A Project-level disable (`skills_project_disabled`) or an Agent allowlist omission - the policy switch outranks both.

### Agent Skill Exclusion
**Definition:** A name in an Identity Agent's optional `excluded_skills` list (`agent.md`). It is removed from what `allowed_skills` grants, also from `*` or a missing allowlist, so `["*"]` plus exclusions means "all except", including Skills added later. It also turns off the Agent's own private Skills of that name (user requirement 2026-09-29: own Skills are toggleable per Agent; a new own Skill is on unless the list already names it), but never the active Project's effective set, so a same-named Project grant still wins. An excluded own Skill leaves the catalog and `skill` activation for that Agent, while `skill_manage` still edits or deletes its package (it works on the private home, not the scoped registry). The Skill stays loaded in the scoped registry like any unselected Skill, and a Skill depending on it becomes unavailable. Config/Project Agents and temporary (Swarm) Agents have no exclusions.
**Not:** A Disabled Skill - the registry's `excluded_names`/`excluded_skills()` bucket is the policy switch, while Agent exclusions are `SkillRegistry.allowlist_exclusions`.

### Shared Skill
**Definition:** An Identity Agent's private Skill the Policy marks shared with specific receiver Identity Agent ids. Each receiver sees it as an extra pool layer (own > project > shared > global > bundled), subject to its own `allowed_skills` and disable, rendered indistinguishably among its own skills (same Agent origin tag, no provenance hint). The owner keeps it unchanged as always-allowed private Skill. Config/Team Agents never see shared Skills. Receivers may co-maintain through `skill_manage`'s edit/patch/write_file/remove_file; `create` stays own-home-only and `delete` owner/human-only. Stale entries (owner gone, package vanished) ignore at load with a warning (once per entry until it resolves) and surface in the manager listing.
**Not:** A copy or move - edits land at the owner's home; not a new origin group; not an all-agents broadcast.

`SkillRuntime.invalidate_agent_skills(owner_id)` owns the dependency from a private home to its shared receivers and invalidates their cached registries across every Project context. Tool and Accessor writes identify the owner without duplicating that dependency. This includes creating, changing or deleting a package named by an existing share, and archiving or renaming the owning Agent; unrelated Agent caches remain intact (`test_runtime_shared_skills.py`).

### Skill History
**Definition:** The append-only revision log of one writable Skill home, `skill-history.jsonl` beside it (`<data_dir>/skill-history.jsonl` for global, `<data_dir>/agents/<id>/skill-history.jsonl` for a private home), outside every scan root. Every write through the authoring owner records who wrote it (`human`, `agent`, or a background `reflection`/`librarian` writer, with Session, Run and Run kind) and the changed files; the history is also where a Skill's origin (who created it) and pin live. Changes made outside vBot become `baseline`/`external` revisions before the next write or history read. People revert revisions, all or none. Contract: `skills/history.md`.
**Not:** Version control or a backup: a text that is not UTF-8 or exceeds 1 MiB is recorded by hash only, and a purged archived package is gone. Not the Memory history (`memory.md` -> History).

### Skill Archive
**Definition:** The folder `skill-archive/` beside a writable home that a deleted Skill package moves into, with reason `deleted`, `absorbed` (its instructions now live in another Skill of that home, `absorbed_into`) or `inactive`. No registry scans it. A person restores a package under its name while no Skill of that name exists in the home, or purges it permanently; the `skill` Tool tells Agents that an archived name was deleted or merged (`tools/skill.md`).
**Not:** An Archive Entry (`archive.md`): no retention period or `archive.*` RPC applies to it. Deleting an Identity Agent moves its private home, Skill History and Skill Archive into the Agent's Archive Entry.

### Pinned Skill
**Definition:** A Skill a person pinned (`skill.set_pinned`, `vbot skill pin`, the WebUI Pin toggle); the pin is recorded in the Skill History. Background Writers never change, delete or absorb a pinned Skill. Only a person pins or unpins.
**Not:** A write lock - people and attended Agents still change it - and not the Prompt-Epoch Catalog's `PinnedSkillCatalog`.

### Background Writer
**Definition:** A Skill write by a background actor (`BACKGROUND_ACTORS`): `reflection` for a Reflection Run, `librarian` for the Librarian: its aging archives, its consolidation Run and every call in a Librarian Session, also while the user talks with it there (`automation.md` -> Librarian). `skill_manage` and `skill` name the writer through `core/tools/skill.py::skill_writer`: a Run of kind `librarian` or a call in a Session bound to a Skill subject (`skill_agent_id`) writes as `librarian`, another unattended Run kind (`core.runs.is_unattended_run_kind`) as `reflection`. A background writer never changes, deletes or absorbs a pinned Skill, never reverts, and its `delete` must name the own Skill that absorbed the instructions. Who created a Skill does not limit it, nor does sharing (it co-maintains a Skill shared in like an attended receiver) or an automation that triggers the Skill, whose trigger follows a merge (user decision 2026-10-03: the pin is the one hands-off the user sets). A history that cannot be read fails closed, because whether the Skill is pinned is unknown. A Librarian Run's first change to an existing Skill that another Run or a person changed after the Librarian Run started is refused once, so the pass reads the Skill again. Background Sessions do not count as Skill use of the Agent whose Skills they change (`statistics.md`).
**Not:** An attended Agent: a `skill_manage` call from any other Run kind and Session writes with actor `agent` under the ordinary write scope.

### Prompt-Epoch Catalog
**Definition:** The System Prompt Skill catalog **text** (`<available_skills>`) snapshotted on a Session's first build and reused until successful Compaction (persisted as `PinnedSkillCatalog`, qualified with the Run's Skill-scope Project so re-rooting an Identity Agent re-renders it at the next Run). Compaction rescans every source and replaces the snapshot, so the next epoch advertises current additions/removals/descriptions/availability while unchanged content stays byte-identical.
**Not:** A freeze on activation - the `skill` Tool and triggers resolve the live registry; only the advertised text pins between Compactions, and activated content is canonical conversation Context outside this snapshot.

### Skill Availability Announcement
**Definition:** A one-time tail `<system-reminder>` when a Skill becomes available+allowed during a prompt epoch and was not already shown (newly authored, opted into a Project, added globally, or freshly scanned). Run setup diffs current available+allowed against the Session's seen-Skill set (`ChatSessionManager.seen_skills`); a Session without a recorded set (a new Session, or one forked or moved into another Agent or Project) and each successful Compaction seed that set silently.
**Not:** A removal notice, a replacement for the Prompt-Epoch Catalog, or the live `skill({})` result. Tools changed mid-epoch get their own `[tool-change]` announcements, including removals (`chat/request-building.md` -> Tool catalog per prompt epoch).

## Authoring & Write Scope

`core/skills/authoring.py` (`SkillAuthoringService`) is the single validated write core behind the Agent Tool, RPC, WebUI, CLI, and `/learn`. It operates on an already-resolved target root with direct install/create/edit/rewrite/delete/write_file/remove_file methods plus `read_text`; each success publishes immediately. Every mutation names its `writer` (`SkillWriter(actor, session_id, run_id, run_kind)`; people pass `HUMAN_WRITER`, the `install` default), enforces the Background Writer rules before the write (`check_writable` refuses up front), and records one Skill History revision after it; a history failure after the write only logs. The same owner serves `history`, `recorded_revisions`, `records`/`record`, `check_revert`/`revert`, `archived`/`archived_skill`, `restore`, `purge` and `set_pinned` (`skills/history.md`). Install prepares a complete package, preserves original file bytes and frontmatter, and publishes it through the same write lock; it neither executes package contents nor changes access policy. Create/edit/SKILL.md rewrites reuse the loader's lenient document parsing and canonicalize complete YAML frontmatter, stamping `author` (`human` for a person, `agent` for every Agent writer) plus optional `source` under `metadata.vbot` and writing atomically; a missing name fills from the trigger-safe directory name and an explicit different name is rejected. Support-file authoring still accepts UTF-8 only, confined to `scripts/`/`references/`/`assets/`. `create` refuses a Skill name, and `write_file` a new support file or folder name, that Windows reserves (`core.utils.ids.is_reserved_name`: devices such as `con` or `nul.py`, `:`, a trailing dot or space) on every platform; replacing an existing file keeps working. `rewrite(target_root, name, relative_path, edit)` is the validated read-modify-write primitive: under the write lock it hands `edit` the current `SKILL.md` or support-file text with LF endings, aborts without writing when `edit` raises, validates a rewritten `SKILL.md` like edit, and writes in the file's detected line-ending style. Text matching is not authoring policy: the `skill_manage` Tool owns it (below). create writes LF; edit/rewrite/write_file preserve an existing file's line endings. edit and write_file replace a file whole, so they also replace an existing file that is not UTF-8 text (written with LF, reported with `before: None`); rewrite refuses it. Every path stays under the target root; protected bundled roots are refused. Failures raise `SkillAuthoringError` with surface-neutral diagnostics. Each result reports the files it changed (`SkillWriteResult.changes`: package-relative path, `created`/`updated`/`deleted`, text with LF endings before and after, `None` for an absent side or text that is not UTF-8 or exceeds 1 MiB); delete moves the package into the Skill Archive and reports every regular file of the package as deleted, root `SKILL.md` first; a link inside it (Windows junctions included) moves as a link, and the files behind it are neither reported nor read.

### `skill_manage` calls

- Schema: `action` + `name` required; `content` (complete SKILL.md for create/edit, complete file for write_file), `old_string`/`new_string`/`replace_all` (patch), `file_path` (support file; patch defaults to `SKILL.md`). Unadvertised `description` (create/edit), `absorbed_into` (delete), `scope` and `category` are validated but not offered.
- Argument repair (`_normalize_skill_manage_arguments`): wrappers and action formatting, `str_replace` -> patch, `delete_file` -> remove_file; `match`/`old_str`/`old_text`/`search`/`find` -> old_string, `new_str`/`new_text`/`replacement` -> new_string, `path`/`file`/`file_pth` -> file_path, `skill`/`skill_name` -> name. `content`, `new_string` and `file_content` are one text field resolved per action (patch keeps it as new_string, the others as content); empty duplicates are placeholders, two different nonempty texts fail before writing. A name with invocation marks (`/name`) or a package path (`name/references/x.md`, `name/SKILL.md`) splits into name and file_path; a leading slash or `name/` prefix is dropped from file_path.
- Patch matching (`_replace`): `fuzzy_match.replace_fuzzy` precise strategies (exact, Unicode/typography folding, trimmed lines, collapsed horizontal whitespace), so CRLF, trailing spaces and curly quotes in a copied `old_string` still address exactly one span. A folded match writes the file's own glyphs into `new_string` (Model curly vs file straight, and the reverse per aligned line). Only when nothing matches, one extra level of JSON escaping (`\n`, `\"`, `\t`, `\\`) is decoded in both strings, with a note. Then, without `replace_all` and unless `new_string` is already present, `copy_match.replace_copied` applies an `old_string` copied with errors (rules: `tools/apply_patch.md`), with a note per differing line and respelled word; a copy resembling several places fails `ambiguous_match` ("does not match exactly and resembles N places ... Copy the current text of the one to change"). A patch whose result equals the file reports `... already reads as new_string at line N; nothing changed.` Misses fail `text_not_found` with up to two closest excerpts and the `skill` read call, plus the support file that holds the text when exactly one does; ambiguity fails `ambiguous_match` with line numbers and the `replace_all` option. No write happens on any failure.
- Action refusals (`invalid_arguments`, before any write) name the corrected call: create/edit without front matter or description show the header template (create builds front matter from `description` when the content has none; a missing front-matter name or description is filled from the arguments); a front-matter name or description that contradicts the arguments fails; edit with `old_string` and a fragment applies as patch with a note, with a complete document it is refused; patch without `old_string` names edit when the text is a complete document; write_file to `SKILL.md` is an edit; remove_file of `SKILL.md`, delete with file_path or text, write_file with old_string, create with a support file_path, and description outside create/edit are refused. `scope` values meaning own (`own`, `private`, `agent`, ...) are accepted; others are refused as read-only; `category` is noted as unused.
- A non-create target missing from the caller's home (and not shared or visible elsewhere) fails `skill_not_found` with similar own names (`similar_skill_names`) or the own-name list; case, separator and near-miss names are suggested, never written.
- Background guards: a call from a Run of kind `librarian` or in a Librarian Session writes as `librarian`, one from another unattended Run as `reflection`, every other call as `agent`, each with the Session, Run and Run kind (`core/tools/skill.py::skill_writer`, `tools/skill.md`). Before any write to an existing Skill (`SkillAuthoringService.check_writable`), a background call fails `skill_protected` for a pinned Skill (`SKILL_MANAGE_PINNED_REFUSAL`) and for one whose history cannot be read (`SKILL_MANAGE_HISTORY_UNREADABLE_REFUSAL`); `create` of a new own Skill stays open. Origin, sharing and automation triggers do not limit it (Background Writer): it edits a Skill shared in from another Agent in the owner's package like an attended receiver. A background `delete` needs `absorbed_into`, another own Skill that now holds the instructions (`SKILL_MANAGE_ABSORBED_INTO_REQUIRED`); an attended delete may name it. Every `delete` with `absorbed_into`, by any writer, follows the merge: `register_skill_manage_tool(follow_merge=...)` (wired to `Runtime.follow_skill_merge`, `core/runtime/_skill_merge.py`) lists, under the automation reference lock, what names the Skill (the owner's shares of it in the Skill Policy and the `/name` or `$name` triggers in the owner's live Bootstrap, Cron and Calendar automations, `AutomationReferences.agent_skill_triggers`), hands that list to the delete, which records it on the archive revision (`followed`, `skills/history.md`), and once the delete succeeded moves each one to the absorbing Skill (`SkillPolicyService.move_shared`, `AutomationReferences.rename_skill_triggers`). The result then adds `Note: These now use Skill ...` for what moved and `Warning: These could not be changed and still name ...` for what did not; chat activation does not follow absorbed redirects, so such a trigger finds nothing. Undoing or restoring the merged Skill moves nothing back (`automation/librarian.md` -> Known gaps). A Librarian Run builds its merges from Skills it read earlier in the Run, so its `edit`, `patch`, `write_file`, `remove_file` or `delete` of an existing Skill fails `skill_changed` (`SKILL_MANAGE_CHANGED_DURING_PASS_REFUSAL`) when that Skill's history holds a revision of another Run, or of a person, recorded after the Librarian Run was created (`register_skill_manage_tool(run_started_at=...)`, wired to `Runtime.run_started_at`, i.e. the Run manager's `Run.created_at`, read on the Event Loop for Librarian Runs only; the check reads the Skill's newest 100 revisions). The refusal comes once per outside change: the handler remembers, per (Run, Skill), the newest outside revision it reported (bounded to 1024 pairs), so the next call goes through whether or not the Agent read the Skill again, and only a further outside change refuses again. `create` and other Run kinds are not checked; a background review defers its Skill dimension while a pass runs instead (`automation.md` -> Reflection). `absorbed_into` on another action, naming the Skill itself or naming no own Skill fails `invalid_arguments`. A delete answers `SKILL_MANAGE_DELETED`, with `absorbed_into` `SKILL_MANAGE_ABSORBED`.
- Success data is `{content}`: one line (for example `Patched SKILL.md of Skill 'x' at line 12.`), then `Warning:` and `Note:` lines. Shared and own targets read identically.
- Detail blocks (`tools.md` -> Display metadata): one diff per changed package file from the authoring result's changes, an info notice `Nothing changed; the file already had this text.` when the write left every file as it was, and the Skill's validation warnings as warning notices. `Note:` lines describe the call's arguments and stay Model-only; paths are package-relative, so shared targets stay indistinguishable.
- Tests: `tests/core/tools/test_skill_manage.py`; probe cases in `scripts/tool_lab/cases/knowledge.json`.

Mutating an existing package requires its `SKILL.md`, including delete and support-file operations. Package directories, the entry document and support-file path components reject symlink/junction redirects before resolution (other reparse points, such as OneDrive cloud-file placeholders, are ordinary files), so aliases cannot bypass document validation or target a different named package. Installation reuses this authoring boundary (`tests/core/skills/test_authoring.py`).

The registered `skill_manage` handler runs scope resolution, authoring and cache invalidation together in the bounded Tool worker pool. Runtime supplies `AgentStore.lifecycle_guard` around that sequence so shared-owner rename/archive cannot detach an already-resolved target. Cancellation after worker admission waits for the write and invalidation to finish (`test_skill_manage.py`, `test_runtime_skill_lifecycle.py`).

**Write-scope boundary (v1 is data-dir only - vBot never writes the repo as runtime state):**

- **Agent Tool `skill_manage`** (always registered, not gated on owning a Skill): one open flat object requiring `action` + `name` (fields and repair above); actions are create/edit/patch/write_file/remove_file/delete. Agent authoring is deliberately **private-only**: every mutation targets the home of the calling Identity Agent (in a Librarian Session, of the Agent it maintains: `tools/skill.md` -> Skill subject), invalidates its registry, reports the change through the handler's `on_changed` after that invalidation (Runtime wires `SkillRuntime.notify_changed`), and emits one content-free control-plane log event. The single exception is **shared-target resolution**: a name not the caller's own but resolving to a shared instance lets update actions (edit/patch/write_file/remove_file) operate on the owner's package and invalidate all agent-aware registries, while create/delete refuse non-own targets. The Result reads identically for both, and the Tool description intentionally never mentions sharing - receivers discover editability through use, not provenance wording. Global authoring uses RPC/WebUI/CLI rather than `skill_manage`; Project/repo and bundled Skills are never Agent Tool targets. `skill_manage` carries the declarative `identity_agent` constraint: withheld from Config/Project Agents at visibility and dispatch, excluded from the Project Tool Whitelist by Projects-owned metadata.
- **`/learn`**: user-triggered internal Run seeded with an authoring brief, using `skill_manage` into the current agent's home (see `chat.md`). The brief checks current catalog and complete target files, prefers a fitting private Skill update, and accepts an unchanged outcome when the source adds no supported reusable learning. It does not copy a correction to a read-only Skill into a private shadow.
- Both Skill Tools repair padded names, matching enclosing package-path quotes, and backslash separators before validation; `skill` can read arbitrary UTF-8 package files while `skill_manage` retains its narrower authoring paths. `skill` loads a name that differs from exactly one allowed Skill only in form (`tools/skill.md`); `skill_manage` never writes to such a name and only suggests it. Similar names are suggestions in errors, never targets. Only optional `name`/`file_path` empties mean omission, after duplicate-value conflicts are checked; content empties remain meaningful. Repaired targets retain the same package containment and write-scope checks.

- **RPC + user Accessors**: `skill.read/create/update/delete/write_file/remove_file` scoped `global` or `agent:<id>`, writer `HUMAN_WRITER`; Project/repo scopes reject. `skill.delete` archives and returns the `archive_id`; write responses carry the recorded `revision`. The same scopes serve `skill.history`, `skill.revert`, `skill.archived`, `skill.restore`, `skill.purge` and `skill.set_pinned` (`skills/history.md` -> Surfaces). Global writes reload skills, Agent writes invalidate that agent's registry. The Agent-scope id validates traversal-safe and must name an **existing Identity Agent** - unknown ids reject with `agent_not_found` rather than creating unowned homes. `skill.set_disabled` and `skill.share` report an unknown or unowned Skill as `skill_not_found` and an unknown owner/receiver as `agent_not_found`.
- **Package installation**: `skill.install` RPC, `vbot skill install`, and the WebUI Skill manager use the same global/private roots. Browser archives enter through bounded multipart HTTP and the same authoring owner. Agents discover this workflow through bundled `vbot-cli/references/skills.md`; CLI `--scope own` resolves the calling Identity Agent without falling back to global. Private imports use the same owner-and-receiver invalidation as other authoring writes. Installation preserves policy and allowlists; the live registry updates while the Prompt-Epoch Catalog stays pinned. Source selection, limits and replacement recovery are in `skills/installation.md`.
- **Project skills** stay repo-owned (authored with ordinary `write`/`apply_patch`, validated at scan); **bundled** `resources/skills/` is read-only - the write core refuses it.

The bundled `vbot-cli` Skill owns Extension authoring guidance in `references/extensions.md` (pages and owned Sessions in `references/extension-pages.md`; each reference must stay within the `skill` Tool's single read), bundled operation guidance in `references/extension-usage.md`, and copyable templates in `assets/extensions/`. Assets are recursively readable Skill resources, not Extension scan roots; the nested `workflow` Skill becomes separately discoverable only after its containing Extension is installed and loaded. Coverage: `tests/resources/skills/test_bundled_skills.py` and `tests/core/extensions/test_examples.py`.

## Data Model

- `SkillMetadata`: normalized `name`/`description`, internal `path`, optional license/compatibility/metadata/`allowed_tools`, parsed vBot requirements. `SkillRegistry.always_allowed` is scoped metadata: Identity registries contain private names minus the Agent's `excluded_skills`, plus the active Project's effective names. `SkillRegistry.allowlist_exclusions` holds the Identity Agent's `excluded_skills`; `filter_allowed`, `is_allowed` and the dependency checks of `availability_for` subtract it from the allowlist grant before adding `always_allowed` back (`test_skills.py`).
- Three availability states: `invalid` (malformed/non-loadable), `unavailable` (loadable, unmet required requirements), `available`; optional requirements never gate availability.
- Frontmatter prefers complete YAML (PyYAML) and degrades in staged fallbacks - BOM strip, re-quoting colon-space scalars, then top-level `key: value` extraction; without usable frontmatter the entire body is the Skill body. Missing name fills from the directory, missing description from the first body text line. Every fallback is a loadable warning, never a gate; name mismatches, overlong names, and trigger-unsafe characters also warn only - such a Skill loads but cannot be triggered via `/`/`$` (only explicit `skill` Tool argument). Two size warnings are likewise non-blocking and never cut anything (`skill_validator.py`, `test_skills.py::test_imperfect_metadata_loads_with_fallbacks_and_warnings`): a description over `MAX_SKILL_DESCRIPTION_LENGTH` (1024 characters, the Agent Skills specification limit; every catalog carries it in full), and stripped instructions over one page of `core/utils/text_pages.py` (50 KB or 2000 lines), which the `skill` Tool then returns in pages (`tools/skill.md`). The warnings reach the manager diagnostics and the `skill_manage` Result.
- vBot requirements live under `metadata.vbot.requirements` (never `compatibility`); details in the Requirements section below.
- Activation returns the SKILL.md body alone as `content`, plus `resource_files {guidance, files}` with `scripts/` paths absolute (direct `bash` execution) and other package files relative (read UTF-8 files via `skill(name, file_path)`), optional `environment_access` Bash guidance, and one internal `<skill_content name="...">` context used for deterministic triggers, epoch dedup, and Compaction recognition - the wrapper never appears in Tool `content`. Resource discovery excludes generated/VCS directories, links and internal install receipts. A `{baseDir}` marker substitutes the absolute Skill directory. A `file_path` call (including relative `scripts/...` source reads) returns `{name, status: "file_loaded", file_path, content}` with no absolute path and skips activation dedup. User-triggered activation persists an internal note; Tool activation uses its Result as durable carrier. Identical activation context deduplicates within one Compaction epoch; a changed package may re-activate before the boundary, and past a committed checkpoint a fresh carrier loads.

## Prompt Catalog

Prompt-facing metadata is origin headings with one `- name: description` line per Skill inside an `<available_skills>` boundary, rendered by `core/skills/skills.py::format_skill_catalog_entries` - the same text as the `skill` Tool's no-argument list and the shape of the new-Skill System Reminder:

```text
<available_skills>
Bundled skills:
- weather: Get weather forecasts.
</available_skills>
```

- Skills group by **origin** (order: Bundled / Your global skills / Skills from project '<name>' / Your own skills; origin tags land at load from each scan root, project tags carry the display name). Originless registries render one "Skills" group.
- Each line holds only name and description (a multi-line description folds onto its line) - the catalog stays **path-free** as a prompt-economy presentation preference, not a hard routing rule. The explicit `project` Tool returns the loaded Project's Skills in its ordinary Result; afterwards the `skill` Tool resolves against that Project-aware registry while the pinned epoch catalog stays unchanged (see `tools/project.md`).
- Values are not escaped. The bundled prompt asks the Model to load any matching or partly relevant Skill and explains that `/skill-name` and `$skill-name` are followed from the injected `<skill_content>` without reloading; how to run scripts and read other package files is taught by each loaded Skill's `resource_files.guidance`, not by the block.
- The catalog includes only available+allowed Skills filtered against the same working-Project/private registry as live activation; `chat.commands` and `prompt.preview` resolve a bare Identity Agent's `root_project_id` (qualified Config Agents get no private layer), failing closed while preserving the saved reference. `chat.commands`, requested whenever a Chat changes Agent address or the command catalog changes, resolves the Agent through `resolve_agent_async` and filters Skills on the catalog pool, never on the Event Loop (availability probes `PATH` for binary requirements). Its optional `session_id` (only with `agent_id`) resolves the Agent as that Session runs it, so a Librarian Session suggests the Skills of the Agent it maintains (`test_catalog_methods.py`).

## Interfaces

Scoped Project/Agent scans publish only if no invalidation or credential refresh occurred during I/O; cache access and publication are synchronized without holding the lock during scans (`test_runtime_skill_cache_races.py`). Global and scoped scans share the same global root ordering and origin rules.

Manager availability evaluates each source package's own requirements, including
same-name packages shadowed in the merged dependency pool. Cross-source Skill
dependencies use that merged pool; required and optional missing diagnostics stay
specific to the displayed package (`test_runtime_shared_skills.py`).

- `core.skills` exports the registry/policy/authoring surfaces (`SkillRegistry`, `SkillPolicyService`, `SkillAuthoringService`), the origin vocabulary, scan helpers, and dataclasses - signatures live in code. `core/skills/runtime.py::SkillRuntime` owns global scan-layer construction, Project/Agent/shared resolution, manager inventory, and scoped registry caches; `Runtime` exposes stable delegates and performs only Tool/Prompt composition after a registry replacement.
- Non-obvious `SkillRegistry.load` behaviors: a scan root whose own path contains `SKILL.md` is a **package root** contributing exactly that package (how shared layers insert without scanning an owner's home); missing roots contribute nothing and one root's enumeration failure degrades to diagnostics without blocking startup; `environment` snapshots requirement-check inputs (defaults `os.environ`); `excluded_names` moves disabled names into a separate bucket readable via `excluded_skills()` - runtime passes them, editor loads omit them; `allowlist_exclusions` (Agent Skill Exclusions) instead keeps packages loaded and only narrows the allowlist grant.
- `Runtime.refresh_skills_for(project_id, identity_agent_id=None)` is the explicit Compaction refresh seam: full pool reload plus cache invalidation returning the fresh scope; normal consumers use cached `skills_for(...)` and must not imitate rescans.
- Manager surface: `runtime.skill_policy` persists the policy file; `runtime.skill_inventory()` makes one exclusion-free pass over every source annotating origin/owner/Project/share-disable state/receivers/availability/warnings plus stale entries, and projects each Identity Agent's effective Skill grants (`agents`) and each Project's Skill pool (`projects`, classified by `runtime.project_skill_pool(project_id)`, which also feeds the Project scan preview); exact shapes in `skills/manager.md`. `agent_owns_private_skill(agent_id, name)`. RPC `skill.set_disabled` validates existence then reloads; `skill.share` requires an existing owning agent, at least one existing receiver id, none equal to the owner. Both publish `resource_changed(kind="skills")` - disable via `reload_skills_async()`, share via `invalidate_agent_skills(None)` (shared Skills never enter the global pool). Every other change that alters the inventory publishes the same kind (publishers: `server/events-and-reconnect.md` -> `resource_changed`); Agent-side `skill_manage` writes reach the server through `SkillRuntime.add_changed_callback`/`notify_changed` (Runtime `add_skill_changed_callback`), bridged in `server/_app_lifecycle.py`. Inventory ids identify exact source packages independently of names; `runtime.inspect_skill(id)` rescans known sources and reads that package's original text without activation or arbitrary client filesystem addressing. Inventory projects the human-editable scope only for loadable packages in the real global/private write roots; external and bundled sources stay read-only even when tagged global. Editable entries carry their Skill History record, the inventory lists every writable home's Skill Archive, and the `skill.inventory` RPC adds Skill use from Statistics (`skills/manager.md`). Inventory and inspection RPC reads use a bounded worker pool so large collections do not block streaming. Tests: `tests/core/runtime/test_runtime_shared_skills.py` and `tests/server/rpc/test_skill_methods.py`.

## Conventions

- Authoring guidance distinguishes supported reusable methods from ordinary work and general preferences, replaces obsolete instructions in the affected passage, and requires current complete-file reads for edits. Descriptions favor clear, concise triggers without a 60-character authoring rule; the catalog renders the full metadata description (over 1024 characters it only warns, see Data Model). These are Model instructions, while parsing and write scope remain enforced by the existing loader and authoring service. Reflection decision evaluation is documented in `automation.md`.
- `allowed_skills=['*']` or missing/`None` exposes all loaded skills - real behavior, not test convenience; `[]` exposes none. Explicit lists match exact names; unknown entries ignore (Skills are not hard execution gates).
- Skill dependency requirements must not bypass allowlists: a disallowed dependency, including one withheld by Agent Skill Exclusions, makes the dependent unavailable.
- Duplicate names resolve first-found-wins with rejected-duplicate diagnostics. The global scan order (`core/skills/runtime.py::_scan_roots`, user decision) is `<data_dir>/skills` > `skill_directories` (listed order) > loaded Extension `skills/` folders (Extension load order) > bundled `resources/skills/`: every global source outranks bundled, matching own > project > shared > global > bundled (`test_global_skill_sources_win_over_bundled_in_documented_order`). In merged registries the project dir scans first, so a project Skill wins over a global or bundled same-named one (the editor drops the shadowed bundled opt-in).
- `skill` and `skill_manage` are ordinary configurable Tools under Tool Access Policy, neither gated on already owning a Skill; `skill` seeds default-on in the Project Tool Whitelist.
- Full instructions have a single provider-visible carrier per activation (Tool Result or trigger note). `register_skill_activation` deduplicates identical content only until the next committed checkpoint; that checkpoint removes carriers from Context, revokes Skill-derived env grants, retains a names-only reminder for the finished epoch, and post-boundary reloads create fresh carriers (see `chat/request-building.md`).
- `/skill-name` and `$skill-name` preserve the original user message; unknown/non-loadable/unavailable triggers become internal reminders, not activations.
- `$` autocomplete lists only currently available Skills (never Commands); `/` autocomplete may list both because backend dispatch handles Commands before the Skill-trigger path - a same-named Skill stays reachable via `$name`.

## vBot Requirements Metadata

```yaml
metadata:
  vbot:
    requirements:
      all:
        - binary: git
        - any:
            - binary: gcc
            - binary: clang
        - any:
            - env: OPENAI_API_KEY
            - env: ANTHROPIC_API_KEY
      optional:
        - binary: jq
```

- `all` requires every child; `any` at least one; `optional` failures report without changing `available`.
- `env` checks a non-empty value in the snapshot environment (process env wins over `.env` fallback). Names match case-insensitively on Windows (`os.name == "nt"`, where `os.environ` reports upper-cased names) and case-sensitively on POSIX (`core/skills/skills.py::_environment_key`, `test_skills.py`). Every declared `env` leaf doubles as an activation-time Bash grant surfaced via `environment_access` (Tool activations as sibling field, internal contexts wrapped before instructions), listing names and per-call `bash.env_keys` - permanent Agent grants are the separate `tools.bash.allowed_env` source (see `tools/bash.md`).
- `binary` resolves via `shutil.which` against the snapshot PATH - lookup, never shell execution. `skill` checks dependency loadable+available+allowed, walking chains with a cycle guard (circular -> `unavailable` with a cycle reason). Malformed requirements make the Skill invalid/non-loadable.

- `pyyaml` (core dependency) parses SKILL.md frontmatter. Browser automation uses the bundled `playwright-cli` Skill through `bash`, with official CLI instructions and on-demand references. CLI/browser setup remains optional and missing binaries do not hide its setup guidance. ## Constraints & Gotchas

- Requirement checks use a snapshot rather than reading `os.environ` at activation. Credential reload updates that snapshot in the global and every cached Project/Agent registry immediately, preserving held Run references and pinned catalogs; explicit Skill reload also refreshes environment and binary availability.
- Bundled scripts and the Playwright CLI execute on the machine running the server through that Run's `bash`. Bundled Python scripts (`resources/skills/*/scripts/*.py`) run on whatever `python` the host's `PATH` provides, not on vBot's interpreter, and support Python 3.9 and later (ruff target `py39`; PROJECT.md -> Development -> Python version). Playwright outputs link to server-side files; the Agent reads or presents them explicitly. Its headed browser/dashboard also belongs to that host.
- Path economy (catalog and `skill({})` results path-free; provenance internal) is presentation preference, not routing: activations expose absolute script paths and relative readable paths under `resource_files`, and `project` Tool Results may carry structured path context - but `skill(name, file_path)` accepts only relative package paths and returns only those.
- Retain non-loadable directories as diagnostics (I/O failures, malformed requirements, duplicate names) so UI can explain them; plain YAML errors and missing ordinary metadata use loadable fallbacks instead. Unknown requirement keys, including YAML non-string keys, invalidate only their package rather than aborting the registry scan.
- Metadata diagnostics log at `DEBUG` (`vbot.skills`) **once per process**, keyed by (path, warning) in a bounded `LoggedConditions` memory (a pair it forgot logs again), because registries reload on every project run/reload - only the log deduplicates; caller-facing diagnostics always carry every warning. For the same reason an unreadable or invalid policy file warns once per file version (modification time and size) and logs INFO once it is usable again (`SkillPolicyService`), and a stale shared entry warns once per owner or owner/Skill until it resolves (`SkillRuntime`), not once per receiver build.
- No in-app legacy compatibility for older `allowed_skills` formats - explicit converter scripts if ever needed.
- A package the Skill History does not know yet (hand-dropped, copied, or written before the history existed) gets a `baseline` whose origin is `agent` only when its `SKILL.md` declares `metadata.vbot.author: agent`, else `human`; Librarian aging therefore never retires a hand-made Skill (`automation/librarian.md`), while background writers can change it like any unpinned own Skill. Origin and pin live only in the history file beside the home, so moving a package between homes by hand starts a new lineage there.
