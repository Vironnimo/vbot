# Extensions

In-process Python extension system loaded by the runtime. Owns discovery, two-phase registration (declare → apply), per-extension identity/config/lifecycle, and per-event hook dispatch; `core/chat/` decides only when each event fires and what its payload means.

## Overview

`core/extensions/` lets power users extend vBot without editing application source. An **extension** is the single unit of discovery, identity, config, and enable/disable; **hooks, tools, and recall backends** are the capability surfaces it uses (see Capability Surfaces). Runtime loads Python modules from `<data_dir>/extensions/` plus optional extra scan roots from `settings.json` `extension_directories`, and always from the fixed bundled root `<resources>/extensions/` scanned **last** (hardcoded — deliberately not part of the `extension_directories` setting, so it cannot be accidentally removed), passing in the disabled set and per-extension config read from the `settings.json` `extensions` section. `examples/extensions/` holds runnable, heavily-commented reference extensions (a `tool_call`-deny hook and a `register_tool` tool); `docs/extensions.md` is the user-facing author guide.

Loading is **two-phase**:

1. **Declare** — each extension's `register(api)` is called with an `ExtensionAPI`. Calls only *collect declarations* (hook handlers, startup/shutdown callbacks) into that extension's `ExtensionRecord`. Nothing goes live. Async `register()` coroutines are awaited to completion deterministically before phase 2.
2. **Apply** — after **all** extensions have registered, the registry installs every loaded extension's hook declarations into the dispatch table in load order.

The module then **dispatches every hook event** through typed per-event methods on `ExtensionRegistry`. `core/chat/` constructs the `HookContext`, chooses the fire-points, supplies each event's payload, and applies the returned results — it never iterates handlers itself. Extensions run in-process on the normal asyncio event loop when one exists. Trust boundary is the kernel's: extension modules run arbitrary in-process Python.

## Bundled extensions

Home Assistant is the **first shipped bundled extension** (`resources/extensions/homeassistant/`) — it exercises the whole surface: external I/O, a secret + a live URL via the settings schema, per-tool readiness. Its behavior and contracts have their own child map: `.vorch/domain-maps/extensions/homeassistant.md`.

## Cross-root name shadowing

Identity is the filesystem name, and a name resolves across roots **first-wins** in scan order (data dir → extras → bundled). The first-discovered occurrence of a name claims that identity and loads normally; every later same-name occurrence in a subsequent root becomes an `overridden` record — **never imported**, no manifest read, no `register()`, no hooks/tools installed — that stays visible in `records()` / `extensions.list` with `overridden_by` pointing at the winner's `entry_path`. This replaces older behavior where two same-name copies both loaded and collided capability-by-capability (double-firing hooks included). A `disabled` name still **claims** its identity: a disabled data-dir copy shadows a bundled same-name copy (recorded `disabled` + `overridden`, neither imported), so disabling a name can never silently activate a different copy of it. Customizing a bundled extension is therefore a deliberate copy into the data dir, which then shadows the shipped version. (Within a single root, two same-name entries are impossible on a filesystem.)

## Data Model

- `API_VERSION = 1` — exported from `core.extensions`. The extension contract version a manifest can pin against.
- `HookContext` (frozen dataclass) — passed as the first positional argument to every handler. Constructed in `core/chat/` at each fire-point.
  - `session_id: str`, `agent_id: str`, `run_id: str`
  - `add_note: Callable[[str], None]` — appends a kernel-internal `role: "note"` entry to the active session. Chat wires it to `session.add_note`; extensions call `ctx.add_note("…")` to inject a `<system-reminder>` for the model (see the System-Reminder rules in PROJECT.md). Defaults to a no-op when built without a session.
- Decision types for `tool_call` (frozen dataclasses, importable from `core.extensions`): `Deny(reason: str)`, `Modify(input: dict)`, `Replace(result: dict)`. A handler returning `None` continues unchanged.
- `ToolCallDecision` — structured outcome `dispatch_tool_call` hands back to chat: `effective_input` (the input after any `Modify`), `deny_reason`/`deny_extension` (set when denied), `replacement` (a validated envelope when replaced). Exactly one disposition holds: proceed, denied, or replaced.
- `ExtensionManifest` (frozen dataclass, optional) — parsed from `extension.json`: `version: str | None`, `description: str | None`, `api_version: int | None`, `display_name: str | None` (from the manifest `name` field, display-only). Identity stays the filesystem name.
- `ExtensionRecord` (one per discovered extension) — `name` (directory/file name, the identity), `root_path`, `entry_path`, `status` (`loaded` / `failed` / `disabled` / `overridden`), `error` (detail when `failed`, else `None`), `overridden_by` (the winning record's `entry_path` string when `status="overridden"`, else `None`), `manifest` (or `None`), `declarations`, `capability_errors`. `declarations` are only meaningful for `loaded` records. `capability_errors` is a list of **non-fatal** per-capability diagnostics (e.g. one tool skipped on a name collision); the extension still `loaded` and is **not** in `diagnostics()` — only `status="failed"` records are. An `overridden` record is a later same-name copy an earlier root already claimed: never imported, no manifest read, no `register()` (see Cross-root name shadowing).
- `ExtensionDeclarations` — what `ExtensionAPI` collects per extension: `hooks` (event → handler list), `startup`, `shutdown`, `tools` (`ToolDeclaration` list), `recall_backends` (`RecallBackendDeclaration` list), `prompt_blocks` (`PromptBlockDeclaration` list), `settings_schema` (`list[SettingsFieldDeclaration] | None`). Internal; the registry applies/fires them. `ToolDeclaration` mirrors `ToolRegistry.register` args (`display` and the optional `ready` predicate forwarded untyped so the module stays decoupled from `core/tools/`); `RecallBackendDeclaration` is `(name, factory)`; `PromptBlockDeclaration` is `(slug, default_text=None, render=None)` with exactly one of `default_text`/`render` set (see Capability Surfaces).
- `ExtensionRegistry`
  - `_handlers: dict[str, list[tuple[str, Callable]]]` — event name → ordered `(extension_name, handler)` pairs in load order. **Private to the registry**: only `install_handler` (the apply primitive) writes it and the registry's own `dispatch_*`/`_invoke` methods read it. No code outside `core/extensions/` touches it.
  - `_records: list[ExtensionRecord]` — every discovered extension in load order.
  - Event names are a fixed, closed set the registry dispatches and `core/chat/` fires: `run_start`, `context`, `tool_call`, `tool_result`, `run_end`. Registering any other name is silently inert — no `dispatch_*` method reads it. (There is **no** prompt-append hook: an extension that wants System Prompt content declares a prompt block instead — see Capability Surfaces.)

## Interfaces

- `ExtensionAPI(extension_name, declarations, *, config, logger, config_provider=None, credential_resolver=None)` — registration facade passed into `register(api)`. Every call only collects a declaration; nothing is live until the apply phase. `config_provider`/`credential_resolver` (both already bound to this extension) back the **live** per-call reads; both default to `None` for standalone construction (tests).
  - `api.on(event, handler) -> None` — declare a hook handler. Called as `handler(ctx, **payload)`.
  - `api.register_tool(name, description, parameters, handler, *, internal=False, display=None, ready=None) -> None` — declare an agent tool, mirroring `ToolRegistry.register`. Applied into the runtime `ToolRegistry` (see Capability Surfaces). `ready` is an optional zero-arg readiness predicate forwarded verbatim into `ToolRegistry.register` (`_apply_one_tool` passes `ready=declaration.ready`): a not-ready tool stays registered but is hidden from the model-facing surfaces until it is ready (e.g. its declared secret is set) — see `.vorch/domain-maps/tools.md` → Readiness.
  - `api.register_recall_backend(name, factory) -> None` — declare a session-recall backend; `factory` is `RecallBackendContext -> RecallBackend`. Applied onto the recall registry.
  - `api.register_prompt_block(slug, *, default_text=None, render=None) -> None` — declare a System Prompt block (see Capability Surfaces). Exactly one of `default_text` (static, editable) / `render` (dynamic, build-time) must be set; passing both or neither raises `ValueError` at declaration (so the mistake surfaces in `register()`, not deep in assembly).
  - `api.register_settings(fields) -> None` — declare the extension's settings **schema** (see Settings Schema). Parses `fields` through `parse_settings_fields`; an invalid field raises `ValueError` naming it (extension → `failed`), and a second call raises `ValueError` ("settings schema already declared").
  - `api.on_startup(handler) -> None` / `api.on_shutdown(handler) -> None` — declare a no-arg lifecycle handler (sync or async).
  - `api.config` — the register-time config **snapshot** from `settings.extensions.config.<name>` (empty `dict` default); for structural decisions inside `register()`.
  - `api.get_config() -> dict` — the config read **live** per call (fresh dict); reflects a `settings.update` config change without a restart. Falls back to a copy of the snapshot when no `config_provider` is wired.
  - `api.resolve_credential(key) -> str` — resolve a credential **live** per call (process env, then the data-dir `.env` snapshot); returns `""` when no `credential_resolver` is wired.
  - `api.logger` — a `vbot.extensions.<name>` logger via the normal `LogManager` pipeline.
- `ExtensionRegistry.load(extensions_dir, extra_dirs=None, *, disabled=None, config=None, bundled_dir=None, config_provider=None, credential_resolver=None) -> ExtensionRegistry` — scans immediate children of each root in order — data-dir `extensions_dir` first, then user `extra_dirs`, then the fixed `bundled_dir` **last** (a `None` `bundled_dir` is skipped) — runs the two-phase load, and returns the populated registry. Cross-root **first-wins name shadowing** applies (see Cross-root name shadowing). Extensions named in `disabled` are recorded `disabled` and **never imported**. `config` maps extension name → its `api.config` snapshot. `config_provider` (`name -> live config dict`) and `credential_resolver` (`key -> value`) back each extension's live reads; both are bound to the extension name per-extension when its `ExtensionAPI` is built (a `None` provider stays `None` on the API). The runtime passes `config_provider=self._live_extension_config` (reads `storage.load_extensions_settings()` live) and `credential_resolver=self.resolve_environment_credential`.
- `ExtensionRegistry.install_handler(extension_name, event, handler) -> None` — the apply phase's primitive: appends `(extension_name, handler)` to `_handlers[event]`. The single writer of `_handlers`; tests build a dispatch table through this seam without the filesystem load path.
- `ExtensionRegistry.apply_tools(tool_registry) -> None` / `apply_recall_backends(recall_registry) -> None` — the capability apply phases the runtime calls at the right bootstrap points (see Capability Surfaces). Both diagnose collisions/errors onto the record's `capability_errors` and fail open.
- `ExtensionRegistry.prompt_block_declarations() -> list[BlockDefinition]` — turns the loaded extensions' block declarations into `core.prompts.BlockDefinition`s (lazy `core.prompts` import so the module stays decoupled). Each becomes id `extension:<slug>`, owner `extension:<extension-name>`; slug collisions resolve first-wins with a diagnostic on the loser (mirrors `_apply_one_tool`); a construction error (bad slug → bad id) is diagnosed and that one block dropped. The runtime calls this after extensions load and on every reload and hands the list to the prompt manager.
- `ExtensionRegistry.loaded_extension_names() -> set[str]` — the set of `loaded` extension names, gate 2's `extension:<name>` membership input. Rebuilt and re-handed to the prompt manager on every (re)load, so a block whose extension failed/disabled/unloaded never renders.
- `ExtensionRegistry.records() -> list[ExtensionRecord]` — every discovered record in load order.
- `ExtensionRegistry.diagnostics() -> list[ExtensionRecord]` — only the `failed` records (mirrors the skills `invalid_diagnostics()` idea). Runtime logs a startup warning when non-empty.
- `ExtensionRegistry.fire_startup() / fire_shutdown()` (async) — fire every loaded extension's startup/shutdown handlers in load order; fail-open per handler (log `error`, continue). `fire_shutdown_blocking()` runs `fire_shutdown()` to completion from synchronous shutdown paths (`Runtime.stop()`); the live reload path awaits `fire_shutdown()`/`fire_startup()` directly on the serving loop instead.
- `ExtensionRegistry.remove_applied_tools(tool_registry)` — teardown counterpart to `apply_tools`: for every `loaded` record, unregister its applied tools by the same handler-identity match as `deactivate` (a collision-skipped name owned by a built-in / another extension is never yanked). It does **not** change record statuses — the whole registry object is discarded right after the reload swap. Used only by `Runtime.reload_extensions`.
- `purge_extension_modules()` (module-level, exported from `core.extensions`) — drop `vbot_ext` and every `vbot_ext.*` key from `sys.modules`. `Runtime.reload_extensions` calls it between tearing the old layer down and the fresh `load`, so an edited **submodule** of a package extension is re-imported (a fresh `load` replaces only the entry-point module; a relative import would otherwise hit the stale cached submodule). Safe for a still-referenced old registry — its handlers hold direct function references, not `sys.modules` lookups.
- `ExtensionRegistry.deactivate(name, tool_registry=None)` (async) — the **live-disable gate**: turn a currently-`loaded` extension dormant *without* a restart. It removes the extension's hook handlers from `_handlers` (all events stop firing), unregisters its applied tools from `tool_registry` (only names whose live registry handler **is** this extension's declaration handler — a collision-skipped name owned by a built-in / another extension is left with its real owner), fires its shutdown handlers (fail-open, reusing `_invoke_lifecycle`), then flips the record to `status="disabled"` and **clears its declarations** — so it afterwards reports exactly like a boot-disabled extension (no schema, empty capabilities, `ready_state: "ready"`, and dropped from `loaded_extension_names()` / `prompt_block_declarations()` / recall re-apply on the next rebuild). The extension's **code stays imported** (dormant). Returns `True` only when a live `loaded` record was deactivated; an unknown / already-`disabled` / `failed` / `overridden` name is a clean no-op returning `False` (no crash, no double shutdown). Persisted permissions/config are untouched. The runtime awaits it via `Runtime.apply_extension_disabled_change` (see below); a full **reload** (`Runtime.reload_extensions`) is the other way a boot-disabled extension is *enabled* live.
- `ToolResultValidator = Callable[[str, dict], dict | None]` — injected by chat into the tool hooks so tool-result-envelope schema knowledge stays in the chat domain. Given `(extension_name, candidate)` it returns the validated envelope or `None` to reject.
- **Per-event dispatch methods** — one typed `dispatch_*` per event, each owning iteration in load order, sync/async handler support (awaits awaitables), per-handler exception isolation (log `warning`, continue via the `_HANDLER_FAILED` sentinel), and the event's composition rule (the composition/return contract is the **Hook events** table below — not repeated per method here). Signatures: `dispatch_run_start(ctx, *, session_id, agent_id) -> None`, `dispatch_run_end(ctx, *, session_id, agent_id, outcome) -> None`, `dispatch_context(ctx, *, messages) -> list`, `dispatch_tool_call(ctx, *, tool_name, tool_call_id, input, validator) -> ToolCallDecision`, `dispatch_tool_result(ctx, *, tool_name, tool_call_id, input, result, validator) -> dict`. Specifics beyond the table: `dispatch_context` returns the final message list (chat passes in a shallow per-message copy and uses the result as the request messages); `dispatch_tool_call` short-circuits on the first `Deny`/valid `Replace` and no longer honors plain-dict returns; `dispatch_tool_result` re-validates each replacement envelope through `validator` and drops invalid/`None`/non-dict (no shallow-merge patching).
- Discovery accepts three entry-point shapes per immediate child:
  - single-file module: `<root>/<name>.py` (`root_path == entry_path`; no manifest)
  - package module: `<root>/<name>/__init__.py`
  - directory fallback: `<root>/<name>/extension.py`
  - package entry points load under the synthetic `vbot_ext` namespace so relative imports inside extension packages work. The optional `extension.json` manifest lives in the directory for the package / directory-fallback shapes.

## Hook events (chat contract)

Each handler receives `ctx: HookContext` first, then the event kwargs below. Handlers may be sync or async; async results are awaited. The composition rule is owned by the matching `dispatch_*` method; the fire-point and payload meaning below are owned by `core/chat/`.

| Event | Composition | Payload (after `ctx`) | Allowed returns |
|---|---|---|---|
| `run_start` | observer | `session_id, agent_id` | ignored |
| `context` | pipeline | `messages` | `list` (replaces running messages) or `None` |
| `tool_call` | decision pipeline | `tool_name, tool_call_id, input` | `None` / `Modify(input)` / `Deny(reason)` / `Replace(result)` |
| `tool_result` | replace pipeline | `tool_name, tool_call_id, input, result` | full replacement envelope `dict` or `None` |
| `run_end` | observer | `session_id, agent_id, outcome` | ignored |

There is **no** prompt-append event in this set. The old accumulator hook that appended a string onto `messages[0]` is gone; an extension that wants standing System Prompt content declares a **prompt block** (Capability Surfaces), which is positioned, gated, and overridable like any other block. Per-request, message-dependent content (the kind that would have inspected `messages`/`run`) belongs in the `context` hook instead.

- `run_start` — fired before the user turn is appended.
- `context` — fired before each provider request on a shallow per-message copy. Each handler in turn may return a list that becomes the running messages the next handler sees; the final running list is the request.
- `tool_call` — fired before a tool runs. `Modify` rewrites `input` and the pipeline continues (later handlers and the tool itself see the modified input). `Deny` stops the pipeline and the tool is not executed; chat builds a `tool_call_denied` failure envelope naming the denying extension. `Replace` stops the pipeline and skips execution; its envelope must pass the chat `validator` or it is logged and treated as continue. The modified arguments are what the tool executes with, what `tool_result` hooks receive, and what the `tool_call_started` timeline event shows; the persisted assistant `tool_calls` (the model's request) are untouched.
- `tool_result` — fired after the result is produced (real run, `Deny` envelope, or `Replace` envelope). Each handler returns a full replacement envelope, re-validated through the chat `validator`; valid replaces the running envelope (the next handler sees it), invalid or non-dict or `None` leaves it unchanged.
- `run_end` — fired in a `finally`, so it always runs. `outcome` is `"success"`, `"error"`, or `"cancelled"`.

## Capability Surfaces (tools, recall backends, prompt blocks)

Hooks are not the only thing an extension declares. `register(api)` also collects tool, recall-backend, and prompt-block declarations; the runtime applies them into the **existing** domain registries (`ToolRegistry`, `RecallBackendRegistry`, the prompt manager's block list) — the extension API is a thin facade, not a new registry. Apply points are order-sensitive (tools late, recall early), so they live in `Runtime.start()`:

- **Tools** — `Runtime` calls `apply_tools(self._tools)` after the **last** built-in tool is registered (cron/bash/subagent/status), right before `SystemPromptManager` consumes the registry. Each declaration goes through the normal `ToolRegistry.register`, so an extension tool is a *normal* tool afterward: provider/prompt definitions, agent allowlists, and dispatch treat it like any other (no special-casing — see `.vorch/domain-maps/tools.md` and `.vorch/domain-maps/prompts.md`). Collision policy (load order must not silently decide behavior): a name already used by a **built-in** is skipped (built-in wins); between **two extensions** the first-loaded wins and **both** sides are diagnosed; a name already claimed by an earlier extension is skipped + diagnosed. Per-tool registration errors fail open. All skips/collisions land in the record's `capability_errors`.
- **Recall backends** — `Runtime._build_recall_backend_registry` applies `apply_recall_backends` onto a fresh `RecallBackendRegistry.with_builtins()` **before** `recall.backend` is resolved, and again on every `reload_recall_backend` (so extension backends survive a live switch). The registry's own rules hold: a duplicate name (built-ins register first) or a non lowercase-snake_case name raises `ValueError`, which is caught, diagnosed on the record, and the backend skipped. `Runtime.available_recall_backends()` returns the registry names (built-ins + extensions); the Settings Recall panel and `settings.update` validation read from it (see `.vorch/domain-maps/recall.md`).
- **Prompt blocks** — `api.register_prompt_block(slug, *, default_text=None, render=None)` declares a System Prompt block (the same contributor path tools use). The runtime merges the extension blocks (`prompt_block_declarations()`) with the tool blocks and re-hands the list (plus `loaded_extension_names()`) to the prompt manager on every extension/skill reload — **no live registry, no per-run reload**; the block list is rebuilt and re-handed, not queried per request. Each block is id `extension:<slug>`, owner `extension:<extension-name>`, **static** (`default_text` — editable through the override cascade) or **dynamic** (`render` — non-editable, build-time, a raising render drops only that block, fail-open). One extension may declare several blocks via distinct slugs. Collision policy mirrors tool names: a slug already claimed by an earlier-loaded extension is skipped + diagnosed (first-wins), and an id colliding with a core/tool block loses to it at assembly dedupe. The owning extension must be in `loaded_extension_names()` for gate 2 to render the block, so a disabled/failed/unloaded extension's block never appears. See `.vorch/domain-maps/prompts.md` for the block model and `.vorch/domain-maps/tools.md` for the parallel tool-block seam.

All three apply phases only touch `loaded` records and never abort bootstrap.

## Settings Schema

`core/extensions/settings_schema.py` owns the structured per-extension settings surface (a separate file because `extensions.py` is already over the 1000-line soft limit; re-exported from `core/extensions/__init__.py`). An extension declares a schema at register time via `api.register_settings(fields)`; the WebUI renders a real form from it and the RPC layer validates config on save. The module is deliberately **decoupled from `core/storage/`** — its key/env-key regexes are local constants (the env-key rule matches storage's `ENV_KEY_PATTERN` semantics without importing it).

- `SettingsFieldDeclaration` (frozen) — one field: `key` (`^[a-z][a-z0-9_]*$`, unique), `type` (`text`/`number`/`toggle`/`secret`), `label` (non-empty), `description?`, `default?` (forbidden for `secret`, else type-matched — `number` rejects `bool`), `required` (default `False`), `env_key` (**required** for `secret`, `^[A-Z][A-Z0-9_]*$`; forbidden otherwise).
- `parse_settings_fields(raw) -> list[SettingsFieldDeclaration]` — full validation per the field rules; any violation raises `ValueError` naming the field (so it surfaces in `register()` and fails the extension). `api.register_settings` calls this and rejects a second call.
- `validate_extension_config(fields, config) -> list[str]` — the on-save contract (empty list = valid): unknown keys rejected, a key naming a `secret` field rejected ("secrets live in .env, not config"), type mismatches rejected, a `required` non-secret field absent or empty-string rejected. Schema validation runs at the **RPC layer** (`settings.update`), where the loaded registry — and thus the schemas — is available; `core/settings/` is intentionally untouched (design decision #2). A schema-less extension keeps today's config pass-through.

**Everything applies live — no restart.** Non-secret config values are read **live** via `api.get_config()` (backed by `Runtime._live_extension_config` → `storage.load_extensions_settings()`), so a config-value save takes effect on the next call. **Disabling** an extension (adding it to the `disabled` set) is applied **live** through the surgical deactivation gate (`ExtensionRegistry.deactivate` → `Runtime.apply_extension_disabled_change`) — hooks off, tools gone, prompt blocks dropped, shutdown fired. **Enabling** (removing from the `disabled` set) triggers a full **extension reload** (`Runtime.reload_extensions`), so code disabled at boot is imported and takes effect immediately. Secrets are stored in the data-dir `.env` under the declared `env_key`, written via `extensions.set_secret` (see Visibility & Management) and read live via `api.resolve_credential(env_key)`.

## Visibility & Management

The extension records are surfaced through the normal accessor stack (CLI is an accessor — everything goes through server RPC):

- **`extensions.list` RPC** (`server/rpc/extensions_methods.py`) returns one entry per discovered record in load order: `name`, `status`, `disabled` (`status == "disabled"`), `root`/`entry` paths, `error`, `overridden_by` (winner's entry path when `overridden`, else `null`), `capability_errors`, manifest fields (`version`/`description`/`display_name`/`api_version`), the persisted `config` (merged from `settings.extensions.config`, read via `storage.load_extensions_settings()`), a `settings_schema` (`null` unless the record is `loaded` and declared one; else per-field `{key,type,label,description,required,default}` plus, for secrets, `env_key` and a **live** `set` bool from `resolve_environment_credential(env_key)` — never the secret value), a `capabilities` summary (`hooks` event→handler-count map, `tools` as a list of `{name, ready}` — each declared name looked up live in the runtime `ToolRegistry` and its readiness re-evaluated, an unregistered name reporting `ready: false` — `recall_backends`, `startup`/`shutdown` booleans), and a top-level **derived** `ready_state`: `"waiting"` when the record is `loaded`, declares at least one tool, and at least one declared tool is not ready; `"ready"` otherwise (including a no-tools record). `ready_state` is display-only (not stored, no third switch) and drives the WebUI Extensions panel's waiting hint and the CLI `list` waiting row. Empty list when no registry loaded.
- **`extensions.set_secret` RPC** (`{name, key, value}`) sets or clears a schema'd extension's secret in the data-dir `.env`. `key` is the **schema field key**, never the env key — the server looks up the declared `env_key`, so a client can never choose where a secret lands. Empty `value` clears (`remove_data_dir_credential`), non-empty sets (`set_data_dir_credential`); both then call `runtime.reload_provider_credentials()` so live resolution sees it. Response `{name, key, set}` (the new resolved state). Unknown extension / not loaded / no schema / unknown field / field-not-secret → `invalid_request`. The secret value is never logged.
- **`extensions.reload` RPC** (`server/rpc/extensions_methods.py`) drives `Runtime.reload_extensions` (the full restart-equivalent rebuild) and returns the **same payload shape as `extensions.list`** (the freshly rebuilt catalog). Rejects params like `extensions.list`; both share the `_extensions_payload(state)` helper.
- **CLI `vbot extensions list|reload|enable|disable <name>`** (`cli/extensions_management.py`): `list` formats the RPC payload; `reload` calls `extensions.reload` and prints a one-line status-count summary (`extensions reloaded: N loaded, N failed, N disabled, N overridden`) plus a per-failure line and a `vbot extensions list` pointer when anything failed; `enable`/`disable` reconstruct the full `extensions` section from `extensions.list` and write it via `settings.update`. Both toggles apply **live** (no restart hint); enable additionally re-lists and appends a `warning: '<name>' is <status>` line when the freshly rebuilt extension did not load. Unknown names get available-candidate + did-you-mean output; an already-enabled/disabled target is an idempotent no-op.
- **WebUI Settings → Extensions panel** (`SettingsExtensionsPanel.svelte`): renders the same data, a "Reload extensions" button next to Refresh (calls `extensions.reload`, then re-lists), and a per-extension enable/disable toggle. A schema'd extension renders a real **form** (text/number/toggle/write-only secret with Set/Clear via `extensions.set_secret`); a schema-less one keeps the raw-JSON `config` editor. There is **no** restart notice — every change (enable/disable/config/secret/reload) applies live. An `overridden` row shows an "Overridden by your copy at …" line and hides the toggle and config surfaces (the winning copy owns them). This panel is the **single** place the derived waiting state is shown: when `ready_state === "waiting"` it renders "On, waiting for configuration" and, from the schema, names the unset secret fields ("Waiting for: <labels>"). The tool pickers never show the waiting state — a not-ready tool is simply absent there (design decision).
- **`settings.update({extensions})`** accepts `{disabled, config}` as a **full-replace** public section (see `.vorch/domain-maps/settings.md`). The async handler schema-validates each loaded schema'd extension's `config` before persisting (`invalid_request` on error), then compares old vs new `disabled` sets and applies the delta after the write: any name **removed** (newly enabled) triggers `await runtime.reload_extensions()` **and nothing else** (the full rebuild reads the freshly persisted state, so it also applies any name disabled in the same save); otherwise any name **added** (newly disabled, no enable) drives `await runtime.apply_extension_disabled_change`. A config-value-only change applies live via `api.get_config()` and triggers neither. The response never carries a restart flag — every extension change is live.

## Lifecycle (startup/shutdown)

- **Startup** handlers fire once bootstrap is complete and an event loop is running. `Runtime.fire_extension_startup()` (async) delegates to `registry.fire_startup()`; the server calls it from inside its async lifespan after `start()`, so handlers run on the live serving loop and may schedule background tasks there. Accessors that never serve (CLI local commands) do not fire startup.
- **Shutdown** handlers fire during runtime shutdown **before** `Runtime._clear_service_references`: `Runtime.aclose()` awaits `registry.fire_shutdown()`; the synchronous `Runtime.stop()` uses `registry.fire_shutdown_blocking()`. A **live disable** also fires just that one extension's shutdown handlers (through `deactivate`), so resources are cleaned up on disable, not only at app shutdown.
- Both phases fail-open per handler (log `error`, continue). Only `loaded` records' handlers fire.

## Reload (restart-equivalent rebuild)

`Runtime.reload_extensions` (async) rebuilds the **whole** extension layer from disk in the running process — the end state equals what a restart from the current persisted settings would produce. It is the explicit trigger behind the `extensions.reload` RPC/CLI/WebUI and behind *enabling* an extension. Sequence: read fresh settings; detach the old layer's tools (`remove_applied_tools`) and `await fire_shutdown()`; `purge_extension_modules()`; `ExtensionRegistry.load(...)` a fresh registry with the same arguments `start()` uses; swap; re-apply tools (`apply_tools`), recall backends (`reload_recall_backend`), and prompt blocks; `await fire_startup()`. It picks up edited code (including package submodules), extensions added to / deleted from a scan root, fixed-`failed` extensions, and boot-`disabled` extensions that were enabled. Always a full atomic rebuild — never per-module hot patching. Every extension-layer mutation (reload **and** live disable) serializes through one `asyncio.Lock` on the runtime, so concurrent toggles/calls queue and the last write wins; the swap-window race (a run dispatching into an already-shut-down old extension) is accepted and caught by per-handler fail-open isolation — no drain.

## Conventions

- Extension discovery is shallow: only immediate children of each configured root are considered.
- Load order is deterministic by sorted extension name within each root; roots are processed in configured order. The apply phase installs hook declarations in that same order, so `_handlers` ordering matches discovery order.
- Identity is the filesystem name. `extension.json` is optional and never required; single-file extensions are first-class and cannot carry one. A manifest `name` is display-only.
- `register(api)` may be sync or async. Async `register()` coroutines are gathered and awaited to completion **before** the apply phase — no fire-and-forget. `_run_coroutine_to_completion` drives them directly when no loop runs, and on a private loop in a worker thread when a loop is already running (e.g. `Runtime.start()` inside the server lifespan), keeping both situations deterministic.
- Failures are fail-open and recorded on the `ExtensionRecord`: disabled extensions are never imported (`status="disabled"`); import / `register()` / manifest errors produce `status="failed"` with an `error` detail (logged at `error`) and never abort the other extensions. Per-event handler failures log at `warning` (`"Extension %r %s handler raised: %s"`); lifecycle handler failures log at `error`. None abort the run.
- A manifest `api_version` greater than `API_VERSION` fails the extension before import with a clear message.
- Dispatch iteration, async/await handling, exception isolation, and all per-event composition semantics live in `core/extensions/`. `core/chat/` owns the fire-points, the `HookContext`, the payload meaning, and applying results (the `context` message copy, the tool-result-envelope `validator`). Prompt blocks are **not** a chat fire-point: they are collected by the runtime and consumed by the prompt manager at build time, never appended in the chat loop.
- Hook-returned result envelopes (`Replace`, `tool_result` returns) must be valid stable result envelopes and JSON-serializable. Invalid envelopes are dropped by the `validator` rather than aborting the run.
- Decision objects (`Deny`/`Modify`/`Replace`) and `API_VERSION` are exported from `core.extensions` because extensions run in-process and import them directly.

## Constraints & Gotchas

- Extension modules run arbitrary in-process Python and therefore share the kernel's trust boundary.
- `_handlers` is private to the registry; only `install_handler` (the apply phase / test seam) writes it. Cross-module code drives hooks through the `dispatch_*` methods; adding a new hook means adding a new event name plus a typed `dispatch_*` method here and a fire-point in `core/chat/`, not iterating `_handlers` elsewhere.
- **Everything applies live — no restart, no restart flag.** **Disabling** an extension takes the surgical deactivation gate (hooks off, tools unregistered, prompt blocks dropped, shutdown fired). **Enabling** triggers a full `Runtime.reload_extensions` rebuild, so code disabled at boot is imported and takes effect immediately. Per-extension **config values** are read **live** via `api.get_config()` and secrets via `api.resolve_credential()`, so a value/secret change takes effect on the next call. `settings.update` routes the disabled-set delta: enable → reload (which also covers a same-save disable), else disable-only → surgical deactivate. A live-deactivated extension's code stays imported but dormant; its record becomes `status="disabled"` with cleared declarations, indistinguishable from a boot-disabled one on every status surface. The register-time `api.config` snapshot stays frozen for structural decisions inside `register()`.
- **Recall edge on live disable.** If a live-disabled extension provided the *currently-active* recall backend, `Runtime.apply_extension_disabled_change` rebuilds the backend registry (now without that extension's backend) and re-resolves — an unknown selected name falls back to the built-in default (`jsonl_scan`) with a warning, so recall never points at dormant code. The persisted `recall.backend` selection is **left untouched**, so re-enabling the extension (a live reload) restores it. A full `reload_extensions` reaches the same recovery through `reload_recall_backend`.
- `context` hook isolation is shallow-copy only: top-level message dict mutations are isolated per request, but deep nested mutations can still affect shared objects.
- `tool_call` is a decision pipeline (`Modify`/`Deny`/`Replace`); `tool_result` is a full-replace pipeline. Both validate envelopes through the chat-injected `validator` (tool-result envelope schema + JSON-serializability) and silently drop invalid ones. The `tool_call_started` event is emitted *after* the `tool_call` hook phase so it reflects modified arguments — this is later in the timeline than a pre-hook emission would be, by design.
- `settings.extension_directories` must be a list of non-empty strings; a non-list value is ignored with a warning, invalid entries are skipped, and paths are `expanduser()`-expanded. The `settings.extensions` section (`disabled` list + `config` map) is validated centrally in `core/settings/validation.py`; the runtime re-parses it defensively and ignores malformed pieces with a warning.
