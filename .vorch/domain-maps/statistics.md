# Statistics

Read-only aggregation over persisted Sessions that produces the WebUI Statistics tab's data in one on-demand scan.

## Overview

`core/statistics/` owns the Statistics domain. It computes reports by scanning the canonical JSONL Sessions that already exist and **adds no persistence of its own** — every local activity figure is derived from persisted `ChatMessage` data ([core/chat/messages.py](../../core/chat/messages.py)). This is a hard constraint from the user: local Statistics must remain derivable from currently persisted Session data, with no derived statistics store. The normalized limit observations physically placed under `<data_dir>/statistics/provider-usage/` remain Provider-owned upstream source data described in `providers/usage.md`; their placement does not make Statistics their writer or cache owner. A fork remains a structural Session, but its copied transcript prefix is history rather than newly executed activity: activity aggregates consume only messages after the fork's recorded `fork_source.message_count`.

`StatisticsService(chat_sessions, agents, projects=None, skill_inventory=None)` is constructor-injected (DI via minimal `Protocol`s, no globals). `report(since=None, until=None)` walks every agent → session → message exactly once and returns a frozen dataclass tree; the scan covers identity agents (global, `project_id=None`) **and** every project-scoped session — for each project it enumerates the session-owning agents under the anchor (`ProjectDirectory.session_owning_agents(project_id)`) and loads them with that `project_id`. Project agents appear in the report under the address form `agent@projekt` (so a bare `builder` stays unambiguous across projects); identity agents keep their bare id, so a report with no projects is byte-identical to before. A global and a project session sharing a UUID live under different anchors, so there is no double-counting. `StatisticsReport.to_dict()` (uses `dataclasses.asdict`) yields the JSON payload the RPC returns. Out of scope by decision: any new persistence or derived cache, cost/pricing, authoritative fallback/subagent attribution, and a per-session sub-tab. A disposable rebuildable cache (the `core/recall/` SQLite-index pattern) is the documented future path if the full scan becomes slow — it is **not** pre-built.

## Data Model

The report tree (frozen dataclasses, all JSON-native fields): `StatisticsReport{generated_at, window, overview, usage, runs, errors, tools, skills}`. The module is now three files: `statistics.py` (scan, aggregator, most sections), `skills.py` (the skills section: `SkillInventorySource` Protocol, `SkillsSection`/`SkillUsageStat` dataclasses, `SkillUsageAccumulator`, inventory join), and `timestamps.py` (the shared `parse_timestamp` leaf helper — extracted because `statistics.py` imports `skills.py`, so a shared helper in `statistics.py` would be a circular import).

- **overview** — totals (agents, sessions, runs, open_run_groups, visible Chat messages, stored Session records), `chat_messages_by_role` (`user` / `assistant`, zero-filled), `session_records_by_role` (all nine canonical persisted roles, zero-filled), last activity, run-status counts, mean + median run duration, tool-call totals, per-agent activity, and a `daily_trend` series whose active UTC-date rows carry `runs` plus `completed` / `failed` / `cancelled` outcome counts. User records always count as visible Chat messages (including Content Blocks); Assistant records count only when `content` contains non-blank text, so visible intermediate status updates count while Thinking-only and Tool-call-only Model steps do not. Per-agent rows carry the same `chat_messages` / `session_records` distinction even though the current table does not display those fields.
- **usage** — `totals` plus per-`provider` and per-`(provider, bare-model)` records, a daily series, and a `cache` section. Each record splits tokens into measured_input/output and estimated_input/output, with `total_tokens` (measured + estimated) provided **only** for ranking/share. Totals, provider, model, and daily records additionally carry `cache_read_tokens`, `cache_write_tokens`, and `cache_input_tokens` (totals/provider/model also `cache_turns`) — accumulated **only** over measured turns whose usage carries cache fields at all, so a hit rate (`cache_read / cache_input`) never paints a provider without cache reporting as 0%. The `cache` section holds `lowest_hit_rate_sessions` (per-session cache effectiveness, worst hit rate first, ≥2 cache-reporting turns required, capped `TOP_CACHE_SESSIONS`) and `suspected_breaks` (`evaluated_turns`, `suspected_turns`, `incidents` capped `TOP_CACHE_BREAK_INCIDENTS`, sorted by lost tokens).
- **runs** — status distribution, cancel/failure rate, duration stats (count, mean, P50/P90/P95), longest runs, runs-with-tool-calls, derived_fallback_runs, per-agent/per-session/per-day counts, and recorded-Run Agentic-Loop depth (`agent_messages` for visible Assistant text, `model_steps` for every Assistant response, plus each average per Run). Open Run groups have no persisted summary and are excluded from these Run-depth totals and averages.
- **errors** — counts by error_kind, provider, model, agent, UTC hour-of-day, and a daily series.
- **tools** — per tool name: calls, successes/failures, success/error rate, mean + P95 duration, top `error.code`; plus calls-per-agent and busiest sessions. The WebUI labels the two rates **Accepted** (`ok:true`) and **Rejected** (`ok:false`) because a validation or guardrail rejection is not by itself a Tool malfunction.
- **skills** — one row per **current-inventory** Skill (joined at build time against the injected inventory): `name`, `origins` (`bundled` / `global` / `agent:<agent-id>` / `project:<display-name>`; multiple entries on a cross-scope name collision — usage is deliberately keyed by bare Skill name), `offered_sessions` (Sessions whose `seen_skills` sidecar list contains the name), `activated_sessions` (all Sessions carrying an activation for the name on either carrier — a `[skill-context]` trigger note or a loading `skill` Tool result, both parsed via the Sessions-domain helpers; at most one per Session by design), `activated_offered_sessions` (the per-Session intersection of those facts), and `usage_rate` (`activated_offered_sessions / offered_sessions`; `null` only without offer data). The section also carries first/last offered and activated timestamps, `by_agent` activation counts, the existing inventory/activation summaries, `offered_unactivated_skills` for evidence-backed delete/improve candidates, and `skills_without_offer_data` so fresh or metadata-poor Skills are never presented as candidates. Usage recorded for a name absent from the current inventory is dropped (deleted Skills are not reported). Rows sort `(-offered_sessions, name)`. Like the Tools section, it carries only names/origins/counts/timestamps — never Skill content.

## Interfaces

- `StatisticsService(chat_sessions: SessionSource, agents: AgentDirectory, projects: ProjectDirectory | None = None, skill_inventory: SkillInventorySource | None = None)`. `SessionSource` needs `list_with_metadata(agent_id, project_id=None)` + `get(agent_id, id, project_id=None).load()` (satisfied by `ChatSessionManager`); `AgentDirectory` needs `list()` returning objects with `.id` (satisfied by `AgentStore`); `ProjectDirectory` needs `list()` + `session_owning_agents(project_id)` (satisfied by `ProjectStore`); `SkillInventorySource` needs `global_skills()` + `agent_skill_names(agent_id)` + `project_skills(project_id)`. Wired in the RPC from `runtime.chat_sessions`, `runtime.agents`, `runtime.projects`, and the RPC-local `_RuntimeSkillInventory` adapter (`global_skills` ← `runtime.skills_for(None, None).list_all()`, `agent_skill_names` ← `scan_skill_names(runtime.agent_skills_dir(id))` guarded by `.is_dir()`, `project_skills` ← `runtime.project_own_skills(id)` tagged via `project_skill_origin`). Omitting `projects` keeps the identity-only scan; omitting `skill_inventory` builds the skills section against an empty inventory (all usage dropped, zero counts).
- **RPC `statistics.report`** ([server/rpc/statistics_methods.py](../../server/rpc/statistics_methods.py)): optional params `{since?, until?}` (ISO-8601, `Z` accepted), validated — unknown fields and inverted/malformed windows are rejected with `RPC_ERROR_INVALID_REQUEST`. The service is lazily built and cached on RPC `state` (mirrors `operations_methods._log_viewer`). Registered in [server/rpc/methods.py](../../server/rpc/methods.py).
- **RPC `statistics.run_activity`**: required `{since, until}` with the same validation. It scans the same global and project-scoped Sessions and returns Runs whose execution interval overlaps the requested usage-change interval, newest first, capped at 200 with `total_runs` and `truncated`. Each row carries Session/Agent identity, Run status/model/Tool-call count, and measured and estimated token totals. This is temporal correlation only; it does not attribute a Provider-limit change to a Run.
- **WebUI**: `webui/src/components/StatisticsView.svelte` calls `rpc('statistics.report')` once on mount (plus manual refresh) and renders six sub-views (Overview / Usage / Runs & errors / Tools / Skills / Limits). Overview presents the all-time Run outcome distribution as an exact linear share and turns `daily_trend` into fixed calendar-correct windows (30 days / 16 ISO weeks / 12 months), zero-filling absent periods in the pure presentation layer; persisted Error records stay separate in Runs & errors instead of sharing a chart scale with Run outcomes. The UI labels Model steps separately from visible Chat messages, states that Provider/Model Run counts are involvement counts, identifies Error hour buckets as UTC and Error Model attribution as a proxy, labels Tool results Accepted/Rejected instead of implying every `ok:false` result is a malfunction, and distinguishes evidence-backed Skill candidates from missing offer data. All formatting/rollup logic is in the pure, unit-tested `webui/src/lib/statisticsView.js`; the nav entry (`navigation.statistics`) and route live in `webui/src/App.svelte`.
- **Limits crosses two owners without merging their sources of truth.** While the sub-view and page are visible, `StatisticsView` calls the Providers-domain `provider.usage` RPC immediately and then 10 seconds after each completed request; leaving Limits or hiding the page stops polling, returning triggers an immediate refresh, and the manual Refresh action does not exist. `LimitHistory` independently refreshes Provider-owned automatic history every 60 seconds. Selecting a change interval then requests the Statistics-owned Session projection through `statistics.run_activity`; the UI explicitly labels the result as temporal overlap rather than causality. See `providers/usage.md` and `webui.md`. The read-only "no derived backend storage, no network" invariant applies to `StatisticsService` only.

## Conventions

- **Run-summary segmentation.** Assistant/tool messages carry no `run_id`; only `run_summary` does, and it annotates the immediately preceding Assistant Run. Per-run aggregates come from segmenting each session's message list at `run_summary` boundaries — the messages between two consecutive `run_summary` records form one run group. Run counts, status, duration percentiles, and cancel/fail rates come straight from `run_summary` records (exact, not estimated).
- **Fork prefixes are excluded from activity.** `ChatSessionManager.fork` records the exact copied complete-message count in `fork_source.message_count`; `StatisticsService` slices that prefix before windowing, Run segmentation, usage/cache/error/Tool accumulation, visible-message/record counts, and Skill-activation parsing. The fork still contributes to structural Session counts, its current `seen_skills` sidecar still contributes offer evidence, and messages appended after the fork count normally. Missing or invalid hand-edited fork provenance fails open and leaves the transcript unsliced.
- **Visible Chat messages and Session records are distinct.** `total_chat_messages` and `chat_messages_by_role` count every persisted `user` record plus only `assistant` records with non-blank text `content`. Thinking, opaque Reasoning metadata, and Tool Calls never add separate Chat-message counts; an Assistant record containing visible text plus those fields counts once. `total_session_records` and `session_records_by_role` expose the complete canonical JSONL vocabulary (`system`, `user`, `assistant`, `tool`, `note`, `error`, `compaction_checkpoint`, `run_summary`, `agent_takeover`), so every Assistant Model step remains technically transparent there and under Usage. The Overview headline and conversation-role shares use visible Chat messages.
- **Real vs estimated tokens never merge.** `usage.estimated: true` marks estimated turns ([core/chat/chat.py](../../core/chat/chat.py) `_apply_usage_estimation`); they are accumulated separately from provider-reported usage and the count of estimated turns is reported. The UI badges estimated tokens. Canonical `input_tokens` already includes cached tokens, so `cache_read_tokens` / `cache_write_tokens` are surfaced only as separate informational totals, never added on top.
- **Cache figures key on field presence.** Estimated turns never carry cache data, and a provider that does not report caching must not read as a 0% hit rate — so every cache aggregate (turns, input, read, write) accumulates only over measured turns whose usage dict contains a cache field, and hit rates divide by `cache_input_tokens`, never by all measured input.
- **Window semantics.** `since`/`until` filter time-derived aggregates at message-timestamp granularity. Structural totals (agent and session counts) and last-activity are window-independent snapshots.
- **Percentiles** use the nearest-rank method (`rank = ceil(p/100 · n)`), deterministic and tested in [tests/core/statistics/test_statistics.py](../../tests/core/statistics/test_statistics.py).
- **No raw tool arguments anywhere.** Only the tool `name`, `timing`, and the `{ok, error.code}` result envelope (validated via `core.tools.is_tool_result_envelope`) feed the report.
- **Skill-usage semantics.** Offered comes from the `seen_skills` Session sidecar (written by the Chat loop: seeded with the full available set on a Session's first build, appended on mid-Session additions) and is window-filtered by the offering Session's `created_at` — the sidecar list carries no per-Skill timestamps, so Session start is the deliberate approximation. Activations come from both carrier parsers exported by Sessions and filter by carrier timestamp. Total activations remain useful even when an older Session has no offer metadata, but offer conversion uses only the per-Session intersection of offered + activated; it therefore stays within 0–100% and never treats missing denominator evidence as a conversion. The inventory join, `total_skills`, and `never_used_skills` are window-independent snapshots, consistent with the structural-totals rule above.

## Constraints & Gotchas

- **Derived fallback is best-effort, not authoritative.** A run group with ≥2 distinct bare models is reported as `derived_fallback_runs` (an in-run model change). The authoritative `model_fallback_activated` event is in-memory and not persisted, so it is not available here; the UI labels this as derived.
- **Suspected cache breaks are a heuristic, labelled derived.** Per session (`_SessionCacheTracker`), each measured cache-reporting turn is compared against the previous measured turn; a turn is *evaluated* only when nothing legitimate explains a cache miss — skipped are the first turn, turns after a `compaction_checkpoint` or `agent_takeover` boundary, model switches, idle gaps beyond `CACHE_BREAK_MAX_GAP_SECONDS` (300s ≈ provider cache TTL), previous prompts under `CACHE_BREAK_MIN_PREVIOUS_INPUT_TOKENS` (2048), and anything following an estimated turn. An evaluated turn whose `cache_read` falls below `CACHE_BREAK_READ_RATIO` (0.5) of the previous prompt becomes an incident. False negatives are accepted by design (thresholds favor low noise); prompt-prefix changes the scan cannot see (settings edits, tool-set changes) can still cause rare false positives.
- **`open_run_groups` is best-effort "active/unterminated".** A trailing message group with conversational activity after the last `run_summary` is counted as open. This conflates a genuinely running run with a crashed/interrupted one — truly-active runs are in-memory (`ChatRunManager`) and out of this read-only scope.
- **Error attribution is by proxy.** `error` messages reject a `model` field, so each error is attributed to the last assistant model seen in its session (`unknown` when none precedes it) and to that model's provider.
- **Sessions predating `seen_skills` metadata contribute no offered counts** (activations still count) — accepted by design, no legacy handling. A Skill's `offered_sessions` is therefore a lower bound over old data; the counter only becomes meaningful from the point the Chat loop started writing the sidecar key. Such activations do not enter `activated_offered_sessions` or `usage_rate`, and a current Skill with no observed offer data is reported separately instead of being labelled a delete/improve candidate.
- **Not derivable from persisted data (kept out of scope):** cost/pricing (normalized catalogs carry no pricing) and authoritative fallback / subagent-per-run attribution.
