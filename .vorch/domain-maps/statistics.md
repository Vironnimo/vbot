# Statistics

Incrementally indexed aggregation over persisted Sessions that produces the WebUI Statistics tab without reparsing unchanged transcripts.

## Overview

`core/statistics/` owns the Statistics domain. Every local activity figure remains derivable from canonical JSONL `ChatMessage` data ([core/chat/messages.py](../../core/chat/messages.py)), while `StatisticsIndex` maintains a disposable compact SQLite read model at `<data_dir>/statistics/session-statistics.sqlite`. Reports reconcile canonical source identity/size/mtime and a Sessions-owned append cursor, ingest only validated new tails, prune removed scopes, then aggregate compact records; a schema mismatch, replacement, corruption, or invalid cursor rebuilds affected derived state rather than changing JSONL. The normalized limit observations under `<data_dir>/statistics/provider-usage/` remain Provider-owned upstream source data described in `providers/usage.md`; their colocated path does not make Statistics their writer or cache owner. A fork remains a structural Session, but its copied transcript prefix is history rather than newly executed activity: the index stores only records after the fork's effective `fork_source.message_count`.

`StatisticsService(chat_sessions, agents, projects=None, skill_inventory=None)` is constructor-injected (DI via minimal `Protocol`s, no globals). `report(since=None, until=None)` covers identity agents (global, `project_id=None`) **and** every project-scoped Session — for each Project it enumerates the session-owning agents under the anchor (`ProjectDirectory.session_owning_agents(project_id)`) and reconciles them with that `project_id`. Project agents appear under `agent@projekt`; identity agents keep their bare id. A global and Project Session sharing a UUID have different composite index keys, so there is no collision or double-counting. `StatisticsReport.to_dict()` yields the unchanged JSON payload. Out of scope by decision: cost/pricing, authoritative fallback/subagent attribution, and a per-session sub-tab.

## Data Model

The report tree (frozen dataclasses, all JSON-native fields) remains `StatisticsReport{generated_at, window, overview, usage, runs, compactions, errors, tools, skills}`. `statistics.py` owns aggregation and report shapes; `index.py` owns SQLite schema/reconciliation and the content-minimizing Message projection; `skills.py` owns Skill inventory/usage; `timestamps.py` owns shared timestamp parsing. The index stores scoped Session source cursors plus ordered compact records containing only fields consumed by aggregation: roles/timestamps, visible-text presence, Model/Usage facts, Run/Tool/Error/Compaction facts, and Skill activation names. Raw Chat text, Reasoning, Tool arguments, Tool success data, Skill content, Compaction projections, and other Provider payloads never enter it.

- **overview** — totals (agents, sessions, runs, open_run_groups, visible Chat messages, stored Session records), `chat_messages_by_role` (`user` / `assistant`, zero-filled), `session_records_by_role` (all nine canonical persisted roles, zero-filled), last activity, run-status counts, mean + median run duration, tool-call totals, per-agent activity, and a `daily_trend` series whose active UTC-date rows carry `runs` plus `completed` / `failed` / `cancelled` / `interrupted` outcome counts. User records always count as visible Chat messages (including Content Blocks); Assistant records count only when `content` contains non-blank text, so visible intermediate status updates count while Thinking-only and Tool-call-only Model steps do not. Per-agent rows carry the same `chat_messages` / `session_records` distinction even though the current table does not display those fields.
- **usage** — `totals` plus per-`provider` and per-`(provider, bare-model)` records, a daily series, and a `cache` section. Each record splits input and output independently into measured and estimated buckets, with `total_tokens` (measured + estimated) provided **only** for ranking/share; a partial Provider response can therefore contribute measured output and estimated input. Totals, provider, model, and daily records carry provider-reported `reasoning_tokens` plus `reasoning_turns`; Reasoning is an informational subset of measured output and never enters `total_tokens`, while the reporting-turn count distinguishes unavailable detail from a reported zero. These records additionally carry `cache_read_tokens`, `cache_write_tokens`, and `cache_input_tokens` (totals/provider/model also `cache_turns`) — accumulated **only** when input provenance is measured and usage carries cache fields at all, so a hit rate (`cache_read / cache_input`) never paints a provider without cache reporting as 0%. The `cache` section holds `lowest_hit_rate_sessions` (per-session cache effectiveness, worst hit rate first, ≥2 cache-reporting turns required, capped `TOP_CACHE_SESSIONS`) and `suspected_breaks` (`evaluated_turns`, `suspected_turns`, `incidents` capped `TOP_CACHE_BREAK_INCIDENTS`, sorted by lost tokens).
- **runs** — status distribution, cancel/failure/interruption rates, duration stats (count, mean, P50/P90/P95), longest runs, runs-with-tool-calls, derived_fallback_runs, per-agent/per-session/per-day counts, and recorded-Run Agentic-Loop depth (`agent_messages` for visible Assistant text, `model_steps` for every Assistant response, plus each average per Run). Open Run groups have no persisted summary and are excluded from these Run-depth totals and averages.
- **compactions** — checkpoint-derived total Compactions, Sessions with in-window Compactions, mean/P50/P95/max Compactions per compacted Session, counts by persisted Strategy, estimated reclaimed-context statistics from checkpoints carrying both `context_tokens_before` and `context_tokens_after`, and the top 20 compacted Sessions with last timestamp and summed estimated reclaim. There is no mutable or separately persisted counter: a legacy checkpoint missing token sizes still counts as a Compaction but not as a reclaim observation.
- **errors** — counts by error_kind, provider, model, agent, UTC hour-of-day, and a daily series.
- **tools** — per tool name: calls, successes/failures, success/error rate, mean + P95 duration, top `error.code`; plus calls-per-agent and busiest sessions. The WebUI labels the two rates **Accepted** (`ok:true`) and **Rejected** (`ok:false`) because a validation or guardrail rejection is not by itself a Tool malfunction.
- **skills** — one row per **current-inventory** Skill (joined at build time against the injected inventory): `name`, `origins` (`bundled` / `global` / `agent:<agent-id>` / `project:<display-name>`; multiple entries on a cross-scope name collision — usage is deliberately keyed by bare Skill name), `offered_sessions` (Sessions whose `seen_skills` sidecar list contains the name), `activated_sessions` (all Sessions carrying an activation for the name on either carrier — a `[skill-context]` trigger note or a loading `skill` Tool result, both parsed via the Sessions-domain helpers; at most one per Session by design), `activated_offered_sessions` (the per-Session intersection of those facts), and `usage_rate` (`activated_offered_sessions / offered_sessions`; `null` only without offer data). The section also carries first/last offered and activated timestamps, `by_agent` activation counts, the existing inventory/activation summaries, `offered_unactivated_skills` for evidence-backed delete/improve candidates, and `skills_without_offer_data` so fresh or metadata-poor Skills are never presented as candidates. Usage recorded for a name absent from the current inventory is dropped (deleted Skills are not reported). Rows sort `(-offered_sessions, name)`. Like the Tools section, it carries only names/origins/counts/timestamps — never Skill content.

## Interfaces

- `StatisticsService(chat_sessions: SessionSource, agents: AgentDirectory, projects: ProjectDirectory | None = None, skill_inventory: SkillInventorySource | None = None)`. `SessionSource` supplies `data_dir`, `list_with_metadata(...)`, and scoped handles with `path`, `load()`, and `load_since(cursor)` (satisfied by `ChatSessionManager`); the other injected directory/inventory contracts are unchanged. Omitting `projects` keeps identity-only scope discovery; omitting `skill_inventory` builds an empty valid Skills section. The live canonical scan remains only the availability fallback after an index failure and one failed discard/rebuild attempt.
- **RPC `statistics.report`** ([server/rpc/statistics_methods.py](../../server/rpc/statistics_methods.py)): optional params `{since?, until?}` (ISO-8601, `Z` accepted), validated — unknown fields and inverted/malformed windows are rejected with `RPC_ERROR_INVALID_REQUEST`. The service is cached on RPC `state`; real server startup calls `warm_index()` in a background worker, and both report RPCs offload any remaining reconciliation so filesystem/SQLite work never blocks the event loop. Runtime stubs without the complete Session/Agent/Project discovery surface skip warmup. Registered in [server/rpc/methods.py](../../server/rpc/methods.py).
- **RPC `statistics.run_activity`**: required `{since, until}` with the same validation. It reads the same reconciled global and Project-scoped projection and returns Runs whose execution interval overlaps the requested usage-change interval, newest first, capped at 200 with `total_runs` and `truncated`. Each row carries Session/Agent identity, Run status/model/Tool-call count, and measured and estimated token totals. This is temporal correlation only; it does not attribute a Provider-limit change to a Run.
- **WebUI**: `webui/src/components/StatisticsView.svelte` calls `rpc('statistics.report')` once on mount (plus manual refresh) and renders seven sub-views (Overview / Usage / Runs & errors / Compactions / Tools / Skills / Limits). Overview presents the all-time Run outcome distribution as an exact linear share across completed, failed, cancelled, and interrupted outcomes and turns `daily_trend` into fixed calendar-correct windows (30 days / 16 ISO weeks / 12 months), zero-filling absent periods in the pure presentation layer; persisted Error records stay separate in Runs & errors instead of sharing a chart scale with Run outcomes. Compactions presents the checkpoint count/distribution, Strategy mix, reclaim estimates, and most compacted Sessions with explicit legacy/window/Fork semantics. The Usage view presents Reasoning beside totals and Provider/Model rows only when at least one turn reported it, and labels it as an output subset. The UI labels Model steps separately from visible Chat messages, states that Provider/Model Run counts are involvement counts, identifies Error hour buckets as UTC and Error Model attribution as a proxy, labels Tool results Accepted/Rejected instead of implying every `ok:false` result is a malfunction, and distinguishes evidence-backed Skill candidates from missing offer data. All formatting/rollup logic is in the pure, unit-tested `webui/src/lib/statisticsView.js`; the nav entry (`navigation.statistics`) and route live in `webui/src/App.svelte`.
- **CLI**: `vbot statistics compactions [--since ...] [--until ...]` formats the same `compactions` report section; it does not rescan Sessions or maintain another count.
- **Limits crosses two owners without merging their sources of truth.** While the sub-view and page are visible, `StatisticsView` calls the Providers-domain `provider.usage` RPC immediately and then 10 seconds after each completed request; leaving Limits or hiding the page stops polling, returning triggers an immediate refresh, and the manual Refresh action does not exist. `LimitHistory` independently refreshes Provider-owned automatic history every 60 seconds. Selecting a change interval then requests the Statistics-owned Session projection through `statistics.run_activity`; the UI explicitly labels the result as temporal overlap rather than causality. See `providers/usage.md` and `webui.md`. Statistics performs no network access and writes only its disposable derived index; Provider Usage remains independent canonical upstream data.

## Conventions

- **Run-summary segmentation.** Assistant/tool messages carry no `run_id`; only `run_summary` does, and it annotates the immediately preceding Assistant Run. Per-run aggregates come from segmenting each session's message list at `run_summary` boundaries — the messages between two consecutive `run_summary` records form one run group. Run counts, status, duration percentiles, and cancel/fail rates come straight from `run_summary` records (exact, not estimated).
- **Canonical-first, repairable projection.** JSONL append succeeds independently and first; Statistics never becomes a write dependency of Chat. Each report enumerates current Session summaries, compares the source with its stored cursor, applies metadata-only changes without transcript reads, ingests append-only growth from the cursor, fully rebuilds a replaced/truncated Session, and deletes rows for missing scoped Sessions. A persisted generation invalidates stale in-memory snapshots across multiple service instances; a snapshot is reused only when reconciliation made no changes and its generation still matches.
- **Fork prefixes are excluded from activity.** `ChatSessionManager.fork` records the exact copied complete-message count in `fork_source.message_count`; `StatisticsService` slices that prefix before windowing, Run segmentation, usage/cache/error/Tool accumulation, visible-message/record counts, and Skill-activation parsing. The fork still contributes to structural Session counts, its current `seen_skills` sidecar still contributes offer evidence, and messages appended after the fork count normally. Missing or invalid hand-edited fork provenance fails open and leaves the transcript unsliced.
- **Visible Chat messages and Session records are distinct.** `total_chat_messages` and `chat_messages_by_role` count every persisted `user` record plus only `assistant` records with non-blank text `content`. Thinking, opaque Reasoning metadata, and Tool Calls never add separate Chat-message counts; an Assistant record containing visible text plus those fields counts once. `total_session_records` and `session_records_by_role` expose the complete canonical JSONL vocabulary (`system`, `user`, `assistant`, `tool`, `note`, `error`, `compaction_checkpoint`, `run_summary`, `agent_takeover`), so every Assistant Model step remains technically transparent there and under Usage. The Overview headline and conversation-role shares use visible Chat messages.
- **Real vs estimated tokens never merge.** `input_tokens_estimated` and `output_tokens_estimated` carry field provenance; aggregate `usage.estimated: true` remains the turn-level signal and legacy payloads with no specific flags mean both fields are estimated. Each token field enters its matching measured or estimated bucket independently, while a turn with either estimate increments `estimated_turns` and only a fully measured turn increments `measured_turns`. Canonical `input_tokens` already includes cached tokens, so `cache_read_tokens` / `cache_write_tokens` are surfaced only as separate informational totals, never added on top. Canonical `reasoning_tokens` is likewise only a measured-output subset.
- **Cache figures key on field presence and measured input.** A provider that does not report caching must not read as a 0% hit rate, so every cache aggregate (turns, input, read, write) requires measured input plus a cache field and hit rates divide by `cache_input_tokens`, never by all measured input. Any turn with estimated input breaks the cache-effectiveness comparison even when its output is measured.
- **Window semantics.** `since`/`until` filter time-derived aggregates, including Compactions, at message-timestamp granularity. Structural totals (agent and session counts) and last-activity are window-independent snapshots.
- **Percentiles** use the nearest-rank method (`rank = ceil(p/100 · n)`), deterministic and tested in [tests/core/statistics/test_statistics.py](../../tests/core/statistics/test_statistics.py).
- **No raw tool arguments anywhere.** Only the tool `name`, `timing`, and the `{ok, error.code}` result envelope (validated via `core.tools.is_tool_result_envelope`) feed the report.
- **Skill-usage semantics.** Offered comes from the `seen_skills` Session sidecar (written by the Chat loop: seeded with the full available set on a Session's first build, appended on mid-Session additions) and is window-filtered by the offering Session's `created_at` — the sidecar list carries no per-Skill timestamps, so Session start is the deliberate approximation. Activations come from both carrier parsers exported by Sessions and filter by carrier timestamp. Total activations remain useful even when an older Session has no offer metadata, but offer conversion uses only the per-Session intersection of offered + activated; it therefore stays within 0–100% and never treats missing denominator evidence as a conversion. The inventory join, `total_skills`, and `never_used_skills` are window-independent snapshots, consistent with the structural-totals rule above.

## Constraints & Gotchas

- **The SQLite index is not a second source of truth.** Its `PRAGMA user_version` schema is replace-not-migrate, its exact file plus WAL/SHM sidecars may be deleted on failure, and a successful report must remain rebuildable from current Sessions. Do not put user-owned or otherwise non-derivable data in it.
- **Source cursors validate the processed prefix.** `SessionReadCursor` records byte offset, Message count, and last Message id; `ChatSession.load_since()` returns `None` when that boundary no longer matches. Source identity changes, same-size rewrites, truncation, changed fork slicing, and invalid cursors rebuild that Session rather than attempting compatibility repair.
- **Derived fallback is best-effort, not authoritative.** A run group with ≥2 distinct bare models is reported as `derived_fallback_runs` (an in-run model change). The authoritative `model_fallback_activated` event is in-memory and not persisted, so it is not available here; the UI labels this as derived.
- **Suspected cache breaks are a heuristic, labelled derived.** Per session (`_SessionCacheTracker`), each measured cache-reporting turn is compared against the previous measured turn; a turn is *evaluated* only when nothing legitimate explains a cache miss — skipped are the first turn, turns after a `compaction_checkpoint` or `agent_takeover` boundary, model switches, idle gaps beyond `CACHE_BREAK_MAX_GAP_SECONDS` (300s ≈ provider cache TTL), previous prompts under `CACHE_BREAK_MIN_PREVIOUS_INPUT_TOKENS` (2048), and anything following an estimated turn. An evaluated turn whose `cache_read` falls below `CACHE_BREAK_READ_RATIO` (0.5) of the previous prompt becomes an incident. False negatives are accepted by design (thresholds favor low noise); prompt-prefix changes the scan cannot see (settings edits, tool-set changes) can still cause rare false positives.
- **`open_run_groups` is best-effort "active/unterminated".** A trailing message group with conversational activity after the last `run_summary` is counted as open. This conflates a genuinely running Run with a crashed/interrupted one — truly active Runs remain in-memory (`ChatRunManager`) and outside the persisted projection's authority.
- **Error attribution is by proxy.** `error` messages reject a `model` field, so each error is attributed to the last assistant model seen in its session (`unknown` when none precedes it) and to that model's provider.
- **Sessions predating `seen_skills` metadata contribute no offered counts** (activations still count) — accepted by design, no legacy handling. A Skill's `offered_sessions` is therefore a lower bound over old data; the counter only becomes meaningful from the point the Chat loop started writing the sidecar key. Such activations do not enter `activated_offered_sessions` or `usage_rate`, and a current Skill with no observed offer data is reported separately instead of being labelled a delete/improve candidate.
- **Not derivable from persisted data (kept out of scope):** cost/pricing (normalized catalogs carry no pricing) and authoritative fallback / subagent-per-run attribution.
