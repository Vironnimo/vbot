# Sub-Agents Agent-facing text

Why each sentence of the Agent-facing text the Sub-Agents domain owns exists: the Sub-Agent role block, the delegation Tool start and send results, activity receipts, and the target, depth and limit refusals. Rules for this file: `.vorch/workflows/domain-map-workflow.md` -> Agent-facing text.

Review labels such as "Review B12" name the reviews of 2026-10-12: `tools/shell/agent-facing-text.md`.

| Text | Reason |
|---|---|
| Role block: `You are a Sub-Agent: another Agent, your Parent Agent, delegated work to you ...` | Without it a Sub-Agent takes the brief as the user's request and addresses the user. |
| Role block: `vBot sends your final answers to your Parent Agent unless the user writes in this Session. ...` | Parent-directed final answers are forwarded; a Sub-Agent that ends a turn while work still runs must say so instead of presenting a result. |
| Role block: `When you find that the task cannot be done as briefed, ... do not switch to a different task on your own. ...` | A Sub-Agent that silently substitutes another approach or scope hands the Parent a result it integrates unknowingly. A question via `message_parent` cannot be awaited within the turn, so a Sub-Agent blocked on the decision ends its turn with the finding instead; one that can continue asks and continues. |
| Role block: `vBot starts a new turn for you when background work you started delivers ...` | Sub-Agents otherwise poll or wait on background work they can leave running. |
| Role block: `If the user writes in this Session, your final answers go to the user. ... You remain connected throughout.` | User input selects the audience without severing the relationship; messaging in either direction restores Parent replies. User decision 2026-10-14. |
| `PARENT_AGENT_INPUT_SYSTEM_REMINDER` | Identifies Parent input and announces that final answers now go to Parent. |
| `PARENT_AGENT_STEERING_SYSTEM_REMINDER` | A steered Parent message must change the running task, and a question in it needs `message_parent` because the final answer comes later. |
| `SUBAGENT_REPLY_TO_USER_SYSTEM_REMINDER` | Announces user replies and how either side restores Parent replies; avoids interpreting user input as permanent disconnection. |
| Forwarded section header (Sub-Agent id/title), Run id, `Answer <message_id>` / `Partial answer <message_id>`, and facts line | The Parent must tell which Sub-Agent answered, how its turn ended, and what is still running before it treats the answer as final. The repeated Agent/Session address was removed on 2026-10-14; the initial result keeps it for Session lookup. Stable Message ids distinguish a main report from a steered addendum in the same Run (observed 2026-10-13); later answers must not displace earlier ones. |
| `FACTS_SIBLINGS_PENDING_TEMPLATE` / `FACTS_NO_SIBLINGS_PENDING_TEXT` | After one of several Sub-Agents answered, a Parent called `subagent` `list` to learn whether the others still ran (black-box runs, 2026-10). |
| `REPLY_TO_USER_NOTICE_TEMPLATE` | The Parent learns the current recipient, its unchanged messaging/status/stop controls, and how to restore automatic replies. |
| `PARENT_MESSAGE_SECTION_TEMPLATE`: `Delivery {delivery_id}.` | Correlates the received message with the Tool result and its activity receipt. |
| Activity receipt: `Pending: submitted for delivery to the Parent Session.` | Submission alone is not confirmed persistence; a disputed delivery needs a visible intermediate state. |
| Activity receipt: `Delivered: stored in the Parent Session.` | Marks the completion coordinator's persistence acknowledgement, without claiming the Model has read it. |
| Activity receipts: `Delivery failed: {error}` / `Cancelled before delivery was confirmed.` | A failed or rejected delivery must not look like a confirmed one; the reason stays with its id. |
| `PARENT_MESSAGE_SECTION_TEMPLATE` closing sentence | A message is not the Sub-Agent's result; the Parent must keep waiting for the answer. |
| Per-Session limit refusals (`SUBAGENT_ACTIVE_LIMIT_MESSAGE_TEMPLATE`, `SUBAGENT_SEND_LIMIT_MESSAGE_TEMPLATE`): `You already have 8 Sub-Agents working, the most you can have at the same time. ... A Sub-Agent stops counting once it has answered or was stopped: wait for an answer or stop one with background_tasks action stop ...` | An earlier wording blamed the current turn; the Agent must learn that the limit counts its concurrently working Sub-Agents and frees a place when one answers or is stopped (user report, 2026-10). It names `background_tasks`, which stops Sub-Agents, only while the Agent can call it; otherwise the clause is `wait for an answer, then ...`. |
| App-wide limit refusals (`SUBAGENT_APP_LIMIT_MESSAGE_TEMPLATE`, `SUBAGENT_SEND_APP_LIMIT_MESSAGE_TEMPLATE`): `50 Sub-Agents are working across vBot ... Do this task yourself, or wait until one of your own working Sub-Agents answers ...` | The Agent cannot stop other Agents' Sub-Agents; waiting is offered only for its own working ones, because an Agent without them that ends its turn to wait is never woken. |
| `MESSAGE_PARENT_QUEUED_NOTE`: `Queued for delivery. Your Parent Agent reads it at its next step, or in a new turn if it is idle. Your final answers now go to your Parent Agent until the user writes again. Continue your work.` | Prevents a Sub-Agent from ending its turn after a message in the expectation of a reply within the same turn. |
| Unknown action: `subagent was not run: action must be one of: run, send.` | The refusal now says nothing ran, like every other `subagent` refusal (review B12). |
| `background_tasks` stop note, continue clause: `...; send it a message to continue.` (a deeper Sub-Agent: `...; your Sub-Agent <parent_id> can send it a message to continue.`), only while the caller can call `subagent`; otherwise the note ends after `Its Session keeps the history.` | A message offered to a caller without `subagent` sets off a call to a Tool it cannot call (F1): the rule Review B10 set for the message refusal, applied in the text fixes after the re-review of 2026-10-12. |
| Start result: `Started in the background. Its final answers arrive as new messages. Continue with other work your task still needs, not the work you gave a Sub-Agent. When no such work is left, end your turn: reply with a short status and no tool call. Your next turn starts when its answer arrives.` | Confirms the start and names how to receive the answer, without repeating `send` syntax. The rest is the shared wait wording (`tools/agent-facing-text.md` -> Waiting for background work); the former "or start a new turn if you are idle" named a state the Agent cannot observe. "not the work you gave a Sub-Agent" keeps the Parent from redoing or cross-checking the delegated work while it waits: in an eval of 2026-10-23, minimax-m3.1-flash read every delegated file and wrote its own check scripts in both Sub-Agent runs before ending its turn. |
| Send results: `Sent to the running Sub-Agent for its next step.` / `Started a new turn with your message.` / `Queued your message for the Sub-Agent's next turn.` plus when final answers return to Parent | Distinguishes steering, new turn and queued input; queuing does not redirect the currently running user turn. |
| Missing title: `Nothing was started. Add "description", a 3-5 word title, and repeat the call with all other fields unchanged.` | The old corrected call replaced a task longer than 60 characters with `<the same task>`, which a Model could send literally (source probe, 2026-10-14). |
| Missing send id: `Nothing was sent. send needs "id" ...` + available children + choose the intended recipient or start one | The old suggested call selected the first child and substituted `<message>` without knowing the intended recipient/content (source probe, 2026-10-14). |
| Missing task/message or id without action: add the missing field to the original call; no sendable placeholders | A copyable example with `<message>` or a brief placeholder fabricates content instead of preserving the task. A supplied id can still be used in a complete stop call. |
| Target/depth/active-limit/not-found/not-direct refusals: outcome first, then the cause and supported next action | Makes it clear that no work or message was admitted before an Agent retries; valid targets and conditional `background_tasks` hints remain. |
| `message_parent` delivery refusal: `message_parent was not queued ... Keep the message in your final answer.` | Immediate rejection must not look like accepted delivery; the final answer preserves the report. |
| `secrets` parameter: `For run, names of your Secrets to pass, such as ["GITHUB"]. A Sub-Agent has only the Secrets you pass.` | User decision 2026-10-21: Sub-Agents get Secrets only through explicit pass-through, also a Sub-Agent of the Parent's own Agent. Without the second sentence a Parent assumes its Secrets carry over and briefs a Sub-Agent that then fails at the first use (F3). |
| `SUBAGENT_SECRETS_NOTE_TEMPLATE`: `Your Parent Agent passed you these Secrets for this session:` + Secret lines + `Write a reference where the value belongs; vBot inserts the value there.` | A Sub-Agent Session has no `## Secrets` block; the passed Secrets reach it as a note at its start, with the use rule, since it may never have seen a Secret before. |
| `Nothing was started. secrets takes Secret names, such as ["GITHUB"].` and `secret_unavailable`: `You cannot pass <NAME>: it is not among your Secrets. Your Secrets: <names>.` | Three-part refusals before anything starts (F5); the second names the passable Secrets so a misspelling is fixed in one call. |
