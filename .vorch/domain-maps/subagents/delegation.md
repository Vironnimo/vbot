# Sub-Agent Delegation

How `subagent` `run` and `send` admit work: settings capture, the checks of each action, cancellation admission, the active limits and target authorization. The Tool side (definitions, call syntax, display) is `tools/subagent.md`.

## Model and settings capture

A new Sub-Agent captures its Model and thinking effort in Session metadata. Self-delegation inherits the running Parent's actual Model/effort, including a fallback route and explicit Provider default; later Parent/default changes cannot alter the child. An explicitly supplied child setting wins. Another Agent uses its own resolved settings (a Project profile with `model: inherit` still takes the caller's actual Model). Tool dispatch carries the Run settings in `ToolContext.agent_model` / `agent_thinking_effort`; callers without that context resolve the Parent Session. Working Project inheritance remains the existing Session-bound rule. Coverage: `test_new_subagent_captures_the_running_parent_or_its_other_agent` and `test_model_and_thinking_effort_belong_to_the_subagent_session`.

## run

`run` always starts a new Sub-Agent in the background and returns at once with `id`, `agent_id` (the address the Tool accepts back: `agent@project` when the Session has a Project), `session_id`, `project_id`, `status: "running"`, a `note` and an `activity_note`. Checks, all before any Session work, in this order: id/`session_id` interpretation, `description` present, target allowed, target resolvable and runnable, depth, active limit. `run` with an `id` or `session_id` naming one of the caller's own Sub-Agents is treated as `send`; an unknown `sub_`-shaped id fails `subagent_not_found`; another id is an ignored label (note); a `session_id` that is not the caller's Sub-Agent starts a new one when it reads as a stand-in (note) and is refused otherwise. `background: false` is ignored with a note. Each start logs one INFO `Sub-agent started` line (`vbot.subagents`) with ids, Sessions, target and Run.

## send

`send` reaches only a direct child (`subagent_not_direct` names the intermediate Sub-Agent); the caller cannot message grandchildren, and Sub-Agents cannot message siblings. It captures the child's generation before asynchronous preflight, rechecks that generation and Parent link under the Session write lock, and carries the generation expectation into native Run admission: a stale send refuses instead of recreating an archived Session or messaging its replacement. It enqueues through `ChatRunManager.enqueue`: an idle Session starts a turn (`started`); otherwise the item is steered into the running turn (`steered`) unless it carries an execution owner or a temporary binding, which stay `queued`. `model`/`thinking_effort` replace stored overrides only after enqueue accepts the input; any admission rejection leaves them unchanged. An executor gate keeps accepted input out of Chat until preparation commits, and queued input regains its native Chat executor before steering becomes eligible. Preparation failure removes queued work or fails an already-admitted Run without executing its content. The Session lock protects validation through settings preparation; no Run-manager lock spans metadata I/O. A stored Model that cannot run, unreadable stored overrides, or a Working Project that no longer exists (`project_not_found`, `retryable: false`, `SUBAGENT_SESSION_PROJECT_MISSING_MESSAGE_TEMPLATE`) refuse before enqueueing. Regression coverage: `test_subagents_admission.py` and the real Chat steering cases in `test_answer_delivery.py`.

## Cancellation admission

Both `stop_tree` and `stop_subagent` take the admission lock while reading the complete subtree and signalling every affected Run, so an in-flight child start is included and every affected Run receives cancellation before cleanup is awaited. They release the lock before awaiting terminal and command shutdown or Run completion. `run` and `send` recheck the calling Run's cancellation under that lock before starting or enqueueing work; a cancelled `send` changes no stored overrides. Past that check the call completes and returns its result even when the calling Run is cancelled meanwhile (`finish_despite_cancel`), so the Parent keeps the Tool result of a Sub-Agent that started or a message that was sent and never repeats the work (`test_a_call_cancelled_once_its_work_began_still_returns_its_result`).

## Limits

The limit settings and their defaults are Sub-Agent settings (`settings/sections.md`). `max_subagent_depth` refuses a `run` when the caller already has that many ancestors. Two active limits refuse a `run`, and a `send` to an idle Sub-Agent (it would start a Run); a refused `send` stores no Model overrides. Working means an active Run or queued input (`is_working`); all working Sub-Agents count regardless of reply target.

- `max_active_subagents` (`subagent_limit_exceeded`) counts the caller's own working Sub-Agents only: not the caller itself, not their Sub-Agents. Its refusal says that one stops counting once it answered or was stopped, and offers waiting, `background_tasks` stop (only while the Agent can call `background_tasks`) or doing the task itself.
- `max_active_subagents_total` (`subagent_app_limit_exceeded`) counts the working Sub-Agent Sessions of the whole process, found among the Run manager's active Runs and queues. Its refusal offers doing the task itself or waiting for one of the caller's own working Sub-Agents, because the caller cannot free other Agents' places.
- A `send` to a working Sub-Agent bypasses the Sub-Agent active limits because it starts no further Run, but Run-manager waiting-work capacity and lifecycle admission still apply. All `run` and these `send` checks are serialized under one coordinator-wide admission lock, so parallel starts cannot pass on a stale count.

## Targets

A bare `agent_id` inherits the caller's scope; `agent@project` selects that Project. The Sub-Agent Session lives in the target scope, its link records the Parent address, and the Parent Session never moves. It works in a Working Project fixed at its start (`sessions.md` -> Terms): an Identity target, a copy of the caller included, works where the caller's Run works (`ToolContext.working_project_id`; the Workspace when none), whatever the target's default Project; a Team target works in its Team's Project. `tools.subagent.allowed_agents` (snapshotted in the caller's Tool settings) lists additional targets only: missing or `['*']` allows every resolvable target, `[]` is self-only, omitting `agent_id` always selects the caller. A Project caller can reach only its own Project, whatever the policy. A generic worker name (`general-purpose`, `default`, `self`, ...) that is no allowed Agent id selects the caller with a note. The built-in Librarian is never a target. `agent_not_found`/`project_not_found` list the valid choices; a target that cannot run fails `agent_unavailable` (`retryable: false`) with the resolver's reason; an unusable `model` fails `invalid_arguments`. Explicit Identity grants carry the Agent-owned incarnation binding captured for the Run (`agent.md`); before opening a child Session, the coordinator checks it offloop while holding the shared Agent lifecycle/reference mutex through Run admission. A replaced target is refused without a Session or Run. Catalogs and Provider schema choices apply the same binding check; wildcard, self, Project-qualified and unbound legacy entries retain their existing scope. The coordinator is the security boundary; Provider-schema narrowing and the prompt block are guidance.
