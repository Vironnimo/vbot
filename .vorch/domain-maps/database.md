# Database

The shared SQLite kernel (`core/database/`): how every vBot database opens, evolves, stays consistent under concurrency, and is snapshotted and recovered.

## Overview

`core/database/` owns connection policy, schema evolution, the canonical and disposable profiles, the data-store marker and maintenance guard, data snapshots (including their JSON document set), quarantine, recovery incidents, automatic restore, the updater's guarded pre-update snapshot rollback, and operator-safe status. An owner declares a `DatabaseSpec` and calls `open_database`; it keeps its own DDL, queries, domain errors and domain semantics. The kernel knows no Session, Channel or Provider concept.

Owners today: the Session store (`sessions.md`, `core/sessions/_store_schema.session_database_spec`), the Decisions store (`model_tasks/decisions.md`, `core/model_tasks/decision_store.decision_database_spec`), the Provider usage history (`providers/usage.md`, `core/providers/usage_history.provider_usage_database_spec`) and the Channel state (`channels.md`, `core/channels/_state_schema.channel_database_spec`), plus Extension databases opened through `host.open_database` (`extensions.md`, `core/extensions/databases.extension_database_spec`). The bundled Swarm Extension is one of them (`extensions/swarm.md`). Disposable owners: the Statistics index (`statistics.md`, `core/statistics/index.statistics_database_spec`) and the two Recall indexes, the Passage FTS index and the vector index (`recall.md`, `core/recall/sqlite_fts.recall_index_database_spec`, `core/recall/vector_store.recall_vectors_database_spec`).

Not owned here: data-directory placement and creation (`storage.md`; `layout.initialize_data_directory` only writes the bootstrap marker through `write_bootstrap_marker`), the CLI/RPC/WebUI operator surfaces (`cli.md`, `server.md`, `webui.md`), and the offline Generation 1 converter (`scripts/converters/persistence_generation_1/`, see References); converters build their outputs with `open_offline_database`, and SQLite areas read their legacy source through `_legacy_sqlite.py` there (read-only open, frozen table and column lists, rowid order, canonical timestamps, refused rows reported).

The Model Usage recorder (`usage.md`, `core/usage/_schema.usage_database_spec`)
owns canonical `model_usage` at `model-usage.db`. It is registered by Runtime and
offline tooling alongside the existing databases, so snapshots and recovery
retain per-request consumption independently of Session deletion.

## Terms

Core terms (Session, Run, Runtime) live in `.vorch/GLOSSARY.md`.

### Format generation
The incompatible-format counter of one database, stored in `PRAGMA user_version`, `kernel_meta.format_generation` and the marker entry. Generation 1 is current. Within a generation only additive changes happen; a new generation needs an explicit offline converter.

### Migration ledger
The `kernel_migrations` table: one row per applied named data migration with `applied_at`, `applied_by_version` and `breaks_older`. It replaces ad-hoc version keys in owner tables.

### Retired index
An index a spec no longer declares and lists in `retired_indexes`; the kernel drops it on open. The only object the kernel ever drops, because an index is derived data.

### Canonical / disposable profile
Canonical: authoritative data, registered in `data-store.json`, `synchronous=FULL`, included in data snapshots, quarantined and auto-restored on corruption (never on a schema mismatch). Disposable: a rebuildable projection with `kernel_meta.projection_version`, `synchronous=NORMAL`; a version mismatch, foreign/newer file or corruption discards the file with its sidecars and rebuilds it empty. Busy or locked is unavailable in both profiles and never grounds to discard or quarantine.

### Data snapshot
A verified copy of the durable data: `<data-dir>/snapshots/<YYYYmmddTHHMMSSZ-uuid8>/` with one `<name>.db` member per canonical database registered in the marker, the JSON document set under `documents/<relative path>`, and a `manifest.json` (see Data Model). Not a Session-only backup. Databases restore per member; the documents restore only as one set.

### JSON document set
Every existing file matching `core.json_documents.SNAPSHOT_DOCUMENTS`: the Generation 1 documents of `DURABLE_DOCUMENTS` except blob sidecars (`settings.md` -> JSON Document Contract), captured as one snapshot member. Symbolic links, Windows junctions and names starting with `.` are never members. `.env`, databases, logs, workspaces and other data-directory files are outside it.

### Update snapshot
The data snapshot an updater takes for one update operation, offline after the previous server stopped: manifest `reason` `update <operation-id>`, bound in memory to a stamp of the data (`update_rollback.UpdateSnapshot`). Only this snapshot may be restored automatically, and only after that operation's candidate failed its verification start.

## Evolution contract (Generation 1)

This is the engineering contract behind the PROJECT.md "Persisted formats are stable" convention.

1. Additive schema changes apply automatically on open: new tables, views, indexes, triggers, and new columns that are nullable or have a default (not generated, not part of the primary key). The reconciler diffs the declared DDL against the live database and applies the missing objects plus pending migrations in one `BEGIN IMMEDIATE` transaction; an up-to-date database needs no write transaction.
2. Forbidden within a generation: renaming, retyping or dropping columns or tables; changing or adding constraints on an existing table; a NOT NULL column without default; changing an existing index, view or trigger definition. A changed object gets a new name. The reconciler never drops or rewrites objects and fails closed with `DatabaseSchemaMismatchError` when a live object with the same name differs, when a planned addition fails on the existing rows (a UNIQUE index over duplicates) or when a declared table or view cannot be read; the error names the database, the object and the difference and states the additive rule. It is a `DatabaseFormatError`: the file is intact, so it is never quarantined or replaced from a snapshot. An invalid declaration is a programming error (`ValueError`). Extra live columns, tables and objects are tolerated: a newer vBot may have added them.
3. Data migrations are `Migration(name, breaks_older=False, apply=None)` steps with stable append-only names (`[a-z0-9][a-z0-9_.-]*`, e.g. `sessions.0003_backfill_x`). `apply` must be idempotent and may only fill new structures or NULLs; it runs after the reconcile inside the same transaction. A freshly created database records every declared migration as applied without running it.
4. `breaks_older=True` is required when older code would misread the data (a new role or enum value, a changed meaning); a marker migration without `apply` is enough. An older vBot that finds an unknown ledger row with `breaks_older=1` refuses to open with `DatabaseFormatError` and never quarantines; recovery is the pre-update data snapshot. A release that ships such a migration (core or bundled Extension) says so in its GitHub release notes: the database it affects and that older versions refuse it from then on (`.vorch/workflows/release-workflow.md` -> Data-compatibility notice).
5. SQL names its columns. Runtime reads under `core/`, `server/` or `resources/extensions/` use no `SELECT *` and no `alias.*`. Every `INSERT` or `REPLACE` under those packages, `cli/` and `scripts/converters/` lists its columns, because an older binary's positional insert fails once a table gains a column; only tables in the connection-private `temp` schema (`temp.` qualified or created `CREATE TEMP TABLE` in the same file) are exempt. `tests/core/database/test_named_columns.py` enforces both: it scans every string literal (f-string text included) and fails on any implicit read or write; there is no allowlist.
6. A generation change is a destructive offline conversion run by the updater or CLI under a data snapshot and the maintenance guard. Normal startup never converts. A canonical database with an older generation, and an existing data directory without a marker (what every pre-Generation-1 directory looks like), raise `DatabaseConversionRequiredError` (a `DatabaseFormatError` with `data_dir`, `database` and `converter_command`); its message names `python -m scripts.converters.persistence_generation_1 <data-dir>` (`GENERATION_1_CONVERTER_COMMAND`), says that it runs from a vBot source checkout because installed builds do not ship `scripts/`, and points to USAGE.md -> "Converting an existing data directory". That next step is `generation_1_conversion_hint(data_dir=None)` (`errors.py`, `<data-dir>` without a directory); `data_store_status` of an existing directory without a marker and the JSON Document Contract's missing-`format_version` diagnostic (`core/json_documents.py`) end with the same text. A newer generation raises a plain `DatabaseFormatError`. App code knows only the current generation. The conversion into Generation 1 has no data snapshot to take (its source has no marker); it moves every file it replaces to `pre-generation-1/` instead.

Schema design rules for every Generation 1 table and later addition: no enum CHECK constraints on extensible vocabularies (roles, kinds, statuses, causes; CHECK stays for permanent invariants such as `>= 0`, `json_valid`, paired nullability); hot tables stay narrow with large payloads in 1:1 side tables; integer surrogate keys for internal relations; JSON only for genuinely open payloads; content-addressed storage for large repeated values; timestamps as fixed-width UTC text `YYYY-MM-DDTHH:MM:SS.ffffffZ`, whose one owner is `core/utils/timestamps.py` (`format_canonical_timestamp`, `parse_timestamp`, `canonical_timestamp`, `utc_now_timestamp`; aware values only, a value without an offset raises; readers of stored values use `parse_canonical_timestamp`, which raises on any non-canonical form because that can only be bad data, or `is_canonical_timestamp` when validating a whole record; `parse_timestamp` stays for incoming values such as CLI or RPC arguments) - the kernel, Stores and Extensions use it instead of private copies, and SQL compares stored timestamps as canonical text, never through `julianday()`; `AUTOINCREMENT` where a key feeds a derived index or projection; every index has a named reader; growing values are appended as chunk rows, never rewritten.

## Data Model

- Kernel tables in every database: `kernel_meta(key, value)` (`database_id`, `database_name`, `format_generation`, `created_at`, `created_by_version`, and `projection_version` for disposable databases) and `kernel_migrations(name, applied_at, applied_by_version, breaks_older)`, both STRICT. `PRAGMA application_id` comes from `APPLICATION_IDS` (one id per owner; Extensions share one).
- Names: `lower_snake` for core owners, `ext.<owner>.<name>` for Extensions. Canonical paths are fixed by name (`canonical_database_path`): `sessions` -> `sessions.db`, `decisions` -> `decisions.db`, `provider_usage` -> `provider-usage.db`, `channels` -> `channels.db`, `ext.<owner>.<name>` -> `extension-data/<owner>/<name>.db`.
- The marker, snapshot manifests and incident records evolve additively like the databases: readers require the known fields, ignore unknown ones, and refuse a marker `format_version` or manifest `manifest_version` other than 1 (incidents carry no version); a record that is rewritten keeps the unknown fields it read, so an older vBot never drops what a newer one added.
- `<data-dir>/data-store.json`: `{"format_version": 1, "databases": {"<name>": {"database_id": "<32 hex>", "format_generation": N}}}`, written atomically; register and unregister keep unknown fields at the top level and in every entry (`DataStoreMarker.unknown_fields`, `MarkerEntry.unknown_fields`). `data-maintenance.json` (`operation_id`, `operation`, `started_at`, `pid`) exists while an offline operation is incomplete. `data-store.lock` is the OS-owned operation lock (msvcrt/flock on an open descriptor; crash-released, never broken by age).
- Snapshot manifest (`manifest_version` 1) members record identity, generation, applied migrations, size, SHA-256, `quick_check`/`foreign_key_check` results and owner facts. The required `documents` key maps each document's relative POSIX path to `{file_size, sha256}` (`{}` when none existed); a manifest without it is not a snapshot. A manifest is written once and never rewritten; another `manifest_version` is not a snapshot, and a document path outside the current `SNAPSHOT_DOCUMENTS` (a document kind a newer vBot added) is ignored: never verified, counted, restored or removed. Document copies keep their source's permission bits (OAuth token files hold credentials). Attempt health: `snapshots/health.json`. Incidents: `<data-dir>/incidents/<name>.json`, `pending` before anything is replaced, `ok` once the restored file verified; completing or acknowledging one keeps unknown fields at the top level and in `possible_loss_interval`. Quarantine: `<data-dir>/quarantine/<name>/<YYYYmmddTHHMMSS>-<uuid8>/` holding the database file plus sidecars, and `quarantine/json-documents/<stamp>-<id>/<relative path>` holding documents a set restore replaced or removed; never deleted automatically (`json-documents` can never be a database name).

## Interfaces

- Declarations (`spec.py`): `DatabaseSpec(name, path, profile, application_id, format_generation, schema_sql, migrations=(), retired_indexes=(), after_open=None, snapshot_facts=None, health=None, projection_version=None, connection_setup=None)`; `connection_setup(connection)` runs on the writer and every pooled reader before any other statement (the vector index loads sqlite-vec there) and must not write; `Migration`; `SnapshotFacts(queries)` (fact name -> SQL returning one integer, recorded per member and recomputed on verification); `DatabaseHealth(state, reason=None, details={})` returned by `health(connection)` for status.
- Opening: `open_database(spec) -> Database` applies the profile rules; `open_offline_database(spec)` creates or opens a canonical file anywhere without marker, guard, registration or restore (converters, staging, tests).
- Disposable owners at runtime (`disposable.py`): `DisposableDatabase(spec)` opens lazily (`get()`, `get_async()` opens off the Event Loop), `discard()` closes the handle and deletes the files so the next `get()` rebuilds empty (refused while another handle in this process has the file open; `discard_async()` runs it off the Event Loop), `close()` ends it. It keeps one worker pool for its whole life: `run_async`, `get_async`, `discard_async` and every handle `get()` opens (rebuilds included) share it, and `close()` shuts it down, so later async work raises `DatabaseUnavailableError` (`is_closed()` reports it). `projection_failure(error)` classifies an operation failure as `busy` (contention; retry later), `unavailable` (permission, disk, I/O, closed or still-open handle), `rebuild` (classified corruption, identity/format/schema failures, and any other SQLite failure of the owner's own statements such as a missing table or violated constraint) or `None` (API misuse, non-SQLite exceptions: propagate). Only `rebuild` grounds `discard()`.
- `Database`: `read()` (context manager, one read transaction), `write(op, *, patience_s=20.0)` (one `BEGIN IMMEDIATE` transaction with jittered busy retry), `read_async`/`write_async`/`run_async` on the database's own `BoundedWorkerPool` (8 workers, threads `vbot-db-<name>_N`; a closed database raises `DatabaseUnavailableError`); owners route all blocking work that uses the database, not only single transactions, through `run_async` instead of `asyncio.to_thread` or a private pool (a step touching two databases becomes one hop per database; work that is mostly file or network I/O with only incidental database access may keep its own pool when the owning map says why, e.g. `projects/resolution.md`), `backup(dest, *, cancelled) -> bool`, `checkpoint()`, `verify_read_write()`, `health()`, `close()`, plus `name`, `path`, `database_id`, `data_dir`, `spec`, `writer` (diagnostics/tests only).
- Snapshots and recovery: `create_data_snapshot(data_dir, *, reason, databases=(), specs=(), cancelled=None) -> Path | None`; `restore_data_snapshot(data_dir, snapshot_dir, *, specs=(), names=None, documents=False, retire_unlisted=False, cause=..., check_only=False) -> SnapshotRestore(snapshot_id, databases, documents, retired, registered)` (`names=None` selects every member; `documents` adds the JSON document set; `retire_unlisted`, only with every member, quarantines and unregisters databases registered after the snapshot; a selected member whose name is no longer registered is installed and registered again with the snapshot's identity (`registered`), while one registered under another identity is refused; nothing selected is `ValueError`); `unregister_database(data_dir, name) -> UnregisteredDatabase(name, database_id, quarantine)` releases one Extension database (see Conventions); `describe_missing_databases(data_dir, marker) -> str | None`; `acknowledge_incident(data_dir, incident_id) -> bool` (raises `IncidentConflictError` when a newer incident replaced the observed one); `list_data_snapshots`, `snapshot_summaries`, `read_verified_manifest`, `read_snapshot_health`, `active_incidents`.
- Update rollback (`update_rollback.py`): `create_update_snapshot(data_dir, *, operation_id, specs=()) -> UpdateSnapshot | None` (`None` when no database is registered; raises `DatabaseError` when it cannot be taken or the data changed during capture); `data_changed_since(data_dir, snapshot) -> str | None`; `restore_update_snapshot(data_dir, snapshot, *, specs=(), cause=UPDATE_ROLLBACK_CAUSE) -> SnapshotRestore`; `find_update_snapshot(data_dir, operation_id) -> str | None`. The caller proves that no server runs on the data directory; the module proves the data side.
- Status: `data_store_status(data_dir, *, databases=(), specs=())` -> one overall state (`maintenance` > `unavailable` > `recovered_with_incident` > `degraded` > `snapshot_degraded` > `healthy`), per-database entries with owner health, verified snapshots and unacknowledged incidents. A data directory without a marker is `unavailable`: an existing one with the `DatabaseConversionRequiredError` text, a missing one with the note that starting vBot creates it. It never mutates the data directory.
- Errors (`errors.py`): `DatabaseError` base; `DatabaseUnavailableError` (busy, locked, permission, disk full, transient I/O, a contended operation lock); `DatabaseCorruptError` (classified SQLite corruption `SQLITE_CORRUPT`/`NOTADB`/`FORMAT`, failed `quick_check` or `foreign_key_check`, a missing, foreign or mismatched kernel identity, untrusted snapshot/incident evidence) - the only class that grounds quarantine and automatic restore; `DatabaseFormatError` (unreadable or newer marker, maintenance guard, newer generation, unknown `breaks_older` migration, a failing migration or `after_open` check) and its subclasses `DatabaseConversionRequiredError(problem, *, data_dir, database=None)` (a data directory without a marker or a canonical database of an older generation; see Evolution contract item 6) and `DatabaseSchemaMismatchError(database, object_name, difference)` (a schema the additive reconcile cannot express, see Evolution contract item 2; also a snapshot fact the current spec cannot compute on a member) - never quarantined or restored; `IncidentConflictError`; `UpdateRollbackRefusedError` (an update rollback precondition failed; nothing changed). None inherits a domain error; owners may subclass (`SessionStoreCorruptError`). RPC maps every `DatabaseError`, schema mismatch included, to `domain_error` with the message naming the database and failure kind, and `IncidentConflictError` to `invalid_request` (`server/rpc/error_mapping.py`); the CLI prints the message and fails.
- Runtime composition: `Runtime.canonical_databases()` returns the open handles; `core/runtime/databases.canonical_database_specs(data_dir)` declares them for offline tools: CLI status and restore, and the Windows updater worker's update snapshot and rollback, which run the previous version's code (the code that wrote the data), so owner facts are recorded and verified. The source-checkout updater's offline pre-update snapshot passes none, so it never depends on the checkout's schema shapes. A new canonical owner is added in both places. Extension databases are the exception: `canonical_databases()` includes the open ones, but offline tools have no Extension specs (declaring them would execute Extension code) and verify those members by kernel identity and integrity only. `Runtime.unregister_extension_database(name)` releases an Extension database through the one Extension database coordinator (`ExtensionDatabases.unregister`, `extensions.md`).
- Metrics: `sqlite.<name>.write`, `sqlite.<name>.write_wait` and `sqlite.<name>.read` on the `sqlite` performance Track (`performance.md`).

## Conventions

- Canonical open: the maintenance guard refuses first; no marker is `DatabaseConversionRequiredError`; a listed database that is missing, corrupt (`DatabaseCorruptError` or an unreadable file), or has another identity is auto-restored from the newest verified snapshot member with the same `database_id`, else the error surfaces; a format error or schema mismatch surfaces without quarantine or restore, and the locked re-probe of `auto_restore_if_needed` independently treats a schema mismatch as untouchable, because an older snapshot would silently drop the newer rows; that re-probe also re-reads the marker and restores nothing unless the database is still registered with the expected `database_id`, so an open racing an unregister cannot bring the database back; an unlisted database is created (or an existing unlisted file adopted after full open checks) and registered under the operation lock, so new owners stay additive.
- Every open checks application id, generation, `kernel_meta` and the ledger read-only before the journal policy may touch the file, then reconciles, runs `after_open`, and probes every declared table and view.
- Recovery stages the verified member bytes before it publishes a `pending` incident or quarantines anything; quarantine moves the bundle all-or-rollback, and a failed rollback keeps the moved members and reports their path. An operational verification, copy, quarantine or publication failure stops candidate fallback instead of trying an older snapshot. A retry keeps the original quarantine reference and failure time, and a pending incident finalizes only when the canonical file matches the intended snapshot member. Malformed incident evidence, including a non-canonical timestamp, is corruption, unreadable evidence is unavailability, and the possible-loss interval stays visible until the exact incident is acknowledged.
- Automatic restore uses pending incidents, not the maintenance guard: a crash mid-restore resumes on the next open. It never replaces a database a newer vBot changed and never picks an older snapshot after a newer candidate failed operationally. An operator restore (`restore_data_snapshot`) also holds the maintenance guard; a failed one leaves the guard so Runtime refuses the half-restored directory until a restore completes.
- Snapshot creation copies open databases online through their handle and unopened registered ones from their files, then reads each JSON document whole in one short open, verifies every member and document before atomic publication, and prunes by `SNAPSHOT_KEEP_COUNT` (5) / `SNAPSHOT_KEEP_BYTES` (512 MiB) always keeping the newly published snapshot and never rehashing retained ones. Owner facts are verified only when a matching spec is supplied, and only the facts the member recorded (a member written before a fact was declared still verifies); a recorded fact the spec cannot compute on the copy is a `DatabaseSchemaMismatchError` that makes the member unusable, like damage. Kernel identity checks always apply. A snapshot verifies (and appears in listings) only when every database member and every document does; a per-database restore candidate still needs only its own member. A manifest whose `created_at` is not canonical is malformed (no snapshot), and a snapshot health record without a canonical `observed_at` reads as degraded (`tests/core/database/test_snapshots.py`).
- A registered database without its file is never skipped by a snapshot, because retention would eventually prune the last copies that hold it. Decision: `create_data_snapshot` fails the attempt and records degraded snapshot health with the next step, `create_update_snapshot` and the CLI updater refuse with the same text, and status reports it per database (`missing_database_reason`): a core database is restored on the next start (or by `vbot data-store snapshot restore <id> --database <name> --yes`); an Extension database is restored on its Extension's next open, and when the Extension was removed the operator releases it with `vbot data-store unregister <name> --yes` (RPC `data_store.unregister`).
- `unregister_database` accepts only Extension names (`ext.<extension>.<name>`; a core name or an unregistered one is `ValueError`), refuses during maintenance, while the operation lock is busy, or while this process holds a connection to the file, then moves the bundle to quarantine (none when the file is gone) and drops the marker entry. It writes no incident. Earlier snapshots keep their copy, and a restore of that member registers it again.
- Extension databases open only when their Extension opens them, never during Runtime bootstrap: the owner-bound host behind `host.open_database` is bound when the server lifespan fires Extension startup handlers after `Runtime.start()` (and again after an Extension reload). Bootstrap loads Extensions only outside safe startup modes (`core/runtime/_bootstrap.py`) and the lifespan skips startup handlers there, so a `--verification-only` or test instance never opens, migrates or auto-restores one (`extensions.md` -> Extension databases). Consequences: startup health - a failed open (format error, unknown `breaks_older` migration, schema mismatch, corruption without a usable snapshot) is logged by the fail-open startup handler and the server starts healthy without that Extension's database, while status checks the unopened file by identity and generation only; verification - an updater's candidate verification start never touches Extension databases, so an Extension open failure after an update never triggers the automatic data rollback; auto-restore of a missing or corrupt Extension database happens at its Extension's open; data snapshots copy an open one online and an unopened one from its file, verified by kernel identity and integrity only (no owner facts); manual restore is `vbot data-store snapshot restore <id> --database ext.<owner>.<name> --yes`, offline and without owner compatibility checks or a post-restore open, so the Extension's next open after the restart reconciles and migrates the restored file or refuses it.
- The JSON document set restores only on request: an operator restore that selects it, or the update rollback; corruption auto-restore never touches documents. A set restore makes the in-scope documents exactly the snapshot's: differing or missing ones are installed from verified staged copies, and documents the snapshot does not hold (created after it) are removed. Every replaced or removed document first moves to one quarantine batch (all-or-rollback); unchanged documents are not touched. Apply order under the guard and lock: database members, then retirement, then documents.
- Update rollback (`restore_update_snapshot`) refuses with `UpdateRollbackRefusedError` and changes nothing unless: no maintenance guard exists; the manifest reason names this operation; its member and document hashes equal the ones recorded at capture; every member's `database_id` is still the registered one; and a `check_only` pass of the complete restore succeeds. It then restores every member and the document set and retires databases registered after the snapshot. Capture compares a stamp (marker hash, size and mtime of each registered database file and its `-wal`/`-journal`, document hashes) before and after; an empty journal counts as absent, because a read-only open of a WAL database leaves an empty `-wal`.
- Journal policy is per SQLite build (`required_journal_mode()`): WAL unless the build carries the WAL-reset bug, in which case rollback-journal (DELETE) mode is used and an existing WAL file is never live-downgraded. Packaged Windows runtimes pin a fixed WAL-safe SQLite (`cli/windows-application.md`); source checkouts use the SQLite bundled with their Python.
- Connections: busy timeout 1s at the SQLite level, then the kernel's jittered retry up to the caller's patience. Readers are query-only, open only after the writer has checked identity and reconciled, and form a LIFO pool of 8 permits (60s open retry); page caches are 64 MiB for the writer and 16 MiB per reader. `close()` drains the pool; in-flight worker-pool work fails as unavailable.
- Owners never open their own connections to a kernel database, never commit inside a helper that receives the kernel's connection, and keep domain decisions (e.g. FTS repair) in their `after_open`/`health` hooks.

## Constraints & Gotchas

- Rollback-journal mode serves reads on the serialized writer, and `backup()` holds the connection lock for the copy's duration; decode large results after the read transaction ends.
- `backup()` uses one `VACUUM INTO` read transaction (cancellable via a progress handler), never a stepped `Connection.backup`, which restarts on every concurrent commit.
- Quarantine, discard and restore refuse while this process still has a tracked connection to the file (`has_live_connection`); every connection goes through `connect_tracked`.
- The operation lock is per open file description, so it is exclusive across threads of one process as well as across processes.
- `open_offline_database` skips all marker safety; never use it for Runtime paths.
- Residual risk of the update rollback: another vBot server or offline tool that writes to the data directory and exits while the candidate runs is indistinguishable from the candidate, so the rollback discards its writes too. The stamp catches writes before the candidate starts; the updater's server-claim check (`core.utils.server_control.live_server_ports`) catches a server still running at rollback time. An interrupted rollback keeps the maintenance guard, and the automatic path never resumes it: an operator repeats it with `vbot data-store snapshot restore <id> --all --yes`.
