# Database

The shared SQLite kernel (`core/database/`): how every vBot database opens, evolves, stays consistent under concurrency, and is snapshotted and recovered.

## Overview

`core/database/` owns connection policy, schema evolution, the canonical and disposable profiles, the data-store marker and maintenance guard, data snapshots (including their JSON document set, and the member freeze and snapshot barrier that make an online snapshot equal a crash at one instant), quarantine, recovery incidents, automatic restore, the updater's guarded pre-update snapshot rollback, configuration backups, and operator-safe status. An owner declares a `DatabaseSpec` and calls `open_database`; it keeps its own DDL, queries, domain errors and domain semantics. The kernel knows no Session, Channel or Provider concept.

Owners today: the Session store (`sessions.md`, `core/sessions/_store_schema.session_database_spec`), the Decisions store (`model_tasks/decisions.md`, `core/model_tasks/decision_store.decision_database_spec`), the Provider usage history (`providers/usage.md`, `core/providers/usage_history.provider_usage_database_spec`) and the Channel state (`channels.md`, `core/channels/_state_schema.channel_database_spec`), plus Extension databases opened through `host.open_database` (`extensions.md`, `core/extensions/databases.extension_database_spec`). The bundled Swarm Extension is one of them (`extensions/swarm.md`). Disposable owners: the Statistics index (`statistics.md`, `core/statistics/index.statistics_database_spec`) and the one Recall Passage index (`recall.md`, `core/recall/passage_index.passage_index_database_spec`).

Not owned here: data-directory placement and creation (`storage.md`; `layout.initialize_data_directory` only writes the bootstrap marker through `write_bootstrap_marker`) and the CLI/RPC/WebUI operator surfaces (`cli.md`, `server.md`, `webui.md`).

The Model Usage recorder (`usage.md`, `core/usage/_schema.usage_database_spec`)
owns canonical `model_usage` at `model-usage.db`. It is registered by Runtime and
offline tooling alongside the existing databases, so snapshots and recovery
retain per-request consumption independently of Session deletion.

## Terms

Core terms (Session, Run, Runtime) live in `.vorch/GLOSSARY.md`.

### Format generation
The incompatible-format counter of one database, stored in `PRAGMA user_version`, `kernel_meta.format_generation` and the marker entry. Generation 1 is current. Within a generation only additive changes happen; a new generation needs an explicit offline converter.

### Migration ledger
The `kernel_migrations` table: one row per applied named data migration with `applied_at`, `applied_by_version` and `breaks_older`. It replaces ad-hoc version keys in owner tables.

### Retired index
An index a spec no longer declares and lists in `retired_indexes`; the kernel drops it on open. The only object the kernel ever drops, because an index is derived data.

### Canonical / disposable profile
Canonical: authoritative data, registered in `data-store.json`, `synchronous=FULL`, included in data snapshots, quarantined and auto-restored on corruption (never on a schema mismatch). Disposable: a rebuildable projection with `kernel_meta.projection_version`, `synchronous=NORMAL`; a version mismatch, foreign/newer file or corruption discards the file with its sidecars and rebuilds it empty. A version mismatch is the designed upgrade path and logs INFO after the discard; a foreign/newer file, corruption or a missing projection version logs WARNING. Busy or locked is unavailable in both profiles and never grounds to discard or quarantine.

### Data snapshot
A verified copy of the durable data: `<data-dir>/snapshots/<YYYYmmddTHHMMSSZ-uuid8>/` with one `<name>.db` member per canonical database registered in the marker, the JSON document set under `documents/<relative path>`, and a `manifest.json` (see Data Model). Not a Session-only backup. Databases restore per member; the documents restore only as one set.

### JSON document set
Every existing file matching `core.json_documents.SNAPSHOT_DOCUMENTS`: the Generation 1 documents of `DURABLE_DOCUMENTS` except blob sidecars (`settings.md` -> JSON Document Contract), captured as one snapshot member. Symbolic links, Windows junctions and names starting with `.` are never members. `.env`, databases, logs, workspaces and other data-directory files are outside it; configuration backups cover `.env`, Workspace identity files and prompt overrides (Configuration backup).

### Compound mutation
One change that spans a canonical database and durable JSON documents as a unit, such as an Agent rename (Session rows plus `agents/<id>/`). It enters the Runtime's snapshot barrier shared, so an online data snapshot copies it either before or after the whole change (Conventions -> Snapshot consistency). An ordinary write to one database or one document is not one; the member freeze orders those (Capture role).

### Capture role
How an online data snapshot captures one canonical database (`DatabaseSpec.snapshot_capture`). `held` (the default): its writes, like every snapshot document change, wait while a capture freezes the members. `anchor`: the one database that keeps taking writes during the freeze and fixes the instant the snapshot stands for; today `sessions`, so Runs go on. `trailing`: keeps taking writes too and is copied after the freeze ends, so its copy may be newer than the anchor's; only data that stays correct ahead of the anchor may trail; today `model_usage`.

### Configuration backup
A frequent, deduplicated copy of the configuration files (`core/database/config_backups.py`): the JSON document set plus `CONFIGURATION_FILE_PATTERNS` - the data-directory `.env`, `SOUL.md`/`USER.md`/`MEMORY.md` of Workspaces in their default location `agents/<id>/workspace/`, and the global and per-Agent prompt overrides under `prompts/`. Not a data snapshot: it holds no database, the Runtime takes it while it runs, and it restores per file. Workspaces at a custom path, other Workspace files and Skills (own history) are outside it.

### Update snapshot
The data snapshot an updater takes for one update operation, offline after the previous server stopped: manifest `reason` `update <operation-id>`, bound in memory to a stamp of the data (`update_rollback.UpdateSnapshot`). Only this snapshot may be restored automatically, and only after that operation's candidate failed its verification start.

## Evolution contract (Generation 1)

This is the engineering contract behind the PROJECT.md "Persisted formats are stable" convention.

1. Additive schema changes apply automatically on open: new tables, views, indexes, triggers, and new columns that are nullable or have a default (not generated, not part of the primary key). The reconciler diffs the declared DDL against the live database and applies the missing objects plus pending migrations in one `BEGIN IMMEDIATE` transaction; an up-to-date database needs no write transaction.
2. Forbidden within a generation: renaming, retyping or dropping columns or tables; changing or adding constraints on an existing table; a NOT NULL column without default; changing an existing index, view or trigger definition. A changed object gets a new name. The reconciler never drops or rewrites objects and fails closed with `DatabaseSchemaMismatchError` when a live object with the same name differs, when a planned addition fails on the existing rows (a UNIQUE index over duplicates) or when a declared table or view cannot be read; the error names the database, the object and the difference and states the additive rule. It is a `DatabaseFormatError`: the file is intact, so it is never quarantined or replaced from a snapshot. An invalid declaration is a programming error (`ValueError`). Extra live columns, tables and objects are tolerated: a newer vBot may have added them.
3. Data migrations are `Migration(name, breaks_older=False, apply=None)` steps with stable append-only names (`[a-z0-9][a-z0-9_.-]*`, e.g. `sessions.0003_backfill_x`). `apply` must be idempotent and may only fill new structures or NULLs; it runs after the reconcile inside the same transaction. A freshly created database records every declared migration as applied without running it.
4. `breaks_older=True` is required when older code would misread the data (a new role or enum value, a changed meaning); a marker migration without `apply` is enough. An older vBot that finds an unknown ledger row with `breaks_older=1` refuses to open with `DatabaseFormatError` and never quarantines; recovery is the pre-update data snapshot. A release that ships such a migration (core or bundled Extension) says so in its GitHub release notes: the database it affects and that older versions refuse it from then on (`.vorch/workflows/release-workflow.md` -> Data-compatibility notice).
5. SQL names its columns. Runtime reads under `core/`, `server/` or `resources/extensions/` use no `SELECT *` and no `alias.*`. Every `INSERT` or `REPLACE` under those packages and `cli/` lists its columns, because an older binary's positional insert fails once a table gains a column; only tables in the connection-private `temp` schema (`temp.` qualified or created `CREATE TEMP TABLE` in the same file) are exempt. `tests/core/database/test_named_columns.py` enforces both: it scans every string literal (f-string text included) and fails on any implicit read or write; there is no allowlist.
6. A generation change is a destructive offline conversion run by the updater or CLI under a data snapshot and the maintenance guard. Normal startup never converts. A canonical database with an older generation, and an existing data directory without a marker (what every pre-Generation-1 directory looks like, and any existing directory vBot did not create), raise `DatabaseConversionRequiredError` (a `DatabaseFormatError` with `data_dir` and `database`). Pre-Generation-1 data (vBot 0.4.4 and earlier; Generation 1 shipped with 0.4.5) has no converter: its offline converter was deleted once every known data directory was converted (user decision, 2026-10-01). The message ends with `older_format_hint()` (`errors.py`): such data predates the current format and this version cannot use it; start with a fresh data directory, or copy what is needed out with the vBot version that wrote it. `data_store_status` of an existing directory without a marker reports the same refusal text, and the JSON Document Contract's missing-`format_version` diagnostic (`core/json_documents.py`) ends with the same hint. A newer generation raises a plain `DatabaseFormatError`. App code knows only the current generation.

Schema design rules for every Generation 1 table and later addition: no enum CHECK constraints on extensible vocabularies (roles, kinds, statuses, causes; CHECK stays for permanent invariants such as `>= 0`, `json_valid`, paired nullability); hot tables stay narrow with large payloads in 1:1 side tables; integer surrogate keys for internal relations; JSON only for genuinely open payloads; content-addressed storage for large repeated values; timestamps as fixed-width UTC text `YYYY-MM-DDTHH:MM:SS.ffffffZ`, whose one owner is `core/utils/timestamps.py` (`format_canonical_timestamp`, `parse_timestamp`, `canonical_timestamp`, `utc_now_timestamp`; aware values only, a value without an offset raises; readers of stored values use `parse_canonical_timestamp`, which raises on any non-canonical form because that can only be bad data, or `is_canonical_timestamp` when validating a whole record; `parse_timestamp` stays for incoming values such as CLI or RPC arguments) - the kernel, Stores and Extensions use it instead of private copies, and SQL compares stored timestamps as canonical text, never through `julianday()`; `AUTOINCREMENT` where a key feeds a derived index or projection; every index has a named reader; growing values are appended as chunk rows, never rewritten.

## Data Model

- Kernel tables in every database: `kernel_meta(key, value)` (`database_id`, `database_name`, `format_generation`, `created_at`, `created_by_version`, and `projection_version` for disposable databases) and `kernel_migrations(name, applied_at, applied_by_version, breaks_older)`, both STRICT. `PRAGMA application_id` comes from `APPLICATION_IDS` (one id per owner; Extensions share one).
- Names: `lower_snake` for core owners, `ext.<owner>.<name>` for Extensions. Canonical paths are fixed by name (`canonical_database_path`): `sessions` -> `sessions.db`, `decisions` -> `decisions.db`, `provider_usage` -> `provider-usage.db`, `channels` -> `channels.db`, `ext.<owner>.<name>` -> `extension-data/<owner>/<name>.db`.
- The marker, snapshot manifests and incident records evolve additively like the databases: readers require the known fields, ignore unknown ones, and refuse a marker `format_version` or manifest `manifest_version` other than 1 (incidents carry no version); a record that is rewritten keeps the unknown fields it read, so an older vBot never drops what a newer one added.
- `<data-dir>/data-store.json`: `{"format_version": 1, "databases": {"<name>": {"database_id": "<32 hex>", "format_generation": N}}}`, written atomically; register and unregister keep unknown fields at the top level and in every entry (`DataStoreMarker.unknown_fields`, `MarkerEntry.unknown_fields`). `data-maintenance.json` (`operation_id`, `operation`, `started_at`, `pid`) exists while an offline operation is incomplete. `data-store.lock` is the OS-owned operation lock (msvcrt/flock on an open descriptor; crash-released, never broken by age).
- Snapshot manifest (`manifest_version` 1) members record identity, generation, applied migrations, size, SHA-256, `quick_check`/`foreign_key_check` results and owner facts. The required `documents` key maps each document's relative POSIX path to `{file_size, sha256}` (`{}` when none existed); a manifest without it is not a snapshot. A manifest is written once and never rewritten; another `manifest_version` is not a snapshot, and a document path outside the current `SNAPSHOT_DOCUMENTS` (a document kind a newer vBot added) is ignored: never verified, counted, restored or removed. Document copies keep their source's permission bits (OAuth token files hold credentials), read-only included: `_files.fsync_file` syncs a read-only file (on Windows by lifting the read-only bit for the sync and setting it back), the cleanup of a disturbed or failed attempt and retention remove snapshot trees with `remove_tree` (`core/utils/tree_move.py`, read-only aware, never follows links), and a set restore installs each document with its copy's bits (`tests/core/database/test_snapshot_documents.py`). Attempt health: `snapshots/health.json`. Configuration backups (`config-backups/`, `manifest_version` 1): `objects/<sha[:2]>/<sha256>` holds each distinct file content once (mode 0o600), and `backups/<YYYYmmddTHHMMSSZ-hex8>.json` names every file with `{file_size, sha256, mode}` plus `damaged: true` for a JSON document that did not parse as a JSON object; a manifest is written once, unknown fields are ignored, a path outside the current file set (a newer vBot's file) is neither shown nor restored but its object stays referenced (`ConfigBackup.other_objects`), and an unreadable manifest is skipped with one WARNING and stops object garbage collection. Incidents: `<data-dir>/incidents/<name>.json`, `pending` before anything is replaced, `ok` once the restored file verified; completing or acknowledging one keeps unknown fields at the top level and in `possible_loss_interval`. Quarantine: `<data-dir>/quarantine/<name>/<YYYYmmddTHHMMSS>-<uuid8>/` holding the database file plus sidecars, and `quarantine/json-documents/<stamp>-<id>/<relative path>` holding documents a set restore replaced or removed; never deleted automatically (`json-documents` can never be a database name).

## Interfaces

- Declarations (`spec.py`): `DatabaseSpec(name, path, profile, application_id, format_generation, schema_sql, migrations=(), retired_indexes=(), after_open=None, snapshot_facts=None, health=None, projection_version=None, connection_setup=None, snapshot_capture="held")`; `snapshot_capture` is the Capture role (`HELD_CAPTURE`, `ANCHOR_CAPTURE`, `TRAILING_CAPTURE` of type `SnapshotCapture`, exported by `core.database`); `connection_setup(connection)` runs on the writer and every pooled reader before any other statement (the vector index loads sqlite-vec there) and must not write; `Migration`; `SnapshotFacts(queries)` (fact name -> SQL returning one integer, recorded per member and recomputed on verification); `DatabaseHealth(state, reason=None, details={})` returned by `health(connection)` for status.
- Opening: `open_database(spec) -> Database` applies the profile rules; `open_offline_database(spec)` creates or opens a canonical file anywhere without marker, guard, registration or restore (offline conversions, staging, tests).
- Disposable owners at runtime (`disposable.py`): `DisposableDatabase(spec)` opens lazily (`get()`, `get_async()` opens off the Event Loop), `discard()` closes the handle and deletes the files so the next `get()` rebuilds empty (refused while another handle in this process has the file open; `discard_async()` runs it off the Event Loop), `close()` ends it. It keeps one worker pool for its whole life: `run_async`, `get_async`, `discard_async` and every handle `get()` opens (rebuilds included) share it, and `close()` shuts it down, so later async work raises `DatabaseUnavailableError` (`is_closed()` reports it). `projection_failure(error)` classifies an operation failure as `busy` (contention; retry later), `unavailable` (permission, disk, I/O, closed or still-open handle), `rebuild` (classified corruption, identity/format/schema failures, and any other SQLite failure of the owner's own statements such as a missing table or violated constraint) or `None` (API misuse, non-SQLite exceptions: propagate). Only `rebuild` grounds `discard()`.
- `Database`: `read()` (context manager, one read transaction), `write(op, *, patience_s=20.0)` (one `BEGIN IMMEDIATE` transaction with jittered busy retry; on a database registered in a data directory it first passes `member_change`, so a write to a held database may wait while a capture copies), `read_async`/`write_async`/`run_async` on the database's own `BoundedWorkerPool` (8 workers, threads `vbot-db-<name>_N`; a closed database raises `DatabaseUnavailableError`); owners route all blocking work that uses the database, not only single transactions, through `run_async` instead of `asyncio.to_thread` or a private pool (a step touching two databases becomes one hop per database; work that is mostly file or network I/O with only incidental database access may keep its own pool when the owning map says why, e.g. `projects/resolution.md`), `backup(dest, *, cancelled) -> bool` (one consistent copy, not yet synced to disk: the caller makes it durable), `checkpoint()`, `verify_read_write()`, `health()`, `close()`, plus `name`, `path`, `database_id`, `data_dir`, `restore_id` (see Conventions -> Restore identity), `spec`, `writer` (diagnostics/tests only).
- Snapshots and recovery: `create_data_snapshot(data_dir, *, reason, databases=(), specs=(), cancelled=None, barrier=None) -> Path | None`; `restore_data_snapshot(data_dir, snapshot_dir, *, specs=(), names=None, documents=False, retire_unlisted=False, cause=..., check_only=False) -> SnapshotRestore(snapshot_id, databases, documents, retired, registered)` (`names=None` selects every member; `documents` adds the JSON document set; `retire_unlisted`, only with every member, quarantines and unregisters databases registered after the snapshot; a selected member whose name is no longer registered is installed and registered again with the snapshot's identity (`registered`), while one registered under another identity is refused; nothing selected is `ValueError`); `unregister_database(data_dir, name) -> UnregisteredDatabase(name, database_id, quarantine)` releases one Extension database (see Conventions); `describe_missing_databases(data_dir, marker) -> str | None`; `acknowledge_incident(data_dir, incident_id) -> bool` (raises `IncidentConflictError` when a newer incident replaced the observed one); `list_data_snapshots`, `snapshot_summaries`, `read_verified_manifest`, `read_snapshot_health`, `active_incidents`.
- Configuration backups (`config_backups.py`): `capture_config_backup(data_dir, *, reason, barrier=None, now=None) -> ConfigBackup | None` (`None` when the files equal the newest backup; raises `OperationLockBusyError` when the operation lock stays busy for `CONFIG_BACKUP_LOCK_SECONDS`, 5 s); `list_config_backups` (newest first), `read_config_backup`, `describe_config_backup` (per file `same`/`differs`/`missing` against the current file, `damaged`, `created_after`), `config_backup_summary`; `restore_config_backup(data_dir, backup_id, *, paths=None, check_only=False) -> ConfigRestore(backup_id, restored, unchanged, skipped, created_after, before_restore)`; `configuration_fingerprint` (path, size, mtime) for cheap change checks. The Runtime's schedule is `core/runtime/_config_backups.ConfigBackupSchedule` (`runtime.md`); the CLI is `vbot data-store config-backup list|show|restore` (`cli.md`).
- Update rollback (`update_rollback.py`): `create_update_snapshot(data_dir, *, operation_id, specs=()) -> UpdateSnapshot | None` (`None` when no database is registered; raises `DatabaseError` when it cannot be taken or the data changed during capture); `data_changed_since(data_dir, snapshot) -> str | None`; `restore_update_snapshot(data_dir, snapshot, *, specs=(), cause=UPDATE_ROLLBACK_CAUSE) -> SnapshotRestore`; `find_update_snapshot(data_dir, operation_id) -> str | None`. The caller proves that no server runs on the data directory; the module proves the data side.
- Status: `data_store_status(data_dir, *, databases=(), specs=())` -> one overall state (`maintenance` > `unavailable` > `recovered_with_incident` > `degraded` > `snapshot_degraded` > `healthy`), per-database entries with owner health, verified snapshots and unacknowledged incidents, plus `config_backups` (`count`, `latest`, `unreadable`, `reason`), which does not affect the overall state. A data directory without a marker is `unavailable`: an existing one with the `DatabaseConversionRequiredError` text, a missing one with the note that starting vBot creates it. It never mutates the data directory.
- Errors (`errors.py`): `DatabaseError` base; `DatabaseUnavailableError` (busy, locked, permission, disk full, transient I/O, a contended operation lock) and its subclasses `OperationLockBusyError` (the operation lock stayed busy; raised by a configuration backup as expected contention its schedule retries quietly) and `MemberFrozenError` (a change admitted with `wait=False` arrived during a member freeze, Freeze admission); `DatabaseCorruptError` (classified SQLite corruption `SQLITE_CORRUPT`/`NOTADB`/`FORMAT`, failed `quick_check` or `foreign_key_check`, a missing, foreign or mismatched kernel identity, untrusted snapshot/incident evidence) - the only class that grounds quarantine and automatic restore; `DatabaseFormatError` (unreadable or newer marker, maintenance guard, newer generation, unknown `breaks_older` migration, a failing migration or `after_open` check) and its subclasses `DatabaseConversionRequiredError(problem, *, data_dir, database=None)` (a data directory without a marker or a canonical database of an older generation; see Evolution contract item 6) and `DatabaseSchemaMismatchError(database, object_name, difference)` (a schema the additive reconcile cannot express, see Evolution contract item 2; also a snapshot fact the current spec cannot compute on a member) - never quarantined or restored; `IncidentConflictError`; `UpdateRollbackRefusedError` (an update rollback precondition failed; nothing changed). None inherits a domain error; owners may subclass (`SessionStoreCorruptError`). RPC maps every `DatabaseError`, schema mismatch included, to `domain_error` with the message naming the database and failure kind, and `IncidentConflictError` to `invalid_request` (`server/rpc/error_mapping.py`); the CLI prints the message and fails.
- Snapshot barrier (`snapshot_barrier.py`): `SnapshotBarrier(*, capture_wait_seconds=30.0)`; `compound_mutation()` (context manager, blocks while a capture copies: worker threads only), `compound_mutation_async()` (the same for the Event Loop, waits without blocking it), `capture(*, cancelled=None)` (yields `False` when cancelled while waiting, raises `DatabaseUnavailableError` when no quiet moment comes within the wait budget). The member freeze in the same module: `member_change(data_dir, *, held=True, wait=True)` (context manager admitting one change of a member of the resolved `data_dir`; `Database.write` and `core.json_documents.document_change` enter it, owners never call it directly; `wait=False` raises `MemberFrozenError` where the change would wait), `capture_members(data_dir, databases, *, copy_database, copy_documents, discard_copies, barrier=None, cancelled=None, drain_seconds=MEMBER_DRAIN_WAIT_SECONDS) -> MemberCapture | None` (the capture order of `create_data_snapshot`; `databases` maps each member name to its spec or `None`, which counts as held; more than one anchor is `ValueError`; `discard_copies` removes a disturbed attempt's copies before the next), `MemberCapture(held_seconds, waited_changes, attempts)`, `MEMBER_DRAIN_WAIT_SECONDS` (10 s), `CAPTURE_ATTEMPTS` (3).
- Runtime composition: `Runtime.snapshot_barrier` is the one barrier of a Runtime (created with it, kept across restarts) and is injected into `AgentStore`, `ProjectStore` and `CommandDispatcher`; `data_store.snapshot_create` passes it to `create_data_snapshot`. A store constructed without one gets a private barrier no snapshot uses. `Runtime.canonical_databases()` returns the open handles; `core/runtime/databases.canonical_database_specs(data_dir)` declares them for offline tools: CLI status and restore, and the updater worker's update snapshot and rollback, which run the previous version's code (the code that wrote the data), so owner facts are recorded and verified. A new canonical owner is added in both places. Extension databases are the exception: `canonical_databases()` includes the open ones, but offline tools have no Extension specs (declaring them would execute Extension code) and verify those members by kernel identity and integrity only. `Runtime.unregister_extension_database(name)` releases an Extension database through the one Extension database coordinator (`ExtensionDatabases.unregister`, `extensions.md`).
- Metrics: `sqlite.<name>.write`, `sqlite.<name>.write_wait` and `sqlite.<name>.read` on the `sqlite` performance Track (`performance.md`).

## Conventions

- Canonical open: the maintenance guard refuses first; no marker is `DatabaseConversionRequiredError`; a listed database that is missing, corrupt (`DatabaseCorruptError` or a file SQLite cannot read as a database), or has another identity is auto-restored from the newest verified snapshot member with the same `database_id`, else the error surfaces; a file that cannot be checked or opened for an operational reason (permission, I/O, an unresponsive share) is `DatabaseUnavailableError` and is never restored over, because it may hold newer data than any snapshot (the probe in `recovery.py` and `_open_canonical` check presence with `exists_strict`, PROJECT.md -> Conventions -> Filesystem checks); a format error or schema mismatch surfaces without quarantine or restore, and the locked re-probe of `auto_restore_if_needed` independently treats a schema mismatch as untouchable, because an older snapshot would silently drop the newer rows; that re-probe also re-reads the marker and restores nothing unless the database is still registered with the expected `database_id`, so an open racing an unregister cannot bring the database back; an unlisted database is created (or an existing unlisted file adopted after full open checks) and registered under the operation lock, so new owners stay additive.
- Every open checks application id, generation, `kernel_meta` and the ledger read-only before the journal policy may touch the file, then reconciles, runs `after_open`, and probes every declared table and view.
- Recovery stages the verified member bytes before it publishes a `pending` incident or quarantines anything; quarantine moves the bundle all-or-rollback, and a failed rollback keeps the moved members and reports their path. An operational verification, copy, quarantine or publication failure stops candidate fallback instead of trying an older snapshot. A retry keeps the original quarantine reference and failure time, and a pending incident finalizes only when the canonical file matches the intended snapshot member. Malformed incident evidence, including a non-canonical timestamp, is corruption, unreadable evidence is unavailability, and the possible-loss interval stays visible until the exact incident is acknowledged.
- Restore identity: `Database.restore_id` is the `incident_id` of `<data-dir>/incidents/<name>.json` when the canonical database opened (`recovery.latest_restore_id`), `None` without an incident and for offline or disposable handles. A restore keeps `database_id` (the snapshot member carries it) but brings back older content, so a projection or cursor that follows a canonical database keys on both and rebuilds when `restore_id` changes (`usage.md`; for `sessions.db`, Statistics and Recall through `ChatSessionManager.history_id`). Every restore path (automatic, operator, update rollback) publishes a new incident id before quarantine and swap; resuming, completing and acknowledging keep it; incidents are outside snapshots and never pruned. The id therefore changes exactly when a restore began: one that stopped before the swap, or an operator deleting the incident file, changes it without new content, which costs a consumer one extra rebuild, never a stale projection. A file replaced outside the kernel keeps its id; only a consumer's own revision-rewind check notices that (`tests/core/database/test_recovery.py`).
- Automatic restore uses pending incidents, not the maintenance guard: a crash mid-restore resumes on the next open. It never replaces a database a newer vBot changed and never picks an older snapshot after a newer candidate failed operationally. An operator restore (`restore_data_snapshot`) also holds the maintenance guard; a failed one leaves the guard so Runtime refuses the half-restored directory until a restore completes.
- Snapshot creation copies open databases online through their handle and unopened registered ones from their files, and reads each JSON document whole in one short open, in the order of Snapshot consistency; then, after the freeze, it syncs every copy to disk and verifies every member and document before atomic publication, and prunes by `SNAPSHOT_KEEP_COUNT` (5) / `SNAPSHOT_KEEP_BYTES` (10 GiB) always keeping the newly published snapshot and never rehashing retained ones; the byte budget never prunes below `SNAPSHOT_KEEP_MINIMUM` (2) snapshots, so a Session history larger than half the budget still keeps one fallback (decision 2026-10-05: a 2 GB `sessions.db` had left a single snapshot under the former 512 MiB budget). Before copying, a snapshot needs its size plus `SNAPSHOT_RESERVE_BYTES` (64 MiB) of free space; when the disk lacks it, `_make_room` removes the oldest snapshots, never the newest, and logs one INFO line naming them, so retained snapshots never block a new one (and the update that takes it); without enough room even then the attempt fails with `insufficient snapshot reserve`. Owner facts are verified only when a matching spec is supplied, and only the facts the member recorded (a member written before a fact was declared still verifies); a recorded fact the spec cannot compute on the copy is a `DatabaseSchemaMismatchError` that makes the member unusable, like damage. Kernel identity checks always apply. A snapshot verifies (and appears in listings) only when every database member and every document does; a per-database restore candidate still needs only its own member. A manifest whose `created_at` is not canonical is malformed (no snapshot), and a snapshot health record without a canonical `observed_at` reads as degraded (`tests/core/database/test_snapshots.py`).
- Snapshot consistency: an online snapshot shows exactly what a crash at one instant would have left - the start of the anchor copy - and holds every compound mutation whole. `create_data_snapshot` runs `capture_members` after taking the operation lock and verifies the copies after it returns. The capture order:
  1. Barrier: with a `barrier`, the capture takes it exclusively. It waits until no compound mutation is in flight (`capture_wait_seconds`, 30 s), and a compound mutation arriving meanwhile waits until step 4.
  2. Freeze: it stops admitting held changes of the data directory - writes of held databases and every write, removal or move of a snapshot document - and waits until those in flight have finished (`MEMBER_DRAIN_WAIT_SECONDS`, 10 s). That is the freeze instant.
  3. Copies: the held databases in name order, then the JSON document set, then the anchor. Anchor and trailing writes never wait, so Runs keep committing.
  4. Thaw: held changes and compound mutations enter again; then the trailing databases are copied.
- Why restoring a whole snapshot is crash-equivalent: no held member changes between the freeze instant and the anchor copy, and the anchor copy is one `VACUUM INTO` read transaction whose view is fixed when it starts (in rollback-journal mode the copy holds the connection lock, so no write lands during it). Every held member, every document and the anchor therefore show the data at the start of the anchor copy, and a crash then would have left the same files, since canonical commits are durable. A compound mutation never overlaps the freeze, because step 1 drains and blocks them for the whole capture, so the document moves and removals inside one need no document gate. A trailing copy may be newer than that instant: harmless for `model_usage`, whose rows are keyed by `usage_call_id` and whose recorder replays the whole Session history for every new Session handle (`import_session_history`).
- Freeze admission: the freeze state is process-wide and keyed by the resolved data directory (the named exception in PROJECT.md -> Conventions -> Dependency injection): it guards files, so every owner, standalone store and offline tool of the process meets the same freeze and none can miss it by not being handed an object. `Database.write` gates writes of every database registered in a data directory (offline and disposable handles are never gated), `core.json_documents.write_json_document` gates every document write, and owners wrap document removals and moves outside compound mutations in `document_change` (`settings.md` -> JSON Document Contract). A held change never waits where waiting could stall or deadlock: on an Event Loop thread, and on a thread already inside a change of the same data directory (a document written inside a database transaction, a held write inside a Session write). Such a change enters at once; entering after the freeze instant would make the copies disagree, so the capture discards its copies and starts over from step 1, at most `CAPTURE_ATTEMPTS` (3) attempts in all. A waiting change keeps every lock its thread holds, so an owner whose lock Event Loop code takes admits its change before taking the lock (`document_change` first, then the lock), and a change it makes under that lock without such an admission - a read that repairs what it finds - passes `document_change(path, wait=False)`: where it would wait it raises `MemberFrozenError`, and the owner gives the lock up, admits with waiting and repeats the read (`AgentStore`, `agent.md`). Failures are `DatabaseUnavailableError` and record degraded snapshot health: a drain that does not finish in time ("a data change was still in progress; retry the snapshot once it has finished"), a change during the freeze of every attempt ("the data changed in a way the snapshot cannot hold while it was taken; retry the snapshot"), and a second capture of the same directory in this process ("another data snapshot of this directory is running").
- Freeze cost: held writes pause from the freeze instant until the anchor copy ends (`held_ms` in the INFO line). That time is dominated by copying `sessions.db` and grows with its size; measured on an SSD with one small held database: about 55-90 ms up to 10 MB, 230 ms at 50 MB, 0.8 s at 200 MB and 2.1 s at 500 MB, roughly 4 ms per MB. A Session write never pauses; async callers of a held database pause on its worker pool, never on the Event Loop.
- Barrier holders: a compound mutation arriving while a capture only waits still enters, so nested entries (the Identity Agent rename around `AgentStore.rename`, a Project archive around `ProjectStore.archive_files`) cannot deadlock; the price is that steady overlapping mutations can starve a capture, which then fails after `capture_wait_seconds` with degraded snapshot health. Holders never wait for what a capture holds: they enter the barrier before any store lock and outside database transactions, never take the operation lock, and stay short. The blocking `compound_mutation()` belongs off the Event Loop, since a capture can hold it for a whole copy; the one entry on the loop is `ensure_bootstrap` in Runtime bootstrap, which runs before the server serves any request and so never meets a capture. A thread inside a change must not wait for a held change on another thread: the freeze could not finish before its budget ends. Offline snapshots (`create_update_snapshot`, the CLI updater with the server stopped) pass no barrier and find no change in flight. Covered compound mutations: `AgentStore.create`/`rename`/`revert_rename`/`recover_rename`/`archive_files`/`restore_files`, the whole Identity Agent rename with its reference retargeting and revert (`core/runtime/_agent_rename.py`), `ProjectStore.archive_files`/`restore_files`, the archive service's Agent and Project archive and restore (the Project archive with the reset of the Agents whose default Project it is; `archive.md`), `/agent` takeover (Session move plus both current-Session pointers) and a Session archive (`session.delete`: archive plus current-pointer re-aim). An archive purge holds none: each Session delete is its own transaction, and a `purging` entry continues where it stopped. A new owner operation that changes the anchor and a held member as one unit enters the barrier too, and a new canonical owner declares its Capture role (held unless it must keep writing during a capture and stays correct ahead of the anchor) (`tests/core/database/test_snapshots.py`, `tests/server/rpc/test_agent_methods_lifecycle.py`).
- A registered database without its file is never skipped by a snapshot, because retention would eventually prune the last copies that hold it. Decision: `create_data_snapshot` fails the attempt and records degraded snapshot health with the next step, `create_update_snapshot` and the CLI updater refuse with the same text, and status reports it per database (`missing_database_reason`; a file that exists but cannot be checked is reported as such, never as missing): a core database is restored on the next start (or by `vbot data-store snapshot restore <id> --database <name> --yes`); an Extension database is restored on its Extension's next open, and when the Extension was removed the operator releases it with `vbot data-store unregister <name> --yes` (RPC `data_store.unregister`).
- `unregister_database` accepts only Extension names (`ext.<extension>.<name>`; a core name or an unregistered one is `ValueError`), refuses during maintenance, while the operation lock is busy, or while this process holds a connection to the file, then moves the bundle to quarantine (none when the file is gone) and drops the marker entry. It writes no incident. Earlier snapshots keep their copy, and a restore of that member registers it again.
- Extension databases open only when their Extension opens them, never during Runtime bootstrap: the owner-bound host behind `host.open_database` is bound when the server lifespan fires Extension startup handlers after `Runtime.start()` (and again after an Extension reload). Bootstrap loads Extensions only outside safe startup modes (`core/runtime/_bootstrap.py`) and the lifespan skips startup handlers there, so a `--verification-only` or test instance never opens, migrates or auto-restores one (`extensions.md` -> Extension databases). Consequences: startup health - a failed open (format error, unknown `breaks_older` migration, schema mismatch, corruption without a usable snapshot) is logged by the fail-open startup handler and the server starts healthy without that Extension's database, while status checks the unopened file by identity and generation only; verification - an updater's candidate verification start never touches Extension databases, so an Extension open failure after an update never triggers the automatic data rollback; auto-restore of a missing or corrupt Extension database happens at its Extension's open; data snapshots copy an open one online and an unopened one from its file, verified by kernel identity and integrity only (no owner facts); manual restore is `vbot data-store snapshot restore <id> --database ext.<owner>.<name> --yes`, offline and without owner compatibility checks or a post-restore open, so the Extension's next open after the restart reconciles and migrates the restored file or refuses it.
- Configuration backups: a capture refuses during maintenance, takes the operation lock (so it never overlaps a data snapshot or restore) and reads the files through `capture_members` with no database, so with the Runtime's barrier its JSON documents agree like a snapshot's; it stores objects before the manifest and is skipped when nothing differs from the newest backup. Retention after each capture keeps the newest `CONFIG_BACKUP_KEEP_LATEST` (10) plus the newest backup of every hour for 48 hours, every day for 30 days and every ISO week for 52 weeks, so a burst of bad states cannot push good ones out; it then removes objects no manifest references. A damaged JSON document is backed up and marked, never restored. A restore is offline (the CLI stops and restarts the server): it verifies every needed object first (`DatabaseCorruptError` for a missing or altered copy), takes a `before restore <id>` backup of the current state, then holds the maintenance guard (`config restore <backup-id>`) while it writes each selected file atomically. An interrupted restore keeps the guard; while it stands every other restore is refused, and repeating that restore (`ConfigRestore.interrupted`) reuses the earlier before-restore backup and ends the guard even when every file already matches, since the attempt may have failed after its last write. It never removes a file: files created after the backup stay, and a file whose folder no longer exists (a deleted or renamed Agent, Project or Channel) or that is damaged is refused when named and skipped by a full restore (`tests/core/database/test_config_backups.py`).
- The JSON document set restores only on request: an operator restore that selects it, or the update rollback; corruption auto-restore never touches documents. A set restore makes the in-scope documents exactly the snapshot's: differing or missing ones are installed from verified staged copies, and documents the snapshot does not hold (created after it) are removed. Every replaced or removed document first moves to one quarantine batch (all-or-rollback); unchanged documents are not touched. Apply order under the guard and lock: database members, then retirement, then documents.
- Update rollback (`restore_update_snapshot`) refuses with `UpdateRollbackRefusedError` and changes nothing unless: no maintenance guard exists; the manifest reason names this operation; its member and document hashes equal the ones recorded at capture; every member's `database_id` is still the registered one; and a `check_only` pass of the complete restore succeeds. It then restores every member and the document set and retires databases registered after the snapshot. Capture compares a stamp (marker hash, size and mtime of each registered database file and its `-wal`/`-journal`, document hashes) before and after; an empty journal counts as absent, because a read-only open of a WAL database leaves an empty `-wal`.
- Journal policy is per SQLite build (`required_journal_mode()`): WAL unless the build carries the WAL-reset bug, in which case rollback-journal (DELETE) mode is used and an existing WAL file is never live-downgraded. The policy logs one INFO line per process (SQLite version, reason), not one per database; each existing WAL database kept on such a build logs a WARNING once per process. Packaged Windows runtimes pin a fixed WAL-safe SQLite, and the Linux package build refuses a runtime whose SQLite is not WAL-safe (`cli/application.md`); development interpreters must match them, which `scripts/push.py` and the performance scripts check (PROJECT.md -> Development -> Setup).
- Connections: busy timeout 1s at the SQLite level, then the kernel's jittered retry up to the caller's patience. Readers are query-only, open only after the writer has checked identity and reconciled, and form a LIFO pool of 8 permits (60s open retry); page caches are 64 MiB for the writer and 16 MiB per reader. `is_closed()` observes the monotonic closed flag without taking the transaction lock, so async admission and cached disposable handles never block the Event Loop behind a writer. Connection access still checks closure under its lock. `close()` keeps writer closure serialized with the current transaction and releases pooled connections; work that later reaches a closed handle fails as unavailable. The test seam `SYNCHRONOUS_OVERRIDE` (`core/database/database.py`) replaces both profiles' `synchronous` levels wherever the kernel opens a database; the test suite sets `OFF` (PROJECT.md -> Testing -> Disk syncs). A new database is built in a temporary file with `synchronous=OFF`, then fsynced once and published under its name by an atomic rename, so building it syncs only once.
- Transaction control: every kernel connection opens with `isolation_level=None` under Python's legacy transaction control (`sqlite3.LEGACY_TRANSACTION_CONTROL`, the `autocommit` default through Python 3.14), and the kernel issues its own `BEGIN IMMEDIATE`/`BEGIN`: a statement outside an explicit transaction commits on its own, and `commit()` does nothing unless an explicit `BEGIN` is open. `write` and `read` own their transactions; `after_open(writer)` runs after the reconcile outside any transaction, so a hook step of several statements opens its own `BEGIN IMMEDIATE` and rolls back on failure (`core/sessions/_store_fts.py`, `core/recall/passage_index._prepare_fts`), never relying on `commit()`. `autocommit=True` is the forward spelling and behaves alike, except that `commit()` no longer ends an explicit `BEGIN`; under `autocommit=False` `isolation_level` has no effect and every explicit `BEGIN` fails, so a Python version change checks the `autocommit` default (`development.md` -> Python version).
- Logging (`vbot.database`, policy in `logging.md`): a published data snapshot logs INFO (snapshot id, database and document counts, reason, and `held_ms`, `waited_changes` and `attempts`: how long held changes were frozen over all attempts, how many waited, and how many attempts the capture needed). Snapshot health logs WARNING when it becomes degraded or its reason changes, a repeated identical failure only DEBUG, and the first healthy attempt afterwards INFO; the transition compares against the durable `health.json`, so it spans restarts. An automatic restore, and the completion of an interrupted one, logs ERROR with database, snapshot, quarantine path and cause, because data written after the snapshot may be lost; a failed automatic restore logs ERROR with its traceback, since the opener only learns that nothing was restored. An operator or update-rollback restore logs one INFO line (snapshot, databases, documents, retired, registered, cause), unregister one INFO line with its quarantine path. A configuration backup logs one INFO line (backup, files, changed, reason) and a WARNING naming damaged documents; a configuration restore one INFO line with the before-restore backup. Quarantine has no line of its own: the restore or unregister line names it, and the incident keeps it. Schema evolution logs INFO once per open that changed something.
- Owners never open their own connections to a kernel database, never commit inside a helper that receives the kernel's connection, and keep domain decisions (e.g. FTS repair) in their `after_open`/`health` hooks.

## Constraints & Gotchas

- Rollback-journal mode serves reads on the serialized writer, and `backup()` holds the connection lock for the copy's duration; decode large results after the read transaction ends.
- `backup()` uses one `VACUUM INTO` read transaction (cancellable via a progress handler), never a stepped `Connection.backup`, which restarts on every concurrent commit.
- Quarantine, discard and restore refuse while this process still has a tracked connection to the file (`has_live_connection`); every connection goes through `connect_tracked`.
- The operation lock is per open file description, so it is exclusive across threads of one process as well as across processes.
- `open_offline_database` skips all marker safety; never use it for Runtime paths.
- Limits of the online snapshot guarantee:
  - A held change on the Event Loop disturbs an overlapping capture attempt instead of waiting, which costs a retry (Freeze admission). Channel state, Cron and Calendar action edits and Project edits write off the loop. Writers still on the loop while serving, because their owner has no off-loop write path yet: Settings (`settings.json` from the Settings, task-Model and Provider Connection RPCs; every loop Settings read takes the lock these writes hold, so the writers can only move off the loop together with those reads), Calendar events (`calendar/events.json` from RPC and the Calendar Tool), Bootstrap jobs (`bootstrap/jobs.json` from RPC and the activation task), OAuth tokens (refresh, device-flow login and disconnect share one lock, so they move together), Terminal groups and launch history, an Agent read-time repair on a loop reader, the first Cron or Calendar load of a `--test-instance` process that creates a missing document, and Extensions that call the synchronous `Database.write` on the loop. Startup writers on the loop (`ensure_bootstrap`, Channel adoption, the decision store interrupting unfinished decisions) never meet a capture: online captures come only from `data_store.snapshot_create`, which the server serves after startup.
  - A worker thread waiting at the gate keeps the locks it holds. `AgentStore` and `ProjectStore`, whose locks Event Loop reads take, admit every change before the lock (Freeze admission), and the other owner locks held across a document write (`StorageManager`'s Settings lock, `TokenStore`'s mutation lock) are taken only on the Event Loop, where a change never waits; a writer of theirs moved to a worker needs the same admission-first order. Database work queued behind pool workers that wait at the gate still waits for the capture.
  - Only this process's changes are frozen; another process writing the data directory is not covered, and an unopened database is copied from its file.
  - Restoring single members mixes instants by design: a per-database restore (`--database <name>`) and the automatic restore of a missing or corrupt database each install one member, the newest verified snapshot member with the same `database_id`, beside newer live members and documents, and automatic restore never touches documents. Only a restore of every member together with the document set reproduces the snapshot's instant.
  - Crash equivalence makes every crash window of a multi-step change outside a compound mutation capturable, so such a change must leave only states that repair themselves or strand no data. Examples: creating a Session and pointing an Agent's current pointer at it (`/handoff`, `session.create` with `make_current`, a `chat.send`/`chat.stream` for a new Session) leaves at worst a dangling pointer, which the next read clears (the Agent then opens a new conversation; no Session is created for it); for Channel create/delete (`channel.json` plus its `channels.db` rows), startup adoption registers a configured Channel whose row is missing, and rows a deleted Channel left behind stay unused until a re-created id resets them; a Telegram chat migration bridges the conversation before it persists the allowlist (`channels/telegram.md`); Swarm Resume records every participant Session again, including one a failed or interrupted Start created without recording it (`extensions/swarm.md`).
- Residual risk of the update rollback: another vBot server or offline tool that writes to the data directory and exits while the candidate runs is indistinguishable from the candidate, so the rollback discards its writes too. The stamp catches writes before the candidate starts; the updater's server-claim check (`core.utils.server_control.live_server_ports`) catches a server still running at rollback time. An interrupted rollback keeps the maintenance guard, and the automatic path never resumes it: an operator repeats it with `vbot data-store snapshot restore <id> --all --yes`.

Tests: `tests/core/database/` (`test_database_runtime`, `test_database_evolution` incl. the older-binary simulation, `test_database_profiles`, `test_marker`, `test_snapshots` incl. an online snapshot while another thread keeps writing, the snapshot barrier, the member freeze (capture order; a held write waits until the anchor is copied while an anchor write proceeds; a document change nested in an in-flight write never waits; one admitted with `wait=False` is refused) and Event Loop writes disturbing a capture, which is retried a bounded number of times, `test_snapshot_documents`, `test_config_backups`, `test_recovery`, `test_update_rollback`, `test_status`, `test_named_columns`); Session integration in `tests/core/sessions/test_store_database.py`.
