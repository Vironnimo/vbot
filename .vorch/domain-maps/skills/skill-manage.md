# skill_manage Tool

How the `skill_manage` Tool (`core/tools/skill_manage.py`) resolves its targets, repairs and refuses calls, matches patches, changes global Skills, publishes, follows merges and guards background writers, plus the bundled `skill-writing` Skill whose limits its hints check. Domain-wide write rules and vocabulary: `skills.md` -> Authoring & Write Scope and Terms; how writes are recorded: `skills/history.md`.

## Targets

- **Agent Tool `skill_manage`** (always registered, not gated on owning a Skill): one open flat object requiring `action` + `name` (fields and repair: Calls); actions are create/edit/patch/write_file/remove_file/delete/publish. Agent authoring targets the private home by default: every mutation targets the home of the calling Identity Agent (in a Librarian Session, of the Agent it maintains: `tools/skill.md` -> Skill subject), invalidates its registry, reports the change through the handler's `on_changed` after that invalidation (Runtime wires `SkillRuntime.notify_changed`), and emits one content-free control-plane log event. The single exception is **shared-target resolution**: a name not the caller's own but resolving to a shared instance lets update actions (edit/patch/write_file/remove_file) operate on the owner's package and invalidate all agent-aware registries, while create/delete refuse non-own targets. The Result reads identically for both, and the Tool description intentionally never mentions sharing - receivers discover editability through use, not provenance wording. The second exception is the **global home**: attended Agents update its packages and publish into it (Calls -> Global Skills, `publish`); folder, Extension, Project/repo and bundled Skills are never Agent Tool targets. `skill_manage` carries the declarative `identity_agent` constraint: withheld from Config/Project Agents at visibility and dispatch, excluded from the Project Tool Whitelist by Projects-owned metadata.
- **`/learn`**: user-triggered Run whose visible message is the user's command, with an authoring brief as the note before it, using `skill_manage` into the current agent's home (see `chat/commands.md`). The brief checks current catalog and complete target files, prefers a fitting private Skill update, and accepts an unchanged outcome when the source adds no supported reusable learning. It does not copy a correction to a read-only Skill into a private shadow.
- Both Skill Tools repair padded names, matching enclosing package-path quotes, and backslash separators before validation; `skill` can read arbitrary UTF-8 package files while `skill_manage` retains its narrower authoring paths. `skill` loads a name that differs from exactly one allowed Skill only in form (`tools/skill.md`); `skill_manage` never writes to such a name and only suggests it. Similar names are suggestions in errors, never targets. Only optional `name`/`file_path` empties mean omission, after duplicate-value conflicts are checked; content empties remain meaningful. Repaired targets retain the same package containment and write-scope checks.

The registered `skill_manage` handler runs scope resolution, authoring and cache invalidation together in the bounded Tool worker pool. Runtime supplies `AgentStore.lifecycle_guard` around that sequence so shared-owner rename/archive cannot detach an already-resolved target. Cancellation after worker admission waits for the write and invalidation to finish (`test_skill_manage.py`, `test_runtime_skill_lifecycle.py`).

Shared-package resolution, stale-share checks and background protection batch names into one whole-home scan per participating owner in each operation. Resolve normalized registry names with the loader's first-found duplicate handling, not folder names; retain only the selected packages in receiver registries. Shared write targets and background protection skip policy-disabled packages, so they follow the same winning owner as activation. Before choosing any write target, `skill_manage` checks the live scope: a same-named Project Skill stays read-only and never redirects a write into a shadowed shared or disabled own package. A disabled own package remains directly editable while no other package of that name is visible (`test_runtime_shared_skills.py`). These intermediate lookups are local to the operation, without a separate persistent cache or invalidation path.

## Calls

- `create` checks the live scoped registry under the authoring lock before writing: a name already resolving to a global, bundled, Project, shared, folder or Extension Skill is refused as `skill_write_rejected`, so neither an attended call nor a Reflection can hide that package with a private copy. A fresh name still creates an own Skill; user Accessors retain their explicit package scopes (`test_skill_manage.py`).
- Schema: `action` + `name` required; `content` (complete SKILL.md for create/edit, complete file for write_file), `old_string`/`new_string`/`replace_all` (patch), `file_path` (support file; patch defaults to `SKILL.md`, see Patch matching for the one exception). Unadvertised `description` (create/edit), `absorbed_into` (delete), `scope` and `category` are validated but not offered.
- Argument repair (`_normalize_skill_manage_arguments`): wrappers and action formatting, `str_replace` -> patch, `delete_file` -> remove_file; `match`/`old_str`/`old_text`/`search`/`find` -> old_string, `new_str`/`new_text`/`replacement` -> new_string, `path`/`file`/`file_pth` -> file_path, `skill`/`skill_name` -> name. `content`, `new_string` and `file_content` are one text field resolved per action (patch keeps it as new_string, the others as content); empty duplicates are placeholders, two different nonempty texts fail before writing. A name with invocation marks (`/name`) or a package path (`name/references/x.md`, `name/SKILL.md`) splits into name and file_path; a leading slash or `name/` prefix is dropped from file_path.
- Patch matching (`_replace`): `fuzzy_match.replace_fuzzy` precise strategies (exact, Unicode/typography folding, trimmed lines, collapsed horizontal whitespace), so CRLF, trailing spaces and curly quotes in a copied `old_string` still address exactly one span. A folded match writes the file's own glyphs into `new_string` (Model curly vs file straight, and the reverse per aligned line). Only when nothing matches, one extra level of JSON escaping (`\n`, `\"`, `\t`, `\\`) is decoded in both strings, with a note. Then, without `replace_all` and unless `new_string` is already present, `copy_match.replace_copied` applies an `old_string` copied with errors (rules: `tools/apply_patch.md`), with a note per differing line and respelled word; a copy resembling several places fails `ambiguous_match` ("does not match exactly and resembles N places ... Copy the current text of the one to change"). A patch whose result equals the file reports `... already reads as new_string at line N; nothing changed.` A patch without `file_path` whose `old_string` misses in SKILL.md (all the steps above) but matches in exactly one support file under `scripts/`, `references/` or `assets/`, and there once (`replace_fuzzy`'s precise strategies, never a copy repair), is applied to that file: the summary names it, and `Note: old_string was not in SKILL.md but in <path>, the only file of the Skill that holds it, so that file was patched.` says why. The text itself names its place, so no similarity picks the file; a `file_path` the call names, `SKILL.md` included (also the `edit` with `old_string`), is never exchanged for another file. Misses fail `text_not_found` with up to two closest excerpts and the `skill` read call, plus the support file that holds the text when exactly one does (with a named `file_path`, or when the text is there more than once); ambiguity fails `ambiguous_match` with line numbers and the `replace_all` option. No write happens on any failure. Tool-call review 2026-10-16: 5 of 1,124 `patch`/`edit` calls since 2026-09-01 missed SKILL.md and got the support-file pointer, one of them sent again unchanged; each next successful call sent the same strings with the pointed `file_path`, so the fallback has exactly that effect one or two calls earlier.
- Action refusals (`invalid_arguments`, before any write) name the corrected call: create/edit without front matter or description show the header template (create builds front matter from `description` when the content has none; a missing front-matter name or description is filled from the arguments); a front-matter name or description that contradicts the arguments fails; edit with `old_string` and a fragment applies as patch with a note, with a complete document it is refused; patch without `old_string` names edit when the text is a complete document; write_file to `SKILL.md` is an edit; remove_file of `SKILL.md`, delete with file_path or text, write_file with old_string, create with a support file_path, and description outside create/edit are refused. `scope` values meaning own (`own`, `private`, `agent`, ...) are accepted, `global` and `user` select the global home (below), others are refused (`SKILL_MANAGE_UNKNOWN_SCOPE`); `category` is noted as unused. publish with file_path or text is refused.
- Global Skills (user requirement 2026-10-05): edit/patch/write_file/remove_file reach a package in the global home (`<data_dir>/skills`) when the name resolves there (`SkillRuntime._resolve_external_skill_scope` answers `global`), or with `scope: global` also behind an own Skill of the same name. create and delete of a global Skill are refused (`SKILL_MANAGE_GLOBAL_CREATE`, the global-delete refusal: only the user deletes one). Folder and Extension packages answer `external` and stay read-only. A background writer gets `skill_protected` (`SKILL_MANAGE_GLOBAL_BACKGROUND_REFUSAL`). A global change invalidates every Agent-aware registry, and the offloaded handler awaits `refresh_global_skills` (wired to `Runtime.reload_skills_async`) after the worker returns.
- `publish` (attended only, `SKILL_MANAGE_PUBLISH_BACKGROUND_REFUSAL` otherwise) moves an own Skill into the global home through `register_skill_manage_tool(publish_skill=...)`, wired to `SkillRuntime.publish_agent_skill`: `SkillAuthoringService.publish` copies the package, records a `create` in the global history with the package's origin and archives the private package with reason `published` (`skills/history.md`). Then what pointed at the private package follows it: its shares end (receivers reach the global Skill through their selection), a turned-off private package turns the home package off instead, and an `allowed_skills` list without `*` gets the name, so the publisher keeps the Skill. A global Skill of that name refuses (`SKILL_MANAGE_PUBLISH_CONFLICT`). Design decision 2026-10-05: move rather than copy, so no private shadow outranks the global Skill for the publisher (`test_runtime_shared_skills.py::test_skill_manage_publishes_into_and_changes_only_the_global_home`).
- A non-create target missing from the caller's home (and not shared or visible elsewhere) fails `skill_not_found` with similar own names (`similar_skill_names`) or the own-name list; case, separator and near-miss names are suggested, never written.
- Background guards: a call from a Run of kind `librarian` or in a Librarian Session writes as `librarian`, one from another unattended Run as `reflection`, every other call as `agent`, each with the Session, Run and Run kind (`core/tools/skill.py::skill_writer`, `tools/skill.md`). Before any write to an existing Skill (`SkillAuthoringService.check_writable`), a background call fails `skill_protected` for a pinned Skill (`SKILL_MANAGE_PINNED_REFUSAL`) and for one whose history cannot be read (`SKILL_MANAGE_HISTORY_UNREADABLE_REFUSAL`); `create` of a new own Skill stays open. Origin, sharing and automation triggers do not limit it (`skills.md` -> Background Writer): it edits a Skill shared in from another Agent in the owner's package like an attended receiver. Any writer may `delete` with or without `absorbed_into`, another own Skill that now holds the instructions (user decision 2026-10-03: a wrong or obsolete Skill has no merge target). Every `delete` runs through `register_skill_manage_tool(follow_merge=...)`. With `absorbed_into` it follows the merge: `register_skill_manage_tool(follow_merge=...)` (wired to `Runtime.follow_skill_merge`, `core/runtime/_skill_merge.py`) lists, under the automation reference lock, what names the Skill (the owner's shares of it in the Skill Policy and the `/name` or `$name` triggers in the owner's live Bootstrap and Cron jobs, `AutomationReferences.agent_skill_triggers`), hands that list to the delete, which records it on the archive revision (`followed`, `skills/history.md`), and once the delete succeeded moves each one to the absorbing Skill (`SkillPolicyService.move_shared`, `AutomationReferences.rename_skill_triggers`). The result then adds `Note: These now use Skill ...` for what moved and `Warning: These could not be changed and still name ...` for what did not; chat activation does not follow absorbed redirects, so such a trigger finds nothing. Without `absorbed_into` nothing moves and nothing is recorded as followed; the result adds `Warning: These still name '<name>', which no longer exists: ...` (`SKILL_MANAGE_ORPHANED_WARNING`) for every share and automation trigger that still names the Skill, and these keep naming it, so restoring the Skill makes them work again. Undoing or restoring the merged Skill moves nothing back (`automation/librarian.md` -> Known gaps). A Librarian Run builds its merges from Skills it read earlier in the Run, so its `edit`, `patch`, `write_file`, `remove_file` or `delete` of an existing Skill fails `skill_changed` (`SKILL_MANAGE_CHANGED_DURING_PASS_REFUSAL`) when that Skill's history holds a revision of another Run, or of a person, recorded after the Librarian Run was created (`register_skill_manage_tool(run_started_at=...)`, wired to `Runtime.run_started_at`, i.e. the Run manager's `Run.created_at`, read on the Event Loop for Librarian Runs only; the check reads the Skill's newest 100 revisions). The refusal comes once per outside change: the handler remembers, per (Run, Skill), the newest outside revision it reported (bounded to 1024 pairs), so the next call goes through whether or not the Agent read the Skill again, and only a further outside change refuses again. The handler runs these checks and the write inside `SkillAuthoringService.exclusive()`, which holds the Skill write lock every write takes, so a person's change cannot land between the check and the write and be overwritten; it waits and lands after. `create` and other Run kinds are not checked; a background review defers its Skill dimension while a pass runs instead (`automation.md` -> Reflection). `absorbed_into` on another action, naming the Skill itself or naming no own Skill fails `invalid_arguments`. A delete answers `SKILL_MANAGE_DELETED`, with `absorbed_into` `SKILL_MANAGE_ABSORBED`.
- Success data is `{content}`: one line (for example `Patched SKILL.md of Skill 'x' at line 12.`), then `Warning:`, `Note:` and `Hint:` lines. Shared and own targets read identically.
- Authoring hints (`core/tools/_skill_conventions.py`): after a successful create, edit, patch or write_file, up to three `Hint:` lines name an authoring convention of the bundled `skill-writing` Skill that the written text breaks, with its fix. They never block or change a write, and an error while computing them only logs. Checks, most consequential first: a description without a situation (no `when`, `whenever`, `if`, `use for`, German `wenn`/`sobald`/`falls`), a description over `SKILL_DESCRIPTION_ADVISED_LENGTH` (250; over 1024 the loader warns instead), a top-level file under `references/` or `scripts/` (not `_`-, `.`- or `test_`-prefixed) that no other package file names (scripts also count as named when another file imports them), SKILL.md over `SKILL_MD_ADVISED_LENGTH` (12000, shared with the Librarian brief; beyond one page the loader warns instead), then in the prose of SKILL.md and `references/*.md` outside code: ISO dates, `PR`/`issue`/`ticket`/`bug #N` and `commit <hash>`, and rule words in capitals (`IMPORTANT`, `CRITICAL`, `MUST`, `NEVER`, `ALWAYS`, `MANDATORY`, `WICHTIG`, `NIEMALS`, `IMMER`). A write that replaced a whole file reports every finding that file decides (SKILL.md decides the description, its size and prose, and which support files are named); a patch reports only findings it introduced, so a one-line change to an older Skill does not ask for a rework. Every writer gets them, Reflection and Librarian included: Reflections write most Agent Skills unattended, and the Librarian's brief asks it to fix hard-to-use Skills, while a patch never surfaces older findings. Hints are Model-only (no display notice). Not loader validation: `skill_validator` judges whether any package from any source loads, and these house conventions would flag imported Skills. Calibration (2026-10): of 48 Agent-written Skills, 24 carried incident dates or commit hashes (every flagged one was an incident note), 13 descriptions named no situation (1 of them a false alarm), 35 descriptions over 250 characters, 5 SKILL.md over 12000 characters, 3 capitalized rules; marketing words and a description repeating the name never occurred and are not checked. Tests: `tests/core/tools/test_skill_manage_hints.py`.
- Detail blocks (`tools/display.md` -> Display metadata): one diff per changed package file from the authoring result's changes, an info notice `Nothing changed; the file already had this text.` when the write left every file as it was, and the Skill's validation warnings as warning notices. `Note:` lines describe the call's arguments and stay Model-only; paths are package-relative, so shared targets stay indistinguishable.
- Tests: `tests/core/tools/test_skill_manage.py`; probe cases in `scripts/tool_lab/cases/knowledge.json`.

## Merge access

A merge preserves access to the absorbed private package for its owner and shared receivers (user decision 2026-10-14). Before deletion, `SkillRuntime.prepare_skill_merge` simulates the share move, source removal and selection changes through the ordinary registry builder. Preparation and deletion run in one Tool worker under Agent lifecycle, Project configuration, Skill authoring and Skill Policy locks, in that order; no lock crosses an await. This prevents an internal rename, edit, Project reconfiguration or disable from landing between the check and deletion. External filesystem edits still follow the ordinary scan boundary. It checks the exact winning package, Agent selection and requirements in the Agent's base scope and every registered Project Context where that source is actually loadable. If the exact successor would be disabled, shadowed or unavailable there, `skill_manage` refuses with `skill_merge_blocked` before changing packages, history, shares, selections or automation triggers (user decision 2026-10-14); it never overrides a disable or package precedence. Project Team ceilings stay unchanged. After a successful share move, `preserve_merged_skill_access` adds the successor to explicit selections and removes its Agent Skill Exclusion for those previously authorized Agents; wildcard or missing selections stay unchanged, and Agents that could not access the old package gain nothing. Old selection names remain because another package can take their place. Each Agent configuration uses its ordinary atomic write, without a cross-store transaction; a failed update is reported in the merge's existing warning as `Agent '<name>'`. Those response-only references never enter the durable `followed` list. As with shares and triggers, restoring or reverting the archived Skill does not roll these access changes back.

## skill-writing Skill

The bundled `skill-writing` Skill (`resources/skills/skill-writing/`) is the one home for what a Skill must look like when an Agent creates or changes one: name, description, instructions, support files, and the steps to create, change and check a Skill. It does not cover merging or cleaning up a library, which the Librarian does, nor where a lesson belongs, which `skill_maintenance.md` and the briefs say. No prompt names it; Agents find it through its catalog description, and `vbot-docs/references/agents.md` points to it when a new Agent gets private Skills. Its rules copy the compact ones in `skill_maintenance.md` and the brief fragments (`skill-shape.md`, `skill-read-current.md`, `learn-intro.md`, `learn-method.md`); those keep their text, so a Reflection, `/learn` or a Librarian pass needs no Skill load (user decision 2026-10-07: copy, never move). The `skill_manage` authoring hints check the same limits (description under 250 characters with `Use when`, SKILL.md under `SKILL_MD_ADVISED_LENGTH`). Change them together so they never disagree. Writing a SOUL, creating an Agent for a purpose and Agent names live in the `vbot-docs` Skill (`cli.md`). These are Model instructions: parsing and write scope stay enforced by the loader (`skills/loading.md`) and the authoring service (`skills/authoring.md`). Reflection decision evaluation is documented in `automation.md`.
