# Skill Policy

The Skill Policy file `<data_dir>/skills/policy.json` (`core/skills/policy.py`, `SkillPolicyService`, persisted through `runtime.skill_policy`): its format, validation and mutation rules, the surfaces that change it, and what disables, Agent Skill Exclusions and shares do. Vocabulary: `skills.md` -> Terms.

## Disables, exclusions and shares

- Disabled Skill (user requirement 2026-10-05: a disable turns off exactly that package, never a same-named one): set through the Skill Policy, or for a Project Skill through its Project's `skills_project_disabled`. The package is skipped at scan before it claims its name, so it vanishes from every runtime consumer, the owner's always-allowed copy included, while the next same-named package in precedence loads; only editor-scope loads still show it (`skills/loading.md`). The switch outranks allowlists and Agent Skill Exclusions and acts for every Agent and Project.
- Agent Skill Exclusion: a name in an Identity Agent's optional `excluded_skills` (`agent/configuration.md`) is removed from what `allowed_skills` grants, also from `*`, so `["*"]` plus exclusions means "all except". It also turns off the Agent's own private Skills of that name (user requirement 2026-09-29: own Skills are toggleable per Agent), but never the active Project's effective set. An excluded Skill stays loaded and editable through `skill_manage` but leaves the Agent's catalog and activation, and Skills depending on it become unavailable. Config, Project and temporary Agents have no exclusions. In code the policy switch is the registry's `excluded_packages`, an Agent exclusion `SkillRegistry.allowlist_exclusions` (`skills/loading.md`).
- Shared Skill: for each receiver, a share adds the owner's package as an extra pool layer between the Project and global layers (`skills.md` -> Overview), subject to the receiver's own `allowed_skills` and the disables and shown like its own Skills, without provenance. Receivers co-maintain it through `skill_manage` update actions; `create` and `delete` stay with the owner (`skills/skill-manage.md` -> Targets). Config and Team Agents never see shared Skills; stale entries are ignored (File).

## File

One validated, versioned control-plane file at `<data_dir>/skills/policy.json`: `{"format_version": 1, "disabled_packages": {"home": ["<name>"], "bundled": ["<name>"], "extensions": {"<extension name>": ["<name>"]}, "folders": {"<skill_directories entry as written>": ["<name>"]}, "agents": {"<agent-id>": ["<name>"]}}, "shared": {"<owner-agent-id>": {"<skill-name>": ["<receiver-agent-id>"]}}}` (Generation 1 contract in `json-documents.md`; unknown top-level fields and unknown `disabled_packages` sources survive mutations). In code each entry is a `SkillPackageRef(source, name, location)` with source `home`/`bundled`/`extension`/`folder`/`agent`. A folder entry follows the configured string, so editing that `skill_directories` entry leaves its old entries stale. The earlier name-wide `disabled` list was dropped without a converter (user decision 2026-10-05); a leftover `disabled` field is kept as an unknown field and has no effect. Missing file means empty policy; a malformed file yields diagnostics plus an empty effective policy instead of breaking startup. Mutations run under one process-local lock with one atomic replace per write. Trigger-unsafe names, `agents` keys and receivers that are not Identity Agent ids produce warnings (in the manager diagnostics and `doctor config`) and drop from the effective policy only: mutations rewrite the stored lists unchanged apart from the one entry they change. Unknown owner ids and names matching no scanned skill are kept in the file but ignored at resolution (surfaced as stale entries). No legacy compatibility or auto-migration.

Policy mutations strictly load the existing document and reject malformed files (including a missing or other `format_version`) without replacing them with the tolerant read fallback; the RPC edge reports that refusal as a `domain_error` carrying the file diagnostics, not as an unexpected failure. A pre-Generation-1 `version` 2 document has no `format_version` and is refused like any other. Writes validate trigger-safe Skill names, canonical Agent ids and a package source with its location (none for `home`/`bundled`, required for the others) before persistence; sharing requires at least one receiver other than the owner.

## Surfaces

RPC `skill.set_disabled {id, disabled}` turns exactly the inventoried package off or on (`SkillRuntime.set_package_disabled`, Runtime `set_skill_package_disabled`): a Project Skill through its Project's `skills_project_disabled` (then publishes `projects` and invalidates that Project's Skills), every other package through the Skill Policy (then reloads); CLI `vbot skill disable/enable <name-or-id>` resolves a name through the inventory and refuses a name several packages share, listing their ids; `skill.share` requires an existing owning agent, at least one existing receiver id, none equal to the owner. Both publish `resource_changed(kind="skills")` - a policy disable via `reload_skills_async()`, share via `invalidate_agent_skills(None)` (shared Skills never enter the global pool). `skill.set_disabled` reports an unknown inventory id and `skill.share` an unknown or unowned Skill as `skill_not_found`; `skill.share` reports an unknown owner or receiver as `agent_not_found`. Tests: `tests/core/runtime/test_runtime_shared_skills.py` and `tests/server/rpc/test_skill_methods.py`.
