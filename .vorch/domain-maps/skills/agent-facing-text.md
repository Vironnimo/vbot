# Skills Agent-facing text

Why each sentence of the Agent-facing text the Skills domain owns exists: the Skill System Prompt blocks (`core:skills`, `core:skill_maintenance`), the `skill_manage` results and refusals, Repository Profile Skill preloads, the bundled `skill-writing` support-file guidance and the bundled `vbot-docs` instructions for Skill history, archive, pins and the Librarian. Rules for this file: `.vorch/workflows/domain-map-workflow.md` -> Agent-facing text.

Repository Profile Skill preloads reuse the existing `skill_content` wrapper and expand `{baseDir}` to the absolute Skill directory. The injected `Skill directory: {absolute_path}` line gives relative script and resource references their package base before any Skill Tool call; it is included only with a selected, available preload. The Profile body remains repository-authored text. Projects owns the preload selection and reports an absent or unavailable Skill instead of pretending it loaded.

Bundled `skill-writing` support-file guidance:

| Text | Reason |
|---|---|
| `Link each reference directly from SKILL.md and say when to read it: ...` | A direct link with a task condition makes optional depth discoverable. The Tool result teaches the read call centrally instead of repeating it in every Skill. |
| `Paths are relative to the Skill directory.` | Keeps reference, script and asset paths portable and gives them one known base. |
| `Keep reference links one level deep ...` | Avoids loading unrelated intermediate files just to discover the reference needed for the task. |

`skill_manage` results and refusals (`core/tools/skill_manage.py`); background refusals carry `skill_protected`, the `absorbed_into` refusals `invalid_arguments`, the concurrent-change refusal `skill_changed`, all `retryable: false`. Every refusal says that nothing changed and names the one valid next action. Background refusals reach a Reflection and the Librarian, also while the user talks with it in a Librarian Session, so they say "you" and "your reply" rather than "in the background" and "your closing reply".

| Text | Reason |
|---|---|
| `Skill '{skill_name}' is still at its source.` / `Publishing failed, and cleanup left files at {destination}.` / `Ask the user to remove that destination folder from the filesystem before retrying.` | Cleanup can remove `SKILL.md` before a locked support file stops it, leaving an incomplete folder that neither loads as a Skill nor can be deleted through Skill controls. Names the preserved source and exact leftover path without claiming a complete destination copy, and gives the user a recovery operation that works (`test_publish_moves_a_skill_into_another_home_with_its_provenance`). |
| `Skill '{skill_name}' is still at its source.` / `Publishing failed, and the destination at {destination} changed or could not be verified, so it was left untouched.` / `Ask the user to inspect that destination before retrying.` | An external editor can change or replace a published package while source archival fails. Unverified destination content is not rollback-owned; names the preserved source and destination without suggesting blind deletion of someone else's changes (`test_publish_moves_a_skill_into_another_home_with_its_provenance`). |
| `Nothing changed. Skill '{skill_name}' is loaded from folder '{package.name}', but folder '{skill_name}' contains another Skill. Ask the user to align the folder names with their SKILL.md names, then retry.` / `Nothing changed. Several packages declare Skill '{skill_name}'. Ask the user to give each package a distinct name, then retry.` | Deletion cannot choose safely between conflicting package identities. Refuses before history/files change and gives the user the concrete repair; the Agent must not delete another package as a workaround (`test_delete_refuses_conflicting_package_identities`). |
| `Nothing changed. Skill '{skill_name}' not found in this home's loaded Skills. Check its name in SKILL.md before deleting it.` | A direct authoring caller can address a folder whose declared Skill name differs. Prevents deleting that folder under the wrong identity. |
| `Deleted Skill '{name}'. Its files are kept in the archive, where the user can restore it.` (`SKILL_MANAGE_DELETED`) | Delete archives now. Says the deletion is reversible by the user, so the Agent neither keeps a backup copy as another Skill nor tells the user the files are gone. |
| `Deleted Skill '{name}'; its instructions now live in Skill '{target}'. Its files are kept in the archive, where the user can restore it.` (`SKILL_MANAGE_ABSORBED`) | Confirms where the instructions went, so the Agent uses `{target}` for that work from now on. |
| `These now use Skill '{target}' in place of '{name}': {items}.` (`SKILL_MANAGE_FOLLOWED_NOTE`, a `Note:` line after `SKILL_MANAGE_ABSORBED`; `{items}` joins `the share with Agent '<name>'`, `Bootstrap job '<name>'`, `Cron job '<name>'`, `Calendar event '<title>'` with `; `) | Tells the Agent that the merge already moved the shares and automation triggers, so it neither edits them by hand nor warns the user about broken automations. |
| `These could not be changed and still name '{name}', which no longer exists: {items}. Name them in your reply so the user can change them to '{target}'.` (`SKILL_MANAGE_NOT_FOLLOWED_WARNING`, a `Warning:` line) | The Skill is deleted, so these references find nothing; the Agent must act on it, hence `Warning:` and the next action. The user can re-share and edit automations; a Reflection or the Librarian may lack the Tools for that. |
| `Agent '{name}'` (a failed access update in `SKILL_MANAGE_NOT_FOLLOWED_WARNING`) | Names the Agent whose selection could not follow the merge, including the owning Agent; calling that a share would misdescribe its own-library access. |
| `Nothing was changed. Skill '{target}' cannot replace '{name}' for {blocked}. Keep '{name}' and name the blocked merge in your reply so the user can resolve the Skill access.` (`SKILL_MANAGE_MERGE_ACCESS_REFUSAL`; blockers name the Agent, optional Project Context, and whether the successor is disabled, shadowed or unavailable) | A successful share/selection move can still load a different same-named package or no package. Refusing before deletion preserves the old instructions and names the access conflict for the user without inviting a bypass through another Tool. |
| `Skill '{name}' is pinned by the user, so you cannot change it; nothing changed. Leave it as it is and name the needed change in your reply.` (`SKILL_MANAGE_PINNED_REFUSAL`) | Gives the observable cause (the user's pin) and the only valid next action, so a background writer does not retry through another action or a copy. The reply is where the Reflection briefs and the Librarian brief ask for changes the Run could not make, and where a user talking with the Librarian reads it. |
| `The history of Skill '{name}' cannot be read, so whether the user pinned it is unknown and you cannot change it; nothing changed. Leave it as it is and name the needed change in your reply.` (`SKILL_MANAGE_HISTORY_UNREADABLE_REFUSAL`) | Fail-closed case of an unreadable history, phrased as the fact the Agent can relay (the pin cannot be checked) instead of an internal error; same next action. No "right now": it invited retries. |
| `Skill '{name}' was changed outside this pass after the pass started; nothing changed. Load '{name}' again with skill and build your change from that text, or leave it as it is.` (`SKILL_MANAGE_CHANGED_DURING_PASS_REFUSAL`) | Librarian Runs only. A merge built from text read before another Run or the user changed the Skill would overwrite or delete that change. "this pass" is the Librarian brief's word for the Run; the next action names the `skill` Tool, whose result is the current text. |
| `These still name '{name}', which no longer exists: {items}. Name them in your reply so the user can change or remove them.` (`SKILL_MANAGE_ORPHANED_WARNING`, after a delete without `absorbed_into`) | Shares and automation triggers of a deleted Skill find nothing; only the user can decide whether to point them at another Skill or remove them, so the Agent reports them. |
| `absorbed_into is used only by delete; nothing changed. Omit absorbed_into for {action}.` (`SKILL_MANAGE_ABSORBED_INTO_ACTION`) | Names the only action that takes the argument and the corrected call. |
| `absorbed_into names '{name}' itself; nothing changed. Name the other Skill that now holds its instructions.` (`SKILL_MANAGE_ABSORBED_INTO_SELF`) | A Skill cannot absorb itself; asks for the other Skill. |
| `absorbed_into names '{target}', which is not one of your own Skills; nothing changed. Name one of your own Skills that now holds the instructions of '{name}'.` (`SKILL_MANAGE_ABSORBED_INTO_UNKNOWN`) | The absorbing Skill must live in the same home; says so in the Agent's terms ("your own Skills"). |
| Description: `... edit, patch, write_file and remove_file also change a Skill listed under "Your global skills", which other Agents use too. publish turns one of your own Skills into a global Skill.` | Names the reachable global set by its catalog heading and that other Agents depend on it; the when-to rules live in `core:skill_maintenance`. +38 tokens. |
| `Skill '{name}' is a global Skill, which you cannot change here; nothing changed. Leave it as it is and name the needed change in your reply.` (`SKILL_MANAGE_GLOBAL_BACKGROUND_REFUSAL`, `skill_protected`) / `You cannot make a Skill global here; nothing changed. Leave Skill '{name}' as it is.` (`SKILL_MANAGE_PUBLISH_BACKGROUND_REFUSAL`) | Background writers never touch global Skills; same next action as the pin refusal, so a Reflection or the Librarian reports instead of copying. |
| `Skill '{name}' is a global Skill, which only the user can delete in the Skill controls; nothing changed.` | Agents fix global Skills but never remove them. |
| `create adds one of your own Skills; nothing changed. Omit scope to create it, and use action publish to make one of your own Skills global.` (`SKILL_MANAGE_GLOBAL_CREATE`) | A global Skill starts as an own Skill; names both corrected calls. |
| `Nothing was changed. Skill '<name>' already exists as <scope>. Use that Skill instead of creating a private copy.` | Enforces the existing no-private-copy rule: `create` previously hid every non-own scope with a same-named private package, including during unattended Reflection (isolated dispatch probe, 2026-10-15). |
| `Skill '{name}' is now a global Skill instead of one of your own. Other Agents can use it when their Skill selection allows it.` (`SKILL_MANAGE_PUBLISHED`) | Says the own copy is gone and that other Agents' access still depends on their selection, so the Agent does not promise more. |
| `A global Skill named '{name}' already exists; nothing changed. Tell the user, who can compare the two Skills in the Skill controls.` (`SKILL_MANAGE_PUBLISH_CONFLICT`) / `Skill '{name}' is already a global Skill; nothing changed.` | Publishing never overwrites a global Skill; the user resolves the conflict. |
| `Skill '{name}' comes from a skill folder or an Extension and is read-only; nothing changed. Tell the user which change it needs; do not edit its files with file or shell Tools.` | Those packages belong to their folder or Extension; an edit there would be overwritten or change another source. |
| `skill_manage changes your own Skills and global Skills; Project and bundled Skills are read-only here, and nothing changed. Omit scope to change a Skill by its name.` (`SKILL_MANAGE_UNKNOWN_SCOPE`) | Lists what the Tool reaches and the corrected call. |
| `Note: old_string was not in SKILL.md but in <path>, the only file of the Skill that holds it, so that file was patched.` (after `Patched <path> of Skill '<name>' at line N.`; a patch without `file_path`) | Agents patched a support file's text without `file_path`; the refusal named the file, and the Agent sent the same strings again with it, or first the unchanged call once more (F2, F5). The text matches one place in the whole Skill, so the target is clear; the note reports the interpretation, so the Agent knows which file changed. Evidence: Patch matching above. |
| `Hint:` label on authoring hints, after `Warning:` and `Note:` lines (`core/tools/_skill_conventions.py`) | Marks advice apart from `Warning:` (acted on) and `Note:` (how the call was read); the summary line before it already says the write succeeded, so no Agent retries the write. |
| `The description does not say when to load the Skill. Add "Use when" and the situations that call for it, in the words of a user's request.` (`SKILL_MANAGE_HINT_NO_SITUATION`) | Agents pick a Skill by its description; one that names no situation is loaded for every task or for none. 13 of 48 Agent-written descriptions named none; 1 of those 13 stated its situation without a marker word. |
| `The description has {length} characters; every request lists it. Shorten it to under 250: what the Skill does, then "Use when" and the situations, with details moved into the instructions.` (`SKILL_MANAGE_HINT_LONG_DESCRIPTION`) | The catalog carries every description in every request; 35 of 48 Agent-written descriptions exceeded 250 characters. Gives the cause in the Agent's terms and the shape of the fix. |
| `No other file of the Skill names {path}, so Agents following SKILL.md never {verb} it. Add a sentence to SKILL.md that says when to {verb} it.` (`SKILL_MANAGE_HINT_UNNAMED_FILE`, `{verb}` `read` for `references/`, `run` for `scripts/`) | Agents open support files only through pointers; a reference written before its pointer (the usual order) otherwise stays unread. Reported on the write that creates the gap, so it reminds at the moment the pointer is due. |
| `SKILL.md has {length} characters. Keep it under 12,000: move material that only some tasks need into a file under references/ and say in SKILL.md when to read it.` (`SKILL_MANAGE_HINT_LONG_SKILL_MD`) | A loaded SKILL.md stays in context for the rest of the Session; same limit as the Librarian brief. |
| `{path} contains dates or change identifiers, such as {example}. Delete them and state each rule with its reason, not when or where it was learned.` (`SKILL_MANAGE_HINT_HISTORY`) | A frequent defect: 24 of 48 Agent-written Skills carried incident dates ("verified 2026-09-17"), which teach the story instead of the rule. Quotes the first one so the Agent finds it. |
| `{path} stresses rules in capitals, such as {example}. Write them in normal case, with must or never only for real requirements.` (`SKILL_MANAGE_HINT_EMPHASIS`) | Shouted rules get over-applied and make plain rules read as optional; names the first word found. |

System Prompt guidance (`resources/prompts/skills.md`, block `core:skills`; `resources/prompts/skill_maintenance.md`, block `core:skill_maintenance`, shown while `skill_manage` is offered). The review and `/learn` briefs share their Skill rules through fragments (`prompts.md` -> Agent-facing text).

| Text | Reason |
|---|---|
| `Skills contain task-specific methods, conventions and the user's preferences.` | Skills carry task preferences (`learning-routing.md`); without saying so, Agents skip loading a Skill for a task they can already do and miss the user's preferences. No blanket claim that every method is tested. |
| `When the user names a Skill or its description matches work required for the task, load it with skill and follow it.` | Explicit requests and applicable descriptions trigger loading; partial keyword overlap alone does not. Replaces the broad instruction to err on the side of loading with a task-scoped trigger. |
| `If its <skill_content> is already in context, follow it without reloading.` | A Skill can already be loaded through an explicit trigger or an earlier turn. Its instructions still apply, without a redundant Tool call. |
| `Your own Skills, listed under "Your own skills", hold how you do recurring kinds of task for this user; maintain them with skill_manage.` | Names the writable set by its catalog heading and the owner Tool. |
| `When the user corrects how you did a kind of task, or a Skill you followed was wrong or incomplete, update that Skill in the same turn when it is your own.` | Corrections are the strongest learning signal (Hermes review signals); waiting for a background review loses them when reviews are off. In-place correction prevents `UPDATE:` tails. |
| `Create a Skill when the user asks for one. First list the Skills ...; when one of your own Skills already covers that kind of task, extend it instead and tell the user.` | Attended creation only on request keeps foreground work quiet; background reviews capture verified methods. Listing first prevents near-duplicates. |
| `Name the kind of task, not today's ticket, error message or output, and describe when to load it.` | Narrow session-named Skills were Hermes' main library failure; the description is what selects a Skill. |
| `Write lessons, not logs: ...` | Skills read as transcripts teach the story, not the rule. |
| `After a failure caused by setup the user can fix, ... save the verified fix, not a claim that a Tool does not work.` | Saved negative claims outlive the fix and make Agents refuse working Tools (Hermes do-not-capture list). |
| `Change a Skill from its current text: read the file with skill ... unless its full current text is in the conversation. After changing a Skill that is loaded in this Session, load it again with skill.` | Stale transcript text overwrote newer Skill content; reloading keeps the Session on the changed instructions. |
| `Save a script only after its exact content ran successfully; ...` | Untested scripts get trusted and rerun by later Sessions. |
| `Change a Skill listed under "Your global skills" only to fix an instruction that is wrong or no longer works, such as a failing command, or when the user asks for that change. Other Agents follow it too: never add your preferences, habits or extra steps to it.` | User requirement 2026-10-05: Agents can fix global Skills, but only with strong cause (a real error), never to tune them to one Agent's taste, so global Skills do not churn. Named by catalog heading; folder and Extension packages under that heading are refused by the Tool. Permanent cost: about +70 tokens with the two rows below. |
| `Use skill_manage action publish only when the user asks to make one of your own Skills global.` | Publishing changes what every Agent sees; it stays the user's decision. |
| `For any other Skill, including one the user asks you to change, tell the user it is managed in the Skill controls; do not edit it through the CLI or file Tools and do not create a private copy.` | Project, bundled, folder and Extension Skills belong to the user's Skill controls; Agents used the shell or private copies as workarounds, which forked the Skill silently. |
