# Runtime

Bootstrap entry point. Wires services and manages start/stop lifecycle.

`runtime.py::Runtime` owns readiness, service references, shutdown, and the stable public access/reload surface. `_bootstrap.py` assembles its dependency-ordered service graph; `_shutdown.py` runs the dependency-ordered shutdown steps of `stop()`, `aclose()` and failed-startup cleanup; `_configuration.py` interprets bootstrap paths; `_settings.py` coordinates live Settings effects; `_agent_rename.py` coordinates the Identity Agent rename across every service that references an Agent id (Identity Agent rename). These are internal files of the same Runtime owner, not additional service layers.

Blocking in-process work crosses named `BoundedWorkerPool` boundaries from `core/utils/workers.py`: each pool owns a dedicated executor, admits at most its worker count per Event Loop, and defers cancellation until an already-started mutation settles, and records its admission wait, run duration and active/waiting gauges as `worker_pool.<name>.*` metrics (`performance.md`). An `OrderedWorker` from the same module is the single-thread variant for owners whose writes must land in submission order (full-document snapshots written by a scheduler and by operator edits, trace publication before cleanup): `call` blocks a synchronous caller, `call_async` awaits without blocking the loop, `hand_off` queues without waiting up to a caller-given limit, and `drain` waits for everything submitted; a submitted operation always runs, and a cancelled `call_async` caller waits until it has settled. `settle_before_cancelling(work, *, on_late_failure=None)` is that wait for any awaitable, such as an edit that saves and then updates memory: a cancelled caller waits for the work, then the cancellation wins. A failure of the work after that reaches no caller, so it is never dropped: `on_late_failure` reports it in the owner's words (RPC and Extension mutations, local speech shutdown), otherwise the helper logs it on `vbot.utils.workers` with the work's code name, an expected `VBotError` at WARNING and anything else at ERROR with its traceback (`tests/core/utils/test_workers.py`). Owners that must finish admitted work before honoring cancellation use it rather than their own `shield` or `wait` loops (RPC mutation serialization in `server/rpc/_mutations.py`, Extension reload/disable/shutdown in `core/extensions/runtime.py`, local speech shutdown). Continuous Terminal I/O stays on its own executor so it cannot consume parser/prompt/Session/Tool capacity.

## DI Contracts

Runtime constructs the canonical `UsageRecorder` after the Model registry and
before request producers. It injects `usage_recorder` into Task services, Chat
dependencies, Compaction, titles and Statistics; Extension sampling records its
own exposed Adapter request. Immediately after Sessions opens, the recorder
imports retained historical Usage before Agent lifecycle operations can remove
history. `canonical_databases()` and offline declarations include
`model-usage.db`; async shutdown drains its producers and Statistics readers
before closing it, and failed-startup cleanup also closes it. Extension sampling
retains its injected recorder through readiness withdrawal during shutdown. See
`usage.md` for the accounting lifetime and import contract.

`core/runtime/interfaces.py` holds `typing.Protocol` contracts. Only `ConfigProtocol` is constructor-injected; the rest are structural typings. `RuntimeServices` is the read-only service surface of a *started* runtime for core modules coordinating across it - consumers access services directly (a missing attribute is a wiring bug, never a `getattr` probe), and Chat deliberately does not consume it: Runtime builds Chat-owned `ChatLoopDependencies`, and Chat projects those into Run-local context. Heavy service types import under `TYPE_CHECKING` only - a runtime import of `core.runtime` loads `Runtime` and everything behind it (import cycle). The central credential contract is `ProviderCredentialResolverProtocol` (`providers.md` -> Usable; details in `providers/connections.md`).

## Bootstrap

`start()` is idempotent and runs dependency-ordered phases. Any exception after startup work begins runs the synchronous shutdown steps (Shutdown) for every service built so far (`clean_up_failed_startup`), which clears references and closes logging; a failing step is logged with its step name but never raised, and the startup error is re-raised unchanged. Cleanup runs outside the exception handler, so a failed step's log entry does not repeat the startup traceback as its context. The cleanup guard starts before Storage construction and clears startup identity and readiness so the same Runtime can retry after failure (`tests/core/runtime/test_runtime_lifecycle.py`). Before that cleanup closes logging, the guard writes the failure once at ERROR with its traceback (`Runtime startup failed`) - the server host reports the re-raised error only after the managed handlers are closed, so it never reaches the log file - unless the data root does not exist, which is never created just for the log (`tests/core/runtime/test_runtime_lifecycle.py`). Ordering constraints worth knowing before touching bootstrap:

1. **Storage & settings** - logger + `StorageManager` + settings load. Invalid Settings never abort startup: malformed JSON or root shape falls back to defaults, schema-invalid keys omit individually while siblings stay live, the source file never rewrites, and mutations stay strict so they cannot overwrite invalid data. Data-dir creation failure is fatal.
2. **Attachments & credentials** - AttachmentStore plus the `.env` fallback snapshot read without mutating `os.environ`.
3. **Providers & models** - tolerant load of bundled config + Custom Provider overlay; each generated Model DB catalog selected from the root that fetched it last (`models.md`); OAuth token store and the central credential resolver wired.
4. **Task services, agents, processes** - TaskModelService + per-task services; one optional LocalSpeechExecutor supplies its catalog to TaskModelService and execution to SpeechService without loading ML packages/weights; AgentStore with live defaults provider, whose `recover_rename()` then finishes the Agent-owned half of a rename the last process left pending, before anything reads the roster; ProcessManager. Invalid agents degrade individually.
5. **Tools, extensions, skills** - ToolRegistry + built-in registration, then extension/skill registries and `skill`/`skill_manage`. Unreadable roots diagnose-and-omit, never fatal.
6. **Sessions, recall & chat** - one Runtime-owned `ChatSessionManager` opens the marker-authorized `<data-dir>/sessions.db` with lightweight readiness checks, then is injected into AgentStore, ProjectStore, Recall, Statistics, and Chat. Right after it the Runtime builds the one disposable `StatisticsIndex` (`statistics_index`) that the Statistics RPC service and the Extension host share (`statistics.md`). Normal Runtime operation never creates data snapshots; snapshot, restore and recovery workflows belong to the database kernel (`database.md`), which receives the open handles through `Runtime.canonical_databases()`. Project/Agent resolution and bootstrap Agent start **before** channels; recall defaults and falls back to `sqlite_fts`, whose construction failure is fatal because no lower registration fallback remains; ChatRunManager receives the shared Sessions persistence owner at construction; the `PerformanceService` is built right after it with the `runs.active`/`runs.queued` gauge samplers. Runtime builds Reflection, titles and ChatLoopDependencies, and supplies one CompactionService to both Chat loops.
7. **Automation surface** - TriggerService (streaming loop for triggers, non-streaming for manual Compaction); TerminalManager; BootstrapService, CronService and CalendarService (whose action owner receives TriggerService, AgentResolver, and Sessions), constructed but not yet started; `AutomationReferences` over those three (`automation.md`); only then the end-to-end CommandDispatcher, which receives it for the Agent Takeover, and applied Extension Commands; ChannelService; a rename pending from step 4 then moves their references (`complete_pending_rename`); then `ArchiveService` (`runtime.archive`, built over these owners by `_bootstrap.py::_archive_services`) finishes or undoes interrupted archive operations, in every startup mode (`archive.md` -> Recovery), while its retention sweep starts only once startup is complete (`_start_archive_retention`, after the Recall indexing start; `archive.md` -> Retention); `LibrarianService` (`automation.md` -> Librarian) is built right after `AutomationReferences` and starts after the retention sweep, in normal startup only; both before the Channel, Cron and Calendar starts and the `channel_send` sync; `cron`/`bash` when dependencies exist. Runtime includes Calendar in stop, asynchronous close, and failed-startup cleanup. Bootstrap registers no Tool and does not activate here.
8. **Sub-agents & prompts** - SubAgentCoordinator, sub-agent tools and `status`, Extension Tools applied **last**, SystemPromptManager, then the `startup_summary` (`RuntimeStartupSummary`: Tool, Skill, usable Provider/Connection and loaded Extension counts plus keep-awake) that the server's start line reports. The Runtime's own startup and shutdown lines are DEBUG; its `LogManager` is opened at startup and closed at shutdown (`logging.md`).

`safe_startup_mode` is only `verification` or `test`. It constructs the core graph but suppresses Extension dependency activation and Extension loading, plus Bootstrap, Channel, Cron, Calendar, and Provider-usage producers, the archive retention sweep and the Librarian's schedule. The performance monitor is a passive observer and starts in every mode once startup completes (`tests/core/runtime/test_runtime_lifecycle.py`). Normal startup alone activates managed Extension dependencies before Extension discovery.

Extension-owned temporary execution groups receive `streaming_chat_loop` through the existing host operations seam, so their Runs expose the same in-flight output and request diagnostics as interactive Chat (`test_runtime_extension_host.py`).

## Shutdown

`stop()`, `aclose()` and failed-startup cleanup run one dependency-ordered step list (`_shutdown.py`); failed-startup cleanup runs the synchronous operations like `stop()` but only logs step failures.

- `aclose()` is the variant accessors in event loops should prefer. It closes Extension mutation admission, drains admitted reload/startup/disable work, shuts down the final registry and closes the Extension databases its handlers left open before withdrawing readiness and stopping producers (Channels/Cron/Calendar actions/Bootstrap, then the archive retention sweep, which ends a purge in progress before its next Session), then Trigger completion delivery (it writes still-pending results into canonical Sessions, `automation.md`), Reflection, the Librarian (cancels passes in progress; their consolidation Runs end with the Runs), titles, and ChatRunManager close - rejecting new work, cancelling queued work, waiting active Runs plus cancellation cleanup - and the Sub-Agent activity files writing those Runs' outcomes (`SubAgentCoordinator.drain_activity`, `subagents.md`) before Decisions, Speech, Provider usage (sampler and `provider-usage.db`), the Debug traces Provider calls handed off (`drain_debug_traces`, `debug.md`), the performance monitor, Process/Terminal managers (killing every tracked process and Terminal tree), Keep Awake, temporary files, Channel state (`channels.db`), the Recall and Statistics indexes, `model-usage.db`, and canonical Sessions close. An active performance Recording is discarded, not written. No Runtime-owned background task may outlive its services.
- `stop()` runs the same steps synchronously and is safe pre-start. It withdraws readiness before its first step, fires Extension shutdown handlers without draining admitted Extension work, and skips the steps that need the Event Loop (Trigger delivery, Reflection, titles, Runs, Sub-Agent activity files, Debug traces).
- Failure isolation: a step that raises an `Exception` is logged at ERROR with its step name and traceback while logging is still open, and the remaining steps still run. Service references are cleared and logging is closed in every case. Afterwards a single failure is re-raised unchanged (an unterminated Terminal tree stays a `TerminalManagerError`), several as one `ExceptionGroup`. Cancellation and other `BaseException`s are not collected: they end the remaining steps and propagate once references are cleared and logging is closed. Callers need not log a raised failure again: the server lifespan only reports it to the stop line and exit status (`server.md`).
- `aclose()` callers share one cleanup task; caller cancellation propagates only after cleanup settles, and a later call reports the same outcome without running any step again. `start()` after a finished close rebuilds every service.
- Coverage: `test_runtime_lifecycle.py::test_runtime_shutdown_runs_every_step_before_reporting_failures` pins both step orders and the failure contract; `test_failed_start_logs_once_releases_started_resources_and_can_retry` pins failed-startup cleanup. The root `tests/conftest.py` fails a test whose loop-started Runtime is still started or left its performance monitor or a canonical database open.

SpeechService's local model and worker are closed in synchronous stop, async
close (after active Chat Runs drain), and failed-startup cleanup. Coverage:
`tests/core/runtime/test_runtime_lifecycle.py::test_runtime_registers_local_speech_and_closes_its_executor`.

## Service properties

Explicit typed service declarations share the read-only readiness/availability guard in `_service_access.py`; special properties retain their individual contracts. Initial construction and every shutdown use the same service-reference initializer, including Extension host groups and the selected Recall integration.

All service properties raise `RuntimeError` outside a started runtime, **except `extensions`** (returns `None`); `chat_runs` is a plain attribute until `start()`. `config` is available pre-start (bind resolution). Non-obvious members beyond self-describing services:

- `provider_credentials` - the central resolver also exposed via `has_provider_credentials`/`get_provider_credentials`; `resolve_environment_credential(key)` resolves env-first without exposing values, `environment_credential_source(key)` reports provenance. On Windows the `.env` fallback matches names case-insensitively (later entry wins), like process environment and Skill `env` requirements, so a granted mixed-case Skill name resolves its upper-case `.env` value. Web Search, Web Fetch, Extensions, and Channels consume this shared instance so live `.env` reloads reach every credential-backed subsystem.
- `tools` - full built-in roster lives in source; `analyze_image` registers but Chat gates its Model-facing visibility on route capability plus ImageService availability; `channel_send` registers dynamically while >=1 valid Agent owns an enabled Channel (adapter liveness irrelevant).
- `file_read_state` - the shared read stamps and mutation locks behind read, the file edit Tools (apply_patch, edit, write) and chat `@`-mention snapshots.
- `command_dispatcher` - the canonical stable dispatcher; server/accessor code must reuse `runtime.chat_loop` / `runtime.streaming_chat_loop` / `runtime.command_dispatcher` - no probing, no fallback construction (stub runtimes must provide them).
- `build` - the `BuildIdentity` of the running code (`core/utils/version.py`: version, source commit, and release or branch), resolved once at startup because a checkout's HEAD moves on while the process keeps running its startup code. A packaged version reads it from its `release.json` (`channel` `main` names branch `main`, anything else is an official release); a Git checkout, Worktree included, from its HEAD files without running Git, where a detached HEAD counts as a release only when the tag `v<version>` points at it. The System Prompt's `{vbot_version}` and `settings.get` `general.build` read it (`tests/core/utils/test_version.py`).
- `performance` - the process `PerformanceService` (Event Loop monitor, stall watchdog, Recordings under `artifacts/performance/`); instrumented code records through the module-level `core.performance` functions instead of this property (`performance.md`).

`decisions` owns the Decision Task Model executor and independent experiment/control tasks. Runtime constructs it after TaskModelService, registers `evaluate`, and drains/cancels it on shutdown. Accessor navigation does not affect its lifecycle (`model_tasks/decisions.md`).

`live_voice` (`LiveVoiceService`) is constructed after TaskModelService and holds no background work itself; the server's call registry owns active Live calls and ends them in the lifespan before the Runtime closes (`model_tasks/live.md`).

### Hot-reload seams

Reload methods refresh already-wired consumers without restart. Provider/Model registry identities stay stable; Skill, Extension, and Recall registries can be replaced through the live callbacks and installation paths below:

- `apply_settings_change(previous, current, refresh_sections=...)` applies all live effects after one validated Settings write and returns `SettingsChangeEffects(commands_changed, skills_changed)`: whether the Extension layer (Commands, page registrations) and the Skill layer changed. Callers keep the mutation serialized through this await. The private `_settings.py` owns reload dependencies: full Extension rebuild covers Recall/Prompts/Skills, surgical disable covers Prompts/Skills and removed-backend recovery but must not suppress an independently changed Recall selection. Explicit Skills/Recall section saves retain their refresh semantics even when values are unchanged. A changed `model_tasks.speech_to_text` binding calls `SpeechService.preload_configured()` (`model_tasks/speech.md`). Tests: `test_runtime_settings.py` owns the reload decision table; `tests/server/rpc/test_settings_methods_update.py` covers only the RPC wiring.
- `reload_custom_providers()` - Settings-owned Providers + manual Models into existing registries.
- `maybe_refresh_local_catalogs(force=False)` - staged copy refresh for auto-refresh Connections, published atomically after validation; failures never raise and leave the last database untouched.
- `reload_skills_async()` scans through the named Runtime worker pool and installs the replacement on the Event Loop; async callers, including Extension reload/disable, use it instead of the synchronous variant. If credentials reload during the scan, the replacement receives the current requirement environment before publication without discarding scanned package changes (`test_runtime_skill_cache_races.py`).
- Sync and async Skill reloads share a Runtime-owned generation: only the latest requested scan can publish, and shutdown invalidates pending results even across a restart. Async scans capture their original Skill owner before worker admission (`test_runtime_skill_cache_races.py`).
- `reload_skills()` - asks `core/skills/runtime.py::SkillRuntime` for a replacement global registry, then re-registers Skill Tools and updates prompts. `SkillRuntime` owns scan-layer resolution, Project/Agent/shared scoping, inventory, and both scoped registry caches; Runtime preserves the existing public facade methods.
- `reload_recall_backend()` re-registers `session_search` from settings without restart. `_recall.py::RecallIntegration` (the `Runtime.recall` service) owns the live backend/registry, Extension fallback, the Settings timezone loader handed to `session_search` for offset-less periods, the shared Passage index with its `SemanticIndexer` (started with the other Event Loop services outside safe-startup mode, nudged by every terminal Run and by `text_embedding` binding changes in `apply_settings_change`), and best-effort deleted-Session and deleted-Agent index cleanup (`recall.md` -> Semantic Indexing, Lifecycle & Removal); Runtime retains the public readiness boundary.
- `reload_keep_awake()` holds/releases the Windows power request per persisted setting (no-op elsewhere).
- `reload_channel_tool()` syncs `channel_send` registration with enabled-Channel existence.
- `reload_environment_credentials()` refreshes the `.env` fallback inside the same resolver instance so every startup-injected consumer sees key/secret/token writes immediately, including requirement snapshots in all cached Skill scopes.
- `reload_extensions()` and `apply_extension_disabled_change(...)` delegate the serialized rebuild/deactivation sequence to `core/extensions/runtime.py::ExtensionRuntime`. Runtime supplies the stable Tool/Command registries plus Recall, Skill, and Prompt refresh callbacks; the Extension owner holds the mutation lock, module purge, registry swap, lifecycle ordering, and last-write-wins behavior. Session-owning Extensions quiesce their exact owned work before capability removal; retired registration callbacks fail closed. Ordinary hooks retain their existing failure isolation.
- Surgical disable removes deactivated Extension backends from the selectable Recall catalog even when the active backend is unaffected; that active instance is retained unless its configured backend was removed.
- Owner-bound Extension hosts receive temporary execution groups, safe editor catalogs and existing Statistics projections (over the Runtime's shared `statistics_index`) through injection. Whole-roster preflight uses ordinary Model, Tool/settings and Project-ceiling validators off the Event Loop, then rechecks the loaded registration before admission. `_extension_host.py::ExtensionHostFactory` owns these groups and projections with explicit services and live registry/Skill callbacks; it never receives the Runtime object. Source/tests: `_extension_host.py`, `tests/core/runtime/test_runtime_extension_host.py`.
- Editor catalogs project Model reasoning capabilities and context size, plus Tool family/activation metadata, from their existing registry owners so isolated editors can use the shared selectors without inventing capability defaults (`test_runtime_extension_host.py`).
- Editor catalogs also expose System Prompt block metadata. Owner-bound `inspect_prompt` resolves a prospective temporary Agent with ordinary Project ceilings, applies Chat's Model-specific Tool routing and the owner's private Tool grants, then returns the combined prompt, rendered block details and effective Tool definitions. Inspection creates no Session or Run and rechecks registration identity after asynchronous work (`test_runtime_extension_host.py`).

The storage scope adapter and Tool/Extension Prompt-block contributions live together in `_prompt_blocks.py`; bootstrap and reload use the same projection.

### Provider operations

Runtime preserves `get_adapter(ConnectionRef)`, token getter/extra access, Reasoning description, local Context-window reads, and local-catalog refresh as facade methods. `core/providers/runtime.py::ProviderRuntime` owns their implementation, including the authoritative Adapter map, credential/token construction, Debug recorder injection, local Context resolver, refresh throttle/staging, and Connection reachability state. `ConnectionRef` is a frozen dataclass in `core/providers/accounts.py` bundling the Provider id and its compositional `provider:connection[:account]` Connection id.

### Identity Agent rename

`rename_agent(agent_id, new_agent_id)` -> `AgentRenameOutcome` is the one entry for renaming an Identity Agent; `agent.rename` calls it under its guards (`server.md`). `_agent_rename.py` owns the order: it first lists the references that already name the new id (`identity_agent_references`: Channels, non-terminal identity Cron and Bootstrap jobs and every Calendar action of the id, also one that can no longer fire, since a revert would move it too) and hands them to `AgentStore.rename`, which refuses the rename with `AgentReferencedError` after its own existence checks while they name it (`agent.md`); otherwise `AgentStore.rename` removes the delegation allow-list entries that name the unused new id, applies the Agent-owned half and leaves the rename record pending (`agent.md` -> Rename crash safety), then Channels (`retarget_agent_async`; only a started Channel service rebuilds adapters), non-terminal identity Cron jobs (`retarget_agent_async`) and Bootstrap jobs (`retarget_agent`) and Calendar actions (`retarget_identity_async`) move, and `finish_rename` removes the record. The rename runs on the Event Loop, which owns the state of these running services: it lists and moves the references there (`test_a_live_rename_moves_every_reference_or_none` asserts no job or action is read or changed off it) and runs each blocking Agent-store step (`rename`, `revert_rename`, `finish_rename`) as its own call on the Session database's pool. It never holds a pool worker while it waits for the loop or for more pool work, which the Cron and Calendar moves need (they check Sessions on that pool), so renames and other pool work cannot starve the pool into a deadlock (the same test gives the pool a single worker). The whole rename, revert included, is one compound mutation entered on the loop (`compound_mutation_async`, `database.md`), and a cancelled caller waits until the rename or its revert has settled. A rename that completes at startup, before they start, uses their blocking variants, which refuse once the owner runs. A failure reverts all of it through `revert_rename` and the same steps with the ids swapped. Runtime owns this order because it alone owns every referencing service: AgentStore must not depend on Channels, Cron or Calendar, and the server edge does not run at startup, where an interrupted rename must finish (Bootstrap steps 4 and 7). Afterwards Runtime invalidates both ids' Skills and removes the moved Sessions' old addresses from the Recall indexes, best effort (`tests/core/runtime/test_runtime_agent_rename.py`). `agent_references(agent_id)` (async), which the `agent.delete` guard awaits, names only what would still start Runs or answer as the Agent: its Channels, whose configs it reads off the Event Loop (`list_channels_async`), plus `AutomationReferences.agent_references` (`automation.md`); delegation allow-lists do not count, because the archive records and removes the Agent from them (`archive.md`).

## Constraints & Gotchas

- First-start recovery creates a bootstrap Agent (`main`/`Main`, shifting to free `main-N` when an invalid preserved directory occupies the name), including first empty Session as current pointer. Existing directories with any valid Agent are preserved - no second `main`.
- Invalid individual Agent/Project configs skip individually; Projects need only `project_id` + `cwd`.
- The bootstrap Agent ensures **before** ChannelService starts so a channel targeting `main` recovers on first start. A pending Agent rename finishes its Agent-owned half before the first roster read and that ensure, and moves its references before any reference owner starts (`test_runtime_agent_rename.py`).
- Channel/Cron starts, the usage collector and the performance monitor share the event-loop guard: wired but not started when no loop exists. Channel startup failures isolate to failed health state; Cron storage corruption disables scheduling without failing startup and protects state from overwrite.

Extension Tool consumers resolve their calling Agent through `ExtensionHost.resolve_tool_agent(context)`. Runtime checks the canonical temporary Session binding against the execution owner before temporary resolution, otherwise uses normal Identity/Project resolution. A context whose Session does not exist is a call outside any Session (Extension management such as MCP `explore`/`invoke`): without an execution owner it resolves the addressed Agent with no Session overrides; with one it fails (`Temporary Tool invocation no longer owns this Session`). MCP policy and sampling share this seam (`tests/core/runtime/test_runtime_mcp_access.py`).
