# Runtime

Bootstrap entry point. Wires services and manages start/stop lifecycle.

Blocking in-process work crosses named `BoundedWorkerPool` boundaries from `core/utils/workers.py`. Each pool owns a dedicated executor, admits at most its configured worker count per Event Loop before submission, and defers cancellation until an already-started mutation settles; continuous Terminal backend I/O remains on its separate executor path so it cannot consume parser, prompt, Session, or Tool capacity.

## Interfaces

`core/runtime/interfaces.py` - `typing.Protocol` DI contracts. Only `ConfigProtocol` is constructor-injected; the rest are structural typings used for DI/testing. `core/runtime/__init__.py` re-exports `ConfigProtocol`, `LoggerProtocol`, and `RuntimeServices` plus the `Runtime` class; `ProviderCredentialResolverProtocol` is imported directly from `interfaces.py` where needed, not re-exported.

- `ConfigProtocol` - `get(key: str, default: Any = None) -> Any` (the one injected dependency).
- `LoggerProtocol` - `debug/info/warning/error(msg, *args)`; types the public `logger` attribute.
- `ProviderCredentialResolverProtocol` - `has_credentials` / `is_connection_enabled` / `is_usable` / `get_credentials` / `list_accounts` / `resolve_account_id`; the central Provider credential and Connection usability contract (`RuntimeServices.provider_credentials`; usable = enabled + credentialed, `providers.md` -> Terms -> Usable; details in `providers/connections.md`).
- `RuntimeServices` - the service surface of a *started* runtime for the remaining core modules that genuinely coordinate across the whole Runtime, including Sub-Agent coordination, reflection/title helpers, and Chat file-mention root resolution. `ChatLoop` and Tool dispatch deliberately do not consume this contract: Runtime constructs Chat-owned `ChatLoopDependencies`, and Chat projects those collaborators into a Run-local execution context. `RuntimeServices` exposes read-only properties `agents`, `providers`, `models`, `provider_credentials`, `storage`, `chat_sessions`, `chat_run_manager`, `tools`, `skills`, `extensions` (`ExtensionRegistry | None`), `system_prompts`, `process_manager`, `terminal_manager`, `streaming_chat_loop`, plus `get_adapter(provider_id, connection_id)`. A missing attribute is a wiring bug, not a silently disabled feature - consumers access services directly, never via `getattr` probes. The heavy service types are imported under `TYPE_CHECKING` only, and consumers must likewise import `RuntimeServices` under `TYPE_CHECKING` (a runtime import of `core.runtime` loads `Runtime` and everything behind it - import cycle).

## Runtime class

`core/runtime/runtime.py` - constructor injection via `ConfigProtocol`.

`__init__` resolves the data dir (`DATA_DIR` / `VBOT_DATA_DIR` / `config.data_dir`) and builds `LogManager(level=config.get("LOG_LEVEL", "INFO"), data_dir=...)` before any bootstrap logging. The `vbot.core` logger itself is created later, in `start()`.

### `start()`

Idempotent - a second call logs at debug and preserves the existing service instances. Boot runs in dependency order through these phases:

1. **Storage & settings** - create the `vbot.core` logger and record `started_at`; build `StorageManager` with its canonical non-destructive layout initializer and start its temporary-file sweeper; load usable `settings.json` values and the upload-size limits. Invalid Settings never abort startup: malformed/non-UTF-8 JSON or root shape falls back to defaults, schema-invalid top-level keys are logged and omitted individually while valid siblings stay active, the source file is never rewritten, and Settings mutations stay strict so they cannot overwrite invalid data. Data-directory creation/write failure remains fatal.
2. **Attachments & credentials** - instantiate the runtime-owned `AttachmentStore`; read `<data_dir>/.env` as a fallback credential snapshot **without** mutating `os.environ` (unreadable `.env` becomes an empty fallback).
3. **Providers & models** - tolerantly load bundled Provider config plus the normalized Custom Provider overlay, select the newer compatible complete Model DB root (the two roots are never mixed), assemble it tolerantly with manual Custom Models, and wire the OAuth `TokenStore` plus the central `ProviderCredentialResolver` (process environment wins over the data-dir fallback). Invalid fragments are logged and omitted while valid siblings remain; Custom Provider registries stay instance-local even when Runtimes share bundled resources.
4. **Task services, agents, processes** - create `TaskModelService` and the speech/image/embedding services; wire `AgentStore` with a live defaults provider so resolved reads always use current persisted defaults; create `ProcessManager`. Invalid/unreadable individual Agent configs degrade to the remaining roster; bootstrap creation continues.
5. **Tools, extensions, skills** - create `ToolRegistry` + `MemoryService` and register the built-in Tools (the authoritative roster lives in the source and `tools.md`); load the `ExtensionRegistry` and `SkillRegistry` and register `skill`/`skill_manage` (ordinary configurable Tools; `skill_manage` carries an Identity-Agent constraint). Unreadable scan roots and invalid individual Extensions/Skills are diagnosed and omitted, never fatal.
6. **Sessions, recall & chat** - create `ChatSessionManager` and register the Session-scoped `history` Tool immediately (**before** extension tools, preserving built-in name ownership), then Project/Agent resolution and the bootstrap Agent (before channels - see Gotchas); create the `RecallBackendRegistry` (`jsonl_scan` construction failure stays fatal because no canonical fallback remains) and register `session_search` + derived `session_read`; create `ChatRunManager`, `ReflectionService`, the shared title service, the explicit Chat-owned `ChatLoopDependencies`, and the non-streaming/streaming chat loops with one shared `CompactionService`.
7. **Automation surface** - wire `TriggerService` (streaming loop for programmatic Runs, non-streaming loop for manual Compaction); start `TerminalManager`; construct `BootstrapService`; only then construct the end-to-end `CommandDispatcher` and apply loaded Extension Commands to that stable dispatcher; wire + start `ChannelService` with the same instance and register `channel_send` (>=1 valid Agent with an enabled config, independent of adapter liveness); register `cron` and `bash` when their dependencies exist. Bootstrap has no Tool registration and is not activated during `Runtime.start()`.
8. **Sub-agents & prompts** - create the `SubAgentCoordinator`, register sub-agent tools and `status`, apply loaded Extension Tools **last** so built-ins retain name ownership, build `SystemPromptManager`, and write the one info-level startup inventory summary.

### Shutdown

- `stop()` - logs `Runtime stopped` if a logger exists, stops `ChannelService` / `CronService` / `BootstrapService` / the Provider usage collector / `ProcessManager` / `TerminalManager`, thereby killing every tracked background process and Terminal Session tree, then stops the shared temporary-file sweeper, clears all service references (including `token_store`), and closes the log manager. Safe to call before `start()`.
- `aclose()` - async variant of `stop()`: after stopping Channel, Cron, and Bootstrap producers, it closes Trigger completion delivery, Reflection, Session titles, and `ChatRunManager`, rejecting new work, cancelling queued work, and waiting for active Runs plus their asynchronous cancellation cleanup before closing Provider usage, Process and Terminal managers, and temporary files. Accessors running inside an event loop should prefer `aclose()` over `stop()`; no Runtime-owned background task may outlive the services it uses.

### Service properties

All service properties raise `RuntimeError` before `start()` and after `stop()`, **except `extensions`**, which returns `None` instead of raising. `chat_runs` is a plain attribute (not a property) that is `None` until `start()`.

- `config` - the injected `ConfigProtocol`. Unlike the service properties it is available **before** `start()`; the server uses it for pre-start bind resolution.
- `logger` - public attribute, `LoggerProtocol | None`. Set by `start()`.
- `providers` / `models` - provider and model registries.
- `provider_credentials` - central provider credential resolver; also exposed through `has_provider_credentials(provider_id)` and `get_provider_credentials(provider_id)`. `resolve_environment_credential(key)` resolves a single environment credential with process-env-first precedence, while `environment_credential_source(key)` reports `process_environment`, `data_dir`, or `None` without exposing the value. Web Search, Extensions, and Channels consume the shared resolver so live fallback reloads reach every credential-backed subsystem.
- `provider_usage` - shared `ProviderUsageService` for coalesced live Provider subscription-limit reads and durable hourly observations under `<data_dir>/statistics/provider-usage/`.
- `token_store` - OAuth token persistence service rooted at `<data_dir>/oauth/`.
- `storage` - `StorageManager` for data-dir/settings/prompt fragments and the internal shared temporary-file lifecycle exposed as `storage.temporary_files`.
- `attachment_store` - runtime-owned `AttachmentStore` rooted at `<data_dir>/artifacts/attachments/`.
- `speech_upload_max_size_bytes` - max accepted uploaded-audio size for transcription (`settings.json` `speech_upload_max_size_bytes`).
- `agents` - `AgentStore` for agent CRUD/workspaces, wired to `settings.json` `defaults.agent`.
- `tools` - runtime `ToolRegistry` with every built-in registered at startup (the roster lives in the source; per-tool ownership in `tools.md`). `analyze_image` remains registered but Chat withholds it from Model-facing definitions unless its effective-route gates pass. `channel_send` is registered dynamically while >=1 valid Agent owns an enabled Channel config; transient adapter start/stop/failure/restart never changes its registration. The Home Assistant tools apply only when the bundled extension loads with `HASS_TOKEN` configured.
- `process_manager` - shared in-memory `ProcessManager` used by `bash` and `process` tools. Owns tracked processes (`TrackedProcess`), output buffers, TTL sweeping, Run-scoped cancellation, graceful process-tree teardown, and the launch seam shared with server-level crash containment.
- `terminal_manager` - shared in-memory `TerminalManager` used by `terminal`. Owns PTY/ConPTY children, VT rendering, attention delivery, TTL sweeping, and vBot Session-scoped lifetime across Runs (see `tools/terminal.md`).
- `file_read_state` - the shared `FileReadState` read-before-write guard injected into `read`/`write`/`edit`; also stamped by the chat layer's `@`-mention snapshot expansion (see `tools/file_state.md`).
- `skills` - `SkillRegistry` loaded from `<data_dir>/skills`, bundled `resources/skills`, and configured extra `skill_directories`.
- `skill_authoring` - shared `SkillAuthoringService` used by `skill_manage` and the Skill-mutation RPCs. It owns direct atomic UTF-8 writes, Skill-document validation, provenance, support-file path confinement, and deletion; it refuses writes under the bundled Skills root.
- `extensions` - `ExtensionRegistry | None` loaded from `<data_dir>/extensions` and configured `extension_directories`. Unlike the other service accessors it does **not** raise before `start()` - it returns `None`.
- `model_tasks` - `TaskModelService` for specialized task-model settings, credential-gated target discovery, and backend-owned option schemas.
- `speech` - `SpeechService` for configured speech-to-text, text-to-speech, and speech artifact lookup.
- `image` - `ImageService` for configured image generation, isolated image understanding, and image artifact lookup.
- `chat_sessions` - `ChatSessionManager` rooted at runtime data dir.
- `recall_backend` - selected `RecallBackend` used by `session_search`; `session_read` bypasses derived Recall and reads canonical Session storage.
- `chat_run_manager` / `chat_runs` - shared `ChatRunManager` used by server chat flows and automation triggers.
- `command_dispatcher` - stable shared end-to-end `CommandDispatcher`: prepares and executes every Built-in and currently applied Extension Command and returns neutral outcomes to RPC and Channel projectors.
- `chat_loop` / `streaming_chat_loop` - resolver-wired non-streaming / streaming `ChatLoop` for server non-SSE and SSE flows respectively.
- `trigger_service` - `TriggerService` for programmatic Run starts and in-memory busy-Session queueing.
- `reflection` - `ReflectionService` for fork-based self-improvement reviews: the `/reflect` orchestration seam and the background run-end cadence trigger (see `automation.md`).
- `channel_service` - `ChannelService` for persisted channel configs, adapter lifecycle, and outbound platform delivery rooted at `<data_dir>/channels/`.
- `cron_service` - `CronService` for persisted cron and one-shot scheduled triggers rooted at `<data_dir>/cron/jobs.json`.
- `bootstrap_service` - `BootstrapService` for persisted startup-triggered Runs rooted at `<data_dir>/bootstrap/jobs.json`; `activate_bootstrap()` is the serving-layer hook and must remain separate from construction.
- `system_prompts` - `core.prompts.SystemPromptManager` using runtime storage/tools/skills.

### Hot-reload methods

- `reload_custom_providers()` - reload normalized Settings-owned Provider definitions and manual Models into the existing Provider and Model registry objects. Registry identity stays stable so already-wired credential, task-model, status, and Recall consumers observe create/edit/delete immediately without a restart.
- `maybe_refresh_local_catalogs(force=False)` - refresh enabled auto-refresh Connections inside a staged copy of the active complete Model DB, publish it atomically to `<data_dir>/artifacts/models/` only after validation, and reload the registry in place. Discovery or publication failures never raise and leave the last published database untouched.
- `reload_skills()` - reload the skill registry from current settings, drop the cached per-project and per-agent registries, re-register the `skill` and `skill_manage` tools, and update `SystemPromptManager` so prompt catalogs and provider tool visibility use the new registry without restarting the app. The runtime also exposes `agent_skills_dir(agent_id)`, `skills_for(project_id, identity_agent_id=None)` (the agent layer applies only to an **existing identity** agent - callers pass the run's agent id for identity runs only, and the runtime double-checks `agents.exists` so a stray unowned `agents/<id>/skills` dir is never layered), and `invalidate_agent_skills(agent_id=None)` for the agent-aware skill pool.
- `reload_recall_backend()` - reload the configured Recall backend from `settings.recall.backend` and atomically re-register both Session Recall Tools so Settings UI backend changes take effect without restart.
- `reload_keep_awake()` - re-read the persisted `keep_awake` setting and hold/release the process power request accordingly (Windows `PowerRequestSystemRequired`; other platforms no-op). Applied at startup in `start()`, live on Settings change via the shared delta hook, and released in `stop()`/`aclose()`. See `core/runtime/keep_awake.py`.
- `reload_channel_tool()` - unregister/re-register `channel_send` to match `channel_service.has_enabled_channels()` so persisted Channel create/delete/enable/disable stays in sync without coupling Tool registration to adapter liveness.
- `reload_environment_credentials()` - reload the data-dir `.env` fallback snapshot used by `resolve_environment_credential` and into the existing `ProviderCredentialResolver`. Resolver identity is stable for the whole started Runtime so every startup-injected consumer (`ChatLoopDependencies`, `AgentResolver`, `TaskModelService`, Channels, Extensions, Web Search, and other credential gates) observes Provider-key, Extension-secret, and Channel-token writes immediately instead of retaining a stale pre-reload snapshot.
- `reload_extensions()` (async) - rebuild the **whole** extension layer from disk in the running process, restart-equivalent (end state == a restart from current persisted settings). The seam behind the `extensions.reload` RPC and behind *enabling* an extension. Under `_extension_reload_lock`: read fresh settings, detach the old layer's Tools and Commands, `await fire_shutdown()`, `purge_extension_modules()`, `ExtensionRegistry.load(...)` a fresh registry with the same args `start()` uses, swap, re-apply Tools and Commands to their stable registries + Recall (`reload_recall_backend`) + Prompt blocks (`_refresh_prompt_block_definitions`), then `await fire_startup()` on the serving loop. Async on purpose: startup/shutdown handlers may schedule background tasks on the live loop, so they are awaited directly, never driven through a blocking worker loop. See `.vorch/domain-maps/extensions.md`.
- `apply_extension_disabled_change(newly_disabled)` (async) - apply an extension **disable** live, without a restart. Called (awaited) by Settings after the new `disabled` set is persisted, with the names **added** to it. Under `_extension_reload_lock`: for each name it awaits `ExtensionRegistry.deactivate(name, self._tools, self._command_dispatcher)` (hooks off, Tools and Commands unregistered, shutdown fired, record -> `disabled`), then `_refresh_prompt_block_definitions()` so extension-owned blocks drop, and guards the Recall edge: if a deactivated Extension provided the currently active backend, it rebuilds the registry and re-resolves to the Built-in default (persisted `recall.backend` left untouched). Enabling - removing from the `disabled` set - is not handled here; it routes through `reload_extensions` instead. See `.vorch/domain-maps/extensions.md`.
- `_extension_reload_lock` (`asyncio.Lock`, created in `__init__`) - serializes **every** extension-layer mutation: both `reload_extensions` and `apply_extension_disabled_change` wrap their whole body in it, so rapid WebUI toggles / concurrent CLI/agent calls queue and run one at a time, each reading the then-current persisted settings (last write wins). The brief swap window where a run can still dispatch into an already-shut-down old extension is accepted (per-handler fail-open isolation) - no drain.

### Adapter factory

`get_adapter(provider_id, connection_id)` builds an async provider-token getter for the selected connection and instantiates the class selected by `ProviderConfig.adapter`; the authoritative adapter-key set lives in `_ADAPTER_MAP` in `core/runtime/runtime.py`. The `openai` adapter is the single `OpenAIAdapter` class that covers both OpenAI Platform API-key access and ChatGPT subscription access; it branches on a per-connection `mode` (set from `ConnectionConfig.mode`) to pick `/chat/completions` vs `/codex/responses`. Every adapter also receives the connection's `mode` as a keyword-only `connection_mode` constructor argument; adapters with a single wire variant accept and ignore it. `api_key` connections resolve the static credential through `provider_credentials` and receive `StaticTokenGetter`; OAuth connections with `OAuthConfig` receive `OAuthTokenGetter` using `runtime.token_store`. OAuth stubs that still have a credential key but no OAuth metadata stay static-credential connections until configured otherwise. Every adapter also gets a provider-scoped, read-only `model_lookup(model_id) -> Model | None` backed by `ModelRegistry`, and - when Debug Mode is enabled - a `ProviderDebugRecorder` built from debug settings; HTTP wires capture through the shared client transport, while the OpenAI Subscription WebSocket feeds the same recorder at its exchange boundary. `get_model(provider_id, model_id)` is a thin convenience over `ModelRegistry.get`.

## Constraints & Gotchas

- On startup with no valid Agent, Runtime creates a bootstrap Agent. It uses `main` / `Main` when that directory is free; if an invalid preserved Agent directory already occupies `main`, it uses the first free `main-N` id. Agent creation also creates the first empty Session and persists it as `current_session_id`.
- Existing data directories with at least one valid Agent are preserved; Runtime does not add another `main` Agent just because `main` is absent. Invalid individual Agent configs are logged and skipped by collection loading, so they do not block Runtime or the remaining Agents from starting.
- Invalid individual Project configs are skipped by Project collection loading and do not block valid Projects. Only `project_id` and `cwd` are required to load a Project; optional presentation/default metadata is reconstructed from defaults.
- The bootstrap Agent is ensured **before** `ChannelService` starts, so a configured channel targeting `main` can come up during first-start recovery.
- `ChannelService.start()`, `CronService.start()`, and the Provider usage collector share the event-loop guard: when Runtime startup happens without an active asyncio loop, each service is wired but its background listeners/sampler are not started.
- Channel startup failures are isolated to the channel service and recorded as failed channel health state; they must not fail `Runtime.start()`.
- Invalid individual Cron entries are skipped while valid siblings schedule. Malformed whole Cron storage disables scheduling without failing `Runtime.start()` and is protected from overwrite until repaired.
- Runtime owns the canonical resolver-wired chat loops (including their compaction service) and the canonical `CommandDispatcher`. Server/accessor code must reuse `runtime.chat_loop` / `runtime.streaming_chat_loop` / `runtime.command_dispatcher` - the server no longer probes for them or constructs fallbacks, so a stub runtime handed to `create_app` must provide them.
