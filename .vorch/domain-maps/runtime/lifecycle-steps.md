# Runtime Lifecycle Steps

Every bootstrap phase of `start()` and every shutdown step of `aclose()` in order, with the reason a service sits where it does. The ordering invariants, the post-startup services, safe startup mode and the shutdown failure contract are in `runtime.md` -> Bootstrap, Shutdown.

## Bootstrap phases

Startup failure logging: before cleanup closes logging, the guard writes the failure once at ERROR with its traceback (`Runtime startup failed`); it marks that exception so the uvicorn log proxy suppresses the duplicate traceback after the host logging pipeline is restored, unless the data root does not exist, which is never created just for the log. Cleanup runs outside the exception handler, so a failed step's log entry does not repeat the startup traceback as its context. The cleanup guard starts before Storage construction and clears startup identity and readiness (`tests/core/runtime/test_runtime_lifecycle.py`).

1. **Storage & settings** - logger + `StorageManager` + settings load. Invalid Settings never abort startup: malformed JSON or root shape falls back to defaults, schema-invalid keys omit individually while siblings stay live, the source file never rewrites, and mutations stay strict so they cannot overwrite invalid data. Data-dir creation failure is fatal.
2. **Attachments & credentials** - first `settle_plaintext_credentials` (the plaintext credential conversion step for this start mode, `secrets.md`), then (normal startup only, not an update's verification start, after the temporary-file service started) the release of `RETIRED_CANONICAL_DATABASES` (`database/snapshots-and-recovery.md` -> Unregister and retire), then AttachmentStore plus the data-directory credential snapshot from the Secret Store, read without mutating `os.environ`.
3. **Providers, models & canonical Sessions** - tolerant load of bundled config + Custom Provider overlay; each generated Model DB catalog selected from the root that fetched it last (`models.md`); OAuth token store and the central credential resolver wired. `ChatSessionManager` opens canonical Sessions before `UsageRecorder` receives it as its lineage source.
4. **Task services and agents** - TaskModelService + per-task services (the stateless `DecisionService` and `LiveVoiceService` follow TaskModelService); one optional LocalSpeechExecutor supplies its catalog to TaskModelService and execution to SpeechService without loading ML packages/weights; AgentStore with live defaults provider, whose `recover_rename()` then finishes the Agent-owned half of a rename the last process left pending, before anything reads the roster. Invalid agents degrade individually.
5. **Tools, extensions, skills** - ToolRegistry + built-in registration, then extension/skill registries and `skill`/`skill_manage`. Unreadable roots diagnose-and-omit, never fatal.
6. **Sessions, recall & chat** - the already-open Runtime-owned `ChatSessionManager` uses the marker-authorized `<data-dir>/sessions.db` with lightweight readiness checks and is injected into AgentStore, ProjectStore, Recall, Statistics, and Chat. The Runtime builds the one disposable `StatisticsIndex` (`statistics_index`) that the Statistics RPC service and the Extension host share (`statistics.md`). Normal Runtime operation never creates data snapshots; snapshot, restore and recovery workflows belong to the database kernel (`database.md`), which receives the open handles through `Runtime.canonical_databases()`. Project/Agent resolution and bootstrap Agent start **before** channels; recall defaults and falls back to `sqlite_fts`, whose construction failure is fatal because no lower registration fallback remains; ChatRunManager receives the shared Sessions persistence owner at construction; the `PerformanceService` is built right after it with the `runs.active`/`runs.queued` gauge samplers. Runtime builds Reflection, titles and ChatLoopDependencies, and supplies one CompactionService to its one Chat loop.
7. **Automation surface** - TriggerService (streaming loop for triggers, non-streaming for manual Compaction); TerminalManager; CommandManager (shell commands, `tools/shell.md`; started at once, its sweeper forgets finished commands); GoalService, which pauses the goals a previous Runtime left active before any Run starts (`automation/goals.md`); BootstrapService, CalendarService (its catalog preloaded before live Cron readers; it runs no task, so it is neither started nor stopped) and CronService (which serves the calendar's event jobs, `bind_event_jobs`), Bootstrap and Cron constructed but not yet started; `AutomationReferences` over Bootstrap and Cron (`automation.md`), then `LibrarianService` and `ArchiveService` (`runtime.archive`); only then the end-to-end CommandDispatcher, which receives the references for the Agent Takeover, and applied Extension Commands; ChannelService; a rename pending from step 4 then moves their references (`complete_pending_rename`); then the archive finishes or undoes interrupted archive operations, in every startup mode (`archive.md` -> Recovery); all before the Channel and Cron starts and the `channel_send` sync; `cron`/`bash` when dependencies exist. Bootstrap registers no Tool and does not activate here: the server activates it once its lifespan is ready (`activate_bootstrap`).
8. **Sub-agents & prompts** - SubAgentCoordinator (installed on the Run manager), then `SessionActivity` (`session_activity`) subscribed to Runs, commands, completion delivery and Sub-Agent forwarding (`activity.md`), sub-agent tools and `status`, Extension Tools applied **last**, SystemPromptManager, then the `startup_summary` (`RuntimeStartupSummary`: Tool, Skill, usable Provider/Connection and loaded Extension counts plus keep-awake) that the server's start line reports. The Runtime's own startup and shutdown lines are DEBUG; its `LogManager` is opened at startup and closed at shutdown (`logging/pipeline.md` -> LogManager). Only then does the token estimation encoding start loading on a daemon thread (`providers/request-policy.md` -> Wire media and request context); started with the earlier phases, it slowed startup by contending for the GIL.

## Shutdown steps of `aclose()`

`aclose()` is the variant accessors in event loops should prefer. It closes Extension mutation admission, drains admitted reload/startup/disable work, shuts down the final registry and closes the Extension databases its handlers left open, then stops the Provider usage sampler (a sample reads Provider credentials through the Runtime, which refuses once readiness is withdrawn), before withdrawing readiness, closing Session activity (step `session_activity`, async only: before the work it follows ends, so shutdown publishes no finished work, `activity.md`) and stopping producers (Channels/Cron/Bootstrap, then the archive retention sweep, which ends a purge in progress before its next Session, then the configuration backup schedule, which takes a last backup of changed configuration), then shell commands (`CommandManager.shutdown`, step `commands`: stopped before Trigger delivery closes, so each background command's "vBot shut down" result is submitted), then Trigger completion delivery (it writes still-pending results into canonical Sessions, `automation.md`), Session goals (step `goals`, before the Runs drain, so the Runs' cancellation starts no automatic turn), Reflection, the Librarian (cancels passes in progress; their consolidation Runs end with the Runs), titles, and ChatRunManager close - rejecting new work, cancelling queued work, waiting active Runs plus cancellation cleanup - and the Sub-Agent activity files writing those Runs' outcomes (`SubAgentCoordinator.drain_activity`, `subagents.md`), then the video jobs cancelled Runs left running (`VideoService.aclose` stops following them and logs each job id, `model_tasks/video.md`), before Speech (its local model and worker, closed in synchronous stop, async close and failed-startup cleanup; `test_runtime_registers_local_speech_and_closes_its_executor`), Provider usage (`provider-usage.db`), the Provider transports kept open between Runs (step `provider_transports`: the OpenAI Responses WebSockets, `providers/openai.md`; synchronous stop aborts them without a closing handshake), the Debug traces Provider calls handed off (`drain_debug_traces`, `debug.md`), the Provider wire observations those calls taught (`wire_observations`), the performance monitor, the command processes (`CommandManager.close`, step `command_processes`: kills what remains and withdraws undelivered results), the Terminal manager (killing every remaining Terminal tree), the page browser, Keep Awake, the Scratch areas, temporary files, Channel state (`channels.db`), the Recall index, embeddings (after Recall, whose indexer may still wait for one), the Statistics index (a running read holds its lock; `aclose` waits on its pool), `model-usage.db`, the attachment collection (only after every producer/Run drain succeeded, `attachments.md`) and canonical Sessions close.
