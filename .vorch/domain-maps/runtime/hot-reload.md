# Hot Reload

The Runtime's live reload paths: `apply_settings_change` and the Provider, local catalog, Skill, Recall, Keep Awake, Channel Tool, credential and Extension reloads that refresh already-wired consumers without restart. The generation rule and the stable-identity rule are in `runtime.md` -> Hot-reload seams.

- `apply_settings_change(previous, current, refresh_sections=...)` applies all live effects after one validated Settings write and returns `SettingsChangeEffects(commands_changed, skills_changed, agents_changed)`: whether the Extension layer (Commands, page registrations), the Skill layer and the shared Agent defaults (`defaults.agent`, which every Agent's effective configuration and Permission Rules resolve through) changed. Callers keep the mutation serialized through this await. The private `_settings.py` supplies its persisted snapshot to Recall, Keep Awake and timezone reloads instead of making those live callbacks read files again. It owns reload dependencies: full Extension rebuild covers Recall/Prompts/Skills, surgical disable covers Prompts/Skills and removed-backend recovery but must not suppress an independently changed Recall selection. Explicit Skills/Recall section saves retain their refresh semantics even when values are unchanged. A changed `model_tasks.speech_to_text` binding calls `SpeechService.transcription_binding_changed()` to retire unselected local STT models after accepted work; then each changed STT/TTS binding calls `preload_configured()` (`model_tasks/speech.md`). Tests: `test_runtime_settings.py` owns the reload decision table; `tests/server/rpc/test_settings_methods_update.py` covers only the RPC wiring.
- `reload_custom_providers_async()` reads Settings and assembles Provider/Model catalogs on bounded workers, then publishes into the existing registries on the Event Loop. Sync reload remains available outside async request handling. Overlapping registry reloads publish only the newest requested generation; Runtime captures the original owners and rejects a result superseded by another reload or shutdown/restart.
- `maybe_refresh_local_catalogs(force=False)` - staged copy refresh for auto-refresh Connections, published atomically after validation; failures never raise and leave the last database untouched.
- `reload_skills_async()` scans through the named Runtime worker pool and installs the replacement on the Event Loop; async callers, including Extension reload/disable, use it instead of the synchronous variant. If credentials reload during the scan, the replacement receives the current requirement environment before publication without discarding scanned package changes (`test_runtime_skill_cache_races.py`).
- Async Skill reloads share scans (`SharedRefresh`, `runtime/workers.md`): each caller waits for a scan that started after its call, so concurrent callers (every Project open of a picker) cost one running and at most one follow-up scan, and an explicit reload queued behind an editor refresh still invalidates every scope. Sync and async reloads share a Runtime-owned generation: a synchronous reload supersedes a running scan, which then cannot publish, and shutdown invalidates pending results even across a restart. Async scans capture their original Skill owner before worker admission (`test_runtime_skill_cache_races.py`).
- `reload_skills()` - asks `core/skills/runtime.py::SkillRuntime` for a replacement global registry, then re-registers Skill Tools and updates prompts. `SkillRuntime` owns scan-layer resolution, Project/Agent/shared scoping, inventory, and both scoped registry caches; Runtime preserves the existing public facade methods.
- `reload_recall_backend()` re-registers `session_search` from settings without restart. `_recall.py::RecallIntegration` (the `Runtime.recall` service) owns the live backend/registry, Extension fallback, the Settings timezone loader handed to `session_search` for offset-less periods, the shared Passage index with its `SemanticIndexer` (started with the other Event Loop services outside safe-startup mode, nudged by every terminal Run and by `text_embedding` binding changes in `apply_settings_change`), and best-effort deleted-Session and deleted-Agent index cleanup (`recall.md` -> Semantic Indexing, Lifecycle & Removal); Runtime retains the public readiness boundary.
- `reload_keep_awake()` holds/releases the Windows power request per persisted setting (no-op elsewhere).
- `reload_channel_tool()` syncs `channel_send` registration with enabled-Channel existence.
- `reload_environment_credentials_async()` reads the Secret Store's credentials (`StorageManager.load_environment`) on the Runtime worker and refreshes the fallback inside the same resolver instance on the Event Loop, including requirement snapshots in all cached Skill scopes. The synchronous variant stays available outside async request handling. Both share a generation, so a delayed read cannot restore credentials superseded by another reload or shutdown/restart.
- `reload_extensions()` and `apply_extension_disabled_change(...)` delegate the serialized rebuild/deactivation sequence to `core/extensions/runtime.py::ExtensionRuntime`. Runtime supplies the stable Tool/Command registries plus Recall, Skill, and Prompt refresh callbacks; the Extension owner holds the mutation lock, module purge, registry swap, lifecycle ordering, and last-write-wins behavior. Session-owning Extensions quiesce their exact owned work before capability removal; retired registration callbacks fail closed. Ordinary hooks retain their existing failure isolation.
- Surgical disable removes deactivated Extension backends from the selectable Recall catalog even when the active backend is unaffected; that active instance is retained unless its configured backend was removed.

Live Skill, credential and Custom Provider reload orchestration and generation-checked publication live in `_settings.py`; Runtime keeps their stable public entrypoints.
