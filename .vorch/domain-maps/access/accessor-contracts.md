# Access: accessor contracts

What an accessor (WebUI, Desktop, CLI/TUI, tray) relies on to reach a server in each Access Mode and to sign in. Rules and owners: `access.md`. Source: `server/access/_routes.py`, `_service.py`, `_guard.py`, `server/rpc/access_methods.py`; tests: `tests/server/test_access.py`.

## Errors and refusals

- HTTP errors of the guard and the `/api/auth/*` endpoints use the RPC envelope `{"ok": false, "error": {"code", "message"}}` with `Cache-Control: no-store`. Accessors branch on `code`, never on `message`.
  - 401 `auth_required` (`WWW-Authenticate: Bearer`): a protected request without a valid credential in `authenticated` mode. Show pairing or sign-in; a host tool re-reads the local access token once (the server writes a new one each start).
  - 403 `access_denied`: the peer or transport is not admitted (wrong network, proxy headers in `local`/`lan`, plain HTTP from another computer in `authenticated`), or the `Host` names no host the server knows (message "Access denied: unknown host name"). Retrying does not help; do not offer pairing.
  - 429 `rate_limited` with `Retry-After` (seconds): too many failed credentials, pairing starts or polls from this client.
  - 409 `auth_disabled`: pairing and login tickets exist only in `authenticated` mode.
  - 503 `devices_unavailable` with `Retry-After: 30`: the device store cannot be read or written; the host must repair it. In `authenticated` mode the guard answers it to a protected request, and to `GET /api/auth/status`, that carries a well-formed device token (`vbt_<device id>_<43>`, as Bearer or cookie): that credential may be valid, so it is neither accepted nor refused, not counted as a failure, and its cookie is not cleared. A missing or malformed credential still gets 401. Accessors keep the credential, show that the server cannot check sign-ins right now, and try again no sooner than `Retry-After`; never drop a token, delete a cookie or offer pairing for it. The `/api/auth/*` endpoints and the access RPCs answer the same code when they need the store.
  - 400 `invalid_request` (also 413/415 for an oversized or non-JSON body).
- RPC errors from the access RPCs travel in the normal `/api/rpc` envelope (HTTP 200): `auth_required`, `access_denied`, `rate_limited` (`data.retry_after`), `auth_disabled`, `devices_unavailable`, `invalid_request`, `pairing_not_found`, `device_not_found`.
- WebSockets refused by the guard are accepted and closed at once: 4401 (sign in), 4403 (not admitted) or 4503 (device store unavailable, as the 503 above), so the browser sees the code instead of a bare handshake failure. When a Device is revoked or expires, its open WebSockets close with 4401 `Device signed out`, its SSE streams and downloads end, and a request still waiting for its answer gets 401 `auth_required` ("Device signed out"). The request that revoked (for example `devices.logout`) still gets its answer. Accessors stop reconnecting on 4401/4403 and reconnect after 4503 no sooner than 30 s.

## Host names

Every mode answers only to a `Host` that is an IP address or a name the server knows: `localhost`, the server computer's host name (also short and as `<short>.local`), its bind host, the public URL's host, and each `--allow-host` (installer `-AllowHost`). This stops DNS rebinding. An accessor that reaches the server by another name (a LAN DNS name, a router alias) gets 403 "unknown host name" until the host adds that name with `--allow-host`. Several `Host` headers are refused. A reverse proxy passes the browser's `Host` through, or sets the public URL's host.

## Credentials

- Device token `vbt_<device id>_<43 base64url>`: Desktop and CLI Devices send `Authorization: Bearer <token>`, only to the `https://` origin that issued it. It is shown once, in the approved poll answer; keep it in the accessor's secret storage. Desktop and CLI pair only over `https://`; a sign-in an older version stored for a plain `http://` origin is ignored.
- Browser Devices get the cookie `__Host-vbot_device` instead: `HttpOnly; Secure; SameSite=Strict; Path=/; Max-Age=34560000` (400 days). The `__Host-` prefix makes browsers keep it only as set (Secure, `Path=/`, no `Domain`), so no other site or subdomain can plant or shadow it; Chromium and Firefox also store and send it on `http://localhost` and `http://127.0.0.1`. Page code never sees the token. `Authorization` wins when both are present. A refused cookie comes back cleared (`Max-Age=0`). A request that carries the cookie more than once is refused as malformed (401 in `authenticated`) and nothing is cleared, since one of the values may be valid.
- Local access token `vbl_<43 base64url>` in `<data-dir>/runtime/local-access-<port>.token`, owner-only, rewritten at every server start once the server listens: JSON `{"token": "vbl_...", "loopback": ["127.0.0.1"]}`, `loopback` holding the loopback IP literals the server listens on (compressed IPv6 without brackets; a wildcard bind counts as `127.0.0.1` or `::1`). Tools on the server's computer send it as `Authorization: Bearer` only over plain `http://` to one of those literals on that port (`http://127.0.0.1:<port>` or `http://[::1]:<port>` works in every mode, also with direct TLS), never to a host name such as `localhost` and never to another address (`core.access.local_token.LocalAccess.admits`). Read it at each connection and again after a 401. `cli/server_client.py` is the reference (`ServerAuth` re-reads it after a 401 and repeats the request once when it changed).
- In `local` and `lan` no credential is needed and a wrong one is ignored.
- A Device unused for 90 days expires and must pair again.

## Endpoints

All exempt from the credential requirement (the peer and transport rules still apply).

- `GET /api/auth/status` -> `{mode, mode_label, authenticated, principal, device}`: `mode` `local|lan|authenticated` with its label; `principal` `host|device|open` or `null`; `authenticated` is `principal != null` (so `true` with `open` in `local`/`lan`); `device {id, name, kind}` for a Device, else `null`. An accessor calls it first to decide whether to show pairing. While the device store is unavailable it answers 503 `devices_unavailable` to a request with a device token (Errors above), so no accessor offers pairing to a Device that may still be valid.
- `POST /api/auth/pair/start {kind, name}` (`kind`: `browser|desktop|cli`; `name` 1-80 characters, whitespace collapsed, no characters of the Unicode categories Cc, Cf, Zl or Zp) -> `{request_id, code, poll_secret, expires_in: 600, poll_interval: 2}`. Show `code` (`XXXX-XXXX`, alphabet `23456789ABCDEFGHJKMNPQRSTVWXYZ`) with the server's origin, and tell the user to approve it only in vBot at that origin, on a device that is already signed in, or with `vbot devices approve <code>` on the server's computer: whoever gets a code approved signs in as the device that holds its `poll_secret`. Keep `poll_secret` private; it alone can claim the result. Limits: 10 starts per client and 100 overall per 10 minutes, at most 256 pending requests (429). A client is its effective address, an IPv6 client its /64. Requests from the server's own computer (direct loopback, no forwarding header) count only against their per-client limit and never against the overall budget or the pending cap. A full table drops the oldest undecided request of the client holding the most; it answers 429 only when every pending request is already approved.
- `POST /api/auth/pair/poll {request_id, poll_secret}` (each a string of at most 128 characters) -> one of
  - `{status: "pending", expires_in}`: poll again after `poll_interval`;
  - `{status: "approved", device: {id, name, kind}, token}` for `desktop`/`cli`; for `browser` the same without `token`, and the response sets the `__Host-vbot_device` cookie;
  - `{status: "denied"}`: denied, or approved by a Device that was revoked or expired before the claim;
  - `{status: "expired"}`: unknown, expired, already claimed, or the secret does not match.
  The Device is created when the approved request is first claimed; concurrent polls share that one claim. A decided request keeps answering for 60 s after the first poll that learned its outcome (`CLAIM_GRACE_SECONDS`): a device whose answer got lost polls again and gets the same outcome, an approved one with the same Device and token (for `browser` the cookie again). Then it is forgotten and polls answer `expired`. The server keeps an approved request's token in memory no longer than that grace. Limits: 60 polls per client and 600 overall per minute (429); the server's own computer is outside the overall budget.
- `GET /auth/ticket/<ticket>`: redeems a login ticket once. Success: 303 to the ticket's `next` (default `/`) with `Cache-Control: no-store`, `Referrer-Policy: no-referrer`. A browser that is already signed in as a browser Device (its cookie) keeps that Device: the ticket is used up and no cookie is set. Any other browser gets a new browser Device (`via: "ticket"`) and its `__Host-vbot_device` cookie, named as the ticket asked and approved by the ticket's issuer. The redirect carries no fragment, so the browser keeps the fragment of the ticket URL (RFC 7231 7.1.2); an accessor that needs a fragment on the landing page puts it on the ticket URL. Failure (unknown, used, expired, issued by a Device revoked or expired since, or not `authenticated` mode): 400 HTML page "Sign-in link not valid", counted as a failed credential. An unavailable device store answers 503 HTML "Sign-in not available" before the ticket is used up.

## Accessor notes

- Desktop (`desktop/sign-in.md`): reads `GET /api/auth/status` after its probe and signs in only in `authenticated` mode. It pairs only an `https://` server, as kind `desktop` under the name the user confirmed on its connection screen (default `vBot Desktop on <computer>`), and keeps the token per origin outside `settings.json`; the installation's own Desktop instead uses the local access token over plain `http://` to a loopback IP literal the token file records (`--server-data-dir`). Its window signs in with `auth.login_ticket {name: "vBot Desktop window on <computer>", next: "/?accessor=desktop&desktop_session=..."}` and opens `/auth/ticket/<ticket>` natively (never through page JavaScript), so the window lands on its WebUI page in one load. Its persistent WebView keeps the cookie, so a later sign-in keeps the window's browser Device; Forget sign-in calls `devices.logout`, which revokes the window's ticket Device with it. Voice and dictation requests send `Authorization: Bearer`; a 401 drops a device token and shows pairing again, a 401 with the local access token re-reads the file once; a 503 drops nothing.
- Tray (`cli/application/tray.md`): the owned server's tray uses the local access token and mints login tickets with `next` set to the page it opens; a Desktop Client's tray follows the Desktop's server and sends the Desktop's device token, read only. It never removes a credential.

## RPCs

Via `POST /api/rpc`; each needs a principal, so in-process dispatch is refused with `access_denied`.

- `auth.login_ticket {name?, next?}` -> `{ticket, path: "/auth/ticket/<ticket>", expires_in: 60}`: needs a signed-in `host` or `device` principal in `authenticated` mode; `name` defaults to `Browser`. `next` is where the redemption redirects (default `/`): a path on this server with an optional query, starting with `/`, made of RFC 3986 path and query characters and percent escapes only, at most 2048 characters, without `//` anywhere and not under `/auth/ticket/`. A scheme, host, fragment, backslash or white space cannot pass; anything else is `invalid_request`. Open `<public-url><path>` in the system browser at once; never log or store the ticket.
- `devices.list {}` -> `{devices: [{id, name, kind, created_at, last_used_at, last_client, approved_by, via, current}]}`, oldest first; `current` marks the calling Device; `approved_by` is `host` or a device id; `via` is `pairing` (claimed an approved pairing), `ticket` (redeemed a login ticket) or `null` for a Device stored before `via` existed.
- `devices.rename {id, name}` -> `{device}`.
- `devices.revoke {id}` -> `{revoked: [ids]}`: the Device and every browser Device created by redeeming a login ticket it issued (`via: "ticket"`, `approved_by` its id), transitively; Devices it approved through pairing stay. Their live connections close at once, and what they approved but nobody claimed yet is withdrawn (pairings poll `denied`, their login tickets stop working). The same holds for `revoke_others` and `logout`; expiry withdraws approvals but revokes only the expired Device.
- `devices.revoke_others {}` -> `{revoked: [...]}`: every Device except the calling one, which stays even when one of the others issued its ticket.
- `devices.logout {}` -> `{revoked: [own id, ...]}`: only for a Device principal; its ticket browsers go with it. The browser cookie cannot be deleted through RPC; the next request clears it.
- Live updates: every change of the paired Devices (paired, renamed, revoked, expired) and every pairing decision publishes `resource_changed {kind: "devices"}` on `/ws` (no data; `server/events-and-reconnect.md`). A Devices list reloads `devices.list` on it instead of polling.
- `devices.pending {code}` -> `{code, name, kind, client, requested_at, expires_in}`: what the approver confirms before approving (`client` is the requester's effective address).
- `devices.approve {code}` / `devices.deny {code}` -> `{status: "approved"|"denied", name}`.
  Pending, approve and deny need a signed-in principal in `authenticated` mode; codes are accepted in any case, with or without the dash or spaces. An unknown code is `pairing_not_found`; 10 wrong codes per principal (50 overall) per 10 minutes block further attempts (`rate_limited`).
- Failed credentials: 20 per client and 200 overall per 10 minutes, then 429 until the window frees up.
