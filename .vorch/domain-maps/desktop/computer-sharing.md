# Desktop computer sharing

`desktop/execution.py` owns the running Desktop's local capability grants and native connection. The user chose this lifetime explicitly: a minimized app remains available; quitting ends its local work, with a warning for live Terminals. No separate daemon is installed. Server registration, Session target choice and authorization belong to `computers.md`.

## Ownership

- `ComputerSharing` owns one async loop on a native thread, independent of the loaded WebUI document. `main.py` starts it after the first connection attempt, follows `ConnectionController`'s selected server, and closes it when the window ends.
- `TerminalCapability` (`desktop/terminal_execution.py`) owns native PTYs and their output retention. Server TerminalManager continues owning the operator/Agent catalog, screen rendering, attachment and completion behavior (`tools/terminal.md`).
- `ComputerExecution` (`desktop/computer_execution.py`) owns the native desktop worker and emergency stop. The Computer Use Extension owns Agent grants, screenshot references and action interpretation (`extensions/computer-use.md`).
- `desktop/extensions.py` owns local native declarations, including the bundled Terminal and Computer Use entries. `ComputerSharing` owns their handler instances and lifecycle. A capability factory receives an event sink and returns a handler with async `execute`, `disconnected` and `close`; a handler can expose async `ready()` and a `read_only_operations` set. Those operations remain admitted during native confirmation/restart fences so observing retained state survives a cancelled dialog. Terminal declares `read` and `status`. Factories load lazily. New capabilities share transport and lifecycle, not another Tool dispatcher or local Agent Runtime.

## Local Extension declarations

An Extension can declare `desktop: {entry: "desktop.py", api_version: 2}` in its existing `extension.json`; API 1 declarations remain accepted. This is the same folder identity as its optional server and browser contributions, with a separate native host contract. On startup `load_desktop_extensions` scans `<desktop-config-dir>/extensions` before bundled `resources/extensions`, sorting folder names within each root. The first folder identity wins even if disabled, broken or server-only. Local `settings.json` section `extensions.disabled` lists identities to skip before import; an invalid list disables native loading and reports a diagnostic without preventing Desktop startup. The Desktop sharing panel's explicit `Reload local Extensions` action rescans these same local roots and settings. Server Extension Reload does not trigger it; no remote installation or server-supplied native code path exists.

Entries are trusted local Python. The entry must be a relative `.py` file resolving inside its Extension; its synthetic package supports sibling imports, including nested entry directories, without executing root/entry-directory `__init__.py` files or the server entrypoint. It exports synchronous `register(api)` and returns `None`. Authors import `DesktopExtensionAPI`, `ExecutionHandler` and `EventSink` from the lightweight `vbot_extension_sdk.desktop` facade; registration collects lazy factories, local consent labels/descriptions and availability. Custom ids are `extension:<percent-encoded-folder-identity>:<local-name>`, so two Extensions can use the same local name. Only the physically bundled Terminal and Computer Use packages retain the Generation 1 ids `terminal` and `computer_use`; a local same-name replacement gets a qualified id. There is no capability count limit: identifiers have a 256 KiB serialized budget and local catalog descriptions a 4 MiB budget, below the native frame limit. Duplicate local names, invalid declarations and exceeded budgets fail that Extension with a visible diagnostic.

Reload fingerprints every regular installed package file, including manifests, assets, configuration and native modules, preserving unchanged declarations and handler instances. It excludes bytecode and known VCS, dependency and cache paths (`.git`, `.hg`, `.svn`, `.venv`, `venv`, `node_modules`, `__pycache__`, `.mypy_cache`, `.pytest_cache`, `.ruff_cache`, `.cache`, `.tox`, `.nox`). Mutable local state belongs outside the installed package. Streaming scans are bounded to 10,000 encountered entries, 256 MiB of included content and 64 directory levels; enumeration/read failures, interior links/junctions and special files fail that package explicitly rather than reusing an incomplete fingerprint. Root directory aliases remain supported. Its cache includes both canonical source and visible folder owner so aliases cannot exchange qualified ids.

The loader first fingerprints the complete local package set without importing replacements. Its `before_load` hook names affected existing capabilities, so changes/removal of running Terminal code receive native stop confirmation before any new package code is imported. Declining leaves the previous catalog and handlers intact. The Terminal-start fence spans confirmation, imports and catalog publication; an unchanged Terminal owner does not prompt for changes to another package. `ComputerSharing` owns the accepted catalog and passes it to each stateless loader call; a failed post-import publication cannot advance the fingerprint/consent baseline. Changed packages are fingerprinted again after registration; a concurrent package update fails that candidate instead of caching declarations under an obsolete revision.

Changed source loads in a fresh namespace without timestamp-based bytecode reuse; old namespaces stay alive with their declarations/handlers and are released after retirement. The existing `ComputerSharing` owner fences changed capabilities immediately, calls their `close()` to release resources and wake admitted operations, then settles those operations before creating a replacement. All retiring handlers share one ten-second wait budget per reload, including their admitted calls. Timeout completes the reload with a visible per-capability failure and retains the exact handler, cleanup Task and calls in quarantine. Neither Python Tasks nor underlying worker threads are assumed stopped: the capability remains unavailable and has no replacement until settlement. A later reload observes the same pending cleanup Task instead of calling `close()` concurrently; completed failed closes can be retried. A handler's `close()` must still safely settle its own work. Scope shutdown retains ownership and awaits that work, rather than transferring unresolved effects to a new server scope. Other handlers remain owned by the same scope.

Reload keeps the current socket, unchanged handlers, pending calls and Computer incarnation; admitted replies finish on their originating socket. New handlers admit calls only after readiness succeeds. Protocol 1 negotiates `capability_updates: 1` in its welcome and uses a `capabilities` frame to update the server's live offer. A connected older server without that feature refuses live reload before local imports and again before publication; if reload completes during its initial handshake, the stale offer is replaced before any calls are admitted. Startup/offline reload remains available. Old handler events cannot enter a replacement. New capabilities remain unshared. The status reports reload progress, added/updated/removed packages and loader/initialization/retirement failures.

The status bridge returns `capability_catalog`, Extension diagnostics and per-capability initialization errors. `DesktopComputerSharing.svelte` renders this catalog and sends grants by capability id; it does not maintain a second fixed capability list. Factory/readiness failure removes and closes only the failed handler; healthy handlers remain available on the shared connection. Readiness refusals appear as local diagnostic text, unexpected failures as exception types without their private messages. Turning the capability off clears its initialization error so it can be enabled again after repair. Native consent uses the local declaration's label and description. Builtins use this exact path through `resources/extensions/terminal/desktop.py` and `resources/extensions/computer_use/desktop.py`; Desktop Client packaging includes those manifests and native entries without server services. Loader contracts are covered in `tests/desktop/test_extensions.py`, app-only imports in `tests/desktop/test_main.py`, and generic handler lifetimes in `tests/desktop/test_execution.py`.

## Local consent and identity

The `computer_sharing` section of Desktop settings stores the display name and a grant for each capability id per normalized server origin; every capability defaults off. An additive `capability_sources` mapping binds grants to their canonical local package path hash; builtins have a stable shipped identity across application updates. Code updates at the same owner/path retain grants after explicit reload; a same-name package from another root cannot inherit them. Existing Generation 1 builtin grants need no migration. Old unqualified custom grants and unknown stored grants remain preserved but cannot authorize a new qualified capability. This state belongs to the Desktop config directory, never the server data directory. The bridge exposes public status through `getComputerSharing`/`setComputerSharing` and local rescanning through `reloadDesktopExtensions`; the latter accepts no paths or code. `PagePermissions` requires the loaded page to remain the selected server before and after consent. Enabling a capability or reloading local code from a remote server's page needs native confirmation; the installation's own server already has this computer's rights. Grant mutation rechecks both the selected server and catalog revision after consent.

`DeviceTokenStore.computer_identity` keeps a separate registration object inside that origin's record in `device-tokens.json`: a stable computer id and a secret protected with the existing Windows DPAPI or POSIX owner-only storage. Its key never reaches page JavaScript, status, events or logs. Pairing or replacing a refused Device token keeps this registration, so the same installation reconnects under its existing name and Session selection with the new sign-in (`computers.md` -> Identity and storage). Forgetting the server removes its identity too; registering again allocates a new computer id. The prior Session target therefore remains unavailable rather than silently referring to the new registration.

## Connection and execution

The native client connects outbound to `/ws/computers`, with `ServerAccess.header`'s exact-origin credential policy, the Desktop TLS context, no environment proxies, a bounded 16 MiB frame and a protocol-versioned hello. It offers only enabled, ready capabilities. The server's welcome identifies the server process and the registered computer incarnation. Calls are bounded and concurrent; capability owners serialize operations where their semantics require it. A call id already received is refused without repeating its effect: pending ids stay until completion, alongside the most recent 4096 completed ids. Native events share the same connection. A server `error` frame (such as `computer_identity_conflict`) becomes the status `error_code`, not a protocol error. Reconnect waits double from 1 s up to 30 s and start again at 1 s after a link that was welcomed. A window reconnect to the same origin keeps a connected link unless the origin's credential changed (a completed pairing).

A network interruption keeps the same native scope and PTYs. The Computer Use handler stops local input and releases held keys/buttons. Its native observations batch window hit tests; captures are checked for layout changes, masked and resized before transfer. Exact-window activation, optional UIA inspection and element actions use the same serialized native owner; UIA runs in its owned, interruptible subprocess. Window wire identity includes the process id, and element observations are invalidated when that subprocess changes. Native stop ids are retained in successful replies as well as events, and each desktop control owns a fresh emergency hook (`extensions/computer-use.md`). Its native worker stays serialized until admitted work settles, including after repeated cancellation, so shutdown cannot overtake resource creation. Admitted calls settle; their replies are dropped when their originating connection is gone, never delivered to a replacement socket and never replayed as mutations. A reconnected server can read retained Terminal output. A changed server process closes the previous native resources and registers a fresh incarnation before accepting new work. Selecting a different server also closes the old scope; resources and grants never transfer to another origin. `ConnectionController` enters the native server-change guard only after the new target has answered and sign-in succeeded. Running or starting Terminals require a native warning naming the target. A cancelled switch, failed probe/sign-in or settings-write failure preserves the previous scope and releases the admission fence; initial launch and same-origin reconnect do not prompt.

The public status push `vbot-desktop-computer-sharing` is a single coalesced snapshot through `PageEventDispatcher`. Browser refreshes and navigation do not own the native connection.

## Closing and updating

Closing first fences new mutations, then warns if native Terminals are running or starting. Terminal reads and status remain available during the dialog. A declined warning lifts the fence. Accepted close shuts down the native handlers before the Desktop exits. Once Computer Use shutdown starts, cancellation waits for input release, hotkey and target closure, and worker shutdown. Turning Terminal sharing off fences new Terminal starts before counting running or starting Terminals, through confirmation and the settings write; existing Terminals remain available, including for reads, status and stopping. If Terminals run or start, it asks a native warning first (the bridge's `confirm`, user decision 2026-10-26); a declined or unavailable warning answers `declined` and keeps it shared. A declined warning or failed settings write releases the fence, and concurrent sharing updates are serialized. Disabling a capability closes its handler. No change silently redirects operations to the server computer.

Automatic package restarts wait indefinitely for local Terminals. Every admitted restart also fences native requests before the successor starts, so a new Terminal cannot slip between the idle check and the handoff. Explicit restart refuses while Terminals remain; the user can stop them first. A failed handoff lifts the fence so the existing app remains usable (`desktop/update-restart.md`).

## Agent-facing text

These transport refusals can be propagated through Terminal or Computer Use. They carry no Tool definitions; capability-specific results and guidance belong to those Tools.

| Text | Reason |
| --- | --- |
| `This request was already received; no action was repeated` | A duplicate request is not another input or process launch; prevents repeating a possibly completed action after reconnect. |
| `The computer has too many pending operations; nothing was started` | Distinguishes refused admission from an action whose outcome is unknown. |
| `This capability is not shared; nothing was done` | Prevents treating a revoked local grant as a transport retry or assuming local effects occurred. |
| `The Desktop is closing, restarting or switching servers; nothing was done` | Explains refusal during the native admission fence without encouraging alternate-machine execution. |
| `Terminal sharing is being turned off; nothing was done` | Explains why a Terminal start was refused and confirms it was not started. |
| `The operation and its parameters are required; nothing was done` | Refuses a malformed internal request before the capability sees it. |
| `The computer operation failed; its effects are unknown.` | Unexpected native failure cannot imply an action was not executed. |
| `Check the current state before repeating it.` | Prevents a second launch or input after an uncertain operation. |

## Tests

`tests/desktop/test_execution.py` covers per-origin grants/identities, call admission and duplication, app close, same-server reconnect, changed server identity, confirmed/cancelled/failed server switches and stale reply isolation using in-memory sockets. `test_bridge.py` covers native consent and navigation races; `test_restart.py` the unbounded Terminal hold; `test_page_events.py` coalescing. Native capability contracts have their own tests; none of these tests captures the user's desktop or launches their programs.
