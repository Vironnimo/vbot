# Desktop Live voice integration

Read for the Desktop side of Live voice: pausing wakeword listening during a call, hands-free starts (per-phrase wakeword action, global shortcut), the pushed Live requests, and the WebView2 switches and microphone permission that let a remote HTTP server use the microphone. The call itself (server, Provider wire, WebUI controller) is owned by `model_tasks/live.md`; the Desktop root map is `desktop.md`.

## Ownership

- The WebUI page owns the Live call (`webui/src/lib/liveVoice.js`, `webui/src/components/LiveVoice.svelte`). The Desktop never opens Live media or calls Live RPCs; it only frees the microphone, asks the page to start or toggle a call, and makes the page able to open the microphone.
- Python: `desktop/_windows.py` (browser arguments, microphone permission hook, single-instance guard), `desktop/live_requests.py` (request push), `desktop/hotkey.py` (global shortcut), `desktop/wakeword/bridge.py` (`setLiveVoiceActive`, shortcut bridge methods, capabilities), `desktop/wakeword/worker.py` (per-model detection action), `desktop/settings.py` (`model_actions`, `live_voice.hotkey`). `desktop/main.py` wires them: origins and dispatcher before the window, permission hook and focus listener on the window, shortcut registration in the `shown` callback, teardown in the `webview.start` `finally`.
- WebUI: `webui/src/lib/desktopBridge.js` (lease, state sync, request listener, shortcut wrappers), `webui/src/lib/liveShortcut.js` (key capture and labels), `webui/src/components/settings/DesktopLiveVoiceShortcut.svelte`, the phrase action select in `WakewordVoiceSettings.svelte`.

## Capabilities

`getDesktopCapabilities()` adds:

- `liveWakeword` - always `true`; marks a Desktop that understands `setLiveVoiceActive` and pushed Live requests. The WebUI skips the pause and hides the phrase action select without it (older Desktop).
- `liveHotkey` - a global shortcut can be registered (Windows only); gates the "Live voice shortcut" Settings section.
- `secureOrigins` - the remote `http://` origins that are secure contexts in this Desktop process (fixed at startup, see WebView2 below).

## Wakeword pause (microphone lease)

- Bridge `setLiveVoiceActive(active)` returns `{active}` (non-`true` values mean inactive). The flag lives in the bridge under the worker lifecycle lock. Becoming active with Voice enabled stops the worker (microphone closed) and publishes state `paused`; status carries `pause_reason: "live_voice"` only in that state. Becoming inactive restarts the worker with the current config and server, like Retry. Unchanged values and Voice disabled are no-ops apart from storing the flag.
- Invariant: every worker start path goes through `_start_worker`, which publishes `paused` instead of starting while the flag is set, so enable, config change, Retry, import activation, and server switch during a call all stay paused and resume when the call ends.
- Reset points, so a replaced or crashed page cannot leave listening paused: every successful in-window connect (`set_server_url`) clears the flag and restarts an enabled worker even for an unchanged URL; and each new page calls `syncDesktopLiveVoiceActive()` once the bridge answers with `liveWakeword`, sending its own state (`false`).
- WebUI: `createDesktopLiveVoiceLease()` is passed to the Live controller as `microphoneLease` in the Desktop accessor only. `acquire()` runs after the status checks and before `getUserMedia`; each successful acquisition is paired with one `release()` when the call releases media or a cancelled start finishes acquiring. Overlapping holders keep wakeword paused until the last release, so a late cancelled start cannot release its successor's microphone lease. Bridge wait, capability read, and the pause call are each bounded to 3 s and failures only log: a broken bridge never blocks Live voice. State delivery is serialized and latest-value-wins (`setDesktopLiveVoiceActive`), with a 10 s bound per bridge call.
- `acquire()` returns `desktop_restart_required` when the page is not a secure context and its origin is not in `secureOrigins` (a server added after the Desktop started); `LiveVoice.svelte` shows "Restart the vBot Desktop app to use the microphone with this server." An insecure page whose origin is listed only logs and continues, and `getUserMedia` then fails as `microphone_unavailable`.
- `paused` is not an error: the sidebar indicator shows the off style with "Wakeword paused during Live voice", the Voice panel "Paused during Live voice"; no Toast or cue.

## Hands-free starts

- Per-phrase action: `wakeword.model_actions` maps a model id to `command` (default when missing) or `live_voice`. A `live_voice` detection publishes `wakeword_detected`, pushes `{action: "start", source: "wakeword"}`, and returns to `listening` without recording or uploading anything; the call's lease then pauses the worker. `getWakewordStatus()` reports the effective action of every active model and keeps stored entries of inactive models; `setWakewordConfig({model_actions})` merges entries, rejects unknown action values and unknown model ids (catalog lookup); deleting an imported model drops its entry.
- Global shortcut: Desktop setting `live_voice: {hotkey: {enabled, ctrl, alt, shift, win, key}}` with `key` a browser `KeyboardEvent.code`; default disabled, Ctrl+Alt+Space. Allowed keys `KeyA`-`KeyZ`, `Digit0`-`Digit9`, `F1`-`F24`, `Space`; at least one modifier unless `F13`-`F24`. A press pushes `{action: "toggle", source: "hotkey"}`.
- Bridge `getLiveHotkey()` / `setLiveHotkey(changes)` return `{supported, enabled, hotkey: {ctrl, alt, shift, win, key}, error_code}`. `setLiveHotkey` merges typed partial changes, persists only valid results (an invalid combination returns `hotkey_invalid` and keeps the saved one; turning off always succeeds), then re-registers. `error_code`: `null`, `hotkey_in_use` (Win32 1409, another app owns it), `hotkey_invalid`, `hotkey_failed`. A failed registration keeps the saved preference and reports the code.
- Registration (`desktop/hotkey.py`): one thread per registered combination runs its own message loop, because Windows delivers `WM_HOTKEY` only to the registering thread; that thread also unregisters. `MOD_NOREPEAT` suppresses auto-repeat. Letters and digits register by physical key: the set-1 scan code is mapped through the active keyboard layout (`MapVirtualKeyW`), so the shortcut stays on the key pressed during capture. Registration is active only from the `shown` callback until exit. The Win32 calls sit behind `HotkeyApi`; tests never register a real hotkey.
- The shortcut applies immediately through the bridge (not Settings autosave); the Desktop answer is authoritative in `DesktopLiveVoiceShortcut.svelte`. Capture ignores lone modifiers, lets Tab move focus, cancels on Escape; labels use the Keyboard Layout Map when the page may read it.

## Live request push

- `desktop/live_requests.py` dispatches `window.dispatchEvent(new CustomEvent("vbot-desktop-live", {cancelable: true, detail: {action, source}}))` through `Window.evaluate_js`. The page acknowledges with `preventDefault()`; `dispatchEvent` returning `false` means handled. Push avoids the 500 ms status poll and the timer throttling of a minimized window.
- `evaluate_js` blocks until the page answers and deadlocks on the GUI thread, so delivery runs on one daemon thread behind a queue of 4; producers (worker, hotkey thread) never block, excess requests are dropped, and a request older than 5 s is dropped instead of starting a call long after the user asked. The connection screen has no listener; unhandled requests log at debug level.
- `onDesktopLiveRequest` (WebUI) validates `action` (`start` | `toggle`) and `source` (`wakeword` | `hotkey`). `LiveVoice.svelte`: server unavailable -> not handled; no Live voice Model -> `not_configured` notice; no call -> start; `toggle` during a call that is not closing -> stop; `start` during a call -> ignored.

## WebView2: secure origins, autoplay, microphone permission

- A remote plain-HTTP page is not a secure context, so `navigator.mediaDevices` is missing. `main.py` collects every remembered server plus an explicit `--host/--port` target, keeps non-loopback `http://` origins (loopback is already secure), and `apply_browser_arguments` exports `WEBVIEW2_ADDITIONAL_BROWSER_ARGUMENTS` right before `webview.start`: `--unsafely-treat-insecure-origin-as-secure=<origins>`, `--autoplay-policy=no-user-gesture-required` (hands-free starts have no user gesture; a pre-existing autoplay policy wins), and pywebview's own `--disable-features=ElasticOverscroll` repeated. A pre-existing value of the variable is merged, list switches combined.
- WebView2 reads the variable once when pywebview creates its environment, so the origin list is fixed for the process: a server added later needs a Desktop restart (the lease's `desktop_restart_required`). Elevated (administrator) processes ignore the variable, so remote HTTP Live voice cannot open the microphone there. Microsoft does not support browser switches for production use; they are the only way to get these behaviors through pywebview.
- Verified 2026-09-25 (pywebview 6.2.1, WebView2 on Windows 11): the browser process command line carries all three switches while pywebview also sets its `AdditionalBrowserArguments`; a LAN `http://` page reports `isSecureContext` true, a new `AudioContext` starts `running`, and without the variable the page is insecure with no `navigator.mediaDevices`.
- `allow_server_microphone` handles WebView2 `PermissionRequested` (pywebview leaves it unhandled, so WebView2 would prompt and remember the answer): a Microphone request whose origin equals the connected server origin (`ConnectionController.active_server_url()`, read per request) is allowed with `SavesInProfile = False`; other kinds and origins keep the default prompt. It attaches in `before_show` to `CoreWebView2InitializationCompleted`; the handler runs on the GUI thread and must not block. Failures log once per stage and leave the prompt in place.
