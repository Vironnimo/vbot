# Desktop Live voice integration

Read for the Desktop side of Live voice: hands-free starts (a wake phrase with the Live voice action, the global shortcut), the pushed Live requests, how Desktop Voice coexists with a running call (the Live hold and the wake phrases sent with each start), and the WebView2 switches and microphone permission that let a remote HTTP server use the microphone. The call itself (server, Provider wire, WebUI controller) is owned by `model_tasks/live.md`; the Desktop root map is `desktop.md`; Voice internals are in `desktop/voice.md`.

## Ownership

- The WebUI page owns the Live call (`webui/src/lib/liveVoice.js`, `webui/src/components/LiveVoice.svelte`). The Desktop never opens Live media or calls Live RPCs; it asks the page to start or toggle a call, reports Voice state the page uses to hold the call, and makes the page able to open the microphone.
- Desktop Voice keeps listening during a call; nothing pauses or hands over the microphone. Both open the same device in shared mode (WDM-KS inputs are excluded for that reason, `desktop/voice.md` -> Capture and microphones), and echo cancellation removes the assistant's speech from what Voice hears.
- Python: `desktop/page_events.py` (`PageEventDispatcher`: Live request push), `desktop/hotkey.py` (global shortcut), `desktop/wakeword/controller.py` (Live voice phrase action), `desktop/wakeword/config.py` (`phrase_actions`), `desktop/bridge.py` (shortcut methods, capabilities), `desktop/_windows.py` (browser arguments, microphone permission hook), `desktop/settings.py` (`live_voice.hotkey`). `desktop/main.py` wires them: secure origins, dispatcher, shortcut controller (`on_press` -> `request_live("toggle", "hotkey")`), and Voice (`live_requests=page_events.request_live`) before the window; permission hook and `attach_window` on the window; shortcut registration in the `shown` callback; teardown (`live_hotkey.stop()`, `voice.close()`, `page_events.close()`) in the `webview.start` `finally`.
- WebUI: `webui/src/lib/desktopBridge.js` (`desktopMicrophoneAccess`, `onDesktopLiveRequest`, shortcut wrappers), `webui/src/lib/wakewordSettings.js` (`liveWakePhrases`), `webui/src/lib/liveShortcut.js` (key capture and labels), `webui/src/components/settings/DesktopLiveVoiceShortcut.svelte`, and the phrase action select in `webui/src/components/voice/VoicePhraseCard.svelte`.

## Capabilities

`getDesktopCapabilities()` carries, for Live voice:

- `liveHotkey` - a global shortcut can be registered (Windows only); gates the "Live voice shortcut" Settings section.
- `secureOrigins` - the remote `http://` origins that are secure contexts in this Desktop process (fixed at startup, see WebView2 below).
- The Live voice phrase action needs no own flag: it is part of the Voice bridge (`voiceApi` 2).

## Hands-free starts

- Phrase action: in the current server's profile, `phrase_actions[model_id] = {type: "live_voice", mode}` with `mode` `start` | `toggle` (default `toggle`); stored and validated by `desktop/wakeword/config.py` (`desktop/voice.md` -> Stored settings). A detection emits `detected` and `live_requested` and calls `request_live(mode, "wakeword")`; nothing is recorded or uploaded. It is forwarded even while a command records, and it has no readiness `problem`.
- Global shortcut: Desktop setting `live_voice: {hotkey: {enabled, ctrl, alt, shift, win, key}}` with `key` a browser `KeyboardEvent.code`; default disabled, Ctrl+Alt+Space. Allowed keys `KeyA`-`KeyZ`, `Digit0`-`Digit9`, `F1`-`F24`, `Space`; at least one modifier unless `F13`-`F24`. A press requests `toggle` from source `hotkey`.
- Bridge `getLiveHotkey()` / `setLiveHotkey(changes)` return `{supported, enabled, hotkey: {ctrl, alt, shift, win, key}, error_code}`. `setLiveHotkey` merges typed partial changes, persists only valid results (an invalid combination returns `hotkey_invalid` and keeps the saved one; turning off always succeeds), then re-registers. `error_code`: `null`, `hotkey_in_use` (Win32 1409, another app owns it), `hotkey_invalid`, `hotkey_failed`. A failed registration keeps the saved preference and reports the code. Without a shortcut controller the methods reject.
- Registration (`desktop/hotkey.py`): one thread per registered combination runs its own message loop, because Windows delivers `WM_HOTKEY` only to the registering thread; that thread also unregisters. `MOD_NOREPEAT` suppresses auto-repeat. Letters and digits register by physical key: the set-1 scan code is mapped through the active keyboard layout (`MapVirtualKeyW`), so the shortcut stays on the key pressed during capture. Registration is active only from the `shown` callback until exit. The Win32 calls sit behind `HotkeyApi`; tests never register a real hotkey.
- The shortcut applies immediately through the bridge (not Settings autosave); the Desktop answer is authoritative in `DesktopLiveVoiceShortcut.svelte`. Capture ignores lone modifiers, lets Tab move focus, cancels on Escape; labels use the Keyboard Layout Map when the page may read it.

## Live request push

- `PageEventDispatcher.request_live(action, source)` accepts `action` `start` | `toggle` and `source` `wakeword` | `hotkey`, and dispatches `window.dispatchEvent(new CustomEvent("vbot-desktop-live", {cancelable: true, detail: {action, source}}))` through `Window.evaluate_js`. The page acknowledges with `preventDefault()`; `dispatchEvent` returning `false` means handled. The same delivery thread carries the Voice pushes (`desktop.md` -> Page pushes).
- Producers (the Voice detection thread, the shortcut thread) never block: at most 4 requests wait, excess requests are dropped, and a request older than 5 s at delivery is dropped instead of starting a call long after the user asked. The connection screen has no listener, so requests there go unhandled.
- `onDesktopLiveRequest` (WebUI) validates `action` and `source` and calls `preventDefault()` unless the handler returns `false`. `LiveVoice.svelte`: server unavailable -> not handled; no Live voice Model bound -> `not_configured` notice (handled); no call -> start; `toggle` during a call that is not closing -> stop; `start` during a call -> ignored.

## Voice during a call

- Live hold: while the Voice status `recording` is set (a spoken command records, `desktop/voice.md` -> Status snapshot) and a call is running and not closing, `LiveVoice.svelte` holds the call with reason `wakeword`; a status without `recording` releases it, also after a missed event. The hold disables the call's microphone track and silences the assistant (WebRTC audio muted, queued relay audio dropped); holds count per reason, are independent of the user's mute, and end with the call (`webui/src/lib/liveVoice.js` `hold` / `release` / `held`).
- Wake phrases: `liveWakePhrases(voiceStatus)` returns the labels of the active phrases whose effective action is a command (only while Voice is enabled and `listening`), cleaned, de-duplicated case-insensitively, at most 8 of up to 60 characters. The Live controller sends them as `wake_phrases` with each `live.start`, so the voice model treats speech starting with a wake phrase as addressed to another Agent (server contract in `model_tasks/live.md`).

## WebView2: secure origins, autoplay, microphone permission

- A remote plain-HTTP page is not a secure context, so `navigator.mediaDevices` is missing. `main.py` collects every remembered server plus an explicit `--host/--port` target (`_windows.webview_secure_origins`), keeps non-loopback `http://` origins (loopback is already secure), and `apply_browser_arguments` exports `WEBVIEW2_ADDITIONAL_BROWSER_ARGUMENTS` right before `webview.start`: `--unsafely-treat-insecure-origin-as-secure=<origins>`, `--autoplay-policy=no-user-gesture-required` (hands-free starts have no user gesture; a pre-existing autoplay policy wins), and pywebview's own `--disable-features=ElasticOverscroll` repeated. A pre-existing value of the variable is merged, list switches combined. Windows only.
- WebView2 reads the variable once when pywebview creates its environment, so the origin list is fixed for the process: a server added later needs a Desktop restart. Elevated (administrator) processes ignore the variable, so remote HTTP Live voice cannot open the microphone there. Microsoft does not support browser switches for production use; they are the only way to get these behaviors through pywebview.
- Verified 2026-09-25 (pywebview 6.2.1, WebView2 on Windows 11): the browser process command line carries all three switches while pywebview also sets its `AdditionalBrowserArguments`; a LAN `http://` page reports `isSecureContext` true, a new `AudioContext` starts `running`, and without the variable the page is insecure with no `navigator.mediaDevices`.
- Microphone access check: in the Desktop accessor, `LiveVoice.svelte` passes `desktopMicrophoneAccess` as the Live controller's `checkMicrophoneAccess`, which runs after the status checks and before `getUserMedia`. A secure context passes without asking the bridge. An insecure page whose origin is in `secureOrigins` logs a warning and continues (`getUserMedia` then fails as `microphone_unavailable`). An insecure page whose origin is not listed, or whose bridge wait or capability read fails or exceeds 3 s, ends the start with `desktop_restart_required`: "Restart the vBot Desktop app to use the microphone with this server."
- `allow_server_microphone` handles WebView2 `PermissionRequested` (pywebview leaves it unhandled, so WebView2 would prompt and remember the answer): a Microphone request whose origin equals the connected server origin (`ConnectionController.active_server_url()`, read per request) is allowed with `SavesInProfile = False`; other kinds and origins keep the default prompt. It attaches in `before_show` to `CoreWebView2InitializationCompleted`; the handler runs on the GUI thread and must not block. Failures log once per stage and leave the prompt in place.
