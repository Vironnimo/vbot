# Chat Usage

Task-gated reference for canonical per-step and whole-Session token Usage. Read this when changing Provider Usage normalization, estimation, persistence, Run events, Session aggregation, output speed, or the WebUI token projection.

## Canonical shape

Assistant `usage` uses canonical `input_tokens` and `output_tokens`, with optional `cache_read_tokens`, `cache_write_tokens`, `reasoning_tokens`, field provenance `input_tokens_estimated` / `output_tokens_estimated`, and the whole-turn summary `estimated`. Primary token Usage lives on Assistant messages; checkpoints carry their separate context fields and optional nested Compaction Model Usage. `input_tokens` means the total prompt including cached tokens. Wires that report cache tokens separately must add them into the canonical input total; OpenAI-style cached-token detail is already a subset of its input count. `reasoning_tokens` is a provider-reported subset of `output_tokens`, never an additional token total.

Provider adapters normalize every available wire counter before Chat sees it; normalized streaming Usage may carry either primary counter independently. `_complete_usage_with_estimates` preserves usable counters, treats a reported zero input for a non-empty vBot request as unavailable, fills only missing/invalid counters (input uses the complete selected-wire request including Tools; output is `core/utils/tokens.py::estimate_output_tokens`: the answer and Tool Calls once, plus a reported `reasoning_tokens`, else the readable Reasoning and one opaque-blob reservation per blob, never the replay copies in `reasoning_meta`), sets the matching field-provenance flag, and sets the summary `estimated=true` when either field is estimated. Provenance lives only in the field flags: `estimated` is present, as `true`, exactly when a field flag is `true`, and `ChatMessage` validation rejects a summary without a field flag or a field flag without the summary. Per-field readers (`usage_token_is_estimated`, Chat History SQL, Statistics, the WebUI token tooltip, `/status`) read only the field flags; only a whole-turn question such as pricing's `estimated_tokens` reads the summary. `/status` shows the Session's Context projection (below) without provenance (no `~`); its cache lines count every turn like the Session totals, an unreported cache counter as zero. `sessions.db` stores only the field flags and the codec derives the summary on read. The request estimator renders the selected wire and counts its text, Content Blocks, Tool Calls, and permitted Reasoning representation, excluding duplicate canonical copies and persistence metadata. Estimates remain explicitly approximate. Selected-wire request estimators pass the active Model through to the shared image policy in `providers/request-policy.md`; callers without a Model use the shared fallback. Tokenizer-data load failure uses the four-characters-per-token heuristic without changing provenance.

Each finalized Assistant Usage stores its Context projection under `context_usage` in the existing Usage extra JSON. The Agentic Loop is the only Assistant writer and stamps the snapshot in its one boundary preparation (`_agentic_progression.py`), so every persisted step has one: Tool-call turns, interrupted partials, visible output kept after Cancel and fallback routes alike, for every Provider. A failed Provider request persists an error entry and Compaction a checkpoint, never an Assistant entry; a step whose preparation fails is not persisted. History and terminal reconciliation restore that snapshot and estimate only newer durable messages. `latest_session_context_usage` never rebuilds a Context from the token counters: an anchor without a snapshot has no Context projection. Usage is persisted on finalized Assistant messages but never echoed into later Provider requests. `_message_to_request_dict` strips it from history, and the live Tool-continuation helper does the same while preserving permitted reasoning.

Current Context Usage is a separate server projection shaped as required `{tokens, estimated}` plus optional measured provenance `{provider_input_tokens, provider_output_tokens, estimated_delta_tokens}` and optional `context_window`: the effective window (`resolve_context_window(agent, target)`) of the Model the projected request goes to, so a Session's Context names the window it fills (user decision 2026-10-03: the window is Session data, the Model that answered decides it, not the Agent's current Model). The Agentic Loop passes it to every `RequestContextUsage.project` call, automatic Compaction passes the window it decides with; a checkpoint or a manual Compaction projection carries the window recorded by the Session's newest Assistant snapshot (`latest_context_window`). A Run's window has one owner, `RequestTargets.resolve_context_window(agent, target)` (user requirement 2026-10-19: wherever a Provider reports a number, vBot uses it): the window the target's Adapter reports (`ProviderAdapter.reported_context_window`: one a rejection stated, or the one a loaded LM Studio instance serves; `providers/request-policy.md` -> Request limits and context), else the target route's effective window (`core/chat/model_resolution.py::resolve_route_context_window`: the Connection's Model fact through `Model.context_window_for` and `resolve_effective_context_window`, local-Model policy included). `resolve_context_capacity` caps it by the Adapter's `input_token_limit`. `/status` (command and Tool) fills a Context that records no window (a Session that has not answered since this was introduced) with exactly that capacity for the route a Run of the Agent resolves to: `ChatLoop.context_capacity(agent)` acquires the route as a Run does (`RequestTargets.agent_context_capacity`) and closes its Adapter; a Model without a usable route keeps the route window below. `chat.history` fills such a Context with the effective window of the route the Agent's Model resolves to as the Session runs it (Session overrides applied), `core/chat/model_resolution.py::resolve_agent_context_window`: the Connection a Run resolves to (pinned, else the first usable one the Model allows) decides the Model fact, a Model without a usable Connection keeps its Model-wide value, and `resolve_effective_context_window` completes the chain. The Agent payload's `context_window` uses it too; neither reads a reported window or input limit, because they run without an Adapter. Both read the projection from the same Sessions-owned entries (`_store_history.context_batch`): the newest anchor and what follows it, and for a checkpoint anchor also the newest Assistant step with Usage before it, so the window it recorded survives Compaction.

### One Context rule

`core/chat/usage.py` owns the only Context calculation (user decision 2026-10-08: one rule wherever Context is computed or needed). A request's Context is the newest Provider-measured input of a compatible request (the anchor) plus the corrected local estimate of what changed since; without an anchor it is the corrected local estimate of the whole request. Corrected always means the local count times the target Model's learned input estimate factor (`usage.md`); measured input is never scaled. Readers: live projections and `model_step_usage`, the pre-send guard and Adapter input budget, the automatic Compaction trigger, manual Compaction's before value, the post-Compaction after value, the estimated input of a step without measured input, `chat.history` and `/status`. A projection names the window it fills (`context_window`): the target's Context capacity, its effective context window or the Adapter's smaller `input_token_limit` (`providers/request-policy.md` -> Request limits and context), which the indicator and the pre-send guard use. The Adapter input budget (`projected_request_input`) keeps the measured part apart from the estimated change, so the Adapter's estimation margin applies to the estimated part only. Compaction's Tail, new-context, reclaim and compacted counts and the `prompt.preview` token counts apply the same factor (`compaction/strategies-and-checkpoints.md` -> Tail selection). Image and opaque Reasoning reserves are local counting rules inside the estimate, not separate corrections. The Compaction Model request reads the calibration for its input budget and teaches it from every attempt whose input the Provider measured, against the uncorrected estimate of exactly that request (`compaction/strategies-and-checkpoints.md` -> Model call); the Decision Model reads and teaches it for its own Model (`model_tasks/decisions.md` -> Execution); other Model requests outside the Agentic Loop (titles, other Task Models) neither teach nor read it.

`RequestContextUsage` holds the anchor: digests and counts of the measured request and its uncorrected selected-wire estimate, so local estimation error in the unchanged part cancels and a factor that changes between steps cannot distort the delta. `observe` anchors a measured request and records the calibration sample (measured input, uncorrected estimate of exactly that request) for every Assistant step with measured input; a Chat step hands the sample to its Usage recorder update instead, which writes it with the call (`usage.md` -> Interfaces), and `observe_prepared(..., calibrated=True)` then only moves the anchor; estimated input never anchors and never replaces a measurement. The anchor is valid while the route (`model_reference`), prompt-cache epoch, System Prompt and Tool catalog stay the same; the context key also carries `ESTIMATOR_VERSION`, so an anchor's estimate from another estimator is never the base of a delta; the System Prompt enters the context key as its text only, because every request build creates a system message with a new id and timestamp (before 2026-10-19 that ended the anchor at every Run start and steering rebuild, and the whole estimate, with unknown-Model images at the 4096-token reserve, triggered Compaction at 322k of a measured 207k); within a prompt epoch the Tool list stays pinned, so a Tool enabled mid-Run keeps it valid, and only a route that lists announced Tools, and a fallback, changes it (`chat/request-building.md` -> Tool catalog per prompt epoch). A subtraction that would erase a nonempty request falls back to the whole estimate. The signed delta includes replayed Assistant content, Tool Results, image retirement, and request-only changes; any changed request is explicitly estimated, even when its delta is zero. Reported output is diagnostic Usage, not an automatic addition to Context. Counting is incremental, so a step costs its newest turn, not the Session length: an identical request is counted once, and a request that keeps the newest counted request up to that request's newest window (from its last user message or Assistant message with Tool Calls) counts as that request plus the change of the window's count, which equals the whole selected-wire estimate (`RequestContextUsage._count`; the estimator shape it relies on: `providers/request-policy.md` -> Request limits and context). A window that repeats a Tool-call id or answers a call made before it, and a change before the window or of route, scope, System Prompt or Tools, count the request whole; a small memo keeps the last few whole counts by context key and request digest. The accounting holds digests, counts and references to the newest counted request's messages, never copies: an in-place change of a message's top-level fields is noticed, a nested in-place change is not (request messages are copy-on-write). Counting runs on the Chat transform workers, never on the Event Loop; `project_prepared` does no scanning. The anchor persists digests only, so changing how the request digest is computed needs no migration: an older anchor's `request` digest never matches, which can mark at most one projection as estimated. Consumers must not substitute cumulative Session Usage or compare the anchor with a complete transcript estimate and select the larger number: persisted reasoning representations can make those evidence bases diverge sharply without increasing the Provider's actual Context.

`RequestContextUsage.prepare` returns an immutable `RequestContextEstimate` containing only the Model reference, digests and uncorrected count of one exact request. Chat prepares it after request hooks and image limiting, reuses it to observe the response, and prepares the Assistant or Tool continuation once for its Context snapshot. Automatic Compaction uses the next needed request's prepared estimate, after steering, Notes, hooks and image limiting, and never the final answer alone. Tool-continuation preparation follows `adopt_tool_changes`, so a route listing newly loaded On-demand Tools counts the updated Tool list; the preceding Assistant snapshot still uses the Tool list of the request that produced that Assistant. Silent `loaded` notes add no request text (`chat/request-building.md` -> Tool catalog per prompt epoch). `project_prepared` always reads the current anchor and calibration; it retains no corrected projection or mutable request content. A hook change, injected note, steering rebuild, image retirement/body retry, route change or prompt-epoch change prepares a new value. Normalized Usage and the Usage recorder update still precede the measured observation. Regressions: `test_usage.py`, `test_chat_loop_usage.py`, `test_chat_loop_tool_definitions.py`, `test_chat_integration_images.py` and `test_chat_loop_stream_cancellation.py`.

Every Assistant step persists `context_estimation: {factor, anchor?}` beside `context_usage` in its Usage extra JSON. A new Run and manual Compaction continue from it (`RequestContextUsage.resume`) unless a newer checkpoint follows, so the anchor survives Runs and restarts; history and `/status` estimate newer durable messages with the recorded factor. Compaction ends the anchor. After Compaction there is no Provider measurement yet, so Chat builds the exact projected next request and takes its whole corrected estimate, including the refreshed System Prompt, request-only Context, Summary+Tail, applicable in-run restored fields, and Tool definitions. This value and its factor (`context_estimation: {factor}`) are stamped onto the checkpoint before append and become the shared `context_usage`; it must not be reconstructed as `before - canonical reclaim`, because those values can use different representations and scopes.

## Output speed

Every complete streamed Assistant step carries `usage.speed` (`core/chat/_output_speed.py`, the one owner of the definition): `first_token_ms` (starting the Adapter stream until the first non-empty Reasoning, answer or Tool Call delta), `first_answer_ms` (until the first answer text or Tool Call), `duration_ms` (until the last output delta) and, when measurable, `output_tokens_per_second` with its `tokens`, `window_ms`, `basis` and optional `estimated: true`. Times are client-observed and per physical attempt: Adapter preparation, authentication and Provider waiting can contribute, but a restart or fallback starts its own clock and omits earlier attempts and backoff. The persisted step names the attempt that answered. Finalization applies the shared inline Reasoning parser's retained content boundary to answer timing, including a boundary inside one delta; the private timer retains only fragment times and lengths, never extra text copies. Interrupted partials, steps kept after a broken stream and the non-streaming fallback get no stream speed.

The stream-derived rate approximates observed output delivery, not the Model's decode speed or whole-request throughput. Queueing and prompt processing count toward `first_token_ms`. Only output after the first arrival group counts: the step's tokens are apportioned by streamed characters and that group's share is left out because it was generated before the window opened. Character allocation and arrival grouping remain approximate even with Provider-reported token totals; `estimated` retains its narrower token-provenance meaning (the numerator uses a local token estimate). The window and numerator follow what the Provider streamed:

- `basis: "output"`: no known hidden/summarized Reasoning was detected, and the counted output (`output_tokens`, Reasoning included) is at most 1.5x the local estimate of the streamed answer, Tool Calls and readable Reasoning plus 16 tokens; its window runs from the first to the last output delta. This coverage heuristic cannot prove that every counted token streamed.
- `basis: "answer"`: reported positive `reasoning_tokens` without readable Reasoning, explicit `reasoning_summary`, a Reasoning count above 1.5x its own readable estimate plus 16, or total output above the coverage threshold excludes hidden work. The answer alone counts over its own window from `first_answer_ms`: `output_tokens - reasoning_tokens` when both were reported, else the local estimate of answer and Tool Calls (`estimated`). A long answer cannot hide a mismatch between counted and readable Reasoning.
- `basis: "provider"`: the Provider measured its own decode speed (`reported_output_tokens_per_second`) and optionally its actual measurement window (`reported_output_duration_ms`; wire mappings and source evidence: `providers/request-policy.md` -> Usage normalization). It takes precedence. With a valid window, the effective `tokens` are reconstructed as `rate * window / 1000`, rounded to an integer; they can differ from `output_tokens` because a Provider can exclude the first generated token from decode timing. A rate without its window remains displayable but has no aggregate weight: vBot never invents a duration from the Usage total. Statistics retains this basis separately from observed stream rates.

Output that arrives in bursts (a buffering proxy, a cached response, a busy Event Loop) can span little of its generation time. Deltas within 2 ms of the previous one are therefore grouped heuristically as one arrival; this cannot recover actual network reads or generation time. A window needs at least four arrivals, 100 ms and 10 tokens after the first arrival, and no arrival after the first may carry more than half of the window's characters; otherwise there is no `output_tokens_per_second` and only the latency fields stay. The stream records raw marks under `usage.stream_timing`, and `_prepare_completed_assistant` replaces them with `usage.speed` after token estimation, so neither the raw marks nor the reported rate/window fields persist. The Usage recorder stores the validated `speed` with the call (`usage.md`), and Statistics aggregates measured tokens and windows per Model and basis (`statistics/report-sections.md` -> Shared shapes).

`core.chat.output_measurements` is the shared live/History projection: it selects a positive finite rate and non-negative finite first-token latency independently, with the responding Model and Assistant message id. The WebUI keeps the Session's newest available rate and latency independently in the composer footer (`webui/chat.md` -> Session settings), so a later step too short for a rate still updates latency while retaining the earlier rate and its identity. Regressions: `test_output_speed.py`, `test_streaming.py`, `test_chat_loop_usage.py`.

## Per-call costs

After token completion, `_prepare_completed_assistant` uses the exact resolved Model registry price to attach `usage.cost`: `{amount_usd, source}` where source is `provider`, `catalog`, or `unknown`. Catalog estimates retain their rate snapshot/source and whether primary tokens were estimated; unknown results retain a reason. Provider adapters may supply finite non-negative `reported_cost_usd`, which the streaming accumulator preserves. OpenRouter supplies the first verified implementation on Chat Completions and Responses (see `providers/openrouter.md`). Cost data uses the existing Usage extra JSON, survives SQLite round trips, and is stripped with Usage from request replay. It does not change Context estimation or the Chat token badge. Model pricing owns the calculation; Statistics owns aggregation and retrospective estimates for older calls.

Runtime also injects the canonical `core/usage` recorder through `ChatLoopDependencies` (`usage.md`). `WireRequestRunner` starts one record immediately before each Adapter attempt and finishes it with normalized counters before returning or propagating failure. Empty responses, stream restarts, fallback attempts and cancellation without visible output retain reported counters; absent fields remain unknown. `StreamingAccumulator.usage` exposes a copy of the reported counters without requiring valid Assistant output. Accepted Assistant Usage carries the stable `usage_call_id`, and `_agentic_progression` enriches that same record with finalized estimates/cost before attempting the Session append. Statistics can therefore count durable attempts once even when no Assistant was saved or a Session later disappears; canonical Session Usage and Context projections still describe only persisted Assistant boundaries. Run, Session, Agent, Project and available Extension owner/group identity accompany the attempt without storing prompt or output content. Regression coverage: `test_chat_loop_usage.py`.

## Session aggregation and events

`core/chat/usage.py::aggregate_session_usage(messages)` produces `{input_tokens, output_tokens, cache_read_tokens, cache_write_tokens, reasoning_tokens}`: plain sums over every Assistant turn with Usage. Every turn counts, estimated counters included, and a counter a turn does not report counts as zero (user decision 2026-10-06: Usage takes everything it gets; a Provider that omits cache counters although it cached is a Provider defect, not a reason to leave a turn out, and no Provider's reporting quality is special-cased). The Session cache hit rate is `cache_read_tokens / input_tokens`. `core/sessions/_store_history.py::session_usage` computes the same shape in SQL over the Session's own audit (superseded turns included, a fork's inherited prefix excluded); `/status` reads its Session cache line from it.

At the first Model step the loop seeds totals from persisted Session history and advances them after each Assistant append through `add_session_turn_usage`. Every finalized Assistant step emits non-visual `model_step_usage` `{usage, model, message_id, session_usage, context_usage, iteration_count}` (the exact step Usage, the Model that answered, its Assistant message id, current Session and Context Usage, the Run-owned Iteration count) right after the Assistant is persisted, including estimated and Tool-only steps; the server bridges it as ordinary `run_output`, and the UI renders no row for it, consuming only its Iteration projection and Usage state. The same Run-local projection drives pre-send checks, automatic Compaction, and the Adapter input budget. The Adapter's estimation margin stays separate and never increases displayed Context. `Run.terminal_payload_extras` carries final Session and Context Usage for every terminal outcome; the loop recomputes both from persisted history in `finally` after the run-summary append, logging and swallowing only diagnostic recomputation failure.

`chat.history` returns the full-transcript Session total and latest durable Context projection even when the visible message page is only a slice. An `after` read that finds nothing appended omits both and the consumer keeps its values; on any other read `context_usage: null` means there is no Context projection. Consumers must not derive either value from their locally loaded page. The final `run_completed` payload may additionally carry the last Assistant step's `usage`; failed/cancelled terminal events do not invent a per-step value.

## Streaming and Provider boundaries

Streaming adapters yield normalized `usage` deltas containing at least one non-negative integer primary counter. `StreamingAccumulator` merges partial deltas and forwards optional cache and Reasoning fields only when they are non-negative integers, and a reported decode speed only when it is finite and positive (Output speed). OpenAI generally supplies final-chunk Usage. Native Anthropic may split input/cache counts at `message_start` and output/Thinking detail at `message_delta`; a compatible Messages gateway may instead repeat a complete input/cache snapshot in the terminal `message_delta`. The shared Messages decoder merges these cumulative counters field by field (a counter an event omits or nulls keeps its earlier value) and emits the input/cache snapshot already at `message_start`, so a stream cut before its terminal Usage keeps them; output follows with the terminal event. Provider-specific wire shapes stay in the Provider maps.

The WebUI token badge consumes only `context_usage`, for its numerator (`tokens`) and its denominator (`context_window`), for every Session alike (roster, Project and hidden Agents); history seeds it, `model_step_usage` and Compaction events update it during an active Run, and the terminal payload provides final reconciliation. Last-step Usage and cumulative Session Usage fill the context card and never determine the badge. The card shows no provenance: no `~`, no Provider anchor or estimated delta, no estimation notes (`webui/design.md`). An update without `context_window` keeps the window already known for the Session (`chatState/sessionState.js::nextContextUsage`). Context-window resolution itself is not owned by Usage; it comes from the Model/Provider configuration of the Model that answered.
