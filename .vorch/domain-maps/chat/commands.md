# Chat Built-in Commands

Task-gated reference for Built-in Command recognition, scheduling, execution, neutral outcomes, and surface projection. Read when changing the command catalog, a command workflow, Channel availability, RPC command responses, or command-started Runs.

## Ownership and execution contract

`core/chat/commands.py::CommandDispatcher` is the single end-to-end owner for every Built-in Command. It declares the catalog, recognizes eligible Chat content, parses the argument once, selects immediate versus serialized execution, enforces command/domain guards, performs all state changes and Run orchestration, and returns a surface-neutral result. RPC and Channel code may validate/authenticate their own ingress, supply addressing and a `ReplySurface`, schedule prepared work, project the result, and publish generic change facts; they must not switch on command names or rebuild a workflow.

`CommandSpec` declares `name`, `description`, `argument` (`none`, `optional`, or `required`), neutral `catalog_result` (`notice`, `detail`, or `state_change`), default `execution_mode`, optional argument-specific execution mode, preferred-new-Session-id support, and unavailable surface kinds. The WebUI catalog retains its public `toast`/`transient`/`action` values through generic RPC projection; those accessor words never enter the Chat contract.

`prepare(content) -> PreparedCommand | None` is the only recognition/parser seam. Eligible content is a string or exactly one `TextBlock`; attachments, mixed blocks, and multiple blocks bypass Built-in Commands and continue as normal Chat input. Unknown slash text and a no-argument command with trailing text also fall through. `PreparedCommand` contains the canonical command name, parsed argument, execution mode, and preferred-id capability; it contains no transport payload.

`unavailability(prepared, reply_surface) -> CommandUnavailability | None` evaluates Chat-owned surface restrictions before Queue admission or execution. `/agent` is unavailable on every Channel surface in both bare and argument forms. Channels render the neutral restriction as `The /agent command is not available through <Platform>.`; this is a permanent ownership constraint, not an unimplemented feature.

`async execute(prepared, CommandExecutionContext) -> CommandOutcome` performs the complete workflow. The context carries the addressed Agent, Session, optional Project, initiating `ReplySurface`, optional generic change observer, and an optional accessor-proposed Session id for `/new`. The outcome carries neutral feedback (`notice` or `detail`), descriptive facts, typed navigation (`continue_in_session` or `offer_session`), typed Runs (`result` or `follow_up`), and final `CommandResourceChange` records. It never contains RPC envelopes, toast/transient vocabulary, Telegram/Discord objects, or an event bus.

A `result` Run is the command's direct response (`/continue`): RPC returns it through the normal send/stream path and Channels relay it. A `follow_up` Run is additional work started after the command completes (`/handoff` or an Agent takeover task): the process-wide `ChatRunManager` start callback exposes it to server events and a Channel relays it once to the initiating conversation. The server must not add command-specific Run bridging. Final change records are projected after execution; the context observer reports time-sensitive intermediate changes such as a `/reflect` fork, and RPC de-duplicates an identical final record by kind and scope.

Runtime constructs `CommandDispatcher` only after `ReflectionService`, both `ChatLoop` instances, and `TriggerService`, then injects `AgentResolver`, Sessions, Models, Providers, Projects, Agents, TriggerService, ReflectionService, Storage, and status dependencies explicitly. The command owner does not receive Runtime as a service locator.

## Scheduling and surface behavior

Immediate commands execute outside the Channel conversation FIFO; serialized commands use the existing per-conversation admission and worker. `/stop`, `/help`, `/status`, bare `/agent`, and bare `/model` are immediate; mutating `/agent <target>` and `/model <value|reset>` are serialized, as are `/compact`, `/handoff`, `/learn`, `/new`, `/reflect`, `/rename`, and `/continue`. Channel authorization and Chat-owned unavailability are checked before either path. Serialized work stores `PreparedCommand` plus conversation facts and resolves the active Session at worker execution time, so work queued after `/new` follows its new anchor.

RPC maps `detail` to the existing transient response, `notice` to toast, and typed navigation to action; facts plus the command name form the existing `data` object. Channels send feedback text, apply only `continue_in_session` to their conversation anchor, ignore `offer_session` for later routing, and relay Runs in outcome order. `/handoff` is therefore a one-shot follow-up through a Channel: it does not change `ChannelConfig.agent_id` or the source anchor. `/new` creates the Session in Chat core, after which the Channel applies its Channel metadata and active pointer.

## Command behavior

- `/help` returns the catalog as detail feedback. `/status` returns the shared status rendering used by the status Tool. `/stop` cancels the active Run for the addressed Session or reports that none exists.
- `/compact [instruction]` calls `TriggerService.compact_session` with the addressed Project and optional instruction and returns its user-facing summary.
- `/continue` calls `TriggerService.continue_run` with the initiating reply surface and returns exactly one `result` Run without waiting in the command owner.
- `/new` refuses while the current Session has an active Run, resolves the Agent, creates a Session (honoring a validated preferred id when supplied), updates the identity Agent's current pointer, and returns `continue_in_session` navigation plus a Sessions change. Project Config Agents have no identity current pointer.
- `/rename [title]` writes the Session title; no argument clears it. Session-title resource publication remains owned by the existing Session title callback rather than a duplicate command change.
- `/model` returns a detail card from `AgentResolver.effective_config`. `/model <value>` validates through `AgentResolver.require_model_configured` and writes the identity Agent model or Project Agent override; `/model reset` clears the corresponding value. The Projects resolver owns Model usability and the precise forbidden pinned-Connection diagnostic; RPC only maps `ModelConfigurationError` to `invalid_request`.
- `/agent` returns the personal/Project Team directory in WebUI. `/agent <address> [task]` moves the entire Session under the same id through `ChatSessionManager.move`, refuses invalid/unknown/same targets, active or queued Runs, Channel-bound Sessions, and Sub-Agent Sessions, strips `SESSION_MOVE_STRIP_META_KEYS`, writes the takeover divider/note, re-homes identity current pointers, and returns `offer_session` navigation. The mutating form atomically guards both source and destination Session keys through the complete move/divider/pointer transition via `ChatRunManager.session_admission_guard`; the earlier active/queued probes provide precise feedback but are not the synchronization boundary. An optional task starts one `follow_up` Run through `TriggerService` after the guard is released. Every `/agent` form is unavailable through Telegram and Discord before execution.
- `/handoff [agent:<address>] [instruction]` uses `parse_handoff_argument`, writes the handoff in an internal Run seeded from the `handoff.md` prompt fragment plus optional instruction, creates a fresh target Session, updates an identity target's current pointer, and starts the receiving Agent as one `follow_up` Run. The outcome returns `offer_session`, target facts, and a Sessions change. It refuses an active source Run, invalid/unknown targets, or an empty generated handoff.
- `/learn [request]` is identity-Agent-only, refuses an active Run, starts an internal authoring Run from the `learn.md` prompt fragment, waits internally, and returns its summary as notice feedback. The Run uses the initiating reply surface and writes through the Agent's normal skill capabilities.
- `/reflect [focus]` is identity-Agent-only, refuses an active Run, delegates fork/review to `ReflectionService`, reports the fork immediately through the change observer, waits for the restricted review, resets cadence counters, and returns the fork facts and final Sessions change.

## Invariants and tests

There is no `CommandAction`, `CommandHandled`, legacy `dispatch`/`recognizes`, server command prompt builder, or Channel unsupported-action fallback. Tests under `tests/core/chat/` own parsing/status contracts; stateful execution is exercised through the neutral core contract, RPC tests cover generic projection/error mapping/integration, and Channel tests cover authorization, scheduling, anchor timing, Run relay, and exact platform refusal text. Static guards in `tests/server/rpc/test_chat_methods_dispatch.py` prevent transport workflow symbols and command-name switches from returning.
