# Chat Slash Commands

Task-gated reference for Built-in and Extension Command recognition, scheduling, execution, neutral outcomes, and surface projection. Read when changing the command catalog, a command workflow, Channel availability, RPC command responses, Extension Command declarations, or command-started Runs.

## Ownership and execution contract

Built-in Command execution keeps Run/Queue orchestration on the Event Loop but routes synchronous Agent/Project settings, prompt-fragment reads, Session CRUD/metadata/transcript operations, status assembly, and directory scans through bounded Command or Session workers. Extension Commands share `invoke_extension_handler`, so synchronous handlers are off-loop while coroutine handlers retain the ordinary async contract.

`core/chat/commands.py::CommandDispatcher` is the single end-to-end owner for every Built-in and Extension Command. It declares the Built-in catalog, owns the live Extension registration table, recognizes eligible Chat content, parses the argument once, selects immediate versus serialized execution, enforces command/domain guards, performs state changes and Run orchestration, and returns a surface-neutral result. RPC and Channel code may validate/authenticate their own ingress, supply addressing and a `ReplySurface`, schedule prepared work, project the result, and publish generic change facts; they must not switch on command names or rebuild a workflow.

`CommandSpec` declares `name`, `description`, `argument` (`none`, `optional`, or `required`), neutral `catalog_result` (`notice`, `detail`, or `state_change`), default `execution_mode`, optional argument-specific execution mode, unavailable surface kinds, and `new_session_mode` (below). The WebUI catalog retains its public `toast`/`transient`/`action` values through generic RPC projection; those accessor words never enter the Chat contract.

`prepare(content) -> PreparedCommand | None` is the only recognition/parser seam. Eligible content is a string or exactly one `TextBlock`; attachments, mixed blocks, and multiple blocks bypass Commands and continue as normal Chat input. Unknown slash text, a no-argument command with trailing text, and a required-argument command without its argument also fall through. `PreparedCommand` contains the canonical command name, parsed argument, execution mode, and the opaque registration identity for Extension Commands; it contains no transport payload.

`unavailability(prepared, reply_surface) -> CommandUnavailability | None` evaluates Chat-owned surface restrictions before Queue admission or execution. `/agent` is unavailable on every Channel surface in both bare and argument forms. Channels render the neutral restriction as `The /agent command is not available through <Platform>.`; this is a permanent ownership constraint, not an unimplemented feature.

`async execute(prepared, CommandExecutionContext) -> CommandOutcome` performs the complete workflow. The context carries the addressed Agent, Session, optional Project, initiating `ReplySurface`, and optional generic change observer. The outcome carries neutral feedback (`notice` or `detail`), descriptive facts, typed navigation (`continue_in_session`, `offer_session`, `open_extension_page`, or `new_session`, which names no Session: the surface opens a new conversation with the Agent), typed Runs, and final `CommandResourceChange` records. It never contains RPC envelopes, toast/transient vocabulary, Telegram/Discord objects, or an event bus.

`async execute_for_new_session(prepared, NewSessionCommandContext) -> NewSessionCommandResult` runs a command sent for a new Session, which does not exist yet (RPC `new_session`, `server.md`). The context carries the Agent, optional Project, `ReplySurface`, change observer, and the Agent overrides the new Session would start with; the result carries the outcome and `session_id`, the Session the command created and kept, else `None`. Each `CommandSpec.new_session_mode` decides:

| Mode | Commands | Behavior |
|---|---|---|
| `session_less` | `/help`, `/status`, `/model`, `/new` | Runs through its own session-less handler and creates no Session. `/status` describes the Agent as the first Run would run it (overrides included, no History, idle); bare `/model` reports that Model; `/new` answers that this is already a new Session. |
| `create_session` | `/learn`, every Extension Command | Resolves the Agent with the overrides first (an unusable override Model fails before anything exists), creates the Session with them (`actor="command"`), and runs as `execute` would. A Session left without History and without active or queued Runs is deleted again under `session_admission_guard`, also after a failure, and the result names none; a kept Session adds a scoped `sessions` change first. |
| `needs_session` | `/agent`, `/compact`, `/handoff`, `/reflect`, `/rename`, `/stop` (the default) | Refused with the notice `/<name> works on an existing session. Send a message first to start this one.` |

The dispatcher refuses to construct when a `session_less` Built-in lacks a session-less handler. The catalog does not project `new_session_mode`; accessors send the command and render the outcome (`tests/core/chat/test_commands_new_session.py`).

A `primary` Run is the command's immediate execution result: generic RPC projection returns it through the ordinary Run/SSE response instead of a `command_handled` envelope, and Channels relay it through their ordinary Run activity path. `/compact` uses this role so manual and automatic Compaction share one server-owned lifecycle. A `follow_up` Run is additional work started after the command completes (`/handoff` or an Agent takeover task): the process-wide `ChatRunManager` start callback exposes it to server events and a Channel relays it once to the initiating conversation. An outcome may contain at most one primary Run. The server must not add command-name-specific Run bridging. Final change records are projected after execution; the context observer reports time-sensitive intermediate changes such as a `/reflect` fork, and RPC de-duplicates an identical final record by kind and scope.

Runtime constructs `CommandDispatcher` only after `ReflectionService`, both `ChatLoop` instances, `TriggerService`, and `TerminalManager`, then injects `AgentResolver`, Sessions, Models, Providers, Projects, Agents, TriggerService, ReflectionService, Storage, TerminalManager, and status dependencies explicitly. The command owner does not receive Runtime as a service locator. The dispatcher binds those collaborators directly to private Built-in functions in `_command_builtin.py` (Session actions) and `_command_status.py` (Model changes and status facts). Those files are internal implementations of the same Command owner; they neither retain the dispatcher nor introduce a second registration or execution layer. Status report rendering is not dispatcher-owned: `core/chat/status_report.py` owns every resolver and formatter behind `/status` and the status Tool, and both call sites only gather inputs and delegate.

`ExtensionRegistry.apply_commands()` validates and installs declarations only after the canonical dispatcher exists. Extension handlers receive a narrower `ExtensionCommandContext`: current addressing, `ReplySurface`, generic change reporting, and `start_run(content, internal=False)` bound through `TriggerService`. Sync and async handlers must return a matching `CommandOutcome`; exceptions or invalid results become neutral failure feedback. Execution revalidates the prepared registration identity, so queued work cannot call removed code or a replacement owner after reload/disable.

## Scheduling and surface behavior

Immediate commands execute outside the Channel conversation FIFO; serialized commands use the existing per-conversation admission and worker. `/stop`, `/help`, `/status`, bare `/agent`, and bare `/model` are immediate; mutating `/agent <target>` and `/model <value|reset>` are serialized, as are `/compact`, `/handoff`, `/learn`, `/new`, `/reflect`, and `/rename`. Extension declarations choose from the same modes and surface restrictions. Channel authorization and Chat-owned unavailability are checked before either path. Serialized work stores `PreparedCommand` plus conversation facts and resolves the active Session at worker execution time, so work queued after `/new` follows its new anchor while registration revalidation prevents stale Extension execution.

RPC maps `detail` to the existing transient response, `notice` to toast, and typed navigation to action; facts plus the command name form the existing `data` object. `open_extension_page` navigation carries the registered owner's `extension`, declared `page`, and a bounded relative inner `route` in `data.navigation`, without inventing a Session destination. The dispatcher validates that destination against the command registration and drops an outcome if that registration retired while its handler was awaited. `new_session` navigation projects as `data.navigation {kind, agent_id}` (the formatted Agent address). Every `command_handled` response carries `session_id`, the Session the command ran in, except a command for a new Session that created none. Channels send feedback text, apply only `continue_in_session` and `new_session` to their conversation anchor, ignore other navigation for later routing, and relay Runs in outcome order. `/handoff` is therefore a one-shot follow-up through a Channel: it does not change `ChannelConfig.agent_id` or the source anchor. `/new` creates no Session: the Channel points the conversation at a fresh id from `new_session_id()`, and its next inbound message creates that Session with its Channel metadata (`channels.md`).

## Built-in Command behavior

- `/stop` cancels the Session's active Run (reason `user`); its background commands, Terminals and Sub-Agents keep working. `/stop all` (case-insensitive argument) calls the injected `stop_all` (`SubAgentCoordinator.stop_tree`, `subagents.md` -> Conventions -> Stop) and reports whether anything was stopped; any other argument, or a dispatcher without `stop_all`, stops nothing and returns the usage notice. `chat.stop_all` is the RPC twin. Coverage: `test_commands.py::test_stop_all_hands_the_session_to_stop_all_and_other_arguments_stop_nothing`.
- `/help` returns the catalog as detail feedback. `/status` returns the shared status rendering owned by `core/chat/status_report.py` (also consumed by the status Tool); its Temperature and Top P lines report what the request sends with its source via `resolve_status_sampling` over `StatusModelDetails`: `<value> (agent)`, a Custom Provider's configured `<value> (provider config)`, else `provider default`, naming a known Model recommendation as `provider default (Model recommends <value>)` without sending it. Only `/status` adds, after Top P, a `Wire profile:` line for the Connection the Agent's Model resolves to as chat resolves it (a `::connection[:account]` suffix, else the first usable allowed Connection): `verified on <date>`, `configured, unverified` or `inferred from defaults, unverified`, then `(Connection <provider:connection[:account]>)`, or the placeholder when no Connection resolves or the lookup fails; a `Learned wire facts:` line follows only when live traffic recorded facts (`reasoning arrives in <field>` or `reasoning is returned`, `rejected parameters: ...`, `rejected reasoning efforts: ...`). The injected `wire_profile_describer` (`Runtime.describe_agent_wire_profile`) runs on the command worker because Connection resolution reads credential state. The status Tool leaves both lines out because Agents cannot act on them: `build_status_reply` omits them unless `wire_profile` is passed (`tests/core/tools/test_status.py`). `/stop` cancels the active Run for the addressed Session or reports that none exists.
- `/compact [instruction]` calls `TriggerService.start_compaction_run` with the addressed Project and optional instruction and returns that dedicated Compaction Run as the outcome's `primary` Run. Unavailable or already-busy Sessions still return immediate notice feedback; once admitted, success, failure, and cancellation are Run lifecycle outcomes.
- `/new` refuses while the current Session has an active Run, resolves the Agent, creates no Session, clears an Identity Agent's current pointer (an `agents` change, only when it was set), and returns `new_session` navigation with the notice `New session: it starts with your next message.`; the accessor's next message for a new Session creates it. Project Config Agents have no identity current pointer.
- `/rename [title]` writes the Session title; no argument clears it. Session-title resource publication remains owned by the existing Session title callback rather than a duplicate command change.
- `/model` returns a detail card from `AgentResolver.effective_config` for the current Session (a Session override reports origin `this session`). `/model <value>` validates through `AgentResolver.require_model_configured` and permanently writes the identity Agent model or Project Agent override; `/model reset` clears the corresponding value. Both also clear the current Session's Model override, so the Session runs the Agent's Model the command just set; other Sessions keep their overrides and the thinking-effort override stays. For a new Session, `/model <value|reset>` changes only the Agent's Model: the new Session's override Model lives in the accessor until its first message, so the command cannot clear it. The Projects resolver owns Model usability and the precise forbidden pinned-Connection diagnostic; RPC only maps `ModelConfigurationError` to `invalid_request`.
- `/agent` returns the personal/Project Team directory in WebUI. `/agent <address> [task]` moves the entire Session under the same id through `ChatSessionManager.move`, refuses invalid/unknown/same targets, active or queued Runs, Channel-bound Sessions, Sub-Agent Sessions, and Sessions a live Bootstrap job, Cron job or Calendar action selects (they address the Session by Agent and id; the notice names each, checked through the injected `AutomationReferences` under its reference lock, `automation.md`), leaves the Agent-bound prompt state (pinned Skill catalog, SOUL, memory and Tool-definition pins, seen Skills) behind and starts a new prompt-cache affinity (the move's cross-scope rule, `sessions.md`), writes the takeover divider/note, transfers every matching live Terminal Session to the destination owner, re-homes identity current pointers, and returns `offer_session` navigation. The mutating form atomically guards both source and destination Session keys through the complete move/divider/Terminal/pointer transition via `ChatRunManager.session_admission_guard`; the earlier active/queued probes provide precise feedback but are not the synchronization boundary. An optional task starts one `follow_up` Run through `TriggerService` after the guard is released. Every `/agent` form is unavailable through Telegram and Discord before execution.
- `/handoff [agent:<address>] [instruction]` uses `parse_handoff_argument`, writes the handoff in an internal Run seeded from the `handoff.md` prompt fragment plus optional instruction, creates a fresh target Session, updates an identity target's current pointer, and starts the receiving Agent as one `follow_up` Run. The outcome returns `offer_session`, target facts, and a Sessions change. It refuses an active source Run, invalid/unknown targets, or an empty generated handoff.
- `/learn [request]` is identity-Agent-only, refuses an active Run, starts an internal authoring Run from `learn_brief` (shared prompt fragments assembled off the Event Loop by `core/prompts/briefs.py`, plus the request or a no-request instruction), waits internally, and returns its summary as notice feedback. The Run uses the initiating reply surface and writes through the Agent's normal skill capabilities.
- `/reflect [focus]` is identity-Agent-only, refuses an active Run, and refuses before forking when the effective Agent can call neither `memory` nor both `skill` and `skill_manage` (`ReflectionService.available_review_scope`). It requests a combined review, which narrows to the callable dimension; delegates fork/review to `ReflectionService`, reports the fork immediately through the change observer, waits for the restricted review, resets the counters of the reviewed scope (`ReflectionResult.scope`), and returns the fork facts and final Sessions change.

## Invariants and tests

There is no `CommandAction`, `CommandHandled`, legacy `dispatch`/`recognizes`, server command prompt builder, or Channel unsupported-action fallback. Tests under `tests/core/chat/` own parsing/status contracts and exercise stateful execution through the neutral core contract against recorded collaborators (`/agent` moves: `test_commands_move.py`; `/handoff`, `/learn` and `/reflect`: `test_commands_workflows.py`; commands for a new Session: `test_commands_new_session.py`); RPC tests cover generic projection/error mapping/integration, and Channel tests cover authorization, scheduling, anchor timing, Run relay, and exact platform refusal text. Static guards in `tests/server/rpc/test_chat_methods_commands.py` prevent transport workflow symbols and command-name switches from returning.
