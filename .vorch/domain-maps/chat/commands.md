# Chat Built-in Commands

Task-gated reference for the built-in slash-command framework and per-command behavior dispatched before a Run starts. Read when changing command recognition, argument/output modes, a command's persistence effects, payload, or server orchestration.

`CommandDispatcher` is the shared pre-Run router for pure-text messages. Unknown slash text falls through to normal Chat and Skill activation. Each built-in is declared once as `CommandSpec(name, description, argument, output)` in `BUILT_IN_COMMANDS`: `argument` is `none`, `optional`, or `required`; `output` is `toast`, `transient`, or `action`. `_match_command` is the single recognition/parser path used by both `dispatch` and `recognizes`; a no-argument command with trailing text falls through, while optional/required commands receive the trimmed remainder. `CommandHandled` carries a non-persisted reply/data projection; `CommandAction` delegates runtime orchestration to `server/rpc/chat_methods.py`. Attachment-bearing or multi-block messages bypass built-in interception and start a normal Run.

- Current built-ins: `/agent` (optional, action), `/compact` (optional, toast), `/handoff` (optional, action), `/help` (none, transient), `/learn` (optional, action), `/model` (optional, action), `/new` (none, action), `/reflect` (optional, action), `/rename` (optional, action), `/continue` (none, action), `/status` (none, transient), `/stop` (none, toast). `/continue` starts the unresolved checkpoint through the shared no-new-message Run path and is unavailable after user Cancel; there is no legacy alias. `/status` reports the current Session and includes run activity (`running` or `idle`) plus active Run `created_at`/`updated_at` timestamps when present. It also reports context usage plus text-only cache lines for the last request and session total; cache lines render the placeholder when the provider did not report cache fields. It resolves the agent through the run-path `AgentResolver` seam (using the dispatcher's `project_id`), so a project session reports the resolved config agent instead of degrading to an empty reply, and it renders a `Project:` line (display name + id, or placeholder for an identity session) — the same builder the `status` tool uses (see `tools/status.md`). `/compact [instruction]` forwards the optional free-text argument into the summarization prompt (see `compaction.md`). `/handoff [agent:<id>] [instruction]` parses its argument with `parse_handoff_argument` (in `core/chat/commands.py`) into an optional leading `agent:<id>` target token (the `agent:` keyword is case-insensitive, the id keeps its case; a bare `agent:` with no id, or a stray colon in free text like `remember: …`, is treated as instruction, not a target) and an optional free-text instruction. The instruction is woven into the handoff-writing prompt via `_build_handoff_prompt` (mirroring `/compact`); its base text is the `handoff.md` backend prompt fragment (read through Storage, user-overridable via a `<data_dir>/prompts/` copy — like `compaction.md`), so without an instruction the prompt is that fragment verbatim (surrounding whitespace normalized away). It writes a handoff via an internal note-driven Run, creates a new session under the target agent (default: current), injects the handoff as a user message and auto-runs the receiving agent, and returns `data: {command: "handoff", session_id, agent_id}`. Recognition and argument parsing live in `core/chat/commands.py`; orchestration lives in `server/rpc/chat_methods.py` (`_handle_handoff_command`). `/agent [<addr>] [task]` is the *unplanned takeover* counterpart to `/handoff`: it **moves** the current session (full verbatim history, **same** session id) to another agent instead of summarizing into a fresh one. It is the first command with an **argument-dependent** result: bare `/agent` returns a `CommandHandled(output="transient")` directory card (personal agents from `AgentStore.list()` plus every project's team via `AgentResolver.scan_project_report(project).team`, team agents shown `name@projekt`); `/agent <addr> [task]` returns `CommandAction(name="move_session", argument=...)`. Its own grammar (`parse_agent_argument`, **not** `parse_handoff_argument`) takes the first whitespace token as the target address and the trimmed remainder as an optional task; the address goes through the one `parse_agent_address` seam, so a `/handoff`-reflex `agent:planner` is rejected as an invalid address rather than reinterpreted. Orchestration (`_handle_move_session_command` in `server/rpc/chat_methods.py`) refuses cleanly with **no partial move** when the address is invalid, the target is unknown (`resolve_agent`) or equals the source pair, the session has an active **or** queued run (stronger than `/handoff`'s active-only check — the queue is not moved), or the session is channel-bound (`source_channel_id`) or a sub-agent session (`is_subagent_session`/`subagent_parent`); otherwise it calls `ChatSessionManager.move(...)` (stripping `SESSION_MOVE_STRIP_META_KEYS` from `core.sessions`: the pinned skill catalog + seen-skills — a move is always cross-agent, so the target must re-pin its own catalog, exactly like a cross-agent fork — plus `visited_projects`), appends the `agent_takeover` divider then a silent takeover note (`AGENT_TAKEOVER_NOTE`, fixed text, not i18n) at the destination under its `write_lock`, re-homes the "current" pointer on each identity side (source via `AgentStore.reset_current_after_session_removed`, target via `update(current_session_id=...)`; project config agents carry no server-side current), publishes `resource_changed(sessions)` for both the source and target agent scopes plus `resource_changed(agents)` when an identity current pointer changed (same emit points as `session.create`/`session.delete`, so other windows refresh), optionally auto-runs the target with the task, and returns `data: {command: "agent", agent_id: <target-address>, session_id}` (same id, new address). `/model [<value>|reset]` persistently changes the **current session's agent model** between runs and, like `/agent`, is argument-dependent: bare `/model` returns a `CommandHandled(output="transient")` card naming the resolved model and its origin, read once through the resolver's provenance seam `AgentResolver.effective_config(project_id, agent_id)["model"]` (`{value, source}`) — no model-chain replication, None-guarded like `/status`. `_model_origin(project_id, source)` maps the winning tier to plain English: identity → `agent configuration` (source `agent`) / `global default` (`global_default`) / `not configured` (null); project → `override (set via /model)` (`override`) / `agent file in repo` (`agent`) / `project default` (`project_default`) / `global default` (`global_default`) / `not configured` (null). `/model <value>` and `/model reset` return `CommandAction(name="set_model", argument=<raw text>)`; execution lives in `server/rpc/chat_methods.py` (`_handle_set_model_command`). The accessor parses a case-insensitive `reset` token (→ clear) and validates a set value via the shared `_ensure_model_usable` gate (`AgentResolver.is_model_configured` — same rule as the scan's `BAD_MODEL` finding — plus, for a `::connection`-pinned value, the `_ensure_model_connection_supported` allowlist check); both reject with `invalid_request`. Routing follows the session kind: identity (`project_id is None`) → `runtime.agents.update(agent_id, model=value or "")`; project → `runtime.projects.set_override(project_id, agent_id, "model", value)` / `clear_override(project_id, agent_id, "model")` (the model override, top model-chain tier; see `projects.md`/`agent.md`). No busy-guard — it takes effect at the next run boundary. Returns `data: {command: "model", agent_id, model}` (toast). Setting an override from the UI is **not** offered; the Projects tab only shows and clears the model override (see `webui.md`). `/learn [request]` (optional, action) authors a reusable skill into the current identity agent's own home: `_handle_learn_command` (`server/rpc/chat_methods.py`) resolves the agent and refuses Config Agents with no Workspace before starting an **internal** run seeded with the `learn.md` brief fragment (read through Storage like `handoff.md`) woven with the optional request via `_build_learn_prompt`. The request is free text that may mix sources (a folder, URL, pasted text) with requirements shaping the skill — the brief instructs the agent to gather every source and honor every requirement; bare `/learn` authors from the recent conversation or asks the user. The agent authors via the `skill_manage` tool (offered to identity agents), and the run's summary is returned as a `CommandHandled` reply. Refused while a run is active. The internal-run starter `_start_command_run` is shared by `/handoff`, agent takeover, and `/learn`. `/reflect [focus]` (optional, action) reviews the current session in a **fork** and saves durable memory/skill updates without touching the original. The fork + review orchestration lives in the **reflection service** (`runtime.reflection.run_review(...)`, `core/automation/reflection.py` — shared with the automatic background cadence trigger; see `automation.md`): same-agent fork (cache-warm, pinned catalog kept, always-strip set from `core.sessions`), a recognizable fork title, then an **internal** run **in the fork** seeded with the `reflect.md` brief (the optional focus is passed as an extra instruction: `"The user asked you to focus this reflection on:\n…"`) under the dispatch-only `tool_restriction=("memory", "skill", "skill_manage")` — enforced at dispatch only (intersection in `core/chat/tool_dispatch.py`), so the fork's system prompt and provider tool definitions stay byte-identical to the source (the prompt-cache invariant); a denied call fails through the existing `tool_not_allowed` path. `_handle_reflect_command` (`server/rpc/chat_methods.py`) owns only the RPC-side gates and follow-ups: identity-agents-only (refuses cleanly when the resolved agent has an empty `workspace`), refused while a run is active on the source, publishes `resource_changed(sessions)` via the service's `on_fork_created` callback (the drawer shows the fork while the review runs), and resets the background cadence counters after success (`reflection.reset_counters` — a manual review covers both dimensions). The review runs on the streaming chat loop (the fork is fresh, never busy — no trigger-service queue), and its summary is returned as `data: {command: "reflect", session_id: <fork id>, agent_id}` so accessors can link to the fork.
