# Chat Run Execution

Task-gated reference for Chat admission, provider/Tool progression, streaming recovery, interruption, Continuation, cancellation, and Run-local Model fallback. Read this when changing those behaviors; Run storage, queue state, and lifecycle types themselves remain owned by `runs.md`.

`request_runner.py` emits request waiting/retrying/finished activity from the Run's shared `recovery.py::RecoveryBudget`; backoff notices include the next attempt and effective ceiling for the current Model route, delay, and Run/Model correlation. Both counts are route-local: normally `2/9` through `9/9`, with the ceiling reduced when fewer total attempts remain. The eighteen-attempt cross-route budget is never presented as eighteen attempts on one Model. Chat owns ordinary request retries through a task-local `core.utils.retry.caller_owns_retries()` scope, preventing nested HTTP retries from multiplying stream restarts. Standalone Adapter consumers retain their retry policy; bounded protocol repairs remain Adapter-owned. Final expected failures and unexpected executor exceptions persist exactly one error message per Run, including failures before the first user message; unexpected errors use a generic `internal_error` description and keep details in the central Run log. Failures during pre-Model preparation also mark the durable summary and completion observers unsuccessful. Cancellation and `RunInterruptedError` retain their terminal semantics (`test_chat_loop_lifecycle.py`, `test_chat_prompt.py`).

## Entry points and admission

Run start and terminal summary diagnostics log at DEBUG, including cancellation. The Run lifecycle remains the single failure-log owner: expected failures and exhausted interruptions log at WARNING, unexpected failures at ERROR with a traceback. Log levels do not change persisted Run summaries or lifecycle events. Coverage: `test_chat_loop_requests.py`, `test_chat_loop_lifecycle.py`, and `test_chat_loop_stream_recovery.py`.

`ChatLoop` exposes `send`, `start_run`, `queue_run`, `build_queue_update`, and `compact_session`. `run_executor(content, agent_overrides=None)` is the public seam handed to `ChatRunManager`; its optional frozen `AgentRunOverrides` captures only a Run-local primary Model and thinking effort for Sub-Agent execution. `child_loop(nesting_depth=...)` shares the explicit `ChatLoopDependencies`, attachment resolution, Compaction, reflection, and title notification but carries no ambient override state. The server-facing paths require an existing Session; the legacy direct `send()` path may still create one when no `session_id` is supplied.

`start_run` persists visible content as a user message and internal content as a note. `sender`, `input_origin`, `reply_surface`, `project_id`, dispatch-only `tool_restriction`, optional live `tool_denial_resolver`, `input_persisted_hook`, `contributes_to_agent_activity`, and the narrow `resume_process_restart` flag ride the admitted executor. The hook runs only after that initiating message is fsynced, including for queued Runs, and its failure is ancillary: Chat logs it without failing the admitted Run. `queue_run` validates the same prerequisites and captures both Tool-policy inputs with the other immutable execution data so a queued item preserves its admission ceiling while live denials can still observe current external state when it starts or dispatches. The activity policy defaults `True`; when false, Chat still persists the complete transcript and `run_summary` but deliberately does not call the Sessions completion-activity recorder, so the Run cannot create durable unread state. The async `build_queue_update` returns replacement data without mutating Queue state; it resolves the Agent and Session off the Event Loop like admission and rebuilds from the queued executor's original `_RunRequest`, replacing only edited content and the edit RPC's `input_origin`, so Sender, reply surface, Tool restrictions/denials, hooks, overrides, and internal/restart semantics cannot be widened or dropped by a WebUI edit.

Session/address ownership and execution context are separate. `run.project_id` is the public Session/address anchor and queue key; Identity Agent Runs keep it `None`. At admission Chat snapshots `run.working_project_id` from the addressed Config Agent's Project or an Identity Agent's explicit root. That snapshot supplies Tool cwd, Project Files/Skills, prompt context, file mentions, and Compaction rebuilds. If the Project/repository disappears before queued work starts, execution fails before new user content is persisted; Workspace is not a fallback.

## Agentic progression and events

Chat resolves or creates Sessions through the async storage facade, while synchronous execution-context preparation and metadata/file reads use its bounded transform pool. At the Run boundary the Agent (including a temporary Session's binding) resolves through the resolver's async entry points, and a Working Project's anchor and repository check run in one transform-pool hop. Provider `send`/stream I/O remains on the Event Loop; non-streaming response normalization, canonical Assistant construction, Usage completion, output-file scanning, and Context Usage estimation return from the transform pool before durable persistence and Run events.

At executor start the loop loads one canonical Session snapshot while holding the Session `write_lock`, then resolves one Run-local execution context: Agent, Session, working Project cwd/prompt inputs, Skill scope and pinned catalog, Continuation tracker/reminder, immutable Tool restriction, live Tool-denial resolver, and a primary Model target containing the exact Provider Connection, adapter policies, Model input modalities, wire media types, and stream timeout. The short locked snapshot gives one transactionally consistent prefix without holding the lock across later Provider work. Context preparation owns the primary adapter until the complete execution context returns and closes it on preparation failure. The snapshot is reused for request construction, Continuation reconciliation, Project Tool Context recovery, Usage aggregation, and terminal projection; Run-owned history writes return their generation-aware delta since the snapshot cursor from the same write transaction, and other refreshes use `load_since_async`, so the snapshot never reloads complete history for its own appends. Automatic Compaction boundaries refresh and commit against this same snapshot instead of loading history. When the admitted request carries `AgentRunOverrides`, Chat asks the common `AgentResolver` for an immutable overlaid runtime view at this boundary; omitted overrides take the exact ordinary resolution path. System Prompt, canonical history, route-filtered Provider Tool definitions, and Chat-derived Session Tool grants then form the context's mutable request state before the first Provider call; `history` appears only after persisted Compaction. Dispatch-only restrictions and denials are deliberately absent from request building, preserving byte-identical System Prompt content and Provider Tool definitions; no admitted request can add a Run-local Tool grant. Provider adapters yield normalized data only. A recognizable malformed Tool attempt, including malformed JSON arguments or a malformed `tool_calls` container, becomes an addressable canonical rejected `ToolCall` rather than a response-parsing exception. Before each stable Assistant event and Session append, Chat resolves eligible `file:` marker spans against the captured working Project cwd or Agent workspace and attaches internal references without reading or copying file bytes. Chat persists finalized Assistant/Tool/Error Messages through Event-Loop-safe Session APIs and emits provider-agnostic `RunEvent`s`; opaque `reasoning_meta` never appears in visible events.

`Run.iteration_count` is the single canonical Agentic Loop count. Chat derives the next debug ordinal from it and increments it exactly once after one Model request returns a response into the loop, before persistence or Tool dispatch: a response containing only Reasoning still counts once, a response requesting any number of sibling Tool Calls still counts once, and an unanswered failed Provider attempt counts zero. Stream replays before a completed response retain the same ordinal. Live `model_step_usage`, terminal Run events, the terminal Run Summary, active-Run RPC responses, and Reflection are projections or consumers of this Run-owned value; none may derive it from Assistant messages, rendered outputs, Tool Calls, or Tool Results.

Each completed Model step carries the Adapter's canonical terminal outcome. Only `tool_calls` authorizes Tool dispatch. A turn ending `output_truncated` with Tool Calls persists the partial Assistant and ordered `tool_call_truncated` Results, invokes neither handlers nor Extensions, and continues so the Model can reissue a complete call. `content_filtered`, `error`, `unknown`, or an outcome inconsistent with the presence of Tool Calls persists correlated `tool_call_rejected` Results without dispatch and then fails the step. This terminal safety gate precedes every Tool execution path.

`output_truncated` without Tool Calls also requires recovery: readable text or Reasoning is persisted as interrupted and continued, never accepted as a final answer. Empty or whitespace-only `stop`/`output_truncated` responses retry without persisting an empty Assistant. Reasoning-only successful-looking output, including inline Reasoning after canonical ingestion, likewise requests the missing answer. These paths share the same budget as transport recovery.

Agentic progression and automatic Compaction receive the Run context plus the current Model target, not the Runtime service surface or a parallel list of Run fields. Tool dispatch receives a Tool-specific projection of the same context. Run-local fallback builds a replacement Model target while retaining the Session, Project, Skill, Tool-policy, and Continuation context, then rebuilds mutable request state so media handling and route-gated Tool visibility match the fallback route.

Streaming deltas (`assistant_output_delta`, `reasoning_delta`, `tool_call_delta`, `tool_call_stdout`, `tool_call_stderr`) and `provider_heartbeat` are transient SSE events and never persisted. A Provider heartbeat reports an SSE transport keepalive plus seconds since the last normalized Model delta; it is visible liveness only, never Assistant content, Reasoning, Tool progress, or a completed Tool Call. Stable events include Assistant output, Tool start/result, the `compaction_started` -> `compaction_completed` / `compaction_aborted` lifecycle, Model fallback, error persistence, per-model-step Usage, and terminal Run lifecycle from the Runs domain. Tool failures use the stable Tool Result envelope with `ok=false`; there is no separate public `tool_call_failed` event.

Chat rate-limits transient Model delta emission through `StreamingDeltaBatcher`: the first visible fragment is immediate, adjacent text or same-Tool fragments are merged for up to 40 ms, and every Provider heartbeat, finish, or recoverable stream failure flushes the pending batch before the next stable boundary. The accumulator and Continuation tracker still consume every normalized Provider fragment, so batching changes only Run/SSE event pressure, not canonical Assistant content, Tool arguments, interruption evidence, or stable event ordering.

Immediately before each Model request, Chat holds the Session write lock, lets Automation persist any Bash/Sub-Agent completion notices ready for that exact active Run, and then drains pending notes into the request as System Reminders. This is a request-boundary join, not a new Provider request: a notice that becomes ready after that point waits for the next iteration, and one with no later iteration falls back to Automation's internal follow-up Run after the boundary Run ends. The seam runs only outside Tool dispatch, so completion notes cannot split an Assistant Tool-call batch from its ordered Tool Results; a manual terminal Process result may still cancel its pending notice before the next boundary.

Sibling Tool Calls from one Assistant turn execute concurrently by default within the shared limits, including multiple calls to the same Tool. A Tool registered with `parallel_safe=False` is the only semantic ordering barrier. Recovery metadata never changes scheduling: calls recovered from one consecutive JSON argument sequence use the same parallel policy as native siblings, validate and fail independently, and an invalid recovered call never blocks a valid sequence sibling. Unknown Tool names also remain in the concurrent batch because they cannot invoke a handler; a called name that clearly means an offered Tool was already resolved before the Assistant turn was persisted (`tools.md` -> Called Tool names). Active Extension `tool_call` and `tool_result` callbacks run one at a time through a batch-local lock, while parallel-safe Tool handlers may still overlap. The next Model request waits for every sibling to terminate, and Chat persists every ordered Tool Result plus any deferred Tool-cycle Notes through one `append_many_async` transaction only after the executor returns the complete batch. Result-persisted callbacks and Continuation Tool-result records run only after that whole canonical batch settles. Therefore a forceful Run cancel can leave even a handler-computed sibling without a durable Result when another sibling was still active; request shaping treats only canonical Session history as surviving evidence and synthesizes each missing Result exactly once without persisting the repair. A Tool may register an `after_result_persisted` callback through its `ToolContext`; Chat invokes it only after that Tool Result commits in the Parent Session, and a callback failure is logged without changing the already-persisted result or failing the Run. Result payloads an Extension Tool attaches (`extensions.md`) are staged per call in `ToolDispatchContext` and merged into that call's `ToolResultFacts`, so they commit in the same batch transaction as their Tool Result; a handler that raises or returns an invalid result drops its staged payloads (the failure envelope replaces them), a cancelled batch persists none, and attaching after the call ended raises. A rejected canonical Tool Call is resolved first and bypasses live denials, Extension hooks, and the Tool handler while emitting the normal lifecycle and its non-retryable rejection envelope. Other calls continue through the live Tool-denial resolver, Runtime Tool registry, effective allowlist, Extension decision pipeline, optional Run-local restriction, and canonical pre-handler validation. Unknown Tools, invalid arguments, handler crashes, and invalid/non-serializable results become per-call failure envelopes so the Model can recover; one failed sibling never blocks valid siblings or aborts the Run. The Run-local failed-Tool circuit breaker compares Tool name, canonical arguments, stable error code, canonical schema fingerprint, and any rejection fingerprint in declared result order: a materially different failed call or any success resets the streak. After the eighth consecutive identical failed call, or when the Tool-iteration ceiling rejects the next requested batch, Chat persists correlated non-retryable Results, adds a finalization reminder, and makes the next Model request with no Tool definitions. If the Model ignores that boundary, Chat persists a `tool_calls_disabled` Result and gives it one bounded recovery request with Tools still disabled; a second violation is also correlated and persisted, then completes gracefully instead of looping or failing the Run.

Auto-compaction runs only at safe completed Model boundaries. Summary+Tail may compact after a complete Tool cycle or final Assistant response; Continuation waits for a final Assistant response so it does not split work whose next action is still unknown. The Session write lock ends at the durable Assistant/Tool boundary before Compaction planning or Model I/O begins. Automatic checkpoint persistence is a later cursor-validated conditional append; a concurrent out-of-band message aborts the stale checkpoint, and a same-Run path rebuilds its uncompacted request from current Session history before the next Model step. Compaction mechanics and policy live in `compaction.md`.

## User steering

Ordinary queued User inputs advertise steering eligibility; Channel/sender-bearing input, internal work, execution-owner bindings, overrides, and requests with special Tool policy or hooks cannot be merged into another execution. `_queued_input.py` retains the immutable queued executor and owns Chat's steering persistence/request rebuild helpers. `Run.accepts_steering` is enabled only for ordinary User Runs. `chat.queue_steer` requires the intended Run id, so a stale click cannot steer its successor.

Before each Model request, under the Session write lock and outside Tool dispatch, Chat delivers selected Queue items in FIFO order. Each item becomes a normal User message with the current Run membership, original content/input origin, and Session image references. The append and Queue acknowledgement finish together before honoring cancellation; failed appends retain the item. The existing `user_message_persisted` event carries its `queue_item_id` for live Queue retirement. Request rebuilding uses ordinary media/Skill handling, preserves live Tool media, current-Run native Reasoning, and Continuation context through the shared live rebuild path, and retains the active Model and execution policy. Steering does not cancel Provider generation or a Tool batch.

After a final Assistant response, a pending steer forces another iteration. If that input is removed before delivery, the persisted final answer remains the Run result and no further Model request is made. Otherwise Chat synchronously closes steering admission before terminal Compaction/cleanup; later clicks fail without removing queued content. Cancel/error leaves undelivered inputs in the ordinary Queue. Tests: `test_chat_loop_steering.py`, `tests/core/runs/test_runs_queue.py`, and `tests/server/rpc/test_chat_methods_queue.py`.

## Model and Connection resolution

Agent Model strings use `<provider>/<model-id>[::<connection-local-id>[:<account-id>]]`. `core/chat/model_resolution.py` parses the optional pin. An explicit pin is used verbatim; an unpinned Model selects the first usable Provider Connection permitted by the Model's `connections` allowlist. A non-empty allowlist with no usable matching Connection fails instead of routing through a forbidden Connection. Unknown Model ids are left for the Provider API to reject after Provider/Connection validation.

If a qualifying failure exhausts same-Model recovery and the Agent has a resolvable `fallback_models` chain, Chat advances candidates in listed order while the shared recovery budget remains. An activated candidate serves the rest of the current Run. Its adapter closes on every exit after construction, including request-rebuild or Compaction failure before its first send. Qualifying errors are retryable Provider failures, exhausted provider/network/timeout interruptions (including chunk/progress stalls and missing-answer recovery), and clearly model-scoped fatals (404 status or unknown-model wording). Rate limits before answer text skip remaining same-Model retries when a chain is configured. Each switch emits `model_fallback_activated`, persists a System Reminder note, rebuilds request state with the fallback route (including `analyze_image` visibility), and leaves Agent configuration unchanged so the next Run starts from the primary Model. A preserved interrupted result receives the continuation reminder on the new route. Resolution dedupes against the primary and earlier candidates; unresolvable, unusable, or unconstructable candidates are skipped with a warning. When no candidate succeeds, the last actual failure determines failed versus interrupted termination. Auth, billing, permission, content-policy, and context-overflow errors never advance the chain.

A Run-local primary Model override leaves `fallback_models` unchanged, so the target Agent's existing fallback policy remains active. The overlaid `thinking_effort` belongs to the Run-local Agent view and therefore reaches both primary and fallback Model steps through the same Provider-neutral Reasoning policy.

## Continuation checkpoint

Every admitted visible Run owns a provider-neutral append-only Continuation journal in `core/chat/continuation.py`. It records original visible requests, readable reasoning/partial output, stable Assistant boundaries, Tool references/status, Compaction boundaries, and the interruption cause without copying opaque reasoning metadata or full Tool Results. The Run's `run_started` record commits inside the history append that persists its input, together with any Skill announcement and its seen-Skill record, so admission costs no separate journal transaction and the journal never records a started Run whose input did not commit; a Run with no input left to persist starts the chain explicitly, and a Run that fails before its input commits writes the start and its interruption in one transaction. Journal I/O uses the Session async boundary, and the tracker serializes every sink write so a periodic stream flush can never land after the stable Assistant/Tool boundary that consumed it; cancellation waits for any already-started sink write to settle. Dirty streaming state flushes at most every two seconds; interruption flushes immediately. Stable Assistant and Tool Result boundaries, with any pending stream deltas, commit inside the history append that persists them, so journal and canonical history agree about every boundary without a separate journal transaction; a failed append keeps the deltas pending. An Assistant boundary registers its Tool Calls as started. Sessions folds every record into typed current state as it is written; recovery, interruption and the reminder refresh read that state (`ChatSession.load_continuation`) and reconcile it only against canonical history, so Chat keeps no second fold. Each persisted Assistant boundary, including an interrupted partial, closes its own journal slot: a replayed attempt discards only its own unpersisted deltas, and a later continuation never overwrites earlier partial output or readable reasoning. Canonical Session history remains authoritative for actual Tool Calls and Results.

An interrupted checkpoint attaches exactly once at executor start to the next visible Run, immediately before that Run's newly persisted user message. Its wrapper only states that the previous Run was interrupted and that the checkpoint records what happened before the interruption; it does not direct the Model to resume, continue, inspect, or repeat anything. Recorded requests, readable reasoning, partial output, and Tool names/ids are JSON-quoted with escaped angle brackets (`{"request": ...}`, `{"readable_thinking": ...}`, `{"partial_output": ...}`, one `{"tool", "tool_call_id", "status"}` object per operation), so recorded text can never close the checkpoint or its System Reminder; budget truncation quotes the kept reasoning tail after cutting it. A complete non-interrupted Assistant result resolves it; a further interruption extends the chain. An `edit_run` neither consumes nor extends an earlier checkpoint: committing its history edit discards the old journal and restarts the editing Run's own chain, so an interrupted edit still leaves its checkpoint. Internal Runs neither consume nor resolve visible Continuation state by default. The sole exception is an explicitly admitted Bootstrap fixed-Session Run with `resume_process_restart=True`: Chat recovers and tracks the checkpoint only when its normalized cause is `process_restart`, leaving user/provider/network/timeout/internal interruptions for the next visible Run. Run management owns durable terminal completion. Successful Continuation state is removed in that same transaction; a failed commit retains recovery state and cannot announce persisted success. Snapshot/Usage diagnostics remain best-effort. There is no separate Continue or Discard action.

Budget truncation always retains the checkpoint closing tag and explicit truncation notice, including when requests or operation lists alone exceed the budget. The checkpoint remains internal to Chat. Its normalized cause is also stored on a preserved partial as `interruption_cause` beside `interrupted: true`, so internal result consumers such as Sub-Agents can distinguish a partial terminal result; both annotations are removed from ordinary Provider-visible history fields. The canonical partial retains readable and opaque Reasoning as durable evidence, but every later request strips its native `reasoning` and `reasoning_meta` even under same-scope `full_history`; recovery returns readable work only as provider-neutral reminder text. User Cancel and any stream interruption that exhausts its bounded same-Run recovery leave the checkpoint for the next eligible visible Run; process restart and non-streaming failures keep their existing checkpoint rules. Missing or unknown effects from `write`, `apply_patch`, `bash`, or historical `edit` Calls are labeled as uncertain filesystem or process effects without an accompanying instruction.

## Streaming recovery

One `RecoveryBudget` in the Run context bounds each unfinished Model step: at most nine attempts per exact Model route (including the initial request), eighteen across configured fallback routes, and thirty minutes from the first recoverable failure. Initial healthy generation is not subject to that recovery deadline. Ordinary establishment retries, stream restarts, non-streaming fallback requests, partial-answer continuations, empty answers, and truncated Tool reissues all spend that same budget. Partial text, Reasoning, heartbeats, and route switches never reset it. A complete Model response (final answer or Tool-call turn, never an interrupted partial or truncated turn) ends the step and resets it, so a following Tool, steering, or finalization request inherits neither attempts nor backoff; the separate failed-Tool breaker and Tool-iteration ceiling still apply. Backoff grows per route (1, 2, 4, 8, 16, 32, 64, then 128 seconds before jitter); a newly selected fallback starts its own short backoff without resetting the shared attempt/time budget. It uses the shared exponential/jitter calculation and capped `Retry-After` hints, including in-band stream errors; waits are cancellable, and a retry whose delay cannot fit the remaining deadline does not start.

`core/chat/streaming.py::decide_stream_recovery` is the single provider-agnostic decision owner. It sees normalized errors plus whether a finish arrived, partial answer content exists, and a same-Model restart remains. It returns `ACCEPT_COMPLETE`, `RESTART`, `FALLBACK`, `PRESERVE_PARTIAL`, `INTERRUPT`, or `FAIL`; `request_runner.py::WireRequestRunner._consume_stream_attempt` owns the side effects.

- After a normalized finish delta, a later transport/provider failure retains that logical outcome and accumulated Usage; empty-answer and output-integrity checks still apply.
- Before answer text, unsupported streaming switches to non-streaming; retryable transient failures restart the identical request while the shared budget remains; other failures propagate. Readable Reasoning and an in-flight Tool Call preview do not block a restart because neither has produced answer text nor executed a Tool. Before replay, Chat appends `stream_attempt_discarded`, clears pending readable deltas from the Continuation Checkpoint, emits `stream_attempt_restarted` so consumers can discard previews, and discards incomplete Tool Calls. Exhausted network/timeout recovery becomes `RunInterruptedError`; retryable Provider errors propagate directly. Both can reach configured Model fallback before terminating. A Provider adapter may select a safer transport for the retry; the replay decision remains provider-neutral.
- After answer text, Chat preserves an `interrupted` Assistant boundary and drops in-flight unexecuted Tool Calls. A transient failure appends a provider-neutral recovery note and continues from the durable partial using the shared budget; only a later complete Tool Call can dispatch. Fatal failures propagate after persistence without an automatic continuation. Exhausted partial recovery may advance the configured Model chain; without a successful candidate it ends interrupted rather than falsely completed. The interrupted Run result combines only the visible fragments of the unfinished step, across its continuations and fallback routes; a complete Tool-call turn or answer ends that step, so earlier fragments never reappear in a later interrupted result. Recovery itself never re-executes completed Tool Calls or consumes the Tool-loop iteration budget.
- Remote Providers use two independent stream guards. A 180-second transport window resets on every normalized Model delta or Provider heartbeat; a 900-second Model-progress window resets only on normalized Reasoning, content, Tool-call, finish, or Usage. OpenAI-compatible SSE comments become transport-only heartbeats because verified gateways can buffer a complete large Tool Call while sending comments, then release all arguments as one delta; the UI reports that connected wait without presenting it as Model output. Incomplete SSE events and arbitrary raw bytes still count as neither. Loopback, localhost/local-domain, RFC1918 private, and link-local base URLs are exempt from both windows so long local prefill does not look like a dead stream.

## Cancellation

Completed visible Assistant output is protected through asynchronous preparation and the durable append when Stop arrives; cancellation still prevents subsequent Model/Tool work. Tool-round counts, repeated-failure tracking, and no-Tool finalization state belong to the Run context and survive Model fallback.

Cancel is best effort. Tool dispatch marks each call active before publishing `tool_call_started`, so an immediate per-call cancel is retained even when Tool-owned cleanup registers a moment later; that callback then fires immediately. `Run.request_cancel` suppresses late non-terminal output, prevents new Tool progression, invokes every still-active per-Tool cancel callback in registration order, calls the runtime ProcessManager cancellation scope, and forcefully cancels the executor task after cleanup signals are scheduled. A Run completion observer releases that closed scope once the Run has settled. Completed Tool Calls have already cleared their callbacks and are not cancelled twice; a callback registered after the Run signal fires immediately. Already persisted history is never rolled back, while any missing member of an interrupted Tool batch remains request-only repair work for the next Provider request.

When readable reasoning or answer content already exists at cancellation, Chat uses the same partial finalization path as other interruptions so every readable block the user saw remains persisted in an `interrupted` Assistant message; a reasoning-only message has no answer content, and the Run still terminates `cancelled`. With neither readable reasoning nor answer content no Assistant message is added; the private checkpoint separately retains recovery state and the `run_summary` remains the timeline anchor. Stop after a complete final answer - while it is being persisted or during the optional post-answer Summary+Tail Compaction - still ends the Run `cancelled`, but that answer stays its result and resolves the Continuation checkpoint instead of being reported to the next Run as interrupted. During Tool dispatch, cooperatively terminated complete batches preserve their ordered Results, while forceful cancellation can interrupt delivery of the whole batch and relies on request-only missing-Result repair.
