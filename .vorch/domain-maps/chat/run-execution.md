# Chat Run Execution

Task-gated reference for Chat admission, provider/Tool progression, streaming recovery, interruption, cancellation, and Run-local Model fallback. Read this when changing those behaviors; Run storage, queue state, and lifecycle types themselves remain owned by `runs.md`.

`request_runner.py` emits request waiting/retrying/finished activity from the Run's shared `recovery.py::RecoveryBudget`; backoff notices include the next attempt and effective ceiling for the current Model route, delay, and Run/Model correlation. Both counts are route-local: normally `2/9` through `9/9`, with the ceiling reduced when fewer total attempts remain. The eighteen-attempt cross-route budget is never presented as eighteen attempts on one Model. Chat owns ordinary request retries through a task-local `core.utils.retry.caller_owns_retries()` scope, preventing nested HTTP retries from multiplying stream restarts. Standalone Adapter consumers retain their retry policy; bounded protocol repairs remain Adapter-owned. Final expected failures and unexpected executor exceptions persist exactly one error message per Run, including failures before the first user message; unexpected errors use a generic `internal_error` description and keep details in the central Run log. Failures during pre-Model preparation also mark the durable summary and completion observers unsuccessful. Cancellation and `RunInterruptedError` retain their terminal semantics (`test_chat_loop_lifecycle.py`, `test_chat_prompt.py`).

## Entry points and admission

Run start logs at DEBUG. The Runs domain writes each Run's one terminal line (`runs.md` -> Constraints & Gotchas); Chat never logs the outcome itself but supplies its facts on the `Run`: `model` (the bare answering route, replaced when a Model fallback activates), `internal`, `retry_count` (every backoff-scheduled Model request retry, partial-answer continuations included) and `stream_recovery_count` (partial answers preserved after a broken stream). Per-attempt retry, stream-recovery and missing-answer lines log at DEBUG, as does a transport failure after a finish delta whose completed response the Run keeps; each Model fallback switch logs one WARNING. An interruption keeps the last failure as its cause so the terminal line can name it. Log levels do not change persisted Run summaries or lifecycle events. Coverage: `test_chat_loop_requests.py`, `test_chat_loop_lifecycle.py`, and `test_chat_loop_stream_recovery.py`.

`ChatLoop` exposes `send`, `start_run`, `queue_run`, `build_queue_update`, and `compact_session`. `run_executor(content)` is the public seam handed to `ChatRunManager`; it carries no Agent overrides, because every Run resolves its Agent as its Session runs it (Session Agent overrides: `projects/resolution.md`). Its executor is a `QueuedChatInput`, so the Queue can steer it into a running turn when the item is steerable; `parent_agent_input=True` marks Parent Agent input in a Sub-Agent Session, which Chat frames with its own System Reminder and never counts as the user's takeover (`subagents.md` -> Conventions). The server-facing paths require an existing Session; the legacy direct `send()` path may still create one when no `session_id` is supplied.

`start_run` persists visible content as a user message and internal content as a note. `sender`, `input_origin`, `reply_surface`, `project_id`, dispatch-only `tool_restriction`, optional live `tool_denial_resolver`, optional per-Run `max_tool_iterations`, `input_persisted_hook`, and `contributes_to_agent_activity` ride the admitted executor. The hook runs only after that initiating message is fsynced, including for queued Runs, and its failure is ancillary: Chat logs it without failing the admitted Run. `queue_run` validates the same prerequisites and captures both Tool-policy inputs with the other immutable execution data so a queued item preserves its admission ceiling while live denials can still observe current external state when it starts or dispatches. The activity policy defaults `True`; when false, Chat still persists the complete transcript and `run_summary` but deliberately does not call the Sessions completion-activity recorder, so the Run cannot create durable unread state. The async `build_queue_update` returns replacement data without mutating Queue state; it resolves the Agent and Session off the Event Loop like admission and rebuilds from the queued executor's original `_RunRequest`, replacing only edited content and the edit RPC's `input_origin`, so Sender, reply surface, Tool restrictions/denials, hooks, and internal/restart semantics cannot be widened or dropped by a WebUI edit.

Session/address ownership and execution context are separate. `run.project_id` is the public Session/address anchor and queue key; Identity Agent Runs keep it `None`. At admission Chat snapshots `run.working_project_id` from the addressed Config Agent's Project or the Session's Working Project (`AgentResolver.resolve_working_project_async`; a Session the start creates stores it, `sessions.md` -> Terms -> Working Project). That snapshot supplies Tool cwd, Project Files/Skills, prompt context, file mentions, and Compaction rebuilds. If the Project/repository disappears before queued work starts, execution fails before new user content is persisted; Workspace is not a fallback. A Session whose Working Project no longer exists is refused the same way (`WorkingProjectMissingError`, `projects/resolution.md` -> Working Project resolution).

## Agentic progression and events

Chat resolves or creates Sessions through the async storage facade, while synchronous execution-context preparation and metadata/file reads use its bounded transform pool. At the Run boundary the Agent (including a temporary Session's binding) resolves through the resolver's async entry points, and a Working Project's anchor and repository check run in one transform-pool hop. Provider stream I/O (and the completed-response fallback) remains on the Event Loop; fallback response normalization, canonical Assistant construction, Usage completion, output-file scanning, and Context Usage estimation return from the transform pool before durable persistence and Run events.

At executor start the loop loads one canonical Session snapshot while holding the Session `write_lock`, then resolves one Run-local execution context: Agent, Session, working Project cwd/prompt inputs, Skill scope and pinned catalog, Continuation tracker and recovered checkpoint, immutable Tool restriction, live Tool-denial resolver, and a primary Model target containing the exact Provider Connection, adapter policies, Model input modalities, wire media types, and stream timeout. The short locked snapshot gives one transactionally consistent prefix without holding the lock across later Provider work. Context preparation owns the primary adapter until the complete execution context returns and closes it on preparation failure. The snapshot is reused for request construction, Continuation reconciliation, Project Tool Context recovery, Usage aggregation, and terminal projection; Run-owned history writes return their generation-aware delta since the snapshot cursor from the same write transaction, and other refreshes use `load_since_async`, so the snapshot never reloads complete history for its own appends. Automatic Compaction boundaries refresh and commit against this same snapshot instead of loading history. Chat resolves the Agent through the common `AgentResolver` with the Run's Session, so the Session's Agent overrides (Model, thinking effort, temperature, top_p) apply at this boundary; admission preflights resolve the same way. System Prompt, canonical history, the prompt epoch's pinned Provider Tool definitions with the Tool changes announced since (`chat/request-building.md` -> Tool catalog per prompt epoch), and Chat-derived Session Tool grants then form the context's mutable request state before the first Provider call. Dispatch-only restrictions and denials are deliberately absent from request building, preserving byte-identical System Prompt content and Provider Tool definitions; no admitted request can add a Run-local Tool grant. Provider adapters yield normalized data only. A recognizable malformed Tool attempt, including malformed JSON arguments or a malformed `tool_calls` container, becomes an addressable canonical rejected `ToolCall` rather than a response-parsing exception. Before each stable Assistant event and Session append, Chat resolves eligible `file:` marker spans against the captured working Project cwd or Agent workspace and attaches internal references without reading or copying file bytes. Chat persists finalized Assistant/Tool/Error Messages through Event-Loop-safe Session APIs and emits provider-agnostic `RunEvent`s`; opaque `reasoning_meta` never appears in visible events.

`Run.iteration_count` is the single canonical Agentic Loop count. Chat derives the next debug ordinal from it and increments it exactly once after one Model request returns a response into the loop, before persistence or Tool dispatch: a response containing only Reasoning still counts once, a response requesting any number of sibling Tool Calls still counts once, and an unanswered failed Provider attempt counts zero. Stream replays before a completed response retain the same ordinal. Tool Calls that start while the response still streams get that request's ordinal in their `ToolContext`, although the count itself moves only when the response is complete. Live `model_step_usage`, terminal Run events, the terminal Run Summary, active-Run RPC responses, and Reflection are projections or consumers of this Run-owned value; none may derive it from Assistant messages, rendered outputs, Tool Calls, or Tool Results.

Each completed Model step carries the Adapter's canonical terminal outcome. Only `tool_calls` authorizes dispatch of the Calls that arrive with the end of the response; Calls the stream completed earlier already started (see Tool Calls during the stream) and keep their real Results whatever the outcome, while the gate below applies to every Call not yet started. A turn ending `output_truncated` with Tool Calls persists the partial Assistant and ordered `tool_call_truncated` Results, invokes neither handlers nor Extensions, and continues so the Model can reissue a complete call. `content_filtered`, `error`, `unknown`, or an outcome inconsistent with the presence of Tool Calls persists correlated `tool_call_rejected` Results without dispatch and then fails the step. This terminal safety gate precedes the execution of every Call that had not started when the response ended.

`output_truncated` without Tool Calls also requires recovery: readable text or Reasoning is persisted as interrupted and continued, never accepted as a final answer. Empty or whitespace-only `stop`/`output_truncated` responses retry without persisting an empty Assistant. Reasoning-only successful-looking output, including inline Reasoning after canonical ingestion, likewise requests the missing answer. These paths share the same budget as transport recovery.

Agentic progression and automatic Compaction receive the Run context plus the current Model target, not the Runtime service surface or a parallel list of Run fields. Tool dispatch receives a Tool-specific projection of the same context. Run-local fallback builds a replacement Model target while retaining the Session, Project, Skill, Tool-policy, and Continuation context, then rebuilds mutable request state so media handling matches the fallback route; the fallback request lists the epoch's pinned Tools plus every announced addition, and Tool changes are still measured on the primary target.

Streaming deltas (`assistant_output_delta`, `reasoning_delta`, `tool_call_delta`, `tool_call_output`: a running shell command's newest screen rows, each replacing the previous) and `provider_heartbeat` are transient SSE events and never persisted. A Provider heartbeat reports an SSE transport keepalive plus seconds since the last normalized Model delta; it is visible liveness only, never Assistant content, Reasoning, Tool progress, or a completed Tool Call. Stable events include Assistant output, Tool start/result, the `compaction_started` -> `compaction_completed` / `compaction_aborted` lifecycle, Model fallback, error persistence, per-model-step Usage, and terminal Run lifecycle from the Runs domain. Tool failures use the stable Tool Result envelope with `ok=false`; there is no separate public `tool_call_failed` event.

Chat rate-limits transient Model delta emission through `StreamingDeltaBatcher`: the first visible fragment is immediate, adjacent text or same-Tool fragments are merged for up to 40 ms, and every Provider heartbeat, finish, or recoverable stream failure flushes the pending batch before the next stable boundary. The accumulator and Continuation tracker still consume every normalized Provider fragment, so batching changes only Run/SSE event pressure, not canonical Assistant content, Tool arguments, interruption evidence, or stable event ordering.

Immediately before each Model request, Chat holds the Session write lock, lets Automation persist any shell command, Terminal or Sub-Agent completion notices ready for that exact active Run, and then drains pending notes into the request as System Reminders. The drained notes (with a temporary Session's delivery note) render exactly as the next request replays them from history: `wire_shaping.extend_request_with_notes` re-renders the notes the live request already ends with together with the new ones, so a boundary never splits a reminder group that replay would merge and the history bytes stay stable for the prompt cache (`tests/core/chat/test_chat_loop_requests.py`). This is a request-boundary join, not a new Provider request: a notice that becomes ready after that point waits for the next iteration, and one with no later iteration falls back to Automation's internal follow-up Run after the boundary Run ends. The seam runs only outside Tool dispatch, so completion notes cannot split an Assistant Tool-call batch from its ordered Tool Results; a manual `terminal` result may still cancel its pending notice before the next boundary.

**Tool Calls during the stream.** A Tool Call starts as soon as the stream has moved past it - a later Tool Call, answer text or Reasoning began - and its arguments form one complete JSON value; the last Call starts with the finish (`streaming.py::StreamingAccumulator.take_completed_tool_calls`, which hands out only a leading run of complete Calls, so started Calls are always a prefix of the turn's Calls and a taken Call is final). `_agentic_progression.py` opens a `tool_dispatch.py::ToolRound` before each Model request when the turn may run Tools (no finalization in progress and the Tool-iteration ceiling not reached; otherwise every Call is refused after the response as before). The round names the Assistant turn up front (pre-allocated message id, so `tool_call_started` and the persisted turn agree), runs its Calls in the `contextvars` context from before the request (never inside the request's `caller_owns_retries()` scope; `_send_until_final` opens a `SessionWriteLeaseScope` there, so a Call that takes its own Session's write lock joins the lease Chat holds while persisting the turn instead of deadlocking, `sessions.md`), buffers Tool Notes until the round finishes and adds Calls that arrive only with the finish after the started ones. The runner flushes pending visible deltas before it starts a Call, so `tool_call_delta` never follows that Call's `tool_call_started`. Persistence is unchanged: the Assistant turn, then all ordered Results in one transaction. Coverage: `test_chat_loop_eager_tools.py`, `test_streaming.py`, `tests/core/tools/test_tools_execution.py::test_batch_starts_each_call_before_later_calls_are_known`.

Sibling Tool Calls from one Assistant turn execute concurrently by default within the shared limits, including multiple calls to the same Tool. A Tool registered with `parallel_safe=False` is the only semantic ordering barrier. Recovery metadata never changes scheduling: calls recovered from one consecutive JSON argument sequence use the same parallel policy as native siblings, validate and fail independently, and an invalid recovered call never blocks a valid sequence sibling. Unknown Tool names also remain in the concurrent batch because they cannot invoke a handler; a called name that clearly means an offered Tool was already resolved before the Assistant turn was persisted (`tools.md` -> Called Tool names). Active Extension `tool_call` and `tool_result` callbacks run one at a time through a batch-local lock, while parallel-safe Tool handlers may still overlap. A Run cancel lets the `tool_result` callbacks of a call whose handler already returned finish within a five-second grace (`tool_dispatch.py::_RESULT_HOOK_CANCEL_GRACE_SECONDS`), so its result survives; callbacks that outlast it are cancelled and the call ends without a result. The next Model request waits for every sibling to terminate, and Chat persists every ordered Tool Result plus any deferred Tool-cycle Notes through one `append_many_async` transaction only after the executor returns the complete batch. Result-persisted callbacks and Continuation Tool-result records run only after that whole canonical batch settles. A forceful Run cancel stops the siblings still running and persists the Results of those that finished, in call order, through the same one transaction (`ToolRound.settle_cancelled`, `_agentic_progression.py::_persist_cancelled_tool_round`); stopped siblings get no Result. Request shaping treats only canonical Session history as surviving evidence and synthesizes each missing Result exactly once without persisting the repair. A Tool may register an `after_result_persisted` callback through its `ToolContext`; Chat invokes it only after that Tool Result commits in the Parent Session, and a callback failure is logged without changing the already-persisted result or failing the Run. Result payloads an Extension Tool attaches (`extensions.md`) are staged per call in `ToolDispatchContext` and merged into that call's `ToolResultFacts`, so they commit in the same batch transaction as their Tool Result; a handler that raises or returns an invalid result drops its staged payloads (the failure envelope replaces them), a call a Run cancel stopped persists none, and attaching after the call ended raises. A rejected canonical Tool Call is resolved first and bypasses live denials, Extension hooks, and the Tool handler while emitting the normal lifecycle and its non-retryable rejection envelope. Other calls continue through the live Tool-denial resolver, Runtime Tool registry, effective allowlist, Extension decision pipeline, optional Run-local restriction, and canonical pre-handler validation. Unknown Tools, invalid arguments, handler crashes, and invalid/non-serializable results become per-call failure envelopes so the Model can recover; one failed sibling never blocks valid siblings or aborts the Run. The Run-local failed-Tool circuit breaker compares Tool name, canonical arguments, stable error code, canonical schema fingerprint, and any rejection fingerprint in declared result order: a materially different failed call or any success resets the streak. After the eighth consecutive identical failed call, or when the Tool-iteration ceiling (`MAX_TOOL_ITERATIONS`, narrowed - never raised - by a Run's `max_tool_iterations`; rejection code `tool_iteration_limit`) rejects the next requested batch, Chat persists correlated non-retryable Results, adds a finalization reminder, and makes the next Model request with the same pinned Tool definitions and no tool choice, so the Provider prompt-cache prefix survives; context-usage measurement uses that same list. If the Model ignores that boundary, Chat persists a `tool_calls_disabled` Result without running the Tool and gives it one bounded recovery request; a second violation is also correlated and persisted, then completes gracefully instead of looping or failing the Run (`MAX_TOOL_FINALIZATION_VIOLATIONS`). The refusal texts are `_step_outcomes.py` constants that the learning-evaluation harness imports. No wire receives a tool choice of none: on Anthropic Messages a changed `tool_choice` invalidates the cached messages (only Tools and system stay cached), and the other wires' cache and acceptance behavior for it is not verified.

Auto-compaction runs only at safe completed Model boundaries. Summary+Tail may compact after a complete Tool cycle or final Assistant response; Continuation waits for a final Assistant response so it does not split work whose next action is still unknown. The Session write lock ends at the durable Assistant/Tool boundary before Compaction planning or Model I/O begins. Automatic checkpoint persistence is a later cursor-validated conditional append; notes that out-of-band writers append meanwhile are carried into the checkpoint, any other concurrent entry aborts the stale checkpoint, and a same-Run path then rebuilds its uncompacted request from current Session history before the next Model step. Compaction mechanics and policy live in `compaction.md`.

## User steering

Ordinary queued User inputs and a Parent Agent's `send` to its Sub-Agent advertise steering eligibility (steered Parent input persists with `PARENT_AGENT_STEERING_SYSTEM_REMINDER` instead of the user steering reminder); Channel/sender-bearing input, internal work, execution-owner bindings, and requests with special Tool policy (including a per-Run iteration limit) or hooks cannot be merged into another execution, because the merge would drop their sender, reply surface, hook, or Tool ceiling. The active Run's origin never limits steering: a system delivery, Cron, Calendar, Channel, or Sub-Agent Run takes the input like a User Run, under its own Model and execution policy (a restricted Run stays restricted; a Channel Run still relays its answer to the Channel). `_queued_input.py` retains the immutable queued executor and owns Chat's steering persistence/request rebuild helpers. `chat.queue_steer` names only the Queue item; a click that lands after the Run's last Model request, or during cancellation, starts the item as the next Run (`runs.md` -> Steer).

Before each Model request, under the Session write lock and outside Tool dispatch, Chat delivers selected Queue items in FIFO order. Each item becomes a normal User message with the current Run membership, original content/input origin, and Session image references. Chat persists `STEERING_SYSTEM_REMINDER` immediately before that message, after any input-origin note, in the same append transaction. The reminder identifies the input as part of the current task, directs the Agent to incorporate corrections and instructions, resume unfinished work after answering a question or status request, and follow an explicit cancellation or replacement. It uses the ordinary persisted-note renderer, so later history replay preserves its position and the visible User text stays unchanged. An item that instead starts a successor Run gets no steering reminder. The append and Queue acknowledgement finish together before honoring cancellation; failed appends retain the item. The existing `user_message_persisted` event carries its `queue_item_id` for live Queue retirement. Request rebuilding uses ordinary media/Skill handling, preserves live Tool media, current-Run native Reasoning, and Continuation context through the shared live rebuild path, and retains the active Model and execution policy. Steering does not cancel Provider generation or a Tool batch.

After a final Assistant response, a pending steer forces another iteration. If that input is removed before delivery, the persisted final answer remains the Run result and no further Model request is made. Input selected after the last pending-input check, or left undelivered by cancel/error, stays queued and starts the next Run. Tests: `test_chat_loop_steering.py`, `tests/core/runs/test_runs_queue.py`, and `tests/server/rpc/test_chat_methods_queue.py`.

## Agent-facing text

Each sentence of `STEERING_SYSTEM_REMINDER` (`_queued_input.py`) applies to the immediately following User message, not to later turns.

| Text | Reason |
|---|---|
| `The following user message was added to your current task.` | Identifies input delivered into an active Run; an ordinary User message alone does not reveal the steering event. |
| `Apply its corrections and additional instructions to that task.` | Keeps the existing objective in view while incorporating the user's steering, rather than treating every added message as a replacement task. |
| `If the message asks a question or requests a status update, answer briefly and then resume any unfinished work on the task.` | Prevents a side question from ending unfinished work; completed work does not require further execution. |
| `If the user clearly cancels or replaces the task, follow that change.` | Preserves the user's authority to stop or change direction instead of over-applying task continuity. |

Black-box evidence (2026-10-03): an isolated instance with production prompts and `read`/`apply_patch` ran four fresh CSV-report tasks each on `openrouter/openai/gpt-4.1-mini` and `openrouter/anthropic/claude-haiku-4.5`: two status questions, one output-path correction, and one explicit cancellation/replacement. All eight selected inputs were delivered into the original Run without Model fallback. Both Models answered the status questions and created correct reports, used the corrected output path, and stopped report creation for the replacement task. These cases verify the intended behavior on these Models and tasks; they do not establish universal compliance. The reminder adds an estimated 70 tokens including its generated wrapper per steered input, with no permanent System Prompt growth.

The interruption notices (`wire_shaping.py::_INTERRUPTION_NOTICES` and its fallbacks) and the missing-result message (`INTERRUPTED_TOOL_RESULT_MESSAGE`). Each notice states only why the previous turn stopped; the earlier work stays visible in the history, so the notice gives no instruction to resume, inspect, or repeat it.

| Text | Reason |
|---|---|
| `The user stopped your previous turn before it was complete.` | Without it the Agent cannot tell a user stop from an answer it never gave, and may treat the stop as an error to work around. |
| `Your previous turn stopped before it was complete because vBot shut down.` / `... vBot restarted.` | Separates a host stop from a user decision, so the Agent does not read it as the user rejecting the work. |
| `... because the connection to the Model provider failed.` / `... the Model provider stopped responding.` / `... the Model provider returned an error.` | Names a transient outside cause, so the Agent neither blames its own work nor tells the user it finished. |
| `... because of an internal error.` / `... because of an error.` | Fallbacks for an interrupted Run without a known cause and for a failed Run whose error the request does not carry; the Agent still learns the turn is unfinished. |
| `Your previous turn was cancelled before it was complete.` | Fallback for a cancel reason without its own notice (for example a Sub-Agent its Parent Agent stopped with `cancel`). |
| `The Tool call was interrupted before its result was recorded.` | The Agent otherwise assumes a missing Result means the call did not run. |
| `Whether it took effect is unknown; check before you repeat it.` | Prevents blind repetition of a call that may already have changed files or state. |

## Model and Connection resolution

Agent Model strings use `<provider>/<model-id>[::<connection-local-id>[:<account-id>]]`. `core/chat/model_resolution.py` parses the optional pin. An explicit pin is used verbatim; an unpinned Model selects the first usable Provider Connection permitted by the Model's `connections` allowlist. A non-empty allowlist with no usable matching Connection fails instead of routing through a forbidden Connection. Unknown Model ids are left for the Provider API to reject after Provider/Connection validation. Such a Model, or a malformed Model string, has no input modalities, so its media degrades to path notes; the lookup failure warns once per Model and failure kind per process and logs INFO when the lookup succeeds again (`test_model_resolution.py`).

If a qualifying failure exhausts same-Model recovery and the Agent has a resolvable `fallback_models` chain, Chat advances candidates in listed order while the shared recovery budget remains. An activated candidate serves the rest of the current Run. Its adapter closes on every exit after construction, including request-rebuild or Compaction failure before its first send. Qualifying errors are retryable Provider failures, exhausted provider/network/timeout interruptions (including chunk/progress stalls and missing-answer recovery), and clearly model-scoped fatals (404 status or unknown-model wording). Rate limits before answer text skip remaining same-Model retries when a chain is configured. Each switch logs one WARNING, emits `model_fallback_activated`, persists a System Reminder note with its display-only `model_fallback` record (the History's switch notice, `chat.md`), rebuilds request state with the fallback route (including `analyze_image` visibility), and leaves Agent configuration unchanged so the next Run starts from the primary Model. Resolution dedupes against the primary and earlier candidates; unresolvable, unusable, or unconstructable candidates are skipped with a warning. When no candidate succeeds, the last actual failure determines failed versus interrupted termination. Auth, billing, permission, content-policy, and context-overflow errors never advance the chain.

A Session Model override leaves `fallback_models` unchanged, so the Agent's existing fallback policy remains active. An overridden `thinking_effort` belongs to the resolved Agent view and therefore reaches both primary and fallback Model steps through the same Provider-neutral Reasoning policy.

## Interruption

Canonical Session history is the only record of an interrupted Run. What the Run persisted before it stopped stays in its original form: User input, complete Assistant turns, Tool Results, and an `interrupted` Assistant partial when readable output existed. Nothing replays that work into a later request a second time, and an interrupted partial's readable and opaque Reasoning stays durable evidence that no later request sends (native `reasoning` and `reasoning_meta` are stripped even under same-scope `full_history`). The normalized cause is stored on the partial as `interruption_cause` beside `interrupted: true`, so internal result consumers such as Sub-Agents can tell a partial terminal result apart; both annotations stay out of Provider-visible fields. There is no Continue or Discard action.

**Notice.** The Run manager stores why a cancelled or interrupted Run stopped as the `run_summary`'s `completion_reason` (`runs.md`): the cancel reason (`user`, `shutdown`, or another caller reason) or the `RunInterruptedError` cause (`network`, `timeout`, `provider`, `internal`, or `process_restart` from restart recovery). `wire_shaping.py` derives the Model-facing notice from that summary at request time: it joins the pending notes before the next message the request sends and renders as one System Reminder (Agent-facing text above). Because the notice is a pure function of persisted history, every later request renders it byte-identically at the same position and the Provider prompt cache holds; nothing is persisted for it. A Run gets a notice only when it stopped unfinished: its last Assistant or Tool entry is not a complete, non-interrupted Assistant answer without Tool Calls. A Run cancelled after its final answer (for example during post-answer Compaction) gets none. A `failed` Run gets the generic failure notice only when its error is not already in the request; a Model-visible `error` entry (`error_kind_llm_visible`) is its own reminder. A Compaction checkpoint's projection replaces compacted history, so only summaries in the effective history render.

**Missing Tool Results.** A Tool Call without a persisted Result (cancel, crash, or interruption during dispatch) gets a request-only `result_unavailable` failure envelope (`chat/request-building.md`); its message says the effect is unknown and to check before repeating the call.

**Stream draft.** A Model step's streamed output exists only in memory until its Assistant entry persists. `core/chat/_stream_draft.py::StreamDraft` copies it into the Run's Stream draft (`sessions.md`) at most every `STREAM_DRAFT_FLUSH_INTERVAL_SECONDS` (2 seconds), so a process crash loses at most that window. One write runs at a time and is never cancelled; a failed write keeps its text, in order, for the next. Persisting the Model step's Assistant entry deletes the draft in the same transaction, and `settle()` runs first: it waits for a running write and drops unwritten deltas, so no draft write can commit after that entry. A stream attempt that ends with an exception (restart, fallback, interruption without a partial, failure) discards its draft. Run completion deletes any remaining draft, and the executor settles the draft before completion. Restart recovery (`recover_interrupted_runs`) turns a left-over draft into the Run's `interrupted` Assistant entry with cause `process_restart`, then completes the Run `interrupted`. Every Run kind drafts; the draft is never read while the process lives.

## Streaming recovery

One `RecoveryBudget` in the Run context bounds each unfinished Model step: at most nine attempts per exact Model route (including the initial request), eighteen across configured fallback routes, and thirty minutes from the first recoverable failure. Initial healthy generation is not subject to that recovery deadline. Ordinary establishment retries, stream restarts, non-streaming fallback requests, partial-answer continuations, empty answers, and truncated Tool reissues all spend that same budget. Partial text, Reasoning, heartbeats, and route switches never reset it. A complete Model response (final answer or Tool-call turn, never an interrupted partial or truncated turn) ends the step and resets it, so a following Tool, steering, or finalization request inherits neither attempts nor backoff; the separate failed-Tool breaker and Tool-iteration ceiling still apply. Backoff grows per route (1, 2, 4, 8, 16, 32, 64, then 128 seconds before jitter); a newly selected fallback starts its own short backoff without resetting the shared attempt/time budget. It uses the shared exponential/jitter calculation and capped `Retry-After` hints, including in-band stream errors; waits are cancellable, and a retry whose delay cannot fit the remaining deadline does not start.

`core/chat/streaming.py::decide_stream_recovery` is the single provider-agnostic decision owner. It sees normalized errors plus whether a finish arrived, partial answer content exists, a Tool Call already started, and a same-Model restart remains. It returns `ACCEPT_COMPLETE`, `RESTART`, `FALLBACK`, `PRESERVE_PARTIAL`, `INTERRUPT`, or `FAIL`; `request_runner.py::WireRequestRunner._consume_stream_attempt` owns the side effects.

- After a normalized finish delta, a later transport/provider failure retains that logical outcome and accumulated Usage; empty-answer and output-integrity checks still apply.
- Before answer text, unsupported streaming switches to non-streaming; retryable transient failures restart the identical request while the shared budget remains; other failures propagate. Readable Reasoning and an in-flight Tool Call preview do not block a restart because neither has produced answer text nor executed a Tool. Before replay, Chat deletes the attempt's Stream draft, emits `stream_attempt_restarted` so consumers can discard previews, and discards incomplete Tool Calls. Exhausted network/timeout recovery becomes `RunInterruptedError`; retryable Provider errors propagate directly. Both can reach configured Model fallback before terminating. A Provider adapter may select a safer transport for the retry; the replay decision remains provider-neutral.
- After a Tool Call started, the stream is never replayed or switched to a completed response (that would run the Call twice). A transient break keeps the output so far with exactly the started Calls as a complete, not interrupted, Tool-call turn (`request_runner.py::_finalize_after_started_tools`); a Call still being written is dropped. After the started Calls' Results, Chat adds `TOOL_CALLS_STREAM_RECOVERY_NOTE` and continues with the next request, spending the shared budget; a fatal break, and any other exception once a Call started (`request_runner.py::_consume_stream_response`), persists the same turn and Results, then fails the step.
- After answer text, Chat preserves an `interrupted` Assistant boundary and drops in-flight unexecuted Tool Calls. A transient failure appends a provider-neutral recovery note and continues from the durable partial using the shared budget; only a later complete Tool Call can dispatch. Fatal failures propagate after persistence without an automatic continuation. Exhausted partial recovery may advance the configured Model chain; without a successful candidate it ends interrupted rather than falsely completed. The interrupted Run result combines only the visible fragments of the unfinished step, across its continuations and fallback routes; a complete Tool-call turn or answer ends that step, so earlier fragments never reappear in a later interrupted result. Recovery itself never re-executes completed Tool Calls or consumes the Tool-loop iteration budget.
- Remote Providers use two independent stream guards. A 180-second transport window resets on every normalized Model delta or Provider heartbeat; a 900-second Model-progress window resets only on normalized Reasoning, content, Tool-call, finish, or Usage. OpenAI-compatible SSE comments become transport-only heartbeats because verified gateways can buffer a complete large Tool Call while sending comments, then release all arguments as one delta; the UI reports that connected wait without presenting it as Model output. Incomplete SSE events and arbitrary raw bytes still count as neither. Loopback, localhost/local-domain, RFC1918 private, and link-local base URLs are exempt from both windows so long local prefill does not look like a dead stream: `ProviderRuntime.get_adapter` marks such an Adapter `local_endpoint` (`core/providers/adapter.py::is_local_provider_base_url`), and `streaming.py::stream_stall_timeout(adapter)` is the one policy Chat and `stream_model_response` (Session titles, image analysis, Extension sampling, the Live Tools probe) apply. Compaction deliberately keeps both windows on local routes (`compaction.md`).

## Cancellation

Completed visible Assistant output is protected after normalized `stop`, including while the stream iterator is closing, through asynchronous preparation and the durable append when Stop arrives; cancellation still prevents subsequent Model/Tool work. Tool-round counts, repeated-failure tracking, and Tool finalization state belong to the Run context and survive Model fallback.

Cancel is best effort. Tool dispatch marks each call active before publishing `tool_call_started`, so an immediate per-call cancel is retained even when Tool-owned cleanup registers a moment later; that callback then fires immediately. `Run.request_cancel` suppresses late non-terminal output, prevents new Tool progression, invokes every still-active per-Tool cancel callback in registration order, calls `TerminalManager.cancel_run` (stopping every shell command the Run started, handed off or not, and rejecting new ones for it), and forcefully cancels the executor task after cleanup signals are scheduled. A Run completion observer releases that cancellation marker (`release_run`) once the Run has settled. Completed Tool Calls have already cleared their callbacks and are not cancelled twice; a callback registered after the Run signal fires immediately. Already persisted history is never rolled back, while any missing member of an interrupted Tool batch remains request-only repair work for the next Provider request.

Before a trustworthy final `stop`, when readable reasoning or answer content already exists at cancellation, Chat uses the same partial finalization path as other interruptions so every readable block the user saw remains persisted in an `interrupted` Assistant message; a reasoning-only message has no answer content, and the Run still terminates `cancelled`. With neither readable reasoning nor answer content no Assistant message is added and the `run_summary` remains the timeline anchor. When Tool Calls already started, the cancelled turn keeps them (interrupted, with its readable output); the calls that finished keep their Results, and the stopped ones are request-only missing-Result repair. Stop after a complete final answer - while the stream is closing, while it is being persisted or during the optional post-answer Summary+Tail Compaction - still ends the Run `cancelled`, but that answer remains complete in history and the next Run gets no interruption notice. During Tool dispatch, cooperatively terminated complete batches preserve their ordered Results; forceful cancellation preserves the Results of the calls that finished and leaves the stopped ones to request-only missing-Result repair. Once every Result exists, storing their media, the batch append and the `after_result_persisted` callbacks finish before Stop is honored (`_finish_visible_boundary`), and so does the Usage write that closes a stream whose Tool Calls started, so its turn still reaches the Session.
