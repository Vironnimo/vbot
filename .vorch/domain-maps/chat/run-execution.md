# Chat Run Execution

Task-gated reference for Chat admission, provider/Tool progression, streaming recovery, interruption, Continuation, cancellation, and Run-local Model fallback. Read this when changing those behaviors; Run storage, queue state, and lifecycle types themselves remain owned by `runs.md`.

## Entry points and admission

`ChatLoop` exposes `send`, `start_run`, `queue_run`, `build_queue_update`, and `compact_session`. `run_executor(content, agent_overrides=None)` is the public seam handed to `ChatRunManager`; its optional frozen `AgentRunOverrides` captures only a Run-local primary Model and thinking effort for Sub-Agent execution. `child_loop(nesting_depth=...)` shares the explicit `ChatLoopDependencies`, attachment resolution, Compaction, reflection, and title notification but carries no ambient override state. The server-facing paths require an existing Session; the legacy direct `send()` path may still create one when no `session_id` is supplied.

`start_run` persists visible content as a user message and internal content as a note. `sender`, `input_origin`, `reply_surface`, `project_id`, dispatch-only `tool_restriction`, optional live `tool_denial_resolver`, `input_persisted_hook`, `contributes_to_agent_activity`, and the narrow `resume_process_restart` flag ride the admitted executor. The hook runs only after that initiating message is fsynced, including for queued Runs, and its failure is ancillary: Chat logs it without failing the admitted Run. `queue_run` validates the same prerequisites and captures both Tool-policy inputs with the other immutable execution data so a queued item preserves its admission ceiling while live denials can still observe current external state when it starts or dispatches. The activity policy defaults `True`; when false, Chat still persists the complete transcript and `run_summary` but deliberately does not call the Sessions completion-activity recorder, so the Run cannot create durable unread state. `build_queue_update` returns replacement data without mutating Queue state.

Session/address ownership and execution context are separate. `run.project_id` is the public Session/address anchor and queue key; Identity Agent Runs keep it `None`. At admission Chat snapshots `run.working_project_id` from the addressed Config Agent's Project or an Identity Agent's explicit root. That snapshot supplies Tool cwd, Project Files/Skills, prompt context, file mentions, and Compaction rebuilds. If the Project/repository disappears before queued work starts, execution fails before new user content is persisted; Workspace is not a fallback.

## Agentic progression and events

At executor start the loop resolves one Run-local execution context: Agent, Session, working Project cwd/prompt inputs, Skill scope and pinned catalog, Continuation tracker/reminder, immutable Tool restriction, live Tool-denial resolver, and a primary Model target containing the exact Provider Connection, adapter policies, Model input modalities, wire media types, and stream timeout. When the admitted request carries `AgentRunOverrides`, Chat asks the common `AgentResolver` for an immutable overlaid runtime view at this boundary; omitted overrides take the exact ordinary resolution path. System Prompt, canonical history, route-filtered Provider Tool definitions, and Chat-derived Session Tool grants then form the context's mutable request state before the first Provider call: `skill_list` accompanies an available `skill` from the Session's first request, while `history` appears only after persisted Compaction. Dispatch-only restrictions and denials are deliberately absent from request building, preserving byte-identical System Prompt content and Provider Tool definitions; no admitted request can add a Run-local Tool grant. Provider adapters yield normalized data only. A recognizable malformed Tool attempt, including malformed JSON arguments or a malformed `tool_calls` container, becomes an addressable canonical rejected `ToolCall` rather than a response-parsing exception. Chat persists finalized Assistant/Tool/Error messages and emits provider-agnostic `RunEvent`s; opaque `reasoning_meta` never appears in visible events.

`Run.iteration_count` is the single canonical Agentic Loop count. Chat derives the next debug ordinal from it and increments it exactly once after one Model request returns a response into the loop, before persistence or Tool dispatch: a response containing only Reasoning still counts once, a response requesting any number of sibling Tool Calls still counts once, and an unanswered failed Provider attempt counts zero. Stream replays before a completed response retain the same ordinal. Live `model_step_usage`, terminal Run events, the terminal Run Summary, active-Run RPC responses, and Reflection are projections or consumers of this Run-owned value; none may derive it from Assistant messages, rendered outputs, Tool Calls, or Tool Results.

Each completed Model step carries the Adapter's canonical terminal outcome. Only `tool_calls` authorizes Tool dispatch. A turn ending `output_truncated` with Tool Calls persists the partial Assistant and ordered `tool_call_truncated` Results, invokes neither handlers nor Extensions, and continues so the Model can reissue a complete call. `content_filtered`, `error`, `unknown`, or an outcome inconsistent with the presence of Tool Calls persists correlated `tool_call_rejected` Results without dispatch and then fails the step. This terminal safety gate precedes every Tool execution path.

Agentic progression and automatic Compaction receive the Run context plus the current Model target, not the Runtime service surface or a parallel list of Run fields. Tool dispatch receives a Tool-specific projection of the same context. Run-local fallback builds a replacement Model target while retaining the Session, Project, Skill, Tool-policy, and Continuation context, then rebuilds mutable request state so media handling and route-gated Tool visibility match the fallback route.

Streaming deltas (`assistant_output_delta`, `reasoning_delta`, `tool_call_delta`, `tool_call_stdout`, `tool_call_stderr`) and `provider_heartbeat` are transient SSE events and never persisted. A Provider heartbeat reports an SSE transport keepalive plus seconds since the last normalized Model delta; it is visible liveness only, never Assistant content, Reasoning, Tool progress, or a completed Tool Call. Stable events include Assistant output, Tool start/result, the `compaction_started` → `compaction_completed` / `compaction_aborted` lifecycle, Model fallback, error persistence, per-model-step Usage, and terminal Run lifecycle from the Runs domain. Tool failures use the stable Tool Result envelope with `ok=false`; there is no separate public `tool_call_failed` event.

Immediately before each Model request, Chat holds the Session write lock, lets Automation persist any Bash/Sub-Agent completion notices ready for that exact active Run, and then drains pending notes into the request as System Reminders. This is a request-boundary join, not a new Provider request: a notice that becomes ready after that point waits for the next iteration, and one with no later iteration falls back to Automation's internal follow-up Run after the boundary Run ends. The seam runs only outside Tool dispatch, so completion notes cannot split an Assistant Tool-call batch from its ordered Tool Results; a manual terminal Process result may still cancel its pending notice before the next boundary.

Sibling Tool Calls from one Assistant turn execute concurrently by default within the shared limits, including multiple calls to the same Tool. A Tool registered with `parallel_safe=False` is an explicit ordering barrier. Active Extension `tool_call` and `tool_result` callbacks run one at a time through a batch-local lock, while parallel-safe Tool handlers may still overlap. The next Model request waits for every sibling to terminate, and Chat persists Tool Results in the Assistant's original order only after the executor returns the complete batch. Therefore a forceful Run cancel can leave even a handler-computed sibling without a durable Result when another sibling was still active; request shaping treats only JSONL as surviving evidence and synthesizes each missing Result exactly once without persisting the repair. A Tool may register an `after_result_persisted` callback through its `ToolContext`; Chat invokes it only after that Tool Result is fsynced in the Parent Session, and a callback failure is logged without changing the already-persisted result or failing the Run. A rejected canonical Tool Call is resolved first and bypasses live denials, Extension hooks, and the Tool handler while emitting the normal lifecycle and its non-retryable rejection envelope. Other calls continue through the live Tool-denial resolver, runtime Tool registry, effective allowlist, Extension decision pipeline, optional Run-local restriction, and canonical pre-handler validation. Unknown Tools, invalid arguments, handler crashes, and invalid/non-serializable results become per-call failure envelopes so the Model can recover; one failed sibling never blocks valid siblings or aborts the Run. The Run-local failed-Tool circuit breaker compares Tool name, canonical arguments, stable error code, canonical schema fingerprint, and any rejection fingerprint in declared result order: a materially different failed call or any success resets the streak. After the eighth consecutive identical failed call, or when the Tool-iteration ceiling rejects the next requested batch, Chat persists correlated non-retryable Results, adds a finalization reminder, and makes the next Model request with no Tool definitions. If the Model ignores that boundary, Chat persists a `tool_calls_disabled` Result and gives it one bounded recovery request with Tools still disabled; a second violation is also correlated and persisted, then completes gracefully instead of looping or failing the Run.

Auto-compaction runs only at safe completed Model boundaries. Summary+Tail may compact after a complete Tool cycle or final Assistant response; Continuation waits for a final Assistant response so it does not split work whose next action is still unknown. Compaction mechanics and policy live in `compaction.md`.

## Model and Connection resolution

Agent Model strings use `<provider>/<model-id>[::<connection-local-id>[:<account-id>]]`. `core/chat/model_resolution.py` parses the optional pin. An explicit pin is used verbatim; an unpinned Model selects the first usable Provider Connection permitted by the Model's `connections` allowlist. A non-empty allowlist with no usable matching Connection fails instead of routing through a forbidden Connection. Unknown Model ids are left for the Provider API to reject after Provider/Connection validation.

If a retryable `ProviderError` escapes adapter retries and the Agent has a resolvable `fallback_model`, Chat may switch for the rest of the current Run. It emits `model_fallback_activated`, persists a System Reminder note, rebuilds request state with the fallback route (including `analyze_image` visibility), and leaves Agent configuration unchanged so the next Run starts from the primary Model. Fallback resolution uses the same pin and allowlist rules; no usable allowed Connection means the fallback is skipped. `NetworkError` is not a Model-fallback trigger.

A Run-local primary Model override leaves `fallback_model` unchanged, so the target Agent's existing fallback policy remains active. The overlaid `thinking_effort` belongs to the Run-local Agent view and therefore reaches both primary and fallback Model steps through the same Provider-neutral Reasoning policy.

## Continuation checkpoint

Every admitted visible Run owns a provider-neutral append-only Continuation journal in `core/chat/continuation.py`. It records original visible requests, readable reasoning/partial output, stable Assistant boundaries, Tool references/status, Compaction boundaries, and the interruption cause without copying opaque reasoning metadata or full Tool Results. Dirty streaming state flushes at most every two seconds; completed Model/Tool boundaries and interruption flush immediately. Canonical Session history remains authoritative for actual Tool Calls and Results.

An interrupted checkpoint attaches exactly once at executor start to the next visible Run, immediately before that Run's newly persisted user message. Its wrapper only states that the previous Run was interrupted and that the checkpoint records what happened before the interruption; it does not direct the Model to resume, continue, inspect, or repeat anything. A complete non-interrupted Assistant result resolves it; a further interruption extends the chain. Internal Runs neither consume nor resolve visible Continuation state by default. The sole exception is an explicitly admitted Bootstrap fixed-Session Run with `resume_process_restart=True`: Chat recovers and tracks the checkpoint only when its normalized cause is `process_restart`, leaving user/provider/network/timeout/internal interruptions for the next visible Run. There is no separate Continue or Discard action.

The checkpoint remains internal to Chat. Its normalized cause is also stored on a preserved partial as `interruption_cause` beside `interrupted: true`, so internal result consumers such as Sub-Agents can distinguish a partial terminal result; both annotations are removed from ordinary Provider-visible history fields. The canonical partial retains readable and opaque Reasoning as durable evidence, but every later request strips its native `reasoning` and `reasoning_meta` even under same-scope `full_history`; recovery returns readable work only as provider-neutral reminder text. User Cancel and any stream interruption that exhausts its bounded same-Run recovery leave the checkpoint for the next eligible visible Run; process restart and non-streaming failures keep their existing checkpoint rules. Missing or unknown effects from `write`, `edit`, or `bash` are labeled as uncertain filesystem or process effects without an accompanying instruction.

## Streaming recovery

`core/chat/streaming.py::decide_stream_recovery` is the single provider-agnostic decision owner. It sees normalized errors plus whether a finish arrived, partial answer content exists, and a same-Model restart remains. It returns `ACCEPT_COMPLETE`, `RESTART`, `FALLBACK`, `PRESERVE_PARTIAL`, `INTERRUPT`, or `FAIL`; `ChatLoop._consume_stream_attempt` owns the side effects.

- After a normalized finish delta, a later transport/provider failure accepts the completed response; later Usage deltas already accumulated remain valid.
- Before answer text, unsupported streaming falls back once to non-streaming; retryable transient failures restart the identical request while the two-restart budget remains; other failures propagate. Readable Reasoning and an in-flight Tool Call preview do not block a restart because neither has produced user-visible answer text nor executed a Tool. Before replay, Chat appends `stream_attempt_discarded`, clears that attempt's pending readable deltas from the active Continuation Checkpoint, emits the transient `stream_attempt_restarted` Run event so consumers can discard the failed attempt's previews, and discards every incomplete Tool Call. If the restart budget is exhausted, readable Reasoning becomes an interrupted partial result; no-output network or timeout exhaustion interrupts without fabricating Assistant text, while a retryable Provider error propagates to the Run-local Model fallback policy and fails normally when no usable fallback exists. A Provider adapter may select a safer transport for the retry, while the replay decision remains provider-neutral.
- After answer text, Chat never replays the request because that would duplicate output. It persists an `interrupted` Assistant boundary, drops any in-flight unexecuted Tool Call, appends an internal provider-neutral recovery note, and asks the Model to continue inside the same Run. The continuation request includes the preserved partial answer and explicitly requires any intended Tool Call to be regenerated completely; only a later complete Tool Call can dispatch. Same-Run continuations have their own budget of two and do not consume the Tool-loop iteration budget; a completed Tool boundary resets that continuation budget. Exhaustion raises `RunInterruptedError`, persists a terminal `run_summary` with `status: "interrupted"`, and emits `run_interrupted` rather than falsely completing the Run.
- Remote Providers use two independent stream guards. A 180-second transport window resets on every normalized Model delta or Provider heartbeat; a 900-second Model-progress window resets only on normalized Reasoning, content, Tool-call, finish, or Usage. OpenAI-compatible SSE comments become transport-only heartbeats because verified gateways can buffer a complete large Tool Call while sending comments, then release all arguments as one delta; the UI reports that connected wait without presenting it as Model output. Incomplete SSE events and arbitrary raw bytes still count as neither. Loopback, localhost/local-domain, RFC1918 private, and link-local base URLs are exempt from both windows so long local prefill does not look like a dead stream.

## Cancellation

Cancel is best effort. `Run.request_cancel` suppresses late non-terminal output, prevents new Tool progression, invokes every still-active per-Tool cancel callback in registration order, calls the runtime ProcessManager cancellation scope, and forcefully cancels the executor task after cleanup signals are scheduled. Completed Tool Calls have already cleared their callbacks and are not cancelled twice; a callback registered after the Run signal fires immediately. Already persisted history is never rolled back, while any missing member of an interrupted Tool batch remains request-only repair work for the next Provider request.

When readable reasoning or answer content already exists at cancellation, Chat uses the same partial finalization path as other interruptions so every readable block the user saw remains persisted in an `interrupted` Assistant message; a reasoning-only message has no answer content, and the Run still terminates `cancelled`. With neither readable reasoning nor answer content no Assistant message is added; the private checkpoint separately retains recovery state and the `run_summary` remains the timeline anchor. During Tool dispatch, cooperatively terminated complete batches preserve their ordered Results, while forceful cancellation can interrupt delivery of the whole batch and relies on request-only missing-Result repair.
