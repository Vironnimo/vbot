# Chat Request Building

Task-gated reference for turning canonical Session history into one provider-ready request. Read this when changing message rendering, notes, Skills, Content Blocks, Compaction-tail reconstruction, reasoning replay, or Tool-cycle repair; it is not required for unrelated Chat work.

## Pipeline and ownership

Prompt assembly and Tool-definition profiling use the Prompt pool; canonical Compaction projection, note embedding, Skill-context restoration, Tool-contract compilation, attachment/media scans, and token estimates use Chat's bounded transform pool. These synchronous transformations finish before the request crosses the async Provider boundary and never consume Event-Loop time proportional to Session size.

`core/chat/messages.py` owns canonical message validation and effective-history projection; `core/chat/wire_shaping.py` turns that history into one provider-ready request (assembly, notes, replay policy shaping, tool-cycle repair) and ingests normalized responses back into canonical messages; `core/chat/chat.py::_build_request_state` coordinates the build; `core/chat/block_resolver.py` resolves attachment-backed content; `core/chat/file_mentions.py` snapshots and renders `@` mentions; `core/chat/tool_dispatch.py` owns Tool definitions and Skill activation. Provider adapters receive normalized request messages and definitions only. They own wire translation, while `core/sessions/` remains the persistence owner and `core/compaction/` owns checkpoint policy and Projection creation.

Each provider request is assembled from one loaded canonical Session snapshot. Chat first derives Session-scoped Tool grants, obtains the allowed/ready configuration-profiled Tool definitions, applies effective Model-route gates, compiles the exact surviving Provider schemas into request-state Tool contracts, passes the surviving Tool names into System Prompt assembly, and only then shapes message history. The same contract mapping crosses `ToolDispatchContext`/`ToolExecutionConfig` into each `ToolContext`, so dispatch and lifecycle fingerprints use the exact schema shown in that Provider cycle after every profile, Sub-Agent target, Bash nesting-depth, and route projection; handlers retain their canonical semantic checks. This mapping is internal Run state and never changes Provider bytes. The current route gate keeps `analyze_image` only when the target Model/Adapter intersection cannot carry images and the configured `image_understanding` binding is live-usable. The System Prompt is assembled whole by `SystemPromptManager`; it is never appended to Session history, and an empty/whitespace prompt is omitted from the provider request.

When a Compaction checkpoint exists, its canonical Projection replaces compacted history. If that Projection omitted the newest complete, unconsumed Assistant Tool-call batch, `_overlay_pending_tool_batch` adds the canonical batch until a later Assistant turn consumes it. Checkpoints themselves are never sent directly. Auto-compaction rebuilds and the live path both flow through the same note embedding and dangling-Tool repair.

## Canonical roles and request visibility

- `system`, `user`, `assistant`, and `tool` map to provider-visible conversation roles after shaping. Only `user` may persist `list[ContentBlock]`; other content is string-or-null according to the `ChatMessage` validator. Assistant `output_files` is canonical presentation metadata and is removed from both ordinary history requests and current-turn Tool continuations.
- `note` is a kernel-internal persistence role. Public history filters it. Ordinary notes become synthetic user messages containing `<system-reminder>` blocks; consecutive notes are grouped, and notes created during a Tool cycle are delayed until all sibling Tool Results have been persisted so they never split the cycle.
- `[skill-context] ` notes are the exception to ordinary note rendering: they become chronological standalone `<skill_content>` user messages. A Skill loaded through the `skill` Tool has no such note because its structured Tool Result already carries the raw instructions and optional resource/environment metadata; Sessions reconstructs the equivalent internal wrapped context only when Compaction replay needs it.
- `[channel-message] ` notes are coalesced into a separate untrusted-background user message, not a System Reminder. Stored records are JSON-quoted and escape control characters plus angle brackets so channel participants cannot break or impersonate the wrapper.
- `[reply-surface] ` notes record WebUI/Desktop or Channel identity in append-only Session chronology. The WebUI/Desktop reminder is the single Model instruction for output files: `To show the user an image or provide a file download, include file:<filesystem-path> in your reply; vBot renders it automatically.` A Channel identity includes platform, configured Channel id, and `direct`/`group` conversation kind; its reminder still requires `channel_send` for files because external platform delivery is an outbound action. At executor start Chat appends one only for the first surface, a surface change, or the first interactive Run after a newer checkpoint; the tag is stripped and the model sees a turn-bounded System Reminder. Runs without a supplied surface do not change this state.
- `run_summary` and `agent_takeover` remain visible history annotations but never enter provider requests. `error` enters later requests only when `error_kind_llm_visible` allows it. `compaction_checkpoint` contributes through its Projection, not as a role.
- User `sender` attribution is rendered only while building the provider request as `[display_name|platform_user_id|role]`, where `role` is the persisted immutable `admin`/`member` snapshot. All attribution parts are sanitized before insertion. `input_origin="speech_transcription"` appends a hidden System Reminder immediately before the unchanged visible user message.

## Reasoning replay

The system default `ReasoningReplayPolicy` is `full_history`; an optional Provider override and then an optional Model override can narrow or replace it (`providers/request-policy.md` owns the hierarchy). The effective policy governs native `reasoning`/`reasoning_meta` replay; Chat owns history shaping and never interprets `reasoning_meta`. `none` strips native readable and opaque reasoning everywhere; `current_run` preserves it only across Tool continuation inside the active Run; `full_history` replays persisted native reasoning when the Assistant's internal `reasoning_scope` exactly matches the current resolved Provider/Model/Connection/Account scope. Across a mismatched route, Chat always strips both native fields and may project only non-empty readable `reasoning` from a completed reasoning-only or Tool-associated Assistant turn as an escaped, request-only provider-neutral System Reminder after its Tool batch. It never projects `reasoning_meta`, scope identity, empty/meta-only state, interrupted work, or ordinary answer-turn reasoning; this avoids both opaque-state leakage and duplicate answer context. An `interrupted` Assistant turn is a hard native-reasoning boundary regardless of policy or matching scope: canonical persistence retains its readable and opaque fields, but request shaping removes both `reasoning` and `reasoning_meta`; the provider-neutral Continuation reminder is the only replay channel for its readable work. `reasoning_scope` is persisted only on reasoning-bearing Assistant messages and is always removed before the provider request.

The current Assistant turn is appended through `_assistant_continuation_dict`, which strips `usage` and `reasoning_scope` but preserves policy-permitted reasoning. Mid-Run rebuild after textual Compaction restores active-Run reasoning by message id so an in-flight Tool cycle remains valid; the persisted checkpoint Projection itself contains no `reasoning`, `reasoning_meta`, or `reasoning_scope`, so later Runs start a new reasoning context. Assistant `phase` remains because it is semantic history required by Responses Models, not opaque provider state.

When run-local Model fallback begins, Chat rebuilds request state with the fallback target's replay policy, exact reasoning scope, input modalities, wire media support, and route-gated Tool definitions, then strips prior Assistant native reasoning/reasoning metadata before the first fallback request regardless of the primary policy. Completed reasoning-only or Tool-associated readable work follows the same bounded provider-neutral projection rule and is placed after the associated Tool Results; opaque primary state never reaches the fallback. Any reasoning produced by the fallback is persisted with the fallback scope even though the Agent's configured primary Model remains unchanged, so a later primary Run cannot inherit its native state.

## Skills and prompt-cache stability

Pure-text `/skill-name` at the start and `$skill-name` anywhere are deterministic Skill activation hints; `$` never routes to a built-in command. The original user message stays unchanged. Only allowed, loadable, currently available Skills activate. An identical name+content activation deduplicates within the current Compaction epoch, while committing a changed package permits the same Skill name to activate again and keeps latest content. A committed checkpoint removes full trigger carriers and compacts loading `skill` Tool Results from its Projection, then adds one names-only reminder for activations since the preceding checkpoint; the instructions and Skill environment grants are inactive until the Model explicitly reloads a still-relevant Skill. Aborted Compaction changes nothing, and a later checkpoint never carries the prior names reminder forward.

`_pinned_skill_catalog` snapshots the rendered Skill catalog text in Session metadata on the first build of a Session or prompt epoch. Later requests reuse that exact text for prefix stability until successful Compaction; the post-checkpoint refresh forces a complete Skill rescan, renders a replacement catalog, and synchronizes the Session's `seen_skills` baseline, so additions/removals/metadata or requirement changes appear without redundant announcements. A newly available+allowed Skill between Compactions does not rewrite the catalog; `_announce_newly_available_skills` adds a one-time System Reminder note instead. The admitted Working Project supplies Project Skills while an Identity Agent retains its private Skill layer; Config Agents remain under Project ceilings. Skill activation carriers remain canonical conversation Context and are not part of this System Prompt refresh.

The same epoch-pinning covers every other file-backed System Prompt input: the rendered SOUL block (`pinned_soul_context`) and the rendered pinned-memory files (`pinned_memory_files`) for Identity Agents, and the Working Project frame for Rooted Identity Agents and Project Config Agents alike (`pinned_working_project_context`). On-disk changes to `SOUL.md`, `MEMORY.md`/`USER.md`, or Project auto-load files therefore cannot alter the System Prompt prefix mid-epoch; they become visible only when a successful Compaction starts the next prompt epoch and re-renders all snapshots (an aborted/failed Compaction changes nothing). Read-before-write stamping happens at snapshot/refresh time only, never on reuse.

## Rooted and Config-Agent Working Project Context

`core:working_project` renders the file-backed `working_project.md` template from the admitted Project's id, display name, absolute Project Workspace, and readable auto-load files. Both a Rooted Identity Agent (via its selected Project) and a Project Config Agent (via its addressed Project) receive that frame as the prompt-epoch snapshot `pinned_working_project_context`: rendered before the first provider request of an epoch, stored in Session metadata, and supplied verbatim until successful Compaction rebuilds it from the current Project, auto-load list, and readable file contents; an explicit `project` Tool call still cannot replace the automatic frame. An Unrooted Identity Agent has no Working Project block and no pin. This pins only the automatic Working Project block; the explicit `project` Tool retains its ordinary persisted Tool result, and every non-file System Prompt input keeps its existing lifecycle. Prompt preview renders a prospective Rooted Identity frame without persisting it and a live Project Config frame from the addressed Project.

## Content Blocks, mentions, and media

`core/chat/content_blocks.py` owns `TextBlock`, `MediaBlock`, `FileBlock`, and `FileMentionBlock` plus JSON round-trip. On admission, Chat assigns every incoming image a positive `image_reference` continuing from the Session's persisted images; this durable reference renders as `Image 1`, never as a made-up filename or a storage path. `core/chat/file_mentions.py` lists cwd files for autocomplete and expands verified mentioned paths into immutable snapshots before Run admission. A `FileMentionBlock` records `path`, `status`, `text`, and `size_bytes`; request rendering always identifies it as a user-supplied file snapshot. Auto-injected Project files and expanded mentions are stamped into `runtime.file_read_state` so later write/edit Tools satisfy read-before-write without duplicating a read.

`ContentBlockResolver` performs provider-agnostic last-mile media routing by intersecting the Model's input modalities with `ProviderAdapter.wire_media_support(model_id)`. A current-turn supported image/audio/PDF becomes a native block followed by a path note. Unsupported, historical, or otherwise non-native media degrades to an explanatory path note; audio may first use Speech-to-Text. Text files carry the bounded rendering used by the `read` Tool. Only stored-blob I/O failure aborts the Run; capability mismatch degrades.

Per-modality degrade policy:

- **Image** - native base64 on the current turn when the model has `"image"` and the image type is in the wire set. A current-turn image to a non-vision model degrades to an `[Image: ... - this model has no vision capability ... - Path: ...]` note instead of aborting; a vision model whose wire cannot carry the type, or any earlier-turn image, degrades to an `[Image from an earlier turn: ...]` / `[Image: ...]` path note; a missing record degrades to a "file no longer available" note. The native image rides with an `[Image: ...]` path note as well, so the agent always holds the file path, not only the pixels.
- **Audio** - a cached `transcription` always wins (current and earlier turns, no STT call). Otherwise current-turn audio goes native base64 only when the model has `"audio"` **and** the media type is in the adapter's wire set (WAV/MP3 on OpenAI-compatible wires; image-only adapters carry no audio, so audio degrades even for an audio-capable model). Everything else - including Ogg voice messages - degrades to speech-to-text with an "automatic transcription, may contain recognition errors" header (cached via `set_transcription()`, cache-write failures logged). No transcriber, an STT failure, or an empty result degrades to an `[Audio: ... - Path: ...]` path note (logged, run never aborts); earlier-turn audio without a cached transcription degrades to a path note. Native audio and transcription replies both carry a trailing `[Audio: ...]` path note too.
- **Document** - a PDF (`application/pdf` -> `pdf` modality; other files -> `file` modality) on the current turn goes native as the canonical `{"type":"document",base64,media_type,filename}` block when the model advertises the modality **and** the wire carries the type (today: OpenAI chat mode, Anthropic); otherwise it stays the `[File: <name> (<type>) - Path: <file_path>]` path note. The native document rides with that path note as well. A `text/*` file is never native: the resolver renders it through the read tool's bounded text view.
- **Video** - always degrades to a `[Video: ...]` path note (no supported provider wire accepts raw video). An unexpected media prefix degrades to a `[Media: ... - Path: ...]` path note rather than aborting the run.

A Tool may return a `read_media` artifact. The persisted Tool Result keeps the compact Attachment reference inside its normal envelope; Chat resolves it only for the active Run and adds the resulting media/path blocks under the request-only `tool_result_content` field of the correlated Tool message. Anthropic-style Messages and Responses wires render those blocks natively inside `tool_result` / `function_call_output`; text-only Tool wires retain text on the Tool Result and add one request-only media fallback after the complete sibling Result batch. No synthetic user message enters Session history, base64 never persists, and later Runs do not reactivate the image. A non-capable Model receives a path note instead of native media. Full modality behavior belongs in `attachments.md`; Tool-side artifact production belongs in the relevant Tool reference.

Assistant output-file references are distinct from input Content Blocks and Attachments. `core/chat/output_files.py` scans ordinary Assistant text outside fenced and indented code for `file:<filesystem-path>` tokens, which may appear around prose or alongside other markers. The path begins immediately after `file:` and ends at whitespace; it may be absolute or relative to the working Project cwd or otherwise the Agent workspace, but paths containing whitespace are intentionally outside this compact grammar. Exact existing filenames win first, after which common sentence-closing punctuation may be peeled from the token so surrounding prose remains intact. A single backtick pair around the complete marker is accepted and included in its span, while fenced and indented code remains inert. Each valid existing regular file produces an internal absolute path plus exact line/start/end span, so server projection replaces only the marker while preserving surrounding text. Unmarked paths, missing paths, directories, and URLs remain ordinary text. The original reply text remains canonical; server public projection consumes the internal reference, while Provider shaping always removes it.

## Tool-cycle invariant and repair

Every Assistant request entry with `tool_calls` must be followed by exactly one Tool Result for each `tool_call_id`, in Assistant-declared order, before any non-Tool message. Sibling calls execute concurrently by default within shared limits unless an explicit serial barrier applies; Session persistence and provider request history always retain the declared order.

If loaded history is missing a Result because a Run was cancelled, crashed, or was interrupted before persistence, `_repair_dangling_tool_calls` creates request-only `result_unavailable` failure envelopes for the missing calls. It never mutates canonical Session history. Cancel during dispatch likewise cannot discard Results already computed: all sibling Result Messages persist before the Run honors cancellation.

After Chat completes canonical history shaping and dangling-cycle repair, an Adapter with an explicit target-wire Tool-call-id profile may deep-copy that outgoing request view and normalize paired call/result ids for its wire. This transform is Provider-owned, request-only, and correlation-scoped to each Assistant batch; it never changes the canonical ids persisted in the Session or reused by Chat events.
