# Chat Request Building

Task-gated reference for turning canonical Session history into one provider-ready request. Read this when changing message rendering, notes, Skills, the prompt-epoch Tool list and Tool-change announcements, pinned dynamic prompt blocks and their change notes, the pinned thinking effort and its change notes, Content Blocks, Compaction-tail reconstruction, reasoning replay, or Tool-cycle repair; it is not required for unrelated Chat work.

## Pipeline and ownership

Request construction keeps three cohesive internal owners: `RequestBuilder` coordinates prompt epochs, Tool catalogs and history assembly; `_request_targets.py::RequestTargets` owns resolved Model routes, Adapter acquisition and Context policy; `_request_media.py::RequestMedia` owns Attachment resolution, Tool-media persistence/replay and the Session image budget. They share the existing Chat dependencies and request records, without a second public request-building interface.

Initial Run targets, fallback targets, route-sensitive Tool previews and the `/status` Context capacity (`ChatLoop.context_capacity`, `chat/usage.md`) resolve credentials and construct Adapters on Chat workers. A cancelled setup first settles the worker and closes any acquired Adapter; a later metadata failure closes it too. Context-capacity reads use the same worker boundary because the live local-Model limit can read Settings; the pre-send guard reuses that resolved value.

Prompt assembly and Tool-definition profiling use the Prompt pool; canonical Compaction projection, note embedding, Skill-context restoration, Tool-contract compilation, attachment/media scans, and token estimates use Chat's bounded transform pool. These synchronous transformations finish before the request crosses the async Provider boundary and never consume Event-Loop time proportional to Session size. Behind that boundary the Adapter builds, encodes and size-checks the wire payload in one Provider worker hop that still sees Chat's `request_input_budget` (`providers/request-policy.md` -> HTTP, retry, and streaming).

At a Model boundary, image limiting and exact request accounting share one transform job (`_request_history.py`). Completed Assistant replay, measured Usage observation and continuation accounting share another (`_step_outcomes.py`), after normalized Usage reaches the recorder. A completed Tool batch limits the live view and continuation and counts that continuation in one job. The prepared accounting value can then project Context without scanning the request again (`chat/usage.md`); persistence, hooks and cancellation remain separate async boundaries.

`core/chat/messages.py` owns canonical records/round-trip, with `_message_validation.py` for role/payload checks and `_message_history.py` for effective-history projection; `core/chat/wire_shaping.py` turns that history into one provider-ready request (assembly, notes, replay policy shaping, tool-cycle repair) and ingests normalized responses back into canonical messages (image retirement in `_request_images.py`, response ingestion in `_response_ingestion.py`; it depends on `messages.py`, never the reverse); `core/chat/_request_builder.py::RequestBuilder.build_request_state` coordinates the build using request-only history helpers in `_request_history.py`; `core/chat/block_resolver.py` resolves attachment-backed content; `core/chat/file_mentions.py` snapshots and renders `@` mentions; `core/chat/tool_dispatch.py` owns dispatch, while `_skill_activation.py` owns deterministic Skill activation. Provider adapters receive normalized request messages and definitions only. They own wire translation, while `core/sessions/` remains the persistence owner and `core/compaction/` owns checkpoint policy and Projection creation.

Each provider request is assembled from one loaded canonical Session snapshot. Chat first resolves the prompt epoch's Tool pin (Tool catalog per prompt epoch below); only a request without a readable pin derives Session-scoped Tool grants and withheld Tools, obtains the allowed/ready configuration-profiled Tool definitions and applies effective Model-route gates to pin them. The request's Tool list is the pin, the dispatch allowlist and request-state Tool contracts follow the pin plus the Tool changes announced since, Chat passes the pinned Tool names into System Prompt assembly, and only then shapes message history. The same contract mapping crosses `ToolDispatchContext`/`ToolExecutionConfig` into each `ToolContext`, so dispatch and lifecycle fingerprints use the exact schema the Model was last told for each Tool - the pinned definition after every profile, Sub-Agent target and route projection, or the definition a `[tool-change]` note announced; handlers retain their canonical semantic checks. This mapping is internal Run state and never changes Provider bytes. The `analyze_image` route gate also accepts an explicit Agent vision grant; binding/wire availability and ordinary permissions still apply (canonical contract: `tools/image.md`). The file edit route gate (`offer_edit_dialect`) keeps one dialect: `apply_patch` for a GPT-family Model, `edit` plus `write` otherwise (`tools/edit.md`). The System Prompt is assembled whole by `SystemPromptManager`; it is never appended to Session history, and an empty/whitespace prompt is omitted from the provider request.

When a Compaction checkpoint exists, its canonical Projection replaces compacted history. If that Projection omitted the newest complete, unconsumed Assistant Tool-call batch, `_overlay_pending_tool_batch` adds the canonical batch at its chronological position - after the Projection, before messages appended after the checkpoint such as steered User input - until a later Assistant turn consumes it. The checkpoint ended every Skill activation, so a restored Skill-loading Result is the same instruction-free digest a retained one gets; otherwise the raw instructions of a failed Run's Skill load would return after every checkpoint. Checkpoints themselves are never sent directly. Auto-compaction rebuilds and the live path both flow through the same note embedding and dangling-Tool repair.

Notes added by Extension `context` hooks are persisted and inserted into both the live continuation and the hook's request view before that same Model step. They therefore occupy the same position before its Assistant reply on replay, across Runs and forks (`test_chat_loop_requests.py::test_notes_keep_their_position_in_live_requests_replay_and_forks`).

## Canonical message fields

- Every role carries `id`, UTC-offset `timestamp` (readers accept `+00:00` and `Z`) and `role`. Explicit and persisted Message ids remain exact, and duplicate checkpoint ids remain valid: Messages are constructed before storage, so id allocation adds no global registry or database uniqueness constraint (`messages.py`, `tests/core/utils/test_ids.py`).
- A Tool message may persist `tool_display`, the final presentation-only snapshot used to reconstruct the same collapsed row from History. Dispatch resolves a start presentation from effective arguments, recomputes the terminal presentation with result/context facts and includes those snapshots beside `tool_call_started`/`tool_call_result`; only the final snapshot persists, as Tool-message UI metadata.
- An Assistant message may persist internal `output_files` references (Content Blocks, mentions, and media below) that identify resolved `file:` marker spans without copying file bytes; every reference carries its `line_index`, `start_index` and `end_index`, and validation rejects one without a span.
- Optional Assistant `reasoning_summary: list[str]` preserves ordered readable summary sections alongside the flat `reasoning` text. This is presentation metadata, persisted with the Message and exposed in public output; a retained Compaction Tail keeps it with the Message's Reasoning. Exact replay still uses opaque `reasoning_meta`, never this display projection.
- `timing` is `{started_at, completed_at, duration_ms}` with UTC display timestamps and a non-negative monotonic duration. Assistant `reasoning_timing` reuses exactly this shape for the first-to-last accepted reasoning delta of one streaming attempt; a stream restart restarts the measurement and non-streaming/fallback responses carry no timing. It never enters opaque-metadata handling; server transport passes it through to clients like Tool timing. Usage is a separate canonical object and never shares timing fields.
- A `history_edit` targets one active plain-text WebUI User message and folds that message plus all active successors out of future context without deleting any raw records.
- A terminal `run_summary` projects its native Run identity and completed `iteration_count`, and may carry the stable public Sub-Agent work id supplied by Run orchestration so exact Child results remain addressable after in-memory Run state is pruned. It may also carry `change_stats` - the server-computed git-style `{files, added, removed, paths, file_stats}` line-diff totals for the run, with `file_stats` giving each path's own `{path, added, removed}` in `paths` order (`tools/change_tracker.md`) - so reloads keep the WebUI's change statistics without re-deriving them from tool facts; an explicit all-zero object records a run whose edits reverted to their baseline rather than absence of data. Validation requires `file_stats`, when present, to match `paths` entry by entry; Runs stored before per-file counts existed have no `file_stats`.
- Request and continuation shaping always remove the presentation-only and internal fields (`tool_display`, `output_files`, `reasoning_summary`, `reasoning_timing`, `reasoning_scope`, `interrupted`) before wire translation.

## Canonical roles and request visibility

- `system`, `user`, `assistant`, and `tool` map to provider-visible conversation roles after shaping. Only `user` may persist `list[ContentBlock]`; other content is string-or-null according to the `ChatMessage` validator. Assistant `output_files` is canonical presentation metadata and is removed from both ordinary history requests and current-turn Tool continuations.
- Assistant declarations and Tool Results marked `programmatic` are durable child activity of `execute_code`, linked by `parent_tool_call_id`. Effective Context and request shaping exclude them before pending-batch recovery, Compaction, media replay and Context estimates. Only the parent program's selected output reaches the Model. Deliberate context effects still apply: a fresh programmatic Skill activation also creates an ordinary `[skill-context]` note. Automatic Compaction waits for a later Model step to consume that activation, including when streamed child work persists before its parent Assistant; a reused Provider call id cannot reactivate an earlier batch's consumed Skill. A programmatic `load_tools` result creates no silent `loaded` note because the Model never saw its definitions. `called_tool_names` likewise counts only Model calls, so child Tools remain on demand at the next epoch.
- `note` is a kernel-internal persistence role. Public history filters it. Ordinary notes become synthetic user messages containing `<system-reminder>` blocks; consecutive notes are grouped, and notes created during a Tool cycle are delayed until all sibling Tool Results have been persisted so they never split the cycle.
- `[skill-context] ` notes are the exception to ordinary note rendering: they become chronological standalone `<skill_content>` user messages. A Skill loaded through the `skill` Tool has no such note because its structured Tool Result already carries the raw instructions and optional resource/environment metadata; Sessions reconstructs the equivalent internal wrapped context only when Compaction replay needs it.
- `[tool-change] ` notes store a JSON payload (`core/chat/_tool_epoch.py::ToolChange`: epoch key, `added`/`removed`/`changed`/`loaded`/`on_demand`, registry Tool name, source fingerprint, definition (for `added`, `changed` and `loaded`), `listed`, `pinned`, optional `detail`, and `summary`, present only on `on_demand` notes). They render as ordinary System Reminders whose text `render_tool_change` builds at request time with the Model-facing Tool name (`powershell` for `bash` on Windows), because `model_facing_request` renames only definitions, calls and Tool messages, never reminder text. An unlisted addition and a `changed` note carry the definition's description and its compact JSON Schema (`separators=(",", ":")`, key order kept), and a `changed` note with `detail` puts it on a `Change: <detail>` line before them. Only a `changed` note of a pinned Tool says the Tool list still shows the previous definition; a changed announced Tool is just told to be called with the new one. An `on_demand` note reads ``Tool {name} is now available: {summary} Load its definition with `load_tools` before you call it.`` (a period is added to a summary without final punctuation; an empty summary gives ``Tool {name} is now available. Load its definition with `load_tools` before you call it.``). A `loaded` note is never rendered: the `load_tools` Result before it already showed the definition. A malformed payload is dropped from the request like a malformed Skill note.
- `[prompt-block-change] ` notes store a JSON payload (`core/chat/_prompt_block_epoch.py::PromptBlockChange`: epoch key, the changed blocks' new state, reminder `text`) and render as ordinary System Reminders carrying `text`; a malformed payload is dropped from the request (Dynamic prompt blocks per prompt epoch below).
- `[channel-message] ` notes are coalesced into a separate untrusted-background user message, not a System Reminder. Stored records are JSON-quoted and escape control characters plus angle brackets so channel participants cannot break or impersonate the wrapper.
- `[reply-surface] ` notes record WebUI/Desktop, terminal TUI or Channel identity in append-only Session chronology. Each reminder names the surface. The WebUI/Desktop reminder explains image rendering and file downloads through `file:<filesystem-path>`. The TUI reminder describes text/Markdown rendering, non-embedded media and the same marker for file downloads. A Channel identity includes platform, configured Channel id, and `direct`/`group` conversation kind; its reminder explains automatic final-text delivery and that ordinary replies attach no files. The `channel_send` definition owns how to send files, so the reminder names no Tool or parameters that might be unavailable. At executor start Chat appends one only for the first surface, a surface change, or the first interactive Run after a newer checkpoint; the tag is stripped and the model sees a turn-bounded System Reminder. Runs without a supplied surface do not change this state. A delivered Steer updates the active Run surface and appends a changed-surface reminder before the next request; a queued but undelivered input does neither.
- `run_summary` and `agent_takeover` remain visible history annotations. An `agent_takeover` never enters provider requests; a `run_summary` enters only as its interruption notice (below). `error` enters later requests only when `error_kind_llm_visible` allows it, as a System Reminder whose text is JSON-quoted as `{"run_error": ...}` with angle brackets escaped, because it can carry raw Provider payloads; portable reasoning and channel quotes use the same `_quote_external_json` helper. A cancelled, interrupted, or failed `run_summary` without a complete answer renders its interruption notice as a System Reminder instead (`chat/run-execution.md` -> Interruption). `compaction_checkpoint` contributes through its Projection, not as a role.
- Real `<system-reminder>` tags reach the Model only from Chat's own reminders. Note and Model-visible error runs, interruption notices and Compaction's instruction reminder render through `wire_shaping.system_reminder_request_message`, which neutralizes look-alike tags inside each body and marks the content with the private `_SystemReminderContent` str type. It subclasses the Adapter contract's `RequestContextText` (`core/providers/adapter.py`), which also marks quoted Channel observations: both are context, not a user turn, for Adapters that tell them apart (Copilot's `x-initiator`, `providers/github-copilot.md` -> Endpoint Policy). Secret masking keeps either mark. The final projection `model_facing_request` (the last step before the adapter: on the Chat transform pool in `WireRequestRunner.send_assistant_request`, on the Compaction worker pool for Compaction's Model request) then rewrites the `<` of every other look-alike tag to `&lt;` (any case, whitespace inside the tag or around the slash, attributes; the rule is `core/providers/_tool_result_text.py::neutralize_system_reminder_tags`) in user text and text blocks (attachments, mentions, Skill-context carriers, channel quotes), Assistant `content` and readable `reasoning`, and Tool `tool_result_content` text blocks; Provider wires neutralize the rendered Tool Result body (`providers/request-policy.md`) and the readable text they replay from `reasoning_meta`: every Responses wire (`_responses_wire._replay_item`: `output_text` of `message` items, `summary_text` and `reasoning_text` of `reasoning` items) and Gemini text parts without a `thoughtSignature` (`_gemini_wire._replay_part`). System messages, signed or encrypted replay state (Responses `encrypted_content` and ids, signed Gemini parts, Anthropic thinking signatures), Chat Completions `reasoning_details`, Tool Call arguments and native media or document blocks are never changed. The rewrite is request-only, deterministic and idempotent: Session history, Run events and Extension hooks keep the original text, and replayed history keeps its prompt-cache prefix. Content rewritten after rendering, including by an Extension `context` hook, loses the mark and is neutralized, so no hook or producer can add a real tag. Coverage: `test_wire_shaping_requests.py`; replay: `tests/core/providers/test_adapter_tools.py`, `test_opencode_zen_gemini.py`.
- `model_facing_request` also masks every known Agent Secret value (`masker`, from `AgentSecrets.masker`) in `content`, `reasoning`, Tool result content blocks and Tool Call arguments of every message, System messages included; media and `reasoning_meta` stay unchanged. It is the last guard for a value that slipped past result and input masking (`secrets/agent-secrets.md` -> Masking).
- Human `sender` attribution is rendered only while building the provider request as `[display_name|platform_user_id|role]`, where `role` is the persisted immutable `admin`/`member` snapshot. All attribution parts are sanitized before insertion. `input_origin` appends a hidden System Reminder immediately before the unchanged visible user message: `speech_transcription` (dictated) says the text may contain transcription errors, `live_voice` (passed on by the Live operator) says it may contain speech recognition errors or the voice assistant's rewording. The origin persists on the User message (`ChatMessage.input_origin`), so the WebUI labels Live voice messages (`You · via Live`).

A User entry with `sender.kind == "session"` is peer input: its stored content stays unchanged and the WebUI labels the sending Session. Request shaping attributes it to another Session and JSON-quotes its source reference, Agent and content with escaped angle brackets, marked `RequestContextText`; it is not a human instruction or a System Reminder. The same projection applies to replay and Compaction. Sender fields come from the authenticated sending Session, never its message text (`chat/run-execution.md` -> Session messages).

## Reasoning replay

The system default `ReasoningReplayPolicy` is `full_history`; an optional Provider override and then an optional Model override can narrow or replace it (`providers/request-policy.md` owns the hierarchy). The effective policy governs native `reasoning`/`reasoning_meta` replay; Chat owns history shaping and never interprets `reasoning_meta`. `none` strips native readable and opaque reasoning everywhere; `current_run` preserves it only across Tool continuation inside the active Run; `tool_turns` applies `full_history` only to Assistant turns with Tool Calls, so an answer turn never carries native reasoning, neither as live continuation nor in later Runs; `full_history` replays persisted native reasoning when the Assistant's internal `reasoning_scope` exactly matches the current resolved Provider/Model/Connection/Account scope. Across a mismatched route, Chat always strips both native fields and may project only non-empty readable `reasoning` from a completed reasoning-only or Tool-associated Assistant turn as an escaped, request-only provider-neutral System Reminder after its Tool batch. It never projects `reasoning_meta`, scope identity, empty/meta-only state, interrupted work, or ordinary answer-turn reasoning; this avoids both opaque-state leakage and duplicate answer context. An `interrupted` Assistant turn is a hard native-reasoning boundary regardless of policy or matching scope: canonical persistence retains its readable and opaque fields, but request shaping removes both `reasoning` and `reasoning_meta`; the provider-neutral Continuation reminder is the only replay channel for its readable work. `reasoning_scope` is persisted only on reasoning-bearing Assistant messages and is always removed before the provider request. Every policy except `current_run` decides per message alone, so the bytes a request sends for a message never change in a later request and the Provider prompt cache keeps its prefix; `current_run` strips a finished Run's reasoning in the next Run and breaks the cache there whenever the Provider rendered that reasoning (test: `tests/core/chat/test_chat_loop_reasoning_replay.py`).

The current Assistant turn is appended through `_assistant_continuation_dict`, which strips `usage` and `reasoning_scope` but preserves policy-permitted reasoning; an interrupted partial loses native `reasoning` and `reasoning_meta` in its same-Run continuation request too, and an entry left without content, Tool Calls, or reasoning is not sent. Every mid-Run rebuild (steering, textual Compaction projection, stale-Compaction recovery, Model fallback) goes through `RequestBuilder.rebuild_live_request_state`, which restores live reasoning by retained message id plus Run-local Tool media; fallback then strips native reasoning. The Summary+Tail planner budgets these live fields before selecting whole retained steps. It never restores omitted Assistant messages, and ordinary retained Tool arguments/results remain unchanged so Responses `response_output` replay cannot undo a payload edit; the persisted checkpoint Projection keeps the Tail's `reasoning`, `reasoning_meta`, and `reasoning_scope`, so later Runs shape the Tail under the same policy and scope rules as any history and resend it unchanged. Assistant `phase` remains because it is semantic history required by Responses Models, not opaque provider state.

When run-local Model fallback begins, Chat rebuilds request state with the fallback target's replay policy, exact reasoning scope, input modalities and wire media support, plus the epoch's Tool list with every Tool the Model may call (Tool catalog per prompt epoch below), then strips prior Assistant native reasoning/reasoning metadata before the first fallback request regardless of the primary policy. Completed reasoning-only or Tool-associated readable work follows the same bounded provider-neutral projection rule and is placed after the associated Tool Results; opaque primary state never reaches the fallback. Every Assistant message produced by the fallback persists the fallback binding as its `model`, and any reasoning is persisted with the fallback scope even though the Agent's configured primary Model remains unchanged, so a later primary Run cannot inherit its native state.

## Skills and prompt-cache stability

Announcement planning and successful Compaction prompt refresh require `SkillRegistry.filter_allowed`; an empty catalog is a valid empty baseline.

Pure-text `/skill-name` at the start and `$skill-name` anywhere are deterministic Skill activation hints; `$` never routes to a built-in command. The original user message stays unchanged. Only allowed, loadable, currently available Skills activate. An identical name+content activation deduplicates within the current Compaction epoch, while committing a changed package permits the same Skill name to activate again and keeps latest content. A committed checkpoint removes full trigger carriers and compacts loading `skill` Tool Results from its Projection, then adds one names-only reminder for activations since the preceding checkpoint; the instructions and Skill environment grants are inactive until the Model explicitly reloads a still-relevant Skill. Aborted Compaction changes nothing, and a later checkpoint never carries the prior names reminder forward.

`pinned_skill_catalog` (`core/prompts/pinned_context.py`) snapshots the rendered Skill catalog text as a Session prompt pin on the first build of a Session or prompt epoch. Later requests reuse that exact text for prefix stability until successful Compaction; the post-checkpoint refresh forces a complete Skill rescan, renders a replacement catalog, and replaces the Session's seen-Skill set in the checkpoint's transaction, so additions/removals/metadata or requirement changes appear without redundant announcements. A newly available+allowed Skill between Compactions does not rewrite the catalog; `_plan_skill_announcement` compares the Run's resolved registry with the stored seen-Skill set and plans a one-time System Reminder note instead (a Session without a recorded set records the current catalog as its baseline, with no note). The note and its seen-Skill update commit in the same write as the Run's input, so a Skill is marked seen exactly when its announcement persists. The admitted Working Project supplies Project Skills while an Identity Agent retains its private Skill layer; Project Agents remain under Project ceilings. Skill activation carriers remain canonical conversation Context and are not part of this System Prompt refresh.

The same epoch-pinning covers every other file-backed System Prompt input: the rendered SOUL block (`pinned_soul_context`) and the combined personal and shared Project Memory rendering (`pinned_memory_files`), the Working Project frame for Identity Sessions working in a Project and Project Agents alike (`pinned_working_project_context`), and a Workspace-less Agent's body (Project Agent, temporary participant; `pinned_agent_body`). A personal Memory mode, effective Memory Project or Project Memory permission change also invalidates its own snapshot, because the pin records the personal mode and effective Memory Project id (`core/prompts/pinned_context.py`; modes: `memory.md` -> Modes and gating). On-disk changes to `SOUL.md`, `MEMORY.md`/`USER.md`, or Project auto-load files therefore cannot alter the System Prompt prefix mid-epoch; they become visible only when a successful Compaction starts the next prompt epoch and re-renders all snapshots (an aborted/failed Compaction changes nothing). Read-before-write stamping happens at snapshot/refresh time only, never on reuse.

## Working Project Context

`core:working_project` renders the file-backed `working_project.md` template from the admitted Project's id, display name, absolute Project Workspace, and readable instruction files (`Project.instruction_files`: the main instruction file, then the additional `auto_load` files; `projects/resolution.md` -> Project Context instructions). A file the Run's Permission Boundary refuses to read is left out (`permitted_project_context`, `core/chat/_run_permissions.py`), at Run start and when a Compaction rebuilds the frame; the prompt preview and an Extension's prompt inspection render without a boundary. Both an Identity Session working in a Project (its Working Project, GLOSSARY -> Working Project) and a Project Agent (its addressed Project) receive that frame as the prompt-epoch snapshot `pinned_working_project_context`: rendered before the first provider request of an epoch, stored as a Session prompt pin, and supplied verbatim until successful Compaction rebuilds it from the current Project, its instruction files (the main file is chosen again), and readable file contents; an explicit `project` Tool call still cannot replace the automatic frame. An Identity Session working in its Agent's Workspace has no Working Project block and no pin. This pins only the automatic Working Project block; the explicit `project` Tool retains its ordinary persisted Tool result, and every non-file System Prompt input keeps its existing lifecycle. Prompt preview renders a prospective Identity frame (the named Session's Working Project, else a new Session's) without persisting it and a live Project Config frame from the addressed Project.

## Folder instructions

While the Working Project's `folder_instructions` switch is on, a Tool batch that worked in a subfolder of its repository hands the Agent that folder's instruction files. Tools report the absolute paths a call worked in through `ToolContext.record_worked_paths` (`tools/registry-dispatch.md` -> ToolContext); `ToolResultPersistence._persist_tool_results` (`core/chat/_tool_results.py`) collects them for the calls whose Results persist, and `core/chat/_folder_instructions.py` asks `FolderInstructions.files_for` (`core/projects/instructions.py`) which files govern them: per folder from the path up to, but without, the repository root, the first of `AGENTS.md`, `CLAUDE.md`, `GEMINI.md`, outermost first; nothing inside `.git`, `node_modules`, `site-packages` or `__pycache__`, and never a file the System Prompt already loads, a main instruction file location such as `.claude/CLAUDE.md` (repository-wide, whichever main file loads) or a file the batch itself touched.

- Each file becomes one `[folder-instructions]` note (JSON: absolute `file`, repository-relative `label` and `folder`, the `render_prompt_file` frame as `text`), added while the Session defers its notes: it persists in the batch's transaction after the Results and reaches the next request as a System Reminder in the same order. Rendering reads only the stored text, so the request bytes never change afterwards; a malformed note is dropped from the request.
- The ledger is the notes visible since the latest Compaction checkpoint (`effective_compaction_messages`); there is no table. A file shown there is not shown again; after a Compaction summarizes a note away, the file is shown again the next time the Agent works there. A note in a kept Tail stays visible and keeps counting. Forks and history edits carry the notes with their messages.
- A shown file is stamped read for read-before-write; an unreadable file, or one the Run's Permission Boundary refuses to read, is skipped and tried again by the next batch. External Runs (`chat/external-run.md`) show no folder instructions.

## Content Blocks, mentions, and media

`core/chat/content_blocks.py` owns `TextBlock`, `MediaBlock`, `FileBlock`, and `FileMentionBlock` plus JSON round-trip. On admission, Chat assigns every incoming image a positive `image_reference` continuing from the Session's persisted images; this durable reference renders as `Image 1`, never as a made-up filename or a storage path. Every incoming audio `MediaBlock` likewise gets its speech-to-text as `transcription` before the user message persists (`ContentBlockResolver.transcribe_audio`, through `RequestBuilder.transcribe_user_audio`): a Run's own input before it takes the Session write lock (Stop abandons it and the input persists without one: `chat/run-execution.md` -> Cancellation), steering input as it is appended, its speech-to-text run before that lock so the append reuses the attachment's cached text. A block that already carries a transcription keeps it, an attachment transcribed before reuses its cached `transcription`, and no service, an unreadable attachment, an error or an empty result leave the block without one; the input is never refused. History, accessors, Session search and Recall (`core/recall/canonical.py::content_block_to_text`) and Session titles therefore carry what a voice message said (`test_voice_input_persists_with_its_transcription`). `core/chat/file_mentions.py` lists the mention root for the `@` picker (`files.list`, `server/path-pickers.md`): an index of the files, and their directories, that the search Tools would search there (ripgrep's selection through `core/tools/search.py`: ignore files, `.git/info/exclude` and global Git excludes apply, hidden files count, `.git` and directory links, Windows junctions included, are never entered; paths are read NUL-separated, so a Linux file name with a line break is one entry), and per directory its direct entries with the ones the index leaves out marked `ignored`. It expands verified mentioned paths into immutable snapshots before Run admission. A `FileMentionBlock` records `path`, `status`, `text`, and `size_bytes`; request rendering always identifies it as a user-supplied file snapshot. Auto-injected Project files and expanded mentions are stamped into `runtime.file_read_state` so later full-file `write` Calls satisfy read-before-write without duplicating a read. Mention snapshots capture their read stamp before reading bytes, so a concurrent rewrite remains unseen to full-file replacement.

`ContentBlockResolver` performs provider-agnostic last-mile media routing by intersecting the Model's input modalities with `ProviderAdapter.wire_media_support(model_id)`. Every turn resolves the same way, earlier turns included, so the request prefix stays byte-identical from Run to Run: a supported image/audio/PDF/video becomes a native block followed by a path note. For images, the shared Attachment ImageConverter can first convert an unsupported source format to PNG, lossless WebP, or high-quality JPEG selected from the actual target Adapter declaration; all images are validated, and native PNGs can be losslessly repacked before applying the effective byte ceiling (`attachments/image-conversion.md`). Chat passes the smaller of the configured Attachment limit and a known Adapter per-image limit. Preparation first preserves full resolution; when required by that ceiling it can lower JPEG quality or resize, and the path note states the sent dimensions and lossy compression. Original blobs and filenames stay unchanged. Invalid images, decoding-limit failures, and multi-frame inputs needing conversion become actionable path notes. The converted base64 payload is subject to the same request image budget. Unsupported or otherwise non-native media degrades to an explanatory path note; audio renders the transcription its block carries. Text files carry the bounded rendering used by the `read` Tool. A text attachment persists as one `FileBlock` and renders the same on every turn; an exactly duplicate `TextBlock` right after it (the former file-plus-full-text representation) is omitted at request assembly, while other text after it stays (`core/chat/block_resolver.py::_is_duplicate_attachment_text`). A missing attachment record degrades to a "file no longer available" note, because the turn stays in every later request; only other stored-blob I/O failure aborts the Run; capability mismatch degrades. Attachment metadata, blob reads, and text renders run on the `chat-attachments` worker pool: all earlier turns resolve in one hop, and the current turn reads its files there before image conversion or Speech-to-Text continue on the Event Loop.

Per-modality degrade policy:

- **Image** - native base64 when the model has `"image"` and the image type is in the wire set. An image to a non-vision model degrades to an `[Image: ... - this model has no vision capability ... - Path: ...]` note instead of aborting; a vision model whose wire cannot carry the type first tries the shared format converter. If conversion is unavailable or fails, it degrades to an `[Image: ...]` path note; a missing record degrades to a "file no longer available" note. The native image rides with an `[Image: ...]` path note as well, so the agent always holds the file path, not only the pixels.
- **Audio** - request building never runs speech-to-text; it ran before the message persisted (Content Blocks above). The block's `transcription` always wins, rendered with an "automatic transcription, may contain recognition errors" header. Without one, audio goes native base64 only when the model has `"audio"` **and** the media type is in the adapter's wire set (WAV/MP3 on OpenAI-compatible wires; image-only adapters carry no audio, so audio degrades even for an audio-capable model); everything else - including untranscribed Ogg voice messages - degrades to an `[Audio: ... - Path: ...]` path note whose reason says whether no speech-to-text service exists or it could not transcribe the audio. Native audio and transcription replies both carry a trailing `[Audio: ...]` path note too.
- **Document** - a PDF (`application/pdf` -> `pdf` modality; other files -> `file` modality) goes native as the canonical `{"type":"document",base64,media_type,filename}` block when the model advertises the modality **and** the wire carries the type (today: OpenAI chat mode, Anthropic); otherwise it stays the `[File: <name> (<type>) - Path: <file_path>]` path note. The native document rides with that path note as well. A `text/*` file is never native: the resolver renders it through the read tool's bounded text view.
- **Video** - native base64 only when the model has `"video"` and the wire carries the type; otherwise a `[Video: ...]` path note. An unexpected media prefix degrades to a `[Media: ... - Path: ...]` path note rather than aborting the run.

A Tool may return a `read_media` artifact. The persisted Tool Result keeps the compact Attachment reference inside its normal envelope; Chat resolves it for every request until Compaction compacts the Tool Result, and adds the resulting media/path blocks under the request-only `tool_result_content` field of the correlated Tool message. Attachment and mid-Run restore correlate by Tool message identity, never by Tool-call id alone, because some Providers reuse ids such as `tool_call_0` in every response. Anthropic-style Messages and Responses wires render those blocks natively inside `tool_result` / `function_call_output`; text-only Tool wires retain text on the Tool Result and add one request-only media fallback after the complete sibling Result batch. No synthetic user message enters Session history and base64 never persists. A non-capable Model receives a path note instead of native media. Attachment storage and sniffing belong in `attachments.md`; Tool-side artifact production belongs in the relevant Tool reference.

Tools that load pixels in memory (`read`, computer use) hand them to Tool dispatch through `ToolContext.result_media`, which delivers them with failed Results too (computer use shows the screen a failed input step left; `test_media_outputs_are_read_media_artifacts_and_loaded_pixels`). Right after dispatch, before the Tool Results persist, `RequestBuilder.store_tool_media` stores each loaded image as an Attachment blob and records `{attachment_id, filename, media_type}` references in the Tool message's internal `tool_media` field (persisted in `tool_call_payloads.media_json`, stripped from every wire). From then on the image resolves like a `read_media` artifact in every request, including the first one after the call and later Runs, with a path note naming the stored blob. Re-reading an overwritten path stores new pixels under the new Tool message while earlier Results keep their own copies (`test_rereading_overwritten_image_delivers_each_calls_own_pixels`). If storing fails, the image stays an in-memory item for the current Run only: `ContentBlockResolver.resolve_tool_image` routes and converts those bytes without file I/O, in-Run Compaction restores them, and Model fallback re-prepares them for the new route. Stored Tool images follow Session reference retention and lifecycle collection (`attachments.md` -> Constraints & Gotchas); Compaction alone does not release their canonical references.

Assistant output-file references are distinct from input Content Blocks and Attachments. `core/chat/output_files.py` scans ordinary Assistant text outside fenced and indented code for `file:<filesystem-path>` tokens, which may appear around prose or alongside other markers. The path begins immediately after `file:` and ends at whitespace; it may be absolute or relative to the working Project cwd or otherwise the Agent workspace, but paths containing whitespace are intentionally outside this compact grammar. Exact existing filenames win first, after which common sentence-closing punctuation may be peeled from the token so surrounding prose remains intact; Windows aliases that normalize away trailing dots do not count as exact filenames. A complete matching Markdown emphasis wrapper of one to three `*` or `_` characters, or a single backtick pair, around the marker is accepted and included in its span because Models commonly format instructed syntax, while fenced and indented code remains inert. Each valid existing regular file produces an internal absolute path plus exact line/start/end span, so server projection replaces only the marker while preserving surrounding text. Unmarked paths, missing paths, directories, and URLs remain ordinary text. A restricted Run resolves through `OutputFileScope(cwd, permissions)`: a path its rules refuse to read is never checked and stays text, and an HTML file, which the server opens as a website preview of its whole folder (`server/browser-capabilities.md` -> Website previews), stays text unless the folder is readable and the rules refuse nothing below it except dot names, which previews never serve. The server mints URLs only for stored references, so it needs no boundary of its own. The original reply text remains canonical; server public projection consumes the internal reference, while Provider shaping always removes it.

`wire_shaping.RequestImageBudget` decides which native images a request still carries, independently of token Compaction. Every image, user or Tool, stays in every request until a Provider limit forces room; vBot sets no limit of its own (user decision 2026-10-04). Limits come only from the route: `ProviderAdapter.request_image_limit(model_id)` (documented image count, carried as `_ModelTarget.max_request_images`) and body-size rejections (below). Chat acknowledges the exact sent image identities and payload hashes only after a completed, non-interrupted, accepted Model response; failed or partial attempts do not make fresh images eligible for retirement. Images already in the history when the Run starts count as delivered; images of the current user turn and new Tool images are fresh. A changed payload at the same address must be delivered again; hashes retain no pixels.

When a request holds more images than the route's image limit, the oldest delivered images retire until at most half the limit remain (fewer only when fresh images alone exceed half), so retirements stay rare and the request prefix before the oldest retired image stays cached. Each retired image becomes a fixed, path-preserving explanatory text block; Tool envelopes, sibling order, Assistant findings, original files, and canonical history stay unchanged. Retirement is keyed by image address `(role, message id, block index)` and persists per Session in the prompt pin `pinned_image_retirement`: a Run restores it on its first request build and writes new retirements after each accepted response, so later Runs render the same notes. Compaction starts the new prompt epoch without it, and an automatic Compaction also resets the Run's budget. Speculative projections (`remember=False`) do not commit retirement. Re-reading an original creates a fresh image at a new message identity.

A Provider wire raises `ProviderRequestTooLargeError` before I/O when the serialized request exceeds its declared `request_body_limit`, and any HTTP 413 answer raises it without sizes (`providers/request-policy.md`). Chat then calls `RequestImageBudget.shrink`, which retires the oldest delivered images until the image data takes at most half the known limit (half the current image data when the limit is unknown), at least one per rejection, and rebuilds the request without rerunning Tools, context hooks, or counting another Iteration. When no delivered image remains, the concrete size error surfaces. Regressions: exact wire bytes in `tests/core/providers/test_ollama_cloud.py` and `test_anthropic_requests.py`; in `tests/core/chat/test_chat_integration_images.py` count and body pressure with request rebuilds and a following Run (`test_long_mixed_image_run_keeps_images_and_can_reopen_originals`) and a streaming rejection (`test_provider_body_overflow_preserves_fresh_inputs_and_stops_without_retry`).

If fresh images alone exceed the route's image limit, `ImageBudgetExceededError` ends the Run with the count and limit before a Model request, rather than discarding unseen pixels. The same projection runs during initial and rebuilt resolution, after context hooks before sending, on live Tool continuations before Compaction, and after rich-content restoration. Session history retains the fresh inputs and correlated Tool Results even when this check fails. Regressions: `tests/core/chat/test_wire_shaping_image_budget.py` and the fresh-user/fresh-Tool overflow scenarios in `tests/core/chat/test_chat_integration_images.py`.

## Tool-cycle invariant and repair

Every Assistant request entry with `tool_calls` must be followed by exactly one Tool Result for each `tool_call_id`, in Assistant-declared order, before any non-Tool message. Sibling calls execute concurrently by default within shared limits unless an explicit serial barrier applies; Session persistence and provider request history always retain the declared order.

If loaded history is missing a Result because a Run was cancelled, crashed, or was interrupted before persistence, `_repair_dangling_tool_calls` creates request-only `result_unavailable` failure envelopes for the missing calls. It never mutates canonical Session history. Cancel during dispatch likewise cannot discard Results already computed: all sibling Result Messages persist before the Run honors cancellation.

Assistant Tool Calls carry the canonical arguments Provider intake produced: plain JSON with recursively sorted object keys, the same form the Session store persists (`providers.md`). The in-Run follow-up, the next Run's history, a fork and Compaction therefore send byte-identical Tool cycles and keep the Provider prompt-cache prefix (`test_notes_keep_their_position_in_live_requests_replay_and_forks`).

After Chat completes canonical history shaping and dangling-cycle repair, an Adapter with an explicit target-wire Tool-call-id profile may normalize paired call/result ids for its wire on a copy-on-write request view. This transform is Provider-owned, request-only, and correlation-scoped to each Assistant batch; it never changes the canonical ids persisted in the Session or reused by Chat events.

## Tool catalog per prompt epoch

Within one prompt epoch every request sends the same Tool list, so the Provider prompt cache survives Tool changes; a change reaches the Model as a `[tool-change]` System Reminder, and dispatch follows what those reminders told it. `core/chat/_tool_epoch.py` owns the pure model; `RequestBuilder` (`build_request_state`, `live_tool_catalog`, `announce_tool_changes`) owns resolution and persistence. Work that grows with the Session or the Tool count runs on Chat transform workers, off the Event Loop: reading, parsing and starting the pin, folding the history's notes, and the catalog's readiness checks and fingerprints.

- **Pin.** The Session prompt pin `pinned_tool_definitions` (`ToolEpochPin` payload `{v: 2, epoch, definitions, sources, on_demand?}`) holds the exact post-route Provider definitions of an epoch's first request under registry names, a random epoch key, a fingerprint of each Tool's registered pre-route definition, and, only when the epoch has any, the On-demand Tools as `on_demand: [[registry name, summary], ...]`, sorted by Model-facing name (On-demand Tools below). `definitions` is one compact JSON string that keeps each definition's key order, because the Session store sorts the keys of stored JSON objects; the pinning request already sends the definitions as they read back, so `tools[]` is byte-identical on every request of the epoch, across Runs and restarts (`tests/core/chat/test_chat_loop_tool_definitions.py`, `test_chat_loop_compaction_prompt_epoch.py`). A request without a readable pin (the Session's first, an unreadable or other-version payload) pins the Tools offered now - allowed, ready and route-gated for the Run's primary route (`RequestBuildInputs.tool_route_*`; `tool_route_model_family` is the primary target's Model family from the Model catalog, `_ModelTarget.model_family`, empty when unknown), even while a fallback target serves the request - through `ensure_prompt_pin`, so a concurrent first request's readable pin wins. Chat resolves this slot itself; it is not a System Prompt input. It is Agent-bound and does not survive a cross-scope fork, move or Takeover (`sessions.md` -> Prompt state). A Model change mid-epoch never re-pins.
- **When changes are measured.** In the locked request-boundary block of `_agentic_progression.py`, after background-completion delivery and before pending notes drain: at the first boundary of every Run, after a steering rebuild, and whenever `(ToolRegistry.revision, pin epoch)` differs from the last evaluation; never on a finalization-only cycle. A readiness flip alone bumps no revision and is therefore seen at the next Run or registry change. `LiveToolCatalog` is measured on the Run's primary target, never a fallback: `usable` (allowed, ready or not), `offered` (ready and route-gated), registered-definition fingerprints and current Session grants. `ToolEpochView.plan` compares it with what the Model knows - the pin folded with this epoch's notes from the loaded history - and each planned change becomes one note that the same request already adopts. Notes therefore follow the User input or the complete sibling Tool Result batch.
- **Withheld Tools.** A Session can withhold a Tool its Agent's policy allows: a Sub-Agent Session at the nesting limit withholds `subagent` (`RequestBuildInputs.subagent_tool_withheld`, from `ChatLoopDependencies.subagent_tool_usable`, asked once per Run context and for a manual Compaction; `subagents/delegation.md` -> Limits). A withheld Tool is not usable: a new pin leaves it out, and the change rules below announce a withdrawal or a return.
- **Change rules.** *Removed:* a Tool the Model may call that is no longer usable (unregistered, policy or grant withdrawn, withheld by the Session). Readiness never removes a known Tool (dispatch answers `tool_not_ready`), and a route gate never removes one; `analyze_image` counts as removed only when the Model knows it, the route gate hides it and no image-understanding backend is available. *Added:* a Tool the Model may not call, once usable, ready and route-gated - a pinned Tool announced as removed becomes available again (`pinned`, listed); any other Tool is announced with its definition, including one that was not ready when the epoch started. *File edit dialect:* fixed for the epoch. The live catalog takes it from the Tools the Model was told about (`ToolEpochView.known_names`: the pin plus every announced Tool, removed ones included; `known_edit_dialect`); only an epoch that knows no file edit Tool picks it by the primary route's Model family. A Model change mid-epoch therefore neither offers nor announces the other dialect (`test_a_model_change_keeps_the_file_edit_tools_of_the_prompt_epoch`). *Changed:* a known Tool whose registered fingerprint changed and whose definition differs from the known one in a part its `announce_changes` names (`tools.md` -> Tool changes in a Session); any other change stays silent until the next prompt epoch. A stored `changed` note may carry an optional `detail`, rendered as its `Change:` line.
- **On-demand Tools.** While the Agent's `tool_loading` switch is on (`tools.md` -> Terms -> On-demand Tool), `LiveToolCatalog.on_demand` maps each offered On-demand Tool to its summary (`on_demand_tool_entries`), and `ToolEpochPin.start` leaves those Tools out of `definitions` and records them in `on_demand`, which the System Prompt block `tool:load_tools` lists (`prompts/contributed-blocks.md`). Only a primary route that serves On-demand Tools gets them (`_ModelTarget.on_demand_tools`, `RequestBuildInputs.tool_route_on_demand_tools`, the Adapter's `on_demand_tools(model_id)`, wire `request.on_demand_tools`): on any other route `on_demand` stays empty and `load_tools` is neither offered nor usable, so the pin lists every Tool. Such a route's Model calls only Tools in `tools[]`, and listing each loaded Tool would cost the cached prefix (`providers/openai.md` -> Tools loaded on demand). A Model change mid-epoch from a serving route to such a route follows the switching-off rule below; a route that lists no announced Tools cannot call those `added` Tools until the next prompt epoch. `load_tools` belongs to an epoch only while it has a Tool to load: the live catalog offers it only while `on_demand` is non-empty and counts it usable while any usable Tool (ready or not) is on demand, the pin lists it only when it leaves at least one Tool out, and `plan` adds it only to an epoch whose pin or notes name an On-demand Tool, ahead of the first `on_demand` note that needs it; once known it is removed only when no usable Tool is on demand, so readiness and route gates never take it away. The Model knows such a Tool by name only (`ToolEpochView.loadable_names`): it is allowed and callable, and its contract compiles from the definition a load would return (`RequestState.tool_loads`, the `loaded` change per loadable Tool on the primary route; `None` until a catalog was measured for the state, which makes the next request boundary measure one), but the request lists no definition for it. A successful `load_tools` call records its loaded registry names (`ToolDispatchContext.record_tool_load`); the Tool Results' batch persists one silent `loaded` note per Tool it loaded, with the definition the call returned, and the Run adopts the notes at once (`RequestToolCatalog.adopt_tool_changes` in `_request_tool_catalog.py`): the Tool becomes known with that definition, `load_tools` answers `already available` for it, and a route that lists announced Tools lists it. A Tool that becomes usable mid-epoch as an On-demand Tool is announced by an `on_demand` note (name and summary) instead of `added`, unless the Model already got its definition in this epoch (it was loaded or announced before a removal): then it is `added` with its definition again, so a route that lists announced Tools keeps listing it (`test_tool_epoch.py::test_on_demand_tools_are_known_by_name_until_a_silent_load_records_the_definition`). Switching the setting off mid-epoch announces each Tool known by name only as `added` with its definition and `load_tools` as removed; switching it on announces `load_tools` under the rule above, while Tools already known keep their definitions. A Run Tool restriction keeps `load_tools` allowed (`tool_dispatch._dispatch_allowed_tools`), and the call loads only Tools the restriction admits. A Tool the Model knows by name only that the primary route does not offer now (not ready, or route-gated) is in `RequestState.unloadable_tools`, which reaches `load_tools` through `ToolDispatchContext.unloadable_tools`; the call reports it, like a Tool the restriction refuses, as listed but not usable now (`tools/load_tools.md`). Tool list and System Prompt stay byte-identical across loads (`test_chat_loop_tool_definitions.py::test_on_demand_tools_are_listed_in_the_system_prompt_and_loaded_when_needed`).
- **Dispatch.** `ToolEpochView.allowed_names` (pinned plus announced additions, minus announced removals) is the request-state allowlist; contracts compile from the definition each Tool was last announced with, except for a Tool no longer registered (deleted by an update, its Extension unloaded): it gets no contract, since only its registration says whether its schema may stay open, and the next request boundary announces it as removed (`test_an_announced_tool_removed_again_fails_as_removed_under_its_own_name`). Announced names count as offered for Called Tool name resolution; `removed_names` count as registered there and reach `ToolDispatchContext.removed_tool_names`, which fails their calls with `tool_removed` (`tools/registry-dispatch.md` -> Removed Tools). The file edit Tools count as one permission: `tool_dispatch._dispatch_allowed_tools` adds the policy-allowed siblings of an allowed one (`edit_tool_siblings`), and a Run Tool restriction naming one admits all three, so a call to the dialect the route did not offer runs under that Tool's registered contract instead of failing (`test_tool_dispatch.py::test_file_edit_tools_share_one_permission_whichever_the_route_offered`).
- **Request Tool list.** Always the pinned bytes, also on finalization requests after Chat disabled Tool execution for the Run (`run-execution.md`): dropping the list would change the cached prefix, so no tool choice is sent either and the finalization note plus correlated refusals stop further calls. A route whose wire profile sets `request.list_announced_tools` (the Adapter's `list_announced_tools(model_id)`, `providers/wire-profiles.md`; `RequestBuildInputs.list_announced_tools`) also lists each Tool announced as added or loaded, in announcement order with its latest definition; the note's `listed` flag and wording follow the primary route. Every fallback route (`RequestBuildInputs.list_all_tools`, `ToolEpochView.fallback_request_tools`) lists every Tool the Model may call: the pin, then each other available Tool in the order the Model first heard of it, an On-demand Tool known by name only with the definition a load would return (`RequestState.tool_loads`). A load therefore moves nothing, so the fallback's Tool list stays the same while it serves the Run (its cache starts cold anyway), and a fallback whose Model calls only listed Tools can still call every Tool; the System Prompt keeps the pinned `tool:load_tools` list, and a load there still returns the definition and is recorded as usual. A fallback never re-pins, re-applies its own route gates or creates notes of its own. A schema-changed pinned Tool keeps its pinned bytes on every route; its note carries the new schema.
- **Epoch boundaries.** Notes of another epoch (after a Takeover, a cross-scope move or a lost pin) are dropped from the request (`without_other_epoch_tool_changes`) and ignored by the fold. Compaction's post-checkpoint projection builds with `fresh_prompt_epoch`, so the new pin lists every Tool offered then on the Run's primary route, also when the Compaction runs on a fallback target, except the On-demand Tools: those the Agent called in the ending epoch (`called_tool_names`, passed as `RequestBuildInputs.keep_listed_tools`: calls after the last checkpoint and the last Agent Takeover, except calls the Provider turn rejected and calls whose Tool Result, matched by `tool_call_id`, reports a refusal at dispatch or a call never started, such as `tool_not_allowed`, `tool_removed` or `tool_calls_disabled`; a call without a Result counts) stay in the Tool list, the others return to the `tool:load_tools` list; and the checkpoint commit writes it into its `PromptEpoch`, even when the rest of the prompt refresh failed, while the Projection drops the `[tool-change]` notes (`compaction.md`).
- **Temporary Sessions.** Every build measures the live catalog for the binding check: the capability Tools must be offered now, and the first request boundary announces any the pin lacks.
- **System Prompt.** Assembly receives the pinned definitions as `effective_tool_definitions` and the pin's On-demand Tools as `on_demand_tools`, so Tool-owned blocks and the opt-in `core:tools_list` describe the pin and stay byte-identical for the epoch: a pinned Tool that stops being ready keeps its block, and an announced Tool gets none until the next epoch (`prompts.md`). The texts of dynamic blocks are pinned separately (next section).
- Deferred MCP Tools remain outside the pin and definitions; their search, describe, and call results append through ordinary history. `ChatLoop.preview_tool_definitions` stays Agent-level and live and lists every Tool with its definition, so it leaves `load_tools` out; its file edit dialect follows the Agent's configured Model.

Regressions: `tests/core/chat/test_tool_epoch.py`, `test_chat_loop_tool_definitions.py`, `test_chat_loop_fallback.py`, `test_chat_loop_compaction_prompt_epoch.py`, `tests/core/compaction/test_compaction_engine.py`, `tests/resources/extensions/mcp/test_mcp_discovery.py`.

## Dynamic prompt blocks per prompt epoch

Chat pins the text, membership and layout positions of contributed Tool/Extension blocks (static and rendered), temporary Session blocks and `core:channels` for each prompt epoch. Reloading or disabling a contributor cannot edit that prefix; additions, changes and removals reach the Model as one `[prompt-block-change]` System Reminder at the next Run's start. `_prompt_block_epoch.py` owns pins and change planning; `RequestBuilder` resolves them; Prompts owns assembly; `RunExecution` persists the note with the input.

- **Pin.** `pinned_dynamic_blocks` holds `{v: 1, epoch, blocks: {<id>: {text, catalog?: {title, frame, entries: [[key, line], ...]}}}, order?: [<block id>, ...]}`. Lists preserve order through the Session store's sorted JSON objects. The pin is Agent-bound and immutable until Compaction. A pin without layout order predates static/temporary contribution pinning: its first use captures only those previously live contributions and the layout, retaining existing block texts and epoch identity. Newly visible rendered blocks and Channels still arrive through change notes. Change planning completes this inventory before comparison, so existing static contributions are not announced as additions. The first snapshot uses the pinned Tool catalog to evaluate owner gates; later builds pass `pinned_blocks=pin.texts()` and `pinned_block_order=pin.order`. Absent contributors are reconstructed from their snapshots, and newly live blocks are excluded. Empty text stays collapsed. Included-file read stamps are recorded only when the chosen snapshot contains the captured text, including newly adopted static contributions. Existing pinned blocks are skipped during adoption, so reading their live replacements cannot refresh stale-file guards.
- **Change note.** Both capture and change planning use the same scoped Skill registry, pinned Skill catalog and prompt-epoch effort as System Prompt assembly. Planning renders the complete current block inventory, including temporary Session blocks, and folds the epoch's previous notes into the pin to recover what the Model knows. Added blocks are announced whole; removed or emptied blocks as no longer applying. An empty `RenderedBlock` in the note records a removal and prevents repeat announcements; reappearance is announced again. A failed renderer leaves its last known state intact instead of pretending the block was removed. A catalog with unchanged title/frame is described by added, changed and removed entries; other changes carry the full current text. Payload `{v: 1, epoch, blocks, text}` stays unchanged.
- **Wording.** Catalogs use `{title} changed since your System Prompt listed them.` plus `Added:`, `Changed to:` and `Removed:` entry groups. Other changes use `The "{section}" section of your System Prompt changed. Use this current version instead:` plus the text; removals use `The "{section}" section of your System Prompt no longer applies.`; additions use `This section now applies in addition to your System Prompt:` plus the text. These tell the Model which earlier guidance or available context to replace without editing history. Section names use the Markdown heading, else the first line cut to 80 characters. Built-in catalog titles are `The Agent ids under Sub-Agents` and `Your configured channels`. Project choices are a Tool-definition change (`tools/project.md`), not a prompt-block catalog.
- **Epoch boundaries.** Compaction's projected request captures a fresh inventory, including temporary Session contributions; the checkpoint commits it with the other prompt pins even if the broader refresh failed. Notes from another epoch are excluded from requests and change planning. Agent-level `prompt.preview` renders live. Concurrent first requests reuse the winning pin; they never merge late blocks into it.
- **Permission rules.** A restricted Run adds the request block `core:permissions` (`_run_permissions.py::permissions_prompt_block`, owner `always`, rank 10000, so it sorts after the layout's blocks) to the temporary Session blocks; it is pinned like them, so a rule change mid-epoch keeps the System Prompt byte-identical and arrives as one `[prompt-block-change]` note. Full access renders nothing. It is not a layout block and `prompt.preview` does not show it. Text rows: `agent-facing-text.md`.

Regressions: `test_prompt_block_epoch.py`, `test_chat_prompt.py::test_dynamic_blocks_stay_pinned_and_each_change_is_announced_once`, `test_chat_run_permissions.py::test_the_permissions_block_is_pinned_and_a_change_is_announced_once`, `test_chat_loop_compaction_prompt_epoch.py`, and `tests/core/prompts/test_prompts_assembly.py::test_dynamic_block_membership_and_position_stay_pinned_after_reload`.

## Thinking effort per prompt epoch

The runtime block shows the Agent's thinking effort (`prompts/core-blocks.md` -> Runtime variables). So that an effort change keeps the System Prompt byte-identical, Chat pins the effort per prompt epoch and carries changes as notes; the Model is not told about a change (user decision 2026-10-11: a stale effort line until the next Compaction is acceptable). `core/chat/_effort_epoch.py` owns the pure model (`EffortPin`, `EffortChange`, `EffortState`); `RequestBuilder.build_request_state` resolves the pin; `_agentic_progression.py` plans the change at the request boundary; `wire_shaping.route_effort` decides what reaches the Adapter.

- **Pin.** The Session prompt pin `pinned_thinking_effort` (`{v: 1, epoch, effort}`, Agent-bound like the other pins) holds the canonical effort (`""` = provider default) of the epoch's first request and a random epoch key. `build_system_prompt(thinking_effort=pin.effort)` renders it. A fresh epoch (Compaction's projection) pins `RequestBuildInputs.fresh_thinking_effort`, the effort the ending epoch's requests used last; any other build without a readable pin pins the Agent's effort (`ensure_effort_pin`).
- **Change note.** At every request boundary, before the write lock, the boundary reads the live effort: the Run's admitted Agent at its first request, a fresh resolve (`resolve_run_agent`, Session overrides included) at later ones; a failed resolve keeps the current effort. `EffortState.plan` compares it with the state folded from the pin and this epoch's notes; a difference becomes one `[effort-change]` note (`{"v":1,"epoch","effort"}`) that the same request adopts. A change between Runs takes effect at the next Run's first request; a change during a Run at its next request, except one to or from `none` or the provider default (`""`), which waits for the next Run, because turning Reasoning on or off inside a Tool loop is rejected or ignored by Models.
- **Request effort.** `RequestState.effort` (`EffortState`) carries `pin` and `current`; `send_assistant_request` passes it to `route_effort`. Each note renders as a request-only `effort_update` message at its place in the history (`wire_shaping.note_request_messages`). A route whose Adapter reports `effort_updates(model_id)` keeps the messages and gets `thinking_effort=current` plus `effort_base=pin.effort`; the Adapter then sends the epoch's effort as the request effort and each change in place, so the cached prefix survives (`providers/request-policy.md` -> Effort updates). Every other route (fallbacks without support, Chat Completions, local wires) gets the messages stripped and `thinking_effort=current`, which changes the request's top-level effort and therefore costs that Provider's cache once.
- **Epoch boundaries.** Notes of another epoch are dropped from the request (`without_other_epoch_effort_changes`) and ignored by the fold. Compaction's checkpoint commit writes the new pin into its `PromptEpoch`, and the Projection drops the `[effort-change]` notes (`compaction.md`).
- **Tool dispatch.** Tools receive the actual request's Model and current effort (`ToolDispatchContext.agent`), including on a fallback route, so a Sub-Agent self-delegation inherits them independently of later Session/default edits.
- **Known limits.** Extension `context` hooks see the `effort_update` dicts in the request messages. Agent-level `prompt.preview` renders the live effort.

## Agent-facing text

Reply-surface reminders are rendered by `ReplySurface.reminder_text` in `core/chat/messages.py`, folder instruction reminders by `FolderInstructionsNote.reminder_text` (Folder instructions above). Their existing chronology is described under Canonical roles and request visibility; group authority rules remain in the Channels System Prompt block (`prompts/core-blocks.md` -> `core:channels`).

| Text | Reason |
|---|---|
| `Reply surface: WebUI/Desktop.` | Identifies the destination when a Session switches from a Channel, so earlier Channel delivery guidance does not keep defining the reply. |
| `To show an image or provide a file download, include file:<filesystem-path> in your reply; vBot renders it automatically.` | Gives the marker the WebUI/Desktop renderer recognizes; an unmarked path does not render an image or download. |
| `Reply surface: terminal TUI. Markdown and code are displayed as text; images, HTML previews, audio and video are not embedded. To provide a file download, include file:<filesystem-path> in your reply.` | Describes terminal capabilities so a Session returning from WebUI or a Channel gives usable text and download references. |
| `Reply surface: <platform> ...` with the conversation kind and `Channel` id | Tells the Agent which platform and direct/group conversation receives the reply, including after a surface switch. |
| `vBot delivers your final text automatically.` | Prevents a duplicate send of an ordinary text reply; the Agent does not need an outbound Tool call for it. |
| ``Folder instructions for `<folder>/` from `<file>`.`` (`FolderInstructionsNote.reminder_text`, `core/chat/_folder_instructions.py`) | Names the scope of a file that arrives mid-Session, so the Agent applies it to that folder and below, not to the whole repository. |
| `They apply to work in that folder and below; where they conflict with your Project Context or the instructions of an enclosing folder, follow them.` | Settles conflicts the way nested `AGENTS.md` files are written for: the nearer file wins over the main instruction file and over an outer folder's file. |
| `Ordinary replies do not attach files.` | Prevents reusing WebUI file markers as Channel attachments. File-send instructions belong to the available Tool definition, not to a reminder that also reaches Agents without that Tool. |
