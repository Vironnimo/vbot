# Chat Request Building

Task-gated reference for turning canonical Session history into one provider-ready request. Read this when changing message rendering, notes, Skills, the prompt-epoch Tool list and Tool-change announcements, pinned dynamic prompt blocks and their change notes, Content Blocks, Compaction-tail reconstruction, reasoning replay, or Tool-cycle repair; it is not required for unrelated Chat work.

## Pipeline and ownership

Prompt assembly and Tool-definition profiling use the Prompt pool; canonical Compaction projection, note embedding, Skill-context restoration, Tool-contract compilation, attachment/media scans, and token estimates use Chat's bounded transform pool. These synchronous transformations finish before the request crosses the async Provider boundary and never consume Event-Loop time proportional to Session size.

`core/chat/messages.py` owns canonical records/round-trip, with `_message_validation.py` for role/payload checks and `_message_history.py` for effective-history projection; `core/chat/wire_shaping.py` turns that history into one provider-ready request (assembly, notes, replay policy shaping, tool-cycle repair) and ingests normalized responses back into canonical messages; `core/chat/_request_builder.py::RequestBuilder.build_request_state` coordinates the build using request-only history helpers in `_request_history.py`; `core/chat/block_resolver.py` resolves attachment-backed content; `core/chat/file_mentions.py` snapshots and renders `@` mentions; `core/chat/tool_dispatch.py` owns dispatch, while `_skill_activation.py` owns deterministic Skill activation. Provider adapters receive normalized request messages and definitions only. They own wire translation, while `core/sessions/` remains the persistence owner and `core/compaction/` owns checkpoint policy and Projection creation.

Each provider request is assembled from one loaded canonical Session snapshot. Chat first resolves the prompt epoch's Tool pin (Tool catalog per prompt epoch below); only a request without a readable pin derives Session-scoped Tool grants, obtains the allowed/ready configuration-profiled Tool definitions and applies effective Model-route gates to pin them. The request's Tool list is the pin, the dispatch allowlist and request-state Tool contracts follow the pin plus the Tool changes announced since, Chat passes the pinned Tool names into System Prompt assembly, and only then shapes message history. The same contract mapping crosses `ToolDispatchContext`/`ToolExecutionConfig` into each `ToolContext`, so dispatch and lifecycle fingerprints use the exact schema the Model was last told for each Tool - the pinned definition after every profile, Sub-Agent target, Bash nesting-depth, and route projection, or the definition a `[tool-change]` note announced; handlers retain their canonical semantic checks. This mapping is internal Run state and never changes Provider bytes. The `analyze_image` route gate also accepts an explicit Agent vision grant; binding/wire availability and ordinary permissions still apply (canonical contract: `tools/image.md`). The file edit route gate (`offer_edit_dialect`) keeps one dialect: `apply_patch` for a GPT-family Model, `edit` plus `write` otherwise (`tools/edit.md`). The System Prompt is assembled whole by `SystemPromptManager`; it is never appended to Session history, and an empty/whitespace prompt is omitted from the provider request.

When a Compaction checkpoint exists, its canonical Projection replaces compacted history. If that Projection omitted the newest complete, unconsumed Assistant Tool-call batch, `_overlay_pending_tool_batch` adds the canonical batch at its chronological position - after the Projection, before messages appended after the checkpoint such as steered User input - until a later Assistant turn consumes it. The checkpoint ended every Skill activation, so a restored Skill-loading Result is the same instruction-free digest a retained one gets; otherwise the raw instructions of a failed Run's Skill load would return after every checkpoint. Checkpoints themselves are never sent directly. Auto-compaction rebuilds and the live path both flow through the same note embedding and dangling-Tool repair.

## Canonical roles and request visibility

- `system`, `user`, `assistant`, and `tool` map to provider-visible conversation roles after shaping. Only `user` may persist `list[ContentBlock]`; other content is string-or-null according to the `ChatMessage` validator. Assistant `output_files` is canonical presentation metadata and is removed from both ordinary history requests and current-turn Tool continuations.
- `note` is a kernel-internal persistence role. Public history filters it. Ordinary notes become synthetic user messages containing `<system-reminder>` blocks; consecutive notes are grouped, and notes created during a Tool cycle are delayed until all sibling Tool Results have been persisted so they never split the cycle.
- `[skill-context] ` notes are the exception to ordinary note rendering: they become chronological standalone `<skill_content>` user messages. A Skill loaded through the `skill` Tool has no such note because its structured Tool Result already carries the raw instructions and optional resource/environment metadata; Sessions reconstructs the equivalent internal wrapped context only when Compaction replay needs it.
- `[tool-change] ` notes store a JSON payload (`core/chat/_tool_epoch.py::ToolChange`: epoch key, `added`/`removed`/`changed`, registry Tool name, source fingerprint, definition, `listed`, `pinned`, optional `detail`). They render as ordinary System Reminders whose text `render_tool_change` builds at request time with the Model-facing Tool name (`powershell` for `bash` on Windows), because `model_facing_request` renames only definitions, calls and Tool messages, never reminder text. An unlisted addition and a `changed` note carry the definition's description and its compact JSON Schema (`separators=(",", ":")`, key order kept), and a `changed` note with `detail` puts it on a `Change: <detail>` line before them. Only a `changed` note of a pinned Tool says the Tool list still shows the previous definition; a changed announced Tool is just told to be called with the new one; a malformed payload is dropped from the request like a malformed Skill note.
- `[prompt-block-change] ` notes store a JSON payload (`core/chat/_prompt_block_epoch.py::PromptBlockChange`: epoch key, the changed blocks' new state, reminder `text`) and render as ordinary System Reminders carrying `text`; a malformed payload is dropped from the request (Dynamic prompt blocks per prompt epoch below).
- `[channel-message] ` notes are coalesced into a separate untrusted-background user message, not a System Reminder. Stored records are JSON-quoted and escape control characters plus angle brackets so channel participants cannot break or impersonate the wrapper.
- `[reply-surface] ` notes record WebUI/Desktop or Channel identity in append-only Session chronology. The WebUI/Desktop reminder is the single Model instruction for output files: `To show the user an image or provide a file download, include file:<filesystem-path> in your reply; vBot renders it automatically.` A Channel identity includes platform, configured Channel id, and `direct`/`group` conversation kind; its reminder still requires `channel_send` for files because external platform delivery is an outbound action. At executor start Chat appends one only for the first surface, a surface change, or the first interactive Run after a newer checkpoint; the tag is stripped and the model sees a turn-bounded System Reminder. Runs without a supplied surface do not change this state.
- `run_summary` and `agent_takeover` remain visible history annotations. An `agent_takeover` never enters provider requests; a `run_summary` enters only as its interruption notice (below). `error` enters later requests only when `error_kind_llm_visible` allows it, as a System Reminder whose text is JSON-quoted as `{"run_error": ...}` with angle brackets escaped, because it can carry raw Provider payloads; portable reasoning and channel quotes use the same `_quote_external_json` helper. A cancelled, interrupted, or failed `run_summary` without a complete answer renders its interruption notice as a System Reminder instead (`chat/run-execution.md` -> Interruption). `compaction_checkpoint` contributes through its Projection, not as a role.
- Real `<system-reminder>` tags reach the Model only from Chat's own reminders. Note and Model-visible error runs, interruption notices and Compaction's instruction reminder render through `wire_shaping.system_reminder_request_message`, which neutralizes look-alike tags inside each body and marks the content with the private `_SystemReminderContent` str type. The final projection `model_facing_request` then rewrites the `<` of every other look-alike tag to `&lt;` (any case, whitespace inside the tag or around the slash, attributes; the rule is `core/providers/_tool_result_text.py::neutralize_system_reminder_tags`) in user text and text blocks (attachments, mentions, Skill-context carriers, channel quotes), Assistant `content` and readable `reasoning`, and Tool `tool_result_content` text blocks; Provider wires neutralize the rendered Tool Result body (`providers/request-policy.md`) and the readable text they replay from `reasoning_meta`: every Responses wire (`github_copilot_responses._replay_item`: `output_text` of `message` items, `summary_text` and `reasoning_text` of `reasoning` items) and Gemini text parts without a `thoughtSignature` (`_opencode_zen_gemini._replay_part`). System messages, signed or encrypted replay state (Responses `encrypted_content` and ids, signed Gemini parts, Anthropic thinking signatures), Chat Completions `reasoning_details`, Tool Call arguments and native media or document blocks are never changed. The rewrite is request-only, deterministic and idempotent: Session history, Run events and Extension hooks keep the original text, and replayed history keeps its prompt-cache prefix. Content rewritten after rendering, including by an Extension `context` hook, loses the mark and is neutralized, so no hook or producer can add a real tag. Coverage: `test_wire_shaping_requests.py`; replay: `tests/core/providers/test_adapter_tools.py`, `test_opencode_zen_gemini.py`.
- User `sender` attribution is rendered only while building the provider request as `[display_name|platform_user_id|role]`, where `role` is the persisted immutable `admin`/`member` snapshot. All attribution parts are sanitized before insertion. `input_origin` appends a hidden System Reminder immediately before the unchanged visible user message: `speech_transcription` (dictated) says the text may contain transcription errors, `live_voice` (passed on by the Live operator) says it may contain speech recognition errors or the voice assistant's rewording. The origin persists on the User message (`ChatMessage.input_origin`), so the WebUI labels Live voice messages ("You · via Live").

## Reasoning replay

The system default `ReasoningReplayPolicy` is `full_history`; an optional Provider override and then an optional Model override can narrow or replace it (`providers/request-policy.md` owns the hierarchy). The effective policy governs native `reasoning`/`reasoning_meta` replay; Chat owns history shaping and never interprets `reasoning_meta`. `none` strips native readable and opaque reasoning everywhere; `current_run` preserves it only across Tool continuation inside the active Run; `tool_turns` applies `full_history` only to Assistant turns with Tool Calls, so an answer turn never carries native reasoning, neither as live continuation nor in later Runs; `full_history` replays persisted native reasoning when the Assistant's internal `reasoning_scope` exactly matches the current resolved Provider/Model/Connection/Account scope. Across a mismatched route, Chat always strips both native fields and may project only non-empty readable `reasoning` from a completed reasoning-only or Tool-associated Assistant turn as an escaped, request-only provider-neutral System Reminder after its Tool batch. It never projects `reasoning_meta`, scope identity, empty/meta-only state, interrupted work, or ordinary answer-turn reasoning; this avoids both opaque-state leakage and duplicate answer context. An `interrupted` Assistant turn is a hard native-reasoning boundary regardless of policy or matching scope: canonical persistence retains its readable and opaque fields, but request shaping removes both `reasoning` and `reasoning_meta`; the provider-neutral Continuation reminder is the only replay channel for its readable work. `reasoning_scope` is persisted only on reasoning-bearing Assistant messages and is always removed before the provider request. Every policy except `current_run` decides per message alone, so the bytes a request sends for a message never change in a later request and the Provider prompt cache keeps its prefix; `current_run` strips a finished Run's reasoning in the next Run and breaks the cache there whenever the Provider rendered that reasoning (test: `tests/core/chat/test_chat_loop_reasoning_replay.py`).

The current Assistant turn is appended through `_assistant_continuation_dict`, which strips `usage` and `reasoning_scope` but preserves policy-permitted reasoning; an interrupted partial loses native `reasoning` and `reasoning_meta` in its same-Run continuation request too, and an entry left without content, Tool Calls, or reasoning is not sent. Every mid-Run rebuild (steering, textual Compaction projection, stale-Compaction recovery, Model fallback) goes through `RequestBuilder.rebuild_live_request_state`, which restores live reasoning by retained message id plus Run-local Tool media; fallback then strips native reasoning. The Summary+Tail planner budgets these live fields before selecting whole retained steps. It never restores omitted Assistant messages, and ordinary retained Tool arguments/results remain unchanged so Responses `response_output` replay cannot undo a payload edit; the persisted checkpoint Projection keeps the Tail's `reasoning`, `reasoning_meta`, and `reasoning_scope`, so later Runs shape the Tail under the same policy and scope rules as any history and resend it unchanged. Assistant `phase` remains because it is semantic history required by Responses Models, not opaque provider state.

When run-local Model fallback begins, Chat rebuilds request state with the fallback target's replay policy, exact reasoning scope, input modalities and wire media support, plus the epoch's Tool list with every announced addition (Tool catalog per prompt epoch below), then strips prior Assistant native reasoning/reasoning metadata before the first fallback request regardless of the primary policy. Completed reasoning-only or Tool-associated readable work follows the same bounded provider-neutral projection rule and is placed after the associated Tool Results; opaque primary state never reaches the fallback. Every Assistant message produced by the fallback persists the fallback binding as its `model`, and any reasoning is persisted with the fallback scope even though the Agent's configured primary Model remains unchanged, so a later primary Run cannot inherit its native state.

## Skills and prompt-cache stability

Announcement planning and successful Compaction prompt refresh require `SkillRegistry.filter_allowed`; an empty catalog is a valid empty baseline.

Pure-text `/skill-name` at the start and `$skill-name` anywhere are deterministic Skill activation hints; `$` never routes to a built-in command. The original user message stays unchanged. Only allowed, loadable, currently available Skills activate. An identical name+content activation deduplicates within the current Compaction epoch, while committing a changed package permits the same Skill name to activate again and keeps latest content. A committed checkpoint removes full trigger carriers and compacts loading `skill` Tool Results from its Projection, then adds one names-only reminder for activations since the preceding checkpoint; the instructions and Skill environment grants are inactive until the Model explicitly reloads a still-relevant Skill. Aborted Compaction changes nothing, and a later checkpoint never carries the prior names reminder forward.

`pinned_skill_catalog` (`core/prompts/pinned_context.py`) snapshots the rendered Skill catalog text as a Session prompt pin on the first build of a Session or prompt epoch. Later requests reuse that exact text for prefix stability until successful Compaction; the post-checkpoint refresh forces a complete Skill rescan, renders a replacement catalog, and replaces the Session's seen-Skill set in the checkpoint's transaction, so additions/removals/metadata or requirement changes appear without redundant announcements. A newly available+allowed Skill between Compactions does not rewrite the catalog; `_plan_skill_announcement` compares the Run's resolved registry with the stored seen-Skill set and plans a one-time System Reminder note instead (a Session without a recorded set records the current catalog as its baseline, with no note). The note and its seen-Skill update commit in the same write as the Run's input, so a Skill is marked seen exactly when its announcement persists. The admitted Working Project supplies Project Skills while an Identity Agent retains its private Skill layer; Config Agents remain under Project ceilings. Skill activation carriers remain canonical conversation Context and are not part of this System Prompt refresh.

The same epoch-pinning covers every other file-backed System Prompt input: the rendered SOUL block (`pinned_soul_context`) and the rendered pinned-memory files (`pinned_memory_files`) for Identity Agents, and the Working Project frame for Rooted Identity Agents and Project Config Agents alike (`pinned_working_project_context`). On-disk changes to `SOUL.md`, `MEMORY.md`/`USER.md`, or Project auto-load files therefore cannot alter the System Prompt prefix mid-epoch; they become visible only when a successful Compaction starts the next prompt epoch and re-renders all snapshots (an aborted/failed Compaction changes nothing). Read-before-write stamping happens at snapshot/refresh time only, never on reuse.

## Rooted and Config-Agent Working Project Context

`core:working_project` renders the file-backed `working_project.md` template from the admitted Project's id, display name, absolute Project Workspace, and readable auto-load files. Both a Rooted Identity Agent (via its selected Project) and a Project Config Agent (via its addressed Project) receive that frame as the prompt-epoch snapshot `pinned_working_project_context`: rendered before the first provider request of an epoch, stored as a Session prompt pin, and supplied verbatim until successful Compaction rebuilds it from the current Project, auto-load list, and readable file contents; an explicit `project` Tool call still cannot replace the automatic frame. An Unrooted Identity Agent has no Working Project block and no pin. This pins only the automatic Working Project block; the explicit `project` Tool retains its ordinary persisted Tool result, and every non-file System Prompt input keeps its existing lifecycle. Prompt preview renders a prospective Rooted Identity frame without persisting it and a live Project Config frame from the addressed Project.

## Content Blocks, mentions, and media

`core/chat/content_blocks.py` owns `TextBlock`, `MediaBlock`, `FileBlock`, and `FileMentionBlock` plus JSON round-trip. On admission, Chat assigns every incoming image a positive `image_reference` continuing from the Session's persisted images; this durable reference renders as `Image 1`, never as a made-up filename or a storage path. `core/chat/file_mentions.py` lists cwd files for autocomplete (honoring `.gitignore`; never entering directory links, Windows junctions included) and expands verified mentioned paths into immutable snapshots before Run admission. A `FileMentionBlock` records `path`, `status`, `text`, and `size_bytes`; request rendering always identifies it as a user-supplied file snapshot. Auto-injected Project files and expanded mentions are stamped into `runtime.file_read_state` so later full-file `write` Calls satisfy read-before-write without duplicating a read.

`ContentBlockResolver` performs provider-agnostic last-mile media routing by intersecting the Model's input modalities with `ProviderAdapter.wire_media_support(model_id)`. Every turn resolves the same way, earlier turns included, so the request prefix stays byte-identical from Run to Run: a supported image/audio/PDF/video becomes a native block followed by a path note. For images, the shared Attachment ImageConverter can first convert an unsupported source format to PNG, lossless WebP, or high-quality JPEG selected from the actual target Adapter declaration; all images are validated, and accepted originals remain byte-identical when within the effective byte ceiling. Chat passes the smaller of the configured Attachment limit and a known Adapter per-image limit. Preparation first preserves full resolution; when required by that ceiling it can lower JPEG quality or resize, and the path note states the sent dimensions and lossy compression. Original blobs and filenames stay unchanged. Invalid images, decoding-limit failures, and multi-frame inputs needing conversion become actionable path notes. The converted base64 payload is subject to the same request image budget. Unsupported or otherwise non-native media degrades to an explanatory path note; audio may first use Speech-to-Text on its own turn. Text files carry the bounded rendering used by the `read` Tool. A missing attachment record degrades to a "file no longer available" note, because the turn stays in every later request; only other stored-blob I/O failure aborts the Run; capability mismatch degrades. Attachment metadata, blob reads, and text renders run on the `chat-attachments` worker pool: all earlier turns resolve in one hop, and the current turn reads its files there before image conversion or Speech-to-Text continue on the Event Loop.

Per-modality degrade policy:

- **Image** - native base64 when the model has `"image"` and the image type is in the wire set. An image to a non-vision model degrades to an `[Image: ... - this model has no vision capability ... - Path: ...]` note instead of aborting; a vision model whose wire cannot carry the type first tries the shared format converter. If conversion is unavailable or fails, it degrades to an `[Image: ...]` path note; a missing record degrades to a "file no longer available" note. The native image rides with an `[Image: ...]` path note as well, so the agent always holds the file path, not only the pixels.
- **Audio** - a cached `transcription` always wins (no STT call). Otherwise audio goes native base64 only when the model has `"audio"` **and** the media type is in the adapter's wire set (WAV/MP3 on OpenAI-compatible wires; image-only adapters carry no audio, so audio degrades even for an audio-capable model). Everything else - including Ogg voice messages - degrades on its own turn to speech-to-text with an "automatic transcription, may contain recognition errors" header (cached via `set_transcription()`, cache-write failures logged). No transcriber, an STT failure, or an empty result degrades to an `[Audio: ... - Path: ...]` path note (logged, run never aborts). Speech-to-text never runs again for an earlier turn: without a cached transcription it keeps that path note in every later request. Native audio and transcription replies both carry a trailing `[Audio: ...]` path note too.
- **Document** - a PDF (`application/pdf` -> `pdf` modality; other files -> `file` modality) goes native as the canonical `{"type":"document",base64,media_type,filename}` block when the model advertises the modality **and** the wire carries the type (today: OpenAI chat mode, Anthropic); otherwise it stays the `[File: <name> (<type>) - Path: <file_path>]` path note. The native document rides with that path note as well. A `text/*` file is never native: the resolver renders it through the read tool's bounded text view.
- **Video** - native base64 only when the model has `"video"` and the wire carries the type; otherwise a `[Video: ...]` path note. An unexpected media prefix degrades to a `[Media: ... - Path: ...]` path note rather than aborting the run.

A Tool may return a `read_media` artifact. The persisted Tool Result keeps the compact Attachment reference inside its normal envelope; Chat resolves it for every request until Compaction compacts the Tool Result, and adds the resulting media/path blocks under the request-only `tool_result_content` field of the correlated Tool message. Attachment and mid-Run restore correlate by Tool message identity, never by Tool-call id alone, because some Providers reuse ids such as `tool_call_0` in every response. Anthropic-style Messages and Responses wires render those blocks natively inside `tool_result` / `function_call_output`; text-only Tool wires retain text on the Tool Result and add one request-only media fallback after the complete sibling Result batch. No synthetic user message enters Session history and base64 never persists. A non-capable Model receives a path note instead of native media. Full modality behavior belongs in `attachments.md`; Tool-side artifact production belongs in the relevant Tool reference.

Tools that load pixels in memory (`read`, computer use) hand them to Tool dispatch through `ToolContext.result_media`, which delivers them with failed Results too (computer use shows the screen a failed input step left; `test_media_outputs_are_read_media_artifacts_and_loaded_pixels`). Right after dispatch, before the Tool Results persist, `RequestBuilder.store_tool_media` stores each loaded image as an Attachment blob and records `{attachment_id, filename, media_type}` references in the Tool message's internal `tool_media` field (persisted in `tool_call_payloads.media_json`, stripped from every wire). From then on the image resolves like a `read_media` artifact in every request, including the first one after the call and later Runs, with a path note naming the stored blob. Re-reading an overwritten path stores new pixels under the new Tool message while earlier Results keep their own copies (`test_rereading_overwritten_image_delivers_each_calls_own_pixels`). If storing fails, the image stays an in-memory item for the current Run only: `ContentBlockResolver.resolve_tool_image` routes and converts those bytes without file I/O, in-Run Compaction restores them, and Model fallback re-prepares them for the new route. Stored Tool images accumulate in the Attachment store; no garbage collection exists yet.

Assistant output-file references are distinct from input Content Blocks and Attachments. `core/chat/output_files.py` scans ordinary Assistant text outside fenced and indented code for `file:<filesystem-path>` tokens, which may appear around prose or alongside other markers. The path begins immediately after `file:` and ends at whitespace; it may be absolute or relative to the working Project cwd or otherwise the Agent workspace, but paths containing whitespace are intentionally outside this compact grammar. Exact existing filenames win first, after which common sentence-closing punctuation may be peeled from the token so surrounding prose remains intact. A single backtick pair around the complete marker is accepted and included in its span, while fenced and indented code remains inert. Each valid existing regular file produces an internal absolute path plus exact line/start/end span, so server projection replaces only the marker while preserving surrounding text. Unmarked paths, missing paths, directories, and URLs remain ordinary text. The original reply text remains canonical; server public projection consumes the internal reference, while Provider shaping always removes it.

`wire_shaping.RequestImageBudget` decides which native images a request still carries, independently of token Compaction. Every image, user or Tool, stays in every request until a Provider limit forces room; vBot sets no limit of its own (user decision 2026-10-04). Limits come only from the route: `ProviderAdapter.request_image_limit(model_id)` (documented image count, carried as `_ModelTarget.max_request_images`) and body-size rejections (below). Chat acknowledges the exact sent image identities and payload hashes only after a completed, non-interrupted, accepted Model response; failed or partial attempts do not make fresh images eligible for retirement. Images already in the history when the Run starts count as delivered; images of the current user turn and new Tool images are fresh. A changed payload at the same address must be delivered again; hashes retain no pixels.

When a request holds more images than the route's image limit, the oldest delivered images retire until at most half the limit remain (fewer only when fresh images alone exceed half), so retirements stay rare and the request prefix before the oldest retired image stays cached. Each retired image becomes a fixed, path-preserving explanatory text block; Tool envelopes, sibling order, Assistant findings, original files, and canonical history stay unchanged. Retirement is keyed by image address `(role, message id, block index)` and persists per Session in the prompt pin `pinned_image_retirement`: a Run restores it on its first request build and writes new retirements after each accepted response, so later Runs render the same notes. Compaction starts the new prompt epoch without it, and an automatic Compaction also resets the Run's budget. Speculative projections (`remember=False`) do not commit retirement. Re-reading an original creates a fresh image at a new message identity.

A Provider wire raises `ProviderRequestTooLargeError` before I/O when the serialized request exceeds its declared `request_body_limit`, and any HTTP 413 answer raises it without sizes (`providers/request-policy.md`). Chat then calls `RequestImageBudget.shrink`, which retires the oldest delivered images until the image data takes at most half the known limit (half the current image data when the limit is unknown), at least one per rejection, and rebuilds the request without rerunning Tools, context hooks, or counting another Iteration. When no delivered image remains, the concrete size error surfaces. Regressions: exact wire bytes in `tests/core/providers/test_ollama_cloud.py` and `test_anthropic_requests.py`; in `tests/core/chat/test_chat_integration_images.py` count and body pressure with request rebuilds and a following Run (`test_long_mixed_image_run_keeps_images_and_can_reopen_originals`) and a streaming rejection (`test_provider_body_overflow_preserves_fresh_inputs_and_stops_without_retry`).

If fresh images alone exceed the route's image limit, `ImageBudgetExceededError` ends the Run with the count and limit before a Model request, rather than discarding unseen pixels. The same projection runs during initial and rebuilt resolution, after context hooks before sending, on live Tool continuations before Compaction, and after rich-content restoration. Session history retains the fresh inputs and correlated Tool Results even when this check fails. Regressions: `tests/core/chat/test_wire_shaping_image_budget.py` and the fresh-user/fresh-Tool overflow scenarios in `tests/core/chat/test_chat_integration_images.py`.

## Tool-cycle invariant and repair

Every Assistant request entry with `tool_calls` must be followed by exactly one Tool Result for each `tool_call_id`, in Assistant-declared order, before any non-Tool message. Sibling calls execute concurrently by default within shared limits unless an explicit serial barrier applies; Session persistence and provider request history always retain the declared order.

If loaded history is missing a Result because a Run was cancelled, crashed, or was interrupted before persistence, `_repair_dangling_tool_calls` creates request-only `result_unavailable` failure envelopes for the missing calls. It never mutates canonical Session history. Cancel during dispatch likewise cannot discard Results already computed: all sibling Result Messages persist before the Run honors cancellation.

Assistant Tool Calls carry the canonical arguments Provider intake produced: plain JSON with recursively sorted object keys, the same form the Session store persists (`providers.md`). The in-Run follow-up, the next Run's history, a fork and Compaction therefore send byte-identical Tool cycles and keep the Provider prompt-cache prefix (`test_tool_time_note_follows_the_results_in_history_and_requests`).

After Chat completes canonical history shaping and dangling-cycle repair, an Adapter with an explicit target-wire Tool-call-id profile may normalize paired call/result ids for its wire on a copy-on-write request view. This transform is Provider-owned, request-only, and correlation-scoped to each Assistant batch; it never changes the canonical ids persisted in the Session or reused by Chat events.

## Tool catalog per prompt epoch

Within one prompt epoch every request sends the same Tool list, so the Provider prompt cache survives Tool changes; a change reaches the Model as a `[tool-change]` System Reminder, and dispatch follows what those reminders told it. `core/chat/_tool_epoch.py` owns the pure model; `RequestBuilder` (`build_request_state`, `live_tool_catalog`, `announce_tool_changes`) owns resolution and persistence. Work that grows with the Session or the Tool count runs on Chat transform workers, off the Event Loop: reading, parsing and starting the pin, folding the history's notes, and the catalog's readiness checks and fingerprints.

- **Pin.** The Session prompt pin `pinned_tool_definitions` (`ToolEpochPin` payload `{v: 2, epoch, definitions, sources}`) holds the exact post-route Provider definitions of an epoch's first request under registry names, a random epoch key, and a fingerprint of each Tool's registered pre-route definition. `definitions` is one compact JSON string that keeps each definition's key order, because the Session store sorts the keys of stored JSON objects; the pinning request already sends the definitions as they read back, so `tools[]` is byte-identical on every request of the epoch, across Runs and restarts (`tests/core/chat/test_chat_loop_tool_definitions.py`, `test_chat_loop_compaction_prompt_epoch.py`). A request without a readable pin (the Session's first, an unreadable or other-version payload) pins the Tools offered now - allowed, ready and route-gated for the Run's primary route (`RequestBuildInputs.tool_route_*`; `tool_route_model_family` is the primary target's Model family from the Model catalog, `_ModelTarget.model_family`, empty when unknown), even while a fallback target serves the request - through `ensure_prompt_pin`, so a concurrent first request's readable pin wins. Chat resolves this slot itself; it is not a System Prompt input. It is Agent-bound and does not survive a cross-scope fork, move or Takeover (`sessions.md` -> Prompt state). A Model change mid-epoch never re-pins.
- **When changes are measured.** In the locked request-boundary block of `_agentic_progression.py`, after background-completion delivery and before pending notes drain: at the first boundary of every Run, after a steering rebuild, and whenever `(ToolRegistry.revision, pin epoch)` differs from the last evaluation; never on a finalization-only cycle. A readiness flip alone bumps no revision and is therefore seen at the next Run or registry change. `LiveToolCatalog` is measured on the Run's primary target, never a fallback: `usable` (allowed, ready or not), `offered` (ready and route-gated), registered-definition fingerprints and current Session grants. `ToolEpochView.plan` compares it with what the Model knows - the pin folded with this epoch's notes from the loaded history - and each planned change becomes one note that the same request already adopts. Notes therefore follow the User input or the complete sibling Tool Result batch.
- **Change rules.** *Removed:* a Tool the Model may call that is no longer usable (unregistered, policy or grant withdrawn). Readiness never removes a known Tool (dispatch answers `tool_not_ready`), and a route gate never removes one; `analyze_image` counts as removed only when the Model knows it, the route gate hides it and no image-understanding backend is available. *Added:* a Tool the Model may not call, once usable, ready and route-gated - a pinned Tool announced as removed becomes available again (`pinned`, listed); any other Tool is announced with its definition, including one that was not ready when the epoch started. *File edit dialect:* fixed for the epoch. The live catalog takes it from the Tools the Model was told about (`ToolEpochView.known_names`: the pin plus every announced Tool, removed ones included; `known_edit_dialect`); only an epoch that knows no file edit Tool picks it by the primary route's Model family. A Model change mid-epoch therefore neither offers nor announces the other dialect (`test_a_model_change_keeps_the_file_edit_tools_of_the_prompt_epoch`). *Changed:* a known Tool whose registered fingerprint and `parameters` both changed; a change that keeps the parameters (description only) stays silent unless the Tool's `definition_change_note` (`tools.md`) returns text, which the note carries as `detail`, as it does on a schema change.
- **Dispatch.** `ToolEpochView.allowed_names` (pinned plus announced additions, minus announced removals) is the request-state allowlist; contracts compile from the definition each Tool was last announced with, except for a Tool no longer registered (deleted by an update, its Extension unloaded): it gets no contract, since only its registration says whether its schema may stay open, and the next request boundary announces it as removed (`test_an_announced_tool_removed_again_fails_as_removed_under_its_own_name`). Announced names count as offered for Called Tool name resolution; `removed_names` count as registered there and reach `ToolDispatchContext.removed_tool_names`, which fails their calls with `tool_removed` (`tools.md`). The file edit Tools count as one permission: `tool_dispatch._dispatch_allowed_tools` adds the policy-allowed siblings of an allowed one (`edit_tool_siblings`), and a Run Tool restriction naming one admits all three, so a call to the dialect the route did not offer runs under that Tool's registered contract instead of failing (`test_tool_dispatch.py::test_file_edit_tools_share_one_permission_whichever_the_route_offered`).
- **Request Tool list.** Always the pinned bytes, also on finalization requests after Chat disabled Tool execution for the Run (`run-execution.md`): dropping the list would change the cached prefix, so no tool choice is sent either and the finalization note plus correlated refusals stop further calls. A route whose wire profile sets `request.list_announced_tools` (the Adapter's `list_announced_tools(model_id)`, `providers.md`) and every fallback route (`RequestBuildInputs.list_announced_tools`) also list each Tool announced as added, in announcement order with its latest definition; the note's `listed` flag and wording follow the primary route. A fallback never re-pins, re-applies its own route gates or creates notes of its own. A schema-changed pinned Tool keeps its pinned bytes on every route; its note carries the new schema.
- **Epoch boundaries.** Notes of another epoch (after a Takeover, a cross-scope move or a lost pin) are dropped from the request (`without_other_epoch_tool_changes`) and ignored by the fold. Compaction's post-checkpoint projection builds with `fresh_prompt_epoch`, so the new pin lists every Tool offered then on the Run's primary route, also when the Compaction runs on a fallback target, and the checkpoint commit writes it into its `PromptEpoch`, even when the rest of the prompt refresh failed, while the Projection drops the `[tool-change]` notes (`compaction.md`).
- **Temporary Sessions.** Every build measures the live catalog for the binding check: the capability Tools must be offered now, and the first request boundary announces any the pin lacks.
- **System Prompt.** Assembly receives the pinned definitions as `effective_tool_definitions`, so Tool-owned blocks and the opt-in `core:tools_list` describe the pin and stay byte-identical for the epoch: a pinned Tool that stops being ready keeps its block, and an announced Tool gets none until the next epoch (`prompts.md`). The texts of dynamic blocks are pinned separately (next section).
- Deferred MCP Tools remain outside the pin and definitions; their search, describe, and call results append through ordinary history. `ChatLoop.preview_tool_definitions` stays Agent-level and live; its file edit dialect follows the Agent's configured Model.

Regressions: `tests/core/chat/test_tool_epoch.py`, `test_chat_loop_tool_definitions.py`, `test_chat_loop_fallback.py`, `test_chat_loop_compaction_prompt_epoch.py`, `tests/core/compaction/test_compaction_engine.py`, `tests/resources/extensions/mcp/test_mcp_discovery.py`.

## Dynamic prompt blocks per prompt epoch

Tool and Extension dynamic blocks (`render` blocks such as `tool:project`, `tool:subagent`, `tool:bash` and Extension render blocks) render from live state. So that the System Prompt stays byte-identical for the epoch, Chat pins their texts like the Tool list; a later change reaches the Model as one `[prompt-block-change]` System Reminder at the next Run's start. `core/chat/_prompt_block_epoch.py` owns the pure model (pin, note, plan, wording); `RequestBuilder` (`build_request_state`, `plan_prompt_block_change`) owns resolution; `RunExecution` adds the note.

- **Pin.** The Session prompt pin `pinned_dynamic_blocks` (`PromptBlockPin` payload `{v: 1, epoch, blocks: {<id>: {text, catalog?: {title, frame, entries: [[key, line], ...]}}}}`; entries are lists because the Session store sorts object keys) holds each block's text and catalog plus a random epoch key. `build_request_state` resolves it after the Tool pin, because the blocks' owner gates and render context use the pinned Tool definitions. `render_dynamic_blocks(skip=<pinned ids>)` renders only the blocks the pin lacks: the epoch's first request pins all of them, and a block shown first mid-epoch (an Extension loaded later, a gate that opens) joins the pin with its current text while pinned blocks keep theirs (`ensure_prompt_block_pin`, through `ensure_prompt_pin`). An empty render is pinned (the block stays collapsed); a failing render is not pinned and renders again on the next request. The build passes `pinned_blocks=pin.texts()` (`prompts.md` -> Interfaces). The slot is Agent-bound (`sessions.md` -> Prompt state).
- **Change note.** At Run start, after the Skill announcement and before the Run input is written, `plan_prompt_block_change` renders the pinned block ids live (the Run's render inputs, the stored Tool pin's definitions) and compares each with what the Model knows: the pin folded with this epoch's notes from the Run's Session snapshot. All blocks whose text differs go into one note, persisted with the Run input, so the Run's first request already carries it. A catalog block whose `title` and `frame` stayed the same is told by its added, changed and removed entries; any other change (a block without a catalog, a changed frame such as the nested Sub-Agent timeout) carries the block's full current text. No note when nothing changed; a block missing from the live render (gated out or failing) is not announced. Payload `{v: 1, epoch, blocks, text}`: the blocks' new state, which later plans fold, and the reminder text.
- **Wording.** A catalog change: `{title} changed since your System Prompt listed them.`, then `Added:`, `Changed to:` and `Removed:` groups, each followed by its entry lines. Full text: `The "{section}" section of your System Prompt changed. Use this current version instead:` plus a blank line and the text; `The "{section}" section of your System Prompt no longer applies.` for a block that became empty; `This section now applies in addition to your System Prompt:` plus a blank line and the text for a block that was empty. `{section}` is the block's Markdown heading, else its first line cut to 80 characters. Paragraphs of several blocks join with a blank line. Catalog titles: `Registered Projects` (`tool:project`), `The Agent ids under Sub-Agents` (`tool:subagent`).
- **Epoch boundaries.** Notes of another epoch are dropped from the request and ignored by the plan (`without_other_epoch_prompt_block_changes`). Compaction's projection builds with `fresh_prompt_epoch` and starts a new pin from the blocks as they render then; the checkpoint commit writes it into its `PromptEpoch` even when the rest of the prompt refresh failed, and the Projection drops the `[prompt-block-change]` notes (`compaction.md`).
- **Known limits.** Two requests that add different newly shown blocks at the same moment can drop one from the stored pin; a later request pins it again. Two Runs admitted before either wrote its input can each add the same note. Agent-level `prompt.preview` renders live.

Regressions: `tests/core/chat/test_prompt_block_epoch.py`, `test_chat_prompt.py::test_dynamic_blocks_stay_pinned_and_each_change_is_announced_once`, `test_chat_loop_compaction_prompt_epoch.py`, `tests/core/compaction/test_compaction_engine.py`.
