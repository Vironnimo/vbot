# Settings

Public Settings schema parsing, raw `settings.json` validation, and whole-data-dir validation orchestration.

## Overview

`core/settings/` owns the public Settings path catalog (`paths.py` - stable accessor boundary resolving dotted segments plus JSON-quoted dynamic keys, effective values with lifecycle metadata, and validated atomic patches), the `settings.update` section schema (`settings.py`), raw-file validation (`validation.py`), and stateless per-section normalization (`normalizers.py`, raising `StorageError`). Agent, Project, Channel, Cron, Bootstrap, Calendar, Skill policy, Terminal, OAuth token, prompt layout, MCP connection, and Task-Model persisted schemas belong to their own domains; `validate_data_dir_config()` only discovers the bundle and delegates each file to its owner. All domains share transport-neutral JSON reports and parsing via `core/config_validation.py` and the Generation 1 document mechanics of `core/json_documents.py` (`json-documents.md`) - manual-edit errors keep consistent diagnostics without making Settings a schema hub.

Storage still owns raw file I/O, process-local locked read-modify-write transactions, atomic writes, and persistence helpers; server delegates own RPC error mapping, runtime-aware validation, catalog expansion for loaded Providers/Extensions, and post-change invalidation. Both public mutation surfaces (`settings.patch`, `settings.update`) validate everything before one locked transaction and then call `Runtime.apply_settings_change(previous, current, refresh_sections=...)` for all live effects - a path update can never silently behave differently from a section update. Each surface logs one INFO line naming the changed dotted setting paths, never their values (`settings.update` also names newly enabled or disabled Extensions; appearance-only changes are silent); `apply_settings_change` logs `Debug Mode enabled|disabled` when `debug.enabled` flips (`test_settings_changes_log_only_operational_changes`). Raw top-level mutation is not a public contract. `settings.set_service_key` is no Settings mutation: it writes one web service API key to the Secret Store (`secrets.md`), never `settings.json` (`tools/web_search.md` -> External Dependencies).

## Where Settings Code Lives

- Strict/tolerant file gates and data-directory diagnostics -> `validation.py`, raw shape -> `_raw_schema.py`, section diagnostics -> `_raw_sections.py`; public paths/catalog/patch -> `paths.py`; `settings.update` dispatch -> `settings.py`, Model/Provider/speech parsing -> `_update_models.py`, shared scalar/field rules -> `_rules.py`; section normalization/defaults -> `normalizers.py`, with `_provider_settings.py`, `_compaction_settings.py` and `_json_settings.py` for the larger rule groups; public path records/formatting -> `_path_types.py`, catalog declarations -> `_path_definitions.py`; persistence transactions -> `core/storage/storage.py`.
- Live side effects -> either read-at-use accessors or the shared Runtime Settings coordinator (`core/runtime/_settings.py`) used by both surfaces (per-section effects: `settings/sections.md`). Restart-applied paths expose active/pending/restart-required metadata instead of pretending the value is active.
- Shared scalar validators (`validate_temperature`, `validate_top_p`, `validate_thinking_effort`, agent-id rule) are canonical here; Agents/Projects and their RPC boundaries delegate instead of copying rules. Storage-facing temperature normalization delegates to the same validator and translates its error type. Numeric bounds are checked before float conversion so oversized JSON integers remain validation failures.
- Opaque Settings objects (Extension configs, Task Model options, and Custom Provider defaults, Model task-option facts and `wire` blocks) use `_json_settings.py` for recursive JSON validation, including finite numbers. Mutation normalizers reject non-finite values before persistence; raw-file validation reports them so tolerant reads omit the owning top-level section and strict reads/doctor diagnose the file.
- The `defaults.agent` field surface has exactly one source of truth: `core/settings/agent_defaults.py`. It owns `AGENT_DEFAULT_FIELDS` (the only literal field set), per-field parse/diagnose/normalize behavior (including the fallback-chain rules: strings, non-empty after strip, capped at `MAX_FALLBACK_MODELS`, no duplicates), the Settings-path catalog entries, and the typed `AgentDefaults` consumed by `AgentStore` baking and the resolver. Raw-file diagnostics enforce the same chain rules, so tolerant reads omit invalid defaults before Agent baking; baking also re-validates every applied default. The `settings.update` parser, raw-file validation, `normalizers.py`, and `paths.py` all derive from it; never hardcode the field list or per-field rules anywhere else.
- Settings runtime parsing and normalization must not eagerly import `core/storage/` (that direction recreates a removed cycle). Whole-data-dir diagnostics deliberately import the Storage-owned prompt-layout validator lazily when delegating that document; its schema stays with Storage.

## Public surface

- `settings.values` (normalized document), `settings.catalog` (path definitions + known dynamic keys), `settings.get_path` (value/source/default/type/lifecycle), `settings.patch` (atomic `{op: set|unset}` list; overlapping operations rejected so order cannot change meaning). Unset removes an override restoring inherited behavior - distinct from setting JSON `null`. A patch keeps containers whose unknown fields still need preserving (`settings/sections.md` -> Patch pruning). Dynamic Extension secret fields are deliberately excluded with a credential-safe CLI hint.
- `settings.json` carries `format_version` 1 (`SETTINGS_FORMAT`); the initial data-dir document (`core/storage/layout.py`), the installer seed, and the worktree seeding fixture (`scripts/fake-provider-settings.json`) carry it. `load_validated_settings_json` is the strict gate for diagnostics/mutations; `load_runtime_settings_json` is the tolerant consumption gate - malformed files fall back to defaults, schema-invalid top-level keys omit individually while valid siblings stay live, never rewriting source; a missing or other `format_version` counts as a malformed file. Storage reads tolerantly but strictly before every mutation, logging unchanged degradation once; only archive retention reads its section strictly (`archive.md` -> Retention); `settings.get` reads it tolerantly like every section. `vbot doctor settings` / `doctor config` remain strict repair diagnostics.
- Raw top-level keys: source of truth `KNOWN_RAW_SETTINGS_KEYS` in `_raw_schema.py` (exported through `validation.py`). Every key optional; unknown keys warn rather than error (forward compatibility); present sections validate per field. `timezone` is an IANA name, defaults to the host zone when absent, and is exposed as `server.timezone`; raw stays flat where history requires it while public paths nest consistently - accessors use public paths, `config raw` is diagnostic only.
- Update sections are sparse or full per their semantics; each section's contract and refusals: `settings/sections.md` -> Update sections.
- `settings.update` and `task_model.update` accept an optional `base`: the caller's view of the sections it updates, in the update's shape and naming only sections of the update. Inside the write transaction each leaf the update would change must still equal its `base` value (compared as effective values), otherwise nothing is written and the RPC fails with `settings_conflict` naming the paths. The refusal is an expected, self-healing outcome: storage logs it once at DEBUG and the RPC dispatcher adds no WARNING for this code. Leaves the update leaves alone or sets to the value already stored never conflict, and a leaf absent from `base` is unguarded, so sparse per-key sections check only the keys they name. Validation runs before the comparison. Without `base` (`settings.patch`, `task_model.patch_options`) a write stays last-writer-wins; a patch writes only the paths it names. WebUI editors send `base` (`webui/autosave.md` -> Concurrent writers); `vbot extensions enable|disable` send it and retry (`cli/system-commands.md` -> Extensions). Plumbing and tests: `settings/sections.md` -> `base` plumbing.
- Custom Provider records under raw `providers.custom` are secret-free; their CRUD goes through the `provider.custom_*` RPCs because it coordinates registry reload plus data-directory credentials in the Secret Store (`providers/connections.md`).

## Constraints & Gotchas

- Public schema errors stay transport-independent inside `core/settings/` (no RPC errors raised there) and distinct from storage-level validation errors, keeping RPC mapping stable. Diagnostics/formatting for agents belongs to CLI doctor commands.
- Unknown raw keys warn because persisted data may temporarily contain unconsumed values; Runtime isolates the owning key instead of rejecting siblings or aborting startup.
- Multi-section payloads and multi-operation patches persist in one locked transaction before lifecycle hooks run; Runtime effects run only after the write succeeds. The RPC mutation remains serialized through refresh and publication, including caller cancellation. Runtime owns the distinction between full Extension rebuild (which refreshes all dependent services) and surgical disable (which must still apply an independent Recall change). Both RPC mutation surfaces serialize through live refresh and finish that sequence even after caller cancellation; Skill-directory refresh uses Runtime's asynchronous reload so scans stay off the Event Loop.
- The Settings mutation lock (`_settings_mutation_lock`) deliberately stays held while a change reloads or deactivates Extensions. The next mutation validates against runtime state those effects rebuild (Extension config schemas, Recall backends, Task Model catalogs, Model connections), and two rebuilds must not interleave. Each lifecycle wait is bounded instead (`extensions/management.md` -> Startup and shutdown), so a save that toggles an Extension, and the saves queued behind it, wait at most the sum of the deadlines of the owners it cycles.
- Server-side schema validation of extension configs happens at the RPC layer where the loaded registry exists - `core/settings/` stays untouched by design.
- `validate_data_dir_config()` imports no Extension package: Extension-owned documents such as the MCP Extension's `connections.json` are validated through the validators their manifest declares in `config_documents` (`validate_extension_documents`, `core/extensions/config_validation.py`), loaded without running the Extension's `register`.
