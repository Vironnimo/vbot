# Settings

Public Settings schema parsing, raw `settings.json` validation, and whole-data-dir validation orchestration.

## Overview

`core/settings/` owns the public Settings path catalog (`paths.py` - stable accessor boundary resolving dotted segments plus JSON-quoted dynamic keys, effective values with lifecycle metadata, and validated atomic patches), the `settings.update` section schema (`settings.py`), raw-file validation (`validation.py`), and stateless per-section normalization (`normalizers.py`, raising `StorageError`). Agent, Project, Channel, Cron, Bootstrap, and Task-Model persisted schemas belong to their own domains; `validate_data_dir_config()` only discovers the bundle and delegates each file to its owner. All domains share transport-neutral JSON reports and parsing via `core/config_validation.py` - manual-edit errors keep consistent diagnostics without making Settings a schema hub.

Storage still owns raw file I/O, process-local locked read-modify-write transactions, atomic writes, and persistence helpers; server delegates own RPC error mapping, runtime-aware validation, catalog expansion for loaded Providers/Extensions, and lifecycle effects. Both public mutation surfaces (`settings.patch`, `settings.update`) validate everything before one locked transaction and then apply the same live-delta helper - a path update can never silently behave differently from a section update. `settings.set_key` no longer exists: raw top-level mutation is not a public contract.

## Where Settings Code Lives

- Raw key validation -> `validation.py`; public paths/catalog/patch -> `paths.py`; `settings.update` schema -> `settings.py`; section normalization/defaults -> `normalizers.py`; persistence transactions -> `core/storage/storage.py`.
- Live side effects -> either read-at-use accessors or the shared server delta hook used by both surfaces (OpenRouter routing snapshots per Run, Skills directories reload, Recall reloads backend, Extension directories rebuild, disabled-set applies surgically, `keep_awake` toggles power request). Restart-applied paths expose active/pending/restart-required metadata instead of pretending the value is active.
- Shared scalar validators (`validate_temperature`, `validate_thinking_effort`, agent-id rule) are canonical here; Agents/Projects and their RPC boundaries delegate instead of copying rules. Only `normalizers.py` keeps storage-facing variants with different messages.
- The `defaults.agent` field surface has exactly one source of truth: `core/settings/agent_defaults.py`. It owns `AGENT_DEFAULT_FIELDS` (the only literal field set), per-field parse/diagnose/normalize behavior, the Settings-path catalog entries, and the typed `AgentDefaults` consumed by `AgentStore` baking and the resolver. The `settings.update` parser, raw-file validation, `normalizers.py`, and `paths.py` all derive from it; never hardcode the field list or per-field rules anywhere else.
- The settings domain must not import `core/storage/` (that direction recreates a removed cycle).

## Public surface

- `settings.values` (normalized document), `settings.catalog` (path definitions + known dynamic keys), `settings.get_path` (value/source/default/type/lifecycle), `settings.patch` (atomic `{op: set|unset}` list; overlapping operations rejected so order cannot change meaning). Unset removes an override restoring inherited behavior - distinct from setting JSON `null`. Dynamic Extension secret fields are deliberately excluded with a credential-safe CLI hint.
- `load_validated_settings_json` is the strict gate for diagnostics/mutations; `load_runtime_settings_json` is the tolerant consumption gate - malformed files fall back to defaults, schema-invalid top-level keys omit individually while valid siblings stay live, never rewriting source. Storage reads tolerantly but strictly before every mutation, logging unchanged degradation once. `vbot doctor settings` / `doctor config` remain strict repair diagnostics.
- Raw top-level keys (source of truth `validation.py`): port aliases, appearance, speech transcription profile, skill/extension directories, extensions, upload limits, Sub-Agent limits, compaction, defaults, providers, recall, reflection, web_search, model_tasks, session_titles, local_models, keep_awake, debug. Every key optional; unknown keys warn rather than error (forward compatibility); present sections validate per field. Raw stays flat where history requires it while public paths nest consistently - accessors use public paths, `config raw` is diagnostic only.
- Update sections are sparse or full per their semantics; notable contracts: `appearance.language` is required so partial updates never reset display prefs; `extensions` is a **full-replace** write whose disabled-delta routes enable through the full rebuild and disable through surgical deactivation, with config values applying live via each extension's reader; `providers` updates exactly OpenRouter routing (Custom Providers have dedicated RPCs coordinating registry reload and write-only credentials); `recall.backend` validates shape only here while membership resolves against built-in plus extension backends at the server edge; `local_models.context_windows` sparse-merges per key (`null` removes); `model_tasks` validates bindings against loaded Models/targets before persistence so generic mutation cannot bypass task validation; `session_titles` reads live per first message; `web_search` loads at call time.
- Custom Provider records under raw `providers.custom` are secret-free; their CRUD is intentionally exposed through `provider.custom_*` RPCs because it coordinates registry reload plus `.env` credentials. OpenRouter routing's full schema lives in `providers/openrouter.md`.

## Constraints & Gotchas

- Public schema errors stay transport-independent inside `core/settings/` (no RPC errors raised there) and distinct from storage-level validation errors, keeping RPC mapping stable. Diagnostics/formatting for agents belongs to CLI doctor commands.
- Unknown raw keys warn because persisted data may temporarily contain unconsumed values; Runtime isolates the owning key instead of rejecting siblings or aborting startup.
- Multi-section payloads and multi-operation patches persist in one locked transaction before lifecycle hooks run; hooks run only after the write succeeds.
- Server-side schema validation of extension configs happens at the RPC layer where the loaded registry exists - `core/settings/` stays untouched by design.
- Setup scripts seed new `settings.json` with default temperature 0.1 and thinking effort "high" as an install-time seed only - existing instances keep prior behavior until explicitly configured; this is not a runtime fallback.
