# Settings

Public Settings schema parsing, raw `settings.json` validation, and whole-data-dir validation orchestration.

## Overview

`core/settings/` owns the product-facing schema for Settings update payloads and the raw `settings.json` schema. It validates what public accessors may send through `settings.update` before the server applies those updates to storage and runtime side effects. Agent, Project, Channel, and Cron persisted schemas belong to their own domains; `validate_data_dir_config()` only discovers the bundle and delegates each file to its owner. All domains share transport-neutral JSON reports, file parsing, and shape primitives from `core/config_validation.py`, so manual edit errors keep consistent diagnostics without making Settings a schema hub. Raw `settings.json` keys and public `settings.update` sections overlap, but they are not the same API; keep that distinction explicit when adding settings.

Storage still owns raw `settings.json` file I/O, process-local locked read-modify-write transactions, atomic writes, prompt fragments, and normalized persistence helpers. Server delegates own RPC error mapping and side effects such as reloading skills after skill directory changes. The raw `settings.set_key` RPC validates the merged raw `settings.json` mapping with `validate_settings_data()` before persisting; warnings such as unknown top-level keys are allowed, but schema errors for known sections are rejected as RPC `invalid_request`.

## Where Settings Code Lives

When adding or changing a setting, touch the layer that owns it:

- Raw `settings.json` validation → `core/settings/validation.py` (`KNOWN_RAW_SETTINGS_KEYS` plus a `_validate_*` helper).
- Public `settings.update` schema → `core/settings/settings.py` (`SETTINGS_UPDATE_SECTIONS` plus a `_parse_*` helper).
- Section normalization and defaults → `core/settings/normalizers.py` (stateless `normalize_*` / `coerce_*` per section; raises `StorageError`).
- Persistence (transactions, atomic write, `load_*` / `update_*` accessors) → `core/storage/storage.py`, which delegates all section knowledge to the normalizers.
- Live runtime side effect → either a read-at-use accessor or a reload hook in the async `server/rpc/settings_methods._update_settings`. Today OpenRouter routing is snapshotted when the next Run constructs its Adapter, `skills` → `runtime.reload_skills()`, `recall` → `runtime.reload_recall_backend()`, and the `extensions` disabled-set delta applies live; sections without either mechanism take effect on the next start. For the `extensions` section every change applies **live**: a config-value change is read by each extension via `api.get_config()` (no hook); a newly-**enabled** name (`old_disabled - new_disabled`) `await`s `runtime.reload_extensions()` — the full rebuild, which also covers a same-save disable; otherwise a newly-**disabled** name (`new_disabled - old_disabled`) `await`s `runtime.apply_extension_disabled_change` (surgical deactivation — hooks off, tools gone, shutdown fired). No restart flag is returned (see Supported Update Sections).

## Interfaces

- `core/settings/__init__.py` exports `parse_settings_update`, `SettingsValidationError`, the shared JSON report aliases, the strict Settings validators/load gate, the runtime-tolerant `load_runtime_settings_json`, and shared Settings schema constants (including `DEFAULT_APPEARANCE_LANGUAGE`, `SUPPORTED_APPEARANCE_LANGUAGES`, `DEFAULT_APPEARANCE_CHAT_WIDTH`, `SUPPORTED_APPEARANCE_CHAT_WIDTHS`, `DEFAULT_RECALL_SETTINGS`, `ALLOWED_THINKING_EFFORTS`, `MIN_TEMPERATURE`, `MAX_TEMPERATURE`, `AGENT_ID_PATTERN`). The `chat_width` constants live in `settings.py` (not `normalizers.py`, which imports them) so the public update parser can validate membership without a circular import.
- `validate_temperature(value, *, label, allow_none)` / `validate_thinking_effort(value, *, label, allow_none)` are the canonical agent field-rule validators (raise `SettingsValidationError` with the label-prefixed message), and `is_valid_agent_id(value)` / `AGENT_ID_PATTERN` are the canonical agent-id format rule. `core/agents/`, `core/projects/`, and their RPC boundaries delegate to these value validators instead of re-encoding the rules; the owning raw-file schemas adapt the same errors into path diagnostics through the public diagnostic adapters in `core/settings/validation.py`. Only `core/settings/normalizers.py` keeps its own storage-facing temperature/effort variant with `Agent default …` messages.
- `core/settings/normalizers.py` owns stateless per-section normalization for persisted `settings.json` sections (appearance, skills, sub-agents, compaction, defaults/agent, recall, debug, web search, model tasks, Session titles) plus the section default constants. Functions raise `StorageError` (defined in `core/utils/errors.py`) on invalid persisted data; `StorageManager` calls them inside its transactions. The settings domain must not import `core/storage/` — that direction would recreate the import cycle the error relocation removed.
- `parse_settings_update(params) -> dict[str, Any]` validates the public `settings.update` request body and returns a normalized per-section update dict.
- `SettingsValidationError` signals malformed public payloads. Server delegates map it to RPC `invalid_request`.
- `validate_settings_file(path) -> SettingsValidationReport` validates one raw `settings.json` file without writing or normalizing it. Missing files are OK because storage defaults apply.
- Persisted non-Settings schemas and read-time gates are exported by their owners: `core.agents`, `core.projects`, `core.channels`, and `core.automation`. Their field contracts live in the corresponding domain maps; Settings does not re-export them.
- `validate_data_dir_config(data_dir) -> tuple[JsonValidationReport, ...]` validates the current user-editable config bundle for `vbot doctor config`.
- `load_validated_settings_json` is the strict gate for diagnostics and mutations. `load_runtime_settings_json` is the consumption gate: malformed JSON or a non-object root yields defaults at the caller, while schema-invalid top-level keys are omitted individually and valid sibling keys remain live. It returns the isolated diagnostics for warning logs and never rewrites the source file.
- `StorageManager` uses tolerant reads but a strict locked load before every mutation. A malformed or schema-invalid file therefore cannot stop Runtime startup and cannot later be overwritten by an unrelated Settings save; unchanged degradation diagnostics are logged once per Storage instance rather than on every live read. `vbot doctor settings` / `vbot doctor config` remain the strict repair diagnostics.
- Data validators return shared `JsonDiagnostic` values with severity, JSON path, and message. `core/config_validation.py` owns the common report/file mechanics and primitive shape checks, not any domain schema.

## Raw Settings Keys

`core/settings/validation.py` is the source of truth for raw top-level keys accepted in `<data_dir>/settings.json`: port aliases (`PORT`, `SERVER_PORT`, `port`, `server_port`), `appearance`, `skill_directories`, `extension_directories`, `extensions`, upload limits (`attachment_max_size_bytes`, `speech_upload_max_size_bytes`), sub-agent limits (`max_subagent_depth`, `max_subagents_per_turn`, `subagent_timeout_minutes`), `compaction`, `defaults`, `providers`, `recall`, `reflection`, `web_search`, `model_tasks`, `session_titles`, `local_models`, and `debug`. Every raw key is optional and `{}` is valid. Unknown top-level raw keys are warnings, not errors. Schema errors remain strict diagnostics, but Runtime consumption isolates the owning top-level key instead of rejecting valid siblings or aborting startup.

`providers` has two separately owned persisted children. `connections` is raw-only: `{ "<provider>:<connection>": bool }` — per-Connection enabled/disabled overrides over the type defaults (keyed Connections on, keyless local Connections off; see `providers.md` → Terms → Usable and `providers/connections.md`). It is written by `connection.set_enabled` through `StorageManager.set_provider_connection_enabled(connection_key, enabled)` and read live at every usability check. `openrouter.routing` is both a raw key and a public `settings.update` surface; its complete schema and request semantics live in `providers/openrouter.md`. Each mutation preserves the sibling child, so saving routing cannot replace Connection overrides and toggling a Connection cannot reset routing.

`extension_directories` is raw-only (loaded only during `Runtime.start()` as extra roots for Python extension discovery; no public `settings.update` section). The `extensions` section (`{ disabled: string[], config: { <ext>: object } }`) **is** a public `settings.update` section (see Supported Update Sections). The `disabled` set is read at `Runtime.start()` (disabled extensions are never imported); at runtime every change applies **live** — **disabling** an extension takes the surgical deactivation gate, **enabling** triggers a full `Runtime.reload_extensions` rebuild that imports code disabled at boot. Per-extension `config` is read **live** by each extension via `api.get_config()`, so a config-value change takes effect without a restart. `attachment_max_size_bytes` is read at runtime startup for `AttachmentStore`, and `speech_upload_max_size_bytes` is read at runtime startup for the server speech upload gate. Port aliases are consumed by server startup, not by the settings update parser.

## Supported Update Sections

- `appearance` — `{ language: string, chat_width?: "comfortable" | "wide" | "full" }`; `language` is required and non-empty (so a partial update never resets it — the section is normalized as a whole). `chat_width` is optional and validated against the supported set when present; the parser rejects unknown values. The WebUI sends the complete section. Storage validates the supported language set; an unknown persisted `chat_width` normalizes to `comfortable` (the default) rather than raising, since it is a display-only preference.
- `skills` — `{ directories: string[] }`; storage validates and normalizes absolute or home-relative paths. Both POSIX and Windows absolute forms are accepted on any host, so a settings.json validates identically across platforms.
- `defaults` — `{ agent: { model?, fallback_model?, temperature?, thinking_effort? } }`; `null` removes an individual Agent default. `temperature` is bounded `0.0`–`2.0`. `thinking_effort: ""` is a valid explicit provider-default value.
- `subagents` — requires `max_subagent_depth`, `max_subagents_per_turn`, and `subagent_timeout_minutes` as positive integers.
- `compaction` — requires the complete Policy `{ enabled, trigger, strategy }`. Trigger is exactly `{ type: "context_ratio", threshold }` with threshold in `(0, 1]` or `{ type: "input_tokens", tokens }` with positive integer tokens. Strategy is exactly `{ type: "summary_tail", tail_tokens, summary_model }` with positive integer tail and `str | null` Model binding, or `{ type: "continuation" }`.
- `recall` — `{ backend: string }`; a lowercase snake_case backend name. The parser validates only the shape — whether the name resolves is checked one layer up in `server/rpc/settings_methods.py` against the recall registry (built-ins **plus** extension-registered backends), not against a fixed first-party set. Updates the backend used by the `session_search` tool.
- `web_search` — `{ provider: "brave" | "searxng", default_count?: int, searxng?: { base_url: string } }`; updates the provider used by the `web_search` tool. `provider` is required in public updates; `default_count` (1–20, default 12; bounds shared from `core/search_config.py`) is the result count a `web_search` call uses when the agent omits `count`; `searxng.base_url` defaults to `http://localhost:8888` when not persisted. Storage merges the section, so omitting `default_count` or `searxng` preserves the stored values.
- `debug` — `{ enabled?: boolean, trace_limit?: positive integer }`; both fields are optional in public updates. `enabled` defaults to `false`, `trace_limit` defaults to `50` and is rejected above `500` (not silently clamped). Updates merge with existing settings — partial updates preserve unspecified fields.
- `reflection` — `{ enabled?: boolean, memory_turn_interval?: positive integer, skill_tool_call_interval?: positive integer }`; all fields optional, partial updates merge like `debug`. Defaults: disabled, `10` turns, `25` tool calls (`REFLECTION_SETTING_DEFAULTS` in `normalizers.py`). No reload hook — the reflection service reads the section live at every run end (`storage.load_reflection_settings()`), so enable/disable and interval changes apply immediately. Consumed by `core/automation/reflection.py` (see `automation.md`).
- `model_tasks` — `{ <task_type>: { target?, options? } }`; supported task types are owned by `core/model_tasks/`. `target` must be a string when present, `options` must be an object, and an empty target clears that task's persisted binding.
- `providers` — public updates accept exactly `{ openrouter: { routing: { default, models } } }`; each routing policy is the complete `{ mode, providers, blocked, allow_fallbacks }` shape documented in `providers/openrouter.md`. Storage replaces only OpenRouter routing and preserves `providers.connections`. A save applies to the next OpenRouter Run because Runtime snapshots the policy at Adapter construction; it never switches Provider inside an active Tool loop.
- `session_titles` — complete `{ enabled: bool, model: string }`, default `{ enabled: false, model: "" }`. `model` may carry the same optional connection pin as Agent Model values; the RPC layer validates an explicit pin against the model catalog. The title service reads this section live for each new Session's first visible user message, so changes require no reload. An empty `model` delegates target selection to that Run's resolved Agent Model.
- `local_models` — `{ context_windows: { "<provider>/<model_id>": positive int | null } }`; the user-configured effective context window per flagged-local model (consumed by `resolve_effective_context_window`, see `models.md` → locality). Keys must contain a `/`; `context_windows` is required in public updates. **Sparse per-key merge**: `null` removes a key (the model falls back to the default cap), unmentioned keys are preserved. Raw and public shape are identical. No reload hook — read live at call time (`storage.load_local_models_settings()`) by the chat budget, `/status`, the agent/model payloads, and the Ollama adapter's `num_ctx` enforcement.
- `extensions` — `{ disabled?: string[], config?: { <ext>: object } }`; a **full-replace** write (both fields default to empty when omitted, so callers send the complete section). The `core/settings/` parser checks shape only; storage's `normalize_extensions_settings` dedupes `disabled` and deep-validates each `config` value as a JSON object. On top of that, the async `server/rpc/settings_methods._update_settings` **schema-validates** each loaded schema'd extension's `config` against its declared schema (`validate_extension_config`) before persisting — `invalid_request` on any error (`core/settings/` stays untouched: schema validation lives at the RPC layer where the loaded registry exists, design decision #2). The `disabled`-set delta (compared against the persisted section read before the write) is applied live after the write: any name **removed** (newly enabled) triggers `await runtime.reload_extensions()` **and nothing else** (the rebuild reads the freshly persisted state, so it also applies a same-save disable); otherwise any name **added** (newly disabled, no enable) drives `await runtime.apply_extension_disabled_change`. A config-value-only change applies live (each extension reads it via `api.get_config()`). The response never carries a restart flag — every extension change is live. See `.vorch/domain-maps/extensions.md`.

## Constraints & Gotchas

- Public schema errors must remain transport-independent in `core/settings/`; do not raise server RPC errors from this module.
- Raw JSON diagnostics and `core/config_validation.py` must remain transport-independent and file-system local. Formatting for agents belongs to CLI doctor commands.
- Unknown top-level raw settings keys are warnings, not errors, because raw settings may temporarily contain values not consumed by current runtime code.
- Raw `settings.json` and public `settings.update` use different shapes for the same data: raw keys are flat (`skill_directories`, `max_subagent_depth` / `max_subagents_per_turn` / `subagent_timeout_minutes`) while public sections nest them (`skills.directories`, `subagents.{…}`). `providers` is asymmetric: raw data may contain `connections` and `openrouter`, while the public update accepts only the complete `openrouter.routing` child. `appearance`, `defaults`, `compaction`, `recall`, `web_search`, `model_tasks`, `session_titles`, and `debug` otherwise keep the same name on both surfaces. Use the shape that matches whichever surface you touch.
- Raw section validators (`recall`, `web_search`, `model_tasks`, `compaction`, `debug`, `appearance`, `defaults`, `extensions`, `local_models`, `providers`) are nullable: an absent or `null` section is fine, but a present one must be an object and is checked per field. For `extensions`, `disabled` (when present) must be a list of non-empty strings and `config` (when present) an object whose values are objects. `recall.backend` only has to be lowercase snake_case at the raw layer — runtime resolves it through `RecallBackendRegistry` and falls back to `jsonl_scan` for unknown names. The public `settings.update` parser now also enforces **only** the lowercase snake_case shape (sharing `RECALL_BACKEND_PATTERN`, defined in `settings.py` and imported by `validation.py`); membership in the actual recall registry — built-ins plus extension-registered backends — is enforced one layer up in `server/rpc/settings_methods.py` against `runtime.available_recall_backends()`, so an extension backend is a valid update target.
- `settings.py` stays focused on public `settings.update` parsing. Raw file validation belongs in `validation.py`.
- `settings.update` accepts sparse Defaults and Model Task updates but full Sub-Agent and Compaction sections. Recall updates are small exact-section writes with only `backend`.
- Runtime side effects do not live here. For example, saving skill directories still happens in storage, and server delegates call `runtime.reload_skills()` after a successful update. Recall backend changes are applied by server delegates through `runtime.reload_recall_backend()`.
- Accepted multi-section `settings.update` payloads are persisted by storage in one locked settings transaction before server-side reload hooks run.
- `settings.web_search` is loaded by the `web_search` tool at call time, so changing the selected search provider does not require a runtime restart or tool re-registration.
- Keep storage-level validation errors distinct from public schema errors so RPC error mapping remains stable.
