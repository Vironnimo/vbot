# Cron Tool

Manages persisted time-based automation jobs through `CronService`.

## Interfaces

- Tool name: `cron`
- Registration: `register_cron_tool(registry, cron_service, reference_lock=...)` registers the Tool-owned `argument_normalizer` and three unadvertised parameters (`timezone`, `enabled`, `late_limits_note`). `create` and `update` hold the Agent reference lock (`AutomationReferences.lock`, `automation.md`) like the cron RPCs, so a job cannot select an Agent or Project between a removal's reference check and the removal (`test_target_choices_wait_for_the_reference_lock`).
- Schema: one open flat object requiring `action`, with optional siblings `id`, `target`, `name`, `prompt`, `schedule`, and `repeat`. The handler requires `prompt` + `schedule` for create, `id` plus at least one changed field for update, and `id` for delete/enable/disable; list takes an optional `id`. `repeat` keeps the genuine `integer | null` semantic because update uses explicit null to remove a limit.
- The description is one sentence: `Schedule jobs that run an instruction later, once or repeatedly.` `prompt` says `Self-contained instruction for each run.`; `schedule` says its forms are in local time, because Models know cron fields from UTC-based schedulers. The fresh-Session contract, the reply that notifies no one, and the server time zone sentence were cut (user decision 2026-10-08); `list` names the zone (`timezone`).
- Display: the summary leads with the normalized `action`, followed by the first available `name`, `id`, target, or schedule; persisted calls keep the Model's spelling and are normalized for the label. A successful `list` derives the exact `results` count from its integer `jobs` field. The WebUI fallback for streaming rows mirrors this label (`toolRows.js`).
- Coverage: `tests/core/tools/test_cron.py` (actions, results, errors), `tests/core/tools/test_cron_call_tolerance.py` (earlier schemas, other harness dialects, state, placeholders) and `tests/core/tools/test_cron_call_times.py` (schedule spellings, time zones), all through production dispatch against a real `CronService` (`tests/core/tools/scheduling_tool_support.py`). `scripts/tool_lab/cases/automation.json` holds the probe cases.

## Conventions

- `create` defaults an omitted `target` to `ToolContext.agent_id` + `ToolContext.project_id`; an explicit target is parsed as `agent` or `agent@project`. Cross-Agent and cross-Project administration is intentional: `list` returns all jobs and every mutating operation may address a job owned by another target. CronService owns target existence validation.
- `schedule` forms: five cron fields, `every <duration>`, `in <duration>`, or an ISO 8601 timestamp. Durations are positive whole numbers followed by `m`, `h`, or `d`. Cron fields and offset-free timestamps are server time; an explicit offset is an absolute instant.
- `repeat` counts future fires, including the next one. On create, omission means unlimited for recurring jobs and one for one-time jobs. On update, omission keeps the count, an integer replaces it, and null removes the limit. A one-time schedule accepts only 1; updating a job to a one-time schedule sets 1.
- `name` is optional on create; CronService derives it once from the first useful prompt line (capped at 80 characters, fallback `Scheduled Run`). Later prompt updates never rename the job, and names need not be unique.
- Every fire starts a fresh Session: the Tool exposes no Session choice. Jobs have no delivery channel; a prompt that should reach the user must say how.
- Results are plain fields, not the persisted record. A job result carries `id`, `name`, `status`, `schedule`, `next_run`, `target`, and, when present, `repeat` (limited recurring jobs only), `last_run`, `last_outcome`, `last_error`, `failures_in_a_row`, and `note`. A one-time job shows its local fire time as `schedule` and no `next_run`. All times are server-local ISO values with offset. `list` returns `jobs` (count), `timezone` (server zone name) and one text block per job ending in an indented `prompt:`; a `failed` job's block names the enable call that restarts it. Delete returns `id`, `name`, `status: deleted`. No result carries `retryable`.

## Argument reading

`_cron_arguments.normalize_cron_arguments` runs before schema validation and executes a call whose intent is unambiguous; it never writes to a guessed job or target and never drops a requested effect. When readings differ, it raises `CronCallRefused` (an `invalid_arguments` failure) before any job changes, and every refusal starts with `cron was not run:` and ends with the exact corrected call, or with one call per reading.

- Shapes: a JSON-string or `request`/`arguments` wrapper, one operation key (`{"create": {...}}`, `{"list": "{}"}`, `{"delete": true}`), and `job`/`data`/`payload` objects (OpenClaw `agentTurn` payloads). Placeholder-only operation keys are ignored; two real operations are refused with both calls.
- Spellings: earlier vBot fields (`agent_id`, `cron_expression`, `run_at`, `schedule_type`, `job_id`), Claude Code (`cron`, `recurring`, `durable`), Hermes (`job_id`, pause/resume/remove, `deliver`), OpenClaw (`schedule` objects with `kind`/`expr`/`at`/`everyMs`/`tz`, `sessionTarget`, `delivery`), and scheduled-task Tools (`cronExpression`, `fireAt`, `description`), plus action synonyms. Spelled and ISO 8601 durations, `@daily`-style macros and interval numbers with a unit are converted. One-time keys (`run_at`, `at`, `atMs`, `fireAt`, `timestamp`...) read a clock time (`"09:00"`, `"9:00"`, `"0900"`, `at 09:00`) as the canonical `at HH:MM`, which `zoned_schedule` turns into its next occurrence in the named or server zone (with a note; a skipped or repeated time is refused with each instant); 12/14-digit strings as a compact local timestamp; 10-digit strings and numbers in 1e9..1e10 as epoch seconds, 13 digits and numbers in 1e12..1e13 as epoch milliseconds (`*Ms` keys take only milliseconds). An epoch is an instant in every zone, so a `timezone` next to it is dropped. Other digits and numbers (`900`, `"2400"`) and an 8-digit date are refused with a stand-in schedule.
- Refused as ambiguous or unavailable, with calls: a bare duration (`in` or `every`), two schedules without a type, a repeating schedule marked one-time, six-field cron, a date without time, unit-less interval numbers, a chosen Session, a delivery request, a non-`agentTurn` payload, run-now (offers a one-time `in 1m` job), stop/cancel (offers disable or delete), a bare `id` (offers delete/disable/enable/list), create with an `id`, update without an `id`, and job fields on list (offers list without them, or update/create) or delete (offers delete without them, or update). Every Send is valid as sent: a refused value is never echoed back; six-field cron and a date without time show a stand-in schedule (`_Problems.add(..., schedule=<stand-in>)`).
- Self words as target (`self`, `me`, `current`, `this`, `default`...) become the canonical `SELF_TARGET`, which the handler resolves to the calling Agent on create and update (so an update moves the job to the caller, never a silent no-op). Placeholders (`<name>`, `placeholder`, `TBD`) are omitted; a placeholder prompt on create is refused with a request for the full instruction. A stand-in in angle brackets as `prompt` on update or as `target` is refused too (without a Send), because dropping it would lose the new instruction or run the job as the caller. `repeat` words `unlimited`/`forever` mean null.
- Late-start limits have no effect (user decision 2026-10-08, `automation.md` -> Catch-up): `max_delay` and the spellings Models use for it (`maxDelay`, `max_lateness`, `late_limit`, `catch_up_window`, `misfire_grace`, `grace_period`, `starting_deadline`, the `*_seconds` forms, APScheduler `misfire_grace_time`, Kubernetes `startingDeadlineSeconds`, Hermes `catch_up_missed`/`catch_up`/`run_missed`/`start_when_available`, OpenClaw `skipMissedJobs`/`skip_missed`). `core/tools/_durations.take_late_limits` (shared with the calendar Tool) removes each one whose value is not empty or a placeholder, and the unadvertised `late_limits_note` carries a note to the handler: `"<key as sent>" has no effect.`, what happens to a missed fire, and that a prompt can tell a late Run to skip the instruction. The call executes. `with_late_limits_note` appends the note to the result's `note`; a refusal carries it before its `Send:` (after the cause when no call follows; before the cause of a choice), so a corrected call never drops the field silently. An update whose only change is a late-start limit gets the normal `update needs a field to change` refusal with the note (`test_late_start_limits_have_no_effect_and_the_result_says_so`, `test_update_needs_a_change`).
- State: `status`/`enabled`/`paused` spellings become the unadvertised `enabled`. On create, active is the default and dropped; inactive creates a `paused` job whose result note names the enable call (the intent is clear and the state is visible, so failing would only cost a round trip). On update and enable/disable with changes, it sets active or paused. Terminal statuses and conflicting values are refused.

## Time zones

Jobs store no zone of their own (a per-job zone would change the persisted format). `_cron_timezone.zoned_schedule` reads a named zone against the server zone and executes only when every fire lands on the instant the named zone means. `_named_zones` finds the exact instants at which each zone changes its UTC offset over the coming year (hourly scan, bisected to the second, cached per zone and day); the difference between server and named time is read now and just after each such change, never sampled. The scheduler steps server wall-clock time (a skipped fire moves past the gap, a repeated hour fires once), so a conversion is exact only when that difference is constant all year: then both zones skip and repeat at the same instants.

- the server zone (by key, or a difference of zero all year), or a relative schedule: dropped;
- an offset-free timestamp that names one instant in that zone: converted to the server-local instant, with a result note naming both times. A time the zone skips or repeats is refused with one server-time call per instant (`does not exist in <zone>` / `happens twice in <zone>`);
- a timestamp with an offset: an absolute instant, executed when the offset is one that zone has at that local time; otherwise refused with the time as written and each reading in that zone;
- cron fields: shifted, with a note, only when the difference is constant all year and the shifted fields fire at the same instants: every fire keeps its day, or every fire moves by the same day while only weekdays are restricted (the weekday field moves with it). Examples that execute: UTC server, Asia/Tokyo `0 3 * * 1` -> `0 18 * * 0`; Europe/Berlin server, Europe/London `*/15 1-3 * * *` -> `*/15 2-4 * * *`. Fields that cannot follow the shift (hour `*` or an hour range crossing midnight with restricted days, a restricted day of month or month that would move, a partial-hour shift of a non-literal minute) are refused with a server-time stand-in. A difference that changes during the year is never exact, even for `*`-hour fields: refused with today's conversion (or the same fields, when they do not change) as the Send, naming why it drifts around the clock changes;
- an unknown zone with a wall-clock schedule, or a zone alone on update: refused.

## Constraints & Gotchas

- Target failures use the codes shared with the Status and Sub-Agent Tools: `agent_not_found`, `project_not_found`, `agent_unavailable` (keeps the resolver's reason), and `invalid_arguments` for a malformed address. They carry target guidance instead of call shapes. An unknown id is `job_not_found` and points to `{"action":"list"}`.
- A one-time time already past on create, update, or enable fails with the past local time, the current time, and the corrected call with the `<future time>` stand-in (for enable, an update call); an update with no change shows `schedule` as the `<when>` stand-in. Refusals never invent a schedule the Agent did not send. A completed or missed job is immutable; the error suggests a new job or the delete call.
- A repeat is consumed when `TriggerService` admits or queues the Run. A fire missed while vBot was not running starts once, late, with a System Reminder naming its due time (`automation.md` -> Catch-up). `last_outcome: missed` and status `missed` appear only on jobs that earlier versions skipped by `max_delay`. Five consecutive recurring failures stop a job as `failed`; enable restarts it and resets the streak.
- The Tool cannot fire a job on demand, carry a per-job time zone, or deliver a reply; these are refused rather than approximated.

## Agent-facing text

Reasons for the late-fire System Reminder (`_LateFire.notice`, `core/automation/cron.py`). Removing `max_delay` (user decision 2026-10-08) took the definition from 520 back to 413 estimated tokens (`python -m scripts.tool_lab definitions`).

| Text | Reason |
|---|---|
| `Cron job <id> was due at <due> and is starting late, at <start>.` / `... is starting at its due time, <due>.` | Names the job and both times so the Run knows it is late and by how much. |
| `The earlier due time <first> was missed ...` / `<N> earlier due times, the first at <first>, were missed and will not run separately.` | Prevents the Run from assuming every missed period is covered elsewhere, or trying to replay them. |
| `vBot did not run the job at those times, for example because the server was off or the computer was asleep.` | Gives the cause, so the Agent does not report a fault or retry. |
| `Carry out the instruction that follows now, and adapt any part of it that depends on when it runs, ...` | Without it Agents either refuse the stale task or send a "good morning" at noon and report on the wrong period. |
| `If the instruction no longer makes sense this late, say so instead of carrying it out.` | Without `max_delay`, a late Run whose task has become moot (a wake-up call at noon) must be able to decline it instead of doing it anyway (user decision 2026-10-08). |
