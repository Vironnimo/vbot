# Cron Tool

Manages persisted automation jobs through `CronService`: at times, and before, at or after the occurrences of a calendar event (`automation.md` -> Event jobs).

## Interfaces

- Tool name: `cron`
- Registration: `register_cron_tool(registry, cron_service, reference_lock=...)` registers the Tool-owned `argument_normalizer` and four unadvertised parameters (`timezone`, `enabled`, `late_limits_note`, `deliver_platform`). `create` and `update` hold the Agent reference lock (`AutomationReferences.lock`, `automation.md`) like the cron RPCs, so a job cannot select an Agent or Project between a removal's reference check and the removal (`test_target_choices_wait_for_the_reference_lock`).
- Schema: one open flat object requiring `action`, with optional siblings `id`, `target`, `name`, `prompt`, `schedule`, `event_id`, `repeat`, `session` (string), `deliver` (enum `here`, `app`, `none`) and `watch` (string). The handler requires `prompt` + `schedule` for create (with `event_id`, an omitted schedule is refused with the event-time stand-in `<start or end, e.g. start - 30m>`), `id` plus at least one changed field for update, and `id` for delete/enable/disable; list takes an optional `id` or `event_id`. `repeat` keeps the genuine `integer | null` semantic because update uses explicit null to remove a limit.
- The description is one sentence: `Schedule jobs that run an instruction later: once, repeatedly, or before, at or after a calendar event.` `prompt` says `Self-contained instruction for each run.`; `schedule` says its forms are in local time, because Models know cron fields from UTC-based schedulers. The fresh-Session contract, the reply that notifies no one, and the server time zone sentence were cut (user decision 2026-10-08); `list` names the zone (`timezone`). Session and delivery are now parameters (`session`, `deliver`, user decision 2026-10-20), and so is a check before each run (`watch`, same decision).
- Display: the summary leads with the normalized `action`, followed by the first available `name`, `id`, target, schedule, or `event_id`; persisted calls keep the Model's spelling and are normalized for the label. A successful `list` derives the exact `results` count from its integer `jobs` field. The WebUI fallback for streaming rows mirrors this label (`toolRows.js`).
- Coverage: `tests/core/tools/test_cron.py` (actions, results, errors), `tests/core/tools/test_cron_call_tolerance.py` (earlier schemas, other harness dialects, state, placeholders) and `tests/core/tools/test_cron_call_times.py` (schedule spellings, time zones, event-time and reminder-offset spellings), all through production dispatch against a real `CronService` bound to a real `CalendarService` (`tests/core/tools/scheduling_tool_support.py`, which registers both Tools in one registry). `scripts/tool_lab/cases/automation.json` holds the probe cases.

## Conventions

- `create` defaults an omitted `target` to `ToolContext.agent_id` + `ToolContext.project_id`; an explicit target is parsed as `agent` or `agent@project`. Cross-Agent and cross-Project administration is intentional: `list` returns all jobs and every mutating operation may address a job owned by another target. CronService owns target existence validation.
- `schedule` forms: five cron fields, `every <duration>`, `in <duration>`, or an ISO 8601 timestamp. Durations are positive whole numbers followed by `m`, `h`, or `d`. Cron fields and offset-free timestamps are server time; an explicit offset is an absolute instant.
- With `event_id`, `schedule` is an event time: `start` or `end`, optionally `+`/`-` a duration up to 31 days (`start - 30m`), stored as edge and signed minutes (`CronService.parse_event_schedule`). The job runs at that time of every occurrence and takes no `repeat`. On update, a job at an event keeps its event when the call sends only an event time, keeps its event time when the call sends only another `event_id`, and leaves its event when the call sends a schedule of another kind; a job moved onto an event without an event time runs at the start, and CronService clears its repeat count.
- `repeat` counts future fires, including the next one. On create, omission means unlimited for recurring jobs and one for one-time jobs. On update, omission keeps the count, an integer replaces it, and null removes the limit. A one-time schedule accepts only 1; updating a job to a one-time schedule sets 1.
- `name` is optional on create; CronService derives it once from the first useful prompt line (capped at 80 characters, fallback `Scheduled Run`). Later prompt updates never rename the job, and names need not be unique.
- **Session and delivery** (user decision 2026-10-20; job semantics in `automation/cron.md` -> Delivery). `session` is `current` (the calling Session) or a Session id that CronService checks; omitted, each run starts in a new Session, and on update `new` unpins the job. `current` for a job of another Agent is refused with the call without it, and a missing Session with both calls (`session: current`, no `session`). `deliver` is `here`, `app` or `none`, `here` when omitted on create. `here` is the calling chat when the call comes from a Channel reply surface and the job runs as the calling Identity Agent (stored as `chat` with the surface's Channel, chat and thread); from the WebUI, the TUI or a background Run (Cron, Sub-Agent) it is `app`. For a job of another Agent, an omitted `deliver` in a chat becomes `app` with a result note, and an explicit `here` is refused with `deliver: app`, as is a chat CronService refuses (Channel gone or of another Agent, a Project job). On update both are read against the Agent that runs the job after the update.
- **Watch** (user decision 2026-10-20; job semantics in `automation/cron-watch.md`). `watch` is one string: an http(s) URL when the whole value is one (`https?://\S+`), any other text a command, so `curl -s <url>` stays a command. A URL CronService refuses is refused with `watch "<url>" is not a valid http or https URL.`, a command over 4,000 characters with the advice to save it as a script file. On update `none` stops watching; on create it is dropped. Only repeating schedules take a watch: a one-time or event schedule is refused with the call with `<repeating schedule>` and, on create, the call without `watch`. A `create` or `update` that sets or changes a watch waits, after releasing the reference lock, at most 90 s for the first check (`CronService.await_first_check`) and adds one note: the output was recorded, the check failed (`last_check_error` shows why), or it still runs; an update that resends the stored watch adds none.
- Results are plain fields, not the persisted record. A job result carries `id`, `name`, `status`, `schedule`, `event` (event jobs: `<title> (<event id>)`, or the id alone when the event is gone), `next_run` (an active event job with no occurrence ahead: `none; no occurrence of the event lies ahead`), `target`, `deliver` (`none`, `app`, or `chat <chat>[, thread <id>,] of Channel <id>`), and, when present, `session` (a pinned Session), `repeat` (limited recurring jobs only), `watch` (the command or URL), `last_check` (local time of the latest check) and `last_check_error`, `last_run`, `last_outcome` (`success (answered [SILENT])` after a silent Run), `last_error`, `failures_in_a_row`, and `note`. A one-time job shows its local fire time as `schedule` and no `next_run`. All times are server-local ISO values with offset. `list` returns `jobs` (count), `timezone` (server zone name) and one text block per job (all jobs, one by `id`, or the jobs of an `event_id`) ending in an indented `prompt:`; a `failed` job's block names the enable call that restarts it (`stopped after failed runs`, or `failed checks or runs` for a watching job). Delete returns `id`, `name`, `status: deleted`. No result carries `retryable`.

## Argument reading

`_cron_arguments.normalize_cron_arguments` runs before schema validation and executes a call whose intent is unambiguous; it never writes to a guessed job or target and never drops a requested effect. When readings differ, it raises `CronCallRefused` (an `invalid_arguments` failure) before any job changes, and every refusal starts with `cron was not run:` and ends with the exact corrected call, or with one call per reading.

The normalizer owns operation wrappers, action and state fields, and call-wide
validation. Its private `_cron_schedule_arguments` unit owns schedule spellings,
time literals and calendar-event offsets; `_cron_call` owns refusal accumulation
and corrected-call rendering shared by those readers. `_cron_arguments` retains
the existing imports for the handler and time-zone reader.

- Shapes: a JSON-string or `request`/`arguments` wrapper, one operation key (`{"create": {...}}`, `{"list": "{}"}`, `{"delete": true}`), and `job`/`data`/`payload` objects (OpenClaw `agentTurn` payloads). Placeholder-only operation keys are ignored; two real operations are refused with both calls.
- Spellings: earlier vBot fields (`agent_id`, `cron_expression`, `run_at`, `schedule_type`, `job_id`, `session_id`), Claude Code (`cron`, `recurring`, `durable`), Hermes (`job_id`, pause/resume/remove, `deliver`), OpenClaw (`schedule` objects with `kind`/`expr`/`at`/`everyMs`/`tz`, `sessionTarget`, `delivery`), and scheduled-task Tools (`cronExpression`, `fireAt`, `description`), plus action synonyms. Spelled and ISO 8601 durations, `@daily`-style macros and interval numbers with a unit are converted. One-time keys (`run_at`, `at`, `atMs`, `fireAt`, `timestamp`...) read a clock time (`"09:00"`, `"9:00"`, `"0900"`, `at 09:00`) as the canonical `at HH:MM`, which `zoned_schedule` turns into its next occurrence in the named or server zone (with a note; a skipped or repeated time is refused with each instant); 12/14-digit strings as a compact local timestamp; 10-digit strings and numbers in 1e9..1e10 as epoch seconds, 13 digits and numbers in 1e12..1e13 as epoch milliseconds (`*Ms` keys take only milliseconds). An epoch is an instant in every zone, so a `timezone` next to it is dropped. Other digits and numbers (`900`, `"2400"`) and an 8-digit date are refused with a stand-in schedule.
- Session and delivery spellings (`_read_session`, `_read_delivery`): Session keys (`session_id`, `sessionKey`, `sessionTarget`) read words for this conversation (`current`, `this`, `main`, OpenClaw's Session of origin...) as `current`, words for a new Session (`new`, `isolated`...) as `new` (dropped on create), and any other string as a Session id; an object or a `<stand-in>` is refused. Delivery keys (`deliver`, `delivery`, `notify*`, `announce`) read words and booleans as `here`, `app` or `none` (OpenClaw `{"mode": "none"}` is `none`, `announce` is `here`); a platform name (`telegram`...) is `here` plus `deliver_platform`, which the handler honors only in a chat on that platform and otherwise refuses with `deliver: app`. A named other chat (`telegram:-100123`, OpenClaw `to`) is refused with `here` and `app`, an unknown target with all three.
- Refused as ambiguous or unavailable, with calls: a bare duration (`in` or `every`), two schedules without a type, a repeating schedule marked one-time, six-field cron, a date without time, unit-less interval numbers, a Session value that names none, a delivery to another chat or an unknown target, a non-`agentTurn` payload, run-now (offers a one-time `in 1m` job), stop/cancel (offers disable or delete), a bare `id` (offers delete/disable/enable/list), create with an `id`, update without an `id`, and job fields on list (offers list without them, or update/create) or delete (offers delete without them, or update). Every Send is valid as sent: a refused value is never echoed back; six-field cron and a date without time show a stand-in schedule (`_Problems.add(..., schedule=<stand-in>)`).
- Watch spellings (`_read_watch`, before the schedule is read): `watch` and `monitor` take a string or the RPC object `{"command": ...}`/`{"url": ...}`; `watch_url`, `monitor_url` (Hermes) and `check_url` a URL, with `https://` added to one without a scheme; `watch_command`, `monitor_command`, `check_command` and `watch_cmd` a command. `none`, `off`, `no`, `nowatch`, `false` and the boolean false mean `none`; other placeholders (`null`, `""`) are omitted, so a Model that fills every field clears no watch. A `<stand-in>` is refused without a Send. Script gates are refused with the watch stand-in `<command or URL to check>`, because a job runs no script of its own and always runs its prompt: `script`, `monitor_script`, `watch_script`, `trigger_script`, Hermes `no_agent: true`, and an OpenClaw `trigger` object with a `script`.
- Self words as target (`self`, `me`, `current`, `this`, `default`...) become the canonical `SELF_TARGET`, which the handler resolves to the calling Agent on create and update (so an update moves the job to the caller, never a silent no-op). Placeholders (`<name>`, `placeholder`, `TBD`) are omitted; a placeholder prompt on create is refused with a request for the full instruction. A stand-in in angle brackets as `prompt` on update or as `target` is refused too (without a Send), because dropping it would lose the new instruction or run the job as the caller. `repeat` words `unlimited`/`forever` mean null.
- Event times (`_read_event_schedule`, `event_time_readings`): with an `event_id` (also spelled `event`, `calendar_event_id`...), the schedule is read from `schedule`, `offset`, `trigger`, `time`, the at/in keys, reminder-offset keys (`minutes_before: 30`, `minutes_after_end`, `before_start`...; `_EVENT_OFFSET_KEYS`), or the stored `edge` + signed `offset` minutes. `-PT30M`, `-30`, `30 minutes before`, `at the end` and `start-30m` all reach the canonical form; a bare edge beside an offset from that edge merges. A value with two readings is refused with one call per reading: unsigned `30m`/`30` (before or after the start), `+30m` or `30 minutes after` (from the start or from the end); several different times are refused with each. A `repeat` beside an `event_id` is refused (`a job at a calendar event runs at every occurrence of the event, so it takes no repeat. Nothing was changed.`, with the call without it), `repeat: null` is dropped, and a time zone is dropped because event times follow the event. On update without `event_id`, a reminder-offset key (or an edge plus a signed offset) alone becomes the schedule of the job's event. A valid event time sent without any `event_id` is refused with the `<calendar event id>` stand-in; an unknown event is refused with `no calendar event has id "<id>".`, naming the calendar list when the calendar Tool is offered (`ToolContext.offers`).
- Late-start limits have no effect (user decision 2026-10-08, `automation.md` -> Catch-up): `max_delay` and the spellings Models use for it (`maxDelay`, `max_lateness`, `late_limit`, `catch_up_window`, `misfire_grace`, `grace_period`, `starting_deadline`, the `*_seconds` forms, APScheduler `misfire_grace_time`, Kubernetes `startingDeadlineSeconds`, Hermes `catch_up_missed`/`catch_up`/`run_missed`/`start_when_available`, OpenClaw `skipMissedJobs`/`skip_missed`). `core/tools/_durations.take_late_limits` removes each one whose value is not empty or a placeholder, and the unadvertised `late_limits_note` carries a note to the handler: `"<key as sent>" has no effect.`, what happens to a missed fire, and that a prompt can tell a late Run to skip the instruction. The call executes. `with_late_limits_note` appends the note to the result's `note`; a refusal carries it before its `Send:` (after the cause when no call follows; before the cause of a choice), so a corrected call never drops the field silently. An update whose only change is a late-start limit gets the normal `update needs a field to change` refusal with the note (`test_late_start_limits_have_no_effect_and_the_result_says_so`, `test_update_needs_a_change`).
- State: `status`/`enabled`/`paused` spellings become the unadvertised `enabled`. On create, active is the default and dropped; inactive creates a `paused` job whose result note names the enable call (the intent is clear and the state is visible, so failing would only cost a round trip). On update and enable/disable with changes, it sets active or paused. Terminal statuses and conflicting values are refused.

## Time zones

Jobs store no zone of their own (a per-job zone would change the persisted format). Event jobs drop a sent zone: they follow their event's occurrences. `_cron_timezone.zoned_schedule` reads a named zone against the server zone and executes only when every fire lands on the instant the named zone means. `_named_zones` finds the exact instants at which each zone changes its UTC offset over the coming year (hourly scan, bisected to the second, cached per zone and day); the difference between server and named time is read now and just after each such change, never sampled. The scheduler steps server wall-clock time (a skipped fire moves past the gap, a repeated hour fires once), so a conversion is exact only when that difference is constant all year: then both zones skip and repeat at the same instants.

- the server zone (by key, or a difference of zero all year), or a relative schedule: dropped;
- an offset-free timestamp that names one instant in that zone: converted to the server-local instant, with a result note naming both times. A time the zone skips or repeats is refused with one server-time call per instant (`does not exist in <zone>` / `happens twice in <zone>`);
- a timestamp with an offset: an absolute instant, executed when the offset is one that zone has at that local time; otherwise refused with the time as written and each reading in that zone;
- cron fields: shifted, with a note, only when the difference is constant all year and the shifted fields fire at the same instants: every fire keeps its day, or every fire moves by the same day while only weekdays are restricted (the weekday field moves with it). Examples that execute: UTC server, Asia/Tokyo `0 3 * * 1` -> `0 18 * * 0`; Europe/Berlin server, Europe/London `*/15 1-3 * * *` -> `*/15 2-4 * * *`. Fields that cannot follow the shift (hour `*` or an hour range crossing midnight with restricted days, a restricted day of month or month that would move, a partial-hour shift of a non-literal minute) are refused with a server-time stand-in. A difference that changes during the year is never exact, even for `*`-hour fields: refused with today's conversion (or the same fields, when they do not change) as the Send, naming why it drifts around the clock changes;
- an unknown zone with a wall-clock schedule, or a zone alone on update: refused.

## Constraints & Gotchas

- Target failures use the codes shared with the Status and Sub-Agent Tools: `agent_not_found`, `project_not_found`, `agent_unavailable` (keeps the resolver's reason), and `invalid_arguments` for a malformed address. They carry target guidance instead of call shapes. An unknown id is `job_not_found` and points to `{"action":"list"}`.
- A one-time time already past on create, update, or enable fails with the past local time, the current time, and the corrected call with the `<future time>` stand-in (for enable, an update call); an update with no change shows `schedule` as the `<when>` stand-in. Refusals never invent a schedule the Agent did not send. A completed or missed job is immutable; the error suggests a new job or the delete call.
- A repeat is consumed when `TriggerService` admits or queues the Run. A fire missed while vBot was not running starts once, late, with a System Reminder naming its due time (`automation.md` -> Catch-up). `last_outcome: missed` and status `missed` appear only on jobs that earlier versions skipped by `max_delay`. Five consecutive recurring failures stop a job as `failed`; enable restarts it and resets the streak.
- The Tool cannot fire a job on demand, carry a per-job time zone, or deliver to a chat other than the calling one; these are refused rather than approximated.
- An update that sends an unsigned event time such as `30m` without `event_id` gets the generic `in`/`every` choice: the normalizer runs before the job is read and cannot know that the job is at an event (open point).

| `Carry out the instruction that follows now, and adapt any part of it that depends on when it runs, ...` | Without it Agents either refuse the stale task or send a "good morning" at noon and report on the wrong period. |
| `If the instruction no longer makes sense this late, say so instead of carrying it out.` | Without `max_delay`, a late Run whose task has become moot (a wake-up call at noon) must be able to decline it instead of doing it anyway (user decision 2026-10-08). |
