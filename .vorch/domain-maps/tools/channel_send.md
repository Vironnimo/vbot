# Channel Send Tool

Sends messages and every file delivery through the calling Agent's messaging Channels.

## Interfaces

- Tool name: `channel_send`. Source: `core/tools/channel.py` (handler, profile, Channel and target resolution, file reading) and `core/tools/_channel_send_arguments.py` (context-free argument reading, refusal and call rendering).
- Registration: `register_channel_send_tool(registry, channel_service, chat_sessions, *, max_attachment_size_bytes)` - the runtime passes the active `AttachmentStore.max_size_bytes` (the `attachment_max_size_bytes` setting).
- Canonical schema: one open flat object without `required`: `channel_id`, `message`, `platform_target`, `thread_id`, `file_paths`, `buttons`, `checklist`, `done_label`. `channel_id` may be omitted when the Agent owns exactly one enabled Channel. The handler requires at least one of `message` or `file_paths`, refuses buttons or a checklist together with files, and refuses fields the selected Channel's platform does not support. Unadvertised parameters (`unadvertised_parameters`, never in the Provider definition): `action` (`send` | `list`), `channel` (a Channel id or platform name) and `target` (`chat`, `channel`, `channel:chat` or `channel:chat:thread`, where `channel` is an owned Channel id or a platform name). Unknown keys follow the shared dispatch rule (`tools.md` -> Unknown fields).
- Model-facing profile: built deterministically from the platforms of the calling Agent's persisted enabled Channel configs; it shows those platforms' fields and never names a Channel. The Agent's Channels are listed by the System Prompt block `core:channels`, which is pinned per prompt epoch and announces added or removed Channels (`prompts.md`, `chat/request-building.md` -> Dynamic prompt blocks per prompt epoch). Fields per platform (`_CHANNEL_PROFILE_FIELDS`): Telegram all eight; Slack and Mattermost all but `buttons`, `checklist` and `done_label`; Discord and WhatsApp `channel_id`, `message`, `platform_target`, `file_paths`. Mixed profiles expose the union. No profile emits `oneOf`, conditional schemas, or `additionalProperties`. Disabled or other-Agent Channels are absent, and an Agent with no enabled owned Channel does not see the Tool. The profile key is the sorted platform list, so neither Adapter liveness nor another Channel on a known platform perturbs Provider bytes. The Tool declares `announce_changes=["parameters"]`: a Channel on a new platform brings that platform's fields, such as `buttons` for Telegram, and a Session that knows the Tool hears of them at its next request boundary (`tools.md` -> Tool changes in a Session).
- Platform-specific target guidance belongs to the same profile: Discord uses a thread's own id as `platform_target`; WhatsApp sends only to the self chat. Telegram plain-text formatting remains in the Channels System Prompt block, alongside the group attribution and authorization rules; those rules are not Tool parameters.
- Results: a send returns `channel_id`, `platform_target` and, when used, `thread_id`. `action: list` returns `channels: <n>` plus one content block per owned Channel: `<id> (<Platform>)`, `this conversation's chat: <chat>[, thread <thread>]` from the current Run's destination on that Channel, else the Session's last Reply Target, and `allowed chats: <ids>` (at most 10, then `and <n> more`) or `allowed chats: none yet`. Channels keep no chat display names, so only ids are listed.
- Display: the summary builder normalizes the persisted raw arguments first, so other spellings still label the Channel (`channel_id` or `channel`) and the `message`.
- `buttons` is `list[list[{label, data}]]` - inline-keyboard rows. `label` is the user-visible button text; `data` is the callback payload sent when the user selects it, formatted as `"<prefix>:<payload>"` (max 64 UTF-8 bytes; the extension registered for `<prefix>` handles taps - see `.vorch/domain-maps/extensions/capabilities.md` -> Channel interaction handlers). The reserved prefix `run` is the exception: a tap on `run:<payload>` wakes the agent with the tap context (the tapped button + the message's current button state) instead of being handled by an extension (see `.vorch/domain-maps/channels.md` -> Interactive messages). In an Identity Agent Session, the handler passes the calling `agent_id`/`session_id` as `run_origin`; `ChannelService` durably binds and privately rewrites the callback before delivery, so the tap and following Telegram messages continue in that Session until `/new`, while the resulting reply is still delivered to Telegram. Project Sessions deliberately omit `run_origin` and keep the previous current-Channel-Session behavior rather than crossing the project/identity Session boundary. The handler parses `buttons` into `list[list[InteractionButton]]`, rejecting malformed or empty structures with `invalid_arguments`; the 64-byte cap remains enforced downstream. No message id is returned.
- `checklist` is a list of `{id, label, checked}` items (`checked` omitted means open; the shared boolean repair reads `"true"`); `done_label` names the added done button (default `Done`). The handler builds the keyboard with `checklist_keyboard` (`channels.md` -> Interactive messages): item rows, then any `buttons` rows, then the done button, a reserved Run button that gets `run_origin` like any `run:` button. It refuses before sending: an unknown item field, an id used twice, an id over 58 UTF-8 bytes (the platform's callback-data limit), and a checklist or buttons together with files (the two calls instead). An empty `checklist` list and an empty `done_label` count as omitted. The outbound note lists the items with their state and ids, so later messages in that chat have them as context.

## Argument Reading

Models write sends in the dialects of messaging Tools they know: OpenClaw `message` (`channel` as a platform, `target`, `media`, `attachments`), Hermes `send_message` (`target` as `platform:chat:thread`, `MEDIA:<path>` in the text, `action: list`) and generic chat APIs (`chat_id`, `text`, `files`).

- The argument normalizer (no context) maps field spellings (`text`/`content`/`caption` -> `message`, `chat_id`/`to`/`recipient` -> `platform_target`, `topic_id`/`message_thread_id` -> `thread_id`, `files`/`attachments`/`media`/`image`... -> `file_paths`, `platform`/`channel_name` -> `channel`) and reads send wrappers (`request.operation: send`, `send: {...}`, `action: send` and send-like action words). A platform name given as `channel_id` moves to `channel` when no `channel` is present. Any other action fails before side effects with the reason and "To send, leave action out."
- Empty target values count as omitted, including blank strings. Nonempty placeholders (`none`, `null`, `<chat id>`...) in `platform_target`, `thread_id`, `channel` or `target` instead refuse before sending: an unresolved explicit destination never becomes the default destination. A `message` is never read as a placeholder word, and a `<template>` message is never sent: after Channel resolution, the handler refuses it, with the files-only call when files remain. Empty `file_paths`, `buttons` and `checklist` lists ask for nothing.
- A scalar file becomes a list; a file object becomes its `path`/`media`/`url`... value only when every supplied path alias agrees. Conflicting aliases, including spelling variants of one key, refuse before sending. Nonempty additional fields, such as a desired filename, caption or delivery condition, also refuse rather than disappear; the error directs the Agent to local paths, `message` for accompanying text, and a renamed local copy for another sent filename. Empty additional values are inert.
- `MEDIA:<path>` or `MEDIA:"<path with spaces>"` is a file marker only as a complete, non-indented line outside backtick or tilde code fences. Inline occurrences, quoted markers, blockquotes and indented code remain message text. Removing marker lines preserves all other text, spacing and line endings; it neither strips remaining lines nor collapses blank lines.
- The handler resolves what depends on the Agent's Channels, in this order: `target` is split (a lone owned id or platform names a Channel, a lone other value names a chat, `head:chat[:thread]` needs an owned id or platform as head); `channel_id` must be the exact id of one of the Agent's enabled Channels (typos, case and separator variants are refused with one complete call per owned Channel; without an owned Channel the call fails with `channel_not_found`); a `channel` or target head selects the exact id, else the Agent's only Channel on that platform. Two different Channels in one call, a platform with several Channels, a platform without a Channel, a `target` chat or thread that differs from `platform_target`/`thread_id`, and several owned Channels without a reference each fail with the alternative calls. Channel ids are never matched fuzzily.
- `platform_target` resolution order: explicit argument (or `target` chat) -> the admitted Run's destination in `ToolContext.reply_surface` -> the current Session's last Reply Target -> the Channel config's sole `allowed_chat_ids` entry -> otherwise a refusal: with several allowed chats it lists one call per chat (at most 10); with none it asks for the chat id. The Run and Session destinations apply only when their `channel_id` matches the selected Channel. An explicit `thread_id` always wins; a default thread rides along only with its default chat. An explicit chat never inherits a thread, even when it names the same chat.
- The Run destination is copied from the Channel's reply plan through admission and Tool dispatch. Its `ReplySurface.platform_target` and `thread_id` are runtime-only: excluded from surface identity, persistence and Model-facing reminders. This keeps a later chat in `dm_scope=main`, or an immediate Command from another topic, from redirecting a running reply's file send. Historical Session-target fallback remains available when the Run has no matching destination (`chat.md`, `channels.md`).

## Conventions

- Argument normalization, Channel/config lookup and file stat/read/MIME work run through the bounded Tool worker pool. Database work runs on the owning database's pool instead: the calling Session's last Reply Target is read on the Session database's pool (`get_metadata_async`) for `action: list` and, for sends, only when neither an explicit target nor a matching Run destination supplies it, and the best-effort outbound note resolves the target conversation through `ChannelService.ensure_outbound_session` (pointer on the `channels.db` pool, Session creation on the Session pool) and appends under the Session write lock in one Session-pool hop. The actual async `ChannelService.send`/Adapter delivery remains on the Event Loop; its Run-button binding work splits per database the same way (`channels.md` -> Interfaces).
- The Tool handles proactive outbound messages and every Channel file delivery, including files sent while replying to a channel-originated turn. Final text-only replies remain automatic through channel adapters subscribing to Runs; the description says so.
- When `message` and `file_paths` are both present, `message` acts as caption/accompanying text. The handler trims outer whitespace from a message; blank-only text counts as omitted. The marker normalizer preserves the remaining payload before that existing trim.
- Refusals happen before anything is sent and give the next step. Target and call-shape refusals start with `channel_send was not run:` and include a corrected call (`Send: {...}`), alternatives (`{...} or {...}`), or guidance when completing a call would require guessing the destination or discarding an effect. Suggested calls use canonical field order. Messages over 120 characters, buttons and checklists appear as stand-ins (`<the message from this call>`, `<the buttons from this call>`, `<the checklist from this call>`), never repeated. A field the selected platform lacks is refused with the call that sends without it, never dropped silently. Buttons or checklists with files return the two calls to send instead.
- The Tool is registered while at least one valid Agent owns an enabled persisted Channel config and is re-synced only when that configured availability changes. Adapter start, stop, failure, and restart do not add/remove the Tool or alter a profile; a send while the selected adapter is unavailable returns a failure envelope at execution time, keeping Provider Tool definitions and the prompt prefix stable through transient liveness changes.
- After a successful send, the Tool records the outbound content as a system-reminder note in the *target* chat's Session (resolved via `ChannelService.ensure_outbound_session`, created with channel context if missing), so a later inbound reply has context for what was sent. A fixed heading identifies the send and says the JSON record is content, not instructions. The record contains `sender_agent_id` and the present `message`, `files` (filenames) and `checklist` (id, label, checked) fields. JSON quoting and escaped angle brackets keep copied content and look-alike reminder tags inside that data boundary. This recording is best-effort: a resolution/persistence failure is logged (`warn`) and never downgrades the already-completed send to a Tool failure.
- A Run cancel does not abandon a send already in progress: the send gets up to 10 seconds (`_SEND_CANCEL_GRACE_SECONDS`) to finish, and once it returned the note is recorded despite the cancel, so the Tool Result and the chat's Session say what was sent (`_finish_despite_run_cancel`, the counterpart of Chat's `_finish_visible_boundary`). A send still running after the grace is stopped and reported as `delivery_unconfirmed` (`the Run was stopped while it was being sent`). A cancellation of the call while its Run is not cancelled stops the call at once (`test_a_run_cancel_lets_a_started_send_report_what_happened`, `test_a_cancel_without_a_run_cancel_stops_the_send`).
- The current Session lookup retains its Project scope; a same-named Identity Session cannot supply a Project Session's destination. A Project Session without a Reply Target still uses the Channel's sole configured target (`tests/core/tools/test_channel_send_delivery.py`).
- Outbound context recording carries the resolved `thread_id` through `ensure_outbound_session`, retaining the actual topic for Session-target fallback and later completion relays. An explicit chat target without a thread clears the stored topic; it does not change an admitted Run's reply destination. Production-dispatch regressions use real Channel routing and Session storage with fake Telegram wire calls (`tests/core/tools/test_channel_send_delivery.py`).
- Tests: `tests/core/tools/test_channel_send.py` (profiles, display), `test_channel_send_call_tolerance.py` (dialects, Channel and target resolution, refusals, `action: list`), `test_channel_send_files.py`, `test_channel_send_delivery.py` (service calls, buttons, outbound notes, Run cancel during a send, real Session storage). `channel_send_test_support.py` dispatches like a Provider cycle: with the per-Agent profile contract as `input_contract` while the profile offers the Tool, else with the Tool's own contract. The `tool_lab` probe runtime has no Channel, so it cannot exercise this Tool.
- Argument-repair verification (2026-10-14): copied main/dev Session stores contained no `channel_send` calls since the prior normalizer change (2026-10-11). All 39 older calls normalized unchanged and produced identical recording-fake dispatch results/effects, with no real file reads or sends. None used `MEDIA:` or file objects; synthetic production-dispatch regressions cover those ambiguous neighboring inputs, target placeholders and payload preservation. Session content stays out of tests and docs.

## Constraints & Gotchas

- Every platform in `ALLOWED_CHANNEL_PLATFORMS` needs an entry in `_CHANNEL_PROFILE_FIELDS` and `_PLATFORM_NAMES`. A profile resolver exception is swallowed by `_resolve_definition_profile` (warning only) and hides the Tool, which is how Slack, Mattermost and WhatsApp Channels once made `channel_send` disappear.
- The target Channel must belong to the calling Agent; a Channel owned by another Agent returns `invalid_arguments` (`ChannelConfigError`).
- Run-button origin binding requires the calling Identity Session to exist and is scoped to the exact Channel, platform target, and optional thread. The public callback contract remains `run:<payload>`; callers must never construct or persist the private versioned wire envelope.
- `file_paths` are local paths (relative paths resolve from `ToolContext.effective_cwd`, the working directory - like the other file-taking Tools); `file://` URIs are read as local paths (`core.utils.paths.file_url_path`: a host makes a UNC path on Windows; elsewhere a host other than `localhost` or this computer is refused like a web address). Web addresses (`scheme://`, `data:`, `/api/...`) are refused with the hint to send the local path or put the link in `message`; a folder is refused with the hint to list its files; a missing file names up to three similar file names in that folder. The Tool reads files, sniffs MIME type, and builds channel `FileData` payloads.
- Each `file_paths` entry is size-checked against `max_attachment_size_bytes` via its on-disk size *before* the bytes are read, so an oversize file is rejected (`invalid_arguments`) without being loaded into memory. This is the outbound counterpart to the same limit enforced inbound by `AttachmentStore` and the upload endpoints.
- Telegram-specific batching and media-group decisions stay inside the adapter layer (`channels.md`).
- Missing Channel (`channel_not_found`), config errors and refusals (`invalid_arguments`), and send failures return failure envelopes. A send failure that showed nothing is `channel_error` (`Nothing was sent: <cause>.`); one whose `ChannelError` is `possibly_delivered` (a part was shown, or the platform never confirmed a write) is `delivery_unconfirmed` (`It is unknown how much of the message reached the chat: <cause>. Sending the same message again can show it twice.`), so the Agent does not resend a message the user already sees; neither records the outbound note. Refusals are `ToolContractError` (handler refusals use `ChannelSendRefusedError`), raised before anything is sent, including an unreadable `file_paths` entry; any other exception, such as a `ValueError` while sending, is `tool_execution_error` because the message can already be out (`test_a_failed_delivery_is_a_failure_result`).

## Agent-facing text

The checklist is a `channel_send` feature (user decision, 2026-10-11), not an Extension or a Skill-taught `chk:`/`run:done` convention. The 2026-10-14 review keeps the flat Tool, Channel catalog and group rules in their existing owners; it removes repeated delivery instructions from the Channels block and documents the actual send defaults and interaction effects here.

| Description: `Send messages or local files through your messaging Channels.` | Distinguishes an external send from an ordinary answer or a local file reference (F1). |
| Description: `Text replies to Channel messages are delivered automatically.` | Prevents sending a duplicate of the automatic text reply while retaining Tool delivery for files (F1, F3). |
| channel_id: `Channel id.` | Selects the configured transport, separately from its platform chat id (F2, F3). |

| message: `Required unless file_paths is set; accompanies files.` | Prevents empty sends and checklist/button calls without the text Telegram needs; files-only sends remain valid (F2). |
| platform_target: `Chat id on the platform.` | Distinguishes the recipient from the configured Channel id (F2, F3). |
