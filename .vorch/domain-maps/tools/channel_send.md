# Channel Send Tool

Sends messages and every file delivery through the calling Agent's messaging Channels.

## Interfaces

- Tool name: `channel_send`. Source: `core/tools/channel.py` (handler, profile, Channel and target resolution, file reading) and `core/tools/_channel_send_arguments.py` (context-free argument reading, refusal and call rendering).
- Registration: `register_channel_send_tool(registry, channel_service, chat_sessions, *, max_attachment_size_bytes)` - the runtime passes the active `AttachmentStore.max_size_bytes` (the `attachment_max_size_bytes` setting).
- Canonical schema: one open flat object without `required`: `channel_id`, `message`, `platform_target`, `thread_id`, `file_paths`, `buttons`. `channel_id` may be omitted when the Agent owns exactly one enabled Channel. The handler requires at least one of `message` or `file_paths`, refuses `buttons` together with files, and refuses fields the selected Channel's platform does not support. Unadvertised parameters (`unadvertised_parameters`, never in the Provider definition): `action` (`send` | `list`), `channel` (a Channel id or platform name) and `target` (`chat`, `channel`, `channel:chat` or `channel:chat:thread`, where `channel` is an owned Channel id or a platform name). Unknown keys are still refused by the shared validator.
- Model-facing profile: built deterministically from the calling Agent's persisted enabled Channel configs, sorted by platform/id. The `channel_id` enum holds the exact available ids, and the description ends with ` Channels: <id> (<Platform>), ...`. Fields per platform (`_CHANNEL_PROFILE_FIELDS`): Telegram all six; Slack and Mattermost all but `buttons`; Discord and WhatsApp `channel_id`, `message`, `platform_target`, `file_paths`. Mixed profiles expose the union. No profile emits `oneOf`, conditional schemas, or `additionalProperties`. Disabled or other-Agent Channels are absent, and an Agent with no enabled owned Channel does not see the Tool. The profile identity hashes only sorted `(platform, channel_id)` configuration, so Adapter liveness cannot perturb Provider bytes.
- Results: a send returns `channel_id`, `platform_target` and, when used, `thread_id`. `action: list` returns `channels: <n>` plus one content block per owned Channel: `<id> (<Platform>)`, `this conversation's chat: <chat>[, thread <thread>]` when the Session's last Reply Target is on that Channel, and `allowed chats: <ids>` (at most 10, then `and <n> more`) or `allowed chats: none yet`. Channels keep no chat display names, so only ids are listed.
- Display: the summary builder normalizes the persisted raw arguments first, so other spellings still label the Channel (`channel_id` or `channel`) and the `message`.
- `buttons` is `list[list[{label, data}]]` - inline-keyboard rows. `label` is the user-visible button text; `data` is the callback payload sent when the user selects it, formatted as `"<prefix>:<payload>"` (max 64 UTF-8 bytes; the extension registered for `<prefix>` handles taps - see `.vorch/domain-maps/extensions/capabilities.md` -> Channel interaction handlers). The reserved prefix `run` is the exception: a tap on `run:<payload>` wakes the agent with the tap context (the tapped button + the message's current button state) instead of being handled by an extension (see `.vorch/domain-maps/channels.md` -> Interactive messages). In an Identity Agent Session, the handler passes the calling `agent_id`/`session_id` as `run_origin`; `ChannelService` durably binds and privately rewrites the callback before delivery, so the tap and following Telegram messages continue in that Session until `/new`, while the resulting reply is still delivered to Telegram. Project Sessions deliberately omit `run_origin` and keep the previous current-Channel-Session behavior rather than crossing the project/identity Session boundary. The handler parses `buttons` into `list[list[InteractionButton]]`, rejecting malformed or empty structures with `invalid_arguments`; the 64-byte cap remains enforced downstream. No message id is returned.

## Argument Reading

Models write sends in the dialects of messaging Tools they know: OpenClaw `message` (`channel` as a platform, `target`, `media`, `attachments`), Hermes `send_message` (`target` as `platform:chat:thread`, `MEDIA:<path>` in the text, `action: list`) and generic chat APIs (`chat_id`, `text`, `files`).

- The argument normalizer (no context) maps field spellings (`text`/`content`/`caption` -> `message`, `chat_id`/`to`/`recipient` -> `platform_target`, `topic_id`/`message_thread_id` -> `thread_id`, `files`/`attachments`/`media`/`image`... -> `file_paths`, `platform`/`channel_name` -> `channel`), turns a scalar file into a list and file objects into their `path`/`media`/`url`... value, moves `MEDIA:<path>` tokens out of the message into `file_paths`, and reads send wrappers (`request.operation: send`, `send: {...}`, `action: send` and send-like action words). Empty strings, placeholders (`none`, `null`...) and `<template>` values count as omitted in the target fields (`platform_target`, `thread_id`, `channel`, `target`); a `message` is never read as a placeholder word, and a `<template>` message is never sent: after the Channel and chat are resolved, the handler refuses it, with the files-only call as the Send when files remain; empty `file_paths`/`buttons` lists ask for nothing. A platform name given as `channel_id` moves to `channel` when no `channel` is present. Any other action fails before side effects with the reason and "To send, leave action out."
- The handler resolves what depends on the Agent's Channels, in this order: `target` is split (a lone owned id or platform names a Channel, a lone other value names a chat, `head:chat[:thread]` needs an owned id or platform as head); `channel_id` must be the Agent's exact id (the per-Agent enum refuses typos, case and separator variants); a `channel` or target head selects the exact id, else the Agent's only Channel on that platform. Two different Channels in one call, a platform with several Channels, a platform without a Channel, a `target` chat or thread that differs from `platform_target`/`thread_id`, and several owned Channels without a reference each fail with the alternative calls. Channel ids are never matched fuzzily.
- `platform_target` resolution order: explicit argument (or `target` chat) -> the current Session's last Reply Target (only when its `channel_id` matches the selected Channel) -> the Channel config's sole `allowed_chat_ids` entry -> otherwise a refusal: with several allowed chats it lists one call per chat (at most 10); with none it asks for the chat id. An explicit `thread_id` always wins; the metadata thread rides along only with the metadata target.

## Conventions

- Argument normalization, Channel/config lookup and file stat/read/MIME work run through the bounded Tool worker pool. Database work runs on the owning database's pool instead: the calling Session's last Reply Target is read, only when no `platform_target` was given (and for `action: list`), on the Session database's pool (`get_metadata_async`), and the best-effort outbound note resolves the target conversation through `ChannelService.ensure_outbound_session` (pointer on the `channels.db` pool, Session creation on the Session pool) and appends under the Session write lock in one Session-pool hop. The actual async `ChannelService.send`/Adapter delivery remains on the Event Loop; its Run-button binding work splits per database the same way (`channels.md` -> Interfaces).
- The Tool handles proactive outbound messages and every Channel file delivery, including files sent while replying to a channel-originated turn. Final text-only replies remain automatic through channel adapters subscribing to Runs; the description says so.
- When `message` and `file_paths` are both present, `message` acts as caption/accompanying text.
- Refusals start with `channel_send was not run:`, happen before anything is sent, and end with the corrected call (`Send: {...}`) or the alternatives (`{...} or {...}`), rendered in canonical field order. Messages over 120 characters and buttons appear as stand-ins (`<the message from this call>`, `<the buttons from this call>`), never repeated. A field the selected platform lacks is refused with the call that sends without it, never dropped silently. Buttons with files return the two calls to send instead.
- The Tool is registered while at least one valid Agent owns an enabled persisted Channel config and is re-synced only when that configured availability changes. Adapter start, stop, failure, and restart do not add/remove the Tool or alter a profile; a send while the selected adapter is unavailable returns a failure envelope at execution time, keeping Provider Tool definitions and the prompt prefix stable through transient liveness changes.
- After a successful send, the Tool records the outbound content as a system-reminder note in the *target* chat's Session (resolved via `ChannelService.ensure_outbound_session`, created with channel context if missing), so a later inbound reply in that chat has context for what was sent. The note names the sending agent (`by agent "<agent_id>"`, the calling `context.agent_id`) and includes the message text and/or attached file names. This recording is best-effort: a resolution/persistence failure is logged (`warn`) and never downgrades the already-completed send to a Tool failure.
- Tests: `tests/core/tools/test_channel_send.py` (profiles), `test_channel_send_call_tolerance.py` (dialects, Channel and target resolution, refusals, `action: list`; dispatches with the per-Agent profile contract as `input_contract`), `test_channel_send_files.py`, `test_channel_send_delivery.py`, `test_channel_send_routing.py`. The `tool_lab` probe runtime has no Channel, so it cannot exercise this Tool.

## Constraints & Gotchas

- Every platform in `ALLOWED_CHANNEL_PLATFORMS` needs an entry in `_CHANNEL_PROFILE_FIELDS` and `_PLATFORM_NAMES`. A profile resolver exception is swallowed by `_resolve_definition_profile` (warning only) and hides the Tool, which is how Slack, Mattermost and WhatsApp Channels once made `channel_send` disappear.
- The target Channel must belong to the calling Agent; a Channel owned by another Agent returns `invalid_arguments` (`ChannelConfigError`).
- Run-button origin binding requires the calling Identity Session to exist and is scoped to the exact Channel, platform target, and optional thread. The public callback contract remains `run:<payload>`; callers must never construct or persist the private versioned wire envelope.
- `file_paths` are local paths (relative paths resolve from `ToolContext.effective_cwd`, the working directory - like the other file-taking Tools); `file://` URIs are read as local paths. Web addresses (`scheme://`, `data:`, `/api/...`) are refused with the hint to send the local path or put the link in `message`; a folder is refused with the hint to list its files; a missing file names up to three similar file names in that folder. The Tool reads files, sniffs MIME type, and builds channel `FileData` payloads.
- Each `file_paths` entry is size-checked against `max_attachment_size_bytes` via its on-disk size *before* the bytes are read, so an oversize file is rejected (`invalid_arguments`) without being loaded into memory. This is the outbound counterpart to the same limit enforced inbound by `AttachmentStore` and the upload endpoints.
- Telegram-specific batching and media-group decisions stay inside the adapter layer (`channels.md`).
- Missing Channel (`channel_not_found`), config errors and refusals (`invalid_arguments`), and send failures (`channel_error`) return failure envelopes.
