# Session Search

Finds conversation content in past Sessions and returns bounded excerpts with canonical conversation context. Extended inspection belongs to the `vbot-cli` Skill, not another Recall Tool.

## Interfaces

- `core/tools/session_search.py` owns the definition, validation and execution; `_session_recall_results.py` owns internal result shaping and the visibility recheck. The selected Recall backend ranks hits over Recall-visible Sessions; canonical `ChatSessionManager` classifies visibility and supplies descriptors and bounded context.
- One flat Provider schema: required `query`, optional `period`, `agent_id`, `session_id`, and boolean `include_subagents`. No `additionalProperties` keyword. The handler also accepts an unadvertised `limit` (also `max_results`/`top_k`, whole number or digit string): 1-10 sets the hit count, a larger value runs with 10 and the result's guidance says so, anything else fails naming the valid range. Backend capabilities supply the summary and query wording. Omitting or blanking `query` fails; there is no Session-list mode or `session_read` Tool.
- Omitted `agent_id` uses the current Agent; omitted `session_id` searches across that Agent's eligible Sessions. The current Agent/Session pair is excluded before ranking. An equal Session id belonging to another Agent remains eligible. Project scope comes only from `ToolContext.project_id`.
- Legacy Sessions without reliable `run_kinds` and Sessions carrying `user`, `channel`, `cron`, or `calendar` are eligible. Reflection kinds and system-only Sessions are always hidden. Sub-Agent markers or Run kinds require `include_subagents: true`; the opt-in never reveals reflection or system-only Sessions. Mixed reflection/User Sessions stay hidden; mixed User/System Sessions stay eligible. The Session store classifies this Recall visibility in SQL (`sessions.md`); the Tool passes `include_subagents` in the request, backends apply it before ranking, and shaping rechecks each hit Session through its descriptor source. The only explicit exclusion is the current conversation.
- `period` is an inclusive ISO-8601 `start/end` interval with either endpoint optionally open. Dates, months (`YYYY-MM`) and times without an offset read in the Settings timezone (`effective_timezone_name`, loaded per call through `RecallIntegration`'s `timezone_name_loader`, so a Settings change applies to the next search; UTC when no loader is registered). A date or month start begins at its first 00:00 and an end includes all of it; a single date or month without `/` means that whole day or month. Explicit offsets and `Z` are kept. Reversed endpoints are interpreted as the same inclusive range. A single timestamp without `/` fails with the open-range call (`"<value>/"`). Period applies to matching evidence; nearby context can lie outside it.
- Ordinary search uses User/Assistant content plus labeled Compaction summaries. Tool Results, Tool arguments, reasoning, errors, Skill contexts, and persisted Recall results are excluded. Content Blocks contribute their searchable text projection; search is not an attachment-content reader.
- `sqlite_fts` is the default: all whitespace-separated terms must match. When every term has at least three characters, trigram provides substring matching; otherwise standard FTS provides whole-token matching for the query. `vector` and `hybrid` retain semantic and combined retrieval; Hybrid's literal Passage arm applies the same three-character rule with a whole-token Passage index. `canonical_scan` is the internal base scan backend, not a selectable backend; `sqlite_fts` degrades to the Session store's substring scan when its index is unavailable. Every returned literal hit matched the query, so result pages are full whenever enough matches exist.
- Dispatch retains shared argument normalization. The Tool additionally repairs recognizable search intent: field casing/separators, the established `qurey` typo, common selector aliases, search-only action/request wrappers, boolean encodings, and since/until intervals. Conflicting values are checked before empty known selections become omission. Unknown fields, including empty-valued fields, remain errors (paging fields such as `page`/`offset`/`cursor` add that there are no result pages); no nearest-name matching infers an unsupported feature. Contradictory duplicate keys in encoded JSON fail before search. Pagination, role/match/order controls and transcript/list operations remain outside this Tool's capability; recognizing a search wrapper does not add those operations.

## Results

- Success uses the normal Tool envelope. Data includes the searched `agent_id` and `project_id`, the resolved `period` when one was given (inclusive endpoints with offsets, plus the timezone name in parentheses when an endpoint was read in local time, e.g. `2026-07-01T09:00:00+02:00/2026-07-02T23:59:59+02:00 (Europe/Berlin)`), `items`, `sessions`, `has_more`, and candidate-Session count. State-specific guidance covers empty, truncated and additional results; degraded pages explain which retrieval remains available and its practical limitation. Empty search is a successful result. The display derives a presentation-only result count, a lower bound when `has_more` is true.
- At most ten backend-ranked Message or Passage hits are returned (fewer with `limit`; `has_more` guidance under a smaller limit points to omitting it). Multiple hits from one Session remain distinct so later corrections or separate matching passages are not collapsed. `session_id` narrows the same search and limit; it requires no prior listing call.
- Hits include rank, Agent/Session/Message identity, timestamp, a source-faithful excerpt and truncation flags. Single-Message hits include their role. Passages spanning multiple Messages use `content_kind: conversation_excerpt` instead of falsely assigning all text to the first speaker; they retain end Message identity and timestamp. Index ids, offsets and retrieval-arm names stay internal. Sub-Agent hits include `include_subagents: true` for a follow-up query. Compaction hits carry `content_kind: compaction_summary` and remain separate from verbatim conversation passages.
- `context` contains at most the enclosing User question and the last nonempty Assistant answer before the next User Message, excluding the hit itself. Each context record includes canonical index/id/role/time, up to 800 characters of text and a truncation flag. Context is always marked `context_is_partial`; it is not a full transcript or proof that no later correction exists. Missing/inactive anchors and summary anchors return no context.
- Context uses `ChatSessionManager.recall_context`, a targeted active-lineage SQL projection; ordinary FTS search never loads a full transcript or Tool graph to decorate a hit. Context is bounded in SQLite before text leaves storage.
- One descriptor per represented Session appears in first-hit order: Agent id, Session id, and an available title capped at 200 characters. One `descriptor_sources` read for the hit Sessions supplies titles and the visibility recheck; raw provenance, duplicate excerpts, counts and null-filled metadata are not returned.
- Excerpts preserve whitespace and Unicode and are capped at 1,800 characters. The complete result is capped at 50 KiB including descriptors and context; shaping first adapts excerpt size, then reduces hit count if fixed context/metadata requires it. `has_more` advises narrowing query, period or Session. Truncation guidance explicitly distinguishes the end of a visible excerpt from the end of its source Message.

## Extended inspection

The bundled `vbot-cli` Skill advertises extended Session search and transcript retrieval and routes to `references/session-search.md`. It teaches when existing excerpts suffice, Session listing through the CLI, read-only SQLite scope selection (Tool `project_id: null` means SQL empty string, not SQL NULL), complete active User/Assistant transcripts, match-centered substring previews including Tool Results, and generation-bound exact Result reads. Search previews return the generation needed for the exact read. It adds no Bash availability prerequisite, Tool grant, or new runtime API.

## Constraints & Gotchas

- Search is evidence discovery with selected context, not lossless transcript retrieval. There are no `read_ref`, reader continuations, or automatic companion Tool.
- Backend tuning and scores stay internal. Visibility is a request selection that backends apply from the Session store's classification, with a Tool-side recheck of hit Sessions; relevance ordering remains backend-owned.
- Historical persisted `session_read` results remain excluded as derived Recall artifacts even though the Tool no longer exists.
- Extension backends must return typed Search pages; visibility shaping rechecks their hit Sessions through descriptor sources just like first-party pages.
- Tests: `tests/core/tools/test_session_search*.py`, `tests/core/skills/test_session_search_reference.py`; backend behavior in `tests/core/recall/`; basic Provider call shapes in `scripts/provider_probe/scenario_history.py`. The reproducible `recall_workflow` scenario in `scripts/probe_provider_tool_call.py` uses production registrations and disposable SQLite: `--recall-case matrix` exercises all three backends, defaults, scopes, recoverable mistakes; `--recall-case all` exercises recovery from actual missing-query/unsupported-option errors and fresh-Agent workflows with the actual Skill and Bash. `--recall-report <path>` preserves synthetic calls, results and exported transcript evidence for review. Vector cases use deterministic fixture embeddings to evaluate continuation, not embedding quality. `tests/scripts/test_probe_recall_workflow.py` verifies the probe measures runtime results and real artifacts.
