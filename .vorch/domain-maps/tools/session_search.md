# Session Recall Tools

Discovers persisted Sessions through backend-native search and retrieves focused canonical conversation blocks or Tool Results through a separate read-only Tool.

## Interfaces

- `core/tools/session_search.py` owns both Tools and their result shaping. `session_search` receives the selected Recall backend plus canonical `ChatSessionManager`; `session_read` uses only canonical `ChatSessionManager`.
- `session_search` has one flat model-facing schema with optional `query`, `period`, `agent_id`, and `session_id`, `required: []`, and no `additionalProperties` keyword. The selected backend supplies the Tool summary and `query` parameter description, while the other fields stay backend-stable. Omitting `query` lists recent Sessions; providing it performs backend-native search, optionally restricted to one known past Session by `session_id`. Both paths return at most ten items and intentionally offer no public limit or continuation. The current Agent/Session pair is excluded before listing and first-party backend ranking; an equal Session id owned by another Agent remains eligible.
- `period` is one inclusive ISO-8601 `start/end` interval. Either endpoint may be open; a date-only start begins at 00:00 UTC and a date-only end covers the complete UTC day. Listing selects Sessions containing at least one default-role conversation Message in the interval; query search applies the same bounds inside Recall.
- `session_read` has one flat model-facing schema with required `session_id` plus optional `message_id`, `agent_id`, `continuation`, and boolean `all_messages`, and no `additionalProperties` keyword. Omitted `message_id` selects the latest conversation block and returns a compact index of every User anchor in the Session; an ordinary Message id selects the containing block from its nearest preceding User through the Message before the next User; a Tool Result Message id selects only that exact canonical Result; `all_messages: true` selects the complete canonical Session with the same large-Result projection and cannot be combined with `message_id`. The current Agent/Session pair fails with `current_session_unavailable`; current context and the compaction-gated `history` Tool own access to that conversation instead.
- Large selections are losslessly segmented as one serialized selection. The result supplies a stateless `next_continuation` token that binds the byte position to the complete selection; the Agent repeats the same arguments with that token, and changing `message_id` or `all_messages` fails with `invalid_continuation`. The token does not depend on a mutable server snapshot, and no public page-size control exists.
- Retired `request.operation`, `action`, operation-key objects, public backend match/order/role controls, result limit, cursors, Message ranges/indexes, tail counts, page sizes, split time bounds, and neighbor-count arguments are rejected.
- Search uses each backend's declared default ranking and matching behavior. Backend capabilities expose Agent-facing `tool_summary` and `query_description` alongside the internal result, match, order, and role capabilities; Tool registration rebuilds both the description and parameter schema from that one capability value. Backends may change wording but never the flat four-field Provider shape.

## Result Contract

- Every success is a normal Tool envelope with `items`, `has_more`, and `formatted_bytes`; segmented reads add `next_continuation`. Results carry no public `action`. Both Tool rows derive a presentation-only `results` count from the returned `items`; `has_more: true` renders the returned count as a lower bound, and failures publish no count.
- Session-list items contain Agent/Session identity, creation/activity timestamps, and a compact Session descriptor: title, classified `run_kinds`, tri-state `is_subagent_session`, safe Sub-Agent parent and fork provenance, Channel platform, Message count, and a whitespace-compacted excerpt of the first User Message capped at 240 characters with an explicit truncation flag. `period` filters which Sessions appear; it does not create a second range-reading contract.
- Descriptor provenance is a deliberate projection, never the raw Session sidecar. Sub-Agent parent and fork addresses retain only Agent/Session/Project identity plus the fork timestamp; Run ids, Tool-call ids, work ids, cache metadata, Channel conversation ids, and other internal metadata are not exposed. An absent or invalid legacy `run_kinds` value remains `null`; a valid mixed-origin list remains visible rather than being collapsed. `is_subagent_session` is `null` when legacy data provides no reliable classification, and Message count/excerpt are `null` when canonical Messages are unavailable.
- Search data identifies the resolved backend, result unit (`message`, `passage`, or `backend_defined`), ranking, and candidate-Session count. First-party pages also carry one `sessions` descriptor per unique Session represented by the returned hits, in first-hit order; hit items reference the Session by identity and do not repeat descriptor metadata.
- Every first-party search item has a page rank, canonical identifiers, one source-faithful adaptive `excerpt`, and a directly callable `session_read` `read_ref` containing `agent_id`, `session_id`, and the hit's anchor `message_id`. `session_read` derives the complete conversation block from canonical Session data, so search does not need to encode two Message boundaries.
- Search items do not repeat exact content in a second field. Every list and search result is capped at 50 KiB; list pages reduce their returned item count when descriptors exhaust the budget, while each search excerpt is capped at 800 characters and search pages reduce hit count only when metadata itself requires it.
- `session_read` returns Session metadata/counts, an explicit `selection` summary (`kind`, first/last absolute Message index, selected count), and selected `ChatMessage.to_dict()` records paired with their absolute zero-based canonical `message_index`. An unanchored read also returns `user_anchors` with each User Message's absolute index, id, timestamp, and a compact excerpt so an Agent can select any conversation block without another public parameter. In a conversation-block read, a Tool Result whose UTF-8 content exceeds 4 KiB remains at its canonical position but its content becomes a bounded redacted preview marker and the item gains a directly callable `read_ref` to that Result Message. Selecting a Tool Result by id bypasses projection and returns the exact canonical record; selections that exceed the 50 KiB result cap are returned through consecutive `selection_json` segments and remain reconstructable without loss, including the anchor index when present.
- An extension backend without the typed first-party search capability is wrapped as one `backend_defined` result and has no claimed first-party ranking semantics.

## Availability

- `session_search` is the single persisted/configurable capability. Runtime availability derives `session_read` whenever `session_search` is allowed, so existing allowlists gain the companion automatically and a search result never advertises an unavailable reader.
- `session_read` is not independently Project-configurable and is removed from persisted Agent allowlists. Wildcard allowlists expose both registered Tools.

## Constraints & Gotchas

- Exact content belongs to `session_read`, not `session_search`; Agents should pass a returned `read_ref` directly when wording, the complete conversation block, or a referenced Tool Result matters.
- Search is not implicitly Session-grouped. JSONL/FTS may return many Messages from one Session, and Vector/Hybrid may return many Passages from one Session.
- Persisted results from both Session Recall Tools are derived artifacts and are excluded from JSONL matching, Passage construction, FTS indexing, and Vector indexing to prevent recall feedback loops.
- No-match pages are successful empty results. Invalid or retired fields, missing canonical references, continuation tokens for a different selection, attempts to read the current Session, and backend failures are failure envelopes with stable codes.
- Search excerpts preserve source whitespace and Unicode. Their truncation flags and source offsets describe presentation loss only; canonical storage is untouched.
