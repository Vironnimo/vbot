# Process Tool

Lets an Agent inspect and control only its own background processes created by the `bash` Tool.

## Terms

### Tracked Process
**Definition:** One OS subprocess spawned through `ProcessManager` (always by the `bash` Tool today), identified by an opaque `process_id` and tracked in memory until exit plus a TTL sweep. The Agent addresses it in Tool results and `process` actions exclusively as `process_id`.
**Not:** A Chat Session or its id - those are separate namespaces even though both are opaque strings. Also not an arbitrary operating-system process: the Tool cannot discover or control anything `ProcessManager` did not spawn.

Shared OS launch flags, server-lifetime containment, and verified process-tree termination live in `core/utils/processes.py`; Bash/Process, Terminal, local Speech, and server startup use that owner. `ProcessManager` owns only tracked background command lifecycle and output.

## Data Model

- `process_id` values are distinct from Chat Session ids and identify only commands that `bash` started through `ProcessManager`. Every tracked process starts with stdin connected to `DEVNULL`; EOF is immediate and no later input can be sent. `TrackedProcess` has no input state or idle-input heuristic.
- `ProcessManager` stores tracked processes in memory by `process_id`, scoped by the complete Agent address (`project_id` plus `agent_id`) and Run.
- A tracked process never outlives the server process that owns its in-memory record. `server.main` activates the shared OS containment boundary before Runtime startup: Windows descendants inherit a kill-on-close Job Object, while POSIX Process Manager children run through `core/utils/process_guardian.py` and receive server death through one parent-liveness pipe. systemd adds a service-cgroup boundary (see `cli.md`).
- A handed-off Bash process may carry one tracked automatic completion-notification task plus a manual-acknowledgement bit. `register_completion_notification(...)` attaches the watcher task; `acknowledge_completion(...)` requires a terminal process, records manual delivery, and cancels the watcher. If the watcher already submitted its result to the shared completion coordinator, cancellation withdraws that still-pending notice.
- Runtime injects Storage's `TemporaryFileManager`. Every tracked process then leases one file under `<data_dir>/artifacts/temp/bash/` and writes combined output incrementally - normalized by independent incremental UTF-8/ANSI decoders for stdout and stderr, then flushed per visible chunk so the file is readable while the process runs. The file is the complete record and is not subject to the in-memory buffer cap. `TrackedProcess.log_file` exposes the path (`None` without a temporary-file manager or after a write error, which disables file logging for that process best-effort). The lease remains active through process exit and both stream readers, then starts Storage's 72-hour retention; ProcessManager does not own file cleanup.

New process ids use `proc_` plus 12 lowercase base32 characters; allocation checks retained processes immediately before synchronous publication (`process_manager.py`, `test_process_manager_containment.py`).

## Interfaces

- Tool name: `process`
- Registration: `register_process_tool(registry, process_manager)`
- Schema: one flat model-facing object with required `action` (`status`, `wait`, or `kill`) and optional `process_id`, `timeout`, `pattern`, `filter`, `limit`, `before` (plus unadvertised `timeout_ms`). The id is required for `wait` and `kill`; omitting it for `status` lists the Agent's processes. Input actions and `input`/`text`/`eof` fields are not accepted: background commands have no stdin. Coverage: `tests/core/tools/test_process.py`, `tests/core/tools/test_process_wait.py`.
- **Argument dialects** (`normalize_process_arguments`, the registered `argument_normalizer`): `session_id`/`sessionId`/`bash_id`/`task_id`/`id` -> `process_id`; `poll`/`log`/`list`/`check`/... -> `status`, `stop`/`terminate`/`cancel`/... -> `kill`; `status` with an id plus a positive timeout or a `pattern` (`until`, `match`, ...) -> `wait`. Placeholder values (`""`, blank, `0`) and fields another action owns (list fields with an id or on `kill`/`wait`, wait fields elsewhere) request nothing and are dropped, so they cannot fail an exact call. Input actions (`write`, `submit`, `send_keys`, ...) fail with the terminal/file/pipeline alternative. Unknown fields still fail at dispatch.
- `wait` blocks until the command exits, an output line matches `pattern` (case-insensitive regex; an invalid regex is matched as plain text with a `note`; output printed before the call counts), or `timeout` seconds pass (default 60, at most 600 with a `note` when clamped; a millisecond-looking value is converted with a `note` through the shell Tool's timeout rule). `ProcessManager.wait(...)` scans the retained buffer incrementally without consuming output and wakes on exit. An exited command returns the same data as detailed `status` and acknowledges completion after persistence. A still-running command returns `process_id`, `status`, the newest 20 lines/4,000 characters of `output`, `matched` when a line matched, and a `note` saying vBot still delivers the result on exit. At depth 0 the wait registers the Run's "Move to background" control, which ends the wait (the command keeps running); a per-call user cancel returns `cancelled_by_user` and leaves the command running.
- `status` without `process_id` lists only running processes by default (result key `processes`); `filter: finished` includes completed/failed/killed records, and `all` includes both. Lists sort newest start first with exact process id as the tie-breaker, default to 20 rows, and accept `limit` from 1 to 100. `counts` reports running/finished totals for the complete Agent address; `history_call` discovers retained finished records from the running view. `next_call` supplies complete arguments for an older page, or null at the end. Its `before` id is an exclusive boundary independent of filter/state, so new starts do not shift later pages. Missing/expired/cross-scope boundaries return `process_not_found` with restart guidance. Pages observe current state, not a frozen history snapshot. Listing never acknowledges completion. Coverage includes 130 retained records, pagination, scope isolation, and invalid arguments in `tests/core/tools/test_process.py`; Provider call shapes live in the process matrix in `scripts/provider_probe/scenario_agents.py`.
- `status` with `process_id` returns an immediate, non-blocking, non-consuming snapshot with lifecycle timestamps, `output` (the newest tail capped at 100 output lines and 8,000 characters including any truncation marker), `truncated`, and `log_file`. Earlier results named these `output_tail`/`output_truncated`; no reader depends on either name. List rows carry `command`, the Agent's command collapsed to one line of at most 60 characters (`ProcessManager.spawn(..., command=...)`, set by the shell Tool). Model-facing `log_file` values use the shared forward-slash presentation while `TrackedProcess` retains the native `Path`.
- `kill` requires `process_id` and stops that process. A failed tree kill returns retryable `process_kill_failed`, keeps the tracked process active, and preserves Windows descendant identities for another kill even if their parent has exited. Scope cleanup attempts every matching process before reporting a failure. Windows uses the existing psutil dependency to capture and verify the tree around taskkill; its fallback kills the captured processes, never just the immediate child. POSIX group-kill errors propagate instead of silently falling back to a direct-child kill. Evidence: `test_process_manager_containment.py` and `test_process.py`.
- Failure codes: `process_not_found` (missing or cross-agent id) and `invalid_arguments` (unsupported action or invalid fields). The not-found message lists up to three of the Agent's own commands (running first, with their command labels) and the full-list call, or says the Agent has none; a `term_` id points to the terminal Tool.
- The Tool description identifies background shell commands as its inspection/wait/termination scope. Truncation and retrieval guidance live in the affected result. `shape_process_output` in `core/tools/process.py` owns the shared Model-facing output policy used by Process status, Bash completion, timeout diagnostics, and the smaller handoff snapshot; it retains the newest text, upstream truncation state, and the available full-log pointer. It first shows the text as a terminal leaves it: CRLF becomes LF, and a line redrawn after bare carriage returns (progress bars) keeps only its last non-empty segment, so redraws cannot use up the line budget; the log file stays raw. Tests: `tests/core/tools/test_process.py`, `tests/core/tools/test_bash_output.py`.
- Display: the summary builder normalizes the call first, then renders `action` plus `process_id` when present, plus a `wait` pattern. A successful `status` without an id derives an exact presentation-only `results` count from `processes`; single-process status, kill, and failures publish no count.
- `ProcessManager.spawn(scope_key, agent_id, argv, *, project_id, env, cwd, execution_owner=None, command=None) -> str`
- `subprocess_creation_flags(*, new_process_group=False, breakaway=False, platform_name=os.name) -> int` is the shared child-process launch policy for core Tools: zero on non-Windows; `CREATE_NO_WINDOW` on Windows, optionally combined with `CREATE_NEW_PROCESS_GROUP`. Lifecycle/update handoff requests breakaway; the owner queries the immediate Job and adds `CREATE_BREAKAWAY_FROM_JOB` only for explicit `BREAKAWAY_OK` without `SILENT_BREAKAWAY_OK`. No Job or forbidden breakaway omits the flag; API errors propagate. vBot's Job permits explicit breakaway, allowing its updater to survive server death even inside a restrictive external ancestor. That ancestor retains its own lifetime authority.
- `activate_process_containment()` establishes the server-process boundary once; `guarded_process_launch(argv)` returns the exact ordinary argv when no POSIX boundary is active and otherwise returns the private guardian argv plus its inherited lifetime descriptor. `ProcessManager` and Terminal Backend share this seam so they cannot acquire different crash behavior.
- `ProcessManager.poll(...)` and `ProcessManager.log(...)` remain internal Bash lifecycle/output primitives and are not public Process actions (the `poll` action name is only an alias of `status`/`wait`). `poll` clears the shared `output_event`, so other waiters must not rely on that event; `ProcessManager.wait` polls the buffer every 0.1 s and wakes on `wait_task` instead.
- `ProcessManager.snapshot(process_id, agent_id, *, project_id)` provides the public non-consuming status view; `ProcessManager.kill(process_id, agent_id, *, project_id)` owns termination.
- `ProcessManager.cancel_for_user(process_id, agent_id, *, project_id) -> TrackedProcess` terminates a running process through the same kill machinery while retaining `cancelled_by_user: true` on the in-memory record; handed-off Bash completion delivery uses that fact for explicit user-abort wording. The Chat Activity surface exposes this through `chat.cancel_process` (params `agent_id` + `process_id`) with an addressed Agent and exact process id; it does not acknowledge or suppress the automatic completion notice.
- `ProcessManager.list_processes(agent_id, *, project_id) -> list[TrackedProcess]`
- `ProcessManager.add_terminal_callback(callback) -> unsubscribe` is the accessor-notification seam: exactly one plain snapshot per **backgrounded** terminal process - `process_id`, bare `agent_id`, `project_id`, raw `status`, `exit_code`, `cancelled_by_user`, ISO `started_at`/`finished_at`, output tail (capped at `PROCESS_TERMINAL_OUTPUT_CAP_CHARS`, 30k, independently of the smaller Model-facing result), `truncated`, and forward-slash `log_file`. The snapshot is pure accessor state and never reaches the Model; the server's app bridge forwards it as the `bash_process_status_changed` WebSocket event. Foreground processes never notify, the callback list must stay synchronous and fast, and a failing callback never blocks the others.
- `ProcessManager.cancel_scope_async(scope_key) -> None` kills a run scope from Run cancel callbacks without blocking the event loop on the Windows tree-kill; synchronous killing is reserved for manager shutdown (`stop`). `release_scope(scope_key)` forgets the scope's closed-admission marker; Chat calls it from a Run completion observer, which runs only after the executor, every Tool task, and all cancellation callbacks have settled.

## Constraints & Gotchas

- Access is isolated by `ToolContext.project_id` plus `ToolContext.agent_id`; missing, cross-agent, and same-id-different-Project processes use not-found semantics.
- `cancel_scope_async(run.id)` kills all active processes started by tools in that Run.
- Combined in-memory output buffers are capped. Detailed `status` returns the newest output tail without advancing Bash's internal polling cursor and points to `log_file` for the complete retained record when available. The shared Bash/Process truncation marker names that file without prescribing shell grep or assuming another Tool is available.
- Core Tool subprocesses must use `subprocess_creation_flags`: the managed command, Bash environment probe, ripgrep search, and Windows `taskkill` helpers stay windowless when vBot runs without a parent console, while managed commands retain their separate process group for tree cancellation.
- Every process launch is manager-tracked and shielded until OS creation settles; cancelling its caller kills the created process before propagating cancellation. Manager shutdown and Run-scope cancellation close admission immediately, and their async variants await pending launches. A late-created process is killed before its id returns. Execution-group cleanup remains limited to that group.
- Closed Run-scope and execution-group markers are released once no launch for them can arrive, so they do not accumulate for the server lifetime: a cancelled Run's marker stays until its completion observer runs (a launch racing the cancellation before the Run settles is still rejected); a group's marker stays for its `close_execution_group` drain and is released afterwards, because `core/agents/temporary.py` closes group resources only after every owned Run is terminal (`test_process_manager.py`, `test_chat_loop_tool_cancellation.py`, `test_temporary.py`).
- Runtime shutdown remains the primary owner and explicitly kills every tracked process tree. Job close, guardian pipe EOF, and the systemd cgroup are crash-only backstops that prevent an obsolete Runtime's children from becoming untracked; they do not create durable or reattachable handles.
- The in-memory finished-process TTL and the complete-output file retention are separate: evicting a `TrackedProcess` does not remove its 72-hour temporary log.
- Process completion observes the shell OS exit independently of pipe EOF, then drains stdout/stderr for at most one second. Descendants inheriting pipes (including Playwright CLI daemons on Windows) cannot keep Bash, timeout cleanup, or shutdown waiting forever after the shell exits. Remaining readers and their pipe transports close with a DEBUG diagnostic; already captured output and the real exit code remain. Reader failures still log as errors. Cancelling a kill waiter or completion-notification watcher cannot cancel the manager-owned finalizer (`test_bash_process_exit.py`).
- The TTL sweeper removes old terminal processes automatically; there is no public clear action. Kill admission checks the OS return code before changing lifecycle state, and async kill confirmation serializes with watcher finalization. A process that has exited while output readers are still draining keeps its natural result (`test_kill_during_reader_drain_preserves_real_exit`).
- A terminal detailed `status` and a successful `kill` register their manual completion acknowledgement through `ToolContext.after_result_persisted`; merely returning from the handler is not delivery. This persistence boundary preserves automatic completion if Chat fails before the manual Tool Result reaches Session history, while cancelling a pending coalesced notice when persistence succeeds.
- Bash/Process owns unattended commands, output, handoff, and termination. Interactive operation belongs to the separate `terminal` Tool (`tools/terminal.md`). Files and pipelines within a Bash command remain supported; closing Bash stdin does not close input channels a command creates for its own children.
- Each pipe has independent incremental UTF-8 and bounded ANSI parser state (`core/tools/_process_output.py`). Incomplete characters/control sequences remain pending across reads and polls; stdout cannot complete stderr bytes or vice versa. A character that cannot continue the current escape/CSI (e.g. a line break after `ESC [`) ends it and is kept as output; control strings (OSC/DCS/APC/PM/SOS) end at CR/LF, a new ESC, or after 4096 characters, and CSI/escape parameters after 64, so unterminated junk cannot swallow later output (`test__process_output.py`). The combined buffer, foreground output, chunks, and full log all store the same normalized UTF-8. Buffer offsets and caps count normalized bytes; truncation preserves character boundaries. Literal terminal controls are not exposed through Process output. Coverage: `test_process_manager_spooling.py`.
