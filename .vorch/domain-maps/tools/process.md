# Process Tool

Lets an Agent inspect and control only its own background processes created by the `bash` Tool.

## Terms

### Tracked Process
**Definition:** One OS subprocess spawned through `ProcessManager` (always by the `bash` Tool today), identified by an opaque `process_id` and tracked in memory until exit plus a TTL sweep. The Agent addresses it in Tool results and `process` actions exclusively as `process_id`.
**Not:** A Chat Session or its id - those are separate namespaces even though both are opaque strings. Also not an arbitrary operating-system process: the Tool cannot discover or control anything `ProcessManager` did not spawn.

Shared OS launch flags, server-lifetime containment, and verified process-tree termination live in `core/utils/processes.py`; Bash/Process, Terminal, local Speech, and server startup use that owner. `ProcessManager` owns only tracked background command lifecycle and output.

`ProcessManager` launches through `core.utils.processes.create_subprocess_exec`, never `asyncio.create_subprocess_exec` directly. On the Windows Proactor loop, the stdlib runs `CreateProcess` on the Event Loop thread, which stalled the live server for 1-4 s under antivirus or disk load; the shared helper creates the OS process on the bounded `process-launch` worker pool and then attaches the stdlib transport and stream protocol on the loop. A launch cancelled after creation kills the created process. Other platforms delegate to asyncio unchanged (`tests/core/utils/test_processes_launch.py`).

## Data Model

- `process_id` values are distinct from Chat Session ids and identify only commands that `bash` started through `ProcessManager`. Every tracked process starts with stdin connected to `DEVNULL`; EOF is immediate and no later input can be sent. `TrackedProcess` has no input state or idle-input heuristic.
- `ProcessManager` stores tracked processes in memory by `process_id`, scoped by the complete Agent address (`project_id` plus `agent_id`) and Run.
- A tracked process never outlives the server process that owns its in-memory record. `server.main` activates the shared OS containment boundary before Runtime startup: Windows descendants inherit a kill-on-close Job Object, while POSIX Process Manager children run through `core/utils/process_guardian.py` and receive server death through one parent-liveness pipe. The guardian reports a child killed by signal N as exit code 128+N, as a shell does. systemd adds a service-cgroup boundary (see `cli.md`).
- A handed-off Bash process may carry one tracked automatic completion-notification task plus a manual-acknowledgement bit. `register_completion_notification(...)` attaches the watcher task; `acknowledge_completion(...)` requires a terminal process, records manual delivery, and cancels the watcher. If the watcher already submitted its result to the shared completion coordinator, cancellation withdraws that still-pending notice.
- Runtime injects Storage's `TemporaryFileManager`. Every tracked process then leases one file under `<data_dir>/artifacts/temp/bash/` and writes combined output incrementally - normalized by independent incremental UTF-8/ANSI decoders for stdout and stderr, then flushed per visible chunk so the file is readable while the process runs. Internal `_process_spool.py` owns ordered file I/O on the bounded `process-output` worker pool, including open/close and lease completion. Each pipe reader awaits its captured chunk, bounding pending spool output to one chunk per pipe and applying pipe backpressure; the in-memory snapshot lock stays free during disk I/O. The file is the complete record and is not subject to the in-memory buffer cap. `TrackedProcess.log_file` exposes the path (`None` without a temporary-file manager or after an I/O error, which disables file logging for that process best-effort). The lease remains active through process exit, both stream readers and settled file writes, then starts Storage's 72-hour retention; ProcessManager does not own file cleanup.

New process ids use `proc_` plus 12 lowercase base32 characters; allocation checks retained processes and reserves ids across asynchronous log opening until synchronous publication (`process_manager.py`, `test_process_manager.py`, `test_process_manager_spooling_async.py`).

## Interfaces

- Tool name: `process`
- Registration: `register_process_tool(registry, process_manager)`
- Schema: one flat model-facing object with required `action` (`status`, `wait`, or `kill`) and optional `process_id`, `timeout`, `pattern`, `filter`, `limit`, `before` (plus unadvertised `timeout_ms`). The id is required for `wait` and `kill`; omitting it for `status` lists the Agent's processes. Input actions and `input`/`text`/`eof` fields are not accepted: background commands have no stdin. Coverage: `tests/core/tools/test_process.py`.
- **Argument dialects** (`normalize_process_arguments`, the registered `argument_normalizer`): `session_id`/`sessionId`/`bash_id`/`task_id`/`id` -> `process_id`; `poll`/`log`/`list`/`check`/... -> `status`, `stop`/`terminate`/`cancel`/... -> `kill`; `status` with an id plus a positive timeout or a `pattern` (`until`, `match`, ...) -> `wait`. Placeholder values (`""`, blank, `0`) and fields another action owns (list fields with an id or on `kill`/`wait`, wait fields elsewhere) request nothing and are dropped, so they cannot fail an exact call. Input actions (`write`, `submit`, `send_keys`, ...) fail with the terminal/file/pipeline alternative. Unknown fields still fail at dispatch.
- `wait` blocks until the command exits, an output line matches `pattern` (case-insensitive regex; an invalid regex is matched as plain text with a `note`; output printed before the call counts), or `timeout` seconds pass (default 60, at most 600 with a `note` when clamped; a millisecond-looking value is converted with a `note` through the shell Tool's timeout rule). `ProcessManager.wait(...)` scans the retained buffer incrementally without consuming output and wakes on exit. An exited command returns the same data as detailed `status` and acknowledges completion after persistence. A still-running command returns `process_id`, `status`, the newest 20 lines/4,000 characters of `output`, `matched` when a line matched, and a `note`: after a match, that vBot still delivers the result on exit; after a timeout without `pattern`, that the result arrives as a new message and dependent work ends the turn (never "wait again", which only spends round trips); after a timeout with `pattern`, only that no line matched, since a server's result never arrives while it serves. The clamp note states only the 600-second limit. Role: `wait` serves what automatic delivery cannot - a line from a command that runs until stopped, such as a server's ready line; the shell handoff note names it only for an immediate `background` start (`bash.md`). At depth 0 the wait registers the Run's "Move to background" control, which ends the wait (the command keeps running); a per-call user cancel returns `cancelled_by_user` and leaves the command running.
- `status` without `process_id` lists only running processes by default (result key `processes`); `filter: finished` includes completed/failed/killed records, and `all` includes both. Lists sort newest start first with exact process id as the tie-breaker, default to 20 rows, and accept `limit` from 1 to 100. `counts` reports running/finished totals for the complete Agent address; `history_call` discovers retained finished records from the running view. `next_call` supplies complete arguments for an older page, or null at the end. Its `before` id is an exclusive boundary independent of filter/state, so new starts do not shift later pages. Missing/expired/cross-scope boundaries return `process_not_found` with restart guidance. Pages observe current state, not a frozen history snapshot. Listing never acknowledges completion. Coverage includes 130 retained records, pagination, scope isolation, and invalid arguments in `tests/core/tools/test_process.py`; Provider call shapes live in the process matrix in `scripts/provider_probe/scenario_agents.py`.
- `status` with `process_id` returns an immediate, non-blocking, non-consuming snapshot with lifecycle timestamps, `output` (the newest tail capped at 100 output lines and 8,000 characters including any truncation marker), `truncated: true` only when output was cut (`shape_process_output` omits a false flag for Bash and Process alike), and `log_file`. Earlier results named these `output_tail`/`output_truncated`; no reader depends on either name. List rows carry `command`, the Agent's command collapsed to one line of at most 60 characters (`ProcessManager.spawn(..., command=...)`, set by the shell Tool). `TrackedProcess.cwd` keeps the spawn directory, which Bash's failure hints check. Model-facing `log_file` values use the shared forward-slash presentation while `TrackedProcess` retains the native `Path`.
- `kill` requires `process_id` and stops that process. A failed tree kill returns retryable `process_kill_failed`, keeps the tracked process active, and preserves Windows descendant identities for another kill even if their parent has exited. Scope cleanup attempts every matching process before reporting a failure. Windows uses the existing psutil dependency to capture and verify the tree around taskkill; its fallback kills the captured processes, never just the immediate child. A taskkill failure (exit code and first stderr line, timeout, or launch error) is DEBUG detail when the fallback ends the tree; only survivors log a WARNING with their count and that cause. POSIX group-kill errors propagate instead of silently falling back to a direct-child kill. Evidence: `test_process_manager.py`, `test_process_manager_containment.py`, and `test_process.py`.
- Failure codes: `process_not_found` (missing or cross-agent id) and `invalid_arguments` (unsupported action or invalid fields, raised as `ToolContractError`; any other exception is `tool_execution_error`, see `../tools.md` -> Failure codes follow the phase). The not-found message lists up to three of the Agent's own commands (running first, with their command labels) and the full-list call, or says the Agent has none; a `term_` id points to the terminal Tool.
- The Tool description identifies background shell commands as its inspection/termination scope and waiting for an expected line as its wait use. Truncation and retrieval guidance live in the affected result. `shape_process_output` in `core/tools/process.py` owns the shared Model-facing output policy used by Process status, Bash completion, timeout diagnostics, and the smaller handoff snapshot; it retains the newest text, upstream truncation state, and the available full-log pointer. It first shows the text as a terminal leaves it: CRLF becomes LF, and a line redrawn after bare carriage returns (progress bars) keeps only its last non-empty segment, so redraws cannot use up the line budget; the log file stays raw. Tests: `tests/core/tools/test_process.py`, `tests/core/tools/test_bash_lifecycle.py`, `tests/core/tools/test_bash_background.py`.
- Display: the parts builder normalizes the call first and returns `action`, `process_id` when present, and a `wait` pattern; ToolDisplay shows only the first two parts, so the activity row and summary show `action` plus `process_id` and never the pattern. A successful `status` without an id derives an exact presentation-only `results` count from `processes`; single-process status, kill, and failures publish no count. Detail blocks (`_process_detail_blocks`, `tools.md` -> Display metadata): a list shows a `results` block (each command's label, or its id when it has none, as title; `running`, `stopped` or `exited with code N` as meta; its start time), or an info notice naming the empty filter, plus `More commands follow on the next page.` when `next_call` is set; single-process `status` and `wait` show `data.output` by reference, the `matched` line as an info notice subject, and `The command is still running.`, `The command was stopped.` or a warning for a non-zero exit code; `kill` shows that the command was stopped (or had already ended). Ids, paging calls, log paths and notes stay in the raw result. Coverage: `test_process.py` list, line-match wait and kill tests.
- `ProcessManager.spawn(scope_key, agent_id, argv, *, project_id, env, cwd, execution_owner=None, command=None) -> str`
- `subprocess_creation_flags(*, new_process_group=False, breakaway=False, platform_name=os.name) -> int` is the shared child-process launch policy for core Tools: zero on non-Windows; `CREATE_NO_WINDOW` on Windows, optionally combined with `CREATE_NEW_PROCESS_GROUP`. Lifecycle/update handoff requests breakaway; the owner queries the immediate Job and adds `CREATE_BREAKAWAY_FROM_JOB` only for explicit `BREAKAWAY_OK` without `SILENT_BREAKAWAY_OK`. No Job or forbidden breakaway omits the flag; API errors propagate. vBot's Job permits explicit breakaway, allowing its updater to survive server death even inside a restrictive external ancestor. That ancestor retains its own lifetime authority.
- `activate_process_containment()` establishes the server-process boundary once; `guarded_process_launch(argv, *, env, controlling_terminal=False)` returns the exact ordinary argv when no POSIX boundary is active and no controlling terminal is requested; otherwise it returns the private guardian argv, plus its inherited lifetime descriptor while the boundary is active. `env` is the environment the caller starts the launch with. `controlling_terminal` (Terminal Backend only) requires the caller to start the launch as a session leader with the PTY slave as stdin (`tools/terminal.md`). `ProcessManager` and Terminal Backend share this seam so they cannot acquire different crash behavior. Windows launches never use the guardian.
- **Guardian isolation:** the guardian starts in the child's working directory and environment, so it runs by absolute file path as `sys.executable -I -S -B -X utf8 <core/utils/process_guardian.py>`: neither the working directory, `PYTHONPATH`/`PYTHONHOME`/other `PYTHON*` variables nor site-packages can replace a module it imports, and it writes no bytecode into an installed version. Run as `-m core.utils.process_guardian` before, it failed with `No module named 'core.utils'` in a project with its own `core` package, and the command never ran. It therefore imports only the standard library; a vBot import would fail there. The child still receives the caller's working directory and exactly `env`, `PYTHON*` variables included: Python's startup sets `LC_CTYPE` (PEP 538 locale coercion) when the environment names no UTF-8 locale, which isolated mode cannot turn off (it ignores `PYTHONCOERCECLOCALE`), so the launch passes the requested value (`--lc-ctype=<value>`, omitted when unset) and the guardian restores it, or its absence, before it starts the child. Coverage: `test_guarded_posix_launch_wraps_exact_argv_and_lifetime_descriptor` and `test_guardian_is_isolated_from_the_command_it_runs` in `test_process_manager_containment.py`, the exec path in `test_terminal_backend.py`.
- `ProcessManager.poll(...)` and `ProcessManager.log(...)` remain internal Bash lifecycle/output primitives and are not public Process actions (the `poll` action name is only an alias of `status`/`wait`). `poll` returns the status and the stream-tagged output chunks since its previous call, which the foreground shell phase streams to the UI; it never waits. `ProcessManager.wait` polls the buffer every 0.1 s and wakes on `wait_task`.
- `ProcessManager.snapshot(process_id, agent_id, *, project_id)` provides the public non-consuming status view; `ProcessManager.kill(process_id, agent_id, *, project_id)` owns termination.
- `ProcessManager.cancel_for_user(process_id, agent_id, *, project_id) -> TrackedProcess` terminates a running process through the same kill machinery while retaining `cancelled_by_user: true` on the in-memory record; handed-off Bash completion delivery uses that fact for explicit user-abort wording. The Chat Activity surface exposes this through `chat.cancel_process` (params `agent_id` + `process_id`) with an addressed Agent and exact process id; it does not acknowledge or suppress the automatic completion notice.
- `ProcessManager.list_processes(agent_id, *, project_id) -> list[TrackedProcess]`
- `ProcessManager.add_terminal_callback(callback) -> unsubscribe` is the accessor-notification seam: exactly one plain snapshot per **backgrounded** terminal process - `process_id`, bare `agent_id`, `project_id`, raw `status`, `exit_code`, `cancelled_by_user`, ISO `started_at`/`finished_at`, output tail (capped at `PROCESS_TERMINAL_OUTPUT_CAP_CHARS`, 30k, independently of the smaller Model-facing result), `truncated`, and forward-slash `log_file`. The snapshot is pure accessor state and never reaches the Model; the server's app bridge forwards it as the `bash_process_status_changed` WebSocket event. Foreground processes never notify, the callback list must stay synchronous and fast, and a failing callback never blocks the others.
- `ProcessManager.cancel_scope_async(scope_key) -> None` kills a run scope from Run cancel callbacks without blocking the event loop on the Windows tree-kill; synchronous killing is reserved for manager shutdown (`stop`). `release_scope(scope_key)` forgets the scope's closed-admission marker; Chat calls it from a Run completion observer, which runs only after the executor, every Tool task, and all cancellation callbacks have settled.

## Constraints & Gotchas

- Access is isolated by `ToolContext.project_id` plus `ToolContext.agent_id`; missing, cross-agent, and same-id-different-Project processes use not-found semantics.
- `cancel_scope_async(run.id)` kills all active processes started by tools in that Run.
- Combined in-memory output buffers are capped. Detailed `status` returns the newest output tail without advancing Bash's internal polling cursor and points to `log_file` for the complete retained record when available. The shared Bash/Process truncation marker names that file without prescribing shell grep or assuming another Tool is available.
- Core Tool subprocesses must use `subprocess_creation_flags`: the managed command, Bash environment probe, ripgrep search, and Windows `taskkill` helpers stay windowless when vBot runs without a parent console, while managed commands retain their separate process group for tree cancellation.
- Every process launch is manager-tracked and shielded until OS creation settles; cancelling its caller kills the created process before propagating cancellation. Manager shutdown and Run-scope cancellation close admission immediately, and their async variants await pending launches. A late-created process is killed before its id returns. Execution-group cleanup remains limited to that group.
- Closed Run-scope and execution-group markers are released once no launch for them can arrive, so they do not accumulate for the server lifetime: a cancelled Run's marker stays until its completion observer runs (a launch racing the cancellation before the Run settles is still rejected); a group's marker stays for its `close_execution_group` drain and is released afterwards, because `core/agents/temporary.py` closes group resources only after every owned Run is terminal (`test_process_manager.py`, `test_chat_loop_tools.py`, `test_temporary.py`).
- Runtime shutdown remains the primary owner and explicitly kills every tracked process tree. Job close, guardian pipe EOF, and the systemd cgroup are crash-only backstops that prevent an obsolete Runtime's children from becoming untracked; they do not create durable or reattachable handles.
- The in-memory finished-process TTL and the complete-output file retention are separate: evicting a `TrackedProcess` does not remove its 72-hour temporary log.
- A finished `TrackedProcess` keeps only what later reads need: status, exit code, timestamps, the capped output buffer and `log_file`. Once the process is final (completed, failed or killed, including a kill retried after a failed tree kill), the manager closes the exited asyncio transport and drops `proc`, the reader tasks, the per-pipe decoders and the tree-kill targets, so finished processes waiting for the 30-minute TTL sweep hold no asyncio process graph. `wait_task` stays as the settled completion signal. A process whose tree kill failed keeps them for the retry. Output chunks exist only for `poll`, which clears them once returned, so unpolled output survives the exit and is returned exactly once (`test_stdin_is_closed_at_start_and_execution_resources_are_released_at_exit`).
- Process completion observes the shell OS exit independently of pipe EOF and cuts off still-open pipes after one second. Descendants inheriting pipes (including Playwright CLI daemons on Windows) cannot keep Bash, timeout cleanup, or shutdown waiting forever after the shell exits. Paused transports resume before close so Windows delivers its pending bytes before EOF; readers then drain their finite buffered bytes and captured spool writes before completion and lease release. Disk I/O can extend this final drain without blocking the Event Loop. Pipe cutoff logs a DEBUG diagnostic; captured output and the real exit code remain. Reader failures still log as errors. Cancelling a reader settles its captured write and incremental decoder; cancelling a kill waiter or completion-notification watcher cannot cancel the manager-owned finalizer (`test_bash_lifecycle.py`, `test_process_manager_spooling_async.py`).
- The TTL sweeper removes old terminal processes automatically; there is no public clear action. Kill admission checks the OS return code before changing lifecycle state, and async kill confirmation serializes with watcher finalization. A process that has exited while output readers are still draining keeps its natural result (`test_kill_during_reader_drain_preserves_real_exit`).
- A terminal detailed `status` and a successful `kill` register their manual completion acknowledgement through `ToolContext.after_result_persisted`; merely returning from the handler is not delivery. This persistence boundary preserves automatic completion if Chat fails before the manual Tool Result reaches Session history, while cancelling a pending coalesced notice when persistence succeeds.
- Bash/Process owns unattended commands, output, handoff, and termination. Interactive operation belongs to the separate `terminal` Tool (`tools/terminal.md`). Files and pipelines within a Bash command remain supported; closing Bash stdin does not close input channels a command creates for its own children.
- Each pipe has independent incremental UTF-8 and bounded ANSI parser state (`core/tools/_process_output.py`). Incomplete characters/control sequences remain pending across reads and polls; stdout cannot complete stderr bytes or vice versa. A character that cannot continue the current escape/CSI (e.g. a line break after `ESC [`) ends it and is kept as output; control strings (OSC/DCS/APC/PM/SOS) end at CR/LF, a new ESC, or after 4096 characters, and CSI/escape parameters after 64, so unterminated junk cannot swallow later output (`test__process_output.py`). An ESC directly followed by a lowercase letter, `` ` ``, `{|}~`, a control character or non-ASCII text starts no terminal control in practice and is shown as the text `\x1b` instead of being dropped with the next character: PowerShell writes ESC for a backtick-e inside double quotes (a Markdown span `` `expected` `` becomes ESC + `xpected`), and the stripped pair used to hide that corruption (Swarm evidence 2026-09). The combined buffer, foreground output, chunks, and full log all store the same normalized UTF-8. Buffer offsets and caps count normalized bytes; truncation preserves character boundaries. Literal terminal controls are not exposed through Process output. Coverage: `test_process_manager_output.py`.

## Agent-facing text

| Text | Reason |
|---|---|
| ``Check on or stop a `powershell` command that runs in the background, or wait until it prints an expected line.`` | Limits the scope to commands the shell Tool started, not arbitrary OS processes (F1). Names waiting for an expected line as the job only `wait` does: a server never exits, so its automatic result never arrives. Before `wait` existed, Agents bridged this with about 100 `Start-Sleep` calls in Runs with a running background command, many followed by an HTTP readiness probe (Sessions, 2026-09-10 to 09-25). |
| `action`: `status: one command's state and recent output, or a list without process_id.` | One clause per action; the target field, not an action, selects list or single command. |
| `action`: `wait: block until the command prints a line matching pattern or exits.` | Both end conditions, the line match first: after the handoff note advertised waiting until exit, Agents blocked on self-terminating builds whose result arrives on its own (56 of 56 waits, Sessions 2026-09-26). The timeout is stated on `timeout`. |
| `action`: `kill: stop the command.` | One clause per action. |
| `process_id`: ``Id from the `powershell` result. Required for wait and kill; omit for status to list your commands, newest first.`` | Identifiers come from results; the omit rule selects the list (F2). |
| `timeout`: `wait: seconds to wait. Omit for 60; at most 600.` | Unit and cap; JavaScript habits send milliseconds, which are converted with a `note` (F3). |
| `pattern`: `wait: return as soon as an output line matches this regular expression (case-insensitive), such as a server's ready line; earlier output counts.` | Pins flavor and case, names the intended use, and prevents waiting for a line printed before the call (F3). |
| `pattern`: `Omit to wait until the command exits.` | Omit rule: Agents invented end markers such as `error\|Finished` that matched progress lines, so 24 of 56 waits returned while the command still ran (F2, F6; Sessions 2026-09-26). |
| `filter`: `List for status without process_id. Omit for running commands; finished includes completed, failed, and killed ones.` | Omit rule, and defines `finished` (F2). |
| `limit`: `Maximum commands per list page. Omit for 20.` | Omit rule with the value (F2). |
| `before`: `List page boundary; use the returned next_call to continue.` | The Agent copies the boundary from a result instead of constructing one (F2). |
