# Tool Display and Media

What a Tool records for the user's view of a call (`ToolDisplay`, `core/tools/_tool_display.py`): display facts, media, detail blocks and file diffs, plus the rich-media artifact and the in-memory media handover to Chat. The root rule (presentation-only, never in Provider definitions or result envelopes) lives in `tools.md` -> Contracts -> Display metadata.

## Display metadata

`ToolDisplay` is presentation-only per-invocation data: typed facts (counts, line ranges, +/- changes) recorded via `ToolContext.add_display_count()`/`add_display_line_changes()` plus the images, videos and audio the user sees in the call's details - files it read, looked at or produced, and with `source=True` files it started from such as a generation's reference images - recorded via `ToolContext.add_display_media(path, media_type, filename=None, source=False)` (`media_type` a media type or only its kind `image`/`video`/`audio`, other kinds ignored; `filename` for a file whose path does not name it, such as a download; persisted as internal `media_files` of absolute `path`, `kind`, `filename` and optional `role: source`, projected by the server into signed `media` URLs; every Tool uses this one path, so the WebUI shows all Tool media alike).

A display declaring `details=True` or a `detail_builder` gets ordered user-facing detail blocks (payload `details`, present even when empty) that the WebUI shows in place of the raw arguments and result - first the blocks the builder derives from the call's arguments and result (`display_notice()`, `display_text()`, `display_results()`; the builder runs again for every projection, so it sees the final result), then those the handler recorded, in recording order:

- a `text` block (`label` `command`/`content`/`input`/`output`/`page`/`query`/`response`/`results`/`screen`/`scrollback`/`task`, either its own `text` of at most 16384 characters or a `source` naming `from` `arguments`/`result` and a key `path` to a string there, so a large value such as command output is not copied into the display; recorded via `ToolContext.add_display_text()`);
- a `results` block (`items` of what the call found, each with a `title` and optional `url` (absolute http(s), at most 2048 characters, otherwise dropped), `meta`, ISO `time` and `text` cut at 600 characters; at most 20 items, untitled ones dropped; recorded via `ToolContext.add_display_results()`);
- a `memory_changes` block (`scope` `agent`/`user`, non-empty `changes` of `op` `added`/`removed` with `text` or `replaced` with `previous` and `text`, optional positive `revision` of the Memory history) recorded via `ToolContext.add_display_memory_changes()`;
- a `notice` block (`level` `info`/`warning`/`error`, `text`, optional `subject`) recorded via `ToolContext.add_display_notice()` - a failed call without a recorded error notice, such as one rejected before its handler, gets one from its result's error message;
- one `file_changes` block at the place of the first changed file, whose `files` are diffs recorded via `ToolContext.add_display_file_change()` (`core/tools/_display_diff.py`, over the minimal line diff `core/tools/_line_diff.py` that Run change statistics share, so both count alike; per file `path`, `change` (`created`/`updated`/`replaced`/`deleted`/`moved`), optional `destination`, `added`/`removed` over every changed line, `hunks` of `old_start`/`new_start` and `+`/`-`/space-prefixed `lines` with 3 context lines, `omitted_lines` beyond one 2000-line budget shared by the call, `binary` for non-text files).

These parts are assembled into a versioned payload that never enters provider definitions or result envelopes. A primary part may carry `detail` (with `detail_kind`), the complete value a shorter part stands for (the command behind a Bash description), which the WebUI shows and copies in the part's value card. A call that used Agent Secrets carries `secrets_used` (`NAME.field (sink)` per use, recorded via `ToolContext.record_secret_uses()`, never a value), and Chat masks known Secret values in the whole payload (`secrets/agent-secrets.md` -> Masking). Every built-in registers an explicit display (an intentional no-summary row included); new growth belongs in the Tool-owned profile, not per-name branches in Svelte.

## Rich media

`read_media_artifact(...)` builds the one cross-Tool artifact `{kind: "read_media", attachment_id, filename, media_type}` used by `web_fetch` and other stored remote media; Chat resolves it as request-only content on the correlated Result in every request until Compaction. Tools that load pixels in memory (`read`, computer use) instead hand them over via `ToolContext.result_media`, delivered with successful and failed Results alike, never through the persisted envelope or public events; Chat stores them as Attachments referenced by the Tool message's internal `tool_media` (`chat/request-building.md`).
