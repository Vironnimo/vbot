# Bash Tool

Runs host shell commands and streams foreground stdout/stderr into the Run timeline.

`bash.py` owns execution and cancellation coordination. Internal `_bash_environment.py` owns the cached host environment and login probe; `_powershell.py` owns the Windows command wrapping (setup, parsing the command after it, the `head`/`tail`/`wc` fallbacks, and the exit-status statement); `_shell_arguments.py` owns other harnesses' argument shapes, the `env` object, timeout units, and the display parts; `_bash_results.py` owns completion/handoff result shaping and durable background-status projection.

Windows PATH refresh expands registry values marked `REG_EXPAND_SZ` before combining machine/user paths; literal registry strings remain unchanged (`test_bash_environment.py`).

## Interfaces

- Tool name: `bash` (registry name). The Model sees `powershell` on Windows and `bash` elsewhere (`SHELL_MODEL_NAME`; contract: `tools.md` -> Model Tool names). Model-facing texts that mention the Tool - Process and Project guidance, the Env-grant block `## Shell Environment Access`, Skill env guidance, the missing-`pwsh` spawn error - use that name or say "shell". The `### Bash process` completion heading stays, because `background_bash_statuses` parses it.
- Registration: `register_bash_tool(registry, process_manager, trigger_service=None)`
- Schema: one open flat object requiring `command`, with optional `mode: "foreground" | "background"`, `description`, `workdir`, `timeout`, and `env_keys`. Omitted `mode` defaults to `foreground` in the handler. `description` is a short command-purpose title with no model-facing length constraint and no effect on execution. `env_keys` is an ordered unique array of shell-portable credential names, never values. The handler authorizes every requested name against the union of permanent `tools.bash.allowed_env` Agent settings and Env requirements from currently active Skills, resolves allowed values through Runtime credential precedence, and overlays them only into the spawned process environment. An ungranted name that the command environment already has (such as `PATH`) runs with a `note` saying the inherited value applies; any other ungranted name fails before spawn with the granted names listed. Unknown arguments fail at dispatch. The model-facing schema emits neither `oneOf` nor `additionalProperties`.
- **Argument dialects** (`_shell_arguments.py:normalize_shell_arguments`, the registered `argument_normalizer`): calls routed here from other harnesses' Tool names (`tools.md` -> Model Tool names) keep their argument shapes, so the normalizer maps every shape whose intent is exact and fails before spawn otherwise. Mapped: `cmd`/`script`/`argv`/`shell_command` -> `command`; argv arrays -> one host command line (a host-shell wrapper such as Codex `bash -lc <script>` or `pwsh -Command <script>` yields its script; otherwise PowerShell quoting on Windows, `shlex.join` elsewhere); a `commands` list -> newline-joined; `cwd`/`dir`/`directory`/`working_directory` -> `workdir`; `timeout_ms` (unadvertised) -> seconds; `background`/`run_in_background`/`is_background` and mode spellings (`auto` -> foreground, `bg` -> background); a zero `yieldMs`/`background_after_seconds` -> background (non-zero is dropped); `explanation`/`justification`/`title`/`label`/`summary` -> `description`; OpenAI `local_shell` `{action: {...}}` unwrapped; `env_keys: []` dropped. Output-only or always-satisfied fields (`login`, `max_output_tokens`, ...) are dropped. Requests for a different effect fail with the next call named: `pty: true` (points to the terminal Tool), elevation, user approval, another `user`, a background flag that contradicts `mode`, disagreeing duplicates. Coverage: `tests/core/tools/test_bash_arguments.py`.
- **`env` object** (unadvertised): plain variables are set only in the spawned process, after the inherited environment and before credentials and `VBOT_*` variables. vBot never passes a credential value written in the call: a literal value for a granted name, or for a credential-looking name (`KEY`, `TOKEN`, `SECRET`, `PASSWORD`, ... segments), fails without echoing the value; a granted name set to `""` or a self-reference (`$NAME`, `$env:NAME`, `%NAME%`) becomes an `env_keys` request; `VBOT_*` names are refused.
- Provider projection: top-level Runs receive the optional `mode` enum (`foreground`, `background`). At `nesting_depth >= 1`, Chat uses the Sub-Agent description and omits `mode` entirely: the Agent has no execution choice. The handler independently rejects background requests at depth. At every depth the projection (`project_bash_tool_definitions`, fed the Tools offered in that request) rewrites the dedicated-Tools sentence to name only the offered ones among `read`, `search_files`, `apply_patch` ("For reading, searching and editing files use ...") and `web_fetch` ("for web pages use web_fetch"), dropping it when none is offered. Provider projection leaves canonical registry metadata untouched.
- `foreground` is the default and returns a short command's completed output inline. At depth 0 it hands a still-running command to vBot after `FOREGROUND_HANDOFF_SECONDS` (90 seconds); `background` hands off immediately. At depth >= 1 foreground waits until exit, timeout, or cancellation without any handoff deadline. Accessor-requested handoff remains available only at depth 0.
- `timeout` is a total runtime limit including time in background: omission applies `DEFAULT_TIMEOUT_SECONDS` (180 seconds) in foreground mode at every depth, while background mode runs without a Tool deadline unless an explicit positive value sets one; `0` disables the Tool deadline in both modes. `timeout_ms` is converted; a `timeout` of at least 10,000 that is a whole multiple of 1,000 is read as milliseconds with a `note`, and `timeout` plus a disagreeing `timeout_ms` fails. Output and handoff never reset it. No output-inactivity kill heuristic is applied because valid work may be silent or redirect output to files.
- Descriptions teach unattended commands, captured output, the input boundary, host-shell syntax, and keeping commands under vBot ownership (no manual detach or daemonize). Both depth variants carry one sentence pointing file reading, searching, and editing to `read`, `search_files`, and `apply_patch`; the registered description names that usual set, and the Provider projection narrows or extends it to the offered Tools. Shell commands that read files or fetch URLs stay valid; the sentence is guidance, not a refusal. Mode selection and automatic result delivery belong in the top-level mode parameter; next-step guidance belongs in the handoff result. Sub-Agent descriptions state that background execution is unavailable.
- Foreground success returns `{ status, exit_code, output }` plus `truncated: true` and `log_file` when truncated (a complete output carries no `truncated` field; every result showed `truncated: false`, 907 times in one Swarm run, 2026-09), where `output` is the combined stdout/stderr process log. Every vBot-authored `log_file` value and complete-log pointer uses the shared forward-slash Model presentation; subprocess output itself is untouched. The final tool result does not include separate `stdout` or `stderr` fields; live stdout/stderr remain SSE-only Run events.
- **Output-pattern failure hints:** a non-zero `exit_code` result additionally carries a `hint` field when a well-known failure shape was recognized - at most one, first match wins, scanned only over the first 4,000 characters of output (`core/tools/bash_hints.py`). Patterns cover POSIX and PowerShell command-not-found (with dedicated bare-`python`/`pip` variants; on PowerShell, English and German messages, with the PowerShell equivalent for bash commands such as `grep`, `sed`, `which`, `export`, `VAR=value cmd`, and bash `if`), bash flags on PowerShell aliases (`ls -la`), `Select-String -Recurse`, PowerShell parser errors from heredocs or `\"` escapes, quote escapes PowerShell passes on unchanged (on Windows only, recognized by the called program's `SyntaxError`: `\"` in a quoted argument or a `@"..."@` here-string, `''` before a word in a `@'...'@` here-string; evidence: 9 such failures without a hint in one Swarm, Sessions 2026-09), `/dev/null`, Python module-not-found, git merge conflicts, "already exists", port-in-use, permission denied, API rate limits, and gh unknown JSON fields; exit codes 126/137/124 have fixed hints. Hints state the next action in one or two sentences and never annotate success. The module-not-found hint reads the process's recorded working directory (`TrackedProcess.cwd`): a dotted name means the parent package imported but lacks that submodule; a top-level name that exists in the working directory means it is off the import path, and when the command ran a script in a subdirectory by path (the first one a traceback names) the hint gives its `python -m` form; otherwise the interpreter has no such package. Session evidence (2026-09): every earlier "wrong interpreter/venv" hint in a Swarm run was false - scripts run by path and missing submodules. The automatic background completion note carries the same hint as a `Hint:` line after the output.
- **PowerShell errors followed by exit 0:** the ordinary command epilogue checks for new PowerShell ErrorRecords, independently of the exit code. It appends a factual note to captured stderr plus the newest counted error (whitespace collapsed, capped at 500 characters), stating that errors may have been handled and asking the Agent to inspect output and verify changed files. It preserves `exit_code` and the Tool envelope; no output-text pattern decides whether this note appears. The baseline uses ErrorRecord identity, so profile errors are excluded and a full error ring still detects a new record. An error the command's own text silenced does not count: the record's position names a command in the parsed command that passes `-ErrorAction SilentlyContinue`/`Ignore` (also `-ea 0`), or that command or an enclosing one redirects the error stream (`2>$null`, `2>&1`, `*>...`), or `$ErrorActionPreference` is SilentlyContinue at the end. In one Swarm Run, 33 of 49 notes named such a silenced error the Agent never saw, all from `-ErrorAction SilentlyContinue` cleanup of absent files (Sessions, 2026-09). Records whose position names no such command, such as a caught `throw` or `Write-Error`, still count. Printed test/error text, native stderr and warnings alone do not trigger it. Explicit `exit`, a top-level `return`, or commands that clear `$Error` can bypass the note; its absence never proves that every statement succeeded. The same captured output reaches foreground results, Process inspection and automatic background completion. Coverage: `test_bash_powershell.py`.
- **Model-facing final-output cap:** completed `output` keeps at most the newest 100 output lines within 8,000 characters, including the truncation marker. `core/tools/process.py:shape_process_output` owns this shared Bash/Process policy; Tool descriptions leave truncation and retrieval guidance to the affected result. `truncated: true` covers both cut causes (model cap here, process buffer cap upstream); either way the *beginning* is what's missing, and a leading marker line says so and names the complete per-process log file under `<data_dir>/artifacts/temp/bash/` (see `process.md`) so the Agent can inspect it with an available file Tool. If temporary-file allocation failed, the marker carries no path.
- Handed-off results return `{ status: "running", delivery: "automatic", process_id, handoff_note, ... }` plus a combined `output` snapshot captured before handoff: at most the newest 20 output lines and 4,000 characters including any truncation marker, and always include `log_file` when temporary-file logging is available. `handoff_note` says that vBot monitors the command, that its result arrives as a new message when it exits, that independent work may continue and dependent work ends the turn, and that the Agent must neither start a duplicate nor sleep or poll for the result; it also states the effective total timeout - that a set limit still applies including time in the background, or that no tool timeout applies. Only an immediate `background` handoff also names `process` action `wait` with a `pattern`, for a command that runs until stopped such as a server's ready line: a foreground command was expected to finish, and advertising `wait` after the 90-second handoff made Agents block on it (31 of 56 waits, Sessions 2026-09-26). A user-requested handoff instead explicitly names the user as the origin and the elapsed process runtime; its note keeps automatic delivery and independent-work guidance but omits the wait and duplicate-start advice. The short snapshot applies to manual, automatic foreground, and immediate background handoffs; completed results and completion notices use the shared 100-line/8,000-character cap (`tests/core/tools/test_bash_background.py`, `test_bash_lifecycle.py`). Process-control arguments live in the `process` Tool schema; output truncation and full-log retrieval guidance live in the affected result, so the handoff carries no separate process note.
- The completion watcher applies the same output cap/marker and submits one uniquely identified result to `TriggerService.submit_completion(...)`. Every Bash completion body places `Process ID: <process_id>` immediately after its status heading; `background_bash_statuses(messages)` folds these durable notes plus successful handed-off Bash and Process Tool Results into the status map returned as `chat.history.background_bash_statuses`, while the notes themselves remain hidden from WebUI history. `BACKGROUND_STATUS_TOOL_NAMES` and `BACKGROUND_STATUS_NOTE_MARKER` name the only records the fold reads, so Sessions selects just those; each record sets its process's status (last wins), so folds over consecutive ranges compose and an incremental History read reports only the appended records' statuses. A result that finishes during an active Run joins that Run at its next existing Model-request boundary as a System Reminder; this creates no extra Provider request. Results with no later request in their boundary Run are combined in one automatic follow-up Run at Run end, while later results stay pending for later delivery. A terminal detailed `process` status or successful kill cancels a still-pending automatic notice only after that manual Tool Result is durably persisted, so the same completion cannot be delivered twice and the status fold can still use that persisted Process result. The completion note body carries no timing - the WebUI's exact process times come from the accessor-only `bash_process_status_changed` event (see `process.md`), so the Model sees no UI-only timestamps. A process killed by the Tool deadline keeps the `killed` status heading and replaces the exit-code line with a `Reason:` line naming the elapsed tool timeout plus the longer-timeout/`timeout: 0` guidance, so the Model learns why the command stopped; the durable status fold still reads `killed`.
- Per-call cancellation: after spawn, Bash registers a cancel callback that kills the process. User cancellation calls `ProcessManager.cancel_for_user`, returns `{ ok: false, error: { code: "cancelled_by_user", message: "Command aborted by the user after <elapsed>" } }`, and leaves the process marked with its user origin. The message appends the compact runtime before the abort (`45s`, `14m 5s`, `1h 2m 3s`, `<1s`) computed from the tracked process start. Another owning-Run cancellation uses ordinary `kill` and returns `run_cancelled`. Foreground never hands off because of cancellation. The Chat Activity cancel control calls the same user-cancel Process path for an already handed-off process. A direct `chat.cancel_process` request while Bash is still in foreground also returns the existing `cancelled_by_user` failure, based on the tracked process origin even when neither Run nor per-call cancellation was set (`tests/core/tools/test_bash_lifecycle.py`). Its completion report uses "aborted by the user after <elapsed>" wording, while the completion coordinator suppresses a new follow-up Run for a user-cancelled origin.
- A successful result carries a `note` field when the call was read in a way the Agent should know (millisecond timeout, inherited `env_keys` name); failures fold the same text into the message where it matters (the timeout message).
- Display: `shell_display_parts` normalizes the call first, so any dialect shows its non-blank `description` (or `explanation`) and falls back to `command`. The command stays copyable either way: as its own copyable part, or as the description's `detail`, which the WebUI value card shows under the description. A handed-off row in the WebUI tracks the process, not the ~instant delegation call: while the process runs the row shows a live tick measured from the Tool call's internal start timestamp (`timing.started_at` - the command spawns at call start, and that timing never reaches the Model) with a running dot; when a terminal status arrives the dot settles and the tick is replaced by the process's real runtime (`finished_at - started_at` from the terminal notification). The expanded Result section swaps the handoff envelope for the actual completion result on the same terminal data. Without known times (terminal status arrived only through the durable fold, or after a full page reload - the live projection is memory-only) the time label stays empty rather than showing the misleading ~0s delegation duration; the durable `background_bash_statuses` fold stays string-valued and carries no timing.

## Conventions

- Relative `workdir` resolves from `ToolContext.effective_cwd` (the working directory); absolute working directories are allowed.
- Uses the platform-native shell: `pwsh -NonInteractive -Command` on Windows, `bash -c` elsewhere. Process output is always decoded as UTF-8, so on Windows `core/tools/_powershell.py` first sets `[Console]::OutputEncoding = UTF-8` and an `en-US` UI culture (PowerShell's messages in English; number and date formats keep the user's culture). Cmdlet output, captured native output, and console programs that follow the console code page (`cmd`, `dir`, ...) then arrive intact (`test_output_keeps_non_ascii_text`, `test_bash_powershell.py`). `pwsh -Command` parses its whole text before running any of it, so the Agent's command travels as a single-quoted literal (quotes doubled, typographic single quotes included) and is parsed after that setup with PowerShell's own parser: `using` statements, a `param` block and named blocks keep their meaning, a syntax error is thrown as PowerShell's usual `ParserError` with the command's own line numbers, and it runs nothing. Before, a syntax error was reported ahead of the setup: in one Swarm Run all 17 were German, 6 had broken umlauts, and every line number was one too high (Sessions, 2026-09). The command runs from a function defined on the first line of the wrapper text, since `Write-Error` reports its caller's position and PowerShell shows a position only beyond the first line; no wrapper line appears in the command's errors. The wrapper adds about 6,000 characters to the 32,767-character Windows command line, which leaves about 26,000 for the command (3 of 28,071 commands exceeded 20,000, Sessions 2026-09). Known limit: programs that write a fixed other encoding regardless of the console (e.g. UTF-16 from `wsl.exe --list`, or bytes explicitly encoded in a legacy code page) are not transcoded. The interactive Terminal needs no setup because ConPTY already delivers UTF-8. The same one-line setup statement installs a `CommandNotFoundAction` for `head`, `tail`, and `wc`, which Agents habitually pipe into: when such a command is genuinely missing (an installed one, e.g. Git's, still wins), the line-count forms (`-n N`, `-N`, `--lines=N`, `tail -n +N`, `wc -l`; pipeline or files) run through `Select-Object`/`Get-Content`, and any other option stops the script with a message naming the PowerShell equivalent (`test_bash_powershell.py`, real `pwsh` on a PATH without Unix tools). `pwsh -Command` alone exits with 1 whenever the last statement failed, so the wrapper preserves the last statement's success before diagnostic bookkeeping and exits with the corresponding status: `exit_code` is the last native program's code as with `bash -c`, 0 after a successful last statement, 1 after a failed cmdlet; an explicit `exit N` wins. The exit-status statement runs at the end of the command's last block: the unnamed body, a named `end` block, or an `end` block added after `begin` or `process` blocks (`test_exit_status_and_error_records_follow_the_last_statement`). `ProcessManager` connects the command's stdin to `DEVNULL` on every platform, so reads immediately receive EOF. There is no post-launch input or stdin opt-in. Required input belongs in files or pipelines inside the command; child processes may still create their own input pipes. Keeping `-NonInteractive` also disables PowerShell host prompts. Both Tool descriptions state the input boundary; Windows guidance names PowerShell and its syntax. Regression coverage: `test_foreground_command_finishes_inline_with_its_result` and `test_shell_pipeline_and_script_owned_input_remain_available` in `tests/core/tools/test_bash.py`, background completion in `test_bash_background.py`, and `test_stdin_reaches_its_end_and_pipelines_feed_nested_shells` in `test_bash_powershell.py`.
- On Windows, command shells, the one-time environment probe, and probe-cleanup `taskkill` use the shared windowless creation flags from `core/utils/processes.py`; none may create a visible console window in Desktop or background-server use.
- Non-zero exits are successful tool results with an exit code.
- `register_bash_tool(..., credential_resolver=..., prompt_blocks=..., update_handoffs=...)` wires Runtime-owned credential lookup and the update handoff registry, and declares the dynamic `tool:bash` Prompt Block. The block is empty without permanent Agent grants; otherwise it lists exact names and explains `env_keys`. Skill activation guidance is owned by the Skill Tool, not this System Prompt block.

## Constraints & Gotchas

- Accessors can request handoff of an already-running foreground Bash through its exact Run and Tool Call. The handler advertises this capability only after spawn and only when the existing depth policy permits background work. The foreground loop consumes the request through the existing handoff result, process tracking, timeout, and completion watcher; it never starts another command. Cancellation or a process that already finished wins over handoff. Coverage: `tests/core/tools/test_bash_background.py`, `tests/core/runs/test_runs_tool_cancellation.py`.

- Combined `output` and the streamed stdout/stderr Run events are ANSI-stripped - terminal color/escape sequences are removed before the text reaches the model or UI. Stripping happens once per pipe in `ProcessManager` (`core/tools/_process_output.py`); an ESC that starts no terminal control stays visible as `\x1b`; see `process.md`.
- The shared `get_shell_env()` entry point in `bash.py` also supplies Terminal launches and default-shell selection. A login shell environment is probed and cached with a bounded TTL
  (`SHELL_ENV_CACHE_TTL_SECONDS`, default 300 s). Concurrent first Bash calls
  share one in-flight probe task, and cancelling one waiter does not cancel
  that shared initialization. On Windows the probe overlays the live PATH from
  the registry (`HKLM` + `HKCU`), because a headless process never receives the
  `WM_SETTINGCHANGE` broadcast that follows a PATH edit. The Windows probe
  transfers Base64 of UTF-8, NUL-separated `NAME=VALUE` pairs so non-ASCII and
  multi-line values survive the console code page; the POSIX `env -0` probe
  decodes like `os.environ` (`os.fsdecode`). Malformed probe output keeps the
  process environment (`test_bash_environment.py`). When the cache is
  stale the next call re-probes directly. A shell-binary `FileNotFoundError`
  also self-heals: the handler logs a WARNING, resets the cache, re-probes, and
  retries the spawn once before failing.
- **Update handoff token:** when Runtime supplies `update_handoffs` and the Tool context has a result-persisted hook, each Bash call gives its command one fresh opaque `VBOT_UPDATE_HANDOFF` token (an inherited value is always removed first). Issuing writes nothing and logs nothing. The in-memory grant is released when the tracked process's wait task completes, in foreground and background mode, or immediately when spawn fails; the after-result-persisted callback acknowledges it, also after release. Only a claim through `application.update_handoff_mint` writes a durable ticket (and logs it once); lifecycle and consumers -> `cli/windows-application.md` -> Agent handoff. Coverage: `tests/core/tools/test_bash_update_handoff.py`.
- Env grants keep values out of Provider-bound prompts and Tool arguments but are not a shell sandbox: a command with an injected credential can print, transform, write, or transmit it. Granting a name authorizes Bash use; this layer does not claim secrecy from the executing Agent and does not redact process output.
- Spawn failures and tool-enforced timeouts are failure envelopes in foreground execution. A `process_timeout` is reported only when the timeout actually killed a still-running process (terminal status `killed`); a process that exits on its own as the deadline elapses keeps its completed/failed result instead of being masked as a timeout, including the interval after OS exit while output readers drain (`test_descendant_pipe_does_not_hide_exit_or_block_timeout` in `test_bash_lifecycle.py`). A failed timeout kill returns `process_kill_failed` from foreground execution and leaves the process available for retry. A handed-off process killed by the same deadline surfaces through its automatic completion note instead, never as a foreground `process_timeout` envelope.
- A `workdir` that does not exist or is a file fails before spawn, naming similar sibling directories or a missing parent.
- The `process_timeout` message names the elapsed limit in seconds, the larger-`timeout`/`timeout: 0` retry, at depth 0 `mode: "background"` for servers and watchers (not for long builds, which Agents then waited on), and any `note` about how the timeout was read. Timeout failures also append the output tail (the same 100-line/8,000-character budget, including its truncation marker) and the complete-log path to the error message, so diagnostics printed before the kill reach the model. A spawn `FileNotFoundError` names the missing shell, with an explicit PowerShell 7 hint when `pwsh` is absent on Windows.
- Completion submission carries the originating Run id and `project_id`, so Project Sessions deliver under their correct Project and user-cancelled origins can be persisted without recursively waking the Agent.
- **No process handoff inside a Sub-Agent.** Its Session cannot receive a later background completion after its Run ends. Background requests fail before spawn; foreground has no handoff deadline and registers no manual-background capability. The Bash timeout and outer Sub-Agent Run timeout still bound execution. `tests/core/tools/test_bash_background.py` covers waiting beyond the top-level handoff window, explicit rejection before spawn, and foreground handoff at depth 0.

- Deadline tasks observe the ProcessManager finalizer without cancelling it and retire when the command finishes, including background commands. Cancellation still kills commands with `timeout: 0`. Default, explicit, silent/noisy, handoff, and deadline-task cleanup regressions live in `tests/core/tools/test_bash_lifecycle.py`; process-tree and inherited-pipe cleanup remain covered by `test_process_manager_containment.py` and `test_bash_lifecycle.py`.

## Agent-facing text

Rows so far cover only the `mode` parameter; the description and the other parameters await their review.

| Text | Reason |
|---|---|
| `mode`: `foreground returns when the command exits, or hands it to the background after 90 seconds.` | States the handoff up front, so Agents do not pick `background` merely to avoid blocking; the number comes from `FOREGROUND_HANDOFF_SECONDS`. |
| `mode`: `background returns at once; use it for servers, watchers and other commands whose result your next step does not need.` | 25 of 56 `process` waits followed a `background` start of a build or test within seconds - a foreground call plus an extra round trip (F6; Sessions, 2026-09-26). |
| `mode`: `Background results arrive automatically.` | Prevents polling plans for a background command (F4). |
| `mode`: `Omit for foreground.` | Omit rule (F2). |
