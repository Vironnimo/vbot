# Bash Tool

Runs host shell commands and streams foreground stdout/stderr into the Run timeline.

`bash.py` owns execution and cancellation coordination. Internal `_bash_environment.py` owns the cached host environment and login probe; `_powershell.py` owns the Windows command wrapping (UTF-8 output setup placement and the exit-status statement); `_bash_results.py` owns completion/handoff result shaping and durable background-status projection.

Windows PATH refresh expands registry values marked `REG_EXPAND_SZ` before combining machine/user paths; literal registry strings remain unchanged (`test_bash_environment.py`).

## Interfaces

- Tool name: `bash`
- Registration: `register_bash_tool(registry, process_manager, trigger_service=None)`
- Schema: one open flat object requiring `command`, with optional `mode: "foreground" | "background"`, `description`, `workdir`, `timeout`, and `env_keys`. Omitted `mode` defaults to `foreground` in the handler. `description` is a short command-purpose title with no model-facing length constraint and no effect on execution. `env_keys` is an ordered unique array of shell-portable credential names, never values. The handler authorizes every requested name against the union of permanent `tools.bash.allowed_env` Agent settings and Env requirements from currently active Skills, resolves allowed values through Runtime credential precedence, and overlays them only into the spawned process environment. Removed `auto` mode and `background_after_seconds` calls fail before spawn; unknown arguments are handler-rejected. The model-facing schema emits neither `oneOf` nor `additionalProperties`.
- Provider projection: top-level Runs receive the optional `mode` enum (`foreground`, `background`). At `nesting_depth >= 1`, Chat uses the Sub-Agent description and omits `mode` entirely: the Agent has no execution choice. The handler independently rejects background requests at depth. Provider projection leaves canonical registry metadata untouched.
- `foreground` is the default and returns a short command's completed output inline. At depth 0 it hands a still-running command to vBot after `FOREGROUND_HANDOFF_SECONDS` (90 seconds); `background` hands off immediately. At depth >= 1 foreground waits until exit, timeout, or cancellation without any handoff deadline. Accessor-requested handoff remains available only at depth 0.
- `timeout` is a total runtime limit including time in background: omission applies `DEFAULT_TIMEOUT_SECONDS` (180 seconds) in foreground mode at every depth, while background mode runs without a Tool deadline unless an explicit positive value sets one; `0` disables the Tool deadline in both modes. Output and handoff never reset it. No output-inactivity kill heuristic is applied because valid work may be silent or redirect output to files.
- Descriptions teach unattended commands, captured output, the input boundary, host-shell syntax, and keeping commands under vBot ownership (no manual detach or daemonize). Both depth variants direct file discovery and content search to `search_files` when available, preserving Bash as a fallback when it is not exposed. Mode selection and automatic result delivery belong in the top-level mode parameter; next-step guidance belongs in the handoff result. Sub-Agent descriptions state that background execution is unavailable.
- Foreground success returns `{ status, exit_code, output, truncated }` plus `log_file` when truncated, where `output` is the combined stdout/stderr process log. Every vBot-authored `log_file` value and complete-log pointer uses the shared forward-slash Model presentation; subprocess output itself is untouched. The final tool result does not include separate `stdout` or `stderr` fields; live stdout/stderr remain SSE-only Run events.
- **Output-pattern failure hints:** a non-zero `exit_code` result additionally carries a `hint` field when a well-known failure shape was recognized - at most one, first match wins, scanned only over the first 4,000 characters of output (`core/tools/bash_hints.py`). Patterns cover POSIX and PowerShell command-not-found (with dedicated bare-`python`/`pip` variants), Python module-not-found (venv slip), git merge conflicts, "already exists", port-in-use, permission denied, API rate limits, and gh unknown JSON fields; exit codes 126/137/124 have fixed hints. Hints state the next action in one or two sentences and never annotate success. The automatic background completion note carries the same hint as a `Hint:` line after the output.
- **Model-facing final-output cap:** completed `output` keeps at most the newest 100 output lines within 8,000 characters, including the truncation marker. `core/tools/process.py:shape_process_output` owns this shared Bash/Process policy; Tool descriptions leave truncation and retrieval guidance to the affected result. `truncated: true` covers both cut causes (model cap here, process buffer cap upstream); either way the *beginning* is what's missing, and a leading marker line says so and names the complete per-process log file under `<data_dir>/artifacts/temp/bash/` (see `process.md`) so the Agent can inspect it with an available file Tool. If temporary-file allocation failed, the marker carries no path.
- Handed-off results return `{ status: "running", delivery: "automatic", process_id, handoff_note, ... }` plus a combined `output` snapshot captured before handoff: at most the newest 20 output lines and 4,000 characters including any truncation marker, and always include `log_file` when temporary-file logging is available. `handoff_note` says that vBot monitors the command, that independent work may continue or the current Run may end, that polling/duplicate starts are unnecessary, and that dependent work must wait for the result; it also states the effective total timeout - that a set limit still applies including time in the background, or that no tool timeout applies. A user-requested handoff instead explicitly names the user as the origin and the elapsed process runtime; its note keeps automatic delivery and independent-work guidance but omits polling and duplicate-start advice. The short snapshot applies to manual, automatic foreground, and immediate background handoffs; completed results and completion notices use the shared 100-line/8,000-character cap (`tests/core/tools/test_bash_output.py`). Process-control arguments live in the `process` Tool schema; output truncation and full-log retrieval guidance live in the affected result, so the handoff carries no separate process note.
- The completion watcher applies the same output cap/marker and submits one uniquely identified result to `TriggerService.submit_completion(...)`. Every Bash completion body places `Process ID: <process_id>` immediately after its status heading; `background_bash_statuses(messages)` folds these durable notes plus successful handed-off Bash and Process Tool Results into the status map returned as `chat.history.background_bash_statuses`, while the notes themselves remain hidden from WebUI history. `BACKGROUND_STATUS_TOOL_NAMES` and `BACKGROUND_STATUS_NOTE_MARKER` name the only records the fold reads, so Sessions selects just those; each record sets its process's status (last wins), so folds over consecutive ranges compose and an incremental History read reports only the appended records' statuses. A result that finishes during an active Run joins that Run at its next existing Model-request boundary as a System Reminder; this creates no extra Provider request. Results with no later request in their boundary Run are combined in one automatic follow-up Run at Run end, while later results stay pending for later delivery. A terminal detailed `process` status or successful kill cancels a still-pending automatic notice only after that manual Tool Result is durably persisted, so the same completion cannot be delivered twice and the status fold can still use that persisted Process result. The completion note body carries no timing - the WebUI's exact process times come from the accessor-only `bash_process_status_changed` event (see `process.md`), so the Model sees no UI-only timestamps. A process killed by the Tool deadline keeps the `killed` status heading and replaces the exit-code line with a `Reason:` line naming the elapsed tool timeout plus the longer-timeout/`timeout: 0` guidance, so the Model learns why the command stopped; the durable status fold still reads `killed`.
- Per-call cancellation: after spawn, Bash registers a cancel callback that kills the process. User cancellation calls `ProcessManager.cancel_for_user`, returns `{ ok: false, error: { code: "cancelled_by_user", message: "Command aborted by the user after <elapsed>" } }`, and leaves the process marked with its user origin. The message appends the compact runtime before the abort (`45s`, `14m 5s`, `1h 2m 3s`, `<1s`) computed from the tracked process start. Another owning-Run cancellation uses ordinary `kill` and returns `run_cancelled`. Foreground never hands off because of cancellation. The Chat Activity cancel control calls the same user-cancel Process path for an already handed-off process. A direct `chat.cancel_process` request while Bash is still in foreground also returns the existing `cancelled_by_user` failure, based on the tracked process origin even when neither Run nor per-call cancellation was set (`tests/core/tools/test_bash_cancellation.py`). Its completion report uses "aborted by the user after <elapsed>" wording, while the completion coordinator suppresses a new follow-up Run for a user-cancelled origin.
- Display: the summary prefers a non-blank `description` and falls back to `command`. A handed-off row in the WebUI tracks the process, not the ~instant delegation call: while the process runs the row shows a live tick measured from the Tool call's internal start timestamp (`timing.started_at` - the command spawns at call start, and that timing never reaches the Model) with a running dot; when a terminal status arrives the dot settles and the tick is replaced by the process's real runtime (`finished_at - started_at` from the terminal notification). The expanded Result section swaps the handoff envelope for the actual completion result on the same terminal data. Without known times (terminal status arrived only through the durable fold, or after a full page reload - the live projection is memory-only) the time label stays empty rather than showing the misleading ~0s delegation duration; the durable `background_bash_statuses` fold stays string-valued and carries no timing.

## Conventions

- Relative `workdir` resolves from `ToolContext.effective_cwd` (the working directory); absolute working directories are allowed.
- Uses the platform-native shell: `pwsh -NonInteractive -Command` on Windows, `bash -c` elsewhere. Process output is always decoded as UTF-8, so on Windows `core/tools/_powershell.py` prepends `[Console]::OutputEncoding = UTF-8` to the command text - after leading `using` statements and a script `param` block, or inside the first named block, which PowerShell requires first. Cmdlet output, captured native output, and console programs that follow the console code page (`cmd`, `dir`, ...) then arrive intact (`test_windows_shell_output_keeps_non_ascii_text`, `test__powershell.py`). Known limit: programs that write a fixed other encoding regardless of the console (e.g. UTF-16 from `wsl.exe --list`, or bytes explicitly encoded in a legacy code page) are not transcoded. The interactive Terminal needs no setup because ConPTY already delivers UTF-8. `pwsh -Command` alone exits with 1 whenever the last statement failed, so the wrapper also appends `if ($?) { exit 0 }; if ($LASTEXITCODE) { exit $LASTEXITCODE }; exit 1`: `exit_code` is the last native program's code as with `bash -c`, 0 after a successful last statement, 1 after a failed cmdlet; an explicit `exit N` wins. A script of named blocks admits no statement after them and keeps PowerShell's own status (`test_windows_shell_reports_the_last_program_exit_code`). `ProcessManager` connects the command's stdin to `DEVNULL` on every platform, so reads immediately receive EOF. There is no post-launch input or stdin opt-in. Required input belongs in files or pipelines inside the command; child processes may still create their own input pipes. Keeping `-NonInteractive` also disables PowerShell host prompts. Both Tool descriptions state the input boundary; Windows guidance names PowerShell and its syntax. Regression coverage: `test_bash_modes_finish_without_stdin_input`, `test_windows_shell_eof_and_command_pipelines`, and `test_shell_pipeline_and_script_owned_input_remain_available` in `tests/core/tools/test_bash.py`.
- On Windows, command shells, the one-time environment probe, and probe-cleanup `taskkill` use the shared windowless creation flags from `core/utils/processes.py`; none may create a visible console window in Desktop or background-server use.
- Non-zero exits are successful tool results with an exit code.
- `register_bash_tool(..., credential_resolver=..., prompt_blocks=..., update_handoffs=...)` wires Runtime-owned credential lookup and the update handoff registry, and declares the dynamic `tool:bash` Prompt Block. The block is empty without permanent Agent grants; otherwise it lists exact names and explains `env_keys`. Skill activation guidance is owned by the Skill Tool, not this System Prompt block.

## Constraints & Gotchas

- Accessors can request handoff of an already-running foreground Bash through its exact Run and Tool Call. The handler advertises this capability only after spawn and only when the existing depth policy permits background work. The foreground loop consumes the request through the existing handoff result, process tracking, timeout, and completion watcher; it never starts another command. Cancellation or a process that already finished wins over handoff. Coverage: `tests/core/tools/test_bash.py`, `tests/core/runs/test_runs_tool_cancellation.py`.

- Combined `output` and the streamed stdout/stderr Run events are ANSI-stripped - terminal color/escape sequences are removed before the text reaches the model or UI. Stripping happens once in `ProcessManager` (shared `core/utils/ansi.strip_ansi`); see `process.md`.
- The shared `get_shell_env()` entry point in `bash.py` also supplies Terminal launches and default-shell selection. A login shell environment is probed and cached with a bounded TTL
  (`SHELL_ENV_CACHE_TTL_SECONDS`, default 300 s). Concurrent first Bash calls
  share one in-flight probe task, and cancelling one waiter does not cancel
  that shared initialization. On Windows the probe overlays the live PATH from
  the registry (`HKLM` + `HKCU`), because a headless process never receives the
  `WM_SETTINGCHANGE` broadcast that follows a PATH edit. The Windows probe
  transfers Base64 of UTF-8, NUL-separated `NAME=VALUE` pairs so non-ASCII and
  multi-line values survive the console code page; the POSIX `env -0` probe
  decodes like `os.environ` (`os.fsdecode`). Malformed probe output keeps the
  process environment (`test_bash_environment.py`). When the cache is
  stale the next call re-probes directly. A shell-binary `FileNotFoundError`
  also self-heals: the handler logs, resets the cache, re-probes, and retries
  the spawn once before failing.
- **Update handoff token:** when Runtime supplies `update_handoffs` and the Tool context has a result-persisted hook, each Bash call gives its command one fresh opaque `VBOT_UPDATE_HANDOFF` token (an inherited value is always removed first). Issuing writes nothing and logs nothing. The in-memory grant is released when the tracked process's wait task completes, in foreground and background mode, or immediately when spawn fails; the after-result-persisted callback acknowledges it, also after release. Only a claim through `application.update_handoff_mint` writes a durable ticket; lifecycle and consumers -> `cli/windows-application.md` -> Agent handoff. Coverage: `tests/core/tools/test_bash.py`, `tests/core/tools/test__bash_update_handoff.py`.
- Env grants keep values out of Provider-bound prompts and Tool arguments but are not a shell sandbox: a command with an injected credential can print, transform, write, or transmit it. Granting a name authorizes Bash use; this layer does not claim secrecy from the executing Agent and does not redact process output.
- Spawn failures and tool-enforced timeouts are failure envelopes in foreground execution. A `process_timeout` is reported only when the timeout actually killed a still-running process (terminal status `killed`); a process that exits on its own as the deadline elapses keeps its completed/failed result instead of being masked as a timeout, including the interval after OS exit while output readers drain (`test_real_timeout_kill_during_reader_drain_keeps_exit`). A failed timeout kill returns `process_kill_failed` from foreground execution and leaves the process available for retry. A handed-off process killed by the same deadline surfaces through its automatic completion note instead, never as a foreground `process_timeout` envelope.
- Timeout failures (`process_timeout`) append the output tail (the same 100-line/8,000-character budget, including its truncation marker) and the complete-log path to the error message, so diagnostics printed before the kill reach the model. A spawn `FileNotFoundError` names the missing shell, with an explicit PowerShell 7 hint when `pwsh` is absent on Windows.
- Completion submission carries the originating Run id and `project_id`, so Project Sessions deliver under their correct Project and user-cancelled origins can be persisted without recursively waking the Agent.
- **No process handoff inside a Sub-Agent.** Its Session cannot receive a later background completion after its Run ends. Background requests fail before spawn; foreground has no handoff deadline and registers no manual-background capability. The Bash timeout and outer Sub-Agent Run timeout still bound execution. `tests/core/tools/test_bash_modes.py` covers waiting beyond the top-level handoff window, explicit rejection before spawn, and default/explicit foreground handoff at depth 0.

- Deadline tasks observe the ProcessManager finalizer without cancelling it and retire when the command finishes, including background commands. Cancellation still kills commands with `timeout: 0`. Default, explicit, silent/noisy, handoff, and deadline-task cleanup regressions live in `tests/core/tools/test_bash_timeout.py`; process-tree and inherited-pipe cleanup remain covered by `test_process_manager_containment.py` and `test_bash_process_exit.py`.
