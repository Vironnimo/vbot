# Sub-Agent Tool

Registers the public `subagent` Tool and the Sub-Agent-only `message_parent` Tool and delegates their behavior to `core/subagents/` (`subagents.md`). Listing, checking and stopping Sub-Agents belongs to `background_tasks` (`core/tools/background_tasks.py`), which follows `subagent` and the shell Tool.

## Data Model

- `core.tools.subagent` owns both Tools' names, descriptions, flat JSON Schemas, display metadata, registration, and the Tool-owned `tool:subagent` System Prompt block. `core/tools/_subagent_arguments.py` owns call-syntax normalization (the `argument_normalizer`); `core/tools/call_syntax.py` holds the shared spelling and placeholder helpers (also used by `status` and `project`).
- `SubAgentCoordinator` in `core/subagents/` owns everything after normalization: interpretation against the caller's tree, authorization, Sessions, Runs, forwarding and every result and refusal text (`core/subagents/_constants.py`).

## Interfaces

- `subagent` schema: one open flat object with optional `action: "run" | "send"` and siblings `content`, `description`, `agent_id`, `id`, `model`, `thinking_effort`, `secrets` (for `run`: names of the caller's Agent Secrets to pass, `secrets/agent-secrets.md` -> Lifetimes and grants); `required: []`, no `minLength`, no branch keywords, no `additionalProperties`. Omitted action means `send` when the call carries an `id` and `content`, a refusal naming the `send` call (and `background_tasks {"action": "stop", "id": "{id}"}` while the Agent can call that Tool) for an `id` alone, and `run` otherwise. `run` needs `content` and `description`; `send` needs `id` and `content`. Actions ignore fields they do not use. `background`, `session_id` and `background_tasks_action` (set only by the normalizer, see the former actions below) are accepted but unadvertised (`UNADVERTISED_PARAMETERS`); unknown fields follow the shared dispatch rule (`tools.md` -> Unknown fields).
- `message_parent` schema: `{content}` (required). Registered with `catalog_visible=False`, `session_scoped=True` and `activation=TOOL_ACTIVATION_SESSION_GRANT`: Chat grants it only in Sessions linked to a Parent Agent (`SUBAGENT_SESSION_TOOL_NAMES`, `subagents.md` -> Conventions), so no other Session ever sees its definition. Both Tools need `open_input_schema=True` and `execution_slot_required=False`.
- `message_parent` success: `{status: "queued", delivery_id, note}`. The id also labels the Parent section and activity log; success confirms submission, while the activity log records persistence or a failed/cancelled delivery. Acceptance restores Parent-directed final answers until the next user input; an immediately rejected submission returns `delivery_unavailable` without changing the target.
- Call syntax (`_subagent_arguments.py`, before schema validation): besides field and enum formatting, `operation` as action and `request`/`arguments`/action-key wrappers, the owner reads other harnesses' shapes, since Chat maps their Tool names (`Task`, `delegate_task`, `spawn_agent`, ...) to `subagent`: Claude Code/opencode `Task` (`description`, `prompt`, `subagent_type`, `run_in_background`), Hermes `delegate_task` (`goal`, `context` appended to the task as a `Context:` section), OpenClaw/pi (`task`, `label`, `agentId`, `agent`, `thinking`), and vBot's earlier `request` string and `blocking`/`non_blocking` flags. Action synonyms: `run` <- spawn, delegate, start, create, launch, ...; `send` <- message, steer, tell, continue, resume, followup, reply, answer, instruct. Placeholder values (`null`, blank or punctuation-only text, `unused`, `invalid-placeholder`, `__omit__`; plus `new` for `session_id` and `default`/`inherit` for `model`/`thinking_effort`) count as omitted. Conflicting spellings or delivery flags refuse. Non-empty `toolsets` and `tasks` refuse with the corrected call (a Sub-Agent always uses its Agent's own Tools; one task per call, sibling calls for several). `run_id`, `queue_item_id` and other unknown fields that could change the call stay invalid. Coverage: `tests/core/tools/test_subagent.py` (dialects, placeholders, refusal before side effects, through real dispatch).
- Former actions: calls that list, check or stop Sub-Agents run as `background_tasks`, because reading and stopping a named Sub-Agent are unambiguous and a refusal would cost a round trip. The normalizer moves `list` or a synonym (`status`, `ls`, `check`, `result`, ...) and `cancel` or a synonym (`stop`, `kill`, `abort`, `terminate`, ...) into `background_tasks_action`; the handler then calls the registered `background_tasks` handler directly, not `registry.dispatch`, so Extension hooks and Run events see only the `subagent` call: `list`, or `status` with an `id` (else a `session_id`), and `stop` with an id. A `cmd_` id is refused instead (`not_a_subagent`): a background command concerns no Sub-Agent and takes its own `background_tasks` call, which the hooks see. The result is that Tool's own, with `This call ran as background_tasks {call}, which lists, checks and stops Sub-Agents and background commands.` (a stop: `This call ran as background_tasks {call}.`) first in `notes`, or in front of the error message. A cancel word without an id returns the `stop` missing-id error unchanged. `wait`, `await` or `poll_until` (`is_wait_action`) fail in the normalizer with `subagent`'s own actions, whatever Tools the caller has: nothing waits for a Sub-Agent. When the caller cannot call `background_tasks` (`ToolContext.can_call`), list and stop words fail as an unknown action (`subagent was not run: "action" must be one of "run", "send"; received "<word>".`), and no `subagent` refusal names `background_tasks` (the missing-task, id-without-action, not-direct-child and limit refusals leave that part out; `core/subagents/_constants.py`). Coverage: `test_subagent.py::test_calls_that_list_check_or_stop_run_as_background_tasks`, `test_refusals_name_background_tasks_only_while_it_is_callable` (also the `cmd_` refusal), `test_unclear_or_unsupported_calls_are_refused_before_any_work` (the wait refusal), and in `tests/core/subagents/test_subagents.py` `test_send_reaches_only_direct_subagents` and `test_limits_refuse_another_subagent` (the stop clause with and without the Tool).
- Display: the row builder normalizes the persisted raw arguments first (falling back to them when normalization refuses), so dialect calls label what they meant. `run` rows show `description`, else the `content` preview, then the target Agent; `send` rows show the action and the public id, and a call run as `background_tasks` shows the action it ran (`list`, `status`, `stop`) and its id. `content` stays hidden from expanded argument details. Detail blocks (`_subagent_detail_blocks`, `tools/display.md` -> Display metadata): the brief as `task` (run) or the message as `content` (send); a notice for `send` outcomes (steered, started, queued); a call run as `background_tasks` shows that Tool's blocks (`background_tasks_detail_blocks`: listed tasks as a `results` block of title, then id, status, runtime or last Tool; one Sub-Agent's state as one result; a stop as a notice); a persisted result of the former `list` or `cancel` keeps its blocks (the listed Sub-Agents, `No sub-agents.`, or the stopped notice). A Sub-Agent's answers are not shown on the call row: they appear in its Session and as a delivery in the Parent's conversation when addressed there. `message_parent` rows show the message as `content`. Ids, notes and activity paths stay in the raw result. Coverage: `test_subagent.py::test_details_show_the_task_the_message_and_what_background_tasks_did`.
- Registration: `register_subagent_tools(registry, coordinator, prompt_blocks=None)` registers both Tools; with the Tool prompt registry it also contributes the dynamic `tool:subagent` block.

## Conventions

- `tools.subagent.allowed_agents` is optional Tool-owned configuration at the root of an Identity Agent's `agent.json`, not an Agent-wide required field. It holds additional targets only: a missing block or field defaults to `['*']`, `[]` is self-only, and explicit entries use bare Identity ids or qualified `agent@project` ids. Omitting `agent_id` on a `run` always selects the calling Agent, which is never repeated in the list. Renaming an Identity Agent moves its bare id in every list, and deleting one removes it (`agent.md`). Authorization and target lookup rules: `subagents/delegation.md` -> Targets.
- `content` for `run` is a self-contained brief (goal, context, scope, constraints, expected result); for `send` it is the follow-up message, which can rely on the Sub-Agent's history.
- Results identify a Sub-Agent by `id`, `agent_id` (exactly the value `agent_id` accepts: `agent@project` when the Sub-Agent has a Project), `session_id` and `project_id`; they never expose internal Run or Queue handles. The start result carries the Session address once; forwarded answers keep only the Sub-Agent id, Run id and answer Message ids. Start/send notes report delivery timing or admission state without repeating how to call `send`.
- The Tool definition explains separate Session history, the Agent's own Tools, the absence of automatic file isolation and automatic answer delivery. `action` explains background start, continued Sessions and the inferred default; `model` and `thinking_effort` name Session-persistent overrides and the different omission rules for `run` and `send`. The `tool:subagent` block carries the target catalog and delegation judgment. The catalog lists each additional Agent as id, name and description (descriptions cut at a word to `TARGET_DESCRIPTION_MAX_CHARACTERS` = 200), followed by the target choice rule (`TARGET_CHOICE_RULE`) only while the list is not empty. Further judgment: parallel work, independent review or context relief; small dependent steps stay with the Parent; file ownership stays separate and integration checks focus on the parts the result depends on. An unavailable requested Agent is named as unavailable and replaced with the caller's own Agent only when it can serve the same purpose. The final paragraph says to keep working or end the turn to await answers, without polling. Reply-target changes are explained by the event-specific reminders (`subagents.md`), not repeated in this block. Chat pins the block per prompt epoch (`chat/request-building.md`): target changes reach the Model as a System Reminder listing those targets (catalog title `The Agent ids under Sub-Agents`, one entry per `agent_id`); a change to the frame (`EXECUTION_GUIDANCE`, preceded by the choice rule while targets exist) sends the block's whole current text, so a list that becomes empty or filled arrives with or without the rule. The block is the same at every depth; a Sub-Agent at the nesting limit gets neither Tool nor block (`subagents/delegation.md` -> Limits).
- Missing-choice errors never invent a recipient or provide a task/message placeholder as an executable correction. A missing `description` asks for that field while preserving the original call; a missing `send` id lists the caller's children without selecting one, or explains how to start a Sub-Agent when none exists. A missing message asks for `content` while retaining the supplied id. Coverage: `test_subagents.py::test_run_without_description_keeps_the_task_for_correction`, `::test_send_reaches_only_direct_subagents`, and the call-refusal cases in `test_subagent.py`.

## Constraints & Gotchas

- Provider-schema narrowing and Tool visibility are guidance; `SubAgentCoordinator` remains the security boundary.
- `message_parent` must stay out of the catalog: it only works in a linked Session and refuses elsewhere, so offering it generally would invite failing calls.

## Verification

`scripts/probe_provider_tool_call.py --scenario tool_first_use --first-use-tool subagent`
supplies natural delegation, parallel review, follow-up and unavailable-target tasks
with competing Tools and production definitions/prompts, plus checking and stopping a
dispatched Sub-Agent, which pass only with a `background_tasks` call (a `subagent`
call run as `background_tasks` is counted separately). Real Sessions, Runs, queueing
and dispatch receive the requests; only the child's Model work is a deterministic
receiver. All attempts, calls, results and final claims are retained with
`--first-use-report`. `--scenario background_tasks --background-tasks-case list|status|stop`
asks for one exact `background_tasks` call on a Sub-Agent.

`python -m scripts.tool_lab probe scripts/tool_lab/cases/delegation.json --visible`
replays anonymized call shapes (dialects, placeholders, echoed fields, conflicts) for
`subagent`, `background_tasks`, `status` and `project` through production dispatch
and shows what the Model reads back.

## Agent-facing text

Review labels such as "Review B12" name the reviews of 2026-10-12: `tools/shell/agent-facing-text.md`.

| Text | Reason |
|---|---|
| `subagent`: `Delegate work to a Sub-Agent in a separate Session without this conversation's history.` | A self-delegation is not a conversation fork. Explicitly naming the missing history prevents a brief that relies on context the child never receives. User-approved review, 2026-10-14. |
| `subagent`: `Sub-Agents use their Agent's Tools and have no automatic file isolation.` | A Parent must supply context and split file ownership rather than expect inherited Tool choices or an automatic worktree. The coordinator starts a Session, not an isolated checkout. |
| `subagent`: `Their final answers arrive automatically unless the user writes to them.` | The first call needs no waiting/polling operation. Recipient switches and restoration reach the Parent through event reminders. |
| `action`: `run starts a new Sub-Agent in the background; send messages one you started, continuing its Session.` | Distinguishes a new delegation from a correction/follow-up and names the direct-child scope. |
| `action`: `Omit for send when id and content are present, otherwise run.` | An omitted action with an existing id does not create a second child. |
| `content`: `For run, a self-contained task: goal, relevant context, scope, constraints and expected result.` | Briefs without context produced Sub-Agents that guessed. |
| `content`: `For send, the message. Required for both.` | A follow-up can use the child's history, but neither action can run without content. |
| `description`: `For run, a 3-5 word title the user sees. Required for run.` | Names the Session and forwarded answers; without it titles were truncated briefs. |
| `agent_id`: `For run, an Agent id listed under Sub-Agents. Omit to use your own Agent.` | Names the available targets and self-delegation without suggesting copied conversation history. |
| `id`: `Sub-Agent id from a run result. Required for send.` | Agents constructed ids or passed Session ids. |
| `model`: `Model override as <provider>/<model-id>, kept for later messages.` | Weak Models used bare Model names; the override persists beyond one call. |
| `model`: `Omit on run to use your current Model for your own Agent, or another Agent's Model; omit on send to keep the current choice.` | Self-delegation captures the running Parent's Model, including a Session choice or fallback; another Agent keeps its own configuration. Follow-ups retain the child's stored choice. |
| `thinking_effort`: `Thinking effort override, kept for later messages.` and its run/send omission rule | Self-delegation also captures the running Parent's effort, including Provider default. Explicit choices win; another Agent uses its own effort. |
| `message_parent`: `Send a message to your Parent Agent ... without ending your turn.` | Reaches the Parent before the final answer. |
| `message_parent`: `Each message interrupts your Parent Agent.` | States the cost of a message so the Sub-Agent weighs it: every message wakes the Parent for a Run. In a GPT 6.1 Terra Session of 2026-10-27, 16 Sub-Agents sent 78 messages (one alone 16), mostly progress such as "commit hook running, merge follows"; the Parent ran 47 times in 20 minutes, 31 of them only to write the user a status. |
| `message_parent`: `Use it to ask what only your Parent Agent can decide while you continue other work, to report a blocker or finding that makes your Parent Agent or its other Sub-Agents change what they are doing, and to answer questions or status requests in its messages.` | Questions while blocked belong in the final answer (role block, `subagents.md`). The former "a finding that changes what your Parent Agent ... is doing" read as every finding: in the same Session each audit finding reached the Parent twice, as a message and again in the final answer. Status updates go out only on request; an unconditional ban contradicted the Parent-steering reminder. |
| `message_parent`: `Put progress, intermediate results and the task result in your final answer instead.` | Names where everything else goes, which avoids duplicate delivery of the task result and progress messages (same Session). |
| `message_parent`: `This call also directs your final answers to your Parent Agent until the user writes again.` | The call restores Parent replies even during a user-directed turn. |
| Block catalog: `Additional Agents:` / `No additional Agents are available.` | Lists exact selectable ids without repeating `agent_id` syntax; self-delegation remains available in both cases. |
| Block catalog, under the list only: `Choose one of these Agents only when the user or your task names it or its description fits the task; for any other work you delegate, use your own Agent.` | A Sub-Agent with two undescribed Identity Agents in its list delegated to them for work they were not meant for (2026-10-18); a listed Agent read as an invitation. Absent with an empty list, where it concerns no Agent. User-approved 2026-10-18. |
| Catalog line descriptions, cut at a word to 200 characters plus `...` | Repository descriptions (Team, Project Agents) can run to paragraphs; the start carries the purpose, the rest cost tokens in every request. Identity descriptions are at most 160 characters and never cut. User-approved 2026-10-18. |
| Block: `Delegate bounded work when it can run alongside other useful work, benefits from an independent review, or keeps a substantial investigation out of your own context.` | Gives concrete reasons to delegate instead of treating all divisible work as worth delegation. User-approved 2026-10-14. |
| Block: `Do small, dependent steps yourself.` | Avoids overhead for work on which the next step immediately depends. |
| Block: `Start independent tasks together and give file-editing Sub-Agents separate ownership.` | Preserves concurrency and avoids overlapping edits in shared files. |
| Block: `Integrate their findings and check the parts your result depends on.` | Keeps responsibility with the Parent without requiring it to repeat every delegated task. |
| Block: `If a requested Agent is unavailable, say so.` | Parents previously substituted self-delegation without disclosing that the requested Agent was unavailable (black-box runs, 2026-10). |
| Block: `Use your own Agent only when it can serve the same purpose; otherwise ask the user.` | A general worker is not automatically an adequate replacement for the requested specialist. |
| Block: `Identify it as your Sub-Agent, not as the requested Agent.` | Prevents inventing the identity the user requested (same black-box runs). |
| Block: `While Sub-Agents run, continue with other work your task still needs, not the work you gave a Sub-Agent. When no such work is left, end your turn: reply with a short status and no tool call. Each Sub-Agent's answer starts your next turn, so do not sleep, poll or read their logs to wait.` | Delegation should free the Parent for independent work, limited to work the task needs (shared wait wording, `tools/agent-facing-text.md` -> Waiting for background work). Agents otherwise poll `background_tasks`, sleep in the shell, reread activity logs or ask repeatedly; ending the turn permits completion delivery to wake them. The named ways to wait are the ones minimax-m3.1-flash used for 17 minutes under the former "do not poll for completion" (live Session, 2026-10-23). "not the work you gave a Sub-Agent" keeps the Parent from redoing or cross-checking the delegated work while it waits: in an eval of 2026-10-23, minimax-m3.1-flash read every delegated file and wrote its own check scripts in both Sub-Agent runs before ending its turn. |
| Redirect note: `This call ran as background_tasks {call}, which lists, checks and stops Sub-Agents and background commands.` | Calls in the former `list`/`cancel` spelling run instead of failing; the note names the Tool that does this from now on and the exact call it ran. |
| Command id refusal (`not_a_subagent`, only while the Agent can call `background_tasks`): `subagent was not run: <cmd> is a background command, not a Sub-Agent. Call background_tasks {"action": "stop", "id": "<cmd>"} instead.` (list and check words: `{"action": "status", ...}`) | A stop of a background command through `subagent` passed the Extension hooks, which saw only `subagent` (F3); the exact call goes through them (F2). Review G1 (a hook that denied `background_tasks` stops did not stop `subagent {"action": "kill", "id": "cmd_x"}`). |
| Wait refusal: `Nothing was run. Unknown action "wait". Use one of: run, send. Sub-Agent answers arrive as new messages. Continue with other work your task still needs, not the work you gave a Sub-Agent. When no such work is left, end your turn: reply with a short status and no tool call. Your next turn starts when an answer arrives.` | An Agent that tries to wait for a Sub-Agent learns that its answer arrives on its own (F4). The choices are `subagent`'s own: the former text listed `background_tasks`'s actions (list, status, stop) as if they were this Tool's (F3; one-shot shell plan, Phase 5 fix). |
| Stop clauses in refusals, only while the Agent can call `background_tasks`: `; to stop it, call background_tasks {"action": "stop", "id": "<id>"}` (an id without action), `, or stop <id> with background_tasks {...}` (a Sub-Agent of a Sub-Agent), ` or stop one with background_tasks action stop` (the active limit), ` To see your Sub-Agents instead, call background_tasks {"action": "list"}.` (no task) | Each names the exact way out of the refusal (F5) without naming a Tool the Agent does not have, which invites a failing call (F1; design rule: mention only Tools the Agent can call, `ToolContext.can_call`; one-shot shell plan, Phase 5 fix). |
