# Tool Registry and Dispatch Internals

How `ToolRegistry` registers and publishes Tools and how `ToolExecutor` dispatches a call: registration rules, contract compilation, dispatch steps, failure-code wording, `ToolContext` fields, concurrency and blocking work, the removed-Tool refusal, Tool prompt blocks, catalog publication, Tool-change comparison and the reach of a Tool rename. The contracts these internals keep live in `tools.md` -> Contracts.

## Source

The public `tools.py` entry point retains registration and dispatch; `_tool_execution.py` owns executor/batch scheduling and cancellation hooks, `_tool_workers.py` bounded blocking work, and `_tool_prompt_blocks.py` prompt-block declarations. Other internal units own definitions (`_tool_definitions.py`), per-call context (`_tool_context.py`), presentation (`_tool_display.py`, `tools/display.md`), and result validation (`_tool_results.py`). The package facade loads public exports and module attributes on first access and caches their original identities; public imports remain stable.

## Registration

- Names match `^[A-Za-z][A-Za-z0-9_]{0,63}$`. Registration compiles the canonical Draft 2020-12 contract up front and rejects invalid schemas, unknown families, or incoherent activation metadata before publishing (a followed Tool names one `activation_source` or a sequence of distinct ones, and is active while any of them is; `tool.list` reports several as a list); fixed-shape objects close by default while model-facing schemas set `open_input_schema=True` and omit `additionalProperties`. The contract treats an omitted root `additionalProperties` like `false`; only an explicit schema, `true` or `patternProperties` accepts undeclared arguments, Extension and MCP schemas included (`core/tools/contracts.py`). Families are comprehension/bulk-action metadata only - membership never implies activation. A Tool may additionally select a configuration-bound Definition Profile per Agent (`tools.md` -> Terms).
- Beyond Draft 2020-12, the contract refuses a `$ref` that leaves the schema (fragments such as `#`, `#/$defs/...` or `#anchor` stay inside it) and a `required` name missing from the same object's `properties` (`contracts._validate_schema_node`). It checks schema positions only: values of `default`, `examples`, `const` and `enum` are instance data, never checked as schemas, while a property of that name is (`test_compile_leaves_schema_like_data_and_local_references_alone`). A `required` name declared only inside `allOf` is still refused; accepting it at the root would also need the parameter list (`tools.md` -> Unknown fields) to include `allOf` properties (open).
- Contract compilation is memoized by the exact JSON content of its inputs, so the per-Provider-cycle contracts reuse one immutable compiled contract per unchanged definition and any content change compiles afresh. Inputs holding non-JSON values (for example tuples) always compile uncached, so the cache never changes whether a schema is accepted.
- A Tool may register `unadvertised_parameters` (name -> schema): root parameters its handler accepts without offering them, such as options copied from older conversation history (`web_fetch`) or a Participant's own identity echoed from reminders (Swarm). Dispatch validates them like advertised parameters, but they never appear in Provider definitions or argument errors. Aliases that an owner normalizer translates into advertised parameters need no declaration.
- A deliberately batched Tool may set `handler_validates_arguments=True` when whole-call schema rejection would violate item independence; its handler must then validate the complete root plus every item before that item's side effects. Handler-deferred validation currently supports independently executed batches whose item errors must not reject valid siblings; complete validation remains the owner's responsibility.
- Extensions register Tools via `api.register_tool(...)`; application order, collisions and diagnostics: `extensions/capabilities.md` -> Tools.

## Dispatch steps

Dispatch authorizes and readiness-checks, normalizes a deep copy of arguments against the cycle's exact input contract (`tools/call-repair.md`), validates unless the registered handler explicitly owns complete argument validation, executes, validates the envelope plus the executing Tool's retained result contract, and verifies finite JSON-serializability. Canonical dispatch records that selected result contract and the allowlist it checked the call against (for `can_call`) on the per-call ToolContext; Chat validation and Extension result hooks reuse it without resolving the live catalog again. Live catalog removal or replacement cannot change an already-started call's result validation. An invalid/non-serializable result raises `InvalidToolResultError`, distinct from argument errors, mapped to `invalid_tool_result`.

After validation, a Tool with `secret_sinks` gets Agent Secret references in those arguments replaced on its copy, on a Tool worker (`_substitute_secrets`); a `SecretUseError` fails the call as `secret_unavailable` (`<tool> was not run: <refusal>`) before the handler runs (`secrets/agent-secrets.md` -> References and sinks).

A live per-name denial resolver runs before hooks and handler for every sibling; the dispatcher also carries that resolver and the Run Tool restriction through ToolContext for delegated calls. Denial returns `tool_not_allowed` without side effects.

`ToolRegistry.authorize` owns the registration, Session-grant, opt-in and allowlist checks. Chat calls it before Extension Tool hooks, so a hook cannot replace a forbidden call or its failure. Canonical dispatch repeats it after the asynchronous hooks, against the current registration. The allowlist already includes the Run-local restriction (`test_runtime_denial_precedes_handlers_and_extension_hooks`).

## Failure codes

Whatever argument repair (`argument_normalizer`, shared normalization) and validation raise refuses the call as `ToolContractError` before the handler runs: `invalid_arguments` with the raised message unchanged (a bare `ValueError` from a normalizer needs no migration; a non-`ValueError` there is a defect, logged, and reads `<tool> was not run: <cause>`). `ToolContractError` (`contracts.py`) is the general refusal type: a handler raises it only before the call has any effect, and the `core/tools/arguments.py` helpers raise it too. `PermissionDenied` (`core/permissions`, `permissions.md`) is a Permission Rules refusal a handler raises before any effect: `permission_denied` with `retryable: false` and the refusal's message as `<tool> was not run: the permission rules refuse ...` (`PermissionRefusal.message(tool=...)`), never `invalid_arguments` (the call was understood) nor `tool_execution_error` (nothing ran). Every other exception escaping a handler, `ValueError`, `JSONDecodeError` and `UnicodeDecodeError` included, is `tool_execution_error`, logged with its traceback: `<tool> failed while running: <cause> It is unknown how much of the call took effect. Check the current state before you call <tool> again.` (`<cause>` is the message, or the exception type name when the message is empty). One mapping, `tool_failure_for_exception` (`_tool_results.py`), serves ToolExecutor and Chat and never raises; an exception without a message gets one complete sentence per code (for example `Tool not allowed: <tool>.`). A handler that catches exceptions itself keeps the same rule: only its argument refusals become `invalid_arguments`; an operation failure after an effect may have started is not an argument error (terminal, process and channel_send catch `ToolContractError`, never `ValueError`). Test helpers that stand in for the executor map exceptions with `tool_failure_for_exception` (`tests/core/tools/tools_test_support.py::dispatch_as_executor`), so a test sees the code the Model reads. Coverage: `test_tools_execution.py::test_failure_code_follows_the_phase_that_raised`, `test_chat_loop_tool_failures.py`.

## ToolContext

Besides the fields named in `tools.md` -> Contracts -> ToolContext, the per-call context carries identity/addressing (`agent_id`, session/run/tool-call ids, iteration number), `workspace`, `cwd`/`effective_cwd` (file Tools and `bash` resolve relative paths from it, `memory` deliberately not; path grammar: `tools/file_state.md` -> Path resolution), `subagent_session` (the Session is linked to a Parent Agent, so Agent Secrets resolve with `passed_only`; `secrets/agent-secrets.md` -> Lifetimes and grants), the admitted Run's `reply_surface` (including runtime-only Channel target/thread facts for `channel_send`; unaffected by later ingress into the same Session), `run_kind` (the dispatching Run's `RunKind`, `None` outside Runs; `runs.md` -> `RunKind`), cancel hooks wired by the chat dispatcher (an awaitable an `on_cancel` callback returns is awaited within the Run's cancellation cleanup budget, `runs/lifecycle.md` -> Cancellation), the change tracker scoped by complete Session address and Run id, `after_result_persisted(callback)` invoked only after ordered persistence, and `attach_result_payload(payload)` (Extension Tools in a Session only; `result_payloads_available` says whether it works; contract in `extensions/host.md` -> Tool result payloads). `can_call(tool_name)` answers, by registry name, whether the allowlist dispatch checked this call against and the Run's denial resolver let the Agent call a Tool. `offers(tool_name)` is `can_call` and listed in the Model request's Tools, `offered_tools`, which the executor fills from the request's input contracts; `None` outside a Model request counts every callable Tool as listed.

**Worked paths:** a file or shell Tool reports the absolute paths a call worked in with `context.record_worked_paths(*paths)`: `read` the file it reads, the edit Tools every path they change or guard (`_file_changes.py`, renames with source and destination), `bash` and `terminal` their working directory, `search_files` its roots. Paths are buffered and passed to `worked_paths_hook` once the call has finished, whatever its result; Chat uses them for folder instructions (`chat/request-building.md` -> Folder instructions). A Tool that touches the filesystem in a new place records its paths there too.

## Model Tool names

Today only the shell Tool `bash` is offered as `powershell` on Windows, because a Tool called `bash` makes Models write bash syntax. Model-facing text that names a Tool uses `model_tool_name`/`SHELL_MODEL_NAME`: Tool descriptions, guidance blocks, the opt-in `core:tools_list` block, `Tool not allowed`, argument errors and the repeated-failure reminder. Registration rejects a name that is another Tool's Model name (`DuplicateToolError`). Provider-native replay data (Responses output items, Gemini parts) keeps the names the Model emitted. Coverage: `test_model_names.py`, `test_tools_registry.py`, `test_tools_execution.py`, `test_chat_loop_tool_definitions.py`, `test_streaming.py`.

## Concurrency and blocking work

- `ToolExecutor.start_batch()` returns a `ToolBatch` that starts each Call the moment it is added (Chat adds Calls while the Model still streams); `execute_many` is the same batch with all Calls known up front. A batch may run its Calls in a given `contextvars` context (Chat passes the one from before its Model request). Unknown Tools invoke no handler and create no barrier. Extension hooks serialize their callbacks batch-locally without serializing parallel-safe handlers. If cancellation or another `BaseException` escapes a parallel group, the executor cancels and drains its remaining child Tasks before propagating the original abort; ordinary `Exception` failures remain per-call envelopes. Result persistence preserves the Assistant's original call order even when a parallel group finishes out of order. Run/provider/process/persistence failures stay outside the per-call envelope boundary. Chat's emitting registry delegates the execution-slot policy (`tools.md` -> Constraints & Gotchas). Interrupted batch recovery belongs to Chat (see `chat/run-execution.md`; coverage: `tests/core/tools/test_tools_execution.py`).
- Handlers offload blocking sections through the dedicated worker pool (`run_tool_worker` / `offload_tool_handler`) with admission backpressure and cancellation shielding; built-ins choose selectively (wholly offloaded: apply_patch/edit/write/project/search_files/memory/session_search/skill_manage; split: skill/read/channel_send/web_fetch). Ordinary sync built-ins keep loop-dispatch because some intentionally call loop-owned APIs; sync Extension handlers auto-offload.

## Removed Tools

Chat's dispatcher (`core/chat/tool_dispatch.py`) fails a call to a Tool announced to the Model as removed in the current prompt epoch (`ToolDispatchContext.removed_tool_names`, `chat/request-building.md`) first, after only a Provider-rejected call and before the denial resolver, hooks, handler and registry lookup, with `tool_removed` (retryable false): `Nothing was run: the Tool <name> was removed from your Tools in this Session. Use your other Tools, or tell the user if the task needs <name>.` An unregistered removed Tool therefore reports its removal instead of `tool_not_found`, and name resolution treats removed names as registered so a call to one is never remapped to another Tool.

## Prompt blocks

A Tool's `ToolPromptBlockRegistry` block renders only when the Tool is effectively allowlisted; `requires_generated` makes static text render nothing while the named Producer renders nothing (`prompts.md` -> Data Model). A renderer may return a `RenderedBlock` whose `BlockCatalog` lets Chat announce a mid-epoch change entry by entry, because Chat pins every dynamic block's text per prompt epoch (`chat/request-building.md` -> Dynamic prompt blocks per prompt epoch). Built-in `subagent` uses a dynamic block for its current catalog, and `secrets` one for the Agent's own Secrets (`secrets/agent-secrets.md` -> How the Agent learns its Secrets); `project` lists choices in its parameter Definition Profile instead (`tools/project.md`).

## Catalog publication

The registry is read from worker threads (prompt assembly) while the loop registers and removes Tools, so every ToolRegistry mutation publishes a new Tool and family dict instead of changing the current one; keep that copy-on-write rule when adding a mutation, or a listing in progress fails with "dictionary changed size during iteration". Live Extension catalogs publish atomically through `ExtensionOperations.replace_tools`; a ToolRegistry revision change makes a running Run compare the live catalog with its prompt epoch's Tool pin at the next request boundary and announce the difference as System Reminders, while the Tool list itself stays pinned until Compaction (`chat/request-building.md` -> Tool catalog per prompt epoch). Removing a catalog retires its authority. Definition-profile context includes the exact Agent/Project identity. See `extensions/mcp.md` for connection opt-ins and remote schema changes.

## Tool changes

Chat itself announces added, removed and On-demand Tools. `announce_changes` is a `register` keyword, also of `api.register_tool` and live Extension catalog declarations. `definition_change_announced` compares the parts a Tool names in it between the definition the Model knows and the current one: `description`, `parameters` (any change of the parameter schema), or `parameters.<name>` (that parameter's schema or whether it is required); without a declaration the next prompt epoch pins the current definition. Declared today: `channel_send` (`parameters`: a Channel on a new platform brings that platform's fields) and the MCP connection Tools (`parameters.target`, which lists the remote Tool names). Coverage: `test_tool_epoch.py::test_a_tool_change_is_announced_only_for_the_parts_the_tool_names`, `test_chat_loop_tool_definitions.py::test_an_announced_tool_change_reaches_the_session_and_validates_calls`.

## Renaming a Tool

Renaming a Tool or one of its parameters reaches beyond the definition: `ToolDisplay` summaries and hidden arguments, WebUI rendering of historical calls, fake Provider scenarios (`scripts/fake-provider.mjs`), generated Tool catalogs, persisted Tool Access Policy names, and Skills or prompts that teach the call shape. Inventory them before the change; recognizable older call shapes stay interpreted. Core names two Extension Tools: the file Tools' errors for a Swarm Wiki page number or Board post sent to them name `swarm_wiki` and `swarm_board` calls (`core/tools/_swarm_references.py`, `tools/read.md`), so renaming those Tools or their `action`, `page_id` or `message_id` parameters updates that module.

Example: the shell's `mode` became `run_in_background` (2026-10-11), which reached `scripts/fake-provider.mjs`, `scripts/tool_lab/cases/shell.json` and the playwright-cli Skill (`resources/skills/playwright-cli/SKILL.md`); `mode` stays an accepted alias (`tools/shell.md`).
