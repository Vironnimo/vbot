# Skill Tool

Tool that exposes the live Skill catalog, activates allowed Skills, and reads their UTF-8 package files. `skill` is directly configurable through Tool Access Policy and seeded default-on in the Project Tool Whitelist (`PROJECT_DEFAULT_ALLOWED_TOOLS`).

## Interfaces

- Tool name: `skill`.
- Registration: `register_skill_tool(registry, resolve_registry, refresh_skills, resolve_archived=None)` registers the Tool; `resolve_archived` (wired to `Runtime.archived_skill`) explains archived names (below). `resolve_registry` maps `(skill_project_id, agent_id)` to the live registry a call uses; `refresh_skills` rescans Skills from disk (wired to `Runtime.reload_skills_async`, invoked once on a named Skill miss). When the Session's `skill_project_id` names a Project that does not exist, registry resolution raises `ProjectNotFoundError` and the call fails `project_not_found` (`skill was not run: the Project "<id>" that this Session's Skills come from does not exist. Tell the user that this Project is missing.`); `skill_manage`'s scope lookup treats the same case as an unknown name (`test_runtime_skills.py::test_skill_tools_in_a_session_of_a_missing_project_refuse_or_miss`). Registry resolution, package reads, resource scans, and catalog projection use the Tool worker boundary; the async Runtime refresh builds its replacement registry in a worker and applies registry/cache/System Prompt mutations back on the Event Loop.
- Skill subject: a call works on the Skills of `ToolContext.skill_subject_id`, the calling Agent or, in a Librarian Session, the Agent it maintains (`ToolContext.skill_agent_id`, set by Chat dispatch from the resolved Agent, `projects/resolution.md` -> Librarian Skill subject). The registry, the archived-name lookup and the read-only marks resolve for it, and `skill_manage` writes its home, shared Skills, cache invalidation and merge references for it. `skill_writer(context)` names the history writer both Tools use: `librarian` for a Run of kind `librarian` and for every call in a bound Librarian Session (also a Run of the user there), `reflection` for another unattended Run, else `agent`, each with the call's Session, Run and Run kind; the first two are background writers, which see read-only marks and cannot change a pinned Skill (`test_skill.py::test_background_runs_see_which_skills_they_cannot_change`, `test_skill_manage.py::test_background_reviews_change_and_merge_unpinned_skills`).
- Schema: one flat model-facing object with optional non-blank `name`, optional `file_path` and optional integer `offset` (minimum 1); no arguments list the live catalog, `name` alone activates, and `name` plus `file_path` reads. `offset` starts a page at that line of the instructions (with `name` alone) or of `file_path`; an `offset` of 0 counts as omitted, and a `"line:character"` string continues a long line (split into `offset` plus the unadvertised `character`, like `read`). `file_path` accepts any portable relative UTF-8 package-file path, including `SKILL.md`, and requires `name` unless it is itself a package path naming the Skill. The unadvertised `args` (another harness's Skill arguments) is accepted; the Result then carries a `note` that Skills take no arguments. Generated/VCS paths and internal install receipts are excluded. The schema omits `additionalProperties`; dispatch rejects unknown arguments and the handler owns field dependencies.
- The Skill owner repairs known call wrappers, field formatting, the aliases `skill`/`skill_name`/`command` -> name and `path`/`file`/`file_pth` -> file_path (Claude Code `Skill {skill|command}` and Hermes `skill_view {name, file_path}` shapes), padded names, matching enclosing quotes, a leading `./`, and backslash separators before schema validation. Optional empty name/path values mean omission only after conflict checks.
- Name resolution (`_locate_skill`): the exact loaded metadata name always wins, including whitespace or trigger-unsafe characters. Otherwise, among the allowed names only, a name that differs from exactly one Skill in case, `-`/`_`/space separators, quotes or a leading `/`, `$`, `@` loads that Skill, and a path whose segment names a Skill (`name/references/x.md`, `skills/name`, an absolute `.../name/SKILL.md`) addresses that Skill and the rest as file_path (`SKILL.md` means activation). A file_path given as an absolute path inside the package, or with a `name/` prefix, is made package-relative. Several same-form matches resolve nothing. The miss path rescans once and asks the Skill Archive (next bullet); a name it does not explain fails `skill_not_found` with up to three similar names (`similar_skill_names`: one stray leading/trailing character, containment, or >= 0.8 similarity), else the allowed names when at most 20, else a pointer to the catalog. Suggestions never load. Package containment and Skill access still apply to the resolved target.
- Archived names: when the rescan still misses, `resolve_archived(agent_id, name)` returns the newest archive entry of that name from the calling Identity Agent's home, else the global home (`skills/history.md`). An entry whose `holder` (the Skill that holds its instructions now, after any later merges; `skills/history.md`) is loaded and allowed activates that Skill and adds `SKILL_ABSORBED_NOTE` to the Result's `note`, with `{target}` the holder and `{date}` the day the instructions reached it; with `file_path` the call fails `skill_not_found` with `SKILL_ABSORBED_FILE_MESSAGE` instead of reading another package's file. Any other archived package still on disk (`deleted`, `inactive`, or absorbed with no holder or one that cannot load; the message names the recorded `absorbed_into`) fails `skill_not_found` with `SKILL_ARCHIVED_MESSAGE`; a purged entry without a loadable target falls through to the ordinary miss. Coverage: `test_skill.py`.
- Display: named calls use `name` or the support-file path as their primary; a successful no-argument catalog call derives an exact presentation-only `results` count from its `count`; failures publish no count. Detail blocks (`_skill_detail_blocks`, `tools.md` -> Display metadata): a loaded Skill or support file shows `data.content` by reference as `content`, the catalog as `results`; a Skill that grants environment credentials adds an info notice that it makes them available to shell commands; an already active Skill shows only a notice saying it was not loaded again. Resource listings, activation guidance and notes stay in the raw result. Coverage: `test_skill.py` environment-access and already-active tests.
- `ToolContext.activate_skill(name, content) -> bool | None` - dedup-only session hook (`ChatSession.register_skill_activation`): `True` fresh, `False` already active, `None` no hook (treated as fresh). Nothing is persisted through the hook - the tool result itself is the durable carrier.

## Conventions

- `skill` is governed by Tool Access Policy plus the scoped registry's Skill policy: the Tool policy decides whether the capability is offered, while the Agent's `allowed_skills`, minus its `excluded_skills` (`skills.md` -> Agent Skill Exclusion), filters listing, activation, and reads from the ordinary shared pool. Agent-private Skills and the effective Skills granted by an active Project Context are always allowed inside that Identity-scoped registry; Project disables and shared-Skill opt-ins decide the Project grant. The no-argument result is `{count, content}`: the current live catalog as origin headings with `- name: description` lines, rendered by the same `core/skills/skills.py::format_skill_catalog_entries` as the System Prompt catalog.
- **The activation Result IS the durable carrier.** A fresh `skill(name)` activation returns `data: {name, status: "loaded", content, resource_files?, environment_access?}`. `content` is only the SKILL.md instruction body after complete YAML frontmatter removal; it contains no `<skill_content>` wrapper, directory preamble, resource block, or environment notice. `resource_files`, when present, is `{guidance, files}`; the guidance (`SKILL_RESOURCE_FILES_GUIDANCE`) says to run a `scripts/` file by its absolute path with the shell Tool and to read another file with `skill` and its relative file_path only when the instructions call for it; scripts are absolute paths, other files stay relative for this Tool. A `{baseDir}` marker in the body is still substituted with the absolute Skill directory (see `skills.md`). Sessions reconstruct the internal wrapped activation context from the structured Result for same-epoch dedup. At a committed Compaction boundary the checkpoint retains an instruction-free digest at the same Tool Result id, while the original durable carrier remains retrievable through `history`.
- When the activated Skill declares one or more vBot `env` requirements, `environment_access` carries the Bash guidance as a sibling of `content`. It lists the newly usable names and explains that each Bash call must request them through `env_keys`; the internal trigger/Compaction context wraps the same text before the instructions. The field is included even when permanent Agent grants already caused the System Prompt's `tool:bash` block to explain the general mechanism. Project Context grants only Skill visibility; requirement checks and Bash environment grants remain unchanged. File reads remain non-activating and do not receive this field.
- **Pages, never silent cuts.** Instructions and files are paged exactly like `read` pages text (`core/tools/_read_text.py::render_text_window`, 50 KB or 2000 lines per page, unnumbered): a cut-off page ends with `[Showing lines A-B of T. ... Continue with skill(name=..., [file_path=...,] offset=N).]`, the exact next call. Instructions longer than one page activate as their first page led by `SKILL_PARTIAL_INSTRUCTIONS_NOTE`; the Tool Result, the Session's activation context and trigger (`/name`) activations carry only that page. `skill(name, offset>1)` returns a later page of the instructions as `status: "continued"` and activates nothing; instruction line numbers count the body after frontmatter with `{baseDir}` replaced, so they match the activation page. Coverage: `test_skill.py::test_long_text_arrives_in_pages_that_end_with_the_next_call`.
- **File reads are relative and non-activating.** `skill(name, file_path)` confines the path to the resolved Skill directory and supported package shape, rejects missing or non-UTF-8 files, and returns `data: {name, status: "file_loaded", file_path, content}`, where `content` is the page that starts at `offset`. Reading `file_path: "SKILL.md"` returns the document including frontmatter, paged like any file, and is the required source for a complete `skill_manage` edit; activation by name returns only the instruction body. The result contains no absolute path and does not call the Session activation hook, so support-file reads remain separately trackable without affecting activation dedup.
- An already-active Skill returns a short stub (`status: "already_active"`, `message`, no content) only within the current Compaction epoch. A committed checkpoint resets dedup, so the next `skill(name)` call returns a fresh `loaded` carrier; aborted Compaction does not.
- **Rescan on name miss.** When a requested `name` is absent from the resolved registry, `skill` calls `refresh_skills` once and re-resolves before giving up, so a Skill hand-dropped after the Session registry was cached can activate or serve a file without a restart. A genuinely unknown name still returns `skill_not_found` (with suggestions, see Interfaces) after that single rescan. The current Prompt-Epoch Catalog is deliberately left untouched - only the live lookup is refreshed, with no availability note; successful Compaction later performs the catalog refresh. A no-argument catalog call reads the resolved live registry without an additional rescan.

## Constraints & Gotchas

- **The loaded envelope shape (`data.name` / `data.status == "loaded"` / `data.content`, plus optional `data.resource_files` / `data.environment_access`) is a persisted read contract**: `core/sessions/` parses it (`skill_tool_activation`) for same-epoch dedup, Compaction names/digest projection, environment grants, and usage statistics. Renaming those fields breaks activation scanning over current-format Sessions.
- When `skill` is excluded or denied by Tool Access Policy, listing, activation, and file reads are all unavailable; when it is available, an empty `allowed_skills` yields an empty catalog and blocks activation/read access.
- Keep all three modes in this one flat optional-field contract: `{}` lists, `{name}` activates, and `{name, file_path}` reads; `offset` only pages the latter two. Do not add an action discriminator or split catalog listing into a companion Tool.

## Agent-facing text

Definition: 141 estimated tokens (`python -m scripts.tool_lab definitions --show skill`), up from 109 before `offset`; the growth buys paged access to long instructions and support files, which otherwise entered the Context whole.

| Text | Reason |
|---|---|
| `List available Skills, load one Skill, or read one file from it.` | Names all three modes so the Agent picks `skill` for listing, loading and support files instead of reading the package through the shell. |
| `Skill to load or read.` | Pins `name` to the Skill, not a file or a trigger string. |
| `Omit to list available Skills; required when file_path is provided.` | Tells the only way to list, and prevents `file_path`-only calls. |
| `Relative path of a UTF-8 file inside the Skill package, including 'SKILL.md'.` | Relative to the package (absolute paths are repaired, but the canonical form is relative); naming `SKILL.md` gives the complete document for `skill_manage` edits. |
| `Omit to load the named Skill.` | Separates loading from reading: `file_path: "SKILL.md"` reads the file without activating the Skill. |
| `Line to start at in the instructions or file_path.` | Says what `offset` addresses in both modes; results name the exact continuation call, so the description carries no paging rules. |
| `Omit to start at the beginning.` | Keeps first calls from inventing offsets; 0 and 1 still load from the start. |
| `Skill '{name}' was {reason} on {date} and cannot be loaded. The user can restore it in the Skill controls. Call skill without arguments to list the available Skills.` (`SKILL_ARCHIVED_MESSAGE`; `{reason}` is `deleted`, `retired after a long time without use` or `merged into Skill '<target>'`, `{date}` is YYYY-MM-DD) | Explains why a name the Agent remembers no longer loads, so it stops retrying similar names; tells it the user can bring the Skill back, which it can pass on, and names the call that shows what is available. |
| `(read-only here: pinned by the user)`, `(read-only here: created by the user)`, `(read-only here: its creator is unknown)`, `(read-only here: shared by another Agent)` (`SKILL_READ_ONLY_MARKS`, appended to own Skills in the list of a Run without the user) | Lets a background review or the Librarian plan before writing instead of learning protection from refusals; the review briefs say the list marks them. Attended lists stay unmarked: those Agents can change these Skills. |
| `Skill '{name}' is {mark}. Do not change it; name a needed change in your closing reply.` (`SKILL_READ_ONLY_NOTE`, the `note` of a load in a Run without the user, before `content`; `{mark}` is a list mark, or `read-only here` for a bundled, global or Project Skill) | Weak Models loaded a global Skill and patched it at once without consulting the list (eval case `protected_skill`, A/B 2026-10-02); the load result is the moment of decision. |
| `Skill '{name}' was merged into Skill '{target}' on {date}; these are the instructions of '{target}'.` (`SKILL_ABSORBED_NOTE`) | Keeps an old name working after a merge and makes clear the content belongs to `{target}`, so the Agent uses the new name from then on. |
| `Skill '{name}' was merged into Skill '{target}' on {date} and has no files of its own anymore. Load '{target}' with skill and read its files instead.` (`SKILL_ABSORBED_FILE_MESSAGE`) | A file path of the old package may not exist in the target; instead of reading a different file under the same path, it names the call that lists the target's files. |
