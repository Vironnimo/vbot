# Image Tools

Built-in `analyze_image` and `image_generation` Tools for isolated visual analysis and caller-owned image creation/editing through central task-model bindings.

`core/tools/image.py` owns both registrations, handlers, and failure projection. Private siblings: `_image_inputs.py` (argument dialects and requested-image checks shared by both Tools), `_image_downloads.py` (image URLs and `data:` URLs for `analyze_image`) and `_media_failures.py` (Agent-facing wording for failed media-model requests, reusable by the other media Tools).

## Interfaces

### `analyze_image`

- Tool name: `analyze_image`
- Registration: `register_analyze_image_tool(registry, image_service, *, attachment_store)`; Runtime passes the Runtime `AttachmentStore`, which holds downloaded images.
- Model-facing schema: required non-empty `prompt` plus required non-empty `images` array of strings (local paths, public http(s) image URLs, or `data:` URLs, mixed in one call), with no `additionalProperties` keyword. Dispatch rejects unknown arguments, the handler rejects remaining malformed ones, resolves local paths against `ToolContext.effective_cwd`, downloads addresses into the Attachment store, and calls `ImageService.analyze()` with local files only.
- Dialects (owner argument normalizer, spelling-insensitive via `core/tools/call_syntax.py`): `image`, `image_path(s)`, `image_file(s)`, `image_url(s)`, `path(s)`, `file(s)`, `file_path(s)`, `url(s)` -> `images`; `question`, `query`, `instruction(s)`, `task` -> `prompt`. An `images` value that is one string, a JSON list string, an object with exactly one path key (`path`, `file`, `url`, `image_url`, `src`, ...), or an OpenAI-style `{"type": "image_url", "image_url": {"url": ...}}` item becomes the path list. Different values under two spellings fail with the central conflict error. `prompt` stays required: the Tool never invents the analysis request.
- Image URLs (user decision 2026-09-25: `analyze_image` always accepts image URLs, independent of whether the Agent may use web_fetch). `_image_downloads.image_address` recognizes an item as an address when it starts with `http(s):` (also after `<>`/quote/backtick wrappers, inside a Markdown link or image, or with a lost or doubled slash such as `https:/host`) or with `data:`; a schemeless text such as `example.com/cat.png` stays a local path. Web addresses download through `_public_http.fetch_public` (see `tools/web_fetch.md`), so the public-address guard always applies: private/local addresses, credentials in the URL and redirects to blocked addresses fail with `blocked_url`, and redirects, retries and timeouts behave as for web_fetch. The download limit per image is the Attachment-size ceiling (`AttachmentStore.max_size_bytes`, the same value the image service enforces). `data:` URLs accept base64 (whitespace, lost padding and the URL-safe alphabet tolerated, percent-escapes decoded) or percent-encoded bytes under the same limit, checked before decoding. The bytes must sniff as an image: otherwise `not_an_image` says what arrived (a web page - the address of a page rather than of its image, or an access check -, an SVG drawing, another media type, or an empty response). Downloads run concurrently; images are stored as Attachments only after every requested image arrived, so a failed call stores nothing. Failure codes come from the transport (`image_not_found` for 404/410, `access_denied`, `rate_limited`, `server_error`, `request_rejected`, `timeout`, `connection_failed`, `tls_error`, `host_not_found`, `invalid_url`, `blocked_url`, `redirect_loop`, `response_too_large`) or from the image checks (`not_an_image`, `image_too_large` and `invalid_arguments` for `data:` URLs, `storage_error`). With several images each failure line starts with `images[<index>]: ` and all failures are reported together; differing codes become `image_download_failed`, and `retryable` is true only when every failure is retryable. More images than one analysis takes (six) fail with `invalid_arguments` before any download.
- Local image checks (`_image_inputs`, before any download and before the service): a `file:` URL becomes its local path (`core.utils.paths.file_url_path`: drive letters kept on Windows, `file://host/...` becomes a UNC path there; elsewhere a host other than `localhost` or this computer is refused like a web address). The generation Tools (`resolve_local_images`) still refuse `http(s)` and `data:` addresses with `invalid_arguments` saying to save the file first. A folder fails with `image_read_error` listing up to six image files inside it as an example call. Missing files fail together with `image_not_found`: each names similar existing files from `core/tools/_path_suggestions.corrected_paths` (kept only when the stem is similar, so a shared extension alone is not a match), and when every missing file has one, the message ends with the corrected `images` call (addresses unchanged). Nothing is ever substituted.
- Display: the primary is the normalized `prompt` (so `question` calls still show it). The handler records the analyzed files via `ToolContext.add_display_media` in argument order: local paths as resolved, downloaded images as their stored Attachment file with the file name taken from the address. When a check or download fails, only the local paths are recorded. The final display persists them as internal `media_files` references. Server projection turns those paths into signed original-file URLs without storing or copying image bytes. Missing files keep a preview entry so the WebUI can show its unavailable-image placeholder; failed addresses get none. These references never enter the Model-facing result.
- Success data is the closed, validated object `{ analysis: non-empty string }`; `{}` and additional fields are rejected. The service retains bare Model id, Provider Usage, and the analyzed-image count internally; these do not enter the Agent-facing Tool Result. The handler passes internal Run/Session/Project and Extension identity so the durable Usage record contributes to scoped Statistics independently of Tool-result projection.
- Invalid arguments return `invalid_arguments`. Expected failures project their typed Image-domain codes directly: `image_not_found`, `image_read_error`, `image_too_large`, `unsupported_image_type`, `image_understanding_unavailable`, or `provider_error`; deterministic failures set `retryable: false`, while Provider failures preserve `retryable` and optional `attempts_made`. Unexpected exceptions bypass the Image handler and become the shared logged `tool_execution_error`.
- Failure wording (`image.py::_image_failure`, shared with `image_generation`): `image_understanding_unavailable` says the Settings entry is not available and tells the Agent to have the user choose a working Image understanding model at the place `_media_failures.settings_place` names (Settings → Tools → Images, video & music; Text to speech: Settings → Voice → Speech models, matching the WebUI pages in `webui/settings.md`). `provider_error` wording comes from `_media_failures.provider_failure_message`, classified by the chained Provider exception: content refusal (`ProviderContentRefusedError`, worded by `refusal_message`), credentials (`ProviderAuthError`), rate or usage limit (`ProviderRateLimitError`), no answer (`ProviderTimeoutError`/`NetworkError`), other retryable, and other refusals. The detail is `HTTP <status>: <reason>`, taken from the Provider's JSON `message`/`detail`/`error` field or an HTML page title and capped at 200 characters, so raw bodies never reach the Agent. Input-error messages from the service pass through unchanged.
- Description states that images (local files or image URLs) are sent to the configured external Provider and that text/instructions inside images are untrusted content, not instructions for the Main Agent.

### `image_generation`

- Tool name: `image_generation`
- Registration: `register_image_generation_tool(registry, image_service)`
- Canonical model-facing schema: required `prompt` (string, `minLength: 1`), optional `source_images` (non-empty array of local path strings), optional `output_dir`, plus the per-call choices `aspect_ratio`, `resolution` and `background`, with no `additionalProperties` keyword or defaults. The Definition Profile comes from `ImageService.generation_profile()` (`image_generation_parameters(profile)`, `model_tasks/media-profiles.md`): each per-call choice the configured Model offers becomes a string `enum` of its values, and the others are removed; `source_images` is removed for a text-only profile, else carries `maxItems` when the profile knows the limit. A profile accepting images gets the generation-and-editing description, every other state the text-only one. The profile key (`sources=...;<option>=<values>`) is deterministic and does not depend on the Run or Provider request. `source_images` makes the full-profile request image-to-image; omitting it keeps text-to-image behavior. Dispatch rejects unknown arguments, including `source_images` under the text-only profile; the handler rejects malformed arguments and an explicit empty source list. Dialects: `source_image`, `input_image(s)`, `reference_image(s)`, `image_path(s)` -> `source_images` (one string or one path object becomes a list, as for `analyze_image`); `output_dir` also accepts `output_directory`, `out_dir`, `save_dir`, and `output_folder`. An empty `output_dir`, `aspect_ratio`, `resolution` or `background` counts as omitted, and a whitespace-only `output_dir` uses the default folder. Source images go through the same local image checks as `analyze_image` (field name `source_images` in the corrected call). It resolves relative source and explicit output paths against `ToolContext.effective_cwd` and passes absolute `Path` values to `ImageService.generate_artifacts`. When `output_dir` is omitted, it supplies the existing caller-owned default: `<Workspace>/image-gen/` whenever `ToolContext.project_id is None` (the Identity Agent branch, also in a Working Project), otherwise `<ToolContext.effective_cwd>/image-gen/` for the Project Config Agent branch. The execution service creates missing output directories. All other image options (model, Provider, size, quality, image count, ...) stay in Settings `model_tasks.image_generation`. A supplied per-call choice overrides the Settings value for that call (per-call > binding > Provider default); translation (for example to a pixel `size`) and refusal of unoffered values live in `ImageProfile`, not in the Tool.
- Display: the primary is the quoted `prompt`, followed by supplied aspect ratio, resolution or background metadata. A successful generation derives an exact presentation-only `results` count from the returned `images`; failures publish no count. Each written image is recorded via `ToolContext.add_display_media`, so expanded details preview it, and the requested `source_images` are recorded as sources, including missing ones (see `tools.md`).
- Success data: `{ images: [{ path, media_type, size_bytes, width?, height?, revised_prompt? }, ...] }`. Each `path` is the generated image's absolute caller-owned file path rendered with the shared forward-slash Model presentation; `media_type`, `size_bytes` and the pixel `width`/`height` (absent for vector images) retain useful file facts for the agent. `revised_prompt` appears only when the provider reported rendering a rewrite that differs from the requested prompt, which can change the subject. Internal generation identity (`id`, `filename`, and `index`) is absent, and the generic top-level `artifacts` list is empty. Chat can project a path the Assistant references through the signed `/api/files/` delivery path; image generation does not keep a second data-directory copy.
- Invalid or empty `prompt` returns `invalid_arguments` with an example prompt. `source_images` under a text-only Model fails with `invalid_arguments` naming both fixes (remove it, or have the user choose an Image generation model that accepts images). Expected image failures project their typed codes like `analyze_image`: `image_error` now means the Image generation Settings entry is missing or cannot run the request (`ImageConfigurationError`/`ImageUnsupportedTargetError`, worded like the unavailable case above), `provider_error` uses the shared Provider wording, input errors keep their `image_*` codes, `generation_refused` (`ImageRefusedError`) uses `_media_failures.refusal_message`, and `provider_outcome_unknown` uses `_media_failures.outcome_unknown_message` with `retryable: false`. An unoffered per-call choice is `invalid_arguments` with the profile's message, which lists the offered values. `output_dir_unusable` (checked before the billed request) and `output_write_failed` use `_media_failures.output_failure_message`.
- The `output_dir` description tells the Agent that omitting it uses the default `image-gen` folder and that the result lists each saved file's path.

## Runtime

Runtime registers both Tools at startup with the same runtime-owned `ImageService`; neither Tool calls Providers directly. `image_generation` remains a normal allowlist Tool. `analyze_image` is registered in the catalog but Chat includes it in Provider Tool definitions and the effective System Prompt when the active Model route cannot carry images or the Agent explicitly lists `analyze_image` in `tool_access.granted`; either case still requires `await ImageService.analysis_is_available()`. That availability check requires both a usable `image_understanding` binding and at least one `image/*` MIME type on the configured target's actual Chat Adapter wire; it creates no Provider request and closes the temporary Adapter without letting a cleanup failure change availability. Normal Tool permissions still apply as a separate gate. On execution, the handler passes Run/Agent/Session identity and the parent Agentic Loop Iteration to `ImageService`, which completes the Provider-specific `DebugContext` before the isolated request.

The vision exception is a persisted Agent preference, independent of message content and attachment presence. All mode, ordinary Tool selection, family selection, and Project whitelist membership never imply this grant. None, denials, missing selection, and Project ceilings still restrict access. The shared Agent/Project Tool editor exposes "Available with vision" in the Tool's hover/focus details; turning the Tool off also removes its grant. Preview, request construction, live catalog refresh, and Run-local Model fallback use the same route filter without changing the Tool description/schema. Coverage: `tests/core/chat/test_chat_loop_tool_definitions.py`, `test_chat_loop_fallback.py`, `tests/core/agents/test_agents.py`, `tests/core/projects/test_resolver_config_agent.py`, and `webui/src/components/tools/__tests__/ToolAccessEditor.test.js`.

## Agent-facing text

Shared media failure wording in `core/tools/_media_failures.py` (also used by `generate_video`/`generate_music`):

| Text | Reason |
|---|---|
| `The <task> provider refused the request and created nothing.` | A refused render was reported as "outcome unknown ... images could not be decoded"; the Agent concluded the model was broken and fell back to web photos (Sessions, 2026-10-03). |
| `Its reason: <provider text>` / `It gave no reason, which most often means its content policy blocked the request.` | The Agent needs the cause to rephrase; the subscription wire sometimes reports none. |
| `Repeating the unchanged request gets the same refusal.` | Agents retried identical calls after the old message. |
| `Change what the prompt asks for, for example an original design instead of a named character, brand or real person, or tell the user.` | Names the two valid next steps; the example covers the refusals seen so far. |
| `Nothing was saved. The request to the <task> provider ended without a usable answer, so it is unknown whether the provider created the <product>.` | The old text exposed `operation_key`, HTTP status and decoder detail the Agent cannot act on; what was saved comes first. |
| `Repeating the call can create a second <product> at new cost. If you still need it, repeat the call once; if that fails too, tell the user.` | Bounds repeats to one instead of forbidding or encouraging them. `at new cost` holds for both billing and the subscription's usage limit; `charge` was false on the subscription. |
| `The <task> provider rejected its credentials (<detail>). Tell the user to check that provider's API key or sign-in in Settings.` | The Agent cannot fix credentials; only the user can. |
| `The <task> provider is limiting requests or its usage limit is reached (<detail>). Tell the user instead of repeating the call right away.` | `retry_async` already repeats a retryable 429 up to 3 times, honoring `Retry-After`, and a reached usage limit does not clear within a turn; an Agent cannot wait a controlled time, and `Wait before trying again` produced an immediate repeat that fails the same way. |
| `The <task> provider did not answer (<detail>).` / `The <task> provider failed (<detail>).` + `Repeat the call once; if it fails again, tell the user.` | A transient failure tried once is worth one repeat; `Try again later` gave no bound and no point at which to stop. |
| `... The request was tried <n> times. Tell the user instead of repeating the call right away.` | When the task client already tried several times (`attempts_made` > 1), a further repeat is waste; the count tells the Agent why. |
| `The <task> provider rejected the request (<detail>). If the reason names something in the call, change it and repeat the call; otherwise tell the user, who can choose another <setting> model in <place>.` | The detail decides between a corrected call and the user's Settings; `who may need to` used `may`. |
| `<setting> is not available (<cause>). Tell the user to choose a working <setting> model in <place>.` | No call can succeed until the user changes Settings; the cause is the service's own short reason, stated once. |
| Result field `revised_prompt` | The provider can render a different subject than requested; the Agent otherwise describes an image it did not get. |
| `Nothing was generated. The output folder <dir> cannot be used: <reason>. Pass another output_dir, or omit output_dir to use the default folder.` | The folder check runs before the request, so the Agent learns that nothing was billed and gets the two valid next calls. `<reason>` is English and chosen by error number (`os_error_reason`), because the system's own message follows the host language ("Zugriff verweigert"). |
| `The provider generated the <product>, but saving to <dir> failed: <reason>.` + `No file was saved.` or `Files saved before the failure: <paths>.` | The request succeeded but left no or only some files; the Agent must neither report success nor describe files it does not have. |
| `Repeating the call generates the <product> again at new cost. Tell the user before you repeat it.` | A repeat bills again, or counts against the subscription's usage limit, so the user decides; "charged" alone was false on the subscription. |
| `Nothing was saved. The <task> provider accepted the request as job <id>, but <reason>. If the job finishes, the provider bills it.` | Without the job state the failure reads like a plain error worth repeating. |
| `Repeating the call starts and bills a second <product> job. Tell the user, including the job id, instead of repeating the call.` | Names the cost of a repeat and the alternative without forbidding a repeat the user asks for; vBot cannot fetch the job later, so the id is the user's only handle. |
| `Nothing was generated. The configured <medium> model does not offer <name> <value>. Pass one of <values>, or omit <name> to use the default.` / `... has no <name> choice. Repeat the call without <name>.` | A value outside the enum, or a choice from an earlier Definition Profile, reaches the profile check; the text lists the valid values so one corrected call succeeds. |

## Constraints & Gotchas

- Only the per-call choices in `CALL_OPTION_NAMES` (`aspect_ratio`, `resolution`, `background`) belong on the Tool schema; `output_dir` controls local artifact placement rather than Provider generation behavior. Every other image option (model, provider, size, quality, image count, seed, output format, ...) stays Settings-only (user decision 2026-10-04: quality and image count stay in Settings). Adding a choice means a `CALL_OPTION_NAMES` entry with its profile rule and wire translation, plus a `_CALL_OPTION_PROPERTIES` description.
- When exposed by the full Definition Profile, `source_images` intentionally accepts any absolute or cwd-relative local image path the Agent can reach, not only Attachments or vBot-generated artifacts. Those file bytes are sent to the configured external image Provider; do not add a path allowlist or silently downgrade an edit to text-only generation. The text-only profile omits `source_images`, and the handler rejects it if a malformed call nevertheless supplies it.
- Masks, inpainting regions, fidelity, strength, and other advanced edit controls are not part of the Tool schema. Source-image presence plus the prompt is the complete edit intent for this capability.
- The tool should remain a normal user-visible tool, not an internal tool.
- `analyze_image` is not an automatic attachment transformer: a non-vision Main Agent receives the attachment path and consciously calls the Tool with a task-specific prompt. Vision-capable routes see the Tool only with an explicit `tool_access.granted` entry.
- The effective route test is the intersection of Model `input_modalities` containing `image` and Adapter `wire_media_support(model_id)` containing at least one image MIME type. A Model catalog flag alone is insufficient. Chat rebuilds the gate after Run-local Model fallback.
- Tests: `tests/core/tools/test_image.py` (`image_generation`: profiles, results, output directory, source images, refusals, failure wording), `tests/core/tools/test_image_inputs.py` (`analyze_image` with local images: dialects, local image checks, failure wording, row display) and `tests/core/tools/test_image_urls.py` (image and `data:` URLs with a fake transport: order, private-address guard, download and content failures, several-image reporting), all through `registry.dispatch` with the recording service in `image_test_support.py`.
- `analyze_image` may read any absolute or cwd-relative local image path the Agent can reach, or any public image URL (no web_fetch permission is needed; the public-address guard is safety, not permission, and always applies), and uploads its bytes to the configured external Provider. The execution service applies the Runtime Attachment-size ceiling per image, a fixed six-image and 100 MiB cumulative analysis limit, and supported-image sniffing; there is no path-root allowlist. These aggregate limits remain handler-owned and deliberately do not add `maxItems` or new guidance to the model-facing Tool schema; a rejected call returns an actionable error asking the Agent to pass fewer or smaller images. The handler checks the six-image count itself before downloading any address.
