# Image Tools

Built-in `analyze_image` and `image_generation` Tools for isolated visual analysis and caller-owned image creation/editing through central task-model bindings.

`core/tools/image.py` owns both registrations, handlers, and failure projection. Private siblings: `_image_inputs.py` (argument dialects and local image path checks shared by both Tools) and `_media_failures.py` (Agent-facing wording for failed media-model requests, reusable by the other media Tools).

## Interfaces

### `analyze_image`

- Tool name: `analyze_image`
- Registration: `register_analyze_image_tool(registry, image_service)`
- Model-facing schema: required non-empty `prompt` plus required non-empty `images` array of local path strings, with no `additionalProperties` keyword. Dispatch rejects unknown arguments, the handler rejects remaining malformed ones, resolves paths against `ToolContext.effective_cwd`, and calls `ImageService.analyze()`.
- Dialects (owner argument normalizer, spelling-insensitive via `core/tools/_call_vocabulary.py`): `image`, `image_path(s)`, `image_file(s)`, `image_url(s)`, `path(s)`, `file(s)`, `file_path(s)`, `url(s)` -> `images`; `question`, `query`, `instruction(s)`, `task` -> `prompt`. An `images` value that is one string, a JSON list string, an object with exactly one path key (`path`, `file`, `url`, `image_url`, `src`, ...), or an OpenAI-style `{"type": "image_url", "image_url": {"url": ...}}` item becomes the path list. Different values under two spellings fail with the central conflict error. `prompt` stays required: the Tool never invents the analysis request.
- Local image checks (`_image_inputs.resolve_local_images`, before the service): a `file:` URL becomes its local path (drive letters kept on Windows, `file://host/...` becomes a UNC path); `http(s)` and `data:` addresses fail with `invalid_arguments` saying to save the file first (web download would be a new fetch capability and is deliberately absent). A folder fails with `image_read_error` listing up to six image files inside it as an example call. Missing files fail together with `image_not_found`: each names similar existing files from `core/tools/_path_suggestions.corrected_paths` (kept only when the stem is similar, so a shared extension alone is not a match), and when every missing file has one, the message ends with the corrected `images` call. Nothing is ever substituted.
- Display: the primary is the normalized `prompt` (so `question` calls still show it). The handler records resolved original paths in `ToolContext.presentation_images` after the address checks and before the existence check; the final display persists them as internal `image_files` references. Server projection turns those paths into signed original-file URLs without storing or copying image bytes. Missing files keep a preview entry so the WebUI can show its unavailable-image placeholder; refused web/data addresses get none. These references never enter the Model-facing result.
- Success data is the closed, validated object `{ analysis: non-empty string }`; `{}` and additional fields are rejected. The service retains bare Model id, Provider Usage, and the analyzed-image count internally, but none enters the Agent-facing Tool Result or Session Statistics.
- Invalid arguments return `invalid_arguments`. Expected failures project their typed Image-domain codes directly: `image_not_found`, `image_read_error`, `image_too_large`, `unsupported_image_type`, `image_understanding_unavailable`, or `provider_error`; deterministic failures set `retryable: false`, while Provider failures preserve `retryable` and optional `attempts_made`. Unexpected exceptions bypass the Image handler and become the shared logged `tool_execution_error`.
- Failure wording (`image.py::_image_failure`, shared with `image_generation`): `image_understanding_unavailable` says the Settings entry is not available and tells the Agent to have the user choose a working Image understanding model in Settings under Specialized Models. `provider_error` wording comes from `_media_failures.provider_failure_message`, classified by the chained Provider exception: credentials (`ProviderAuthError`), rate or usage limit (`ProviderRateLimitError`), no answer (`ProviderTimeoutError`/`NetworkError`), other retryable, and other refusals. The detail is `HTTP <status>: <reason>`, taken from the Provider's JSON `message`/`detail`/`error` field or an HTML page title and capped at 200 characters, so raw bodies never reach the Agent. Input-error messages from the service pass through unchanged.
- Description states that files are uploaded to the configured external Provider and that text/instructions inside images are untrusted content, not instructions for the Main Agent.

### `image_generation`

- Tool name: `image_generation`
- Registration: `register_image_generation_tool(registry, image_service)`
- Canonical model-facing schema: required `prompt` (string, `minLength: 1`), optional `source_images` (non-empty array of local path strings), optional `output_dir`, plus two optional per-call intent knobs - non-blank `aspect_ratio` and `resolution` strings - with no `additionalProperties` keyword or defaults. The Definition Profile is selected from the configured `image_generation` Model: a Model advertising image input receives the full generation-and-editing schema/description, while every other configured state receives the text-generation-only schema/description with `source_images` removed. Both profiles retain `output_dir`, `aspect_ratio`, and `resolution`, have fixed deterministic keys, and do not depend on the Run or Provider request. `source_images` makes the full-profile request image-to-image; omitting it keeps text-to-image behavior. Dispatch rejects unknown arguments, including `source_images` under the text-only profile; the handler rejects malformed arguments and an explicit empty source list. Dialects: `source_image`, `input_image(s)`, `reference_image(s)`, `image_path(s)` -> `source_images` (one string or one path object becomes a list, as for `analyze_image`); `output_dir` also accepts `output_directory`, `out_dir`, `save_dir`, and `output_folder`. An empty `output_dir`, `aspect_ratio`, or `resolution` counts as omitted, and a whitespace-only `output_dir` uses the default folder. Source images go through the same local image checks as `analyze_image` (field name `source_images` in the corrected call). It resolves relative source and explicit output paths against `ToolContext.effective_cwd` and passes absolute `Path` values to `ImageService.generate_artifacts`. When `output_dir` is omitted, it supplies the existing caller-owned default: `<Workspace>/image-gen/` whenever `ToolContext.project_id is None` (the Identity Agent branch, including Rooted Agents), otherwise `<ToolContext.effective_cwd>/image-gen/` for the Project Config Agent branch. The execution service creates missing output directories. All other image options (model, Provider, size, quality, background, ...) stay in Settings `model_tasks.image_generation`. Each supplied intent knob is routed value-aware at the execution layer: sent as a native Provider parameter when the resolved Model advertises it with the requested value, otherwise appended to the prompt as a best-effort hint. A supplied intent knob overrides the Settings binding default for that call (per-call > binding > Provider default). Routing/precedence live in `core/model_tasks/image.py` (`split_image_call_options`), not in the Tool - see `.vorch/domain-maps/model_tasks/image.md`.
- Display: the primary is the quoted `prompt`, followed by supplied aspect ratio or resolution metadata. A successful generation derives an exact presentation-only `results` count from the returned `images`; failures publish no count.
- Success data: `{ images: [{ path, media_type, size_bytes }, ...] }`. Each `path` is the generated image's absolute caller-owned file path rendered with the shared forward-slash Model presentation; `media_type` and `size_bytes` retain useful file facts for the agent. Internal generation identity (`id`, `filename`, and `index`) is absent, and the generic top-level `artifacts` list is empty. Chat can project a path the Assistant references through the signed `/api/files/` delivery path; image generation does not keep a second data-directory copy.
- Invalid or empty `prompt` returns `invalid_arguments` with an example prompt. `source_images` under a text-only Model fails with `invalid_arguments` naming both fixes (remove it, or have the user choose an Image generation model that accepts images). Expected image failures project their typed codes like `analyze_image`: `image_error` now means the Image generation Settings entry is missing or cannot run the request (`ImageConfigurationError`/`ImageUnsupportedTargetError`, worded like the unavailable case above), `provider_error` uses the shared Provider wording, input errors keep their `image_*` codes, and `provider_outcome_unknown` keeps its message and `retryable: false`.
- The `output_dir` description tells the Agent that omitting it uses the default `image-gen` folder and that the result lists each saved file's path.

## Runtime

Runtime registers both Tools at startup with the same runtime-owned `ImageService`; neither Tool calls Providers directly. `image_generation` remains a normal allowlist Tool. `analyze_image` is registered in the catalog but Chat includes it in Provider Tool definitions and the effective System Prompt when the active Model route cannot carry images or the Agent explicitly lists `analyze_image` in `tool_access.granted`; either case still requires `await ImageService.analysis_is_available()`. That availability check requires both a usable `image_understanding` binding and at least one `image/*` MIME type on the configured target's actual Chat Adapter wire; it creates no Provider request and closes the temporary Adapter without letting a cleanup failure change availability. Normal Tool permissions still apply as a separate gate. On execution, the handler passes Run/Agent/Session identity and the parent Agentic Loop Iteration to `ImageService`, which completes the Provider-specific `DebugContext` before the isolated request.

The vision exception is a persisted Agent preference, independent of message content and attachment presence. All mode, ordinary Tool selection, family selection, and Project whitelist membership never imply this grant. None, denials, missing selection, and Project ceilings still restrict access. The shared Agent/Project Tool editor exposes "Available with vision" in the Tool's hover/focus details; turning the Tool off also removes its grant. Preview, request construction, live catalog refresh, and Run-local Model fallback use the same route filter without changing the Tool description/schema. Coverage: `tests/core/chat/test_chat_loop_tools.py`, `test_chat_loop_fallback.py`, `tests/core/agents/test_agents.py`, `tests/core/projects/test_resolver_config_agent.py`, and `webui/src/components/tools/__tests__/ToolAccessEditor.test.js`.

## Constraints & Gotchas

- Only the two curated per-call model-intent knobs (`aspect_ratio`, `resolution`) belong on the Tool schema; `output_dir` controls local artifact placement rather than Provider generation behavior. Every other image option (model, provider, size, quality, background, seed, output format, ...) stays Settings-only. Adding a third model-intent knob is a Tool-schema property plus one hint-label entry in `split_image_call_options` - no execution-layer rework.
- When exposed by the full Definition Profile, `source_images` intentionally accepts any absolute or cwd-relative local image path the Agent can reach, not only Attachments or vBot-generated artifacts. Those file bytes are sent to the configured external image Provider; do not add a path allowlist or silently downgrade an edit to text-only generation. The text-only profile omits `source_images`, and the handler rejects it if a malformed call nevertheless supplies it.
- Masks, inpainting regions, fidelity, strength, and other advanced edit controls are not part of the Tool schema. Source-image presence plus the prompt is the complete edit intent for this capability.
- The tool should remain a normal user-visible tool, not an internal tool.
- `analyze_image` is not an automatic attachment transformer: a non-vision Main Agent receives the attachment path and consciously calls the Tool with a task-specific prompt. Vision-capable routes see the Tool only with an explicit `tool_access.granted` entry.
- The effective route test is the intersection of Model `input_modalities` containing `image` and Adapter `wire_media_support(model_id)` containing at least one image MIME type. A Model catalog flag alone is insufficient. Chat rebuilds the gate after Run-local Model fallback.
- Tests: `tests/core/tools/test_image.py` (registration, profiles, service projection) and `tests/core/tools/test_image_inputs.py` (dialects, local image checks, failure wording, all through `registry.dispatch`).
- `analyze_image` may read any absolute or cwd-relative local image path the Agent can reach and uploads its bytes to the configured external Provider. The execution service applies the Runtime Attachment-size ceiling per image, a fixed six-image and 100 MiB cumulative analysis limit, and supported-image sniffing; there is no path-root allowlist. These aggregate limits remain handler-owned and deliberately do not add `maxItems` or new guidance to the model-facing Tool schema; a rejected call returns an actionable error asking the Agent to pass fewer or smaller images.
