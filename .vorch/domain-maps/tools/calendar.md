# Calendar Tool

Manages the local calendar through `CalendarService`: listing with expanded occurrences, single and repeating events, single-occurrence removal, free-time search, and event-relative Agent actions.

## Interfaces

- Tool name: `calendar`
- Source: `core/tools/calendar.py` (registration, dispatch, list/find_free and event handlers, event results), `_calendar_arguments.py` (call reading before validation), `_calendar_times.py` (zone, end and window reading into server time; time rendering), `_calendar_actions.py` (action handlers and action lines), all under `core/tools/`.
- Registration: `register_calendar_tool(registry, calendar_service)` registers the Tool-owned `argument_normalizer` (`_calendar_arguments.normalize_calendar_arguments`) and six unadvertised parameters (`timezone`, `end`, `location`, `query`, `duration_minutes`, `duration_days`) that only the normalizer's readings produce or keep.
- Schema: one open flat object requiring `action` (`list`, `create`, `update`, `delete`, `find_free`, `add_action`, `update_action`, `delete_action`), with optional siblings `when`, `id`, `title`, `start`, `duration`, `rrule`, `notes`, `prompt`, `target`, `session`. The handler requires `title` + `start` for create, `id` plus a changed field for update, `id` for delete, `id` + `when` + `prompt` for add_action, and an action id for update_action/delete_action. `rrule` keeps the genuine `object | null` semantic because update uses explicit null to stop repetition.
- The description names only what the Tool manages: events, free time, and actions attached to an event, instructions an Agent carries out before, at or after it (user decision 2026-10-08: the time zone, how an action's Run starts, that actions move and are deleted with their event, and the pointer to `cron` were cut). `start` says times are local; `list` names the zone (`timezone`); update and delete results report an event's actions.
- Display: the summary leads with the normalized `action`, followed by the first available `title`, `id`, or `when`; persisted calls keep the Model's spelling and are normalized for the label. A successful `list` derives the exact `occurrences` count; other results carry no such field.
- Coverage: `tests/core/tools/test_calendar.py` (actions, results, errors), `tests/core/tools/test_calendar_call_tolerance.py` (other shapes, repetition, ids, stand-ins, conflicts) and `tests/core/tools/test_calendar_call_times.py` (lengths, time zones, action times), all through production dispatch against a real `CalendarService` (`tests/core/tools/scheduling_tool_support.py`). `scripts/tool_lab/cases/automation.json` holds the probe cases; the probe shares one calendar across a file's cases, so each calendar case uses its own dates and titles.

## Conventions

- `when` for list/find_free accepts `today`, `tomorrow`, `this week`, `next week`, `this month`, `next month`, a `YYYY-MM-DD` date, a `YYYY-MM` year-month, or `start..end` (a date end side includes that whole day), resolved by `core/calendar/when.py`. `list` defaults to the current month, `find_free` to the next 7 days. For actions, `when` is `start` or `end`, optionally `+`/`-` a whole duration in `m`, `h` or `d`.
- The start form decides the event kind: a date makes an all-day event, a local date-time a timed one. The Tool never exposes `all_day`; update passes the matching `all_day` so kind switches work. `duration` is minutes for timed events and find_free, days for all-day events; create defaults to 60 minutes / 1 day, update keeps the current length. A length whose unit the call names (`"1.5h"`, `"2 days"`, ISO `PT90M`/`P1W`, `minutes`/`duration_hours` fields, a numeric `days` without a frequency) becomes `duration_minutes` or `duration_days` in the normalizer, independent of the event; `_calendar_times.apply_length` then reads it against the start (sent, else stored): days on an all-day event and minutes on a timed one are the duration; minutes on an all-day event become days only in whole days, else a choice between a timed event (`<HH:MM>` start) and rounded-up whole days; days on a timed event become the minutes to the same server clock time that many days later (days x 1440 for repeating events), named in a note with the end; find_free reads days as x 1440 minutes with a note; lengths that disagree offer one call each.
- `rrule` accepts `freq` (daily/weekly/monthly/yearly), `interval`, `count` or `until` (inclusive date), and `by_weekday` for weekly rules. Null on update stops repetition; null on create is refused.
- Omitted `target` on add_action uses the calling Agent and Project; explicit targets are `agent` or `agent@project`. Omitted `session` means a fresh Session per execution; `current`/`this` resolve to the calling Session only when the target is the caller. `max_delay` (add_action, update_action) is a string `<n>m`, `<n>h` or `<n>d`, `0m` (skip every missed start), or `unlimited` (no own limit; on update_action it removes the limit); the handler stores whole minutes as `max_delay_seconds`, which only shortens the window the event sets (`calendar.md` -> Catch-up). Omission on add_action leaves the event's window; on update_action it keeps the limit. add_action, update_action and update hold the Agent reference lock (`AutomationReferences.lock`, passed to `register_calendar_tool` as `reference_lock`) like the calendar RPCs, so a call cannot select or revive a reference between a removal's reference check and the removal (`test_reference_changes_wait_for_the_reference_lock`).
- Results are plain fields in server-local time, never the persisted record or UTC instants, and never carry `retryable`:
  - an event: `id`, `title`, `start`, then `end` (timed) or `days` (all-day), `repeats` (the rule as the Agent would send it, without nulls or `interval` 1), `removed_occurrences`, `notes`, `actions` (count), `note`. A timed `end` comes from `CalendarService.event_span`, so across a DST transition local end minus start can differ from the duration. A repeating event's own zone resolves through `_calendar_times.event_zone`, which refuses the call (`calendar was not run: event <id> ... keeps its times in the time zone ...`) instead of raising when this server's time zone data lacks it; the service already skips such events at load, so only zone data changing while vBot runs reaches that refusal.
  - `list`: `events`, `occurrences`, `window`, `timezone`, optional `matching`, `action_error`, `note`, and one text block per event. A repeating event's block shows its occurrence starts (more than 8 are abbreviated to the count, the first three and the last); each action shows `action <id>: <when>, runs <target> in <Session>` (plus `, max_delay <d>` when set), an indented prompt, the last 3 non-pending executions with Session ids (an execution that could not start its Run shows its stored reason instead: `<due> failed: <reason>`), and `next:` for the next pending one.
  - `find_free`: `free`, `window`, `timezone`, `note`, and one line per free span `<start> to <end> (<length>)`. Each span is a whole gap of at least `duration` (max 10 shown; the note says when more free time follows or none was found). find_free ignores cron jobs.
  - `delete`: `status: deleted` plus `actions_removed`, or for one occurrence of a repeating event `removed_occurrence` and `status: occurrence removed; the rest of the series stays`.
  - an action: `id`, `event` (`Title (evt_...)`), `when`, `target`, `session` (`a fresh Session each time` when omitted), `next_due` or a note that no occurrence lies ahead; delete_action returns `id`, `event`, `status: deleted`.

## Argument reading

`_calendar_arguments.normalize_calendar_arguments` runs before schema validation and executes a call whose intent is unambiguous; it never writes to a guessed event, never drops a requested effect and never picks between conflicting values. When readings differ, it raises `CalendarCallRefusedError` (an `invalid_arguments` failure) before any change; every refusal starts with `calendar was not run:` and ends with the exact corrected call (`Send: {...}`) or one call per reading. Stand-ins in angle brackets (`<instruction>`, `<e.g. start - 1h>`) mark values the Agent must supply, so a template never executes: sent back unchanged in `title`, `notes`, `prompt` or `target` it is refused (without a Send, naming what belongs there), since storing it would make it real and dropping it would lose or default the value; in the other fields it is omitted. Placeholder words (`TBD`, `none`...) count as omitted in these fields. Prompts and notes longer than 120 characters are replaced in corrected calls by `<the prompt from this call>`.

- Shapes: a JSON string; `event`/`resource`/`requestBody`/`data` wrappers; Google time objects (`dateTime`, `date`, `timeZone`; an all-day `end` date is exclusive); top-level recurrence parts (`frequency`, `byday`); `duration_hours`; reminder minutes (`minutes_before`).
- Spellings: Google/iCalendar and common Tool fields (`summary`, `description`, `event_id`, `start_time`, `dtstart`, `recurrence`, `timeMin`/`timeMax`, `instruction`, `agent_id`, `session_id`), action synonyms (`add_reminder`, `reschedule`, `free_busy`, ...), RRULE strings (`FREQ=WEEKLY;BYDAY=MO,WE`, BYMONTHDAY/BYMONTH equal to the start's day/month), phrases (`weekly`, `every 2 weeks`, `weekdays`, `mon, wed`), spelled and ISO 8601 durations, and reminder phrasing (`30 minutes before`, `-30m`, `at start`).
- Accepted extras: `end` becomes a duration (all-day same date = 1 day, an `HH:MM` end before the start rolls to the next day); `location` becomes a `Location:` first notes line; a `title` on list becomes the `query` filter over titles and notes; `id` on list shows that event (or an action's event) even outside the window; inert Google keys (`orderBy`, `sendUpdates`, ...) and the default calendar id are dropped.
- Refused with calls: several events matching a title where an id is needed (one match supplies its id in the corrected call), an event id where an action id belongs or the reverse (naming the event's action ids), a relative `when` or action fields on create/update (offers add_action or the event call alone), change fields on list/find_free, `id` on create, changes on delete, an unsupported RRULE part (offers the reduced rule), an `interval` or `count` (also RRULE `INTERVAL`/`COUNT`) that is no whole number (`rrule.interval must be an integer between 1 and 1000`; `test_rule_number_that_is_no_whole_number_is_refused`), an all-day end on a later date (through or ending before), an all-day end that is no date or names a day that does not exist (`"end" 2030-02-30 does not exist: February 2030 has 28 days.`; both offer the length in days as duration), end and duration that disagree, lengths that disagree, a time span on a date start, an unreadable duration (with a duration stand-in, never the refused text), a bare number or `+30m` as action `when` (start or end), a clock time as a repeating event's action `when` (offers the relative form at the nearest occurrence), another calendar, attendees (offers them in notes), and reminders (points to add_action).
- `max_delay` spellings and flags are read as in the cron Tool (`tools/cron.md` -> `max_delay`) by the shared `core/tools/_durations.read_max_delay`; refusals say `missed start` and show the stand-in `<duration such as 2h>`.
- Event fields on add_action/update_action/delete_action (a `title` that does not find the event, `start` beside a `when`, lengths, `rrule`, `notes`, `end`, `location`) change nothing: the result note names them with the event's `update` call (keeping `timezone` next to start/end), and update_action carrying only event fields is refused with that call. A `start` without a `when` is the action's due time. delete_action with action fields is refused (offers delete_action alone or update_action).
- A delete `start` must name an occurrence within a week of it (the nearest three are offered); a non-repeating event whose own start matches is deleted whole with a note.

## Time zones

Events store no zone of their own (recurring events anchor in the server zone; a per-event zone would change the persisted format). The unadvertised `timezone` (or Google `timeZone`) is read against the server zone through `core/tools/_named_zones.py` and executed when the reading is exact:

- the server zone (by key, or a difference of zero all year; `_named_zones` reads the difference now and just after every exact offset change of either zone over the coming year): dropped;
- list/find_free windows: read in that zone, with a note naming the server-time window;
- a single event's start/end: converted to the server-local instant, with a note naming both times. A local time the zone skips or repeats is refused with one call per instant, each written with that zone's offset and keeping `timezone`, so the other time field still reads in that zone;
- a repeating event: its occurrences keep the written wall-clock time in the server zone (gap shifted forward, repeated hour first), so it is converted only when the difference to the server zone is constant all year and the date stays the same; the written wall time is shifted, so a first occurrence in a gap keeps its wall time on later dates. Otherwise refused with every time field as the server wall time at the first occurrence, `timezone` omitted, and the reason;
- an aware value whose offset is not one that zone has at that local time: refused with the time as written and each reading in that zone, all in that zone's offset and keeping `timezone`; each time in its own zone (two different `timeZone`s): executed as exact instants;
- an unknown zone: refused with the call without it. A clock-time action `when` is read in the named zone (a skipped or repeated time is refused with each instant) and converted to the relative form for single events.

## Constraints & Gotchas

- Error codes: `invalid_arguments` (every refusal above), `event_not_found`/`action_not_found` (point to `{"action":"list"}` and a later `when`), `calendar_storage_error` and `calendar_service_error` ("Do not repeat the same call unchanged"). `action_target_missing`: an `update` that would let an action that no longer fires run again although its Agent, Project or selected Session no longer exists names each such action and what is missing, and points to update_action or delete_action before repeating the update (`test_update_refuses_to_revive_an_action_whose_session_is_gone`). Target validation keeps the service reason plus target guidance; a malformed `target` address is a `CalendarValidationError` (`target does not identify an agent (...)`) from `core/calendar/actions.py`. A date or clock time that names no real day or time (`2030-02-30`, `25:99`) counts as no date or time (`parse_date`, `parse_time_of_day` in `_calendar_arguments.py`), so it is refused with the same calls as other unreadable values instead of escaping as an execution error (`TestImpossibleValues` in `test_calendar_call_tolerance.py`).
- Absent and explicit-null arguments differ: omitted `rrule` on create is a single event; on update omission keeps the rule and null clears it.
- `add_exdate` does not verify that the value is an occurrence; the Tool verifies it before calling (`_occurrence_start`), other accessors use the UI's server-provided `occurrence_start`.
- The Tool cannot invite attendees, keep reminders, select another calendar or hold a per-event zone; these are refused or recorded in notes rather than approximated.

## Agent-facing text

Reasons for the `max_delay` parameter description and the late-start System Reminder (`late_notice`, `core/calendar/actions.py`). The definition grew from 597 to 732 estimated tokens (`python -m scripts.tool_lab definitions`).

| Text | Reason |
|---|---|
| `How late an action that vBot missed, for example while the server was off, can still start:` | Without the situation, Agents read the field as a Run timeout or a start offset. |
| `a duration such as '30m' or '2h'; '0m' skips every missed start.` | Names the accepted form and the only way to say "never start late"; Models otherwise send seconds or `false`. |
| `Without it, an action due before its event can start until the event starts, one due during it until it ends, and one due after it until its next occurrence, or however late after the last;` | States the default, so Agents do not set a limit to keep a preparation from arriving after the meeting (user decision 2026-10-08). |
| `max_delay only shortens this.` | Prevents the false belief that a long `max_delay` lets a preparation start after its event. |
| `Set it only when the user asks for it or a late Run would be useless.` | Weak Models fill every optional field; a needless limit drops the Run the user expects after downtime. |
| `On update_action, 'unlimited' removes the limit.` | The schema has no null; without it Agents cannot clear a limit. |
| `Calendar action <id> was due at <due> and is starting late, at <start>.` | Names the action and both times so the Run knows it is late and by how much. |
| `vBot did not run it at the due time, for example because the server was off or the computer was asleep.` | Gives the cause, so the Agent does not report a fault or retry. |
| `Carry out the instruction that follows now, and adapt any part of it that depends on when it runs, such as the time left before the event or how long ago it ended.` | Without it Agents either refuse the stale task or announce "the meeting starts in 15 minutes" when it starts in 2. |
