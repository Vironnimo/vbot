# Calendar Tool

Manages the local calendar through `CalendarService`: events and their occurrences, and free-time search. It runs nothing itself; an instruction at an event is a cron job (`tools/cron.md`, `automation.md` -> Event jobs).

## Interfaces

- Tool name: `calendar`
- Source: `core/tools/calendar.py` (registration, dispatch, attendee and reminder refusals), `_calendar_read.py` (detached reads and rendering) `core/tools/_calendar_arguments.py` (call reading before validation), and `core/tools/_calendar_pages.py` (bounded text and stateless continuation), with `_durations.duration_minutes` and `_named_zones.named_zone` shared with the cron Tool. The reminder refusal renders its cron call with `_cron_arguments.render_call`.
- Registration: `register_calendar_tool(registry, calendar_service, *, reference_lock, cron_service=None)`. Runtime passes its `CronService`, so results name the cron jobs bound to each event; without it they name none. It registers the Tool-owned `argument_normalizer` and four unadvertised parameters only the normalizer produces: `when` (a window phrase), `reminder` (a requested reminder the handler refuses) `attendees` (the names of requested attendees, which the handler refuses), and `original_start` (validated occurrence selector resolved in the stored event zone before mutation). The schema is model-facing (`open_input_schema=True`, no `additionalProperties`), so its root properties are still the complete parameter list (`tools.md`).
- Schema (user decision 2026-10-08: the shapes Models know from Google Calendar v3 and the Google Calendar MCP servers): one flat object requiring `action` (`list`, `get`, `search`, `create`, `update`, `delete`, `find_free_time`) with `id`, `title`, `start`, `end`, `description`, `location`, `rrule` (a string), `time_min`, `time_max`, `query`, `duration` (integer minutes, default 60), and `cursor`. The handler requires `title` + `start` for create, `id` plus a changed field for update, `id` for get and delete. `timezone` selects a named timed-event zone. `_calendar_read.py` owns detached read rendering, `_calendar_pages.py` lossless continuations.
- update and delete hold the Agent reference lock (`AutomationReferences.lock`, passed as `reference_lock`) like the calendar RPCs, so an event change cannot revive a cron job bound to the event between a removal's reference check and the removal (`test_changes_wait_for_the_reference_lock`).
- Display: the summary leads with the normalized `action`, followed by the first available `title`, `id`, `query`, `time_min` or `when`; persisted calls keep the Model's spelling and are normalized for the label. Calls persisted with the removed actions still render: `add_action` reads as update with a reminder, `update_action` and the other removed actions get no label (`test_display_labels_the_meant_action`). Read counts derive from `occurrences` (list) or `events` (search). Description and parameter changes are announced to existing Sessions.
- Coverage: `tests/core/tools/test_calendar.py` (canonical calls, results, errors) and `tests/core/tools/test_calendar_call_tolerance.py` (accepted dialects, reminder refusals, calls with different readings), through production dispatch against a real `CalendarService` bound to a real `CronService` (`tests/core/tools/scheduling_tool_support.py`, which offers both Tools unless a test drops cron). `scripts/tool_lab/cases/automation.json` holds the probe cases; the probe shares one calendar across a file's cases, so each calendar case uses its own dates and titles. `scripts/provider_probe/scenario_automation.py` holds the canonical calls a Provider must reproduce.

## Conventions

- New timed events default to the application zone; updates default to the stored event zone. `timezone` selects an IANA zone; changing it keeps local clocks. An occurrence keeps its series zone. Explicit offsets name exact instants. The start form decides the event kind: a date makes an all-day event, a local date-time a timed one. `end` is exclusive (an all-day event ending on the 12th has the 13th as `end`); an all-day end on the start day means that one day. Create without `end` gives 1 hour or 1 day; update without `end` keeps the event's length (`CalendarService.update_event`), also for an occurrence.
- `id` is an event id or an occurrence id `<event id>_YYYYMMDD[THHMM]` (`calendar.md`). With an occurrence id, update changes and delete removes only that occurrence; an `rrule` there is refused with the series id. `get` reads exactly that id; an occurrence id never widens to its series. `list(id)` without bounds repairs to get; with bounds it filters those occurrences. `search` scans stored events across all dates, once per event; it finds text in the base event or any changed occurrence and exposes matching occurrence ids. Search plus bounds repairs to list.
- On update, an explicit `""` for `description` or `location` clears that field; an omitted field keeps its value. This also holds when the action is inferred from the id and changes.
- `rrule` is RFC 5545 RRULE text; `""` on update stops the repetition, on create it is dropped. The service validates the rule.
- Windows are half-open: `time_min` defaults to now (to the minute), `time_max` to 30 days later for list and 7 days for find_free_time, on the local wall clock. A bound is a date (local midnight) or a date-time (local unless it carries an offset). Explicit windows have no span cap (user decision 2026-10-30). The unadvertised `when` phrase (`today`, `this week`, `next month`, `2030-01`, `a..b`; `core/calendar/when.py`) sets the whole window and is refused next to `time_min`/`time_max`.
- Read pages (`list`, `get`, `search`, `find_free_time`): at most 30,000 Model-visible characters including metadata and the next call; `complete` says whether the query is exhausted. `next_cursor` and a ready-to-send call continue with only `action` and `cursor`. The opaque cursor retains resolved bounds, filters, clock, record position and text offset. Calendar, timezone or bound-job changes refuse continuation and request a fresh query; repeated equivalent bounds/filters remain accepted. Oversized records split losslessly. `occurrences`, `events` and `free` count records on this page, including a continued record fragment; no total is computed. Expansion uses lazy occurrence streams, not bulk expansion followed by slicing. Malformed positions/offsets refuse rather than skip content.
- `query` matches case-insensitively in title, description and location of each occurrence. `duration` on find_free_time is the minimum free span; each span shown is the whole gap (`CalendarService.find_free_slots`, paged by output size; a note says when none was found). find_free_time ignores cron jobs.
- Results render timed values with their actual UTC offset and event IANA `timezone`; window bounds and free spans use the application zone, explicitly named. All-day values stay dates with an exclusive end and last-day annotation. No result carries `retryable`.
- `list` returns chronological concrete occurrences with `id`, `series` for repeating instances, effective title/start/end/location/description, zone and bound `cron_jobs`; no group expansion or per-field abbreviation. Its header names `window` and `window_timezone`, not an event zone. `get(event)` returns full event fields, rule, next three occurrence ids/times, and changed/removed occurrence ids; `get(occurrence)` returns only that instance. `search` returns full event records with the same next preview and matching override ids. Reads place records in `content` and explicitly mark `complete`.
- Create/update return the changed event or occurrence with complete fields and the event's next preview. `cron_jobs` names each bound job, its schedule, target and inactive status. Delete returns id/title/status and deleted bound jobs; occurrence deletion says the rest of the series stays and shows its next instances. Free search returns whole gaps, `free`, `window`, `timezone`, and a no-match note where needed.

## Argument reading

`_calendar_arguments.normalize_calendar_arguments` runs before schema validation and executes a call whose intent is clear; when readings differ it raises a contract error (an `invalid_arguments` failure) before any change. Every refusal starts with `calendar was not run:` and ends with the corrected call (`Send: {...}`) or one call per reading. Stand-ins in angle brackets (`<title>`, `<event id from list>`) mark values only the Agent can supply; are omitted only in selector/time fields. Payloads (`title`, `description`, `location`, `query`) are literal, including `TBD`, `none` and `???`. An empty/null query is omitted. Descriptions longer than 120 characters show as `<the description from this call>` in corrected calls.

- Accepted silently (user decision 2026-10-08): `summary`/`name`/`subject` -> title, `notes`/`details`/`body` -> description, `event_id`/`eventId` -> id, `timeMin`/`timeMax`/`from`/`to` -> time_min/time_max, `when` phrases -> window, `q`/`search` -> query, `recurrence`, an `RRULE:` prefix, a one-rule list or an old rule object (`{"freq":"weekly","by_weekday":["mo"]}`) -> rrule, Google `{date|dateTime, timeZone}` start/end, an `event`/`requestBody` wrapper, `duration`/`"1.5h"` on create or update with a start -> end (wall-clock; on an all-day start only whole days), `find_free`/`freebusy` and other action synonyms, `original_start`/`originalStartTime` with the series id -> the occurrence id (invalid, conflicting and fractional-second selectors refuse before mutation; offsets are resolved in the stored event zone and seconds preserved). Also dropped without effect: inert Google keys (`calendarId` naming the default calendar, `sendUpdates`, `colorId`, ...). `limit`, `maxResults` and `orderBy` reach shared unknown-field handling. Cancelled status, transparency and default-reminder requests are refused before effects; confirmed status and opaque transparency are harmless accepted defaults. On list, a `title` becomes `query` and `start`/`end` the window; fields an action does not use are dropped.
- Google `timeZone` and top-level `timeZone`/`timezone` preserve a named event zone, so weekly clocks survive differing DST transition dates. Window-only zones resolve bound instants then disappear. Contradictory zones refuse. Equivalent end spellings compare parsed times, not raw strings.
- Reminders: `reminders` with overrides, `minutes_before`-style keys, `prompt`/`instruction` and the `add_reminder`/`add_action` actions become the unadvertised `reminder`, which the handler refuses: `calendar was not run: the calendar has no reminders.`, then, when cron is offered (`ToolContext.offers("cron")`), `cron runs an instruction before, at or after an event.`, the event call without the reminder (`Send:`), and the cron create call (`Then send to cron:` with the event id, `<event id from the result>` on create, for an occurrence it offers a one-time job and explicitly warns that an event-bound job covers the whole series, without a broader ready call; the reminder's minutes as `start - <n>m`, else a stand-in). The event is not created in the same call (open point: one extra round trip).
- Attendees (`attendees`, `guests`, `invitees`, `participants`; a list, one entry or a JSON text of either, entries as names, emails or Google attendee objects) become the unadvertised `attendees` on create and update and are dropped on the other actions. The handler refuses them before any change and offers them as an `Attendees: ...` description line: on create, and on update when the call sends a description, the line joins the description sent; otherwise it joins the stored description of the event or occurrence, so the corrected update keeps that text. When no call can carry it (update without `id`, or a result longer than 120 characters), the refusal names the step and the get call that shows the description instead of a call. An unknown `id` gets the `event_not_found` error. Corrected calls of other refusals keep `attendees`, so they are not dropped silently.
- Refused with calls: another calendar, several rules, a `duration` without a start or minutes on an all-day start (`send end instead`), an `end` and `duration` that disagree, create with an `id` (offers update or create without it), delete with changes (offers delete or update), the window given twice, and a reversed window. Remaining unknown parameters follow the shared dispatch rule (`tools.md` -> Unknown fields); a refusal lists the parameters.
- Removed with the redesign: title lookup of an event id (the refusal names global search with `query`), bare clock-time ends, rule phrases (`weekly`) and top-level frequency parts, the DST refusals for repeating events in other zones, and the late-start note.

## Constraints & Gotchas

- Tool reads require successful calendar loading: unavailable storage never becomes an empty list or free-time result. Contradictory zone aliases refuse before effects; unknown window fields reach shared argument validation.
- Error codes: `invalid_arguments` (every refusal above and the service's validation errors, with the field's stand-in when the call sent it; a `start`, `end`, `time_min` or `time_max` that is neither a date nor a date-time is refused by the handler with the value received, `<field> "<value>" is not a date or local date-time.`), `event_not_found` (`calendar was not run: no event has id "<id>"; {"action":"search"} shows events and their ids.`; an unknown occurrence of a stored event names get with the series id, one of an unknown event global search), `calendar_storage_error` (no path or operating system text: a change says `Nothing was changed`, since the service rolls a failed save back and replaces the file atomically, and both kinds tell the Agent that retrying will not help and to tell the user), `calendar_service_error` (the service's text; a change names get, or global search after create, to inspect whether anything changed), and `cron_storage_error` when an event was deleted but the cron jobs bound to it could not be (the event stays deleted, the jobs no longer run; `test_a_deleted_event_whose_cron_jobs_cannot_be_deleted_says_so`).
- The Tool cannot invite attendees, keep reminders, select another calendar or create transparent/cancelled events; these are refused or recorded in the description rather than approximated.
- A series update whose exceptions collide is `invalid_arguments`: the service's refusal names both original occurrence keys and their common target, says nothing changed, and asks for a `start` or `rrule` that keeps them distinct (`calendar.md` -> Interfaces). The calendar file, live event and change notifications stay untouched (`test_series_change_refuses_colliding_exceptions`).
- Tests whose calls or expected results depend on the current time fix the Tool's clock by patching `core.tools.calendar.datetime` with `clock_at` (`tests/core/tools/scheduling_tool_support.py`); dates hard-coded against the real clock break when the month rolls over.

## Agent-facing text

Shared reason for every row (user decision 2026-10-08): minimal, trained shapes; calendar API conventions from Google Calendar v3 / Google Calendar MCP servers. The description and location parameter texts state how to clear a stored value; their names explain the fields themselves.

| Text | Reason |
|---|---|
| Description: `Manage events in vBot's local calendar and find free time.` | Names the two jobs and local ownership; prevents assuming connected external calendars. |
| action: `list shows occurrences in a time window; search finds stored events across all dates; get reads one exact id.` | Separates agenda browsing, global discovery and exact inspection; the independent reviews found list was overloaded and occurrence ids widened to series. |
| action: `update changes only the fields you send.` | Patch semantics as in Google `events.patch`; without it Models resend every field or fear clearing them. |
| id: `Event or occurrence id from list or search.` | Gives both discovery paths without inventing ids or forcing a time window. |
| id: `An event id targets the whole series; an occurrence id targets only that occurrence.` | Makes read and mutation identity consistent; prevents broadening one-instance intent. |
| id: `Required for get, update and delete.` | The one rule the schema cannot express per action. |
| title: `Required for create.` | Same. |
| description/location: `On update, "" clears the description.` / `On update, "" clears the location.` | Distinguishes clearing a value from omitting it. |
| start: `Local date-time such as 2030-01-10T15:00, or a date such as 2030-01-10 for an all-day event.` | One example per form; the form decides the event kind, so no `all_day` flag is needed. The timezone parameter defines the local zone. |
| start: `Required for create.` | Per-action requirement. |
| end: `Same form as start, exclusive: for an all-day event the day after the last day.` | Google/iCal convention Models know; stating it prevents the classic off-by-one, and results show the last day. |
| end: `Omit on create for 1 hour or 1 day; on update to keep the length.` | Distinguishes new-event defaults from preserving an existing duration. |
| rrule: `RFC 5545 rule such as FREQ=WEEKLY;BYDAY=MO,WE.` | The rule text every calendar API uses, one example with BYDAY. |
| rrule: `On update, "" stops repeating.` | The only way to remove a rule; a string field cannot be null. |
| time_min: `Start of the window for list and find_free_time: a date or local date-time.` | Google `timeMin` name and role. |
| time_min: `Omit to start now.` | The default. |
| time_max: `End of the window, exclusive.` | Half-open window as in Google `timeMax`. |
| time_max: `Omit for 30 days after time_min, or 7 days for find_free_time.` | The defaults per action. |
| query: `For search or list: text to find in title, description and location, ignoring case.` | Names both supported scopes and literal matching rather than regex or semantic search. |
| query: `Omit for all results.` | Enables discovering all stored events without constructing a dummy query. |
| duration: `Minimum free time in minutes for find_free_time.` | Unit and action; the default 60 is in the schema. |
| Collision refusal: `Nothing was changed.` | States that the whole update was refused, including other fields sent with it. |
| Collision refusal: `Exceptions for ... would both apply to ...` | Names the original occurrences and their conflicting target so the Agent can explain why the requested series change would lose an exception (MO/TU reproduction, user decision 2026-10-23). |
| Collision refusal: `Choose a start or rrule that keeps these occurrences distinct.` | Offers a valid next step without choosing which exception to discard or suggesting a destructive retry. |
| cursor: `For reads: continuation from next_cursor.` | All four reads can exceed the output budget; continuation needs no manual date arithmetic. |
| cursor: `Omit for the first page; to continue, send only action and cursor.` | Retains resolved defaults and filters without Agent reconstruction; avoids gaps when time advances. |
| Result: `More results follow. Continue with ...` | Names an executable continuation; `complete` distinguishes a partial page from exhausted results. |
| Cursor refusals: `cursor is invalid` / `the calendar, its time zone or its bound jobs changed` / `cursor already retains` | Prevents silently using malformed, stale or contradictory continuation state; tells the Agent to restart or use only action/cursor. |
| Oversized continuation: `Use a shorter query.` | A continuation containing a pathological query can itself exceed the output budget; no data is silently discarded. |
| Occurrence selector refusals: `original_start ...` / `id and original_start name different occurrences.` | A malformed or contradictory explicit target must never widen update/delete to the whole series. |
| Zone refusal: `time zones disagree; send one time zone.` | Refuses conflicting aliases rather than picking the first zone silently. |
| Reminder recovery: `Use a one-time cron job for this occurrence; an event-bound job would cover the whole series.` | Keeps a one-occurrence request from becoming a series-wide reminder. |
| timezone: `IANA zone for timed create/update, such as America/New_York.` | Named recurrence clocks must survive different DST dates; fixed-offset conversion lost that meaning in the reviewed Tool. |
| timezone: `Omit on create for the application zone; on update to keep the stored zone.` | Prevents changing old events when application settings change. |
| timezone: `Changing it keeps local clock times.` | Defines the choice the Agent makes: retime the event in a new zone. |
| timezone: `An occurrence keeps its series zone.` | Prevents attempting an independent instance zone and widening the operation to its parent. |
| Unsupported-effect refusals: `status=cancelled`, `transparency=transparent`, `default reminders` | Prevents successful calls that silently create blocking events or omit requested reminders. |
