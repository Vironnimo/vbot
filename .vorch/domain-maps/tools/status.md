# Status Tool

Reports current or targeted agent/session/runtime status through the same status builder used by chat commands.

## Interfaces

- Tool name: `status`
- Registration: `register_status_tool(registry, agent_resolver, sessions, models, chat_runs, started_at, providers=None, projects=None, context_window_resolver=None, reasoning_render_describer=None, timezone_name_loader=None)` - resolves the target agent through the run-path `AgentResolver` seam (so a project session reports the resolved config agent), and uses the optional `ProjectStore` to label the session's project.
- The model-facing schema is one flat object with optional `session_id` and `agent_id` (no `minLength`), `required: []`, and no `additionalProperties` keyword. Descriptions explain all three targeting forms; unknown arguments follow the shared rule (`tools.md` -> Unknown fields); the handler rejects malformed ones and requires `session_id` when selecting another Agent.
- Targeting rules:
  - No arguments checks the calling Agent's current Tool Context Session.
  - `session_id` checks that Session for the calling Agent.
  - `agent_id` plus `session_id` checks that exact Agent/Session pair.
  - Before validation (`_normalize_status_arguments`), known `current` action/wrapper forms, call-field formatting, and the `session`/`session_key` and `agent`/`agent_name` spellings are repaired. Placeholder values (blank, punctuation-only, `null`, `unused`, ...; for `session_id` also `current`, `this`, `active`, `mine`) count as omitted; other identifiers stay exact. An `id` field is read by its value: a `ses_` id becomes `session_id` (a different explicit `session_id` conflicts), and any other value that is not a task id refuses naming the valid fields, as does such a value in `work_id` or `subagent_id`. A Sub-Agent (`sub_`) or background command (`cmd_`) id, sent as `id`, `work_id`, `subagent_id` or `session_id`, or as `agent_id` in the generated form (the prefix plus 12-16 lowercase letters and digits, so an Agent named such as `sub_reviewer` stays an Agent), is refused before any lookup (unadvertised `task_id_sent`, set only by the normalizer), naming the `background_tasks` status call for it only when the Agent can call `background_tasks` (`test_status_tool_refuses_unclear_ids_before_lookup`). Repeating the calling Agent without a Session uses the current Session. Unsupported actions and another Agent without a Session fail without lookup; the latter names the call with both ids.
- Success data contains the status text built from Agent, Session, project, model, runtime, run activity state, context usage, and cache usage, plus machine-readable `agent_id` and `session_id`. All report content, including run activity and cache details, is text-only: the tool does not add machine-readable activity or cache fields.
- The status text carries a `Project:` line: `<display name> (<id>)` for a project session, the placeholder for an identity session (and the bare id when the project can't be loaded). Resolved by the shared `resolve_status_project_label(projects, project_id)` helper, so the `/status` command and the tool agree.
- The status text carries `Last request cache:` and `Session cache:` lines. They render provider-reported cache read/write tokens and hit rate only when cache fields are present on assistant usage whose input was measured (an estimated output alone does not exclude a turn); otherwise they render the placeholder, so providers without cache reporting do not look like a 0% hit.
- The status text renders activity as `running` or `idle`; unknown/missing Agent or Session targets return failure envelopes.
- Display: no summary. A status call must render as `status`, not `status ({})`.
- The `Context usage:` line is the Session's Context projection, the value `chat.history` returns (`status_session_facts_from_snapshot` -> `latest_session_context_usage`), as `<tokens> / <window>`: the window the projection records, else the Context capacity a Run of the Agent budgets against (`context_window_resolver`, an async callable wired to `ChatLoop.context_capacity`; `chat/usage.md`): a window the Provider reported for the route, else the route's effective window, capped by the Provider's input limit, so the line never shows the full window where a Run budgets against less. A Session without a projection renders the placeholder; token counters alone are never shown as Context.
- Both surfaces consume the Sessions-owned `status_snapshot`: SQL supplies Session start, User-turn count, latest Assistant Usage, whole-Session Usage/cache aggregates, the Context projection inputs, and no complete transcript. The Agent-callable Tool's handler is async: the target lookup and the report run on the cancellation-safe Tool worker (`run_tool_worker`), the Context capacity is awaited between them; `/status` uses the command worker path the same way.

## Constraints & Gotchas

- The `/status` command and status tool share the same status text builder. `/status` always reports the current Session; the tool may target another Session.
- Active Run timestamps render in the status text; an idle Session renders placeholders.
- Times render in the configured application zone (`timezone_name_loader`, wired to `Runtime.timezone_name`) and name it (`%Z`). When that zone cannot be loaded (an invalid persisted `settings.timezone` raises `SettingsValidationError`), the report falls back to UTC with a warning log instead of failing, like `session_search` (`test_status.py::test_status_times_name_the_configured_zone_or_utc`).
- Expected target lookup problems are represented as tool failure envelopes (`agent_not_found`, `project_not_found`, `agent_unavailable`, `session_not_found`, or `invalid_arguments`) instead of an `unknown` status. Only a missing Agent or Project reports a not-found code; an Agent that exists but cannot run (for example, no usable Model) reports `agent_unavailable` (`retryable: false`) with the resolver's reason and tells the Agent to report it to the user. `session_not_found` suggests omitting `session_id` only when one was sent, and adds the owner hint (pass that Agent's `agent_id`) only when `agent_id` was omitted.
- `status` reports a chat Session; it does not track Sub-Agent work or background commands. Their progress belongs to `background_tasks` with `action: "status"` (`tools/shell.md`); `subagent` results carry the child `agent_id`/`session_id` that this Tool accepts.
