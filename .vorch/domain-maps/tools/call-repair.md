# Tool Call Reading

How dispatch reads a Tool call before its handler runs: called-name resolution and unknown-Tool errors, shared argument repair and quote repair of JSON text, unknown-field mechanics, validation messages, the owner call-syntax toolkit, and private file replay in `tool_lab`. The contracts these mechanics serve (Agent error tolerance, failure codes, the unknown-field rule) live in `tools.md` -> Contracts; why each shared message is worded as it is: `tools/agent-facing-text.md`.

## Called Tool names

Models also call Tools by names from other harnesses or with a namespace prefix. Before Chat persists an Assistant turn, `called_tool_name` (`model_names.py`) maps each Call whose name is neither offered in that request (listed, or available in the prompt epoch without being listed: an announced addition or an On-demand Tool the Model knows by name only, so `KillShell` reaches `background_tasks` before it is loaded) nor registered (a Tool announced as removed counts as registered) to the offered Tool it clearly means. Tool-call markup leaked after the name (`<` or `</` followed by `|`, a full-width bar or a letter, such as DeepSeek's `board_placeholder</...DSML... parameter>`) is cut off first; the rest is resolved like any called name and, unresolved, is the name the Call keeps (Swarm Sessions, 2026-10-12). Then namespace prefixes (`functions.`, `default_api:`, ...), case and separators are ignored (`Read`, `WebFetch`), and a fixed table maps other harnesses' names for the same capability to the first offered of its targets (`Edit`/`MultiEdit`/`str_replace` -> `edit`, else `apply_patch`; `Write`/`create_file` -> `write`, else `apply_patch`; `patch`/`apply_diff` -> `apply_patch`; `Grep`/`Glob`/`ls` -> `search_files`, `Task` -> `subagent`, `shell`/`run_shell_command` -> the shell Tool, ...). A name outside that table maps to the one offered Tool whose registry or Model spelling (at least 5 characters without separators) it misses by one inserted, removed, replaced or swapped character (`powerhell` -> the shell Tool on Windows); two such Tools leave it unresolved. The Tool name selects the operation, not a target, so this does not relax the rule against guessed targets. The target's own argument handling then decides whether the Call runs. History, Run events and dispatch all carry the resolved name, so the next request replays the Call under the name the Model should use. A spelling shared by two offered Tools stays unresolved even when the fixed harness-name table has a target; a target not offered also stays unresolved.

An unresolved name fails `tool_not_found` with `Unknown Tool: <name>. Call one of the available Tools instead: <names>.`, listing the ready, non-deferred Tools the caller may use under their Model names (loadable On-demand Tools and listed internal Tools included, `tools/load_tools.md`; with none: `Unknown Tool: <name>. No Tools are available in this Run.`). When the Call's arguments fit exactly one of those Tools (every field one of its parameters, its required ones present, the value of a parameter with fixed values such as `action` one of them; `_arguments_fit` in `tools.py`), the message names that Tool instead of the list: `Unknown Tool: pash. These arguments fit powershell; call powershell with them.` It never runs that Tool, because the name did not say which Tool was meant. Otherwise a Call that shows damage from a Provider's parser splitting the Model's tool-call markup wrongly is asked for again complete instead of being sent to the list: one that arrived with no arguments at all (`Unknown Tool: <name>. Nothing was run: the call arrived with no arguments at all. If you sent some, the call was garbled on the way: send the complete call again.`), or with `<`, `>`, `=` or `"` in its name or an argument name (`... the call arrived with tool-call markup in the argument name "parameter=command", so it was garbled on the way. Send the complete call again.`). It ends with `The closest available Tool is <name>.` when one Model name clearly resembles the called one (difflib ratio of the separator-free spellings at least 0.5 and 0.1 ahead of the next; markup and what follows it in the name are ignored; `_closest_tool_name`), else `Available Tools: <names>.`; that Tool is never run either. The evidence behind these messages: `tools/agent-facing-text.md`.

Coverage: `test_model_names.py`, `test_tools_execution.py`, `test_chat_loop_tool_definitions.py` (`test_tool_called_by_another_harness_name_runs_and_is_stored_under_its_name`, listed and On-demand).

`computer_action` is a fixed alias for an offered `computer`, never for its batch or app companions (observed retry with identical arguments, Sessions 2026-10-19). An actual registered Tool wins over aliases after namespace and `()` removal as well, so a prefixed call to a registered but unavailable Tool still reaches that Tool's dispatch refusal.

## Shared argument repair

`ToolContract.normalize_arguments` (`contracts.py`, implemented in `_argument_repair.py`) normalizes copied schema-guided value encodings: numeric counts without rounding, boolean aliases, JSON containers, and scalar arrays. Accepted text and arbitrary object keys remain unchanged. Generic repair does not rename fields, rewrite enums, unwrap business objects, or omit explicit empty/null values. Conflicting duplicate encoded JSON keys and multiple valid conversion meanings fail rather than selecting a value by branch order. Shared normalization always leaves meaningful operation validation in place. Verify equivalent calls and plausible different calls against independently specified receiving arguments and effects, not an expectation derived from the same repair code.

One call shape is read before the owner's `argument_normalizer`, for every Tool with `coerce_arguments`: a call sent as one name/value pair is the parameter it names (`ToolContract.read_name_value_pair`, called by `_checked_arguments`), so `{"name": "command", "value": "ls"}` reaches the owner as `{"command": "ls"}` and the owner's repairs apply to the value. It applies only when neither `name` nor `value` is a parameter of the Tool (advertised or unadvertised), `name` is exactly a parameter the Model request offered, and every other field is another parameter or repeats this one with the same value; anything else stays as sent and is refused for its unknown fields. Silent, as a representation repair. Evidence, the 2026-10-12 Swarm run: one `powershell` command arrived as such a pair and ran in the regular field right after; no other call in the Session database had the shape. Coverage: `test_contracts.py::test_a_call_sent_as_one_name_value_pair_runs_as_that_parameter`.

A Tool may register a pure `argument_normalizer` for domain-specific repairs that must precede required-field validation. Dispatch invokes it on a deep copy after access/readiness checks, then applies the cycle's exact canonical contract normally. It changes no Provider schema or authorization policy.

Public and private Session Tools use dispatch normalization. The production Swarm probe checks independently prescribed calls, real registry results, and durable receipts.

## Quote repair of JSON text

An array or object argument sent as JSON text that does not decode is read once more (`_argument_repair.py::_repaired_json_text`; some Providers pass an argument they could not decode on as text): a raw line break, tab or other control character inside a string stands for itself, and the stray `"` inside the text of the schema's declared fields are escaped (`core/utils/json_text.py::escape_inner_quotes`). A single string that writes line breaks both raw and as `\n`/`\r` escapes gets no reading: a raw one there can be a slip of the output (Swarm 2026-10-12: one raw break inside a word among 27 escaped ones). Different strings in the same object or array can use different representations; `_has_mixed_line_breaks` checks each string, respecting escaped quotes and backslashes (Swarm 2026-10-14: an edit batch used raw line breaks in one new text and escaped breaks in another).

Inside such a field's string, a `"` ends the text only where `}` or `]` follows, a `:` before a value (`"`, `{`, `[`, a number, `true`, `false`, `null`), a comma before a string, object or array, a comma before a declared field name that lost its opening quote, or the end of the text; every other `"` belongs to the text, since read as structure it would leave text where JSON needs a value (`got "x": not a number`). Closing brackets (`]`, `}`) after the end of a complete value close nothing it opened and are left out (Swarm 2026-10-13: an `edits` array followed by one `}`); any other text there, such as `, {...}`, keeps the text refused, since it can be a value meant to run.

The text is read with and without its quotes escaped; the value counts only when exactly one distinct reading is valid for the field's schema and every object in it uses only declared fields (an object schema with `properties` and no `additionalProperties`/`patternProperties` counts as closed); a repeated field or an ambiguous conversion also discards it. Otherwise the original text goes on to validation unchanged; `decode_json_argument` then raises the first break past the raw control characters (a cut-off text reports its end, not an earlier raw line break), else the strict decoding error. Schemas without declared field names (string arrays such as `search_files` `patterns`) are never repaired. Silent, as a representation repair. Owner field normalizers reach the same reading through `decode_json_argument(text, schema)` (edit's `edits`, `tools/edit.md`).

Replay 2026-10-11 over all 249 live calls with JSON-looking text in a field: 5 decoded differently than before, all `edits`, each identical to the reviewed manual reading; the rest unchanged. Replay 2026-10-12 over the 18 live `edit` calls with JSON-looking `edits` text, for the raw control characters and the `:` rule: 1 more decoded (raw line breaks and a `"` before `:` and text; 3 edits, checked against the reviewed reading), the rest unchanged; no other live array or object argument failed strict decoding where these rules apply. Coverage: `test_contracts.py::test_slips_in_json_text_are_read_only_into_a_value_the_schema_accepts`.

## Unknown fields

The rule (`tools.md` -> Contracts -> Unknown fields) applies to a root field that is not a parameter (nor an `unadvertised_parameters` entry) of a Tool with a closed parameter list; vBot has no per-call read-only marker, and action Tools mix reads and changes. Shared normalization drops an undeclared root argument whose value is null, `""`, `[]` or `{}` (it requests nothing). `commentary` (a label some Models attach to the channel of their output) is dropped silently. Any other unknown field is dropped before the handler (`ToolContract.drop_inert_fields`, called by `_checked_arguments` in `tools.py`), and the result says so, unless ignoring it could give an effect the Agent did not ask for. It stays, and validation refuses the call before any effect, when its name is close to a parameter (contains one or is a typo of one: the "Did you mean" suggestion), when it is a parameter of the Tool that this Model request's definition left out (`withheld`), when a word of its name reads as a mode, condition or safety switch (`dryRun`, `mode`, `force`, `if_exists`), as a target (`thread_id`, `path`, `to`) or as content (`message`, `body`, `patch`) (`_DECISIVE_WORDS`), or when its value is content or call fields rather than a label: an object, or text with a line break or longer than 80 characters. A refused call names every unknown field, the dropped ones included.

The dropped names reach the Agent as `ignored_fields_note`: `"transition" had no effect: swarm_board has no such parameter.` A success carries it first in `data.note` (`with_call_note` in `_tool_results.py`, before an existing string note), a failure envelope and a handler's `ToolContractError` end their message with it. Because `note` is reserved, `validate_success_data` checks a result against a schema that does not declare `note` without it, so closed result schemas (`load_tools`, `analyze_image`) admit it. Extension Tools get the note through the same dispatch, rendered as a `note:` line of the result.

Evidence, the 2026-10-12 Swarm run: 21 calls were refused for unknown fields, among them complete swarm_board posts with `transition: "support wiring"` (x3) and `commentary: "analysis"`, which now run; the rule keeps refusing a post whose text came as multi-line `retext`, `action` on apply_patch, `path` on swarm_wiki and the `*_id` references. Coverage: `test_contracts.py::test_dispatch_rejects_invalid_arguments_before_handler`, `::test_an_unknown_field_without_effect_is_left_out_and_the_result_says_so`, `::test_a_parameter_the_model_request_left_out_is_never_ignored`; Extension Tools in `test_capabilities.py` and `test_examples.py`.

## Validation messages

A validation failure reports every problem at once in Agent-readable sentences (`<tool> was not run: ...`; at most six, then `...and N more.`): the field, the expectation, the received value, for a missing parameter its valid values when it has an `enum` (a first sentence that describes the values one by one ends mid-list), else the first sentence of its description, a suggested parameter for an unknown name (never applied), and the parameter list whenever a name was missing or unknown. A call that arrived as exactly `{}` and is refused, by the owner's repair or by validation, lost its arguments on the way (mostly Tool-call markup a Provider could not read), so it gets `ToolContract.no_arguments_message()` instead: `<tool> was not run: the call arrived with no arguments at all. Send the complete call again.` plus the parameter list. A call the owner's repair emptied did send arguments and keeps the ordinary message. Coverage: `test_contracts.py::test_a_call_that_arrived_without_arguments_is_asked_for_again_complete`.

## Owner-selected call repair

`call_syntax.py` is the public call-syntax toolkit for every Tool owner outside the registry as well (Extensions, the Live Tools, Subagent interpretation): `spelling`, `SpellingAliases`, `PLACEHOLDER_WORDS`/`is_placeholder`, and `normalize_call_arguments`. `normalize_call_arguments` is used by `argument_normalizer` hooks and item-validating handlers. It repairs one declared call object's field formatting, explicit field aliases, and known wrappers; enum formatting and empty-as-omission require explicit field selection, and so does `wrapping_fields`: a selected field whose value is an object of the call's own fields (or JSON text of one) wraps those fields, so owners select only fields whose real values can never be such an object (apply_patch's `patch`). Optional per-field normalizers run on canonical field names before shared schema conversion and alias conflict checks (search_files uses this for encoded argument lists and output synonyms). It never applies edit-distance matching and never recursively treats nested payloads as call syntax. Conflicts are checked before omission. Batch owners invoke it separately per item to preserve independent execution. Target ids are not vocabulary enums.

## Private file replay

`scripts/tool_lab/replay.py::Dispatcher` permits only `apply_patch`, `edit`, `write` and `read`. Before setup or dispatch it checks reconstructed file keys and every target after current production argument normalization, including move destinations, against the fresh case directory. External paths, traversal, links and indeterminate targets fail closed. An older corpus can omit targets that a new argument repair makes executable; an empty file list is not evidence of no effects. Coverage: `tests/scripts/tool_lab/test_tool_lab.py`.
