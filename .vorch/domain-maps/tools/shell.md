# Shell Tool (`bash` / `powershell`) and `background_tasks`

Runs one host shell command per call, in a new process without input or terminal, returns its clean output with an honest outcome, and lets a command that runs longer continue in the background; `background_tasks` lists, checks and stops the caller's background commands and Sub-Agents.

## Boundary

> User requirement (stated repeatedly; recorded 2026-10-11): The shell Tool (`powershell` on Windows, `bash` elsewhere) runs one-shot commands, like Claude Code's Bash tool. A command never receives input and runs without a terminal, so a program that asks for input fails at once instead of waiting. A command that runs long, a server included, continues in the background and delivers its result when it ends. The Agent lists, checks and stops its background commands with `background_tasks`, which never waits for output and never gives input. Nothing gives a command input or turns it into a terminal; programs that need input or a terminal run only through the terminal Tool. Changing this boundary needs the user's explicit approval, also in a rebuild.

User decisions of 2026-10-11, in order:
1. The shell Tool keeps its names: `powershell` on Windows (PowerShell 7 as today), `bash` elsewhere. No waiting for output lines anywhere; no `process` Tool under that name.
2. `timeout` is how long the call waits: omitted 120 seconds, at most 600. When it passes, the command is not stopped but moves to the background, and the result tells the Agent it runs longer than expected, so it can let it run or stop it. No timer stops a command.
3. A small companion Tool with actions `list`, `status` and a stop action, so the Agent can see and stop its background commands. No wait, no input.
4. A Parent Agent sees the background commands and terminals of its Sub-Agents (all depths) in `background_tasks list` and `terminal list`, each marked with the Sub-Agent it belongs to, and can check and stop those commands. Every result about a background command names the file that holds its complete output, so the Agent can read it directly.
5. The companion is `background_tasks` with `list`, `status`, `stop` and one `id` field, for background shell commands and Sub-Agents alike (as Claude Code's `TaskOutput`/`TaskStop` cover shells and agents). `subagent` keeps only `run` and `send`; its `list` and `cancel` move to `background_tasks`. No `type` parameter: the id's prefix (`cmd_`, `sub_`) tells the kinds apart, and list rows carry `type`.

> User requirements of 2026-10-13 (stated emphatically):
> 1. The shell Tool runs the Agent's command exactly as written: vBot does not change what the command does or prints. The Windows bootstrap keeps only UTF-8 console encoding, English UI culture (PowerShell's own messages in English; the user's culture for numbers and dates stays untouched), plain-text rendering, a 200-column host buffer, and the real exit code of the last native program. vBot never adds shims or rewrites of its own: no `head`/`tail`/`wc` emulation, no `/dev/null` rewrite, no number-culture change, no private formatter.
> 2. vBot's own remarks never appear inside `output`; they go into separate result fields (`hint`, `next`, `notes`).
> 3. The log file holds exactly the bytes the shell wrote: raw, stdout and stderr together.
> 4. The `output` of an ended command is the cleaned text (escape sequences removed, `\r` and backspace applied as a terminal would), whole up to 30,000 characters; longer output shows its first lines within 2,000 characters, one marker line naming the raw log, and its last lines in the rest (at least 28,000).

The rebuild of 2026-10-04 (1a2b28e2e) ran commands in hidden ConPTY terminals with an open stdin, and later commits added idle hand-offs, input into commands, driven commands and a timeout stop after input; none of that was approved. ## Terms

### Background command
A shell command that runs on after the call that started it returned: started with `run_in_background`, still running when the call's wait passed, or moved to the background by the user. It has a `cmd_` id, is listed by `background_tasks list` and in the WebUI Activity panel, raises `command_status_changed` events, and delivers its result once as a new message when it ends (D7 below). A command that ended in its call while processes it started still run is a background command too, without a delivery: `background_tasks` lists it, and the WebUI shows it as `processes still running` until those processes end. A foreground command (still inside its call) is unlisted. Not a Terminal Session, and not every background task: `background_tasks` also covers Sub-Agents.

### Command end
A command ends when its shell exited and every process the shell left running ended or went quiet: no output, no new process and at most 0.15 s CPU for 2 s (`COMMAND_LEFTOVER_QUIET_SECONDS`, `IDLE_CPU_SECONDS`); output after the shell's exit is read for at most 1 s (`COMMAND_DRAIN_SECONDS`). An end caused outside vBot, such as `taskkill /T` on the shell, is an ordinary end. When the process tree cannot be read at the shell's exit, the command does not end: its exit code is kept, it counts as running (so its call moves it to the background, and it is listed and stoppable), and the next process-tree poll that reads the tree decides (`test_processes_that_cannot_be_inspected_at_the_exit_keep_the_command_running`). Until then the call waits, the command reports `running`, and nothing is delivered. Reason: PowerShell does not wait for a GUI-subsystem program (for example a tray app's exe used as a CLI), which prints its answer after the shell exited; ending at the shell's exit returned empty output and sent Agents into repeated waits (Sessions, 2026-10-07: 11 such results). A server the command started waits quietly, so it ends the command within about 3 s and is reported as still running.

### Warm shell
On Windows, a `pwsh` started with the bootstrap before a call needs it, waiting for its request, so a call need not wait for PowerShell's start. One launch claims it; it is then that command's shell and exits with the command. It is never reused, keeps nothing from one command for the next, and is not a command: no list, count or limit of commands includes it. Behavior: CommandManager contract -> Warm shell.

## Shell Tool interfaces

- Registry name `bash` (`SHELL_TOOL_NAME`); the Model sees `powershell` on Windows and `bash` elsewhere (`SHELL_MODEL_NAME`, `tools.md` -> Model Tool names). Registration: `register_shell_tool(registry, command_manager, credential_resolver=..., prompt_blocks=..., update_handoffs=..., projects=..., scratch_areas=...)`, family `execution`, summary `Run shell commands.`; Runtime bootstrap passes the `ProjectStore`. It also declares the dynamic `tool:bash` Prompt Block `## Shell Environment Access` (empty without permanent Agent env grants; text from `format_shell_env_usage`, shared with Skill env guidance).
- Schema (`SHELL_TOOL_PARAMETERS`): one open flat object requiring `command`, with optional `description`, `workdir`, `timeout` (number, minimum 0, default 120, no schema maximum: the handler caps it and some Provider adapters reject extra keywords), `run_in_background` (boolean) and `env_keys`. Accepted but unadvertised: `timeout_ms`, `env`, `mode`. The definition names no other Tool, so it is the same for every Tool set; what happens to a long command, and the calls that follow it up, the results say when it happens. On Windows it names the user's regional format with an example number and date where that format is not en-US or invariant (`_powershell.py:powershell_culture`: the culture name, decimal separator and short date Windows reports for the user's default locale with the user's changes, which pwsh uses; read with no shell, once per process, so the definition stays the same for the Provider's cache; left out when it cannot be read; user decision 2026-10-13). Sub-Agents (Session depth >= 1) get the same definition and behavior, `run_in_background` included (user decision 2026-10-05). A text names `background_tasks` or `terminal` only when the Agent can call it (`ToolContext.can_call`, so also as an On-demand Tool it has not loaded, since an exact call works without loading) and any other Tool only when it is offered (`named_tools`).
- Argument tolerance (`_shell_arguments.py:normalize_shell_arguments`): `cmd`/`script`/`commands` and argv arrays (joined into one host command line, each item one argument: on Windows a bare word or a `powershell_literal`; a host-shell `-c`/`-Command` wrapper is unwrapped), OpenAI `local_shell` `action` objects, `cwd`/`directory`/`working_directory`, `timeout_ms`/`timeout_seconds`, title-like description fields. `run_in_background` is canonical: `mode` (`foreground`/`background` and their spellings such as `fg`, `bg`, `async`, `detach`), `background`/`is_background` flags and a zero yield field (`yieldMs`, `yield_time_ms`, `yield_after`, `background_after_seconds`) map onto it; fields that ask for both fail with the conflict, and an unknown `mode` value fails naming `run_in_background`. Fields that cannot have an effect run the command with a note instead (`NO_EFFECT_FIELDS`, `no_effect_notes`): `pty`/`tty`/`interactive` true, `stdin`/`input` with text, a non-zero yield field; false or empty ones are dropped, and so are requests vBot always satisfies or that only shape output (`notify_on_complete`, `login`, `max_output_tokens`, `dangerously_disable_sandbox`). Calls asking for another effect (`elevated`, escalated sandbox permissions, `require_user_approval: true`, a non-empty `user`) fail before running with the fix.
- `workdir`: absolute or relative to `effective_cwd`; a missing directory fails naming similar directories and the fix (pass an existing directory, or omit `workdir`); a file fails saying so, with the fix to pass the directory it is in or omit `workdir`; a missing working directory with `workdir` omitted names only the first. Unadvertised `project:<project-id>` runs in that Project's directory (`_workdir.project_workdir`, shared with `terminal`; the Projects block teaches each Project's path); its failures (`ProjectWorkdirError.code`: `invalid_workdir`, `project_not_found`, `project_unavailable`) are `invalid_arguments` failures here, each naming a next step.
- `timeout` is how long the call waits for the command, in seconds: omitted 120 (`SHELL_DEFAULT_WAIT_SECONDS`), at most 600 (`SHELL_MAX_WAIT_SECONDS`; a larger value is read as 600 with a note), `0` read as omitted with a note. A value of at least 10,000 that is a whole thousand is read as milliseconds with a note; disagreeing `timeout`/`timeout_ms` fail; a negative one fails. With `run_in_background` it is ignored. No timer ever stops a command (user decision 2).
- `env` (unadvertised) sets plain variables; vBot never passes a credential value written in the call. Credentials come only through granted `env_keys` names resolved server-side. An ungranted `env_keys` name the server process itself has passes with a note; an unknown one fails, naming the granted keys.
- Host shell (`_shell_start`, resolved against the call's fresh environment's PATH off the Event Loop): Windows `pwsh -NoProfile -NonInteractive -Command <powershell_bootstrap()>`, the same text for every call, started with the environment's base; the command, the `workdir` and the call's own environment layer travel as the request on the shell's stdin (`powershell_request`; PowerShell bootstrap below), so no command-line limit applies to the command. POSIX `bash -c <command>` with the complete environment. A missing `pwsh`/`bash` fails with "Ask the user to install it". These failures are `command_not_started` (not `invalid_arguments`), because the command is right and the host cannot run it.
- Start failures (`tool_failure`; nothing ran, the update token is released): `command_limit` (retryable) when vBot already runs 64 commands, naming `background_tasks` list and stop when the Agent can call it, otherwise to run again once one of its background commands exited; `command_not_started` when the turn was cancelled or vBot shuts down, when the `workdir` was removed after the call was checked (the missing-directory text), or when the shell could not start. The last case is logged at WARNING (`Starting a shell command failed`) and named by the state the operating system error reports (`_launch_problem`), never by the error's own message, which is in the host's language and names no next step: no operating system error, out of memory or process resources (`ENOMEM`, `EAGAIN`, `EMFILE`, `ENFILE`; Windows errors 4, 8, 14, 1450, 1455; naming `background_tasks` list and stop when callable), and any other error with its number are retryable and say to tell the user if it fails the same way; a full disk (`ENOSPC`, `EDQUOT`; Windows 39, 112) and denied access (to the `workdir` when the shell starts, to vBot's data directory when the output file is created) are not retryable and say to tell the user (`test_a_shell_that_cannot_start_names_the_state_instead_of_the_raw_error`). On Windows a call also fails `command_not_started` after the start when the bootstrap ran nothing of the command (PowerShell bootstrap -> Nothing ran).
- Results (`tool_success` data; `ok: true` for every started command, also for a non-zero exit), fields in this order and omitted when empty:
  - ended: `status` (`exited` | `stopped`), `exit_code` (exited, when known; a stopped command has none, because its code is vBot's kill, not the program's), `exit_code_hex` (the hexadecimal form of a high-bit 32-bit Windows exit value, when present), `stopped_because` (stopped), `output`, `failed_programs` (direct child programs of the shell that exited non-zero before any stop, Windows only, such as `git.exe exited with code 128` or `python.exe exited with code 2 (-m pytest)`; omitted when exactly one failed with the `exit_code` of a command that exited by itself, which it would only repeat), `hint` (non-zero exit with a known failure shape, or a command that did not run as written whatever its exit code; after a stop by vBot only the held-output hint, Output shaping -> Holding pipe stages), and for processes the command left running `command_id`, `still_running` (`name (pid N)`) and `next` (the call that stops them). Such a command is listed as a background command without delivery, so the user and the Agent can see and stop what remains; its result names the log file only when the output was cut.
  - running: `status: "running"`, `command_id`, `output` (the newest output only, below) and `next`, which says why the call returned (the Agent's timeout, the default 120 seconds, the user's move after how long it ran, or `run_in_background`), names the log file (with a holding pipe stage, says when the output piped into it appears; Output shaping -> Holding pipe stages), says the result arrives as a new message, forbids starting it again or sleeping and polling for its result, and names the exact stop call. On Windows, when the wait passed (not the user's move) while the command has printed nothing, not even a partial line, and its processes were idle over the wait's last 10 seconds (`wait` -> `idle`), and no pipe stage holds the output until its input ends (`holding_stage`: the stage explains the silence, and an idle program behind it, such as one in a retry back-off, may print later; Swarm run 2026-10-13), `next` also says it may wait for console input, with the stop call and the non-interactive form (Constraints & Gotchas, user decision 8 of 2026-10-12); only that call's result says so, not `background_tasks` status or the delivery. Every command that outlives its call delivers its result. Durations read `45 seconds`, `14 minutes 5 seconds`, `1 hour 2 minutes` (`duration`, singular for 1).
  - `notes` lists how the call was read leniently (timeout 0, over 600, milliseconds, inherited env key, fields without effect).
- Output shaping (`command_output_text`, `running_output_text`; user requirements 2 and 4 of 2026-10-13): `output` holds only the command's cleaned output, never a remark of vBot's. The transcript (`CommandTranscript`) keeps it bounded: `head` the first whole lines within 2,000 characters (`COMMAND_HEAD_CHARS`, lines joined by line breaks), `tail` the last whole lines after them within 30,000 (`COMMAND_TAIL_CHARS`), `total_lines` every line, and the computed `omitted_lines` the lines neither holds. A first line longer than 2,000 characters is held as its start (`head_cut` characters short), a last line longer than 30,000 alone as its end (`tail_cut` short), which any later line replaces, also when a backspace left that end shorter than 30,000 (review 2026-10-13: the Event Loop's copy of the transcript then lost the lines after it); the line still being written is the last line. The cleaner keeps a line in progress longer than 60,000 characters as its first and its last 30,000, so backspaces that erase its kept end leave the line whole again once it is 30,000 characters or shorter; a longer rest shows its start, a cut, and the end it has (review 2026-10-13: 70,000 characters and 41,000 backspaces left an empty line). An ended command's `output` is the whole output when the transcript holds every line and it fits in 30,000 characters (`SHELL_OUTPUT_CHARS`); otherwise the head, one marker line, and the last whole lines within the rest of the 30,000 (at least 28,000; a last line longer than that room keeps its end, and a single line longer than both parts shows its start and its end). The marker says what was left out, in lines, characters of cut lines, or both, and names the log file: `[... N lines omitted; vBot kept this command's complete raw output in <path> for you to read ...]` (`tools/shell/agent-facing-text.md`); without a log file it only counts (`test_long_output_keeps_its_first_and_last_characters_and_names_the_log_file`), and once writing the file failed it says how much the file holds and how to get the rest (Log file below). A running command's result shows the newest 20 lines within 4,000 characters (`SHELL_RUNNING_OUTPUT_LINES`/`_CHARS`; a longer last line keeps its end) after a marker counting the earlier lines and cut characters, `[... N earlier lines omitted ...]`; it names no file, since the result's `next` does (shell review 2026-10-13: the file was named twice; `test_running_output_is_the_newest_lines_and_its_log_file_has_every_line`). The same holds for `background_tasks` status of a running command.
- Holding pipe stages: when the command pipes into a stage that passes nothing on before its input ends (`Select-Object -Last`, `tail`, `Sort-Object`/`sort`, `Group-Object`, `Measure-Object`, `wc`, `Out-String` without `-Stream`; `holding_stage`, the last such stage of the command text), a running result's `next` (shell and `background_tasks` status) says after the log sentence that output piped into that stage appears only once the command before the pipe has finished, and calls the log file neither complete nor live: the stage's lines reach it only at the end. After a stop by vBot the result's `hint` (and the delivery's `Hint:` line) says that the stage held that output and the stop lost it, the only hint a stopped command gets, and the sentence naming the log file calls it the raw output that reached vBot: the held lines never left the shell (Swarm run 2026-10-13: a stop result claimed the complete output while the stage's lines were lost). When no output reached vBot, no sentence names the file (shell review 2026-10-13: the delivery's `Output: (none)` was followed by a pointer to the empty file; `test_a_stop_does_not_call_the_log_complete_when_a_pipe_stage_held_output`). Keeping those lines would need vBot to change the command (Constraints & Gotchas -> Trim stages).
- Live output: while the call waits, the Run event `tool_call_output {tool_call_id, command_id, output}` carries the newest 40 clean lines at most every 0.5 s while output arrives (`COMMAND_PROGRESS_LINES`/`_SECONDS`); each replaces the previous one (transient, never persisted).
- Display: `shell_display_parts` shows the `description` or the command (copyable either way); `shell_detail_blocks` shows the command, the result's `data.output`, warnings for a stop, the non-zero exit code of an `exited` result and failed programs, an info notice `Hint: ...`, and for a running result the info `The command continues in the background.` The WebUI renders a `stopped` result as a cancelled row, not a success (`webui/chat.md`).

## Execution lifecycle

1. `_parse_call` validates and resolves everything before anything starts: `workdir`, the wait, env, credentials and the no-effect notes.
2. An update handoff token is issued when the call has a result-persistence boundary; it stays claimable exactly until every process of the command ended (`wait_finished`).
3. One worker builds the fresh `command_environment` (below), the shell argv and, on Windows, the request; PATH searches probe the filesystem and stay off the Event Loop. The executable is not cached across calls. `CommandManager.launch` starts the command in the foreground, on Windows in the warm shell when one is ready for the same start (not for a call that sets an empty `env` value, Environment layers).
4. `run_in_background`: `to_background(deliver=True)` at once and the running result. Otherwise `wait(seconds)` until the command ended or the wait passed; the user can move the call to the background earlier (`background_registration_hook`, set by Chat's Tool dispatch). Per-call cancellation stops the command (`run_cancelled` when the Run was cancelled, else `user`) only until the call hands it to the background: from then on the call's cancel callback does nothing, so a Run cancel or a stop of the call leaves a background command running (D7; `test_the_user_stops_the_command_or_moves_it_to_the_background`).
5. Ended with no process left -> the ended result. Ended with processes still running -> `to_background(deliver=False)` and the ended result with `still_running`. Still running -> `to_background(deliver=True)` and the running result.

## CommandManager contract

Agent rename and Session move await matching admitted launches before transferring
commands, including their delivery ownership and transfer counts. Command process
handles stay open until an in-flight kill finishes its confirmation, even if the
supervisor has already observed the exit or the stop caller was cancelled.

- `launch(owner, argv, *, command, description, cwd, env, origin_run_id, formatter, execution_owner, on_output, request, warm, not_run_codes) -> CommandHandle` (`cmd_` id from `new_id("cmd")`, the shell's PID). With `request`, `env` is the shell's start environment and the request, written to its stdin, carries the rest (`CommandLauncher.launch`); `warm=False` marks an `env` that holds values of the call, so no warm shell serves it; `not_run_codes` maps exit codes by which the shell says it ran nothing of the command to the reason (`NotRunReason`: `request_unreadable` | `workdir_unavailable` | `language_mode_unavailable`), which `CommandReport.not_run` names once the shell exited with one of them (logged once at WARNING; PowerShell bootstrap -> Nothing ran); the command's runtime counts from the launch's return, so a claimed warm shell's wait before does not count. Refuses with `CommandNotStartedError` when the origin Run was cancelled, the execution group closed or vBot shuts down, `CommandCapacityError` (retryable) when 64 commands are unfinished (`COMMAND_MAX_LIVE`, launches in progress included, separate from the terminal limits), and `CommandLaunchError` when the process cannot be started or tracked. A cancelled caller leaves no command behind.
- Transport (`_command_launch.py`): stdout and stderr share one pipe (order kept); stdin is the null device on POSIX and a pipe on Windows, where the null device is a character device that programs take for a console. Without a request that pipe has no writer; with one, the launcher writes the request on a thread of its own and closes the pipe (vBot's end is not inheritable), and the bootstrap reads it to its end before the command runs. A thread that cannot start ends the shell and releases its pipe and Job; a request pipe exists only on Windows (`launch_pipe_process` refuses it elsewhere). No PTY is attached, so `isatty()` is false for all three and a program that reads stdin gets EOF at once (verified for a native program started by a command in a claimed warm shell, `test_command_launch.py`). On Windows the process still has a console: `CREATE_NO_WINDOW` gives it a hidden one (`conhost.exe`) that nothing writes to (Constraints & Gotchas). On POSIX it has none. Windows creates the shell `CREATE_SUSPENDED | CREATE_NO_WINDOW | CREATE_NEW_PROCESS_GROUP`, assigns it to a kill-on-close Job Object, then resumes it, so no process escapes in its first instruction; the windowless console host (`conhost.exe`) in the Job is ignored by end detection. POSIX starts the shell in a new session through the guarded launch (`tools/os-processes.md`). A process that cannot be tracked is killed and not started.
- Warm shell (`PipeLauncher`, Windows only; the user's design of 2026-10-12, `test_command_launch.py`). Commands stay one-shot: a warm shell is only started earlier, serves exactly one command and exits with it.
  - At most one exists. After every launch with a request the launcher starts one for the same argv, start environment and tracker unless one exists, in the system directory (`%SYSTEMROOT%\System32`: it always exists, and users cannot plant a program or library there that the shell would load from its working directory). It is created exactly like a command's shell (suspended, windowless, new process group, in its Job before its first instruction). The first call of a server starts cold and starts the first warm shell; none starts with the Runtime, avoiding the memory and compilation cost until the first command needs a shell (current measurements: PowerShell bootstrap -> Warm-up and cost).
  - A launch claims it when argv, start environment (`CommandEnvironment.base`) and tracker are equal and its process has been created; one still being created stays for a later launch while this one starts its own shell, so a burst of parallel calls starts no more shells than calls (plus the next warm one), and a warm shell is never claimed twice. A launch with another start ends the warm shell and starts its own. A launch with `warm=False` starts its own shell and leaves the warm shell waiting; none starts after it.
  - It ends unclaimed after `WARM_SHELL_IDLE_SECONDS` (10 minutes) and at once when the launcher closes (`CommandManager.shutdown`, `aclose`, `close`); a start in progress is cancelled, which ends the process it created, and no launch starts another one. `close()` after its Event Loop closed still kills a ready warm shell and raises nothing; a start in progress there never resumes, and the kill-on-close Job ends a process it created at the latest with vBot's process. A warm shell that exited or could not start is passed over (the launch starts its own shell), with one WARNING per kind (`exited`, `start`).
  - It lives in the launcher only: no list, count, limit, status event or scope close of commands includes it.
- Output host: cleaning costs CPU time in proportion to what a command prints, so each command's `OutputCleaner` runs on a worker of the manager's output host (`InterpreterHost`): a thread that owns a subinterpreter with its own GIL, loaded with only `_command_decoding.py`, `_command_cleaning.py` and `_hosted_objects.py`. Workers start one per `prepare()` (called through `run_blocking` at each launch) up to `DEFAULT_WORKERS` = min(4, half the CPUs, at least 1); a `prepare()` while no worker runs yet and every allowed one is still starting waits for that start (a `threading.Condition`), so commands launched together right after server start all get workers (re-review 2026-10-12: the second of two parallel launches on a one-worker host cleaned on the Event Loop for its whole life). A `prepare()` whose own start failed while another start is in flight waits for that one too: `prepare()` returns only once a worker runs or the host is inline (or closed), so `open()` on the Event Loop never waits (final review 2026-10-12, N3: such a launch's `open()` blocked the Event Loop for the rest of the other start, 772 ms in the probe). Commands are assigned to workers in turn, and each command's calls stay ordered on its worker. The reader reads at most 64 KiB at a time and reads the next chunk only once the previous one is written to the log file and cleaned, so a command that prints heavily has one chunk in its worker's queue and delays another command by at most that chunk; Terminal screens use their own host and share no workers. Each `feed` returns only the transcript changes (`OutputUpdate`: lines added to the head and the tail, the line count, the start and end of the line still being written), which `CommandOutput` applies to its own `OutputLines`, so `transcript()` and `latest()` read on the Event Loop without waiting for the worker. A subinterpreter that cannot start (WARNING log) stops the host from adding workers; once none started and none is starting, the host runs its objects inline, on the Event Loop, and says so once at WARNING when it hands out the first such object (`test_interpreter_host.py`). A worker's start resolves within 30 s (`_WORKER_START_SECONDS`; a start takes 35-90 ms), also when `concurrent.interpreters` cannot be imported: one that has not started by then counts as a failed start, and its thread ends once the start does, so a start that never resolves cannot hold every later launch (final review 2026-10-12, nit: the Condition wait relied on every start resolving). Tests use `InterpreterHost.in_process()`. `CommandManager(output_host=...)` owns the default host and closes it at `aclose`/`close` after the output work already queued; a host closed during a launch refuses it (`CommandNotStartedError`, "vBot is shutting down"). Errors from a hosted call arrive as `RuntimeError` with the original message only. When cleaning fails (a cleaner bug, or the host closed under the command), the reader logs one ERROR, keeps reading the pipe (the command never blocks on a full pipe) and discards nothing: the log file keeps every byte, and that chunk and all later output enter the transcript decoded and split into lines but not cleaned, so escape sequences and `\r` can show in `output`. Decoding resumes from the complete interpretation state after the last successful update (`OutputUpdate.decoder_state`: encoding, pending bytes and surrogate, and emitted lookbehind), so a character or encoding marker split across the failure stays whole without duplicating text already shown (review 2026-10-13: the fallback started a fresh decoder and turned such a character into U+FFFD; probe 2026-10-13 with a real subinterpreter host closed under the command: `Grün` stayed whole) (`test_output_that_cannot_be_cleaned_is_kept_uncleaned_and_logged_whole`). The probe for moving cleaning off the loop (2026-10-12, Windows, 20 MB of short lines) measured Event Loop lag p99 106 ms with cleaning on the loop and 9-14 ms after, against 7 ms for an idle loop.
- Output cleaning (`_command_cleaning.py`, rules in its module docstring): incremental UTF-8/UTF-16 interpretation through the same `CommandOutputDecoder` as `read` (byte order marks select UTF-16 LE/BE, clear unmarked Latin runs select UTF-16 LE; invalid sequences become U+FFFD); no per-line diagnostic ranges are retained by the live cleaner, keeping its state bounded. Ordinary short UTF-8 output and unambiguous UTF-16 lines remain visible before EOF; only incomplete characters or ambiguous encoding switches wait for more bytes. Escape sequences are removed (CSI, two-character sequences, OSC/DCS/SOS/PM/APC strings, each started by ESC; parsing is bounded, so an unterminated sequence cannot hide output); an ESC that cannot start a control shows as the text `\x1b`; the C1 code points U+0080-U+009F are removed one by one and start no sequence, since a UTF-8 terminal does not interpret them (review 2026-10-13: UTF-8 text decoded as Latin-1, `GrÃ¼Ã\x9fe und mehr`, lost the rest of its line after U+009F, an APC start); `\r\n` ends a line; a lone `\r` restarts the line (a redrawn progress line keeps its final state); a backspace erases the character before it; other C0 controls and DEL are removed, tabs stay. Only the transcript is cleaned. A chunk whose only control characters are line breaks is split into lines in bulk. The line still being written keeps only its first 2,000 and last 30,000 characters once it exceeds 60,000 (twice `COMMAND_TAIL_CHARS`), so an endless line holds bounded memory.
- Log file (user requirement 3 of 2026-10-13): a private file in Storage's temp category `commands` (`artifacts/temp/commands/tmp_<12 base32>.log`, 72 h retention after the command finished, mode 0600 on POSIX; `storage.md`). The manager opens it with `os.open`, and `CommandLog` appends each chunk the shell wrote, unchanged (stdout and stderr together, escape sequences, `\r` and invalid UTF-8 included), through `run_blocking` as it arrives and before the chunk is cleaned (`test_log_file_has_every_byte_the_command_wrote_as_it_arrives`). A failed write logs one WARNING, closes the file and stops writing; the file keeps what was written before, and `report().log_loss` (`LogLoss`: the error, the bytes kept and the line feeds among them) says so, while `log_path` stays named unless the file holds nothing (`test_a_log_file_that_cannot_be_written_reports_what_it_kept_and_why`). Every text that would name the file then says exactly how many raw bytes it holds and why not all of it; a lost copy never undoes the command, so any repeat advice is conditional on safely repeating its effects (`lost_output`, Agent-facing text; review 2026-10-13: the file was dropped from the texts without a word). Without temporary-file storage a command has no log file.
- `wait(id, *, seconds, check_idle=False) -> "ended" | "deadline" | "idle"`: event-driven; cancelling it changes nothing. Only a caller requesting `check_idle` follows the command's processes over its last 10 seconds (`COMMAND_IDLE_WINDOW_SECONDS`; a shorter wait whole, which on Windows includes pwsh's start when the shell started for the command, and is then not idle) with the leftover quiet test (no output, no new process, at most `IDLE_CPU_SECONDS` of CPU time, polled every `TREE_POLL_SECONDS`) and returns `idle` when they stayed quiet, else `deadline`. The shell Tool requests this only on Windows for its silent-console-input hint; a POSIX foreground wait never samples the process tree. Nothing else follows the tree while the shell runs. The window is long enough that work in bursts, or a transfer that uses more than 1.5 % of a core, is not idle (probe 2026-10-12, real pwsh: a tree waiting in `getpass` or `RawUI.ReadKey()` used at most about 0.06 s of CPU in any 10 s after its first second, in which pwsh's start took about 0.45 s). `wait_finished(id)`: every process ended.
- `to_background(id, *, deliver)`: lists the command (status events start) and, with `deliver`, arms its delivery; a command that had ended already delivers nothing (the caller reports the result).
- `stop(id, reason) -> CommandReport`: kills the whole tree; Windows terminates the Job, POSIX sends SIGINT to the process group and kills after 3 s (`COMMAND_STOP_GRACE_SECONDS`). The first reason wins and fixes the outcome. A stop after the end kills the leftovers and keeps the outcome; a finished command is returned unchanged. Every stop fixes the count of failed child exits before its interrupt or kill, also after the end, so exits the kill causes never count as the command's failures, even when a poll of the leftovers records them before the kill is confirmed (re-review 2026-10-12, lifecycle note on kill exits during a terminate). A kill must be confirmed within 5 s (`process_tree.py`); otherwise `CommandStopError` names the surviving processes, the command stays live and listed, and a later stop retries. `ProcessTree.terminate` tells a kill the operating system refused, which no process got (a plain `OSError`), from one it sent but could not confirm (`KillNotConfirmedError`, carried as `CommandStopError.kill_sent`). A stop that sent no kill - refused, or cancelled or failed before its kill began, as when a Run cancel interrupts the POSIX grace - gives its reason and exit count back unless the command ended meanwhile (the interrupt before the kill can end it; it then stays `stopped`): the command runs on as if not stopped, and an end it reaches by itself reports `exited` with its exit code and delivers its result; a `scope` stop's withdrawal of the delivery stays (re-review 2026-10-12, texts finding 2: after `stop_failed`, such an end read "you stopped it.", without exit code or delivery). A stop whose kill was sent keeps both, also when the kill is not confirmed or the stop is cancelled after its kill began (the kill then runs to its end): processes that end later end of the kill, so the end reads `stopped` with that reason, and `stop_failed` still names the survivors (final review 2026-10-12, N1: an unconfirmed Job kill was undone, so the death it caused read `exited` with code 1 and the killed children as failed programs, delivered to the Agent that had stopped it; N2: a stop cancelled in its grace kept `agent`, so the command ran on as stopped and its own end delivered nothing). A confirmed kill takes its stop's reason when every stop before it gave its reason back. An `agent` stop suppresses the delivery only while it holds the reason.
- Reasons: `agent` (the command's own Agent, through `background_tasks`), `parent` (an ancestor Session's Agent), `user` (one command, from the chat), `run_cancelled` (the Run whose call waits for it was cancelled), `shutdown`, `scope` (Stop all, a Sub-Agent stop, removal of the Session, Agent or Project, an Extension execution group's close).
- Reads: `report(id)`, `latest_output(id, lines)` (at most `COMMAND_RECENT_LINES` = 200, the line being written included, as far as the transcript holds them: its last 30,000 characters), `status(id)` (`running` | `completed` | `failed` | `stopped`; None for an unknown or foreground command), `commands(owners)` (the background commands of those Sessions, newest first, each naming its Session; foreground ones are not listed). `acknowledge(id)`: a persisted Tool result showed the end, so a delivery not yet handed over is withdrawn; one whose delivery TriggerService already claimed is delivered once, as submitted. Any caller finds a command by id alone; the caller decides which Sessions it may act for.
- Lifecycle: `cancel_run(run_id)` stops only the Run's commands still inside their call and refuses new launches for it, `release_run(run_id)` forgets that marker (Chat's Run cancel callback and completion observer, `chat/run-execution.md`); `close_scope(owner)`, `close_agent_scope(agent_id, project_id)`, `close_project_scope(project_id)` stop with reason `scope` and return how many unfinished commands they stopped; `transfer_scope(source, target)`, `transfer_agent_scope(agent_id, new_agent_id)` move commands with their Session; deliveries follow, and a result already submitted to the old Session and not yet delivered is withdrawn there and submitted with the same body to the new one, unless its delivery already claimed it (`test_transferred_commands_deliver_to_their_new_session`); `has_execution_work(owner)` and `close_execution_group(extension, group_id, epoch)` serve Extension execution groups. A lifecycle scope close logs an unconfirmed kill (`A command survived the close of its scope (...); it stays listed`) instead of raising: the lifecycle step goes on, and the command stays live and listed for a later stop.
- `shutdown()` (Runtime shutdown step `commands`, before Trigger delivery closes, `runtime/lifecycle-steps.md`): refuses new launches, closes the launcher (ending the warm shell, as `aclose()` and `close()` also do) and stops every unfinished command with reason `shutdown`; background ones submit their stopped result. It raises `CommandStopError` after every command was stopped or tried. `aclose()` (step `command_processes`) waits for launches in progress, kills every remaining command off the Event Loop and in parallel (`CommandRecord.kill_and_release` through `run_blocking`), awaits the commands' tasks, closes its own output host and withdraws undelivered results (`test_aclose_kills_the_remaining_commands_off_the_event_loop_together`). A command whose kill was not confirmed is released all the same: its tasks are cancelled and its surviving processes logged at WARNING (`name (pid N)`), so Runtime stop never waits for them (re-review 2026-10-12, lifecycle finding 2: `aclose` waited forever for such a command's reader and supervisor); `close()` is the fallback without an Event Loop, each kill blocking the calling thread (`kill_now`). Both raise `CommandManagerError` naming the commands whose kill was not confirmed. `start()` runs the sweeper that forgets a command 30 minutes after its last process ended (`finished_at`; `COMMAND_RETENTION_SECONDS`, checked every 60 s).
- `add_changed_callback(callback)`: called with a background command's id when it moves to the background, ends, when a process it left running ends (after the end each process-tree poll updates `still_running`), when it finishes, and when it is forgotten (`status` is then None); the server bridges it into `command_status_changed`.

### Deliveries (D7)

- One delivery per command that outlived its call, when it ends, through `TriggerService.submit_completion(notice_id="command:<id>", origin_run_id=..., body=formatter(report), project_id=..., execution_owner=..., wake=True)`. It joins the Session's active Run at its next request or starts one, also in Sub-Agent Sessions at every depth (user decision 2026-10-05), and is checkpointed before handoff and delivery so it survives a restart. A delivery to a closed execution owner (`RunAdmissionBlockedError`) is dropped at DEBUG.
- Recovery (`_command_checkpoint.py`, canonical Session-owned `session_background_commands`): the shell waits for its background checkpoint before returning. Status changes and final delivery bodies are serialized off the Event Loop through the Session database worker; a failed write remains a failure until that command's full checkpoint is saved again. If storage fails, the Tool still names the command that already started, with its current outcome and a warning that completion notification is not guaranteed. Startup restores ended reports without reopening old PIDs. A command that had not finished is rebuilt from its raw log file (`read_log`, cleaned on the output host as live output is; skipped when writing the file had failed, since the saved transcript then holds more): its transcript is what the file holds, and a file over 4.25 MiB is read as its first 256 KiB and its last 4 MiB, with the line count of the whole file. One that had not ended reports `stopped` (`server_restart`) with an unknown outcome and a minimum duration: from its saved start (`started_at`) to the file's last write, or its last saved elapsed time when that is later (incident 2026-10-16: a dev server killed with vBot was recovered as `Output: (none)` and an unknown duration while its log held 1,527 bytes, and the Agent ran everything again). Nothing runs again; a foreground call interrupted by vBot's stop keeps the generic `result_unavailable` failure. Pending delivery checks the exact command body in canonical Session Notes before replay and stays durable until persistence acknowledges it. Ordinary Sessions use the original Run for completion delivery. An Extension-owned command's old execution epoch cannot run again: recovery persists its outcome Note and an atomic command receipt through `append_notes_once`, bound to the original live generation, without waking a Run or reviving its group. A deleted or archived generation receives nothing. The generation captured before process launch follows moves, including before the first checkpoint, and cannot rebind to a replacement Session at the same address. The Session foreign key cascades deletion; forks do not inherit command ownership. Scope close and durable Tool acknowledgement withdraw recovered pending deliveries; Session moves reroute unclaimed ones. No pending checkpoint expires before delivery; settled records keep their absolute 30-minute expiry across restarts.
- No delivery: a stop by the command's own Agent (`agent`: the stop result is the outcome; when that stop fails or is cancelled once its kill was sent, its call showed no end, so the end the kill causes is delivered), a `scope` stop (withdrawn), a command whose end a persisted `background_tasks` status or stop result of the owning Session already showed (`acknowledge`), and a command that ended in its call (its result is the outcome). A withdrawal only takes effect before TriggerService claims the delivery (`automation/completion-delivery.md` -> Submission and delivery): a claimed result is delivered once, and the command side never cancels the delivery itself (it awaits it through `asyncio.shield`).
- Delivered: an end on its own, a kill from outside vBot (ordinary end with the exit code it got), `user` ("the user stopped it."), `parent` (to the command's own Session, whose Agent did not see the stop), and `shutdown` ("vBot shut down.").
- Run cancel stops only commands still inside their call; background commands keep running and deliver. Stop all, `/stop all`, stopping the owning Sub-Agent, Session/Agent/Project removal and an Extension group's close stop without delivery.
- The delivery names Tools from a snapshot taken at the call (`delivery_names`: `HINT_TOOL_NAMES` plus `background_tasks`), since it outlives the call.

### Sub-Agent work and log files (D10, D11)

- `background_tasks` covers the commands of the caller's Session and of its descendant Sessions (Sub-Agents at every depth), never a parent's or a sibling's. A descendant's command row carries `subagent`, the id of the Sub-Agent whose Session runs it; `status` and `stop` accept it, and an ancestor's stop uses reason `parent` (delivered to the owning Session) while the ancestor gets the stop result with `stopped_because: "you stopped it."` and a note that the Sub-Agent receives a message. A later `status` or repeated `stop` from above tells the reason from the reader's side: `Sub-Agent <id> stopped it.` or `an Agent above Sub-Agent <id> stopped it.` (`stopped_because(..., subagent=...)`). `terminal list` and `status` mark a Sub-Agent's terminal the same way (`tools/terminal.md`).
- Every result about a background command names its log file when Storage provides one: running shell results (`next`), `background_tasks` rows (`log`), status and stop results, and the delivery (`vBot kept this command's complete raw output in <path> for you to read.` unless an output marker already names it; after a stop of a command whose pipe stage held output, `the raw output that reached it` instead, and nothing when no output reached vBot; never for a command the shell ran nothing of, whose file is empty; the wording says the file is the Tool's own copy for the Agent, so Agents told to stay in their working directory read it instead of running the command again). Once a write of the file failed, each of these places says instead how much of the output the file holds and why not all of it, naming the file unless it holds nothing; the markers say the command has already run and allow repeating it only if its effects are safe to repeat; running results additionally require interruption to be safe, and list rows carry it as `log_incomplete` (`lost_output`). A command that ended in its call names the file only when its output was cut, because that is every ordinary call.

## `background_tasks`

- Registration: `register_background_tasks_tool(registry, command_manager, *, subagents=None)`, family `execution`, `catalog_visible=False`, open input schema, `activation: follows` with `activation_source=("bash", "subagent")`: active exactly while either source is, also in a fixed Tool set, and absent from `tool.list`, so the Tool picker and the Project Tool Whitelist show only its sources; a persisted denial of `background_tasks` itself still vetoes it (`tools.md` -> Policy resolution, as for `edit`/`write` in `tools/edit.md`). Not always loaded; results name its exact calls, which work without loading.
- Schema: `action` (`list` | `status` | `stop`, required) and `id`. Unadvertised `action_missing`, `input_action`, `message_content` and `no_effect_fields` are set only by the normalizer.
- Dispatch by id prefix: `cmd_` -> `CommandManager`, `sub_` -> the Sub-Agent branch (`SubAgentTree`: `subagents(caller)`, `running_work`, `stop_subagent`; behavior in `subagents/tree-control.md` -> `background_tasks` list, status and stop; Tool-side tolerance in `tools/subagent.md`). A `term_` id fails `not_a_background_task` with the `terminal` status call; a `ses_` id that is the Session of exactly one Sub-Agent below the caller (the whole tree) is read as that Sub-Agent with a note. All descendants and their commands remain visible and stoppable regardless of their reply target (`subagents.md`). Any other id, or one outside the caller's tree, fails `task_not_found` naming up to 5 of the caller's running tasks: Sub-Agents that work or are queued, and commands that run or left processes running.
- `list`: `tasks`, Sub-Agents first, breadth first (at most 1,000), then background commands newest first. Command row: `id`, `type: "command"`, `command` (the label: the description, else the command with each run of line breaks and blanks as one space, at most 120 characters; Swarm run 2026-10-13: the first line alone read `python -c "` for code passed on the lines after it), `subagent` (a descendant's command), `status` (`running` | `exited` | `stopped` | `not_run`), `exit_code` (exited, when known; never on a stopped or not-run row), `still_running` (`name (pid N)` of the processes an ended command left running), `runtime`, `log` (not for `not_run`, nor when writing it failed before its first byte), `log_incomplete` (once writing the log failed: how much it holds and why). Sub-Agent row: `id`, `type: "subagent"`, `title`, `agent_id`, `session_id`, `parent_id` (below a direct Sub-Agent), `status`, `last_tool` (working), `activity_file`. User-directed Sub-Agent rows also carry `reply_to: "user"`; their status and controls stay unchanged. A note when empty, and a note against polling while one of the caller's own commands runs or one of its direct Sub-Agents works or is queued with Parent-directed replies (a deeper Sub-Agent's answer goes to its own Parent).
- `status` of a command: running -> `status`, `command_id`, `subagent`, `output` (newest 20 lines) and `next`; ended -> the ended shell result, led by `status`, `command_id` and, for a Sub-Agent's command, `subagent`, plus the log file sentence in `next`, and for the caller's own command an acknowledgement once the result is persisted. A command the shell ran nothing of shows `status: "not_run"`, `command_id` and `not_run_because` (the text of the shell's `command_not_started` failure, `_shell_results.not_run_problem`), without exit code, output or log file: its acknowledgement withdraws the delivery that said why, so the status says it (shell review 2026-10-13: list and status showed such a command as `exited` with the reserved code 1447165953, and the explanation never reached the Agent; `test_a_command_the_shell_ran_nothing_of_says_why_in_list_and_status`). Both add a display result naming the command by its label, since the call names only the id. From the third status of the same running command of the caller's own (`_CHECKS_NAMED`, counted per Tool instance; a count is dropped when its command ends or is no longer running), `next` names how often it was checked and says to end the turn unless other work is waiting, instead of the plain delivery sentence (Swarm run 2026-10-13: Agents checked one running command many times, seconds apart).
- `stop` of a command: stops with reason `agent` (own) or `parent` (a descendant's) and returns the ended result; an ended command succeeds with a note (`nothing was stopped`, or the leftovers it stopped). An unconfirmed kill fails `stop_failed` (retryable) naming the processes that still ran when vBot stopped waiting, or saying that whether they ended is unknown.
- It never waits and never writes input or messages: `wait`/`await`/`poll_until` fail in the normalizer. Message and input actions are refused by the handler (`invalid_arguments`), since only it knows which Tools the Agent can call: a message action with a `sub_` id names the `subagent` send call, with the message the call carried, only when `subagent` is callable, and otherwise the Tool's own actions; input actions, and message actions without a `sub_` id, name `terminal` only when callable. Fields of other harnesses' output Tools run the call with a note that they have no effect (`no_effect_fields`): wait fields (`block`, `wait`, `timeout`, `timeout_ms`, `timeout_seconds`) and filter fields (`filter`, `grep`). A value that asks for nothing (false, 0, empty, `no`, `none`, `null`, a placeholder) is dropped silently, and `block: false` drops the wait fields with it.
- Argument tolerance (`normalize_background_tasks_arguments`): `id` aliases `task_id`, `command_id`, `subagent_id`, `work_id`, `shell_id`, `bash_id`, `process_id`, `proc_id`, `job_id`; `terminal_id`, `session_id` and `agent_id` count as `id` only when their value has a prefix this Tool reads (conflicting values fail). Action synonyms: `ls`, `all` -> list; `output`, `log`, `logs`, `check`, `get`, `poll`, `read`, `show`, `inspect`, `info` -> status; `kill`, `cancel`, `terminate`, `end`, `abort`, `halt`, `interrupt` -> stop. A missing action with an id runs `status` with a note naming the stop call (a stop is never guessed), so Claude Code's `TaskOutput {task_id, block, timeout}` and `BashOutput {bash_id, filter}` show the status; a list of one id is that id, several fail. Harness Tool names (`core/tools/model_names.py`): `bashoutput`, `killshell`, `killbash`, `taskoutput`, `taskstop`, `process`, `shelljobs`, `backgroundcommands`, `backgroundtasks` -> `background_tasks`.
- Display: the action and the id; details show listed tasks as a `results` block (title or label, then id, status, runtime or last Tool), one Sub-Agent's or command's state as one result, a stop as a notice, and a command's output with a running notice or, for an `exited` command, a non-zero exit warning; a `not_run` command shows the warning `The command did not run.`

## Server and WebUI

- `command_status_changed {command_id, session_id, status, still_running}` app event, bridged from the change callbacks in `server/_app_lifecycle.py` (`_register_command_status_bridge`): published once per change of a background command's `status` or `still_running` (processes it started still run after its shell exited), so also when the last such process ends; a foreground or forgotten command publishes nothing. `session_id` names the command's Session, since a fork shares its source's History but not its commands. The bridge is removed with the other bridges before the Runtime's shutdown: uvicorn has closed every WebSocket by then, so the shutdown's stops could reach no accessor; accessors learn them from History after their `epoch_changed` reconnect (`server/events-and-reconnect.md`).
- `chat.history` returns `background_command_statuses` (command id -> `running` | `completed` | `failed` | `stopped`) and `background_commands_still_running` (the Session's commands whose shell exited while processes they started still run). `background_command_statuses(records)` folds durable `bash` and `background_tasks` results that carry a `command_id` (`running` never overrides a shown end; `exited` gives `completed` for exit 0, else `failed`; `not_run` gives `failed`) and delivery Notes (`COMMAND_STATUS_NOTE_MARKER` = `The background command `: `completed` for exit 0, `failed` for another or an unknown code and for a command that did not run, `stopped`). The server (`_current_command_statuses`) keeps the folded ends, sets every background command of the Session that `CommandManager.commands` knows to its current status (also one whose hand-off result is not saved yet because its Tool batch still runs), and drops a recorded `running` that is not one of them: that command predates durable checkpoints, or it belongs to another Session, as in a fork. Recovered checkpoints supply stopped status immediately, and their delivered Notes keep it durable after manager retention. Folding a later range onto an earlier fold equals folding both. An `after` read carries the appended records' statuses plus those of every live command of the Session (only the live ones when nothing was appended), so a caller learns that a `running` it holds and the read leaves out has ended; the still-running list is always complete; a `before` page carries neither field. Every read but a `before` one also lists in `subagent_background_commands` (`{subagent_id, session_id, command_id, label}`, complete each time) the background commands still running or leaving processes running in the Sessions of the Session's Sub-Agents at every depth down to a Sub-Agent the user took over, which with everything below it is left out (what its Stop all stops below it); `subagent_id` names the Session's own Sub-Agent above the Session that runs the command (`_subagent_background_commands`). The read walks the Sub-Agent tree (about 12 ms for 300 descendants) only while `CommandManager.has_unfinished_background(besides=<the Session>)` finds an unfinished background command of another Session; otherwise the list is empty without the walk. Only this marker is read (Generation 1): the about 4 terminal-era deliveries have no status, and the WebUI shows such commands as ended.
- `chat.stop_command {session_id, command_id}` -> `{stopped, status}` stops one background command with reason `user` (its Agent receives the stopped result), or the processes a command that already ended left running (it keeps the status it ended with, and nothing more is delivered). `stopped` is false when nothing of it ran any longer or another stop came first; `status` is the command's status afterwards. `chat.command_output {session_id, command_id}` -> `{status, still_running, output}` with at most the newest 200 clean lines (`latest_output`). ## PowerShell bootstrap (`_powershell.py`)

`powershell_bootstrap()` builds the `-Command` text of each single-use Windows
shell, cold or warm, with a fixed cache directory owned by the server's user. It prepares the console and runner, reads one request from
stdin, applies its environment and workdir, and executes the command text
unchanged. It prints no runner diagnostics. `pwsh -NoProfile -NonInteractive`
uses pipes; `Read-Host`, `Get-Credential` and confirmation prompts fail rather
than waiting for an answer.

- **Request:** `powershell_request(command, workdir, changes)` returns the ASCII
  `data` and request-specific `not_run_codes`. The first line is a random
  nine-digit base code; subsequent fields are Base64 UTF-8 (workdir, command,
  then environment changes), followed by `.`. A name alone removes an environment
  variable; a name plus a space and value sets it. The bootstrap reads `$input`
  to EOF, which avoids racing PowerShell's own stdin reader. The command and its
  children receive closed stdin, never the request.
- **Nothing ran:** base code means an unreadable request, base+1 an inaccessible
  workdir, and base+2 an initial language mode that cannot host the runner.
  The language-mode guard runs before setup or `Add-Type`, consumes the request
  and exits without running user code or weakening the policy. A command that
  itself switches to `ConstrainedLanguage` still runs under that mode and its
  output/status are reported by the separate runner. An unreadable first field
  uses `REQUEST_UNREADABLE_EXIT_CODE`, treated as an ordinary exit code because a
  fixed code alone proves nothing. Only the codes drawn for this request produce
  `CommandReport.not_run`; they are not exposed to the command. A chance collision
  remains possible. `_shell_results.not_run_problem` serves foreground failure,
  background delivery and `background_tasks` consistently, with no command exit
  code or empty log presented as a result. Only an unreadable request is retryable.
- **Environment and workdir:** removals use `[NullString]::Value`; both PowerShell's
  location and the process directory follow `workdir`. A warm shell undoes its
  temporary location before entering the workdir, including the waiting drive's
  location. The command gets a fresh runspace after these changes, preserving
  cold/warm location, drive-location and `cd -` behavior.
- **Allowed setup (user requirement 1 of 2026-10-13):** console input/output code
  pages are UTF-8; PowerShell renders plain text in a host at least 200 columns
  wide (up to 199 formatted characters); UI messages use en-US. Regional number
  and date formats remain the user's. The original ConsoleHost owns its UI,
  native-program console-mode/title changes and interactive-host operations.
  Nested prompts follow the closed-stdin behavior below. No command rewrite,
  `head`/`tail`/`wc` shim or `/dev/null` replacement
  is installed. Native bytes are preserved in the log; display decoding belongs
  to the shared output/read decoder, not the PowerShell runner.
- **Parsing:** PowerShell's own parser receives the original text after setup.
  `using`, `#requires`, `param` and named blocks retain their meaning. Syntax
  errors run nothing and use the command's own positions. Incomplete input such
  as a trailing backtick produces a ParserError and exit 1, where bare
  `pwsh -Command` is silent with exit 1.
- **Execution owner:** `VBotPowerShellHost`, loaded from the validated cache or
  compiled through public `Add-Type`,
  delegates to the existing ConsoleHost while recording real native starts,
  completions and `SetShouldExit` calls. The command runs globally through
  `AddScript(text, useLocalScope: false)` in a fresh runspace. Its initial
  variables, `$PROFILE`, modules and preferences match a new no-profile shell;
  `$Error` is empty and `$LASTEXITCODE` is unset. Keeping the original host in the
  outer runspace avoids recursive host delegation and keeps runner bookkeeping
  usable when the command restricts its own language mode. No private reflection
  or security-policy bypass is used.
- **Input semantics:** ConsoleHost treats a lexical root reference to `$input`
  as an input stream. With stdin closed, its `process` block must not run. Only
  in that case an empty upstream pipeline stage reproduces the same behavior;
  `$input` in an uncalled nested function does not count. A standalone `process`
  block without root `$input` still runs once. The original text is not rewritten.
- **Nested prompt at EOF:** `$Host.EnterNestedPrompt()` evaluates the command's
  own `prompt` function once in that runspace, writes its first result through
  the original host UI, and returns because stdin is already closed. Delegating
  ConsoleHost's input loop would deadlock against the waiting outer runspace.
  This preserves the default/custom prompt, `$NestedPromptLevel`, prompt effects,
  the fallback after a failed prompt, subsequent EOF calls and a prior host exit.
- **Status (user decision 2026-10-13):** the last executed statement decides.
  Start with PowerShell's `$?` (0 or 1), then preserve the real native/script code
  when runtime evidence shows that execution determined the last statement's
  status, including a final call through a function or script block. This does
  not replace PowerShell's pipeline and control-flow semantics with Bash's.
  Native host notifications cover aliases, resolved `CommandInfo` and
  `DebuggerHidden` functions. The remaining script lookup hook resolves aliases
  to `ExternalScriptInfo`. Observation stores call frames, the prior
  `$LASTEXITCODE` object and newest `$Error`; a failed observer discards its
  evidence and cannot prevent the original host notification or user execution.
  The frame walk rejects later executed statements, later named blocks and
  `finally` work. Merely assigning `$LASTEXITCODE`, or code that never ran, is not
  a program exit. A matching `NativeCommandExitException` from
  `$PSNativeCommandUseErrorActionPreference` does not hide the actual native code;
  a later unrelated error leaves the decision to PowerShell's own status.
- **Control flow:** `exit N` and `$Host.SetShouldExit(N)` retain their actual
  precedence; a later explicit exit replaces a pending host exit. Top-level
  `return` preserves the returned native expression's status. `break`,
  `continue`, stopping errors and `throw` follow plain pwsh. The final reader
  captures `$?` before housekeeping and restores a false value without output
  or an `$Error` entry, so the user's `clean` block observes the same status.
  In particular, `end { Write-Error 'bad' } clean { exit 7 }` remains failure 1,
  not false success 0. The reader observes a completed `clean` block on
  PowerShell 7.3 and later; unsupported observation falls back conservatively.
- **Explicit fallback limits:** use plain pwsh's own status when the executed
  code cannot be attributed safely: `switch`, `ForEach-Object` script blocks,
  `Invoke-Expression`, and loops whose native call does not end every pass.
  A statement that does nothing can leave stale `$?`: `cmd /c exit 5;
  if ($false) {}` and `while ($true) { cmd /c exit 5; break }` retain plain pwsh's
  1. A pre-resolved `ExternalScriptInfo` invoked with `& $commandInfo` bypasses
  script lookup; if its only failure is `exit 5`, there is no native notification.
  That call retains plain pwsh's 1 directly, or 0 through a successful function
  call. This is a documented attribution limit, not evidence that the script
  succeeded. Replacing the script lookup hook similarly leaves unobserved script
  calls to plain pwsh; native host observation remains active.
- **Output:** the original script feeds PowerShell's `Out-Default`, merging its
  error stream as `pwsh -Command` does. Errors keep their order among formatted
  objects and their selected error view. Host/warning/information streams keep
  their normal route. Native stdout/stderr pass as bytes without added line
  buffering, also through aliases/functions. Formatter-held rows are discarded
  on explicit exit, and output/errors from `clean` after `Out-Default` ended are
  dropped, as in plain pwsh. Raw logs keep all bytes that actually reach vBot.
- **Visible runner differences:** `Get-PSCallStack` and error script stacks now
  show only the command's frames; tracing and error positions use its own lines.
  `$MyInvocation.PipelineLength` still counts the final reader (3 instead of 2
  without the optional upstream input stage),
  `$input.Reset()` succeeds on the empty pipeline input where console input
  throws, and `Get-Runspace` can see the extra runspace. The script lookup hook
  and loaded host type remain inspectable; transcript headers identify the
  actual bootstrap process command line. These are not hidden by rewriting the
  command or its output.
- **Host assembly cache:** `_powershell_host.py` owns a disposable cache under
  the server user's `~/.cache/vbot-powershell-host/`, resolved in Python before
  command environment changes. It is separate from installations and canonical
  data; no startup provisioning or package build is required. Its key includes
  the exact C# source hash, PowerShell version/home, and the loaded PowerShell
  and core runtime modules' MVIDs. A runtime or source change gets a different
  entry; the key identifies runtime compatibility, not every compiler reference.
  The initial language-mode guard runs before any cache access.
  Each `v1-<hash>.bin` is one bounded entry (at most 1 MiB), a SHA-256 checksum
  followed by assembly bytes. Only the verified bytes are loaded, without a file
  lock. Entries are disposable executable code in the user's own cache; checksums
  detect damage, not malicious replacement by that same user.
  A per-entry exclusive file handle serializes builders, rechecking the entry
  after acquisition; the OS releases the handle if a builder dies. Completed
  bytes publish with one same-directory atomic rename. Each builder removes its
  own staging files on normal completion; an abruptly killed builder can leave
  disposable staging files. Lock files remain as stable coordination names.
  An unusable cache or a lock still held after 3 s falls back to the same host
  compiled in memory, without changing command output or execution. Once a host
  is loaded, a publication failure does not trigger another compilation.
  Old keys are not loaded after an update and can be deleted with the cache.
- **Warm-up and cost:** the waiting shell prepares the host, parser, formatting,
  observer and frame walk before reading a request. Its synthetic warm-up
  runspace is discarded; the command gets a new one. No extra native program is
  launched to warm the observer. A cache hit avoids compiling the host in each
  process. The first miss still pays compilation once per source/runtime key;
  an unavailable cache retains the previous per-process cost. Explicit GC is
  not used. Interleaved Windows probes against `3b857f657` measured prepared
  processes at about 49 MB private memory instead of 86 MB, and 131 MB RSS
  instead of 176 MB. With a populated cache, fresh-process-to-exit medians were
  438-500 ms instead of 855-892 ms; prepared request-to-exit medians were
  81-118 ms instead of 124-171 ms. The initial build took 959 ms including the
  first trivial command. These are local measurements, not timing guarantees;
  they show avoided compiler work, not that Roslyn assemblies remain unloaded.

Verification includes the prior 120-case exit battery in cold and genuinely
claimed warm shells, additional execution/alias/CommandInfo/language-mode/host
probes, exact native byte streams and formatted output, and real descendant
cancellation. Durable regressions live in `test_powershell.py` and `test_shell.py`.

otherwise it names the file the working directory's package folder lacks, and no text asks to create the module); already exists; port in use (also Windows' `Only one usage of each socket address`); permission denied (Windows: a locked file, also for PowerShell's `Access to the path ... is denied`; POSIX: owner and permissions; both: ask the user for elevated rights); API rate limit. Hints that point into the output say "the files the output lists", not "above": a delivery puts `Hint:` before the output. Exit codes 126/137 get fixed hints on every host (on Windows they come through bash, wsl, docker or ssh); exit 124 gets a hint only when the command calls the `timeout` program (vBot has no timer that stops a command).

## Environment layers (`shell_environment.py`)

Built fresh for every start (about a millisecond; no cache), each layer over the previous:
1. Login base: Windows a fresh user environment block (registry `PATH` included, so newly installed programs are found); POSIX the server environment. vBot's own process variables (`PYTHONHOME`, `PYTHONPATH`, `VIRTUAL_ENV`, `__PYVENV_LAUNCHER__`, the venv on `PATH`) are removed.
2. Instance: `VBOT_DATA_DIR`, `VBOT_SERVER_PORT`, `VBOT_INSTALL_ROOT` exactly when the server has them.
3. Output: `TERM=dumb` for commands, which write to a pipe no one renders; `TERM=xterm-256color` for Terminal Sessions.
4. Commands only - unattended defaults: `GIT_EDITOR` accepts a message git prepared (rebase/merge/cherry-pick/revert `--continue`, `git revert`, `commit --amend` work as typed) and fails with the `-m` fix when the message is comments only (`commit`/`tag -a` without `-m`; lines below the `commit -v` scissors line are no message); `GIT_SEQUENCE_EDITOR` fails with the fix `$env:GIT_SEQUENCE_EDITOR = ":"` (POSIX `GIT_SEQUENCE_EDITOR=:`), so `rebase -i` never reports a rebase that changed nothing; `GIT_MERGE_AUTOEDIT=no`, `GIT_TERMINAL_PROMPT=0`, `GCM_INTERACTIVE=never`, `GIT_PAGER`/`GH_PAGER`/`PAGER=cat`, `NO_COLOR=1`, `PYTHONIOENCODING=utf-8` (Python's piped output is UTF-8, as vBot decodes it; without it non-ASCII text arrived garbled) and `PYTHONUNBUFFERED=1` (on a pipe Python would hold its output until the buffer fills or it exits; line by line, the live log, `status` and the WebUI view stay current), and `PYTHONUTF8=1` unless the login base sets `PYTHONUTF8` (Python's UTF-8 mode: `open()` reads and writes UTF-8 instead of the Windows code page; in a Swarm run on 2026-10-12 a script read a UTF-8 file as cp1252 and garbled its non-ASCII text without an error; a user's own setting stays, and the Agent's `env` overrides either). Git runs both editors through `sh -c '<editor> "$@"'`, so each value is sh builtins ending in a function that takes the file name, and `GIT_EDITOR` overrides `core.editor` (an Agent cannot work around a broken one with `-c core.editor`).
5. Commands only - `env` variables, then granted credentials.
6. Agent processes - Session scratch: `TEMP`, `TMP`, `TMPDIR` point at the own Scratch folder's `tmp/` child; `VBOT_SCRATCH_DIR` names the own folder. Shell calls resolve `ScratchAreas.folder_for` on every launch, recreating missing directories before starting a process (`tools/scratch.md`). This layer overrides explicit variables and credentials.
7. Commands only - Run identity last: `VBOT_RUN_AGENT_ID`, `VBOT_RUN_SESSION_ID`, `VBOT_RUN_PROJECT_ID`, `VBOT_UPDATE_HANDOFF` (an inherited token is always removed).

`command_environment` returns a `CommandEnvironment` in two parts. `base` is layers 1-4 without any Run identity, the same for every call until the login environment or the instance changes: the environment a Windows shell starts with, warm or cold, and what a warm shell's claim compares. `changes` is what layers 5-7 set (a value) or remove (None) over `base`; `complete()` is the whole environment, which POSIX shells start with. On Windows the changes travel in the request and apply before the command runs; credentials and the update token travel only over the shell's own stdin pipe and are never logged or put on a command line. A call that sets an empty value is the exception: `SetEnvironmentVariable(name, '')` removes the variable on .NET 8 (pwsh 7.4; .NET 10, pwsh 7.6, keeps it, verified 2026-10-12), so the request cannot carry it. Such a call starts a shell of its own with `complete()` and a request without changes (`warm=False`), whatever the pwsh version, and the warm shell keeps waiting.

Interactive Terminal Sessions use `terminal_environment()` (layers 1-3, `test_terminal_environment_has_no_command_layers`); Agent launches pass layer 6 as their overlay (`tools/terminal.md`). Operator Terminals and vBot-internal temporary files keep their own environment and lifecycle.

Scratch setup is optional: `ScratchAreas.folder_for` logs an unavailable folder
and raises `ScratchUnavailableError`; the Shell Tool skips that overlay and
launches the requested command with the normal temporary-directory environment.
Cancellation and interruption still propagate. No Scratch setup failure becomes
a failed command or a new Agent-facing reminder.

`CommandManager.busy_addresses()` returns the Sessions of pending launches and every unfinished command, including a command whose shell ended while child processes still run. Runtime includes it in Scratch retention's busy source. A warm shell carries only `base`: each command claims a fresh, single-use process and receives its own scratch variables over stdin, so no Session's paths leak to the next command (`test_command_launch.py`).

## Constraints & Gotchas

- Trim stages (`| Select-Object -First/-Last N`, or an installed `head`/`tail`): the command's output reaches vBot only after the last stage, so the log file holds the trimmed output, a `-Last` stage shows no progress, a stop loses what it held, and `-First` stops the pipeline early (the program fails at its next write and `$LASTEXITCODE` stays empty). Keeping the output before the stage would need vBot to change the command, which user requirement 1 of 2026-10-13 rules out; the hints and result texts say what the stage does instead (Failure hints, Output shaping -> Holding pipe stages).
- The raw log (user requirement 3 of 2026-10-13) is not the cleaned `output`: it can hold escape sequences (a program that ignores `NO_COLOR` and `TERM=dumb`), every state of a line redrawn with `\r`, and invalid UTF-8. `read` ends a line also at a lone `\r`, so its line numbers can differ from the cleaned lines an output marker counts. `read` shows a log as text whatever bytes it holds. It shares UTF-8/UTF-16 interpretation with `output`, including the UTF-16 some Windows programs such as `wsl.exe` write to a pipe (`tools/read.md` -> Command logs). Arbitrary unframed encoding switches are ambiguous; `read` names inferred UTF-8 transitions and accepts an explicit `encoding` for a file known to use one encoding. This changes only the text view, never the raw log.
- Regional formats: PowerShell formats and parses numbers and dates in the user's culture, as in the user's own shell (user requirement 1 of 2026-10-13 keeps it; only the UI culture is en-US). A German regional format prints `6,6` and `0,1s`, which can read as two values or a thousands separator, and parses `[double]::Parse('3.14')` as 314 (Swarm review 2026-10-11). The description names the format (Shell Tool interfaces -> Schema); `test_powershell.py` `english-messages-own-culture` checks that pwsh prints numbers and dates as vBot read them.
- Console reads on Windows: a program that reads the console directly instead of stdin blocks until it is stopped, because `CREATE_NO_WINDOW` still gives the process a console, whose input nothing writes. Examples: Python's `getpass`, `$Host.UI.RawUI.ReadKey()`, a program that opens `CONIN$`. Its call reports `running` once the wait passes, and the command continues in the background like any other. The stdin rule (stdin empty, no PTY) covers only stdin, so this case does not fail at once as the user requirement says a program that asks for input does (Review A1). User decision 8 (2026-10-12) accepts this and adds a hint: when the wait passes while the command has printed nothing and its processes are idle (`wait` -> `idle`), the running result's `next` says it may wait for console input and how to stop it and pass the answer as an option or argument (`tools/shell/agent-facing-text.md`). A silent, idle command that waits for something else (`Start-Sleep`, a lock, a slow server) gets the same conditional hint; one that printed first, such as a prompt line before `getpass`, gets none. In the same probes `input()`, `Read-Host`, `Get-Credential`, `[Console]::ReadKey()`, `choice`, `cmd /c pause` and `set /p` failed within 2 s (real `CommandManager` and `pwsh`, 2026-10-12).
- On POSIX the shell starts in a new session without a controlling terminal, so a program that opens `/dev/tty` fails at once (`ENXIO`).
- Process escape: Windows tracks the tree with a Job Object (children that break away, as the update handoff does, leave it). Linux guarded launches retain descendants under a child subreaper, including `setsid` and double-fork; they remain reported and stoppable after the shell exits. The root exit arrives on a separate private pipe so ordinary command-end and quiet-leftover behavior stays unchanged (`tools/os-processes.md`). Other POSIX launches retain session-based tracking.
- Child exit codes come from Job notifications on Windows, which are best effort: a missing `failed_programs` entry proves nothing. POSIX reports no child exit codes.
- Env grants are not a sandbox: a command can print or send an injected credential. The shell runs with the server user's full rights.
- POSIX commands get the server's environment, not a login shell's `PATH`.
- Windows startup and memory costs are measured under PowerShell bootstrap -> Warm-up and cost. A call starts its own shell when the warm process is unavailable, already claimed, still starting, or incompatible with the start environment; commands never share a used shell. Pipes add no ConPTY startup.
- A warm shell starts before its call, so its own startup sees only the base environment: variables set through `env` or credentials that configure pwsh itself at start (`DOTNET_*` runtime settings, `POWERSHELL_TELEMETRY_OPTOUT`) reach the programs the command starts but not the pwsh that runs it. `PSModulePath` set through `env` replaces the value pwsh extended at start with its own module folders (user, Program Files, `$PSHOME`), so the command finds modules only in the folders it names (probe 2026-10-12). A shell started for its call behaves the same, since it starts with the same base; only a call with an empty `env` value starts with its whole environment.
- Capacity: at most 64 unfinished commands server-wide (`COMMAND_MAX_LIVE`), independent of the interactive terminal limits (4 per Session, 32 global).
- A background command stays queryable (`list`, `status`, the WebUI) while any of its processes runs and for 30 minutes after the last one ended, then is forgotten; its log file is kept 72 h.
- A Sub-Agent's background command delivers to the Sub-Agent Session like any completion, also after its Run ended; what then reaches the Parent is the Sub-Agent domain's concern (`subagents.md`).
- Old stored results with `process_id`/`delivery: "automatic"` or a `terminal_id` are plain rows; nothing folds them.
