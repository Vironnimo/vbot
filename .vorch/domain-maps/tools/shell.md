# Shell Tool (`bash` / `powershell`) and `background_tasks`

Runs one host shell command per call, in a new process without input or terminal, returns its clean output with an honest outcome, and lets a command that runs longer continue in the background; `background_tasks` lists, checks and stops the caller's background commands and Sub-Agents.

## Boundary

> User requirement (stated repeatedly; recorded 2026-10-11): The shell Tool (`powershell` on Windows, `bash` elsewhere) runs one-shot commands, like Claude Code's Bash tool. A command never receives input and runs without a terminal, so a program that asks for input fails at once instead of waiting. A command that runs long, a server included, continues in the background and delivers its result when it ends. The Agent lists, checks and stops its background commands with `background_tasks`, which never waits for output and never gives input. Nothing gives a command input or turns it into a terminal; programs that need input or a terminal run only through the terminal Tool. Changing this boundary needs the user's explicit approval, also in a rebuild.

User decisions of 2026-10-11, in order:
1. The shell Tool keeps its names: `powershell` on Windows (PowerShell 7 as today), `bash` elsewhere. No waiting for output lines anywhere; no `process` Tool under that name.
2. `timeout` is how long the call waits: omitted 120 seconds, at most 600. When it passes, the command is not stopped but moves to the background, and the result tells the Agent it runs longer than expected, so it can let it run or stop it. No timer stops a command.
3. A small companion Tool with actions `list`, `status` and a stop action, so the Agent can see and stop its background commands. No wait, no input.
4. A Parent Agent sees the background commands and terminals of its Sub-Agents (all depths) in `background_tasks list` and `terminal list`, each marked with the Sub-Agent it belongs to, and can check and stop those commands. Every result about a background command names the file that holds its complete output, so the Agent can read it directly.
5. The companion is `background_tasks` with `list`, `status`, `stop` and one `id` field, for background shell commands and Sub-Agents alike (as Claude Code's `TaskOutput`/`TaskStop` cover shells and agents). `subagent` keeps only `run` and `send`; its `list` and `cancel` move to `background_tasks`. No `type` parameter: the id's prefix (`cmd_`, `sub_`) tells the kinds apart, and list rows carry `type`.

History: 2026-09-09 (8edafd3d5) closed the shell's stdin and removed `process` input. The rebuild of 2026-10-04 (1a2b28e2e) ran commands in hidden ConPTY terminals with an open stdin, and later commits added idle hand-offs, input into commands, driven commands and a timeout stop after input; none of that was approved. The one-shot rebuild of 2026-10-11 reverted that behavior and kept the rebuild's gains for non-interactive commands: head-and-tail output with the complete log file, process-tree tracking and kill, processes left running reported, failed child programs, the PowerShell wrapper, failure hints, the unattended environment, the update handoff, and Sub-Agent delivery at every depth. The tests that guard the requirement are named under Tests.

Agent-facing wording stays in the Tools.
- `core/tools/background_tasks.py` owns the `background_tasks` schema, texts and result layout; `_background_tasks_arguments.py` reads its dialects. It dispatches on the id prefix to `CommandManager` (commands) and to the `SubAgentTree` the Runtime passes (`SubAgentCoordinator`, `subagents.md`), which keep their behavior.
- `core/tools/process_tree.py` (process-tree tracking: liveness, CPU time, child exit codes, kill) is shared with the interactive terminals. The terminal domain (`tools/terminal.md`) holds no command code: no command runs in a Terminal Session, and `terminal` refuses `cmd_` ids. Add follow-up capabilities for commands to `CommandManager` and `background_tasks`, never to the terminal subsystem.

## Terms

### Background command
A shell command that runs on after the call that started it returned: started with `run_in_background`, still running when the call's wait passed, or moved to the background by the user. It has a `cmd_` id, is listed by `background_tasks list` and in the WebUI Activity panel, raises `command_status_changed` events, and delivers its result once as a new message when it ends (D7 below). A command that ended in its call while processes it started still run is a background command too, without a delivery: `background_tasks` lists it, and the WebUI shows it as `processes still running` until those processes end. A foreground command (still inside its call) is unlisted. Not a Terminal Session, and not every background task: `background_tasks` also covers Sub-Agents.

### Command end
A command ends when its shell exited and every process the shell left running ended or went quiet: no output, no new process and at most 0.15 s CPU for 2 s (`COMMAND_LEFTOVER_QUIET_SECONDS`, `IDLE_CPU_SECONDS`); output after the shell's exit is read for at most 1 s (`COMMAND_DRAIN_SECONDS`). An end caused outside vBot, such as `taskkill /T` on the shell, is an ordinary end. When the process tree cannot be read at the shell's exit, the command does not end: its exit code is kept, it counts as running (so its call moves it to the background, and it is listed and stoppable), and the next process-tree poll that reads the tree decides (`test_processes_that_cannot_be_inspected_at_the_exit_keep_the_command_running`). Until then the call waits, the command reports `running`, and nothing is delivered. Reason: PowerShell does not wait for a GUI-subsystem program (for example a tray app's exe used as a CLI), which prints its answer after the shell exited; ending at the shell's exit returned empty output and sent Agents into repeated waits (Sessions, 2026-10-07: 11 such results). A server the command started waits quietly, so it ends the command within about 3 s and is reported as still running.

## Shell Tool interfaces

- Registry name `bash` (`SHELL_TOOL_NAME`); the Model sees `powershell` on Windows and `bash` elsewhere (`SHELL_MODEL_NAME`, `tools.md` -> Model Tool names). Registration: `register_shell_tool(registry, command_manager, credential_resolver=..., prompt_blocks=..., update_handoffs=..., projects=...)`, family `execution`, summary `Run shell commands.`; Runtime bootstrap passes the `ProjectStore`. It also declares the dynamic `tool:bash` Prompt Block `## Shell Environment Access` (empty without permanent Agent env grants; text from `format_shell_env_usage`, shared with Skill env guidance).
- Schema (`SHELL_TOOL_PARAMETERS`): one open flat object requiring `command`, with optional `description`, `workdir`, `timeout` (number, minimum 0, default 120, no schema maximum: the handler caps it and some Provider adapters reject extra keywords), `run_in_background` (boolean) and `env_keys`. Accepted but unadvertised: `timeout_ms`, `env`, `mode`. The definition names no other Tool, so it is the same for every Tool set; what happens to a long command, and the calls that follow it up, the results say when it happens. Sub-Agents (Session depth >= 1) get the same definition and behavior, `run_in_background` included (user decision 2026-10-05). A text names `background_tasks` or `terminal` only when the Agent can call it (`ToolContext.can_call`, so also as an On-demand Tool it has not loaded, since an exact call works without loading) and any other Tool only when it is offered (`named_tools`).
- Argument tolerance (`_shell_arguments.py:normalize_shell_arguments`): `cmd`/`script`/`commands` and argv arrays (joined into one host command line, each item one argument: on Windows a bare word or a `powershell_literal`; a host-shell `-c`/`-Command` wrapper is unwrapped), OpenAI `local_shell` `action` objects, `cwd`/`directory`/`working_directory`, `timeout_ms`/`timeout_seconds`, title-like description fields. `run_in_background` is canonical: `mode` (`foreground`/`background` and their spellings such as `fg`, `bg`, `async`, `detach`), `background`/`is_background` flags and a zero yield field (`yieldMs`, `yield_time_ms`, `yield_after`, `background_after_seconds`) map onto it; fields that ask for both fail with the conflict, and an unknown `mode` value fails naming `run_in_background`. Fields that cannot have an effect run the command with a note instead (`NO_EFFECT_FIELDS`, `no_effect_notes`): `pty`/`tty`/`interactive` true, `stdin`/`input` with text, a non-zero yield field; false or empty ones are dropped, and so are requests vBot always satisfies or that only shape output (`notify_on_complete`, `login`, `max_output_tokens`, `dangerously_disable_sandbox`). Calls asking for another effect (`elevated`, escalated sandbox permissions, `require_user_approval: true`, a non-empty `user`) fail before running with the fix.
- `workdir`: absolute or relative to `effective_cwd`; a missing directory fails naming similar directories and the fix (pass an existing directory, or omit `workdir`); a file fails saying so, with the fix to pass the directory it is in or omit `workdir`; a missing working directory with `workdir` omitted names only the first. Unadvertised `project:<project-id>` runs in that Project's directory (`_workdir.project_workdir`, shared with `terminal`; the Projects block teaches each Project's path); its failures (`ProjectWorkdirError.code`: `invalid_workdir`, `project_not_found`, `project_unavailable`) are `invalid_arguments` failures here, each naming a next step.
- `timeout` is how long the call waits for the command, in seconds: omitted 120 (`SHELL_DEFAULT_WAIT_SECONDS`), at most 600 (`SHELL_MAX_WAIT_SECONDS`; a larger value is read as 600 with a note), `0` read as omitted with a note. A value of at least 10,000 that is a whole thousand is read as milliseconds with a note; disagreeing `timeout`/`timeout_ms` fail; a negative one fails. With `run_in_background` it is ignored. No timer ever stops a command (user decision 2).
- `env` (unadvertised) sets plain variables; vBot never passes a credential value written in the call. Credentials come only through granted `env_keys` names resolved server-side. An ungranted `env_keys` name the server process itself has passes with a note; an unknown one fails, naming the granted keys.
- Host shell (`_shell_argv`, resolved against the call's fresh environment's PATH off the Event Loop): Windows `pwsh -NoProfile -NonInteractive -Command <text>`, where `_powershell.powershell_command(command)` builds `<text>` (PowerShell wrapper below); a command line over 32,000 characters fails before running, naming the room left for the command (about 25,400 characters, or about 23,300 when the command can spell `null`; PowerShell wrapper below) and the save-to-`.ps1` fix. POSIX `bash -c <command>`. A missing `pwsh`/`bash` fails with "Ask the user to install it". These failures are `command_not_started` (not `invalid_arguments`), because the command is right and the host cannot run it.
- Start failures (`tool_failure`; nothing ran, the update token is released): `command_limit` (retryable) when vBot already runs 64 commands, naming `background_tasks` list and stop when the Agent can call it, otherwise to run again once one of its background commands exited; `command_not_started` when the turn was cancelled or vBot shuts down, when the `workdir` was removed after the call was checked (the missing-directory text), or when the shell could not start. The last case is logged at WARNING (`Starting a shell command failed`) and named by the state the operating system error reports (`_launch_problem`), never by the error's own message, which is in the host's language and names no next step: no operating system error, out of memory or process resources (`ENOMEM`, `EAGAIN`, `EMFILE`, `ENFILE`; Windows errors 4, 8, 14, 1450, 1455; naming `background_tasks` list and stop when callable), and any other error with its number are retryable and say to tell the user if it fails the same way; a full disk (`ENOSPC`, `EDQUOT`; Windows 39, 112) and denied access (to the `workdir` when the shell starts, to vBot's data directory when the output file is created) are not retryable and say to tell the user (`test_a_shell_that_cannot_start_names_the_state_instead_of_the_raw_error`).
- Results (`tool_success` data; `ok: true` for every started command, also for a non-zero exit), fields in this order and omitted when empty:
  - ended: `status` (`exited` | `stopped`), `exit_code` (exited, when known; a stopped command has none, because its code is vBot's kill, not the program's), `stopped_because` (stopped), `output`, `failed_programs` (direct child programs of the shell that exited non-zero before any stop, Windows only, such as `git.exe exited with code 128`; omitted when exactly one failed with the `exit_code` of a command that exited by itself, which it would only repeat), `hint` (non-zero exit with a known failure shape, never when vBot stopped the command), and for processes the command left running `command_id`, `still_running` (`name (pid N)`) and `next` (the call that stops them). Such a command is listed as a background command without delivery, so the user and the Agent can see and stop what remains; its result names the log file only when the output was cut.
  - running: `status: "running"`, `command_id`, `output` (the newest output only, below) and `next`, which says why the call returned (the Agent's timeout, the default 120 seconds, the user's move after how long it ran, or `run_in_background`), names the live log file, says the result arrives as a new message, forbids starting it again or sleeping and polling for its result, and names the exact stop call. Every command that outlives its call delivers its result. Durations read `45 seconds`, `14 minutes 5 seconds`, `1 hour 2 minutes` (`duration`, singular for 1).
  - `notes` lists how the call was read leniently (timeout 0, over 600, milliseconds, inherited env key, fields without effect).
- Output shaping (`command_output_text`, `running_output_text`): the transcript holds the clean output as final lines (first 40 and last 80, whole up to 140 lines with `COMMAND_TAIL_SPARE_LINES`, so it never leaves out fewer than 21 lines). A result keeps whole lines within 4,000 head and 8,000 tail characters, where an end that needs less gives its room to the other, shows output that exceeds the 12,000 characters by at most 1,000 whole (`SHELL_OUTPUT_OMIT_MIN_CHARS`), and cuts single lines at 2,000 characters. Reason: markers for 2 to 5 lines saved less than the read of the log file they invite (Swarm review 2026-10-11: 3 such results). A running command's result shows only the newest 20 lines within 4,000 characters (`SHELL_RUNNING_OUTPUT_LINES`/`_CHARS`) after a marker counting the earlier lines (`test_running_output_is_the_newest_lines_and_its_log_file_has_every_line`). Every marker names the log file when there is one (without Storage it only counts what was omitted). When the command pipes into a stage that passes nothing on before its input ends (`Select-Object -Last`, `tail`, `Sort-Object`/`sort`, `Group-Object`, `Measure-Object`, `wc`, `Out-String` without `-Stream`; `_holding_stage`, the last such stage of the command text), a running result, and a stopped result or delivery, ends its `output` with a line naming that stage (`tools/shell/agent-facing-text.md`).
- Live output: while the call waits, the Run event `tool_call_output {tool_call_id, command_id, output}` carries the newest 40 clean lines at most every 0.5 s while output arrives (`COMMAND_PROGRESS_LINES`/`_SECONDS`); each replaces the previous one (transient, never persisted).
- Display: `shell_display_parts` shows the `description` or the command (copyable either way); `shell_detail_blocks` shows the command, the result's `data.output`, warnings for a stop, the non-zero exit code of an `exited` result and failed programs, an info notice `Hint: ...`, and for a running result the info `The command continues in the background.` The WebUI renders a `stopped` result as a cancelled row, not a success (`webui/chat.md`).

## Execution lifecycle

1. `_parse_call` validates and resolves everything before anything starts: `workdir`, the wait, env, credentials and the no-effect notes.
2. An update handoff token is issued when the call has a result-persistence boundary; it stays claimable exactly until every process of the command ended (`wait_finished`).
3. One worker builds the fresh `command_environment` (below) and the shell argv; PATH searches probe the filesystem and stay off the Event Loop. The executable is not cached across calls. `CommandManager.launch` starts the command in the foreground.
4. `run_in_background`: `to_background(deliver=True)` at once and the running result. Otherwise `wait(seconds)` until the command ended or the wait passed; the user can move the call to the background earlier (`background_registration_hook`, set by Chat's Tool dispatch). Per-call cancellation stops the command (`run_cancelled` when the Run was cancelled, else `user`) only until the call hands it to the background: from then on the call's cancel callback does nothing, so a Run cancel or a stop of the call leaves a background command running (D7; `test_the_user_stops_the_command_or_moves_it_to_the_background`).
5. Ended with no process left -> the ended result. Ended with processes still running -> `to_background(deliver=False)` and the ended result with `still_running`. Still running -> `to_background(deliver=True)` and the running result.

## CommandManager contract

- `launch(owner, argv, *, command, description, cwd, env, origin_run_id, formatter, execution_owner, on_output) -> CommandHandle` (`cmd_` id from `new_id("cmd")`, the shell's PID). Refuses with `CommandNotStartedError` when the origin Run was cancelled, the execution group closed or vBot shuts down, `CommandCapacityError` (retryable) when 64 commands are unfinished (`COMMAND_MAX_LIVE`, launches in progress included, separate from the terminal limits), and `CommandLaunchError` when the process cannot be started or tracked. A cancelled caller leaves no command behind.
- Transport (`_command_launch.py`): stdout and stderr share one pipe (order kept); stdin is the null device on POSIX and an empty pipe without a writer on Windows, where the null device is a character device that programs take for a console; no PTY is attached, so `isatty()` is false for all three and a program that reads stdin gets EOF at once. On Windows the process still has a console: `CREATE_NO_WINDOW` gives it a hidden one (`conhost.exe`) that nothing writes to (Constraints & Gotchas). On POSIX it has none. Windows creates the shell `CREATE_SUSPENDED | CREATE_NO_WINDOW | CREATE_NEW_PROCESS_GROUP`, assigns it to a kill-on-close Job Object, then resumes it, so no process escapes in its first instruction; the windowless console host (`conhost.exe`) in the Job is ignored by end detection. POSIX starts the shell in a new session through the guarded launch (`tools/os-processes.md`). A process that cannot be tracked is killed and not started.
- Output host: cleaning costs CPU time in proportion to what a command prints, so each command's `OutputCleaner` runs on a worker of the manager's output host (`InterpreterHost`): a thread that owns a subinterpreter with its own GIL, loaded with only `_command_cleaning.py` and `_hosted_objects.py`. Workers start one per `prepare()` (called through `run_blocking` at each launch) up to `DEFAULT_WORKERS` = min(4, half the CPUs, at least 1); a `prepare()` while no worker runs yet and every allowed one is still starting waits for that start (a `threading.Condition`), so commands launched together right after server start all get workers (re-review 2026-10-12: the second of two parallel launches on a one-worker host cleaned on the Event Loop for its whole life). Commands are assigned to workers in turn, and each command's calls stay ordered on its worker. The reader awaits each 64 KiB chunk's `feed` before it reads the next, so a command that prints heavily has one chunk in its worker's queue and delays another command by at most that chunk; Terminal screens use their own host and share no workers. Each `feed` returns only the transcript changes (head lines, the newest lines, the line count, the current line), which `CommandOutput` keeps, so `transcript()` and `latest()` read on the Event Loop without waiting for the worker. A subinterpreter that cannot start (WARNING log) stops the host from adding workers; once none started and none is starting, the host runs its objects inline, on the Event Loop, and says so once at WARNING when it hands out the first such object (`test_interpreter_host.py`). A worker's start always resolves, also when `concurrent.interpreters` cannot be imported, so nothing waits on it forever. Tests use `InterpreterHost.in_process()`. `CommandManager(output_host=...)` owns the default host and closes it at `aclose`/`close` after the output work already queued; a host closed during a launch refuses it (`CommandNotStartedError`, "vBot is shutting down"). Errors from a hosted call arrive as `RuntimeError` with the original message only. When cleaning a chunk fails (a cleaner bug, or the host closed under the command), the reader logs it once at ERROR and keeps reading the pipe, discarding the rest of the output, so the command never blocks on a full pipe; the transcript and the log file end at the failure, `CommandTranscript.processing_failed` is set, and the result says so after the last line (re-review 2026-10-12, lifecycle note "full pipe after a cleaner error"). The fix's probe (2026-10-12, Windows, 20 MB of short lines) measured Event Loop lag p99 106 ms with cleaning on the loop and 9-14 ms after, against 7 ms for an idle loop.
- Output cleaning (`_command_cleaning.py`, rules in its module docstring): incremental UTF-8 decoding (invalid bytes become U+FFFD); escape sequences removed (CSI, two-character sequences, OSC/DCS/SOS/PM/APC strings, also in C1 form; parsing is bounded, so an unterminated sequence cannot hide output); an ESC that cannot start a control shows as the text `\x1b`; `\r\n` ends a line; a lone `\r` restarts the line (a redrawn progress line keeps its final state); a backspace erases the character before it; other C0 controls and DEL are removed, tabs stay. Lines longer than 65,536 characters keep only their beginning in memory and are written whole to the log file. A chunk with no control characters other than `\r\n` is split into lines in bulk and written with one call.
- Log file: a private file in Storage's temp category `commands` (`artifacts/temp/commands/tmp_<12 base32>.log`, 72 h retention after the command finished, mode 0600 on POSIX; `storage.md`). The manager opens it with `os.open` and the cleaner writes it through that descriptor on its worker. Completed lines are appended at once and flushed at least every second (`COMMAND_LOG_REFRESH_SECONDS`); the line still being written shows at the end at each flush. Without temporary-file storage a command has no log file.
- `wait(id, *, seconds) -> "ended" | "deadline"`: event-driven; cancelling it changes nothing. `wait_finished(id)`: every process ended.
- `to_background(id, *, deliver)`: lists the command (status events start) and, with `deliver`, arms its delivery; a command that had ended already delivers nothing (the caller reports the result).
- `stop(id, reason) -> CommandReport`: kills the whole tree; Windows terminates the Job, POSIX sends SIGINT to the process group and kills after 3 s (`COMMAND_STOP_GRACE_SECONDS`). The first reason wins and fixes the outcome. A stop after the end kills the leftovers and keeps the outcome; a finished command is returned unchanged. Every stop fixes the count of failed child exits before its interrupt or kill, also after the end, so exits the kill causes never count as the command's failures, even when a poll of the leftovers records them before the kill is confirmed (re-review 2026-10-12, lifecycle note on kill exits during a terminate). A kill must be confirmed within 5 s (`process_tree.py`); otherwise `CommandStopError` names the surviving processes, the command stays live and listed, and a later stop retries. Unless the command ended meanwhile (the interrupt before the kill can end it; it then stays `stopped`), the failed stop gives its reason and exit count back: the command runs on as if not stopped, and an end it reaches by itself reports `exited` with its exit code and delivers its result; a `scope` stop's withdrawal of the delivery stays (re-review 2026-10-12, texts finding 2: after `stop_failed`, such an end read "you stopped it.", without exit code or delivery). An `agent` stop suppresses the delivery only while it holds the reason.
- Reasons: `agent` (the command's own Agent, through `background_tasks`), `parent` (an ancestor Session's Agent), `user` (one command, from the chat), `run_cancelled` (the Run whose call waits for it was cancelled), `shutdown`, `scope` (Stop all, a Sub-Agent stop, removal of the Session, Agent or Project, an Extension execution group's close).
- Reads: `report(id)`, `latest_output(id, lines)` (at most `COMMAND_RECENT_LINES` = 200, the line being written included), `status(id)` (`running` | `completed` | `failed` | `stopped`; None for an unknown or foreground command), `commands(owners)` (the background commands of those Sessions, newest first, each naming its Session; foreground ones are not listed). `acknowledge(id)`: a persisted Tool result showed the end, so a delivery not yet handed over is withdrawn; one whose delivery TriggerService already claimed is delivered once, as submitted. Any caller finds a command by id alone; the caller decides which Sessions it may act for.
- Lifecycle: `cancel_run(run_id)` stops only the Run's commands still inside their call and refuses new launches for it, `release_run(run_id)` forgets that marker (Chat's Run cancel callback and completion observer, `chat/run-execution.md`); `close_scope(owner)`, `close_agent_scope(agent_id, project_id)`, `close_project_scope(project_id)` stop with reason `scope` and return how many unfinished commands they stopped; `transfer_scope(source, target)`, `transfer_agent_scope(agent_id, new_agent_id)` move commands with their Session; deliveries follow, and a result already submitted to the old Session and not yet delivered is withdrawn there and submitted with the same body to the new one, unless its delivery already claimed it (`test_transferred_commands_deliver_to_their_new_session`); `has_execution_work(owner)` and `close_execution_group(extension, group_id, epoch)` serve Extension execution groups. A lifecycle scope close logs an unconfirmed kill (`A command survived the close of its scope (...); it stays listed`) instead of raising: the lifecycle step goes on, and the command stays live and listed for a later stop.
- `shutdown()` (Runtime shutdown step `commands`, before Trigger delivery closes, `runtime.md`): refuses new launches and stops every unfinished command with reason `shutdown`; background ones submit their stopped result. It raises `CommandStopError` after every command was stopped or tried. `aclose()` (step `command_processes`) waits for launches in progress, kills every remaining command off the Event Loop and in parallel (`CommandRecord.kill_and_release` through `run_blocking`), awaits the commands' tasks, closes its own output host and withdraws undelivered results (`test_aclose_kills_the_remaining_commands_off_the_event_loop_together`). A command whose kill was not confirmed is released all the same: its tasks are cancelled and its surviving processes logged at WARNING (`name (pid N)`), so Runtime stop never waits for them (re-review 2026-10-12, lifecycle finding 2: `aclose` waited forever for such a command's reader and supervisor); `close()` is the fallback without an Event Loop, each kill blocking the calling thread (`kill_now`). Both raise `CommandManagerError` naming the commands whose kill was not confirmed. `start()` runs the sweeper that forgets a command 30 minutes after its last process ended (`finished_at`; `COMMAND_RETENTION_SECONDS`, checked every 60 s).
- `add_changed_callback(callback)`: called with a background command's id when it moves to the background, ends, when a process it left running ends (after the end each process-tree poll updates `still_running`), when it finishes, and when it is forgotten (`status` is then None); the server bridges it into `command_status_changed`.

### Deliveries (D7)

- One delivery per command that outlived its call, when it ends, through `TriggerService.submit_completion(notice_id="command:<id>", origin_run_id=..., body=formatter(report), project_id=..., execution_owner=..., wake=True)`. It joins the Session's active Run at its next request or starts one, also in Sub-Agent Sessions at every depth (user decision 2026-10-05), and survives a restart like every completion. A delivery to a closed execution owner (`RunAdmissionBlockedError`) is dropped at DEBUG.
- No delivery: a stop by the command's own Agent (`agent`: the stop result is the outcome), a `scope` stop (withdrawn), a command whose end a persisted `background_tasks` status or stop result of the owning Session already showed (`acknowledge`), and a command that ended in its call (its result is the outcome). A withdrawal only takes effect before TriggerService claims the delivery (`automation.md` -> Completion coordinator): a claimed result is delivered once, and the command side never cancels the delivery itself (it awaits it through `asyncio.shield`).
- Delivered: an end on its own, a kill from outside vBot (ordinary end with the exit code it got), `user` ("the user stopped it."), `parent` (to the command's own Session, whose Agent did not see the stop), and `shutdown` ("vBot shut down.").
- Run cancel stops only commands still inside their call; background commands keep running and deliver. Stop all, `/stop all`, stopping the owning Sub-Agent, Session/Agent/Project removal and an Extension group's close stop without delivery.
- The delivery names Tools from a snapshot taken at the call (`delivery_names`: `HINT_TOOL_NAMES` plus `background_tasks`), since it outlives the call.

### Sub-Agent work and log files (D10, D11)

- `background_tasks` covers the commands of the caller's Session and of its descendant Sessions (Sub-Agents at every depth), never a parent's or a sibling's. A descendant's command row carries `subagent`, the id of the Sub-Agent whose Session runs it; `status` and `stop` accept it, and an ancestor's stop uses reason `parent` (delivered to the owning Session) while the ancestor gets the stop result with `stopped_because: "you stopped it."` and a note that the Sub-Agent receives a message. A later `status` or repeated `stop` from above tells the reason from the reader's side: `Sub-Agent <id> stopped it.` or `an Agent above Sub-Agent <id> stopped it.` (`stopped_because(..., subagent=...)`). `terminal list` and `status` mark a Sub-Agent's terminal the same way (`tools/terminal.md`).
- Every result about a background command names its log file when Storage provides one: running shell results (`next`), `background_tasks` rows (`log`), status and stop results, and the delivery (`The complete output is in <path>.` unless an output marker already names it). A command that ended in its call names the file only when its output was cut, because that is every ordinary call.

## `background_tasks`

- Registration: `register_background_tasks_tool(registry, command_manager, *, subagents=None)`, family `execution`, `catalog_visible=False`, open input schema, `activation: follows` with `activation_source=("bash", "subagent")`: active exactly while either source is, also in a fixed Tool set, and absent from `tool.list`, so the Tool picker and the Project Tool Whitelist show only its sources; a persisted denial of `background_tasks` itself still vetoes it (`tools.md` -> Policy resolution, as for `edit`/`write` in `tools/edit.md`). Not always loaded; results name its exact calls, which work without loading.
- Schema: `action` (`list` | `status` | `stop`, required) and `id`. Unadvertised `action_missing`, `input_action`, `message_content` and `no_effect_fields` are set only by the normalizer.
- Dispatch by id prefix: `cmd_` -> `CommandManager`, `sub_` -> the Sub-Agent branch (`SubAgentTree`: `subagents(caller)`, `running_work`, `stop_subagent`; behavior in `subagents.md` -> `background_tasks` list, status and stop; Tool-side tolerance in `tools/subagent.md`). A `term_` id fails `not_a_background_task` with the `terminal` status call; a `ses_` id that is the Session of exactly one Sub-Agent below the caller (the whole tree, within a takeover too) is read as that Sub-Agent with a note. A takeover is a boundary (`SubAgentState.within_takeover`, `subagents.md`): the caller keeps the taken-over Sub-Agent to list, check and stop as a whole, but a background command of its Session or of a Session below it, and a Sub-Agent below it, fail `subagent_taken_over` (nothing is stopped; the commands run on for the user). Any other id, or one outside the caller's tree, fails `task_not_found` naming up to 5 of the caller's running tasks: Sub-Agents that work or are queued, and commands that run or left processes running.
- `list`: `tasks`, Sub-Agents first, breadth first (at most 1,000), then background commands newest first. Command row: `id`, `type: "command"`, `command` (the label: the description, else the first line, at most 120 characters), `subagent` (a descendant's command), `status` (`running` | `exited` | `stopped`), `exit_code` (exited, when known; never on a stopped row), `still_running` (`name (pid N)` of the processes an ended command left running), `runtime`, `log`. Sub-Agent row: `id`, `type: "subagent"`, `title`, `agent_id`, `session_id`, `parent_id` (below a direct Sub-Agent), `status`, `last_tool` (working), `activity_file`. Rows stop at a takeover: neither the Sub-Agents below a taken-over one nor the commands of its Session and theirs are listed. A note when empty, and a note against polling while one of the caller's own commands runs or one of its direct Sub-Agents works or is queued (a deeper Sub-Agent's answer goes to its own Parent).
- `status` of a command: running -> `status`, `command_id`, `subagent`, `output` (newest 20 lines) and `next`; ended -> the ended shell result, led by `status`, `command_id` and, for a Sub-Agent's command, `subagent`, plus the log file sentence in `next`, and for the caller's own command an acknowledgement once the result is persisted. Both add a display result naming the command by its label, since the call names only the id.
- `stop` of a command: stops with reason `agent` (own) or `parent` (a descendant's) and returns the ended result; an ended command succeeds with a note (`nothing was stopped`, or the leftovers it stopped). An unconfirmed kill fails `stop_failed` (retryable) naming the processes that still ran when vBot stopped waiting, or saying that whether they ended is unknown.
- It never waits and never writes input or messages: `wait`/`await`/`poll_until` fail in the normalizer. Message and input actions are refused by the handler (`invalid_arguments`), since only it knows which Tools the Agent can call: a message action with a `sub_` id names the `subagent` send call, with the message the call carried, only when `subagent` is callable, and otherwise the Tool's own actions; input actions, and message actions without a `sub_` id, name `terminal` only when callable. Fields of other harnesses' output Tools run the call with a note that they have no effect (`no_effect_fields`): wait fields (`block`, `wait`, `timeout`, `timeout_ms`, `timeout_seconds`) and filter fields (`filter`, `grep`). A value that asks for nothing (false, 0, empty, `no`, `none`, `null`, a placeholder) is dropped silently, and `block: false` drops the wait fields with it.
- Argument tolerance (`normalize_background_tasks_arguments`): `id` aliases `task_id`, `command_id`, `subagent_id`, `work_id`, `shell_id`, `bash_id`, `process_id`, `proc_id`, `job_id`; `terminal_id`, `session_id` and `agent_id` count as `id` only when their value has a prefix this Tool reads (conflicting values fail). Action synonyms: `ls`, `all` -> list; `output`, `log`, `logs`, `check`, `get`, `poll`, `read`, `show`, `inspect`, `info` -> status; `kill`, `cancel`, `terminate`, `end`, `abort`, `halt`, `interrupt` -> stop. A missing action with an id runs `status` with a note naming the stop call (a stop is never guessed), so Claude Code's `TaskOutput {task_id, block, timeout}` and `BashOutput {bash_id, filter}` show the status; a list of one id is that id, several fail. Harness Tool names (`core/tools/model_names.py`): `bashoutput`, `killshell`, `killbash`, `taskoutput`, `taskstop`, `process`, `shelljobs`, `backgroundcommands`, `backgroundtasks` -> `background_tasks`.
- Display: the action and the id; details show listed tasks as a `results` block (title or label, then id, status, runtime or last Tool), one Sub-Agent's or command's state as one result, a stop as a notice, and a command's output with a running notice or, for an `exited` command, a non-zero exit warning.

## Server and WebUI

- `command_status_changed {command_id, session_id, status, still_running}` app event, bridged from the change callbacks in `server/_app_lifecycle.py` (`_register_command_status_bridge`): published once per change of a background command's `status` or `still_running` (processes it started still run after its shell exited), so also when the last such process ends; a foreground or forgotten command publishes nothing. `session_id` names the command's Session, since a fork shares its source's History but not its commands. The bridge is removed only after the Runtime's shutdown, so the stops of the shutdown are published too (`server/events-and-reconnect.md`).
- `chat.history` returns `background_command_statuses` (command id -> `running` | `completed` | `failed` | `stopped`) and `background_commands_still_running` (the Session's commands whose shell exited while processes they started still run). `background_command_statuses(records)` folds durable `bash` and `background_tasks` results that carry a `command_id` (`running` never overrides a shown end; `exited` gives `completed` for exit 0, else `failed`) and delivery Notes (`COMMAND_STATUS_NOTE_MARKER` = `The background command `: `completed` for exit 0, `failed` for another or an unknown code, `stopped`). The server (`_current_command_statuses`) keeps the folded ends, sets every background command of the Session that `CommandManager.commands` knows to its current status (also one whose hand-off result is not saved yet because its Tool batch still runs), and drops a recorded `running` that is not one of them: that command ended without a delivered result (vBot restarted), or it belongs to another Session, as in a fork. Folding a later range onto an earlier fold equals folding both. An `after` read carries the appended records' statuses plus those of the Session's live commands, while the still-running list is always complete; a `before` page and an `after` read with nothing appended carry neither field. Only this marker is read (Generation 1): the about 4 terminal-era deliveries have no status, and the WebUI shows such commands as ended.
- `chat.stop_command {session_id, command_id}` -> `{stopped, status}` stops one background command with reason `user` (its Agent receives the stopped result), or the processes a command that already ended left running (it keeps the status it ended with, and nothing more is delivered). `stopped` is false when nothing of it ran any longer or another stop came first; `status` is the command's status afterwards. `chat.command_output {session_id, command_id}` -> `{status, still_running, output}` with the newest 200 clean lines. Both fail `command_not_found` (`No background command <id> runs or ran recently in this Session.`) for an unknown or forgotten id, another Session's command, and a command still inside its call (`server/rpc/chat_methods.py`).
- `chat.stop_all` stops background commands through `SubAgentCoordinator.stop_tree` (no delivery); `chat.cancel_tool_call` stops a foreground command (reason `user`).
- WebUI (`webui/chat.md`): a `bash` row whose result has a `command_id` represents the background command (a `running` result, or an `exited`/`stopped` one whose command left processes running), with a stop control (`chat.stop_command`), an output view (`components/chat/CommandOutput.svelte`, `chat.command_output` every 2 s while the command or the processes it left run) and a "Command ID" detail row. Processes left running show as running with the label `processes still running` and no ticking time; a handed-off command with no known status shows as ended. The Terminals panel never shows commands.

## PowerShell wrapper (`_powershell.py`)

`powershell_command(command)` returns one setup line, then the Agent's command as a single-quoted literal (quotes doubled, typographic single quotes included), then the statements that run it. `pwsh` runs with `-NonInteractive`, so `Read-Host`, `Get-Credential` and confirmation prompts fail at once.
- Setup: `[Console]::OutputEncoding` and `InputEncoding` UTF-8 (native programs and PowerShell's capture of them use the console code pages; vBot decodes UTF-8), plain-text rendering (`PLAIN_TEXT_STATEMENT`: `$PSStyle.OutputRendering = 'PlainText'`, no ANSI in PowerShell's formatting and errors), a host buffer 200 columns wide (`OUTPUT_COLUMNS`; formatted rows such as `Format-Table` keep up to 199 characters instead of the 120 of a default host; a host whose buffer cannot be resized keeps its width), en-US UI culture (PowerShell's messages in English for the Agent and the hints) and the user's culture with numbers in a decimal point without grouping (`CULTURE_STATEMENT`: a German regional format printed `6,6` and `0,1s`, which reads as two values or a thousands separator, and parsed an Agent's `[double]::Parse('3.14')` as 314; Swarm review 2026-10-11. A full en-US culture fixed that but read the user's `Get-Date '11.10.2026'` as November 10 and wrote English month names, so dates, names and the list separator keep the user's format. A German decimal string such as `1,5` fails to parse instead of reading as 15; native programs keep the user's settings), the ErrorRecord baseline, and a `CommandNotFoundAction` for genuinely missing `head`/`tail`/`wc`: the line-count forms (`-n N`, `-N`, `--lines=N`, `tail -n +N`, `wc -l`; pipeline or files) run through `Select-Object`/`Get-Content`, any other option stops the script with a message naming the PowerShell equivalent. An installed one (Git's) still wins.
- The command is parsed after the setup with PowerShell's parser and run from a function defined on the wrapper's first line: `using`, `#requires`, a `param` block and named `begin`/`process`/`end` blocks keep their meaning; a syntax error is PowerShell's `ParserError` with the command's own line numbers, and nothing runs. No wrapper line appears in the command's errors.
- `/dev/null`: PowerShell resolves `/dev/null` as a path on the current drive, so `2>/dev/null` silently wrote the file `C:\dev\null` wherever `C:\dev` existed (and failed elsewhere), and a native program given `/dev/null` (`curl -o /dev/null`, `python script.py /dev/null`) opens that same file. Before running, the literal `/dev/null` or `\dev\null` (any case, any quoting, nested script blocks included) is rewritten, padded to the same length, so every offset, line and column stays as written and the syntax tree the wrapper parsed keeps describing the text that runs (the silenced-error lookup and the exit-status insertion rely on it). A multi-line target, a here-string, stays as written, since padding it would move later lines.
  - As a `FileRedirectionAst` target (`>`, `>>`, `2>`, `*>`) it becomes `$null`.
  - As a native program's argument it becomes `NUL`, Windows' null device: a whole argument, the argument of a `-name:/dev/null` parameter, or the end of a bareword after `=` (`--output=/dev/null`, `--output='/dev/null'`). The command name is resolved after the setup and before the command runs with `$ExecutionContext.InvokeCommand.GetCommand(name, 'All')`, PowerShell's own precedence, and only an `ApplicationInfo` counts. Cmdlets, functions and aliases keep `/dev/null` (`Out-File /dev/null`, `echo /dev/null`; the hint covers the cmdlet paths), and so does a program named by a variable (`& $exe`) or one the command itself defines, installs or reaches only after a `cd`. Programs with `msys-2.0.dll` or `cygwin1.dll` in their folder (Git's `usr\bin`, MSYS2, Cygwin) keep it, because they handle `/dev/null` themselves and treat `NUL` as an ordinary file name (MSYS2 `touch NUL` created a real file); so do `bash`, `sh`, `wsl`, `ssh`, `docker`, `podman` and `kubectl`, whose arguments reach a Linux system. Only commands with such an argument are resolved, about 40 ms for a missing name.
  - The rewrite walks the syntax tree, about 20 ms of every call, so it runs only when the command text can spell `/dev/null` (`_may_spell_null_device`): it contains `null` in any case, a backtick escape (``nu`ll``, ``"`u{6e}ull"``), or a character other than printable ASCII and whitespace, since PowerShell's culture-aware comparison reads `nu<U+00AD>ll` and `nu<U+0001>ll` as `null`. Other commands get the same wrapper without it (probe 2026-10: the wrapper's own time for `python --version` 50 -> 32 ms). The parse stays: parse errors, the silenced-error lookup and the exit-status insertion need it.
- Exit status: the statement at the end of the command's last block (the body, a named `end` block, or an `end` block added after `begin`/`process`) exits with the last native program's code as `bash -c` does, otherwise 0 or 1 by the last statement's success; an explicit `exit N` wins.
- Recorded errors: when the last statement succeeded after PowerShell recorded a new ErrorRecord (compared by identity, so profile errors and a full error ring do not matter), the exit code stays 0 and `POWERSHELL_ERROR_NOTE` plus the newest such error (whitespace collapsed, at most 500 characters) is printed to the error stream. Errors the command's own text silenced do not count (`-ErrorAction SilentlyContinue`/`Ignore`/`-ea 0`, a redirected error stream on the command or an enclosing one, `$ErrorActionPreference` SilentlyContinue at the end); a caught `throw` or `Write-Error` does. Printed error text, native stderr and warnings alone never trigger it. `exit`, a top-level `return` or `$Error.Clear()` bypass it.
- The wrapper adds about 6,600 characters to the command line, or about 8,700 when the command can spell `null` and carries the `/dev/null` rewrite, which leaves about 25,400 or 23,300 characters for a command without quotes (measured 2026-10-12 as `subprocess.list2cmdline` of the real argv; the error computes the exact room); each `'` and each escaped `"` or `\` costs more.

## Failure hints (`shell_hints.py`)

`annotate_failure(command, exit_code, output, *, workdir=None, offers=...)` returns at most one hint for a non-zero exit, first match wins, over the first and the last 4,000 output characters (an error printed after long progress output ends it; stdout and stderr share one pipe, so stderr does not arrive first); the command is scanned whole, so every pattern over it must run in linear time (`test_shell_hints.py` long-command cases). A hint names a Tool only when `offers(name)` is true; `HINT_TOOL_NAMES` lists the Tools hints can name (`search_files`, `read`, the edit Tools, `terminal`). Families, in order: gh unknown JSON field; git conflict, naming the stopped operation's `--continue`/`--abort` (rebase, cherry-pick, revert, merge or pull) or the stash; then the three input hints, placed before the not-installed families so a prompt failure never reads as a missing program: a PowerShell prompt refused in NonInteractive mode (English `PowerShell is in NonInteractive mode`, German `Nichtinteraktiv-Modus`), a container started with `-t`/`-it` (`the input device is not a TTY`), and a program that read the end of its empty input (`EOF when reading`, `stdin is not a terminal`, `not a tty`, `Inappropriate ioctl for device`, inquirer's `User force closed the prompt`, click's `Aborted!` or `click.exceptions.Abort`); POSIX command not found (`python`/`pip` variants, otherwise `command -v`); PowerShell "not recognized" in English and German, with the PowerShell equivalent of bash commands (`test`, `env` and `chmod` included, so none of them reads as a missing install; bash keywords such as `done` get the bash-syntax hint); Windows' Microsoft Store placeholder for Python ("Python was not found; run without arguments to install from the Microsoft Store", exit 9009), only when the command calls `python3`; Windows' `find.exe` (output lines starting `FIND: `, in any display language) for a command that calls `find`, naming `Get-ChildItem -Recurse -Filter` and `search_files` when offered; in a `ParserError`, bash heredocs, then bash control flow (a statement starting with `then`, `fi`, `done`, a `do` that opens no `{` block, or `[ `/`[[ `, outside here-strings), then bash's quote inside single quotes (`'\''`, `'"'"'`: write it twice), then `\"` escapes; `\"` escapes, and in a `@'...'@` here-string `''` or bash's quote idioms, that break the code PowerShell passes on (Windows only, the called program's `SyntaxError`); bash flags on PowerShell aliases (`ls -la`; a terminal drops the space after the cmdlet in PowerShell's multi-line error header, so `Cmdlet:` at a line end counts too); `Select-String -Recurse`; `/dev/null` as a cmdlet path (redirections and native programs never reach it, see the wrapper); a wildcard a program got unexpanded (Windows only: PowerShell expands wildcards only for cmdlets; an unquoted word of the command with `*` and a path mark, reported as written by the program; git's `did not match any file` and a `ParserError` excluded), naming `(Get-ChildItem <word>).FullName`; Python module not found (reads `workdir`: script run by path from a subdirectory, a process that ran elsewhere (Python run with `-m`, or the last traceback frame before the error is `<string>`/`<stdin>`, so the start directory was on the path), working directory not on the path, missing submodule, single module, unknown package); already exists; port in use (also Windows' `Only one usage of each socket address`); permission denied (Windows: a locked file, also for PowerShell's `Access to the path ... is denied`; POSIX: owner and permissions; both: ask the user for elevated rights); API rate limit. Hints that point into the output say "the files the output lists", not "above": a delivery puts `Hint:` before the output. Exit codes 126/137 get fixed hints on every host (on Windows they come through bash, wsl, docker or ssh); exit 124 gets a hint only when the command calls the `timeout` program (vBot has no timer that stops a command).

## Environment layers (`shell_environment.py`)

Built fresh for every start (about a millisecond; no cache), each layer over the previous:
1. Login base: Windows a fresh user environment block (registry `PATH` included, so newly installed programs are found); POSIX the server environment. vBot's own process variables (`PYTHONHOME`, `PYTHONPATH`, `VIRTUAL_ENV`, `__PYVENV_LAUNCHER__`, the venv on `PATH`) are removed.
2. Instance: `VBOT_DATA_DIR`, `VBOT_SERVER_PORT`, `VBOT_INSTALL_ROOT` exactly when the server has them.
3. Output: `TERM=dumb` for commands, which write to a pipe no one renders; `TERM=xterm-256color` for Terminal Sessions.
4. Commands only - unattended defaults: `GIT_EDITOR` accepts a message git prepared (rebase/merge/cherry-pick/revert `--continue`, `git revert`, `commit --amend` work as typed) and fails with the `-m` fix when the message is comments only (`commit`/`tag -a` without `-m`; lines below the `commit -v` scissors line are no message); `GIT_SEQUENCE_EDITOR` fails with the fix `$env:GIT_SEQUENCE_EDITOR = ":"` (POSIX `GIT_SEQUENCE_EDITOR=:`), so `rebase -i` never reports a rebase that changed nothing; `GIT_MERGE_AUTOEDIT=no`, `GIT_TERMINAL_PROMPT=0`, `GCM_INTERACTIVE=never`, `GIT_PAGER`/`GH_PAGER`/`PAGER=cat`, `NO_COLOR=1`, `PYTHONIOENCODING=utf-8` (Python's piped output is UTF-8, as vBot decodes it; without it non-ASCII text arrived garbled) and `PYTHONUNBUFFERED=1` (on a pipe Python would hold its output until the buffer fills or it exits; line by line, the live log, `status` and the WebUI view stay current). Git runs both editors through `sh -c '<editor> "$@"'`, so each value is sh builtins ending in a function that takes the file name, and `GIT_EDITOR` overrides `core.editor` (an Agent cannot work around a broken one with `-c core.editor`).
5. Commands only - `env` variables, then granted credentials.
6. Commands only - Run identity last: `VBOT_RUN_AGENT_ID`, `VBOT_RUN_SESSION_ID`, `VBOT_RUN_PROJECT_ID`, `VBOT_UPDATE_HANDOFF` (an inherited token is always removed).

Interactive Terminal Sessions use `terminal_environment()` (layers 1-3, `test_terminal_environment_has_no_command_layers`).

## Constraints & Gotchas

- Console reads on Windows: a program that reads the console directly instead of stdin blocks until it is stopped, because `CREATE_NO_WINDOW` still gives the process a console, whose input nothing writes. Examples: Python's `getpass`, `$Host.UI.RawUI.ReadKey()`, a program that opens `CONIN$`. Its call reports `running` with empty output and no hint once the wait passes, and the command continues in the background like any other. The stdin rule (stdin empty, no PTY) covers only stdin, so this case does not fail at once as the user requirement says a program that asks for input does (Review A1). In the same probes `input()`, `Read-Host`, `Get-Credential`, `[Console]::ReadKey()`, `choice`, `cmd /c pause` and `set /p` failed within 2 s (real `CommandManager` and `pwsh`, 2026-10-12).
- On POSIX the shell starts in a new session without a controlling terminal, so a program that opens `/dev/tty` fails at once (`ENXIO`).
- Process escape: Windows tracks the tree with a Job Object (children that break away, as the update handoff does, leave it). POSIX tracks the shell's session; a process that calls `setsid` leaves it. Escaped processes are neither reported nor killed.
- Child exit codes come from Job notifications on Windows, which are best effort: a missing `failed_programs` entry proves nothing. POSIX reports no child exit codes.
- Env grants are not a sandbox: a command can print or send an injected credential. The shell runs with the server user's full rights.
- POSIX commands get the server's environment, not a login shell's `PATH`.
- On Windows a call costs about 0.22 s beyond the command itself: `pwsh -NoProfile` starts in about that time. Pipes add no console start of their own (the ConPTY start the terminal design paid is gone).
- Capacity: at most 64 unfinished commands server-wide (`COMMAND_MAX_LIVE`), independent of the interactive terminal limits (4 per Session, 32 global).
- A background command stays queryable (`list`, `status`, the WebUI) while any of its processes runs and for 30 minutes after the last one ended, then is forgotten; its log file is kept 72 h.
- A Sub-Agent's background command delivers to the Sub-Agent Session like any completion, also after its Run ended; what then reaches the Parent is the Sub-Agent domain's concern (`subagents.md`).
- Old stored results with `process_id`/`delivery: "automatic"` or a `terminal_id` are plain rows; nothing folds them.
