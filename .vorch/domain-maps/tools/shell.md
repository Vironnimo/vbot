# Shell Tool (`bash` / `powershell`)

Runs one host shell command per call, each in a new Terminal Session of kind `command`, and returns its rendered output with an honest outcome.

`core/tools/shell.py` owns the Tool: definition and its projection to the offered Tools, call parsing, the wait/hand-off decision, result and delivery text (also for `terminal` actions on command terminals, through `command_terminal_result`), the durable status fold, and display. Next to it: `_powershell.py` builds the Windows command text (the wrapper), `shell_hints.py` maps failure output to one `hint`, `_workdir.py` resolves `project:<id>` workdirs for this Tool and `terminal`, `shell_environment.py` builds the environment of every shell vBot starts (commands and interactive terminals), `_shell_arguments.py` owns other harnesses' argument shapes, the `env` object, timeout units and display parts, and `update_handoff.py` owns the `vbot update` token (`cli/application.md`). The terminal domain (`tools/terminal.md`) owns everything below: the PTY/ConPTY, the command session (`_terminal_command.py`: transcript, `CommandReport`), process-tree tracking (`_terminal_process_tree.py`), and the command API of `TerminalManager`.

A command that outlives its call is a listed Terminal Session, followed up through `terminal` (`wait`, `status`, `input`, `kill`) and delivered by the terminal attention path; add follow-up capabilities there, not as a second process-tracking layer.

## Terms

### Command terminal
A Terminal Session started by `spawn_command` for one shell call. It is hidden (absent from the Terminal list, catalog and `resource_changed` events) until handed off.

### Hand-off
`hand_off_command(terminal_id, deliver=...)` makes a still-running command terminal a listed Terminal Session. With `deliver`, the command's result is submitted to its Session as a completion when the shell exits (`CommandReport.delivers_result`). Hand-offs happen on `mode: "background"`, after the 90-second wait, when the command looks idle (only for an Agent offered `terminal`), when the user moves the call to the background, and without delivery when the shell exited but processes it started still run.

## Interfaces

- Registry name `bash` (`SHELL_TOOL_NAME`); the Model sees `powershell` on Windows and `bash` elsewhere (`SHELL_MODEL_NAME`, `tools.md` -> Model Tool names). Registration: `register_shell_tool(registry, terminal_manager, credential_resolver=..., prompt_blocks=..., update_handoffs=..., projects=...)` (Runtime bootstrap passes the `ProjectStore`); it also declares the dynamic `tool:bash` Prompt Block `## Shell Environment Access` (empty without permanent Agent env grants; text from `format_shell_env_usage`, shared with Skill env guidance).
- Schema: one open flat object requiring `command`, with optional `description`, `workdir`, `timeout`, `env_keys` and `mode` (`foreground` | `background`). `project_shell_tool_definitions(definitions)` (called by Chat's request builder) fits the description to the Tools actually offered: the file-Tool sentence names per use (reading, searching, creating, editing) the offered Tool (`read`, `search_files`, then `apply_patch`, or `write`/`edit` on the edit dialect, `tools/edit.md`), `web_fetch` only when offered, the continuation sentence by whether `terminal` is offered, and the boundary sentence only when it is. Sub-Agents (Session depth >= 1) get the same definition and the same behavior as top-level Agents, `background` included (user decision 2026-10-05). Every Tool name in a result or delivery text is checked with `context.offers(name)`.
- Unadvertised aliases and dialects (`_shell_arguments.py:normalize_shell_arguments`): `cmd`/`script`/`commands`, argv arrays (joined into one host command line; a host-shell `-c`/`-Command` wrapper is unwrapped), OpenAI `local_shell` `action` objects, `cwd`/`directory`/`working_directory`, `timeout_ms`/`timeout_seconds`, background booleans, title-like description fields, harmless foreign flags (`pty`, `tty`, `login`, ...). Calls asking for a different effect (`elevated`, escalated sandbox permissions, `require_user_approval: true`, a non-empty `user`, contradicting mode fields) fail before running with the fix.
- `workdir`: absolute or relative to `effective_cwd`; a missing directory fails naming similar directories and the fix (pass an existing directory, or omit `workdir`); a missing working directory with `workdir` omitted names only the first. Unadvertised `project:<project-id>` runs in that Project's directory (`_workdir.project_workdir`, shared with `terminal`; the Projects block teaches each Project's path). Its failures (`ProjectWorkdirError.code`: `invalid_workdir`, `project_not_found`, `project_unavailable`) are `invalid_arguments` failures here, each naming a next step: the directory path, or for a missing Project directory an existing directory or omitting `workdir`.
- `timeout` is seconds of total runtime from the start, including time after a hand-off and after the shell exited: processes the command left running are stopped by it too. Omitted: 600 (`SHELL_DEFAULT_TIMEOUT_SECONDS`) in the foreground, none with `mode: "background"` (servers outlive 10 minutes); `0` -> no limit. A value that is clearly milliseconds is read as such with a `notes` entry; disagreeing `timeout`/`timeout_ms` fail.
- `env` (unadvertised) sets plain variables; vBot never passes a credential value written in the call. Credentials come only through granted `env_keys` names resolved server-side. An ungranted `env_keys` name the server process itself has passes with a `notes` entry; an unknown one fails, naming the granted keys.
- Host shell: Windows `pwsh -NoProfile -Command <text>`, where `_powershell.powershell_command(command)` builds `<text>` (see PowerShell wrapper below); command lines over 32,000 characters fail before running, naming the room left for the command (about 24,000 characters) and the save-to-`.ps1` fix. POSIX `bash -c <command>`. A missing `pwsh`/`bash` fails with "ask the user to install it". The command terminal is 200x50.
- Results (`tool_success` data; `ok: true` even for non-zero exits):
  - exited: `status: "exited"`, `exit_code`, `output`, plus when present `log_file` (only when output was cut), `failed_programs` (direct child programs of the shell that exited non-zero, e.g. `git.exe exited with code 128`; when vBot stopped the command, only those that failed before the stop; omitted when exactly one program failed with the result's `exit_code`, which it would only repeat), `hint` (non-zero exit, a known failure shape, `shell_hints.py`), and for processes the command left running `terminal_id`, `still_running` (`name (pid N)`) and `next` (the `terminal kill` call).
  - stopped by vBot: `status: "stopped"`, `stopped_because` (timeout with the retry fix, the user, the cancelled Run, shutdown, or "you stopped it"), and the fields above except `hint`.
  - still running: `status: "running"`, `terminal_id`, `output`, optional `log_file`, and `next`: the hand-off text, or the idle text when the command printed nothing and got no input for 15 seconds and its whole process tree used under 0.15 s CPU; the idle text names the real silent time in whole seconds (`TerminalManager.command_idle_seconds`, `tools/terminal.md` -> Command sessions). `next` states the time limit left (or none), names the exact `terminal` calls with the real id, and says the result arrives as a new message: every command handed off while its shell runs delivers its result.
  - `output` of a running command is the transcript followed by the whole current screen, without gap or overlap: `_report_with_screen` reads the screen (`command_screen`, under the session lock that rendering holds) and takes the report with no await in between; a command that exited meanwhile uses the transcript alone, which then holds the screen.
  - `notes` lists how the call was read leniently (millisecond timeout, inherited env key).
- `command_terminal_result(terminals, context, terminal_id, *, wait_ended=None) -> JsonObject`: the same result data for a command terminal, not wrapped in `tool_success`, plus `wait_ended` when given. A running command's `next` is the idle text whenever the command is idle (except after a match), otherwise the follow-up text for how the call ended: `matched`, `timeout` (wait again), or neither (`status`, `input`). `terminal` uses it for `status`, `wait`, `input` and `kill` on command terminals, so both Tools speak one vocabulary. Raises `TerminalManagerError` for an unknown terminal or one without a command.
- Output shaping (`command_output_text`): the transcript is the rendered output as final logical lines (no ANSI, no progress-bar redraws), held as the first 40 and last 80 lines; the result keeps whole lines within 4,000 head and 8,000 tail characters and cuts single lines at 2,000 characters, with an in-text marker naming `log_file`. The full transcript is a private file in Storage's `artifacts/temp/commands` (72 h retention).
- Delivery (`format_command_delivery(report, *, offers=...)`): a handed-off command's result reaches its Session as a completion Note starting `The command in terminal <id> (<description or first line>) exited with code N.` or `... was stopped: <reason>`, then `Hint: ...`, failed programs (by the `failed_programs` rule when the first line names the exit code; all of them after a stop), still-running processes (with the `terminal kill` call when `terminal` is offered), `Full output: <log>` when cut, and the output. `offers` is a snapshot of the hint Tools and `terminal` taken at spawn, since the delivery outlives the call. It goes through `TriggerService.submit_completion` with the origin Run id, so it survives a restart like every completion. An Agent's own `terminal kill` delivers nothing.
- Status fold (`background_command_statuses(records)`): durable `bash` results with `data.status == "running"` and a `terminal_id` give `running`; delivery Notes give `completed` (exit 0), `failed` (other code) or `stopped`. The fold reads only the first line of a delivery, so the `Hint:` line follows it. Folding a later range onto an earlier fold equals folding both. `chat.history` returns it as `background_command_statuses` after replacing each `running` with `TerminalManager.command_status(id)` and dropping commands vBot no longer knows. Live changes are the `command_status_changed {terminal_id, status}` app event (`server/events-and-reconnect.md`).
- Live output: while the call waits, the Tool emits the Run event `tool_call_output {tool_call_id, terminal_id, screen}` at most every 0.5 s while output arrives; `screen` is the newest 40 rows and replaces the previous one (transient, never persisted).
- Display: `shell_display_parts` shows the `description` or the command (copyable either way); `shell_detail_blocks` shows the command, the result's `data.output`, warnings for a stop, a non-zero exit code and failed programs, an info notice `Hint: ...`, and an info notice for a running command. The WebUI renders a `stopped` result as a cancelled row, not a success (`webui/chat.md`).

## Execution lifecycle

1. `_parse_call` validates and resolves everything before anything starts: `workdir`, timeout, env, credentials, and on Windows the command-line length.
2. An update handoff token is issued when the call has a result-persistence boundary; it stays claimable exactly until the command's whole process tree has ended (`wait_finished`).
3. `command_environment` builds the environment (below); `spawn_command` starts the shell in a hidden command terminal. A process tree that cannot be tracked is not started. A cancelled Run's id is rejected (`cancel_run`).
4. Foreground: `wait_command` waits for exit, the hand-off deadline (90 s) or idleness (only when the Agent is offered `terminal`). The user can move the call to the background (`background_registration_hook`, set by Chat's Tool dispatch). Per-call cancellation stops the command (`run_cancelled` or `user`); Run cancellation also terminates the Run's handed-off commands, without delivery (`TerminalManager.cancel_run`).
5. Exit -> exited/stopped result; a shell that exited while processes it started still run is handed off without delivery, so the user and Agent can see and stop them. Otherwise the command is handed off with delivery and a running result returned. Background mode hands off at once.

`stop_command(reason)` sends Ctrl+C, waits 3 s for the shell, then kills the whole tree. The timeout keeps running after a hand-off and after the shell's exit until the whole tree has ended; when it fires after the shell exited, it kills what the shell left running and the result stays `exited` (`tools/terminal.md` -> Command sessions). `shutdown_commands` stops every command before the delivery service closes, so handed-off commands deliver a "vBot shut down" result.

## PowerShell wrapper (`_powershell.py`)

`powershell_command(command)` returns one setup line, then the Agent's command as a single-quoted literal (quotes doubled, typographic single quotes included), then the statements that run it:
- Setup: `[Console]::OutputEncoding` and `InputEncoding` UTF-8 (native programs and PowerShell's capture of them use the console code pages; the terminal decodes UTF-8), en-US UI culture (PowerShell's messages in English for the Agent and the hints; number and date formats keep the user's culture), the ErrorRecord baseline, and a `CommandNotFoundAction` for genuinely missing `head`/`tail`/`wc`: the line-count forms (`-n N`, `-N`, `--lines=N`, `tail -n +N`, `wc -l`; pipeline or files) run through `Select-Object`/`Get-Content`, any other option stops the script with a message naming the PowerShell equivalent. An installed one (Git's) still wins.
- The command is parsed after the setup with PowerShell's parser and run from a function defined on the wrapper's first line: `using`, `#requires`, a `param` block and named `begin`/`process`/`end` blocks keep their meaning; a syntax error is PowerShell's `ParserError` with the command's own line numbers, and nothing runs. No wrapper line appears in the command's errors.
- `/dev/null`: PowerShell resolves `/dev/null` as a path on the current drive, so `2>/dev/null` silently wrote the file `C:\dev\null` wherever `C:\dev` existed (and failed elsewhere), and a native program given `/dev/null` (`curl -o /dev/null`, `python script.py /dev/null`) opens that same file. Before running, the literal `/dev/null` or `\dev\null` (any case, any quoting, nested script blocks included) is rewritten, padded to the same length, so every offset, line and column stays as written and the syntax tree the wrapper parsed keeps describing the text that runs (the silenced-error lookup and the exit-status insertion rely on it). A multi-line target, a here-string, stays as written, since padding it would move later lines.
  - As a `FileRedirectionAst` target (`>`, `>>`, `2>`, `*>`) it becomes `$null`.
  - As a native program's argument it becomes `NUL`, Windows' null device: a whole argument, the argument of a `-name:/dev/null` parameter, or the end of a bareword after `=` (`--output=/dev/null`, `--output='/dev/null'`). The command name is resolved after the setup and before the command runs with `$ExecutionContext.InvokeCommand.GetCommand(name, 'All')`, PowerShell's own precedence, and only an `ApplicationInfo` counts. Cmdlets, functions and aliases keep `/dev/null` (`Out-File /dev/null`, `echo /dev/null`; the hint covers the cmdlet paths), and so does a program named by a variable (`& $exe`) or one the command itself defines, installs or reaches only after a `cd`. Programs with `msys-2.0.dll` or `cygwin1.dll` in their folder (Git's `usr\bin`, MSYS2, Cygwin) keep it, because they handle `/dev/null` themselves and treat `NUL` as an ordinary file name (MSYS2 `touch NUL` created a real file); so do `bash`, `sh`, `wsl`, `ssh`, `docker`, `podman` and `kubectl`, whose arguments reach a Linux system. Only commands with such an argument are resolved, about 40 ms for a missing name.
- Exit status: the statement at the end of the command's last block (the body, a named `end` block, or an `end` block added after `begin`/`process`) exits with the last native program's code as `bash -c` does, otherwise 0 or 1 by the last statement's success; an explicit `exit N` wins.
- Recorded errors: when the last statement succeeded after PowerShell recorded a new ErrorRecord (compared by identity, so profile errors and a full error ring do not matter), the exit code stays 0 and `POWERSHELL_ERROR_NOTE` plus the newest such error (whitespace collapsed, at most 500 characters) is printed to the error stream. Errors the command's own text silenced do not count (`-ErrorAction SilentlyContinue`/`Ignore`/`-ea 0`, a redirected error stream on the command or an enclosing one, `$ErrorActionPreference` SilentlyContinue at the end); a caught `throw` or `Write-Error` does. Printed error text, native stderr and warnings alone never trigger it. `exit`, a top-level `return` or `$Error.Clear()` bypass it.
- The wrapper adds about 8,000 characters to the command line, which leaves about 24,000 characters for a command without quotes; each `'` and each escaped `"` or `\` costs more.

## Failure hints (`shell_hints.py`)

`annotate_failure(command, exit_code, output, *, workdir=None, offers=...)` returns at most one hint for a non-zero exit, first match wins, over the first 4,000 output characters; the command is scanned whole, so every pattern over it must run in linear time (`test_shell_hints.py` long-command cases). A hint names a Tool only when `offers(name)` is true; `HINT_TOOL_NAMES` lists the Tools hints can name. Families, in order: gh unknown JSON field; git conflict, naming the stopped operation's `--continue`/`--abort` (rebase, cherry-pick, revert, merge or pull) or the stash; POSIX command not found (`python`/`pip` variants, otherwise `command -v`); PowerShell "not recognized" in English and German, with the PowerShell equivalent of bash commands (`test`, `env` and `chmod` included, so none of them reads as a missing install; bash keywords such as `done` get the bash-syntax hint); Windows' Microsoft Store placeholder for Python ("Python was not found; run without arguments to install from the Microsoft Store", exit 9009), only when the command calls `python3`; Windows' `find.exe` (output lines starting `FIND: `, in any display language) for a command that calls `find`, naming `Get-ChildItem -Recurse -Filter` and `search_files` when offered; in a `ParserError`, bash heredocs, then bash control flow (a statement starting with `then`, `fi`, `done`, a `do` that opens no `{` block, or `[ `/`[[ `, outside here-strings), then `\"` escapes; `\"` escapes that break the code PowerShell passes on (Windows only, the called program's `SyntaxError`); bash flags on PowerShell aliases (`ls -la`); `Select-String -Recurse`; `/dev/null` as a cmdlet path (redirections and native programs never reach it, see the wrapper); Python module not found (reads `workdir`: script run by path from a subdirectory, working directory not on the path, missing submodule, single module, unknown package); already exists; port in use; permission denied (Windows: a locked file; POSIX: owner and permissions; both: ask the user for elevated rights); API rate limit. Exit codes 126/137 get fixed hints only on POSIX; there is no exit-124 hint (vBot's own timeout is a stop with `stopped_because`).

## Environment layers (`shell_environment.py`)

Built fresh for every start (about a millisecond; no cache), each layer over the previous:
1. Login base: Windows a fresh user environment block (registry `PATH` included, so newly installed programs are found); POSIX the server environment. vBot's own process variables (`PYTHONHOME`, `PYTHONPATH`, `VIRTUAL_ENV`, `__PYVENV_LAUNCHER__`, the venv on `PATH`) are removed.
2. Instance: `VBOT_DATA_DIR`, `VBOT_SERVER_PORT`, `VBOT_INSTALL_ROOT` exactly when the server has them.
3. `TERM=xterm-256color`.
4. Commands only - unattended defaults: `GIT_EDITOR` accepts a message git prepared (rebase/merge/cherry-pick/revert `--continue`, `git revert`, `commit --amend` work as typed) and fails with the `-m` fix when the message is comments only (`commit`/`tag -a` without `-m`; lines below the `commit -v` scissors line are no message); `GIT_SEQUENCE_EDITOR` fails with the fix `$env:GIT_SEQUENCE_EDITOR = ":"` (POSIX `GIT_SEQUENCE_EDITOR=:`), so `rebase -i` never reports a rebase that changed nothing; `GIT_MERGE_AUTOEDIT=no`, `GIT_TERMINAL_PROMPT=0`, `GCM_INTERACTIVE=never`, `GIT_PAGER`/`PAGER=cat`. Git runs both editors through `sh -c '<editor> "$@"'`, so each value is sh builtins ending in a function that takes the file name, and `GIT_EDITOR` overrides `core.editor` (an Agent cannot work around a broken one with `-c core.editor`).
5. Commands only - `env` variables, then granted credentials.
6. Commands only - Run identity last: `VBOT_RUN_AGENT_ID`, `VBOT_RUN_SESSION_ID`, `VBOT_RUN_PROJECT_ID`, `VBOT_UPDATE_HANDOFF` (an inherited token is always removed).

Interactive Terminal Sessions use `terminal_environment()` (layers 1-3).

## Constraints & Gotchas

- Process escape: Windows tracks the tree with a Job Object (children that break away, as the update handoff does, leave it; a process created between the root's start and job assignment escapes). POSIX tracks the shell's session; a process that calls `setsid` leaves it. Escaped processes are neither reported nor killed.
- Child exit codes come from Job notifications on Windows, which are best effort: a missing `failed_programs` entry proves nothing. POSIX reports no child exit codes.
- Env grants are not a sandbox: a command can print or send an injected credential. The shell runs with the server user's full rights.
- POSIX commands get the server's environment, not a login shell's `PATH`.
- Commands run in a terminal, not on pipes: stdin is the terminal, so `Read-Host` and native prompts wait for input (the idle hand-off names the `terminal input` call), and `-NonInteractive` is not passed. A test that a command's stdin reads EOF no longer applies.
- On Windows a call costs about 0.25 s beyond the command itself: `pwsh -NoProfile` starts in ~0.22 s, ConPTY adds ~0.02 s, and the exit is noticed within a few milliseconds. The first command after a server start costs another ~0.3 s once (first ConPTY start).
- Capacity: at most 64 live command terminals, independent of the interactive limits (4 per Session, 32 global).
- A Sub-Agent's handed-off command delivers to the Sub-Agent Session like any completion, also after its Run ended; what then reaches the Parent is the Sub-Agent domain's concern (`subagents.md`, `tools/terminal.md` -> Generic activity delivery).
- Old stored results with `process_id`/`delivery: "automatic"` are plain rows; nothing folds them.
