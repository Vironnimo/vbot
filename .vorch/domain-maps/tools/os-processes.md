# OS Processes (`core/utils/processes.py`)

Shared OS launch flags, server-lifetime containment, and verified process-tree termination. Terminal Sessions (and so the shell Tool), decision actions, local Model tasks (embeddings, speech, setup), search, the CLI, and server startup use this owner. Per-command process-tree facts (liveness, CPU, child exit codes) belong to the terminal domain (`_terminal_process_tree.py`, `tools/terminal.md`).

## Contracts

- `subprocess_creation_flags(*, new_process_group=False, breakaway=False, platform_name=os.name) -> int` is the child-process launch policy: zero on non-Windows; `CREATE_NO_WINDOW` on Windows, optionally combined with `CREATE_NEW_PROCESS_GROUP`. Lifecycle/update handoff requests breakaway; the owner queries the immediate Job and adds `CREATE_BREAKAWAY_FROM_JOB` only for explicit `BREAKAWAY_OK` without `SILENT_BREAKAWAY_OK`. No Job or forbidden breakaway omits the flag; API errors propagate. vBot's Job permits explicit breakaway, allowing its updater to survive server death even inside a restrictive external ancestor. That ancestor retains its own lifetime authority.
- Core subprocesses use `subprocess_creation_flags`, so ripgrep search, local Model workers, CLI helpers and Windows `taskkill` stay windowless when vBot runs without a parent console.
- `server.main` calls `activate_process_containment()` once before Runtime startup: Windows descendants inherit a kill-on-close Job Object; POSIX launches that go through `guarded_process_launch` run under `core/utils/process_guardian.py` and receive server death through one parent-liveness pipe. systemd adds a service-cgroup boundary (`cli.md`). These are crash-only backstops; Runtime shutdown remains the primary owner and stops every process tree explicitly. They create no durable or reattachable handles.
- `guarded_process_launch(argv, *, env, controlling_terminal=False)` returns the exact argv when no POSIX boundary is active and no controlling terminal is requested; otherwise the private guardian argv, plus its inherited lifetime descriptor while the boundary is active. `env` is the environment the caller starts the launch with. `controlling_terminal` (Terminal Backend only) requires the caller to start the launch as a session leader with the PTY slave as stdin (`tools/terminal.md`). Windows launches never use the guardian. The guardian reports a child killed by signal N as exit code 128+N, as a shell does.
- `kill_process_tree(proc, targets=...)` / `kill_process_tree_async`: POSIX signals the process group and propagates group-kill errors instead of falling back to a direct-child kill. Windows captures the tree with psutil around `taskkill /T`; its fallback kills the captured processes, never just the immediate child, and `targets` retains descendant identities so a retry can kill them after their parent exited. A taskkill failure (exit code and first stderr line, timeout, or launch error) is DEBUG detail when the fallback ends the tree; only survivors log a WARNING with their count and that cause. The async variant runs `taskkill` in a worker thread so the Event Loop never stalls behind it.

## Gotchas

- **Guardian isolation:** the guardian starts in the child's working directory and environment, so it runs by absolute file path as `sys.executable -I -S -B -X utf8 <core/utils/process_guardian.py>`: neither the working directory, `PYTHONPATH`/`PYTHONHOME`/other `PYTHON*` variables nor site-packages can replace a module it imports, and it writes no bytecode into an installed version. Run as `-m core.utils.process_guardian`, it failed with `No module named 'core.utils'` in a project with its own `core` package. It therefore imports only the standard library. The child still receives the caller's working directory and exactly `env`: Python's startup sets `LC_CTYPE` (PEP 538) when the environment names no UTF-8 locale, which isolated mode cannot turn off, so the launch passes the requested value (`--lc-ctype=<value>`, omitted when unset) and the guardian restores it, or its absence, before it starts the child.
- **Guardian wait:** the guardian sleeps without a timeout until its child exits or the lifetime pipe reaches EOF and reports the child's exit at once (the exit wins when both are ready). It waits on a pidfd (`os.pidfd_open`, Linux >= 5.3); where that fails (older kernel, seccomp) or on other POSIX systems, on a pipe a reaper thread closes once it reaped the child. An earlier 0.2 s poll added ~200 ms to every short command. It starts its child with `os.posix_spawnp` (resetting ignored signals, lifetime pipe non-inheritable) and parses its private arguments by hand, importing neither `subprocess` nor `argparse` (~13.5 ms median startup, WSL). The child never holds the lifetime pipe.
