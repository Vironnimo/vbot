# OS Processes (`core/utils/processes.py`)

Shared OS launch flags, server-lifetime containment, and verified process-tree termination. Shell commands (`CommandManager`, `_command_launch.py`), Terminal Sessions, decision actions, local Model tasks (embeddings, speech, setup), search, the CLI, and server startup use this owner. Per-command process-tree facts (liveness, CPU, child exit codes) belong to `core/tools/process_tree.py`, which `CommandManager` (`tools/shell.md`) and the Terminal Sessions (`tools/terminal.md`) share.

## Contracts

- `subprocess_creation_flags(*, new_process_group=False, breakaway=False, platform_name=os.name) -> int` is the child-process launch policy: zero on non-Windows; `CREATE_NO_WINDOW` on Windows, optionally combined with `CREATE_NEW_PROCESS_GROUP`. Lifecycle/update handoff requests breakaway; the owner queries the immediate Job and adds `CREATE_BREAKAWAY_FROM_JOB` only for explicit `BREAKAWAY_OK` without `SILENT_BREAKAWAY_OK`. No Job or forbidden breakaway omits the flag; API errors propagate. vBot's Job permits explicit breakaway, allowing its updater to survive server death even inside a restrictive external ancestor. That ancestor retains its own lifetime authority.
- `foreign_job() -> ForeignJob | None` (Windows; `None` elsewhere) reports another application's Job that holds this process: only the immediate Job is visible, and its outermost member in this process's ancestry (`name`, `pid`) names the owner, usually the application whose exit ends the Job. A vBot executable as that member (the tray in the logon tasks' Job, a server in its own Job), or this process itself (its parent is outside the Job), returns `None`. `confines_children` is true when the Job allows neither explicit nor silent breakaway, so a `breakaway=True` child stays inside too. API failures raise `OSError`. Users: the server's startup warning (`server/process-lifecycle.md` -> Start and stop lines), `core/utils/outside_job.py` (below), and `scripts/deploy_local.py`'s warning.
- `core/utils/outside_job.py` starts processes that must outlive another application's Job. `confining_job()` is `foreign_job()` narrowed to a Job with `confines_children` (`None` elsewhere, and when inspection fails, logged as WARN). `start_outside_job(argv, *, cwd, creationflags, env=None)` creates the process through WMI from a short PowerShell broker (request as base64 JSON on stdin, 30 s timeout) and returns a Popen-like `OutsideJobProcess` (not a child: exit code unknown, reported as 1); `env=None` gives the user's default environment, otherwise `env` replaces the whole block. Every refusal or timeout raises `OSError` (Defender's rule against process creation from WMI is one cause). `start_outside_foreign_job(argv, *, cwd, env, spawn)` is the one policy for long-lived processes: outside a confining Job it calls `spawn()`; inside one it uses WMI (windowless, own process group) and, when that fails, calls `spawn()` anyway and returns a `Confinement(job, reason)` so the caller warns that the process ends with that application. Users: `vbot server start`/`restart` (`cli/server-lifecycle.md` -> Commands, `cli/application.md` -> Update operation) and the tray start in update dispatch (`cli/application.md` -> Update operation). Tests neutralize Job inspection by patching `core.utils.processes.foreign_job` (autouse in `tests/cli/conftest.py`).
- Observed Windows behavior (Windows 11, verified 2026-10-16 with disposable processes): breaking away from a nested Job (explicitly or silently) lands the child in the next outer Job, so a restrictive outer Job keeps it; Task Scheduler runs all of a user's logon tasks in one per-session Job without breakaway (the tray, its servers and unrelated apps share it, which is benign); coding-agent apps run their shells in such a Job (the Claude desktop app's allows no breakaway; closing the Codex desktop app ended an installed server that an update run from its shell had restarted, without a log line); a process created through WMI (`Win32_Process.Create`) belongs to no Job (its parent is `WmiPrvSE.exe`) and runs in the caller's interactive session with the user's default environment, or exactly the `Win32_ProcessStartup.EnvironmentVariables` block passed (non-ASCII values intact), in the passed working directory and with the passed `CreateFlags` (`CREATE_NO_WINDOW | CREATE_NEW_PROCESS_GROUP` accepted).
- Core subprocesses use `subprocess_creation_flags`, so ripgrep search, local Model workers, CLI helpers and Windows `taskkill` stay windowless when vBot runs without a parent console.
- `server.main` calls `activate_process_containment()` once before Runtime startup: Windows descendants inherit a kill-on-close Job Object; POSIX launches that go through `guarded_process_launch` run under `core/utils/process_guardian.py` and receive server death through one parent-liveness pipe. systemd adds a service-cgroup boundary (`cli/application.md` -> Autostart and server supervision). These are crash-only backstops; Runtime shutdown remains the primary owner and stops every process tree explicitly. They create no durable or reattachable handles.
- `guarded_process_launch(argv, *, env, controlling_terminal=False, report_exit=False)` returns the exact argv when no POSIX boundary is active and no controlling terminal is requested; otherwise the private guardian argv, plus its inherited lifetime descriptor while the boundary is active. `env` is the environment the caller starts the launch with. `controlling_terminal` (Terminal Backend only) requires the caller to start the launch as a session leader with the PTY slave as stdin (`tools/terminal.md`). Windows launches never use the guardian. The guardian reports a child killed by signal N as exit code 128+N, as a shell does. On Linux, `report_exit=True` supplies a private `GuardedChildExit` pipe; its owner calls `spawned()` after launch, reads the root exit independently of the remaining tree, and closes the pipe when releasing the process. Shell and Terminal owners use it; the child inherits neither this pipe nor the server-lifetime descriptor.
- `kill_process_tree(proc, targets=...)` / `kill_process_tree_async`: Linux guarded launches signal their identity-checked guardian and confirm its exit; the guardian retains descendants until they are reaped, including after `setsid` and double-fork. Other POSIX launches signal the process group and propagate group-kill errors instead of falling back to a direct-child kill. Windows captures the tree with psutil around `taskkill /T`; its fallback kills the captured processes, never just the immediate child, and `targets` retains descendant identities so a retry can kill them after their parent exited. A taskkill failure (exit code and first stderr line, timeout, or launch error) is DEBUG detail when the fallback ends the tree; only survivors log a WARNING with their count and that cause. The async variant runs termination and its confirmation in a worker thread so the Event Loop never stalls behind it.

## Gotchas

- **Guardian isolation:** the guardian starts in the child's working directory and environment, so it runs by absolute file path as `sys.executable -I -S -B -X utf8 <core/utils/process_guardian.py>`: neither the working directory, `PYTHONPATH`/`PYTHONHOME`/other `PYTHON*` variables nor site-packages can replace a module it imports, and it writes no bytecode into an installed version. Run as `-m core.utils.process_guardian`, it failed with `No module named 'core.utils'` in a project with its own `core` package. It therefore imports only the standard library. The child still receives the caller's working directory and exactly `env`: Python's startup sets `LC_CTYPE` (PEP 538) when the environment names no UTF-8 locale, which isolated mode cannot turn off, so the launch passes the requested value (`--lc-ctype=<value>`, omitted when unset) and the guardian restores it, or its absence, before it starts the child.
- **Linux guardian lifetime:** before starting user code, the guardian becomes a kernel child subreaper (`PR_SET_CHILD_SUBREAPER`) and opens its own procfs child list. Missing subreaper/procfs support fails the launch. It sleeps on the lifetime pipe and a SIGCHLD/SIGTERM/SIGHUP wakeup pipe, reports the root exit immediately through the optional status pipe, and stays alive until `waitpid(-1)` proves no child remains. On server death or explicit stop it kills its direct children repeatedly; their surviving descendants are adopted before the next reap, so a fork or Session change cannot escape between enumeration and kill. An exited child cannot have its PID reused before this single-threaded guardian reaps it. A refused kill keeps the guardian alive and the caller reports an unconfirmed stop. The guardian closes its own standard streams after spawning; it never holds command output or a PTY open by itself. Non-Linux POSIX retains the process-group guardian and child-exit reaper thread.
- **Process observation:** `find_process_guardian` recognizes the actual isolated launcher argv; the returned psutil identity guards against PID reuse without a process registry. `process_tree.py` follows its descendants and treats a live guardian as unresolved work when a child-list read races orphan adoption. Only guardian exit proves the tree empty. Explicit update handoffs continue outside the guarded launch and retain their intended independent lifetime.
