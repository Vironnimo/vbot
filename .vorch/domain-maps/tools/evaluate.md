# Evaluate Tool

`core/tools/evaluate.py` registers the flat execution-family Tool `evaluate(state, questions)` against the Runtime's shared DecisionService; `core/tools/_evaluate_arguments.py` reads the calls. It returns focused typed judgments from the configured Decision Task Model without starting an Agent Run or external application action. The canonical executor/experiment/control contract is `../model_tasks/decisions.md`; the question vocabulary (`choice|score|noul`) is the Decisions wire's and the Jev editor's, so the Tool keeps `noul` and explains it as the probability of yes.

## Interfaces

- Schema: `state` (text, JSON object or JSON array) and `questions` are required. Each question has `type` and `instructions` (required), an optional `id` (defaults to `q1`, `q2`, ... by position, skipping ids already taken) and type-specific `criteria`: choice maps at least two labels to descriptions; score lists level descriptions, lowest first, answered by level number from 0; noul criteria are optional `{"true": ..., "false": ...}`. No conversation context, images or explanation generation is implicit.
- Results: fields `model` and `usage` (`<n> input and <n> output tokens[, cost <c>]`), then one content line per answer in question order: `<id>: probability of yes <p>` for noul, `<id>: <label>` for choice and `<id>: level <n>[ on levels 0-<max>]` for score, each followed by `(confidence <c>; <label> <p>, ...)` when the Provider reported them. Numbers show three significant digits. Missing optional probabilities, confidence and cost are not invented.
- Failures carry the DecisionError code and message (such as `outcome_unknown`, `provider_error`, `invalid_result`) without a retry flag; the `outcome_unknown` text says a new evaluation may incur another charge.

## Argument Reading

The argument normalizer (no context) accepts the Decisions wire's map of id to question, one question object, bare question text, a JSON-encoded question list, and question fields written straight into the call (merged into the only question). Spellings: `input`/`content`/`data`/`text`... -> `state`, `question` -> `questions`; per question `name`/`key` -> `id`, `kind` -> `type`, `question`/`prompt`/`text` -> `instructions`, `options`/`labels`/`levels` -> `criteria`. Type words: `yes_no`/`boolean`/`probability`... -> `noul`, `classification`/`select`/`multiple_choice`... -> `choice`, `rating`/`scale`/`likert`... -> `score`. Choice criteria given as a label list use each label as its own description (label objects take `label`/`name` plus `description`/`meaning`); score criteria numbered `0..n-1` become the level list; noul `yes`/`no` criteria become `true`/`false`; a number or boolean state is judged as its text.

It never infers a missing type, never matches type typos, and never shifts score levels. Refusals start with `evaluate was not run:`, happen before the Provider is called, and show the corrected question: a missing type offers the noul, choice and score forms; score levels numbered from another start show the list with the note which level becomes 0; unsupported question fields (such as `explain`) are named with the question without them; a field given inside and outside the question with different values offers both questions; loose fields beside several questions are refused. Missing `state`/`questions` and duplicate ids are refused with the missing piece. Unknown top-level fields still fail at dispatch instead of discarding requested behavior; arbitrary state object fields and text are preserved. Domain validation in `decision_types.validate_input` stays the final guard.

## Conventions

The Tool is registered consistently but only exposed when its Decision binding is usable through the implemented OpenRouter wire; dispatch checks readiness before reading arguments, so the `tool_lab` probe (no Decision model) reaches only the readiness hint. Existing Tool Access Policy still applies. The Tool cannot configure or execute control commands. The display summary counts the questions after argument reading.

Tests: `tests/core/tools/test_evaluate.py` (actual registry dispatch: payload preservation, access/readiness, other question shapes, refusals, result lines) and the executor tests listed in the canonical map. These verify execution contracts; they do not establish independent Model Tool choice. Usability evidence must meet `designing-agent-tools.md` rather than infer reliability from a Model receiving the production definition alone. No separate Skill is needed for a single self-contained evaluation operation.
