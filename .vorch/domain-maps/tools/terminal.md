# Interactive Terminal Sessions (`terminal`)

`terminal_manager.py` owns Session admission, lookup, attachment/lifecycle scope, launch, and shutdown coordination; it hands callers immutable `TerminalInfo` views (`_terminal_state.py`), never live Session objects. `_terminal_session.py` (`TerminalSession`) owns one process: PTY reads and writes, its rendered screen, activity, attention and delivery, retained output, and the event stream. `_terminal_activity.py` (`TerminalActivity`) is the pure activity state machine (phases, quiet-boundary wakeups, delivered-screen baseline) that the Session drives with explicit times; it owns no tasks and no clock. `terminal_emulator.py` (`TerminalEmulator`) is the VT emulation: screen, history with stable line numbers, query replies, and the ANSI snapshot. It imports only the standard library and pyte so `_terminal_render_host.py` can run it off the Event Loop. `_terminal_launch.py` builds the shell-native start of a manual launch command. The internal catalog (`_terminal_catalog.py`) owns groups, ordering and operator summaries; `_terminal_input.py` encodes Agent input; `_terminal_state.py` holds Session values, limits, and errors. Components receive explicit services (`TerminalSessionServices`), never the manager.

New Terminal Session ids use `term_` plus 12 lowercase base32 characters, allocated against the retained catalog after async launch and before synchronous publication. Created groups use `grp_` with the same suffix; automatic group identities stay deterministic (`terminal_manager.py`, `test_parallel_terminal_ids_skip_collisions` in `test_terminal_manager_lifecycle.py`).

## Boundary and invariants

`terminal` gives an Agent a real interactive terminal; the shell Tool runs each of its commands in a Terminal Session too (Command sessions below). Every requested executable uses the same PTY/ConPTY transport and receives the exact declared argument vector. The terminal capability contains no executable detection, program-specific flags, hooks, configuration injection, lifecycle protocol, or screen-text heuristics. Codex, Claude Code, other coding CLIs, shells, editors, games, and arbitrary interactive programs therefore share one contract.

- Every Terminal Session records immutable process provenance (`owner`: the starting Agent Session, or `None` for a local-operator start), an independent lifecycle scope (`lifecycle_owner`: the transferable Agent Session scope that owns cleanup, or `None` for an operator-started process), and at most one mutable Agent Tool/event binding (`attachment`). Agent `start` initializes all three Agent scopes to the current Session; an operator start initializes all three as local/unbound. The local operator can observe and control every active Terminal Session without changing any of them.
- The Agent Tool, WebUI, and child process use the same live PTY/ConPTY. Agent and WebUI input are written to that process, WebUI output is the sequenced raw VT stream, and Agent status is rendered from the same stream.
- A Terminal Session ends only on explicit `kill`, natural child exit, applicable lifecycle-owner Session/Agent/Project removal, or Runtime shutdown, and it finishes only once its processes have ended (a command's: its whole tree). The end of its output - EOF, a closed PTY, a failure to read, render or log it - is no end of the program: a program that still runs keeps its capacity slot, its lifecycle owner and its kill path, and `terminal.forget` keeps refusing it (failure handling under Generic activity delivery). Operator-started sessions have no Agent lifecycle scope and are therefore unaffected by Agent, Session, and Project cleanup even while attached. `detach`, leaving a Run, or navigating away from the WebUI never ends a Terminal Session.
- Handler argument refusals raise `ToolContractError` and return `invalid_arguments`; an `OSError` or other exception escaping an action (for example a failed input write) is `tool_execution_error` with unknown effects (`tools.md` -> Failure codes follow the phase; `test_a_failure_while_acting_reports_unknown_effects`).
- Launch failures wrapped by `TerminalManager` reach the Agent as `terminal_launch_failed` naming the original cause (a missing program, `FileNotFoundError`, as `terminal_command_not_found`); the Tool does not guess the cause from a generic filesystem exception. Failed launches release their capacity and retain no Terminal Session. Evidence: `test_launch_failure_is_reported_and_releases_capacity` in `test_terminal.py`.
- Starting processes reserve the same per-Session and global capacity as live processes before any worker is launched. Cancellation during creation waits for the launch outcome and stops the resulting child before releasing the reservation; shutdown also waits for pending launches. Already-started Terminal Sessions retain their independent Run lifetime.
- Internal live states are `starting`, `ready`, and `working`; terminal states are `exited` and `error`. These states describe terminal activity and process lifetime, not application-specific turns or prompts. The Agent sees only `running`, `exited`, `stopped` (vBot, the user or an Agent stopped the program: `TerminalInfo.stopped`) and `failed` (`error`); whether an interactive program's new output settled is the `wait_ended` of a wait.
- Raw output and rendered history are bounded. The manager retains a finished Terminal Session's metadata and rendered history for 30 minutes so the operator can inspect it as a read-only snapshot; `terminal.forget` may remove that in-memory record sooner. When Storage is available, the manager additionally retains the raw output in a leased `<data_dir>/artifacts/temp/terminals/*.log` and starts the normal temporary-file retention clock after the Terminal Session ends.
- Successful manual launches additionally update a durable, newest-first launch history under `<data_dir>/terminals/launch-history.json`. Each entry preserves the requested command (including the default-shell choice), exact argument vector, and operator-entered working-directory text; identical configurations move to the front instead of duplicating, the list is capped at 50 entries, and failed launches never enter it. Both durable Terminal files (`launch-history.json`, `groups.json`) are Generation 1 JSON documents (`format_version` 1; contract in `settings.md`): unknown fields survive writes; an invalid or duplicated entry is skipped with a logged warning, written back verbatim and reported by `doctor config`; a file whose document root fails to load reads as empty and is never overwritten - changes then stay in memory with a logged warning until the file is repaired or removed. The 50-entry cap applies to the valid launch entries.
- Terminal Sessions are grouped for operator display. A Session's **effective group** is: the `finished` retention group once it is `exited`/`error`; otherwise its explicit `group_id` when it names an existing user/agent group; otherwise the automatic group `auto:manual` for operator-started terminals or `auto:agent:<agent_id>` per Agent owner. Groups exist in four kinds: **user** groups (durable, created/renamed/deleted by the operator, survive restarts, persist while empty), **agent** groups (created by the terminal Tool via its `group` name parameter, in-memory only, deleted by the operator or disappear on restart), **automatic** groups (synthesized per Agent and for manual terminals, never durable, hidden when empty), and the single **finished** retention group (present only while it holds retained finished sessions). User groups persist under `<data_dir>/terminals/groups.json`; agent/automatic/finished groups are never persisted. Deleting a user or agent group kills every live terminal in it (they land in the finished group like an explicit kill) and removes the group; automatic and finished groups cannot be deleted. Group names are unique case-insensitively across user and agent groups; the Agent Tool reuses any matching existing group instead of creating a duplicate. Group create/rename/delete log INFO with the `grp_` id (and kind), never the name, which is operator or Agent text (`test_user_groups_are_unique_persistent_and_renamable`).
- Within a user or agent group, a user-set terminal order can be stored (`group.order`); the default order is newest-first for live and finished terminals, a user-set order is authoritative, and newly spawned terminals append at the end. The order persists only for user groups.

## Command sessions

The shell Tool (`tools/shell.md`) starts each command through the command API; the Tool owns Agent-facing wording, this domain owns the mechanics. A command session is a Terminal Session of kind `command` (200x50, exact environment from `command_environment`) with a `CommandState` (`_terminal_command.py`) and a process tree tracked from the start (`_terminal_process_tree.py`; a tree that cannot be tracked is not started).

- `spawn_command(owner, argv, command=, description=, cwd=, env=, timeout_seconds=, formatter=, origin_run_id=, execution_owner=)` -> terminal id. The session is hidden (no catalog row, Terminal list entry or change callback) until `hand_off_command`. Capacity: 64 live commands (`TERMINAL_MAX_LIVE_COMMANDS`), separate from the interactive limits. A Run id passed to `cancel_run` is rejected.
- `wait_command(id, seconds=, idle_seconds=, progress=)` -> `exited` (the command ended, see End below) | `deadline` | `idle`. Idle means no new output or input and under 0.15 s CPU in the whole tree for `idle_seconds` (and no new process); only a command whose shell still runs turns idle. `progress` receives the newest 40 screen rows at most every 0.5 s while output arrives.
- The idle rule has one shared baseline per command (`_QuietWatch` in `TerminalSession._quiet`): output or Agent/operator input ends a quiet period, and the next one's CPU baseline is taken once activity paused for 1 s - by the reader on a read timeout, by a wait polling every 0.5 s, or by a status check - so a check right after a pause does not have to wait another 15 s. `command_idle_seconds(id)` -> the seconds since the last output or input while the command meets the idle rule for `COMMAND_IDLE_SECONDS` (15 s) now, else None (it works, or its shell exited); the shell result's idle text states them.
- `wait(id, owner, seconds=, pattern=, after_revision=, on_match=)` serves `terminal wait` for both kinds (`on_match` receives the line where a match starts) (Agent Tool contract below). For a command it ends only at the command's end (`exited`), a `pattern` match or the timeout - never `quiet`, so a build that prints a line, then works silently, keeps a wait until it ends (eval round 1 E2: every quiet-ended wait after the next line cost another call); the result tells an idle command apart through `command_idle_seconds` (`test_command_wait_ends_only_at_exit_match_or_timeout`). After a match, a command's wait lingers up to `_COMMAND_MATCH_EXIT_SECONDS` (2 s) and ends `exited` when the command ends in that time, so a final line such as `BUILD OK` returns the exit code instead of a running command (eval round 2: 4 of 5 build runs reported an exit code they had not seen after a `matched` result); a server's ready line costs those 2 s (`exit-right-after-match` in `test_a_command_exit_a_kept_result_showed_is_not_delivered_again`).
- `wait_for_reply(id, owner, seconds=, after_quiet=)` serves `input`'s wait for both kinds: `exited`, `quiet` once a quiet boundary follows the input (`send_input` reports the session's `quiet_boundaries` count, which every quiet boundary after activity raises, a command's included although it sets no attention; input restarts the quiet timer, so input without output settles too), or `timeout`.
- `stop_command(id, reason)` writes Ctrl+C, waits 3 s for the shell, then kills the tree; reasons `timeout`, `user`, `agent`, `run_cancelled`, `shutdown` (the first wins). `timeout_seconds` arms this from the start and keeps running after a hand-off and after the shell's exit, until the session finishes: processes the shell left running are killed when it fires. Before the command ended, that records the stop reason; after it ended (quiet processes), the stop reason stays unset (`test_survivors_keep_a_finished_command_live_until_they_are_killed`); and when its own Ctrl+C makes the shell exit, the kill follows at once (`test_timeout_interrupts_the_command_and_reports_why_it_stopped`).
- `hand_off_command(id, deliver=)` lists the session (`_publish_state`, change callbacks fire); with `deliver`, the command's end sets `exited` attention whose body is `formatter(report)` and submits it through TriggerService like any terminal delivery. An Agent `terminal kill` terminates the tree at once (reason `agent`) and suppresses the delivery; `cancel_run` touches only commands still in the foreground (hidden), which have no delivery. `kill_for_operator` on a command runs `stop_command("user")`, which delivers a "the user stopped it" result. A command records no `output_settled` attention and Agent input on it arms no activity delivery: its output is its result, delivered when it ends. A durable result that showed the end acknowledges it (`acknowledge_exit`), so the delivery is withdrawn or never submitted (`test_a_command_exit_a_kept_result_showed_is_not_delivered_again`). A command stays attached to the Session that ran it: `attach` from another Session raises `TerminalIsCommandError` (the Tool never gets there, because other Sessions cannot see the command), `attach` from its own Session changes nothing, and `detach` always raises it.
- `command_report(id)` -> `CommandReport` (`exited` once the command ended, exit code, stop reason, transcript head/tail, failed direct children, processes still running after the end, seconds until the timeout stops what still runs); `command_view(id, rows)` -> the report and the output after its transcript, both taken under the session lock (`tools/shell.md` -> Interfaces); `command_status(id)` -> `running`/`completed`/`failed`/`stopped` for a listed command, None otherwise; `command_screen(id, lines)`; `wait_finished(id)` waits until no process of the tree runs.
- Transcript: on shell exit and again at the command's end the screen and its scrollback are committed as final logical lines (`TerminalEmulator`/render host `commit_transcript`; `pending_transcript` reads the rows it would commit without committing them), written to a private `artifacts/temp/commands` log file (mode 0600 on POSIX, 72 h retention) and held as the first 40 and last 80 lines (each at most 65,536 characters in memory). After the final lines the log file holds the rendered rows that are not final yet (`pending_transcript`), rewritten after output at most every `COMMAND_LOG_REFRESH_SECONDS` (1 s) and on the next read timeout, so it has the whole output while the command runs; committed lines replace those rows (`CommandState.show_pending`, `TerminalSession._refresh_log`).
- End: the shell's exit is detected by a liveness check every 0.5 s plus up to 1 s draining its last output. The command ends at the shell's exit when no process it started still runs; otherwise once those processes ended (with up to 1 s draining their last output) or went quiet - no output, no new process and under 0.15 s CPU for `COMMAND_LEFTOVER_QUIET_SECONDS` (2 s), checked by the tree poll every second (`TerminalSession._settle_leftovers`). Working leftovers - a GUI-subsystem program PowerShell did not wait for - so hold the command, and their output is part of its result; a quiet server ends it (`test_working_processes_left_running_hold_the_command_until_their_output_is_complete`, `test_quiet_processes_left_running_are_reported_and_listed`). The `exited` attention is set at the command's end: at once when quiet processes still run, otherwise once the session has finished. Processes still running keep the session unfinished; the tree is polled every second until it ends or is killed (kill, timeout, Run cancellation, shutdown). A tree that cannot be inspected counts as running: during reading the poll just continues, after the output ended a WARNING logs when the check starts failing and an INFO when it recovers.
- `cancel_run(run_id)` (a Run cancel callback, `core/chat/_run_state.py`) waits for pending launches of that Run and terminates its command sessions still in the foreground (hidden) with `run_cancelled`; handed-off commands keep running and deliver their result (the user's "Stop all" stops them); `release_run` forgets the marker after the Run settled. `shutdown_commands()` stops every command with reason `shutdown` before Trigger delivery closes, so handed-off commands deliver their stopped result (`runtime.md` -> Shutdown).
- Interactive sessions are unaffected by Run cancellation (below).

## Agent Tool contract

The voice companion uses operator APIs, preserving Agent bindings: `terminal.read` projects rendered output without updating Agent observation state; optional `expected_screen_revision` on `terminal.input` rejects stale input under the existing session lock. Optional `expected_program` (a command name such as `codex`) writes only while that program runs in the Terminal's process tree - the Terminal's own process or a descendant that is not stopped, identified by its name, executable, first argument, or, for `node`/`bun`, its script or npm package (`process_tree_runs` in `core/utils/processes.py`, injectable as `TerminalManager(program_probe=...)`); the check runs under the same lock right before the write, fails closed when the tree cannot be inspected, and rejects with `TerminalProgramNotRunningError` (RPC code `terminal_program_not_running`). Coverage: `test_operator_input_expecting_a_program_writes_only_while_it_runs` in `test_terminal_manager_operator.py`, `tests/core/utils/test_processes.py`, `tests/server/rpc/test_terminal_methods.py`. `terminal.programs` (`running_programs_for_operator`) answers, with the same probe off the Event Loop, whether each unfinished manual Terminal still runs the program of its launch command (file name without extension), keyed by terminal id; plain shells are left out. A manual Terminal's shell outlives its program, so its state alone cannot tell (`test_operator_reads_whether_each_terminal_still_runs_its_launch_program`). It is a separate method so `terminal.list`, which the UI calls often, never scans process trees. The underlying Terminal capability remains program-agnostic. Voice-specific launch constraints and UI operations live in `model_tasks/live-operator.md`.

`core/tools/terminal.py` exposes one open flat action schema and performs semantic validation; `core/tools/_terminal_arguments.py` normalizes each call before central validation (see the argument-dialects bullet below). Actions (`TERMINAL_ACTIONS`): `start`, `list`, `status`, `wait`, `input`, `kill`, `attach`, `detach`. Advertised parameters: `action`, `terminal_id`, `command`, `args`, `workdir`, `name`, `group`, `text`, `key`, `data`, `lines` (schema default 30), `pattern`, `timeout` (seconds, schema default 60). Accepted but unadvertised (`TERMINAL_UNADVERTISED_PARAMETERS`): `timeout_ms`; `start_line` (results carry ready paging calls); `expected_screen_revision` and `after_revision` (the terminal tracks both itself, and no result shows a revision); `columns`/`rows` (on `start` only). The description opens with the boundary - interactive programs driven by typing (REPLs, TUIs, coding-agent CLIs) and commands the shell Tool left running here; commands that finish on their own belong to the shell Tool - then says that a program outlives the turn and which messages arrive on their own. `project_terminal_tool_definitions(definitions)`, called by Chat's request builder after the shell projection, fits the description and the `terminal_id` text to the Tools offered: the shell Tool's Model name appears only when it is offered. Sub-Agents (Session depth >= 1) get the same definition and behavior as top-level Agents (user decision 2026-10-05). Coverage: `test_definition_follows_flat_action_conventions_within_its_budget` (exact properties, budget <= 760 tokens) and `test_definition_fits_the_offered_tools` in `test_terminal.py`.

An omitted `command` opens the host user's default interactive shell - the same selection the manual operator path uses: on Windows `pwsh.exe`, then `powershell.exe`, then `%COMSPEC%`/`cmd.exe`; on POSIX `$SHELL`, then the account login shell, then `/bin/sh`. A provided `command` launches that exact executable with the given `args`. Either way the default working directory is the current one with 80 columns and 24 rows; there is no program-specific default executable. `workdir` accepts absolute and relative filesystem paths plus the unadvertised exact prefix `project:<project-id>`, which the resolver shared with the shell Tool (`core/tools/_workdir.py`) resolves to the registered Project's live `cwd` by stable id before spawn. The Project reference changes only the child start directory: it does not load Project Context, change Rooting, or reassign Terminal ownership, and a spawned process does not move if the Project is later re-pointed. A missing Project returns `project_not_found`; an invalid/unreadable Project record or unreachable Project `cwd` returns `project_unavailable`; an empty id or a path that is not a directory returns `invalid_arguments`; all fail before process creation and before a named `group` is created (`test_start_rejects_unresolvable_workdirs_before_spawn`).

- `start`: launches exact `[command, *args]`, records immutable Agent provenance and lifecycle scope, and attaches the new Terminal Session to the current Session. It then waits (`TerminalManager.wait_for_startup`, at most `TERMINAL_START_WAIT_SECONDS` = 10 s from the start) until the start-up output paused for the 2-second activity quiet period - with `text`, until the output after the typed text settled - or the program ended, and returns that screen: `terminal_id`, `state`, `exit_code` once ended, `screen`, and `history`/`scrollback` when present, so a program that exits at once shows its end and last screen, and a start with a task shows the program's first reply. Optional `text` is sent followed by Enter once the screen is stable (output, then 0.5 s quiet, at most 15 s); line breaks ending it are dropped, since Enter follows anyway. When `start` returns before the text was typed, a `note` says it is typed once the screen stops changing; when the output after it has not settled yet (snapshot `initial_output_pending`), a `note` says the text was submitted, to `wait` for its output and not to send it again (terminal review R6). Optional `name` (trimmed, max 80 chars) is a conversation label between Agent and operator; optional `group` (max 80 chars) names a group the Terminal joins - an existing user/agent group with that name is reused, otherwise a non-durable agent group is created. Unadvertised `columns`/`rows` set a start size within the operator bounds (40-240 x 10-80). A `command` containing whitespace that names no program but whose first word (split with the host's quoting; backslashes stay literal on Windows) is a program on the login-environment PATH starts as those words plus any `args`, with a `note`; a path with spaces that exists stays one program. A non-empty `terminal_id` naming a live (not exited or errored) terminal fails before launch with the input call that types into it; any other `terminal_id`, including a finished terminal's, is ignored with a note naming the assigned id. Coverage: the start tests in `test_terminal.py` and `test_terminal_dialects.py`.
- `list`: one row per terminal the Session can see - interactive terminals of every Session and command terminals of this Session only (`_visible`: the command's attachment or lifecycle scope is the calling Session). A row holds `terminal_id`, `program` (`TerminalInfo.program`: the Agent's shell command for a command terminal, the requested program of a manual terminal, otherwise the started command line; its first line, at most 80 chars), `name`, `state`, `exit_code` once ended, and `attached` (`here` | `other` | `no`); empty values are omitted. Discovery grants no control: `wait`, `input` and `kill` on a terminal not attached to the calling Session return `terminal_not_owned` naming the attach call, or the `status` call when another Session holds it; `terminal_not_found` is reserved for an id the Session cannot see. Its Tool row derives an exact presentation-only `results` count from `terminals`; other actions and failures publish no count.
- `attach`: binds one running interactive Terminal Session with no attachment to the current Session without changing its process, rendered content, PTY dimensions, provenance, lifecycle scope, or WebUI behavior, and returns its `list` row. Repeating it from the same Session succeeds with a note that nothing changed; another Session's attachment returns `terminal_already_attached` naming the `status` call that reads it without attaching. A successful attachment authorizes `wait`, `input`, and `kill`, records the current Run as the automatic-delivery origin, ignores pre-attachment attention, and arms the current activity cycle for its next quiet boundary. On a command terminal of the calling Session it changes nothing and says so.
- `detach`: requires the current Session's exact attachment and removes only that binding plus its pending delivery state; the process, provenance, lifecycle scope, rendered content, dimensions, and WebUI behavior remain unchanged. A mismatched caller receives `terminal_not_attached`. A command terminal refuses with `command_terminal`, naming the `kill` call, because detaching would drop the delivery of its result (interface audit defect 1). A deliberate attachment transfer is two explicit operations, `detach` followed by `attach`; there is no implicit `reattach` action.
- `status` reads any terminal the Session can see, attached or not, without attaching it or acknowledging anything (`TerminalManager.read`), except that a default read by the attached Session acknowledges (screen-bearing results below). On an interactive terminal it returns `terminal_id`, `state`, `exit_code` once ended, the launch facts (`program`, `title`, `workdir`, `log`, `name`; `log` is the sentence `Everything the program printed is written live to <raw log>, as raw text with its terminal control sequences.`), up to `lines` history lines right above the screen (default 30, at most 100) and the `screen`; a terminal not attached here adds `attached` and a `next` naming the attach call, or saying that another Session holds it. Model-facing `workdir` and raw-log paths use the shared forward-slash presentation while spawn and manager state retain native paths. History and screen lines carry stable line numbers that never shift as output arrives or old lines are evicted: `scrollback.first_line` is the oldest retained line, `screen_start_line` the first screen line, and `total_lines` the end. An unadvertised `start_line` returns only the page starting there (clamped to the retained range; a page may reach into the screen) without a separate `screen`; `lines` sets the page size. `history` holds the page text; `scrollback` reports `first_line`, `start_line`, `end_line`, `total_lines`, `screen_start_line`, and ready-made `status` requests `older_request`/`newer_request` for the adjacent pages (`newer_request` only on an explicit `start_line` page, because the default page ends at the screen). Default reads include `scrollback` only when there is history or an older page. A program on the alternate screen keeps no terminal history: `status` then adds a `note` to use the program's own scrolling or paging. History pages never acknowledge attention or screen/resize observations. On a command terminal `status` returns the shell result (command terminals below), and `lines`/`start_line` only add a note that the result shows the output and names the file with the complete output when it shows only part. A `cursor` argument is rejected as unknown. Evidence: `TerminalEmulator.page` and `_screen_result` in `terminal.py`; coverage: `test_status_pages_the_whole_buffer_by_absolute_start_line` and `test_only_a_persisted_current_screen_acknowledges_resize_and_attention` in `test_terminal_observation.py`, and the attach test in `test_terminal.py` (status of an unattached terminal).
- Screen-bearing Tool results (`start`, a default `status` by the attached Session, `wait`, `input` on an interactive terminal) remember the delivered screen revision and dimensions only after result persistence. After any later real resize, the next screen result includes `size_change` with the previously observed dimensions and a notice to use the current screen positions; repeated resizes collapse into one notice, including a return to the former size. Reads without persistence and operator views never consume it, older callbacks cannot roll back the baseline or consume a newer resize, and a new attachment starts without another Session's observation. Resize alone schedules no Agent delivery; output after resizing follows the repaint rule under Generic activity delivery. The snapshot carries the shown screen as a hidden `observation` (`TerminalObservation`: screen revision, resize count, dimensions) that the Tool passes back. Evidence: `TerminalManager.acknowledge_screen`, `_acknowledge_after_persistence` in `terminal.py`, and the resize-observation tests in `test_terminal_observation.py`.
- `wait` waits up to `timeout` seconds (default 60, at most `TERMINAL_WAIT_MAX_SECONDS` = 600; `0` means 600; a longer one is capped, and a capped wait that timed out says so in a `note`) until the program exits, its output matches `pattern`, or - without `pattern`, for an interactive program - its new output settles, and returns `wait_ended`: `exited` | `matched` | `quiet` | `timeout` (`TerminalManager.wait`). `timeout_ms` is accepted and reconciled with `timeout` by the shell Tool's `resolve_timeout`, which notes a millisecond-sized `timeout` and refuses disagreeing values. `pattern` is a Python regular expression compiled with `IGNORECASE | MULTILINE` (`^`/`$` at every line) and searched in the rendered output as logical lines (`TerminalEmulator.pattern_text`: rows an auto-wrapped line fills are joined), including output printed before the call - except, once the Agent typed (`send_input` -> `mark_input`), the lines up to and including the cursor's line at that input, which hold earlier output and the input's echo, wrapped continuation rows included; after a screen clear (ED 2/3, RIS on the primary screen) the cleared screen's lines count again; on the alternate screen only the screen counts. Without input every retained line counts, from the oldest. Later checks of one wait resume at the logical line above the screen. ED 0 from the home position is deliberately no clear: ConPTY repaints with it. Invalid syntax is matched as literal text with a note (terminal review R1, R2). An interactive program's new output settled when an `output_settled` attention above the last acknowledged one (or the unadvertised `after_revision`) exists; with `pattern` that does not end the wait. A command's wait never ends `quiet` (Command sessions above). The user can end a wait as they move a shell call to the background (`background_registration_hook`): the result then has `wait_ended: "user"` and a note that the program keeps running (`test_user_can_end_a_wait_on_a_command`). A wait or `input` that matched adds `matched`, the line where the match starts (at most 500 characters). A wait that timed out says so in a note: with a pattern, that no output matched it within the seconds; on a command, that it did not exit within them. An interactive result is the screen result plus `wait_ended`; a command's is the shell result. A timeout never owns or pauses the child. Coverage: the wait tests in `test_terminal_dialects.py`, `test_pattern_text_holds_the_logical_lines_printed_after_the_last_input` in `test_terminal_emulator.py`, and `test_command_wait_ends_only_at_exit_match_or_timeout` and `test_terminal_reads_answers_and_waits_for_a_command_in_the_shell_result_shape` in `test_terminal_commands.py`.
- `input` returns the reply: after writing it waits (`TerminalManager.wait_for_reply`) until the output settled after the input (the 2-second activity quiet period, which the input itself starts), the program exits, or `TERMINAL_START_WAIT_SECONDS` (10 s) pass, as `start` does for its first screen (eval round 1 E3: after every input came a separate wait). An interactive result is the screen result (`terminal_id`, `state`, `exit_code` once ended, `history`/`screen`/`scrollback`) plus `key` and `bracketed_paste` as below, notes, and - only when the 10 s passed before the output settled - a `next` saying that the reply arrives as a new message, or how to wait for it now. A command's result is the shell result. Unadvertised `timeout`/`timeout_ms` replace the 10 s (capped like `wait`, with the cap note only on a timeout); an unadvertised `pattern` makes `input` wait like `wait` (60 s default) and adds `wait_ended`. The shown screen is acknowledged after persistence like any screen result, so its settle is not delivered again; a reply still printing at the 10 s limit is delivered when it settles, as `next` says.
- `input`: accepts exact `data`, the convenience combination of `text` and/or one named `key`, or empty optional fields that are ignored. `data` cannot be combined with the convenience fields after empty optional values are omitted. If no input remains, the call succeeds as a validated no-op that waits for nothing and returns `terminal_id` with a `note` naming the `status` call; it does not start activity delivery. Use `key: "enter"` to submit text; use `data` for arbitrary or combined sequences. `text` ending in line breaks (`\n`, `\r\n`, `\r`) with `key` omitted or `enter` is submitted: the breaks are dropped and Enter is pressed once, instead of typing them into a pasted block (eval round 1 E4: `"import calc\n"` was pasted and never ran); text alone stays only typed, and the result's `note` says it was not submitted and names the Enter call. Enter is no default, because Agents that send Enter in a second call would answer the next prompt with it. Multiline `text` is wrapped in one bracketed-paste sequence only when the current rendered terminal mode says the foreground program enabled it, while single-line `text`, named keys, and exact `data` retain their ordinary semantics; the result reports `bracketed_paste` only for multiline text. Named keys cover Enter, navigation, Insert/Delete/Home/End/Page Up/Page Down, Shift-Tab, F1-F12, and Ctrl-A through Ctrl-Z; the definition lists them in the `key` description instead of an enum, and the handler rejects another name with the list. The result is the reply (previous bullet); `characters_sent`, which `TerminalManager.send_input` still returns for its callers, is not shown, since the screen shows the text. Input reaches command terminals too (prompts). Unadvertised `expected_screen_revision` rejects stale input with `stale_screen`. Real Agent or operator input advances the observation revision before writing, including input with no echo, so the same guarded observation cannot be reused. Operator input cancels any pending Agent initial-input task; a manual launch command is no input at all (shell start options, see the operator surface below). An empty Agent input leaves the revision, suppression, and pending initial input unchanged. Evidence: `TerminalSession.send_input`/`send_operator_input`, the initial-input regressions in `test_terminal_manager.py`, the guarded-input regressions in `test_terminal_manager_attention.py` / `test_terminal_manager_operator.py`, `test_input_returns_the_reply_once_its_output_settles`, `test_input_types_text_keys_and_exact_data_against_the_current_screen` and `test_enter_flags_and_ending_line_breaks_press_enter_after_the_input` in `test_terminal_dialects.py`, and `test_terminal_reads_answers_and_waits_for_a_command_in_the_shell_result_shape` in `test_terminal_commands.py` (input to a command).
- `kill`: requests termination of the Windows child tree or POSIX process group, suppresses an automatic exit delivery caused by that explicit action, and leaves a bounded exited snapshot until finished-session expiry. An interactive result is `terminal_id`, `state` (`stopped`) and `exit_code`; when the program had already ended it shows the last `screen` and a note that nothing was stopped. On a command terminal the tree is terminated at once (reason `agent`), the result is the shell result with `stopped_because: "you stopped it."`, and nothing is delivered; when the operating system did not end the processes, the call fails with `terminal_failed` saying so, naming the kill call to try again and the status call; when the shell had already exited, the result is the exited shell result with a `note` naming the leftover processes it stopped, or saying that nothing was stopped (terminal review R8; `test_kill_stops_a_command_and_says_what_it_stopped`). A POSIX descendant that has detached into another process group is outside killpg; this is not a guarantee of reclaiming arbitrary escaped descendants. Transport close and bounded reads release reader workers independently of such a descendant retaining the PTY slave.
- Command terminals (commands the shell Tool handed off, `tools/shell.md`): only the Session that ran one sees it (`list` and every action; another Session gets `terminal_not_found`). `status`, `wait`, `input` and `kill` return the shell result through `shell.command_terminal_result` (imported lazily: `status`, `exit_code`, `stopped_because`, `output`, `failed_programs`, `still_running`, `hint`, `next`, plus `wait_ended` on a wait), so a follow-up reads like the call that started the command; the Tool passes how a wait ended (`matched`, `timeout`, or none for `status` and `input`), and the shell Tool words `next` from it (`tools/shell.md`). A result with status `exited` or `stopped` acknowledges the end once persisted, so the result is not delivered again. `input` types into it and returns the shell result once the output settled after the input (above); `attach` and `detach` behave as above. Coverage: the `Tools` harness tests in `test_terminal_commands.py`, which drive both Tools through one registry.
- No `resize` action: the PTY follows the WebUI tile used last (Transport section), and the Agent learns of a change through `size_change`. `resize`/`setsize`/`size` fail before any effect naming the `status` call, and `columns`/`rows` on any action but `start` fail with `invalid_arguments`. The operator resize (`resize_for_operator`) treats the current dimensions as a no-op, otherwise resizes the host PTY/ConPTY and renderer together and, when the terminal is `ready`, opens the repaint window (`test_resize_to_current_dimensions_is_a_no_op`).
- Argument dialects (`normalize_terminal_arguments`, registered as the Tool's argument normalizer): field aliases (`session_id`/`id` and the old shell ids `process_id`/`proc_id`/`bash_id`/`shell_id`/`task_id` -> `terminal_id`, `expected` -> `pattern`, Codex `chars` -> `data`, `input` -> `text`, `cwd` -> `workdir`, `cols` -> `columns`, `yield_time_ms` -> `timeout_ms`, `screen_revision` -> `expected_screen_revision`, `regex`/`until`/`wait_for`/`expect`/`match` -> `pattern`), action spellings (`close`/`stop`/`terminate`/`killshell`/`cancel`/`abort` -> `kill`, `read`/`poll`/`info` -> `status`, `join`/`block` -> `wait`, `type`/`write_stdin`/`send_keys` -> `input`, `submit` -> `input` plus Enter), key spellings (`Ctrl+C`, `^C`, `C-c`, a raw control character, `Return`, `esc`, `ArrowUp`, ...), `enter`/`submit` flags (Enter after text, `\r` appended to `data`, conflict with another key fails), line breaks ending `text` (on `input` with `key` omitted or `enter`: dropped and Enter pressed once; on `start`: dropped), a Codex argv array as `command`, a call without `action` that names `command` and no `terminal_id` as `start` (only start takes a command; eval rounds 2 and 3: one such call per round), and placeholders (`null`, empty strings, empty `args`, zero `columns`/`rows`/`lines`) dropped. Fields another action owns are dropped when they only shape a result, wait, or guard input (`lines`, `start_line`, `after_revision`, `timeout_ms`, `timeout`, `pattern`, `expected_screen_revision`), when they are start labels on another action (`name`, `group`, `workdir`), or when `list` gets a `terminal_id`; `start` drops `key: "enter"`. Input fields on a non-input action, `command`/`args` outside `start`, `columns`/`rows` outside `start`, `data` or another key on `start` fail before any effect with the call that provides the effect. Evidence: `test_terminal_dialects.py`.
- Results never show revisions, attention records, timestamps, dimensions or null values (`_HIDDEN_SNAPSHOT_FIELDS`); `size_change` reports a real resize. Launch facts appear only in `status`; `start`, `wait` and `input` on an interactive terminal show `terminal_id`, `state`, `exit_code` once ended, `history`/`screen`/`scrollback`, and `wait_ended` for waits (and for `input` with the unadvertised `pattern`). No persisted consumer reads these fields. Every error states what happened and the next call with real values (Agent-facing text below); a missing or unknown `terminal_id` names up to 3 terminals attached to the calling Session (running ones first, newest first) or how to find one (`_terminals_text`, `_not_found_message`).
- Detail blocks (`_terminal_detail_blocks`, `tools.md` -> Display metadata): `start` and `input` show what was typed as an `input` text (exact `data` with control characters spelled out as escapes such as `\x1b`, or `text` followed by `<key>`), also when the call failed; a result with `history`, `screen` or `output` shows them by reference as `scrollback`, `screen` and `output` texts; a `stopped` state adds `The program was stopped.`, a `failed` state a warning, an exited program `The program exited.` or a warning naming a non-zero exit code, and a wait that ran out of time `The program was still running when the wait ended.`; `list` shows a `results` block (name, program or id as title; state or `exited with code N` and the attachment as meta) or `No terminal is open.`. Paging requests, notes and `next` stay in the raw result; `attach` and `detach` show Args and Result directly. Coverage: `test_terminal_dialects.py` (input, close, follow-up wait) and `test_terminal_observation.py::test_list_shows_every_terminal_with_its_title_and_attachment`.
- The `name` field is a purely human-facing conversation label: the Agent maps a spoken name to the `terminal_id`, and every Tool call addresses the Session by `terminal_id`, never by `name`. It never affects launching, ownership, or lifecycle. It appears in `list` rows, `attach`/`detach` results and `status`, and labels the terminal in deliveries (else the program); `start`, `wait`, `input`, and `kill` never include it. Agent-owned and manual sessions both expose it in their operator summaries; the operator RPC surface (`terminal.start` with `name`) uses the same trimmed non-blank <=80-char rule. The WebUI tile and list title prefer the custom `name`, then the program-announced `title`, then the launched command.

## Generic activity delivery

Generic terminal bytes cannot reliably distinguish a question, approval request, completed application-level task, idle animation, or prompt. `TerminalManager` therefore emits only `output_settled`, `exited`, and `error` attention kinds and never claims application semantics.

- Agent input starts one activity cycle, changes state to `working`, records the current Run as delivery origin, and arms a two-second quiet timer. Every later PTY output restarts that timer. At quiet, state becomes `ready` and a revisioned `output_settled` record becomes observable. Automatic delivery compares visible cells including attributes, so a changed selection can count even when plain text is unchanged; cursor-only refreshes stay silent. A text-less Agent start stays silent until explicit input or attach. The notification carries the bounded plain-text screen tail (the last 20 lines, `TERMINAL_DELIVERY_TAIL_LINES`), captured together with its screen revision without an intervening await. The body shows no revision (Agent-facing text below); the manager keeps it as the delivered-screen baseline and for the unadvertised `expected_screen_revision` guard, which later input, output, or resize still invalidates before writing. Command terminals never record `output_settled` (Command sessions). `input` waits for this quiet boundary itself and shows the screen; that result acknowledges the screen after persistence like `wait`, so the settle that follows the input is not delivered again unless the screen changed since. Cell attributes affect change detection but are not yet represented in Agent observations. Coverage: `test_notification_revision_authorizes_only_the_delivered_screen` in `test_terminal_manager_attention.py`. Evidence: `TerminalActivity` (`_terminal_activity.py`), `ScreenObservation.signature` in `terminal_emulator.py`, `TerminalSession._settle_after_quiet`, and the manager attention tests.
- A same-dimension resize is a no-op. A real resize of a `ready` terminal opens a 1-second repaint window (`TERMINAL_REPAINT_WINDOW_SECONDS`, the `repainting` phase of `TerminalActivity`, shown as `ready`): output inside it is the program redrawing its screen for the new size. It keeps the state `ready`, wakes nobody, records no attention, and its settled screen becomes the delivery baseline, so a later identical screen stays silent too; a pending Agent delivery stays pending. Agent/operator input closes the window, output after it is ordinary activity, and resizing a `working` terminal opens none. The rule is timing-only: it does not compare repaint content, so real output arriving inside the window after resizing a quiet terminal counts as repaint. Measured on Windows ConPTY, Claude Code 2.1, Codex 0.160 and OpenCode 2.0 redraw in one burst within ~15-125 ms; the multi-wave repaints that motivated the former 4-15 s grace window came from the WebUI sending transient sizes. Evidence: `TerminalActivity.resize`/`output`/`settle`, `TerminalSession.resize`/`_render_output`; `test_repaint_after_resizing_a_quiet_terminal_does_not_wake_agent` and `test_activity_around_a_resize_wakes_agent` in `test_terminal_manager_attention.py`.
- While attached, Agent input, operator input, and spontaneous output use the same state and quiet detection and request automatic delivery at the next quiet boundary; attach also arms an activity cycle already in progress. Initial startup output of a newly Agent-started terminal settles once without a duplicate wakeup unless `start` supplied initial input, after which later attached activity is deliverable. An unattached Terminal Session has no Agent delivery target. Settled revisions remain observable through `wait` only for the attached Session.
- Natural exit and terminal failure create `exited` or `error` attention and request delivery; both bodies carry the last screen lines. Both are set only once the program has ended. An unexpected failure to read its output (ERROR log) stops the reading, and the reader polls the program every second (`COMMAND_TREE_POLL_SECONDS`) until it exits or is killed. A failure to render (WARNING when it starts, INFO when a later chunk renders again) keeps the output read, logged and streamed while the screen misses it, and records no `output_settled` meanwhile. Either failure becomes the `error` outcome when the program ends; a render failure only if rendering had not recovered. A failing raw-log write closes the log with one WARNING, and a refused query reply is ignored; the liveness checks decide. A PTY write that fails (EOF/closed or `OSError`) ends an interactive Session as a natural exit, with the same `exited` delivery and `terminal_closed`, only when its program no longer runs; while it runs, the input fails with `terminal_failed` (`The input could not be written to terminal <id>`) and nothing ends. A command whose shell exited answers `terminal_closed` and finishes with its last process. Explicit kill and scope shutdown suppress that delivery. A durable result that showed the end - a `stopped`, `exited` or `failed` state in a default `status` by the attached Session, `wait`, `input` or `kill`, or a command's `exited`/`stopped` shell result - acknowledges it after persistence (`TerminalManager.acknowledge_exit`): a pending delivery is cancelled and a later one is never scheduled. Coverage: `test_refused_write_ends_the_terminal_only_once_its_program_ended` and `test_terminal_failure_keeps_the_program_until_it_ends_then_delivers_the_error` in `test_terminal_manager_attention.py`.
- Sub-Agent Sessions (depth >= 1) get the same deliveries as top-level Sessions, command results included (user decision 2026-10-05). Verified 2026-10-04 against the Trigger delivery path: an interactive delivery reaches the Sub-Agent while its Run is active; after that Run ended, a delivery starts a Run of its own in the Sub-Agent Session whose answer did not reach the Parent (open finding; Sub-Agent communication is owned by `subagents.md`).
- A default `status` by the attached Session, `wait`, `input`, and `kill` acknowledge an equivalent pending delivery only through `ToolContext.after_result_persisted`; handler return alone is not durable acknowledgement. Session transfer moves matching lifecycle and attachment scopes and reroutes pending delivery without rewriting immutable provenance.

## Transport, rendering, and local operator surface

The renderer answers cursor/status, primary/secondary device-attribute, character-size, and supported mode queries from the canonical terminal state. The Session writes these replies to the PTY under its lock; they are not operator input and never cancel queued Agent input. Queries split across read chunks retain their order. The WebUI suppresses its own query replies (including color/window/status-string reports) and drops viewer focus reports, so observation does not inject duplicate keystrokes. Unsupported reports do not gain capabilities from an attached browser. Every launch sets `TERM=xterm-256color` for the real terminal; explicit launch environment overrides remain authoritative. Evidence: `TerminalEmulator.feed` (`EmulatorUpdate.responses`), `TerminalSession._render_output`, `TerminalManager._start_process`, `TerminalsView.svelte` parser handlers, and the emulator/manager/component tests.

`core/tools/terminal_manager.py` is the public owner of Terminal Session identity, immutable provenance, lifecycle scope, one-Session attachment authorization, and cleanup; each `TerminalSession` carries its activity timing, attention delivery, retained output, and stream sequencing. Durable operator state lives in `core/tools/terminal_store.py` (same domain): the persisted models (`TerminalLaunchHistoryEntry`, `TerminalGroup`, group-id vocabulary), per-entry document parsing for `groups.json`/`launch-history.json` (`parse_groups`/`parse_launch_history` return valid and verbatim invalid entries), and `TerminalOperatorStore`, which holds both live collections, rewrites them atomically on change, degrades a file with an unreadable root to an empty collection with a warning at startup, and owns the newest-first launch-history dedupe/cap policy. The manager keeps every CRUD workflow (including killing sessions on group delete) and re-exports the moved names, so Tool/RPC consumers import from `terminal_manager` unchanged. `core/tools/terminal_backend.py` hides the blocking platform adapter, Windows launcher adaptation, and process-tree termination. Rendering runs off the Event Loop: `TerminalRenderHost` serves each screen from one of up to four renderer workers, each a thread with its own subinterpreter (and GIL) loaded with only `terminal_emulator.py` and pyte, so a program printing heavily does not stall other server work; a screen stays on one worker so its calls stay ordered. When a subinterpreter cannot start, the host renders inline with a warning; tests use `TerminalRenderHost.in_process()`. The manager owns its host unless one is injected and closes it on shutdown. Reads use a manager-owned executor sized for the global live-terminal cap, separate from short adapter operations through `asyncio.to_thread`. Each adapter read waits at most 200 ms for output. POSIX reads the PTY master with nonblocking I/O and incremental UTF-8 decoding; an incomplete character never extends the deadline. Windows reads the ConPTY in a dedicated thread with blocking reads (`_WindowsTerminalAdapter`), not through pywinpty's `PtyProcess`, whose socket relay sleeps 1 ms per read and delivered 3,000 lines seconds after the program ended. ConPTY never ends its output when the program exits, so a second thread waits on the program's process handle and, once its output has paused for 20 ms, wakes the waiting read with a timeout: the Session notices the exit within milliseconds instead of at the next 200 ms deadline. In measurements ConPTY delivered all output before the exit completed. `close()` cancels the pending read until the thread ends. A Session closes its adapter when it finishes, a natural exit included: until then ConPTY keeps the reader thread and its console host (`OpenConsole.exe`) alive (probe 2026-10-05; `test_reader_reads_on_after_idle_timeouts_and_stops_when_the_program_ends`). Stop closes the adapter transport independently of process-tree EOF, then drains/cancels its reader. Idle or inherited open PTY handles cannot permanently consume executor workers. Coverage: bounded adapter reads, the immediate ConPTY exit report (`test_windows_terminal_read_reports_the_program_exit_at_once`), 35 successive closes without tree EOF, and a real PTY/ConPTY output-and-stop test in the backend/manager suites.

- Windows uses `pywinpty`/ConPTY. POSIX opens a PTY with `os.openpty()` and starts the child through `subprocess.Popen` as a session leader (`start_new_session=True`, PTY slave as stdin/stdout/stderr, window size set on the master first) without `preexec_fn`: Python code in a child forked from the multi-threaded server can deadlock it, which is why `ptyprocess`/`forkpty` (Python 3.14 warns about it) is gone. The private guardian (`core/utils/process_guardian.py --controlling-terminal`) makes the PTY the controlling terminal with `TIOCSCTTY` after exec; without server containment it then replaces itself with the declared command, restoring the SIGPIPE/SIGXFSZ default actions Python ignores. Shells therefore have job control, Ctrl-C reaches the foreground job, and a supervising guardian ignores the terminal SIGINT/SIGQUIT meant for its child. A missing program raises `FileNotFoundError` before launch (`_require_program`), so the manager's PATH-refresh retry still applies. A child killed by signal N reports exit code 128+N. The adapter closes the master once, on `close()` (when the Session finishes) or through a finalizer when an adapter is dropped without it; an in-flight read/write keeps the descriptor number from being reused. Packaged Windows servers must start with an attached, windowless console to prevent pywinpty from allocating then hiding a visible console; the native-host requirement belongs to `cli/application.md`. On Windows, resolved `.cmd` or `.bat` launchers use the platform command processor as a generic executable-format adapter; no command name receives special handling. Their arguments are quoted whenever they contain whitespace or a cmd metacharacter, because the batch file's `%*` is parsed by cmd once more (`windows_command_processor_line`; `test_batch_programs_receive_their_arguments_unchanged_through_the_command_processor`); an argument holding both a quote and a metacharacter can still break at that second parse. A process started in a new process group, as the managed Server is, ignores Ctrl+C and its children inherit that, ConPTY children included; before starting a ConPTY child the backend clears it for the Server process (`_accept_console_interrupts`), so Ctrl+C typed into a Terminal stops console programs (`test_ctrl_c_stops_a_terminal_program_of_a_server_that_ignores_ctrl_c`). Windows terminal descendants inherit the server's kill-on-close Job Object. POSIX PTY children run their exact declared command through the same parent-liveness guardian as Process Manager, inside the PTY process group, so abrupt server death kills the terminal tree even though Runtime shutdown cannot run. The guardian is isolated from the terminal's working directory and Python environment, which the program receives unchanged (`tools/os-processes.md` -> Guardian isolation).
- Interactive launches and both Agent/operator default-shell selection use `shell_environment.terminal_environment()`, built fresh for every start: on Windows a fresh user environment block (registry PATH included), on POSIX the server environment, without vBot's own Python/venv variables, plus the instance variables and `TERM` (`tools/shell.md` -> Environment layers); explicit launch environment overrides apply last. An omitted manual command selects an interactive host shell without changing the PTY path. Windows prefers PowerShell 7 (`pwsh.exe`), then Windows PowerShell (`powershell.exe`), and falls back to `%COMSPEC%`/`cmd.exe`; POSIX prefers `$SHELL`, then the account login shell, and finally `/bin/sh`.
- `pyte`, wrapped by `TerminalEmulator`, owns bounded terminal rendering. The emulator preserves a separate primary and alternate screen, resizes both buffers, restores the primary screen on alternate-screen exit, tracks the bracketed-paste mode advertised by the foreground program, serializes the retained primary-screen scrollback followed by the current active screen into one authoritative ANSI snapshot for late WebUI viewers, skips the empty continuation cell of each wide Unicode glyph so snapshots preserve cell positions without inserting spaces or extra wraps, and exposes OSC title/icon metadata as one whitespace-normalized, single-line title capped at 160 characters. Title extraction and terminal-mode tracking are protocol behavior; the manager does not inspect process trees or add program-specific hooks. The authoritative snapshot re-emits the tracked terminal modes before the screen content - alternate screen (`?1049h`), application cursor keys (`?1h`), mouse reporting and other private modes (`?<mode>h`), and bracketed paste (`?2004h`) - so a late viewer lands in the same interactive state as the live terminal instead of rendering a TUI's alternate screen as dead text on the primary screen. Mode tracking lives on the pyte screen subclass (`alternate_active`, `private_modes`, `bracketed_paste_enabled`) and is captured with the screen state, so alternate-screen enter/exit restores the exact prior mode set. pyte ignores the `<`/`>`/`=` CSI prefixes and dispatches the payload as a normal sequence, so xterm keyboard-mode sequences such as `CSI > 4 ; 1 m` (modifyOtherKeys, emitted by opencode2 at startup) are misread as SGR "underscore + bold" - every blank cell written afterwards inherits those attributes and the snapshot paints white underlines under blank rows (the historical white-lines root cause). The emulator therefore strips `CSI <`/`>`/`=` keyboard/DA sequences before feeding pyte (except the secondary device attributes query `CSI > c`, which it answers), holding back an incomplete tail across feed boundaries, including a lone ESC or CSI introducer; do not remove that stripping without a pyte-side fix, and never rewrite output in the WebUI instead (the server renderer and viewer must consume the same bytes).
- The manager publishes an authoritative ANSI history-and-screen snapshot followed by contiguous sequenced output/state events. Replay retains at most 4,096 events and 4 MiB of conservatively measured Python event payloads; each subscriber queue also has a 4 MiB budget besides its event-count limit. Oversized events are not retained, slow subscribers are evicted, and sequence gaps recover through a fresh authoritative snapshot. The optional byte accounting belongs to `core/event_stream.py`; other consumers retain their existing count-only policy. Coverage: `test_event_stream.py` and `test_terminal_snapshots_obey_byte_budget_and_reconnect` in `test_terminal_manager_operator.py`. It additionally publishes a sequenced `terminal_snapshot` after an alternate-screen exit, at the quiet boundary following bracketed-paste disable, and immediately before a final exited/error state; these program-agnostic resynchronization points cover TUIs that clear the primary screen instead of using the alternate buffer. A title change publishes a state event and catalog invalidation even for a non-selected background Terminal Session; finished-session expiry publishes the same invalidation. `server/rpc/terminal_methods.py` maps operator start/list/read/input/kill/forget/programs and the group CRUD/order surface (`terminal.group.create`/`rename`/`delete`/`order`); `terminal.input` serves the voice companion's guarded input. The WebUI's live traffic uses the operator WebSocket `/ws/terminals/{terminal_id}` (`server/_terminal_socket.py`) in both directions: the server streams `terminal_ready` (the authoritative snapshot) followed by sequenced `terminal_output`/`terminal_snapshot`/`terminal_state` events, or one retained snapshot for a finished Session; the viewer sends `{"type": "input", "data"}` and `{"type": "resize", "request", "columns", "rows"}`. One worker per socket applies these requests in arrival order, so keystrokes and sizes reach the PTY in the order the operator made them. A failed input answers `input_failed`; a resize answers `resize_done` (with the operator summary) or `resize_failed`, naming the same request id; a malformed request answers `protocol_error`. Replies carry no sequence. Coverage: `test_terminal_websocket_applies_operator_requests_in_order_and_answers_them` in `tests/server/test_websocket.py`. Requests repeating the known dimensions are dropped client-side and a same-dimension resize is a server-side no-op, so revisiting or rearranging the tab without a size change produces no PTY operation and no repaint. `terminal.list` returns the operator-visible groups (`groups`), the retained Terminal Session catalog with each summary's effective `group_id` (`terminals`), and the durable manual `launch_history`; `terminal.start` accepts an optional command, exact argument list, working directory, dimensions, and group id, then returns the started Terminal Session plus the updated history. `terminal.group.create`/`rename` take a unique name (<=80 chars, blank rejected); `terminal.group.delete` kills the group's live terminals and returns the count; `terminal.group.order` persists a group's terminal order and appends unknown members. A manual terminal is always the operator's interactive default shell, so it behaves like a normal terminal: an omitted command opens a bare shell, and a provided command plus arguments is handed to that shell through its own start options (`shell_launch` in `_terminal_launch.py`) - never typed into it and never spawned as the bare PTY child - so nothing depends on recognizing a prompt or on shell start timing. PowerShell gets `-NoExit -EncodedCommand` (the profile loads first; PowerShell literal strings, the call operator for a quoted executable path, Windows PowerShell native command-line escaping); a batch-file program (such as an npm shim) with an argument containing a quote or cmd metacharacter runs through `cmd.exe --% /d /s /c "<exact line>"` instead, because PowerShell hands such arguments to batch files unprotected. cmd gets `/d /s /k "<line>"` as an exact Windows command line (the adapter factory's `command_line`); bash an `--rcfile` that sources `~/.bashrc` first; zsh a private `ZDOTDIR` whose `.zshenv`/`.zshrc` source the user's files first; fish `-C`; another POSIX shell `/bin/sh -c '<line>; exec <shell>'` with an interrupt trap; another shell on Windows `%COMSPEC% /d /s /c "<line> & <shell>"`. The private rc files live in a temporary directory that the shell removes while loading them and the Session removes when it ends. PowerShell, bash and zsh also enter the line into the shell history (PSReadLine `AddToHistory` once the first prompt idles - PSReadLine drops entries added before it - , `history -s`, `print -s`), so Up recalls it. A started command neither ends the Session nor changes the exit semantics: Ctrl+C or program end returns to the shell prompt and the operator keeps typing. Coverage: `test_terminal_launch.py` (start contracts per shell), `scripts/probe_terminal_shell_command.py` (live real-shell probe). Manual summaries expose `launch_command` and `launch_args` (the operator-requested command) beside `command`/`arguments` (the running shell); the list item and tile show the launched command, and the launch history keeps remembering the requested command with its arguments. The Manager never runs the requested command outside the shell; it resolves it only to recognize a batch file under PowerShell. An empty or blank command or an empty argument rejects.
- `webui/src/lib/terminalsView.js` (with its internal `lib/terminalsView/` modules) owns start, group and retained-catalog and launch-history reconciliation, viewer geometry, and teardown. Each streamed Terminal has one connection owner, `lib/terminalsView/connection.js` (`createTerminalConnection`): its socket, reconnect backoff and connect timeout, sequence-gap recovery, the frame sanitizer, authoritative `terminal_snapshot` application, input batching, and resize requests. Input waits in a bounded backlog (65,536 characters) until the stream is ready (`terminal_ready`) and then goes out over the socket in order, also after a reconnect; a resize request still unanswered when the socket closes is sent again on the next stream. The operator surface uses a horizontally scrolling group bar above the selected group's terminals, so group selection never reserves terminal width: streams open only for the visible group, switching groups closes the outgoing and opens the incoming streams (the same mechanism as tab remount), the default selection is the first non-empty group, and a group's user-set order is applied optimistically before the server confirms it. A terminal that transitions to `exited`/`error` is marked finished immediately: its stream stops reconnecting, buffered input is discarded, and a failed input of an ending terminal is never surfaced as `actionError` (the transition itself is the expected outcome, for example after Ctrl+C or a program exit). The viewer clamps every fitted grid into the server's accepted bounds (40-240 columns, 10-80 rows) so a small tile produces a legal minimum grid instead of a rejected request, sends a debounced socket `resize` only when the fitted grid differs from the session's known dimensions (maximize sends immediately), keeps only the newest pending dimensions behind an in-flight resize (including a return to the prior grid), and adopts the server-confirmed dimensions from the `resize_done` summary. The xterm WebGL addon is intentionally not used - the DOM renderer is the only render path, and the historical white-line sources are documented in `webui.md` Constraints (the WebGL fractional-scale trap plus the pyte keyboard-mode misparse, which is fixed server-side). A canvas layout change (tile count or maximize) re-fits every mounted viewer after the DOM update, not only the newly created tile. `TerminalsView.svelte` dynamically mounts xterm.js, offers a compact New terminal dialog whose Recent setup selector defaults to the newest launch and fills an editable command line and working directory, lets the operator pick a target group (or Automatic), offers create/rename/delete dialogs for user and agent groups (deleting warns that running terminals are stopped), reorders the active group's terminals by drag & drop on the tile bar, focuses a newly started terminal for immediate input, makes every running terminal directly writable when clicked regardless of owner, and rebuilds bounded scrollback from every authoritative snapshot after mount, selection, reconnect, navigation, or a TUI mode/exit resynchronization. Geometry follows one rule (user decision 2026-10-04): the PTY follows the WebUI tile that was used last, so a tile looks like a native terminal. A tile is claimed when it opens and again on typing, pointer input, or a real change of its box (ResizeObserver); a claimed tile fits its box at the 12 px base font with FitAddon, grows the font only when the fit exceeds the server maximum, and sends that grid. Every other viewer of the same Terminal Session mirrors the PTY grid it learns from `terminal_state` (or a failed resize) and shrinks its font down to 4 px rather than clip a larger grid; a grid change its own pending or in-flight resize explains (`resizeSettling`) is ignored. Hidden tiles (zero-size host) keep the PTY at its size. There is no independent Agent grid and no CSS scale; the Agent learns of a size change through `size_change` on its next screen read, and redraws stay silent through the repaint window. Snapshots carry an in-band reset (RIS) so output still queued in xterm cannot land on top of them. A failed list refresh shows its banner above the canvas and keeps the live tiles. The caller receives an error and can retry stopping that same tree. ## Runtime and lifecycle integration

Runtime constructs `TerminalManager` after `TriggerService`, injects the Storage-owned launch-history path, the user-groups path (`<data_dir>/terminals/groups.json`), and atomic-staging root, registers `terminal` before System Prompt assembly, exposes it through `RuntimeServices`, and closes it before temporary-file cleanup. Run cancellation never closes already-started interactive Terminal Sessions (it stops the Run's commands still in the foreground); cancellation while process creation is still pending waits for and disposes that launch. Session deletion, Agent removal, Project removal, and archiving or deleting an Extension's temporary group (`close_scope` per live participant Session, through `core/agents/temporary.py::release_temporary_group`) terminate only matching Agent lifecycle scopes; they detach matching bindings from surviving operator-started or differently scoped terminals. Extension execution-group close (`close_execution_group`) terminates only terminals owned by that exact group epoch without changing attachment authority; it rejects launches for the epoch while pending launches drain and releases that admission marker afterwards, because the group owner closes resources only after every owned Run is terminal (`runs.md` -> Extension execution ownership; `test_terminal_manager.py`). Successful `/agent` moves transfer matching lifecycle and attachment scopes and reroute pending delivery while leaving immutable provenance unchanged. An Identity Agent rename does the same for every scope of that Agent's Sessions (`transfer_agent_scope`, called by `core/runtime/_agent_rename.py`, and again with the ids swapped on a revert): background commands and Terminals keep running, and their completion notices reach the renamed Session. Provenance, and with it the automatic group `auto:agent:<old id>`, keeps the old id (`test_identity_agent_rename_moves_only_that_agents_scopes_and_keeps_provenance`). Operator-started Terminal Sessions end only through explicit stop, natural exit, Runtime shutdown, or the server-level crash boundary. No Terminal Session, retained catalog, or agent/automatic group survives a Runtime restart; the independent manual launch history and user groups do survive. Ended sessions remain in the in-memory retained catalog until the 30-minute expiry or explicit operator forget. `terminal` is an ordinary built-in Tool and is part of the default Project Tool allowlist. The bundled `coding-agents` Skill is the program-agnostic operating playbook for Codex, Claude Code, OpenCode, and future interactive coding-agent CLIs: it maps a coding task onto `start`, says how to read a settled screen and judge the task's success by its results, and when to report a missing CLI; input, wait, delivery and paging guidance lives in the Tool definition and results. References retain CLI-specific launch settings and saved-conversation syntax, with `<angle-bracket>` placeholders for the repository path and task. The Skill prescribes no discovery-first, reuse-first, or new-terminal policy. Reference JSON examples are dispatched through the real Tool registry in `test_terminal.py`, checking exact argv and submitted input.

Focused coverage lives in `tests/core/tools/test_terminal_emulator.py` (VT emulation, paging, query replies, render-host smoke test), `test_terminal_launch.py` (shell-native manual launch), `tests/core/tools/test_terminal_backend.py` (including real Linux PTY contracts, with and without the guardian: no fork warning with other threads running, controlling terminal, resize, Ctrl-C, exit status, missing program, exact working directory and environment in a project whose own `core` package would hide vBot's), the `test_terminal_manager*.py` behavior suites, and `test_terminal.py` / `test_terminal_observation.py` / `test_terminal_dialects.py`, with Runtime, lifecycle, RPC, WebSocket, controller, rendered-component, and bundled-Skill contract coverage in their owning test trees. `tests/e2e/tests/terminal-lifecycle.spec.js` exercises the platform default shell and multiple simultaneous real PTY/ConPTY processes through browser start, native input, foreground and background title changes, background output, selection changes, stream reconstruction, navigation, and selective stop.
