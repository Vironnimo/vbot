# Interactive Terminal Sessions (`terminal`)

## Boundary and invariants

`terminal` gives an Agent a real interactive terminal rather than Bash's pipe-based background processes. Every requested executable uses the same PTY/ConPTY transport and receives the exact declared argument vector. The terminal capability contains no executable detection, program-specific flags, hooks, configuration injection, lifecycle protocol, or screen-text heuristics. Codex, Claude Code, other coding CLIs, shells, editors, games, and arbitrary interactive programs therefore share one contract.

- Every Terminal Session records immutable process provenance (`owner`: the starting Agent Session, or `None` for a local-operator start), an independent lifecycle scope (`lifecycle_owner`: the transferable Agent Session scope that owns cleanup, or `None` for an operator-started process), and at most one mutable Agent Tool/event binding (`attachment`). Agent `start` initializes all three Agent scopes to the current Session; an operator start initializes all three as local/unbound. The local operator can observe and control every active Terminal Session without changing any of them.
- The Agent Tool, WebUI, and child process use the same live PTY/ConPTY. Agent and WebUI input are written to that process, WebUI output is the sequenced raw VT stream, and Agent status is rendered from the same stream.
- A Terminal Session ends only on explicit `kill`, natural child exit, applicable lifecycle-owner Session/Agent/Project removal, Runtime shutdown, or unrecoverable terminal failure. Operator-started sessions have no Agent lifecycle scope and are therefore unaffected by Agent, Session, and Project cleanup even while attached. `detach`, leaving a Run, or navigating away from the WebUI never ends a Terminal Session.
- Starting processes reserve the same per-Session and global capacity as live processes before any worker is launched. Cancellation during creation waits for the launch outcome and stops the resulting child before releasing the reservation; shutdown also waits for pending launches. Already-started Terminal Sessions retain their independent Run lifetime.
- Live states are `starting`, `ready`, and `working`; terminal states are `exited` and `error`. These states describe terminal activity and process lifetime, not application-specific turns or prompts.
- Raw output and rendered history are bounded. The manager retains a finished Terminal Session's metadata and rendered history for 30 minutes so the operator can inspect it as a read-only snapshot; `terminal.forget` may remove that in-memory record sooner. When Storage is available, the manager additionally retains the raw output in a leased `<data_dir>/artifacts/temp/terminals/*.log` and starts the normal temporary-file retention clock after the Terminal Session ends.
- Successful manual launches additionally update a durable, newest-first launch history under `<data_dir>/terminals/launch-history.json`. Each entry preserves the requested command (including the default-shell choice), exact argument vector, and operator-entered working-directory text; identical configurations move to the front instead of duplicating, the list is capped at 50 entries, and failed launches never enter it.
- Terminal Sessions are grouped for operator display. A Session's **effective group** is: the `finished` retention group once it is `exited`/`error`; otherwise its explicit `group_id` when it names an existing user/agent group; otherwise the automatic group `auto:manual` for operator-started terminals or `auto:agent:<agent_id>` per Agent owner. Groups exist in four kinds: **user** groups (durable, created/renamed/deleted by the operator, survive restarts, persist while empty), **agent** groups (created by the terminal Tool via its `group` name parameter, in-memory only, deleted by the operator or disappear on restart), **automatic** groups (synthesized per Agent and for manual terminals, never durable, hidden when empty), and the single **finished** retention group (present only while it holds retained finished sessions). User groups persist under `<data_dir>/terminals/groups.json`; agent/automatic/finished groups are never persisted. Deleting a user or agent group kills every live terminal in it (they land in the finished group like an explicit kill) and removes the group; automatic and finished groups cannot be deleted. Group names are unique case-insensitively across user and agent groups; the Agent Tool reuses any matching existing group instead of creating a duplicate.
- Within a user or agent group, a user-set terminal order can be stored (`group.order`); the default order is newest-first for live and finished terminals, a user-set order is authoritative, and newly spawned terminals append at the end. The order persists only for user groups.

## Agent Tool contract

`core/tools/terminal.py` exposes one open flat action schema and performs action-specific accepted-field and semantic validation. Its model-facing description starts with the selection boundary: use a real PTY/ConPTY when a program waits for interactive input or must be operated by typing into and observing its live screen, such as a REPL, TUI, prompt, or debugger. An omitted `command` opens the host user's default interactive shell - the same selection the manual operator path uses: on Windows `pwsh.exe`, then `powershell.exe`, then `%COMSPEC%`/`cmd.exe`; on POSIX `$SHELL`, then the account login shell, then `/bin/sh`. A provided `command` launches that exact executable with the given `args`. Either way the default working directory is the current one with 120 columns and 32 rows; there is no program-specific default executable. Its existing `workdir` string accepts ordinary absolute and relative filesystem paths plus the reserved exact prefix `project:<project-id>`, which resolves the registered Project's live `cwd` by stable id before spawn. The Project reference changes only the child start directory: it does not load Project Context, change Rooting, or reassign Terminal ownership, and a spawned process does not move if the Project is later re-pointed. A missing Project returns `project_not_found`; an invalid/unreadable Project record or unreachable Project `cwd` returns `project_unavailable`; all fail before process creation.

- `start`: launches exact `[command, *args]`, records immutable Agent provenance and lifecycle scope, and automatically attaches the new Terminal Session to the current Session; optional `text` waits for a stable initial TUI screen and then sends text followed by Enter; optional `name` labels the Session (max 80 chars) as a conversation label between Agent and operator; optional `group` (max 80 chars) names a group the Terminal joins - an existing user/agent group with that name is reused, otherwise a non-durable agent group is created. The Session always starts at the default 120x32 grid; the Agent Tool no longer accepts `columns`/`rows` for `start` (they remain `resize`-only). The result explains that the Terminal Session survives the Run and that output settling is not a semantic completion signal.
- `list`: returns compact summaries for all discoverable retained Terminal Sessions, including the bounded title announced through the standard terminal protocol when present, the human-friendly `name` when set, and `attachment: current | none | other` relative to the calling Session. Discovery grants no operational access; attempting a controlling action (`status`, `wait`, `input`, `resize`, `kill`) or `detach` against a listed Session that is not attached to the calling Session returns `terminal_not_owned` with a message telling the Agent to `attach` it first - it is NOT `terminal_not_found`, which is reserved for a Terminal Session that genuinely does not exist. Its Tool row derives an exact presentation-only `results` count from `terminals`; other actions and failures publish no count.
- `attach`: binds one running Terminal Session with no attachment to the current Session without changing its process, rendered content, PTY dimensions, provenance, lifecycle scope, or WebUI behavior. Repeating it from the same Session is idempotent; another Session's attachment returns `terminal_already_attached` instead of silently taking over. A successful attachment authorizes `status`, `wait`, `input`, `resize`, and `kill`, records the current Run as the automatic-delivery origin, ignores pre-attachment attention, and arms the current activity cycle for its next quiet boundary.
- `detach`: requires the current Session's exact attachment and removes only that binding plus its pending delivery state; the process, provenance, lifecycle scope, rendered content, dimensions, and WebUI behavior remain unchanged. A mismatched caller receives `terminal_not_attached`. A deliberate attachment transfer is therefore two explicit operations, `detach` followed by `attach`; there is no implicit `reattach` action.
- `status`: returns the current rendered screen, up to 30 prior scrollback lines by default, at most 100 lines, process facts, dimensions, screen/activity revisions, the bounded program-announced title, and the raw-log path when available. Model-facing `workdir` and raw-log paths use the shared forward-slash presentation while spawn and manager state retain native paths. The whole buffer is addressable by absolute zero-based line numbers: an optional `start_line` (0 = oldest retained scrollback line; the current screen follows the scrollback) pages forward with plain numbers, optional `lines` selects the page size within the 1-100 bound, and the result reports `scrollback.total_lines`, `start_line`, `end_line`, `next_start_line`, `cursor_row` (scrollback length + on-screen cursor row), and `viewport_rows` - the Hermes `read_terminal`-style one-call page for long agent/build logs. When older output remains, `scrollback.next_request` is a complete copy-ready `status` request carrying `start_line` and the current page size; callers should follow it until null rather than reading the raw VT log as ordinary rendered output. The signed `cursor` continuation and the manager-side cursor encoding were removed in favor of this single plain-number addressing; a `cursor` argument is rejected as unknown. The default (no `start_line`) reads the newest lines and still exposes `total_lines`/`cursor_row` so the model always knows where it stands.
- `wait`: waits at most 1,000 ms by default and 10,000 ms maximum for a newer generic activity revision, exit, or error. A timeout is a successful current snapshot with `timed_out=true`; it never owns or pauses the child.
- `input`: accepts exact `data`, the convenience combination of `text` and/or one named `key`, or empty optional fields that are ignored. `data` cannot be combined with the convenience fields after empty optional values are omitted. If no input remains, the call succeeds as a validated no-op with `characters_sent: 0` and does not start activity delivery. Use `key: "enter"` to submit text; use `data` for arbitrary or combined sequences. Multiline `text` is wrapped in one bracketed-paste sequence only when the current rendered terminal mode says the foreground program enabled it, while single-line `text`, named keys, and exact `data` retain their ordinary semantics. Named keys cover Enter, navigation, Insert/Delete/Home/End/Page Up/Page Down, Shift-Tab, F1-F12, and Ctrl-A through Ctrl-Z; arbitrary sequences use `data`. Optional `expected_screen_revision` rejects stale input.
- `resize`: validates conservative bounds, treats a resize repeating the current dimensions as a no-op, otherwise resizes the host PTY/ConPTY and renderer together and arms the post-resize delivery grace window; it returns the dimensions and screen revision either way.
- `kill`: terminates the complete child process tree, suppresses an automatic exit delivery caused by that explicit action, and leaves a bounded exited snapshot until finished-session expiry.
- The `name` field is a purely human-facing conversation label: the Agent maps a spoken name to the `terminal_id`, and every Tool call addresses the Session by `terminal_id`, never by `name`. It never affects launching, ownership, or lifecycle. The name appears only where it can change or be discovered: `start` (the assigned label), `list` and `status` (lookup context). `wait`, `input`, `resize`, and `kill` never include it. Agent-owned and manual sessions both expose it in their operator summaries; the operator RPC surface (`terminal.start` with `name`) uses the same trimmed non-blank <=80-char rule. The WebUI tile and list title prefer the custom `name`, then the program-announced `title`, then the launched command.

## Generic activity delivery

Generic terminal bytes cannot reliably distinguish a question, approval request, completed application-level task, idle animation, or prompt. `TerminalManager` therefore emits only `output_settled`, `exited`, and `error` attention kinds and never claims application semantics.

- Agent input starts one activity cycle, changes state to `working`, records the current Run as delivery origin, and arms a two-second quiet timer. Every later PTY output restarts that timer. When the stream stays quiet, state becomes `ready`, a monotonically revisioned `output_settled` record is created, and `TriggerService.submit_completion` wakes the owning vBot Session - unless the rendered screen is unchanged since the last delivered settle (status refreshes, cursor frames, and repaint echoes that write bytes but keep the screen identical are not work and stay silent). Two further noise sources are suppressed generically: a text-less Agent start stays silent until the first explicit input or attach (the startup screen - banner, prompt, TUI boot - is observed by the starting Agent and visible to the operator, and its identical status refreshes stay silent too), and after a real resize settle deliveries stay suppressed until the repainted screen is observed stable across two consecutive quiet boundaries, then that stable screen becomes the new already-seen baseline (TUIs repaint the same content at the new size in several waves whose intermediate frames differ - re-wrapped lines, redrawn border, status refresh - so a single-settle swallow is not enough; the post-resize grace deadline bounds this gate, and identical refreshes afterwards stay silent via the signature rule while a genuinely changed screen delivers normally). All three clear on input. The notification embeds a bounded tail of the current rendered screen (`screen_tail`, newest 20 non-blank rows, ANSI-stripped) so the Agent can usually act without a follow-up `status` call, and still says that quiet output does not imply completion or a need for input.
- An explicit resize repeating the current dimensions is a server-side no-op that never touches the PTY. A real dimension change arms a post-resize grace window: output settling inside it updates screen, state, and revisions but creates no agent delivery, because the foreground program's repaint is viewer noise rather than work. Repaint output inside the base window (4 s) extends that window rollingly, while every output inside the hard deadline (15 s) stays suppressed - a TUI whose repaint arrives in several waves cannot leak a wakeup, and a genuinely long-running stream still delivers once the cap expires. Agent or operator input clears the grace entirely: what the user types in response to the new dimensions is work, so the next settle delivers immediately. An already pending undelivered wakeup is not withdrawn by the grace window.
- While attached, Agent input, operator input, and spontaneous output use the same state and quiet detection and request automatic delivery at the next quiet boundary; attach also arms an activity cycle already in progress. Initial startup output of a newly Agent-started terminal settles once without a duplicate wakeup unless `start` supplied initial input, after which later attached activity is deliverable. An unattached Terminal Session has no Agent delivery target. Settled revisions remain observable through `wait` only for the attached Session.
- Natural exit and terminal failure create `exited` or `error` attention and request delivery. A PTY write that reports EOF/closed before the reader observes process exit is treated as natural exit, marks the Terminal Session finished, and requests the same `exited` delivery instead of escaping as an unexpected Tool or operator RPC error. Explicit kill and scope shutdown suppress that delivery.
- `status`, `wait`, `input`, and `kill` acknowledge an equivalent pending delivery only through `ToolContext.after_result_persisted`; handler return alone is not durable acknowledgement. Session transfer moves matching lifecycle and attachment scopes and reroutes pending delivery without rewriting immutable provenance.

## Transport, rendering, and local operator surface

`core/tools/terminal_manager.py` is the deep owner of Terminal Session identity, immutable provenance, lifecycle scope, one-Session attachment authorization, activity timing, attention delivery, retained output, stream sequencing, and cleanup. Durable operator state lives in `core/tools/terminal_store.py` (same domain): the persisted models (`TerminalLaunchHistoryEntry`, `TerminalGroup`, group-id vocabulary), strict document parsing for `groups.json`/`launch-history.json`, and `TerminalOperatorStore`, which holds both live collections, rewrites them atomically on change, degrades a corrupt file to an empty collection with a warning at startup, and owns the newest-first launch-history dedupe/cap policy. The manager keeps every CRUD workflow (including killing sessions on group delete) and re-exports the moved names, so Tool/RPC consumers import from `terminal_manager` unchanged. `core/tools/terminal_backend.py` hides the blocking platform adapter, VT renderer, alternate-screen handling, Windows launcher adaptation, and process-tree termination. Blocking reads use a manager-owned executor sized for the global live-terminal cap, separate from short adapter operations through `asyncio.to_thread`. Idle readers must never exhaust the workers needed for input, resize, stop, or process creation; shutdown closes the reader executor after stopping its children.

- Windows uses `pywinpty`/ConPTY and POSIX uses `ptyprocess`/PTY. On Windows, resolved `.cmd` or `.bat` launchers use the platform command processor as a generic executable-format adapter; no command name receives special handling. Windows terminal descendants inherit the server's kill-on-close Job Object. POSIX PTY children run their exact declared command through the same parent-liveness guardian as Process Manager, inside the PTY process group, so abrupt server death kills the terminal tree even though Runtime shutdown cannot run.
- An omitted manual command selects an interactive host shell without changing the PTY path. Windows prefers PowerShell 7 (`pwsh.exe`), then Windows PowerShell (`powershell.exe`), and falls back to `%COMSPEC%`/`cmd.exe`; POSIX prefers `$SHELL`, then the account login shell, and finally `/bin/sh`.
- `pyte` owns bounded terminal rendering. The renderer preserves a separate primary and alternate screen, resizes both buffers, restores the primary screen on alternate-screen exit, tracks the bracketed-paste mode advertised by the foreground program, serializes the retained primary-screen scrollback followed by the current active screen into one authoritative ANSI snapshot for late WebUI viewers, skips the empty continuation cell of each wide Unicode glyph so snapshots preserve cell positions without inserting spaces or extra wraps, and exposes OSC title/icon metadata as one whitespace-normalized, single-line title capped at 160 characters. Title extraction and terminal-mode tracking are protocol behavior; the manager does not inspect process trees or add program-specific hooks. The authoritative snapshot re-emits the tracked terminal modes before the screen content - alternate screen (`?1049h`), application cursor keys (`?1h`), mouse reporting and other private modes (`?<mode>h`), and bracketed paste (`?2004h`) - so a late viewer lands in the same interactive state as the live terminal instead of rendering a TUI's alternate screen as dead text on the primary screen. Mode tracking lives on the pyte screen subclass (`alternate_active`, `private_modes`, `bracketed_paste_enabled`) and is captured with the screen state, so alternate-screen enter/exit restores the exact prior mode set. pyte ignores the `<`/`>`/`=` CSI prefixes and dispatches the payload as a normal sequence, so xterm keyboard-mode sequences such as `CSI > 4 ; 1 m` (modifyOtherKeys, emitted by opencode2 at startup) are misread as SGR "underscore + bold" - every blank cell written afterwards inherits those attributes and the snapshot paints white underlines under blank rows (the historical white-lines root cause). The renderer therefore strips `CSI <`/`>`/`=` keyboard/DA sequences before feeding pyte, holding back an incomplete tail across feed boundaries, including a lone ESC or CSI introducer; do not remove that stripping without a pyte-side fix, and never rewrite output in the WebUI instead (the server renderer and viewer must consume the same bytes).
- The manager publishes an authoritative ANSI history-and-screen snapshot followed by contiguous sequenced output/state events. It additionally publishes a sequenced `terminal_snapshot` after an alternate-screen exit, at the quiet boundary following bracketed-paste disable, and immediately before a final exited/error state; these program-agnostic resynchronization points cover TUIs that clear the primary screen instead of using the alternate buffer. A title change publishes a state event and catalog invalidation even for a non-selected background Terminal Session; finished-session expiry publishes the same invalidation. `server/rpc/terminal_methods.py` maps operator start/list/input/resize/kill/forget, the group CRUD/order surface (`terminal.group.create`/`rename`/`delete`/`order`), and `/ws/terminals/{terminal_id}` carries the selected live stream or one retained finished snapshot. Operator resize is an explicit PTY operation through `terminal.resize`. The WebUI sends it only when its fitted grid differs from the session's authoritative columns/rows: requests repeating the known dimensions are dropped client-side (including any pending burst ending at the current size), and the server additionally treats a same-dimension resize as a no-op, so revisiting or rearranging the tab without a size change produces no PTY operation and no repaint. `terminal.list` returns the operator-visible groups (`groups`), the retained Terminal Session catalog with each summary's effective `group_id` (`terminals`), and the durable manual `launch_history`; `terminal.start` accepts an optional command, exact argument list, working directory, dimensions, and group id, then returns the started Terminal Session plus the updated history. `terminal.group.create`/`rename` take a unique name (<=80 chars, blank rejected); `terminal.group.delete` kills the group's live terminals and returns the count; `terminal.group.order` persists a group's terminal order and appends unknown members. A manual terminal is always the operator's interactive default shell, so it behaves like a normal terminal: an omitted command opens a bare shell, and a provided command plus arguments is entered into that shell like typed input (exact `data`, then Enter) once a stable prompt screen is rendered - never spawned as the bare PTY child and never sent through bracketed paste or the Agent `send_input` contract. The entered command uses the actual host shell's argument grammar: POSIX literal quoting, PowerShell literal strings and the call operator for quoted executable paths, Windows PowerShell native command-line escaping, and cmd metacharacter escaping for native arguments. The pre-command output and typed line remain visible in rendered history. Real-shell regression coverage checks spaced paths, quotes, backslashes, variable-like strings, and metacharacters. The launch command runs in its own `operator_command_task` (bounded shell-readiness wait, written once, then Enter), never in the Agent initial-input slot: operator input that arrives while the shell is still booting waits for that task instead of cancelling it, so the WebUI's immediate focus after start cannot lose or corrupt the command. A started command inside the shell neither ends the Session nor changes the exit semantics: Ctrl+C or program end returns to the shell prompt and the operator keeps typing. Manual summaries expose `launch_command` and `launch_args` (the operator-requested command) beside `command`/`arguments` (the running shell); the list item and tile show the launched command, and the launch history keeps remembering the requested command with its arguments. The Manager never resolves or executes the requested command itself; an empty or blank command rejects, and a command that never sees a stable prompt (silent shell, no prompt marker) is simply not entered.
- `webui/src/lib/terminalsView.js` owns start, group and retained-catalog and launch-history reconciliation, stream reconnect and gap recovery, authoritative `terminal_snapshot` application, exact per-terminal xterm input batching, viewer geometry, and teardown. The operator surface uses a horizontally scrolling group bar above the selected group's terminals, so group selection never reserves terminal width: streams open only for the visible group, switching groups closes the outgoing and opens the incoming streams (the same mechanism as tab remount), the default selection is the first non-empty group, and a group's user-set order is applied optimistically before the server confirms it. A terminal that transitions to `exited`/`error` is marked finished immediately: its stream stops reconnecting, buffered input is discarded, and a terminal-closed RPC error from an in-flight request is never surfaced as `actionError` (the transition itself is the expected outcome, for example after Ctrl+C or a program exit). The viewer clamps every fitted grid into the server's accepted bounds (40-240 columns, 10-80 rows) so a small tile produces a legal minimum grid instead of a rejected request, sends a debounced `terminal.resize` only when the fitted grid differs from the session's known dimensions (maximize sends immediately), keeps only the newest pending dimensions behind an in-flight resize (including a return to the prior grid), and adopts the server-confirmed dimensions from the RPC response's `terminal` summary. A completed request confirming a different grid remains visible as a mismatch instead of causing a reactive retry loop; failed requests remain retryable. The xterm WebGL addon is intentionally not used - the DOM renderer is the only render path, and the historical white-line sources are documented in `webui.md` Constraints (the WebGL fractional-scale trap plus the pyte keyboard-mode misparse, which is fixed server-side). A canvas layout change (tile count or maximize) re-fits every mounted viewer after the DOM update, not only the newly created tile. `TerminalsView.svelte` dynamically mounts xterm.js, offers a New terminal dialog whose Recent setup selector defaults to and fills all fields from the newest launch, lets the operator pick a target group (or Automatic), offers create/rename/delete dialogs for user and agent groups (deleting warns that running terminals are stopped), reorders the active group's terminals by drag & drop on the tile bar, focuses a newly started terminal for immediate input, makes every running terminal directly writable when clicked regardless of owner, and rebuilds bounded scrollback from every authoritative snapshot after mount, selection, reconnect, navigation, or a TUI mode/exit resynchronization. The browser renderer fits each xterm.js instance to its tile by adjusting font size, so the TUI fills the tile at full resolution while inverse pointer mapping preserves canonical mouse cells. Finished Terminal Sessions remain selectable as read-only history until manager expiry. The group bar and compact tile bar prefer the program-announced title; before one exists they humanize known default shell executable names while retaining the exact command in detail metadata. There is no Observe/Take control state, secondary text composer, or program-specific input path. Navigation and socket teardown never own the Terminal Session lifetime. The single close action removes the tile from the canvas immediately (optimistic) and runs the server-side stop and catalog removal in the background; a failed stop restores the session from the server list and surfaces the error. The production Vite build deliberately uses Terser: esbuild minification of xterm 6.0.0's DEC-mode query handler can emit an undeclared enum variable and make nvim output fail at runtime even though the unminified dependency is valid.

## Runtime and lifecycle integration

Runtime constructs `TerminalManager` after `TriggerService`, injects the Storage-owned launch-history path, the user-groups path (`<data_dir>/terminals/groups.json`), and atomic-staging root, registers `terminal` before System Prompt assembly, exposes it through `RuntimeServices`, and closes it before temporary-file cleanup. Run cancellation never closes already-started Terminal Sessions; cancellation while process creation is still pending waits for and disposes that launch. Session deletion, Agent removal, and Project removal terminate only matching Agent lifecycle scopes; they detach matching bindings from surviving operator-started or differently scoped terminals. Successful `/agent` moves transfer matching lifecycle and attachment scopes and reroute pending delivery while leaving immutable provenance unchanged. Operator-started Terminal Sessions end only through explicit stop, natural exit, terminal failure, Runtime shutdown, or the server-level crash boundary. No Terminal Session, retained catalog, or agent/automatic group survives a Runtime restart; the independent manual launch history and user groups do survive. Ended sessions remain in the in-memory retained catalog until the 30-minute expiry or explicit operator forget. `terminal` is an ordinary built-in Tool and is part of the default Project Tool allowlist. The bundled `coding-agents` Skill is the program-agnostic operating playbook for Codex, Claude Code, OpenCode, and future interactive coding-agent CLIs: it starts, attaches, or reuses normal TUI commands through `terminal`, handles questions and approvals against the current screen revision, and preserves the live `terminal_id` across Runs instead of requiring binary-specific headless modes.

Focused coverage lives in `tests/core/tools/test_terminal_backend.py`, `test_terminal_manager.py`, and `test_terminal.py`, with Runtime, lifecycle, RPC, WebSocket, controller, rendered-component, and bundled-Skill contract coverage in their owning test trees. `tests/e2e/tests/terminal-lifecycle.spec.js` exercises the platform default shell and multiple simultaneous real PTY/ConPTY processes through browser start, native input, foreground and background title changes, background output, selection changes, stream reconstruction, navigation, and selective stop. Real Windows validation must use actual ConPTY programs and an unmodified installed Codex CLI because fake adapters cannot prove executable launch fidelity, alternate-screen rendering, browser keyboard/paste behavior, resize, or process-tree stop.
