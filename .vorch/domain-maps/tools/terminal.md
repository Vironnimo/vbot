# Interactive Terminal Sessions (`terminal`)

`terminal_manager.py` owns Session admission, attachment/lifecycle scope, and shutdown coordination. Its internal catalog (`_terminal_catalog.py`) owns groups, ordering and operator summaries; `_terminal_events.py` owns streamed state and rendered observations; `_terminal_io.py` drives PTY input/output, initial-command readiness, activity and completion delivery. `_terminal_input.py` contains shell/input encoding, and `_terminal_state.py` holds Session values, limits and resource cleanup. Each component receives explicit Session/data dependencies, never the manager. The public manager and Tool contracts remain unchanged.

New Terminal Session ids use `term_` plus 12 lowercase base32 characters, allocated against the retained catalog after async launch and before synchronous publication. Created groups use `grp_` with the same suffix; automatic group identities stay deterministic (`terminal_manager.py`, `test_terminal_manager.py`).

## Boundary and invariants

`terminal` gives an Agent a real interactive terminal rather than Bash's pipe-based background processes. Every requested executable uses the same PTY/ConPTY transport and receives the exact declared argument vector. The terminal capability contains no executable detection, program-specific flags, hooks, configuration injection, lifecycle protocol, or screen-text heuristics. Codex, Claude Code, other coding CLIs, shells, editors, games, and arbitrary interactive programs therefore share one contract.

- Every Terminal Session records immutable process provenance (`owner`: the starting Agent Session, or `None` for a local-operator start), an independent lifecycle scope (`lifecycle_owner`: the transferable Agent Session scope that owns cleanup, or `None` for an operator-started process), and at most one mutable Agent Tool/event binding (`attachment`). Agent `start` initializes all three Agent scopes to the current Session; an operator start initializes all three as local/unbound. The local operator can observe and control every active Terminal Session without changing any of them.
- The Agent Tool, WebUI, and child process use the same live PTY/ConPTY. Agent and WebUI input are written to that process, WebUI output is the sequenced raw VT stream, and Agent status is rendered from the same stream.
- A Terminal Session ends only on explicit `kill`, natural child exit, applicable lifecycle-owner Session/Agent/Project removal, Runtime shutdown, or unrecoverable terminal failure. Operator-started sessions have no Agent lifecycle scope and are therefore unaffected by Agent, Session, and Project cleanup even while attached. `detach`, leaving a Run, or navigating away from the WebUI never ends a Terminal Session.
- Launch failures wrapped by `TerminalManager` reach the Agent as `terminal_launch_failed` with the original launch message; the Tool does not guess the cause from a generic filesystem exception. Failed launches release their capacity and retain no Terminal Session. Evidence: `test_dispatch_returns_launch_failure_and_releases_capacity` in `test_terminal.py`.
- Starting processes reserve the same per-Session and global capacity as live processes before any worker is launched. Cancellation during creation waits for the launch outcome and stops the resulting child before releasing the reservation; shutdown also waits for pending launches. Already-started Terminal Sessions retain their independent Run lifetime.
- Live states are `starting`, `ready`, and `working`; terminal states are `exited` and `error`. These states describe terminal activity and process lifetime, not application-specific turns or prompts.
- Raw output and rendered history are bounded. The manager retains a finished Terminal Session's metadata and rendered history for 30 minutes so the operator can inspect it as a read-only snapshot; `terminal.forget` may remove that in-memory record sooner. When Storage is available, the manager additionally retains the raw output in a leased `<data_dir>/artifacts/temp/terminals/*.log` and starts the normal temporary-file retention clock after the Terminal Session ends.
- Successful manual launches additionally update a durable, newest-first launch history under `<data_dir>/terminals/launch-history.json`. Each entry preserves the requested command (including the default-shell choice), exact argument vector, and operator-entered working-directory text; identical configurations move to the front instead of duplicating, the list is capped at 50 entries, and failed launches never enter it. Both durable Terminal files (`launch-history.json`, `groups.json`) are Generation 1 JSON documents (`format_version` 1; contract in `settings.md`): unknown fields survive writes; an invalid or duplicated entry is skipped with a logged warning, written back verbatim and reported by `doctor config`; a file whose document root fails to load reads as empty and is never overwritten - changes then stay in memory with a logged warning until the file is repaired or removed. The 50-entry cap applies to the valid launch entries.
- Terminal Sessions are grouped for operator display. A Session's **effective group** is: the `finished` retention group once it is `exited`/`error`; otherwise its explicit `group_id` when it names an existing user/agent group; otherwise the automatic group `auto:manual` for operator-started terminals or `auto:agent:<agent_id>` per Agent owner. Groups exist in four kinds: **user** groups (durable, created/renamed/deleted by the operator, survive restarts, persist while empty), **agent** groups (created by the terminal Tool via its `group` name parameter, in-memory only, deleted by the operator or disappear on restart), **automatic** groups (synthesized per Agent and for manual terminals, never durable, hidden when empty), and the single **finished** retention group (present only while it holds retained finished sessions). User groups persist under `<data_dir>/terminals/groups.json`; agent/automatic/finished groups are never persisted. Deleting a user or agent group kills every live terminal in it (they land in the finished group like an explicit kill) and removes the group; automatic and finished groups cannot be deleted. Group names are unique case-insensitively across user and agent groups; the Agent Tool reuses any matching existing group instead of creating a duplicate.
- Within a user or agent group, a user-set terminal order can be stored (`group.order`); the default order is newest-first for live and finished terminals, a user-set order is authoritative, and newly spawned terminals append at the end. The order persists only for user groups.

Bash/Process launches unattended commands with stdin closed and offers no later input. Prepared command pipelines and test-owned child pipes remain Bash capabilities; operating a program through later Agent input belongs here (`bash.py`, `process.py`, `process_manager.py`; input regression tests in `tests/core/tools/test_bash.py`).

## Agent Tool contract

The voice companion uses operator APIs, preserving Agent bindings: `terminal.read` projects rendered output without updating Agent observation state; optional `expected_screen_revision` on `terminal.input` rejects stale input under the existing session lock. Optional `expected_program` (a command name such as `codex`) writes only while that program runs in the Terminal's process tree - the Terminal's own process or a descendant that is not stopped, identified by its name, executable, first argument, or, for `node`/`bun`, its script or npm package (`process_tree_runs` in `core/utils/processes.py`, injectable as `TerminalManager(program_probe=...)`); the check runs under the same lock right before the write, fails closed when the tree cannot be inspected, and rejects with `TerminalProgramNotRunningError` (RPC code `terminal_program_not_running`). Coverage: `test_operator_input_expecting_a_program_writes_only_while_it_runs`, `tests/core/utils/test_processes.py`, `tests/server/rpc/test_terminal_methods.py`. The underlying Terminal capability remains program-agnostic. Voice-specific launch constraints and UI operations live in `model_tasks/live.md`.

`core/tools/terminal.py` exposes one open flat action schema and performs semantic validation; `core/tools/_terminal_arguments.py` normalizes each call before central validation (see the argument-dialects bullet below). Its model-facing description starts with the selection boundary: use a real PTY/ConPTY when a program waits for interactive input or must be operated by typing into and observing its live screen, such as a REPL, TUI, prompt, or debugger. An omitted `command` opens the host user's default interactive shell - the same selection the manual operator path uses: on Windows `pwsh.exe`, then `powershell.exe`, then `%COMSPEC%`/`cmd.exe`; on POSIX `$SHELL`, then the account login shell, then `/bin/sh`. A provided `command` launches that exact executable with the given `args`. Either way the default working directory is the current one with 80 columns and 24 rows; there is no program-specific default executable. Its existing `workdir` string accepts ordinary absolute and relative filesystem paths plus the reserved exact prefix `project:<project-id>`, which resolves the registered Project's live `cwd` by stable id before spawn. The Project reference changes only the child start directory: it does not load Project Context, change Rooting, or reassign Terminal ownership, and a spawned process does not move if the Project is later re-pointed. A missing Project returns `project_not_found`; an invalid/unreadable Project record or unreachable Project `cwd` returns `project_unavailable`; all fail before process creation.

- `start`: launches exact `[command, *args]`, records immutable Agent provenance and lifecycle scope, and automatically attaches the new Terminal Session to the current Session; optional `text` waits for a stable initial TUI screen and then sends text followed by Enter; optional `name` labels the Session (max 80 chars) as a conversation label between Agent and operator; optional `group` (max 80 chars) names a group the Terminal joins - an existing user/agent group with that name is reused, otherwise a non-durable agent group is created. The Session starts at the default 80x24 grid unless the call names `columns`/`rows`, which `start` accepts within the `resize` bounds although the definition describes them for `resize` only. A `command` containing whitespace that names no program but whose first word (split with the host's quoting; backslashes stay literal on Windows) is a program on the login-environment PATH starts as those words plus any `args`, with a `note`; a path with spaces that exists stays one program. A non-empty `terminal_id` naming a live (not exited or errored) terminal fails before launch with the input call that types into it; any other `terminal_id`, including a finished terminal's, is ignored with a note naming the assigned id. The result carries `delivery: automatic_terminal_activity`; the Tool description, not the result, explains notifications.
- `list`: returns compact summaries for all discoverable retained Terminal Sessions, including the bounded title announced through the standard terminal protocol when present, the human-friendly `name` when set, and `attachment: current | none | other` relative to the calling Session. Discovery grants no operational access; attempting a controlling action (`status`, `wait`, `input`, `resize`, `kill`) or `detach` against a listed Session that is not attached to the calling Session returns `terminal_not_owned` with a message telling the Agent to `attach` it first - it is NOT `terminal_not_found`, which is reserved for a Terminal Session that genuinely does not exist. Its Tool row derives an exact presentation-only `results` count from `terminals`; other actions and failures publish no count.
- `attach`: binds one running Terminal Session with no attachment to the current Session without changing its process, rendered content, PTY dimensions, provenance, lifecycle scope, or WebUI behavior. Repeating it from the same Session is idempotent; another Session's attachment returns `terminal_already_attached` instead of silently taking over. A successful attachment authorizes `status`, `wait`, `input`, `resize`, and `kill`, records the current Run as the automatic-delivery origin, ignores pre-attachment attention, and arms the current activity cycle for its next quiet boundary.
- `detach`: requires the current Session's exact attachment and removes only that binding plus its pending delivery state; the process, provenance, lifecycle scope, rendered content, dimensions, and WebUI behavior remain unchanged. A mismatched caller receives `terminal_not_attached`. A deliberate attachment transfer is therefore two explicit operations, `detach` followed by `attach`; there is no implicit `reattach` action.
- `status`: returns the current rendered screen, up to 30 prior scrollback lines by default, at most 100 lines, process facts, dimensions, screen/activity revisions, the bounded program-announced title, and the raw-log path when available. Model-facing `workdir` and raw-log paths use the shared forward-slash presentation while spawn and manager state retain native paths. The whole buffer is addressable by absolute zero-based line numbers: an optional `start_line` (0 = oldest retained scrollback line; the current screen follows the scrollback) pages forward with plain numbers, optional `lines` selects the page size within the 1-100 bound, and the result reports the page text as the multi-line `history` field plus the paging facts in `scrollback`: `total_lines`, `start_line`, `end_line`, `next_start_line`, `cursor_row` (scrollback length + on-screen cursor row), and `viewport_rows` - the Hermes `read_terminal`-style one-call page for long agent/build logs. When older output remains, `scrollback.next_request` contains a `status` request carrying `start_line` and the current page size. Current pagination caveat: the default tail page points backward once, but explicit `start_line` pages continue forward, so following the default continuation until null does not recover all older output. Complete traversal currently requires starting explicitly at `start_line: 0` and following forward continuations; indices are relative to the retained buffer and shift when old lines are evicted. Evidence: `TerminalRenderer.page`/`page_from` in `terminal_backend.py`; reproduced in `.vorch/terminal-integration-audit.md`. The signed `cursor` continuation and the manager-side cursor encoding were removed in favor of this single plain-number addressing; a `cursor` argument is rejected as unknown. The default (no `start_line`) reads the newest lines and still exposes `total_lines`/`cursor_row` so the model always knows where it stands. Explicit `start_line` Tool results contain only the requested page in `history`, omitting the separate `screen` to avoid duplicate current-screen content. Default reads include `scrollback` only when there is history or an older page. Such history reads do not acknowledge attention or screen/resize observations; a normal screen-bearing read or actual input retains that responsibility. Operator and manager snapshots retain their existing screen shape. Coverage: `test_status_pages_forward_with_absolute_start_line` and `test_history_page_does_not_acknowledge_an_unseen_resize_or_attention` in `test_terminal.py`.
- Screen-bearing Tool results (`start`, default `status`, `wait`, `kill`) remember the delivered screen revision and dimensions only after result persistence. After any later real resize, the next screen result includes `size_change` with the previously observed dimensions and a notice to use the current screen positions; repeated resizes collapse into one notice, including a return to the former size. Reads without persistence and operator views never consume it, older callbacks cannot roll back the baseline or consume a newer resize, and a new attachment starts without another Session's observation. Resize alone schedules no Agent delivery; ambiguous output after resizing retains the generic quiet/grace delivery rules. Evidence: `TerminalManager.acknowledge_screen`, `_snapshot_data`, `_acknowledge_after_persistence`, and the resize-observation tests in `test_terminal.py` / `test_terminal_manager.py`.
- `wait`: waits 5,000 ms by default (longer than the 2 s quiet period, so a default wait can observe a settle) and at most 10,000 ms for a newer generic activity revision, exit, or error. A larger `timeout_ms` is capped; when the wait then times out the result carries a `note`. An unadvertised `timeout` in seconds is accepted and reconciled with `timeout_ms` by the shell Tool's `resolve_timeout`. `after_revision` is accepted but no longer advertised; by default the wait goes beyond the acknowledged revision. A timeout is a successful current snapshot with `timed_out=true`; it never owns or pauses the child.
- `input`: accepts exact `data`, the convenience combination of `text` and/or one named `key`, or empty optional fields that are ignored. `data` cannot be combined with the convenience fields after empty optional values are omitted. If no input remains, the call succeeds as a validated no-op with `characters_sent: 0` and does not start activity delivery. Use `key: "enter"` to submit text; use `data` for arbitrary or combined sequences. Multiline `text` is wrapped in one bracketed-paste sequence only when the current rendered terminal mode says the foreground program enabled it, while single-line `text`, named keys, and exact `data` retain their ordinary semantics. Named keys cover Enter, navigation, Insert/Delete/Home/End/Page Up/Page Down, Shift-Tab, F1-F12, and Ctrl-A through Ctrl-Z; arbitrary sequences use `data`. The definition lists them in the `key` description instead of an enum; the handler rejects another name with the list. An optional `timeout_ms` (or `timeout`) makes `input` wait like `wait` for the reply to settle after the input and return the shaped screen with `timed_out` (plus `delivery` when it timed out); zero means no wait, and no input sent means no wait. Optional `expected_screen_revision` rejects stale input. Real Agent or operator input advances the observation revision before writing, including input with no echo, so the same guarded observation cannot be reused. Operator input cancels any pending Agent initial-input task; the separate manual shell launch command retains its existing queue-before-input behavior. An empty Agent input leaves the revision, suppression, and pending initial input unchanged. Evidence: `send_input`, `send_operator_input`, and the guarded-input/initial-input regressions in `test_terminal_manager.py`.
- Argument dialects (`normalize_terminal_arguments`, registered as the Tool's argument normalizer): field aliases (`session_id`/`id` -> `terminal_id`, Codex `chars` -> `data`, `input` -> `text`, `cwd` -> `workdir`, `cols` -> `columns`, `yield_time_ms` -> `timeout_ms`, `screen_revision` -> `expected_screen_revision`), action spellings (`close`/`stop`/`terminate` -> `kill`, `read`/`poll` -> `status`, `type`/`write_stdin`/`send_keys` -> `input`, `submit` -> `input` plus Enter), key spellings (`Ctrl+C`, `^C`, `C-c`, a raw control character, `Return`, `esc`, `ArrowUp`, ...), `enter`/`submit` flags (Enter after text, `\r` appended to `data`, conflict with another key fails), a Codex argv array as `command`, and placeholders (`null`, empty strings, empty `args`, zero `columns`/`rows`/`lines`) dropped. Fields another action owns are dropped when they only shape a result, wait, or guard input (`lines`, `start_line`, `after_revision`, `timeout_ms`, `timeout`, `expected_screen_revision`), when they are start labels on another action (`name`, `group`, `workdir`), or when `list` gets a `terminal_id`; `start` drops `key: "enter"`. Input fields on a non-input action, `command`/`args` outside `start`, `columns`/`rows` outside `start`/`resize`, `data` or another key on `start` fail before any effect with the call that provides the effect. Evidence: `test_terminal_dialects.py`.
- Results: screen-bearing results omit the attention record, `attention_revision`, timestamps, and null values. `start` shows the launch facts (command, non-empty arguments, workdir, dimensions) without `log_file`; `status` also shows `title`, `name`, and `log_file`; `wait`, `kill`, and `input` with a wait show only `terminal_id`, `state`, `exit_code`, `screen_revision`, `history`, `screen`, `scrollback` when needed, and `columns`/`rows` only with a `size_change`. `list` rows omit null and empty values. No persisted consumer reads these fields. A missing `terminal_id` or an unknown id lists up to 3 terminals attached to the calling Session (live and newest first) or says how to find one; a `proc_` id points to the process Tool; `terminal_not_owned` names the exact attach call, or says another Session holds the attachment.
- `resize`: validates conservative bounds, treats a resize repeating the current dimensions as a no-op, otherwise resizes the host PTY/ConPTY and renderer together and arms the post-resize delivery grace window; it returns the dimensions and screen revision either way.
- `kill`: requests termination of the Windows child tree or POSIX process group, suppresses an automatic exit delivery caused by that explicit action, and leaves a bounded exited snapshot until finished-session expiry. A POSIX descendant that has detached into another process group is outside killpg; this is not a guarantee of reclaiming arbitrary escaped descendants. Transport close and bounded reads release reader workers independently of such a descendant retaining the PTY slave.
- The `name` field is a purely human-facing conversation label: the Agent maps a spoken name to the `terminal_id`, and every Tool call addresses the Session by `terminal_id`, never by `name`. It never affects launching, ownership, or lifecycle. The name appears only where it can change or be discovered: `start` (the assigned label), `list` and `status` (lookup context). `wait`, `input`, `resize`, and `kill` never include it. Agent-owned and manual sessions both expose it in their operator summaries; the operator RPC surface (`terminal.start` with `name`) uses the same trimmed non-blank <=80-char rule. The WebUI tile and list title prefer the custom `name`, then the program-announced `title`, then the launched command.

## Generic activity delivery

Generic terminal bytes cannot reliably distinguish a question, approval request, completed application-level task, idle animation, or prompt. `TerminalManager` therefore emits only `output_settled`, `exited`, and `error` attention kinds and never claims application semantics.

- Agent input starts one activity cycle, changes state to `working`, records the current Run as delivery origin, and arms a two-second quiet timer. Every later PTY output restarts that timer. At quiet, state becomes `ready` and a revisioned `output_settled` record becomes observable. Automatic delivery compares visible cells including attributes, so a changed selection can count even when plain text is unchanged; cursor-only refreshes stay silent. A text-less Agent start stays silent until explicit input or attach. The notification includes the bounded plain-text screen tail and its `screen_revision`, captured together without an intervening await. The Agent can pass that revision as `expected_screen_revision` directly; later input, output, or resize still rejects stale input before writing. The Tool definition and bundled Skill explain the delivered screen and additional `status` reads; start results do not repeat this guidance. Cell attributes affect change detection but are not yet represented in Agent observations. Coverage: `test_notification_revision_authorizes_only_the_delivered_screen` in `test_terminal_manager_attention.py`. Evidence: `TerminalRenderer.screen_signature`, `_settle_after_quiet`, and the terminal backend/manager tests.
- A same-dimension resize is a no-op. A real resize coalesces subsequent output delivery in a rolling 4-second window capped at 15 seconds after the resize. Quiet boundaries remain observable and acknowledgeable during this window. The quiet task stays alive to deliver the latest unacknowledged changed screen when the window ends, even if no further output arrives. Repeated identical output does not make an undelivered answer an observed baseline. Agent/operator input clears the delay; new output replaces the deferred boundary; durable acknowledgement, detach, exit, and shutdown prevent stale deferred delivery. The terminal does not infer whether changed output is a repaint or an application answer. Evidence: `_resize_session`, `_read_terminal`, `_settle_after_quiet`, `acknowledge_attention`, and resize delivery regressions in `test_terminal_manager_resize.py`.
- While attached, Agent input, operator input, and spontaneous output use the same state and quiet detection and request automatic delivery at the next quiet boundary; attach also arms an activity cycle already in progress. Initial startup output of a newly Agent-started terminal settles once without a duplicate wakeup unless `start` supplied initial input, after which later attached activity is deliverable. An unattached Terminal Session has no Agent delivery target. Settled revisions remain observable through `wait` only for the attached Session.
- Natural exit and terminal failure create `exited` or `error` attention and request delivery. A PTY write that reports EOF/closed before the reader observes process exit is treated as natural exit, marks the Terminal Session finished, and requests the same `exited` delivery instead of escaping as an unexpected Tool or operator RPC error. Explicit kill and scope shutdown suppress that delivery.
- Default `status`, `wait`, `input`, and `kill` acknowledge an equivalent pending delivery only through `ToolContext.after_result_persisted`; handler return alone is not durable acknowledgement. Session transfer moves matching lifecycle and attachment scopes and reroutes pending delivery without rewriting immutable provenance.

## Transport, rendering, and local operator surface

The renderer answers cursor/status, primary/secondary device-attribute, character-size, and supported mode queries from the canonical terminal state. The manager drains these replies directly to the PTY under its lock; they are not operator input and never cancel queued Agent input. Queries split across read chunks retain their order. The WebUI suppresses its own query replies (including color/window/status-string reports) and drops viewer focus reports, so observation does not inject duplicate keystrokes. Unsupported reports do not gain capabilities from an attached browser. A service-inherited missing, empty, or `dumb` TERM becomes `xterm-256color` for the real terminal; explicit launch environment overrides remain authoritative. Evidence: `TerminalRenderer.feed`/`take_responses`, `_read_terminal`/`_spawn`, `TerminalsView.svelte` parser handlers, and terminal backend/manager/component tests. Live Windows verification with an unmodified Codex CLI and two simultaneous viewers is recorded in `.vorch/terminal-integration-audit.md`.

`core/tools/terminal_manager.py` is the deep owner of Terminal Session identity, immutable provenance, lifecycle scope, one-Session attachment authorization, activity timing, attention delivery, retained output, stream sequencing, and cleanup. Durable operator state lives in `core/tools/terminal_store.py` (same domain): the persisted models (`TerminalLaunchHistoryEntry`, `TerminalGroup`, group-id vocabulary), per-entry document parsing for `groups.json`/`launch-history.json` (`parse_groups`/`parse_launch_history` return valid and verbatim invalid entries), and `TerminalOperatorStore`, which holds both live collections, rewrites them atomically on change, degrades a file with an unreadable root to an empty collection with a warning at startup, and owns the newest-first launch-history dedupe/cap policy. The manager keeps every CRUD workflow (including killing sessions on group delete) and re-exports the moved names, so Tool/RPC consumers import from `terminal_manager` unchanged. `core/tools/terminal_backend.py` hides the blocking platform adapter, VT renderer, alternate-screen handling, Windows launcher adaptation, and process-tree termination. Reads use a manager-owned executor sized for the global live-terminal cap, separate from short adapter operations through `asyncio.to_thread`. Each native socket/PTY read has a 200 ms readiness deadline and uses nonblocking I/O with incremental UTF-8 decoding; an incomplete character never extends the deadline. Stop closes the adapter transport independently of process-tree EOF, then drains/cancels its reader. Idle or inherited open PTY handles cannot permanently consume executor workers. Coverage: bounded adapter reads, 35 successive closes without tree EOF, and a real PTY/ConPTY output-and-stop test in the backend/manager suites.

- Windows uses `pywinpty`/ConPTY and POSIX uses `ptyprocess`/PTY. On Windows, resolved `.cmd` or `.bat` launchers use the platform command processor as a generic executable-format adapter; no command name receives special handling. Windows terminal descendants inherit the server's kill-on-close Job Object. POSIX PTY children run their exact declared command through the same parent-liveness guardian as Process Manager, inside the PTY process group, so abrupt server death kills the terminal tree even though Runtime shutdown cannot run.
- Terminal launches and both Agent/operator default-shell selection use Bash's shared cached login environment, including Windows registry PATH refresh. A missing executable resets that cache and retries launch once; explicit environment overrides survive the refresh. An omitted manual command selects an interactive host shell without changing the PTY path. Windows prefers PowerShell 7 (`pwsh.exe`), then Windows PowerShell (`powershell.exe`), and falls back to `%COMSPEC%`/`cmd.exe`; POSIX prefers `$SHELL`, then the account login shell, and finally `/bin/sh`.
- `pyte` owns bounded terminal rendering. The renderer preserves a separate primary and alternate screen, resizes both buffers, restores the primary screen on alternate-screen exit, tracks the bracketed-paste mode advertised by the foreground program, serializes the retained primary-screen scrollback followed by the current active screen into one authoritative ANSI snapshot for late WebUI viewers, skips the empty continuation cell of each wide Unicode glyph so snapshots preserve cell positions without inserting spaces or extra wraps, and exposes OSC title/icon metadata as one whitespace-normalized, single-line title capped at 160 characters. Title extraction and terminal-mode tracking are protocol behavior; the manager does not inspect process trees or add program-specific hooks. The authoritative snapshot re-emits the tracked terminal modes before the screen content - alternate screen (`?1049h`), application cursor keys (`?1h`), mouse reporting and other private modes (`?<mode>h`), and bracketed paste (`?2004h`) - so a late viewer lands in the same interactive state as the live terminal instead of rendering a TUI's alternate screen as dead text on the primary screen. Mode tracking lives on the pyte screen subclass (`alternate_active`, `private_modes`, `bracketed_paste_enabled`) and is captured with the screen state, so alternate-screen enter/exit restores the exact prior mode set. pyte ignores the `<`/`>`/`=` CSI prefixes and dispatches the payload as a normal sequence, so xterm keyboard-mode sequences such as `CSI > 4 ; 1 m` (modifyOtherKeys, emitted by opencode2 at startup) are misread as SGR "underscore + bold" - every blank cell written afterwards inherits those attributes and the snapshot paints white underlines under blank rows (the historical white-lines root cause). The renderer therefore strips `CSI <`/`>`/`=` keyboard/DA sequences before feeding pyte, holding back an incomplete tail across feed boundaries, including a lone ESC or CSI introducer; do not remove that stripping without a pyte-side fix, and never rewrite output in the WebUI instead (the server renderer and viewer must consume the same bytes).
- The manager publishes an authoritative ANSI history-and-screen snapshot followed by contiguous sequenced output/state events. Replay retains at most 4,096 events and 4 MiB of conservatively measured Python event payloads; each subscriber queue also has a 4 MiB budget besides its event-count limit. Oversized events are not retained, slow subscribers are evicted, and sequence gaps recover through a fresh authoritative snapshot. The optional byte accounting belongs to `core/event_stream.py`; other consumers retain their existing count-only policy. Coverage: `test_event_stream.py` and `test_terminal_snapshots_obey_byte_budget_and_reconnect`. It additionally publishes a sequenced `terminal_snapshot` after an alternate-screen exit, at the quiet boundary following bracketed-paste disable, and immediately before a final exited/error state; these program-agnostic resynchronization points cover TUIs that clear the primary screen instead of using the alternate buffer. A title change publishes a state event and catalog invalidation even for a non-selected background Terminal Session; finished-session expiry publishes the same invalidation. `server/rpc/terminal_methods.py` maps operator start/list/input/resize/kill/forget, the group CRUD/order surface (`terminal.group.create`/`rename`/`delete`/`order`), and `/ws/terminals/{terminal_id}` carries the selected live stream or one retained finished snapshot. Operator resize is an explicit PTY operation through `terminal.resize`. The WebUI sends it only when its fitted grid differs from the session's authoritative columns/rows: requests repeating the known dimensions are dropped client-side (including any pending burst ending at the current size), and the server additionally treats a same-dimension resize as a no-op, so revisiting or rearranging the tab without a size change produces no PTY operation and no repaint. `terminal.list` returns the operator-visible groups (`groups`), the retained Terminal Session catalog with each summary's effective `group_id` (`terminals`), and the durable manual `launch_history`; `terminal.start` accepts an optional command, exact argument list, working directory, dimensions, and group id, then returns the started Terminal Session plus the updated history. `terminal.group.create`/`rename` take a unique name (<=80 chars, blank rejected); `terminal.group.delete` kills the group's live terminals and returns the count; `terminal.group.order` persists a group's terminal order and appends unknown members. A manual terminal is always the operator's interactive default shell, so it behaves like a normal terminal: an omitted command opens a bare shell, and a provided command plus arguments is entered into that shell like typed input (exact `data`, then Enter) once a stable prompt screen is rendered - never spawned as the bare PTY child and never sent through bracketed paste or the Agent `send_input` contract. The entered command uses the actual host shell's argument grammar: POSIX literal quoting, PowerShell literal strings and the call operator for quoted executable paths, Windows PowerShell native command-line escaping, and cmd metacharacter escaping for native arguments. The pre-command output and typed line remain visible in rendered history. Real-shell regression coverage checks spaced paths, quotes, backslashes, variable-like strings, and metacharacters. The launch command runs in its own `operator_command_task` (bounded shell-readiness wait, written once, then Enter), never in the Agent initial-input slot: operator input that arrives while the shell is still booting waits for that task instead of cancelling it, so the WebUI's immediate focus after start cannot lose or corrupt the command. A started command inside the shell neither ends the Session nor changes the exit semantics: Ctrl+C or program end returns to the shell prompt and the operator keeps typing. Manual summaries expose `launch_command` and `launch_args` (the operator-requested command) beside `command`/`arguments` (the running shell); the list item and tile show the launched command, and the launch history keeps remembering the requested command with its arguments. The Manager never resolves or executes the requested command itself; an empty or blank command rejects, and a command that never sees a stable prompt (silent shell, no prompt marker) is simply not entered.
- `webui/src/lib/terminalsView.js` owns start, group and retained-catalog and launch-history reconciliation, stream reconnect and gap recovery, authoritative `terminal_snapshot` application, exact per-terminal xterm input batching, viewer geometry, and teardown. The operator surface uses a horizontally scrolling group bar above the selected group's terminals, so group selection never reserves terminal width: streams open only for the visible group, switching groups closes the outgoing and opens the incoming streams (the same mechanism as tab remount), the default selection is the first non-empty group, and a group's user-set order is applied optimistically before the server confirms it. A terminal that transitions to `exited`/`error` is marked finished immediately: its stream stops reconnecting, buffered input is discarded, and a terminal-closed RPC error from an in-flight request is never surfaced as `actionError` (the transition itself is the expected outcome, for example after Ctrl+C or a program exit). The viewer clamps every fitted grid into the server's accepted bounds (40-240 columns, 10-80 rows) so a small tile produces a legal minimum grid instead of a rejected request, sends a debounced `terminal.resize` only when the fitted grid differs from the session's known dimensions (maximize sends immediately), keeps only the newest pending dimensions behind an in-flight resize (including a return to the prior grid), and adopts the server-confirmed dimensions from the RPC response's `terminal` summary. A completed request confirming a different grid remains visible as a mismatch instead of causing a reactive retry loop; failed requests remain retryable. The xterm WebGL addon is intentionally not used - the DOM renderer is the only render path, and the historical white-line sources are documented in `webui.md` Constraints (the WebGL fractional-scale trap plus the pyte keyboard-mode misparse, which is fixed server-side). A canvas layout change (tile count or maximize) re-fits every mounted viewer after the DOM update, not only the newly created tile. `TerminalsView.svelte` dynamically mounts xterm.js, offers a compact New terminal dialog whose Recent setup selector defaults to the newest launch and fills an editable command line and working directory, lets the operator pick a target group (or Automatic), offers create/rename/delete dialogs for user and agent groups (deleting warns that running terminals are stopped), reorders the active group's terminals by drag & drop on the tile bar, focuses a newly started terminal for immediate input, makes every running terminal directly writable when clicked regardless of owner, and rebuilds bounded scrollback from every authoritative snapshot after mount, selection, reconnect, navigation, or a TUI mode/exit resynchronization. The browser's FitAddon computes each tile's grid at the current font size, and the controller propagates a changed fitted grid to the PTY. The font increases when the fitted grid exceeds the server maximum; the current component does not reduce it again when the tile shrinks. There is no independent Agent grid or CSS scale/inverse pointer mapping. External dimension changes currently update the catalog metadata without resizing the mounted xterm instance on `terminal_state`; this can leave the mismatch hint visible until a later fit or snapshot. Unequal dimensions alone are not a demonstrated rendering defect; the user requirement is compact Agent observation independent of available operator UI space (product requirement, distinct from the current UI geometry). Evidence: `TerminalsView.svelte` (`fitTerminal`, `writeSnapshot`) and `terminalsView.js` (`handleStreamEvent`); browser reproduction in `.vorch/terminal-integration-audit.md`. Finished Terminal Sessions remain selectable as read-only history until manager expiry. The group bar and compact tile bar prefer the program-announced title; before one exists they humanize known default shell executable names while retaining the exact command in detail metadata. There is no Observe/Take control state, secondary text composer, or program-specific input path. Navigation and socket teardown never own the Terminal Session lifetime. The single close action removes the tile from the canvas immediately (optimistic) and runs the server-side stop and catalog removal in the background; a failed stop restores the session from the server list and surfaces the error. The production Vite build deliberately uses Terser: esbuild minification of xterm 6.0.0's DEC-mode query handler can emit an undeclared enum variable and make nvim output fail at runtime even though the unminified dependency is valid.

Terminal tile microphones use the existing browser recorder and shared server STT endpoint, including configured local engines. `terminalsView.js` owns one terminal-bound recording/transcription at a time; `TerminalsView.svelte` shows recording/processing feedback and a discard action, then inserts the transcript with xterm's native `paste`, preserving the foreground program's bracketed-paste mode. Transcript control characters and line separators become spaces; no Enter is appended. Another tile may be selected while transcription runs without redirecting input or stealing focus. Closing/finishing the target, switching groups, losing the stream/server, hiding it through another tile's maximize, or leaving the view cancels capture/upload and rejects late permission/transcription results. Finished or disconnected tiles cannot start recording. Coverage: `lib/__tests__/terminalsView.test.js` and `components/__tests__/TerminalsView.test.js` under `webui/src/`.

A failed explicit stop retains captured descendant process identities and leaves the Terminal Session unfinished, even if the root process reaches EOF. The caller receives an error and can retry stopping that same tree. Runtime shutdown attempts every terminal before reporting any unconfirmed trees. `core/utils/processes.py` owns OS process-tree termination for both Terminal and Bash/Process.

## Runtime and lifecycle integration

Runtime constructs `TerminalManager` after `TriggerService`, injects the Storage-owned launch-history path, the user-groups path (`<data_dir>/terminals/groups.json`), and atomic-staging root, registers `terminal` before System Prompt assembly, exposes it through `RuntimeServices`, and closes it before temporary-file cleanup. Run cancellation never closes already-started Terminal Sessions; cancellation while process creation is still pending waits for and disposes that launch. Session deletion, Agent removal, and Project removal terminate only matching Agent lifecycle scopes; they detach matching bindings from surviving operator-started or differently scoped terminals. Extension execution-group close (`close_execution_group`) terminates only terminals owned by that exact group epoch without changing attachment authority; it rejects launches for the epoch while pending launches drain and releases that admission marker afterwards, because the group owner closes resources only after every owned Run is terminal (`runs.md` -> Extension execution ownership; `test_terminal_manager.py`). Successful `/agent` moves transfer matching lifecycle and attachment scopes and reroute pending delivery while leaving immutable provenance unchanged. Operator-started Terminal Sessions end only through explicit stop, natural exit, terminal failure, Runtime shutdown, or the server-level crash boundary. No Terminal Session, retained catalog, or agent/automatic group survives a Runtime restart; the independent manual launch history and user groups do survive. Ended sessions remain in the in-memory retained catalog until the 30-minute expiry or explicit operator forget. `terminal` is an ordinary built-in Tool and is part of the default Project Tool allowlist. The bundled `coding-agents` Skill is the program-agnostic operating playbook for Codex, Claude Code, OpenCode, and future interactive coding-agent CLIs: it explains normal interactive launch commands, task supervision across Runs through `terminal_id`, and missing-CLI recovery. Shared input, observation, paging, and launch-recovery guidance lives in the Skill entrypoint; references retain CLI-specific launch settings and saved-conversation syntax. The Skill prescribes no discovery-first, reuse-first, or new-terminal policy. Reference JSON examples are dispatched through the real Tool registry in `test_terminal.py`, checking exact argv and submitted input.

Focused coverage lives in `tests/core/tools/test_terminal_backend.py`, the `test_terminal_manager*.py` behavior suites, and `test_terminal.py` / `test_terminal_observation.py` / `test_terminal_dialects.py`, with Runtime, lifecycle, RPC, WebSocket, controller, rendered-component, and bundled-Skill contract coverage in their owning test trees. `tests/e2e/tests/terminal-lifecycle.spec.js` exercises the platform default shell and multiple simultaneous real PTY/ConPTY processes through browser start, native input, foreground and background title changes, background output, selection changes, stream reconstruction, navigation, and selective stop. Real Windows validation must use actual ConPTY programs and an unmodified installed Codex CLI because fake adapters cannot prove executable launch fidelity, alternate-screen rendering, browser keyboard/paste behavior, resize, or process-tree stop.

The WebUI command-line editor represents the existing executable plus literal-argument RPC contract, not a shell script. `parseTerminalCommandLine` / `formatTerminalCommandLine` in `terminalsView.js` own quote grouping, quoted quote/backslash escapes, exact history reconstruction, and validation before start. Unquoted backslashes remain path separators; shell expansion and pipelines are not evaluated. The RPC and persisted history retain their structured command/args representation. Evidence: `lib/__tests__/terminalsView.test.js` and `components/__tests__/TerminalsView.test.js`.

It uses registered production definitions and dispatch with a disposable terminal adapter, covering actions, omissions, input families and conditional errors. Some cases use natural phrasing and existing observations; the coding-agent continuation case also loads the bundled Skill and CLI reference. However, the catalog contains only `terminal` and acceptance requires one call, so this is guided single-Tool conformance, not evidence of independent Tool choice or complete task success. It never launches Model-selected host executables and cannot establish real PTY or application compatibility.
