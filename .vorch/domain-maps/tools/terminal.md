# Interactive Terminal Sessions (`terminal`)

`terminal_manager.py` owns Session admission, lookup, attachment/lifecycle scope, launch, and shutdown coordination; it hands callers immutable `TerminalInfo` views (`_terminal_state.py`), never live Session objects. `_terminal_session.py` (`TerminalSession`) owns one process: PTY reads and writes, its rendered screen, activity, attention and delivery, retained output, and the event stream. `_terminal_activity.py` (`TerminalActivity`) is the pure activity state machine (phases, work cycles and their idle boundaries, delivered-screen baseline) that the Session drives with explicit times; it owns no tasks and no clock. `terminal_emulator.py` (`TerminalEmulator`) is the VT emulation: screen, history with stable line numbers, query replies, the ANSI snapshot, and the signals a program declares about its work (`SignalScanner`). It imports only the standard library and pyte so `_terminal_render_host.py`, a thin layer over the generic `InterpreterHost` (`_interpreter_host.py`, `tools/shell.md` -> Output host), can run it off the Event Loop. `_terminal_launch.py` builds the start of an interactive shell with shell integration and the shell-native start of a manual launch command. The internal catalog (`_terminal_catalog.py`) owns groups, ordering and operator summaries; `_terminal_input.py` encodes Agent input; `_terminal_state.py` holds Session values, limits, and errors. Components receive explicit services (`TerminalSessionServices`), never the manager.

New Terminal Session ids use `term_` plus 12 lowercase base32 characters, allocated against the retained catalog after async launch and before synchronous publication. Created groups use `grp_` with the same suffix; automatic group identities stay deterministic (`terminal_manager.py`, `test_parallel_terminal_ids_skip_collisions` in `test_terminal_manager_lifecycle.py`).

## Boundary and invariants

> User requirement (stated repeatedly; recorded 2026-10-11): The shell Tool (`powershell` on Windows, `bash` elsewhere) runs one-shot commands, like Claude Code's Bash tool. A command never receives input and runs without a terminal, so a program that asks for input fails at once instead of waiting. A command that runs long, a server included, continues in the background and delivers its result when it ends. The Agent lists, checks and stops its background commands with `background_tasks`, which never waits for output and never gives input. Nothing gives a command input or turns it into a terminal; programs that need input or a terminal run only through the terminal Tool. Changing this boundary needs the user's explicit approval, also in a rebuild.

> User decision 2026-10-13: the terminal Tool passes the Agent's input to the program as a real terminal would, and shows the Agent what a human sees, without losing or silently cutting anything. `start` types nothing: the Agent sends its first input with `input` once the program's screen shows that it is ready for it.

> User decisions D1-D6 of 2026-10-13 (the Tool's texts): D1 `start`, `input` and `wait` show `history` only for lines this Session has not seen yet (the newest 30 at most) and no `scrollback`; `status` keeps its pages. The unseen-lines note offers the `status` page of the newest 100 unseen lines it leaves out, plus the log for all of them. D2 The description says that ⟦ and ⟧ mark reverse-video text, such as a selection or a drawn cursor; background colours are not marked for now. D3 `cancel`, `abort` and `interrupt` are refused with both calls they can mean: Ctrl+C as input, and kill. D4 A running program whose start screen is empty gets a `next` saying that its first screen arrives as a new message, with the wait call, and no `cursor`; input given to `start` is not sent, and the note says to answer what the screen asks first and then send it with `input`. D5 After input, an idle program that did not declare its end gets a `next` saying it can still be working unless its screen shows it waiting for input. D6 Faint suggestion text after the cursor is marked ⟪ ⟫, which the description explains within its 760-token budget.

`terminal` gives an Agent a real interactive terminal for programs it drives by typing. No shell command runs in a Terminal Session: the shell Tool runs commands without a terminal, and `background_tasks` serves the ones that outlive their call (`tools/shell.md`); the terminal subsystem holds no command code, and the `terminal` Tool refuses the ids of background commands and Sub-Agents (Agent Tool contract). History: the 2026-10-04 rebuild ran shell commands in hidden Terminal Sessions and later let Agents type into them, which the user had not approved; the one-shot shell rebuild of 2026-10-11 removed that. Every requested executable uses the same PTY/ConPTY transport and receives the exact declared argument vector, except that a plain interactive shell starts with shell integration through its own start options (Transport section). The terminal capability contains no detection of other programs, no program-specific flags, hooks or configuration, no lifecycle protocol, and no screen-text heuristics: what a program does is read only from standard terminal sequences it emits on its own and from its process tree (Generic activity delivery; user requirement 2026-10-11: the terminal Tool must not be built around coding agents). Codex, Claude Code, other coding CLIs, shells, editors, games, and arbitrary interactive programs therefore share one contract.

- Every Terminal Session records immutable process provenance (`owner`: the starting Agent Session, or `None` for a local-operator start), an independent lifecycle scope (`lifecycle_owner`: the transferable Agent Session scope that owns cleanup, or `None` for an operator-started process), and at most one mutable Agent Tool/event binding (`attachment`). Agent `start` initializes all three Agent scopes to the current Session; an operator start initializes all three as local/unbound. The local operator can observe and control every active Terminal Session without changing any of them.
- The Agent Tool, WebUI, and child process use the same live PTY/ConPTY. Agent and WebUI input are written to that process, WebUI output is the sequenced raw VT stream, and Agent status is rendered from the same stream.
- A Terminal Session ends only on explicit `kill`, natural child exit, applicable lifecycle-owner Session/Agent/Project removal, or Runtime shutdown, and it finishes only once its program has ended. The end of its output - EOF, a closed PTY, a failure to read, render or log it - is no end of the program: a program that still runs keeps its capacity slot, its lifecycle owner and its kill path, and `terminal.forget` keeps refusing it (failure handling under Generic activity delivery). Operator-started sessions have no Agent lifecycle scope and are therefore unaffected by Agent, Session, and Project cleanup even while attached. `detach`, leaving a Run, or navigating away from the WebUI never ends a Terminal Session.
- Handler argument refusals raise `ToolContractError` and return `invalid_arguments`; an `OSError` or other exception escaping an action (for example a failed input write) is `tool_execution_error` with unknown effects (`tools.md` -> Failure codes follow the phase; `test_a_failure_while_acting_reports_unknown_effects`).
- Launch failures wrapped by `TerminalManager` reach the Agent as `terminal_launch_failed` naming the original cause (a missing program, `FileNotFoundError`, as `terminal_command_not_found`); the Tool does not guess the cause from a generic filesystem exception. Failed launches release their capacity and retain no Terminal Session. Evidence: `test_launch_failure_is_reported_and_releases_capacity` in `test_terminal.py`.
- Starting processes reserve the same per-Session and global capacity as live processes before any worker is launched. Raw-log lease creation runs off the Event Loop inside that admitted launch. Cancellation during creation waits for the launch outcome and stops the resulting child before releasing the reservation and temporary-file leases; shutdown also waits for pending launches. Session, Agent and Project scope cleanup also fences new matching launches while draining those already admitted, even if the cleanup caller is cancelled. A launch still in preparation is refused before process creation; a process already being created is stopped before normal publication. If that stop fails, its Terminal Session stays listed with its lifecycle owner and captured process identities for a retry, and cleanup reports the failure. The fence is released after cleanup so a later Run can start again. `close_scopes` applies one fence and one unique count to a captured Session tree, including terminals whose attachment and lifecycle owner name different Sessions in it. Scope cleanup reports live terminals stopped or detached plus pending launches; unrelated scopes and operator-owned processes survive. A raw log that fails to open releases its already-created lease for normal retention cleanup. Already-started Terminal Sessions retain their independent Run lifetime.
- Internal live states are `ready` and `working`; terminal states are `exited` and `error`. These states describe terminal activity and process lifetime, not application-specific turns or prompts. The Agent sees only `running`, `exited`, `stopped` (vBot, the user or an Agent stopped the program: `TerminalInfo.stopped`) and `failed` (`error`); whether an interactive program went idle is the `wait_ended` of a wait.
- Raw output and rendered history are bounded. The manager retains a finished Terminal Session's metadata and rendered history for 30 minutes so the operator can inspect it as a read-only snapshot; `terminal.forget` may remove that in-memory record sooner. When Storage is available, the manager additionally retains the raw output in a leased `<data_dir>/artifacts/temp/terminals/*.log` and starts the normal temporary-file retention clock after the Terminal Session ends.
- Successful manual launches additionally update a durable, newest-first launch history under `<data_dir>/terminals/launch-history.json`. Each entry preserves the requested command (including the default-shell choice), exact argument vector, and operator-entered working-directory text; identical configurations move to the front instead of duplicating, the list is capped at 50 entries, and failed launches never enter it. Both durable Terminal files (`launch-history.json`, `groups.json`) are Generation 1 JSON documents (`format_version` 1; contract in `settings.md`): unknown fields survive writes; an invalid or duplicated entry is skipped with a logged warning, written back verbatim and reported by `doctor config`; a file whose document root fails to load reads as empty and is never overwritten - changes then stay in memory with a logged warning until the file is repaired or removed. The 50-entry cap applies to the valid launch entries.
- Terminal Sessions are grouped for operator display. A Session's **effective group** is: the `finished` retention group once it is `exited`/`error`; otherwise its explicit `group_id` when it names an existing user/agent group; otherwise the automatic group `auto:manual` for operator-started terminals or `auto:agent:<agent_id>` per Agent owner. Groups exist in four kinds: **user** groups (durable, created/renamed/deleted by the operator, survive restarts, persist while empty), **agent** groups (created by the terminal Tool via its `group` name parameter, in-memory only, deleted by the operator or disappear on restart), **automatic** groups (synthesized per Agent and for manual terminals, never durable, hidden when empty), and the single **finished** retention group (present only while it holds retained finished sessions). User groups persist under `<data_dir>/terminals/groups.json`; agent/automatic/finished groups are never persisted. Deleting a user or agent group kills every live terminal in it (they land in the finished group like an explicit kill) and removes the group; automatic and finished groups cannot be deleted. Group names are unique case-insensitively across user and agent groups; the Agent Tool reuses any matching existing group instead of creating a duplicate. Group create/rename/delete log INFO with the `grp_` id (and kind), never the name, which is operator or Agent text (`test_user_groups_are_unique_persistent_and_renamable`).
- Within a user or agent group, a user-set terminal order can be stored (`group.order`); the default order is newest-first for live and finished terminals, a user-set order is authoritative, and newly spawned terminals append at the end. The order persists only for user groups.

## Agent Tool contract

Agent `start` calls resolve `ScratchAreas.folder_for` immediately before spawn
and pass `TEMP`, `TMP`, `TMPDIR` (the own folder's `tmp/`) plus `VBOT_SCRATCH_DIR`
(the own folder) through the terminal environment overlay. Each launch repairs
missing folders. `spawn_for_operator` and internal shell integration files keep
their existing temporary-file handling. `TerminalManager.busy_addresses()`
reports pending Agent launches and live Agent lifecycle owners for Scratch
retention; operator terminals, including attached ones, have no Agent lifecycle
owner and do not keep an area alive. See `tools/scratch.md`.

If Scratch setup remains unavailable, its owner logs the condition and raises
`ScratchUnavailableError`. Agent `start` then omits the Scratch overlay and
launches the requested program with its normal environment; no failure result
or extra reminder is added for this optional feature. Cancellation and
interruption still propagate.

The voice companion uses operator APIs, preserving Agent bindings: `terminal.read` projects rendered output without updating Agent observation state; optional `expected_screen_revision` on `terminal.input` rejects stale input under the existing session lock. Optional `expected_program` (a command name such as `codex`) writes only while that program runs in the Terminal's process tree - the Terminal's own process or a descendant that is not stopped, identified by its name, executable, first argument, or, for `node`/`bun`, its script or npm package (`process_tree_runs` in `core/utils/processes.py`, injectable as `TerminalManager(program_probe=...)`); the check runs under the same lock right before the write, fails closed when the tree cannot be inspected, and rejects with `TerminalProgramNotRunningError` (RPC code `terminal_program_not_running`). Coverage: `test_operator_input_expecting_a_program_writes_only_while_it_runs` in `test_terminal_manager_operator.py`, `tests/core/utils/test_processes.py`, `tests/server/rpc/test_terminal_methods.py`. `terminal.programs` (`running_programs_for_operator`) answers, with the same probe off the Event Loop, whether each unfinished manual Terminal still runs the program of its launch command (file name without extension), keyed by terminal id; plain shells are left out. A manual Terminal's shell outlives its program, so its state alone cannot tell (`test_operator_reads_whether_each_terminal_still_runs_its_launch_program`). It is a separate method so `terminal.list`, which the UI calls often, never scans process trees. The underlying Terminal capability remains program-agnostic. Voice-specific launch constraints and UI operations live in `model_tasks/live-operator.md`.

`core/tools/terminal.py` exposes one open flat action schema and performs semantic validation; `core/tools/_terminal_arguments.py` normalizes each call before central validation (see the argument-dialects bullet below). Actions (`TERMINAL_ACTIONS`): `start`, `list`, `status`, `wait`, `input`, `kill`, `attach`, `detach`. Advertised parameters: `action`, `terminal_id`, `command`, `args`, `workdir`, `name`, `group`, `text`, `key`, `data`, `lines` (schema default 30), `pattern`, `timeout` (seconds, schema default 60). Accepted but unadvertised (`TERMINAL_UNADVERTISED_PARAMETERS`): `timeout_ms`; `start_line` (results carry ready paging calls); `expected_screen_revision` and `after_revision` (the terminal tracks both itself, and no result shows a revision); `columns`/`rows` (on `start` only). The description draws the boundary - interactive programs driven by typing (REPLs, TUIs, coding-agent CLIs) here, all other commands, servers included, with the shell Tool - and says that a program outlives the turn; which messages arrive on their own is said by the `start` and `attach` results (`next`). `project_terminal_tool_definitions(definitions)`, called by Chat's request builder, fits the description to the Tools offered: the shell Tool's Model name appears only when it is offered. Sub-Agents (Session depth >= 1) get the same definition and behavior as top-level Agents (user decision 2026-10-05). Coverage: `test_definition_follows_flat_action_conventions_within_its_budget` (exact properties, budget <= 760 tokens) and `test_definition_fits_the_offered_tools` in `test_terminal.py`.

An omitted `command` opens the host user's default interactive shell - the same selection the manual operator path uses: on Windows `pwsh.exe`, then `powershell.exe`, then `%COMSPEC%`/`cmd.exe`; on POSIX `$SHELL`, then the account login shell, then `/bin/sh`. A provided `command` launches that exact executable with the given `args`. Either way the default working directory is the current one with 80 columns and 24 rows; there is no program-specific default executable. `workdir` accepts absolute and relative filesystem paths plus the unadvertised exact prefix `project:<project-id>`, which the resolver shared with the shell Tool (`core/tools/_workdir.py`) resolves to the registered Project's live `cwd` by stable id before spawn. The Project reference changes only the child start directory: it does not load Project Context, change Rooting, or reassign Terminal ownership, and a spawned process does not move if the Project is later re-pointed. A missing Project returns `project_not_found`; an invalid/unreadable Project record or unreachable Project `cwd` returns `project_unavailable`; an empty id or a path that is not a directory returns `invalid_arguments`; all fail before process creation and before a named `group` is created (`test_start_rejects_unresolvable_workdirs_before_spawn`).

- Background task ids: a `terminal_id` starting with `cmd_` (a background command) or `sub_` (a Sub-Agent) is refused on every action, `start` included, with `not_a_terminal` before anything runs or changes; the refusal names the `background_tasks` call for that id when the Agent can call that Tool (`context.can_call`), as the shell results name it (`_background_task_refusal`): `stop` for `kill`, `status` for every other action. Coverage: `test_ids_of_background_tasks_are_refused_before_anything_runs` in `test_terminal.py`, and `test_background_commands_are_never_terminals` in `test_background_tasks.py`, which guards the user requirement above on the Runtime's own wiring (a background command is never listed, and `status` and `kill` refuse its id).
- `start`: launches exact `[command, *args]` (`args: [""]` is one empty argument; review T2), records immutable Agent provenance and lifecycle scope, and attaches the new Terminal Session to the current Session. It types nothing (user decision above). It then waits (`TerminalManager.wait_for_startup`, at most the manager's `start_wait_seconds`, default `TERMINAL_START_WAIT_SECONDS` = 10 s) until the program printed something visible and its output then paused for the 2-second activity quiet period, or the program ended, and returns that screen: `terminal_id`, `state`, `exit_code` once ended, `log` (left out when the unseen-lines note names the log), `history`/`screen`/`cursor` when present (screen results below), so a program that exits at once shows its end and last screen. A first output that comes right after a resize counts as a redraw (repaint window below), and its non-blank screen still ends the wait (code review R6: the WebUI's first resize made start wait its whole wait). A terminal's own set-up sequences (ConPTY's reset and cursor queries) draw nothing and do not end the wait: a start-up cycle that ends on a blank screen opens again with the program's next output (`TerminalActivity.idle` with `blank`; review finding 4: start returned an empty screen once ConPTY's sequences paused). A program that shows nothing within the start wait returns an empty screen without `cursor` and a `next` saying that its first screen arrives as a delivery, with the wait call; an empty screen that is out of date (below) gets the usual `next` (`_first_screen_pending_text`; user decision D4; probe 2026-10-13: a program silent for 13 s returned after 10.0 s, and its screen was delivered 5 s later). `start` sends no input: `text` (also one of only blanks or line breaks), `data` and a named `key` all launch the program, and a `note` says what was not sent and how to send it with `input` once the program is ready (`_UnsentStartInput`; code review R11: `data` and keys were refused before launch, and blank text got no note). `key: "enter"` without text is dropped; an unknown key name is refused before launch with the named keys, as on `input`. When the screen cannot be read after the launch, the result still reports the started terminal, with a `note` naming the status call (`_unread_screen_result`). Optional `name` (trimmed, max 80 chars) is a conversation label between Agent and operator; optional `group` (max 80 chars) names a group the Terminal joins - an existing user/agent group with that name is reused, otherwise a non-durable agent group is created. Unadvertised `columns`/`rows` set a start size within the operator bounds (40-240 x 10-80). A `command` containing whitespace that names no program but whose first word (split with the host's quoting; backslashes stay literal on Windows) is a program on the login-environment PATH starts as those words plus any `args`, with a `note`; a path with spaces that exists stays one program. A non-empty `terminal_id` naming a live (not exited or errored) terminal fails before launch with the input call that types into it; any other `terminal_id`, including a finished terminal's, is ignored with a note naming the assigned id (a background task's id is refused, above). Coverage: the start tests in `test_terminal.py` and `test_terminal_dialects.py`.
- `list`: one row per retained terminal, of every Session. A row holds `terminal_id`, `program` (`TerminalInfo.program`: the requested program of a manual terminal, otherwise the started command line; its first line, at most 80 chars), `name`, `state`, `exit_code` once ended, and `attached`: `here`, `other`, `no`, or `subagent` for a terminal attached to the Session of one of the caller's Sub-Agents at any depth, whose id the row adds as `subagent` (user decision 2026-10-11: a Parent Agent sees its Sub-Agents' terminals marked with the Sub-Agent; plan D10). The Tool learns those Sessions from `subagents()` of the `SubAgentTree` Runtime passes (`core.subagents`, implemented by `SubAgentCoordinator`), asked only when some terminal is attached to another Session; without it such a terminal stays `other`. Reply routing does not change this membership or discovery. Empty values are omitted. Discovery grants no control, a Sub-Agent's terminal included: `wait`, `input` and `kill` on a terminal not attached to the calling Session return `terminal_not_owned` naming the attach call, or the `status` call when another Session holds it; `terminal_not_found` is reserved for an id no retained terminal has. Coverage: `test_list_and_status_name_the_sub_agent_whose_session_holds_a_terminal` in `test_terminal.py`. Its Tool row derives an exact presentation-only `results` count from `terminals`; other actions and failures publish no count.
- `attach`: binds one running interactive Terminal Session with no attachment to the current Session without changing its process, rendered content, PTY dimensions, provenance, lifecycle scope, or WebUI behavior, and returns its `list` row. Repeating it from the same Session succeeds with a note that nothing changed; another Session's attachment returns `terminal_already_attached` naming the `status` call that reads it without attaching. A successful attachment authorizes `wait`, `input`, and `kill`, records the current Run as the automatic-delivery origin, ignores pre-attachment attention, and arms the current work cycle for its idle boundary.
- `detach`: requires the current Session's exact attachment and removes only that binding plus its pending delivery state; the process, provenance, lifecycle scope, rendered content, dimensions, and WebUI behavior remain unchanged. A mismatched caller receives `terminal_not_attached`. A deliberate attachment transfer is two explicit operations, `detach` followed by `attach`; there is no implicit `reattach` action.
- `status` reads any terminal, attached or not, without attaching it or acknowledging anything (`TerminalManager.read`), except that a default read by the attached Session acknowledges (screen-bearing results below). It returns `terminal_id`, `state`, `exit_code` once ended, the launch facts (`program`, `title`, `workdir`, `log`, `name`; `log` is a sentence naming the raw log, Agent-facing text below), up to `lines` history lines right above the screen (default 30, at most 100) and the `screen`; a terminal not attached here adds `attached` (with `subagent` as in `list` for a terminal one of the caller's Sub-Agents holds: one layout for both actions) and a `next` naming the attach call, or saying that another Session holds it. Model-facing `workdir` and raw-log paths use the shared forward-slash presentation while spawn and manager state retain native paths. History and screen lines carry stable line numbers that never shift as output arrives or old lines are evicted: `scrollback.first_line` is the oldest retained line, `screen_start_line` the first screen line, and `total_lines` the end. An unadvertised `start_line` returns only the page starting there (clamped to the retained range, which a `note` then says, naming the log; a page may reach into the screen) without a separate `screen`; `lines` sets the page size. `history` holds the page text; `scrollback` reports `first_line`, `start_line`, `end_line`, `total_lines`, `screen_start_line`, and ready-made `status` requests `older_request`/`newer_request` for the adjacent pages (`newer_request` only on an explicit `start_line` page, because the default page ends at the screen). Default reads include `scrollback` only when there is history or an older page. A program on the alternate screen keeps no terminal history: `status` then adds a `note` to use the program's own scrolling or paging. History pages never acknowledge attention or screen/resize observations. A `cursor` argument has no effect: the call runs with the note `"cursor" had no effect: terminal has no such parameter.` (`ignored_fields_note`). Evidence: `TerminalEmulator.page` and `_screen_result` in `terminal.py`; coverage: `test_status_pages_the_whole_buffer_by_absolute_start_line` and `test_only_a_persisted_current_screen_acknowledges_resize_and_attention` in `test_terminal_observation.py`, and the attach test in `test_terminal.py` (status of an unattached terminal).
- Screen-bearing Tool results (`start`, a default `status` by the attached Session, `wait`, `input`) remember the delivered screen revision and dimensions only after result persistence. After any later real resize, the next screen result includes `size_change` with the previously observed dimensions and a notice to use the current screen positions; repeated resizes collapse into one notice, including a return to the former size. Reads without persistence and operator views never consume it, older callbacks cannot roll back the baseline or consume a newer resize, and a new attachment starts without another Session's observation. Resize alone schedules no Agent delivery; output after resizing follows the repaint rule under Generic activity delivery. The snapshot carries the shown screen as a hidden `observation` (`TerminalObservation`: screen revision, resize count, dimensions) that the Tool passes back. Evidence: `TerminalManager.acknowledge_screen`, `_acknowledge_after_persistence` in `terminal.py`, and the resize-observation tests in `test_terminal_observation.py`.
- What screen results and deliveries show (user decision above): `screen` marks reverse-video runs with ⟦ and ⟧ (`HIGHLIGHT_START`/`HIGHLIGHT_END`): a cell's own SGR 7, which the screen-wide reverse mode (DECSCNM) leaves alone (fidelity review E6: pyte flipped every cell, so the mode erased every highlight). Faint text (SGR 2) right of the visible cursor, including subsequent rows of the same soft-wrapped logical line, stands between ⟪ and ⟫ (`SUGGESTION_START`/`SUGGESTION_END`): a PSReadLine prediction or a CLI placeholder, which Enter does not submit (user decision D6 above); a hard newline ends that logical line, and faint text elsewhere, or while the cursor is hidden, is ordinary text. The wrapped prediction and unrelated dim text after a hard newline are covered by `test_observation_marks_faint_text_after_the_visible_cursor_as_a_suggestion`. Concealed text (SGR 8) is blank (fidelity review E7: a concealed password reached the Agent). Trailing blanks of a row are stripped, blanks inside a run kept. `cursor` (`row R, column C`, 1-based) is the visible cursor of a running program (`ScreenObservation.cursor`; none while the program hides it). Literal ⟦ or ⟧ in program output look the same. The Session tracks the history line above which the attached Agent has seen every line (`seen_line`): a persisted result or a delivered message advances it to the end of the screen it showed, and a cleared screen (ED 2, RIS) moves it back to the cleared screen's first line (`EmulatorUpdate.cleared_line`, the first clear of a chunk). A result or delivery that becomes durable after a clear acknowledges only the lines above that clear's first line: each observation carries the clear count it was taken at, and the Session keeps the first line of its latest 64 clears; an older one advances nothing (`TerminalObservation.clears`, `_saw_lines`; code review R8: a late acknowledgement undid the clear). A result or delivery that leaves unseen lines out above what it shows says how many and where to read them: with a complete log, the log and the `status` page of the newest 100 of them, right above what it shows (user decision D1); otherwise the page of the oldest kept ones, the part of the log that has them, or that they are no longer kept (`unseen_lines_note`; review finding 8); a `status` of a terminal not attached here counts every line. While the screen misses output, results and the `exited`/`error` delivery say it is out of date and name the log (review T4: a stale screen was shown as current), until a screen drawn anew from the log replaces it (Generic activity delivery, failures). Once writing the log failed, every result that names it says from which line it lacks output (`log_end_line`: the line output went to at the failure, the cursor's line also while the program hides the cursor, unknown while the screen misses output; code review R5: a hidden cursor named the last drawn row), and unseen-line and page notes send the Agent to the log only for lines it has (review T3: an incomplete log was offered as complete). Coverage: `test_results_say_what_they_leave_out_and_where_to_read_it`, `test_input_and_wait_show_only_the_history_no_result_showed`, `test_a_screen_persisted_after_a_clear_leaves_the_lines_drawn_since_unseen` and `test_a_screen_that_cannot_be_drawn_says_so_and_catches_up_later` in `test_terminal_observation.py`, `test_observation_marks_highlighted_text_and_the_visible_cursor` and `test_observation_marks_faint_text_after_the_visible_cursor_as_a_suggestion` in `test_terminal_emulator.py`.
- `wait` waits up to `timeout` seconds (default 60, at most `TERMINAL_WAIT_MAX_SECONDS` = 600; `0` means 600; a longer one is capped, and a capped wait that timed out says so in a `note`) until the program exits, its output matches `pattern`, or - without `pattern` - it goes idle showing a screen this Session has not seen, and returns `wait_ended`: `exited` | `matched` | `idle` | `timeout` (`TerminalManager.wait`), or `stopped` where the result's state or status is `stopped`, since such a program did not exit on its own (`_wait_end`; Swarm review 2026-10-11 found a stopped program reported with `wait_ended: "exited"`). `timeout_ms` is accepted and reconciled with `timeout` by the shell Tool's `resolve_timeout`, which notes a millisecond-sized `timeout` and refuses disagreeing values. `pattern` is a Python regular expression compiled with `IGNORECASE | MULTILINE` (`^`/`$` at every line) and searched in the rendered output as logical lines (`TerminalEmulator.pattern_text`: rows an auto-wrapped line fills are joined), including output printed before the call - except, once the Agent typed (`send_input` -> `mark_input`), the lines up to and including the cursor's line at that input, which hold earlier output and the input's echo, wrapped continuation rows included; after a screen clear (ED 2/3, RIS on the primary screen) the cleared screen's lines count again; on the alternate screen only the screen counts. Without input every retained line counts, from the oldest. Later checks of one wait resume at the logical line above the screen. ED 0 from the home position is deliberately no clear: ConPTY repaints with it. Invalid syntax is matched as literal text with a note (terminal review R1, R2). The program went idle when an `idle` attention above the last acknowledged one (or the unadvertised `after_revision`) exists; with `pattern` that does not end the wait. The user can end a wait from the chat, as they move a call to the background (`background_registration_hook`, `_wait_unless_released`): the result then has `wait_ended: "user"` and a note that the program keeps running (the `user` case of `test_wait_ends_at_the_exit_a_matching_line_or_an_idle_program` in `test_terminal_dialects.py`). A wait or `input` that matched adds `matched`, the line where the match starts (at most 500 characters). A wait with a pattern that timed out says so in a note: no output matched it within the seconds. The result is the screen result plus `wait_ended`. A timeout never owns or pauses the child. When the reply ends on an idle program that did not declare the end of its work (idle reason `quiet` or `fallback`), `next` says that it can still be working unless its screen shows it waiting for input (`_PAUSED_TEXT`; review finding 11: a coding agent waiting for its model shows neither output nor CPU time; user decision D5). When the screen cannot be read after the input was written, the result still succeeds, with a `note` that the input was sent and the status call (`_unread_screen_result`; review finding 3: a render error turned delivered input into an error). While rendering fails, no quiet boundary comes, so the reply waits its whole timeout. If no input remains, the call succeeds as a validated no-op that waits for nothing and returns `terminal_id` with a `note` naming the `status` call; it does not start activity delivery. Real Agent or operator input advances the observation revision before writing, including input with no echo, so the same guarded observation cannot be reused. - `kill`: requests termination of the Windows child tree, Linux guardian tree, or other POSIX process group, suppresses an automatic exit delivery caused by that explicit action, and leaves a bounded exited snapshot until finished-session expiry. ## Generic activity delivery

Generic terminal bytes cannot reliably distinguish a question, approval request, completed application-level task, idle animation, or prompt. `TerminalManager` therefore emits only `idle`, `exited`, and `error` attention kinds and never claims application semantics: `idle` says that a cycle of work ended by the evidence below, not that a task succeeded. The goal is one wake-up per finished piece of work, at its end, for any program (user requirement 2026-10-11: the Agent was woken at every 2-second output pause while a coding agent in its terminal still worked; a fixed 15-second idle threshold alone was rejected as too slow after short work such as an install).

- Work comes in cycles (`TerminalActivity`). Agent or operator input starts one (state `working`; Agent input records the current Run as delivery origin), the program's start-up starts the first, and output after the program went idle starts a spontaneous one. Every output or input restarts the 2-second quiet timer (`TERMINAL_ACTIVITY_QUIET_SECONDS`), whose boundary ends the reply of `input` and `start` (`quiet_boundaries`). A cycle ends at its idle boundary - state `ready` - by the first reason that holds (`IdleReason`, kept as the attention's `details.reason`): `declared` - the program declared the end of its work (signal `attention`: a BEL outside control strings, OSC 9 text, OSC 777;notify, OSC 99; `progress_end`: OSC 9;4 state 0, 2 or 4 after state 1 or 3; `prompt`: OSC 133/633 A or D, OSC 9;12, or a line editor turning bracketed paste on, CSI ?2004h, counted only as a change of the mode) and printed nothing for the quiet period; a later `command` signal (OSC 133/633 C, bracketed paste turned off) withdraws an earlier prompt. `quiet` - in a cycle that input or start-up began, the program showed work without a pause longer than 3/4 of the quiet period (output, CPU time, a process the cycle started), printed nothing for the quiet period, and now runs no process the cycle started, no shell command line (`command` without a later `prompt`) and no progress indicator, and used under 0.2 of a core over the last second. `fallback` - no output for `TERMINAL_IDLE_SECONDS` (15 s), with neither CPU time over 0.15 s nor a new process in the tree since the output paused. A spontaneous cycle ends only as `declared` or by the fallback: a program that resumed work on its own (a coding agent between its tool calls) can pause without being done. Output after a `quiet` end can resume the input/start-up cycle before its fallback was due (15 s after its last output), retaining that cycle's process baseline. Every resumption needs fresh work before another quick idle: continuous output spanning at least half the quiet period (1 s at the default), busy CPU, a new child process, or progress. This has no fixed resumption count, so repeated work bursts and process work settle promptly at each pause. One isolated redraw, including a frame split into several short PTY reads, does not qualify; periodic clock or `top` frames therefore create no extra quick-idle delivery after start-up. A lone changed frame with no other evidence still waits for a declared end or fallback: generic output cannot prove that it is a completed task. Coverage also includes `test_periodic_changed_redraws_do_not_wake_the_agent`. `SignalScanner` (`terminal_emulator.py`) finds the signals across chunk boundaries. Coverage: `test_attention_auto_delivers_and_manual_ack_cancels_exactly_once` (`quiet`), `test_work_the_program_resumed_on_its_own_wakes_at_a_declared_end_or_the_fallback` and `test_work_the_processes_show_keeps_a_quiet_program_working` in `test_terminal_manager_attention.py`; `test_update_reports_what_the_program_declares_about_its_work` in `test_terminal_emulator.py`.
- Process evidence: `TerminalManager(process_observer=...)` - Runtime passes `observe_process_tree` (`process_tree.py`: a Windows Job Object without kill-on-close, a Linux guardian tree, or another POSIX session) - observes an interactive program's process tree without owning its lifetime; without an observer, or while sampling fails (WARNING when it starts, INFO when it recovers), only output and declared signals show work. While a cycle runs the Session samples the tree every 0.5 s (`PROCESS_SAMPLE_SECONDS`, `_sample_cycle`); the sample taken right before input gives the cycle's baseline of running processes and the first CPU reading, and once the output was quiet for the quiet period each sample can end the cycle.

- A same-dimension resize is a no-op. A real resize of a `ready` terminal opens a 1-second repaint window (`TERMINAL_REPAINT_WINDOW_SECONDS`, the `repainting` phase of `TerminalActivity`, shown as `ready`): output inside it is the program redrawing its screen for the new size. It keeps the state `ready`, wakes nobody, records no attention, and its settled screen becomes the delivery baseline, so a later identical screen stays silent too; a pending Agent delivery stays pending. Agent/operator input closes the window, output after it is ordinary activity, and resizing a `working` terminal opens none. The rule is timing-only: it does not compare repaint content, so real output arriving inside the window after resizing a quiet terminal counts as repaint. - While attached, Agent input, operator input, and spontaneous output use the same cycles and request automatic delivery at the cycle's idle boundary; attach also arms a cycle already in progress. The start-up output of a newly Agent-started terminal goes idle once; its screen is delivered only when the persisted `start` result did not show it, and later attached activity is deliverable. An unattached Terminal Session has no Agent delivery target. Idle revisions remain observable through `wait` only for the attached Session.
- Natural exit and terminal failure create `exited` or `error` attention and request delivery; both bodies carry the last screen. Both are set only once the program has ended. An unexpected failure to read its output (ERROR log) stops the reading, and the reader polls the program every second (`TREE_POLL_SECONDS`) until it exits or is killed. A failure to render (WARNING when it starts, INFO once a screen is drawn anew) keeps the output read, logged and streamed while the screen misses it, and records no `idle` attention meanwhile; a chunk that failed is never fed again (code review R1: a malformed sequence was fed again before every chunk and froze the screen). While the raw log is complete, the Session stops feeding the broken screen and draws a new one from the log in the background (`_LogReplay`, through the `open_screen` service): it opens a screen at the launch size, replays the log in 1 MiB pieces outside the Session lock with each resize and the input mark at the log offset where they happened, replays the last 64 KiB under the lock, finalizes its UTF-8 decoder, and swaps the screens. Piece boundaries retain decoder state; incomplete final bytes appear as replacement characters on the screen and remain unchanged in the raw log. The new screen brings the modes the replayed output set (bracketed paste, cursor keys, alternate screen), `seen_line` moves back to the first line a clear erased in the missed output, and query replies are not sent again. A redraw that fails is retried after twice the quiet period, doubling up to 5 seconds (code review R2: the catch-up kept only the newest 256 KiB of missed output, dropped the rest and the warning, and fed modes from a partial stream). Without a complete log the old screen keeps being fed and the out-of-date note stays. When the program ends, a pending redraw runs once more, for at most 1 second, before the end is delivered; results and the `exited`/`error` body of a screen that still misses output carry the out-of-date note (`screen_behind_note`). A pyte operation that fails on a sequence (pyte raises on ED 5, `ESC [ 5 J`) is skipped and the rest of the chunk drawn (`_GuardedScreen` in `terminal_emulator.py`, `EmulatorUpdate.skipped`, one WARNING per terminal), so it is no render failure; such a failure before killed the rest of its chunk. The parser never raises on output either (Transport section; code review R1: pyte's parser raised on `CSI ² m`). A read failure becomes the `error` outcome when the program ends; a render failure never does (code review R1: a clean exit was reported as an error). A failing raw-log write closes the log with one WARNING, and results that name the log say from which line it lacks output (review T3), and a refused query reply is ignored; the liveness checks decide. A PTY write that fails (EOF/closed or `OSError`) reports `terminal_closed` only when its program no longer runs, after waiting for the reader to drain pending output and record the natural exit. Only the reader finishes that natural exit and closes its log, so the final screen and delivery include the last received output. Cancelling the input leaves the reader running; stopping the reader does not cancel the waiting input or its Run. While the program still runs, the input fails with `terminal_failed` (`The input could not be written to terminal <id>`) and nothing ends. Explicit kill and scope shutdown suppress that delivery. A durable result that showed the end - a `stopped`, `exited` or `failed` state in a default `status` by the attached Session, `wait`, `input` or `kill` - acknowledges it after persistence (`TerminalManager.acknowledge_exit`): a pending delivery is cancelled and a later one is never scheduled. ## Transport, rendering, and local operator surface

Physical Agent, operator and terminal-protocol writes are serialized by the Terminal Session. A blocked write never holds the screen/state lock, and the output reader only queues protocol replies, so a program can print while consuming a large input without filling both PTY buffers into a deadlock. Cancelling an input caller leaves its already-started write ordered before subsequent input; the rest of that cancelled call, such as a following Enter, is not sent. Input revision/program guards are checked after earlier writes finish, named keys use the mode at their physical write, and the text-to-key pause starts after the text finishes writing. Quiet/idle observation waits for pending input writes, then settles the current output generation. Shutdown closes the adapter and awaits the Session-owned writer. Coverage: the concurrent-input, cancellation and shutdown contracts in `test_terminal_manager.py`. Real Linux probes (Ubuntu 24.04 under WSL2, Python 3.14, 2026-10-13) reproduced the old lock deadlock and verified the correction with 60,000 input bytes, 240,029 output bytes and a query during the exchange, with and without process containment. Independent input captures and byte comparisons also covered Unicode/control input, a 1,512,022-byte stdout/stderr log, EOF/EIO with incomplete UTF-8 tails, delayed final reads and renderer recovery.

The renderer answers cursor/status, primary/secondary device-attribute, character-size, and supported mode queries from the canonical terminal state, and answers a program that enables focus reporting that the terminal has no focus (Generic activity delivery). The Session writes these replies to the PTY under its lock; they are not operator input and never cancel queued Agent input. Queries split across read chunks retain their order. The WebUI suppresses its own query replies (including color/window/status-string reports) and drops viewer focus reports, so observation does not inject duplicate keystrokes. Unsupported reports do not gain capabilities from an attached browser. Every launch sets `TERM=xterm-256color` for the real terminal; explicit launch environment overrides remain authoritative. Evidence: `TerminalEmulator.feed` (`EmulatorUpdate.responses`), `TerminalSession._render_output`, `TerminalManager._start_process`, `TerminalsView.svelte` parser handlers, and the emulator/manager/component tests.

`core/tools/terminal_manager.py` is the public owner of Terminal Session identity, immutable provenance, lifecycle scope, one-Session attachment authorization, and cleanup; each `TerminalSession` carries its activity timing, attention delivery, retained output, and stream sequencing. Durable operator state lives in `core/tools/terminal_store.py` (same domain): the persisted models (`TerminalLaunchHistoryEntry`, `TerminalGroup`, group-id vocabulary), per-entry document parsing for `groups.json`/`launch-history.json` (`parse_groups`/`parse_launch_history` return valid and verbatim invalid entries), and `TerminalOperatorStore`, which holds both live collections, rewrites them atomically on change, degrades a file with an unreadable root to an empty collection with a warning at startup, and owns the newest-first launch-history dedupe/cap policy. The manager keeps every CRUD workflow (including killing sessions on group delete) and re-exports the moved names, so Tool/RPC consumers import from `terminal_manager` unchanged. `core/tools/terminal_backend.py` hides the blocking platform adapter, Windows launcher adaptation, and process-tree termination. Rendering runs off the Event Loop: `TerminalRenderHost` serves each screen from one of up to `DEFAULT_WORKERS` (min(4, half the CPUs, at least 1)) renderer workers, each a thread with its own subinterpreter (and GIL) loaded with only `terminal_emulator.py` and pyte (plus the host's object registry `_hosted_objects.py`), so a program printing heavily does not stall other server work; a screen stays on one worker so its calls stay ordered. Workers start on demand, one per `prepare()` before a screen opens (a screen opened while the first worker is still starting waits for it; `tools/shell.md` -> Output host), and share nothing with the command output host. When no subinterpreter can start, the host renders inline with a warning; tests use `TerminalRenderHost.in_process()`. The manager owns its host unless one is injected and closes it on shutdown. Reads use a manager-owned executor sized for the global live-terminal cap, separate from short adapter operations through `asyncio.to_thread`. Each adapter read waits at most 200 ms for output. POSIX reads the PTY master with nonblocking I/O and incremental UTF-8 decoding; an incomplete character never extends the deadline, and the bytes of a character the output ends inside reach the Session when the output ends (EOF, or the EIO Linux reports once every holder of the terminal closed it), so the log keeps them (code review R4: a log lost the last bytes of a cut character). Windows reads the ConPTY in a dedicated thread with blocking reads (`_WindowsTerminalAdapter`), not through pywinpty's `PtyProcess`, whose socket relay sleeps 1 ms per read and delivered 3,000 lines seconds after the program ended. ConPTY never ends its output when the program exits, so a second thread waits on the program's process handle and, once its output has paused for 20 ms, wakes the waiting read with a timeout: the Session notices the exit within milliseconds instead of at the next 200 ms deadline. In measurements ConPTY delivered all output before the exit completed. `close()` cancels the pending read until the thread ends. A Session closes its adapter when it finishes, a natural exit included: until then ConPTY keeps the reader thread and its console host (`OpenConsole.exe`) alive (probe 2026-10-05; `test_reader_reads_on_after_idle_timeouts_and_stops_when_the_program_ends`). ## Runtime and lifecycle integration

Runtime constructs `TerminalManager` after `TriggerService`, injects `observe_process_tree` as its process observer, the Storage-owned launch-history path, the user-groups path (`<data_dir>/terminals/groups.json`), and atomic-staging root, registers `terminal` after the Sub-Agent coordinator, whose Sub-Agent Sessions `list` names (`SubAgentTree`), and before System Prompt assembly, exposes it through `RuntimeServices`, and closes it before temporary-file cleanup. Run cancellation never closes a Terminal Session; cancelling an Agent `start` while process creation is still pending waits for and disposes that launch (`test_cancelled_start_waits_for_child_cleanup`). Session deletion, Agent removal, Project removal, and archiving or deleting an Extension's temporary group (`close_scope` per live participant Session, through `core/agents/temporary.py::release_temporary_group`) terminate only matching Agent lifecycle scopes; they detach matching bindings from surviving operator-started or differently scoped terminals. Extension execution-group close (`close_execution_group`) terminates only terminals owned by that exact group epoch without changing attachment authority; it rejects launches for the epoch while pending launches drain and releases that admission marker afterwards, because the group owner closes resources only after every owned Run is terminal (`runs.md` -> Extension execution ownership; `test_terminal_manager.py`). Successful `/agent` moves transfer matching lifecycle and attachment scopes and reroute pending delivery while leaving immutable provenance unchanged. An Identity Agent rename does the same for every scope of that Agent's Sessions (`transfer_agent_scope`, called by `core/runtime/_agent_rename.py`, and again with the ids swapped on a revert): Terminals keep running, and their completion notices reach the renamed Session (shell commands move the same way through `CommandManager.transfer_agent_scope`, `tools/shell.md`).
