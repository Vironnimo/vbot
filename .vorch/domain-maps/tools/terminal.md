# Interactive Terminal Sessions (`terminal`)

## Boundary and invariants

`terminal` gives an Agent a real interactive terminal rather than Bash's pipe-based Process Session. Every requested executable uses the same PTY/ConPTY transport and receives the exact declared argument vector. The terminal capability contains no executable detection, program-specific flags, hooks, configuration injection, lifecycle protocol, or screen-text heuristics. Codex, Claude Code, other coding CLIs, shells, editors, games, and arbitrary interactive programs therefore share one contract.

- A Terminal Session is either Agent-owned by one exact `TerminalOwner(project_id, agent_id, session_id)` or manual with no Agent owner. Agent-owned sessions survive individual Runs and enforce that owner; the local operator projection may create manual sessions and observe or control every active Terminal Session without changing ownership.
- The Agent Tool, WebUI, and child process use the same live PTY/ConPTY. Agent and WebUI input are written to that process, WebUI output is the sequenced raw VT stream, and Agent status is rendered from the same stream.
- A Terminal Session ends only on explicit `kill`, natural child exit, applicable owner Session/Agent/Project removal, Runtime shutdown, or unrecoverable terminal failure. Manual sessions have no Agent scope and are therefore unaffected by Agent, Session, and Project cleanup. Leaving a Run or navigating away from the WebUI does not end either kind.
- Live states are `starting`, `ready`, and `working`; terminal states are `exited` and `error`. These states describe terminal activity and process lifetime, not application-specific turns or prompts.
- Raw output and rendered history are bounded. The manager retains a finished Terminal Session's metadata and rendered history for 30 minutes so the operator can inspect it as a read-only snapshot; `terminal.forget` may remove that in-memory record sooner. When Storage is available, the manager additionally retains the raw output in a leased `<data_dir>/artifacts/temp/terminals/*.log` and starts the normal temporary-file retention clock after the Terminal Session ends.
- Successful manual launches additionally update a durable, newest-first launch history under `<data_dir>/terminals/launch-history.json`. Each entry preserves the requested command (including the default-shell choice), exact argument vector, and operator-entered working-directory text; identical configurations move to the front instead of duplicating, the list is capped at 50 entries, and failed launches never enter it.

## Agent Tool contract

`core/tools/terminal.py` exposes one open flat action schema and performs action-specific accepted-field and semantic validation. Its model-facing description starts with the selection boundary: use a real PTY/ConPTY when a program waits for interactive input or must be operated by typing into and observing its live screen, such as a REPL, TUI, prompt, or debugger. An omitted `command` opens the host user's default interactive shell — the same selection the manual operator path uses: on Windows `pwsh.exe`, then `powershell.exe`, then `%COMSPEC%`/`cmd.exe`; on POSIX `$SHELL`, then the account login shell, then `/bin/sh`. A provided `command` launches that exact executable with the given `args`. Either way the default working directory is the current one with 120 columns and 32 rows; there is no program-specific default executable. Its existing `workdir` string accepts ordinary absolute and relative filesystem paths plus the reserved exact prefix `project:<project-id>`, which resolves the registered Project's live `cwd` by stable id before spawn. The Project reference changes only the child start directory: it does not load Project Context, change Rooting, or reassign Terminal ownership, and a spawned process does not move if the Project is later re-pointed. A missing Project returns `project_not_found`; an invalid/unreadable Project record or unreachable Project `cwd` returns `project_unavailable`; all fail before process creation.

- `start`: launches exact `[command, *args]`; optional `text` waits for a stable initial TUI screen and then sends text followed by Enter; optional `name` labels the Session (max 80 chars) so the Agent and operator can recognize it later. The result explains that the Terminal Session survives the Run and that output settling is not a semantic completion signal.
- `list`: returns compact retained Terminal Session summaries for the current owner, including the bounded title announced through the standard terminal protocol when present and the human-friendly `name` when set. Its Tool row derives an exact presentation-only `results` count from `terminals`; other actions and failures publish no count.
- `status`: returns the current rendered screen, up to 30 prior scrollback lines by default, at most 100 lines, an opaque signed cursor for older pages, process facts, dimensions, screen/activity revisions, the bounded program-announced title, and the raw-log path when available. Model-facing `workdir` and raw-log paths use the shared forward-slash presentation while spawn and manager state retain native paths. A cursor fixes Terminal Session and exclusive line boundary; optional `lines` independently selects the continuation page size within the same 1–100 bound. When older output remains, `scrollback.next_request` is a complete copy-ready `status` request carrying the signed cursor and current page size; callers should follow it until null rather than reading the raw VT log as ordinary rendered output.
- `wait`: waits at most 1,000 ms by default and 10,000 ms maximum for a newer generic activity revision, exit, or error. A timeout is a successful current snapshot with `timed_out=true`; it never owns or pauses the child.
- `input`: accepts either exact non-empty `data`, written unchanged in one PTY write, or the convenience combination of non-empty `text`, one named `key`, and `enter`. `data` cannot be combined with the convenience fields. `enter` defaults to false, so a single character such as `i` never acquires an implicit Enter; callers opt in with `enter: true`. Multiline `text` is wrapped in one bracketed-paste sequence only when the current rendered terminal mode says the foreground program enabled it, while single-line `text`, named keys, and exact `data` retain their ordinary semantics. Named keys cover navigation, Insert/Delete/Home/End/Page Up/Page Down, Shift-Tab, F1-F12, and Ctrl-A through Ctrl-Z; arbitrary sequences use `data`. Optional `expected_screen_revision` rejects stale input.
- `resize`: validates conservative bounds, resizes the host PTY/ConPTY and renderer together, and returns the new dimensions and screen revision.
- `kill`: terminates the complete child process tree, suppresses an automatic exit delivery caused by that explicit action, and leaves a bounded exited snapshot until finished-session expiry.
- The `name` field is a purely human/Agent-facing label: it never affects launching, ownership, or lifecycle. Agent-owned and manual sessions both expose it in their summaries; the operator RPC surface (`terminal.start` with `name`) uses the same trimmed non-blank ≤80-char rule. The WebUI tile and list title prefer the custom `name`, then the program-announced `title`, then the launched command.

## Generic activity delivery

Generic terminal bytes cannot reliably distinguish a question, approval request, completed application-level task, idle animation, or prompt. `TerminalManager` therefore emits only `output_settled`, `exited`, and `error` attention kinds and never claims application semantics.

- Agent input starts one activity cycle, changes state to `working`, records the current Run as delivery origin, and arms a two-second quiet timer. Every later PTY output restarts that timer. When the stream stays quiet, state becomes `ready`, a monotonically revisioned `output_settled` record is created, and `TriggerService.submit_completion` wakes the owning vBot Session. The notification explicitly requires the Agent to inspect `status` and says that quiet output does not imply completion or a need for input.
- Operator input and spontaneous output use the same state and quiet detection, but do not independently request an automatic Agent wakeup. A manual Terminal Session has no Agent delivery target at all. Settled revisions remain observable through `wait` for an Agent-owned session.
- Natural exit and terminal failure create `exited` or `error` attention and request delivery. Explicit kill and scope shutdown suppress that delivery.
- `status`, `wait`, `input`, and `kill` acknowledge an equivalent pending delivery only through `ToolContext.after_result_persisted`; handler return alone is not durable acknowledgement. Scope transfer reroutes a pending delivery to the new owner.

## Transport, rendering, and local operator surface

`core/tools/terminal_manager.py` is the deep owner of Terminal Session identity, authorization, lifecycle, activity timing, attention delivery, retained output, stream sequencing, and cleanup. `core/tools/terminal_backend.py` hides the blocking platform adapter, VT renderer, alternate-screen handling, Windows launcher adaptation, and process-tree termination. Blocking adapter operations run through `asyncio.to_thread`.

- Windows uses `pywinpty`/ConPTY and POSIX uses `ptyprocess`/PTY. On Windows, resolved `.cmd` or `.bat` launchers use the platform command processor as a generic executable-format adapter; no command name receives special handling. Windows terminal descendants inherit the server's kill-on-close Job Object. POSIX PTY children run their exact declared command through the same parent-liveness guardian as Process Manager, inside the PTY process group, so abrupt server death kills the terminal tree even though Runtime shutdown cannot run.
- An omitted manual command selects an interactive host shell without changing the PTY path. Windows prefers PowerShell 7 (`pwsh.exe`), then Windows PowerShell (`powershell.exe`), and falls back to `%COMSPEC%`/`cmd.exe`; POSIX prefers `$SHELL`, then the account login shell, and finally `/bin/sh`.
- `pyte` owns bounded terminal rendering. The renderer preserves a separate primary and alternate screen, resizes both buffers, restores the primary screen on alternate-screen exit, tracks the bracketed-paste mode advertised by the foreground program, serializes the retained primary-screen scrollback followed by the current active screen into one authoritative ANSI snapshot for late WebUI viewers, and exposes OSC title/icon metadata as one whitespace-normalized, single-line title capped at 160 characters. Title extraction and terminal-mode tracking are protocol behavior; the manager does not inspect process trees or add program-specific hooks. The authoritative snapshot re-emits the tracked terminal modes before the screen content — alternate screen (`?1049h`), application cursor keys (`?1h`), mouse reporting and other private modes (`?<mode>h`), and bracketed paste (`?2004h`) — so a late viewer lands in the same interactive state as the live terminal instead of rendering a TUI's alternate screen as dead text on the primary screen. Mode tracking lives on the pyte screen subclass (`alternate_active`, `private_modes`, `bracketed_paste_enabled`) and is captured with the screen state, so alternate-screen enter/exit restores the exact prior mode set.
- The manager publishes an authoritative ANSI history-and-screen snapshot followed by contiguous sequenced output/state events. It additionally publishes a sequenced `terminal_snapshot` after an alternate-screen exit, at the quiet boundary following bracketed-paste disable, and immediately before a final exited/error state; these program-agnostic resynchronization points cover TUIs that clear the primary screen instead of using the alternate buffer. A title change publishes a state event and catalog invalidation even for a non-selected background Terminal Session; finished-session expiry publishes the same invalidation. `server/rpc/terminal_methods.py` maps operator start/list/input/resize/kill/forget and `/ws/terminals/{terminal_id}` carries the selected live stream or one retained finished snapshot. `terminal.list` returns both the retained Terminal Session catalog and durable manual `launch_history`; `terminal.start` accepts an optional command, exact argument list, working directory, and dimensions, then returns the started Terminal Session plus the updated history. A manual terminal is always the operator's interactive default shell, so it behaves like a normal terminal: an omitted command opens a bare shell, and a provided command plus arguments is entered into that shell like typed input (exact `data`, then Enter) once a stable prompt screen is rendered — never spawned as the bare PTY child and never sent through bracketed paste or the Agent `send_input` contract. The entered command is shell-quoted only when a token needs it (spaces or shell metacharacters); `pwsh`/`bash`/`cmd`/`sh` all accept the double-quoted form, and the pre-command output plus the exact typed line stay visible in the rendered history. The launch command runs in its own `operator_command_task` (bounded shell-readiness wait, written once, then Enter), never in the Agent initial-input slot: operator input that arrives while the shell is still booting waits for that task instead of cancelling it, so the WebUI's immediate control takeover after start cannot lose or corrupt the command. A started command inside the shell neither ends the Session nor changes the exit semantics: Ctrl+C or program end returns to the shell prompt and the operator keeps typing. Manual summaries expose `launch_command` and `launch_args` (the operator-requested command) beside `command`/`arguments` (the running shell); the list item and tile show the launched command, and the launch history keeps remembering the requested command with its arguments. The Manager never resolves or executes the requested command itself; an empty or blank command rejects, and a command that never sees a stable prompt (silent shell, no prompt marker) is simply not entered.
- `webui/src/lib/terminalsView.js` owns manual start, retained-catalog and launch-history reconciliation, stream reconnect and gap recovery, authoritative `terminal_snapshot` application, exact xterm input batching, resize debounce, and teardown. A terminal that transitions to `exited`/`error` is marked finished immediately: its stream stops reconnecting, buffered input and pending resizes are discarded, and a terminal-closed RPC error from an in-flight request is never surfaced as `actionError` (the transition itself is the expected outcome, for example after Ctrl+C or a program exit). `TerminalsView.svelte` dynamically mounts xterm.js, offers a New terminal dialog whose Recent setup selector defaults to and fills all fields from the newest launch, starts manual terminals in focused direct-control mode, defaults live Agent-owned terminals to observe mode, makes a primary click on a live terminal take control and focus native xterm keyboard/paste input, rebuilds bounded scrollback from every authoritative snapshot after mount, selection, reconnect, navigation, or a TUI mode/exit resynchronization, explicitly refreshes xterm after each rebuild, and confirms process-tree stop. Finished Terminal Sessions remain selectable as read-only history until manager expiry. The Secondary list and detail heading prefer the program-announced title; before one exists they humanize known default shell executable names while retaining the exact command in detail metadata. There is no secondary text composer or program-specific input path. Navigation and socket teardown never own the Terminal Session lifetime. The production Vite build deliberately uses Terser: esbuild minification of xterm 6.0.0's DEC-mode query handler can emit an undeclared enum variable and make nvim output fail at runtime even though the unminified dependency is valid.

## Runtime and lifecycle integration

Runtime constructs `TerminalManager` after `TriggerService`, injects the Storage-owned launch-history path and atomic-staging root, registers `terminal` before System Prompt assembly, exposes it through `RuntimeServices`, and closes it before temporary-file cleanup. Run cancellation never closes Terminal Sessions. Session deletion, Agent removal, Project removal, and successful `/agent` moves close or transfer exact Agent-owned Terminal scopes inside their existing lifecycle boundaries; manual Terminal Sessions end only through explicit stop, natural exit, terminal failure, Runtime shutdown, or the server-level crash boundary. No Terminal Session or retained catalog survives a Runtime restart, and its OS process tree cannot survive separately; the independent manual launch history does survive. Ended sessions remain in the in-memory retained catalog until the 30-minute expiry or explicit operator forget. `terminal` is an ordinary built-in Tool and is part of the default Project Tool allowlist. The bundled `coding-agents` Skill is the program-agnostic operating playbook for Codex, Claude Code, OpenCode, and future interactive coding-agent CLIs: it starts or reuses normal TUI commands through `terminal`, handles questions and approvals against the current screen revision, and preserves the live `terminal_id` across Runs instead of requiring binary-specific headless modes.

Focused coverage lives in `tests/core/tools/test_terminal_backend.py`, `test_terminal_manager.py`, and `test_terminal.py`, with Runtime, lifecycle, RPC, WebSocket, controller, rendered-component, and bundled-Skill contract coverage in their owning test trees. `tests/e2e/tests/terminal-lifecycle.spec.js` exercises the platform default shell and multiple simultaneous real PTY/ConPTY processes through browser start, native input, foreground and background title changes, background output, selection changes, stream reconstruction, navigation, and selective stop. Real Windows validation must use actual ConPTY programs and an unmodified installed Codex CLI because fake adapters cannot prove executable launch fidelity, alternate-screen rendering, browser keyboard/paste behavior, resize, or process-tree stop.
