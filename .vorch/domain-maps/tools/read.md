# Read Tool

Reads a file from the working directory or an absolute path. Text files return their contents with an unpadded `N| ` line-number gutter and separator space; image, audio, and video files are handled by media type.

## Interfaces

- Tool name: `read`
- Registration: `register_read_tool(registry, *, attachment_store, speech_service, file_state, speech_max_size_bytes)`. The handler is built by `make_read_handler(attachment_store, speech_service, file_state, *, speech_max_size_bytes)` (factory pattern, mirrors `image_generation`) and is **async** — path resolution, filesystem probes/reads/stamps, attachment persistence, document extraction, and text rendering run through the Tool worker boundary; only `SpeechService.transcribe(...)` remains awaited on the Event Loop after bounded audio preparation. `render_text_file(raw, offset=None, limit=None)` remains the pure renderer for already-bounded text attachment bytes; local file reads use the streaming path in the same module.
- Schema: required `path`; optional positive 1-indexed `offset` and `limit` controls; `offset` accepts an ordinary line number or an exact `line:character` continuation address returned by the Tool, and omitted `limit` uses 2000 in the handler. The model-facing schema omits `additionalProperties` and JSON Schema defaults; the handler rejects unknown arguments.
- Success: `{ ok: true, data: { content }, error: null, artifacts: [...] }`. `data` is always `{ content }`; `artifacts` is empty except for the image branch.
- Display: primary `path`; when the call explicitly supplies `offset` and/or `limit`, an argument-derived `line_range` fact carries the requested inclusive line range from the started event onward. A continuation address uses its line component, an omitted offset starts at 1, and an omitted limit uses the handler's 2000-line default; an ordinary unbounded/default call has no range fact.

## Conventions

- Relative paths resolve from `ToolContext.effective_cwd` (the working directory); absolute paths are allowed.
- A missing path remains a `file_not_found` failure but appends up to five directly reusable similar-file paths from the same target directory. Candidate discovery is native filesystem I/O, examines at most 50 directory entries, excludes directories, and ranks exact case-insensitive names, equal stems, prefix/substring relationships, then bounded filename similarity.
- `read` is the authoritative read-like tool and must not include a provider/tool parameter named `description`.
- Successful results do not include `data.path`; the agent already knows the requested path from arguments.
- After the path is confirmed to be a file, the handler reads only a bounded leading probe and classifies it with `sniff_media_type` (see `attachments.md`). The branch is chosen by the sniffed media type, not the file extension — **except** the document-extraction branch, which is chosen by `detect_extractable_document(name, media_type)` (sniffed type first, extension fallback; see below). Only a size-approved image, audio file, or extractable document is then materialized, through a reader capped at one byte beyond that branch's limit so a concurrent file growth cannot create an unbounded allocation.
- **Read-before-write stamp:** immediately *before* reading the bytes, the handler calls `file_state.record_read(session_id, resolved)` so the `write`/`edit` guard knows this session has seen the file (see `file_state.md`). Stamping before the byte read is deliberate — if an external write lands in the tiny window after, the stamp stays older than the new content and the next write/edit errs toward a harmless re-read rather than missing the change. Any successful read of an existing file stamps it (text, media, extracted, or binary notice); a partial read (offset/limit or truncation) counts as a full read.

## Behavior by media type

- **text/\*** or anything not image/audio/video → the local file is decoded incrementally as UTF-8 with replacement; a leading BOM is stripped, each retained line receives the unpadded `N| ` gutter whose separator space visually distinguishes the gutter from source content beginning with punctuation, and the reader stops once the requested line window plus evidence of continuation or the 50 KB byte ceiling is known. It never retains an arbitrarily long line or scans to EOF merely to calculate a total. Consequently a truncated local read reports exact shown lines and continuation `offset`, but omits the total line count; an EOF or beyond-EOF read still knows the exact total. A resumed partial line uses `N:C| ` (`C` is a 1-indexed character position). Numbering and the separator space still count against the 2000-line/50-KB output budget. `render_text_file` applies the same caps/gutters to already-bounded attachment bytes and may include the exact total because those bytes already exist in memory.
- **extractable documents** (PDF / `.docx` / `.xlsx` / `.ipynb`, matched by `detect_extractable_document(name, media_type)` — sniffed type first, extension fallback — checked *after* media routing but *before* the binary check) → the raw/compressed file size is rejected before materialization when it already exceeds the extractor's 128 MB budget, and the bounded full reader protects the same ceiling if the file grows concurrently. Approved documents are rendered as plain text by `core/tools/read_extract.py`. Office/notebook rendering is stdlib only (`zipfile` + `xml.etree` + `json`); **PDF text extraction uses `pypdf`** (pure Python, a core dependency). Output is `[Extracted text from <name> (<label>)]:\n<body>` where the body is gutter-free but still passes the shared line/byte truncation. The same budget also caps admitted uncompressed content so an Office archive cannot inflate without bound; exceeding either side returns `document_too_large`. A malformed document falls through to the bounded binary-notice / streaming-text path.
- **binary** (a NUL byte in the bounded leading probe, checked *after* media routing so PNG/MP3/MP4 still take their own branch) → a short `[Binary file: <name> — Path: <resolved>]` notice without reading the remainder of the file. The resolved path and every other vBot-authored path in read failures/notices use the shared forward-slash Model presentation. NUL detection is content-based and non-UTF-8 text without a NUL still streams with replacement characters.
- **image/\*** → `AttachmentStore.ensure_within_limit(file_size)` rejects oversize input before materialization; a bounded read guards concurrent growth, then `AttachmentStore.store()` rechecks size and MIME as the backstop. Successful reads return a neutral `Loaded image …` note plus the `read_media` artifact; Chat resolves the artifact onto that same Tool Result for the active Run and never persists base64 or a synthetic user message.
- **audio/\*** → the runtime's configured `speech_upload_max_size_bytes` rejects oversize input with `audio_too_large` before materialization; a bounded read guards concurrent growth, then `SpeechService.transcribe(bytes, filename=…, media_type=…)` produces plain text.
- **video/\*** → a `[Video: <name> (<type>) — Path: <resolved>]` path note only; the handler never reads beyond the classification probe because no provider wire accepts raw video.

## Constraints & Gotchas

- Expected file, argument, and read-time filesystem errors return failure envelopes (`invalid_arguments`, `file_not_found`, `not_a_file`, `file_read_error`). Similar-file discovery is best-effort: an unreadable/missing parent or no relevant candidates preserves the ordinary not-found message.
- Image promotion failures (oversize or disallowed type from the attachment store) map to an `attachment_error` failure envelope, never a crash.
- Oversize audio maps to `audio_too_large`; STT failures and empty/whitespace transcriptions map to `transcription_failed`. Neither aborts the Run.
- Each image read creates one attachment with no garbage collection, matching the existing attachment policy (GC is out of scope — see `attachments.md`).
- The `N| ` / `N:C| ` gutter, including its separator space, is display-only. `write` content and `edit.new_string` dominated by consecutive gutters are rejected before they can corrupt a file. When raw `edit.old_string` does not match, a complete consecutive gutter block is instead stripped and retried automatically; raw matching always runs first so a real file containing gutter-shaped text keeps literal semantics. The detector (`looks_like_line_numbered_content`), strict recovery helper (`line_number_gutter_candidates`), and shared `LINE_NUMBER_GUTTER_SEPARATOR` live in `core/tools/arguments.py`; both current spaced and reproduced compact gutters are supported. The gutter is the read tool's alone — prompt file inclusion (`{include:...}`) and the memory block render raw file content without it.
- A leading UTF-8 BOM is stripped on read so the model never sees a phantom `U+FEFF`. The `write` tool re-adds a BOM the file already had (see `write.md`) and `edit` round-trips it (the `U+FEFF` stays in the read content and is re-encoded on write), so the read→edit/write loop does not silently drop the marker.
