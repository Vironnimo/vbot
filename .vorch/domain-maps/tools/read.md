# Read Tool

Reads a file or lists a directory, from the working directory or an absolute path. Text files return their contents with an unpadded `N| ` line-number gutter and separator space; image, audio, and video files are handled by media type.

## Interfaces

- Tool name: `read`
- Registration: `register_read_tool(registry, *, attachment_store, speech_service, file_state, speech_max_size_bytes)`. The handler is built by `make_read_handler(attachment_store, speech_service, file_state, *, speech_max_size_bytes)` (factory pattern, mirrors `generate_image`) and is **async** - path resolution, filesystem probes/reads/stamps, image encoding, document extraction, and text rendering run through the Tool worker boundary; only `SpeechService.transcribe(...)` remains awaited on the Event Loop after bounded audio preparation.
- Modules: `read.py` owns the definition, handler, media routing, directory listing I/O, and display. `_read_text.py` owns numbered text windows: `render_text_file(raw, offset=None, limit=None)` (the pure renderer for already-bounded attachment bytes, re-exported from `read.py` for `core/chat/block_resolver.py`), the streaming local-file renderer, line counting, the pattern line filter (`render_matching_lines`; `render_matching_path` for a local file), directory entry paging, and decoded file I/O (UTF-8, an explicit encoding, or a command log; `render_text_path` and `render_matching_path` take `command_log`). `_command_decoding.py` is the shared stdlib-only owner of incremental command-output interpretation (`CommandOutputDecoder`); the Read renderer owns its line-scoped decoding notes. `_read_arguments.py` owns the argument normalizer.
- Schema: required `path`; optional text `encoding`, and integer `offset` and `limit` (integer >= 1; omitted means 2000 in the handler). A positive `offset` is a 1-indexed line and a negative one counts back from the end (`-50` = the last 50 lines). The `line:character` continuation address a cut-off read names (`offset="12:241"`) is accepted but not advertised: the normalizer splits it into `offset` and the hidden `character`. The model-facing schema has no `oneOf`, `additionalProperties`, or JSON Schema defaults; unknown arguments follow the shared rule (`tools.md` -> Unknown fields).
- Unadvertised parameters (`READ_HIDDEN_PARAMETERS`): `pattern`, `ignore_case`, `context` - the line filter below - and `character` (integer >= 1), the 1-indexed character of a continued line. `read_position(arguments)` in `_read_text.py` combines `offset` and `character`.
- Argument normalizer (`normalize_read_arguments`, runs before contract validation): other harnesses' spellings (`SpellingAliases` from `core/tools/call_syntax.py`, shared with other Tools) map to `path` (`file_path`, `filePath`, `filename`, `target_file`, `absolute_path`, `directory`, ...), `offset` (`start_line`, `line_start`, `from`, `start_line_one_indexed`, `line`, ...), `limit` (`max_lines`, `num_lines`, `count`, `n`, `head`, ...), an end line (`end_line`, `line_end`, `to`, `end_line_one_indexed_inclusive`, ...), a range (`lines`/`range`/`line_range`/`line_ranges`/`view_range` as `"10-20"`, `"10:20"`, `"10..20"`, `"L10-L20"`, `"10-"`, `[10, 20]`, `[10, -1]`, `{start, end}`, or an `offset` string such as `"10-20"`), a tail count (`tail`, `last_lines`), and search fields (`query`, `regex`, `-i`, `context_lines`, ...). Each window turns into `offset`/`limit`; a one-item list of ranges (`line_ranges: ["10-20"]`) is that range. A one-file list (`paths`, `file_paths`, `files`, `target_files`, `absolute_paths`, or a list under a `path` spelling; items are paths or objects such as Roo's `{path, line_ranges}`) runs as that file. Notes that request no effect are dropped: `explanation`, `description`, `command: "view"`, and `IncludeSummaryOfOtherLines: false` (a `true` runs with the note that it had no effect, `tools.md` -> Unknown fields). Any other `command` comes back as that command and its `path`, which the handler refuses as `invalid_arguments` naming the edit Tool the Agent was offered (`read has no command "X": it shows the file or lists the directory given as path. To change a file, call apply_patch.`, or `edit`; the last sentence is left out when neither is offered; `change_command_refusal`, `offered_edit_tool`), because only the handler knows the offered Tools. A call that names a Swarm Board post as `message_id` (any spelling) and no path comes back as that `message_id` (with `path: "."` only to pass the contract), which the handler refuses before reading anything: `read has no message_id: it shows the file or lists the directory given as path. #452 is a Swarm Board post; read it with swarm_board {"action": "read", "message_id": "#452"}.`, the second sentence only when `swarm_board` is offered (`message_id_refusal`, `core/tools/_swarm_references.py`; Swarm Sessions, 2026-10-12: two such calls failed naming only `path`). Several files or several ranges fail listing one call per file or range. `offset` 0 or 1 and `limit` <= 0 are dropped (start of file, default bound); `should_read_entire_file: true` drops every line bound. Any other `offset` text (`"max-10"`) fails naming `offset=10` and `offset=-10`. Windows that disagree (`offset` vs a range, `limit` vs an end line, a tail vs `offset`), a range that ends before it starts, and a bare `lines: N` (first N lines or line N) fail as `invalid_arguments` naming the call(s) to send; conflicting spellings of one field use `ToolContractError.conflicting_values`, which names the Tool, both spellings and their values (`read was not run: Conflicting values for offset: offset is 3 and start_line is 5. Send only the intended one.`). Fields only a multi-file search uses (`glob`, `include`, `output_mode`, `files_with_matches`, `file_pattern`) fail with the equivalent `search_files(...)` call. All of this fails before the handler, and the `command` refusal before the handler reads anything, so nothing is stamped.
- Success: `{ ok: true, data: { content, next_offset? }, error: null, artifacts: [...] }`. A cut-off text window, extracted document, directory listing or matching-lines page includes `next_offset`, the same integer line/entry or `"line:character"` address named in its continuation hint. It is absent when the page has no continuation. `_read_text.ReadPage` carries this value from rendering without parsing display text; attachment and Skill renderers retain their text-only interfaces. `artifacts` is empty, including for images.
- Display: a `parts_builder` shows the normalized `path` (so `file_path` and other spellings display), and when the normalized call supplies `offset` and/or `limit`, an argument-derived `line_range` fact carries the requested inclusive line range from the started event onward. A continuation address uses its line component, an omitted offset starts at 1, and an omitted limit uses the handler's 2000-line default; an ordinary unbounded/default call and a negative offset have no range fact.

## Conventions

- Relative paths resolve from `ToolContext.effective_cwd` (the working directory); absolute paths are allowed.
- vBot-authored paths in results and errors are relative to the working directory when the file is under it, absolute otherwise, always with forward slashes (`display_search_path`, shared with `search_files`).
- A missing path fails with `file_not_found`: `File not found: <path> (similar: a, b).` using up to five suggestions from `corrected_paths` in `core/tools/_path_suggestions.py` (shared with `search_files`: a relative path that repeats the end of the working directory, per-component spelling repair, for a name missing from an existing folder inside the working directory the same name in other folders below it (shallow levels first, at most 6 levels and 5000 entries, hidden folders, `node_modules` and `__pycache__` skipped; `corpus.py` -> `tests/corpus.py`), then similar names beside the missing one, files or directories: the same name or stem, a name that begins with or contains the other, or one that is at most one typo per four characters of the missing stem away (at least one; inserted, removed, replaced or swapped characters, `core/utils/edit_distance.py`); names with the same extension are compared by stem, since a shared `.py` made `parser.py` suggest `planner.py`, `ast.py`, `analyzer.py`, `lexer.py` and `shell.py` (Swarm Sessions, 2026-10). The typo bound replaced a similarity ratio that a shared beginning dominated: a missing `tests/test_expr.py` suggested `test_index.py`, `test_api.py`, `test_errors.py`, `test_planner.py` and `test_shell.py` (Swarm Sessions, 2026-10-12)). Under Permission Rules, refused entries of the deepest existing readable folder whose names are close to the first missing part follow as `Similar: secrets - the permission rules refuse reading it.` (`Also similar:` after suggestions; `refused_note`), never anything inside a refused folder. Without suggestions it names the listing call when the parent exists as a copyable call (`read(path="<dir>") lists its directory.`) or says the parent does not exist. Suggestions are never applied. `missing_file_message` in the same module builds this text for `read` and for `apply_patch`/`edit` operations on missing files. A missing bare Swarm Wiki page number directly in the working directory (`w2`, `w2.md`, any case) names the `swarm_wiki` call instead of the listing call when `swarm_wiki` is offered: `w2 is not a file. Swarm Wiki page w2 reads with swarm_wiki {"action": "read", "page_id": "w2", "offset": 5400, "limit": 1400}.`; a positive `offset` and `limit` are carried along when each is at least 1000, as a Wiki read's character continuation is, because an Agent sent one to `read` (`wiki_page_call` in `core/tools/_swarm_references.py`; Swarm Sessions, 2026-10-12). Smaller values are line numbers, which `swarm_wiki` would read as characters, so the call leaves them out and the sentence says so: `... reads with swarm_wiki {"action": "read", "page_id": "w2"}. The call leaves out offset 190 and limit 20: swarm_wiki counts them in characters, not lines. To read around a passage, add query with words from it.` (Swarm run 2026-10-12: of two such reads, one carried a Wiki continuation's characters, the other lines a peer had cited). With similar names the sentence follows the suggestions. `edit` and `apply_patch` name the change instead: `w3.md is not a file. Swarm Wiki page w3 changes with swarm_wiki: action "update", page_id "w3", and old_text and new_text for the passage.` (`write` creates a missing file and has no such error).
- A path whose status cannot be checked fails with `file_read_error` and the same English OS reason as a failed read; only confirmed absence receives missing-path suggestions.
- A directory path lists its entries: `Directory <dir>/ (<N> entries):`, then one name per line sorted case-insensitively, hidden entries included, directories suffixed `/`; each shown file is followed by two spaces and its size (`7 B`, `1.5 KB`, `12 KB`: bytes below 1 KB, one decimal below 10 units, whole units from 10 up; omitted when it cannot be read; only the shown page is sized). Sizes were added because Agents ran 36 shell listings only to see file sizes (Swarm review, 2026-10). `offset`/`limit` page entries like lines (negative offset from the end, 50 KB cap, `[Showing entries A-B of N. Use offset=M to continue.]`). Under Permission Rules, entries the rules refuse to read are left out and named in a closing note, folders first, up to five, the rest counted (`listing_note` in `core/tools/_refused_notes.py`). A listing never stamps anything. A path that is neither a file nor a directory fails with `not_a_file`.
- `pattern` (unadvertised) on a text file or extracted document shows only the matching lines, numbered like a read, with `context` lines around each match and `--` between separated groups; the first line states the filter (`<N> lines of <path> match "<pattern>":`, or `No line of <path> matches ...`). An invalid regex matches as plain text, said in that line; `ignore_case` adds case folding; a positive `offset` starts the search at that line and `limit` bounds shown lines, with a continuation offset. A matching line over 2000 characters is cut with its `line:character` continuation. `pattern` on a directory fails with the equivalent `search_files(...)` call; on an image, audio, video, or binary file it fails before any read. A filtered read stamps the file like any successful read.
- `read` is the authoritative read-like tool and must not include a provider/tool parameter named `description`.
- Successful results do not include `data.path`; the agent already knows the requested path from arguments.
- Without an explicit `encoding` and outside command logs, after the path is confirmed to be a file the handler reads only a bounded leading probe and classifies it with `sniff_media_type` (see `attachments.md`). The branch is chosen by the sniffed media type, not the file extension - **except** the document-extraction branch, which is chosen by `detect_extractable_document(name, media_type)` (sniffed type first, extension fallback; see below). Only a size-approved image, audio file, or extractable document is then materialized, through a reader capped at one byte beyond that branch's limit so a concurrent file growth cannot create an unbounded allocation.
- **Read-before-write stamp:** immediately *before* reading the bytes, the handler captures `file_state.stamp(resolved)`, and it records that stamp with `record_stamp(session_id, resolved, stamp)` only after the read succeeded (for audio, after transcription), so the full-replacement guard knows this session has seen the file (see `file_state.md`). Capturing before the byte read is deliberate - if an external write lands during the read, the recorded stamp stays older than the new content and the next full-file write errs toward a harmless re-read rather than missing the change. Any successful read of an existing file stamps it (text, media, extracted, or binary notice); a partial read (offset/limit or truncation) counts as a full read. Failed reads (`audio_too_large`, `transcription_failed`, `document_too_large`, `attachment_error`, `file_read_error`, invalid offsets) never stamp (`test_failed_read_does_not_stamp_the_file`).

## Behavior by media type

- **Line numbering:** lines end only at LF, CRLF, or a lone CR (`TEXT_LINE_BREAK` / `split_text_lines` in `arguments.py`, shared with `apply_patch` matching and previews and change statistics). Form feed, vertical tab, `\x1c`-`\x1e`, NEL, and U+2028/U+2029 are ordinary in-line characters, so `read` numbers match `search_files` coordinates. Remaining difference: ripgrep counts only LF, so a file with lone-CR line endings reports search matches on ripgrep's lines (`test_line_numbers_break_only_at_lf_crlf_and_cr_like_search_files`).
- **text/\*** or anything not image/audio/video -> the local file is decoded incrementally as UTF-8 with replacement; a leading BOM is stripped, each retained line receives the unpadded `N| ` gutter whose separator space visually distinguishes the gutter from source content beginning with punctuation, and every rendered line break is a plain LF (the CR of CRLF or lone-CR files is not shown; `apply_patch` preserves the file's endings). The reader stops once the requested line window plus evidence of continuation or the 50 KB byte ceiling is known and never retains an arbitrarily long line. A truncated read then counts the file's lines in a separate byte pass (`count_lines`, same LF/CRLF/CR rules) when the file is <= 256 MB, so the hint reads `[Showing lines A-B of T. Use offset=N to continue.]`; larger files omit ` of T`. A negative `offset` counts lines first (no size cap) and starts at `max(1, T + offset + 1)`. A resumed partial line uses `N:C| ` (`C` is a 1-indexed character position), and the hint quotes its continuation: `Use offset="N:C" to continue.` A `line:character` pair whose character is past the end of that line is read as a line range when the character is >= the line (`offset: "100:120"` -> `[Line 100 has no character 120, so offset "100:120" was read as offset=100, limit=21.]` before the lines; an explicit `limit` keeps its count and the note says `offset=100`); otherwise nothing is shown and the note names `offset=<line>` (`_past_line_end`). An empty file returns `[<path> is empty.]`. Numbering and the separator space still count against the 2000-line/50-KB output budget. `render_text_file` applies the same caps/gutters/line-end rules to already-bounded attachment bytes.
- **extractable documents** (PDF / `.docx` / `.xlsx` / `.ipynb`, matched by `detect_extractable_document(name, media_type)` - sniffed type first, extension fallback - checked *after* media routing but *before* the binary check) -> the raw/compressed file size is rejected before materialization when it already exceeds the extractor's 128 MB budget, and the bounded full reader protects the same ceiling if the file grows concurrently. Approved documents are rendered as plain text by `core/tools/read_extract.py`. XLSX worksheet relationship targets resolve relative to the workbook part or from the package root, normalizing dot segments before ZIP lookup. Office/notebook rendering is stdlib only (`zipfile` + `xml.etree` + `json`); **PDF text extraction uses `pypdf`** (pure Python, a core dependency). Output is `[Extracted text from <name> (<label>)]:\n<body>` where the body is gutter-free but still passes the shared line/byte truncation. The same budget also caps admitted uncompressed content so an Office archive cannot inflate without bound; exceeding either side returns `document_too_large`. A malformed document falls through to the bounded binary-notice / streaming-text path.
- **Command logs** (files under `DataDirectoryLayout(ToolContext.data_root).command_temporary`, `artifacts/temp/commands`; `tools/shell.md`) -> always text, also with `pattern`, before media routing or binary detection. Raw bytes remain unchanged. Without `encoding`, `CommandOutputDecoder` interprets mixed program output incrementally: valid UTF-8 first; UTF-16LE without a BOM after at least 3 consecutive U+0001-U+00FF code units; either UTF-16 BOM selects its byte order. A BOM owns at least the whole current line, including CJK and surrogate pairs. After a decoded UTF-16 line end, a complete NUL-free UTF-8 line within the 256-byte inference window can switch back to UTF-8; an aligned UTF-16 line end in that window keeps UTF-16. Unterminated or longer ambiguous suffixes keep the BOM's encoding. Other NUL bytes are omitted. These are interpretations, not a universal mixed-encoding detector: a CR/LF byte inside a CJK code unit can imitate a UTF-8 line, and unmarked UTF-16 beyond U+00FF need not have recognizable zero bytes. `encoding="utf-16"` honors a BOM throughout; `utf-16-le`/`utf-16-be` choose a fixed byte order without requiring a BOM. The raw log remains available for byte inspection. The renderer, line count, tail, search and character continuations use the same decoding. `_LogDecoding.note` identifies only the shown lines that contain decoded UTF-16, omitted NUL bytes or inferred UTF-8 after UTF-16; more than 6 disjoint line ranges are summarized. It names the exact fixed-encoding recovery for an inferred switch. Tests: `test_a_command_log_reads_as_the_text_its_programs_wrote`, `test_an_inferred_encoding_change_is_named_only_for_the_lines_shown` (review 2026-10-13: UTF-8 before NUL, mixed byte orders, CJK at/after a BOM, and image-like log prefixes).
- **Explicit text encoding** (`encoding`) -> validates a standard Python text codec before opening the path, then reads the file as text in that encoding before media routing, document extraction or binary detection. No automatic switches or NUL omission; invalid sequences use replacement characters. This applies to ordinary files and command logs, line counting, negative offsets, `pattern` and character continuations. `utf-16` requires a BOM and follows it; explicit `utf-16-le`/`utf-16-be` do not require one. An unknown/non-text codec returns `invalid_arguments`; a required but missing BOM also returns `invalid_arguments` with byte-order guidance. Empty placeholders mean omission. A directory still lists its entries. The optional parameter is an escape hatch for evidenced ambiguous bytes: the same suffix can be valid single-stream UTF-16 and mixed UTF-8 output, so automatic inference alone cannot promise the author's intent (`test_an_explicit_encoding_applies_to_the_whole_file`).
- **binary** (a NUL byte in the bounded leading probe, checked *after* media routing so PNG/MP3/MP4 still take their own branch; not for command logs or an explicit `encoding`) -> a short `[<path> is a binary file, so it is not shown as text. A <shell> command for this file type can inspect it.]` notice (`<shell>` is `SHELL_MODEL_NAME`; the second sentence only when the Agent is offered the shell, `ToolContext.offers`) without reading the remainder of the file. NUL detection is content-based and non-UTF-8 text without a NUL still streams with replacement characters.
- **image/\*** -> the configured attachment size limit rejects oversized input before materialization, and a bounded read guards concurrent growth. Successful reads return the existing `Loaded image ...` note with no artifact. Pixels cross `ToolContext.result_media` in memory; Chat stores them as an Attachment and adds supported media/path blocks to the correlated request-only Tool Result (`chat/request-building.md`). The Tool itself writes no attachment, sidecar, or other image copy. Presentation metadata retains only the original absolute path for signed preview delivery, including the existing missing-image placeholder after deletion.
- **audio/\*** -> the runtime's configured `speech_upload_max_size_bytes` rejects oversize input with `audio_too_large` before materialization; a bounded read guards concurrent growth, then `SpeechService.transcribe(bytes, filename=..., media_type=...)` produces plain text.
- **video/\*** -> a `[<path> is a video (<type>); this model cannot view video.]` note only; the handler never reads beyond the classification probe because no provider wire accepts raw video.

## Constraints & Gotchas

- Expected file, argument, and read-time filesystem errors return failure envelopes (`invalid_arguments`, `file_not_found`, `not_a_file`, `file_read_error`). `file_read_error` reads `Could not read <path>: <reason>.` (`Could not list ...` for a directory); `os_error_reason` in `file_state.py` gives the reason in English without the absolute path, because Windows reports OS messages in the system language. Normalizer failures are raised as `ValueError`/`ToolContractError` and become `invalid_arguments` in Chat dispatch. Similar-path discovery is best-effort.
- Image size-limit failures map to an `attachment_error` failure envelope, never a crash.
- Oversize audio maps to `audio_too_large`; STT failures and empty/whitespace transcriptions map to `transcription_failed`. Neither aborts the Run.
- Loaded pixels stay with their Tool Result in every request until Compaction or a Provider image limit retires them; Chat keeps the stored copy, so later Runs and restarts need no re-read. Chat validates loaded pixels and prepares them against known destination limits, including HEIC/HEIF input; altered copies and failures receive path notes (see `attachments.md` and `chat/request-building.md`).
- The `N| ` / `N:C| ` gutter, including its separator space, is display-only. `apply_patch` recovers supported gutter blocks only under its patch-specific rules (see `apply_patch.md`); literal matching takes precedence for files containing gutter-shaped text. The strict recovery helper (`line_number_gutter_candidates`) and shared `LINE_NUMBER_GUTTER_SEPARATOR` live in `core/tools/arguments.py`; both current spaced and reproduced compact gutters are supported. The gutter is the read tool's alone - prompt file inclusion (`{include:...}`) and the memory block render raw file content without it.
- `apply_patch` diagnostics use the same `line:character` offset for truncated
  candidate excerpts. The continuation names the first omitted character, allowing
  the Agent to reconstruct a complete old-text locator across reads; centered
  mismatch windows separately identify the differing character without implying
  that an excerpt is a whole line (`test_apply_patch_reports.py`).
- A leading UTF-8 BOM is stripped on read so the model never sees a phantom `U+FEFF`. `apply_patch` preserves it during full replacement and targeted Updates.

## Agent-facing text

| Text | Reason |
|---|---|
| `Read a text file with line numbers, list a directory, view an image, transcribe an audio file, or extract the text of a PDF, Word, Excel or Jupyter file.` | Names every input kind, so an Agent does not reach for the shell or a converter for images, audio, or Office files (F1). |
| `Text lines start with "N\| " (the line number, not file content).` | Agents copied the gutter into patches and quotes (F4); `apply_patch` recovers it, but the result stays readable only if the gutter is known. |
| `Use this instead of cat, head, tail, Get-Content or ls in the shell.` | Shell reads bypass the read stamp and the 50 KB bound (F1, F6). |
| `offset`: `Line to start at, counting from 1.` | Pins the base; 0-based and 1-based habits differ between harnesses (F2). |
| `offset`: `A negative number counts back from the end: -50 shows the last 50 lines.` | Replaces tail in the shell; the example fixes the sign. |
| `offset`: `Omit to read from the start.` | Omit rule: an optional field without one invites placeholder values such as 0 (F2). Advertised as integer only: Models read the former `line:character` string form as a line range (`"1:300"`), which returned nothing (Sessions, 2026-09). |
| `limit`: `Maximum number of lines to show. Omit to show up to 2000 lines.` | Omit rule with the bound, so Agents do not ask for huge counts or read in tiny windows (F6). |
| `limit`: `Output is capped at 50 KB.` | A 143-line document stopped at line 114 despite the advertised 2000-line default (Sub-Agent report, 2026-10-13). Exposes the independent byte ceiling before the call. |
| `encoding`: `Read as text in this encoding, such as utf-8 or utf-16.` | A deliberate text decoding choice bypasses media/binary routing. Ambiguous UTF-16 CJK bytes were reinterpreted as UTF-8; the parameter gives an exact reading without guessing (Shell review 2026-10-13). |
| `encoding`: `Omit to detect command-log encodings and use UTF-8 for other text files.` | Keeps ordinary calls automatic and prevents filling an encoding unnecessarily, which would disable mixed-log interpretation and media routing. |
| Inferred log note: `Line 3 was read as UTF-8 after UTF-16; this encoding change is inferred.` | Names a heuristic interpretation only for affected shown lines, including tail/search. Unframed mixed output and a pure CJK stream can have identical bytes. |
| Same note: `For a single UTF-16 stream, pass encoding="utf-16".` | Gives the precise recovery when the interpretation differs from the known source encoding, instead of implying that inference is guaranteed. |
| `Unknown text encoding '...'` | Rejects unknown names and non-text transforms before opening a file, instead of silently applying the default. |
| `Use a text encoding such as "utf-8", "utf-16", "utf-16-le" or "utf-16-be".` | Gives valid choices at the failed call; an unrecognized codec name otherwise invites retries with the same value. |
| `Could not decode <path> using encoding='...'.` | A codec can be valid but unsuitable for these bytes, such as `utf-16` without a BOM; this distinguishes decoding failure from a missing file or an unknown codec. |
| `Pass the file's text encoding, including its byte order (such as "utf-16-le") when it has no byte order mark.` | Explains the choice needed to recover a BOM-less UTF-16/UTF-32 stream, without guessing byte order. |
| `file_not_found` for a page number: `w2 is not a file. Swarm Wiki page w2 reads with swarm_wiki {...}.` | An Agent sent Wiki page `w2` with a Wiki read's character `offset` and `limit` to `read` and got `File not found` with an unrelated listing call (Swarm Sessions, 2026-10-12). Only when `swarm_wiki` is offered. |
| Same, with line positions: `The call leaves out {offset 190 and limit 20}: swarm_wiki counts them in characters, not lines. To read around a passage, add query with words from it.` | The suggested call copied `read`'s line positions into `swarm_wiki`, which would have read 20 characters from character 190 (Swarm run 2026-10-12: 1 of 2 such reads). The first sentence says why the values are gone, so the Agent does not add them back; the second names the `swarm_wiki` way to find a passage. |
| Command log note: `[Lines 2-4 contain text decoded as UTF-16.]` and `[NUL bytes in line 1 are left out.]` before the lines, for the lines shown only | The text shown differs from the file's bytes: a search or shell read of the log finds the NUL bytes, not the text (F4). Shell review 2026-10-13 (finding D). It names the lines and says how they were decoded, not what they are: a log mixes encodings, and the runs are a reading of its bytes (review 2026-10-13: the earlier note `[Decoded the UTF-16 text in this output; other NUL bytes are left out.]` stood for the whole file whenever its first 64 KiB held a NUL, and `[Decoded from UTF-16.]` for a log that only started with a byte order mark). |
| Listing note: `[Not listed: secrets/, .env and 3 more - the permission rules refuse reading them.]` | A listing that silently omits entries reads as the whole folder, and the Agent does not hunt for the entries through the shell only when it knows why (F4). The names say what exists but is refused: under the former count alone (`[2 entries are not listed: ...]`) an Agent that never learned of a refused `secrets/` told the user the project had no API key, and another called a refused folder empty (eval 2026-10-22). They reveal nothing new: they are entries of a folder the Agent may read. Folders first, since the count after five hides the rest. |
| Not-found sentence: `Similar: secrets - the permission rules refuse reading it.` / `Also similar: ...` after the suggestions | A typo such as `secret/api.key` for a refused `secrets/` answered only that `secret` does not exist, which reads as absence (F4, same eval).
