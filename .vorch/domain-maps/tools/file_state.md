# File-State and Mutation Coordination

The per-session read stamps, per-path mutation locks, and atomic replacement shared by `read` and `apply_patch`. Lives in `core/tools/file_state.py`.

## Overview

A single runtime-owned `FileReadState` registry remembers, per Session, the `(mtime, size)` of every file a Session has read. Full-file `apply_patch` Add uses that stamp as a hard precondition for an existing target; an `apply_patch` Update instead treats its unique match against current bytes as the optimistic precondition and consults the stamp only to report metadata drift after a successful merge. The same object owns ephemeral per-resolved-path locks so in-process mutations of one file serialize without blocking different files. It is constructor-injected into `read`, `apply_patch`, and the explicit `project` Tool (one instance built in `Runtime`, like `ProcessManager` for `bash`) - not a module singleton. Three non-`read` sources stamp files the model receives: (1) the `@`-mention expansion (`core/chat/file_mentions.py`) stamps an inlined send-time file snapshot - a degraded snapshot (too large / not text / missing) is deliberately not stamped; (2) the System Prompt build stamps every auto-injected prompt file (SOUL, on-disk pinned-memory files, Project auto-load files, workspace `{include:...}`) through `ChatLoop._stamp_prompt_files_read`; (3) the `project` Tool directly stamps every Project auto-load file returned in its result through the prompt renderer's read observer. Stamp design follows OpenCode's (since-removed) `FileTimeService`; it deliberately does not track sibling identities, store read timestamps, or hash content because `(mtime, size)` answers whether the path changed since this Session saw it.

## Interfaces

- `FileReadState.record_read(session_id, resolved)` - stat the file and store `(mtime, size)`. Called by `apply_patch` *after* a successful mutation (a mutation is an implicit read of the resulting content), by `apply_patch` when a refused full replacement shows the whole unchanged file in its error (small text files; see `apply_patch.md`), and by the other stamping sources below.
- `FileReadState.stamp(resolved)` / `record_stamp(session_id, resolved, stamp)` - two-phase variant used by `read`: capture `(mtime, size)` *before* reading bytes, record it only *after* the read succeeded.
- `FileReadState.check_stale(session_id, resolved) -> StaleReason | None` - `NEVER_READ` (no stamp for this Session+path), `MODIFIED` (current `(mtime, size)` != stamp), or `None` (current). Returns `None` when the file cannot be stat'd (vanished mid-call -> a race, not staleness). Add replacement maps either stale reason to a hard failure; Update ignores `NEVER_READ` and converts `MODIFIED` into a post-success entry in `warnings` only when its current-content match succeeds.
- `FileReadState.lock_path(resolved)` - context manager that serializes mutations of exactly one resolved path. Lock entries count holders plus waiters and disappear when the final user leaves, so the Runtime does not accumulate a permanent path-lock catalog.
- `stale_failure_text(reason, resolved) -> (code, message)` - Full replacement mapping to `file_not_read` / `file_modified_since_read`; names the `read` Tool because shell reads do not stamp files, and gives current-context Update as the alternative when read is unavailable. The known path uses forward-slash presentation. Observation: no production caller remains; `apply_patch` builds its own guard text (`_guard_failure`), and only `core/tools/__init__.py` exports and `test_file_state.py` use it.
- `atomic_write_bytes(resolved, payload, *, mode=None, before_replace=None)` - flush bytes through an exclusive same-directory temporary file (opened `0o666`, so a new file gets the ordinary umask-derived mode, e.g. `0o644` under umask 022, instead of `mkstemp`'s owner-only `0o600`), preserve an existing target's permission bits unless an explicit source mode is supplied for a patch move, install with `os.replace`, and remove the temporary file on every failure before replacement (clearing a copied Windows read-only attribute first; a still-failing removal logs a warning). A target marked read-only on Windows raises non-retryable `ReadOnlyFileError` ("the file is read-only") before or instead of replace retries, because Windows refuses to replace it; POSIX replaces a read-only target and keeps its mode. With a caller-supplied precondition callback, retry only replace-stage Windows errors 5/32/33 up to six times (1.57s total scheduled delay), checking caller preconditions before each attempt. Exhausted errors carry `attempts_made` for the caller's retry metadata. No callback means no retry. Preparation, observation and deletion failures never replay a replacement.
- `FILE_STATE_GUARD_ENABLED` (module constant, default `True`) - process-wide read-stamp off switch; when `False`, `record_read` no-ops and `check_stale` returns `None`, while path locks and atomic replacement remain active.

## Constraints & Gotchas

- `apply_patch` receives the same Runtime-owned registry. It locks all resolved patch paths in deterministic order, attempts ordered hunks/file operations independently against current bytes, rechecks writes, and stamps successful surviving files including no-ops. Its Update semantics are current-content optimistic matching; multi-file failure and byte recheck semantics belong in `apply_patch.md`.

- **Stamp key is `(session_id, str(resolved))`** - per Session, by resolved absolute path. Different Sessions (including Sub-agents, which get their own Session) never share read history. State is in-memory only, lost on restart (which forces a re-read only for a later full-file overwrite).
- **New files, empty files and identical Add no-ops are exempt at the patch call site.** Add runs `check_stale` only when it would change existing bytes that are not empty or whitespace-only (a BOM alone counts as empty); an `apply_patch` Update operates on an existing file but never treats `NEVER_READ` as a conflict. `check_stale` itself reports `NEVER_READ` for any unstamped path regardless of existence - callers own operation-specific policy.
- **Comparison is not-equal on `(mtime, size)`**, not strictly-newer. `size` is a free second signal that catches some same-`mtime`-tick changes (coarse filesystem resolution). A same-length change within the same mtime tick is the accepted blind spot - no content hashing closes it by design.
- **Stamp before the byte read** (in `read`): if an external write lands in the window after the stamp, the stamp stays older than the new content, so a later full replacement errs toward a harmless re-read while Update can disclose that it merged against newer bytes. The captured stamp is recorded only for a successful read.
- **Bash writes are not stamped.** A file changed via `bash` (e.g. `sed -i`) is later seen as `MODIFIED`; full replacement forces a re-read, while Update applies only through its current-content match and reports the drift after success. vBot deliberately does **not** parse bash commands to re-stamp touched files.
- **Partial reads count as full reads** - `record_read` ignores offset/limit/truncation, so a truncated read of a large file still satisfies the guard for a later full replacement; Update needs no stamp because its match is against current bytes.
- **Locks are process-local.** They prevent interleaving among Tools using the one Runtime-owned `FileReadState`; another process or an uncoordinated external writer is still outside the lock. Stamp checks detect prior metadata drift, while same-directory atomic replacement prevents partial target contents but is not a portable filesystem compare-and-swap against an external writer racing after the check.
- **Bounded:** at most `_MAX_TRACKED_FILES` (8192) entries; oldest insertion evicted first. A rare eviction only costs a harmless re-read.
