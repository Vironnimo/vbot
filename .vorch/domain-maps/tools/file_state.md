# File-State and Mutation Coordination

The per-session read stamps, per-path mutation locks, and atomic replacement shared by `read`, `write`, and `edit`. Lives in `core/tools/file_state.py`.

## Overview

A single runtime-owned `FileReadState` registry remembers, per Session, the `(mtime, size)` of every file a Session has read. Full-file `write` uses that stamp as a hard precondition for an existing target; targeted `edit` instead treats its unique match against current bytes as the optimistic precondition and consults the stamp only to report metadata drift after a successful merge. The same object owns ephemeral per-resolved-path locks so in-process mutations of one file serialize without blocking different files. It is constructor-injected into `read`, `write`, `edit`, and the explicit `project` Tool (one instance built in `Runtime`, like `ProcessManager` for `bash`) - not a module singleton. Three non-`read` sources stamp files the model receives: (1) the `@`-mention expansion (`core/chat/file_mentions.py`) stamps an inlined send-time file snapshot - a degraded snapshot (too large / not text / missing) is deliberately not stamped; (2) the System Prompt build stamps every auto-injected prompt file (SOUL, on-disk pinned-memory files, Project auto-load files, workspace `{include:...}`) through `ChatLoop._stamp_prompt_files_read`; (3) the `project` Tool directly stamps every Project auto-load file returned in its result through the prompt renderer's read observer. Stamp design follows OpenCode's (since-removed) `FileTimeService`; it deliberately does not track sibling identities, store read timestamps, or hash content because `(mtime, size)` answers whether the path changed since this Session saw it.

## Interfaces

- `FileReadState.record_read(session_id, resolved)` - stat the file and store `(mtime, size)`. Called by `read` *before* reading bytes, and by `write`/`edit` *after* a successful mutation (a mutation is an implicit read of the resulting content).
- `FileReadState.check_stale(session_id, resolved) -> StaleReason | None` - `NEVER_READ` (no stamp for this Session+path), `MODIFIED` (current `(mtime, size)` != stamp), or `None` (current). Returns `None` when the file cannot be stat'd (vanished mid-call -> a race, not staleness). `write` maps either stale reason to a hard failure; `edit` ignores `NEVER_READ` and converts `MODIFIED` into a post-success `stale_warning` only when its current-content match succeeds.
- `FileReadState.lock_path(resolved)` - context manager that serializes mutations of exactly one resolved path. Lock entries count holders plus waiters and disappear when the final user leaves, so the Runtime does not accumulate a permanent path-lock catalog.
- `stale_failure_text(reason, resolved) -> (code, message)` - `write` mapping to `file_not_read` / `file_modified_since_read`; the known path inserted into the Model-facing message uses the shared forward-slash presentation.
- `atomic_write_bytes(resolved, payload)` - flush bytes through a same-directory temporary file, preserve an existing target's permission bits, install with `os.replace`, and remove the temporary file on every failure before replacement.
- `FILE_STATE_GUARD_ENABLED` (module constant, default `True`) - process-wide read-stamp off switch; when `False`, `record_read` no-ops and `check_stale` returns `None`, while path locks and atomic replacement remain active.

## Constraints & Gotchas

- **Stamp key is `(session_id, str(resolved))`** - per Session, by resolved absolute path. Different Sessions (including Sub-agents, which get their own Session) never share read history. State is in-memory only, lost on restart (which forces a re-read only for a later full-file overwrite).
- **New files are exempt at the `write` call site, not here.** `write` runs `check_stale` only when `resolved.exists()`; `edit` always operates on an existing file but never treats `NEVER_READ` as a conflict. `check_stale` itself reports `NEVER_READ` for any unstamped path regardless of existence - callers own operation-specific policy.
- **Comparison is not-equal on `(mtime, size)`**, not strictly-newer. `size` is a free second signal that catches some same-`mtime`-tick changes (coarse filesystem resolution). A same-length change within the same mtime tick is the accepted blind spot - no content hashing closes it by design.
- **Stamp before the byte read** (in `read`): if an external write lands in the window after the stamp, the stamp stays older than the new content, so a later full `write` errs toward a harmless re-read while `edit` can disclose that it merged against newer bytes.
- **Bash writes are not stamped.** A file changed via `bash` (e.g. `sed -i`) is later seen as `MODIFIED`; full `write` forces a re-read, while `edit` applies only through its current-content match and reports the drift after success. vBot deliberately does **not** parse bash commands to re-stamp touched files.
- **Partial reads count as full reads** - `record_read` ignores offset/limit/truncation, so a truncated read of a large file still satisfies the guard for a later full `write`; `edit` needs no stamp because its match is against current bytes.
- **Locks are process-local.** They prevent interleaving among Tools using the one Runtime-owned `FileReadState`; another process or an uncoordinated external writer is still outside the lock. Stamp checks detect prior metadata drift, while same-directory atomic replacement prevents partial target contents but is not a portable filesystem compare-and-swap against an external writer racing after the check.
- **Bounded:** at most `_MAX_TRACKED_FILES` (8192) entries; oldest insertion evicted first. A rare eviction only costs a harmless re-read.
