# File-State and Mutation Coordination

The per-session read stamps, per-path mutation locks, and atomic replacement shared by `read` and the file edit Tools (`apply_patch`, `edit`, `write`, which reach them through the change pipeline `_file_changes.py`). Lives in `core/tools/file_state.py`. Also the shared path grammar of `ToolContext.resolve_path` and the link-entry tests (Path resolution, below).

## Overview

A single runtime-owned `FileReadState` registry remembers, per Session, the `(mtime, size)` of every file a Session has read. Full-file replacement (`apply_patch` Add, `write`) uses that stamp as a hard precondition for an existing target; a text change (`apply_patch` Update, `edit`) instead treats its unique match against current bytes as the optimistic precondition and consults the stamp only to report metadata drift after a successful merge. The same object owns ephemeral per-resolved-path locks so in-process mutations of one file serialize without blocking different files. It is constructor-injected into `read`, `apply_patch`, `edit`/`write` (`register_edit_tools`), and the explicit `project` Tool (one instance built in `Runtime`, like `TerminalManager` for `bash` and `terminal`) - not a module singleton. Three non-`read` sources stamp files the model receives: (1) the `@`-mention expansion (`core/chat/file_mentions.py`) stamps an inlined send-time file snapshot - a degraded snapshot (too large / not text / missing) is deliberately not stamped; (2) the System Prompt build stamps every auto-injected prompt file (SOUL, on-disk pinned-memory files, Project auto-load files, workspace `{include:...}`) through `ChatLoop._stamp_prompt_files_read`; (3) the `project` Tool directly stamps every Project auto-load file returned in its result through the prompt renderer's read observer. Stamp design follows OpenCode's (since-removed) `FileTimeService`; it deliberately does not track sibling identities, store read timestamps, or hash content because `(mtime, size)` answers whether the path changed since this Session saw it.

## Interfaces

- `FileReadState.record_read(session_id, resolved)` - stat the file and store `(mtime, size)`. Called when a refused full replacement shows the whole unchanged file in its error (small text files; see `apply_patch.md`), and by the other stamping sources below. A read clears the file's unseen mark (next item).
- `FileReadState.record_change(session_id, resolved, *, merged)` - stamp a file after a change of the Session wrote it or left it as it was (`_file_changes._commit`, for every surviving path of a step). The change is an implicit read of what the Session already knew: with `merged` (the file was `MODIFIED` before the change, so it merged over another writer's content) the file is marked unseen, and an earlier unseen mark stays until a read clears it. A move carries `MODIFIED`/`UNSEEN` from the source to the destination, including a case-only rename: its result does not show the unseen file content. Without the mark, a merge stamped the other writer's content as read, so a later `write` or Add could replace it unseen (Swarm 2026-10-13).
- `FileReadState.stamp(resolved)` / `record_stamp(session_id, resolved, stamp)` - two-phase variant used by `read`: capture `(mtime, size)` *before* reading bytes, record it only *after* the read succeeded.
- `FileReadState.recent_files(session_id, limit)` - the files the Session read or changed, most recent first (a re-read or change moves a file to the front). The edit Tools look there for an `old_string` that is not in the edited file (`edit.md`).
- `FileReadState.check_stale(session_id, resolved) -> StaleReason | None` - `NEVER_READ` (no stamp for this Session+path), `MODIFIED` (current `(mtime, size)` != stamp), `UNSEEN` (stamp current, but marked unseen by `record_change`), or `None` (current). Returns `None` when the file cannot be stat'd (vanished mid-call -> a race, not staleness). Full replacement maps every stale reason to a hard failure (`UNSEEN` with `MODIFIED`'s code and wording, `file_modified_since_read`: the file changed after the Session last read it); a text change ignores `NEVER_READ`, converts `MODIFIED` into a post-success note when its current-content match succeeds (not `UNSEEN`: that note was given when the merge happened), and gives the stale-read note on a match failure for `MODIFIED` and `UNSEEN` alike.
- `FileReadState.lock_path(resolved)` - context manager that serializes mutations of exactly one resolved path. Lock keys and the pipeline's acquisition order use platform `Path` equality and ordering: Windows case aliases share a lock even for a not-yet-existing file, while POSIX case-distinct paths remain distinct. Lock entries count holders plus waiters and disappear when the final user leaves, so the Runtime does not accumulate a permanent path-lock catalog.
- `atomic_write_bytes(resolved, payload, *, mode=None, before_replace=None)` - flush bytes through an exclusive same-directory temporary file (opened `0o666`, so a new file gets the ordinary umask-derived mode, e.g. `0o644` under umask 022, instead of `mkstemp`'s owner-only `0o600`), preserve an existing target's permission bits unless an explicit source mode is supplied for a patch move, install with `os.replace`, and remove the temporary file on every failure before replacement (clearing a copied Windows read-only attribute first; a still-failing removal logs a warning). A target marked read-only on Windows raises non-retryable `ReadOnlyFileError` ("the file is read-only") before or instead of replace retries, because Windows refuses to replace it; POSIX replaces a read-only target and keeps its mode. With a caller-supplied precondition callback, retry only replace-stage Windows errors 5/32/33 up to eight times (5.07s total scheduled delay; test runs and scripts held edited files for several seconds in Swarm Sessions, 2026-09), checking caller preconditions before each attempt. Exhausted errors carry `attempts_made` for the caller's retry metadata and keep the original `errno`/`winerror` on every platform, with one correction: Windows answers a replace of a file that another program holds open without delete sharing with access denied (5), so an exhausted 5 whose target still refuses an open for deletion with a sharing violation reports 32 instead, and `os_error_reason` names the other program rather than a missing permission. No callback means no retry. Preparation, observation and deletion failures never replay a replacement.
- `os_error_reason(error, *, reading=None) -> str` - the Model-facing reason for a filesystem failure: English, lowercase, without the path (`another program is using it`, `permission denied`, `the disk is full`). Checks `ReadOnlyFileError`, then known Windows codes, then known `errno` values, then `os.strerror`. The raw Windows `strerror` is localized and repeats the absolute path, so `read` and the file edit Tools never show it. `reading` names the file a failed open or read was for: Python reports a Windows sharing or lock violation there as a bare `PermissionError` (errno 13, no `winerror`), so a held file read as `permission denied` until the reason checked `_held_open_elsewhere` (review 2026-10-22). `read` and the change pipeline pass it; the pipeline's snapshot also gives a failed read of an opened file its path, which Python leaves out (`Could not read permission denied.`). Tests: `test_read.py::test_a_read_time_filesystem_error_names_the_reason`, `test_apply_patch_files.py::test_a_file_another_program_holds_is_named_with_that_reason`.
- `FILE_STATE_GUARD_ENABLED` (module constant, default `True`) - process-wide read-stamp off switch; when `False`, `record_read` no-ops and `check_stale` returns `None`, while path locks and atomic replacement remain active.

## Constraints & Gotchas

- The file edit Tools receive the same Runtime-owned registry. The shared pipeline locks all resolved paths of a call in deterministic order, plans steps against current bytes (`apply_patch` each hunk/file operation independently; `edit` its canonical one-file call as one step written once, skipping its failed edits, or its explicit multi-file dialect one item at a time in input order), rechecks writes, and stamps successful surviving files including no-ops (`record_change`). Text changes use current-content optimistic matching; multi-file failure and byte recheck semantics belong in `apply_patch.md`, and the accepted per-item target dialect in `edit.md`.

- **Stamp key is `(session_id, str(resolved))`** - per Session, by resolved absolute path. Different Sessions (including Sub-agents, which get their own Session) never share read history. State is in-memory only, lost on restart (which forces a re-read only for a later full-file overwrite).
- **New files, empty files and identical replacements are exempt at the call site.** Add and `write` run `check_stale` only when they would change existing bytes that are not empty or whitespace-only (a BOM alone counts as empty); an `edit` with an empty `old_string` only creates or fills such a file; an `apply_patch` Update or `edit` replacement operates on an existing file but never treats `NEVER_READ` as a conflict. `check_stale` itself reports `NEVER_READ` for any unstamped path regardless of existence - callers own operation-specific policy.
- **Comparison is not-equal on `(mtime, size)`**, not strictly-newer. `size` is a free second signal that catches some same-`mtime`-tick changes (coarse filesystem resolution). A same-length change within the same mtime tick is the accepted blind spot - no content hashing closes it by design.
- **Stamp before the byte read** (in `read`): if an external write lands in the window after the stamp, the stamp stays older than the new content, so a later full replacement errs toward a harmless re-read while Update can disclose that it merged against newer bytes. The captured stamp is recorded only for a successful read.
- **Bash writes are not stamped.** A file changed via `bash` (e.g. `sed -i`) is later seen as `MODIFIED`; full replacement forces a re-read, while Update applies only through its current-content match and reports the drift after success. vBot deliberately does **not** parse bash commands to re-stamp touched files.
- **Partial reads count as full reads** - `record_read` ignores offset/limit/truncation, so a truncated read of a large file still satisfies the guard for a later full replacement; Update needs no stamp because its match is against current bytes.
- **Locks are process-local.** They prevent interleaving among Tools using the one Runtime-owned `FileReadState`; another process or an uncoordinated external writer is still outside the lock. Stamp checks detect prior metadata drift, while same-directory atomic replacement prevents partial target contents but is not a portable filesystem compare-and-swap against an external writer racing after the check.
- **Bounded:** at most `_MAX_TRACKED_FILES` (8192) entries; oldest insertion evicted first. A rare eviction only costs a harmless re-read.

## Path resolution

`ToolContext.resolve_path` follows host path grammar without filesystem-dependent fallback. Windows double quotes may wrap a path because they cannot be literal filename characters; single quotes remain literal. POSIX quotes and backslashes remain literal even when a different unquoted/slash-separated file exists. Path objects remain literal. A path containing NUL raises `ToolContractError` (`<tool> was not run: the path ... contains a NUL character ...`) before any filesystem access, whether or not the host's `Path.resolve` would raise; every caller resolves before its effect, and callers that catch `ValueError` or `ToolContractError` pass the message through (`test_read.py::test_read_refuses_invalid_arguments_before_reading`). A `file:` URL names its local path (`core.utils.paths.file_url_path`; on POSIX only with `/` after `file:`, since `file:notes.txt` is a legal name there). `UnusablePathError` (a `ToolContractError`) refuses, also before any access, a path that would lead elsewhere than it names: a `file:` URL of another computer (POSIX), on Windows a `:` in a folder name, a `:` in the final name for every access but `read` (which opens that alternate data stream), a drive letter without `/` (`D:notes.txt`, the server process's current folder on that drive), and a result that is still not absolute after resolving (`ntpath.realpath` falls back to drive-relative paths). Before, `file:///C:/x` and colon folder names reached a file below the server process's working directory while results named the intended one (review 2026-10-22). The change pipeline (`_patch_entries._resolve`) reports its `reason` as that operation's `invalid_path` failure (`test_tools_execution.py::test_tool_paths_take_file_urls_and_refuse_names_that_lead_elsewhere`, `test_edit_tools.py::test_failed_changes_change_nothing_and_say_what_to_send`). Scope, read-state, and mutation checks still use the resolved target. The keyword `access` is required: `read`, `write` and `start_dir` check the resolved path against `ToolContext.permissions` and raise `PermissionDenied` (`permission_denied`, not retryable) before any access; `display` (paths shown, never accessed) is never checked. A full-access Run skips the check without I/O (`test_read.py::test_permission_rules_refuse_a_read_before_the_file_is_touched`). `follow_final_link=False` resolves only the parent, for operations on a link entry itself (apply_patch Delete/Move); `is_link_entry` (a path) and `is_link_status` (unfollowed metadata, such as search traversal's `DirEntry` stat) in `_tool_context.py` are the shared symlink-or-junction test (`Path.is_symlink` misses junctions; reparse tags exist only on Windows, so elsewhere only symlinks count).

Under Permission Rules a Run learns nothing about a path its rules refuse to read: every path a Tool stats, lists, suggests or names for it is checked first, and a full-access Run skips each check without I/O.
- Missing-path suggestions (`core/tools/_path_suggestions.py`): every function takes the keyword `permissions`. No candidate is statted and no folder listed unless its parent is readable, and refused names are never suggested, only named as refused when they are close entries of a readable folder (`refused_note`, `tools/read.md` -> Conventions); when the missing path's parent is unreadable, `missing_file_message` answers only `File not found: <path>.`. Callers: `read`, the change pipeline, `search_files`, `channel_send`, image inputs, the shell workdir messages; `_shell_hint_python.py` passes `UNRESTRICTED`, since shell hints get no boundary yet.
- Listings filter through `PermissionBoundary.readable_entries` (`permissions/paths.md` -> Patterns and subtrees); the omission notes that name what they leave out live in `core/tools/_refused_notes.py`.
- The change pipeline carries `ChangeBatch.permissions`. Every file the Run may change it may also read (`permissions.md` -> Requirements), so failures show their usual excerpts; the recent-files hint leaves out files the rules now refuse to read. A Move whose destination is refused touches nothing. `edit` resolves its target with `write` access.
- Coverage: `test_read.py::test_permission_rules_name_refused_entries_in_listings_and_suggestions`, `test_file_changes_permissions.py`, and the permission cases in `test_search_files.py`, `test_image_inputs.py`, `test_channel_send_files.py`, `test_media_generation.py` and `test_project.py`.

## Agent-facing text

The refusals of `resolve_path` (`core/tools/_tool_context.py`), shown by every Tool that resolves a path; the change pipeline shows the reason after `Cannot use path <path>: `.

| Text | Reason |
|---|---|
| `<tool> was not run: cannot use path "<path>": ` | Says nothing ran and quotes the path as sent, so a trailing space or a URL stays visible (F4). |
| `Windows file and folder names cannot contain ":". Use another character, such as "-"` | A time stamp such as `meeting 10:30.md` failed as `invalid argument` after creating its folder, and a `:` in a folder name reached a file below the server's working directory (review 2026-10-22). Names the forbidden character and a replacement, so the Agent renames instead of resending (F5). |
| `"D:" needs "/" after it. Send "D:/notes.txt" for that path on drive D:, or "notes.txt" for one in the working directory` | A drive letter without `/` names that drive's current folder of the server process. The two calls cover both readings without guessing one (F3). |
| `it names a file on another computer. Send the path of a file on this computer` | POSIX cannot open a `file://host/` URL; Windows reads it as a UNC path instead (F5). |
| `it does not lead to a complete path on this computer. Send an absolute path, or one relative to the working directory` | The rare remaining drive-relative result; names the two path forms that resolve (F5). |
