# Music Generation

Task-gated reference for the `music_generation` Task Model and OpenRouter Music execution path.

## Boundary

`core/model_tasks/music.py` owns binding resolution, image-input compatibility, local reference-image loading, provider-error normalization, and caller-owned artifact persistence. `core/model_tasks/music_providers.py` owns the OpenRouter Chat Completions audio-stream wire and Base64 audio assembly. `core/tools/media_generation.py` owns only the Agent Tool schema, effective-cwd path resolution, caller-owned default directory, and result projection.

## Model Classification

OpenRouter exposes Music and conversational Audio Models through the same `output_modalities=audio` filter and currently supplies no first-class Music task tag. The OpenRouter normalizer therefore assigns `music_generation` only to the provider's distinct Music capability signature `text+image->text+audio` with exact text/image inputs and text/audio outputs. Generic Audio Models such as GPT Audio remain `audio_generation` only. This rule is deliberately provider-specific and conservative; do not derive Music globally from audio output.

## Execution Contract

Music generation uses `POST /chat/completions` with text/audio output modalities and streaming enabled. Optional local reference images become Base64 data URLs only when the configured Model advertises image input. SSE `delta.audio.data` fragments are concatenated and decoded after the `[DONE]` marker; absence or malformed audio fails closed. Lyria output is persisted as MP3 unless the provider later supplies a different authoritative media type. Generated bytes are written exclusively under the caller-selected directory, defaulting to `<Workspace>/music-gen/` for Identity/Rooted calls and `<effective cwd>/music-gen/` for Project Agent calls.

In-band error payloads fail generation even after valid audio fragments have arrived; a later `[DONE]` cannot turn those partial bytes into a successful artifact. The client never automatically replays a Music generation request. Music retains its task HTTP read timeout (600 seconds of inactivity); Chat's read-unbounded stream helper is not applicable because this client has no Chat streaming clocks.

Explicit non-`stop` finish outcomes also reject partial audio, as do native `network_error` / `server_error` outcomes concealed by a normalized `stop`. Repeated `stop` accounting frames are harmless; the client still requires `[DONE]` and valid non-empty Base64 audio. Synthetic regression coverage verifies local handling, not live Music compatibility. OpenRouter's [streaming reference](https://openrouter.ai/docs/api_reference/streaming) and [API overview](https://openrouter.ai/docs/api_reference/overview) describe the terminal fields (read 2026-09-22).

Non-null `audio.data` values must be strings; malformed fragments cannot be dropped to turn earlier partial audio into a successful artifact. Base64 validation applies to the complete concatenation, preserving fragment boundaries inside encoded groups.

The stream POST records one durable `music_generation` attempt. Reported SSE `usage` fields update its latest counters; repeated cumulative reports are not added. Failure or cancellation retains any telemetry already received, and artifact persistence is independent of that record. Tool callers pass their internal execution scope. A stream without Usage remains an unknown-cost call, with no inference from generated audio length. Coverage: `test_task_usage.py` and the stream outcome tests.
