# Music Generation

Task-gated reference for the `music_generation` Task Model and its OpenRouter and Google execution paths.

## Boundary

`core/model_tasks/music.py` owns binding resolution, image-input compatibility, local reference-image loading, provider-error normalization, and caller-owned artifact persistence. `core/model_tasks/music_providers.py` owns both wires behind `ProviderMusicClient`, chosen by the Provider's adapter: the OpenRouter Chat Completions audio stream with Base64 audio assembly, and Google's native `generateContent` (see Google route). `MUSIC_PROVIDERS` in `music.py` lists the Providers the service accepts as Music targets. `core/tools/media_generation.py` owns only the Agent Tool schema, effective-cwd path resolution, caller-owned default directory, and result projection.

A Connection or Account that disappears during client preparation is a `MusicConfigurationError`, preserving the Tool's unavailable-Model guidance before any generation request is sent.

## Model Classification

OpenRouter exposes Music and conversational Audio Models through the same `output_modalities=audio` filter and currently supplies no first-class Music task tag. The OpenRouter normalizer therefore assigns `music_generation` only to the provider's distinct Music capability signature `text+image->text+audio` with exact text/image inputs and text/audio outputs. Generic Audio Models such as GPT Audio remain `audio_generation` only. This rule is deliberately provider-specific and conservative; do not derive Music globally from audio output. Google's discovery assigns `music_generation` to the `lyria-3*` ids (`providers/google.md`); `lyria-realtime-exp` is a bidi streaming API outside this task.

## Execution Contract

OpenRouter Music generation uses `POST /chat/completions` with text/audio output modalities and streaming enabled. Optional local reference images become Base64 data URLs only when the configured Model advertises image input. SSE `delta.audio.data` fragments are concatenated and decoded after the `[DONE]` marker; absence or malformed audio fails closed. `delta.audio.transcript` and `delta.content` text are collected too and returned as `MusicArtifact.transcript`/`text` (the Tool returns them as `transcript`/`model_reply` when non-empty). `source_images` for a Model without image input raises `MusicOptionError` (`invalid_arguments`) before any request. The media type is sniffed from the decoded bytes (fallback `audio/mpeg`). Empty `temperature`, `top_p` and `seed` options are omitted. `generate_artifact` checks the output folder before the request (`OutputDirectoryError`) and writes off the Event Loop (`OutputWriteError` on failure). Generated bytes are written exclusively under the caller-selected directory, defaulting to `<Workspace>/music-gen/` for Identity Agent calls (also in a Working Project) and `<effective cwd>/music-gen/` for Project Agent calls.

In-band error payloads fail generation even after valid audio fragments have arrived; a later `[DONE]` cannot turn those partial bytes into a successful artifact. The client never automatically replays a Music generation request (the one exception is the Google 503 below). Configured Task Model chains may retry or switch only after a provably unaccepted request: connection establishment failure, explicit rate limit, or credential/configuration failure. Stream establishment uses the shared non-idempotent task transport/status classifiers; read/write failures before response headers and unverified 5xx responses are already ambiguous and stop the chain.

A refusal is a known outcome: a 4xx refusal body, a content-filter `finish_reason` (`content_filter` or GLM's `sensitive`, the set Chat Completions shares: `OPENAI_CONTENT_FILTER_FINISH_REASONS`), or a stream that answers with text but no audio raises `ProviderContentRefusedError` (the text, cut to 500 characters, is the reason), reported as `MusicRefusedError` (`generation_refused`). Once the Provider accepted the stream, every other failure (broken stream, missing `[DONE]`, no or undecodable audio) is `ProviderOutcomeUnknownError`, reported as `MusicOutcomeUnknownError`, because a billed track may already exist. Music retains its task HTTP read timeout (600 seconds of inactivity); Chat's read-unbounded stream helper is not applicable because this client has no Chat streaming clocks.

Explicit non-`stop` finish outcomes also reject partial audio, as do native `network_error` / `server_error` outcomes concealed by a normalized `stop`. Repeated `stop` accounting frames are harmless; the client still requires `[DONE]` and valid non-empty Base64 audio. Synthetic regression coverage verifies local handling, not live Music compatibility. OpenRouter's [streaming reference](https://openrouter.ai/docs/api_reference/streaming) and [API overview](https://openrouter.ai/docs/api_reference/overview) describe the terminal fields (read 2026-09-22).

Non-null `audio.data` values must be strings; malformed fragments cannot be dropped to turn earlier partial audio into a successful artifact. Base64 validation applies to the complete concatenation, preserving fragment boundaries inside encoded groups.

The stream POST records one durable `music_generation` attempt. Reported SSE `usage` fields update its latest counters; repeated cumulative reports are not added. The attempt settles only after audio decoding, so a refusal or unusable result after `[DONE]` records failure. Failure or cancellation retains any telemetry already received, and artifact persistence is independent of that record. Tool callers pass their internal execution scope. A stream without Usage remains an unknown-cost call, with no inference from generated audio length. Coverage: `test_task_usage.py` and the stream outcome tests.

## Google route

Google Lyria Models (`lyria-3.5`, `lyria-3-pro-preview`, `lyria-3-clip-preview`) run through one non-streamed `POST /models/{model}:generateContent`; Google documents no streaming for them, and the answer carries the whole track. The request is a single user turn: the prompt as a text part and each reference image as an `inlineData` part (Google allows up to 10 images and enforces that limit itself). Lyria has no sampling controls; duration, vocals and structure are steered by the prompt only (Clip always renders 30 seconds). Without a format choice the request sends no `generationConfig` and Google returns MP3. The `response_format` option (`mp3`/`wav`) renders only from the Model's `task_options` fact, which Google's catalog normalizer sets for Lyria 3.5 alone, the only Model documented with WAV; a choice sends `generationConfig.responseModalities: [AUDIO, TEXT]` and `responseFormat.audio.mimeType` (`AUDIO_MP3`/`AUDIO_WAV`). `extra_options` adds top-level request fields such as `safetySettings`.

The answer's non-thought `inlineData` audio parts are the track (media type sniffed from the bytes, else the declared `mimeType`); its text parts, lyrics or a song-structure description, are joined as `MusicGenerationResult.text` (the Tool's `model_reply`); `transcript` stays empty. A `promptFeedback.blockReason`, a content-filter `finishReason` (the shared Gemini set, reason from the Model's text or `finishMessage`) or a text-only answer with `STOP` is a refusal. A missing or unexpected finish, a missing candidate, malformed or undecodable audio raise inside `post_and_parse`, whose non-replayable policy reports them as `ProviderOutcomeUnknownError`. An empty `finishReason` does not confirm completion ([GenerateContent Candidate](https://aistudio.google.com/api-reference/generate-content#Resource:Candidate)). HTTP statuses classify through the Google Adapter's task hook: 429 with a zero or daily quota is a non-retryable `ProviderError`, other 429s are rate limits. 503 is a verified-unprocessed status (Google documents it as overload to retry, as on the image route), so the client retries it; every other 5xx and transport failure after sending stays ambiguous. `usageMetadata` is projected through the shared Gemini usage normalizer into the attempt's Usage.

Not verified live: the free tier has no Lyria quota (HTTP 429 `limit: 0` for all three Models on 2026-11-17, and Google's pricing lists Lyria as paid only). The [current music generation guide](https://aistudio.google.com/docs/music-generation) shows the Interactions API. The current vBot route uses the `generateContent` contract, with mocked response coverage.
