# Live voice operator

Read for the Live Tools (what the Live Agents and OpenAI's hosted backend model can do in the app) and Run announcements during a call. Call lifecycle, owner socket, the Live Agents' Sessions, handed-on requests and trust rules: `model_tasks/live.md`.

## Ownership

The Live Tool definitions and their registration are core (`core/tools/live.py`: `live_tool_definitions`, `vbot_request_definition`, `register_live_tools`, `LiveToolHost`, `LiveToolHosts`, the Tool name constants and `LIVE_READ_ONLY_TOOLS`); the operator that runs them is the server host of a call (`server/live/`). `_arguments.py` prepares each call (`prepare_live_call`). `_tools.py` (`LiveToolExecutor`) runs one call's Tool executions and dispatches: `overview`, `open` and `end_call` itself, the Session Tools to `_sessions.py` (`LiveSessions`: start, send, read, stop, Session lines), coding Terminals to `_terminals.py` (`LiveTerminals`: start, typing, keys, reading), and the `manage_terminals` layout actions to `_terminal_layout.py` (`LiveTerminalLayout`: groups, order, maximize, close). Shared: `_targets.py` (`LiveRefs`, app catalogs, target resolution), `_programs.py` (`CODING_PROGRAMS`: Codex and Claude Code commands, readiness markers, startup questions, interrupt key), `_context.py` (RPC and UI request seams, the reported app context, the per-call Tool lock, shared failure texts). `_feed.py` (`LiveRunFeed`) announces Runs.

## Live Tools

- Registration (`register_live_tools`, Runtime bootstrap): the nine Live Tools and `vbot_request` are ToolRegistry Tools of family `live` (`Live voice` in the Tool catalog), with `requires_opt_in` and the constraint `live_call`, so only the Live Agents can have them (`tools.md` -> Policy resolution, `agent.md` -> Live Agents). They keep an open input schema and validate their own arguments without coercion (`open_input_schema`, `handler_validates_arguments`, `coerce_arguments=False`), so the preparation below sees the arguments as the Model wrote them. `vbot_request` is not `catalog_visible`: no Agent selects it; a call adds it to the voice Agent's Run (`model_tasks/live.md` -> Live Agents and Sessions). A handler finds the call by the calling Session (`LiveToolHosts.get(session_id)`); a Session no running call bound gets the failure `no_live_call` and nothing happens. The Agent's Session stores each call and result like any Tool call, and the chat shows a Live Tool row by its target, Agent, program or view, else the quoted task or text.
- Definitions: `live_tool_definitions()` and `vbot_request_definition()` in `core/tools/live.py`, canonical and rendered non-strict by the Adapter; descriptions, instructions, and failure texts are runtime Agent-facing text. The instructions list no Tools: each Model learns its Tools from these definitions alone. `overview` and `read_output` only look (`LIVE_READ_ONLY_TOOLS`); every other Tool may change something.
- Results: a Tool result envelope whose success data is one plain-text `content` (`live_success`); `ok` means the call's whole effect happened. Folder paths vBot writes into results (Project folders, Terminal working directories) use `/` separators (`core.utils.paths.model_path`); a failure (`live_failure`) says what was wrong and names the next valid call with example arguments. The voice model reads results as plain text (`live_result_text`); the Live backend Agent reads them like any Tool result in its Chat Run. Effects are never replayed; a failure after a possible effect says so (`UNCERTAIN_DELIVERY`: do not send it again); an unexpected failure of a read-only Tool says nothing changed and allows one more try.
- Preparation (`prepare_live_call`, every caller): the Tool dispatch already resolved the name (wrapper prefixes such as `functions.` and other harnesses' Tool names, `tools.md` -> Model Tool names); JSON-text arguments, other harnesses' field names (`prompt`, `session_id`, `workdir` ...), program, key, and view spellings become one canonical call, validated by the shared Tool contract (unknown fields are rejected). Contract compilation is cached. Payload fields (`task`, `text`, `name`, under any of their spellings) keep their text unchanged; only a missing or blank value leaves them out. Lookup and choice fields (`agent`, `target`, `folder`, `project`, `program`, `key`, `view`, `action`, `count`) also treat placeholder words (`none`, `null`, `n/a` ..., `core/tools/call_syntax.py`) and punctuation-only text as omitted.
- Refs and targets: `LiveRefs` (one per call, owned by its `LiveToolExecutor`) assigns the refs, stable for the call, and keeps a label per ref for later requests (`known_refs`); Run announcements use the same table. A ref (tolerant spellings `S2`, `s-2`, `#s2`) decides; an unknown ref fails and asks for `overview`. Otherwise every kind the Tool accepts contributes its matches: its exact ids (Session id or `address/session_id`, Terminal id, group id, Agent address, Project id) when any match, else its names (Terminal, group, Agent name/address/bare id, Project name/id, compared by `spelling`; Sessions have no names). Exactly one match across all accepted kinds resolves; several are ambiguous even across kinds (a Terminal and an Agent called "coder"), and the failure lists each candidate with its ref or id; for several kinds it adds how to pick one (conversation targets: `overview` with the Agent's id for its Session refs; `open`: the same target with the view of the kind). With a target, `open`'s `view` limits the kinds: `chat` Session or Agent, `terminals` Terminal or group, `agents` Agent (its page), `projects` Project. An Agent name as a Session target must leave one clear Session (working, started or addressed by Live in this call, or active since the call started; `stop` only working ones; `read_output` falls back to the latest); otherwise the failure lists the candidates and asks for a ref. It selects among the Agent's Sessions that no Cron job or Channel started (`session.list` with `include_cron`/`include_channels` false); Cron and Channel Sessions count only when the Agent has no other Session, are marked "Cron or Channel Session" in `overview` for that Agent, and a failure says when one was skipped. `open` with an Agent name shows its latest such Session. Scoped exception to `PROJECT.md` -> Object IDs ("no display aliases or abbreviated incoming ids"): refs exist only inside Live Tool calls; ids are never matched by prefix.
- Sessions (`_sessions.py`): `start_agent_session` starts top-level Sessions (never subagents) at an identity Agent, or with `project` at that Project's team Agent, by sending the task through `chat.stream` with `new_session: {}` and `input_origin: live_voice` (`count` 1-10, text <= 16,000 chars): the server creates each Session together with its task's Run, so a refused task leaves no empty Session (`server.md` -> Chat submission target). A task starting with `/` runs as a slash command, which may start no Session; that start fails with `start_failed` and the Tool text `The task ran as a slash command and started no Session. To start a Session with it, send the task without the leading slash.` A partial start reports the started refs and retries nothing. `send_message` to a Session uses the same send (a working Session queues it). `read_output` returns the newest user, assistant, and error texts from `chat.history` (20 messages, 8,000 chars shared, cut at a word) as quoted lines. `stop` cancels the active Run (`chat.cancel`).
- `overview` lists identity Agents, the selected Project's team, Projects with folders, running then recently finished Sessions (finished since the call started or touched by Live; 12 shown) with the end of the final message through `chat.run_result` (160 chars; a final message ending in `?` reads "waiting for an answer", a heuristic, not a Run state), and Terminals (an idle or working coding Terminal whose program no longer runs, by `terminal.programs`, reads "Codex is not running; only the command line is open"; the overview still lists the Terminals when that check fails); with `agent`, that Agent's Sessions. Agents and Projects come from `agent.list` / `project.list`, the selected Project's team from `project.show` (which rescans the Project, so a call reuses each team for 60 s), and the view and selection from the owner's latest context report (`overview` names the Session shown in the chat). Catalog loads of one execution run concurrently and at most once.
- Coding Terminals, security contract (`_terminals.py`): a task never becomes part of a command line (Windows `.cmd` shims let quotes, `&`, `%` in free text escape into the shell). `start_coding_terminal` runs `terminal.start` with the program's command only (`codex` | `claude`), `count` 1-10, in a Project's folder (name match), an existing absolute folder, or the selected Project's folder, inside an editable group named after the program (created when missing). It waits (poll 0.05 s, <= 25 s, screen stable 0.8 s) until the program shows its own input line, also without a task (a start succeeds only when the program is ready in every Terminal; a startup question, a timeout, or a program that did not start make it `partial`). When the shell prompt is the last line again below the line that ran the program command, the program did not start (`program_start_failure`, e.g. `codex` not found after a broken npm update): the result quotes the shell output in between (<= 200 chars) and types nothing. With a task it types the task as bracketed paste (line breaks flattened when paste is off; control characters rejected) guarded by `expected_screen_revision` (up to 3 attempts on a stale screen), then sends Enter in a separate write once the program's input line shows the text (its first 12 characters, or a `[Pasted` placeholder; re-read every 0.05 s, for at most 1.5 s). It never types while the shell prompt, a menu, or a startup question (folder trust, Codex update) shows; it reports the question and names the `manage_terminals` key calls and the following `send_message`. A start with a task succeeds only when the task was sent in every Terminal; otherwise the result is the failure `partial`, whose message names the started Terminals and what happened to the task in each. A Terminal start that fails partway reports the started refs; nothing is retried or typed. The markers and the CLI versions they were observed with are documented in `server/live/_programs.py`; update them when a CLI changes its screens.
- Fail-closed program check: every Live write to a coding Terminal - paste, Enter, and `manage_terminals`/`stop` keys - passes `expected_program` (`codex` | `claude`) to `terminal.input`, so the Terminal manager writes it only while that program runs in the Terminal's process tree (see `tools/terminal.md`); a refusal reports that the program no longer runs and nothing reached the shell (`program_not_running` for keys). The screen rules are the second line: the input line is the last line starting with the program's arrow (`›` Codex, `❯` Claude Code) and must not be a numbered menu answer or have numbered answers below it; the shell prompt as the last line covers PowerShell, cmd, `user@host` bash/zsh/fish prompts, and prompt themes ending in `❯` (starship, oh-my-posh).
- Startup questions are answered by the Agent with `manage_terminals` keys; Enter on a screen showing a known question is pressed only while the answer Live's guidance names (`CliPrompt.choice`: Codex "Yes, continue" / "Skip", Claude Code "Yes, I trust this folder") is the selected one; otherwise `answer_not_selected` names the selected answer and the next step, and other answers are left to the user in the app.
- `send_message`, `read_output`, `stop`, and `manage_terminals` `key` work only on coding Terminals: messages are typed like tasks, screens return the last 8,000 chars, `stop` presses the program's interrupt key (Escape). Operator reads preserve Agent bindings.
- `open` navigates through the owner (`open` UI request): a Session in the chat, an Agent's latest Session or with `view: agents` its page, a Project's page (a team Agent has no Agent page, so its Project page opens), or a view (also `calendar`, `cron`, `skills`, `settings`, `statistics`, `logs`, which show no single thing and take no target: `invalid_view`); Terminals and groups show through `terminal_view`. `manage_terminals` actions (`_terminal_layout.py` except `key`): maximize, restore, key, close (stop then forget like the UI close action; failures report confirmed or uncertain state and never replay), reorder, create/rename/delete group (only `user` / `agent` groups are editable; delete stops the group's Terminals). close and delete_group refuse Terminals in state `working` as `terminal_working` (naming the call with `confirm: true` to repeat once the user agreed), since closing breaks off their work (the 2026-10-01 call closed a Terminal mid Codex update). A completed change stays reported when the following layout refresh fails.
- UI requests (shapes in the `server/live/_tools.py` docstring; the page validates them in `lib/liveUiRequests.js`): `open` (any of the views above with no target, or `chat` | `agents` | `projects` with exactly one of `agent_id` + `session_id` (chat), `agent_id` (agents, identity Agents only), `project_id` (projects); `false` / `{applied: false}` when the app did not switch, reported as `navigation_not_applied`), `terminal_view` ops `show` / `maximize` / `show_group` / `restore` / `refresh`. Other actions answer `unsupported_action`. The owner answers through `live.ui_result` with exactly one of `result` or `error`.
- Activity: each executed Live Tool call (not calls rejected before running) reaches the owner as `{type: "action", tool, arguments (string values <= 200 chars), ok, result (the text the Model read, <= 2000 chars), links}`; `links` name what the known refs in the result point to, in order of first mention (<= 12): `{ref, kind: "session", agent_id, session_id, label}` or `{ref, kind: "terminal", terminal_id, label}` (`action_update` in `_tools.py`, `LiveRefs.link`). `action` updates are disposable when the buffer is full.
- Execution: operations dispatch the registered RPC handlers in-process, so validation and `/ws` publication match other accessors. The executor runs one call's Tool executions one at a time (`LiveContext.exclusive`). Only `start_coding_terminal` lets others run once its Terminals are started (`let_others_run`), while it waits for the programs and types (<= 25 s per Terminal); until the program is ready and any task typed, `send_message`, `stop`, and `manage_terminals` `key` on those Terminals fail as `terminal_busy` without writing (`read_output`, `overview`, layout, and `close` still work). After stop or replacement, multi-step operations stop before further effects (`voice_stopped`) and report confirmed partial results.

## Run announcements

- `LiveRunFeed` follows the server event bus from the call's start and announces completed/failed/interrupted Runs once (cancelled Runs stay silent). It skips Runs that finished before the call and Runs excluded from Agent activity. It loads each excerpt through `chat.run_result` for the exact scoped Run, so newer replies in the same Session never replace it (see `chat.md`). After a bus lag it resubscribes; Runs that left retention stay silent.
- The call dedups announcements, ignores them once closing, stores each as a note in the voice Session, passes it on in the next backend request's context note (`model_tasks/live.md` -> Handed-on requests), and speaks them once `live` (up to 5 that arrived while connecting are spoken when the call goes live). Text: `vBot update: {"run", "agent", "session" (the Session's ref), "result_excerpt" (<= 600 chars), "excerpt_truncated"}`. Finished Runs are announced briefly; Agent questions are relayed, summaries only on request. Terminal quietness never proves a coding task finished. Wires that announce like user input get no excerpt (`model_tasks/live.md` -> Instructions and trust).

## Agent-facing text

Reasons for the Tool-level texts of `core/tools/live.py`. The other Live Tool descriptions and failure texts kept their wording from the former `server/live/_brief.py`; only the Tool names changed.

| Text | Reason |
|---|---|
| Tool names `read_output`, `manage_terminals` | Registry names are global: `read` (files) and `terminal` (the Terminal Tool) name other Tools, and a Model with both kinds would confuse them. |
| `vbot_request`: `Hand one request to vBot, which operates the app for the user: starting Agents or coding agents on tasks, sending messages and answers, reading or summarizing Sessions and Terminals, stopping work, and showing things in the app.` | The voice model must know which requests to hand on; the list names what the backend can do. |
| `vbot_request`: `The result arrives later as this Tool's output and ends with what vBot changed for the request; keep talking with the user meanwhile and do not claim success before it arrives. Requests run one after another.` | Voice models claimed starts no Tool call confirmed (2026-10-01 call); the effects line is the only confirmation. |
| `vbot_request` `request`: `The user's request, passed on faithfully with exact names and wording.` | The backend acts only on what is handed on; paraphrased names fail target resolution. |
| `end_call`: `Say a short goodbye before you call it: the call ends as soon as that goodbye has played, and nothing said after the call is heard.` | vBot closes the call as soon as the voice model's speech has played, with no fixed delay (user decision 2026-10-07); a goodbye spoken after the call would be cut off. |
| `_NO_CALL`: `This Tool works only during a Live voice call, and none is running for this Session. Nothing was done.` | A Live Agent's Session can outlive its call (a Run still running, a late Tool call); the result must not read like an effect, and says why. |
