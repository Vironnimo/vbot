# Video Generation

Task-gated reference for the `video_generation` Task Model and its OpenRouter and Google execution paths.

## Boundary

`core/model_tasks/video.py` owns binding resolution, exact configured-Model capability validation, local frame-image loading, provider-error normalization, and caller-owned artifact persistence. `core/model_tasks/video_providers.py` owns both wires behind one job contract (submit once, poll, collect, never resubmit): OpenRouter's asynchronous `POST /videos` -> same-origin job polling -> authenticated content download, and Google's Interactions API (-> Google route). `VIDEO_PROVIDERS` (`video.py`) lists the Providers with a route. `core/tools/media_generation.py` owns only the Agent Tool schema, effective-cwd path resolution, caller-owned default directory, and result projection.

A Connection or Account that disappears during client preparation is a `VideoConfigurationError`, preserving the Tool's unavailable-Model guidance before any create request is sent.

## Discovery and Options

OpenRouter's ordinary `output_modalities=video` catalog supplies the coarse `video_generation` task tag. The dedicated `/videos/models` catalog is an independent fail-soft enrichment source for exact resolutions, aspect ratios, sizes, durations, frame-image positions, audio generation, seed support, and passthrough keys. Dedicated-catalog-only entries become minimal non-chat Models. Targets need a published `duration` choice and exclude router Models. `VideoProfile` decides the per-call Tool fields and validates their values (`model_tasks/media-profiles.md`); the service rejects unsupported values with the offered choices (`VideoOptionError`, `invalid_arguments`). A requested aspect ratio or resolution drops the Settings `size`. Google publishes no catalog parameters; `_video_capabilities` (`core/providers/google.py`) writes the Omni facts (-> Google route).

## Execution Contract

Video creation is non-idempotent and uses the shared outcome-unknown retry policy. The initial response must yield a usable job id inside that policy's parser boundary; a success response without one remains an unknown outcome with its operation key and is never resubmitted automatically. The returned `polling_url` and unsigned storage URLs are never followed; vBot takes only the opaque job id, URL-encodes it, and polls/downloads through the configured OpenRouter base URL so credentials cannot be redirected off-origin. Terminal failed, cancelled, or expired jobs fail; a failure reason that names a content refusal raises `ProviderContentRefusedError`, which the service reports as `VideoRefusedError` (`generation_refused`, reason kept). Completed jobs download index `0`; the media type is sniffed from the bytes. `generate_artifact` checks the output folder before the create request (`OutputDirectoryError`) and writes off the Event Loop (`OutputWriteError` on failure). Generated bytes are written exclusively under the caller-selected directory, defaulting to `<Workspace>/video-gen/` for Identity Agent calls (also in a Working Project) and `<effective cwd>/video-gen/` for Project Agent calls.

Polling checks the job every 10 seconds (`VIDEO_POLL_INTERVAL_SECONDS`) for at most 20 minutes; the deadline includes poll intervals, active status requests and their retry waits. A transient status failure keeps polling until the deadline and is named in the timeout reason. Expiry, a non-retryable status failure, and a failed download of the finished video raise `VideoJobUnfinishedError` with the job id; the service reports it as `VideoOutcomeUnknownError(job_id=...)`. A Session Tool call whose job was recorded returns a pending result. Without a durable receipt the Tool gives the Agent the job id for the user. None of them submits another generation. The completed-content download has its own request timeout.

OpenRouter has no endpoint to cancel or delete a job (only submit, poll and download), so a submitted job runs and is billed whether or not vBot still waits. Caller cancellation remains cancellation: `generate` raises `CancelledError` at once. A cancel while the job is polled hands the running poll (same deadline, same Usage observer) to the `VideoService`, which follows it in a `video-job-cost` task until the job ends: a completed status records its reported cost on the create call's Usage; the video is not downloaded. When the cost cannot be recorded (deadline, a non-retryable status failure, or Runtime shutdown, whose `VideoService.aclose` stops every followed job after the Runs drained), one WARNING names the job id and Model so the charge can be traced. A cancel during the create request or the download follows nothing: the create attempt records itself as cancelled, and a completed poll has already recorded the cost. A restart ends cost-only watchers. Collection receipts for Session work survive it.

Non-null job statuses must be strings before polling logic inspects them. Malformed initial statuses retain outcome-unknown classification; malformed poll statuses fail as ordinary non-retryable Provider errors without resubmission. Missing/null statuses and unknown string values remain pending rather than claiming an unverified terminal meaning.

Durable `video_generation` accounting starts at each create POST attempt. Poll responses may enrich the accepted create call with reported Usage; status and content GETs never add Model calls. Consumption survives a failed download or artifact write. Tool callers pass their internal execution scope; absent Provider counters or costs remain unknown. `test_task_usage.py` covers polling enrichment followed by download failure, and a cancelled generation whose job later reports its cost or is logged by id at shutdown.

Shutdown cancels the owned status polls directly and drains their cost watchers, including a watcher that has not started yet. Caller cancellation cannot finish service shutdown while an adopted poll still runs.

## Session delivery after a lost response

`VideoRecovery` records the accepted job on its original Run and Tool call before polling. Recovery retrieves that id on the original Provider endpoint and pinned account. A definitive failed job releases its receipt before an eligible configured fallback. A pending Tool result makes the job collectable during the same Run. After a shutdown or process restart ordinary Sessions resume collection. A cancelled Run, expired execution owner, replaced or archived Session cannot receive the result. The current Session permission boundary and original lexical and resolved directory are checked before collection, exclusive publication and delivery. Temporary per-call grants do not outlive the call.

The receipt records the digest and selected filename before publication. On another pass an already published matching file is reused. A normal Tool result confirms foreground delivery. A background result is acknowledged in the same transaction as the completion input, including grouped Extension continuations. A missing job, definitive refusal or changed destination produces a terminal notice. A response with no accepted job id never enters background collection.

## Agent-facing text

| Text | Reason |
|---|---|
| `The video request was accepted. vBot will collect it and send the result to this Session. No further call is needed.` | A second generation can incur a second charge. The result tells the Agent who will collect the existing job and where it will arrive. |
| `Video job <receipt>: Video saved to "<path>"` | Identifies the completed job and its local file for the original Session. The path is quoted as data. |
| `The Provider returned a video vBot could not read. Provider job ID: "<job>"` | A completed interaction contains immutable missing or unreadable inline data. The reference lets the user identify it at the Provider. |
| `The Provider no longer has a video to collect.` | Settles the pending result after a definitive Provider failure. |
| `The destination or its permissions changed. Provider job ID: "<job>"` | Explains why delivery ended and preserves the Provider reference without exposing an inaccessible path. If access changes during final delivery only the destination change is reported. |

## Google route

Gemini Omni (`gemini-omni-*`) is not a Chat Model and has no Veo-style `predictLongRunning`; Google documents it on the Interactions API only (Omni and Interactions API guides, read 2026-11-17; Veo 3.1 Preview was shut down on the Gemini API on 2026-10-22). One `POST /interactions` sends `background: true, store: true`, the prompt as `input` (with frames: image items first, last, then the text, plus `generation_config.video_config.task = image_to_video`), and `response_format {type: video, aspect_ratio, resolution, duration: "<n>s"}`. Published choices: `16:9 9:16`, `360p 720p 1080p 4k`, durations 3-15 s on 1.2 and 3-10 s on 1.1 and the preview; frames are a first frame, or first and last for at most 10 s. A last frame alone or a longer frame pair is rejected before the request. Only 503 is replayed (`TaskRequestRetryPolicy`, as for image and music).

`GET /interactions/{id}` polls with the shared loop. `completed` and `incomplete` end the job; the video is the first `video` item of a `model_output` step, inline base64 (no download; `raw` drops the data). `failed`, `cancelled` and the `requires_*` states fail with the first `errors[]` entry: `RESOURCE_EXHAUSTED` is `ProviderUsageLimitError` (fallback switch), a refusal code or phrase is `ProviderContentRefusedError`, anything else a non-retryable `ProviderError`. A finished interaction with only text is a refusal; a video without inline data or undecodable data is `VideoJobUnfinishedError`. Usage (`total_input/cached/output/thought_tokens`) is normalized like `generateContent`: output includes thoughts. A caller cancel during polling first POSTs `/interactions/{id}/cancel` once (best effort, no Model call recorded) and hands over a task that then follows the poll like OpenRouter's. Stored interactions are not deleted after collection (Google's retention applies). Live (2026-11-17, free-tier key): all three Omni Models accepted the background interaction, which then failed with `RESOURCE_EXHAUSTED` (-> `ProviderUsageLimitError`); a generated video, safety outcomes, Usage and the cancel endpoint are verified from docs and mocked tests only.
