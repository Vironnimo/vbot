# Live voice

Read for Live voice calls: the `live_voice` Task Model, provider wires, delegated reasoning, the server call registry and owner socket, spoken app operations, or proactive Run announcements. Shared task-client authentication/retry belongs to `providers.md`; Chat and Terminal behavior remain in their existing domains.

## Ownership

The server owns everything except media. The provider control channel, delegated reasoning, Tool execution, and Run announcements run on the server; the accessor owns only microphone/speaker media, the UI requests the server sends it, and the displayed call state. The bound Provider decides the media kind: `webrtc` (OpenAI; the accessor connects audio directly to the provider) or `relay` (xAI; the server holds the provider socket and relays PCM16 mono 24 kHz over the owner socket). Barge-in and turn-taking happen in the provider's voice model (relay: the provider's server VAD plus a `playback_clear` update); vBot never pauses the conversation for app work.

- `core/model_tasks/live.py` is the public surface: `LiveVoiceService` (`status()`, `start_call`), the `LiveCallHost` / `LiveCall` / `LiveRuntime` protocols, `LiveRunNotice`, `LIVE_MEDIA_KINDS`, and `LiveStartRejected` with `LIVE_START_REJECTION_CODES` (`not_configured`, `invalid_offer`, `access_denied`, `rate_limited`, `outcome_unknown`, `provider_error`, `control_failed`, `media_mismatch`). Runtime constructs it as `runtime.live_voice`.
- Internal core files: `_live_wire.py` (provider-neutral `LiveWire` protocol, normalized events, media descriptors), `_live_openai.py` (OpenAI wire), `_live_xai.py` (xAI wire: realtime socket driving the sans-IO `_XaiSession`), `_live_brain.py` (delegation Tool loop), `_live_call.py` (`LiveCallSession` lifecycle, relay audio pump), `_live_tools.py` (voice, direct-mode, and delegation instructions, the `vbot_request` and two app Tool definitions, shared Tool-call checks and error results), `_live_options.py` (backend Model candidates for option schemas, `NO_BACKEND_MODEL`).
- A new provider adds a `LiveWire` implementation and an entry in `_PROVIDER_WIRES` (`live.py`): its media kind, whether its voice model may call the app Tools directly, and the wire opener. `LiveCallSession` and `LiveBrain` stay provider-neutral. Registered: `openai` (`webrtc`, delegation only) and `xai` (`relay`, direct Tools capable); any other binding rejects as `not_configured`.
- `server/live.py` (`LiveCallRegistry`, `app.state.live_calls`) owns call ownership, the owner socket `/ws/live/{call_id}` (JSON updates plus binary relay audio), UI requests, and the per-call Tool lock. `server/_live_tools.py` (`LiveToolExecutor`) runs app operations; `server/_live_feed.py` (`LiveRunFeed`) announces Runs. `server/rpc/live_methods.py` exposes `live.status`, `live.start`, `live.stop`, `live.ui_result`. The lifespan ends Live calls (bounded to 10 s) before the Runtime closes.
- WebUI: `lib/api/live.js` (RPC wrappers, owner socket with `sendAudio`/`onAudio`, close-code outcomes), `lib/liveVoice.js` (controller: media kind per `live.status`, owner socket, UI requests, bounded captions), `lib/liveAudio.js` (relay audio engine: 24 kHz `AudioContext` with a device-rate fallback, capture and playback nodes) with its AudioWorklet module `lib/liveAudioWorklet.js` (self-contained, emitted as a separate build asset), `components/LiveVoice.svelte` (mounted through AppShell's `sidebarFooter` in `App.svelte`, outside tab remounts). `App.svelte`'s `liveUiActions` implement UI requests through existing autosave navigation and the `TerminalsView.svelte` controller.
- Desktop accessor: `LiveVoice.svelte` passes the Desktop microphone lease (`createDesktopLiveVoiceLease` in `lib/desktopBridge.js`) to the controller, which acquires it before `getUserMedia` and releases it with the media, so Desktop wakeword listening pauses for the call. It also handles pushed hands-free requests (wakeword phrase: start; global shortcut: toggle). Contracts: `desktop/live-voice.md`.

## Terms

### Live call

One realtime voice conversation: a provider media session plus its control channel, owned by the server. At most one per server; starting another replaces it.

### Voice model / backend model

The voice model (the binding target) talks with the user. The backend model (option `backend_model`) handles delegated requests by calling the app Tools. On a direct-Tools-capable Provider the backend model is optional (`""`). vBot's coding Agents still do coding work.

### Direct Tools mode

A Live call without a backend model: the voice model gets `vbot_app` / `vbot_terminal` and `DIRECT_VOICE_INSTRUCTIONS` instead of `vbot_request`, and each Tool call runs once through the host's Tool path. Only Providers registered as direct-capable (today `xai`) allow it.

### Delegation

A request the voice model hands to vBot during the conversation. It returns one spoken-style answer to the voice model. Several run at once.

### Owner

The accessor that started the call. It attaches the owner socket and answers UI requests; only it holds media.

## Binding and options

- Task type `live_voice` is explicit-only (`MODEL_TASK_ORDER`, no modality derivation): voice Models declare it in `task_types`. Catalog entries: `resources/models/openai.overrides.json` has `gpt-live-1` (`api-key` Connection) and `gpt-live-1-codex` (`subscription` Connection); `resources/models/xai.overrides.json` has `grok-voice-think-fast-2.0` (`api-key` and `subscription`, 28 voices, default `eve`). They show in the Chat picker only under "Show all models", like other task-only Models.
- Options come from `task_options.live_voice.parameters`: `voice` (enum with a declared default) and `backend_model` (spec type `model`; OpenAI default `gpt-5.6-terra`). A `backend_model` spec with `allow_none` (xAI, default `""`) adds the choice "None (the voice model uses vBot directly)" and makes the field optional; the runtime picks direct Tools mode from `""` on a direct-capable Provider, not from the catalog flag. `live_backend_candidates` offers tool-capable chat Models of the same Provider that the binding's Connection allows, so the Settings UI and save validation agree. `options_with_defaults` fills all options before start; a stale or disallowed `backend_model` rejects start as `not_configured`.
- `backend_thinking_effort` ("Backend reasoning") accompanies `backend_model`, never declared without it. Choices are the canonical effort ladder (`""` = Model default, then `none` ... `max`; same set as `ALLOWED_THINKING_EFFORTS`), default `low` for spoken latency; a binding saved without it (or with `null`) uses `low`. Its `options_by` narrows the visible choices per backend candidate that publishes `reasoning.levels` to `""`, `none`, and those levels (the Agent editor rule); candidates without a ladder keep every choice. With `allow_none`, `options_by` maps `""` to an empty list, which hides the field; direct Tools mode ignores the effort. Save validation accepts the full ladder; an invalid stored value rejects start as `not_configured`. The Adapter fits the effort to the backend's ladder (`resolve_reasoning_intent`), so a later backend change never breaks a call.
- `live.status` returns `{configured, usable, target, media}`; `usable` proves credentials only, not account access to the voice Model; `media` is the kind a start must request (`null` when the bound Provider has no Live wire). The accessor shows the control when `settings.model_tasks.live_voice.target` is set. Settings -> Voice -> "Live voice" edits the binding through the shared Task Model editor.

## Call lifecycle

- `live.start {media, sdp?}`: `media` must be `webrtc` or `relay` and match the bound Provider, else `{error: "media_mismatch"}` (the accessor re-reads `live.status` and retries once). `webrtc` requires the offer: it must start with `v=0`, contain `m=audio`, and be <= 64 KiB; the server creates the provider call (non-idempotent task-client policy; never replayed), joins the control channel immediately (it does not replay earlier events), and returns `{call_id, media: {type: "webrtc", sdp}}`. `relay` rejects `sdp`; the server joins the provider socket and returns `{call_id, media: {type: "relay", audio: {encoding: "pcm16", sample_rate: 24000, channels: 1}}}`. Expected failures return `{error: <code>}` instead of an RPC error.
- WebRTC: the accessor gathers ICE non-trickle (5 s cap), attaches the owner socket, then applies the answer. Relay: the accessor starts capture and playback before `live.start` (failing as `audio_unsupported` or `playback_blocked` without a provider call), requests `echoCancellation: "all"` where the microphone track offers it, attaches the owner socket, and sends microphone audio only once `live`. Updates: `state` (`connecting` -> `live` on provider session start -> `closing` -> `closed` | `failed`), `caption` (`user` | `assistant`, `final`, text <= 1000 chars), `activity` (`busy`, label `working` while delegations run), `playback_clear` (relay: drop queued assistant audio at once; sent at every user speech start), exactly one `closed {reason, usage}`. The server may add a non-fatal `error` frame (`notification_failed`) and idle `heartbeat` frames (25 s).
- Relay audio uses binary owner-socket frames. Inbound microphone PCM (even length, <= 64 KiB, current owner only; malformed frames are dropped and logged once) goes to `LiveCall.push_audio`, which drops audio before `live` and while closing and keeps at most 2 s of backlog. Outbound assistant PCM goes only to an attached owner and counts toward the owner queue (overflow closes with 1013).
- `live.stop` closes gracefully in the background: the session asks the provider to close and waits up to 15 s for a confirmed close with usage. Abort (owner lost, replacement, shutdown) sends a best-effort close within 1 s. A call that is not `live` within 45 s aborts with `start_timeout`.
- Closed reason priority: abort reason > confirmed provider reason > `closed` (after stop) > `connection_lost`. Phase `failed` only for `connection_lost` and `start_timeout`. A replaced call gets `closed` with reason `replaced`.
- Registry limits: owner must attach within 15 s and may reattach within 10 s after a socket loss, else the call ends; UI requests time out after 20 s; up to 200 updates buffer before attach; owner queue 1000. Close codes: 1000 after `closed`, 1008 unknown call, 1013 owner fell behind, 4000 replaced by a newer owner socket (do not reconnect).

## Delegation and trust

- `LiveBrain` runs a Tool loop over `runtime.get_adapter(ConnectionRef).send(...)` with the backend Model on the voice binding's Connection, the configured `backend_thinking_effort` as `thinking_effort` (`None` for `""`), at most 8 steps, and the last 10 request/answer pairs of the call as history. Each input carries the delegated request, the recent conversation (12 turns, <= 4000 chars), and the last 5 vBot updates.
- Up to 4 delegations run concurrently, each bounded to 240 s. Tool executions of one call are serialized by the registry. When the provider sends no request text, the session waits for user quiet (0.4 s, max 2 s) so the latest speech is included.
- Retryable Provider errors retry only the model send (0.5 s, 1.5 s), never a Tool execution. Unknown Tools and non-object arguments do not execute. Failures and timeouts answer with a spoken note naming mutating actions already performed as possibly completed; nothing is retried.
- Direct Tools mode: the wire emits `WireToolCall`; `LiveCallSession` applies the brain's checks (`live_tool_rejection`: known Tool, object arguments), runs `LiveCallHost.execute_tool` once within the same 4-slot limit and 240 s bound, and returns the JSON result as the call output. Timeouts and failures return `live_tool_error` results (`timeout`, `tool_failed`); nothing is retried. A `vbot_request` reaching a call without a backend model answers that no backend model is configured.
- Voice and delegation instructions (`VOICE_INSTRUCTIONS`, `DIRECT_VOICE_INSTRUCTIONS`, `DELEGATION_INSTRUCTIONS` in `_live_tools.py`) are runtime Agent-facing text. Chat messages, Terminal contents, and vBot updates are quoted data, not instructions. Provider appends are ephemeral provider context, never vBot Session history or kernel reminders; acknowledgments do not prove audible speech.

## App operations

- `vbot_app`: `context`, `open` (UI requests), `sessions` (`session.list`, 30), `read` (`chat.history`, 20 messages reduced to the recent 8,000 chars), `send` (`chat.stream` with `input_origin: speech_transcription`, normal Queue admission, text <= 16,000 chars). Exact Agent/Session ids; an unseen Session address is validated through `chat.history` first.
- `vbot_terminal`: list, start, read, input, show, maximize, restore, reorder, group create/show/rename/delete, close. Operations dispatch the registered RPC handlers in-process, so validation and `/ws` publication match other accessors.
- Terminal start accepts only Codex/Claude Code, a positive count (default one, no Live ceiling; TerminalManager capacity is authoritative), and an explicit server directory; without a `group_id` it reuses an editable group named after the program or creates one. A failed batch returns the requested count, confirmed Terminal summaries, and the error, never replaying accepted launches. This validates launch scope, not the foreground program after the CLI exits to its shell.
- Operator reads preserve Agent bindings; screens return the last 8,000 chars. Input rechecks the rendered screen revision (`expected_screen_revision`), rejects raw control characters, honors bracketed paste for multiline text, and supports named keys. `close` stops then forgets the exact Terminal like the UI close action; failures report confirmed or uncertain stop/removal state and never replay. A completed mutation stays reported when the following layout refresh fails (`layout_error`).
- UI requests (`context`, `open` for `chat` | `terminals`, `terminal_view` ops `context` / `refresh` / `show` / `maximize` / `restore` / `show_group`) go to the owner, which answers through `live.ui_result` with exactly one of `result` or `error`. After stop or replacement, multi-step operations stop before further effects (`voice_stopped`) and report confirmed partial results.

## Run announcements

- `LiveRunFeed` follows the server event bus from the call's start and announces completed/failed/interrupted Runs once (cancelled Runs stay silent). It skips Runs that finished before the call and Runs excluded from Agent activity. It loads each excerpt through `chat.run_result` for the exact scoped Run, so newer replies in the same Session never replace it (see `chat.md`). After a bus lag it resubscribes; Runs that left retention stay silent.
- The call dedups announcements, ignores them once closing, keeps the last 5 as brain context, and speaks them only while `live`. Text: `vBot update: {"run", "agent", "session_id", "result_excerpt" (<= 600 chars), "excerpt_truncated"}`. Finished Runs are announced briefly; Agent questions are relayed, summaries only on request. Terminal quietness never proves a coding task finished.
- Security gotcha: a wire whose announcements reach the voice model like user input (`LiveWire.announces_as_user_input`, the xAI wire) gets the notice without `result_excerpt` / `excerpt_truncated`; brain context keeps the full text. Live probes (2026-09-24) showed Grok Voice executing an instruction quoted in an unsolicited excerpt (a `vbot_app send` to another Session in 4/4 trials as a user message, 4/4 as a synthetic Tool output) but never after excerpt-free notices (0/4) or in Tool results the user asked for (0/4). Do not put untrusted text into such announcements.

## OpenAI wire

- The Connection mode picks the dialect: `codex_responses` (ChatGPT subscription) -> codex, otherwise public API.
- Codex: `POST <codex base>/codex/realtime/calls?intent=quicksilver&architecture=avas` with `{sdp, session}` (model, instructions, voice, `delegation: {type: "client"}`); headers add `OpenAI-Alpha: quicksilver=v2`, `originator: vbot`, the Account id, and fresh session/thread ids. The SDP answer is the body; the call id comes from `Location`. Control: `wss://api.openai.com/v1/live/<call_id>` with the same headers. Delegations carry request text; results use `delegation.context.append` and announcements `session.context.append` (channel `speakable`, <= 500 bytes per append).
- Public: `POST /live/sessions` returns `{session: {id}, transport: {sdp}}`; the page's data channel is locked to no events. Control: `<base>/live/sessions/<id>/attach`. Delegations carry no text; results and announcements use `session.commentary.append` (<= 1500 bytes per append). Transcripts come from `session.input_transcript.delta` / `session.output_transcript.delta`.
- Call ids must match `^[A-Za-z0-9_-]{1,128}$`. Audio frames on the control channel are dropped unparsed. Logs carry the call id and a public target label without Account id; tokens, SDP, and transcripts never enter logs.

## xAI wire

- `wss://api.x.ai/v1/realtime?model=<id>` with the Connection's auth header; handshake HTTP 401/403 go through the shared OAuth request recovery. The SuperGrok subscription token is accepted (live-verified); the `api-key` Connection is not live-verified. xAI has no WebRTC endpoint, hence relay media.
- Right after connect, `session.update` sets instructions, voice, `server_vad` (threshold 0.85, prefix 333 ms, silence 500 ms), PCM 24 kHz in and out, input transcription `grok-transcribe`, and one Tool set (`vbot_request`, or the app Tools in direct Tools mode). `session.updated` starts the call (`WireStarted`, 120 min lifetime).
- Response gate: vBot sends `response.create` only for its own additions (Tool outputs, announcements) that no completed response covered, and only while no response is pending or active, the user is not speaking, every function call of the last completed response has output, and the estimated playback has drained (+0.2 s). One create covers all pending additions. A create without `response.created` is retried once after 5 s; an "active response" error backs off 1 s; a response silent for 30 s stops blocking.
- Barge-in (`input_audio_buffer.speech_started`): emits `WirePlaybackClear`, truncates each unplayed assistant item at the estimated played milliseconds (`conversation.item.truncate`), fences that response so late output is dropped, and keeps the caption text received so far (the provider's truncated transcript is unreliable).
- Captions: user transcription snapshots are cumulative; only `.completed` with `status: "completed"` is final. Duplicate event families (`output_audio*` and `audio*`, transcript and text) lock to the first carrier per item.
- Announcements are user text messages: Grok Voice ignores system messages added mid-conversation (live-verified; it repeated its previous answer). The echoed item does not finish the user's open caption.
- No session close event exists; closing the socket ends the session. `usage` is empty on subscription sessions, so `closed.usage` stays `null`. Error types `max_duration` / `timeout` close the call.

## Verification and limits

- Tests: `tests/core/model_tasks/test_live.py`, `test__live_openai.py`, `test__live_xai.py`, `test__live_brain.py`, `test__live_tools.py`, `test__live_options.py`; `tests/server/test_live.py`, `test__live_tools.py`, `test__live_feed.py`, `tests/server/rpc/test_live_methods.py`; Run attribution in `tests/server/rpc/test_chat_methods.py`; Terminal guards in the Terminal manager/method tests. WebUI: `lib/__tests__/liveVoice.test.js`, `liveAudio.test.js`, `api.test.live.test.js`, `components/__tests__/LiveVoice.test.js`.
- The codex dialect's call creation, control join, and event shapes were probed against a ChatGPT subscription; the public dialect follows the official docs only. A full spoken call with delegation is not yet verified end to end.
- xAI (2026-09-24, development subscription, scratch probes outside the repo): the real `XaiLiveWire` under `LiveCallSession` with a fake host took a spoken German question as relayed PCM, ran `vbot_app` `context` then `sessions` (direct Tools mode) or one `vbot_request` (delegate mode), and spoke the answer in German; a Run announcement was spoken afterwards. An earlier raw-socket probe confirmed that `conversation.item.truncate` at the estimated played milliseconds is accepted during barge-in. Not yet verified: relay audio in a real browser (AudioWorklet capture/playback, the Firefox device-rate fallback) and acoustic echo with speakers (`echoCancellation: "all"` is best effort; a loopback `RTCPeerConnection` is the known fallback if echo triggers barge-in).
- Browser microphone access needs HTTPS or localhost. Providers other than OpenAI and xAI have no Live wire. The Desktop makes the remote HTTP servers it knows at startup secure contexts; a server added later shows the `desktop_restart_required` notice until the Desktop app restarts. Desktop wakeword Voice no longer conflicts with Live: it pauses during the call.
- Voice duration (including idle time) and backend usage bill separately at the Provider. Canonical Usage records one `live_voice` call and each delegated `live_voice_backend` send/outer retry under its own Model. Cumulative wire Usage replaces previous counters; the final close settles once and preserves the last report after control loss. Unknown duration/pricing units remain unknown, including subscription calls without token telemetry. Adapter-internal retries are not separately visible. Captions remain transient and never enter the Usage store. Persistence failure still publishes the closed state and releases waiters. Coverage: `test_live.py`, `test__live_brain.py`.
- Official public-API sources: OpenAI guides `live`, `voice-webrtc?api=live`, `live-delegation`, `live-conversations`, and `voice-server-controls?api=live` at `https://developers.openai.com/api/docs/guides/`.
