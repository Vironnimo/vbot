# Live voice

Read for Live voice calls: the `live_voice` Task Model, provider wires, delegated reasoning, the server call registry and owner socket, the Live Tools (spoken app operations), proactive Run announcements, or Live call records. Shared task-client authentication/retry belongs to `providers.md`; Chat and Terminal behavior remain in their existing domains.

## Ownership

The server owns everything except media. The provider control channel, delegated reasoning, Tool execution, and Run announcements run on the server; the accessor owns only microphone/speaker media, the UI requests the server sends it, and the displayed call state. The bound Provider decides the media kind: `webrtc` (OpenAI; the accessor connects audio directly to the provider) or `relay` (xAI; the server holds the provider socket and relays PCM16 mono 24 kHz over the owner socket). Barge-in and turn-taking happen in the provider's voice model (relay: the provider's server VAD plus a `playback_clear` update); vBot never pauses the conversation for app work.

- `core/model_tasks/live.py` is the public surface: `LiveVoiceService` (`status()`, `start_call`), the `LiveCallHost` / `LiveCall` / `LiveRuntime` protocols, `LiveRunNotice`, `LIVE_MEDIA_KINDS`, and `LiveStartRejected` with `LIVE_START_REJECTION_CODES` (`not_configured`, `invalid_offer`, `access_denied`, `rate_limited`, `outcome_unknown`, `provider_error`, `control_failed`, `media_mismatch`). Runtime constructs it as `runtime.live_voice`.
- Internal core files: `_live_wire.py` (provider-neutral `LiveWire` protocol, normalized events, media descriptors), `_live_openai.py` (OpenAI wire), `_live_xai.py` (xAI wire: realtime socket driving the sans-IO `_XaiSession`), `_live_brain.py` (delegation Tool loop, Tool call and delegation records), `_live_call.py` (`LiveCallSession` lifecycle, relay audio pump, direct Tool calls), `_live_tools.py` (voice, direct-mode, and delegation instructions, the `vbot_request` and eight Live Tool definitions, `live_success` / `live_failure` / `live_result_text`), `_live_arguments.py` (`prepare_live_call`), `_live_programs.py` (`CODING_PROGRAMS`: Codex and Claude Code commands, readiness markers, startup questions, interrupt key), `_live_options.py` (backend Model candidates for option schemas, `NO_BACKEND_MODEL`).
- A new provider adds a `LiveWire` implementation and an entry in `_PROVIDER_WIRES` (`live.py`): its media kind, whether its voice model may call the app Tools directly, and the wire opener. `LiveCallSession` and `LiveBrain` stay provider-neutral. Registered: `openai` (`webrtc`, delegation only) and `xai` (`relay`, direct Tools capable); any other binding rejects as `not_configured`.
- `server/live.py` (`LiveCallRegistry`, `app.state.live_calls`) owns call ownership, the owner socket `/ws/live/{call_id}` (JSON updates plus binary relay audio), UI requests, the per-call Tool lock, and the calls' records (`LiveCallRecorder` in `server/_live_record.py`). `server/_live_tools.py` (`LiveToolExecutor`) runs the Live Tools with `_live_targets.py` (per-call refs, app catalogs, target resolution), `_live_terminals.py` (coding Terminals: start, typing, keys, layout), and `_live_context.py` (RPC and UI request seams, shared failure texts); `server/_live_feed.py` (`LiveRunFeed`) announces Runs. `server/rpc/live_methods.py` exposes `live.status`, `live.start`, `live.stop`, `live.ui_result`. The lifespan ends Live calls (bounded to 10 s) before the Runtime closes.
- WebUI: `lib/api/live.js` (RPC wrappers, owner socket with `sendAudio`/`onAudio`, close-code outcomes), `lib/liveVoice.js` (controller: media kind per `live.status`, owner socket, UI requests, bounded captions), `lib/liveAudio.js` (relay audio engine: 24 kHz `AudioContext` with a device-rate fallback, capture and playback nodes) with its AudioWorklet module `lib/liveAudioWorklet.js` (self-contained, emitted as a separate build asset), `components/LiveVoice.svelte` (mounted through AppShell's `sidebarFooter` in `App.svelte`, outside tab remounts). `app/liveUiActions.js` (`createLiveUiActions`, wired in `App.svelte`) implements UI requests through the existing autosave navigation: Chat Sessions through the app controller, Agent pages through the shared Agent selection, Project pages through the managed Project selection (an open `ProjectsView` switches itself via `selectVoiceProject`), and Terminal layout through the `TerminalsView.svelte` controller.
- Desktop accessor: Desktop Voice keeps listening during a call. `LiveVoice.svelte` passes the controller a microphone access check (`desktopMicrophoneAccess` in `lib/desktopBridge.js`, run before `getUserMedia`) and the active command wake phrases, which each start sends as `wake_phrases`. While Desktop Voice records a spoken command, it holds the call (`hold`/`release`, reason `wakeword`): the microphone track is disabled and assistant audio is muted (WebRTC) or dropped (relay), independent of the user's mute. It also handles pushed hands-free requests (wake phrase action or global shortcut: start or toggle). Contracts: `desktop/live-voice.md`.

## Terms

### Live call

One realtime voice conversation: a provider media session plus its control channel, owned by the server. At most one per server; starting another replaces it.

### Voice model / backend model

The voice model (the binding target) talks with the user. The backend model (option `backend_model`) handles delegated requests by calling the Live Tools. On a direct-Tools-capable Provider the backend model is optional (`""`). vBot's coding Agents still do coding work.

### Direct Tools mode

A Live call without a backend model: the voice model gets the Live Tools and `DIRECT_VOICE_INSTRUCTIONS` instead of `vbot_request`, and each Tool call runs once through the host's Tool path. Only Providers registered as direct-capable (today `xai`) allow it.

### Delegation

A request the voice model hands to vBot during the conversation. It returns one spoken-style answer to the voice model. Several run at once.

### Live Tools

The eight intent Tools through which the backend model (or the voice model in direct Tools mode) operates vBot as the user: `overview`, `start_agent_session`, `start_coding_terminal`, `send_message`, `read`, `stop`, `open`, `terminal`. They are not Agent Tools: not registered in the ToolRegistry, no ToolContext.

### Ref

A per-call alias (`s1`, `t1`) for a Session or Terminal, assigned in order of first mention in a Live Tool result or Run announcement and stable for the call. It exists only inside the call; storage and RPCs keep exact ids.

### Owner

The accessor that started the call. It attaches the owner socket and answers UI requests; only it holds media.

## Binding and options

- Task type `live_voice` is explicit-only (`MODEL_TASK_ORDER`, no modality derivation): voice Models declare it in `task_types`. Catalog entries: `resources/models/openai.overrides.json` has `gpt-live-1` (`api-key` Connection) and `gpt-live-1-codex` (`subscription` Connection); `resources/models/xai.overrides.json` has `grok-voice-think-fast-2.0` (`api-key` and `subscription`, 28 voices, default `eve`). They show in the Chat picker only under "Show all models", like other task-only Models.
- Options come from `task_options.live_voice.parameters`: `voice` (enum with a declared default) and `backend_model` (spec type `model`; OpenAI default `gpt-5.6-terra`). A `backend_model` spec with `allow_none` (xAI, default `""`) adds the choice "None (the voice model uses vBot directly)" and makes the field optional; the runtime picks direct Tools mode from `""` on a direct-capable Provider, not from the catalog flag. `live_backend_candidates` offers tool-capable chat Models of the same Provider that the binding's Connection allows, so the Settings UI and save validation agree. `options_with_defaults` fills all options before start; a stale or disallowed `backend_model` rejects start as `not_configured`.
- `backend_thinking_effort` ("Backend reasoning") accompanies `backend_model`, never declared without it. Choices are the canonical effort ladder (`""` = Model default, then `none` ... `max`; same set as `ALLOWED_THINKING_EFFORTS`), default `low` for spoken latency; a binding saved without it (or with `null`) uses `low`. Its `options_by` narrows the visible choices per backend candidate that publishes `reasoning.levels` to `""`, `none`, and those levels (the Agent editor rule); candidates without a ladder keep every choice. With `allow_none`, `options_by` maps `""` to an empty list, which hides the field; direct Tools mode ignores the effort. Save validation accepts the full ladder; an invalid stored value rejects start as `not_configured`. The Adapter fits the effort to the backend's ladder (`resolve_reasoning_intent`), so a later backend change never breaks a call.
- `live.status` returns `{configured, usable, target, media}`; `usable` proves credentials only, not account access to the voice Model; `media` is the kind a start must request (`null` when the bound Provider has no Live wire). The accessor shows the control when `settings.model_tasks.live_voice.target` is set. Settings -> Voice -> "Live voice" edits the binding through the shared Task Model editor.

## Call lifecycle

- `live.start {media, sdp?, wake_phrases?}`: `media` must be `webrtc` or `relay` and match the bound Provider, else `{error: "media_mismatch"}` (the accessor re-reads `live.status` and retries once). `webrtc` requires the offer: it must start with `v=0`, contain `m=audio`, and be <= 64 KiB; the server creates the provider call (non-idempotent task-client policy; never replayed), joins the control channel immediately (it does not replay earlier events), and returns `{call_id, media: {type: "webrtc", sdp}}`. `relay` rejects `sdp`; the server joins the provider socket and returns `{call_id, media: {type: "relay", audio: {encoding: "pcm16", sample_rate: 24000, channels: 1}}}`. Expected failures return `{error: <code>}` instead of an RPC error.
- `wake_phrases` (optional) names phrases that address other vBot Agents during the call: <= 8 strings, each trimmed to 1..60 chars without control, format, line/paragraph-separator, or surrogate characters; case-insensitive duplicates keep the first spelling; `[]` equals absent; anything else is an `invalid_request` RPC error (validated in `live_methods.py`). They reach `LiveVoiceService.start_call(wake_phrases=...)` and the voice instructions of every wire (see Delegation and trust).
- WebRTC: the accessor gathers ICE non-trickle (5 s cap), attaches the owner socket, then applies the answer. Relay: the accessor starts capture and playback before `live.start` (failing as `audio_unsupported` or `playback_blocked` without a provider call), requests `echoCancellation: "all"` where the microphone track offers it, attaches the owner socket, and sends microphone audio only once `live`. Updates: `state` (`connecting` -> `live` on provider session start -> `closing` -> `closed` | `failed`), `caption` (`user` | `assistant`, `final`, text <= 1000 chars), `activity` (`busy`, label `working` while delegations run), `playback_clear` (relay: drop queued assistant audio at once; sent at every user speech start), exactly one `closed {reason, usage}`. The server may add a non-fatal `error` frame (`notification_failed`) and idle `heartbeat` frames (25 s).
- Relay audio uses binary owner-socket frames. Inbound microphone PCM (even length, <= 64 KiB, current owner only; malformed frames are dropped and logged once) goes to `LiveCall.push_audio`, which drops audio before `live` and while closing and keeps at most 2 s of backlog. Outbound assistant PCM goes only to an attached owner and counts toward the owner queue (overflow closes with 1013).
- `live.stop` closes gracefully in the background: the session asks the provider to close and waits up to 15 s for a confirmed close with usage. Abort (owner lost, replacement, shutdown) sends a best-effort close within 1 s. A call that is not `live` within 45 s aborts with `start_timeout`.
- Closed reason priority: abort reason > confirmed provider reason > `closed` (after stop) > `connection_lost`. Phase `failed` only for `connection_lost` and `start_timeout`. A replaced call gets `closed` with reason `replaced`.
- Registry limits: owner must attach within 15 s and may reattach within 10 s after a socket loss, else the call ends; UI requests time out after 20 s; up to 200 updates buffer before attach; owner queue 1000. Close codes: 1000 after `closed`, 1008 unknown call, 1013 owner fell behind, 4000 replaced by a newer owner socket (do not reconnect).

## Delegation and trust

- `LiveBrain` runs a Tool loop over `runtime.get_adapter(ConnectionRef).send(...)` with the backend Model on the voice binding's Connection, the configured `backend_thinking_effort` as `thinking_effort` (`None` for `""`), at most 8 steps, and the last 10 request/answer pairs of the call as history (answers only: earlier Tool results are not replayed, so a later delegation reads refs again through `overview` unless the request or an update names them). Each input carries the delegated request, the recent conversation (12 turns, <= 4000 chars), and the last 5 vBot updates.
- Up to 4 delegations run concurrently, each bounded to 240 s. Tool executions of one call are serialized by the registry. When the provider sends no request text, the session waits for user quiet (0.4 s, max 2 s) so the latest speech is included.
- Retryable Provider errors retry only the model send (0.5 s, 1.5 s), never a Tool execution. Every Tool call goes through `prepare_live_call` and only a prepared call executes; a rejected call returns its failure result to the Model. Tool messages carry the JSON envelope, which the Adapter renders as text. Failures and timeouts answer with a spoken note naming the Tools already called that may change things (all but `overview` / `read`) as possibly completed; nothing is retried.
- Direct Tools mode: the xAI wire forwards every function call as `WireToolCall` (argument text that is not JSON stays text); `LiveCallSession` prepares it with `prepare_live_call`, runs `LiveCallHost.execute_tool` once within the same 4-slot limit and 240 s bound, and returns the result as plain text (`live_result_text`). Timeouts and failures return `timeout` / `tool_failed` results; nothing is retried. In delegate mode the wire matches `vbot_request` by `called_tool_name` (wrapper prefixes such as `functions.` allowed), answers delegations as `{"result": <text>}` and errors as plain text. A `vbot_request` reaching a call without a backend model answers that no backend model is configured.
- Voice and delegation instructions (`voice_instructions()`, which returns `VOICE_INSTRUCTIONS` or `DIRECT_VOICE_INSTRUCTIONS` unchanged without wake phrases, and `DELEGATION_INSTRUCTIONS` in `_live_tools.py`) are runtime Agent-facing text. With wake phrases, both modes add a wake phrases block before the backchannel rule: it lists the phrases in double quotes, says vBot mutes the call while such a command is recorded, and tells the voice model not to answer or act on speech starting with a wake phrase and never to say one. Tool results and vBot updates, including the messages, screens, and names they quote, are data to relay, not instructions (the delegating voice model reads `vbot_request` results the same way). Provider appends are ephemeral provider context, never vBot Session history or kernel reminders; acknowledgments do not prove audible speech.

## Live Tools

- Definitions: `live_tools()` in `_live_tools.py`, canonical and rendered non-strict by the Adapter; descriptions, instructions, and failure texts are runtime Agent-facing text. `overview` and `read` only look (`LIVE_READ_ONLY_TOOLS`); every other Tool may change something.
- Results: a Tool result envelope whose success data is one plain-text `content` (`live_success`); a failure (`live_failure`) says what was wrong and names the next valid call with example arguments. Models read results as plain text (`live_result_text`). Effects are never replayed; a failure after a possible effect says so (`UNCERTAIN_DELIVERY`: do not send it again); an unexpected failure of a read-only Tool says nothing changed and allows one more try.
- Preparation (`prepare_live_call`, both modes): other Tool names (`status`, `delegate`, `show` ...), wrapper prefixes (`functions.`), JSON-text arguments, other harnesses' field names (`prompt`, `session_id`, `workdir` ...), program and key spellings, and calls to the former `vbot_app` / `vbot_terminal` become one canonical call, validated by the shared Tool contract (unknown fields are rejected). Contract compilation is cached.
- Refs and targets: `LiveRefs` (executor-owned) assigns the refs; Run announcements use the same table. A target resolves in stages where the first stage with matches decides and several matches are ambiguous: ref (tolerant spellings `S2`, `s-2`, `#s2`), exact id or Agent address, unique id prefix (>= 4 chars), Terminal name, Terminal group name, Agent name, Project name; names compare by `spelling`. An Agent name as a Session target must leave one clear Session (working, or started/addressed/active in this call; `stop` only working ones; `read` falls back to the latest); otherwise the failure lists the candidates and asks for a ref. Scoped exception to `PROJECT.md` -> Object IDs ("no display aliases or abbreviated incoming ids"): refs and id prefixes exist only inside Live Tool calls.
- Sessions: `start_agent_session` creates top-level Sessions (`session.create`, never subagents) at an identity Agent, or with `project` at that Project's team Agent, and sends the task through `chat.stream` with `input_origin: speech_transcription` (normal Queue admission, `count` 1-10, text <= 16,000 chars); a partial start reports the started refs and retries nothing. `send_message` to a Session uses the same send (a working Session queues it). `read` returns the newest user, assistant, and error texts from `chat.history` (20 messages, 8,000 chars shared, cut at a word) as quoted lines. `stop` cancels the active Run (`chat.cancel`). `overview` lists identity Agents, the selected Project's team, Projects with folders, running then recently finished Sessions (finished since the call started or touched by Live; 12 shown) with the end of the final message through `chat.run_result` (160 chars; a final message ending in `?` reads "waiting for an answer", a heuristic, not a Run state), and Terminals. The Agent and Project catalogs come from the owner's `context` UI request, falling back to `agent.list` / `project.list`.
- Coding Terminals, security contract: a task never becomes part of a command line (Windows `.cmd` shims let quotes, `&`, `%` in free text escape into the shell). `start_coding_terminal` runs `terminal.start` with the program's command only (`codex` | `claude`), `count` 1-10, in a Project's folder (name match), an existing absolute folder, or the selected Project's folder, inside an editable group named after the program (created when missing). It waits (poll 0.5 s, <= 25 s, screen stable 0.8 s) until the program shows its own input line, types the task as bracketed paste (line breaks flattened when paste is off; control characters rejected) guarded by `expected_screen_revision` (up to 3 attempts on a stale screen), then sends Enter in a separate write once the program's input line shows the text (its first 12 characters, or a `[Pasted` placeholder; re-read every 0.5 s, up to 3 times). It never types while the shell prompt, a menu, or a startup question (folder trust, Codex update) shows; it reports the question and names the `terminal` key calls and the following `send_message`. A partial start reports the started refs; nothing is retried or typed. The markers and the CLI versions they were observed with are documented in `_live_programs.py`; update them when a CLI changes its screens.
- Fail-closed program check: every Live write to a coding Terminal - paste, Enter, and `terminal`/`stop` keys - passes `expected_program` (`codex` | `claude`) to `terminal.input`, so the Terminal manager writes it only while that program runs in the Terminal's process tree (see `tools/terminal.md`); a refusal reports that the program no longer runs and nothing reached the shell (`program_not_running` for keys). The screen rules are the second line: the input line is the last line starting with the program's arrow (`›` Codex, `❯` Claude Code) and must not be a numbered menu answer or have numbered answers below it; the shell prompt as the last line covers PowerShell, cmd, `user@host` bash/zsh/fish prompts, and prompt themes ending in `❯` (starship, oh-my-posh).
- Startup questions are answered by the Agent with `terminal` keys; Enter on a screen showing a known question is pressed only while the answer Live's guidance names (`CliPrompt.choice`: Codex "Yes, continue" / "Skip", Claude Code "Yes, I trust this folder") is the selected one; otherwise `answer_not_selected` names the selected answer and the next step, and other answers are left to the user in the app.
- `send_message`, `read`, `stop`, and `terminal` `key` work only on coding Terminals: messages are typed like tasks, screens return the last 8,000 chars, `stop` presses the program's interrupt key (Escape). Operator reads preserve Agent bindings.
- `open` navigates through the owner (`open` UI request): a Session in the chat, an Agent's latest Session or with `view: agents` its page, a Project's page (a team Agent has no Agent page, so its Project page opens), or a view; Terminals and groups show through `terminal_view`. `terminal` actions: maximize, restore, key, close (stop then forget like the UI close action; failures report confirmed or uncertain state and never replay), reorder, create/rename/delete group (only `user` / `agent` groups are editable; delete stops the group's Terminals). A completed change stays reported when the following layout refresh fails.
- UI requests (shapes in the `server/_live_tools.py` docstring): `context`, `open` (`chat` | `terminals` | `agents` | `projects` with no target or exactly one of `agent_id` + `session_id` (chat), `agent_id` (agents, identity Agents only), `project_id` (projects); `false` / `{applied: false}` when the app did not switch, reported as `navigation_not_applied`), `terminal_view` ops `show` / `maximize` / `show_group` / `restore` / `refresh` (the accessor also still answers `context`, which the server no longer sends). The owner answers through `live.ui_result` with exactly one of `result` or `error`.
- Execution: operations dispatch the registered RPC handlers in-process, so validation and `/ws` publication match other accessors. The registry serializes one call's Tool executions; the lock stays held through a Terminal readiness wait (<= 25 s). After stop or replacement, multi-step operations stop before further effects (`voice_stopped`) and report confirmed partial results.

## Run announcements

- `LiveRunFeed` follows the server event bus from the call's start and announces completed/failed/interrupted Runs once (cancelled Runs stay silent). It skips Runs that finished before the call and Runs excluded from Agent activity. It loads each excerpt through `chat.run_result` for the exact scoped Run, so newer replies in the same Session never replace it (see `chat.md`). After a bus lag it resubscribes; Runs that left retention stay silent.
- The call dedups announcements, ignores them once closing, keeps the last 5 as brain context, and speaks them only while `live`. Text: `vBot update: {"run", "agent", "session" (the Session's ref), "result_excerpt" (<= 600 chars), "excerpt_truncated"}`. Finished Runs are announced briefly; Agent questions are relayed, summaries only on request. Terminal quietness never proves a coding task finished.
- Security gotcha: a wire whose announcements reach the voice model like user input (`LiveWire.announces_as_user_input`, the xAI wire) gets the notice without `result_excerpt` / `excerpt_truncated`; brain context keeps the full text. Live probes (2026-09-24) showed Grok Voice executing an instruction quoted in an unsolicited excerpt (a send to another Session through the former `vbot_app` Tool in 4/4 trials as a user message, 4/4 as a synthetic Tool output) but never after excerpt-free notices (0/4) or in Tool results the user asked for (0/4). Do not put untrusted text into such announcements.

## Records

- Every Live Tool call (both modes) and every delegation is recorded locally to measure how Models use the Live Tools: `LiveCallHost.record(event)` -> `LiveCallRecorder` appends one JSON line to `<data_dir>/artifacts/live-calls/<YYYY-MM-DD>.jsonl` (UTC day; `DataDirectoryLayout.live_calls`, created on first write), adding `at` and `call_id`. Tool records: `{type: "tool", mode: "direct" | "delegated", called, tool, arguments (as the Model sent them), run_arguments (prepared; `null` when rejected), ok, result (the text the Model read), duration_ms}`. Delegation records: `{type: "delegation", request, answer, steps, tool_calls, failure, duration_ms}`.
- Records hold conversation content (requests, arguments, result texts): they stay on this machine and never enter logs. One ordered writer thread (`live-records` `OrderedWorker`) appends; beyond 256 pending records a new one is dropped with a WARNING, write failures log only the error type, and recording never fails a call. Files older than 30 days are deleted when the first record of a new UTC day is written. `LiveCallRegistry.aclose()` drains the writer.

## OpenAI wire

- The Connection mode picks the dialect: `codex_responses` (ChatGPT subscription) -> codex, otherwise public API.
- Codex: `POST <codex base>/codex/realtime/calls?intent=quicksilver&architecture=avas` with `{sdp, session}` (model, instructions, voice, `delegation: {type: "client"}`); headers add `OpenAI-Alpha: quicksilver=v2`, `originator: vbot`, the Account id, and fresh session/thread ids. The SDP answer is the body; the call id comes from `Location`. Control: `wss://api.openai.com/v1/live/<call_id>` with the same headers. Delegations carry request text; results use `delegation.context.append` and announcements `session.context.append` (channel `speakable`, <= 500 bytes per append).
- Public: `POST /live/sessions` returns `{session: {id}, transport: {sdp}}`; the page's data channel is locked to no events. Control: `<base>/live/sessions/<id>/attach`. Delegations carry no text; results and announcements use `session.commentary.append` (<= 1500 bytes per append). Transcripts come from `session.input_transcript.delta` / `session.output_transcript.delta`.
- Call ids must match `^[A-Za-z0-9_-]{1,128}$`. Audio frames on the control channel are dropped unparsed. Logs carry the call id and a public target label without Account id; tokens, SDP, and transcripts never enter logs.

## xAI wire

- `wss://api.x.ai/v1/realtime?model=<id>` with the Connection's auth header; handshake HTTP 401/403 go through the shared OAuth request recovery. The SuperGrok subscription token is accepted (live-verified); the `api-key` Connection is not live-verified. xAI has no WebRTC endpoint, hence relay media.
- Right after connect, `session.update` sets instructions, voice, `server_vad` (threshold 0.85, prefix 333 ms, silence 500 ms), PCM 24 kHz in and out, input transcription `grok-transcribe`, and one Tool set (`vbot_request`, or the Live Tools in direct Tools mode). `session.updated` starts the call (`WireStarted`, 120 min lifetime).
- Response gate: vBot sends `response.create` only for its own additions (Tool outputs, announcements) that no completed response covered, and only while no response is pending or active, the user is not speaking, every function call of the last completed response has output, and the estimated playback has drained (+0.2 s). One create covers all pending additions. A create without `response.created` is retried once after 5 s; an "active response" error backs off 1 s; a response silent for 30 s stops blocking.
- Barge-in (`input_audio_buffer.speech_started`): emits `WirePlaybackClear`, truncates each unplayed assistant item at the estimated played milliseconds (`conversation.item.truncate`), fences that response so late output is dropped, and keeps the caption text received so far (the provider's truncated transcript is unreliable).
- Captions: user transcription snapshots are cumulative; only `.completed` with `status: "completed"` is final. Duplicate event families (`output_audio*` and `audio*`, transcript and text) lock to the first carrier per item.
- Announcements are user text messages: Grok Voice ignores system messages added mid-conversation (live-verified; it repeated its previous answer). The echoed item does not finish the user's open caption.
- No session close event exists; closing the socket ends the session. `usage` is empty on subscription sessions, so `closed.usage` stays `null`. Error types `max_duration` / `timeout` close the call.
