# Live voice

Read for Live voice calls: the `live_voice` Task Model, the call lifecycle and owner socket, delegated reasoning, and the trust rules of what the voice model hears. The voice operator's Tools, memory and records are in `model_tasks/live-operator.md`; provider wire details in `model_tasks/live-wires.md`. Shared task-client authentication/retry belongs to `providers.md`; Chat and Terminal behavior remain in their existing domains.

## Ownership

The server owns everything except media. The provider control channel, delegated reasoning, Tool execution, and Run announcements run on the server; the accessor owns only microphone/speaker media, the UI requests the server sends it, and the displayed call state. The bound Provider decides the media kind: `webrtc` (OpenAI; the accessor connects audio directly to the provider) or `relay` (xAI; the server holds the provider socket and relays PCM16 mono 24 kHz over the owner socket). Barge-in and turn-taking happen in the provider's voice model (relay: the provider's server VAD plus a `playback_clear` update); vBot never pauses the conversation for app work.

- Core (`core/model_tasks/`): `live.py` is the public surface: `LiveVoiceService` (`status()`, `start_call`), the `LiveCallHost` / `LiveCall` / `LiveRuntime` protocols, `LiveBrief` (voice instructions, the `vbot_request` definition, delegation instructions, Tool definitions), `LiveToolRun` (a Tool result plus the canonical name of a Tool that may have changed something), the result helpers `live_success` / `live_failure` / `live_result_text`, `LiveRunNotice`, `LIVE_MEDIA_KINDS`, and `LiveStartRejected` with `LIVE_START_REJECTION_CODES` (see Call lifecycle). Runtime constructs it as `runtime.live_voice`. Internal: `_live_wire.py` (provider-neutral `LiveWire` protocol, normalized events, media descriptors), `_live_openai.py` (OpenAI wire), `_live_xai.py` (xAI wire: the realtime socket) driving `_live_xai_session.py` (sans-IO `XaiSession`), `_live_brain.py` (delegation Tool loop over the host's Tools, delegation records), `_live_call.py` (`LiveCallSession` lifecycle, relay audio pump, direct Tool calls, closed reasons), `_live_results.py` (result envelopes and their plain text), `_live_options.py` (backend Model candidates for option schemas, `NO_BACKEND_MODEL`).
- The core knows no Live Tool: the host supplies a call's instructions and Tools (`LiveCallHost.brief(direct_tools=...)`, asked once at start) and runs every Tool call as the Model made it (`LiveCallHost.run_tool(name, arguments, rejection=None)`, raw name and arguments). The host also takes the call's updates (`publish`, `publish_audio`), records (`record`) and names the refs results gave (`known_refs`).
- A new provider adds a `LiveWire` implementation and an entry in `_PROVIDER_WIRES` (`live.py`): its media kind, whether its voice model may call the app Tools directly, and the wire opener. `LiveCallSession` and `LiveBrain` stay provider-neutral. Registered: `openai` (`webrtc`, delegation only) and `xai` (`relay`, direct Tools capable); any other binding rejects as `not_configured`.
- Server (`server/live/`, the operator): `registry.py` (`LiveCallRegistry`, `app.state.live_calls`) starts and stops calls (one active), attaches owner sockets, routes UI results, keeps an ended call's final updates for a reconnecting owner, and carries the operator memory between calls. `owner.py` defines the owner socket protocol `/ws/live/{call_id}` (frames, close codes; `LiveOwnerStream`). `_call.py` (`LiveCallEntry`, `LiveCallLimits`) is the `LiveCallHost` of one call: brief, Tool calls, the update buffer, UI requests, Run feed, `end_call`, idle hangup, Debug Mode records. The Live Tools, memory, Run feed and records: `model_tasks/live-operator.md`. `server/rpc/live_methods.py` exposes `live.status`, `live.start`, `live.stop`, `live.ui_result`. The lifespan ends Live calls (bounded to 10 s) before the Runtime closes.
- WebUI: `lib/api/live.js` (RPC wrappers, owner socket with `sendAudio`/`sendJson`/`onAudio`, close-code outcomes); `lib/liveVoice.js` (controller: media kind per `live.status`, owner socket, context reports (`reportContext`), bounded captions and operator actions in arrival order (`seq`; kept after the call until the next start), call time, provider expiry and idle deadlines, speaker mute (`muteSpeaker`), `stay`, holds); `lib/liveUiRequests.js` (validates the server's UI requests and runs them through the app's UI actions); `lib/liveAudio.js` (relay audio engine: 24 kHz `AudioContext` with a device-rate fallback, capture and playback nodes) with its AudioWorklet module `lib/liveAudioWorklet.js` (self-contained, emitted as a separate build asset); `components/LiveVoice.svelte` (mounted through AppShell's `sidebarFooter` in `App.svelte`, outside tab remounts) with `components/voice/LiveActivityPanel.svelte`. `app/liveUiActions.js` (`createLiveUiActions`, wired in `App.svelte`) reports what the app shows (`context()`, which `LiveVoice.svelte` pushes on every change) and implements UI requests through the existing autosave navigation: Chat Sessions, Agent pages and Project pages as navigator steps (`webui/app-shell.md` -> Navigation), and Terminal layout through the `TerminalsView.svelte` controller.
- Sidebar control (`LiveVoice.svelte`): start/stop, busy dot, activity panel, speaker mute, microphone mute; a status row with the latest caption and the call time. Warnings outrank the caption: the idle warning (`idle`, with a "Keep call" button sending `stay`, plus one `idle_warning` toast for layouts without the status row) and the provider limit in its last 2 minutes (`expiry`). The activity panel lists captions and operator actions in order; an action shows its Tool, arguments, result (long ones folded), and its links, which open the Session in the chat (`uiActions.open`) or show the Terminal (`uiActions.terminalView`); a link that fails warns (`link_failed`). It stays readable after the call. While a call runs in a browser (not the Desktop accessor), `beforeunload` asks before leaving the page. Notices map the closed reasons `hung_up`, `idle`, `expired` and the start codes `provider_unavailable`, `backend_unavailable` to their own texts.
- Chat: messages Live passes on to a Session carry `input_origin: live_voice`; the Model gets a hidden System Reminder that the text may contain speech recognition errors or the assistant's rewording, and the chat labels the message "You - via Live" (`chat/request-building.md`).
- Recordings in the page (chat composer and Terminal dictation through `lib/audioRecorder.js`) and a recording Desktop dictation (`desktop/dictation.md` -> Live hold) claim the microphone in `lib/microphoneUse.js`; while one records, `LiveVoice.svelte` holds the call with reason `recording`, so a dictation never reaches the voice model.
- Desktop accessor: Desktop Voice keeps listening during a call. `LiveVoice.svelte` passes the controller a microphone access check (`desktopMicrophoneAccess` in `lib/desktopBridge.js`, run before `getUserMedia`) and the active command wake phrases, which each start sends as `wake_phrases`. While Desktop Voice records a spoken command, it holds the call (`hold`/`release`, reason `wakeword`): the microphone track is disabled and assistant audio is muted (WebRTC) or dropped (relay), independent of the user's mute. It also handles pushed hands-free requests (wake phrase action or global shortcut: start or toggle). Contracts: `desktop/live-voice.md`.

## Terms

### Live call

One realtime voice conversation: a provider media session plus its control channel, owned by the server. At most one per server; starting another replaces it.

### Voice model / backend model

The voice model (the binding target) talks with the user. The backend model (option `backend_model`) handles delegated requests by calling the Live Tools. On a direct-Tools-capable Provider the backend model is optional (`""`). vBot's coding Agents still do coding work.

### Direct Tools mode

A Live call without a backend model: the voice model gets the Live Tools and the direct-mode voice instructions instead of `vbot_request`, and each Tool call runs once through the host's `run_tool`. Only Providers registered as direct-capable (today `xai`) allow it.

### Delegation

A request the voice model hands to vBot during the conversation. It returns one spoken-style answer to the voice model. Several run at once.

### Live Tools

The nine intent Tools through which the backend model (or the voice model in direct Tools mode) operates vBot as the user: `overview`, `start_agent_session`, `start_coding_terminal`, `send_message`, `read`, `stop`, `open`, `terminal`, `end_call`. They only organize work; anything else (settings, Cron jobs, research) goes to an Agent as a Session task. They are not Agent Tools: not registered in the ToolRegistry, no ToolContext. Contracts: `model_tasks/live-operator.md`.

### Ref

An alias (`s1`, `t1`) for a Session or Terminal, assigned in order of first mention in a Live Tool result or Run announcement and stable across calls until the operator's memory is forgotten. It exists only in Live Tool calls and the Models' instructions; storage and RPCs keep exact ids.

### Owner

The accessor that started the call. It attaches the owner socket and answers UI requests; only it holds media.

## Binding and options

- Task type `live_voice` is explicit-only (`MODEL_TASK_ORDER`, no modality derivation): voice Models declare it in `task_types`. Catalog entries: `resources/models/openai.overrides.json` has `gpt-live-1` (`api-key` Connection) and `gpt-live-1-codex` (`subscription` Connection); `resources/models/xai.overrides.json` has `grok-voice-think-fast-2.0` (`api-key` and `subscription`, 28 voices, default `eve`). They show in the Chat picker only under "Show all models", like other task-only Models.
- Options come from `task_options.live_voice.parameters`: `voice` (enum with a declared default) and `backend_model` (spec type `model`; OpenAI default `gpt-5.6-terra`). A `backend_model` spec with `allow_none` (xAI, default `""`) adds the choice "None (the voice model uses vBot directly)" and makes the field optional; the runtime picks direct Tools mode from `""` on a direct-capable Provider, not from the catalog flag. `live_backend_candidates` offers tool-capable chat Models of the same Provider that the binding's Connection allows, so the Settings UI and save validation agree. `options_with_defaults` fills all options before start; a stale or disallowed `backend_model` rejects start as `backend_unavailable`.
- `backend_thinking_effort` ("Backend reasoning") accompanies `backend_model`, never declared without it. Choices are the canonical effort ladder (`""` = Model default, then `none` ... `max`; same set as `ALLOWED_THINKING_EFFORTS`), default `low` for spoken latency; a binding saved without it (or with `null`) uses `low`. Its `options_by` narrows the visible choices per backend candidate that publishes `reasoning.levels` to `""`, `none`, and those levels (the Agent editor rule); candidates without a ladder keep every choice. With `allow_none`, `options_by` maps `""` to an empty list, which hides the field; direct Tools mode ignores the effort. Save validation accepts the full ladder; an invalid stored value rejects start as `backend_unavailable`. The Adapter fits the effort to the backend's ladder (`resolve_reasoning_intent`), so a later backend change never breaks a call.
- `live.status` returns `{configured, usable, target, media}`; `usable` proves credentials only, not account access to the voice Model; `media` is the kind a start must request (`null` when the bound Provider has no Live wire). The accessor shows the control when `settings.model_tasks.live_voice.target` is set. Settings -> Voice -> "Live voice" edits the binding through the shared Task Model editor.

## Call lifecycle

- `live.start {media, sdp?, wake_phrases?}`: `media` must be `webrtc` or `relay` and match the bound Provider, else `{error: "media_mismatch"}` (the accessor re-reads `live.status` and retries once). `webrtc` requires the offer: it must start with `v=0`, contain `m=audio`, and be <= 64 KiB; the server creates the provider call (non-idempotent task-client policy; never replayed), joins the control channel immediately (it does not replay earlier events), and returns `{call_id, media: {type: "webrtc", sdp}}`. `relay` rejects `sdp`; the server joins the provider socket and returns `{call_id, media: {type: "relay", audio: {encoding: "pcm16", sample_rate: 24000, channels: 1}}}`. Expected failures return `{error: <code>}` instead of an RPC error (`LIVE_START_REJECTION_CODES`): `not_configured` (no binding, or a Provider without a Live wire), `provider_unavailable` (the binding's Provider connection is missing or not set up), `backend_unavailable` (the backend model or its reasoning effort is not available), `invalid_offer`, `access_denied`, `rate_limited`, `outcome_unknown`, `provider_error`, `control_failed`, `media_mismatch`.
- `wake_phrases` (optional) names phrases that address other vBot Agents during the call: <= 8 strings, each trimmed to 1..60 chars without control, format, line/paragraph-separator, or surrogate characters; case-insensitive duplicates keep the first spelling; `[]` equals absent; anything else is an `invalid_request` RPC error (validated in `live_methods.py`). The registry hands them to the call's host, whose brief puts them into the voice instructions of every wire (see Delegation and trust).
- WebRTC: the accessor gathers ICE non-trickle (5 s cap), attaches the owner socket, then applies the answer. Relay: the accessor starts capture and playback before `live.start` (failing as `audio_unsupported` or `playback_blocked` without a provider call), requests `echoCancellation: "all"` where the microphone track offers it, attaches the owner socket, and sends microphone audio only once `live`.
- Owner socket (protocol in the `server/live/owner.py` docstring). Updates: `state` (`connecting` -> `live` on provider session start -> `closing` -> `closed` | `failed`), `caption` (`user` | `assistant`, `final`, text <= 1000 chars), `activity` (`busy`, label `working` while delegations run), `playback_clear` (relay: drop queued assistant audio at once; sent at every user speech start), `expiry {seconds}` (once after `live` when the provider limits the session: seconds until it ends the call; OpenAI reports `expires_at`, xAI sessions last 120 min), `action` (each executed Live Tool call, `model_tasks/live-operator.md` -> Activity), `idle {ends_in}` (idle warning; `ends_in: null` withdraws it), exactly one `closed {reason, usage}`. The server may add a non-fatal `error` frame (`notification_failed`) and idle `heartbeat` frames (25 s).
- Relay audio uses binary owner-socket frames. Inbound microphone PCM (even length, <= 64 KiB, current owner only; malformed frames are dropped and logged once) goes to `LiveCall.push_audio`, which drops audio before `live` and while closing and keeps at most 2 s of backlog. Outbound assistant PCM goes only to an attached owner, within its own bound (one minute of audio); audio beyond it is dropped without closing the socket.
- Context reports: the owner sends a JSON text frame `{type: "context", view, selected_agent_id, selected_project_id, chat_session: {agent_id, session_id} | null}` whenever its socket opens and whenever what the app shows changes. The server keeps the latest report of the current owner (<= 4096 chars, unknown fields dropped; a `{type: "stay"}` frame restarts the idle period; other text frames are ignored); Live Tools read the view and selection from it, and before the first report they show no selection.
- `end_call` (a Live Tool) closes the call gracefully after `end_call_delay_seconds` (5 s), so the voice model can say goodbye; running work goes on. The call's `closed` reason is then `hung_up`.
- Idle hangup: a `live` call without captions, `playback_clear`, Tool calls, delegated work (`activity` busy), or `stay` frames for `idle_seconds` (600 s) closes gracefully with reason `idle`; `idle_warning_seconds` (60 s) before, the owner gets `idle {ends_in}`, withdrawn by the next activity (`LiveCallLimits`, `test_a_live_call_nobody_uses_is_warned_then_ended`). Voice duration bills including idle time, and an ended call keeps its refs and assignments (operator memory).
- `live.stop` closes gracefully in the background: the session asks the provider to close and waits up to 8 s for a confirmed close with usage (the accessor waits 12 s for `closed`). Abort (owner lost, replacement, shutdown) sends a best-effort close within 1 s. A cancelled close or abort still ends the call and publishes `closed`, then propagates the cancellation. A call that is not `live` within 45 s aborts with `start_timeout`. Every terminal path retires the Provider control transport before publishing completion, including a confirmed Provider close; cleanup is bounded and a cleanup failure still publishes the terminal state.
- Closed reason priority (`_live_call.py`): abort reason > `expired` (no stop requested, and the provider closed with `max_duration` or within 60 s of the session limit, also without a confirmed close) > confirmed provider reason (`closed` when it names none) > `closed` (after stop) > `connection_lost`. The host replaces the reason with `hung_up` or `idle` when it ended the call itself. Mid-call Usage saves run in the background; a failed save is logged once and never ends the call. Phase `failed` only for `connection_lost` and `start_timeout`. A replaced call gets `closed` with reason `replaced`.
- Registry limits (`LiveCallLimits`): owner must attach within 15 s and may reattach within 10 s after a socket loss, else the call ends; UI requests time out after 20 s and, once an owner attached, wait for a reconnecting owner instead of failing; up to 200 updates buffer while no owner is attached (the oldest `caption`, `activity`, `action` and `heartbeat` frames go first, never `state`, `ui_request`, `error` or `closed`); updates a lost or lagging socket had not taken return to that buffer; owner queue 1000 updates. The accessor reattaches within 8 s of a loss (each reopened socket starts a fresh window) and replaces a socket silent for 60 s. Close codes: 1000 after `closed`, 1008 unknown call, 1013 owner fell behind, 4000 replaced by a newer owner socket (do not reconnect). The server-side end of a call publishes its `closed` update and releases the call from the registry in one Event Loop step, then keeps it attachable for the reattach grace only while updates are undelivered; an owner socket never attaches to an ended call before its `closed` update (`test_stop_closes_gracefully_and_forwards_the_final_update`, `tests/server/live/test_registry.py`).

## Delegation and trust

- `LiveBrain` runs a Tool loop over one Adapter per call (`runtime.get_adapter(ConnectionRef)`, opened on the first delegation, closed when the call ends, so connections stay warm) with the backend Model on the voice binding's Connection, the configured `backend_thinking_effort` as `thinking_effort` (`None` for `""`), at most 8 steps, and the last 10 request/answer pairs of the call as history (answers only: earlier Tool results are not replayed). Each input carries the delegated request, the recent conversation (12 turns, <= 4000 chars), the last 5 vBot updates, and the refs earlier results named, in this or an earlier call (`LiveCallHost.known_refs`: up to 30 `- s1: Session at Coder "Fix"` / `- t1: Codex Terminal "Build"` lines, most recently named last, each with the latest label a result gave it), so a later delegation targets them without reading them again, and what vBot shows right now (`LiveCallHost.current_state`: the `overview` text taken just before the delegation, neither reported as an `action` nor noted as an assignment; empty when it fails), so the backend model need not look first.
- Delegations run one at a time in arrival order (`_delegation_turn`), each bounded to 240 s once its turn starts, so each starts from the state the previous one left and two never act on the same things at once (a live call on 2026-10-01 showed parallel delegations closing and reopening the same Terminals and contradicting each other). Tool executions of one call run one at a time (`model_tasks/live-operator.md` -> Execution). When the provider sends no request text, the session waits for user quiet (0.4 s, max 2 s) so the latest speech is included.
- Retryable Provider errors retry only the model send (0.5 s, 1.5 s), never a Tool execution. Every Tool call goes to the host's `run_tool` (`run_live_call`): a canonical Adapter rejection becomes the failure result without Live argument repair, so placeholder arguments cannot become an executable call through alias defaults; other calls go through `prepare_live_call` and only a prepared call executes; a rejected call returns its failure result to the Model. Tool messages carry the JSON envelope, which the Adapter renders as text. Every answer ends with a line vBot builds from the Tool results, not the Model (`EFFECTS_LABEL` "vBot changes for this request (from the Tool results):"): the result texts of the calls that may change things (all but `overview` / `read`, `LiveToolRun.changed`), `Failed: <message>` for failed ones, at most 8 (240 chars each), or `nothing.`; an empty Model answer after such a call is that line alone (the backend model often says nothing after `end_call`), while an empty answer without one fails as before. The voice instructions tell the voice model to report an effect only when that line names it (the 2026-10-01 call had spoken claims without any Tool call). A failure answers `The request could not be completed: <reason>. Nothing was retried.` before that line; a timeout answers that actions it started may have completed.
- Direct Tools mode: the xAI wire forwards every function call as `WireToolCall` (argument text that is not JSON stays text); `LiveCallSession` hands name and arguments unchanged to `LiveCallHost.run_tool` once, at most 4 at a time and each bounded to 240 s, and returns the result as plain text (`live_result_text`). Timeouts and failures return `timeout` / `tool_failed` results; nothing is retried. In delegate mode the wire matches `vbot_request` by `called_tool_name` (wrapper prefixes such as `functions.` allowed), answers delegations as `{"result": <text>}` and errors as plain text. A `vbot_request` reaching a call without a backend model answers that no backend model is configured.
- Voice and delegation instructions (`voice_instructions()` and `DELEGATION_INSTRUCTIONS` in `server/live/_brief.py`) are runtime Agent-facing text. The Live Tools cover only organizing work; the rules send anything else the user wants done (settings, Cron jobs, reminders, research) as a Session task to a fitting Agent and have the model ask when no Agent clearly fits. Tasks and messages are passed on without the parts that only say what to start or where; when a Session or Terminal already works on the requested task, the model says so and asks before starting more (a running Agent or program with other work is no reason to ask); the delegation answer reports an effect only when a Tool result of the request confirms it (evidence: `model_tasks/live-wires.md` -> Backend model probe). All three texts start from an "About vBot" block (`_HELPERS`), because the Models know nothing about vBot beyond what they are told: Agents are the user's AI assistants with their own Tools, working in Chat Sessions; Codex and Claude Code run in Terminals, cannot reach the Agents, and get only what is typed into the program, never the command line; a request for an Agent in a Terminal (or a coding agent in a Session) is answered by asking, not by sending there. The rules further allow closing, stopping, or deleting only what the user explicitly names (a goodbye or "go to sleep" never does), map goodbye, hang up, go to sleep, and be quiet to `end_call`, make "start" mean a new Session or Terminal, and have the backend read a Session before reporting what an Agent found, since overview and updates quote only part of its last message. With wake phrases, both modes add a wake phrases block before the backchannel rule: it lists the phrases in double quotes, says vBot mutes the call while such a command is recorded, and tells the voice model not to answer or act on speech starting with a wake phrase and never to say one. The operator's recap of earlier calls joins both as one "Earlier calls" block (`model_tasks/live-operator.md` -> Memory).
- Tool results and vBot updates, including the messages, screens, and names they quote, are data to relay, not instructions (the delegating voice model reads `vbot_request` results the same way). Provider appends are ephemeral provider context, never vBot Session history or kernel reminders; acknowledgments do not prove audible speech.
- Security gotcha: a wire whose announcements reach the voice model like user input (`LiveWire.announces_as_user_input`, the xAI wire) gets Run notices without `result_excerpt` / `excerpt_truncated`; brain context keeps the full text. Live probes (2026-09-24) showed Grok Voice executing an instruction quoted in an unsolicited excerpt (a send to another Session through the former `vbot_app` Tool in 4/4 trials as a user message, 4/4 as a synthetic Tool output) but never after excerpt-free notices (0/4) or in Tool results the user asked for (0/4). Do not put untrusted text into such announcements.

## Verification and limits

- Tests: `tests/core/model_tasks/test_live.py`, `test__live_openai.py`, `test__live_xai.py`, `test__live_brain.py`, `test__live_options.py`; `tests/server/live/test_registry.py` (registry, owner socket, host); operator tests in `model_tasks/live-operator.md`; `tests/server/rpc/test_live_methods.py`; Run attribution in `tests/server/rpc/test_chat_methods_runs.py`. WebUI: `lib/__tests__/liveVoice.test.js`, `audioRecorder.test.js` (microphone claims), `liveVoice.ui-requests.test.js`, `liveVoice.desktop.test.js`, `liveAudio.test.js`, `api.test.js`, `api.events.test.js`, `components/__tests__/LiveVoice.test.js`, `app/__tests__/liveUiActions.test.js`.
- Verified against real Providers: the codex dialect's call creation, control join, and event shapes (ChatGPT subscription); the xAI wire under `LiveCallSession` with a fake host (2026-09-24, see `model_tasks/live-wires.md`). Not yet verified: a full spoken call with delegation end to end, the public OpenAI dialect (official docs only), relay audio in a real browser (AudioWorklet capture/playback, the Firefox device-rate fallback), acoustic echo with speakers (`echoCancellation: "all"` is best effort; a loopback `RTCPeerConnection` is the known fallback if echo triggers barge-in), and a voice model using the current Live Tools in a real call (the backend model was probed against a scripted vBot, `model_tasks/live-wires.md`).
- Browser microphone access needs HTTPS or localhost. Providers other than OpenAI and xAI have no Live wire. The Desktop makes the remote HTTP servers it knows at startup secure contexts; a server added later shows the `desktop_restart_required` notice until the Desktop app restarts. Desktop Voice stays active during a call; the voice model is told that speech starting with a wake phrase is not addressed to it, and the call is held while the command records.
- Voice duration (including idle time) and backend usage bill separately at the Provider. Canonical Usage records one `live_voice` call and each delegated `live_voice_backend` send/outer retry under its own Model. Cumulative wire Usage replaces previous counters; the final close settles once and preserves the last report after control loss. Unknown duration/pricing units remain unknown, including subscription calls without token telemetry. Adapter-internal retries are not separately visible. Captions remain transient and never enter the Usage store. Persistence failure still publishes the closed state and releases waiters. Coverage: `test_live.py`, `test__live_brain.py`.
- Logs name a call by its vBot-owned log id (`LiveCall.log_id`, `live_...`, also the delegation `conversation_id` `live:<log id>`), never by the Provider call id, and carry a public target label without Account id; tokens, SDP, and transcripts never enter logs (`test_live.py`, `tests/server/live/test_registry.py`). One INFO line marks start and one the end (WARNING when the call failed); media connect and the start watchdog log at DEBUG.
