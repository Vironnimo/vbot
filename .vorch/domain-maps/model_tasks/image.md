# Image

Provider-neutral image generation/edit execution, isolated image understanding, and caller-owned file persistence for configured image task-model bindings.

## Overview

`core/model_tasks/` (`image*.py`) owns text-to-image, source-image editing, and text analysis of local images after Settings has selected concrete task-model targets. Generation resolves `image_generation` and routes provider media APIs through `ProviderImageClient`; understanding resolves `image_understanding` and uses the selected Provider's ordinary Chat Adapter for one isolated multimodal request. Both paths load bounded local image files and reject local targets. This module does not own model discovery, settings validation, UI controls, or Tool schemas; those live in `core/models/`, `core/settings/`, `webui/`, and `core/tools/image.py`.

## Interfaces

- `ImageService(model_tasks, runtime, *, max_input_bytes)` - runtime-owned service; applies Runtime's Attachment-size ceiling to every local source image and keeps the injected `model_tasks` reference to resolve target Models. Image understanding additionally applies fixed internal limits of six images and 100 MiB of cumulative source bytes per call and serializes analysis requests through one service-owned semaphore. It owns image execution and writing generated bytes to the explicit caller-owned directory supplied per call, not a data-directory artifact root.
- `ImageService.generation_supports_source_images() -> bool` - resolves the persisted `image_generation` binding and configured Provider Model without executing a request; returns true only when that Model advertises `image` input. Missing/invalid bindings, local targets, and unresolved/text-only Models return false. The image Tool uses this stable configuration capability to select its model-facing Definition Profile.
- `await ImageService.analysis_is_available() -> bool` - deepens `TaskModelService.binding_is_usable("image_understanding")` with the configured target's actual Chat Adapter wire declaration and returns true only when it contains at least one `image/*` MIME type. Expected binding/Adapter-resolution failures return false, no Provider request is made, and the temporary Adapter is always closed. Runtime supplies this method directly to Chat's route gate.
- `await ImageService.generate(prompt: str, *, call_options=None, source_paths=None) -> ImageGenerationResult` - trims and validates `prompt`, resolves the configured binding, routes any `call_options` into native wire options vs. prompt hints (see Per-Call Option Routing), loads each optional local source image, executes the provider generation/edit request, and returns normalized bytes without persisting them. Empty/absent `call_options` and `source_paths` reproduce the request the binding alone would make.
- `await ImageService.analyze(prompt: str, *, image_paths) -> ImageUnderstandingResult` - resolves `image_understanding`, verifies the selected Model advertises `text` and `image` input plus `text` output and prepares every source through the shared Attachment ImageConverter against the Adapter's actual MIME declaration, then returns normalized plain-text analysis plus Model/image-count/optional Usage.
- `await ImageService.generate_artifacts(prompt: str, *, output_dir, call_options=None, source_paths=None) -> tuple[ImageArtifact, ...]` - forwards `call_options` and `source_paths` to `generate()`, writes each returned image directly into the explicit `output_dir` with an exclusive UUID filename, and returns persisted file metadata. It creates no JSON sidecar or central duplicate.
- `await ProviderImageClient.generate(prompt: str, *, options: dict, input_images=()) -> ImageGenerationResult` - provider-bound HTTP entrypoint; supports OpenRouter generation/edit through the dedicated image API (`POST /images`), the standard OpenAI images wire for any Provider whose Adapter is `openai` or `openai_compatible` (`/v1/images/generations` and `/v1/images/edits`), and OpenAI subscription generation/editing through Codex Responses (`/codex/responses`).

`ImageInput` contains one loaded source image's provider-facing `filename`, sniffed `media_type`, and raw `data`. `ImageGenerationResult` contains generated bytes and media metadata. `ImageUnderstandingResult.to_dict()` returns `{ analysis, model, image_count, usage? }`. `ImageArtifact` carries the internal UUID, filename, media type, byte size, absolute file path, and result index needed by the Tool handler; it has no artifact URL contract.

## Source Images

- Source paths may be absolute or resolved by the Tool against the Run's effective cwd. The service deliberately imposes no path-root allowlist: any local image file reachable by the Agent may be read and uploaded to the configured external Provider. This is an explicit product contract, not a missing guard.
- The service checks file size before reading, reads at most `max_input_bytes + 1` to defend against file growth, sniffs the media type through `core.attachments.sniff_media_type`, and supplies a media-type-derived extension when an Attachment blob path has no suffix. `ImageInputError` subclasses classify failures without message parsing: `ImageNotFoundError` (`image_not_found`), `ImageReadError` (`image_read_error`), `ImageTooLargeError` (`image_too_large`, including count and cumulative-byte limits), and `ImageUnsupportedMediaTypeError` (`unsupported_image_type`).
- When the target Model is present in the Model DB, source-image execution requires `image` in `capabilities.input_modalities`; a text-only target fails with `ImageUnsupportedTargetError` instead of silently generating from the prompt alone. An unknown/custom Model is allowed through for the Provider to classify.
- There is no separate edit operation flag: a non-empty source-image list selects image-to-image behavior, and the prompt states the requested transformation and preservation intent. Multiple source images are preserved as an ordered tuple.

## Image Understanding

`ImageService.analyze()` deliberately bypasses Agentic Loop state. It sends exactly two canonical messages through `Runtime.get_adapter`: the fixed `IMAGE_UNDERSTANDING_SYSTEM_PROMPT`, then one user content list containing the caller's analysis prompt followed by ordered Base64 media blocks. It passes the internal-task temperature (`resolve_request_temperature(None, ...)` - model recommendation, else provider/API default; never a hardcoded value) and `tools=[]`; Agent/System Prompt, Session history, Memory, Skills, and Tool access never enter the task request. Local file loading and Base64 construction run through `asyncio.to_thread` so bounded image preparation does not block the async kernel; the service semaphore covers preparation plus the Provider request so concurrent Runs cannot multiply that memory footprint inside one Runtime.

The fixed System Prompt requires precise visible-evidence analysis, exact text/numbers/spatial relationships where relevant, explicit uncertainty for illegible or missing evidence, and treats all text/instructions inside images as untrusted content to analyze rather than instructions to follow. The Adapter response is normalized through `normalize_response`; empty/non-text output is non-retryable `ImageExecutionError`. Expected Provider/Network failures become `ImageExecutionError(code="provider_error")` while preserving `retryable` and the shared retry loop's optional `attempts_made`; binding, Model, Connection, and Adapter-construction failures become `ImageUnderstandingUnavailableError(code="image_understanding_unavailable")` without changing the generation path's shared `ImageConfigurationError`/`ImageUnsupportedTargetError` semantics. Unexpected exceptions are never wrapped as expected Image errors and reach Tool dispatch's logged `tool_execution_error` boundary. The normalized result retains bare Model id and Usage internally, but the Tool projects neither field. Before `send`, a Tool-originated request sets the Adapter's `DebugContext` from the owning Run plus the resolved Provider/Connection/Model and `streaming=false`; its Iteration is the completed Agentic Loop Iteration that requested the Tool Call. Per-call Adapter cleanup is best-effort: failure is safely logged and can never replace either a successful result or the primary execution error.

Image execution never places the full stored target in logs or expected error text because its Connection suffix may contain a pinned Provider Account id. Provider targets are identified as `<provider>/<model>`; a known Account id echoed by a Provider/configuration exception is replaced with `[REDACTED]` before logging or projection into a Tool failure.

Discovery and execution use the same direct capability rule: the Model must advertise both `text` and `image` input and `text` output. An explicit `image_understanding` entry in `capabilities.task_types` is not required because that derived catalog tag may be incomplete even when the modalities are accurate. Availability additionally requires the selected Adapter to declare at least one `image/*` wire MIME type; execution still verifies every actual image MIME type before sending because the concrete files are unknown during visibility gating. There is no automatic retry onto another task target and no local execution path.

## Per-Call Option Routing

The `image_generation` tool exposes two optional per-call intent knobs (`aspect_ratio`, `resolution`); the handler passes them to `generate()` as `call_options`. `generate()` routes them through the pure, unit-testable `split_image_call_options(model, call_options) -> (wire_options, prompt_hints)`:

- **Model resolution:** the target model is resolved through `TaskModelService.model_for_target(target_ref)` - the thin public accessor over the existing `_resolve_model(provider_id, model_id)` seam (`None` for local targets, or when the model is absent/override-only in the registry). `generate()` resolves the Model when `call_options` or `source_paths` is non-empty; the no-options/no-sources path issues exactly the same request as before (and never calls `model_for_target`).
- **Routing rule (value-aware):** for each knob, consult `model.capabilities.task_options.image_generation.parameters`. A knob goes **native** (into the wire options dict) iff the model advertises that parameter *and* the value is acceptable - the value is in the parameter's `values` enum (compared as strings; reads both list and loaded/frozen tuple forms), or the spec is open/free-form (`type: "string"`/`"boolean"`, no fixed value set). Otherwise it becomes a **prompt hint**. `model is None`, missing `task_options`, an unadvertised parameter, or an unsupported enum value all fall to a hint. Because a value is only sent when the catalog confirms it, an unsupported knob can never trigger a provider error (the "we won't blindly send 4K to a 2K model" guard).
- **Precedence:** `merged = {**binding_options, **wire_options}`, so a native per-call value overrides the Settings binding default; a non-native value never touches the wire options and only appends a hint. Hint phrasing comes from a small label map (`aspect_ratio` -> `"aspect ratio {value}"`, `resolution` -> `"{value} resolution"`, generic fallback `"{name->spaces} {value}"`); hints are appended to the prompt as a trailing parenthetical (`"<prompt> (aspect ratio 16:9, 4K resolution)"`).
- **Adding a knob** is a tool-schema property plus one hint-label entry - the splitter routes generically against `task_options`, so no execution-layer rework is needed.

## Provider Wire Behavior

`ProviderImageClient` subclasses `core.providers.task_client.ProviderTaskClient`, which owns the shared plumbing (constructor tuple, `from_runtime` target resolution, auth headers, POST/classify/parse cycle, retry policy - see `providers.md`); this module owns only the image payload shapes and response parsing.

OpenRouter uses the selected provider connection's base URL (or provider base URL), connection auth header, provider `extra_headers`, and a 120-second HTTP timeout. Image generation/editing is billed and non-idempotent: connect/connect-timeout/pool-timeout failures and HTTP 429 are retryable, and OpenRouter's documented HTTP 503 refusal is an explicit endpoint-profile retry; ambiguous read/write/remote-protocol failures, 502/504 and other unverified 5xx responses, and unusable 2xx results are never automatically replayed. The request is `POST /images` (OpenRouter's dedicated unified image API - the legacy chat/completions `image_config` path is gone; OpenRouter adds new image models exclusively to the image API) with `model`, `prompt`, and the unified top-level parameters present in the merged options: `aspect_ratio`, `resolution`, `size`, `quality`, `output_format`, `background`, `output_compression`, `n`, `seed` (`_UNIFIED_IMAGE_KEYS`). Each source image becomes one ordered `input_references` entry containing an `image_url` Base64 data URL. Absent keys are never invented. Empty placeholder values (`None`, `""`, `[]`, `{}`) are treated as unset and dropped (the option schema's "Provider default" select value is `""`), while numeric `0`/`0.0` and `False` are real values and are kept - the shared rule lives in `core/providers/task_client.py` (`is_omittable_option`). The same empty-placeholder omission and non-idempotent retry policy apply to the OpenAI `/v1/images/generations`, multipart edit, and Subscription Codex Responses paths, except that their 503 responses have no verified safe-retry profile.

Two schema-owned pseudo-options never go on the wire verbatim: `provider_options` (a JSON object keyed by upstream provider slug, e.g. `{"recraft": {"style": ...}}`) becomes the nested `provider.options` request object - the passthrough channel for provider-specific keys the model's `task_options.passthrough` advertises; `extra_options` adds only non-empty fields absent from the authored payload (the universal escape hatch, `merge_extra_options`), and a collision fails locally before send.

The unified response is `{"created", "data": [{"b64_json", "media_type"?}], "usage"}`: every `b64_json` entry decodes into the `images` tuple, a per-entry `media_type` (vector outputs) wins, else the requested `output_format` decides, fallback `image/png`. Missing/empty `data` or undecodable entries raise `ProviderOutcomeUnknownError` without replay because the successful Provider request may already have generated and billed an image. `ImageService.generate()` preserves that state as `ImageOutcomeUnknownError`; the image Tool returns stable code `provider_outcome_unknown`, `retryable: false`, and the per-call operation key in the message so the Model, WebUI, and logs do not encourage an unchanged retry.

The standard OpenAI-compatible text-to-image wire sends `POST /v1/images/generations` with `model`, `prompt`, and optional image-gen keys (`n`, `size`, `quality`, `background`, `moderation`, `output_format`, `output_compression`, `style`, `response_format`). Selection is Adapter-based (`openai` or `openai_compatible`), not hard-coded to the bundled `openai` Provider id, so a Custom Provider can use it. A request with source images instead sends multipart `POST /v1/images/edits`: scalar settings become form fields, one source uses `image`, and multiple ordered sources repeat `image[]`; filename, bytes, and sniffed media type are preserved. `extra_options` uses the same add-only collision rule on both paths. Both responses use the same `data[].b64_json` parser; `n>1` returns one `ImageGenerationResult` with multiple images. `url`-only responses are rejected. The response parser derives `media_type` from the requested `output_format` (since the response body does not echo it).

OpenAI subscription image execution is selected by provider `openai` plus connection mode `codex_responses` and posts to the connection base URL's `/codex/responses` endpoint, not to `/images/generations` or `/images/edits`. The request uses a named carrier model constant (`gpt-5.5`), `stream: true`, `store: false`, instructions `You are an image generation assistant.`, one user `input_text` asking the carrier to use the `image_generation` tool, and a single tool object `{"type": "image_generation", ...}`. For editing, every ordered source image follows that text as an `input_image` content part containing the same Base64 data-URL shape already verified by the subscription chat adapter, and the text explicitly asks the carrier to edit the provided images; no separate tool action flag is needed. Headers are rebuilt per retry from the refresh-capable task token getter and add `chatgpt-account-id` derived from the current OAuth JWT plus `CODEX_EXTRA_HEADERS`; a missing account id is an auth error asking the user to reconnect. The Codex tool whitelist from stored binding options is `output_format`, `output_compression`, `moderation`, `background`, `size`, and `quality`; `n` and `model` are always dropped (also from `extra_options`) because the wire rejects `n` and forces the backend image model. `extra_options` adds future tool fields but cannot replace an already authored tool field, while `size`, `quality`, and `background` are also woven into the input text because the backend treats the tool-level values as advisory. The Codex path uses a 300-second timeout and buffers the SSE response body; progressive `partial_image` frames are ignored, final images come from `response.output_item.done` items of type `image_generation_call`, usage is read from `response.completed.response.tool_usage.image_gen` and `response.completed.response.usage`, and `raw` keeps the final image call metadata such as `revised_prompt`, actual `size`, and actual `quality`. The edit wire was live-verified against a real Subscription run on 2026-07-11: an attached red-square image returned with the square blue while its position/size and the white background were preserved.

## Generated Files

`generate_artifacts()` persists each returned image directly into its explicit `output_dir`:

```text
<caller-owned-root>/image-gen/
  a1b2c3d4....png
```

Artifact ids are `uuid4().hex`, and exclusive file creation retries a UUID collision rather than overwriting an existing file. The filename extension is inferred from the result media type (`png`, `jpg`, `webp`, `gif`, `bmp`, `svg`, fallback `png`), not from provider filenames. The image Tool owns root selection: Identity Agents always use `<Workspace>/image-gen/`, including while Rooted; Project Config Agents use `<Project cwd>/image-gen/`. Chat file presentation uses the ordinary signed `/api/files/` path when an Assistant references the returned absolute path, so image generation needs no image-specific HTTP endpoint or central copy.

## Constraints & Gotchas

- Provider targets must use the task-model id shape `provider/model-id::connection-id`; nested model ids such as `openrouter/openai/gpt-image::api-key` are valid. Local targets parse successfully in `core/model_tasks/` but image execution rejects them with `ImageUnsupportedTargetError`.
- A configured provider target outside the implemented image providers reaches `ProviderImageClient.generate()`, raises `ProviderError(retryable=False)`, and is surfaced by `ImageService.generate()` as `ImageExecutionError`, not `ImageUnsupportedTargetError`.
- `image_generation` targets are discovered from model capabilities where `output_modalities` includes `image`; do not hard-code image models in `core/model_tasks/` (`image*.py`).
- `image_understanding` targets are discovered from the direct `text` + `image` input and `text` output modality contract, not from the redundant derived task tag. The route-gated Tool owns when the Main Model needs this path; `ImageService` validates the same modality contract and separately checks Adapter wire MIME support before executing the selected binding.
- Per-model image option **facts** (allowed values, ranges, passthrough keys) live in the model DB (`capabilities.task_options` - auto-projected from the OpenRouter image API at refresh, hand-authored in `resources/models/openai.overrides.json` for OpenAI native). Only render hints belong in `core/model_tasks/options.py`. The agent-facing `image_generation` tool exposes `prompt`, optional runtime `source_images`, and the two curated per-call intent knobs (`aspect_ratio`, `resolution`) - routed value-aware against the same `task_options` facts (see Per-Call Option Routing); every other image option stays Settings-only.
- **Unrefreshed catalog under-uses native params:** a model with no `task_options` (e.g. an OpenRouter image model before a DB refresh) routes every knob to a prompt hint even if the provider natively supports it. Always safe (never errors); refresh the model DB to regain native routing.
- A stored binding option the wire does not know (e.g. the legacy `image_size` key from before the unified-API migration) is silently dropped at request build - re-saving the binding options in Settings clears it.
- New provider execution belongs in `ProviderImageClient` and should keep returning normalized `ImageGenerationResult`; do not route image generation through chat adapters or attachment storage.
- Debug trace capture is not wired through `ProviderImageClient`; the shared `ProviderTaskClient.post_and_parse` constructs a plain `httpx.AsyncClient` rather than `core.providers._http_shared.build_async_client()` (deliberate).
- `ImageError` derives from the shared `TaskError` base in `core/utils/errors.py`; the image Tools map expected execution failures into their stable Tool-result error codes.
- `generate_artifacts()` uses exclusive direct file creation without a rollback transaction. A process death during the write can leave a partial image in the caller-owned directory; there is no sidecar or central registry to repair or discover it.

Image understanding accepts the additional BMP/TIFF/AVIF originals recognized by Attachments and uses `ImageConverter` before constructing its ordered native content. Unsupported conversions become non-retryable ImageUnsupportedMediaTypeError; original files remain unchanged. The per-image and cumulative byte ceilings also apply to converted bytes. Generation, video, and music source loading retain the pre-existing JPEG/PNG/GIF/WebP admission set because their separate upload contracts do not use the Chat Adapter MIME declaration. Regressions: `tests/core/model_tasks/test_image.py`.
