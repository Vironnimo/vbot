# Live voice wires

Read when changing the OpenAI or xAI Live wire, adding a Live provider, or probing the backend. The provider-neutral contract (`LiveWire`, normalized `Wire*` events, media descriptors) is `core/model_tasks/_live_wire.py`; registration in `_PROVIDER_WIRES` (`live.py`) is described in `model_tasks/live.md` -> Ownership.

## OpenAI wire (`_live_openai.py`)

- The Connection mode picks the dialect: `codex_responses` (ChatGPT subscription) -> codex, otherwise public API.
- Codex: `POST <codex base>/codex/realtime/calls?intent=quicksilver&architecture=avas` with `{sdp, session}` (model, instructions, voice, `delegation`, see below); headers add `OpenAI-Alpha: quicksilver=v2`, `originator: vbot`, the Account id, and fresh session/thread ids. The SDP answer is the body; the call id comes from `Location`. Control: `wss://api.openai.com/v1/live/<call_id>` with the same headers. Delegations carry request text; results use `delegation.context.append` and announcements `session.context.append` (channel `speakable`, <= 500 bytes per append).
- Public: `POST /live/sessions` returns `{session: {id}, transport: {sdp}}`; the page's data channel is locked to no events. Control: `<base>/live/sessions/<id>/attach`. Delegations carry no text; results and announcements use `session.commentary.append` (<= 1500 bytes per append). Transcripts come from `session.input_transcript.delta` / `session.output_transcript.delta`.
- Delegation (both dialects): with backend `vbot`, `{type: "client"}`, and every delegation arrives as a `WireDelegation` that vBot answers. With backend `openai`, `{type: "responses", responses: {model, instructions, tools}}` (`OpenAIBackend`; `tools` as `{type: "function", name, description, parameters}`): OpenAI's hosted backend model answers and calls vBot's function Tools. A finished function call is read from `response.output_item.done` / `delegation.output_item.done` (an item of type `function_call`), `response.function_call_arguments.done` or `delegation.function_call` (flat), also inside the wrappers `response.event`, `delegation.event`, `delegation.response.event` (two levels); each call id becomes one `WireToolCall` once. Its output goes back as `response.item.create` with a `function_call_output` item, and once every open call has an output, `response.create` lets the hosted model continue. These shapes follow the docs and are not verified live.
- Call ids must match `^[A-Za-z0-9_-]{1,128}$`. Audio frames on the control channel are dropped unparsed.
- Verification: the codex dialect's call creation, control join, and event shapes were probed against a ChatGPT subscription; the public dialect follows the official docs only (OpenAI guides `live`, `voice-webrtc?api=live`, `live-delegation`, `live-conversations`, and `voice-server-controls?api=live` at `https://developers.openai.com/api/docs/guides/`).

## xAI wire (`_live_xai.py`, `_live_xai_session.py`)

- `XaiLiveWire` (`_live_xai.py`) owns the socket: `wss://api.x.ai/v1/realtime?model=<id>` with the Connection's auth header; handshake HTTP 401/403 go through the shared OAuth request recovery. It drives the sans-IO `XaiSession` (`_live_xai_session.py`) with socket frames, commands, and timer ticks and sends each step's client events under one lock. The SuperGrok subscription token is accepted (live-verified); the `api-key` Connection is not live-verified. xAI has no WebRTC endpoint, hence relay media.
- Right after connect, `session.update` sets instructions, voice, `server_vad` (threshold 0.85, prefix 333 ms, silence 500 ms), PCM 24 kHz in and out, input transcription `grok-transcribe`, and the voice Agent's Run Tools as function Tools (its Tools, plus `vbot_request` with backend `vbot`). Every function call becomes one `WireToolCall` (the voice Session resolves the name and the call prepares the arguments); its output is the result's plain text. `session.updated` starts the call (`WireStarted`, 120 min lifetime).
- Response gate: vBot sends `response.create` only for its own additions (Tool outputs, announcements) that no completed response covered, and only while no response is pending or active, the user is not speaking, every function call of the last completed response has output, and the estimated playback has drained (+0.2 s). One create covers all pending additions. A create without `response.created` is retried once after 5 s; an "active response" error backs off 1 s; a response silent for 30 s stops blocking and is fenced like a barge-in.
- Barge-in (`input_audio_buffer.speech_started`): emits `WirePlaybackClear`, truncates each unplayed assistant item at the estimated played milliseconds (`conversation.item.truncate`), fences that response so late output is dropped and its function calls never run, even when it later ends `completed` (each gets an `interrupted` output), and keeps the caption text received so far (the provider's truncated transcript is unreliable).
- Captions: user transcription snapshots are cumulative; only `.completed` with `status: "completed"` is final. Duplicate event families (`output_audio*` and `audio*`, transcript and text) lock to the first carrier per item.
- Announcements are user text messages: Grok Voice ignores system messages added mid-conversation (live-verified; it repeated its previous answer). The echoed item does not finish the user's open caption. This is why the xAI wire announces like user input (`model_tasks/live.md` -> Instructions and trust).
- No session close event exists; closing the socket ends the session. `usage` is empty on subscription sessions, so `closed.usage` stays `null`. Error types `max_duration` / `timeout` close the call.
- Numeric `response.done` Usage contributes once per Response id for the whole call, using `response.id` or the envelope's `response_id`. Repeated or delayed completions of that id emit no additional Usage; different Response ids still accumulate. Synthetic duplicate events are covered by `test__live_xai.py`, including the final close totals. This proves local idempotency, not the frequency of duplicate events from xAI.
- Verification (2026-09-24, development subscription, scratch probes outside the repo): the real `XaiLiveWire` under `LiveCallSession` with a fake host took a spoken German question as relayed PCM, ran the former `vbot_app` `context` then `sessions` (direct Tools mode) or one `vbot_request` (delegate mode), and spoke the answer in German; a Run announcement was spoken afterwards. An earlier raw-socket probe confirmed that `conversation.item.truncate` at the estimated played milliseconds is accepted during barge-in.

## Backend probe

`scripts/probe_provider_tool_call.py --scenario live_tools` gives voice-style requests (`scripts/provider_probe/live_cases.py`) to the Model with what the Live backend Agent gets in a call: its Live call instructions (`backend_instructions(has)`), the System Reminder before the request (the context note with the scripted vBot's overview), and the Live Tools with their argument preparation. It runs its own small Tool loop (at most 4 steps) instead of a Chat Run, so the rest of the Agent's System Prompt and its web Tools are missing. A scripted vBot answers, so nothing in vBot changes. The verdict judges the first Tool call (`ideal`, `lookup` = a valid read-only call first, `wrong`, `error`); a text argument can also be required to leave out request parts (`Contains(..., without=...)`, such as the program a task was passed on with). An answer that reports a start, send, or stop although no Tool call changed anything counts as an unconfirmed claim and fails the trial (a word heuristic; check flagged answers). `--live-case`, `--repetitions`, `--live-report` (transcripts). Offline smoke test: one `live_tools` case in `tests/scripts/test_provider_probe.py`. Paid; ask first. The runs below probed the former backend (its own Tool loop with the former delegation instructions and the Tool names `read` and `terminal`); the current instructions keep their rules, and no run has probed them yet.
- Run 2026-10-01 (ChatGPT subscription, `gpt-6-luna` medium, 11 cases): every first call was right, but `sessions_count` claimed three starts it never made (3/3, when the fixture already showed three Coder Sessions on the same topic), and `codex_task` passed the whole sentence including "Start codex in vBot" on as the task. The rules on passing on only the task, asking when vBot already shows the requested work, and confirming effects by Tool results came from this run.
- Second run 2026-10-01 (same target, 13 cases x 2, the probe passing the overview as the request's state like a real call): 24 ideal, 2 lookups, 0 wrong, 0 unconfirmed claims. Before the final wording, "tell the Researcher in the Codex Terminal ..." typed the task into Codex (2/2) until the About vBot block said to ask instead; with the state given up front, "Start codex ... and fix the test" was sent to the running Codex until the "start means new" rule; an excerpt-only Reviewer result was half-guessed until the rule to read cut quotes; and `end_call` was followed by an empty answer that counted as a failure (3/3) until empty answers after a change became the effects line.
