# Project Sources

Read for adapters, discovery, translation, source priority or findings.

## Ownership and inputs

`core/projects/sources/` is an internal part of Projects. `profile.py` defines `AgentProfile` (Agent id, display name, delegation description, instructions, Model wish, Tool and permission wishes, Skills, provenance and its translation report), ordered Tool/target rules, translations and Source selections. `catalog.py` owns detection and collision-safe refresh. `sources.py` assembles the Team and shadowed definitions and reads live Profiles. Downstream code never interprets foreign syntax.

`opencode.py` reads Markdown in `.opencode/agents/` and `.opencode/agent/`, plus Agent objects and global rules in `opencode.json`, `.opencode/opencode.json` and their `.jsonc` variants (comments and trailing commas allowed). Entries that only adjust OpenCode's built-in Agents (`build`, `plan`, `general`, `explore` without a `prompt`) define no Team member. Prompt file references stay inside the repository. `markdown.py` reads Claude (`.claude/agents/` and repository settings), Copilot (`.github/agents/`), Cursor (`.cursor/agents/`) and Gemini (`.gemini/agents/`). Markdown without frontmatter is documentation, not an Agent (Copilot `*.agent.md` files excepted). `codex.py` reads `.codex/agents/*.toml` and role config-file references from `.codex/config.toml`, whose sandbox, approval, permission-profile, web search and feature settings every Codex Agent inherits. Discovery is recursive within known folders and never traverses links/junctions. `_reading.py` limits inputs to 128 KiB, accepts UTF-8, rejects duplicate metadata keys and normalizes line endings while retaining instructions.

Skill Sources include `.agents/skills/` and each supported ecosystem's Skill directory, plus Skill folder Sources: `folder:<path>` ids the user adds (`catalog.py::source_definition`), the path repository-relative when the folder lies inside the repository (so it follows a re-pointed `cwd`), else absolute. `detect_sources(..., selections=)` detects them beside the catalog; a missing one is not detected, and while switched on it yields an `invalid_source` finding (`Skill folder not found`) instead of failing the Project. `adopt_folder_sources` canonicalizes newly added ones at the RPC boundary: an existing directory, normalized but not resolved (a link stays the link), and refused when it names a folder another Skill Source already names; stored ones stay as they are. Skills loads these ordered roots, first name wins. A Skill folder that links to another Skill folder (`.claude/skills` -> `.agents/skills`) is neither detected nor loaded; the real folder supplies its Skills once. If only links name the same folder, the first Source supplies it instead of all links excluding each other. Repository instruction files are not scanned as Sources: the main instruction file and folder instructions follow `core/projects/instructions.py` (`resolution.md` -> Project Context instructions). Cursor conditional/path rules are excluded, never flattened into always-on instructions.

## Translation and access

Tool access and Permission Rules are separate (user decision 2026-10-21, superseding the 2026-10-06 rule that vBot has no per-command and per-path rules): Tool rules decide which whole vBot Tools an Agent gets; command, path and host scopes become `AgentProfile.permission_rules` where vBot has an equivalent (Permission Rules translation below). vBot has no sandbox or approvals. An Agent that may do something in its own tool, even only for some commands or paths, after approval or inside a sandbox, gets the vBot Tool that does it; only a capability the Agent lacks entirely removes the Tool: an unscoped denial, an explicit Tool list without it, a read-only mode, a disabled feature. Sandboxes, approvals, hooks and isolation therefore change no Tool; an Agent's own hooks and other behavior vBot does not run are reported. Broken or unreadable metadata still makes the Profile unavailable with a finding.

Every behavior/access setting is applied, translated, not supported or overridden by vBot. A foreign value vBot lacks (an effort level, say) is reported and dropped; only malformed metadata makes a Profile unavailable. A Model wish list uses its first entry. Claude, Cursor, Gemini and OpenCode subagents without a Model wish inherit the delegating caller's Model. Appearance settings can be dropped; other unknown settings are reported. Status is ready, limited (unsupported settings) or needs_attention (unavailable). Disabled OpenCode Agents remain visible and unavailable.

Claude retains Model wishes, effort and Skill preloads. Explicit Tool lists become exact selections; empty means no Tools; `Read(src/**)` grants `read`. A Bash denial covers bash and terminal. `disallowedTools` and `permissions.deny` remove a Tool only when unscoped; `ask` rules change no Tool and are reported as not translated, because vBot asks no approvals. Scoped Agent/Skill names are represented as target rules. Permission modes: `plan` keeps read and search only, `dontAsk` keeps only Tools its `permissions.allow` rules pre-approve, and the other modes leave the Tools unchanged. MCP, isolation, memory, background, turn limits and hooks remain in the report; no external engine, hook or sandbox is run.

OpenCode global rules precede Agent rules with ordered last-match precedence. A capability is usable when its last `*` rule, or any rule after it, allows or asks; without a `*` rule it stays usable, so scoped denies alone keep the Tool. `shell` is the newer name of `bash` and shares its state. Several capabilities can share a vBot Tool (Grep and Glob for search); any usable one grants it. A denied capability vBot does not have (`todowrite`, `lsp`) changes nothing. Codex sandboxes and permission profiles change no Tool (read-only confines writes through Permission Rules instead); approval policies change nothing; `web_search = "disabled"` and `features.shell_tool = false` remove their Tools. Copilot `agents` lists limit delegation targets; qualified Tool names (`read/readFile`) map through their Tool set. Cursor readonly selects read capabilities. Gemini local Profiles prohibit recursive delegation; remote Profiles are unavailable.

An OpenCode named `task` or `skill` allow/ask exception also re-enables its vBot Tool after a broader denial; the named target/Skill rules still narrow what it can reach. Scoped denials alone keep their existing name-filtering semantics (`test_sources.py`).

## Permission Rules translation

Adapters fill `AgentProfile.permission_rules` through `RuleDraft` (`_translation.py`). They also record `AgentProfile.rule_files`, the repository files besides the definition the rules are read from (Claude settings files, `.codex/config.toml`, OpenCode config files and `{file:...}` prompt references), also before they exist; a restricted Session may read them where its rules allow but never write them (`permissions.md`). Resolution adds the locations where a definition could replace the member's (`resolution.md` -> Permission Rules). Team resolution applies it automatically below the Project override, as a restriction of the global default that never permits more than it (`resolution.md` -> Permission Rules); there is no opt-in switch. A translation only restricts what the source restricts: it sets a base only below full access and adds deny rules only for source denials; allow rules that would only widen are kept only when the same source restricts something, otherwise reported as needing no rule. Rows use the existing translation report: a rule with no faithful vBot meaning is `not_supported` (Profile `limited`); a translated rule that covers more than its source (a host rule also covers subdomains) says so in its row. `ask` always reads as allowed and is reported, since vBot asks no approvals.

| Source | Translated | Not translated |
|---|---|---|
| Claude `.claude/settings.json` + `settings.local.json` (`permissions`), Agent `disallowedTools` | Scoped `Read/Glob/Grep/LS(path)` -> Read, `Edit/Write/MultiEdit/NotebookEdit(path)` -> Edit, `Bash/PowerShell(cmd)` -> Shell, `WebFetch(domain:h)` -> Web deny rules. `dontAsk`: `read: work_area` unless an unscoped read allow, `write: scratch` / `commands: listed` / `web: listed` when only scoped allows exist, scoped allows -> allow rules, `additionalDirectories` -> Read allows. Other modes: `additionalDirectories` -> Edit allows only when something restricts. `blockReadsOutsideWorkingDirectories` -> `read: work_area` | `ask`, `!` patterns, `//**` on Windows (one drive only), other `permissions` keys |
| OpenCode `permission` (global, then Agent; last match wins) | `read`, `edit` (edit/write/apply_patch), `shell`/`bash`, `webfetch`: a deny `*` with exceptions -> base `work_area`/`scratch`/`listed` plus allow rules; denied patterns after the last `*` -> deny rules. `external_directory` deny -> `read: work_area` and `write: work_area` with exceptions as Edit allows; its denied patterns -> Read denies | `ask`; an allow after a deny cannot reopen it (deny always wins, reported) |
| Codex `.codex/config.toml` | `sandbox_mode` `read-only` -> `write: scratch`, `workspace-write` -> `write: work_area` plus `sandbox_workspace_write.writable_roots` as Edit allows, `danger-full-access` -> none. `default_permissions` / `[permissions.<name>]` (with `extends`): `:workspace` -> `write: work_area`, else `write: scratch`; `filesystem` write -> Edit allow, deny -> Read deny, `:workspace_roots` subpaths -> `{workdir}/...` | `network_access` and profile `network` (vBot does not control shell network), `exclude_tmpdir_env_var` / `exclude_slash_tmp`, other `:` folder sets |

Path mapping follows each source's documented semantics. Claude (https://code.claude.com/docs/en/permissions): `//p` absolute (`//c/x` -> `C:/x` on Windows), `~/p` home, `/p` relative to the settings source -> `{project}/p`, `p` and `./p` relative to the cwd -> `{workdir}/p`; gitignore depth: a bare name, and a single-segment directory pattern like `secrets/**` in a deny rule, match at any depth -> `{workdir}/**/...`; `WebFetch(domain:h)` matches the exact host, but a vBot host rule also covers subdomains (reported). OpenCode (https://opencode.ai/docs/permissions/): `*` crosses `/`, so a `*` segment becomes `**`; `~`/`$HOME` -> `~`; relative patterns anchor at `{workdir}` (assumption: the docs do not state the anchor); `webfetch` patterns match URLs, translated to the host. Codex: https://learn.chatgpt.com/docs/config-file/config-reference (formerly developers.openai.com/codex/config-reference).

## Priority, refresh and findings

Source order decides winners, then stable path order within a Source; Agent names and Skill names compete only within their kind. The Team is sorted by Agent id. Losing definitions remain in `ScanResult.shadowed`; duplicate Skill names produce findings. Off Sources keep their rows. New Sources append active unless they collide with an existing active name. Existing Projects use the named additive backfill (`configuration.md`). Optional `agent_paths` limits a Source to repository-relative file patterns; the backfill retains the old top-level Markdown scope of OpenCode Projects. Excluded definitions stay visible with `source_scope` findings. Explicit expansion removes that limit; adapters and runtime configuration stay format-neutral.

`ScanReport` owns records only: bad_model, slug_collision, unslugifiable_name, orphan, unavailable_tool, invalid_source, skill_collision and source_scope. Source assembly supplies structural findings; resolution supplies usable-Model and pointer findings; RPC supplies unavailable Project Tools. Each Profile also carries its translation report.

Membership and its winning definition can be cached; each Run uses the adapter's direct read of the selected file or named definition, with live inherited settings. This reuses the Team's source choice, not its configuration; new competitors require the normal Team rescan/invalidation. Removed or renamed definitions fall back to the ordered live search. Selected discovered files are checked for links along their source-folder path before reading. Codex still validates every explicit role config file because an invalid role source makes the shared configuration unavailable, but translates only the selected role and does not scan unrelated standalone files. There is no separate parsed-configuration cache. Project show/open rescans and refreshes detection. Skill registry/inventory rebuilds also refresh Sources. Mutations of order, activation, cwd or Model mappings invalidate Team/Skill projections.

## Source and evidence

Skill inventory passes its operation-local `SkillScan` through `ProjectStore.refresh_sources` and `detect_sources`, reusing those package reads for the inventory's later projections. Project opening still rescans the Team and that Project's Skills, but an unchanged global Skill catalog no longer invalidates unrelated Project/Agent scopes, and an unchanged Project Skill rescan keeps that Project's cached registries (`skills/manager.md` -> Invalidation).
