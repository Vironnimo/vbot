# CLI

Command-line accessor for local server lifecycle, RPC-backed management of a local or remote server, and full-screen terminal conversations. It owns user-visible command parsing, target resolution, lifecycle process control, and deterministic agent-facing output; it does not own server business logic.

## Overview

Used by human users and agents. Local commands are server lifecycle (`server start|stop|restart|status`), `home`, the `desktop` GUI launch, `doctor`, the documented local data-store maintenance paths, and the packaged installation's `application`, `update`, `uninstall`/data reset and `autostart` (`cli/application/`; a development checkout refuses them). Every other command, including `chat`, calls the running server's RPC contract rather than reading or mutating runtime files directly. `tui` opens the interactive Textual accessor (`cli/tui.md`). Ordinary commands are automation-safe: they never open the browser, print explicit status/output, and exit non-zero for failed operations. `tui` requires terminal stdin and stdout.

## Terms

### Update channel
Where an installation installs and updates from: `release` (published releases) or `main` (the rolling `main-build` prerelease of main commits whose CI and packages passed). Recorded as `release_url` in `application.json` (`cli/application.md` -> Update operation). Not a messaging Channel (see `channels.md`).

### Development checkout
A Git checkout running vBot from source for development and tests (`pip install -e ".[dev]"`, Worktrees included). It is not an installation: it has no `application.json`, is updated with git, and refuses the installation commands.

## Interfaces

- Module split: `cli/main.py` is the lightweight process entrypoint, and `cli.main.run` dispatches the installation commands (`cli/application/`) before the console command surface. `cli/parser.py` composes the `argparse` tree from internal `_parser_<area>.py` builders; `_parser_common.py` owns shared target arguments, value readers, choice constants, help vocabulary and `COMMAND_PATHS`. `_commands.py` loads the console surface and routes to `_dispatch_<area>.py` argument translators; the `*_management.py` modules translate parsed args into RPC params, reject local no-op mutations when useful, validate only CLI-local input shape and format deterministic text. `_input.py` owns shared text decoding, `_output.py` outcome rendering and exit codes, `_recovery.py` failure guidance, `_progress.py` status decoration and elapsed-time reporting.
- `vbot --help` and parse errors load no HTTP stack: the command surface imports only light domain members (choice constants, `DEFAULT_HOST`; `core.utils.config` loads `core.settings` only when it reads `settings.json`), and `_server_target.py`, `rpc_client.py` and `server_management.py` import `httpx` inside the functions that send requests.
- Grammar: `vbot <area> <command> [target] [options]`, including deeper subcommands. The parser normalizes explicit area aliases before dispatch, rejects abbreviated options, and gives concise syntax errors with help and command suggestions; unknown spellings are never executed as corrections. **Primary identifiers are positional arguments, not flags** (`agent show <agent-id>`, `provider status <provider-id>`, `cron delete <job-id>`); secondary parameters stay flags. `COMMAND_PATHS` registers related actions as nested command groups; legacy spellings resolve to the same leaf parser and dispatch id, and help advertises the readable paths. Bare groups and `vbot help [path]` show help without side effects; `build_parser()` exposes the full static tree.
- **`agent@project` address form:** the `session` and `cron` agent positionals and `chat --agent` accept `agent@project` and pass the string straight to the RPC, which owns the one parse seam (`core.projects.parse_agent_address`); the CLI does not re-parse. A bare name is identity; Project agents display in address form. `session link-channel` keeps the bare `<agent-id>` form (Channels stay identity-only).
- `cli/rpc_client.py` posts `{ method, params }` to `/api/rpc`, normalizes envelopes into `RpcPayload`, preserves server RPC error code/message text, and reports malformed transport responses as command failures. Calls use a 10 s timeout; methods in `_LONG_RUNNING_METHODS` (accepted long work such as Model DB refresh, snapshot creation, Skill install and the archive deletes, restores and purges) and `data_store.status` with `verify_search: true` use an unbounded read with short connect/write/pool timeouts, so long work can finish while an unreachable server still fails fast.
- `RpcPayload` and `CommandResult.failure` retain `RpcFailure` evidence: method, error code, HTTP status, `data` and delivery state (`not_sent` for connection/pool failures, `unknown` for other request failures and malformed responses, `responded`). A valid error envelope requires boolean `ok: false` and string code/message. Delivery evidence applies only to that RPC, never proves command-wide rollback; composite results and candidate-lookup helpers keep the original failure metadata alongside saved-step details. Transport failures print `rpc_method`, `server`, `request_state` and recovery text naming possible effects. The client never replays a request or prints exception text or request/response bodies (`tests/cli/test_rpc_client.py`).
- `cli/server_client.py` is the one owner of what every connection to a server target needs (`http_options`, `websocket_target`, `access_refusal`); RPC, Run event streams, the TUI, the tray and `devices pair|logout` build on it, and nothing else attaches credentials. A loopback target sends the local access token of its port where `LocalAccess.admits` allows, an `https://` target the stored Device sign-in of its exact origin, anything else neither (`access.md` -> Invariants). Detail: `cli/server-access.md`.
- `server_management.py` owns `classify_server` (Health outcomes below), `stop_server(initiator=...)` and `log_bypassed_stop`, which the packaged application, `data-store snapshot restore` and the tray reuse; `cli/_server_target.py` owns target resolution, HTTP health classification and local listener matching.
- `inline_text` (`cli/formatting.py`) is the only way server-supplied text (names, addresses, codes) reaches the terminal: it escapes characters of the Unicode categories Cc, Cf, Zl and Zp (escape sequences, bidirectional overrides).

## Conventions

- CLI output is agent-facing. Success and failure must be explicit enough for an agent to choose the next command without guessing; silent success and silent failure are invalid, and central printers emit fallback lines if a result unexpectedly carries none. Mutations name target and action; reads print structured state for follow-ups. Failures include the server RPC code/message; for bounded identifiers prefer candidate suggestions ("did you mean") that branch on `failure.code` and suggest from the ids the command itself sent, never by parsing message text.
- Exit codes: 0 success, 1 failed operation or RPC failure, 2 usage error (nothing executed), 130 Ctrl-C. A command whose exit differs in a documented case (such as `server status` on a listener conflict) states it in its supplementary file.
- `_output.with_command_output` scopes parsing, presentation, result status and progress across every area. Management data stays on stdout; extra progress and completion notices use stderr. Result owners supply explicit `CommandResult.attention` for warnings/pending work instead of interpreting arbitrary result text; exit status still follows operation success. Ctrl-C stops reporting and advises inspecting the same target before repeating a mutation. `chat` has its own output path (`cli/chat.md`).
- Shared `--output auto|human|plain` selects terminal record layout, forced readable records, or stable data with no extra progress/completion notices. `formatting.record_fields` lays out producer-supplied fields without parsing or truncating values; JSON and content reads are never reformatted. Long operations get scoped elapsed reporting, with real phases where the RPC or lifecycle owner announces them; calling management functions outside the CLI starts no progress threads. Lifecycle/Doctor keep their own reports. Supported terminals get status symbols and color, non-terminals and dumb terminals plain status labels without cursor movement; `NO_COLOR` disables color, and help follows the same rule (`color_enabled`), so Python's own `FORCE_COLOR` never colors piped help.
- `_recovery.py` presents failure explanations and suggested read/help commands across areas, also in plain mode on stderr. Suggestions preserve resolved targets, content scopes and Agent addresses; they never execute recovery or repeat mutations. Known RPC codes select the relevant inspection (`agent_not_found` -> `agent list`, `project_not_found` -> `project list`, `skill_not_found` -> `skill inventory`), also for missing parts of an `agent@project` address; because `agent list` shows only Identity Agents, the `agent_not_found` explanation also names `vbot project show <project>` for Team members, constant rather than parsing the address. Expected local configuration, value and OS errors return a normal failure with guidance.
- Shared parser errors suggest known commands, options and choice values, report that no command executed, and point to the selected command's help. Unknown-option diagnostics omit unconsumed values because they can be credentials. Contradictory setter/clear flags fail before dispatch. Command descriptions carry argument guidance and examples that include the `vbot` executable; `tests/cli/test_cli_recovery.py` parses every published description example without dispatching it.
- **Targets.** Shared `--host`, `--port` and `--data-dir` apply to server lifecycle, autostart and RPC-backed commands; RPC-backed commands also take `--url <url>`. Precedence: `--url` > explicit `--host`/`--port` > `VBOT_SERVER_URL` > the local server by port resolution. `VBOT_SERVER_URL` is ignored inside an Agent's Run (`VBOT_RUN_AGENT_ID`), whose commands must reach the server that runs it. A packaged installation rejects lifecycle and autostart values that conflict with its recorded target, and its management commands default to that target; `update` and `uninstall` take no target options. Target flags can precede the area or follow the leaf command, and command-specific restrictions stay in force; equal repeats are accepted and conflicting repeats refused before dispatch. Address parsing and `--url` targets: `cli/server-access.md`.
- Port resolution follows `--port` > `VBOT_SERVER_PORT` > validated `settings.json` port keys > `22332` (`DEFAULT_PORT`), through the shared resolver in `core/utils/config.py`; the CLI does **not** import the `server` package. A damaged Settings document refuses target inference instead of falling back to the default port (`cli/server-access.md`).
- All local CLI HTTP disables proxy/`.netrc` environment trust (`trust_env=False`) across transport, probes and updater: RPC targets may be remote and bodies carry secrets, so ambient proxies can never divert credentials off-host. Every client passes `verify=ssl_context_for(url)` (why: PROJECT.md -> Conventions -> Dependency injection). A target counts as vBot only when `/health` answers per the identity contract owned by `server.md`.
- The process entrypoint reconfigures stdout/stderr to UTF-8 with `backslashreplace`. Explicit secret stdin readers (Providers, Extensions, Channels) accept a leading BOM, strip trailing CR/LF, and return normal failure on decode errors rather than falling back to a legacy code page that could silently corrupt a secret.
- The bundled product skill `resources/skills/vbot-docs/` teaches vBot's own Agents the CLI surface (lean SKILL.md routing to per-area reference files). Its update workflow runs `vbot update`, ends the Run after acceptance and relies on the update's own Session continuation (`cli/application.md` -> Agent handoff). When command shapes, areas, or flags change, update the matching reference file (and SKILL.md's area table if areas/subcommands changed) in the same change.

## Constraints & Gotchas

- The CLI is an accessor, not a second control plane. Do not add management commands that write `settings.json`, Agent configs, Channel configs, prompt fragments, logs, model catalogs, or other runtime files directly; route them through server RPC unless the command is explicitly local lifecycle/home/desktop-launch/doctor/update/uninstall/autostart behavior or a documented data-store maintenance path.
- **Health outcomes.** Lifecycle decisions go through `classify_server` on top of `probe_health_patiently`, never one quick probe: a stalled Event Loop or, on Windows, a refused connection both surface as a timeout, so a timeout alone never proves a listener absent. States: `running` (the control record's exact process lives and the target answers as vBot), `unresponsive` (it lives but does not answer: busy, starting or stopping; the record exists before the listener), `foreign` (another process or another data directory's vBot holds or answers the target), `absent` (no live recorded process and no listener). `start` spawns only on `absent`. `stop` terminates only a verified local target whose current control record (PID plus process creation time; PID alone is never trusted) identifies the exact server process, never a non-vBot occupant; it asks for cooperative shutdown first and kills a process that has not exited `DEFAULT_SHUTDOWN_TIMEOUT_SECONDS` (30 s) after the request. Probe budgets and the command outcomes: `cli/server-lifecycle.md`.
- Secrets never reach output or logs. Channel tokens, `data-store secrets set` values and secret Extension operation input come only from stdin or a hidden prompt, never argv. `provider set-key <id> <api-key>` accepts a direct value because agents configure local instances through the CLI, and `extensions set` takes a secret field's value positionally or with `--stdin`; such a value goes only to its RPC and is never printed.

## Agent-facing text

This domain owns the bundled `vbot-docs` Skill (`resources/skills/vbot-docs/`) and the CLI refusals and recovery texts Agents read, such as `agent_busy` in `cli/_recovery.py`. Before you change, add or delete a sentence of them, read `cli/agent-facing-text.md`: it records why each sentence exists. Update its row for every sentence you change and add one for every sentence you add.
