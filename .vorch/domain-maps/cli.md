# CLI

Local command-line accessor for server lifecycle and RPC-backed management areas. It owns user-visible command parsing, target resolution, lifecycle process control, and deterministic agent-facing output; it does not own server business logic.

## Overview

`cli/` is the local process-management and management-command entrypoint used by human users and agents. It owns `server start`, `server stop`, `server restart`, `server status`, the local `desktop` GUI launch, the local `update` self-updater, the local `autostart` manager, local `doctor` validation, and RPC-backed management commands for agents, projects, sessions, channels, providers, models, task-model bindings, skills, tools, prompts, logs, cron jobs, debug traces, statistics, and config. The CLI is non-interactive and automation-safe: it never opens the browser, prints explicit status/output, and exits non-zero for failed management operations except for the documented `server status` non-vBot conflict case. Every command outside server lifecycle, the desktop launch, and doctor calls the running server's RPC contract rather than reading or mutating runtime files directly.

## Interfaces

- `cli/parser.py` owns the `argparse` tree, shared target arguments, choice constants, and all help text; every command description carries an inline `Example:` line. `cli/main.py` re-exports `parse_args` and owns dispatch functions, exit-code mapping, and central output printers. When exact argument spelling matters, read `python cli/main.py <area> <command> --help` and the parser constants in `cli/parser.py`.
- **Primary identifiers are positional arguments, not flags:** `agent show <agent-id>`, `agent create <agent-id> <name>`, `channel remove <channel-id>`, `prompt update <fragment-name>`, `prompt preview <agent-id>`, `log read <log-file>`, `provider status <provider-id>`, `provider set-key <provider-id> <api-key>`, `model refresh [<provider-id>]`, `session list <agent-id>`, `cron delete <job-id>`, `debug trace <trace-id>`, `task-model targets <task-type>`. Secondary parameters stay flags (`--connection`, `--name`, `--prompt`, ...).
- `cli/server_management.py` owns `ServerInstance`, target resolution, `/health` and WebUI probes, background server startup, local process lookup, stop/kill behavior, and status classification.
- `cli/rpc_client.py` posts `{ method, params }` to `/api/rpc`, normalizes success/error envelopes into `RpcPayload`, preserves server RPC error code/message text when present, and reports malformed transport responses as command failures. Calls use a 10s timeout by default; methods in `_LONG_RUNNING_METHODS` (currently `model.refresh_db`, which fans out sequentially to provider catalogs) instead use an unbounded read with a short connect timeout, so the server bounds the work while an unreachable server still fails fast.
- `cli/*_management.py` modules for `agent`, `session`, `channel`, `provider`, `model`, `task_model`, `skill`, `tool`, `prompt`, `log`, `cron`, `debug`, `statistics`, and `config` translate parsed args into RPC params, reject local no-op mutations when useful, validate only CLI-local input shape, and format deterministic plain-text output.
- `server start [--host] [--port] [--data-dir]` resolves the target instance, starts `python -m server.main` in the background when no vBot server is already reachable there, and succeeds only after the exact vBot `/health` contract responds.
- `server stop [--host] [--port] [--data-dir]` targets a local vBot server at the resolved address, refuses non-vBot listeners, terminates the matched process, and force-kills after the bounded timeout when graceful termination does not finish.
- `server restart [--host] [--port] [--data-dir] [--service-name]` restarts the resolved target. On a systemd-managed install — a `<service-name>.service` **user** unit exists and is active — it restarts through the unit (`systemctl --user restart`) instead of fighting it with an out-of-band terminate/spawn; otherwise it stops the first resolved target if present, then re-resolves host/port/data-dir from current args, env, and settings before starting (if stop fails, restart does not start). `--service-name` (default `vbot`) names the unit to check; the systemd path is shared with `update` and lives in `cli/server_management.py` (`restart_server` / `is_systemd_managed`).
- `server status [--host] [--port] [--data-dir]` reports running/not running, resolved URL, WebUI available/unavailable, resolved data dir, and log path. A non-vBot listener at the target prints a conflict note but still exits 0 for `status` so automation can inspect the state.
- `desktop [--host] [--port]` is the first **local GUI-launch** action — it opens the pywebview Desktop window pointed at a local or remote server, and is **not** an RPC command and **not** server lifecycle. It branches before the shared `resolve(...)` (like `server`/`doctor`/`update`/`autostart`) and never builds a `ServerInstance`; it lazily imports `desktop.main` (so the default CLI path needs no pywebview) and forwards **only** the flags the user actually supplied, so a bare `vbot desktop` reaches the launcher's last-used auto-connect path instead of a silent localhost target. It takes no `--data-dir` (the Desktop uses its own per-user config dir, not the server data-dir; see `desktop.md`). The call blocks until the window closes, then prints `desktop window closed` and exits 0; a missing `[desktop]` group surfaces the launcher's install hint as a failure exit.
- `update [--host] [--port] [--data-dir] [--discard | --stash] [--no-restart] [--service-name]` is a local self-updater (`cli/update_management.py`) for git-based installs. It auto-detects the track from the checkout (branch → `git pull --ff-only` + local WebUI rebuild when `webui/` changed; detached release tag → fetch the latest release tag + its prebuilt `webui-dist.tar.gz` asset, re-downloaded only when the tag actually changed or `webui/dist` is missing, unpacked via staging and swapped in as a wholesale `dist` replacement so stale bundles never accumulate and a corrupt archive never costs the existing dist), reinstalls the editable package only when `pyproject.toml` changed (release extras `server,cli`, dev extras `dev`, plus `desktop` when the desktop accessor is importable in the environment — the checkout does not record install-time add-ons), then restarts the resolved server target through the same systemd-aware path as `server restart` (`--service-name`, default `vbot`). It refuses a checkout with local changes to tracked files unless `--discard` (hard reset) or `--stash` (stash then reapply) is passed, and never touches the `~/.vbot` data dir. External git/pip/npm calls run with a per-command timeout and git's interactive credential prompt disabled (`GIT_TERMINAL_PROMPT=0`) so a stuck or auth-needing remote fails fast instead of hanging. Like `server`/`doctor`, it runs without an already-running server.
- `autostart enable | disable | status [--host] [--port] [--data-dir] [--task-name] [--service-name]` is a local OS-autostart manager (`cli/autostart_management.py`), OS-branched: Windows Task Scheduler logon task, Linux systemd **user** unit + login lingering. `enable` registers autostart **and** starts the server now (Linux via `systemctl --user enable --now`; Windows via a managed background start — creating the task needs an elevated terminal); `disable` removes the entry and leaves a running server alone; `status` reports registered/not. Runs without an already-running server. The installers call `vbot autostart enable` by default (opt out with `--no-autostart`).
- `agent list|show|create|update|delete` maps to `agent.list`, `agent.get`, `agent.create`, `agent.update`, and `agent.delete`. `agent create <agent-id> <name>` takes id and display name positionally. Create/update accept only public mutable RPC fields: model/fallback model/temperature/thinking effort/memory prompt mode (`--memory-prompt-mode off|agent|agent_user`)/custom prompt toggle (`--custom-system-prompt true|false`)/tool and skill allowlists, plus name and current session on update.
- `agent update` rejects empty updates before RPC and prints the valid update flags. Clear flags send JSON `null` for inherited defaults, while literal domain values such as `--thinking-effort none` send the string value and must stay distinct from clearing the field.
- `channel add|list|remove|update|enable|disable|status` maps to `channel.create`, `channel.list`, `channel.delete`, `channel.update`, `channel.enable`, `channel.disable`, and `channel.status`. `--platform` accepts `telegram` or `discord`; `--allow` parses ids as strings and replaces the full allowed chat-id list, omitted update fields remain unchanged, and `channel status` prints enabled/running/failed plus failure reason when one exists, followed by the channel's denied inbound chats (chat id, kind, name, last seen, message count) with an explicit `channel update --allow` suggestion line — the agent-facing chat-id discovery flow (see `channels.md`).
- `provider list` calls `connection.list` and prints configured connections — per row `enabled`, `usable`, `reachable` (auto-refresh connections only) — including per-connection account sub-lines (`id`, `usable`, `source`). `provider status <provider-id> [--connection <provider:connection-id>]` filters that same RPC result and should print available candidates plus a close-match suggestion when the target is missing.
- `provider enable|disable <provider-id> [--connection <provider:connection-id>]` calls `connection.set_enabled`. Without `--connection`, a single-connection provider resolves automatically; a multi-connection provider fails with the candidate connection ids. On enable, the output reports the probe outcome for local auto-refresh connections ("endpoint reachable" / "endpoint not reachable — the connection stays enabled") and hints at `provider set-key` when the enabled connection has no credential yet. Keyless local providers (e.g. Ollama) start disabled — this is the agent's switch to turn them on.
- `set-key`, `unset-key`, `connect`, `disconnect`, and `connect-status` all accept `[--account <account-id>]` — a named credential slot on the connection (omitted means the server default `default`). The CLI passes it through and renders the resolved Account from the response; semantics live in `providers/connections.md` → Identity and Accounts.
- `provider set-key <provider-id> <api-key> [--connection <provider:connection-id>] [--account <account-id>] [--refresh-models]` calls `provider.set_key`, which writes the resolved account's derived API-key credential to the data-dir `.env`, reloads runtime provider credentials, rejects OAuth connections, and never returns or prints the secret. `--refresh-models` chains `model.refresh_db` for the same provider only after the credential update succeeds.
- `provider unset-key <provider-id> [--connection <provider:connection-id>] [--account <account-id>]` calls `provider.unset_key` to remove that account's API-key credential from the data-dir `.env`. When the response reports the account still configured (process-environment credential), the CLI says so and points at unsetting the variable there.
- `provider connect|disconnect|connect-status <provider-id> --connection <provider:connection-id> [--account <account-id>]` maps to `provider.connect`, `provider.disconnect`, and `provider.connection_status`, all per (connection, account). `connect` starts the OAuth device flow and prints `user_code`, `verification_uri`, expiry, and the follow-up `connect-status` command (with `--account` appended for non-default accounts); the server polls in the background, so the CLI stays non-interactive. `connect-status` prints `connected=` and `flow_active=`.
- `model list` calls `model.list` and prints available models. `model refresh [<provider-id>]` calls `model.refresh_db` and refreshes provider model catalogs through the server/runtime path.
- `project add <path> [--name] [--format opencode|claude] [--default-agent] [--default-model] [--auto-load f1,f2]`, `project list`, `project show <project-id>`, `project set <project-id> [--cwd|--name|--format|--default-agent|--clear-default-agent|--default-model|--clear-default-model|--auto-load]`, and `project rm <project-id>` map to `project.add`/`project.list`/`project.show`/`project.set`/`project.rm`. `--clear-default-agent` and `--clear-default-model` send JSON `null`, removing the Project tier so resolution falls through; like the existing Project clear flags, a clear flag wins when its paired set flag is also supplied. `--format` is the user-facing flag mapping to the RPC `source_format` (GLOSSARY → Source Format); on `add` it is optional (omitted → the server auto-detects from the repo, defaulting to `opencode` when both/neither format is present), on `set` it switches the format (team + skills re-derive from the other ecosystem's directories). `show`/`set`/`add` render the `format:` config line and the scan preview (team + report findings); `rm` prints the archive path or the `project_busy`/`project_in_use` block message. Project work is stateless — there is no current-project flag; the project rides the `agent@projekt` address form on agent arguments.
- **`agent@projekt` address form on positional agent arguments.** The `session` and `cron` agent positionals accept `agent@projekt` (e.g. `session list orchestrator@vbot`, `cron create builder@vbot ...`) and pass the string straight to the RPC, which owns the one parse seam (`core.projects.parse_agent_address`); the CLI does not re-parse. A bare name is identity (unchanged). Project agents are displayed in the address form (e.g. `cron list` shows the server's `target`). `session link-channel` keeps the bare `<agent-id>` form (channels stay identity-only).
- `session list <agent-id>`, `session create <agent-id> [--id <session-id>] [--make-current]`, `session delete <agent> <session-id> --yes`, and `session link-channel <agent-id> <session-id> --channel <channel-id> --conversation <platform-conv-id>` map to `session.list`, `session.create`, `session.delete`, and `session.link_channel`. `session delete` refuses without `--yes` (the Session is archived, not erased) and on success prints the `next_session_id` to land on. List rows show id, created/last-active timestamps, and the source channel when linked.
- `cron list|create|update|delete|enable|disable` maps to the `cron.*` RPC handlers. `cron create <agent-id> --prompt <text>` requires exactly one of `--cron <expression>` (recurring) or `--at <iso-datetime>` (one-time) — the CLI derives `schedule_type` from which flag is used; `--timezone` and `--session` are optional. `cron update <job-id>` accepts the same flags plus `--status active|paused|completed` and rejects empty updates before RPC. List rows show id, agent, status, `cron[expr]`/`once[run-at]` schedule, next fire time, and a 60-char prompt preview.
- `debug status|traces|trace <trace-id>|clear|probe <provider-id> --connection <provider:connection-id>` maps to `debug.status`, `debug.trace_list`, `debug.trace_get`, `debug.trace_clear`, and `debug.model_probe`. `trace` prints the full sanitized trace as sorted JSON; `probe` prints status/duration/trace id plus the model preview and never dumps the raw response (it points at `debug trace <id>` instead). Trace listing and probing fail server-side while debug mode is disabled; `status` and `clear` always work.
- `task-model list|targets|options|set|clear` maps to `task_model.settings`, `task_model.list_targets`, `task_model.options`, and `task_model.update`. `<task-type>` is validated locally against `SUPPORTED_TASK_TYPES`. `task-model set <task-type> <target-id> [--options <json-object>]` sends a sparse `model_tasks` update; `task-model clear <task-type>` sends an empty `target` to remove the binding. `--options` is parsed locally and must be a JSON object.
- `skill list` calls `skill.list` and prints valid skills plus unavailable, optional-missing, and invalid skill diagnostics. `tool list` calls `tool.list` and prints registered public tools.
- `statistics overview|usage|runs|errors|tools|skills [--since <iso>] [--until <iso>]` (`cli/statistics_management.py`) makes one `statistics.report` RPC call and renders only the requested section as deterministic plain text; `--since`/`--until` are passed through verbatim (the server validates ISO-8601 and window order). Every section has an explicit empty state. The `skills` output leads with the never-used list (the agent's delete/improve decision input), then the per-skill table (name, origins, offered, activated, usage rate — `0.00` for offered-but-never-activated, `-` only when never offered — and last activated).
- `extensions` is **name-first**: the first token is either a reserved verb (`list`/`reload`/`enable`/`disable`) or an extension name, routed in `dispatch_extensions_command` (argparse cannot enumerate dynamic names, so this area uses a `selector` + `rest` positional pair instead of fixed sub-parsers). `list` prints loaded/failed/disabled/overridden extensions with status, version, capabilities, failure reasons, and — for a `waiting` extension — what it is waiting for. `reload` (no args → usage error otherwise) calls `extensions.reload` (the full restart-equivalent rebuild) and prints a one-line status-count summary (`extensions reloaded: N loaded, N failed, N disabled, N overridden`) plus a `  <name> failed: <error>` line per failure and a `run 'vbot extensions list' for details` pointer when anything failed. `enable`/`disable <name>` read the current `extensions` section via `extensions.list` and write the full section back through `settings.update`; both apply **live** (no restart hint) — enabling additionally re-lists and appends `warning: '<name>' is <status>` (plus an `  error:` line) when the freshly rebuilt extension did not load.
- `extensions <name>` (bare name, no verb) shows one extension's settings from its `extensions.list` payload: each schema field with type + current value, a secret shown only as `set`/`not set` (never the value); a schema-less extension falls back to raw config. `extensions <name> set <field> <value>` writes one setting, **routed by the field's declared schema type**: a `secret` field calls `extensions.set_secret` (`{name, key, value}` — the caller names the schema field key, the server maps it to the declared `.env` key), any other field is coerced to its declared type (text/number/toggle) and written to the extension's live config via `settings.update`. Both are applied **live, without a restart**. `--stdin` reads the value (typically a secret) from stdin to keep it out of shell history; an empty value clears a secret. Unknown extension/field get available-candidate + did-you-mean output.
- `prompt list|update|reset|preview` maps to `prompt.list`, `prompt.update`, `prompt.reset`, and `prompt.preview`. `prompt update <fragment-name> (--content <text>|--file <path>)` may read one local source file, but storage writes still happen only through `prompt.update`; preview prints token metadata plus the rendered System Prompt text.
- `log list|read` maps to `log.list` and `log.read`. The CLI must not read `<data_dir>/logs/` directly; `log read <daily-log-name>` prints parsed entries plus the returned cursor.
- `config`, `config get <key>`, and `config set <key> <value>` call `settings.get_raw` or `settings.set_key` over RPC. `config set` coerces the CLI value to JSON-native data with `json.loads()` before falling back to a plain string; missing keys print available top-level keys and a close-match suggestion when possible.
- `doctor settings [--data-dir]` and `doctor config [--data-dir]` run locally without a reachable server. They validate `settings.json` or the full user-editable JSON config bundle through `core/settings/validation.py`, report missing files as OK when defaults apply, and format diagnostics as severity, JSON path, and message for agent callers.

## Conventions

- Shared `--host`, `--port`, and `--data-dir` target options apply to server lifecycle and RPC-backed management commands. Doctor commands accept only `--data-dir` because they are local file validators.
- Port resolution follows `--port` > `VBOT_SERVER_PORT` > validated `settings.json` port keys > `8420`, using the shared host/port resolver (`DEFAULT_HOST`, `resolve_port`, `resolve_server_bind`) that now lives in `core/utils/config.py`. The CLI imports it from there (via `cli/server_management.py`) and does **not** import the `server` package for it; `server/main.py` re-exports the same names for compatibility. Ambient `PORT` and `SERVER_PORT` process environment variables are ignored; those names matter only when present as settings keys inside `settings.json`.
- All local CLI HTTP disables proxy/`.netrc` environment trust (`trust_env=False`) — the RPC transport, the health/WebUI probes, and the updater alike. The CLI only ever talks to the local server over loopback and RPC bodies carry secrets (e.g. `provider.set_key`), so a credential is never divertible off-host through an ambient `HTTP_PROXY`. A target counts as vBot only when `/health` returns HTTP 200 and JSON exactly equal to `{ "status": "ok" }`.
- Built WebUI assets are optional. Missing `webui/dist` may make `/` unavailable while `/health` is healthy; lifecycle output reports `webui: unavailable` instead of treating startup as failed.
- CLI output is agent-facing. Success and failure output must be explicit enough for an agent to choose the next command without guessing; silent success and silent failure are invalid. Central printers emit fallback success/error lines if a command result unexpectedly has an empty message.
- The process entrypoint reconfigures stdout and stderr to UTF-8 with `backslashreplace` before dispatch. Commands such as `debug trace` must therefore print Unicode-rich server payloads without crashing under a legacy Windows console code page; imported streams that cannot be reconfigured keep their own output contract.
- `extensions <name> set <field> --stdin` treats piped bytes as UTF-8 (a leading BOM is accepted), strips trailing CR/LF, and returns a normal failure without calling the setter when decoding fails; it never falls back to a legacy code page that could silently corrupt a secret or text value.
- Local lifecycle subprocesses (`update`, `autostart`, and systemd server management) capture bytes rather than locale-decoded text. `decode_command_output()` prefers UTF-8 and falls back to the process locale with undecodable bytes escaped, so Git/Node Unicode and native localized tools both remain usable and a decode failure cannot erase stdout/stderr used for track or status decisions.
- Successful mutating commands name the target and action performed. Read commands print enough structured state for follow-up decisions. RPC failures and malformed envelopes surface as non-zero exits with clear messages.
- Failures include server RPC error code/message when available. For bounded identifiers such as providers, connections, settings keys, agents, channels, prompt fragments, and log files, prefer available-candidate output and `did you mean` suggestions when the CLI has enough local/RPC-returned candidates.
- CLI-managed lifecycle logs belong under `<data_dir>/logs/` through the managed `LogManager`. Background server startup must not bypass that logger or rely on raw child stdout/stderr.
- Tests mirror the module split under `tests/cli/`. When changing parser shape, command behavior, output text, target resolution, or lifecycle behavior, update the focused CLI tests.
- The bundled product skill `resources/skills/vbot-cli/` (a lean SKILL.md routing to per-area files under `references/` — server, providers, agents-projects, channels, cron, configuration, diagnostics, telegram-setup) teaches vBot's own agents the CLI surface. When command shapes, areas, or flags change, update the matching reference file (and the SKILL.md area table if areas/subcommands changed) in the same change.

## Constraints & Gotchas

- The CLI is an accessor, not a second control plane. Do not add management commands that write `settings.json`, Agent configs, Channel configs, prompt fragments, logs, model catalogs, or other runtime files directly; route them through server RPC unless the command is explicitly local lifecycle/desktop-launch/doctor/update/autostart behavior. The `desktop` launch is a local GUI action with no RPC and no `ServerInstance`.
- If a vBot server is already running at the target address/port, `start` reports `already running` and does not spawn another instance. If a reachable non-vBot process occupies the target, `start`, `stop`, and `restart` fail with a conflict and must not terminate that process.
- `server status` reports `running: no` plus a conflict note for non-vBot port occupants, and this specific status conflict maps to exit code 0. The same conflict is a failure for `start`, `stop`, and `restart`.
- Process termination is allowed only after `/health` confirms the target is vBot. Local process lookup must match the resolved host/address and port, not port alone; wildcard listeners are matched only when they can receive the requested target traffic.
- Stop is best effort: terminate first, kill after the bounded timeout, and report `forced: true` when the kill fallback was needed. On Windows this can still interrupt in-flight Runs abruptly.
- Live reachability and `/health` classification are the authority. The CLI intentionally has no stale PID or launch-metadata recovery path.
- Startup waits for health readiness and cleans up the just-spawned child if readiness times out, the child exits early, or a non-vBot responder appears during startup.
- `provider set-key` accepts a direct API-key value because agents are expected to configure local vBot instances through the CLI. It must send the value only to `provider.set_key` and must never include the secret in success, error, log, or refresh output.
