# CLI

Local command-line accessor for server lifecycle and RPC-backed management areas. It owns user-visible command parsing, target resolution, lifecycle process control, and deterministic agent-facing output; it does not own server business logic.

## Overview

`cli/` is the local process-management and management-command entrypoint used by human users and agents. It owns `server start`, `server stop`, `server restart`, `server status`, the local `home` path report, the local `desktop` GUI launch, the local `update` self-updater, the local `uninstall`/data-reset flow, the local `autostart` manager, local `doctor` validation, and RPC-backed management commands for agents, projects, sessions, channels, providers, models, task-model bindings, skills, tools, prompts, logs, cron jobs, Bootstrap jobs, debug traces, statistics, and config. The CLI is automation-safe: it never opens the browser, prints explicit status/output, and exits non-zero for failed management operations except for the documented `server status` non-vBot conflict case. `uninstall` is the sole interactive exception when stdin is a TTY; non-interactive callers must select an explicit removal mode and confirmation flag. Every command outside server lifecycle, home/desktop, update/uninstall/autostart, and doctor calls the running server's RPC contract rather than reading or mutating runtime files directly.

## Interfaces

- `cli/parser.py` owns the `argparse` tree, shared target arguments, choice constants, and all help text; every command description carries an inline `Example:` line. `cli/main.py` re-exports `parse_args` and owns dispatch functions, exit-code mapping, and central output printers. When exact argument spelling matters, read `python cli/main.py <area> <command> --help` and the parser constants in `cli/parser.py`.
- `home [--data-dir]` is a local, read-only command that needs no running server and prints exactly two deterministic fields: `vbot_root` is the absolute checkout/install root containing the running vBot code, and `data_dir` is the absolute runtime data root selected by the normal explicit argument → `VBOT_DATA_DIR` → applicable `.vbot-worktree` → `~/.vbot` chain. `core.utils.config.VBOT_ROOT` is the shared vBot-root source used by the Runtime and local install lifecycle commands; `Config` owns data-root selection. Neither field is the caller's arbitrary shell cwd or a Project cwd; the retired `app_dir` output is not retained as an alias.
- **Primary identifiers are positional arguments, not flags:** `agent show <agent-id>`, `agent create <agent-id> <name>`, `channel remove <channel-id>`, `prompt update <fragment-name>`, `prompt preview <agent-id>`, `log read <log-file>`, `provider status <provider-id>`, `provider set-key <provider-id> <api-key>`, `model refresh [<provider-id>]`, `session list <agent-id>`, `cron delete <job-id>`, `bootstrap delete <job-id>`, `debug trace <trace-id>`, `task-model targets <task-type>`. Secondary parameters stay flags (`--connection`, `--name`, `--prompt`, ...).
- `cli/server_management.py` owns `ServerInstance`, target resolution, `/health` and WebUI probes, background server startup, local process lookup, stop/kill behavior, and status classification.
- `scripts/install.sh` and `scripts/install.ps1` are the only public installation entrypoints: they select a release or current checkout, establish an isolated checkout-local `.venv`, obtain or build the WebUI, and then call the internal `scripts/setup.*` helper for package/data/autostart configuration. Fresh installer-owned clones carry `.vbot-install-root` and are deleted wholesale on uninstall; installs in an existing checkout carry `.vbot-install-venv` and remove only the managed environment and launcher. Uninstallers still recognize the retired `.vbot-bootstrap` marker so an older installed release remains removable after updating. `cli/install_state.py` owns the versioned, checkout-local `.vbot-install.json` lifecycle manifest used by setup, updater, and uninstallers. It atomically persists the install shape (`server`, `server-desktop`, or `desktop-client`), exact dependency groups, absolute Python environment entry point without resolving a venv symlink back to its base interpreter, source track, applied Git revision, dependency-file digest, WebUI revision, and the complete host/port/data-directory target for a server install; older manifests without a recorded target remain valid. This is install-management state, not runtime configuration: it contains no credentials or data-dir content and is git-ignored. The Windows public Installer exposes `vbot` through an installer-owned `bin/vbot.cmd` that invokes the environment's Python module entrypoint rather than pip's replaceable `vbot.exe`, so the command launcher does not lock itself during an update. The Windows setup helper creates `vBot Desktop.lnk` only for Desktop shapes and points it at the package's `vbot-desktop` GUI-script launcher rather than the console `vbot` entrypoint; Linux uses the corresponding application-menu entry. Both Uninstallers inspect the recorded install shape and remove those per-user Desktop artifacts only for `server-desktop` or `desktop-client`; an old install without a manifest qualifies only when its conventional `.venv` still contains the Desktop launcher, so a server-only uninstall cannot remove another installation's Accessor entry. The Windows setup helper's narrow `-DesktopShortcutTarget` mode exists solely so the updater can refresh that installer-owned shortcut without touching dependencies, data, WebUI, or Autostart. The Windows public Installer refuses an elevated process before install mutation so the checkout, environment, runtime data, and server stay user-owned; `-AllowElevatedInstall` is reserved for disposable automation such as the release smoke workflow. Both public Installers normally show only high-level phases and capture internal setup output in an OS-temporary log; a clean verified install deletes the log, while failures or unresolved lifecycle problems preserve it and print its exact path. Bash `--verbose` and PowerShell `-Verbose` stream those details live as well. For server shapes, each Installer reads the recorded target and independently checks actual vBot health plus its platform Autostart mechanism when Autostart was requested before printing `vBot is ready`; a live URL is printed only after the health check reports a running vBot server. The internal Windows setup helper provides the same status distinction before returning to the public Installer.
- `cli/rpc_client.py` posts `{ method, params }` to `/api/rpc`, normalizes success/error envelopes into `RpcPayload`, preserves server RPC error code/message text when present, and reports malformed transport responses as command failures. Calls use a 10s timeout by default; methods in `_LONG_RUNNING_METHODS` (currently `model.refresh_db`, which fans out sequentially to provider catalogs) instead use an unbounded read with a short connect timeout, so the server bounds the work while an unreachable server still fails fast.
- `cli/*_management.py` modules for `agent`, `session`, `channel`, `provider`, `model`, `task_model`, `skill`, `tool`, `prompt`, `log`, `cron`, `bootstrap`, `debug`, `statistics`, and `config` translate parsed args into RPC params, reject local no-op mutations when useful, validate only CLI-local input shape, and format deterministic plain-text output.
- `bootstrap list|create|update|delete|enable|disable` maps to the matching RPCs and is the only Bootstrap management surface. Create requires an explicit `--mode once|always` plus either a positional Agent address and optional `--session`, or `--current-session`. `--current-session` reads `VBOT_RUN_AGENT_ID`, `VBOT_RUN_SESSION_ID`, and optional `VBOT_RUN_PROJECT_ID`, which the existing Bash Tool injects from its `ToolContext`; it rejects conflicting explicit targets, missing Run context, and remote server targets. Update supports `--clear-session`; completed one-shots remain immutable server-owned history.
- `server start [--host] [--port] [--data-dir]` resolves the target instance, starts `python -m server.main` in the background when no vBot server is already reachable there, and succeeds only after the exact vBot `/health` contract responds. On Windows the background process uses a new process group, `CREATE_NO_WINDOW`, and explicit breakaway from any invoking Job so the new server can establish its own kill-on-close Job Object; the server remains alive after its invoking PowerShell or Command Prompt exits without leaving a Python console window open. Every `server start|stop|restart|status` invocation flushes a readable action-and-target sentence before lifecycle work, preserves the deterministic detail fields, and ends with a complete outcome sentence; no-op states, non-vBot port conflicts, forced termination, and failures are stated explicitly.
- `server stop [--host] [--port] [--data-dir]` targets a local vBot server at the resolved address and refuses non-vBot listeners. When the listener PID matches the current local control record, it posts the per-process secret to the private shutdown route and waits for FastAPI/Runtime teardown; a missing/rejected record falls back to platform termination, and either path force-kills after the bounded timeout.
- `server restart [--host] [--port] [--data-dir] [--service-name]` restarts the resolved target. On a systemd-managed install — a `<service-name>.service` **user** unit exists, is active, and its vBot `ExecStart` targets the resolved host, port, and data directory — it restarts through the unit (`systemctl --user restart`) instead of fighting it with an out-of-band terminate/spawn; a same-named unit for another Server Instance is never treated as the target's owner. Otherwise it stops the first resolved target if present, then re-resolves host/port/data-dir from current args, env, and settings before starting (if stop fails, restart does not start). `--service-name` (default `vbot`) names the unit to check and must start with a letter or number, followed only by letters, numbers, `.`, `_`, `@`, and `-`, without a `.service` suffix; validation happens before any path construction or `systemctl` call, so option-like names are rejected. The systemd path is shared with `update` and lives in `cli/server_management.py` (`restart_server` / `is_systemd_managed`).
- `server status [--host] [--port] [--data-dir]` reports running/not running, resolved URL, WebUI available/unavailable, resolved data dir, and log path. A non-vBot listener at the target prints a conflict note but still exits 0 for `status` so automation can inspect the state.
- `desktop [--host] [--port]` is the first **local GUI-launch** action — it opens the pywebview Desktop window pointed at a local or remote server, and is **not** an RPC command and **not** server lifecycle. It branches before the shared `resolve(...)` (like `home`/`server`/`doctor`/`update`/`uninstall`/`autostart`) and never builds a `ServerInstance`; it lazily imports `desktop.main` (so the default CLI path needs no pywebview) and forwards **only** the flags the user actually supplied, so a bare `vbot desktop` reaches the launcher's last-used auto-connect path instead of a silent localhost target. It takes no `--data-dir` (the Desktop uses its own per-user config dir, not the server data-dir; see `desktop.md`). The call blocks until the window closes, then prints `desktop window closed` and exits 0; a missing `[desktop]` group surfaces the launcher's install hint as a failure exit. This remains the console/terminal launch surface; package installation separately exposes `vbot-desktop` as a GUI-script entrypoint for windowless Windows Start-menu launch.
- `update [--host] [--port] [--data-dir] [--discard | --stash] [--no-restart] [--service-name]` is a local self-updater (`cli/update_management.py`) for git-based installs. It reads `.vbot-install.json` and preserves the recorded install shape, exact dependency groups, Python executable, and complete server target; each explicit target flag overrides only its matching recorded field, while an omitted field falls back to the manifest before normal legacy resolution. A legacy checkout is inferred once but persisted only after update preflight passes. Branch installs use `git pull --ff-only` and `npm ci`; detached release installs preflight the latest tag's `webui-dist.tar.gz` before changing the checkout. Dependency and WebUI completion use their own persisted digest/revision markers, so either step is retried after a partial failure even if Git already advanced. On Windows, the updater refuses before mutation when the exact environment-local `vbot.exe` package launcher is active and prints a one-time source-based resume command through the recorded Python executable; a successful launcher-independent run migrates an existing installer-owned `bin/vbot.cmd` to the Python module entrypoint, so later updates do not lock pip's replaceable launcher. On Windows Desktop shapes, the updater separately matches running processes against the exact environment-local `vbot-desktop.exe` before any checkout/manifest mutation and again immediately before pip; a match fails with a close-Desktop instruction and the same source-based resume command, so another installation's same-named launcher is irrelevant. Any pip failure also prints that launcher-independent resume route because pip may already have removed the editable package metadata or normal `vbot` launcher. After dependencies are current, Windows Desktop shapes require that Desktop launcher and invoke the setup helper's shortcut-only mode so existing Start-menu entries migrate to the windowless GUI launcher; a missing launcher or failed shortcut write fails the update and is retried on the next run. WebUI assets are unpacked into staging and swapped as a wholesale `dist` replacement with the previous dist restored on extraction or swap failure. Desktop Client installs skip WebUI work and server restart. Tracked changes require `--discard` or `--stash`; the updater restores its named stash after both successful and failed attempts, while a pop conflict keeps the stash and prevents a misleading restart. Only after all managed steps succeed does it record the applied revision and restart a server installation through the shared systemd-aware path. In a Bash-injected vBot Run context, the public invocation remains exactly `vbot update`: the updater detaches one private helper outside the old server's process containment, strips all `VBOT_RUN_*` environment, waits for the outer server-owned launcher to finish, performs one normal restart, logs its outcome, and exits; ordinary callers retain synchronous restart behavior. It never touches the data dir. External git/pip/npm/PowerShell calls have bounded timeouts and disable interactive Git credential prompts. Interactive output reads the live version from `pyproject.toml`, flushes an announcement before update work, keeps the detailed step report, and ends with an explicit version transition or unchanged-version success sentence; partial failures that already changed the version are not reported as clean success.
- `uninstall [--app-only | --data-only | --all] [--yes] [--host] [--port] [--data-dir] [--task-name] [--service-name]` owns the local removal/reset orchestration in `cli/uninstall_management.py`. A TTY caller with no mode gets a four-choice menu (application only, data only, both, cancel); non-interactive callers must provide one mutually exclusive mode and `--yes`. The target defaults to the complete server target in `.vbot-install.json`, then normal Config resolution, and explicit target flags win. A Desktop Client owns no local server target: application-only and targetless all remove only the accessor installation without resolving, probing, or stopping a default server; data-only requires `--host`, `--port`, and `--data-dir` together, and a targetless interactive uninstall offers only application removal. Data-removing modes show the exact resolved path and require `DELETE` unless `--yes`; guards refuse filesystem roots, the user home, a path containing the installation, and a path containing the caller's cwd. Application removal also refuses when the caller's cwd is inside the installation. Data-only stops the target, deletes its directory, and restores the prior running state; an active systemd user unit is stopped/started through `cli/server_management.py`, while unmanaged/Windows servers use normal lifecycle primitives. Server-owning application-removing modes synchronously stop the exact selected server before launching cleanup, use the systemd unit when it owns the target, abort without handing files to a remover when that stop fails, and preserve data for application-only. Linux then replaces the CLI process with `scripts/uninstall.sh`; Windows launches an elevated helper after UAC, waits for the current `vbot.exe` to exit, and invokes `scripts/uninstall.ps1`. The Windows caller reports the absolute application directory and explicitly distinguishes successful helper launch from completed removal; UAC cancellation or another launch failure can leave a previously running server stopped but precedes application/data deletion. Both bundled scripts repeat the mandatory stop for server-owning installs before removing Autostart, launchers, packages, data, or the managed environment, while a manifest-backed Desktop Client skips that stop unless explicit data removal selected a complete target.
- `autostart enable | disable | status [--host] [--port] [--data-dir] [--task-name] [--service-name]` is a local OS-autostart manager (`cli/autostart_management.py`), OS-branched: Windows Task Scheduler logon task, Linux systemd **user** unit + login lingering. Windows uses the Task Scheduler COM interface to create a passwordless per-user task with the current user's interactive token and low UAC run level; registration, status, and removal require no elevation and distinguish a genuinely absent task from Scheduler failures. The task invokes the active Python environment's `vbot-autostart` GUI-script launcher, which delegates to `server start` while suppressing its console output; this keeps login windowless without changing normal interactive `vbot` output or its 10-second readiness budget. The Windows launcher instead allows 60 seconds for cold-start readiness, and its task retries a failed launch up to three times at one-minute intervals. Resolution consults `PATH` only when that environment has no launcher, preventing another checkout from silently winning registration. If registration fails, `enable` still attempts the normal-user managed start and returns failure with both outcomes. Linux unit paths are constructed only after the restrictive shared service-name validation, unit values quote and escape executable/path arguments and systemd `%` specifiers, and an enable failure rolls the prior unit back. Generated units use `KillMode=mixed`: systemd first signals the main process for normal Runtime teardown and removes every remaining descendant from the service cgroup after `TimeoutStopSec`, including after a crash. Disable checks `systemctl`/reload failures instead of deleting the unit and claiming success; status reports unknown `systemctl` states as failures. `enable` registers autostart and requests a start now (Linux via the unit; Windows via a managed background start). A failed `loginctl enable-linger` is a warning that boot-before-login is not guaranteed, not a false full-success claim. `disable` leaves an already-running server alone. Runs without an already-running server. The installers call `vbot autostart enable` by default (opt out with `--no-autostart`).
- `agent list|show|create|update|rename|delete` maps to `agent.list`, `agent.get`, `agent.create`, `agent.update`, `agent.rename`, and `agent.delete`. `agent create <agent-id> <name>` and `agent rename <current-id> <new-id>` take primary ids positionally. Create/update accept the shared Run, Memory, prompt, Tool, Skill, delegation (`--subagent-allow`), and Agent Policy (`--compaction-policy`) fields; update additionally exposes clear-model/Policy flags, Workspace relocation (`--workspace` / `--default-workspace`, optionally `--copy-workspace-files`), Identity-Agent Project selection (`--project` / `--clear-project`), name, and current Session. Rename is its own RPC because id changes coordinate the complete Identity Agent tree and live references; it is never folded into ordinary update flags. These location flags preserve the core separation: Project controls cwd for relative file/shell work, while Workspace remains the SOUL/Memory home.
- `agent update` rejects empty updates before RPC and prints the valid update flags. `--copy-workspace-files` requires a Workspace destination in the same command and maps to the RPC's non-persisted `copy_workspace_identity_files` operation input. Clear/default flags send JSON `null` or the stored empty model sentinel for the corresponding inherited value, while literal domain values such as `--thinking-effort none` remain distinct from clearing the field. `agent show`, `create`, and `update` report Workspace, default Workspace, Project, delegation, own/effective Agent Policy, and configuration-source provenance; relocation output additionally reports copied/backed-up files. A full Agent response with no effective Model remains a successful persisted resource for onboarding but appends an explicit cannot-run warning plus `model list --task chat` and `agent update --model` recovery commands.
- Channel config/lifecycle commands map to their matching `channel.*` RPCs. Add requires exactly one token source: recommended `--token-stdin` sends the UTF-8 stdin value as a write-only managed `token`, while `--token-env` references an already externally managed variable; `set-token <id> --stdin` rotates the configured credential and prints its non-secret effective source/applied state, targeted-adapter restart decision, immediate health, and a status verification command. `--platform` accepts `telegram` or `discord`; `--allow` and `--mention-pattern` replace their complete lists, while omitted update fields remain unchanged. `--response-mode` and `--observe-unaddressed` expose the Channels-owned group-gating policy. `channel identity <id> [--user <id>]` shows or sets the Channel account's own identity, `channel access <id> --group <scope>` lists one group's saved participants/admins, and `channel grant-admin|revoke-admin <id> --group <scope> --user <id>` are additive idempotent one-user mutations. Create/update/enable/disable and access mutations print saved state; `channel status` separately prints enabled/running/failed plus failure reason and denied inbound chats with an explicit allowlist suggestion (see `channels.md`).
- `provider list` calls `connection.list` and prints configured connections — per row `enabled`, `usable`, `reachable` (auto-refresh connections only) — including per-connection account sub-lines (`id`, `usable`, `source`). `provider status <provider-id> [--connection <provider:connection-id>]` filters that same RPC result and should print available candidates plus a close-match suggestion when the target is missing. `provider usage [--connection <provider:connection-id>]...` calls `provider.usage`, with repeated filters when supplied, and prints each live subscription plan, used/remaining percentage, reset timestamp, and isolated Provider error; this is separate from persisted Session statistics.
- `provider custom-list`, `custom-save <provider-id> --name ... --base-url ... [--adapter openai_compatible] [--auth api_key|none] [--api-key ...] [--models-endpoint /models] [--model <wire-id>]...`, and `custom-delete <provider-id>` map to `provider.custom_*`. Save is a complete replacement of the Provider record; repeated `--model` values create conservative manual chat Models, while the WebUI or direct validated `settings.json` editing exposes richer Model facts. The optional key is write-only and command output never echoes it.
- `provider enable|disable <provider-id> [--connection <provider:connection-id>]` calls `connection.set_enabled`. Without `--connection`, a single-connection provider resolves automatically; a multi-connection provider fails with the candidate connection ids. On enable, the output reports the probe outcome for local auto-refresh connections ("endpoint reachable" / "endpoint not reachable — the connection stays enabled") and hints at `provider set-key` when the enabled connection has no credential yet. Keyless local providers (e.g. Ollama) start disabled — this is the agent's switch to turn them on.
- `set-key`, `unset-key`, `connect`, `disconnect`, and `connect-status` all accept `[--account <account-id>]` — a named credential slot on the connection (omitted means the server default `default`). The CLI passes it through and renders the resolved Account from the response; semantics live in `providers/connections.md` → Identity and Accounts.
- `provider set-key <provider-id> <api-key> [--connection <provider:connection-id>] [--account <account-id>] [--refresh-models]` calls `provider.set_key`, which writes the resolved account's derived API-key credential to the data-dir `.env`, reloads runtime provider credentials, rejects OAuth connections, and never returns or prints the secret. `--refresh-models` chains `model.refresh_db` for the same provider only after the credential update succeeds.
- `provider unset-key <provider-id> [--connection <provider:connection-id>] [--account <account-id>]` calls `provider.unset_key` to remove that account's API-key credential from the data-dir `.env`. When the response reports the account still configured (process-environment credential), the CLI says so and points at unsetting the variable there.
- `provider connect|disconnect|connect-status <provider-id> --connection <provider:connection-id> [--account <account-id>]` maps to `provider.connect`, `provider.disconnect`, and `provider.connection_status`, all per (connection, account). `connect` starts the OAuth device flow and prints `user_code`, `verification_uri`, expiry, and the follow-up `connect-status` command (with `--account` appended for non-default accounts); the server polls in the background, so the CLI stays non-interactive. `connect-status` prints `connected=` and `flow_active=`.
- `model list` calls `model.list` and exposes the RPC's Provider, capability, task, modality, and minimum-context filters through repeatable flags. The server includes only Models with at least one usable Connection; CLI rows print the exact selectable id, effective context window, capability/task summaries, and local `reachable: no` state when present. `model show <provider>/<model-id>` calls `model.get` and prints the complete loaded Model projection as deterministic JSON, including supported voices/task options and usable Connections. `model list --task chat` is the primary recovery/discovery command for an Agent without an effective Model. `model refresh [<provider-id>]` calls `model.refresh_db`, stages a complete copy of the active Model DB, refreshes the requested Provider projections, and atomically publishes the whole database under `<data_dir>/artifacts/models/`; it never writes the installed checkout. `scripts/refresh_model_db.py [<provider-id>]` is the maintainer-only system-target client for updating this branch checkout's tracked `resources/models/`, and the RPC rejects it unless the serving checkout matches the requested resources path.
- `project add|list|show|set|set-override|clear-override|rm` maps to the corresponding `project.*` RPCs. Add/set expose Project defaults, Source Format, auto-load files, Tool Whitelist, and bundled/global/Project Skill policy lists; clear flags remove the Project tier. `set-override`/`clear-override` target one Team Agent field (`model`, `temperature`, `thinking_effort`, or `compaction_policy`) without editing the repo. Add/set/override mutations print the saved Project and fresh scan preview including effective Tools, repo denials, overrides, and per-field provenance. `rm --copy-rooted-agent-files` maps to `copy_rooted_agent_identity_files`; output reports the archive path, unrooted Identity Agents, and copied/backed-up identity files. Project work remains stateless — there is no current-Project flag; the Project rides the `agent@projekt` address form on Agent arguments.
- **`agent@projekt` address form on positional agent arguments.** The `session` and `cron` agent positionals accept `agent@projekt` (e.g. `session list orchestrator@vbot`, `cron create builder@vbot ...`) and pass the string straight to the RPC, which owns the one parse seam (`core.projects.parse_agent_address`); the CLI does not re-parse. A bare name is identity (unchanged). Project agents are displayed in the address form (e.g. `cron list` shows the server's `target`). `session link-channel` keeps the bare `<agent-id>` form (channels stay identity-only).
- `session list|create|fork|rename|set-compaction-policy|delete|link-channel` maps to the corresponding `session.*` RPCs. `fork` optionally re-homes the copy through `--target-agent`; `rename` explicitly sets/clears the title; `set-compaction-policy` sets a full JSON Session Policy or clears it to resume live inheritance and prints override/effective/source. `delete` refuses without `--yes` and prints the landing `next_session_id`. List rows include title, timestamps, source Channel, and own/effective Session Policy when returned.
- `cron list|create|update|delete|enable|disable` maps to the `cron.*` RPC handlers. `cron create <agent-id> --name <name> --prompt <text>` requires a non-empty human-readable name and exactly one of `--cron <expression>` (recurring) or `--at <iso-datetime>` (one-time) — the CLI derives `schedule_type` from which flag is used; `--session` is optional and names need not be unique. Cron expressions and offset-free Once values use the server timezone; the CLI has no timezone flag. `cron update <job-id>` accepts the same flags, including optional `--name`, plus `--status active|paused` and rejects empty updates before RPC. Create/update/enable/disable print the saved job with name before id, qualified target, schedule, status, and next fire time; list uses the same row projection.
- `debug status|traces|trace <trace-id>|clear|probe <provider-id> --connection <provider:connection-id>` maps to `debug.status`, `debug.trace_list`, `debug.trace_get`, `debug.trace_clear`, and `debug.model_probe`. `trace` prints the full sanitized trace as sorted JSON; `probe` prints status/duration/trace id plus the model preview and never dumps the raw response (it points at `debug trace <id>` instead). Trace listing and probing fail server-side while debug mode is disabled; `status` and `clear` always work.
- `task-model list|targets|options|set|set-option|unset-option|clear` maps to `task_model.settings`, `task_model.list_targets`, `task_model.options`, `task_model.update`, and `task_model.patch_options`. `<task-type>` is validated locally against `SUPPORTED_TASK_TYPES`. `options` uses the current binding when its optional target is omitted and prints the field schema plus configured/effective values. `set` accepts either a whole `--options` object, UTF-8 `--options-stdin`, or repeatable typed `--option <name> <value>` pairs. `set-option`/`unset-option` mutate one current-binding field without replacing siblings; `set-option --stdin` supports JSON values without shell-quoting loss. Every successful mutation prints the saved binding, and `clear` sends an empty target.
- `skill list` calls `skill.list` and prints the effective catalog plus unavailable, optional-missing, and invalid diagnostics. `skill read|create|update|delete|write-file|remove-file` maps to the matching `skill.*` RPC for editable `global` or `agent:<id>` scopes; Project/bundled/Extension scopes remain unwritable, content may come from a local `--file`, and destructive operations require `--yes`. Mutation output prints normalized operation/name/scope/warnings. `tool list` calls `tool.list` and prints registered public Tools.
- `statistics overview|usage|runs|errors|tools|skills [--since <iso>] [--until <iso>]` (`cli/statistics_management.py`) makes one `statistics.report` RPC call and renders only the requested section as deterministic plain text; `--since`/`--until` are passed through verbatim (the server validates ISO-8601 and window order). Every section has an explicit empty state. Overview labels visible Chat messages separately from stored records and includes interrupted Runs; Usage and Runs call Assistant Provider responses Model steps; Runs prints cancel, failure, and interruption rates; Errors states its last-Model proxy attribution; Tools states that Statistics does not read arguments. The `skills` output separates Skills whose recorded offers produced no conversion from Skills without offer data, then reports total activations, activations matched to recorded offers, and offer conversion per Skill.
- `extensions` is **name-first**: the first token is either a reserved verb (`list`/`reload`/`enable`/`disable`) or an extension name, routed in `dispatch_extensions_command` (argparse cannot enumerate dynamic names, so this area uses a `selector` + `rest` positional pair instead of fixed sub-parsers). `list` prints loaded/failed/disabled/overridden extensions with status, version, capabilities, failure reasons, and — for a `waiting` extension — what it is waiting for. `reload` (no args → usage error otherwise) calls `extensions.reload` (the full restart-equivalent rebuild) and prints a one-line status-count summary (`extensions reloaded: N loaded, N failed, N disabled, N overridden`) plus a `  <name> failed: <error>` line per failure and a `run 'vbot extensions list' for details` pointer when anything failed. `enable`/`disable <name>` read the current `extensions` section via `extensions.list` and write the full section back through `settings.update`; both apply **live** (no restart hint) — enabling additionally re-lists and appends `warning: '<name>' is <status>` (plus an `  error:` line) when the freshly rebuilt extension did not load.
- `extensions <name>` (bare name, no verb) shows one extension's settings from its `extensions.list` payload: each schema field with type + current value, a secret shown only as `set`/`not set` (never the value); a schema-less extension falls back to raw config. `extensions <name> set <field> <value>` writes one setting, **routed by the field's declared schema type**: a `secret` field calls `extensions.set_secret` (`{name, key, value}` — the caller names the schema field key, the server maps it to the declared `.env` key), any other field is coerced to its declared type (text/number/toggle) and written to the extension's live config via `settings.update`. Both are applied **live, without a restart**. `--stdin` reads the value (typically a secret) from stdin to keep it out of shell history; an empty value clears a secret. Unknown extension/field get available-candidate + did-you-mean output.
- `prompt list|update|reset|create|remove|set-layout|reset-layout|preview` maps to the matching `prompt.*` RPCs. Every command accepts `--scope default|agent:<id>`; the management function maps a non-default selection to the RPC scope object and omits the default object because the server already defines that default. Content may come from a local `--file`, while storage writes remain RPC-owned. Layout is a locally shape-checked JSON array; preview prints text and Tool-definition token metadata plus the rendered System Prompt.
- `log list|read` maps to `log.list` and `log.read`. The CLI must not read `<data_dir>/logs/` directly; `log read <daily-log-name>` prints parsed entries plus the returned cursor.
- `config` is the public Settings-path catalog and is equivalent to `config list`; `config list [<prefix>]`, `describe <path>`, `get <path> [--details]`, `set <path> <value>`, `unset <path>`, and repeatable `patch --set <path> <value> --unset <path>` map to `settings.catalog`, `settings.get_path`, and `settings.patch`. Patch operations are one atomic server mutation; invalid or overlapping operations persist nothing. Values are JSON-decoded before falling back to strings. Static segments are dotted and dynamic map keys are bracketed JSON strings. Mutation output reports active value, pending restart value when applicable, application lifecycle, and aggregate `restart_required`. `config effective` prints `settings.values`; `config raw` is the explicit diagnostic-only internal document. Secrets stay on their dedicated Provider, Extension, and Channel commands.
- `doctor settings [--data-dir]` and `doctor config [--data-dir]` run locally without a reachable server. The first validates `settings.json` through Settings; the second asks Settings to discover the full bundle and delegate each file to its owning domain. Both report missing files as OK when defaults apply and format the shared diagnostics as severity, JSON path, and message for agent callers.

## Conventions

- Shared `--host`, `--port`, and `--data-dir` target options apply to server lifecycle, uninstall/reset, and RPC-backed management commands. Doctor commands accept only `--data-dir` because they are local file validators.
- Port resolution follows `--port` > `VBOT_SERVER_PORT` > validated `settings.json` port keys > `8420`, using the shared host/port resolver (`DEFAULT_HOST`, `resolve_port`, `resolve_server_bind`) that now lives in `core/utils/config.py`. The CLI imports it from there (via `cli/server_management.py`) and does **not** import the `server` package for it; `server/main.py` re-exports the same names for compatibility. Ambient `PORT` and `SERVER_PORT` process environment variables are ignored; those names matter only when present as settings keys inside `settings.json`.
- All local CLI HTTP disables proxy/`.netrc` environment trust (`trust_env=False`) — the RPC transport, the health/WebUI probes, and the updater alike. The CLI only ever talks to the local server over loopback and RPC bodies carry secrets (e.g. `provider.set_key`), so a credential is never divertible off-host through an ambient `HTTP_PROXY`. A target counts as vBot only when `/health` returns HTTP 200 and JSON exactly equal to `{ "status": "ok" }`.
- Built WebUI assets are optional. Missing `webui/dist` may make `/` unavailable while `/health` is healthy; lifecycle output reports `webui: unavailable` instead of treating startup as failed.
- CLI output is agent-facing. Success and failure output must be explicit enough for an agent to choose the next command without guessing; silent success and silent failure are invalid. Central printers emit fallback success/error lines if a command result unexpectedly has an empty message.
- The process entrypoint reconfigures stdout and stderr to UTF-8 with `backslashreplace` before dispatch. Commands such as `debug trace` must therefore print Unicode-rich server payloads without crashing under a legacy Windows console code page; imported streams that cannot be reconfigured keep their own output contract.
- `extensions <name> set <field> --stdin`, `channel add ... --token-stdin`, and `channel set-token ... --stdin` share the explicit UTF-8 stdin reader (a leading BOM is accepted), strip trailing CR/LF, and return a normal failure without calling the setter when decoding fails; they never fall back to a legacy code page that could silently corrupt a secret or text value.
- Local lifecycle subprocesses (`update`, `uninstall`, `autostart`, and systemd server management) capture bytes rather than locale-decoded text. `decode_command_output()` prefers UTF-8 and falls back to the process locale with undecodable bytes escaped, so Git/Node Unicode and native localized tools both remain usable and a decode failure cannot erase stdout/stderr used for track or status decisions.
- Successful mutating commands name the target and action performed. Read commands print enough structured state for follow-up decisions. RPC failures and malformed envelopes surface as non-zero exits with clear messages.
- Failures include server RPC error code/message when available. For bounded identifiers such as providers, connections, settings keys, agents, channels, prompt fragments, and log files, prefer available-candidate output and `did you mean` suggestions when the CLI has enough local/RPC-returned candidates.
- CLI-managed lifecycle logs belong under `<data_dir>/logs/` through the managed `LogManager`. Background server startup must not bypass that logger or rely on raw child stdout/stderr.
- Tests mirror the module split under `tests/cli/`. When changing parser shape, command behavior, output text, target resolution, or lifecycle behavior, update the focused CLI tests.
- The bundled product skill `resources/skills/vbot-cli/` (a lean SKILL.md routing to per-area files under `references/` — server, providers, agents-projects, channels, cron, bootstrap, configuration, skills, diagnostics, telegram-setup) teaches vBot's own Agents the CLI surface. Its update workflow creates and verifies a one-shot current-Session Bootstrap before a restarting `vbot update`, then asks that Run to inspect server status and logs without repeating the update. When command shapes, areas, or flags change, update the matching reference file (and the SKILL.md area table if areas/subcommands changed) in the same change.

## Constraints & Gotchas

- The CLI is an accessor, not a second control plane. Do not add management commands that write `settings.json`, Agent configs, Channel configs, prompt fragments, logs, model catalogs, or other runtime files directly; route them through server RPC unless the command is explicitly local lifecycle/home/desktop-launch/doctor/update/uninstall/autostart behavior. `home` only reports locally resolved paths; the `desktop` launch is a local GUI action. Neither uses RPC or constructs a `ServerInstance`.
- If a vBot server is already running at the target address/port, `start` reports `already running` and does not spawn another instance. If a reachable non-vBot process occupies the target, `start`, `stop`, and `restart` fail with a conflict and must not terminate that process.
- `server status` reports `running: no` plus a conflict note for non-vBot port occupants, and this specific status conflict maps to exit code 0. The same conflict is a failure for `start`, `stop`, and `restart`.
- Process termination is allowed only after `/health` confirms the target is vBot. Local process lookup must match the resolved host/address and port, not port alone; wildcard listeners are matched only when they can receive the requested target traffic.
- Stop is best effort: terminate first, kill after the bounded timeout, and report `forced: true` when the kill fallback was needed. If the bounded wait after `kill()` also times out, `stop_server` returns a failed `CommandResult` with `forced=True` rather than raising or claiming success; startup cleanup suppresses the equivalent second timeout so it cannot replace the original readiness failure. On Windows this can still interrupt in-flight Runs abruptly.
- Live reachability and `/health` classification are the authority. The CLI intentionally has no stale PID or launch-metadata recovery path.
- Startup waits for health readiness and cleans up the just-spawned child if readiness times out, the child exits early, or a non-vBot responder appears during startup.
- `provider set-key` accepts a direct API-key value because agents are expected to configure local vBot instances through the CLI. It must send the value only to `provider.set_key` and must never include the secret in success, error, log, or refresh output.
- Channel token values must never be command-line arguments or output. Managed setup/rotation reads them only from stdin and sends them only to `channel.create`/`channel.set_token`; `--token-env` carries a variable name, not a token.
