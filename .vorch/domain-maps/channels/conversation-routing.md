# Channel conversation routing and ingress

The engine's ingress entry points, the per-conversation FIFO and its capacity, Session routing through conversation anchors and pointers, Commands and navigation, and platform chat-id migration.

## Ingress

- The engine's ingress surface: `handle_inbound_text` (authorize a Command or gate/enqueue text), `handle_inbound_media` (gate then enqueue one message or buffered album), `trigger_internal_reply` (note-driven Run whose reply relays like any answer), `trigger_interaction_reply` (reserved Run taps -> `enqueued`/`denied`/`busy`/`already_handled`/`unavailable`), `ensure_channel_session` (routing for the proactive `channel_send` entry). Text/media ingress reports admission and accepts bounded observed context (`channels/groups.md`). The engine owns the per-conversation FIFO, immediate-vs-serialized Command scheduling, generic `CommandOutcome` projection, Run relay, navigation/metadata, and platform-aware unavailability text; Chat owns every Command workflow.
- A closed database fails ingress and outbound work with `DatabaseUnavailableError` before anything is sent, bound or created (`tests/core/channels/test_channels_delivery.py`, `test_engine_routing.py`).
- Media-ingest is per-message: one failing item never drops siblings, identical failure replies deduplicate per batch, and capacity rejection happens before any download (shared busy reply at most once per chat per 30 seconds).

## FIFO and capacity

The engine serializes inbound messages, reserved Run taps, serialized Commands, and media work per conversation through one FIFO keyed by platform target. A conversation's FIFO and worker Task exist only while it has work: the worker retires once its FIFO is empty, with no await between that check and its removal, so the next item either joins the running worker or starts a new one, never a second concurrent one (`test_engine_queue.py`). Every queued candidate first reserves capacity in `ChatRunManager`: a chat may hold at most 8 waiting items (`CHANNEL_WAITING_WORK_LIMIT`), and the shared waiting-work limit of 32 counts all queued Runs and reservations of the process, not only Channels' (`runs.md`); reservations transfer into the Run FIFO when the Session is busy. Ordinary queued work resolves the active Session in the worker, so work queued behind `/new` follows the new pointer. An origin-bound Run tap instead retains its exact Agent/Session route through the FIFO and rechecks that the Session exists before triggering; a missing origin fails without fallback. It repoints the anchor before enqueuing, but processing never overwrites subsequent navigation. Immediate Commands consume no Queue capacity (`/stop` works even when both limits are full). Non-text media is never prepared as a Command; RPC may prepare exactly one `TextBlock` because Chat owns structural eligibility.

A removed queued Run admission ends only that inbound turn with the cancellation reply; the Channel worker continues with its followers and releases their waiting-work reservations.

## Session routing

- The derived id is a stable conversation anchor; routing resolves the conversation's `channel_conversations` pointer first and falls back to the anchor itself. The pointer is Channel state: deleting or archiving the anchor Session does not reset it. All inbound text/media, observed messages, and proactive `channel_send` follow the pointer; without one the anchor *is* the session ("no pointer" is the default - no migration branch). A claimed origin-bound Run tap repoints the anchor at the invoking Identity Agent Session before entering the FIFO, so following platform messages continue there; `/new` repoints it to a fresh Session id from `new_session_id()` and detaches the platform again; no Session exists until the conversation's next inbound message (or a proactive `channel_send`) creates it with its Channel metadata, like any missing pointer target. The agent-wide `current_session_id` is deliberately not consulted for channel routing.
- `channel_conversations(channel_id, conversation_id, conversation_kind, active_session_id, updated_at)` holds the pointer per derived anchor id. A row exists once a conversation was first pointed; a NULL `active_session_id` means the anchor itself is active.
- An example of the ambiguous derived id: `tg` with chat `-100123` and `tg-` with chat `100123` both derive `ch-tg--100123`. When a conversation without a pointer finds its anchor Session already holding another Channel's own anchor (that Session's `source_channel_id` and `platform_conv_id` derive the same id), routing leaves it to that Channel and points this conversation at a fresh `ses_` Session; the check runs inside the metadata write, so concurrent first messages cannot both claim the anchor. A Session another Channel's pointer merely shares (a Run tap) stays shared (`test_engine_routing.py`).
- Routing re-asserts the Channel metadata through `ChatSessionManager.ensure_metadata`: a known conversation with unchanged context costs only reads, and a first message creates the Session with its context in one write. A repeated `channel_send` target writes only its outbound note (`test_engine_groups.py`).
- Discord threads route as their own chats; Telegram forum topics share the parent group Session while delivery follows the topic via `thread_id`.

## Commands and navigation

Slash Commands execute the shared live Chat-owned set through `prepare`/`execute` - neither transport has a command-name switch. `/new` creates no Session and returns `new_session` navigation; the engine repoints the conversation at a fresh `ses_` id (`sessions.md` -> `new_session_id()`), not an id derived from the anchor, and replies that a new Session started. `/handoff` and Extension follow-up Runs relay generically without changing `ChannelConfig.agent_id` or the source anchor. Every `/agent` form is refused before execution with `The /agent command is not available through <Platform>.` - permanent wording, never implying future implementation.

## Platform chat-id migration

Telegram group->supergroup upgrades: the new chat id's conversation gets a one-hop pointer at the old active Session (no Session is created for the new anchor), that Session's Channel metadata moves to the new id, a session note informs the model, and the allowlist swap plus the merge of the group's admins and participants into the new access scope persist without restarting the adapter; idempotent when the old id is gone. How migrations interact with config changes: `channels/config-lifecycle.md` -> Supervision and health.
