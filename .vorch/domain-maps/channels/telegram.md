# Telegram Channels

Telegram adapter for vBot channels. Owns the Telegram platform I/O behind the shared conversation engine: long polling, update parsing, media ingestion, the typing indicator, and Telegram outbound send.

## Overview

`core/channels/telegram.py` implements the first concrete `ChannelAdapter`. It is reduced to Telegram platform I/O: `python-telegram-bot` async long polling, parsing updates for text, photos, documents, voice messages, audio, video, video notes, and animations into `ConversationFacts` and canonical content blocks, Telegram outbound send, and the typing indicator. It composes a `ChannelConversationEngine` (see `channels.md`) and implements `ConversationTransport`; the engine owns queueing, command handling, run trigger/relay, and session routing/metadata. Inbound files are stored through the runtime `AttachmentStore`, downloaded inside the engine's per-conversation worker (not the update handler). It does not own channel config storage, RPC methods, or the `channel_send` tool registration lifecycle; those stay in the parent channels domain.

## Data Model

- Telegram channels use the generic `ChannelConfig` with `platform: "telegram"`. `token_env_var` names the Telegram bot token credential; `allowed_chat_ids` is the inbound allowlist; `dm_scope` controls direct-message session derivation; `response_mode`/`mention_patterns`/`observe_unaddressed` control group response gating and passive context capture. Group authorization comes from the parent Channels access store (see `channels.md`).
- `platform_target` is a Telegram chat id rendered as a string. Adapter sends parse it back to an integer and raise `ChannelConfigError` when it is not an integer chat id. The optional `thread_id` (a forum topic id, also an integer string) rides beside it: all outbound paths (`send`, `send_text`, files, media groups, the typing action) put it on the wire as `message_thread_id` on **every** chunk/item, so multi-part replies never fall into the General topic.
- `ConversationFacts.thread_id` is set only for real forum topics: `message_thread_id` is used **only when `is_topic_message` is set**, because non-forum supergroups also fill `message_thread_id` for plain reply threads and sending it back into a non-forum group fails with "message thread not found". Session routing ignores the topic (all topics share the group Session, see `channels.md`); only delivery follows it. `access_scope_id` is always the parent Telegram group chat id, so every topic shares one admin list.
- The adapter classifies a conversation's `kind` for the engine: negative chat ids are `group`, all other chats are `direct`; Telegram private chats use `chat_id == user_id`. The engine derives the concrete session id from `kind` and `dm_scope` (see `channels.md`).
- The adapter supplies the per-message addressing facts on `ConversationFacts`: `message_id` (from `effective_message.message_id`), `mentioned_bot` (case-insensitive runtime-derived regexes for both `@botusername` and the bot's visible Telegram full name over message text *and* caption; the name matches as a complete name with flexible internal whitespace, never as part of a longer word), and `is_reply_to_bot` (`reply_to_message.from_user.id == bot id`). The visible name comes from `get_me()` on every adapter start and is not persisted into `mention_patterns`, so a Telegram rename takes effect after a Channel restart while configured aliases remain independent.
- Session creation and proactive target resolution write only Channel metadata. Interactive Telegram text/media, private `/start`, and reserved `run:` taps supply a Chat-owned reply surface whose display name is `Telegram` and whose conversation kind is explicit; Chat decides whether the direct/group reminder is needed when the Run starts.

## Interfaces

- `TelegramChannelAdapter(config, trigger_service, chat_sessions, credential_resolver, attachment_store=None, *, command_dispatcher, chat_migration_persister=None, interaction_dispatcher=None, run_button_binding_registry=None, access_registry=None)` - constructor injection only, no runtime handle; `credential_resolver` is the `Callable[[str], str]` passed down from `ChannelService`, `chat_migration_persister` is the service's `record_chat_id_migration` bound to this channel, `interaction_dispatcher` is the live-reading extension button-tap dispatcher, `run_button_binding_registry` is the ChannelStorage-backed origin/idempotency seam used only by reserved Run taps, and `access_registry` supplies platform-neutral participant roles to the engine. Extension taps bypass the composed `ChannelConversationEngine`; reserved `run` taps deliberately enter it.
- `start()` builds a Telegram application (with PTB's `AIORateLimiter` - see Constraints & Gotchas), registers text, media (photo/document/voice/audio/video/video-note/animation), unsupported-message-type, and a `CallbackQueryHandler` (button taps), fetches the bot's own identity with `get_me()` after `initialize()` (id + username + visible full name feed addressing detection, reply-to-bot checks, and `/cmd@botname` parsing), loads the persisted update-id watermark (`UpdateOffsetStore`, see `channels.md`), deletes the webhook with `drop_pending_updates=False`, starts polling, and waits until stopped. Every inbound handler claims its update id first: ids at or below the watermark are re-delivered duplicates and are dropped before gating or dispatch; the watermark persists atomically off-loop after the claim, so a graceful stop never loses it. Message handlers are restricted with `filters.UpdateType.MESSAGE` to new messages only: edited messages and channel posts are ignored (edits must not trigger new Runs; `filters.UpdateType.MESSAGES` would still match `edited_message` and is deliberately not used). The `CallbackQueryHandler` is **additive** - a `callback_query` is a distinct update type, so it is never wrapped with `UpdateType.MESSAGE` and the existing message handlers are untouched.
- A `StatusUpdate.MIGRATE` handler (registered first) reacts to group->supergroup upgrades, which change the chat id in place and would otherwise silently kill the allowlist and access-scope match: it swaps the old id for the new one in the runtime allowlist, persists the swap plus access-state migration via `chat_migration_persister`, bridges the conversation through `engine.migrate_group_conversation` (see `channels.md`), and sends a best-effort confirmation into the new chat. Authorization is the *old* id's allowlist membership; Telegram announces the migration twice, so the second event finds the old id gone and is a no-op.
- Location (incl. venue), contact, and poll messages are rendered as bracketed text (`[location shared] ...`, `[contact shared] ...`, `[poll] ...` with one `- option` line each) and routed through the normal inbound-text path - same gating, observation, and queueing as typed text. A group location can therefore only trigger via reply-to-bot (its rendered text has no wake word); that is accepted.
- Every remaining real user message type (stickers, dice, games, ...) falls into a catch-all handler that sends the eager "this message type isn't supported yet" reply; no Run is triggered and no Session is created. The reply is gated through `engine.should_respond(conversation)`, so unaddressed group stickers stay silent. Status updates (member joined, pinned message, ...) are excluded from the catch-all - service noise gets no reply; only the migration status update has its own handler. Animations are a first-class media type: the ANIMATION filter routes them to the media handler, and the animation payload is resolved before the backward-compat `document` field Telegram also sets on animation messages.
- The text handler strips a `/cmd@botusername` suffix from the first token before handing text to the engine - but only when the suffix matches this bot's username (case-insensitive). `/cmd@otherbot` stays unchanged and is therefore never dispatched as our command.
- For group text replies, the adapter carries the raw triggering Telegram message through the engine FIFO. After the trigger passes addressing and Queue admission, `build_quoted_message` inspects `reply_to_message`; when it belongs to a non-bot sender and contains a supported photo/document/voice/audio/video/video-note/animation, the adapter downloads and classifies that original attachment on demand. The engine combines it with the current question and original sender/role marker in one current-turn content list. A reply to plain text or to a bot message keeps the existing path, while an inaccessible original yields the engine's quoted-message-unavailable marker.
- Built-in and Extension Command behavior is platform-neutral and lives in Chat/`ChannelConversationEngine`; Telegram supplies parsing, authorization facts, reply targeting, and `platform_display_name="Telegram"`. Bare `/agent` and `/agent <target>` therefore both return exactly `The /agent command is not available through Telegram.` before Queue admission or Command execution; this is a permanent surface constraint, not an implementation-status message.
- `/start` in a **private chat** (Telegram's first-contact ritual) never reaches the model as literal user text: the adapter translates it into `engine.trigger_internal_reply` with a greeting instruction (plus the deep-link `start` payload when present), so the agent greets in its own voice via an internal note-driven Run. In groups `/start` stays on the normal command/gating path.
- `stop()` sets the stop event, cancels the engine workers and album flush tasks, then stops the updater/application and shuts it down.
- `send(message, platform_target, files=None, thread_id=None, buttons=None)` sends text, files, or both to one Telegram chat id. Text is split with `split_telegram_message(message, TELEGRAM_MESSAGE_LIMIT)`. When files are present, a message that fits `TELEGRAM_CAPTION_LIMIT` (`1024`) rides along as the first file's caption; a longer message is sent as standalone text first (so nothing is dropped) and the files go out uncaptioned. The transport's `send_text` reply callback routes through this method when no reply target is set; with `reply_to_message_id` it sends chunked text where only the first chunk carries `ReplyParameters(message_id, allow_sending_without_reply=True)` (deleted originals must not break the reply), while a `thread_id` goes on every chunk. When `buttons` is set, `_buttons_to_markup` builds an `InlineKeyboardMarkup` attached to the **last** text chunk only (a keyboard belongs on the final visible message); a keyboard cannot ride on a media group, so `buttons` **combined with** `files` is rejected with `ChannelConfigError` rather than silently dropped. Outbound sends and inbound file API calls run inside the same error boundary that translates `python-telegram-bot` errors (`telegram.error.TelegramError`, e.g. `BadRequest`) into `ChannelError`, so ingress, the `channel_send` tool, and the engine relay see the uniform ChannelError family instead of a raw PTB exception. The boundary classifies transient transport faults - `NetworkError` (including `TimedOut`) and flood-control `RetryAfter` (which also carries its wait hint) - as `retryable` on the ChannelError, while permanent rejections stay non-retryable; the engine relay and inbound file download both use the shared bounded retry policy.
- `ensure_outbound_session(platform_target)` builds `ConversationFacts` for the target (chat id alone determines routing: private chats use `chat_id == user_id`, negative ids are `group`) and delegates to the engine's `ensure_channel_session`, which creates the Session and base Channel metadata without a reply-surface note when missing.

## Interactive messages (button taps)

The tap path is owned entirely by the adapter and, for extension-handled prefixes, does **not** touch the engine, `should_respond`, `TriggerService`, or the per-conversation FIFO - such a tap is dispatched to an in-process extension, not turned into a Run (see `channels.md` -> Interactive messages, and `extensions/capabilities.md` -> Channel interaction handlers). The one exception is the reserved `run` prefix, which the adapter routes to the engine to wake the agent (below). All new PTB symbols (`InlineKeyboardMarkup`, `InlineKeyboardButton`, `CallbackQueryHandler`) come through `_load_telegram()`/`_load_telegram_ext()` - never a top-level `import telegram`.

- **`_handle_callback_query(update, _context)`** reads `update.callback_query` (`.id`/`.data`/`.from_user`/`.message`). It reuses `_conversation_facts(update)` (which resolves for a `callback_query` too - `effective_message`/`effective_chat`/`effective_user` are the tapped message, its chat, and the tapper) for chat/user/kind/message-id/thread-id, and reuses `_is_chat_allowed` + `_record_denied_inbound` for gating. Missing/empty `data` or a denied chat is silently acknowledged (`_best_effort_ack`) and never dispatched (a denied tap is also recorded). Otherwise it builds the neutral `InteractionEvent` (buttons via `_markup_to_buttons(message.reply_markup.inline_keyboard)` - empty tuple when no keyboard; `text` from `message.text`; `message_id` = the tapped message, i.e. the edit target) and a `_TelegramInteractionResponder`. **If the tapped data's prefix is the reserved `RUN_TRIGGER_PREFIX` (`run`)**, it calls `self._engine.trigger_interaction_reply(conversation, event)` and returns before extension dispatch. `enqueued` is silently acknowledged and closes the keyboard; `already_handled` closes it with an explanatory toast; `unavailable` closes it with an alert; `busy` and unauthorized group taps are silently acknowledged but keep the keyboard for retry. Unexpected handling failures log internally and produce the same unavailable alert without exposing details. Non-Run taps call the injected `interaction_dispatcher` when present, then send a **fallback ack** if `responder.answered` is still false - so every tap is acknowledged exactly once and the tapper's spinner always stops.
- **`_TelegramInteractionResponder`** implements `InteractionResponder` over the bot + `callback_id`/`chat_id`/`message_id`/`channel_id`: `answer()` -> `bot.answer_callback_query(...)` (sets `answered`); `edit(text=...)` -> `bot.edit_message_text(...)`, else `edit(buttons=...)` -> `bot.edit_message_reply_markup(...)`. An **empty** `buttons` list removes the keyboard - it maps to `reply_markup=None` (an empty `InlineKeyboardMarkup` would not clear it on Telegram). Both wrap the Bot API call in `_telegram_error_boundary`, so a failed edit/ack surfaces as `ChannelError` (logged, never fatal - the fallback ack still runs).
- **Neutral <-> PTB helpers** (`_buttons_to_markup(rows)`, `_markup_to_buttons(inline_keyboard)`) are the only place that maps `InteractionButton.label`/`.data` <-> PTB `InlineKeyboardButton.text`/`.callback_data`.
- **Concurrent extension-tap clobber is accepted.** Each extension-owned tap carries Telegram's keyboard snapshot at tap time, so two near-simultaneous taps on the same message can each edit from a stale snapshot and revert the other's flip. It self-heals (the tapper re-taps); PTB's sequential update processing (`concurrent_updates` off) mildly mitigates it. Core does not persist extension-owned selection state; an extension may hold its own authoritative in-memory state to avoid it. Reserved Run buttons are different: their origin/consumed binding is durable and one-shot even across restart, while the model still reads checklist selection state from the keyboard snapshot.

## Conventions

- Telegram tokens resolve through the injected `credential_resolver` (Runtime wires `resolve_environment_credential`, which prefers process environment over the data-dir `.env` fallback). The adapter never reads `os.environ` itself; a missing or empty token raises `ChannelConfigError` at construction. Managed creation/rotation is parent-Channels control-plane behavior (`channel.create` with `token`, `channel.set_token`): it updates the fallback snapshot and rebuilds only this adapter, so Telegram I/O owns no secret persistence or server-restart logic.
- Empty `allowed_chat_ids` denies all inbound Telegram chats.
- A visible-name address is a plain group message from Telegram's perspective. BotFather privacy mode must be disabled for Telegram to deliver it; @username mentions, replies, and Commands remain available with privacy mode enabled.
- Every allowlist-denied inbound message (text, media, structured, unsupported-type - all four gates) is recorded in the adapter's `DeniedChatLog` for the channel-status discovery flow (see `channels.md`): display name is the chat title for groups and the sender name for direct chats. The first denial per chat logs at info, repeats at debug, so a chatty denied chat cannot flood the log. The migration status-update handler does not record (not an inbound user message).
- PTB processes this adapter's updates sequentially (`concurrent_updates` stays off; the engine queue owns ordering), so the update handler must never await slow work. The handler only parses the update, checks the allowlist, and hands off to the engine; serialized Commands, normal Runs, and media downloads run in the engine's per-conversation worker, while immediate Commands execute outside it according to Chat's prepared execution mode. The engine reserves shared waiting-work capacity before a worker calls `build_media_blocks`, so an over-limit message receives the throttled busy reply without starting a Telegram download. The adapter owns only platform batching state: albums by `media_group_id`, plus a 500 ms possible-forward-comment buffer. A non-command text with a valid message id is held for that window; a directly adjacent forwarded medium (`forward_origin`, same chat/user/topic, next message id) claims it as `companion_text`, so Chat receives one Run with leading `TextBlock` + media. Non-matches flush as their original text turn, and every Chat-recognized Command bypasses the delay. Album state buffers raw messages, one merged `ConversationFacts` (a username/name address or reply-to-bot on any item addresses the whole album), and any claimed companion text; the flush hands them to `engine.handle_inbound_media`, where gating includes both companion text and captions. Queue ordering, response gating, Command projection, and relay/reply rules live in the engine (see `channels.md`).
- The transport's `activity_indicator` shows Telegram's `typing` chat action, refreshed every `_TYPING_REFRESH_SECONDS` (4 s, since Telegram expires the action after ~5 s) by a background task scoped to an async context manager. The indicator is best-effort and cosmetic: `send_chat_action` failures stop it quietly (debug log) without affecting the reply, and it is always cancelled when the engine's relay/compact block exits.

## External Dependencies

- `python-telegram-bot[rate-limiter]` - async Telegram Bot API client used for long polling, inbound handlers, outbound messages, media groups, and file download; the `rate-limiter` extra (aiolimiter) backs the `AIORateLimiter` flood-control pacing.

## Constraints & Gotchas

- Outbound calls run through PTB's `AIORateLimiter` (configured in `_build_application`): it paces sends against Telegram's flood limits (~30 msg/s overall, 20 msg/min per group) so multi-chunk replies and media groups do not trip flood control, and retries a send Telegram answers with `RetryAfter` up to `_SEND_MAX_RETRIES` (3), honoring the server delay. Without it a flood-control error mid-reply would lose the remaining chunks; only after the retries are exhausted does the error surface as `ChannelError` via the send boundary.
- Telegram measures its length limits in **UTF-16 code units**, not Unicode code points, so an astral-plane character (most emoji) counts as two. `split_telegram_message` chunks by UTF-16 length up to `TELEGRAM_MESSAGE_LIMIT` (`4096`) and never splits inside a character - code-point slicing would let an emoji-heavy chunk exceed the wire limit and fail with `BadRequest`.
- Outbound image files use `send_photo`; non-image files use `send_document`. Multiple files are partitioned into image and document batches, sent in groups of at most 10 homogeneous media items, and the caption is attached only to the first item of the first batch. Captions are capped at `TELEGRAM_CAPTION_LIMIT` (`1024`) UTF-16 units; an over-limit message is sent as standalone text instead of a caption (see Interfaces -> `send`).
- Inbound captions become a leading `TextBlock`; a reunited forward comment precedes both the caption and media as its own `TextBlock`. Photos store the largest photo variant and become `MediaBlock`; voice/audio/video/video-note/animation payloads become `MediaBlock` with the server-sniffed media type (filenames default to `telegram-voice-<unique>.ogg`, `telegram-audio-<unique>`, `telegram-video-<unique>.mp4`, `telegram-video-note-<unique>.mp4`, `telegram-animation-<unique>.mp4` when the platform provides none). Documents are classified by their server-sniffed type, not by Telegram's delivery channel, through the shared `content_block_for_attachment` rule in `adapter.py` (identical across channels): image/audio/video documents become `MediaBlock`; a text document is one `FileBlock`, whose bounded text rendering happens later in the chat resolver; and any other document becomes `FileBlock`. An MP3/MP4 sent as a Telegram *document* is therefore media (native audio or transcription, video path note), not a generic file - exactly like a voice/video message. Whether audio goes native, gets transcribed, or fails is decided by the chat-layer resolver, not the adapter.
- Inbound media requires the runtime-owned `AttachmentStore`. Without it the transport's `build_media_blocks` raises, which the engine maps to the generic media-failure reply with no Run for that payload. The adapter builds blocks per message; per-item isolation, the failure->reply mapping (`AttachmentTypeNotAllowedError`/`AttachmentTooLargeError`/other), and reply dedup are engine-owned (see `channels.md`).
- An oversized file is rejected before its body is fetched: `_store_inbound_attachment` calls `bot.get_file` (metadata only - size and path) and then `AttachmentStore.ensure_within_limit` on the reported `file_size`, so `download_as_bytearray` never runs for an over-limit file. When Telegram omits `file_size`, the store's post-download size check is the backstop (the Bot API also caps `getFile` downloads at 20 MB). The `AttachmentTooLargeError` flows through the engine's media-failure mapping to the "file too large" reply.
- Telegram albums are grouped by `media_group_id`; the 500 ms flush window (`_ALBUM_FLUSH_SECONDS`) restarts with each buffered item, so slow album delivery does not split one album into multiple Runs. The handler buffers raw messages plus an optional reunited forward comment; downloads happen in the engine's worker after the flush hands them off.
- With BotFather privacy mode on (the default), Telegram only delivers group messages that @mention the bot, reply to one of its messages, or are commands - visible-name addresses and unaddressed group messages never reach the adapter at all. Visible-name matching and `observe_unaddressed: true` therefore require privacy mode to be disabled through BotFather.
- Telegram includes the replied-to message inside an addressed reply update, so a user can reply directly to another participant's previously unobserved media and address vBot; vBot does not need to have received or downloaded the original post. A Telegram reply references one album item, not the complete media group, so on-demand ingestion sees only the item Telegram embeds in `reply_to_message`.
- User-facing Telegram failure replies must not leak internal exception text. Exhausted transient inbound downloads are identified as messaging-platform download failures and ask the user to resend; unsupported or oversized files retain their distinct replies. Lifecycle failures are logged by the adapter; trigger, command-execution, Run-relay, and media-ingest failures are logged by the engine with Channel/Session/target/command context and traceback detail for operators.
- Lifecycle stop tolerates Telegram `RuntimeError` from already-stopped components; other lifecycle failures are warnings, not hard shutdown failures.
