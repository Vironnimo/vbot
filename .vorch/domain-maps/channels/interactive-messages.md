# Channel interactive messages

Buttons on outbound messages, Run-button bindings, taps and checklists across Channels; per-platform tap completion (when keyboards close, toast/alert wording) lives in `channels/telegram.md`.

## Taps

A message can carry an inline keyboard; tapping produces a tap event normally routed to an in-process extension handler, so extension-owned taps are handled deterministically with no Run. Channels carry the neutral interaction contract (`InteractionButton`/`InteractionEvent`/`InteractionResponder` from `core/extensions/interactions.py`); extension tap-handling logic lives in extensions (`extensions/capabilities.md`).

- Extension-handled taps bypass the engine entirely - no `should_respond`, no `TriggerService`, no FIFO (queuing taps behind Runs would add latency). They reuse only inbound identity + allowlist plumbing; a denied tap is recorded and silently acknowledged, never dispatched.
- **One reserved prefix wakes the agent:** authors emit only the public form `run:<payload>`; no extension can claim it. For an Identity Agent `channel_send`, the tool supplies its calling Session as `run_origin`; the service swaps the wire callback for an opaque versioned binding (public values preserved durably) and removes the binding only when the send failed before anything could be shown: a failure before the adapter started sending, or a `ChannelError` without `possibly_delivered`. A possibly delivered send, an unexpected exception or a cancellation while sending keeps it, so a tap on a delivered button still works (`test_channels_delivery.py`). On tap: verify Channel/target/thread, claim the binding once, restore the public keyboard for the model-facing note, verify the origin Session exists (never recreate), repoint the conversation anchor, queue an internal Run there - the reply still relays to the tapped chat and a following platform message enters the same FIFO behind the tap. A duplicate tap is terminal even across restarts; invalid bindings return `unavailable` without fallback Sessions. Queue rejection, cancellation, or preparation failure restores the pending claim and reverses only this tap's conversation pointer (a conditional update that leaves later navigation in place). Bound tap preparation, admission and compensation serialize per Session anchor, including distinct buttons that target the same Session; waiting taps retain that lock and idle anchors retire automatically. Compensation completes even under repeated cancellation; only admitted or terminally unavailable taps remain consumed. An unadmitted bound tap, including one failing on a closed database, restores its pointer and binding before the error propagates (`tests/core/channels/test_engine_interactions.py`). Project-session `channel_send` keeps raw callbacks and wakes the Channel's current active Identity Session.
- **Checklists** (`checklist.py`): `channel_send`'s `checklist` builds the keyboard through `checklist_keyboard`: one row per item with label `<glyph> <label>` (`⬜` open, `✅` checked) and callback data `chk:<0|1>:<item id>` (the state it was sent with; ids at most `CHECKLIST_ITEM_ID_MAX_BYTES`, 58), then the call's other button rows, then the done button `run:checklist` (an ordinary reserved Run button, bound to the sending Identity Session like any other). The whole checklist lives in the message and nothing is stored: the adapter flips a tapped item's glyph in place (`toggled_checklist_buttons`, no Run, no Extension; prefix `chk` is runtime-reserved), and the Run note of the done tap reports only the items whose glyph differs from their sent state, by id and label (`checklist_changes`, `_format_interaction_note`), plus the count of unchanged items. Reporting changes rather than the full state keeps a submit from overwriting what changed elsewhere since sending (another device ticking an item the keyboard still shows open). Concurrent taps can clobber like extension taps (`channels/telegram.md`). Evidence: `test_engine_interactions.py`, `test_telegram_interactions.py`, `tests/core/tools/test_channel_send_delivery.py`.
- The interaction dispatcher is injected live-reading, so extension reload/disable needs no channel re-wiring - the next tap uses the current registry.
- Guaranteed single acknowledge: the adapter's responder tracks `answered`; after dispatch a fallback ack runs whenever the handler did not acknowledge (or none matched/it raised), so the tapper's spinner always stops. Extension tap state stays message-carried - the platform delivers the current keyboard with every tap. Reserved Run taps also persist their origin binding and, until a Run takes over, the accepted wire keyboard needed to reissue a retry after interruption (`channels/reply-delivery.md` -> Owed replies).

## Outbound buttons and bindings

- Outbound `send` validates `buttons` centrally (rows of `InteractionButton`, non-empty data <=64 UTF-8 bytes) before delegating, so a bad payload fails uniformly across adapters. With `run_origin`, the Channel must belong to that Identity Agent and its origin Session must exist.
- Only interactive-capable adapters honor `buttons`; Discord, Slack, Mattermost and WhatsApp reject them (`ChannelError`).
- A Run-button send checks its origin Session on the Session pool, then reads the Channel config, checks ownership and saves the binding in one `channels.db` hop, like other `channel.json` reads that belong to Channel state work.
- Cancellation during outbound Run-button preparation keeps a binding the `channels.db` worker already saved and removes it before returning, because its message was never sent. Repeated cancellation still waits for that cleanup on the `channels.db` pool.
- `channel_run_buttons(channel_id, binding_id, platform_target, thread_id, origin_session_id, button_data_json, created_at, consumed_at)` holds origin bindings for `channel_send`-authored `run:*` buttons - routing/idempotency state, not conversation state. A claim is one conditional update of a NULL `consumed_at` inside a write transaction, so of racing taps exactly one claims; consumed rows are retained (no retention limit yet) so a duplicate or post-restart tap cannot start a second Run.
