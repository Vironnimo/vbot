# Channel reply delivery

How a Run's answer and the engine's other replies reach the platform: the reply surface, Run relay, owed replies and their recovery after restarts, reply threading, and how send failures are classified.

## Reply surface

Every Channel Run whose output is relayed supplies `RunKind.CHANNEL` and a Chat-owned `ReplySurface` (platform, display name, Channel id, direct/group). Ingress also captures the reply plan's target and thread as runtime-only fields on that surface, including command-started Runs. Chat carries them to `ToolContext` so `channel_send` follows the same destination as the Run's text reply even when later ingress changes `last_reply_target`. They do not enter the persisted surface note, Model reminder, or surface identity; repeated Runs on the same surface do not repeat the reminder. Regression coverage: `test_engine_routing.py` holds a Run while another DM chat under `dm_scope=main`, or `/status` in another group topic, updates the Session destination; `test_chat_loop_tools.py` checks propagation to sibling Tool handlers.

## Run relay

The service marks the engine connected when the adapter reports its connection and disconnected when the adapter task ends, so a queued item or a finished Run's reply waits for the next adapter instead of failing on the stopped one.

Run relay keeps the latest ordinary Assistant output until the first preserved interrupted Assistant boundary, then accumulates partial plus recovery output; terminal states map to recovered/partial/generic failure/cancellation/empty-output replies. A cancelled or failed Run whose latest Assistant output is a complete answer (not interrupted, no Tool Calls), as after Stop during post-answer Compaction or a failure while recording the Run's end, delivers that answer instead of the cancellation or failure reply; a user input the Run received after that answer (a steered message) voids it, since it no longer answers the latest input; Chat keeps that answer complete in history (`chat/run-execution.md`). A Run cancelled because vBot shut down (cancel reason `shutdown`) is treated like an interrupted one: its kept partial answer, else the interrupted reply. One projection (`RunReply` in `_conversation_content.py`) serves live output and Session history. Every relay waits for the Run to end and projects its exact persisted history, so a bounded or late event replay cannot lose earlier answer fragments; observed live output is the fallback only when history is unavailable or empty. A live terminal outcome supplies the status when its summary could not persist; a Run left by an earlier process defaults to interrupted (Owed replies, below).

The same engine relay accepts background completion Runs: `ChannelService` validates the Run Agent and latest Session `last_reply_target`, hands the Run to the started Channel's engine (also while its adapter reconnects), and preserves the stored thread/topic target; `relay_run` returns once the Run ended and the engine delivers the owed answer.

Reply sends retry transient transport failures (the adapter-classified `retryable` ChannelError family) through the shared bounded backoff policy. A write is retryable only when the platform cannot have posted it - a rate-limit refusal, or on Telegram a connection that never opened; after a timeout, a dropped connection or a server error the message may already be visible, so a repeat would duplicate it (`core/utils/http_status.py`, per-platform rules in the child maps); when retries are exhausted the answer is logged at error level as lost, or as incomplete when a part may have reached the chat (`possibly_delivered`) - a reply is never silently dropped.

## Owed replies

`engine.py`, `channel_pending_replies`: admitted work that a Run will answer (not observed notes) is recorded as owed at admission, on the `channels.db` pool without blocking ingress; the Run's answer takes over that record (same `reply_id`, now with `run_id`), and a background or Command relay records its own. Admission and Run writes are ordered, survive relay cancellation, and are drained by engine stop, including when stop arrives before either write finishes. A send claims the record (`sending_at`), sends and deletes it; work that ended without a reply deletes its record. Admitted work that never got a Run answers through its record: a removed queued turn (for example from the WebUI Queue) gets the cancellation reply, a trigger failure the failure reply. Delivery is at-most-once: a claim succeeds once, and a reply left mid-send by an ended engine is dropped rather than repeated. A send that failed provably unsent (a `ChannelError` without `possibly_delivered`) while the adapter disconnected releases its claim and waits for the next connection. A recorded reply is never sent without a confirmed durable claim. Claim failures retry three times with backoff; after exhaustion the reply stays owed for the next engine, with a warning. A grouped claim failure releases its known unsent claims before retrying.

At start the Channel's next engine takes the rows earlier engines left (`take_pending_replies`, oldest first): a Run still running in this process (`TriggerService.running_run`) is followed to its end; any other Run's reply is projected from its Session history (`Session.load_run_messages_async`; no `run_summary` means interrupted). Ordinary rows without a Run become one notice per conversation/topic asking to send the message(s) again (`_UNANSWERED_*` texts in `engine.py`). Each queued Run-button tap gets its own retry notice with its saved wire keyboard, original message reference and topic, after its binding is successfully restored; that binding still admits only one tap. A missing binding, a failed restoration or an older row without a usable keyboard instead asks to send the request again, without a button. Startup runs `recover_interrupted_runs` before Channels start, and shutdown closes Channels before `ChatRunManager`, so Runs cut off by a shutdown or crash reach the next start through history. Replies sent from the adapter's own inbound handling (busy, Command unavailability, Commands answered from ingress) never wait for a connection, because waiting would hold that adapter's shutdown (`test_engine_owed_replies.py`, `test_channel_state.py`).

`channel_pending_replies(channel_id, reply_id, platform_target, thread_id, reply_to_message_id, agent_id, session_id, run_id, binding_id, owner, created_at, sending_at, retry_keyboard_json)` holds the replies a Channel still owes its conversations (`PendingReplyStore`). `owner` names the engine that recorded the row; `run_id` (with the Run's Agent and Session) marks a Run's answer, its absence admitted work no Run answered yet; `binding_id` names the Run-button binding a queued tap claimed; optional `retry_keyboard_json` keeps that tap's wire keyboard until a Run takes over (open JSON payload, unknown fields preserved on roundtrip); `sending_at` marks a send in flight. The nullable keyboard column is reconciled additively when an older database opens; older rows remain readable without it. Rows of an ended engine that were mid-send or are older than 7 days (`PENDING_REPLY_RETENTION_SECONDS`) are deleted unsent when the next engine takes the rest.

## Reply threading

All engine replies tied to one inbound message use the reply plan's `reply_to_message_id` (group replies reference the answered message); Tool-driven `channel_send` output never threads. Engine reply strings use the transport's `platform_display_name`.

## Send results and failures

- `channel_send` reports success only after `ChannelService.send()` and the adapter send complete - not fire-and-forget.
- A failed adapter `send` raises `ChannelError` with `possibly_delivered` set unless nothing of the message can be visible: a multi-part send sets it once a part was acknowledged (`DeliveryProgress` in `adapter.py`: chunks, file batches, text before files), and each write classifier sets it when the platform's answer never arrived or was a server error (Telegram timeouts and dropped connections, Discord connection and server faults, Slack/Mattermost request errors and 5xx, WhatsApp unconfirmed or disconnected bridge calls). A refusal (4xx, rate limit) or a connection that never opened leaves it unset. `channel_send` and the Run-button binding read it (`tools/channel_send.md`).
