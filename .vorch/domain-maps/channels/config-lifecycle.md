# Channel configuration and adapter lifecycle

Channel CRUD and config reads, what a platform, token or Agent change does to Channel state, and adapter supervision with its health logging; the domain-wide rules stay in `channels.md`.

## Config reads and CRUD

- `ChannelService` opens `ChannelStateStore` at construction, adopts every Channel id with a `channel.json` into the registry together with the platform that config names (keeping existing rows unless they belong to another platform, see Platform, token and bot changes), and closes it with the service.
- The async `get_channel` and `list_channels_async` read `channel.json` on the `channels.db` pool and are the only config reads of the RPC layer; `get_channel` raises `ChannelNotFoundError` for a Channel without config and `ChannelConfigError` for one whose config fails to load, which listings skip with a warning. `create_channel`, `update_channel`, `enable_channel`, `disable_channel`, `delete_channel` and `restart_channel` are async and write `channel.json` off the loop. The sync `list_channels`, prompt/Tool checks, enabled-state checks and synchronous adapter construction use `ChannelStorage`'s immutable published configuration snapshot: reads never acquire its file-I/O lock. Successful reads/writes publish detached values; failed writes retain the previous view, and explicit async get/list refresh hand-edited files. Create/delete existence checks, supervised/deferred restart refreshes and WhatsApp status/setup read on the state pool.
- `token_env_var`: managed tokens get a deterministic collision-free key (`VBOT_CHANNEL_TOKEN__` plus the Channel id's uppercase hex); externally managed deployments may supply their own key.
- `channel.create` and `channel.set_token` hold the shared Settings mutation lock through credential writes, adapter changes, rollback and publication, so a failed Channel change cannot overwrite another credential edit. Admitted mutations settle before request cancellation propagates; creation takes the Agent reference lock before this admission.
- Config reads pass through the Channels-owned schema; schema errors raise `ChannelConfigError` with file/path diagnostics, while runtime-only failures such as missing credentials do not mutate persisted config.
- Create resets any rows left under a reused id; delete removes `channel.json`, then unregisters the Channel, removing all its rows in one transaction. Both registry writes run together with their `channel.json` write as one unit on the `channels.db` worker pool (`Database.run_async`), never on the Event Loop: create writes `channel.json` first and removes both again when the registration, the adapter start, or a cancellation after the unit fails; delete stops the adapter on the loop first. Update, enable and disable read and write `channel.json` on the same pool (`_change_config`): the write lands before a running adapter is disturbed, so a failed write leaves config and connection untouched; the adapter then stops and starts on the loop, and a failed adapter start or a cancellation after the write restores the previous config and the adapter it ran (enabling a Channel whose start fails therefore leaves it disabled). A platform change also waits for the old adapter's stop and rebinds the state before the new adapter starts (below). Restart reads its config there too. While any of these config changes is in flight, every other change of that Channel id (create, update, enable, disable, restart, delete, WhatsApp setup/pairing) is refused with `ChannelError` (`_pending_config_changes`, `tests/core/channels/test_channels_service.py`, `test_channels_recovery.py`).
- Public create/update paths reject unknown Agent IDs before persisting. Create/update preflight adapter construction where possible and roll back persisted config if starting the enabled adapter fails. Runtime startup degrades per channel: a corrupt `channel.json` skips with a logged warning, one failed adapter marks only that Channel failed - startup never blocks as a whole.
- `restart_channel(channel_id)` preflights and rebuilds only that enabled Channel from current config and live credential, preserving server and sibling uptime; disabled channels retain the new credential for their next enable.
- Channel configuration checks distinguish absence from unavailable files or directories. Platform adoption retains an unavailable Channel with unknown platform, ordinary listings log and skip it while continuing with readable siblings, and direct get/delete report an access failure rather than `ChannelNotFoundError`.
- `channel.list` combines configuration with the same in-memory health, connection and denied-chat facts as `channel.status`; it does not read durable group access or WhatsApp pairing/QR state. Detailed group access is fetched when an accessor opens a Channel.
- `denied_chats(channel_id)` exposes the running adapter's rejected-chat log (empty when inactive) to the `channel.status` RPC, CLI status output, and the WebUI panel's per-entry Allow action; access reads/mutations work independently of adapter liveness. Allowlist-rejected chats land in this bounded recency log on the adapter - that log is the discovery workflow: message the bot once, read the id from status, allow it. Recording never changes gating; restarts clear the log.

## Platform, token and bot changes

User, chat, group and message ids of one platform mean nothing on another. A committed platform change (`channel.update` from RPC, CLI or the WebUI edit form, through `_change_config`) therefore resets that Channel's state in one transaction (`ChannelStateStore.bind_platform`): own identity, group access, conversation pointers, Run-button bindings, receipts, owed replies and watermark. The reset runs after the old adapter finished stopping, so its last writes cannot land afterwards, and before the new adapter starts; a failed change binds back to the previous platform, whose state then stays empty too. Only the pointer of the `dm_scope` `main` anchor (`main_conversation_id`), which names no platform id, survives: dropping it would revive the anchor Session instead of the Session `/new` or a Run tap moved to. A NULL `channels.platform` (no readable config yet) takes the first platform without a reset. At construction, `adopt` resets state recorded for another platform than `channel.json` names (a hand edit, or a change interrupted between `channel.json` and `channels.db`) and logs `Channel state reset for a new platform`.

Everything else deliberately stays: a rotated token or another Telegram or Discord bot (`channel.set_token`, `token_env_var`, the stored credential) keeps access and pointers because user and chat ids are global on both platforms; only the watermark is per bot (`channels/telegram.md`), and an old bot's Run buttons can never reach the new bot because Telegram delivers a tap to the bot that sent the message. A Slack workspace or Mattermost server change cannot be told apart from a token rotation or URL change of the same one; ids of another workspace or server are opaque and practically never match, so leftover rows stay inert (their groups remain visible in the access settings). WhatsApp re-pairing keeps its state (`channels/network-platforms.md`). Session metadata stays too: a completion relay refuses a reply surface of another platform, and a `channel_send` to a previous-platform `last_reply_target` fails as an ordinary Tool failure (`tests/core/channels/test_channels_platform_change.py`).

## Agent changes and the Identity Agent rename

- Changing a Channel to another Agent drains the old adapter before clearing its conversation pointers and Run-button origin bindings. The new Agent starts at its own conversation anchors; platform access, participants, receipts, watermark and owed replies stay intact. An Identity Agent rename preserves the routes because its Sessions move with it; unavailable platform credentials leave the renamed Channel visibly failed and retrying instead of rolling the Agent rename back. A failed change restores the previous config; routes already cleared remain cleared, like state reset by a platform change.
- `ChannelConfig.agent_id` is a live reference: the Identity Agent rename (`runtime/agent-rename.md`) retargets matching Channels through `retarget_agent_async`, its worker thread handing the call to the Event Loop that owns the adapters. A started service changes each Channel through `update_channel` with normal validation and per-channel rollback. A service that is not started (a rename that completes during startup, or a safe startup mode) only rewrites `channel.json` through `retarget_agent`, which refuses once the service runs, and never starts an adapter (`test_runtime_agent_rename.py`).

## Supervision and health

- Adapter failures restart with exponential backoff (`1s`, `2s`, `4s`, capped at `30s`). After 3 fast retries the channel is marked failed in runtime-local health state, but recovery continues indefinitely at the capped interval while enabled - a channel is the operator's lifeline, so transient blips must self-heal. An adapter up >= 5 minutes counts as healthy: its next crash resets counters. `is_failed()` never reports failure while the task runs. `channel.json` remains configuration truth. Restart backoff caps its exponent before numeric conversion, including arbitrarily large failure counts.
- Adapter construction failures at service startup, automatic retry, or deferred restart after shutdown enter the same recovery cycle. A failed constructor must not strand an enabled Channel; explicit stop/disable cancels recovery and stale callbacks cannot revive it.
- Health logging is owned by `ChannelService`, not the adapters: each adapter calls `_report_connected()` (`ChannelAdapter.observe_connection`) when its platform connection is up (Telegram after polling starts, Discord `on_ready`, Slack/Mattermost/WhatsApp when connected). The first report of an adapter logs INFO `Channel adapter started (channel, platform)`, or after a supervised failure one INFO `Channel adapter recovered (channel, platform, attempts, down_for)`; later reports of the same adapter log at DEBUG. A stop logs INFO `Channel adapter stopped`. A supervised outage runs from the first failure of a running Channel to its next connection or stop: that first failure logs one WARNING with traceback (at service startup an expected `ChannelError` such as a missing credential logs WARNING without traceback, an unexpected one ERROR; a deferred start keeps its ERROR), the crashes, failed restarts and restart attempts that follow log at DEBUG, and exhausting the fast retries marks the Channel failed with one WARNING (`_AdapterOutage`, `test_channels_recovery.py`).
- Telegram chat-id migrations share the service's per-Channel config lease with public changes: a migration waits for an ongoing change, while a public change refuses an ongoing migration without blocking the Event Loop. Platform changes release that lease before draining the old adapter; its late Telegram migrations leave the replacement platform untouched but retain their id rewrites for a failed or cancelled switch's Telegram rollback. Rollback replays group-access migration too, preserving access when cancellation occurs before the platform reset. Deferred starts reload persisted config after shutdown, preserving migrations completed by drained handlers. Repeated start/restart requests during one shutdown coalesce into one replacement.
