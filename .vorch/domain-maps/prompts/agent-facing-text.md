# Prompts Agent-facing text

Why each sentence of the Agent-facing text the Prompts domain owns exists: the System Prompt framing and notices `core/prompts/` renders (such as `SOUL_FRAMING`, `FILE_READ_HINT`, `FILE_TOO_LARGE_NOTICE` and `identity_runtime.md`), the Reflection and `/learn` brief fragments, and guidance sentences it renders for other domains. Rules for this file: `.vorch/workflows/domain-map-workflow.md` -> Agent-facing text.

| Text | Reason |
|---|---|
| `calls in the same response can run in any order` (`tools.md`) | States an execution fact alongside the existing rule to hold dependent calls back; `can` avoids reading the former `may` as permission. |
| `For Telegram messages, use plain text without Markdown formatting.` (`channels.md`) | Telegram delivery does not parse the Agent's Markdown as platform formatting. Kept in the System Prompt so it applies to automatic replies and Tool sends alike. Fresh-Agent eval 2026-10-14: DeepSeek V4.1 Flash used backticks and bold markers in its two file-task replies under the former "Use plain text for Telegram messages." wording; GLM 5.3 Flash used plain text. The user-approved follow-up explicitly names Markdown; its effect has not been evaluated with Models (`tools/channel_send.md` -> fresh-Agent eval). |
| `An admin can authorize any Tool available to you. A member can authorize only web_search and web_fetch.` (`channels.md`, names marked as code in the prompt) | Retains the existing group authorization boundary; `can` replaces ambiguous `may`. Together with sender tags, quoted-sender attribution and per-message approval rules, this stays in the System Prompt (user decision 2026-10-14); no Compaction preservation mechanism is added. |
| `[Not included: this file has {size} bytes, more than the {limit}-byte limit for automatically loaded files.` (`FILE_TOO_LARGE_NOTICE`) | Marks the cut: without it the Agent reads the empty frame as an empty file, or never learns that the instructions (SOUL, an include, a Project file) exist. |
| `The following is your SOUL: your role, how you work, your voice and your boundaries.` (`SOUL_FRAMING`, `core/prompts/_types.py`) | Labels the block as the Agent's own role and conduct, not reference data, and names the four parts a SOUL holds. Where the file lives, what belongs in it and when to change it live only in the `vbot-docs` Skill (`references/soul.md`), so an Agent that wants to change its SOUL loads that guide (user decision 2026-10-07). Earlier framings said "who you are", which invited any identity request such as a new name into SOUL.md, and carried change rules that did not stop it. Eval 2026-10-07 with this framing: GLM 5.3 Flash still edits SOUL.md directly through its Workspace path without loading the Skill (rename 2 of 3, requested change 2 of 2, unrequested change after feedback 1 of 2); DeepSeek V4.1 Flash loads the Skill and renames correctly in 4 of 6 runs, otherwise only offers it. |
| `## vBot Environment` (`identity_runtime.md` heading; formerly `Identity Environment` with `You are an Identity Agent in this vBot server environment.`) | Names the place the Agent works in with a word it can act on: the bundled `vbot-docs` Skill is the guide to vBot. The sentence went with the rename; `Identity Agent` is vBot vocabulary a fresh Agent cannot use. A sentence `You work inside vBot, which holds your settings, your Skills and your Sessions.` showed no effect on renames in the eval of 2026-10-07 and was not kept (user decision 2026-10-07). |
| ``- Your display name: `{agent_name}`; your Agent id: `{agent_id}` `` (`identity_runtime.md`) | Without it no prompt text tells the Agent its own name or id: it cannot answer to its name, and commands about itself (`vbot agent update <agent-id>`) need a lookup. The identity block is not pinned per prompt epoch, so a rename reaches later Runs without a Compaction. |
| ``When your work needs its content, read `{path}` with the `read` Tool, which returns large files in pages.`` (`FILE_READ_HINT`) | Gives the way to the rest. Only when the receiving Agent can call `read`: otherwise it points at a Tool the Agent cannot call. The absolute path because the Agent's relative paths can resolve against another directory than the file's (the Working Project's files, `project` Tool files); naming paging keeps Agents from dumping the whole file through the shell. |
| `... This is a background review: the user does not see your replies, and the user can see and undo every change you make. From now on only ... work; do not continue the task under review.` (`review-intro-*.md`) | The fork carries the whole task: without this the review answers the user or resumes the task. Reversibility counters the timidity of "no change is fine" texts. |
| `Act when the conversation shows one of these signals:` + per-scope lists (`review-signals-*.md`) | Hermes' signal list: concrete, observable triggers make weak Models act on corrections and not on long routine tasks. |
| `Without such a signal, reply "Nothing to save." and stop; ... With a signal, make the change: a lesson left unsaved repeats in every later Session.` (`review-signals-end.md`) | Quiet by default, active on evidence. The old "no change is a successful outcome" lead made reviews skip real corrections; Hermes' "be ACTIVE" without a gate produced junk. |
| `Store each lesson or fact in exactly one place: ...` (`learning-routing.md`) | The shared routing rule (`memory/agent-facing-text.md`): Skills hold task lessons and task preferences, Memory only all-work facts. |
| `This review changes only Memory|Skills, so leave ... unsaved.` (`review-routing-*-only.md`) | A single-scope review otherwise stores the other store's lesson where it can write. |
| `Never save: ...` (`review-skip.md`) | Hermes' do-not-capture list: setup failures, negative Tool claims, resolved errors and dead ends become standing self-restrictions. The general-conduct item stops a corrected guess from becoming a "do not guess" Skill or Memory entry (eval case `retracted_guess`). |
| `For Memory, first call memory with action list; ...` (`review-memory.md`) | The prompt shows Session-start entries; listing prevents duplicates and stale replacements. |
| `A Skill is SKILL.md plus optional support files. ...` (`skill-shape.md`, shared with `/learn`) | Hermes' Skill shape: procedure first, pitfalls as rules with a reason, one rule once, corrections in place, no restated Tool docs. |
| `Choose the first option that fits: 1. ... 4. ...` (`skill-ladder.md`) | Hermes' update ladder: patching the Skill in play beats new narrow Skills; the class-level name test keeps libraries small. Option 4 names the list check because reviews otherwise created a Skill after one failed load by name (A/B 2026-10-02). |
| `Before changing a Skill file, read its current text with skill ...` (`skill-read-current.md`) | Resolves the earlier brief conflict on read-before-write (one rule for reviews and `/learn`); `patch` with a short `old_string` fails safely on stale text. "change nothing" stops reviews from adding redundant clarifications to a Skill that already covers the lesson; "keep every unrelated rule" restores the baseline's "preserve unrelated content" after a review dropped a word limit inside its `old_string`. |
| `Here you can change only Skills listed under "Your own skills" that the list from skill does not mark as read-only ...` (`review-skill-limits.md`) | Names global and project Skills because the catalog heading "Your global skills" read as ownership: without it every protected-Skill eval run attempted the write (A/B 2026-10-02). Matches the background guards (`skills/history.md`) and the list marks (`tools/skill.md`); a Reflection merges and deletes like the Librarian (user decision 2026-10-03: the background writers are not restricted beyond the pin), so an overlap or a wrong Skill seen in the conversation is fixed at once instead of waiting for a pass; scripts cannot be run in a review. |
| `Finish with one or two sentences: ...` (`review-closing.md`) | The closing reply is the Run summary; refusals point here for changes the Run could not make. |
| `The user asked you to focus this reflection on:\n{focus}` (`REFLECTION_FOCUS_TEMPLATE`, `briefs.py`) | Appends the `/reflect` focus after the review brief as its own paragraph, so the brief's scope rules stay in force. |
| `The request to learn from is the user's /learn message after this note.` (`LEARN_REQUEST_TEXT`) or `No request was given. If the recent conversation clearly establishes reusable learning, apply the instructions above to it. Otherwise, ask the user what they want captured.` (`LEARN_WITHOUT_REQUEST`) | Ends the `/learn` brief by pointing at the user's request, which follows as the user's own visible message (the brief is its context note), or says what to do without one instead of manufacturing a Skill. |
