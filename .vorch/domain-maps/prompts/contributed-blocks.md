# Contributed Blocks

How Tool-, Extension- and temporary-Session blocks enter the System Prompt: On-demand Tools and `tool:load_tools`, the dynamic `tool:subagent` and `tool:bash` blocks, a temporary Agent's `prompt_blocks` selection and request-local blocks of bound temporary Sessions. The block contract and gates are in `prompts.md`.

## On-demand Tools and Tool-owned blocks

- On-demand Tools (`tools.md` -> Terms): while at least one of the Agent's Tools is on demand, `provider_tool_definitions` and the prompt definitions append the internal `load_tools` definition (an Agent whose Tool list keeps every Tool never gets it), and `build_system_prompt` / `render_dynamic_blocks` take `on_demand_tools` (Chat passes the Tool pin's `(registry name, summary)` entries). The `on_demand_tool_list` Producer renders them as `- {Model-facing name}: {summary}` lines (`- {name}` without a summary) in the given order; without `on_demand_tools` a build with `effective_tool_definitions` lists none, and a live build (previews) classifies its own definitions with `on_demand_tool_entries`. The On-demand Tools count for gate 2 and `tool_available` (they are callable, so guidance blocks such as `tool:subagent` and `memory:guidance` stay), and the live `core:tools_list` leaves them out like the pinned one (`test_prompts_tools_skills_extensions.py::test_on_demand_tools_are_listed_in_their_block_instead_of_the_tool_list`).
- `BlockRenderContext.tool_available` (`_tool_policy.py::tool_availability`) answers by registry name: plain membership in the given `effective_tool_definitions` or On-demand Tools, otherwise the Agent's live Tool policy, resolved once on the first question through the same path as the Tool list.
- The dynamic `tool:subagent` block renders exactly when its Tool is effectively available and agrees with provider visibility and addressing routing; preview supplies the same scope. In Chat its text is pinned per prompt epoch like every contributed dynamic block; previews render live. The `project` catalog lives in its Tool definition, with no dedicated prompt block (`tools/project.md`).
- The dynamic `tool:bash` block renders only with permanent `tools.bash.allowed_env` grants and lists credential names plus the `env_keys` contract; Skill-derived grants never enter the System Prompt (their payload carries its own notice at load time).

## Temporary Agents and Sessions

A temporary Agent's optional `prompt_blocks` selection overrides block enablement exhaustively while retaining layout order: `None` inherits the ordinary layout, an explicit list includes only selected active non-empty blocks, and newly registered blocks remain off. `build_system_prompt(block_details=...)` optionally collects rendered content, enabled/active state and actual inclusion for previews; this explicit inspection also renders disabled active blocks to show their content, without including them in the combined prompt. Normal rendering does not read disabled block files or invoke their renderers. Source/tests: `prompts.py`, `blocks.py`, `test_prompts_layouts_overrides.py`.

Bound temporary Sessions supply request-local data block definitions through `build_system_prompt`; the normal assembly engine owns ordering and joining. Chat gates and revalidates their exact Extension registration and complete Session Tool grant set. These definitions never enter editable/global block catalogs or unbound previews (`tests/core/chat/test_chat_loop_extension_tools.py`).
