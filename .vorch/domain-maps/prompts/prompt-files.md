# Prompt Files

How `render_prompt_file` reads the files vBot puts into a Model's Context on its own, and how `{include:...}` markers resolve.

## Reading a prompt file

`render_prompt_file` (`core/prompts/blocks.py`) is the single reader for every file vBot puts into a Model's Context on its own: workspace `{include:...}` files (SOUL included), Project instruction files (Working Project block and `project` Tool result) and folder instruction notes (`chat/request-building.md` -> Folder instructions). A file enters whole up to `INLINE_FILE_MAX_BYTES` (128 KiB, the same cap as `@`-mention snapshots): these blocks ride on every request of the Session, so the cap only stops a runaway file (generated dump, wrong path) from flooding the Context; real instruction files stay far below it. A larger file keeps its `<file>` frame but holds `FILE_TOO_LARGE_NOTICE` (size and limit) instead of its content; `FILE_READ_HINT` (the file's absolute path and `read`) is appended only when the receiving Agent can call `read`. At most cap+1 bytes are read, the file is not stamped read, and missing (includes only), unreadable and oversized files each log once per condition through `LoggedConditions` without content, with an INFO line when the file loads whole again; there is no aggregate budget across files. An optional `on_issue(PromptFileIssue)` callback reports missing, inaccessible, non-file, non-UTF-8, unreadable, and oversized inputs; the explicit `project` Tool uses it to explain partial loads without changing prompt assembly (`test_blocks.py`, `test_project_files_render_readable_files_after_memory_and_report_them`). Memory is not a file here: its scopes are cut to their Memory budgets by the Memory domain (`memory.md` -> Prompt block).

The manager's `render_project_files(project_context, *, tool_available, on_read=None, on_issue=None)` takes the caller's answer to which Tools the Agent can call (`tool_available`; the `project` Tool passes `ToolContext.can_call`), which decides `FILE_READ_HINT`. `render_project_skills(..., *, tool_available)` lists names/descriptions and names the `skill` Tool only when callable.

The `on_read` observer receives `(resolved_path, (mtime, size))` captured before the byte read, only for content included whole. Prompt assembly, prompt-epoch capture, Compaction and the explicit `project` Tool carry this stamp to `FileReadState.record_stamp` without restatting the path, so a concurrent rewrite never counts as content the Agent has seen. If a concurrent first build wins the prompt pin with different text, the losing render's reads are discarded; existing read stamps stay unchanged.

## Includes

`{include:filename}` accepts safe flat filenames under the agent workspace and renders through `render_prompt_file`: wrapped as `<file name="...">`, an oversized file as its notice, missing/unreadable files dropped with a warning (never aborting a run) - logged once per path and state rather than on every build, with an INFO line once the file loads whole again; unsafe paths in the template raise `PromptError`. That includes do not nest and that an empty workspace never resolves includes are domain rules in `prompts.md` -> Conventions.

Project instruction files (`projects/resolution.md` -> Project Context instructions) reach the System Prompt through the `core:working_project` data block (`prompts/core-blocks.md` -> Data blocks), each file through `render_prompt_file`.
