# Adding a Pinned Prompt Input

Task-gated depth for the prompt-epoch pinning contract in `prompts.md` (Assembly Pipeline): every file-backed System Prompt input is pinned per prompt epoch as a Session prompt pin and re-read from disk only when a successful Compaction starts a new epoch. The current pins are the Skill catalog, Working Project Context, SOUL block, and pinned-memory text.

Adding a new pinned input touches five places:

1. `core/prompts/pinned_context.py`: a `PINNED_*_SLOT` constant (Sessions accepts only slot names starting with `pinned_`) plus a wrapper built on `_pinned_epoch_text(dependencies, slot, agent_id, session_id, project_id, render)` - it returns the matching stored pin (`sessions.prompt_pin`) or renders and stores it through `sessions.ensure_prompt_pin`. A pin that must not survive a fork or move into another Agent or Project belongs in `AGENT_BOUND_PROMPT_PIN_SLOTS` (`core/sessions/_types.py`), which today holds the Skill catalog, SOUL and pinned-memory slots; the Project-qualified Working Project Context pin carries over (`sessions.md` -> Prompt state). Sessions stores each pin content-addressed in `prompt_blobs`, shared by forks. When the text depends on a Run-admission input that can change mid-Session (Memory mode, working Project), pass it as `attributes` so a changed value re-renders. When the input reads workspace files, collect `read_paths` inside the render closure and pass them to `stamp_prompt_files_read` so auto-injected files count as read-before-write (follow `pinned_soul_context`).
2. `core/chat/_run_state.py::create_run_execution_context`: resolve the wrapper and store the value on `_RunExecutionContext`, next to the existing pins.
3. `core/chat/_run_state.py::_CompactionPromptRefresh`, `core/chat/compaction_host.py` (`_prompt_epoch`), and `pinned_context.py::prompt_epoch_pins`: a successful Compaction commits every pin slot through its `PromptEpoch` when the new epoch starts (a `None` value removes that pin) - add the new slot (with the same attributes the reader checks) to that mapping.
4. The request-build call into `build_system_prompt(...)`: thread the value through so the System Prompt build receives it (grep the existing pins' path from `_RunExecutionContext`).
5. Prompts domain: the block renderer/producer returns the pinned text verbatim when present, and a public `render_*` method serves both the live render and the snapshot closure.

Adding a keyword parameter to `build_system_prompt` also breaks the duplicated prompt-manager test doubles - see `prompts.md` -> Constraints & Gotchas.
