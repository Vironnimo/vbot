# Adding a Pinned Prompt Input

Task-gated depth for the prompt-epoch pinning contract in `prompts.md` (Assembly Pipeline): what `core/prompts/pinned_context.py` pins, how dynamic block catalogs describe their entries, and the steps for adding a new pinned input.

Every file-backed System Prompt input is pinned per prompt epoch as a Session prompt pin and re-read from disk only when a successful Compaction starts a new epoch. The current pins are the Skill catalog, Working Project Context, SOUL block, pinned-memory text and the body of a Workspace-less Agent (`pinned_agent_body`; Project Config Agent or temporary participant). Two pins do not follow these steps: the Provider Tool-definition pin (`pinned_tool_definitions`) is not a System Prompt input, and the dynamic block pin (`pinned_dynamic_blocks`) holds the ordered inventory and texts of contributed Tool/Extension blocks (static and rendered), temporary Session blocks and Channels, whose gates depend on the Tool pin. Chat resolves both in `RequestBuilder.build_request_state`, and the Compaction commit takes both from the projected request state (`chat/request-building.md` -> Tool catalog per prompt epoch, Dynamic prompt blocks per prompt epoch). New contributions join the next Compaction snapshot; changes within the current epoch are announced through System Reminders. A pin without layout metadata adopts previously unpinned static/temporary contributions once while retaining its existing texts and epoch identity (`chat/request-building.md`). Concurrent first builds use the winning Session pin even when its text is empty; an empty snapshot is a value, not a missing pin (`test_chat_prompt.py`).

## `pinned_context.py`

`core/prompts/pinned_context.py` owns the Chat-side pinned-snapshot assembly persisted as Session prompt pins between Compactions, plus `stamp_prompt_files_read` for read-before-write state. Initial SOUL/Memory/Project renders stamp their reported files; snapshot reuse never updates stamps. Memory snapshots carry their rendering mode and refresh when that mode changes, while unchanged-mode file edits stay pinned. The Working Project Context and Skill catalog pins carry the `working_project_id` they were rendered for (the catalog: its Skill-scope Project), because Chat resolves the Working Project per Run admission and a Session's can still change: a move or fork into another scope, or a Project restored under a new id (`sessions.md` -> Terms -> Working Project), re-renders both at the next Run instead of showing the old Project until Compaction; a Run in the Workspace ignores a stale Working Project pin. A pin missing a qualifier re-renders (`tests/core/chat/test_chat_prompt.py`). `prompt_epoch_pins` returns the same qualified shapes for the Compaction commit's `PromptEpoch`. Called directly by ChatLoop/Compaction via a narrow dependency slice, no chat-owned copy. The module also names the `pinned_tool_definitions` and `pinned_dynamic_blocks` slots, but Chat resolves and commits those pins itself (`chat/request-building.md` -> Tool catalog per prompt epoch, Dynamic prompt blocks per prompt epoch).

The manager's `render_soul(agent)`, `render_memory_files(agent)` and `render_working_project_context(agent, project_context)` render Chat's epoch snapshots before a request exists, so a notice in them names a Tool by the Agent's live Tool policy. `build_system_prompt` emits the snapshots it receives (`working_project_context`, `soul_context`, `memory_files_context`) verbatim instead of reading the files; Working Project pinning covers only its own block. Its `read_paths` is a pure side channel reporting files actually read (only when rendering/refreshing a snapshot, never on reuse). The `memory_files` Producer likewise emits Chat's pinned epoch rendering verbatim instead of re-reading.

## Dynamic block catalogs

`render_dynamic_blocks` also fills two side channels: `block_order` receives the full resolved layout order; `read_paths` receives files read while capturing a snapshot. A renderer returns `str` or `RenderedBlock(text, catalog)`: a `BlockCatalog(title, entries, frame)` names the block's keyed entries (`(key, line)` pairs) and the rest of its content (`frame`), so a change can be told per entry. Built-in catalogs: `tool:subagent` (one entry per target id, frame = execution guidance), `tool:secrets` (title `Secrets`, one entry per Secret name with its Secret line, frame = the block head) and `core:channels` (title `Your configured channels`, one entry per enabled Channel id with its block line, frame = the block's unexpanded override or default text).

## Steps for a new pinned input

Adding a new pinned input touches five places:

1. `core/prompts/pinned_context.py`: a `PINNED_*_SLOT` constant (Sessions accepts only slot names starting with `pinned_`) plus a wrapper built on `_pinned_epoch_text(dependencies, slot, agent_id, session_id, project_id, render)` - it returns the matching stored pin (`sessions.prompt_pin`) or renders and stores it through `sessions.ensure_prompt_pin`. A pin that must not survive a fork or move into another Agent or Project belongs in `AGENT_BOUND_PROMPT_PIN_SLOTS` (`core/sessions/_types.py`), which today holds the Skill catalog, SOUL, pinned-memory, Tool-definition, dynamic block and Agent body slots; the Project-qualified Working Project Context pin carries over (`sessions.md` -> Prompt state). Sessions stores each pin content-addressed in `prompt_blobs`, shared by forks. When the text depends on a Run-admission input that can change mid-Session (Memory mode, working Project), pass it as `attributes` so a changed value re-renders. When the input reads workspace files, collect `read_paths` inside the render closure and pass them to `stamp_prompt_files_read` so auto-injected files count as read-before-write (follow `pinned_soul_context`).
2. `core/chat/_run_state.py::create_run_execution_context`: resolve the wrapper and store the value on `_RunExecutionContext`, next to the existing pins.
3. `core/chat/_run_state.py::_CompactionPromptRefresh`, `core/chat/compaction_host.py` (`_prompt_epoch`), and `pinned_context.py::prompt_epoch_pins`: a successful Compaction commits every pin slot through its `PromptEpoch` when the new epoch starts (a `None` value removes that pin) - add the new slot (with the same attributes the reader checks) to that mapping. An input that exists only for some Agents passes `None` for the others, which removes a stale pin (the Agent body: `_CompactionPromptRefresh.pins_agent_body`).
4. The request-build call into `build_system_prompt(...)`: thread the value through so the System Prompt build receives it (grep the existing pins' path from `_RunExecutionContext`).
5. Prompts domain: the block renderer/producer returns the pinned text verbatim when present, and a public `render_*` method serves both the live render and the snapshot closure.

Adding a keyword parameter to `build_system_prompt` also breaks the duplicated prompt-manager test doubles - see `prompts.md` -> Constraints & Gotchas.
