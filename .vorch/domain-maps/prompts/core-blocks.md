# Core Blocks

What each core, memory and data block renders, the Runtime variables, and the `core:channels` contract; the block model, gates and layout fallback stay in `prompts.md`.

## Core and data block ids

`core:runtime`, `core:identity_runtime` (owner `identity`), `core:tools`, `core:system_reminders` (the static anchor telling the Model that `<system-reminder>` messages come from vBot; Models distrust those messages without it, `model-communication.md`. It says nothing about Tool changes: each `[tool-change]` note says itself how to treat its Tool), `core:subagent_role` (owner `subagent_session`; tells a Sub-Agent who delegated its work and where its answers go, `subagents.md`; every scope reads the bundled `subagent_role.md` like `core:system_reminders`), `core:tools_list` (**ships disabled** - providers already receive Tool descriptions natively, so the prompt copy is an opt-in booster for models attending poorly to schemas), `core:channels`, `core:skills` (owner `tool:skill`), `core:skill_maintenance` (owner `tool:skill_manage`, Identity Agents only), `core:soul`, `core:working_project`, `core:agent_body` (data, per-run), `memory:guidance`, `tool:load_tools` (registered with the `load_tools` Tool, `tools/load_tools.md`: user-editable text whose default `LOAD_TOOLS_BLOCK_TEXT` is a Python constant, so a Runtime without prompt resources still boots; it wraps `{generated:on_demand_tool_list}` and requires that Producer). `working_project.md` backs the non-editable dynamic block. `core:permissions` is no layout block: Chat adds it per request for a restricted Run (`chat/request-building.md` -> Dynamic prompt blocks per prompt epoch). The bundled order and default enablement are `resources/prompts/layout.json`.

## Runtime variables

`{server_hostname}`, `{vbot_version}`, `{operating_system}`, `{model}`, `{agent_id}`, `{agent_name}` (the display name, the id when it is empty), `{identity_workspace}`, `{vbot_root}`, `{data_root}`, `{thinking_effort}`, `{current_local_date}`, `{timezone}` substitute exactly, one pass, non-recursively; unrelated `{...}` stays literal; vBot-authored path values use the forward-slash Model presentation; retired names have no aliases and remain literal. `runtime.md` (owner `always`) carries OS/model/thinking effort plus the current date in the configured IANA timezone and the timezone name - unset effort renders "provider default", never blank. Chat passes `build_system_prompt(thinking_effort=...)` the effort its prompt epoch pinned, so `{thinking_effort}` changes only at Compaction (`chat/request-building.md` -> Thinking effort per prompt epoch); a build without it (`prompt.preview`, other Model jobs) renders the Agent's live effort. The runtime block deliberately exposes no clock time: its date changes at most once per configured-zone day. This daily change remains an intentional exception to prompt-epoch stability (user decision 2026-10-13). `identity_runtime.md` (owner `identity`) carries hostname/version/workspace/roots, so Config Agents receive none of those.

## Data blocks

`core:soul` renders workspace SOUL.md through the single include-expansion path plus a framing prefix (kept out of shared wrapping so it never leaks onto other includes; missing/empty workspace returns "" before framing so the block gates out clean), pinned per prompt epoch. `core:working_project` renders the file-backed template from `ProjectPromptContext` (only `{project_name}/{project_id}/{project_workspace}/{project_files}`; retired `$project_*` unresolved); metadata renders once in Markdown while `<project_context>` wraps the instruction files (`Project.instruction_files`, `projects.md` -> Project Context) verbatim; their paths are taken verbatim with no location restriction, reads lazy and fail-soft (a missing file is skipped silently), each file through `render_prompt_file` (`prompts/prompt-files.md`). Identity Sessions working in a Project and Config Agents receive Chat's pinned prompt-epoch snapshot instead of re-reading; a Session working in its Agent's Workspace gates the block out. `core:agent_body` carries a Config Agent's body verbatim (empty for Identity Agents -> gates out); Chat pins the body of every Workspace-less Agent (Project Config Agent, temporary participant) per prompt epoch as `pinned_agent_body` (`pinned_context.py::pinned_agent_body`), so an edited Agent file reaches the System Prompt only at the next Compaction, with no announcement.

## `core:channels`

- The `core:channels` block (owner `always`, `requires_generated="channel_list"`) renders nothing without an enabled Channel of the Agent - no `- None` fallback. Its producer lists persisted enabled Channels as `- <id>: <platform>`, independent of adapter liveness or allowed-chat count. The block retains group sender/quote attribution and admin/member authorization rules in the System Prompt, plus Telegram plain-text guidance; send arguments and destination fallback belong to the Tool definition. The catalog gives no target-availability hint, because the admitted Run and Session can supply a destination even with zero or several configured allowed chats. Chat pins the block's text per prompt epoch like a dynamic block, so a Channel added, removed or changed mid-epoch leaves the System Prompt byte-identical and reaches the Model as a `[prompt-block-change]` System Reminder; the gate therefore depends on the channel list itself, which the pinned text carries, not on the live `channel` owner. `channel_send`'s definition names no Channel (`tools/channel_send.md`).
- `resources/prompts/channels.md` carries the static group-authorization contract (member attribution format, admin/member authorization split, authority-by-message rule); per-group identities and live roles never enter blocks or producers, so access changes never break the cache.
