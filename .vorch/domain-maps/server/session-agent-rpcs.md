# Server: Session, Agent and learning RPCs

The server side of `session.*`, `agent.*`, `tool.list`, `permissions.*` and `learning.*` in `server/rpc/session_methods.py`, `agent_methods.py`, `agent_refs.py`, `permission_methods.py` and `learning_methods.py`. The reference lock and mutation ordering they share with other handlers: `server.md` -> Overview.

## Session and Agent RPCs

- `session_methods.py` owns canonical Session RPCs (listing, activity/read state, create/delete/fork, title, Compaction policy, Agent overrides and Channel link). `session.create` accepts optional `agent_overrides` (`model`, `thinking_effort`, `temperature`, `top_p`; an unusable Model fails before the Session exists) and an optional `working_project_id` (`validation.py::_optional_working_project`; GLOSSARY -> Working Project: omitted -> the Agent's default Project, `null` -> the Workspace, a Project id -> that Project; an unknown Project -> `project_not_found`, a default Project that no longer exists -> `domain_error`, any value for a Team Agent address -> `invalid_request`), and its result names the new Session's `working_project_id`; `session.create` captures the resolved Model and effort, including explicit Provider default (`thinking_effort_default: true`). `make_current: true` is Identity-only; a Project Agent receives `invalid_request` before Session creation, because it has no current-Session pointer. `session.set_agent_overrides {agent_id, session_id, agent_overrides, remember?}` sets or clears (`null`) fields and returns the stored overrides plus their `effective` values. With `remember: true`, only Model and effort are accepted: the resolver preserves other live Sessions and also writes the Agent's start values for new Sessions, publishing both Session and Agent/Project invalidations. Without it the mutation remains Session-only. Both use the Projects resolver (`projects/resolution.md`). `session.activity_list` answers every requested Agent address from one Sessions read without resolving Agents; an address without completed live Sessions, including an unknown Agent, returns an empty list. `session.get` point-reads one live Session's list summary (`{session: null}` when absent) without Compaction Policy or active-Run fields. `session.list` and `session.get` rows carry the Session's `working_project_id` (`null`: the Workspace), its stored `agent_overrides` when it has any, and its `change_stats` totals when its Runs changed files, and `session.change_stats {agent_id, session_id, include_subagents?}` returns them with the changed files (`{change_stats: null}` when none), with `include_subagents` over the Session's Sub-Agent tree too (`sessions/runs.md` -> Change statistics). `session.list` and `session.project_groups` rows also carry `has_active_run` (Live voice reads it) and the Session activity as `activity_state`, `work_started_at` and `waiting_for` (`server/events-and-reconnect.md` -> Session activity). `session.project_groups {limit?, include_*?}` lists the newest Sessions of every Agent per registered Project (all of them, also without Sessions) plus a last group with `project_id: null` for the Sessions that work in no registered Project; built-in Agents' Sessions are left out, the Project groups follow the user's Project order (`projects/configuration.md` -> Project order), and each group is a `session.list` page (`sessions`, `next_cursor`, `total_count`). `session.list` with `working_project_id` (a registered Project id, or `null`) in place of `agent_id`/`agent_ids` continues one group; it refuses `required_session` and an unregistered Project. All Session list paths, including a single Agent and an `agent_ids` batch, resolve each listed owner's Compaction Policy once and fall back to the global policy for an Agent that no longer resolves; a missing Team definition never hides its persisted Sessions or fails the other Agents' rows (`sessions/lists-and-metadata.md`, `test_session_methods.py`). Channel-link and Compaction Policy changes use Sessions' atomic `mutate_metadata_with_previous` rather than replacing an earlier metadata snapshot; that mutation also rejects a missing Session, so neither handler reads the Session first. A Project Agent's delete landing is Sessions' `newest_session_id`, `null` when none remains; no Session is created for a landing (an Identity Agent's is its re-aimed current pointer, `archive/operations.md` -> Archive outcomes). `session.delete` names the archived and landing Session ids in its scoped `sessions` invalidation so other windows can leave the archived Session (`server/events-and-reconnect.md`). Under the reference lock it refuses a Session that `Runtime.automation_references` reports as selected by a live Bootstrap or Cron job (`automation.md`) with `session_in_use`: `message` names them as `kind:id`, `data.references` lists `{kind, id, name}` (the job name) for accessors (`tests/server/rpc/test_session_methods_delete.py`). Agent delete and Project removal need no such check: their reference guards (`agent_references` / `project_references` of the same owner) already refuse every live job and action targeting the Agent or Project; server RPC handlers apply no liveness rules of their own. Agent configuration/lifecycle stays in `agent_methods.py`; `agent.update` accepts `current_session_id: null` to clear the pointer (a new conversation, `agent.md`), and Agent payloads carry `current_session_id: null` while it is empty. Agent payloads carry `description` (`""` when none) and `agent.create`/`agent.update` accept it, `null` clearing it; `agent.suggest_description {id}` returns `{description}`, a Model draft it does not save (`agent.md`). Agent payloads carry the effective `tool_loading` at the top level (shared default baked in; `null` while neither sets it), the Agent's own parts as `config.tool_loading`, and `tool_loading_default`, the complete value it inherits; `agent.create`/`agent.update` accept the own value, `null` or `{}` removing it (`agent/configuration.md` -> `tool_loading`). `tool.list` items carry `loaded_by_default` (in the built-in always-loaded set); the internal `load_tools` never appears there. Both run their blocking Session and Agent store work on the Session database's pool (`ChatSessionManager.run_async`, or the Sessions async API) and resolve Agents through `AgentResolver.resolve_agent_async`; the RPC layer owns no pool for Session work, so a closed Session database surfaces as `domain_error` (`tests/server/rpc/test_session_methods.py`).

`agent.list`/`agent.get`/`agent.reorder` run their Agent store work on the Session database's pool (`ChatSessionManager.run_async`) too, because Agent reads verify, and may repair, a current-Session pointer. Every Agent payload is built there as well, also for `agent.rename` and the remaining Agents of `agent.delete`: its `context_window` resolves the Model's Connection, which reads credential state (`chat/usage.md`). A payload's `config` and `effective` come from one read of the Agent's persisted values (`get_raw`, then `AgentResolver.effective_config_for_identity`); `agent.list` and `agent.reorder` pass the values the roster read already holds (`AgentListResult.persisted`), so they read each `agent.json` once per call.

`agent.soul.get {id}` and `agent.soul.set {id, content, revision}` read and replace an Identity Agent's SOUL.md (`agent.md` -> Conventions & Rules) and answer `{content, revision, path, prompt_limit_bytes}`, where `prompt_limit_bytes` is `INLINE_FILE_MAX_BYTES`, above which a System Prompt carries only a size notice (`prompts/prompt-files.md`). A write based on an older revision fails `soul_conflict` with the current file as `data {content, revision}`; a successful one publishes `resource_changed(agents)` and logs `Agent SOUL.md updated` at INFO. Both run on the Session database's pool like the other Agent store work.

`agent.update` also accepts `subagent_allow`, a string list that patches only the delegation allow-list through the Agent store's locked sparse update (`agent/configuration.md` -> Tool permission and Tool settings). It is update-only and conflicts with a full `tools` replacement; change reporting still names the persisted `tools` field.

`session.set_fast_mode {agent_id, session_id, enabled}` accepts a Boolean and atomically changes only the Session's `fast_mode` metadata, then publishes a scoped Session invalidation. It never remembers an Agent default; `session.get` and lists expose the preference when true. Chat applies it at the next Model request (`chat/run-execution.md` -> Fast mode).

## Session computer selection

`session.create` accepts optional `execution: {computer_id, allowed_computer_ids}` and stores it with the creating transaction. `session.get` always exposes `session.execution`, defaulting to server-only for older Sessions. `session.set_execution {agent_id, session_id, execution}` returns `{execution}` and publishes the scoped Session invalidation. These explicit grants require an admitted operator request (`current_principal()`); internal Agent RPC calls cannot create or change them. Every id must be a known computer and the default must be included. Offline computers and disabled capabilities remain valid choices; dispatch checks the requested capability when a Tool runs.

The setter holds the Session write lock and Run admission guard through persistence and publication. Active or queued work returns `session_busy`, so changing a default cannot redirect a Run already admitted. When editing a linked Sub-Agent, the requested grants must be a subset of its Parent's stored grants at that edit. Each Session otherwise keeps its own policy: editing the Parent alone does not rewrite existing children; a later delegation `send` intersects their grants (`subagents/delegation.md`). Unknown fields in stored policy survive mutation; unknown input fields are rejected. Coverage: `tests/server/rpc/test_session_methods_execution.py`.

## Permission Rules

- `agent.create`/`agent.update` accept `permission_rules` (an object normalized by `normalize_permission_rules`, `null` removes it; a malformed set is `invalid_request` naming `params.permission_rules...`). Payload fields: `agent/configuration.md` -> Fields.
- `permissions.validate {permission_rules, agent_id?, new_agent?}` saves nothing and never fails for a bad rule set: `{valid, permission_rules (normalized or null), notes, errors [{part, index, rule, message}], preset, inherited_preset, presets, bases, inherited, effective, preview}`. `preset` is the `matching_preset` of the effective set (own over inherited; `effective` and `preview` are `null` when it restricts nothing), `presets` each core preset as the change it makes (a `null` part is removed; `full_access` sets the explicit full set), `bases` `editor_bases` for the candidate even while it has problems (per base part `value`/`source`, `inherit`, `choices`, `excluded`, and `write.narrowed_by_read`; `permissions/rule-language.md` -> Presets), `preview` a `describe_permission_rules` layer. Without `agent_id` the set stands alone (the shared default, placeholders kept); with an Identity Agent it inherits `defaults.agent.permission_rules` and expands placeholders for the folder its new Sessions work in; `new_agent: true` (no `agent_id`) inherits that default for an Agent being created and keeps the placeholders of its folders; with `agent@project` it is the Team member's vBot override over the default restricted by the repository's translated rules, previewed in the repository. Coverage: `tests/server/rpc/test_permission_methods.py`.
- `permissions.session {agent_id, session_id?, working_project_id?}` -> `{restricted, layers, stored_ceiling}`: full access (also rules that restrict nothing) answers `{restricted: false, layers: [], stored_ceiling: false}` without describing anything. Otherwise the layers are the Agent's own resolved rules (`source` `agent`, for the Session's Working Project or, without `session_id`, a new Session's) followed by every inherited ceiling layer (a Sub-Agent Session's `parent` ceiling, the `cron` ceiling a fire joined into the Session, a temporary Agent's `extension` ceiling); `stored_ceiling` says whether the Session stores an inherited ceiling (`parent` or `cron`). The Scratch Area stays `{scratch}`. The Session payload itself carries no summary.
- `permissions.clear_session_ceiling {agent_id, session_id}` -> `{cleared}` removes the Session's stored ceiling, so its later Runs work under the Agent's own rules; a Run in progress keeps its boundary, and a later Cron fire or delegation into the Session joins its ceiling again. It is the user's way out of limits a Session inherited (`automation/cron.md` -> Permission ceiling). The owner `AgentResolver.clear_session_ceiling` logs the change; the RPC publishes `resource_changed(sessions)` for that Session only when one was removed. A missing Session maps like other Session RPCs.

## Agent rename and lifecycle helpers

- `agent.rename` holds the reference lock plus both Run guards, refuses open Sub-Agent activity, delegates the whole rename to `Runtime.rename_agent` (`runtime/agent-rename.md`), and publishes agents invalidation before Sessions/Channels/Cron so accessors remap selection first; `agent_refs.py` keeps the reference-lock and reference-lookup helpers plus `_guard_agent_lifecycle` (the reference lock, then cancellation-safe admission on the Agent lifecycle mutation lock) that Agent create/update/rename/delete and `archive.restore` share; `agent.reorder` serializes against rename/delete via the same lock with stable conflict errors.

## Learning RPCs

Shared Project Memory changes carry `project_id` on their learning-change and conflict items. A successful undo also publishes a `memories` invalidation for each affected Project; a failed undo publishes a general Memory invalidation because it may have written several owners (`automation/learning-changes.md`).

- `learning_methods.py` serves the Memory and Skill changes of one Run of an Identity Agent (`automation/learning-changes.md`): `learning.changes {agent_id, run_id}` -> `{agent_id, run_id, summary {memory, skills, undone}, changes}` and `learning.undo {agent_id, run_id}` -> the same shape after the undo. Both resolve the Agent's Workspace under the Agent reference lock and work on the `learning-rpc` pool; undo is a serialized mutation, records its reverts as `rpc`/`human`, and publishes `resource_changed(kind="memories", scope {agent_id})` and, after invalidating the Agent's Skills, `skills` for the stores it changed (both when a failed undo may have written). A refusal over a later change is `learning_undo_conflict` with `data {store, revision, later {revision, at, actor, run_kind?}, scope, text}` (Memory) or `{store, revision, later, skill}` (Skill); a Run that is still running is `active_run` with `data {run_id}`; other learning errors are `domain_error`. `_chat_reads.py` adds each finished review row's `outcome` (the summary) to `reflection_runs` (`server/events-and-reconnect.md` -> Reflection recovery). Tests: `tests/server/rpc/test_learning_methods.py`.

## Notification policy and read state

- `session.notification_policy {agent_id, session_id, policy}` saves `all`, `errors` or `muted`, returns the fresh Session summary and publishes the Session invalidation. It does not mark results read.
- `session.mark_read {agent_id, session_id, run_id}` also accepts `run_ids` (1-200 exact ids) instead of the scalar. Acknowledgements affect only completed own Runs and return fresh revisioned counters; old results can be read independently.
- `session.notification_status {agent_id, session_id, run_id}` returns `{allowed}` for desktop delivery immediately before showing a toast, combining current source policy, eligibility and unread state. A deleted Schedule suppresses its pending toast.
