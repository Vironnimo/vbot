# Server: process lifecycle

How `server/main.py` starts, runs and stops the server process: uvicorn options, the `create_app` hooks, the start and stop lines and exit statuses, the control record, claim and shutdown route, the restart callback and the update RPCs. Rules for the whole server edge: `server.md`.

## uvicorn options

- `server/main.py` runs uvicorn with `proxy_headers=False` (forwarding headers: `access.md`). With direct TLS it replaces uvicorn's HTTP protocol with the TLS-sniffing one of `server/access/tls.py`.
- `server/main.py` disables per-message compression for all incoming WebSocket connections (`ws_per_message_deflate=False`), avoiding synchronous DEFLATE work on the Event Loop at the cost of larger wire payloads. Message contents, ordering and replay contracts are unchanged. This server setting does not configure outbound Provider connections or HTTP/SSE compression. Startup coverage: `tests/server/test_main.py`.

## Shutdown ordering

`server/main.py` sets the `shutdown_event` injected into `create_app` on control shutdown, scheduled restart or a signal. Ordinary and Extension Run SSE streams end and unsubscribe first; uvicorn then drains HTTP work for at most 5 seconds (`timeout_graceful_shutdown`) before lifespan teardown closes the Runtime and cancels Runs in its dependency order. The deadline bounds transport draining, not the Runtime's service cleanup. Coverage: `tests/server/test_main.py`, `test_sse.py`.

Once `Runtime.start()` succeeds, lifespan cleanup also runs after a later startup failure and closes only services whose initialization was reached. Cleanup failures are logged and mark the stop unclean while remaining cleanup steps and Runtime shutdown still run; they do not replace the original startup error. A failure inside `Runtime.start()` stays owned by Runtime startup recovery (`tests/server/test_app.py`).

## `create_app` hooks

- `create_app(on_ready=..., on_stopped=...)`: `on_ready(runtime)` runs once at the end of lifespan startup, before uvicorn accepts connections; `on_stopped(runtime_stopped_cleanly)` runs once at the end of lifespan shutdown, after the Runtime closed, even when teardown raised, and receives whether the Runtime shut down without a failed step (`False` too when an earlier teardown step raised before it). The lifespan reports a failed Runtime shutdown only that way and does not raise it: the Runtime already logged each failed step with its name and traceback (`runtime.md` -> Shutdown), and uvicorn would log the same traceback again as `Application shutdown failed`. Only `server/main.py` passes them. Its ready hook sets the GIL switch interval to 0.5 ms (below Windows' 1 ms wait, see `performance/diagnosis.md` -> Reading stalls and lag), then runs a full `gc.collect()` and then `gc.freeze()` (DEBUG `Startup heap frozen (objects=... collect_ms=...)`), then writes the start line. Later cyclic collections skip the frozen startup objects (modules, classes, Runtime services); otherwise every collection of the old generation traverses them while holding the GIL and stalls the Event Loop. Frozen objects that later become unreachable cyclic garbage are never collected, which bounds the cost to the startup heap. The hook then sets the collection thresholds to `(2000, 10, 100)`: CPython's young and middle defaults, and 100 instead of 10 middle collections before a full one. CPython 3.14.5 and later (the CI-built packages) collect generationally and start a full collection after the 10th middle one once a quarter of the old generation is new; in a 10-Agent `perf_load.py --duration 8` run on 3.14.7 the raised threshold cut full collections from 19 to 2, their total from 10 s to 1.5 s and the worst pause from 1.8 s to 0.8 s, while peak RSS rose from 650 to 850 MB, because cyclic garbage that reached the old generation waits longer. CPython 3.14.0-3.14.4 collect incrementally and ignore the third value. Test and embedded apps omit the hook, so a test process never freezes its heap (`tests/server/test_app.py`, `tests/server/test_main.py`).

## Start and stop lines

`server/main.py` owns the process's single INFO start line and single stop line (`logging.md`). The start line (`Server started (...)`, written after lifespan readiness and successful socket binding) carries the version and the Runtime's build identity (`Runtime.build`: short revision, `release=yes` or the branch), the installed version id when the code runs from `versions/<id>/app`, mode (`normal`/`verification`/`test`), `access` (the Access Mode, `access.md`), pid, listen address, data directory, startup duration since process creation and `Runtime.startup_summary` (Tools, Skills, usable Providers and Connections, loaded Extensions, keep-awake). The same start line splits startup into `pre_main` (process creation through interpreter initialization and imports), `setup` (entrypoint configuration and app construction), and `app` (uvicorn startup, lifespan, final heap preparation and socket binding); the latter two use a monotonic clock. These phases locate cold-start delays without adding per-step INFO records. The stop line (`Server stopped (reason=... uptime=...)`) is written after Runtime teardown and before uvicorn re-raises a captured signal: `control` with its initiator, `restart` (a restart the server scheduled itself), `signal` with its name (Ctrl+C is `SIGINT`, a closed console `SIGBREAK`), or `startup_failed` at WARN. After a failed Runtime shutdown the stop line adds `shutdown=failed` at WARN. Once its log and control record are closed, the process exits with `STARTUP_FAILED_EXIT_CODE` (3) when the application failed to start (current uvicorn raises its own status 3 itself; for older versions, whose `Server.run` returns, `main()` raises it) and with `SHUTDOWN_FAILED_EXIT_CODE` (70) after a stop whose Runtime shutdown failed; a failed bind retains uvicorn's startup-failure exit status, and a signal stop still ends by uvicorn re-raising the signal. Both constants live in `core/utils/server_control.py`: they are the statuses a supervisor must not answer with a restart, and the generated systemd unit lists them in `RestartPreventExitStatus` (`cli/application.md` -> Autostart and server supervision). The process owns a `LogManager` created after `uvicorn.Config` (which closes existing handlers while configuring logging); the Runtime's own manager nests inside it. Right after it, the process enables its crash log (`logging/pipeline.md` -> Crash logs) and, when it started inside another application's Windows Job (`core.utils.processes.foreign_job`, checked before its own containment Job exists; `tools/os-processes.md`), writes one WARN `Server started inside another application's Windows Job; ... (owner=<exe> owner_pid=<pid>)`: closing that application (a coding agent's app, say) ends the server without a stop line, so this line explains such a silent end. uvicorn's lifecycle lines and `Server application ready/stopping` are DEBUG (`tests/server/test_main.py`).

## Control route, record and claim

- `POST /_vbot/control/shutdown` is the private cooperative lifecycle edge letting the local CLI trigger normal lifespan teardown; it requires the current per-process secret from `<data_dir>/runtime/server-<port>.json` (an owner-only file) and is therefore exempt from the access guard's credential check. An optional `X-VBot-Stop-Initiator` header names the caller (`STOP_INITIATORS`: `cli`, `scheduled_restart`, `tray_stop`, `tray_restart`, `tray_quit`, `update`); a missing or other value reads `unknown`, and `request_shutdown(initiator)` receives it. The transport-neutral `core/utils/server_control.py` owns secret comparison, atomic persistence, PID plus process-creation-time identity for the post-listener shutdown window, and exact-owner cleanup.
- A stale control record is not authority: while the listener exists its PID must match, and after the listener closes both PID and process creation time must match the live process. Startup replaces the record atomically; cleanup requires PID and secret ownership. Never expose the token through health/RPC/logs/payloads.

Server startup holds `core.utils.server_control.server_control_claim` for the lifetime of its exact data-directory/port target. Because the claim writes into the data directory, `server/main.py` first creates a missing data root with `initialize_data_directory` (data-store bootstrap marker included); an existing root is left to Runtime startup, which refuses it without a marker (`tests/server/test_main.py`). A competing launch cannot publish or remove the existing process's shutdown authority, including when the existing process predates this lock. The claim yields the record of an earlier process that is no longer alive: its shutdown removes the record last, after its stop line, so that process ended without shutting down (killed from outside or crashed). `server/main.py` logs `Previous server process ended without shutting down (pid=...)` at WARN right after its `LogManager` opens, before the start line. Regression coverage lives in `tests/core/utils/test_server_control.py` and `tests/server/test_main.py`.

## Restart callback

- `server/main.py` also supplies an optional app-state restart callback. It reuses
  the detached CLI lifecycle helper for its exact bind/data directory, waits for
  its own PID to exit, and schedules cooperative shutdown after the RPC response.
  Local-speech setup admits restart only after verification; embedded apps without
  this callback report restart unavailable. See `model_tasks/speech.md` and
  `tests/server/test_main.py`.

## Update RPCs

- `application.update_continuation` is the private application-control RPC of an update: it requires the current server-control token and exact update operation id. The update stops the server without asking it about its work (`cli/application.md` -> Update operation). A handoff ticket is honored only when its Session durably holds the named Tool call with its result, checked by Sessions' single indexed `tool_result_persisted_async` probe off the Event Loop rather than a transcript load. `application.update_continuation` checks the ticket and creates its Bootstrap job, which selects the ticket's Session, under the Agent reference lock (`tests/server/rpc/test_application_methods.py`).
- `application.update_handoff_mint { handoff_token }` -> `{ handoff_ticket }` (absolute ticket path) is the one application RPC without the server-control token: the live shell-command token from `VBOT_UPDATE_HANDOFF` is its whole authorization and only accepted parameter, and ticket identity comes solely from the server-side record of the issuing Tool call. Unknown or released tokens fail with `invalid_request`; repeated claims return the same ticket. Lifecycle -> `cli/application.md` -> Agent handoff.
