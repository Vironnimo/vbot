# Server: chat RPCs

The server side of the chat RPCs: `server/rpc/chat_methods.py` owns submission, Run control and registration; `_chat_reads.py` owns History/timeline/Reflection/Sub-Agent reads, `_chat_input.py` owns target parsing, file mentions, current-Session marking and generic command outcomes, and `_chat_queue.py` owns public Queue operations and their scoped invalidation. These internal helpers keep `SessionAddress` after parsing; core APIs retain their own addressing contracts. This reference also covers chat reads that depend on a Working Project. Chat semantics stay in `chat.md` and its supplements.

## Chat submission target

`chat.send`/`chat.stream {agent_id, content, input_origin?, file_mentions?, widget_states?}` name exactly one of `session_id` (an existing Session) and `new_session` (an object asking for a new Session), else `invalid_request`. Unknown top-level parameters are refused before command dispatch, Session creation or Run admission. `new_session` accepts optional `session_id` (a caller-allocated canonical Session id, atomically claimed on creation; collisions refuse admission and never resume the existing Session), `agent_overrides`, validated like `session.create`'s but without `null` values (`validation.py::_optional_agent_overrides`), and `working_project_id`, validated like `session.create`'s: the new Session's Working Project, where its `@`-mentions resolve too. A plain message for a new Session starts through `ChatLoop.start_run_in_new_session` (`chat.md`), which checks the Agent, an override Model and the Provider before the Session exists, so a refused message leaves none (unusable override Model -> `invalid_request`, unknown Agent -> `agent_not_found`, an unknown requested Project -> `project_not_found`, an Agent without a usable Model -> `domain_error`); `@`-mentions pre-allocate its id (`new_session_id()`) because each file snapshot stamps the Session that read it. The created Session publishes a scoped `sessions` change and, for an Identity Agent, becomes the current one with an `agents` change. A slash command for a new Session runs through `CommandDispatcher.execute_for_new_session` (`chat/commands.md`); a Session it created and kept becomes current the same way. Every response names its Session in `session_id`: Run responses, `{queued, session_id, item}` and `command_handled` responses; only a command for a new Session that created none omits it. `session.create` stays for explicit creation (`tests/server/rpc/test_chat_methods_send.py`, `test_chat_methods_commands.py`). `widget_states` (1-8 `{widget_id, state}`, each state a JSON object of at most 8 KiB compact JSON) carries values the user changed in Agent widgets; a new-Session send refuses it, a command ignores it, and ids the Session's current view no longer shows are dropped (`tools/show_widget.md` -> Return path).

## Working Project of chat reads

`chat.commands`, `prompt.preview` and `files.list` take an optional `session_id` (that Session's Working Project counts) or, without one, a `working_project_id` validated as for `session.create` (the Project a new Session would work in); naming both is `invalid_request` (`validation.py::_draft_working_project`). For a Session whose Working Project no longer exists, `chat.commands` offers no Skills, while `files.list`, `prompt.preview` and every Run start fail with `domain_error` and the `WORKING_PROJECT_MISSING_MESSAGE` text (`projects/resolution.md` -> Working Project resolution). Tests: `tests/server/rpc/test_catalog_methods.py`, `test_operations_methods.py`, `test_session_methods.py`.

## History, edit and timeline

- The Chat RPC boundary must not match command names or mutate command-owned state (generic projection only). It re-aims an Identity Agent's `current_session_id` on plain sends/edits so restarts reopen the last-written session, and obtains each paged folded-History response plus whole-Session Usage from one Sessions read snapshot; `next_before` is the older-page continuation; `next_after` requests bounded appended History records. The whole read, including Compaction Policy, background-status records, reflection Runs and the Sub-Agent links below the Session (read only while another Session has an unfinished background command), is one Session-pool hop (plus one to resolve an Identity Agent's current Session when `session_id` is omitted; an Identity Agent without one gets an empty newest page with `session_id: null` and no Session read); projecting a changed page (file capabilities, background statuses, Context Usage) then runs on the shared `chat-rpc` pool (`_chat_reads.py`), which also expands `@`-mentions for `_chat_input.py`, and an unchanged page skips it. An `after` read that finds nothing appended returns the cursor fields and the background fields of the live commands only (below), and omits `session_usage`, `context_usage`, `compaction_policy` and `reflection_runs`; callers keep those values. Every other read carries `session_usage` and `context_usage` (null when none). `background_command_statuses` (command id -> `running`/`completed`/`failed`/`stopped`, `tools/shell.md`) is the complete map on a replacement read and, on an incremental read, the appended records' statuses plus those of the Session's live background commands: every background command of the Session the CommandManager knows carries its current status, and a recorded `running` it does not know is dropped, so a caller may end a `running` it holds that an incremental read leaves out. `background_commands_still_running` always lists every command of the Session whose shell exited while processes it started still run (`chat.stop_command` and `chat.command_output` stop one background command of the Session, or the processes it left running, or read its newest output, `tools/shell.md` -> Server and WebUI); `subagent_background_commands` lists the unfinished background commands of the Session's Sub-Agent Sessions at every depth down to a Sub-Agent the user took over, each under the Session's own Sub-Agent above it (`tools/shell.md` -> Server and WebUI); a `before` page omits all three and `compaction_policy`; `reflection_runs` accompany only reads with neither cursor (`tests/server/rpc/test_chat_methods_history.py`). Responses carry generation, per-record sequence/Run attribution, incremental/reset mode and `has_newer`; an edit or generation change requires snapshot replacement. A public Message id remains accepted for older-page input. `chat.edit` delegates idle-only edit admission to Chat and never falls back to Queue.
- Public History (`server/rpc/payloads.py::history_message`, shared by `chat.history` and Extension page History) shows a note with a `model_fallback` record as its switch notice: a `role: "model_fallback"` record with `id`, `timestamp`, `from_model`, `to_model` and, when known, `run_id` and `retry_at` (when new Runs try `from_model` again), never the note text. A note with a `goal_event` record appears the same way as a `role: "goal_event"` record with `id`, `timestamp`, its fields and, when known, `run_id`; a note with `subagent_messages` as a `role: "subagent_message"` record with `id`, `timestamp`, `messages` and, when known, `run_id`; a note with `widget_states` as a `role: "widget_state"` record with `id`, `timestamp`, `widgets` (`{widget_id, title, state}`) and, when known, `run_id`. These notices therefore survive the Run and reloads. A requested `limit` is a target rather than a hard cut: when a page's oldest record belongs to a Run, `chat.history` extends the page back to that Run's start (`core/sessions/_store_timeline.py`, `complete_run_segment`); records without a Run keep fixed-size paging. `chat.timeline` also widens the newer edge to whole Runs (`chat/timeline.md`).

`chat.timeline` exposes authoritative semantic conversation items and existing History/Session facts. `/api/runs/{id}/timeline` sends a fresh snapshot and bounded-rate patches through `server/timeline.py`; raw History and Run-event APIs remain available. See `chat/timeline.md` for identity, paging, recovery and sanitization contracts.

Its `last_usage` preserves the newest public Assistant Usage before child windowing drops raw Assistant records. Replacement reads without Usage return null; incremental reads without new Assistant Usage omit the field so accessors keep the preceding turn's value.

`output_speed` and `output_latency` are independent whole-current-view Session facts from the same read snapshot, not from the delivered page (`sessions/history-api.md`). Changed reads without `before` carry both, null when absent; unchanged and older-page reads omit them. Each measurement includes the answering Model and Assistant message id. A captured active Run overlays any newer measurement before child windowing; semantic Run snapshots/patches and settled reconnects preserve the same identities (`chat/timeline.md`).

## Queue and work

`chat.queue_update` accepts an optional `reply_surface` when an accessor edits queued input. Omission preserves the original surface; an explicit terminal/WebUI surface replaces it with the edited input. Listing or selecting a Steer does not change the captured surface.

Public Queue mutations publish `resource_changed(kind="queue")` with the full Session scope (`project_id`, bare `agent_id`, `session_id`); the TUI refreshes the addressed conversation when another accessor changes it.

`chat.work {agent_id, session_id}` serves the Sub-Agent coordinator's live work snapshot of the Session's subtree (`subagents.md` -> Interfaces, `work_snapshot`), independently of paged History. Accessors refresh it from existing Run, command, Queue and Terminal events and reconnects.
