# Delegation Bindings

Read when changing which Identity Agents a delegation grant reaches across archive, restore and rename: explicit target bindings (`delegation_bindings`), grant removal on archive and re-adding on restore, the retirement journal `agents/retirements.json`, and `delegation_target_allowed`. The allow-list setting itself (`tools.subagent.allowed_agents`) is in `configuration.md`, the rename's allow-list cleanup in `lifecycle.md` -> Rename, Sub-Agent admission in `../subagents.md`.

## Explicit target bindings

- `delegation_bindings` is private Agent-owned metadata for explicit bare Identity targets, never an editable Tool setting. A stored creation timestamp binds an existing target; an opaque journal-scoped integer cursor waits for the first target identity after that point in `agents/retirements.json`. User decision 2026-10-25 revokes explicit bare Identity grants without a binding: old failed cleanup and an intentional future grant cannot be distinguished retrospectively. Side-effect-free reads omit those targets immediately; normal config loads persist their removal once, and writes and archive restores apply the same rule. An explicit re-add establishes a new binding, so later reads preserve it; unavailable or invalid configs remain untouched and cannot supply a grant. Wildcards, implicit self-delegation and Project-qualified targets retain their existing scope rules.
- Explicit target bindings survive failed holder cleanup. Before archive or rename detaches a readable Identity Agent, the store appends its persisted creation timestamp to that id's retirement occurrences under the same lifecycle lock. `agents/retirements.json` is an Agent-owned Generation 1 document, included in snapshots and configuration backups and retained after archive purge. Each journal has a random identity encoded in its cursors, so missing history recreated later cannot reactivate older grants. A future cursor binds permanently to the first occurrence after it; repeated restore/archive of the same identity adds another occurrence. Recovery only appends while the source still exists; an interrupted or failed operation may leave a harmless occurrence naming the still-current identity. A history write failure prevents detachment. Rename records a revocation occurrence for its destination before publishing the move, so an older Run cannot reuse a removed future grant for the renamed Agent. Creation and restore still honor future grants. Rename moves bindings with their target; archive grant records preserve the original target proof, and restore only re-adds it for that same identity. A stale entry left by failed cleanup cannot become a new grant when a replacement Agent is archived and restored. New creation timestamps avoid collisions with current and retired persisted identities; an explicit grant to a legacy target without a usable stamp establishes one durably before saving the grant. `delegation_target_allowed` compares a captured binding with the current persisted identity and fails closed on missing, malformed, newer-format or inconsistent history. Sub-Agent admission carries that binding separately from Tool settings and checks it through admission under Runtime's existing reference mutex (`subagents/delegation.md` -> Targets); older Run snapshots cannot authorize a replacement. Coverage: `tests/core/agents/test_delegation_bindings.py`.

## Grants on archive and restore

Delegation allow-lists never block deletion: once the archive is committed, `remove_delegation_grants` records each grant (holder id, immutable `agent_created_at`, position, and original `target_created_at` proof for new bound grants) in the entry before it writes, then removes the bare id from every other valid Agent's `tools.subagent.allowed_agents` (qualified `agent@project` entries and invalid configs stay), so a later Agent with the same id does not inherit the grant; a list left empty means self-only, so no grant widens. A restore re-adds the restored id at the recorded positions only when the holder's creation timestamp still matches and the grant proves its original target identity, including when that same holder was archived and restored or was renamed (a unique persisted creation-identity match); a replacement reusing its id gets no grant. Older grant records without a valid holder or target creation stamp are skipped rather than bound to the current namesake. `delegation_grant_problem` is the read-only, never-raising holder probe, shared with restoration: `holder_missing` (checked before stamps), `holder_unproven` (missing/malformed creation stamps or an unreadable/invalid config), `holder_replaced` (valid creation stamps differ), or `None` (same incarnation). It uses the stored creation stamp, never a synthesized missing-field default; the archive service owns warnings (`archive/operations.md` -> Restore checks and outcomes), retaining `grant_target_missing` for a missing holder. After the irreversible archive this is best effort: a config it cannot read or write keeps its entry and logs WARNING, and that entry names no Agent and does not block a rename (`lifecycle.md` -> Rename). `agent.delete` reads `remaining_agents` after the archive, so they show the cleaned lists, and the archive's INFO line counts the changed `policies` (`test_agents_archive.py`, `tests/core/archive/test_archive_service.py`, `tests/server/rpc/test_agent_methods_lifecycle.py`).
