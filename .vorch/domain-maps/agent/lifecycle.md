# Agent Lifecycle

Read when changing how `AgentStore` renames, archives or restores an Identity Agent: the store operations, tree moves, the references a rename moves or refuses, the rename record and its recovery, and `ensure_bootstrap`. The guards every change must keep are in `../agent.md` -> Constraints & Gotchas, the cross-domain rename order in `../runtime/agent-rename.md`, the archive workflow in `../archive.md`, and delegation grants in `delegation.md`.

## Store operations

- `ensure_bootstrap()` creates a bootstrap Agent only when zero valid Agents exist; invalid directories stay for diagnosis and an occupied `main` shifts to the first free `main-N`.
- `rename` applies the Agent-owned half of a rename and returns with its record still pending: live Sessions and the Sub-Agent parent links to them, then the whole tree (`os.replace`; case-only Windows renames go through the temporary sibling named in the record), the config with an in-tree Workspace rebased (external paths preserved), the roster position, and exact bare-id references in every `allowed_agents` list (never qualified addresses); before the record it removes allow-list entries that already name the unused new id (Constraints). Its caller, Runtime (`runtime.md`), moves the other domains' references and then calls `finish_rename`, or `revert_rename` and `finish_rename` with the reversed record on failure; `recover_rename` is the startup half. Archive and restore are context managers around the archive service's Session commit (`archive.md`): `archive_files(agent_id, tree)` moves `agents/<id>/` into the payload `tree` and yields `ArchivedAgent` (the config with defaults, roster index, stored Workspace and whether it lies outside the Agent's directory); `restore_files(source, target_id, workspace=, root_project_id=)` moves the payload to `agents/<target_id>/`, then rewrites its `agent.json` to the target id, Workspace and default Project (`root_project_id`; unknown fields stay) and seeds missing Workspace files; a failing body moves either tree back, and a failed restore first writes the archived `agent.json` bytes back, so the payload stays unchanged. `inspect_archived` reads a payload without changing it (`payload_missing`, `payload_invalid`, `older_format`, `newer_format`), `restore_target_problem` names `invalid_target_id` or `agent_id_taken` (also an id an unfinished rename holds), and `remove_delegation_grants`, `restore_delegation_grants` and `place_in_roster` are the best-effort cross-Agent steps around them.
- Archive startup recovery uses `complete_restore_files` to repeat `restore_files`' configuration rewrite on a tree already at its destination. It loads the raw document and preserves its current-Session pointer while those Sessions are still archived; the archive service persists and supplies the planned Workspace and default Project (`archive/recovery.md` -> Interrupted restores).
- `update_with_metadata` owns transactional Workspace relocation with copied/backed-up metadata; `agents_rooted_in`/`restore_update` support Project removal compensation.

## Tree moves

A custom Workspace outside the Agent's directory stays where it is: the entry records it, a restore re-attaches it, and nothing deletes it. A rename between volumes copies first (a link inside the tree, Windows junctions included, is recreated as a link to the same target, as a rename would keep it), sets the original aside by renaming it and only then deletes it; a failed deletion leaves a hidden `.<name>.moved-*` leftover next to the source and a log warning, not a failed move. Every archive gets its own payload; none replaces another. A failed archival or restore reaches the caller as `AgentError`; if compensation also fails, the message names where the Agent's files remain. Seeding never overwrites existing workspace files (`test_agents_archive.py`, `test_tree_move.py`).

## Rename

- Rename moves live references (Channels, non-terminal identity Cron and Bootstrap jobs, delegation entries, functional parent links, the lifecycle and attachment scopes of live Terminal Sessions, `tools/terminal.md`, and the scopes of shell commands, `CommandManager.transfer_agent_scope` in `tools/shell.md`), and keeps terminal history/logs historical, including a Terminal Session's immutable provenance.
- The refused references (a Channel or a non-terminal identity Cron or Bootstrap job naming the new id, also an event Cron job that cannot fire now, since an event change can revive it and a revert would move it; `identity_agent_references` in `core/runtime/_agent_rename.py`) are checked before anything changes. Such references are usually leftovers of a deleted Agent: the renamed Agent would silently adopt them, and a revert, which moves everything naming the new id back, would take them along. They block rather than only warn because the user can change or remove each one. A delegation allow-list entry naming the new id does not block: once the existence checks pass, the id names no Agent, so the entry grants nothing - a leftover from before deletion cleaned allow-lists or of a failed cleanup, or a grant saved before any Agent had the id (saves do not check allow-list targets). After the refusal checks and before the rename record, outside every rename direction, `AgentStore.rename` removes such entries, so the renamed Agent does not inherit them, a revert cannot move them to the old id, and an interruption leaves only fewer of them; `policy_agent_ids` (RPC `agent_policies_updated`) include those Agents. No startup sweep removes allow-list entries that name no Agent, because such an entry may be a deliberate grant for an Agent still to be created; `create` honors it for the first actual target identity. An aborted creation consumes no future grant. Derived references instead follow what they point at, so a revert leaves pre-existing ones alone: a Sub-Agent parent link moves only when its parent Session moved (`sessions/ownership.md` -> Identity-rename retargeting) (`test_agents_rename.py`, `tests/core/runtime/test_runtime_agent_rename.py`). Fork provenance (`fork_source`) is derived from the parent Session's current row, so it follows the retargeted Sessions to the new id (`sessions/lists-and-metadata.md` -> Metadata facade). Runtime logs one INFO summary per rename with counts per kind (Sessions, Channels, Cron and Bootstrap jobs, policies, session links, Terminal Sessions) and one INFO line when a start completes or rolls back a pending rename; the per-reference retarget steps log at DEBUG, an incomplete rollback or recovery at ERROR (`logging.md`).

## Rename crash safety

`agents/rename-pending.json` (Generation 1 document: `source_id`, `target_id`, `staging_name`, `rollback`) is written atomically before the first change and removed only after every reference moved. Every step selects only what still names `source_id` or converges on its target state, so repeating a direction finishes it and swapping the ids (`rollback: true`) reverts it. A failure reverts the whole rename in-process; a process that dies leaves the record, and the next start applies it again before the first roster read and `ensure_bootstrap` (`AgentStore.recover_rename`), then Runtime moves the references before Channels and Cron start (`runtime.md`). A direction that cannot complete flips to rollback; a record that fails both ways, or cannot be read, stays and logs ERROR on each start. While a record exists, `rename` refuses (`An earlier Agent rename is still pending; restart vBot to finish it`) and `create`/`ensure_bootstrap` never claim either id, so recovery cannot merge a new Agent's Sessions (`test_agents_rename.py`, `tests/core/runtime/test_runtime_agent_rename.py`).
