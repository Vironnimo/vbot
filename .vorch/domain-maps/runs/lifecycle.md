# Run Lifecycle

Run cancellation, per-Tool cancellation, terminal settlement, terminal payloads and the terminal log line in `core/runs/`. The ownership rule - the manager alone settles terminal state - is in `runs.md` -> Constraints & Gotchas.

## Cancellation

- `Run.request_cancel(reason=None, *, initiator=None)` marks cancellation requested, stores the optional `reason` on `Run.cancel_reason` for inclusion in the `run_cancelled` terminal payload and the optional `initiator` on `Run.cancel_initiator` for the terminal log line only (`cancelled_by=`), first cascades every still-active per-Tool callback in registration order, and then schedules registered sync/async Run callbacks. Completed Tool Calls have already cleared their entries and do not receive a late callback; a callback registered after the Run cancel signal fires immediately and observes the call as cancelled.
- The manager drains scheduled asynchronous cancellation callbacks before publishing terminal cancellation, releasing the Session, or starting its next queued Run, with one shared five-second budget including nested registrations. On expiry it logs a warning, cancels pending Futures, and proceeds without waiting for cancellation-resistant callbacks; async callbacks registered afterward are immediately cancelled. Normal cleanup prevents overlap with the successor; after expiry resource termination remains best effort.
- Once the manager task has entered its execution wrapper it is cancelled forcefully; a request made before that first step leaves the wrapper scheduled long enough to perform terminal cancellation bookkeeping without entering the caller's executor, so the Session is always released. Cancelling immediately after `start(...)` returns must still move the Run to `cancelled`, resolve `Run.wait()`, remove the active-session entry, and drain queued work. Do not cancel a newly created manager task before its execution wrapper has entered the lifecycle `try/finally`; Python otherwise skips that coroutine body entirely and strands the Session in `running`.
- `Run.add_cancel_callback(callback)` registers cleanup for active provider/tool/host work; callbacks registered after cancellation is already requested are scheduled immediately.
- A synchronous cancellation callback raising `asyncio.CancelledError` is isolated and logged like an ordinary callback failure. Later callbacks and executor cancellation still run, so terminal publication releases the Session and advances its Queue (`test_runs_cancellation.py`).
- Cancellation cleanup retires each settled Future snapshot directly; it must not depend on scheduled completion callbacks getting a turn, because awaiting already-completed Futures may not yield. Cleanup registered by earlier callbacks shares the original drain deadline. Regression coverage: `tests/core/runs/test_runs_cancellation.py`.
- `await ChatRunManager.aclose()` closes Run admission atomically, cancels queued items and reservations, requests shutdown cancellation for every active Run, and waits for their executor and cancellation-cleanup tasks. A closed manager rejects later start, enqueue, and reservation calls and never drains another queued item.
- Cancel initiators (`initiator`, log only): `rpc` (`chat.cancel`), `webui_command` or `channel_command:<channel_id>` (`/stop`), `shutdown` (Runtime close, including the server stop of an update), `extension:<name>` (temporary Run groups), `parent_run:<run_id>` (a `background_tasks` stop of a Sub-Agent), and `user_stop_all` (Stop all: `/stop all`, `chat.stop_all`). Normal Stop surfaces pass `reason="user"`; Chat records that as the internal interruption cause while using the same checkpoint recovery path as other interrupted Runs.

## Per-Tool cancellation

- `Run.begin_tool_call(tool_call_id)` marks a dispatched call active before `tool_call_started` is emitted, so an accessor can cancel it immediately even when Tool-owned cleanup has not registered yet. `Run.register_tool_cancel(tool_call_id, callback)` attaches that cleanup without touching the Run's overall cancellation state; registration after either an early per-call cancel or `request_cancel` schedules the callback immediately, so neither race can orphan cleanup.
- `Run.cancel_tool_call(tool_call_id) -> bool` marks an active call user-cancelled and invokes its callback when already registered; an early cancel remains pending until registration. It returns `False` for unknown, completed, or already-cancelled ids. It does NOT set `cancel_requested` and does NOT cancel the executor task: per-call cancellation remains local, while `request_cancel` deliberately subsumes all still-active per-call cancellations.
- `Run.tool_call_cancelled(tool_call_id)` reports whether a specific call was user-cancelled via `cancel_tool_call`; `Run.clear_tool_cancel(tool_call_id)` removes its registry entry.
- `chat.cancel_tool_call` validates the complete Agent/Project address when its optional `agent_id` is supplied, refusing a different owner before cancellation; id-only calls remain supported. Exact Agent/Project/Session/Run validation is at `chat.control_run` (`tests/server/rpc/test_chat_methods_runs.py`, `tests/core/runs/test_runs_tool_cancellation.py`).

## Terminal settlement

- Every executor exit settles terminal state before releasing the Session: an escaping non-`Exception` `BaseException` propagates from the executor Task while a final guard settles the Run as cancelled, including when exception-handler cleanup itself escapes. `Run.wait()` therefore keeps its ordinary terminal cancellation contract for completion watchers; `KeyboardInterrupt`/`SystemExit` retain cancelled-and-propagate semantics. Coverage: `tests/core/runs/test_runs_cancellation.py`.
- Retained terminal errors preserve their type, attributes, notes and cause/context chains without tracebacks; each `wait()` or failed `wait_admitted()` raises a fresh copy so completed-Run retention keeps neither executor nor waiter frames. Native extension exceptions use their copy/reduction protocol when built-in allocation cannot reconstruct them. An exception that cannot be copied becomes a stable `RuntimeError` naming its original type and message; snapshot failures never prevent terminal settlement. The original error remains available to terminal logging.
- A terminal commit failure yields a failed live Run with `history_persisted=false`; restart can settle the abandoned database row. Notification failures are logged and included as `completion_notification_errors` without rewriting a committed outcome.
- Completion observer cancellation is recorded as a notification diagnostic; process-level observer aborts propagate only after terminal publication and Queue release. Neither changes the committed execution outcome.
- **Terminal release.** Publishing the terminal event settles the Run: it drops every cancel callback, completion finalizer and observer, Tool background callback and active per-Tool cancel entry, so the adapters, clients and Tool resources those closures capture become collectable while the Run stays addressable. The manager has already drained cancellation cleanup and notified completion observers by then. Per-call cancelled markers remain, so `tool_call_cancelled` keeps answering; `cancel_tool_call` on a finished Run returns `False`. Registrations on a finished Run (`add_cancel_callback` without a pending cancel, `add_completion_observer`, `begin_tool_call`, `register_tool_cancel`, `register_tool_background`) are ignored. Coverage: `test_finished_run_releases_execution_callbacks` (`tests/core/runs/test_runs_terminal.py`).
- Chat's run-end cleanup (statistics, Stream draft, Adapter close) settles before a cancellation reaches the manager (`settle_before_cancelling` in `core/chat/_run_execution.py`). A Tool's background callback is retired as soon as its call is cancelled or completes, not only at Run end (`core/runs/run.py`).

## Terminal payloads

`run_started` carries `{"status": "running"}` with an optional `queue_item_id` when the Run was started from a queued item. Terminal payloads include `timing` with `{ started_at, completed_at, duration_ms }` and the Run-owned `iteration_count`; duration uses a monotonic clock and timestamps are UTC ISO strings for display/persistence. `run_completed` may also include `usage`, kept separate from `timing`. `run_cancelled` also includes the optional `reason` field when one was supplied to `Run.request_cancel(...)`. `run_interrupted` is terminal, carries `{status: "interrupted", cause, timing, iteration_count, ...terminal_payload_extras}` with the normalized `cause`, and never masquerades as `run_completed`. Executors may fill the `Run.terminal_payload_extras` dict before returning/raising; the manager merges it into the terminal payload of every outcome alongside `timing`, while the manager itself supplies `iteration_count`. The chat loop supplies `session_usage` on every outcome.

## Terminal log line

The manager's one `mark_*` call per Run writes the Run's one terminal log line (`vbot.runs`), whatever the executor (interactive, cron, channel, sub-agent, manual Compaction): completed and cancelled at INFO, interrupted and an expected `VBotError` failure at WARNING with the error summary, any other failure and a failed terminal commit (`history_persisted=false`) at ERROR with traceback. It carries run, agent, session, project, Run kind, internal flag, model, duration, Iterations, Tool calls, token totals, retries, stream recoveries, and the cancel reason and initiator or the interruption cause. Executors fill the Run's `model`, `internal`, `retry_count` and `stream_recovery_count` and never log the outcome themselves (e.g. `core/chat`'s `_persist_run_error`, sub-agent result folding). Coverage: `test_every_run_outcome_logs_one_terminal_line_at_its_level` (`tests/core/runs/test_runs_terminal.py`). A Run a previous process left running never reaches the manager: Session restart recovery settles it and writes its terminal line instead (`sessions.md`).
