# Run Queue and Admission

The live Queue of `ChatRunManager` (`core/runs/runs.py`): queued items, `RunAdmission`, steering selection, waiting-work capacity and Extension execution ownership. Steer is a shared term (`.vorch/GLOSSARY.md`); Waiting-Work Admission, Run Admission Guard and the shared-manager invariants are in `runs.md`.

## Admission

- `ChatRunManager.start(address, executor, *, admission=DEFAULT_RUN_ADMISSION)` starts immediately or raises `ActiveRunError` when that Session already has a running Run. The positional `address` is the required `SessionAddress`; the created `Run` reads its project anchor, agent, and session from it. `enqueue(address, executor, *, display_content="", editable=False, internal=False, waiting_work_admission=None, admission=DEFAULT_RUN_ADMISSION)` accepts the same shape plus queue-display inputs, starts immediately when idle and resolves the item future at once, or stores them on the FIFO `QueuedRunItem` so a later drained Run keeps the decisions.
- `admission` (`core.runs.RunAdmission`: `working_project_id`, `run_kind`, `contributes_to_agent_activity`, `work_id`, `owner`, `input_id`, accessor-only `source_session_id` for review Runs, optional `expected_session_generation_id`, optional `completion_activity`) carries the immutable origin/activity/work-correlation decisions and Session-generation expectation as one bundle. Sessions checks the expectation in its admission transaction before executor entry; omitting it retains deliberate create-missing admission. `work_id` is internal orchestration state that is stored on the native Run at admission and completion. `completion_activity(status, result)` replaces the Run's `contributes_to_agent_activity` once it finished, before `finalize_completion`, the Session completion and the terminal event, so all three agree; a raising decision keeps the admitted flag (`_decide_completion_activity`, `test_runs_lifecycle.py`). Cron admits its Runs as non-activity and decides per outcome (`automation/cron.md` -> Delivery).
- Both methods check Run Admission Guards under the manager's same `_lock` before admitting work and raise `RunAdmissionBlockedError` on a guarded Session, Agent, Project anchor, or internal working Project. `RunAdmissionBlockedError` subclasses `ActiveRunError`, so existing start-then-queue ingress reaches `enqueue()` and receives the same expected conflict while a lifecycle guard is held.

## Queue items

- `QueuedRunItem` - pending request with display preview, executor, `internal` flag, public `editable` capability, created timestamp, single-owner `future`, one immutable `admission` bundle, and a transient waiting-scope tag. The queue key still owns only Session identity; public queue payloads include the run kind and `editable` but omit the other admission decisions. Chat preserves complete textual display content and marks raw strings editable; structured content and attachments remain non-editable. Public `steerable` and `steering` describe eligible input and pending delivery. Pending steering disables editing; in-flight persistence also rejects removal. `chat.queue_update`/`chat.queue_remove` report these rejections as `queue_item_steering`, distinct from `queue_item_not_found`; the WebUI explains it and re-syncs the Queue.
- `ChatRunManager.list_queued(...)`, `remove_queued(...)`, and `update_queued(...)` are raw Queue controls; they include internal items, and public RPC filtering belongs in `server/rpc/chat_methods.py`. `all_queued()` returns a fresh cross-Session Queue snapshot in per-Session FIFO order (the `/ws` handshake's `queues`, `server/events-and-reconnect.md`).
- `enqueue(...)` may resolve the item future at once to a running Run. Cancelling a bare future abandons transient work. Accepted Accessor input belongs to the server; losing its waiter never withdraws it.
- Removing a queued item or rejecting it at the waiting-work capacity limit cancels its future. The manager rechecks editability at mutation time, so a stale public Queue update cannot overwrite an item another update made non-editable; updating replaces both executor and display preview and recalculates editability from the replacement content, so build replacements through `ChatLoop.build_queue_update(...)` when user-visible Chat content changes. Chat rebuilds that executor from the queued request itself and replaces only the edited content/input origin; transports must not synthesize a fresh executor because that would discard immutable Sender, reply-surface, Tool-policy, hook, or override inputs.
- Session release and Queue drain share the admission lock, and a non-empty Queue remains an admission barrier after the current Run becomes terminal, so new work cannot overtake existing Queue items. Queue drain resolves an item whose admission or start fails with that exception and continues with the next item: `RunAdmissionBlockedError` is expected, any other exception is logged as an error; one broken item never strands the rest of the Queue (`tests/core/runs/test_runs_queue.py`).

## Steering

- Runs owns the selection, its pending state, drain order and removal; Chat owns which items are eligible and the Message built from them (last bullet).
- Steering targets whatever active Run the Session has, whoever started it (user, system delivery, Cron, Calendar, Channel, Sub-Agent), at its next safe Model-request boundary. A steered item stays in the Queue, marked `steering`, until its User message is persisted.
- A Run takes selected input unless it is Extension-owned or has another working Project. Selected input no Run took before the active one ends starts the next Run ahead of unselected items, in Queue order; the rest of the selection reaches that Run at its first Model request. Delivery resolves the item's future to the Run that took it.
- `steer_queued(...)` marks eligible input for the Session's next Model request without naming a Run; `pending_steering(run)` returns the selection that Run can take and `deliver_steering` persists it at safe boundaries without holding the global manager lock across persistence.
- `remove_queued` refuses an item whose steering append is in flight; `clear_queued(...)` empties a Session's Queue for good: such an item is marked withdrawn and leaves the Queue when its append ends, so an append cut off by cancellation cannot start the item as a new Run.
- Chat's side (eligibility, Message construction, the steering reminder): `chat/run-execution.md` -> User steering.

## Waiting work

At most `DEFAULT_WAITING_WORK_LIMIT` (32) tasks may wait system-wide, across queued Runs and ingress reservations; active Runs do not count. `enqueue` rejects a new normal queued Run at that ceiling. Channel ingress calls `reserve_waiting_work(scope, scope_limit)` before accepting raw work or downloading media; the reservation counts against the same ceiling and its per-scope limit. It is released when non-Run work begins, or transferred atomically through `enqueue(..., waiting_work_admission=...)`, so no second queue can over-admit. An item being durably accepted holds its waiting slot across the persistence await, including its reservation scope; failed or cancelled acceptance releases the slot. `release_waiting_work(...)` cleans up a reservation when processing fails or shuts down; `waiting_work_count()` is the central diagnostic count. Internal waiting-work reservation ids keep their private format (`runs.py`).

## Extension execution ownership

`RunAdmission.owner` is immutable execution provenance retained by Runs and Queue items. Admission validation runs again under the manager lock, including Queue drain; a closed owner epoch cannot admit late descendant work. Ownership is separate from Session Tool grants: child Runs can retain cancellation/usage ownership without receiving the parent's Session Tools. `core/agents/temporary_execution.py` closes group admission before cancelling exact owned Runs, Queue items and injected resource owners. Resources close only after those Runs are terminal, so they may release their per-group admission state after their own drain. The completion coordinator keeps no such state; it validates each owned submission against current group admission (`automation.md`). Unrelated work in a reused target Session remains outside that group (`tests/core/agents/test_temporary.py`, `tests/core/subagents/test_subagents.py`).

## Durable ordinary Accessor input

Sessions owns accepted input identities and state (`sessions/owned-execution.md` -> Ordinary Accessor inputs). Chat owns their serializable execution context (`core/chat/_accessor_inputs.py`); the Run manager remains the only Queue and admission owner. `enqueue(..., persist_input=...)` checks capacity/guards and commits acceptance before installing its live projection. Cancellation after admission settles persistence plus projection; losing the RPC response permits the same input id to be retried.

Chat's async Queue mutations serialize the receipt write and RAM change through `queued_input_mutation`; acquiring that boundary remains cancellable. Use `clear_queued_async` when withdrawing work that can contain accepted inputs. Shutdown only discards live projections. Receipt claims commit with native Run admission, and selected input claims commit with their User-message append, so neither restart boundary can execute one input twice. Already-started Runs retain normal interruption recovery.

Startup decodes all recovered inputs before installing any, preserves stable Queue ids and acceptance times, and uses the same steering-first ordering as drain. Synchronous bootstrap installs these projections before producers get an Event Loop turn; the async Chat restore entry point covers explicit standalone use. Accepted inputs retain their capacity even if a later waiting limit shrinks.
