# Providers

Provider configuration, credential resolution, adapter creation, retry/error classification, and provider-specific request/response translation.

## Overview

`core/providers/` translates canonical vBot chat requests into external provider wire protocols. Provider configs live in `resources/providers/*.json`; normalized model catalogs live in `resources/models/*.json`; runtime creates adapters with one explicit connection, an async token getter, provider defaults, optional debug capture, and provider-scoped model lookup. Concrete wire behavior belongs in the provider child maps under `.vorch/domain-maps/providers/`; keep the root map focused on shared contracts and extension rules. A single provider can serve multiple connection variants (different auth, base URL, or wire protocol) through one adapter class that branches on the connection's declared `mode`; OpenAI is the canonical example with `api-key` and `subscription` connections on one `OpenAIAdapter`.

## Terms

Domain-specific vocabulary for providers and the wire. Core terms (Provider, Model, Reasoning) live in `.vorch/GLOSSARY.md`; the Model-DB terms (Canonical id, Refresh, Load, Reasoning control) live in `models.md`.

### Adapter
**Definition:** A code class that speaks a specific wire protocol. The adapter hierarchy:

- `ProviderAdapter` (ABC) — defines the interface: `send()`, `stream()`
- `OpenAICompatibleAdapter` — concrete class for the generic OpenAI `chat/completions` protocol. Used directly by fully compatible providers; mostly compatible providers should subclass it when runtime behavior or catalog discovery differs.
- `OpenCodeGoAdapter`, `OpenRouterAdapter`, and `GitHubCopilotAdapter` — OpenAI-compatible subclasses that own provider-specific runtime or model-catalog knowledge.
- `AnthropicAdapter` — concrete class for Anthropic's Messages API. Own wire protocol, own message format, own thinking/reasoning parameters.
- Custom adapters can inherit from `OpenAICompatibleAdapter` and override specific methods when a provider is mostly but not fully OpenAI-compatible.

**Not:** A model, a provider config, or a data format. The adapter is purely the wire protocol translation layer.

### Connection
**Definition:** One authentication/wire variant of a Provider, declared statically in `resources/providers/<name>.json`: auth type (`api_key`/`oauth`), optional per-connection base URL, wire `mode`, and models endpoint. Addressed as `<provider>:<connection>` (e.g. `openai:api-key`, `openai:subscription`); model catalogs and discovery are connection-scoped.
**Not:** An Account. The Connection defines *how* vBot talks to the provider; the Account decides *which credential* is used on it. Also not a network/HTTP connection.

### Account
**Definition:** A named credential slot on a Connection — one of possibly several API keys or OAuth logins for the same Connection, addressed as `<provider>:<connection>[:<account>]` with default slot `default`. When no account is pinned, the first usable one is chosen deterministically (`default` first, then sorted); API-key accounts map to derived env keys (`BASE__<ACCOUNT>`), OAuth accounts to per-account token files.
**Not:** A Connection, and not a user account in the product sense. Accounts are interchangeable credentials — they never change the wire protocol or the model catalog.

### Usable (connection)
**Definition:** A connection is *usable* when it is **enabled AND credentialed** — the single gate behavior consumers ask via `ProviderCredentialResolver.is_usable(provider_id, connection_id=None)`. *Enabled* is the user switch: the settings override `providers.connections["<provider>:<connection>"]` when present, else the type default from `connection_default_enabled` (keyed `api_key`/`oauth` → enabled, keyless `none` → **disabled**). Enablement is connection-level (an account suffix is ignored); overrides are read live from settings on every check, no reload hook.
**Not:** `has_credentials` — that stays the pure credential question (used by credential-management surfaces like the settings panel's `configured` flag and `set_key`/`unset_key`). A keyless connection is always credentialed but not usable until the user enables it.

### Reasoning intent
**Definition:** The provider-neutral description of what a single request should ask of the model's reasoning, produced once by `resolve_reasoning_intent(...)` (in `core/providers/reasoning.py`) from `(model control, agent effort)`. One of five kinds: `default` (no effort selected — leave the provider default untouched), `off` (do not reason), `effort` (reason at a snapped effort level), `budget` (reason within a token budget), or `on` (reason, binary toggle). Each adapter has a small *render* step that translates the intent into its own wire fields — adding a future provider or control kind is a new render, never new policy. The effort→budget math, `none`→off mapping, and `max_tokens` clamp all live in this one resolver.
**Not:** A wire payload or a provider parameter. The intent is the shared vocabulary *between* the decision and the per-adapter render; it never goes on the wire as-is. The model-side capability it reads (`control`) is defined in `models.md`.

### Chain of Thought (CoT)
**Definition:** The opaque output produced during reasoning — both readable text and provider-specific data (signatures, encrypted content) that must be preserved unchanged for round-tripping. How far persisted CoT replays into later requests is the adapter's per-provider reasoning-replay policy (`none` / `current_run` / `full_history`): within tool-use loops dropping it breaks model continuity, and providers like Anthropic expect it back unchanged across the whole same-model conversation. The adapter handles all serialization and round-trip preservation; the chat layer owns history shaping (which entries keep CoT) but never interprets CoT data.
**Not:** Reasoning. CoT is the opaque output; reasoning is the capability and its configuration (GLOSSARY → Reasoning).
**Example:** Anthropic returns `thinking` blocks with a `signature` field. Whenever history is replayed — a tool-use loop or, under `full_history`, a later run on the same model — the adapter must send both fields back unchanged; dropping the signature breaks continuity even though vBot never reads it.

## Data Model

- Provider JSON owns `id`, `name`, adapter selector, base URL, `connections`, optional `defaults`, optional `extra_headers`, optional `models_endpoint`, and an optional `context_window`. `context_window` is the per-provider **read-side fact default** — a positive int (validated; `0`/negative/non-int rejected) applied when a model on this provider has no window of its own. It is distinct from `defaults` (which holds request-shaping params like `max_tokens`): the fine line is *request-shaping defaults → `defaults`/adapter; read-side facts like `context_window` → provider-config level*.
- Connection JSON is provider-local until exposed externally as `<provider_id>:<local_connection_id>`. Supported connection types are `api_key`, `oauth`, and `none`; API-key connections require `auth.credential_key`, OAuth Device Flow connections store their flow metadata under `oauth`, and `none` is a first-class **keyless** connection (e.g. local Ollama): its `auth` block is optional (defaults to an empty `AuthConfig`), it always reports exactly one implicit usable account (`ProviderAccount(id="default", usable=True, source="none")`), resolves to credential value `""`, and passes every credential gate — adapters and discovery skip the auth header when the header name or the credential is empty. Because it passes every credential gate, a keyless connection is **disabled by default** and needs an explicit user enable before vBot probes or lists it (see Terms → Usable). `provider.set_key`/`unset_key` reject `none` targets (they only accept api_key connections). A connection may also carry:
  - `mode: str` — adapter-interpreted wire-variant selector. The provider's adapter reads it at construction time and picks the right request builder / response parser for the connection (e.g. OpenAI `codex_responses` vs the generic chat-completions default). `None` and the default chat-completions value both mean the generic path.
  - `models_endpoint: str` — per-connection discovery endpoint, overrides the provider-level `models_endpoint`. Used when different connections of the same provider talk to different model catalogs.
  - `base_url: str` — per-connection base URL, overrides the provider-level base URL. Used when different connections of the same provider hit different hosts (e.g. Platform `api.openai.com` vs ChatGPT `chatgpt.com`).
  - `auto_refresh: bool` — marks the connection's model catalog for automatic refresh (server startup + `model.list`, throttled, **only while the connection is enabled**; see `models.md` → "Local catalogs auto-refresh"). Meant for local endpoints whose installed-model set changes outside vBot; remote catalogs stay explicit-refresh only. Must be a boolean when present.
  Both `mode` and `models_endpoint` must be strings when present; non-string values are a config error.
- **Accounts** (`core/providers/accounts.py`): an account is a named credential slot on a connection — multiple API keys or OAuth logins per connection. Compositional id grammar is `provider:connection[:account]`; the default slot is `default`. Account ids match `^[a-z0-9][a-z0-9_]{0,31}$` (no dashes — keeps env-key derivation bijective and token filenames unambiguous). API-key accounts map to derived env keys via `derive_credential_key`: `default` → the connection's base `credential_key` unchanged, named accounts → `BASE__<ACCOUNT>` (uppercased). Accounts are discovered by scanning process env + data-dir `.env` for the base key and `BASE__*` keys (`BASE__DEFAULT` is rejected — the default account's only canonical spelling is the base key). `ProviderAccount(id, usable, source, credential_key)` with `source` in `process_env`/`data_dir`/`oauth`; process env wins over data dir for the same account. Catalogs and discovery stay connection-level — accounts are interchangeable credentials, not separate catalogs.
- `ProviderRegistry.load(resources_dir)` parses `resources/providers/*.json`, rejects duplicate provider ids/connection ids, validates connection types/OAuth device-flow names, and caches the registry by resolved resources path. Provider ids must not contain `:`; connection ids must not contain `--` or `:` (compositional-id and token-filename ambiguity guards).
- `TokenStore` persists OAuth tokens under `<data_dir>/oauth/<provider_id>-<local_connection_id>.json` for the `default` account and `<provider_id>-<local_connection_id>--<account>.json` for named accounts, after validating ids against path traversal. `list_account_ids` enumerates stored accounts (default first, then sorted). Expired tokens still count as usable when they have a refresh path (`refresh_token` or Copilot's stored `github_oauth_token`).
- Each catalog model may carry a `connections` allowlist (`tuple[str, ...]`) that binds it to a subset of its provider's connections; empty tuple means "all connections". Discovery writes each refreshed model with `connections: [<credential_connection.id>]` and refresh merge keeps models belonging to other connections intact (see `models.md` and `model_tasks.md` for the read-side filter).

## Interfaces

- `runtime.get_adapter(provider_id, connection_id)` is the adapter factory. It requires a compositional `provider:connection[:account]` id, resolves the selected connection, injects `StaticTokenGetter` or `OAuthTokenGetter` (bound to the resolved account), injects `model_lookup(model_id)`, and passes a `ProviderDebugRecorder` when debug mode is enabled. An absent account part resolves to the connection's first usable account (`default` first, then sorted); an explicitly pinned OAuth account is used as given so a mid-flight login still works. The connection's `mode` is threaded into the adapter as `connection_mode`; adapters that ignore it (because they have a single wire variant) accept the keyword-only parameter and discard it.
- `ProviderCredentialResolver` reads API-key credentials from process environment first, then the data-dir `.env` fallback, per account via derived credential keys. OAuth credentials come from `TokenStore`; OAuth connections without `oauth` metadata are treated as static-token stubs (their accounts also resolve via derived env keys). `list_accounts(provider_id, local_connection_id)` returns the connection's `ProviderAccount`s; `resolve_account_id(provider_id, local_connection_id, account_id=None)` validates an explicit account or picks the first usable one.
- The resolver is also the single owner of connection **usability** (Terms → Usable): `is_connection_enabled(provider_id, connection_id=None)` answers the user switch (settings override, else `connection_default_enabled`), `is_usable(...)` the conjunction enabled AND credentialed — at provider level the conjunction is per connection, never across two different ones. The runtime injects `enabled_overrides_loader` (a live settings read); a resolver built without it applies pure type defaults. **Gating consumers ask `is_usable`**: `model.list`'s per-model gate, task-target expansion (`model_tasks`), the local-catalog auto-refresh targets, the usage probe, the chat layer's unpinned-connection pick, and the config-agent model probes (`core/projects/resolver.py`). **Credential-management surfaces keep `has_credentials`**: the settings panel's `configured`, `set_key`/`unset_key` responses. `runtime.get_adapter` rejects a disabled connection with a clear `ConfigError` ("… is disabled — enable it …") *before* credential resolution, so a disabled provider fails with the real reason, not "credentials not found". The user toggle is the `connection.set_enabled` RPC (`server.md`) / `vbot provider enable|disable` (CLI), persisted via `StorageManager.set_provider_connection_enabled` (settings section in `settings.md`).
- **Local-endpoint reachability** is runtime state, not resolver state: `Runtime.maybe_refresh_local_catalogs` records each auto-refresh probe outcome per connection id and `Runtime.connection_reachability(connection_id)` returns `True`/`False`/`None` (never probed). Surfaced on connection payloads (auto-refresh connections only) and as the `model.list` `reachable: false` marker (`models.md`, `server.md`).
- Server RPC `provider.set_key` only targets API-key connections. It writes the resolved account's derived credential key to the data-dir `.env`, reloads runtime fallback credentials, and never returns the secret value. `provider.unset_key` is the inverse: it removes the account's derived key from the data-dir `.env` and reloads; process-environment credentials are out of its reach, so its `configured` response field can stay `true` after removal. The full account-aware RPC contract lives in `server.md`.
- Model discovery uses the effective `models_endpoint` (`connection.models_endpoint` or provider-level fallback) and base URL (`connection.base_url` or provider-level fallback) for each connection. A refresh iterates every connection that is usable (enabled + credentialed) and has an effective `models_endpoint`; each iteration's discovered models are tagged with `connections: [<credential_connection.id>]` and merged into the existing catalog by replacing only models whose `connections` include the current connection id. Discovery also uses adapter `discovery_headers()`/`discovery_params()`/`supplementary_discovery_params()` hooks and `normalize_catalog_entry()`. Discovery accepts top-level `data` or `models` lists and writes refreshable catalog artifacts. The catalog GET shares the chat path's transient-failure handling: it runs inside `retry_async` with `wrap_network_error`/`classify_http_status`, so transport/timeout errors and retryable statuses (429/502/503/504, honoring `Retry-After`) are re-issued with backoff while fatal statuses (401/403/404/500) and malformed bodies abort immediately; the surfaced error is still wrapped as `ModelDiscoveryError`, and a failed *supplementary* fetch is logged-and-skipped, never fatal.
- `ProviderAdapter.send()`, `stream()`, and `normalize_response()` are the chat-facing contract. `stream()` yields normalized vBot deltas only; raw provider chunks and SSE event names stay inside adapters.
- `ProviderAdapter.reasoning_replay_policy(model_id) -> ReasoningReplayPolicy` (`none` / `current_run` / `full_history`, defined in `core/providers/reasoning.py` and exported from `core.providers`) declares how persisted assistant `reasoning`/`reasoning_meta` replays into request history. The ABC default is `current_run` (the historical behavior); the chat layer queries the hook per request build and owns the resulting history shaping, including the same-model gate for `full_history` (semantics in `chat.md` → Conventions). The policy is adapter-coded only — no catalog field, no provider-JSON field, no agent setting. `model_id` is part of the contract because one adapter can route models to different wires.
- `ProviderAdapter.wire_media_support(model_id) -> frozenset[str]` declares the concrete media types (MIME, e.g. `image/png`, `audio/wav`, `application/pdf`) this adapter's wire can carry natively. This is the **wire-capability** half of attachment routing; the **model-capability** half stays `capabilities.input_modalities`. The chat layer intersects the two per request build and the resolver degrades anything outside the intersection (semantics in `attachments.md`/`chat.md`) — no provider format constant lives in the chat layer. ABC default is `frozenset()` (carry nothing — a forgotten declaration degrades, never crashes); every concrete adapter overrides it. Mirrors `reasoning_replay_policy`: adapter-coded only, `model_id` in the signature, and concrete adapters may branch on `self._connection_mode` (OpenAI: chat carries images + WAV/MP3 + `application/pdf`; `codex_responses` images only). The shared image set is `IMAGE_WIRE_MEDIA_TYPES` in `core/providers/adapter.py`. **`application/pdf` is declared only on verified adapters (OpenAI chat mode, Anthropic), never on the `OpenAICompatibleAdapter` base** — so OpenRouter/MiniMax/etc. do not inherit native PDF. Document *encoding* is separate from declaration: the OpenAI-compatible translator maps a canonical `{"type":"document",base64,media_type,filename}` block to a Chat Completions `file` part (`file_data` data-URL), and the Anthropic adapter maps it to a base64 `document` block — both encoders exist regardless of which adapters declare the format.
- `core/providers/task_client.py` — `ProviderTaskClient`, the shared base for the task-model HTTP clients in `core/model_tasks/` (`ProviderSpeechClient`, `ProviderImageClient`, `ProviderEmbeddingClient` — see `model_tasks.md` and its child maps). Owns the bound `(provider, connection, token_getter, model_id)` constructor, the `from_runtime(runtime, target_ref)` factory (structural `TaskClientRuntime`/`TaskTargetRef` protocols defined locally — the module must not import `core.runtime` or `core.model_tasks`, import-cycle risk), auth-header assembly, and `post_and_parse(endpoint, *, timeout, parse, json=None, data=None, files=None, headers=None)`. `from_runtime` uses `runtime.get_connection_token_getter(...)`, so OAuth-backed task targets refresh tokens the same way chat adapters and usage probes do; headers are rebuilt inside each retry attempt, never bound once before the retry loop. The optional `headers` builder lets a task wire add connection-mode-specific headers (for example OpenAI subscription image generation adds `chatgpt-account-id` and Codex headers) while preserving shared retry/status behavior. The `parse` callback runs **inside** `retry_async`, so retryable `ProviderError`s raised during response parsing are retried like transient HTTP errors. `classify_task_response(response)` is the shared status classifier that appends the error body as detail. Task clients deliberately use a plain `httpx.AsyncClient` — no debug capture, unlike chat adapters.

## Provider Usage Probe

`core/providers/usage.py` — `ProviderUsageService`, an on-demand probe of each logged-in connection's *own* subscription usage (rolling-window percent used, reset time, plan). This is **live provider state**, deliberately separate from `core/statistics/` (a read-only Session aggregation that never hits the network); the only coupling is the WebUI Limits subtab that surfaces it (see `statistics.md`, `webui.md`). Exposed via RPC `provider.usage` (`server.md`), never through chat.

- **Common shape** (`to_dict()`-able frozen dataclasses): `UsageWindow{label, used_percent, reset_at}`, `ProviderUsageSnapshot{connection, display_name, plan, windows, error}`, `UsageReport{generated_at, providers}`. `used_percent` is clamped 0–100; `reset_at` is ISO-8601 UTC or `null`.
- **DI, no import cycle.** Constructed from a local `UsageProbeRuntime` protocol (`providers`, `provider_credentials`, `get_connection_token_getter`, `get_connection_token_extra`) — like `task_client.py` it must not import `core.runtime`. The HTTP GET is an injectable `UsageTransport` (httpx by default) so tests never hit the network. Not exported from `core.providers.__init__` (import directly), mirroring `task_client.py`.
- **Fan-out / fail-open.** `report(connections=None)` queries only connections with a registered fetcher AND `is_usable` (enabled + credentialed — a disabled connection is never probed); fetchers run concurrently with a per-fetcher timeout; one failure (timeout → `Timeout`, HTTP error → `HTTP <code>`, shape mismatch → `Unsupported response shape`, anything else → `Unavailable`) becomes that snapshot's `error` and never breaks siblings; snapshots with neither a window nor an error are dropped. The per-connection in-memory cache keeps successful snapshots for 10 seconds and error snapshots for 60 seconds; a per-connection async lock coalesces concurrent cache misses so multiple WebUI windows never multiply an outbound fetch.
- **Token safety.** Never caches raw OAuth tokens and logs no token data — it pulls a fresh token per fetch via the runtime token getter (`get_connection_token_getter`), and reads token-store `extra` via `get_connection_token_extra` (Copilot's `github_oauth_token`, OpenAI's mirrored `chatgpt_account_id`).
- **Supported connections.** `openai:subscription` (live-verified 2026-06-16), `github-copilot:oauth` and `minimax:api-key` (blind from openclaw field names, degrade to an `error` snapshot on shape mismatch). Per-endpoint facts live in `providers/openai.md`, `providers/github-copilot.md`, `providers/minimax.md`.

## Adding A Provider

1. Add `resources/providers/<name>.json` with an adapter selector, at least one connection, and `models_endpoint` only when the catalog is refreshable.
2. Inspect the real models endpoint response before designing catalog normalization; preserve discoverable modalities, request parameters, limits, and small runtime-relevant metadata.
3. Send at least one probe inference request against the runtime endpoint you plan to support, including streaming when the provider advertises it.
4. Verify real behavior for reasoning controls, tools, structured output, streaming, output-token limits, and response shape.
5. Put discoverable facts in adapter normalization/runtime policy. Use model overrides only for durable facts provider APIs do not expose.

## Conventions

- Usage normalization is canonical across adapters: `input_tokens` always means the total prompt including cached tokens, and provider prompt-cache counters map to optional `cache_read_tokens`/`cache_write_tokens` (OpenAI-style `prompt_tokens_details.cached_tokens` / Responses `input_tokens_details.cached_tokens` are subsets of the wire's input count; Anthropic-style separate cache counters are added onto `input_tokens`). Semantics live in `chat.md` → Token Usage.
- Reasoning feedback signals are surfaced, never swallowed. The canonical helpers live in `core/providers/reasoning.py` and are called from the OpenAI-compat `send()` path (covering all `OpenAICompatibleAdapter` subclasses): (1) when a provider returns HTTP 400 whose detail conservatively names a reasoning/effort control, a structured `warn` (logger `vbot.providers.*`) names the model + selected effort **before** `classify_http_status` runs — classification/retry policy is unchanged (`core/utils/http_status.py` stays the owner; 400 stays fatal/non-retryable); (2) when a non-`none` effort was selected but the response `usage` reports `completion_tokens_details.reasoning_tokens == 0`, a `warn` names model + effort. Both are conservative — an absent/unknown signal stays silent (no false reclassification). No token values are logged.
- **Per-model wire SELECTORS are data, MECHANICS stay in the adapter.** A published per-model wire fact (which protocol, which reasoning mode, which response field carries reasoning) lives in a **provider-scoped** `metadata` blob on the model (`metadata.<provider_id_underscored>.*`, e.g. `metadata.opencode_go.protocol`, `metadata.mistral.prompt_mode`, `metadata.<provider>.reasoning_response_field`) — never a generic top-level field, so one provider's quirk can't pollute the schema for all. The adapter reads the fact via its injected `model_lookup` and owns only the *how* (building the Anthropic vs OpenAI request, the `prompt_mode` vs `reasoning_effort` shape). At load, `metadata` is replaced **wholesale** by the highest layer (assembly contract). The facts are projected at refresh where models.dev publishes them (e.g. `interleaved` → `reasoning_response_field`) and hand-carried in `<provider>.overrides.json` where the endpoint/feed does not (opencode-go `protocol`, mistral `prompt_mode`). Generalizes the original `metadata.github_copilot` pattern. `normalize_response(response, *, model_id=None)` takes an optional `model_id` so the OpenAI-compatible path can read `reasoning_response_field` per model; it reads the field WHEN PRESENT and falls back to the hardcoded default-key scan otherwise (graceful — works whether or not catalogs carry the field).
- **Reasoning is one policy, many renders.** `resolve_reasoning_intent(*, supported, control, levels, effort, budget_max, max_tokens)` (in `core/providers/reasoning.py`) is the single decision layer: it turns `(model control, agent effort)` into a provider-neutral `ReasoningIntent` (`default`/`off`/`effort`/`budget`/`on`). It owns the policy — effort→budget math (`effort_to_budget`: proportional to `budget_max` or an absolute fallback ladder, clamped `[1024, budget_max]` and under `max_tokens`), `none`→off, and the `max_tokens` clamp/skip. Each adapter resolves the intent and *renders* it onto its own wire; the per-model accessors are `model_reasoning_control` / `model_reasoning_levels` / `model_reasoning_budget_max`. Snapping is still per-model against the effective ladder — the adapter passes `model_reasoning_levels(...)` **or its floor** as `levels`, so a model with no feed ladder snaps against the adapter constant (`OPENAI_REASONING_EFFORTS`, `OPENROUTER_REASONING_EFFORTS`, `ANTHROPIC_EFFORT_FLOOR`, …). Renders: **openai-compatible base** → `reasoning_effort` (budget/on degrade to effort, no native field); **OpenRouter** → `reasoning:{effort}` for effort *and* budget (it maps effort→budget internally, so no token budget is sent), `reasoning:{enabled}` for on/off; **Anthropic** → adaptive thinking + `output_config.effort` for effort, native `thinking:{type:enabled,budget_tokens}` for budget, enabled+floor for on, `{type:disabled}` for off; **MiniMax M3** → adaptive thinking + `reasoning_split` (no native budget); **Copilot `/v1/messages`** → policy-driven adaptive/`output_config`, and a budget-only Claude derives a native `thinking_budget` from the effort via the shared `effort_to_budget`, clamped to the policy's min/max and under `max_tokens`. `mistral` and `openai` (subscription) stay effort-only (no reachable non-effort model) and snap via `closest_supported_effort`. The rendered result is also resolvable **outside** the adapter (`resolve_actual_thinking_effort` in `core/chat/commands.py`, which reuses the same resolver) so `/status` reports the snapped effort, `on`/`off`, or the rendered budget.
- **Output allowance defaults to the model's catalog ceiling.** Provider `defaults` are request defaults, not model facts (lower priority than caller kwargs) and never backfill a model fact — a model with no discoverable output ceiling still normalizes as `max_output_tokens: null`. But the flat provider-config `max_tokens` default (commonly 8192) would truncate any model whose real ceiling is higher — reasoning models most, since their trace counts toward the same allowance. So the `OpenAICompatibleAdapter` base (`_apply_model_output_limit` → `_model_max_output_tokens`, inherited by openai/openrouter/mistral/minimax and the Copilot chat path) and the Anthropic adapter both default request `max_tokens` to the model's catalog `max_output_tokens` when the caller sent **no** explicit output limit (`max_tokens` / `max_completion_tokens` / `max_output_tokens`); an unknown ceiling keeps the flat config default as the fallback. opencode-go overrides `_model_max_output_tokens` for its flat vendor-prefixed namespace and applies the same resolution in `send`/`stream`, so its Anthropic sub-route gets the ceiling too.
- **Context-window resolution is read-side and shared.** `resolve_context_window(model_context_window, provider_config)` (in `core/providers/providers.py`, exported from `core.providers`) is the single source of truth for "what window do we actually use": model value → provider-config `context_window` default → `GLOBAL_CONTEXT_WINDOW_FLOOR` (a named, conservative last resort, ~8k, that keeps custom/window-less models alive). Non-positive values at any layer (a stray `0`) are treated as unknown and skipped, so a fake `0` can never reach a caller as a budget; the return is always a positive int. **Flagged-local models resolve one level higher through `resolve_effective_context_window(...)`** (same module): user-set settings value (`local_models.context_windows["<provider>/<model_id>"]`), else `min(LOCAL_CONTEXT_DEFAULT_CAP=32768, chain value)`; `model_is_local(metadata)` reads the refresh-stamped locality flag (see `models.md` → locality). Read-side callers (compaction/token-budget in `core/chat/chat.py`, `/status` in `core/chat/commands.py`, the agent payload in `server/rpc/payloads.py`) all route through the effective helper — no caller re-implements the chain, and the helpers live at the provider-config level, **not** in an adapter. The `model.list` payload deliberately carries the *raw* `context_window` (`null` when unknown) plus an `effective_context_window` (resolved for flagged-local models, else = raw) — accessors tolerate `null` and the WebUI shows a no-context badge variant — only the *active agent's* window (agent payload) is resolved through the chain for the token badge.
- Adapter catalog normalizers never bake a placeholder window: a window-less endpoint yields `context_window: null` (OpenAI-compatible, GitHub Copilot, Mistral all drop their old `DEFAULT_CONTEXT_WINDOW`/`or 0`); OpenRouter normalizes its `context_length: 0` (non-chat models) to `null`. The fill happens read-side via the chain, never in the data.
- Provider JSON uses `connections`; old single-provider `auth` JSON is invalid.
- Provider chat HTTP clients use bounded connect/write/pool timeouts and no read timeout; long non-streaming generations may exceed one minute. Streaming stalls are guarded by the chat streaming chunk timeout.
- Sparse OpenAI-compatible catalogs remain usable as text chat catalogs. Missing optional facts are unknown, not authoritative negatives, unless the provider-specific adapter says otherwise.
- Subclass `OpenAICompatibleAdapter` only when runtime behavior, streaming, reasoning, catalog normalization, or request policy differs from the generic `/chat/completions` contract.
- Adapters must not re-implement history-wide reasoning strips on top of `reasoning_replay_policy` — the chat layer owns history shaping. Adapter-side reasoning handling is limited to wire formatting (visible text vs. opaque blocks) of whatever reasoning survives shaping.
- Token values, API keys, authorization codes, user codes, refresh tokens, and account ids must never be logged.
- None-valued caller kwargs are treated as not specified — adapters drop them before building payloads; provider defaults then apply. Falsy-but-not-None values (e.g. `temperature=0.0`) survive the filter and continue to override defaults.
- Every httpx transport failure is classified into a vBot error type: `httpx.TimeoutException` (and its subclasses — `ConnectTimeout`, `ReadTimeout`, `PoolTimeout`, `WriteTimeout`) → `ProviderTimeoutError`; every other `httpx.TransportError` (`ConnectError`, `ReadError`, `WriteError`, `RemoteProtocolError`, `LocalProtocolError`, `ProtocolError`, …) → `NetworkError`. Both stay retryable so `retry_async` re-attempts; the chat loop catches them and persists a `role: "error"` message.
- Which HTTP statuses are retryable is decided once in `core/utils/http_status.py` (`is_retryable_status`), shared by adapters and the HTTP-calling tools so the definition can't drift per call site. Policy: **429/502/503/504 retryable for any method**; **500 retryable only for idempotent requests** (GET/HEAD), because a non-idempotent POST may have been partly applied and a 500 is often deterministic. `classify_http_status` calls it with `idempotent=False` (all provider HTTP is POST) plus `extra_retryable` (e.g. Anthropic `529`), so the provider path retries 429/502/503/504(+529) but not 500.
- `Retry-After` is honored. `classify_http_status` takes the response headers and `parse_retry_after` (home: `core/utils/http_status.py`, shared with the HTTP tools; re-imported by `_http_shared`) reads the wait hint — `retry-after-ms` (millisecond hint, highest priority), then `Retry-After` as `delay-seconds`, then `Retry-After` as an HTTP-date. The parsed seconds ride on the retryable error's `retry_after`; `retry_async` uses it as a *floor* over its exponential backoff (never retry earlier than the server asked), capped at `MAX_RETRY_AFTER_SECONDS` (60s) so a malformed/hostile header can't stall an interactive request. A malformed header parses to `None` (ignored, not an error); non-retryable statuses (401/403, other 4xx) never carry a hint.
- A 2xx response with an unparseable JSON body is a fatal `ProviderError(retryable=False)` (mirroring how malformed SSE data is handled by `parse_sse_json_data`). The raw `json.JSONDecodeError` is preserved as `__cause__`.

## Constraints & Gotchas

- Runtime adapter creation has no fallback to "first usable connection"; callers must pass the exact connection id. Provider-level credential checks may choose the first usable connection only for status/listing/discovery helper paths. Account selection is the deliberate exception: an absent account part in an otherwise exact connection id resolves deterministically to the first usable account.
- Agent models and task targets may pin an account via the suffix grammar `<provider>/<model>::connection[:account]`; the suffix passes through verbatim into the compositional connection id. `TaskModelTargetRef.account_id` is empty when not pinned, and task target listing/expansion stays connection-level (no per-account target cross-product); the WebUI chat-model picker, in contrast, does expand options per usable account (see `webui.md`).
- API-key credentials resolve when an adapter is created. OAuth tokens may refresh during requests through `OAuthTokenGetter`, so do not cache the raw OAuth access token outside the getter. Both `send()` and `stream()` rebuild auth headers *inside* the retry closure (one `_build_headers()` call per attempt), so a connect retry after a 429/503 backoff that spans a token refresh uses the new token — never bind headers once outside the closure.
- Streaming retry inside the adapter only covers connection establishment. Once an SSE stream is open, mid-stream read/provider errors propagate to the chat layer, which restarts the whole stream when nothing visible was emitted yet (see `chat.md` → mid-stream restart).
- `ProviderStreamingUnsupportedError` is the only streaming error that triggers the chat loop's non-streaming fallback. Other streaming failures are not silently retried as non-streaming requests.
- Provider catalogs under `resources/models/` are refreshable artifacts. Durable behavior belongs in adapter code, runtime policy, or externally verified overrides, not hand-edited generated model files.
- `NetworkError` is retryable but not provider-specific and must not trigger model fallback.
