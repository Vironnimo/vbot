# Agents

Persisted agent configuration and workspace lifecycle management.

## Overview

`core/agents/` owns `agent.json` CRUD, the canonical Identity Agent roster order, and coordinated Identity Agent rename under `<data_dir>/agents/`. Creating an Agent seeds a workspace from bundled templates and creates no Session: its `current_session_id` stays empty until a first message creates one (`server.md` -> `chat.send`/`chat.stream` `new_session`). Renaming moves the Agent-owned tree and retargets live global Session addresses; it is recorded durably so an interrupted rename ends fully old or fully new on the next start (Constraints). Deleting archives the Agent as an archive entry (`archive.md`): the store moves its tree into the entry's payload while the archive service archives its live Sessions, and moves the tree back when that fails; afterwards the Agent leaves every other Agent's delegation allow-list, recorded so a restore re-adds it (Constraints). A restore moves the payload back, under the archived id or another one. A **per-agent private skills home** may exist at `<agent-dir>/skills/` (created on first write by `skill_manage` or skill RPCs, private and always-allowed - see `skills.md`); it moves/archives with the Agent, together with its Skill History `skill-history.jsonl` and Skill Archive `skill-archive/` beside it in the Agent directory, and is not seeded at creation.

## Data Model

Tool permission persists as root `tool_access`: mode `all`/`selected`/`none`, `selected` requires `allowed`, any mode may carry explicit opt-ins in `granted` (also used for the vision exception in `tools/image.md`) and absolute `denied` names winning after activation and grants; the retired root `allowed_tools` is an ordinary unknown field (a `doctor config` warning, kept on disk). `memory_prompt_mode` stays independent (prompt Memory, not permission). `<data_dir>/agents/order.json` holds `{revision, agent_ids}` collection metadata: missing preserves id-sort until first materialization, absent valid agents append, stale ids filter out, malformed files never hide agents (`doctor config` reports; explicit reorder replaces). A listing never rewrites an `order.json` it could not load, an unreadable one or one that cannot be checked included. `agent.json` and `order.json` are Generation 1 JSON documents (`format_version` 1, unknown fields kept on every write, never overwritten after a failed load; contract in `settings.md`).

Besides `format_version`, `id` is the only load-required field - every other field defaults when missing/null while present-but-malformed values invalidate that one Agent. Key fields:

- `id` doubles as directory name, changed only through coordinated rename.
- `model` / `fallback_models` are user-facing `<provider>/<model-id>` optionally pinned `::<connection-local-id>[:<account-id>]`; empty resolves against `defaults.agent.model` at read time without rewriting disk. `fallback_models` is the ordered fallback chain (max 5, duplicates rejected at save). Chat owns runtime eligibility and shared retry limits, including exhausted network/timeout recovery; see `chat/run-execution.md`. Unresolvable/unusable candidates are skipped with a warning, and an activated candidate stays for the rest of that Run only without changing the persisted primary Model.
- Persisted empty models / null temperature/top_p/effort mean "no override": `AgentStore` bakes `defaults.agent` values into `get()`/`list()`/mutation results; raw disk stays unresolved (`get_raw` skips baking for the resolver's provenance seam).
- `memory_prompt_mode`: `off` | `agent` | `agent_user` (default) controls prompt-visible memory files.
- `workspace` defaults to the data-dir location and stays independent of Project. Resolved paths are always absolute in API/UI; inside the data dir `agent.json` stores a forward-slash relative path anchored to it (making the data dir portable), external workspaces stay absolute. Relocation is always explicit: declining copy repoints with normal SOUL seeding; accepting copy moves only SOUL/USER/MEMORY, backs up replaced destinations, rolls back on failure. A source or destination file that cannot be checked fails the relocation (and rolls it back) instead of counting as missing; seeding creates `SOUL.md` exclusively, so it never replaces one it could not see.
- `root_project_id` is the Agent's default Project (GLOSSARY -> Default Project): the Working Project of each new Session whose creator names none (`sessions.md` -> Terms -> Working Project). Selecting/clearing changes nothing else - existing Sessions keep their Working Project, and Workspace, private Skills, prompt customizations, permissions, and Sub-Agent addressing stay independent. Missing means new Sessions work in the Workspace; loading never infers from Workspace.
- `current_session_id` is empty or names a live Session; empty means a new conversation whose Session does not exist yet, and no read or repair creates a Session. A dangling pointer is cleared on load (rewriting during read, one INFO line `Dangling current Session pointer cleared`). `update(current_session_id="")` clears it too (RPC `agent.update` with `null`; `/new` does this); a non-empty value must name a live Session. After a Session leaves via move/delete, `reset_current_after_session_removed` lands on the last-active *remaining* Session instead (Sessions' `newest_session_id`, one bounded page read), or clears the pointer when none remains. That write-time repair does not close the gap: the pointer (`agent.json`) and Sessions (SQLite) share no transaction, so a failed or interrupted re-aim, a restored Session store, or an offline edit can still leave it dangling. Reads that return the pointer (`get`, `list`/`list_with_order`, and the loads inside `update`/`rename`) therefore keep verifying it; a roster read verifies every pointer in one Session read (`ChatSessionManager.existing_addresses`), a single `get` in one point read. `get_raw` serves configuration provenance only and returns the stored pointer unverified (`test_agents_mutations.py`). Because of that repair, Event-Loop callers read one Agent with `get_async`, which runs `get` as one unit on the Session database's pool (`ChatSessionManager.run_async`); Agent resolution uses it, and a closed Session database raises `DatabaseUnavailableError` (`tests/core/projects/test_resolver_scan_identity.py`).
- `tool_access` defaults `{"mode":"all"}`; unknown Tool names persist for temporarily unavailable Extensions; `allowed`/`denied` must not overlap; the retired `*` wildcard is invalid. Tool-owned settings live under optional root `tools.<tool>`: `tools.subagent.allowed_agents` lists only *additional* targets (`['*']` default, `[]` self-only, bare or qualified ids); `tools.bash.allowed_env` is the ordered deduplicated permanent env-grant list. Denying an owning Tool deactivates its settings without deleting them. Automatic Tools (`memory`, Session-granted Extension Tools) are not independently selected but explicitly deniable.
- `custom_system_prompt_enabled` gates reading the agent's own prompts directory; disabling ignores files without deleting them.
- `librarian_enabled` (boolean, default `true`; missing or `null` reads as `true` without a rewrite) is the per-Agent switch of Librarian passes over the Agent's own Skills: off, the schedule skips the Agent and `librarian.run` refuses (`automation/librarian.md`). Only the Librarian reads it; no prompt, Tool or ordinary Session depends on it. Surfaces: `agent.create`/`agent.update` (`server.md`), `--librarian true|false` (`cli.md`), the Agent editor's Librarian row.
- `builtin` (optional, written only when set) marks a built-in Agent vBot creates itself; the only value is `librarian`, valid only on the id `librarian` (otherwise the Agent is invalid). See Built-in Librarian below.
- `allowed_skills` (`["*"]` or missing = all, `[]` = none) grants Skills beyond the private and active-Project ones, which it cannot narrow. Optional `excluded_skills` (default `[]`, written only when non-empty, deduplicated; blank names and `*` are invalid) withholds names from that grant, including from `*`, and turns off the Agent's own private Skills of those names; the active Project's set stays granted. Semantics: `skills.md` -> Agent Skill Exclusion.

## Built-in Librarian

The Librarian (GLOSSARY -> Librarian) is an ordinary Identity Agent directory `agents/librarian/` whose `agent.json` carries `"builtin": "librarian"`; constants and `is_librarian(agent)` (any resolved Agent) live in `core/agents/_types.py`. Behavior (`test_agents.py`, `tests/core/runtime/test_runtime_wiring.py`):

- **Creation:** Runtime startup calls `AgentStore.ensure_librarian()` right after `ensure_bootstrap()`; it creates the Agent through the normal create path (first Session, Workspace with the bundled `SOUL.md`) with a new Agent's defaults, so its Model is empty and resolves to `defaults.agent.model` until the user picks one. `librarian_problem()` names why it is unavailable: `missing` (not created yet), `agent_id_taken` (an Agent of the user, or an unfinished rename, holds the id - that Agent stays untouched and keeps working) or `invalid_config`; `librarian()` returns it or `None`; `librarian_problem_message(problem)` says it to the user with the way out (`automation/librarian.md` -> Surfaces). Startup logs a WARNING for an unavailable Librarian, and no pass runs while it is unavailable.
- **Fixed capabilities:** every load (`_agent_from_dict`) and create forces `tool_access` to `selected` `skill`/`skill_manage` with `fixed` set (`tools.md`: no Memory, Session-grant or follower Tool can activate), `memory_prompt_mode` `off`, no custom System Prompt, no Project root, no Tool settings and `librarian_enabled` false, whatever `agent.json` says. Skills, compaction policy and the Model settings stay as stored.
- **Lifecycle refusals (`BuiltinAgentError`, an `AgentError`, RPC `domain_error`):** `rename` of the Librarian, `archive_files` (so `agent.delete`), and `update` of any field but `model`, `fallback_models`, `temperature`, `thinking_effort` and `current_session_id`. `_validate_new_agent_id` reserves `librarian` in any case for `create`, a rename target and a restore under another id; `restore_target_problem` reports it as `agent_id_taken`.
- **Hidden surfaces:** `list`/`list_with_order` (roster, `agent.list`, roster order, `/agent` directory, Sub-Agent catalogs, Skill inventory, prompt scopes, the Librarian schedule) skip built-in Agents; `list_with_builtins()` appends the available Librarian for Statistics, so its Runs count as its own activity. `get`/`find`/`exists` and Agent resolution still return it, so its Sessions and Runs work like any Agent's. A Sub-Agent call naming it fails `agent_not_found` like an unknown Agent; Channels refuse it as `agent_id`; `/handoff` to it and `/agent` moves to or from it are refused; Reflection never reviews it (`callable_review_dimensions` reports no dimension). Automations are not refused: their pickers read the roster.
- **Skill subject:** a Session of the Librarian whose metadata holds `skill_agent_id` (`SKILL_AGENT_ID_KEY`) works on that Agent's Skills; the resolver applies the binding (`projects/resolution.md` -> Librarian Skill subject) and `skill_subject_id(agent)` names the Agent whose Skills any resolved Agent works on. `Agent.skill_agent_id` carries it on that runtime view only and is never persisted. An Agent rename moves the bindings that name the old id (`AgentStore._apply_rename`, `sessions.md`); an archived or deleted subject leaves them, and such a Session cannot run.
- **RPC payload:** `agent.get`/`agent.update` responses carry `builtin` (`librarian` or `null`).

## Uniform Agent Resolution

Owner-managed temporary Agents resolve through `AgentResolver.resolve_temporary_agent` using an exact canonical Session generation. `core/agents/temporary.py` owns their immutable configuration, indexed bindings and execution groups; Identity creation, workspace seeding and roster operations are not involved. `TemporaryExecutionGroups.owned_run`/`owned_runs` inspect exact Run ids with one indexed read (ids without an owned record raise `RunNotFoundError` or are absent), and `start` detects a replayed input by its durable input id rather than scanning the group's Run history. A selected Project does not narrow the configured Tool and Skill selection (`projects.md`). Tests: `tests/core/agents/test_temporary.py` and `tests/core/projects/test_resolver_config_agent.py`.

`TemporaryExecutionGroups.delete_group` requires a closed group and current
registration, waits for draining, closes the Terminal Sessions of its live
participants, deletes its bound participant Sessions through the Session manager
under a no-Run guard (`release_temporary_group`, shared with `archive_group`), and
releases its in-memory group. Repeated deletion is safe;
other owners and groups are outside its scope (`test_swarm_operations.py`).

Temporary configurations and persisted bindings carry optional `prompt_blocks`:
`None` inherits the normal layout; an explicit list selects all allowed System
Prompt contributions. Prompts owns its assembly semantics. Continuation input may
be empty so an owner can retain a canonical admission receipt without adding
guidance to the Model request; initial input must still be non-empty.
Evidence: `temporary.py`, `test_temporary.py`, `test_swarm_start.py`,
`test_swarm_stop_resume.py`.

They also carry an optional `compaction_policy`: `None` inherits the global
Compaction Policy; a dict is validated and normalized as one complete Policy by the
shared Settings normalizer when the configuration is built, and resolves as the
participant's Agent-level Policy (`compaction.md` -> Policy Resolution). The binding
config stores the key only when set, so inheriting participants and bindings that
predate the key are identical and resolve to `None` (`test_temporary.py`).

A temporary configuration can name `repository_profile`, a Team Agent id in its selected Project. Projects resolves the neutral Profile against the owner's selection, then Agents persists its resolved configuration and original creation request. Model/scalars, instructions and the resolved Tool policy stay immutable in the binding. Replayed creation returns that snapshot after repository edits. Swarm formations expose the selection (`extensions/swarm.md`); no Agent kind is added.

Run paths resolve through one seam, `AgentResolver.resolve_agent(project_id, agent_id)` (owned by `core/projects/`; details in `projects/resolution.md`) - never `runtime.agents.get(...)` directly. Identity branch (`project_id=None`): this domain's store, unchanged behavior. Project branch synthesizes a workspace-less Config Agent from the Team scan whose policy computes inside the Project Tool Whitelist (repository denials narrow; a vBot override fully replaces scanned policy within the ceiling).

Two freshness levels: team membership comes from the scan (cached per project, refreshed on open/re-scan); a single member's config reads fresh from the repo file on every resolve, mirroring identity agents re-reading `agent.json`.

Chains: identity agents keep model -> global -> empty. Config agents resolve override -> mapped repository Model wish -> Project default -> global -> error, where a candidate counts only if configured in this instance (registered provider, cataloged Model, usable credential permitted by its connection allowlist; pinned suffixes checked verbatim); unconfigured repository models surface as scan-time findings, and exhausted chains raise `AgentResolutionError` mapped to clean failures per caller. Temperature, top_p and thinking resolve override -> value -> project default -> global -> Provider default, where `""` (effort) and `0.0` (sampling) are real stopping values, not absent ones. Identity agents keep their two-tier injection unchanged. `effective_config(...)` exposes per-field `{value, source}` provenance using `get_raw` so persisted values distinguish from baked defaults.

## Conventions & Rules

- Agent IDs: filesystem-safe slugs, letter/digit start, letters/digits/hyphen/underscore, max 64 chars. `create`, the new id of `rename` and a `restore_files` under another id also refuse names Windows reserves for devices (`con`, `aux`, `nul`, `com0`-`com9`, `lpt0`-`lpt9`, any case) on every platform (`_validate_new_agent_id`, `InvalidAgentIdError`); existing Agents with such ids keep working everywhere else (`test_agents.py`, `test_agents_rename.py`, `test_agents_archive.py`). Lookups are exact on every platform: `get`/`get_raw`/`exists`/update/rename/archive/current-Session repair require a directory entry with exactly the requested spelling (`_stored_agent_path`), so a case variant is `AgentNotFoundError` (RPC `agent_not_found`, also when it arrives through Agent resolution; `projects/resolution.md`) even where the filesystem would open the stored tree, while a persisted id disagreeing with its directory stays a plain `AgentError` (`test_agents.py`). A store-local reentrant lock serializes complete lifecycle read-modify-write operations, current-Session repairs, and roster revisions across worker threads. Event Loop code takes it for reads, so no thread waits for a data snapshot while holding it: every mutation, and `lifecycle_guard`, admits its Agent document change before the lock (`_change`), and a read that must repair (a dangling current-Session pointer, a missing Workspace field, the roster order) while a snapshot is being taken gives the lock up, waits for the snapshot and repeats (`_repairing_read`; `database.md` -> Freeze admission). A read that repairs nothing never waits, so Agent resolution goes on during a snapshot (`test_agents_mutations.py`). Writes use temp-file atomic replace; relative persisted Workspaces resolve only against the active data directory, never cwd.
- The only seeded template is `SOUL.md`; USER.md/MEMORY.md belong to the memory system and create lazily on first write - a memory-off agent has neither, and deletion does not resurrect them. The seeded `resources/workspace-templates/SOUL.md` is a short behavior spec (reply sizing, uncertainty, disagreement, checking work) without a name, since the name comes from the display name in the Identity Environment block; existing Workspaces keep the text they were seeded with. How to write a SOUL: the bundled `agent-authoring` Skill (`skills.md`).
- Mutable-field validation lives server/core-side: effort vocabulary `null|""|none|minimal|low|medium|high|xhigh|max` (null inherits, "" = provider default), temperature null or 0.0-2.0 and top_p null or 0.0-1.0 (0.0 real; `agent.json` carries `top_p` only when set), strict policy shape, shell-portable env names. Enabling custom prompts seeds the agent prompt directory once; re-enabling preserves existing files.
- Run-local model fallback never mutates persisted model/fallback fields. The `::connection[:account]` suffix stores the provider-local slug, reconstructed to full runtime form at resolution; Account semantics in `providers/connections.md`.

## Store Operations

- `agents.py` keeps catalog mutation, Session coordination, compensation and the rename record. Internal `_types.py` holds records/errors, `_config.py` owns JSON validation and normalization, and `_workspace.py` owns paths, template seeding and reversible file relocation. Model fallback validation reuses Settings' `validate_fallback_chain`; Agent diagnostics and mutation errors retain their surface-specific wording.
- `create` creates the first Session (in `sessions.db`, before the Agent directory so a failure leaves no ghost directory), seeds the Workspace and persists the config; a failure removes the Session and the directory again. Returned Agents are effective-resolved. `get` bakes defaults and stays strict for addressed invalid agents; `list` isolates individual unreadable configs (log+skip) and degrades to empty roster on enumeration failure so bootstrap can still run. `list_with_order`/`reorder` guard roster replacement with optimistic revision + exact-set matching (`AgentOrderConflictError` otherwise).
- `ensure_bootstrap()` creates a bootstrap Agent only when zero valid Agents exist; invalid directories stay for diagnosis and an occupied `main` shifts to the first free `main-N`.
- `rename` applies the Agent-owned half of a rename and returns with its record still pending: live Sessions and the Sub-Agent parent links to them, then the whole tree (`os.replace`; case-only Windows renames go through the temporary sibling named in the record), the config with an in-tree Workspace rebased (external paths preserved), the roster position, and exact bare-id references in every `allowed_agents` list (never qualified addresses); before the record it removes allow-list entries that already name the unused new id (Constraints). Its caller, Runtime (`runtime.md`), moves the other domains' references and then calls `finish_rename`, or `revert_rename` and `finish_rename` with the reversed record on failure; `recover_rename` is the startup half. Archive and restore are context managers around the archive service's Session commit (`archive.md`): `archive_files(agent_id, tree)` moves `agents/<id>/` into the payload `tree` and yields `ArchivedAgent` (the config with defaults, roster index, stored Workspace and whether it lies outside the Agent's directory); `restore_files(source, target_id, workspace=, root_project_id=)` moves the payload to `agents/<target_id>/`, then rewrites its `agent.json` to the target id, Workspace and default Project (`root_project_id`; unknown fields stay) and seeds missing Workspace files; a failing body moves either tree back, and a failed restore first writes the archived `agent.json` bytes back, so the payload stays unchanged. `inspect_archived` reads a payload without changing it (`payload_missing`, `payload_invalid`, `older_format`, `newer_format`), `restore_target_problem` names `invalid_target_id` or `agent_id_taken` (also an id an unfinished rename holds), and `remove_delegation_grants`, `restore_delegation_grants` and `place_in_roster` are the best-effort cross-Agent steps around them.
- `rename`, `revert_rename`, `recover_rename`, `archive_files` and `restore_files` change `sessions.db` and the Agent tree as one unit (the archive service commits the Sessions inside the last two), and `create` writes the Agent tree with its `agent.json` (no Session), so each enters the injected snapshot barrier before its document change and the store lock (`database.md` -> Snapshot consistency).
- `exists` is the validity-aware, never-raising probe behind identity-only gates such as private-skill layering and the skill RPC write scope. `find` is the same probe returning the stored Agent (raw persisted values, no `defaults.agent` baking, no Workspace seeding or current-Session repair) or `None`; Skill scoping reads `excluded_skills` through it. `reset_current_after_session_removed` re-homes the current pointer bypassing read-time normalization (otherwise `get` would clear the dangling pointer before landing logic runs).
- `lifecycle_guard` lets another domain hold the store's existing mutation lock across private-home lookup, writes and invalidation; like a mutation it admits an Agent document change first, so guarded work waits for a running data snapshot before it takes the lock. Runtime injects it into the registered Skill authoring Tool to protect shared-owner trees from concurrent rename/archive. Guarded work runs in a worker and must not call back into the Event Loop; Agent deletion also offloads its roster read, and the archive service its archive (`tests/core/runtime/test_runtime_skill_lifecycle.py`).
- `update_with_metadata` owns transactional Workspace relocation with copied/backed-up metadata; `agents_rooted_in`/`restore_update` support Project removal compensation.

A retired Tool name left in `tool_access` is an ordinary unknown Tool name (`tools.md`).

## Constraints & Gotchas

- Archive and restore move the Agent tree through `move_tree` (`core/utils/tree_move.py`), which is all or nothing: a refused or failed move leaves its source exactly as it was and creates no destination, so compensation only moves trees back and never deletes payload content (that may be the last complete copy of the Agent's data). A custom Workspace outside the Agent's directory stays where it is: the entry records it, a restore re-attaches it, and nothing deletes it. A rename between volumes copies first (a link inside the tree, Windows junctions included, is recreated as a link to the same target, as a rename would keep it), sets the original aside by renaming it and only then deletes it; a failed deletion leaves a hidden `.<name>.moved-*` leftover next to the source and a log warning, not a failed move. Every archive gets its own payload; none replaces another. A failed archival or restore reaches the caller as `AgentError`; if compensation also fails, the message names where the Agent's files remain. Seeding never overwrites existing workspace files (`test_agents_archive.py`, `test_tree_move.py`).
- `agent.delete` refuses the last Agent; the archive service refuses one with active/queued Runs (`agent_busy`) or one referenced by Channels or by a live automation (`agent_in_use`, listed by `Runtime.agent_references`): a non-terminal identity Cron or Bootstrap job or a Calendar action that can still fire, as `AutomationReferences.agent_references` reports (`automation.md`); the handler holds the reference lock and the service the admission guard across the check and the archive. `AgentStore.archive_files` owns only the file move and its compensation, not those product-level guards. Delegation allow-lists never block deletion: once the archive is committed, `remove_delegation_grants` records each grant (holder and position) in the entry before it writes, then removes the bare id from every other valid Agent's `tools.subagent.allowed_agents` (qualified `agent@project` entries and invalid configs stay), so a later Agent with the same id does not inherit the grant; a list left empty means self-only, so no grant widens. A restore re-adds the restored id at the recorded positions of holders that still exist (`grant_target_missing` warns about the others). After the irreversible archive this is best effort: a config it cannot read or write keeps its entry and logs WARNING, and that entry names no Agent and does not block a rename (next bullet). `agent.delete` reads `remaining_agents` after the archive, so they show the cleaned lists, and the archive's INFO line counts the changed `policies` (`test_agents_archive.py`, `tests/core/archive/test_archive_service.py`, `tests/server/rpc/test_agent_methods_lifecycle.py`).
- Rename holds reference lock plus admission guards for both ids, refuses open Sub-Agent relations/collisions/invalid ids and a new id that still owns live Sessions, moves live references (Channels, non-terminal identity Cron and Bootstrap jobs, Calendar actions, delegation entries, functional parent links), and keeps terminal history/logs historical. The whole rename, retargeting and revert included, holds the snapshot barrier, so an online data snapshot never sees the Sessions renamed but the Channels or Cron jobs not (`core/runtime/_agent_rename.py`).
- Rename refuses a new id that a reference of another owner still names - a Channel, non-terminal identity Cron or Bootstrap job, or Calendar action (also one that can no longer fire, since `retarget_identity` moves every action of the id; `identity_agent_references` in `core/runtime/_agent_rename.py`) - with `AgentReferencedError` (RPC `agent_in_use`) naming each one, before anything changes. Such references are usually leftovers of a deleted Agent: the renamed Agent would silently adopt them, and a revert, which moves everything naming the new id back, would take them along. They block rather than only warn because the user can change or remove each one. A delegation allow-list entry naming the new id does not block: once the existence checks pass, the id names no Agent, so the entry grants nothing - a leftover from before deletion cleaned allow-lists or of a failed cleanup, or a grant saved before any Agent had the id (saves do not check allow-list targets). After the refusal checks and before the rename record, outside every rename direction, `AgentStore.rename` removes such entries, so the renamed Agent does not inherit them, a revert cannot move them to the old id, and an interruption leaves only fewer of them; `policy_agent_ids` (RPC `agent_policies_updated`) include those Agents. No startup sweep removes allow-list entries that name no Agent, because such an entry may be a deliberate grant for an Agent still to be created; `create` inherits it. Derived references instead follow what they point at, so a revert leaves pre-existing ones alone: a Sub-Agent parent link moves only when its parent Session moved (`sessions.md`), a Calendar execution row only with its Session or, without one, its action (`calendar.md`) (`test_agents_rename.py`, `tests/core/runtime/test_runtime_agent_rename.py`). Fork provenance (`fork_source`) is derived from the parent Session's current row, so it follows the retargeted Sessions to the new id (`sessions.md`). Runtime logs one INFO summary per rename with counts per kind (Sessions, Channels, Cron and Bootstrap jobs, Calendar actions, policies, session links) and one INFO line when a start completes or rolls back a pending rename; the per-reference retarget steps log at DEBUG, an incomplete rollback or recovery at ERROR (`logging.md`).
- Rename crash safety: `agents/rename-pending.json` (Generation 1 document: `source_id`, `target_id`, `staging_name`, `rollback`) is written atomically before the first change and removed only after every reference moved. Every step selects only what still names `source_id` or converges on its target state, so repeating a direction finishes it and swapping the ids (`rollback: true`) reverts it. A failure reverts the whole rename in-process; a process that dies leaves the record, and the next start applies it again before the first roster read and `ensure_bootstrap` (`AgentStore.recover_rename`), then Runtime moves the references before Channels, Cron and Calendar start (`runtime.md`). A direction that cannot complete flips to rollback; a record that fails both ways, or cannot be read, stays and logs ERROR on each start. While a record exists, `rename` refuses (`An earlier Agent rename is still pending; restart vBot to finish it`) and `create`/`ensure_bootstrap` never claim either id, so recovery cannot merge a new Agent's Sessions (`test_agents_rename.py`, `tests/core/runtime/test_runtime_agent_rename.py`).
- Roster order is the selection fallback for accessors without valid saved selection - it never changes current selections, Sessions, default Projects, or Run configuration; Config Agents come from Team scan order and are not in this document.
