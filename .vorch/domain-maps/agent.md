# Agents

Persisted agent configuration and workspace lifecycle management.

## Overview

`core/agents/` owns `agent.json` CRUD, the canonical Identity Agent roster order, and Identity Agent tree rename under `<data_dir>/agents/`. Creating an agent also creates its sessions directory and seeds a workspace from bundled templates. Renaming moves the complete Agent-owned tree; deleting archives its active agent directory and workspace instead of permanently deleting them. The agent directory may also hold a **per-agent private skills home** at `<data_dir>/agents/<agent-id>/skills/` — created on first write by the agent's `skill_manage` tool (or the `agent:<id>` skill RPCs), private and always-allowed for that agent (see `skills.md`). Because it lives inside the agent directory it moves or archives **with the agent** for free; it is not seeded at creation, so an agent that never authored a skill has no `skills/` subdir.

## Data Model

`<data_dir>/agents/order.json` is collection metadata with a positive `revision` and a complete ordered `agent_ids` list. A missing file preserves the historical id-sorted roster and is materialized on the first non-empty list; valid Agents absent from a stored order append at the end, while stale ids are filtered and reconciled. A malformed file is reported by `doctor config` but never hides valid Agents: list falls back to id order, and an explicit valid reorder can replace the broken auxiliary document.

`id` is the only load-required `agent.json` field. Every other Agent field is optional and receives its domain default when missing or null; malformed values that are present still invalidate that one Agent. `Agent` fields include the independent `workspace` identity home and nullable `root_project_id` stable Project reference alongside run configuration, Session pointer, permissions, and timestamps. Missing or null `root_project_id` means `No project`; loading never infers it from Workspace.

- `id` is the filesystem directory name and changes only through the explicit coordinated Identity Agent rename operation; ordinary `update` keeps it immutable.
- `model` is user-facing `<provider>/<model-id>` and may optionally carry a pinned local connection suffix as `<provider>/<model-id>::<connection-local-id>[:<account-id>]`. The persisted value may be empty; when empty it resolves to `defaults.agent.model` at read time if configured, without rewriting disk. If no default is configured, the effective value stays empty.
- `fallback_model` is an optional secondary `<provider>/<model-id>` with the same optional `::<connection-local-id>[:<account-id>]` suffix support. It is used when a retryable provider error escapes the primary adapter's built-in retries during a Run. Once activated, it stays active only for the rest of that Run; the next turn starts from `model` again.
- Persisted `model` and `fallback_model` may be empty, and persisted `temperature` and `thinking_effort` may be `null`, to mean "no explicit per-agent override". `AgentStore` applies `settings.json` `defaults.agent` values for those four fields at read time for `get()`, `list()`, and returned create/update results; raw disk state remains unresolved.
- `memory_prompt_mode` controls prompt-visible pinned memory for the Agent: `off` includes no pinned memory, `agent` includes only `MEMORY.md`, and `agent_user` includes both `MEMORY.md` and `USER.md`. The default is `agent_user`.
- `workspace` defaults to `<data_dir>/agents/<id>/workspace/` and remains freely editable and independent of Project. `Agent.workspace`, `AgentStore.default_workspace()`, RPC payloads, and UI values are always resolved absolute paths; `agent.json` stores any Workspace whose resolved location is inside the active data directory as a forward-slash relative path anchored to that data directory, while an external Workspace stays absolute. This persistence/runtime split makes the complete data directory portable without changing callers or rebasing external repositories. Every changed Workspace is an explicit relocation choice: declining copy repoints and applies normal missing-SOUL seeding; accepting copy preserves the sources, copies only `SOUL.md`, `USER.md`, and `MEMORY.md`, backs up replaced destination versions under the Agent's data home, and rolls destination changes back if persistence fails.
- `root_project_id` stores the stable registered Project id selected in the Agent editor. Selection or manual clearing never changes Workspace, Sessions, private Skills, prompt customizations, or permissions; in particular, a rooted Identity Agent remains an Identity Agent whose `tools.subagent.allowed_agents` policy can still address targets outside that Project. Existing configs without the field load unrooted.
- `current_session_id` stores the agent's active Session. Every new Agent gets an initial empty Session immediately; configs without this field, with an empty value, or whose referenced Session no longer exists are normalized to a valid Session when loaded. That normalization creates a new Session and rewrites `agent.json` during the read. A cross-agent `/agent` move re-homes this pointer through `reset_current_after_move` (below) — landing on the last-active *remaining* Session rather than the read-time fresh-empty fallback.
- `allowed_tools` and `allowed_skills` default to `['*']`. Tool-owned Agent settings live in the optional root `tools.<tool>` object in `agent.json`; `tools.subagent.allowed_agents` contains only additional targets, where a missing block or missing field defaults to `['*']`, `[]` means self-only, and an explicit list permits only its bare Identity-Agent ids or qualified `agent@project` ids. `tools.bash.allowed_env` is the ordered, deduplicated list of permanent environment credential names the Agent may request through Bash's per-call `env_keys`; its values never enter Agent configuration or model-facing Tool arguments. Whenever the `subagent` Tool is active, omitting `agent_id` delegates to a separate Session of the calling Agent regardless of this list. Disabling either owning Tool through `allowed_tools` makes its settings inactive but does not delete them, so re-enabling restores the prior policy. `allowed_tools` stores only independently configurable Tools; `memory` is runtime-derived from `memory_prompt_mode` and is stripped from persisted allowlists on create/update. Session-scoped Tools such as `history` are also absent from Agent configuration: a checkpoint-derived Session grant can make one available independently of this allowlist.
- `custom_system_prompt_enabled` is an optional persisted boolean. Missing or `false` means the Agent uses the default prompt scope; `true` means chat and preview may read `<data_dir>/agents/<agent-id>/prompts/` for editable system-prompt fragments. Disabling the toggle ignores Agent prompt files without deleting them.

## Interfaces

- `core/agents/__init__.py` exports `Agent` and store/error types. System Prompt assembly lives in `core/prompts/`.
- `AgentStore(data_dir, template_dir=None, defaults_provider=None)` — CRUD store rooted at a data directory, with optional read-time agent-default injection.
- `create(agent_id, name=None, **fields) -> Agent` — requires only the initial id; a missing, null, or blank display name defaults to that id. It persists `agent.json`, creates `sessions/`, creates the first Session, sets `current_session_id`, and seeds workspace files. Returned value is the effective resolved Agent; persisted raw unset run fields stay unset on disk.
- `get(agent_id) -> Agent` — returns the effective Agent with `defaults.agent` applied.
- `get_raw(agent_id) -> Agent` — returns the **un-baked** Agent (same load path as `get`, but no `defaults.agent` injection): raw `model`/`fallback_model` stay `""` and raw `temperature`/`thinking_effort` stay `None` when unset. The provenance seam the resolver's identity `effective_config` reads; every other consumer keeps `get`/`list`/`update` baking.
- `list() -> list[Agent]` — returns effective valid Agents with `defaults.agent` applied in canonical roster order; an unreadable or invalid individual `agent.json` is logged and skipped without hiding other Agents or failing application startup. `get()` remains strict for an explicitly addressed invalid Agent.
- `list_with_order() -> AgentListResult` returns that same ordered roster plus `order_revision`; `reorder(agent_ids, expected_revision=...)` atomically replaces the full order only when the revision and exact current valid-Agent set match. A stale revision or changed roster raises `AgentOrderConflictError`, so another Accessor cannot silently overwrite a newer order.
- `ensure_bootstrap() -> Agent | None` — creates a bootstrap Agent only when no valid Agent can be listed. Invalid Agent directories are preserved for diagnosis; if one occupies `main`, the first free `main-N` id is used instead of overwriting it.
- `core.agents` exports `validate_agent_data`, `validate_agent_file`, and `load_validated_agent_json`; Agent reads pass `agent.json` through this domain-owned schema before constructing `Agent` objects. Strict single-Agent reads map malformed JSON or schema errors to `AgentError` with file/path diagnostics, while collection loading isolates them as described above. The load path validates **once**: `_agent_from_dict` trusts the validated mapping and only normalizes shapes (workspace fallback, Tool-list sanitization, optional-field defaults). The root `tools` object is optional; its Tool blocks must be objects, and `tools.subagent.allowed_agents` is validated only when present.
- The full `agent.json` field schema lives in `core/agents/agents.py`. Shared scalar rules remain canonical in Settings: the agent-id format is `is_valid_agent_id` / `AGENT_ID_PATTERN`, and value rules are `validate_temperature` / `validate_thinking_effort` plus `ALLOWED_THINKING_EFFORTS`, `MIN_TEMPERATURE`, and `MAX_TEMPERATURE`. Agent schema diagnostics, `AgentStore` create/update, and the server's `agent.*` RPC validation delegate to those value rules instead of copying them.
- `update(agent_id, **changes) -> Agent` remains the ordinary facade. `update_with_metadata(..., copy_workspace_identity_files=...) -> AgentUpdateResult` owns transactional Workspace relocation and returns non-persisted copied/backed-up-file metadata; `agents_rooted_in(project_id)` and `restore_update(...)` support coordinated Project removal and compensation.
- `rename(agent_id, new_agent_id) -> AgentRenameResult` atomically moves the complete Agent tree, rewrites `agent.json.id`, and rebases any Workspace inside that tree while preserving an external Workspace path. `restore_rename(...)` is the compensation seam. Case-only Windows renames use a temporary sibling path. `retarget_allowed_agent_references(old, new)` updates exact bare ids in every `tools.subagent.allowed_agents` list, never qualified Config Agent addresses, and returns exact config snapshots for rollback.
- `delete(agent_id) -> Path` — moves active data under `<data_dir>/archive/agents/<agent-id>/` (the agents archive subtree, sibling to `archive/sessions/` and `archive/projects/` — a flat `archive/<agent-id>` would let an agent named `sessions`/`projects` collide with those roots, and delete's replace-archive rmtree would wipe them).
- `exists(agent_id) -> bool` — validity-aware identity-store probe that never raises; invalid ids, missing files, malformed configs, and a persisted id that disagrees with its directory all yield `False`. It is the guard behind identity-only gates such as the runtime's private-skill layering and the skill RPC's `agent:<id>` write scope.
- `reset_current_after_session_removed(agent_id, removed_session_id) -> Agent` — re-homes an identity agent's current pointer after a Session left this home, by a `/agent` move **or** a delete. If `current_session_id == removed_session_id`, it points at the most recently active *remaining* Session (max `last_active_at` from `ChatSessionManager.list_with_metadata`), or a fresh empty Session when none remain; otherwise it leaves the pointer untouched. Reads the stored config **without** the read-time `_ensure_current_session` normalization — `get` would replace the just-removed dangling pointer with a fresh empty Session before this method could choose the last-active landing. Identity-only; project config agents carry no server-side current pointer (on a move, the target identity agent's pointer is set to the moved Session by the move orchestrator via `update`; on a delete, `session.delete` calls this for the source).

## Uniform Agent Resolution

Run paths no longer call `runtime.agents.get(...)` directly. They go through one seam, `AgentResolver.resolve_agent(project_id, agent_id) -> RuntimeAgent` (owned by `core/projects/`; see `projects/resolution.md`), so identity and Project Agents load through the same call. The fork is at exactly one place:

- `project_id is None` → the identity `AgentStore` (this domain), with the same persisted identity, defaults injection, Workspace behavior, and root `tools` settings as before. Target existence and authorization remain execution-time concerns rather than mutating or live-filtering the stored policy during resolution.
- `project_id` set → a **config agent** synthesized from that Project's Team scan (no `agent.json`, no Workspace, `memory_prompt_mode="off"`). Its capabilities are resolver-computed: `allowed_tools` = Project Tool Whitelist minus scanned denials, `allowed_skills` combines discovered Project Skills with enabled bundled/global Skills and then subtracts disabled Project Skill names and `"*"`, and `tools.subagent.allowed_agents` contains the other current Team members admitted by the repository Agent's ordered target rules when a Sub-Agent Tool is available (see `projects/resolution.md` → Effective Capabilities). The config Agent itself stays implicit and is never materialized in that list.

`RuntimeAgent` is a `Protocol` that the store `Agent` already satisfies, so consumers read the same attribute surface (`id`, `model`, `fallback_model`, `workspace`, `temperature`, `thinking_effort`, `allowed_tools`, `allowed_skills`, `tools`, `memory_prompt_mode`, …) regardless of source; a config agent is a `ConfigAgent` carrying that surface plus its verbatim prompt `body`.

**Two freshness levels:** team membership (which agents exist) comes from the **scan**, cached per project and refreshed at open / explicit re-scan — not per turn. A single agent's **config** (model/body) is read **fresh from the repo file on every resolve**, mirroring how identity agents re-read `agent.json` each turn.

**Model chain.** Identity agents keep model→global→empty (the store). Config agents resolve **override→**model→project-default→global→**error**: the agent's model **override** (`project.overrides[agent_id]["model"]` — vBot-owned, data-dir only) is the top tier and wins over the repo-declared model, then the repo value, Project default, and global default. A model counts only if it is *configured in this instance* (Provider registered, Model in catalog, and a usable credential on a Connection the Model's per-Model `connections` allowlist permits; a pinned `::connection[:account]` suffix is checked verbatim — matching what run-time Connection resolution enforces); an unconfigured candidate (including an override whose credential later vanished) falls through the chain. A declared repository model that is unconfigured is surfaced as a `BAD_MODEL` scan-report finding at scan time, not at first Run. If the chain falls all the way through, resolution raises `AgentResolutionError`. Run paths map that to a clean failure (Chat → domain error at the RPC edge via `error_mapping.py`; `subagent` → `agent_not_found` Tool failure; `status` → `agent_not_found`). The model override is set/cleared persistently through `/model`; Project management can set/clear every supported override through `project.set_override`/`project.clear_override` (see `projects/configuration.md`).

**Provenance seam (`effective_config`).** Alongside `resolve_agent`, the resolver exposes `AgentResolver.effective_config(project_id, agent_id)` reporting per Run field `{value, source}` (the winning tier), sharing the same chain logic. Its identity branch reads the Agent's **un-baked** values through `AgentStore.get_raw(agent_id)` — the same load path as `get` (Workspace seeding, current-Session normalization) but **without** the `defaults.agent` injection, so raw `model`/`fallback_model` stay `""` and raw `temperature`/`thinking_effort` stay `None` when unset. `get`/`list`/`update` keep baking for every other consumer; `get_raw` exists only so the provenance seam can tell an own persisted value from an inherited global default. See `projects/resolution.md` → Model & Scalar Resolution for the Project branch and its current provenance scope.

**Temperature & thinking chain.** For **config agents**, `temperature` and `thinking_effort` resolve through override → Agent value → Project default (`project.default_temperature` / `project.default_thinking_effort`) → global `defaults.agent` → Provider default. The first non-`None` tier wins; falling through every tier yields `None`, so the field is dropped at the wire and the Provider default applies. For thinking effort, `""` is a real value meaning "Provider default" that **stops** the chain (a Project `default_thinking_effort=""` blocks the global default), while `null`/absent falls through; for temperature, `0.0` is a real value (the floor) that stops the chain. The global tier is the live `defaults.agent` map (read once per resolve). **Identity agents are unchanged**: they keep the existing two-tier `defaults.agent` injection (Agent value → global) applied by `AgentStore` at read time — Project tiers are config-Agent-only.

## Conventions

- Agent IDs must be conservative filesystem-safe slugs: start with a letter or number, then use only letters, numbers, hyphen, or underscore, max 64 characters.
- Writes to `agent.json` use a same-directory temp file plus atomic replace.
- Relative persisted Workspace values resolve only against the active data directory, never the process cwd. Every AgentStore write serializes an internal resolved Workspace back to its relative form; absolute external Workspaces remain absolute.
- The only workspace template is `SOUL.md` in `resources/workspace-templates/`, seeded with a generic vBot-agent identity/persona starter — the one file the workspace layer seeds. `USER.md` and `MEMORY.md` are **not** workspace templates and are **not** seeded here: they belong to the memory system and are created lazily on the first `memory` tool write (see `memory.md`). So a memory-off agent has neither, and deleting them does not resurrect them.
- Prompt bodies are file-backed and assembled through `core/prompts/`, not hardcoded in Agent code.

## Constraints & Gotchas

- Agent deletion currently replaces an existing archive for the same ID.
- Creating an Identity Agent appends it to the canonical roster, rename preserves its position, and delete removes it. The ordered first Agent is the selection fallback only when an Accessor has no still-valid saved selection; ordering does not change current selections, Sessions, Rooting, or Run configuration. Project Config Agents come from Project Team scan order and are not part of this document.
- Workspace seeding does not overwrite existing workspace files.
- The server rejects deleting the last remaining Agent, an Agent with active or queued Runs (`agent_busy`), or an Agent referenced by Channels or Cron jobs (`agent_in_use`). Identity-Agent deletion holds both the server Agent-reference `asyncio.Lock` and `ChatRunManager.agent_admission_guard(project_id=None)` across reference validation and archive, so a concurrently waiting Run cannot enter after the idle check; same-named Project Team Agents remain outside that guard. Core `AgentStore.delete()` remains a filesystem archive operation and does not enforce product-level guards itself. Server RPC context lives in `server.md`.
- Identity Agent rename holds the shared Agent-reference lock plus Run Admission Guards for both old and new ids, refuses open Sub-Agent relations, collisions, and invalid ids, then coordinates live server-owned references. Channels, non-terminal unqualified Cron jobs, bare Identity Agent delegation entries, and functional `subagent_parent` links move to the new id; terminal Cron history, fork/transcript provenance, logs, and qualified Config Agent addresses remain historical or independent. A failed reference update compensates every completed server-owned change before returning an error.
- Agent mutable fields are validated server/core-side. `thinking_effort` is one of `null`, `""`, `none`, `minimal`, `low`, `medium`, `high`, `xhigh`, or `max`; `temperature` may be `null` or a finite number from `0.0` through `2.0`. `null` means "inherit defaults.agent" while `""` for `thinking_effort` means "provider default". `allowed_tools` and `allowed_skills` must be lists of strings; `tools` must be an object whose Tool values are objects, optional `tools.subagent.allowed_agents` must be a list of strings, and optional `tools.bash.allowed_env` must contain shell-portable environment names matching `[A-Za-z_][A-Za-z0-9_]*`. When present, `memory_prompt_mode` must be one of `off`, `agent`, or `agent_user`; it also drives the effective `memory` Tool: `off` disables the Tool, while the other modes enable it even when `allowed_tools` is otherwise empty. Neither `memory` nor Session-scoped Tools are configured independently through `allowed_tools`. `custom_system_prompt_enabled` must be a boolean; when omitted, the custom prompt toggle defaults to `false`.
- Enabling `custom_system_prompt_enabled` through public Agent RPC seeds the Agent prompt directory from the current effective default prompt fragments. Re-enabling preserves existing Agent prompt files.
- Automatic fallback is run-local only. It does not mutate persisted `model` or `fallback_model`.
- The optional `::<connection-local-id>[:<account-id>]` suffix stores the provider-local connection slug, optionally with a pinned credential account. Runtime reconstructs the full connection ID as `<provider>:<connection-local-id>[:<account-id>]` from the model prefix; Account semantics live in `providers/connections.md` → Identity and Accounts.
