# Development Tooling

The tooling that checks, tests, pushes and builds vBot itself: the commit hook, the push check, CI, the local test core pool, the supported Python version and the dependency locks.

## Overview

`scripts/commit_check.py` (run by `.githooks/`), `scripts/push.py`, `.github/workflows/` (`ci.yml`, `main-build.yml`, `release.yml`) and `tests/cpu_pool.py` decide what a commit, a push and a release must pass. Everyday use (commands, what to do when the hook blocks) lives in `.vorch/PROJECT.md` -> Development and Testing, how to write tests in `development/testing.md`; the push and release procedures live in `.vorch/workflows/push-workflow.md` and `release-workflow.md`. This map holds what an agent needs before changing that tooling, the Python version or the dependency locks. Other workflows have other owners: the package builds `windows-package.yml` and `linux-package.yml` and their smokes `cli/application.md` -> Installers and published packages and the post-publication canary `release-smoke.yml` `.vorch/workflows/release-workflow.md`.

Provider probe CLIs and their disposable Eval workers use Runtime-owned startup policies; source-only verification and production-catalog Eval isolation are distinct (`runtime.md` -> Bootstrap).

## Developer harness ownership

Worktree creation and listing stay in `scripts/worktree.py`; merge landing, rollback and repair belong to `_worktree_merge.py`, and service shutdown, data ownership and checkout cleanup to `_worktree_removal.py`. Both use an explicit `WorktreeContext` (`_worktree_context.py`) for repository and executing-checkout identity, subprocesses and port locking; helpers never import entrypoint globals. The push check uses the same private-checkout cleanup owner. Safety and recovery protocols remain documented in `scripts/README-worktree.md`.

Load-scenario defaults, validation and result serialization belong to `scripts/perf_load_suite/config.py`; `runner.py` owns orchestration. Tool lab replay keeps recorded-history decoding in `_replay_evidence.py`, Session path identity and rewriting in `_replay_paths.py`, and forward simulation in `_replay_history.py`.

The exact reasoning replay probe binds Adapter, Model, effort and sampling in `_reasoning_probe_wire.ReplayTarget`, which owns payload rendering and sending with common request settings. Scenario histories and replay-policy experiments stay in `probe_reasoning_replay_exact.py`; the Responses roundtrip keeps its fixed high effort and omitted temperature.

## Python version

vBot supports exactly one CPython minor version, the one its packages bundle (currently 3.14, `scripts/package_build.PYTHON_VERSION`). Development checkouts, mypy and every CI job use it too; there is no compatibility floor and no matrix across versions. Changing it is one deliberate commit that moves every pin together: `requires-python` and mypy's `python_version` in `pyproject.toml`, `PYTHON_VERSION` (the Windows builder's runtime check and the Linux runtime layout), the python-build-standalone runtime in `scripts/linux/python.lock.json`, all five runtime dependency locks (regenerated with `--python-version` and checked to resolve with `--only-binary :all:`), every workflow's and `.github/actions/*`'s `python-version`, and the setup documentation. `tests/scripts/test_package_build.py` fails while one of them disagrees.

The managed local engine environments (STT, TTS, embeddings: `model_tasks/speech.md`, `model_tasks/embeddings.md`) follow it without a pin of their own: each runs on the server's `major.minor` unless its `[tool.vbot.*]` recipe in `pyproject.toml` names `python`, and setup recreates an environment whose Python differs (`python_changed`). Only Chatterbox's recipe names one, 3.13, because its dependency `spacy-pkuseg` publishes no wheels for newer Pythons (the recipe's comment says when to drop it).

Two kinds of vBot files therefore run on other interpreters: `core/model_tasks/speech_worker.py`, which every speech environment runs, Chatterbox's on 3.13 (it imports only the standard library at startup, and vBot's source only for managed STT, which runs on the server's Python), and the bundled Skill scripts (`resources/skills/*/scripts/**/*.py`, including packages such as the pdf Skill's `pdf_tools`), which run on whatever `python` the host's `PATH` provides. Ruff's global `target-version` is `py314`; `[tool.ruff.per-file-target-version]` pins the speech worker to `py313` and the Skill scripts to `py39`, the oldest version each supports, so neither lint nor formatter introduces newer syntax there. Ruff sees only syntax: the commit hook and CI also run mypy `--python-version 3.13` over the speech worker (`scripts/commit_check.OLDER_PYTHON_FILES` and `OLDER_PYTHON_VERSION`), which rejects standard-library names added after 3.13. `tests/scripts/test_commit_check.py` fails while these pins differ from the oldest Python a speech environment runs; once every speech environment runs on the server's Python, drop the pins and the extra mypy check. Nothing checks the Skill scripts' standard-library use; keep it to what 3.9 offers.

A Python version change also checks that `sqlite3`'s `autocommit` default is still `LEGACY_TRANSACTION_CONTROL`: the database kernel relies on legacy `isolation_level=None` and issues its own `BEGIN IMMEDIATE`; `autocommit=True` is the forward spelling, but there `commit()` no longer ends an explicit `BEGIN` (`database.md` -> Conventions -> Transaction control).

## Interpreter and SQLite

The development interpreter must run the SQLite the packages bundle, because its SQLite decides the journal mode of every database (`database.md`), so tests and measurements see what installations run. On Windows install the pinned library into it once from an elevated terminal (`python -m cli.application.runtime_sqlite`); on Linux use a Python whose SQLite runs WAL, such as the packages' runtime of `scripts/linux/python.lock.json`. `cli.application.runtime_sqlite.interpreter_problem` names a mismatch, and `scripts/push.py` (its `sqlite` step), `perf_bench.py` and `perf_load.py` refuse to run on one. Worktree creation, the push check, CI and packaging run `cli.search_runtime` (`tools/search_files.md` -> Provisioning).

## Dependencies

A change to the base dependencies or the `server`, `cli`, `application`, `desktop`, or `dev` extras runs `python scripts/test_dependencies.py refresh` with the declared uv version. This preserves existing package pins where possible, regenerates all five hashed runtime locks and the three hashed test-only overlays, and records their dependency-input fingerprints. `check` refuses stale pyproject inputs, stale runtime constraints and conflicting shared pins. Windows/Linux build details: `scripts/windows/requirements.md`, `scripts/linux/README.md`. The `desktop` Voice stack: `desktop/voice.md` -> Dependencies; optional local speech setup: `model_tasks/speech.md`; the local embedding engine's managed environment recipe (`[tool.vbot.local-embeddings.onnx]`, never a base or extra dependency): `model_tasks/embeddings.md` -> Local Engine.

CI and the push check install the complete platform server runtime lock plus its test overlay into a separate virtual environment; they never resolve a fresh `.[dev]` dependency set or mutate the developer interpreter. Windows test packages shared with either Desktop shape use those shapes' pins as constraints too; this does not add Desktop-specific test coverage. The editable build uses locked Hatchling and its explicit `editables` requirement without build isolation. Native push environments live in the private checkout; WSL keys its cached environment by both locks, the helper and the base interpreter.

`sniffio` stays a direct dependency although vBot never imports it: httpcore probes it on every connection and stream, and each failed probe costs an import and `sys.path` scan (~0.4 ms of GIL time).

## Commit hook

What `scripts/commit_check.py` checks: `.vorch/PROJECT.md` -> Commit hook. It re-stages its fixes only for completely staged files and checks partially staged files as they are in the working tree. A mypy error blocks when it is in a staged file or in a file without uncommitted changes; one in unstaged or untracked work is reported without blocking. Beyond that: mypy runs over the configured project plus staged Python files outside it, once per platform (`--platform`, concurrently, each with its own cache); mypy `--python-version 3.13` covers the speech worker (`OLDER_PYTHON_FILES`) when it or `pyproject.toml` is staged, as CI's static job does on every run (Python version above); `npm run lint` and `format:check` run over every source when the WebUI packages or the lint or format configuration change. `scripts/_webui_packages.py` compares `webui/node_modules` with `package-lock.json`, and a staged `package.json` that the lock does not record blocks until `npm install` in `webui/` updates the lock. Staged domain maps, `.vorch/PROJECT.md` and `.vorch/GLOSSARY.md` go through `scripts/domain_maps.py`: in maps, non-ASCII characters outside code spans and References entries that name no file block; a root map above `ROOT_BUDGET` (16,000 characters), PROJECT.md above `PROJECT_BUDGET` (30,000) or the glossary above `GLOSSARY_BUDGET` (12,000) that the commit makes larger is reported without blocking. Run without arguments, the script prints the corpus report the domain-map audit starts from (`.vorch/workflows/domain-map-audit-workflow.md`).

- A mypy note goes with the error it follows; a note alone never blocks.
- Authorship: `scripts/commit_authorship.py` enforces the authorship rule of `AGENTS.md` -> Git from four hooks: `pre-commit` and `pre-merge-commit` refuse an AI tool author or committer (`identity`), `commit-msg` strips `Co-Authored-By`, `Claude-Session` and "Generated with" lines (`message`), `pre-push` refuses to push commits that carry either (`push`); CI's `authorship` job checks all of HEAD's history (`history`). The tracked `.claude/settings.json` turns off Claude Code's attribution, pins the git identity through `env`, and enables `core.hooksPath` at session start, so Claude Code sessions in this repository, cloud sessions included, follow it without local setup.
- Attribution stripping matches standalone trailers and footers, preserving prose that mentions them. If stripping would empty a non-empty message, the hook refuses the commit and leaves the original file intact.
- The `dev` extra pins Ruff and mypy exactly so the hook and CI agree; upgrade them deliberately, together with the fixes a new version requires.

## Push check

`python scripts/push.py` checks the commit `main` points to in a private checkout (`.worktrees/.push-*`): Ruff, mypy for both platforms, the complete native pytest suite on every core of the pool, and the WebUI's format check, lint, Vitest and build; on Windows also the complete pytest suite on Linux in WSL (`scripts/linux/push_tests.sh`, cache in WSL's `~/.cache/vbot-push`). It pushes exactly that commit to origin's `main`, as a fast-forward, only when every step passed (`--no-push` checks only). Backend tests that fail run once more alone for diagnosis; the first failure still blocks even when the retry passes. The complete output goes to a log under `.git/vbot-push-logs/`. Procedure: `.vorch/workflows/push-workflow.md`.

The WSL suite runs alongside the WebUI checks with the ordinary local worker budget (`tests/cpu_pool.py`, two workers, capped by the pool size). `push.py` puts extraction, setup and all test processes in one systemd user scope: memory reclamation above 2.5 GiB, a hard 3 GiB limit including file cache, and no swap. An OOM kills the whole scope and fails the step, rather than retrying an incomplete suite. This needs WSL 2 with systemd and a working user manager; there is no unbounded fallback. The limit belongs to this test run, not the whole WSL VM: Linux, existing cache and other workloads add to the Windows Task Manager total. CI keeps its own concurrency.

## CI

`pages.yml` publishes the bundled MCP client metadata unchanged to the project's GitHub Pages site, with only a small index page alongside it (`extensions/mcp.md` -> OAuth sign-in). It runs on `main` when that document or workflow changes, or on manual dispatch; Pages must first be enabled with the GitHub Actions source. Its validation refuses a document whose client identity differs from the deployment URL. The workflow uses only the built-in token with Pages and OIDC permissions, and never publishes the rest of the repository.

`ci.yml` runs the static checks and the complete pytest suite on Linux (x64 and ARM64) and Windows with the one supported Python version (Windows split into shards through `VBOT_TEST_SHARD`) and the WebUI checks. The backend jobs run on the Python the packages bundle (`.github/actions/packaged-python`): on Linux the python-build-standalone runtime of `scripts/linux/python.lock.json`, on Windows the runner's CPython with the SQLite library of `scripts/windows/sqlite.lock.json`. Their SQLite decides the journal mode the databases run in (`database.md`), so the tests run in the mode installations use; the runners' own SQLite is older and would confine them to the rollback journal.

`main-build.yml` calls it on every push to `main` that changes more than development documentation (`.vorch/`, the root guides), alongside the signed main-channel package builds, and publishes them to the `main-build` prerelease only once CI and every package passed; a newer push cancels the CI and package jobs of an older run. It can also be started by hand (`gh workflow run ci.yml`). The CI runs once per commit: `release.yml` does not call it but gates on it, as its `ci` job (`scripts/release_gate.py`) waits until a `main-build` run of the dispatched commit completed with every `ci.yml` job successful, while the release packages build. It fails when that CI failed or was cancelled, or when no run starts within ten minutes (a documentation-only push starts none; dispatch `main-build.yml` then). The gate names `ci.yml`'s jobs in `CI_JOBS`; its test fails when they diverge.

Linux x64 also provisions the Playwright Chromium headless shell for the live PDF creation test, through the `playwright` Python package pinned in the `dev` extra (the PDF Skill's own `setup --install-browser` uses the same package); `PLAYWRIGHT_BROWSERS_PATH` points to an absolute runner-temp directory so the isolated test homes still discover it. Before the backend tests each job provisions what a test would otherwise fetch or warm inside its 30 s budget: the search engine, the token estimation encodings (tiktoken downloads them on first use) and, on Windows, the native host toolchain (a runner's first clang-cl build takes 20-30 s). A red run notifies the maintainer through GitHub; the release workflow checks the latest one on `main` first. An isolated diagnostic retry never clears a failing suite: CI keeps the original failure, reports the retry outcome and blocks publication. Passing in isolation does not establish the cause of the first failure.

## Test core pool

Locally, every pytest run of every checkout claims its workers' cores from one pool per machine (all logical cores but two, at least the physical ones, `tests/cpu_pool.py`) and waits while they are busy, so parallel sessions queue instead of overloading the machine; `-n auto` means 2 workers there, an explicit `-n N` at most the pool's size. Each run appends a line to `~/.cache/vbot-test-cores/runs.jsonl` (checkout, cores, wait, duration, outcome). CI skips the pool and uses all cores.
