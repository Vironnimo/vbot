# Development Tooling

The tooling that checks, tests, pushes and builds vBot itself: the commit hook, the push check, CI, the local test core pool, the supported Python version and the dependency locks.

## Overview

`scripts/commit_check.py` (run by `.githooks/`), `scripts/push.py`, `.github/workflows/` (`ci.yml`, `main-build.yml`, `release.yml`) and `tests/cpu_pool.py` decide what a commit, a push and a release must pass. Everyday use (commands, the test conventions, what to do when the hook blocks) lives in `.vorch/PROJECT.md` -> Development and Testing; the push and release procedures live in `.vorch/workflows/push-workflow.md` and `release-workflow.md`. This map holds what an agent needs before changing that tooling, the Python version or the dependency locks.

## Python version

vBot supports exactly one CPython minor version, the one its packages bundle (currently 3.14, `scripts/package_build.PYTHON_VERSION`). Development checkouts, mypy and every CI job use it too; there is no compatibility floor and no matrix across versions. Changing it is one deliberate commit that moves every pin together: `requires-python` and mypy's `python_version` in `pyproject.toml`, `PYTHON_VERSION` (the Windows builder's runtime check and the Linux runtime layout), the python-build-standalone runtime in `scripts/linux/python.lock.json`, all five runtime dependency locks (regenerated with `--python-version` and checked to resolve with `--only-binary :all:`), every workflow's and `.github/actions/*`'s `python-version`, and the setup documentation. `tests/scripts/test_package_build.py` fails while one of them disagrees.

The managed local engine environments (STT, TTS, embeddings: `model_tasks/speech.md`, `model_tasks/embeddings.md`) follow it without a pin of their own: each runs on the server's `major.minor` unless its `[tool.vbot.*]` recipe in `pyproject.toml` names `python`, and setup recreates an environment whose Python differs (`python_changed`). Only Chatterbox's recipe names one, 3.13, because its dependency `spacy-pkuseg` publishes no wheels for newer Pythons (the recipe's comment says when to drop it).

Two kinds of vBot files therefore run on other interpreters: `core/model_tasks/speech_worker.py`, which every speech environment runs, Chatterbox's on 3.13 (it imports only the standard library at startup, and vBot's source only for managed STT, which runs on the server's Python), and the bundled Skill scripts (`resources/skills/*/scripts/**/*.py`, including packages such as the pdf Skill's `pdf_tools`), which run on whatever `python` the host's `PATH` provides. Ruff's global `target-version` is `py314`; `[tool.ruff.per-file-target-version]` pins the speech worker to `py313` and the Skill scripts to `py39`, the oldest version each supports, so neither lint nor formatter introduces newer syntax there. Ruff sees only syntax: the commit hook and CI also run mypy `--python-version 3.13` over the speech worker (`scripts/commit_check.OLDER_PYTHON_FILES` and `OLDER_PYTHON_VERSION`), which rejects standard-library names added after 3.13. `tests/scripts/test_commit_check.py` fails while these pins differ from the oldest Python a speech environment runs; once every speech environment runs on the server's Python, drop the pins and the extra mypy check. Nothing checks the Skill scripts' standard-library use; keep it to what 3.9 offers.

A Python version change also checks that `sqlite3`'s `autocommit` default is still `LEGACY_TRANSACTION_CONTROL`: the database kernel relies on legacy `isolation_level=None` and issues its own `BEGIN IMMEDIATE`; `autocommit=True` is the forward spelling, but there `commit()` no longer ends an explicit `BEGIN` (`database.md` -> Conventions -> Transaction control).

## Interpreter and SQLite

The development interpreter must run the SQLite the packages bundle (`.vorch/PROJECT.md` -> Development -> Setup). `cli.application.runtime_sqlite.interpreter_problem` names a mismatch, and `scripts/push.py` (its `sqlite` step), `perf_bench.py` and `perf_load.py` refuse to run on one. `cli.search_runtime` provisions the search engine; worktree creation, CI and packaging run it (`tools/search_files.md`).

## Dependencies

A change to the base dependencies or the `server`, `cli`, `application`, or `desktop` extras also regenerates the hashed package runtime locks: Windows (`scripts/windows/requirements.md`) and Linux (`scripts/linux/README.md`). The `desktop` Voice stack: `desktop.md` -> External Dependencies; optional local speech setup: `model_tasks/speech.md`; the local embedding engine's managed environment recipe (`[tool.vbot.local-embeddings.onnx]`, never a base or extra dependency): `model_tasks/embeddings.md` -> Local Engine.

`sniffio` stays a direct dependency although vBot never imports it: httpcore probes it on every connection and stream, and each failed probe costs an import and `sys.path` scan (~0.4 ms of GIL time).

## Commit hook

`.githooks/pre-commit` and `.githooks/pre-merge-commit` run `scripts/commit_check.py` on every commit and merge commit, in every checkout. It runs the static checks on the staged files and no tests: Ruff fix, format and lint; mypy over the configured project plus staged Python files outside it, once for Windows and once for Linux (`--platform`, concurrently, each with its own cache); mypy `--python-version 3.13` over the speech worker (`OLDER_PYTHON_FILES`), when it or `pyproject.toml` is staged, as CI's static job does on every run (Python version above); Prettier and ESLint for WebUI and Extension page `ui/` sources, and `npm run lint` and `format:check` over every source when the WebUI packages or the lint or format configuration change. It re-stages its fixes only for completely staged files and checks partially staged files as they are in the working tree. The WebUI checks block while `webui/node_modules` differs from `package-lock.json` (`scripts/_webui_packages.py` compares them). A staged `package.json` that the lock does not record blocks until `npm install` in `webui/` updates the lock.

- Blocking: a mypy error blocks when it is in a staged file or in a file without uncommitted changes; one in unstaged or untracked work is reported without blocking. A mypy note goes with the error it follows; a note alone never blocks.
- Authorship: `scripts/commit_authorship.py` enforces the authorship rule of `AGENTS.md` -> Git from four hooks: `pre-commit` and `pre-merge-commit` refuse an AI tool author or committer (`identity`), `commit-msg` strips `Co-Authored-By`, `Claude-Session` and "Generated with" lines (`message`), `pre-push` refuses to push commits that carry either (`push`); CI's `authorship` job checks all of HEAD's history (`history`). The tracked `.claude/settings.json` turns off Claude Code's attribution, pins the git identity through `env`, and enables `core.hooksPath` at session start, so Claude Code sessions in this repository, cloud sessions included, follow it without local setup.
- The `dev` extra pins Ruff and mypy exactly so the hook and CI agree; upgrade them deliberately, together with the fixes a new version requires.

## Push check

`python scripts/push.py` checks the commit `main` points to in a private checkout (`.worktrees/.push-*`): Ruff, mypy for both platforms, the complete pytest suite on every core of the pool, and the WebUI's format check, lint, Vitest and build; on Windows also the complete pytest suite on Linux in WSL (`scripts/linux/push_tests.sh`, cache in WSL's `~/.cache/vbot-push`). It pushes exactly that commit to origin's `main`, as a fast-forward, only when every step passed (`--no-push` checks only). Backend tests that fail run once more alone; those that pass then are reported as flaky without blocking. The complete output goes to a log under `.git/vbot-push-logs/`. Procedure: `.vorch/workflows/push-workflow.md`.

## CI

`ci.yml` runs the static checks and the complete pytest suite on Linux (x64 and ARM64) and Windows with the one supported Python version (Windows split into shards through `VBOT_TEST_SHARD`), the WebUI checks and E2E. The backend and E2E jobs run on the Python the packages bundle (`.github/actions/packaged-python`): on Linux the python-build-standalone runtime of `scripts/linux/python.lock.json`, on Windows the runner's CPython with the SQLite library of `scripts/windows/sqlite.lock.json`. Their SQLite decides the journal mode the databases run in (`database.md`), so the tests run in the mode installations use; the runners' own SQLite is older and would confine them to the rollback journal.

`main-build.yml` calls it on every push to `main` that changes more than development documentation (`.vorch/`, the root guides), alongside the signed main-channel package builds, and publishes them to the `main-build` prerelease only once CI and every package passed; a newer push cancels the CI and package jobs of an older run. It is also the release gate (`release.yml`) and can be started by hand (`gh workflow run ci.yml`).

Linux x64 also provisions the Playwright Chromium headless shell from `tests/e2e/package-lock.json` for the live PDF creation test; `PLAYWRIGHT_BROWSERS_PATH` points to an absolute runner-temp directory so the isolated test homes still discover it. Before the backend tests each job provisions what a test would otherwise fetch or warm inside its 30 s budget: the search engine, the token estimation encodings (tiktoken downloads them on first use) and, on Windows, the native host toolchain (a runner's first clang-cl build takes 20-30 s). A red run notifies the maintainer through GitHub; the release workflow checks the latest one on `main` first. Backend tests that fail run once more, alone: tests that then pass failed only under the parallel load and become a `Flaky tests` warning annotation and job-summary entry instead of failing the job; fix them like any failure.

## Test core pool

Locally, every pytest run of every checkout claims its workers' cores from one pool per machine (all logical cores but two, at least the physical ones, `tests/cpu_pool.py`) and waits while they are busy, so parallel sessions queue instead of overloading the machine; `-n auto` means 2 workers there, an explicit `-n N` at most the pool's size. Each run appends a line to `~/.cache/vbot-test-cores/runs.jsonl` (checkout, cores, wait, duration, outcome). CI skips the pool and uses all cores.
