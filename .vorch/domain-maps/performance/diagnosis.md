# Performance diagnosis

How the stall watchdog and the Heap Census capture their data and what that costs, and how to read stalls, Event Loop lag and process-level causes of a slow loop.

## Stall capture

- Work running in a Task of its own (a parallel Tool call, a Channel worker, a background Task) shows only that Task's frames down to the Event Loop's callback dispatch, not the Run or service that started it: the first sample that finds the loop running a Task therefore also reads Python 3.14's asyncio call graph once and keeps the frames of the suspended Tasks awaiting it (`awaited_by`, innermost first, following the first awaiter of each level). On Windows and Linux it also reads every Python thread's CPU time on each sample and samples the stacks of the other threads that ran since the previous one; the stall names the other threads that used at least 10% of the measured CPU window, with their stacks.
- Stack sampling uses `sys._current_frames()`; frames are rendered relative to the vBot root or the Python library root. During a stall the watchdog keeps stacks as raw (file, line, name) tuples and renders them once the stall ends: rendering resolves paths through file system calls, each of which releases the GIL and, while another thread holds it, costs a 5 ms switch interval (15.6 ms on Windows) to get it back. Per-thread CPU reads keep the GIL for the same reason (`PyDLL` calls on Windows, the kernel's per-thread CPU clock on Linux; psutil's thread listing scans the whole system on Windows, about 34 ms).
- Outside stalls the watchdog costs nothing beyond its 50 ms wakeup. With 43 Python threads, a stall sample takes about 0.16 ms of GIL time (0.33 ms for the first, which also samples every thread once), and ending the stall about 0.4 ms (Python 3.14, Windows).
- The call graph costs about 30-50 us of GIL time once per stall (`asyncio.current_task(loop)` about 4 us per sample until a Task is found; Python 3.14, Windows). Walking it from the watchdog thread is not thread-safe: the loop thread may add or drop awaiters meanwhile, so any failure leaves `awaited_by` empty instead of failing the stall (`test_an_unreadable_call_graph_still_records_the_stall_without_awaiters`). The Task the loop runs is fixed at the first sample that finds one; a stall made of several callbacks names only that Task's awaiters. Task names are not recorded: Tasks that libraries start are named outside vBot's naming rules (`logging.md`).
- A stall >= 1 s logs a WARNING with `gc_ms`, `loop_cpu_ms` (as `<cpu>/<window>`), its five innermost frames, its three innermost vBot frames (files in the vBot source tree, bundled Extensions included; when the stack has none, those of `awaited_by`, written `- (awaited by: ...)`) and the busiest other thread with its CPU and innermost vBot frames (or innermost frames), at most once per 30 s (suppressed count reported).

## Reading stalls and lag

- The loop's own CPU in the stall's CPU window tells the cases apart: close to the window means the loop computed itself; near zero means it waited, on I/O, a lock, or the GIL held by a named busy thread. Few samples over a long stall mean the watchdog could not get the GIL either: a long GIL-holding call, most often a cyclic garbage collection, which `gc_ms` then shows.
- Windows timer granularity (about 15.6 ms) gives `event_loop.lag` a baseline of 0-16 ms; judge lag by p99 and stalls, not p50.
- A system suspend or debugger pause can show up as one long stall whose samples do not explain it.
- A worker thread that computes in Python holds the GIL until the Event Loop asks for it, and the loop waits one switch interval before asking, again after every I/O operation. Windows rounds such a wait of 1 ms or more up to its 15.6 ms timer tick: with the default 5 ms, one busy thread cut a loop from about 22,000 to 11 local I/O round trips per second (Python 3.12 and 3.14). The server therefore sets 0.5 ms once ready (`server/process-lifecycle.md` -> `create_app` hooks); the loop then asks at once, and at realistic loop load the computing thread lost no measurable time. Such stalls name the busy thread (`busiest other thread`) while the loop samples sit in I/O calls such as `SSLObject.read`.
- Stalls whose loop samples sit in `IocpProactor._poll` with `loop_cpu_ms` near zero, `gc_ms` 0 and no busy thread, while `process.rss_mb` is far below the process's private bytes, are page faults of a trimmed working set: the loop thread waits for its memory to be paged back in. Check the server's priority class, I/O and memory priority first; a Task Scheduler start at the default task priority lowers all three (`cli/application.md` -> Autostart and server supervision).
- A stall shows only what the loop thread runs. For a wedged loop, or Tasks that wait forever without blocking it (a hung Run, a deadlocked queue), Python 3.14's `python -m asyncio ps <pid>` lists every Task of the server process with its name and awaiter chain, and `python -m asyncio pstree <pid>` prints them as an await tree. Both read the target process's memory without its Event Loop's cooperation, so they work against a wedged loop; they need the server's user, not administrator rights (verified on Windows). On Windows, redirected `pstree` output needs `python -X utf8`: its box-drawing characters fail in the legacy code page. Long-lived Tasks carry names for this listing (naming rules: `logging.md`).

## Heap Census cost

- A Heap Census lists each generation with one interpreter call that holds the GIL, then counts in 20,000-object slices: 5 million tracked objects took 355 ms with at most 107 ms of continuous Event Loop blocking (Python 3.14, Windows). It also holds references to every listed object until counted. Automatic collection pauses while the generations are listed: a collection between two listings, started by any thread's allocations, would move objects to a generation listed next and count them twice (on Python 3.14 whole old-generation lists at once) or miss them (`test_heap_census_counts_types_by_generation_and_reports_growth`).
