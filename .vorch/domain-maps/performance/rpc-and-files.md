# Performance RPC, files and trace events

The `performance.*` RPC shapes and errors, the Recording and History Window files, the trace events a Recording writes, and the costs and limits of Recordings and History Windows. Field names here are a contract: an external load-test harness and the `vbot performance` CLI consume them.

## RPC contract

- `performance.snapshot` `{}` -> `{started_at, uptime_seconds, metrics, gauges, counters, stalls, recording}`. `metrics` maps name -> `{count, sum_ms, min_ms, max_ms, p50_ms, p90_ms, p99_ms}`; `gauges` maps name -> latest value; `counters` maps name -> total occurrences; `stalls` is the retained list (max 50, oldest first) of `{started_at, duration_ms, gc_ms, cpu_window_ms, loop_cpu_ms, samples: [{count, stack: [frame]}], awaited_by: [frame], threads: [{name, cpu_ms, samples}]}` with samples ordered most frequent first; `awaited_by` holds at most 40 frames of the Tasks awaiting the Task the loop ran, innermost first, and is empty when the loop ran no Task during the stall's samples, nothing awaited it, or the call graph could not be read; `gc_ms` is the cyclic garbage collection pause time of all threads between the stall's last on-time monitor tick and its end, capped at `duration_ms` (its window opens up to one 100 ms tick early); `cpu_window_ms` is the stretch from the stall's first sample until the watchdog saw the loop resume, over which `loop_cpu_ms` and each thread's `cpu_ms` were measured (Windows counts CPU in 15.6 ms ticks); `threads` lists at most 5 other threads by CPU, each with at most 5 distinct stacks; the three CPU fields are `null`/empty on platforms without per-thread CPU time; `recording` is the status below or `null`. Values are process-lifetime, not windowed.
- `performance.recording_start` `{label?, max_seconds?}` -> status `{recording_id, label, started_at, elapsed_seconds, max_seconds, event_count, truncated}`. `label` is non-blank, <= 200 characters; `max_seconds` is an integer 1..3600, default 300.
- `performance.recording_stop` `{}` -> `{recording_id, label, started_at, duration_seconds, event_count, truncated, stopped_reason, trace_path, summary: {metrics, gauges_max, counters, stalls}}`. `summary` covers only the Recording window.
- `performance.recording_list` `{limit?}` (1..100, default 20) -> `{recordings: [...]}` newest first, each the stop result without `summary`.
- `performance.heap` `{top?}` (1..100, default 20) -> `{taken_at, duration_ms, previous_taken_at, tracked, generations: [{objects, collections, collected, uncollectable}], frozen, types, modules, growth}`. `types` and `modules` are the `top` largest rows `{name, count, change}` (`change` is `null` on the first census of the service); `growth` holds the `top` rows with the largest positive `change` (empty on the first census). Censuses run one at a time on the `performance` worker pool.
- `performance.history` `{since?, until?, limit?, names?}` -> `{interval_seconds, retention_days, windows}`: the newest `limit` (1..2016, default 144 = one day) stored History Windows with `ended_at >= since` and `started_at <= until`, oldest first. `since`/`until` are ISO 8601 timestamps with an offset; `names` (at most 50) keeps only those metrics, counters and gauges in each window. A window is `{started_at, ended_at, reason, process_started_at, metrics, counters, gauges, gauges_max, stalls, stalls_dropped}`: `reason` is `interval` or `shutdown`; `process_started_at` changes when the server restarted; `metrics` holds summaries (snapshot shape) of the observations made in the window only; `counters` the occurrences added in it; `gauges` the last values and `gauges_max` the highest value set in the window, at least the value at its start; `stalls` at most 20 (`stalls_dropped` counts the rest), each with its 3 most frequent samples, its whole `awaited_by` and each named thread with its most frequent one. Window extremes the window did not move are bucket estimates (about 10%).
- `performance.client_report` `{histograms?, counters?}` -> `{accepted, skipped}`: one WebUI client's measurements since its previous report. `histograms` maps a name to `{count, sum_ms, min_ms, max_ms, buckets}` (`buckets` maps a bucket index, as a string, to its count; see `merge_histogram` in `performance/metric-catalog.md`); `counters` maps a name to an integer 1..1,000,000; at most 200 names per report. A malformed value rejects the whole report with `invalid_request` before anything is recorded. Only the `webui.*` names of the Metric Catalog are merged; other names are listed in `skipped` (sorted, at most 20) so an older or newer WebUI still reports the rest. Across all clients, at most 60 reports per sliding minute are accepted; a report beyond that returns `{accepted: 0, skipped: [], rate_limited: true}` and counts `webui.reports_dropped`.
- Errors: `performance_recording_active` (start while recording), `performance_recording_inactive` (stop while idle), `invalid_request` (unknown params, bad label/limits, malformed client reports).
- `stopped_reason` is `requested` or `max_seconds`. `trace_path` is an absolute path with `/` separators.

## Files

`<data_dir>/artifacts/performance/<recording_id>.trace.json` (Chrome Trace Event JSON object format: `{"traceEvents": [...], "displayTimeUnit": "ms"}`, `ts`/`dur` in microseconds from the Recording start) and `<recording_id>.summary.json` (list fields plus `stopped_at` and `summary`). Recording ids use the `perf_` prefix (`core/utils/ids.py`). Both files are atomic; the summary is written last and marks a complete Recording, so listing reads summaries only. The newest 20 Recordings are retained; older pairs are pruned after each write. Listing and pruning share one order, the summary's `started_at` (file times are too coarse on Windows to order Recordings written in quick succession); files without a readable summary (a trace still being written or left by a crash) are never listed and are placed by their newest modification time.

History Windows are appended to `<data_dir>/artifacts/performance/history/<YYYY-MM-DD>.jsonl`, one compact JSON line per window in the file of its UTC end date; a line torn by a crash is skipped on read and the next line starts fresh. After each append, day files older than 14 days or beyond 64 MB in total (oldest first, never the current day) are deleted. A heavily used server writes roughly 3-6 MB per day (about 25-40 KB per window with 200-300 active metrics); idle windows are small. Like Recordings they are diagnostics outside the JSON document contract (`settings.md`). Placement is owned by Storage (`storage.md`).

## Trace events

Each Track emits a `process_name` metadata event and each Lane a `thread_name` (`lane <n>`); spans are `X` events with `cat` = first metric segment; gauges and `event_loop.lag` are `C` counters; stalls are process-scoped `i` events named `event_loop.stall` with `duration_ms`, `gc_ms`, `cpu_window_ms`, `loop_cpu_ms`, `samples`, `awaited_by` and `threads` args; counted occurrences with a track are process-scoped `i` events named after their counter (an accepted client report is a `webui.reports` event on the `webui` Track with `rpcs`, `long_tasks`, `long_task_max_ms` and `invalidations` args); garbage collections of at least 1 ms are `gc gen<n>` spans on the `runtime` Track.

## Costs and limits

- A Recording buffers at most 500,000 events (roughly 75-175 MB in memory) and sets `truncated` when full; histograms continue. Trace JSON is written off the Event Loop in 1000-event chunks.
- A span appears only if it began inside the Recording; `measure` blocks open when the Recording stops are dropped from the trace but still counted in histograms.
- Ending a History Window copies every histogram once and runs on the `performance` worker pool: about 10 ms for 300 active metrics. Tracking gauge peaks for windows adds about 30 ns to `set_gauge`.
