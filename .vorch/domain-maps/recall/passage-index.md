# Passage Index

Read this reference when you change the Passage catalog or index: Passage windows, tables, refresh and restore, attribution, literal FTS or vec0 storage, Embedding space pinning, the KNN limit, or damage recovery. The shared invariants (one index per Runtime, Passages reported once, disposable projection) stay in `recall.md`.

## Passage windows

Eligible input comes only from default conversation roles (`user`, `assistant`, `compaction_checkpoint`) - Tool Results, reasoning, Tool arguments, errors, notes, Skill contexts, and persisted Recall results are excluded (policy owner: `core/sessions/search_content.py`, `recall.md` -> Passage Policy). Only canonical content text contributes; Compaction summaries are built as separate Passages so they can be labeled reliably. Text is used verbatim (no whitespace rewriting); each canonical entry independently owns 1,500-char windows with 200-char overlap, so long Messages become multiple Passages instead of truncating. Windows never cross entry boundaries: a branch's later continuation cannot change its inherited entry's text or retrieval identity. Adjacent conversation remains available through the result's bounded canonical context, including inherited context. Each records exact text, policy-derived stable id, boundary Message ids/timestamps/roles, and in-message offsets; fusion keys id together with `session_id` because forks share Message ids.

Passage construction visits each Message once and advances offsets within its text; it adds no inter-Message separators. `PASSAGE_POLICY_VERSION` feeds the Passage index's projection version, so a policy change rebuilds it (Passage Catalog -> Recovery); version 2 rebuilt prior cross-entry windows in the disposable index.

## Passage Catalog

`core/recall/_passage_catalog.py` owns the catalog the Passage index holds. The index is one kernel disposable database (`database.md`) opened through `DisposableDatabase` and used only through the async `read`/`write` variants, so no SQLite work runs on the Event Loop. Blocking Session reads (refresh planning, scope reads, `canonical_scan` and Passage FTS pages) run on the Session database's worker pool through `ChatSessionManager.run_async`, not `asyncio.to_thread`. Time filters (`time_bounds`) compare the Passages' boundary timestamps, the Session's canonical stored text, directly with the canonical form of the bound. Tables: `indexed_sessions` (one freshness stamp `(generation_id, history_revision)` per Session, recorded even for Sessions without Passages), `catalog_history` (the `ChatSessionManager.history_id` the stamps were taken from), `passages` (stored once per Recall scope under `passage_key`, a hash of Passage id, text hash, boundary Message ids, timestamps and roles - the id alone does not distinguish valid repeated public Message ids) and `passage_views(session_ref, passage_ref, owned)`. Passages are built over each Session's complete current view, so a fork and its origin build identical Passages over shared history and share the rows; `owned` follows its entry's current-view position (position >= `SessionReadBatch.inherited_count`), never a lookup by public Message id, because those ids may repeat.

- Restore: a data snapshot restore of `sessions.db` brings back older history, after which a Session can reach a stamped `(generation_id, history_revision)` again with other content. A refresh that finds another `history_id` than `catalog_history` first sets every stamp's revision to -1 (`follow_history`), so each Session is reread once and diffed by `passage_key`: Passages of discarded history leave, unchanged ones keep their rows and vectors (no re-embedding). An index from before the table follows the same path once.
- Refresh: one stamp read prunes Sessions that left the given live set and finds the candidates whose stamp changed; only those are reread on the Session database's worker pool (`load_since(None)` returns history and version atomically) and diffed by `passage_key`. One write transaction applies it: compare-and-set on each stamp (a stamp that moved since planning is skipped), new Passages and views, changed `owned` flags, and deletion of Passages no Session shows. A scope whose candidates all match their stamps and that lost no indexed Session needs no Session read. A search refreshes once for its own candidates and prunes by the complete live scope; an indexing pass refreshes every Recall-visible Session of every live scope at once (`refresh_scopes`: one stamp read over every indexed Session, a write per changed scope, then one write evicting the indexed scopes it did not name), so hidden Sessions are pruned there (`recall/semantic-indexing.md`). Deleting an origin materializes its entries into descendants and bumps their history revision, so they are reindexed and then own that history.
- Attribution: a Passage matches only when a candidate Session shows it, and its hit is reported for exactly one candidate, the highest `(owned, creation_order, session_id)`: the owner when it is eligible and still shows it, else the newest eligible Session that shows it (`RecallScope.creation_orders` from `list_history_revisions`). This mirrors store search (`sessions/search.md`), so a fork and its origin never both return shared history. Entry-anchored windows remain identical when either branch grows; shared fork tails therefore also appear once. History materialized into several descendants is reported once, for the newest.
- Recovery: `PassageCatalog.recovering` discards a damaged database (`projection_failure` is `rebuild`) and runs the operation once more; busy or unavailable never discards (writes wait 5 s, then fail as busy); canonical read failures propagate unchanged. `projection_version(layout) = layout + PASSAGE_POLICY_VERSION - 1`: both counters started at 1 with Generation 1 and only grow.

## Index storage

`<data_dir>/recall/passage_index.sqlite` (kernel disposable projection `recall_index`, `passage_index.passage_index_database_spec`; `connection_setup` loads sqlite-vec on every connection; the Python package, which imports numpy, is imported with the first connection or vector, not with the module). It is never authoritative and holds:

- the Passage Catalog;
- literal FTS over `passages`: two external-content FTS tables kept in step by triggers, `passages_fts` (trigram) for queries whose every term (or phrase) has at least three characters and `passages_fts_tokens` (unicode61) for all others with whole-token candidates. The kernel cannot declare virtual tables, so the spec's `after_open` creates missing FTS tables and triggers and fills a new FTS table from `passages`;
- vectors: a singleton `store_header` pinning the Embedding space, the vec0 table `passage_vectors` (rowid = `passage_ref`, partitioned by Recall scope, start/end timestamps as microseconds; a Passage timestamp that is not canonical is damage (`DatabaseCorruptError`) instead of a guessed instant), and `pending_vectors`, the queue of Passages without a vector (an insert trigger on `passages` fills it; a new Passage whose text already has a vector in the pinned space copies it at once);
- `skipped_texts` (text hashes the provider permanently rejected, with a reason code) and `indexer_state` (document embedding usage spent in the pinned space and the last completed pass). `store_vectors(..., usage=, characters=)` also classifies each call by what it reported into `SpentMeasure`: the characters and tokens of requests that reported tokens, tokens and cost of those that reported both, and of those without a cost the tokens or, without tokens, the characters; a call that reported for only some of its requests stays unclassified. An index file from before the measure gains its columns at zero, so its earlier usage stays unclassified.

An Embedding space is the provider, configured model, binding fingerprint (`EmbeddingSpaceIdentity`), index policy and dimension that `store_header` pins. The model name the provider reports serving (`response_model_id`) is recorded but is not part of the space: a router such as OpenRouter answers one configured model from several hosts that report different names (seen live with `baai/bge-m3`), and treating each name as a new space wiped the index on every alternation.

The first space is pinned when vec0 is created; another space (`use_space`) drops vec0, skipped texts and spent usage, replaces the header and requeues every stored Passage while keeping the catalog. `reset_vectors` (rebuild) does the same without a new header. A header without its vec0 table is damage. `knn_search` asks vec0 for `k = min(limit, KNN_MAX_K)` (4096, the sqlite-vec limit) and reports `truncated` when the limit cut the ranking; a KNN query sqlite-vec rejects as a parameter error raises `PassageIndexError`, which is not damage, so the index is never discarded for it.

## Source and tests

- `core/recall/passage_index.py`, `_passage_catalog.py`; Passage construction and `PASSAGE_POLICY_VERSION` in `core/recall/passages.py`; `core/recall/canonical.py` keeps its prior helper imports as compatibility exports of `core/sessions/search_content.py`.
- `tests/core/recall/test_passages.py` covers Passage construction; `test_passage_index.py` covers the index (projection identity, space/queue/skipped/spent bookkeeping, catalog refresh and scope eviction, KNN limit, literal search, damage). `recall_test_support.py` owns the shared request builder, the fake embedding service (recording document and query inputs), `embed_documents` (one indexing pass), stored-Passage row readers, `forbid_event_loop_calls` (fails synchronous Session store calls made on the Event Loop) and `forbid_database_calls_on_loop` (fails blocking kernel reads/writes and asynchronous read callbacks on the Event Loop or on any thread other than that database's own worker pool). The directory's `conftest.py` provides a `sessions` fixture over a cloned current-format store and the `vector_backend`/`hybrid_backend` factory fixtures (typed by `VectorBackendFactory`/`HybridBackendFactory` in `recall_test_support.py`), which close every backend they open, and with it its own Passage index, when the test ends.
