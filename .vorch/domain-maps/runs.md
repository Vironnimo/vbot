# Runs

Run lifecycle, cancellation, replayable timeline events, and in-memory busy-session queue coordination.

## Overview

`core/runs/` owns the provider-agnostic execution envelope around one active Session turn. It does not own provider/tool execution, ChatMessage construction, Session persistence, server transport, or WebUI state; those domains consume Run state through `core.runs`. `ChatLoop` builds the `RunExecutor` and calls `ChatRunManager.start(...)` or `enqueue(...)`; the manager creates the `Run`, runs the executor in a background task, publishes lifecycle events, and drains queued work.

## Terms

Core term Run lives in `.vorch/GLOSSARY.md`.

### Waiting-Work Admission

**Definition:** A manager-owned reservation for an inbound item that has been accepted but cannot yet be represented as a queued Run, such as a channel attachment before its download. It atomically becomes a queued Run or is released when work starts or aborts.

**Not:** A second queue or a Run; it only accounts for capacity in the existing `ChatRunManager`.

### Run Admission Guard

**Definition:** A `ChatRunManager`-owned, async context-managed boundary that atomically verifies a Session, Agent, or Project has no active/queued work and then rejects new `start()` and `enqueue()` calls for that scope until a destructive transition finishes.

**Not:** A cancellation mechanism or persistence lock. It prevents new Run admission; the owning workflow still performs Session, Agent, or Project storage changes through its own domain APIs.

## Data Model

- `RunStatus` - `running`, `completed`, `failed`, `cancelled`, or `interrupted`. `interrupted` is a terminal unsuccessful outcome for a Run whose execution ended without a trustworthy completion after bounded recovery; it is distinct from both an ordinary failure and user cancellation.
- `RunKind` - stable producer category carried by every Run: `user`, `channel`, `cron`, `reflection`, `memory_reflection`, `skill_reflection`, `subagent`, or `system`. The two scoped reflection kinds distinguish memory-only from skill-only review Runs (the combined/manual `/reflect` review keeps the generic `reflection` kind). It is independent of `internal` and Agent-activity policy: consumers use it for origin-aware presentation and selection, never to infer execution privileges.
- `RunEvent` - replayable timeline event with Run-local `sequence`, ids, `type`, JSON `payload`, and UTC ISO `timestamp`. It also carries `project_id` (the emitting Run's anchor, `None` for an identity run) and `run_kind`: `agent_id` stays bare, so a consumer that keys by the outside `agent@projekt` address rebuilds it from these fields. Mirrored into `to_dict()` and the `/ws` bridge payload. Events from Runs excluded from Agent activity also carry `contributes_to_agent_activity: false`; the default `true` is omitted from serialized payloads for compatibility.
- `Run` - active execution state with separate `project_id` Session/address ownership and internal `working_project_id` working context, immutable `run_kind`, bounded replay/subscriber state, cancellation, result/error, executor task, lightweight execution telemetry (canonical `iteration_count`, total `tool_call_count`, and dispatched `tool_call_names`), and the generic `contributes_to_agent_activity` projection policy (default `True`). The activity policy controls only Agent/Session attention status; neither it nor `run_kind` changes execution, Run admission, cancellation, persistence, timeline visibility, or diagnostics. `working_project_id` remains internal; the Runs/server edges project `iteration_count` into Run responses, active snapshots, and terminal payloads, while Chat projects it at each completed response and into durable history.
- `QueuedRunItem` - pending request with display preview, executor, `internal` flag, public `editable` capability, created timestamp, single-owner `future`, one immutable `admission` bundle (`core.runs.RunAdmission`: working Project, run kind, Agent-activity policy, durable work correlation), and a transient waiting-scope tag. The queue key still owns only Session identity; public queue payloads include the run kind and `editable` but omit the other admission decisions. Chat marks an item editable only when its complete content is a short raw string that the public preview preserves losslessly; structured content, attachments, and truncated long text are not editable.
- `ChatRunManager` - in-memory owner of active Runs, completed-Run lookup retention, per-session FIFO queues, Run Admission Guards, cancellation, Run-start callbacks, and the bounded system-wide waiting-work accounting used by channel ingress.
- `RunExecutor` - async callable receiving the `Run` object and returning the final result. The manager translates returned results, raised errors, and cancellation into terminal Run state.
- `RunError`, `RunInterruptedError`, `ActiveRunError`, `RunAdmissionBlockedError`, `RunNotFoundError`, `RunCancelledError`, and `WaitingWorkLimitError` are expected domain errors for caller/RPC mapping. `RunInterruptedError` carries the normalized cause and optional partial result that the manager stores on the terminal Run; `RunAdmissionBlockedError` subclasses `ActiveRunError`, so existing start-then-queue ingress reaches `enqueue()` and receives the same expected conflict while a lifecycle guard is held.

## Event Contract

Most stable event constants live in `core.runs`: lifecycle (`run_started`, `run_completed`, `run_failed`, `run_cancelled`, `run_interrupted`), output (`user_message_persisted`, `reasoning`, `tool_call_started`, `tool_call_result`, `assistant_output`, `error_message_persisted`, `model_fallback_activated`, `model_step_usage`, `compaction_started`, `compaction_aborted`, `compaction_completed`), and transient activity (`assistant_output_delta`, `reasoning_delta`, `tool_call_delta`, `tool_call_stdout`, `tool_call_stderr`, `provider_heartbeat`, `stream_attempt_restarted`). `run_interrupted` is terminal, carries `{status: "interrupted", cause, timing, iteration_count, ...terminal_payload_extras}`, and never masquerades as `run_completed`. Chat emits the non-visual `model_step_usage` payload `{usage, session_usage, context_usage, iteration_count}` after the corresponding Model response is persisted, including estimated and Tool-only responses; server bridges it as ordinary `run_output`, and the UI consumes only its canonical Iteration projection plus Usage state without rendering the event as a row. Chat emits the equally non-visual `run_change_stats` payload `{change_stats}` (git-style `{files, added, removed, paths}` totals from the Change Tracker) after each dispatched Tool round whenever the totals changed since the last emission - an all-zero object retires an earlier nonzero total, and no event is emitted while nothing is tracked; the terminal payload's `change_stats` equals the last live value by construction, and the WebUI keeps its per-tool-call sum only as fallback for runs without any server value. `provider_heartbeat` is also bridged as ordinary `run_output`; its `{idle_seconds, state}` payload is Provider transport liveness, the UI projects it only as running metadata, and it never becomes Session history or Assistant output. `stream_attempt_restarted` tells a Run consumer to discard the failed current stream attempt's transient deltas; it stays SSE-only and is not Session history. Chat emits `compaction_started` immediately when Compaction work begins; automatic attempts include `{context_tokens_before}`, while a dedicated manual Compaction Run may emit an empty payload before asynchronous request preparation so the activity is observable without delaying Run admission. `compaction_aborted` carries a non-sensitive reason when no checkpoint will follow. `compaction_completed` carries `{message, checkpoint, checkpoint_id, history_available, context_tokens_before, context_tokens_after}` after persistence; `message` carries the same token pair in checkpoint Usage so History reloads preserve the completed presentation. `subagent_session_started` is emitted on a Run timeline too, but its constant belongs to `core.subagents` because the payload is owned by the sub-agent domain.

Every emitted event increments the Run-local `sequence`, including transient deltas. Sequences are monotonic for that Run and are never reused when old events fall out of the retained replay window. `Run.subscribe(after_sequence=...)` replays retained events with larger sequence numbers, then follows live events until a terminal event; late subscribers can only replay the retained window.

`core/event_stream.py` owns the shared replay/live handoff, sequence de-duplication, bounded subscriber queues, and lag eviction used by both Run timelines and the server event bus. Run remains the owner of event creation, Run-local sequencing, cancellation suppression, and terminal-event semantics; do not move those domain rules into the generic stream.

Run event payload ownership stays with the domain that emits the event. `core/chat/` owns ChatMessage, tool-call, fallback, compaction, and error-message payloads; `core/subagents/` owns `subagent_session_started`; `server/` only maps Run events to SSE/WebSocket/RPC payloads and strips opaque provider metadata.

## Interfaces

- `Run.emit(event_type, payload=None, *, allow_after_cancel=False) -> RunEvent | None` appends and publishes an event unless the Run is terminal or cancellation suppression drops a non-terminal event. `allow_after_cancel=True` is the one deliberate suppression escape: an executor may still publish an event that finalizes output the user has already seen (the chat loop's preserved partial answer on cancel) - never new or late results. The `run_started` payload is `{"status": "running"}` with an optional `queue_item_id` when the run was started from a queued item.
- `Run.subscribe(after_sequence=0)` streams retained and future events until terminal state; lagging live subscribers are evicted instead of building unbounded queues.
- `Run.wait()` waits for terminal state, returns the executor result, re-raises failures, raises `RunCancelledError` for cancelled Runs, and re-raises the stored `RunInterruptedError` for interrupted Runs while the partial result remains available on the Run.
- `Run.request_cancel(reason=None)` marks cancellation requested, stores the optional `reason` on `Run.cancel_reason` for inclusion in the `run_cancelled` terminal payload, first cascades every still-active per-Tool callback in registration order, and then schedules registered sync/async Run callbacks. Completed Tool Calls have already cleared their entries and do not receive a late callback; a callback registered after the Run cancel signal fires immediately and observes the call as cancelled. The manager awaits every scheduled asynchronous cancellation callback before publishing the terminal cancellation, releasing the Session, or starting its next queued Run, so an old Tool or Process cannot overlap its successor. Once the manager task has entered its execution wrapper it is cancelled forcefully; a request made before that first step leaves the wrapper scheduled long enough to perform terminal cancellation bookkeeping without entering the caller's executor, so the Session is always released.
- `Run.add_cancel_callback(callback)` registers cleanup for active provider/tool/host work; callbacks registered after cancellation is already requested are scheduled immediately.
- `Run.begin_tool_call(tool_call_id)` marks a dispatched call active before `tool_call_started` is emitted, so an accessor can cancel it immediately even when Tool-owned cleanup has not registered yet. `Run.register_tool_cancel(tool_call_id, callback)` attaches that cleanup without touching the Run's overall cancellation state; registration after either an early per-call cancel or `request_cancel` schedules the callback immediately, so neither race can orphan cleanup.
- `Run.cancel_tool_call(tool_call_id) -> bool` marks an active call user-cancelled and invokes its callback when already registered; an early cancel remains pending until registration. It returns `False` for unknown, completed, or already-cancelled ids. It does NOT set `cancel_requested` and does NOT cancel the executor task: per-call cancellation remains local, while `request_cancel` deliberately subsumes all still-active per-call cancellations.
- `Run.tool_call_cancelled(tool_call_id) -> bool` reports whether a specific tool call was user-cancelled via `cancel_tool_call`.
- `Run.clear_tool_cancel(tool_call_id)` removes the per-tool-call cancel registry entry.
- `Run.raise_if_cancelled()` lets executors stop between provider/tool steps once cancellation was requested.
- `ChatRunManager.start(address, executor, *, admission=DEFAULT_RUN_ADMISSION)` starts immediately or raises `ActiveRunError` when that Session already has a running Run. The positional `address` is the required `SessionAddress`; the created `Run` reads its project anchor, agent, and session from it. `enqueue(address, executor, *, display_content="", editable=False, internal=False, waiting_work_admission=None, admission=DEFAULT_RUN_ADMISSION)` accepts the same shape plus queue-display inputs, starts immediately when idle and resolves the item future at once, or stores them on the FIFO `QueuedRunItem` so a later drained Run keeps the decisions. `admission` (`core.runs.RunAdmission`: `working_project_id`, `run_kind`, `contributes_to_agent_activity`, `work_id`) carries the immutable origin/activity/work-correlation decisions as one bundle; it never influences admission, execution, or cancellation, and `work_id` is internal orchestration state that reaches durable storage only through Chat's terminal Run Summary. Both methods check Run Admission Guards under the manager's same `_lock` before admitting work and raise `RunAdmissionBlockedError` on a guarded Session, Agent, Project anchor, or internal working Project.
- `session_admission_guard(*session_addresses)` atomically guards one or more exact `SessionAddress` identities (no raw tuples); Agent Takeover supplies source and destination together. `agent_admission_guard(agent_id, *, project_id)` guards all Sessions owned by one Agent in one anchor. `project_admission_guard(project_id)` guards both Project-anchored Sessions and Identity-Agent Runs whose internal working Project selects that Project. Guard acquisition refuses existing active/queued work or an overlapping guard and release is guaranteed by the async context manager.
- **Waiting-work capacity is manager-owned.** At most `DEFAULT_WAITING_WORK_LIMIT` (32) tasks may wait system-wide; active Runs do not count. `enqueue` rejects a new normal queued Run at that ceiling. Channel ingress calls `reserve_waiting_work(scope, scope_limit)` before accepting raw work or downloading media; the reservation counts against the same ceiling and its per-scope limit. It is released when non-Run work begins, or transferred atomically through `enqueue(..., waiting_work_admission=...)`, so no second queue can over-admit. `release_waiting_work(...)` cleans up a reservation when processing fails or shuts down; `waiting_work_count()` is the central diagnostic count.
- **The dedup key is the `SessionAddress`** `(project_id, agent_id, session_id)` (born in `core.sessions`). The project anchor is part of the key because `session.create` accepts caller-chosen session ids, so identity `builder` and project `builder@vbot` can both own a session named `main` - the two sessions must never block, cancel, or guard each other (the recall FTS index was scoped by project for exactly this case). Admission-facing methods (`start`, `enqueue`, `session_admission_guard`) take the address as one positional value; every public lookup method (`active_run`, `cancel_by_session`, `list_queued`, `remove_queued`, `update_queued`, `has_activity_for_session`) deliberately keeps scalar `agent_id`/`session_id` plus a **required** keyword-only `project_id` (`None` = the identity anchor), so no caller can silently fall into the wrong scope. Every RPC surface knows the project from its parsed `agent@projekt` address; the queue RPCs (`chat.queue_*`) parse the address too.
- `ChatRunManager.list_queued(...)`, `remove_queued(...)`, and `update_queued(...)` are raw queue controls. They include internal items; public RPC filtering belongs in `server/rpc/chat_methods.py`.
- `ChatRunManager.get(run_id)`, `active_run(...)`, `cancel(run_id, reason=None)`, and `cancel_by_session(..., reason=None)` are the lookup/cancellation surface used by server RPCs, slash commands, channels, tools, and sub-agent cleanup. Normal Stop surfaces pass `reason="user"`; Chat records that as the internal interruption cause while using the same checkpoint recovery path as other interrupted Runs.
- `await ChatRunManager.aclose()` closes Run admission atomically, cancels queued items and reservations, requests shutdown cancellation for every active Run, and waits for their executor and cancellation-cleanup tasks. A closed manager rejects later start, enqueue, and reservation calls and never drains another queued item.
- `ChatRunManager.has_activity_for_agent(agent_id, *, project_id)`, `has_activity_for_working_project(project_id)`, and `has_activity_for_session(...)` are execution/admission snapshot queries and therefore include Runs whose Agent-activity projection is disabled. They are not UI-attention queries or synchronization primitives: destructive Session/Agent/Project workflows use the corresponding Run Admission Guard so a new Run cannot enter after an idle check.
- `ChatRunManager.active_runs() -> list[Run]` returns a snapshot (fresh list) of all entries in `_active_by_session` whose `status == RunStatus.RUNNING`. Public accessor mirroring `active_run(...)`; the `/ws` `connection_ready.active_runs` projection includes each Run's canonical `created_at` as `started_at` so reconnecting accessors can resume live elapsed time rather than restarting a timer locally.
- `ChatRunManager.all_queued() -> list[tuple[SessionAddress, QueuedRunItem]]` returns a fresh cross-session Queue snapshot in per-session FIFO order. The `/ws` handshake groups its non-internal items by Project, Agent, and Session; internal queued work remains server-only.

## Cross-Domain Contracts

- `core/chat/` owns provider calls, tool execution, message persistence, retry/fallback behavior, and which Run events to emit. New chat execution paths should call the manager instead of constructing `Run` directly.
- `core/chat/` records the admitted Run's `run_kind` on its Session when execution begins; fork creators that must expose a classified Session before the Run starts may record it earlier through Sessions' idempotent API.
- `core/sessions/` owns durable history. Run timelines are process-local replay buffers and are not a substitute for canonical SQLite Session history. `session.delete` and Agent Takeover hold Run Admission Guards across their awaited archive/move and follow-up metadata writes; a Session `write_lock` alone cannot prevent a later Run from recreating a moved or archived address.
- `server/` exposes `Run.events` in RPC responses, streams raw Run events over SSE, and bridges non-delta events to WebSocket lifecycle summaries. High-volume text/Tool deltas are SSE-only; the low-rate `provider_heartbeat` transient is also WebSocket-bridged so an observing Parent can retain child Run liveness.
- `core/automation/`, `core/subagents/`, channels, tools, and slash commands share the same `ChatRunManager`; they must not create parallel per-domain busy-session queues. Channel ingress reservations are manager state, not a separate scheduler, and are transferred to the normal Run FIFO when a turn is busy.
- `webui/` treats queue state and Run lifecycle truth as server-owned projections.

## Constraints & Gotchas

- Only one Run may be active per `(project_id, agent_id, session_id)`; Runs in different Sessions (including a project and an identity session sharing agent/session ids) execute in parallel. `Run.project_id` mirrors the key's project dimension and is what the executor's session I/O reads.
- Busy checks followed by awaited or external lifecycle work are inherently racy unless the scope remains guarded in `ChatRunManager`. Never reintroduce a check-then-archive/move/delete sequence based only on `has_activity_for_*`.
- Queue state, ingress reservations, active Run lookup, completed Run lookup, and Run event replay windows are all in-memory and bounded. The shared waiting-work ceiling is 32 across queued Runs and reservations; process restart loses Queue state and old timeline replay. `connection_ready.queues` reports the new process's complete public Queue state for client reconciliation; it does not persist or resume discarded work.
- `enqueue(...)` is not "always queued"; callers must handle the item future already being resolved to a running Run. A caller that awaits the bare future and is cancelled abandons that queued work; do not shield or replace the future-cancellation removal without introducing another explicit ownership contract.
- Removing a queued item cancels its future. A public Queue update is accepted only while the current item is marked editable; updating replaces both executor and display preview and recalculates editability from the replacement content, so build replacements through `ChatLoop.build_queue_update(...)` when user-visible Chat content changes. Chat rebuilds that executor from the queued request itself and replaces only the edited content/input origin; transports must not synthesize a fresh executor because that would discard immutable Sender, reply-surface, Tool-policy, hook, or override inputs.
- The manager starts terminal bookkeeping. Normal executors should emit domain events and return or raise; they should not call `mark_completed`, `mark_failed`, `mark_cancelled`, or `mark_interrupted` themselves unless they deliberately own lifecycle completion. An executor signals the last case by raising `RunInterruptedError`.
- `Run.mark_failed(...)` is the single authoritative failure-log chokepoint: every executor (interactive, cron, channel, subagent) reaches it, so it logs there - expected `VBotError` at `warning` (no traceback), anything else at `error` with traceback (`vbot.runs`). Failure handlers elsewhere (e.g. `core/chat`'s `_persist_run_error`, subagent result folding) must not re-log the same failure.
- Cancellation cleanup retires each settled Future snapshot directly; it must not depend on scheduled completion callbacks getting a turn, because awaiting already-completed Futures may not yield. Cleanup registered by earlier callbacks still drains before the Session is released.
- Cancellation is best effort. Late non-terminal provider/tool output is suppressed after `cancel_requested`, `Run.emit()` returns `None` for suppressed events, and already-emitted events remain replayable.
- Cancelling immediately after `start(...)` returns must still move the Run to `cancelled`, resolve `Run.wait()`, remove the active-session entry, and drain queued work. Do not cancel a newly created manager task before its execution wrapper has entered the lifecycle `try/finally`; Python otherwise skips that coroutine body entirely and strands the Session in `running`.
- After cancellation suppression starts, only terminal events and an explicit `allow_after_cancel` emit (the preserved-partial finalization - see `Run.emit`) pass. Terminal payloads include `timing` with `{ started_at, completed_at, duration_ms }` and the Run-owned `iteration_count`; duration uses a monotonic clock and timestamps are UTC ISO strings for display/persistence. `run_completed` may also include `usage`, kept separate from `timing`. `run_cancelled` also includes the optional `reason` field when one was supplied to `Run.request_cancel(...)`; `run_interrupted` includes the normalized `cause`. Executors may fill the `Run.terminal_payload_extras` dict before returning/raising; the manager merges it into the terminal payload of every outcome alongside `timing`, while the manager itself supplies `iteration_count`. The chat loop supplies `session_usage` on every outcome. Continuation checkpoint contents remain internal Chat state even though the normalized interruption cause is projected in the terminal event.
- WebSocket bridge code filters out SSE-only deltas and de-duplicates recently bridged Runs. Fix transport mapping in `server/rpc/event_bridge.py`, not in `core/runs/`.
