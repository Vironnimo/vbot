# Session storage

Task-gated detail for `sessions.md`: the store's internal modules, the Session database tables and named migrations, its kernel integration (write budgets, snapshot facts, bootstrap) and operator-style SQLite inspection. Source: `core/sessions/store.py`, `schema.py`, `_store_*.py`.

## Source routing

The public `core.sessions` package routes stable imports to the Session service in `sessions.py`, the buffered Session handle in `session.py`, immutable records in `_types.py`, and semantic history helpers in `history.py`. Metadata validation/cursors and bounded I/O/write leases live in `_metadata.py` and `_io.py`. `_lifecycle.py` applies creation, address, Working Project and title policy; `_run_persistence.py` translates live Runs into stored execution records and completion notifications. Canonical timestamps come from `core/utils/timestamps.py`.

`store.py` opens the Session database through the shared kernel (`database.md`) and keeps read/write admission, history/metadata operations and FTS error recovery. Its private `SessionExecutionStore` (`_execution_store.py`) groups Run admission/settlement, Stream drafts and durable owner/accessor deliveries on those same transactions; callers outside Sessions continue through `ChatSessionManager`, never the storage helper. Private `_store_*` modules receive its connection:
- `codec` - per-role entry rows and side tables, set-wise decoding, Tool-result linking; `copies` - materialized entries, Runs, Tool calls and payloads during lineage detachment.
- `lineage` - the lineage visibility predicate (`admits`, the one fragment every view read, the search candidates and the FTS membership views are built from), view ranges, fork lineage and edit truncation; every current-view read goes through `view_ranges` plus `ordered_rows` (one index range scan per range) or `view_query` (one set-wise query over a `VALUES` CTE of the ranges). It imports no other store module, so `schema.py` builds on it.
- `history` - bounded reads over one explicit view (current view, own audit, own spend), cursors and deltas, Run lookups, Recall context.
- `usage` - paged accounting-only own-audit export across live and archived generations, through `ChatSessionManager.usage_history`; includes entry and Message identities plus Assistant interruption state, without inherited prefixes or content decoding. The independent canonical recorder imports this evidence and repairs incomplete records after restore (`usage.md`).
- `timeline` - the shared Chat History snapshot and edit eligibility (`_editable`, `latest_takeover`). Its `complete_runs` option expands requested page edges and touched incremental Runs inside one database snapshot, so semantic timeline callers receive complete Run segments; the limit is a target. The exact-Run read serves durable timeline reconnect without loading unrelated conversation history (`chat/timeline.md`).
- `operations` - compound transactions: the Compaction commit and the history edit.
- `prompts` - prompt pins, seen Skills and the prompt-cache affinity id.
- `tool_invocations` - durable dispatch admissions, exact Result settlement and incremental own-audit reads (`sessions/runs.md` -> Canonical Tool invocations).
- `runs` - admission, completion, Stream drafts and restart recovery; `notifications` - per-Run eligibility, read marks, Schedule provenance, bounded Schedule History and notification policy.
- `mutations` - lifecycle (create, move, fork, delete with delete-time detachment, the review forks that follow a Session), metadata writes and plain appends.
- `archive` - the archive entry ledger: every statement on `archive_entries`, `archive_entry_sessions` and `archive_entry_trees`, the compare-and-set state transitions, archiving Sessions into an entry, making an entry's members live again, and the purge steps. `archive_backfill` - adoption of archives that have no entry (legacy trees under `archive/`, archived Sessions without membership); the only code that knows the legacy layouts. The public facade is `SessionArchiveLedger` (`archive_ledger.py`, `ChatSessionManager.archive_ledger`), which the archive service drives (`archive.md`).
- `queries` - catalog, Session-list summaries, descriptors and revisions.
- `owned` - temporary bindings, delivery receipts and owned Runs.
- `accessor_inputs` - ordinary Accessor acceptance receipts, opaque queued execution payloads, attachment roots and atomic Run/Steer consumption (`sessions/owned-execution.md` -> Ordinary Accessor inputs).
- `values` - Session row columns, the metadata facade, scope and value validation.
- `fts` - disposable index lifecycle; `search` - bounded search, consuming `_search_request.py` for normalization, literal matching and FTS preparation. `search_content.py` owns canonical searchable roles, derived Recall-result exclusions and Content Block extraction; Recall consumes it rather than Sessions importing Recall.
- `external_notes` - whole-batch exactly-once Notes from durable accessor inboxes; `extension_results` - receipts bound to an original Extension Tool invocation and idempotent late outcomes; `commands` - opaque background-command checkpoints bound to the Session's immutable key. These use the execution store; their domain policy stays with Channels, Extensions and commands.
- `attachments` - retained-entry blob reachability across live, archived and superseded history; startup attachment collection reads it through the manager (`attachments.md`).
- `schema` - the kernel spec (public lazy export `core.sessions.session_database_spec`: the DDL from `schema.py`, the FTS readiness hook, snapshot facts and status health). `health` keeps cheap index status separate from the last explicit coverage check (`sessions/search.md`).

Read helpers that reconstruct Messages or decode JSON columns (summaries, temporary bindings) select rows inside the read transaction and return a decoder; `store.py` (`_read_decoded`) runs it after the transaction ends, because a rollback-journal store serves reads on the serialized writer.

## Tables

Programmatic Tool activity uses the existing Assistant declaration and Tool Result tables with additive `entries.programmatic` (default false) and `parent_tool_call_id` columns. These entries remain in public History but never enter Model Context; no parent foreign key is required because eager script calls can persist before their enclosing Assistant. Migration `sessions.0010_programmatic_tool_activity` refuses older readers that would otherwise replay this internal activity as Model turns. Result linkage, payloads and canonical invocation settlement keep their normal transaction (`sessions/runs.md`; `test_tool_invocations.py`).

- All tables are `STRICT`. The partial unique index `sessions_one_live_address` permits exactly one live row per public address while retaining any number of archived generations; `sessions_archived_address` serves archived-address lookups (id allocation). `run_stream_drafts` references its Run. The retired `continuations`, `continuation_requests`, `continuation_steps`, `continuation_step_chunks` and `continuation_operations` tables stay in format generation 1 (removals are not additive) and nothing reads or writes them. `store_meta` holds the FTS lifecycle markers.
- `entries` holds every history item (`sessions.md` -> Terms -> Entry) with `UNIQUE(session_key, seq)`; large or role-specific values live in 1:1 side tables (`entry_text`, `assistant_entries`, `assistant_reasoning`, `assistant_output_files`, `user_entry_senders`, `user_entry_origins`, `error_entries`, `history_edit_entries`, `note_model_fallbacks`, `note_goal_events`, `checkpoint_entries`, `checkpoint_projections`; `assistant_output_files`, `note_subagent_messages` and `note_widget_states` hold ordered lists keyed by `(entry_key, ordinal)`). Reads select entry rows first and then only the side tables their roles need, set-wise by `entry_key`, and decode entries into `ChatMessage`s. `assistant_entries` stores the Usage field-provenance flags but not the whole-turn `estimated` summary, which the codec derives on read; `assistant_output_files` requires every reference's marker span (`start_index`, `end_index` NOT NULL). `entry_key` is `AUTOINCREMENT` because it is the FTS rowid and the rebuild high-water mark. JSON is reserved for open payloads (content blocks, arguments, Provider extras, display payloads).
- The `sessions` row carries history state (`next_seq`, `history_revision`, `state_revision`, `cursor_floor_seq`, `last_activity_at`, `last_entry_id`), fork columns (`fork_parent_key` with `ON DELETE SET NULL`, `forked_at`, `fork_point_seq`), prompt state columns, the latest-completion columns (Run references by `run_key`, `sessions/runs.md` -> Completion activity), the Session-list fields (titles, Channel identity, Sub-Agent parent link, the Session Compaction Policy, the Session Agent overrides, the derived visibility mask), and `working_project_id` (GLOSSARY -> Working Project; NULL for a Project Session and for the Workspace). That column carries no CHECK, because an older vBot that does not know it moves Sessions between scopes; the partial index `sessions_by_working_project` serves archive-time association capture. Run kinds live in `session_run_kinds`. List filtering never parses open-ended JSON (`metadata_json` holds only residual metadata); ordered pages use declared keyset indexes, and exact per-scope counts use a narrow covering index. There is no projection backfill.
- The named migration `sessions.0005_attachment_references` backfills structured and inline blob references into `session_attachment_refs`; `session_attachment_ids` retains the ids previously observed after the last referencing entry disappears. Older writers are refused because collection relies on every writer maintaining these references. Canonical entry deletion cascades its references; collection acknowledges only successfully removed ids. `unreferenced_attachment_ids(additional=...)` filters known orphan ids and supplied expired-upload candidates against canonical entry/accepted-input roots and references held by retained snapshots through the database kernel's read-only inventory, including ids without prior-ownership ledger evidence. It is valid only at quiescent startup/shutdown boundaries.
- Every stored timestamp is canonical UTC text (PROJECT.md -> Conventions -> Time), so text order is time order; writes normalize other ISO 8601 forms and reject values without an offset.
- `SCHEMA_SQL` (`schema.py`) declares format generation 1 of the Session database. The kernel checks identity and generation, applies the additive reconcile and probes every table before readers open; an already current schema requires no write transaction.
- Other named migrations: `sessions.0001_archive_entries` (`archive/legacy-adoption.md`), `sessions.0002_session_working_projects` and `sessions.0004_restore_provenance` (`sessions/ownership.md`), `sessions.0003_subagent_reply_targets` (`sessions/history-api.md` -> Sub-Agent reply targets), and `sessions.0006_review_lineage` (`sessions/lineage.md` -> Delete; refuses older writers that do not maintain review provenance).
- `sessions.0007_accessor_inputs` refuses older runtimes that cannot recover accepted ordinary Accessor work. Its additive tables keep the indexed receipt narrow, the Chat-owned execution payload separate, the canonical fallback User/Notes independent of that opaque format, and attachment roots outside transcript entries; their lifetime follows the receipt's immutable Session key.
- `sessions.0009_tool_invocations` adds the independent Tool-start ledger and backfills proven own Results in bounded batches; older writers are refused (`sessions/runs.md` -> Canonical Tool invocations).

## Kernel integration

Connection and journal policy, the serialized writer, the read pool, error classification, quarantine, data snapshots and metrics are kernel behavior (`database.md`); the Session store adds only the following.

- Session write budgets are 20s by default, 60s for transcript writes (appends, receipt appends, `finish_run`, `commit_compaction` and `apply_edit`) and 0.5s for the advisory completion-read write `mark_terminal_run_read` (`store.py`). Whole-database `quick_check`, foreign-key, hash, and FTS coverage scans never block normal Runtime readiness. Stored rows that cannot be trusted raise `SessionStoreCorruptError` (a `DatabaseCorruptError`). Metrics are `sqlite.sessions.write`, `.write_wait` and `.read` (`performance/metric-catalog.md`).
- The Session spec adds the snapshot facts `session_count`, `entry_count`, `latest_history_revision` and `latest_state_revision`, recomputed when the copy is verified.
- A fresh directory is bootstrapped only when `initialize_data_directory` creates the root (the call whose `mkdir` succeeded) and writes a marker listing no databases; the first open then creates and registers `sessions.db`. An existing directory without a marker is refused without any JSONL inspection (`database.md` -> Evolution contract, item 6). A process that loses a concurrent root-creation race and opens the store before the winner publishes its marker therefore fails with that error; there is no cross-process wait.

## Operator inspection

Runtime Session readers use `ChatSessionManager`. The bundled `vbot-docs` Skill's script `scripts/sessions.py` additionally reads the Session database read-only for extended Session search and transcripts, scoped by Project/Agent/Session, live generation, current view and canonical sequence; it mirrors that view logic in SQL and creates no other runtime storage owner, so a schema change to those tables updates the script and `tests/resources/skills/test_vbot_docs_sessions.py`.

`run_notifications` keeps each own Run's source Schedule, policy snapshot, delivery eligibility and read mark. Session notification policy lives on `sessions`; partial unread and source indexes keep result lookups bounded without sorting each Session's past. Migration `sessions.0008_run_notifications` adopts only the legacy latest completion and its known read state, never inventing unread history. Cron later attaches each saved `last_run_id` to its exact Schedule; earlier legacy Runs cannot be reliably assigned. The migration refuses older writers that would lose this state.
