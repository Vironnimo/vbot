# Session Runs, Tool calls and completion activity

Task-gated detail for `sessions.md`: how Runs, Tool calls and their result payloads, Stream drafts, change statistics and completion activity are stored, admitted, settled and recovered. Source: `core/sessions/_store_runs.py`, `_store_codec.py`, `_store_values.py`, `_store_queries.py`, `session.py`, `sessions.py`. Tests: `tests/core/sessions/test_sessions_runs.py`, `test_tool_result_payloads.py`.

## Runs and Tool calls

`runs` owns each execution: status, timing, work id, `start_seq` (the Session's `next_seq` at admission), `inherited`, `contributes_to_activity`, completion facts, and its `run_summary` entry (`end_entry_key`); `(status = 'running') = (completed_at IS NULL)` is a CHECK. Entries reference their exact Run by `run_key`. `tool_calls` holds one invocation per Assistant entry and ordinal with status, timing and the linked result entry (`result_entry_key`, unique); arguments, display and the stored-image references of the Result (`media_json`, a Tool message's `tool_media`) live in `tool_call_payloads`; arguments are stored with recursively sorted keys, the form Provider intake already gives every valid call (`providers.md`), so a stored call replays with the same bytes as the in-Run request. A call stays `pending` without timing while its Tool executes; the Tool-result append links exactly one stored call of the same Session (and Run, when given) and sets its terminal status (`ToolResultFacts`: `completed`, `failed` or `cancelled`; no facts means `completed`), timing and outcome in the same transaction; Run finish or restart recovery settles unfinished calls as `cancelled` or `interrupted`. A Tool that is currently running is visible only through Run events, never as stored state. `tool_result_payloads` holds Extension-attached result payloads per Tool call (`payload_id`, `owner_name`, JSON text): the Tool-result append inserts `ToolResultFacts.payloads` (`ToolResultPayload`) in the transaction that links the result, refusing the whole append for unsafe or duplicate ids, an empty owner or non-text JSON, and materialized copies copy them.

## Admission and settlement

- Run admission (`admit_run`, via `ChatSessionManager.start_run(run)`) commits in one transaction: it requires the named live generation when `SessionRunAdmission.expected_generation_id` is set; without that expectation it may create a missing live Session, which works in `SessionRunAdmission.working_project_id` (the Run's working Project; none for a Project Session). It then inserts the running row at the current `next_seq`, records the Run kind in `session_run_kinds`, and inserts the execution owner (`run_execution_owners`, `sessions/owned-execution.md`) when the Run has one. Re-admitting a running Run with the same owner and input is a no-op; a settled or inherited Run is rejected. `fork(..., run_kind=...)` records the fork's Run kind in its creating write, so a fork is classified before its Run starts. Admission and that fork label are the only ways a Session gains a Run kind.
- `finish_run` commits the `run_summary` entry, the terminal Run columns, the final change statistics when the completion carries them (replacing the stored ones; without them the Run keeps what it recorded while running), unfinished Tool calls (`cancelled` for a cancelled Run, else `interrupted`), deletion of the Run's Stream draft, the `completion_reason` of a cancelled or interrupted Run on its `run_summary`, the latest-completion columns (only for an activity-contributing Run), revisions and FTS together, and returns the committed Chat History cursor. Only then does Run management publish a persistence acknowledgement.
- Startup (`recover_interrupted_runs`) settles running non-inherited Runs of live Sessions as `interrupted` with `completion_reason` `process_restart`, keeping the change statistics they recorded, without replaying Model or Tool work. After the commit, `ChatSessionManager.recover_interrupted_runs` writes each settled Run's terminal line, which the Run manager never sees: `Run interrupted (run=... agent=... session=... [project=...] kind=... started=... iterations=... cause=process_restart)` at WARN on `vbot.sessions` (`runs.md`; `tests/core/sessions/test_sessions_runs.py`).

## Stream drafts

Stream draft rows (`sessions.md` -> Terms -> Stream draft) live in `run_stream_drafts` (`run_key`, `model`, `reasoning_delta`, `content_delta`, and `tool_calls_json` for the canonical Tool Calls that started with the chunk; `_store_runs.py`). Chat writes them through `ChatSession.append_stream_draft_async` and deletes them through `discard_stream_draft_async`; both require a running, admitted Run of the Session. Appending an Assistant entry of the Run deletes the draft in the same transaction, `finish_run` deletes what remains, and restart recovery turns a left-over draft into the Run's `interrupted` Assistant entry (concatenated chunks with their started Tool Calls in order, model of the last chunk, cause `process_restart`; those calls settle `interrupted` without Results) before it settles the Run. Chat's write discipline: `chat/run-execution.md` -> Interruption.

## Tool result payloads

`ChatSessionManager.tool_result_payload_async(address, payload_id, *, owner_name)` returns the decoded payload only when one with that id and owner belongs to a Tool call whose result entry is in the address's current view (own, inherited or materialized), else `None` (also for an unknown Session). It is one statement driven by `tool_result_payloads_by_id` (`test_store_query_plans.py`); its caller is the Extension host (`extensions/host.md` -> Tool result payloads); coverage `tests/core/sessions/test_tool_result_payloads.py`.

## Change statistics

- `record_run_changes` (`ChatSession.record_change_stats_async`, called by Chat after each Tool round that changed them) stores a running Run's change statistics so far: the `runs` change columns and one `run_change_paths` row per path with its own `lines_added`/`lines_removed` from `change_stats.file_stats` (NULL for Runs stored before per-file counts, whose summaries then omit `file_stats`). `finish_run` and restart recovery treat them as described under Admission and settlement.
- Rows of `list_summaries_page` and `summary` carry `change_stats` `{files, added, removed}` when the Session's own Runs changed files: sums over its non-inherited Runs (running ones with the statistics recorded so far, Runs a history edit removed from the view included), `files` counting each path once and at least as many as any one Run reported; `change_stats(address)` adds `file_stats` (up to 500 paths in path order, each summed over the Runs, counts `None` when a Run stored the path without them) for the Session information panel; `change_stats(address, merged=...)` counts the own Runs of further live Sessions as the Session's own (each path once, Sessions no longer live skipped), which `session.change_stats {include_subagents: true}` uses for the Session's Sub-Agent tree (answering `subagents`, the merged count). A fork's inherited Runs count only for their source.

## Completion activity

Completion activity is the latest-completion columns: `finish_run` sets them for activity-contributing Runs, and records the completion read at once when the summary's terminal Sub-Agent reply target is `parent` (the Run reported to its Parent, not to the user; user input switches the target to `user`, `subagents/forwarding.md`), returning `completion_read: true`, which the terminal Run event carries so live clients show no unread marker. `mark_terminal_run_read` writes (and fires completion-read callbacks, `sessions/titles.md` -> Callbacks) only when it marks the latest completion read. Clients reach it through `session.mark_read`; the WebUI sends that only while the result is on a visible, focused page (`webui/chat.md`), so a client's read mark means the user has seen the result. The latest completion and its read mark name `runs` rows of the same Session by integer key (`latest_completion_run_key`, `read_completion_run_key`); reads map them to the public Run id at the store boundary (`_store_values._COMPLETION_ACTIVITY_COLUMNS`), so RPC and WebUI keep the `latest_completion_run_id` key. A Run is deleted only with its Session, so the keys never dangle; they carry no SQL foreign key, which would scan `sessions` for every deleted Run. A fork starts without a completion and never names an inherited Run: marking an inherited Run's id read in a fork is a no-op. Ancestor-delete materialization copies Runs under new keys and leaves the descendant's completion columns untouched.

## Run reads

- `ChatSession.run_records(expected_generation_id=None)` returns the Session's own Runs (`inherited = 0`) in start order as `SessionRunRecord`s with status and completion facts; it raises `SessionNotFoundError` for a missing Session or another live generation. Statistics reads it after `load_since`.
- `ChatSession.reflection_runs()` selects, for each live direct review fork of this generation (`sessions.md` -> Terms -> Review fork), its first settled own Run by start sequence, including the review's own Agent/Project for opening and learning outcomes after source moves. Inherited (copied) Runs never count, so they cannot masquerade as review results.
