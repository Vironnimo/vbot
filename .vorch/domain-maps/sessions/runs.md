# Session Runs, Tool calls and completion activity

Task-gated detail for `sessions.md`: how Runs, Tool calls and their result payloads, Stream drafts, change statistics and completion activity are stored, admitted, settled and recovered. Source: `core/sessions/_store_runs.py`, `_store_codec.py`, `_store_tool_invocations.py`, `_store_values.py`, `_store_queries.py`, `session.py`, `sessions.py`. Tests: `tests/core/sessions/test_sessions_runs.py`, `test_tool_result_payloads.py`, `test_tool_invocations.py`.

## Runs and Tool calls

`runs` owns each execution: status, timing, work id, `start_seq` (the Session's `next_seq` at admission), `inherited`, `contributes_to_activity`, completion facts, and its `run_summary` entry (`end_entry_key`); `(status = 'running') = (completed_at IS NULL)` is a CHECK. Entries reference their exact Run by `run_key`. `tool_calls` holds one declared call per Assistant entry and ordinal with status, timing and the linked result entry (`result_entry_key`, unique); arguments, display and the stored-image references of the Result (`media_json`, a Tool message's `tool_media`) live in `tool_call_payloads`; arguments are stored with recursively sorted keys, the form Provider intake already gives every valid call (`providers.md`), so a stored call replays with the same bytes as the in-Run request. A call stays `pending` without timing while its Tool executes; the Tool-result append links exactly one stored call of the same Session (and Run, when given) and sets its terminal status (`ToolResultFacts`: `completed`, `failed` or `cancelled`; no facts means `completed`), timing and outcome in the same transaction; Run finish or restart recovery settles unfinished calls as `cancelled` or `interrupted`. `tool_result_payloads` holds Extension-attached result payloads per Tool call (`payload_id`, `owner_name`, JSON text): the Tool-result append inserts `ToolResultFacts.payloads` (`ToolResultPayload`) in the transaction that links the result, refusing the whole append for unsafe or duplicate ids, an empty owner or non-text JSON, and materialized copies copy them.

## Canonical Tool invocations

`tool_invocations` records dispatch admissions independently of Assistant declarations and Tool Results. Chat and ExternalRun commit one stable invocation key before publishing `tool_call_started` or entering the handler; rejected/unknown dispatches and the existing correlated refusal lifecycle also count, while declared work that never reaches that boundary does not. Run counters and Statistics count these admissions. Reused public call or Message ids do not identify ledger rows.

A start remains `running` with unknown result outcome until its exact Result commits. `ToolResultFacts.invocation_key` correlates that append by immutable key plus Session, Run, call id and name; a mismatch rolls back the entire append. Result commit supplies outcome and timing; cancellation, finish and restart recovery settle remaining starts as `cancelled` or `interrupted` without inventing successful or failed Results. Stop during admission waits for the start transaction and prevents subsequent handler entry.

The ledger is an own-audit fact: history edits retain it, moves and archive/restore keep the immutable Session key, inherited/materialized fork prefixes never copy it, and a recreated address starts with an empty generation. Start and settlement bump history/state revisions without adding entries or changing sequence/anchor; ordinary incremental History cursors stay valid. `ChatSession.tool_invocations_since(after_revision, expected_generation_id=...)` returns changed own rows and the current revision; a consumer applies rows by `invocation_key` and advances to the returned revision.

The bounded migration `sessions.0009_tool_invocations` imports only existing linked Results of own calls as dispatch evidence. It decodes valid historical envelopes when scalar outcome facts are absent, preserves malformed outcomes as unknown, excludes synthetic `tool_stopped` carriers, and never reconstructs resultless historical starts from Assistant declarations or cancellation status. Older writers are refused after migration because they cannot maintain this ledger; downgrading requires a compatible runtime or restoring a pre-migration snapshot.

## Admission and settlement

- Run admission (`admit_run`, via `ChatSessionManager.start_run(run)`) commits in one transaction: it requires the named live generation when `SessionRunAdmission.expected_generation_id` is set; without that expectation it may create a missing live Session, which works in `SessionRunAdmission.working_project_id` (the Run's working Project; none for a Project Session). It then inserts the running row at the current `next_seq`, records the Run kind in `session_run_kinds`, and inserts the execution owner (`run_execution_owners`, `sessions/owned-execution.md`) when the Run has one. Re-admitting a running Run with the same owner and input is a no-op; a settled or inherited Run is rejected. `create(..., run_kind=...)` and `fork(..., run_kind=...)` record the Session's Run kind in its creating write, so it is classified before its Run starts. Admission and these creation labels are the only ways a Session gains a Run kind.
- An ordinary Accessor input is claimed from queued to started in that same admission transaction, independently of Extension-owned input ids. An already consumed or removed receipt rejects a second Run; restart settlement never requeues a started input (`sessions/owned-execution.md` -> Ordinary Accessor inputs).
- `finish_run` commits the `run_summary` entry, the terminal Run columns, the final change statistics when the completion carries them (replacing the stored ones; without them the Run keeps what it recorded while running), unfinished Tool calls (`cancelled` for a cancelled Run, else `interrupted`), deletion of the Run's Stream draft, the `completion_reason` of a cancelled or interrupted Run on its `run_summary`, the latest-completion columns (only for an activity-contributing Run), revisions and FTS together, and returns the committed Chat History cursor. Only then does Run management publish a persistence acknowledgement.
- Startup (`recover_interrupted_runs`) settles running non-inherited Runs of live Sessions as `interrupted` with `completion_reason` `process_restart`, keeping the change statistics they recorded, without replaying Model or Tool work. After the commit, `ChatSessionManager.recover_interrupted_runs` writes each settled Run's terminal line, which the Run manager never sees: `Run interrupted (run=... agent=... session=... [project=...] kind=... started=... iterations=... cause=process_restart)` at WARN on `vbot.sessions` (`runs.md`; `tests/core/sessions/test_sessions_runs.py`).

## Stream drafts

Stream draft rows (`sessions.md` -> Terms -> Stream draft) live in `run_stream_drafts` (`run_key`, `model`, `reasoning_delta`, `content_delta`, and `tool_calls_json` for the canonical Tool Calls that started with the chunk; `_store_runs.py`). Chat writes them through `ChatSession.append_stream_draft_async` and deletes them through `discard_stream_draft_async`; both require a running, admitted Run of the Session. Appending an Assistant entry of the Run deletes the draft in the same transaction, `finish_run` deletes what remains, and restart recovery turns a left-over draft into the Run's `interrupted` Assistant entry (concatenated chunks with their started Tool Calls in order, model of the last chunk, cause `process_restart`; those calls settle `interrupted` without Results) before it settles the Run. Chat's write discipline: `chat/run-execution.md` -> Interruption.

## Tool result payloads

`ChatSessionManager.tool_result_payload_async(address, payload_id, *, owner_name)` returns the decoded payload only when one with that id and owner belongs to a Tool call whose result entry is in the address's current view (own, inherited or materialized), else `None` (also for an unknown Session). It is one statement driven by `tool_result_payloads_by_id` (`test_store_query_plans.py`); its callers are the Extension host (`extensions/host.md` -> Tool result payloads) and the `widget_states` check of `chat.send` (`tools/show_widget.md`); coverage `tests/core/sessions/test_tool_result_payloads.py`. `tool_result_payload_by_id_async(payload_id, *, owner_name)` loads a payload from whichever Session keeps it, for a holder of a server-issued capability over the id (the widget document route); copies of one payload share id and content.

## Change statistics

- `record_run_changes` (`ChatSession.record_change_stats_async`, called by Chat after each Tool round that changed them) stores a running Run's change statistics so far: the `runs` change columns and one `run_change_paths` row per path with its own `lines_added`/`lines_removed` from `change_stats.file_stats` (NULL for Runs stored before per-file counts, whose summaries then omit `file_stats`). `finish_run` and restart recovery treat them as described under Admission and settlement.
- Rows of `list_summaries_page` and `summary` carry `change_stats` `{files, added, removed}` when the Session's own Runs changed files: sums over its non-inherited Runs (running ones with the statistics recorded so far, Runs a history edit removed from the view included), `files` counting each path once and at least as many as any one Run reported; `change_stats(address)` adds `file_stats` (up to 500 paths in path order, each summed over the Runs, counts `None` when a Run stored the path without them) for the Session information panel; `change_stats(address, merged=...)` counts the own Runs of further live Sessions as the Session's own (each path once, Sessions no longer live skipped), which `session.change_stats {include_subagents: true}` uses for the Session's Sub-Agent tree (answering `subagents`, the merged count). A fork's inherited Runs count only for their source.

## Completion activity

Sessions owns per-Run read state and notification provenance through `SessionNotifications` (`notifications.py`, `_store_notifications.py`), backed by `run_notifications` in the same transaction as admission and settlement. A Run records its Schedule id when admitted; a manual Run in the same Session has no Schedule source. Completion eligibility (including silent delivery and Sub-Agent replies to the Parent) is separate from the source's `all` / `errors` / `muted` notification policy. Policy filters attention, never marks results read. Replaced History results lose eligibility; archived Sessions contribute no unread activity.

`session.mark_read` acknowledges exact completed own Run ids, including older results, with completion-read callbacks only for changed marks. A fork starts without unread results; inherited Runs do not acquire new read state. Reading the newest result leaves older unread results intact. The latest-completion columns remain a compatibility projection, while `notification_revision` (the Session state revision) orders current counters and read snapshots. Session counters include only non-Schedule results; local unread state includes both sources.

Schedule History uses descending Run keys and bounded keyset pages (default five, maximum 50). Bulk read acknowledges only completed results through a supplied Run key, so later fires stay unread. SessionActivity's supplied busy-Session snapshot filters visible attention without modifying stored read state. Current Schedule policy is applied by Cron; the stored policy snapshot preserves restart behavior.

## Run reads

- `ChatSession.run_records(expected_generation_id=None)` returns the Session's own Runs (`inherited = 0`) in start order as `SessionRunRecord`s with status and completion facts; it raises `SessionNotFoundError` for a missing Session or another live generation. Statistics reads it after `load_since`.
- `ChatSession.reflection_runs()` selects, for each live direct review fork of this generation (`sessions.md` -> Terms -> Review fork), its first settled own Run by start sequence, including the review's own Agent/Project for opening and learning outcomes after source moves. Inherited (copied) Runs never count, so they cannot masquerade as review results.
