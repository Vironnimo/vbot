# Session lifecycle APIs, lists and metadata

Task-gated detail for `sessions.md`: Session creation and lookup APIs, Session lists and summaries, batched reads, the metadata facade and its keys, prompt-state APIs and Recall visibility. Source: `core/sessions/sessions.py`, `_store_mutations.py`, `_store_queries.py`, `_store_values.py`, `_store_prompts.py`, `_metadata.py`. Tests: `tests/core/sessions/test_sessions_metadata.py`, `test_store_query_plans.py`.

## Creation and lookup

- Generated Session ids use `ses_` plus 12 lowercase base32 characters. Creation and forking allocate inside the SQLite write transaction, checking live and archived addresses in the destination scope; caller-chosen ids remain exact opaque values. The public facade returns the committed address (`store.py`, `tests/core/sessions/test_sessions_concurrency.py`). `new_session_id()` names a Session before it exists (`ses_` plus 16 characters, 80 random bits, no store claim); creating at an id that does exist fails instead of reusing it. Its callers are a Channel conversation that `/new` points at a Session its next message creates (`channels.md`) and a `chat.send`/`chat.stream` for a new Session with `@`-mentions, whose file snapshots need the Session id first (`server.md`).
- Creation returns a `ChatSession` bound to the generation from its creating transaction. `discard_unused(address, generation_id)` atomically removes only that live generation with no History entries and no recorded Run; its caller must hold the Run admission guard so pending admission cannot race cleanup.
- `existing_addresses(addresses)` answers existence for many addresses in one indexed statement per 300 addresses; callers must use it instead of per-address `exists` loops.
- `get_or_create` reads first and creates a missing Session in one write transaction. `ensure_metadata(address, mutation, create_missing=...)` applies an idempotent mutation against a read snapshot and enters the writer only for a real change or creation (reapplying the mutation to the latest row), so re-asserted routing state costs no write; its mutation may run twice and must be deterministic.
- `create(..., run_kind=..., metadata=...)` labels the new Session with a `RunKind` and merges the given open metadata (through `mutate_metadata`'s rules) in its creating write, so a background Session is classified, bound and titled before any reader sees it (a Librarian pass: Run kind `librarian`, `skill_agent_id`, `auto_title`, `automation/librarian.md`). Its Working Project argument: `sessions/ownership.md` -> Working Project.
- `create(..., actor=...)` logs `Session created` at INFO when a caller names who asked for it (`rpc` for `session.create` and a `chat.send`/`chat.stream` for a new Session, `command` for `/handoff` and a command that creates a new Session) and at DEBUG for Sessions created as a side effect of other work (triggered Runs, Sub-Agents); `delete_temporary_group` and `archive_temporary_group` log one INFO line with the Session count. Fork and other user-facing Session changes are logged by their only caller, the Session RPCs, and archive entries by the archive service (`logging.md`, `archive.md`).

## Metadata facade

- `mutate_metadata` and `mutate_metadata_with_previous` perform one transactional read-modify-write. Domain code must use them for partial updates; `set_metadata` is reserved for complete replacement and exact compensation snapshots. A metadata mutation whose persisted form is unchanged issues no `UPDATE`, so it neither fsyncs nor bumps `state_revision`; that column only feeds the snapshot manifest's `latest_state_revision` watermark and is not a per-change signal (`test_sessions_metadata.py`).
- The facade includes three managed values a write may repeat but not change (`Session metadata <key> is managed by Sessions`): `run_kinds` from `session_run_kinds`, `fork_source` = `{agent_id, session_id, project_id, forked_at}`, read through the direct parent's current row, so it follows the parent's renames and moves and disappears when the parent is deleted, and `working_project_id` (`sessions.md` -> Terms -> Working Project: the address Project, else the column; absent for the Workspace). Prompt-state keys (`seen_skills`, `prompt_cache_affinity_id`, `pinned_*`) are rejected (`Session prompt state has dedicated APIs, not metadata`).
- The facade key `agent_overrides` (an object, stored in the `agent_overrides_json` column; empty clears it) holds the Session Agent overrides, whose meaning and only writer belong to the Projects resolver (`projects/resolution.md`); forks copy it. The open key `skill_agent_id` (a string in `metadata_json`) binds a Session of the built-in Librarian to the Agent whose Skills it maintains; the Librarian service writes it and the Projects resolver reads it (`projects/resolution.md` -> Librarian Skill subject); forks copy it.
- Session Goal metadata: open key `goal` (`SESSION_GOAL_META_KEY`, owned by `automation/goals.md`) is stripped by forks; Session summaries (`list_summaries*`, `summary`) expose its `objective`, `status`, `pause_reason`, `turns` and `max_turns` as `goal`. `live_addresses_with_metadata_field(key, field, value)` lists live Sessions whose metadata object `key` holds `field == value` in one SQL read (the restart pause of active goals).
- Channel metadata keys are listed in `channels.md`.

## Prompt state APIs

`prompt_pin(address, slot)`, `ensure_prompt_pin(address, slot, value, accept)` (keeps an acceptable pin, else pins `value`; check and write share one transaction), `seen_skills(address)` (`None` before the first record), `record_seen_skills(address, SeenSkillsUpdate(baseline, added))` (seeds from `baseline` on first use, then adds `added`; an addition that changes nothing writes nothing) and `prompt_cache_affinity_id(address)`. The affinity id is the `prompt_cache_affinity_id` column; while that is NULL, `prompt_cache_affinity_id(address)` derives a deterministic default from the address. Unreferenced prompt blobs are deleted in the transaction that drops their last reference. `metadata_value(address, "seen_skills")` reads `None`, because prompt state is not in the facade; use `seen_skills(address)`.

## Lists and batched reads

- `list_summaries_page` is the bounded accessor read model: one SQLite transaction globally orders one or many Agent scopes, applies execution-category and Channel inclusion filters (a Session with a `librarian` Run kind is listed only in the global scope of the built-in Librarian, where it is an ordinary conversation, and never elsewhere whatever the filters, which hides the pass Sessions an earlier vBot left in the curated Agent's scope; a Session with a `live` Run kind likewise only in the global scope of the built-in Live voice or Live backend Agent; `_LIST_VISIBILITY_LIBRARIAN`), returns a keyset cursor and total count, and may add one explicitly required selected Session without letting it alter cursor progression. Channel filtering uses the existing platform plus conversation-id metadata, applies before counts/pagination, and defaults to inclusion at the service/RPC edge; the WebUI explicitly opts out.
- `list_summaries` returns only normalized list/completion columns plus explicitly requested `metadata_keys`, of which only `seen_skills` exists (derived from the seen-Skill relation, name-ordered, present only once recorded). The Agent-facing Search Tool has no listing mode. There is no full-metadata listing.
- `newest_session_id(agent_id, project_id)` is the landing read after a Session leaves its scope: `list_summaries_page(limit=1)` with every run kind included and Extension-owned Sessions excluded. `list_addresses(project_id, agent_id=...)` lists bare addresses of one scope or one Agent. `metadata_value(address, key)` (async: `metadata_value_async`) returns one facade value from the Session row (`None` when absent; prompt state is not in the facade).
- `list_completion_activity(scopes)` reads many `(project_id, agent_id)` scopes in one statement per bounded chunk (a scope `VALUES` join on the live address index) and maps each scope to its live Sessions that have a latest completion, selecting only completion columns; Sessions without a completion are omitted. `summary(address)` point-reads one live Session's list row (`None` when absent). Every row of `list_summaries_page` and `summary` carries `working_project_id` (`null`: the Workspace), and `agent_overrides` (the Session Agent overrides) when the Session stores any; their `change_stats`: `sessions/runs.md` -> Change statistics.
- Bounded current User entry counts (`active_user_message_count`) and newest prefixed Note lookup (`latest_note`) are direct SQL reads over the current view. `descriptor_sources(addresses)` returns, in set-oriented reads, each live Session's metadata facade and Recall visibility (`SessionDescriptorSource`). `recall_context(address, message_id)` reads only the enclosing current User question and final Assistant answer, with text bounded in SQL and no full-history hydration.
- `list_history_versions(addresses)` resolves generation plus revision for many addresses in one query per scope; Statistics refreshes its freshness stamps with it, because comparing revision alone is insufficient. Those stamps hold only for one history: `history_id` (Session database identity plus `Database.restore_id`) changes when a restore brings back older history, after which a Session can reach a stamped generation and revision again with other content; Statistics and Recall reread every Session when it changes. `list_history_revisions(agent_id, project_id)` returns every live Session's generation, revision, Recall visibility and creation order (its `session_key`, larger is newer) for one scope in one query; Recall uses the creation order to attribute inherited Passages to the newest Session that shows them, the same rule as store search.

## Recall visibility

Recall visibility (`SessionRecallVisibility`) is classified in SQL from the visibility mask column, so callers never classify metadata in Python: reflection and `librarian` Run kinds make a Session `hidden`; otherwise a Sub-Agent flag or Run kind makes it `subagent`; otherwise a Session without recognized Run kinds or with a user-facing Run kind (`user`, `channel`, `cron`, `calendar`) is `conversation`; anything else (system-only, memory, Skill) is `hidden`. `recall_visibilities(include_subagents=...)` names the admitted values. `list_live_scopes()` names every `(project_id, agent_id)` scope with a live Session in one read, so Recall's background indexing walks scopes without listing Agents. Message search (`search_messages`) applies it to the eligible Sessions before any candidate is checked.
