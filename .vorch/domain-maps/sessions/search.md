# Session search and FTS

Task-gated detail for `sessions.md`: the integrated FTS indexes, their upkeep and rebuild, and `search_messages`. Source: `core/sessions/_store_search.py`, `_store_fts.py`, `schema.py` (FTS DDL and membership SQL), `store.py` (`search_messages`, write retry). Tests: `tests/core/sessions/test_session_fts.py`, `test_store_query_plans.py`, `test_lineage_model.py`. Recall's use of this search: `recall.md`.

## Indexes

- Both indexes are disposable external-content FTS5 tables over views of the entries that are current in some Session's view (`FTS_MEMBERSHIP_SQL`): `searchable = 1`, and either not superseded or still admitted by some descendant's lineage segment. The rowid is `entry_key`, so each stored entry is indexed once however many Sessions show it. There is no mirrored search-text table.
- `entries_fts` (tokenizer `unicode61`) over `entries_fts_source`: text (`content`) and User block text (`search_text`: text blocks, attachment names and types, an audio block's transcription, mentioned paths), the only columns search MATCHes (`{content search_text}`) and the literal check reads. Assistant reasoning, Tool names and arguments and error kinds are not indexed: the pre-Generation-1 index stored them but search never matched them. Making Tool calls searchable later is a derived-index change: extend the source view (or add a per-call index keyed by `call_key`), widen the MATCH and literal check, and bump `FTS_STORAGE_VERSION` so every store rebuilds from canonical tables.
- `entries_fts_trigram` over `entries_fts_trigram_source`: `content` and `search_text` of `FTS_TRIGRAM_ROLES` (`user`, `assistant`, `compaction_checkpoint`) entries that have text, so bulk Tool output is not indexed twice. SQLite builds without the trigram tokenizer create only the standard index (`FTS_SQL_FALLBACK`).
- `searchable` is decided at append from `search_content.message_is_searchable`; canonical text extraction and role policy have that one Sessions-owned home, also used by Recall. Only conversation roles (`user`, `assistant`, `tool`, `error`, `compaction_checkpoint`), never persisted Recall results (`session_search`/`session_read` Tool results) or `[skill-context]` Notes, and only entries with content. An Assistant entry with only reasoning or Tool calls is not a member.

## Upkeep

- One rule keeps both indexes exact: before a change can end an entry's membership, forget its rows through the source view (`fts_forget`, `fts_forget_keys`), which still returns the indexed values; after the change, index the same candidates again (`fts_index_keys`), and the view admits only those still members. Appends, `finish_run`, materialized copies, history edits and deletion follow it (`sessions/lineage.md`).
- Writers maintain the indexes only while they exist and no rebuild is pending (`_fts_writable`). A write that fails with an FTS error detaches both indexes (drops them, sets the stale marker and a degraded reason in `store_meta`) and the canonical write is retried once without them, so a derived-index failure never blocks canonical persistence (`store.py` `_execute_write`). An FTS error names FTS in its message or reports a corrupt virtual table (`SQLITE_CORRUPT_VTAB`, `_is_fts_failure`): the indexes are the store's only virtual tables, and SQLite reports damaged index storage as a malformed database image without naming the index. Open-time health skips FTS5's internal integrity check, so such damage surfaces at the first write or search that reads it; the next open rebuilds the detached indexes.
- Rebuild runs in the spec's `after_open` hook (`_ensure_fts_schema`): recreate missing or unsupported indexes, then backfill in committed windows of 500 entry keys with generation plus target/completed high-water marks taken from `sqlite_sequence` (keys are `AUTOINCREMENT`, never reused), resumable after interruption, and clear the stale marker only after an explicit standard and trigram coverage check. Each step is one `BEGIN IMMEDIATE` transaction - replacing the indexes with the rebuild markers, every window with its progress markers, the coverage check with clearing the markers - because the hook's writer commits every statement outside an explicit transaction on its own (`database.md` -> Conventions -> Transaction control); an interruption leaves the last committed step whole (`test_fts_rebuild_resumes_after_an_interruption_from_its_last_whole_step`). Interruption reports rebuilding/degraded state, never healthy incompleteness.
- Version rule: the indexes are trusted only when `store_meta` `fts_storage_version` equals the code's `FTS_STORAGE_VERSION` (1). Any other value, missing, older or newer, marks FTS degraded and the next open drops and rebuilds both indexes from canonical tables. The comparison is deliberately `!=`, not `<`: a newer version means a later build wrote an index this build cannot read, and because the indexes are derived, rebuilding is always safe, so a downgrade never needs a migration. Bumping `FTS_STORAGE_VERSION` is how an index change forces every store to rebuild (`test_only_conversation_text_is_indexed_and_a_foreign_index_version_rebuilds`).
- Ordinary search availability and the data-store status health hook trust the lifecycle/version/stale/high-water markers and never run canonical coverage anti-joins. Startup repair and explicit `fts_health()` checks own coverage validation; data snapshot verification does not check FTS coverage. `data_store.status {verify_search: true}` requests that explicit check on the Session database's pool before returning status; `vbot data-store status --verify-search` exposes it online and offline.
- Operator status is the kernel's `data_store_status` (`database.md`). The Session member reports `degraded` with a `Session search: ...` reason and `fts` details when the search index is not healthy; details contain no Session content.
- `SessionStore`'s internal `SessionHealth` (`_store_health.py`) retains the last explicit coverage result in memory, with its completion timestamp and index generation. Status exposes it as `details.fts.last_coverage_check` (`null` until checked in this store's lifetime; offline status has none unless explicitly checking). It is historical evidence, not a claim that later writes were checked. A known coverage failure remains degraded until a successful explicit check or another index generation; lifecycle degradation always remains visible. Status and checks write no evidence to the database, and a pending check never holds the evidence lock while scanning.

## `search_messages`

`ChatSessionManager.search_messages` retains the public keyword interface and builds one internal `SessionSearchRequest`; the store and query executor pass that request intact. It owns whitespace normalization, literal matching, FTS expression/trigram preparation and timestamp normalization.

- Returns a typed `SessionSearchResult` of exact hits (`SessionSearchHit`: address, Message id, role, timestamp, matched text, rank) plus `complete`, `method` (`fts`/`scan`) and `fallback_reason`. Results are bounded by `limit` (default 1,000).
- Eligible Sessions (one `MATERIALIZED` CTE): live Sessions of the requested Project scope (the Identity scope for `project_id=None`) whose Recall visibility the request admits, optionally one Agent and one Session, minus excluded Session ids. Candidates are the current entries of eligible Sessions: their own non-superseded entries and the ancestor entries their lineage admits, filtered by role and time before any candidate is checked. Each stored entry is one candidate, so a fork never duplicates its origin's hits.
- An FTS search checks only its hits against that set, each by its key (`_IS_CURRENT`: the owner is eligible and still shows the entry, or a lineage segment of an eligible Session admits it; only entries of Sessions that eligible ones inherit from reach the lineage check), so its cost follows the number of hits, not the size of the store. A scan enumerates the set (own entries `UNION` inherited ones).
- Attribution (`_REPORTED_SESSION`): a hit is reported for the Session that stores the entry when it is eligible and the entry is not superseded; otherwise for the newest eligible Session (highest `session_key`) whose lineage admits it.
- Index choice: a request uses the trigram index only when every requested role belongs to `FTS_TRIGRAM_ROLES`, every term (or the phrase) has at least 3 characters and the trigram index exists; everything else uses standard whole-token FTS. A standard miss never retries trigram. FTS queries keep the query's Unicode spelling for SQLite's tokenizer (for example a German sharp s); Python case folding belongs only to the literal candidate check, not the FTS expression (`test_fts_query_keeps_unicode_tokenizer_spelling`).
- FTS only enumerates candidates: by bm25 rank (one full `MATCH` scan keeps bm25 statistics whole-index; equal ranks break by recency, then key) or by `created_at` for newest/oldest. Each candidate's conversation text (`COALESCE(content, search_text)`; roles outside the Recall conversation roles and persisted Recall results read as empty) is checked with the literal case-insensitive matcher before it counts, so results are full whenever enough matches exist. Candidates are checked in keyed batches (16-256) that never split a rank; at most `_SEARCH_CANDIDATE_LIMIT` (10,000) are checked, and a result that budget cut short is `complete=False`.
- Fallbacks: a healthy FTS miss that excludes Tool rows returns empty without scanning. A Tool-inclusive FTS miss scans with `fallback_reason` `tool_inclusive`; an unavailable index scans with `fts_unavailable`; a SQLite error during the FTS search scans with `fts_error`, and detaches the indexes first only for an FTS error (Upkeep; `test_a_failed_fts_search_scans_instead_and_detaches_only_a_failed_index`); `use_fts=False` scans directly. Scans order eligible current entries by `created_at` (relevance scans newest first) under the same matcher and budget.
- Time filters (`since`/`until`) canonicalize their input and compare stored canonical text, so `Z`, `+00:00`, equivalent offsets and fractional precision stay equivalent (`test_time_filters_compare_exact_instants_across_timestamp_encodings`).
