# Session history API

Task-gated detail for `sessions.md`: history appends and reads, the `ChatSession` handle, read cursors, the Chat History snapshot, the Compaction commit, Sub-Agent reply targets, deferred Notes, the Skill activation cache and the Session write lock. Source: `core/sessions/session.py`, `sessions.py`, `_store_history.py`, `_store_timeline.py`, `_store_operations.py`, `history.py`. Tests: `tests/core/sessions/test_sessions_history.py`, `test_timeline_snapshot.py`. History edits: `sessions/lineage.md` -> History edit.

## Appends

Appends are transactional: `append_messages` writes the entries at `next_seq`, then updates `next_seq`, `last_activity_at` (the last Message's canonical timestamp), `last_entry_id`, both revisions and the FTS rows in the same commit. Plain appends accept `system`, `user`, `assistant`, `tool`, `note`, `error`, `compaction_checkpoint` and `agent_takeover`; other roles are written by their Session operation. A Compaction checkpoint without a projection is rejected. An `agent_takeover` raises `cursor_floor_seq` past itself.

## ChatSession handle

`ChatSession` is a path-free handle: `append`/`append_many`, `load` (own audit), `load_active` (current view), `commit_compaction`, `apply_edit`, Stream draft writes, Notes, Skill activation state, and `load_since(cursor)`. `append_many(messages, *, tool_results, seen_skills, subagent_reply_target, since)` and owned receipt appends return the `load_since` delta for a given cursor within their write transaction. Frequent partial consumers use dedicated read models instead: one atomic Chat History snapshot, the status aggregate, targeted Run summary/result lookup (`load_run_result`/`load_run_result_async`), and the manager's `tool_result_persisted_async` probe (an Assistant Tool call stored in the live Session and its durable result, via `tool_calls_by_call_id`; calls a fork inherits through lineage do not count). Async counterparts execute through bounded worker pools at their owning boundary.

## Read cursors

`SessionReadCursor` carries generation id, history revision, next sequence and the prior entry id anchor. `load_since` returns `None` so disposable consumers rebuild when the generation differs, the cursor's history revision is below the Session's `cursor_floor_revision` (raised when an Identity Agent rename rewrites stored Skill package owners, Skill activation cache below), `next_seq` is out of range or below `cursor_floor_seq` (after an edit or Agent takeover), or the entry at `next_seq - 1` has another id; other revision changes do not end a cursor (`_store_history._cursor_continues`). A current cursor returns an empty delta from the Session row alone; otherwise one read returns `SessionReadBatch(messages, cursor, active_messages, inherited_count)`: `messages` are the own-audit entries after the cursor, `active_messages` the current view after it, and a fork's own conversation is `active_messages[inherited_count:]`.

## Chat History snapshot

- `read_chat_history_snapshot` returns a consistent page or bounded append batch over the current view with Usage, editability, record sequence, stored Run membership and explicit Run completeness. `after` is a generation/next-sequence cursor; hidden rows advance it. Excluding `note` keeps the Notes that carry a Model fallback record (the Run's display notice), and Run completeness counts them as visible records (`_store_timeline.py`). An edit/takeover floor or generation mismatch forces a replacement snapshot. An incremental read covers at most `limit` (500 without one) sequences after the cursor. With `skip_unchanged`, an `after` cursor already at the Session's end returns an `unchanged` snapshot from the Session row alone: an empty page and no Usage, Context messages or background records. Callers request background-status candidates by Tool names plus a Note content marker; the snapshot then carries only narrow `SessionBackgroundRecord(role, name, content)` rows for matching current Tool Results and Notes, limited to the appended range for an incremental read. `before` independently pages older history; its cursor anchors the first returned visible entry, even when complete-Run expansion includes a hidden Note prefix (`test_timeline_snapshot.py`). Page expansion uses native Run starts (`runs.start_seq`). A page selects narrow sequence/key rows first and reads full records by key; its Run descriptions are ordered by Run start sequence. `load_run_result` and `load_run_messages_async` query exact Run membership; consumers must not infer ownership from preceding footers or Message coverage.
- Timeline Run completeness uses only a terminal summary visible in the requested history view, so detaching a fork after its source is deleted preserves that fact.
- `status_snapshot` reports the current view's first entry time, User count and latest Assistant Usage, plus the Session's own spend.

## Compaction commit

`commit_compaction(checkpoint, *, since, epoch: PromptEpoch)` appends a `compaction_checkpoint` only while `since` still names the newest entry (same generation, at or above the cursor floor, same `next_seq` and last entry id); otherwise it writes nothing and returns `None`. In the same transaction it replaces the named prompt pins (`epoch.pins`; `None` removes a slot), replaces the seen Skills when `epoch.seen_skills` is given, and leaves the prompt-cache affinity id unchanged; it returns the delta after `since` as a `SessionReadBatch`.

## Sub-Agent reply targets

`append_many` and `apply_edit` with `subagent_reply_target="user" | "parent"` commit the selected recipient with the input, only for a linked Session. Every new entry and terminal Run summary snapshots the current target in `entries.subagent_reply_target`; ordinary Sessions leave it null. This internal Message field never enters Provider requests or public payloads. Migration `sessions.0003_subagent_reply_targets` maps the historical takeover timestamp to user replies once, preserving explicit targets (`subagents.md`).

## Deferred Notes

Deferred Notes stay in the Session handle's retry batch until a write commits. `take_deferred_notes` snapshots that batch and ends deferral without clearing it; append, edit and flush acknowledge only committed Note ids, preserving Notes added during the write. Chat's snapshot commit acknowledges transaction-returned Messages too, including owned receipt writes that bypass the handle. The separate pending-Context delivery buffer is unchanged. Coverage: `test_deferred_notes_keep_their_existing_ordering` (`test_sessions_history.py`).

## Skill activation cache

- The Skill activation cache is synchronized from the supplied current history snapshot when one is provided and otherwise preserves explicit in-memory registrations; a committed Compaction checkpoint resets the epoch from its own appended batch, since the checkpoint is then the newest entry. `apply_edit` drops the cache. A cache miss reads only current `[skill-context]` Notes and `skill` Tool Results after the newest current checkpoint (`current_skill_activation_messages`), never the full history, so edited-away checkpoints and activations cannot leak into it.
- Skill Tool carriers optionally include `resource_files.directory`; `skill_tool_activation` passes it to the shared resource formatter so restored activations match live ones. Older carriers without it retain their original resource paths and context. Coverage: `test_sessions_history.py::test_skill_activation_cache_follows_checkpoints_and_history_edits` (no resources, older resources, directory-bearing resources).
- Skill activation carriers keep optional internal `skill_package` identity in nullable entry columns; old entries remain unqualified. Cache deduplication compares both instructions and package. An Identity Agent rename retargets only exact private-package owner refs, also in other Agents' Sessions, and increments affected own/inherited history revisions plus `cursor_floor_revision`; older `SessionReadCursor`s require a full reread while newly issued cursors continue. Request-history snapshots then refresh activation caches. No Model-visible content or public timeline field changes. Coverage: `test_sessions_history.py`.

## Write lock

`write_lock(address)` is context-reentrant for a holder and child tasks. Inside a `SessionWriteLeaseScope` (entered by one task), a lease that task takes is also joined by tasks whose context carries the scope but were started before the lease existed; Chat uses it so Tool Calls started during the Model stream can write to their Session while Chat holds the lock and waits for them (`chat/run-execution.md` -> Tool Calls during the stream). Waiters re-check after every release, so a task already waiting joins as soon as the shared lease appears. It protects ordered Chat boundaries and whole move/fork/archive operations; Provider latency and other unbounded work stay outside it. Locks are manager-owned and released with manager lifetime. Session write locks are weakly retained while callers hold or await them; releasing the last caller also restores its prior ContextVar state. Neither the manager nor an idle task context accumulates one permanent lock record per used Session.
