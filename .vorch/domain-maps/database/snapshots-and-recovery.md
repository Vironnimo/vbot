# Snapshots and recovery

The data-store marker and guard formats, data snapshots, canonical open with automatic restore, recovery incidents, quarantine, staging, operator restores, unregistering and retiring databases, the update rollback, data-store status and the kernel's log lines: their files, APIs and procedures. How an online capture stays consistent is `snapshot-consistency.md`; configuration backups are `config-backups.md`.

`recovery.py` coordinates quarantine, probing and restores; `_incidents.py` owns incident documents, acknowledgement and restore ids. `snapshots.py` owns inventory, capture and retention; `_snapshot_manifest.py` owns snapshot records and manifest parsing, and `_snapshot_verification.py` verifies database copies and their manifest claims. The existing snapshot and recovery APIs remain available from their public modules.

## Files

- The marker `<data-dir>/data-store.json`: `{"format_version": 1, "databases": {"<name>": {"database_id": "<32 hex>", "format_generation": N}}}`, written atomically; register and unregister keep unknown fields at the top level and in every entry (`DataStoreMarker.unknown_fields`, `MarkerEntry.unknown_fields`). The maintenance guard `data-maintenance.json` (`operation_id`, `operation`, `started_at`, `pid`) exists while an offline operation is incomplete; `maintenance_locked(resume=True)` lets a repeated operation take over its own guard, and `replaces=<operation>` another operation's guard in the same atomic write (a configuration restore replacing an unfinished one, `config-backups.md`). A guard that cannot be parsed reads as `damaged` with operation `unknown`; nothing resumes or replaces it, so `require_no_maintenance` and taking over the guard refuse it with the way out: delete the file by hand, then, if in doubt, restore a data snapshot or configuration backup (only these restores hold the guard). The operation lock `data-store.lock` is OS-owned: crash-released, never broken by age, exclusive across threads and processes.
- Snapshot layout: `<data-dir>/snapshots/<YYYYmmddTHHMMSSZ-uuid8>/` with one `<name>.db` member per canonical database registered in the marker, the JSON document set under `documents/<relative path>`, and a `manifest.json`. The JSON document set is every existing file matching `core.json_documents.SNAPSHOT_DOCUMENTS` (which kinds: `../json-documents.md` -> Snapshots and doctor); symbolic links, Windows junctions and names starting with `.` (staging files) are never members.
- Generated snapshot manifests and incident records use LF line endings on every platform, including Windows.
- Restore guards also record an optional `scope` object: a data snapshot restore binds its snapshot id, selected database set, document-set flag and unlisted-database retirement flag. Planning and mutation both require the same recorded scope to resume; changed selections and snapshot ids leave the guard and data untouched. An interrupted snapshot restore without recorded scope needs operator recovery: keep the server stopped, inspect the interrupted restore, remove the named guard by hand, then perform a complete restore from a verified snapshot. Configuration restore replacement rules remain in `config-backups.md`; guard rewrites preserve unknown top-level fields.
- The marker, snapshot manifests and incident records evolve additively like the databases: readers require the known fields, ignore unknown ones, and refuse a marker `format_version` or manifest `manifest_version` other than 1 (incidents carry no version); a record that is rewritten keeps the unknown fields it read, so an older vBot never drops what a newer one added.
- Snapshot manifest (`manifest_version` 1) members record identity, generation, applied migrations, size, SHA-256, `quick_check`/`foreign_key_check` results and owner facts. The required `documents` key maps each document's relative POSIX path to `{file_size, sha256}` (`{}` when none existed); a manifest without it is not a snapshot. A manifest is written once and never rewritten; another `manifest_version` is not a snapshot, and a document path outside the current `SNAPSHOT_DOCUMENTS` (a document kind a newer vBot added) is ignored: never verified, counted, restored or removed.
- Document copies keep their source's permission bits, read-only included: `_files.fsync_file` syncs a read-only file (on Windows by lifting the read-only bit for the sync and setting it back), the cleanup of a disturbed or failed attempt and retention remove snapshot trees with `remove_tree` (`core/utils/tree_move.py`, read-only aware, never follows links), and a set restore installs each document with its copy's bits (`tests/core/database/test_snapshot_documents.py`).
- Attempt health: `snapshots/health.json`.
- Incidents: `<data-dir>/incidents/<name>.json`, `pending` before anything is replaced, `ok` once the restored file verified; completing or acknowledging one keeps unknown fields at the top level and in `possible_loss_interval`.
- Quarantine: `<data-dir>/quarantine/<name>/<YYYYmmddTHHMMSS>-<uuid8>/` holding the database file plus sidecars, and `quarantine/json-documents/<stamp>-<id>/<relative path>` holding documents a set restore replaced or removed; never deleted automatically (`json-documents` can never be a database name).

## Interfaces

- Snapshots and recovery: `create_data_snapshot(data_dir, *, reason, databases=(), specs=(), cancelled=None, barrier=None) -> Path | None`; `restore_data_snapshot(data_dir, snapshot_dir, *, specs=(), names=None, documents=False, retire_unlisted=False, cause=..., check_only=False) -> SnapshotRestore(snapshot_id, databases, documents, retired, registered)` (`names=None` selects every member; `documents` adds the JSON document set; `retire_unlisted`, only with every member, quarantines and unregisters databases registered after the snapshot; a selected member whose name is no longer registered is installed and registered again with the snapshot's identity (`registered`), while one registered under another identity is refused; nothing selected is `ValueError`); `unregister_database(data_dir, name) -> UnregisteredDatabase(name, database_id, quarantine)` releases one Extension database; `retire_core_databases(data_dir, names) -> tuple[UnregisteredDatabase, ...]` releases core databases whose owner was removed (both: Unregister and retire); `remove_interrupted_staging(data_dir)` removes what killed snapshots, restores and database creations left (Staging); `describe_missing_databases(data_dir, marker) -> str | None`; `acknowledge_incident(data_dir, incident_id) -> bool` (raises `IncidentConflictError` when a newer incident replaced the observed one); `list_data_snapshots`, `snapshot_summaries`, `read_verified_manifest`, `read_snapshot_health`, `active_incidents`.
- `remove_retired_document_copies(data_dir, patterns) -> int` deletes copies of documents the current document set no longer holds (OAuth token files an older vBot captured before the Secret Store) from every snapshot under the operation lock; manifests stay as they are, since the current reader leaves unknown documents out, so every snapshot stays usable here. A version that still knows those documents finds them listed but missing and treats the snapshot as damaged (`secrets.md` -> Constraints & Gotchas).
- `snapshots.read_retained_snapshot_members(data_dir, name, read)` lets an owner read its member in every retained snapshot through read-only connections under the operation lock. It checks each published manifest and member identity, generation and migration ledger without rehashing immutable copies. An unavailable or malformed published snapshot raises instead of becoming an empty root set. Attachment collection uses the Session owner's decoder so images remain available after restoring older retained history (`attachments.md`; `test_snapshot_member_reads.py`).
- Update rollback (`update_rollback.py`): `create_update_snapshot(data_dir, *, operation_id, specs=(), retain_as=None) -> UpdateSnapshot | None` (`None` when no database is registered; raises `DatabaseError` when it cannot be taken or the data changed during capture); `data_changed_since(data_dir, snapshot) -> str | None`; `restore_update_snapshot(data_dir, snapshot, *, specs=(), cause=UPDATE_ROLLBACK_CAUSE) -> SnapshotRestore`; `find_update_snapshot(data_dir, operation_id) -> str | None`. The caller proves that no server runs on the data directory; the module proves the data side.
- Status: `data_store_status(data_dir, *, databases=(), specs=(), secret_store=None)` (Status).
- Offline specs: `core/runtime/databases.canonical_database_specs(data_dir)` serves the offline tools - CLI status and restore, the updater worker's snapshot and rollback - which run the code that wrote the data (`../database.md` -> Interfaces).

## Canonical open and automatic restore

- Canonical open: the maintenance guard refuses first; no marker is `DatabaseConversionRequiredError`; a listed database that is missing, corrupt (`DatabaseCorruptError` or a file SQLite cannot read as a database), or has another identity is auto-restored from the newest verified snapshot member with the same `database_id`, else the error surfaces; a file that cannot be checked or opened for an operational reason (permission, I/O, an unresponsive share) is `DatabaseUnavailableError` and is never restored over, because it may hold newer data than any snapshot (the probe in `recovery.py` and `_open_canonical` check presence with `exists_strict`, PROJECT.md -> Conventions -> Filesystem checks); a format error or schema mismatch surfaces without quarantine or restore, and the locked re-probe of `auto_restore_if_needed` independently treats a schema mismatch as untouchable, because an older snapshot would silently drop the newer rows; that re-probe also re-reads the marker and restores nothing unless the database is still registered with the expected `database_id`, so an open racing an unregister cannot bring the database back; an unlisted database is created (or an existing unlisted file adopted after full open checks) and registered under the operation lock, so new owners stay additive.
- Recovery stages the verified member bytes before it publishes a `pending` incident or quarantines anything; quarantine moves the bundle all-or-rollback, and a failed rollback keeps the moved members and reports their path. An operational verification, copy, quarantine or publication failure stops candidate fallback instead of trying an older snapshot. A retry keeps the original quarantine reference and failure time, and a pending incident finalizes only when the canonical file matches the intended snapshot member. Malformed incident evidence, including a non-canonical timestamp, is corruption, unreadable evidence is unavailability, and the possible-loss interval stays visible until the exact incident is acknowledged.
- Retrying an interrupted restore retains its incident identity and original quarantine, but extends the possible-loss interval through the retry's failure detection: pending evidence cannot prove that no later writes occurred. Merely confirming an already installed snapshot preserves the original interval.
- Automatic restore uses pending incidents, not the maintenance guard: a crash mid-restore resumes on the next open. It never replaces a database a newer vBot changed and never picks an older snapshot after a newer candidate failed operationally. An operator restore (`restore_data_snapshot`) holds one operation lock from planning through maintenance-guard removal, so another restore cannot resume its live guard or change registrations after validation; a failed one leaves the guard so Runtime refuses the half-restored directory until a restore completes. An optional `before_restore` callback runs after planning under that guard and lock, before any replacement, to admit a fresh restore against application-owned live-server/data checks. Its failure removes only the fresh guard and leaves data untouched; it cannot resume an existing guard, and `check_only` skips the callback.
- Restore identity mechanics: `Database.restore_id` is the `incident_id` of `<data-dir>/incidents/<name>.json` when the canonical database opened (`recovery.latest_restore_id`), `None` without an incident and for offline or disposable handles. Every restore path (automatic, operator, update rollback) publishes a new incident id before quarantine and swap; resuming, completing and acknowledging keep it; incidents are outside snapshots and never pruned. The id therefore changes exactly when a restore began: one that stopped before the swap, or an operator deleting the incident file, changes it without new content, which costs a consumer one extra rebuild, never a stale projection. A file replaced outside the kernel keeps its id; only a consumer's own revision-rewind check notices that (`tests/core/database/test_recovery.py`).

## Snapshot creation and retention

Snapshot creation copies open databases online through their handle and unopened registered ones from their files, and reads each JSON document whole in one short open, in the capture order (`snapshot-consistency.md`); then, after the freeze, it syncs every copy to disk and verifies every member and document before atomic publication (with the shared bounded Windows sharing-violation retry), and prunes by `SNAPSHOT_KEEP_COUNT` (5) / `SNAPSHOT_KEEP_BYTES` (10 GiB) always keeping the newly published snapshot and never rehashing retained ones; the byte budget never prunes below `SNAPSHOT_KEEP_MINIMUM` (2) snapshots, so a Session history larger than half the budget still keeps one fallback (decision 2026-10-05: a 2 GB `sessions.db` had left a single snapshot under the former 512 MiB budget).

`create_data_snapshot(..., retain_as=<owner>)` publishes a named retention claim atomically under the capture operation lock, before pruning. `snapshots/retention.json` stores version 1 with an `owners` map from owner ids to snapshot ids and preserves unknown record fields. Count/byte pruning and free-space reclamation keep every claimed snapshot; owners release their own claims with `release_snapshot_retention`. A missing record means no claims, while an unreadable or malformed record refuses cleanup and snapshot creation. Application updates use operation ids as owners and retain the snapshot paired with the previous application payload, plus unresolved recovery snapshots.

Before copying, a snapshot removes the staging of killed attempts (Staging) and then needs its size plus `SNAPSHOT_RESERVE_BYTES` (64 MiB) of free space; when the disk still lacks it, `_make_room` removes the oldest unclaimed snapshots, never the newest or a named retention claim, and logs one INFO line naming them; without enough room even then the attempt fails with `insufficient snapshot reserve`.

Owner facts (`DatabaseSpec.snapshot_facts`: fact name -> SQL returning one integer) are recorded per member at capture and verified only when a matching spec is supplied, and only the facts the member recorded (a member written before a fact was declared still verifies); a recorded fact the spec cannot compute on the copy is a `DatabaseSchemaMismatchError` that makes the member unusable, like damage. Kernel identity checks always apply. A snapshot verifies (and appears in listings) only when every database member and every document does; a per-database restore candidate still needs only its own member. A manifest whose `created_at` is not canonical is malformed (no snapshot), and a snapshot health record without a canonical `observed_at` reads as degraded (`tests/core/database/test_snapshots.py`).

A registered database without its file is never skipped by a snapshot, because retention would eventually prune the last copies that hold it. Decision: `create_data_snapshot` fails the attempt and records degraded snapshot health with the next step, `create_update_snapshot` and the CLI updater refuse with the same text, and status reports it per database (`missing_database_reason`; a file that exists but cannot be checked is reported as such, never as missing): a core database is restored on the next start (or by `vbot data-store snapshot restore <id> --database <name> --yes`); an Extension database is restored on its Extension's next open, and when the Extension was removed the operator releases it with `vbot data-store unregister <name> --yes` (RPC `data_store.unregister`).

## Staging

`_staging.py` is the one home of these names: a snapshot, a restore and a database creation build their result under a dot name beside its final place and publish it with one atomic rename: `snapshots/.<snapshot-id>.<pid>.partial/`, `.<file>.restore.<32 hex>.tmp` beside a canonical database or snapshot document, and `.<file>.<32 hex>.creating` (plus SQLite sidecars) beside a canonical database. Every such attempt holds the operation lock while its staging exists and removes it when it fails, so under the lock any staging found belongs to a killed attempt. `remove_interrupted_staging` removes it at every Runtime start, the verification start of an update included (a busy lock logs a WARNING and leaves it for the next start), and every snapshot attempt does the same before it checks free space, so killed copies give way before any verified snapshot. The names are a persisted format: a newer vBot must still recognize what an older one left. A disposable database is created the same way without the lock, but never at a canonical location, the only place creation staging is removed from (`tests/core/database/test_snapshots.py`, `tests/core/runtime/test_runtime_lifecycle.py`).

## Unregister and retire

Both operations recheck the maintenance guard while holding the operation lock: a restore that fails while they wait must leave its files and registrations untouched.

- `unregister_database` accepts only Extension names (`ext.<extension>.<name>`; a core name or an unregistered one is `ValueError`), refuses during maintenance, while the operation lock is busy, or while this process holds a connection to the file, then moves the bundle to quarantine (none when the file is gone) and drops the marker entry. It writes no incident. Earlier snapshots keep their copy, and a restore of that member registers it again. `Runtime.unregister_extension_database(name)` releases an Extension database through the one Extension database coordinator (`ExtensionDatabases.unregister`, `extensions/databases.md` -> Removal and unregister); the local CLI fallback calls it directly (`cli/data-store.md`).
- `retire_core_databases` is the core-name counterpart, called only by normal Runtime startup with `core/runtime/databases.RETIRED_CANONICAL_DATABASES` (an update's verification start skips it, because the rollback needs every registration unchanged; a failure logs a WARNING and retries at the next start). It refuses Extension names, skips names that are not registered, and has the same maintenance, lock and open-connection refusals; each registered bundle moves to quarantine and leaves the marker, logged as one INFO `Retired database` line. Covered by `tests/core/database/test_recovery.py` and `tests/core/runtime/test_runtime_lifecycle.py`.

## JSON document set restore

The JSON document set restores only on request: an operator restore that selects it, or the update rollback; corruption auto-restore never touches documents. A set restore makes the in-scope documents exactly the snapshot's: differing or missing ones are installed from verified staged copies, and documents the snapshot does not hold (created after it) are removed. The kinds in `core.json_documents.DOCUMENTS_KEPT_BY_RESTORES` (today only the Secret Store `secrets.json`) are the exception: `plan_document_restore` neither installs nor removes them, so an operator set restore and the update rollback keep the current store, present or absent, and a snapshot from before the plaintext conversion never drops the converted credentials (`secrets.md`). Every replaced or removed document first moves to one quarantine batch (all-or-rollback); unchanged documents are not touched. Apply order under the guard and lock: database members, then retirement, then documents.

## Update rollback

`restore_update_snapshot` refuses with `UpdateRollbackRefusedError` and changes nothing unless: no maintenance guard exists; the manifest reason names this operation (`update <operation-id>`); its member and document hashes equal the ones recorded at capture; every member's `database_id` is still the registered one; and a `check_only` pass of the complete restore succeeds. It keeps one operation lock across those checks and the complete restore, so another operation cannot enter maintenance after automatic rollback was admitted. It then restores every member and the document set and retires databases registered after the snapshot. Capture compares a stamp (marker hash, size and mtime of each registered database file and its `-wal`/`-journal`, document hashes) before and after; an empty journal counts as absent, because a read-only open of a WAL database leaves an empty `-wal`.

Residual risk: another vBot server or offline tool that writes to the data directory and exits while the candidate runs is indistinguishable from the candidate, so the rollback discards its writes too. The stamp catches writes before the candidate starts; the updater's server-claim check (`core.utils.server_control.live_server_ports`) catches a server still running at rollback time. An interrupted rollback keeps the maintenance guard, and the automatic path never resumes it: an operator repeats it with `vbot data-store snapshot restore <id> --all --yes`.

## Status

`data_store_status` returns one overall state (`maintenance` > `unavailable` > `recovered_with_incident` > `degraded` > `snapshot_degraded` > `healthy`), per-database entries with owner health, snapshot inventory and unacknowledged incidents, plus `config_backups` (`count`, `latest`, `unreadable`, `reason`), which does not affect the overall state. A registered database not open here is checked read-only by identity and generation, plus owner health only when a spec with `health` is supplied, so Extension databases report identity and generation only. `secret_store` is the caller's Secret Store projection (`core.secrets.secret_store_health`; this module never opens the store): it is returned as `secrets`, and its `degraded_reason` (unavailable store, damaged entries, ignored plaintext credential files, plaintext copies in the document quarantine, a quarantined store while `secrets.json` is missing) makes the state `degraded` with the reason prefixed `secrets: `. Routine owner health is a cheap operational report, not a full integrity scan; Session search coverage is explicitly requested and its last result is distinguished from lifecycle status (`sessions/search.md`). A data directory without a marker is `unavailable`: an existing one with the `DatabaseConversionRequiredError` text, a missing one with the note that starting vBot creates it. It never mutates the data directory.

## Logging

`vbot.database`, policy in `logging.md`: an open whose schema reconcile changed something logs one INFO `Evolved database schema` line (database, path, changes); a published data snapshot logs INFO (snapshot id, database and document counts, reason, and `held_ms`, `waited_changes` and `attempts`: how long held changes were frozen over all attempts, how many waited, and how many attempts the capture needed). Snapshot health logs WARNING when it becomes degraded or its reason changes, a repeated identical failure only DEBUG, and the first healthy attempt afterwards INFO; the transition compares against the durable `health.json`, so it spans restarts. An automatic restore, and the completion of an interrupted one, logs ERROR with database, snapshot, quarantine path and cause, because data written after the snapshot may be lost; a failed automatic restore logs ERROR with its traceback, since the opener only learns that nothing was restored. An operator or update-rollback restore logs one INFO line (snapshot, databases, documents, retired, registered, cause), unregister one INFO line with its quarantine path. Removing staging of killed attempts logs one INFO line naming the removed paths, and a WARNING for each one that cannot be listed or removed. Quarantine has no line of its own: the restore or unregister line names it, and the incident keeps it. Configuration backup lines: `config-backups.md` -> Logging.
