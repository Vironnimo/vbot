# Snapshot consistency

How an online data snapshot equals a crash at one instant: the capture order, why a whole-snapshot restore is crash-equivalent, the member freeze and the snapshot barrier in detail, and the limits of the guarantee. The rules every owner follows are in `../database.md` -> Snapshot consistency.

## Capture order

An online snapshot shows exactly what a crash at one instant would have left - the start of the anchor copy - and holds every compound mutation whole. `create_data_snapshot` runs `capture_members` after taking the operation lock and verifies the copies after it returns. The capture order:

1. Barrier: with a `barrier`, the capture takes it exclusively. It waits until no compound mutation is in flight (`capture_wait_seconds`, 30 s), and a compound mutation arriving meanwhile waits until step 4.
2. Freeze: it stops admitting held changes of the data directory - writes of held databases and every write, removal or move of a snapshot document - and waits until those in flight have finished (`MEMBER_DRAIN_WAIT_SECONDS`, 10 s). That is the freeze instant.
3. Copies: the held databases in name order, then the JSON document set, then the anchor. Anchor and trailing writes never wait, so Runs keep committing.
4. Thaw: held changes and compound mutations enter again; then the trailing databases are copied.

API (`snapshot_barrier.py`): `SnapshotBarrier(*, capture_wait_seconds=30.0)` with `compound_mutation()` (context manager, blocks while a capture copies: worker threads only), `compound_mutation_async()` (the same for the Event Loop, waits without blocking it) and `capture(*, cancelled=None)` (yields `False` when cancelled while waiting, raises `DatabaseUnavailableError` when no quiet moment comes within the wait budget). The member freeze in the same module: `member_change(data_dir, *, held=True, wait=True)` (context manager admitting one change of a member of the resolved `data_dir`; `Database.write` and `core.json_documents.document_change` enter it, owners never call it directly; `wait=False` raises `MemberFrozenError` where the change would wait), `capture_members(data_dir, databases, *, copy_database, copy_documents, discard_copies, barrier=None, cancelled=None, drain_seconds=MEMBER_DRAIN_WAIT_SECONDS) -> MemberCapture | None` (the capture order of `create_data_snapshot`; `databases` maps each member name to its spec or `None`, which counts as held; more than one anchor is `ValueError`; `discard_copies` removes a disturbed attempt's copies before the next), `MemberCapture(held_seconds, waited_changes, attempts)`, `MEMBER_DRAIN_WAIT_SECONDS` (10 s), `CAPTURE_ATTEMPTS` (3). A configuration backup runs `capture_members` with no database (`config-backups.md`).

## Crash equivalence

Why restoring a whole snapshot is crash-equivalent: no held member changes between the freeze instant and the anchor copy, and the anchor copy is one `VACUUM INTO` read transaction whose view is fixed when it starts (in rollback-journal mode SQLite's read lock prevents commits during it). Every held member, every document and the anchor therefore show the data at the start of the anchor copy, and a crash then would have left the same files, since canonical commits are durable. A compound mutation never overlaps the freeze, because step 1 drains and blocks them for the whole capture, so the document moves and removals inside one need no document gate. A trailing copy may be newer than that instant: harmless for `model_usage`, whose rows are keyed by `usage_call_id` and whose recorder replays the whole Session history for every new Session handle (`import_session_history`).

Crash equivalence makes every crash window of a multi-step change outside a compound mutation capturable, so such a change must leave only states that repair themselves or strand no data. Examples: creating a Session and pointing an Agent's current pointer at it (`/handoff`, `session.create` with `make_current`, a `chat.send`/`chat.stream` for a new Session) leaves at worst a dangling pointer, which the next read clears (the Agent then opens a new conversation; no Session is created for it); for Channel create/delete (`channel.json` plus its `channels.db` rows), startup adoption registers a configured Channel whose row is missing, and rows a deleted Channel left behind stay unused until a re-created id resets them; a Telegram chat migration bridges the conversation before it persists the allowlist (`channels/telegram.md`); Swarm Resume records every participant Session again, including one a failed or interrupted Start created without recording it (`extensions/swarm.md`).

## Freeze admission

The freeze state is process-wide and keyed by the resolved data directory (`../database.md` -> Process-wide state): every owner, standalone store and offline tool of the process meets the same freeze and none can miss it by not being handed an object (`write_json_document` callers have no injected object a per-Runtime freeze could travel through). `Database.write` and canonical open (writer setup, schema reconciliation, migrations and `after_open`) gate changes of every database registered in a data directory (offline and disposable handles are never gated), `core.json_documents.write_json_document` gates every document write, and owners wrap document removals and moves outside compound mutations in `document_change` (`../json-documents.md` -> Writing).

A held change never waits where waiting could stall or deadlock: on an Event Loop thread, and on a thread already inside a change of the same data directory (a document written inside a database transaction, a held write inside a Session write). Such a change enters at once; entering after the freeze instant would make the copies disagree, so the capture discards its copies and starts over from step 1, at most `CAPTURE_ATTEMPTS` (3) attempts in all. A waiting change keeps every lock its thread holds, so an owner whose lock Event Loop code takes admits its change before taking the lock (`document_change` first, then the lock), and a change it makes under that lock without such an admission - a read that repairs what it finds - passes `document_change(path, wait=False)`: where it would wait it raises `MemberFrozenError`, and the owner gives the lock up, admits with waiting and repeats the read (`AgentStore`, `agent.md`).

Failures are `DatabaseUnavailableError` and record degraded snapshot health: a drain that does not finish in time ("a data change was still in progress; retry the snapshot once it has finished"), a change during the freeze of every attempt ("the data changed in a way the snapshot cannot hold while it was taken; retry the snapshot"), and a second capture of the same directory in this process ("another data snapshot of this directory is running").

## Freeze cost

Held writes pause from the freeze instant until the anchor copy ends (`held_ms` in the INFO line). That time is dominated by copying `sessions.db` and grows with its size; measured on an SSD with one small held database: about 55-90 ms up to 10 MB, 230 ms at 50 MB, 0.8 s at 200 MB and 2.1 s at 500 MB, roughly 4 ms per MB. A WAL Session write can commit during the copy; rollback-journal commits wait within their contention budget. Async callers of a held database pause on its worker pool, never on the Event Loop.

## Barrier holders

`Runtime.snapshot_barrier` is created with the Runtime and kept across its restarts, so a restart keeps coordinating with a capture still copying; a store constructed without one gets a private barrier no snapshot uses. It is injected into `AgentStore`, `ProjectStore`, `CommandDispatcher`, the archive services (`ArchiveServices`), the Identity Agent rename services (`AgentRenameServices`) and the configuration backup schedule (`ConfigBackupSchedule`); `data_store.snapshot_create` passes it to `create_data_snapshot`.

A compound mutation arriving while a capture only waits still enters, so nested entries (the Identity Agent rename around `AgentStore.rename`, a Project archive around `ProjectStore.archive_files`) cannot deadlock; the price is that steady overlapping mutations can starve a capture, which then fails after `capture_wait_seconds` with degraded snapshot health. Holders never wait for what a capture holds: they enter the barrier before any store lock and outside database transactions, never take the operation lock, and stay short. The blocking `compound_mutation()` belongs off the Event Loop, since a capture can hold it for a whole copy; the one entry on the loop is `ensure_bootstrap` in Runtime bootstrap, which runs before the server serves any request and so never meets a capture. A thread inside a change must not wait for a held change on another thread: the freeze could not finish before its budget ends. Offline snapshots (`create_update_snapshot`, the CLI updater with the server stopped) pass no barrier and find no change in flight.

Covered compound mutations: `AgentStore.create`/`rename`/`revert_rename`/`recover_rename`/`archive_files`/`restore_files`, the whole Identity Agent rename with its reference retargeting and revert (`core/runtime/_agent_rename.py`), `ProjectStore.archive_files`/`restore_files`, the archive service's Agent and Project archive and restore (the Project archive with the reset of the Agents whose default Project it is; `archive.md`), `/agent` takeover (Session move plus both current-Session pointers) and a Session archive (`session.delete`: archive plus current-pointer re-aim). An archive purge holds none: each Session delete is its own transaction, and a `purging` entry continues where it stopped. A new owner operation that changes the anchor and a held member as one unit enters the barrier too (`tests/core/database/test_snapshots.py`, `tests/server/rpc/test_agent_methods_lifecycle.py`).

## Limits of the guarantee

- A held change on the Event Loop disturbs an overlapping capture attempt instead of waiting, which costs a retry (Freeze admission). Channel state, Cron job edits and Project edits write off the loop. Writers still on the loop while serving, because their owner has no off-loop write path yet: Settings (`settings.json` from the Settings, task-Model and Provider Connection RPCs; every loop Settings read takes the lock these writes hold, so the writers can only move off the loop together with those reads), Calendar events (`calendar/events.json` from RPC and the Calendar Tool), Bootstrap jobs (`bootstrap/jobs.json` from RPC and the activation task), OAuth tokens (refresh, device-flow login and disconnect share one lock, so they move together), Terminal groups and launch history, an Agent read-time repair on a loop reader, the first Cron or Calendar load of a `--test-instance` process that creates a missing document, and Extensions that call the synchronous `Database.write` on the loop. Startup writers on the loop (`ensure_bootstrap`, Channel adoption, retiring removed core databases) never meet a capture: online captures come only from `data_store.snapshot_create`, which the server serves after startup.
- A worker thread waiting at the gate keeps the locks it holds. `AgentStore` and `ProjectStore`, whose locks Event Loop reads take, admit every change before the lock (Freeze admission), and the other owner locks held across a document write (`StorageManager`'s Settings lock, `TokenStore`'s mutation lock) are taken only on the Event Loop, where a change never waits; a writer of theirs moved to a worker needs the same admission-first order. Database work queued behind pool workers that wait at the gate still waits for the capture.
- Only this process's changes are frozen; another process writing the data directory is not covered, and an unopened database is copied from its file.
- Restoring single members mixes instants by design: a per-database restore (`--database <name>`) and the automatic restore of a missing or corrupt database each install one member, the newest verified snapshot member with the same `database_id`, beside newer live members and documents, and automatic restore never touches documents. Only a restore of every member together with the document set reproduces the snapshot's instant.

Tests: `tests/core/database/test_snapshots.py` covers an online snapshot while another thread keeps writing, the snapshot barrier, the member freeze (capture order; a held write waits until the anchor is copied while an anchor write proceeds; a document change nested in an in-flight write never waits; one admitted with `wait=False` is refused) and Event Loop writes disturbing a capture, which is retried a bounded number of times.
